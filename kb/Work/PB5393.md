# PB5393 - ENABLE INPUT and DISABLE INPUT never answer status 80: when a queue structure names a known level already in the requested state and an unknown level below it, SetPath answers 20 as soon as FindQueue fails and never asks the 15 condition of the known prefix

**Sites:**

- `src/WiseOwl.Cobol.Runtime/Communication/MessageStoreState.cs#QueuePathsAre` (new) and `FindQueuePrefix` (new)
- `src/WiseOwl.Cobol.Runtime/Communication/MessageDefinitions.cs#Resolve` (new; `FindQueue` and `FindQueuePrefix` share it)
- `src/WiseOwl.Cobol.Runtime/Communication/MessageControlSession.cs#SetPath` (the `CommunicationPath.Input` arm: `state.FindQueue(area.QueuePath()) is { } queue ? SetPaths(...) : Unknown`)
- `src/WiseOwl.Cobol.Runtime/Communication/MessageStoreState.cs#FindQueue` and `src/WiseOwl.Cobol.Runtime/Communication/MessageDefinitions.cs#FindQueue` (each resolves the whole path or nothing, so the known prefix is lost)
- `docs/rearchitecture/DESIGN-communication-facility.md#6. The message control system` (the paragraph that begins "**Logical paths.**", at line 362 on origin/main 3798495df1): "Status 80 appears only for destinations, the one place one statement names several." An INPUT statement names up to four queue levels, so the sentence is wrong and the fix corrects it in the same change.

**Mechanism.** `SetPath`'s Input arm asks `FindQueue` for the whole queue path. When any level is unknown the answer is null and the arm returns 20 at once. The known prefix is never examined, so the case in which it is already wholly in the requested state (condition 15) and a level below it is unknown (condition 20) reports 20 alone. The compiler judges that prefix correctly on its own: the same run answers 15 for `ENABLE INPUT` of Q1 when Q1 is already enabled.

**Inventory.** `work.py check` refuses a 1985 rule id in `inventory_rows` (kb/Work PB5094, open), so `inventory_rows` is empty and the rows this note claims are the rule ids below.

**Rules (every citation checked with `scripts/spec/cite.py --check`).**

- `1985-GR-XIV.2.2.4-34` (recorded CONFORMS before this note; re-recorded PARTIAL naming this note) - `§1985:XIV.2.2.4 GR34`: "The actual association between the content of the data item referenced by data-name-6 and the status condition itself is defined in table 1". `§1985:XIV.2.2.5`: "An 'X' on a line in a statement column indicates that the associated status key value shown for that line is possible for that statement". Table 1 marks 80 possible for the ENABLE INPUT and DISABLE INPUT columns (and OUTPUT), not for INPUT TERMINAL or I-O TERMINAL: "A combination of at least two status key conditions 10, 15, and 20 have occurred" (`§1985:XIV.2.2.5 Table 1`). The two conditions are "Symbolic source, or one or more queues or destinations already disabled/enabled" (15) and "One or more queues or subqueues unknown. No action taken" (20), both `§1985:XIV.2.2.5 Table 1`.
- Appendix B states the case outright: "The new communication status key value of 80 is also returned in the case of an ENABLE or DISABLE statement where new communication status key condition 15 and communication status key condition 20 both apply" (`§1985:B.2.2`), with condition 15 defined as "If, at the time a DISABLE or ENABLE statement is executed, the source or a queue or a destination referenced is already disabled or enabled respectively" (`§1985:B.2.2`).
- `1985-GR-XIV.3.2.4-1` and `1985-GR-XIV.3.3.4-1` (the status key "indicates this condition"): "No action is taken when a DISABLE statement is executed which specifies a source or destination which is already disconnected, except that the value in the status key data item indicates this condition" (`§1985:XIV.3.2.4 GR1`); "No action is taken when an ENABLE statement is executed which specifies a source or destination which is already connected, except that the value in the status key data item indicates this condition" (`§1985:XIV.3.3.4 GR1`).

**Repro.** `E:/COBOL-coord/scratch/held-85/set4/p/p1.cob` with `E:/COBOL-coord/scratch/coderead-85/out-reread2/refute-rr-05/mcs-r1.json` (queue Q1 with sub-queues S1 and S2, queue Q2) copied into a fresh directory as `mcs.json`: `pwsh -NoProfile -File E:/COBOL-coord/scratch/held-85/set4/p/run.ps1 -src <p1.cob> -mcs <mcs-r1.json>`, which runs `cobol.exe --std 85 --source-format fixed --run p1.cob` with `WISEOWL_COBOL_MCS` set to that directory. On a fresh store every queue is enabled. The program runs `ENABLE INPUT` of Q1/SX, Q1/S1, Q1 and QZ, then `DISABLE INPUT` of Q1, Q1/SX, Q1/S2/S9 and Q1/S2, displaying the status key after each.

**Observed (the pinned compiler of `E:/COBOL-wt/coderead85-tree-b`, rerun 2026-11-12):**

```
ENA Q1/SX fresh 20
ENA Q1/S1 fresh 15
ENA Q1 fresh    15
ENA QZ          20
DIS Q1          00
DIS Q1/SX       20
DIS Q1/S2/S9    20
DIS Q1/S2       15
[exit 0]
```

**Expected (from the 1985 text).** `ENA Q1/SX fresh` 80 (Q1 already enabled, SX unknown); `DIS Q1/SX` 80 (Q1 already disabled, SX unknown); `DIS Q1/S2/S9` 80 (Q1/S2 already disabled, S9 unknown). Every other line is right as observed. Each 80 takes no action, as each 20 does now, so no path changes under either answer; only the status key is wrong, and the program is told nothing is wrong with the known part of the structure.

**Fix direction (root cause, CLAUDE.md rule 4).** Resolve the queue path level by level so the deepest known level is available when a lower level is unknown. When the structure is unknown below a known prefix, answer 80 if the prefix structure is already wholly in the requested state, else 20; take no action either way. Correct the design doc's sentence on status 80 in the same change, and add the 80 cases to the witness of `1985-GR-XIV.2.2.4-34`.
