# PB4681 - generate.py's timeout reds whole populations on a busy host

**Sites:** `tests/_shared/SuiteManifest.cs#Generator`, `tests/_shared/ObservationBudget.cs#UnitMs`

**Witness.** Wave 20261868 group D, gate run 000001 was RED: its report says generate.py "timed out twice at 120 s with
the host 100 % busy (HarnessNonObservationException), so ten Unit classes and the Conformance population count failed".
The re-gate, run 000002-20261104T234322Z, was GREEN with no code change. One witness so far; its rate is not measured.

**Mechanism, not yet confirmed.** `SuiteManifest` runs the one manifest generator once per test process, so one timeout
fails every class that reads the manifest. The 120 s figure matches `ObservationBudget.UnitMs`, whose remarks justify it
as a multiple of the cost of compiling and running ONE program. The generator reads every case header, so its cost grows
with the suite, and that multiple does not describe it. The implementer should confirm which budget the generator's start
actually takes and measure the generator alone and under gate load.

**Related, different mechanism.** PB4398 is about the evidence a non-observation report drops. It would help diagnose this
red but would not stop it.

**Not done here.** No fix is proposed: "re-gate past it" is the thing the owner's flake rule forbids, so the fix belongs at
the budget or at the generator's cost, chosen from the measurement.
