# PB573

## Mechanism
the ALIGNED clause has NO grammar rule anywhere in the front end - `genericClause` swallows it as vendor noise - so §13.18.1.4 GR1's byte-boundary alignment and the §8.5.1.6.3 arm it scopes are accepted and inert

### The refutation this note is written from
Row `GR-13.18.60.4-5` was adjudicated CONFORMS and OVERTURNED to `PARTIAL` by the refuter. Its reasoning, verbatim:

> REFUTED -> PARTIAL. GR5's third sentence makes 8.5.1.6.3 the WHOLE of the alignment law for a USAGE BIT item, and 8.5.1.6.3's OPENING SENTENCE scopes its default placement rules to 'when neither a SYNCHRONIZED clause nor an ALIGNED clause is specified'. Two conditions displace the default arm; the adjudicator verified the default arm and neither condition. SYNCHRONIZED IS DISCHARGED - I checked and it survives: 8.5.1.6.3's own filler list makes it implementor latitude ('As defined by the implementor for a bit data item described with the SYNCHRONIZED clause. The implementor defines the positioning rules associated with any filler bit positions'), docs/CONFORMANCE.md DOC-A.1-195 defines it as zero bit positions and MEASURES it (conformance:2002/l1_byte_length_implicit_filler, the SBIT=1 leg, which is exactly two same-level 3-bit USAGE BIT siblings with only the second SYNCHRONIZED). ALIGNED IS NOT DISCHARGED, and it is not latitude. 13.18.1.4 GR1 is mandatory: 'An ALIGNED clause causes the subject of the entry to be aligned on the first bit of the first available byte boundary. Implicit filler bits may be generated to complete the assignment of bits as described in 8.5.1.6.3' - the two sections are interlocked, 8.5.1.6.3 names ALIGNED as a scope condition and 13.18.1.4 GR1 points back into 8.5.1.6.3 for its filler. THE CLAUSE DOES NOT EXIST IN THE COMPILER: zero hits for ALIGNED across all twelve .g4 files and zero in the binder/model. BitLayout's placement predicate is 'IsBitItem(c) && prev is not null && IsBitItem(prev) && prev.Level == c.Level' - it reads only kind and level and has NO ALIGNED (or SYNCHRONIZED) input at all, so it applies 8.5.1.6.3's default arm to items the standard puts outside that arm's scope. The result is a silently wrong storage layout, not a rejection. Everything else in 8.5.1.6.3 I re-measured and it holds, so this is PARTIAL, not DIVERGES: the mixed bit/char group's byte alignment, group image and reference modification all agree (the GR8 national two-width split does NOT exist for bit - ImageWidth and ByteWidth both route through BitLayout.Characters(BitLayout.ExtentBits)); bit GROUP items work including the 'bit group item immediately following a bit group item of the same level' arm; the level-1/77 rule and its NOTE hold; a bit leaf under OCCURS packs contiguously; the 2002 edition gate is right. The golden conformance:2023/pb43_usage_bit_occupies_bits is genuinely spec-derived (its MIX / ADJ / SPLIT legs each quote and derive from 8.5.1.6.3) and registered at manifest.json line 163 - but it pins only the default arm, and cannot pin the ALIGNED arm because the clause is not implemented. Citation re-run: cite.py --check 13.18.60.4 -> OK 13.18.60.4 5); cite.py-equivalent read of 13.18.1.4 GR1 and 8.5.1.6.3 direct from specs/ISO_COBOL.md lines 15413 and 7082-7108.

### Inventory row `GR-13.18.60.4-5` (PARTIAL)
THREE CLAIMS, EACH MEASURED, AND THE THIRD MEASURED AGAINST ITS OWN DISCRIMINATOR. (1) "bits shall be used to represent a boolean data item" - probe q8 (--std 2023) moves B"10000001" into a `PIC 1(8) USAGE BIT` leaf inside a group and reads the group's SINGLE image byte with FUNCTION ORD: 0x81, i.e. the eight boolean positions packed into one byte high-order first. (2) "A data item described with USAGE BIT is a bit data item" - BitLayout.IsBitLeaf is that predicate (elementary, category Boolean, Usage.Bit) and IsBitItem widens it to a GROUP-USAGE BIT group per 13.18.29.4 GR1a; SR5's picture screen (adjudicated CONFORMS in part 1) keeps non-boolean pictures out. (3) "The alignment ... is specified in 8.5.1.6.3" - the four placement rules are implemented as a CURSOR WALK rather than a width sum, and the walk was exercised on both branches: probe q6 shows two same-level `PIC 1(4) USAGE BIT` items SHARING one byte (FUNCTION BYTE-LENGTH of the group is 1) while each keeps its own value (1010 and 0101 read back distinct), and `1(3) BIT / X(1) / 1(3) BIT` occupies 3 bytes because a bit item that does not immediately follow a same-level bit item restarts at the first bit position of the next available byte. An ELEMENTARY level-01 `PIC 1(4) USAGE BIT` reports BYTE-LENGTH 1 and LENGTH 4 - the 8.5.1.6.3 NOTE excludes a level-1 elementary item from the trailing-filler rule, and WidthBits keeps its exact bit count.
