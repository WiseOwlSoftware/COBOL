# PB865 — OPEN — a clause with no restriction rule and no effect

Source: the `PB523` implementer report, item C, which recorded it rather than assuming it — the right call, and
the reason this is an adjudication.

## The facts, on this tree

`DataBinder.BindLinageClause` and `StatementValidation` place no organization restriction on the clause;
`FileRegistry.WriteAnyOrg` passes the `LinagePage` only to `SequentialConnector` — `RelativeConnector.Write` and
`IndexedConnector.Write` take no page at all. So the clause binds, `LINAGE-COUNTER` is generated and can be
referenced, and it never moves.

## What the standard does and does not say

§13.18.34 is the LINAGE clause; §14.9.51.4's ADVANCING and end-of-page rules are print-file rules
(`cite.py --find "LINAGE clause is specified in the file description entry"` -> `§14.9.51.4 26)`), and §13.4.5's
prose speaks of the file description entry **for a sequential file**. The transcription carries NO syntax rule
forbidding the clause on a relative or indexed FD.

## The two readings

1. **It is forbidden and the rule is implicit** (the clause belongs to sequential organization by the whole
   clause's framing). Then the compiler owes a diagnostic, and the row is an under-rejection.
2. **It is admitted and inert** — in which case `LINAGE-COUNTER` on such a file has a defined value the compiler
   must produce, and today it produces a stale zero.

Either way today's behaviour is wrong; which fix applies depends on the reading.

## Owner question

Does a LINAGE clause on a RELATIVE or INDEXED file description entry draw a diagnostic, or does it define a
LINAGE-COUNTER that the connector must maintain?
