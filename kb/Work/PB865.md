# PB865 — LANDED (CONFORMS, w1033) — a clause with no restriction rule and no effect

Source: the `PB523` implementer report, item C, which recorded it rather than assuming it — the right call, and
the reason this is an adjudication.

## The facts, on this tree

`DataBinder.BindLinageClause` and `StatementValidation` place no organization restriction on the clause;
`FileRegistry.WriteAnyOrg` passes the `LinagePage` only to `SequentialConnector` — `RelativeConnector.Write` and
`IndexedConnector.Write` take no page at all. So the clause binds, `LINAGE-COUNTER` is generated and can be
referenced, and it never moves.

## What the standard does and does not say

§13.18.34 is the LINAGE clause; §14.9.51.4's ADVANCING and end-of-page rules are print-file rules
(`cite.py --find "LINAGE clause is specified in the file description entry"` -> `§14.9.51.4 26)`), and §13.4.5's
prose speaks of the file description entry **for a sequential file**. The transcription carries NO syntax rule
forbidding the clause on a relative or indexed FD.

## The two readings

1. **It is forbidden and the rule is implicit** (the clause belongs to sequential organization by the whole
   clause's framing). Then the compiler owes a diagnostic, and the row is an under-rejection.
2. **It is admitted and inert** — in which case `LINAGE-COUNTER` on such a file has a defined value the compiler
   must produce, and today it produces a stale zero.

Either way today's behaviour is wrong; which fix applies depends on the reading.

## Owner question

Does a LINAGE clause on a RELATIVE or INDEXED file description entry draw a diagnostic, or does it define a
LINAGE-COUNTER that the connector must maintain?

## Code sites

`src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindLinageClause`;
`src/Cobol.Net.Runtime/IO/FileRegistry.cs#WriteAnyOrg`; `RelativeConnector.Write`, `IndexedConnector.Write`.

## Sibling sweep whoever decides owes

* The other FD clauses with an implied organization: CODE-SET, BLOCK CONTAINS, the REPORT clause, PADDING
  CHARACTER. Each one asks this same question and the answer should be one table, not four `if`s.

**Outcome: CONFORMS, NO DEFECT. Closed by the adjudication; no code change.** The suspected defect was real when filed (2026-09-13) and was fixed
by `PB1238` (commit `3b503f61f`, an ancestor of the pin; its cluster lists PB865). `wrong_answer` and `silent` are cleared. The note's premise

**Spec (cite.py --check OK; the refuter re-ran all nine and added more).**
- `§13.4.5.2` prints three FD formats (PDF pages 372-373, rendered by both files). Format 1 (sequential) has `[ linage-clause ]`; Format 2
  (relative-or-indexed) has only IS EXTERNAL, IS GLOBAL, BLOCK CONTAINS, record-clause; Format 3 (report) has no linage-clause.
- `§13.4.5.3 7)`: "Format 2 is the file description entry for a relative file or an indexed file"; `5)` Format 1 sequential; `8)` Format 3 report;
  `§13.4.5.3 4)` a line sequential file is a sequential file (Format 1), so LINAGE is legal on it; `§9.1.22` report file.
- `§13.18.34.4 GR7`: a LINAGE-COUNTER is generated by the presence of a LINAGE clause, so none exists for a Format 2 file.
- `§4.2.2` requires a warning mechanism for general-format violations (the refuter notes it does not by itself force an error; a documented
  extension under `§4.2.10` would also conform, but the project documents none); `§A.4.11 10)` lists LINAGE with the Report Writer optional
  elements but adds nothing to a general format, so the report-FD refusal stands.
