# PB4596 — relative-random-update-moves-position: RELATIVE file, DYNAMIC access: a successful random DELETE, REWRITE or WRITE moves the READ NEXT position

Filed 2026-11-04 from the independent review of fuzz night 10's batch-1 report `n10-relative-delete-rewrite` (the PB4539 status-23 ticket). Its reviewer and its drafter each noticed, while probing positions, that a SUCCESSFUL random DELETE or REWRITE changes which record the next READ NEXT returns; both kept it out of that ticket as a separate defect. The vetting added the random WRITE, which has the same mechanism. Upstream status `unreported`: the owner has not yet decided to report it. The probe programs are local, outside any git tree (`~/gc-notes/PB4596/relpos.cob` and `relwr.cob` under WSL): the minimal program below is the repro.

## Summary

For a RELATIVE file in DYNAMIC access, a READ NEXT after a successful random DELETE, REWRITE or WRITE continues from the slot the update named, not from the record last read. After `READ` of record 1 and `DELETE` of record 3, `READ NEXT` returns R005 (the first record after slot 3) where the standard requires R002 (the first record after record 1). After `REWRITE` of record 5 it returns R006, and after a random `WRITE` of record 5 it returns R006; both should return R002. Every statement returns status 00, so the program silently processes the wrong records. A READ NEXT loop that updates other records by key re-reads records as well as skipping them: in the drafter's `rwnext`, a successful REWRITE of record 3 followed by READ NEXT returns R004 a second time, where ISO gives end of file (status 10); and READ 5, DELETE 2, READ NEXT returns R003, where ISO gives R006. Class: wrong output. This is distinct from PB4539 (DELETE and REWRITE of an empty slot return 00, not 23) and from PB4530 (consecutive READ PREVIOUS skip records).

## Minimal test case

Fixed reference format. Records 1, 2, 3, 5 and 6 are written; each I-O pass reads record 1, updates another record by key, then reads next.

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. RELPOS.
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
           SELECT F ASSIGN TO "relpos.dat"
               ORGANIZATION IS RELATIVE
               ACCESS MODE IS DYNAMIC
               RELATIVE KEY IS RK
               FILE STATUS IS FS.
       DATA DIVISION.
       FILE SECTION.
       FD F.
       01 REC PIC X(4).
       WORKING-STORAGE SECTION.
       01 RK PIC 9(2).
       01 FS PIC XX.
       PROCEDURE DIVISION.
           OPEN OUTPUT F
           MOVE 1 TO RK MOVE "R001" TO REC WRITE REC
           MOVE 2 TO RK MOVE "R002" TO REC WRITE REC
           MOVE 3 TO RK MOVE "R003" TO REC WRITE REC
           MOVE 5 TO RK MOVE "R005" TO REC WRITE REC
           MOVE 6 TO RK MOVE "R006" TO REC WRITE REC
           CLOSE F
           OPEN I-O F
           MOVE 1 TO RK READ F
           DISPLAY "READ 1      " FS " " REC
           MOVE 3 TO RK DELETE F RECORD
           DISPLAY "DELETE 3    " FS
           READ F NEXT
           DISPLAY "READ NEXT   " FS " " REC " RK " RK
           CLOSE F
           OPEN I-O F
           MOVE 1 TO RK READ F
           DISPLAY "READ 1      " FS " " REC
           MOVE 5 TO RK MOVE "N005" TO REC REWRITE REC
           DISPLAY "REWRITE 5   " FS
           READ F NEXT
           DISPLAY "READ NEXT   " FS " " REC " RK " RK
           CLOSE F
           STOP RUN.
```

The WRITE variant (`relwr.cob`) writes records 1, 2, 6 and 7, then in I-O mode reads record 1, writes record 5 by key (`MOVE 5 TO RK MOVE "N005" TO REC WRITE REC`, status 00) and reads next.

## Environment

`cobc (GnuCOBOL) 3.2.0` and 3.3-dev r5751 (`cobc (GnuCOBOL) 3.3-dev.0`, tarstamp 2026-10-29, through the `cobc-dev` and `run-dev` wrappers in `~/opt/gnucobol-3.3-dev/bin`), WSL2 Ubuntu x86_64. Compiled with `cobc -x -std=cobol2014 relpos.cob -o relpos` and run as `./relpos`, from a directory with no `relpos.dat`. Repeated with `-std=cobol2002`, `-std=cobol85` and `-std=default`.

## Observed result

Every compile exits 0 with no cobc diagnostic (3.2.0's gcc step prints its two `_FORTIFY_SOURCE redefined` lines on stderr); every run exits 0. Both versions, all four dialects, print:

```text
READ 1      00 R001
DELETE 3    00
READ NEXT   00 R005 RK 05
READ 1      00 R001
REWRITE 5   00
READ NEXT   00 R006 RK 06
```

The WRITE variant prints `READ 1 00 R001`, `WRITE 5 00`, `READ NEXT 00 R006 RK 06` on both versions and all four dialects.

## Expected result (per ISO)

Both READ NEXT lines print `00 R002 RK 02`, and so does the WRITE variant's.

- §14.9.30.4 29) (checked): "For a relative file, execution of a READ statement sets the file position indicator to the value contained in the data item referenced by the RELATIVE KEY clause for the file". The random READ of record 1 sets the file position indicator to 1.
- §14.9.10.4 9) (checked): "The file position indicator is not affected by the execution of a DELETE RECORD statement."
- §14.9.35.4 13) (checked): "The file position indicator in the rewrite file connector is not affected by the execution of a REWRITE statement."
- §14.9.51.4 2) (checked): "The file position indicator is not affected by the execution of a WRITE statement."
- §9.1.11 (checked): "The setting of the file position indicator is affected only by the CLOSE, OPEN, READ, and START statements."
- §14.9.30.4 21) c) (checked), for a relative file: "If the file position indicator was established by a prior successful READ statement, the first existing record in the physical file whose relative key number is greater than the file position indicator if NEXT is specified or implied" is selected. The indicator is still 1, so the record selected is 2 (record 2 exists in both passes).

Edition: 2014. The 2009 committee draft (CD 1.2) that became the 2014 edition has the same rules: 9.1.11 (same sentence), DELETE 14.9.9 general rule 9, REWRITE 14.9.33 general rule 12, WRITE 14.9.47 general rule 10, and READ 14.9.29 general rules 18 d) and 26). The 2002 working document (`t2002.txt`, dated 2001-12-04) has them too: 9.1.11, 14.8.9 rule 9, 14.8.33 rule 12, 14.8.47 rule 9 and 14.8.29 rule 18 d). The published 2014 and 2002 texts were not checked; their rules are inferred from these drafts.

## Our compiler

WiseOwl COBOL (`--std 2014` and `--std 2023`, `--run`): both READ NEXT lines print `00 R002 RK 02`, and the WRITE variant prints `00 R002 RK 02`, exit code 0. Ours is correct.

## Fix site

`libcob/fileio.c` in r5751. The relative file keeps its file position indicator in the descriptor's offset: `relative_read_next` (line 3229) starts from `lseek (f->fd, 0, SEEK_CUR)`, and a successful random `relative_read` (line 3184) leaves the offset just past the slot it read. The random/dynamic arms of `relative_write` (line 3335) and `relative_rewrite` (line 3397), and `relative_delete` (line 3436), which has no access-mode test and seeks to the slot the RELATIVE KEY names in every access mode (lines 3436-3470), seek the same descriptor to that slot and leave it just past it, which moves the position. This is the same fileio.c design as PB4564, where the descriptor offset serves as the file position indicator (READ NEXT after a failed random READ). Observed from the code and consistent with the output: R005 is the first record after slot 3 (slot 4 is empty) and R006 the first after slot 5. Inferred and untested: the fix is for those three arms to save the offset on entry and restore it after the update (or for the file to keep the indicator in its own field). PB4539's draft patch returns 23 after `lseek` to `off + relsize` and does not touch this path; its reviewer found its READ results identical patched and unpatched.

Observed (every status 00, exit code 0):

```text
READ 1      00 R001
DELETE 3    00
READ NEXT   00 R005 RK 05
READ 1      00 R001
REWRITE 5   00
READ NEXT   00 R006 RK 06
```

A random WRITE does the same: read record 1, `WRITE` record 5 by key, and READ NEXT returns the record after slot 5.

Expected: both READ NEXT statements return R002. ISO/IEC 1989:2023 §14.9.30.4 29): a READ of a relative file "sets the file position indicator to the value contained in the data item referenced by the RELATIVE KEY clause", so it is 1. §14.9.10.4 9): "The file position indicator is not affected by the execution of a DELETE RECORD statement." §14.9.35.4 13) says the same for REWRITE and §14.9.51.4 2) for WRITE; §9.1.11: "The setting of the file position indicator is affected only by the CLOSE, OPEN, READ, and START statements." By §14.9.30.4 21) c), READ NEXT then selects "the first existing record in the physical file whose relative key number is greater than the file position indicator", which is record 2. The 2009 draft has the same rules.

Saving the offset on entry and restoring it after the update would keep the position (not tested).
