# PB531

## Mechanism — picture-clause-p2
PictureAnalyzer.ExpandRepeats parses a parenthesized repetition factor with `int.TryParse` and feeds it straight to `StringBuilder.Append(char, int)` with no unsigned and no nonzero test (PictureAnalyzer.cs:379-394). A negative factor therefore throws an unhandled System.ArgumentOutOfRangeException out of the binder and kills the process with a stack trace and no diagnostic; a zero factor expands to nothing and yields a ZERO-LENGTH numeric item, which then slips the 13.18.40.3 SR14 1..31 digit-position gate because DataBinder.cs:2666-2669 guards that check with `pic.DigitPositions > 0`; a signed-positive factor is silently accepted. Both the literal and the constant-name paths reach the same code -- DataBinder.Constants.ExpandPicConstants (DataBinder.Constants.cs:337-363) rewrites `(constant-name)` to `(integer)` in the source string and hands the result to the same unvalidated expander, so `01 CONSTANT-N CONSTANT AS -3.` + `PIC 9(CONSTANT-N)` crashes identically. This is the two-arm shape: the constant arm was added without re-deriving the repetition factor's own syntax rule, so both arms inherit the hole.

### Expected, from the standard
ISO/IEC 1989:2023 13.18.40.3 SR6 (cite.py --check 13.18.40.3 OK): 'An unsigned nonzero integer that is enclosed in parentheses indicates the number of consecutive occurrences of the symbol that immediately precedes the left parenthesis. The integer may be specified by a constant-name, in which case the length of the integer, not the length of the constant-name, is counted toward the maximum number of characters in character-string-1.' A repetition factor that is negative, signed, or zero is therefore not an integer this rule admits, and each shall draw a named PICTURE diagnostic -- never an unhandled exception, and never a bound item. The zero case is doubly excluded: 13.18.40.3 SR14 (cite --check OK) puts a numeric item's digit positions at 1 through 31, so a zero-digit numeric item does not exist in the standard.

### Observed
The negative case is the only reachable HARD CRASH found in this whole part -- the compiler exits 1 with a .NET stack trace and emits no COBOL diagnostic at all, so a user sees an internal failure rather than a source error, and a batch build gets no attributable location. The zero case is worse than a missing diagnostic because it produces a data item: PicInfo(Category: Numeric, Length: 0, Digits: 0, Scale: 0) that FUNCTION LENGTH reports as 0 and that every record-layout, MOVE and file-image consumer downstream will size at zero bytes. The fix belongs in ExpandRepeats (one validated parse of the factor, rejecting non-digits, a leading sign, and zero, with the diagnostic naming SR6) rather than in the two call sites, and the `DigitPositions > 0` guard in DataBinder.cs:2666 should be re-derived at the same time -- it exists to skip the float-edited form (whose DigitPositions is 0 by design, kb/Work PB66) and silently doubles as an escape hatch for degenerate pictures.
