# PB1969

Found by wave 1015 group X (PB1407 admitted a reference-modified ADDRESS OF operand), filed by the train-1015 lander
from the implementer's lead 2. Not re-probed by the lander.

## Rule

§8.4.3.3.4 5): "If the evaluation of leftmost-position or length results in a non-integer value, a zero value, or a
value that references a position outside the area of identifier-1, the EC-BOUND-REF-MOD exception condition is set to
exist." (`cite.py --check 8.4.3.3.4 "a value that references a position outside the area of identifier-1"` -> OK
§8.4.3.3.4 5)). For a group that contains an OCCURS DEPENDING ON table, the area of identifier-1 is its CURRENT size
(§13.18.38.4 GR8, the variable-occurrence data item's extent at the time of reference).

## Observed (implementer's report, w1015x)

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/PtrBinder.cs#AddressRefModOf` (~line 355) takes the position count
from `RefModPlace.PositionCount(item)`, the size of the item's DESCRIPTION, i.e. the maximum extent. Under
EC-BOUND-REF-MOD checking, `SET P TO ADDRESS OF G (k:1)` with k past the current end of G but inside its maximum
extent therefore raises nothing.

## Next step

Write the repro (a group with an ODO table, DEPENDING ON set below the maximum, `>>TURN EC-BOUND-REF-MOD CHECKING ON`,
ADDRESS OF G (k:1) with k in the gap) and compare with the ordinary read path (`DISPLAY G (k:1)`), which should
already measure the current extent; the fix is to share that measure, not to add a second one.
