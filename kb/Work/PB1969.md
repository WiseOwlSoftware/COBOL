# PB1969

Found by wave 1015 group X (PB1407 admitted a reference-modified ADDRESS OF operand), filed by the train-1015 lander
from the implementer's lead 2. Not re-probed by the lander.

## Rule

§8.4.3.3.4 5): "If the evaluation of leftmost-position or length results in a non-integer value, a zero value, or a
value that references a position outside the area of identifier-1, the EC-BOUND-REF-MOD exception condition is set to
exist." (`cite.py --check 8.4.3.3.4 "a value that references a position outside the area of identifier-1"` -> OK
§8.4.3.3.4 5)). For a group that contains an OCCURS DEPENDING ON table, the area of identifier-1 is its CURRENT size
(§13.18.38.4 GR8, the variable-occurrence data item's extent at the time of reference).

## Observed (implementer's report, w1015x)

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/PtrBinder.cs#AddressRefModOf` (~line 355) takes the position count
from `RefModPlace.PositionCount(item)`, the size of the item's DESCRIPTION, i.e. the maximum extent. Under
EC-BOUND-REF-MOD checking, `SET P TO ADDRESS OF G (k:1)` with k past the current end of G but inside its maximum
extent therefore raises nothing.

## Landed (wave 1019 group C)

**For the next implementer.** `src/Cobol.Net.Compiler/CodeGen/Roslyn/PlaceRenderer.cs#CurrentPositionsExpr` is the one
answer to "how many reference-modification positions does an occurs-depending group have NOW": REUSE it for any operand
that needs the size and not the string. `src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs#ResolveForAddressOf` carries the
`OdoGroupPlace` (`AddressOfOperand.CurrentExtent`); `src/Cobol.Net.Compiler/CodeGen/Verbs/PtrEmitter.cs#AddressOfText` renders
it. Trap: a bit ODO group's leftmost position must be byte-aligned (§8.4.3.11.3 SR4 b), so a probe with `BG(4:1)` draws
COBOLNET2786 before it reaches the extent test; use `BG(9:1)`.

Reproduced on the pre-fix build exactly as the note says: with `N = 3`, `SET P TO ADDRESS OF G (5:1)` raised nothing
while `MOVE G (5:1) TO W` raised EC-BOUND-REF-MOD. `PtrEmitter.AddressOfText` handed `CobolString.RefModStartOffset` the
group's MAXIMUM position count (`AddressRefMod.Positions`, from `RefModPlace.PositionCount(item)`).

**Fix: share the read's measure, add no second one.** `ReferenceResolver.ResolveForAddressOf` already builds the operand's
place through `PlaceForItem`, which wraps a group holding an OCCURS DEPENDING ON table in an `OdoGroupPlace`; it now carries
that place (`AddressOfOperand.CurrentExtent`, `AddressRefMod.CurrentExtent`) and `PtrEmitter` renders the size through the new
`PlaceRenderer.CurrentPositionsExpr`, whose three arms are the three channels `SendingGroupValue` already chooses between (an
alphanumeric group's `CharLengthExpr`, a bit group's `LengthExpr`, a national group's `NatLengthExpr`), i.e. exactly the
length of the string the read slices, so the address and the read cannot disagree about "the area of identifier-1"
(§8.4.3.3.4 5), whose current size §13.18.38.4 GR8 gives an occurs-depending group; both `cite.py --check`ed OK).
`RuntimeApi.StrRefModStartOffset` takes the size as an expression now (a literal, the extent, or `UnknownRefModSize`).

Golden: 2002/pb1969_address_of_odo_group_current_extent (alphanumeric, national and bit ODO groups; in-range legal, past the
current end raises and RESUME AT NEXT STATEMENT leaves the pointer unchanged, a raised DEPENDING value makes the position
legal). It FAILS on the pre-fix build (the SET past the current end completes and P is set). A group whose DEPENDING item
`WrapIfOdoGroup` could not resolve to a place stays unwrapped and keeps the maximum; I did not find a shape that does so
for a cell-backed record (not measured exhaustively).
