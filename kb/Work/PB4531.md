# PB4531 — search-varying-item-set-to-occurrence: SEARCH ... VARYING integer-item stores the occurrence number instead of incrementing the item

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

In a serial `SEARCH table VARYING n`, where `n` is an integer data item (not an index), cobc stores the search index's
occurrence number into `n` instead of incrementing `n` by one each time the search index is incremented. When `n` does
not start equal to the index's starting occurrence, the result differs: starting the index at 2 with `n` = 10 and
finding the match at occurrence 4, cobc leaves `n` = 4; ISO gives 12.

## Minimal test case

Free reference format (`-free`).
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. SRCHVARY.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 T VALUE "ABCDE".
   05 E PIC X OCCURS 5 TIMES INDEXED BY X.
01 N PIC 99.
PROCEDURE DIVISION.
    SET X TO 2
    MOVE 10 TO N
    SEARCH E VARYING N
        AT END DISPLAY "NOT FOUND"
        WHEN E (X) = "D"
            DISPLAY "FOUND D, N = " N
    END-SEARCH
    STOP RUN.
```

## Environment

cobc (GnuCOBOL) 3.2.0 on WSL2 Ubuntu. `cobc -x -free -std=cobol2014 -o p prog.cob && ./p`.

## Observed result

Exit code 0:
```
FOUND D, N = 04
```

## Expected result (per ISO)

§2023:14.9.37.4 3) b) 2.: "If identifier-2 references an integer data item, that data item is incremented by the value one
at the same time as the search index is incremented." The search starts at occurrence 2 (§2023:14.9.37.4 4), "starting from
the occurrence number that corresponds to the value of the search index"); the WHEN is false at 2 and 3 and true at 4,
so the search index is incremented twice and N goes 10, 11, 12. The rule is in the 2014 edition. Expected output:
```
FOUND D, N = 12
```

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`) compiles it with no diagnostic and prints
`FOUND D, N = 12`, exit 0.

## Fix site

cobc/codegen.c, `output_search_whens` (read in the GnuCOBOL 3.2 source): when a VARYING item other than the table's
index is given (`var && var != idx`), it emits `output_move (idx, var)`, a store of the index value, where an increment
of the VARYING item alongside the index increment is required. An index data item or another table's index-name
(§2023:14.9.37.4 3) b) 1. and 3) c) 2.) needs the "same amount" or "one occurrence number" increment instead.

## Draft issue

**Title:** SEARCH VARYING sets the VARYING item to the search index's value instead of incrementing it

As posted (owner-reviewed, 2026-11-04):

When a serial SEARCH has a VARYING phrase that names an integer data item, an index data item, or an index-name of another table, cobc does not increment that item.

### To reproduce

`srchvary.cob` (attached) starts the search index X at 2 and the VARYING item N at 10. The WHEN is true at occurrence 4:

~~~~
       IDENTIFICATION DIVISION.
       PROGRAM-ID. SRCHVARY.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  T  VALUE "ABCDE".
           05  E  PIC X OCCURS 5 TIMES INDEXED BY X.
       01  N  PIC 99.
       PROCEDURE DIVISION.
           SET X TO 2
           MOVE 10 TO N
           SEARCH E VARYING N
               AT END DISPLAY "NOT FOUND"
               WHEN E (X) = "D"
                   DISPLAY "FOUND D, N = " N
           END-SEARCH
           STOP RUN.
~~~~

    cobc -std=cobol2014 -x srchvary.cob && ./srchvary

### What happens

3.2.0 and 3.3-dev r5751 both print

~~~~
FOUND D, N = 04
~~~~

`srchend.cob` and `srchidx.cob`, attached, show the same at AT END (`FOUND N=03`, `AT END N=04`) and for an index-name of another table and a USAGE INDEX item (`04` for each).

### What should happen

N goes up by one each time X does, 10, 11, 12, so the program should print `FOUND D, N = 12`. ISO/IEC 1989:2023 14.9.37.4 general rule 3 b) 2.: "If identifier-2 references an integer data item, that data item is incremented by the value one at the same time as the search index is incremented." Rules 3 b) 1. and 3 c) 2. give an index data item and an index-name the same step; the same in 2002 and in the 2014 FCD.

### Why it happens

In `cobc/codegen.c`, `output_search_whens` increments the search index and then generates a MOVE of it to the VARYING item (`output_move (idx, var)`), so the item's own starting value is lost, with no message.

### Proposed fix

The attached `n10-search-varying.patch` (against 3.3-dev r5751) replaces that MOVE with `output_stmt (cb_build_add (var, cb_int1, cb_high))`, the call `cb_build_perform_varying` uses for the PERFORM VARYING step. A SEARCH without VARYING, or VARYING one of the table's own indexes, generates the same code as before. With the patch `srchvary` prints `FOUND D, N = 12`, `srchend` `FOUND N=12` and `AT END N=15`, and `srchidx` `07` for each.

The patch also enforces syntax rule 5 (14.9.37.3), which cobc did not check: `cb_emit_search` in `cobc/typeck.c` now calls `cb_check_integer_value` on the VARYING item, so a non-integer item, floating-point included, is now refused at the SEARCH; `srchbad.cob`, attached, varies a `PIC XX` item and printed `FOUND [00]`, and now stops with `'V' is not an integer`. A boolean `PIC 1` item still passes, because cobc compiles PIC 1 as numeric (bugs #1269).

It adds the testsuite cases "SEARCH VARYING checks" to `syn_misc.at` and "SEARCH VARYING data item / other index" to `run_misc.at`, with ChangeLog entries. `make check`: 1374 expected, 9 skipped, 0 failed (1372 unpatched); the new tests fail without the patch. The NIST suite gives the same results with and without it.
