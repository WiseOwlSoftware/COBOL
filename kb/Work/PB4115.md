# PB4115 — INSPECT with a function operand

**Sites:** `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/InspectEmitter.cs:190` (`InspectEmitter.CounterMayChangeInputs`, `InspectEmitter.MayReadStorageOf`, `InspectEmitter.CounterMayOverlapTarget`, `InspectEmitter.TallyOperandTexts`, `InspectEmitter.EmitBody`), `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/StringEmitter.cs:199` (`StringEmitter.ReachOf`), `src/WiseOwl.Cobol.Compiler/Binding/Model/StorageOverlap.cs` (`StorageOverlap.MayShareStorage`).

**Lead 2 of the PB1908 implementer ("Carried (same family as R2-2)") and review lead R2-2 (low, round 2).** An INSPECT whose operand is
a function-identifier: `InspectEmitter.MayReadStorageOf` (InspectEmitter.cs:203-212) answers "may" for ANY function-identifier, so
`CounterMayChangeInputs` re-reads the image and the operands for a counter even when the function's arguments sit over storage disjoint
from the counter. The same question for STRING is answered by the operand/expression/position walk `StringEmitter.ReachOf` (three
overloads, StringEmitter.cs:199-233), which grew as a private member of StringEmitter and proves a function operand disjoint where it
can. Two copies of one question, one of them coarser.

**Fix shape (the reviewer's):** move the walk beside `StorageOverlap.MayShareStorage` and have both emitters ask it (it rewrites both
emitters, so the PB1908 finisher left it as a redesign beyond its slice; neither file was changed there). Rule 4/5: one mechanism per job.

**Repro/evidence:** none beyond the code sites; the observable effect is redundant re-reads (no wrong answer reported). PB1908 pins the
STRING side (`pb1908_string_function_order`, `pb1908_string_overlap_*`); an INSPECT golden with a function operand over disjoint storage
would pin the new shared walk.

## Resolution (wave 20261921 group B)

**Re-probe (this build, before the fix):** `INSPECT FUNCTION UPPER-CASE(G) TALLYING T FOR ALL "A" T FOR ALL "3"` with T
inside G over `0A1A1A` gave `4A1A1A` (the function was evaluated again after T stored 3, and the "3" counted);
`INSPECT S2 TALLYING QT FOR ALL "B" QT FOR ALL FUNCTION UPPER-CASE(Q)` with QT inside Q gave `2X`; the audit's
`INSPECT FUNCTION CURRENT-DATE` with two counters rendered `CobolDate.CurrentDate()` twice. A WRONG ANSWER, not only a
redundant re-read.

**Root cause:** not the coarseness of the walk but the premise under it. `MayReadStorageOf` treated a function-identifier
as re-readable, so the D-INS1 re-run evaluated it again. The standard defines the case: a function-identifier
"references a temporary data item whose value is determined when the function is referenced at runtime"
(§2023:8.4.3.2.4 GR1) and INSPECT identifies each identifier once (§2023:14.9.22.4 GR6); no counter can occupy a
temporary item, so GR13's undefined overlap never reaches one, whatever its arguments.

**Fix:** `InspectEmitter.TallyOperandTexts` evaluates every TALLYING operand that is neither a data item nor a literal
(a function-identifier) once, in source order, into a local before the first cycle; `MayReadStorageOf` answers only for a
data-item reference (`StorageOverlap.MayShareStorage`), and the re-run re-reads identifier-1 only when the previous
counter may overlap it. docs/CONFORMANCE.md D-INS1 records the rule and the GnuCOBOL 3.2 divergence (cobc evaluates
identifier-1 once but a pattern's or delimiter's function at its phrase: `2X`, `3B`; the standard controls). Pinned by
`conformance:cases/14.9.22-INSPECT/pb4115_inspect_function_evaluated_once` and `unit:InspectFunctionOnceDriftTests`.

**The estimate, corrected (rule 5):** the note's fix shape (move `StringEmitter.ReachOf` beside
`StorageOverlap.MayShareStorage` and have INSPECT ask it) would have kept the wrong premise and only narrowed it. With a
function evaluated once INSPECT asks no function walk at all, so there is no second copy left to share: INSPECT and
UNSTRING (`LiveReads.Of`) now both ask only "is this a data item that may share storage". `StringEmitter.ReachOf`
remains STRING's own, serving the D-STR4 determination, which the same GR1 reading puts in question (reported as a
lead, not changed here: it reverses a documented, golden-pinned determination).

## Landing

- `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/InspectEmitter.cs#TallyOperandTexts` owns "a TALLYING function operand is evaluated once, into a local, in source order"; REUSE it for any new TALLYING operand position, never render a function inline into the `tally` text that the D-INS1 re-run repeats.
- `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/InspectEmitter.cs#MayReadStorageOf` answers for a data-item reference only (`StorageOverlap.MayShareStorage`); a function-identifier is a temporary item (§2023:8.4.3.2.4 GR1) no counter occupies. Trap: the re-run's identifier-1 re-read is now gated on `CounterMayOverlapTarget` of the previous counter, so a function identifier-1 is never evaluated twice even when a pattern overlap forces the re-run.
- GnuCOBOL 3.2 diverges on pattern/delimiter functions (evaluates at the phrase); D-INS1 documents it, the standard controls.
