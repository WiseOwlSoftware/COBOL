# PB4115 — INSPECT with a function operand

**Sites:** `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/InspectEmitter.cs:190` (`InspectEmitter.CounterMayChangeInputs`, `InspectEmitter.MayReadStorageOf`), `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/StringEmitter.cs:199` (`StringEmitter.ReachOf`), `src/WiseOwl.Cobol.Compiler/Binding/Model/StorageOverlap.cs` (`StorageOverlap.MayShareStorage`).

**Lead 2 of the PB1908 implementer ("Carried (same family as R2-2)") and review lead R2-2 (low, round 2).** An INSPECT whose operand is
a function-identifier: `InspectEmitter.MayReadStorageOf` (InspectEmitter.cs:203-212) answers "may" for ANY function-identifier, so
`CounterMayChangeInputs` re-reads the image and the operands for a counter even when the function's arguments sit over storage disjoint
from the counter. The same question for STRING is answered by the operand/expression/position walk `StringEmitter.ReachOf` (three
overloads, StringEmitter.cs:199-233), which grew as a private member of StringEmitter and proves a function operand disjoint where it
can. Two copies of one question, one of them coarser.

**Fix shape (the reviewer's):** move the walk beside `StorageOverlap.MayShareStorage` and have both emitters ask it (it rewrites both
emitters, so the PB1908 finisher left it as a redesign beyond its slice; neither file was changed there). Rule 4/5: one mechanism per job.

**Repro/evidence:** none beyond the code sites; the observable effect is redundant re-reads (no wrong answer reported). PB1908 pins the
STRING side (`pb1908_string_function_order`, `pb1908_string_overlap_*`); an INSPECT golden with a function operand over disjoint storage
would pin the new shared walk.
