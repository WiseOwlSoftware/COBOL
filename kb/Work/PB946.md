## Expected, from the standard — §11.8.3 in full

`specs/ISO_COBOL.md`, `#### 11.8.3 Syntax rules`, the WHOLE clause:

> 1\) Interface-name-1 shall be the name of an interface specified in the REPOSITORY paragraph of the containing
> class definition.
>
> 2\) Each method prototype in each implemented interface shall be such that the object interface of this class
> conforms to all implemented interfaces.

```
$ python scripts/spec/cite.py --check 11.8.3 "Interface-name-1 shall be the name of an interface specified in the REPOSITORY paragraph of the containing class definition"
  OK  §11.8.3 1)  (Syntax rules)
```

**Two rules, and neither forbids writing an interface-name twice.** SR1 is a rule about where the name is
DECLARED, and the probe satisfies it — `ISPKR` is in the class's REPOSITORY paragraph, which is the only reason
`OoNameResolution.Resolve` succeeded and control reached the duplicate arm at all. SR2 is a conformance rule
about method prototypes and is satisfied a fortiori by a repeated name. §11.8.2's general format is
`IMPLEMENTS { interface-name-1 } …`, and §5.2.6 makes `{ } …` a repetition of the enclosed operand — the notation
that permits the second occurrence.

So the message is a **misfiled citation over a prohibition that does not exist**: the clause number is real, the
quoted obligation is real, and the program violates neither. `feedback_a_real_clause_can_answer_a_different_question`
— the shape flagged ⛔ **3× in one session** in the memory index, and the reason `kb/Work/PB932` and `PB900`
exist. `audit_code_citations --check` passes it because §11.8.3 SR1 exists.

## The code site

`src/Cobol.Net.Compiler/Oo/OoClassTable.cs:472` — inside `CaptureImplements`:

```csharp
if (into.Contains(isym))
    edition.Error("COBOLNET0840",
        $"class '{sym.Name}' ({where}): duplicate IMPLEMENTS '{iref.GetText()}' ({citation})");
else
    into.Add(isym);
```

`citation` is the paragraph's own — `ISO §11.8.3 SR1` for OBJECT, `ISO §11.4.3 SR1` for FACTORY. **Train 43's
`PB838` fixed the THREADING of that parameter into this arm** (it had been hard-coded to §11.8 there, so a
FACTORY duplicate was reported against the OBJECT paragraph's clause) — a real two-arm fix. It did not ask
whether the arm should fire, and this note is that question, arrived at by PB388's implementer reading the clause
PB838 had just threaded.

## What the fix has to decide, and the default if the owner does not

The conforming behaviour is one of:

* **Accept and de-duplicate** — the `else into.Add(isym)` branch for both occurrences, since a set of implemented
  interfaces is what §11.8.4 consumes and a repeated member changes nothing about it. This is what the absence of
  a prohibition means.
* **Accept with a WARNING** under §4.2.2's warning mechanism, if the survey shows the other compilers diagnose it.

⛔ It is **not** an owner question to escalate: `feedback_owner_decision_protocol` — where the standard is silent,
survey the model implementations and follow them (GnuCOBOL and Micro Focus for OO IMPLEMENTS), and
`feedback_follow_gnucobol_on_split_latitude`. An ERROR that refuses the compilation is excluded either way,
because §4.2.2 admits an error only for a rule the source violates.

## The sibling sweep the fixer owes

`CaptureImplements` is called **twice** — OBJECT and FACTORY — and a fix on one arm is the defect shape this
repository reproduces most (`feedback_two_arm_dispatch`). Beyond it, sweep the OO tables for the same construct:
every `into.Contains(...)`-style duplicate guard in `src/Cobol.Net.Compiler/Oo/` must name the rule that forbids
the duplicate, and any that cannot name one is this note's population. Start with the REPOSITORY paragraph's own
repeated entries (§12.3.8) and the `INHERITS` list, both of which are printed as `{ } …` repetitions too.

## Goldens the fix owes

A positive at the introducing edition — a class whose OBJECT paragraph names one interface twice, running — and
its FACTORY twin, since that is the arm a one-arm fix would leave. If the survey lands on a warning, the `.err`
belongs on a positive with a `*> warn-at:` expectation, never on a negative.
