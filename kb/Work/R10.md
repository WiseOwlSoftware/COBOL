## FLOAT HALF LANDED (2026-08-07); COMP-5 HALF: OWNER DECISION TAKEN, IMPLEMENTATION NEXT

**Float half (Phase-B F72) landed exactly as diagnosed.** The implementor usage latitude is
SMALLEST-ALGEBRAIC's alone (§15.83.3 r4 / Annex A.1 item 180 — cite-checked); HIGHEST/LOWEST now take every
float under NATIVE arithmetic and fold §15.43.4 r2 / §15.58.4 r2's greatest finite carrier magnitude (COMP-2 →
1.7976931348623157E+308; COMP-1 → 3.4028235E+38; decimal-float carriers → decimal.MaxValue), negated for
LOWEST. The mode-aware bars are usage-precise: STANDARD-DECIMAL bars only §3.166 FLOAT-BINARY-*, and
STANDARD-BINARY only §3.167 FLOAT-DECIMAL-* — the old guard's message asserted COMP-1/COMP-2 were barred by
rule 2, which was FALSE and shipped in a user-visible diagnostic (F72's secondary). SMALLEST keeps its 1516
with a corrected text. Facts: carrier-extreme folds both directions · SMALLEST float guard retained · the r2
bar under OPTIONS ARITHMETIC IS STANDARD-DECIMAL (the fact failed until the mode was genuinely set — it
discriminates). Gate: intrinsic class 154/154 · Unit 4048/4048.

**COMP-5 half (F73/F74/F75 — the 19–31-digit OverflowException, the WrapBinary bits=128 shift-mask bug where
modulus collapses to 1, and the 10–18-digit fold/storage disagreement): OWNER DECISION 2026-08-07 — UNSIGNED
CARRIERS. LANDED 2026-08-08.** Unsigned COMP-5 emits `ulong` (8-byte container) / `UInt128` (16-byte);
`PicInfo.IsUnsignedLongBinary`/`IsUnsignedWideBinary` are the carrier classifiers. The implementation record:

- **WrapBinary/InBinaryRange bits≥128 arms** (F74): a C# Int128 shift count is masked to 7 bits, so `1 << 128`
  was modulus 1 — signed 16-byte stores collapsed to 0 and the signed range read as EMPTY (every checked
  16-byte store reported size error). The 16-byte store returns CONTAINER BITS; the emitted
  `unchecked((UInt128))` cast reinterprets.
- **The unsigned runtime lane** — `StoreU`/`TryStoreU`/`FormatDisplayU`/`FormatUnsignedDisplayU`/`CompareU`/
  `Widen`; U-NAMED, not overloaded: an int constant converts implicitly to BOTH Int128 and UInt128, and a
  same-name overload pair made 119 corpus programs fail CS0121. `RoundDiv` genericized over `INumber<T>` so
  both lanes round by ONE kernel.
- **The emitter U-lane** — `NumX.U` (a UInt128 read or a >Int128 fold literal); value paths (store/display/
  relations) keep the full range; arithmetic funnels through `Widen` (loud beyond the documented Int128
  intermediate, CONFORMANCE.md items 123/179 — §14.7.5 case 5 makes intermediate-range checking a size error).
  The ulong tier lifts to `(Int128)` at the ONE read site instead.
- **AddChecked/SubChecked** (MulChecked's siblings): HIGHEST-ALGEBRAIC of `PIC S9(19) COMP-5` is exactly
  Int128.MaxValue, where an unchecked `ADD 1` wrapped past the ENGINE and stored "in range" with no size error.
- **The fold now keys on `PicInfo.Truncation == BinaryCapacity`** — its hand-maintained usage list (the second
  copy of the one table) is DELETED; `AlgebraicFoldContainerAgreementTests` pins fold-vs-runtime boundary
  agreement per container, the usage SET, the 16-byte bits contract, and the carrier table. Decimalize's false
  "nothing produces a >Int128 magnitude" doc-claim corrected (it hid F73).
- Golden `highest_algebraic_comp5_unsigned` (2023): both unsigned container maxes, the UInt128 round trip, the
  genuine 16-byte size-error boundary, the Widen size error. CONFORMANCE.md items 208 (carrier decision),
  123 + 179 (new); COBOLNET_DESIGN §1.2/§3.2; DESIGN-data-model §1.
- **Citation sweep**: the unsigned-magnitude rule is §14.9.25.4 **GR6d2b** — "§14.9.25 GR8" was the inherited
  wrong clause in CobolNum.cs (5×) and CONFORMANCE.md item 205.
