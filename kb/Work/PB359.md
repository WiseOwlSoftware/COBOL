# PB359 — the one unsuccessful exit that skips the shared failure routine

**Rows:** `GR-14.9.41.4-7` (shared with **PB352**, which owns the sequential organization's total absence of
GR7).

## Recorded as LATENT, and deliberately not asserted unreachable

`RelativeConnector.Start` / `StartFirstLast` and `IndexedConnector.Start` / `StartFirstLast` all open with

```csharp
if (!IsOpen || Mode is FileOpenMode.Output or FileOpenMode.Extend)
    return Status = FileStatusCode.ReadNotOpenForInput;
```

— a plain return, where **every other unsuccessful exit routes through `StartFail()`**.

> §14.9.41.4 GR7: Following the unsuccessful execution of a START statement, the file position indicator is set
> to indicate that no valid record position has been established.

`--check 14.9.41.4 "the file position indicator is set to indicate that no valid record position has been
established"` → **OK**. GR7 is unconditional on the KIND of failure, and §9.1.13.7 item 7 makes '47' — *The
execution of a READ or START statement is attempted referencing a file connector that is not open in the input or
I-O mode* — an unsuccessful execution, so the indicator must be invalidated there too, which item 6 a) would then
surface as '46' on the next sequential READ.

**No observing program was constructed, and that is reported rather than concluded.** Every route into the branch
either already leaves the indicator invalid (`OpenCore` sets `_fpiValid = mode is Input or IO`, so OUTPUT/EXTEND
are false before the START) or requires an intervening OPEN, which resets `_fpi`/`_fpiValid` — and a READ on a
connector in those same states answers '47' before it consults the indicator. **That is an argument about the
CURRENT shape of `OpenCore` and `ReadSequential`, not a property of the rule**, so it survives only until one of
them changes. Reachability is measured, not deduced, and this one is not yet measured in the affirmative.

## The fix shape

Route the '47' exit through `StartFail` as well, with `StartFail` taking the status to return. That makes GR7 hold
**by construction** for every unsuccessful exit instead of only for the ones someone remembered — the cheap
correct shape, and the one that survives a change to `OpenCore`.

**Code sites:** `RelativeConnector.cs#Start`, `#StartFirstLast`, `#StartFail` · `IndexedConnector.cs#Start`,
`#StartFirstLast`.

## Landed (wave 1084 E, 2026-10-15) — the START half DISCHARGED by PB352, the READ twin fixed here

**Re-probe (this build, `E:/COBOL-coord/scratch/w1084/w1084e/probe/PB359P1.cob`).** The shape this note describes
is gone: kb/Work PB352 (9bb9535fb, then 703bb3c16 for the permanent-error arm) replaced the five hand-written `'47'`
returns with `FileConnector.StartOpenModeGuard`, which calls the virtual `InvalidateFilePosition` on both of its

prints `47` for START in OUTPUT mode and on a closed connector, `00 AAAA` for the READ NEXT after a reopening
OPEN, and `23` then `46` for a random READ miss followed by READ NEXT, on both keyed organizations.

**The sibling arm, fixed (CLAUDE.md rule 4).** The READ statement carries the same rule — §14.9.30.4 GR18,
"Unless otherwise specified, at the completion of any unsuccessful execution of a READ statement, … the file
position indicator is set to indicate that no valid record position has been established" (`cite.py --check`
OK) — and its exits had the shape this note named: the `'47'` READ (sequential and random, with its
permanent-error replay) returned with nothing; the random READ's `'23'`, both absent-OPTIONAL arms, the keyed
at-end and `'14'` exits and the sequential at-end exits set `LastReadUnsuccessful` by hand, skipping the keyed
connectors' `_fpiValid` bit; and the sequential non-seekable PREVIOUS arm set `'30'` without invalidating. None
was observable, for the reason this note gave for the START (every route had already invalidated, or forced a
reopening OPEN). Now every unsuccessful READ and START exit returns through ONE terminal,
`FileConnector.Unsuccessful(status)` (the twin of `ReadSucceeded`: `InvalidateFilePosition`, then the status), the
guards (`ReadOpenModeGuard`, `SequentialReadGuard`, `RandomReadAbsentOptionalGuard`, `StartOpenModeGuard`) are
pure, and a successful START returns through `StartPositioned`. `FilePositionInvalidationDriftTests` (Roslyn)
fails when any READ/START entry of a connector assigns `Status` itself — the `return Status = X;` and the
`Status = X; return false;` shapes alike (branch review w1084e R1-1 showed the first version of the gate could not
see the second) — when the terminal stops invalidating first, or when a guard changes state; it also keeps the
virtual the one writer of the flag's `true` and the overrides the only writers of `_fpiValid = false`, with a
failure proof.
