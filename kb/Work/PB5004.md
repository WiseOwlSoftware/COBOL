# PB5004 - a decoded message frame bypasses the one construction of a slot-carrying body

**Found.** PB4957 made `MessageBody.Carrying` (`src/WiseOwl.Cobol.Runtime/Messaging/PeerFrame.cs`) the one construction
of a body with slots: it drops each slot whose token the image does not hold, and the record summary and the PB4957
Landing section call it THE ONE construction. `PeerFrameCodec.Reader.Body` (the decoder, same file) still ends with
`return new MessageBody(image, extents, slots);`, so a frame read from the wire keeps every slot it announces.

**Why it is not a wrong answer today.** Every writer goes through `Carrying` or `Truncated`, so a well-formed frame
holds only slots whose token is in its image. A frame from a peer that does not (a malformed or hostile one) enters the
receiver with slots standing for positions the image lacks, which is the state `Carrying` exists to make unrepresentable.

**Owed.** Build the decoded body through `Carrying`, or make the constructor refuse a slot whose token the image lacks
(a decode that refuses it as `InvalidDataException`, as the party byte already does); then the record's own
constructor cannot be called around the rule. A codec test decodes a frame whose slot token is absent from its image.

**Sites:** `src/WiseOwl.Cobol.Runtime/Messaging/PeerFrame.cs` (`PeerFrameCodec.Reader.Body`, `MessageBody.Carrying`)

**Landing.** `PeerFrameCodec.Reader.Body` refuses a slot whose token the decoded image lacks (`InvalidDataException`, as for the party byte) and builds the body through `MessageBody.Carrying`; `MessagingProtocolTests.APayloadThatDoesNotParseIsRefused` decodes such a frame.
