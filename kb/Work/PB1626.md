# PB1626

Filed 2026-09-26 by the train-63 lander from the w62l (PB1592) implementer's lead 3.

**What.** `ConditionalCompilationProcessor.cs:492` (the `>>DEFINE name PARAMETER` arm) reads the environment value
with `decimal.TryParse(env, NumberStyles.Number, InvariantCulture)`. Only a value that parses becomes a numeric
compilation variable (`CtValue.Numeric(CtNumeric.FromDecimal(num), env)`); any other value becomes alphanumeric.
System.Decimal holds at most about 28–29 significant digits. So a 29–31-digit numeric value, which is a valid
fixed-point literal (§8.3.3.3.2) and which standard arithmetic (the 2002/2014 compile-time mode since PB1592) can
carry, is classified ALPHANUMERIC at every edition.

**Documented, so not a defect as it stands.** `docs/CONFORMANCE.md` DOC-A.1-49 documents the classification as "an
invariant-culture decimal number" (§7.3.11.4 leaves the external value's form to the implementor). What is open is
whether the classification should follow the edition's carrier: parse through `CtNumeric.TryParseLiteral` below
2023, System.Decimal at 2023. That would keep the classification rule in one place with the arithmetic mode. It is
an implementor-latitude choice, so the precedence is GnuCOBOL next (CLAUDE.md rule 1). Survey how GnuCOBOL 3.2
classifies a long numeric `>>DEFINE … PARAMETER` value before choosing.

## Survey and decision (2026-09-27)

**GnuCOBOL 3.2** (`cobc/ppparse.y`, the `VARIABLE_NAME _as PARAMETER _override` action and `ppp_check_needs_quote`,
read from the local tarball `tests/external/gnucobol-3.2.tar.xz`; GPL, only read, nothing copied):
- An empty value, or one starting with a space, leaves the name UNDEFINED.
- A value starting with `"` or `'` is taken as the literal as written, when its last character closes the quote.
  An improperly quoted value leaves the name undefined.
- Otherwise the classification is SYNTACTIC: an optional leading `+`/`-`, then digits with at most one `.`, and at
  least one digit, is a NUMERIC literal of ANY length. The literal's own limits apply later, where it is used.
  Anything else becomes an alphanumeric literal of the text.

**Ours differs in four ways:**
1. The value comes from `decimal.TryParse(NumberStyles.Number)`, so a 29-digit-plus value is alphanumeric.
2. `1,000`, surrounding white space and a trailing sign are numeric; none is a numeric literal's spelling.
3. A quoted value keeps its quotes as alphanumeric content.
4. An empty value is a zero-length alphanumeric value, where GnuCOBOL leaves the name undefined.

**Decision (standing precedence: CLAUDE.md rule 1 and the owner-decision protocol of 2026-08-30).** §7.3.11.4 GR4
leaves the value's form to the implementor, and GnuCOBOL has an answer, so it decides. Classify SYNTACTICALLY, as a
numeric literal's spelling: optional sign, digits, at most one `.`. Carry the value in `CtNumeric`
(`TryParseLiteral`). Take a quoted value as the quoted literal. Before implementing, derive and cite two things:
- how an over-long (more than 31 digits) numeric spelling is diagnosed — at the definition or at the use, as
  GnuCOBOL does;
- whether an empty value leaves the name undefined (GnuCOBOL) or defines a zero-length literal. The spec forbids a
  zero-length literal in some positions (e.g. §8.3.3.6.3 SR2), so check which one GR4's "value" is.
The implementation must rewrite `docs/CONFORMANCE.md` DOC-A.1-49 in the same change, because it documents the
current `decimal` rule word for word. No owner question remains: this note is now an implementation item.

## Landed (wave 20261027, group D)

Re-probed on a fresh build first: with `PVAL=1234567890123456789012345678901` and `QVAL=1,000`, `>>IF PVAL > 0` was refused
(COBOL1619, 'Alphanumeric' vs 'Numeric') at 2002 and 2023 alike, and `QVAL` was numeric.

The rule is now ONE site, `DefineParameterValue.Classify` (`src/Cobol.Net.Frontend/Preprocessor/DefineParameterValue.cs`), asked by the
PARAMETER arm of `ConditionalCompilationProcessor.ApplyDefine`; GnuCOBOL 3.2's classification as the note decided, at every edition:
- no value: an empty text, a text that begins with a space, a text that begins with a quotation symbol and is not exactly ONE
  closed literal (GnuCOBOL tests only the first and last characters; here `"a"b"` and `"a" & "b"` are no value);
- a quoted value is that literal; the spelling of a fixed-point numeric literal (`NumericLiteral.IsFixedPointLiteralForm`,
  §8.3.3.3.2: the ONE spelling test, extracted from `IsFloatingPointForm`'s local helper) is numeric of any length;
  anything else (`1,000`, `1E5`, `7 `) is alphanumeric text as given. `5.` is alphanumeric, where GnuCOBOL calls it numeric:
  §8.3.3.3.2 3) forbids the decimal point as the rightmost character.
- a numeric or quoted value is then evaluated by `EvaluateOperandText`, the path `>>DEFINE X AS <literal>` takes, so the value
  is the `CtNumeric` carrier's, never System.Decimal's, and the digit capacity and the literal screening are that path's.

The two questions the note left open, decided: an over-long (more than 31 digits) numeric value is refused at the DEFINITION
(COBOL1619 naming `>>DEFINE name AS PARAMETER`), as `>>DEFINE X AS <32 digits>` is, where GnuCOBOL defers to the use (only the
diagnostic's position differs); an empty value leaves the name UNDEFINED (§7.3.11.4 GR4 second sentence: no value made available;
a zero-length LITERAL is a different thing and `""` quoted is still a zero-length literal). `>>DISPLAY PARAMETER` shares the
variable lookup but not the classification: its text is transferred unchanged (DOC-A.1-55), an empty variable an empty image.
DOC-A.1-49 rewritten in `docs/CONFORMANCE.md`; DESIGN-compile-time-expressions.md §9 states the rule. Goldens are unit tests
(`ConditionalCompilationDefineTests`, `DefineParameterValueTests`): the conformance harness cannot set the compiler's environment.
