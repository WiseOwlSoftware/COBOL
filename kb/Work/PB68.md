# PB68 — LANDED 2026-08-18 — the D2/D3 layers of RV-15.13.4-1: one class-boolean rule written in four places, none of which learned the computed operand

> ⚙ **flags:** wrong-answer, crashes, silent, rejects-legal · split out of RV-15.13.4-1 when its D1 layer
> (the wide argument bridge) landed 2026-08-09; the row STAYS DIVERGES on this note's defect.

**The rule, once:** §15.13.1 "The function type is boolean" + §15.2 item 2 make a BOOLEAN-OF-INTEGER call's
result class/category BOOLEAN (`IntrinsicCatalog` maps it correctly — `BoundIntrinsicCall.ResultCategory` is
Boolean). **The defect:** four checkpoints each re-derive operand class themselves and none has an arm for a
`BoundComputedOperand` wrapping a boolean-result intrinsic call (mechanism located by the 2026-08-09 triage,
`docs/rearchitecture/backlog-triage-2026-08-09.json` RV-15.13.4-1 D2/D3):

- `StatementValidation#CheckRelationalOperands` — `IF FUNCTION BOOLEAN-OF-INTEGER(544, 6) = B"100000"` is
  REJECTED (COBOLNET0844) though §8.8.4.2.8 defines exactly this boolean comparison; the MIRROR comparison
  with an alphanumeric literal is ACCEPTED and evaluates TRUE — a silent wrong answer on illegal source.
- `ConditionBinder#BindBoolOperandValue` — a legal B-AND operand rejects with COBOLNET1511.
- `IntrinsicBinder#BindLengthFold` — `FUNCTION LENGTH(FUNCTION BOOLEAN-OF-INTEGER(5, 8))` misclassifies the
  boolean result as a numeric literal (COBOLNET1627) where §15.50.3 r1 admits a data item of any class and
  the answer is 8 boolean positions.
- `IntrinsicBinder#IsStringOperand` — a numeric context (`COMPUTE N = FUNCTION BOOLEAN-OF-INTEGER(5,8) + 1`)
  dies with an unhandled `NotImplementedCobolFeatureException` — a CRASH on legal-shaped source (the correct
  outcome is the §8.8.1.1 class screen's diagnostic, not an exception escape).

**The fix shape (one_rule_one_place):** the class of a computed operand belongs to ONE classifier that all
four checkpoints consult — extract it, give it the ResultCategory-Boolean arm, and delete the four local
re-derivations. Probes: the triage row's p1341b/c/e/f shapes (four class-boolean contexts), p1341d (LENGTH),
plus the accepted-mirror negative. Fix, sweep the checkpoint list for a FIFTH site, goldens per context,
then re-verdict RV-15.13.4-1.

### ✅ LANDED 2026-08-18 (DEVLOG 1300) — RV-15.13.4-1 → CONFORMS (GAP 4048 → 4047)

> The ONE classifier (`IntrinsicResultType.OperandCategory`, now with the `BoundBoolOperand` arm) is what every
> checkpoint asks: `CheckRelationalOperands` (the two local switches deleted), `BindBoolOperandValue` (a sole
> function reference with a boolean result → `BoundBoolCall`, rendered by the string channel; `IsBooleanValueOperand`
> routes it; `Gr3Width`/`BoolExprAllLengthOne`/the EC walk know the node), the LENGTH fold and `IsStringOperand`
> (Boolean added to the string-class result arms), and the FIFTH site the sweep asked for — `ConditionRenderer.
> StringCategoryOf`/`BoolRead` (a computed boolean vs a boolean literal or another function result now takes the
> §8.8.4.2.8 pad). The §8.8.1.1 arithmetic screen fires at BIND for a string-class function operand
> (`ExpressionBinder.BindPrimary`, COBOLNET0844, `--permissive` decodes the digits like a data item — the renderer's
> runtime loud value is gone). Golden `pb68_boolean_function_operand_contexts` (five relation shapes, B-AND/B-XOR,
> LENGTH, a boolean-expression relation, a simple condition, three MOVEs, two EVALUATEs); negatives
> `pb68-boolean-function-vs-alphanumeric-literal` (the accepted mirror) and `pb68-boolean-function-arithmetic` (the crash).
