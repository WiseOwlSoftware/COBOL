# PB3489 — a syntax error three function calls deep hangs the compiler

## Scenario (`--std 2014 --source-format free`; the only statement of a one-paragraph program)

```cobol
01 A PIC X(10).
01 N PIC 9(8).
...
MOVE FUNCTION DATE-OF-INTEGER(FUNCTION INTEGER-PART(FUNCTION NUMVAL(FUNCTION SUBSTRING(A FROM 1 FOR 4)))) TO N
```

`SUBSTRING` is not an ISO intrinsic (kb/Work PB3488 measured the models writing it), and `A FROM 1 FOR 4` is not
an argument list, so the statement is a syntax error. **Expected:** one diagnostic, promptly — the compiler
already gives `COBOL0001: cannot parse construct near 'FROM'` for the same text one or two calls deep.
**Observed:** the compile does not finish (killed at 120 s; the fuzz harness's 90 s guard killed the original).

## Measured (same build, wall clock)

| Nesting around the bad call | Result |
|---|---|
| 1 (`NUMVAL(SUBSTRING(A FROM 1 FOR 4))`) | COBOL0001 near 'FROM', < 1 s |
| 2 | COBOL0001 near 'FROM', < 1 s |
| 3 (`DATE-OF-INTEGER(INTEGER-PART(NUMVAL(SUBSTRING(…))))`) | **> 90 s, killed** |
| 4 (the fuzz program's shape) | **> 120 s, killed** |
| 3, same nesting, bad call spelled `SUBSTRING(A, 1, 4)` (valid argument syntax, unknown name) | COBOLNET1501, < 1 s |
| 3, unknown name `FOO(A FROM 1 FOR 4)` | **> 90 s, killed** |
| 3, inside `COMPUTE N = …` instead of MOVE | **> 90 s, killed** |

So the trigger is a parse ERROR inside ≥ 3 nested argument lists, not the function names and not the statement;
the time grows super-linearly with depth, which is the signature of ANTLR adaptive prediction or error recovery
re-exploring the alternatives of every enclosing `functionIdentifier` argument on each failed inner parse.

## Harm

A compiler hang on a typo. The user's build never finishes and never says why; in a CI job it eats the timeout.
Crash class for the register (the process does not end), hence `crashes: true`.

## Where to look (as filed)

- The grammar's function-identifier / argument rules (`grammar/*.g4`: the `functionIdentifier` argument list and
  whatever alternatives admit a bare `FROM` after an identifier in that position, e.g. a reference-modification
  or a `FROM` of some other statement being predicted). `--trace`/the ANTLR profiler on the depth-3 input shows
  which decision's lookahead explodes; the compiler's own PB1590 history has the deep-nesting timing harness.
- The repair is grammatical (left-factor the decision so prediction is bounded, or a left-edge predicate — see
  feedback `left_edge_predicates` / `grammar_precedence`), never a timeout. Then a drift test that compiles the
  depth-6 shape of this input under a generous structural bound (never a wall-clock assertion — PB1590).
- Sweep for siblings (rule 4): the same error inside nested subscripts, nested reference-modification
  arithmetic, and nested `EVALUATE` selection subjects; measure each at depth 1, 3 and 6.

## Landed

The grammar was not the cause. A stack sample (dotnet-stack) of the depth-3 compile showed the parse had already
failed at FROM; the time was in `CobolErrorStrategy.ClosedFormatResidue`, the 0g hint that names a closed general
format, called from `ReportNoViableAlternative`. It re-simulated the tokens the failed prediction read with a closure
of its own, keeping one linked call stack per path. Every argument reaches a function-identifier along many call
paths (and the walk evaluates no predicate), so the distinct stacks multiplied per nested argument list: 257, 19,585
and 320,041 configurations at depths 0, 1 and 2; depth 3 never finished.

Fix (owner's direction, 2026-10-21: "Why duplicate existing functionality?"): the walk is `ResidueWalk`, a
`ParserATNSimulator` subclass that runs ANTLR's own full-context `Closure`, its graph-structured `PredictionContext`
stacks (seeded with `FromRuleContext(parser.Context)`) and its merge; the answer is read off the final configuration
set. The compiler's own closure, `Config`, `Frame` and stack bookkeeping are deleted. Two runtime shortcuts were
weighed and refused, each for a measured reason written at the class: `NoViableAltException.DeadEndConfigs` (SLL
dead ends follow a rule's end to every caller) and `ComputeReachSet` (it skips the closure once one alternative
remains). The walk never predicts, so it never reads a DFA; it is given an empty array of the parser's size so it
never touches the parser's shared DFA cache (branch review R1-2 corrected an earlier, false reason).

Measured on the fix, as the compiling thread's allocation at depths 0–2 (branch review R1-1: a configuration count
cannot see the stacks, because ANTLR merges configurations per state): 1.31 MB · 8.22 MB · 8.26 MB, against the
per-path walk's 1.29 MB · 10.4 MB · 63.7 MB; every repro above, the fuzz program and the sibling sweep (nested subscripts,
reference modification, parentheses, IF, DISPLAY, CALL USING at depth 6) answer COBOL0001 near 'FROM' in under a
second. Sweep finding: EVALUATE operands hang on LEGAL nested function calls inside ANTLR's own prediction, a different
mechanism, filed as PB3504.

## Landing

- `src/Cobol.Net.Frontend/Parsing/CobolErrorStrategy.cs#ResidueWalk` - the 0g walk on ANTLR's simulator: `Consume`
  (the token step), `Probe` (error-production frames on any stack, period edges in the parser's own context via
  `_own`, the `FromRuleContext` stack of each real ancestor).
- `tests/Cobol.Net.Tests.Unit/ResidueWalkNestingTests.cs` - allocation at depths 0–2 after a warm-up (the second level
  at most 3× the first: 0.006 fixed, 5.8 on the per-path walk, verified red on it); the diagnostic at depths 1, 3, 5.
- `docs/rearchitecture/DESIGN-frontend-grammar.md` - the 0g paragraph describes the walk.
