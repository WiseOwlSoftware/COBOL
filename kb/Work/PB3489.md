# PB3489 — a syntax error three function calls deep hangs the compiler

## Scenario (`--std 2014 --source-format free`; the only statement of a one-paragraph program)

```cobol
01 A PIC X(10).
01 N PIC 9(8).
...
MOVE FUNCTION DATE-OF-INTEGER(FUNCTION INTEGER-PART(FUNCTION NUMVAL(FUNCTION SUBSTRING(A FROM 1 FOR 4)))) TO N
```

`SUBSTRING` is not an ISO intrinsic (kb/Work PB3488 measured the models writing it), and `A FROM 1 FOR 4` is not
an argument list, so the statement is a syntax error. **Expected:** one diagnostic, promptly — the compiler
already gives `COBOL0001: cannot parse construct near 'FROM'` for the same text one or two calls deep.
**Observed:** the compile does not finish (killed at 120 s; the fuzz harness's 90 s guard killed the original).

## Measured (same build, wall clock)

| Nesting around the bad call | Result |
|---|---|
| 1 (`NUMVAL(SUBSTRING(A FROM 1 FOR 4))`) | COBOL0001 near 'FROM', < 1 s |
| 2 | COBOL0001 near 'FROM', < 1 s |
| 3 (`DATE-OF-INTEGER(INTEGER-PART(NUMVAL(SUBSTRING(…))))`) | **> 90 s, killed** |
| 4 (the fuzz program's shape) | **> 120 s, killed** |
| 3, same nesting, bad call spelled `SUBSTRING(A, 1, 4)` (valid argument syntax, unknown name) | COBOLNET1501, < 1 s |
| 3, unknown name `FOO(A FROM 1 FOR 4)` | **> 90 s, killed** |
| 3, inside `COMPUTE N = …` instead of MOVE | **> 90 s, killed** |

So the trigger is a parse ERROR inside ≥ 3 nested argument lists, not the function names and not the statement;
the time grows super-linearly with depth, which is the signature of ANTLR adaptive prediction or error recovery
re-exploring the alternatives of every enclosing `functionIdentifier` argument on each failed inner parse.

## Harm

A compiler hang on a typo. The user's build never finishes and never says why; in a CI job it eats the timeout.
Crash class for the register (the process does not end), hence `crashes: true`.

## Where to look (not yet fixed)

- The grammar's function-identifier / argument rules (`grammar/*.g4`: the `functionIdentifier` argument list and
  whatever alternatives admit a bare `FROM` after an identifier in that position, e.g. a reference-modification
  or a `FROM` of some other statement being predicted). `--trace`/the ANTLR profiler on the depth-3 input shows
  which decision's lookahead explodes; the compiler's own PB1590 history has the deep-nesting timing harness.
- The repair is grammatical (left-factor the decision so prediction is bounded, or a left-edge predicate — see
  feedback `left_edge_predicates` / `grammar_precedence`), never a timeout. Then a drift test that compiles the
  depth-6 shape of this input under a generous structural bound (never a wall-clock assertion — PB1590).
- Sweep for siblings (rule 4): the same error inside nested subscripts, nested reference-modification
  arithmetic, and nested `EVALUATE` selection subjects; measure each at depth 1, 3 and 6.
