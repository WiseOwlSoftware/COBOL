# PB75 — LANDED 2026-08-18 — `IF 10 ** 100000 > 5 …` under STANDARD-DECIMAL died with an unhandled `CobolSizeError` stack trace, exit 127

**Landed (2026-08-18, DEVLOG 1312).** `CobolSizeError` IS a `CobolFatalException` (its EcName the Table 13 level-3
name); the binder's ambient tail queries the EC-SIZE family for every NON-arithmetic statement and
`EcEmitter.FatalAmbientGates` carries the four names (flag null — unconditional raise sites), so a checked IF /
DISPLAY / MOVE / PERFORM gets the generic guard: status set, USE F3 / PERFORM WHEN dispatch (§14.6.13.1.3 #4/#5),
RESUME or abnormal termination (#7); arithmetic statements are excluded by the structural marker
`IArithmeticStatement` (`EmitArith` owns their §14.7.5 shape — and the binder's own arithmetic type list became
that marker too). With checking OFF the raise reaches `ProgramTable.RunMain` and terminates loudly, exit 1 (#8 —
documented on CONFORMANCE.md item 70), never a stack trace. **Found on the way and fixed in the same landing:** every
fatal EC was dispatched ONCE PER NESTING LEVEL — an inner statement's guard rethrew for the abnormal termination and
each enclosing statement's guard (the PERFORM, the IF …) caught the same exception and ran the F3 selection again
(a USE declarative for EC-BOUND-REF-MOD ran twice for one raise inside `PERFORM 2 TIMES`); `CobolFatalException.
Dispatched` marks a processed condition and every guard's `when (!Dispatched && …)` lets it pass, and every
dispatched-then-terminate throw (RAISE unresumed, the arithmetic EC-SIZE default, the I-O fatal default, the
CALL-site dispatches) throws pre-marked. Measured: golden `pb75_sdidi_overflow_outside_arithmetic` (USE + RESUME on
an IF, a function argument and a MOVE — the IF's branches skipped per §14.9.33.4 GR2 NOTE 1; PERFORM WHEN + RESUME
AT NEXT STATEMENT; the ON SIZE ERROR phrase untouched), `SizeErrorDispositionTests` (checking off → exit 1 with the
named condition on stderr for the four shapes; checking on with no handler → abnormal termination; the native
receiverless-lane raise the same; a fatal raise inside a PERFORM dispatched once), `EcSizeGuardDriftTests`.
Verdicts GR-14.7.5-7, GR-14.7.5-L3.3, GR-14.6.13.1.3-4/-5/-7 → CONFORMS, GR-14.6.13.1.3-8 extended (GAP 4008 → 4003).
**Not swept here — registered as [[PB91]]:** the NATIVE carrier's Int128 intermediate overflow in a non-arithmetic
context (`IF A * B > 5` past 10^38 with `>>TURN EC-SIZE-OVERFLOW CHECKING ON`) is not detected at all — `MulChecked`
is emitted only under `InSizeError` (an arithmetic statement's shape) and a condition wraps silently.

*As registered (2026-08-17):*

> ⚙ **flags:** crashes (loud, wrong stage — never a wrong answer) · found 2026-08-17 while probing PB60's
> NUMVAL-F Dec branch (`DISPLAY FUNCTION NUMVAL-F("1E+9999")` under SD lands in the same place through
> `CobolDec.FromParsed`'s §8.8.1.5.2 r2 range check).

**Measured repro** (`--std 2023`, `OPTIONS. ARITHMETIC IS STANDARD-DECIMAL.`):
`IF 10 ** 100000 > 5 DISPLAY "GT" ELSE DISPLAY "LE" END-IF` →
`Unhandled exception. CobolNet.Runtime.CobolSizeError: standard-decimal intermediate exceeds the decimal128
range (ISO §8.8.1.5.2 r2)` + a .NET stack trace, `EXIT=127`. Any SDIDI operation result past decimal128's
range in a NON-arithmetic-statement context — a condition, a DISPLAY operand, a subscript, an intrinsic
argument — takes this path; inside an arithmetic statement the statement's own `try/catch (CobolSizeError)`
(the §14.7.5 machinery) catches it correctly.

**The charge:** §14.7.5 — the size error condition "may occur as a result of … the evaluation of an
arithmetic expression", and with no SIZE ERROR phrase EC-SIZE-OVERFLOW "is set to exist and processing
proceeds as specified in 14.6.13.1.3". §14.6.13.1.3 #7 (checking enabled) is the §14.6.12 abnormal
termination — a `>>TURN EC-SIZE-OVERFLOW CHECKING ON` program with a USE declarative (#5) or a PERFORM
WHEN (#4) must reach them; #8 (checking off) leaves continue-or-stop to the implementor, and this
implementation's settled §18.16 choice for a fatal that reaches the boundary is `abnormal run-unit
termination: <message>` + exit 1 (`ProgramTable.RunMain`'s comment: "neither escapes as a raw CLR crash").
`CobolSizeError`'s own doc says it "is thrown ONLY from the checked arithmetic helpers a statement opts
into" — no longer true since `CobolDec.Clamp` (P10) throws it from EVERY SDIDI operation.

**Mechanism:** `ProgramTable.RunMain` catches `CobolFatalException` / `CobolCallException` /
`CobolImplementorFatalException` — not `CobolSizeError`; and no expression-level site converts an SDIDI
overflow into the EC model (`ExceptionState` raise + the checking-enabled fatal path). **Fix shape:** the
SDIDI range check raises through the EC model like `ExceptionState.ArgumentError` does for
EC-ARGUMENT-FUNCTION (checking on ⇒ the fatal-EC path with USE/WHEN visibility; checking off ⇒ the
implementor's #8 disposition, documented), with the arithmetic-statement `catch (CobolSizeError)` shape
kept for the SIZE ERROR phrase. Sweep: `CobolDec.Pow`'s loop-bound overflow, `FromDouble`'s
Infinity/NaN, the PROHIBITED-inexact throw, `ScaleForHalving`'s Int128 escape — every `CobolSizeError`
raise site reachable outside an arithmetic statement.
