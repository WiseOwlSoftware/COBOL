# PB1939 — LANDED (wave 1033 H, with PB2004: one root)

Filed by the train-1006 lander from wave 1006 group D's report (`w1006d-PB1144-report.md`, "New defects", item 3).

## Defect

§14.6.9.2 rule 2 leaves the receiving elements past the sender's capacity space filled, and §14.6.9.4 space-fills a
dynamic table's elements. For an elementary NUMERIC element the typed-native carrier holds a number, so
`CobolDynTable.SpaceFillElements` stores zero and the element later displays `0000` where its storage holds spaces.
This is the familiar typed-native question (a numeric item whose storage is not a valid number): the answer must come
from the design's invalid-content model, never from a byte substrate (CLAUDE.md, typed-native only).

**Repro.** `scratchpad/w1006d/p2b.cob` (wave 1006 group D scratchpad): line A prints `RT(3)` as `[0000]`; the
expected output is `[    ]`.

**Site.** `src/Cobol.Net.Runtime/Values/Tables/CobolDynTable.cs#SpaceFillElements`.

## Landed (wave 1033 H, 2026-10-07)

Re-probed on the wave's build: `MOVE G2 TO GR2` (sender capacity 1, receiver `FROM 3`) printed `[0012][0000][0000]`
and a shorter fixed group into the same receiver `[0000][0000][0000]`; §14.6.9.2 2) and §14.6.9.4 require spaces.

**Root.** The runtime was right: `SpaceFillElements` / `FromCurrentImage` hand each element the spaces through the
codec's element store. The element's CARRIER was the defect. `StorageFormPass.Classify` returned
`DynamicTable(BaseElementary(item))` and so ignored the promotion every other leaf takes: an elementary numeric
dynamic table under a whole-group operand WAS in the promoted set (`AddImagePromotableLeaves`), but its element stayed
a native `long`, so the codec decoded the spaces to zero. The fix wraps the PROMOTED element form
(`DynamicTable(CharImage(Numeric))`, a `CobolDynTable<string>`), and `DataItem.StoreAsImage` asks the element form, a
per-occurrence question like `ElementType`. The design (DESIGN-data-model §2.1) now says so.

**Sibling (the group arm).** `UsageCollectionPass.P` skipped a `DynTablePlace`, so a group ELEMENT used as a whole
operand (`MOVE SPACES TO DT (1)`) never promoted its numeric members: `000` where the element holds spaces. A
dynamic group element is now a whole-group operand like any other place. PB2004 is the channel arm of the same root.

Witnesses: `conformance:2014/pb1939_dyn_numeric_element_spaces` (A-E) and the floor
`negative/pb1939-dyn-numeric-element-spaces-2002`. The golden `2014/dyn_nested_group_move` had encoded the defect
(`B5=[00]` for the spaces `MOVE "AB7" TO G (5)` leaves in `PIC 9(2)` B; a fixed table reads `[  ]`) and is corrected.

## Landing — for the next implementer

- `src/Cobol.Net.Compiler/Binding/Passes/StorageFormPass.cs#Classify` / `#Promoted` — the ONE promotion of a leaf AND
  of a dynamic-table element; reuse `Promoted`, never re-test the promoted set by hand.
- `src/Cobol.Net.Compiler/Binding/Model/DataItem.cs#StoreAsImage` — per-occurrence: answers the dynamic element's form.
- `src/Cobol.Net.Compiler/Binding/Passes/UsageCollectionPass.cs#P` — a `DynTablePlace` group element is a whole-group
  operand; trap: the old early `return` hid every group-element fill from the promotion.
