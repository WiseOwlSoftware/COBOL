# PB43 — LANDED — `USAGE BIT` does not use bits

> ⚙ **FOUND WHILE DERIVING [[PB24]]'s LAST OPEN SUB-ITEM, and it DISSOLVES that sub-item.** PB24 recorded
> "§15.50.4 r9, the rounding step: MEASURED AND VIOLATED" with the fix shape "compute group length in BITS and
> convert with a ceiling". Deriving the rule first (the `spec-lookup` order) showed **both the diagnosis and the
> fix shape were wrong**, for the same reason: `FUNCTION LENGTH` is faithfully reporting a layout that is itself
> non-conforming.

## ⛔ THE SPECIFIC GOVERNING RULE, WHICH THE DESIGN DID NOT READ

`PicInfo.Usage.Bit`'s own doc comment states the current decision:

> USAGE BIT … maps to the SAME one-'0'/'1'-character-per-position string storage as a display-form boolean item
> (the §13.18.40.4 GR14 R14 representation license, D-B1)

**§13.18.40.4 GR14 is real and says what the comment says** (`cite.py --check`ed): *"Each symbol '1' represents a
boolean position that shall contain a boolean character. **Each boolean character can be represented in storage as
a bit, an alphanumeric character, or a national character.**"* So for a boolean item with no USAGE clause, the
char-per-position representation is expressly licensed and COBOL.NET is CONFORMING.

**But GR14 describes the available representations; the USAGE clause SELECTS one** —
**§13.18.60.4 GR5**: *"The USAGE BIT clause specifies that **bits shall be used** to represent a boolean data item.
A data item described with USAGE BIT is a bit data item. The alignment of a data item described with USAGE BIT is
specified in 8.5.1.6.3."* `shall`, not `may`. And **§8.5.1.6.3 exists solely to align items that occupy bits** —
a clause with nothing to say if USAGE BIT were char-per-position.

⚠ This is the `spec-lookup` failure mode exactly: **the nearest general sentence was read instead of the specific
governing rule.** GR14 is true and does not license this.

## 📐 MEASURED (2026-08-04, at `478ff839`)

```cobol
01 W-BIT.  05 A1 PIC X(3).  05 A2 PIC 1(5) USAGE BIT.
01 W-E   PIC 1(8) USAGE BIT.
01 W-SPLIT. 05 C1 PIC 1(3) USAGE BIT. 05 C2 PIC X(1). 05 C3 PIC 1(3) USAGE BIT.
01 W-PLAIN. 05 B1 PIC X(3).  05 B2 PIC 1(5).            *> no USAGE — GR14 latitude
```

| `BYTE-LENGTH(W-BIT)` | **8** | **4** | same layout |
| `LENGTH(W-E)` | 8 | 8 | ✅ §15.50.4 r1 — a bit item returns BOOLEAN positions |
| `BYTE-LENGTH(W-E)` | **8** | **1** | 8 bits = 1 byte |
| `LENGTH(W-SPLIT)` | **7** | **3** | each bit run takes its own byte (C1 padded for C2's boundary; C3 padded at record end) |
| `LENGTH(W-PLAIN)` | 8 | 8 | ✅ **§13.18.60.3 SR13(b)** implies USAGE DISPLAY, and **§13.18.60.4 GR7** makes DISPLAY "an alphanumeric coded character set" — char-per-position is REQUIRED here, not merely licensed |
| `LENGTH(W-B)` where `01 W-B. 05 B1 PIC 1(5) BIT. 05 B2 PIC 1(3) BIT.` | **8** | **1** | see the correction below |

⚠ **A CLAIM OF MINE DID NOT SURVIVE EITHER, AND IT IS THE SAME MISTAKE THIS NOTE IS ABOUT.** I first read
`LENGTH(W-B) = 8` as CORRECT under §15.50.4 r1 ("a bit group item returns boolean positions"). **W-B is not a bit
group item.** §13.18.29.4 GR3: *"If a GROUP-USAGE clause is not specified or implied for a group item that is not
strongly typed and is not a variable-length group, that group item is an **alphanumeric group item**"*, and
§13.16.4 GR1 implies GROUP-USAGE BIT only for a group *subordinate to a bit group*. So r1 does not apply, **r3**
does — alphanumeric character positions — and §8.5.1.6.3 packs B1 (bits 0–4) and B2 (bits 5–7, "immediately
following an elementary bit data item of the same level" → next bit position) into ONE byte. **The answer is 1.**
Reading r1's "bit group item" as "a group of bit items" is the nearest-general-sentence error again, one level up.

## ⛔ WHY [[PB24]]'s STATED FIX WOULD HAVE BEEN WRONG TWICE OVER

1. **`W-SPLIT` refutes "sum the bits, then ceil".** That model gives `3 + 8 + 3 = 14 bits → 2`. §8.5.1.6.3
   requires **3**: a bit item not immediately following a bit item *of the same level* starts at the first bit of
   the next available byte, and filler advances to the next item's natural boundary. The rule is a LAYOUT, not a
   sum. A fix built from PB24's shape would have replaced one wrong answer with another and shipped a golden
   pinning it.
2. **Fixing it inside `FUNCTION LENGTH` would be a workaround (CLAUDE.md rule 4).** The item genuinely occupies
   8 character positions in this implementation, and `LENGTH` and `BYTE-LENGTH` **agree** at 8 — the model is
   internally consistent. Making `LENGTH` answer 4 while storage stays 8 chars would make it lie about its own
   storage, break the documented ONE-WIDTH invariant (`ImageWidthIsStorageWidthTests`), and put it in conflict
   with §15.14.4. **The wrongness is upstream of every size surface.**

## ▶ THE REAL SCOPE, AND WHY IT IS AN OWNER DECISION

Conforming `USAGE BIT` means genuine bit-granular layout, which reaches: the layout model (`ImageWidth` /
`ByteWidth` / `RecordLayout`, all character-granular today), §8.5.1.6.3 alignment and implicit filler, the record
image codec, REDEFINES sizing, `FUNCTION LENGTH` / `BYTE-LENGTH`, and SYNCHRONIZED/ALIGNED interaction. It also
pulls in **GROUP-USAGE BIT (§13.18.29), which is not modelled at all** (`DataBinder`: "GROUP-USAGE is not
modeled") — and without it every group of bit items is an alphanumeric group whose length must still be computed
in bits, so the bit layout is required either way.

## ⚖ OWNER DECISION 2026-08-04 — IMPLEMENT IN FULL

Asked whether to implement bit-packed storage, record a documented non-conformance, or reject `USAGE BIT` loudly.
**Ruling: implement it in full.** This REVERSES **D-B1**, so the data-model design doc is re-decided first and the
implementation follows it (CLAUDE.md rule 2).

⭐ **THE ARCHITECTURE THIS FOLLOWS IS ALREADY IN THE TREE — V59's numeric byte forms.** A `PIC 9(4) COMP` holds its
VALUE in a native `long` and occupies its BYTE form (`PicInfo.StorageWidth`) in the record image; `PIC 9(4)
COMP-3` likewise images as BCD. **The C# carrier is not what the standard constrains** — sizes, offsets, overlays
and the record image are. So a bit item keeps a `'0'`/`'1'` string carrier and gains a BIT width plus a
bit-granular offset, exactly as BINARY/PACKED gained byte forms. The one thing bit items need that no numeric byte
form does is **sub-byte sharing** — two same-level bit items occupying one byte — which is what makes the layout
walk's `int` character offset insufficient.

⚠ **Bounded blast radius:** a program that writes no `USAGE BIT` and no `GROUP-USAGE BIT` is unaffected, because
plain `PIC 1(n)` is USAGE DISPLAY and its char-per-position storage is REQUIRED by GR7 — not merely tolerated.

## ✅ LANDED 2026-08-04 — implemented from D19

**The layout is ONE function**, `BitLayout.ExtentBits` — a §8.5.1.6.3 cursor walk, not a sum, because position
depends on the previous sibling's kind and level. `DataItem.ImageWidth` / `ByteWidth`, `RecordLayout.ImageWidth` /
`PhysicalWidth` route through it **iff the subtree has a `USAGE BIT` leaf** (`HasBitDescendant`); without one the
walk and the old character sum agree by construction, so every bit-free program keeps byte-identical widths —
which is the proof the change is inert for the entire pre-existing corpus, not an optimization.

**§15.50.4 r1 needed its own arm, and the reason is the interesting part.** An elementary boolean item's LENGTH is
in BOOLEAN positions; the generic fold reads `ImageWidth`, which is now its OCCUPANCY. While USAGE BIT was stored
char-per-bit those were the same number, so r1 and r3 could not be told apart and one arm answered both. **The arm
was not missing — it was unnecessary**, and giving bit items their real occupancy is what made it necessary.

**The image had to move too, or LENGTH would have lied.** After the width fix alone, `FUNCTION LENGTH` said 4
while the group's image was still `ABC10101` — 8 characters. Sizes right, image wrong, worse than the consistent
wrong answer it replaced. So `CobolBits.Pack`/`Unpack`/`Slice` (runtime) plus a `Physical.BitRun` in the emitter
pack a run into its bytes, **high-order bit first** (§8.5.1.6.3 numbers from "the first bit position"), trailing
filler zero. A run spans several FIELDS because same-level bit items share a byte, so the run's leader carries the
whole width and emits one `Pack`; continuations carry width 0. `MOVE W-MIX TO W-IMG` now transfers `"ABC"` + the
byte 168 (`10101000`), and moving it back restores both fields.

⚠ **A two-run group failed to compile at first** (`CS0128`): each run emitted `var __bits`, and a character item
between two bit items makes TWO runs in one method scope. The carrier local is named for the run's offset now.

⚠ **AND THE SWEEP FOUND THE OTHER IMAGE PATH (rule 4).** `AsImage`/`FromImage` were packed, but
`GroupImageCodec.ImageInitOfOne` — the compile-time seed for a **Tier-B REDEFINES backing** — still composed a bit
member as its `n`-character carrier. The backing is sized from `ImageWidth` (now `ceil(n/8)`), so the seed would
have been silently truncated against it. Two paths compose the same bytes and must agree; both pack now. Found by
asking what ELSE builds an image, not by a failing test.

**MEASURED** (golden `tests/conformance/2023/pb43_usage_bit_occupies_bits`): `MIX=4` · `MIX-BYTES=4` · `ADJ=1` ·
`SPLIT=3` · `ELEM-LEN=8` · `ELEM-BYTES=1` · `PLAIN=8` · `PACKED=168` · round-trip `[ABC][10101]`. **`SPLIT` is the
discriminator** — "sum the bits then round once" returns 2 there, which is what the [[PB24]] entry's stated fix
would have shipped.

⚠ **A GREEN UNIT TEST HAD PINNED THE DEFECT.** `Boolean_Pic1x4_ImageWidthEqualsLength_CharImageBoolean` asserted
`ImageWidth == 4` for `PIC 1(4) USAGE BIT`, citing "SR5/SR13b make DISPLAY and BIT the same string storage" —
neither rule says that. Replaced with a test that pins BOTH usages and a second that pins the split-run layout.
See [[feedback_green_test_can_hold_a_gap_open]].

## ▶ WHAT REMAINS, NAMED RATHER THAN LEFT TO BE DISCOVERED

- **`GROUP-USAGE BIT` (§13.18.29) is still not modelled** — `DataBinder` says so in its own comment. A *declared*
  bit group stays rejected. Note that this does NOT affect the cases above: §13.18.29.4 GR3 makes a group without
  the clause an alphanumeric group item, which is what every case here is.
- **A sub-byte `REDEFINES` overlay** (a redefiner starting mid-byte) is refused rather than given a rounded
  offset — D-N2's byte≠char containment already covers it.
