## Measured

### Finding property-clause — ISO/IEC 1989:2023 §13.18.42.3 SR2, SR3, SR5, SR6 (wrong-answer; rows SR-13.18.42.3-2, SR-13.18.42.3-3, SR-13.18.42.3-5, SR-13.18.42.3-6)

**Mechanism.** OoBindPropertyClauses screens the subject for only two of the six §13.18.42.3 syntax rules (own-OCCURS and superclass collision) and finds the subject by FIRST NAME MATCH rather than from the entry that carries the clause

**Repro.** OBJECT WS of a class, each compiled at --std 2023 with a client doing DISPLAY N OF A: (a) `01 R1. 05 N PIC X VALUE 'A'. 01 R2. 05 N PIC 9 VALUE 7 PROPERTY.` -> compiles, prints A; (b) `01 G. 05 T OCCURS 3. 10 E PIC 9 PROPERTY.` -> CS0103 'E' does not exist; (c) `01 G PROPERTY. 05 X PIC 9.` -> CS0029; (d) `01 CR CONSTANT RECORD. 05 N PIC 9 VALUE 1 PROPERTY.` -> clean; (e) `01 O USAGE OBJECT REFERENCE ACTIVE-CLASS PROPERTY.` -> clean. Probes under out13/probe/property-clause (sr3_qualified, sr2_under_occurs, sr3_group, sr5_const_record, sr6_active_class).

**Expected, from the standard.** Each is a compile-time error: §13.18.42.3 SR2 (subject to an OCCURS clause, including by subordination), SR3 (elementary item only; a name needing qualification is excluded), SR5 (SET phrase required under CONSTANT RECORD), SR6 (no ACTIVE-CLASS object reference). None may compile, and none may reach the C# backend.

**Observed.** The loop tests only based/typedef (§13.16.3 SR21), FILLER, `subject.Occurs is not null` and the base-chain PropertyName walk. The subject is `Roots.SelectMany(Flatten).FirstOrDefault(i => name equals subjName)`, so with two same-named items the accessor binds whichever is first in tree order -- (a) returns R1's N ('A'), not R2's (7), and SR3 is not asked. No ancestor walk for OCCURS, no IsGroup test, no CONSTANT RECORD ancestor test, no ACTIVE-CLASS test.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.Oo.cs#OoBindPropertyClauses (subject lookup + SR screens, ~lines 639-705)

### Finding property-clause — ISO/IEC 1989:2023 §13.18.42.3 SR1 (under-rejects; rows SR-13.18.42.3-1)

**Mechanism.** The PROPERTY clause is bound only inside OBJECT/FACTORY working-storage; everywhere else BindEntry's propertyClause arm is an empty block, so the clause is silently inert instead of refused (§13.18.42.3 SR1 has no owner)

**Repro.** `IDENTIFICATION DIVISION. PROGRAM-ID. PSR1A. DATA DIVISION. WORKING-STORAGE SECTION. 01 N PIC 9 PROPERTY. PROCEDURE DIVISION. M. DISPLAY N STOP RUN.` at --std 2023 -> compiles, prints 0. Same for `01 N PIC 9 VALUE 3 PROPERTY.` in a method's LOCAL-STORAGE (prints 3). Probes sr1_program_ws, sr1_method_ls.

**Expected, from the standard.** §13.18.42.3 SR1: 'The PROPERTY clause may be specified only in the working-storage section of a factory definition or an instance definition.' -- a compile-time error in a program, a function, a method's data division, and any file/linkage/local-storage/report/screen section.

**Observed.** DataBinder.BindEntry: `else if (clause.Context.propertyClause() is not null) { /* binds in the OO pass */ }`; OoDriver calls OoBindPropertyClauses only with objectParagraph()/factoryParagraph() workingStorageSection(). No other code reads the clause, so outside those two sections nothing sees it. The placement screen belongs at the one BindEntry arm every entry reaches (the SELECT WHEN precedent at the same site).

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindEntry (propertyClause arm, ~line 3966); src/Cobol.Net.Compiler/Oo/OoDriver.cs (~lines 74, 93)

## Landing (wave 68, group U)
Re-probed on the w68u build with generated class+client probes (`mkprop.py`, under the w68u scratch `p/`):
- program WS `01 N PIC 9 PROPERTY` and a method's LOCAL-STORAGE PROPERTY compiled, and the clause did nothing;
- `N` in R1 and R2, with PROPERTY on R2's, gave `DISPLAY N OF A` = the value of R1's N (the first-name match);
- a PROPERTY item under an `OCCURS 3` group failed only in the C# backend (CS0103);
- a group PROPERTY failed in the C# backend (CS0029);
- CONSTANT RECORD without WITH NO SET, and an ACTIVE-CLASS object reference, compiled clean.

**Mechanism.** The clause was never recorded on the item it was written on. The OO pass re-walked the parse entries
of object and factory working storage, then found each subject by name, so nothing outside those two sections ever
saw the clause. Fixed at the one place it binds:
- `BindEntry` now records it as `DataItem.Property` (a `PropertyClauseSpec`; the description copy carries it, as
  EntryOnly). SR1 is screened there, since its axis is the source element (object/factory WS only; not a
  program, a method, or any other section).
- The data-clause placement table gains two rows: §13.16.3 SR21 (NotWith BASED/TYPEDEF; it was a private arm of the
  OO pass, and COBOLNET2333 is kept) and SR3's elementary half (ElementaryOnly). A refused group defines no accessor.
- `OoBindPropertyClauses` iterates the object/factory WS items that CARRY the clause. It asks SR2 (by ancestry,
  every OCCURS format), SR3's qualification half, SR5 and SR6. New code **COBOLNET2563**; SR4 and the duplicate
  accessor keep COBOLNET0842.
- Sibling: `RecordLayout.IsSubjectToOccurs` asked `Occurs`, which is null for an OCCURS DYNAMIC table. It now asks
  `IsTable` through the new `OccursSubjectOf`. This affects every "subject to an OCCURS clause" caller: FILE STATUS,
  LINAGE, and the key clauses.

Goldens: `2002/pb1273_property_subject` (a subordinate property with GET/SET, and a CONSTANT RECORD property WITH NO
SET), plus five negatives, one per rule: `pb1273-property-under-occurs`, `-name-needs-qualification`,
`-constant-record-without-no-set`, `-active-class` and `-in-method-storage`. The group arm is covered by
`DataClausePlacementDriftTests`. `COBOLNET_OO_SLICE_BRIEFS.md` D-P1 is updated.
