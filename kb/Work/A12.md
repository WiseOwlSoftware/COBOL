# A12 — BATTERY DETERMINISM AUDIT

- BATTERY DETERMINISM AUDIT — name the mechanism behind a non-reproducible red, or prove there isn't one
- ⛔ **OBSERVED, NOT THEORISED (2026-07-30):** two FULL Conformance runs on an IDENTICAL tree returned **4159/4160** (`IntrinsicFunctionDifferentialTests.NumvalC_Formats_PinnedToSpec` red) then **4160/4160**. The named test passes in isolation. The suspect is the parallel-contention class §0 already warns about — each conformance test spawns a `dotnet` process via `CutRunner` with a **30-second timeout**, and a fully parallel 4,000-test suite can exceed it — **but that is UNPROVEN**: the quiet log carries no assertion detail and the second run left nothing to inspect. ⛔ **THE DANGEROUS DIRECTION IS THE OTHER ONE.** A harness that false-REDs under load can equally MASK a real failure, and the whole v1.0 claim (`zero GAP`, every leg green) rests on the battery meaning what it says. A red that is dismissed as "flake" without a mechanism is indistinguishable from one that was real — `feedback_gate_on_the_verdict_line` forbids exactly that, and this row exists so the observation does not survive as folklore in a NEXT item that gets rewritten.
- Either a NAMED mechanism + a fix (raise/parameterise the timeout, cap test parallelism, or make the harness report the timeout distinctly from a value mismatch so a contention red is never mistaken for a semantic one) — or evidence that no non-determinism exists and the two runs differed for a found reason
- **Before the P15 cut-over**, and before any "all legs green" claim is used as v1.0 evidence; cheap to start (re-run the full suite N times and record the distribution)
- **MECHANISM NAMED AND FIXED 2026-08-03; the standing distribution is now collected PASSIVELY.** The mechanism was not the timeout value — it was that on expiry the harness KILLED the process and returned its PARTIAL OR EMPTY stdout, which the caller then compared against a golden. A contention timeout was therefore reported as a VALUE MISMATCH, indistinguishable from a semantic regression. ⛔ **The same fifteen lines existed SEVEN times** across five test projects (`CutRunner.RunExit`, `AcceptDifferentialTests.AcceptRun`, `CobolNetTestBase.CompileAndRun`, three in `EndToEndTestBase`, and `BinderDecompositionTests` — which read both streams SYNCHRONOUSLY and then read `ExitCode` without checking `WaitForExit`'s result). `EndToEndTestBase`'s own comment already named the symptom ("mistaken for a hang … the source of the transient file-I/O guard flakes, DEVLOG 352/355") and answered it by RAISING the timeout while still returning the partial output. All seven now route through `tests/_shared/ProcessObservation.cs`, which retries once (serialized) and then RAISES `HarnessNonObservationException` rather than fabricating a value — so no assertion anywhere can mistake it, whatever it chose to assert on. `ProcessObservationDriftTests` keeps the extraction collapsed (it found the seventh copy on its first run) and pins that a killed run yields an EMPTY stdout, never content. **Every retry and non-observation appends to `COBOLNET_HARNESS_LOG`, so the rate is measured on every ordinary run instead of by dedicated repeat runs** — the first full Conformance run after the change was 4180/4180 in 13 m 54 s with **ZERO** harness events.
