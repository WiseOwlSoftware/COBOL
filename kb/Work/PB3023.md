# PB3023 — landing is a deterministic script; agents only resolve conflicts and bounces

**Owner decisions 2026-10-11 (kb/Work PB3015):** Q1b "GitHub merge queue (Recommended)"; Q3 "One PR per finished branch
(Recommended)": every finished implementer branch is its own pull request; the loop reviews it, rebases it, runs the
targeted local gate, verifies its DEVLOG entry file and enqueues it; GitHub tests the queued pull requests together and
lands them in order; a CI red bounces one branch to a finisher while the others land.

**Design:** `DESIGN-test-build-ci.md` §3.17.2 (steps 3–4), DESIGN §3.17.5; `DESIGN-orchestrator-loop.md` §3 (the pointer).

## What changes
1. `scripts/orchestrator/enqueue.py <branch> [--worktree <path>]`: `git fetch`; rebase onto `origin/main` (a conflict →
   exit 3, the branch's report gains `BLOCKED: rebase conflict in <files>`); the one local gate (PB3022) on the rebased
   head, **under a gate slot** (`gate_slot.py`, the shared cap of 3, so several enqueues run concurrently up to the cap
   and never beyond it — operator review item 3) → exit 5 on RED with the verdict line; `devlog.py stamp` (PB3025:
   allocates the entry number at enqueue, renames `DEVLOG/pending-<slug>.md`, one commit on the branch) then
   `devlog.py check` and `landing_check.py` (the R3 file-set partition, PB2118) → exit 6 / exit 7; `gh pr create --title
   "<subject>" --body-file <forensic message>`; `gh pr merge --auto --merge` (merge commit: the branch's commits stay
   ancestors of main; the queue admits it when `ci-gate` passes on the merge group); exit 0 with the PR number.
   Idempotent on re-run (an existing PR for the branch is reused). `--self-test` with planted repositories for every
   exit arm.
1b. `scripts/prune_worktrees.py` (named here on the operator's review, item 1): its landed test stays ancestry-based
   (`carried()`, `git cherry`) because landings are merge commits; it gains the PR states ENQUEUED (a PR exists and sits
   in the queue) and BOUNCED (removed from the queue; the CI red named) from `gh pr view --json
   state,mergeQueueEntry,statusCheckRollup`, offline-safe (no network → the git-only states). PB2987's defect (the main
   checkout is never fast-forwarded after a landing, so `ledger_state.py` reads a stale HEAD and announces no publish) is
   fixed here: the `enqueue` unit fast-forwards the main checkout after each merged PR (or `ledger_state.py` reads
   `origin/main`), and PB2987 joins this cluster.
2. `scripts/orchestrator/units/land.md` → `units/enqueue.md`: candidates = `prune_worktrees.py --brief` WAITING TO LAND,
   in harm order (PB2981's ranking kept); per branch run `enqueue.py`; a conflict or a bounce (`gh pr view --json
   mergeQueueEntry,statusCheckRollup`) dispatches ONE finisher (`cobol-finisher`, the renamed `cobol-lander`, turn cap
   160) with the conflict or the CI red named; render the ledger; hand off. `next_unit.py` names `enqueue` where it named
   `land`; `orchestrate.ps1`'s unit set follows.
3. Retired in the same change (rule 4): `train_apply.py`, `lander-train-brief.md`, `lander-brief.md`,
   `golden-lander-brief.md`, the `train` concept in `prune_worktrees.py --train`, `TRAIN_MAX`, MANDATORY-PRACTICES L1
   (the train's one DEVLOG entry), L12 (per-cluster attribution of a train red), O11's "one lander" exception (there is
   no lander), `wf_rolling_wave.js`'s `land()` and its `train_size`/`min_final_train` args (PB3016 by removal), the
   `cobol-lander` agent (→ `cobol-finisher`), `dispatch_guard.py`'s lander arm.
4. The attended session with the loop stopped runs `enqueue.py` by hand for its own branch (no agent); while the loop
   runs the `enqueue` unit is the one landing path (O11 restated).
5. `prune_worktrees.py` learns the PR states: WAITING TO LAND → ENQUEUED (PR open, in the queue) → LANDED (merged) /
   BOUNCED (removed from the queue, CI red named); `--apply` removes LANDED worktrees as today.
