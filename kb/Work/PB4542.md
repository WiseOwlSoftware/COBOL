# PB4542 — sort-merge-collating-sequence-carried-over: SORT/MERGE without COLLATING SEQUENCE reuses the alphabet of the previous SORT/MERGE statement

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

A SORT or MERGE statement without a COLLATING SEQUENCE phrase uses the alphabet named in the COLLATING SEQUENCE phrase of
the previous SORT or MERGE statement in the source, instead of the program collating sequence. The second statement
orders its records in the wrong sequence.

## Minimal test case

Free reference format (`-free`).
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. MG.
ENVIRONMENT DIVISION.
CONFIGURATION SECTION.
SPECIAL-NAMES.
ALPHABET AL-REV IS "ZYXWVUTSRQPONMLKJIHGFEDCBA".
INPUT-OUTPUT SECTION.
FILE-CONTROL.
SELECT F-A ASSIGN TO "mga.dat" ORGANIZATION IS SEQUENTIAL.
SELECT F-B ASSIGN TO "mgb.dat" ORGANIZATION IS SEQUENTIAL.
SELECT F-O ASSIGN TO "mgo.dat" ORGANIZATION IS SEQUENTIAL.
SELECT MF ASSIGN TO "mgs.tmp".
DATA DIVISION.
FILE SECTION.
FD F-A.
01 FA-REC PIC X.
FD F-B.
01 FB-REC PIC X.
FD F-O.
01 FO-REC PIC X.
SD MF.
01 MF-K PIC X.
WORKING-STORAGE SECTION.
01 WS-EOF PIC X.
PROCEDURE DIVISION.
MAIN-PARA.
OPEN OUTPUT F-A F-B
MOVE "A" TO FA-REC WRITE FA-REC
MOVE "B" TO FB-REC WRITE FB-REC
CLOSE F-A F-B
MERGE MF ON ASCENDING KEY MF-K COLLATING SEQUENCE IS AL-REV
USING F-A F-B GIVING F-O
PERFORM SHOW
MERGE MF ON ASCENDING KEY MF-K
USING F-A F-B GIVING F-O
PERFORM SHOW
STOP RUN.
SHOW.
MOVE "N" TO WS-EOF
OPEN INPUT F-O
PERFORM UNTIL WS-EOF = "Y"
READ F-O AT END MOVE "Y" TO WS-EOF
NOT AT END DISPLAY FO-REC WITH NO ADVANCING
END-READ
END-PERFORM
CLOSE F-O
DISPLAY " ".
```

## Environment

cobc (GnuCOBOL) 3.2.0 on WSL2 Ubuntu. `cobc -x -free -std=cobol2014 -o p mg.cob && ./p`. The same program with both
MERGE verbs replaced by SORT behaves the same way.

## Observed result

```
BA
BA
```
Exit code 0. Each line ends with the space that `DISPLAY " "` writes (`BA `).

## Expected result (per ISO)

§14.9.24.4 rule 5 (MERGE; 2014 and 2023) determines the collating sequence "at the beginning of the execution of the
MERGE statement": a) "First, the collating sequence established by the COLLATING SEQUENCE phrase, if specified, in this
MERGE statement", b) "Second, the collating sequences established as the program collating sequences." §14.9.40.4 rule 5
b) says the same for SORT. With no PROGRAM COLLATING SEQUENCE clause, §12.3.6.4 rule 10: "the initial program collating
sequences are the native alphanumeric collating sequence". The first MERGE orders by AL-REV (B before A); the second has
no phrase and orders by the native sequence (A before B). Expected:
```
BA
AB
```

## Our compiler

WiseOwl COBOL (fresh judge) prints the expected output (`BA`, then `AB`).

## Fix site

cobc/parser.y (read in the GnuCOBOL 3.2 release source (gnucobol-3.2.tar.xz)): rule `_sort_collating` has an empty alternative
that does not reset the file-static `alphanumeric_collation` (and `national_collation`), which `collating_sequence`
sets; `sort_merge_body` then passes the stale value to `cb_emit_sort_init`. The empty alternative should set both to NULL
so that `cob_file_sort_init` falls back to the module's collating sequence.

## Draft issue

**Title:** SORT/MERGE without a COLLATING SEQUENCE phrase reuse the alphabet of an earlier phrase or clause

As posted (owner-reviewed, 2026-11-04):

A SORT or MERGE without a COLLATING SEQUENCE phrase, or with one for national keys only, can use an alphabet left over from earlier in the same program: the phrase of an earlier SORT or MERGE, or the COLLATING SEQUENCE clause of a SELECT.

### To reproduce

`tabcol.cob` (attached) sorts the same table three times: with no phrase, with `COLLATING SEQUENCE IS CI` (an alphabet in which "a" sorts with "A" and "b" with "B"), then with no phrase again:

~~~~
       IDENTIFICATION DIVISION.
       PROGRAM-ID. TABCOL.
       ENVIRONMENT DIVISION.
       CONFIGURATION SECTION.
       SPECIAL-NAMES.
           ALPHABET CI IS "A" ALSO "a" "B" ALSO "b".
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 T VALUE "bAaB".
          05 E PIC X OCCURS 4 TIMES.
       PROCEDURE DIVISION.
           SORT E ON ASCENDING KEY E
           DISPLAY "NATIVE 1 " T
           SORT E ON ASCENDING KEY E COLLATING SEQUENCE IS CI
           DISPLAY "CI       " T
           SORT E ON ASCENDING KEY E
           DISPLAY "NATIVE 2 " T
           STOP RUN.
~~~~

    cobc -std=cobol2014 -x tabcol.cob && ./tabcol

### What happens

3.2.0 and 3.3-dev r5751 both print

~~~~
NATIVE 1 ABab
CI       AaBb
NATIVE 2 AaBb
~~~~

and on r5751 `cobc -C` passes `s_CI` to the third `cob_table_sort_init`. The other attachments show the same: `pcol.cob`, where an earlier SORT's phrase beats `PROGRAM COLLATING SEQUENCE IS AL-REV` (`PROG   ABC`); `dcol.cob`, the same with `-fdefault-colseq`; `mrgcol.cob` and `srtcol.cob`, a file MERGE and a file SORT; `selcol.cob`, a table SORT after an indexed SELECT with the clause; and `natcol.cob`, a SORT whose phrase names only `FOR NATIONAL`, so its alphanumeric key keeps the earlier AL-REV. On r5751 each SELECT first stores the default file collating sequence, so only the last SELECT's clause leaks (`selcol2.cob`), and `-fdefault-file-colseq=EBCDIC` reaches a table SORT (`fdefcol.cob`).

### What should happen

Each SORT and MERGE uses its own phrase if it has one, otherwise the program collating sequence, so tabcol should print `NATIVE 2 ABab` and pcol `PROG   CBA`. The rule is ISO/IEC 1989:2023 14.9.40.4 SORT general rule 5 b), for all formats, and the same MERGE rule in 14.9.24.4: "Second, the collating sequences established as the program collating sequences." A PROGRAM COLLATING SEQUENCE clause sets the alphanumeric one (12.3.6.4 rule 9). The same in 2002 and in the 2014 FCD.

### Why it happens

In `cobc/parser.y`, `coll_sequence_values` stores the alphabet in the file-static `alphanumeric_collation`. A statement without a phrase, or with a FOR NATIONAL phrase only, does not reset it, and `sort_merge_body` passes it to `cb_emit_sort_init` for every SORT and MERGE.

### Proposed fix

The attached `n10-sort-merge-collating.patch` (against 3.3-dev r5751; its parser.y part also applies to 3.2 with offsets) sets `alphanumeric_collation` and `national_collation` to NULL in `sort_statement` and `merge_statement`, before the phrase is parsed, so libcob uses the program collating sequence for anything a phrase does not name. A SELECT's clause still applies to its own file's keys. It also changes one other behavior: `-fdefault-file-colseq` no longer reaches a SORT or MERGE (fdefcol prints `NATIVE 1Aa`). With the patch every program gives the expected result. It adds testsuite case 794, "SORT / MERGE: COLLATING SEQUENCE applies per statement", to `tests/testsuite.src/run_misc.at`, with ChangeLog entries. `make check`: 1373 expected, 9 skipped, 0 failed (1372 unpatched); the new test fails without the patch.
