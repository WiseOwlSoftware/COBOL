# PB4542 — sort-merge-collating-sequence-carried-over: SORT/MERGE without COLLATING SEQUENCE reuses the alphabet of the previous SORT/MERGE statement

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

A SORT or MERGE statement without a COLLATING SEQUENCE phrase uses the alphabet named in the COLLATING SEQUENCE phrase of
the previous SORT or MERGE statement in the source, instead of the program collating sequence. The second statement
orders its records in the wrong sequence.

## Minimal test case

Free reference format (`-free`).
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. MG.
ENVIRONMENT DIVISION.
CONFIGURATION SECTION.
SPECIAL-NAMES.
ALPHABET AL-REV IS "ZYXWVUTSRQPONMLKJIHGFEDCBA".
INPUT-OUTPUT SECTION.
FILE-CONTROL.
SELECT F-A ASSIGN TO "mga.dat" ORGANIZATION IS SEQUENTIAL.
SELECT F-B ASSIGN TO "mgb.dat" ORGANIZATION IS SEQUENTIAL.
SELECT F-O ASSIGN TO "mgo.dat" ORGANIZATION IS SEQUENTIAL.
SELECT MF ASSIGN TO "mgs.tmp".
DATA DIVISION.
FILE SECTION.
FD F-A.
01 FA-REC PIC X.
FD F-B.
01 FB-REC PIC X.
FD F-O.
01 FO-REC PIC X.
SD MF.
01 MF-K PIC X.
WORKING-STORAGE SECTION.
01 WS-EOF PIC X.
PROCEDURE DIVISION.
MAIN-PARA.
OPEN OUTPUT F-A F-B
MOVE "A" TO FA-REC WRITE FA-REC
MOVE "B" TO FB-REC WRITE FB-REC
CLOSE F-A F-B
MERGE MF ON ASCENDING KEY MF-K COLLATING SEQUENCE IS AL-REV
USING F-A F-B GIVING F-O
PERFORM SHOW
MERGE MF ON ASCENDING KEY MF-K
USING F-A F-B GIVING F-O
PERFORM SHOW
STOP RUN.
SHOW.
MOVE "N" TO WS-EOF
OPEN INPUT F-O
PERFORM UNTIL WS-EOF = "Y"
READ F-O AT END MOVE "Y" TO WS-EOF
NOT AT END DISPLAY FO-REC WITH NO ADVANCING
END-READ
END-PERFORM
CLOSE F-O
DISPLAY " ".
```

## Environment

cobc (GnuCOBOL) 3.2.0 on WSL2 Ubuntu. `cobc -x -free -std=cobol2014 -o p mg.cob && ./p`. The same program with both
MERGE verbs replaced by SORT behaves the same way.

## Observed result

```
BA
BA
```
Exit code 0. Each line ends with the space that `DISPLAY " "` writes (`BA `).

## Expected result (per ISO)

§14.9.24.4 rule 5 (MERGE; 2014 and 2023) determines the collating sequence "at the beginning of the execution of the
MERGE statement": a) "First, the collating sequence established by the COLLATING SEQUENCE phrase, if specified, in this
MERGE statement", b) "Second, the collating sequences established as the program collating sequences." §14.9.40.4 rule 5
b) says the same for SORT. With no PROGRAM COLLATING SEQUENCE clause, §12.3.6.4 rule 10: "the initial program collating
sequences are the native alphanumeric collating sequence". The first MERGE orders by AL-REV (B before A); the second has
no phrase and orders by the native sequence (A before B). Expected:
```
BA
AB
```

## Our compiler

WiseOwl COBOL (fresh judge) prints the expected output (`BA`, then `AB`).

## Fix site

cobc/parser.y (read in the GnuCOBOL 3.2 release source (gnucobol-3.2.tar.xz)): rule `_sort_collating` has an empty alternative
that does not reset the file-static `alphanumeric_collation` (and `national_collation`), which `collating_sequence`
sets; `sort_merge_body` then passes the stale value to `cb_emit_sort_init`. The empty alternative should set both to NULL
so that `cob_file_sort_init` falls back to the module's collating sequence.

## Draft issue

**Title:** SORT/MERGE without COLLATING SEQUENCE reuses the alphabet of the previous SORT/MERGE statement

cobc (GnuCOBOL) 3.2.0, WSL2 Ubuntu, `cobc -x -free -std=cobol2014 -o p mg.cob && ./p`.

Steps: the program below merges two one-record files twice: first with `COLLATING SEQUENCE IS AL-REV` (a reversed
alphabet), then with no COLLATING SEQUENCE phrase. The program has no PROGRAM COLLATING SEQUENCE clause.

Observed: `BA` then `BA`. Expected: `BA` then `AB`. ISO/IEC 1989:2014 §14.9.24.4 rule 5 (§14.9.40.4 rule 5 for SORT)
uses the statement's own COLLATING SEQUENCE phrase if specified, otherwise the program collating sequence, which here is
the native sequence (§12.3.6.4 rule 10). Replacing MERGE by SORT gives the same result.

In cobc/parser.y the empty alternative of `_sort_collating` leaves `alphanumeric_collation` (and `national_collation`)
set by the previous statement's `collating_sequence`, and `sort_merge_body` passes it to `cb_emit_sort_init`.
