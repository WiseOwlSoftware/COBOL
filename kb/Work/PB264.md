# PB264 — the BY VALUE argument lands in a `long`, whatever the literal was

Found by the SIBLING SWEEP of owner decision D-B (the arithmetic wave, 2026-08-31). **The wide-literal half is
pre-existing at HEAD `6cd228b6` and untouched by D-B; the float-literal half changed shape under D-B (from a
truncation to integer, to a truncation at the receiver-less working scale) and is still lossy.**

## Measured, 2026-08-31 (after D-B; both arms of the same statement, same callee)

Callee formal and caller receiver are both `PIC S9(5)V9(20)` — 25 digits, ample for either literal.

| written | arrived |
|---|---|
| `BY VALUE 1.2345678901234567890123E+3` | `1234.56789` — the fraction truncated after five digits |
| `BY VALUE 1234.5678901234567890123` | `0.0000048071159228778590190` — **not a truncation at all: the Int128 unscaled value's low-order bits** |

The second row is the serious one. The literal is 23 digits, legal at COBOL-2002+ (§8.3.1.2 admits 1–31), and
the callee's formal can hold it exactly. What the callee received is unrelated to what was written, with no
diagnostic anywhere, and nothing downstream can tell the difference — the value is simply a different number.

## The site and the root cause

`src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs`, the `case BoundComputedOperand expr:` arm (which is where
a BY VALUE literal argument binds — the bare-literal `BoundNumericLiteral` arm is the BY CONTENT one, [[PB263]]):

```csharp
NumX x = num.Landed(NumericRenderer.DeU(num.Render(expr.Expr, ReceiverContext.None)), ReceiverContext.None);
return $"new CobolArg({...}, ManagedPointer<long>.Cell((long)({x.Expr})), 18, {x.Scale})";
```

Two independent faults in one line:

1. **The cell is hard-wired to `long` and the cast is unchecked.** `x.Expr` for a 23-digit literal is an
   `Int128.Parse("12345678901234567890123")`; `(long)` of it is the modular low 64 bits. The R10 unsigned-wide
   funnel and the PB84 landing exist precisely to stop this class of silent narrowing, and this site funnels
   through neither on the way out.
2. **The landing scale is the RECEIVER-LESS one**, not the formal parameter's. `ReceiverContext.None` gives the
   `Landed` funnel `WorkingScale(NumvalScaleFloor)` fraction digits, so a literal with more fraction digits than
   that loses them before the callee's own conformance (§14.9.4.4 GR10) ever runs. The formal's description IS
   available at this point — the AS NESTED callee table is what [[PB131]] added for exactly this reason.

Root cause shared with [[PB263]]: the CALL argument lane derives its own carrier and scale instead of taking
them from the one operand rendering. Fixing either arm alone would leave the other — the two-arm dispatch shape
([[feedback_two_arm_dispatch]]) that has now bitten six times.

## Fix shape (NOT implemented in the arithmetic wave — §14.9.4 argument conformance is its own subsystem)

One numeric-argument funnel for both arms (see [[PB263]] for the shape), landing at the FORMAL's scale when the
formal is known and choosing the carrier from the rendered `NumX`; the narrowing that remains raises the size
error condition rather than wrapping, exactly as `CobolNum.Widen` does on every other arithmetic path. A golden
must pass, in one program, a wide fixed-point literal and a wide floating-point literal BY VALUE and BY CONTENT
and display what the callee received — the four-cell table above is the assertion.

⚠ Not yet measured: `OoEmitter.cs:838` renders an INVOKE numeric-literal argument through the same
`EmitText.UnscaledLit` helper with its own `NumStore`. It is the third arm of the same dispatch and this note
does not claim it is broken — it claims nobody has looked.

## LANDED 2026-09-02 — together with [[PB263]] (one root cause, one funnel)

**The third arm was measured and it WAS broken**, in the float half only: `INVOKE … USING BY CONTENT 1.5E+3`
emitted a C# `double` into an `Int128`-typed store — `error CS1503`. Its wide FIXED-POINT half was already
correct, which is why the golden pins the two side by side.

**Both faults in the BY VALUE line are fixed, and a third that neither note had seen.**

1. *The hard-wired `long` and the unchecked cast.* `ManagedPointer<long>.Cell((long)(x.Expr))` narrowed a value
   the `DeU`/`Landed` funnel delivers on the Int128 lane, so a 23-digit literal crossed as its modular low bits.
   The cell is now `ManagedPointer<Int128>` with a WIDENING conversion — the narrowing is REMOVED rather than
   checked, because no value on the Int128 lane can overflow an Int128 cell, and every carrier the ABI accepts is
   read back through `CobolArgAdapt.ReadNumericCell`.
2. *The receiver-less landing scale.* A BY VALUE **literal** no longer lands at all: it is a compile-time
   constant, so it takes the same exact `(unscaled, scale)` rendering as the BY CONTENT arm. `CallEmitter`'s two
   non-place arms now funnel through ONE carrier build, which is what makes the two spellings agree.
3. ⛔ **THE ARM NEITHER NOTE NAMED, found by probing rather than reading** — and it is the two-arm shape one level
   down. At a literal position the sign is part of the token (`numericLiteral : signedNumericLiteral`), but inside
   an ARITHMETIC EXPRESSION — which is what a BY VALUE argument binds as — a leading `-` before the FLOATING-POINT
   form is taken by `unaryExpression` first. So `BY VALUE -1.234E-5` arrives as `BoundNegate(BoundNumLiteral)`
   while `BY VALUE -0.00001234` arrives as a bare `BoundNumLiteral`. Matching only the bare shape fixed the
   unsigned spelling and left the SIGNED one still landing at the working scale: **−0.00001234 crossed as
   −0.000012**, silently. `ConstLiteralText` folds the negation, so all four spellings agree. Had the probe only
   used unsigned literals this would have shipped looking fixed.

**Measured, at HEAD, before and after** (formal `PIC S9(5)V9(20)` / `S9(9)V9(9)` for the signed rows):

| written | before | after |
|---|---|---|
| `BY VALUE 1234.5678901234567890123` | `0.0000048071159228778590190` | `1234.5678901234567890123` |
| `BY VALUE 1.2345678901234567890123E+3` | `1234.56789` | `1234.5678901234567890123` |
| `BY VALUE -1.234E-5` | `-0.000012` | `-0.00001234` |
| `BY VALUE -0.00001234` | `-0.00001234` | `-0.00001234` |

**RESIDUE, deliberately not claimed.** A genuine runtime EXPRESSION argument (`BY VALUE A ** 2`) still lands at
`ReceiverContext.None`'s working scale, because landing at the FORMAL's scale needs the resolved corresponding
formal on `BoundCallArg` — that is [[PB165]] leg A's spine, not this wave. This note's measured rows were all
literals and all are exact; the expression case is recorded on [[PB289]].
