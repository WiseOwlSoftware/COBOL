## Measured

**linkage-section** — The grammar's non-ISO linkageEntry alternative linkageProcedureParameter (`level dataName? USING [BY] {REFERENCE|VALUE|CONTENT} data-ref clauses.`) is accepted at 2002+ in the strict lane and then silently DROPPED by CallBindLinkage (it keeps only dataDescriptionEntry children); no binder or diagnostic ever sees it.

- **Repro:** out13/probe/linkage-section/ext1.cob --std 2023 (and --std 2002) --run: LINKAGE SECTION. 01 L-X USING BY VALUE W-A PIC 9(4). -> compiles clean and runs (A=0012). ext2.cob, which then DISPLAYs L-X, gets COBOLNET1639 'L-X is not defined' — the declaration vanished without a word.
- **Expected (spec):** §13.7.2 (and §13.2.1) admit exactly four entry kinds in the linkage section: 77-level-description-entry, constant-entry, record-description-entry, type-declaration-entry. An entry with a USING phrase matches none of them and is a syntax error in the strict lane (or, if kept as an extension, an extension diagnostic — never a silent discard).
- **Observed:** Clean compile; LevelNumberPass.cs:242 itself notes linkageProcedureParameter reaches 'NO binder at all'. The four legal alternatives work at 2023 and 85 (fmt1.cob, fmt85.cob).
- **Code site:** src/Cobol.Net.Frontend/Grammar/Core/CobolData.g4:223-238 (linkageEntry / linkageProcedureParameter / parameterDescriptionBody / parameterPassingClause); src/Cobol.Net.Compiler/Binding/DataBinder.Linkage.cs:230-236 (the null filter)
