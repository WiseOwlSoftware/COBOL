# PB2880 — the gate's legs wait instead of compute

Owner, 2026-10-09 ~11:00 PDT, watching Task Manager during the first parallel run: "Still about 9% CPU use".

## Measured (PB2879's first parallel run, HEAD 1ed8002d7, 2026-10-09 10:55-10:59)

| leg | alone (serial gate) | in parallel |
|---|---|---|
| unit | 84 s | 169 s |
| conformance | 63 s | 151 s |
| guard | 69 s | 132 s |
| selftests-built | 38 s | 155 s |

`top` inside WSL during the run: `%Cpu(s) 15.4 us, 80.7 id, 0.0 wa`, load average 80.69, one `dotnet` (the unit test
host) at ~360 % CPU. Load that high with the CPUs idle means threads are blocked, not computing; `wa` 0 suggests it is
not plain disk wait.

## What closes it (performance-diagnosis: measure first, then find the mechanism)

1. Sample where the blocked threads wait (`dotnet-stack` / `dotnet-trace` on the unit test host during a run; `ps -L`
   thread states), and what the legs share (the compiled-program cache, a named mutex or file lock, the test runner's
   `maxParallelThreads`, the per-run temp directories).
2. Run one leg alone, two legs, all legs: the scaling curve says whether it is one shared resource or per-process
   limits.
3. Fix the mechanism, prove the gate's verdicts unchanged (the same populations, GREEN), and record the wall time and
   CPU use before and after. A structural guard, never a wall-clock assertion.

**Valley 1 — the Linux gate's prelude (removed).** Linux git reading the Windows tree through `/mnt` found the
index's stat data foreign (Windows git wrote it), re-hashed all 16,278 tracked files across 9P for the one `status`
(34.4 s, every run, at about half of one core) and then WROTE the refreshed index into the real worktree (an
optional lock; its mtime moved), which Windows git rewrote on its next command (1.2 s). `scripts/linux-gate.sh`'s
`wgit` is now the tree's own git: `git.exe` (WSL interop) with the Windows path for a tree on a Windows drive, Linux
git for a Linux tree, both `--no-optional-locks`, so no read refreshes the real index. `LinuxGateDriftTests`
holds every git call on the tree to `wgit` and every arm to the flag (mutation-tested: a planted `git -C "$tree"
status` is red). Sibling sweep: no other script runs Linux git on a Windows tree (`wslpath`, `/mnt/`, `wsl -d`).

**Valley 2 — the lander's audits (removed).** The lander never stops on a red audit, so nothing waited for them, yet
they ran first: 42.1 s set by the self-test runner's long poles. `scripts/run_gate_legs.py` now has ONE mechanism for
work beside the critical path (`BESIDE`, `Gate._beside` / `_join_beside`: joined once before the population check
and on every early end, its output printed whole, a piece that raises a named RED with its traceback); the lander's
audits and the post-build self-tests run on it. An implementer's audits stay ahead of its slot: they fail fast
(PB2523). Self-test arms: the audits see the build start (beside-ness), a raising piece is RED with the legs still
run, a failed build still reports the audits.

**Leads (valleys measured but not removed in this slice):**
1. *The Conformance leg is latency-bound, not thread-bound.* Alone and warm it ran 122 s, 80 s, 54 s and 64 s in
   four consecutive runs (32, 64, 32, 64 xUnit threads): the thread count is noise against the host's warm-up, and
   the machine sat at 40-50 % with ~26 tests in flight, each spawning `dotnet prog.dll`
   (`tests/Cobol.Net.Tests.Conformance/CompilerUnderTest.cs` `CutRunner.RunExit`, line 51). In the lander gate its
   tail after Unit ends runs at 22-40 % for 30-65 s. Measure where a run waits (process creation, the real-time scan
   of each new program, the compiled-program cache's copy) before choosing a fix.
2. *The self-test runner's long poles* set an implementer gate's audit phase (ahead of its slot): on Windows
   `landing_check.py --self-test` 93-174 s (a serial chain of git processes over one scratch repository,
   `scripts/orchestrator/landing_check.py` `self_test`, line 276), `gate_slot.py` 65-108 s, `prune_worktrees.py`
   57-103 s; `filter_population.py --self-test` (the post-build half) 89-166 s.
3. *The Linux unit leg's critical path* is one partition: `StorageFormNistEquivalenceTests_P6` 162 s against P1 54 s
   (the eight partitions are unbalanced), ending the leg ~15 s after everything else at 5-10 % of the VM.
4. *The build* (Linux 19-24 s, Windows 27 s cold) runs at 10-80 % (ANTLR's Java step, then the project chain).

## Landing

- `scripts/linux-gate.sh#wgit` — the ONE way the script reads the tree (HEAD, git directory, dirty count, tripwire):
  `git.exe` with the Windows path for a Windows-drive tree, Linux git for a Linux tree, both `--no-optional-locks`;
  `wpath` turns git's paths into this shell's form. Trap: Linux git on a `/mnt` tree is correct but re-hashes the
  whole tree (34 s) and writes the real index; `LinuxGateDriftTests.TheLinuxGateReadsTheTree_*` forbids it.
- `scripts/run_gate_legs.py#Gate._beside` / `#Gate._join_beside` / `BESIDE` — work that needs nothing the critical
  path is making runs here (the lander's audits, the post-build self-tests); REUSE it for the next such step instead
  of a private pool. Trap: an implementer's audits must stay ahead of its slot (fail fast, PB2523).
- Measuring: the counter API's `\Process(*)` set costs WMI 1-4 cores; sample `\Processor(_Total)` plus
  `Get-Process` CPU deltas, and `/proc/stat` inside WSL. Conformance alone varies 54-122 s run to run on host state:
  compare runs in the same state.
