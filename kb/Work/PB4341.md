`EXEC SQL ... END-EXEC` draws `COBOL0001: cannot parse construct near 'SQL'`. The message names a syntax fault, so a user
with working embedded-SQL source reads it as a typo. Searched `kb/Work` for `EXEC SQL`, `EXEC` with `precompil` and
`END-EXEC`: no existing note documents the non-support, so this is the first.

**Spec clause to derive.** Whether the standard has any `EXEC` construct, and which diagnostic class the unsupported
case takes (the project's rule is that unsupported means a named diagnostic, not a parse failure), is for the
implementer to derive from `specs/ISO_COBOL.md` and `cite.py --check`; this note cites none and decides nothing. The
manual's migrating page (PR #933) is where the limitation should also be stated.

## Landed (wave 20261804 group B)

**Re-probe (2026-11-01, base 2ce2e70a2).** `EXEC SQL SELECT A INTO :W-X FROM T END-EXEC.` drew `(8,17) COBOL0001: cannot
parse construct near 'SQL'`. A program with blocks in WORKING-STORAGE and the procedure division drew ONE diagnostic
in all: the block failed in a decision of `compilationUnit` or `procedureDivision`, and that recovery lost the rest of
the program, every later block and every later fault included.

**Derivation.** ISO/IEC 1989 has no EXEC construct and §8.9 reserves neither EXEC nor END-EXEC at any edition (no
occurrence in specs/ISO_COBOL.md). §4.2.14 names precompilers as components outside the implementation (cite.py OK
4.2.14 "This permits an implementation to require components outside the COBOL implementation, such as
precompilers"). No support is claimed (docs/CONFORMANCE.md 3.2 item 4), so unsupported means a named diagnostic
(kb/Work R43): COBOL5818 (`embedded-precompiler-block`), from this wave's allocation.

**Fix (as landed, after branch review round 1).** A block is EXEC, a word naming the language, and the text through the
first END-EXEC with no separator period between (ISO §8.3.5 rule 3: the period of a qualified SQL name `T.A` is block
text). `EmbeddedBlockReading.Read`, before every reader of the token stream (`Frontend.LexAndParseOnce`, after the token
rewriters and before the screens), makes each block one `EMBEDDED_BLOCK` token spanning it and moves the rest to the
`EMBEDDED_BLOCK_TEXT` channel, which the parser does not read and the separator, literal, PICTURE and word-character
screens skip (`ProgramText.Holds`). Where a statement may begin the grammar takes the token as `embeddedBlockStatement`;
elsewhere (an entry of WORKING-STORAGE) `CobolErrorStrategy.Sync` -> `SkipsEmbeddedBlock` consumes it as nothing, with
the period after it where the block was the whole entry (`WasAWholeUnit`), and a report at the token is the block's own
fault. The reading reports COBOL5818 once per block after the parse (placed by position), and a source holding a block
never parses. EXEC is not reserved, so the source reads EXEC as an opener only when every EXEC of it opens a block; a
source that writes EXEC as a word anywhere is read as COBOL throughout (`DISPLAY EXEC SQL END-EXEC.` with three data items
so named compiles and runs).

**Review round 1 (2026-11-01, review finisher).** The first shape found a block only at a parse decision whose walk could
not read it as COBOL, consumed it as nothing, and stopped its scan at ANY period. R1-1: a block that was the only
statement of an IF's or ELSE's branch or a WHEN left the construct without its statement (`IF … EXEC SQL OPEN C1 END-EXEC
ELSE …` drew a false COBOL0306 at END-IF, `EVALUATE … WHEN 1 EXEC … WHEN OTHER` a false COBOL2073, both branches holding a
block lost every later block and fault); a prediction made before the block looked into its text (`WHEN 1 EXEC SQL` read
the class condition "1 IS EXEC") or failed before it was met (`WHEN OTHER EXEC SQL`). R1-2: `T.A` ended the scan, so the
block drew the PB4341 symptom. Reading the block as one token before the parse answers both, and lead 1 of the first
report (`DISPLAY W-X` then `EXEC CICS RETURN END-EXEC.`, three COBOL1639) with them; the COBOL2632 / COBOL2630 the
separator screen drew inside SQL text are gone with the screens' skip.

**For the next implementer.**
- `src/WiseOwl.Cobol.Frontend/Parsing/EmbeddedBlockReading.cs#Read` - the one place a block is found, before any reader of the stream; `CobolErrorStrategy.SkipsEmbeddedBlock` only decides "nothing" where no statement may begin. Trap: never find a block during the parse again; a prediction made before the parser meets the block reads its text (review R1-1).
- Not covered: a source with one EXEC that opens no block (a declaration, or a block left without its END-EXEC) is read as COBOL throughout, so its well-formed blocks draw COBOL diagnostics; recorded as a lead in the wave 20261804 group B report.
