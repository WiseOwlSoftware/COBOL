# PB4888 - review-cycle throughput empties the merge queue

**What the owner saw.** From 18:13 to 18:43 PST on 2026-11-06, GitHub's merge queue was empty. No pull request was open,
while the operator's loop was running wave 20261887 and Mythos was running wave 20261889. Nothing was broken: no branch was
reviewed CLEAN, so none was eligible to land. #1257 and #1258 merged at 18:13. The next two CLEAN stamps came at about
18:38, and the landing lane started both at 18:43.

**Measured** (`E:\COBOL-coord\scratch\throughput\measure_review_cycle.py <wave> [<since>]`, which reads the wave's
`review-w<wave>-<letter>.jsonl` findings files and GitHub's merge times):

| | wave 20261885 | wave 20261887 |
|---|---|---|
| branches with FINDINGS at round 1 | 4 of 7 | 6 of 6 |
| findings (severity) | 28 medium, 22 low | 11 medium, 20 low, 1 info |
| findings (category) | 32 correctness, 4 requirement, 4 test-coverage | 15 correctness, 5 requirement, 3 test-coverage, 2 silent-failure |
| one review, start to verdict | median 6 min, max 11 | median 5 min, max 8 |
| a FINDINGS verdict to the next review's start (the review finisher's fix and gate) | median 43 min, max 98 (n = 8) | median 31 min, max 44 (n = 4; four more still open at 02:44Z) |

From 20:00Z to 02:44Z, 23 pull requests merged, with seven gaps over 20 minutes between merges: 33, 27, 51 (the #1237
bounce), 28, 23, 26 and 37 minutes.

**What it means.** The review itself is cheap. The time goes into the fix round: a review finisher starts, reads the
findings, fixes them, runs the whole gate and returns, and only then does the next review start. Round 1 now finds something
on nearly every branch (10 of 13 across the two waves), and medium is a blocking severity (`review_findings.py verdict
--blocking`, default critical, high, medium), so almost every branch pays at least one fix round. When the branches of a
wave reach review together, they also enter the fix round together, so the queue empties for a whole round.

**Levers to measure, not yet decided** (the operator lane owns the loop's tuning; any change to a blocking rule, model or
budget is the owner's):
1. **Fewer round-1 findings.** About half of the correctness findings are of kinds an implementer can check before it
   returns DONE: a sibling arm not swept, a requirement of the campaign missed, an untested exception path. Measure whether a
   self-review step against the reviewer's own checklist (the review skill's branch form), run by the implementer before
   DONE, cuts the round-1 FINDINGS rate. Compare one wave with it and one without.
2. **A faster fix round.** Break the 31 to 43 minute median into its parts: finisher start-up and reading, the fix, and the
   gate, whose test phase has a median of about 7.6 minutes (session probe's GATE GROWTH). Then attack the largest part. A
   gate whose tree a recorded GREEN already covers is REUSED today (PB4331); check whether review finishers hit that path.
3. **Stagger the wave.** A rolling wave that releases branches to review as they finish, not in a batch, keeps some branch
   always near CLEAN, so the queue does not empty all at once. Measure the queue's empty minutes per wave hour before and
   after.
4. **Name what blocks.** The ratio of low to medium (20 to 11 in wave 20261887) suggests the severity calibration is right.
   Record each blocking finding's category, so that a category which is always fixed in one line can be moved into the
   implementer's own checks (lever 1).
5. **A metric that cannot be gamed.** Report "queue empty minutes per hour while the loop runs" and "round-1 FINDINGS rate"
   in the operator's PROGRESS line. Fix the "merged 0" count first (PB3725), so the line can be trusted.

**Lever 2 measured (operator, 2026-11-07).** `E:\COBOL-coord\scratch\throughput\breakdown_fix_cycle.py` split the 10
FINDINGS-to-next-review cycles of wave 20261887 into phases, from the wave's agent transcripts, the gate logs and
`.git/cobol-gate-growth` (`breakdown-20261887.txt`). Medians in minutes, maximum in parentheses:

| phase | median (max) |
|---|---|
| verdict to the review finisher's start | 0.3 (0.4) |
| the finisher's own work: reading, fixing, local build | 4.7 (10.2) |
| its gates, launch to verdict, summed per cycle | 35.0 (94.2) |
| of which waiting for a gate slot | 13.7 (31.1) |
| of which corpus, build and tests | 23.1 (63.2) |
| last verdict to the next review's start | under 1 |
| the whole cycle | 40.4 (102.0) |

The gates are 86 % of the cycle (428 of 497 minutes). The 10 cycles launched 22 gates: 11 GREEN, 11 RED. Six of the 10
needed two or more gates, and each RED cost another slot wait and another whole-population run. The 102-minute cycle ran
four gates, three of them RED, and waited 31 minutes for slots. The reviewers and the lane ticks are not the cause.

**Decided (the owner, 2026-11-07, through Mythos: "the owner approved both levers from your PB4888 measurement").** The
operator lane implements both and records them here:
1. **A review finisher runs the targeted tests before it launches the gate.** After its fix, it runs `dotnet test
   --filter` over the tests that cover what each finding touches: the finding's own golden or test, and the tests of the
   members it changed. It launches the gate only once those pass. The gate is still the only evidence (the inner loop
   claims nothing; CLAUDE.md Testing), and this practice only stops a known RED from spending a slot and a whole run. It
   goes into `templates/MANDATORY-PRACTICES.md` with this measurement, into the finisher brief and the review finisher's
   prompt in `wf_rolling_wave.js`, and into `check_practices.py`, so a rendered brief without it is refused.
2. **A fix round's gate waits behind fewer gates.** The slot cap stays the owner's 3 (`DEFAULT_SLOTS`, 2026-10-10). Add
   a third gate class between `landing` and `implementer`, served in that order (`GATE_CLASSES`, `_service_key`), for a
   gate that re-tests a branch already through a review round. A review or gate finisher sets it through `CLASS_ENV`,
   the way `enqueue.py land` sets `landing`. A branch one fix away from CLEAN then stops queueing behind a new group's
   first gate. Keep the self-test's service-order cases, add one for the new class, and keep the waiting message naming
   why a later ticket is served first.

**Records missing for the next measurement** (fix them with lever 2): nothing records when a gate took its slot; a RED
run keeps no test time (`.git/cobol-gate-growth` stores GREEN runs only); and a later gate overwrites an earlier gate's
`gate*.log` in the same worktree. Measure one wave after both levers land with the same script. The measures are the
cycle's median, the RED-rerun share and the slot wait.
