# PB6104 - a wiseowl-tree witness is read as an uncleared suite test

**Lead** (review R1-1 of PB6047), re-verified on main ae1136f781.

**Mechanism.** `conformance-suite/harness/generate.py#Case.in_suite` is `tree == "cases" and folder != UNASSIGNED and portable` (line 218): a test of the
`wiseowl/` tree never joins a per-edition suite. `conformance-suite/harness/obligations.py#classify` (lines 95-125) picks the witness for a row in order:
non-support, `suite` (any accepted test with `in_suite`), determination, derivation, then `accepted-uncleared` for ANY accepted test (line 119-120). A row whose only
accepted-at-85 tests are in `wiseowl/` therefore lands in `accepted-uncleared`, which the module docstring (line 17) defines as "none of them cleared yet (Stage 2
clears them)". Stage 2 cannot clear them: the tree, not the clearing, excludes them. The `else` arm (lines 124-127) has the same blind spot: a `test-ref` test in the
wiseowl tree whose `accept` is exactly `(85,)` is offered as a header to repair (`header-omits`), though such a test needs a `cases/` test (Stage 3 authoring), not a header.

**Failure scenario.** The completeness report overstates the Stage 2 queue and understates the Stage 3 authoring queue by every row witnessed only by a wiseowl-tree
test; a Stage 2 pass works the rows, clears nothing, and the count never falls.

**Sites:** none (every file below is outside the campaign roots: conformance-suite/ or adjudication/). Files:
- `conformance-suite/harness/obligations.py#classify` (lines 119-127)
- `conformance-suite/harness/generate.py#Case.in_suite`
- `conformance-suite/harness/obligations.py` module docstring (the `accepted-uncleared` and `header-omits` definitions)

**Next:** classify an accepted test of the wiseowl tree as its own witness kind (or as `no-test` for the obligation) and exclude `tree != "cases"` tests from
`repairs`; extend the kind list, the docstring and the status line's terms in the same change, with a self-test case for each of the two arms.
