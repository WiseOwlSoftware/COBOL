**Why the records move and the codec does not (verified against the types, 2026-10-31).** The records are pure data: `RepositoryRecord.cs` names only `System.Collections.Immutable` and the runtime's `WiseOwl.Cobol.Runtime.Repository` enums (`RepositoryUnitKind`, `PassingMode`, `RepositoryAccessor`, …), so in `WiseOwl.Cobol.Binding.Model` they add only compiler.model → runtime, which §8.1 allows. The codec CANNOT move with them, as the implementer's lead proposed: its encoder reads the binder (`Of(OoInterfaceSymbol, DataBinder)`, `Currencies(DataBinder)` through `BoundUnit.Data`, `new Encoder(OoClassTable)` from `WiseOwl.Cobol.Compiler.Oo`), its decoder admits prototypes into `PrototypeSignatureClasses` (`Binding/PrototypeSignatureClasses.cs`), and `RepositoryVocabulary`, which it uses throughout, maps binder types (`NumericDisplayForm` of `WiseOwl.Cobol.Binding`, read through the enclosing namespace); in compiler.model the codec would only turn this row into compiler.model → compiler.binding, which §8.1 also refuses. What the backend reads of the codec is two things: `RepositoryCodec.Of(...)` (`HostEntryEmitter.EmitEntry`, `OoEmitter.EmitClassUnit`, `OoEmitter.EmitInterfaceUnit`), an ENCODE over the bound compilation that the backend has no business running, and `RepositoryCodec.KindOf(BoundUnit)` (`HostEntryEmitter.EmitEntry`, `RepositoryAttributeRenderer.IndexOf`), a pure function of `BoundUnit.IsFunction` and `IsPrototype`. `RepositoryReader` (the metadata reader, which the binder's resolution calls) and `RepositoryVocabulary` stay in compiler.binding: code generation names neither (`RepositoryAttributeRenderer`'s summary names `RepositoryReader` only in a `<see cref>`, no metadata reference).

**The shape.**
1. `Binding/Repository/RepositoryRecord.cs` moves to `Binding/Model/RepositoryRecord.cs`, namespace `WiseOwl.Cobol.Binding.Model` (folder equals namespace, §8.2), every type unchanged; every `using WiseOwl.Cobol.Binding.Repository;` that only served the records goes.
2. The encode moves to the end of `BinderDriver.Bind`: under `--repository-update on` the binder writes each published unit's record with the same `RepositoryCodec.Of` over the same bound data (the bound compilation is immutable after Bind: "no CodeGen write into the Binding data model remains", `BoundCompilation`'s summary), and the bound compilation carries them as model data: `BoundUnit` and `OoClassUnit` a `RepositoryRecord? Record` (null under `--repository-update off`), `BoundCompilation` an interface map beside `InterfaceData`. The option reaches the binder the way `NumericDisplay` and `SignEncoding` do, on the per-compilation options object, and the emitters' `repositoryUpdate` flag becomes "the unit carries a record", read in one place.
3. `RepositoryCodec.KindOf(BoundUnit)` becomes a `BoundUnit` member (its repository kind) and is deleted from the codec; the codec's own `Of(BoundUnit)` and both backend callers read the member (CLAUDE.md rule 4: no forwarder).
4. The backend's comments stop naming binder types: `HostEntryEmitter`'s summary (`<see cref="RepositoryCodec.Of"/>`) and `RepositoryAttributeRenderer`'s (`<see cref="RepositoryReader"/>`) say what they mean without a cref into compiler.binding, which PB4273's assembly split would turn into an unresolved reference.
