# PB3149 — which spelling of the MCS "no requester" exception condition is the name?

> flags: spec inconsistency, owner decision (not a code defect)

Source: `E:/COBOL-coord/scratch/reports/w1069g-PB2720-report.md`, "New defects (note-ready)" item 3 (branch `worktree-wf_d63f7207-db5-30`).

**The two spellings in `specs/ISO_COBOL.md`** (each verified with `cite.py --check`):
- `EC-MCS-NO-REQUESTER`: §14.6.13.1.6, Table 13 row `| EC-MCS-NO-REQUESTER | NF | RECEIVE statement |`; and the alphabetic Index line `EC-MCS-NO-REQUESTER exception [13.18.64]` (the note first called this site "§G.2 3)"; that was wrong, see Adjudicated below and PB3306).
- `EC-MCS-NO-REQUESTOR`: §E.3.2 3), the list of new exception conditions for the Asynchronous messaging facility. (The report named the second site "Annex F"; in this transcription the other REQUESTER site is the alphabetic Index, not §G.2, and no Annex F site was found.)
- The sibling condition is spelled `EC-MCS-REQUESTOR-FAILED` (-OR) in Table 13 itself, so the table is internally inconsistent too.

**Current code.** `src/Cobol.Net.Runtime/Exceptions/ExceptionCatalog.cs:171` registers `EC-MCS-NO-REQUESTER`, following Table 13.

**Decision needed.** Keep Table 13's spelling (current behavior; `>>TURN EC-MCS-NO-REQUESTOR` is then an unknown name), or accept both. The spec text cannot settle it mechanically; per CLAUDE.md rule 1 the spec decides, and here it contradicts itself, so it goes to the owner. First check the PDF page of Table 13 and E.3.2 (`scripts/render-spec-page.py`) to see whether the transcription introduced the discrepancy. Record the outcome in `docs/CONFORMANCE.md`.

## Adjudicated (2026-10-16, read-only adjudicator w1103z)

Source: `E:/COBOL-coord/scratch/reports/w1103z-PB3149-report.md` (record `E:/COBOL-coord/scratch/w1103/w1103z/adjudicate-PB3149.jsonl`). Verdict: **PDF INCONSISTENT**. The PDF itself prints both spellings, and the transcription matches the PDF at every site, so there is no transcription fix. A PyMuPDF text-layer scan of the whole PDF found NO-REQUEST* on three pages only (585, 1211, 1241), each rendered at 300 dpi and read.

Sites (PDF page / printed folio), each checked with `cite.py --check`:
1. Table 13, §14.6.13.1.6, PDF page 585 (folio 555): prints `EC-MCS-NO-REQUESTER | NF | RECEIVE statement` and, in the same table, `EC-MCS-REQUESTOR-FAILED`. Both agree with the transcription (`specs/ISO_COBOL.md` :21545, :21548).
2. §E.3.2 3), PDF page 1211 (folio 1181): prints `EC-MCS-NO-REQUESTOR` next to `EC-MCS-REQUESTOR-FAILED`. Agrees with :43235.
3. The alphabetic Index, PDF page 1241 (folio 1211): prints `EC-MCS-NO-REQUESTER exception 555`. Agrees with :45076. **Correction:** this is the site the note earlier called "§G.2 3)". G.2 itself has no occurrence; `cite.py` attributed the Index line to G.2 only because it treats the text after G.2 (Bibliography, Index) as G.2's region (PB3306).

No general rule raises the condition: the RECEIVE general rules (§14.9.31.4, PDF page 733, folio 703) raise only EC-MCS-INVALID-TAG and EC-MCS-REQUESTOR-FAILED, so the only normative appearance of NO-REQUEST* is the Table 13 row.

GnuCOBOL 3.2: `libcob/exception.def` (`tests/external/gnucobol-3.2.tar.xz`) registers only `EC-MCS-NO-REQUESTER` (1A05), alongside `EC-MCS-REQUESTOR-FAILED` (1A08); it has no NO-REQUESTOR alias.

Owner question (bare, sent to the operator's inbox as 20261016-155503): Table 13 and the index spell it EC-MCS-NO-REQUESTER, and Annex E.3.2 spells it EC-MCS-NO-REQUESTOR: should the compiler accept only NO-REQUESTER (current catalog; then `>>TURN EC-MCS-NO-REQUESTOR` is an unknown name), or accept both spellings as one condition? Evidence: Table 13 is the normative definition (§14.6.13.1.6); E.3.2 is informative Annex E; Table 13 itself spells the sibling -OR (REQUESTOR-FAILED); `src/Cobol.Net.Runtime/Exceptions/ExceptionCatalog.cs:171` registers EC-MCS-NO-REQUESTER.

The status stays `owner` until the owner answers. Tooling leads from the same report: PB3306, PB3307.
