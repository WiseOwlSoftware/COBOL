## Reproduced

`<scratch>/pb960.cob`:

```cobol
       01 W-BAD PIC 9V9V9.
       01 W-N   PIC 9(4) VALUE 0.
       PROCEDURE DIVISION.
           ADD W-BAD TO W-N
```

`cobol pb960.cob --std 2023` → exit 70, TWO diagnostics:

```
(5,8): error COBOLNET1934: invalid PICTURE 9V9V9 — data item 'W-BAD': the symbol 'V' appears 2 times …
                            (ISO §13.18.40.3 SR12 b)                                    ← CORRECT
(8,12): error COBOLNET0844: item 'W-BAD' of category alphanumeric is not a numeric operand …
                            (ISO §8.8.1.1)                                              ← FALSE
```

The user wrote a NUMERIC picture. It is invalid, and COBOLNET1934 says so correctly. COBOLNET0844 then tells them
their item is **alphanumeric**, which is not true of anything they wrote — it is true only of the recovery object
the binder substituted after the first error.

## Mechanism

When `PictureAnalyzer` cannot analyse a picture it yields a RECOVERY `PicInfo` so that binding can continue and
report further real errors. `PicInfo.IsRecovery` exists precisely to say "my category is a placeholder, not an
analysis" — and only four sites in `DataBinder` ask it. Every other reader of `OperandCategory` treats the
recovery object's category as a measured fact, so the first invalid PICTURE in a program seeds a false category
that any later operand check can trip over.

⭐ **This is the same shape as the half PB453 fixed** in wave 44: `SetFormatSelection.KindOf` was one such reader,
and it was repaired by asking the USAGE rather than the recovered category. That fix was correct for its one site
and did not generalise — which is the `two_arm_dispatch` / `scan_all_similar` pattern this project keeps meeting,
seen from the far side: one arm was fixed, and the shape was left in place for every other reader.

## Harm

Not a wrong answer and not a rejection of legal source — the program is genuinely invalid. The harm is to the
DIAGNOSTIC, which is user-facing text that contradicts the user's own source and sends them looking at the wrong
thing. A commercial-quality compiler does not tell someone their `PIC 9V9V9` is alphanumeric.

## Fix shape (design, not yet implemented)

1. **Make the recovery category unaskable.** Reading `OperandCategory` on a recovery `PicInfo` should be
   impossible rather than merely discouraged — return an explicit `Unknown`/`Recovered` category that no rule
   table matches, so a reader must handle it, instead of a plausible-looking `Alphanumeric` that silently flows
   into §8.8.1.1's screen.
2. **Suppress the cascade at the source.** An operand whose `PicInfo.IsRecovery` is true has already produced a
   diagnostic at its declaration; downstream operand checks on that item should be skipped, not re-answered.
3. **Sweep every `OperandCategory` reader** (rule 4 — `src/Cobol.Net.Compiler/Binding/Model/PicInfo.cs#Recovery`
   names the four that ask `IsRecovery`; the sweep is the readers that do NOT), and pin the result with a drift
   test asserting no reader consumes a recovery category unguarded.
4. **A negative golden per arm**, asserting the real diagnostic is present and the false one is ABSENT — the
   absence is the assertion that matters, and it is the one a normal negative fixture would not make.
