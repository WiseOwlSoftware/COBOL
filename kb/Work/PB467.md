# PB467 — the based-item screen resolves through a flat map, so it cannot see method scope

Lane-3 adjudication batch b2, group g7-set-a. **Every repro below was measured on HEAD `89044aa0`.**

**`inventory_rows` is deliberately EMPTY.** `SR-14.9.39.3-18` belongs to **[[PB450]]**, which owns both the row
and the mechanism it is primarily about (Format 7's dropped outer repetition, so SR18 is never asked about the
second and later `ADDRESS OF` operands). This note owns the *resolver* defect that also reaches that row and
reaches §14.9.3 SR1 through the same helper. Fix them together; neither is a special case of the other.
↔ [[PB450]] §3b/§4 cross-references this note.

## 1. THE MECHANISM

`PtrBinder.PtrResolveBased` (`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/PtrBinder.cs:293-303`) is the ONE
place that decides whether an operand is a based data item — for `SET ADDRESS OF` (called from `:40`) and for
`ALLOCATE` (called from `:187`). It resolves like this:

    DataItem? item = dref.ChildCount == 1 && ctx.Data.ByName.TryGetValue(dref.GetText(), out var list)
        && list.Count > 0 ? list[0] : null;
    if (item is { IsBased: true }) return item;
    … COBOLNET0869 citing SR18

`ctx.Data.ByName` is the **unit-wide** multimap. It has no notion of the reference's scope. The scope-aware
lookup exists, one file away, and already implements the right precedence —
`SymbolTable.TryResolve` (`src/Cobol.Net.Compiler/Binding/Model/SymbolTable.cs:46-60`) consults
`scope.Method.ByName` **first** and falls back to `_data.ByName`, and its own doc comment cites §8.4.6.2.1
rule 3a for doing so.

So the project has already derived the correct rule and written it in the correct place. `PtrResolveBased`
bypasses it — and the class doc-comment at `PtrBinder.cs:20-23` says so out loud: "the raw `ctx.Data.ByName`
lookup in `PtrResolveBased` (the documented SymbolTable bypass — the convergence is a flagged
behavior-sensitive follow-up)". **This note is that follow-up coming due, with the behaviour measured rather
than predicted.**

The consequence is not "methods are unsupported". It is that **the SR18 verdict is decided by the wrong item**,
and it goes wrong in *both* directions, which is the signature of a lookup that answers a different question
rather than one that is merely incomplete:

* the method's own declaration is invisible, so a **legal** method-local `01 MB BASED` is refused;
* the object-level declaration is visible when it must not be, so a method-local **non-based** item that legally
  shadows an object-level BASED one is accepted for rebasing.

Moving the *same* declaration between the object's data division and the method's flips the verdict — which is
the proof that scope, not the declaration, is deciding.

**Second arm: the whole domain is behind a residue.** Every one of these programs also draws
`COBOLNET0899: BASED data or ADDRESS OF in a class definition's data divisions is recognized but not yet
implemented (the OO cell/bridge emission — a named Phase-4b residue …)`, fired once per compilation for the
class. §13.16.3 SR16 admits BASED in the linkage, working-storage and local-storage sections — which object,
factory and method definitions all have — so SR18's entire domain inside class definitions is loud-unimplemented
today.

⚠ **Stated plainly so nobody over-reads the flags: the wrong verdicts are PRINTED but currently MASKED.**
Because 0899 fails the same compile, no user program is silently mis-compiled by this today. The harm flags are
set from what the screen *does* — it refuses legal source and admits illegal source — and the honest
qualification is that both become live the moment the 0899 residue lifts, which is exactly the wave that will
make method-local BASED data worth writing. Fixing the resolver **before** that landing is the cheap order;
fixing it after means the residue's removal ships two wrong verdicts as its visible behaviour.

**And the scoping is correct everywhere else**, which is what makes this method scope specifically rather than a
general resolver fault — measured, not assumed:

    cobol i2_based_shadow.cob   --std 2002 --run   → SX=[BBBB]    # two PROGRAMS, same 01 name, one BASED
    cobol s5_nested_prog_based.cob --std 2002 --run → NBA=[AAAA]  # a nested program's BASED item

`ByName` is per source element for programs; the method overlay is the sub-scope it does not model.

             working-storage section, and in the local-storage section. The level number of such data

    python scripts/spec/cite.py --check 8.4.6.2.1 "A local name may be referenced only in the source element in which it is declared"
    OK  §8.4.6.2.1   (General)

    python scripts/spec/cite.py --check 8.4.6.2.1 "If the name is declared in source element B, the item in source element B is the referenced item"
    OK  §8.4.6.2.1 3) a)  (General)

§13.16.3 SR16 is what makes both probes legal source: it names **local-storage** and **working-storage**
explicitly, and a method definition has both. §8.4.6.2.1 is what makes the method's declaration the referenced
one — a method definition is a source unit (identification division through `END METHOD`) and therefore a
source element, so its declarations are local names and rule 3a picks them over an outer declaration of the
same spelling.

⚠ **Two citations I did NOT carry over from the adjudication, because I could not validate them.** The refuter's
record leaned on "§8.4.6.2.2 makes the OBJECT's data-names global" and `SymbolTable`'s own comment cites
"§11.7.4 GR5" for method-local privacy. `cite.py --find` locates **no** clause containing either claim's
wording, and `--check 11.7.4 "may be referenced only"` FAILS. The argument does not need them: §8.4.6.2.1's
local-name rule and rule 3a settle the precedence on their own, in the direction the compiler's own
`SymbolTable` already implements. The `SymbolTable` comment's §11.7.4 reference should be re-derived or dropped
in the same change set.

## 4. THE CODE SITE AND THE SHAPE OF THE REPAIR

| arm | file:line |
|---|---|
| the bypass | `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/PtrBinder.cs:293-303` `PtrResolveBased` |
| its callers | `PtrBinder.cs:40` (`SET ADDRESS OF`, SR18) · `PtrBinder.cs:187` (`ALLOCATE`, §14.9.3.3 SR1) |
| the doc comment that flagged it | `PtrBinder.cs:20-23` |
| the scope-aware lookup it should use | `src/Cobol.Net.Compiler/Binding/Model/SymbolTable.cs:46-60` `TryResolve` |
| the residue masking the whole domain | the `COBOLNET0899` BASED-in-a-class-definition stage |

⛔ **The repair is to delete the bypass, not to add a method case** (CLAUDE.md rules 4 and 5). A special-case
"also look in `scope.Method.ByName`" written into `PtrResolveBased` would reproduce `TryResolve`'s precedence a
second time, in a second place, and the next scope the resolver grows would go wrong here again —
`one_rule_one_place`. `PtrResolveBased` should take the reference's `Scope` and call `ctx.Symbols.TryResolve`,
so that the based-item screen inherits *every* scoping rule the resolver knows, now and later.

Two details the swap must not lose, both already correct today:

* **the `ChildCount == 1` bare-name guard.** A based entry is level 01/77 (§13.16.3 SR16) and data-name-1 is a
  data-name, so no qualified, subscripted or reference-modified spelling is legal here. Keep the guard; it
  turns nothing legal away.
* **the `list[0]` first-wins pick.** Harmless across *programs* (measured in §1) but it is the same
  "flat map, one arm" shape; once the lookup is scoped, the multimap's remaining ambiguity is the ordinary
  qualification question and should get the ordinary diagnostic, not a silent first-wins.

Pair the fix with a **drift test that moves one declaration**: the same `01 X BASED` compiled once at object
level and once in the method, plus the shadow pair, asserting the verdict follows the declaration's scope. That
is the test that would have failed on this tree.

## 5. THE SIBLING SWEEP THE FIXER MUST DO

* **Every other reader of `ctx.Data.ByName` that is answering a question the `SymbolTable` scopes.** Measured
  on HEAD, the readers outside `SymbolTable` itself are:
  `BinderDriver.cs:494` (a shadow test — `if (data.ByName.ContainsKey(g.CobolName)) continue;` for §13.18.27
  GR2 GLOBAL propagation), `BinderDriver.cs:669` and `DataBinder.Oo.cs:382` (both *writers*, populating the
  map), and `PtrBinder.cs:296` (this defect). `BinderDriver.cs:494` is the one to re-read hardest: it asks
  "does a nearer name shadow this global?" — a scoped question — from the flat map, which is the identical
  shape one clause away.
* **ALLOCATE and FREE**, which reach the same helper: §14.9.3.3 SR1 gets the same wrong verdict, and
  `PtrBinder.cs:155` resolves the RETURNING pointer through a different path that must agree with it.
* `SymbolTable.TryResolveCondition` / `TryResolveIndex` (`SymbolTable.cs:63-91`) already model the method
  overlay; anything that reproduces their precedence by hand elsewhere is the same defect in a different rule.
* The unvalidated `§11.7.4 GR5` reference in `SymbolTable.cs`'s doc comments (§2) — re-derive or drop it while
  in the file, since this note's fix will be read against those comments.
* When the **0899 residue lifts**, this defect stops being masked. Sequence the resolver fix first, or that
  landing's first visible behaviour is a legal program refused.

## 6. ROWS

**None claimed.** `SR-14.9.39.3-18` is [[PB450]]'s, and `§14.9.3.3 SR1` is carried by the ALLOCATE clause's own
inventory rows, which this note does not adjudicate. What this note adds to both is the *mechanism*: the screen
they rest on resolves through a map that cannot see the reference's scope, so their verdicts are correct only
for references declared at unit level.
