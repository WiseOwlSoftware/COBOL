## Measured (adjudicator / refuter evidence, verbatim)
### [exception-conditions] raising-last-object-no-pd-check: GOBACK/EXIT ... RAISING LAST EXCEPTION re-propagates the current exception OBJECT (ExceptionState.SetPropagatingLast's object branch) without the §14.6.13.1.5 list-item-1 test against the containing element's PD-header RAISING classes/interfaces; the binder's static SR4/SR5 discharge (design D-EO5) covers only RAISING identifier-1, whose declared class is known at compile time
- **Rows:** GR-14.6.13.1.5-L2.1 — harm `wrong-answer`
- **Repro:** out/probe/exc-oo/o3.cob: '>>TURN EC-OO-EXCEPTION CHECKING ON'; EXO3A (REPOSITORY CLASS CXO3E) with DECLARATIVES 'USE AFTER EXCEPTION OBJECT CXO3E' (DISPLAY "A-F4") and 'USE AFTER EC EC-OO-EXCEPTION' (DISPLAY "A-ECOO " FUNCTION EXCEPTION-STATUS, RESUME AT NEXT STATEMENT), MAIN 'CALL "EXO3B". DISPLAY "A-AFTER".'; EXO3B has a PROCEDURE DIVISION header with NO RAISING phrase, a declarative 'USE AFTER EXCEPTION OBJECT CXO3E' that displays B-F4 and executes 'GOBACK RAISING LAST EXCEPTION', and MAIN 'INVOKE CXO3E "NEW" RETURNING W-E. RAISE W-E.'; CLASS-ID CXO3E is empty.
- **Expected (spec):** The CXO3E object is neither a) an instance of a class in EXO3B's PD-header RAISING phrase nor b) an implementor of an interface there (the phrase is absent), so per §14.6.13.1.5 list item 1 the GOBACK is as if RAISING EXCEPTION EC-OO-EXCEPTION and processing continues per §14.6.13.1.3; raised in EXO3A (checking enabled there, §14.9.18.4 GR1 b)), fatal (Table 13), #5 selects the F3 declarative: 'B-F4 / A-ECOO EC-OO-EXCEPTION / A-AFTER'. The F4 declarative must not run.
- **Observed:** Observed: 'B-F4 / A-F4 / A-AFTER', exit 0 - the object reached the activator's F4 declarative as if list item 2 applied. SetPropagatingLast: 'if (LastName == ExceptionState.ObjectSentinel) { _propagatedObject = (true, ExceptionObject, StagingFor); _propagated = null; return; }' - its pdRaising argument carries only EC-USER names (CallEmitter.EmitRaisingStage passes r.PdRaising). The design brief D-EO5 said the static discharge 'must be revisited when FACTORY/INTERFACE-ID land' (landed: PB814/PB815) and never considered LAST. Fix shape: carry the PD-header object RAISING targets (RaisingPhrase.Partition's class/interface tuples, with FACTORY flag) to the LAST staging and test the runtime object's class/implements closure there, converting to a staged EC-OO-EXCEPTION on a miss.
- **Code site:** src/Cobol.Net.Runtime/Exceptions/ExceptionState.cs#SetPropagatingLast; src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs#EmitRaisingStage; src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.cs (RAISING LAST binding, PdRaising names only)

### [exception-conditions] object-conversion-ignores-activator-checking: the activator-side EC-OO-EXCEPTION conversion for an exception object no USE AFTER EXCEPTION OBJECT declarative takes (list item 4, and list item 1's conversion once it exists) is emitted as an unconditional Set + F3 dispatch + CobolFatalException, never asking whether EC-OO-EXCEPTION checking is enabled in the ACTIVATING element - the object arm of EmitPropagationPickup was not brought under the PB408 rule the named arm follows (TakeRaisedPropagation(site.ActivatorChecking))
- **Rows:** GR-14.6.13.1.5-L2.4 — harm `wrong-answer`
- **Repro:** out/probe/exc-oo/o1.cob (no >>TURN anywhere): program EXO1 'INVOKE CXO1S "NEW" RETURNING S. INVOKE S "BOOM". DISPLAY "AFTER " FUNCTION EXCEPTION-STATUS. STOP RUN.' with no declaratives; class CXO1S method BOOM 'PROCEDURE DIVISION RAISING CXO1E.' executes 'INVOKE CXO1E "NEW" RETURNING W-E. GOBACK RAISING W-E.'
- **Expected (spec):** No F4 declarative and no PROPAGATE, so list item 4: the GOBACK is as if RAISING EXCEPTION EC-OO-EXCEPTION; §14.9.18.4 GR1 b) raises that condition in the activating element only 'if checking for that exception condition is enabled in the activating runtime element', and §14.6.13.1.1 'By default, checking is not enabled for any exception condition' - so nothing is raised, the INVOKE completes normally and 'AFTER ...' is displayed, exit 0. (With >>TURN EC-OO-EXCEPTION CHECKING ON in the activator - probe o2 - abnormal termination per §14.6.13.1.3 #7 is correct and is what the compiler does.)
- **Observed:** Observed o1: 'abnormal run-unit termination: EC-OO-EXCEPTION (fatal): an exception object was not handled', exit 1. The emitted object arm is 'if (__or == -3) { ExceptionState.Set("EC-OO-EXCEPTION", true); int __oq = <EcDispatch>; ...; if (__oq != -2) throw new CobolFatalException("EC-OO-EXCEPTION", ...) }' with no ActivatorChecking test, while the named arm directly below it is gated by TakeRaisedPropagation(site.ActivatorChecking.Encoded). The two-arm dispatch shape: PB408 fixed the named arm only. conformance-test:OoSpineTests.GobackRaisingObject_NoF4_F3CatchesEcOoException (no >>TURN, a USE AFTER EC EC-OO declarative fires) pins the divergent behaviour and must be re-derived when this lands; COBOLNET_CONDITIONS_EXCEPTIONS_DESIGN.md's 'The pickup' bullet describes the unconditional conversion and needs the same correction.
- **Code site:** src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs#EmitPropagationPickup (object branch, the 'rule 4' block); src/Cobol.Net.Compiler/CodeGen/Verbs/OoEmitter.cs#EmitInvokePickup (the same pickup at INVOKE sites)

## What the fixer owes
(1) ExceptionState.SetPropagatingLast's object branch checks the object against the PD-header RAISING classes/interfaces at run time (the binder's D-EO5 discharge only covers RAISING identifier-1); (2) CallEmitter.EmitPropagationPickup's object branch and OoEmitter.EmitInvokePickup gate the conversion on the ACTIVATOR's checking (PB408's rule, now for objects). Both arms: CALL and INVOKE pickup.
