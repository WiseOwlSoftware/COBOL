# R26 — HIGHEST/LOWEST-ALGEBRAIC take a user-defined function (folding a constant from its temp) and refuse the report/page counters that ARE category-numeric data items

> R00 ledger-audit orphan (2026-08-08): F76 + F77 of `PHASE-B-15.32-15.44-findings.md`, probe-verified OPEN
> against the R10-landed tree (`5312996a`). The probe programs are reproducible from the finding text.

PROBES (2026-08-08):
- `COMPUTE R = FUNCTION HIGHEST-ALGEBRAIC(FUNCTION MY-FN)` over a prototyped UDF RETURNING PIC S9(4) —
  accepted, folds +9999 from the TEMP's picture (prints 00000999I); §15.43.3 r1 forbids an integer/numeric
  function as argument-1. The BoundFieldOperand guard passes because the UDF binds to a temp Place
  (ledger F76: the fix is a positive is-a-user-declared-data-item test in BindAlgebraicFold, NOT in
  OperandOf — other verbs need that mapping).
- `FUNCTION HIGHEST-ALGEBRAIC(LINAGE-COUNTER OF F)` → COBOLNET1516 "not a … DATA ITEM", but §8.5.2.12
  items 3/4/5 make LINE-COUNTER/LINAGE-COUNTER/PAGE-COUNTER category-numeric DATA ITEMS, so r1 admits them
  (ledger F77). The fold needs their implementor-defined PICTURE — a decision about the registers' declared
  capacity, then the guard widens. Both directions live in the same guard; land together.

## LANDED 2026-08-08

Both arms in `BindAlgebraicFold`, landed together as the note demanded. **The UDF exclusion (F76):**
`DataItem.IsCompilerTemp` — set ONLY in `CreateCompilerTemp`, THE ONE synthesized-temp constructor, so
property temps are covered identically — is the positive is-a-declared-item test; a function-result
argument now draws COBOLNET1516 citing r1's own words ("shall not be an integer function or numeric
function" — an exclusion the standard must write because §8.5.2.12 items 6/7 make functions
category-numeric too). Placed in the fold, NOT in `OperandOf`: every other verb legitimately needs the
temp→operand mapping. **The register admission (F77):** `BoundLinageCounterRef`/`BoundReportCounterRef`
operands fold before the data-item pattern. LINAGE-COUNTER's capacity is §8.4.3.14.4 GR1's own tie to
the page size — the LINAGE literal directly (66 → 66), a data-name operand's all-nines maximum;
PAGE-/LINE-COUNTER take the documented implementor shape **PIC 9(18)** (the runtime's long carriers —
CONFORMANCE.md item 216, new). All three unsigned: LOWEST = 0, SMALLEST = 1.

Probes: the UDF shape draws 1516 (folded +9999 silently before); LINAGE folds print 66/0/1. Goldens:
positive `algebraic_counter_registers` (2023 — all six register×function folds, the report counters
folding as compile-time constants with no INITIATE) + negative `algebraic-udf-argument` (reject-at
2002 2014 2023). Gate: Conformance Intrinsic|Corpus 658/658 (+2 = exactly the new cases) · the
algebraic set 31/31 by name · Unit incl. drift 3197/3197 · characterization 33/33.

⚠ **CORRECTION (2026-08-08, caught by [[R23]]'s audit run):** this landing's CONFORMANCE entry was
mis-filed as "§7 item 216" — §7 is keyed to Annex A.1's OWN item numbers (A.1-216 is USAGE POINTER), and
no A.1 item covers the counter registers' size. The determination is unchanged and now lives in

a §7 number is an A.1 citation, never a sequence — and the audit now enforces exactly that.
