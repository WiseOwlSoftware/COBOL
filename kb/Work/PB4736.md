# PB4736 — MCS 85/2002 slice 3: the Communication facility's queues move to the paged store; the landed mcs.lock is skipped where flock fails, so two run units can lose or duplicate a CD message

A slice of `docs/rearchitecture/DESIGN-communication-facility.md` (§6, §9 item 3), which the owner approved on 2026-11-04 (the owner, 2026-11-04: "yes, both approved" (the transports) and "Yes" (both documents and Q1-Q9 as recommended)). Build exactly what that section and the slice's entry say, with its goldens, tests and doc changes in the same landing.

**The defect this slice closes.** The landed store serialises each statement by opening `mcs.lock` with `FileShare.None` (`src/WiseOwl.Cobol.Runtime/Communication/MessageStore.cs#AcquireLock`). On Unix .NET implements that with `flock`, and `SafeFileHandle.Unix.cs` (dotnet/runtime) ignores an `flock` that fails with ENOTSUP or EACCES and opens the file unlocked. On such a file system two run units then run one CD statement at once over the same `mcs-state.json`, and a message can be lost or delivered twice: a wrong answer. Both judges of the transport evaluation (E:/COBOL-coord/scratch/pb4700/TRANSPORT-DECISION.md) found it independently. The slice replaces the lock with the store engine's region-lock mutex and refuses a host whose locks answer `Unavailable` with status 92.

**Landing (2026-11-06, wave 20261885 group C).** Built as DESIGN-communication-facility.md section 6 and section 9 item 3 state: the MCS's queues live in one paged store, `mcs.store`, on the engine's statement entry (`StatementLanding.Complete`); `MessageStore.Run` is one engine statement under the store mutex, and a host whose locks answer `Unavailable` is refused with status 92 before the statement reads anything. The landed `mcs.lock`, `mcs-state.json`, `LockWait`, `AcquireLock`, `Commit`, `TakeBack` and the state's `ToJson`, `Overlay`, `Touch`, `Dirty` and `Empty` are deleted with every caller. A refusal the engine reports is decided inside the hold (a read-only reopen compares the adopted page 2 with the statement's stamp): 92 means no action, 93 means the outcome is not known. Two corrections of the design, both written into it: a device the store never transmitted to is committed at 0 and the first statement cuts it, and a statement answering 92 puts the devices it wrote back, best effort (`McsStore.CutBack`). Left to PB4737 as the design assigns it: the `Waits` table and the bell, so seeding deletes no `Waits` row yet and a RECEIVE still polls. Witnesses: `unit:MessageControlTests` (the region-lock refusal, seeding, devices, the presence byte, 92 and 93), `unit:McsStoreCrashMatrixTests` (every statement kind with the run unit killed after every write and with the host refusing every write from the nth); the `pb4677_mcs_*` goldens and the CCVS programs are unchanged.
