# PB703 — LANDED — a clause-boundary rule enforced per operand

Found 2026-09-05 by the `PB364` implementer (report §"New defect"), by the sweep for PB364's shape:
`grep -rn -A3 "if (!.*\.Add(" src/Cobol.Net.Compiler/` against duplicate-screen diagnostics.

## The rule

§12.4.5.7.3 SR8 (`cite.py --check 12.4.5.7.3 "more than one COLLATING SEQUENCE clause"` → OK 8)): *"Neither
data-name-1 nor record-key-name-1 shall be specified in more than one COLLATING SEQUENCE clause."* The Format-2
figure (§12.4.5.7.2 and its figure note) writes `COLLATING SEQUENCE OF { data-name-1 | record-key-name-1 } … IS
alphabet-name-3` — the ellipsis applies to the brace group, so one or more such names may be listed, and nothing
requires distinctness. One clause is not more than one clause.

## The mechanism

`src/Cobol.Net.Compiler/Binding/DataBinder.cs` ≈966–977: `var seenInClause = new HashSet<string>(…)` is declared
outside `foreach (var (names, _) in file.KeyLevelCollating)` while `seenInClause.Add(n)` runs in the per-NAME loop,
so it screens per operand across every clause at once; the variable's name describes the intended scope, not the
implemented one. **Repro** (`<a9d94900 scratch>\PB364\probe\COLLSAME.cob`): an INDEXED file whose FILE-CONTROL
entry carries `COLLATING SEQUENCE OF IX-KEY IX-KEY IS ALPHA-X` → `error COBOLNET1582: file 'IX': key 'IX-KEY' is
named in more than one COLLATING SEQUENCE clause (ISO 12.4.5.7.3 SR8)` at every edition the clause exists in.

## Fix

PB364's shape: the clause is the unit, so stage each clause's names and fold at the clause boundary — or hoist
PB364's `UseOperandRegister<TKey>` (`ProcedureTableBuilder`, private today) somewhere shared: its ordinal is "which
occurrence of the enclosing construct", nothing USE-specific, and this is its second consumer, which is the signal
to extract it. Positive golden with a key named twice in one clause; the existing negative for two clauses kept;
sweep the other `seenIn…` sets in `DataBinder` for the same declared-outside-the-loop shape while there.

## Landed — 2026-09-05

**Reproduced first, on this tree's own `cobol.exe`:** `tests/conformance/2002/pb703_collating_key_named_twice.cob`
(`COLLATING SEQUENCE OF IX-KEY IX-KEY IS REV`) drew
`error COBOLNET1582: file 'IXF': key 'IX-KEY' is named in more than one COLLATING SEQUENCE clause
(ISO 12.4.5.7.3 SR8)` — the diagnostic's own text falsified by a program with one clause.

**The rule, re-derived.** §12.4.5.7.3 SR8 counts CLAUSES: *"Neither data-name-1 nor record-key-name-1 shall be
specified in more than one COLLATING SEQUENCE clause."* The Format-2 figure was RENDERED from the printed page
(PDF page 352 / folio 322) rather than read from the transcription: it writes
`COLLATING SEQUENCE OF { data-name-1 | record-key-name-1 } … IS alphabet-name-3` with the ellipsis immediately
right of the CLOSING BRACE, so by §5.2.7 the repeated portion is the brace group and nothing requires the
repetitions to be distinct. One clause may list a key twice, and one clause is never *more than one*.
§12.4.5.7.4 GR6 is indifferent — `ResolveKeyCollating` takes the first clause naming the key, and a key written
twice in one clause is named by that one clause.

**The fix is the EXTRACTION, not a scope narrowing.** PB364 had already met this rule shape on §14.9.49.3's four
USE rules and built a private `UseOperandRegister<TKey>` for it; this note is its second consumer, so the register
is now `src/Cobol.Net.Compiler/Binding/ConstructOperandRegister.cs` — ONE duplicate-operand screen for every rule
whose boundary is a CONSTRUCT and whose subject is an OPERAND written inside it, with the consumer list in its own
doc comment. `DataBinder.ResolveFileCollating` registers per clause and calls `EndConstruct()` at the clause
boundary; the `HashSet` hoisted out of the clause loop is gone.

**One correction to the register while extracting it.** Its ordinal was FIRST-seen, which reports one violation
twice: both writes of `… OF K K` in a SECOND clause compare against the ordinal of the FIRST clause. It now
remembers the LAST construct that registered a key. That is measured, not reasoned — flipping `Register` back to
first-seen turns all seven `*_DiagnosedOnce` rows red at once
(`UseF1_SameFileRepeatedInTheSecondStatement_DiagnosedOnce` ×4 editions,
`KeyLevel_SameKeyRepeatedInTheSecondClause_DiagnosedOnce` ×3); it was fired red before the assertion was trusted.
The pre-fix `HashSet` had the same fault: it emitted COBOLNET1582 TWICE for that program (measured).

**Sweep (the requested `seenIn…` / hoisted-set sweep of `DataBinder`).** Two other `if (!x.Add(…))` screens exist
and NEITHER is this shape: `ExpandType`'s `expanding` set is a recursion-cycle detector whose scope is the
expansion CHAIN (§13.18.58.3 SR2), and `CloneItem`'s `_typedIndexNames` is per PROGRAM UNIT because its rule is
"referenced at most once" over the whole unit. The three per-construct "specified only once" screens in
`DataBinder` (§5.2.6.4 on the USAGE clause's float-format phrases, §13.18.13.2 on CODE-SET's FOR alternatives,
§12.4.5.7.3 SR3's file-level count) all accumulate in a LOCAL of the clause being bound and are correct. Widening
to the whole compiler, `EcBinder.CheckSr14Sr15` looked like the shape and is not: §14.9.28.3 SR14/SR15 count
occurrences "within the scope of a format 3 PERFORM statement", so the census across all WHEN phrases is the
boundary the rule names (its diagnostic TEXT is loose about it — see the new-defect paragraph in the report).

**Coverage.** `conformance:FileCollatingSequenceSpecTests` is the clause's home: both SR8 arms and the
one-diagnostic count at 2002/2014/2023, SR3, SR4, and the 85 edition gate (COBOLNET0900 and NOT SR8). Goldens:
`tests/conformance/2002/pb703_collating_key_named_twice` (the legal repeat, whose OUTPUT also proves GR6 — the
prime key under `REV` reads Z,M,A and the alternate under `DREV` reads 3,2,1 = A,Z,M, so neither half can pass
with the other's sequence or with native ordinals) and
`tests/conformance/negative/pb703-collating-key-in-two-clauses` (`*> reject-at: 2002 2014 2023`).

**Rows.** SR-12.4.5.7.3-3, SR-12.4.5.7.3-4, SR-12.4.5.7.3-8 and GR-12.4.5.7.4-6 to CONFORMS (GAP 2851 → 2847).
SR5 is deliberately NOT claimed: the SR4 test names a data-name, not a record-key-name. A second batch re-wrote
the `code-location` of PB364's SR-14.9.49.3-8 and SR-14.9.49.3-14, which named the register in its old home.

**Docs.** `COBOLNET_FILES_DESIGN.md` gains the clause's section (the boundary, the register, the edition posture,
the witnesses); `COBOLNET_CONDITIONS_EXCEPTIONS_DESIGN.md`'s USE paragraph now names the shared type, its home and
