# PB4454 - a GLOBAL file's operands in a contained program have no place

**Sites:**
- `src/WiseOwl.Cobol.Compiler/Binding/Passes/PlaceTablePass.cs` (`PlaceTablePass`)
- `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/KeyedIoEmitter.cs` (whole: the RELATIVE KEY site at line 494)
- `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/SequentialIoEmitter.cs` (whole: ASSIGN USING at line 446, VARYING DEPENDING at line 890)
- `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/SortEmitter.cs` (whole: the sites at lines 332 and 385)

**Seen.** The branch review of w20261827a found this in round 2 (lead R2-1, low as a review lead, but a crash on legal
source). PlaceTablePass builds a contained program's table from its containers' GLOBAL items only (§2023:13.18.27.4 GR2: a
contained program may not name a container's non-GLOBAL item). The emitters, however, ask that table for the operands
of a GLOBAL FILE declared in the container. A RELATIVE KEY, an ASSIGN USING data-name, a VARYING DEPENDING item and a
SORT key can each be a non-GLOBAL item of the container, and the compiler then throws InvalidOperationException. On
main before PB2375 the same source produced C# that failed with CS0120. Both are a failure to compile legal source.
Only FILE STATUS uses the right mechanism (`anc.Places` plus `AnchorPlace`): the operand is the FILE's, reached through
the container that declares it, not a name the contained program writes.

**Fix.** A GLOBAL file's own clause operands are resolved at the container that declares the file, and they reach the
contained program's I/O statements through that file's anchor, as FILE STATUS already does: one mechanism for every
file-clause operand. Sweep every file-clause operand the emitters read, and add goldens: a contained program that
READs, WRITEs and SORTs a container's GLOBAL file whose RELATIVE KEY, ASSIGN USING, VARYING DEPENDING and SORT key are
non-GLOBAL container items. Cite the clause with `cite.py --check` before writing the expected output.

**Landed (wave 20261839, group A).** Re-probed on the PB2375 tree: RELATIVE KEY (READ/WRITE/SORT GIVING), RECORD VARYING
DEPENDING ON and LINAGE operands each threw InvalidOperationException from `PlaceTable.Of`; the note named three of the five
operands (the LINAGE operands were a sibling it did not list, `SequentialIoEmitter.LinageOpExpr`), and an SD cannot be
GLOBAL (COBOL1970), so there is no SORT-key operand. The ASSIGN USING operand failed the same way.

The shape differs from the note's "anchor" fix and is the stronger one: FILE STATUS used a one-off re-anchoring of a place
built in the container (`AnchorPlace`, `EmitterState.InheritedStatusPlace`), total only for a plain item. Every operand is
now one list, `FileModel.ClauseOperandItems`; `DataBinder.GlobalFileOperandRoots` takes the roots outside any global
record; `InheritStep.ContainerBridgedRootsOf` bridges them (the C# half, member names reserved) without offering a name
(ISO 13.18.27.4 GR2); `GlobalPlaceableItems` puts them in the contained unit table. FILE STATUS rides the same list, and
the special mechanism (`AnchorPlace`, `InheritedStatusPlace`, `AccessPath.Reroot`, `RootFieldSegment.Anchor`) is deleted.
`FileClauseOperandDriftTests` is red until a new data-item property of `FileModel` is on the list.
Goldens: `cases/13.18.27-GLOBAL/pb4454_contained_io_on_global_file_clause_operands`, `..._assign_using`,
`pb4454_global_file_operand_beside_intermediate_same_name` (two levels out, RECURSIVE container, an intermediate local
of the same name).
