# PB5770 - a sequential READ's record lock is set outside any cross-run-unit hold, and a refused grant is dropped

**Sites:**
- `src/WiseOwl.Cobol.Runtime/IO/FileRegistry.cs:2377` (`FileRegistry.ApplyPostReadLockActions`, where the lock grant's
  result is discarded; `FileRegistry.ReadShared`, `FileRegistry.ReadSharedInStatement`)
- `src/WiseOwl.Cobol.Runtime/IO/FileConnector.cs:938` (`FileConnector.BeginStatement`: inert for every organization but
  the keyed ones)
- `src/WiseOwl.Cobol.Runtime/IO/Sharing/PhysicalFileTable.cs:198` (`PhysicalFileTable.LockRecord`)
- Landed fix (PB5770): `src/WiseOwl.Cobol.Runtime/IO/FileRegistry.cs` (`FileRegistry.ApplyPostReadLockActions` now returns the refused
  grant's status; `FileRegistry.ReadSharedInStatement` and `FileRegistry.ReadKeyedSharedInStatement` make it the READ's status;
  `FileRegistry.ReadLockWindow`, the test seam); witness `CrossRunUnitSequentialLockDriftTests.ALockGrantAnotherRunUnitTookFirst_IsTheReadsStatus`.
  Review R1-1: `FileRegistry.GrantReadLockBeforeRetrieval` takes a lock-setting READ's grant before its retrieval (GR9's RETRY,
  GR10a's unchanged position), `FileRegistry.ReleaseUnusedReadLockGrant` gives it back when no record is made available,
  `FileRegistry.NoLockQuestion` peeks for a READ that sets a lock, GR22's skip-scan skips a refused post-retrieval grant;
  witness `CrossRunUnitSequentialLockDriftTests.ARefusedLockGrant_IsRetriedUnderTheRetryPhrase`.
  The REWRITE's lock set at completion (`FileRegistry.RewriteSharedInStatement`, `_physical.LockRecord` for GR12c) also drops its result; the
  rewrite has already happened there, so it is not this fix's shape (see the report's lead).

**Rule.** §2002:12.3.4.8.3 GR8: "The setting of a record lock is part of the atomic operation of an I-O statement"
(`cite.py --check` OK). §2002:14.8.29.3 GR10c and §2023:14.9.30.4 GR11c: "If the lock mode is automatic, the record lock
associated with a successfully accessed record is set" (both OK), and §2023:9.1.16: "While locked by a given file
connector, a record is not accessible to another file connector in the same or a different run unit" (OK). 2023 has no
sentence with GR8's words (`cite.py --find "atomic operation"` finds none), but GR11c and 9.1.16 together still require that
a READ which answers success holds the lock it was required to set. 1985 has no record locking; no 1985 row is claimed.

**The code** (read on this branch's tree, 2026-11-15):

```
    private void ApplyPostReadLockActions(ConnectorShare meta, PhysicalFileTable.State st, string name,
        FileConnector c, string recId, FileRecordLock phrase)
    {
        ...
        if (ReadSetsRecordLock(meta, phrase) && LocksEffective(meta, st, name))
            _physical.LockRecord(st, name, recId, c);           // GR11 c)/d)
        else if (meta.Multiple && phrase == FileRecordLock.WithNoLock)
            PhysicalFileTable.ReleaseSingle(st, name, recId);   // GR11 b)
    }
```

`PhysicalFileTable.LockRecord` returns `FileStatusCode.RecordLocked` ('51') WITHOUT recording the lock when another run
unit holds the record's byte (`case RegionLockResult.Held: return FileStatusCode.RecordLocked;   // 51 — another run unit
holds it`). `FileRegistry.ReadShared` runs the READ inside `Require(name).BeginStatement()`, which for a
`SequentialConnector` is `FileConnector.BeginStatement` (`internal virtual StoreStatement BeginStatement() => default;`,
"Inert for every organization but the keyed ones"); only `KeyedConnector` overrides it with the store mutex (PB2660). So
for a sequential file the conflict test (`HoldingsConflict`), the read and the lock are three steps another run unit can
interleave with.

**Failure.** Run unit A READs record R of a shared sequential file under LOCK MODE AUTOMATIC: R is unlocked at the
conflict test; run unit B locks R; A's `LockRecord` answers '51' and records nothing; the result is dropped and A's READ
answers '00' with the record, holding no lock. A then REWRITEs a record B holds locked, or B's update is lost. Expected
(GR8, GR11c): A either holds the lock or gets the conflict status.

**Witness needed (the fix's job).** Two processes on one shared SEQUENTIAL file under LOCK MODE AUTOMATIC with a forced
interleaving (a test hook between the read step and `ApplyPostReadLockActions`), asserting A's status is 51 or that A
holds the lock; a plain race is not a reliable witness. The draft's user-level sketch is
`E:/COBOL-coord/scratch/gl2002/lane1/out/g2002u-12-3-4-5-alternate-record-key/defects/seq-lock-not-atomic.cob`.

**Fix direction (root).** Give the sequential connector a cross-run-unit statement hold as PB2660 gave the keyed store, or
make the lock grant itself the conflict test (take the lock, then read) and propagate a refused grant as the READ's
status. Sweep the other discarded `_physical.LockRecord` results in `FileRegistry.cs` (lines 899, 2644 and 2713; the
public `FileRegistry.LockRecord` at 2817 returns it) for the same pattern on the sequential organization; PB2749 and PB2759 restructure the same lock governance and should
not duplicate this fix.
