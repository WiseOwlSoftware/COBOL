# PB3499 — the second-attempt gate is a proxy

Lead R1-2 (low) of the branch review of PB3482 (`E:/COBOL-coord/scratch/reports/w1140c-PB3482-report.md`).

`src/Cobol.Net.Runtime/IO/Sharing/RunUnitFileLock.cs` about line 126: the second-attempt gate asks whether ANY other INPUT opener holds a column, a proxy for the one case that needs it (an INPUT opener holding a WRITABLE handle because its transaction owes writes). So on Windows a SHARING WITH READ ONLY OPEN (the default of a clause-less OPEN INPUT, DOC-A.1-77) beside an outside writer changes from 61 to 00 whenever an unrelated WiseOwl ALL OTHER INPUT reader is open, and its handle then admits outside writers for the rest of the OPEN. The design doc (`docs/rearchitecture/DESIGN-runtime-library.md`) names the consequence. No test pins the 61 to 00 arm; only the no-INPUT-opener arm is pinned (`AReadOnlyOpenBesideAnOutsideWriterIsRefusedWhereTheShareModeRefusesIt`).

**Open judgment (the clerk did not make it).** Whether the 00 is a wrong answer. §9.1.15 2) (sharing with read only restricts concurrent access through other file connectors to input mode) and §9.1.13.9 1) arbitrate file connectors; an outside writer is not a file connector, so the spec may not decide it, and the choice is then latitude (GnuCOBOL first, CLAUDE.md rule 1). The implementer decides against those clauses (`cite.py --check` each) and sets `wrong_answer` accordingly (filed true so the note surfaces in `work.py next`; it is provisional). If it is wrong: make the gate test the exact condition (the INPUT opener's handle is writable) instead of the proxy, and pin both arms.

## Landed

**Re-probe (Windows, a fresh build).** The new `FileLockPostureDriftTests.AnInputOpenerThatOwesNoWritesDoesNotAdmitAReadOnlyOpenBesideAnOutsideWriter`
(all three organizations: an ALL OTHER reader open, a bare writer open, `OPEN INPUT` under `SHARING WITH READ ONLY`) answered '00'
where the same OPEN with no reader open answers '61' (`AReadOnlyOpenBesideAnOutsideWriterIsRefusedWhereTheShareModeRefusesIt`).

**The judgment: it is a wrong answer.** Section 9.1.15 2) (`cite.py --check 9.1.15`: *"restricts concurrent access to a physical
file through file connectors other than this one, to input mode"*) arbitrates file connectors, and an outside writer is not one,
so the standard does not decide it and the choice is implementor latitude (§9.1.15, *"their interaction with COBOL file sharing is
defined by the implementor"*, Annex A.1 item 75). GnuCOBOL has no Windows share-mode determination to follow, and the project's own
determination (`docs/CONFORMANCE.md` DOC-A.1-75, DESIGN-runtime-library.md 2.2.1.8's determination) already says the opposite of the
code: *"a program outside the protocol that holds the file open for writing, with no WiseOwl COBOL INPUT opener beside it, still refuses
a READ ONLY request '61'"*. The proxy made the answer depend on an unrelated reader (and weakened the OPEN's handle to `FileShare.ReadWrite` for
its whole life), so the code, not the determination, was wrong. `wrong_answer: true` stands.

**The root.** The gate asked "does another INPUT opener hold a column", a fact of the table, where the share mode needs a fact the table
does not carry: another connector's handle is open for WRITING while its mode is INPUT. That fact is now published by the holder itself,
as one more exclusive byte of an owed-writes range beside the columns' (`HostRegionLocks.OwedWritesRangeStart`, written by
`HandleColumnLockHost`), in the same `IColumnLockHost.Establish` request as its column (`owesWrites`), by both `RunUnitFileLock.Take`
and `Amend` (and put back by `Revert`), and tested exactly as a column's range is (`RunUnitFileLock.AnotherOwesWrites`, replacing
`AnotherInputOpenerHolds` and the host's `AnotherHolds(column)`, both deleted). The connector says it before the body from what the CLOSE
kept (`FileConnector.OwesWrites` / `KeyedConnector.WillTakeWritableHandle`, the one expression `KeyedConnector.Lock` opens the handle by,
now `HandleAccess`), and after the body from the handle (`FileLock.CanWrite`) on the arm that takes its column after it (a CLOSE under
`SHARING WITH NO OTHER`, whose kept `FileShare.None` handle publishes no column). The Linux and lock-file hosts ignore it: they have no
mandatory share mode to yield.

**Sibling sweep.** The other consumers of the second posture (`FileConnector.HostShare`, `FileLockPosture.WhenOwedWritesAreAdmitted`)
read `_ownedWritesAdmitted`, which only `Open` sets, after this gate. The two arms by which a connector's column is established (a kept
column's `Amend`, a fresh `Take`) both carry the fact, and each has its own end-to-end witness; the proxy appeared in no other place
(`grep AllOtherInput|ReadOnlyInput src`: Table 19 and the wire numbers only).

**Witnesses.** `FileLockPostureDriftTests.AnInputOpenerThatOwesNoWritesDoesNotAdmitAReadOnlyOpenBesideAnOutsideWriter` (was red, three organizations),
`HandleColumnLockHostDriftTests.AHolderThatOwesWritesIsSeenByAnotherHolderAndOnlyByAnother`, `OwingWritesChangesNoAnswerOfTheTable` (every
request), `TheOwedWritesRangeLiesPastEveryColumnsRange`, `CommitRollbackRuntimeTests.An_input_opener_whose_column_is_taken_afresh_after_a_NO_OTHER_close_publishes_that_it_owes_writes`
(red when the `Take` arm is not carried) and the existing `An_input_opener_that_owes_its_transactions_writes_admits_what_Table_19_admits`
(red, all eight cases, when `Amend`'s arm is not carried). `AnOpenWhoseSecondAttemptIsRefusedTooAnswers61AfterExactlyTwoRequestsAndLeavesNothingBehind`
and `A_reopen_refused_on_its_second_attempt_too_keeps_what_the_close_kept_and_makes_no_third_attempt` named the proxy in their setups (a plain reader
that owes nothing stood for the writer's owner); they now hold a lock that owes writes.
