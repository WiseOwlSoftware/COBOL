# PB2114 — unify the grammar alternatives the legacy forced (R69)

Plan §0's standing caution: "A SHARED-GRAMMAR CHANGE MUST BE ADDITIVE UNTIL P15. Collapsing a rule to a shared one
deletes the generated `.dataReference()` / `.literal()` accessors and breaks the LEGACY compiler … Add an
alternative; unify at P15." Several landings did exactly that (DEVLOG 2288: PB1135's `callArgument` /
`callByContent` / `invokeArgument`; DEVLOG 20601 records them as ADDITIVE grammar alternatives placed so the legacy
compiler kept parsing). Each is a duplicated rule shape kept for a consumer that no longer exists.

**Prerequisite:** PB2110 landed. **Model:** Opus (grammar).

## Scope

1. Measure, never deduce: find every alternative added for the legacy — `grep -n -i "legacy\|additive" src/**/*.g4`
   and the DEVLOG mentions of "additive" grammar alternatives — and list each with the rule it duplicates in the
   implementer report (not in this note).
2. Unify each into one rule where the spec's general format has one shape; delete the accessor the legacy needed
   and change every greenfield binder caller in the same change.
3. Delete the caution from plan §0 and `DESIGN-frontend-grammar.md` where it is restated (if PB2111 has not).

## Verification

The token-stream and parse-tree shape differentials over the whole lexer-input population (DESIGN-architecture-review
§4 item 3), the whole-population gate, the Linux gate, CI. A unification that changes a parse is not a unification;
it is a finding for the fix lane.

## Landed (wave 1028 group D)

**Measured list.** Nine copies of the sending operand `{identifier-n | literal-n}` (`literal | functionCall |
inlineMethodInvocation | dataReference`): `addOperand`, `subtractOperand`, `multiplyOperand`, `divideOperand`,
`moveSendingOperand`, and inline in `writeFrom`, `rewriteFrom`, `releaseFrom` and `initializeReplacingItem`, plus
`inspectChar` (the same set with an unreachable `figurativeConstant` arm: `literal` reaches every figurative first).
Three copies of the arithmetic TO / FROM / INTO union (`addToPhrase`'s four `TO …` alternatives, kept apart from a
wrapper rule for the legacy `.receivingArithmeticOperand()` read, `subtractFromOperand`, `divideIntoOperand`), four
identical GIVING phrases, and the two `xOperandList` wrappers.

**Unified.** `sendingOperand` (CobolParserCore.g4) is the one rule for all ten positions; `receiversOrSendingOperand`
for ADD TO, SUBTRACT FROM and DIVIDE INTO; `arithmeticGivingPhrase` for the four GIVING phrases. The binders read the
one `SendingOperandContext` through `MoveBinder.SendingOperand` (MOVE, the three FROM phrases, INITIALIZE after its
NULL arm); INSPECT keeps its §14.9.22.3 screens over the same node and lost the dead `figurativeConstant()` lookup.
`ArithmeticOperandRole.MixedRules` is two rules. `ArithmeticSendingOperandDriftTests` (which pinned four copies
identical) is replaced by `SendingOperandDriftTests`, which fails on any rule writing the set out. Plan §0's
"A SHARED-GRAMMAR CHANGE MUST BE ADDITIVE UNTIL P15" caution is deleted; DESIGN-frontend-grammar §3.15 records the
shape rules.

**Kept, by measurement.** DISPLAY's inline set: naming `sendingOperand` there parsed all legal source identically but
changed 83 error-recovery trees (17 with a higher syntax-error count; `DISPLAY COLUMN.` at 85 went from 1 to 2), so
it is the drift test's one recorded exemption. MULTIPLY's `multiplyByOperand+` admits a repeated or ROUNDED sending
operand that the binder names, so folding it into `receiversOrSendingOperand` would change what parses.

**Neutrality.** Token-stream and parse-tree-shape differential over every lexer input the three test assemblies
produce (compile cache off, external GnuCOBOL corpus present): 20,494 inputs common to both runs with identical token
streams (the rest are randomized PROGRAM-IDs, different in every run) and 0 tree-shape differences with the new
wrapper rules flattened; 7,624 of the inputs parse a `sendingOperand`, 3,167 a `receiversOrSendingOperand`.
