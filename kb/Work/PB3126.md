# PB3126 — a failed agent spawn loses a review round, and the watchdog cannot get past it

> flags: process-only

Source: wave unit 2026-10-13 (wave 1071, run `wf_4959cab1-c5a`).

**What happened.** Group B's round-2 review (`w1071b-review-r2`) found 2 findings on
`worktree-wf_4959cab1-c5a-11` @ `1a473341f`, one of them a medium correctness finding (an object data-name spelled
like a METHOD-ID now passes binding and dies in Roslyn with CS0102: `E:/COBOL-coord/scratch/review-w1071-b.jsonl`).
The workflow then called `agent()` for `fix-B-r2`. The journal recorded
`{"type": "failed", "key": "v2:f192e0a0…", "agentId": ""}`. No transcript or `.meta.json` exists for it, but its
isolation worktree was created: `E:\COBOL\.claude\worktrees\wf_4959cab1-c5a-20`, branch
`worktree-wf_4959cab1-c5a-20`, clean at main's `3b1261dfe`, with no commit. `wf_rolling_wave.js` `reviewed()` catches
the throw as `NO-RESULT` (`try { f = await fixFindings(...) } catch (e) { f = null }`). That is the right outcome for a
finisher that ran and failed. It is the wrong outcome for an agent that never started: the branch kept its
`FINDINGS 2` stamp and waits a whole wave for a finisher that one retry would have started at once.

**How often.** Under this account's project, 4 `failed` entries with an empty `agentId` appear in 3 of the 37 workflow
journals: `wf_8f6c2cfa-5a7` (2026-10-10, 2), `wf_787860dd-104` (2026-10-12, 1) and `wf_4959cab1-c5a` (2026-10-13, 1).
Measure with
`grep -h '"type": *"failed"' ~/.claude-acct2/projects/E--COBOL/*/subagents/workflows/*/journal.jsonl`.

**The watchdog arm.** `stall_watch.py` reported `(): FAILED (the agent died; the journal holds no result)` and exited,
which is its notify-by-exit design (O8). But the failure stays in the journal, so a restarted watchdog reports the same
entry and exits again at once. It has no way to acknowledge a known failure (no `--ack <key>`, and no "only entries
after my start"). For the last ~35 minutes of wave 1071, fix-A-r1, fix-F-r1/r2, three reviews and the G review ran
unwatched; the unit fell back to `--once` snapshots between waits. Its empty label `()` also hides which call failed:
the `failed` entry carries no label, so the watchdog would have to take it from the matching `started` key, and a
spawn that failed never wrote one.

**Fix shape (to be confirmed by the implementer).**
1. `wf_rolling_wave.js`: tell "never spawned" apart from "ran and returned nothing". When the rejection carries no
   agent id (or the journal's `failed` entry has an empty `agentId`), retry the same `agent()` once before falling
   back to `NO-RESULT`, and log the retry. This applies to every `agent()` arm (implementer, reviewer, finisher), not
   only `fixFindings`.
2. The orphan worktree: let the retry reuse it, or have `prune_worktrees.py` classify a clean worktree at a main
   commit, with no report and no commits, as LANDED, so `--apply` removes it. Check which one the survey already does
   before changing it.
3. `stall_watch.py`: report each `failed` key once, then keep watching. Either take `--ack <key>…` or skip `failed`
   entries already present at start. Name the failed call from the workflow's own log line when the journal has no
   label.

**Done when.** A spawn failure in a rolling wave is retried once and logged, a restarted watchdog keeps watching past
a known failure, and a self-test covers both (a journal fixture with a `failed`/empty-agentId entry).

## Third arm (wave 1072/1072b/1073, handoff of the wave unit that ended 2026-10-14 ~03:40Z): the harness refuses the isolation worktree

7 of that wave unit's 26 `agent()` spawns failed before starting. The harness refused the isolation worktree with
"protected checkout E:\COBOL has git metadata that could not be resolved", "git could not be run", and "could not read
the repository git config". This is not tied to a `.git/config` write. The empty worktrees it left (872-1, 872-6,
872-8, 872-12, b3b-1, and others) held no commits. It is the same never-spawned shape as the arm above (journal
`failed`, no agent id), so fix shape item 1's single retry covers it, and item 2's orphan-worktree classification
(clean at a main commit, no report, no commits) matters more: there are now several such worktrees per wave. Whether
the retry should wait (the failures may be a transient git-metadata race on the protected checkout) is for the
implementer to measure.
