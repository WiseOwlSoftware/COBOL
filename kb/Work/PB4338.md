# PB4338 — the population check misreads astral characters in theory names

**Found** by the PB4264 finisher (wave 20261791 group A, branch `worktree-wf_15d43d1b-129-12`, report
`E:\COBOL-coord\scratch\reports\w20261791a-PB4264-report.md`, "Review findings", LEAD carried from round 0), and seen
again by the PB380 finisher (group B, report `w20261791b-PB380-report.md`, "Gate": run `000001-20261101T015900Z` was RED
on the Unit POPULATION check alone; 4 supplementary-plane theory cases, `NormalizerTests.SpanForm_EqualsTheStringForm`
and `WordCharacterEveryEditionTests`, were NEVER RAN / NOT IN THE POPULATION while all 20,362 + 39,104 + 36 tests passed
on Windows and Linux).

**Sites:** `scripts/test_population.py:125` (`parse_listing`), `scripts/test_population.py:198` (`read_trx`).

**Mechanism.** `dotnet test --list-tests` prints the astral character itself; xunit writes the same display name into the
trx as escaped surrogates (`\ud834\udd5e`). The two readers produce different strings for one test, so the case reads as
both unlisted-but-run and listed-but-never-run on a plan that holds the whole of tier 1.

**When it bites.** Only on a whole-tier-1 plan, which a new source file the impact map has never seen forces (PB380's
first gate), and which a README edit forces too (see PB4339: its fix is held until this is fixed). The PB380 report
names PB4274 as the defect "fixed on the wf_2201113e-54d-26 branch and not yet on main"; no `kb/Work/PB4274.md` exists
on main, so the implementer first checks whether that branch already carries this fix and lands it rather than
re-deriving it.

No spec clause (gate tooling). Do not add a second reader: normalize both spellings at the one parse step.
