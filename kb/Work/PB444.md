# PB444 — SEARCH has no syntax-rule pass, and the one check it has is staged as a missing feature

Adjudicated in lane-3 batch b2 (`search-statement` part 1, finding search-p1-F2). **Re-measured on HEAD
89044aa0.** This note owns the END-SEARCH / NEXT SENTENCE row; the mechanism it names is the shared cause
behind PB443's rows and PB211's.

## 1. The mechanism

`SearchBinder` is the only site in the tree that inspects a SEARCH, and the only conditions it tests are
*"is identifier-1 a table"*, *"does it have INDEXED BY"* and the nested-dynamic-capacity guard. Each is
expressed as a `BoundUnsupported`, which `StatementEmitter.cs:211`
(`Visit(BoundUnsupported n) => _ctx.Writer.Line(LoudStmt(n.Feature))`) lowers to a **run-time throw**, never a
diagnostic. So:

* the one all-formats syntax rule the compiler reacts to (the INDEXED phrase) is delivered as a
  `NotImplementedCobolFeatureException` at run time — **and only if the statement is reached**;
* syntax rule 1, syntax rule 2's second sentence, syntax rule 3's requirement half, syntax rule 4 and both
  sentences of syntax rule 5 draw no reaction of any kind.

Two further defects sit inside those same two lines:

* **The message miscites itself.** `SearchBinder.cs:29` and `:88` both read
  `"SEARCH table '{tableName}' without INDEXED BY (ISO §14.9.37 SR1)"`. The INDEXED requirement is syntax rule
  **2**; syntax rule 1 is the reference-modification prohibition. This is the inherited-citation failure mode
  CLAUDE.md rule 1 names, now **duplicated across two arms and reachable by users in shipped message text**.
* **It labels a USER error as a COMPILER gap.** "a COBOL feature that is not yet implemented" sends the reader
  looking for a missing feature instead of a bad program.

For this note's own row: nothing anywhere pairs a scope terminator with a NEXT SENTENCE phrase. A tree-wide
grep for NEXT SENTENCE in `src/` returns only the archaic-feature warning
(`Validation/VersionConformancePass.cs:670-672`, COBOLNET0903), the bound node, and the lowerings at
`CodeGen/StatementEmitter.cs:199` / `CodeGen/DispatchEmitter.cs:297-330` — for SEARCH or for any other
statement carrying the same prohibition.

```

$ python scripts/spec/cite.py --check 14.9.37.3 "The data description of identifier-1 shall contain an OCCURS clause with an INDEXED phrase and identifier-1 shall not be subscripted at the level for which the SEARCH is applicable"

$ python scripts/spec/cite.py --check 14.9.37.3 "Identifier-1 shall not be reference-modified"

$ python scripts/spec/cite.py --check 14.9.37.4 "the index being varied by the search operation remains set at the occurrence number that caused a WHEN condition to be satisfied"
OK  §14.9.37.4 1) a)  (General rules)

$ python scripts/spec/cite.py --check 4.2.2 "An implementation shall provide a warning mechanism that optionally may be invoked by the user at compile time to indicate violations of the general formats and the explicit syntax rules of standard COBOL"
OK  §4.2.2   (Acceptance of standard language elements)
```

The last two together are why the silence is harmful rather than merely lax. **`§4.2.2` obliges a compile-time
mechanism**, and the CLI exposes no strictness axis in that direction at all — the only related flag is
`--permissive`, which loosens — so the default build *is* the strict mode and each violation below owes a
diagnostic. And the reason the standard forbids the END-SEARCH / NEXT SENTENCE pair rather than defining which
wins is visible in the general rule quoted fourth: with END-SEARCH present, the SEARCH no longer runs to the
sentence's period, so "the next separator period" that NEXT SENTENCE targets is no longer the statement's own
end. Accepting the pair makes this compiler's answer a de-facto extension.

## 4. The code site and the shape of the repair

* `.../Verbs/SearchBinder.cs:28-29` and `:87-88` — the mis-staged, miscited INDEXED check (two copies).
* `.../Verbs/SearchBinder.cs:21-75` / `:81-117` — neither binder inspects `s.END_SEARCH()` at all, and no site
  pairs it with a NEXT SENTENCE phrase.
* `.../CodeGen/StatementEmitter.cs:211` — `BoundUnsupported` → run-time throw, the reason every SEARCH
  "check" is staged wrong.
* `.../Validation/VersionConformancePass.cs:670-672` — the only NEXT SENTENCE site in the tree.

**The right shape is a SEARCH syntax-rule pass that runs at bind time and reports through the normal diagnostic
channel**, with the detected-but-mis-staged INDEXED check *moved into it and re-cited*. Writing syntax rule 4
as a one-off `if` inside `BindSearch` would leave the other five rules, the two copies, and the
`BoundUnsupported`-as-diagnostic confusion exactly where they are. `StatementValidation` already exists and is
where the INITIALIZE rules live; the SEARCH entries belong beside them.

⛔ Distinguish two things the current code conflates: `BoundUnsupported` means *this compiler does not
implement a legal construct* (loud is right), and a syntax-rule violation means *this program is illegal* (a
diagnostic is right). Every SEARCH condition currently expressed as `BoundUnsupported` is in the second
category. The nested-dynamic-capacity guard is genuinely in the first and must stay.

## 5. The sibling sweep the fixer must do

* **Both arms, four times over.** `BindSearch` and `BindSearchAll` each carry the miscited INDEXED check;
  fixing one leaves the other, and the miscitation is *in shipped text*, so it must be corrected in both.
* **Every statement with the END-SEARCH / NEXT SENTENCE prohibition.** The rule shape recurs across the
  conditional statements that admit NEXT SENTENCE. Grep for the scope-terminator/NEXT SENTENCE pairing across
  all of them before assuming SEARCH is the only one — nothing in the tree pairs them anywhere.
* **⛔ Syntax rule 5's second sentence is currently UNOWNED.** `kb/Work/PB211.md` (open) names only the
  operand-**class** screen, so the self-subscript ban — measured above as *silently changing the answer* —
  belongs in PB211's scope and must be added there when it lands. This note does not claim that row.
* **The other miscited diagnostics.** Grep `src/` for `ISO §14.9.37` — the adjudication found 15 hits, all doc
  comments or general-rule-side code, plus these two wrong ones. Re-derive each number with `--check`; a
  citation nobody re-derived is exactly what CLAUDE.md rule 1 forbids.
* **Editions.** Everything here reproduces identically at 85, 2002, 2014 and 2023; nothing is edition-gated.
