# PB3867 — the fuzz_ollama self-test's stub had a racy end-of-request flag

**Sites:** `scripts/fuzz_ollama.py` (`_StubOllama.do_POST`, `self_test`)

## The defect

PB3537 (#676) added a stub Ollama server to `fuzz_ollama.py --self-test`. Each `chat()` call cleared one shared
`threading.Event`, `server.finished`, and each handler set it in `do_POST`'s `finally`. The "length" request's handler can
still be in that `finally` when the test has already read its reply and started the "endless" request, so its `set()`
lands after the "endless" request's `clear()`. `server.finished.wait(30)` after `chat("endless")` then returns at once,
while the endless handler is still streaming and has not yet hit the write error that sets `client_left`, so the check
reads `client_left False, sent_all False` and fails. On Linux it failed 1 run in 8, then 7 in 40, in a WSL clone of main;
it went RED in CI's `audits` job on PR #682 (PB3569), a branch that does not touch the harness, so any landing could
bounce on it.

## The fix

The stub counts handlers that returned (`server.handled`, under a `threading.Condition`) instead of sharing one flag, and
the check waits until every request so far, the endless one included (its body is recorded before it answers), has a
handler that returned. In the same WSL clone: the old code failed 7 of 40 isolated runs, the fix 0 of 40; Windows PASSED.

## Acceptance

- `python scripts/fuzz_ollama.py --self-test` passes every run (0 of 40 on Linux), and no other check reads a shared
  end-of-request flag.
- A red that passes on a re-run is a defect (CLAUDE.md, the gate skill): PR #682's re-run is not the fix; this is.
