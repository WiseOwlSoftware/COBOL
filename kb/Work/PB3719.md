# PB3719 — a predecessor pull request cut off at 100 files is still read by ancestry

**Sites:** `scripts/orchestrator/enqueue.py#open_predecessors` (with `FILES_LISTED = 100` and `PR_LIST_FIELDS`, the `gh pr list --json number,headRefName,headRefOid,files` request).

## What happens

`kb/Work/PB3145.md` (landed) made `open_predecessors` the one reader of "which open pull request owns a stamped DEVLOG entry this
branch carries": it maps each open pull request to the entries its current head adds, by the `files` list GitHub returns. GitHub
lists only the first 100 files (`FILES_LISTED`), so for a pull request that changes 100 or more files the function falls back to
ancestry: `git merge-base --is-ancestor <headRefOid> HEAD` (the branch must CONTAIN the predecessor's current head), then reads the
entries that head adds with `devlog.landing_entries`.

That fallback fails when the predecessor's head moved after the branch merged it (a bounce re-landed with newer main, a catch-up
merge): its new head is no longer an ancestor of the branch. The entry is then not attributed to the open pull request, the branch
carries two stamped entries, `pull_request_text` returns no title, and `enqueue.py land` ends exit 6 NO ENTRY, a stop the landing lane
never relaunches. It should end exit 15 PREDECESSOR QUEUED (a wait the lane relaunches). The PB3145 report called this the residual
("is still read by ancestry and ends exit 6 as before").

## Fix shape

Read the full file list when GitHub cut it off (`gh pr view <n> --json files` is also capped; `gh api repos/.../pulls/<n>/files`
paginates), or read the stamped entry names another way, so ancestry is no longer the only test for a long file list. Add a self-test
to `enqueue` with a 100-file predecessor whose head moved after the merge.

On origin/main `open_predecessors` (enqueue.py near line 667) holds `FILES_LISTED = 100`, `PR_LIST_FIELDS` (line 663), and the
