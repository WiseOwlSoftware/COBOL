# PB2554

Filed by the train 1037b lander from the wave-1037 group H report (lead 1; PB1643 landed in that train).

**What a user sees.** `E:\COBOL-coord\scratch\w1037h\p\oo3.cob`: a class whose SPECIAL-NAMES says DECIMAL-POINT IS COMMA,
invoked from a driver that does not, edits its `ZZ9,99` formal with the driver's period mode. Wrong output, no diagnostic.

**Rule.** §12.3.7.4 GR14 b) (cite.py --check OK): "For the basic format of the PICTURE clause, the character written in
character-strings, and inserted in numeric-edited items to represent the decimal separator shall be the comma" — a
property of the source element that DESCRIBES the item. §12.3.4 GR1 makes a
contained program inherit it; a separately compiled class does not take its invoker's.

**Code sites.** `src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs:663` and `:794` read `ctx.Data.DecimalPointIsComma`
— the EMITTING unit's mode — for an item another unit describes; `ConditionRenderer` and `ValueInitializer` read it the same
way; the OO content conversion in `OoEmitter` crosses the boundary.

**Fix shape.** The decimal-point mode belongs to the item: carry it on `PicInfo` (set where the PICTURE is analyzed, from
the describing unit) and have every editing / de-editing / rendering consumer read the item's, never the context's. A
drift test that no CodeGen site reads `ctx.Data.DecimalPointIsComma` for an item's PICTURE keeps it single.

## Landed (wave 1039 D) -- the decimal-point mode is read off the item

Re-probed on the wave-1039 build before any edit: `w1037h/p/oo3.cob` (DPC class, period driver) printed `I:E=[  0,12]` for both `BY CONTENT 12.5` and `BY CONTENT 12` (the formal edited under the DRIVER's period mode); expected `[ 12,50]` / `[ 12,00]` (ISO 12.3.7.4 GR14 b), `cite.py --check` OK).
Root cause: every editing / de-editing / receiver-scale / edited-image consumer took the mode from `ctx.Data.DecimalPointIsComma` (the EMITTING unit) although the item's PICTURE is described by another unit. Fix as the note's shape: `PicInfo.DecimalPointIsComma` (read off `Clause`, the one record of the describing unit's state, set where the PICTURE is analyzed) is the only source; `EmitCore.EditCfg(pic)`, `PicInfo.ReceiverScale()`, `RuntimeApi.MaskScale`, `AlgebraicRanges.Of`/`OfFunctionReturnedValue`, `ValueInitializer.EditedImageOfNumericValue`, `GroupImageCodec`, `ConditionRenderer` and the binder's `SetBinder`/`IntrinsicBinder` pic arms lost their `commaMode` parameter or read the item, and `DataBinder`'s own pic arms read it too. `DecimalPointModeDriftTests` closes the list of CodeGen / procedure-binder readers of the unit's own mode (NUMVAL parse mode, date-time format literals, the literal image).
Sibling sweep: the mirror (period class, DPC driver), BY CONTENT from a numeric item, from a numeric-edited item of the driver's other mode, and from a literal are all in the goldens; the remaining `ctx.Data` readers are about what the unit itself wrote or runs, listed with reasons in the drift test.
Goldens: `2002/pb2554_class_comma_driver_period`, `2002/pb2554_class_period_driver_comma` (+ `.out`) and `negative/pb2554_decimal_point_class_below_2002` (COBOLNET0900 at 85).
