# PB2554

Filed by the train 1037b lander from the wave-1037 group H report (lead 1; PB1643 landed in that train).

**What a user sees.** `E:\COBOL-coord\scratch\w1037h\p\oo3.cob`: a class whose SPECIAL-NAMES says DECIMAL-POINT IS COMMA,
invoked from a driver that does not, edits its `ZZ9,99` formal with the driver's period mode. Wrong output, no diagnostic.

**Rule.** §12.3.7.4 GR14 b) (cite.py --check OK): "For the basic format of the PICTURE clause, the character written in
character-strings, and inserted in numeric-edited items to represent the decimal separator shall be the comma" — a
property of the source element that DESCRIBES the item. §12.3.4 GR1 makes a
contained program inherit it; a separately compiled class does not take its invoker's.

**Code sites.** `src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs:663` and `:794` read `ctx.Data.DecimalPointIsComma`
— the EMITTING unit's mode — for an item another unit describes; `ConditionRenderer` and `ValueInitializer` read it the same
way; the OO content conversion in `OoEmitter` crosses the boundary.

**Fix shape.** The decimal-point mode belongs to the item: carry it on `PicInfo` (set where the PICTURE is analyzed, from
the describing unit) and have every editing / de-editing / rendering consumer read the item's, never the context's. A
drift test that no CodeGen site reads `ctx.Data.DecimalPointIsComma` for an item's PICTURE keeps it single.
