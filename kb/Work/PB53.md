# PB53 — LANDED — the wrong clause, applied conservatively, is still the wrong clause

> ⚙ **FILED WHILE CLOSING [[PB46]]'s INVOKE HALF, DELIBERATELY NOT FOLDED INTO IT** — and the reason it was
> filed rather than fixed then still holds: the EMITTER half is the load-bearing one, and it needed the
> conformance screen corrected first to become reachable at all.

## ⛔ MEASURED — three pairings the standard admits, refused

```
INVOKE O "TAKEN" USING BY CONTENT B1   (PIC 1(4) → PIC N(4))
  ⛔ COBOLNET0828: … does not conform to formal 'P': category mismatch (formal National, argument Boolean)
INVOKE O "TAKEB" USING BY CONTENT A1   (PIC X(4) → PIC 1(4))
  ⛔ … category mismatch (formal Boolean, argument Alphanumeric)
INVOKE O "TAKEB" USING BY CONTENT N1   (PIC N(4) → PIC 1(4))
  ⛔ … category mismatch (formal Boolean, argument National)
```

§14.9.25.3 **Table 16** admits all three: boolean→national **Yes**, alphanumeric→boolean **Yes**,
national→boolean **Yes**. And each diagnostic cited **§14.8.2.3.3** while applying **§14.8.2.3.2** — the
citation named the right clause and the code ran the other one.

## ▶ THE CAUSE WAS A COMMENT THAT DESCRIBED THE DEFECT AS A VIRTUE

`OoContentMismatch`'s default arm read:

```csharp
_ => OoConformance.DescriptionMismatch(formal, arg, anyLengthActivationRelax: true),
   // edited/other: conservative strict gate
```

`DescriptionMismatch` is **§14.8.2.3.2 — the BY REFERENCE identity rule**. It is exactly right there and it is
the wrong rule for BY CONTENT, which §14.8.2.3.3 rule 2d sends to MOVE. "Conservative" reads as *safe*; what it
actually described was *rejects legal source*, which CLAUDE.md rule 4 forbids outright. A gate that is stricter
than the standard is not a cautious version of the right answer.

## ⭐ THE FIX IS ONE TABLE 16, IN ONE PLACE, WITH TWO CALLERS

`MoveTable16.Refusal(sender, receiver)` over a `Table16Operand` — the axes the table actually keys on, which are
finer than `PicCategory`: **alphabetic** and **alphanumeric-edited** are separate rows/columns while sharing one
category here, and the numeric row splits **integer vs noninteger**. `MoveBinder` and `OoContentMismatch` both
ask it.

⚠ **WHAT STAYED WITH `MoveBinder`, because it is not a category question:** §14.9.25.3 **SR7** (a figurative
whose characters are not boolean characters, and the ALL-literal form of the same) and **SR8** (the fixed-width
binary family). Those key on the bound operand's SHAPE, which no category table can see. Extracting them too
would have been the tidier-looking change and the wrong one.

## ⛔ THE EMITTER HALF WAS ONLY SAFE BECAUSE THE BINDER OVER-REJECTED

`OoStringReadOf` width-fitted for an ALPHANUMERIC formal and passed everything else through verbatim. That was
correct *only* while strict identity guaranteed both sides matched in category and width — **correcting the
screen made this line load-bearing in the same change set**. It now reaches
`MoveEmitter.ConvertSource`, where the receiving category's store discipline is already written once: boolean
pads and truncates in boolean ZEROS (§14.6.8.6), alphanumeric in spaces, national in national spaces, a
numeric-edited receiver EDITS (§14.9.25.4 GR5). The identical-category alphanumeric case keeps its proven fast
path byte-for-byte.

## ⚙ VALIDATED AS AN AGREEMENT, WHICH IS WHAT THE RULE ACTUALLY SAYS

Rule 2d does not prescribe values — it says the crossing behaves **as a MOVE does**. So
`pb53_by_content_move_rules` performs each transfer TWICE, once across the INVOKE and once as a plain MOVE, and
prints both; a pair that disagrees is a violation whatever either value is. All six pairs agree, including the
two WIDTH-DIFFERING crossings strict identity had made unreachable (`PIC 1(6)`→`PIC 1(4)` = `1100`,
`PIC X(6)`→`PIC 1(4)` = `ABCD`, both right-truncated per §14.6.8.6) and an identical-description control that
must keep taking the fast path.

⚠ **A NOTE ON WHAT THE PAIRS DO NOT ASSERT.** `MOVE A1 TO <boolean item>` stores `WXYZ` into a `PIC 1(4)` —
characters that are not boolean characters. Table 16 says the MOVE is VALID, and the resulting content is an
§14.6.13.2 incompatible-data question detected on use, not a reason to refuse the transfer. Whether this
compiler should also flag that content is a separate question about MOVE itself; the pairs assert only that
INVOKE and MOVE agree, which is what rule 2d requires and all this change may claim.
