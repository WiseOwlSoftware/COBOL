# PB53 — BY CONTENT is judged by the BY REFERENCE rule for three formal categories

> ⚙ **FOUND WHILE CLOSING [[PB46]]'s INVOKE HALF, AND DELIBERATELY NOT FOLDED INTO IT.** PB46 fixed the
> §14.8.2.3.2 screen that made boolean / national / numeric-edited / pointer formals impossible outright. This
> is the NEXT layer: with those formals now legal, the BY CONTENT arm still judges them by the wrong clause.

## ⛔ THE TWO CLAUSES ARE DIFFERENT RULES, AND ONE IS STANDING IN FOR THE OTHER

`OoBinder.OoContentMismatch` dispatches on the formal's category and ends in

```csharp
_ => OoConformance.DescriptionMismatch(formal, arg, anyLengthActivationRelax: true),
   // edited/other: conservative strict gate
```

`DescriptionMismatch` is **§14.8.2.3.2** — the BY **REFERENCE** rule, "the same ALIGN, BLANK WHEN ZERO, DYNAMIC
LENGTH, JUSTIFIED, PICTURE, SIGN, and USAGE clauses". It is exactly right there, and it is the wrong rule for
BY CONTENT: **§14.8.2.3.3 rule 2d** says a non-numeric, non-index, non-ANY-LENGTH formal conforms by "the same
[rules] as for a MOVE statement with the argument as the sending operand and the corresponding formal parameter
as the receiving operand" — i.e. §14.9.25.3 **Table 16**, which is a CATEGORY-PAIR table, not an identity test.

The arms already present cover the formals whose Table-16 row was written out by hand (alphanumeric, numeric,
object reference — `OoContentMismatch`'s alphanumeric arm even gets boolean→alphanumeric right). What falls to
the strict gate is every **boolean, national and numeric-edited FORMAL**, and there Table 16 admits pairings
identity refuses:

| argument | formal | Table 16 | today |
|---|---|---|---|
| boolean | national | **Yes** | refused (category mismatch) |
| alphanumeric | boolean | **Yes** | refused (category mismatch) |
| national | boolean | **Yes** | refused (category mismatch) |
| alphanumeric / national / numeric-edited | numeric-edited | **Yes** | refused |

⚠ **A DIFFERENT-LENGTH pairing of the SAME category is refused too**, which BY CONTENT never required: a MOVE
pads and truncates, and §9.3.6 resolution rule 5 already exempts literal arguments from the no-truncation
requirement. Strict identity demands equal length.

## ▶ WHY IT IS NOT MERELY "ADD THE TABLE" — the EMITTER is the load-bearing half

Under strict identity both sides are guaranteed to agree on width and category, and the marshaling relies on
that: `OoEmitter.OoStringReadOf` width-normalizes ONLY for an alphanumeric formal and otherwise passes the read
verbatim. Loosen the screen to Table 16 and the crossing must acquire the RECEIVING CATEGORY's MOVE store
discipline — a boolean receiver pads and truncates in boolean ZEROS (§14.6.8.6), an alphanumeric one in spaces,
a numeric-edited one EDITS (§14.9.25.4 GR5/GR6). That discipline already exists, written once, in
`MoveEmitter`'s per-category store — so the fix is to REACH it rather than to re-derive it
([[feedback_one_rule_one_place]]), which is the shape that makes this worth doing properly rather than as four
more arms.

## ⚠ THE BOOLEAN-EXPRESSION ARM WAS MADE TO AGREE WITH THE DEFECT, ON PURPOSE

[[PB46]]'s new `BY CONTENT boolean-expression-1` arm applies Table 16's BOOLEAN row but accepts only the
**boolean and alphanumeric** receivers — refusing the **national** receiver Table 16 admits — precisely so it
matches what the identifier arm beside it does. Two arms of one rule disagreeing is a worse defect than one
named residue ([[feedback_two_arm_dispatch]]), and a reader comparing them would have had no way to tell which
one was right. **Fixing this note means fixing BOTH arms in the same change set**, and the golden
`pb46_invoke_by_content_boolean` plus `pb46-invoke-by-content-boolean-numeric-formal` are where the boolean
half's expectations are pinned.
