# PB548

## Mechanism — usage-clause-p3
usage-p3/F4 — THE THIRD ARM. The restricted-data-pointer type-safety screen (14.9.39.3 SR19/SR20) lives in PtrBinder.BindSetAddress, which handles the two ADDRESS-OF forms of SET Format 7 and whose own comment congratulates itself on "THE SECOND ARM, AND IT IS A SEPARATE CODE PATH - the two-arm question asked and answered". The plain pointer-to-pointer Format-7 assignment (`SET p TO q`) is a THIRD path — SetBinder.BindSetPointer — which resolves both operands, checks only `Pic?.Category is PicCategory.Pointer`, and never consults StrongTypeModel at all. So an UNRESTRICTED pointer holding any address can be assigned into a RESTRICTED data-pointer, and the based item rebased through it reads another type's storage under the declared type's description. kb/Work PB153 is status LANDED and its note claims "14.9.39.3 SR19 and SR20 in BOTH arms of BindSetAddress" — true, and the arm it never counted is the one that leaks; the pb153 negative goldens pin only the two ADDRESS-OF directions.

### Expected, from the standard
13.18.60.4 GR23 last sentence (cite.py --check OK): "A restricted data-pointer shall contain only the predefined address NULL or the address of a data item of the specified type." Its statement-level enforcement is 14.9.39.3 SR19 first sentence (cite.py --check OK): "If identifier-5 references a restricted data-pointer, identifier-6 shall be the predefined address NULL or shall reference a data-pointer restricted to the same type." R is USAGE POINTER — unrestricted — so it is neither NULL nor a data-pointer restricted to type TT, and `SET P TO R` violates SR19. Annex D.9.2.2 (cite.py --check OK) states the purpose the rule serves: "Use of restricted data-pointers provides type safety by precluding the treatment of data of one type as data of another type." EXPECTED: COBOLNET0869 on `SET P TO R` naming 14.9.39.3 SR19, exactly as the ADDRESS-OF arm already does; the program shall not compile.

### Observed
Measured at --std 2023 with the pinned compiler: the program COMPILES and RUNS, printing UNRESTRICTED-INTO-RESTRICTED-ACCEPTED and then L=[1234] — the TT-typed based item L is now describing the first four characters of an unrelated PIC X(8) item, delivered as if it were of type TT. The screen exists and works on the other two paths (q40: `SET P TO ADDRESS OF B` with B of a different strong type -> COBOLNET0869 SR19; q49: `SET R TO ADDRESS OF B` into an unrestricted receiver -> COBOLNET0869 SR20), which is what makes this a missed arm rather than an absent feature. By inspection, SetBinder.cs:195-231 BindSetPointer resolves targets and sender with `Pic?.Category is not PicCategory.Pointer` and returns BoundSetPointer with no StrongTypeModel.PointerRestriction / SameRestriction call anywhere on the path. ⚠ Same site, separate defect: BindSetPointer's two diagnostics cite "ISO 14.9.39 Format 4" for a data-pointer SET, but Format 4 is the condition-name SET (its rules are SR6/SR7) and data-pointer assignment is Format 7 (SR17-SR19) — an inherited-citation error in user-visible text.
