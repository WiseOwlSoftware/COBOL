# PB3153 — the census does not see a use of an inherited SPECIAL-NAMES name

Source: wave 1076 (unit `w1076a`, PB2921), new-defects lead 1. The repro was run by the w1076a implementer on its build (bf8-1 at 3429aad94), not re-probed by the clerk (R2). It is the residue PB3132 (RETIRED) named as a separate mechanism. No open note covers it (R1: a grep of kb/Work for CensusOf, OoReparent*, BindClassData and COBOL2692 found only PB2160, PB2626 and PB372, none about this).

**The rule.** `python scripts/spec/cite.py --check 8.3.2.2 "a given user-defined word may be used as only one type of user-defined word"` -> OK, §8.3.2.2 "User-defined words". Cross-element scope: §8.4.6.1 (checked OK).

**Observed.** The outer program declares `CLASS DIGS IS "0" THRU "9"`; the contained program writes `IF X IS DIGS` (a class-name use) and declares a paragraph `DIGS.`. It compiles clean. The flat twin (one program, same word as class-name and paragraph-name) is refused. Expected: refusal COBOL2692 (the word-type conflict), as in the flat twin.

**Code site (per the report).** The class-condition, mnemonic, alphabet and symbolic-character lookups in `DataBinder` / `StatementBinder` record nothing in `OoClassTable.CensusOf`. The inherited name is never declared in the contained element, so the declaration funnel never sees the use: `DataBinder.DeclareUserWord` (census `_wordTypes` at `src/Cobol.Net.Compiler/Binding/DataBinder.cs:3410`, the conflict check at :3424). Declaration sites for the four kinds: `DataBinder.Switches.cs:930` (mnemonic), `:1300` (alphabet), `:2030` (class), `:2196` (symbolic character). A grep of `src` on origin/main did not find the symbol `CensusOf`; the implementer must locate the actual member.

**Repro (`s1.cob`, scratch path transient, source inline):**

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. S1OUT.
       ENVIRONMENT DIVISION.
       CONFIGURATION SECTION.
       SPECIAL-NAMES.
           CLASS DIGS IS "0" THRU "9".
       PROCEDURE DIVISION.
           CALL "S1IN".
           STOP RUN.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. S1IN.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 X PIC X VALUE "5".
       PROCEDURE DIVISION.
           IF X IS DIGS DISPLAY "DIG" END-IF.
       DIGS.
           DISPLAY "IN".
       END PROGRAM S1IN.
       END PROGRAM S1OUT.
```

**Fix shape.** An implementer decides whether a use of an inherited name registers it in the using element's census (with the exception table `UserWordKinds.MayBeOneWord`), for all four kinds together (rule 4). Whether §8.4.6.1 instead makes a same-spelling local declaration the item referenced (the PB3132 `d.cob` variant) is a spec judgment for an adjudicator first.

## Landing (wave 1078 G)

**Re-probe (this worktree's build, base c29af1704).** `E:\COBOL-coord\scratch\w1078g\p\s1.cob` (the repro above) compiled and ran (`DIG`, `IN`); its flat twin `s1flat.cob` was refused COBOL2692. Reproduced. A sibling found on the way: the SYMBOLIC CHARACTERS of a containing program were never handed down at all (`InheritConfiguration` copied every other SPECIAL-NAMES registry), so `p\s3.cob` (outer `SYMBOLIC CHARACTERS BEL IS 66`, inner `MOVE BEL TO X`) was refused COBOL1639 on conforming source (`python scripts/spec/cite.py --check 8.4.6.1 "may be referenced only by statements and entries either in that source element that contains a configuration section or in any source element contained within that source element"` -> OK; `12.3.4 "apply to each directly or indirectly contained source unit"` -> OK §12.3.4 1)).

**Determination.** §8.3.2.2 says "used" (`cite.py --check 8.3.2.2 "a given user-defined word may be used as only one type of user-defined word"` -> OK), so the census records the use, and the refusal is COBOL2692, the flat twin's. §8.4.6.1's second sentence (`"a source element's reference to such a name, even when it is a different type of user-defined word, is to the item which that source element describes"` -> OK) refuses the same programs (the reference would be to the paragraph or data item, which is no class-name) and decides the one case where the two readings differ: where a format admits an identifier as well as the inherited name, the element's own item is asked first and the program is legal.

**Fix.** Every type §8.4.6.1 lists as declared in a configuration section (alphabet-name, class-name, condition-name, dynamic-length-structure-name, locale-name, mnemonic-name, ordering-name, symbolic-character) now resolves through a registry whose resolution IS a recorded use: `ConfigurationNames<T>` (new; no `TryGetValue`, only `TryUse(site, name)`, which records, and the non-recording `Declares` / `TryPeek`) for the seven data-binder tables, and `Procedure.MnemonicRegistry.TryUse` (its map now private) for the mnemonic-names. Both call the ONE recorder `DataBinder.RecordConfigurationNameUse`, which records through `OoClassTable.RecordReferenceUse` (PB3132's per-element census; it now returns whether a census took the record, and a binder with no element table records into its own census). `InheritConfiguration` hands every table down with `InheritFrom`, the symbolic characters included. Local item first (§8.4.6.1) at the three positions that admit an identifier too: `ExpressionBinder.LiteralAliasOf` (a bare symbolic-character operand), `SetBinder` SET LOCALE ... TO, `SequentialIoBinder.MnemonicOperand` (WRITE ... ADVANCING). The resolvers that took only a name now take the referring node too: `TryResolveRangeAlphabet`, `CodedCharacterSetOf`, `ResolveLocaleName`, `SymbolicOf`, `SymbolicRaw`, `LiteralEnvironment.SymbolicValue`, `ConditionBinder.BindUserWordClassCondition` / `BindPartialClassName`; the file and SORT/MERGE COLLATING SEQUENCE phrases record their written names where they are read (`DataBinder.UseAlphabetName`).

**Witnesses.** Negative `pb3153-contained-program-paragraph-spells-an-inherited-class-it-uses` (reject-at 85 2002 2014 2023); golden `85/pb3153_inherited_special_names_words` (an inherited symbolic character and class-name used; a same-spelled local data item and paragraph legal, the data item winning); `InheritedConfigurationNameUseTests` (all eight types refused with the use and legal without it, and a method over its class's SPECIAL-NAMES); `UserWordDeclarationDriftTests.EveryConfigurationSectionNameType_ResolvesThroughARecordingTable` (parses §8.4.6.1's list) and the widened `TheCensus_IsRecordedOnlyByTheDeclarationAndReferenceFunnels`.

**For the next implementer.**
- `src/Cobol.Net.Compiler/Binding/ConfigurationNames.cs#TryUse`: the only resolving lookup of a SPECIAL-NAMES table; `Declares`/`TryPeek` only where the word is NOT being taken as that type (a predicate, a duplicate check, a re-read of a name already resolved).
- `src/Cobol.Net.Compiler/Binding/DataBinder.cs#RecordConfigurationNameUse`: the one recorder; pass the REFERRING node (a method's census is found from it).
- `src/Cobol.Net.Compiler/Binding/Procedure/MnemonicRegistry.cs#TryUse`: mnemonic-names; `TryPeek` for diagnostics.
- Trap: a resolver asked BEFORE the identifier reading (a literal alias, SET LOCALE, ADVANCING) must ask `ctx.Refs.Probe` first, or an inherited name both shadows the element's own item (a wrong answer) and records a false use (COBOL2692 on legal source).

## Review round 1 (wave 1078 G finisher, kb/Work PB3027)

The branch reviewer found the probe-first trap missed at four more positions, each re-probed on the finisher's build and refused COBOL2692 on legal source (`E:\COBOL-coord\scratch\w1078g\f\{sc,ev,vc,vk}.cob`, copied from the reviewer's `E:\tmp\w1078g-review`): FUNCTION STANDARD-COMPARE's three-argument position 3 (`IntrinsicBinder.BindStandardCompare`), the EVALUATE range's trailing `IN word` (`EvaluateBinder.BindRangeHigh`), the VALUE clause's IN-omitted alphabet peel (`DataBinder.RangeAlphabetPhraseOf`; origin/main answered N there, a pre-existing wrong answer) and the VALUE operand reader, which asked the symbolic-character before the constant-name (`DataBinder.RawValueOperandText`). Each now asks the element's own reading first (§8.4.6.1, `cite.py --check 8.4.6.1 "a source element's reference to such a name, even when it is a different type of user-defined word, is to the item which that source element describes"` -> OK); after the fix they print `<`, `IN`, `Y`, `Z`. The STANDARD-COMPARE argument-4 position of the four-argument form yields to the own item too. Golden `2014/pb3153_inherited_names_yield_to_own_items` pins both readings of each position.

**Sweep.** Every `TryUse`, `Declares`, `TryPeek`, `IsAlphabetName`, `IsClassConditionWord` and symbolic-character resolver call in `src` was classified. The positions that admit a second reading now all ask the own reading first: the literal alias, the VALUE operand, SET LOCALE, WRITE ADVANCING, `ConditionBinder.BareClassWord` (already did), STANDARD-COMPARE, and both THROUGH-range alphabet phrases. The positions that admit the configuration-section type only (a class condition, ACCEPT/DISPLAY mnemonic, SET switch, the LOCALE function arguments, CODE-SET, COLLATING SEQUENCE, PICTURE LOCALE, DYNAMIC LENGTH) keep the census refusal. The disambiguation sites that are diagnostics or ask the symbol table first (`InspectBinder` CONVERTING, `ReferenceResolver`, `ConditionBinder.RefuseNonCondition`, `SetAlterBinder.SwitchCondOf` behind level-88) need nothing. Two configuration-section names of different types cannot meet across elements: a contained program has no configuration section (§12.3.3 SR1, `cite.py --check 12.3.3 "The configuration section shall not be specified in a program that is contained within another program"` -> OK), and neither does a method (SR2).

## Review round 2 (wave 1078 G finisher, kb/Work PB3027)

The round-2 reviewer (finding R2-1) found that round 1's own-item test asked only `ctx.Refs.Probe`, which resolves data items and not constant-names. So in the three-argument STANDARD-COMPARE form, a contained program's own `01 LVL CONSTANT AS 1` was still claimed as the inherited ordering-name LVL and refused COBOL2692, although argument-4 is an integer argument and a constant-name "may be used anywhere that a format specifies a literal of the class and category of constant-name-1" (§13.10.3 SR2). Re-probed on the finisher's build (`E:\COBOL-coord\scratch\w1078g\r2\kc3.cob`): COBOL2692 (constant-name and ordering-name).

**Sweep.** The same raw probe stood at two more positions that admit a literal, and both reproduced: `WRITE … AFTER ADVANCING KN` with an own `01 KN CONSTANT AS 2` and an inherited `C01 IS KN` (`r2\wa.cob`, COBOL2692 constant-name and mnemonic-name), and an EVALUATE object `WHEN KW` with an own `01 KW CONSTANT AS "AB"` and an inherited `CLASS KW` (`r2\ev.cob`, COBOL2692 constant-name and class-name). SET LOCALE TO, the EVALUATE `IN alphabet-name` phrase (a qualified reference, never a constant) and the literal-alias symbolic arm (constant asked first) were behavior-neutral but used the same raw probe.

**Fix.** One own-item test, `ReferenceResolver.DescribesOwnItem(dref)`: an own constant-name (`DataBinder.ConstantOf`) or an own data item (`Probe`). Every procedure-division position that pairs a configuration-section-name lookup with the own reading asks it: IntrinsicBinder (STANDARD-COMPARE), SequentialIoBinder (WRITE ADVANCING), ConditionBinder.BareClassWord, ExpressionBinder.LiteralAliasOf, EvaluateBinder.BindRangeHigh and SetBinder (SET LOCALE). The drift test `UserWordDeclarationDriftTests.AConfigurationNameLookup_AsksTheOneOwnItemTest_NeverARawProbe` refuses a configuration-name lookup paired with a raw `Refs.Probe` in one expression (on the pre-fix tree it finds five sites), and pins the helper's two halves. After the fix kc3 prints `<`, wa writes its record, ev prints `EQ`.

**Goldens.** `2014/pb3153_inherited_names_yield_to_own_items` gains PB3153Y3 (own constant-names at STANDARD-COMPARE argument-4, the EVALUATE object and WRITE ADVANCING integer-1) and a PB3153Y1 arm for the inherited class-name as a partial expression. `InheritedConfigurationNameUseTests` gains constant-name rows for STANDARD-COMPARE (three-argument legal, four-argument position 3 refused 2692 "constant-name and ordering-name") and WRITE ADVANCING.

**Not fixed here.** A CALL / CANCEL target constant-name (`CALL KP` with `01 KP CONSTANT AS "SUB"`) is refused COBOL1639 even in one element, a §13.10.3 SR2 position covered by PB780. CallBinder's program-prototype test (lines 138, 924) also asks a raw probe, and must ask `DescribesOwnItem` when that arm lands. Reported as a lead.

## Review round 4 (wave 1085 D review finisher, kb/Work PB3027)

The reviewer of `86bba07ff` found w1085d R1-1: the bare-operand switch-status arm missed the own-item test the other
two-reading positions ask. `SetAlterBinder.SwitchCondOf` (reached from `ConditionBinder.AnalyzeBareOperand` and from SET

program's own `01 SWON PIC 1` written `IF SWON` was therefore recorded as a §8.3.2.2 use of SWON as a condition-name and

TO TRUE` over the own item draws COBOL1639 (not a condition-name), the code a program with no such switch gets,
instead of COBOL2692 plus a message naming SWITCH-1. An own constant-name `SWON` in `IF SWON` draws the flat
program's COBOL1639 too.

Why the drift guard missed it: `UserWordDeclarationDriftTests.AConfigurationNameLookup_AsksTheOneOwnItemTest_NeverARawProbe`

`Refs.DescribesOwnItem`. Mutation check: removing the new clause fails it, naming `SetAlterBinder.cs:184`. Sibling
sweep: the other procedure `TryUse` sites either ask the test already (STANDARD-COMPARE's ordering-name, WRITE
ADVANCING's mnemonic, SET LOCALE) or take a dedicated name token that admits no operand (ACCEPT FROM / DISPLAY UPON,
the class condition's class-name, SET Format 3's mnemonic). Goldens: `2002/pb3153_own_item_hides_switch_condition`
(inherited switch reading and own boolean items, bare, NOT, parenthesized and EVALUATE) and the negative
`pb3153-contained-own-item-set-to-true-names-no-switch` (reject-at 2002 2014 2023, COBOL1639).
