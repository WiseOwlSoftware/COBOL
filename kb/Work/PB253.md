# PB253

**Rows:** `RV-15.89.4-1`

RenderFloat tests the RECEIVER shape before the arithmetic mode, so under STANDARD-DECIMAL every receiver-less or float-receiver reference to the prose float family keeps a raw binary64 where §15.4.1 requires the SDIDI container.

ROW: RV-15.89.4-1 (§15.89.4 r1, TAN) — but the mechanism is the whole prose float family (SQRT, LOG/LOG10, the trig family, RANDOM: every catalog row with `Float: true` and no RenderDec arm).

WHAT IS CORRECT AND WAS RE-VERIFIED: `CobolIntrinsics.Float.cs:27 Tan(double x) => Math.Tan(x)` takes RADIANS, which is what §15.89.1 requires; the argument conversion handles a negative PICTURE-P scale (`NumericRenderer.Real:697-700` divides the unscaled carrier by 10^scale with Pow10D); the Codomain column is correctly EMPTY (the tangent is unbounded and `IntrinsicCodomain` exists only for a §15.x.4 rule that STATES a bound — clamping TAN would be the defect, not the fix); and the native-mode quantizer path has no 9.2e9-class saturation.

⛔ THE DEFECT — THE ARM ORDER. The three arms inside RenderFloat are tested in this order: the receiver-less/float test FIRST and unconditionally, THEN the StandardDecimal test, THEN the FromDouble/FromDoubleBounded quantizer. So under `ARITHMETIC IS STANDARD-DECIMAL` (and the 2002 plain STANDARD — `NumericRenderer.StandardDecimal` is `Arithmetic is StandardDecimal or Standard`, :394) the standard-decimal arm is UNREACHABLE for every receiver-less or float-receiver reference; the returned value stays a raw binary64. Only the FIXED-POINT-RECEIVER context reaches the SDIDI arm.

SPEC BASIS, mechanically re-checked and NOT inherited: `cite.py --check 15.4.1 "contained in a temporary standard data item in the intermediate form defined for the arithmetic mode in effect"` → OK — 'When standard-decimal arithmetic or standard-binary arithmetic is in effect, the returned value for numeric and integer functions is contained in a temporary standard data item in the intermediate form defined for the arithmetic mode in effect.' That sentence is UNCONDITIONAL on whether an equivalent arithmetic expression exists. The exemption the code leans on is §15.4.1's last paragraph ('When a numeric or integer function does not have an equivalent arithmetic expression, its returned value is implementor-defined unless otherwise specified in the function definition' → OK) and it exempts the VALUE, not the CONTAINER. Worse, the receiver-less arm's own comment block quotes 'When NATIVE arithmetic is in effect, the characteristics and representation of the returned value are defined by the implementor' (→ OK) to justify an arm that runs in EVERY mode — the a_real_clause_can_answer_a_different_question shape.

OBSERVABLE, not theoretical: the text channel keeps the binary64 and renders it through `CobolFloat.Display`, which on .NET Core 3.0+ is shortest-round-trip INCLUDING EXPONENTIAL NOTATION for large magnitudes, so under STANDARD-DECIMAL `DISPLAY FUNCTION TAN(1.5707963267948966)` prints `1.633123935319537E+16` where an SDIDI-carried returned value's item-92 text is plain digits. TAN is exactly the function that reaches those magnitudes (unbounded codomain, values near π/2), so this is not a corner the function cannot occupy.

SCOPE MEASURED, NOT GUESSED: the RELATION channel RECOVERS — `ConditionRenderer.cs:185` skips the native double compare when `num.StandardDecimal` and falls to `CobolDec.Compare(DecOperand(l), DecOperand(rr))`, lifting the float per §8.8.1.5.1 — so the divergence is confined to the receiver-less TEXT/MOVE-source contexts and the float-receiver context; the arithmetic-receiver context is correct. STANDARD-BINARY is out of scope for a separate, verified reason (the mode is refused at bind; PB198's recorded decline).

FIX SHAPE: the mode must be tested before the receiver shape — `if (num.StandardDecimal) return DecFromDouble(RealResult(call));` ahead of the receiver-less/float arm, with the receiver-less arm restated as the NATIVE-mode determination its own citation actually licenses. Then sweep: the same order question exists for every `Float: true` row, and the corpus has no STANDARD-DECIMAL program for ANY of them.

CLOSING EVIDENCE OWED: a STANDARD-DECIMAL golden that DISPLAYs a large-magnitude prose-family value (TAN near π/2) and one that MOVEs it, plus the relation leg as the control.

VERIFIED LIVE AT HEAD (read-only): :424 still precedes :433 and is still unconditional; test-ref stays empty — no spec-derived test exists and none would have caught it.

## Mechanism

src/Cobol.Net.Compiler/CodeGen/Emit/IntrinsicRenderer.cs#RenderFloat — `if (num.Receiver.Real || num.Receiver.Receiverless) return RealResult(call);` at :424 runs BEFORE `if (num.StandardDecimal) return DecFromDouble(RealResult(call));` at :433, and the first test is NOT mode-conditional; the value then reaches the text channel through OperandText.NumericExprText (ReceiverContext.None → `x.Real ? RuntimeApi.FloatDisplay(x.Expr)`) and src/Cobol.Net.Runtime/Values/CobolFloat.cs:25 `Display(double v) => v.ToString(InvariantCulture)`

## Lineage

PB13 (landed) established the receiver-less binary64 determination under NATIVE and moved the raise site; PB56 (landed) added the StandardDecimal arm. Neither note addresses the ORDER between them — kb/Work greps show `Receiverless` only in PB13, PB60 and PB91, and `RealResult` in none — so this is not a re-report of a fixed defect.
