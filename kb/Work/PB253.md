# PB253

**Rows:** `RV-15.89.4-1`

RenderFloat tests the RECEIVER shape before the arithmetic mode, so under STANDARD-DECIMAL every receiver-less or float-receiver reference to the prose float family keeps a raw binary64 where §15.4.1 requires the SDIDI container.

ROW: RV-15.89.4-1 (§15.89.4 r1, TAN) — but the mechanism is the whole prose float family (SQRT, LOG/LOG10, the trig family, RANDOM: every catalog row with `Float: true` and no RenderDec arm).

WHAT IS CORRECT AND WAS RE-VERIFIED: `CobolIntrinsics.Float.cs:27 Tan(double x) => Math.Tan(x)` takes RADIANS, which is what §15.89.1 requires; the argument conversion handles a negative PICTURE-P scale (`NumericRenderer.Real:697-700` divides the unscaled carrier by 10^scale with Pow10D); the Codomain column is correctly EMPTY (the tangent is unbounded and `IntrinsicCodomain` exists only for a §15.x.4 rule that STATES a bound — clamping TAN would be the defect, not the fix); and the native-mode quantizer path has no 9.2e9-class saturation.

⛔ THE DEFECT — THE ARM ORDER. The three arms inside RenderFloat are tested in this order: the receiver-less/float test FIRST and unconditionally, THEN the StandardDecimal test, THEN the FromDouble/FromDoubleBounded quantizer. So under `ARITHMETIC IS STANDARD-DECIMAL` (and the 2002 plain STANDARD — `NumericRenderer.StandardDecimal` is `Arithmetic is StandardDecimal or Standard`, :394) the standard-decimal arm is UNREACHABLE for every receiver-less or float-receiver reference; the returned value stays a raw binary64. Only the FIXED-POINT-RECEIVER context reaches the SDIDI arm.

SPEC BASIS, mechanically re-checked and NOT inherited: `cite.py --check 15.4.1 "contained in a temporary standard data item in the intermediate form defined for the arithmetic mode in effect"` → OK — 'When standard-decimal arithmetic or standard-binary arithmetic is in effect, the returned value for numeric and integer functions is contained in a temporary standard data item in the intermediate form defined for the arithmetic mode in effect.' That sentence is UNCONDITIONAL on whether an equivalent arithmetic expression exists. The exemption the code leans on is §15.4.1's last paragraph ('When a numeric or integer function does not have an equivalent arithmetic expression, its returned value is implementor-defined unless otherwise specified in the function definition' → OK) and it exempts the VALUE, not the CONTAINER. Worse, the receiver-less arm's own comment block quotes 'When NATIVE arithmetic is in effect, the characteristics and representation of the returned value are defined by the implementor' (→ OK) to justify an arm that runs in EVERY mode — the a_real_clause_can_answer_a_different_question shape.

OBSERVABLE, not theoretical: the text channel keeps the binary64 and renders it through `CobolFloat.Display`, which on .NET Core 3.0+ is shortest-round-trip INCLUDING EXPONENTIAL NOTATION for large magnitudes, so under STANDARD-DECIMAL `DISPLAY FUNCTION TAN(1.5707963267948966)` prints `1.633123935319537E+16` where an SDIDI-carried returned value's item-92 text is plain digits. TAN is exactly the function that reaches those magnitudes (unbounded codomain, values near π/2), so this is not a corner the function cannot occupy.

SCOPE MEASURED, NOT GUESSED: the RELATION channel RECOVERS — `ConditionRenderer.cs:185` skips the native double compare when `num.StandardDecimal` and falls to `CobolDec.Compare(DecOperand(l), DecOperand(rr))`, lifting the float per §8.8.1.5.1 — so the divergence is confined to the receiver-less TEXT/MOVE-source contexts and the float-receiver context; the arithmetic-receiver context is correct. STANDARD-BINARY is out of scope for a separate, verified reason (the mode is refused at bind; PB198's recorded decline).

FIX SHAPE: the mode must be tested before the receiver shape — `if (num.StandardDecimal) return DecFromDouble(RealResult(call));` ahead of the receiver-less/float arm, with the receiver-less arm restated as the NATIVE-mode determination its own citation actually licenses. Then sweep: the same order question exists for every `Float: true` row, and the corpus has no STANDARD-DECIMAL program for ANY of them.

CLOSING EVIDENCE OWED: a STANDARD-DECIMAL golden that DISPLAYs a large-magnitude prose-family value (TAN near π/2) and one that MOVEs it, plus the relation leg as the control.

VERIFIED LIVE AT HEAD (read-only): :424 still precedes :433 and is still unconditional; test-ref stays empty — no spec-derived test exists and none would have caught it.

## Mechanism

src/Cobol.Net.Compiler/CodeGen/Emit/IntrinsicRenderer.cs#RenderFloat — `if (num.Receiver.Real || num.Receiver.Receiverless) return RealResult(call);` at :424 runs BEFORE `if (num.StandardDecimal) return DecFromDouble(RealResult(call));` at :433, and the first test is NOT mode-conditional; the value then reaches the text channel through OperandText.NumericExprText (ReceiverContext.None → `x.Real ? RuntimeApi.FloatDisplay(x.Expr)`) and src/Cobol.Net.Runtime/Values/CobolFloat.cs:25 `Display(double v) => v.ToString(InvariantCulture)`

## Landed — 2026-09-05

**ONE MECHANISM: the ARITHMETIC MODE is tested before the RECEIVER SHAPE.** `IntrinsicRenderer.RenderFloat` ran
`if (num.Receiver.Real || num.Receiver.Receiverless) return RealResult(call)` FIRST and unconditionally, so under
`ARITHMETIC IS STANDARD-DECIMAL` — and under 2002's plain `ARITHMETIC IS STANDARD`, which
`ArithmeticModes.IsDecimalEngine` also selects — the SDIDI arm below it was UNREACHABLE for every receiver-less or
float-receiver reference and the raw binary64 escaped. The two arms are now swapped and each carries the citation
that actually licenses it: the standard-mode arm §15.4.1's container sentence, the receiver-shape arm §15.4.1's
NATIVE-mode sentence, which is the scope that sentence always had.

**The rule.** §15.4.1: "When standard-decimal arithmetic or standard-binary arithmetic is in effect, the returned
value for numeric and integer functions is contained in a temporary standard data item in the intermediate form
defined for the arithmetic mode in effect" (`cite.py --check 15.4.1` → OK) — unconditional on whether an
equivalent arithmetic expression exists AND on the shape of whatever consumes the value. §8.8.1.5.1 settles the
half the old comment elided: standard-decimal arithmetic is "a method of evaluating an arithmetic expression, an
arithmetic statement, the SUM clause, **and certain integer and numeric functions as specified in 15.4.1**"
(`--check 8.8.1.5.1` → OK), so the FUNCTION is evaluated under the mode, not merely its use as an operand.
§15.4.1's last paragraph ("its returned value is implementor-defined unless otherwise specified in the function
definition", `--check` → OK) exempts the VALUE — the binary64 approximation this family computes — never the
CONTAINER.

**Measured on this worktree's own `cobol.exe`, before and after.** With `TINY` the exact scale-20 value 1E-20 and
`A = 1.570796326794896619231321691639`:

| channel | before | after |
| --- | --- | --- |
| `DISPLAY FUNCTION SIN(TINY)` | `1E-20` | `0.00000000000000000001` |
| `MOVE FUNCTION TAN(A) TO S9(24)V9(2)` | `16331239353195368.96` | `16331239353195370.00` |
| `COMPUTE r = FUNCTION TAN(A)` | `16331239353195370.00` | `16331239353195370.00` |
| `MOVE` vs `COMPUTE` of `FUNCTION RANDOM(7)` | `0.3832204692918902784` vs `0.38322046929189024` | equal |

The MOVE/COMPUTE split is the sharpest harm: one function, one argument, TWO returned values inside a single run,
which §15.4.1 forbids by name ("the returned value is the same for all instances of a given function within a
single execution of the runtime element so long as the value and order of the arguments, the collating sequence,
and the locale are unchanged"). NATIVE arithmetic is unchanged — re-measured in every channel; PB13's binary64
determination still holds there.

**Sweep.** The order is one decision at one site, so the whole residue moves with it: ACOS, ASIN, ATAN, COS, SIN,
TAN, LOG, LOG10 and RANDOM — every `Float: true` catalog row that `RenderNum`'s standard-mode arm has not already
claimed (E / PI / EXP / EXP10 by name, SQRT / FACTORIAL / ANNUITY / PRESENT-VALUE / VARIANCE / STANDARD-DEVIATION
through `RenderDec`'s `alwaysDec` list). `grep -n "Receiver\.Real\|Receiverless" src/Cobol.Net.Compiler/**/*.cs`
found four other receiver-shape tests and each was read: `NumericRenderer.CombineCore` (:511), `NumericRenderer.Power`
(:755) and `NumericRenderer.Landed` (:852) all test the mode FIRST already, and `IntrinsicRenderer`'s `NumvalF` arm
is not live under a standard mode because NUMVAL-F is in `RenderDec`'s `alwaysDec` list and is claimed before the
switch is reached. `RenderFloat` was the single outlier from the ordering `COBOLNET_NUMERIC_DESIGN.md` D3 already
states for the whole engine ("the mode branch runs BEFORE the D16 float branch").

**The design doc was wrong in the same way the code was, and is corrected in this change set.** Its prose-family
paragraph read "implementor-defined in every mode (§15.4.1 last ¶), converting into expressions per §8.8.1.5.2 r1"
— which describes only the OPERAND case, and is what let the container rule be read as receiver-conditional. It now
states that under a standard mode the returned value is itself contained in an SDIDI, and that the
mode-before-D16 ordering binds `RenderFloat` exactly as it binds `CombineCore`, `Power` and `Landed`.

**Goldens** (each one FAILS against the pre-fix compiler — verified by restoring the pre-fix `IntrinsicRenderer.cs`,
rebuilding the solution and running all three): `tests/conformance/2014/pb253_prose_float_sdidi_container`
(the full set — the item-92 text channel, the MOVE-source and arithmetic-receiver channels, the float-receiver and
relation channels, and RANDOM's seeded form), `tests/conformance/2023/pb253_prose_float_sdidi_container` (the
default edition) and `tests/conformance/2002/pb253_prose_float_standard_container` (the plain-`STANDARD` spelling,
which a 2014-only golden would have left unproved). The edition gate itself needed nothing new: `constructs.json`
already carries `arithmetic-standard-decimal-2014` and `arithmetic-standard-2002` with `expectDiagnostic`
COBOLNET0900, and STANDARD-BINARY stays out of scope because `DataBinder` refuses it with COBOLNET0806.
