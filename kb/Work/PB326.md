# PB326 — two report-writer exception conditions that exist only as names

**Rows:** `GR-14.9.27.4-7`, `GR-14.9.49.4-10`. Reported by open-statement p3 and use-statement p2 as two
mechanisms; both are `ReportWriter` lacking a piece of state the rule needs, and one fixer supplies both.

## Part 1 — EC-REPORT-FILE-MODE (§14.9.27.4 GR7)

**Program.** `SELECT RF ASSIGN TO "rpt.dat"`, an RD on RF, and an INITIATE executed with RF not open (or open
INPUT). The report goes active and each GENERATE stamps '48' on RF's FILE STATUS while the program sees no
exception.

**Rule.** §14.9.27.4 GR7 requires the OPEN to precede the INITIATE. §14.9.21.4 GR3 supplies the detection:

> The INITIATE statement does not open any file connector with which report-name-1 is associated. Therefore,
> the INITIATE statement may be executed only if the corresponding file connector is open in the extend mode or
> the output mode. If the file connector is not open in the output or extend mode, the EC-REPORT-FILE-MODE
> exception condition is set to exist and no action is taken on the report.

`--check 14.9.21.4 "the EC-REPORT-FILE-MODE exception condition is set to exist"` → **OK**.

**Observed.** `ReportWriter.Initiate` (lines 190-208) performs GR1 a-c and GR4 unconditionally; its own summary
calls the check an *EC-REPORT-FILE-MODE seam*. `ExceptionCatalog.cs:171` registers the name as an L3 Fatal
condition, and no site in `src` raises it. The OPEN-side half of GR7 holds — nothing opens a report file
connector implicitly — so this is the unimplemented half of a two-half rule.

## Part 2 — EC-FLOW-REPORT (§14.9.49.4 GR10)

**Program.** `<lane3 scratch>/out-b1/probe/gr10-flow-report/p1.cob` — one report R-1 with a detail DET-1
sourcing WS-N; `BR-SEC SECTION. USE BEFORE REPORTING DET-1. / BR-P. ADD 1 TO WS-N. IF WS-N < 3 PERFORM GEN-P
END-IF.` and, in a SECOND declarative section, `GEN-P. GENERATE DET-1.` (so §14.9.49.3 SR10 is satisfied and SR4
permits the PERFORM — the program is legal). MAIN does OPEN OUTPUT / INITIATE / GENERATE / TERMINATE / CLOSE and
reads the report file back.

**Rule.** §14.9.49.4 GR10: a GENERATE, INITIATE or TERMINATE executed within the range of a declarative
procedure whose USE statement contains the BEFORE REPORTING phrase sets **EC-FLOW-REPORT** to exist, the result
is unsuccessful, and the state of the report is unchanged. `--check 14.9.49.4 "the EC-FLOW-REPORT exception
condition is set to exist"` → **OK**. Expected output: `N=1` / `LINE:DE 1` — exactly one detail line.

**Observed.** `N=1` / `LINE:DE 1` / `LINE:DE 1` — the nested GENERATE produced a second detail line, so the
report state changed. `ReportWriter.Generate`/`Initiate`/`Terminate` have no in-declarative guard, and
EC-FLOW-REPORT appears in the tree only as a catalog row. **The *unsuccessful, state unchanged* half is
unconditional** — it does not depend on `>>TURN` — so this is wrong at every edition and every checking setting,
which is why the harm here is a wrong answer and not merely an inert directive.

## The fix shape

`ReportWriter.RunBeforeReporting` is already the ONE funnel for all seven presentation paths: it owns a range
flag set around `group.BeforeReporting?.Invoke()` that `Generate`/`Initiate`/`Terminate` consult — the same
shape as the `__useActive` guard (**PB368**). `Initiate` additionally takes the connector's open-mode view
(`FileRegistry.OpenModeOf`, already the USE-declarative scoping input) and raises EC-REPORT-FILE-MODE beside the
existing EC-REPORT-ACTIVE seam. **PB349** owns the drift test that would have caught both: every turnable name
in `ExceptionCatalog` has a raise site.

**Code sites:** `ReportWriter.cs#Initiate`, `#RunBeforeReporting`, `#Generate`, `#Terminate` ·
`src/Cobol.Net.Runtime/Exceptions/ExceptionCatalog.cs` (line 171).

## Landed — 2026-09-05

Both parts, plus the two siblings the same funnel makes free. Reproduced first on this worktree's own
`cobol.exe`: the Part-2 program printed `N=1 / D=1 / D=1` (the nested GENERATE produced a second detail line),
and the Part-1 program INITIATEd a not-open connector silently.

**The state the engine was missing, and where it lives.** `ReportFlowState` (`src/Cobol.Net.Runtime/IO/
ReportWriter.cs`) is a DEPTH counter hung on `RunUnit.ReportFlow`; `RunBeforeReporting` — already the ONE funnel
all seven presentation paths use — brackets `group.BeforeReporting` with `Enter()`/`Exit()` in a `finally`, so a
fatal EC thrown out of a declarative cannot latch the range. ⛔ **The range is the RUN UNIT's, not one report's**:
§14.9.49.4 GR10 attaches no element qualifier where §14.9.18.4 GR6 attaches one explicitly for
EC-FLOW-GLOBAL-GOBACK ("… and that USE statement is specified in the same program as the GOBACK statement"), and
§14.9.32.4 GR1's "within the range of an input procedure" reads dynamically the same way. The note's own fix
shape said "a range flag on `RunBeforeReporting`" without saying whose; a per-`CobolReport` flag would have been
the one-arm-of-two defect, and `conformance:2002/pb326_flow_report_cross_report` is the arm it fails.

**Connector open mode.** `CobolFile.OpenModeIfOpen` → `FileRegistry.OpenModeIfOpen` → `FileConnector.
OpenModeIfOpen`, a new three-line accessor chain beside the existing `OpenModeOf`. The note proposed
`FileRegistry.OpenModeOf`, and that would have been WRONG: `OpenModeView` deliberately also answers with the
ATTEMPTED mode of a FAILED open (§14.9.49.4 GR6b's "in the process of being opened"), so an INITIATE after an
unsuccessful `OPEN OUTPUT` would have proceeded. §14.9.21.4 GR3 asks whether the connector IS OPEN in a mode,
which is a different question, so it gets its own accessor.

**Scope grew from two rules to four, deliberately (CLAUDE.md rule 5).** Building the raise CHANNEL —
`CheckingFlags` field + `ExceptionEngine` property + raise helper + static shim, an `EcBinder` PRECISE arm on the
bound node, an `EcEmitter.FatalAmbientGates` row — is the whole cost; a fifth line in the same guard closes
EC-REPORT-ACTIVE (§14.9.21.4 GR2) and EC-REPORT-INACTIVE (§14.9.16.4 GR7, §14.9.46.4 GR1), which were the
identical shape: a precondition the engine already computed, a bare `return`, and a catalogue row nothing raised.
Their inventory rows `GR-14.9.21.4-2` / `GR-14.9.16.4-7` / `GR-14.9.46.4-1` were unadjudicated GAPs owned by no
note, and are claimed here.

**The checking model.** Each of the four rules states its LENIENT outcome outright ("has no other effect", "no
action is taken on the report", "the execution of the statement is unsuccessful", "the state of the report is
unchanged"), so the engine's RETURN is unconditional and only the RAISE is gated by `>>TURN` (§14.6.13.1.1) —
the EC-FLOW-SEARCH / EC-BOUND-TABLE-LIMIT precedent, which is why the harm was a wrong answer and not an inert
directive.

**Rows:** `GR-14.9.27.4-7` PARTIAL→CONFORMS, `GR-14.9.49.4-10` DIVERGES→CONFORMS, and `GR-14.9.21.4-2`,
`GR-14.9.21.4-3`, `GR-14.9.16.4-7`, `GR-14.9.46.4-1` GAP→CONFORMS. GAP 2830 → 2824.
