# PB4302 - `DataBinder.PtrDescendants` is a recursive yield iterator - 22.7% of binder allocation on the corpus - and the pointer scans built on it re-walk every contained program's subtree from every container, so bind is superlinear in nesting depth (558 ms at 100, 3,640 ms at 200)

Found by the Mythos front-end review, gap pass, 2026-10-31 (GAP-REVIEW.md, G6-1; artifact https://claude.ai/artifact/KaxkLe85tfZBZ3nZ1tDGTs). Pin d7daee1cf.

**Where the review found it, at the pin:** `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.Ptr.cs` (`PtrDescendants` :402-410, `ScanByReferenceOperands` :295-347 with its local `OperandIdentifier`, `PtrScanAddressOfSenders` :389-399, `PtrScanAddressOfTargets` :369-385, `PtrBindBasedAndAddressables` :135-137/:175-181 where the container's IsUserFunction predicate lives); `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.Linkage.cs:445-447`; siblings `DataBinder.Constants.cs:220-228` (`Descendants`), `DataBinder.PreOrder`, `SetAlterBinder.AlterStatementsIn`.

**Finding.** `DataBinder.PtrDescendants` (DataBinder.Ptr.cs:402-410) is a recursive `yield` iterator (O(nodes x depth) MoveNext chain, one iterator object per interior node); the three pointer scans built on it (ScanByReferenceOperands :295-347, PtrScanAddressOfSenders :389-399, PtrScanAddressOfTargets :369-385; PtrBindBasedAndAddressables :135-137/:175-181 over `program.nestedProgram().SelectMany(...)`; DataBinder.Linkage.cs:445-447 for USING) re-walk every CONTAINED program's whole subtree from every containing unit. Corpus allocation (refuter re-run): bind 4,144 -> 3,205 MiB with an explicit-stack prototype (-940 MiB, -22.7%), outcomes identical {bind-error 2672, bound 3167, no-tree 172, frontend-error 205}; that is ~1.4% of whole-corpus allocation including DB201A/OBNC1M (the first report's "10.4% of every byte" excluded them). Depth: NESTED_100 bind 558 ms/143 MiB -> 156 ms/12.3 MiB; NESTED_200 3,640 ms/551 MiB -> 223 ms/25 MiB (x6.5 per doubling at the pin, not x8); 400 SIBLING programs ~70 ms; EVALS BindUnitData 174 ms/62.5 MiB -> 34 ms/0.1 MiB (the scans walk the PROCEDURE division from the data bind). With the iterator linear, the per-container re-walk is still quadratic (prototype BindUnitData 114/154/665 ms at depth 100/200/400). Production depth (10-25) binds in 18-29 ms, hence MEDIUM. The corpus wall-time gain did NOT reproduce on the loaded box (base 8.0 s, prototype 10.5 s, with the identical front end moving 5.5 -> 7.5 s): allocation deltas are the attributable evidence, wall time is not. Siblings Descendants, PreOrder, AlterStatementsIn allocate 271/165/327 MiB in the same profile. PB3227 lists PtrDescendants as a unify-wave member only, without the measurement (cross-reference; PB3227 gains an addendum).

**Fix direction.** Replace the iterator with an explicit-stack walk, then remove the per-container re-walk. The first report's bottom-up merge ("the container needs only the names the contained unit's own scan already yields") is NOT established: the container scans the contained subtree with the CONTAINER's IsUserFunction predicate (:175-177), so a merge must keep that predicate and region or prove them equal, else it changes which items are forced into cells.

## Resolution (wave 20261795, group B)

Re-probe on the fix lane build (`cobol check-batch`, 5 reps of one file per manifest, Debug, loaded box): NESTED_100 3,480 ms and NESTED_200 12,731 ms before; after, NESTED_100 2,881-3,607 ms and NESTED_200 4,212-5,433 ms (NESTED_10 1,160-1,739 ms is the fixed process cost): x3.7 per doubling became x1.5. Fixed at the root, not in the iterator alone: `StorageClaimScan` walks the compilation tree ONCE with an explicit stack and records the ADDRESS OF heads and the BY REFERENCE operands in document order with the span under every procedure division and every contained program, so a container asking about the programs it contains takes a slice instead of re-walking their subtrees (`BindSession.ClaimScans`, one per compilation; `StorageClaimScanTests` pins the answers and the walk count, never a clock). The container keeps its own `IsUserFunction` predicate, applied to the recorded function-call arguments at read time (the note flagged a bottom-up merge as unproven; this keeps the predicate and the region). A unit that declares no GLOBAL name no longer asks about contained programs at all (both claim loops discard a contained head that is not among its GLOBAL roots, so the question had no possible answer), and a procedure division with no USING phrase no longer collects the contained programs' ADDRESS OF names. Siblings swept: `DataBinder.Descendants`, `AlterStatementsIn`, the two report subscript walkers, `DataBinder.PreOrder` and `DataItem.DescendantsOf` (recursive yield iterators) are explicit-stack walks. Conformance witness: `13.18.27-GLOBAL/pb4302-address-of-global-from-grandcontained` (GR-13.18.27.4-2, a GLOBAL record addressed two programs down).

## Landing

- `Binding/StorageClaimScan.cs#StorageClaimScan` - the ONE owner of the ADDRESS OF heads and BY REFERENCE operands of a compilation (`AddressTargets`, `ByReferenceOperands`, region = a procedureDivision or a nestedProgram); reuse it, never walk a contained program from a container. Trap: the root is the top of the PARENT chain (a contained unit's synthetic programUnit from `BinderDriver.Reparent` has no parent, but its child rule contexts keep theirs), so ask with the original node, never the synthetic unit.
- `Binding/ParseTreeWalk.cs#ParseTreeWalk` - the one explicit-stack pre-order walk for a node (`Descendants`, `SelfAndDescendants`); a recursive yield iterator over a tree costs depth per node.
- `Binding/DataBinder.Ptr.cs#PtrBindBasedAndAddressables` - the contained arms ask only when the unit has GLOBAL roots (`CallGlobalRoots`); `Binding/DataBinder.Linkage.cs#CallBindLinkage` collects the addressed set only when the PROCEDURE DIVISION has formals.
- `Binding/Model/DataItem.cs#DescendantsOf`, `SelfAndDescendantsOf` - the data-item twins (explicit stack); `DataBinder.PreOrder` is gone.
- Gate trap: a new source file makes a whole-tier-1 plan, and until PB4274 is on main that plan reads RED on kb/Work PB4338 with every case passed.
