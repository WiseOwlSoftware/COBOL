# PB2665 — resume/meter livelock behind a dead lander's lease

**Sites:** `scripts/orchestrator/next_unit.py` (`base_choice`, the lease deferral), `scripts/orchestrator/orchestrate.ps1`
(the meter unit's failure handoff and the breaker's count), `docs/rearchitecture/DESIGN-orchestrator-loop.md` (§3.2, §4.7).

## What happened (2026-10-08, 03:02 to 03:22 PDT, account2 supervisor `orchestrate-20261008-0014.out.log`)

The train 1039b `land` unit ended SPLIT at 03:02:27 on the supervisor's context wind-down. Its lander had acquired the
landing lease for `E:/COBOL-wt/train1039b` (heartbeat 09:52:02Z, expiry 10:22:02Z) and kept it, as the lander brief
says a SPLIT should (lander-train-brief.md step 2b: "A SPLIT keeps it: your resumer, in this same worktree, re-takes
it with the same acquire"). The supervisor then ran this sequence:

| started | unit | outcome | cost |
|---|---|---|---|
| 03:02:30 | resume | done, `next_unit: land` | $1.58 |
| 03:06:34 | meter | failed (Chrome extension not connected) | $0.36 |
| 03:08:43 | meter | synthesized (invalid) | $0.35 |
| 03:11:53 | resume | done, `next_unit: land` | $0.77 |
| 03:13:53 | meter | synthesized (invalid), "FAILURE 1 of 3" | $0.37 |
| 03:16:00 | resume | done, `next_unit: land` | $0.56 |
| 03:17:18 | meter | synthesized (invalid), "FAILURE 1 of 3" | $0.37 |
| 03:19:31 | resume | (this note's unit) | |

Every resume found the same state, with every branch head unchanged, and named the same `land`. No unit did any
work for 20 minutes, and the cycle ended only because the lease's 30-minute TTL ran out.

## Mechanism (three defects compose)

1. **The unit choice defers the resumer that the lease is kept for.** `next_unit.py#base_choice` defers a
   handoff-named `land` whenever `landing_lease.current()` is live, without asking whose lease it is. The lease's
   owner is its WORKTREE (`landing_lease.py` docstring), and a SPLIT lander keeps it so that its resumer in the same
   worktree can re-take it. The `land` named here resumes in exactly that worktree (`E:/COBOL-wt/train1039b`), so the
   rule defers the one lander the lease was kept for, until the TTL frees it for anyone. `landing_lease.dead_reason`
   checks for two deaths, an expiry that has passed and a worktree that is gone. The supervisor could tell this
   loop's own landers apart, because it runs one unit at a time: once a `land` unit ends, no lander of this loop is
   still alive.
2. **A failed meter unit discards the named unit.** The meter unit's failure handoff (`next_unit: null`,
   `meter_reading: null`) is schema-invalid, so `orchestrate.ps1` synthesizes one through `checkpoint.py synthesize`,
   which always names `resume`. That synthesized handoff overwrites `handoff.last.json`, so the `land` that the
   previous resume chose is lost, and a full resume unit has to re-derive the same state. A meter unit reads a web page.
   It touches no branch, so its failure is not evidence that the work state changed.
3. **The breaker cannot see a failure that alternates with a success.** `$failures` resets to 0 after every unit
   that is not failed. The interleaved resume ends `done`, so a meter failure that recurs on every cycle (the
   extension stays disconnected) prints "FAILURE 1 of 3" forever and never reaches `Add-OwnerQuestion`. The owner
   action this needs is reconnecting the Claude in Chrome extension, and no owner question ever asks for it.

## Fix shape (not started)

- `next_unit.py`: do not defer a `land` whose handoff's `branches_pending` name the lease's own worktree (the
  module's same-worktree rule). This keeps the deliberate SPLIT-keeps-the-lease design and removes only the
  self-deferral. Record the change in DESIGN-orchestrator-loop.md §3.2 and §4.7.
- `orchestrate.ps1`: a failed `meter` unit leaves `handoff.last.json` as it was (synthesizing only for units that
  touch work), and meter failures count per unit TYPE: N consecutive failed meter units raise
  `Add-OwnerQuestion 'meter unreadable'` whatever ran in between. A drift test pins both rules.
- A test in `next_unit.py --self-test` (or `tests/orchestrator`): a handoff naming `land` plus a lease held by that
  handoff's worktree chooses `land`, not `meter`.

Filed by the 03:19 resume unit; notes only.

## Seen again 2026-10-18 16:53 to 17:07 PDT (supervisor `orchestrate-20261017-212242.out.log`)

Three meter units in a row could not record a reading, because the Chrome extension was signed into
`brent@wiseowl.com` (account 1) while the loop runs as account 2 (`claude@wiseowl.com`); `units/meter.md` correctly
refuses to record another account's meter. `units.jsonl` shows the breaker gap of mechanism 3 in a second form:

| started | unit | handoff | `failed` | cost |
|---|---|---|---|---|
| 16:53:54 | meter | failed (valid handoff, `outcome: failed`) | false | $0.53 |
| 16:57:10 | meter | failed (valid handoff, `outcome: failed`) | false | $0.36 |
| 17:00:29 | meter | synthesized (invalid) | true, "FAILURE 1 of 3" | $0.37 |
| 17:06:57 | resume | (this entry's unit) | | |

A meter unit that writes a schema-valid handoff with `outcome: failed` is not counted as a failure at all, so two of
the three consecutive failures never reached the breaker, and the third (synthesized) counted as the first. The
synthesized handoff then named `resume` (mechanism 2), whose unit re-derived an unchanged branch state. The owner
action this needs is signing the extension into account 2, and no owner question asked for it. The fix shape above
covers it if "meter failures count per unit TYPE" counts every meter unit whose handoff outcome is `failed`, valid or
synthesized; the drift test should pin that case too.
