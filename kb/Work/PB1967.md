# PB1967

Found by wave 1014 group S (while fixing PB1416), filed by the train-1014 lander. Pre-existing: it reproduces with
the lexer as it was before PB1416's change.

## Rule

§8.4.3.12.2 prints `ADDRESS OF FUNCTION { function-prototype-name-1 | identifier-1 }`, and §8.4.3.1.3 SR1 lets any
identifier slot take any identifier format, so a function-identifier whose argument is a subscripted identifier is
legal there (row SR-8.4.3.1.3-1, owned by kb/Work PB1407/PB1425). Spacing between a name and its subscript list is
insignificant.

## Repro

`scratchpad\w1014s\probe\p1lB.cob` (orchestrator scratchpad of session e8598e10) against `p1lE.cob` / `p1lA.cob`
(the unspaced form and the DISPLAY form, both of which compile): `SET P TO ADDRESS OF FUNCTION FUNCTION
UPPER-CASE(WS-NAME (1)).` then any statement -> COBOL0001 on that next statement.

## Code site

`src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4#OnDefaultLParen` (the SUBSCRIPT / FNARG mode interplay and the
`_fnParenStack`), with `src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4#functionAddressIdentifier`. PB1416 added
`_functionIsAddressOperand` (the FUNCTION after ADDRESS [OF] heads no function-identifier); the inner `FUNCTION
UPPER-CASE(` does, and the spaced `(1)` inside its argument appears to pop the wrong paren-stack entry.

## Retired 2026-10-04 (wave 1017 group D) — not a defect: the repro's `)` was past margin R

Re-probed on `79ef16831`'s build: the repro reproduces as filed (`SET FP TO ADDRESS OF FUNCTION FUNCTION
UPPER-CASE(WS-NAME (1)).` then `IF …` → COBOL0001 near IF), and the unspaced form compiles. But the lexer is not
involved: a token dump of the spaced and unspaced statements gives IDENTICAL streams (`FUNCTION FUNCTION IDENTIFIER
FNARG_LPAREN IDENTIFIER LPAREN SUB_INTEGERLIT SUB_RPAREN FNARG_RPAREN DOT`), and the raw `CobolParserCore` parses the
whole program. The difference is the line LENGTH: the spaced statement, indented to column 12, is 74 characters, so
its closing `)` stands at position 73 — past margin R. `cite.py --check 6.3.1 "Margin R is immediately to the right of
the rightmost character position of the program-text area"` → OK §6.3.1; this compiler's margin R follows position 72
and text beyond it is not program text (docs/CONFORMANCE.md DOC-A.1-158). The statement the compiler saw had an
unclosed argument parenthesis, so the parse failed at the next statement — correct fixed-form behaviour. Every
variant measured agrees: `ADDRESS FUNCTION` (3 characters shorter) compiles, `UPPER-CASE (WS-NAME(1))` (as long)
fails, and the same statement split over two lines inside margin R prints SPACED-OK.

Witness: `conformance:2014/pb1967_function_address_spaced_subscript` (the spaced subscript AND a spaced argument
paren, inside margin R; SPACED-OK, NEXT-OK). No code change.
