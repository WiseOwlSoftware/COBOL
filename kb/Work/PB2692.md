# PB2692 — cross-run-unit record locks, sequential arm

## What was found (w1042 D, PB2660, landed in train 1042)
PB2660 published record locks of RELATIVE and INDEXED files to other run units as host byte-range locks
(`PhysicalFileTable.LockRecord` through `FileConnector.RecordLockHandle`, `HostRegionLocks`: Windows LockFileEx,
Linux OFD). `SequentialConnector` does not override `RecordLockHandle` (the base default is null), so a sequential
file's record lock stays visible only inside its own run unit.

§9.1.16 (`cite.py --check` OK): "While locked by a given file connector, a record is not accessible to another file
connector in the same or a different run unit, except by the execution of a READ statement with the IGNORING LOCK
phrase." §9.1.13.8 1): "I-O status = 51 ... record that is currently locked by another file connector".

## Repro (expected, not yet probed)
Two processes on one ORGANIZATION SEQUENTIAL file opened I-O with SHARING WITH ALL OTHER and LOCK MODE MANUAL: A runs
READ WITH LOCK, then B runs READ WITH LOCK on the same record. Expected B: 51; observed (by the code): 00. Model the
probe on PB2660's `E:\COBOL-coord\scratch\w1042d\probes\l2.ps1` (lka/lkb), and the unit witness on
`tests/Cobol.Net.Tests.Unit/CrossRunUnitKeyedStoreDriftTests.cs` (two FileRegistry instances = two run units).

## Site
`src/Cobol.Net.Runtime/IO/SequentialConnector.cs` (the reader/writer handles, lines ~21-22): override
`RecordLockHandle`/`RecordLockHandleWritable` with the handle the connector's mode holds; `FileConnector.cs#RecordLockHandle`
(line ~613). A REWRITE after another run unit's write also needs PB2660's store coherence question asked for the
sequential arm (the record id is the relative position).
