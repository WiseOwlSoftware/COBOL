# PB2692 — cross-run-unit record locks, sequential arm

## What was found (w1042 D, PB2660, landed in train 1042)
PB2660 published record locks of RELATIVE and INDEXED files to other run units as host byte-range locks
(`PhysicalFileTable.LockRecord` through `FileConnector.RecordLockHandle`, `HostRegionLocks`: Windows LockFileEx,
Linux OFD). `SequentialConnector` does not override `RecordLockHandle` (the base default is null), so a sequential
file's record lock stays visible only inside its own run unit.

§9.1.16 (`cite.py --check` OK): "While locked by a given file connector, a record is not accessible to another file
connector in the same or a different run unit, except by the execution of a READ statement with the IGNORING LOCK
phrase." §9.1.13.8 1): "I-O status = 51 ... record that is currently locked by another file connector".

## Repro (expected, not yet probed)
Two processes on one ORGANIZATION SEQUENTIAL file opened I-O with SHARING WITH ALL OTHER and LOCK MODE MANUAL: A runs
READ WITH LOCK, then B runs READ WITH LOCK on the same record. Expected B: 51; observed (by the code): 00. Model the
probe on PB2660's `E:\COBOL-coord\scratch\w1042d\probes\l2.ps1` (lka/lkb), and the unit witness on
`tests/Cobol.Net.Tests.Unit/CrossRunUnitKeyedStoreDriftTests.cs` (two FileRegistry instances = two run units).

## Site
`src/Cobol.Net.Runtime/IO/SequentialConnector.cs` (the reader/writer handles, lines ~21-22): override
`RecordLockHandle`/`RecordLockHandleWritable` with the handle the connector's mode holds; `FileConnector.cs#RecordLockHandle`
(line ~613). A REWRITE after another run unit's write also needs PB2660's store coherence question asked for the
sequential arm (the record id is the relative position).

## Landed (2026-10-08, wave 1047 group B, branch `worktree-wf_8750e914-ee4-2`)

**Re-probed first on the branch's own build (base `29362158a`):** two processes on one ORGANIZATION SEQUENTIAL file,
SHARING WITH ALL OTHER, LOCK MODE MANUAL (`E:\COBOL-coord\scratch\w1047b\probes\sq.ps1`, sqa/sqb): A `READ WITH
LOCK` record 1 and waits; B `READ WITH LOCK` answered `00 REC=AAAA` and its REWRITE `00`, file `ZZZZBBBB`. After the
fix: B `51`, its REWRITE `43` (no successful READ, §14.9.35.4), file `AAAABBBB`.

**The mechanism was three facts, not one** (the note named the first):
1. **The handle.** `SequentialConnector.RecordLockHandle` is the handle beneath its reader or writer
   (`HostFile.HandleOf`), so `PhysicalFileTable.LockRecord`/`HolderOf` publish and test its locks as they do a keyed
   connector's.
2. **The identity of a RELEASED record.** A sharing writer numbered its records from `State.ReleasedOrdinal`, a mint
   only its own run unit advances, so after another run unit's append its `WRITE WITH LOCK` guarded a different
   record. Where the file lock admits another writer the ordinal is now counted off the medium
   (`ReleaseRecord` → `PhysicalOrdinalOfRelease`, `SharedAppendStream.ReleaseStart`, the one bounded framing count
   `CountRecords`, which replaced `ExistingRecordCount`; `RecordFraming.FrameStarts` takes a range).
3. **Coherence.** A reader whose lock admits another writer re-anchors at every frame (`EnsureReaderCoherent`):
   the release generation is one run unit's memory, so another run unit's REWRITE was served from the read-ahead
   (measured: the witness's `YYYY` read back `BBBB` with that arm disabled).

Plus one host fact: Linux refuses the SHARED presence-byte hold through a write-only descriptor, so a writer that
registered a record-locking posture opens its handle read-write (`SequentialConnector.HostAccess`, inside the
`FileLockPostureDriftTests` band); .NET refuses `FileMode.Append` with read access, so `HostFile.OpenConnectorWriteStream`
takes the access (kb/Work PB2758's target for the sequential handles) and opens such a writer `OpenOrCreate` at the end.

**Witness:** `CrossRunUnitSequentialLockDriftTests` (two `FileRegistry` instances = two run units, fixed, line and
varying framings): `51` on READ WITH LOCK, IGNORING LOCK, a rewrite read back from the file, and a sharing writer's
lock on the record at its physical place. No conformance golden: a cross-run-unit rule needs two run units, which a
single-program golden cannot express (PB2660 has the same witness shape). Design: DESIGN-runtime-library.md §2.2.
