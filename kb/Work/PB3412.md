# PB3412 — the prune self-test hung once on Windows under load

**The observation (the Mythos lane, mail of 2026-10-18 22:52).** While verifying the `-326-31` bounce fix (the loop's
finisher's cc441f527: self-tests run with git auto-maintenance off, and the prune fixture's git calls checked), a
standalone Windows run of `python scripts/prune_worktrees.py --self-test` hung for more than 3 minutes "in process
creation". At the time, two landing gates, the Linux gate and a game had the CPU at 100 %. The gate's own run of the same
self-test passed. The Mythos lane did not root-cause it and recorded no log. It said that if a gate ever shows the
self-test as a HANG, that is a defect to root-cause.

**Why it is filed now.** A hang that passes on a rerun is a defect, not a flake (the project's rule on timing failures).
The fixture builds a repository with dozens of git processes per run, and the merge-queue bounce of PR #268 was this same
self-test reading the fixture repository wrong under a concurrent actor (git 2.55's detached auto-maintenance). A second
unexplained behaviour of the same fixture under load is the next lead.

**What to do.** Reproduce on Windows under a planted load: the gate's slot cap, a CPU burner per core, and the fixture's
git calls timed one by one. Find whether the time goes to process creation itself (an antivirus scan of each new
`git.exe`, a handle or desktop-heap limit) or to a git process waiting on a lock. Then fix the cause: fewer processes
(one `git fast-import` for the fixture's history, say) or the missing isolation. Record the measurement here.
