# PB6211 - the R2 launch room check ignores the orchestrator loop's in-flight wave reservation

On 2026-11-25 account 1 reached 61.3 % weekly against the 57.2 % day line (+4.1 over). Cause: `scripts/arch/r2_collect.py --launch`
sized R2 batch 1a part 1 (4.03 weekly points) against "week 5.0" room from `budget.py`, without subtracting the wave the
orchestrator loop was running at the same time (wave 20262171, 46 groups).

**Sites:** `scripts/arch/r2_cost.py` (`room`, `size`, `add_budget_args`), `scripts/arch/r2_collect.py` (`launch`)

## Cause (read in this tree, main at 1774be2903)

- `scripts/arch/r2_collect.py:808` calls `launch(a.out, r2_cost.budget_from(a), a.session_reserve, only)`; the budget is
  `budget.current(borrow_days=...)` (`scripts/arch/r2_cost.py:137-143`), i.e. measured usage so far.
- The weekly room is `float(b["headroom_pct"])` unchanged (`scripts/arch/r2_cost.py:147`): `room()` subtracts `reserve` from the
  SESSION window only, and the fit test is `week <= r["week"]` (`r2_cost.py:166`).
- `--session-reserve` defaults to 0.0 (`r2_cost.py:133`) and is a session-points knob the operator must remember; there is no
  weekly reserve at all. A wave that has been dispatched but has not yet spent its tokens is in neither number, so the room looks
  free to both the loop and R2.

## Fix direction

The R2 launch room check, and any launch beside the loop, deducts the loop's in-flight reservation (the dispatched wave's
estimated weekly points, from the loop's coordination state) from `room["week"]` as well as the session window; or the loop and R2
draw on one shared reservation record so neither can size against room the other already holds. Pair it with a self-test arm
in `r2_cost.py` (a budget with an in-flight reservation refuses a plan that fits without it).
