# PB3845 — A parse failure masks the bind-time word-character diagnosis

**Sites:** `src/WiseOwl.Cobol.Frontend/Common/CobolWordRule.cs#CharacterViolation`; `src/WiseOwl.Cobol.Frontend/Parsing/WordCharacterScreen.cs#RunOnTokens` / `#RunOnTree` / `#Check` (the asker); `src/WiseOwl.Cobol.Frontend/Pipeline/Frontend.cs#LexAndParseOnce` (the failed-parse call); `src/WiseOwl.Cobol.Compiler/Binding/BinderDriver.cs` (the successful-parse call); `src/WiseOwl.Cobol.Frontend/Preprocessor/DiagnosticBagSink.cs#BagSink` (the one adapter, with the cursored form the failed-parse call uses); `src/WiseOwl.Cobol.Frontend/Grammar/CobolParserCore.g4#commentEntry` (the one comment-entry rule); `src/WiseOwl.Cobol.Compiler/Validation/VersionConformancePass.cs#VisitCobolWord` (the character half left it)

Repro: the U+00A0-only line of golden `pb1660` draws a bare COBOL0001, never COBOL2773 naming U+00A0 (PB1402's character-outside-Annex-B diagnostic). `CharacterViolation` runs at bind only, so a source whose offending character already breaks the parse never reaches it and the user is told cannot-parse without the cause. Check whether the word-character test can run where the lexer produces the word, so the cause is named at parse time as well.

Register class: a message that names the wrong fault is filed `process_only: true` today because the register has no harm class for it (kb/Work PB3836); the flag becomes the new class when PB3836 lands.

## Acceptance

- The pb1660 line draws COBOL2773 naming U+00A0 (with or without the parse failure), and every other character class `CharacterViolation` rules on is checked the same way.
- Fix the root cause, never simply making the diagnostic pass; be consistent with ourselves barring an explicit requirement differently.

## Landed (wave 20261764 group D)

Re-probed on the worktree build first: `pb1660-nbsp-only-line-is-not-blank` drew only `COBOL0001 cannot parse construct
near 'STOP'` at every `--std` (reproduced). Root cause: the character half of ISO §8.3.2.1 was asked in the parse-tree
funnel `VersionConformancePass.VisitCobolWord`, which never runs on a source that does not parse, although the lexer
does read the word (`NAME_BODY` admits every non-basic character on purpose, so the diagnostic can name it).

- **The fix.** `WordCharacterScreen` asks the character half of the rule of every `IDENTIFIER` token (the only token built
  from `NAME_BODY`): the underscore gate (`user-word-underscore-2002`), the extended-letter gate
  (`user-word-extended-letter-2002`), COBOL2773 and the 2023 removal (`user-word-character-removed-2023`, a warning under
  `--permissive`), one report per distinct word (the Annex C fold). The tree funnel's copy is deleted. One body, two word
  sources: a failed parse is screened by `Frontend.LexAndParseOnce` over the lexer's whole stream (`RunOnTokens`), a
  successful one by `BinderDriver` over the tree's words (`RunOnTree`, so the binder's own diagnostics still accompany
  the report: golden `pb2983-supplementary-letters-parser-error-column` needs its COBOL1941 beside COBOL2773 at 2002 and
  2014). The pb1660 line now draws COBOL2773 naming U+00A0 at every edition, beside the parse error (at 85 too, by
  PB4130: no edition's Annex B holds U+00A0, so it is no extended letter).
- **The sibling arms** (one mechanism, all four swept): the underscore gate, the extended-letter gate and the 2023 removal
  were masked by a parse failure exactly as COBOL2773 was; all move with it.
- **The structure.** A comment-entry is arbitrary text, so `AUTHOR. JOSÉ` is legal '85 and its words are not words. The six
  `authorContent`/`installationContent`/... rules were the same `~DOT+` six times; they are now ONE rule `commentEntry`,
  which is how the screen finds the tokens that are not words (a seventh comment paragraph needs no arm).
- **Goldens:** `pb3845-nbsp-word-unparseable` (85-2023, COBOL2773), `pb3845-extended-letter-unparseable-85`,
  `pb3845-underscore-unparseable-85` (85, COBOL0900), `pb3845-removed-character-unparseable-2023` (COBOL0902), and
  `WordCharacterScreenTests` (comment entry is not words at all four editions, one report per distinct word, the permissive
  warning, a phrase-word position).

### Review round 1 (finisher)

- **R1-1 (blocking), fixed.** `RunOnTokens` read every `IDENTIFIER` of the stream, including the words of a fixed-form
  debugging line that is a comment (channel `ABSENT_DEBUG_LINE`), so a failed parse named a character of comment text.
  `IsCandidate` now skips that channel as `SeparatorRule` and `PictureSeparatorPeriodRule` do.
- **R1-2.** The stream screen now runs whenever the frontend bag holds an error (the binder is skipped on any), placed after
  the last reader of the stream, and counts the pass's earlier errors (`priorErrors`: preprocessor, COPY, reference format).
- **R1-3.** `CursorBagSink` is deleted; `BagSink` has the cursored form, so the severity mapping has one copy.
- **R1-4.** `WordCharacterScreenTests` covers the failed-parse comment entry, a comment debugging line and a parsed source
  beside a separator error; each was checked to fail with its fix removed.

### Conflict finisher (merge with main's PB4130)

Main's PB4130 (this note's first lead) changed the same rule in the tree funnel this branch deleted: below 2002 a character
that no edition's Annex B holds is COBOL2773, not the extended-letter gate (`CobolWordRule.CharacterViolation` asks
`CobolCharacterRepertoire.ViolationAtEveryEdition`). The merge keeps the branch's move and carries PB4130's test into
`WordCharacterScreen.Check`, the one body both word sources run, so a failed parse at 85 gets it too:
`pb3845-nbsp-word-unparseable` is refused at 85 with COBOL2773, and its comment says why. The R2-1 lead (three comments
still stating the parse-failed/succeeded split instead of frontend-errored/clean) is fixed in the same change.
