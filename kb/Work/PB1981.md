# PB1981 — OPEN: which loop-engineering techniques improve the compiler implementation plan

Source: the owner's 2026-10-04 screenshots of an AI chat's summary of "loop engineering for autonomous system improvements"
(deterministic checks instead of wall-clock, an autonomous propose-test-deploy cycle gated on metrics, feature-flag rollout
with real-user metrics, 150+ parallel threads each with a human owner). The numbers in the source (3.1x faster PRs, 78 %
lower CPU) are anecdotes, not evidence; this note takes the structure only.

## Already in place (nothing to do)

- Deterministic checks: the traceability inventory (GAP is the metric), spec-derived goldens, the drift tests, the ordered
  whole-population gate, and the owner rule against wall-clock tests (2026-09-25).
- The autonomous cycle with human approval: the rolling wave proposes branches, the gate and `push-main.sh` land them only
  on green with CI as proof, and owner decisions stay reserved.
- A scheduled job exists (`build-and-test.yml`, 06:00 UTC), but it runs only the legacy-oracle cross-check.
- Staged rollout: edition and dialect gating stage new behaviour per edition; there are no users to monitor before 1.0.

## To adopt, by value per token

1. **A wave planner** (`scripts/` or the workstream skill): from a budget in weekly points, compute the groups (rows claimed
   per cluster, finishers first: a note whose report says SPLIT or NOT STARTED), assign the model by a recorded rule, allocate
   codes and lead ids, render the specs, run `check_practices.py`, and emit the Workflow args. Waves 1011-1015 each cost the
   orchestrator a hand-written `groups.json`. Also record tokens per group against rows closed, per model and area
   (`usage_report.py`), so routing is measured.
2. **A closed-rows ratchet**: a per-landing deterministic check that no closed inventory row reopens and that GAP does not
   rise without a stated reason. No such test exists (searched `tests/` 2026-10-04); `DefectiveRowCoverage` and
   `ClosesRowsBackLink` guard other things.
3. **Deterministic performance baselines** replacing wall-clock: bytes allocated compiling a fixed corpus, emitted C# size,
   IL size, with a committed baseline that needs an explicit commit to change. Today only collation and Unicode have
   BenchmarkDotNet benchmarks and nothing gates a commit, although `PROMPT.md` makes performance a required review
   dimension. Instruction counts (the source's valgrind idea) do not fit: .NET under valgrind is impractical and WSL exposes
   no hardware counters.
4. **Nightly deterministic jobs, not nightly agents**: the quota, not the thread count, is the limit, so the cheap form of
   "scale" is scheduled deterministic compute that finds work for free (the comprehensive battery, which is owed as #88, the
   GnuCOBOL differential, the ratchet, the performance baseline), with an agent spawned only on a red.

## Not worth doing

Feature flags for staged rollout (edition gating already does it; a CI change is staged with a branch run, as the
`ubuntu-26.04` pin was); 150 parallel agent threads (a six-group wave already costs about 3 weekly points).

## What Anthropic's own engineering articles add (read 2026-10-04)

Sources: "Building a C compiler with a team of parallel Claudes" (2026-02-05), "Harness design for long-running application
development", "Demystifying evals for AI agents", "How we built our multi-agent research system"
(anthropic.com/engineering). The first is the closest match to this project.

Already matches what we do: tests as the specification of the task ("write extremely high-quality tests", a known-good GCC
as oracle: our spec, corpus and GnuCOBOL differential); harness output kept small and logged to files, because "context
pollution" and "time blindness" were real failure modes (our 25-line return caps and log files); a progress file per agent
(STATUS.md, DEVLOG); fresh agents from a structured handoff instead of ever-longer transcripts (their own finding: context
resets worked better than compaction on Sonnet 4.5); failures become test cases (defect, kb/Work, golden); token use explains
most of the variance (80 % on BrowseComp), so effort is budgeted, not unbounded.

New or sharper, in order of value:

1. **Re-test every harness assumption against the current models.** "Every component in a harness encodes an assumption
   about what the model can't do on its own"; their sprint decomposition and context resets became unnecessary on Opus 4.6.
   Our turn caps (400 implementer, 160 read-only), the quadratic cost law (fitted on an earlier model and marked "not yet
   validated" for the current one), one mechanism per implementer, and same-file successor chains are such assumptions.
   Wave 1011 group C ran out of turns before its fourth note, so the cap binds. Measure on Opus 5.5 and Sonnet 5.5 with
   `usage_report.py`, then relax or remove what no longer pays.
2. **A skeptical, tool-grounded evaluator separate from the implementer**, with hard thresholds, found the "last mile" gaps
   that self-evaluation missed, at about 20x the cost of a solo run. The open owner decision on an independent judge in the
   fix lane gets this evidence. Use it only where a wrong landing is expensive (high-harm notes, the lander's review), not
   on every group.
3. **A note that fails twice is a spec problem, not a weak agent.** "0 % pass@100 typically indicates broken task specs".
   PB1167 was planned in waves 1011 and 1012 and not started before wave 1013. After two failed attempts, re-scope or
   adjudicate the note before a third implementer is spent on it.
4. **Standing specialist roles run continuously**: one agent only coalescing duplicate code, one on performance, one on code
   quality, one on documentation. `PROMPT.md` makes these review dimensions a comprehensive pass; the article ran them as
   standing roles inside the loop. Reserve one slot in every few waves for a clone-detection pass (the `roslyn-analysis`
   skill) instead of waiting for the comprehensive pass.
5. **Use the oracle to unstick a monolithic failure**: when every agent hit the same giant failure they re-compiled parts
   with GCC to bisect it. `cobc` 3.2.0 is now runnable in WSL, so a failing NIST program can be bisected against it (an aid
   for finding the divergence; the ISO text still decides what is correct).

Considered and rejected: a deterministic random sample of the test population per agent (their `--fast`, 1 % or 10 %). The
owner decision of 2026-09-28 is to order the whole population, never skip. Their own caveat applies to us too: "new
features and bugfixes frequently broke existing functionality" even with strict CI, which is why the ratchet (item 2 above in
the first list) matters.

## Prototype built (owner 2026-10-04: "prototype the full workflow"), not yet run against a real session

Design: `docs/rearchitecture/DESIGN-orchestrator-loop.md`. Code: `scripts/orchestrator/`. What exists, by row of the
table above:

- **Row 1, the ratchet: built, not wired.** `inventory_ratchet.py` (closed set never shrinks, GAP never rises without
  an added `reopens-rows: <ids> — <reason>` line in DEVLOG or kb/Work); self-test 18/18; green on `HEAD~300..HEAD`.
  Wiring into the lander brief and CI's `audits` job is design open decision D5.
- **Row 2, the allocator: built and in use by the probe.** `alloc.py` (one lock, reservations in `E:\COBOL-coord`
  outside every worktree, `seed` for values handed out before it existed); `session-probe.ps1` now prints its
  `peek code --probe` line instead of computing the rule a second time; self-test 23/23 with eight parallel processes.
- **Row 3, the wave planner: built.** `plan_wave.py` + `model_rules.json` (awaiting-landing exclusion, finishers first,
  half clusters, rows-claimed ranking, same-file successors, model routing with its reason, budget fill, codes and
  lead ids through `alloc.py`, `groups.json` + specs + `check_practices.py` + the rolling-wave args); self-test 28/28;
  a real run rendered specs that `check_practices.py` passed. Recording tokens per group against rows closed is the
  supervisor's `units.jsonl` per unit, not yet per group.
- **Beyond the table:** the supervisor `orchestrate.ps1` (single instance, STOP, circuit breaker, budget holds,
  `next_unit.py`, context cap via `STOP-UNIT`, handoff schema validation, `units.jsonl`), the unit prompts, `budget.py`
  (quota estimate from telemetry anchored on meter readings), and the token-free agent watchers in Windows Terminal
  tabs (`watch_agent.py`, `watch-agent.ps1`, `open-watchers.ps1`; the terminals-mode experiment is described, not
  built). Self-tests: `test_budget.py` 24/24, `test_watch_agent.py` 15/15, `test_orchestrate.ps1` 39/39.

Not built: rows 4-10; the separate-process agent pool; a Task Scheduler entry; CI wiring of the new self-tests. The
design's open decisions D1-D8 list what waits on the owner; D8 matters first: with no meter anchor, `budget.py`
estimated 28.4 weekly points spent by 14:50 on 2026-10-04 from telemetry, which the first meter reading will confirm
or correct.
