## Repro (measured by the PB547 implementer, branch build)

`E:\COBOL-coord\scratch\w20261032b\pb547a.cob` at `--std 2023`: a WRITE of a record holding a character above U+00FF is

## Open: a spec judgment the clerk did not make

Whether an implementor-defined I-O status refused with a FILE STATUS item present must continue (the item receives
'91' and execution goes on) or may end the run unit is governed by the I-O exception and FILE STATUS rules of §9.1.13
and §14.6.13 and by what EC-I-O-IMP's default is. The implementer called it "unverified, possibly intended". An
adjudicator decides; if the fatal end is intended, close this note with the citation.

## Retired (wave 20261500, group D) - intended behavior, now witnessed

Re-probed on this worktree's own build (`dotnet build Cobol.Net.sln -c Debug`, 0 warnings, 0 errors).
`pb547a.cob` still ends with `abnormal run-unit termination: EC-I-O-IMP (fatal): I-O status 91 on PB547A::F`, but its
source holds `>>TURN EC-ALL CHECKING ON`. Without that directive the same WRITE stores `91` in the FILE STATUS item and
the run unit continues (`FS=91`, then the next statement runs). So the termination is the CHECKING-ENABLED arm, not a
FILE STATUS bypass, and it is the arm `docs/CONFORMANCE.md` DOC-A.1-103 already determines: "With checking enabled
(`>>TURN EC-I-O CHECKING ON`, or a level above it) ... the run unit terminates abnormally, even when the file has a
FILE STATUS clause" (`'48'` on WRITE and `'35'` on OPEN behave identically).

The spec: `'91'` is an implementor-defined 9x status (`cite.py --check 9.1.13.11 "An implementor-defined condition
exists"` OK), fatal because the implementor defines it so (DOC-A.1-110; `--check 9.1.13.1 "The implementor may either
continue or terminate the execution of the run unit"` OK), and its condition is EC-I-O-IMP. A fatal EC-I-O condition
whose checking is enabled meets `--check 14.6.13.1.3 "If checking for the exception condition is enabled, execution of
the run unit is terminated abnormally"` (rule 7, OK) once no PERFORM WHEN phrase, USE declarative or PROPAGATE directive
applies; rule 3 lets the implementor "specify otherwise" and DOC-A.1-103 declines to.

Nothing in `SequentialConnector.cs` is wrong (the status 91 arms at `WriteRecord` and the report-line write only set the
status; the dispatch is the generated after-hook, `SequentialIoEmitter.EmitUseHook`, and `FileRegistry.IoConditionName`).
The gap the note exposed was a missing witness: no test pinned `'91'` under the two checking settings. Added
`DocA1Item103WitnessTests.CharacterWithoutByteImage_Status91_WithFileStatusClause_Continues` and
`...CheckingEnabled_TerminatesAbnormally`, and listed them in DOC-A.1-103's witnesses.
