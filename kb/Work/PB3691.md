# PB3691 — the D-FNUSE reading applied to relation conditions

✅ **DECIDED (2026-10-25, the owner): "Refuse it per the spec".** Held at filing under the owner's fuzz rule ("Do not begin fixing any fuzz identified issues without my explicit approval"); this decision is that approval.

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/RelationComparability.cs:77` (`RelationComparability.IsNumericIntegerOperand`),
`src/WiseOwl.Cobol.Compiler/Binding/Procedure/SendingValueTemp.cs:95` (`SendingValueTemp.FunctionValuePic`, comment only),

## The question

PB3665 recorded the determination D-FNUSE in `docs/CONFORMANCE.md` (owner-approved 2026-10-24): §15.2 gives numeric and
integer functions no usage, so a numeric, integer, index or boolean function-identifier is not "described … as usage
display or national", and STRING and INSPECT refuse it where they require that usage. §8.8.4.2.5 (checked) reads: "The
numeric integer operand shall be an integer literal or an integer numeric data item of usage display or national." By
the same reading, `IF FUNCTION INTEGER(N) = "0007"` compares a numeric integer operand that is neither, and should be
refused; today it compiles (repro `E:/COBOL-coord/scratch/op/w20261102a/p/r1.cob`). `SendingValueTemp.FunctionValuePic`
describes a numeric function's temporary as USAGE DISPLAY, which is the representation the relation path relies on and
contradicts D-FNUSE's premise.

Applying D-FNUSE here refuses programs that compile today. Either refuse them (consistent with D-FNUSE, the spec's text),
or record a documented extension that admits a numeric function in this comparison. The owner decides.

## Decided (2026-10-25, the owner)

The operator explained (2026-10-25 ~00:40 PDT): §8.8.4.2.5 (checked) defines the comparison as a text comparison after the integer is "treated as though it were moved … to an elementary data item of the same length in terms of character positions as the number of digits in the integer" (checked), so it needs the operand's digit count; a display item has one (its PICTURE), a binary item and a function result do not. Measured the same night: `01 B PIC 9(4) COMP VALUE 7. IF B = "0007"` is already refused by WiseOwl (COBOL2532, quoting §8.8.4.2.5) and accepted as equal by GnuCOBOL 3.2; `IF FUNCTION INTEGER(N) = "0007"` (N PIC 9(4) VALUE 7) compiles in both and answers not equal in both (repro `E:/Temp/claude/E--COBOL/0a5c7c77-9adc-4c3a-80ea-c89037d1bab4/scratchpad/fuzz4/verify/rel/`). The owner asked why a function differs from an integer field, then decided: "Refuse it per the spec".

**The bar.** One rule in one place: the predicate that admits an operand of §8.8.4.2.5 (`RelationComparability`) asks the SAME question D-FNUSE's STRING and INSPECT checks ask ("described … as usage display or national"), through one shared reader, so a numeric, integer or index function-identifier is refused with COBOL2532 exactly as a binary item is (no new code). Sweep every site that reaches §8.8.4.2.5 (or its national form): the relation condition in both operand orders, abbreviated combined relations, EVALUATE subject/object pairs, SEARCH WHEN, PERFORM UNTIL and the other conditions that bind a relation; and `SendingValueTemp.FunctionValuePic`, which describes a numeric function's temporary as USAGE DISPLAY and contradicts D-FNUSE's premise (fix the description or prove no reader relies on it). Goldens: each refused shape (the diagnostic text), the admitted shapes still admitted (`FUNCTION INTEGER(N) = 7`, a `PIC 9(n)` display item, an alphanumeric or national function compared with text). `docs/CONFORMANCE.md` D-FNUSE gains the relation-condition paragraph with the §8.8.4.2.5 citation (checked) and this decision, in the same change.

## Landed (2026-10-25, wave 20261505 group E)

Re-probed on a fresh Debug build: `IF FUNCTION INTEGER(N) = "0007"` (N PIC 9(4) VALUE 7) compiled and answered not equal, and the sweep found the rule wider than the note: `"0007" = FUNCTION INTEGER(N)`, `X = FUNCTION ABS(N)` / `MAX(N 3)` / `ORD-MAX`, the folded `FUNCTION LENGTH(N) = "4"` (the fold reaches the relation as a literal-shaped operand and answered equal, so one function drew two answers by what the optimizer folded), `FUNCTION LENGTH(G)` over a variable-length group, an abbreviated `X = "0007" OR FUNCTION INTEGER(N)`, EVALUATE subject and object, SEARCH WHEN, PERFORM UNTIL and the national form `U = FUNCTION INTEGER(N)` all compiled. `FUNCTION NUMVAL(X) = X` (a non-integer numeric function) was already COBOL2532, and an index function (`FUNCTION MAX(IX IX)`) opposite a character operand was already COBOL2533 (§8.8.4.2.13), so the index half needed no change.

Fix: `RelationComparability.IsNumericIntegerOperand` asks the ONE reader STRING SR1 and INSPECT SR2 ask, `IntrinsicArgumentRules.FunctionIsNotDisplayOrNational`, before any other arm, so a numeric, integer or index function-identifier (call, lowered tree or folded literal) is never item 6's numeric integer operand and the pair is COBOL2532 (no new code); the one relation checkpoint (`StatementValidation.CheckRelationalOperands`) carries it to every surface. The INTEGER-function arm that admitted it "as the integer numeric temporary §15.4 makes it" is deleted. `SendingValueTemp.FunctionValuePic` was proved to be no usage claim: its USAGE DISPLAY is the implementor's representation (§15.4.1) that sizes the item for `FUNCTION LENGTH` and IN-ARITHMETIC-RANGE, and the only readers are those two (`AlgebraicRange.OfFunctionReturnedValue`, `IntrinsicBinder.FunctionResultLength`); its doc comment now says so and `DisplayOrNationalUsagePredicateDriftTests.RelationItem6NumericOperand_AsksTheOneFunctionReader_AndNoReturnedValueDescription` pins that the relation table asks the one reader first and never reads a returned-value description. The EVALUATE subject intermediate (a Display-usage temp) cannot reopen the hole: the checkpoint judges the operand as written (`ConditionBinder.Written`). Diagnostic text (`COBOL2532` description and message) names the function-identifier. `docs/CONFORMANCE.md` D-FNUSE gained the relation-condition paragraph, D-RELCLASS retracts its INTEGER-function admission, and `CONDITIONS_EXCEPTIONS_DESIGN.md` follows.

Goldens: nine refusals `pb3691-*` (integer function either order, numeric function, folded LENGTH, EVALUATE, SEARCH WHEN, PERFORM UNTIL, abbreviated, national), the controls `pb3691_relation_function_operands` (all four editions) and `pb3691_relation_national_function_controls` (2002+), and `RelationComparabilityTests` (the 24-kind pair matrix now has an alphanumeric and a national function kind and FI/FL are no longer item-6 integer operands; `FunctionIdentifier_IsNoItem6IntegerOperand_AtEverySurface`, `FunctionIdentifier_InADefinedRelation_Compiles`). The old golden `da2_function_as_text` asserted the retracted admission on one line (`TXT = FUNCTION MIN(3 -14 0)` answered `CF=EQ`); that relation is removed and its comment says why. A scan of every conformance-suite, tests and samples program that names a FUNCTION (1,725 programs) found no other relation the new rule refuses. Row `GR-8.8.4.2.1-6` is re-verdicted by batch (its notes retracted the INTEGER-function admission).

The user-defined function is untouched and correct: its temporary is "the description ... of the item specified in the RETURNING phrase" (§8.4.3.2.4 GR1), so `FUNCTION UDISP(N) = "0007"` with a `PIC 9(4)` RETURNING item is admitted and a `COMP` one is refused.
