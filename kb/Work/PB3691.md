# PB3691 — the D-FNUSE reading applied to relation conditions

✅ **DECIDED (2026-10-25, the owner): "Refuse it per the spec".** Held at filing under the owner's fuzz rule ("Do not begin fixing any fuzz identified issues without my explicit approval"); this decision is that approval.

**Sites:** `src/Cobol.Net.Compiler/Binding/RelationComparability.cs` (about line 77),
`src/Cobol.Net.Compiler/Binding/Procedure/SendingValueTemp.cs` (`FunctionValuePic`, about line 95).

## The question

PB3665 recorded the determination D-FNUSE in `docs/CONFORMANCE.md` (owner-approved 2026-10-24): §15.2 gives numeric and
integer functions no usage, so a numeric, integer, index or boolean function-identifier is not "described … as usage
display or national", and STRING and INSPECT refuse it where they require that usage. §8.8.4.2.5 (checked) reads: "The
numeric integer operand shall be an integer literal or an integer numeric data item of usage display or national." By
the same reading, `IF FUNCTION INTEGER(N) = "0007"` compares a numeric integer operand that is neither, and should be
refused; today it compiles (repro `E:/COBOL-coord/scratch/op/w20261102a/p/r1.cob`). `SendingValueTemp.FunctionValuePic`
describes a numeric function's temporary as USAGE DISPLAY, which is the representation the relation path relies on and
contradicts D-FNUSE's premise.

Applying D-FNUSE here refuses programs that compile today. Either refuse them (consistent with D-FNUSE, the spec's text),
or record a documented extension that admits a numeric function in this comparison. The owner decides.

## Decided (2026-10-25, the owner)

The operator explained (2026-10-25 ~00:40 PDT): §8.8.4.2.5 (checked) defines the comparison as a text comparison after the integer is "treated as though it were moved … to an elementary data item of the same length in terms of character positions as the number of digits in the integer" (checked), so it needs the operand's digit count; a display item has one (its PICTURE), a binary item and a function result do not. Measured the same night: `01 B PIC 9(4) COMP VALUE 7. IF B = "0007"` is already refused by WiseOwl (COBOLNET2532, quoting §8.8.4.2.5) and accepted as equal by GnuCOBOL 3.2; `IF FUNCTION INTEGER(N) = "0007"` (N PIC 9(4) VALUE 7) compiles in both and answers not equal in both (repro `E:/Temp/claude/E--COBOL/0a5c7c77-9adc-4c3a-80ea-c89037d1bab4/scratchpad/fuzz4/verify/rel/`). The owner asked why a function differs from an integer field, then decided: "Refuse it per the spec".

**The bar.** One rule in one place: the predicate that admits an operand of §8.8.4.2.5 (`RelationComparability`) asks the SAME question D-FNUSE's STRING and INSPECT checks ask ("described … as usage display or national"), through one shared reader, so a numeric, integer or index function-identifier is refused with COBOLNET2532 exactly as a binary item is (no new code). Sweep every site that reaches §8.8.4.2.5 (or its national form): the relation condition in both operand orders, abbreviated combined relations, EVALUATE subject/object pairs, SEARCH WHEN, PERFORM UNTIL and the other conditions that bind a relation; and `SendingValueTemp.FunctionValuePic`, which describes a numeric function's temporary as USAGE DISPLAY and contradicts D-FNUSE's premise (fix the description or prove no reader relies on it). Goldens: each refused shape (the diagnostic text), the admitted shapes still admitted (`FUNCTION INTEGER(N) = 7`, a `PIC 9(n)` display item, an alphanumeric or national function compared with text). `docs/CONFORMANCE.md` D-FNUSE gains the relation-condition paragraph with the §8.8.4.2.5 citation (checked) and this decision, in the same change.
