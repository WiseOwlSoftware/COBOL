### [inspect-statement-p2] LEADING's anchor is set when the shared cycle first VISITS the operand, not at the start of its eligibility region: CobolInspect.Tally/Replace set expectedPos = pos on the first cycle that reaches the LEADING operand, but the GR8 cycle breaks on the first earlier operand that matches, so when an earlier operand consumes the region start the anchor slides forward and a later run is wrongly counted/replaced as 'leading'
- **Rows:** GR-14.9.22.4-12, GR-14.9.22.4-17 — harm `wrong-answer`
- **Repro:** 01 S1 PIC X(4). 01 NX PIC 99 VALUE 0. 01 NA PIC 99 VALUE 0. MOVE 'XAAB' TO S1. INSPECT S1 TALLYING NX FOR ALL 'X' NA FOR LEADING 'A' -> NA=02. MOVE 'XAAB' TO S1. INSPECT S1 REPLACING ALL 'X' BY 'Y' LEADING 'A' BY 'Z' -> 'YZZB'. Also Annex D.25 EXAMPLE 3 row 1 'BBEABDABABBCABEE' -> COUNT-1=1 COUNT-2=1 'BBEXYZXYXYWCABVE'. (E:/Temp/claude/E--CobolSharp/a700c052-f9e4-4942-84ff-a13c7505d6ec/scratchpad/adj-d1/out/probe/inspect-p2/p1.cob T1/T2/T3/T9, p4.cob)
- **Expected (spec):** NA=00 and S1='YAAB': the LEADING occurrence must be 'at the point where comparison began in the first comparison cycle in which literal-1 was eligible to participate' (GR12b / GR17c) - the operand is eligible (GR9a/b/c) from position 1 of the region, where 'X' sits. Annex D.25 EXAMPLE 3 row 1 prints COUNT-1=0, COUNT-2=2, 'BBEXYZXYXYZCABVE'.
- **Observed:** Tally: `if (expectedPos[k] < 0) { if (!inRegion) continue; expectedPos[k] = pos; }` runs only when the loop reaches operand k, and the loop `break`s after an earlier operand's match, so at the region start the LEADING operand is never visited and its anchor is taken from the next unconsumed position. Replace copies the same machinery. The fix is an anchor fixed before the first cycle (the operand's region start, in scan direction) - the same place Region() already fixes the boundaries. Existing Tally_SharedCycle_EarlierAllStarvesLeading passes only because its later position does not hold the pattern.
- **Code site:** src/Cobol.Net.Runtime/Verbs/CobolInspect.cs#Tally (LEADING arm); src/Cobol.Net.Runtime/Verbs/CobolInspect.cs#Replace (ReplaceLeading arm)

### [inspect-statement-p3] INSPECT LEADING anchors its run at the first cycle that REACHES the operand, not the first cycle in which it is ELIGIBLE: CobolInspect.Tally/Replace set expectedPos lazily inside the operand loop, so when an earlier operand matches at the eligible start the LEADING operand is never visited there and later anchors at a downstream position and counts/replaces a non-leading run
- **Rows:** GR-14.9.22.4-L2.2 — harm `wrong-answer`
- **Repro:** 01 X PIC X(4) VALUE "ABBC". 01 C1 PIC 99 VALUE 0. 01 C2 PIC 99 VALUE 0. 01 Z PIC X(4) VALUE "ABBC". INSPECT X TALLYING C1 FOR ALL "A" C2 FOR LEADING "B". INSPECT Z REPLACING ALL "A" BY "a" LEADING "B" BY "b". DISPLAY C1 C2 Z.
- **Expected (spec):** C1=01 C2=00 Z=aBBC — GR9 a) makes position 1 the first eligible point, GR12 b)/GR17 c) require the first occurrence to be there, and position 1 holds 'A'.
- **Observed:** Pinned cobol.exe prints C1=01 C2=02 and Z=abbC. In Tally/Replace, `if (expectedPos[k] < 0) { if (!inRegion) continue; expectedPos[k] = pos; }` runs only when the loop reaches operand k; the `break` after an earlier operand's match skips it for that cycle. The fix is to fix each LEADING operand's anchor (its region start) up front, before the first cycle, as Region already does for eligibility.
- **Code site:** src/Cobol.Net.Runtime/Verbs/CobolInspect.cs#Tally (LEADING arm, ~L127-148); #Replace (ReplaceLeading arm, ~L240-258)

## What the fixer owes
Set the LEADING operand's expected position at the START of its eligibility region (after its AFTER delimiter), independent of which operand the cycle visits; a match elsewhere first closes the leading run. Fix CobolInspect.Tally AND Replace (ReplaceLeading) — the two arms.
