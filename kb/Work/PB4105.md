# PB4105 — GnuCOBOL: a national-edited item counts each B, 0 or / as one byte: PIC NNBNN is 9 bytes with LENGTH 4 (18 bytes, LENGTH 9 with USAGE NATIONAL) instead of five national character positions

Found by patcher C while working the drafted ticket `national-storage-move-compare` (kb/Work PB3937): its probe
`~/gc-fix/national-storage-move-compare-run/nedit.cob` (WSL) showed `PIC NNBNN` at 9 bytes. Recorded nowhere before
this note. Re-run and extended for this filing on 2026-10-30.

## Summary

GnuCOBOL sizes a national-edited item by counting each `N` as two bytes (its UTF-16 national character) and each
insertion symbol `B`, `0` or `/` as one byte. `PIC NNBNN` (implicitly USAGE NATIONAL) is allocated 9 bytes,
`FUNCTION LENGTH` returns 4, and a following item in the same group starts one byte early (the group of `PIC NNBNN`
and `PIC X` is 10 bytes). The standard makes every symbol of a national-edited picture a national character position,
so the item is five national character positions: LENGTH 5, and on GnuCOBOL's two-byte representation 10 bytes, as
`PIC N(5)` already is. With an explicit `USAGE NATIONAL` the 9 is then doubled (PB3937's defect) to 18 bytes, LENGTH 9.
`NN0NN` and `NN/NN` give the same 9 / 4, `NBBBN` 7 / 3. Present in 3.2.0 and 3.3-dev r5751, under `-std=cobol2014` and
the default dialect. Class: wrong output.

## Expected result (per ISO)

`10 5`, `10 5`, `10 5`, `11` (and `10 5`, `10 5`, `10 5` for nesib). The LENGTH values are fixed by the standard; the
BYTE-LENGTH values follow from GnuCOBOL's own two bytes per national character, which `PIC N(5)` shows.

- §13.18.40.4 10) (checked): "To define an item as national-edited, character-string-1 shall include" at least one 'N'
  and one of 'B', '0', '/' (or character-1): `NNBNN` is national-edited.
- §13.18.60.3 13) a) (checked): "if the explicit or implicit picture character-string contains the symbol 'N', a USAGE
  NATIONAL clause is implied", so IMP-E and EXP-E describe the same item.
- §13.18.40.4 1) (checked): "When the usage of the subject of the entry is national, each symbol representing a
  character position defines a national character position."
- §13.18.40.4 14) (checked): "Each symbol 'B' represents a character position into which the character space will be
  inserted during editing. Each symbol 'B' is counted in the size of the item." The same rule says so of '0' and '/',
  and of 'N': "Each symbol 'N' represents a national character position ... Each symbol 'N' is counted in the size of
  the item." So `NNBNN` is five national character positions.
- §15.50.4 2) (checked): for an elementary data item of usage national "the returned value is an integer equal to the
  length of argument-1 in national character positions": LENGTH is 5. A result of 4 (and 9 bytes, an odd byte count
  for a two-byte national representation) cannot be read as encoding latitude.

## Class

wrong-output: the item's size, its LENGTH and the offsets of the items after it in a record are wrong for a legal
description. GnuCOBOL warns that USAGE NATIONAL handling is unfinished, so the defect is not silent.

## Fix site

- 3.3-dev r5751: `cobc/tree.c`, `cb_build_picture`, the "Calculate size" step (about line 3835): every symbol other than
  `V` and `P` adds `n`, and only `N` adds `n * (COB_NATIONAL_SIZE - 1)`. The category is decided after the loop
  (`case PIC_NATIONAL_EDITED:`, about line 3962), so a `B`, `0` or `/` (and character-1) in a national-edited picture
  never receives the national width. Inferred fix: when the category resolves to national-edited, count those symbols
  at `COB_NATIONAL_SIZE` too (for example by tracking the insertion-symbol count in the loop and adding
  `count * (COB_NATIONAL_SIZE - 1)` in the `PIC_NATIONAL_EDITED` case). 3.2.0 has the same step (`cobc/tree.c`, about
  line 3821).
- The 18 / 9 of EXP-E is this size doubled by `cobc/field.c` `compute_size`, `case CB_USAGE_NATIONAL:`
  `f->size = f->pic->size * COB_NATIONAL_SIZE` (about line 3142), which is PB3937's site: fixing only this record gives
  `EXP-E` 20 / 10 until PB3937 is fixed too.
- Not built or tested; the site is read from the source and matches the observed sizes (2+2+1+2+2 = 9).

## Draft issue

**Title:** national-edited item counts B, 0 and / as one byte: PIC NNBNN is 9 bytes, FUNCTION LENGTH 4

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1) and 3.3-dev r5751, x86_64 Linux.

Steps: `cobc -std=cobol2014 -fformat=free -x nesize.cob && ./nesize` with the attached `nesize.cob` (the program above).

Observed: `9 4` for `PIC NNBNN`, `18 9` for `PIC NNBNN USAGE NATIONAL`, `10 5` for `PIC N(5)`, and a group of
`PIC NNBNN` plus `PIC X` is 10 bytes. `NN0NN` and `NN/NN` give `9 4`, `NBBBN` gives `7 3`.

Expected: `PIC NNBNN` is five national character positions, so LENGTH 5 and (at two bytes per national character, as
`PIC N(5)`) 10 bytes; the group is 11. ISO/IEC 1989:2023 §13.18.40.4 general rule 1: "When the usage of the subject of
the entry is national, each symbol representing a character position defines a national character position"; rule 14:
"Each symbol 'B' ... is counted in the size of the item" (likewise '0' and '/'); §15.50.4 rule 2: LENGTH of a national
item is its length "in national character positions". A picture with 'N' implies USAGE NATIONAL (§13.18.60.3 rule 13 a),
so the explicit-USAGE form should be the same 10 bytes; it is 18 because the separate doubling of an explicit USAGE
NATIONAL item (reported with PB3937's repro) applies on top.

Where: `cobc/tree.c`, `cb_build_picture`, "Calculate size": only 'N' adds `COB_NATIONAL_SIZE - 1`; the insertion
symbols of a national-edited picture should too, once the category is known to be national-edited.
