# PB2022 — LANDED: the prompt write is asynchronous, and a unit silent at start is killed

The wave unit started 2026-10-04 23:53 sat for two hours with a 0-byte stream log, no checkpoint, `claude.exe` at 0.66 s of CPU with no
session transcript and no children. Nothing was at risk (no worktree or branch), and no compiler work was done in that time. Cause, reproduced:
`Invoke-Unit` wrote the prompt with a synchronous `StandardInput.WriteLine` BEFORE it started reading stdout. The CLI writes a large `init`
event (tools, MCP servers, slash commands) to stdout before it reads stdin; once that fills the stdout pipe the child blocks until the supervisor
reads, and a synchronous write of a prompt larger than the stdin pipe buffer (about 4 KB) blocks until the child reads: each waits for the other.
The wave prompt crossed that size on 2026-10-04 when PB2015 and PB2016 added paragraphs to `units/common.md` and `units/wave.md` (about 4.5 KB;
`meter` stays near 3 KB, which is why it kept working), so the first wave started after those landings hung. Earlier hypotheses, tested and
discarded with evidence: a machine sleep (the AC sleep timeout is 0 and the power log has no suspend event), a slow checkpoint (`checkpoint.py`
takes 0.4 s).

Fix (`scripts/orchestrator/orchestrate.ps1`): the prompt goes through `WriteLineAsync` and the read loop starts at once; a failed write kills the
unit and says so. Second line of defence: a startup watchdog counts loop TICKS (one per second waited, so a suspended machine cannot trip it)
with no event at all and kills a unit still silent after `-StartupTicks` (300); the unit counts as failed and its handoff is synthesized (PB2015).
Tests (`test_orchestrate.ps1` 4j and 4k, 78/78): a fake that writes a 300 KB `init` before it reads stdin (the run is bounded, so a regression FAILS
instead of hanging the suite; against the old code both checks failed with a 90 s timeout), and a fake that emits nothing.

Lesson recorded in the design doc: a supervisor must never block on a write to a child while it is not also reading the child's output.
