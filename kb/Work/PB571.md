# PB571

## Mechanism
`IF <index data item> IS NUMERIC` compiles clean and answers TRUE: PicInfo.IndexItem records category NUMERIC and CheckClassConditionOperand screens only a boolean subject, so the class question about a class-INDEX item is answered as though its class were numeric

### The refutation this note is written from
Row `GR-13.18.60.4-10` was adjudicated CONFORMS and OVERTURNED to `PARTIAL` by the refuter. Its reasoning, verbatim:

> The rule's second sentence - 'The class and category of an index data item are index' - is NOT carried through to every class-sensitive site, and the adjudicator measured only the two arms that pass (MOVE -> COBOLNET0809, DISPLAY -> pb148). The class-condition arm leaks and produces a WRONG ANSWER. PicCategory has no Index member at all (PicInfo.cs:10-48); PicInfo.IndexItem is built as `new(PicCategory.Numeric, Usage.Index, ...)` (PicInfo.cs:621), i.e. the model records class/category NUMERIC and the index-ness lives only in Usage. ConditionBinder.CheckClassConditionOperand implements exactly one half of the sibling syntax rule it must honour (SS8.8.4.4.3 SR1, verified with cite.py): it rejects a strongly-typed group and then `if (pic is not { Category: PicCategory.Boolean }) return;` - so class index / pointer / object operands are never screened. Measured with the pinned cobol.exe: `01 IX USAGE INDEX. ... SET IX TO 3 IF IX IS NUMERIC` compiles clean at --std 2023 and PRINTS 'IX IS NUMERIC' (exit 0), where SS8.8.4.4.3 SR1 requires a diagnostic because IX is class index. So the compiler answers a class question about an index data item as though its class were numeric - the precise contradiction of this rule's sentence 2. (The arithmetic-operand arm the adjudicator flagged as PB213 is in fact CLOSED in this pinned tree - COBOLNET0844 fires on both COMPUTE and ADD - which makes the class-condition hole the live one, not a duplicate of PB213.) Sentences 1, 3 and 4 (occurrence-number carrier, implementor determination = 8-byte big-endian, documented at CONFORMANCE.md item 211) do hold. Two halves, one verified => PARTIAL by the standing rule; the leaking half is not merely untested but measurably wrong.
