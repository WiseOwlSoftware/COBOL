# PB807 — OPEN — `operandRequired` is a presence test where a grammar belongs

Filed 2026-09-09 by the registrar from the PB794 implementer's report (§10, N2), which was never filed as a
note. Re-measured on main at `d497f3c7` with this worktree's own build.

## Reproduced on main

`cc_display_junk.cob`:

```cobol
       PROCEDURE DIVISION.
       MAIN-PARA.
       >>DISPLAY )( 3 +
           STOP RUN.
```

`cobol --std 2023 cc_display_junk.cob` → **exit 0, zero diagnostics.** Unbalanced parentheses in reverse order,
a bare integer and a trailing `+`: not an arithmetic expression, not a boolean expression, not a literal, not a
PARAMETER phrase — four alternatives, none of them matched, and no diagnosis.

## The rule

`cite.py --check 7.3.12.2 "PARAMETER"` → **OK, §7.3.12.2** (General format). The printed format:

```
          ╭ arithmetic-expression-1               ╮
          │ boolean-expression-1                  │
>>DISPLAY ┤                                       ├ …
          │ literal-1                             │
          ╰ PARAMETER compilation-variable-name-1 ╯

┌      ╭ │ compile-time-device-1 … │ ╮ ┐
│ UPON ┤ │                         │ ├ │
└      ╰ │ LISTING                 │ ╯ ┘
```

Four facts the current row cannot express:

1. **The operand is a CHOICE of four alternatives**, not free text. `cite.py --check 7.3.12.3 "The DISPLAY
   directive shall begin on a new line"` → **OK, §7.3.12.3 1)**; SR2 and SR3 bind two of the four to their own
   clauses — *"Arithmetic-expression-1 shall be formed in accordance with 7.3.6"* and *"Boolean-expression-1
   shall be formed in accordance with 7.3.7"*.
2. **The operand REPEATS** (the trailing `…`), and §7.3.12.4 GR4 depends on the order: *"When a DISPLAY
   directive contains more than one operand the values of the operands are transferred in the sequence in which
   the operands are encountered."*
3. ⛔ **The UPON group is enclosed in CHOICE INDICATORS** — the `|` bars inside its braces. Per §5.2.6.4 that
   means ONE OR MORE of the enclosed alternatives, each at most once, in any order, so a single `UPON` phrase
   may name `compile-time-device-1` alone, `LISTING` alone, or **both**. `cite.py --check 5.2.6.4 "Choice
   indicators"` → **OK, §5.2.6.4**.
4. **The UPON phrase is optional and has a default** — §7.3.12.4 GR6: *"If the UPON phrase is not specified,
   the default is as if UPON LISTING were specified."*

None of the four is enforced. The construct is `under_rejects` + `silent`.

## The code site

`tests/version-matrix/constructs.json`, row `display-directive-2023`:

```json
"directiveOperand": { "form": "text", "operandRequired": true,
                      "citation": "ISO §7.3.12.2 general format: the operand braces are not brace…" }
```

Consumed by `CompilerDirectiveCatalog.CheckOperand` (`src/Cobol.Net.Editions/CompilerDirectiveCatalog.cs`) and
`DirectiveOperandSyntax` (`src/Cobol.Net.Editions/DirectiveOperandSyntax.cs`), called once from
`ConditionalCompilationProcessor.cs:213`. `form: text` means *"any non-empty text"*; `operandRequired: true` is
therefore a **presence test** — it is what turned `>>DISPLAY` with nothing after it from silent acceptance into
COBOLNET1911, and it is the whole of the checking. [[PB794]] recorded this honestly rather than closing the row:
the citation string on the row names the residue, and `FMT-7.3.12.2` was deliberately left GAP.

## Shape of a fix

⛔ **This is the first directive whose operand is a real GRAMMAR rather than a closed word set**, so the answer
is not another `directiveOperand` form flag. §7.3.12.3 SR2/SR3 point at §7.3.6 and §7.3.7 — the compile-time
arithmetic and boolean expression grammars — which the conditional-compilation stage **already evaluates** for
`>>IF` and `>>EVALUATE` (`EvaluateCceText`). The DISPLAY operand list is those same two evaluators plus a
literal and a `PARAMETER` name, in a repeating list, and the natural shape is to reach the existing evaluator
rather than to grow a third spelling of expression parsing (`feedback_one_rule_one_place`).

The UPON phrase then needs §5.2.6.4 choice-indicator semantics — one or more, each once, any order — which is
the *same* shape several other formats carry and which nothing in the tree models generally. Deciding whether
to model choice indicators once (and derive this use from it) or to hand-write this one occurrence is a design
question that belongs in the compiler-directives design doc **in the same change set** (CLAUDE.md rules 2
and 5); prefer the shape that makes the next choice-indicator format automatic.

Also required by §7.3.12.4: GR1/GR4 (transfer each operand, in order), GR3 (a PARAMETER value comes from the
operating environment by an implementor-defined method, and **no transfer takes place** when the environment
supplies none), GR5/GR6 (UPON's two destinations and the UPON-LISTING default). ⚠ §7.3.12.4 GR2 makes the
transfer implementor-defined when the compiler produces no source listing — this compiler produces none, which
is a **documented determination to record in `docs/CONFORMANCE.md`**, not a licence to skip the syntax.

## Sweep the fixer must do

- **`>>PAGE`, `>>FLAG-85` and `>>FLAG-NATIVE-ARITHMETIC` carry the same `form: text` with
  `operandRequired: false`** — the identical presence-only test with the boolean flipped. `>>PAGE`'s operand is
  `comment-text-1`, genuinely free text, so its row is right; the two window rows are worth re-deriving against
  their own formats rather than assumed (`feedback_a_dead_lookup_is_also_unverified`).
- **Every `form: stage` row** — see [[PB806]]: that form currently means both *"a stage checks it"* and
  *"nobody does"*.
- **The catalog-derived witness must gain a DISPLAY leg that is proven RED first** on `>>DISPLAY )( 3 +`;
  `CompilerDirectiveCatalogDriftTests` today drives only the closed-word-set rows, so the DISPLAY row is
  outside the population its green attests to (`feedback_measure_the_selectors_complement`).
