## Finding — compiler-directives (under-rejects)

directive-word-reservation: no check anywhere in src consults the §8.12 compiler-directive-word list for a user-defined-word slot INSIDE a directive. The >>DEFINE stage accepts any COBOL word as compilation-variable-name-1, including the words of DEFINE's own general format, so the context reservation of §7.3.3 SR7 (and its specific instance §7.3.11.3 SR1, also §7.3.8.4.4 SR1 for the defined condition) is never enforced. The other half of SR7 (the words are ordinary outside directives) is correct.

**Rows:** SR-7.3.3-7

**Repro:**

```
PROCEDURE DIVISION. '       >>DEFINE OVERRIDE AS 1' / DISPLAY "R2". STOP RUN. Likewise DEFINED (R3), PARAMETER (R4), OFF (R5), IS (R6), PUSH (R7), IMP (I2); and R1 '>>DEFINE AS AS 1' followed by '>>IF AS = 1' (E:\Temp\claude\E--CobolSharp\a700c052-f9e4-4942-84ff-a13c7505d6ec\scratchpad\adj-d2\out\probe\cd\R1.cob..R7.cob, I2.cob).
```

**Expected from the spec:** §7.3.3 SR7 'When a compiler-directive word is specified in the general format of a compiler directive, that compiler-directive word is reserved within the context of that directive.'; §7.3.11.3 SR1 'Compilation-variable-name-1 shall not be the same as a compiler-directive word.' (both cite.py --check OK). Every one of these >>DEFINE lines must be rejected at the DEFINE.

**Observed:** R2-R7 and I2 compile clean and run; R1 is accepted at the DEFINE and only the later >>IF fails, with a misleading 'malformed compile-time expression'. Outside directives the same words (DEFINED, CHECKING, PARAMETER, TURN, PUSH, POP, ...) are correctly usable as data-names (R11 prints '12456789ABCDE'). Inventory row SR-7.3.11.3-1 is unadjudicated and should be claimed by the same note.

**Code site:** src/Cobol.Net.Frontend/Preprocessor/ConditionalCompilationProcessor.cs (the >>DEFINE arm of Render: compilation-variable-name-1 is taken without a §8.12 screen); the §8.12 list has no representation in src (it should be data, derived once, beside CompilerDirectiveCatalog)

## Finding — defined-condition (under-rejects)

No compiler-directive-word screen on a compilation-variable-name: the defined-condition (and the >>DEFINE directive) accept any cobolWord, so §8.12 words and exception-names are silently treated as ordinary (undefined, or even definable) compilation variables.

**Rows:** SR-7.3.8.4.3-1

**Repro:**

```
>>SOURCE FORMAT FREE / IDENTIFICATION DIVISION. PROGRAM-ID. PSR. PROCEDURE DIVISION. / >>IF LISTING IS DEFINED / DISPLAY "DEF" / >>ELSE / DISPLAY "UNDEF" / >>END-IF / STOP RUN.  -- cobol --std 2023 --run prints UNDEF with no diagnostic (same for TURN, EC-SIZE, CHECKING, LEAP-SECOND, DEFINE, NUMVAL). Sibling: >>DEFINE LISTING AS 1 is accepted and >>IF LISTING IS DEFINED then prints DEF.
```

**Expected from the spec:** §7.3.8.4.3 SR1: 'Compilation-variable-name-1 shall not be the same as a compiler-directive word.' Every word in the §8.12 table and every §14.6.13.1 exception-name ('all of the exception-names specified in 14.6.13.1, Exception conditions, are reserved in the context of compiler directives') written as compilation-variable-name-1 shall be diagnosed at compile time; §7.3.11.3 SR1 imposes the same constraint on the >>DEFINE name.

**Observed:** Grammar definedCondition : cobolWord IS? NOT? DEFINED and EvalDefined (_resolveName lookup) have no word screen; ConditionalCompilationProcessor.ApplyDefine checks only the §8.3.2.1 length. Only the words the primed directive lexer happens to tokenize (IF, PAGE, SOURCE, FORMAT) are rejected, and then as COBOLNET1619 'malformed', not as the SR. The fix belongs in one place: a single §8.12 compiler-directive-word set (plus the exception-name catalog) consulted at both the defined-condition and the DEFINE name site, with a drift test against the §8.12 table.

**Code site:** src/Cobol.Net.Frontend/Expressions/CompileTimeExpressionEvaluator.cs#EvalDefined; src/Cobol.Net.Frontend/Preprocessor/ConditionalCompilationProcessor.cs#ApplyDefine; src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4#definedCondition
