# PB3648 — the Linux gate's disk bound does not count the audit clone

**Sites:** `scripts/linux-gate.sh` (the bound comment near `GATES_ROOT`, `check_disk`, `MIN_FREE_INODES`, `MIN_FREE_KB`, the audit clone and its `dotnet build Cobol.Net.sln`).

## What happens

Since PB2878 the full-lane Linux gate makes an audit clone and builds `Cobol.Net.sln` in it, beside the main clone's build. The comment at the PB3194 bound says one built gate is about 80,000 inodes and 1 GB (measured 2026-10-23) and that the floors hold about twelve gates. With two clones per gate the same floors hold about six, and `check_disk` can refuse a gate, or the disk can fill, that PB3194 said it prevents. No measurement of the added build cost or footprint is recorded.

## Fix direction

Measure a gate's footprint and build time with the audit clone, update `MIN_FREE_INODES`, `MIN_FREE_KB` and the comment from the measurement, or build the audit clone without a second `dotnet build`.

Report `w20261029a2-PB2878-report.md` (PB2878 part 2, landed in PR #501), review lead R1-4.

## Landing (wave 20261104, group A2)

Re-probed by measurement, not by reading: a full-lane `bash scripts/linux-gate.sh --nice` of this branch's head (WSL
Ubuntu, 32 processors), its gate directory sampled every 20 s with `du -sk` and `find | wc -l`.

- Before PB2878 (PB3194, 2026-10-23), one built clone: about 1 GB and 80,000 inodes, one `dotnet build Cobol.Net.sln`.
- The full lane now, two built clones: a peak of 1,714,628 KB (1.64 GiB) and 101,682 inodes, and two builds that run
  concurrently, 49.5 s and 49.8 s, so the wall clock of one.

So the note's arithmetic was too pessimistic (the second clone adds about 0.7 GB and 22,000 inodes, not another 1 GB and
80,000, since the sources are a `--shared` clone and only the build output doubles) and its premise held: the old bound
comment sized one clone. The second `dotnet build` stays: the audit clone exists so the script self-tests and the guard
read inert paths outside the inert watch of the test legs (DESIGN-test-build-ci.md §3.18), and the assemblies bake in
the clone's path (`[CallerFilePath]`), so the legs cannot share one build. Fixed at the root, so it cannot go stale
again:

- The bounds are no hand-kept numbers: `MIN_FREE_INODES = GATES_HELD * GATE_INODES` and `MIN_FREE_KB = GATES_HELD *
  GATE_KB`, with GATES_HELD 12 (the gate cap plus the implementers beside it), GATE_INODES 110,000 and GATE_KB 1,800 MiB
  (the measured full lane, with headroom), sized for the dearest lane because `check_disk` runs before the lane is known.
- Every gate (full and targeted) measures itself before its verdict (`footprint_report`): a line `linux-gate: footprint of
  this gate: N KB, M inodes (...)` in its log (the driver keeps it in the run's `linux-leg.log`), and a `FOOTPRINT NOTE`
  naming the constants when it holds more than they allow. Never a verdict; the next growth of the gate is a line in a
  log. Self-tests: the bounds equal the product; a gate under the figures reports without a note, one over them notes it.

A targeted gate's own footprint (one clone) is recorded by that line in the run that gates this branch.

**For the next implementer.** `scripts/linux-gate.sh#footprint_report` and the `GATES_HELD`/`GATE_INODES`/`GATE_KB` constants own the disk bound (the bound is their product; re-measure by reading any gate's `footprint of this gate` line, never by sampling the gate directory while the inert watch runs: a `find` or `du` of the watched clone lists its inert directories and reddens the watch).
