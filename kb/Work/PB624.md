# PB624 — LANDED — a dead arm with the live defect's shape

Found 2026-09-05 by the `PB253` implementer (report §"New defects" (2)), whose sweep of every `Receiver.Real` /
`Receiverless` test in the emitter found one more site with the receiver-before-mode ordering and measured it
unreachable rather than assuming it: the standard-mode arm at the top of `RenderNum` claims NUMVAL-F before the
switch is reached.

## The site

`src/WiseOwl.Cobol.Compiler/CodeGen/Emit/IntrinsicRenderer.cs`, `case "NumvalF":` (≈`:354` on PB253's tree) tests
`num.Receiver.Real || (num.Receiver.Receiverless && !num.Receiver.MoveSender)` with no mode guard. Under a standard
arithmetic mode §15.4.1 makes the CONTAINER unconditional — the returned value "is contained in a temporary standard
data item in the intermediate form defined for the arithmetic mode in effect" (`OK §15.4.1`) — and the arm as
written would hand out a binary64 for a receiver-less reference. It does not today only because NUMVAL-F is a
member of the always-SDIDI set consulted first (PB252's `StandardValueFixedByRule` after train 5 lands;
`alwaysDec` before it). Nothing asserts the coupling: `StandardModeReturnedValueContainerDriftTests` (PB253) covers
`Float: true` catalog rows, and NUMVAL-F's row is not one.

## Fix shape

Two mechanisms are on offer and PB253 deliberately did not choose between them: hoist the container decision above
the WHOLE exact switch (so no arm inside it can test the receiver shape before the mode — the structural answer,
and the one PB253's `RenderFloat`/`RenderFloatNative` split already gives the float family), or extend the drift
test so a function routed by an always-SDIDI set is asserted to be routed there. Take the first: it makes the next
case automatic ([[PB253]]'s rule-5 argument), and it leaves the NUMVAL-F arm free to lose its receiver test. Then
widen `StandardModeReturnedValueContainerDriftTests` from "every `Float: true` row" to "every row whose runtime method
returns a double", so NUMVAL-F is inside the guard by derivation rather than by a flag.

## Landed with PB3839

The `case "NumvalF"` arm is deleted (kb/Work PB3839): NUMVAL-F joined NUMVAL and NUMVAL-C in `IntrinsicCarrierRules.ReturnsExactParse`, which
`RenderNum` asks BEFORE the arithmetic-mode dispatch, so no arm inside the switch can test the receiver shape before the mode, and
`ReceiverShapeReaderDriftTests.TheExactParseFunctions_HaveNoArmOfTheirOwn_AndOneSdidiBody` asserts the coupling this note found unasserted (a
member of the set has no `RenderNum` arm and an SDIDI arm in `RenderDec`). The structural fix this note preferred (hoisting the container
decision above the whole exact switch) is what PB3829 did for the float family and this does for the NUMVAL family.
