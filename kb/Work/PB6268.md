**Rule it breaks:** DESIGN-architecture-review §5.4 (complexity at a stated input size; one pass where one suffices) and dimensions.md 3 (no repeated work on a hot path); IntrinsicRenderer's own INTAKE(PREDICATE) members render a full argument only to read its carrier flags and discard the text

**Scenario:** Count read from the pinned code, native arithmetic, fixed-point receiver: COMPUTE R = FUNCTION MAX(A B) over two fixed-point data items renders the arguments through num.AsNum 17 times where 2 are needed (8n+1 for n arguments: AnyDecRaw n, SelectionNeedsExactLane's eagerly evaluated AnyRealArgument n + AllRealArguments 1 + AnyFloatItemArgument n + AnyApproximateArgument n, SelectionPastReceiverHeadroom 2n, the PB635 AnyRealArgument n, RawArgPairs n). A nested call is re-rendered whole each time (NumericRenderer.Visit(BoundIntrinsicCall) calls RenderNum with no memo, and RenderWide adds one more pass when any argument is computed), so the work multiplies per level: FUNCTION ABS(FUNCTION ABS(X)) renders X 12 times and a depth-d ABS chain 3*4^(d-1) times; MAX(MAX(MAX(A B) C) D) renders its leaves about 19*19*17 = 6137 times for 4 operands. Every discarded render also allocates its C# text and advances _withSerial. The perf baseline (b1a42fc36e8b) has no intrinsic-nesting row, so the wall-clock cost is unmeasured; the pass count is exact.

No row in perf-baseline b1a42fc36e8b covers intrinsic nesting.
