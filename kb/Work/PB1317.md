# PB1317 — OPEN — the declarative runs, the growth never happens

## Measured (`ovfres.cob`, `--std 2023`)
```cobol
       01 T.
          05 E PIC 9(3) OCCURS DYNAMIC CAPACITY IN CAP
                FROM 1 TO 3 INITIALIZED.
       01 I PIC 9(2) VALUE 5.
       PROCEDURE DIVISION.
       DECLARATIVES.
       D-OVF SECTION.
           USE AFTER EXCEPTION CONDITION EC-BOUND-OVERFLOW.
       D-1.
           DISPLAY "DECL " FUNCTION EXCEPTION-STATUS.
           RESUME NEXT STATEMENT.
       END DECLARATIVES.
       MAIN SECTION.
       M-1.
      >>TURN EC-BOUND-OVERFLOW CHECKING ON
           MOVE 42 TO E (I).
           DISPLAY "CAP=[" CAP "] E5=[" E (I) "]".
```
```
DECL EC-BOUND-OVERFLOW
CAP=[0000000001] E5=[000]
```

## The rule
```
$ cite.py --check 8.5.1.9.6 'executes a RESUME statement with the NEXT STATEMENT phrase, the operation shall be allowed to continue'
  OK  §8.5.1.9.6 1)  (Exceeding capacity)
      If checking for the EC-BOUND-OVERFLOW exception condition is not turned on, or results in the execution of
      a declarative procedure or a procedure in a WHEN phrase of a PERFORM statement that executes a RESUME
      statement with the NEXT STATEMENT phrase, the operation shall be allowed to continue …
```
The declarative ran and executed RESUME NEXT STATEMENT, so the MOVE's implicit growth to occurrence 5 is supposed
to complete. Expected: `CAP=[0000000005] E5=[042]`. Observed: the table did not grow, the store was lost, and the
program printed a stale value with nothing raised. That is a silent wrong answer.

## Mechanism
`src/Cobol.Net.Runtime/Values/Tables/CobolDynTable.cs:72` `RefReceiving(long occ)` raises
`ExceptionState.BoundOverflowError(...)` BEFORE `GrowTo(occ)`. `BoundOverflowError` goes to
`NonfatalIfEnabled` (`src/Cobol.Net.Runtime/Exceptions/ExceptionState.cs:396/540`), which THROWS the resume
signal when a declarative handles the condition. That unwinds out of `RefReceiving`, so neither `GrowTo` nor the
store runs, and RESUME NEXT STATEMENT then resumes after the MOVE. The raise and the operation are ordered as
"raise, then act", but the rule describes a condition that is raised while the operation continues.

## What the fixer owes
- Model "continue after the handler" as a first-class outcome. Either grow before signalling, or have the raise
  site run the declarative and RETURN, not unwind, when the handler's RESUME is NEXT STATEMENT for a condition
  whose rule says the operation continues. That is a design question for `DESIGN-EXCEPTIONS` (or the
  exception-handling deep-dive; see `docs/COBOLNET_DESIGN.md` §0.5), and the doc is updated in the same change.
- The PERFORM … WHEN handler form of the same sentence gets its own golden.
- **Sibling sweep:** every non-fatal EC whose rule says the operation continues after the handler. EC-BOUND-SET
  (§14.9.39.4 GR30, landed by PB460 as "raised before the change"; check which ordering its rule text requires),
  EC-SIZE-* on arithmetic with ON SIZE ERROR absent, and EC-DATA-CONVERSION are the candidates.
  `NonfatalIfEnabled`'s callers are the list.
- Goldens: the repro above (positive, 2023), and the checking-off arm, which should grow silently.
