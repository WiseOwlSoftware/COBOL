# PB1114 — LANDED (its float-formal legs; row GR-14.8.2.3.3-L2.2 stays with PB1113)

## Landed 2026-09-30 — root cause and what changed
**Root cause (corrected from the note's "misclassified Text").** The callee's float formal was NOT misclassified: a
non-resident float formal crosses `Native` (`CobolArgAdapt.Num<double>`). The defect was that BOTH halves of the
§14.2.3 GR9/GR10 COMPUTE spoke fixed-point only: the activator's `CallEmitter.LandedForFormal` guard admitted
`IsClassNumericFixedPoint` formals, and the callee's `Num`/`NumValue` converting arms landed the fixed-point argument
through the float formal's description — `Digits = 0` — whose capacity reduction (`value % 10^0`) stored 0. The
note's suggested "FLOAT crossing class" was not needed; a float formal's crossing form was already right.
**Mechanism (one rule, every arm).** `CobolArgAdapt.LandFloat` — the float twin of `LandScalar` — lands the sender through
`FloatResultant` (THE one transfer into a float resultant identifier: implied TRUNCATION §14.7.4.3 rule 10, exact
one-rounding conversion of a scaled sender, §14.7.5 case 3 raise under EC-SIZE checking via the new
`FloatResultant.From…OrRaise` / `CobolSizeError.FloatTruncation`), selected by one predicate `IsFloatFormal` at every
arm that had a fixed-point landing: `LandForFormal`, `NumValue`, `TextValue` (replacing a private round-to-nearest
`ArgDouble`) and the `Num` converting view. `PicInfo.IsClassNumeric` (fixed OR float, never INDEX) replaces the
fixed-point-only guard in the emitter.
**Siblings swept and fixed in the same change (rule 4).** (1) BY VALUE float formal of a PROGRAM or FUNCTION —
refused COBOLNET0899 "value-copy carrier not yet implemented" (PB1051 flagged it: "the fixer owes both arms") — now
carried; the catalog text of `ByValueFormalCarrier` is narrowed to the METHOD arm PB1051 still owns. (2) A numeric
literal or arithmetic expression BY CONTENT into a float formal — refused COBOLNET1688 "documented refinement"
(`OoConformance.ContentNumericLiteralMismatch` / `ContentArithmeticMismatch`; PB1113's first finding) — admitted.
(3) The INVOKE channel: the binder's "fixed-point⇄float CONTENT conversion is not carried across INVOKE" refusal is
gone and `OoEmitter` lands a fixed-point / other-usage float identifier, literal-2 or expression into a float
method formal through the same `FloatResultant` (`IsFloatLanding`; same-usage floats keep the verbatim read); its
raising form is `RuntimeApi.FloatResultantStoreOrRaise`. **Left open, not this note's:** PB1113's index-formal, ANY
LENGTH and numeric-edited / national literal legs; PB1051's METHOD BY VALUE formals.
Witnesses: `conformance:2023/pb1114_call_content_float_formal`, `conformance:2002/pb1114_invoke_content_float_formal`, the
EC-SIZE-checked pair `conformance:2023/pb1114_call_float_formal_landing_checked` /
`conformance:2023/pb1114_invoke_float_formal_landing_checked` (checking ON raises EC-SIZE-TRUNCATION in the activating element
before the callee is entered; OFF lands the largest finite binary32), `CallAbiFloatLandingTests` (11 cases). Citations checked: §14.8.2.3.3 2) a); §14.2.3 9); §14.7.4.3 10); §14.7.5 4);
§14.2.2 2).

## Review finding fixed (w0930 train review, finisher 2026-09-30)
The train's reviewer confirmed that the INVOKE channel's first landing missed the third sender class: `INVOKE OBJ "TAKEN" USING
BY CONTENT BIG` with BIG `FLOAT-LONG` and an image-carried or `COMP` fixed-point formal `PIC 9(3)V99` failed to compile (Roslyn
CS0103 `_P_0`; before the cluster it was a clean bind diagnostic). **Cause (the two-arm shape):** `OoEmitter.OoStringReadOf` took its
§14.2.3 GR9 COMPUTE branch only for a FIXED-POINT sender (`IsFloat: false` on both sides), so a float sender fell to
`MoveEmitter.ConvertSource`, a MOVE store that renders the formal's profile BARE in the activating class — and is a MOVE where §14.7.5
r4 owes the EC-SIZE raise. **Fix:** the branch asks `fp.IsClassNumericFixedPoint` for the formal and `IsClassNumeric` for the sender (a
COMPUTE's sending operand may be floating-point; §14.2.3 9), §14.8.2.3.3 2) a) — both `cite.py --check`ed), and `StoreExpr` tells the
lanes apart (a Real intermediate lands through `ToScaled`, CHECKED when it raises). **Sweep:** the CALL lane (`CallEmitter.LandedForFormal` /
`CobolArgAdapt.LandForFormal`) probed correct for float senders into DISPLAY, COMP and REDEFINES formals (nested CALL, with the
unsigned-receiver absolute value); the INVOKE native, literal and expression arms probed correct; the universal INVOKE is BY REFERENCE
only (§14.9.23.3 SR6). The unprobed ALPHABET lead is DISCHARGED: a numeric ordinal above 65536 is refused under SR14 c1 (COBOLNET1906),
and a supplementary LITERAL is two national characters under D-N1 — which the standard itself states (§8.4.3.3.4 5) NOTE: "the COBOL
system treats the two halves of a surrogate pair as separate character position", DOC-A.1-188). Golden
`conformance:2023/pb1114_invoke_content_float_to_fixed_formal`.
