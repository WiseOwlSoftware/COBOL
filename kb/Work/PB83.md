# PB83 — LANDED 2026-08-18 — `COMPUTE R = 100000 / D30` under STANDARD-DECIMAL stored 0 (8.1E-25 owed)

> ⚙ **flags:** wrong-answer, silent · found 2026-08-18 landing PB69 (a 45-digit power's Dec approximation divided
> by an exact 30-digit one gave 999.99 for a ratio of ~1E15) · fixed in the same commit (DEVLOG 1301).

**Measured** (`--std 2023`, `OPTIONS. ARITHMETIC IS STANDARD-DECIMAL.`, `01 D30 PIC 9(30) VALUE
123456789012345678901234567890. 01 N PIC 9(6) VALUE 100000. 01 R PIC 9V9(30).`): `COMPUTE R = N / D30` printed
`0000000000000000000000000000000` where the exact quotient 8.10000007290000066339000603685715…E-25 lands as
0.000000000000000000000000810000. `5 / D30 * 10^30` (= 40.5000003645…) printed 4.

**Mechanism:** `CobolDec.Div` pre-scales the numerator so the integer quotient has 34–36 significant digits:
`scaleUp = 34 + digits(den) − digits(num) + 1` — up to 73 for a 1-digit numerator over a 38-digit denominator — but
multiplied by `Pow10.AsWide(Math.Min(scaleUp, 38))` (the multiplier had to fit Int128) while the result exponent
subtracted the UNCAPPED `scaleUp`. Whenever `digits(den) − digits(num) > 3` the quotient was 10^(scaleUp − 38) too
small. Every SDIDI division with a much longer denominator than numerator — every `small / large` under a standard
mode, and every native expression PB69 now routes to the SDIDI — was affected.

**Fix:** the scale is applied in two exact steps — first inside the numerator's own Int128 headroom
(`k = min(scaleUp, 38 − digits(num))`, exact), then the remainder through the 256-bit product
(`scaleUp − k = digits(den) − 3 ≤ 36`, so the second factor always fits). `CobolDecDivisionTests` pins the widest
case (1 digit over 38), the measured case, the PB69 ratio, and the exact-integer MOD/REM fast path; golden
`pb83_standard_decimal_division_prescale`.
