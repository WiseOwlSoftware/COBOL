# PB4588 — cobc 3.2.0 folds `literal ** literal` in a wrapping signed 64-bit integer

Filed 2026-11-04 from sibling S8 of the PB4569 determination (wave 20261861 a). Upstream status `unreported`: the tracker has
not been searched and nothing is posted. Evidence, outside git on one machine: `E:/COBOL-coord/scratch/op-w20261861/a/p/`
(`p1.cob`, its GnuCOBOL binary `p1g`, and the output quoted below).

## Minimal test case

Fixed reference format, `cobc -x -o fold f.cob` (re-run for this note on cobc 3.2.0, 2026-11-04):

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. FOLD.
       PROCEDURE DIVISION.
           DISPLAY "7**45   " FUNCTION ABS (7 ** 45).
           DISPLAY "2**130  " FUNCTION ABS (2 ** 130).
           STOP RUN.
```

## Environment

- `cobc (GnuCOBOL) 3.2.0`, Ubuntu package `gnucobol3 3.2-4build1`, WSL2 Ubuntu on Windows 11.
- `cobc -x -o fold f.cob` (default dialect, no `-std`).

## Observed result

```
7**45   6418094003492566503
2**130  0
```

6418094003492566503 is 7^45 mod 2^64, and 2^130 mod 2^64 is 0. The other probes of `p1.cob` agree: `ABS (10 ** 40)` shows
5047021154770878464 (the magnitude of 10^40 mod 2^64 read as signed), `ABS (2 ** 127)`, `ABS (2 ** 126)` and
`ABS ((2 ** 65) * (2 ** 65))` show 0, and `COMPUTE RM = 2 ** 130 / 2 ** 120` warns "divide by constant ZERO" and takes
ON SIZE ERROR. The run-time path with a data-item operand is exact: with `X1 PIC 9 VALUE 2` and `N PIC 999 VALUE 130`,
`ABS (2 ** N)` shows 1361129467683753853853498429727072845824, and so do `ABS (2.0 ** 130)` and `ABS (X1 ** 130)` (p1 A5, A2, A3).

## Expected result

ISO/IEC 1989:2023 §8.8.1.3 makes native evaluation of an arithmetic expression implementor-defined, and §15.4.1 says the value
returned for an equivalent expression "is an implementor-defined approximation of the value of that expression". A 64-bit wrap is
no technique and no approximation of 2^130; the same expression with a data-item operand in the same compiler gives the exact
1361129467683753853853498429727072845824. Both clauses were checked with `scripts/spec/cite.py --check` by the PB4569
determination.

## Our compiler (WiseOwl)

Today `ABS (2 ** 130)` shows 1361129467683754000000000000000000000000 (a binary64 approximation, PB4569); once PB4569 lands it
shows 1361129467683753853853498429727072845824. It is not scored against GnuCOBOL's folded 0: a differential that compares a
folded power with GnuCOBOL must not score it.

## Fix site

Not located. The determination read no cobc source; the evidence is behavioural (the wrapped values above are exactly the
64-bit residues). The fold is in cobc's compile-time evaluation of a constant `**`, not in the run-time `cob_decimal_pow`, which is
exact (`mpz_pow_ui`).

## Upstream state

`unreported`. The tracker was not searched, nothing was posted, and the repro was not run on the 3.3 development line.

## Draft issue

**Title:** cobc 3.2.0 folds a constant `literal ** literal` in a wrapping 64-bit integer: ABS (2 ** 130) displays 0

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu `gnucobol3 3.2-4build1`), Linux x86_64.

Steps: compile the program below with `cobc -x -o fold f.cob` and run it.

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. FOLD.
       PROCEDURE DIVISION.
           DISPLAY "7**45   " FUNCTION ABS (7 ** 45).
           DISPLAY "2**130  " FUNCTION ABS (2 ** 130).
           STOP RUN.
```

Observed: `7**45   6418094003492566503` and `2**130  0`. The first is 7^45 mod 2^64, the second 2^130 mod 2^64.

Expected: every digit of the power (2^130 = 1361129467683753853853498429727072845824), as the run-time
path gives when an operand is a data item (`01 X PIC 9 VALUE 2. 01 N PIC 999 VALUE 130.` and `ABS (X ** N)`), or at least a
size error; a silent wrap is wrong.
