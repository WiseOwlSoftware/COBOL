# PB4372 - The margin-R note has two uncovered shapes

**Sites:** `src/WiseOwl.Cobol.Frontend/Parsing/CobolErrorListener.cs` (`CobolErrorListener.NoteMarginRCut`, `CobolErrorListener.ReportMarginRCut`),
`src/WiseOwl.Cobol.Frontend/Common/MarginRCut.cs` (`MarginRCut`, `MarginRCut.RecurrenceThatMakesATag`, `MarginRCut.LastProgramTextPosition`,
`MarginRCut.LastCutPosition`), `src/WiseOwl.Cobol.Frontend/Preprocessor/ReferenceFormatMap.cs` (`ReferenceFormatMap` constructor,
`ReferenceFormatMap.CutOf`), `src/WiseOwl.Cobol.Editions/Diagnostics/DiagnosticCatalog.cs` (`DiagnosticCatalog.ProgramTextPastMarginR`, summary only).
PB2555 landed (bb6b3ab18), so the file is on main.

The note's owed shape is "the parse fails on a line whose predecessor carried non-blank text past margin R". `NoteMarginRCut` looks only at the physical line of the token before the offending one. Two shapes escape or misfire:

1. A statement written only past margin R, on a line whose program-text area is blank, has no token to anchor, so no note is given. The implementer recorded it in PB2555 as "Not covered, deliberately" with no owner decision, which CLAUDE.md rule 3 forbids (the complete feature, deferral only by explicit owner decision).
2. A lone tag-shaped word (identification area) on a minority of lines is indistinguishable from a cut word and fires the note.

Fix: anchor on the preceding non-blank physical line (not the preceding token's line), and tell a tag column from a cut by the same line-population rule `ReferenceFormatMap` uses. If the owner wants shape 1 left out, that is an owner decision and gets recorded as one.

## 2026-11-01 - LANDED (wave 20261808, group G)

Re-probe on the Debug build (probe files rebuilt from the layouts above; `E:/COBOL-coord/scratch/w20261808g/p/`): shape 1 gave only
`COBOL5506 cannot parse construct near 'STOP'`, no note; shape 2 (`DISPLAY WS-MSG.` with `TAG1` at position 73, then a stray `END-IF.`)
gave COBOL5788 "the statement that line began may have continued past it" beside the unrelated COBOL0306.

**Shape 1 (fixed at its root).** The listener asked about the line of the token BEFORE the offending one only. It now also asks, for each
resultant line strictly between the two tokens, whether that physical line was cut (`CobolErrorListener.NoteMarginRCut`). The cut records
whether the line's program-text area holds anything (`MarginRCut.HoldsProgramText`), and the message for a line that holds none says it
"has no program text" and that the line "reads as blank", instead of "it ends at position 72".

**Shape 2 (the rule changed, the remainder is irreducible).** The old rule nulled tag-shaped cuts only when MORE THAN HALF of the code
lines carried one. A file that tags a minority of its lines (a revision mark on the lines an edit touched) kept firing. The rule is now
recurrence: a tag-shaped word (one word of at most eight characters) on two or more lines of a file is a column convention, a tagged blank
line counts, and every such cut of the file is dropped (`MarginRCut.RecurrenceThatMakesATag`, `ReferenceFormatMap`'s constructor). ONE
tag-shaped word in a file stays a possible cut: nothing in a single line tells `REV0042` from the one-word tail of a statement (`END-IF`
alone is tag-shaped too), and a missing note on a real cut is the worse error for a warning that says "may". The cost of the rule is a
file whose only overflows are one-word tails on two lines or more: it hears no note. Pinned by `TagsOnAMinorityOfLines_AreNotACut` and
`ALoneTagShapedWord_IsStillNamedAsAPossibleCut`.

**Found in the same files (I9).** (a) `MarginRCut.Margin` is the PHYSICAL column but doubled as the 1-based POSITION of margin R in the
message, so a line holding a tab named a margin other than 72 (PB2555 review R1-2): `LastProgramTextPosition` is now its own member,
set from `FixedFormLine.MarginR`, and `LastCutPosition` counts characters (`CharacterPositions.Count`), not UTF-16 units. PB4373
landed the same fix on main first; the merge took its `Column` and tab remark and kept this note's `HoldsProgramText`, and the
no-program-text message form states the tab remark too (`ALineWithNoProgramTextHoldingATab_StatesMarginRAtPosition72`). (b)
`ACommentLinePastMarginR_IsNotACut` could not fail (R1-3): the comment line now stands between the two tokens.

**Witnesses.** `unit:MarginRCutNoteTests` (16 cases), `conformance:cases/A.1-Implementor-defined-language-element-list/pb4372-statement-only-past-margin-r`.

**Review R1-1 (omitted lines).** The between-lines arm asks only of lines whose program-text area is blank. A tokenless line that holds program text was omitted by a later stage (a false `>>IF` branch, ISO 7.3.16.4 3); a debugging line without debugging mode), so it is no cut's effect. Residual: a line with text ONLY past margin R inside an omitted branch is still asked about, because no stage tells the listener which blank lines were omitted.
