# PB522

## Mechanism — data-description-entry-p3
DataItem.GroupUsage is absent from BOTH of the two helpers that copy a data description onto another entry -- DataBinder.CopyEntryDescription (the shared GR-1 body of ExpandType and ExpandSameAs) and DataBinder.CloneItem (the per-node deep clone). Both copy Pic, Pending, RawValue, Justified, BlankWhenZero, OwnUsage, OwnSign, TypeName and StrongType; neither copies GroupUsage, the one field that makes an item a bit group or a national group. Consequence chain: (1) a subject declared `TYPE t` or `SAME AS d` where t/d is a bit or national group is bound as an ORDINARY alphanumeric group -- wrong class, wrong category, wrong LENGTH; (2) an explicit GROUP-USAGE clause on a group NESTED inside a TYPEDEF is lost when the template is cloned; and (3) because the parent is no longer a bit/national group, the 13.16.4 GR1/GR2 implication that ought to run over its subordinate groups has a false antecedent and never fires, so a whole subtree silently changes category. The implication itself (DataBinder.ResolveIndexItems) is correct -- it is the antecedent that is destroyed upstream. Tell-tale that the loss is narrow and mechanical: CopyEntryDescription DOES copy DataItem.Pending, so the 13.18.60.3 SR12 leaf screens still fire through a TYPE reference while the group's own category is gone.

### Expected, from the standard
13.18.57.4 GR1 (--check OK): 'The effect of the TYPE clause is as though the data description identified by type-name-1 had been coded in place of the TYPE clause, excluding the level-number, name, alignment, and the GLOBAL, SELECT WHEN, and TYPEDEF clauses specified for type-name-1' -- GROUP-USAGE is NOT in that exclusion list, so it is carried. 13.18.49.4 GR1 (--check OK) is the same for SAME AS, excluding only level-number, name, CONSTANT RECORD, EXTERNAL, GLOBAL, REDEFINES and SELECT WHEN; GR4 of the same clause even propagates a GROUP-USAGE from data-name-1's SUPERORDINATE, so the clause is plainly meant to travel. 8.5.2.10 item 3 / 8.5.2.5 item 3 (--check OK): a group 'explicitly or implicitly described with a GROUP-USAGE clause with the NATIONAL [BIT] phrase' is of category national [boolean]. 13.16.4 GR1/GR2 (--check OK) then imply the clause for every subordinate group. 15.50.4 r1/r2/r3 (--check OK) fix the observable: a bit group's LENGTH is in boolean positions, a national group's in national character positions, everything else in alphanumeric character positions.
So (A) LEN-VIATYPE=4, LEN-T1=4; (B) LEN-VIABIT=3, LEN-BT1=3; (C) LEN-DST=4, LEN-SG-DST=4, LEN-BDST=5, LEN-BG-DST=5; (D) LEN-NG-TEMPLATE-COPY=3. In every case the TYPE / SAME AS copy must measure exactly what its byte-identical inline spelling measures.

### Observed
Read: CopyEntryDescription (DataBinder.cs ~L1693) assigns to.Pic, to.Pending, to.RawValue, to.Justified, to.BlankWhenZero, to.Synchronized (SAME AS only), to.OwnUsage, to.OwnSign, to.TypeName, to.StrongType -- GroupUsage appears nowhere in the method. CloneItem (~L1722) builds the clone's initializer with Pic, Pending, OwnSign, OwnUsage, RawValue, Occurs, OccursSpec, RedefinesTargetName, Justified, BlankWhenZero, TypeRefName, SameAsName -- again no GroupUsage. Measured: the eight LENGTH values above, each against a byte-identical inline control in the same program. The category loss is not merely a LENGTH artefact -- GroupUsage is what DataItem.AsIfPic, DataItem.IsAsIfElementary, BitLayout.IsBitItem, PhysicalModel and PlaceRenderer all key on, so the copy also loses the elementary-item treatment a bit/national group has in MOVE, comparison, INSPECT and reference modification (13.18.29.4 GR1b/GR2b), and under BIT it loses the 8.5.1.6.3 bit packing. The compiler is silent throughout.

### Code site
src/Cobol.Net.Compiler/Binding/DataBinder.cs#CopyEntryDescription (~L1693) and #CloneItem (~L1722); the correct downstream consumer is #ResolveIndexItems (~L3299, the GR1/GR2 implication) and src/Cobol.Net.Compiler/Binding/Model/DataItem.cs#GroupUsage / #AsIfPic. A fix belongs in the ONE clause-copy funnel (both helpers), not at the reference sites, and should come with a drift test that asserts every description-bearing DataItem field is either copied or listed in an explicit GR-1 exclusion set -- the field-by-field hand list is exactly the shape that lost this clause.
