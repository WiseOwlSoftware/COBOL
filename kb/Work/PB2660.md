# PB2660 — OPEN — two run units on one keyed file under ALL OTHER lose each other's updates

Found 2026-10-08 by the cobol-adjudicator drafting PB1636 determinations (lead **L2** of
`E:\COBOL-coord\scratch\w1040-drv\drafts.md`, pin `ea20c28e3`). Filed by the wave 1040 group U implementer, who
re-ran the probe on `853f38cab` and extended it to INDEXED. ⛔ **NOTE ONLY: no fix was attempted.** The fix is a
design-level change (record-level cross-process I/O for the keyed organizations) for the fix lane to plan.

## Repro (re-run on 853f38cab, two processes)

`E:\COBOL-coord\scratch\w1040u\probes\lka.cob` + `lkb.cob` (RELATIVE, RANDOM, `SHARING WITH ALL OTHER`,
`LOCK MODE IS MANUAL`), driven by `l2.ps1`: A writes records 1 `AAAA` and 2 `BBBB`, re-opens I-O, `READ … WITH LOCK`
record 1, waits 6 s (`CONTINUE AFTER 6 SECONDS`), re-reads record 1 and CLOSEs. B starts 3 s after A.

```
B OPEN FS=00
B READ-LOCK 1 FS=00 REC=AAAA        <- §9.1.13.8 1) requires 51: A holds the lock
B REWRITE 1 FS=00
B WRITE 3 FS=00
A OPEN FS=00
A LOCKED 1 FS=00
A REREAD 1 FS=00 REC=AAAA           <- B's REWRITE is invisible to A
FILE BYTES: ...AAAABBBB             <- after A's CLOSE: B's ZZZZ and record 3 CCCC are gone
```

`ixa.cob` + `ixb.cob` (the same programs as INDEXED, `RECORD KEY IS F-KEY PIC X(4)`, run by `ix.ps1`) give the
identical result: `B READ-LOCK 1 FS=00 REC=0001AAAA`, REWRITE `00`, WRITE `00`, and the file holds only
`AAAA`,`BBBB` after A's CLOSE. Both run units were told `'00'` for every statement.

## Rule

- §9.1.16 (`cite.py --check 9.1.16` → OK): *"While locked by a given file connector, a record is not accessible to
  another file connector in the same or a different run unit, except by the execution of a READ statement with the
  IGNORING LOCK phrase."*
- §9.1.13.8 1) (OK 1)): *"I-O status = 51. The input-output statement is unsuccessful due to an attempt to access a
  record that is currently locked by another file connector."*
- §9.1.15 3) (OK 3)): *"The sharing with all other mode allows concurrent access to a physical file through other file
  connectors specifying input, I-O, or extend mode, subject to any further restrictions that apply. Record locks are in
  effect."* and (OK) *"Multiple paths of access may exist in the same runtime element, contained elements, separate
  runtime elements within the same run unit, or runtime elements in different run units."*
- §14.9.51.4 GR16 (OK 16)): WRITE RETRY exists for *"files opened for file sharing for the case where resources needed
  to write a record are locked by another run unit"*.

Table 19 legitimately admits a second `ALL OTHER` I-O opener in another run unit, so B's OPEN `'00'` is right; what
is wrong is everything after it.

## Structural cause

1. **Whole-store snapshot.** A keyed connector reads the whole physical file at OPEN and rewrites it whole at CLOSE
   (`src/Cobol.Net.Runtime/IO/RelativeConnector.cs#Load` → `RecordFraming.ReadStore`, l.551–561; the CLOSE persist
   `RecordFraming.WriteStore`, l.571; `src/Cobol.Net.Runtime/IO/IndexedConnector.cs#Load`, l.921–931, persist l.308;
   `src/Cobol.Net.Runtime/IO/RecordFraming.cs#ReadStore` l.243 / `#WriteStore` l.189). Between OPEN and CLOSE each run
   unit works on its own in-memory copy, so the last CLOSE wins and every other run unit's updates are erased.
2. **In-process lock table.** Record locks live in `src/Cobol.Net.Runtime/IO/Sharing/PhysicalFileTable.cs#LockRecord`
   (l.92) and `#IsLockedByOther` (l.108), a per-process dictionary keyed by host path. Another process never sees them.
3. kb/Work PB771 (landed) gave the keyed organizations a host FILE lock, which closes the NO OTHER and READ ONLY
   halves; it cannot close ALL OTHER, which must admit the second writer.

DOC-A.1-109's premise that "every record lock is held by a connector of the executing run unit" is false here, and the
held draft for GR-12.4.5.9.4-2 (drafts.md) depends on this note's outcome.

## Target (for the fix lane to plan — a design change, not a patch)

Record-level cross-process I/O for RELATIVE and INDEXED under a sharing mode that admits another writer
(`FileLockPosture.AdmitsAnotherWriter`): each record operation reads and writes the physical file in place (no
whole-store snapshot), and record locks are host byte-range locks on the record's frame (or an equivalent
cross-process lock table) so another run unit's access receives `'51'`. The sequential organization's unbuffered
ALL OTHER path (kb/Work PB1587) is the precedent for the visibility half. It needs a design section in
`docs/rearchitecture/DESIGN-runtime-library.md` §2.2 (IO) before implementation; the alternative, declaring
cross-run-unit record locking unsupported, would make GR-12.4.5.9.4-2 observable and still leaves the lost-update
defect, so it is not a fix.
