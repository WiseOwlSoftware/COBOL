## Finding — `function-identifier` (rejects-legal-source; rows none (side lead))

**Mechanism.** LEAD, found while probing SR11's integer positions and not owned by a row of this subject: the GO TO Format 2 DEPENDING ON operand refuses every function-identifier at parse (COBOL0001), including an integer function. This is the PB86 PERFORM TIMES shape (a missing functionCall grammar arm) in a sibling statement.

**Repro.** out/probe/function-identifier/r6_sr11_goto_int.cob: GO TO P1 P2 DEPENDING ON FUNCTION INTEGER(2.5) -> COBOL0001 unexpected 'FUNCTION'.

**Expected from the spec.** §14.9.17.3 SR1 requires identifier-1 to 'reference a numeric elementary data item that is an integer'. §8.4.3.1.2 Format 1 makes a function-identifier an identifier, and §8.4.3.2.4 GR1 has it reference a temporary elementary item. So an integer function is legal: this program transfers to P2 and displays P2. A NUMERIC function there stays barred by SR11. Needs a --check of §14.9.17.3 SR1 by the registrar before filing.

**Observed / reasoning.** The grammar's GO TO DEPENDING operand admits a dataReference only (it is parsed like PERFORM TIMES before PB86). This is not adjudicated against a rule of this subject; it is filed as a lead for the registrar.

**Code site.** src/Cobol.Net.Frontend/Grammar/Core/CobolControlFlow.g4 (goToStatement DEPENDING operand)

Add the functionCall arm to goToStatement's DEPENDING operand (integer identifier); sweep every grammar slot that names an integer identifier for the same missing arm (the PB86 sweep evidently stopped at PERFORM).

## Landed (wave 1021 C, 2026-10-05)

- **Re-probed first** on this worktree's build of `17924fbb4`: `GO TO P1 P2 DEPENDING ON FUNCTION INTEGER(2.5)` →
  `COBOL0001: unexpected 'FUNCTION'` (reproduced). After the fix it prints `P2`.
- **Rule** (each `cite.py --check` OK): §14.9.17.3 SR1 "Identifier-1 shall reference a numeric elementary data item
  that is an integer"; §8.4.3.2.4 GR1 "A function-identifier references a temporary data item whose value is
  determined when the function is referenced at runtime"; §8.4.3.2.3 SR11 "A numeric function shall not be specified
  where an integer operand is required".
- **Fix.** `CobolControlFlow.g4#goToStatement` Format 2 takes `(functionCall | inlineMethodInvocation | dataReference)`
  (the per-site pairing `InlineMethodInvocationOperandDriftTests` holds); `GoToFormats.Of` keys Format 2 on the
  `DEPENDING` keyword, the one child every operand alternative shares. `ControlFlowBinder.BindGoTo` binds the
  alternative written. The ONE operand-class screen (`OperandClassScreen.Screen(BoundOperand)`) no longer refuses a
  function-identifier as "not a data item": it classes the temporary item by its RESULT through the ONE integer
  classifier (`IntrinsicResultType.IsIntegerOperand`) and the ONE category reader, so an integer function meets SR1
  and a numeric one draws COBOLNET2324 naming SR11.
- **Sibling sweep** (every "identifier-n shall ... integer" syntax rule in clause 14, by awk over `specs/ISO_COBOL.md`):
  the other SENDING integer slot, §14.9.51.3 SR14 WRITE ... ADVANCING identifier-2 (`CobolIO.g4#writeBeforeAfter`),
  had the same missing arm and is fixed the same way (`SequentialIoBinder.BindAdvancing` / `ScreenAdvancingCount`
  route every identifier format to the screen). PERFORM ... TIMES (PB86) and the STOP/GOBACK status already admitted a
  function; SET UP/DOWN BY and the VARYING FROM/BY slots are arithmetic-expression/valueOperand slots that already
  do; SEARCH VARYING, UNSTRING COUNT/TALLYING, STRING/UNSTRING POINTER and the SET Format-1 receiver are RECEIVING
  positions (§8.4.3.2.3 SR1); the ACCEPT/DISPLAY screen LINE/COLUMN integers are in the declined screen module.
- **Goldens.** `conformance:85/pb1421_goto_depending_function_identifier` (INTEGER, folded LENGTH, an out-of-range
  value that falls through per §14.9.17.4 GR2, and WRITE ADVANCING FUNCTION INTEGER(M) LINES);
  `conformance:negative/pb1421-goto-depending-numeric-function` (SQRT(4) → COBOLNET2324);
  `unit:OperandClassScreenDriftTests.SendingRow_ClassesAFunctionIdentifierByItsResult` (both sending rows × integer,
  folded, numeric and alphanumeric functions). `DESIGN-binder-bound-tree.md` §3.6 states the function arm.
- **Train 1021 review C-3 (fixed in the cluster).** A FOLDED function value answered the integer classifier by its
  TEXT: HIGHEST-ALGEBRAIC / LOWEST-ALGEBRAIC of a numeric-edited item is a NUMERIC function (§15.43.1 / §15.58.1,
  "Alphanumeric | Numeric"; PIC ZZ9 is an Alphanumeric argument by §15.3 r2) and folds to the integral `999` / `0`,
  so `GO TO … DEPENDING ON FUNCTION HIGHEST-ALGEBRAIC(E)`, `WRITE … ADVANCING` and `PERFORM … TIMES` (pre-existing,
  PB86) admitted it against §8.4.3.2.3 SR11. The fold now carries its §15.2 type (`BoundNumLiteral.FunctionType`,
  stamped by `IntrinsicBinder.Folded` through the ONE `IntrinsicResultType.Resolve`), and
  `IntrinsicResultType.IsIntegerOperand` answers from it. Goldens
  `conformance:negative/pb1421-goto-depending-folded-numeric-function` (COBOLNET2324) and
  `conformance:negative/pb1421-perform-times-folded-numeric-function` (COBOLNET1646).
