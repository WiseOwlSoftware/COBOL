# PB384 — LANDED — a misfiled determination, the citation it propagated, and the green check that never looked

**Rows:** `DOC-A.1-209`, `DOC-A.1-22`, `DOC-A.1-188`. Found independently by the round-2 golden writers
`misc-p1` (row 22) and `misc-p2` (rows 209 and 188) while deriving witnesses; each row's writer reached
`defect-suspected` because *no golden can close a row whose determination answers a different question*.
CONFORMANCE.md §7's own preamble names this the worse failure: *"an undocumented determination and a wrongly-
documented one are both non-conformance, and the second is worse."*

## 1. `DOC-A.1-209` carried the USAGE BIT determination

A.1 item 209 is **"USAGE DISPLAY (size and representation of characters) … (13.18.60, USAGE clause, General
rule 7)"** (`specs/ISO_COBOL.md:34654`). The §7 row's Element cell read *"**USAGE BIT clause — alignment and
representation of data**, §13.18.60.4 GR5 + §8.5.1.6.3"* and its code-location was `BitLayout.cs#BitLayout`.
Both halves answer **GR5**, a real clause about a different question — the failure mode
`feedback_a_real_clause_can_answer_a_different_question` names, and it is why `cite.py --check` gave no
protection: every sentence in the row was true.

**Repaired.** The row now states GR7's own determination — **one byte per character position** — and all three
of GR7's obligations are MEASURED by `tests/conformance/2023/l1_usage_display_character_size` rather than
asserted: uniform size (`UNI=1 5 9`), the constraint against the national size (`LEQN=1 2`, and 1 ≤ 2 is what
makes the choice constrained rather than free), character-boundary alignment generating no filler (`ALIGN=5`),
the position/byte identity of `FUNCTION LENGTH` vs `FUNCTION BYTE-LENGTH` (`POS=5 5`), and the numeric-DISPLAY
sign grid (`NUM=5 5 6` — §13.18.52.4 GR5 a vs GR6 a). The row also now states that COBOL.NET provides **no**
option to vary the size per compilation unit, which item 209 permits and the row never addressed.

**The USAGE BIT determination is real content and was NOT deleted with the misfiling.** Annex A.1 has no USAGE
BIT item at all — it runs 208 (COMPUTATIONAL, GR6) straight to 209 (DISPLAY, GR7), and §8.5.1.6.3 is
cross-referenced only by item 195 (SYNCHRONIZED, whose row carries only the SYNCHRONIZED half). So it moved
verbatim to **CONFORMANCE.md §3**, the §4.2.6 behavior-determination list, where a determination with no A.1
number belongs.

## 2. The wrong item number propagated into a landed golden

`tests/conformance/2002/l1_byte_length_implicit_filler.cob:51` cited *"COBOL.NET pins 8 (CONFORMANCE.md
§4.2.16; **Annex A.1 item 209**)"* for the bits-per-byte determination. That is **item 12**, *"Byte (number of
bits in) … (8.1.2, Computer's coded character set)"*. The number was inherited from the misfiled row — CLAUDE.md
rule 1's exact failure mode, and one the mechanical `--check` cannot see, because **A.1 item numbers are not
§-clauses**. Repaired in place, with the inheritance named so the next reader knows where it came from. Swept:
`grep -rn "A.1 item 209"` over `tests/ src/ docs/` returns only this site, the repaired row itself, and one
DATED forensic artifact (`docs/rearchitecture/pb59-mechanism-map-2026-08-09.md:205`) that records the tree as it
stood on 2026-08-09 and is deliberately left as the snapshot it is.

## 3. `DOC-A.1-22` documented the branch the STANDARD decides

§15.16.4 r2 has two sentences and only the second is an implementor obligation:

> *"If more than one character has the same position in the national program collating sequence, the character
> returned is the first character defined for that character position. **If the order of multiple characters
> having the same position is undefined, the implementor shall define which of those multiple characters is
> returned**; for a given implementation, collating sequence, and ordinal position, every invocation of the
> CHAR-NATIONAL function shall return the same character."*

Item 22's own title is that second sentence verbatim. The row documented the FIRST — the `ALSO` order, which
§12.3.7.4 GR7 k)6 fixes for the implementor — and named `NationalCollation.CharAt`, the ALSO reader, which
cannot reach the undefined-order branch at all. The existing golden
`2002/l1_char_national_also_positions` says in its own header that it therefore does **not** close item 22, and
it was right: nothing could, because the row asked the wrong question.

**Repaired**, and the branch turns out to be reachable through a different class. An `ALPHABET … FOR NATIONAL IS
LOCALE` sequence is an ALGORITHM, not a written order, so characters the locale collates equally share one
ordinal position with no order among them — r2's second branch exactly. COBOL.NET returns **the lowest-coded
member of the rank**: `LocaleCollation.OrderVector.FirstOfRank`, whose own field comment reads *"position → the
LOWEST code unit collating there"*, materialized once per collator so the third sentence's stability is
structural rather than incidental. `tests/conformance/2002/l1_char_national_locale_tie` measures both sentences
(`TIE1=000001`, `TIE2=000001` — position 1 is the completely-ignorable rank and its lowest-coded member is
U+0000). Determination **L7** under the locale facility states the position model this refines; it was never
connected to item 22, which is why the row and the code could disagree without anything noticing.

## 4. `DOC-A.1-188` denied UCS-4 the collating sequence Table 6 gives it

The row said *"UCS-4 and UTF-8 name **coded character sets only** (GR7 g/h + Table 6 — no collating sequence)"*.
**Table 6** (`specs/ISO_COBOL.md`, *Relationship of alphabet-name to coded character set and collating
sequence*) gives row `UCS-4` a **Y in both columns**, and GR7 f says outright *"The collating sequence
referenced by the UCS-4 phrase shall be defined by the order in which characters appear in ISO/IEC 10646."* It
is **UTF-8 and UTF-16** whose collating-sequence column is empty.

**Documentation only — the COMPILER was right all along.** `src/Cobol.Net.Compiler/Binding/CollatingModel.cs`
models UCS-4 as both (and explains why the appearance order IS code-unit order on the one-code-unit-per-position
substrate) and sets `HasCollatingSequence` false for exactly UTF-8 and UTF-16. The row is now the same statement
as the code.

## 5. The audit that should have caught all of this printed `ok` — REPAIRED

`scripts/spec/audit_annex_a1.py` exists precisely to catch a row filed under the wrong number, and its own
docstring records it doing so on its first run (a §15.3.3.2 determination filed as item 87). It reported
`ok DOC-A.1-209 USAGE DISPLAY (size and representation of characters)` for a row whose entire body was USAGE
BIT, every run, from the day that row landed.

**Mechanism, measured:** `corresponds()` accepted a row on *"at least two shared significant words"*. The
misfiled row shared `usage` and `representation` with item 209 — and those are near-universal in A.1's own
headers (`character` appears in 26 subjects, `value` 23, `representation` 16, `usage` 14), so an **absolute**
threshold measures vocabulary, not identity, and can never separate siblings inside one A.1 family. A green
check that never looked at what it was checking (`feedback_green_gates_arent_evidence`).

**The fix is relative, with no tuned constant** (`feedback_model_the_rule_shape_not_one_case`): a row must fit
the item it is filed under **at least as well as it fits every other A.1 item**. The misfiling scores 2 against
item 209 and **3** against each of 205 / 208 / 210 / 211 / 215 — that is the finding. Measured over all 47 §7
rows: **zero** correctly filed rows are flagged, so the rule adds no noise, and it generalizes without an edit
the next time a determination lands under a sibling's number. A threshold-tuning alternative was measured and
rejected: no document-frequency cutoff separates the misfiling (best shared word df 14) from the correct
DISPLAY row (best shared word df 9) with any margin worth trusting. `--self-test` gained a case that replays
the misfiling verbatim, so the new arm is proven able to fail for its own reason.

## What it cost, and the drift test

Three A.1 obligations sat undischargeable behind wrong subjects; three round-2 witnesses were written, validated
green, and then withheld because their rows asked different questions; and one wrong item number reached a
landed golden's comment. Rows 209 and 22 close in this change set on their re-derived witnesses; 188 was already
closed and is now closed on a statement that matches its code. The relative-fit rule IS the drift test — it runs
in `--check` on every build through `AnnexA1RegisterDriftTests`.
