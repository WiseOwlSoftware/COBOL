# PB4149 — the partition share check names a false cause when a partition class is missing

**Sites:**
- `tests/_shared/TestPartitioning.cs#TestPartitionAudit.AuditRowSource` (check ③, the share loop)
- `docs/rearchitecture/DESIGN-test-build-ci.md` section 3.11 ("How many partitions")

**R1-1 (the defect).** Check ③ computes `Share(whole.Count, counts.Count)`, where `counts.Count` is the number of
concrete partition classes the audit found. Every sliced member divides by the declared `Partitions` constant. When a
partition class is deleted (or a slot is written twice), the slices still use the declared count, so every surviving
partition holds `n/declared` rows, which is outside `n/found`: ③ flags every survivor and blames the sliced member's
stride. Check ④ reports the real effect (one slot's rows NEVER RUN), but its message is buried under the false ones.

**Fix.** Compare the classes found with the declared count first: name each slot in `0..declared-1` that has no class and
each slot that has two, then compute the share at `declared`. Pin it with a Unit fact that plants a missing slot and
asserts the one true message. Sweep the other family audits for the same found-versus-declared mix.

**R1-2 (decided here; record it in section 3.11).** PB4146's note asked for a drift test that no partition's MEASURED
time exceeds the others by a stated factor. The branch guards the row-count share instead, and that is the right shape:
a stopwatch ceiling in a test is forbidden (PB1590; the owner's correction of 2026-09-25), the shared timings store is
not present on every host or in CI's merge group, and the stride interleaves the manifest's rows, so a row share is an
even share of cost unless the slicing itself is broken, which is what ③ detects. Write that reason into section 3.11
beside the "generated classes" determination, in the same change as the fix.
