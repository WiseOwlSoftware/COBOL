# PB870 — OPEN — two rows whose edition band disagrees with the construct registry

Source: the `PB356` implementer report, §13 ("Two further observations that are NOT defects"). PB356 deliberately
did not re-adjudicate rows it had not tested — the right call, and the reason this is an ANALYSIS note rather
than a verdict change.

## The rows, as measured on this tree

```
GR-14.9.41.4-11 | CONFORMS | OK | editions 2014,2023 | test-ref conformance:2023/l1_start_first_last_relative
GR-14.9.41.4-12 | CONFORMS | OK | editions 2014,2023 | test-ref conformance:2023/l1_start_first_last_relative
```

Both are CONFORMS, so nothing is mis-stated about the COMPILER; what may be mis-stated is the EDITION BAND, and
a band that is too narrow is how an edition-gate sweep later "discovers" a regression that is really a metadata
error.

## What to check before changing anything

* `constructs.json`'s `start-first-last-2002` row — if the construct is admitted from 2002, the rule rows that
  describe its behaviour cannot be 2014-only.
* The INDEXED siblings PB356 widened in the same clause: the two sets must agree or the difference must be
  stated (a rule may genuinely have arrived later for one organization).
* `docs/VERSION_CHANGE_REFERENCE.md`'s START rows.

## Why it is worth a note rather than a silent fix

`feedback_a_dead_lookup_is_also_unverified`: a band nothing enforces has never been contradicted. Widening it
without re-deriving it would be the same conservative guess in the other direction.

## Sibling sweep whoever takes it owes

* A sweep of every `editions:` band in the inventory against `constructs.json`'s edition for the same construct —
  that comparison is mechanical and belongs in a drift test, not in a one-off read.
