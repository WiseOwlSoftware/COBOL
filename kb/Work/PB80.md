# PB80 — LANDED 2026-08-18 — `MOVE BODO TO OUT` over a BASED occurs-depending group copied the MAXIMUM, not data-name-1's extent

> ⚙ **flags:** wrong-answer, silent · found 2026-08-18 landing PB61 (the LENGTH r4a based-entry leg); owns the
> based half of `RV-15.50.4-4` / `RV-15.14.4-2` leg (a), recorded on those rows' PB61 verdicts.

**Measured repro** (`--std 2023`, `scratchpad/sr6/bs2.cob`), NN = 2, occurrences 1..3 filled "ccc"/"ddd"/"eee":
```
       01 WODO.  05 WF1 PIC X(2).  05 WT OCCURS 1 TO 5 DEPENDING ON NN PIC X(3).      -> W:ABcccddd
       01 BODO BASED.  05 BF1 PIC X(2).  05 BT OCCURS 1 TO 5 DEPENDING ON NN PIC X(3). -> B:ABcccdddeee   (WRONG)
       COMPUTE L = FUNCTION LENGTH(BODO)   -> NotImplementedCobolFeatureException (the named PB61 loud stage)
```
§13.18.38.4 GR8a: "If the data item referenced by data-name-1 is outside the group, only that part of the table
area that is specified by the value of the data item referenced by data-name-1 at the start of the operation
will be used." The ordinary group is sliced (2 occurrences); the BASED one, after ALLOCATE, sends its full
maximum image.

**Mechanism:** `ReferenceResolver.PlaceForItem` — a BASED root is forced to a `RedefinesTier.StringCanonical`
class (`DataBinder.Ptr.cs`, `ForceStringCanonical(root, "BASED item")`), and the resolver's class-tier branch
returns a `RedefViewPlace` BEFORE the `OdoModel.WrapGroup` step that wraps an occurs-depending group operand as an
`OdoGroupPlace`. Nothing downstream (MoveEmitter's GR8 sending slice, `PlaceRenderer.SendingImage`,
`IntrinsicBinder.VariableLengthGroupSum`'s r4b term) therefore sees the ODO. The same branch serves any
string-canonical record — a REDEFINES-class record holding an ODO table has the same hole; measure it.

**Spec for the LENGTH half:** §15.50.4 r4a / §15.14.4 r2a — "if argument-1 is a based entry not associated with
actual data or is a type declaration, the length of argument-1 is determined in accordance with the rules of the
OCCURS clause for a receiving data item" (GR8b: "the maximum length of the group") — so an UNASSOCIATED based
group answers the MAXIMUM, an associated one (r4b, sending) data-name-1's current extent: a RUNTIME test of the
implicit data-address pointer (`__addr_X` null?) selecting between the two.

**Landed (2026-08-18, DEVLOG 1308):** ONE wrap rule — `ReferenceResolver.WrapIfOdoGroup`, applied to the class-tier
`RedefViewPlace` and the struct `MemberPlace` alike (`OdoModel.WrapGroup` takes any `Place`); ONE image reader —
`PlaceRenderer.GroupImage` (a struct's `AsImage()`, a window's `Read`, an ODO wrapper's inner) — used by
`SendingImage`, `ReceiveInto` (which now stores through `WriteGroupImage`), `WriteGroupImage`'s ODO arm, the
group ref-mod channel and CALL's boundary read; the LENGTH/BYTE-LENGTH ODO term carries `BoundOdoExtent.BasedAddress`
so an UNASSOCIATED based entry answers r4a's maximum through the runtime's null-pointer test (`RuntimeApi.PtrIsNull` —
the null pointer is the `ManagedPointer.Null` singleton, a bare `is null` was always false), before data-name-1
is read. Measured (golden `pb80_based_odo_group`, the WORKING-STORAGE twin as the control on every row): LENGTH
17 unassociated / 8 associated / 17 after `SET ADDRESS OF BODO TO NULL`; MOVE BODO TO OUT = ABcccddd; a MOVE into
BODO writes only the current part (BT(3) keeps "eee"); `IF BODO = "XYZ12345"` compares the current part; BODO(2:4)
= "YZ12"; NN = 3 sends 11 characters. `SET ADDRESS OF … TO NULL` (SR19) was itself a parse error — [[PB89]],
landed in the same commit. Verdicts RV-15.50.4-4, RV-15.14.4-2 (PARTIAL → CONFORMS), GR-13.18.38.4-8, SR-14.9.39.3-19
→ CONFORMS (GAP 4019 → 4015). A REDEFINES-class ODO group cannot be declared (§13.18.44 forbids redefining a
variable-size item), so BASED is the only class-tier shape the rule reaches.

**Fix shape (as designed):** wrap the class-tier group place too — `OdoGroupPlace(Inner: RedefViewPlace …)` — and teach the
two consumers that assume a struct inner (`PlaceRenderer.SendingImage` uses `.AsImage()`; `ReceiveInto`) the
string-backed form; then `VariableLengthGroupSum` gets its ODO term from the wrapped place as for any group, with
the r4a association test as a `CobolPtr` null check around the depending read (a null data-address pointer
must select the maximum BEFORE any subordinate is dereferenced — `CobolPtr.Deref` traps). Goldens: the MOVE slice
above (both directions, GR8a and GR8b), LENGTH/BYTE-LENGTH before and after ALLOCATE.
