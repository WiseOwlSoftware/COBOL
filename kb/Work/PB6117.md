# PB6117 - AssignProcessToJobObject fails intermittently for a live test child

**Observed.** `ArchReviewFleetDriftTests.TheWorkflow_DryRunDrivesEveryArm` failed in 17 s with
`System.ComponentModel.Win32Exception : AssignProcessToJobObject failed for process 44404`, thrown by
`KillOnCloseJob.Assign` (`tests/_shared/HostBoundChildren.cs:82`) from `HostBoundChildren.Bind`, from
`ProcessObserver.Observe` (`ProcessObserver.cs:170`). The branch changed only the 1985 Markdown, a Python lint, its
selftest, a ledger and notes: nothing the test reads or runs. The other 224 RepoDrift tests passed. Three of account 1's
gates held the other slots at the time (host under load).

**Why it cannot be classified yet.** `Assign` passes the error code to `Win32Exception(int, string)`, whose message replaces
the system text, so the log shows neither the code nor its meaning. Candidates: ERROR_ACCESS_DENIED (5) when the child is
already in a job that forbids nesting or breakaway; a child in mid-exit, whose `HasExited` still reads false; a handle
race in `ProcessObserver.Observe` between `Start` and `Bind`.

**Fix.** Put the code and its system text in the message (`new Win32Exception(error).Message`), then classify the next
occurrence and fix the cause (CLAUDE.md rule 4). The proper shape may be to start the child suspended inside the job
(`CREATE_SUSPENDED` plus assign, then resume) so no window exists between start and binding, or to have the observer
inherit the job, which a child created by a process already in the job joins automatically.

**Sites:** tests/_shared/HostBoundChildren.cs (`KillOnCloseJob.Assign`, `HostBoundChildren.Bind`); tests/_shared/ProcessObserver.cs (`Observe`).
