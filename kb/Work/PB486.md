# PB486

## Mechanism — data-description-entry-p2
F1 — The data-description clause list is a SET, not a sequence: `dataDescriptionClauses : dataDescriptionClause*` accepts every clause in every order, and BindEntry's decoding loop is a single order-insensitive `foreach`. So the two POSITIONAL obligations of §13.16.3 SR4 — the REDEFINES clause and the TYPEDEF clause each shall immediately follow the entry-name clause — are checked by nothing at any stage. The written order survives in the parse tree (the clause contexts are ordered children) and is simply never read; the fix belongs at the one place that already walks that list, not in a second pass.

### Expected, from the standard
ISO/IEC 1989:2023 §13.16.3 SR4 (cite-checked): "The REDEFINES clause, if specified, shall immediately follow the entry-name clause, if specified; otherwise, the REDEFINES clause shall immediately follow the level-number. If the TYPEDEF clause is specified, the data-name format of the entry-name clause shall also be specified and the TYPEDEF clause shall immediately follow the entry-name clause. The remaining clauses may be written in any order." A REDEFINES or TYPEDEF clause written after any other clause is nonconforming and shall be rejected at compile time.

```
$ python scripts/spec/cite.py --check 13.16.3 "The REDEFINES clause, if specified, shall immediately follow the entry-name clause, if specified; otherwise, the REDEFINES clause shall imme..."
  OK  §13.16.3 4)  (Syntax rules)
```

### Observed
Both programs compile AND RUN clean at --std 85, 2002, 2014 and 2023 — p_sr4_redef prints `ABCD`, p_sr4_typedef prints `ABCD`. No diagnostic of any severity. Reading confirms why: CobolData.g4:266 `dataDescriptionClauses : dataDescriptionClause*` imposes no order, and DataBinder.BindEntry's `foreach (var clause in e.Clauses)` (DataBinder.cs ~2228) dispatches on clause KIND only. The two obligations that DO hold hold for unrelated reasons — the entry-name's position is forced by the entry rule's shape (`levelNumber dataName? dataDescriptionBody DOT`, CobolData.g4:212), and TYPEDEF-requires-a-data-name is caught by RegisterTypeDecl (DataBinder.cs:752-757). Nothing reads the clause SEQUENCE anywhere in the frontend or the binder.

## Mechanism — sign-clause
sign-duplicate-clause-last-wins

### Expected, from the standard
The SIGN clause's general format -- rendered from the canonical PDF, page 513 / printed folio 483 -- is '[ SIGN IS ] { LEADING / TRAILING } [ SEPARATE CHARACTER ]', LEADING and TRAILING in BRACES with no choice indicators, so exactly one is selected. The data description entry (§13.16.2) and the report group description entry (§13.15.2) each print `[ sign-clause ]` once, and §5.2.6.2 makes a bracketed portion one that 'may be explicitly specified ... or that portion of the general format may be omitted' -- never repeated. `01 A PIC S9(3) SIGN IS TRAILING LEADING VALUE -12.` and `01 A PIC S9(3) SIGN IS LEADING SEPARATE SIGN IS TRAILING VALUE -12.` are therefore both syntax violations and shall be diagnosed.

### Observed
Both compile clean, at every edition, and the compiler SILENTLY TAKES THE LAST clause. `SIGN IS TRAILING LEADING` stores a LEADING over-punch (`}12`) although the program's first selection was TRAILING. Worse, `SIGN IS LEADING SEPARATE SIGN IS TRAILING` drops the SEPARATE character position entirely: a group holding that item plus a one-character filler prints `[01K|]` -- 4 characters -- where the first-written clause makes it 5. An illegal source line thus silently changes the RECORD LAYOUT, which is exactly the class of change that must never be silent. Mechanism: `dataDescriptionClause` is a plain star and the binder's clause loop reassigns `ownSign` each time it sees a signClause, with no 'already specified' guard. This is a pattern, not one clause -- the same loop assigns justified, blankWhenZero, synchronized and the rest the same way, so the guard belongs in the loop (a specified-once set keyed by clause kind, reported once per repeat) rather than in a SIGN-specific test; §5.2.6.4's already-implemented 'each alternative at most once' handling for the USAGE float phrases (DataBinder.cs:2505-2560, COBOLNET1718) is the shape to generalize.

## Mechanism — synchronized-clause
sign-duplicate-clause-last-wins (SAME MECHANISM, second subject - MERGE INTO THE EXISTING NOTE, do not open a new one). `dataDescriptionClauses : dataDescriptionClause*` lets any clause be written more than once on one entry and the binder's clause loop reassigns unconditionally, so `01 A PIC X SYNC SYNCHRONIZED.` and `01 A PIC X SYNC LEFT SYNC RIGHT.` both compile clean at every edition. Reported this batch against FMT-13.18.52.2 (the SIGN clause), where the same hole silently changes the record layout; the SIGN finding's own text already names SYNCHRONIZED as one of the siblings ('the same loop assigns justified, blankWhenZero, synchronized and the rest the same way, so the guard belongs in the loop'). This row is the confirmation from the SYNCHRONIZED side and adds FMT-13.18.55.2 to the affected set; for SYNCHRONIZED the repeat is value-idempotent (both passes set the same bool), so the harm is under-rejection only, with no wrong answer following.

### Expected, from the standard
13.16.2's Format 1 prints the SYNCHRONIZED bracket exactly once and 13.18.55.2's own figure prints the clause once; 5.2.6.2 makes a bracketed portion one that may be specified or omitted, never repeated. `01 A PIC X SYNC SYNCHRONIZED.` and `01 A PIC X SYNC LEFT SYNC RIGHT.` are therefore syntax violations and shall be diagnosed at every edition.
