# PB647 — OPEN — the value is one now; the MODE still is not

Found 2026-09-05 by the `PB623` implementer (report §"New defects" (1)), measured AFTER its landing: PB623 made
every binary64→scaled-Int128 landing compute the same exact expansion, so the remaining MOVE/COMPUTE split for a
float intrinsic is no longer a value difference but a ROUNDING-MODE difference between two channels. Deliberately
not taken there: it is a mode determination with its own documented rationale (hazard H2 in the numeric design),
a separate mechanism, and flipping it moves every float-intrinsic golden.

## Repro (`--std 2014`, native arithmetic; measured on PB623's tree)

```cobol
       01 S PIC 9V9(9).
           MOVE FUNCTION SQRT(3) TO S        *> 1.732050807
           COMPUTE S = FUNCTION SQRT(3)      *> 1.732050808
```

`sqrt(3)` in binary64 is exactly 1.732050807568877193176604123436845839023590087890625. The MOVE truncates at
scale 9; the COMPUTE's operand was quantized NEAREST-AWAY at the working scale before the store. Ordinary values,
not a knife edge: any returned value whose exact expansion has a digit ≥ 5 past the receiver's last digit splits.

## The rule, and the tension

§15.4.1: "the returned value is the same for all instances of a given function within a single execution of the
runtime element so long as the value and order of the arguments, the collating sequence, and the locale are
unchanged" (`OK §15.4.1`). §14.6.8.2 r4 governs the MOVE: "aligned by decimal point and is transferred to the
receiving digits with zero fill or truncation on either end" (`OK §14.6.8.2 4)`). §14.7.4.3 item 10 governs the
COMPUTE with no ROUNDED phrase: "the arithmetic value is rounded to the nearest value nearer to zero that can be
represented in the resultant identifier" (`OK §14.7.4.3 10)`) — truncation — yet the value reaching the receiver
was already rounded UP at the working scale. Against that stands §8.8.1.3's native latitude ("Native arithmetic
is an implementor-defined method of evaluating an arithmetic expression, an arithmetic statement, the SUM clause,
and all integer and numeric functions", `OK §8.8.1.3`) and `FromDouble`'s documented rationale that rounding at the
working scale is the better approximation. Both readings cannot be right for ONE returned value reaching ONE
receiver two ways; §15.4.1's identity sentence decides which channel yields.

## The mechanism

`src/Cobol.Net.Runtime/Intrinsics/CobolIntrinsics.cs#FromDouble` (`:222` on PB623's tree) hard-codes
`CobolRounding.NearestAwayFromZero` for the arithmetic channel's quantization, while `MoveEmitter` /
`NumericRenderer.StoreArgs` pass the RECEIVER's own mode to `ToScaledUnchecked`. Same exact expansion (PB623),
two modes.

## Fix shape

One mode determination for a float returned value entering fixed-point arithmetic, written once: the working-scale
quantization uses the statement's rounding mode (the receiver's, or the default `ROUNDED MODE` in force), so a
no-phrase COMPUTE truncates exactly as the MOVE does and a `ROUNDED` one rounds in both channels alike; the
"better approximation" rationale is retired with the derivation that §15.4.1's identity outranks it, in
`COBOLNET_NUMERIC_DESIGN.md` (hazard H2) and `docs/CONFORMANCE.md`'s item-92 determination. Goldens at 2002/2014/2023:
SQRT(3), the 0.9/1.0 split, a ROUNDED twin, and the PB623 invariant legs (MOVE = COMPUTE) extended to a value with a
5 past the last digit; every float-intrinsic golden whose `.out` encoded the working-scale rounding is re-derived,
not re-observed. Drift: `CarrierLandingFormTests` asserts that the arithmetic quantizer and the MOVE landing take
their mode from the same source.
