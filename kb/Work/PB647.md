# PB647 — LANDED — the value is one now, and so is the MODE

Found 2026-09-05 by the `PB623` implementer (report §"New defects" (1)), measured AFTER its landing: PB623 made
every binary64→scaled-Int128 landing compute the same exact expansion, so the remaining MOVE/COMPUTE split for a
float intrinsic is no longer a value difference but a ROUNDING-MODE difference between two channels. Deliberately
not taken there: it is a mode determination with its own documented rationale (hazard H2 in the numeric design),
a separate mechanism, and flipping it moves every float-intrinsic golden.

## Repro (`--std 2014`, native arithmetic; measured on PB623's tree)

```cobol
       01 S PIC 9V9(9).
           MOVE FUNCTION SQRT(3) TO S        *> 1.732050807
           COMPUTE S = FUNCTION SQRT(3)      *> 1.732050808
```

`sqrt(3)` in binary64 is exactly 1.732050807568877193176604123436845839023590087890625. The MOVE truncates at
scale 9; the COMPUTE's operand was quantized NEAREST-AWAY at the working scale before the store. Ordinary values,
not a knife edge: any returned value whose exact expansion has a digit ≥ 5 past the receiver's last digit splits.

## The rule, and the tension

§15.4.1: "the returned value is the same for all instances of a given function within a single execution of the
runtime element so long as the value and order of the arguments, the collating sequence, and the locale are
unchanged" (`OK §15.4.1`). §14.6.8.2 r4 governs the MOVE: "aligned by decimal point and is transferred to the
receiving digits with zero fill or truncation on either end" (`OK §14.6.8.2 4)`). §14.7.4.3 item 10 governs the
COMPUTE with no ROUNDED phrase: "the arithmetic value is rounded to the nearest value nearer to zero that can be
represented in the resultant identifier" (`OK §14.7.4.3 10)`) — truncation — yet the value reaching the receiver
was already rounded UP at the working scale. Against that stands §8.8.1.3's native latitude ("Native arithmetic
is an implementor-defined method of evaluating an arithmetic expression, an arithmetic statement, the SUM clause,
and all integer and numeric functions", `OK §8.8.1.3`) and `FromDouble`'s documented rationale that rounding at the
working scale is the better approximation. Both readings cannot be right for ONE returned value reaching ONE
receiver two ways; §15.4.1's identity sentence decides which channel yields.

## The mechanism

`src/Cobol.Net.Runtime/Intrinsics/CobolIntrinsics.cs#FromDouble` (`:222` on PB623's tree) hard-codes
`CobolRounding.NearestAwayFromZero` for the arithmetic channel's quantization, while `MoveEmitter` /
`NumericRenderer.StoreArgs` pass the RECEIVER's own mode to `ToScaledUnchecked`. Same exact expansion (PB623),
two modes.

## Fix shape

One mode determination for a float returned value entering fixed-point arithmetic, written once: the working-scale
quantization uses the statement's rounding mode (the receiver's, or the default `ROUNDED MODE` in force), so a
no-phrase COMPUTE truncates exactly as the MOVE does and a `ROUNDED` one rounds in both channels alike; the
"better approximation" rationale is retired with the derivation that §15.4.1's identity outranks it, in
`COBOLNET_NUMERIC_DESIGN.md` (hazard H2) and `docs/CONFORMANCE.md`'s item-92 determination. Goldens at 2002/2014/2023:
SQRT(3), the 0.9/1.0 split, a ROUNDED twin, and the PB623 invariant legs (MOVE = COMPUTE) extended to a value with a
5 past the last digit; every float-intrinsic golden whose `.out` encoded the working-scale rounding is re-derived,
not re-observed. Drift: `CarrierLandingFormTests` asserts that the arithmetic quantizer and the MOVE landing take
their mode from the same source.

## Landed — 2026-09-05

Reproduced first on this worktree's own build (`--std 2014`, `PIC 9V9(9)`): `MOVE FUNCTION SQRT(3)` 1.732050807
against `COMPUTE` 1.732050808, and `SQRT(0.9999999999)` into `PIC 9V9` 0.9 against 1.0 — exactly as filed. Two
things the note did not say turned up in the probe and are part of the same mechanism:

- **The ROUNDED phrase was a NO-OP on the whole family.** `COMPUTE S ROUNDED = FUNCTION SQRT(3)` and the
  no-phrase `COMPUTE S = FUNCTION SQRT(3)` both answered 1.732050808 — whatever the statement said, the
  quantizer rounded NEAREST-AWAY-FROM-ZERO.
- **A COMP-2 item holding the identical binary64 was already correct in all four positions** (MOVE, COMPUTE,
  nested, relation), which is what identified this as the repo's recurring two-arm shape with one arm fixed —
  and it made the reference behaviour measurable rather than argued: `C2 * 2` gave 3.464101615 where
  `FUNCTION SQRT(3) * 2` gave 3.464101616.

**The fix is bigger than "thread the mode", and the rule was already in this codebase.** `NumericRenderer.Divide`
asks whether the value it is computing IS the value transferred to a single resultant identifier (`_outermost`)
and answers in two arms — the receiver's scale + the receiver's mode for the final transfer, a guard scale +
TRUNCATION for a nested intermediate; `Align` states the same thing for every other float→fixed intermediate. The
float-intrinsic quantizer and native `**` were the two arms of that rule nobody had written. So the landing is
`ReceiverContext.FloatLanding(finalTransfer)` — ONE method deciding the SCALE and the MODE together:

- final transfer → `(Scale, Rounding)`: §14.7.4.1 puts the truncation "relative to the size provided for the
  resultant identifier" (`OK §14.7.4.1`) and §14.7.4.3 rule 2 makes a no-phrase store TRUNCATION
  (`OK §14.7.4.3 2)`), which is exactly the MOVE's §14.6.8.2 rule 4 landing (`OK §14.6.8.2 4)`) — so §15.4.1's
  identity holds by construction, not by coincidence. Landing AT that scale also makes the store's rescale the
  identity, so there is no second rounding left to contradict the first.
- nested → `(FloatWorkingScale, Truncation)`: never the receiver's mode, because §14.7.4.3's per-mode rules each
  bind to "the resultant identifier" and the one receiver store performs that rounding.
- a floating-point numeric-edited resultant (`FloatEdited`, new on `ReceiverContext`) is never a final transfer
  for this purpose: it has no fixed fraction scale to round at.

`CobolIntrinsics.FromDouble` / `FromDoubleBounded` take the mode as a REQUIRED parameter — no default, so a new
call site must decide rather than inherit — and **§14.7.4.3 rule 7's PROHIBITED raise moved into `FromDouble`**
(`OK §14.7.4.3 7)`), gated on `checkedLanding`. It had to: a final transfer lands at the receiver's scale, so the
store's own PROHIBITED test can no longer see the discarded fraction. That also fixed a defect nobody had filed —
`COMPUTE S ROUNDED MODE IS PROHIBITED = FUNCTION SQRT(3) … ON SIZE ERROR` **raised into `PIC 9V9` and stored
silently into `PIC 9V9(9)`**, the condition depending on the receiver's SCALE rather than on the transfer's
exactness.

**Hazard H2 is retired with its derivation.** "Rounding at the working scale is the better approximation" is a
statement about the returned VALUE, which §15.4.1's last paragraph does leave to the implementor; the rounding of
the TRANSFER is not left to the implementor, and §8.8.1.3's native latitude (`OK §8.8.1.3`) reaches the
intermediate, not that transfer. `COBOLNET_NUMERIC_DESIGN.md` D20 and `CONFORMANCE.md` A.1-92 / A.1-70 carry it.

**Measured after** (`--std 2014`): MOVE = COMPUTE = 1.732050807; `COMPUTE ROUNDED` = 1.732050808 (the phrase does
something now); the 0.9/1.0 split is 0.9 both ways; `3 ** 0.5` truncates; PROHIBITED raises at both scales. The
family-wide sweep (SIN, LOG, LOG10, EXP, ANNUITY, STANDARD-DEVIATION, FRACTION-PART, NUMVAL-F) shows MOVE and
COMPUTE agreeing on every member.

**Blast radius, measured, not estimated.** The note expected "every float-intrinsic golden" to move. The whole
Conformance corpus moved exactly ONE golden in two lines: `2023/pb65_codomain_clamp` (`ASINH` 0.523598776 →
0.523598775, `SQRTD` 1.000000000 → 0.999999999), both re-derived from the exact binary64 expansions. That golden
gained six ROUNDED legs, because truncation can never leave a codomain the double is already inside — PB65's clamp
would otherwise have been held open by a green test that no longer exercised it.

**Goldens:** `pb647_float_landing_mode` at 2002/2014/2023 (`PB647FM2`/`FM1`/`FM3`), manifest-registered.
**Drift:** `FloatLandingModeDriftTests` (five invariants over 32×32 legal picture shapes × 8 modes, plus a source
scan that the runtime quantizer names no mode of its own); `CarrierLandingFormTests.FromDouble_IsTheSameLandingAsTheMove`
now sweeps all eight modes. All three watchdogs were PROVEN to fail: with the nested arm changed to inherit
`Rounding` and `TryExactScaled`'s mode changed back to a literal, they went red; probe reverted.

**Inventory:** `inventory_rows` stays empty and NO verdicts were recorded. `GR-14.7.4.3-1..10` are all GAP and
this landing supplies genuine evidence for rules 1, 2, 4, 7, 9 and 10 — but those rules govern EVERY arithmetic
statement and every receiver category, and claiming them on a float-intrinsic golden would be the over-claim rule 3
forbids. Flagged for the registrar lane instead. `RV-15.4.1-1/-2/-3` already read CONFORMS and are strengthened,
not changed, by this.

**Not fixed here, and filed separately in the report:** a NESTED float operand still quantizes at
`max(receiverScale, 9)` with NO guard digits, so at a receiver scale ≥ 9 an expression over a float FUNCTION is one
digit adrift of the same expression over a COMP-2 holding the identical value (`FUNCTION SQRT(3) * 2` into
`PIC 9V9(9)` gives 3.464101614 where `C2 * 2` gives the correct 3.464101615 — it was 3.464101616 before, so the
magnitude of the error is unchanged and only its sign moved). That is a working-SCALE question, not a mode one.
