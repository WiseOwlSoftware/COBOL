# PB464 — an undocumented resolution of an internally tense sentence

**Row:** `GR-14.9.39.4-37` (SET Format 16 — the sign test and the non-integer conversion for
arithmetic-expression-5). From the b2 adjudicator `set-statement-p5`. **Re-run on the HEAD `cobol.exe`
(base 89044aa0)**; the observed behaviour is unchanged.

⚠ **This is an `analysis` note, not a defect.** The compiler's behaviour is one of two admissible readings and
is probably the right one; what is missing is a determination and a test. Filed so the choice stops being an
accident.

## THE TENSION

`--check 14.9.39.4 "If arithmetic-expression-5 does not evaluate to a nonnegative number, the length of
data-name-3 is set to 0 and an EC-STORAGE-NOT-AVAIL exception condition is set to exist. If
arithmetic-expression-5 evaluates to a number that is not an integer, the result of arithmetic-expression-5 is
truncated to the nearest integer."` → **OK §14.9.39.4 37) (General rules)**.

The second sentence pairs two operations that are not the same one. *Truncation* discards the fraction (2.7 → 2;
toward zero). *Nearest* selects the closer integer (2.7 → 3). For 2.7 the two readings give different lengths,
so the sentence cannot be applied as written without choosing.

**It is the standard's ONLY occurrence.** `grep -c "nearest integer" specs/ISO_COBOL.md` → **1**, and
`cite.py --find "truncated to the nearest integer"` → **1 occurrence, §14.9.39.4 37)**. There is no sibling use
in another clause to calibrate against, which is what makes this worth writing down rather than assuming.

## WHY TOWARD-ZERO IS THE DEFENSIBLE READING

The standard's own vocabulary settles it, and this is the part the finding did not supply:

* `--check 14.7.4.3 "If the ROUNDED phrase is not specified, execution is as if ROUNDED MODE IS TRUNCATION had
  been specified."` → **OK §14.7.4.3 2) (General rules)**. "Truncation" is a named rounding MODE in this
  standard, not a loose synonym — so GR37's verb is the mode's name.
* `--check 11.9.11.2 "If the TRUNCATION phrase is specified and an intermediate value cannot be represented
  exactly in SBIDI form, the value shall be rounded to the nearest value that can be represented exactly in that
  format that is nearer to zero than the intermediate value."` → **OK §11.9.11.2 e) (General rules)**.

That second citation is the key: the standard DEFINES its TRUNCATION mode using the words "rounded to the
nearest … nearer to zero". GR37's "truncated to the nearest integer" is the same idiom compressed — *the
nearest integer in the toward-zero direction* — not a nearest-away-from-zero rounding. **So the tension is
resolvable from within the standard, and the compiler's answer is the right one.** What remains is that nothing
in this project says so, and nothing pins it.

## OBSERVED — re-run on HEAD

```
$ cobol.exe gr37-nearest.cob --std 2023 --run
   >>TURN EC-STORAGE-NOT-AVAIL CHECKING ON
   01 WS-D PIC X DYNAMIC LENGTH LIMIT IS 9.   01 WS-A PIC 9V9 VALUE 2.7.   01 WS-B PIC 9V9 VALUE 2.2.
   MOVE "ABCDEFGHI" TO WS-D.  SET SIZE OF WS-D TO WS-A.   …then the same with WS-B
L(2.7)=02
L(2.2)=02
```

Toward-zero, both directions. Under the nearest reading `L(2.7)` would be `03`.

The code site is one line:

```
src/Cobol.Net.Runtime/Values/Text/CobolDynString.cs:65
    n = (long)newLen;        // GR37 — non-integer truncates toward zero
```

A `(long)` cast of a `double` in C# truncates toward zero, so the behaviour follows from the cast rather than
from a decision anyone recorded. The comment states the reading; a comment is not a determination
(the same lesson PB460 draws for the A.1 register).

## WHAT NOTHING PINS

* **No determination.** The only SET-SIZE determination in `docs/CONFORMANCE.md` (`:257-263`) covers GR38's
  third sentence, the storage-unavailable leg. GR37's second sentence is not mentioned.
* **No test.** The `2023/ec_storage_not_avail` golden's fractional case is **−0.5**, which GR37's FIRST sentence
  (`newLen < 0.0` at `CobolDynString.cs:53`) catches before the truncation at `:65` is ever reached. So no test
  in the tree drives a fractional POSITIVE amount, and nothing would notice if `:65` changed to `Math.Round`.
  That is the `feedback_green_gates_arent_evidence` shape: a green suite that never looked at this line.

## WHAT THE FIXER SHOULD DO

1. Record the determination beside the existing GR38 one: GR37's "truncated to the nearest integer" is applied
   as **toward-zero truncation**, with the §11.9.11.2 e) TRUNCATION-mode definition cited as the internal
   calibration. (⛔ This note does not edit `docs/CONFORMANCE.md`.)
2. Add a golden that drives a fractional POSITIVE amount through `SET SIZE OF` — 2.7 and 2.2 into the same
   item, expecting length 2 both times. One row, and the line stops being unpinned.
3. While in the file: `:65`'s neighbours are PB463's unchecked `(int)` casts at `:67` and PB458's absent SR34
   screen. All three land in `CobolDynString.SetSize`; sequence them so the truncation golden is written against
   the post-PB463 shape.

## THE SIBLING SWEEP

* Every other place a COBOL non-integer becomes an integer by a bare C# cast rather than by a named rule:
  `SetEmitter.cs:28/86/96` (PB459's three `(long)` narrowings) are the same shape with a DIFFERENT correct
  answer — there the standard requires an exception condition, not a truncation. A single "convert to integer"
  helper must therefore carry the RULE, not just the direction.
* Any other single-occurrence phrase in §14.9.39 that the compiler resolves by a language primitive's default
  rather than by a stated reading.

## ROWS

* `GR-14.9.39.4-37` — the sign leg (`newLen < 0.0` → length 0 + nonfatal EC-STORAGE-NOT-AVAIL) is implemented
  and golden-driven; the non-integer leg is implemented as toward-zero and MEASURED here, but rests on an
  undocumented reading with no test. The row is held below CONFORMS by the missing determination and the
  missing golden, not by a behavioural divergence.
