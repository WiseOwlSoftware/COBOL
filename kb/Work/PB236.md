# PB236

**Rows:** `SR-14.9.2.3-4`, `SR-14.9.2.3-6` (ADD, below) and `FMT-14.9.27.2`, `SR-14.9.32.3-1`, `SR-14.9.34.3-1`, `SR-14.9.41.3-5`, `GR-14.9.41.4-4`, `GR-14.9.41.4-8`, `FMT-14.9.47.2` (the I-O and sort verbs, adjudication batch b1 — see the section at the foot of this note)

an ADD's syntax rules are decided at RUN time, not at bind: a category-illegal or elementary CORRESPONDING operand compiles clean and throws NotImplementedCobolFeatureException, and a reference-modified GIVING receiver escapes even that guard into a raw Roslyn type error.

Rows: SR-14.9.2.3-4 (Format 2 — identifier-3 shall be numeric or numeric-edited), SR-14.9.2.3-6 (Format 3 — identifier-1 and identifier-2 shall be group items, and the rule enumerates which group kinds). ONE stage error: both syntax rules are decided by emit-time code instead of by a bind-time diagnostic, so violating source COMPILES.

SR4 — THE ADMITTED HALF IS IMPLEMENTED AND TESTED, so this note is not read as doubting it. A NUMERIC identifier-3 stores through the ordinary funnel (NumericRenderer.StoreArgs at the receiver scale + ROUNDED mode), pinned by conformance:2023/ca4_giving_composite (`ADD A B GIVING C` into PIC 9(6)V9(10) → 0000030000000000). A NUMERIC-EDITED identifier-3 is a first-class receiver with THREE dedicated arms — the floating-point edited mask (D21/PB66), the LOCALE format-2 edit (PB64 T6) and the ordinary EditMask arm, each with its own checked/unchecked landing — pinned by conformance:2023/pb66_float_edited_picture, whose `ADD 1 0.5 GIVING E4` prints `ADD      [ 15.000E-01]`, an edited image derived from the mask and not from an oracle. The numeric-edited admission is the discriminator that makes SR4 different from SR2, and it is correctly modelled.

SR4 — THE PROHIBITION HALF IS NOT ENFORCED AT COMPILE TIME (under_rejects). ResolveReceiving applies no category screen, so an identifier-3 of category alphanumeric, alphanumeric-edited, national or boolean, or a group item, BINDS without a diagnostic and falls to StoreArith's default guard at ArithmeticEmitter.cs:436, which emits EmitCore.LoudStmt → a RUN-TIME NotImplementedCobolFeatureException. It IS rejected — unlike SR2's numeric-edited case, which executes — but at the wrong stage and under a message that names an unimplemented feature rather than a violated syntax rule.

SR4 — AND THE RUN-TIME GUARD DOES NOT CATCH EVERYTHING (crashes). A REFERENCE-MODIFIED identifier-3 over a numeric item escapes it entirely. §8.4.3.3.4 GR6c makes a ref-mod result of a numeric item class and category ALPHANUMERIC, so `ADD 1 2 GIVING N(1:2)` with N PIC 9(5) violates SR4 — but Place.cs:37 defines `PlaceDecorator.Item => Inner.Item`, so for a RefModPlace `target.Item.Pic` is the INNER item's PicInfo, category Numeric, and StoreArith's guard PASSES. The store then goes down the fixed-point funnel and its numeric value is handed to PlaceRenderer.cs:104's RefModPlace arm, `Write(r.Inner, RuntimeApi.StrSpliceInto(Read(r.Inner), …))`, which splices a STRING — so the failure is a raw Roslyn type error on generated user source, not the named loud the record relies on, and for a StoreAsImage receiver it is not obviously a failure at all.

SR6 — THE GROUP REQUIREMENT IS CHECKED AT THE WRONG STAGE. CorrespondingBinder.Bind:53-66 resolves both operands then returns BoundUnsupported when either is not a group (DataItem.IsGroup, Model/DataItem.cs:334, is `Pic is null && Children.Count > 0`), with the SR citation already in the message — and StatementEmitter renders BoundUnsupported as LoudStmt, touching no diagnostic channel, so `ADD CORR ELEM TO GRP` COMPILES and throws only if the statement is reached.

SR6 — THE GROUP SUB-KINDS ARE NOT DISTINGUISHED. The rule admits alphanumeric group items, national group items, variable-length groups and strongly-typed group items — i.e. it EXCLUDES some group shapes — and the binder's own class doc (:45-47) records the gap: 'the SR6/SR12 2002+/2014+ operand categories (national / bit / strongly-typed / variable-length groups) … have no representation in this data model yet'. One asymmetry checked against the spec and worth keeping: §14.7.6's D1/D2 list (specs/ISO_COBOL.md:21816) INCLUDES bit group items while SR6's list does not, so an ADD CORR over bit groups is a rule SR6 alone decides — and neither list is modelled here.

SR6 — THE LEVEL-66 EXCLUSION HOLDS ONLY INCIDENTALLY (silent). A RENAMES entry is built by DataBinder.BindRenames (:1960-1984) with Pic null and no Children, into `_lastRoot.Renames66` rather than Children, so IsGroup is false for it and it lands in the SAME BoundUnsupported 'elementary operand' arm — rejected, but at run time and under a message naming the wrong reason. The in-code claim at :59-62 that the shape 'already failed the resolves above' is not what actually happens: that is comment-vs-behaviour drift and should be corrected with the fix.

WHAT WOULD CLOSE IT: a receiving-side category screen in ResolveReceiving (the same one SR-14.9.2.3-2's row names), with the GIVING arm admitting numeric-edited and rejecting the ref-mod result per §8.4.3.3.4 GR6c; a bind-time SR6 diagnostic for the non-group and level-66 cases; and the group sub-kinds modelled once the national/bit/variable-length/strongly-typed categories bind. Negatives: `ADD 1 2 GIVING <PIC X>`, `ADD 1 2 GIVING <numeric>(1:2)`, `ADD CORR <elementary> TO <group>`, `ADD CORR <level-66 name> TO <group>`.

SPEC REFS as carried by the rows: §14.9.2.3 SR4, SR6; §8.4.3.3.4 GR6c; §14.7.6 (the D1/D2 list at :21816); §14.9.25.3 SR12 and §14.9.44.3 SR6 (the two sibling rules the same message cites).

## Mechanism

src/Cobol.Net.Compiler/Binding/ExpressionBinder.cs#ResolveReceiving applies no category screen, so the decision falls to src/Cobol.Net.Compiler/CodeGen/Verbs/ArithmeticEmitter.cs#StoreArith's default guard (:436, `if (target.Item.Pic is not { Category: PicCategory.Numeric, IsFloat: false })` → EmitCore.LoudStmt) and to src/Cobol.Net.Compiler/Binding/Procedure/Verbs/CorrespondingBinder.cs#Bind (:53-66, `return new BoundUnsupported($"{verbName} CORRESPONDING over an elementary operand … ISO Sec.14.9.25.3 SR12 / Sec.14.9.2.3 SR6 / Sec.14.9.44.3 SR6")`), both landing in src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:211 (`Visit(BoundUnsupported n) { _ctx.Writer.Line(LoudStmt(n.Feature)); return false; }`) → EmitCore.cs:93 `LoudStmt(feature) => "NotImplemented.Run(...)"`; the ref-mod escape is src/Cobol.Net.Compiler/Binding/Model/Place.cs:37 (`public override DataItem Item => Inner.Item;`) with src/Cobol.Net.Compiler/CodeGen/Roslyn/PlaceRenderer.cs:104 (the RefModPlace write arm splicing a string)

## THE SAME CARRIER, SEVEN MORE SITES ACROSS THE I-O AND SORT VERBS (adjudication batch b1, 2026-09-02)

Seven rows joined this note because they are the identical stage error, not seven new ones. `BoundUnsupported` is
documented at `BoundTree.cs:535` as *An unsupported / unresolved statement - the backend emits a loud runtime
guard (§1.4)* — the carrier for FEATURES COBOL.NET has not built — and `StatementEmitter.cs:211` renders every
one of them as `EmitCore.LoudStmt` -> `NotImplemented.Run(...)`. It is doing **three incompatible jobs**, and only
the first is its own:

1. a genuine feature deferral (correct: a loud runtime stage for something not yet built);
2. an **ill-formed OPERAND** — a user error, which belongs at compile time;
3. an **illegal PLACEMENT** — likewise.

Jobs 2 and 3 produce a message that tells the programmer THE COMPILER is incomplete when in fact THE SOURCE is
wrong, which sends the diagnosis in the wrong direction; and on an unexecuted path they produce no message at all,
so illegal source ships.

**A. An UNDECLARED file-name, seven binder sites, one mechanical pattern.** `grep -rn "of undeclared file"` over
`src/` returns exactly seven: `FileLockBinder.cs:32` (UNLOCK), `KeyedIoBinder.cs:142/178/207` (DELETE, DELETE
FILE, START), `SequentialIoBinder.cs:41/64/150` (OPEN, CLOSE, READ). Measured at `--std 2002/2014/2023`, all
silent at compile time and all fatal at run time: `probe/unlock/n6.cob` (`UNLOCK NOSUCH`), `u1.cob`
(`OPEN INPUT NOSUCH`), `u2.cob` (`CLOSE NOSUCH`), `u3.cob` (`READ NOSUCH AT END ...`), `u4.cob`
(`DELETE NOSUCH RECORD`), and `probe/open-p1/und1.cob`, which opens a WORKING-STORAGE item
(`OPEN OUTPUT WS-X`) and prints `BEFORE` before aborting. §14.9.27.2's and §14.9.47.2's general formats write the
operand as **file-name-1**; §8.3.2.2 lists file-name among the user-defined words; and
`cite.py --check 8.4.2.1 "In order to use a resource, a statement shall contain a reference that uniquely
identifies that resource."` -> **OK**. A word that names no file connector identifies no resource, so the source
is not conforming COBOL. The compiler's own posture elsewhere is the right one: `UNLOCK "F".` and `UNLOCK.`
already get parser diagnostics. **The grammar's use of `dataReference` rather than `fileName` is defensible** — a
targeted binder diagnostic beats a parse error — **but only if the binder then ISSUES that diagnostic.** The fix
belongs in the SHARED file-name resolution step (one `ctx.Edition.Error` on an unresolved file-name), after which
the seven call sites simply do not need the `BoundUnsupported` arm.
Rows: `FMT-14.9.27.2`, `FMT-14.9.47.2`, and it is the *benign edge* recorded against `SR-14.9.41.3-5` (an operand
failing NAME RESOLUTION short-circuits before SR5 runs).

**B. A SYNTAX-RULE violation carried by the same node.** `SortBinder.BindRelease` returns
`BoundUnsupported($"RELEASE record '{...}' is not a record of a sort-merge description entry (ISO 14.9.32.3
SR1)")` and `SortBinder.BindReturn` the §14.9.34.3 SR1 twin — **the right predicate, the right citation, the wrong
stage.** `probe/neg/neg.cob` compiles clean and dies at run time; `probe/p13/p13.cob` likewise, and
`probe/p14/p14.cob` puts the same RETURN in a paragraph the flow `GO TO`s past, so it compiles AND runs to normal
completion with no diagnostic at any time. §4.2.2 (`--check` -> **OK**) requires a compile-time warning mechanism
for violations of the explicit syntax rules. The sweep inside the sort family alone: `BindRelease` (14.9.32.3
SR1), `BindReturn` (14.9.34.3 SR1), `SortBindFile` (14.9.40.3 SR4/SR6a/SR6b/SR8), `SortBindTable` (14.9.40.3
SR13/SR14a/SR14e) and `BindMerge` (14.9.24.3).
Rows: `SR-14.9.32.3-1` (its OPERAND defect is `kb/Work/PB347`), `SR-14.9.34.3-1`.

**C. START, where two of five `BoundUnsupported` returns carry no diagnostic and three do.**
`probe/rel-nokey/STPRB8.cob` — a RELATIVE file with ACCESS SEQUENTIAL and deliberately NO RELATIVE KEY clause,
which §12.4.5.13 permits — compiles with no diagnostic and dies with *START on RNK with no resolvable RELATIVE
KEY item*. §14.9.41.4 GR8 substitutes `KEY IS EQUAL TO data-name-1 ... the name of the key specified in the
RELATIVE KEY clause`; with no such clause the substitution has no operand, so REJECTING the program is right and
the rejection belongs in the SAME channel as the SR1/SR3/SR5/SR6 checks the very same method already reports as
COBOLNET0862. The other two returns without a diagnostic are the sequential-organization arm (`kb/Work/PB352`,
`kb/Work/PB353`). The asymmetry is accidental, not designed.
Rows: `GR-14.9.41.4-8`, `GR-14.9.41.4-4`.

**D. And the placement job, which is job 3.** `StatementBinder.BindStatementCore`'s bottom arm,
`_ => new BoundUnsupported($"statement '{FirstToken(s)}'")`, catches a USE statement written outside the
declaratives portion — `kb/Work/PB361` owns that rule, and it is listed here because the bottom arm is the same
carrier guessing between *not implemented* and *illegal here*.

### The invariant this note should land with

Separating the jobs is the fix, and a per-site habit is what produced the asymmetry in C. Make the diagnostic an
**invariant**: a `BoundUnsupported` reachable from a statement the grammar ACCEPTED must carry a reported
diagnostic, enforced by a validator (`BoundTreeValidator` already exists to hang it on). That also closes the
edition-gate hole `kb/Work/PB353` describes, since a bail-out that must report cannot silently skip a
shape-keyed gate.
