# PB2602 — one landing queue while the loop runs

**Controller directive 2026-10-08 00:35 PDT**, on the owner's 00:25 "The new session for account 2 is operating with
horrible accuracy" and 00:30 "you have literally wasted many, many hours rebasing and rerun tests and CIs repeatedly".

**Model:** Opus. One group with PB2600 and PB2601 (wave 1038 group V).

## Defect

Two landing mechanisms race for main: attended landers (dispatched by the operator session by hand) and the loop's
land unit (and the trains its waves start). Whichever pushes second finds main moved, rebases, re-gates and re-runs CI;
when both keep landing, every train pays that again. Nothing in the workstream skill said which mechanism owns main
while the loop runs, so the attended session kept dispatching landers beside it.

## Rule

While the loop runs (its `orchestrate.lock` names a live process), the attended session dispatches NO lander. A
finished attended branch becomes a report the land unit can see: named `w<wave><letter>-PB<lead>-report.md`
(plan_wave.py `REPORT_NAME`; a suffixed name is invisible), starting `Status: DONE`, then its worktree, branch, HEAD
and base. The next land unit batches ALL DONE branches into one train. If one cannot wait, exactly ONE lander carries
every ready branch.

## Fix shape

The rule in MANDATORY-PRACTICES, the workstream SKILL.md §3 and `references/landing.md`; `units/land.md` collects the
attended DONE reports (through the PB2600 lifecycle report's WAITING TO LAND rows); a check that an attended lander's
dispatch brief names the loop state; the report-name shape documented where attended dispatchers read it.
