## Landed (wave w0930-numeric, one bundled commit with PB1526/PB1379/PB1510/PB1686/PB1143/PB638/PB621)

**Root cause (the rule, not a lane tweak).** `CombineCore` took the binary64 lane whenever ANY operand was `Real`, and a
floating-math function's returned value (and a non-integer native power, and NUMVAL-F's receiver-less binary64) is a `Real`
that the ENGINE produced — not the content of a float data item. §14.9.2.4 GR4 / §14.9.44.4 GR4 withdraw the native latitude
only for operands "described with usage … float-long …" and §14.7.7 r2 lists an intrinsic function and a float usage as
separate bullets, so beside non-float operands "enough places shall be carried so as not to lose significant digits" (all
three `cite.py --check`ed). `13.2 + FUNCTION SQRT(16)` therefore carried 13.2 as 13.199999999999999 and the truncating store
gave 17.1. Fix: `NumX.Approximate` marks the engine-produced binary64 (`IntrinsicRenderer.RenderFloatNative`, `Power`, NUMVAL-F);
`CombineCore` lifts it to the SDIDI (shortest round-trip decimal — the same value) unless `FloatItemLane` (a float item, a
float carrier literal, a float receiver) owns the lane; `Negate` carries the flag. Precedent where the ISO text is silent:
GnuCOBOL evaluates every intrinsic result as a decimal. Documented in docs/CONFORMANCE.md DOC-A.1-92 / -123 and
COBOLNET_NUMERIC_DESIGN.md D26.

**Siblings swept** (all double-backed numeric functions share `RenderFloatNative`, so one mechanism): ADD / SUBTRACT /
MULTIPLY / DIVIDE / COMPUTE all go through `CombineCore` (probed: 17.2, 9.2, 6.6, 26.4, LOG10 15.2); the receiver-less
RELATION channel had the same defect (`0.1 + FUNCTION SQRT(0.04) = 0.3` was FALSE, now TRUE); a native `**` with a
non-integer exponent and NUMVAL-F are the other two Real producers and are covered; a COMP-2 ITEM operand stays binary64
by D16 (`13.2 + COMP-2 4.0` is still 17.1 — a float item, not this defect); standard modes already lifted every float.
Golden `2023/pb1641_function_result_beside_decimal_operands`.

Filed 2026-09-27 by the train-65 lander from the wave-65 C implementer report (PB1142). Unrelated to PB1142's
root; found while probing function-identifier operands.

**Observed.** `13.2 + FUNCTION SQRT(16)` gives 17.1, in both ADD and COMPUTE. `MULTIPLY FUNCTION SQRT(4) BY B` with
B = 3.3 gives 6.5. SQRT(16) alone is exactly 4, so the error comes from the combination: once a float-typed intrinsic
joins the expression, the decimal operands appear to be carried in binary floating point and then truncated.

**Repro.** `E:\Temp\claude\E--COBOL\eb162d4b-e0bb-4027-b8a0-86fd190d20be\scratchpad\w65c\sq.cob` and
`...\scratchpad\w65c\p0\fn.cob`.

**Expected.** 17.2 and 6.6. The literal operands are exact decimals and SQRT(16) = 4 exactly; §14.9.2.4 GR2 (the sum
is stored in the receiver) and the §8.8.1.5 arithmetic mode leave no room for a binary rounding artifact on these
operands.

**Code site.** `src/Cobol.Net.Compiler/Binding/IntrinsicCatalog.cs:142` (the SQRT row, runtime `Sqrt`), and the place
where the arithmetic lane is chosen once a float-typed intrinsic joins the expression. PB116 made `CobolDec.Sqrt`
exact, so the defect is probably the lane choice rather than the function. Check every other double-backed numeric
function for the same lane (PB653 and PB623 are the landed siblings on float operands).
