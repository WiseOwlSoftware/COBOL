# PB15 — LANDED 2026-08-04 — the §15.x.1 RESULT-TYPE tables were ignored for TEN functions, not four

⚙ **THE ENTRY WAS RE-MEASURED BEFORE ANY CODE CHANGED, AND ITS COUNT WAS SHORT.** It named four findings
(FORMATTED-DATE, FORMATTED-DATETIME, FORMATTED-TIME, TRIM). The measured population is **eight broken functions
out of twenty that carry a result-type table** — the four above plus **FORMATTED-CURRENT-DATE, SUBSTITUTE, CONCAT
and BASECONVERT**. Its harm flags were also wrong in a way that matters: it was filed `wrong_answer: true`, and
the run-time VALUE was correct in every case measured. The defect is a **silent under-rejection**.

## What it was

Twenty §15 functions do not have a constant type. Their own §15.x.1 clause carries a table whose left column is
an ARGUMENT property and whose right column is the function type — "The type of this function depends on the type
of argument-1 as follows". `IntrinsicCatalog` stored ONE SCALAR type per function, so every such function needed
a hand-written exception in the binder, and only five ever got one, in **two separate name lists**:

    IntrinsicBinder ~550   RuntimeMethod is "UpperCase" or "LowerCase" or "Reverse"     (CA25, 3 functions)
    IntrinsicBinder ~567   sig.Name is "MAX" or "MIN"                                   (V54,  2 functions)

**Nothing reminded anyone of the other ten, and nothing could: a name list has no way to say what it omits.**
`COBOLNET_INTRINSICS_DESIGN.md` D2 says the catalog "is the single source of result-category truth" — it was not;
three mechanisms decided the property.

**MEASURED** (`MOVE FUNCTION <F>(<national args>) TO <PIC X>`, which §14.9.25.3 SR10 / Table 16 requires be
rejected — National row, AN column = No):

| | before | after |
|---|---|---|
| TRIM · SUBSTITUTE · CONCAT · BASECONVERT · the four FORMATTED-* | **compiled clean** | `COBOLNET0819` |
| UPPER-CASE · LOWER-CASE · REVERSE · MAX · MIN | `COBOLNET0819` | unchanged |

The run-time value in the LEGAL direction (national result → national receiver) was already correct and is
byte-identical after the fix — the runtime bodies operate on UTF-16 strings, so only the LABEL was wrong. That is
what makes it silent: a mislabelled national result does not compute anything wrong, it walks past the guard that
should have stopped it.

## The fix — a catalog COLUMN, not an eleventh name

`IntrinsicResultRule` is now a column on the catalog row (`IntrinsicSig.Result`) and
**`IntrinsicResultType.Resolve` is the ONE reader**. Seven spec-derived shapes cover all twenty functions;
`FollowsArgument1` alone covers ten. Adding a function is a column, never an edit to the binder.

⛔ **THE HALF THAT WOULD HAVE BEEN MISSED — AND IT IS THE FAMILY'S SIGNATURE SHAPE.** `BindTrim` and
`BindSubstitute` parse phrase keywords, so they build their **own** `BoundIntrinsicCall` with a hardcoded
`PicCategory.Alphanumeric` and never reach the generic path. Landing the catalog column alone would have left
TRIM and SUBSTITUTE broken **with the fix present, the column correct and every test green** — the two-arm
dispatch in its silent form, now six occurrences in this codebase. `NoBespokeBindPath_HardcodesAStringResultCategory`
asserts the shape, not the two instances.

⭐ **Resolve returns the §15.2 TYPE, not the category.** `ResultCategory` folds Integer/Numeric/Index into
`PicCategory.Numeric`, so resolving to a category would have made the four integer-following rules
unrepresentable — dead members reading as coverage. Resolving the type keeps §15.2 intact and leaves the answer
already correct for the first consumer of integer-ness that arrives.

## The guard that makes the next one automatic

`IntrinsicResultTypeDriftTests` **re-derives the population from `specs/ISO_COBOL.md` on every run** — the
structural key is a markdown table in §15.x.1 whose header names the "Function type" column — so a function whose
clause grows a table, or a new function that has one, fails the build until its row declares a rule. It also
asserts the converse (no row invents a rule the standard does not give it), that the resolver is wired, that
every enum member has an arm, and that no bespoke bind path hardcodes a string category.

⚠ **Keying it on the TABLE rather than the sentence is the whole trick.** The clauses do not agree on wording —
§15.38.1 "depends on the argument type", §15.39.1 "depends on the type of argument-1", §15.18.1 "depends upon the
argument types" — and the first scanner keyed on prose and found **ten of the twenty**: a dead guard inside the
guard against a dead lookup.

## ⛔ AND A "SIBLING DEFECT" I FOUND, FIXED, AND THEN HAD TO UNFIND

Sweeping for siblings turned up `FUNCTION REVERSE(grp)` over a group of `PIC N` children compiling clean into a
`PIC X` receiver, with `OperandCategory` discarding every group's category (null) while
`IntrinsicArgumentRules.ClassOfPlace` derived it — one rule written twice, disagreeing. I implemented the §8.5.2.1
group arm and measured: **still accepted**, because the premise was false. §8.5.2.10 item 3 defines a group of
category national as one "described with a GROUP-USAGE clause with the NATIONAL phrase" (§13.18.29 — and my first
draft cited **§13.18.27**, which `cite.py --check` rejected: the clause exists and says something else, the exact
inherited-citation failure rule 1 names); a group whose CHILDREN are national is an ordinary **alphanumeric**
group, so the alphanumeric result and the accepted MOVE are both CORRECT. GROUP-USAGE is not modelled here, so no
group this compiler can express is anything but alphanumeric. Reverted — keeping only the comment, because the
change would also have silently tightened `CheckRepertoireArgs` (DISPLAY-OF/NATIONAL-OF) on an unrelated axis.
`validate_the_premise_not_only_the_rule`: the citation was right and the finding was still impossible.

## What is NOT closed by this

- **§15.19 CONVERT was never broken.** Its catalog comment claimed the category is "computed per §15.19.1";
  measured, `BindConvert` genuinely does it (`dst == 3 ? National : Alphanumeric`). The claim was true — checked
  rather than trusted, since a queue entry's own root cause is a claim (PB8 is the standing proof).
- **Two rows of §15.18.1 CONCAT are unreachable**, and that is pre-existing staging, not a hole opened here:
  `PIC 9 USAGE NATIONAL` / `PIC 1 USAGE NATIONAL` are the §13.18.40.4 SR12 national-form legs, staged loud at the
  DATA DIVISION (`COBOLNET0899`), so no such item can reach a CONCAT call. No arm was written for them — that
  would be dead code reading as coverage.
- **The INTEGER-following rules are declared but not yet observable.** ABS · RANGE · SUM · the three ALGEBRAIC
  functions now resolve to `IntrinsicType.Integer` correctly, but every consumer reads `ResultCategory`, which
  folds Integer into Numeric. They are right and inert. The first consumer of integer-ness — a function result in
  a subscript or an §15.3 type-6 argument position, which is [[PB17]]'s territory — finds them already correct.

**Goldens:** `2023/pb15_result_type_follows_argument` (both rows of the table for eight functions, so a "fix" that
labelled everything national would fail it) · negative `pb15-trim-national-result-to-an` ·
`pb15-substitute-national-result-to-an` · `pb15-concat-national-result-to-an` ·
`pb15-formatted-date-national-result-to-an`.
