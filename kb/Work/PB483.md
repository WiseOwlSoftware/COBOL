# PB483 — LANDED — a format constraint with no rule behind it is still a constraint

Found 2026-09-04 by the `PB205` implementer, which added §13.18.16.3 SR6's uniqueness screen for data-name-1
and deliberately did not extend it to FINAL, because SR6 does not say FINAL. Re-derived on this tree for this
note.

## The mechanism

`BindReportDescriptionClauses` in `src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs` — the FINAL arm of
the CONTROL clause appends a FINAL control level each time the word appears. `CONTROLS ARE FINAL FINAL CX`
therefore builds a hierarchy with two FINAL levels; §13.18.16.4 GR2 places FINAL as the highest level, and
the second copy is a level that can never break (nothing is "more major" than FINAL to break it), so any
TYPE CF FINAL or RESET ON FINAL that resolves to it is silently inert.

## The rule

```
python scripts/spec/cite.py --check 13.18.16.3 "Data-name-1 shall be unique in any given CONTROL clause"
OK  §13.18.16.3 6)
```

SR6 constrains data-name-1 only. The constraint on FINAL is the general format itself: §13.18.16.2 writes
`FINAL [ data-name-1 ] …` with the ellipsis on the bracketed data-name, so FINAL is a single optional token
before a repeated group — render the page (`scripts/render-spec-page.py`) before implementing, because the
OCR'd diagrams were lossy toward falsely-restrictive syntax and the exact bracket placement is load-bearing
here. A second FINAL is source the format does not describe; the conforming posture is a compile-time
rejection, as for any other general-format violation.

## Fix shape

Reject the second FINAL in the CONTROL-clause bind (the same site PB205's SR6 screen lives in) with a
diagnostic that names the format rather than SR6; one negative golden (`*> reject-at: 85 2002 2014 2023`).
Sweep: the RD's other single-token phrases (`PAGE LIMIT`, `HEADING`, `FIRST DETAIL`, `LAST DETAIL`,
`FOOTING`) for the same "append on every occurrence" shape.

## Landed (wave 58, implementer w58h)

Re-probed on the worktree build first: `CONTROLS ARE FINAL FINAL CX`, `CONTROLS ARE CX FINAL`, two CONTROL clauses
and `PAGE LIMIT 30 LINES HEADING 1 HEADING 2` each compiled clean at 2023 (and ran). The misplaced-FINAL shape is a
WRONG ANSWER the note did not name: FINAL became the MINOR level, so TERMINATE printed CF FINAL before CF CX.

```
python scripts/spec/cite.py --check 13.18.16.4 "FINAL, if specified, is associated with the highest level in the hierarchy"
OK  §13.18.16.4 2)
```

```
python scripts/spec/cite.py --check 5.2.7 "the ellipsis applies to the portion of the format between the determined pair of delimiters"

```

The figure was rendered from the PDF (p422): `FINAL [ data-name-1 ] …`, FINAL once and first.

Fix: `BindReportDescriptionClauses` refuses a FINAL written after any operand of its clause — which is both
shapes — as COBOLNET2421 (the general format, not SR6). The sibling sweep the note asked for found the same
"append on every occurrence" shape one level up: §13.14.2's four RD clauses and §13.18.39.2's four PAGE phrases
are each a bracket with no ellipsis (§5.2.6.2 / §5.2.7) while §13.14.3 SR2 / §13.18.39.3 SR4 license ORDER only;
they now read ONE helper, `UnrepeatedElements.AtMostOnce` (COBOLNET2423), written so the data description
entry's identical defect (a lead in the wave-58 report) can reuse it. Goldens: `85/pb483_control_final_first`,
`negative/pb483-control-final-placement`, `negative/pb483-report-format-element-repeated`; per-shape
`ReportClauseFormatScreenTests`. Rows closed: FMT-13.18.16.2, GR-13.18.16.4-2, SR-13.14.3-2.
