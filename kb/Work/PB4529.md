# PB4529 — indexed-duplicate-key-status-02-not-set: BDB indexed files: WRITE and READ NEXT through a duplicate alternate key return status 00, not 02

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

With the BDB indexed handler, cobc never sets I-O status 02 for an alternate record key WITH DUPLICATES. A WRITE that
creates a duplicate alternate key value returns 00, and a READ NEXT whose next record (in the alternate key of
reference) has the same key value returns 00. ISO requires 02 in both cases, so a program cannot tell from the status
where a run of duplicate alternate key values ends.

## Minimal test case

Free reference format (`-free`).
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. DUPNEXT.
ENVIRONMENT DIVISION.
INPUT-OUTPUT SECTION.
FILE-CONTROL.
    SELECT F ASSIGN TO "dupnext.dat"
        ORGANIZATION IS INDEXED
        ACCESS MODE IS DYNAMIC
        RECORD KEY IS K
        ALTERNATE RECORD KEY IS A WITH DUPLICATES
        FILE STATUS IS ST.
DATA DIVISION.
FILE SECTION.
FD F.
01 R.
   05 K PIC X(2).
   05 A PIC X(2).
WORKING-STORAGE SECTION.
01 ST PIC XX.
PROCEDURE DIVISION.
    OPEN OUTPUT F
    MOVE "01XX" TO R
    WRITE R
    MOVE "02XX" TO R
    WRITE R
    DISPLAY "WRITE DUP " ST
    CLOSE F
    OPEN INPUT F
    MOVE "XX" TO A
    START F KEY IS EQUAL TO A
    READ F NEXT RECORD
    DISPLAY "READ 1 " R " " ST
    READ F NEXT RECORD
    DISPLAY "READ 2 " R " " ST
    CLOSE F
    STOP RUN.
```

## Environment

cobc (GnuCOBOL) 3.2.0 on WSL2 Ubuntu, `cobc --info`: indexed file handler BDB. `cobc -x -free -std=cobol2014 -o p
prog.cob && ./p`, run in an empty directory.

## Observed result

Exit code 0:
```
WRITE DUP 00
READ 1 01XX 00
READ 2 02XX 00
```

## Expected result (per ISO)

§2023:9.1.13.2 2): "I-O status = 02. The input-output statement is successfully executed but a duplicate key is detected."
Its item a): "For a READ statement with the NEXT phrase specified or implied, the key value for the current key of
reference is equal to the value of the same key in the next record in the physical file." Its item c): "For a REWRITE
or WRITE statement, the record just written created a duplicate key value for at least one alternate record key for
which duplicates are allowed." The second WRITE creates a second 'XX'; after the START on A, the first READ NEXT
returns 01XX and the next record in A order (02XX) has the same A, so 02; the second READ NEXT returns the last 'XX',
so 00. Status 02 and these cases are in the 2014 edition. Expected output:
```
WRITE DUP 02
READ 1 01XX 02
READ 2 02XX 00
```

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`) compiles it with no diagnostic and prints the expected
three lines (`WRITE DUP 02`, `READ 1 01XX 02`, `READ 2 02XX 00`), exit 0.

## Fix site

libcob/fileio.c. In `indexed_write_internal` (the WITH_DB arm), the secondary-key loop assigns
`COB_STATUS_02_SUCCESS_DUPLICATE` to a loop-local `ret` when `get_dupno` exceeds 1, and the same `ret` is then
overwritten by the `DB_PUT` result, so the 02 never reaches the caller. The READ NEXT path of the BDB handler has no
"next record has the same key" test; the 02 code for reads exists only in the ISAM handler arms, under
`COB_WITH_STATUS_02`. Read observationally in a 3.3-dev tree.

GnuCOBOL 3.2.0, WSL2 Ubuntu, indexed file handler BDB, `cobc -x -free -std=cobol2014 -o p prog.cob && ./p`.

With ALTERNATE RECORD KEY ... WITH DUPLICATES, a WRITE that creates a duplicate alternate key value returns file status
00, and READ NEXT along that key returns 00 even when the next record has the same key value.

ISO/IEC 1989:2014, I-O status 02 (9.1.13, "Successful completion"): "The input-output statement is successfully

alternate record key for which duplicates are allowed."

```

READ 1 01XX 02
READ 2 02XX 00
```

following `DB_PUT` result.
