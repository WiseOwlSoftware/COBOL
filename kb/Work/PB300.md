# PB300 — a clause with no standard behind it, and the user word it costs

Found by the citation-repair sweep ([[PB290]]) while re-deriving the grammar comments: `Core/CobolIO.g4`
announced an **"ISO §12.4.5.9 PADDING CHARACTER clause"**. `cite.py --check 12.4.5.9 "LOCK MODE"` → **OK
§12.4.5.9 (LOCK MODE clause)**. The comment was repaired by the sweep; the GRAMMAR was not, and that is this
note — which, on re-measurement at the landing, turned out to carry a **second and worse harm the sweep did not
name**.

## The measurement (2026-09-02, on the merged tree, with the built `cobol.dll`)

The file control entry's clauses are **§12.4.5.4 through §12.4.5.15**, and none of them is PADDING — the 2023
standard has no PADDING CHARACTER clause anywhere. The construct is a pre-2002 vendor/1985 surface;
`tests/version-matrix/reserved-words.json` agrees, and it is the key to both halves:
`PADDING` is `r85: true · r2002: true · r2014: false · r2023: false`.

**Harm 1 — UNDER-REJECTION.** A SELECT carrying `PADDING CHARACTER IS SPACE`:

| `--std` | outcome |
|---|---|
| 85 | accepted, no diagnostic |
| 2002 | accepted, no diagnostic |
| 2014 | accepted, no diagnostic |
| 2023 | accepted, no diagnostic |

`paddingCharacterClause : PADDING CHARACTER? IS? (literal | dataReference)` sits in `fileControlClause` with no
`{isXXXX()}?` predicate and no `constructs.json` row, so nothing gates it and nothing tells the user the clause
does nothing. It is parsed and ignored: it changes no output today.

**Harm 2 — REJECTS LEGAL SOURCE, and this one is a wrong answer to a legal program.** Because `PADDING` is a
lexer token that `cobolWord` does not admit, `01 PADDING PIC X(3) VALUE "ABC".` is a **parse error at
`--std 2014` and `--std 2023`**:

```
error COBOL0001: no viable alternative at input 'PADDING'
error COBOL0307: unexpected 'PADDING'. A period may be missing at the end of the previous sentence.
```

§8.9 does not reserve PADDING at 2014 or 2023, so that declaration is legal COBOL at both editions and the
compiler refuses it — the exact shape of [[PB301]], and the reason the two notes must be read together: a
declined or vendor construct may not cost the user the WORD.

## Why harm 1 is still a defect on its own

⛔ `docs/COBOLNET_DESIGN.md`'s dialect doctrine is two axes — version and STRICTNESS — and **every leniency is
dialect-gated**. This one is not: at `--std 2023` the compiler accepts a clause the targeted standard does not
contain, and a program relying on it silently gets no padding behaviour from a compiler that never said a word.
A user migrating a 1985 program has no way to learn from the compiler that the clause is gone.

## The fix shape (LANDED — see “Landed” below)

The two harms have ONE fix, and it must be taken as one:

1. **Removed-construct gating for the CLAUSE** — PADDING is a construct the standard REMOVED after 2002, so it
   belongs on `EditionContext.Removed`: an error under strict at 2014/2023, a warning with the pre-removal
   (no-op) reading under `--permissive`, with a `constructs.json` row and the mandatory edition-gate test sweep
   (`new-construct` skill). That puts the leniency on the strictness axis where the doctrine puts it, and it is
   the shape every other removed clause already uses. ⚠ Deleting the rule outright is the alternative, but only
   after MEASURING that no NIST or GnuCOBOL-differential program writes it — not assumed.
2. **A `cobol-words.json` nameSlot row for PADDING, reservation-gated** (`{!reservedHere("PADDING")}?`, the
   CRT/CURSOR precedent of [[PB301]] and the COMMIT/ROLLBACK precedent of [[PB137]]), so the word is a legal
   user-defined name exactly where §8.9 leaves it — 2014 and 2023 — and stays reserved at 85/2002. Regenerate
   with `scripts/gen-cobol-words.ps1` and pin both directions in a drift test.

⛔ Doing (1) without (2) leaves the parse error; doing (2) without (1) leaves the ungated clause. One token, two
arms (feedback_two_arm_dispatch).


## Landed 2026-09-05

**Both harms reproduced first, on this tree's own `cobol.exe`, before anything was changed** — harm 1 accepted
`PADDING CHARACTER IS SPACE` with no diagnostic at 85/2002/2014/2023, and harm 2 refused
`01 PADDING PIC X(3) VALUE "ABC".` with `COBOL0001 no viable alternative at input 'PADDING'` at all four,
including the two where §8.9 does not reserve the word. The note's own re-measurement held with one correction,
recorded below.

**Arm 1 — the clause is now on the STRICTNESS axis, where the doctrine puts every leniency.** Registry row
`padding-character-removed-2014` (introduced 85, removed 2014, `COBOLNET0902`) gated from
`VersionConformancePass.ParseArm.VisitPaddingCharacterClause` — the site every other removed clause already uses
(`VisitMultipleFileClause`, `VisitValueOfClause`, `VisitRerunClause`), so the severity decision stays in the one
`EditionSeverityPolicy` seam and nothing local tests `Permissive`. The clause still parses at every edition
(the superset shape) so the gate can NAME it instead of the user getting a parse error at the clause's own
literal. Nothing is captured on the `FileModel`, deliberately: COBOL.NET has no blocking model, so a stored
padding character would be a field nothing reads.

**Deleting the rule was MEASURED and rejected, exactly as the note demanded.** NIST `SQ216A` writes
`PADDING CHARACTER IS "9"` and `SQ217A` writes the operand form `PADDING PADDING-CHARACTER` (no `CHARACTER`, no
`IS`); both compile at `--std 85` and both have goldens in `tests/nist/valid/`. The 85/2002 accepted-inert
reading has to stay, which is the `MULTIPLE FILE` / `RERUN` posture of VCR Table 7 rows 7.6/7.15.

**⚠ THE NOTE'S EDITION CLAIM DID NOT HOLD AS WRITTEN, and the correction is load-bearing.** The note calls the
construct "a pre-2002 vendor/1985 surface" while quoting `reserved-words.json`'s own `r2002: true` in the next
sentence. Those disagree, and the flags are not by themselves proof either way: `SEGMENT-LIMIT` is
`r2002: true` yet its construct is `removed 2002` (Table 7 row 7.8), so GnuCOBOL's per-standard word lists can
keep a word reserved past the deletion of the construct that spelled it. The repo holds no 2002 or 2014 text
(ratified decision #1), so the edge is DERIVED and the derivation is stated in VCR row 7.20 so it can be
overturned in one line: a clause whose leading word is not a reserved word cannot be written, so `r2014: false`
puts the clause's disappearance at 2014 at the latest; and choosing `removedIn: 2014` — exactly where
`reservedHere()` stops reserving the word — is what keeps arm 1 and arm 2 from contradicting each other.
`removedIn: 2002` would have manufactured the `SEGMENT-LIMIT` shape here.

**Arm 2 — the word, and the ROOT CAUSE turned out to be one layer under the note.** `PADDING` is now a
`reservationGated` row in `tests/version-matrix/cobol-words.json`, so `cobolWord` admits it under
`{!reservedHere("PADDING")}?` exactly at 2014/2023. But the note's step 2 would have left the 85/2002 rejection a
raw parse error, because the DECLARATION half of reservation gating lived in a **hand-maintained list of two
words** — `{reservedHere("COMMIT")}? COMMIT | {reservedHere("ROLLBACK")}? ROLLBACK` inside `CobolData.g4`'s
`dataName`, mirrored by a hand-written `ctx.COMMIT() ?? ctx.ROLLBACK()` extraction in the funnel. Three places
naming one set, and it had ALREADY ROTTED: [[PB301]] made `CRT` and `CURSOR` reservation-gated and extended
neither, so `01 CRT PIC X.` at `--std 2002` answered `COBOL0001` and never named §8.9. `gen-cobol-words.ps1` now
emits a second generated rule `reservedGatedWord` from the SAME `reservationGated` flag, `dataName` has one
alternative instead of a list, and `VisitDataName` reads the subrule's own text (every alternative is a single
token) instead of enumerating words. The next gated word needs no edit in any of the three places
(CLAUDE.md rule 5). `PROCEDURE` stays a separate hand-written `dataName` alternative on purpose — it is
§8.9-reserved at every edition and NC205A legally names a data item with it, so it must never reach the funnel.
The duplicated §8.9 report that `VisitCobolWord` and `VisitDataName` each carried is now one
`FlagReservedUserWord`.

**Measured after.** `PADDING CHARACTER IS SPACE`: clean at 85/2002, `COBOLNET0902` at 2014/2023.
`01 PADDING PIC 9 VALUE 1.`: `COBOLNET0901 'PADDING' is a reserved word in COBOL-85 / COBOL-2002 and cannot be
used as a user-defined word (ISO §8.9)` at 85/2002, compiles clean at 2014/2023. `01 CRT PIC X.` at `--std 2002`
now reaches its declaration diagnostic too — the [[PB301]] sibling, fixed by the same structure.

**Evidence.** Registry rows `padding-character-removed-2014` and `user-word-padding-2014` put all four editions
× both harms through `VersionMatrixTests` (`Construct_MatchesEditionExpectation`,
`RemovedConstruct_CompilesPermissive_WithWarning`, `IntroducedConstruct_IsRejectedUnderPermissive`), which is
the mandatory edition-gate sweep. `tests/conformance/2014/pb300_padding_user_word` measures the legal-source arm
as OUTPUT rather than as "it compiled" — the plain name slot, a SUBSCRIPTED reference (the lexer trigger set's
own leg) and a qualified one. `tests/conformance/negative/pb300-padding-clause-dataname` writes the clause's
OTHER operand arm (SQ217A's bare data-name form) and so also measures that admitting `PADDING` to `cobolWord`
did not let a user-word reading absorb the clause and silence its gate. `CobolWordsDriftTests
.CobolWordsG4_ReservedGatedWord_Matches_Json_ReservationGated` pins the generated halves set-equal in both
directions and refuses a gated word that does not straddle a §8.9 boundary.

**No owner determination was found and none was needed.** `docs/CONFORMANCE.md` carries no PADDING row; per
CLAUDE.md rule 3 a decline with no owner decision behind it is not a decline, so the clause was implemented to
its edition window rather than declined.

**Diagnostic codes: NONE allocated.** `COBOLNET0902` (removed construct) and `COBOLNET0901` (§8.9 reserved word)
already existed and are the right codes; the range reserved for this landing was left unused.
