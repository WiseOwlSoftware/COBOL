# PB5784 - at --std 85 the abbreviated condition NOT NOT < is refused, where the 1985 rules make the first NOT the logical operator and the second part of the relational operator

**What is wrong.** `IF A > B OR NOT NOT < C` is refused at `--std 85` (`COBOL0001: cannot parse construct near 'NOT'`). By `§1985:VI.6.3.3 GRL2.1` the second NOT, followed by `<`, is part of the relational operator and the first is the logical operator, so the condition is `A > B OR NOT (A NOT < C)`; the same condition written `NOT IS NOT <` compiles. The checker's reasoning: 1985's abbreviation format is [NOT] [relational-operator] object and the operator table prints IS optional (pages 293 and 287 rendered), so `A > B OR NOT NOT < C` is [NOT] + `NOT <` + object. GRL2.1: the first NOT is followed by NOT, not GREATER, `>`, LESS, `<`, EQUAL or `=`, so "otherwise" (GRL2.2) it is the logical operator; the second NOT is followed by `<` and is part of the operator. The expansion is (A > B) OR (NOT (A NOT < C)); the result of insertion holds no NOT NOT pair (SR2, Table 1). The parser predicate adds NOT as a seventh word to GRL2.1's six, so no parse exists; the IS-spelled twin compiles and prints the right answer. At 2023 the refusal is right (`§2023:8.8.4.12.4 GR1`: NOT cannot immediately precede an extended-relational operator), so the cause is (a): 85 needs its own arm. kb/Work PB5123's landing (`kb/Work/PB5123/2026-11-14-landed.md`) asserts "`NOT NOT > C` ... stay COBOL0001 at 85, correctly" without argument. The inventory's KEPT reason assigns the NOT NOT case to sibling row `1985-GR-VI.6.3.3-L2.2`, which shares the mechanism.
