# PB323 — the presence probe the PB140 sweep replaced everywhere but here

**Rows:** `GR-14.9.27.4-3`.

## The program

`<lane3 scratch>/out-b1/probe/gr3-authority/` — create `locked/secret.dat`, then
`icacls locked /inheritance:r /grant:r "<user>:(F)"` followed by `icacls locked /deny "<user>:(RX)"`
(restore with `/remove:d` + `/inheritance:e`). `p.cob` declares `SELECT FP ASSIGN TO "locked/secret.dat"` and
`SELECT OPTIONAL FQ` over the same path, and opens both INPUT.

## The rule

> §14.9.27.4 GR3: If the file associated with file-name-1 is present and insufficient authority exists to open
> the file, the execution of the OPEN statement is unsuccessful, and the I-O status value in the file connector
> referenced by file-name-1 is set to '37'.

`--check 14.9.27.4 "insufficient authority exists to open the file"` → **OK**. Both opens must be unsuccessful
with '37'. Table 18's *file is available* predicate (*physically present and recognized by the operating
environment*) is likewise not satisfied by an authority failure.

## What the compiler does

Non-optional `OPEN INPUT` = **'35'** (file not present); OPTIONAL `OPEN INPUT` = **'05'** — a SUCCESSFUL open —
and the first READ reports AT END '10'. So a program is told a file it merely lacks authority to read does not
exist, and the OPTIONAL arm then invents an empty file. The .NET behaviour was confirmed on the same path:
`File.Exists` returns `False` while `File.GetAttributes` throws.

`FileRegistry.DeleteFile` already documents the mechanism verbatim: *File.Exists swallows every access error and
answers false, classifying a PRESENT-but-unobservable file as gone — GR16 requires '37' there — so the probe is
File.GetAttributes, whose failures DISTINGUISH the two (PB140).* This is the OPEN arm that sweep never reached,
in three connectors.

**Code sites:** `SequentialConnector.cs#OpenCore` (line 210) · `RelativeConnector.cs#OpenCore` (line 96) ·
`IndexedConnector.cs#OpenCore` (line 126) · contrast `FileRegistry.cs#DeleteFile` (lines 462-465).

## The fix shape

ONE shared presence probe returning `present / absent / unauthorized`, used by DELETE FILE and by all three
`OpenCore` bodies, rather than three hand-written `File.Exists` calls plus one correct one — and a drift test
asserting no `File.Exists` survives in `src/Cobol.Net.Runtime/IO`.

## Landed

The presence question now has ONE site and THREE answers. `HostFile.Probe` (`src/Cobol.Net.Runtime/IO/FileSupport.cs`) returns `FilePresence.Absent` / `Present` / `Unauthorized` from
`File.GetAttributes`, whose FAILURES carry the distinction `File.Exists` collapses: a missing file or directory is
§9.1.13.6 item 5's '35', a refused one is §14.9.27.4 GR3's '37'. Every other `IOException` propagates, so §9.1.13.6
item 1's '30' stays mapped in exactly one place.

`FileConnector.Open` takes that probe ONCE per OPEN, answers GR3 from it above the organizations, and hands the
result down as `OpenCore(mode, presence)` — so no connector re-asks the host, no two probes in one statement can
disagree, and the next organization gets GR3 for free. GR10's comparison and GR17's creation arm now test `Present`
and `Absent` explicitly rather than a boolean that meant neither.

**OUTPUT is deliberately outside the short-circuit, and that exclusion is required.** GR18 makes OUTPUT a creation
that never consults presence, §9.1.13.6 item 5 is defined only *"for an OPEN statement with the INPUT, I-O, or
EXTEND phrase"*, and a directory this process may WRITE but not LIST legitimately accepts a new file (measured on
the repro path: create OK, truncate-existing `UnauthorizedAccessException`). A blanket '37' would have rejected an
OPEN OUTPUT the operating environment carries out perfectly. An OUTPUT over a present-and-refused file still reaches
'37', through the creating stream's own exception and `Open`'s catch.

**Swept, all ten sites.** The three `OpenCore` bodies and `FileConnector.Open`'s own second `File.Exists` (the same
question asked twice in one statement); both keyed `Load` bodies and `SequentialConnector.SeedSharedWriteBase`, whose
"absent loads empty" guard must key on Absent alone; `NoticeIfLayoutDisagrees`, which read `.Exists` off a var-named
`FileInfo` — the shape the drift guard's first regex sailed past; the `FixedFileAttributes.Load` sidecar pre-check,
deleted outright as pure duplication of its own catches; and `FileRegistry.DeleteFile`, which had carried the only
correct copy of this rule since PB140 and now shares it instead of restating it.

**Probe, before and after** (a file under a directory whose DACL denies the running user):

| | before | after |
|---|---|---|
| sequential, non-optional, OPEN INPUT | 35 | **37** |
| sequential, OPTIONAL, OPEN INPUT | 05 + first READ 10 | **37** |
| relative, non-optional, OPEN INPUT | 35 | **37** |
| indexed, non-optional, OPEN INPUT | 35 | **37** |

A genuinely ABSENT file inside the same denied directory still answers '35' — the fix does not over-fire.

**Tests.** `unit:FileAuthorityPresenceTests` establishes the GR3 precondition for real (a DACL deny ACE on Windows,
mode 000 on Unix) and proves the denial took with a raw `File.OpenRead`, never with the subject under test; no
conformance golden can reach this arm, because the corpus runner compiles a `.cob` and compares output with nowhere
to express "first make this file unreadable". Eight of its assertions were shown to FAIL with the GR3 short-circuit
disabled. `conformance:2023/pb323_open_presence_arms` pins the probe's other two answers across all three
organizations and both OPTIONAL states — the regression net for the refactor itself. `unit:FileExistenceProbeDriftTests`
keeps the probe singular, and flags all ten pre-fix sites when run against `000b6242`.

`GR-14.9.27.4-3` re-verdicted DIVERGES → CONFORMS (GAP 2845 → 2844). Its `editions` field also carried `85,2002,2014`
while its own notes adjudicated all four; corrected to `85,2002,2014,2023`, which is what `docs/CONFORMANCE.md` §3
determines for this status. Docs updated in the same change set: `DESIGN-runtime-library` §2.2 (the probe is now a
named design point and the `OpenCore` signature matches the code), `CONFORMANCE.md` Annex A.3 item 11 and the §3
'37' bullet.
