# PB4203 — constructs.json holds the merge queue the way diagnostics.json and the inventory did

**Sites:** `.gitattributes:44` (the `merge=cobol-keyed-constructs` line), `scripts/merge_drivers.py:431`
(`DRIVERS`: the `Driver("cobol-keyed-constructs", ...)` entry), `tests/version-matrix/constructs.json` (whole: split into one
file per row), and every reader of the file (find them with a grep for `constructs.json` in `scripts/`, `tests/` and
`src/`; each changes in the same change set, with no loader kept for the old single file).

**The mechanism.** GitHub's merge queue merges without the repository's merge drivers. A file that needs a driver therefore
conflicts there, and `enqueue.py land` holds every other branch that changes it at exit 16 DRIVER FILE QUEUED while one
pull request that changes it is open. PB4147 removed the hold for `diagnostics.json` (one file per refusal) and PB4148 for the
traceability inventory (one file per row); `constructs.json` is the remaining file in the driver set that carries rows
(`publicapi` is the other driver and is a symbol set). No open note covers it (grep of `kb/Work` for `constructs.json`
with the merge driver, exit 16 and DRIVER FILE QUEUED found PB3642, PB4147 and PB4148, all landed).

**Fix direction.** Split `constructs.json` the same way: one file per construct row, a loader that reads the directory, the
`DRIVERS` entry and the `.gitattributes` line deleted in the same change, and a drift test that nothing is driver-merged
for a row file (PB4148's shape). The `new-construct` skill and `kb-sync` name the file; update them in the same change.
