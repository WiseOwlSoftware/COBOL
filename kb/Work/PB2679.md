## Mechanism

The planner's declared set for a Delete note is its sites, the callers the member index finds and the files under
its site folders (`plan_wave.py --cluster`, `note_file_set`). A deleted member with ZERO callers has no caller file,
so the set is just its declaring file. But the wave contract (in every census note) says "the drift test that pinned
the thing goes with it", and the files that pin or narrate a dead member do so as TEXT, which no reference index
sees: `IntrinsicArgumentClassDriftTests` reads `IntrinsicBinder.cs` as a string and its doc comments named
`IntrinsicSig.ArgKind(int)`; the PB1 history comments in `IntrinsicBinder.cs`, `IntrinsicArgumentRules.cs` and
`DiagnosticCatalog.cs` named it too. An honest Delete (CLAUDE.md rule 6: docs and comments current in the same change)
therefore edits files the set never declared, and the landing check either stops it (outside the set) or, as here,
finds those files shared with long-open fix-lane dispatches.

## Fix shape

- `note_file_set` adds, for a Delete note's member, every tracked file under the campaign roots whose TEXT names the
  member by its qualified or `Type.Member` spelling (a word-boundary grep, not the member index), so the comment and
  drift-test sweep the contract requires is inside the declared set and is checked against the in-flight sets at
  PLANNING time, where the collision costs nothing, instead of at the landing.
- Re-land PB2169 from `train1041-dropped-d-pb2169` once w1039B (PB1722), w1039F (PB2496, PB2497) and the `whand`
  entries naming PB1636, PB1701, PB175, PB468, PB1253, PB754 and PB1587 are terminal, or once the ledger shows they are
  no longer in flight; then delete the branch (O10).
