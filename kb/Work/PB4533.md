# PB4533 — divide-remainder-stored-after-quotient-size-error: DIVIDE ... REMAINDER stores the remainder when the quotient has a size error

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

In `DIVIDE ... GIVING q REMAINDER r ON SIZE ERROR ...`, when the quotient does not fit `q` (a size error on the
quotient), cobc leaves `q` unchanged, as required, but still computes and stores a remainder into `r`. ISO develops
and stores the remainder only if the size error condition is not raised, so `r` must keep its previous value.

## Minimal test case

Free reference format (`-free`).
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. DIVREM.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 Q PIC 99 VALUE 11.
01 R PIC 99 VALUE 5.
PROCEDURE DIVISION.
    DIVIDE 7 INTO 1000 GIVING Q REMAINDER R
        ON SIZE ERROR DISPLAY "SIZE ERROR Q=" Q " R=" R
        NOT ON SIZE ERROR DISPLAY "NO SIZE ERROR Q=" Q " R=" R
    END-DIVIDE
    STOP RUN.
```

## Environment

cobc (GnuCOBOL) 3.2.0 on WSL2 Ubuntu. `cobc -x -free -std=cobol2014 -o p prog.cob && ./p`.

## Observed result

Exit code 0:
```
SIZE ERROR Q=11 R=06
```

## Expected result (per ISO)

§14.9.12.4 6) (DIVIDE formats 4 and 5): "b) The quotient is then formed as specified in General rule 1 and stored in
identifier-3 as specified in 14.7.7, Arithmetic statements. c) If the size error condition is not raised, a subsidiary
quotient is developed that is signed and derived from the quotient by truncation of digits at the least significant end
and that has the same number of digits and the same decimal point location as the data item referenced by
identifier-3. The remainder is calculated as indicated in General rule 7 and is stored in the data item referenced by
identifier-4 ...". §14.9.12.4 7) defines the remainder from that subsidiary quotient: "the remainder is the result of
the arithmetic expression (dividend - (subsidiary-quotient * divisor))". The quotient 142 does not fit PIC 99, so the
size error condition is raised and Q is unchanged (the ON SIZE ERROR phrase is specified); no subsidiary quotient is
developed, so no remainder is calculated or stored, and R keeps 05.

The general size error rule §14.7.5 does not override this. Its rule 2 for a specified SIZE ERROR phrase leaves the
overflowing receiver unchanged ("the content of that resultant identifier is not changed from the content that existed
at the start of the execution of the arithmetic statement") and says "The values of resultant identifiers for which the
size error condition did not occur are the same as they would have been if the size error condition had not existed for
any of the resultant identifiers." For DIVIDE REMAINDER the specific rule §14.9.12.4 6) c) makes the remainder's
existence conditional on the quotient's size error not being raised, and that condition would have no effect if the
general rule supplied a remainder anyway. cobc's 06 is 1000 - 142 * 7, the remainder from the full quotient 142, which
is not the §14.9.12.4 7) remainder under either reading: the subsidiary quotient has the two digits of Q. The rules are
in the 2014 edition. Expected output:
```
SIZE ERROR Q=11 R=05
```

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`) compiles it with no diagnostic and prints
`SIZE ERROR Q=11 R=05`, exit 0.

## Fix site

libcob/numeric.c (read in the GnuCOBOL 3.2 source): `cob_div_quotient` stores the quotient with
`(void)cob_decimal_get_field (&cob_d1, quotient, opt)`, discarding its size-error result, then computes the remainder
into `cob_d_remainder` regardless, from the quotient truncated to Q's scale but not to Q's number of digits. It marks `cob_d_remainder` with
`COB_DECIMAL_NAN` (which makes the later `cob_decimal_get_field` in `cob_div_remainder` skip the store) only for a zero
divisor, so after a size error on the quotient `cob_div_remainder` stores the remainder anyway. The two calls are
emitted by cobc/typeck.c (`cob_div_quotient`, then `cob_div_remainder`).

## Draft issue

**Title:** DIVIDE ... REMAINDER stores the remainder when the quotient has a size error

GnuCOBOL 3.2.0, WSL2 Ubuntu, `cobc -x -free -std=cobol2014 -o p prog.cob && ./p`.

`DIVIDE 7 INTO 1000 GIVING Q REMAINDER R ON SIZE ERROR ...` with Q PIC 99: the quotient 142 does not fit, Q stays
11, but R is set to 6. ISO/IEC 1989:2014 (DIVIDE general rule 6 c), formats 4 and 5): "If the size error condition is
not raised, a subsidiary quotient is developed ... The remainder is calculated ... and is stored in the data item
referenced by identifier-4". With a size error on the quotient, R must be unchanged.

Observed:
```
SIZE ERROR Q=11 R=06
```
Expected:
```
SIZE ERROR Q=11 R=05
```
In libcob/numeric.c, `cob_div_quotient` discards the size-error result of storing the quotient and suppresses the later
`cob_div_remainder` store (COB_DECIMAL_NAN) only for a zero divisor, not for a size error on the quotient. The stored 6
is 1000 - 142 * 7, the remainder from the full quotient, not from a two-digit subsidiary quotient.

Program (free format):
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. DIVREM.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 Q PIC 99 VALUE 11.
01 R PIC 99 VALUE 5.
PROCEDURE DIVISION.
    DIVIDE 7 INTO 1000 GIVING Q REMAINDER R
        ON SIZE ERROR DISPLAY "SIZE ERROR Q=" Q " R=" R
        NOT ON SIZE ERROR DISPLAY "NO SIZE ERROR Q=" Q " R=" R
    END-DIVIDE
    STOP RUN.
```
