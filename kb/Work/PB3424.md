# PB3424 — --permissive coercion of a variable-length group as a function argument aborts at run time

Source: w1120c implementer lead, carried by w1128b (PB3358's "Landed" section calls it "a separate lead, not this mechanism").
Grepped `kb/Work` for `GroupImage`, `permissive`, `UPPER-CASE`, `Tier-C`, `COBOLNET1627`: PB3358 (landed) records the symptom in one sentence and no
open note owns it; PB2074 / PB2079 own the strict-mode COBOLNET1627 refusal, not the permissive path.

**Symptom.** Without `--permissive`, `FUNCTION UPPER-CASE (PG)` over a variable-length group draws COBOLNET1627 (a group is not a
class-alphanumeric operand under ISO 15.3). Under `--permissive` the source is non-standard: the compiler coerces the group
to a string argument, warns, and the program then aborts at run time with `NotImplementedCobolFeatureException`
(the Tier-C byte island), with or without a pointer/object-reference leaf. Severity MINOR: the source is not legal COBOL
and `--permissive` is the opt-in; the defect is that a coercion the compiler chooses to accept ends in a run-time abort
instead of an image (or a compile-time refusal).

**Repro.** `E:\COBOL-coord\scratch\w1120c\run\P6.cob` (PG holds `05 PA PIC X DYNAMIC LENGTH LIMIT IS 10` and `05 PN PIC 9(2)`;
`MOVE FUNCTION UPPER-CASE (PG) TO WS-X`), compiled with `--permissive`. NOT re-probed by the clerk (carried from w1120c / w1128b).

**Code sites** (verify before editing). `OperandText.AsString` (`src/Cobol.Net.Compiler/CodeGen/Emit/OperandText.cs:63`) renders the
group operand through `PlaceRenderer.GroupImage` (`src/Cobol.Net.Compiler/CodeGen/Roslyn/PlaceRenderer.cs`), which for a
variable-length group not gated by the current-extent capability reaches the Tier-C island. The fix shape: route the
permissive coercion through the current-extent image (`DataItem.CurrentExtentTransferImageCapable`, the one-way sending law PB3358 made the single
reference-tolerant capability) so the coerced string is the group's current image, or refuse it at bind with a diagnostic.

**Sibling sweep for the fixer.** Every `OperandText.AsString` caller that can receive a group under `--permissive` (other
intrinsics taking an alphanumeric argument: LOWER-CASE, REVERSE, TRIM, LENGTH, NUMVAL), over a fixed group, a variable-length group and a variable-length strong typedef group.

## Landed (2026-10-19, w1130 group A)

**Re-probe.** On a fresh Debug build of main fae388908, `P6.cob` under `--permissive` warned COBOLNET1627 twice and aborted at run time with `NotImplementedCobolFeatureException: whole-group image of 'PG' with a dynamic-length / dynamic-capacity member ... the Tier-C byte island`. The strong typedef twin (`WS-G`, with an object-reference leaf) died the same way. The sibling sweep found the same abort one position over: a variable-length group in a NUMERIC position (`FUNCTION ABS (PG)`, `COMPUTE X = PG + 1`, `ADD PG TO X`) died with "numeric use of group item 'PG' ... Tier-C byte island".

**Root cause.** One question, "what are this group's characters", answered three ways. DISPLAY (`AcceptDisplayEmitter`) carried the variable-length arm inline (`VarGroupCurrentImage`, gated on `CurrentExtentTransferImageCapable`); `OperandText.AsTransferString`, the reader the function-argument visitor (`StrArgVisitor.Visit(BoundFieldOperand)`) asks, had only the fixed-group pointer-leaf arm, so a variable-length group fell through to `AsString` and `GroupImage`'s Tier-C refusal; `NumericRenderer.FieldNumCore`'s group arm went through `SendingGroupValue` and the same refusal (its comment said a variable-length group "stays loud even under --permissive").

**Fix.** `PlaceRenderer.VarGroupOperandImage(place, context, transfer)` is the one reader (the DISPLAY arm's predicate and image, moved, with the `RedefViewPlace` exclusion and its `VarGroupWindow` exception). `AsTransferString` asks it (transfer true) and DISPLAY now calls `AsTransferString` alone, so DISPLAY and a function argument cannot differ; `FieldNumCore` asks it too, and passes `transfer: true` to `SendingGroupValue` (a new flag) for the fixed arm: a group holding a class pointer or object leaf, fixed or variable-length, was also loud in a numeric position (`COMPUTE X = G + 1` over a strong typedef group with an object-reference leaf aborted in the Tier-C island, found by the sweep), and a digit decode never reads the characters back, so the leaf is its placeholder (no digit) exactly as DISPLAY shows it. `VariableLengthBoundaryDriftTests` pins that the consumers read through the one reader and that DISPLAY keeps no gate of its own. Both coercions are `--permissive` only (ISO 15.3 admits a variable-length group as a function argument only where the function says so, 8.8.1.1 bars a group arithmetic operand); the image is the A.1 item 57 current-extent image, documented in the DOC-A.1-57 row, which now names the two coercions and their witnesses.

**Sibling sweep.** Walked every `OperandText.AsString` caller that can meet a group under `--permissive`: the intrinsic string arguments (UPPER-CASE, LOWER-CASE, REVERSE, TRIM, CONCAT, NUMVAL, ORD) over a fixed group, a scalar variable-length group, a group holding an OCCURS DEPENDING table beside a dynamic-length member, a group holding a dynamic-capacity table and a strong typedef group with an object-reference leaf; the numeric position (ABS, COMPUTE, ADD). STRING/INSPECT/relation operands are statements, not coercions, and the binder refuses a variable-length group there in strict (COBOLNET2492 for a comparison with a non-group). LENGTH and BYTE-LENGTH keep their own sum (`IntrinsicRenderer` ByteLength arm).

**Tests.** `VariableLengthGroupArgumentPermissiveTests` (Conformance, 8 cases): strict refuses (COBOLNET1627 / COBOLNET0844), the permissive string lane for the five shapes against hand-derived A.1-57 images, the numeric lane (1206 / 1206 / 1207 / 2413), the strong-typed reference-leaf group against the image DISPLAY shows, and its fixed and variable-length numeric decode (1206 / 1206). The conformance-suite manifest runs strict only, so a permissive run-time golden lives here, as for `FloatIntegerArgumentPermissiveTests`; the strict negative is the standing `15.3-Arguments/pb124-vlg-function-argument`.

**Review round 1 (w1130 finisher).** (R1-1) CONVERT's ANY source (`IntrinsicRenderer.StorageArg` -> `OperandText.AsStorageImage(transfer: true)`)
over a variable-length group still aborted in the Tier-C island: `AsStorageImage`'s group arm now asks `PlaceRenderer.VarGroupOperandImage` for a
one-way consumer, test `ConvertAnySource_IsTheCurrentExtentImageDisplayShows`. (R1-2) The "placeholder contributes no digit" wording holds for an
object-reference leaf and a NULL pointer only; a non-NULL POINTER leaf transfers its address-token image, whose bytes may be digit characters.
Wording corrected in `NumericRenderer.FieldNumCore`, the DOC-A.1-57 row and the DEVLOG entry; `StronglyTypedGroupWithANullPointerLeaf_...` pins the NULL case.

**Review round 2 (w1130 finisher).** (R2-1, blocking) The round-1 fix made CONVERT ANY, the raw-STORAGE channel (15.19.3 r7), return the current-extent
character image for any variable-length group. That image is the storage only where every member is composed as the bytes it occupies: a dynamic-length
NATIONAL item (and a dynamic-capacity table of national elements) is composed character for character (A.1 item 63), so `QG` = `N"xy"` + `PIC 9(2)` read
`78793036` where the storage is `007800793036` (a loud abort had become a silent wrong value). `DataItem.CurrentImageIsStorageImage` states the fact once and
`AsStorageImage`'s one-way arm asks it before the reader, so such a group stays at the named run-time loud for that source. Tests:
`ConvertAnySource_FixedNationalMemberRidesAsItsUtf16Bytes` (control), `ConvertAnySource_DynamicNationalMemberStaysLoud` (item and table), `ConvertAnySource_DynamicNationalItemItselfIsItsUtf16Bytes`.
**Found, too large for this slice (a lead, no id allocated):** A.1 item 57 says `LENGTH(G)` equals the displayed width with no exception, but for a group holding a
dynamic-length national item the width DISPLAY shows (`xy06`, 4) differs from `BYTE-LENGTH (QG)` (6); the cause is the contiguous record image of A.1 item 63
(one character a position), so making the group image carry UTF-16BE bytes is a record-framing redesign (`ContiguousLayout`, `CobolContiguousLayout`, the Dyn carrier). The DOC-A.1-57 row now records the divergence.
