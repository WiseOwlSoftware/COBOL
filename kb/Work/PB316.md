# PB316 — one OPEN phrase, every file in the statement

**Rows:** `FMT-14.9.27.2`, `GR-14.9.27.4-20`, `GR-14.9.27.4-23`. Reported independently by three adjudication
parts (open-statement p1 M1, p2, p3) as three mechanisms; it is one, and this is that one note.

## The programs

All under `<lane3 scratch>/out-b1/probe/` — `open-p1/leak1.cob`, `leak2.cob`, `shrA.cob`, `shrB.cob`;
`openmulti/OPMUL01.cob`, `OPMUL03.cob`, `OPMUL04.cob`; `open-sharing-scope/p.cob` + `ctrl.cob`.

* **Wrong answer.** `leak1.cob` writes the GR20 reference form — `OPEN INPUT FA` and then, as a separate
  statement, `OPEN INPUT SHARING WITH NO OTHER FB` — and prints `A=00 B=00`. `leak2.cob` writes the identical
  thing as ONE statement with two groups — `OPEN INPUT FA INPUT SHARING WITH NO OTHER FB` — and prints
  `A=00 B=61`. In `open-sharing-scope/p.cob` (`OPEN INPUT FA I-O SHARING WITH ALL OTHER FB.`) FA's declared
  `SHARING WITH NO OTHER` is destroyed: both files report `00` where the control (phrase removed) reports
  `FB=61`.
* **Legal source rejected.** `shrA.cob` is `OPEN OUTPUT SHARING WITH ALL OTHER F1 OUTPUT F2` where F2 has
  neither a SHARING clause nor a LOCK MODE clause: rejected `COBOLNET1512`. `shrB.cob` is the SAME two groups
  in the other order and compiles clean. `OPMUL01.cob` is the same shape and is rejected naming FB, whose group
  carries no sharing phrase at all.
* Reproduces at `--std 2002`, `2014` and `2023`; at 85 the construct is edition-gated first (COBOLNET0900).

## The rule

§14.9.27.2's general format nests `[sharing-phrase]` and `[retry-phrase]` INSIDE the outer repeatable group,
beside the file-names they govern: `{ open-mode } [ sharing-phrase ] [ retry-phrase ]
{ file-name-1 [ WITH NO REWIND ] } ...`, the outer group carrying the trailing ellipsis.

§14.9.27.4 GR20 settles the semantics:

> If more than one file-name is specified in an OPEN statement, the result of executing this OPEN statement is
> the same as if a separate OPEN statement had been written for each file-name in the same order as specified in
> the OPEN statement.

> These separate OPEN statements would each have the same open mode specification, the sharing-phrase,
> retry-phrase, and REWIND phrase as specified in the OPEN statement.

`python scripts/spec/cite.py --check 14.9.27.4 "the result of executing this OPEN statement is the same as if a
separate OPEN statement had been written for each file-name"` → **OK**, and the second sentence likewise → **OK**.

The OPEN MODE is unarguably per-group — that is what a multi-group OPEN is FOR — so the phrases listed beside it
are per-group too. §14.9.27.4 GR23's third sentence bounds the other direction: where a file has no sharing
phrase of its own, *"file sharing is completely specified in the file control entry"* (`--check 14.9.27.4` →
**OK**), so FA in `leak2` must not acquire FB's mode. Therefore `leak2` must print exactly what `leak1` prints,
and `shrA` and `shrB` — two orderings of one repeated group — must get the same compile verdict.

## What the compiler does

`SequentialIoBinder.BindOpen` declares `SharingMode? sharing = null; RetrySpec? retry = null;` **outside**
`foreach (var clause in o.openClause())`, assigns them from whichever clause carries the phrase, never resets
them at a group boundary, and returns one `new BoundOpen(opens) { SharingOverride = sharing, Retry = retry }`.
`BoundOpen`'s own XML doc states the wrong model as if it were the design: *"Applies to every file in the
statement."* `SequentialIoEmitter.EmitOpen` then computes `bool shared = o.SharingOverride is not null ||
o.Retry is not null` ONCE, outside the per-file loop, and routes every file through `FileOpenShared` with that
single override.

The two leaks have different shapes, and the asymmetry is the fingerprint of a scalar standing in for a
per-group value: the BIND leak is forward-only (later groups see an earlier group's phrase, which is `shrA`),
while the EMIT leak is order-independent (files written BEFORE the phrase are affected too, which is `shrB`).
It also escapes the statement: `FileRegistry.OpenShared` does `if (!_connectorShares.ContainsKey(name))
RegisterSharing(name, FileSharing.AllOther, FileLockMode.None, false)`, so a file that inherited a phrase it
never carried becomes sharing-active — and its streams switch to `FileShare.ReadWrite` — for the rest of the run.

**Code sites:** `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SequentialIoBinder.cs#BindOpen` (lines 22-48) ·
`src/Cobol.Net.Compiler/Binding/Bound/BoundTree.cs#BoundOpen` ·
`src/Cobol.Net.Compiler/CodeGen/Verbs/SequentialIoEmitter.cs#EmitOpen` ·
`src/Cobol.Net.Compiler/Binding/Validation/StatementValidation.cs#CheckOpenSharingAllOther` (the COBOLNET1512
site the leaked value reaches) · `src/Cobol.Net.Runtime/IO/FileRegistry.cs#OpenShared`.

## The fix shape (CLAUDE.md rule 5)

The phrases belong on a PER-GROUP record, not on the statement. `BoundOpen.Files` becomes
`(FileModel File, BoundOpenMode Mode, SharingMode? Sharing, RetrySpec? Retry, bool NoRewind, string? Unsupported)`
— the general format's own shape — `BindOpen` declares `sharing`/`retry` INSIDE the `openClause` loop, and
`EmitOpen`'s per-file loop reads its own values. That single change also gives PB317 (the NO REWIND phrase) and
PB318 (SR5/SR6, which pair NO REWIND with the open mode) the per-group carrier they need, so all three land
together. Pair it with a drift test asserting that a multi-group OPEN carrying a phrase in one group leaves the
other groups' files at their file-control sharing, and that no `BoundOpen` field is statement-scoped except the
statement itself.

## Landed — 2026-09-05

**THE PHRASES ARE NOW WHERE THE GENERAL FORMAT PUTS THEM, AND THE STATEMENT HAS NO PHRASE STATE AT ALL.**
`BoundOpenFile(FileModel File, BoundOpenMode Mode, SharingMode? Sharing, RetrySpec? Retry, string? Unsupported)`
(new, `BoundTree.cs`) is one entry per file-name, and `BoundOpen` is nothing but a list of them — the
`SharingOverride` and `Retry` properties are GONE from the statement node, so no consumer can re-broaden a
phrase's scope. That shape is not a convenience: it is §14.9.27.4 GR20's own normal form, "a separate OPEN
statement … for each file-name in the same order as specified in the OPEN statement … each hav[ing] the same
open mode specification, the sharing-phrase, retry-phrase, and REWIND phrase as specified in the OPEN
statement", so the rule is executed by the data structure rather than restated by its consumers.
`BindOpen` declares `sharing`/`retry` INSIDE the `openClause` loop; `EmitOpen`'s per-file loop computes its own
`bool shared` from that file's entry. The general-format DIAGRAM was RE-RENDERED from the PDF (page 705) rather
than read from the transcription, because it is the whole argument: the OUTER brace pair encloses
`{open-mode} [sharing-phrase] [retry-phrase] {file-name-1 [WITH NO REWIND]} …` and carries the trailing
ellipsis. The transcription's figure note matches the printed page.

**Both halves were re-probed on this tree's own `cobol.exe` before anything was changed, and both reproduced.**
`OPEN INPUT FA INPUT SHARING WITH NO OTHER FB` printed `A=00 B=61` where its GR20 reference form printed
`A=00 B=00`; `OPEN OUTPUT SHARING WITH ALL OTHER F1 OUTPUT F2` (F2 with no LOCK MODE clause) was rejected
`COBOLNET1512` while the same two groups in the other order compiled clean. After the fix all four agree.

**Goldens.** `conformance:2002/pb316_open_group_scope` writes every arbitration TWICE — once as separate OPEN
statements, once as one statement with the same groups — and requires the two to print the same I-O statuses,
which asserts GR20 directly and leans on no implementor-defined default. Its `61`s are derived from Table 19
(row `SHARING WITH ALL OTHER` / INPUT against column *sharing with no other* = "Unsuccessful open", §9.1.13.9
item 1). The RETRY phrase gets its own observable, because its leak has no status of its own: a file in a
phrase-less group was being made a sharing participant for the rest of the run, so a LATER open arbitrated
against a different set. Two negatives guard the complement: `negative/pb316-open-sharing-all-no-lockmode` keeps
SR8 firing when the ALL phrase is on the file's OWN group, and `negative/pb316-open-sharing-group-below-2002`
pins the 2002 introduction gate on a phrase written on a group other than the first. The positive golden was
FALSIFIED once — on the pre-fix compiler it does not even compile (`COBOLNET1512` on `F-C`), and with the SR8
part removed it prints the leak (`ONE-B=00` against `REF-B=61`).

**⛔ `GR-14.9.27.4-23` MOVED TO PB322 rather than closing.** GR23 has three sentences. Sentences (1) and (2) —
the phrase overrides only *file-name-1*'s file control entry, and with no phrase "file sharing is completely

`OPEN INPUT` then `OPEN OUTPUT` on one physical file answers `30` where every one of the three modes gives
Table 19's `61` (re-probed 2026-09-05). The row is now in PB322's `inventory_rows`, which is what keeps

**What this note said that did NOT survive contact.** Its fix shape put `bool NoRewind` on the per-group record.
It is not there: PB317 owns the NO REWIND phrase and its two rules, and a field with no consumer is a lookup
nothing contradicts. The carrier is shaped so PB317 adds `NoRewind` and PB318 adds its SR screens to
`BoundOpenFile` without touching any of this again. The note also called the two phrases "per-statement" in the
binder's own comment; that comment is now the citation for why they are not.
