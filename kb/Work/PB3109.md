# PB3109 — the lock directory goes delete-pending and a waiting hold answers Unavailable

> ⚙ **flags:** wrong-answer · silent

Source: `E:/COBOL-coord/scratch/reports/w1069c-PB2690-report.md`, "## New defects"; root-caused by the PR 19 finisher, round 4.

**Bounced PR 19.** It left GitHub's merge queue on merge-group run 38323871783 (2026-10-13 00:00Z): `RegionLocksDriftTests.TwoWaitingHoldsBothGetTheByteInTurn(kind: LockFiles)`, `Expected [Ok, Ok] Actual [Unavailable, Ok]`. Until this is fixed, any landing can bounce the same way.

**Harm.** Where it happens, `KeyedConnector.HoldStoreMutex` maps non-Ok to "no mutex" and the statement runs unprotected (the PB2936 lost-update shape); an OPEN can get a spurious '61'. The reach is limited and the report says so: lock-file hosts run only off Windows or off OFD-Linux, so a shipped program meets this only on a Windows-semantics lock directory such as an SMB share, which is unverified.

Report paragraph, verbatim:

**Lead (no id allocated; root-caused by the round-4 finisher; it bounced PR 19). Summary: on Windows the lock-file
host's LOCK DIRECTORY passes through DELETE-PENDING when its last holder closes, and a waiting hold that meets it answers
`Unavailable` instead of waiting.**
The last holder's CLOSE removes the empty lock directory (`SidecarLockFiles.LockFileHolder.Dispose`,
`src/Cobol.Net.Runtime/IO/Sharing/SidecarLockFiles.cs:170`, `Directory.Delete`). Windows' RemoveDirectory sets the delete
disposition and then closes its handle; between the two (and for as long as any other handle, an indexer's or a scanner's,
is open on the directory) the directory is DELETE-PENDING, and every open inside it and every listing of it is "access
denied" (0x80070005) while `Directory.Exists` still says true. The PB2917 fix (`Retire`: rename a lock FILE away before
deleting it, so "access denied" stays a decisive answer) was never applied to the DIRECTORY. Two sites then misread the state:
(1) `SidecarLockFiles.Publish` (`SidecarLockFiles.cs:92-98`): `CreateLockDirectory` is a no-op (the name exists) and
`HostFile.OpenLockHolder` (`src/Cobol.Net.Runtime/IO/FileSupport.cs:378`, `FileMode.CreateNew`) throws
UnauthorizedAccessException, which the retry catches at `SidecarLockFiles.cs:109-111` do not take, so it escapes to
`SidecarRegionLocks.Hold`'s catch at `SidecarRegionLocks.cs:114` -> `Unavailable`, whatever `wait` says;
(2) `SidecarRegionLocks.Look` (`SidecarRegionLocks.cs:152`) reads the access-denied listing as `Conflict.Unobservable` (the
PB2917 "may enter but not list" case) -> `Unavailable` for a waiting hold (`:92`, `:104`), `Held` for a non-waiting one.
Sibling: `SidecarColumnLockHost.Establish` (`SidecarColumnLockHost.cs:47-52`) reads the same escaping UnauthorizedAccessException
as "this user may not write the lock directory" and tests the others over the delete-pending listing: a spurious '61' for an
OPEN made just as another run unit CLOSEd, or `Unavailable` (the OPEN granted with no file lock).
**Measured** (standalone harness `E:\tmp\pb2690-regionlock-repro`, against this branch's `Cobol.Net.Runtime.dll`):
(a) DETERMINISTIC, any host speed, NTFS `C:` and ReFS `E:` alike: create the lock directory
(`SidecarLockFiles.LockDirectoryOf(file)`) empty, open it with `CreateFileW(DELETE|SYNCHRONIZE, share RWD,
FILE_FLAG_BACKUP_SEMANTICS)`, set `SetFileInformationByHandle(FileDispositionInfo, DeleteFile=1)` and keep the handle (the
deleter frozen between its two steps): `Hold(StoreMutexByte, exclusive, wait: true)` -> `Unavailable`, `wait: false` ->
`Unavailable`, the listing and a `CreateNew` inside -> UnauthorizedAccessException 0x80070005; after the handle closes,
`Hold(wait: true)` -> `Ok`. (b) The test's own shape (two endpoints, barrier, waiting exclusive holds) with CPU burners on NTFS:
5 of 1,500 rounds non-Ok, and exactly 5 first-chance `UnauthorizedAccessException 0x80070005 at HostFile.OpenLockHolder` (site 1).
**Reach:** the lock-file hosts are chosen only off Windows and off OFD-Linux (`RunUnitFileLock.cs:59-62`,
`HostRegionLocks.cs:151`), where an rmdir is atomic, so a shipped program meets it only on a lock directory served with Windows
delete semantics (an SMB share; unverified); but `KeyedConnector.HoldStoreMutex` (`KeyedConnector.cs:372-373`) maps any non-Ok to
"no mutex", so wherever it happens the statement runs unprotected (the PB2936 lost-update shape), and the Windows arm is the
contract `SidecarLockFiles`' remarks claim and `RegionLocksDriftTests` holds on every machine.
**Why the local gate passed it** (CI invariant, kb/Work PB1957): it RAN it. The class carries `[Trait("Host", "ReFS")]` (tier 0h),
and `TwoWaitingHoldsBothGetTheByteInTurn(kind: LockFiles)` is `outcome="Passed"` in all four of this branch's leg-1 runs
(`TestResults\build-local\20261012T224156Z-b6d530`, `...225022Z-f7026e`, `...232512Z-ecf59f`, `...233759Z-206672`). No leg,
pin or setting is missing: the witness is a repetition race (about 0.3 % per round under load, so a few % per 25-round run),
a coin flip at every gate; the implementer's own gate hit it once (the lead this paragraph replaces). The local-gate defect is
the missing DETERMINISTIC witness, shape (a), which fails every run.
**Fix direction:** model the directory as `Retire` models a file (no name a publisher or tester enters is deleted in place:
rename it to a retired name, then delete; or leave an empty lock directory standing where share modes are mandatory), so
"access denied" on the directory stays a decisive answer; add shape (a) as a `[Trait("Host", "ReFS")]` witness for both the
region host and the column host. Not this branch's: its footprint (`Values/CobolVarGroup.cs`, `Values/GroupCompatibility.cs`)
shares no code path with `IO/Sharing/`.
