# PB168

`__filesRegistered` is emitted as a per-INSTANCE field (ProgramEmitter, the registration guard in
DispatchEmitter's `__Activate`), and ProgramTable.CallProgram gives a RECURSIVE (or INITIAL) unit a FRESH
instance per activation — so every such activation re-runs `CobolFile.Register(...)`, and
`FileRegistry.Register` does `_files[cobolName] = new ...Connector(...)`, unconditionally REPLACING the live
entry. The displaced connector's StreamWriter/StreamReader is never disposed (dispose is only reachable from
Close), so the OS handle leaks and its buffered writes are lost.

CONSEQUENCE (recursive, non-INITIAL): §14.6.2.3.2 puts internal file connectors "in no open mode" only on
(1) first activation in the run unit, (2) an INITIAL program's activation, (3) after CANCEL — a second
activation of a RECURSIVE non-INITIAL program is §14.6.2.3.3 LAST-USED state and must keep its connector.
Today: a RECURSIVE program that OPENs F at depth 1 and recurses finds its connector replaced by a closed
stranger — the depth-2 READ/WRITE answers '42', and the resumed depth-1 activation's connector is gone. For
an INITIAL unit the re-registration is semantically the required re-initialization, but the REPLACE arm still
drops an open connector undisposed when the prior activation ended abnormally.

MASKING (recorded by the PB154 review fleet): `2023/pb154_cancel_initial`'s REOPEN=00 leg is
host-locking-dependent — on POSIX the next activation's re-registration hands back a fresh CLOSED connector
even if the CANCEL-time close never ran; only Windows' sharing violation ('30') discriminates. A fix here
should re-pin that leg in a host-independent way.

WHAT WOULD CLOSE IT: key the registration guard to the connector's true scope (the unit, not the instance —
a static flag for a RECURSIVE unit, per-activation only where §14.6.2.3.2 requires re-initialization), or
make Register close/dispose what it displaces; plus a golden where a RECURSIVE unit OPENs, recurses, and
WRITEs at both depths.
