# PB321 — the sharing table arbitrates only for the connectors it can see

**Rows:** `GR-14.9.27.4-4`, `GR-14.9.27.4-22`. Two independent holes in one arbitration, reported as two
mechanisms by open-statement p3; one fixer, one restructuring.

## Part 1 — sub-case (e) is missing, and the fall-through carries its letter

`<lane3 scratch>/out-b1/probe/open-output-conflict/p.cob` — FA and FB both `ASSIGN TO "shr1.dat"`, both
`SHARING WITH ALL OTHER` + `LOCK MODE IS MANUAL`; seed the file, `OPEN INPUT FA`, then `OPEN OUTPUT FB`.

> §9.1.13.9 1) e): An attempt is made to open a physical file in the output mode and the physical file is
> currently open by another file connector

`--check 9.1.13.9` → **OK**. I-O status '61'. Table 19's two OUTPUT request rows (SHARING WITH READ ONLY ×
OUTPUT, SHARING WITH ALL OTHER × OUTPUT) are *Unsuccessful open* in all five columns, and §14.9.27.4 GR25 then
requires the file to be unaffected.

**Observed:** `OPEN INPUT FA` = '00'; `OPEN OUTPUT FB` = '00', and the physical file FA still holds open is
truncated and rewritten. `FileRegistry.Conflicts` (lines 552-559) tests only the NoOther pair,
`ex.ReadOnly`-vs-non-input and `inc.ReadOnly`-vs-non-input; its final `return false;` carries the comment
`// (e) ALL OTHER` — the letter of the missing sub-case attached to the fall-through that causes it.

**A green test holds it open.** `unit:CobolFileLockTests.Conflicts_ClassifiesTable19` (lines 101-112) is 6
`InlineData` rows against Table 19's 35 cells, labelled '(a)'-'(e)', with **no row whose incoming mode is
Output**.

## Part 2 — the table is consulted only when the INCOMING connector is sharing-active

`<lane3 scratch>/out-b1/probe/open-noother-vs-plain/p.cob` — FA `ASSIGN TO "shr5.dat" SHARING WITH NO OTHER`,
FB the same path with no sharing or lock clause; seed, `OPEN INPUT FA`, `OPEN OUTPUT FB`, WRITE, CLOSE.
Contrast `open-default-sharing/p.cob`, where BOTH connectors are plain.

> §9.1.13.9 1) a): An attempt is made to open a physical file that is currently open by another file connector
> in the sharing with no other mode

`--check 9.1.13.9` → **OK**. §9.1.15 rule 1 says the same at file level. Table 19's first column is
*Unsuccessful open* for every request row, so FB's OPEN OUTPUT must be unsuccessful and the file unaffected.

**Observed:** FA='00', FB='00', and `shr5.dat` afterwards contains `CLOBBERED` — the record FB wrote over the
file FA holds exclusively. In the all-plain contrast run the same OPEN OUTPUT is refused at the OS layer and
reports '30'. **Declaring the most restrictive sharing mode made the file strictly less protected than declaring
nothing.** `FileRegistry.Open` (lines 174-180) gates `SharedOpenAttempt` on `IsSharingActive` (line 507), and
`RegisterSharing` (lines 498-504) sets `c.SharedStreams = true`, after which every connector opens with
`FileShare.ReadWrite` on the stated ground that *the Table-19 registry, not the OS handle, arbitrates* — true
only for connectors the registry actually sees.

## The fix shape

One restructuring closes both: **route EVERY OPEN through the physical-file registry**, registering an
unshared connector under the documented implementor default (which **PB322** must first make exist), so the
sharing table is the single arbiter for all connectors rather than an opt-in overlay. Derive `Conflicts` from
the five §9.1.13.9 sub-cases as a data-driven list, and drive the unit theory from all **35** Table-19 cells so
a missing arm cannot be green.

**Code sites:** `FileRegistry.cs#Conflicts` · `FileRegistry.cs#Open` · `FileRegistry.cs#IsSharingActive` ·
`FileRegistry.cs#RegisterSharing` · `FileConnector.cs#SharedStreams` ·
`tests/Cobol.Net.Tests.Unit/CobolFileLockTests.cs#Conflicts_ClassifiesTable19`.

## Landed — 2026-09-05

**Row `GR-14.9.27.4-4` DIVERGES → CONFORMS (GAP 2845 → 2844).** Both parts closed by one restructuring.
`GR-14.9.27.4-22` did NOT close and was **moved to `PB603`** rather than orphaned: PB321 fixed only the third
of that row's three divergences (the `SharedStreams` inversion), the first is PB316's SHARING-phrase-scope
hoist and the second is the missing CROSS-run-unit file lock, whose subject — the physical-file registry's
run-unit hygiene — is PB603's.

**Table 19 is now a STRUCTURE, not a predicate chain** — `src/Cobol.Net.Runtime/IO/Sharing/OpenTable19.cs`,
7 named rows × 5 named columns = 35 exhaustively-switched cells, the sibling of `Table14` (PB235).
`FileRegistry.Conflicts` is a lookup into it. The PRINTED page was rendered (PDF 707 / printed 677) and the
Markdown transcription proved faithful cell for cell.

⛔ **THE FIX SHAPE ABOVE WAS WRONG ON ONE POINT AND THE DESIGN WAS CORRECTED.** "Derive `Conflicts` from the
five §9.1.13.9 sub-cases as a data-driven list" would have shipped four NEW wrong cells. Read literally, those
five sub-cases do not reproduce Table 19: (c) and (d) say *"I-O or extend"* where the table's existing-side
column groups are `extend I-O output`, so they answer *Normal open* in four combinations the printed table
marks *Unsuccessful open* (an incoming SHARING WITH READ ONLY request against a connector open in the OUTPUT
mode). §9.1.15 rule 2 settles it for the table — *"unsuccessful if the physical file is associated with another
file connector whose open mode is other than input"* (`--check 9.1.15` OK) — and OUTPUT is a mode other than
input. `OpenTable19Tests.NineOneFifteenRules_ReproduceTheWholeTable` asserts the §9.1.15 prose reproduces all
144 (sharing, mode)² combinations and that the sub-case reading disagrees in **exactly four**, so the finding
cannot rot back into prose.

**PB322 was not decided.** `FileRegistry.ImplementorDefaultSharing` is the ONE place §9.1.15's implementor
default is named and it is `null` — UNDETERMINED. `Conflicts` arbitrates an undetermined mode **universally**:
a conflict only where EVERY candidate mode yields *Unsuccessful open*, so no '61' this compiler answers today
can be contradicted by PB322's answer. With both sides undetermined that leaves exactly §9.1.13.9 1) e), the
sub-case that names no sharing mode — which is what turns PB316's `IO-A=00 IO-B=30` probe (an OS sharing
violation leaking into the I-O status) into a deterministic `61`. The quantifier is extensionally identical to
substituting ALL OTHER, because ALL OTHER is Table 19's least restrictive row AND its least restrictive column
group; `UndeterminedDefault_ConflictsOnlyWhereEveryCandidateAgrees` pins that, so a PB322 landing that picks a
mode fails a test instead of silently changing every clause-less program.

**Two silent defaults were removed on the way**: the emitter registered a LOCK-MODE-only file as ALL OTHER (a
LOCK MODE clause is not a sharing specification, §9.1.15) and `OpenShared` registered a RETRY-phrase-only OPEN
as ALL OTHER — three arms of one determination, two of which had already answered it.

**Sweep.** Every OPEN entry is one `OpenCore` (which also drains the GC close queue for both arms, where only
the plain one used to); every CLOSE path deregisters from the physical-file table (`SharedClose`,
`CloseDisplaced`, `CloseAll`, `CloseAndDrop`), because a total registration needs a total release; the
registration is gated on the OPEN's STATUS rather than on `IsOpen`, so an already-open connector's '41' no
longer re-registers it under the failed request's mode. SORT/MERGE's implicit opens (§14.9.40 GR12a /
§14.9.24 GR7a) route through `CobolFile.OpenInput`/`OpenOutput` → `Open`, so Table 19's *"including those
implicitly opened by the SORT and MERGE statements"* is satisfied with no separate arm.

**Goldens.** `conformance:2002/pb321_table19_open_arbitration` (sub-cases a/b/e, the four-combination
disagreement, two permitted pairs, the '41' non-re-registration, GR25's *"the file is not affected"*, and the
CLOSE that releases the file lock) and `conformance:2023/pb321_default_sharing_arbitration` (two clause-less
connectors: INPUT/INPUT permitted, INPUT/OUTPUT `61`, file unaffected, then permitted after CLOSE).
`unit:CobolFileLockTests.Conflicts_ClassifiesTable19` — 6 `InlineData` rows against 35 cells with no OUTPUT
incoming mode, the green test that held this open — is deleted; `OpenTable19Tests` enumerates all 144 pairs.

⚠ **Residue, reported for an owner determination and not fixed here: the runtime has no edition.** The
arbitration therefore runs at `--std 85` too, where no SHARING clause is accepted, so the only conflict it can
raise is sub-case (e): a second OPEN OUTPUT now answers `61` where the OS accident used to answer `30`. Table 19
rides Annex A.4.7, a COBOL-2002 introduction, so whether a pre-2002 edition may report a value from the 2002
5x/6x family belongs to Annex A.1 item 77's determination family (PB322's). Nothing in the corpus exercises it —
the full `CorpusRunner` across all four editions and the 375 NIST cases are green.
