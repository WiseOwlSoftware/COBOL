# PB321 — the sharing table arbitrates only for the connectors it can see

**Rows:** `GR-14.9.27.4-4`, `GR-14.9.27.4-22`. Two independent holes in one arbitration, reported as two
mechanisms by open-statement p3; one fixer, one restructuring.

## Part 1 — sub-case (e) is missing, and the fall-through carries its letter

`<lane3 scratch>/out-b1/probe/open-output-conflict/p.cob` — FA and FB both `ASSIGN TO "shr1.dat"`, both
`SHARING WITH ALL OTHER` + `LOCK MODE IS MANUAL`; seed the file, `OPEN INPUT FA`, then `OPEN OUTPUT FB`.

> §9.1.13.9 1) e): An attempt is made to open a physical file in the output mode and the physical file is
> currently open by another file connector

`--check 9.1.13.9` → **OK**. I-O status '61'. Table 19's two OUTPUT request rows (SHARING WITH READ ONLY ×
OUTPUT, SHARING WITH ALL OTHER × OUTPUT) are *Unsuccessful open* in all five columns, and §14.9.27.4 GR25 then
requires the file to be unaffected.

**Observed:** `OPEN INPUT FA` = '00'; `OPEN OUTPUT FB` = '00', and the physical file FA still holds open is
truncated and rewritten. `FileRegistry.Conflicts` (lines 552-559) tests only the NoOther pair,
`ex.ReadOnly`-vs-non-input and `inc.ReadOnly`-vs-non-input; its final `return false;` carries the comment
`// (e) ALL OTHER` — the letter of the missing sub-case attached to the fall-through that causes it.

**A green test holds it open.** `unit:CobolFileLockTests.Conflicts_ClassifiesTable19` (lines 101-112) is 6
`InlineData` rows against Table 19's 35 cells, labelled '(a)'-'(e)', with **no row whose incoming mode is
Output**.

## Part 2 — the table is consulted only when the INCOMING connector is sharing-active

`<lane3 scratch>/out-b1/probe/open-noother-vs-plain/p.cob` — FA `ASSIGN TO "shr5.dat" SHARING WITH NO OTHER`,
FB the same path with no sharing or lock clause; seed, `OPEN INPUT FA`, `OPEN OUTPUT FB`, WRITE, CLOSE.
Contrast `open-default-sharing/p.cob`, where BOTH connectors are plain.

> §9.1.13.9 1) a): An attempt is made to open a physical file that is currently open by another file connector
> in the sharing with no other mode

`--check 9.1.13.9` → **OK**. §9.1.15 rule 1 says the same at file level. Table 19's first column is
*Unsuccessful open* for every request row, so FB's OPEN OUTPUT must be unsuccessful and the file unaffected.

**Observed:** FA='00', FB='00', and `shr5.dat` afterwards contains `CLOBBERED` — the record FB wrote over the
file FA holds exclusively. In the all-plain contrast run the same OPEN OUTPUT is refused at the OS layer and
reports '30'. **Declaring the most restrictive sharing mode made the file strictly less protected than declaring
nothing.** `FileRegistry.Open` (lines 174-180) gates `SharedOpenAttempt` on `IsSharingActive` (line 507), and
`RegisterSharing` (lines 498-504) sets `c.SharedStreams = true`, after which every connector opens with
`FileShare.ReadWrite` on the stated ground that *the Table-19 registry, not the OS handle, arbitrates* — true
only for connectors the registry actually sees.

## The fix shape

One restructuring closes both: **route EVERY OPEN through the physical-file registry**, registering an
unshared connector under the documented implementor default (which **PB322** must first make exist), so the
sharing table is the single arbiter for all connectors rather than an opt-in overlay. Derive `Conflicts` from
the five §9.1.13.9 sub-cases as a data-driven list, and drive the unit theory from all **35** Table-19 cells so
a missing arm cannot be green.

**Code sites:** `FileRegistry.cs#Conflicts` · `FileRegistry.cs#Open` · `FileRegistry.cs#IsSharingActive` ·
`FileRegistry.cs#RegisterSharing` · `FileConnector.cs#SharedStreams` ·
`tests/Cobol.Net.Tests.Unit/CobolFileLockTests.cs#Conflicts_ClassifiesTable19`.
