# PB720 — OPEN — the register's cheap validator cannot see a dangling row id

Raised 2026-09-06 by the PB697+PB698 implementer (report, "New defects", paragraph (c)) after re-keying 20
notes' `inventory_rows` through an inventory rebuild that moved 4,371 rows to 4,348. Re-measured here on `main`
at `c34f01ad`, and re-confirmed at `f86a5764`, which a parallel lander pushed mid-session (it re-verdicts
66 inventory rows and changes neither the row COUNT nor any subject named here).

⛔ **The report's premise does not survive the probe, and the correction is the note.** It says *"nothing checks
them"* and proposes `work.py check` as the guard. **Something does check them**, and it is worth knowing before
anyone writes a duplicate.

## What actually exists on main

`tests/Cobol.Net.Tests.Unit/DefectiveRowCoverageDriftTests.cs` carries **two** facts, not one:

- `EveryDefectiveRow_IsClaimedByALiveWorkNote` (`:189`) — the ROW→NOTE direction the report knew about.
- **`EveryInventoryRowsClaim_NamesARealRule` (`:209-217`)** — the NOTE→ROW direction, over the whole register
  and every claim, via `ClaimsNamingNoRow` (`:162-171`): *"A claim on a rule-id the inventory does not have. A
  typo here is worse than useless: it satisfies nothing while LOOKING like ownership."* It is proved to fail:
  `TheseChecks_ActuallyFail_OnAFabricatedRegister` (`:224`) drives the same pure functions over a hand-built
  register.

Measured on this tree
(`E:\Temp\claude\E--CobolSharp\49b17747-ce58-4386-8c49-ecb2ce644f8d\scratchpad\pb720_probe.py`):

```
inventory rows loaded  : 4371 | distinct ids: 4371
work notes loaded      : 766
frontmatter claims     : 1158 | naming no inventory row: 0
```

So the C# invariant holds right now, and **the 20 notes in PB698's re-keying would not have failed silently —
they would have turned the unit suite red.** That is the correction. The residue below is what is genuinely
missing.

## What is genuinely missing — three measured facts

**1. `work.py check` never reads the field.** `scripts/spec/work.py#check` (`:255`) validates: the four
required scalars, `kind` ∈ KINDS, `status` ∈ STATUSES, the H1 heading's status word agreeing with the
frontmatter, an open defect with no harm flag, duplicate ids, and `check_base_agrees()`. `inventory_rows` is
named nowhere in it. The check that is missing is an **existence check per claimed id**, and it would go in
`check()`'s per-item loop, beside the harm-flag check, as a pure helper `check_rows_exist(items)` returning
`bad` lines the same way `check_base_agrees()` does — so the failure is reported **by note id**, which is what
a fixer needs and what the C# report already gives (`f"{n.File}: inventory_rows names '{claim}', which is not
a rule-id in the inventory"`).

**2. The module docstring justifies the omission with a test that answers a different question.** `work.py`'s
own docstring says:

> ⛔ The field is enforced by `DefectiveRowCoverageDriftTests` (tests/Cobol.Net.Tests.Unit) and NOT here, on
> purpose: … validating a rule-id against the inventory from Python as well would be the same rule in two
> places.
>
> What that gate asserts is that every defective-verdict row is claimed by a note whose status is not terminal

The first sentence is right for the wrong stated reason: the paragraph describes only the ROW→NOTE assertion,
which cannot catch a dangling claim at all. The NOTE→ROW assertion that CAN is real but unmentioned, so a
reader deciding whether to add the check is reasoning from an incomplete account of what protects the field.
This is `feedback_a_real_clause_can_answer_a_different_question` in a docstring: a real gate cited to justify
an omission it does not cover.

**3. `work.py`'s loader mis-parses the field, so the check cannot simply be dropped in.** `load()` (`:196-217`)
handles a list value as `[x.strip() for x in v.strip("[]").split(",") if x.strip()]` and **never strips the
per-element quotes**. Measured:

```
work.py load() sees   : PB142.md ['"GR-14.9.10.4-6"', '"GR-14.9.10.4-15"']
work.py load() sees   : PB144.md ['"GR-14.9.10.4-1"', '"GR-14.9.10.4-3"', '"SR-14.9.10.3-2"']
```

The C# reader does strip them (`ParseNote`, `:115-122`, `.Select(x => x.Trim('"'))`). ⛔ **The two readers of
the same frontmatter are already on different grammars** — the exact drift `ParseNote`'s comment says it exists
to prevent (*"pulling a YAML dependency in to read three fields would put the two readers on different
grammars"*). Any new Python consumer of `inventory_rows` that trusts `load()` compares quoted strings against
unquoted ids and reports **every** claim as missing, or, worse, is written to strip quotes locally and the
mis-parse survives one caller longer. Fix `load()`, not the caller.

## Why it matters

`work.py check` is the register's cheap validator: it is what `scripts/session-probe.ps1` runs every session,
what the `kb-sync` skill runs at a phase close, and what a landing runs to say the register is CURRENT — no
build, no test host, sub-second. The `inventory_rows` back-link is called, in the register's own docstring,
*"THE BACK-LINK TO THE P14 TRACEABILITY INVENTORY, and the register's newest field"*, and it is the field an
inventory rebuild invalidates. Today the only signal that it broke arrives from a different language, in a
suite named for a different invariant, after a solution build — so during a denominator change the person
holding the register cannot ask the question at the moment they need it answered.

MINOR and `process_only`: no user program changes. Not low-value — CLAUDE.md rule 8 makes `kb/Work/` the ONE
work register, and a register whose back-links can rot between builds is the failure mode rule 8 exists for.

## The fix shape

1. **Repair `load()` first** — strip matching quotes per list element, so the Python and C# readers agree on
   the same three fields. One line, and it is a prerequisite for everything below.
2. **`check_rows_exist(items)`**, called from `check()`: read
   `tests/version-matrix/traceability-inventory.json`, build the id set, and report every claim not in it as
   `"<note file>: inventory_rows names '<id>', which is not a rule-id in the inventory"`. Fail as a `check`
   failure (non-zero exit, the existing `bad` list), keyed by note id.
3. **A known-missing allowance, and it is not optional.** A denominator change moves the inventory and the
   notes in the same change set but not in the same instant: PB698's rebuild takes 4,371 rows to 4,348, and a
   note re-keyed to a 4,348-row id is *correctly* re-keyed while main's 4,371-row inventory still lacks it —
   and the reverse during a revert. Without an allowance the check goes red on correct work and gets disabled,
   which is worse than not having it. Shape: an explicit, dated, id-listed allowance that the check prints as
   a **warning with its reason**, so an allowance that outlives its migration is visible rather than silent —
   an unexplained allowance is `feedback_green_gates_arent_evidence`.
4. **Do not duplicate the predicate — decide where it lives.** Two copies of "does this id exist" in two
   languages is `feedback_one_mechanism_per_job`, and `check_base_agrees()` already documents the one case
   where the project accepted a second copy *and built a gate to hold the copies together*. Either do the
   same here (the C# gate asserts the Python check exists and covers the same set) or make one the caller of
   the other. Whichever is chosen, **update `work.py`'s docstring paragraph**: it currently misdescribes what
   the C# gate asserts, and that misdescription is finding 2.
5. **Prove it fires before trusting it** (`feedback_prove_the_watchdog_fails`): a fixture note claiming a
   fabricated id must make `work.py check` exit non-zero, and the currently-measured population is **0 of
   1,154 claims**, so a green run today is evidence of nothing until the failure branch has been seen once.

## Sweep

The frontmatter claims are covered; the **prose is not**, in either reader. Rule-id-shaped tokens in note
BODIES are checked by nothing, and PB698 deliberately left the prose alone (*"the PROSE was deliberately not
rewritten — it argues about the rows as they stood"*). Measured on this tree: **1,172 rule-id-shaped tokens in
note bodies, of which 8 notes carry at least one token absent from the live inventory** — `PB39` (
`GR-9.3.8.2.3-L2.6`, `RV-15.30.3-3`, `RV-15.31.3-3`, `RV-15.95.4-5`), `PB55`, `PB88`, `PB284`, `PB522`,
`PB63`, `PB77`, `PB662`. ⚠ These are **candidates, not defects**: several are clause-level shorthand rather
than row ids (`GR-9.3.6`, `FMT-15.30`, `GR-1`), and a note's prose legitimately argues about rows as they
stood at the time. Triage them by hand before deciding whether prose ids are worth a check at all —
PB698's judgment (an argument edited to change an id is an argument broken) is the reason the answer may well
be "no", and if it is, that decision belongs in the docstring so it is not re-litigated.
