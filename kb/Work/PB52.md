# PB52 — OPEN — the residue [[PB48]] left, itemised so no worklist has to infer it

> ⚙ **[[PB48]] moved the decidable cases to BIND time. These are the ones its mechanism could not reach, and
> each is ILLEGAL source diagnosed at the wrong STAGE — the [[PB47]] shape, never a wrong answer.**
> They are recorded here rather than in PB48's closing paragraph because a paragraph is not a work list
> (CLAUDE.md rule 8), and this is the residue that used to rot in exactly that position.

## MEASURED (2026-08-05, on the PB48 tree)

| source | today | required |
|---|---|---|
| `FUNCTION SQRT(SPACE)` | run-time `figurative 'S' in a numeric context` | a bind diagnostic |
| `FUNCTION MAX(SPACE 5)` | run-time `figurative 'S' in a numeric context` | a bind diagnostic (§15.59.3 r2) |
| `FUNCTION BYTE-LENGTH(5)` | run-time `a numeric literal is not a valid argument` | a bind diagnostic (§15.14.3 r1) |

## THE THREE CAUSES, WHICH ARE NOT THE SAME CAUSE

1. **SQRT is not in `IntrinsicArgumentRules.Verified`.** That table is deliberately fail-open: a function is
   screened only once its §15.x argument rule has been READ AND CITED, because asserting the catalog's unaudited
   `ArgKinds` column rejected 12 legal corpus programs ([[PB1]]). So this is not a defect in the screen — it is
   the screen's coverage, and it closes one clause at a time as the Phase-B review adjudicates. ⚠ Do NOT
   "fix" it by widening from `ArgKinds`.
2. **§15.59.3 r2 is a CROSS-ARGUMENT rule and the screen is per-position.** "All arguments shall be of the same
   class with the exception that mixing of arguments of alphabetic and alphanumeric classes is allowed"
   (`--check`ed) is what makes `FUNCTION MAX(SPACE 5)` illegal, and a per-position screen cannot express it.
   This is the same residue already recorded against §15.79.3 r3 and §15.48.3 r3 — **three instances now, which
   is the argument for the per-position/cross-argument SCHEMA that [[PB12]] identified as its design half**
   rather than three more special cases.
3. **`BYTE-LENGTH`'s literal-class rule is enforced in the FOLD, not in a screen.** §15.14.3 r1 admits "an
   alphanumeric or national literal", so a numeric literal is inadmissible — a statically decidable fact that
   `BindByteLengthFold` reports as a `BoundExprError`, i.e. at run time. `LENGTH` (§15.50.3 r1) has the identical
   shape and the identical wrong stage.

## ▶ WHAT TO CHECK FIRST

⚠ Cause 3 is the cheapest and is NOT blocked on the schema: both folds already know the rule and already have
the operand: they need to emit a diagnostic instead of a `BoundExprError`. Doing that alone would close two of
the three rows without touching the screen's coverage question.
⚠ Cause 2 is where the design work is; do not fold it into cause 1. `Verified` maps a function to ONE kind, and
r2 is a statement about the LIST — a different shape of rule, which is precisely
[[feedback_model_the_rule_shape_not_one_case]].
