## ⛔ CAUSE 1 WAS FIVE FUNCTIONS, NOT THE ONE THE NOTE NAMED

`Verified` is deliberately fail-open — a function is screened only once its §15.x rule has been READ AND CITED,
because asserting the catalog's unaudited `ArgKinds` column rejected 12 legal corpus programs ([[PB1]]). SQRT was
absent. So were **SIGN, COS, SIN and TAN**, each carrying the identical rule, each read individually:

```
§15.84.3 r1  SQRT   Argument-1 shall be of class numeric.
§15.81.3 r1  SIGN   Argument-1 shall be of class numeric.
§15.20.3 r1  COS    Argument-1 shall be of class numeric.
§15.82.3 r1  SIN    Argument-1 shall be of class numeric.
§15.89.3 r1  TAN    Argument-1 shall be of class numeric.
```

⚠ **SQRT IS §15.84, NOT §15.81 — §15.81 IS SIGN.** A first pass read §15.81.3's "Argument-1 shall be of class
numeric", `--check`ed it, and took it for SQRT's: the text is real, the clause belongs to another function
([[feedback_a_real_clause_can_answer_a_different_question]]). Every row above was re-extracted BY ITS CLAUSE
ANCHOR afterwards, so the function→clause mapping is mechanical rather than recalled.

⚠ **AND A FIXTURE NAME IMPLIED THE COVERAGE THAT WAS MISSING.** `pb1-numeric-arg-trig-family` screens ACOS, ASIN
and ATAN — the three INVERSE functions — and its comment says so honestly. Its NAME does not: a reader asking
"is the trig family screened?" reads yes, while COS/SIN/TAN sat unscreened. Nothing was claimed falsely; a name
did the implying ([[feedback_green_test_can_hold_a_gap_open]], by a route no assertion could catch).

## ⛔ CAUSE 3 IS TWO CLAUSES THAT DIFFER IN EXACTLY ONE WORD

§15.14.3 r1 and §15.50.3 r1 both admit **"a data item of any class or category"**, so only a LITERAL argument is
restricted — a screen on the operand's CLASS would reject the numeric ITEMS both clauses permit, which is PB1's
direction. The folds already knew the rule; they returned a `BoundExprError`, i.e. reported it at RUN TIME.

```
§15.50.3 r1  LENGTH       an alphanumeric, national, or BOOLEAN literal …
§15.14.3 r1  BYTE-LENGTH  an alphanumeric or national literal …            ← no boolean
```

**So `FUNCTION LENGTH(B"101")` is legal and `FUNCTION BYTE-LENGTH(B"101")` is not**, and a single shared check
would have got one of them wrong. Both now emit a cited bind diagnostic through one `InadmissibleArgument`
helper that takes the admissible set per clause. Verified: `LENGTH(B"101")`→3, `BYTE-LENGTH(B"101")`→rejected,
`LENGTH(N"AB")`→2 (character positions), `BYTE-LENGTH(N"AB")`→4 (bytes, D-N1).

⚠ **THE HELPER DELIBERATELY DOES NOT TAKE THE `--permissive` DOWNGRADE** the class screen's `Report` applies.
That warning says "accepted … with the existing coercion", and here there is no coercion: the fold has no value
it could produce for a numeric literal, so a warning would be followed by the identical run-time abort.
Permissive is the migration mode for constructs an EDITION removed; this is illegal in every edition.

⚠ **AND THE OTHER `BoundExprError`s IN THOSE FOLDS ARE LEFT ALONE, ON PURPOSE.** A ref-modified, ODO, ANY LENGTH
or DYNAMIC LENGTH argument has a RUNTIME length a compile-time fold genuinely cannot produce — a staged gap,
correctly loud where it is found. Only an inadmissible LITERAL is decidable from the source text, and only those
three arms moved.
