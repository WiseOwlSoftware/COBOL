# PB4196 — one GLOBAL data item outranks a nearer report entry

**Sites:**
- `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs` (`DataBinder.ResolveClauseOperand`: `survivors.Single`;
  `DataBinder.QualifiedCandidates`, `DataBinder.QualifiedConditionCandidates`: the narrowing now asks the report entries)
- `src/WiseOwl.Cobol.Compiler/Binding/Model/SymbolTable.cs` (`SymbolTable.NearestDeclaringNamed`, the one narrowing;
  `SymbolTable.TryResolveUnqualified`, the procedure division's `MOVE PV TO W` lookup; `SymbolTable.NearerDataNameHides`)
- `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.Reports.cs` (`DataBinder.NearerReportEntryHides`, new;
  `DataBinder.ReportEntryReferenceRefused`, whose `DataItemsAmbiguousBeforeReportEntry` is deleted)
- `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.Constants.cs` (`DataBinder.DeclaredNearerThan`)
- `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs` (`ConditionBinder.ReportMisqualifiedCondition`)
- `src/WiseOwl.Cobol.Compiler/Binding/ReferenceResolver.cs` (comment), `docs/REPORT_WRITER_DESIGN.md` (the PB3767 paragraph)

**The rule.** `python scripts/spec/cite.py --check 8.4.6.2.1 "3)"` OK. §8.4.6.2.1 3): when more than one item is identified,
"If zero or one of the items has a name local to source element B, the following rules apply: a) If the name is declared in
source element B, the item in source element B is the referenced item." A report entry declared in the contained program is
declared in source element B, so it is the referenced item, and the container's GLOBAL item of the same name is not.

**The defect.** When the name matches exactly ONE data item (the container's GLOBAL PV) and one report entry (INNER's own
DET-1 PV), the lookup takes the single data item without asking where the report entry is declared. The program below
compiles and `MOVE PV TO W` reads the container's PV; `FILE STATUS IS PV` names it too. It should be refused as a reference
to a report entry (COBOL5092), the answer PB3767 and PB3766 give when TWO GLOBAL data items match (`DataBinder.Reports.cs`,
`ReportEntryReferenceRefused` applies the nearer-report-entry rule there, branch c21-35). Wrong answer, silent: the program
runs with another program's data.

**Repro** (at every edition):

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. PBX.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  G1 GLOBAL.
           05  PV PIC 9(2).
       PROCEDURE DIVISION.
       MAIN.
           CALL "INNER".
           STOP RUN.

       IDENTIFICATION DIVISION.
       PROGRAM-ID. INNER.
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
           SELECT RPT ASSIGN TO "pbx.rpt".
           SELECT DAT ASSIGN TO "pbx.dat" FILE STATUS IS PV.
       DATA DIVISION.
       FILE SECTION.
       FD  RPT REPORT IS R-1.
       FD  DAT.
       01  DAT-REC PIC X(3).
       WORKING-STORAGE SECTION.
       01  W PIC 99 VALUE 1.
       REPORT SECTION.
       RD  R-1 PAGE LIMIT IS 10 LINES.
       01  DET-1 TYPE DE LINE PLUS 1.
           05  PV COLUMN 1 PIC 99 SOURCE W.
       PROCEDURE DIVISION.
       SHOW.
           MOVE PV TO W.
           GOBACK.
       END PROGRAM INNER.
       END PROGRAM PBX.
```

**To fix.** The nearer-declaration rule belongs in the ONE name lookup, so the report entries take part in §8.4.6.2.1 3)
with the data items rather than being consulted only when the data items are ambiguous; then the clause resolvers and the
procedure-division references all get it. Goldens: the repro's `MOVE` and `FILE STATUS` forms, COBOL5092, four editions;
and the same with the report entry in the CONTAINER (the GLOBAL data item in INNER wins there, by rule 3 a)).

## Landed

Re-probed on the build (Debug 0/0): the note's repro compiled with FILE STATUS bound to the container's `PV` (it drew COBOL2455
only because that PV is numeric); `MOVE PV TO W` alone compiled clean; with `PIC XX` the FILE STATUS form compiled clean.
**Root and fix.** `QualifiedCandidates` (qualified) and `TryResolveUnqualified` (bare) narrowed a data-name set to the nearest
declaring source element but never asked the report entries, which §8.4.2.2.3 SR1 counts as data-names of the element that
declares their report. `SymbolTable.NearestDeclaringNamed` is now the ONE narrowing (data-names and condition-names): it
leaves no survivor when `DataBinder.NearerReportEntryHides` finds a report entry the written qualifiers reach in a nearer
element (`cite.py --check 8.4.6.2.1 "If the name is declared in source element B, the item in source element B is the
referenced item"` OK), so every caller meets an unidentified reference and its existing `ReportEntryReferenceRefused` names
the entry (COBOL5092, §13.8.6.2.3). The PB3767 order is therefore the lookup's, and `DataItemsAmbiguousBeforeReportEntry` is
deleted (`dataItems.Count > 1` is the ambiguity). Siblings swept: condition-names (`IF CN`: golden), index-names and
capacity registers (`NearerDataNameHides` asks the entries: golden), constants (`DeclaredNearerThan`: goldens `pb4196-contained-constant-...` and `pb4196-contained-report-entry-hides-global-report-sum-counter`, review R1-1); the sum counter keeps
its own earlier path. Not changed: `SearchAllFormat2Rules` words a hidden condition-name as misqualified (still refused).
