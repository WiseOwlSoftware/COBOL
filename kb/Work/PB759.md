## What the grammar spells

`src/Cobol.Net.Frontend/Grammar/Core/CobolOO.g4:42-44` on main, verbatim:

```
classIdParagraph
    : CLASS_ID DOT className externalizedNamePhrase? (IS? FINAL)? (INHERITS FROM className+)? DOT
    ;   // [AS literal-1] sits between object-class-name-1 and [IS FINAL] per the §11.3.2 format (kb/Work PB303); …
```

and `:76-86`:

```
interfaceDefinition
    : (IDENTIFICATION DIVISION DOT)? INTERFACE_ID DOT interfaceName
      // The INTERFACE-ID paragraph general format (§11.6.2) prints [AS literal-1] between interface-name-1
      // and the INHERITS clause; kb/Work PB303.
      externalizedNamePhrase?
      (INHERITS FROM interfaceName+)? DOT
      …
```

Both rules walk the §11.3.2 / §11.6.2 format phrase by phrase — `[AS literal-1]` (added by PB303), `[IS FINAL]`,
`[INHERITS FROM …]` — and then stop one bracket short of the printed period. There is **no USING slot on either
rule**, and no comment records the omission.

⚠ **The design doc already quotes the phrase and does not say it is unparsed.** `docs/COBOLNET_OO_DESIGN.md:78`:
*"CLASS-ID's only modifiers are `[AS literal-1] [IS FINAL] [INHERITS FROM …] [USING …]`"* — written to bound the
ISO surface against a vendor `ABSTRACT`, and correct about what the standard prints. A reader consulting the
SSOT design doc is told the compiler's model of CLASS-ID includes USING. It does not.
`feedback_a_real_clause_can_answer_a_different_question` in its documentary form: the doc's citation is right and
the sentence still leaves the gap invisible.

⚠ **Where the family-3 branch differs.** `worktree-agent-a334880f747b22665` (train 17) relaxes both rules'
`INHERITS FROM` to `INHERITS FROM?` — FROM is PLAIN on both pages, as re-measured above, so that change is
correct and it touches the phrase immediately BEFORE this one. Whoever adds the USING slot must add it after the
INHERITS group and before the `DOT`, and must not lose the `FROM?`.

## Why it matters

Parameterized classes are a whole ISO feature — §9.3.12 in the concepts division, two general formats, six
syntax and general rules — and this compiler has no surface for any of it. Every generic class or interface
definition in a conforming COBOL-2002/2014/2023 source unit is refused at the paragraph header, before any of its
content is seen, with a diagnostic about punctuation. There is no dialect gate, no `--std` message, and no
§4.2.7 named decline; a facility this implementation does not provide must be diagnosed BY NAME, and this is a
generic parse-recovery hint.

## The fix shape — and it is a FEATURE, not a token

The grammar half is small and belongs on both rules symmetrically (`feedback_two_arm_dispatch` — there are two
sites and the INHERITS history in this same pair shows one of them getting fixed alone):

```
classIdParagraph
    : CLASS_ID DOT className externalizedNamePhrase? (IS? FINAL)?
      (INHERITS FROM? className+)? (USING classParameterName+)? DOT
    ;
```

with the twin on `interfaceDefinition`. But the grammar is the smallest part, and CLAUDE.md rule 5 applies —
the estimate is not the ceiling:

1. **The parameter names have to reach the class model.** `src/Cobol.Net.Compiler/Oo/OoClassTable.cs` is where a
   class's identity, bases and interfaces live; a formal parameter list is a new dimension on that record, not a
   field on the paragraph node.
2. **§11.3.3 SR8 / §11.6.3 SR4** require each parameter-name to be a class-specifier or interface-specifier in
   THIS source element's REPOSITORY paragraph — a bind-time check against the repository table.
3. **§11.3.3 SR9 / §11.6.3 SR7** forbid a repeated parameter-name in one USING clause — a local duplicate check.
4. **§9.3.12** is the behavior, and it is the open design question: what a parameterized class MEANS when
   expanded, and whether the C# projection is a generic type or an expansion per instantiation. That decision
   belongs in `docs/COBOLNET_OO_DESIGN.md` before any emitter work, and it is what makes this a design-doc item
   rather than a grammar item.
5. **The edition gate.** The whole OO subsystem is COBOL-2002+, so the USING phrase inherits that gate; at
   `--std 85` it must draw the existing OO not-introduced diagnostic, not a parse error
   (`feedback_edition_gate_sweep`).

**If the owner elects NOT to implement §9.3.12 in this pass, the answer is still not silence:** §4.2.7 makes
non-support conformant only when diagnosed, so the minimum landing is the grammar slot plus a NAMED decline
(a new `COBOLNET####` with a `DiagnosticCatalog` descriptor and a `docs/DIAGNOSTICS.md` row) and a
`docs/CONFORMANCE.md` row saying the item is Not claimed — the `DeclinedFacilityPass` /
`Grammar/Core/CobolDeclined.g4` seam that PB283 built exists for exactly this. What must NOT stand is the current
state, where legal source dies on a punctuation hint.

## Sweep

`docs/COBOLNET_OO_DESIGN.md:78`'s sentence should be corrected in the same change set to say which of the four
CLASS-ID modifiers are parsed — a doc that enumerates the ISO surface while the grammar implements three of four
is how the next reader stops looking. Beyond this construct, the general form is the one [[PB303]] already
demonstrated on `AS literal-1` across five paragraphs: a printed identification-division phrase with no grammar
slot. The mechanical guard is a per-paragraph format-vs-rule join over §11's general formats, the same shape
`audit_grammar_optional_words.py` runs for optional words — a phrase the format prints and the rule cannot
mention is a testable claim, and no hand-kept list should hold it (CLAUDE.md rule 8).
