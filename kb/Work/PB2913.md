# PB2913 — the loop's campaign lanes cannot change between units

Found 2026-10-10 by the operator applying the owner's priority decision (kb/Work PB2911). `orchestrate.ps1 -Cluster`
is read once when the supervisor starts and passed to `next_unit.py --cluster`; `steer.ps1` names only the next UNIT
(`wave|campaign|land|resume|meter`), never the lane list. To drop PB2119 and add PB2911,PB1086 the operator must run
`stop.ps1`, which winds the RUNNING unit down (its agents checkpoint and return SPLIT, a lander mid-landing included),
then restart the supervisor. There is no "stop after this unit" either.

**Fix (rule 5, the next case automatic):** the lane list is operator state the supervisor re-reads before choosing
each unit, set by the same validated path as a steer (e.g. `steer.ps1 -Lanes PB2911,PB1086` writing a lanes file
beside `handoff.operator.json`, validated against kb/Work like `-Cluster` is today, logged by the supervisor when it
changes); `-Cluster` seeds it at start. Self-test: a lane change written during a unit takes effect at the next unit
without a stop, and an unknown lead is refused at the steer. Alternatively or as well, `stop.ps1 -AfterUnit` ends the
loop at the next unit boundary without winding anything down.
