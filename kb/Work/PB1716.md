# PB1716 — TableValueOdometer.Resolve fills a table VALUE up to MaxFillElements (64,000,000) BEFORE the §13.18.63.3 SR23 check rejects the entry

Filed by the orchestrator from the PB1708 pivot design (workflow wf_08642598-d3c, reviewed APPROVE_WITH_CHANGES, all eleven findings resolved by the reviser), 2026-09-28.
## Defect

`src/Cobol.Net.Compiler/Binding/Model/TableValuePlan.cs` `TableValueOdometer.Resolve` (called from
`DataBinder.ResolveTableValues`) fills a Format 2 table VALUE up to `MaxFillElements` (64,000,000) before SR23
rejects the entry. The fill should instead be bounded by the elements the phrase names.

**Evidence:** all 3 stack samples of the pb505 negative program (26 lines, 29.6 s through the CLI) are in
`TableValueOdometer.Resolve`.

## Harm

- A user's erroneous program takes about 30 s to be rejected, and a large table can take longer or use a large
  amount of memory.
- It is the suite's longest test (219 s).

## Fix (PB1708 pivot M7; `docs/rearchitecture/DESIGN-test-build-ci.md` section 3.14.5 and the section 3.14.9 row)

Check SR23 before any table-value fill, and bound the fill by the phrase. The battery summary also gets a top-5
slowest-tests report; it only reports and asserts no wall-clock limit.

**Acceptance:**
- pb505 is rejected with `COBOLNET1946` in under 1 s through the CLI;
- both tests keep their assertions;
- every Format 2 VALUE golden is unchanged.

SR23 is verified: `cite.py --check 13.18.63.3 "If the TO phrase is specified and an OCCURS clause with a DYNAMIC phrase but no TO phrase"` passes (2026-09-28).

## Harm flag

## Landed (wave 71 group B, 2026-09-28)

**Re-probe on this build, before the fix:** pb505 took 25.3 s through the CLI (exit 70, `COBOLNET1946`).

**Root.** The fill had no bound of its own. `Resolve` walked the GR12 odometer until it reached the TO tuple or
`MaxFillElements`, and an SR23-violating phrase never reaches its TO, because the odometer cannot carry out of a
dimension with no ceiling. The screen reported `COBOLNET1946` first, and then the pass ran the 64,000,000-element
fill anyway.

**Fix (`src/Cobol.Net.Compiler/Binding/Model/TableValuePlan.cs`).**
- `TableValueOdometer.ElementCount(dims, from, to)` is the number of elements a phrase names: the mixed-radix
  distance from subscript-1 to subscript-2, computed by borrow subtraction and saturating at `long.MaxValue`. It
  is computed BEFORE the fill. It is null when the phrase names no well-formed run: a subscript outside
  1..`Ceiling` (SR20/SR21), TO before FROM (SR21), or unequal subscripts at a level SR23 constrains.
- `Resolve` fills exactly `ElementCount` elements, and `MaxFillElements` is deleted.
- `TableValueDim.Ceiling` replaces `DataBinder.SubscriptCeiling`, so the SR20/SR21 ceiling is written once.

**Sibling (the other arm).** SR23's screen in `DataBinder.TableValue.cs` tested only the OUTERMOST dimension that
is DYNAMIC with no TO, and then `break`. The rule binds EVERY such OCCURS clause, so with two nested ones
`FROM (1 1) TO (2 1)` compiled clean after a 22.9 s fill that was truncated at the cap. That was an under-reject.
`TableValueOdometer.UnboundedBelow(dims, level)` now states the rule's shape once: a level is constrained when ANY
less inclusive dimension is unbounded. The screen and `ElementCount` both read it. A second sibling had the same
root: a TO subscript past the §8.5.1.9.1 maximum capacity was diagnosed with `COBOLNET1587` and still filled
50,000,000 elements (17.5 s). It is now counted null and fills nothing.

**After the fix:** pb505 rejects in 0.49 s, the nested case in 0.41 s (now `COBOLNET1946`), and the out-of-range
case in 0.41 s. Both named tests keep their assertions, and no Format 2 VALUE golden changed.

**Goldens:** `2014/pb1716_table_value_element_count` (a carry between the tuples, an unbounded outer dimension,
and two nested unbounded dimensions, each overlaid on a whole-table phrase so a miscount shows) and
`negative/pb1716-table-value-nested-dynamic-span` (`COBOLNET1946` at 85/2002/2014/2023). The unit test
`TableValueElementCountTests` proves the count equals the odometer walk for every tuple pair of a 2x3x2 table.

**Battery.** `scripts/battery.sh` prints the five slowest tests of its three legs, through
`scripts/profile-test-parallelism.py --slowest`. It is a report only and never changes RC.

**Rows.** SR-13.18.63.3-23 was OK but under-rejected the nested shape; it is re-verdicted with the new site and
witnesses. GR-13.18.63.4-12 is re-verdicted with `ElementCount` as a site. Both rows are in batch
`w71b-pb1716`.

**For the next implementer.**
- `src/Cobol.Net.Compiler/Binding/Model/TableValuePlan.cs#TableValueOdometer.ElementCount` owns how many elements a
  phrase names, and `#UnboundedBelow` owns SR23's shape. Reuse both; never loop the odometer "until TO".
- `src/Cobol.Net.Compiler/Binding/Model/TableValuePlan.cs#TableValueDim.Ceiling` is the one SR20/SR21 ceiling.
- `src/Cobol.Net.Compiler/Binding/DataBinder.TableValue.cs#ScreenTableValueGeometry` diagnoses; the odometer
  fills. A demoted (`--permissive`) diagnostic still reaches `Resolve`, so `ElementCount` must return null for
  every shape the screen rejects.
- Trap: in fixed-form goldens, a `VALUES ARE ... FROM (..) TO (..)` line past column 72 is cut off silently, and
  the parse error then reports an "unexpected 'TO'".
