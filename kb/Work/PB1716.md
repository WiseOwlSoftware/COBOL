# PB1716 — TableValueOdometer.Resolve fills a table VALUE up to MaxFillElements (64,000,000) BEFORE the §13.18.63.3 SR23 check rejects the entry

Filed by the orchestrator from the PB1708 pivot design (workflow wf_08642598-d3c, reviewed APPROVE_WITH_CHANGES, all eleven findings resolved by the reviser), 2026-09-28.
## Defect

`src/Cobol.Net.Compiler/Binding/Model/TableValuePlan.cs` `TableValueOdometer.Resolve` (called from
`DataBinder.ResolveTableValues`) fills a Format 2 table VALUE up to `MaxFillElements` (64,000,000) before SR23
rejects the entry. The fill should instead be bounded by the elements the phrase names.

**Evidence:** all 3 stack samples of the pb505 negative program (26 lines, 29.6 s through the CLI) are in
`TableValueOdometer.Resolve`.

## Harm

- A user's erroneous program takes about 30 s to be rejected, and a large table can take longer or use a large
  amount of memory.
- It is the suite's longest test (219 s).

## Fix (PB1708 pivot M7; `docs/rearchitecture/DESIGN-test-build-ci.md` section 3.14.5 and the section 3.14.9 row)

Check SR23 before any table-value fill, and bound the fill by the phrase. The battery summary also gets a top-5
slowest-tests report; it only reports and asserts no wall-clock limit.

**Acceptance:**
- pb505 is rejected with `COBOLNET1946` in under 1 s through the CLI;
- both tests keep their assertions;
- every Format 2 VALUE golden is unchanged.

SR23 is verified: `cite.py --check 13.18.63.3 "If the TO phrase is specified and an OCCURS clause with a DYNAMIC phrase but no TO phrase"` passes (2026-09-28).

## Harm flag

`process_only: true` because the register has no harm flag for COMPILE-TIME PERFORMANCE: the defect changes no
program's output or diagnostics, only how long the compile takes. It is a product defect all the same (it ships in
the `cobol` CLI).
