# PB781 — OPEN — the rule with no site, because the clause it screens is not modelled at all

Filed 2026-09-06 by the registrar, on [[PB773]]'s explicit instruction that this row *"needs its own note — do
not let it ride in on this one and then vanish"*. Every clause number, line number and inventory field below was
re-derived on this worktree; nothing is inherited from PB773 or PB692.

⚠ **No runtime probe was run.** This worktree has no built CLI (`src/Cobol.Net.Cli/bin/Debug/net10.0/cobol.dll`
does not exist) and building was out of scope, so the acceptance below is derived STATICALLY — from the measured
absence of any reader of the clause — not from a compiled program. That derivation is the stronger evidence here
anyway: a screen cannot fire from a fact the binder never records.

## The rule, quoted and mechanically checked

```
$ python scripts/spec/cite.py --check 12.4.5.2 "If the LINE SEQUENTIAL phrase of the ORGANIZATION clause is specified, the RESERVE clause shall not be specified."
OK  §12.4.5.2 12)  (Syntax rules)
    12\) If the LINE SEQUENTIAL phrase of the ORGANIZATION clause is specified, the RESERVE clause shall not be specified.
```

It is a **syntax rule of the file control entry** — a clause-pair exclusion, decidable from the SELECT alone,
violated by the entry whether or not any statement ever names the file. It sits under the `FORMAT 3` sub-heading
of §12.4.5.2 (`specs/ISO_COBOL.md:13256`, between SR11 at `:13258` and the `FORMAT 4` heading), so it is stated
about the same entry format [[PB773]] claims SR11 for.

The clause it forbids is §12.4.5.14 (`cite.py --check 12.4.5.14.1 "The RESERVE clause allows the user to specify
the number of input-output areas allocated"` → **OK**), whose format is `<u>RESERVE</u> integer-1 [ AREA |
AREAS ]` (`--check 12.4.5.14.2 "<u>RESERVE</u> integer-1"` → **OK**) and whose single general rule assigns the
count (`--check 12.4.5.14.3 "the number of input-output areas allocated is equal to the value of integer-1"` →
**OK §12.4.5.14.3 1)**).

⚠ **The `<u>` markup in those two quotations is not decoration, it is a workaround.**
`cite.py --check 12.4.5.14.2 "RESERVE integer-1"` — the plain, correct spelling — **FAILS** today. That is
[[PB779]] Part B, and §12.4.5.14.2 is one of its three measured instances. Until PB779 lands, a citation of this
clause's format either carries HTML tags or is weakened to a fragment.

## ⛔ The mechanism — the clause parses and is then dropped on the floor

The grammar has the clause. `src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4:128-130`:

```
fileReserveClause
    : RESERVE integerLiteral (AREA | AREAS)?
    ;
```

and it is an alternative of the file control entry's clause set at `:71` (`| fileReserveClause`).

**Nothing reads it.** Measured, case-insensitively, over the whole of `src/`:

```
$ grep -rin "filereserve" src/
src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4:71:    | fileReserveClause
src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4:128:fileReserveClause
```

Two hits, both the grammar's own. No binder visitor, no `VersionConformancePass` arm, no `Declined` call. The
clause ladder in `src/Cobol.Net.Compiler/Binding/DataBinder.cs` — `BindFileControl`, the chain at `:837-899` — has
**eleven arms** (one `if` plus ten `else if`, measured): ASSIGN `:837`, ORGANIZATION `:849`, ACCESS MODE `:850`,
FILE STATUS `:853`, RECORD KEY `:855`, ALTERNATE RECORD KEY `:861`, RELATIVE KEY `:873`, SHARING `:879`, LOCK
MODE `:881`, FILE COLLATING SEQUENCE `:883`, RECORD DELIMITER `:897`. **None of them is RESERVE.** `src/Cobol.Net.Compiler/Binding/Model/FileModel.cs` has no field for it either
(`grep -in "reserve"` on that file matches only the copyright line's "rights reserved").

So the compiler cannot know that a RESERVE clause was written. SR12's antecedent — *"the RESERVE clause shall
not be specified"* — is a fact the binder does not hold, and a screen for it has nowhere to read from. **This is
not "a missing `if`"; it is a missing carrier**, and that is the difference between this note and every other
member of the §12.4.5.2 family, all of which screen clauses the binder already models.

⚠ **The RESERVE clause is otherwise legitimately ignorable, and that is why nobody noticed.** §12.4.5.14.3 GR1
makes the count implementor-defined when the clause is absent, so dropping the clause is a defensible
implementation of the clause itself — it is only SR12 that needs the *presence* recorded. A note that read
"RESERVE is unimplemented" would be wrong; what is unimplemented is the syntax rule that keys on it.

## What the fix must be, and where — from the criterion already written down

⛔ Do not invent a home. `src/Cobol.Net.Compiler/Binding/FileControlKeyRules.cs:141-146` already states the
criterion, and names the design decision it comes from:

> ⚖ THE SIBLING SITE. Entry rules that are decidable from the CLAUSES ALONE — §12.4.5.5.2 SR2 (no DYNAMIC or
> RANDOM on a sequential file, kb/Work PB692) and the §12.4.5.9 SR2 screen beside it — stay inline in
> `DataBinder.BindFileControl`, because they need nothing resolved and can report as the entry is read. This
> table holds the rules that need a RESOLVED DATA ITEM … That is the whole criterion for which of the two a new
> entry rule joins — `COBOLNET_FILES_DESIGN.md` D19.

SR12 names no data-name and needs nothing resolved, so by that criterion it is a `BindFileControl` rule, beside
the two screens already there. [[PB773]]
reaches the same conclusion independently (`:155-161`) and that is precisely why it excluded SR12 from its own
claim: PB773's two rules are ENTRY-vs-FILE-DESCRIPTION-ENTRY consistency rules and argue for a structural home
(an entry-level rule kind in the table); this one is not that shape and must not be dragged in behind them.

The two sibling screens, measured: §12.4.5.5.2 SR2 is the comment at `DataBinder.cs:901` and the predicate at
`:925`, reporting with the citation string at `:932`; §12.4.5.9 SR2 is the comment at `:934` and the predicate at
`:939`. SR12's screen goes with them.

**So the fix is three things, in this order, and only the first is new work:**

1. **A carrier.** An arm in the `BindFileControl` ladder for `fileReserveClause` that records the clause's
   PRESENCE and its cursor on `FileModel` — the same shape as `accessAt` (`DataBinder.cs:827`, *"the ACCESS MODE
   clause cursor for §12.4.5.5.2 SR2, below"*), which exists for exactly this reason: a rule that must report AT
   the offending clause needs the clause's cursor kept. Whether it also stores `integer-1` is a separate
   question the implementer should answer from §12.4.5.14.3 GR1 rather than from this rule.
2. **The screen**, inline beside its two siblings: LINE SEQUENTIAL written **and** RESERVE present ⇒ error at the
   RESERVE clause's cursor, quoting SR12 and citing `§12.4.5.2 SR12`. Use `FileModel`'s existing spelling of the
   organization rather than a second read of the parse tree — `DataBinder.cs:937-939` records that
   `FileModel.IsSequential` is *"the ONE spelling of 'this file has sequential organization'"* and that a second
   open-coded copy is the shape that file exists to prevent. ⛔ But note the predicate here is **LINE
   SEQUENTIAL specifically**, not `IsSequential`: `IsSequential` covers RECORD SEQUENTIAL and the omitted clause
   too (§12.4.5.10.3 GR6, `--check 12.4.5.10.3 "When the ORGANIZATION clause is not specified, sequential
   organization with the RECORD SEQUENTIAL phrase is implied"` → **OK §12.4.5.10.3 6)**), and SR12 does not
   forbid RESERVE on those. Using `IsSequential` here would reject legal COBOL — see the NIST evidence below.
3. **The row.** `SR-12.4.5.2-12` verdict + code-location + test-ref + notes, through a verdict batch, with a
   negative golden for the violation and a positive one for `RESERVE` on a RECORD SEQUENTIAL file.

## ⛔ The edition question, and the NIST programs the screen must not break

`RESERVE` on a non-LINE-SEQUENTIAL file is legal and is exercised by the corpus.
`tests/nist/extracted/newcob.val` writes it in seven programs — IX4014 (`:99723`, `RESERVE 2 AREAS`), RL4014
(`:245406`), SG2044 (`:257061`, `:257064`), SQ2034 (`:306847`, `:306857`), SQ2264 (`:321156`, the bare
`RESERVE 1` with no AREA/AREAS word), SQ4014 (`:325911`) and ST1154 (`:331462`). Every one of them must keep
compiling: the screen fires only when the ORGANIZATION clause carries LINE SEQUENTIAL.

`LINE SEQUENTIAL` is itself edition-gated in this compiler as a COBOL-2023 introduction —
`src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs:1148` checks
`Constructs.FileOrganizationLineSequential2023` — so at `--std 85/2002/2014` the antecedent is already rejected
by the introduction gate and SR12's screen is unreachable. **Read that gate before filling the row's `editions`
column**: writing `85,2002,2014,2023` would claim a rejection at three editions where the test program cannot
compile at all, which is `feedback_edition_gate_sweep` in reverse. The rule TEXT is edition-invariant in the
2023 transcription; its reachability is not.

## Sweep — SR12 is not alone in §12.4.5.2, and the empty column is the finding

Of §12.4.5.2's thirteen syntax rules, **four are live** (SR7, SR8, SR9, SR10) and **nine are GAP with no site**:
SR1–SR6, SR11, SR12, SR13. [[PB773]] owns SR11 and SR13; this note owns SR12. **SR1–SR6 are unowned and
unexamined**, and PB773's own sweep already flags them: *"the implementer should read that column once and say
which are genuinely enforced-but-unclaimed (the shape [[PB702]] found for SR7) before adding rows, rather than
discovering a fifth dead member next year."* That instruction stands and this note does not discharge it —
`feedback_a_dead_lookup_is_also_unverified`.

**The clause-with-no-reader shape is the sweep axis worth running**, and `fileReserveClause` is unlikely to be
the only one: the question is *which `.g4` rules under the file control entry (and the FD) are matched and never
visited*, because every one of them is a syntax rule of that entry that no screen can reach. Measuring that is a
mechanical grep of each `CobolIO.g4` clause rule name against `src/**/*.cs`, and it should be done once and
recorded rather than rediscovered per rule (`feedback_scan_all_similar`).
