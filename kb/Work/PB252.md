# PB252

**Rows:** `RV-15.88.4-1`, `RV-15.4.1-L2.1`

The native exact-Int128 intrinsic lane still has arms neither sweep reached: SUM and RANGE accumulate UNCHECKED and wrap sign-first, and MOD/REM raise a size error where the SDIDI holds the answer.

ROWS: RV-15.88.4-1 (§15.88.4 r1, the SUM EAE) and RV-15.4.1-L2.1 (§15.4.1 r1, 'the returned value shall equal the value of the equivalent arithmetic expression').

HALF ONE — THE UNCHECKED ACCUMULATOR (RV-15.88.4-1). `CobolIntrinsics.Exact.cs#SumScaled` is verbatim `Int128 s = 0; foreach (var x in xs) s += x; return s;` — plain `Int128.op_Addition`, and neither `Directory.Build.props` nor `src/Cobol.Net.Runtime/Cobol.Net.Runtime.csproj` sets `CheckForOverflowUnderflow`, so the context is unchecked and the add WRAPS silently. The renderer's own comment claims the lane is guarded, but the guard is on the PER-ARGUMENT RESCALE ONLY: `NumericRenderer.Align` (:526) emits `CobolNum.RescaleEscape`, whose test is `Int128.Abs(value) > Int128.MaxValue / Pow10Wide(toScale - fromScale)` — it bounds each ALIGNED ARGUMENT and says nothing about their sum. The same file proves this is a miss and not a design: `MedianScaled`/`MidrangeScaled` route every add through `AddForHalving` (`try { return checked(a + b); } catch (OverflowException) { throw new CobolSizeError(… "EC-SIZE-OVERFLOW"); }`), introduced by PB32 with the policy stated for the whole family — 'A wrap is never a conforming answer — §15.4.1 asks at worst for an implementor-defined approximation, and a value 3.2x out with its top thirty digits wrong approximates nothing.'

MEASURED WITNESS, inside the compiler's own 31-digit cap (`EditionContext.CheckDigitCapacity`): with `P PIC S9(31) VALUE ALL '9'` beside `Q PIC SV9(7)`, `AlignedArgsEx` sets the common scale to 7; `Align(P,7)` = 99999999999999999999999999999990000000, which PASSES RescaleEscape (the bound is Int128.MaxValue / 10^7 = 17014118346046923173168730371588). `COMPUTE R = FUNCTION SUM(P P P Q)` accumulates 299999999999999999999999999999970000000, exceeds Int128.MaxValue and wraps to −40282366920938463463374607431798211456. Stored into a `PIC S9(31)` receiver WITH an ON SIZE ERROR phrase: the true value needs 32 digits and would raise, while the WRAPPED value fits — so the phrase is NOT taken and a sign-flipped answer is stored silently. This is the lane an ordinary COMPUTE takes: `OptionsModel.cs:22` makes NATIVE the default (§11.9.5.2 r4). `RangeScaled` is `MaxScaled(xs) - MinScaled(xs)` — the same unchecked shape, and it belongs to §15.76.4.

WHY THE GOLDENS MISSED IT (output-shaped evidence): every cited golden sits far below the carrier boundary (SUM=15, 39, 60, 21, 10.50), and the one boundary golden, pb62_standard_decimal_summing_family, runs under ARITHMETIC IS STANDARD-DECIMAL — the single lane that is exact.

HALF TWO — THE ARMS PB62 LEFT (RV-15.4.1-L2.1's surviving residue). `alwaysDec` (IntrinsicRenderer.cs:636-644) names Sqrt, Factorial, Annuity, PresentValue, Variance, StandardDeviation, the NUMVAL family, SumScaled, RangeScaled, MeanScaled, MedianScaled, MidrangeScaled — and NOT ModScaled/RemScaled. With an ALL-FIXED-POINT argument list `AnyDecOrRealRaw` is false, `RenderDec` returns null, and `FUNCTION MOD(A, B)` with `A PIC 9(31)` and `B PIC 9V9(18)` takes the native switch arm at :164-171, which aligns both to scale 18 on Int128 — 49 digits, past the carrier — and raises through Align's RescaleEscape, where §15.4.1 r1 requires the §15.64.4 r1 EAE's SDIDI value. PB62's own recorded reason for moving the summing family ('a 31-digit integer beside a scale-18 item needed 49 digits and RescaleEscape raised a size error where the SDIDI holds the answer exactly') applies to MOD/REM word for word.

RV-15.4.1-L2.1's OTHER TWO recorded halves are CLOSED at HEAD and are carried in the stale-verdict note, not here: STANDARD-DEVIATION/SQRT's 34-digit root (PB116 — `alwaysDec` names "Sqrt", `RenderDec:668 "Sqrt" when num.StandardDecimal => SqrtDec`, `CobolIntrinsics.Dec.cs:213 StdDevDec => CobolDec.Sqrt(VarianceDec(mode, xs), mode)`) and FACTORIAL(34) returning the §15.3 default 0 (PB125 — `RenderDec:671 "Factorial" when num.StandardDecimal => FactorialDec`).

FIX SHAPE: a checked accumulator in SumScaled raising CobolSizeError/EC-SIZE-OVERFLOW at the D1 escape boundary exactly as AddForHalving already does, the same for RangeScaled's subtraction, ModScaled/RemScaled added to `alwaysDec`, and a drift test asserting every Exact.cs accumulator either goes through the checked helper or is named as deliberately exempt.

VERIFIED LIVE AT HEAD (read-only): SumScaled:146-150 and RangeScaled:154 unchanged; `alwaysDec`:636-644 still omits ModScaled/RemScaled.

## Mechanism

src/Cobol.Net.Runtime/Intrinsics/CobolIntrinsics.Exact.cs:146-150 SumScaled (`Int128 s = 0; foreach (var x in xs) s += x;`) and :154 RangeScaled (`MaxScaled(xs) - MinScaled(xs)`), against the checked twin AddForHalving/ScaleForHalving twenty lines below; plus src/Cobol.Net.Compiler/CodeGen/Emit/IntrinsicRenderer.cs:636-644 `alwaysDec`, which lists SumScaled/RangeScaled/MeanScaled/MedianScaled/MidrangeScaled and NOT ModScaled/RemScaled; the per-argument bound is NumericRenderer.cs:526 Align → CobolNum.RescaleEscape

## Lineage

PB32 (landed) added AddForHalving/ScaleForHalving for MEDIAN/MIDRANGE and recorded the policy in terms that cover SUM exactly; PB62 (landed) moved the SUMMING family to `alwaysDec` for the alignment size error; PB65 (landed) fixed MIN's widening wrap. SUM/RANGE are the arms PB32 did not reach and MOD/REM are the arms PB62 did not reach — feedback_two_arm_dispatch, twice on one lane.

## Landed

**2026-09-05 (kb/Work PB252).** Both halves reproduced on a freshly built `cobol.exe` before anything was
touched, and one of the note's own premises did not survive that re-probe.

**HALF ONE — reproduced exactly as written, and it is worse than SUM.** `COMPUTE R = FUNCTION SUM(P P P Q)`
with `P PIC S9(31) VALUE ALL '9'`, `Q PIC SV9(7)` and `R PIC S9(31)` printed
`402823669209384634633746074317R` — the wrapped **−4028236692093846346337460743179**, sign-flipped, with the
`ON SIZE ERROR` phrase NOT taken. The true value needs 32 digits, so §14.7.5 rule 3 makes the size error
condition exist there with **no implementor latitude at all**; the wrapped value fits 31 digits, which is why it
stored silently. RANGE wraps the same way — a witness at scale 8 (`±1.7e30` aligned) returned a **NEGATIVE
range**, a value §15.76.4 r1 cannot produce (MAX ≥ MIN by §15.59.4 r1 / §15.63.4 r1). **MEAN is a third arm the
note did not name**: the renderer composes it from the very same `SumScaled`, so it wrapped too and is fixed by
the same change.

**HALF TWO — REM only. The note's MOD repro is impossible from conforming source.** §15.64.3 r1 is
"Argument-1 and argument-2 shall be integers" (`--check` OK), so MOD's common scale is always 0, `Align` is an
identity and the 49-digit alignment cannot arise; the compiler already **rejects** the note's own repro with
COBOLNET1627. REM is the live half — §15.77.3 r1 is "shall be of class numeric" (`--check` OK) — and it
reproduced: `FUNCTION REM(A B)` with `A PIC 9(31)`, `B PIC 9V9(18)` terminated the run unit with
EC-SIZE-OVERFLOW under `ARITHMETIC IS STANDARD-DECIMAL`, where §15.4.1 r1 fixes the value at **0.5** exactly.
MOD is routed with REM anyway, because the property that decides the routing is structural (the arm
cross-aligns), not anecdotal.

**⛔ THE CITATION IN THE SHIPPED MESSAGE WAS WRONG, and it was inherited.** PB32's escape-boundary text cited
"ISO §8.8.1.2 rule 7" — a real clause answering a *different* question (arithmetic expressions are exempt from
the composite-of-operands limit). The governing rule is **§14.7.5 rule 5**: "if native arithmetic is in effect
and the implementor defines that the range of values allowed for the intermediate data item is to be checked,
when an arithmetic operation on the intermediate data item would cause the new value to be outside of the
allowed range" (`--check` OK). Swept: every *other* §8.8.1.2 r7 citation in the tree uses it correctly for the
composite limit — this one site was the outlier.

**THE FIX IS TWO STRUCTURES, NOT TWO PATCHES.**

1. *Runtime.* PB32's helpers were named for MEDIAN's halving (`ScaleForHalving`, `AddForHalving`), which is
   exactly why SUM and RANGE looked like a different problem. They are now named for the OPERATION they guard —
   `ExactAdd` / `ExactSub` / `ExactMul` over one `SizeEscape` raise site — and every exact-carrier step goes
   through one of them or an inline `checked` block. `SumScaled` accumulates `checked` under ONE try for the
   whole loop and takes the COBOL function name, because it is the one body serving two EAEs (§15.88.4's Σ and
   §15.60.4's numerator), so a MEAN overflow now says MEAN. `ModScaled`'s `a − b×q` is checked too — unreachable
   from conforming source, reachable under `--permissive`.
2. *Renderer.* The always-SDIDI routing is no longer an inline `is … or …` chain. Its first half is now
   **derived from the property that decides it** — `CrossAlignedNativeArms` (MOD · REM · SUM · RANGE · MEAN ·
   MEDIAN · MIDRANGE) — beside `StandardValueFixedByRule` for the members that are there for their own cited
   reasons (SQRT, FACTORIAL, the four inexact-EAE functions, the NUMVAL family).

**The drift test is the point.** `ExactCarrierBoundaryDriftTests` holds both invariants without a name list:
it closes the exact-carrier entry-point set by **reflection** (every public `CobolIntrinsics` entry taking and
returning only carrier values is boundary-pinned or exempted with a reason), and it reads the native switch to
collect every arm that calls `AlignedArgs`/`AlignedArgsEx`/`NumericRenderer.Align(x, s)` and fails if one is
missing from the routing set. Its failure branch was proven twice by accident — the scan's first version
swallowed the file past the last arm, and its second dropped MOD's stacked fall-through label, both surfaced by
the `≥ 7` floor — and once on purpose, by unrouting MOD and watching it go red.

**GOLDENS, both verified to FAIL on the pre-fix build.** `2002/pb252_native_carrier_boundary` (COBOL-85 caps
fixed-point at 18 digits, so 2002 is the earliest edition at which the defect is expressible) pins the
no-latitude §14.7.5 r3 case, the two-outcome DISJUNCTION for RANGE, the never-negative consequence, and two
in-carrier controls; pre-fix it printed `SUM-R3-SIZE-ERROR=NO` / `RANGE-CONFORMS=NO` / **`RANGE-SIGN=NEGATIVE`**.
`2014/pb252_mod_rem_standard_decimal` pins REM's exact 0.5 across the 49-digit alignment plus the §15.64.4 NOTE
sign table on the SDIDI carrier; pre-fix it aborted with EC-SIZE-OVERFLOW and printed nothing. Nothing in either
file pins an implementor determination.

**ROWS.** `RV-15.88.4-1` PARTIAL → CONFORMS and `RV-15.4.1-L2.1` PARTIAL → CONFORMS (GAP 2906 → 2904).
`RV-15.4.1-L2.1`'s four recorded residues were each re-measured at HEAD rather than taken on trust: SQRT /
STANDARD-DEVIATION's 34-digit root and FACTORIAL(34) are closed by PB116/PB125 (measured —
`STANDARD-DEVIATION(1 2 3)` = 0.816496580927726032732428024901), MOD/REM is this landing, and the
"keeps more than 34 digits" residue is obsolete: the EAE-bearing functions still on the Int128 lane under a
standard mode are exactly ABS, INTEGER-PART, FRACTION-PART and SIGN, each a unary operation bounded by its one
≤31-digit operand and therefore exact in a 34-digit SDIDI too. `RV-15.76.4-1` was re-verdicted CONFORMS →
CONFORMS with its evidence WIDENED: its code-location and its only test-ref were both the FLOAT lane, so nothing
had ever exercised the native fixed-point arm that returned a negative range.

**Docs.** `COBOLNET_NUMERIC_DESIGN.md`'s escape-boundary section said MULTIPLY and that omission shipped twice —
rewritten as a per-OPERATION policy anchored on §14.7.5 r5, with r5/r3/r1 added to its ISO citation list;
`COBOLNET_INTRINSICS_DESIGN.md`'s always-SDIDI paragraph now states the structural rule and names the drift test.
The class summary in `CobolIntrinsics.Exact.cs` carried the FALSE premise that made the omission look safe
("MOD/REM … ≤31 digits", "SUM … ≤32-digit sums per step") — those are the UNALIGNED bounds — and is corrected.
No diagnostic code was needed.
