# PB1399 — LANDED (wave 1009 B)

## Landed

Re-probed on the wave's own build: the note's program reproduced exactly (`COBOLNET0844` on `SET TX TO FUNCTION
MAX(IA IB)`, `COBOLNET2326` on `SET IC TO FUNCTION MIN(IA IB)`). The fix is the note's own "what the fixer owes",
taken to the root: the sender is classified by what it IS, not by how it is written. `SetSenders.Classify` (new,
`SetSender.cs`) reads the sending `arithmeticExpression` once and returns a `SetSender` — a data reference, a bound
function-identifier / inline method invocation / keyword-omitted function, or neither — and `IndexAssignmentSenderOf`
asks its CLASS (`IntrinsicArgumentRules.ClassOf`, which un-folds §15.2 item 6's index functions that the storage
model folds into category numeric): class index is the identifier-2 alternative (`cite.py --check 14.9.39.3
"Identifier-2 shall reference a data item of class index"` OK), so `SET TX TO FUNCTION MAX(IA IB)` positions the
index-name at the occurrence number (§14.9.39.4 GR2 a) and `SET IC TO FUNCTION MIN(IA IB)` copies it into the index
data item (GR2 b), with §14.9.39.3 SR3 satisfied. A function of any OTHER non-numeric class still draws §8.8.1.1's
screen (`ExpressionBinder.ScreenIdentifierOperand`, now `internal`: the same call `BindIdentifierOperand` makes), so
`pb172-set-to-alphanumeric-function` is unchanged; a NUMERIC receiver now draws SR4 alone
(`pb1399-set-numeric-receiver-index-function`).

**The sweep (PB1929 is the other half).** The note's last sentence asked for the other SET formats' sender
classifiers: Formats 5, 7, 8 and 9 took the same `OoExtractBareReference` sniff, and PB1929 measured their refusal
(`COBOLNET0867` / `0869`). All four now read the one `SetSender` (see PB1929). The formats that bind the amount as an
expression of their own (14, 16) are decided from the receiving list BEFORE the sender is classified, because a
classification binds a function-identifier and its activation registers a statement pre-op.

Witnesses: `conformance:85/pb1399_set_index_function_sender` (MAX, MIN, an index-data-item receiver and the
subscripted `IXE(1) IXE(2)` form; 85 because intrinsic functions compile at every edition, like
`85/pb1662_index_name_against_function`), negative `pb1399-set-numeric-receiver-index-function`. The inventory row
`GR-8.5.2.8-2` was already CONFORMS through PB1398; this landing adds its SET-sender witnesses.

## Finding — `class-and-category-of-data-items-and-literals-p1` (rejects-legal-source; rows `GR-8.5.2.8-2`)

**Mechanism.** F2 - The SET Format 1 sender classifier only recognizes identifier-2 (a data item of class index) when the sender is a BARE DATA REFERENCE. IndexAssignmentSenderOf returns ArithmeticExpression whenever OoExtractBareReference yields null, which includes every function-identifier, so an INDEX FUNCTION sender never reaches the identifier-2 alternative. It is then refused by §14.9.39.3 SR3 (index data item receiver) or by the §8.8.1.1 arithmetic class screen (index-name receiver).

MOVE "ABCDEFGHI" TO T SET TX TO 3 SET IA TO TX SET TX TO 7 SET IB TO TX SET TX TO FUNCTION MAX(IA IB) DISPLAY "MAX->" TE(TX) SET IC TO FUNCTION MIN(IA IB) SET TX TO IC DISPLAY "MIN->" TE(TX) STOP RUN. (probe E:\Temp\claude\E--CobolSharp\a700c052-f9e4-4942-84ff-a13c7505d6ec\scratchpad\adj-d2\out\probe\cat1\p8.cob, pinned cobol.exe, --std 2023 and --std 85)

**Expected from the spec.** Compiles and prints 'MAX->G' then 'MIN->C'. §15.59.1 / §15.63.1 give MAX/MIN over Index arguments an Index result. §15.2 item 6 says 'Index functions. These are of the class and category index', and a function 'may be used anywhere a sending data item of that class and category may be specified'. §8.5.2.8 item 2 makes an index function an index data item, and §8.4.3.2.1 says a function-identifier references a data item. So the sender satisfies §14.9.39.3 SR2 'Identifier-2 shall reference a data item of class index'. §14.9.39.4 GR2 then places the occurrence number in the index (index-name receiver) or copies it unchanged (index data item receiver).

**Observed / reasoning.** Line 16: 'error COBOLNET0844: FUNCTION MAX (an index function, ISO §15.2) is not a numeric operand: ISO §8.8.1.1 ...'. Line 18: 'error COBOLNET2326: SET 'IC' TO 'FUNCTIONMIN(IAIB)' violates ISO §14.9.39.3 SR3: "If identifier-1 references a data item of class index, arithmetic-expression-1 shall not be specified"'. The compiler types the result correctly as an index function (its own message says so) but routes it to the arithmetic-expression alternative. The header of conformance:2023/pb124_index_function says an index function participates in 'a relation condition ... and nowhere else', which is why the SET identifier-2 position was never tested. The same bare-reference sniff (OoExtractBareReference) selects the sender in the Format 5/7/8/9 pointer and object senders too. Those formats have no function type of their class today, but a sweep should confirm that.

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SetBinder.cs#SetBinder.IndexAssignmentSenderOf (`if (senderDref is null) return IndexAssignmentSender.ArithmeticExpression;`); src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SetBinder.cs#SetBinder.BindSetTo

## What the fixer owes

Classify the sender by its bound CLASS (a BoundComputedOperand whose result is class index is identifier-2), not by syntactic bareness; sweep the other SET formats' sender classifiers for the same test.
