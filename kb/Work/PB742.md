Reported 2026-09-06 by the `PB699` fix-lane implementer (report

| probe | file control entry | result |
|---|---|---|
| `pb742a.cob` | `SELECT SQF ASSIGN TO "…" ORGANIZATION IS SEQUENTIAL RECORD KEY IS SQ-KEY` | **compiles clean**, runs, `OPEN=35` |

Zero diagnostics of any severity in both. (`'35'` is only the absent input file; it is the proof that binding and

is the one that matters: it is not a contrived spelling, it is the shape a program written without an
ORGANIZATION clause has, and §12.4.5.10.3 GR6 is what puts it on the wrong side of SR8.

## What the standard prints

Both rules re-derived with `cite.py --check`; neither clause number was taken from the report:

- `--check 12.4.5.2 "Format 1 shall be specified only for an indexed file"` → **OK §12.4.5.2 8)** —
  *"Format 1 shall be specified only for an indexed file. The associated file description entry shall not be a
  sort-merge file description entry."* Format 1 of §12.4.5.1 is the file control entry format carrying RECORD KEY
  and ALTERNATE RECORD KEY.
- `--check 12.4.5.2 "Format 2 shall be specified only for a relative file"` → **OK §12.4.5.2 9)** — the twin, for
  Format 2 and RELATIVE KEY. It is in the same note because a rule set with one member enforced is the shape
  where the missing member is hardest to see (`feedback_model_the_rule_shape_not_one_case`), and because
  `KeyedValidateFile` today enforces §12.4.5.13.3's RELATIVE KEY rules **only after** checking
  `file.Organization != FileOrganization.Relative` — i.e. it *skips* the very entry SR9 forbids.
- `--check 12.4.5.10.3 "When the ORGANIZATION clause is not specified, sequential organization with the RECORD
  SEQUENTIAL phrase is implied"` → **OK §12.4.5.10.3 6)**. This is why the common shape is caught: the compiler
  already knows it (`DataBinder.cs:891` quotes GR6 verbatim, and `:918` renders *"record sequential by default,
  the ORGANIZATION clause being omitted (ISO §12.4.5.10.3 GR6)"* into a diagnostic), so nothing has to be
  inferred — the organization is bound to record sequential and the key clause is bound beside it, and the two
  facts are never compared.

## Why it is harm and not tidiness

`under_rejects` + `silent`. The user's key semantics are not *misapplied*, they are **absent**: the RECORD KEY
name resolves, is stored on the `FileModel`, and then nothing reads it, because every key consumer is on a keyed
path a sequential file never enters. A program written against a mistaken belief that `RECORD KEY` makes a file
keyed compiles, runs, and reads its records in arrival order with no indication whatever that half its file
control entry was inert. It is MINOR only because the mistake is a program's own, and no correct program's
output changes.

## The code, at current line numbers on `89555b09`

There is **no** site that compares a key clause against the organization. The two places that could:

- `DataBinder.cs:854` captures `RECORD KEY` unconditionally
  (`(file.RecordKeyName, file.RecordKeyQualifiers) = KeyReference(rk);`) with no organization test, and
  `DataBinder.ResolveFiles` resolves it at `:1420` the same way.
- `KeyedIoBinder.KeyedValidateFile` (`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/KeyedIoBinder.cs:407`)
  holds every key-clause syntax rule the compiler does enforce — §12.4.5.12.3 SR1 / §12.4.5.6.3 SR1 (no OCCURS),
  §12.4.5.13.3 SR1/SR2/SR3 — and it is reached **only from a keyed verb**, which is PB699's whole subject. A
  sequential file never has one, so even a rule written there would not fire for this defect. **SR8/SR9 are
  entry rules and have to be enforced where the entry is bound.**

## The fix shape

⛔ **Land it as two more rows in `FileControlKeyRules`, not as two `if`s.** PB699's fix (train 16 row 6, in
flight — `status: open` on `kb/Work/PB699.md`, `FileControlKeyRules.cs` not yet on main) moves the file control
entry's key rules out of `KeyedValidateFile` into a table evaluated when the ENTRY is bound, keyed today on the
clause and the file's organization. SR8 and SR9 are the same shape one column over — a row that fires on the
CLAUSE's presence and the organization's *disagreement* rather than on a keyed verb — so once that table exists
this is two rows and a diagnostic message, and the generalization the report describes ("keyed on the CLAUSE's
presence rather than on the file's organization — a small generalization of the table's `Organization` column")
is the whole of the work. **This note is therefore blocked in practice on PB699 landing**, not by a
`blocked_by` dependency but by the fact that landing it first would build the second mechanism PB699 exists to
remove (`feedback_one_mechanism_per_job`). Diagnostic code: take it from `pwsh scripts/session-probe.ps1`'s
next-free, never a guessed number — and the message must name the *organization* the entry actually has,
including the "by default, the ORGANIZATION clause being omitted" case, or the common shape produces a
diagnostic the user cannot act on.

⛔ **Sweep the external corpus BEFORE it lands.** This rule newly REJECTS source that compiles today, and the
population it rejects is exactly the sloppy-but-widespread `SELECT … RECORD KEY` with no ORGANIZATION clause.
`feedback_edition_gate_sweep`'s reasoning applies unchanged even though this is not an edition gate: run the
GnuCOBOL differential and the external corpus (`tests/external/gnucobol/tests/`) and count the newly-refused
programs before the commit, not after. If a real population is hit, the answer is a dialect-strictness decision
(the version × strictness model — `docs/COBOLNET_DESIGN.md:183`, *"(version × strictness) model applies
throughout"*), not a quiet deferral — CLAUDE.md rule 3.

**Rows claimed:** `SR-12.4.5.2-8` and `SR-12.4.5.2-9`, both GAP today. They are claimed together because one
screen closes both and a note claiming only SR8 would leave a rule whose enforcement site had already been
written (`feedback_a_dead_lookup_is_also_unverified`).

## Sweep

- **The rest of §12.4.5.2's format rules.** SR11 is already known to the binder — `DataBinder.cs:898-899` quotes
  it verbatim, and `--check 12.4.5.2 "Format 3 shall be specified only for a sequential file or a report file"`
  → **OK §12.4.5.2 11)** — though it is quoted there to DERIVE where LINE SEQUENTIAL sits, not enforced; SR7 is
  genuinely enforced (`DataBinder.cs:1443-1475`, COBOLNET1811). SR8 and SR9 are the two members of that family
  with no site at all — the *dead* members of a set whose other members are live, which is the shape this
  repository has been bitten by repeatedly.
- **The `SORT-MERGE` half of both rules** — *"The associated file description entry shall not be a sort-merge
  file description entry"* is a second obligation inside SR8 and SR9, over the SD rather than the organization.
  Read the whole printed rule before writing the row; do not close SR8 on its first sentence.
