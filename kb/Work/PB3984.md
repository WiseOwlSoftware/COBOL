# PB3984 — fuzz_triage's triage directory is documented as outside every git checkout, but coord.scratch_problem checks only this repository's checkout and its main checkout, while readonly_repo.py refuses a write inside ANY git working tree

**Sites:** `scripts/fuzz_triage.py:403` (`triage_directory`), `scripts/orchestrator/coord.py:207` (`scratch_problem`), `scripts/hooks/readonly_repo.py`

Found by the round-2 review of PB3972: branch `worktree-wf_aee78301-ec3-5` (PR #714, bounced from the merge queue, under a finisher).
`scripts/fuzz_triage.py` is not on origin/main yet; the lines cited are on that branch (tip `10fe2567e`). Re-check against main once
PB3972 lands. Source: PB3972's report, "Review findings" R2-1.

> R2-1 LEAD (low, not blocking at round 2): scripts/fuzz_triage.py:403 triage_directory claims to keep the triage directory OUTSIDE every
> git checkout (docstring, --triage help, design section 3.2), but coord.scratch_problem checks only this repository checkout and its main
> checkout, while readonly_repo.py refuses a write inside ANY git working tree.

Failure scenario: `--triage` naming a path inside some other clone passes `scratch_problem`, then every read-only adjudicator and
refuter Write into it is refused by `readonly_repo.py`, so the verdict files are never written.

## Acceptance
- One rule decides where a fleet's files may live: either `scratch_problem` refuses any path inside a git working tree (the
  `readonly_repo.py` test, shared not copied), or the docstring, `--triage` help and design section 3.2 stop claiming "every
  checkout". A test passes a path inside a foreign clone.
