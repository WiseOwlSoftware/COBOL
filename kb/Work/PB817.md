# PB817 — LANDED — two carriers of one USAGE tail, one rule between them, written once

## LANDED — 2026-09-12, with [[PB452]]'s Format 8 (batch `pb452-pb817-set-format-8-function-pointer`)

Both rows are `CONFORMS`. **The note's central claim was taken literally and is now the code's shape:** §14.9.39.3 SR20 and SR22 are ONE same-signature test, `PrototypeSignatures.Same`, over ONE carrier field, `PicInfo.RestrictedPrototypeName`, which holds the `TO {function|program}-prototype-name-1` operand for both USAGE clauses; the CATEGORY says which namespace resolves the name (§8.4.6.6 vs §8.4.6.8 — themselves the same sentence twice, and screened by one block in `DataBinder`), and COBOLNET1959 is one code because it is one rule.

* **Both declarations bind.** `PictureAnalyzer.ParseUsage`'s FUNCTION-POINTER arm no longer stages loud and the PROGRAM-POINTER `TO` arm no longer draws `ProgramPointerRestricted`; both 0899 descriptors were DELETED. `PicCategory.FunctionPointer` + `PicInfo.FunctionPointerItem` carry the new category.
* **`SetBinder`'s re-route gained its function-pointer arm in the same change set** — the note's “the other end, which a fixer will otherwise miss”. Without it a declarable function-pointer would have fallen through into the Format-1 arithmetic store.
* ⛔ **ONE THING IN THIS NOTE DID NOT HOLD, and it changed the work.** The measurement calls `01 PP USAGE PROGRAM-POINTER TO PBRPRO2.` conforming; §13.18.60.3 **SR19** makes it nonconforming — *“If program-prototype-name-1 is specified, the TYPEDEF clause shall be specified for the subject of the entry”* — exactly as SR18 does for `POINTER TO type-name-1`. SR19 was UNIMPLEMENTED ([[PB497]], [[PB609]]), and lifting the staging without it would have turned a latent under-rejection into a live one, which PB497 predicted outright. SR18 and SR19 are now ONE screen, and the conforming spelling is the 2002 golden `conformance:2002/pb817_restricted_program_pointer` (a TYPEDEF restricted program-pointer, SET TO ENTRY, copied under SR22, set to NULL, and CALLed through). There is NO function-pointer twin of SR18/SR19 — measured: §13.18.60.3 stops at SR21 and carries no function-prototype-name sentence.
* **An UNRESTRICTED sender is an SR22 violation**, not a vacuous pass: the rule requires prototypes “associated with identifier-7 and identifier-8” and an unrestricted program-pointer is associated with none (`conformance:negative/pb817-set-program-pointer-signature`). That is deliberately DISTINCT from a prototype that names no compile-time signature — §12.3.8.4 GR10 c)'s external repository — which conforms, because refusing it would reject a legal separately-compiled target.
* **Rows beyond this note's two** closed with it and are recorded on [[PB452]] and [[PB497]]: GR-13.18.60.4-25, GR-13.18.60.4-26 and SR-13.18.60.3-19.
* **Still open, and deliberately not claimed:** [[PB609]]'s `SR-14.9.4.3-14` — the CALL-side consumption of the restriction — and `StrongTypeModel.PointerRestriction`'s missing `ProgramPointer` arm.

## The rules, quoted, from the transcription

> 20) Identifier-12 shall reference a data item of category function-pointer. Identifier-13 shall be of category
> function-pointer. Identifier-13 shall be the predefined address NULL or shall reference a function-pointer.
> The function-prototypes associated with identifier-12 and identifier-13 shall have the same signature.
>
> 22) If identifier-7 references a restricted program-pointer, identifier-8 shall be the predefined address NULL
> or shall reference a program-pointer and the program-prototypes associated with identifier-7 and identifier-8
> shall have the same signature.

`--check` lines, re-run rather than inherited from the rows' notes:

```
$ python scripts/spec/cite.py --check 14.9.39.3 "Identifier-12 shall reference a data item of category function-pointer"   -> OK  §14.9.39.3 20)
$ python scripts/spec/cite.py --check 14.9.39.3 "the program-prototypes associated with identifier-7 and identifier-8 shall have the same signature"  -> OK  §14.9.39.3 22)
```

**They are the same rule twice.** "The *X*-prototypes associated with the two identifiers shall have the same
signature", over function-prototypes and program-prototypes. Writing it twice is how the two copies drift
(`feedback_one_rule_one_place`).

## The other end, which a fixer will otherwise miss

`SetBinder`'s category re-route (`BindSetTo`) tests `Pointer`, `ProgramPointer` and `ObjectReference` and stops
(`SetBinder.cs:63-64`, `:240-299`). **There is no function-pointer arm at all**, so even a declarable
function-pointer would fall through into the Format-1 arithmetic store — a silent wrong answer waiting behind
the loud one. Format 8 must acquire its re-route in the same change set as the declaration.
