# PB498

## Mechanism — picture-clause-p1
Two user-facing PICTURE diagnostics name a clause that does not carry the obligation they enforce - the 'a real clause can answer a different question' shape, where --check passes on the quoted text and the clause number is still wrong for the message. (1) PictureAnalyzer.cs:646 rejects an EDITING character-1 on a floating-point edited picture citing "ISO 13.18.40.3 SR12 a)", but SR12 a) sits inside the 'If the FOR phrase is specified' branch and its second sentence bars only EXTENDED editing sign control symbols; the probe that trips it uses the IS form, which SR12's first sentence makes a FIXED editing sign control symbol. The rejection is correct on other authority - 13.18.40.6 gives 'es' the non-floating 'cs' precedence and Table 10 row E admits only B 0 /, ',', '.', the leftmost '+ -' and '9' before E, so no es may appear in a float-edited character-string - so only the citation is wrong. (2) COBOLNET0801/0802 report a PICTURE's digit-position overflow citing "ISO 8.3.3.3.2", which is Fixed-point numeric LITERALS; the picture obligation is 13.18.40.3 SR14, which the code comment at DataBinder.cs:2661 cites correctly while the message the user reads does not.

### Expected, from the standard
The message shall cite the clause that carries the obligation. For (1) that is ISO/IEC 1989:2023 13.18.40.6 - "If the EDITING phrase is specified, the precedence of 'es' as related to Table 10 ... has the same precedence as the 'cs' symbol in the column and row of non-floating insertion symbols" plus Table 10 row E - with 13.18.40.3 SR12 a) cited only for the extended (FOR) case it actually governs. For (2) it is 13.18.40.3 SR14, "the number of digit positions described by character-string-1 shall range from 1 through 31" (with the COBOL-85 18-digit cap named as the edition restriction it is); 8.3.3.3.2 remains the right citation for the literal-side leg of the same diagnostic, which is why the message needs both, chosen per site.

```
$ python scripts/spec/cite.py --check 13.18.40.3 "the number of digit positions described by character-string-1 shall range from 1 through 31"
  OK  §13.18.40.3 14)  (Syntax rules)
```

### Observed
Both citations were validated mechanically against specs/ISO_COBOL.md: the quoted TEXT of SR12 a) and of 8.3.3.3.2 exists, which is exactly why the defect survives a --check-style validation - the clause is real, it just answers a different question. No behaviour is wrong at either site, so the harm is silent: a maintainer who follows the citation reads a rule about extended sign control symbols (or about numeric literals) and cannot reconstruct why the compiler rejected the program, and the wrong clause number is exactly what propagates into the next design doc and golden.

## Mechanism — value-clause-p2
A CITATION DEFECT OF THE INHERITED KIND. src/Cobol.Net.Compiler/Binding/DataBinder.cs:2125-2130 refuses a THROUGH range over a NATIONAL conditional variable with COBOLNET0899 and cites "(ISO 13.18.63 SR31)"; docs/DIAGNOSTICS.md:34 carries the same attribution for diagnostic id `national-through-range` ("ISO 13.18.63 SR31"), and src/Cobol.Net.Editions/Diagnostics/DiagnosticCatalog.cs:486 repeats the string. SR31 is about alphabet-name-1: when it may be written, and which class of alphabet it shall reference. It says nothing about whether a national THROUGH range is permitted -- SR31's own second sentence PRESUPPOSES that national literal-2/literal-3 ranges are legal. The rule that would license refusing them is not SR31; the refusal is a staged-not-implemented decision ("Phase 4a residue") wearing a syntax rule's citation. The comment block at DataBinder.cs:2121-2124 states the position correctly ("A national THROUGH range is spec-legal but orders under a NATIONAL alphabet (SR31) -- recognized, staged"), so the defect is that the user-visible text and the docs promote an explanatory aside into the rule being enforced.

### Expected, from the standard
SR31 (13.18.63.3): "Alphabet-name-1 may be specified only when the literals specified in the THROUGH phrase are of class alphanumeric or national. If literal-2 and literal-3 or literal-5 and literal-6 are of class national, alphabet-name-1 shall reference an alphabet that defines a national collating sequence; otherwise, alphabet-name-1 shall reference an alphabet that defines an alphanumeric collating sequence." (cite --check OK) A diagnostic refusing a national THROUGH range shall not cite SR31 as its authority: SR31 permits such ranges and only constrains the alphabet they may name. A recognized-not-implemented refusal should cite the construct it stages (13.18.63.2 Format 3 with a national conditional variable, and 14.7.8 rule 2 for the ordering it cannot yet perform) and name the staging decision, not a syntax rule the source does not violate.

```
$ python scripts/spec/cite.py --check 13.18.63.3 "Alphabet-name-1 may be specified only when the literals specified in the THROUGH phrase are of class alphanumeric or national. If literal-2 ..."
  OK  §13.18.63.3 31)  (Syntax rules)
```

### Observed
MEASURED at --std 2023. This is the inherited-citation shape the project has been bitten by before: the quoted rule genuinely exists and genuinely concerns the same clause, so `cite.py --check` passes on its text, and the wrong attribution then propagates from the code comment into the diagnostic message and into docs/DIAGNOSTICS.md. Cost today is only diagnostic quality (a user reading SR31 will not find the prohibition the message implies), which is why the harm is recorded as silent; but the same citation is the one a future implementer will follow when the national ordering lands, and SR31 will send them to the alphabet-name channel that this part's main finding shows does not exist.

## Mechanism — value-clause-p4
Two sites cite '13.18.63 GR6' for behaviour that 13.18.63.3 SR6 defines -- the conversion of a numeric VALUE literal on a numeric-edited item to its edited form. GR6 in 13.18.63.4 is the OCCURS ... DEPENDING initialization rule ('behaves as if the value of the data item referenced by the DEPENDING phrase ... is set to the maximum number of occurrences'), an unrelated subject. This is the inherited-citation failure mode CLAUDE.md rule 1 names: the quoted behaviour is genuinely in the standard, so a --check on the TEXT passes, but the clause NUMBER was never re-derived and it has now propagated from a code comment into a conformance test's summary. It is worth fixing because the mis-cite makes GR6 look covered by a test that tests something else -- exactly the trap this adjudication has to avoid when it looks for a covering witness.

### Expected, from the standard
13.18.63.3 SR6: 'If the item is of category numeric-edited, then, subject to Syntax rules 2 and 3, literals in formats 1, 2, and 4 of the VALUE clause may be numeric when they shall be converted to their numeric-edited forms according to the rules for the MOVE statement ...'. 13.18.63.4 GR6 is the occurs-depending initialization rule.

```
$ python scripts/spec/cite.py --check 13.18.63.4 "If the item is of category numeric-edited, then, subject to Syntax rules 2 and 3, literals in formats 1, 2, and 4 of the VALUE clause may be..."
  FAIL: §13.18.63.4 exists but does NOT contain 'If the item is of category numeric-edited, then, subject to Syntax rules 2 and 3, literals in formats 1, 2, and 4 of the VALUE clause may be numeric when they shall be converted to their numeric-edited forms according to the rules for the MOVE statement '
$ python scripts/spec/cite.py --check 13.18.63.3 "If the item is of category numeric-edited, then, subject to Syntax rules 2 and 3, literals in formats 1, 2, and 4 of the VALUE clause may be..."
  OK  §13.18.63.3 6)  (Syntax rules)
```

### Observed
Both sites say GR6 where SR6 is meant. Confirmed by reading both clauses in the spec; `cite.py --check 13.18.63.3 "...converted to their numeric-edited forms..."` resolves to SR6 and `--check 13.18.63.4 "...set to the maximum number of occurrences..."` resolves to GR6.
