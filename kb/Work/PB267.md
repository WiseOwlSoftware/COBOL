# PB267 — the loop-bound probe used as a value

Found by the arithmetic-wave review fleet over the D-B/D-C/PB194/PB195 working tree, 2026-08-31, and fixed in the change set that landed the wave. Every number below was re-derived independently by the implementer (a 34-digit emulation of `CobolDec.cs` validated against the shipped `pb167` goldens, and 80–120-digit `Decimal` truth) BEFORE the confirming run, and then confirmed by it.

## The mechanism

`TryIntegerValue` reports integer-ness and a magnitude, CLAMPING the magnitude at `long.MaxValue`. Its own doc
asserted the caller *"rejects it before the MAGNITUDE is used"*. It does not — the loop bound only ROUTES it, and
the escape then built `PowCore`'s exponent as `new CobolDec(±clamped, 0)`. So the development answered a
different expression than the one written, with no diagnostic, for every exponent past 2⁶³−1.

Pre-existing (the deleted `PowByLogs` consumed the same clamped value); what the D-C wave did was CERTIFY it, by
flipping GR-8.8.1.5.4-2 to CONFORMS with this arm inside the claim.

## Measured, before and after (probe `za2sat.cob`, `--std 2023`, STANDARD-DECIMAL)

```
                                                      BEFORE                  AFTER
(1+10**-33) ** 1.0E+20   into 9V9(13)         10000000000000          10000000000001
(1+10**-33) ** 1.0E+36   into 9V9(13)         10000000000000          SE EC-SIZE-TRUNCATION
0.9999999999999999 ** 1.0E+25 into 9V9(13)    00000000000000  (silent) SE EC-SIZE-UNDERFLOW
1.0000000000000001 ** 1.0E+25 into 9V9(13)    SE EC-SIZE-TRUNCATION   SE EC-SIZE-OVERFLOW
```

Derived first: ln(1 + 10⁻³³) ≈ 10⁻³³, so 10²⁰ × ln b = 10⁻¹³ and the value is
exp(10⁻¹³) = 1.000000000000100000000000005 — while the clamped probe computes
exp(9.223372036854775807×10¹⁸ × 10⁻³³) = 1.0000000000000092, equal in the first thirteen fraction digits.
At 10³⁶ the true value is exp(1000) = 1.97E+434, past every fixed-point receiver.

## The fix

`PowMagnitude` carries the exponent OPERAND. An SDIDI holds |operand-2| exactly, so there was never anything to
reconstruct; the clamped number's only remaining consumer is the `> LoopBound` comparison and the
square-and-multiply loop under it, where by construction it has not clamped. `TryIntegerValue`'s doc says so.

## ⛔ And the disposition is NOT "|base| ≷ 1 ⇒ out of range"

The obvious repair — screen a clamped exponent by which side of 1 the base is on — is PB145's spurious size error
again. The closest SDIDI value to one is 1 ± 10⁻³³, and (1 + 10⁻³³) ** 10²⁰ = 1.0000000000001 is comfortably
representable. `pb167`'s NEARU leg and `PastLongRangeExponent_UsesTheOperand_NotTheClampedBoundProbe` pin the
value precisely so that repair cannot be made later by accident.

## The second half: naming the right condition

With the true exponent flowing, `Mul(p, ln b)` can itself leave the decimal128 range — `1.0E-6176 ** 1.0E+6144`
has |p × ln b| ≈ 1.4E+6148 — and `Round34Wide`'s clamp raises EC-SIZE-OVERFLOW whichever way the RESULT is out of
range. For ln b < 0 the result is out of range DOWNWARD, which §8.8.1.5.2 r2 gives its own name. `PowCore` now
screens the ORDER of the product before forming it: `Order(p) + Order(ln b) > 6` ⇒ |p × ln b| ≥ 10⁵ ⇒
|q| > 43 000, past BOTH of `Exponential`'s range screens, so the result is certainly out of range and — p being a
magnitude — the DIRECTION is the sign of ln b alone. Below the threshold the product cannot overflow and
`Exponential`'s own screens, which see the exact q, keep sole authority: no second range verdict is introduced.
