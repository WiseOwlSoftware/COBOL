# PB463 — the determination that declares the overflow case unreachable is false

**Row:** `GR-14.9.39.4-38` (SET Format 16 — the length is set to integer-2 or to arithmetic-expression-5, with a
clamp-to-maximum plus EC-STORAGE-NOT-AVAIL, and a storage-unavailable leg). From the b2 adjudicator
`set-statement-p5`. **Re-run on the HEAD `cobol.exe` (base 89044aa0)**; reproduces unchanged, and I measured a
SECOND arm the finding predicted from reading but did not run.

## THE MECHANISM

`CobolDynString.SetSize` (`src/Cobol.Net.Runtime/Values/Text/CobolDynString.cs:49-68`) computes the new length
as a `long`, clamps it to the item's LIMIT **only when `limit >= 0`** (`:58`), and then returns:

```csharp
CobolDynString.cs:67
    return n <= current.Length ? current[..(int)n] : current + new string(' ', (int)n - current.Length);
```

Two unchecked `long → int` narrowings, on both the shrink arm and the grow arm. A dynamic-length item written
WITHOUT a LIMIT phrase has `DataItem.DynLengthLimit = -1` (`Binding/Model/DataItem.cs:314`), so the `:58` clamp
is skipped entirely and ANY requested length reaches those casts:

* a request of 2³² + k silently becomes k — the item gets a length nobody asked for, exit 0, no condition;
* a request between `int.MaxValue` and 2³² narrows to a NEGATIVE `int`, and `new string(' ', negative)` throws
  a raw `System.ArgumentOutOfRangeException` straight out of generated code.

`docs/CONFORMANCE.md:257-263` pins the opposite as a determination: "a dynamic-length elementary item is a
managed .NET `System.String`, always allocatable within the runtime string limit, so the … branch is
unreachable. **Pinned choice: that third leg never raises**". That is true only if something bounds the request,
and **nothing does** — `DynLengthLimit = -1` means "no bound", not "the implementor maximum". The determination
describes an implementation the code does not have.

(The same determination block ends "The integer-2 literal form is compile-time bounded by SR34, so its
out-of-range cases are compile diagnostics, not this runtime EC." That is measurably false as well — PB458.)

**Expected.** 4294967306 (and 3000000000) exceed any maximum size this runtime can offer (§8.5.1.10.1), so the
conforming outcomes are GR38's clamp leg — length set to the implementor maximum with EC-STORAGE-NOT-AVAIL set
to exist — or GR38's storage-unavailable leg — length unchanged at 5 with EC-STORAGE-NOT-AVAIL set to exist.
Neither is a wrapped length of ten, and neither is a raw .NET exception escaping generated code.

The `crashes` flag on this note is **measured**, not read: the second probe above is a raw framework exception
on legal COBOL, which is the failure mode the project forbids.

## THE CODE SITES AND THE SHAPE OF THE REPAIR

| site | today |
| --- | --- |
| `Runtime/Values/Text/CobolDynString.cs:58` | `else if (limit >= 0 && newLen > limit)` — the clamp is skipped when there is no LIMIT |
| `Runtime/Values/Text/CobolDynString.cs:67` | `current[..(int)n]` and `new string(' ', (int)n - current.Length)` — two unchecked narrowings |
| `Binding/Model/DataItem.cs:314` | `public int DynLengthLimit { get; set; } = -1;` — the sentinel that means "no bound at all" |
| `docs/CONFORMANCE.md:257-263` | the determination this contradicts (⛔ this note does not edit that file) |

⛔ **The repair is NOT a cast guard** (CLAUDE.md rule 5). Guarding `(int)n` converts a silent wrong length into a
loud one and leaves the model wrong. §8.5.1.10.1's "maximum permitted by the implementor" must become a REAL
implementor maximum that `DynLengthLimit` **falls back to** when no LIMIT phrase is written, so that:

* GR38's clamp leg becomes the ONE path for an over-large request, with EC-STORAGE-NOT-AVAIL set as the rule
  says;
* the storage-unavailable leg becomes genuinely unreachable — which is what the determination already claims,
  and it will then be true;
* `(int)n` becomes safe by construction rather than by inspection, and GR39's fill (`:67`) stops being a
  narrowing site;
* the maximum is itself an implementor-defined item, so it belongs in the same determination block in
  `docs/CONFORMANCE.md` (the A.1 register discipline PB460 asks for).

Sentinel-as-`-1` is the shape that made this possible: "no LIMIT clause" and "no maximum" are different facts
and one field holds both. Prefer a real default over a sentinel the clamp has to special-case.

## LANDED — 2026-09-13 (train 33 candidate)

**The implementor maximum exists, and it is what every leg of GR38 is now stated against.** §8.5.1.10.1's
"smallest of" became a real computation in ONE place — `CobolDynString.MaxSizeOf(Int128?)`: the LIMIT phrase read
WIDE (integer-1 no longer goes through an `int.TryParse` that DROPPED an out-of-range literal and left the item
unbounded — that parse was the compile-side half of this defect and it had never been measured), bounded by
`CobolDynString.MaxLength = 0x3FFFFFDF`, the implementor maximum, which is the carrier's own ceiling: a
dynamic-length item IS a native `System.String`. `DataItem.DynLengthLimit` became `DataItem.DynMaxSize`, defaulting
to that maximum, and every reader — `StorageFormPass`, `SetBinder`, `SendingValueTemp`, `MoveEmitter`,
`ValueInitializer`, `GroupImageCodec`, `ProgramEmitter` — now reads a real bound. `StorageForm.DynamicString.Limit`
and `BoundSetSize.Limit` were renamed `MaxSize` for the same reason: the field is the §8.5.1.10.1 maximum size, not
the written phrase, and the sentinel is gone rather than guarded.

**Measured, on this worktree's build.** Before: `SET SIZE OF WS-D TO 4294967306` on a no-LIMIT item gave
`LEN=000000000010` with an empty EXCEPTION-STATUS, and `TO 3000000000` threw
`System.ArgumentOutOfRangeException: count ('-1294967301')` out of `__Dispatch`. After: both print
`LEN=001073741791  EC[EC-STORAGE-NOT-AVAIL]` — GR38's clamp leg, which is now the ONE path for an over-large
request, with the narrowing exact by construction.

**GR38's third leg is implemented, not declared unreachable.** The maximum is a ceiling on the SIZE, not a promise
the host can hand over two gigabytes, so an `OutOfMemoryException` at the growth site returns the item UNCHANGED
with the condition set to exist (once per statement — a request that already took the clamp leg has set it). The
`docs/CONFORMANCE.md` §4 determination that read "always allocatable … the branch is unreachable … that third leg
never raises" is rewritten to what the code does, and §7 gained row `DOC-A.1-62` carrying the maximum in both
published spellings. `DynamicLengthTests.ImplementorMaximum_IsTheNumberPublishedInConformanceSection7` reads the
number back out of that row, so the determination and the constant cannot drift apart — the drift pin this note
asked for when it observed that a determination asserting a branch is unreachable is a claim about code.

**New diagnostic.** COBOLNET2027 (warning) — a LIMIT phrase above the implementor maximum. The entry stays LEGAL
(§13.18.19.3 bounds integer-1 only when a dynamic-length-structure-name is written too, SR4) and §8.5.1.10.1 simply
takes the smaller candidate; the report exists so a program planning on the larger bound learns of the smaller one
at compile time rather than through a clamped SET SIZE.

**Sibling sweep.** The other two “COBOL-supplied length narrowed to `int`” sites in `src/Cobol.Net.Runtime` already
carry this exact shape and were not touched: `CobolDynTable<T>.GrowTo` (wide `Int128` carrier, `MaxOccurrences`
tested BEFORE the narrowing — kb/Work PB459) and `CobolPtr.Allocate` (wide carrier, explicit `int.MaxValue` screen,
`OutOfMemoryException` → "not available" — kb/Work PB151). `CobolTiming.ContinueAfter`'s `(int)` is bounded by
`MaxSeconds` = 86 400. The dynamic-length site was the one left.

**Rows.** `GR-14.9.39.4-38` DIVERGES → CONFORMS and `DOC-A.1-62` GAP → CONFORMS, batch
`pb463-dynamic-length-implementor-maximum` (GAP 2501 → 2499). **Not closed here:** PB458 still owns
§14.9.39.3 SR34 (integer-2 compile-time bounded by the maximum size) and `GR-14.9.39.4-39`; SR34's screen is now
writable for the first time, because the maximum size it is stated against finally exists.
