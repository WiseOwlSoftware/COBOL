# PB4759 - the cd-name, file-name and data-name USE FOR DEBUGGING triggers are not modeled

**What the report says (New defect 1).** The cd-name, file-name and data-name USE FOR DEBUGGING triggers are not modeled (staged
COBOL1571 in `FinalizeDebug`), so legal CCVS DB205A (and the DB201A family's data and file triggers) is still refused. The report
says it needs DEBUG-ITEM and DEBUG-CONTENTS instrumentation of ENABLE, DISABLE, PURGE, RECEIVE and SEND, of file I/O and of
data statements, and that it was too large for the slice; the finisher's brief allowed it no note.

**R1.** No open note covers it. PB4713 (landed) modeled the part it did; PB175 and R61 (open) do not concern these triggers.

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/ProcedureTableBuilder.cs#FinalizeDebug`.

**Wave 20261879, group D: BLOCKED with no change (report `w20261879d-PB4759-report.md`).** The note still reproduces on
0f13f82fc: `cobol --nist DB205A` gives COBOL1571 twice, and `cobol --nist DB201A` gives COBOL1571 on every data trigger.
The implementer stopped for two reasons. The trigger semantics come from X3.23-1985's Debug module chapter, which is not in
the repository, and ISO 2023 no longer has the facility. The work is also a redesign across `BoundDebugSubject`, `DebugItem`,
`DispatchEmitter` and every statement lowerer, not an edit to `FinalizeDebug`. It asked for an owner decision: supply the 1985
text, or name an IBM or Micro Focus reference.

The wave unit did not relay that as an owner question. CLAUDE.md rule 1 already names IBM Enterprise COBOL or Micro Focus
where GnuCOBOL has nothing, but no one has yet read either vendor's manual to see whether it covers these triggers, or
whether rule 1's latitude clause reaches a 1985-only facility. Do that first. Ask the owner only if it leaves the question
open. Then write a design-doc section and split the work by trigger kind (data-name, file-name, cd-name). Do not send this
note to a Sonnet implementer as one slice again. [[PB4808]] holds that reading, and this note is `blocked_by` it.

## Split (2026-11-05, after PB4808)

PB4808 found the data-name and file-name trigger rules in GnuCOBOL 3.3-dev and Micro Focus general rules 1-23; they moved to
PB4810 (data-name) and PB4811 (file-name). This note keeps ONLY the cd-name trigger. No readable source defines it: GnuCOBOL
records the target and never fires it, IBM supports procedure triggers only, and Micro Focus's rules never mention a cd-name.
Undetermined: which of ENABLE, DISABLE, PURGE, RECEIVE, SEND and ACCEPT MESSAGE COUNT fire it, before or after, and what
DEBUG-CONTENTS holds for each.

**Held on the owner (status owner).** Asked 2026-11-05 whether to buy ANSI INCITS 23-1985 (R2001) so the rules come from its
Debug module, keep cd-name triggers refused, or design them as implementor latitude; the owner asked for the purchase URL
(webstore.ansi.org/standards/incits/ansiincits231985r2001) and has not yet decided. Until then a cd-name trigger stays refused
(COBOL1571).

## Unblocked (2026-11-05): the 1985 text is in hand

The owner bought ANSI INCITS 23-1985 (R2001) and the 2002 standard (2026-11-05); both are in the private submodule
(`spec_pdf.path(1985)`, `specs-private/ANSI_COBOL_1985.pdf`). The Debug module's USE FOR DEBUGGING general rules,
cd-name-1 included, are around PDF page 698. The design section (with PB4810's) is written from that text first, under rule
2, citing module and page until PB4812's transcription lands; quotations in the public repository stay short. The PDF is a
scan with an OCR text layer, so each rule read from it is checked against the rendered page.

## Landed (wave 20261885, group A)

Read from the rendered pages of the owner's copy (PDF pages 693-698, each rule checked against the page image, not only the OCR layer):
USE FOR DEBUGGING general rule 8 — "After the execution of any ENABLE, DISABLE, and SEND statement that references cd-name-1; after the
execution of a RECEIVE statement referencing cd-name-1 that does not result in the execution of the NO DATA imperative-statement; and after
the execution of an ACCEPT MESSAGE COUNT statement that references cd-name-1" — and rule 23: DEBUG-NAME is the cd-name, DEBUG-CONTENTS "the
content of the area associated with the cd-name". PURGE is NOT in the list (this note's earlier text listed it; the standard does not).
Landed with PB4810 as `docs/CONTROL_FLOW_DESIGN.md` D20: a cd-name operand is a `BoundDebugTarget` of kind `CdName`, `DebugTriggerPlanner.PlanCd`
plans its fires, `CommunicationEmitter.EmitReceive` lands the RECEIVE one (`DebugWhen.AfterAction`, where the data arrived and before the WITH
DATA statements). DB205A compiles and runs but does not finish (killed after five minutes with an empty report file); the cause was not diagnosed
here — a RECEIVE with no NO DATA phrase on a queue the MCS does not seed waits for data, which is the communication facility's
behavior (PB4677) and not this note's mechanism; the report lists it as a lead. Golden
`conformance:wiseowl/cases/_unassigned/pb4759_debug_cd_name_triggers` (the MCS seeds its queue, `mcs.json`); `pb4713-debug-cd-name` now accepts.
