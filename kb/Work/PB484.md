# PB484 — LANDED — every report's vertical placement was off by one, and four goldens pinned it

Found 2026-09-04 by the `PB205` implementer, whose positive golden deliberately skips all-space lines so as
not to depend on the placement; re-derived on this tree for this note.

## Repro

An unpaged report (no PAGE clause — §13.18.39.4 GR2a: "If integer-1 is not specified, the report consists of
a single page of indefinite length") whose first body group is `LINE PLUS 1`: the report file begins with one
blank line, then the group. The paged twin is already in the corpus: `tests/conformance/2002/rw_suppress_bare`
declares `FIRST DETAIL 3` and its `.out` shows the first body group on line 4.

## The rule

```
python scripts/spec/cite.py --check 13.18.35.4 "the report group's first line number is obtained by adding integer-2 to the current value of the report's LINE-COUNTER"
OK  §13.18.35.4 5) 5. c)
python scripts/spec/cite.py --check 14.9.21.4 "LINE-COUNTER is set to zero."
OK  §14.9.21.4 1) b)
```

INITIATE sets LINE-COUNTER to zero (GR1b); the first `LINE PLUS 1` group's first line number is therefore
0 + 1 = 1 (GR5c). For a paged report the governing arm is GR5b3 — the first body group printed on the current
page takes the FIRST DETAIL integer as its line number — so with `FIRST DETAIL 3` the group belongs on line 3,
not 4. Both arms disagree with the tree by exactly one line, which points at one place: the line-number
computation in `src/Cobol.Net.Runtime/IO/ReportWriter.cs` (around the `LineCounter` arithmetic at `:381-405`
— `trial = LineCounter; … LineCounter + lines[i].Value` — read whether the first line is being advanced from a
counter that has already been incremented, or whether a "relative to the previous line" convention is being
applied to a counter that is still at its initial value).

## What closes it

The fix at that one site, derived from GR5b3 and GR5c side by side (the two arms must move together);
`2002/rw_suppress_bare.out` re-baselined FROM THE SPEC (line 3), with the derivation in the golden; a new
unpaged golden whose first body group is `LINE PLUS 1` and whose `.out` begins with the group on line 1; and a
sweep of every Report Writer `.out` in the corpus for a leading blank line or a FIRST DETAIL + 1 first line,
each re-derived. Sibling arms to check while there: GR5a (absolute LINE integer-1 on the first group) and
GR5d (a `LINE PLUS` group following a group that ended the page).


## Landed — 2026-09-21

RE-PROBED FIRST on this worktree's own build (base main 8e321d13b). An unpaged report whose first body group is
`LINE PLUS 1` and whose second is `LINE PLUS 2` printed FIRST on physical line 2 and SECOND on line 4 — every
line exactly one too low, as the note measured.

THE ROOT WAS THE TRAVEL, NOT THE LINE NUMBER. `ReportWriter.PresentBody` already computed the line NUMBERS
correctly (§13.18.35.4 GR5c `LineCounter + integer-2` unpaged, GR5b3 `_firstDetail` paged, GR7b for subsequent
lines) and `PresentLine` already assigned LINE-COUNTER from them (GR6, first half). The defect was GR6's SECOND
half — "the line is now printed on the page at that vertical location": `PresentLine` turned line number *n*
into *n* line advances of the print stream, and the stream rests AT page line 1 with nothing written (a record
emitted with no advance occupies line 1, both at INITIATE and after the §14.9.16.4 GR6b form feed). So every
line landed on n+1 and the report opened with a blank line. `_physLine == 0` means "this page is still empty",
not "line zero": the travel is now `target - 1` while it is empty and `target - _physLine` afterwards, and the
EC-REPORT-LINE-OVERLAP clamp (GR3) applies only once a line has been printed — on an empty page there is
nothing to overlap. ONE site, `src/Cobol.Net.Runtime/IO/ReportWriter.cs#PresentLine`; `_physLine` is written in
exactly two other places (INITIATE and `AdvancePage`), both of which mean the same empty page.

Both of the note's arms moved together, as it required: the paged GR5b3 arm now lands the first body group ON
the FIRST DETAIL integer (`2023/rw_suppress_bare` GROUP-1 on line 3, not 4) and the unpaged GR5c arm lands the
first body group on line 1. Sweep: every `.out` of every REPORT SECTION program in the corpus was re-run and
diffed (31 programs, 4 editions). Exactly four had recorded the extra blank line — `2023/rw_suppress`,
`2023/rw_suppress_bare`, `2023/rw_present_when`, `2023/declined_rw_present_varying_control` — each re-derived
from GR5/GR6/GR7 in its own comment block and re-baselined; the other 27 skip blank lines in their read-back and
were byte-identical before and after. New golden `conformance:85/pb484_report_line_placement` NUMBERS every
physical line, blanks included, so the placement can never drift silently again.

Rows: `GR-13.18.35.4-6` CONFORMS (both halves of GR6 now proved by the new golden). GR5, GR7 and GR8 stay
unverdicted — their unexercised arms (GR5b1/b2/b4/b5 heading and footing placement, GR7a a subsequent ABSOLUTE
line, GR8's NEXT GROUP alteration) have no spec-derived golden, and claiming them off this one would be the
over-claim the schema's evidence invariant forbids.
