**Scenario:** Binding.Model.FileAccessMode {Sequential, Random, Dynamic} and Runtime.IO.KeyedAccess {Sequential=0, Random=1, Dynamic=2} are one fact written twice and joined only by a comment: KeyedIoEmitter.EmitRegistration emits (int)file.AccessMode and FileRegistry.RegisterRelative/RegisterIndexed cast it back with (KeyedAccess)accessMode. Reordering either enum (or adding a member, e.g. a vendor access mode) compiles cleanly and silently swaps RANDOM and DYNAMIC at run time, which changes which §14.9.51.4 GR29 / §14.9.35.4 GR5-vs-GR21 / §14.9.10.4 GR2-vs-GR4 branch every keyed WRITE, REWRITE and DELETE takes; no test pins the ordinals (the only test use passes (int)KeyedAccess.Dynamic, i.e. the runtime side only). The sibling bridges show the cost of the pattern: SharingMode->FileSharing is hand-mapped in SequentialIoEmitter.RuntimeSharing, whose doc says it is THE ONE rendering because a second switch is a second place a new member is forgotten (kb/Work PB714), yet EmitSharingRegistration carries its own second copy of that switch (plus LockKind->FileLockMode, a third hand map).
