# PB754 — OPEN — an unguarded `Clear()` on shared state, and the two things that make it unreachable

Found 2026-09-06 by the `PB739` implementer (report, "New defects (b)"), which read the arm because PB739 moved
the `Clear()` call and explicitly left it **unmeasured** — *"deliberately left unmeasured because it is outside
the release path my dispatch fenced me to … **Probe it before filing a severity**."* This note honours that: it
verifies against main (`0a24276f`) by reading, files at MINOR/latent, states what the probe is, and **answers
one half of the report's open question by reading rather than leaving it open**.

## ⚠ On the harm flags — the register corrected the first draft of this note, and the correction is the lesson

This note was first written with **every harm flag false and `process_only: false`**, on the reasoning that an
unmeasured hypothesis should not be ranked beside measured defects. `python scripts/spec/work.py check` refused
it, in as many words:

> PB754.md: open defect with no harm flag set — it can never appear in `work.py next`. Set one of
> ['wrong_answer', 'crashes', 'rejects_legal_source', 'under_rejects'], or process_only: true if it genuinely
> does nothing to a user's program.

**The validator is right and the first draft was wrong**, for exactly the reason
`feedback_measure_the_selectors_complement` records (`work.py next` hid nine harmful items for months): a
flagless open defect is not "ranked cautiously", it is **invisible**, which is the one outcome a latent note must
not have. The flags say what the defect DOES **if reached** — records vanishing from every attached connector's
view, with `'00'` everywhere and no status to say so, hence `wrong_answer` + `silent`. **The latency is carried
by `severity: MINOR`, by this section, and by the title — not by pretending the consequence is nothing.**

⛔ The corollary still stands: **do not raise the severity to MAJOR without running the probe below**
(`feedback_reachability_is_measured_not_deduced`). MINOR here means *"the two defences in the next section are
verified and hold"*, not *"the consequence is small"*.

## The site

Two arms, identical in shape, both carrying the same comment naming the note that made the store shared:

`src/Cobol.Net.Runtime/IO/RelativeConnector.cs:113-118`

```csharp
case FileOpenMode.Output:
    Attach();
    _slots.Clear();                            // OPEN OUTPUT empties the SHARED view (kb/Work PB143)
    RecordFraming.WriteStore(HostPath, []);          // a new physical file; records persist at CLOSE
    _seqNext = 1;                              // §14.9.51 GR29a — first record released is 1
    break;
```

`src/Cobol.Net.Runtime/IO/IndexedConnector.cs:198-203` — the same, `_recs.Clear()` at `:200`, `_nextOrdinal = 1`.

And these are genuinely the SHARED objects, not per-connector copies: `_slots` is
`_st.Slots` (`RelativeConnector.cs:25`) and `_recs` is `_st.Recs` (`IndexedConnector.cs:36`), where `_st` comes
from `KeyedStoreTable.AttachRelative` / `AttachIndexed` (`KeyedStoreTable.cs:32-52`) — *"the FIRST opener loads
from disk, later openers ATTACH to the live store (never reload — the in-memory store IS the truth while any
connector holds it)"* ([[PB143]]). So `Clear()` on an attached store is a mutation every other attached connector
sees instantly, by design.

The `Clear()` itself is **correct** — §14.9.27.4's OUTPUT semantics create a new physical file, so emptying the
view is what OPEN OUTPUT means. What is missing is any statement, anywhere in these two files, of the condition
under which it is safe.

## Why it is unreachable through conforming source today — the two defences, both verified

### Defence 1 — Table 19 refuses every OUTPUT open against any other open connector

`FileRegistry.SharedOpenAttempt` (`src/Cobol.Net.Runtime/IO/FileRegistry.cs:776`ff) runs the arbitration
**before** the connector body that holds the `Clear()`: it iterates `st.Open` and returns `'61'` on a conflict,
and only then calls `string status = c.Open(mode);` — which is the call that reaches `OpenCore` and the
`Clear()`. So an OUTPUT open that Table 19 refuses never executes a line of the arm above.

Every clause below re-derived with `cite.py --check`, none inherited:

- `--check 9.1.13.9 "An attempt is made to open a physical file in the output mode and the physical file is
  currently open by another file connector"` → **OK §9.1.13.9 1) e)**. This is the sub-case that names **no
  sharing mode at all**, which is exactly why the OUTPUT column is unconditional.
- `--check 9.1.15 "Before access to a shared physical file is allowed through an OPEN statement, the sharing mode
  and the open mode of that OPEN statement shall be allowed by all other file connectors that are currently
  associated with the physical file"` → **OK §9.1.15**. The gate is the set of file connectors, arbitrated by
  Table 19.
- `--check 14.9.27.4 "| SHARING WITH NO OTHER | EXTEND I-O INPUT OUTPUT | Unsuccessful open | Unsuccessful open |
  Unsuccessful open | Unsuccessful open | Unsuccessful open |"` → **OK §14.9.27.4 4)**. The first of the three
  OUTPUT-bearing rows, quoted from Table 19 itself.

Table 19 prints **seven** rows; three of them can carry an OUTPUT request, and all three are `Unsuccessful open`
in all five columns:

| Table 19 row (open request) | the five columns |
|---|---|
| `SHARING WITH NO OTHER / EXTEND I-O INPUT OUTPUT` | U · U · U · U · U |
| `SHARING WITH READ ONLY / OUTPUT` | U · U · U · U · U |
| `SHARING WITH ALL OTHER / OUTPUT` | U · U · U · U · U |

⚠ **Only the first of those three is mechanically citable, and the reason matters more than the inconvenience.**
The other two are printed as CONTINUATION rows whose stub cell is empty — in `specs/ISO_COBOL.md` they read
`| | OUTPUT | Unsuccessful open | …`. Running `cite.py --check 14.9.27.4 "| | OUTPUT | Unsuccessful open | …"`
returns **OK** and then prints back the `SHARING WITH NO OTHER` row: the whitespace-tolerant matcher found a
different row, and a citation that was never re-derived would have shipped pointing at the wrong one. This was
hit while writing this note and is recorded rather than quietly worked around
(`feedback_a_real_clause_can_answer_a_different_question` — a real clause answering a different question,
`--check` passing, and the gap shipping). **Cite the NO OTHER row, or cite the row by position and say so.**

The compiler's own transcription of the table agrees cell for cell —
`src/Cobol.Net.Runtime/IO/Sharing/OpenTable19.cs:125-130` (`NoOtherAnyMode`), `:146-151` (`ReadOnlyOutput`),
`:167-174` (`AllOtherOutput`), the last carrying §9.1.13.9 1) e) verbatim in its comment at `:168-169` — and
`OpenTable19Tests.Cell_CoversEveryRowByColumnPair` enumerates both enums so a new member cannot land unmapped.

### Defence 2 — a closed connector does not alias the store, contrary to the report's hypothesis

The report's remaining question was: *"whether any registered-but-closed connector can retain a reference to a
store another connector then clears."* **Read on main: it cannot.** Both `CloseCore`s drop the alias in a
`finally`, immediately after detaching:

- `RelativeConnector.cs:176-180` — `finally { SharedStores?.Detach(HostPath); _st = new RelativeStore(); }`
- `IndexedConnector.cs:266-270` — `finally { SharedStores?.Detach(HostPath); _st = new IndexedStore(); }`

and `KeyedStoreTable.Detach` (`:56-60`) removes the entry on the last detach *"so a later OPEN reloads from
disk"*. The comment above both `finally` blocks already asserts the property — *"the connector leaves the shared
store, and never aliases a detached one"* — and here the code actually does what the comment says. That half of
the report's question is therefore **closed by reading and needs no probe**.

## ⛔ What the probe still has to answer

Defence 1 holds only if **attached ⇒ registered open**. `SharedOpenAttempt` registers a connector in `st.Open`
only on the `'0'` success family (`FileRegistry.cs:799`, `if (status[0] == '0')   // the success family
'00'/'05'/'07' — §9.1.13.2`), while `Attach()` is called inside `OpenCore`, one layer down. Reading says the two agree — every failure return in both connectors precedes its `Attach()`
(`RelativeConnector.cs:105`, `:122`, `:134`; `IndexedConnector.cs:190`, `:207`, `:220`), and the only statuses
returned after an `Attach()` are `'00'` and `'05'` (`OptionalFileNotFound`), both in that family. **That is
reading, not measurement, and it is precisely the invariant a fourth organization or a new OPEN arm can break
silently.** The probe:

1. Two `SELECT`s on one `ASSIGN`, `ORGANIZATION IS INDEXED` (then RELATIVE), both `SHARING WITH ALL OTHER`:
   open A INPUT, write records, then attempt `OPEN OUTPUT B` while A is open — assert `'61'` and assert A can
   still READ every record. Repeat for A open I-O and A open EXTEND. This pins defence 1 as *behaviour* rather
   than as a table.
2. The OPTIONAL-absent shape, which is the one place `Attach()` runs on a non-`'00'` status: `SELECT OPTIONAL`
   on a file that does not exist, opened INPUT (`'05'`, `Attach()` at `RelativeConnector.cs:107` /
   `IndexedConnector.cs:192`), then a sibling `OPEN OUTPUT` — assert `'61'`, i.e. that the `'05'` connector was
   registered and the arbitration saw it.
3. ⛔ Fire the guard's failure branch once before trusting its silence (`feedback_green_gates_arent_evidence`,
   `feedback_prove_the_watchdog_fails`): temporarily neuter the arbitration and confirm the probe goes red and
   the records vanish, then restore. A latent-defect probe that has only ever been green proves nothing about
   what it is watching.

## The fix shape

⛔ **This is not a behaviour change — the `Clear()` is right.** It is a missing invariant
(`feedback_defensive_checks`: propose invariants and validators unprompted; `feedback_a_dead_lookup_is_also_
unverified`: a rule nothing checks has never been contradicted).

1. **State the precondition where the mutation is.** Before `Clear()`, assert that no OTHER connector is
   registered open on this host path — loudly, in the style already used one file over for the analogous
   impossible state: `KeyedStoreTable.cs:44-45` throws *"physical file '…' is open under two different
   organizations … — a compiler/registration defect (kb/Work PB143)"*. An OUTPUT open reaching a store another
   connector holds is the same class of impossible, and should say so rather than silently emptying it.
2. **Prefer moving the clear to where the arbitration already is.** The registry knows the arbitrated outcome at
   `SharedOpenAttempt` time; a store reset performed there — or a `KeyedStoreTable.ResetFor(host)` that itself
   refuses when `Attached > 1` — makes the precondition structural instead of remembered, which is the shape that
   makes the next organization automatic (CLAUDE.md rule 5). ⚠ It must not disturb the OPTIONAL-absent `'05'`
   arms, which legitimately clear a store nobody else can hold.
3. **A drift test** that no `Clear()` on a `KeyedStoreTable`-owned store exists outside that one place.

## Sweep

- **The I-O and EXTEND arms clear too** — `RelativeConnector.cs:124`, `:136`; `IndexedConnector.cs:209`, `:222` —
  but only inside their `!exists` branches, i.e. the §14.9.27.4 GR17 *create-as-if-OUTPUT* path for an absent
  OPTIONAL file, where the store is empty by construction. Checked and excluded so a later reader does not
  re-open them; they inherit the same invariant for free if fix shape 2 is taken.
- **The sequential organizations have no store to clear** — their shared medium is the file system itself, which
  is why their sharing defects take a different shape entirely: [[PB753]] (a reader's buffer stale after a
  sibling's REWRITE), [[PB740]] (an unshared connector's OS handle posture), [[PB713]] (a seed probe's
  `FileShare.Read` colliding with a held write handle).
- **The `SharedStores is null` fallback** (`RelativeConnector.cs:155-158`, `IndexedConnector.cs:244-247`) gives a
  standalone connector a PRIVATE freshly-loaded store — the pre-PB143 shape. No arbitration applies there and
  none is needed, because nothing else is attached. Named so the reachability argument above is complete.
