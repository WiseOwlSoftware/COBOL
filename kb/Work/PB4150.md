# PB4150 — does per-row parallelism beat the partition classes now that M6 removed the lexer lock?

**Sites:**
- `tests/_shared/TestPartitioning.cs` (`SliceRows`, the slot types, `TestPartitionAudit`)
- `tests/WiseOwl.Cobol.Tests.Conformance/ConformanceSuiteTests.cs#ConformanceSuiteTestsBase` and the other partitioned
  families (`VersionMatrixTests`, `NistDifferentialTests`, `OptionalWordSubsetDriftTests`)
- `tests/Directory.Build.props` (test-host settings; server GC, PB2526)
- `docs/rearchitecture/DESIGN-test-build-ci.md` sections 3.11, 3.11.1 and the M6 measurements

**The question.** xUnit 2.9.2 parallelizes by test collection, and each class is one collection, so every row of a
`[Theory]` in one class runs serially. The repository answers that with partition classes (PB2527; PB4146 made their
balance a share check). Section 3.11.1 declared the class-split lever exhausted, but it measured that under the ANTLR
lexer's ATN-simulation lock; M6 removed the lock (one benchmark went from 110.1 s to 3.4 s at one thread, with zero
contended acquisitions) and server GC was adopted after it (PB2526). The doc itself says the partition counts are
re-measured after M6. A framework that runs theory rows inside one class in parallel would make every partition
class, slot type and share audit unnecessary (CLAUDE.md rule 5: the shape that makes the next case automatic).

**The experiment (on an experiment branch that does not land the package).**
1. Arm A, today: the Conformance assembly as on main (32 partition classes), compiled-program cache OFF, server GC.
2. Arm B: the same assembly with `Meziantou.Xunit.ParallelTestFramework` (the latest release that supports xUnit v2),
   theory rows parallel inside a class, the same thread cap; if it needs the partition classes collapsed to show its
   effect, measure that variant too.
3. Same host, arms alternated, at least three runs each, the host otherwise idle (no other gate in its slot); record
   wall time, CPU utilisation, GC pause share and the pass set. The pass sets must be IDENTICAL; any row that fails only
   under arm B is shared mutable state and is listed by name (for example `OptionalWordBaselines`, console
   redirection, the current directory).
4. If arm B clears the bar, repeat the comparison on the Unit assembly.

**The bar.** Arm B is adopted only if it is faster by more than run-to-run noise (state the noise measured) with an
identical pass set. A wall-clock reading is evidence here, never a test assertion (PB1590).

**Done when.** The measurements are in this note and in DESIGN-test-build-ci section 3.11.1 (replacing the pre-M6
"exhausted" verdict with the post-M6 numbers, whatever the outcome), and the determination is written: either adopt
(a new defect note naming every site the replacement deletes: the partition classes, slot types, `TestPartitionAudit`,
its drift tests, and `gate_plan.py`'s collection-is-a-class model) or keep the partitions with the measured reason.

- **Noise, and the protocol step this series did not meet.** Step 3 asks for an otherwise idle host; this host was never
  idle: 0–4 other gate slots were held and system CPU averaged 55–96 % per run, so the noise below is the shared host's.
  Arm A alone ran 170–277 s (standard deviation 43.5 s, n = 9). B minus A in the same round: +115, −46, −35, +161, −54,
  −22 s (median −29 s), inside A's own noise; B's standard deviation is 96 s. B2 minus A: −2, −10, −39, −68, −80, +114 s
  (B2 faster in 5 of 6, median −24.5 s). Ag and A64 do not beat the noise.

**The second series (review finding R1-1, 2026-10-30 evening).** The first series' determination was reviewed as resting
on a host step 3 forbade and as not reporting B2's paired rounds, so A, B2 and Ag were rebuilt from `773f18466` with this
note's branch merged (19,961 cases) and re-run, every run sampling the gate slots every 5 s (`quiet/` under the scratch
directory above: `run_arm.sh`, `analyze_quiet.py`, `paired.py`, `analysis-quiet.txt`, `paired.txt`). Rounds 1–5 ran A,
B2, Ag; rounds 6–8 ran B2 first. Walls (s) A / B2 / Ag: 196/208/177, 193/170/141, 181/143/173, 140/140/178,
211/160/229, 290/254/–, 441/233/–, 414/494/–. Only rounds 4 and 5 saw no other gate in a slot (and other sessions'
builds still ran: A took 140 s and 211 s in them); the fleet's next wave filled every slot from round 6, so the series
stopped after round 8 rather than hold a slot four implementer gates were queued behind.
- **Pooled B2 against A, 14 pairs:** faster in 10, slower in 3, tied in 1; median ratio 0.878, geometric mean of the
  ratios 0.877 (about 12 % faster); paired t-test on the log ratio p = 0.070 (t = −1.97, df 13), exact sign test
  p = 0.092. Pooled Ag against A: 8 faster, 6 slower, geometric mean 0.977, p = 0.70, so a real B2 gain comes from
  per-row parallelism, not from `aggressive`.
- **Pass sets:** identical by name key in all 21 runs, except B2's two by-construction witnesses.
- **Pass sets.** Identical by name key in every run of every arm, except the witnesses each variant trips by
  construction: `GateLegDriftTests.Arm4_ThisAssembly_NamesTheGateFramework` (B, B2) and
  `ConformancePartitioningDriftTests.TheSuiteRunner_KeepsItsMeasuredPartitionFloor` (B2). No row failed only under
  per-row parallelism; no shared mutable state surfaced in the Conformance assembly.
- **Concurrency, CPU, GC.** Every arm keeps 32 cases in flight until its tail (average concurrency 25–32). A mid-run
  `dotnet-stack` sample of arm B: 32 test threads, 26 of them in `Process.WaitForExit` on a compiled program; the test
  host used 548–734 s of CPU per run. GC pause share 2–5 % in most runs (range 1.6–13.5 %).

**The first arm-B run, under xunit's default algorithm, never finished.** `ParallelTestAssemblyRunner` overrides
`RunTestCollectionAsync` without calling the base, so it skips the `conservative` algorithm's
`SemaphoreSlim(maxParallelThreads)` (decompiled from xunit.execution 2.9.2 and the package), and with no
`MaxConcurrencySyncContext` its method runner starts every case with `Task.Run`. The host reached 1,720 threads, 1,710
of them inside `ProcessObserver.Observe`; a child that had used 0.1 s of CPU never exited, so
`DisplayUponTests.Upon_EachOutputDevice_TransfersALongOperandAsOneLine` read HARNESS NON-OBSERVATION twice (120 s each,
host 31–35 % busy); the run was stopped at 10 minutes (`runs\unbounded-armB-1`, `armB1-stacks.txt`). Every measured B
run therefore used `aggressive`, which bounds it to the 32 threads.

**The long pole moves to the end under per-row parallelism.**
`ConformanceSuiteRunnerDriftTests.BothRunners_GiveEverySuiteTestTheSameVerdict` (one case, 50–205 s) is its own
collection under the partitions; under B it queued behind the partitions' rows, started 113–234 s into four of the six
runs and ended all four. It ended one of the nine arm-A runs. And per-row parallelism lifts the partitions' bound on a
heavy family: round 4 ran three rows of `NistDifferentialTests_P3` together at 52–56 s each (12–24 s for the slowest NIST
rows under the partitions).

## Determination (2026-10-30): keep the partition classes until a reserved-host measurement decides

The pass sets are identical, but B2's lead (about 12 %, 10 of 13 decided pairs) does not clear the shared host's noise
(p = 0.07), and the idle host step 3 called for was not available in either series. So the bar is not met on this
evidence and the partition machinery stays, but per-row parallelism is NOT rejected: the question is open until A and
B2 run alternately with every gate slot reserved for the experiment (an owner-scheduled window, since it stops the
fleet's gates), which this landing leaves as a new note for the registrar. Its costs, each witnessed, are what an
adoption must answer: it is unbounded under xunit's default algorithm; it names its own
`[assembly: Xunit.TestFramework]`, so it cannot coexist with `GateTestFramework` without re-implementing its runners
there; it schedules the long pole last; and it removes the bound on concurrent rows of a heavy family. Step 4 (the
Unit assembly) did not run, as the Conformance arm has not cleared the bar; there `AcceptSourceTests` sets
`Console.In` in each of its five facts and would race with its own rows (the `process-globals` classes would stay
serial). The leg is bound mostly by 32 threads waiting on child processes and by the shared host's load; the class
structure costs at most B2's unproven 12 %. DESIGN-test-build-ci.md section 3.11.1 carries both series and replaces
the pre-M6 "exhausted" verdict. No package lands.

## Landing

- `docs/rearchitecture/DESIGN-test-build-ci.md` section 3.11.1 holds the post-M6 measurement and the determination; a
  successor re-measuring parallelism starts from its table and from the experiment scripts in the scratch directory above
  (`run_arm.sh` runs one arm inside a gate slot from a copy of the build output under `bin/<arm>/Debug/net10.0`, so
  `TestRepo` still resolves the configuration and the repository root).
- Trap: xunit 2.9.2's default `conservative` algorithm bounds COLLECTIONS with a semaphore and sets no synchronization
  context, so a runner that overrides `XunitTestAssemblyRunner.RunTestCollectionAsync` without calling the base runs
  unbounded; only `parallelAlgorithm: aggressive` (a `MaxConcurrencySyncContext`) bounds the threads.
- Trap: the shared gate host's load swings a whole-assembly run by 100 s (300 s when the fleet fills every slot);
  alternate the arms within a round, compare the rounds' paired ratios, never one run per arm, and record the gate
  slots DURING each run (`quiet/inner.sh` samples them every 5 s): an empty slot table before and after a run does not
  make it quiet.
- Settled by kb/Work PB4195 (2026-10-31): on the reserved host B2 was 2.6 % faster than A (129.7 s against 133.2 s, six
  paired rounds, t = -1.23), inside the noise, so the partition classes stay.
