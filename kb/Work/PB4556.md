# PB4556 — global-clause-in-local-storage-refused: -std=cobol2014: GLOBAL on a level-1 LOCAL-STORAGE item is refused ("GLOBAL not allowed here")

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

cobc 3.2 refuses the GLOBAL clause on a level-1 data description entry in the local-storage section: "GLOBAL not allowed here", and a contained program that references the item then reports it as not defined. ISO lists the local-storage section among the sections where GLOBAL may be written. Class: rejects legal source. Fuzz programs: fz00869, fz02278 (slice D3).

## Minimal test case

Free reference format.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. GLB1.
DATA DIVISION.
LOCAL-STORAGE SECTION.
01 L1 IS GLOBAL PIC 99 VALUE 11.
PROCEDURE DIVISION.
    DISPLAY L1
    CALL "GLB1-IN"
    STOP RUN.
IDENTIFICATION DIVISION.
PROGRAM-ID. GLB1-IN.
PROCEDURE DIVISION.
    DISPLAY L1
    GOBACK.
END PROGRAM GLB1-IN.
END PROGRAM GLB1.
```

## Environment

`cobc (GnuCOBOL) 3.2.0`, WSL2 Ubuntu x86_64. Compiled with `cobc -x -free -std=cobol2014 -o glb1.x glb1.cob` (the same diagnostics under `-fsyntax-only`); no executable is produced.

## Observed result

Compile, exit code 1:

```text
glb1.cob:5: error: GLOBAL not allowed here
glb1.cob:13: error: 'L1' is not defined
```

`cobc -fsyntax-only -free glb1.cob` (default dialect) gives the same two errors.

## Expected result (per ISO)

The program is legal and prints `11` twice (once in GLB1, once in the contained GLB1-IN).

- §2023:13.18.27.3 (checked): "specified in the file, working-storage, local-storage, or linkage section". Syntax rule 1 b): a level-1 data description entry in any of these sections may carry GLOBAL.
- §2023:13.18.27.4 (checked): "A statement in a program contained directly or indirectly within a program that describes a global name may reference that name without describing it again.". General rule 2: GLB1-IN may reference L1.

Edition: 2014. The 2009 draft of the 2014 standard (CD 1.2) has the same syntax rule 1 b) naming local-storage (the 2002 text limits GLOBAL only to level-number 1 entries); Annex E of 2023 lists only a clarification of GLOBAL against EXTERNAL.

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`): compiles with no diagnostic; the run prints `11` and `11`, exit code 0.

## Fix site

`cobc/parser.y`, rule `global_clause`: the branch `current_storage == CB_STORAGE_LOCAL` issues `"%s not allowed here"` for GLOBAL. The branch is the same in the 3.2 source and the 3.3-dev tree; a fix also needs the contained program to address the containing activation's local storage.

## Draft issue

**Title:** GLOBAL on a level-1 LOCAL-STORAGE item is refused ("GLOBAL not allowed here")

As posted (owner-reviewed, 2026-11-04):

cobc refuses the GLOBAL clause on a level-1 item in the LOCAL-STORAGE SECTION, so a contained program cannot reference that item. ISO allows GLOBAL there, as in the file, working-storage and linkage sections.

### To reproduce

`glbls.cob` (attached, free format):

~~~~
IDENTIFICATION DIVISION.
PROGRAM-ID. GLBLS.
DATA DIVISION.
LOCAL-STORAGE SECTION.
01 L1 IS GLOBAL PIC 99 VALUE 11.
PROCEDURE DIVISION.
    DISPLAY L1
    CALL "GLBLS-IN"
    DISPLAY L1
    STOP RUN.
IDENTIFICATION DIVISION.
PROGRAM-ID. GLBLS-IN.
PROCEDURE DIVISION.
    DISPLAY L1
    ADD 1 TO L1
    GOBACK.
END PROGRAM GLBLS-IN.
END PROGRAM GLBLS.
~~~~

    cobc -x -free -std=cobol2014 -fno-diagnostics-show-caret glbls.cob && ./glbls

### What happens

3.2.0 and 3.3-dev r5751 both stop with

~~~~
glbls.cob:5: error: GLOBAL not allowed here
glbls.cob:14: error: 'L1' is not defined
~~~~

The same happens without `-std` and with `-std=cobol2002`, `ibm` and `mf`, and for `glbrec.cob`, attached, a RECURSIVE program whose contained program displays the item.

### What should happen

The program should print 11, 11 and 12. ISO/IEC 1989:2023 13.18.27.3 syntax rule 1 b) allows GLOBAL in "A data description entry whose level-number is 1 that is specified in the file, working-storage, local-storage, or linkage section", and general rule 2 lets a contained program reference a global name without describing it again; the same in 2002 and in the 2014 FCD.

### Why it happens

`global_clause` in `cobc/parser.y` refuses GLOBAL when `current_storage == CB_STORAGE_LOCAL`. Dropping that branch alone is not enough: LOCAL-STORAGE is addressed through `cob_local_ptr`, a local variable of the containing program's C function, so the C compile of the contained program fails with "'cob_local_ptr' undeclared".

### Proposed fix

The attached `n10-global-local-storage.patch` (against 3.3-dev r5751) drops that branch and, in `cobc/codegen.c`, gives each GLOBAL LOCAL-STORAGE record a static base pointer, and each index-name of its tables a static int, both at file scope, where GLOBAL WORKING-STORAGE storage already is. `output_internal_function` points each record's pointer into the new LOCAL-STORAGE, saves the previous pointers and index values on entry and restores them on exit, so every activation of a recursive program has its own copy; a USE GLOBAL declarative entered from a contained program keeps the active ones. `output_base`, `output_nonlocal_base_cache` and `create_field` use, declare and cache them, with a new flag in `tree.h`. A LOCAL-STORAGE with no GLOBAL item generates the same code as before. With the patch `glbls` prints 11, 11, 12 and `glbrec` prints 3, 2, 1.

A BASED GLOBAL item is now accepted in LOCAL-STORAGE, but a contained program referencing it still fails in the C compile, as in WORKING-STORAGE and as in bugs #870, because that pointer is declared inside the owning program's function.

It adds the testsuite case "GLOBAL in LOCAL-STORAGE" to `run_fundamental.at`, with ChangeLog entries. `make check`: 1373 expected, 9 skipped, 0 failed (1372 unpatched); the new test fails without the patch.
