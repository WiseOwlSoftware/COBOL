# PB924 — OPEN — a lexer REGION decision standing where a parse decision belongs

Source: the `PB882` report, "New defects". Re-measured here, with its control.

## The measurement

`<scratch>/reg7/probe/k_sum_paren.cob`, `--std 2023` — a REPORT SECTION entry:

```cobol
             05 COLUMN 1 PIC 9999 SUM (WS-K * WS-M).
```
```
k_sum_paren.cob(17,40): error COBOL0001: unexpected 'WS-K'
```

The error is on the token INSIDE the parentheses, which is the signature of a mode push: the lexer has
already decided this `(` opens a subscript list, so `WS-K` arrives as a subscript element and the
expression grammar never sees it.

**The control**, `<scratch>/reg7/probe/k_sum_plain.cob` — the identical entry with the parentheses removed,
`SUM WS-K * WS-M` — **compiles clean**. So the addend is expressible; only the parenthesised-first spelling
is not.

## The rule

```
$ python scripts/spec/cite.py --check 13.18.54.3 "Otherwise, SUM refers to the report writer SUM clause"
OK  §13.18.54.3 9)  (Syntax rules)
    9) Within a report description entry, if the keyword SUM is preceded by the keyword FUNCTION, SUM is a
       reference to the SUM intrinsic function. Otherwise, SUM refers to the report writer SUM clause,
       even when SUM is imp…
```

SR9 settles it outright: inside a report description entry, a SUM not preceded by FUNCTION is the CLAUSE.
The clause's operand is `arithmetic-expression-1`, so the `(` that follows can only open a parenthesised
arithmetic expression. There is no reading in which it opens a subscript list.

## The code site

`tests/version-matrix/cobol-words.json`, row `SUM`, carries `subscriptTrigger: true` — put there for
§8.4.3.2.3 SR2's keyword-omitted intrinsic call `SUM(1 2 3)` — and `CobolLexer.g4#OnDefaultLParen` acts on
it unconditionally. The lexer has no notion of "inside a report description entry", which is exactly
SR9's discriminator.

## Why this is ONE mechanism and not one word

`SUM` is not alone: every word in §8.9 ∩ §8.11 — a reserved word that is also an intrinsic-function name —
carries the same ambiguity, and `LENGTH`, `RANDOM` and `SIGN` are the named siblings. The lexer's region
decision is the mechanism; the word list is its population. **PB883** (landed) built the grammar surface
for `arithmetic-expression-1`, so the parser is ready; what is missing is the recovery of a capture the
lexer already made under the wrong assumption.

The precedent is in the tree: the D2 re-parse hook (`PrimeFunctionArgs` / `functionArgListFragment`) does
exactly that for function arguments. Extending it — or, better, making the trigger CONTEXTUAL, so a
`subscriptTrigger` word inside a report description entry does not fire — is the fix, and the drift test
that keeps it true is "every §8.9 ∩ §8.11 word, parenthesised, in both regions".
