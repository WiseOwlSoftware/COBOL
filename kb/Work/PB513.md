# PB513

## Mechanism — data-description-entry-p1
The TYPE arm has NO same-entry composition guard, while the SAME AS arm has one -- and the two arms share CopyEntryDescription, whose `to.Pic ??= from.Pic` (receiver-wins) is safe ONLY under such a guard. The doc comment on that method states its warrant explicitly -- 'a SAME AS subject can own none of these, 13.16.3 SR12' -- which is true for SAME AS and false for TYPE, because SR14 is unenforced. The subject's illegal own clause therefore silently DISCARDS the type's declared description.

### Expected, from the standard
13.16.3 SR14: 'The TYPE clause shall not be specified in the same data description entry with any clauses except BASED, CLASS, CONSTANT RECORD, DEFAULT, DESTINATION, entry-name, EXTERNAL, GLOBAL, INVALID, level-number, OCCURS, PRESENT WHEN, PROPERTY, TYPEDEF, VALIDATE-STATUS, VALUE, and VARYING.' PICTURE, USAGE, JUSTIFIED, SYNCHRONIZED, SIGN, BLANK WHEN ZERO, REDEFINES, GROUP-USAGE and SAME AS are all OUTSIDE that set, so each shall be rejected with a named diagnostic. 13.18.57.4 GR1 then makes the subject's description the TYPE's description -- which is only well defined once SR14 holds. For the repro: `01 A TYPE T PIC 9(5).` shall be REJECTED; it shall never yield a 5-digit numeric A.

```
$ python scripts/spec/cite.py --check 13.16.3 "The TYPE clause shall not be specified in the same data description entry with any clauses except BASED, CLASS, CONSTANT RECORD, DEFAULT, DE..."
  OK  §13.16.3 14)  (Syntax rules)
```

### Observed
TYPE+PICTURE, TYPE+USAGE, TYPE+JUSTIFIED, TYPE+SYNCHRONIZED, TYPE+SIGN, TYPE+BLANK WHEN ZERO, TYPE+REDEFINES and TYPE+GROUP-USAGE all compile clean at --std 2023 and --std 2002, on weak and STRONG types alike. The only two rejected shapes are rejected from the OTHER side (TYPE+SAME AS by SR12's COBOLNET1555; TYPE+ANY LENGTH by 13.18.2.3 SR1's picture-shape check), so nothing in the compiler implements SR14. Because CopyEntryDescription lets the receiver win, A is a 5-digit numeric and FUNCTION LENGTH(A) is 5 where type T declares PIC X(3) -- a typed item whose runtime description is not the type's. That is the wrong answer, and it defeats 8.5.3's whole purpose. The fix is the guard the SAME AS arm already has, factored so ONE permitted-set predicate serves both arms of the shared clone.

## Landed — wave 39 (2026-09-19)

SR14 is enforced. Its permitted set is ONE constant, `DataClauseKinds.TypeCoPermitted`
(`src/Cobol.Net.Frontend/Cst/DataClauseKind.cs`), read over the entry's WRITTEN clause set exactly as
SR12's `SameAsCoPermitted` is, and the guard sits in `BindEntry` beside SR12's and reports COBOLNET2150
naming the offending clause. CLASS, DEFAULT, DESTINATION, INVALID, PRESENT WHEN, VALIDATE-STATUS and
VARYING arrive as the single `Validation` bit — exactly the set §13.16.2's `validation-clauses` term
names. The guard is placed AFTER the CONSTANT RECORD block so §13.16.3 SR13 ¶2 still sees the TYPE
clause the programmer wrote rather than the one this recovery cleared.

`CopyEntryDescription`'s doc comment already cited SR12 *and* SR14 as the warrant for its receiver-wins
copy; the warrant is now true on both arms, so `01 T IS TYPEDEF PIC X(3). 01 A TYPE T PIC 9(5).` is
refused instead of silently discarding the type's description.

SIBLING SWEEP (CLAUDE.md rule 4, the two-arm shape): `ExpandSameAs` has always expanded a target that
itself carries a TYPE clause before copying; `ExpandType` did not, so a type declaration whose own
description is `TYPE T` (§13.18.58.3 SR2 contemplates exactly that shape, and §13.18.58.4 GR3 hands its
clauses on) was copied UNEXPANDED and `01 F TYPE TT.` became a synthesized one-character item —
measured `F=[u] LEN=1` where the chain declares PIC X(3). `ExpandType` now takes the same hop, carrying
`expanding` so a cyclic chain is still the SR2 rejection (COBOLNET1530, measured).

Goldens: `tests/conformance/2002/pb513_type_entry_composition` (the permitted co-clauses, every expected
value computed from §13.18.57.4 GR1/GR3 and §8.5.1.6.1) and
