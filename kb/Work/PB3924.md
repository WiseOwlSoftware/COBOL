# PB3924 — usage-bit-and-aligned-not-supported--usage-bit: Feature request: USAGE BIT (announced by -Wpending as not implemented) is held as whole bytes: wrong group size and wrong compare

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S8) and refutation (RECLASSIFY). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\usage-bit-and-aligned-not-supported--usage-bit.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\usage-bit-and-aligned-not-supported--usage-bit\`.

## Summary

GnuCOBOL 3.2 accepts `USAGE BIT` under `-std=cobol2014` with the warning `USAGE BIT is not implemented [-Wpending]`,
exits 0, and builds a program that runs. The program does not hold the items as bits: each USAGE BIT item is given a
whole number of bytes of its own, so two adjacent 4-bit items in a group take 2 bytes where the standard packs them
into 1, and a 4-bit item initialised with `VALUE B"1010"` compares unequal to `B"1010"`. The parser comment and
ChangeLog say USAGE BIT was added "as pending" for parsing only (feature request 303).

Verdict FEATURE-MISSING (edition 2014, introduced 2002; corrected by the refuter from `compiles but is not implemented
at run time`): cobc names the gap at compile time on every BIT line (parser.y lines 7994-8005, `CB_PENDING`, a warning
by design; `-Werror=pending` makes it an error, rerun), so the observed `NE` and the group size of 2 are symptoms of
the announced missing feature, not a separate bug. The ISO side holds (13.18.60.4 5), 8.5.1.6.3, 15.14.4 1),
13.18.63.4 4), 13.18.63.3 10), 8.8.4.2.8 all `--check` OK, and USAGE BIT is in neither A.3 nor A.4, so it is
required). Sites verified: field.c `compute_size` (line 3195, whole bytes), tree.c `cb_tree_type` (line 1580).

## Observed result

Compile exit code 0, with warnings only:

```
ubit.cob:5: warning: USAGE BIT is not implemented [-Wpending]
ubit.cob:7: warning: USAGE BIT is not implemented [-Wpending]
ubit.cob:8: warning: USAGE BIT is not implemented [-Wpending]
```

Run exit code 0, output:

```
NE
2
```

Control, same compiler and options (`work\usage-bit-and-aligned-not-supported\s8\p3.cob`): a usage-display boolean
item `01 D PIC 1(4) VALUE B"1010"` compares equal to `B"1010"` (`D EQ`), so the unequal result is specific to USAGE BIT.
In the same program `MOVE B"1010" TO C` into a 4-bit USAGE BIT item leaves `C = B"1010"` false (`C NE`), and a
`PIC X` redefinition of C shows the one character `1` (default dialect: byte 0x31 by `FUNCTION HEX-OF`). `DISPLAY B`
prints `1` (`p1.cob`).

## Expected result (per ISO)

The program prints:

```
EQ
1
```

- §13.18.60.4 5) (checked): "The USAGE BIT clause specifies that bits shall be used to represent a boolean data item.
  A data item described with USAGE BIT is a bit data item. The alignment of a data item described with USAGE BIT is
  specified in 8.5.1.6.3".
- §8.5.1.6.3 (checked): alignment of bit data items "is at the next bit position in storage when that item is: — an
  elementary bit data item immediately following an elementary bit data item or bit group item of the same level";
  filler is generated after the last bit item of an alphanumeric group only "as needed to increase the number of bits
  to fill an integral number of characters". G1 occupies bits 1-4 and G2 bits 5-8 of one byte; G is 8 bits, 1 byte.
  The informative Annex D example of 8.5.1.6.3 shows `item-1 pic 11 usage BIT` and `item-2 pic 1 usage BIT` sharing
  byte 1 of an alphanumeric group.
- §15.14.4 1) (checked): "The returned value is an integer that is the length of argument-1 in number of bytes." So
  `BYTE-LENGTH(G)` is 1.
- §13.18.63.4 4) (checked): "data items with a VALUE clause are initialized to the specified value"; §13.18.63.3 10)
  (checked): "If the category of the subject of the entry is boolean, literals in the VALUE clause shall be boolean
  literals." B holds the boolean value 1010.
- §8.8.4.2.8 (checked): "Comparison of operands of class boolean is a comparison of their boolean value, regardless of
  their usage." B and `B"1010"` have equal length and equal boolean values: the condition is true.

Edition: 2014. Boolean data and USAGE BIT were introduced in 2002 (WiseOwl's `constructs.json` row `boolean-data-2002`)
and Annex E (2014 to 2023) lists no change to USAGE BIT or to 8.5.1.6.3.

Edition as recorded by the adjudicator: 2014 (introduced 2002). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Class

Feature missing (edition 2014, introduced 2002; known upstream: `USAGE BIT is not implemented [-Wpending]`). Corrected by the refuter from `compiles but is not implemented at run time`: the compile-time warning announces the gap, the wrong value and the wrong group size are its symptoms.

## Our compiler (WiseOwl)

WiseOwl COBOL (built from main 6ed90bd1c), `cobol ubit.cob --std 2014 --source-format free -o ubit.dll`, then
`dotnet ubit.dll`: compile exit 0, run exit 0, output `EQ` / `1`.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/parser.y`, rule `usage` (line 7989), alternatives `BIT` and `BIT ALIGNED` (lines 7994-8005): set
  `CB_USAGE_BIT` and emit `CB_PENDING ("USAGE BIT")`, the -Wpending warning; nothing refuses the program.
- `cobc/field.c`, `compute_size` (line 2822), the `CB_USAGE_BIT` arm (line 3195): sizes each item as its bit count
  rounded up to whole bytes, so items never share a byte and there is no bit offset in the field model.
- `cobc/tree.c`, `cb_tree_type` (line 1525): maps `CB_USAGE_BIT` to `COB_TYPE_BOOLEAN` under a FIXME; libcob has no
  bit-level move, compare or initialisation for that type (`libcob/common.c` names it only in `explain_field_type`).
- A fix needs a bit offset and bit length in `cb_field`/`cob_field` and bit-level move, compare and VALUE handling.
  Until then, refusing USAGE BIT with an error (as for other unimplemented features) would stop the wrong results.

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1), x86_64 Linux.

This asks for the missing USAGE BIT run-time support (FR 303 added it "as pending", for parsing only); cobc announces
the gap at compile time, and the wrong results below are its symptoms, not a separate bug.

Steps: `cobc -std=cobol2014 -fformat=free -x ubit.cob && ./ubit` with

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. UBIT.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 B PIC 1(4) USAGE BIT VALUE B"1010".
01 G.
   05 G1 PIC 1(4) USAGE BIT.
   05 G2 PIC 1(4) USAGE BIT.
PROCEDURE DIVISION.
IF B = B"1010" DISPLAY "EQ" ELSE DISPLAY "NE" END-IF
DISPLAY FUNCTION BYTE-LENGTH(G)
STOP RUN.
```

Observed: three `warning: USAGE BIT is not implemented [-Wpending]`, compile exit 0; the program prints `NE` and `2`,
exit 0. With `-Werror=pending` the warnings become errors and no program is built.

What the standard specifies (USAGE BIT is a required element: it is in neither the processor-dependent nor the
optional list of Annex A): `EQ` and `1`. ISO/IEC 1989:2014 (2023 numbering): USAGE BIT "specifies that bits shall be
used to represent a boolean data item" (§13.18.60.4 rule 5); a bit item that follows a bit item of the same level is
aligned "at the next bit position in storage" (§8.5.1.6.3), so G1 and G2 share one byte and BYTE-LENGTH(G) is 1
(§15.14.4 rule 1); boolean comparison compares boolean values "regardless of their usage" (§8.8.4.2.8), and B was
initialised to B"1010" (§13.18.63.4 rule 4).

Where: `compute_size` in cobc/field.c gives each USAGE BIT item whole bytes; the `usage` rule in cobc/parser.y accepts
BIT with CB_PENDING only. Request: bit storage for USAGE BIT. Until it exists, an error for USAGE BIT by default
(rather than a -Wpending warning) would keep silently wrong programs from being built.
