# PB3932 — table-format-value-from-to-not-supported--value-is-spelling: Table-format VALUE clause spelled `VALUE IS ... FROM (...)` is refused ("syntax error, unexpected FROM"); only `VALUES ARE` is parsed

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S10) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\table-format-value-from-to-not-supported--value-is-spelling.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\table-format-value-from-to-not-supported--value-is-spelling\`.

## Summary

GnuCOBOL 3.2 refuses the table-format VALUE clause (Format 2) when it is spelled with `VALUE` or `VALUE IS`:
`05 E PIC 9 OCCURS 3 TIMES VALUE 7 FROM (1) TO (3).` draws `syntax error, unexpected FROM`. The same clause spelled
with `VALUES` compiles. The standard's general format offers `VALUE IS` and `VALUES ARE` as alternatives, and
§13.18.63.3 17) makes VALUE and VALUES equivalent. The table-format VALUE clause has been in the standard since
ISO/IEC 1989:2002 and is in the 2014 edition that `-std=cobol2014` claims. The refused spelling is legal source,
so this is a defect. (Separately, the `VALUES` spelling that compiles does not initialize the table. That is a
second mechanism, recorded as `table-format-value-from-to-not-supported--values-are-ignored`.)

(`VALUE IS 0 FROM (1) TO (10)`) and fz02647 (`VALUE IS 1 FROM (1) TO (5)`) both stop at the table entry with the
same diagnostic. The rest of each program compiles once that entry is removed. Their other content (an alphanumeric
VALUE on a numeric-edited item, THROUGH ranges on level-88 entries) is unrelated to this record.

```cobol

DATA DIVISION.
WORKING-STORAGE SECTION.
01 T.
   05 E PIC 9 OCCURS 3 TIMES VALUE 7 FROM (1) TO (3).
PROCEDURE DIVISION.
    DISPLAY E (1) E (2) E (3)
    STOP RUN.
```

File: `E:\COBOL-coord\scratch\op\pb3838\records\table-format-value-from-to-not-supported--value-is-spelling.cob`.

The program is legal. The entry has an OCCURS clause (§13.18.63.3 18)). The subscripts are integer numeric literals
(19)). The FROM and TO phrases each give one subscript for the one OCCURS level, and neither exceeds 3 (20), 21)).
`VALUE 7 FROM (1)` without TO (`tfx.cob`) gets the same diagnostic.

0, run exit 0, output `000`. The wrong output is the second record's mechanism.

## Expected result (per ISO)

The program compiles and prints `777`.

- §13.18.63.2 (checked), Format 2 (table), from the rendered page (PDF p546, folio 516):
  `{VALUE IS | VALUES ARE} {{literal-1}... FROM ({subscript-1}...) [TO ({subscript-2}...)]}...`.
  `VALUE IS` is the first alternative of the brace.
- §13.18.63.3 17) (checked): "The words VALUE and VALUES are equivalent." This is Format 2's own syntax rule.
- §13.18.63.3 18) (checked): "A data description entry that contains the VALUE clause shall contain an OCCURS clause
  or be subordinate to a data description entry that contains an OCCURS clause."
- §13.18.63.3 19) (checked): "Subscript-1 and subscript-2 shall be integer numeric literals."
- §13.18.63.4 12) (checked): "A format 2 VALUE clause initializes a table element to the value of literal-1. The table
  element initialized is identified by subscript-1."
- §13.18.63.4 13) (checked): "If the TO phrase is specified, all occurrences of literal-1 are reused, in the order
  specified, as a source during the initialization described in General rule 12." So E (1) through E (3) are each 7.

Edition: the table format is in ISO/IEC 1989:2002. The post-ballot 2002 text has "Subscript-1 and subscript-2 shall
be integer numeric literals" and "A format 2 VALUE clause initializes a table element ...". The 2009 committee draft
that became the 2014 edition (CD 1.2) has the same two rules. GnuCOBOL's own grammar comment calls the format
"COBOL2002 table-format". It is a 2014 feature, carried unchanged into 2023 (Annex E items 27 to 29 change only
numeric-edited VALUE literals).

Edition as recorded by the adjudicator: 2002 (carried into 2014 and 2023). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Class

GNUCOBOL-DEFECT: legal source of the claimed edition (2014; the feature dates from 2002) refused. The feature is
implemented for the `VALUES` spelling only.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/parser.y`, rule `value_clause` (line 8625). The table-format alternative is `VALUES _are
  value_table_item_list` only. The comment beside it says that `VALUE _is` would also be correct but is left out
  "because of parser conflicts". The `VALUE _is value_item` alternative (format 1) takes `VALUE 7` and then fails
  at `FROM`.
- `value_from_subscripts_is_are` (BS2000 `VALUE FROM (...) IS ...`) is a different, non-ISO order and does not
  cover this spelling.
- A fix needs `VALUE _is value_table_item_list` as a table-format alternative, with the conflict against format 1
  resolved by lookahead on FROM after the literal list.
