# PB4597 — relative-key-zero-delete-rewrite-status-24: RELATIVE DELETE and REWRITE with relative key 0 return 24, not 23

Filed 2026-11-04 from the vetting of a sibling lead that the independent review of fuzz night 10's batch-1 report `n10-relative-delete-rewrite` found while it probed that report's patch (lead (d), probe `key0`). The drafter's patch for PB4539 does not touch this path: its built tree still gives 24. Upstream status `unreported`: the owner has not yet decided to report it. The probe programs are local (`~/gc-notes/PB4597/key0.cob` under WSL, and the drafter's `E:/COBOL-coord/scratch/mythos/gc-file-n10/work-n10-relative-delete-rewrite/key0.cob`): the minimal program below is the repro.

## Summary

For a RELATIVE file in random or dynamic access, cobc 3.2.0 and 3.3-dev give I-O status 24 when a DELETE or REWRITE is executed with the relative key set to 0. No record can have relative record number 0, because numbering starts at 1. The record specified by the key therefore does not exist, and the DELETE and REWRITE rules make that the invalid key condition with status 23. Status 24 is the status for an attempt to write outside the file's boundaries, and a DELETE or REWRITE is not such an attempt. The READ of the same key already gives 23. Class: wrong output (the wrong I-O status value; the invalid key branch is still taken, since 24 is also an invalid key status).

## Minimal test case

Fixed reference format.

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. KEY0.
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
           SELECT F ASSIGN TO "key0.dat"
               ORGANIZATION IS RELATIVE
               ACCESS MODE IS RANDOM
               RELATIVE KEY IS RK
               FILE STATUS IS FS.
       DATA DIVISION.
       FILE SECTION.
       FD F.
       01 REC PIC X(4).
       WORKING-STORAGE SECTION.
       01 RK PIC 9(2).
       01 FS PIC XX.
       PROCEDURE DIVISION.
       MAIN-PARA.
           OPEN OUTPUT F
           MOVE 1 TO RK
           MOVE "R001" TO REC
           WRITE REC
           CLOSE F
           OPEN I-O F
           MOVE 0 TO RK
           READ F
           DISPLAY "READ 0    " FS
           MOVE 0 TO RK
           MOVE "XXXX" TO REC
           REWRITE REC
           DISPLAY "REWRITE 0 " FS
           MOVE 0 TO RK
           DELETE F RECORD
           DISPLAY "DELETE 0  " FS
           MOVE 1 TO RK
           READ F
           DISPLAY "READ 1    " FS " " REC
           CLOSE F
           STOP RUN.
```

## Environment

`cobc (GnuCOBOL) 3.2.0` (`/usr/bin/cobc`) and `cobc (GnuCOBOL) 3.3-dev.0` built from r5751 (`~/opt/gnucobol-3.3-dev/bin/cobc-dev`, run through `run-dev`, which sets `LD_LIBRARY_PATH` to the dev runtime), WSL2 Ubuntu x86_64. Commands: `rm -f key0.dat; cobc -x -std=cobol2014 -o key0 key0.cob; ./key0` and `rm -f key0.dat; cobc-dev -x -std=cobol2014 -o key0 key0.cob; run-dev ./key0`. Also run with `-std=cobol2002`, `-std=cobol85` and `-std=default`. The 3.2.0 compile prints the distribution's `_FORTIFY_SOURCE redefined` C-compiler warning and nothing else.

## Observed result

Compile exit code 0 and run exit code 0 on both versions, under all four `-std` values. The output is the same in every run:

```text
READ 0    23
REWRITE 0 24
DELETE 0  24
READ 1    00 R001
```

The drafter's DYNAMIC-access probe gives `DELETE 0   24` and `REWRITE 0  24` on both versions, and on the built tree of the PB4539 patch as well (`~/gc-fix/n10-relative-delete-rewrite`).

## Expected result (per ISO)

```text
READ 0    23
REWRITE 0 23
DELETE 0  23
READ 1    00 R001
```

- §12.4.5.13.4 1) (checked): "The first logical record has a relative record number of 1". No record can exist at relative record number 0.
- §14.9.35.4 21) (checked), REWRITE of a relative file in random or dynamic access: "If the file does not contain the record specified by the key, the invalid key condition exists. When the invalid key condition is recognized, the execution of the REWRITE statement is unsuccessful and the I-O status in the rewrite file connector is set to the invalid key condition '23'." The rule names the value itself, and no REWRITE general rule (1 to 25), in either file organization, gives 24. A spec-wide search shows every '24' is 9.1.13.5 4), WRITE 29 a), 33 b) and c), 42 d), or A.1 107). (§14.9.35.4 14) lists "General rules 2, 5, 11, 16, 17, 20, 21, 22, 23, and 25" for a failed REWRITE, a list that names rule 2, which sets no status, and omits rule 3, which sets '49'; it is not relied on here.)
- §14.9.10.4 4) (checked), DELETE of a relative file in random or dynamic access, "logically removes from the physical file that record identified by the content of the relative key data item", and "If the physical file does not contain the record specified by the key, the invalid key condition exists." §9.1.14 1) (checked) sets the status "to a value indicating the invalid key condition as described in 9.1.13.5".
- §9.1.13.5 3) a) (checked) gives 23 when "an attempt is made to randomly access a record that does not exist in the physical file". That is this case.
- §9.1.13.5 4) (checked) gives 24 when "An attempt is made to write outside the externally-defined boundaries of a physical relative or indexed file", or for a sequential WRITE whose relative record number is too large for the key. A DELETE writes no record. As supporting evidence only, §9.1.13.5 2) c) (checked) says "to write or rewrite a record" when it means both statements, which contrasts with the bare "write" of rule 4). This repository's own keyed store gives 24 to a REWRITE at a host boundary (kb/Work PB3333, PB3334 R1-1, PB3331 and PB3396), so the WRITE-only reading of rule 4) is contested here and the REWRITE argument does not rest on it. DELETE needs no such argument: PB3331 agrees a DELETE gets no 24.
- So 24 does not apply to either statement, and the latitude of §9.1.13.1 (checked: "If more than one value applies, the implementor determines which of the applicable values to place in the I-O status") does not arise: 23 is the only value that applies.

Edition: 2014. The 2009 committee draft that became the 2014 edition has the same rules (3) a) and 4) of its 9.1.12.4; rule 4) reads "write beyond" where 2023 reads "write outside"), "write or rewrite" in 2) c), the more-than-one-value sentence, DELETE rule 4, REWRITE rule 20 with '23', and the relative record number rule. The 2002 text (`t2002.txt`) has the same rules, with "write beyond" in the status 24 rule. The published 2014 text was not checked; it is inferred from the 2009 draft and from 2023.

## Our compiler

WiseOwl COBOL (`--std 2014`, `2023`, `2002` and `85`) prints `READ 0 23 / REWRITE 0 23 / DELETE 0 23 / READ 1 00 R001`, exit code 0, which is correct. Side note from the vetter, not this record and not re-checked here: 2023's 14.9.51.4 29) b) newly gives '34' for a random WRITE with key below 1, where GnuCOBOL `relative_write` returns 24; our side of that is already PB1192.

## Fix site

`libcob/fileio.c` in r5751 (read): `relative_rewrite` (line 3419, random and dynamic arm) and `relative_delete` (line 3452) both compute `relnum = cob_get_int (f->keys[0].field) - 1` and return `COB_STATUS_24_KEY_BOUNDARY` when `relnum < 0`. `relative_read` (line 3206) does the same test and returns `COB_STATUS_23_KEY_NOT_EXISTS`, which is right. The fix is to return `COB_STATUS_23_KEY_NOT_EXISTS` in the two `relnum < 0` arms of rewrite and delete (inferred; not built). `relative_write`'s `kindex < 0` arm, which returns 24, is a WRITE, so it is outside this record.

## Upstream state

Unreported. 3.3-dev r5751 behaves the same as 3.2.0, so this is not fixed upstream.
