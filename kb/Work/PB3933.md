# PB3933 — table-format-value-from-to-not-supported--values-are-ignored: Table-format `VALUES ARE ... FROM (n) [TO (m)]` compiles without a diagnostic but the table is not initialized (elements stay at their default)

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S10) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\table-format-value-from-to-not-supported--values-are-ignored.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\table-format-value-from-to-not-supported--values-are-ignored\`.

## Summary

GnuCOBOL 3.2 accepts the table-format VALUE clause in its `VALUES` spelling and compiles it without a diagnostic,
even under `-Wall`. The generated program never stores the values: every element keeps its default content.
`VALUES 1 2 3 FROM (1)` on a 3-element table and `VALUES 0 FROM (1) TO (1) 7 FROM (2) TO (3)` on another print
`000 000` where the standard requires `123 077`. The table format is in ISO/IEC 1989:2002 and in the 2014 edition that `-std=cobol2014`
claims. The result is a silent wrong answer, so this is a defect. GnuCOBOL's NEWS lists FROM and TO as "pending".
(The `VALUE IS` spelling of the same clause is refused at compile time; that is the companion record
`table-format-value-from-to-not-supported--value-is-spelling`.)

Two code sites, both to be named in the issue (added by the refuter): (1) codegen.c `output_initialize_compound`
never sets `needs_table_format_value`, so the deferred step is skipped and even `VALUES 1 2 3` (no FROM) prints `000`;
(2) when another member forces the step, FROM and TO are ignored (the FIXME in `output_initialize_multi_values`): the
refuter's program `v9.cob` prints `  123 000 456 700 800` (re-run for this note, 2026-10-27) where the standard gives
`Z 123 077 456 777 088` (S (1) has no VALUE; its `0` is cobc's default; the Fix site section).

## Minimal test case

Free reference format (`-fformat=free`), 11 lines, written for this record while reducing night 6's fz01237 and
fz02647. Those witnesses use the `VALUE IS` spelling, so GnuCOBOL refused them before this mechanism could show.
When the same entries are respelled with `VALUES`, they compile and print zeros.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. TFY.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 T.
   05 E PIC 9 OCCURS 3 TIMES VALUES 1 2 3 FROM (1).
01 U.
   05 F PIC 9 OCCURS 3 TIMES VALUES 0 FROM (1) TO (1) 7 FROM (2) TO (3).
PROCEDURE DIVISION.
    DISPLAY E (1) E (2) E (3) " " F (1) F (2) F (3)
    STOP RUN.
```

File: `E:\COBOL-coord\scratch\op\pb3838\records\table-format-value-from-to-not-supported--values-are-ignored.cob`.

The program is legal. Each entry with a VALUE clause has an OCCURS clause (§13.18.63.3 18)). The subscripts are
integer literals (19)), one per OCCURS level, within 1 to 3 (20), 21)). In each FROM/TO pair of F, the TO element is
the same as or after the FROM element (21)). Format 2 repeats its `{literal-1}... FROM ... [TO ...]` group, so F
names two ranges in one clause. Every element of both tables gets a value from the clause.

## Observed result

`-std=cobol2014`: compile exit 0 with no diagnostic (`-fsyntax-only -Wall`: exit 0, no output; default dialect:
compile exit 0). Run exit 0, output:

```
000 000
```

`tfw.cob` (`VALUES 7 FROM (1) TO (3)`): compile 0, run 0, output `000` (expected `777`). The non-ISO BS2000 form
without FROM (`VALUES 1 2 3`, in `tfz.cob`) also prints `000`, under `-std=cobol2014`, `-std=bs2000` and the default
dialect. In the C that `cobc -C` generates for `tfz.cob`, the WORKING-STORAGE initialization for both tables is a
`memset` to `'0'` (`/* initialize field E */ memset (b_1, 48, 3);`). There is no block that stores the listed values.

## Expected result (per ISO)

The program prints `123 077`. GnuCOBOL's `0` for F (1) is right only by coincidence. The finding rests on E (1) to
E (3), F (2) and F (3).

- §13.18.63.2 (checked), Format 2 (table), from the rendered page (PDF p546, folio 516):
  `{VALUE IS | VALUES ARE} {{literal-1}... FROM ({subscript-1}...) [TO ({subscript-2}...)]}...`.
- §13.18.63.4 12) (checked): "A format 2 VALUE clause initializes a table element to the value of literal-1. The table
  element initialized is identified by subscript-1. Consecutive table elements are initialized, in turn, to the value
  of successive occurrences of the literal-1." So E (1), E (2) and E (3) are 1, 2 and 3.
- §13.18.63.4 13) (checked): "If the TO phrase is specified, all occurrences of literal-1 are reused, in the order
  specified, as a source during the initialization described in General rule 12. This repetition is done until the
  table element identified by subscript-2 is initialized." So F (1) is 0, and F (2) and F (3) are both 7.
- §13.18.63.4 14) (checked): without TO, the clause acts as though TO named the last occurrence. E's single FROM
  therefore covers E (1) to E (3).

Edition: the table format and general rules 12 and 13 are in ISO/IEC 1989:2002 (post-ballot text: "A format 2 VALUE
clause initializes a table element to the value of literal-1") and in the 2009 committee draft that became the 2014
edition. They are unchanged in 2023 (Annex E items 27 to 29 change only numeric-edited VALUE literals). This is a
2014 feature.

Edition as recorded by the adjudicator: 2002 (carried into 2014 and 2023). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/parser.y`, `value_clause` (line 8625) and `value_table_item` (line 8699): parse the clause and build a
  `CB_TAG_TAB_VALS` node (`cb_build_table_values`, `cobc/tree.c` line 3954) that carries values, FROM, TO and
  REPEATED.
- `cobc/field.c`, `validate_multi_value` (line 1752): counts the values only. Its FIXME at line 1764 says the count
  "works only if "FROM" is 1 and there is REPEATED TO END / TO ...".
- `cobc/codegen.c`, `output_initialize_multi_values` (line 5394): its FIXME at line 5432 says "handle FROM -> TO and
  FROM -> REPEATED times". `output_initialize_record_one` (line 5468) and `output_initialize_values_table_format`
  (line 5659) are where the deferred multi-value step would be emitted. For these programs the WORKING-STORAGE
  initialization of the generated C contains only the default `memset`, so the step is never emitted.
- A fix needs the storage initialization to apply each table-values entry: start at the FROM element, step the
  least inclusive subscript (§13.18.63.4 12)), repeat the literal list up to the TO element (13)) or to the last
  occurrence (14)), and let a later FROM override an earlier one (15)).

**The two code sites a fix must cover (added by the refuter).**
(1) `cobc/codegen.c`, function `output_initialize_compound`: its OCCURS shortcut (the `memset`, line 5593, then
`continue`) never sets `needs_table_format_value` (only `output_initialize_record_one` does, line 5479), so the
deferred multi-value step is skipped, even for the BS2000 form `VALUES 1 2 3` (no FROM), which prints `000`.
(2) When another member forces the step, `output_initialize_multi_values` ignores FROM and TO (its FIXME at line
5432). The refuter's program
`E:\COBOL-coord\scratch\op\pb3838\refute\table-format-value-from-to-not-supported--values-are-ignored\v9.cob` (one
record T holding `H PIC X VALUES "Z" FROM (1)` under `G OCCURS 1`, then `E` = `VALUES 1 2 3 FROM (1)`, `F` = `VALUES 0
FROM (1) TO (1) 7 FROM (2) TO (3)`, `K` = `VALUES 4 5 6`, `W` = `VALUES 7 FROM (1) TO (3)`, `S` = `VALUES 8 FROM (2)`,
each `PIC 9 OCCURS 3`) prints `  123 000 456 700 800` on cobc 3.2.0 `-std=cobol2014` (re-run 2026-10-27). By
§13.18.63.4 12)-14) the values are H `Z`, E `123`, F `077`, K `456`, W `777` (TO reuses the literal up to element 3)
and S elements 2 and 3 `8` (no TO: as if TO the last occurrence); S (1) has no VALUE, and cobc's default for it is `0`.

## Draft issue

**Title:** Table-format `VALUES ARE ... FROM (n) [TO (m)]` compiles without a diagnostic but the table is not initialized (elements stay at their default)

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1), x86_64 Linux.

Steps: `cobc -std=cobol2014 -fformat=free -x tfy.cob && ./tfy` with

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. TFY.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 T.
   05 E PIC 9 OCCURS 3 TIMES VALUES 1 2 3 FROM (1).
01 U.
   05 F PIC 9 OCCURS 3 TIMES VALUES 0 FROM (1) TO (1) 7 FROM (2) TO (3).
PROCEDURE DIVISION.
    DISPLAY E (1) E (2) E (3) " " F (1) F (2) F (3)
    STOP RUN.
```

Observed: compile exit 0 with no warning (also with `-Wall`), output `000 000`. The generated C initializes both
tables with `memset` to '0' and never stores the listed values. The BS2000 form without FROM (`VALUES 1 2 3`) also
yields `000`.

Expected: `123 077`. ISO/IEC 1989:2002 onward, VALUE clause Format 2 (§13.18.63 in the 2023 edition), general
rule 12: "A format 2 VALUE clause initializes a table element to the value of literal-1. The table element
initialized is identified by subscript-1. Consecutive table elements are initialized, in turn, to the value of
successive occurrences of the literal-1." Rule 13: with TO, the literals are reused "until the table element
identified by subscript-2 is initialized." Rule 14: without TO, the range ends at the last occurrence.

Two code sites, as far as we can see:

1. `codegen.c` `output_initialize_compound`: its OCCURS shortcut (`memset`, then `continue`) never sets
   `needs_table_format_value` (only `output_initialize_record_one` does), so the deferred multi-value step is never
   emitted for these tables, even for the BS2000 form `VALUES 1 2 3`.
2. When another member forces the step, `output_initialize_multi_values` ignores FROM and TO (its FIXME "handle FROM
   -> TO and FROM -> REPEATED times"). In one record with `H PIC X VALUES "Z" FROM (1)` (under `G OCCURS 1`), the two
   tables above, `K ... VALUES 4 5 6`, `W ... VALUES 7 FROM (1) TO (3)` and `S ... VALUES 8 FROM (2)` (each `PIC 9
   OCCURS 3`), the program prints `  123 000 456 700 800`; rules 12-14 give `Z 123 077 456 777` and `8` for S (2) and
   S (3).

NEWS for 3.2 says "FROM and TO pending", and the FIXME in `field.c` (`validate_multi_value`) says the same. While the
feature is pending, the clause should be diagnosed rather than accepted with no effect.
