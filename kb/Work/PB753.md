# PB753 — READ — the read-ahead is a snapshot of a file another connector is changing

Found 2026-09-06 by the `PB739` implementer (report, "New defects (a)"), **MEASURED on its own fixed tree**, and
filed rather than folded in because it is a different mechanism from PB739: PB739 was the WRITE side (a release
positioned and numbered from state captured at OPEN); this is the READ side (a record image served from a buffer
filled before the release happened).

## ⛔ Reproduction status — read this before designing the fix

- **The measurement is real and is NOT re-run here.** It was taken on the PB739 implementer's **fixed** tree —
  i.e. with PB739's own change set applied, which is in flight in landing trains 16–17 together with
  [[PB713]] — using `…\a9d94900-79fe-4a38-89f0-921976861543\scratchpad\PB739\probe\pb739rs.cob` (`PB739RS`).
  That tree is not main.
- **This registrar did not compile or run anything.** Main's `cobol.exe` was deliberately not used
  (`feedback_reachability_is_measured_not_deduced` — a reachability claim is a probe to run, not a conclusion).
- ⛔ **Reproduce on main after trains 16–17 land**, before the fix is designed. The probe is the whole
  specification of the repro and needs no rewriting.
- ⚠ **What READING main says about reachability, stated as reading and not as measurement.** Every element of the
  mechanism below is at a main line number, and neither of the two things that would block the probe on main is
  on this path: both `SELECT`s in `pb739rs.cob` carry `SHARING WITH ALL OTHER` **and** `LOCK MODE IS MANUAL`, so
  `FileRegistry.RegisterSharing` (`src/Cobol.Net.Runtime/IO/FileRegistry.cs:711`) sets `SharedStreams` on both —
  which takes the INPUT and I-O opens down the `FileShare.ReadWrite` arms and therefore clear of [[PB740]]'s
  unshared-posture refusal — and `SequentialConnector.SeedSharedWriteBase` returns immediately unless the mode is
  EXTEND (`SequentialConnector.cs:109`), so [[PB713]]'s `IOException` is not on an I-O open either. **That is an
  argument, not a run.** Treat it as the hypothesis the reproduction tests, not as a claim that main is already
  broken this way.

## What was measured

`pb739rs.cob` — one `ASSIGN TO "pb739rs.dat"`, `ORGANIZATION IS SEQUENTIAL`, three `SELECT`s: `FS` seeds
**300 four-byte records** (1200 bytes — deliberately over the 1024-character `StreamReader` buffer, which is what
makes the read-ahead observable at all), then `FR` opens INPUT and reads record 1, then `FW` opens I-O, reads
forward to record 3, `REWRITE`s it to `NEW`, and closes; `FR` then reads records 2 and 3.

```
R-1=OLD   W-IO=00   W-RW=00
R-2=OLD   R-3=OLD           ← the record FW replaced, served from FR's buffer
DISK-3=NEW                  ← what is actually in the physical file
```

Both statuses are `'00'`. **No status anywhere says the reader is looking at superseded data**, which is why
`silent: true` accompanies `wrong_answer: true`: a concurrent read/update pass computes from data the same run
unit has already replaced, and reports success at every step.

**The APPEND case is NOT affected, and this was measured too** (`pb739rv.cob`, `pb739rw.cob`): a record appended
by a sibling IS delivered to an already-open reader, both when the reader has read nothing and when it has
already consumed the whole file — because a reader can only have buffered what existed. Recorded here so a
later reader does not widen the note to a shape that was checked and is correct.

## What the standard prints — every clause re-derived with `cite.py --check`, none inherited

- `--check 14.9.35.4 "The successful execution of the REWRITE statement releases a logical record to the
  operating environment"` → **OK §14.9.35.4 4)**. The REWRITE that reported `'00'` did not merely intend to
  write; GR4 says the record **is** with the operating environment. The measurement confirms the standard is
  satisfied on disk — `DISK-3=NEW`.
- `--check 9.1.15 "The sharing with all other mode allows concurrent access to a physical file through other file
  connectors specifying input, I-O, or extend mode"` → **OK §9.1.15 3)**. The concurrency the probe sets up is
  **legal**, explicitly. This is the clause that makes the situation the compiler's problem rather than the
  program's.
- `--check 14.9.30.1 "For sequential access, the READ statement makes available the next logical record from a
  file"` → **OK §14.9.30.1**. What a READ makes available is *the next logical record from the file* — not the
  next record from a buffer of what the file said earlier. Together with GR4 that is the whole derivation: a
  READ executed after a release must deliver the released record.

⚠ **The derivation deliberately does not lean on a rule about buffering, because the standard has none to lean
on.** §9.1.15's model is file connectors over a physical file; the read-ahead is entirely ours. That is what
makes this a defect and not an implementor-defined latitude question — no reading of §9.1.15 3) admits an
input connector that shows a record the physical file no longer contains.

## The mechanism, at current line numbers on main (`0a24276f`)

1. `src/Cobol.Net.Runtime/IO/SequentialConnector.cs:21` — `private StreamReader? _reader;`. A `StreamReader`
   buffers; the class header says so itself at `:28-29`: *"the StreamReader BUFFERS, so BaseStream.Position is
   the buffer-fill boundary, never the read position"*.
2. `:297-300` — the INPUT open. The §9.1.15 participant arm, `:298`, is
   `new StreamReader(new FileStream(HostPath, FileMode.Open, FileAccess.Read, FileShare.ReadWrite),
   Encoding.Latin1)`: the **OS handle** was made shareable, and the **buffer above it** was not made coherent.
   That is the whole defect in one line — sharing was solved at the handle and not at the read.
3. `:337-338` — the I-O open, `SharedStreams ? FileShare.ReadWrite : FileShare.Read`, so the sibling's handle can
   coexist.
4. `:745-753` — the record-sequential REWRITE writes through **`_reader.BaseStream`**, seeking to
   `_lastReadBlockStart`, writing the Latin-1 bytes and calling `stream.Flush()` at `:751`. The bytes reach the
   file. Nothing notifies any other connector.
5. `:690-700` (`FillChars`, the fixed-width/varying path — `int n = _reader!.Read(buf, total, count - total);` at
   `:695`) and `:710-723` (the line-sequential path — `_reader.Read()` / `_reader.Peek()`) serve from the buffer
   filled before step 4. There is **no** invalidation on either path.

## ⛔ The rule is already written down — for one arm only

`SeekToRecord` (`:846-849`) is the ONLY `DiscardBufferedData` call in the file, and its doc comment at `:844-845`
states the rule this defect breaks, in the standard's own terms:

> `StreamReader.DiscardBufferedData` is required: the reader buffers ahead of the base stream, so seeking the
> stream alone would keep serving stale characters.

So the connector knows that a change to the underlying stream invalidates its buffer — **when the change is its
own** (a `START`). The identical change made by a *sibling* connector over the same physical file was never
given the same treatment. `feedback_two_arm_dispatch` (a dispatch with two arms, only one ever fixed) and
`feedback_one_rule_one_place` (the extraction IS the fix): the invalidation rule must stop being a private
courtesy inside `SeekToRecord` and become a property of the shared physical file.

## The fix shape

⛔ **Not a `DiscardBufferedData()` sprinkled at the top of `Read`.** That would be correct-by-accident and
per-call-site, and CLAUDE.md rule 5 asks for the shape that makes the next case automatic. Two admissible
structures, both of which put the rule where the sharing already lives:

1. **A mutation generation on the physical file's shared state.**
   `src/Cobol.Net.Runtime/IO/Sharing/PhysicalFileTable.State` is already the per-host-path record of who is open
   and what is locked, keyed by resolved host path — the same key `KeyedStoreTable` uses. Give it a monotonically
   increasing *release counter* bumped by every WRITE/REWRITE/DELETE that reaches the physical file, have each
   reader record the value its buffer was filled at, and re-fill when they differ. This is the read-side twin of
   PB739's write-side rule stated in PB739's own DEVLOG paragraph — **the position and the identity of a released
   record are read from the shared medium at the release, never from per-connector state captured at OPEN** — and
   it generalises to `RelativeConnector`/`IndexedConnector` unchanged should they ever stop being store-backed.
2. **An unbuffered reader for a §9.1.15 participant.** Simplest and demonstrably sufficient (the participant
   already takes a different `FileStream` arm at `:298`, so there is a natural place for it), but it pays the
   cost on every read of every sharing-active file whether or not anyone else is writing, and it leaves the rule
   unstated — a third organization or a fourth framing can re-introduce the divergence.

⭐ Shape 1 is preferred, shape 2 is the fallback, and **whichever is chosen the drift test is the deliverable
that keeps it true**: no read path under `src/Cobol.Net.Runtime/IO` may serve characters buffered before the
shared state's release counter last moved. Pair it with the probe as a golden — the matrix, not the case
(`feedback_probe_the_shape_the_subject_hides`): reader-then-writer and writer-then-reader, buffer-crossing and
sub-buffer record counts, all three sequential framings (record / varying / line), and the APPEND legs above as
the controls that must stay green.

## Sweep

- **All three sequential framings share `_reader`.** The probe is record-sequential; `_lineSequential`'s
  `ReadPhysicalLine` (`:710-723`) and the varying framing both read through the same buffered `_reader`, so the
  same staleness is expected there and is **unmeasured**. PB739's write side found precisely this — *"it was
  wider than the report that filed it: all three sequential framings lost a record"* — so assume the same width
  here until measured (`feedback_scan_all_similar`).
- **The keyed organizations are already correct, and for the reason that names the fix.** `RelativeConnector` and
  `IndexedConnector` do not read the host file per operation: they attach to the ONE `KeyedStoreTable` store for
  the path ([[PB143]]), so every mutation is instantly visible to every attached connector. That is shape 1
  above, already built, for the other two organizations — which is the strongest argument that the sequential
  connector's shared medium wants the same treatment rather than a buffer tweak.
- **Not this note:** [[PB740]] (an unshared connector's OS posture refusing opens Table 19 permits) and
  [[PB713]] (`SeedSharedWriteBase`'s `FileShare.Read` probe colliding with a held write handle) are both about
  the *handle*, before any record is read. This is about the *buffer*, after. Checked and excluded deliberately
  so the three are not conflated by a later reader — though all three want the same restructuring of where a
  connector's stream posture is decided, so **landing order matters: PB713 → PB739 → PB740 → PB753**.
