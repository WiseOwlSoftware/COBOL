# PB4340 — `check-batch --help` shows the root command's `<source>`

**Found 2026-10-31** by the PB1610 review finisher (wave 20261791 group C, report
`E:\COBOL-coord\scratch\reports\w20261791c-PB1610-report.md`, "New defects" 2). The help text sends a reader to a
command line that does not exist: `cobol check-batch --help` lists `<source>` and prints
`cobol <source> check-batch <manifest>`.

**Sites:** `src/WiseOwl.Cobol.Cli/Program.cs:210` (`Program.BuildParser`, the `check-batch` command).

The `<source>` argument belongs to the root command; the subcommand inherits it into its usage line. The fix is in how
`BuildParser` declares the root argument against the subcommand (a root-level argument the subcommand does not take), not
in the help text. The report gives the symptom only; the implementer confirms the mechanism against the System.CommandLine
version the CLI uses. Related: PB2619 (hand-written CLI help for the edition list), PB4126 (the same builder).

## Landed (wave 20261816, group A)

**Re-probe** (this tree): `cobol check-batch --help` printed `cobol <source> check-batch <manifest> [options]` and
listed `<source>`; `cobol x.cob check-batch m.tsv` ran the batch and ignored `x.cob`. **Mechanism** (System.CommandLine
2.0.9): a parent command's arguments are written before a subcommand, in the usage line and in the grammar alike, so a
subcommand of the compile root inherits its positional. **Fix:** the two verbs are two command trees,
`Program.BuildParser` (the compile) and `Program.BuildCheckBatchParser`, and `Program.Parse` chooses the tree by the
first word; the compile's description names the batch check. After the fix the help prints
`cobol check-batch <manifest> [options]` with only `<manifest>`, and a source before check-batch is a usage error.
Pinned by `CliParserTests`.
**Sites (added by the landing):** `src/WiseOwl.Cobol.Cli/Program.cs` (`Program.Main`, `Program.Parse`,
`Program.BuildParser`, `Program.BuildCheckBatchParser`), `tests/WiseOwl.Cobol.Tests.Unit/CliParserTests.cs`.
