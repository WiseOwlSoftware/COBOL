# PB3536 — a wave re-runs a gate its agent left running

## Owner (2026-10-22 ~16:50 PDT, verbatim)

"Reruning these simply wastes tokens: but the workflow returned before its gate finished, so it needs the gate re-run at
its head and a round-2 review. - we should have the failure in the first place"

## Evidence

Wave 1150 group A (PB3527), review finisher round 1 on `worktree-wf_79d63bf1-b34-12` returned:

`status SPLIT, head 450962a35, gate_run "none: the gate was still running when the workflow forced this return (log scratchpad/w1150/w1150a-fin/gate.log)", gate_verdict "INCOMPLETE: no BUILD-LOCAL GATE verdict yet (the audits were GREEN)"`

(journal `C:\Users\brent\.claude\projects\E--COBOL\6152fc0c-4ad8-43af-8091-47da881f4100\subagents\workflows\wf_79d63bf1-b34\journal.jsonl`,
agent ab2b8fa560552d97a).

The finisher had fixed three blocking findings and two leads and spent its turn budget (cap 160, each gate wait a bounded
`timeout 580` tool call) before the gate verdict landed. `wf_rolling_wave.js` wraps the finisher in
`withCeiling(agent(...), CEILING_MIN 240)` and reads any non-DONE as SPLIT (`asSplit`, line about 333), with no reading of
the gate run the agent named. The Mythos session then had to dispatch a second finisher whose whole job is to re-run
`build-local.ps1` at the same head.

Code sites: `.claude/skills/workstream/templates/wf_rolling_wave.js`, `scripts/build-local.ps1`.

## Fix shape (two parts, one change)

1. The wave AWAITS a gate the agent left running: an agent may return `status GATE-PENDING` with `gate_run` (the run
   directory) and `head`. The wave polls that run's verdict file (never the log tail) until the verdict lands, then
   continues exactly as if the agent had returned DONE with that verdict (review on a CLEAN-able DONE, finisher on RED),
   inside the same ceiling. The agent brief says so (MANDATORY-PRACTICES P2 stays: never end a turn while YOUR OWN
   background job runs, except by this handoff).
2. `build-local.ps1` reuses a recorded verdict for the same head and an unchanged tree (the self-test reuse rule, kb/Work
   PB2914/PB3022, extended to the gate): the run directory records the head and the tree hash it measured, and a re-gate at
   that head with no change answers from it and says so in its verdict line.

## Golden / drift

Self-tests for both parts.

## Landed (wave 1152 group A)

**Re-probe.** The wave-1150 finisher's gate run `20261022T225440Z-2797b8` (worktree `wf_79d63bf1-b34-12`) holds no file
at all and its log stops in the audits at 15:55:22: the return KILLED the gate, it did not merely leave it unread. The
agent's shell is in no job object (`IsProcessInJob` false), so the harness kills by walking the process tree, and a
calibration showed a target its caller starts directly dies with that walk whatever its creation flags. So the fix
shape grew by one mechanism (CLAUDE.md rule 5): a gate the wave can await must first SURVIVE the return.

- **`scripts/detached.py`** — THE one launch that outlives its caller: a launcher starts the target and exits at once
  (no tree walk reaches it; Windows: its own process group, a console with no window, out of the caller's job where
  allowed; POSIX: its own session). `land_lane.py`'s `spawn` moved here (its no-window arm with it); its runners were
  exposed to the same tree kill.
- **`scripts/run_gate_legs.py`** — `build-local` makes the run directory, starts the gate (`--run <run>`) DETACHED with
  `gate.log` and `gate.pid` there, and FOLLOWS it (log echoed, the gate's exit code). `watch` / `--await <run>
  [--worktree W] [--wait-s N]` is the one wait: the verdict file's line and exit code; a process that DIED with none
  `NOT RUN [verdict]` (2); PENDING (4, since main's PB3527 made 3 BUSY); no run directory `NOT RUN [run]` (2); a
  relative run name is W's run (`resolve_run`, review R1-1). Every verdict record (schema 3) carries head, the tree
  measured at start and end (the working tree through a private index, coord.NEVER_WORK's paths at HEAD's content so
  the harness's edit of the tracked `.claude/settings.local.json` is no difference: review R1-2), base and exit code; `Gate.reusable` answers a re-gate of an unchanged tree and base from the newest GREEN under
  a scope it covers, its line `… GREEN — REUSED (kb/Work PB3536): …` naming the measuring run. A RED, another tree, another
  base, a narrower scope or a tree edited while gated never reuses.
- **`wf_rolling_wave.js`** — `GATE-PENDING` in the schema; `settleGate` awaits the run's verdict file (one
  `cobol-locator` per window running `--await`, inside the agent's own ceiling, a cancel flag stopping new windows):
  GREEN reads DONE (finished test, review), any other verdict one gate finisher (`gate_fix_rounds`), no verdict STALLED;
  a review finisher's GATE-PENDING settles the same way.
- **`plan_wave.Report`** — `Status: GATE-PENDING` with a `Gate run:` field; `gate_state` (GREEN only for the report's
  HEAD and that commit's tree); `finished` includes a GREEN one, so the survey and the wave's finished test need no
  awaiter; the planner waits on a RUNNING handed gate and plans a finisher for an ENDED one.
- Docs: MANDATORY-PRACTICES P2 (the one exception) and I1, the dispatch spec's HOW TO WAIT step 4, the finisher and
  fix-lane briefs, the report template, the gate skill, DESIGN-test-build-ci.md §3.14.12, DESIGN-orchestrator-loop.md 4.9.
- Self-tests: `run_gate_legs.py` +10 arms (declared in `GateLegDriftTests` Arm3), `detached.py` 3 arms,
  `test_rolling_wave.py` +4 (GATE-PENDING → GREEN → review, → RED → gate finisher, never a verdict → STALLED, a review
  finisher's handoff), `test_plan_wave.py` +3.
