# PB3918 — order-table-clause-not-supported: SPECIAL-NAMES ORDER TABLE clause refused ('PROCEDURE DIVISION header missing'); COBOL 2002/2014 require the syntax to be accepted

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S7) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\order-table-clause-not-supported.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\order-table-clause-not-supported\`.

## Summary

GnuCOBOL 3.2 refuses the SPECIAL-NAMES clause `ORDER TABLE ordering-name-1 IS literal-9` (cultural ordering, the
companion of FUNCTION STANDARD-COMPARE) with `PROCEDURE DIVISION header missing` and `syntax error, unexpected ORDER`,
under `-std=cobol2014`, `-std=cobol2002` and the default dialect. The clause is processor-dependent (it depends on an
implementation of ISO/IEC 14651), but the 2002 standard, and the 2009 committee draft that led to the 2014 standard,
both require an implementor without 14651 support to accept the syntax and set EC-ORDER-NOT-SUPPORTED. Only the 2023
edition lets the implementor refuse the syntax. Class: rejects legal ISO source (editions 2002 and 2014).

## Minimal test case

Free reference format (`-fformat=free`), 9 lines, written for this record. The 9 fuzz witnesses of nights 3 to 5
(for example fz00329, fz00387, fz00429; 58 programs across the nights) all stop on `PROCEDURE DIVISION header missing`
at their ORDER TABLE line and reduce to it.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. ORDTAB.
ENVIRONMENT DIVISION.
CONFIGURATION SECTION.
SPECIAL-NAMES.
    ORDER TABLE OT IS "ISO 14651_2020_TABLE1".
PROCEDURE DIVISION.
DISPLAY "OK"
STOP RUN.
```

File: `E:\COBOL-coord\scratch\op\pb3838\records\order-table-clause-not-supported.cob`.

The program is legal: the clause follows the general format of §12.3.7.2; literal-9 is an alphanumeric literal, not
zero-length and not a symbolic character (§12.3.7.3 10) and 11)); the ordering-name is not used outside STANDARD-COMPARE
(§12.3.7.3 9)); the allowable content of literal-9 is the implementor's (§12.3.7.4 17)), so its text cannot make the
program illegal. The program does not call STANDARD-COMPARE, so its output does not depend on 14651 support.

## Expected result (per ISO)

Under the 2002 and 2014 editions: the program compiles and prints `OK`.

- ISO/IEC 1989:2023 §12.3.7.2 (checked) carries `[ ORDER TABLE ordering-name-1 IS literal-9 ]` as the last clause
  of the SPECIAL-NAMES paragraph. §12.3.7.4 17) (checked): "When ORDER TABLE is specified, ordering-name-1 shall
  reference a cultural ordering table that is identified by literal-9 and constructed in accordance with ISO/IEC
  14651:2020, Annex A. The implementor specifies the allowable content of literal-9."
- §12.3.7.3 9) (checked): "Ordering-name-1 may be specified only in the STANDARD-COMPARE intrinsic function."
  §12.3.7.3 10) (checked): "Literal-4 and literal-9 shall be alphanumeric or national literals."
- The clause is processor-dependent. The 2023 text, §A.3 25) (checked): "The STANDARD-COMPARE intrinsic function, the
  EC-ORDER-NOT-SUPPORTED exception condition, and the ORDER TABLE clause in the SPECIAL-NAMES paragraph are dependent
  upon an implementation of ISO/IEC 14651:2020. The implementor need not accept the syntax or set the
  EC-ORDER-NOT-SUPPORTED exception condition to exist when support for ISO/IEC 14651:2020 is not provided."
- Editions 2002 and 2014 say the opposite. The 2002 text (ISO/IEC 1989:2002(E), the post-ballot text of 2001-12-04),
  Annex B.3 item 8: "The STANDARD-COMPARE intrinsic function and the ORDER TABLE clause in SPECIAL-NAMES are dependent
  upon an implementation of ISO/IEC 14651:2001. The implementor is required to accept the syntax and set the
  EC-ORDER-NOT-SUPPORTED exception condition to exist when support is not provided." The 2009 committee draft that led
  to 2014 (ISO/IEC 1989:20xx CD 1.2, 2009-08-23), Annex A.3 item 14, has the same sentence ("The implementor is
  required to accept the syntax and set the EC-ORDER-NOT-SUPPORTED exception condition to exist when support is not
  provided."). Both drafts carry the clause in the SPECIAL-NAMES general format.

Edition: the clause is a 2002 feature. For 2002 the requirement to accept the syntax is in the 2002 text. For 2014 it is
derived from the 2009 committee draft: the published 2014 text is not in hand, and the 2023 Annex E (§E.1, the list of
2014-to-2023 changes) does not record the relaxation, so the point at which "required to accept" became "need not
accept" is not established from the 2023 text alone. If the published 2014 text already carries the 2023 wording,
this record becomes implementor latitude for `-std=cobol2014` and remains a defect for `-std=cobol2002`.

Under the 2023 wording the refusal is allowed, but §4.2.6 (checked) still requires "a warning mechanism at compile time
to indicate use of syntactically-detectable processor-dependent language elements not supported by that
implementation", one that identifies the unsupported element; `PROCEDURE DIVISION header missing` does not identify
it. (Recorded for completeness: GnuCOBOL 3.2 does not claim 2023.)

Edition as recorded by the adjudicator: 2002 (2002 text, Annex B.3 item 8) and 2014 (derived from the 2009 CD 1.2, Annex A.3 item 14: 'required to accept the syntax'); the 2023 text A.3 25) relaxes it. `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Our compiler (WiseOwl)

WiseOwl COBOL (built from main 6ed90bd1c), `cobol ordtab.cob --std 2014 --source-format free -o ordtab.dll`, then
`dotnet ordtab.dll`: compile exit 0, run exit 0, output `OK`. WiseOwl claims support for §A.3 25) and implements
STANDARD-COMPARE over the clause (`docs/CONFORMANCE.md` §2 row 25); a literal-9 it does not recognize draws the
COBOL1662 warning and sets EC-ORDER-NOT-SUPPORTED at each reference (night-3 witness fz00429).

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/parser.y`, rule `special_name` (line 4488): no ORDER TABLE alternative; the `ORDER` token (declared line
  3065) is used only by `_in_order` (line 20430). The parser's error recovery then reports
  `PROCEDURE DIVISION header missing` at the clause.
- A minimal conforming fix for 2002/2014 adds the clause to `special_name`, records ordering-name-1 for
  STANDARD-COMPARE, and, without ISO/IEC 14651 support, sets EC-ORDER-NOT-SUPPORTED when the function uses it (see
  the separate record standard-compare-not-implemented-at-run-time for the function's own state in 3.2).
