# PB5157 - a wave's concurrency is a snapshot of a moving value

**Sites:** `scripts/orchestrator/plan_wave.py` (`wave_concurrency`, `plan_main`); 
`.claude/skills/workstream/templates/wf_rolling_wave.js` (whole: its worker pool is sized once from `args.concurrency`); `docs/rearchitecture/DESIGN-orchestrator-loop.md` and the
workstream skill's rolling-wave text that describe the derivation.

**Evidence (2026-11-10).** `E:\COBOL-coord\scratch\wf-args-w20261983.json` carries `"concurrency": 2`, planned at 10:23 when one
slot was held by another lane's gate (cap 3 - 1 held - 0 waiting). At 11:54 `gate_slot.py status` showed all three slots free; the
wave's groups C to H had been queued 104 minutes (each mailing a false STALL, PB5097). `prune_worktrees.py`: 0 waiting to land, 0
enqueued; the merge queue sat empty because the fix lane produced nothing to land, not because the landing lane lagged.

**What is wrong.** PB5100 derived the number from the gate pool but evaluated it at one instant. Another lane's gate that
happens to hold a slot at planning time lowers the wave's width for hours after it has finished. The opposite moment (all slots
free at planning, then other lanes gate) is harmless, because an extra implementer only waits on `gate_slot`'s queue.

**Fix direction.** The width must follow the pool as it moves: either the pool size is the cap (the gate-slot queue already
serialises gates, and an implementer waiting on a ticket is cheaper than a slot idle for 100 minutes), or the rolling wave reads
the free slots each time a worker frees and starts that many. Pick the shape that makes the next case automatic (rule 5) and pair
it with a drift test that fails when a wave's width is fixed from a planning-time reading.
