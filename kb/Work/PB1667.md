# PB1667 — LANDED

Filed 2026-09-27 by the train-68 lander from the wave-68 V report (`w68v-PB1130-report.md`, new defects 1 and 2),
restated by V2 (`w68v2-PB1272-report.md`, lead 3) as one root: a zero advance on a line that is still open.

**Arm 1 — WRITE ADVANCING 0.** Repro `scratchpad/w68v/l/adv0.cob` writes `ABC    XYZ` on ONE line. Rule:
§14.9.51.4 25) c) (`cite.py --check 14.9.51.4` OK §14.9.51.4 25) c)): "If integer-1 or the value of the data item
referenced by identifier-2 is zero, no repositioning of the representation of the printed page is performed" — the
second line is presented at the SAME vertical position (an overprint), not concatenated to the first line's text.
Code: `src/Cobol.Net.Runtime/IO/SequentialConnector.cs#WriteAdvancingRecord` (~1262) → `Present` (~749), which
appends to the open line.

**Arm 2 — re-INITIATE on an open report file.** Repro: OPEN OUTPUT; INITIATE; GENERATE; TERMINATE; INITIATE;
GENERATE; TERMINATE — the second run's first detail lands on the first run's last CF line (`S=05`, seen in golden
`2002/pb1130_report_sum_size_line_overlap`'s development). Rule: §13.18.35.4 6) (`cite.py --check 13.18.35.4` OK
§13.18.35.4 6)): the line "is now printed on the page at that vertical location". Code:
`src/Cobol.Net.Runtime/IO/ReportWriter.cs#Initiate` (~514) sets `_physLine = 0` while the connector's line is open,
so the next advance is 0.

**What the fixer owes.** One representation of "the open line" owned by the connector (V moved the held line into
it), with a zero advance meaning overprint at the device boundary; the report engine's page-empty state must not
reuse the physical line. Goldens for both arms.

## Analysis 2026-09-29 (batch 8, not taken)

Arm 1 needs a determination first: how a zero advance (overprint) is REPRESENTED in a text file (ISO leaves the device representation implementor-defined; §14.9.51.4 25) c) only says no repositioning). Candidates are a bare CR, or keeping the line open; the choice belongs in docs/CONFORMANCE.md with the GnuCOBOL survey (rule 1 precedence) before code. Arm 2 (`ReportWriter.Initiate` setting `_physLine = 0` while the connector line is open) depends on that representation.

## Decided 2026-09-30 (owner) — kb/Work R54

ADVANCING 0 is written as a bare carriage return (GnuCOBOL `cob_seq_write_opt`); implement arm 1 that way and re-derive arm 2 (re-INITIATE line state) from it. Decision note R54; documented in docs/CONFORMANCE.md.

## Landed 2026-09-30 (batch PB1840 implementer, DEVLOG 1816)
**Arm 1.** `SequentialConnector.WriteTravel` (the one travel of a WRITE's own ADVANCING amount, reached by `Advance` and `PositionOnLogicalPage`): a zero amount writes a bare carriage return when a line is open (`DeviceOnOpenLine`), nothing otherwise. Determination in docs/CONFORMANCE.md "ADVANCING 0 is an overprint" (R54). Golden `2023/pb1667_advancing_zero_overprint` (record sequential AFTER/BEFORE/identifier/LINAGE, bytes read back). Re-pinned: `LinageConformanceTests` LNGBYI, `FileIoDifferentialTests.WriteAdvancingMnemonic_ZeroLineAdvance…` (CSP = ADVANCING 0), NIST `Normalize` now DROPS a lone CR as its doc always said (SQ101M/SQ207M).
**Arm 2.** `CobolReport.PresentLine` treats its empty page model as "device at line 1" only while `CobolFile.DeviceOnOpenLine` is false, else the device stands at line 0; `PageFeed` writes its empty image BEFORE the feed so the feed leaves no open line. Golden `2002/pb1667_reinitiate_open_report_file`.
**Not done (PB1840):** a BEFORE-placed record presented on a line still open (an AFTER write's record) is appended (GnuCOBOL) rather than overprinted from column 1; LinageConformanceTests LNGBYF pins the append. Also REPORTS ARE r1 r2 on one FD is COBOLNET0899 (existing), so a second-report-on-the-same-file leg could not be written.
