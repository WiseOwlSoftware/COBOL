# PB547

## Mechanism — usage-clause-p3
usage-p3/F1 — an alphanumeric (USAGE DISPLAY) item admits characters the implementation's own documented character size cannot represent, and loses them silently at the byte boundary. In memory a DISPLAY character position holds a UTF-16 code unit (probe: U+2603 stored in a PIC X(3) and read back through FUNCTION ORD); at every byte channel the position is one byte, so a code unit above 0xFF is written as '?' (0x3F). The project already DECIDED the disposition for exactly this substitution — docs/CONFORMANCE.md DOC-A.1-33: "the serialization substitutes '?' (0x3F) and sets EC-DATA-CONVERSION ... visible under checking and never silent" — and wired it into CONVERT's ANUM->BYTE leg only; the record/file write path substitutes without raising anything, so the same decision has two arms and one was implemented.

### Expected, from the standard
13.18.60.4 GR7 (cite.py --check OK): "Alphanumeric characters shall be represented in the storage of the computer as characters of uniform size equal to or less than the size of characters in the computer's national character set. Each implementor shall specify the size and representation of characters stored for usage DISPLAY." One uniform size covering everything the item may hold. Under the implementation's own determination (DOC-A.1-209, one byte per character position) a character above 0xFF is outside the alphanumeric coded character set and must not be admitted silently; under the alternative determination its own DOC-A.1-188/DOC-A.1-33 state ("the native alphanumeric and national repertoires are UTF-16, one code unit per character position") the character IS in the repertoire and shall survive the byte channel. Either way, the substitution the implementation actually performs is the case DOC-A.1-33 already decided: substitute '?' AND set EC-DATA-CONVERSION, so FUNCTION EXCEPTION-STATUS shall report EC-DATA-CONVERSION after the WRITE under >>TURN EC-ALL CHECKING ON.

```
$ python scripts/spec/cite.py --check 13.18.60.4 "Alphanumeric characters shall be represented in the storage of the computer as characters of uniform size equal to or less than the size of ..."
  OK  §13.18.60.4 7)  (General rules)
```

### Observed
Measured at --std 2023 with EC-ALL checking ON: W1=66 and W3=9732 (FUNCTION ORD is code+1, so the item holds 'A' and U+2603 — the wide character IS admitted and read back), up3gr7g.dat is exactly 3 bytes `41 E9 3F` (the snowman became '?'), and LASTEC comes back BLANK — no exception was set. Probe q50 shows the same admission through the group image (IMG=66 234 9732). Probe q72 is the same write without checking and gives the identical 3-byte file. So the loss is real, unchecked and undiagnosed, and it contradicts the implementation's own published disposition rather than any borderline reading of the standard. Note the neighbouring documentation conflict this exposes: DOC-A.1-209 pins the alphanumeric character at ONE byte while DOC-A.1-188 and DOC-A.1-33 pin the alphanumeric repertoire at UTF-16 code units — the two answers to GR7's 'shall specify' obligation disagree.

### Finding — `character-sets` (wrong-answer; rows `GR-8.1.2-1`)

**Mechanism.** The mixed-usage REDEFINES byte image assumes one char == one byte, but an alphanumeric item may hold a UTF-16 code unit above U+00FF; CobolBits.NatReadWindow shifts image[hi] << 8 and casts to char, silently discarding the code unit's high byte, so a national view (and every write back through it) turns the alphanumeric character into a different one - a third, silent, value-changing arm beside PB547's '?' file arm and CONVERT's documented '?'+EC-DATA-CONVERSION arm.

**Repro.** probe/cs1/p2.cob (--std 2023): 01 G1. 05 A1 PIC X(4). 01 R1 REDEFINES G1. 05 N1 PIC N(2). 01 SAVEN PIC N(2). MOVE "€ABC" TO A1; MOVE N1 TO SAVEN; MOVE SAVEN TO N1; DISPLAY "[" A1 "]"; IF A1 = "€ABC" ... -> prints [¬ABC] and DIFF. p1.cob: DISPLAY N1 right after MOVE "€ABC" TO A1 prints U+AC41 U+4243.

**Expected from the spec.** §8.1.2 1) (cite.py OK): every character of the alphanumeric coded character set is represented in the same compile-time number of bytes; §13.18.44.4 GR1 makes the REDEFINES one storage area. A character admitted into A1 must therefore have a fixed-size image that a write-back of the same bytes restores unchanged (A1 = "€ABC" after the round trip) - or the character must not be admitted into the alphanumeric set at all (diagnosed where it enters). A silent change to U+00AC is neither.

**Observed / reasoning.** Generated p2.g.cs: SAVEN = CobolString.Store(CobolBits.NatReadWindow(_redef_G1, 0, 2), 2); NatReadWindow: chars[i] = (char)((image[hi] << 8) | (image[hi + 1] & 0xFF)) - image[hi] is U+20AC, << 8 overflows the char and the high byte 0x20 is lost; NatWriteWindow then writes (char)(c >> 8) = 0xAC back. No exception, no diagnostic.

**Code site.** src/Cobol.Net.Runtime/Values/Text/CobolBits.cs#CobolBits.NatReadWindow (line ~167); root = admission of >U+00FF code units into DISPLAY items against DOC-A.1-209's one-byte determination (open kb/Work PB547 and PB690 own the file arms - this arm belongs in PB547's sibling sweep, inventory_rows += GR-8.1.2-1)
