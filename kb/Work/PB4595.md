# PB4595 — relative-sequential-delete-uses-relative-key: a sequential DELETE removes the slot the RELATIVE KEY names, not the record just read

Filed 2026-11-04 from the first independent review of fuzz night 10's n10-relative-delete-rewrite draft (the PB4539 patch), whose reviewer found this pre-existing defect while probing the draft's sequential case; the drafter listed it among the defects to keep out of that ticket. The vetting below reproduced it on 3.2.0 and 3.3-dev and found no tracker ticket. Upstream status `unreported`: the owner has not yet decided to report it. The probe programs are local, outside any git tree (`~/gc-notes/PB4595/relseq.cob`, `relnokey.cob`, `relrw.cob` under WSL): the minimal program below is the repro.

## Summary

For a relative file in sequential access mode with a RELATIVE KEY clause, `DELETE file RECORD` removes the slot whose number is in the relative key data item when the DELETE runs, not the record that the preceding READ returned. If the program changes the key between the READ and the DELETE, a different record is destroyed, the record that was read survives, and the status is 00. When the RELATIVE KEY clause is omitted, cobc gives the file a hidden record-number field that only the runtime writes, and the right record is deleted. REWRITE in the same situation replaces the record that was read. Class: wrong output (the wrong record is lost).

## Minimal test case

Fixed reference format.

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. RELSEQ.
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
           SELECT F ASSIGN TO "relseq.dat"
               ORGANIZATION IS RELATIVE
               ACCESS MODE IS SEQUENTIAL
               RELATIVE KEY IS RK
               FILE STATUS IS FS.
       DATA DIVISION.
       FILE SECTION.
       FD F.
       01 REC PIC X(4).
       WORKING-STORAGE SECTION.
       01 RK PIC 9(2) VALUE 0.
       01 FS PIC XX VALUE SPACES.
       PROCEDURE DIVISION.
           OPEN OUTPUT F
           MOVE "R001" TO REC WRITE REC
           MOVE "R002" TO REC WRITE REC
           MOVE "R003" TO REC WRITE REC
           CLOSE F
           OPEN I-O F
           READ F NEXT
           READ F NEXT
           DISPLAY "READ   " FS " " REC " RK " RK
           MOVE 1 TO RK
           DELETE F RECORD
           DISPLAY "DELETE " FS
           CLOSE F
           OPEN INPUT F
           PERFORM UNTIL FS NOT = "00"
               READ F NEXT
               IF FS = "00"
                   DISPLAY "LEFT   " REC " RK " RK
               END-IF
           END-PERFORM
           CLOSE F
           STOP RUN.
```

## Environment

`cobc (GnuCOBOL) 3.2.0` (`/usr/bin/cobc`) and a 3.3-dev tree (tarstamp 2026-10-29, `COB_NUM_TAR_DATE 20261029`, run through `~/opt/gnucobol-3.3-dev/bin/cobc-dev` and `run-dev`), WSL2 Ubuntu x86_64. Compiled with `cobc -x -o relseq32 relseq.cob` (also `-std=cobol2014`, `cobol2002`, `cobol85` and `default`) and run as `./relseq32` with no `relseq.dat` present. Controls: the same program without the RELATIVE KEY clause (`relnokey.cob`) deletes R002; the same program with `MOVE "XXXX" TO REC` and `REWRITE REC` in place of the DELETE (`relrw.cob`) replaces R002.

## Observed result

The program compiles with no diagnostic (3.2.0 prints only the toolchain's `_FORTIFY_SOURCE redefined` warning), exit code 0, and prints on 3.2.0 and 3.3-dev, under every `-std` tried:

```text
READ   00 R002 RK 02
DELETE 00
LEFT   R002 RK 02
LEFT   R003 RK 03
```

R001, which was never the subject of the DELETE, is gone; R002, the record the READ returned, is still in the file. With RK naming no record (`MOVE 9 TO RK`) cobc returns 23 and deletes nothing, and with `MOVE 0 TO RK` it returns 24, an invalid-key status in a mode where INVALID KEY cannot be written (§2023:14.9.10.3 2)); `MOVE 3 TO RK` deletes R003. ISO requires R002 deleted with status 00 in every case. Probes: `~/gc-notes/refute-PB4595/k9.cob`, `k0.cob`, `k3.cob`.

## Expected result (per ISO)

The program prints `LEFT   R001 RK 01` and `LEFT   R003 RK 03`: the DELETE removes R002, the record the last READ returned, whatever the program has since moved to RK.

- §2023:14.9.10.4 2) (checked): "For a file that is in the sequential access mode, the last input-output statement executed for file-name-1 prior to the execution of the DELETE RECORD statement shall have been a successfully executed READ statement. The mass storage control system logically removes from the physical file the record that was accessed by that READ statement." The MOVE is not an input-output statement, so the last one is the successful `READ F NEXT` that returned R002.
- §2023:14.9.10.4 4) (checked): "If the file is relative and the access mode is random or dynamic, the mass storage control system logically removes from the physical file that record identified by the content of the relative key data item associated with file-name-1." Only random and dynamic access identify the record by the key's content; rule 2 governs sequential access.
- §2023:14.9.30.4 25) (checked): the READ "moves the relative record number of the record made available to the relative key data item" — the key is output from the READ, and §2023:12.4.5.13.4 2) (checked) says only that data-name-1 "is used to communicate a relative record number between the user and the mass storage control system"; nothing forbids the program from changing it, or makes the DELETE read it, in sequential access.

Edition: 2014. The 2009 committee draft that became the 2014 edition has rules 2 and 4 the same rules (its 14.9.9.3 2) and 4), worded "DELETE statement" where 2023 has "DELETE RECORD statement", with "(MSCS)"), and so does the 2001-12 pre-publication text of ISO/IEC 1989:2002 (`t2002.txt`, WG4 N 0147; 14.8.9.3 2) and 4), same wording as the 2009 draft); the published 2014 text was not checked and is inferred to match.

## Our compiler

WiseOwl COBOL (`--std 2014`, fixed format): prints `LEFT   R001 RK 01` and `LEFT   R003 RK 03` after `DELETE 00`, exit code 0 — correct (main build of 2026-11-03).

## Fix site

`libcob/fileio.c`, `relative_delete` (about line 3436 in the 3.3-dev tree): it has no access-mode arm. It always computes the slot as `cob_get_int (f->keys[0].field) - 1`, so in sequential access it deletes whatever slot the user's RELATIVE KEY item holds. `relative_rewrite` (about line 3397) does have a `COB_ACCESS_SEQUENTIAL` arm and works from the file offset the READ left, which is why REWRITE is right here. Without a RELATIVE KEY clause `cobc/codegen.c` (about line 9444) gives the file a hidden `_recnum` field that only the runtime sets (`relative_write` on a sequential WRITE, in its "Update RELATIVE KEY" block after the write at 3.3-dev line 3335 onward, and `relative_read_next` on a READ), so the defect needs a user key. Inferred fix: in sequential access, delete the slot of the last successful READ. Remembering that slot number in the `cob_file` is more robust than deriving it from the file offset, because `relative_read_next`'s READ PREVIOUS arm leaves the offset one slot further back (PB4530's mechanism). The pending PB4539 patch (n10-relative-delete-rewrite) edits the same function. For this program it changes nothing (DELETE 00, R001 still removed; run by the refuter against the patched libcob in `~/gc-fix/n10-relative-delete-rewrite/libcob/.libs`, confirmed with ldd, printing DELETE 00, LEFT R002, LEFT R003, because RK=1 names R001, which exists). Only when RK names an empty slot, as in the reviewer's two-DELETE probe, does it change the status from 00 to 23; it never changes which record is removed.

## Draft issue

**Title:** RELATIVE file, ACCESS SEQUENTIAL: DELETE removes the slot named by the RELATIVE KEY item, not the record the last READ returned

Environment: GnuCOBOL 3.2.0 (and a 3.3-dev tree of 2026-10-29), WSL2 Ubuntu x86_64; `cobc -x -std=cobol2014 -o relseq relseq.cob`.

Program (`relseq.cob`, fixed format): write R001-R003; OPEN I-O; READ NEXT twice, giving R002; `MOVE 1 TO RK`; `DELETE F RECORD`; list what is left.

```cobol

               RELATIVE KEY IS RK

       DATA DIVISION.
       FILE SECTION.
       FD F.
       01 REC PIC X(4).
       WORKING-STORAGE SECTION.
       01 RK PIC 9(2) VALUE 0.

           OPEN OUTPUT F

           MOVE "R002" TO REC WRITE REC
           MOVE "R003" TO REC WRITE REC
           CLOSE F
           OPEN I-O F
           READ F NEXT
           READ F NEXT
           DISPLAY "READ   " FS " " REC " RK " RK
           MOVE 1 TO RK
           DELETE F RECORD
           DISPLAY "DELETE " FS
```

Observed (exit code 0, no diagnostic): `DELETE 00`, then the file holds R002 and R003: R001 was deleted and R002, the record just read, was not.

Expected: the file holds R001 and R003. ISO/IEC 1989:2023 §2023:14.9.10.4 2): "For a file that is in the sequential access mode, the last input-output statement executed for file-name-1 prior to the execution of the DELETE RECORD statement shall have been a successfully executed READ statement. The mass storage control system logically removes from the physical file the record that was accessed by that READ statement." Only random and dynamic access use the relative key's content (§2023:14.9.10.4 4)). REWRITE in the same program already replaces the record that was read, and the same program without a RELATIVE KEY clause deletes R002.

Fix site (observed): `libcob/fileio.c`, `relative_delete` always takes the slot from `f->keys[0].field` and has no `COB_ACCESS_SEQUENTIAL` arm, unlike `relative_rewrite`.
