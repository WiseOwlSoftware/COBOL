`4da7ba02d`, read-only; nothing was deleted.

## What was measured

`git merge-base --is-ancestor <sha> origin/main`:

```

origin/ci/c5b94bf05423  *** NOT on main    Train 33: DEVLOG 1603 …            09-13 13:15
origin/ci/c774def44463  (train 43, IN FLIGHT at the time of filing — legitimate, not litter)
```

**Six of the eight are not ancestors of main at all**, although their commit SUBJECTS name trains that
demonstrably landed. So the surviving branches are not one failure mode but two.

## Two mechanisms, and the first one is not the one I first guessed

⚠ My initial hypothesis — "a caller cut off by the command timeout re-runs, and the idempotent path resumes
past the cleanup" — is **WRONG**, and reading the script disproves it: `DELETE_BRANCH=1` is the default
(`scripts/push-main.sh:34`) and the delete at `:168-172` is deliberately unconditional, with a comment saying
so, precisely to cover the re-run path. The premise was plausible and the code says otherwise. Recording the
dead hypothesis because the next reader will form the same one.

**Mechanism A — orphaned verification attempts (6 branches).** `BRANCH="$PREFIX/$SHORT"` (`:55-56`) is
computed from **HEAD at invocation**. When a lander pushes `ci/<sha1>`, then rebases onto a moved
`origin/main` or amends the commit, its next invocation computes `ci/<sha2>`, lands `sha2`, and deletes
**only `ci/<sha2>`**. `ci/<sha1>` is orphaned permanently — no invocation will ever compute that name again.
The script already knows this class of problem exists: `:157` warns "HEAD moved while CI ran" for the case
where HEAD moves *during* its own run. The case where the CALLER moves HEAD *between* runs has no handler.

**Mechanism B — a cleanup that cannot report its own failure (2 branches).** The delete is
`git push --quiet origin --delete "$BRANCH" 2>/dev/null && say "…deleted…"`. Stderr is discarded and the
success message is gated behind `&&`, so a refused or failed delete produces **no output and no exit code
anyone reads** — the landing prints its ✅ either way. Two branches whose commits ARE on main prove the
delete silently did not happen at least twice. This is the `green_gates_arent_evidence` shape applied to a
cleanup step: the absence of the "deleted" line is the only signal, and nobody was looking for a line that
is absent.

## Why it is worth fixing rather than sweeping

Each orphan keeps an **unlanded commit permanently reachable** on the remote, so it is never GC'd, and a
reader cannot distinguish an abandoned verification attempt from a landing that is genuinely stuck —
`git branch -r` noise is exactly how a stuck landing would hide. It also makes `ci/*` useless as a liveness
signal for an orchestrator watching a landing, which is the use I was putting it to when I found this.

## Fix shape (design, not yet implemented)

1. **Make the cleanup sweep, not guess.** After a successful fast-forward, delete every `origin/ci/*` whose
   tip is an ancestor of `origin/main` (mechanism B's survivors) **and** every `origin/ci/*` older than a
   threshold whose tip is unreachable from main (mechanism A's orphans) — or, more precisely, record the
   attempt branch in a file beside the worktree so a re-run after a rebase deletes its own predecessor. The
   sweep is the shape that makes the NEXT orphan automatic rather than the one that makes this case small
   (CLAUDE.md rule 5).
2. **Delete the silencing.** Drop `2>/dev/null`, read the exit code, and print `⚠ could not delete <branch>:
   <stderr>` on failure. A cleanup that cannot fail loudly is not a cleanup.
3. **Drift test.** A check that fails when `origin/ci/*` contains a branch whose tip is an ancestor of
   `origin/main` — the state that proves mechanism B recurred.

## Not done here

Nothing was deleted: eight of the nine branches are safe to remove (their commits are either on main or are
abandoned attempts), but deleting remote branches is an outward-facing action on the owner's repository and
is not mine to take unasked while a landing is in flight on the ninth.

## ⭐ CONFIRMED LIVE the same afternoon — mechanism A reproduced under observation

The filing above was archaeology over eight surviving branches. **Ninety minutes later the wave's own close
reproduced mechanism A while I watched**, which upgrades this from inference to a measured defect:

- Registrar #8 landed first, moving `origin/main` to `9172f1a74`.
- Battery #82, which had computed its branch name from its pre-rebase HEAD, had already pushed
  **`ci/410280c17f6e`**. It then rebased onto the moved main and landed **`e3902c8f3`** — same commit subject,
  different sha.
- `git merge-base --is-ancestor origin/ci/410280c17f6e origin/main` → **false**. The branch is an orphan, created
  and abandoned inside one landing, exactly as the mechanism predicts.

**And the counter-observation matters just as much:** train 43's own branch `ci/c774def44463` **was deleted
correctly** in the same window. So mechanism B (the silenced delete) is INTERMITTENT, not universal — the delete
works on the ordinary path and the two landed-but-undeleted survivors came from some other condition. Do not
"fix" B by assuming it always fails; reproduce its condition first, which the silencing currently makes
impossible. That is the argument for removing `2>/dev/null` BEFORE attempting the sweep: the diagnostic comes
first, because right now a failing delete leaves no evidence at all.

Net effect measured across one afternoon: one landing wave of nine agents produced **one new permanent orphan**.
