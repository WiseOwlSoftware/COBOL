# PB557

## Mechanism — value-clause-p2
TWO-ARM DISPATCH WITH TWO ARMS MISSING. SR9 names FOUR usages; src/Cobol.Net.Compiler/Binding/DataBinder.cs:2458-2472 screens exactly two of them (`if (entryUsage is Usage.ProgramPointer or Usage.FunctionPointer) { ... if (rawValue is not null) Edition.Error(... "(ISO 13.18.63 SR9)") ... }`). There is no OBJECT-REFERENCE VALUE screen anywhere -- the neighbouring POINTER gate at :2482-2487 checks PICTURE only -- and USAGE MESSAGE-TAG is absent from the grammar, so that arm is vacuous by absence rather than enforced. With no screen, the raw VALUE text survives into the record-struct initializer and the Roslyn backend meets a `string` where the field is a `CobolObject` / `ManagedPointer`, turning a syntax-rule violation into a compiler crash.

### Expected, from the standard
SR9 (13.18.63.3): "The VALUE clause shall not be specified if a USAGE clause with a phrase of FUNCTION-POINTER, MESSAGE-TAG, OBJECT-REFERENCE, or PROGRAM-POINTER is also specified." (cite --check OK) -- all four shall draw a compile-time diagnostic, exactly as PROGRAM-POINTER and FUNCTION-POINTER already do. For the plain-POINTER sibling the licence is different but the outcome is the same: SR9 does not name USAGE POINTER, but 13.18.63.2 Format 1 takes literal-1, and NULL is not a literal -- 8.4.3.10.1: "NULL is a predefined address of class pointer or a predefined content of class message-tag" (cite --check OK), i.e. an identifier under 8.4.3. 13.18.63.4 GR4 additionally settles what a pointer's initial value IS without any VALUE clause: "data items of class message-tag, class object, and class pointer are initialized to null" (cite --check OK). Under no reading may either shape reach the code generator.

```
$ python scripts/spec/cite.py --check 13.18.63.3 "The VALUE clause shall not be specified if a USAGE clause with a phrase of FUNCTION-POINTER, MESSAGE-TAG, OBJECT-REFERENCE, or PROGRAM-POINT..."

```

### Observed
MEASURED at --std 2002 and 2023. The two enforced arms and the two unenforced ones sit in the SAME `if`, so the sweep question is which arm was fixed -- here, the two that had a diagnostic band already. The OBJECT REFERENCE arm fails in two distinct ways depending on the literal (silently discarded for a quoted literal, backend crash for NULL), which is the signature of an unscreened value reaching the emitter rather than of a deliberate leniency.

## Landed 2026-09-20 — wave 41 (E)

RE-PROBED FIRST on this worktree's own build. Two of the note's four measurements still hold exactly:
`01 O USAGE OBJECT REFERENCE VALUE "X".` compiled, linked and RAN CLEAN (rc=0, `OK`) with the literal silently
discarded, and `VALUE NULL` on the same entry failed the whole Roslyn compilation (`CS0029: Cannot implicitly
convert type 'string' to 'CobolNet.Runtime.CobolObject'`). The POINTER sibling reproduced the same CS0029 against
`ManagedPointer`. ⚠ ONE DID NOT: **MESSAGE-TAG is no longer absent from the grammar** — `01 M USAGE MESSAGE-TAG
VALUE "X".` is refused by name with COBOLNET1943 (declined non-support, Annex A.3 item 4), so that arm is
NOT vacuous, either: measured after the fix, that entry draws COBOLNET1943 AND COBOLNET2168 — the decline
says this implementation does not provide the Annex A.3 item 4 facility, SR9 says the standard forbids the
clause on that usage at all, and neither stands in for the other.

FIXED AS A SET, in the shape its neighbour already had. `UsageFamilies.AdmitsNoValueLiteral` sits beside
`UsageFamilies.IsPictureless` in `PicInfo.cs` and is read by ONE screen in `BindEntry`, COBOLNET2168. The screen
covered two of SR9's four usages — exactly the two that already had a diagnostic band. WHICH ARM DID I FIX? Both
missing ones, plus the sibling one level out.

⚠ DETERMINATION (the owner may overturn). USAGE POINTER is a DELIBERATE addition to the set that SR9 does not
name. The licence: §13.18.63.2 format 1 takes literal-1; §8.4.3.10.1 makes NULL "a predefined address of class
pointer or a predefined content of class message-tag" — an identifier under §8.4.3, not a literal — and
§8.3.3.6.2 does not list NULL among the figurative constants; and no syntax rule of §13.18.63.3 types a literal
for a subject of class pointer (SR2 numeric, SR4 alphabetic/alphanumeric/alphanumeric-edited, SR5 national,
SR6/SR7 numeric-edited, SR10 boolean). §13.18.63.4 GR4's closing paragraph makes the prohibition costless: such
an item is null at initial state with no clause written. The reading REJECTED is accepting `VALUE NULL` on a
pointer as a dialect leniency; what it replaced was not an accepted program but a compiler crash.

DRIFT: `tests/Cobol.Net.Tests.Unit/ValueClauseUsageSetDriftTests` re-reads SR9's own sentence out of
`specs/ISO_COBOL.md` on every run — the twin of `PicturelessUsageSetDriftTests`, and for the same reason: a
behavioural probe cannot contradict a wrong set, because dropping an arm moves the screen and every test of the
screen together. Its failure branch was fired once, deliberately (OBJECT REFERENCE removed from the set → red),
then restored.

GOLDENS: `tests/conformance/negative/pb557-value-on-object-reference` (written with a QUOTED literal on purpose
— the NULL spelling pinned a backend crash instead of the silent half a user never sees),
`…/pb557-value-null-on-pointer`, and `tests/conformance/2002/pb557_pointer_class_initial_value_is_null` — without
which the negatives would be a screen with no evidence that what it refuses was unnecessary.

ROW: `SR-13.18.63.3-9` DIVERGES → CONFORMS. CODE: COBOLNET2168.

NOTE-READY LEAD (not filed — ids are central): USAGE MESSAGE-TAG's SR9 arm and USAGE FUNCTION-POINTER's are both

the second because a function-pointer entry needs a prototype the repository work has not landed. Both are
