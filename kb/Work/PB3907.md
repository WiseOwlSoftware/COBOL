# PB3907 — evaluate-condition-name-subject-and-object: EVALUATE with a condition subject and a condition object refused ('invalid use of 88 level in WHEN expression')

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S6) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\evaluate-condition-name-subject-and-object.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\evaluate-condition-name-subject-and-object\`.

## Summary

GnuCOBOL 3.2 refuses an EVALUATE whose selection subject is a condition (condition-1) and whose matching selection
object is a condition (condition-2), a combination Table 15 of the standard permits. With a condition-name as the
object the diagnostic is `invalid use of 88 level in WHEN expression`; with relation conditions on both sides it is
`condition expression found where decimal expression was expected`. The fuzz witnesses hit it inside an ALSO list
(`EVALUATE TRUE ALSO cond-name WHEN TRUE ALSO cond-name`). The same subject with the object TRUE or FALSE compiles.
Class: rejects legal ISO source. A condition-name subject paired with a relation-condition object crashes cobc; that
is the split record `evaluate-condition-name-subject-and-object--condition-name-subject-crash`.

## Expected result (per ISO)

The program is legal. IS-TWO is false (N is 1) as subject and as object, the truth values match, and it prints
`MATCH`. `evcC` and `evcD` print `MATCH` for the same reason.

- §14.9.13.3 7) b) (checked): "Condition-2 or the words TRUE or FALSE appearing as a selection object shall correspond
  to condition-1 or the words TRUE or FALSE in the set of selection subjects."
- §14.9.13.3 10) (checked) and Table 15 (rendered from the printed page, 2023 PDF page 650): the row "Condition" has
  "Y" in the column "Condition" and in the column "TRUE or FALSE".
- §8.8.4.5.3 3) (checked): a condition-name condition is a condition; "The result of the test is true if one of the
  values corresponding to condition-name-1 equals the value of its associated conditional variable."
- §14.9.13.4 3) e) (checked): "Any selection subject specified by condition-1 is assigned a truth value according to
  the rules for evaluating conditional expressions."
- §14.9.13.4 4) a) 3. (checked): "If the selection object is condition-2, the selection subject is either TRUE or
  FALSE. If the truth value of the selection subject and selection object match, the result of the analysis is true."
  Read with 3) e), "either TRUE or FALSE" is the truth value the subject was assigned; Table 15 and syntax rule 7) b)
  admit condition-1 there.

Edition: 2014. The 2009 committee draft that became ISO/IEC 1989:2014 (CD 1.2) has the same syntax rule 7) b) and the
same Table 16 (rendered from its PDF, page 475 of the draft: row "Condition", "Y" under "Condition" and under "TRUE or
FALSE"). The 2002 text (ISO/IEC 1989:2002 as balloted, 2001-12) carries the same syntax rule 7) b).

Edition as recorded by the adjudicator: 2014 (also 2002). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Our compiler (WiseOwl)

WiseOwl COBOL (built from main 6ed90bd1c), `cobol evcA.cob --std 2014 --source-format free -o evcA.dll`, then
`dotnet evcA.dll`: compile exit 0, run exit 0, output `MATCH`. `evcC` and `evcD`: `MATCH`; `evcE`: `NO MATCH`.
WiseOwl refuses the combinations Table 15 marks invalid (a condition subject with a literal or identifier object:
COBOL1634), so its acceptance here is not an under-rejection. On the night witnesses its output was checked by hand
(fz02660: `XOR-TT FAIL`, `XOR-NEST FAIL`, `RES=XFCF`; fz04174: `TRUE-ALSO`).

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/typeck.c`, `evaluate_test`: an object that is a reference to a level-88 item draws the `invalid use of 88
  level in WHEN expression` error whenever the subject is not the word TRUE or FALSE; there is no case for a subject
  that is itself a condition (condition-1), which should compare truth values like the TRUE/FALSE-subject case does.
  Any other condition object falls into the "Regular comparison" (`=` between subject and object), which for two
  relation conditions draws the `condition expression found where decimal expression was expected` error from
  `decimal_expand` (same file).
- `cobc/parser.y`, `evaluate_subject` (the `expr` alternative) and `evaluate_object`: a conditional subject is kept as
  a plain expression; nothing records that it is condition-1, so `evaluate_test` cannot tell it from a value.
