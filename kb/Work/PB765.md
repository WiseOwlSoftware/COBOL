# PB765 — OPEN — the same illegal program, two editions, two different stories

Filed 2026-09-06 by the registrar from the PB704 implementer's report ("New defects", N2).
**⛔ The report's probe does NOT reproduce on main, and re-deriving that is most of this note.**

## ⛔ Premise correction — the report measured the FIXED tree, not main

N2's repro is `scratchpad/PB704/v6.cob` — a SORT whose duplicates phrase reads `WITH DUPLICATES IN FOO` — and it
describes it as *"(now correctly rejected)"*. That parenthesis is load-bearing: **"now" is the PB704 branch**,
where `sortDuplicatesPhrase` was changed to `WITH? DUPLICATES IN? ORDER?`. On main the rule is still
`WITH? DUPLICATES IN? cobolWord?` (`src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4:744-746`), so `FOO` simply
matches `cobolWord`, `FOO` is not a reserved word, and nothing fires at all. Measured, main's build, that exact
file:

```
$ cobol v6.cob --std 85     →  (no output)   exit 0
$ cobol v6.cob --std 2023   →  (no output)   exit 0
```

So the divergence N2 reports is a property of branch `worktree-agent-aad37de314c6cef0b` (train 18) and arrives
on main WITH PB704. Main's own behaviour on `v6.cob` is a different fault — `WITH DUPLICATES IN <any word>` is
accepted at every edition where §14.9.40.2 prints only `[ WITH <u>DUPLICATES</u> IN ORDER ]`, an
**under-rejection that [[PB704]] already owns and closes with the ORDER token**. It is not claimed here.

⚠ *Build provenance.* Building was out of scope for this pass, so the probes ran on the checkout's existing
`src/Cobol.Net.Cli/bin/Debug/net10.0/cobol.dll` (2026-09-06 03:12), three `src/` commits behind `1e7b5085`.
It is confirmed main-like on the subject: `WITH DUPLICATES IN ORDER` reproduces PB704 exactly —
`(24,35): error COBOLNET0901: 'ORDER' is a reserved word in COBOL-2023 …` at 2023, clean at 85.

## The general defect IS real on main — measured with a different edition-gated construct

The mechanism N2 names ("an edition-gated alternative changing the prediction, so the recovery point moves") is a
live property of main; it just needs a construct that main actually gates in the GRAMMAR. `CobolIO.g4:237-240`:

```
    // It must precede genericClause, which would otherwise match the bare word APPLY and then die on COMMIT
    // with an unnamed error. {is2023()}? because the whole commit-and-rollback facility is a COBOL-2023
    // addition (Annex E.3.2 item 2) — below 2023 APPLY and COMMIT are user-defined words …
    | {is2023()}? applyCommitClause
```

Probe (`applyc.cob`, an I-O-CONTROL paragraph whose only fault is `APPLY COMMIT ON 5.`):

```
--std 85    applyc.cob(9,12): error COBOL0001: no viable alternative at input 'APPLY'
            applyc.cob(9,12): error COBOL0001: cannot parse construct near 'APPLY'

--std 2023  applyc.cob(9,28): error COBOL0001: no viable alternative at input '5'
            applyc.cob(9,28): error COBOL0308: unexpected '5'. A data-name is expected here, not a literal.
```

Same file, same fault, both editions reject — and the reader is told two unrelated things. At 2023 the
diagnostic names the offending token, the expected category and a real code; at 85 it names the clause's first
word, twice, with no code beyond the generic one. **The direction is the OPPOSITE of what N2 reports for SORT**
(there 85 is the good arm and 2023 the bad one), which is the point: the quality is not a property of the
edition, it is a property of which alternative the predicate happened to leave in the prediction set.

## The rule — the source is illegal at every edition, so the editions should agree

Mechanically checked (`scripts/spec/cite.py --check`):

- `12.4.6.3.2 "APPLY"` → **OK**: `<u>APPLY</u> <u>COMMIT</u> ON [ [ file-name-1 ] [ identifier-1 ] ]…` — a
  literal is admissible in neither operand slot, so `ON 5` is illegal at COBOL-2023.
- `12.4.6.3.1 "The APPLY COMMIT clause specifies which files and data-items are to be subject to COMMIT and
  ROLLBACK"` → **OK** — the facility is the 2023 addition, so at COBOL-85 §12.4.6 prints no such clause at all
  and the whole entry is illegal there.
- `5.2.3 "Optional words are reserved words or context-sensitive words"` → **OK** — the rule N2 cites for the
  SORT instance: a general format admits its own keywords and optional words and nothing else, so `IN FOO` is
  illegal at every edition, exactly as `ON 5` is.

§4.2.16 conformance says nothing about the *wording* of a diagnostic, so this is a product-quality defect, not a
conformance one — `process_only`, MINOR. It is filed because the compiler is sold as four per-edition compilers
(`docs/VERSION_TEST_MATRIX_DESIGN.md`) and a user migrating a program between `--std` values is exactly the
person who sees both answers.

## Fix shape

Not the grammar. The recovery point is chosen by
`src/Cobol.Net.Frontend/Parsing/CobolErrorStrategy.cs` and reported by `CobolErrorListener.cs`; the divergence is
that a `{isNNNN()}?` predicate removes an alternative from prediction, so ANTLR's `NoViableAlt` is raised against
a different (usually earlier, less specific) decision. Two candidate shapes, in the order they should be tried:

1. **Report from the construct, not from the failed decision.** Where a predicate excluded an alternative that
   WOULD have matched the token run, the listener already has the material to say so — the same information
   `CobolErrorListener` uses today to re-code a reservation-gated token (`DESIGN-frontend-grammar.md:401-405`,
   the `CobolLexer.IsReservationGated` path). Extend that mechanism to *edition-gated alternatives*: recognise
   the construct, then emit the edition diagnostic ("APPLY COMMIT is a COBOL-2023 clause") instead of a bare
   COBOL0001 at the clause's first word. That converts the 85 arm into a BETTER answer than the 2023 one, not
   merely an equal one.
2. **Failing that, a per-edition negative golden pair** asserting that the two editions name the same token.
   `feedback_green_gates_arent_evidence`: make it fail once against today's `applyc.cob` before trusting it.

⛔ Whichever is chosen, the sweep is small and bounded — **six edition predicates in grammar code on main**,
measured (`grep -rn "}?" --include=*.g4` over the whole grammar, comment lines dropped, then tallied by
predicate: `{is2023()}?` ×3, `{is2002()}?` ×3, and no `{is2014()}?` / `{isAtLeast…}?` at all):

| site | predicate | alternative |
|---|---|---|
| `CobolParserCore.g4:786` | `{is2023()}?` | `inlineMethodInvocationStatement` |
| `CobolControlFlow.g4:49` | `{is2023()}?` | `LOCATION` |
| `CobolData.g4:206` | `{is2002()}?` | `levelNumber dataName? parameterDescriptionBody DOT` |
| `CobolData.g4:309` | `{is2002()}?` | `validationClause` (declined A.4.14) |
| `CobolData.g4:672` | `{is2002()}?` | `validateValidPhrase` |
| `CobolIO.g4:240` | `{is2023()}?` | `applyCommitClause` — **the probe above** |

⚠ Do not sweep on the raw grep: `grep -rn "{is20NN()}?" --include=*.g4` returns **18 lines, and 12 of them are
inside COMMENTS** (`CobolData.g4:392/:494/:670`, `CobolDeclined.g4:79/:81`, `CobolExpressions.g4:70`,
`CobolIO.g4:74/:237`, `CobolLexer.g4:205/:576`, `CobolOO.g4:6/:196` — prose describing a gate that lives
elsewhere or was removed). Each of the six real sites is a place where the same illegal source gets two
stories. `feedback_scan_all_similar`.

## ⛔ Not [[PB657]], and the distinction is the fix

[[PB657]] has the same symptom family — a bare `COBOL0001: no viable alternative` where a named diagnostic
belongs, varying by edition — and a *different mechanism*: there the word is kept out of `cobolWord` by the §8.9
reservation gate, so a REFERENCE has no parse and the error lands at the reference instead of at the declaration
that already earned COBOLNET0901. Its fix is scoped to the reservation gate and explicitly declines to touch
prediction ("Do not admit the word to `cobolWord` at the reserving edition to 'fix' this"). This note's subject
is the `{isNNNN()}?` predicate itself, at eleven sites that have nothing to do with §8.9. They should be fixed
together in `CobolErrorStrategy`/`CobolErrorListener` — one mechanism, two callers
(`feedback_one_rule_one_place`) — but PB657 does not own this and closing it would not close this.
