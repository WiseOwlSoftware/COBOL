# PB825 — OPEN — the item's value and the item's DISPLAY image are two different numbers

Filed 2026-09-09 by the registrar (third pass) from the **PB452 implementer's report** §13 item (1) —
`scratchpad/reports/PB452-report.md`. **Every fact below is re-measured on this worktree's own
`dotnet build CobolSharp.sln -c Debug` (exit 0) at `094739b3`**, and the re-measurement corrects the report's
rule attribution and materially NARROWS the population — see "Premise corrections", which is the substantive
half of this note.

## Repro — measured, `--std 2023`

`scratchpad/registrar3/probe/p1_comp5_display.cob` (PROGRAM-ID `PBR825`):

```cobol
       01 B PIC S9(4) COMP-5.
       01 C PIC S9(2) COMP-5.
       01 D PIC 9(4)  COMP-5.
       01 E PIC S9(4) COMP.
       01 W PIC S9(9) SIGN LEADING SEPARATE.
```

```
B-DISPLAY=[-2768]        <- MOVE -32768 TO B, then DISPLAY B          ⛔ WRONG
B-VIA-W  =[-000032768]   <- MOVE B TO W,     then DISPLAY W              the value IS right
B-POS    =[2767]         <- MOVE  32767 TO B                           ⛔ WRONG
B-POS-W  =[+000032767]
C-DISPLAY=[00]           <- MOVE 100 TO C   (1-byte container, PIC 2)  ⛔ WRONG
C-VIA-W  =[+000000100]
D-DISPLAY=[5535]         <- MOVE 65535 TO D (unsigned 2-byte)          ⛔ WRONG
D-VIA-W  =[+000065535]
E-COMP   =[1234]         <- USAGE COMP: correct, and correct FOR A DIFFERENT REASON (below)
```

The same value reached through the intrinsic rather than a literal prints the same way
(`p1_comp5_highest.cob`: `MOVE FUNCTION HIGHEST-ALGEBRAIC(B) TO B` → `HI-DISPLAY=[2767]`,
`HI-VIA-W=[+000032767]`; `LOWEST-ALGEBRAIC` → `LO-DISPLAY=[-2768]`, `LO-VIA-W=[-000032768]`), so the fold and
the store agree with each other and only the render dissents.

## Expected, from the standard

**§14.9.11.4 GR1 — the DISPLAY statement transfers the CONTENT of the operand.** The content of `B` after
`MOVE -32768 TO B` is −32768; the compiler itself proves it is −32768 by moving it to a wider item. Nothing in
§14.9.11.4 licenses re-deriving the content from the PICTURE.

```
$ python scripts/spec/cite.py --check 14.9.11.4 "The DISPLAY statement causes the content of each operand to be transferred to the device in the order listed"
  OK  §14.9.11.4 1)  (General rules)
```

**Why the ISO usages are the discriminator, and USAGE COMP is NOT a sibling.** The truncation the renderer
performs is CORRECT for `USAGE BINARY` / `COMPUTATIONAL`, because for those the standard makes the PICTURE the
range:

```
$ python scripts/spec/cite.py --check 13.18.60.4 "Sufficient computer storage shall be allocated by the implementor to contain the maximum range of values implied by the associated decimal picture character-string"
  OK  §13.18.60.4 4)  (General rules)
```

For the binary-char / binary-short / binary-long / binary-double family the range is the CONTAINER's, and the
compiler gets those right:

```
$ python scripts/spec/cite.py --check 13.18.60.4 "The usages binary-char, binary-short, binary-long, and binary-double define integer numeric data items that are held in a binary format suitable for the machine on which the runtime module is to run"
  OK  §13.18.60.4 12)  (General rules)
```

`p1_binshort.cob` (PROGRAM-ID `PBR825C`) and `p1_siblings.cob` (`PBR825D`), measured:

```
S-DISPLAY=[-32768]              01 S  USAGE BINARY-SHORT           ✅ correct
U-DISPLAY=[65535]               01 U  USAGE BINARY-SHORT UNSIGNED  ✅ correct
CHR-DISPLAY=[-128]              01 CHR USAGE BINARY-CHAR           ✅ correct
BL-DISPLAY=[-2147483648]        01 BL USAGE BINARY-LONG            ✅ correct
BD-DISPLAY=[18446744073709551615]  01 BD USAGE BINARY-DOUBLE UNSIGNED (20 digit positions) ✅ correct
```

They are correct because those usages admit no PICTURE, so `Digits` is synthesized from the container and the
two models coincide. **COMP-5 is the only usage that can present a PICTURE alongside container-range
semantics, and it is therefore the whole reachable population.**

## Premise corrections — three, and the third changes the shape of the finding

1. ⛔ **The report's rule citation is a PHANTOM.** It offers
   `cite.py --check 13.18.60.4 "The amount of storage occupied"` as the rule that "locates the container rule".
   Re-run on this tree:

   ```
   $ python scripts/spec/cite.py --check 13.18.60.4 "The amount of storage occupied"
     FAIL: §13.18.60.4 exists but does NOT contain 'The amount of storage occupied'
   $ python scripts/spec/cite.py --find "The amount of storage occupied"
     NO CLAUSE contains 'The amount of storage occupied' — the citation names text the standard does not have
   ```

   The container rule the finding needs is **GR12**, quoted above, and GR12 names four usages by name.
2. ⛔ **The report cites "§14.9.13.4 (DISPLAY sends the *content* of the operand)". §14.9.13 is the EVALUATE
   statement.** The DISPLAY statement is **§14.9.11**; its general rules are §14.9.11.4 and GR1 is the sentence
   the finding wants. A fixer grepping `14.9.13.4` for a DISPLAY rule finds EVALUATE.
3. ⛔ **GR12 does not govern COMP-5, because COMP-5 is not in the standard at all.**
   `grep -c "COMP-5\|COMPUTATIONAL-5" specs/ISO_COBOL.md` → **0**. It is a dialect word this compiler admits by
   the follow-GnuCOBOL latitude decision, and the compiler's own model says so:
   `PicInfo.cs:232` renders it as `"COMPUTATIONAL-5"` with the comment *"no §13.18.60.2 spelling — the dialect
   word IS the name"*. So the ISO rule that is BROKEN here is §14.9.11.4 GR1 (the content is not what is
   transferred); §13.18.60.4 GR4 and GR12 are the two rules that establish which population may legitimately be
   truncated to its PICTURE and which may not, and the dialect places COMP-5 in the GR12 half.

## The mechanism — one rule, three sites, and the render is the site that dissents

`NumericTruncation.BinaryCapacity` is THE capacity discipline: an item so marked owns its container's whole
two's-complement range, not the range its PICTURE implies. It is honoured in two of the three places that need
it and dropped in the third.

| site | file | reads | verdict |
|---|---|---|---|
| store / MOVE | the record-struct field is the native container | the container | ✅ |
| intrinsic fold | `IntrinsicBinder.cs:2493-2506` — `int bits = 8 * pic.StorageWidth;   // container width (§13.18.60.4 GR12) — the item owns the full range` | the container | ✅ |
| **DISPLAY render** | `CobolNum.FormatUnsignedDisplay` (`src/Cobol.Net.Runtime/Values/Numeric/CobolNum.cs:676`) and `FormatUnsignedDisplayU` (`:440`) | **`receiver.Digits`** | ⛔ |

```csharp
public static string FormatUnsignedDisplay(Int128 value, int digits)
{
    if (digits <= 0) return "";
    Int128 v = value % Pow10Wide(digits);        // ⛔ the truncation
    ...
}
```

`digits` arrives as `NumProfile.Digits`, which is the PICTURE's digit count. `NumProfile` already carries
everything the correct answer needs — `Truncation` and `StorageLength` are fields on the same record — so this
is not a missing-information problem; it is the conflation the type's own doc comment forbids:

> `NumProfile.cs:125` — *"**Three orthogonal axes, and conflating any two is a defect:** `Truncation` is the …"*

⛔ **It is a THREE-arm dispatch and every arm is wrong, which is the thing a fixer must be told before touching
it** (`feedback_two_arm_dispatch` — the most reproducible defect shape in this tree):

| arm | entry | measured witness |
|---|---|---|
| signed | `FormatDisplay(Int128, …)` → `FormatDisplaySigned` (`:647`) → `FormatUnsignedDisplay(unscaled, receiver.Digits)` | `B-DISPLAY=[-2768]` |
| unsigned | `FormatDisplay(Int128, …)` → `FormatUnsignedDisplay(unscaled, receiver.Digits)` | `D-DISPLAY=[5535]` |
| **unsigned wide** | `FormatDisplayU(UInt128, …)` (`:435`) → `FormatUnsignedDisplayU(value, receiver.Digits)` (`:440`) | `X-HI=[63374607431768211455]` |

The third arm is the loudest and the easiest to miss, because it is a *distinctly named* lane rather than an
overload (the CS0121 reason is written at `:428-434`). `p1_wide.cob` (PROGRAM-ID `PBR825E`),
`01 X PIC 9(20) COMP-5.` — a 16-byte container:

```
X-HI      =[63374607431768211455]                 <- DISPLAY of HIGHEST-ALGEBRAIC(X)   ⛔ the low 20 digits
X-HI-VIA-Y=[920938463463374607431768211455]       <- the same value through PIC 9(30)     2^128-1, correct
```

⛔ **And the defect is WRITTEN INTO that arm's own doc comment**, naming the exact population it breaks:

> `:428` — *"The DISPLAY image of an unsigned wide item's value … (a **16-byte unsigned COMP-5 item** is always
> unsigned, so the image is the bare magnitude run **at the picture's digit count**)."*

That sentence is a correct description of what the code does and a statement of the bug. It is why no reviewer
caught it: it reads as a specification (`feedback_a_dead_lookup_is_also_unverified` — a rule nothing
contradicted).

## Sibling sweep — measured, not deduced

* **`FormatDisplay` is also the group-image codec's numeric leaf encoder** (`CobolNum.Image.cs:36`,
  `GroupImageCodec.cs:18`) and the CALL-ABI's formal-image bridge (`CallAbi.cs:183,251,314`). A group MOVE
  across a COMP-5 leaf was probed (`p1_siblings.cob`: `01 G. 05 GA PIC X(2). 05 GB PIC S9(4) COMP-5.` →
  `MOVE G TO H`) and **the value survives** — `HB-VIA-W=[-000000000000032768]` — because a whole-group MOVE of
  two same-shaped records is a native field copy, not an image round-trip. So the image path is a POTENTIAL
  second surface that this probe did not reach; the reference-modified / RENAMES-span view over a COMP-5 item is
  the shape that would reach it, and it is NOT measured here.
* **`ParseDisplay` is the declared inverse** (`CobolNum.cs:731` — *"inverse of `FormatDisplay`"*). If the image
  ever becomes the storage form for a COMP-5 leaf, the inverse of a truncating format is a lossy round trip.
* **`USAGE COMP` / `BINARY` are NOT siblings** — measured correct, and correct by §13.18.60.4 GR4.
* **The BINARY-\* family is NOT a sibling** — measured correct at all four widths and both signednesses.

## The row, and why it is NOT re-verdicted here

`GR-14.9.11.4-1` reads **CONFORMS / OK** in the traceability inventory while the rule is measurably violated for
the BinaryCapacity population. This is the PB258 shape (`feedback_green_test_can_hold_a_gap_open`): the verdict
was earned on the DISPLAY/BINARY population, which is genuinely conforming, and it has never been contradicted
because nothing asked it about a COMP-5 item. **The registrar claims the row and does not flip it** — a verdict
change is a golden-round act that must land with its evidence, and flipping on a read is the cheap claim PB258
exists to refuse. The fixer flips it, with a golden, in the commit that lands the fix.

## What the fix has to be

`FormatDisplay`/`FormatUnsignedDisplay` must take the digit count from the item's CAPACITY when
`Truncation == NumericTruncation.BinaryCapacity` — the same `8 * StorageWidth` two's-complement bound
`IntrinsicBinder` already computes — and from `Digits` otherwise. ⛔ **Not by adding a `Usage.Comp5` test at the
render**: that is the hand-list `IntrinsicBinder.cs:2494-2496` was explicitly refactored AWAY from
(*"this branch previously carried its own usage list (Comp5/BinaryChar/BinaryShort/BinaryLong/BinaryDouble), the
same rule written twice"*, kb/Work R10). The capacity-to-digits function belongs beside the capacity table, read
by the fold AND the render, with a drift test asserting the two agree for every `BinaryCapacity` profile — the
shape `AlgebraicFoldContainerAgreementTests` already established for the fold alone.

A golden must pin **all three arms** (signed, unsigned, and the 16-byte unsigned wide lane —
`01 X PIC 9(20) COMP-5.`), **both extremes** (the container MINIMUM, which is the case a magnitude-only fix
misses), and **a `USAGE COMP` control** proving the PICTURE truncation is still applied where §13.18.60.4 GR4
requires it. The `FormatDisplayU` doc comment quoted above must be rewritten in the same change set: it
currently documents the defect as the contract.
