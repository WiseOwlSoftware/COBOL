# PB5468 - the shard-spread report measured a subset leg whose spread no regeneration changes

**Sites:** `scripts/shard_weights.py` (`trx_assemblies`, `Shard`, `shard_walls`, `spreads`, `verdict`, `dealt_assemblies`,
`report`, the self-test); `.github/workflows/nightly.yml` (`shard-spread` comment);
`docs/rearchitecture/DESIGN-test-build-ci.md` (`shard-spread` row); `docs/DOC_INDEX.md` (`scripts/shard_weights.py` row).

**The symptom.** The nightly of 2026-11-13 went red on `shard-spread`: 1.64x OVER, run 43430492045, Windows, slowest
shard 4 at 162 s against a mean of 98 s over 7 shards. Its remedy, per the report, is `shard_weights.py generate`.

**The measurement** (the eight runs the report read, each downloaded and every trx read: per shard, the sum of the trx
`<Times>` walls and the test assemblies its trx define):

| run | Linux (all 3 assemblies) | Windows: assemblies | Windows spread |
|---|---|---|---|
| 43437574066 | 1.38x | (leg skipped) | - |
| 43432533540 | 1.11x | Char+Conf+Unit | 1.40x |
| 43430915941 | 1.21x | Char+Conf+Unit | 1.24x |
| 43430492045 | 1.33x | **Unit only** | **1.65x** (walls 78, 81, 71, 162, 79, 101, 117 s) |
| 43428906689 | 1.43x | (leg skipped) | - |
| 43417801455 | 1.48x | Conf+Unit | 1.25x |
| 43417437765 | 1.36x | (leg skipped) | - |
| 43410076120 | 1.45x | (leg skipped) | - |

In run 43430492045 the Windows jobs' `Characterization` and `Conformance` steps were skipped (the store ref held their
passes at the merged tree's key, PB5235) and only `Unit, this shard` ran (shard 4: 13:08:23 to 13:11:07). Job setup is
not in the measure (the trx `<Times>` cover the `dotnet test` run alone): shard 4's job spent 3 m 18 s on checkout,
toolchain, packages and build before its 164 s of tests.

**The cause.** `TestWeights.Deal` (tests/_shared/GateLegs.cs) deals every class the weights file names, of every
assembly, in ONE longest-first pass, so it balances each shard's SUM over the three assemblies, not each assembly's share.
Simulating the deal over the committed weights (2026-11-04) gives 543 s on each of the 7 Windows shards in total, but a
Unit share of 104.8, 75.5, 95.1, 146.8, 193.9, 208.3 and 145.9 s: 1.50x with every weight exact. The full runs show the
same unevenness inside Unit (Unit-only spreads 1.26x to 1.46x in 43432533540, 43430915941 and 43417801455) while their
totals sit at 1.24x to 1.40x. Since PB5235 a Windows leg runs only the assemblies with no published pass, so a Unit-only
leg measures the deal's design plus run-to-run noise (shard 4's Unit share took 98 to 107 s in the other runs and 162 s
in this one). Regenerating the weights cannot change it, so the red asked for a remedy that does not exist. The cause is
(b) of the brief: since PB5235 the report measured a population the deal does not balance.

**The fix.** The report measures a spread only over the population the weights deal. Each shard now carries the test
assemblies of its trx's definitions (`trx_assemblies`, keyed by `codeBase` exactly as `generate` keys them); an OS of a
run whose shards together ran fewer than every assembly of the weights file (`dealt_assemblies`) is PARTIAL, left out
and named in the verdict line. A weights file that names an assembly no shard of the window ran is UNMEASURED (exit 2),
because the Linux leg accepts no record and runs every target whenever the matrix runs (scripts/ci_plan.py), so such an
assembly no longer exists and the file wants regenerating; without that arm every run would read as partial and the
report would go blind. An unreadable or empty weights file is UNMEASURED too. The threshold is unchanged and nothing is
muted.

**Proof.** The self-test replays run 43430492045's walls and assemblies: over the three dealt assemblies it is 1.33x
WITHIN (Linux decides, Windows named as partial); over a deal of Unit alone the same Windows shards are 1.65x OVER. With
the partial branch removed (a mutation of `spreads`) the self-test fails on both partial arms.

**Not changed, and why.** Whether the deal itself should balance each assembly is a separate design question: a Windows
subset leg today ends well before the Linux shards (Windows shard 4's job ended at 13:11:12, Linux shard 2's at 13:15:42
in the same run), so its imbalance does not lengthen the merge group. If a subset Windows leg ever becomes the critical
path, the remedy is a deal over the assemblies the plan runs (the leg's `<leg>_targets`), not a regeneration.
Separately, Linux's full-population spread has risen to 1.38x to 1.48x with shard 2 the slowest in every run, which is the
committed weights (2026-11-04) aging; it is WITHIN and the report will say OVER when it crosses.
