Filed 2026-09-22 by **REGISTRAR #11** from wave 46 group J's leads 2 and 3 (PB716 implementer report; lander leads
J2 and J3 — one root: the "historical superset" postfix FOR phrase). **Re-run on this registrar's own build of
main `6871b6e10`** (0/0).

## Reproduced

- `reg11/j2.cob`: `SPECIAL-NAMES. ALPHABET A2 IS NATIVE FOR NATIONAL.` → compiles, runs (`12`), no diagnostic at
  `--std 2023`. Under-reject, silent.
- `reg11/j3.cob`: `CLASS DG IS "0" THRU "9" FOR ALPHANUMERIC.` → **`j3.cob(6,37): error COBOL0001: unexpected 'FOR'`**.
  Correctly refused (the printed position is between class-name-1 and IS), but through the parser's generic error,
  not a named diagnostic that says where the phrase belongs.

## Rule — the printed positions (transcription; the fixer renders the page before relying on it)

`specs/ISO_COBOL.md` §12.3.7.2 General format: the alphanumeric ALPHABET arm is
`ALPHABET alphabet-name-1 [ FOR ALPHANUMERIC ] IS { NATIVE | STANDARD-1 | STANDARD-2 | code-name-1 | literal-phrase … }`
and the CLASS clause is `CLASS class-name-1 [ FOR { ALPHANUMERIC | NATIONAL } ] IS …`. The FOR phrase follows the
name, never the definition. (The PB716 train-47 lander confirmed the CLASS position on the diagram while fixing
`GrammarBatch1Tests.Class_ForAlphanumeric_ParsesSuccessfully`.)

## What the fixer owes

One decision for both clauses (and SYMBOLIC CHARACTERS, the third FOR-bearing entry — measure it): either the postfix
form is a vendor extension that some dialect owns — then it is accepted ONLY under that dialect / `--permissive`
with a warning and refused at strict with a NAMED code — or it is not, and both clauses refuse it with the same
named diagnostic ("the FOR phrase follows alphabet-name-1 / class-name-1 — ISO §12.3.7.2"). Decide by CLAUDE.md rule 1's
precedence (GnuCOBOL, else IBM / Micro Focus) — latitude only, never a non-ISO extension at strict. FMT-12.3.7.2 is PARTIAL and claimed by PB829 (half) for
other arms; this note co-claims it for the FOR positions.

## Landed

Wave 51 group F (2026-09-22). **Re-probed first on the worktree's own build of `5963d9ca0`**: `reg11/j2.cob`
compiled clean and ran (`12`); `reg11/j3.cob` drew `COBOL0001: unexpected 'FOR'`; the third FOR-bearing clause,
measured as the note asked, `SYMBOLIC CHARACTERS SA IS 66 FOR NATIONAL` also drew `COBOL0001: unexpected 'FOR'`.

**Decision (CLAUDE.md rule 1's precedence).** No edition prints a trailing FOR phrase (§12.3.7.2); GnuCOBOL's grammar
takes the FOR target only between the name and IS, and IBM Enterprise COBOL's ALPHABET clause has no FOR phrase —
surveyed from the published syntax, not measured (no `cobc` on this host). So the postfix is owned by no dialect and
is refused at EVERY edition and strictness, with one named code for all three clauses.

**Fix.** The grammar's shared `specialNamesForPhrase` stays the ONE printed-position rule; a new error production
`misplacedSpecialNamesForPhrase` (a distinct rule, so no clause's accessor can return the misplaced phrase by
mistake) sits at the end of the ALPHABET, CLASS and SYMBOLIC CHARACTERS clauses, and ONE visitor,
`ClosedFormatPass.VisitMisplacedSpecialNamesForPhrase`, refuses it: **COBOLNET2315**. The binders read it only to
recover the intended class (`DataBinder.ForPhraseIsNational`). COBOLNET0898's "the FOR phrase may be written once"
arm is gone (the doubled spelling is now the misplaced one). Three `ConfigPdEditionTests` sources that used the
trailing ALPHABET spelling now write the printed one — they test the FOR phrase's 2002 gate, not its position.

Evidence: `negative/pb977-special-names-for-trailing` (reject-at 85 2002 2014 2023) and
`ClassClauseForPhraseTests.TrailingForPhrase_IsRefusedByName` (ALPHABET at 2023 and 85, CLASS with and without IN
and without the optional FOR, SYMBOLIC CHARACTERS). FMT-12.3.7.2 re-verdicted PARTIAL with the new witnesses.
