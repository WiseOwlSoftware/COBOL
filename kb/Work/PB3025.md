# PB3025 — one file per DEVLOG entry, so two queued landings never touch the same file

**Owner decision 2026-10-11 ~11:36 PDT (kb/Work PB3015 Q2): "Yes, one file per entry (Recommended)"** — `DEVLOG/NNNN-slug.md`
per landing; a script renders the descending narrative; a CI check refuses a landing with no entry file; no two landings
touch the same file. Rule 6 (CLAUDE.md) is unchanged in substance: one entry per landing on main, newest first, the only
history. Why: with a merge queue, two queued pull requests that both insert at the top of one `DEVLOG.md` collide and the
second is bounced; the work register solved the same problem with one file per note.

**Design:** `DESIGN-test-build-ci.md` §3.17.4.

## What changes
1. `DEVLOG/` directory; one file per entry, `NNNN-<slug>.md` (`NNNN` zero-padded to the current width, the slug from the
   title); the file's first line is the header exactly as today: `## Entry NNNN — YYYY-MM-DD HH:MM TZ — Title`; the body
   follows unchanged. Line endings: LF, like every tracked text file (PB3029, owner 2026-10-11: one line-ending format);
   the migration keeps each entry's content and normalizes its line endings to LF; `DEVLOG.md -text` leaves
   `.gitattributes` with the file.
2. `scripts/devlog.py`: `render [--since NNNN] [--out <file>]` (the descending view; `DEVLOG.rendered.md` gitignored);
   `stamp <branch>` (allocates `NNNN` through `alloc.py devlog`, renames the branch's `DEVLOG/pending-<slug>.md`,
   completes the header's number and stamp, one commit — called by `enqueue.py` so number order is enqueue order and
   therefore landing order; operator review item 2); `check [--base origin/main]` (exactly one NEW stamped entry file
   in the change, header well-formed, number not already on `main`, stamp parseable, no `pending-` file; the content
   of `landing_devlog.py` moves here and that script is deleted); `next` (the highest number in `DEVLOG/`, the
   allocator's floor); `--self-test` with planted trees for every arm.
3. The implementer writes `DEVLOG/pending-<slug>.md` with its entry's title and body and NO number (the
   `implementer-brief` and `dispatch-spec-implementer.md` say so; the lander's L1 "one entry per train" is gone with
   PB3023); `plan_wave.py` allocates no DEVLOG number any more (the stamp at enqueue does). The attended session's own
   branch follows the same shape.
4. **One-time migration** (`scripts/devlog_migrate.py`, run once in this landing, then deleted or kept as a self-tested
   tool with no further use — rule 4 says deleted): split `DEVLOG.md` (1,976 `## Entry` headers, 7.1 MB, CRLF,
   unnormalized) into the files byte-faithfully; prove it by rendering and comparing bytes to the original before
   deleting `DEVLOG.md` and `scripts/prepend-devlog.py`.
5. Every reader of `DEVLOG.md` moves to `devlog.py`: `session-probe.ps1`, `gen_ledger.py` / `ledger_state.py` (the entry
   number on the ledger), the `devlog` memory and `brent-tools:devlog` skill text, `land-a-fix`, `kb-sync`, the DEVLOG
   drift tests (`DevlogDriftTests` or their current name), `docs/DOC_INDEX.md` (the `DEVLOG.md` row becomes `DEVLOG/`),
   CLAUDE.md rule 6 (the shape, not the rule), MANDATORY-PRACTICES L1/I-rules that say "the TOP of DEVLOG.md".
6. CI's `audits` job runs `devlog.py check` on `pull_request` and `merge_group`.

**Not blocked.** Lands before PB3023 (which calls `devlog.py check`).
