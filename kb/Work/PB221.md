# PB221

The cluster-B review fleet's real catch, 2026-08-31 — and the only MAJOR in the cluster, because half of it is a
WRONG ANSWER rather than a missing diagnostic.

`ReferenceResolver.Probe` is `ResolveImpl(dref, report: false)`. Its doc comment has always read: "a probe is a
TYPE-DISCRIMINATING sniff **whose Place is discarded after reading its Item**, so in probe mode the resolver
must be SIDE-EFFECT-FREE: no diagnostics, no OO property temp/op registration, and no D18 subscript
materialization". Everything `_probing` suppresses is therefore correct — **provided the premise holds**. It
did not, at four call sites, which passed the probe's `Place` straight into the bound tree:

  * `CallBinder` — the `BY CONTENT` arm (`args.Add(new BoundCallArg(Content, cp, null))`)
  * `OoBinder` — the INVOKE receiver, and the SET object-reference sender
  * `PtrBinder` — `TryBindSetUpDown`'s first target

**MEASURED before the fix** (`--std 2023`, strict, `01 XE PIC X(4) VALUE "0002"`, `05 E PIC X OCCURS 3`):

    CALL "SUB7A" USING BY CONTENT E(XE).   -> compiles CLEAN (rc 0)
    MOVE E(XE) TO R.                       -> error COBOLNET0844 (rc 70)

One rule, one reference, two verdicts — and the sharper form needs only ONE statement, because CallBinder's
`BY REFERENCE` arm commits through `ResolveReceiving` (screened) while its `BY CONTENT` arm probed:
`CALL "S" USING BY REFERENCE E(XE) BY CONTENT E(XE)` diagnosed the first operand and not the second.

**AND THE OTHER HALF IS A WRONG ANSWER, not an under-rejection.** `MaterializeViaFragment` short-circuits to the
literal string `"1"` under `_probing` (R30 purity — a function-bearing segment would bind and later ACTIVATE
twice). At the four committing sites that string became the emitted occurrence, so
`CALL "S" USING BY CONTENT E(FUNCTION INTEGER(2))` passed occurrence **1**. That half predates this wave — it
has been live since [[PB157]] landed the flag on 2026-08-29, under a landing note asserting the opposite ("Every
Probe caller is pure now") — so it is registered here rather than attributed to the wave.

## ⛔ THE FIX IS THE RETURN TYPE, because a comment could not hold the invariant

`Probe` now returns a `ProbeResult` — `(DataItem Item, PicCategory? OperandCategory)` — and NOT a `Place`. The
compiler then found all four leaks itself: five compile errors, each at a site that had committed the sniff.
The `OperandCategory` member is the one thing a caller legitimately wanted a Place for (§8.4.3.3.4 GR6 for a
ref-modified reference via `RefModPlace.Category`, else `DataItem.OperandPic`, the D20 one reader), so the
callers lost nothing.

The four sites now PROBE to discriminate and `Resolve` to commit — the pattern `SetBinder.BindSetLocale`
already used one file away. ⚠ A naive Probe→Resolve swap would have been wrong: each site has a legal
non-data-item alternative on the null arm (CALL's arithmetic-expression arm, INVOKE's class-name receiver, SET's
EXCEPTION-OBJECT / class-name sender, SET UP/DOWN's index path) that the R30 undefined-name diagnostic would
have broken. The two-step preserves both.

**A FIFTH SITE WAS CHECKED FOR AND DOES NOT EXIST.** All 13 `Refs.Probe` call sites were read: the other nine
(ArithmeticBinder ×3, ConditionBinder ×2, SetBinder ×4) read only `.Item`/`.Category` and discard the result, as
the contract says. `ConditionBinder`'s boolean-operand predicate looked like a fifth because it pattern-matched
`RefModPlace`; it now reads `ProbeResult.OperandCategory`, which is the same GR6 answer through the one reader.

**MEASURED after:** `CALL … BY CONTENT E(XE)` and `MOVE E(XE)` both draw exactly one COBOLNET0844;
`CALL … BY CONTENT E(FUNCTION INTEGER(2))` compiles through the D18 materializer in COMMIT mode, so the §15.4
temp is registered once and the occurrence is computed rather than pinned to 1.

**PINNED BY:** `ArithmeticOperandClassTests.ProbedCallByContentOperand_IsScreenedLikeEveryOtherReference` (which
asserts the CALL form and the MOVE form reach the same verdict) and the negative fixture
`pb221-call-content-probed-subscript` at all four editions. The durable guard is the TYPE: a future site that
commits a probe's result is a compile error, not a review finding.
