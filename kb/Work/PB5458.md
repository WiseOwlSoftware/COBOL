# PB5458 - `toolchain.py latest` learns the newest git-linux from the runner-images readme, which lags the image GitHub deploys, so the nightly `images` job goes red on a version `bump` cannot see

**Sites:** `scripts/toolchain.py` (`image_readme` near l.151, `_image_git` near l.159), `toolchain.env`

**Facts measured by the Mythos session, 2026-11-12:**
- Nightly run 43270832950 (2026-11-12T17:34Z, 4792ae4c9c), job `images (does each runner image carry the git toolchain.env names for it?) (ubuntu-26.04)`: `MISMATCH git-linux 2.56.1 — toolchain.env names 2.56.0` and `=== TOOLCHAIN: RED — image: git-linux 2.56.1 (toolchain.env 2.56.0) ...`.
- `python scripts/toolchain.py latest` on main b8cb5f6d51 at 15:20 PST the same day: `LATEST   git-linux 2.56.0`.

**Reported by the toolchain worker (report `E:\COBOL-coord\scratch\reports\toolchain-20261112-report.md`; a claim until the fixer re-reads the code):** `latest` reads the git version from the runner-images readme on `main` (`scripts/toolchain.py`: `image_readme` near l.151, `_image_git` near l.159). The readme still listed image 20261101.186.1 with Git 2.56.0 while the failing run used image 20261111.196.1, whose `/usr/bin/git` is 2.56.1. `bump` therefore left git-linux at 2.56.0.

**Harm:** the `images` job is red for as long as the readme lags the deployed image, with no action that clears it, so the nightly's first line is red for a reason nobody can act on, which hides a real red beside it.

**Shape (the fixer decides from the code):** the newest git-linux must come from the same source the check reads (the git the image in use carries), or the job must tell "image newer than its published readme" from "manifest behind" and not fail the first. Sibling to sweep: every other tool whose `latest` source is a document about the image, not the image.

**related:** PB5207, PB5235. **cluster:** none.
