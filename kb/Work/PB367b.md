# PB367b — the residual of the USE-dispatch rows

**Why this note exists.** `kb/Work/PB367` claimed six rows because ONE defect — a handler end derived from
paragraph shape — was a listed limit on all six. That defect is landed and `GR-14.9.49.4-13` closed with it. The
other five stay `PARTIAL` on limits that were never PB367's mechanism, and with PB367 landed nothing live owned
them (`DefectiveRowCoverageDriftTests.EveryDefectiveRow_IsClaimedByALiveWorkNote` went red, which is exactly the
event that gate exists to catch). This note holds them until each is worked. It is a RESIDUAL note, not a second
register: every claim below is copied from the row it belongs to, and the row remains the record.

## 1. `GR-14.9.49.4-3` — a nonfatal condition raised at a RUNTIME site never reaches selection

GR3 selects a declarative by walking the USE statements; the tiers are implemented and the first-match-wins shape
is right (measured — see the row). What is missing is upstream of it: **an exception raised from the RUNTIME
rather than from an emitter-inserted guard never asks for a declarative at all.**

CONFIRMED BY READING on today's tree: `src/Cobol.Net.Runtime/Exceptions/ExceptionState.cs#Set` (the engine
method, line 94, and the static facade at 971) records `LastName` / `LastFatal` / the §15.32 location operands and
RETURNS. There is no `__EcDispatch` call and no callback into the generated selector. The emitter's own raise
sites (`EcEmitter.EmitArgOrPlain` / `EmitRaise` / `EmitSizeHandling`) route through `EcDispatchExpr` and therefore
DO select a declarative; a condition detected inside the runtime does not.

⚠ **The POPULATION is the row's claim and has not been re-measured here** (`feedback_reachability_is_measured_not_deduced`):
the row names EC-DATA-CONVERSION and EC-BOUND-OVERFLOW as conditions on that path. Whoever takes this note should
measure which enabled nonfatal conditions actually reach `ExceptionState.Set` without a generated guard before
sizing the fix — the code reading above is solid, the blast radius is not.

The rule the omission belongs to is §14.6.13.1.4 (nonfatal exception conditions); it is recorded on the GR3 row
only as the limit on that row's coverage.

Also still open on this row: selection tiers **c, d and f** and WITHIN-TIER SOURCE ORDER have no witness. The two
tests that exist pin GR3a-beats-GR3b-beats-the-rest and GR3e-before-GR3g.

## 2. `GR-14.9.49.4-8` and `-9` — the Report Writer's other six presentation paths, and two unadjudicated edges

The BEFORE REPORTING hook is installed per report group and invoked as the first act of every presentation path
(`ReportWriter.cs#PresentBody` for detail/CH/CF, `#PresentPageHeading`, `#PresentPageFooting`,
`#PresentHeadingFooting` for RH/RF), so all seven group types are covered BY READING. Only the DETAIL path has
witnesses (`ReportWriterConformanceTests.UseBeforeReporting_Gr8_RunsBeforeEachProduction` and
`…_UseProcedureIsTheWholeSection`). RH / PH / PF / RF / CH / CF are unverified.

Two edges are UNADJUDICATED, and either could be a divergence rather than a test gap:

- **GR8 / §13.18.41.4 GR2.** The hook fires BEFORE `EvaluatePresent`, so a group all of whose LINE clauses are
  absent under PRESENT WHEN — which GR2 says is treated "as though the entire report group description entry were
  omitted" — still runs its declarative. Whether GR8's "just before the named report group is produced" is
  satisfied when nothing is produced has not been decided.
- **GR9 b) for a CONTROL FOOTING group.** GR9b requires the declarative to run "after incrementing sum counters
  defined in the report group". `Generate` accumulates after break processing and before `PresentBody(detail)`, so
  a detail group is right; a CONTROL FOOTING group is presented DURING break processing, i.e. before this
  GENERATE's accumulation — which is §13.18.54.4 GR7c's own requirement. Whether that satisfies GR9b for a CF
  group is not established.

GR9 a), b) and c) have no test at all.

## 3. `GR-14.9.49.4-7` and `-12` — the SORT/MERGE arm, and the implementor determination

- **GR7 a) / GR12 a): "If the USE statement was invoked from a MERGE or a SORT statement, the rules for those
  statements are followed."** `SortEmitter.EmitInputFile` / `#EmitGivingFile` do call `EmitUseHook` around the
  implicit OPEN/CLOSE, so a declarative CAN fire there — but §14.9.40.4 GR17 ("If a USE procedure invoked while a
  format 1 SORT statement is active does not complete normally, the SORT statement is terminated") has no
  modelling anywhere. Unverified in both directions: no witness that the hook fires, and no implementation of the
  rule it is supposed to defer to.
- **GR7 c) / GR12 c): the implementor determination for a fatal I-O status is `kb/Work/PB322`.** It is not one
  determination today — the action taken depends on a `>>TURN` directive the rule does not mention — and Annex A.1
  item 218 makes writing it down a conformance obligation. That half is PB322's and is not duplicated here.

## What would close each row

`-3`: a dispatch hook on the runtime raise path plus witnesses for tiers c/d/f and within-tier order.
`-8`/`-9`: witnesses for the six non-detail presentation paths, and an adjudication of the two edges above.
`-7`/`-12`: §14.9.40.4 GR17 modelled with a SORT-invoked-USE witness, and PB322's determination written down.

## Landed — 2026-09-13

**1. `GR-14.9.49.4-3` → CONFORMS. The runtime raise path now runs the §14.6.13.1.4 #3 selection, and the
POPULATION was measured rather than assumed.** The note asked for the blast radius first; it is FOUR conditions,
not two, and all four reproduced on the pre-fix compiler (`<scratch>/PB367b/probe/p1,p2,p4,p5` — the status was
set, the declarative never ran):

| condition | runtime raise site | rule |
|---|---|---|
| EC-BOUND-OVERFLOW | `CobolDynTable.RefReceiving` | §8.5.1.9.6 GR1 |
| EC-RANGE-INVALID | `CobolString.ThruMember` / `CobolCollation.ThruMember` | §14.7.8 rule 2 |
| EC-STORAGE-NOT-AVAIL | `CobolDynString.SetSize` ×2 | §14.9.39 Format 16 GR37/GR38 |
| EC-DATA-CONVERSION | `CobolIntrinsics.ByteSub` | §15.19.4 rule 3 / item 209 |

Every other runtime raise is FATAL and reaches a declarative already, by throwing `CobolFatalException` into the
emitted statement guard; EC-CONTINUE-LESS-THAN-ZERO is nonfatal but its site reports the raise to an emitted
dispatch (the PB138 shape). So the defect was exactly "nonfatal + no statement-level node to hang a dispatch on".

**The fix is one channel, at the scope the rule names.** `ExceptionEngine.NonfatalIfEnabled` — the ONE place
§14.6.13.1.1's raise rule is written (PB676) — now also runs the selection, through
`ICobolProgram.NonfatalDispatch(string ec)`, whose default is the protocol's "no qualifying declarative" so a
program with no Format-3 machinery emits nothing (the zero-scaffolding invariant is untouched) and a program with
it emits one expression-bodied override onto the existing `EcDispatchExpr` funnel (so §14.6.13.1.4 #2's "No
associated USE EXCEPTION declarative is executed" still holds through `__EcPerform`). The dispatcher is the
ACTIVATION's, installed and restored by `ProgramTable.RunMain`/`CallProgram` beside the ModuleStack frame — a
condition raised inside a CALLed program selects THAT program's declaratives (§14.9.49.4 GR3's "the USE
statements in the source element", GR4 a)).

**Two hand-copied raises became the fifth and sixth uses of the ONE shape.** EC-RANGE-INVALID and
EC-STORAGE-NOT-AVAIL were `ExceptionState.Set(name, fatal: false)` written out at the site — the exact copy the
`CheckingFlags` doc forbids — with their enablement threaded a SECOND way (the emitter chose the `ThruMember`
carrier only under checking; `SetSize` took a `checkStorage` argument). Both are now `CheckingFlags` fields with
engine helpers, static shims and `EcEmitter.NonfatalAmbientGates` rows, so `ExceptionRaiseHelperDriftTests`
covers them by construction and `BoundSetSize.CheckStorage` is deleted.

**The return, adjudicated.** `-1`/`-3` return to the raise point and the statement finishes under its own rules
(§14.6.13.1.4 #3's "execution continues as specified in the rules for normal execution" — and each of the four
conditions has a rule naming that continuation: §14.7.8 rule 2's "upon completion of any exception processing,
execution proceeds as if the range of values were empty" is the clearest). §14.9.49.4 GR13 a) is the alternative
for a condition whose statement rules name none. A RESUME is an explicit transfer and unwinds through
**`RaiseResumeSignal`**, a type DISTINCT from `ResumeSignal`: the two have different landing sites, and sharing
one made the nearer one swallow the farther — the emitted wrapper caught the signal a declarative's own RESUME
was throwing at `__RunUse`, turning `RESUME AT NEXT STATEMENT` into a CONTINUE. Caught in the first golden run.

**Tiers c/d/f and within-tier source order are witnessed** by `conformance:2023/pb367b_use_selection_tiers`,
whose six declaratives are written in the REVERSE of the tier order so that tier order beating source order is
the observation; the two EC-ALL declaratives (legal — SR14 forbids only a repeated (exception-name-2,
file-name-2) PAIR) pin within-tier order.

**2. `GR-14.9.49.4-8` and `-9` → CONFORMS.** All seven presentation paths are witnessed at once by
`ReportWriterConformanceTests.UseBeforeReporting_Gr8_EveryGroupTypeInvokesItsOwnDeclarative` (each group prints
the digit ITS OWN declarative wrote). Both edges are adjudicated:

- **PRESENT WHEN** is an implementor DETERMINATION, recorded in `COBOLNET_REPORT_WRITER_DESIGN`'s PRESENT WHEN
  row and pinned by `…UseBeforeReporting_PresentWhen_DeclarativeRunsBeforeTheConditionIsEvaluated`: GR9 d) and
  §13.18.41.4 GR2 place the declarative and the condition evaluation at the SAME boundary ("before the processing
  of any LINE clauses") with no rule ordering them, so the order is ours; the declarative runs FIRST, because the
  reverse makes its execution depend on data it exists to set.
- **GR9 b) for a CONTROL FOOTING** is CONFORMING, and the chain is the answer the note asked for: §13.18.54.4
  GR7 c) 1. adds on every GENERATE and §14.9.16.4 GR5 a) places the breaking record's own addend after the break
  processing, so a CF presented during the break has already received every increment that belongs to it.
  `…UseBeforeReporting_Gr9ab_AfterBreakProcessingAndAfterSumIncrement` witnesses a) and b).

**3. `GR-14.9.49.4-7` and `-12` stay PARTIAL, and their rows moved to `kb/Work/PB322`.** §14.9.40.4 GR17 is
modelled — a USE procedure invoked from a SORT/MERGE implicit transfer that does not complete normally
(§14.6.13.1.2 #1: a RESUME) terminates the statement, via an end-of-statement label `EmitUseHook` jumps to;
`conformance:2023/pb367b_sort_use_not_normal` is the witness (the OUTPUT PROCEDURE never runs, and pre-fix it did
— and the declarative fired TWICE, once per implicit transfer). What remains on both rows is ONLY PB322's
determination E (GR7 c) / GR12 c), A.1 item 218), which is why they are now that note's rows: this mechanism
cannot close them and they must stay claimed.

**New defect found, outside this mechanism** (reported, not fixed here): a NAMED SUM COUNTER is rejected in the
procedure division — `03 CF-SUM COLUMN 4 PIC 99 SUM WS-AMT` then `MOVE CF-SUM TO X` fails COBOLNET1639, while
§13.18.54.4 GR5 ("the data-name is the name of the sum counter") and GR12 ("It is permissible for procedure
division statements to alter the content of sum counters") make it legal. It cost GR9 b) its direct observable.
