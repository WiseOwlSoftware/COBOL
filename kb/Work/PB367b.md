# PB367b — the residual of the USE-dispatch rows

**Why this note exists.** `kb/Work/PB367` claimed six rows because ONE defect — a handler end derived from
paragraph shape — was a listed limit on all six. That defect is landed and `GR-14.9.49.4-13` closed with it. The
other five stay `PARTIAL` on limits that were never PB367's mechanism, and with PB367 landed nothing live owned
them (`DefectiveRowCoverageDriftTests.EveryDefectiveRow_IsClaimedByALiveWorkNote` went red, which is exactly the
event that gate exists to catch). This note holds them until each is worked. It is a RESIDUAL note, not a second
register: every claim below is copied from the row it belongs to, and the row remains the record.

## 1. `GR-14.9.49.4-3` — a nonfatal condition raised at a RUNTIME site never reaches selection

GR3 selects a declarative by walking the USE statements; the tiers are implemented and the first-match-wins shape
is right (measured — see the row). What is missing is upstream of it: **an exception raised from the RUNTIME
rather than from an emitter-inserted guard never asks for a declarative at all.**

CONFIRMED BY READING on today's tree: `src/Cobol.Net.Runtime/Exceptions/ExceptionState.cs#Set` (the engine
method, line 94, and the static facade at 971) records `LastName` / `LastFatal` / the §15.32 location operands and
RETURNS. There is no `__EcDispatch` call and no callback into the generated selector. The emitter's own raise
sites (`EcEmitter.EmitArgOrPlain` / `EmitRaise` / `EmitSizeHandling`) route through `EcDispatchExpr` and therefore
DO select a declarative; a condition detected inside the runtime does not.

⚠ **The POPULATION is the row's claim and has not been re-measured here** (`feedback_reachability_is_measured_not_deduced`):
the row names EC-DATA-CONVERSION and EC-BOUND-OVERFLOW as conditions on that path. Whoever takes this note should
measure which enabled nonfatal conditions actually reach `ExceptionState.Set` without a generated guard before
sizing the fix — the code reading above is solid, the blast radius is not.

The rule the omission belongs to is §14.6.13.1.4 (nonfatal exception conditions); it is recorded on the GR3 row
only as the limit on that row's coverage.

Also still open on this row: selection tiers **c, d and f** and WITHIN-TIER SOURCE ORDER have no witness. The two
tests that exist pin GR3a-beats-GR3b-beats-the-rest and GR3e-before-GR3g.

## 2. `GR-14.9.49.4-8` and `-9` — the Report Writer's other six presentation paths, and two unadjudicated edges

The BEFORE REPORTING hook is installed per report group and invoked as the first act of every presentation path
(`ReportWriter.cs#PresentBody` for detail/CH/CF, `#PresentPageHeading`, `#PresentPageFooting`,
`#PresentHeadingFooting` for RH/RF), so all seven group types are covered BY READING. Only the DETAIL path has
witnesses (`ReportWriterConformanceTests.UseBeforeReporting_Gr8_RunsBeforeEachProduction` and
`…_UseProcedureIsTheWholeSection`). RH / PH / PF / RF / CH / CF are unverified.

Two edges are UNADJUDICATED, and either could be a divergence rather than a test gap:

- **GR8 / §13.18.41.4 GR2.** The hook fires BEFORE `EvaluatePresent`, so a group all of whose LINE clauses are
  absent under PRESENT WHEN — which GR2 says is treated "as though the entire report group description entry were
  omitted" — still runs its declarative. Whether GR8's "just before the named report group is produced" is
  satisfied when nothing is produced has not been decided.
- **GR9 b) for a CONTROL FOOTING group.** GR9b requires the declarative to run "after incrementing sum counters
  defined in the report group". `Generate` accumulates after break processing and before `PresentBody(detail)`, so
  a detail group is right; a CONTROL FOOTING group is presented DURING break processing, i.e. before this
  GENERATE's accumulation — which is §13.18.54.4 GR7c's own requirement. Whether that satisfies GR9b for a CF
  group is not established.

GR9 a), b) and c) have no test at all.

## 3. `GR-14.9.49.4-7` and `-12` — the SORT/MERGE arm, and the implementor determination

- **GR7 a) / GR12 a): "If the USE statement was invoked from a MERGE or a SORT statement, the rules for those
  statements are followed."** `SortEmitter.EmitInputFile` / `#EmitGivingFile` do call `EmitUseHook` around the
  implicit OPEN/CLOSE, so a declarative CAN fire there — but §14.9.40.4 GR17 ("If a USE procedure invoked while a
  format 1 SORT statement is active does not complete normally, the SORT statement is terminated") has no
  modelling anywhere. Unverified in both directions: no witness that the hook fires, and no implementation of the
  rule it is supposed to defer to.
- **GR7 c) / GR12 c): the implementor determination for a fatal I-O status is `kb/Work/PB322`.** It is not one
  determination today — the action taken depends on a `>>TURN` directive the rule does not mention — and Annex A.1
  item 218 makes writing it down a conformance obligation. That half is PB322's and is not duplicated here.

## What would close each row

`-3`: a dispatch hook on the runtime raise path plus witnesses for tiers c/d/f and within-tier order.
`-8`/`-9`: witnesses for the six non-detail presentation paths, and an adjudication of the two edges above.
`-7`/`-12`: §14.9.40.4 GR17 modelled with a SORT-invoked-USE witness, and PB322's determination written down.
