# PB1130 — LANDED 2026-09-27 (wave 68 V, with PB1130 PB1131 PB1186 PB1187 PB1247 — one report-engine pass)

## Landed (wave 68 V, 2026-09-27) — the sum counter's size error indicator, and the engine's first nonfatal raise

- **SUM-SIZE.** `CobolReport.SumEntry` carries GR1's size error indicator and its capacity, the PICTURE's digit count
  (`AddSum(id, digits, …)`, emitted from the counter's register). `Add` tests every addition (GR3): past the bound the
  counter keeps its value as ADD ON SIZE ERROR leaves it (§14.7.5 1)), the indicator is set and EC-REPORT-SUM-SIZE is
  raised (fatal, checking-gated). The emitted compose asks `SumPresentable(id)`: while the indicator is set the
  printable item is SPACES (GR4 — unconditional) and the condition is raised. INITIATE (§14.9.21.4 GR1 a)) and every
  GR2 reset unset it (`SumEntry.Reset`). Probe p1.cob now prints `S=` (spaces), then `S=05` after re-INITIATE.
- **The nonfatal raise and its resume.** `CobolReport.PresentLine` raises EC-REPORT-LINE-OVERLAP
  (`ExceptionState.ReportLineOverlapError`, §13.18.35.4 GR3) for a line on or above one already printed; when it is
  RAISED the line is abandoned and LINE-COUNTER keeps naming the last line printed — §14.9.16.4 GR8 / §14.9.46.4 GR5
  "execution resumes at the next report item, line, or report group". Both names bind PRECISELY to GENERATE and
  TERMINATE (`EcBinder.ReportProductionNames`); the prior attempt had added them only to the EC emitter's flag
  table, so `>>TURN … CHECKING ON` wrapped nothing.
- **Golden:** `conformance:2002/pb1130_report_sum_size_line_overlap` (size error → `S=  `, re-INITIATE → `S=05`;
  a runtime overlap of two PRESENT WHEN absolute lines runs the declarative and the next group lands on line 6).
- **Not here:** EC-REPORT-PAGE-LIMIT / -PAGE-WIDTH / -COLUMN-OVERLAP / -VARYING still have no raise site — kb/Work
  PB1188 owns them (their own rules' rows). GR-14.9.16.4-8 is CONFORMS because every nonfatal condition that IS raised
  during GENERATE now resumes as the rule states.

## Measured (adjudicator / refuter evidence, verbatim)
### [generate-statement] The nonfatal report exception conditions that GENERATE processing can raise have no raise site, and the report engine has no resumption point at item, line or group granularity. §14.9.16.4 GR8's rule, 'execution resumes at the next report item, line, or report group', is therefore never exercised. With checking enabled, a user's USE declarative for these conditions never runs.
- **Rows:** GR-14.9.16.4-8 — harm `silent`
- **Repro:** >>TURN EC-REPORT-LINE-OVERLAP CHECKING ON (or EC-REPORT-PAGE-LIMIT / EC-REPORT-PAGE-WIDTH / EC-REPORT-COLUMN-OVERLAP), a USE AFTER EXCEPTION CONDITION EC-REPORT-LINE-OVERLAP declarative that DISPLAYs a marker, and a detail with two absolute lines LINE 5 and LINE 3 (they overlap on print: GR7a places the second line above the first). GENERATE the detail. The declarative never runs, and the engine silently advances the second line by one.
- **Expected (spec):** §13.18.35.4 GR3: an overlap sets EC-REPORT-LINE-OVERLAP to exist. Table 13 marks it NF. §14.6.13.1.4: when checking is enabled, the declarative is executed. §14.9.16.4 GR8: GENERATE then resumes at the next report item, line or report group. The marker must be displayed, and the next line or group must still be printed.
- **Observed:** A search of src for EC-REPORT-COLUMN-OVERLAP, LINE-OVERLAP, PAGE-LIMIT and PAGE-WIDTH finds them only in ExceptionCatalog.cs registrations. ReportWriter.PresentLine clamps an overlapping target with `advance = 1` and carries only a comment 'EC-REPORT-LINE-OVERLAP seam'. PB326 (landed) listed these as the remaining CONTENT/GEOMETRY seams. PB1037 (open, process-only analysis) proposes only a drift test. No open defect note owns them.
- **Code site:** src/Cobol.Net.Runtime/IO/ReportWriter.cs#CobolReport.PresentLine; src/Cobol.Net.Runtime/Exceptions/ExceptionCatalog.cs (EC-REPORT-* registrations)

### [initiate-statement] The report engine's sum counter has no size error indicator: CobolReport.SumEntry is an unbounded `long Value`, accumulation (`s.Value += t.Addend()`) never tests the result against the digits the entry's PICTURE derives (§13.18.54.4 GR1/GR3), so there is no indicator for INITIATE to reset (§14.9.21.4 GR1a, §13.18.54.4 GR2), no EC-REPORT-SUM-SIZE raise, and the print step MOVEs the overflowed total (high-order truncated) instead of filling the printable item with spaces (§13.18.54.4 GR4).
- **Rows:** GR-14.9.21.4-1 — harm `wrong-answer`
- **Repro:** out/probe/initiate/p1.cob (--std 2023; the same at every edition): `01 WS-N PIC 99 VALUE 60.` / `RD R-A CONTROL IS FINAL ...` / `01 TYPE CF FINAL LINE PLUS 1. 02 COLUMN 1 PIC X(2) VALUE "S=". 02 COLUMN 3 PIC 99 SUM WS-N.` ; OPEN OUTPUT, INITIATE R-A, GENERATE DET-A twice, TERMINATE R-A. Observed control footing line: `S=20`.
- **Expected (spec):** The sum counter has two integer digits (§13.18.54.4 GR1 'derived from the corresponding number of digits ... in the PICTURE clause'); the second addition 60+60 is a size error (GR3 'Each addition is tested for size error; if a size error occurs, the EC-REPORT-SUM-SIZE exception condition is set to exist'), which sets the entry's size error indicator; at presentation GR4 'If the associated size error indicator is set, an EC-REPORT-SUM-SIZE exception condition is set to exist and the printable item is filled with spaces' -> the line is `S=  `. A following TERMINATE/INITIATE unsets the indicator (§14.9.21.4 GR1a, §13.18.54.4 GR2), so a re-INITIATEd report summing 5 prints `S=05` (observed correct only because no indicator exists).
- **Observed:** Measured with the pinned cobol.exe: p1.rpt holds `60`,`60`,`S=20`, then after re-INITIATE `05`,`S=05`. ReportWriter.cs: SumEntry has only `public long Value`; line 514 `s.Value += t.Addend()` with no digit bound; grep for SizeError / SUM-SIZE in the runtime finds only the Initiate doc comment ('size-error indicators are the EC-REPORT-SUM-SIZE seam') and the ExceptionCatalog registration `L3("EC-REPORT-SUM-SIZE", EcFatality.Fatal)` with no raise site. PB326 and PB482 (both landed) name this seam as remaining; no open kb/Work note owns it. The printable-fill-with-spaces outcome is unconditional in GR4 (not gated on checking), so it is wrong at every edition regardless of >>TURN.
- **Code site:** src/Cobol.Net.Runtime/IO/ReportWriter.cs#SumEntry (line ~294), #Initiate (line ~419), the GENERATE accumulation loop (line ~512) and the reset/print path (line ~1060)

## What the fixer owes
SumEntry carries the PICTURE's digit bound and a size-error indicator (§13.18.54.4 GR1-GR3): accumulation tests the bound, sets the indicator and raises EC-REPORT-SUM-SIZE; INITIATE zeroes both; the print path honours the indicator. Give PresentLine a resumption point per item/line/group for the nonfatal EC-REPORT-* raises. PB1037's drift test should then see these names raised.
