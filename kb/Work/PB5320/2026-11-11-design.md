## 1. What a case observes today, and through which channel

### The run path
- `CutRunner.RunExit` (`tests/WiseOwl.Cobol.Tests.Conformance/CompilerUnderTest.cs:70-93`) builds `dotnet "<dll>"` with the working directory set to the case directory (`:73`) [R].
  - It pins `COBOL_USER_LOCALE` and `COBOL_SYSTEM_LOCALE` to `INVARIANT` (`:35-39`, `:82`) and sets `WISEOWL_COBOL_MCS` to the case directory (`:85`).
  - It applies the caller's environment overlay, where a null value removes the variable (`:86-89`).
  - It calls `ProcessObserver.ObserveOrThrow(..., runDirectory: workDir)` (`:91`) and returns the normalized stdout and stderr (`:92`).
- **A second mechanism does the same job.** `WiseOwlCobolTestBase.RunAssembly` (`tests/WiseOwl.Cobol.Tests.Unit/WiseOwlCobolTestBase.cs:49-57`) starts its own `dotnet` with no locale pin and normalizes differently (`ReplaceLineEndings("\r\n").TrimEnd()`) [R]. It is used in 47 Unit files. Rule 4 calls for one mechanism; Stage 0 unifies them.
- `NistRunner` passes `COBOL_SWITCH_1=ON` (`NistRunner.cs:38`) and runs chain predecessors in the same directory (`:44-54`) [R].

### Exit code: how each ending reaches it
The generated `Main` is `ProgramRegistry.Reset(); [FileInit;] try { RunModule(EnsureRegistered, main); } catch (StopRun) { }` (`ProgramEmitter.cs:894-916`) [R]. `RunModule` (`ProgramTable.cs:341-349`) calls `StandardStreams.EnsureUtf8()` (`:346`), runs the run unit on its own 384 MiB thread (`ActivationStack.cs:65-83`), and writes `Environment.ExitCode = Position32(ExitStatus)` in a `finally` (`:348`). That is the only exit-code write in `src`.

| Ending | Mechanism |
|---|---|
| STOP RUN | `SetExitStatus` when a status phrase is given (`StatementEmitter.cs:143`), then `throw new StopRun()` (`:144`). The run unit's `finally` calls `Terminate`, `RunModule`'s `finally` sets the exit code, and `Main` catches `StopRun` and returns [R]. |
| GOBACK from the main program | Returns through the same `RunModule` `finally` [R]. |
| Abnormal termination (a fatal EC, or `CobolCallException`) | Caught in `RunOnThisThread` (`ProgramTable.cs:370`). `AbnormalTermination` writes `abnormal run-unit termination: …` to `Console.Error` and sets status 1 (`:425-435`). The process exits normally with code 1 [R]. |
| Any other unhandled exception (a defect) | Leaves `RunModule` after its `finally` and leaves `Main`. The CLR prints `Unhandled exception. …` to stderr and the process dies: exit 0xE0434352 on Windows, 134 (SIGABRT) on Linux. This is known .NET behaviour, not measured here [I]. Tests assert `DoesNotContain("Unhandled exception")` (`RunUnitTerminationTests.cs:256`, `SizeErrorDispositionTests.cs:91,127,392,463`) [R]. |
| Runtime-detected fatal conditions | They go through the abnormal-termination row above. Nothing calls `Environment.Exit` or `FailFast`: `ProcessStateOwnerDriftTests.cs:37` forbids both anywhere in `src` [R]. Stack exhaustion is turned into EC-PROGRAM-RESOURCES before the CLR would kill the process (`ActivationStack.cs:22-30`) [R]. |
| After `Main` returns | `AppDomain.ProcessExit` runs `RunUnit.EndAtProcessExit` (`RunUnit.cs:295, 306-318`). It closes any run unit still owing files, and can write to stderr (`:315`) [R]. |
| POSIX parent | Sees only the low 8 bits of the exit code (CONFORMANCE item 192) [R in the `RunUnit.cs:274-278` doc]. |

### Standard streams
- **DISPLAY** is emitted as `global::System.Console[.Error].Write/WriteLine` directly in generated code (`AcceptDisplayEmitter.cs:52-53`); STOP literal is `Console.Error.WriteLine` (`StatementEmitter.cs:151`) [R].
- **Process-entry setup.** `EnsureUtf8` runs once per process (`StandardStreams.cs:96`). On a redirected handle it installs `StreamWriter(OpenStandardOutput(), UTF8(no BOM)) { AutoFlush = true }`, and the same for stderr and stdin (`:134-148`) [R].
- **Harness side.** The observer redirects all three streams with BOM-less UTF-8 (`ProcessObservation.cs:137-150`) and drains both outputs asynchronously (`:171-172`). The two captures are separate pipes, so no interleaving is observed in either mode [R].
- **Byte-level detail.** .NET's `Process` decodes stdout with a `StreamReader` that detects a byte-order mark [I]. A leading U+FEFF that a program DISPLAYs is therefore stripped today. The runner must decode the same way (section 3).

### Standard input for ACCEPT
- `AcceptSource.Device` reads `Console.In.ReadLine()` (`AcceptSource.cs:93, 99`) [R].
- The harness writes the whole input, then closes the pipe, so an over-reading ACCEPT sees end of input (`ProcessObservation.cs:175-178`) [R].

### Environment variables and the command line
- **No command-line or environment ACCEPT exists.** `AcceptKind` has only Device and the temporal kinds (`BoundAccept.cs:57`). The generated `Main()` takes no arguments, and the runtime never reads `GetCommandLineArgs` [R].
- **Every variable the runtime reads** is registered in `RuntimeConfig.All` (`RuntimeConfig.cs:67-157`). When each is read:
  - Per use: the clock pin (`Clock.cs:38-42`).
  - Per run unit: the locale defaults (`LocaleState.cs:195, 320`), the switches (`SwitchStore.cs:57`), sort memory and directory, the indexed-file key check, and messaging settings.
  - Once per process: the collation key-cache configuration (latched in `CollationRuntime.Initialize`, `CollationRuntime.cs:80-88`) [R]. The tailoring and CLDR directories are re-read per call (`TailoringRules.cs:123-126`, `CldrLocaleLoader.cs:183-185`), but whether their results are cached is not checked [I].

### Current directory and files
- Relative ASSIGN names resolve through the current directory: `Path.GetFullPath(spelling)` (`CobolFile.cs:431`) and the `FileRegistry` sites (`:1059, 1375, 1511`) [R].
- The message control system's directory falls back to `Directory.GetCurrentDirectory()` (`McsDirectory.cs:48`) [R].
- SORT spill files go to `Path.GetTempPath()` (`SortMemory.cs:54`), named with `Environment.ProcessId` and deleted on close (`FileSupport.cs:780`) [R].
- The "beside the application" lookups use `AppContext.BaseDirectory`: the sibling-module probe (`ProgramTable.cs:1098`) and the collation directories [R].
- **The probe loads a sibling into `AssemblyLoadContext.Default` (`ProgramTable.cs:1107`)** [R]. This matters for options (a) and (b).
- What a test reads afterwards: NIST grades every file the run wrote, by snapshot and modification time (`NistRunner.cs:63, 86`); `CompileRunAndReadFile` reads raw bytes (`CompilerUnderTest.cs:135-153`) [R].

### Time limits
- One harness unit is 120 s (`ObservationBudget.cs:28, 46`) [R].
- On timeout the observer kills the whole process tree and returns no stdout (`ProcessObservation.cs:180-190`) [R].
- `ObserveWithRetry` (`:283-321`) captures `RunDirectoryState` first, retries once behind `RetryGate`, restores the run directory before the retry, and waits for a process that survived its kill [R].

### Runtime static state
- **Per run unit, by design.** `RunUnit` owns all run-unit state behind an `AsyncLocal` (`RunUnit.cs:27`). The generated `Main`'s first statement, `Reset`, is `Begin`, which creates a new object every time (`:367`). Only `Clock`, `DebugMode` and `MessagingSettings` carry over between run units (`:125`). `RunUnitStateDriftTests` holds this [R].
- **Covered by the run unit.** The CANCEL program table, EXTERNAL data, the file table and SPECIAL-NAMES switches are run-unit members [R].
- **Static storage.** A program's static storage is reset when a run unit adopts it (`:187-193`) [R].
- **Process-wide state.**
  - `StandardStreams._applied`.
  - `RunUnit._openRunUnits` and its `ProcessExit` handler (`:293-295`).
  - The collation latch.
  - `PointerImage.Epoch`, which is random per process (`PointerImage.cs:72`).
  - The `ProcessId` used in sort file names and as the messaging identity (`MessagingPeer.cs:266`).
- **Culture.** It comes from the process; the run-unit thread copies the caller's culture (`ActivationStack.cs:77-78`) [R].
- **Finalizers.** `~CobolObject` only queues closes on the run unit that owns the object (`CobolObject.cs:214-218`) [R].

### Product hosting contract (already shipped)
- DOC-A.1-167 (`docs/CONFORMANCE.md:4714`): a host process may run many run units in sequence, each fresh. STOP RUN and fatal conditions end the run unit only. Only the entry that is the process writes the exit code or configures the console [R].
- `RunUnitHostConsoleTests` shows that under a host, DISPLAY goes to whatever `Console.Out` the host installed [R].

## 2. The options

### (a) A collectible load context per case inside the test host: rejected
- **Console:** recoverable without a product change. A routing writer keyed on an `AsyncLocal` would work, because the run-unit thread inherits the execution context (`ActivationStack.cs:61-63`).
- **Exit code:** `Environment.ExitCode` would race between 32 concurrent cases. Reading `RunUnit.ExitStatus` instead bypasses `RunModule`'s mapping, so it no longer tests the process entry.
- **Current directory and environment:** impossible for concurrent cases unless the product gains a per-run-unit base directory and environment. Those would be test-driven hosting features, which the brief forbids.
- **Crashes:** a stack overflow, a `FailFast` inside the BCL or a native access violation kills the test host. All 32 in-flight cases and the rest of the run are lost.
- **Hangs:** .NET cannot abort a thread, so one hung program hangs the gate.
- **The runtime would have to load once per context.** A per-context runtime registers its own `ProcessExit` handler (`RunUnit.cs:295`). That static CoreLib event holds a delegate into the context, so the context can never unload [I, by construction]. It would also lose ReadyToRun: collectible contexts JIT everything [I; spike].
- **Verdict:** the crash and hang isolation alone rule (a) out.

### (b) A pool of long-lived runner processes: the core of the design
Each runner runs one case at a time, which makes every process-wide channel settable per case.

**The runtime is shared.** It is loaded once per runner into the Default context, from the ReadyToRun image the gate's programs deploy (`AssemblyPackager.cs:103-116`, design section 3.16). Each program goes into a new collectible `CaseLoadContext`. Three reasons:
1. The product promises run-unit isolation within one process (DOC-A.1-167, PB1069).
2. ReadyToRun code is kept.
3. The per-context `ProcessExit` handler that would pin every context goes away.

**Isolation compared with the other options.**
- Weaker than a process: runtime and .NET process state (JIT tiers, the GC, the thread pool, the culture and time-zone caches) is shared.
- Stronger than (a): a crash or hang kills one runner and one case, and the case is re-run as a process.

**What it cannot observe faithfully, and what happens to it:**

| Item | How the runner handles it |
|---|---|
| CLR crash output and exit code (unhandled exception, stack overflow) | Fallback to a process |
| `ProcessExit`-time closes (`EndAtProcessExit`) | Not run per case. Detected indirectly: an owing run unit holds files open (open-handle probe) and keeps the context alive (unload proof). Fallback. |
| Process-start state: culture from `LANG`, `TZ`, `DOTNET_*` | Constant per runner. A case whose environment overlay touches it falls back. |
| The muxer: framework resolution from `prog.runtimeconfig.json` | Not exercised. CI's process mode covers it (D1). |
| The sibling probe loading into Default | Cases with companion modules fall back (Stage 4 can lift this). |

**Pool size.** K = min(processor count, xunit's maximum threads): 32 here, 4 on a GitHub runner. Runners are created lazily, with at most 8 being created at once per host; the measured best machine-wide creation rate was at 8 threads, 12.1 per second, against 7.3 at 16 [M]. A runner is recycled after a taint or after 1,000 cases.

**Product change needed:** none.

### (c) Keep one process per case and cut the cost around it

**Start children without .NET's lock.** A Windows `HandleListLauncher` would call `CreateProcessW` with `STARTUPINFOEX` and `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, which passes each child only its own three pipe handles. That is exactly what `s_createProcessLock` exists to guarantee (findings section 1.2). The child would go into a job object so a tree kill still works.
- Degraded box: process creation stays 0.5 to 2 s, but stops being serialized per host. The limit becomes the machine's roughly 10 creations a second [M]. Conformance goes from about 4,556 s to 800 to 1,200 s for one gate [M-modeled, findings section 5(b)1], and up to about 2,400 s when three gates draw on the same rate [I].
- Healthy box: the lock is held about 7 ms × 8,000 ≈ 56 s across a 167 s run. The gain is 5 to 20 s [I].
- It applies to every child the tests start, including python and git, so the oracle and the process-mode remainder benefit too.

**Apphost instead of `dotnet prog.dll`:** the same number of creations. It would only save the PATH search for `dotnet`, and it needs a compiler change. Rejected.

**ReadyToRun for programs:** the runtime is already ReadyToRun (104.7 → 74.5 ms per start [M section 3.16]). Compiling every program ahead of time costs seconds per compile and does not touch creation. Rejected.

**A shared startup snapshot:** CoreCLR has no checkpoint or fork mechanism. Not available.

**Not observable:** none, because it is still a real process. **Product change:** none.

### (d) Hybrid: the recommendation
Every eligible case runs in a runner from (b). The declared subset and every case a detector rejects run as a process, through the lock-free launcher from (c). The oracle in section 3 certifies the population. No product change is needed in Stages 0 to 3; the Stage 4 product questions stand on their own merits.

## 2a. The concrete shape

### Harness side (`tests/_shared/`)
- **`ProgramRun.Run(ProgramRunRequest) → ProgramObservation`:** the one way a test runs a compiled program.
  - `ProgramRunRequest(EntryDll, WorkDir, Stdin, Environment, Budget)`.
  - `CutRunner.RunExit` and `WiseOwlCobolTestBase.RunAssembly` both call it. Unit passes an empty overlay where Conformance passes the pinned one, so no test's behaviour changes. The old psi code is deleted.
- **`ProgramObservation`:** carries `ExitCode`, `StdoutBytes`, `StderrBytes`, `Mode` (Runner or Process), `FallbackReason`, and `Taints`.
- **`CapturedText.Decode(bytes)`:** the one decoder for both modes, reproducing `Process`'s `StreamReader(UTF8(false), detectEncodingFromByteOrderMarks: true)`. `ProcessObserver.Observe` changes to read raw bytes from `BaseStream` and decode through it.
- **`HostExitCode.AsReportedToParent(int)`:** the identity on Windows, `code & 0xFF` on POSIX.
- **`ProgramRunMode`** (Process, Runner or Oracle): read from `WISEOWL_COBOL_PROGRAM_RUN`, which only `gate.host_env` sets. The default is Process, so a hand-run `dotnet test` claims nothing new.
- **`RunnerEligibility.WhyNot(request)`:** the checks made before a run. Any reason sends the case to a real process.
  1. The entry is not a WiseOwl COBOL module with a `Main`. This is a metadata read without loading the assembly, and it covers the host programs in `RunUnitHost*Tests` and `HostEntryTests`.
  2. The run directory holds managed modules other than the entry and the runtime (companions, chain predecessors' DLLs are fine because they are not loaded).
  3. The deployed `WiseOwl.Cobol.Runtime.dll` differs from the runner's, by length and XxHash128. This catches the `RuntimeVersionSkew` tests.
  4. An overlay variable is not a `RuntimeConfig` entry read per use or per run unit. Until Stage 4's `ReadScope` exists, the variables used today are listed in `ProcessStartStateEmulation` (below).
  5. The test is marked `[ProgramRunsAsProcess(Reason, Note)]`, an xunit `BeforeAfterTestAttribute` that sets an `AsyncLocal`.
- **`RunnerPool`, `RunnerLease` and `RunnerProcess`:**
  - Each runner is started once and reached over a named pipe. On Linux, .NET backs `System.IO.Pipes` with a Unix socket.
  - The harness drains the runner's real stdout and stderr; any byte there is a taint, meaning a case wrote around `Console`.
  - The budget is enforced harness-side. On timeout the runner's tree is killed, the observation is `TimedOut`, the runner is replaced, and the existing retry restores the run directory and re-runs the case as a process.

### Runner side (new exe `tests/WiseOwl.Cobol.ProgramRunner/`)
**Configuration.** Its runtimeconfig has no `configProperties`, matching the one `AssemblyPackager.cs:122-143` writes for programs: workstation GC, default tiering.

**Startup (`RunnerHost`):**
1. Load the runtime image from the path the harness names.
2. Call `StandardStreams.EnsureUtf8()` once. It is public and idempotent (`:94-96`). This must happen before any routing writer is installed, or the first case's `RunModule` would replace it.
3. Install `RoutingTextWriter` for Out and Error and `RoutingTextReader` for In. Each dispatches on an `AsyncLocal<CaseSink>`. A write with no case attached is a taint.
4. Snapshot the baseline environment and the working directory.

**Each case (`CaseExecutor`):**
1. Restore the baseline environment, then apply the overlay.
2. Set `Environment.CurrentDirectory` to the case directory.
3. Set `AppContext.SetData("APP_CONTEXT_BASE_DIRECTORY", dir)`, as the muxer does; the spike confirms `BaseDirectory` honours it [I].
4. Create the case sink: UTF-8 (no BOM) `StreamWriter`s with `AutoFlush` over `MemoryStream`s, built exactly as at `StandardStreams.cs:141, 146`, and stdin as a `MemoryStream` holding the UTF-8 bytes.
5. On a new thread, started with `ExecutionContext.SuppressFlow` so that no ambient `RunUnit` leaks between cases, set the sink and invoke `asm.EntryPoint`.
6. Read `Environment.ExitCode`, then reset it to 0.
7. Move the working directory back to a neutral one, so Windows can delete the case directory.

**`CaseLoadContext.Load(name)`:**
- The runtime maps to the shared assembly.
- `<dir>/<name>.dll` loads from bytes. This mirrors the muxer, which puts every DLL in the app directory on the trusted-assembly list when there is no `deps.json` [I].
- Anything else returns null, which falls back to the framework.

**Checks after the run (`CasePostChecks`).** Each check, if it fails, sends the case to a real process: the run directory is restored and the case is re-run, then recorded.
- `EntryPoint` threw (`TargetInvocationException`).
- A file under the case directory is still open. On Windows this is an exclusive open; on Linux, a scan of `/proc/self/fd`.
- New threads other than thread-pool threads are still alive. The filter uses OS thread names; the spike settles it.
- The context did not unload: a `WeakReference` survives a bounded number of collect, wait-for-finalizers, collect rounds.
- A case-tagged write arrived after the case returned.

Other handle-count growth only marks the runner for recycling.

### Drift tests
- **`RunnerEmulationDriftTests`** (Unit). It follows the pattern of `ProcessStateOwnerDriftTests`. It scans `src/WiseOwl.Cobol.Runtime` for reads of process-wide or process-start state:
  - `Environment.GetEnvironmentVariable`, `Directory.GetCurrentDirectory`, `AppContext.BaseDirectory`, `CultureInfo.Current*`, `Path.GetTempPath`, `Environment.ProcessId`, `GetCommandLineArgs` and `TimeZoneInfo`;
  - `Console.*`, `Environment.ExitCode`, `AppDomain.*Exit` and `AssemblyLoadContext.Default`.

  Each read must have a row in `ProcessStartStateEmulation` saying it is Emulated, Constant-per-runner or handled by fallback with a named detector. A future read, such as an ACCEPT of the command line, therefore fails the test until the runner handles it. This keeps the next case automatic (rule 5).
- Planted witnesses, one per arm:
  - for fallback: a crash, an open file, a leftover thread, a raw-handle write, a timeout, a companion module, a skewed runtime;
  - for faithfulness: STOP RUN with status 4294967296, the `& 0xFF` mapping on POSIX, a BOM and a lone surrogate in output, stdin at end of input.

## 3. The behaviour-neutrality oracle

**Mode.** With `WISEOWL_COBOL_PROGRAM_RUN=oracle`, `ProgramRun` handles each program run as follows:
1. Capture `RunDirectoryState`. This is the existing mechanism from PB3388.
2. Run as a process and capture the result: exit code (as the parent sees it), stdout and stderr bytes, and the run directory's changed set (names and SHA-256 of bytes, excluding the compiler's own artefacts).
3. Restore the directory, run in the runner, and capture the same.
4. If any channel differs, restore and run both modes once more:
   - process == process, runner == runner, and process ≠ runner: a deterministic divergence, which is a finding;
   - process ≠ process: the case is nondeterministic, which is a finding about the test.
5. Return the process observation, so an oracle run is also a full process-mode gate.

**Comparison.** It is made on raw bytes, before `CutRunner.Normalize`, and is stricter than any test. It ignores timing: modification times, durations and budgets. Files outside the run directory (sort spill files, MCS sockets) are not compared, and the design doc says so.

**Ledger.** Each assembly writes one JSON-lines file in the gate's run directory. A record holds: test display name, ordinal of the run within the test, entry name, eligibility or fallback reason, the per-channel hashes for both modes, and the verdict.
`scripts/program_run_oracle.py` turns it into: N compared, N identical, the divergences named by channel, the nondeterministic cases, and a fallback histogram. It also has `--case <name>`, which re-runs one case in both modes to classify a red.

**Coverage.**
- Windows: the whole Unit and Conformance populations, run locally.
- Linux: the WSL reproduction tool (section 3.15), then CI's `nightly.yml`.
- Gate trigger: the gate runs Conformance in oracle mode whenever the diff touches `tests/WiseOwl.Cobol.ProgramRunner/**` or `tests/_shared/ProgramRun*.cs`, because the instrument certifies itself. Two globs in `gate.py`.

**A diverging case is a finding about the mode, never a silent pass.**
1. It becomes a `kb/Work` defect: area test-harness, or runtime when the cause is a run-unit isolation defect, which DOC-A.1-167 makes a product bug.
2. The case gets `[ProgramRunsAsProcess(Note = "PBnnnn")]` until the cause is fixed, either a missing detector or a runtime defect.
3. `ProgramRunPinDriftTests` fails when a pin cites a closed note, so stale pins cannot accumulate.

**Order.** Contamination can depend on which cases ran before in the same runner, so the oracle's runner pass assigns cases to runners at random.

## 4. What the gate and CI run afterwards

**Locally (the code lane).**
- Unit and Conformance: the runner for eligible cases; a real process, through the lock-free launcher, for declared and fallback cases.
- Characterization: unchanged, since it runs no programs (no `ProcessStartInfo` or `CompileAndRun` in that project) [R].
- Linux: still not run locally.
- `verdict.json` gains `program_runs: {runner, process_declared{reason:n}, process_fallback{reason:n}}`, launches per kind, and a creation-time probe that is reported but never asserted (findings section 5(b)6).

**Merge group (recommended under D1).** Unchanged: process mode, Windows and Linux, Release. It is the whole-population check of the shipped product.

**Nightly.** The oracle: Windows locally, Linux in CI.

**Proposed rewording of CLAUDE.md's rule:**
> "⛔ THE RULE: every case the merge group runs on Windows already ran green at the pushed head, on this host, under the same `toolchain.env`, through the program-run mode the gate chose for it (DESIGN-test-build-ci section 3.19). … The merge group is therefore the FIRST run of (a) … (e), and (f) a runner-run case as its own process since the program-run oracle last certified the population. A red of class (f) is a `kb/Work` finding against the runner, classified with `scripts/program_run_oracle.py --case` before anything is changed."

If the controller chooses CI in runner mode instead, the rule stays word for word and class (f) moves to the nightly.

## 5. Expected gain and risks

### Gain (launches modeled at about 8,000 per Conformance run [M-modeled])
| Box | Mode | Conformance | Unit | Characterization |
|---|---|---|---|---|
| Healthy (about 7 ms per creation) | today | 167 s best [M] | 183 s best [M] | 3–33 s [M] |
| Healthy | runner | about 120–150 s [I] | small gain [I] | 0 |
| Degraded at 0.55 s | today | 4,556 s [M] | 400–1,158 s [M] | unchanged |
| Degraded at 0.55 s | lock-free launcher only | 800–1,200 s [M-modeled] | — | — |
| Degraded at 0.55 s | runner + launcher | about 220–300 s [I] | most of the excess over 183 s, depending on its python/git share | 0 |
| Degraded at 2.0 s | today | up to 16,000 s (8,000 × 2 s, serialized per host) [I] | — | — |
| Degraded at 2.0 s | runner + launcher | about 300–500 s [I] | — | — |

**Healthy arithmetic.**
- A process-mode program costs about 74.5 ms to start [M].
- A runner case costs about 10 to 20 ms: creating the load context, loading from bytes, the unload proof and the IPC [I; spike].
- So 8,000 × about 60 ms ≈ 480 thread-seconds, divided by 32 threads ≈ 15 s.
- Add the lock's queueing over about 56 s of total lock hold.
- Result: 10 to 30 % on Conformance.

**Degraded arithmetic.**
- The remainder is about 32 runners + P fallback or declared cases (estimated at 5 %, about 400, to be measured by the Stage 0 census) + about 20 recycles ≈ 450 creations.
- At about 10 creations a second machine-wide this is about 45 s, or about 135 s when three gates share it, overlapping with compilation.
- That lands near the 170 s floor plus 50 to 130 s.
- At 2 s per creation the machine rate is lower (about 4 a second [I]): about 110 to 330 s.

**Unit.** Its python and git launches remain; findings section 5(b)4 covers them, and the launcher helps them.

### Risks, ranked
1. **False green:** a runner pass where a process would fail. Mitigated by the detectors, the whole-population oracle on both operating systems, and D1 (the merge group stays process mode, so a divergence cannot reach main).
2. **Contamination between cases, depending on order.** Mitigated by the unload proof, the handle and thread probes, the late-write sink, recycling, and the oracle's random assignment.
3. **Emulation drift:** a new runtime read of process-start state. Mitigated by `RunnerEmulationDriftTests`.
4. **Pool machinery bugs** producing harness non-observations. Mitigated by the existing exception class, HarnessLog counts, and retry as a process.
5. **Platform asymmetry:** the environment is a managed copy on Linux, the exit code is masked to 8 bits, and open handles are detected differently. Mitigated by the Linux oracle and CI's process mode.
6. **Memory:** about 32 runners × about 100 MB × 3 gate slots ≈ 10 GB, on a 128 GB box [I].
7. **Mistakes in the lock-free launcher:** the environment block, quoting, handle leaks. Mitigated by a drift test that runs the same children through both launchers and compares the observations.
8. **Recursion depth:** a different JIT tier in a warm runner could change the depth at which EC-PROGRAM-RESOURCES fires. The oracle would show it.

## 6. Staged plan

- **Stage 0: measure and unify.** Harness only; lands alone.
  - `ProgramRun` replaces the two run mechanisms (fixing the rule-4 duplication), still in process mode only.
  - `RunnerEligibility` logs each pre-run reason (a census of P).
  - Launch counts per kind go into HarnessLog and `verdict.json`.
  - A scratch spike, not landed, measures: per-case overhead, unload success, ReadyToRun use in Default, `AppContext` base-directory override, and the thread-name filter.
- **Stage 1: the lock-free launcher.** The smallest stage that pays on its own.
  - `HandleListLauncher` on Windows behind `ProcessObserver.Observe`, with at most 8 creations at once per host; Linux keeps `Process.Start`.
