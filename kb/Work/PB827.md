# PB827 — OPEN — the compiler's front door has no fault boundary

Filed 2026-09-09 by the registrar (third pass) from the **PB487 implementer's report**, "New defects found
outside my mechanism" item (a) — `scratchpad/reports/PB487-report.md`. **Re-probed on this worktree's own
`dotnet build CobolSharp.sln -c Debug` (exit 0) at `094739b3`.** No open note owned it: `kb/Work/PB782` (the
shipped exe has no exit-code contract test) and `kb/Work/PB768` (the process-launcher drift guard) are the two
open CLI/harness notes and neither covers an unhandled exception or operand validation — but PB782 is this
note's twin and the two must land together (below).

## Repro — measured, verbatim

```
$ cd .../registrar3/probe && mkdir -p outdir
$ cobol.exe p5_cli.cob -o outdir
Unhandled exception: System.IO.IOException: Access to the path '…\registrar3\probe\outdir' is denied.
 ---> System.UnauthorizedAccessException: Access to the path '…\registrar3\probe\outdir' is denied.
   at Microsoft.Win32.SafeHandles.SafeFileHandle.CreateFile(…)
   … 15 frames …
   at Microsoft.CodeAnalysis.FileSystemExtensions.Emit(Compilation compilation, String outputPath, …)
   at CobolNet.CodeGen.RoslynBackend.Compile(…) in …\src\Cobol.Net.Compiler\CodeGen\RoslynBackend.cs:line 83
   at CobolNet.CodeGen.RoslynBackend.Emit(…)          in …\RoslynBackend.cs:line 42
   at CobolNet.CompilerDriver.Compile(Options options) in …\src\Cobol.Net.Compiler\CompilerDriver.cs:line 149
   at CobolNet.Cli.Program.RunCompile(CliOptions options) in …\src\Cobol.Net.Cli\Program.cs:line 175
   at System.CommandLine.Invocation.InvocationPipeline.Invoke(ParseResult parseResult)
exit=1
```

⚠ **Two premise corrections against the report.** The trace is **18** frames, not 12 (the report undercounts,
which matters only because a fixer matching on frame shape will not find it), and — the substantive one — **the
process exits `1`**. `src/Cobol.Net.Cli/Program.cs` documents and returns `0 · 65 FrontendError · 66
SourceNotFound · 70 BackendError · the child's code under --run · always 0 from --check-batch`. **`1` is not in
that set.** It is the .NET runtime's unhandled-exception code, so the CLI's exit-code contract is not merely
undocumented for this path — it is silently violated. That is `kb/Work/PB782`'s exact subject matter, and PB782
records that NO test drives `cobol.dll`'s contract at all, which is why nothing caught it.

## Expected

There is no ISO rule for a command-line operand — §4.2.2's warning-mechanism requirement is about violations of
the general formats and syntax rules, not about the invocation — so the bar here is the product bar, not the
conformance bar: **a production compiler never presents a .NET stack trace to a user, and never returns an exit
code outside its own published set.** The expected outcome is a diagnostic naming the operand and the reason
("`-o outdir`: the output path names an existing directory; give a file path"), and exit **65** or a
CLI-operand code that the contract defines.

## Mechanism — the root is the absence of a boundary, not the missing check

`Program.cs` contains **no `try` and no `catch` anywhere**
(`grep -n "catch\|try" src/Cobol.Net.Cli/Program.cs` returns only doc-comment prose and `return 66;`).
`RunCompile` (`:172-175`) calls `CompilerDriver.Compile` bare and maps only the *result*, never a *throw*.
Downstream, `CompilerDriver.cs:147` resolves the path with no validation at all —

```csharp
string outputDll = options.OutputPath ?? Path.ChangeExtension(options.SourcePath, ".dll");
```

— and `RoslynBackend.cs:83` hands it straight to `compilation.Emit(outputDllPath)`, which opens the path with
`File.Create`. A directory at that path throws.

So there are two defects stacked, and **fixing only the operand check leaves the class open**:

1. **No fault boundary.** Any IO failure on any path — a read-only output directory, a locked DLL from a running
   process, a full disk, a `--copy` path that vanishes mid-compile — reaches the user the same way.
2. **No operand validation.** `-o` accepts a value that cannot be a file.

## Sibling sweep — measured

| probe | outcome | verdict |
|---|---|---|
| `cobol p5_cli.cob -o outdir` (existing dir) | unhandled `IOException`, exit **1** | ⛔ the defect |
| `cobol p5_cli.cob -o nosuchdir/out.dll` (missing parent) | **exit 0**, directory created, `out.dll` + `Cobol.Net.Runtime.dll` written | ✅ fine — the driver creates the parent |
| `cobol outdir` (source operand IS a directory) | `source file not found: outdir`, exit **66** | ✅ diagnosed, contract-conformant |

The source operand has its guard; the output operand does not. That asymmetry is the whole finding at the
validation layer, and the missing `try` is the finding underneath it.

## What the fix has to be

**One boundary, at the one place every invocation passes through** — `Program.Main`/the `SetAction` lambdas, not
scattered `try`s in the driver. It catches, prints a one-line diagnostic with the operand and the OS reason,
prints the exception detail only under a diagnostic switch, and returns a code the published contract names.
⛔ **It must not swallow programmer errors into a generic "internal error"**: an `IOException` on a user-supplied
path is a user error and gets a user diagnostic; a `NullReferenceException` is a compiler bug and must stay
loud and identifiable (an "internal compiler error, please report" line with the exception type, plus a distinct
exit code) — collapsing both into one silent code would trade this defect for a worse one.

**Land it with `kb/Work/PB782`.** PB782 is "the shipped exe has no exit-code contract test"; this note is "the
shipped exe violates the contract it has no test for". A fix here that is not pinned by PB782's missing test
regresses the first time anyone touches the CLI. The contract test must assert the *set* — including that no
invocation ever returns 1 — which is the assertion that would have caught this one
(`feedback_green_gates_arent_evidence`: make it fail once, on this repro, before trusting it).
