## Measured (adjudicator / refuter evidence, verbatim)
### [execution] UNSTRING identifies its receiving operands (INTO identifier-4, DELIMITER IN identifier-5, COUNT IN identifier-6, WITH POINTER identifier-7, TALLYING IN identifier-8) at the moment each is STORED, not at the start of the statement: EmitUnstring re-renders every receiver's subscripts inside the per-receiver store (move.Emit(r.Store), DelimiterStore, CountIn) and again in the POINTER/TALLYING write-back after the loop, so a subscript that depends on an EARLIER receiver of the same statement selects a different occurrence than §14.6.4 requires.
- **Rows:** GR-14.6.4-7 — harm `wrong-answer`
- **Repro:** 01 I PIC 9 VALUE 1. 01 S PIC X(10) VALUE "3,QQ,RR". 01 U. 05 UE PIC X(2) OCCURS 4 VALUE "--". 01 PT. 05 PE PIC 99 OCCURS 4 VALUE 1. ... UNSTRING S DELIMITED "," INTO I UE(I). DISPLAY U. / MOVE 1 TO I. UNSTRING S DELIMITED "," INTO I WITH POINTER PE(I). DISPLAY PT. (probe E:\Temp\claude\E--CobolSharp\a700c052-f9e4-4942-84ff-a13c7505d6ec\scratchpad\adj-d1\out\probe\iid\iid2.cob, pinned cobol.exe, identical at --std 85 and 2023)
- **Expected (spec):** §14.6.4: 'Unless otherwise specified, item identification is done for an identifier as the first step in the evaluation of that identifier and the identifiers within a statement are evaluated in left to right order as the first operation of the execution of that statement.' §14.9.48.4 GR1-GR18 specify NO other timing (unlike MOVE's 'immediately before', §14.7.7 4b for arithmetic, SET GR2/GR12/14/16/20 and INITIALIZE GR3). So UE(I) and PE(I) are identified with I=1 before '3' is stored in I: U = 'QQ------', PT = '03010101'; with DELIMITER IN DL(I) COUNT IN CE(I) on both receivers, DT = ',---' and CT = '2000'.
- **Observed:** U = '----QQ--' (UE(3)), PT = '01010301' (PE(3)), DT = '--,-', CT = '0020'. Sweep owed: every emitter that stores several receivers of ONE statement without a statement-specific timing rule (UNSTRING is the one found; INSPECT TALLYING+REPLACING, CALL/INVOKE RETURNING with subscripted operands, and ACCEPT/READ INTO are the siblings to measure). The 85 edition's own UNSTRING subscript-timing text is not in this document; an edition-gated difference, if any, must be derived from the 85 standard before the fix.
- **Code site:** src/Cobol.Net.Compiler/CodeGen/Verbs/StringEmitter.cs#StringEmitter.EmitUnstring (the receiver loop's move.Emit(r.Store) / DelimiterStore / CountIn, and the trailing arith.StoreArith(p|t, ...))

### [inspect-statement-p3] INSPECT operand item identification is not done once: the emitter renders each Place at its point of use, so a subscript that depends on a TALLYING counter is re-evaluated after the counter update — the identifier-1 write-back and the REPLACING operands of a format 3 statement address a different occurrence
- **Rows:** GR-14.9.22.4-6 — harm `wrong-answer`
- **Repro:** 01 Y. 05 YE PIC X(3) OCCURS 5 VALUE "AAA". 01 J PIC 9 VALUE 1. INSPECT YE(J) TALLYING J FOR ALL "A" REPLACING ALL "A" BY "Z". DISPLAY J " " Y.
- **Expected (spec):** J=4 Y=ZZZAAAAAAAAAAAA — GR6 identifies YE(J) once (J=1) as the statement's first operation, and GR19 identifies every format-2 identifier before the format-1 pass.
- **Observed:** Pinned cobol.exe prints J=4 Y=AAAAAAAAAZZZAAA: the image is read from YE(1), then EmitStore writes it through PlaceRenderer.Write(p, img) and re-evaluates J=4. The same applies to REPLACING pattern/replacement/delimiter operands (OperandTextOf at the Replace call) and to a counter subscripted by an earlier counter (StoreArith per operand). The fix is to evaluate every subscript, ref-mod and ODO in the INSPECT operands into temporaries (or bind stable Place snapshots) before the first operation.
- **Code site:** src/Cobol.Net.Compiler/CodeGen/Verbs/InspectEmitter.cs#Emit (counter StoreArith loop, Replace/Convert argument rendering); #EmitStore

### [invoke-statement-p3] F2 — INVOKE's RETURNING identifier-4 is identified (its subscripts evaluated) AFTER the method returns, not at the beginning of the statement

### GR-14.6.4-1 (PARTIAL)
Rule: step 1 of item identification is 'locale identification' (cite.py --check 14.6.4 -> OK). The locale-dependent reads (PICTURE format 2 editing/de-editing, LOCALE-* functions) consult the run unit's ONE locale state at the time of the edit (§14.6.6 r6 'the locale current at the time of editing or de-editing'). Whether locale identification happens FIRST - before a subscript/function/refmod operand inside the SAME identifier that executes SET LOCALE (a user-defined function can) - was not probed and is not decided by reading: no code site models locale identification as an item-identification step, so the ordering against steps 2-7 is unverified. PARTIAL on an evidence burden, not a measured wrong answer.
- **Code location (record):** src/Cobol.Net.Runtime/Control/RunUnit.cs#RunUnit.Locale; src/Cobol.Net.Compiler/CodeGen/Roslyn/PlaceRenderer.cs

## What the fixer owes
ONE mechanism: an emitter helper that snapshots a Place's resolved address (subscripts, ref-mod start/length, ODO extent) into temps at statement start and hands the snapshot to every later read/store. Adopt it in StringEmitter.EmitUnstring, InspectEmitter.Emit, OoEmitter.EmitInstanceInvoke/EmitUniversalInvoke (RETURNING), and PlaceRenderer's RefModPlace arm (ODO length before the ref-mod operands, §14.6.4 steps 6→7). Sweep every multi-receiver verb (STRING, CALL RETURNING, SORT/SEARCH) for the same re-render. GR-14.6.4-1 (locale identification first) is an evidence gap on the same model — a probe with a user function that SETs LOCALE inside a subscript.
