## Task brief (research 2026-09-30)

**Spec (cite-checked):** §14.6.13.2 5) "When the internal format of a dynamic-length elementary item is not correctly
formed or does not agree with the corresponding DYNAMIC LENGTH clause an EC-DATA-INCOMPATIBLE exception condition is
set to exist." (OK); 6) the same for "a dynamic-capacity table … does not agree with the corresponding OCCURS clause"
(OK); the clause's closing paragraph — "If the content of a sending operand is not referenced by a given execution of a
statement, any incompatible data in that operand is not detected" — and NOTE 2 (a receiving-only operand is not
referenced). EC-DATA-INCOMPATIBLE is fatal (Table 13); its ambient checking gate and raise helper already exist
(`ExceptionState.DataIncompatibleError`, the EC-DATA-INCOMPATIBLE ambient statement gate ~l.1371).

**Size: ONE SLOT (Sonnet).** Independent.

1. **Where a disagreement can arise — decide it structurally, not per site.** A dynamic-length item's content always
   agrees with the description that STORED it (`Store` truncates to `maxSize`). It can disagree only when the item is
   READ through a DIFFERENT description of the same storage: a LINKAGE formal (BY REFERENCE), a BASED item, an EXTERNAL
   record, a REDEFINES/RENAMES view, `SET ADDRESS OF`. Find the one place the emitter renders a SENDING read of a
   dynamic-length item (the `Place` read path for the dynamic-length class) and, for a place whose storage is not owned
   by this description (the same "cell-backed / linkage" test the place model already makes), wrap the read in
   `CobolDynString.Agree(value, maxSize)` — a new helper that calls `ExceptionState.DataIncompatibleError(…)` when
   `value.Length > maxSize` (the only agreement fact a UTF-16 string can violate — "not correctly formed" cannot happen
   to a managed string; say so in the helper's comment). Locally-owned storage emits no check (byte-identity), and a
   unit test pins WHY (every store path truncates).
2. Receiving-only references never check (NOTE 2); a MOVE into F then a read of F agrees again.
3. **Rule 6 (dynamic-capacity tables):** the registrar found no sharing path that produces a disagreement (EXTERNAL
   dynamic table is COBOLNET0899; a VLG CALL argument SR12; a fixed group into a FROM-5 VLG formal space-fills). Either
   add the same `Agree` check where a `CobolDynTable` is read through a foreign description, or — if the crossing
   normalization makes it unreachable — write that DETERMINATION into `docs/CONFORMANCE.md` and pin it with a drift test
   that enumerates the crossing paths (`CobolDynTable` construction sites) and asserts each normalizes to the
   receiving OCCURS. The note's row `GR-14.6.13.2-6` closes on either.
4. **Golden (in the edition directory of the existing dynamic-length goldens, e.g. `2023/pb165_dynamic_length_boundary`;
   check the construct's introduction edition in `constructs.json` first):** caller `LIMIT 10` holding `"ABCDEFGH"` (8) passed BY
   REFERENCE to a formal `LIMIT 4`; the callee does `MOVE F TO W4` (W4 PIC X(4) VALUE "....") then `DISPLAY "W4 [" W4
   "]"`, with the declarative displaying `HANDLED ` FUNCTION EXCEPTION-STATUS and `RESUME AT NEXT STATEMENT`. Expected:
   `HANDLED EC-DATA-INCOMPATIBLE` / `W4 [....]`. Control arm: the caller holds `"AB"` (2 ≤ 4) → `W4 [AB  ]`, no HANDLED.
   Unchecked twin: no raise (checking off, §14.6.13.1.1) — pin the continued value.
5. Rows: closes `GR-14.6.13.2-5` (and `-6` per step 3).
