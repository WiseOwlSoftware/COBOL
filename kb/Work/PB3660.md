# PB3660 — the lander misnames an older gate's record and prescribes a remedy that cannot work

**Sites:** `scripts/orchestrator/enqueue.py#tested_locally` (the `not head_tree or tree != head_tree` arm),
`scripts/orchestrator/enqueue.py#land` (step 1c, the `BLOCKED: enqueue — no local gate is recorded GREEN` remedy text),
`scripts/run_gate_legs.py#RECORD_SCHEMA` and the record it writes, both scripts' self-tests.

## What happened (resume unit, 2026-10-24 ~15:50 PDT)

Landing attempt `000086-20261024T224717Z-worktree-wf_1973801d-4fe-29` (PB2974, reviewed CLEAN) ended exit 14:

> UNTESTED — no gate run in …\wf_1973801d-4fe-29\TestResults\build-local covers 47e0205831e7 GREEN — 000004-20261024T221346Z:
> it measured a working tree that was not the committed head's (uncommitted changes); 000003-…: (same); 000002-…: (same)

and wrote into the branch's report: "A finisher runs `pwsh scripts/build-local.ps1 -Priority BelowNormal` on the tip".

Both statements are wrong:

1. **The tree WAS the committed head's.** Run 000004's `verdict.json` reads `head` 47e0205831e7 and `tree` bbc6a12f…, which
   is exactly `git rev-parse 47e0205831e7^{tree}`. What the record lacks is `head_tree` (and `linux`): it was written by
   the BRANCH's `scripts/run_gate_legs.py`, which predates PB3612 (#516) and records neither. `tested_locally` folds
   "no `head_tree`" into the dirty-tree arm (`elif not head_tree or tree != head_tree`), so an absent field is reported
   as uncommitted changes. The only dirt in that worktree was the harness's `.claude/settings.local.json`, which
   `measured_tree` already excludes (coord.NEVER_WORK).
2. **The remedy loops.** A finisher that gates the tip as told runs the branch's own pre-PB3612 driver again and
   writes the same record without `head_tree`, and the next landing refuses it with exit 14 again. The cure is to merge
   origin/main into the branch FIRST (bringing in the gate that writes the record this lander reads), then gate that
   merged head. The resume unit did exactly that by hand.

## The root cause

PB3612 changed the gate record's FORMAT (it added `head_tree` and `linux`, and the lander now requires both) but left
`RECORD_SCHEMA = 3`. The record is written by the branch's driver and read by main's lander, so any change to the format
strands every branch gated before it lands, and with the schema number unchanged the reader cannot even say why.

## The fix

- Bump `RECORD_SCHEMA` whenever the record gains a field the lander requires (here: 4), and pin the pairing with a
  self-test assertion: the lander's `tested_locally` names the minimum schema it accepts, and the driver's
  `RECORD_SCHEMA` meets it.
- In `tested_locally`, a record below that schema (or with no `head_tree`) gets its own reason: "written by a gate
  older than this lander (schema N < M; the branch's run_gate_legs.py predates <note>): merge origin/main into the branch,
  then gate the merged head". Keep "uncommitted changes" for `tree != head_tree` only.
- The step 1c `BLOCKED` text prescribes that merge-then-gate remedy when that is the reason, never "gate the tip".
- Sweep: every other reader of a field a newer driver writes (`plan_wave.Report.gate_state`, the GATE-PENDING check,
  `prune_worktrees` lifecycle text) for the same "absent field read as a failure of another kind".

## Reach today

Only branches gated before #516 landed are exposed. On 2026-10-24 the one such unlanded branch was
`worktree-wf_1973801d-4fe-29` (with `worktree-wf_1973801d-4fe-23`, whose two commits it contains), unblocked by hand as
above. The defect stays for the next record-format change.
