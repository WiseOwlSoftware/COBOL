# PB3930 — exception-object-not-supported: EXCEPTION-OBJECT refused: 'EXCEPTION-OBJECT' is a reserved word, but isn't supported

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S9) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\exception-object-not-supported.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\exception-object-not-supported\`.

## Summary

GnuCOBOL 3.2 refuses every reference to the predefined object reference EXCEPTION-OBJECT: `'EXCEPTION-OBJECT' is a
reserved word, but isn't supported`, followed by `'EXCEPTION-OBJECT' cannot be used here`. EXCEPTION-OBJECT is in
ISO/IEC 1989:2002 and 2014 and is not an optional element, so this is a missing feature of the edition
`-std=cobol2014` claims. Class: feature missing. It belongs with the object-reference gap recorded as
`universal-object-reference-not-supported--feature` (EXCEPTION-OBJECT is a universal object reference), but has its own
fix site (the reserved-word table) and its own diagnostic.

## Minimal test case

Free reference format (`-fformat=free`), 9 lines, written for this record. The night-2 witnesses fz02200 and fz03023
and the night-5 witnesses fz03905 and fz06018 stop at the same word.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. EXOBJ.
PROCEDURE DIVISION.
IF EXCEPTION-OBJECT = NULL
    DISPLAY "NULL"
ELSE
    DISPLAY "NOT NULL"
END-IF
STOP RUN.
```

File: `E:\COBOL-coord\scratch\op\pb3838\records\exception-object-not-supported.cob`.

The program is legal: EXCEPTION-OBJECT is a sending operand here (§8.4.3.6.3 1) forbids only a receiving use), and it
and NULL are both of class object, which may be compared (§8.8.4.2.15). No syntax rule restricts EXCEPTION-OBJECT to
declarative procedures (the general text, §8.4.3.6.1, says it "is used in a declarative procedure", which describes its
purpose).

## Environment

- `cobc (GnuCOBOL) 3.2.0`, Ubuntu package `gnucobol3 3.2-4build1`, WSL2 Ubuntu (x86_64) on Windows 11.

## Observed result

`-std=cobol2014`, exit code 1:

```
exobj.cob:4: error: 'EXCEPTION-OBJECT' is a reserved word, but isn't supported
    2 | PROGRAM-ID. EXOBJ.
    3 | PROCEDURE DIVISION.
    4 > IF EXCEPTION-OBJECT = NULL
    5 |     DISPLAY "NULL"
    6 | ELSE
exobj.cob:4: error: 'EXCEPTION-OBJECT' cannot be used here
```

The default dialect gives the same first error, exit 1.

## Expected result (per ISO)

The program compiles and prints `NULL`. ISO/IEC 1989:2023, each citation checked with `scripts/spec/cite.py --check`:

- §8.4.3.6.3 2): "EXCEPTION-OBJECT is implicitly described as class object and category object reference, as an
  external data item, and as a universal object reference."
- §8.4.3.6.3 1): "EXCEPTION-OBJECT shall not be specified as a receiving operand." (This use is a sending one.)
- §8.4.3.6.4 1): "EXCEPTION-OBJECT references the current exception object. If an exception object is not associated
  with the current exception, EXCEPTION-OBJECT is set to null." No exception condition has been raised and no exception
  object exists, so EXCEPTION-OBJECT is null.
- §8.8.4.2.15: "An operand of class object may be compared with another operand of class object." §8.4.3.7.3 2):
  "NULL is implicitly described as class object and category object reference". The relation is true.

Edition: EXCEPTION-OBJECT is in the 2001-12-04 text headed "ISO/IEC 1989:2002(E)" (its clause 8.4.2.6 of that text, with the same two
syntax rules) and in the 2009 committee draft CD 1.2 that led to 2014 (its clause 8.4.2.6 of that text). It is not an optional element in
the 2009 draft's list (its A.4) or in 2023's (§A.4.10 lists only multiple inheritance and parametric polymorphism).
GnuCOBOL's own reserved-word table tags the word as 2002.

Edition as recorded by the adjudicator: 2002 (carried into 2014). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Our compiler (WiseOwl)

WiseOwl COBOL (built from main 6ed90bd1c), `cobol exobj.cob --std 2014 --source-format free -o exobj.dll`, then

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/reserved.c`, the reserved-word table entry for EXCEPTION-OBJECT (line 1231): token -1, marked 2002; so
  `lookup_reserved_word` (line 4887) reports "'%s' is a reserved word, but isn't supported" (line 4902).
- `cobc/error.c`, `undefined_error` (line 1106): reports "'%s' cannot be used here" (line 1126) for the word that
  then fails to resolve.
- A fix needs a parser token and a predefined object-reference item, plus libcob support for the current exception
  object (none exists); it depends on the object-reference support missing in
  `universal-object-reference-not-supported--feature`.
