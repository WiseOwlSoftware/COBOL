# PB4512 — INITIALIZE ... TO VALUE edits an EDITED item's VALUE literal a second time (PIC XXBXX VALUE 'AB CD' becomes 'AB  C'), where §14.9.20.4 6) a) 3. asks for the item's initial value

**Found:** 2026-11-03 by the Sonnet-written fuzz batch; adjudicated WISEOWL-DEFECT (Opus adjudicator, billed to the API key), and its reduced repro re-run on a judge built from main a0e05167d (`fuzz_triage.py verify`) still shows it.

**The adjudicator's finding.** INITIALIZE ... TO VALUE moves the VALUE literal itself into an EDITED item, so editing is applied a second time: PIC XXBXX VALUE 'AB CD' becomes 'AB  C', PIC ZZ9.99 VALUE ' 12.50' becomes '250.00', PIC X/XX VALUE 'Q/RS' becomes 'Q//R'; expected the initial values (cobc gives them). Reduced repro t13 on the fresh judge: INIT [AB  C] [250.00] [Q//R], expected [AB CD] [ 12.50] [Q/RS]. No kb/Work note covers it (searched INITIALIZE x edited x VALUE phrase). Siblings to sweep: national-edited items, table-format VALUE occurrences (TableValuePlan arm, InitializeBinder.cs:377). Other lines of fz00489 (NUMERIC TO VALUE THEN REPLACING ALPHANUMERIC) are WiseOwl-correct per GR5 c) 2.; cobc ignores the REPLACING (not filed).

**The rule** (each marked checked by the adjudicator; re-run `cite.py --check` before writing one into code): §14.9.20.4 6) a) 3. 'The actual sending-operand is a literal that, when moved to the receiving-operand with a MOVE statement, produces the same result as the initial value of the data item' (checked)

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs`:580 (SenderFor, the ViaValue arm: InitializeValueOperand(raw) sends the raw VALUE literal through MOVE editing); the fix: `InitializeBinder.cs` (`ElementaryAction`, `ValueIsNotAMoveResult`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundInitialize.cs` (`InitializeStoreValue`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundStores.cs` (`InitStores`), `src/WiseOwl.Cobol.Compiler/Binding/Passes/UsageCollectionPass.cs` (`InitAct`), `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/InitializeEmitter.cs` (`EmitAction`)

**Landed.** Re-probed on a main bfbbec994 build: the repro printed `INIT [AB  C] [250.00] [Q//R]`, and the sweep found the same root in two siblings: a `JUSTIFIED RIGHT` receiver (`PIC X(5) JUSTIFIED RIGHT VALUE "AB"` initialized to `   AB`, the VALUE clause gives `AB   `, §13.18.63.4 GR7) and BLANK WHEN ZERO with an alphanumeric literal (`PIC ZZZ9 BLANK WHEN ZERO VALUE "0000"` initialized to spaces, GR8), plus `X/XX VALUE ALL "Q"` (`QQQQ`, which no literal moved to the edited receiver can produce). The root: GR6 a) 3. wants the result of the VALUE clause, and a MOVE of the raw literal edits, justifies and blanks what the VALUE clause does not. A receiver of an edited category or a JUSTIFIED one now binds `InitializeStoreValue`, rendered by `DataEmitter.ValueImageOf`, the one §13.18.63 recipe the declaration, the report section and `SET condition-name TO TRUE` already share. Goldens: `pb4512_initialize_to_value_edited_receivers` (2002), `pb4512_initialize_to_value_numeric_literal_in_edited` (2023), refusal `pb4512-initialize-to-value-below-2002`.
