# PB4512 — INITIALIZE ... TO VALUE edits an EDITED item's VALUE literal a second time (PIC XXBXX VALUE 'AB CD' becomes 'AB  C'), where §14.9.20.4 6) a) 3. asks for the item's initial value

**Found:** 2026-11-03 by the Sonnet-written fuzz batch; adjudicated WISEOWL-DEFECT (Opus adjudicator, billed to the API key), and its reduced repro re-run on a judge built from main 3c8b2845c (`fuzz_triage.py verify`) still shows it.

**The adjudicator's finding.** INITIALIZE ... TO VALUE moves the VALUE literal itself into an EDITED item, so editing is applied a second time: PIC XXBXX VALUE 'AB CD' becomes 'AB  C', PIC ZZ9.99 VALUE ' 12.50' becomes '250.00', PIC X/XX VALUE 'Q/RS' becomes 'Q//R'; expected the initial values (cobc gives them). Reduced repro t13 on the fresh judge: INIT [AB  C] [250.00] [Q//R], expected [AB CD] [ 12.50] [Q/RS]. No kb/Work note covers it (searched INITIALIZE x edited x VALUE phrase). Siblings to sweep: national-edited items, table-format VALUE occurrences (TableValuePlan arm, InitializeBinder.cs:377). Other lines of fz00489 (NUMERIC TO VALUE THEN REPLACING ALPHANUMERIC) are WiseOwl-correct per GR5 c) 2.; cobc ignores the REPLACING (not filed).

**The rule** (each marked checked by the adjudicator; re-run `cite.py --check` before writing one into code): §14.9.20.4 6) a) 3. 'The actual sending-operand is a literal that, when moved to the receiving-operand with a MOVE statement, produces the same result as the initial value of the data item' (checked)

**The code site:** src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs:580 (SenderFor, the ViaValue arm: InitializeValueOperand(raw) sends the raw VALUE literal through MOVE editing)
