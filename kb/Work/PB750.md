# PB750 — LANDED — a gate that had always tested the other compiler

Found 2026-09-06 by the battery #58 adjudicator (`b58/attribution.md`, finding 1) while explaining why the same
battery printed `guard NIST: 353 MATCH, 0 REGRESSION(S)` and `NistDifferentialTests_P0("NC215A") [FAIL]` about the
same tree.

## The facts

- `scripts/guard-fast.sh:28` and `scripts/guard.sh:39` set `CLI="src/CobolSharp.CLI/bin/Debug/net10.0/cobolsharp.dll"`
  and drive the NIST compile-and-run leg (and its audit) through it. `CobolSharp.Compiler.csproj` references only
  `CobolSharp.Runtime` and `Cobol.Net.Frontend`; `Cobol.Net.Compiler` (the Roslyn code generator) is not in its
  build graph. The leg is therefore structurally blind to every greenfield codegen defect.
- Edition, dialect and the legacy-differential switch are not the difference: both runners default NIST to `--std 85`
  and neither sets `COBOLSHARP_LEGACY_DIFFERENTIAL`. The two runners simply drive different compilers, and each
  reports the truth about the one it drives.
- The greenfield NIST evidence has always been the Conformance assembly's `NistDifferentialTests_P0…Pn` partitions,
  which is where PB741's regression appeared. Every battery record in plan §9 that quotes the guard's `NIST: … MATCH`
  line as evidence about COBOL.NET is, to that extent, a claim about the oracle.

## Why it matters

`feedback_green_gates_arent_evidence`: a passing check proves nothing if it never looked at what changed. The
battery's most prominent NIST line was a green over a compiler this project is retiring at P15, and the doctrine
names the legacy oracle a regression net with known holes, never authority. The guard's other legs (witnesses,
audit) inherit the same blindness wherever they run programs through `$CLI`.

## The fix shape

Point the guard's `CLI` at the greenfield `cobol` (`src/Cobol.Net.Cli`), keep the legacy run only behind the
existing opt-in differential switch, and make the guard's summary line NAME the compiler it drove
(`NIST (cobol): …`). Then reconcile: the guard's NIST run and the Conformance partitions should produce one
population and one verdict set — if both remain, assert they agree, or retire one (one mechanism per job). Pair it
with a check that fails when `$CLI` resolves to a binary whose assembly references do not include
`Cobol.Net.Compiler` (prove the watchdog fails once).

## Sweep

`grep -rn "CobolSharp.CLI\|cobolsharp.dll" scripts/ tests/ docs/` — every script and doc line that still routes a
gate through the legacy CLI is the same defect; plan §9's battery records need a one-line caveat until the leg is
redirected.

## Landed 2026-09-06

**Reproduced first, then fixed, and the two halves were observed side by side on ONE tree.** With the same nine
programs and the same build: `COBOLSHARP_LEGACY_DIFFERENTIAL=1` gives `NC215A: MATCH` and
`=== NIST (legacy): 7 MATCH, 0 REGRESSION(S) ===`, audit CLEAN; the default gives
`NC215A: DIFF — REGRESSION!` and `=== NIST (cobol): 8 MATCH, 1 REGRESSION(S) ===`. The defect is not that the
guard was wrong — it is that it was answering about the other compiler.

**The mechanism.** `scripts/guard-compiler.sh` is now the ONE place that answers "which compiler is this gate
measuring?", sourced by `guard.sh`, `guard-fast.sh` and `run-suite.sh`. It selects `cobol`
(`src/Cobol.Net.Cli`) by default and the legacy oracle only under the project's existing opt-in switch
`COBOLSHARP_LEGACY_DIFFERENTIAL=1`, and `guard_assert_compiler_identity` then **refuses to run** unless the
resolved binary's own `.deps.json` closure matches the claim — `Cobol.Net.Compiler` present for `cobol`, absent
for `legacy`. `--self-test` proves both refusals fire (it is run by `guard-verify.sh`, hence by `battery.sh`
phase 2a). Every summary line names the compiler: `=== NIST (cobol): … ===`, `=== FAILURES (cobol): … ===`,
`=== COMPILER UNDER TEST WAS: … ===`; `battery.sh` requires the `(cobol)` tag and reds without it.

**Three consequences the redirect forced, each a defect of its own had it been skipped:**
- `LEGACY_DIVERGENT` is emptied unless the run is the legacy differential. Those eleven goldens were
  re-baselined to the ISO-CONFORMING output *because the legacy is non-conforming there*; carrying the exemption
  into a `cobol` run would have skipped the comparison on the eleven programs a codegen regression is likeliest
  to break. Under `cobol` they compare — and IX111A/NC235A were observed MATCHing.
- `guard-nist-audit.sh`'s expected verdict is now derived PER COMPILER (a `divergent` row expects
  `LEGACY DIVERGENT` from the oracle, `MATCH` from `cobol`); an unknown compiler name is refused rather than
  silently audited against a default. Its `--self-test` grew four compiler-identity arms, all proven red first.
- `scripts/guard-compile.sh` holds the compile invocation once: `cobol` needs `--nist NAME` (its parser binds
  the next token, so `--nist prog.cob` consumes the SOURCE and the compile dies with "Required argument
  missing"), the legacy takes a bare `--nist`. Four call sites share it.

**Reconciliation — one population, two paths, kept honest mechanically.** The guard's NIST leg (CLI, separate
process, 376 in-scope programs, Linux/bash) and `NistDifferentialTests_P0…P5` (in-process `CompilerDriver`, 349
green∪divergent rows, both OSes) both remain, because neither subsumes the other. What is asserted is that they
are two views of `tests/nist/corpus.tsv`: `CorpusManifestTests` (new) requires the guard population ⊇ every
program the golden suite asserts, ⊆ the manifest, with a surplus of `pending` rows only, and that no guard
hard-codes a CLI path again — that last fact was shown RED by re-adding the old `CLI=` line.

**Residual, stated rather than hidden:** `guard.sh`'s `NIST_TESTS` is still hand-written, because that string
also encodes the SERIAL guard's run ORDER (producers before consumers; anti-dependencies like "no other TF022
writer between RL107A and RL117A") which `corpus.tsv` cannot express. It can no longer drift silently — the new
drift facts red on any divergence — but retiring it means giving the serial guard the parallel guard's
per-component isolation, or adding an order column.

## Verified end to end 2026-09-06

The redirect was finished and measured on one tree at `origin/main 1e7b5085`.

- **The whole leg, default arm:** `bash scripts/guard-fast.sh` →
  `=== NIST (cobol): 364 MATCH, 0 REGRESSION(S) ===`,
  `=== NIST AUDIT: CLEAN — every declared program produced exactly the verdict the manifest predicts ===`
  over `population=376`, legacy Unit 1203/1203, Integration 503/504 (1 skipped),
  `=== COMPILER UNDER TEST WAS: cobol (src/Cobol.Net.Cli/bin/Debug/net10.0/cobol.dll) ===`,
  `=== ALL GREEN ===`. `NC215A` — the wrong answer this note was opened over — is among the 364.
- **Both arms of the serial guard, one selector** `NC101A IX111A RL101A RL102A RL103A`. `IX111A` is a
  `LEGACY_DIVERGENT` program, so the two arms must disagree about it BY DESIGN, and they do:
  `GUARD_COMPILER=legacy` gives `IX111A: LEGACY DIVERGENT (golden = ISO-conforming baseline; expected diff)`
  with `=== NIST AUDIT (legacy) === … CLEAN`, and the default gives `IX111A: MATCH` with
  `=== NIST AUDIT (cobol) === … CLEAN`. Both `=== ALL GREEN ===`; each names its own run-scoped SNAPSHOT
  (`/tmp/nistguard.*/cli/cobolsharp.dll` vs `…/cli/cobol.dll`), so the identity assertion holds on the copy
  that actually runs, not only on the built binary.
- **The reconciliation is a MEASUREMENT, not a claim.** The guard's 376 verdict lines against a trx of
  `NistDifferentialTests_P0…P5` (+`CorpusManifestTests`), 358/358 passed: guard population 376,
  conformance 349, intersection 349, **DISAGREEMENTS 0**, conformance-only EMPTY, guard-only exactly the
  27 `pending` rows, and the guard's only 12 non-MATCH verdicts are all `NO BASELINE` — the golden-less
  rows the manifest predicts. That is the dynamic half of what `CorpusManifestTests` asserts structurally.
- Self-tests: `guard-compiler.sh --self-test` 14/14 (including the LEGACY dll REFUSED when `cobol` is
  claimed, and the mirror), `guard-nist-audit.sh --self-test` 16/16, `guard-verify.sh --witnesses` ALL GREEN.

⚠ **One reading was thrown away, and why.** The FIRST `guard-fast.sh` run on this same tree reported
`362 MATCH, 2 REGRESSION(S)` (`RL203A`, `SQ223A`). Both were FALSE: `cmp` proves each preserved report is
BYTE-IDENTICAL to its golden, and re-running each program's exact chain group serially gives `MATCH`. The
second full run of the unchanged tree is the `364 MATCH, 0` above. This is not PB750 and not codegen — it is
the residual of kb/Work/PB473 in the COMPARE arm, where the normalization is still a two-stage PIPE
(`tr | sed`) and a truncated result is indistinguishable from a difference; the mtimes prove the report was
complete four seconds before the comparison began, so it is not a partial write.
