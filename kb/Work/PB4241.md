# PB4241 — The §6.5 converter's own 'which division' reading (per physical line, before conditional compilation, skipping continuation lines, reading REPLACING operands) rejects legal source: a continued `PROCEDURE DIVI/-SION` header at 85/2002/2014, a `COPY ... REPLACING ==PROCEDURE DIVISION== BY ==X==` operand at 85, and an omitted `>>IF` branch spelling IDENTIFICATION DIVISION at 2023 each make the following comment-entry draw COBOL0001 or COBOL5563: the PB2739 rule is shared, the TEXT it reads is not

**Sites** (file:line at pin 84cdb410f, the review's): `ReferenceFormatProcessor.LogicalConversion.cs:192, :262 (CommentEntryOf / _division.Read)`; `DivisionCursor.cs:53-78`; `CopyProcessor.cs:738-758`.

**Evidence.** S7-refute probes r1b, r2b, r2e, r3b against their COPY twins r1a, r2a, r2d, r3a (which print correctly). The review also cites E.2 1) and §7.3.16.4 3); those citations could not be mechanically validated and are not relied on here.

**Direction.** Analysis before fix. PB2739 landed the shared rule; the text it reads differs between the converter and the COPY processor. The converter needs the division to decide comment-entry lines, which is why it reads early.

**Landed (wave 20261788 group E).** One root, three symptoms: the converter fed the one `DivisionCursor` rule the wrong TEXT. (1) It read each fixed-form line's own program-text area and skipped continuation lines, so `PROCEDURE DIVI` / `-SION.` was never a header; the cursor now reads the LOGICAL lines the `LogicalLineBuilder` has settled (`ReadInto`, asked where a new source line is about to be classified; both converters). (2) It read the words of a `COPY ... REPLACING ==PROCEDURE DIVISION== BY ...` operand (and of a REPLACE statement); the cursor now passes over a COPY or REPLACE statement itself, from its keyword to its separator period outside pseudo-text, across lines, which made `CopyProcessor`'s own `Skip` redundant and it is deleted (the COPY driver was also reading REPLACE operands). (3) It read branches conditional compilation omits (6.5 converts BEFORE conditional compilation, so it cannot see them); the cursor now follows `>>IF`/`>>EVALUATE` groups and counts a division word in a group only when every branch ends in the same division, else the text is taken for NO IDENTIFICATION DIVISION (review round 1, R1-3, replaced the first reading, which kept the pre-group division and so rejected a legal program whose SELECTED branch leaves the IDENTIFICATION DIVISION; docs/CONFORMANCE.md D-CE2). The determination is the implementor's: no edition has both a comment-entry and a `>>IF`, so the reading that rejects no standard program is the one that finds no comment-entry after an undecidable group. Its residue, named there: a non-standard COBOL-85 comment-entry directly after such a group is read as program text; the exact reading needs the comment-entry decision made after conditional compilation, a redesign of the stage order this note does not take. Goldens: 6.5-Logical-conversion/pb4241_continued_division_header, pb4241_continued_division_header_across_blank_line (R1-1), pb4241_copy_operand_names_division, pb4241_omitted_branch_division_header, pb4241_selected_branch_division_header (R1-3), pb4241_when_other_word_is_not_the_default (R1-2) (+ the 85 refusals pb4241_omitted_branch_division_header_at_85, pb4241_selected_branch_division_header_at_85, pb4241_when_other_word_is_not_the_default_at_85); unit tests: DivisionCursorTests. Review round 1 also fixed: a blank or comment line no longer asks the cursor to read the latest logical line (it is discarded and a continuation line after it still joins that line; `LogicalLineBuilder.TryFirstText`), and `>>WHEN OTHER` is recognised as a WORD by the one `CompilerDirectiveLine.StartsWithWord` the conditional-compilation stage also asks. Also fixed in the same arm: a fixed-form line that continues a floating-indicator literal (`AwaitsFloatingContinuation`) is no longer asked whether it opens a comment-entry, as the free-form converter already did.
