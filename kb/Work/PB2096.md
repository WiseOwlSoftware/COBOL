# PB2096 — a GLOBAL formal forwarded from a contained program loses its area

Filed 2026-10-05 by the train-1023 lander from the w1023a implementer report (PB2087 finisher, lead 3).

**Rule.** ISO §14.2.3 GR8: "If the argument is passed by reference, the activated runtime element operates as if the
formal parameter occupies the same storage area as the argument."

**Mechanism.** PB2089 (train 1023) gave a carrier-resident BY REFERENCE formal the area it arrived with
(`LinkageFormal.ArgumentAreaField`, `__lna{Uid}`), and a forward of the WHOLE formal passes it on
(`CallEmitter` forwarding arm, `src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs` ~645). The forward is recognized by
`CallEmitter.WholeFormal` (~839), which searches only `callState.Formals` — the unit's OWN formals. A contained program
that names its container's GLOBAL formal as a BY REFERENCE operand is not recognized, has no bridge to the container's
`__lna{Uid}` member (`DataBinder.GlobalBridgesOf` bridges the carrier, not the area), and crosses through the carrier
alone; an area formal (group, REDEFINED or addressed) of the next callee then gets a fresh cell, filled at entry and stored
back at return. On the w1023a branch the same lookup is `EmitterState.WholeFormalArea`, with the same limit.

**Repro.** A (`01 N PIC 9(4)`) `CALL "B" USING N`; B: `LINKAGE SECTION. 01 LF PIC 9(4) GLOBAL.` and a contained program C
that does `CALL "D" USING LF LF`; D: `01 LD-1 PIC X(4). 01 LD-1R REDEFINES LD-1 PIC 9(4). 01 LD-2 PIC 9(4).` stores 7
through LD-2 and DISPLAYs LD-1R — the copy shows the old value, and LD-1's copy-back at return undoes the store.

**Fix direction.** Bridge the area member with the carrier in `GlobalBridgesOf` (one residence row in
`GlobalBridgeResidenceDriftTests`), and make the whole-formal lookup see the GLOBAL formals in scope, not only the unit's.

## Landed 2026-10-07 (wave 1033 group B, w1033b)

**Re-probed on this tree first** (`E:\COBOL-coord\scratch\w1033b\p\gf.cob`, the repro above): `LD-1R=0001`, `N=0001`.
The same lookup also lost two more facts: a GLOBAL GROUP formal forwarded twice printed `LE-A=ABCD` and the argument
ended `ABXY` (the second copy-back undid the first store), and an omitted GLOBAL formal forwarded from a contained
program arrived PRESENT, so §8.8.4.8.4 GR1c's transitive omission was broken too.

**Fix, both halves the note named.** (1) `DataBinder.GlobalBridgesOf` bridges a carrier-resident BY REFERENCE formal's
argument area (`CallBridgeKind.ArgumentArea`, `ref CellPointer? __lna{Uid}`) beside its carrier. (2) The recognition
of a forwarded formal sees every formal in scope: each bridge that reaches a container FORMAL names it (`CallBridge.Formal`
on the Carrier, ArgumentArea and an area formal's Address bridge), `BoundUnit.InheritedFormals` reads them off the bridges,
and `ProgramEmitter` sets `CallUnitState.Formals` to the unit's own formals plus those. The member names are Uid-keyed and
bridged under the same names, so `CallEmitter.WholeFormal`, `CallUnitState.WholeFormalArea` and `WholeFormalProbe` render
a GLOBAL formal's carrier, area and presence exactly as the container would. The INVOKE lane asks the same three, so a
contained program's INVOKE with a GLOBAL formal is fixed by the same change.
§13.18.27.4 GR2 is why the forward is the formal itself: the contained program "may reference that name without describing it again"
(`cite.py --check 13.18.27.4` gives OK §13.18.27.4 2)).

**Witness.** `conformance:2002/pb2096_global_formal_forward_area`: the note's repro, a GLOBAL group formal forwarded twice to
an elementary and a group area formal, and an OMITTED argument forwarded through a contained program. Expected values were
derived from GR8 and GR1c before the run, and the run matched. No `GlobalBridgeResidenceDriftTests` row: the area is a second
member of the existing carrier-resident residence (row 8), not a new residence, and that matrix's shape (read, store, see the
store) cannot express a forward; the golden pins the forward.
