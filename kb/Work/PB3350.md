# PB3350 — the frame index is O(records) memory

Filed 2026-10-17 by the clerk from `w1111c-PB3339-report.md` "New defects (note-ready)", second bullet's last sentence
(`RecordFraming.cs:568` `FrameStarts` uses O(records) memory for backward READ). The line number moved: on origin/main
8307a2143 the member is at `src/Cobol.Net.Runtime/IO/RecordFraming.cs:589`. No wrong answer; a memory and scaling cost.

PB2754 (landed) unified the four varying-frame decoders and names `FrameStarts` as one of them; it fixed WHAT a frame is,
not how many offsets are kept. PB802 (landed) only records that the prefix is shared. PB2692 (landed) bounded the walk by
`from`/`to` for the append count. Grep of kb/Work for `_varyingStarts` and "O(records)" finds only PB2754. No open note
covers the memory.

## Mechanism and sites
- `RecordFraming.cs:589` `FrameStarts(Stream fs, long from, long to)` adds the start offset of EVERY frame in [from, to) to
  a `List<long>` (8 bytes per record plus list growth): a 100-million-record file holds about 800 MB (a doubling list can
  transiently hold twice that).
- `SequentialConnector.cs:1621` `_varyingStarts ??= RecordFraming.FrameStarts(stream)` keeps the whole list for the life of
  the open (field at line 93, reset at line 1013), for a backward READ (§14.9.30.4 GR21) that needs one offset at a time.
- `SequentialConnector.cs:488` `CountRecords` calls `FrameStarts(fs, from, to).Count`: the list is built only to take its
  count, although the walk needs no storage at all.

## The design is written — `docs/rearchitecture/DESIGN-runtime-library.md` 2.2.3 (kb/Work PB3426, 2026-10-19)

Implement FROM 2.2.3 (CLAUDE.md rule 2): one walk, two products — `RecordFraming.CountFrames` (a count, no storage) for
`CountRecords`, the OPEN EXTEND base and the REVERSED count; `FrameIndex` (a checkpoint per 4096 frames plus a window of at
most 4096 exact starts) for the backward READ, built for free by the forward walk and by one counting walk for a target
beyond it; `SeekToRecord` the one reposition; the drift test and the byte-identical GR21 and REVERSED goldens. The "Fix shape"
below is the sketch 2.2.3 decided; 2.2.3 wins where they differ.

## Fix shape
Two consumers, two shapes, one walk (`ReadStreamFrame` stays the one decoder):
1. A counting walk that returns the number of frames in [from, to) without a list (`CountRecords`).
2. For the backward READ, an index that does not grow with the file: keep a position cursor (the current ordinal and its
   start) and step back one frame by walking forward from a bounded checkpoint (a sparse index, one offset per N records),
   or by reading the trailing length word if the format is ever given one. Choose by the PB352 `SeekToRecord` contract:
   the reposition is still the one primitive.
A structural guard, not a wall-clock test: a drift test that `CountRecords` never allocates a per-record collection (an
allocation count over a generated file, or the absence of `List<long>` in its call chain).
