# PB852 — LANDED — the report SOURCE operand is an identifier and only an identifier

Source: the `PB506` implementer report, "New defects found outside this mechanism" item (A). PB506's own
mechanism is the format-4 VALUE lane; the implicit COMPUTE was deliberately left out of its scope and said so in
the grammar comment.

## Repro — re-run on this tree, `--std 2023`

`scratchpad/reg4/probe/p15c_source_arith.cob` and `p15d_source_rounded.cob` (PROGRAM-IDs `R4P15C` / `R4P15D`),
each a report description with a TYPE DE group:

```
p15c:  03 COLUMN 1 PIC 9(3) SOURCE IS (WS-A + WS-B).
       (17,42): error COBOL0001: no viable alternative at input '('
       (17,48): error COBOL0307: unexpected '+'. ...
p15d:  03 COLUMN 1 PIC 9(3) SOURCE IS WS-A ROUNDED.
       (17,47): error COBOL0307: unexpected 'ROUNDED'. A period may be missing at the end of the previous sentence.
```

## The rule, quoted

```
$ python scripts/spec/cite.py --check 13.18.53.4 "Arithmetic-expression-1 specifies the operand of an implicit COMPUTE statement that is executed implicitly whenever the associated item is printed."
  OK  §13.18.53.4 2)  (General rules)
```

§13.18.53.2's general format is `{ SOURCE IS | SOURCES ARE } { identifier-1 | arithmetic-expression-1 } ...
[ rounded-phrase ]`, and §13.18.53.3 SR3, SR5 and SR7 exist ONLY for the arithmetic-expression operand (SR7:
"If the SOURCE clause has more than one operand of which at least one is an arithmetic-expression, each operand
shall be enclosed in parentheses"). With no surface, those three syntax rules plus GR2 — and the COMPUTE half of
GR3 — have no reachable population; the rows are claimed here so that stays visible.

## Code sites

`src/Cobol.Net.Frontend/Grammar/Core/CobolReportWriter.g4#reportSourceClause` (the `dataReference+` list covers
identifier-1 only); the emitter needs a `FieldComputeSource` beside `FieldDataSource` in
`src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs` and an `ArithmeticEmitter` render in
`ReportWriterEmitter.FieldImage`.

## Sibling sweep the fixer owes

* The SUM clause's `UPON` and the `rounded-phrase` in the SUM clause share the ROUNDED model — one
  rounded-phrase parse rule, not two.
* §13.18.53.3 SR7's parenthesization rule is a SYNTAX rule about operand lists and must be enforced, not assumed
  from the grammar's shape.
* ROUNDED carries the full §14.6.11 rounding-mode phrase (`ROUNDED MODE IS ...`); the report clause inherits it,
  so reuse the statement-level parse rule rather than writing a second one.

## Landed - 2026-09-19, wave 39 (group REPORT-WRITER-SUM)

`status: landed`. The SOURCE clause's `arithmetic-expression-1` operand and its ROUNDED phrase have a grammar
surface, written ONCE and shared with the SUM clause exactly as the note's sibling sweep required: one
`reportValueOperand` production, one `roundedPhrase?` per clause - the SHARED S14.7.4 rule, not a second copy,
which is how the report clauses acquire the 2014 `MODE IS` introduction gate with nothing written down twice
(`tests/conformance/negative/pb852-source-rounded-mode-below-2014.cob`). S13.18.53.4 GR2's implicit COMPUTE is
`FieldComputeSource`, bound in the procedure phase through the one `ExpressionBinder.BindExpr` and rendered
through the one `MoveEmitter.ConvertSource` with the clause's rounding mode threaded. SR7 is ENFORCED
(COBOLNET2142), not assumed from the grammar's greedy shape, as the note demanded; SR3 is COBOLNET2141 and the
SR4 section rule COBOLNET2144. `SR-13.18.53.3-3`, `-5`, `-7` and `GR-13.18.53.4-2` recorded CONFORMS.

WARNING - the `ArithmeticEmitter`-render shape the note predicted turned out not to be the right one: the
COMPUTE's receiving operand is the printable item, so the transfer IS the conversion every other operand already
takes, and threading a rounding mode into it was smaller and kept ONE mechanism instead of two. The design doc
records the corrected shape.
