# PB5739 - buildgraph.py reads git ls-tree -r -z --full-tree through subprocess with no time limit: when the reader thread hit MemoryError under host memory pressure, git blocked on its full pipe and the gate hung with no verdict

**Sites:**
- `scripts/buildgraph.py#tree_entries` (`subprocess.run(["git", "ls-tree", "-r", "-z", "--full-tree", tree], ..., capture_output=True)`, no `timeout`)
- `scripts/buildgraph.py#Published.read` (`_git(repo, "ls-tree", "-r", "-z", "--full-tree", commit)`, the store ref's listing, the same shape)

**What happened.** Gate run 000001 of branch `record-2023-pb5678-and-case-collision` (2026-11-15), under the host memory pressure
kb/Work PB5697 records, hung with no verdict: the thread reading `git ls-tree`'s output raised MemoryError, nothing drained
the pipe, git blocked writing to it, and `subprocess.run` waited on git forever. The gate printed no `=== BUILD-LOCAL GATE: `
line, so a waiting implementer could not tell a hang from a slow run.

**The defect.** A tree listing of the whole repository is read with no bound on time and no failure path when the reader
dies: an input the tool cannot read must fail loudly (a red with its cause), never wait. The fix: one helper for every git
call of `buildgraph.py` with a time limit and a kill of the child on any exception in the reader, so the gate ends red
naming the command; and a self-test that plants a reader failure and sees the red. Sweep: every other `subprocess.run` /
`_git` call of the gate's scripts (`gate.py`, `buildgraph.py`, the landing's checks) with `capture_output` and no `timeout`.

**Repro.** Not reproduced in this job (HOST SAFETY: no program whose point is to exhaust memory is run on this host). The
evidence is the hung run's record of 2026-11-15; a self-test can plant the failure by making the reader raise.
