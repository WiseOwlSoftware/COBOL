# PB3935 — binary-usage-over-18-digits-refused: USAGE BINARY with more than 18 digits refused ("binary field cannot be larger than 18 digits"); ISO 2002/2014 allow 31

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S10) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\binary-usage-over-18-digits-refused.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\binary-usage-over-18-digits-refused\`.

## Summary

GnuCOBOL 3.2 refuses `01 B PIC S9(3)V9(20) BINARY VALUE 1.5.` with `'B' binary field cannot be larger than 18 digits`.
The PICTURE has 23 digit positions. ISO/IEC 1989 allows 1 through 31 digit positions for a numeric item
(§13.18.40.3 14)) and requires the implementor to allocate enough storage for a BINARY item to hold the full range
its PICTURE implies (§13.18.60.4 4)). Both rules are in the 2002 and 2014 editions. The 18-digit ceiling is the
COBOL-85 limit and refuses legal 2014 source. GnuCOBOL's TODO lists "Finish USAGE BINARY for sizes > 18 digits"
(item 3.2.2 of the 3.2 tree's TODO file, which the draft cites). Expected, the compiled program DISPLAYs the value 1.5
in the 23-digit form of the item, not the text `1.5` (corrected by the refuter).

## Expected result (per ISO)

The program compiles, and DISPLAY shows the value +1.5 in the 23-digit form of the item. The exact DISPLAY rendering
of a signed non-display numeric item is not what this record is about.

- §13.18.40.3 14) (checked): "For data items of category numeric, and for fixed-point data items of category
  numeric-edited, the number of digit positions described by character-string-1 shall range from 1 through 31."
- §13.18.60.4 4) (checked): "The USAGE BINARY clause specifies that a radix of 2 is used to represent a numeric item
  in the storage of the computer. ... Sufficient computer storage shall be allocated by the implementor to contain
  the maximum range of values implied by the associated decimal picture character-string." The representation is
  the implementor's choice, but the range is not.
- §4.2.15 (checked), Limits: "In general, standard COBOL specifies no upper limit on such things as the number of
  statements in a compilation group ... A conforming implementation may place such limits." That latitude covers
  quantities the standard leaves open. It does not cover this one, because the standard fixes the digit range at 1
  through 31 and requires BINARY storage for the full range.

Edition: both rules are in ISO/IEC 1989:2002 (post-ballot text: "For data items of category numeric and
numeric-edited, the number of digit positions described by character-string-1 shall range from 1 through 31"; and
"Sufficient computer storage shall be allocated by the implementor to contain the maximum range of values implied by
the associated decimal picture character-string"). Both are also in the 2009 committee draft that became the 2014
edition. Annex E of 2023 records no change. The 18-digit ceiling matches COBOL-85's maximum for numeric items. That
is stated from general knowledge, not quoted: the repository holds no 1985 text.

Edition as recorded by the adjudicator: 2002 (carried into 2014 and 2023). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Class

GNUCOBOL-DEFECT: legal source of the claimed edition (2014; the rule dates from 2002) refused. The limit is an
implementation ceiling below the standard's required range. It is not a feature GnuCOBOL lacks outright, since
BINARY items of up to 18 digits work.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/field.c`, function `compute_size` (starts line 2822), case `CB_USAGE_BINARY` / `CB_USAGE_COMP_5`
  (lines 3078 to 3097). The active branch refuses `size > 18` with this diagnostic and clamps the size to 18. An
  `#if 0` branch ("RXWRXW - Max binary") would instead allow up to `COB_MAX_BINARY` (39, `libcob/common.h` line 610).
- In the same switch, `CB_USAGE_COMP_X` / `CB_USAGE_COMP_N` already size up to 16 bytes (36+ digits), so field
  storage beyond 8 bytes exists. A fix needs `compute_binary_size`, the libcob binary move and arithmetic paths
  (`cob_binary_*`), and display conversion to handle binary fields wider than 64 bits.
- `config/cobol2014.conf` line 92, `binary-size: 1-2-4-8`. The dialect's storage-size choices stop at 8 bytes. They
  would need a wider step (for example 16) for a 23-digit item.
