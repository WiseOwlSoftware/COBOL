# PB813 — OPEN — an accepted paragraph that does nothing is worse than a rejected one

Filed 2026-09-09 by the registrar (second pass) from the **PB365 implementer's report** ("New defects" (a)) —
`scratchpad/reports/PB365-report.md`. **Re-probed on this worktree's own build at `d3ba5795`, and the report's
own citation was re-run rather than inherited** (the report says in as many words that `cite.py --check 12.3.3`
had *not* yet been run on that text).

## The measurement — BOTH definitions, not just the one the report named

```
$ cobol.exe p06_repo_in_object.cob  --std 2023 --run   ->  DONE      exit 0, zero diagnostics
$ cobol.exe p06_repo_in_factory.cob --std 2023 --run   ->  DONE      exit 0, zero diagnostics
```

(`registrar2/probe/p06_repo_in_object.cob` and `…_in_factory.cob`: a class whose `OBJECT.` — respectively
`FACTORY.` — paragraph carries a complete `ENVIRONMENT DIVISION. CONFIGURATION SECTION. REPOSITORY. CLASS …`.)
The report measured the instance definition; the **factory definition is the second arm** and it is equally
unscreened (`feedback_two_arm_dispatch`). SR3 names both, so a fix that screens one leaves the rule half-written.

## The rule, quoted, with the `--check` line actually run

```
$ python scripts/spec/cite.py --check 12.3.3 "The SOURCE-COMPUTER, OBJECT-COMPUTER, and REPOSITORY paragraphs shall not be specified in a factory definition or an instance definition."
OK  §12.3.3 3)  (Syntax rules)

```

## Expected vs observed

| | expected | observed |
|---|---|---|
| REPOSITORY in an `OBJECT.` definition | a diagnostic naming §12.3.3 SR3 | accepted, silent, **inert** |
| REPOSITORY in a `FACTORY.` definition | a diagnostic naming §12.3.3 SR3 | accepted, silent, **inert** |

**Inert is the harm.** `OoRepositoryScope` and every other reader resolve against the *class definition's*
REPOSITORY, so the accepted paragraph contributes nothing. A programmer who declares a class name only in the
OBJECT paragraph is then told, by §8.4.6.4, that the name is unknown — a diagnostic that points at the reference
instead of at the paragraph the standard forbids. Accepting illegal source is bad; accepting it and then
blaming the user's *legal* reference for the consequence is the shape that costs a debugging session.

## Code site

- Grammar admits it: `src/Cobol.Net.Frontend/Grammar/Core/CobolOO.g4:33-40` (`factoryParagraph`) and `:61-68`
  (`objectParagraph`) each carry `environmentDivision?`. The grammar is a deliberate superset here — the screen
  belongs in the binder, not in the `.g4`.
- Enforce it beside its twin: `src/Cobol.Net.Compiler/Binding/DataBinder.Oo.cs:145-153` already enforces
  §12.3.3 **SR2**, the METHOD-definition form, in the COBOLNET1519 family. One rule, one place
  (`feedback_one_rule_one_place`): SR2 and SR3 are the same sentence over three definition kinds and should be
  one screen taking the definition kind as a parameter, not two.
