# PB1761 — LANDED — the declarative-completion model

## The rules (cite-checked)

| § / rule | Text (abridged, verbatim where quoted) | What it asks of the runtime |
|---|---|---|
| §14.6.13.1.2 1) | "An EXIT PROGRAM, GOBACK, RESUME, or STOP statement that is specified in this function, method, or program is executed, or a fatal exception occurs within the scope of the declarative." | A per-ACTIVATION flag: "something made this declarative not complete normally" — set by a RESUME (even one GR1 turns into a CONTINUE) and by a fatal raise anywhere in its dynamic scope, not only by the control transfer. |
| §14.9.33.4 1) | "If the RESUME statement is executed within the scope of execution of a global declarative, it is the equivalent of the execution of a CONTINUE statement." | No transfer — but the RESUME was still EXECUTED, so the declarative still did not complete normally (row above). |
| §14.9.49.4 13) a) / b) | a) "If the exception condition is not fatal, control is returned to an implicit CONTINUE statement following the statement whose execution caused the exception." b) "If the exception condition is fatal, execution continues as specified in 14.6.12, Abnormal run unit termination." | After a Format-3 non-EC-I-O USE procedure that FALLS OFF ITS END the disposition is by fatality, whatever the normal-completion flag says. So for a plain raise site a not-normal fall-off behaves exactly like a normal one. |
| §14.6.13.1.3 5) | "If execution of the declarative completes normally the execution of the run unit is terminated abnormally" | Consistent with GR13 b) above — no rule makes a not-normal FALL-OFF continue. |
| §14.9.40.4 17) | "If a USE procedure invoked while a format 1 SORT statement is active does not complete normally, the SORT statement is terminated." | The ONE place the flag changes behaviour: the SORT. |
| §14.9.24.4 7) b) 1. (and GR12's siblings) | "If there is an applicable USE procedure that completes normally, the MERGE statement continues." | MERGE's implicit transfers: not normal ⇒ the MERGE is terminated. |

**What this settles for the defect notes.** PB1122's premise is RIGHT as a model gap but its consequence is NARROWER
than its title suggests: at an ordinary raise site the not-normal fall-off is disposed of by §14.9.49.4 GR13, which
does not look at normal completion — MEASURED: `p1122f.cob` (a fatal EC-SIZE-OVERFLOW selecting D1, whose body's
checked EC-BOUND-SUBSCRIPT is RESUMEd by D2) prints `D1-START / D2 EC-BOUND-SUBSCRIPT / D1-END` then terminates
abnormally, and that termination IS what GR13 b) requires. The flag is observable only where a rule keys on
"completes normally": SORT GR17 and MERGE GR7/GR12 (and the Format-1 I-O GR7 a) / Format-3 GR12 a) "invoked from a
MERGE or a SORT statement" arms that defer to them).

## What the code does today

- `src/Cobol.Net.Compiler/CodeGen/DispatchEmitter.cs#EmitRunUseBody` — the EC-model `__RunUse` catches `ResumeSignal`
  (returns its target) and otherwise `return -1;   // normal completion (§14.6.13.1.2)`. Nothing records a fatal
  raise inside the range; a raise handled by a nested declarative's RESUME leaves no trace.
- `src/Cobol.Net.Compiler/CodeGen/EcEmitter.cs#EmitResume` — `throw new ResumeSignal(...)` unconditionally (PB1160).
- The dispatch-result protocol (`-1` normal · `-2` RESUME NEXT · `-3` no handler · `-4` handled nonfatal · `≥0`
  RESUME AT pc — `ResumeSignal.NextStatement` / `ResumeSignal.HandledNonfatal`, documented in
  `COBOLNET_CONDITIONS_EXCEPTIONS_DESIGN.md` "The declarative dispatch-result protocol") is consumed as BARE LITERALS in
  emitted strings at: `EcEmitter.cs` (the `__IoCheckEc` body ~l.871/876/898–916, `__RunF3` ~l.988, the propagation
  `== -3` ~l.94), `EmitterState.cs` (`ResumeTransfer` ~l.241, the raise-resume leg ~l.277), `SequentialIoEmitter.cs`
  (`EmitUseHook` ~l.92–107, whose `notNormalLabel` is the SORT/MERGE implicit-transfer landing), `CallEmitter.cs`
  (`EmitPropagationPickup` ~l.354). Adding a result value today means finding every literal by hand — the shape
  CLAUDE.md rule 5 forbids.

## The proposed single structure

1. **`DispatchResult` — the protocol as ONE named runtime type** (`src/Cobol.Net.Runtime/Exceptions/DispatchResult.cs`):
   constants `Normal = -1`, `ResumeNext = -2`, `NoHandler = -3`, `HandledNonfatal = -4`, and the new
   `NotNormal = -5` ("fell off its end, but §14.6.13.1.2 1) says it did not complete normally"), plus the predicates the
   consumers actually ask — `IsTransfer(r)` (`r >= 0`), `SuppressesFatal(r)` (`ResumeNext` or a transfer),
   `TerminatesSortMerge(r)` (`ResumeNext` or `NotNormal` — GR17 / MERGE GR7), `RanAHandler(r)`. `ResumeSignal.NextStatement`
   and `ResumeSignal.HandledNonfatal` MOVE here — every caller changes, no forwarding constant is left behind (CLAUDE.md
   rule 4). Every emitter renders the names, never the numbers.
2. **The declarative activation record** — `ExceptionState` gains a run-unit stack of open DECLARATIVE activations
   (run-unit scoped because "within the scope of the declarative" is dynamic and crosses CALL). `__RunUse` pushes one
   for a declarative id (`__id < DeclCount` — the F3 PERFORM handler ids are not declaratives, the same split
   `FlowUseError` already makes) and pops it in its `finally`. Two events mark EVERY open frame not-normal:
   a FATAL condition RAISED (the `ExceptionState.Set(name, fatal: true, …)` funnel — "occurs" read as "is raised",
   i.e. checking enabled; with checking off nothing exists to occur, §14.6.13.1.1), and a RESUME executed under
   §14.9.33.4 GR1 (the CONTINUE arm, PB1160). On fall-off `__RunUse` returns `NotNormal` when its frame is marked,
   else `Normal`. (A RESUME that transfers already returns its action; its frame needs no mark.)
3. **Consumers** map `NotNormal` per the table: every ordinary raise site / I-O hook treats it exactly as `Normal`
   (§14.9.49.4 GR13, GR7 b)/c), GR12 b)/c)); the SORT/MERGE landing (`EmitUseHook`'s `notNormalLabel`) treats it as
   `ResumeNext` via `TerminatesSortMerge`; the Format-4 object declarative (§14.6.13.1.5 names only the normal case)
   treats it as `Normal` — a documented implementor reading, recorded in `docs/CONFORMANCE.md`.

**Drift test (the "automatic stays automatic" half).** `DispatchResultProtocolDriftTests`: (a) no emitter source file
under `src/Cobol.Net.Compiler/CodeGen/` contains a dispatch-result comparison against a bare negative literal inside
an emitted string (regex over `== -[1-9]` / `!= -[1-9]` / `return -[1-9]` inside string literals, with an explicit
allow-list for non-protocol uses such as `StringEmitter`'s `cnt >= 0`); (b) every `DispatchResult` constant is named
by at least one consumer predicate. Prove it fails once by re-introducing one literal.

## Landed 2026-10-01 (wave 1001 group A, w1001a)

The model is realized end to end: PB1122 Task A (`DispatchResult`), PB1160 (the GR1 CONTINUE-RESUME and the SR2 ordering)
and PB1122 Task B (the declarative activation record and `NotNormal`). Deviations from the proposal above, each recorded
where it lives: the mark records the owner (`__useActive`) so a no-op RESUME marks only its own program's records while a
fatal raise marks every open record (docs/CONFORMANCE.md §3); `FinishesStatement` was added beside the briefed
predicates because `NonfatalIfEnabled` tested `Normal`/`NoHandler` directly; and the SORT-based golden the briefs sketch
is unreachable (a SORT's implicit transfers over sequential files only produce FATAL unsuccessful statuses, which
terminate whatever the declarative did), so the golden is the MERGE GIVING fatal-OPEN cell
(`conformance:2002/pb1122_declarative_fatal_in_scope_merge`). PB1177's explicit-statement arm (a USE invoked by a
statement INSIDE an input/output procedure) remains its own open note and consumes `TerminatesSortMerge`.
