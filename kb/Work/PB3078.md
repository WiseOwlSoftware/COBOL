# PB3078 — the repository moves to the WiseOwlSoftware organization

## The finding (2026-10-11 18:44 PDT, Mythos session, the second `ruleset.py apply` on the owner's 16:27 go)
With the committed pair fixed (ruleset-settings-PB3024, on main in train 1064 at dfb0a611d) the repository PATCH went
through — the live repository now has `allow_auto_merge`, `merge_commit_title=MERGE_MESSAGE`, `merge_commit_message=
PR_TITLE`, `delete_branch_on_merge` — and the ruleset POST was refused:
`gh api --method POST repos/BrentRector/COBOL/rulesets` → HTTP 422 `Validation Failed`, errors `["Invalid rule
'merge_queue': "]`, no parameter named (every committed parameter is inside GitHub's documented ranges). Nothing else
changed: `ruleset.py check` = ABSENT (exit 3), the classic protection stands (`ci-gate`, `enforce_admins`), every land
unit keeps `push-main.sh`.

The cause is the platform, not the rule: GitHub's merge queue is available in public repositories owned by an
ORGANIZATION and in private repositories owned by organizations on GitHub Enterprise Cloud — never in a repository
owned by a personal account (GitHub Docs, "Managing a merge queue"; the same 422 is reported from other user-owned
repositories). `BrentRector/COBOL` is owned by the personal account (`owner.type` User, public). No parameter and no
plan on the personal account can make the `merge_queue` rule valid there.

## The owner's decision (AskUserQuestion, 2026-10-11 ~18:50 PDT)
Asked as one bare question with three options — transfer the repository to WiseOwlSoftware (recommended), keep landing
through push-main with no merge queue, or decide later — the owner chose: **"Transfer the repository to WiseOwlSoftware
(Recommended)"**. The WiseOwlSoftware organization (free plan; the owner is its admin; `WiseOwlSoftware/COBOL` is free)
qualifies because the repository is public.

## What the transfer does and does not change (GitHub's transfer semantics)
- Moves with the repository: issues, pull requests, the wiki, stars and watchers, the repository webhooks (the CLA
  Assistant hook on `pull_request` and `merge_group`), the classic branch protection, Actions workflows and runs,
  releases. Secrets: none exist. Deploy keys: none. Collaborators: the owner only.
- GitHub redirects the old name (`BrentRector/COBOL`) to the new one for git, the web and most of the API, exactly as
  the 2026-09-26 rename did, so every running worktree, `push-main.sh` (which reads the repository from `gh repo view`)
  and `ruleset.py` (the same) keep working before the remotes are re-pointed.
- Does not move: GitHub Packages (none used), the personal account's other repositories (`BrentRector/COBOL-private`,
  the licensed-PDF submodule, and `BrentRector/claude-skills`, the public skills submodule, stay where they are).
- Organization settings that may need the owner: the org's Actions policy ("allow all actions" is the default for a
  new free organization) and the default workflow token permissions; the API to read them needs the `admin:org` scope,
  which the session's `gh` token does not carry. The first CI run after the transfer is the check.

## Why not the alternatives
Keeping push-main forever would retire PB3024 phase 2 and `enqueue.py` after they were built and reviewed, and keep the
landing lease as the only serialization; the owner's 2026-10-11 decision is maximal productivity and minimal cost for
the pipeline, which the queue serves (the merge group runs the whole population once per queued landing, off the
operator's critical path). A second personal repository or a mirror cannot host a queue either.
