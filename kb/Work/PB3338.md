# PB3338 — the compiler's APPLY COMMIT

The hold is mechanical: `status: owner` puts "status: owner" in this note's `waiting_on` (`work.py` `cluster_order`), and `plan_wave.py` plans no note with a waiting entry, so no wave dispatches it until the owner's decision sets the status back to open.

Implement FROM `docs/rearchitecture/DESIGN-runtime-library.md` §2.2.1.10 ("The compiler half") and the spec clauses named in

## Mechanism

- Binding: `DataBinder` binds the APPLY COMMIT clause (§12.4.6.3.3 SR1-SR11: the file-names of the FILE-CONTROL paragraph, no
  sort-merge or report file, 01/77 items of the three sections, no reference modification, not in a recursive element nor a
  class/factory/interface, no object references, GR2's external-file-connector rule for a connector named in several elements,
  SR9's automatic inclusion of file status, LINAGE and RECORD items, SR10's BASED exclusion); a LOCK clause or an UNLOCK on such a
  file is refused (§9.1.16, the implicit AUTOMATIC WITH LOCK ON MULTIPLE RECORDS posture).
- Codegen: at the runtime element's activation, `RegisterCommitControl` for each listed connector (§12.4.6.3.4 GR5's "active");
  COMMIT → snapshot the listed data items into the element's commit image, then `FileRegistry.Commit()` (§14.9.7.4 GR3/GR5);
  ROLLBACK → `FileRegistry.Rollback()` then restore the image (§14.9.36.4 GR3, the canceled/exited exclusions of GR4-GR6);
  `BoundCommitRollback` stops being CONTINUE where an APPLY COMMIT clause is active (`conformance:cases/14.9.7-COMMIT/pb137_commit_inert` keeps
  pinning the no-clause case, §14.9.7.4 GR1 / §14.9.36.4 GR1). The abnormal paths: a fatal exception condition on a file under
  an active APPLY COMMIT clause executes a ROLLBACK unconditionally (§14.6.13.1.3 item 8), and the run unit's abnormal
  termination executes the FILE-ONLY rollback (§14.6.12: files restored, the data items not) through `FileRegistry.Rollback()`
  before the process exits; a termination the runtime cannot reach (a kill) is rolled back at the first writable entry or the
  first lock test that meets one of its holdings (PB3337, rounds 3 and 4). A COMMIT is decided by its promotion's slot
  write and ANSWERED only by the sync after it (2.2.1.10's three regions, rounds 4 and 5): refused before the slot write,
  it has committed nothing and item 8's unconditional ROLLBACK restores every before-image; sync 2 landed, it answers
  success; sync 2 refused, the runtime REVERSES the COMMIT under its own mutex hold before it answers unsuccessful, so item
  8's ROLLBACK finds no transaction on that file (and, when the reversal is refused too, answers by its own promotion's
  sync on the file marked UNACKNOWLEDGED). What the program is told is this group's commit row in `docs/CONFORMANCE.md`:
  COMMIT and ROLLBACK have no I-O status (§9.1.13.1 sets it only for CLOSE, DELETE, OPEN, READ, REWRITE, START, UNLOCK and
  WRITE), so a COMMIT or ROLLBACK the medium refuses raises the fatal EC-I-O-PERMANENT-ERROR for the refused file with '30'
  in that file's status item — exactly item 8's condition — and files are committed one at a time, in the order of the run
  unit's open stores, so a COMMIT refused at file i leaves the files before i committed and the files from i on at the
  previous COMMIT (cross-file atomicity is the owner's question in PB3330).
  COMMIT and ROLLBACK touch only this run unit's changes (2.2.1.10); `docs/CONFORMANCE.md`'s commit row states the
  determination that a connector opened INPUT between a run unit's death and the first writable statement reads its uncommitted
  records.
- Exceptions: EC-FLOW-APPLY-COMMIT (§12.4.6.3.4 GR6, address change — detection processor dependent, documented), EC-FLOW-COMMIT
  and EC-FLOW-ROLLBACK under a recursive element or an active SORT/MERGE (§9.1.18.7, §14.9.7.4 GR2, §14.9.36.4 GR2), EC-FLOW-APPLY
  at activation under a recursive element or a SORT/MERGE (§12.4.6.3.4 GR3/GR4) — the catalog rows already exist.
- Editions: the clause and both statements are 2023 constructs (`constructs.json` rows, the edition-gate sweep of
  `feedback_edition_gate_sweep`).
- Out of scope, recorded here so it is not lost: APPLY COMMIT on a SEQUENTIAL file (§9.1.18.2 admits any mass-storage file) has
  no engine to commit on; it is kb/Work PB3340.
