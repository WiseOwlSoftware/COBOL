# PB6003 - how the 1985 rows a mint opens are read and recorded

**Decision.** The 657 1985 rows PB5452's mint opened (636 new paragraph, list-item and table rows, 21 reopened
parents) are decided by READING, on the path of DESIGN-spec-conformance-review.md section 10.6: a subagent fleet reads each
row on its own 1985 text at `--std 85`, a refuter attacks each SAME and each argued derivation, and
`audit_batch.py import-reads --edition 1985` turns the reads into tracked read records. They close on OWN verdicts, each
outcome through its one writer:
- `own-verdict-from-pointer` (a SAME its refuter UPHELD): `audit_batch.py own-verdict-batch`;
- `needs-own-witness` (a reader or refuter showed the compiler correct at 85, `compiler-at-1985`): the probe is placed
  as the row's own test by `place_witnesses.py`, whose batch now carries the row's own verdict and code location;
- `derivation` (a rule no program can show, its argued arm UPHELD by a refuter): `audit_batch.py derivation-batch`,
  which writes the section 8 register row, the refuter record and the store record in one operation;
- `defect`: a kb/Work note.
They do NOT go through the Message Batches arm (section 10.3: route, map, verify, adjudicate) that PB5453 first named.

**Why.**
1. *No pairing to route.* 1985's next held edition is 2023 (2002 is bridged), and the candidate pairing pairs 0 of the
   2,911 1985 rules: 1985 wording never matches 2023's word for word. The Batches arm's map and verify passes produce
   CARRIES dispositions for KEPT change records, which the writer refuses for every new 1985 row (`targets are not the
   pairing's`). A run of it would spend its answers on records that cannot be written.
2. *Own text, own edition.* The owner's rule (2026-11-14, "2002 spec covers 2002 rules"; 2026-11-15, the same for
   1985) judges an older rule on its own text at its own `--std`, with a 2023 rule only a pointer. A reader with the
   compiler and the probe runner can show that; a Batches request cannot run a probe.
3. *Cost.* The Batches arm spends API credit, which is the owner's money and reserved (CLAUDE.md Ownership; the
   balances are for a capped batch job). The fleet runs on the subscription quota the plan in force already budgets
   (`budget.py`).

**What the pilot showed (slice s-01, 30 rows).** Run on the planner's read at the tooling's base (pb5452-mint
4b7d463c00): `kept 0, refused {'no refuter record': 7}, work {'undecided': 23}`. The reads were right; the tooling dropped
them: `lineage_reads._judgment` read only `compiler-at-2002`, so 13 rows proven correct at 85 imported `undecided`, and
the 4 definitional rows with a proposed derivation had no route. With branch pb5453-read-tooling the same read imports
`work {'derivation': 4, 'needs-own-witness': 13, 'undecided': 6}`, the 7 SAMEs awaiting their refuter as before.

**What it changes.** The design (section 10.6, "The 1985 rows a read decides close on their OWN verdicts" and "A
derivation from a read") states the route; the reader brief adds `code-location` to a derivation proposal for a row the
store holds no record of, and a derivation refuter brief writes `<slice>-derivation-refute.json`. A signing session adds
its `claude: <date>` key to the schema's `signatures`, mapped to the decision that read the rows, in the change that
writes them (section 1.1).
