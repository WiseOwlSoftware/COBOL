# PB842 — OPEN — an EVALUATE subject may be a condition, and only one shape of condition parses

Sources: the `PB400` report item (A) (`EVALUATE NOT <boolean-item>`) and the `PB394` report item (2) (the
subject re-analysed per WHEN). They are one mechanism seen from two ends — the grammar admits one condition
shape, and the binder has nowhere to PUT a truth value — so one implementer closes both.

So exactly two subject shapes reach the binder, and both are side-effect free — which is why the
re-analysis defect below is LATENT rather than observable today.

## The rules, quoted

```
$ python scripts/spec/cite.py --check 14.9.13.4 "At the beginning of the execution of the EVALUATE statement, each selection subject is evaluated and assigned a value, a range of values, or a truth value"
  OK  §14.9.13.4 3)  (General rules)
$ python scripts/spec/cite.py --check 14.9.13.4 "any selection subject specified by condition-1 is assigned a truth value"
  OK  §14.9.13.4 3) e)  (General rules)
      e) Any selection subject specified by condition-1 is assigned a truth value according to the rules for evaluating conditional expressions.
```

GR3 e) presupposes that condition-1 IS a selection subject (§14.9.13.2's general format prints it), and GR3's
stem puts the evaluation "at the beginning of the execution of the EVALUATE statement" — ONCE, before any WHEN
is compared. §8.8.4.3.2's format for a simple boolean condition is `[ NOT ] boolean-expression-1`, which makes
`NOT BW` a condition and therefore a legal condition-1.

## Code sites

* `src/Cobol.Net.Frontend/Grammar/Core/CobolControlFlow.g4:153-156` —
  `evaluateSubject : booleanLiteral | valueOperand (IS? NOT? classCondition)?` — no leading-NOT alternative and
  no condition alternative beyond the class condition.
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs#SubjectAsCondition` and the surviving
  `UdfStagePerEvaluationResidue` call in `#BindWhenItem`: the chained lowering re-emits the subject condition
  once per WHEN. The bound tree has no condition-to-boolean bridge — `BoundComputeBoolean` takes a
  `BoundBoolExpr` and `BoundCondition` is a different hierarchy — so there is nowhere to store the truth value.

## Shape of the fix (the structural one)

Add the bridge FIRST (a `BoundBoolFromCondition` leaf, or a `BoundIf` pre-op storing 1/0 into a one-character
boolean temp). With it, the same `SubjectSlot` carries a truth value, `UdfStagePerEvaluationResidue` can be
deleted outright, and the grammar can then admit the full condition-1 alternative without multiplying the
re-emission. Doing the grammar first would widen a defect instead of closing one.

## Sibling sweep the fixer owes

* `SubjectSlot`'s other consumers (the TRUE/FALSE objects, the ANY object) must all read the stored value.
