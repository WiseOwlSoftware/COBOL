# PB1163 — LANDED

## The rule (every citation re-run by the registrar through `cite.py --check`)

> 3) If the FOREVER phrase is specified, the mass storage control system shall attempt to gain access to a locked resource until the input-output operation has been completed.

`python scripts/spec/cite.py --check 14.7.9.3 "…"` → `OK  §14.7.9.3 3)  (General rules)`

## Finding — `retry-phrase` (wrong-answer; rows `GR-14.7.9.3-3`, `GR-14.7.9.3-2`)

**Mechanism.** RETRY FOREVER gives up after one re-attempt on a file-sharing conflict held by ANOTHER run unit (the 'no releaser exists' premise of D8 / A.1-109/165/166 was falsified by PB860's cross-run-unit detection)

**Repro.** SELECT F ASSIGN "held.dat" ORGANIZATION SEQUENTIAL FILE STATUS ST. ... DELETE FILE F RETRY FOREVER. DISPLAY ST.  Run while another process holds held.dat open with FileShare.None and releases it 4 s later (probe: out/probe/retry-phrase/forever.cob + hold.ps1). Same with OPEN INPUT RETRY FOREVER F (SHARING WITH NO OTHER).

**Expected from the spec.** §14.7.9.3 GR3 (cite.py --check OK 3)): 'shall attempt to gain access to a locked resource until the input-output operation has been completed' — the DELETE FILE completes after the holder releases: status '00', file deleted (OPEN: '00').

**Observed / reasoning.** DELFOREVER=62 after 72 ms, file still present; OPENFOREVER=61 after 72 ms. RetryLoop's Forever arm makes one re-attempt then lands the conflict's status, justified in D8/DOC-A.1-109 by 'the holder is a connector of the executing run unit and cannot release' — true for record locks, false for the host-level sharing conflicts PB860 added (FileRegistry.DeleteFile comment: 'another run unit CAN close mid-loop'). The same false premise is the stated ground of DOC-A.1-165/166 (zero interval, zero maximum meaningful timeout); the probe `RETRY 100000000 TIMES` -> '00' vs `RETRY FOR 30 SECONDS` -> '62' on one holder shows a positive timeout DOES change the outcome. The A.1-166 value itself is letter-legal and the owner's to keep or revise; the GR3 behaviour is not latitude. Fix: FOREVER (and, if the owner revises A.1-166, SECONDS) must actually wait/poll when the conflict's holder is outside the run unit, keeping the in-run-unit deadlock detection; correct D8 and the three CONFORMANCE rows.

**Code site.** src/Cobol.Net.Runtime/IO/FileRegistry.cs#RetryLoop (Forever arm), #ExhaustionStatus, #DeleteFile, #OpenCore; docs/COBOLNET_FILES_DESIGN.md D8; docs/CONFORMANCE.md DOC-A.1-109/165/166

## Landed (wave 73 group B, 2026-09-29)

**Re-probed first** on the w73b Debug build (`86cdf4456`): `DELETE FILE F RETRY FOREVER` and `OPEN INPUT RETRY FOREVER G`
(`SHARING WITH NO OTHER`), each file held `FileShare.None` by another process for about 3 s, answered `DELFOREVER=62`
and `OPENFOREVER=61` after 68 ms, with the file still present. After the fix both answer `00` once the holder lets
go, and the file is deleted.

**The mechanism.** Every attempt under the RETRY discipline now returns a `RetryAttempt`
(`src/Cobol.Net.Runtime/IO/RetryAttempt.cs`), which carries its I-O status and whether a conflict's holder is
OUTSIDE the executing run unit. The attempt is the only place that knows the holder. Table 19's '61'
(`SharedOpenAttempt`), `OpenByAnotherConnector`'s '62' and every record lock (`ConflictOnLockedRecord`) are held
inside the run unit. The host refusal, `FileConnector.Open`'s '61' and `HostFile.IsHeldByAnother`'s '62', is held
outside it. `FileRegistry.RetryLoop`:
- FOREVER re-attempts while the holder is outside, until the operation completes (§14.7.9.3 GR3, `cite.py --check`
  OK 3)). Against an inside holder it makes one re-check and stops, as before.
- n TIMES waits `FileRegistry.RetryInterval` (100 ms) before each re-attempt against an outside holder, and none
  against an inside one. This is a revised A.1 item 165 determination, GR1 "The implementor determines the interval
  between these attempts" (`--check` OK 1)).
- The pause goes through `FileRegistry.PauseObserver` in tests, so no test times a sleep.

The test-only forwarder `CobolFile.RetryLoop` was deleted, and its callers call `FileRegistry.RetryLoop`.

**Docs.** D8 in `docs/COBOLNET_FILES_DESIGN.md` gained the holder paragraph, and its GR2 ground is corrected.
DOC-A.1-109, -165 and -166 are rewritten. The `retry-phrase-2002` row of `constructs.json` is updated.

**⚠ For the owner: A.1 item 166.** The zero maximum meaningful SECONDS value is kept, because it is letter-legal.
Its stated ground is now documented as true only for holders inside the run unit, and `FOR n SECONDS` is the one
form that does not wait for another program. Revising the value (a positive maximum, polled at `RetryInterval`) is
the owner's decision, as this note said.

**Witnesses.** Unit: `CobolFileLockTests.RetryForever_AgainstAHolderOutsideTheRunUnit_WaitsUntilTheOperationCompletes`,
`CobolFileLockTests.RetryAgainstAnOutsideHolder_PausesBeforeEachReattempt_AndOnlyThen`, and
`SharingRefusalStatusTests.RetryForever_WaitsForAnotherRunUnitToRelease_DeleteFileAndOpen` (a real exclusive
handle, for all three organizations). No corpus golden is possible, because a golden program has no second run unit
to hold its file. Rows `GR-14.7.9.3-2/-3/-4` re-verdicted CONFORMS (batch `w73b-pb1163-retry-outside-holder`, GAP
866 → 863).
