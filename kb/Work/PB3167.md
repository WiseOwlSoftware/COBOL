# PB3167 — ALIGNED members in later occurrences of a mid-byte bit-group table

Source: `E:\COBOL-coord\scratch\reports\w1078e-PB3158-report.md`, item 2 (the reporter rates it low).

- A table whose element is a bit group that starts mid-byte: later occurrences' ALIGNED members are not on record byte boundaries.
- The reporter says a decision on per-occurrence padding is the owner's if wanted, hence kind analysis. First step: the spec reading of ALIGNED inside an OCCURS element (PB3158 cites §13.18.1.4 and §8.5.1.6.3).

## Landed 2026-10-16 (w1103 D)

Re-probed on a fresh build: `05 BA PIC 1(2). 05 SUB GROUP-USAGE BIT OCCURS 3. 10 SA PIC 1. 10 TA PIC 1(5) ALIGNED`
laid every occurrence 11 bits apart (LENGTH(BG) 35), so TA(2) sat at bit 19 and TA(3) at bit 30; the same with the
element's FIRST item ALIGNED at phase 0 (TA(2) at bit 6). **The standard is not silent**: TA is subordinate to an
OCCURS entry, so it has an occurrence per occurrence of SUB (13.18.63.4 9) "every occurrence of the associated data
item"), and 13.18.1.4 GR2 ("applies to each occurrence of that item") with GR1 puts every one of them on a byte.
**DETERMINATION** (docs/CONFORMANCE.md USAGE BIT; the owner may overturn it): a table whose element lays out
differently at different phases strides whole bytes (`BitLayout.HoldsByteStart`, `StrideBits` = width rounded up),
so every occurrence begins at the first one's phase and lays out as the first; filler sits between occurrences,
none after the last. It keeps the one length of "the subject of the entry" (13.18.38.4 7)), mirrors 13.18.55.4 8) b)
for SYNCHRONIZED and IBM's inter-occurrence slack bytes; GnuCOBOL 3.2 rejects GROUP-USAGE BIT. Rejected: each
occurrence at the next bit position (different offsets and lengths per occurrence).
**Siblings fixed (I9).** (1) `KeepsPosition` asked only the subject: a bit group whose FIRST item is ALIGNED began
before it (8.5.1.6.3 "the same bit position", both ways): LENGTH(SUB) 11, now 5; the REDEFINES SR15 screen
(`DataBinder.RedefinesEntry`) now asks the same predicate (negative `pb3167-redefines-group-first-item-aligned`,
COBOLNET2739). (2) The character ODO channel (`CobolTable.OdoExtentChars`) did not give the last occurrence's
trailing filler back (harmless while only an ALIGNED table, which begins on a byte, had any), so the new
whole-byte-stride table that begins mid-byte staged BYTE-LENGTH ("fixed extent is negative") and would send one
character too many; it now takes `trailingUnits` (runtime major 6 -> 7, ABI pin re-pinned).
(3) The placement dispatch had three spellings (walk, PhaseOf, the new stride test): one `BitLayout.Continues`.
Golden `2002/pb3167_aligned_member_in_bit_group_table`; `BitRunImageDriftTests` BRD13, BRD14;
`BitGroupPhaseDriftTests.TheStride_AsksWhetherTheLayoutDependsOnThePhase_AndAGroupBeginsWithItsFirstItem`.

## Landing

- `src/Cobol.Net.Compiler/Binding/Model/BitLayout.cs#HoldsByteStart` - whether an occurrence's layout depends on its
  phase; `StrideBitsAt` reads it. `#Continues` is the one placement dispatch; `#KeepsPosition` recurses into a group's
  first item.
- `src/Cobol.Net.Runtime/Values/Tables/CobolTable.cs#OdoExtentChars` - the character extent is `OdoExtentTrimmed`
  rounded up; never round before giving the trailing filler back.
- `src/Cobol.Net.Runtime/Values/Tables/CobolTable.cs#TrimmedExtent` - the one extent rule (`fixed + c x stride -
  trailing`), read by the ODO extent channels and by `OdoTail.CharactersAt` (review R1-1: `OdoTail`, the
  variable-length group codec's and a cell window's geometry, had no trailing term, so a mid-byte whole-byte-stride
  table measured one character past its end). `OdoModel.FixedImageTail` fills `OdoTail.Trailing` from
  `OdoGeometry.TrailingUnits`; any new extent reader asks `TrimmedExtent`.
