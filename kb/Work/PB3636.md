# PB3636 — notes no lane can reach, and nothing says so

**Sites:** `scripts/spec/work.py`, `scripts/session-probe.ps1`, `scripts/orchestrator/orchestrate.ps1`, a work.py self-test or drift test over a fabricated register.

Filed 2026-10-24 ~11:20 PDT by the attended operator session (2f7da35b) at the owner's instruction: "file the no-lane
check", after the owner asked "What others notes aren't being enacted".

## Measurement (origin/main `06b09391f` plus the PB2699 note branch, 2026-10-24 ~11:10 PDT)

A scratch script over `work.load()` sorted every `open`/`half` note into the lane that can plan it, against the loop
then running `-Cluster PB1957,PB3608`:

| lane | notes |
|---|---|
| campaigns the loop runs (PB1957, PB3608) | 7 |
| fix lane (`work.actionable`: a harm flag, not process_only, not blocked) | 31 |
| blocked (an open `blocked_by` or `blocked: true`) | 173 |

| **no lane at all: no harm flag and no campaign** | **435** |

The 435 are mostly MINOR process, tooling and test defects, but 49 are MAJOR: the A-series analyses, PB782 (the shipped
`cobol` has no exit-code contract test), PB827 (an unhandled IOException for `-o <existing directory>`), PB294 (a
vacuous diagnostic-registry drift test), and ten loop and landing defects the owner moved into PB1957 the same hour
(PB3628 among them, the very reason PR #467 sat 13 hours NOT QUEUED). A further group is "in a campaign" only nominally:
about 200 `cluster:` values name a single note, not a campaign anyone runs.

## Defect

A note reaches a lane only through `work.actionable` (the fix lane) or `cluster_order` for a campaign the operator
names. A `process_only` note, or any note without a harm flag, outside a running campaign is planned by nothing, and
neither `session-probe.ps1`, `work.py next`, `work.py check` nor `next_unit.py` counts or names it. It is invisible
until someone asks, exactly as the five-register era hid live defects in prose (CLAUDE.md rule 8).

## Fix direction

- ONE classifier in `work.py` (beside `actionable` and `cluster_order`): every open note gets exactly one lane:
  fix lane · campaign `<lead>` (a cluster whose lead note is open and lists itself, i.e. a real campaign) · blocked ·
  owner-held · **no lane**. `cluster:` values that name no campaign are reported as such, not counted as a lane.
- `work.py lanes` prints the counts and the no-lane list (MAJOR first); `--json` for the tools.
- `session-probe.ps1` prints a `lanes` line with the no-lane count and the MAJOR no-lane ids, and the supervisor logs it
  per unit, so the operator sees a growing orphan pool without asking.
- `work.py check` refuses a NEW MAJOR note filed with no lane (a filer must name the campaign or a harm flag); the
  existing pool is a ratchet that may only shrink (record the baseline, 435 at this filing).
- Drift test: a fabricated register with one note per lane classifies each correctly, and the ratchet refuses a new
  MAJOR orphan.
- The owner decides the existing pool's disposition (which campaign takes what, or retire); file that question once the
  `lanes` view exists.
