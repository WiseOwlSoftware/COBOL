# PB3608 — a finished branch waits up to an hour for its reviewer

**Sites:** `scripts/orchestrator/orchestrate.ps1` (the supervisor), `scripts/orchestrator/land_lane.py` (the lane it
ticks beside every unit, the shape to follow), `docs/rearchitecture/DESIGN-orchestrator-loop.md` (sections 4.9 and the
unit catalog).

## Measured (2026-10-23 ~16:00 PDT, the operator's loop on account 2)

All three gate slots free, the merge queue empty, and finished branches waiting. A branch DONE outside a rolling wave (an
attended branch, a finisher's new tip, a lane's notes branch) is reviewed only when the loop's next `enqueue` unit runs,
and units run one at a time: that day's units ran 3,308 s, 4,579 s and (the wave from 14:13) over two hours. The
attended branch `fix-self-test-wall-leads` was DONE at ~14:00 and still WAITING FOR REVIEW at 16:00, until the operator
dispatched its reviewer by hand (CLEAN in 187 s). The landing itself is not the bottleneck: the landing lane
(`land_lane.py tick`, kb/Work PB3103) starts every WAITING TO LAND branch within its 3-minute tick.

## The fix (a design, for the implementer)

A REVIEW LANE beside the landing lane, under the same supervisor: on each tick, every branch `prune_worktrees.py` lists
WAITING FOR REVIEW and that no reviewer is already reviewing (a lease per branch head, the landing lane's attempt record
as the model) gets ONE read-only `cobol-reviewer` in its own headless session (`claude -p` with the review skill's branch
form prompt, a findings file per branch, `RF stamp` on its report), capped at N concurrent reviewers and charged to the
budget like any unit. The enqueue unit keeps the finishers and the leads; it no longer starts reviews. The stall rule the
waves use (`reviewer_ceiling_min`) bounds each review. Measure: DONE -> review stamp latency per branch before and after
(`review_findings.py summary`, `landing_measure.py`).

## Standing requirements

- The lane must be restart-safe: a reviewer killed mid-review leaves the findings file's `start` record, and the next tick
  repairs nothing by hand; it reads the torn or unfinished file through `review_findings.last_verdict` and starts the
  round again.
