# PB2094 — variable-length group formal copies at the boundary

Filed 2026-10-05 by the train-1023 lander from the w1023a implementer report (PB2087 finisher, lead 1).

**Rule.** ISO §14.2.3 GR8: "If the argument is passed by reference, the activated runtime element operates as if the
formal parameter occupies the same storage area as the argument." Nothing in GR8 exempts a variable-length group.

**Mechanism.** PB2087 and PB2089 lay every AREA formal over the argument's cell, except a formal whose class
`DataBinder.CellCanCarry` refuses: a group holding a dynamic-capacity table or a dynamic-length item
(`src/Cobol.Net.Compiler/Binding/DataBinder.Linkage.cs` `CellCanCarry`, ~line 909, `HoldsVariableLengthComponent`). Such a
formal keeps the §8.5.1.12 image round trip — copied in at entry (`ProgramEmitter.EmitCallMethod`, the
`CallCrossing.VarGroup` arm, `src/Cobol.Net.Compiler/CodeGen/ProgramEmitter.cs` ~197) and out at return, and the INVOKE
lane's non-area copy-out in `OoEmitter.EmitMethod`. So `CALL "S" USING V V` with a variable-length group V shows the second
formal stale data after a store through the first, exactly the PB2087 failure for this one shape. The design doc used to
cite §13.18.5.3 SR2 as permission for the copy; that rule governs a WRITTEN BASED clause only, so it grants nothing here
(the w1023a finisher removed the citation from `CellCanCarry` on its branch).

**Repro.** The PB2087 shape with a variable-length group: `01 V. 05 N PIC 9. 05 T OCCURS 1 TO 5 DEPENDING ON N PIC X.`
passed twice, `CALL "S" USING V V`; S stores into the first formal and DISPLAYs the second: prints the old value, must
print the new one.

**Fix direction.** A cell area whose window length follows the item's current extent (the dynamic shapes already carry
their length in the cell's slot side, `DynSlotWindow`), so the variable-length formal is laid over the argument like every
other area formal; then delete the `VarGroup` copy arms.

## Landed 2026-10-07 (wave 1034 group A, w1034a)

**Re-probed on this tree** (probes in `E:\COBOL-coord\scratch\w1034a\p\`): the note's ODO repro (`vodo.cob`) no longer
reproduces — an OCCURS DEPENDING table is fixed-capacity storage and has crossed as an area since PB2087 — but the
variable-length shapes did, worse than the note said: `vdl.cob` (`CALL "VDLS" AS NESTED USING V V`, V = X + `PIC X
DYNAMIC LENGTH`) printed `L2=H/ABC/` and `AFTER=H/ABC/` (the second formal's copy-back undid the store through the first
entirely); `vdyn.cob` (a dynamic-capacity table) the same, `AFTER=H/0000000003/ABC`. After: `L2=Q/WXYZ/`,
`AFTER=Q/WXYZ/`; `AFTER=Q/0000000005/ZBC`.

**Mechanism.** A variable-length group's components are slots of a cell numbered in storage order
(`DataBinder.AssignCellComponents`); an area formal laid over an argument at an offset had no way to number its
components from the argument's first one, so `CellCanCarry` refused the shape and it kept the image round trip. Now
`CellPointer.DynBase` (the component ordinal the area begins at) and `CellPointer.Shape` (its §8.5.1.12 atoms) ride the
argument's area (`CallEmitter.AreaOf`, from `VarGroupWindow.DynBase`); every reference through a pointer-routed class
numbers its components from `CobolPtr.DynBaseOf(pointer)` (`ReferenceResolver.CellOrdinalBase`, the leading term of the
one scope walk and of `PlaceCursor.AtCellTable`); `CobolArgAdapt.Area` lays a formal over the area only when
`GroupCompatibility.LaysOver(formal, area)` — the same storage, or a prefix whose last fixed run is shorter — and
otherwise hands it its own seeded fresh cell (`DataEmitter.AreaFormalShape`: the atoms and a static factory of a cell
holding its dynamic-capacity tables at FROM capacity), filled and stored back through the reshaping component carrier.
`CellCanCarry` no longer excludes variable-length components, so the argument is claimed onto a cell like any BY
REFERENCE operand. The INVOKE lane takes the same decision (`ArgAdaptAreaOf`; `MethodCellFormalLoad` / `Store` gained the
variable-length arm). A cell store keeps a formal's copy-in whole (`WriteVarGroupImage` `formalStorage`, PB1937's rule).
The gate exposed a sibling arm: a cell window over a dynamic-capacity table (one occurrence, the element at offset zero
of its element cell) answered the TABLE's image capability, so `MOVE "99z" TO GT(2)` in a record now claimed onto a cell
(golden `2014/pb189_dynamic_table_element_operand`) was the Tier-C loud — the same hole any EXTERNAL record with such a
table already had. `RedefViewPlace.ImageCapable` / `TransferImageCapable` now take `DynTablePlace`'s law (PB189).

**Witnesses.** Golden `2014/pb2094_vlg_formal_shares_argument_area` (V V with a dynamic-length item and a
dynamic-capacity table; a subordinate group inside a fixed table whose record has components before it, `DynBase` 4; a
prefix formal with a shorter tail; the INVOKE lane; BY CONTENT twice). `VariableLengthAreaOverlayTests` (every arm of the
area decision). No negative: a wrong answer on legal source; the edition gating of the constructs is the version
matrix's.
