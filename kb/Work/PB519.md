# PB519

## Mechanism — data-description-entry-p2
F3 — EXTERNAL x REDEFINES is unscreened, and the unscreened combination is then actively harmful: CallBindExternalAndGlobal re-bases an EXTERNAL record onto the run-unit ExternalStore cell AFTER redefines classification, deliberately folding the redefiner's WHOLE class onto the shared backing. When the EXTERNAL clause sits on the redefinER, that fold silently re-homes the redefines ANCHOR too, and the anchor's VALUE is lost. The BASED sibling of the same rule IS screened (COBOLNET0881, quoting SR5) — the classic two-arm dispatch with only one arm ever fixed.

### Expected, from the standard
ISO/IEC 1989:2023 §13.16.3 SR5 (cite-checked): "The EXTERNAL clause shall not be specified in the same data description entry as the REDEFINES or BASED clause." The program shall be rejected at compile time.

```
$ python scripts/spec/cite.py --check 13.16.3 "The EXTERNAL clause shall not be specified in the same data description entry as the REDEFINES or BASED clause"
  OK  §13.16.3 5)  (Syntax rules)
```

### Observed
The program compiles clean and prints four SPACES where A's own VALUE clause says ABCD. The mechanism is in DataBinder.Linkage.cs#CallBindExternalAndGlobal's own doc comment: 'Runs at the END of Bind (after REDEFINES classification) so an EXTERNAL record that is also a redefines anchor folds its whole class onto the shared backing' — a deliberate design for the LEGAL case (the EXTERNAL clause on the anchor), which SR5 makes the only case that can occur. With the clause on the redefinER, the same fold re-bases A onto the external cell, whose fresh content is spaces, so the anchor's initialization is discarded with no diagnostic. Grep confirms the missing arm: the only `hasExternal` conflict test in BindEntry is inside `if (isBased) { ... else if (hasExternal) ... }` (DataBinder.cs ~2827) — reachable only when BASED is also present, so a REDEFINES+EXTERNAL entry never reaches any check.
