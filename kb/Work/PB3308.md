# PB3308 — a transient SDK download failure fails a CI job

**Sites:** `scripts/install-dotnet-sdk.sh` (`DOTNET_SDK_VERSION`, `DOTNET_SDK_FEEDS`, `dotnet_sdk_install`, `dotnet_sdk_fetch`, `dotnet_sdk_archive`, its `--self-test`), `.github/actions/setup-dotnet/action.yml` (the one SDK step), `.github/workflows/build-and-test.yml` (the six building jobs' `Setup .NET SDK` steps, the `dotnet-sdk-cache` job, `ci-gate`'s `needs`), `scripts/wsl/setup-wsl.sh` (calls the script), `scripts/cloud/setup-env.sh` (the `dotnet-sdk-install` block, `install_dotnet`), `global.json` (the floor the pin must satisfy, unchanged), `tests/WiseOwl.Cobol.Tests.Unit/DotnetSdkInstallDriftTests.cs` (the drift test), `docs/rearchitecture/DESIGN-test-build-ci.md` §1.4, `docs/DOC_INDEX.md`, `kb/Work/PB1957.md` row 8.

Filed 2026-10-16 by the enqueue unit.

## Recurrence (2026-10-25): every code merge group fails, for as long as the origin refuses

Filed by the enqueue unit. From about 18:50Z every merge-group run whose matrix runs failed `Setup .NET 10` in EVERY
building job (Windows and Linux alike), so `ci-gate` failed and GitHub removed the pull request from the queue: PR #576
(worktree-wf_6e0a917c-500-21, run 40222506225), PR #578 (worktree-wf_ba46c1d4-922-3, runs 40222675508 and 40224097874),
and the code groups of PRs #580 and #581 (runs 40223113824, 40223731912, 40224540131, 40224541544). Notes-only groups
skip the matrix and kept merging (#577, #582). The last green code groups were #573 and #575 (about 18:34-18:38Z).

The cause is not a flaky transfer: `dotnet-install` tries the aka.ms link first, aka.ms answers 301 to
`https://dotnetorigin.blob.core.windows.net/dotnet/Sdk/10.0.403/dotnet-sdk-10.0.403-linux-x64.tar.gz`, and that storage
account answers `409 <Code>PublicAccessNotPermitted</Code> Public access is not permitted on this storage account`
(measured from this host at 19:12Z with curl; the runtime tarball 10.0.14 the same). Its three retries all get the same
409, and it then gives up with `Could not find .NET Core SDK with version = 10.0.403`; it never tried a feed that works.
The same file is served by `https://builds.dotnet.microsoft.com/dotnet/Sdk/10.0.403/dotnet-sdk-10.0.403-linux-x64.tar.gz`
(200 at 19:12Z). So a retry of the step, the first fix shape below, would not have helped: no landing of code can pass
the queue until Microsoft restores the redirect or CI stops depending on it. No finisher was dispatched for #576 or
#578: their branches are not at fault (bounce causes recorded `infrastructure` by `landing_measure.py record`).

## Mechanism

`.github/workflows/build-and-test.yml`: every job that builds has a `Setup .NET 10` step (lines 367, 435, 483, 572, 661,
711) of `uses: actions/setup-dotnet@v6` with `dotnet-version: 10.0.x`. The action resolves the newest 10.0.x and runs
`dotnet-install`, which downloads the SDK from `aka.ms` on every job: no retry around the step and no cache of the
installed SDK, so one failed download fails the job and, through `ci-gate`, the whole merge-group run. No kb/Work note
covered it; PB1957 row 8 ("SDK version") is about WHICH SDK patch CI picks, not about the download failing.

## Fix shape

Make the SDK install survive both a transient failure and a refusing origin (the 2026-10-25 recurrence): install from
a feed that does not go through the aka.ms redirect (`builds.dotnet.microsoft.com`, with the runner image's
preinstalled SDK as the fallback; `https://ci.dot.net/public/Sdk/10.0.403/...` answered 404 at 19:12Z, so it is no fallback), and cache the installed SDK keyed on the resolved version / `global.json`, so
neither a failed download nor a refusing origin fails the job while the cache is warm. A bare retry is not enough. One shape for all six job steps (a
shared composite action or one reusable step, never six hand edits).

## CI-invariant obligation

PB1957's survey maps every CI job to a local leg or a recorded reason it cannot run locally. The fix extends
PB1957's row 8 (SDK version) with the reason "the SDK download is an external network dependency the local gate
cannot exercise", and the drift test PB1957 carries keeps the mapping true.

**The bar.** CI's SDK install must not depend on the aka.ms redirect: install the exact SDK the build needs (the version `global.json` and its rollForward accept, resolved once) from the feed that serves it (`builds.dotnet.microsoft.com`, with `ci.dot.net` as the second feed), and cache the installed SDK keyed on that version so a later outage of every feed still finds it; ONE install shape for all six job steps (a composite action or one step template, no copies), and the same feed order in `scripts/wsl/setup-wsl.sh` and `scripts/cloud/setup-env.sh`, pinned by a drift test. The fix's own merge group is the proof: it runs the new workflow while the origin still refuses. Re-arm #576 and #578 once it lands (their branches are not at fault).

## Landed (wave 20261700, group A)

**Re-probe (19:22Z, 2026-10-25, from this host).** `https://aka.ms/dotnet/10.0/dotnet-sdk-linux-x64.tar.gz` answered 301
to `https://dotnetorigin.blob.core.windows.net/dotnet/Sdk/10.0.403/dotnet-sdk-10.0.403-linux-x64.tar.gz`, which answered
409; `https://builds.dotnet.microsoft.com/dotnet/Sdk/10.0.403/` served the linux-x64 tarball, the win-x64 zip and both
`.sha512` files (200); `https://ci.dot.net/public/Sdk/10.0.403/` and `/10.0.402/` answered 404. The feed's
`release-metadata/10.0/releases.json` and `Sdk/10.0/latest.version` still named 10.0.402, so "the newest 10.0" was not
even one answer: aka.ms said 10.0.403, the metadata 10.0.402.

**Fix: one pinned SDK, one install script, one action.** `scripts/install-dotnet-sdk.sh` pins `DOTNET_SDK_VERSION=10.0.403`
(the SDK the Windows dev box already builds with) and its feeds (`builds.dotnet.microsoft.com/dotnet`, then
`ci.dot.net/public`), downloads `dotnet-sdk-<version>-<os>-<arch>` with its `.sha512` from the first feed that serves it,
checks the SHA-512, unpacks it, and only then writes `.dotnet-sdk-<version>.complete`, so an interrupted install is redone.
A broken-off transfer is retried on the same feed (curl's retries plus three attempts); a refusal (curl exit 22, a 404 or a
409, or 37 for a missing file) moves straight to the next feed. An exact version never goes through aka.ms. The composite
action `.github/actions/setup-dotnet` replaces all six `actions/setup-dotnet` steps: it restores the SDK from the Actions
cache (key `dotnet-sdk-<version>-<os>-<arch>`), runs the script (a no-op on a hit), saves it (a failed save warns), puts
it first on `PATH` with `DOTNET_ROOT`, and fails unless `dotnet --version` reports the pin. Because a merge group's ref is
new every time and main's push run skips the matrix, a new job `dotnet-sdk-cache` (push to main and dispatch only, Ubuntu
and Windows, in `ci-gate`'s `needs`) saves the SDK under main, where every merge group can restore it; its install step is
`continue-on-error` with a warning, so a failed warm-up never fails main's run. `setup-wsl.sh` calls the script;
`setup-env.sh` (run before the clone) carries the script's block between the `dotnet-sdk-install` markers. A bare retry
and the runner image's preinstalled SDK were both rejected: a retry gets the same 409, and a preinstalled SDK is a
different patch from the local hosts' (PB1957 row 8). `global.json` is unchanged: its `10.0.100` with `latestMinor`
accepts the pin, and the drift test checks that.

**Held by `DotnetSdkInstallDriftTests`** (Unit, a tree sweep): the pin is an exact SDK version global.json's floor and
rollForward accept (the policies modelled from the global.json reference: patch, feature, minor, major, their latest
forms, disable); the feeds start at builds.dotnet.microsoft.com, are https and never aka.ms; every workflow job that runs
a `dotnet` command has `uses: ./.github/actions/setup-dotnet` before its first one; no workflow, action or setup script
names `actions/setup-dotnet`, `dotnet-install` or aka.ms outside a comment; the action derives its key from the script's
version, restores, installs with the script, saves under `continue-on-error`, and checks `dotnet --version`; the
`dotnet-sdk-cache` job runs on push, on Ubuntu and Windows, through the action, tolerated; `setup-wsl.sh` calls the script
and `setup-env.sh`'s block equals the script's. A self-test feeds each audit its forbidden shapes. The script's own
`--self-test` (run in every gate and in CI through `scripts/self_tests.py`, on Linux and Windows) drives the real install
over local file:// feeds: first feed serves; a refusing first feed hands over; a checksum mismatch hands over; no feed
fails naming them; an installed version is not fetched again; a missing marker redoes it; a broken-off transfer is
retried; a refusal is not. The checksum, fallback and marker witnesses were each shown to fail on a mutated copy.

**Sibling sweep.** The other external downloads a CI job makes: `actions/checkout` (GitHub, retries inside itself); NuGet
restore (`dotnet restore` retries; packages cached); `pip install` of pinned `pyyaml`/`tzdata` in `audits` and
`windows-self-tests` (pip retries five times by default); the GnuCOBOL testsuite (`scripts/fetch-gnucobol-tests.ps1`,
three attempts since PB3140); the ANTLR jar is vendored (`src/WiseOwl.Cobol.Frontend/ANTLR4/`). No other job resolves a
version through a redirect at install time. The local and cloud install sites were the same route (`dotnet-install
--channel 10.0`) and now use the script.

**Owner actions (not done by the branch).** Paste the new `scripts/cloud/setup-env.sh` into the cloud environment's
"Setup script" field (its header requires it), and re-run `scripts/wsl/setup-wsl.sh` in WSL so the Linux half of every
gate builds with the pin. Re-arm PRs #576 and #578 once this lands (their branches are not at fault). Moving to a newer
SDK is one edit to `DOTNET_SDK_VERSION`, copied into `setup-env.sh` (the drift test names the copy).

**For the next implementer.**
- `scripts/install-dotnet-sdk.sh#dotnet_sdk_install` owns the install; reuse it, never a second download. Trap: Git
  Bash's curl is a native Windows program, so a file:// feed needs `pwd -W`'s `C:/…` form (the self-test does it).
- `.github/actions/setup-dotnet/action.yml` is the only SDK step a job may use; on Windows its `C:\…` paths reach bash, so
  the script runs `cygpath -u` and the check runs `cygpath -u` on the `dotnet` it executes.
- `tests/WiseOwl.Cobol.Tests.Unit/DotnetSdkInstallDriftTests.cs#Accepts` models global.json's rollForward; `#Jobs` reads a
  workflow's jobs (a blank line between jobs must not merge them).

Measured at 20:38Z: aka.ms now redirects to `builds.dotnet.microsoft.com` (200) while `dotnetorigin` itself still answers 409, so Microsoft repointed the redirect rather than restoring the origin.
