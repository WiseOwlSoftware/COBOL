# PB3308 — a transient SDK download failure fails a CI job

Filed 2026-10-16 by the enqueue unit.

## Harm

A green branch loses a merge-group cycle and its re-queue. GitHub removes the failed pull request from the merge queue
(`failed_checks`) and drops what is queued behind it: PR #149 was removed the same moment with `merge_conflict` (it
conflicts with #139 in `tests/Cobol.Net.Tests.Unit/RuntimeAbiPinDriftTests.cs`, not with main). The enqueue unit re-armed
#139 at the same head (`land_lane.py rearm`).

## Repro (2026-10-16)

Merge-group run 38974314534 (PR #139, branch `worktree-wf_d588a65b-0ab-6`, head 0bf6aea7b84a, group base 0c53cc440):
the ONLY failed job was `Windows conformance (sharded) (matrix-cont-2002, FullyQualifiedName~Cobol85Program_StillCompilesA...`,
failed step `Setup .NET 10`; `ci-gate` then failed its `Verdict` step. Every other job was green. GitHub removed PR #139
from the queue at about 22:26Z. `gh run view 38974314534 --log-failed`:

- `dotnet-install: Downloading from "aka.ms" link has failed with error: ... Error while copying content to a stream.`
- `Could not find ".NET Core SDK" with version = 10.0.402`
- `##[error]Failed to install dotnet, exit code: 1.`

## Recurrence (2026-10-25): every code merge group fails, for as long as the origin refuses

Filed by the enqueue unit. From about 18:50Z every merge-group run whose matrix runs failed `Setup .NET 10` in EVERY
building job (Windows and Linux alike), so `ci-gate` failed and GitHub removed the pull request from the queue: PR #576
(worktree-wf_6e0a917c-500-21, run 40222506225), PR #578 (worktree-wf_ba46c1d4-922-3, runs 40222675508 and 40224097874),
and the code groups of PRs #580 and #581 (runs 40223113824, 40223731912, 40224540131, 40224541544). Notes-only groups
skip the matrix and kept merging (#577, #582). The last green code groups were #573 and #575 (about 18:34-18:38Z).

The cause is not a flaky transfer: `dotnet-install` tries the aka.ms link first, aka.ms answers 301 to
`https://dotnetorigin.blob.core.windows.net/dotnet/Sdk/10.0.403/dotnet-sdk-10.0.403-linux-x64.tar.gz`, and that storage
account answers `409 <Code>PublicAccessNotPermitted</Code> Public access is not permitted on this storage account`
(measured from this host at 19:12Z with curl; the runtime tarball 10.0.14 the same). Its three retries all get the same
409, and it then gives up with `Could not find .NET Core SDK with version = 10.0.403`; it never tried a feed that works.
The same file is served by `https://builds.dotnet.microsoft.com/dotnet/Sdk/10.0.403/dotnet-sdk-10.0.403-linux-x64.tar.gz`
(200 at 19:12Z). So a retry of the step, the first fix shape below, would not have helped: no landing of code can pass
the queue until Microsoft restores the redirect or CI stops depending on it. No finisher was dispatched for #576 or
#578: their branches are not at fault (bounce causes recorded `infrastructure` by `landing_measure.py record`).

## Mechanism

`.github/workflows/build-and-test.yml`: every job that builds has a `Setup .NET 10` step (lines 367, 435, 483, 572, 661,
711) of `uses: actions/setup-dotnet@v6` with `dotnet-version: 10.0.x`. The action resolves the newest 10.0.x and runs
`dotnet-install`, which downloads the SDK from `aka.ms` on every job: no retry around the step and no cache of the
installed SDK, so one failed download fails the job and, through `ci-gate`, the whole merge-group run. No kb/Work note
covered it; PB1957 row 8 ("SDK version") is about WHICH SDK patch CI picks, not about the download failing.

## Fix shape

Make the SDK install survive both a transient failure and a refusing origin (the 2026-10-25 recurrence): install from
a feed that does not go through the aka.ms redirect (`builds.dotnet.microsoft.com`, with the runner image's
preinstalled SDK as the fallback; `https://ci.dot.net/public/Sdk/10.0.403/...` answered 404 at 19:12Z, so it is no fallback), and cache the installed SDK keyed on the resolved version / `global.json`, so
neither a failed download nor a refusing origin fails the job while the cache is warm. A bare retry is not enough. One shape for all six job steps (a
shared composite action or one reusable step, never six hand edits).

## CI-invariant obligation

PB1957's survey maps every CI job to a local leg or a recorded reason it cannot run locally. The fix extends
PB1957's row 8 (SDK version) with the reason "the SDK download is an external network dependency the local gate
cannot exercise", and the drift test PB1957 carries keeps the mapping true.
