# PB1702 — LANDED (2026-09-28)

**Owner, 2026-09-28:** "Fix PB1702 too".

## The defect, as MEASURED

A tool call writes nothing to the agent's transcript between its `tool_use` record (written when the call starts)
and its `tool_result` (written when it returns). The fix-lane protocol's gate wait,
`timeout 580 bash -c 'tail -n +1 -f <log> | grep -m1 …'`, runs up to ~580 s.

Measured on train 69 (the three wave-69 finishers and the lander): each agent had 5–7 transcript silences over 120 s,
the longest 582–585 s, and every one opened with a Bash `tool_use`. `fleet_active_build.py` counted a transcript
live only if written within 120 s, so during every gate wait, which is when that agent's binaries are in use, the
guard ALLOWED a build in the same tree. That is the 2026-08-04 harm it exists to prevent. `scripts/gaps.py` in the
orchestrator's scratch holds the measurement.

## ⚠ Correction of how this note was first filed

The note was first filed claiming subagent transcripts are "written lazily", citing a 20+ minute silence on
2026-09-28 at 00:32–00:53. That was WRONG. The owner's `/clear` at ~00:33 started a new session id, and the
still-running workflow's agents wrote the rest of their transcripts into the NEW session's directory
(`…/73cac64c-…/subagents/workflows/wf_64d3a01e-a3d/`), while its journal stayed in the old one. The orchestrator's
watchdog read the old directory. The same wrong cause went into DEVLOG 1750, orchestrator memory and public
agent-fleet v1.7.0; each is corrected (DEVLOG 1752, public v1.8.0). The defect above is real and measured
separately.

## The fix

`is_live(path, now)`: a transcript is live if written within 120 s (unchanged), OR if its last decisive record is an
unanswered `tool_use` and it was written within 660 s. 660 s is the shell tools' 600 s maximum plus a margin. The
bound keeps a KILLED agent, which also leaves a dangling tool call, from denying forever. `pending_tool_call`
reads only the file's last 256 KiB, and any parse failure falls back to the old rule. The change can only ADD
liveness the old rule missed. The deny message names both windows.

- **Self-test:** 6 new liveness cases over real files with set mtimes (fresh, mid-tool 5 min, answered, ended,
  dangling past the bound, unparseable), plus all the existing cases: PASS.
- **Real transcripts:** `pending_tool_call` is True on the stale-folder wave-69 transcripts (frozen mid-Bash at
  /clear).
- **Sibling sweep:** no other script judges agent liveness by mtime; `tooling_check.py`'s mtime is a days-old
  stamp.

## Known limitation, not in this fix

`agent_working_tree` maps an agent to `.claude/worktrees/agent-<id>`. Workflow agents launched with
`isolation: 'worktree'` get `wf_<run>-<n>` worktrees, which that mapping cannot associate with an agent id, so they
count as working in the MAIN tree. The effect is fail-closed: a main-tree build is denied while any workflow
implementer is live, which is the conservative direction. Recorded for whoever next restructures the tree map.
