# PB555

## Mechanism — value-clause-p2
THE FORMAT-3 MODEL CARRIES ONE OF THE FORMAT'S THREE OPERAND-BEARING CONSTITUENTS. 13.18.63.2 Format 3 prints three things after VALUE/VALUES: the literal-2 [THROUGH literal-3] group, [ IN alphabet-name-1 ], and [ WHEN SET TO FALSE IS literal-4 ]. The grammar parses all three (src/Cobol.Net.Frontend/Grammar/Core/CobolData.g4:621-624), but src/Cobol.Net.Compiler/Binding/Model/Condition88.cs:11-25 models only the first -- its entire state is `Name`, `Parent` and `List<(string Low, string? High)> Values`. src/Cobol.Net.Compiler/Binding/DataBinder.cs:2105-2166 BindCondition walks `value.valueItem()` and nothing else, so alphabet-name-1 and literal-4 are DISCARDED at bind time and every downstream consumer is structurally unable to see them: src/Cobol.Net.Compiler/CodeGen/Emit/ConditionRenderer.cs:398-421 orders EVERY alphanumeric/national range by `ctx.CollateArg` / `ctx.NatCollateArg` (the PROGRAM collating sequence) because there is no per-range alternative to read, and src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SetBinder.cs:451-454 returns BoundUnsupported for SET condition-name TO FALSE because there is no false value to store. This is ONE structural cause with three rule consequences (SR31's alphabet, 14.7.8-via-SR32's alphabet leg, SR27's literal-4 screen), and the fix is one restructuring -- give Condition88 the shape the general format prints -- not three separate guards. ⛔ COLLATION ITSELF IS NOT THE PROBLEM: the same range ordered by PROGRAM COLLATING SEQUENCE is correct, so the missing piece is only the binding of a per-range alphabet-name into the existing collation channel.

### Expected, from the standard
SR31 (13.18.63.3): "Alphabet-name-1 may be specified only when the literals specified in the THROUGH phrase are of class alphanumeric or national. If literal-2 and literal-3 or literal-5 and literal-6 are of class national, alphabet-name-1 shall reference an alphabet that defines a national collating sequence; otherwise, alphabet-name-1 shall reference an alphabet that defines an alphanumeric collating sequence." (cite --check OK) SR32 delegates the range to 14.7.8, whose rule 2 says "When the IN alphabet-name phrase is specified, the collating sequence used for range evaluation is the collating sequence defined by that alphabet" (cite --check OK). Under ALPHABET MYALPH IS "Z" "Y" "X" "A" the ordinals are Z=1, Y=2, X=3, A=4, so "Y" lies within "Z" THRU "X" and the condition is TRUE (C=TRUE), while "A" lies outside it (C2=FALSE). SR27: "The value of literal-4 shall not be equal to the value of any occurrence of literal-2. When the THROUGH phrase is specified: a) when literal-2 is of a class other than alphanumeric or national, the value of literal-4 shall not be equal to any value in the range of any occurrence of literal-2 through literal-3, inclusive." (cite --check OK) -- so v27a and v27b are both nonconforming source and shall be diagnosed; and 13.18.63.4 GR20, "When a condition-name is referenced in a 'SET condition-name TO FALSE' statement, the value of literal-4 from the FALSE phrase is placed in the associated conditional-variable" (cite --check OK), requires the legal control to run.

```
$ python scripts/spec/cite.py --check 13.18.63.3 "Alphabet-name-1 may be specified only when the literals specified in the THROUGH phrase are of class alphanumeric or national. If literal-2 ..."

```

### Observed
v31b prints C=FALSE where the spec computes C=TRUE: with the alphabet discarded, the range is ordered by the native sequence, in which 'Z'(0x5A) collates AFTER 'X'(0x58), so the range is INVERTED and therefore empty (14.7.8 rule 2's last paragraph), and every member test is false. C2=FALSE is right by coincidence, not by construction -- which is why a one-sided probe would have passed. The four SR31 prohibitions are unenforced because nothing ever looks at the parsed IDENTIFIER: `(IN IDENTIFIER)?` at CobolData.g4:623 is not even resolved against SPECIAL-NAMES, so an undeclared word and a symbolic-character name are equally accepted. The literal-4 half is unmodelled rather than unchecked -- Condition88 has no field for it -- which is why SetBinder can only stage the statement loud. MEASURED unchanged at --std 85, 2002, 2014 and 2023.

## 2026-09-13 — Landed

**The note was PARTLY STALE, and re-probing it first is what made the remaining work legible.** Of Format 3's
three operand-bearing constituents, `alphabet-name-1` had already been modelled and bound by the time this fix
started — `Condition88.Alphabet` + `DataBinder.TryResolveRangeAlphabet`, landed as [[PB398]] — so the note's
"Observed" paragraph (`v31b` prints `C=FALSE`) no longer reproduced: on a freshly built `cobol.exe` it prints
`C=TRUE / C2=FALSE`, the spec-derived answer. **literal-4 was the constituent still missing**, and that is what
this landing adds, together with the two rules it held shut.

### What landed

1. **`Condition88.FalseValue`** — literal-4 in the same raw-operand-text convention as `Values`.
   `DataBinder.ScreenFalsePhraseOperand` became `BindFalsePhraseOperand`: it keeps [[PB732]]'s literal-position
   screen and now STORES the operand. The note's own diagnosis was right and the [[PB732]] append's caveat
   ("screened but not bound") was the accurate description of main until now; the reasoning that a field "would
   be a lookup nothing reads" had the causality backwards, which is recorded in the model's doc comment.
2. **§13.18.63.3 SR27** — `DataBinder.CheckFalseValueDistinct`, **COBOLNET2048**. Sentence 1 is unconditional (no
   class qualifier, no THROUGH precondition) and is tested against every occurrence of literal-2; a) adds
   algebraic range membership (§14.7.8 rule 1) and b) collated range membership (rule 2). b)'s "runtime collating
   sequence is known" precondition is read off SR26's NOTE — a LOCALE alphabet is the only unknowable arm, and it
   drops the range half rather than guessing. The ordering is the **runtime's own** `CobolCollation.Compare`,
   materialized at bind time by the new `CollatingTable.Collation(national)`, so the product holds ONE §12.3.7.4
   GR7 k weighting and ONE §8.8.4.2.7 comparison.
3. **§13.18.63.4 GR20 / §14.9.39.4 GR7** — `SET condition-name TO FALSE` stores literal-4. GR6 and GR7 are the
   same sentence with one word changed, so `BoundSetConditions` gained a `ToTrue` selector and `SetEmitter` has
   ONE store path; the FALSE arm inherits the figurative fill, the group-image splice and the category funnel.
   §14.9.39.3 SR7 (the phrase must exist) is **COBOLNET2049**. ⚠ `docs/COBOLNET_CONDITIONS_EXCEPTIONS_DESIGN.md`
   D7 had reserved `COBOLNET0705` for this; that code was never registered in `DiagnosticCatalog` and never
   reached `docs/DIAGNOSTICS.md`, so the doc was corrected to the centrally-allocated 2049 in the same change set.
4. **The 2002 edition gate.** Implementing GR20 without it would have CREATED an under-rejection where a loud
   stage stood: `SET X TO FALSE` at `--std 85` would have compiled and run. Rows `value-false-phrase-2002` and
   `set-condition-false-2002` in `constructs.json`, fired recognition-first from
   `VersionConformancePass.ParseArm`. The edge is DERIVED, not quoted (no 85→2002 VALUE/SET row in the 2023
   Annex E — the A.1 authority gap, D18; and `FALSE` is already reserved at 85 for EVALUATE, so the
   reserved-word evidence cannot date it), and the derivation is stated in the row so it can be overturned in
   one line.
