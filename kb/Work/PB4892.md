# PB4892 - duplicate delivery on a failed ACK write

**What the report says (the implementer's words).** "Duplicate delivery on a failed ACK write (Take), as in the reviewed
report; MessagingProtocol.Take / OnActionFailed; shares root with PB4866." The report gives no repro and no rule. The reviewed
report (`w20261887d-PB4866-report.md`'s predecessor) is not in the scratch directory.

**What the code does on main (read, not run).** `Take` removes the offer, writes `AckFrame`, records the message in `_active`
and completes the RECEIVE with the message. A failed `Write` then reaches `OnActionFailed`, whose trailing block ends the link
(`EndIn(inLink, closeIt: true)`); the requestor, which never saw its ACK, is the side that may send the message again. Whether the
requestor resends, and whether the server then delivers it a second time, is what a later implementer must establish.

**Landed (wave 20261918 B).** Re-probe: `MessagingProtocolTests.AnAckThatCannotBeWrittenDeliversNothingSoTheRequestorsNewRoundIsTheOnlyDelivery` failed before the
fix (the RECEIVE completed when its ACK write failed, and the requestor's new round offered the message again: two deliveries). Root: `Take` issued `Write(ACK)`
and `Complete` as two independent actions, and the executor ran `Complete` after the failed write. Fix: one `Deliver(Ack, Result)` action, performed by
`MessagingPeer.Execute` as write-then-complete; a failed write answers `ActionFailed(Deliver)`, and `OnActionFailed` forgets the `_active` entry, makes the RECEIVE
current again from `_delivery`, and ends the link, so the requestor's new round is the only delivery. Design section 5.4.2 says so.

**Sites:** `src/WiseOwl.Cobol.Runtime/Messaging/MessagingProtocol.cs` (`MessagingProtocol.Take`, `MessagingProtocol.OnActionFailed`, `MessagingProtocol.CompleteReceive`), `src/WiseOwl.Cobol.Runtime/Messaging/ProtocolMessages.cs` (`Deliver`), `src/WiseOwl.Cobol.Runtime/Messaging/MessagingPeer.cs` (`MessagingPeer.Execute`).
