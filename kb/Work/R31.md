# R31 — ResolveQualified requires the QUALIFIER to be unique instead of the MATCH: legal 'Z IN X' (one Z under any X, two Xs) is rejected

> Found by the R21+R22+R30 comprehensive battery's differential leg (2026-08-08): flip
> `syn_definition:931` ("Unique reference with ambiguous qualifiers"), AGREE_ACCEPT →
> WE_REJECT_THEY_ACCEPT carrying COBOLNET1639's qualified arm.

THE CASE (GnuCOBOL's own testsuite, compile-clean expected):
`01 G1. 02 X. 03 Y.` / `01 G2. 02 X. 03 Z.` then `DISPLAY Z IN X`. Two items named X; Z exists under
exactly ONE of them. §8.4.2.2.1: "All available qualifiers need not be specified so long as uniqueness
is established" — the uniqueness demanded is of the QUALIFIED MATCH ("Identical user-defined names may
be specified in a source unit; however, uniqueness shall be established through qualification"), never
of each qualifier name in isolation. `Z IN X` has exactly one match → legal, and GnuCOBOL accepts it.

OUR BEHAVIOR: `ResolveQualified("Z", ["X"])` returns null — the message's own text ("'Z' is declared,
but not under the given qualifier (X)") shows the walk resolves/uniquifies the qualifier first and
fails on X's ambiguity rather than set-matching Z-under-any-X. ⚠ Before R30 this fell into the silent
unresolved staging: the program COMPILED CLEAN and the mis-resolution was invisible — R30's COBOLNET1639
turned a latent wrong-resolution into a visible over-rejection (strictly better, and now fixable at the
root). FIX: ResolveQualified matches the full candidate set — every declaration of the name filtered by
ancestor-chain containment of each written qualifier in order — and demands exactly ONE survivor;
ambiguity of an intermediate qualifier name is irrelevant when the survivor is unique. Sweep the
sibling: the same walk serves condition-names and the OTHER qualified forms (§8.4.2.2.2 formats).
