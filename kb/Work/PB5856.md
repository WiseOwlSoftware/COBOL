# PB5856 - ACCEPT from the device into a binary or packed numeric item converts the whole 80-character record (every edition)

**Ruling: UPHELD (b), harm wrong_answer (silent).** The row `1985-GR-VI.6.5.4-4` does not close on its inherited verdict. An ACCEPT from the device into a binary or packed numeric item converts the whole 80-character record, so characters the rule says are ignored decide the value: the line `12345678` into `PIC 9(4) COMP` stores 5678, where a `PIC 9(4)` DISPLAY item stores 1234. The checker's confidence: high. Cause (b): the same at `--std 2023`. Severity MAJOR: a wrong-answer defect is at least MAJOR.

**Mechanism 1, decided: the code is wrong and one register sentence with it.** `§1985:VI.6.5.4 GR4b` says "only the leftmost characters of the transferred data are stored in the receiving data item" (cite.py OK), and the size it compares is the item's: `§1985:IV.4.3.4` says "The size of an elementary data item or a group item is the number of characters in standard data format of the item" (cite.py OK), four for `PIC 9(4)` whatever its usage. What `§1985:VI.6.5.4 GR1` leaves to the implementor is the conversion ("Any conversion of data required between the hardware device and the data item referenced by identifier-1 is defined by the implementor", cite.py OK), not which characters are converted: a value decided by characters five to eight is a breach of GR4b, not a conversion. The register already says so in A.1 item 5 (the receiving size is "the digit count plus a SIGN SEPARATE position for a fixed-point numeric one"); the sentence of A.1 item 1 that gives a binary or packed item one whole record is wrong and is corrected by the fix. kb/Work PB3513 (landed) took the whole-record read from GnuCOBOL's behaviour; the ISO text controls here, so GnuCOBOL does not decide (CLAUDE.md rule 1). The signed result is right as it is: the five characters `12345` into `S9(4) SIGN LEADING SEPARATE` give `+2345`.

**The checker's evidence (rulings.json, copied).** GR2 fixes the transfer size per hardware DEVICE (one 80-character record here), not per receiver; GR3 and GR4 compare it with the size of the receiving data item, and IV.4.3.4 makes that size the characters in standard data format whatever the usage (`PIC 9(4) COMP` is 4; "usage may cause a difference between this size and that required for internal representation"). 80 is more than 4, so GR4b stores the leftmost four characters and IGNORES the rest. GR1's implementor conversion governs how the stored characters become the item's representation; it cannot let ignored characters decide the value. C4 = K4 = 5678 is decided by characters 5 to 8, and CV = 0 by the "CR" in positions 6 and 7: a breach of GR4b, not a GR1 conversion. Expected: C4 = K4 = 1234, CV = 12.50. S4 `+2345` from `12345` is RIGHT: GR4b's window is the item's 5 characters `12345`, and the register's conversion (DOC-A.1-1 (d): a surplus high-order digit is dropped, the low-order digits kept; no sign is positive) is GR1 latitude over characters GR4b stored.

**The two register entries the checker quotes, and which is right.** DOC-A.1-5 says "The receiving size GR3/GR4 compare against is ... the digit count plus a SIGN SEPARATE position for a fixed-point numeric one ... and exactly one record for a floating-point one": this agrees with ISO, and the code breaks it for binary and packed. DOC-A.1-1 says the text converted is "ONE WHOLE RECORD (item 5) for a binary or packed item, which has no character positions to size a window by" and that "12.50CR into PIC 9(3)V99 COMP is zero": this documents the code and contradicts both DOC-A.1-5 and IV.4.3.4 (the item HAS a standard-data-format size). **DOC-A.1-5 is right; DOC-A.1-1's binary and packed sentence is wrong.**

**What the checker says of kb/Work PB3513.** PB3513 decided the DECIMAL-FORM conversion (GR1 latitude, GnuCOBOL 3.2.0 measured as the tiebreaker) and in passing sized binary and packed as one record because GnuCOBOL does (`termio.c#cob_accept` cuts the line to f->size only for COB_TYPE_NUMERIC_DISPLAY and `cob_move`s the whole line into any other numeric field); it never asked GR4b of that arm, though it applied GR4b to NATIONAL against GnuCOBOL. By CLAUDE.md rule 1 the ISO text controls where it speaks (GR4b's "ignored" is not latitude), so GnuCOBOL is no tiebreaker here. kb/Work PB5755 (landed) closed this row for harness tooling only; no open note covers it.
