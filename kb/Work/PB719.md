# PB719 — LANDED — an ordinal FORM drift re-levels a whole general-rules block

Found 2026-09-06 by the PB697+PB698 implementer (report, "New defects", paragraph (b)). Re-measured here on
`main` at `c34f01ad` and re-confirmed at `f86a5764` (`specs/` and `cite.py` are byte-identical across the
two). The report named GR 5, 6 and 7 — measured, the drift runs from **GR1** and the damage is wider than
one rule.

⚠ **Where the repair's tooling lives.** The `rule-digest` carry guard and the text-keyed migration batches
built for [[PB698]] are on branch `worktree-agent-a978d10810e78251a`, **not on main**.

## What the transcription holds

`specs/ISO_COBOL.md` §14.9.10.4 (DELETE, General rules), md lines 23298–23389. FORMAT 1's rules are written:

```
23302  1. The open mode of the file connector referenced by file-name-1 shall be I-O …
 …
23310  5. After the successful execution of a DELETE RECORD statement, the identified record …
23312  6. If record locking is enabled for the file connector referenced by file-name-1 …
23316     a) The record is not logically removed, and may be accessed.
23318     b) A value is placed into the I-O status associated with file-name-1 …
23320     c) The DELETE RECORD statement is unsuccessful.
23322  7. If record locks are in effect and the file is not subject to an active APPLY COMMIT clause …
 …
23333  8\) The execution of a DELETE RECORD statement does not affect the content of the record area …
23335  9\) The file position indicator is not affected by the execution of a DELETE RECORD statement.
23337  10\) …
23339  11\) …
```

**Rules 1 through 7 carry the `N.` delimiter; 8 through 11 carry the escaped `N\)`.** The printed page numbers
general rules `N)`. The clause's FORMAT 2 block (md 23341 onward, GR12–GR21) carries `N\)` throughout, so the
drift is confined to FORMAT 1's opening run and the correctly-formed rules sit in the SAME clause as the
drifted ones — which is what makes the contrast below decisive.

## The harm, measured — `cite.py --check` on this tree

`scripts/spec/cite.py:44` `TOP = re.compile(r"^(\d+)\\?\)\s")` matches the `)` form only, and
`SUBSUB = re.compile(r"^\s{2,}(\d+)\\?\.\s")` requires two leading spaces, so a column-0 `N.` matches **neither**.
`rule_path` (`:61-72`) walks straight past it and keeps going to the clause heading:

| probe (`python scripts/spec/cite.py --check 14.9.10.4 …`) | answers | the printed path |
|---|---|---|
| `"The open mode of the file connector referenced by file-name-1 shall be I-O"` | `OK §14.9.10.4` *(empty path)* | `1)` |
| `"After the successful execution of a DELETE RECORD statement, the identified record has been logically removed"` | `OK §14.9.10.4` *(empty path)* | `5)` |
| `"If record locking is enabled for the file connector referenced by file-name-1 and the record identified for deletion is locked"` | `OK §14.9.10.4` *(empty path)* | `6)` |
| `"If record locks are in effect and the file is not subject to an active APPLY COMMIT"` | **`OK §14.9.10.4 c)`** | `7)` |
| `"A lock held by that file connector on the deleted record is released at the completion"` | `OK §14.9.10.4 a) 1.` | `7) a) 1.` |
| `"The execution of a DELETE RECORD statement does not affect the content of the record area"` | `OK §14.9.10.4 8)` | `8)` ✔ |
| `"The file position indicator is not affected by the execution of a DELETE RECORD statement"` | `OK §14.9.10.4 9)` | `9)` ✔ |

⛔ **GR7 is reported as `c)`** — a top-level general rule handed the path of a lettered sub-item, and the
sub-item it borrowed belongs to GR6's nested list. The walk stepped over the column-0 `7.`, matched `c)` at
line 23320 as its sub level, then found no `N)` above it and stopped at the clause heading. GR1–GR6 get an
**empty** path: `§14.9.10.4` with no ordinal, which a reader will file as a clause-level citation for a rule
that has an ordinal. GR8 and GR9, which carry the correct form, are correct — that contrast is the proof that
the FORM is the variable.

The sixth row shows the same loss one level down: GR7 a) 1. resolves to `a) 1.` with the top-level ordinal
missing. Every citation of anything in GR1–GR7 of this clause — the whole record-locking block — is affected.

## Why it matters

CLAUDE.md rule 1 makes `cite.py --check` the mechanical gate that stops a wrong clause number from
propagating into code comments, goldens, adjudications and the DEVLOG. Here it answers `OK` and prints the
wrong path, so a citation validated exactly as the rule demands still ships a wrong path. That is the
`feedback_a_real_clause_can_answer_a_different_question` shape mechanized, and the same harm class as
[[PB718]] (lettered items outdented) and [[PB698]] (numbered tails outdented). §14.9.10.4 is a live subject:
`GR-14.9.10.4-6` and `GR-14.9.10.4-15` are claimed by [[PB142]], `GR-14.9.10.4-1` and `-3` by [[PB144]].

MINOR and `process_only`: nothing compiled changes.

## The fix shape, and why it is NOT a one-line sed

**Repair the delimiter form to the printed one, decided on the page** — `python scripts/render-spec-page.py`
against `specs-private/ISO+IEC+1989-2023_ for X_952804 COBOL.pdf`, reading the printed ordinals for
§14.9.10.4 rather than inferring them from the neighbours (PB698's method: the printed page decides). CRLF and
line count preserved, bytes checked after any scripted write.

⛔ **The block must be re-levelled, not just re-punctuated, and the id set must be DIFFED rather than assumed
unchanged.** The form is load-bearing state in the extractor, not cosmetics:
`extract_rule_catalog.py:102` `ORDINAL` captures the delimiter as `form`, and `place()` (`:363-411`) segments
levels on it — case 1 is a *same-form* continuation, case 3 a *same-form* restart, and case 4 exists only as an
escape hatch for exactly this drift (its comment cites §13.18.40.3, which writes SR 1–5 as `N.` and SR 6–37 as
`N\)`). Today §14.9.10.4's ids are produced through that escape hatch; after the repair they are produced
through case 1. The two are expected to agree, and that expectation has not been measured here — measuring it
requires editing `specs/ISO_COBOL.md`, which this registration does not do.

The block already carries a positional sub-list id: **`GR-14.9.10.4-L2.2`** ("A lock held by that file
connector on another record is released at the beginning of the execution …"), the flattened numeric tail at
md line 23329 that [[PB698]] repairs on its branch. So this clause is simultaneously a PB698 site, a
[[PB718]] site (md 23331, `b)` at column 0 — measured to resolve as `a) 1.`) and this one. Sequencing:

1. **Land PB698's branch first.** It removes `GR-14.9.10.4-L2.2` and installs the guard the rest needs.
2. Repair the form here; rebuild `extract_rule_catalog.py` → `build_inventory.py` and **diff the id set for
   this clause before and after**.
3. Run `build_inventory.py --check` with the `rule-digest` carry guard: a positional `L<sublist>.<n>` id
   SHIFTS when a sub-list changes, and PB698 measured six adjudicated rows keeping their id while their text
   changed underneath. If any id moves, migrate **by TEXT**, using PB698's batch format — never by id.
4. Repair PB718's `b)` at md 23331 in the same pass; the three defects overlap in one 40-line block and
   repairing them separately means measuring the same page three times.

**Ship a check that fails first** (`feedback_prove_the_watchdog_fails`). The form drift is detectable
mechanically — a general-rules block whose ordinals change delimiter form mid-run, where the printed page uses
one — and §13.18.40.3 proves this is not a population of one. A `--check`-class gate over the transcription
that enumerates form-drifting blocks, with a fixture proving it fires, is what stops the class regrowing.

## Sweep

⚠ **Not yet enumerated, and it must be before this is called done.** §13.18.40.3 is a known second instance
(named in the extractor's own comment, where the drift is tolerated rather than repaired). The sweep to run is:
every clause whose ordinal run changes delimiter form mid-block, and for each, whether `cite.py` loses the
top-level ordinal the way it does here. Do it with the same probe shape used above — a `--check` on the first
rule after the drift point — rather than by reading the markdown, because the reported path is the artifact
that matters. Family: [[PB698]] (numbered tails), [[PB718]] (lettered items), this note (ordinal form).
