# PB1027 — OPEN

## The rule
`OK  §14.9.51.4 25)` — "If the ADVANCING phrase is not used, automatic advancing shall be provided by the implementor to
act as if the user has specified AFTER ADVANCING 1 LINE."
After `WRITE … BEFORE ADVANCING 1`, the device is already positioned at the start of a fresh line; "AFTER 1" read
literally advances again, leaving an empty line. On a LINAGE file's first write of a page the same reading leaves line 1
blank.

## What the adjudicator owes
Decide under the ISO → GnuCOBOL precedence (`feedback_follow_gnucobol_on_split_latitude` covers only implementor
latitude — "shall be provided by the implementor to act as if" is a behaviour, not a choice, so the literal reading
wins unless the standard elsewhere says a positioned device satisfies it). Measure GnuCOBOL's output for both shapes;
record the ruling in docs/CONFORMANCE.md and golden it, and reconcile with the NIST goldens that pass today.

**The defect.** On every file the build treats as vertically positioned (record-sequential print files, LINAGE files of either organization, line
sequential files), a WRITE with no ADVANCING phrase does not act as AFTER ADVANCING 1 LINE: when no line is open the single advance is placed as a
BEFORE advance. The file differs from the one the same program writes with `AFTER ADVANCING 1 LINE` spelled out; on a LINAGE page overflow the overflowing
record lands on the wrong page.

**Spec (cite.py --check OK; the refuter notes `cite.py` takes the BARE clause number, `14.9.51.4`, with the rule number in the quoted text).**
- `§14.9.51.4 25)`: "If the ADVANCING phrase is not used, automatic advancing shall be provided by the implementor to act as if the user has specified
  AFTER ADVANCING 1 LINE." No implementor choice of placement. `25) a), e), f)`: advance, BEFORE presents before the advance, AFTER presents after it.
- `§14.9.51.4 26)`: "If the AFTER phrase is specified or implied, the device is repositioned to the first line that may be written on the next logical page
  and the logical record is presented on that line." ("or implied" names the plain WRITE.)
- `§13.18.34.4 7)`: LINAGE-COUNTER is the line the device is positioned at, set to one at OPEN OUTPUT, "When the ADVANCING phrase of the WRITE statement is not
  specified, the LINAGE-COUNTER is incremented by the value one", reset to one at each following logical page.
- Escape: `§14.9.51.4 25)` "If the physical file does not support vertical positioning, the ADVANCING and END-OF-PAGE phrases are ignored"; the build honours
  explicit ADVANCING on line sequential files (`docs/CONFORMANCE.md` DOC-A.1-114), so the plain WRITE must equal explicit AFTER 1. Refuter additions: `§A.3 37)`
  makes positioning capability processor-dependent; `§14.9.27.4 18)` makes the post-OPEN position implementor-defined (DOC-A.1-130); `§14.9.51.4 18)` EXTEND.
- NIST SQ101M GF-19/-21/-22 and SQ209M GF-03 self-describing text fit the strict device model; the repo's NIST print goldens are this compiler's own output
  (re-baselined at PB964) and are no evidence.

**Observed (pinned build; explicit AFTER 1 versus plain; ls = LINE SEQUENTIAL, rs = record sequential, lsl/rsl = with `LINAGE IS 6 LINES`).**

| shape | explicit AFTER 1 | plain WRITE |
|---|---|---|
| ls: two writes | CRLF AAAAA CRLF BBBBB CRLF (leading empty line) | AAAAA CRLF BBBBB CRLF |
| lsl/rsl: two writes (LC 2, 3 both) | leading empty line first | none |
| BEFORE 1 A, then B | AAAAA, empty line, BBBBB | AAAAA, BBBBB (no blank) |
| ls no LINAGE: AFTER A, plain B, AFTER C | clean | an extra blank line before C (double travel) |
| LINAGE overflow | C on page 2, body line 1 | C on page 1, body line 3 (identical to explicit BEFORE 1) |

Minimal repro `PB1027\src2\ovf-rs-plain.cob`: `FD F1 LINAGE IS 3 LINES LINES AT TOP 1 LINES AT BOTTOM 1`, five plain writes A..E; counters and END-OF-PAGE on C
are identical for the three forms, the bytes are not (plain = explicit BEFORE 1, byte for byte). Refuter additions (same defect): `bpage-rsl/lsl` and `bpage-rs/ls`
(BEFORE PAGE then plain), `foot-rsl/lsl` (FOOTING overflow), `--std 85` (not edition-specific); `extend-ls`: the fix ALSO puts an empty line at the start of every
OPEN EXTEND session.

**Code.** `src/Cobol.Net.Runtime/IO/SequentialConnector.cs#ImplicitAdvanceIsBefore` (`!_lineOpen`, line 1176), consumed by `WriteRecord` (line 1077, print/LINAGE reroute
`WriteAdvancingRecord(..., before: ImplicitAdvanceIsBefore, ...)`) and by both arms of `EmitLineSequentialRecord` (lines 1154 and 1158). The tests that pin the defect:
`LinageConformanceTests.Bytes_LineSequentialLinageFile_GetsTheSameMargins` (cites the BEFORE rule for a plain WRITE) and
`Bytes_LineSequential_EveryPlacementMix` row LNGBYH (`AAAA\r\nBBBB\r\nCCCC\r\n`).

**Fix guidance.** Make the plain WRITE the explicit AFTER ADVANCING 1 LINE path in every state: delete `ImplicitAdvanceIsBefore`, route the omitted phrase through
`WriteAdvancingRecord(..., lines: 1, before: false, ...)` on every arm (this also removes the line sequential double travel); pair with a drift test writing each mix twice
(phrase omitted and `AFTER ADVANCING 1 LINE` written) asserting byte equality. Consequence to state openly: a non-LINAGE LINE SEQUENTIAL file written only with plain WRITEs
gains a leading empty line (a READ returns an extra empty first record). Scope additions from the refuter: `docs/CONFORMANCE.md` DOC-A.1-130 pins the defective placement in
its worked example (TOP 2: "one plain `WRITE` of `AAA` gives two empty lines" becomes three), DOC-A.1-114, the `docs/COBOLNET_FILES_DESIGN.md` print-stream paragraph ("when no
line is open ... lands the record on a fresh line") and the `SequentialConnector` comments citing GR25 e) for a plain WRITE; re-baseline every golden pinning the BEFORE placement.

**Corrections to the decision (refuter; none reverses the verdict).**
1. The GnuCOBOL `-fwrite-after` claim is overstated: on LINAGE files it does NOT match section 1 (`gcwa\lsl-after2`, `lsl-beforeafter` give `AAAAA\nBBBBB\n`, no blank body line
   1, no blank after BEFORE). GnuCOBOL witnesses only the overflow page and the non-LINAGE line sequential shapes; the fixer must not take LINAGE bytes from GnuCOBOL. (See also the
   operator caveat: `-fwrite-after` is non-default.) Default cobc: BEFORE (no leading blank), LINAGE overflow with plain WRITE puts C on page 1.
2. "The only conforming way to avoid the leading empty line is the GR25 escape clause" is false: `§A.3 37)` (per-file capability) and `§14.9.27.4 18)` (post-OPEN position) are
   two more latitudes. Any owner question must list these options.
3. "Differs in every mix" is overstated: after an AFTER write (open line) plain and explicit AFTER are byte-identical on rs, rsl and lsl; only non-LINAGE line sequential differs.
4. Expected (2), "the first plain WRITE on a LINAGE page leaves body line 1 blank", holds after OPEN, after BEFORE PAGE and after a BEFORE-arm overflow, NOT after an implied-AFTER
   overflow, where GR26 a) presents the record ON line 1. A literal reading would wrongly blank line 1 of every page.
