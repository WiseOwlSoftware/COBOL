# PB843 — LANDED — one word, two name classes, and the parser picks first

Source: the `PB398` implementer report, items (A) and (B). One mechanism: in both cases BOTH readings are
complete parses and §8.3.2.2 makes alphabet-names, class-names and data-names DIFFERENT TYPES of user-defined word
("Within a source element, a given user-defined word may be used as only one type of user-defined word" —
`cite.py --check 8.3.2.2` OK; this note first carried §8.4.1, which says no such thing), so only the resolved
symbol separates them.

(B) `p07_eval_bare_classname.cob` vs its control `p07b_eval_is_classname.cob`:

## The rules, quoted

```
$ python scripts/spec/cite.py --check 14.9.13.3 "Alphabet-name-1 may be specified only when the literals or identifiers specified in the THROUGH phrase are of class alphabetic, alphanumeric, or national"
  OK  §14.9.13.3 3)  (Syntax rules)
```

SR3 names "the literals **or identifiers** specified in the THROUGH phrase", so an identifier-4 range with
`IN alphabet-name-1` is legal source.

```
$ python scripts/spec/cite.py --find "a class condition without the identifier"
  §14.9.13.3 5)  (Syntax rules)
      5) A selection object is a partial-expression if the leftmost portion of the selection object is a relational operator, a class condition without the identifier, a sign condition without the ...
```

A bare class-name IS a selection object shape the standard prints; the `IS`-led spelling working while the bare
one does not is the tell that the grammar, not the rule, is deciding.

## Code sites

* `src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs#ResolveImpl` — the resolver cannot re-resolve a reference
  without its trailing qualifier; its four independent `dataReferenceSuffix()` walks (~181, ~344, ~660, ~848,
  ~903) each consume the qualifier eagerly.
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs#ObjectKind` — needs an EVALUATE-local symbol
  probe routing a class-name to the already-extracted `ConditionBinder.BindClassConditionOn`.

Flipping the ANTLR preference is not the fix: making the `IN` phrase an earlier alternative makes the OPPOSITE
legal reading (a genuinely qualified identifier-4) unreachable instead. The structural answer is one
symbol-aware re-resolution service both sites call — "resolve this word-run, and tell me which name class
consumed each trailing word" — with a drift test over the four walks so a fifth cannot be added blind.

## Sibling sweep the fixer owes

  IN alphabet`), and the SORT/MERGE KEY `IN` phrase.
* `CobolExpressions.g4#valueRange`'s comment already records the ambiguity — keep it accurate.

## Landed — wave 45 finisher (w45e2)

Re-probed first on the finisher's build (`w45e2/p07.cob`): both shapes still COBOLNET1639 (`'MY-DIG' is not defined`,
`'WS-HIINAL' does not uniquely identify`). AFTER: `CLASS-YES`, `IN-RANGE`.

**Shape.** The note's prescription — one symbol-aware re-resolution SERVICE over the resolver's four suffix walks —
proved larger than the problem once the standard was swept: the ONLY general format that prints `IN alphabet-name`
after an operand that can be an identifier is §14.9.13.2's range-expression (the VALUE clause's formats 3/5, the CLASS
clause and SYMBOLIC CHARACTERS put it after literals/integers; the SEARCH ALL, relation and SORT/MERGE siblings the
note listed print no such phrase). So the resolver is not taught a second resolution path; the binder that owns the
phrase decides by symbol and hands the resolver the DECIDED reference:

* (A) `EvaluateBinder.BindRangeHigh` — a LAST suffix that is `IN word` (never `OF`, never subscripted) naming a
  declared alphabet of either class (`DataBinder.IsAlphabetName`) is the phrase. The reference is bound from
  `ReferenceResolver.WithoutTrailingSuffix`, a synthetic copy that ADOPTS the original children (the
  `BinderDriver.Reparent` technique) without mutating the tree, so every walk sees the decided reference.
  `WS-H2 IN GRP1 IN AL` keeps GRP1 as a qualifier and AL as the alphabet. `TrailingInPhraseDriftTests` scans every
  `.g4` rule for an identifier-ending operand followed by `IN cobolWord` and requires a named symbol-aware consumer,
  so a second such phrase cannot be added blind (the note's drift test, aimed at the grammar, where the next case
  would actually arrive).
* (B) `ConditionBinder.BareClassWord` is the one symbol test (a bare word naming a class-name / alphabet-name that
  does not probe as a data item); `AnalyzeBareOperand` reports it as the new `BareOperandForm.ClassName`, and
  `EvaluateBinder.ObjectKind` maps it to Table 15's partial-expression row. The SAME defect had a THIRD parse the note
  did not name: the word LEADING a combined object (`WHEN MY-DIG AND WS-F = "Y"`) is claimed by `evaluateWhenItem`'s
  `condition` alternative, and it compiled clean and died at run time (`NotImplementedCobolFeatureException:
  condition 'MY-DIG'`). `LeadingBareClassWord` finds it; the one SR8 arm binds all three parses; the sole-operand leaf
  consumes the spliced subject exactly as `partialComparison` does. The user-word class arms of
  `BindClassConditionOn` were extracted to `BindUserWordClassCondition`, so the §8.8.4.4.3 SR2 LOCALE refusal and the
  SR3/SR4 operand screens are shared with the written `IS class-name` spelling.
