# PB1929 — LANDED (wave 1009 B)

## Landed

Re-probed: `SET B TO FUNCTION FOBJ(1)` (object reference) was `COBOLNET0867` and `SET P TO FUNCTION FPTR(1)` (pointer)
`COBOLNET0869`, exactly as filed. Fixed through the ONE sender classifier the note asks for — the same `SetSender` /
`SetSenders.Classify` PB1399's Format 1 arm reads (see PB1399): the sender is an identifier of any of §8.4.3.1.2's formats
(§8.4.3.1.3 SR1), and a function-identifier or inline method invocation references a data item whose class and category
are the RETURNING item's (§8.4.3.2.1; `cite.py --check 8.4.3.4.4 "temporary data item"` OK for the invocation).

* Formats 7, 8 and 9 (`BindSetPointer` / `BindSetFunctionPointer` / `BindSetProgramPointer`) resolve the sender through
  one helper, `CarrierSenderPlace`: a data reference through the sending chokepoint, a function / invocation through
  its returned temporary (bound ONCE by the classifier; the activation is a statement pre-op). The three carrier arms had
  each written the same resolve-and-screen scaffold; they now share it.
* Format 5 (`OoBinder.OoBindSetObjectRef`) takes the sender as a `SetSender`: the EXCEPTION-OBJECT and class-name readings
  stay properties of a WRITTEN reference, while an identifier sender enters the conformance table
  (`ObjectRefAssignmentMismatch`) through its temporary's own object-reference description.
* The keyword-omitted function (`SET B TO FOBJ(1)`, §8.4.3.2.3 SR2) is classified as the function it is, and the inline
  invocation (`SET A4 TO F1 :: "MAKE"`) as the Format 4 identifier it is.
* `BindSetTo` decides Formats 14, 16, 17 and "no format" from the receiving list BEFORE classifying the sender (a
  classification binds, and F14/F16 bind the same amount themselves).

Witnesses: `conformance:2002/pb1929_set_identifier_senders` (UDF object reference, the keyword-omitted spelling, an inline
invocation, a UDF returning a data pointer, a UDF returning a program pointer that is then CALLed, a UDF returning an
index) and negatives `pb1929-set-object-from-numeric-function` (SR9, `COBOLNET0867`) and
`pb1929-set-pointer-from-object-function` (SR17, `COBOLNET0869`). Format 8 has its own 2014 golden,
`conformance:2014/pb1929_set_function_pointer_function_sender`, because writing it found a SIBLING DEFECT (I9, fixed in
this change): a FUNCTION-ID `RETURNING USAGE FUNCTION-POINTER` did not compile at all — the generated
`StoreReturn(__ret, L_RES)` bound only to the object-reference generic (`CS0315`) since `CobolArgAdapt.StoreReturn` had
overloads for the data-pointer and program-pointer carriers and none for `FunctionPointer`. The overload is the program
twin's; the golden's `SET FP TO FUNCTION PB1929FP(1)` then equals the address `ADDRESS OF FUNCTION` produced (`FP-SAME`).

Filed by the train-1005 lander from wave 1005 group C's report (`w1005c-PB1423-report.md`, lead 1). Not re-probed by
the lander (MANDATORY-PRACTICES R2: the lead carries its repro and code site).

## The defect

A function-identifier IS an identifier (§8.4.3.2.4 GR1 — it references a temporary data item with the RETURNING
item's description), so it may stand wherever SET's syntax rules ask for an identifier of the right category:
`python scripts/spec/cite.py --check 14.9.39.3 "Identifier-6 shall be of category data-pointer"` →
`OK §14.9.39.3 17)`. `SetBinder.BindSetTo` extracts the sender through `OoBinder.OoExtractBareReference`, which is
null for anything but a bare data reference, so the Format 5 (pointer), Format 7 (object reference) and Format 8
(program/function pointer) arms see "no identifier" and refuse the sender as a literal or an expression. PB1399 is the
same shape for the index Format 1 arm (`IndexAssignmentSenderOf`); fix both through one sender classifier.

**Repro.** A FUNCTION-ID `FOBJ` returning `USAGE OBJECT REFERENCE`, then `SET B TO FUNCTION FOBJ(1)` with `B` an object
reference — COBOLNET0869. The same with a pointer-returning function and Format 5 — COBOLNET0867.

**Sites.** `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SetBinder.cs` (~:1047 the extraction; the per-format
`senderRef`-null arms ~:449, ~:549, ~:644).
