# PB5674 - SET of an index outside its table does not raise EC-BOUND-SUBSCRIPT at --std 2002 with checking enabled

**Sites:** `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/SetEmitter.cs#EmitSetTo`, `#EmitSetUpDown`, `#AugmentSetTarget`;
`src/WiseOwl.Cobol.Runtime/Values/Tables/CobolIndex.cs#TryAmount`, `#Land`, `#Accept`, `#Augment`.

**The harm.** A wrong answer at `--std 2002` with checking enabled: under `>>TURN EC-BOUND-SUBSCRIPT CHECKING ON`, `SET IX TO 11` on a table of 10 leaves IX at 11 and runs no declarative, where the 2002 rules leave IX unchanged (3) and raise EC-BOUND-SUBSCRIPT. The program then reads a wrong index value and never sees the exception it enabled checking for.

## What 2002 requires

Adjudication PB5625 reading C decides it: with checking enabled the normative rules of SET apply as written.

- Format 1, `SET index-name-1 TO arithmetic-expression-1`: §2002:14.8.35.3 GR2a.1, the value is a subscript determined
  as 8.4.1.2 describes, "otherwise the execution of the SET statement is unsuccessful and the content of the receiving
  operand is unchanged"; §2002:8.4.1.2.3 GR2 makes a value "greater than the highest permissible occurrence number" (or
  less than one) the EC-BOUND-SUBSCRIPT condition: "greater than the highest permissible occurrence number, the
  EC-BOUND-SUBSCRIPT exception condition is set to exist".
- Format 2, `SET index-name-3 UP BY / DOWN BY arithmetic-expression-2`: §2002:14.8.35.3 GR3b, "otherwise the
  EC-BOUND-SUBSCRIPT exception condition is set to exist, the execution of the SET statement is unsuccessful, and the
  content of the receiving operand is unchanged"; GR3a, the same for an amount that is not an integer ("If
  arithmetic-expression-2 does not evaluate to an integer, the EC-BOUND-SUBSCRIPT exception condition is set to exist").

EC-BOUND-SUBSCRIPT is fatal (§2002:14.5.12.1.5, "Subscript out of bounds"). With checking NOT enabled the result is
implementor-defined (§2002:14.5.12.1.2 item 5) and is determination `D-SET-INDEX-UNCHECKED`, not this defect.

## Mechanism (read, not fixed)

`SetEmitter.EmitSetTo` and `EmitSetUpDown` land the amount through `CobolIndex.TryAmount` / `TryAmountReal` (the one
SET-family amount landing, kb/Work PB459) and store or augment inside its success leg. The landing tests integrality
(EC-BOUND-SUBSCRIPT) and the implementor index range of the 64-bit carrier (EC-RANGE-INDEX); `CobolIndex.Augment` tests
only that range. No path consults the table's occurrence bounds, by design: the type's remarks state the 2023 rule ("an
index pointing past its own table is legal and must not raise. A table-bounds test here would reject conforming
programs"), and every comment on these members cites §2023:14.9.39.4.

**Edition-dependent paths today:** none at run time. The emitter and `CobolIndex` take no edition and branch on none.
The binder's only edition-dependent step for these formats is `SetBinder.GateCobol85IndexAmount`, which gates the
SYNTAX of the sending operand at `--std 85` (construct row `set-arithmetic-expression-2002`); it does not touch the
range rule. So `--std 2002` runs the 2023 semantics.

## Scope for the fix

The adjudication names the sibling arms: in the 2002 text EC-BOUND-SUBSCRIPT is named only in 8.4.1.2.3 and in SET's
GR3a and GR3b, so the arms are SET format 1 (through 8.4.1.2) and both rules of format 2; PERFORM VARYING has no such
rule in 2002 (F.2 item 93 agrees). Whether 2014 and 2023 word SET differently is for the fix to read in each edition's
own text. The fix also owns the comments in `CobolIndex` and `SetEmitter` that state the 2023 rule as edition-free.
