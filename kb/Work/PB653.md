# PB653 — OPEN — the mode is right now; the scale still is not

Found 2026-09-05 by the `PB647` implementer (report §"New defects" (1)), which made the float→fixed landing's
SCALE and MODE one decision on `ReceiverContext.FloatLanding(finalTransfer)`: a final transfer lands at the
resultant identifier's scale with the statement's mode, a NESTED operand at the capped working scale with
truncation. The nested arm is where this note lives: its working scale carries no guard digits, so the
truncation happens one digit too early and the later multiply propagates the loss.

## Repro (`--std 2014`, native arithmetic; measured on PB647's tree)

```cobol
       01 R  PIC 9V9(9).
       01 C2 USAGE COMP-2.
           COMPUTE C2 = FUNCTION SQRT(3)
           COMPUTE R  = C2 * 2                   *> 3.464101615   (correct: 2 × 1.7320508075688772… = 3.4641016151…)
           COMPUTE R  = FUNCTION SQRT(3) * 2     *> 3.464101614   ⛔
```

Same binary64 in both positions — the COMP-2 item and the function's returned value — two different answers. The
COMP-2 arm is right because a data item's operand path lands through `Align` with the guard the division path
also uses; the function's returned value lands through the nested float arm at exactly the working scale.

## The rule

§15.4.1: "the returned value is the same for all instances of a given function within a single execution of the
runtime element so long as the value and order of the arguments, the collating sequence, and the locale are
unchanged" (`OK §15.4.1`) — and a returned value that is the same binary64 as a COMP-2 item must produce the same
arithmetic result when used the same way; §8.8.1.3 grants native arithmetic "an implementor-defined method of
evaluating an arithmetic expression, an arithmetic statement, the SUM clause, and all integer and numeric
functions" (`OK §8.8.1.3`), which licenses a working scale but not two working scales for one value. The measured
reference behaviour (the COMP-2 arm) is the implementation's own determination, applied to one of two identical
operands.

## The mechanism

`src/Cobol.Net.Compiler/CodeGen/Emit/NumericRenderer.cs`: `Divide` carries `private const int DivGuardDigits = 14`
(`:565`) and computes `guard = Math.Min(DivGuardDigits, maxExp - …)` (`:596`) — the working-scale question asked
and answered for division. PB647's nested float arm (`ReceiverContext.FloatLanding(finalTransfer: false)` → the
capped working scale, TRUNCATION) has no equivalent: the double is quantized at the working scale itself, so a
subsequent `* 2` starts from a value already short by the truncated digit.

## Fix shape

Give the nested float arm a guard exactly as `Divide` does — `FloatLanding(false)` returns `min(working scale +
guard, the carrier's capacity)` with the guard derived the way `DivGuardDigits` is (the carrier headroom at that
integer width), so a nested float operand carries the digits a nested quotient carries; state the guard once (a
shared `GuardDigits` helper for both arms, not a second constant). Goldens at 2002/2014/2023: the pair above
asserting equality, `SQRT(3) * 2`, `SQRT(2) / 3` (a nested quotient of a float), and a chain of three float
operands; extend `FloatLandingModeDriftTests` with an invariant that a nested float operand and a COMP-2 item
holding the same double produce the same result across the 32×32 picture shapes.
