# PB653 — LANDED — the mode was right; the scale was not, and the answer is not to tune it

Found 2026-09-05 by the `PB647` implementer (report §"New defects" (1)), which made the float→fixed landing's
SCALE and MODE one decision on `ReceiverContext.FloatLanding(finalTransfer)`: a final transfer lands at the
resultant identifier's scale with the statement's mode, a NESTED operand at the capped working scale with
truncation. The nested arm is where this note lives: its working scale carries no guard digits, so the
truncation happens one digit too early and the later multiply propagates the loss.

## Repro (`--std 2014`, native arithmetic; measured on PB647's tree)

```cobol
       01 R  PIC 9V9(9).
       01 C2 USAGE COMP-2.
           COMPUTE C2 = FUNCTION SQRT(3)
           COMPUTE R  = C2 * 2                   *> 3.464101615   (correct: 2 × 1.7320508075688772… = 3.4641016151…)
           COMPUTE R  = FUNCTION SQRT(3) * 2     *> 3.464101614   ⛔
```

Same binary64 in both positions — the COMP-2 item and the function's returned value — two different answers. The
COMP-2 arm is right because a data item's operand path lands through `Align` with the guard the division path
also uses; the function's returned value lands through the nested float arm at exactly the working scale.

## The rule

§15.4.1: "the returned value is the same for all instances of a given function within a single execution of the
runtime element so long as the value and order of the arguments, the collating sequence, and the locale are
unchanged" (`OK §15.4.1`) — and a returned value that is the same binary64 as a COMP-2 item must produce the same
arithmetic result when used the same way; §8.8.1.3 grants native arithmetic "an implementor-defined method of
evaluating an arithmetic expression, an arithmetic statement, the SUM clause, and all integer and numeric
functions" (`OK §8.8.1.3`), which licenses a working scale but not two working scales for one value. The measured
reference behaviour (the COMP-2 arm) is the implementation's own determination, applied to one of two identical
operands.

## The mechanism

`src/Cobol.Net.Compiler/CodeGen/Emit/NumericRenderer.cs`: `Divide` carries `private const int DivGuardDigits = 14`
(`:565`) and computes `guard = Math.Min(DivGuardDigits, maxExp - …)` (`:596`) — the working-scale question asked
and answered for division. PB647's nested float arm (`ReceiverContext.FloatLanding(finalTransfer: false)` → the
capped working scale, TRUNCATION) has no equivalent: the double is quantized at the working scale itself, so a
subsequent `* 2` starts from a value already short by the truncated digit.

## Fix shape

Give the nested float arm a guard exactly as `Divide` does — `FloatLanding(false)` returns `min(working scale +
guard, the carrier's capacity)` with the guard derived the way `DivGuardDigits` is (the carrier headroom at that
integer width), so a nested float operand carries the digits a nested quotient carries; state the guard once (a
shared `GuardDigits` helper for both arms, not a second constant). Goldens at 2002/2014/2023: the pair above
asserting equality, `SQRT(3) * 2`, `SQRT(2) / 3` (a nested quotient of a float), and a chain of three float
operands; extend `FloatLandingModeDriftTests` with an invariant that a nested float operand and a COMP-2 item
holding the same double produce the same result across the 32×32 picture shapes.

## Landed 2026-09-22 (wave 44, fix-lane group B)

RE-PROBED FIRST on this worktree's own build, and it reproduced exactly as written:
`COMPUTE R = FUNCTION SQRT(3) * 2` into `PIC 9V9(9)` gave 3.464101614 against the COMP-2 arm's 3.464101615.
The re-probe also measured THREE things the note did not:

1. **Native `**` had the same defect through the same eager quantization** — `COMPUTE T = FUNCTION SQRT(10) ** 2`
   gave 9.999999998 where `C2 ** 2` gave 10.000000000. `NumericRenderer.Power`'s `b.Real` arm never fired,
   because the nested SQRT had ALREADY been quantized to a non-`Real` `NumX` before it got there.
2. **The RELATION channel was already correct**, and agreed with the COMP-2 item
   (`IF FUNCTION SQRT(10) * FUNCTION SQRT(10) = 10` and `IF C2 * C2 = 10` both answered NE, the honest binary64
   answer under §8.8.4.2.4). So the arithmetic channel was the one arm out of step, not the float lane.
3. **The note's fix shape — guard digits — is WRONG, and measurably so.** A landing cannot know how many
   multiplications sit above it, so a guarded scale ACCUMULATES: at `DivGuardDigits`'s 14 a nested float operand
   lands at scale 23 and `FUNCTION SQRT(10) * FUNCTION SQRT(10)` multiplies two scale-23 operands into a
   scale-46 product — past the 38-digit `Int128` carrier, where the unchecked no-phrase store WRAPS.
   `Divide` can afford its guard only because it clamps against its OWN radix alignment, which it knows.

**The fix is therefore the root, not the tuning: a nested float operand is NOT QUANTIZED AT ALL.** It keeps its
binary64, `CombineCore`'s `Real` lane evaluates the expression entirely in IEEE binary64 (numeric design D16,
§8.8.1.3's implementor-defined method), and the ONE quantization happens where the value is transferred to the
resultant identifier. §15.4.1's identity then holds BY CONSTRUCTION across the arithmetic, relation, text and
MOVE channels instead of by arithmetic luck.

`ReceiverContext.FloatLanding` now returns a `FloatLandingDecision` — `Binary64`, or `At(scale, mode)` — and
ABSORBS the receiver-shape half both consumers used to spell for themselves (`Receiver.Real ||
Receiver.Receiverless` in `IntrinsicRenderer.RenderFloatNative`, `b.Real || e.Real || _rcv.Real ||
_rcv.Receiverless` in `NumericRenderer.Power`). Those two private copies of half a rule are exactly why neither
consumer inherited the nested case when PB647 added it — feedback_two_arm_dispatch, sixth sighting.
`FloatLandingModeDriftTests` gained the `Binary64` invariants and a source scan that fails if either consumer
re-derives the receiver-shape test in its own landing body.

Goldens: `85/pb653_nested_float_operand` (the introducing edition — FUNCTION SQRT, COMPUTE, COMP-2 and `**` are
all COBOL-85 constructs here; seven paired arms, every expected value computed from the exact binary64
expansion), `2014/pb653_nested_float_rounded_mode` (the eight-mode ROUNDED phrase over a nested-float
expression, the `SQRT(0.0625)` exact-half tie that separates the four NEAREST modes, and PROHIBITED finally
seeing the whole value), `negative/pb653-nested-float-rounded-mode-below-2014` (COBOLNET0803).
Design: `docs/COBOLNET_NUMERIC_DESIGN.md` D20 rewritten (its "Known residue" paragraph, which was this note,
is retired) and D18 cross-referenced.

**Sibling found and NOT fixed here** — `IntrinsicRenderer`'s `NumvalF` arm has the identical working-scale
truncation for a NESTED operand (`COMPUTE R = FUNCTION NUMVAL-F("1.7320508075688772") * 2` into `PIC 9V9(9)`
gave 3.464101614 against the COMP-2 arm's 3.464101615, measured), but PB653's cure does NOT fit it: its
fixed-receiver landing is an EXACT decimal parse (§15.69.4 r2 / PB60) carrying MORE precision than a binary64,
so routing it to the binary64 lane would LOSE digits (a 20-digit argument feeding `PIC 9(31)`). It needs its own
determination and is reported as a lead.
