Filed 2026-09-26 by the **train-62 lander** from the w61h implementer report (PB1418/PB1115), lead 2.

## Observation (reported by the implementer, not re-probed by the lander)
PB1418 made a figurative constant or `ALL literal` argument passed BY CONTENT fill an ELEMENTARY formal to its size,
as §8.3.3.6.4 GR2 requires. The helper `CallEmitter.FigurativeFillWidth`
(`src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs`) returns a width only for an elementary formal that is not
any-length and not dynamic-length. A GROUP formal gets width null, so its argument crosses as one occurrence
(`"*"` rather than `"****"`). The implementer limited the fill to elementary formals on purpose: a group's extent
can be variable (OCCURS DEPENDING ON) and is then known only at run time.

Repro: `CALL "SUB" USING BY CONTENT ALL "*"`, with SUB's linkage formal `01 G. 05 A PIC X(2). 05 B PIC X(2).`
and SUB displaying G. Expected: `****`. Actual: `*` followed by the space-filled rest.

## Fix direction
For a fixed-extent group, the fill width is the group's image width at bind time. For a variable-extent group,
the width has to come from the run-time crossing. `CobolArgAdapt` or the content carrier sizes the value to the
formal's current extent, which is the one place that knows it. The fix should give one answer for both, not a
second compile-time table.

## Landed (w62o implementer, 2026-09-26)
Re-probed on the worktree build: `CALL "S" AS NESTED USING BY CONTENT ALL "*"` into `01 G. 05 A PIC X(2). 05 B PIC X(2).`
displayed `G=[*   ]`; a function with a group formal returned `*   `; and INVOKE refused every figurative but NULL
(COBOLNET0828 "not yet carried") - so the defect was one arm wider than the note said.

**Rule.** §14.2.3 GR9 second branch (cite.py OK 9)): the allocated record is "a data item with the same description and
the same number of bytes as the formal parameter, where the maximum length is used if the formal parameter is described
as a variable-occurrence data item", filled by "a MOVE statement"; §8.3.3.6.4 GR2 (OK 2)) repeats the figurative to its
positions. The note's premise that a variable-length extent is a run-time fact does not hold: an OCCURS DEPENDING
formal's record is allocated at its MAXIMUM (compile-time), and a §8.5.1.12 variable-length group admits no move from
a non-group at all (§8.5.1.12.1, OK) - a bind-time non-conformance, not a fill.

**Fix.** `CallEmitter.FigurativeArgumentImage` is the ONE value of a figurative / ALL-literal argument for CALL, function
and INVOKE (new `BoundInvokeArg.ContentFill` channel; ZERO into a numeric INVOKE formal takes the numeric-literal
lane); `FigurativeFillWidth` = the formal's text-crossing window `BoundaryImageWidth` (groups, as-if groups, ODO at max).
The private GR2 copy `CallEmitter.RepeatToWidth` is deleted for `EmitText.RepeatToWidth`. Sibling: a group formal now asks
`ParameterConformance` the WHOLE MOVE question (`MoveTable16.Validity`, §14.9.25.3 SR2 strong type + SR9 variable-length),
which also admits an integer literal into a group formal (was refused); and a class-pointer / object-reference
formal takes §14.8.2.3.3's SET paragraph, refusing a literal or non-NULL figurative at bind (was a run-time
EC-PROGRAM-ARG-MISMATCH on CALL, and a backend CS1503 on INVOKE once INVOKE carried figuratives).
Goldens: `tests/conformance/2002/pb1617_figurative_group_formal_fill`; negatives
`pb1617-call-content-figurative-varlength-group` (2014/2023, COBOLNET1688), `pb1617-invoke-figurative-strong-group`
(2002+, COBOLNET0828) and `pb1617-call-content-figurative-pointer-formal` (2002+, COBOLNET1688).
