# PB377 — a schedule-dependent red in the collation key cache

Found by the orchestrator while watching CI on 2026-09-02/03: the Linux unit shard failed
`Collation.CollationKeyCacheTests.ConcurrentCallers_GetOneKeyPerText_AndNeverAWrongOne` on three of the eight
`main` runs of the day (commits fd57ef89, c5643508 and the pause commit 80b4f1e6), and the failed job passed when
re-run once. Windows never reproduced it. Owner standing rule: **do not dismiss it as noise** — a failure that a
re-run hides is exactly the shape PB126 had, and PB126 turned out to be a real cross-test race.

## What is known

- PB106 landed the cache (`ConcurrentDictionary<string, CacheEntry>`, static `GetOrBuild`, LRU / size-based
  eviction, `CacheConfig` from the environment). PB126 landed the shared xUnit collection that serialises the
  cache tests against `RuntimeConfigTests`' process-global reads. Both are `landed`; this is a THIRD mechanism.
- The failing assertion is the concurrency invariant itself: N callers asking for the key of the same text must
  all receive one key, and never a key built for a different text. A wrong key at runtime WOULD be a wrong answer
  (a SORT/MERGE key column or an INDEXED LOCALE key comparing unequal texts as equal or equal ones as unequal), so
  the harm flags above are provisional: **flip `wrong_answer: true` if the mechanism is in the cache**, leave
  them if it is in the test's assumption.
- Candidates, none yet confirmed: eviction racing a concurrent `GetOrBuild` (an entry evicted between the
  lookup and the return); a `CacheEntry` published before its key bytes are fully written (a non-volatile field
  read across threads); the test's own accounting (a shared counter or list mutated without synchronisation);
  the size cap being hit under Linux's different thread-pool ramp so that "one key per text" is violated by
  design (rebuild after eviction) and the test's expectation is what is wrong.

## What closes it

Reproduce under load on Linux (WSL; memory: `wsl_linux_repro`) with the test looped until it fails; find the
mechanism in THIS code (memory: a remembered pattern is a hypothesis); fix the cache or correct the test's
assumption at the one place the invariant belongs; prove the failure branch (the fixed test must fail once
against the un-fixed cache, or the un-fixed test against the fixed cache); a WAVE-LOCAL gate over
`~Collation|~RuntimeConfig`. Flip this note to `landed` in the landing commit.

## Mechanism found

**It is the cache, and the failing assertion was never the wrong-key one.** The CI stack points at
`CollationKeyCacheTests.cs:151`, which is `Assert.True(cache.Count <= 64)` — the SIZE BOUND. The per-iteration
`k.CompareTo(Collator.Root.GetKey(t))` never fired in any run, on CI or in any of the ~2.6M lookups stressed here,
so no caller ever received a key built for a different text. `wrong_answer` therefore stays **false**: the harm is
that a configured memory bound was not a bound, not a wrong answer. (The note's provisional instruction to flip it
"if the mechanism is in the cache" was premised on the wrong-key assertion being the one that failed.)

**The mechanism — a dropped eviction signal.** `Lookup` inserts and then, if its own increment carried the count
past `MaxEntries`, calls `Evict`. `Evict` was a try-once batch: `Interlocked.CompareExchange(ref _evicting, 1, 0)`
and, on failure, `return`. Two things followed from that, and they are the same root cause — *the pass treated its
own snapshot as the whole job*:

1. the winner took its removal budget ONCE, before it started (`int toRemove = Count - keep;`), so every insert
   landing during the pass raised the count without being removed; and
2. every caller that overflowed while the flag was held found it taken, went on, and **left no trace of itself
   anywhere** — no pending flag, no queue, nothing. Its overflow was simply forgotten.

So when the pass ended the cache held `keep + (however many racers arrived)`, and it was repaired only if some
LATER insert happened to overflow while the flag was clear. When the workload ends inside a pass — a `Parallel.For`
whose eight workers all finish within one eviction window, which is exactly this test's shape — no such insert ever
comes, and the cache stays over its maximum for good.

Linux-only in CI because the failure needs the eviction window to be long relative to an insert: on the 2-core
GitHub runner, executing the 5,293-test suite with xUnit's parallel collections, the thread inside `Evict` is
descheduled mid-pass while the other workers keep inserting. On a 32-core Windows box the pass finishes first — the
shipped test never failed in 30 unpinned runs, nor in 40 pinned to two cores.

**Measured, on the pre-fix cache** (`E:\Temp\claude\pb377\stress`, a harness against the built Runtime assembly):

| shape | result on the un-fixed cache |
|---|---|
| 32 threads, 90 texts, cap 64 (the test's own shape) | settled at **Count=73, Entries=73** — the CI number — and in another round at **90**, i.e. the entire working set, in a cache configured for 64 |
| 64 threads, 200 texts, cap 64 | live count peaked at **213** (3.3× the cap) |
| 64 threads, 1600 texts, cap 512 | settled over the cap in **23 of 30** rounds; worst **1,594** (3.1×) |

Quiescent counter drift was **0 in every configuration** (`Count` always equalled `Entries.Count`), which refutes
the note's other candidates: `Collator.GetKey` allocates a fresh `CollationKey` per call, so the `ReferenceEquals`
guard cannot double-count; no entry is published half-built (`CacheEntry` is immutable but for interlocked stamps);
and the test's own accounting is a `ConcurrentDictionary` that is never asserted on.

**The fix** (`src/Cobol.Net.Runtime/Collation/Cache/CollationKeyCache.cs`) puts the invariant where it belongs — the
thread that evicts owns the whole job, including the overflows raised while it held the flag. `Evict` became a drain
loop over an extracted `EvictOneBatch`, re-deriving the budget from the live count each batch and re-checking after
it releases the flag; `EvictOneBatch` returns its removal count so no-progress cannot spin. The release is
`Interlocked.Exchange`, not `Volatile.Write`, and that is load-bearing: a racer's `Interlocked.Increment` of
`_count` happens-before its failed CAS on `_evicting`; that failed RMW and the release are operations on the same
location and so are totally ordered, and the CAS failed only because the flag was still held, so it precedes the
release; a full barrier then forbids the loop's re-read of `_count` from being hoisted above it. A release-store
followed by an acquire-load permits exactly the StoreLoad reordering that would drop the racer.

`MaxEntries` is now documented for what it can be — a **quiescence** bound. The instantaneous count still rides
above it by design (an insert must push it over before anything evicts, and a batch counts its removals once at the
end), and that overshoot is unbounded in principle because the design refuses to block lookups; what is guaranteed,
and now enforced, is that once the last caller returns the cache holds at most `MaxEntries` keys.

**Sibling sweep.** `grep -rn "ConcurrentDictionary" src/Cobol.Net.Runtime` returns nine sites; eight are unbounded
memoization tables over a bounded key domain (locale tags, collation tables) with no eviction and no side counter,
so the shape cannot occur there. `grep -rni "evict" src` reaches only this cache and `RuntimeConfig`'s description
of its environment variable. `grep -rn "CompareExchange" src` finds one other CAS guard,
`CollationRuntime.Initialize` — a one-shot init whose loser has no request to drop (a different shape; see the new
finding in the landing report). Within this file two siblings of the same "the counter and the map disagree" class
were fixed: `Clear` wrote a flat zero, which DISCARDS the increment of a lookup that inserted between the two
statements and leaves the counter under-reporting the map for the rest of the process — the unsafe direction, since
the cache then never reaches its eviction trigger; it now re-reads the count from the map. And `Lookup` decided
whether to count an insert by asking whether the returned KEY was ours, which is correct only while
`Collator.GetKey` allocates per call; it now asks whether our ENTRY won.

**Failure branch proved.** The new drift test `TheMaximum_IsABound_OnceTheCallersStop_HoweverTheyRaced` (callers all
stop on one flag, so the round has a real chance of ending mid-pass) run against the un-fixed cache:
`Failed! - Failed: 1, Passed: 0` — `round 1: the cache settled at 536 keys, over its maximum of 512`. Against the
fixed cache, `Passed!` in 243 ms, and 0 violations in a 60-round soak of the harshest shape.
