**The rule it breaks:** `DESIGN-backend-abstraction.md` §1.1 (what a bound node MAY contain: resolved symbols, a
structural `Place`, categories and numeric facts, literal values, neutral runtime-data strings, control-flow shape) —
neither a binder nor a parse context is on it; §1.3 lists the leaks L1–L5 and records L5 ("`RoslynBackend` …
performs no binding") as DONE, while the emitters run the `Place` builder at emit time. A CIL backend implementing
`ICodeGenBackend` would have to drive the C# compiler's binder to emit anything.

**Scenario:** a second backend (P16) is written against `BoundCompilation`; it cannot compute a `Place` without calling
`ReferenceResolver.ResolveItem`, i.e. without the binder and the parse tree — the seam §1 promises does not exist.

**Target:** DESIGN-architecture-review §8.1 (the tolerated rows `CodeGen → Binding` 93, `CodeGen.Emit → Binding` 33,
`CodeGen → Binding.Procedure` 4, `CodeGen → Compiler.Oo` 19, `Binding.Model → Binding` 20, `Binding.Model →
Frontend.Generated` 4) and §8.3 (4) then (1): `PlaceBuilder` in `compiler.model` run at bind time, `DataBindResult`
(immutable) on `BoundUnit` / `BoundCompilation` / `EmitContext` in place of the binder, the parse-context reads turned
into bound-node facts. The R1 Draft 2 change set added the leak to backend-abstraction §1.3 as L6 (OPEN); the landing wave marks it
removed (CLAUDE.md rule 6). The OO symbols carry parse contexts too (`Oo/OoClassSymbol.cs:29` `ClassDefinitionContext Ctx`, `Oo/OoInterfaceSymbol.cs:25`, `Oo/OoMethodSymbol.cs:15` `MethodDefinitionContext Ctx`; after external-repository slice 8, `Origin`'s source case), and §1.1 lists `OoMethodSymbol` as a permitted resolved symbol while it holds one: moving them to `compiler.model` as they are would grow `Binding.Model → Frontend.Generated` from 4 to 7 (R1 refuter 2, D1), so their context is extracted first (PB2401) and the move follows (PB2402).
