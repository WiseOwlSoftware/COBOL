# PB5369 - landing_measure.py complete derives bounces from failed merge-group runs, not from the queue's removal events: a pull request removed while its run was cancelled, or before any run, reads 0 bounces and then every complete refuses its record

**Sites:**

- `scripts/orchestrator/landing_measure.py:680` (`complete`, the bounce count taken from run conclusions)
- `scripts/orchestrator/landing_measure.py:199` (`validate`, the cause-count versus bounce-count refusal)
- `scripts/orchestrator/landing_measure.py:1000` (`_self_test`, the runs fixture, which must gain a removed-while-cancelled case)

**Evidence (enqueue unit's report).** Pull request 1510 (spec-2002-catalog) has 3 `added_to_merge_queue` and 3 `removed_from_merge_queue` timeline events (removed 2026-11-11T20:08:06Z and 21:18:33Z, merged 22:03:57Z). Its merge-group runs are 43084093039 (cancelled) and 43106701465 (success). The lane wrote its record with bounces 1 and bounce_causes [infrastructure]; `complete` re-counts from the runs, finds 0 failed, and now refuses on every call: "landing-measure: PR #1510: 1 bounce cause(s) name more than the 0 bounce(s)". Not re-run here; the figures are the report's.

**Mechanism.** The bounce count is derived from run conclusions (a run GitHub cancelled is excluded, PB3096's design), not from the queue's own record of removal, the issue timeline's `removed_from_merge_queue` events. A removal while the run was cancelled, or before any run existed, is a bounce the queue made but no failed run shows. The count disagrees with what the lane wrote, and the writer-versus-recount consistency check at line 199 then blocks every later `complete`.

**Fix direction.** Count bounces from the timeline's removal events (a pull request's removals minus the one that is its merge), the queue's own record, and keep the failed-run count only to attribute causes. A self-test fixture with a cancelled run and a removal event pins it. Repair the PR 1510 record by running the fixed `complete`, not by hand-editing its bounce fields.
