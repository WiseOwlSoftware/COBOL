# PB3857 — a write that takes MEMORY.md over its cap is refused where it is written

**Sites:** `scripts/hooks/` (a new write-guard hook), `scripts/orchestrator/account.py` (`memory_index`, `MEMORY_INDEX_CAP_CHARS`)

## The defect

PB3779 trimmed MEMORY.md to 5,053 characters and put the cap (`MEMORY_INDEX_CAP_CHARS`, 6,000) in `account.py`
(`--memory-index`, exit 1 over). Only the probe line and a header rule counter growth: any session (the operator, the
Mythos lane, auto-memory) appends dated lines freely, so the index regrows past the cap. When PB3779's work began the
file was 17,394 characters. A hook refusing a write that takes the file over the cap would close it, and would share its
root (the cap, `memory_index`) with PB3779.

## Owner question

May a hook refuse another session's write to MEMORY.md when the write takes it over 6,000 characters?

## Acceptance

- After the owner's answer: if yes, a hook under `scripts/hooks/` reads the cap from `account.py` (one owner of the
  number), refuses the over-cap write with a message naming `project_history_index.md` as the place for the dated line,
  and has a self-test seen RED first; if no, the note records the decision and the probe line stays the instrument.
- Standing owner rules: fix the root causes, never simply making the diagnostic pass; always be consistent with
  ourselves barring an explicit requirement differently.
