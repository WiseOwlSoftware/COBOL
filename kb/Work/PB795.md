## Mechanism 1 — the deny helper decides `broken` from a claim, not a measurement

`tests/Cobol.Net.Tests.Unit/FileAuthorityPresenceTests.cs`:

```
:416  private string? Refused()          // deny (RX) on the DIRECTORY, then raw File.OpenRead the child
:483  private static bool BypassesFilePermissions() =>
          !RuntimeInformation.IsOSPlatform(OSPlatform.Windows)
          && string.Equals(Environment.UserName, "root", StringComparison.Ordinal);
:110  public void TheDenyHelperWorksOnThisHost()  =>  Assert.True(refused || BypassesFilePermissions(), "…")
```

`BypassesFilePermissions` carries its reasoning in a doc comment: *"A merely ELEVATED Windows token does not
bypass an explicit deny ACE for its own SID, so Windows has no bypass case here."* That is an UNMEASURED claim
about every Windows host there will ever be, and the guard's whole job is to classify a host it has just failed
on. `feedback_reachability_is_measured_not_deduced`: the closing sentence gets the least scrutiny.

⛔ **The discriminating evidence is inside the same red run, and it narrows the mechanism sharply.**
`TheCapabilityHelpersWorkOnThisHost` (:357) PASSED on that runner, and it asserts `NotWritable() is not null`
and `NotReadable() is not null` with the same `BypassesFilePermissions()` escape (false on Windows). So on the
GitHub Windows runner:

- `File.SetAttributes(FileAttributes.ReadOnly)` denies this process a write — works.
- `icacls <file> /deny "<UserDomainName>\<UserName>:(RD)"` denies this process a read of a FILE — works. So
  `icacls` runs, the identity string resolves to the token's own user SID, and a deny ACE for that SID is
  honoured by the access check.
- Only `Refused()` — the DIRECTORY-scoped denial — fails to establish its precondition.

A directory-scoped deny does not deny the child by itself. Opening `locked\secret.dat` by full path consults
`locked` only for FILE_TRAVERSE, and **SeChangeNotifyPrivilege ("Bypass traverse checking") is granted to
Everyone by default**, so the deny ACE on the directory is not what makes the child unreadable on ANY Windows
host. What makes it unreadable on the owner's machine is the second effect of `icacls locked /inheritance:r`:
the directory stops having inheritable ACEs, `SetNamedSecurityInfo` re-propagates, and the child's DACL — which
held nothing but inherited ACEs — is left EMPTY. The precondition therefore rests on an inheritance side effect,
and the class has one measured host (the runner) where that chain does not end in a refusal. The FILE-scoped
deny that the same class already proves works on that host is never applied to this witness.

**So the fix is two-part and both parts are root-cause.** (a) `Refused()` must establish its precondition on the
FILE as well as on the directory — the directory denial stays, because `OpenOutput_NewFileUnderARefusedDirectory_
StillSucceeds` needs an unreadable-but-writable directory and `Probe_PresentButRefused` needs `File.Exists` to
answer false. (b) The classification must be MEASURED: read the object's security descriptor back and separate
*"the denial we asked for is not on the object"* (the helper really is broken → RED, with the `icacls` exit code
and output) from *"the denial IS on the object and this identity still gets access"* (the host bypasses it →
report the token's user SID, its group SIDs and its privilege names, so the next red is diagnosable from the log
instead of from a claim).

## Mechanism 2 — a `FileShare.Read` file lock cannot exist on Linux

`FileLockPostureDriftTests` measures §9.1.15's file lock from outside the connector with a real second handle,
and expects the three sharing modes to be distinguishable:

```
:199  [InlineData(Mode.NoOther,    false, false)]   // §9.1.15 1) exclusive
:200  [InlineData(Mode.ClauseLess, true,  false)]   // FileShare.Read — a reader yes, a writer no
:201  [InlineData(Mode.AllOther,   true,  true )]   // §9.1.15 3) concurrent access
```

.NET on Unix implements `FileShare` with **advisory `flock`**, and it has exactly two states: `FileShare.None`
takes `LOCK_EX`, every other value takes `LOCK_SH`. The outsider probe (`OutsiderCan`, :180) asks for
`FileShare.ReadWrite` on purpose — so that the probe never manufactures the refusal it measures — which is
`LOCK_SH`, and `LOCK_SH` is compatible with `LOCK_SH`. A connector holding `FileShare.Read` therefore CANNOT
refuse an outside writer on Linux; `outsiderMayWrite: True` is the host telling the truth about itself. The
`NoOther` arm (`FileShare.None` → `LOCK_EX`) and the `AllOther` arm both still hold, which is why exactly one
row of the theory and one `Assert.False` in `WideningForASiblingDoesNotAdmitAnOutsider` are red.

This is NOT fixable by changing the posture. §9.1.15 2) restricts other connectors *"to input mode"* — it
explicitly ADMITS a reader — so mapping `ReadOnly`/the undetermined default onto `LOCK_EX` would refuse an
access the standard grants, trading an under-refusal for an over-refusal. Neither `flock` state expresses rule 2,
Linux mandatory locking is gone, and `fcntl` record locks are advisory in the same way. **So it is a
DETERMINATION about the operating environment and it belongs in writing** (`DESIGN-runtime-library.md`, PB740's
section): on a host whose sharing is advisory and binary, §9.1.15's file lock degrades rule 2 toward rule 3
(concurrent access) rather than toward rule 1 (exclusive), because over-refusing would deny access the standard
allows — and rule 1's own exclusivity binds only processes that also take the advisory lock. A user running this
compiler on Linux gets weaker protection from OTHER RUN UNITS than on Windows, and that is a documented fact
rather than a hidden one.

The test's job then changes shape: the ISO expectation stays primary and is asserted wherever the host can
express it, the degraded expectation is asserted (never skipped into silence) where it cannot, and which of the
two applies is decided by a MEASURED host capability rather than by an `OSPlatform` literal — so a host that
gains or loses the ability turns the capability assertion red instead of quietly re-classifying every arm.

**Half 1 — the GR3 deny helper (`tests/Cobol.Net.Tests.Unit/FileAuthorityPresenceTests.cs`).**

- `Refused()` now denies the WITNESS FILE explicitly as well as its directory, in that order (once the
  directory refuses this process, `icacls` can no longer reach the child). Both denials are load-bearing and
  each was measured separately on 2026-09-06: a directory-scoped `deny (RX)` ALONE leaves `File.OpenRead` of the
  child **succeeding** and `File.Exists` **true** (opening a child by full path consults the parent only for
  FILE_TRAVERSE, and "Bypass traverse checking" is granted to Everyone by default); a file-scoped `deny (RX)`
  alone leaves `File.GetAttributes` **succeeding** (a caller that may list the parent is implicitly granted
  FILE_READ_ATTRIBUTES on its children). Together — with NO reliance on `/inheritance:r` propagation —
  `File.Exists` is false, `File.GetAttributes` raises `UnauthorizedAccessException` (so `HostFile.Probe` answers
  `Unauthorized`), `File.OpenRead` is refused, and creating a NEW file under the refused directory still
  succeeds, which is `OpenOutput_NewFileUnderARefusedDirectory_StillSucceeds`' premise.
- The bypass claim is gone. `tests/_shared/HostCapability.cs` classifies every precondition from measurements:
  `Enforced` · `BypassedByThisIdentity` (the denial WAS applied and the host granted the access anyway — the
  message then carries the host's own `whoami /user /groups /priv`, or `id`) · `ToolFailed` (the host's tool did
  not report success — the helper, with its exit codes and stderr). The identity is read lazily through
  `ProcessObserver`, so a green run spawns nothing.
- ⛔ The twenty silent passes are gone too, and that is the half the brief did not ask for: every
  `if (Refused() is not { } witness) return;` is now `{ NoPrecondition(); return; }`, which turns the test RED
  with the measured evidence unless the bypass is MEASURED. Previously a broken helper made twenty §14.9.27.4
  GR3 assertions vacuous and exactly one test red.
- ⚠ **No dynamic skip was used, because this xUnit pin has none.** The brief asks for an xUnit `Skip` carrying
  the measured fact. Measured: xunit 2.9.2 / xunit.runner.visualstudio 2.8.2 — `DynamicSkipToken` and the
  `$XunitDynamicSkip$` marker exist ONLY inside `xunit.assert.dll`; no runner or execution assembly in this pin
  contains the string, so `Assert.Skip` would report a FAILURE, not a skip. The shape landed instead is
  strictly stronger for the case that matters (an unestablished precondition is RED, not skipped) and records
  the one genuinely unassertable case — a permission-bypassing host — through `ITestOutputHelper`.
