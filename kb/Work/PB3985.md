# PB3985 — fuzz_triage's record_held requires every cited clause to be named in Expected result, so a clause that only the Draft issue cites can never pass, and refute.md does not tell the refuter so

**Sites:** `scripts/fuzz_triage.py:920` (`record_held`)

Found by the round-2 review of PB3972: branch `worktree-wf_aee78301-ec3-5` (PR #714; tip `10fe2567e`); `scripts/fuzz_triage.py` is not on
origin/main yet. The refuter prompt `refute.md` is also on that branch only: the fix names its path from the branch. Source:
PB3972's report, "Review findings" R2-2. Distinct from PB3984 (a different function and rule), though one finisher may fix both.

> R2-2 LEAD (low, not blocking at round 2): scripts/fuzz_triage.py:920 record_held requires the section-sign clauses of Expected result AND
> Draft issue to be in the refutation citations, and every cited clause to be named in Expected result, so a clause the Draft issue alone
> cites can never pass; refute.md tells the refuter to list every clause the Expected result (and Draft issue) cites, without saying the
> Draft issue may cite only clauses the Expected result names.

Failure scenario: a Draft issue cites a clause the Expected result does not, the refuter lists it as instructed, and `record_held`
holds the record in the triage report for a reason the refuter was never told.

## Acceptance
- Either `record_held` accepts a clause cited by the Draft issue alone (when the refuter lists it), or `refute.md` states the
  constraint; a test pins the Draft-issue-only citation.
