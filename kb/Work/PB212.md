# PB212

Found by the PB169–PB172 burn-down cluster's funnel-entry sweep (2026-08-31). ISO §14.9.39.3 syntax rule 1
(`cite.py --check 14.9.39.3 "Identifier-1 shall reference a data item of class index or an integer data item"`
→ OK) constrains the SET *receiver*; `SetBinder.SetTargetOf` applies no class rule at all.

⛔ IT IS THE TWO-ARM SHAPE AGAIN, and that is the reason to register it rather than leave it in prose: the
arithmetic-statement twin `ExpressionBinder.ScreenResultant` exists and does exactly this job for ADD /
SUBTRACT / MULTIPLY / DIVIDE / COMPUTE resultants (kb/Work PB128), citing each verb's own resultant SR. SET's
receiver was never given one. One rule, two arms, one written — the repository's most reproducible defect
shape, recorded in feedback_two_arm_dispatch.

⚠ Note the SENDING side of the same statement was fixed by cluster B (PB172 widened the §8.8.1.1 intrinsic
screen to the index-name window contexts, of which SET is one), which makes the receiving gap the more
visible of the pair: `SET IX TO FUNCTION LOWER-CASE(X)` is now rejected while `SET WS-X TO 5` with an
alphanumeric receiver still compiles.

WHAT WOULD CLOSE IT: extend `ScreenResultant` (or a sibling that shares its classifier) to the SET receiver
with §14.9.39.3 SR1's own citation, negative fixtures per excluded class, a golden for the two legal shapes,
and a row in the funnel entry-point table.

## 2026-09-04 — lane-3 adjudication batch b2 widened this note to THREE rows; the SET Format-1 receiver/sender pair is one gate, not one screen

**Rows claimed: `SR-14.9.39.3-1`, `SR-14.9.39.3-3`, `SR-14.9.39.3-4`.** All three are answered — or rather not
answered — at the SAME site, so they are this note's. Everything below was **re-measured on this worktree's
HEAD `cobol.exe` (base 89044aa0)** at `--std 2023`; the b2 adjudication also measured `--std 85` identical.
Probes in `probe/set1/` and `probe/set2/`.

### SR1 (this note's own rule) — confirmed, and it has a SILENT arm the note does not mention

`--check 14.9.39.3 "Identifier-1 shall reference a data item of class index or an integer data item"` →
`OK §14.9.39.3 1)`.

This note's own case still reproduces: `01 WS-X PIC X(4).` + `SET WS-X TO 5` (`set1/a1_alnum_recv.cob`) compiles
with zero diagnostics, then throws `NotImplementedCobolFeatureException: arithmetic into a non-fixed-point
target 'WS-X'`. A GROUP receiver (`a3_group_recv`) and a `USAGE POINTER` receiver via `SET P1 TO 4`
(`k4_int_to_ptr`) do the same.

⛔ **NEW: two shapes do not crash — they RUN and STORE.**

- `01 WS-D PIC 9(4)V99.` + `SET WS-D TO 5` (`a2_nonint_recv`) prints `D=[000500]`, rc 0, no diagnostic. Class
  numeric but NOT an integer data item, so SR1 excludes it.
- `01 WS-E PIC ZZZ9.` + `SET WS-E TO 5` (`a6_edited_recv`) prints `E=[   5]`. Category numeric-edited — neither
  class index nor an integer data item.

So ONE missing screen produces TWO harms: a run-time throw for the non-fixed-point receivers, and a **silent
acceptance-and-store** for the non-integer numeric and numeric-edited ones. The silent arm is the worse of the
two and is the one this note's title does not name. Note what makes these land in the arithmetic lane at all:
`SetBinder.cs`'s category re-routes fire only when the SENDER is a bare data reference, so a LITERAL sender
takes every non-numeric receiver straight past them.

### SR3 and SR4 are NOT closed by this note's stated fix

`--check 14.9.39.3 "If identifier-1 references a data item of class index, arithmetic-expression-1 shall not be specified"`
→ `OK §14.9.39.3 3)`.
`--check 14.9.39.3 "If identifier-1 references a numeric data item, index-name-2 shall be specified"` →
`OK §14.9.39.3 4)`.
`--check 14.9.39.4 "the occurrence number of the table element referenced by index-name-2"` → `OK §14.9.39.4 2)`
(rule 2 c) — the confirming half: the only defined semantic for a numeric Format-1 receiver is to receive an
occurrence number from an index-name.

**These are RELATIONS between the receiver's class and which sender alternative is legal**, and this note's
stated fix — extend `ScreenResultant` (or a sibling sharing its classifier) to the SET receiver — looks at ONE
operand and has no sender to consult. Landing PB212 exactly as written would leave both rows open.

Measured, all compiling clean and running with no diagnostic:

| `set2/sr3_idxdata_arith` | `01 IXD USAGE INDEX.` + `SET IXD TO 3.` | SR3 | prints `OK-SR3-ARITH` |

Legal controls still work: `sr3_idxdata_idxname` (`SET IXD TO IDX`) → `OK-SR3-LEGAL`; `sr4_num_idxname_legal`
(`SET IDX TO 4. SET N TO IDX.`) → `N=0004`. So this is pure under-rejection, not a mis-selected format.

### The shape the fix should take, and one test that must move

⛔ Not three independent `if`s. §14.9.39.4 GR2 defines semantics for exactly two receiver/sender pairings and no
others, because no third pairing is legal — so the right structure is a small **receiver-class × sender-
alternative table consulted once in `BindSetTo`**, which gives SR1 its home as the receiver-class column and
makes SR3/SR4 the cells rather than extra clauses (CLAUDE.md rule 5: the shape that makes the next case
automatic).

`tests/Cobol.Net.Tests.Unit/FlagDirectiveTests.cs:615`
(`Compile_RangeExceptionForIndex_NotFlagged_OnPlainNumericReceiver`) uses `SET N TO 3.` with `01 N PIC 9(4).` as
its fixture and asserts only that no FLAG-02 warning appears — a green test standing on source SR4 forbids
(`feedback_green_test_can_hold_a_gap_open`). The fix must re-point it at a legal SET or at another verb.
