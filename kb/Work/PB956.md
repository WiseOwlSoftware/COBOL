# PB956 — LANDED — the residue that owned a row in someone else's note

## Repro — measured

`scratchpad/reg9/probe/oob.cob`, `cobol.exe oob.cob --std 2023`:

```
       IDENTIFICATION DIVISION.
       CLASS-ID. R9CLS.
       IDENTIFICATION DIVISION.
       OBJECT.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  OB PIC X(4) BASED.
       01  P1 USAGE POINTER.
       PROCEDURE DIVISION.
       METHOD-ID. M1.
       …           SET ADDRESS OF OB TO P1.
```

```
  error COBOLNET0899: BASED data or ADDRESS OF in a class definition's data divisions is recognized but not
  yet implemented (the OO cell/bridge emission — a named Phase-4b residue; ISO §13.18.5 / §8.4.3.11)
```

The diagnostic has no line/column: it is a WHOLE-UNIT refusal. One BASED root anywhere in a class's data
divisions, or one record named by any `SET p TO ADDRESS OF x` in the unit, refuses the compilation.

## The rule — nothing bars it

```
$ python scripts/spec/cite.py --check 13.18.5.3 "The subject of the entry shall not be of class object"
OK  §13.18.5.3 1)  (Syntax rules)
    1) The subject of the entry shall not be of class object.
```

§13.18.5.3 has exactly **two** syntax rules — SR1 above, and SR2 (*"The subject of the entry shall not be a
dynamic-length elementary item or a variable-length group"*). `01 OB PIC X(4) BASED.` is neither. Nothing in
the BASED clause, and nothing in §8.4.3.11 (data-address identifiers), excludes a class definition's data
division. And the posture is not a licensed decline: `docs/CONFORMANCE.md:696` states *"the OO core itself is
mandatory surface and is implemented"*, and A.4.10 claims only the three OPTIONAL items separately. So this is
**conforming source refused by name**, not a documented non-support, and §4.2.6/§4.2.7 give no cover.

## The code site, and why it is a whole-unit refusal

`src/Cobol.Net.Compiler/Binding/DataBinder.Ptr.cs:52-64`, in `PtrBindBasedAndAddressables`:

```csharp
        if (OoIsClassUnit)
        {
            if (Roots.Any(r => r.IsBased) || PtrScanAddressOfTargets(program).Any())
                Edition.Error(DiagnosticCatalog.OoBasedInClass, "BASED data or ADDRESS OF in a class definition's data "
                    + "divisions is recognized but not yet implemented (…)");
            return;
        }
```

and the comment above it states the real constraint: *"the OO emitter renders `FieldEmitter` output only, never
the program-class cell/bridge loops, so a BASED item or ADDRESS-OF target in OBJECT/method data would reference
undeclared members (a CS0103 compiler-crash channel)."* The refusal is therefore standing in for **missing
emission**, not for a rule — the honest shape while the emission is absent, and debt either way
(`feedback_no_deferral_default`).

## What the fix is

The cell/bridge emission for OBJECT and method data: the same per-instance cell + `ManagedPointer.At(cell,
offset)` machinery the PROGRAM path already has (`PtrAddressableCellOf`, the pointer-routed StringCanonical
template for a BASED root), rendered by the OO emitter for a class's data divisions. This is a CODEGEN increment
with a design decision in it — where an object's addressable cell lives relative to the .NET object — so it is
implemented FROM `docs/rearchitecture/` (CLAUDE.md rule 2) and the design doc is updated in the same change set
if the answer differs from the program-class one.

## Landed (wave 52 DE, 2026-09-22)

Re-probed first on the implementer's own build: `oob.cob`'s shape (object `01 OB PIC X(4) BASED` + `SET ADDRESS OF
OB TO P1` in a method) drew the whole-unit COBOLNET0899, and a method-local `SET P TO ADDRESS OF LV` drew COBOLNET0869
because the ADDRESS-OF pre-scan walked the synthetic class unit, which has no procedure division. Both run now.

**The fix is the program path's own mechanism, reached — not a second one.** `DataBinder.PtrBindBasedAndAddressables`
no longer refuses a class unit: BASED roots force exactly as in a program, and the ADDRESS-OF pre-scan walks each
bound METHOD's procedure division (`OoBoundMethods`), resolving every head in the method's own scope (§11.7.4 GR5).
ProgramEmitter's two member loops moved into ONE renderer, `OoEmitter.EmitPointerBackings`, which both the program
class and both OO type-halves call. The design decision the note asked for — where an object's cell lives — is D3's
storage-duration table: object/factory WS → an instance member of that type-half; method WS → `static`
(`StaticBasedBridgeAddrs` / new `StaticAddressableCells`, §8.6.4 static items); method LOCAL-STORAGE / non-formal
LINKAGE → a per-ACTIVATION member that `EmitMethod` saves, re-seeds (NULL pointer §13.18.5.4 GR2; a fresh cell with the
initial image, §8.6.4) and restores in the activation's `finally` — measured with a three-deep recursive INVOKE SELF.
A method formal / RETURNING item is not forced (it crosses as its carrier), so `ADDRESS OF` a method formal stays the
program path's named 0869 residue. `RecordStructEmitter.MethodRedefinesBackingDecl` now skips a cell-backed class (its
local would shadow the bridge). The `oo-based-in-class` descriptor is deleted (name retired).

**Sibling found on the way and fixed (it was unreachable before this landing):** a PROPERTY accessor rendered
`=> {subject.CsName}`, a CS0103 once its subject's record is cell-backed (or a Tier-B REDEFINES window); it now reads
and writes through the subject's place. **PB521 landed in the same change set**, as this note required.

Golden `tests/conformance/2002/oo_based_class_data` (factory ALLOCATE INITIALIZED, recursive LOCAL-STORAGE, static
method WS, a PROPERTY over an ADDRESS-OF target); `BasedItemScopeTests`' positive cases now assert the class compiles.
Row SR-14.9.39.3-18 PARTIAL → CONFORMS (batch `pb956-oo-based-class-data`).
