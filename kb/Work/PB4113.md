# PB4113 — VALUE holds a COMP-5 item to its PICTURE's digits; everything else uses its container

## What happens (probes `E:\COBOL-coord\scratch\adj\PB4013\wo_*.txt`, built compiler at main)

VALUE refuses, with COBOL1625: 10000 to 65535 on `PIC 9(4) COMP-5`; 32767 and -32768 on `PIC S9(4) COMP-5`;
`PIC 9(2) COMP-5 VALUE 255`; `PIC S99V99 COMP-5 VALUE 327.67`; the same values on a level-88 (formats 2 and 3, and a
`WHEN SET TO FALSE` literal). On the same items `MOVE 65535` displays 65535, ADD past 65535 or below -32768 raises SIZE
ERROR, and SET of an 88, INITIALIZE and comparisons all use the container. VALUE alone disagrees.

## The rule (each quote checked with `cite.py --check`, OK)

- COMP-5 is not in ISO/IEC 1989:2023 (the §13.18.60.2 USAGE format lists COMPUTATIONAL / COMP and no COMPUTATIONAL-n;
  cobc -std=cobol2014 rejects it outright): a §4.2.10 1) extension ("documented language elements not defined in this
  Working Draft International Standard"), registered as `usage-comp-5`.
- §13.18.63.3 SR2: the literals "shall be permissible values within the range indicated by the PICTURE clause or the USAGE
  clause". A usage that takes its range from the USAGE has its VALUE range from the USAGE too. Even standard COMPUTATIONAL
  leaves the range to the implementor (§13.18.60.4 GR6, "and upon the range of values that the data item may hold"), so
  this compiler's refusal of `COMP PIC 9(4) VALUE 65535` rests on DOC-A.1-208, not on the standard (the refuter's
  amendment).
- For COMP-5 the implementor's determination is made: docs/CONFORMANCE.md DOC-A.1-208 bounds the value by the native
  two's-complement range of the container, never by the picture's digit count. It does not mention VALUE; that is the gap.
- Precedence (CLAUDE.md rule 1) agrees: GnuCOBOL 3.2.0 (-std default, ibm, mf) accepts 65535 and -32768 and refuses
  65536 / 32768 / -32769; IBM's Programming Guide: "Literals specified in VALUE clauses for COMP-5 items can, with a few
  exceptions, contain values of magnitude up to the capacity of the native binary representation."
- §13.18.63.3 SR2's other sentence still binds: "The values specified shall be representable exactly in the subject of
  the entry, without truncation of leading or trailing nonzero digits". The PICTURE's scale bounds the trailing side:
  `S99V99 COMP-5 VALUE 1.234` stays refused (GnuCOBOL wrongly accepts it).

## The conforming behavior

For a subject whose `PicInfo.Truncation == NumericTruncation.BinaryCapacity` (COMP-5; the BINARY-* usages already pass),
a numeric VALUE literal in formats 1, 2 and 3 is admitted on the leading side iff it lies in `AlgebraicRanges.Of(pic)`'s
band (the container's two's-complement range at the PICTURE's scale), and COBOL1625 cites that USAGE range ("0 through
65535", "-32768 through 32767", "-327.68 through 327.67"). The trailing side and SR3 are unchanged, and so are BINARY /
COMP / COMP-4 / PACKED-DECIMAL / DISPLAY (the PICTURE bounds them).

## Sites

- `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs#ValidateNumericValue`: the SR2 PICTURE test (from `StoredShapeOf`)
  refuses on the HIGH side first, so the `else if` USAGE-band branch that already names COMP-5 is unreachable for a
  leading-side value. For a BinaryCapacity subject only the low-side test comes from the PICTURE; the band decides the
  high side. One funnel (`ScreenValueLiteral`) serves formats 1 to 3, so the level-88 rows follow. Its `<remarks>` claim
  that the digit test "never false-rejects a capacity-valid value" is false for COMP-5 with a PICTURE: correct it.
- `src/WiseOwl.Cobol.Compiler/Binding/AlgebraicRange.cs#AlgebraicRanges.Of` / `#Admits` already give the band (`Admits`
  compares magnitude only, so the trailing-digit test stays separate).
- `docs/CONFORMANCE.md` DOC-A.1-208: add that the same band bounds a VALUE-clause literal (formats 1 to 3), with the
  trailing-side rule, and the new goldens in its evidence cell. The determination itself is not reversed.
- Goldens (expected images from DOC-A.1-56's DISPLAY rule and the container band, never from cobc output): run-pass
  `PIC 9(4) COMP-5 VALUE 65535`, `PIC S9(4) COMP-5 VALUE -32768` and `32767`, `PIC 9(2) COMP-5 VALUE 255`,
  `PIC S99V99 COMP-5 VALUE -327.68`, an 88 `VALUE 10000 THRU 65535` that tests true, a `WHEN SET TO FALSE` literal, a
  format-2 table VALUE, the 4- and 8-byte containers, and a P-scaled picture (GnuCOBOL is no oracle there: it wraps
  `PP99 VALUE .0256` to 000); compile-fail 65536, 32768, -32769, 256, 327.68 (USAGE-band message) and
  `S99V99 COMP-5 VALUE 1.234` (trailing-digit message).
- Inventory `SR-13.18.63.3-2` (CONFORMS for the standard usages; its code-location names `ValidateNumericValue`): the fix
