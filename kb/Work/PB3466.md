# PB3466 — BYTE-LENGTH as the last DISPLAY operand is a parse error

Source: PB3441 implementer report (`E:\COBOL-coord\scratch\reports\w1133b-PB3441-report.md`, "New defects").
Repro: `E:/COBOL-coord/scratch/w1133b/p/T13.cob`:
`DISPLAY FUNCTION BYTE-LENGTH (G1) " " FUNCTION BYTE-LENGTH (K1)` fails to parse when BYTE-LENGTH is the LAST
operand; substituting FUNCTION LENGTH parses. Legal source is rejected (§15.14.4 defines BYTE-LENGTH as a function;
§14.9.11.3 allows a function-identifier operand of DISPLAY).

Suspected sites (not narrowed further): the function-call rule in
`src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4` near line 636 and `constantByteLengthWord`
(`src/Cobol.Net.Frontend/Grammar/Core/CobolData.g4` line 333), which may let the BYTE-LENGTH word take the
`CONSTANT ... AS BYTE-LENGTH OF` reading at the end of the operand list. The fix is the root grammar cause plus a
golden; sweep the other statements that end in a function operand. The PB3441D golden avoids the defect by MOVEing
the function result to a field.

**Discharged — RETIRED unlanded, not a defect (wave 1135 A, re-probed on 0b8553f01, 2026-10-20).** The repro is
fixed-form source whose DISPLAY line is 74 characters long, and its last two characters `1)` sit in positions 73-74,
past margin R. §6.3.1: "Margin R is immediately to the right of the rightmost character position of the program-text
area. The rightmost character position of the program-text area is a fixed position defined by the implementor." This
compiler's position is 72 (`docs/CONFORMANCE.md` DOC-A.1-158: text beyond margin R is not program text and is
ignored), so the program text the parser receives is `FUNCTION BYTE-LENGTH (K` with no closing parenthesis, and the
parse error at the next statement is the correct answer. LENGTH "parses" only because it is five characters shorter
and the line then ends inside the program-text area; BYTE-LENGTH plays no part. Probes (scratch `w1135a/p`, own Debug
build): the T13 line is refused in fixed form; the same file under `--source-format free` parses (and draws only the
repro's own COBOLNET1675, `COMPUTE K1` into an alphanumeric item); the same two BYTE-LENGTH calls wrapped onto two
lines inside positions 8-72 parse and display `3 1`; a BYTE-LENGTH form padded past position 72 (73 characters, probe Y2) is
refused the same way; and a token and parse-tree dump of the raw text (no margin applied) parses the DISPLAY with both function
calls. No sibling exists: every statement operand reads the program text after the one §6.5 logical conversion
(`ReferenceFormatProcessor`), and the margin is already witnessed by
`conformance:cases/A.1-Implementor-defined-language-element-list/l1_margin_r_program_text_area`. The PB3441D golden's
MOVE workaround was never needed for BYTE-LENGTH; it needed only a line that ends within margin R.
