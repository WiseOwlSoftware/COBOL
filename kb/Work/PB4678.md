# PB4678 — the VALUE literal class screens skip TYPEDEF templates

**What is wrong.** `src/WiseOwl.Cobol.Compiler/Binding/Passes/CheckValueLiteralClassesPass.cs`, `Run` (about line 89), walks
`Forest.Roots` and `Forest.Conditions`, never `Forest.TypeDecls`. An oversize national literal on a USAGE NATIONAL
numeric-edited TYPEDEF is therefore refused only at each TYPE user, and not at all if the type is unused. The alphanumeric
twin refuses it once at the TYPEDEF. The SR7 class screen in the same pass has the same hole (the same loop feeds both).

**Fix shape.** Walk the TYPEDEF templates in `Run`, as `CheckUsageDeclarationsPass` already does (its comment names
`ForestSlice.TypeDecls`), so the verdict is given once at the declaration and the user-site refusal is not duplicated.
Pin the used and the unused TYPEDEF with goldens. Sweep the other passes that walk `Roots` alone for the same omission.

**Landed (wave 20261869 C).** Re-probed on a fresh build before the change: `01 T1 TYPEDEF PIC 99B99 USAGE NATIONAL VALUE N"ABCDEFGHIJ".`
unused compiled clean (COBOL0898 only at a `01 U1 TYPE T1.` user, anchored at the user), and the same typedef with the
alphanumeric `VALUE "ABC"` (SR7 class, COBOL5984) was clean unused and refused only at a user. Its alphanumeric twin
(`PIC 99B99 VALUE "ABCDEFGHIJ"`, COBOL1570) was refused once at the declaration. The cause is as the note says, and its reach is
wider than the note's two literals: the same loop fed the Format 2 (table) literals, read off `TableValuePlan`, which a template never has
(`ResolveTableValuesPass` skips a type declaration), and the condition-names, read off `Forest.Conditions`, where a template's own are
deliberately absent (`CloneConditionOnto`: "a declaration's condition-names stay off the index").
`Run` now walks `DataBinder.DeclaredForest()` (the roots plus the TYPEDEF templates and their subtrees, the compiler temps pruned) and
asks each item's `Own88s` instead of the index. The subject of both screens is the entry that WROTE the literal, so it skips an item whose
VALUE was copied (`DataItem.ValueCopiedFrom`: a TYPE clone, a SAME AS copy) and a condition-name a clone reproduced
(`Condition88.ClonedFrom`); the verdict is given once at the declaration. A VALUE the TYPE reference site writes itself is no copy and is
still asked there against the composed description. The table literals are now read off the clause (`TableValues`), which also screens a
phrase `ResolveTableValues` dropped as mis-shaped (the class rule holds of what was written). Re-probed after: the unused typedef is
refused once at its entry (line 5), the used typedef once (it was at the user), a group typedef's member, table literal and 88 once each
with two TYPE users, and a SAME AS pair once. Sweep: `UsageInheritancePass`, `InheritSignClausesPass`, `CheckUsageDeclarationsPass`,
`ExpandTypesPass`, `ResolveRedefinesPass`/`CheckStrongTypeDeclarationsPass` (`ClauseResolutionForest`) already walk the templates; the
`AllItems()`-only `ClassifyRedefinesClassesPass` has its SR5 screen reached through another path (`05 A OCCURS 3. 05 B REDEFINES A` in an
unused typedef is COBOL1701); `StorageFormPass` is about storage and a declaration has none (ISO §2023:13.18.58.4 GR2).
Goldens (13.18.63-VALUE): `pb4678_typedef_value_national_edited` (2002-2023, exact-size and group-inherited national values, a table value
and a condition-name in a used declaration) and the three refusals `pb4678-typedef-unused-value-oversize-national` (COBOL0898),
`pb4678-typedef-unused-value-class` and `pb4678-typedef-group-member-condition-class` (COBOL5984), each 2002-2023. Rows SR-13.18.63.3-5 and
-7 stay CONFORMS and gain the witnesses.
