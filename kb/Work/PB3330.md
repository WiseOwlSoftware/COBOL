# PB3330 — the keyed organizations' whole-store model is replaced (owner, 2026-10-17)

> flags: owner decision · architecture · hard design (the Mythos lane)

## Owner decision, 2026-10-17 ~11:20 PDT (verbatim)

The operator, explaining PB1636, quoted the design doc's weak spot ("every changing statement on such a file rewrites
the whole indexed or relative file, so a bulk load through ALL OTHER is quadratic"). The owner answered:
"THis is a completely unacceptable design".

The quoted cost is one symptom of the model, so this note covers the model itself.
`docs/rearchitecture/DESIGN-runtime-library.md` had called a record-level format "the next step if that cost is ever
measured to matter". The owner's ruling replaces that wait-and-see answer.

## The model today (measured on origin/main 20161db10)

- **OPEN reads the whole file into memory.** `KeyedConnector.ReadImage` (`src/Cobol.Net.Runtime/IO/KeyedConnector.cs:505`)
  reads every byte through the connector's handle into one rented array, and `RecordFraming.DecodeStore` decodes it into
  the run unit's `KeyedStore` (`KeyedStoreTable.cs:98`). Reading one record by key costs a read of the whole file.
- **The file is written back whole.** A connector whose sharing mode admits no other writer persists at CLOSE.
  A `SHARING WITH ALL OTHER` connector runs every record statement under the cross-run-unit store mutex and persists the
  whole store after each statement that changed it (`KeyedConnector.BeginStatement` → `StoreStatement`; design doc,
  "The coherent STATEMENT"). That is O(file) per WRITE, REWRITE or DELETE, so a bulk load through such a connector is
  O(n²). Each statement also reloads the whole file when another run unit's generation stamp moved.
- **The size of a file is capped by the size of an array.** `RecordFraming.MaxStoreBytes = 0x7FFFFFC7`
  (`RecordFraming.cs:213`, .NET's `Array.MaxLength`). `docs/CONFORMANCE.md` DOC-A.1-107 documents that as the boundary
  of every relative and indexed file (2 147 483 591 bytes). Memory use is the whole file per open.
- **A process that dies before CLOSE loses every change since OPEN.** The runtime registers no exit-time persist
  (no `ProcessExit` or `UnhandledException` handler under `src/Cobol.Net.Runtime`), so a kill, an out-of-memory failure
  or a power loss discards the run unit's whole session of updates to every keyed file it had open.
  §9.1.18.5 (`cite.py --check 9.1.18.5` → OK): *"When a run unit terminates abnormally, all file changes made since the
  previous commit or, if none, the beginning of the run unit are rolled back for all files for which there are active
  APPLY COMMIT clauses."* The standard rolls back only the files under an active APPLY COMMIT. This model rolls back
  every keyed file, and an abnormal termination gives no chance to write anything. That is the wrong-answer harm: a
  WRITE, REWRITE or DELETE that reported '00' is absent from the file afterwards.

## What other implementations do

GnuCOBOL 3.2 (`tests/external/gnucobol-3.2.tar.xz`, `libcob/fileio.c`, read 2026-10-17):
- RELATIVE is one fixed-size slot per record number, read and written in place. `relative_read` seeks to
  `relnum * (record_max + sizeof size)` (lines 3073-3075).
- INDEXED is stored by an on-disk keyed library: Berkeley DB opened as `DB_BTREE` (line 4625), or C-ISAM, D-ISAM or
  VBISAM through `isread` and friends (lines 110-143, 3418).
Neither organization reads the whole file to open it.

The survey of other vendors' record locking (`E:\Temp\claude\E--COBOL\c95c0b86-dc22-481b-af28-432ce3f04580\scratchpad\record-locking-survey.md`)
did not cover their storage formats. The design step surveys IBM VSAM (KSDS, RRDS, control intervals), Micro Focus's
indexed formats and ACUCOBOL-GT's Vision from their documentation, not from memory.

## The bar for the replacement (the design is the Mythos lane's: owner rule 2026-10-15, Mythos only for hard design)

- No statement reads or writes the whole file. OPEN reads only the header. A keyed READ, WRITE, REWRITE or DELETE
  touches O(log n) pages for INDEXED and O(1) slots for RELATIVE.
- The size limit comes from the host file system, not from a .NET array.
- A statement's change reaches the file when the statement completes, crash-consistently: a process that dies leaves
  the file in the state after its last completed statement, and never a torn one. APPLY COMMIT / ROLLBACK
  (§9.1.18.5) are built on this design, not around it.
- `SHARING WITH ALL OTHER` stays coherent at record or page granularity: two run units updating one file cost
  O(change) per statement, with no whole-store reload and no whole-store persist. The record locks of §9.1.16 /
  §12.4.5.9.4 sit on the record's own region of the file and keep their current cross-run-unit behaviour (status 51,
  RETRY outside the statement, the lock-file host on macOS).
- Every current golden and drift test keeps passing, plus a measured performance test that fails on a regression.
  Example: a bulk load of N records through ALL OTHER and through NO OTHER must be linear in N, and a random READ on a
  large file must read O(log n) pages. Pair it with a drift test that refuses any whole-store load or persist.
- One storage engine serves both organizations and every sharing mode. No second "small file" path is kept, and no
  reader of the old format (CLAUDE.md rule 4: no compatibility layer; an old store answers '39' as format 3 does
  today).
- The design doc (`DESIGN-runtime-library.md`, the keyed-store sections) and `docs/CONFORMANCE.md` DOC-A.1-107 and
  DOC-A.1-75 are rewritten in the same change.
