# PB392 — a boolean where the rule names a set of four kinds

## THE MECHANISM

`CorrespondingBinder.Bind` screens the two Format-3 operands with
`if (!src.Item.IsGroup || !dst.Item.IsGroup)` (`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/CorrespondingBinder.cs:63`)
— **a boolean "is it a group", where §14.9.44.3 SR6 names a SET of four group KINDS** (alphanumeric, national,
variable-length, strongly-typed) and additionally bars level-66. This is the
`model_the_rule_shape_not_one_case` shape, and here it costs in *both* directions at once:

* **A BIT group passes** the boolean and is accepted. §3.11 defines an alphanumeric group item as a *"group item
  except for a bit group item, a national group item, a strongly-typed group item, or a variable-length group
  item"*, so a `GROUP-USAGE BIT` group is in **none** of SR6's four kinds. The statement then executes as a
  **silent no-op**, because §14.7.6 rule 3 requires both items of an ADD/SUBTRACT pair to be numeric and every
  child of a bit group is category boolean — which is exactly *why* SR6 leaves bit groups out. Illegal source,
  accepted, and invisible in the output as well as at compile time.
* **A VARIABLE-LENGTH group — a kind SR6 explicitly ADMITS — never reaches pair selection.** `CorrAccess.Create`
  returns null for it (the resolved `Place` is neither `MemberPlace` nor `RedefViewPlace`), the bind returns
  `BoundUnsupported` and the backend emits a run-time loud. Legal source is compiled and then aborts.
* **A genuine violation is diagnosed at RUN TIME.** An elementary operand and a level-66 RENAMES name both
  compile clean and abort with *"a COBOL feature that is not yet implemented was reached at run time"* — the
  wrong stage and the wrong party (that half is the mechanism of `kb/Work/PB390`, which owns the MOVE and
  PERFORM rows of the same shape; this row is its SUBTRACT arm).

The screen's own comment concedes the kind axis is unmodelled, but the PREMISE it gives ("the 2002+/2014+
operand categories … have no representation in this data model yet") is **false for bit groups**: the compiler
models them well enough to give a `GROUP-USAGE BIT` receiver an as-if `PICTURE 1(m)` in the boolean COMPUTE
path, and `Table16Operand.Of` already computes a bit/national group's as-if picture. A second false premise sits
at `:60-62` ("RENAMES entries are not data-tree members — both shapes already failed the resolves above"); the
level-66 probe below **disproves it** — `RN` resolves fine and falls out two lines later at the `IsGroup` test,
where it is misreported as *"an elementary operand"*.

## THE RULE, QUOTED, `--check`ED ON THIS TREE

* `--check 14.9.44.3 "Identifier-4 and identifier-5 shall be alphanumeric group items, national group items,
  variable-length groups, or strongly-typed group items and shall not be described with level-number 66"` →
  **`OK §14.9.44.3 6)`**. ADD's twin is word-for-word identical: the same fragment `--check 14.9.2.3` →
  **`OK §14.9.2.3 6)`** — one rule, two verbs, one screen.
* `--check 3.11 "group item except for a bit group item"` → **`OK §3.11`**, the definition of *alphanumeric group
  item*, which is what puts a bit group outside all four admitted kinds.
* `--check 13.18.29.1 "treated as an elementary item of usage bit and category boolean"` →
  **`OK §13.18.29.1 (General)`** — the GROUP-USAGE BIT clause.
* `--check 14.7.6 "In an ADD or SUBTRACT statement, both of the data items are numeric data items"` →
  **`OK §14.7.6 3)`** — why the bit-group statement is a no-op once accepted.
* ⚠ **Do not read §14.7.6's preamble as licence.** `--check 14.7.6 "D1 and D2 are identifiers that refer to
  alphanumeric group items, bit group items, national group items, strongly-typed group items, or
  variable-length groups"` → **`OK §14.7.6`** — that general discussion DOES list bit groups, because it also
  serves MOVE CORRESPONDING. The narrower list is the verb's own SR6, and it governs here.

## OBSERVED ON HEAD (`89044aa0`), `--std 2023` — all three legs still reproduce

```
$ cobol.exe f3_corr_bit.cbl --run          # 01 SRC GROUP-USAGE BIT. 05 P PIC 1(4).  (same for DST)
OK                                          # SUBTRACT CORR SRC FROM DST — compiles, runs, does NOTHING
                                            # expected: rejected at compile time, naming SR6

$ cobol.exe m5_corr_varlen.cbl --run       # 05 TB PIC X OCCURS 1 TO 5 DEPENDING ON N in both groups
Unhandled exception … NotImplementedCobolFeatureException: SUBTRACT CORRESPONDING group operand storage shape
  ('SRC' / 'DST' is neither a member path nor a REDEFINES view)     # a kind SR6 ADMITS
$ cobol.exe n1_corr_fixedocc.cbl --run     P=000G     # control: same shape, FIXED OCCURS → works (10-3=7)
$ cobol.exe m4_corr_strong.cbl   --run     P=000G     # control: strongly-typed group → works

$ cobol.exe f2_corr_66.cbl --run           # 66 RN RENAMES P THRU Q as identifier-4
Unhandled exception … SUBTRACT CORRESPONDING over an elementary operand 'RN' (group items required —
  ISO §14.9.25.3 SR12 / §14.9.2.3 SR6 / §14.9.44.3 SR6)
```

The two controls localize the variable-length failure to the ODO group itself, not to the nesting or the verb.
The level-66 output is the disproof of the in-code premise: `RN` was resolved and then mislabelled.

## THE CODE SITE, AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/CorrespondingBinder.cs:63-66` — the `IsGroup` screen and its
  SR citation; `:59-62` — the false RENAMES premise; `:45-47` — the false "no representation" premise.
* `…/CorrespondingBinder.cs:70-77` and `:228-239` (`CorrAccess.Create`) — the `_ => null` arm that swallows a
  variable-length group.
* `src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:211` — the run-time landing.

**Repair (CLAUDE.md rule 5):** replace the boolean with a **group-KIND predicate** — one function answering
`GroupKind(item) ∈ {Alphanumeric, National, Bit, StronglyTyped, VariableLength, NotAGroup}` — and write SR6 as a
membership test against the rule's own set, plus the explicit level-66 test. One predicate, used by **MOVE, ADD
and SUBTRACT** CORRESPONDING (their SR6/SR12 differ, so each verb names its own admitted set against the same
kind function). Then:

1. give `CorrAccess.Create` a real arm for a variable-length group instead of `_ => null`, so an ADMITTED kind
   stops aborting the program;
2. route the refusal through `ctx.Edition.Error` with the SR citation instead of `BoundUnsupported` (PB390);
3. delete both false comments in the same change set — a comment asserting a case is impossible is not a check.

* A national group of national NUMERIC children is blocked upstream by the declared Phase-4a national-numeric
  residue (COBOLNET0899) — that is a different row and must not be conflated with this one when testing.
