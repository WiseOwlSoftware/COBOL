# PB1722 — LANDED (wave 1042 A): the plan is its phrases, the emitters compose occurrence RUNS

## Landed (wave 1042 A, 2026-10-08) — no ceiling needed

**Re-probed first** on the wave's Debug build of 7fb5cab75 (`E:\COBOL-coord\scratch\w1042a\p\`), compile + run:
`t1000.cob` (the filed shape at 1000 x 1000) 42.8 s / 2,491 MB / 27 MB of C#; `n1000.cob` (a Format 1 `VALUE "A"` on
the OCCURS entry) 39.5 s / 2,422 MB; `e1000.cob` (NO VALUE at all) 35.0 s / 1,922 MB / 20 MB of C#. **The harm was
not the table VALUE's dictionary**: the record-struct lane (`ValueInitializer.FieldInit`) wrote an array literal with
one initializer per occurrence whether or not a VALUE was written (`Enumerable.Repeat` repeated the TEXT), so every
large table compiled in time and memory linear in its element count, and the filed 10000 x 10000 table was an
out-of-memory crash on any host.

**Determination.** The standard sets no element-count ceiling here, and a ceiling would reject legal source (rule 3):
none was added and no implementor-limit diagnostic was needed. The fix is the representation (rule 5).

**Fix (one mechanism, every lane).**
- `Binding/Model/TableValuePlan.cs`: `TableValuePlan` holds the well-formed `TableValuePhrase`s (FROM/TO tuples,
  element count, literals), never an element map. `LiteralAt` scans them last to first (§13.18.63.4 GR15) and takes
  the literal at the element's run position modulo the list (GR13). `AddBreaks`/`PeriodAt` and the new
  `TableValueRuns.Of` answer which occurrences of a level initialize alike: one uniform run without a table VALUE in
  the subtree; with one, the union of every plan's phrase boundaries and, per run, the lcm of each plan's period
  k / gcd(k, S mod k). `RankForm` gives a phrase's run as a rank range.
- `CodeGen/DataDivision/OccurrenceRunEmit.cs` (new): ONE emit of a table's initial content from its runs — `Array`
  (`CobolTable.Fill<T>(n, (int __oD) => …)`, the element composed afresh per occurrence at run time), `Image`
  (`CobolString.Repeat` of a run's period), `Switch` (a dynamic table's seed, one arm per run), `RunsOfRepeats` (the
  group-VALUE slicer's windows). Callers: `ValueInitializer.FieldInit`/`DynTableNew`/`OccurrenceSwitch`,
  `GroupImageCodec.ImageInitOf`/`InitialBitCarrierOf`/`CellTable`, `GroupValueSlicer.SliceInit`/`SliceBitInit`.
- The sibling lane: a group VALUE's §13.18.63.4 GR5 area (`GroupArea`) is now its literal head plus a repeated unit
  of minimal period, never a full-width string; windows compare by phase, the image lane repeats the unit at run time.
- INITIALIZE … TO VALUE (`InitializeBinder.ExpandTableValue`): one arm per distinct literal of each phrase, last
  phrase first, each an `OccurrenceSpan` (pinned occurrence numbers + a rank range + a residue) tested by
  `CobolTable.InSpan` — never one tuple test per occurrence.
- The §13.18.63.3 SR7 pass screens each literal the clause WRITES once (it read the element map, once per element,
  and missed a literal a later phrase overwrote): negative `pb1722-table-value-overwritten-literal-class`.

**After** (same probes): `t1000` 2.9 s / 224 MB / 3.6 KB of C#; `e1000` 3.3 s / 222 MB; `c1000` (cyclic list +
overriding row + INITIALIZE ALL TO VALUE) correct; **the filed `t10000.cob` compiles in 1.7 s / 223 MB / 3.6 KB**.
The run-time table (100,000,000 elements) is the program's own storage and costs what the program declared.

**Witnesses.** Golden `2002/pb1722_table_value_runs` (values from GR12–GR15, GR5 and §14.9.20.4 GR5 c) 1. c);
negative `pb1722-table-value-overwritten-literal-class` (SR7, COBOLNET0898 at 2002/2014/2023); unit
`TableValueElementCountTests` (LiteralAt, RankForm and TableValueRuns.Of each checked against the step-walk oracle
over every element of a 3 x 4 x 2 table); drift `TableInitialStateRunsDriftTests` (the 10000 x 10000 program in every
lane emits under 20,000 characters and within 1,000 of its 10 x 10 twin; the plan holds no per-element collection; no
data-division emitter writes a per-occurrence array literal). Design: `COBOLNET_DESIGN.md` (VALUE init),
`COBOLNET_DATA_MODEL_DESIGN.md` §10.

## Finding

**Repro (NOT RUN, to protect the host during the wave).**
`E:\Temp\claude\E--COBOL\73cac64c-391d-42c0-bcdf-c880e3e10305\scratchpad\w71b\lead-huge-table.cob`:
`03 G OCCURS 10000. 05 T PIC X OCCURS 10000 VALUE "A" FROM (1 1).` — a legal Format 2 VALUE whose phrase (GR14
supplies the whole-table TO) names 100,000,000 elements.

**History.** Before PB1716 the fill stopped silently at a 64,000,000-element defensive cap (`MaxFillElements`), so
every element past it took no value: a silent wrong answer. PB1716 deleted the cap and bounds each phrase's fill by
`TableValueOdometer.ElementCount`, so the answer is now right but the fill materializes every element in the
subscript-tuple dictionary (`TableValuePlan.Literals`), and the emitters read it element by element.

**Code sites.** `src/Cobol.Net.Compiler/Binding/Model/TableValuePlan.cs` `TableValueOdometer.Resolve` (the
dictionary fill); `src/Cobol.Net.Compiler/CodeGen/DataDivision/ValueInitializer.cs` `FieldInit` and
`src/Cobol.Net.Compiler/CodeGen/DataDivision/GroupImageCodec.cs` `ImageInitOf` (the element-wise readers). There is
no size-limit descriptor in `DiagnosticCatalog`.

**The decision owed.** A table's total size is an implementor limit. Two questions for the owner: the ceiling (on
elements, or on bytes), and whether exceeding it is diagnosed at compile time. Independently of the ceiling, a
run-length representation of a phrase (FROM, count, literals) instead of a per-element dictionary would make the
fill O(phrases) — a re-architecture candidate under rule 5.

**Next step.** The `crashes` flag is PROVISIONAL (the expected harm of 100,000,000 dictionary entries, unmeasured). Run the repro under a memory-limited job to measure the harm (time, peak working set, crash or not).

## Measured 2026-10-04 (wave 1013 group N, w1013n) — the harm is real, COMPILE-time, linear, and NOT the dictionary alone

**Measured at 1/100 of the filed scale** (`w1013n/p/huge1k.cob`: `03 G OCCURS 1000. 05 T PIC X OCCURS 1000 VALUE "A"
FROM (1 1).`, 1,000,000 elements, `cobol.exe` compile only, `--std 2023`, Debug build of `c2f2e2f56`, polled
`Process.PeakWorkingSet64`): **23.6 s and 2,462 MB peak working set**, exit 0. Both scale linearly with the element
count (the odometer fill, the dictionary and the emitted source all do), so the filed 100,000,000-element table is
~40 minutes and ~245 GB — an out-of-memory crash on any host. A 4,000 x 4,000 table (16,000,000 elements, 0.16 of the
filed one) already projects to ~6 minutes and ~39 GB. `crashes: true` is therefore CONFIRMED (not run at full scale, to protect the host).
GnuCOBOL has nothing to compare (it has no Format 2 VALUE), so ISO silent + GnuCOBOL silent leaves the ceiling to the
implementor (CLAUDE.md rule 1) — but the ceiling is the WRONG fix: a limit that rejects legal source is rule 3 debt, and
the same program with no VALUE phrase compiles in linear time with one element composed and repeated.

**Why the dictionary is only the first of four per-element lanes — the finisher's map (all file:line on `c2f2e2f56`):**
1. `TableValuePlan.cs` `TableValueOdometer.Resolve` (l.168) fills `Dictionary<Subscripts,string>` — one entry per element.
2. `ValueInitializer.cs` `FieldInit` (l.109-117): a fixed OCCURS entry that `ContainsTableValue` emits
   `new T[] { ElementInit(o=1), …, ElementInit(o=n) }` — per element, per level, so the GENERATED C# SOURCE is
   O(elements) (this, not the map, is most of the 2.4 GB at 1M elements). The no-VALUE branch above it composes ONE
   element and repeats it.
3. `GroupImageCodec.cs` `ImageInitOf`/`ImageInitOfOne` (l.31-99, via `DataItem.ValueAt`, l.206 / l.786) and
   `GroupValueSlicer.cs` l.101 — the character-image seeds read `ValueAt` per element.
4. `InitializeBinder.cs` `ExpandTableValue` (l.620-684): `plan.Literals.Keys.ToList()` then one `InitializeOccurrenceArm`
   entry per element; and `DataBinder.cs` l.2992 screens `plan.Literals.Values`.

**Design sketch (not started).** Make the plan the PHRASES, not the map: per phrase `(from, rankFrom, count, literals)`
in odometer rank space (`ElementCount` already computes the rank distance by mixed radix), `LiteralAt(subs)` = scan the
phrases last-to-first (GR15), O(phrases). Give every consumer a *uniform-span* query instead of an enumeration: for a
prefix of subscripts, "the maximal runs of the next dimension over which the element initializer is identical"
(breakpoints are the phrases' FROM/TO ranks; a run is uniform when the block lies inside one phrase and the literal list
length divides the block size). Lane 2 then emits one `CobolTable.Repeat(count, () => elem)` per run, lane 3 repeats
the image string per run, lane 4 emits one arm per run with a range test instead of one tuple per element. A drift test
should pin "no consumer reads `Literals` as a map" the way `InitializeLaneDriftTests` pins the lanes. Add the
`DiagnosticCatalog` implementor-limit descriptor only if the owner wants a ceiling ON TOP of the O(phrases) fill (the
runtime array of 100,000,000 strings still needs ~800 MB).

**Status.** Left OPEN and unfixed by w1013n: it is a second mechanism (four lanes and an INITIALIZE arm representation),
not the variable-length-group codec that PB244 and PB1937 share; finishing it in the same slice would have passed the turn cap.
