**Rule it breaks:** §2023:8.8.4.5.3 GR2: a condition-name test compares by the relation-condition rules, i.e. by the one numeric comparison RenderNumericRelational implements (its NumCompareU arm exists for exactly this carrier, ConditionRenderer.cs:526-531); CLAUDE.md rule 4 (no second mechanism) and the file own doctrine that 88, relation and EVALUATE range share one comparison

**Scenario:** RenderCondition88 reads a numeric conditional variable through num.FieldNum(c.Parent).Expr (ConditionRenderer.cs:1046); for a PicInfo.IsUnsignedWideBinary item (unsigned, BinaryCapacity, 16-byte, e.g. PIC 9(25) COMP-5) that read is the raw UInt128 field (NumericRenderer.cs:724). RenderMembershipTest then emits read == loN / read >= loN && read <= hiN (:1147-1150) with loN from NumericMembershipValue -> EmitText.UnscaledAtScale -> IntLiteral, which for a literal past 18 digits is Int128.Parse(...) (EmitCore.cs:368-371). C# defines no ==, >= or <= between UInt128 and Int128 and neither converts implicitly to the other, so 01 U PIC 9(25) COMP-5 with 88 U-BIG VALUE 1000000000000000000000 makes IF U-BIG a CS0019 on the generated .g.cs: legal source rejected by the backend with no COBOL diagnostic. The same membership also lacks the scale-mismatch escape and SDIDI arms the relation has; it relies on the VALUE being at the item scale.

**Spec:** §2023:8.8.4.5.3 "The rules for comparing a conditional variable with a condition-name value are the same as those specified for relation conditions" (`cite.py --check` passed at collection)

**Target:** The numeric arm of RenderMembershipTest builds the relation pair (subject == literal, or >= low and <= high) and renders it through RenderNumericRelational, so the 88 test, IF U = literal and EVALUATE share the U, wide, Dec and scaled arms; NumericMembershipValue and the raw text comparison are deleted
