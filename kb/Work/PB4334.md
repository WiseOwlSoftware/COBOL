## The approved wording (review §13), verbatim

> ## Testing
> The owner decided on 2026-11-0X (kb/Work PB____): THE POPULATION IS THE PLAN. **The gate has ONE shape:
> `pwsh scripts/build-local.ps1 -Priority BelowNormal`** (`scripts/gate.py`), run once at a branch's head before it is
> enqueued, and after every fix. It decides a lane from the diff's paths: an **inert** change (`inert_lane.py classify`,
> proven by the inotify watch in CI) runs the tree audits (≈ 40 s); a **tooling** change (`scripts/`, `.github/`, `tools/`,
> `.claude/`, any `*.py`/`*.ps1`/`*.sh`) runs the audits and the self-tests whose recorded inputs it touches; every other
> change is a **code** change and runs the build once and the WHOLE Unit, Conformance and Characterization populations on
> Windows, three assemblies at once, longest collections first, the audits beside them. There is no impact map, no tier,
> no selected leg and no Linux half per change; the inner loop (`dotnet test --filter` by hand) is the agent's and claims
> nothing. **A branch lands through ONE script, `python scripts/orchestrator/enqueue.py land <branch>`** (kb/Work PB3023):
> it refuses a tip no GREEN record covers (exit 14), merges `origin/main` in, stamps the DEVLOG entry, runs the landing
> checks and queues one pull request in GitHub's merge queue; it never gates the merged head. **The merge group is the
> whole-population net on both OSes** (12 time-weighted shards, the audits with every Linux self-test, the Windows
> self-tests when a tooling path changed) and the ONLY run of the merged tree, of Linux and of Release. A nightly runs the
> CLI NIST guard, every self-test on both OSes and the GnuCOBOL differential. Build `WiseOwl.Cobol.sln` (not a single
> project) before any `--no-build` run. Commands and the current baseline are in plan §0 "Gates" and §9.
> ⛔ **THE RULE (owner 2026-11-0X, replacing the CI invariant of 2026-10-04): every case the merge group runs on Windows
> already ran green at the pushed head, on this host, under the same `toolchain.env`.** The merge group is therefore the
> FIRST run of (a) the merged tree, (b) Linux, (c) Release with a cold compile cache, (d) the Windows tooling self-tests on
> a tooling change, and (e) GitHub's runners; a merge-group red is one of those five, a flake, or infrastructure — never
> an untested case. The landing lane classifies every red against the branch's gate record (PB4271) before anyone is
> blamed: INFRA and RUNNER re-queue once automatically; MERGE and a genuine red go to a finisher; a flake is a kb/Work
> defect fixed at its root, never retried inside the run. A red of class (b), (c) or (e) is ALSO a finding against the
> pipeline's record of that class, filed with its rate (`kb/Work/PB1957`). **CI and every local host run the SAME tool
> versions, the LATEST releases** (owner 2026-10-28; kb/Work PB4007): one toolchain manifest, everything installs from it.
