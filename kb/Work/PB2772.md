**Harm:** The implementation's own rule for an [import] of a collation that does not exist is Expand's branch: report 'no such collation; nothing imported' in Unsupported and import nothing. What runs instead imports the locale's DEFAULT collation and reports nothing, so a program collating under that locale gets orderings neither the site file nor the implementation's rule specifies (measured below: nz versus n-tilde-a orders as es-standard instead of root). The trigger is a site file under COBOL_CLDR_DIR; the 135 embedded CLDR files all import types that exist.

**Scenario:** Measured on the pin (8be230068): a site file zz.xml under COBOL_CLDR_DIR whose standard collation is [import es-u-co-tradtional] (a misspelt type) resolves with Unsupported empty and collates as es/standard (Compare('nz', U+00F1 'a') = -1, where root gives +1 and the correctly spelt import gives the traditional order, Compare('cz','ch') = -1). Expand (CldrTailoringBuilder.cs:418-443) calls ResolveCollation(tag-u-co-type) and reports only when sel.Collation is null; ResolveCollation (CldrLocaleLoader.cs:142-167) never returns null for a non-standard type the chain lacks: it falls back to the chain's default type and records the fallback in sel.Unsupported, which Expand never reads. Expand's branch can fire only for a type equal to standard on a chain with no standard collation. A COBOL program whose LOCALE (12.3.7.4 GR7) or ALPHABET IS LOCALE names that locale compares and sorts by tailoring rules no one asked for, with no notice.

**Reproduction:** pwsh 7 on the pin's Cobol.Net.Runtime.dll. COBOL_CLDR_DIR=<probe>/site holding zz.xml = <collation type="standard"><cr>[import es-u-co-tradtional]</cr> (misspelt): CollationEngine.ResolveLocale('zz').Unsupported = [] ; Collator.Compare('cz','ch') = 1 ; Compare('nz', U+00F1 'a') = -1 (the es order; root gives +1). With the correct spelling [import es-u-co-traditional] (<probe>/site2): Compare('cz','ch') = -1 (traditional). With no site file: Compare('nz', U+00F1 'a') = 1. So the misspelt import silently splices es/standard where the stated rule would import nothing and report it.

**Target:** One rule for what a missing import type means, stated once: the import path asks for exactly the named type along the chain (no default-type fallback; a ResolveCollation option or a separate exact lookup) and reports a missing one through Expand's existing 'no such collation; nothing imported' branch, or Expand reads sel.Unsupported and carries the fallback reason. A unit test pins both spellings (misspelt: reported, nothing imported; correct: traditional order).
