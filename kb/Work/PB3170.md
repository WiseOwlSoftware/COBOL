# PB3170 — the planner re-plans a branch its successor already replays

> ⚙ **flags:** process-only · silent

**Found 2026-10-14 ~17:25 PDT by the wave-1079 unit**, reading `plan_wave.py`'s table.

## What happens

`python scripts/orchestrator/plan_wave.py --from-budget --borrow-days 0` (run from the main checkout at `c2822f21c`;
output `E:\COBOL-coord\scratch\plan_wave-out.txt`) planned three finishers:

```
A  opus           finisher  notes PB3101 (lead PB3101)  src/Cobol.Net.Runtime/Control/ActivationRelations.cs
B  opus           finisher  notes PB2099 (lead PB2099)  src/Cobol.Net.Runtime/Control/ProgramRegistry.cs
A2 opus  after A  finisher  notes PB3127 (lead PB3127)  src/Cobol.Net.Runtime/Control/ActivationRelations.cs
```

A2's pred: "predecessor w1077b (PB3127) returned SPLIT ... Its branch worktree-wf_84f0c364-28e-2 ... is UNLANDED:
cherry-pick its unlanded commits onto current main (never merge the branch)". But:

- w1077b's own title reads `# PB3127 (landed) + PB3101 (BY REFERENCE and RETURNING halves; remainder NEXT)`: the
  report finished PB3127 on its branch (the note's status flips in its commit `741169af5`, "PB3127 landed"); it is
  SPLIT only for PB3101's remainder.
- Group A's predecessor `worktree-wf_15ec6338-3a0-2` (w1078b, SPLIT, lead PB3101) replays all four 28e-2 commits:
  `git cherry -v worktree-wf_15ec6338-3a0-2 worktree-wf_84f0c364-28e-2 c29af1704` prints `-` (patch-equivalent) for
  `3b21b579b`, `7428e4e56`, `741169af5` and `9e5054890`, while `git merge-base --is-ancestor worktree-wf_84f0c364-28e-2
  worktree-wf_15ec6338-3a0-2` exits 1. PB3127's note records 28e-2 ABANDONED for exactly this reason (the record is on
  `notes-w1078-abandon-28e`, unlanded at the time).

So A2 had nothing to do, and its `after: A` would have HELD group A's branch, which carries PB3101 and PB3127, until
A2 landed (MANDATORY-PRACTICES O2: a predecessor lands through its successor). The unit released the wave
(`plan_wave.py --release 1079`) and re-planned with `--max-groups 2` (A and B only).

The planner on origin/main at the time (`de8cf80db`, which added `--drain` and `branch_carrier` for PB3150) does the
same: its dry run (`E:\COBOL-coord\scratch\plan_wave-main-dry.txt`), with A and B held in the dispatch ledger, planned
`A opus finisher notes PB3127` with no `after:`, so a second finisher would have cherry-picked the same four commits
onto main in parallel with wave 1079's group A, and the same commits would reach the merge queue on two branches.

## Mechanism

`scripts/orchestrator/plan_wave.py`:

- `branch_carrier()` (the `carried()` closure) finds a carrier only among branches of **DONE** reports, and only by
  `git merge-base --is-ancestor`. 3a0-2's report is SPLIT, and 3a0-2 cherry-picked 28e-2, so neither test can see it.
- `finisher_pred()`'s UNLANDED arm tells every SPLIT successor "cherry-pick its unlanded commits onto current main
  (never merge the branch)". So by the planner's own instruction, a SPLIT predecessor is never an ancestor of its
  successor: the ancestor test misses every carrier that this pred creates. It sees only same-file successors
  (`after:`), which merge.
- `plan()`'s `newest` loop keys PB3127 on w1077b, its newest report by id, and w1077b is SPLIT, so PB3127 joins
  `finisher_by_rep`. The report format has no per-note outcome, so "PB3127 (landed)" inside a SPLIT report is
  invisible to the planner.
- An ABANDONED record (`prune_worktrees.abandon_record`, PB3161) for the report's branch is not consulted either.

The plan repeats every wave until a branch carrying `741169af5` lands and flips PB3127 to `landed` on main.

## Fix direction

One rule for "this branch's work is carried elsewhere", shared with `prune_worktrees.py`. Its LANDED class already
uses patch equivalence (`git cherry`, kb/Work PB2708). A branch counts as carried when every commit it has beyond its
merge base with main is patch-equivalent to a commit of another unlanded branch that has a report (any status), or to
main. Its notes then go to that branch's report, never to a finisher of their own. A report's branch recorded
ABANDONED (the same `abandon_record` matcher) is never planned from. Regression tests in
`scripts/orchestrator/test_plan_wave.py`: (1) a SPLIT report whose branch's commits are cherry-picked onto another
SPLIT report's branch is not planned; (2) the same with the carrier DONE; (3) a SPLIT report whose branch has one
commit the carrier lacks is still planned, with a pred that names only that commit. Sibling sites to sweep: the
`unlanded` arm (`unlanded_branch_notes()`) and the half-note arm, both of which resume from a branch without asking
whether another branch replays it.
