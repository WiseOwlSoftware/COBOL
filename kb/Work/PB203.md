# PB203

Found 2026-08-31 during the cluster-A burn-down, while checking whether [[PB173]]'s new `BitImagePlace` needed
a `RedefViewPlace` arm. It does not — because the shape that would need one does not compile at all, for an
unrelated and earlier reason.

**MEASURED** at `--std 2023`:

```cobol
01 A PIC X(2) VALUE "AB".
01 BV REDEFINES A GROUP-USAGE BIT.
   05 BV1 PIC 1(8).
   05 BV2 PIC 1(8).
...
DISPLAY "BV=[" BV "]".
```

→ four `error CS0103: The name 'BV1' does not exist in the current context` / `'BV2'`, the first pair on the
plain `DISPLAY BV` line. No reference modification is involved: the view's subordinate bit leaves are never
emitted as fields, so every reference to them names nothing.

**LEGAL SOURCE.** §13.18.44.3's syntax rules bar an object/pointer/strongly-typed subject (SR12), a
variable-length group or dynamic-length item on either side (SR17), and an occurs-depending table (SR5). A
GROUP-USAGE BIT group is none of those, and §13.18.29 places no REDEFINES restriction on a bit group. So this
is conforming source that fails BACKEND compilation.

**PRE-EXISTING — MEASURED, NOT ARGUED.** The cluster-A working tree was stashed, the solution rebuilt
at 876d8ab0, and the repro re-run: byte-identical output, the same four CS0103 diagnostics at the same
positions. So this is not a regression from [[PB173]]'s `BitImagePlace` landing — and the "it cannot be,
because PB173 only touched the ref-mod path" argument did not have to be trusted.

**WHERE TO LOOK.** The REDEFINES class tier for this shape, and the field emission that follows it: a bit
group's storage is a §8.5.1.6.3 bit RUN, not a character window, so `ComputeTier` / `RecordStructEmitter`'s
Tier-B path (a `(offset, width)` character window over the class backing) has no obvious representation for it.
The likely honest answers are a Tier-D rejection with a derived reason, or a real bit-window model — DERIVE
which before choosing, and note that §13.18.44.4 GR1 states the storage association **in BITS** ("starts at the
first bit … an area sufficient to contain the number of BITS required"), which is a point in favour of the
model rather than the rejection.

**RELATED.** Once this compiles, re-check whether `BitImagePlace` needs a `RedefViewPlace` arm the way
`GroupImage` has one — [[PB173]]'s wrap deliberately skips `RedefViewPlace` (mirroring `GroupImagePlace`), and
that choice is currently unobservable for exactly this reason.
