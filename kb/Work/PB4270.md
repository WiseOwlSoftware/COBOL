# PB4270 — impact maps go stale whenever the loop is not adopting main

**Sites:** `scripts/orchestrator/adopt_main.py` (`adopt`), `scripts/orchestrator/impact_lane.py` (`request`, `work`), `scripts/spec/impacted_tests.py` (`drifted_change`).

## What happens

PB3663 (owner decision, landed) made the loop record an impact map for every main commit it adopts.
`adopt_main.py adopt` runs only from the supervisor (`orchestrate.ps1`), between units. So no map is recorded:

- while the loop is stopped. On 2026-10-30 22:10 to 2026-10-31 08:58 it was stopped for the reserved quiet window and
  the weekly reset, while the Mythos session landed branches by hand;
- while the checkout cannot be adopted. On 2026-10-31 08:58 to 10:06 a local, uncommitted `model_rules.json` cap
  override kept `adopt` at `4a05f0ff7` ("1 tracked file(s) are modified in the checkout");
- for the commits main gains in between, when several land during one unit.

A gate does not fail on a stale map. `impacted_tests.drifted_change` takes every hunk of a file that differs between
the map and the base at FILE level, so the plan gets coarser, leg 1 falls back to the cheapest slice, and the verdict
still reads GREEN. PR #880's gate (`000004-20261031T074021Z`) planned against map `0d9b640e4`, 111 commits behind its
base, with 48 `src/` files differing. 19,609 of 19,972 conformance cases were tier 1, and the 11 the change broke were
left to CI (PB2696's evidence).

## The fix's shape

Record maps from the event that changes main, not from the loop's schedule. Either a job after every merge to main,
on this host or in CI with the map as an artifact the gate fetches, or the gate itself: when its nearest map is more
than N commits, or any changed file, behind its base, it records the base's map first and then plans. The gate's
verdict line names the map's distance from the base, so a stale plan is never silent. With PB4269 (an unattributed
tier runs whole) a stale map costs time, never coverage. This note makes it cost neither.
