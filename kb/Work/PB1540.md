# PB1540 — OPEN

## The rule

> 2) … Each record in a line sequential file is terminated by an implementor-defined line delimiter. The range of allowable characters in a line sequential file is implementor-defined.

`cite.py --check 12.4.5.10.3 "Each record in a line sequential file is terminated by an implementor-defined line delimiter"` → OK §12.4.5.10.3 2).
A.1 item 114 (specification of the line delimiter) is required and documented.

## Precedent (CLAUDE.md rule 1: ISO silent → GnuCOBOL)

GnuCOBOL 3.2 opens a LINE SEQUENTIAL file in C text mode (`libcob/fileio.c` 1894-1899, "w" unless COB_UNIX_LF), so the delimiter
is the host newline; `lineseq_write` emits `\r` only under `cob_ls_uses_cr`, which 3.2 never sets. On READ (`fileio.c` 2528-2538)
a CR is dropped only when LF follows it — a lone CR is data.

## Repro (`/tmp/adj/doc/doc-w1-s4/probe/p114w.cob`, `p114r.cob`; re-probed on Linux, `--std 2023`)

WRITE of "AB" and "CDE" → file bytes `41 42 0D 0A 43 44 45 0D 0A` (CR LF on a POSIX host). READ of the bytes `AB\rCD\nEF\n` into
`PIC X(5)` → three records `AB` / `CD` / `EF`, status 00 each. Expected (precedent): `41 42 0A 43 44 45 0A`; READ → two records,
the first `AB\rCD` (the CR is data — whether it is in the line-sequential character set is item 115's question).

## Code sites

`src/Cobol.Net.Runtime/IO/SequentialConnector.cs#OpenWriter` (`NewLine = "\r\n"`) and `ReadPhysicalLine` (LF, CR, CR LF all end
a line). ⚠ The golden `tests/conformance/2023/pb964_ls_plain_write_after_after` pins CR LF; the fixer re-derives it from the
determination, it does not preserve it. Then write DOC-A.1-114 (host newline; CR only as part of CR LF on input).
