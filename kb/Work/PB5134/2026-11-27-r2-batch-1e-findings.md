**Finding:** Two position facts the section already records are re-derived by pc arithmetic: in a debugging section (a _pendingDebug range scan beside SectionInfo.IsDebugging) and a debug subject in the declaratives (SubjectPc < EntryPc, written in the binder and again in the emitter)

**Rule:** One rule in one place / no recomputation of what an earlier stage resolved (DESIGN-architecture-review §5.2; dimensions.md 4); SectionInfo.cs:15-20 states the project rule for exactly this fact: is this pc below EntryPc is an arithmetic re-derivation of a fact the collection already knows, and the rules ask about the SECTION (kb/Work PB433, the same arithmetic EcBinder.cs:180 records removing for RESUME)

**Scenario:** The debugging-section fact is answered two ways in one bind: StatementBinder.BindParagraphs sets _inDebuggingSection from table.ParaSections[i] is { IsDebugging: true } (StatementBinder.cs:243), while BinderContext.Enclosing asks ProcedureTableBuilder.InDebuggingSection(BindCursor), a linear scan of _pendingDebug pc ranges (ProcedureTableBuilder.cs:553, BinderContext.cs:140) that also costs one scan per Enclosing read. The declaratives fact is SubjectPc < _entryPc at ProcedureTableBuilder.cs:562 (DebugsUseProcedure, read per statement at StatementBinder.cs:457) and recomputed in codegen at DispatchEmitter.cs:53 from BoundProgram.EntryPc. **Target:** One answer per fact, from the per-pc owning section: InDebuggingSection(pc) becomes ParaSections[pc] is { IsDebugging: true } (or is deleted for that expression at both callers), and a BoundDebugSubject carries whether its subject section IsDeclarative (set where AddDebugSubject has the SectionInfo), so DebugsUseProcedure and DispatchEmitter read that one recorded bit; the EntryPc comparisons are deleted.
