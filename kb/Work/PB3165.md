# PB3165 — a method's CAPACITY register leaks to sibling methods

Source: `E:\COBOL-coord\scratch\reports\w1078d-PB3154-report.md` (carried from `w1077c-PB3154-report.md`).

- Repro: `E:\COBOL-coord\scratch\w1077c\r2\r9.cob`.
- Code site: `ReferenceResolver.cs#CapacityRegisterFor` (the lookup PB457 and PB2988 changed; both landed, check them first).
- Observed: the CAPACITY IN register of a table declared in one method resolves from a sibling method, and the backend then fails with CS0103 because the register is not in scope in the generated sibling method.

## Landed

Re-probed on this tree: `r9.cob` reproduced CS0103 (`U` does not exist in the sibling method). The root was that
`DataBinder.CapacityRegisters` is ONE map per unit, so a CAPACITY register declared in a method's LOCAL-STORAGE was
visible from every method (and from object-level code), while the method's table is a C# local of its own method. The
same flat map also made two methods that each write `CAPACITY IN Q2` collide (COBOLNET1523 on legal source: two source
elements, §10.5) and made a method register that spells an object-level data-name or register a false duplicate (§11.7.4
GR5 makes the object's declaration inaccessible to the method).

Fix: the register now has the visibility of its entry's data-names. `OoMethodDataScope.CapacityRegisters` holds a method's
registers; `DataBinder.DynamicResolve` registers into, and judges SR30's "elsewhere in the source element" against, the
owning scope (and declares the user word in the method's census); `SymbolTable.CapacityCandidates` is the one
scope-aware lookup (method registers replace the unit's, a method data-name or index-name hides an object-level register) and
`ReferenceResolver.CapacityRegisterFor` reads it. `DeclaredCapacityRegisterTables` still yields the method tables so the
class emits their profiles. Goldens: `pb3165_method_capacity_register_scope` (2014) and the negatives
`pb3165-method-capacity-register-in-sibling-method` (COBOLNET1639) and
`pb3165-method-capacity-register-duplicates-method-data-name` (COBOLNET1523). Sibling arm not fixed here: PB3164 (a
method's CONSTANT entries leak the same way).

Merge-queue bounce (PR #81, run 38794330038): with PB3154 on main, `2014/pb3154_half_capacity_register_hides_symbolic`
printed `A2 CCC`: PB3154's `DataBinder.ActiveMethodDeclares` looked for the method's register in the class's register
index, which this change emptied of method registers. Fixed at the root: `OoMethodDataScope.Declares` asks every name
index of the method's scope (data-, condition-, index-names, CAPACITY registers) and is the one method-tier predicate,
asked by `ActiveMethodDeclares` and `SymbolTable.CapacityCandidates`; `GlobalNameClassDriftTests.MethodDeclares_AsksEveryMethodNameIndex`
holds it to the scope's indexes by reflection.

Branch review R2-1 (head 4d1893ded): `SymbolTable.IndexCandidates` kept the hand-written method tier this change had
replaced in `CapacityCandidates`, asking only the method's data-names and index-names, so a method CAPACITY register `QI`
spelled like an object-level index-name `QI` drew COBOLNET1637 on `COMPUTE N = QI` (legal source refused). The sweep found
the same tier in `TryResolve` (a method condition-name `X` let `MOVE X TO N` read the object's data-name `X`) and
`TryResolveCondition` (a method data-name `X` let `IF X` test the object's level-88 `X`), and a method condition-name `QI`
let `SET QI TO 2` move the object's index. Fixed at the root: every method tier answers from its own class's method index,
then asks `OoMethodDataScope.Declares` and stops before the unit's maps (§11.7.4 GR5, §8.4.6.1).
`GlobalNameClassDriftTests.EverySymbolTableMethodTier_AsksTheMethodsWholeDeclaration` holds every method-tiered
`SymbolTable` member to it. Golden `SHOWF` (`F 0003`) and negatives `pb3165-method-condition-name-hides-object-data-name`
(COBOLNET1639), `pb3165-method-data-name-hides-object-condition-name` (COBOLNET2318) and
`pb3165-method-condition-name-hides-object-index-name` (COBOLNET1639).

## Landing route (wave 1085 D, PB3153 review finding R1-1)

Two branches fixed this defect in two designs. PB3153's enqueue finisher (`47cf8d500` on `worktree-wf_15ec6338-3a0-19`)
kept every method's register in the class binder's one index and filtered it by the owning method at reference time
(`DataBinder.OwningMethodScope`). This note's branch (`worktree-wf_5579bfb3-423-17`, then its review finisher
`worktree-wf_d6f41ebf-faa-3`) moved a method's registers into the method's own scope (`OoMethodDataScope.CapacityRegisters`).
The scope-owned design is kept, because it gives the register the visibility of its entry's data-names in one place:
every reader of the name (`SymbolTable.CapacityCandidates`, `OoMethodDataScope.Declares`, and the §13.18.38.3 SR30
duplicate test in `DataBinder.DynamicResolve`) sees only the method's own registers. The reference-time filter fixed
one reader of the index and left the SR30 test reading the whole class, which refused two methods that each declare
`CAPACITY IN R2` (PB3153 review R1-2). The merge on `worktree-wf_d6f41ebf-faa-7` deleted `OwningMethodScope` and
PB3153's duplicate negative `pb3153-method-reaches-a-sibling-methods-capacity-register` (the same reference as
`pb3165-method-capacity-register-in-sibling-method`). Both branches land through `worktree-wf_d6f41ebf-faa-7`; this
note's `status: landed` and `closes_rows` land with it. The CONSTANT sibling arm stays with PB3164 (open).
