Filed 2026-09-22 by **REGISTRAR #11** from wave 46 group I2's lead 1 (PB757 finisher report, lander lead I2-1). The
lead said the condition was "keyed to the program carrier": a method never raised EC-OO-ARG-OMITTED, a function
raised the PROGRAM name, and the program arm was assumed to work. **Re-measured on this registrar's own build of
main `6871b6e10`** (0 warnings / 0 errors), the defect is WIDER: **the program arm does not raise either**, and the
function arm raises nothing at all (not the PROGRAM name). Probes under `<scratch>/reg11/`.

## Reproduced (every probe: the EC is Fatal in Table 13, so a raise must either run a declarative or end the run unit)

| `i2om2.cob` / `i2om3.cob` | `INVOKE B "SHOW" USING OMITTED`, method `USING OPTIONAL X` + `DISPLAY X` | in the method / line 1 | `X=[    ]` `AFTER SHOW` |
| `i2fn2.cob` | `MOVE FUNCTION R11OMF(OMITTED) TO W`, function `USING OPTIONAL X RETURNING R` + `MOVE X TO R` | line 1, caller declarative on EC-ALL | `W=[    ]`, no declarative, no termination |

The generated C# shows the mechanism: `grep -c ProgramArgOmittedChecking i2pg3.g.cs` = **0** — the callee's
`>>TURN EC-PROGRAM-ARG-OMITTED CHECKING ON` emits nothing — and in `i2pg.g.cs` the one assignment sits in the CALLER's
statement scope (`ExceptionState.ProgramArgOmittedChecking = true;` around the CALL), while the callee's `DISPLAY`
statement scope sets a list of other `…Checking` flags and never this one. The runtime raise site exists
(`CallAbi.Omitted<T>` → `ExceptionState.ProgramArgOmittedError` → `FatalIfEnabled(ProgramArgOmittedChecking, …)`),
so the gate is always closed when the reference executes.

Probable root (the fixer confirms): `EcBinder`'s per-statement query lists `EC-PROGRAM-ARG-OMITTED` in `ProgramNames`,
"the EC-PROGRAM family a CALL/CANCEL raises" — so only a CALL statement is ever marked as able to raise it, and the
§7.3.25.4 statement-scoped checking save/restore (`SaveChecking`) enables the flag only around CALLs. A statement in
the ACTIVATED element that REFERENCES a formal is never marked, so its scope never enables the check. There is no
method or function counterpart name in any list.

## Rules

- `python scripts/spec/cite.py --check 14.9.4.4 "the EC-PROGRAM-ARG-OMITTED exception condition is set to exist"` → OK §14.9.4.4 12)
- `… --check 14.9.23.4 "the EC-OO-ARG-OMITTED exception condition is set to exist"` → OK §14.9.23.4 10)
- `… --check 8.4.3.2.4 "the EC-FUNCTION-ARG-OMITTED exception condition is set to exist and the results of the execution of the function are undefined"` → OK §8.4.3.2.4 8)

Each is keyed to the ACTIVATED element's kind: a program → PROGRAM, a method → OO, a function → FUNCTION.
With checking OFF the documented lenient read (PB133's benign empty value) is correct and must stay.

## What the fixer owes

1. The referencing statement's EC query must name the right *-ARG-OMITTED condition when the statement references
   an OPTIONAL formal of the current element, so its checking scope enables the gate — one rule, three names, keyed
   to the element kind (never the program carrier's name in a method or function).
2. Method formals are copy-in locals (`long N = __omitted0 ? 0L : __N;`, see PB973's generated code): the omitted
   state must survive the copy-in so a reference can raise at all.
3. Group and REDEFINED program formals (a reference to a subordinate item) — the source report inferred, never
   probed, that a subitem reference does not raise; measure it.
4. Re-verdict GR-14.9.4.4-12 (CONFORMS today on the lenient half only) and re-check the pb133 golden header.
5. A golden per activation kind (program 2002, method 2002, function at its edition) with checking on and a
   declarative that shows `FUNCTION EXCEPTION-STATUS`.
