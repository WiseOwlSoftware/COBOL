# PB586 — LANDED — three arms, two unified, one left

Found 2026-09-04 by the `PB208` implementer, which made the format-1 and format-2 VALUE literals share one
screen (`DataBinder.ScreenValueLiteral`) and deliberately left the level-88 arm as its own mechanism. Re-derived
on this tree for this note.

## Repro (`--std 2023`)

```cobol
       01  W  PIC 9(2).
           88  C-BIG  VALUE 12345.      *> compiles clean; the condition can never be true
       01  W2 PIC 9(2) VALUE 12345.     *> error COBOLNET1625
```

## The rule

```
python scripts/spec/cite.py --check 13.18.63.3 "The values specified shall be representable exactly in the subject of the entry, without truncation of leading or trailing nonzero digits"
OK  §13.18.63.3 2)
```

SR2 is an ALL FORMATS rule; Format 3's own SR24 adds only SRs 10 and 17, but SR2 governs it regardless. The three
call sites in `src/Cobol.Net.Compiler/Binding/DataBinder.cs` (`BindCondition`, at the level-88 arms around
`:2190`/`:2206`) call `ValidateValueCategory` — the CLASS half — and never `ValidateNumericValue` — the
representability and SR3 sign half — so an unrepresentable literal is accepted and the condition-name is
unsatisfiable. `ValidateValueCategory`'s doc comment (PB208) now warns any caller of exactly this.

Related, not the same: the registrar's `PB488` (the level-88 pre-filter skips `BindEntry`, so NO clause on a
level-88 entry is screened) and `PB575` (every Format-3 guard reads `parent.Pic`, null for a bit or national
group conditional variable). Land this one on top of PB488's eligibility screen.

## Fix shape

A level-88-shaped sibling of `ScreenValueLiteral` — the same funnel with the conditional variable's PICTURE as the
subject — applied to every literal and to both ends of a THROUGH range (SR3's sign leg and §14.7.8's range rules
interact: a range whose low end is representable and high end is not is still non-conforming). Negative goldens
per edition for the single literal and the range; a positive for the boundary values.

## Landed 2026-09-23 (wave 58, group KC — VALUE clause screens)

Re-probed on the wave-58 build: `01 W PIC 9(2). 88 C-BIG VALUE 12345.` compiled clean at every edition, as did the
THROUGH-range end, the WHEN SET TO FALSE literal-4, a negative literal on an unsigned variable and a fraction on
an integer one.

**Fix.** The three level-88 literal sites (`BindCondition`'s singleton and range arms, `BindFalsePhraseOperand`)
now call `ScreenValueLiteral` — the ONE funnel — instead of its class half, so SR2's range and SR3's sign reach
format 3 with the conditional variable's picture as the subject (§13.18.63.4 GR19). The funnel's size check stays
dark for a condition-name (`ValueSubject.ForConditionName` carries no size, PB598).

**Sibling sweep — the FOURTH arm, fixed in the same change.** The report section's format-4 literals reached
only SR6's edition gate: `03 COLUMN 1 PIC 9(2) VALUE 12345.` PRINTED `45`, `PIC 9(2) VALUE -3` printed `03`, and
`PIC 9(2) VALUE "AB"` leaked Roslyn CS0103. `DataBinder.Reports` now routes each operand through the same funnel
and stores the text it returns. Goldens: `negative/pb586-level88-literal-out-of-range`,
`negative/pb586-report-literal-out-of-range`, `85/pb586_level88_range_boundaries`; `ValueClauseScreenTests`.
⚠ PB942 (open) is untouched: a range whose BOTH ends violate the same rule still reports twice.
