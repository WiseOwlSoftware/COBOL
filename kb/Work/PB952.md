# PB952 — LANDED 2026-09-22 — a domain rule enforced by an artifact, and the artifact has a hole

## Repro — measured

`scratchpad/reg9/probe/acos.cob` (PROGRAM-ID `R9ACOS`), `cobol.exe acos.cob --std 2023 --run`, with
`>>TURN EC-ARGUMENT-FUNCTION CHECKING ON` as line 1:

```
       01  JUST-OVER PIC 9V9(18) VALUE 1.000000000000000001.
       01  R         PIC S9V9(6).
           COMPUTE R = FUNCTION ACOS(JUST-OVER).   DISPLAY "ACOS-JUST-OVER=" R.
           COMPUTE R = FUNCTION ASIN(JUST-OVER).   DISPLAY "ASIN-JUST-OVER=" R.
           COMPUTE R = FUNCTION ACOS(2).           DISPLAY "ACOS-2=" R.
```

```
ACOS-JUST-OVER=000000{
ASIN-JUST-OVER=157079F
NOW THE CONTROL
abnormal run-unit termination: EC-ARGUMENT-FUNCTION (fatal): floating-point intrinsic argument out of domain (NaN result)
```

`000000{` is +0.000000 and `157079F` is +1.570796 — π/2 — in `PIC S9V9(6)` with the trailing overpunch. The run
continued past both. **The control proves the directive is live**: the same program's `FUNCTION ACOS(2)`
terminates the run unit. So the domain screen exists and has a hole exactly where the argument is closest to
the bound, which is the only place a user's data is likely to sit.

The item holds the value exactly (19 digits, inside §13.18.40.3 SR14's 31), so the COBOL value IS greater
than 1. It is the CONVERSION to the body's `double` that rounds it to 1.0, after which `Math.Acos`/`Math.Asin`
return a perfectly ordinary finite number and nothing is NaN.

## The rule — `--check`ed on this tree

```
$ python scripts/spec/cite.py --check 15.8.3 "The value of argument-1 shall be greater than or equal to -1 and less than or equal to +1"
OK  §15.8.3 2)  (Argument rules)
    2) The value of argument-1 shall be greater than or equal to –1 and less than or equal to +1.

$ python scripts/spec/cite.py --check 15.10.3 "The value of argument-1 shall be greater than or equal to -1 and less than or equal to +1"
OK  §15.10.3 2)  (Arguments rules)

$ python scripts/spec/cite.py --check 15.3 "an incorrect value for that argument or for the returned value"
OK  §15.3 14)  (Arguments)
    … If the evaluation of an argument results in an incorrect value for that argument or for the returned
    value according to the rules specified in the function definition and no exception condition was raised
    during item identification or expression evaluation, the EC-ARGUMENT-FUNCTION exception condition is set
    to exist. … If the EC-ARGUMENT-FUNCTION exception condition is set to exist and checking for
    EC-ARGUMENT-FUNCTION is not enabled, the implementor defines the result of the function reference.
```

Both rule 2s are **VALUE** rules, so §15.3 rule 14 is the whole obligation: the condition SHALL be set to exist
for an argument whose value is outside the closed interval. **Expected from the spec:** with checking enabled,
both `JUST-OVER` references set EC-ARGUMENT-FUNCTION. **Observed:** neither does; both return a value.

## WHAT THE SOURCE REPORT GOT WRONG — do not inherit it

The PB620 report and the lander report both say *"ASIN returns π/2 where §15.3 requires 0"*. **§15.3 requires no
such thing.** Its last sentence makes the result implementor-defined only *when checking is NOT enabled*, and
neither returned-value rule names a substitute:

```
$ python scripts/spec/cite.py --check 15.10.4 …   §15.10.4 1) "The returned value is the approximation of the
   arcsine of argument-1 and is greater than or equal to –p/2 and less than or equal to +p/2."   (see PB958 —
   that `p` is a transcription defect for π)
   §15.8.4 1) "… the arccosine of argument-1 and is greater than or equal to zero and less than or equal to π."
```

The defect does not need that claim and is stronger without it: under ARMED checking the condition is not set
at all, and that is a rule violation on its own terms. A fixer who implements "return 0" as a spec obligation
will be writing an unlicensed rule.

## Code site

`src/Cobol.Net.Runtime/Intrinsics/CobolIntrinsics.Float.cs`:

```
:22  public static double Acos(double x) => Math.Acos(x);     // §15.8 — arccos in [0, π]; |x|>1 → NaN → 0
:23  public static double Asin(double x) => Math.Asin(x);     // §15.10 — arcsin in [−π/2, π/2]
:49  public static double Sqrt(double x) => x < 0 ? …ArgumentError("SQRT argument-1 shall be zero or positive (ISO §15.84.3 rule 2)") : …
:55  public static double Log(double x)  => x <= 0 ? …ArgumentError("LOG argument must be > 0 (ISO §15.55.3 r2)")  : Math.Log(x);
:56  public static double Log10(double x)=> x <= 0 ? …ArgumentError("LOG10 argument must be > 0 (ISO §15.56.3 r2)"): Math.Log10(x);
```

Four lines below the hole, three bodies decide their own domain explicitly. The NaN artifact they replaced is
caught centrally by `CobolIntrinsics.cs:272` (`if (double.IsNaN(d)) return …ArgumentError("floating-point
intrinsic argument out of domain (NaN result)")`), which is what fires for `ACOS(2)` and what cannot fire here.

⭐ **ROOT CAUSE SHARED WITH [[PB246]], WHICH ARGUED THIS EXACT POINT AND DID NOT SWEEP.** PB246 landed the
SQRT guard, and its surviving `<remarks>` in this same file says, in the compiler's own words, *"The artifact
is not total"* — then demonstrates a conversion path (`CobolDec.ToDouble`) that turns an out-of-domain value
into an in-domain double. ACOS/ASIN are the siblings it did not reach: `feedback_scan_all_similar`, and the
fix must be the SAME shape (the rule decided at the body, citing its own clause), not a second mechanism.

witness must be the closest representable argument outside the interval, derived — not a round number.

## The sibling sweep the fixer owes

Every body in `CobolIntrinsics.Float.cs` whose §15.x.3 rules constrain a VALUE and which has no explicit guard.
`Atan`/`Cos`/`Sin`/`Tan`/`Exp`/`Exp10` are total over the reals and owe nothing; the question to ask at each is
whether the clause states a domain, and — the part PB246 proved and this note re-proves — whether the
CONVERSION into the body can move a value across that domain's edge. Wherever it can, the screen belongs
BEFORE the conversion, on the COBOL value, not after it on the double.

## Landed 2026-09-22 (wave 49, branch worktree-wf_ca96470f-e1c-3) — one screen, on the exact operand, for all seven

Re-probed first: `ACOS-JUST-OVER=000000{`, `ASIN-JUST-OVER=157079F` under armed checking, control `ACOS(2)` fatal —
reproduced as filed. The sweep the note asked for found the rule shape is SEVEN rows, not two: every §15.x.3 "The
value of argument-1 shall be …" of the binary64 family — ACOS/ASIN r2 [−1, +1], SQRT r2 and ANNUITY r2 [0, ∞),
LOG/LOG10 r2 (0, ∞), PRESENT-VALUE r2 (−1, ∞). The conversion moves a value across the bound in BOTH directions:
past it (the note's ASIN) and ONTO it from the legal side — `PRESENT-VALUE(-0.99999999999999999999 …)` rounds to
−1.0 and the body's `rate <= -1` raised on a legal rate (measured).

- `IntrinsicSig.Domain` + `DomainRule` (catalog column, the argument-side twin of `Codomain`);
  `IntrinsicRenderer.DomainArg` screens argument-1 on its own carrier (`RuntimeApi.DomainArg` →
  `CobolIntrinsics.DomainScaled` exact Int128 vs 10^scale / `DomainDec` exact CobolDec compare / `DomainReal` for a
  value already binary64). A rejected argument raises and becomes NaN, so the checking-off result is the one §15.3
  default via `RealResult`/`FromDouble`.
- The bodies' own tests are GONE (Sqrt/Log/Log10's explicit guards, PresentValue's `rate <= -1`, Annuity's rate arm):
  a second test on the double is the partial copy, and on the legal side it over-rejects. The Dec twins keep their
  exact tests.
- `IntrinsicArgumentDomainDriftTests` derives the column from the standard's §15.x.3 text for every Float row
