# PB242

**Rows:** `GR-14.9.10.4-7`

DELETE's §14.9.10.4 GR7 record-lock release discipline has never been observed: neither branch of the `!meta.Multiple` dispatch, nor the completion release of a self-held lock, is driven by any test — the whole rule rests on a code read plus PB143's vacuity argument.

ROWS: GR-14.9.10.4-7 (PARTIAL, GR7 a)1) and GR-14.9.10.4-L2.2 (PARTIAL, GR7 a)2 + GR7 b) — the same rule's flattened tail). Both rows' own notes carry the READ evidence and both end at the same sentence: the actions are right, and nothing has ever watched them run.

MECHANISM (one symbol, three releases). `FileRegistry.DeleteShared` (FileRegistry.cs:752-770) implements GR7 in three statements: `if (!meta.Multiple) PhysicalFileTable.ReleaseAllExcept(st, name, target);` at the top (GR7 a)2 — 'at the beginning of the execution', correctly not gated on success; the row's note traces `meta.Multiple` to SequentialIoEmitter.EmitSharingRegistration's `bool multiple = file.LockMode?.Multiple ?? false`, i.e. the genuine LOCK ON MULTIPLE RECORDS flag); then the GR6 conflict RetryLoop; then `if (status[0] == '0' && target.Length > 0) PhysicalFileTable.ReleaseSingle(st, name, target);` (GR7 a)1 and GR7 b), at completion, on success only). `ReleaseAllExcept` drops every lock this connector owns whose key is not the target, so the deleted record's own lock survives to the completion rules; `State.RecordLocks` is recId -> ONE owner, which §9.1.16 licenses, so 'all locks held on the deleted record' collapses to one.

WHY THE CORRECTNESS HALF IS CLOSED AND THE ROWS STILL CANNOT MOVE. GR7's antecedent conjunct 'If record locks are in effect' is never evaluated on this path — unlike the siblings `RewriteShared` (:725, :735) and `WriteShared` (:693), which do consult `LocksEffective(meta, st, name)`. PB143 landed the adjudication of exactly that asymmetry and wrote it into the summary comment at :747-751: the siblings gate lock ACQUISITIONS, DELETE acquires none, and a connector for which locks are not effective holds none to release, so the unconditional releases are correct BY VACUITY. That is a documented determination, not a defect — and it is also why the rows are dangerous: the argument is entirely deductive.

THE RESIDUE — ZERO END-TO-END EVIDENCE, MEASURED. (1) tests/Cobol.Net.Tests.Unit/CobolFileLockTests.cs exercises `ReleaseSingle` / `ReleaseAllForConnector` as PRIMITIVES — it never drives a DELETE statement through DeleteShared. (2) conformance:2002/file_sharing_mutate holds locks only through the NON-deleting connector, which is the GR6 conflict path (DELQ51=51 / DELQRT=51 / DELQ=00 after UNLOCK), not GR7. (3) Consequently NEITHER branch of the `!meta.Multiple` dispatch has ever been observed on a DELETE, and no test has ever had a lock for `ReleaseAllExcept` to drop or for the completion release to free. A refactor that reordered the two releases, or that gated a)2 on success, would pass every gate in the repo.

WHAT CLOSES IT (both rows, one change set): a 2002 golden under LOCK MODE IS MANUAL WITH LOCK ON MULTIPLE RECORDS that locks two records through the deleting connector, DELETEs one, and shows the OTHER lock intact; its single-locking twin showing the other lock gone at statement START (proving a)2 fires before the operation, not after); and a case that READs a record WITH LOCK, DELETEs it, and shows a second connector can then lock the same id (GR7 a)1/b) at completion). SPEC REFS carried from the rows: §14.9.10.4 GR7 a)1, a)2, b) (both texts --check OK against 14.9.10.4 per the rows' notes); §9.1.16 (one owner per record lock).
