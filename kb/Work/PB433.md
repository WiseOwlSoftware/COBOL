# PB433 — the declaratives-straddling PERFORM range: no check, and a stack overflow when it bites

## 1. THE MECHANISM

`ControlFlowBinder.BindPerform` composes the range from two INDEPENDENT `ResolveProcedure` calls and never asks
which section either name belongs to, or whether that section is declarative —
`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:288-317`:

    if (ctx.Table.ResolveProcedure(names[0]) is not { } first) return new BoundUnsupported(…);   // :304
    (int start, int end) = first;                                                                // :305
    if ((p.THRU() is not null || p.THROUGH() is not null) && names.Length >= 2)
    {
        if (ctx.Table.ResolveProcedure(names[1]) is not { } thru) return new BoundUnsupported(…);
        end = thru.End;                                                                          // :311
    }

`(start, end)` is a pair of pc indexes and nothing else. The information the rule needs already exists and is
simply never consulted: `ProcedureTableBuilder` records every section and its pc range, and it builds the
DECLARATIVE sections into the same pc space for USE dispatch (`:123-131` walks `pd.declarativePart()`,
`:218-267` collects each declarative section, filling `info.StartPc` / `info.EndPc` at `:263`). A grep for
"declarative" in a §14.9.28 context across `src/` returns only USE-statement machinery.

The consequence is not a missing message. Because the range is POSITIONAL — `__Dispatch(startPc, exitPc)` runs
the pc space forward — a range that begins inside the declaratives and ends outside runs whatever physically
follows the declarative paragraph, and what physically follows is the ordinary procedure division, including the
PERFORM itself. The dispatcher recurses until the CLR kills the process.

## 3. EXPECTED vs OBSERVED — RE-RUN ON HEAD (89044aa0)

Both halves still reproduce. HEAD `cobol.exe`, `--std 2023`.

**(1) One name inside the declaratives, one outside — the canonical violation:**

           PROCEDURE DIVISION.
           DECLARATIVES.
           D-SEC SECTION.
               USE AFTER STANDARD ERROR PROCEDURE ON F1.
           D-P1.
               ADD 1 TO N.
           END DECLARATIVES.
           MAIN-SEC SECTION.
           MAIN-P.
               PERFORM D-P1 THRU MAIN-P2
               DISPLAY "N=" N
               GOBACK.
           MAIN-P2.
               ADD 10 TO N.

    $ cobol.exe .../pf_sr11_decl_split.cob --std 2023 --run
    exit 3221225725
    Stack overflow.
       at System.Int128.op_Division(System.Int128, System.Int128)
       at CobolNet.Runtime.CobolNum.Store(System.Int128, Int32, CobolNet.Runtime.NumProfile ByRef, …)
       at _PRG_PFSR11.__Dispatch(Int32, Int32)
       at _PRG_PFSR11.__Dispatch(Int32, Int32)
       … (repeating until the CLR kills the process)

The program COMPILES CLEAN — no diagnostic at any `--std` — and then dies. The composed range runs from the
declarative paragraph forward through MAIN-P, which contains the PERFORM itself.

**(2) Both names in the declaratives, in DIFFERENT declarative sections:**

           D-SEC1 SECTION. USE … ON F1.   D-P1. ADD 1 TO N.
           D-SEC2 SECTION. USE … ON F2.   D-P2. ADD 10 TO N.
           …    PERFORM D-P1 THRU D-P2

    $ cobol.exe .../pf_sr11_two_decl_sections.cob --std 2023 --run
    exit 0
    N=0011

Compiles, runs, prints 11 — it silently performs a range spanning a declarative-section boundary, which the
standard forbids because the two sections carry different USE dispatch. The adjudicator swept both halves at
`--std 85` and got the same results; I re-ran both at 2023 on HEAD and confirmed the edition-independence by
reading — `BindPerform` has no edition arm, and `VersionConformancePass` has no §14.9.28.3 visitor at all.

**Expected:** both programs violate SR11 and §4.2.2's compile-time warning mechanism shall be able to indicate
both. Both are decidable from the procedure table alone, at bind time, with no run-time information.

## 4. THE CODE SITE AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:288-317` — `BindPerform`, the range
  composition with no section / declaratives test
* `src/Cobol.Net.Compiler/Binding/Procedure/ProcedureTableBuilder.cs:123-131` (the declarative walk), `:218-267`
  (per-section collection, `info.EndPc` at `:263`), `:150-157` (ordinary sections), `:183-199`
  (`ResolveProcedure`)
* `src/Cobol.Net.Compiler/Binding/Procedure/SectionInfo.cs` — the record a declarative flag belongs on

⛔ **The repair is a MISSING FIELD, not a lookup helper.** `ResolveProcedure` returns `(int Start, int End)` — a
naked pc pair that has already thrown away which section the name came from, so any check bolted on afterwards
must re-derive it, and every future rule about a procedure's SECTION will re-derive it again. Follow rule 5:

1. **`SectionInfo` gains `IsDeclarative`** (it is already constructed on the declarative path at
   `ProcedureTableBuilder.cs:218-267`, so the flag costs one constructor argument).
2. **`ResolveProcedure` returns the resolved PROCEDURE, not a pc pair** — the range plus its owning
   `SectionInfo?`. Every caller that only wants the range keeps working through a property; the callers that
   need the section (this rule, and `GO TO`'s and `ALTER`'s analogous constraints) stop guessing.
3. **SR11 then reads as the rule reads**: with both names specified, if either resolved procedure's section is
   declarative, the two sections shall be the same object. One predicate, one new diagnostic naming
   §14.9.28.3 SR11.

⚠ **Both halves must land together.** Case (1) is the one that crashes and is the obvious target; case (2)
("both in the declaratives but different sections") is the quieter half and is the one a smallest-diff fix —
"reject when one name is declarative and the other is not" — would silently leave open.

## 5. THE SIBLING SWEEP

* **SR12 and SR13** live in the same `BindPerform` and constrain procedure-name-1 / procedure-name-2 to the same
  source element; check whether either is enforced, because they share the site and the missing structure.
* **Every other statement that names a procedure RANGE or a procedure in the declaratives.** `GO TO`, `ALTER`,
  the SORT/MERGE `INPUT PROCEDURE` / `OUTPUT PROCEDURE` phrases, `USE FOR DEBUGGING` subjects, and `RESUME AT
  procedure-name` all resolve through `ResolveProcedure` and all inherit the same amnesia about which section a
  name came from. Each has its own declaratives constraint in its own clause — audit them once the resolver
  carries the section.
* **The dispatcher's own defencelessness.** A range whose two ends are not in the same section is exactly the
  shape that makes `__Dispatch` run off into unrelated code; the empty-section case (**PB440**) is the same
  positional-range failure reached a different way. A fixer landing either should check whether a bind-time
  invariant "the composed range is contained in one section, or procedure-name-2 is reachable from
  procedure-name-1" is worth asserting.
* **Edition sweep.** SR11 exists at 85 / 2002 / 2014 / 2023 alike (there is no introduction gate for it), so a
  new rejection fires at every edition — run the NIST corpus, which contains declarative-heavy programs.

## 6. ROWS

* `SR-14.9.28.3-11` — NOT-IMPLEMENTED. Both halves of the rule are open and were measured; the verdict rests on
  the two programs above plus the absence of any declaratives test at `BindPerform:288-317`, and on the fact
  that the information the rule needs is already in the procedure table and simply not consulted.
