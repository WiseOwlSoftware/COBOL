# PB4540 — search-varying-integer-set-to-index: SEARCH ... VARYING integer-item stores the index value instead of incrementing the item

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

In a serial SEARCH (Format 1) with `VARYING identifier-2` where identifier-2 is an integer data item that is not an
index of the table, cobc stores the search index's occurrence number into identifier-2 instead of incrementing
identifier-2 by one each time the search index is incremented. A starting value of identifier-2 other than the index's
is therefore lost.

## Minimal test case

Free reference format (`-free`).
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. SRCHVAR.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 N PIC 9(2) VALUE 10.
01 T.
   05 E OCCURS 3 TIMES INDEXED BY X.
      10 K PIC 9.
PROCEDURE DIVISION.
    MOVE 1 TO K (1)
    MOVE 2 TO K (2)
    MOVE 3 TO K (3)
    SET X TO 1
    SEARCH E VARYING N
        AT END DISPLAY "AT END N=" N
        WHEN K (X) = 3 DISPLAY "FOUND N=" N
    END-SEARCH
    SET X TO 1
    SEARCH E VARYING N
        AT END DISPLAY "AT END N=" N
        WHEN K (X) = 9 DISPLAY "FOUND N=" N
    END-SEARCH
    STOP RUN.
```

## Environment

cobc (GnuCOBOL) 3.2.0 on WSL2 Ubuntu. Command: `cobc -x -free -std=cobol2014 -o p search-varying-integer-set-to-index.cob && ./p`
(cobc issued no diagnostic, compile exit code 0; the host C compiler's `_FORTIFY_SOURCE redefined` warning is an environment artifact of this WSL install; run directly).

## Observed result

```
FOUND N=03
AT END N=04
```
Exit code 0.

## Expected result (per ISO)

§14.9.37.4 3) b) 2.: "If identifier-2 references an integer data item, that data item is incremented by the value one at
the same time as the search index is incremented." §14.9.37.4 4): "If none of the conditions is satisfied, the search
index is incremented by one occurrence number.", and the search is unsuccessful when "the new value for the search index
corresponds to a table element outside the permissible range of occurrence values, in which case the search operation is
unsuccessful". The first SEARCH increments X twice (1 to 2 to 3) before the WHEN is true, so N goes 10 to 12. The second
SEARCH does not reset N; it increments X three times (2, 3, then 4, past the table, AT END), so N goes from 12 to 13, 14
and 15. The rule is in the 2014 edition (SEARCH VARYING is an original feature; `docs/VERSION_CHANGE_REFERENCE.md` lists no
change). Expected:
```
FOUND N=12
AT END N=15
```

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`) prints the expected output above, with no diagnostic.

## Fix site

cobc/codegen.c `output_search_whens`: when `var` is given and is not the table's own index, the generated loop does
`output_move (idx, var)` after incrementing the search index, which copies the index's value into identifier-2 rather
than adding one to identifier-2 (an index data item would likewise need the same increment as the index, rule 3 b) 1.).
Confirmed in the GnuCOBOL 3.2 release source (cobc/codegen.c).

cobc (GnuCOBOL) 3.2.0, WSL2 Ubuntu, `cobc -x -free -std=cobol2014 -o p prog.cob && ./p`.

```
01 N PIC 9(2) VALUE 10.

   05 E OCCURS 3 TIMES INDEXED BY X.
      10 K PIC 9.
...
    SET X TO 1
    SEARCH E VARYING N

        WHEN K (X) = 3 DISPLAY "FOUND N=" N

```
with K = 1, 2, 3 prints `FOUND N=03`; expected `FOUND N=12`. ISO/IEC 1989:2014 SEARCH general rule 3 b) 2: an integer

moves the search index into N (`output_move (idx, var)` in `output_search_whens`) instead of adding 1 to N, so N's own
starting value is lost. The full program is above; a second SEARCH that ends AT END, with N left at 12 by the first, shows the same (`N=04`, expected `N=15`).
