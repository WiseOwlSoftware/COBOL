# PB2130 — interface members used only through their implementations

Found by wave 1026 group C (PB2115, the R0 census; report `w1026c-PB2115-report.md`), filed by the train-1026 lander.

## Observation

The census's semantic walk found no use of three interface members in `src/WiseOwl.Cobol.Compiler/Binding/Bound`:
`IArithmeticStatement.SizeError`, `IBoundRead.AdvancingOnLock` and `IBoundRead.Kind`. Only `SymbolFinder`'s cascade
(an interface member counts as used when an implementation is) keeps them out of the unreferenced list. The census
record lists them as `walkMisses`:
`docs/rearchitecture/evidence/arch-census/79a4b6c58bcae74f5b22964457b2c890a0b85ed4.json`.

## What the Delete wave owes

Confirm by a caller query (LSP `findReferences` on each member) that no code reads the member through the interface
type. If none does, either remove it from the interface (the implementations keep their own property) or record why
the interface must carry it (a generic consumer still to come). Prove neutrality with the R0 oracle
(`python scripts/arch/compare_oracle.py`) and the whole-population gate. Input to the Delete program, PB2119.

## Resolution (wave 20262147 group E)

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundKeyedIo.cs` (`IBoundRead` deleted, `ReadKind` summary,
`BoundKeyedRead` base list), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundTree.cs` (`IArithmeticStatement`,
`BoundRead` base list), `src/WiseOwl.Cobol.Compiler/Validation/VersionConformancePass.cs` (comments of the Step 14h.5
block and `VisitReadAdvancingOnLock`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/KeyedIoBinder.cs`
(`BindRead`, a comment), `src/WiseOwl.Cobol.Runtime/IO/RelativeConnector.cs` (`ReadPrevious`, a comment),
`docs/FILES_DESIGN.md`, `docs/rearchitecture/DESIGN-version-conformance-pipeline.md`,
`conformance-suite/cases/14.9.30-READ/pb343-read-previous-relative-85.cob` and
`conformance-suite/cases/_unassigned/pb353-read-previous-unbindable-file-names-its-edition.cob` (comments).

**Caller query (2026-11-23, at main 223cd4fab5):** `git grep -n "IBoundRead" -- '*.cs'` and the same for
`IArithmeticStatement` find no `is IBoundRead`, and no `IBoundRead` parameter, local or cast: the type was named only
in base lists and comments. Its one consumer, the `VersionConformancePass.GateStatement` arm, moved to the parse arms
(`VisitReadDirection`, `VisitReadAdvancingOnLock`) in kb/Work PB353, and every emitter reads the concrete node.
`IArithmeticStatement` has exactly one reader, the type test `ec.Inner is IArithmeticStatement` in `EcEmitter` (plus
`EcSizeGuardDriftTests`); every `.SizeError` read (`BoundStores`, `StatementEmitter`, `ArithmeticEmitter`,
`CorrespondingEmitter`) goes through the concrete node.

**Decision.** `IBoundRead` is deleted whole: with both members unread it would be an empty interface nothing tests
for, and `BoundIoPhraseConsumptionDriftTests` (kb/Work PB340) already holds each READ node's phrase members to its
emitter. `IArithmeticStatement` stays as a pure marker (`public interface IArithmeticStatement;`, the shape of
`IBoundTransfersControl`): its job is the type test, and
`EcSizeGuardDriftTests.EveryStatementWithASizeErrorPhrase_IsAnArithmeticStatement` checks marker and phrase in both
directions, so the member duplicated an enforcement the test already carries. No generic consumer of either member
is planned (the arithmetic emitters dispatch per node through the visitor). Behavior-neutral: no emitted text changes.
