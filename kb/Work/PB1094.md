# PB1094 — LANDED — the DYNAMIC LENGTH STRUCTURE layout (GR18 PREFIXED length field, GR19 DELIMITED binary-zero delimiter) is recorded on `Model/DynamicLengthStructure` and never r

## Rule text (every citation re-run by the registrar)
- `python scripts/spec/cite.py --check 12.3.7.4 "a delimiter shall directly follow the data described with dynamic-length-structure-name-1"` → `OK  §12.3.7.4 19)  (General rules)`

### Adjudicator finding (special-names-paragraph-p3, harm wrong-answer)
- **Mechanism:** The DYNAMIC LENGTH STRUCTURE layout (PREFIXED length field, GR18; DELIMITED binary-zero delimiter, GR19) is recorded on Model/DynamicLengthStructure and never realized, on the stated premise (CONFORMANCE.md §3 D-DL3, PB991) that 'no operation gives it an addressable byte image'. WRITE does: a dynamic-length item inside an FD record is inlined into the record image as bare content, with neither prefix nor delimiter, so a record holding two such items cannot be read back.
- **Repro:** probe/snp3/g19b.cob, --std 2023: SPECIAL-NAMES. DYNAMIC LENGTH STRUCTURE DLD IS DELIMITED. SELECT F ASSIGN TO "g19b.dat" ORGANIZATION SEQUENTIAL. FD F. 01 R. 05 D1 PIC X DYNAMIC LENGTH DLD. 05 D2 PIC X DYNAMIC LENGTH DLD. PROCEDURE: OPEN OUTPUT F. MOVE "AB" TO D1. MOVE "CDE" TO D2. WRITE R. CLOSE F. OPEN INPUT F. READ F. DISPLAY D1, LENGTH(D1), D2, LENGTH(D2).
- **Expected (spec):** GR19: each item's data is directly followed by one alphanumeric character with all bits zero - record data 'A' 'B' X'00' 'C' 'D' 'E' X'00' - and the structure lets the READ recover D1 = 'AB' (length 2), D2 = 'CDE' (length 3). (GR18's PREFIXED form: a binary length field before each item's data.)
- **Observed:** Measured: file bytes 05 00 00 00 41 42 43 44 45 (4-byte record-length framing + 'ABCDE', no delimiter); READ gives D1=[ABCDE] LENGTH 5 and D2=[] LENGTH 0 - silent data corruption on a round trip. SHORT PREFIXED (g19c.cob, GR18 sibling, a p2 row) is byte-identical and fails identically. §8.5.1.10.3 lets the implementor locate a dynamic-length item outside the record, but this implementation places it INSIDE the record image, so the structure the source declared governs that image. PB991 (open analysis) owns GR-12.3.7.4-19 as 'not observable'; this measurement refutes the premise and should extend PB991 (or open a defect note it points at), together with the D-DL3 determination's sentence.
- **Code site:** src/Cobol.Net.Compiler/Binding/Model/DynamicLengthStructure.cs#DynamicLengthStructure (Delimited / Prefix recorded, read by nothing downstream); the record-image serialization of an FD record containing a DYNAMIC LENGTH item (the file codec - it writes the item's content only)
- **Clause (adjudicator):** ISO/IEC 1989:2023 §12.3.7.4 GR19 (cite.py --check 12.3.7.4 "a delimiter shall directly follow the data described with dynamic-length-structure-name-1" -> OK); sibling §12.3.7.4 GR18; latitude §8.5.1.10.3

## What the fixer owes
Realize the structure in the record-image codec for a dynamic-length item placed inside an FD record (prefix for PREFIXED/SHORT PREFIXED, delimiter for DELIMITED), in both directions, or place such items outside the record as §8.5.1.10.3 permits and say so. Rewrite D-DL3's sentence. This note takes GR-12.3.7.4-19 from PB991 (analysis), whose 'not observable' premise the measurement refutes.

Rows claimed: GR-12.3.7.4-19. Flip `status` and write `closes_rows` in the landing commit (CLAUDE.md rule 8).

## Landed (wave 1003 A)

**Re-probed first, on the wave's own build** (`g19b`, `g19c`, scratchpad `w1003a`): the round trip had already stopped
corrupting (PB1053's extent table, which the note predates, returns `D1=AB`, `D2=CDE`), but the file still held
`41 42 43 44 45` — bare content, no delimiter, no length field — so GR18 and GR19 were recorded on
`Model/DynamicLengthStructure` and read by nothing. The note's remaining defect was exactly the layout.

**Decision (the dispatch offered two spec-licensed shapes; this is the one the rule's text and the design doc's own
words pick).** §8.5.1.10.3 lets the item sit "within the record they are subordinate to", and the design doc already
said a length prefix in the record is "the DYNAMIC LENGTH STRUCTURE clause's job". The other shape (the item outside the
record, §8.5.1.10.3's second option) makes GR18 and GR19 unobservable. So a structured item occupies
`[length field][data][delimiter]` in the record a file holds (D-DL3, rewritten), and the program never sees it:
§8.5.1.11.2's procedural view stays the data alone. A record therefore has two forms, the *contiguous* image and the
*medium* image, and the redesign is that distinction, not a patch to one writer.

**Mechanism (one place each).** `CobolDynStructure` (runtime, new): `Frame`, `ContentOf` (extent known), `TakeAt` (no
table), a `Code` int the compiler passes as constant data. `CobolContiguousLayout` carries each component's code and
makes both forms: `MediumImage` / `MediumExtents` on the way out, `Decompose` on the way in; the frame's extent table
keeps describing the STORED image, so `Position` (a key behind a structured member), the sort store, `ToFixedForm`
(members at their maximum EXTENT) and the READ landing needed no second rule. `CobolVarGroup.ComponentTake` is the one
step of the record walk (`FromContiguous` and `Position` both read it). Compiler: `FileModel.StructureOf` is the one
reader of a declaration; `MaxDynamicExtent` / `MinExtent` count the structure, so GR8-GR10, the RECORD clause SR3/SR4
comparisons, `RecordMax`, `VaryMin/VaryMax` and the key windows follow from it; `OperandText.RecordSendImage` /
`RecordSendExtents` are the send channel (WRITE, REWRITE, RELEASE, keyed READ/START/DELETE) and `RecordAreaImage` stays
the procedural view READ INTO uses; `SequentialIoEmitter.EmitOutOfLineInto` unframes an elementary record; the
cell-backed (EXTERNAL) arm carries the codes through `VarGroupWindow` / `StorageCell`.

**Siblings swept** (variant-analysis, the two-arm rule): the dispatch arms of the record image were the struct group,
the cell-backed group, the ODO wrapper and the elementary record, each through the same `RecordSendImage` /
`EmitOutOfLineInto`; the keyed key image, the released-record "also available" store and the sort `RELEASE` /
`USING` / `GIVING` all ride the same pair (probed: indexed variable and Format 1, relative, sequential variable and
Format 1 with REWRITE, RECORD VARYING DEPENDING, SORT USING/GIVING and procedures, EXTERNAL, national member and
national record). LINE SEQUENTIAL cannot hold the structure (DOC-A.1-115: the characters below U+0020 are outside its
character set), so such a WRITE is the '71' of §14.9.51.4 GR23 — documented in D-DL3, not a defect.

**For the next implementer (code sites and traps).**
- `src/Cobol.Net.Runtime/Values/CobolDynStructure.cs#Frame` / `ContentOf` / `TakeAt` — the ONE codec of a structured member; reuse, never re-spell the length-field or delimiter bytes. Trap: the unit (image characters per position) is 1 for a group member and 2 for a national item that IS the record.
- `src/Cobol.Net.Runtime/Values/CobolContiguousLayout.cs#MediumImage` / `MediumExtents` / `Decompose` / `Position` — the contiguous and medium forms of one record. Trap: a table built by `ExtentsOf` describes the CONTIGUOUS image; only `MediumExtents` describes what a file holds, and `Position` must always be asked of the medium pair.
- `src/Cobol.Net.Runtime/Values/CobolVarGroup.cs#ComponentTake` — the one step of the record walk; a plain member before a structured one with no table is ambiguous by construction (documented, not a bug).
- `src/Cobol.Net.Compiler/Binding/Model/FileModel.cs#StructureOf` / `CarriesStructure` / `MaxDynamicExtent` — the one reader of a declaration and the one place sizes count it.
- `src/Cobol.Net.Compiler/CodeGen/Emit/OperandText.cs#RecordSendImage` / `RecordSendExtents` — every send (WRITE, REWRITE, RELEASE, keyed key image) uses these; `RecordAreaImage` is the procedural view (READ INTO) — a new sender that calls it would silently send an unframed record. `StartTemporaryKeyAreaDriftTests` pins the START arm's name.
- `src/Cobol.Net.Compiler/CodeGen/Roslyn/PlaceRenderer.cs` cell arm: the procedural char store into a cell-backed group passes ALL-ZERO structure codes on purpose; only the READ landing and the send pass the real ones.
- CONFORMANCE.md prose must say "A.1 item N", never `DOC-A.1-N` (AnnexA1RegisterDriftTests counts the token).

**Known limit, stated in D-DL3 (not left implicit).** With NO extent table (a file another program wrote, or a Format 1
file) a plain member followed by a structured one is read as the D-FRA take step reads it, and DELIMITED data that holds
a binary zero ends at that zero; with a table (every file WiseOwl COBOL writes in a variable-length organization) both
round-trip exactly.
