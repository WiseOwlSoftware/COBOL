## The rule (every citation re-run through `cite.py --check`)

> e) If the TRUNCATION phrase is specified and an intermediate data item cannot be represented exactly in SDIDI form, the value shall be the nearest value in that format that is nearer to zero than the intermediate value.

`OK  §11.9.11.2 b)  (General rules) — cite.py's locator reports the OCR sub-item; the printed rule is 3) e)`


## Finding — `intermediate-rounding-clause` (wrong-answer; rows `GR-11.9.11.2-3`)

**Mechanism.** CobolDec.AddSigned folds the far-exponent operand's discarded tail into an UNSIGNED sticky bit; Round34Wide reads it as excess in the result's direction, so an opposite-sign addition whose tail is dropped over-states the magnitude and every non-PROHIBITED INTERMEDIATE ROUNDING mode can deliver the wrong 34-digit SDIDI

**Repro.** OPTIONS. ARITHMETIC IS STANDARD-DECIMAL INTERMEDIATE ROUNDING IS TRUNCATION. 01 R PIC S9 SIGN LEADING SEPARATE. COMPUTE R = ((1 - 1.0E-50) - 1) * 1.0E+34 -> displays +0; COMPUTE R = ((1.0E-50 - 1) + 1) * 1.0E+34 -> +0. Without INTERMEDIATE ROUNDING (default NEAREST-AWAY-FROM-ZERO) or with NEAREST-EVEN: COMPUTE R = ((1 - (5.0E-35 + 1.0E-60)) - 1) * 1.0E+34 -> +0. Control: ((1 - 1.0E-36) - 1) * 1.0E+34 under TRUNCATION -> -1 (correct; exponent gap fits the scratch).

**Expected from the spec.** TRUNCATION (11.9.11.2 3e): 1 - 1E-50 is not representable in 34 digits, so the value is the nearest one nearer to zero, 0.9999999999999999999999999999999999 (1 - 1E-34); minus 1 is -1E-34 exactly; times 1E34 = -1. Symmetrically (1E-50 - 1) -> -(1 - 1E-34), +1 -> 1E-34, times 1E34 = +1. NEAREST-AWAY-FROM-ZERO (3a/3b) and NEAREST-EVEN (3c): 1 - 5.0000000000000000000000001E-35 = 0.(34 nines)4999... whose nearest 34-digit value is 1 - 1E-34 (not a tie), so the result is -1. Cross-checked with Python decimal at precision 34 in each mode.

**Observed / reasoning.** AddSigned shifts the higher-exponent significand up to 38 digits, then for the residual gap calls ShiftDownSticky(loSig, residual) = (sig / 10^n, sig % 10^n != 0): C# truncation toward zero of a NEGATIVE low operand yields a smaller-magnitude addend, and the lost tail is reported only as a sign-less 'dropped' bool. Round34Wide(extraSticky: true) then (TRUNCATION) keeps the over-stated digits, or (NEAREST modes) treats roundDigit 5 + sticky as above half. For 1 - 1E-50: hiSig = 10^37, loSig truncates to 0 with sticky, S = 10^37 -> 1.000...0 instead of 0.(34 nines). Every op is reachable from ordinary COMPUTE/ADD/SUBTRACT under STANDARD-DECIMAL (and on the native Dec lane via a float literal, PB274). Silent - no diagnostic, no exception. Suggested root fix: make the discarded tail signed - e.g. jam the sticky into the lowest scratch digit with the low operand's sign (loSig += sign(lo) when dropped), which is always below the round digit because |hi| >= 10^37 and |lo| < 10^34 after the shift - and sweep the sibling alignment in any other add/compare path.

**Code site.** src/Cobol.Net.Runtime/Values/Numeric/CobolDec.cs#AddSigned (lines ~478-503); CobolDec.cs#ShiftDownSticky (~865); CobolDec.cs#Round34Wide (~677-712)

## What the fixer owes

Carry the discarded tail's SIGN relative to the result (a signed sticky / guard digit) through AddSigned → Round34Wide so the directed modes see 'below' vs 'above' correctly; re-derive NEAREST-EVEN, NEAREST-AWAY and TRUNCATION on the opposite-sign cancellation cases. Unit tests on CobolDec with exact expected SDIDI per mode, and a golden with the repro's two COMPUTEs under each INTERMEDIATE ROUNDING mode. Sweep ShiftDownSticky's other callers (subtract, multiply-add paths).
