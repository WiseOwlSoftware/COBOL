# PB784 — OPEN — one directory, N agents, and a filename nobody owns

Filed 2026-09-06 by the registrar from the PB712 finisher's report (`PB712-report.md` §"New defects" (a)).
**Every claim below was re-measured on the shared directory itself**, which still holds the evidence.

## The mechanism

A fleet's implementers each get their own git worktree — the briefs are emphatic about that
(`implementer-brief.md:1`: *"You are in an isolated git worktree … work ONLY there"*). They do **not** get their
own scratchpad. Every subagent of one parent session is handed the same directory, and the briefs' only
instruction about writing into it is a bare noun:

- `.claude/skills/workstream/templates/implementer-brief.md:18` (step 7, the gate) — *"read the verdict line
  from the redirected file"*. It mandates a redirect and names no path.
- `.claude/skills/workstream/templates/implementer-brief.md:16` (step 5) — *"write a record_verdicts batch
  (scratchpad, then `python scripts/spec/record_verdicts.py --dry-run` then apply)"*. Same shape: the directory,
  never a filename.
- `.claude/skills/workstream/SKILL.md:25` — the orchestrator row is the ONE place a name is fixed, and it is
  fixed by CLUSTER: *"reports are FILES under the scratchpad (`reports/<cluster>-report.md`)"*. That row is
  collision-free precisely because it interpolates the cluster; nothing generalises that habit to the agents.

`lander-brief.md:9` (`<scratch>/{CLUSTER}.patch`), `lander-train-brief.md:9` (`<scratch>/<cluster>.patch`) and
`SKILL.md:23` (`<out>/<stage>-<slug>.jsonl`) are the three sites that already interpolate an identity and are
therefore **safe** — recorded here so a fixer does not "fix" them.

## Measured, on the shared directory, today

`E:\Temp\claude\E--CobolSharp\49b17747-ce58-4386-8c49-ecb2ce644f8d\scratchpad` — one parent session — holds
**1034 entries**, of which **eleven** are gate output under a generic basename:

```
gate-integration.log  gate-lock.log  gate-nist.log  gate-union.log  gate-union2.log
gate.txt  gate1.log  gate1.txt  gate2.log  gate2.txt  gate3.txt
```

`gate3.txt` is the artifact of the reported collision and is still on disk, mtime `Sep 6 11:31`:

```
3576 files scanned for phantoms, 1717 for construct agreement · 254 constructs keyed to their own clause
⛔ 0 finding(s)
```

The PB712 finisher's own audit scanned **3572** files. So the file it opened as its verdict was a sibling's, and
the count differed by four — the discrepancy is what made it look. Its report records the write side of the same
event: *"PowerShell refused: `Out-File: The process cannot access the file … because it is being used by another
process`; the file that came back held ANOTHER agent's filter
(`~Directive|~VersionMatrix|~EditionGate|~ExceptionCondition|~Corpus|~Vcr|~Nist`)"*. It worked around it by
inventing a private path (`…\scratchpad\pb712probe\gate-pb712-run1.txt`) — a per-agent convention, arrived at
privately, and written down nowhere.

## Why this is worth a note rather than a shrug

⛔ **The loud failure is the lucky branch.** A write that collides with a live handle throws, and the agent
notices. A write that lands *after* the sibling's has closed does not collide at all — the second agent simply
overwrites, or reads, a file whose contents belong to a different worktree, a different filter and a different
compiler build. Nothing in the loop can tell those apart: the brief says read the verdict line from *the*
redirected file, and a stale sibling's `Passed! - Failed: 0` is a perfectly well-formed verdict line
(`feedback_specify_the_bar_not_the_format` — worthless but well-formed is exactly the failure this shape
produces, and `feedback_gate_on_the_verdict_line` presumes the line came from YOUR run).

It is `process_only` because no user program is affected. It is `silent` because the failure mode it enables
produces no error at all — the same reason `kb/Work/PB775` and `kb/Work/PB767` are on the register: a brief
that reads correctly and cannot be complied with safely.

## Fix shape — a name with an identity in it, in the briefs, not in each agent's head

⛔ Not a lock, not a retry, not a helper script. The register already knows the pattern that works — every
collision-free site in the workstream skill interpolates the identity of the writer (`<cluster>`, `<slug>`).
Apply it to the two sites that do not:

1. **A per-agent subdirectory, named once at the top of each brief**: `<scratch>/{CLUSTER}/` (implementers and
   landers already receive `{CLUSTER}`; the registrar and workflow stages receive `{BATCH}` / `<slug>`),
   created by the agent's first write, with the standing rule *"every file you write goes under it; you never
   write a bare basename into `<scratch>` itself"*.
2. **Name the gate file in the step that mandates reading it.** `implementer-brief.md:18` should say the path
   as well as the obligation — *"redirect to `<scratch>/{CLUSTER}/gate-<n>.txt` and read the verdict line from
   THAT file"* — because the sentence that creates the file is the only place the convention can be enforced by
   reading. Same for step 5's `record_verdicts` batch, whose path the report is then required to quote.
3. ⭐ **Prefer the shape that makes the next agent automatic** (CLAUDE.md rule 5): the identity belongs in the
   ONE line of each brief that names the scratchpad, so no future step has to remember. There is no drift test
   available here — the scratchpad is outside the repo and nothing in CI can see it — so the mechanical half is
   the interpolation itself, and the note says so rather than inventing a gate that cannot exist.
