# PB4089 — STRING into a numeric DISPLAY receiver decodes a number instead of moving characters

**Sites:** `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/StringEmitter.cs#WriteImage` (the `NumParseDisplay` arm, deleted), `src/WiseOwl.Cobol.Compiler/Binding/Passes/UsageCollectionPass.cs#Visit` (the `BoundStringStmt` overload: identifier-3 is a character channel), `docs/STRING_OPS_DESIGN.md` (the STRING receiver line), `src/WiseOwl.Cobol.Compiler/Binding/Passes/StorageFormPass.cs#ComputePromotedSet` (arm 6: a promoted Tier-A alias promotes its canonical), `src/WiseOwl.Cobol.Compiler/Binding/Model/PicInfo.cs#IsCharacterFormNumeric` (doc comment)

**Observed** (the PB1908 implementer, 2026-10-29). With `01 N PIC 9(6) VALUE 123456`, `STRING "AB" DELIMITED BY SIZE INTO N`
leaves N as `003456`. GnuCOBOL 3.2 gives `AB3456`. `WriteImage` re-reads the whole receiver image as a number
(`RuntimeApi.NumParseDisplay`) and stores that value.

**Expected (ISO/IEC 1989:2023, each citation checked with `cite.py --check`).**
- §14.9.43.3 SR1: identifier-3 need only be "described implicitly or explicitly as usage display or national", so a
  numeric DISPLAY integer receiver is legal (SR5 forbids only edited and JUSTIFIED receivers).
- §14.9.43.4 GR3 a): characters are transferred "in accordance with the MOVE statement rules for alphanumeric-to-alphanumeric moves".
- GR6: "the moves behave as though the characters were moved one at a time" into the receiver's character positions.
- GR7: "only the portion of the data item referenced by identifier-3 that was referenced during the execution of the
  STRING statement is changed".

So positions 1-2 receive `A` and `B`, positions 3-6 keep `3456`, and N holds the characters `AB3456`. The value is not
re-interpreted, nothing is decoded, and the untouched positions keep their content. GnuCOBOL agrees.

**Fix.** Write the transferred characters into the receiver's character positions as STRING does for an alphanumeric
receiver, and leave the other positions alone. Do this for every numeric DISPLAY receiver shape: signed (an
overpunched or separate sign position is just a character position here), unsigned, with or without POINTER.
Golden: the case above plus a POINTER variant writing into the middle, a signed receiver and a value that is not all
digits. Check the editions (Annex E) for whether a numeric receiver was legal before 2002. Sibling sweep: UNSTRING
into a numeric receiver uses MOVE semantics (§14.9.48), which is a different rule, so confirm it is unaffected.

## Landing

Re-probe on the build of 20fecec14: `N=003456` (the whole image decoded to a number), `SS=003456+`, `G=AB3XYZ` correct, and a REDEFINES pair `A1 PIC 9(4)` / `A2 REDEFINES A1` lost the letters too (`A1=0034`).

Root cause: `StringEmitter.WriteImage` re-read a native-numeric identifier-3 as a number because nothing gave the numeric DISPLAY item a character-image carrier. STRING already reads the receiver's image (`ReadImage`), so the emitter was right and the STORAGE FORM was wrong. The fix is one line at the existing mechanism: `UsageCollectionPass.Visit(BoundStringStmt)` records an elementary identifier-3 as a CHARACTER CHANNEL (`Channel(n.Into)`), the twin of INSPECT's (kb/Work PB1128), so `StorageFormPass` promotes the item to `CharImage(Numeric)` (a Tier-A REDEFINES alias forwards to its promoted canonical, kb/Work PB3563) and `WriteImage` assigns the image. The decode arm is deleted: no receiver can reach it. Verified: signed overpunch, SIGN TRAILING SEPARATE, POINTER into the middle, a table occurrence, a Tier-A and a Tier-B REDEFINES, EXTERNAL, BASED and LINKAGE items, a national numeric item, and a numeric result used afterwards (`ADD 1 TO N`). UNSTRING into a numeric receiver is a MOVE (kb/Work PB979) and is unchanged.

Witness: `conformance:cases/14.9.43-STRING/pb4089_string_into_numeric_display` (accept 2014, 2023: Annex E lists no STRING change, so the rule is the 2014 one; the 85 and 2002 edges are not derivable in this repository).
