# PB567

## Mechanism
the condition-name subordination relation has only a POSITIVE side: a condition-name qualified by a data-name it is NOT subordinate to is neither resolved nor diagnosed

### The refutation this note is written from
Row `SR-13.16.3-23` was adjudicated CONFORMS and OVERTURNED to `PARTIAL` by the refuter. Its reasoning, verbatim:

> REFUTED -> PARTIAL, on two independent grounds, both measured. (1) ONLY HALF THE RULE IS IMPLEMENTED. 'Each condition-name is subordinate to THE data-name with which it is associated' asserts a relation with a positive and a negative side: the condition-name resolves through that data-name and its containing groups, and it resolves through NOTHING ELSE. The positive side is genuinely solid -- I widened the adjudicator's three probes to nine and every one is right: qualification by a NON-IMMEDIATE ancestor (`IS-A OF G1`, which the adjudicator never tried -- they only tried the negative `IS-A IN G2`), full qualification, a three-deep hierarchy where G, M and S each serve as qualifier, an 88 on a level-77 item, an 88 on a level-01 elementary item, an 88 on an alphanumeric GROUP, subscripting inherited from the conditional variable (`IS-X (1)` F / `IS-X (2)` T), SET through a non-immediate qualifier, and the ambiguity diagnostic COBOLNET1639 when two identically-named 88s make an unqualified reference non-unique. The NEGATIVE side does not exist. A condition-name reference qualified by a data-name it is NOT subordinate to is neither resolved nor diagnosed: `IF IS-A OF H1` (H1 an unrelated record that has no IS-A), `IF IS-A OF T` (an unrelated elementary item), `IF IS-A OF G2 OF G1` (both names real, no containment between them) and `IF IS-A OF G1 OF S` (real ancestors in REVERSED hierarchical order, which 8.4.2.2 forbids) ALL compile clean, exit 0, and emit `NotImplemented.Value<bool>("condition 'IS-AOFH1'")` into the generated C# -- a run-time NotImplementedCobolFeatureException. `SET IS-A OF H1 TO TRUE` likewise compiles clean, emitting `NotImplemented.Run("SET 'IS-AOFH1' TO TRUE (not a condition-name)")`. This is the two_arm_dispatch shape and I measured both arms side by side in ONE program: the DATA-name arm has the failure branch -- `MOVE "C" TO ST-CODE OF NOSUCHREC` gives COBOLNET1639 "'ST-CODE' is declared, but not under the given qualifier (NOSUCHREC)" -- while the CONDITION-name arm, the arm this rule is about, has none. So the compiler enforces subordination for data-names and merely PERMITS it for condition-names. Two halves, one verified => PARTIAL. (The fallback is shared with an entirely undeclared name -- `IF NO-SUCH-COND` and `SET NO-SUCH-COND TO TRUE` behave identically -- so the missing branch is one place: the condition-name arm of the qualifier walk in ReferenceResolver, which the adjudicator itself named as this row's code-location.) (2) THE CITED TEST CANNOT FAIL FOR THIS RULE'S REASON, so the test-ref must be cleared to empty. conformance-test:TypedefConditionTests.TwoRecordsQualifiedConditions_CompileClean asserts ONLY `ok == true` over a program whose condition-name content is `SET OPEN-ST OF DOOR TO TRUE` and `IF OPEN-ST OF DOOR AND CLOSED-ST OF GATE`. Because both of those statement forms degrade to compile-clean NotImplemented stubs when the condition-name does not resolve, I took that test's EXACT source, changed only the condition-name qualifiers to nonsense (`OPEN-ST OF NOSUCHREC`, `NOT-A-COND OF GATE`), and it still compiled clean at --std 2002, exit 0. Its only real teeth are the `MOVE "C" TO ST-CODE OF GATE` line -- a DATA-name, which does have a failure branch -- so the test pins the TYPEDEF clone of ST-CODE, not condition-name subordination. It is a green gate with no power over this row (green_gates_arent_evidence), and it was also written for 13.18.58.4 GR1, a different question. With it removed the row has no closing test, which is fine and expected -- but it is now PARTIAL-untested, not CONFORMS. Editions unchanged (85,2002,2014,2023): the qualified positive case behaves identically at --std 85, 2002 and 2014, and the missing negative branch is edition-independent. Cosmetic defect noticed in passing, worth a sweep line: every qualified reference is rendered in diagnostics and in the NotImplemented feature string with the OF/IN separators stripped -- 'IS-AOFS', 'IS-AOFG2OFG1', 'ST-CODEOFNOSUCHREC' -- so the user is shown a name they did not write.

### Inventory row `SR-13.16.3-23` (PARTIAL)
Verified by construction and by probe. Two identically-named condition-names on two different records resolve through the conditional variable's ancestry: `01 G1. 05 S PIC X VALUE "A". 88 IS-A VALUE "A". 01 G2. 05 S PIC X VALUE "B". 88 IS-A VALUE "A".` gives `IS-A OF S OF G1` TRUE, `IS-A OF S OF G2` FALSE and `IS-A IN G2` FALSE — i.e. the condition-name is reachable through, and only through, the name hierarchy under its own data-name, with no ambiguity error. The named test asserts the same qualification path over TYPEDEF-cloned conditions, but asserts compile-clean only, not the truth values; a value-asserting golden would close this row more strongly. || REFUTED: PARTIAL — REFUTED -> PARTIAL, on two independent grounds, both measured.
