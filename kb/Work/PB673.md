# PB673 — one delegate on a connector where the rule is written per executing runtime element

Found 2026-09-05 by the `PB324` implementer (report §"New defects" 1), which installed the ASSIGN … USING source
with exactly the shape [[PB168]] chose for the LINAGE evaluator and, in doing so, measured that the shape is wrong
for both.

## The rule

§12.4.5.3 GR3 b (`cite.py --check 12.4.5.3` → `OK 3) b)`): *"…identified by the content of the data item
referenced by data-name-1 **in the runtime element that executes** the OPEN, SORT, or MERGE statement"*. An EXTERNAL
file connector is one per run unit (§13.18.22.4 GR4 a, *"the file connector associated with this file description
entry is an external file connector"*), and §12.4.5.3 GR1 b requires only *"A consistent specification for
data-name-1, device-name-1, and literal-1"* — unlike GR1 i, which for FILE STATUS says the data item shall be the
same external item. So two programs may legally describe one EXTERNAL connector with their own, separate,
identically-named `data-name-1`, and the standard says which one is read: the executing program's. §13.18.34.4 GR2
(*"the value of the data item referenced by data-name-1"*) is the LINAGE twin.

## The mechanism

`SequentialIoEmitter.EmitAssignSources` (on PB324's branch, train 10 row 2) emits
`CobolFile.SetAssignUsing(key, () => <data-name-1>)` unguarded on every activation, beside
`EmitLinageEvaluators`' `SetLinage`, and for the same PB168 reason — the closure must read THIS activation's
instance, and the guarded alternative froze the FIRST activation's capture forever. Both install ONE delegate on a
run-unit-scoped connector (`FileConnector.SetAssignUsing`, `SequentialConnector.SetLinage`), so the delegate the
connector holds is the last activator's, not the executor's.

**Repro sketch:** programs A and B both `FD F IS EXTERNAL` with `SELECT F ASSIGN USING FNAME` and their own
`01 FNAME PIC X(20)`; A activates, then B activates (overwriting the closure), then A executes `OPEN INPUT F` — the
file opened is the one B's `FNAME` names. Silent: status '00', wrong physical file. The LINAGE twin gives a wrong
logical page the same way.

## Fix

Structural, one change serving both clauses: key the installed source by the executing unit, or resolve it through
the activation frame at the OPEN/SORT/MERGE (and at the LINAGE read), rather than storing one delegate on the
connector. Sweep for a third face — any other per-activation source installed on a run-unit-shared object (FILE
STATUS is exempt by GR1 i's "same external data item"; RECORD KEY / ALTERNATE RECORD KEY / RELATIVE KEY sources need
the same reading). Goldens: two programs, one EXTERNAL connector, the non-last activator executes the OPEN.
Code sites: `src/Cobol.Net.Compiler/CodeGen/Verbs/SequentialIoEmitter.cs#EmitAssignSources`, `#EmitLinageEvaluators`;
`src/Cobol.Net.Runtime/IO/FileConnector.cs#SetAssignUsing`; `src/Cobol.Net.Runtime/IO/SequentialConnector.cs#SetLinage`.
Do not dispatch before train 10 lands (PB324 is where `EmitAssignSources` lives).

## ✅ LANDED 2026-09-05 — the operands travel with the STATEMENT, not with the connector

**One structural change served both clauses, and it deleted a mechanism rather than guarding it.** A file
connector holds NO per-element source any more: `FileConnector.SetAssignUsing`, `SequentialConnector.SetLinage`,
their `FileRegistry`/`CobolFile` forwarders, `SequentialIoEmitter.EmitAssignSources` / `EmitLinageEvaluators`
and `RuntimeApi.FileSetAssignUsing` / `FileSetLinage` are gone. In their place every OPEN entry takes the
EXECUTING element's `assign, assignDynamic, page` triple and every sequential WRITE entry takes its
`LinagePage?` — **with no defaults**, so an emitter path that forgets them is a C# compile error rather than a
silent wrong file or a dead page model. `SequentialIoEmitter.ExecutingElementArgs(file)` / `LinageArg(file)`
render them inside the unit that runs the statement, which IS the executing runtime element, so the emitted
expression reads the LIVE activation's storage. `FileConnector.Associate(spec, dynamic)` is the one association
entry for both GR3 arms; `SequentialConnector.BeginLinagePage` adopts the page at the COMPLETION of a successful
OPEN OUTPUT, which is where §13.18.34.4 GR6 b) 1. puts it (it used to run inside `OpenCore`, before completion).
`HasLinage` is gone with the closure: "this FD has a LINAGE clause" is now exactly "the statement supplied a
page".

**The premise did not hold in one half, and the note is corrected here.** The LINAGE twin has NO cross-program
face: §13.4.5.4 GR2 c) 2. requires every file description entry for one external connector to specify LINAGE
with *"the same corresponding external data items"* (and COBOLNET1624 enforces the externality half at 2023),
exactly the way §12.4.5.3 GR1 i) exempts FILE STATUS. What the LINAGE half really has is the cross-ACTIVATION
face, which ASSIGN … USING shares: a RECURSIVE non-INITIAL unit's connector is unit-scoped (§8.6.4,
§14.6.2.3.3) while its LOCAL-STORAGE is per-activation, so after an inner activation returns the installed
closure reads DEAD storage. `2023/pb673_recursive_assign_linage` pins that face for both clauses at once.

**The sweep found a third face and the change closed it for free.** `OoEmitter.EmitFileMembers`' class ctor
installed the ASSIGN source but NOT the LINAGE evaluator (only `DispatchEmitter.__Activate` did) — the two-arm
dispatch with one arm fixed, so an object's or factory's LINAGE FD had no page model at all: no counter, no
end-of-page, `LINAGE-COUNTER` stuck at 0. **MEASURED, not deduced:** at the pre-change base `1a3cc30d` a
factory FD with `LINAGE IS 4 LINES WITH FOOTING AT 2` printed `NOEOP1`/`NOEOP2`; it now prints
`EOP1`/`EOP2`, and `2002/pb673_oo_factory_linage` pins it. Moving the operands onto the statement removes
the second arm entirely rather than adding a second install. FILE STATUS was checked and is exempt (§12.4.5.3 GR1 i, and it was already stored at the statement);
RECORD KEY / ALTERNATE RECORD KEY are record offsets registered once (GR1 j/k), and RELATIVE KEY is read at its
own verb sites in `KeyedIoEmitter` — neither is an installed source. `ReportWriter`'s closures are per-INSTANCE
engine state, and a report FD cannot carry LINAGE (§13.4.5.2 Format 3 has no linage-clause), so it passes
`page: null` with that citation.

**Measured** with the worktree `cobol.exe`: the note's own repro sketch put `AAAAA` in `pb673b.dat` — the LAST
ACTIVATOR's file — with status '00'; it now lands in `pb673a.dat`, the EXECUTOR's.
`2023/pb673_external_assign_executor` (CHKB=05 · CHKA=00 · READA=AAAAA) and
`2023/pb673_recursive_assign_linage` (EOP=N LC=02 · EOP=Y LC=03 · CHKI=05 · CHKO=00) pin both faces, expected
values derived from §12.4.5.3 GR3 b), §13.18.34.4 GR6 b) 1./GR7 c) 2./GR7 d) and §14.9.51.4 GR26 b).

**Also landed with it:** `docs/CONFORMANCE.md` §7 gained the MISSING **DOC-A.1-72** row — Annex A.1 item 72
("FILE-CONTROL entry, ASSIGN clause (consistency rules for external file connectors)") is REQUIRED and had no
determination, while the rule was already being ENFORCED by the `SelectFingerprint` EC-EXTERNAL-FILE-MISMATCH
check. It is textual sameness of the clause (same target, same data-name-1 spelling), never sameness of the
data ITEM — which is precisely what leaves GR3 b) something to decide.
