# PB673 — OPEN — one delegate on a connector where the rule is written per executing runtime element

Found 2026-09-05 by the `PB324` implementer (report §"New defects" 1), which installed the ASSIGN … USING source
with exactly the shape [[PB168]] chose for the LINAGE evaluator and, in doing so, measured that the shape is wrong
for both.

## The rule

§12.4.5.3 GR3 b (`cite.py --check 12.4.5.3` → `OK 3) b)`): *"…identified by the content of the data item
referenced by data-name-1 **in the runtime element that executes** the OPEN, SORT, or MERGE statement"*. An EXTERNAL
file connector is one per run unit (§13.18.22.4 GR4 a, *"the file connector associated with this file description
entry is an external file connector"*), and §12.4.5.3 GR1 b requires only *"A consistent specification for
data-name-1, device-name-1, and literal-1"* — unlike GR1 i, which for FILE STATUS says the data item shall be the
same external item. So two programs may legally describe one EXTERNAL connector with their own, separate,
identically-named `data-name-1`, and the standard says which one is read: the executing program's. §13.18.34.4 GR2
(*"the value of the data item referenced by data-name-1"*) is the LINAGE twin.

## The mechanism

`SequentialIoEmitter.EmitAssignSources` (on PB324's branch, train 10 row 2) emits
`CobolFile.SetAssignUsing(key, () => <data-name-1>)` unguarded on every activation, beside
`EmitLinageEvaluators`' `SetLinage`, and for the same PB168 reason — the closure must read THIS activation's
instance, and the guarded alternative froze the FIRST activation's capture forever. Both install ONE delegate on a
run-unit-scoped connector (`FileConnector.SetAssignUsing`, `SequentialConnector.SetLinage`), so the delegate the
connector holds is the last activator's, not the executor's.

**Repro sketch:** programs A and B both `FD F IS EXTERNAL` with `SELECT F ASSIGN USING FNAME` and their own
`01 FNAME PIC X(20)`; A activates, then B activates (overwriting the closure), then A executes `OPEN INPUT F` — the
file opened is the one B's `FNAME` names. Silent: status '00', wrong physical file. The LINAGE twin gives a wrong
logical page the same way.

## Fix

Structural, one change serving both clauses: key the installed source by the executing unit, or resolve it through
the activation frame at the OPEN/SORT/MERGE (and at the LINAGE read), rather than storing one delegate on the
connector. Sweep for a third face — any other per-activation source installed on a run-unit-shared object (FILE
STATUS is exempt by GR1 i's "same external data item"; RECORD KEY / ALTERNATE RECORD KEY / RELATIVE KEY sources need
the same reading). Goldens: two programs, one EXTERNAL connector, the non-last activator executes the OPEN.
Code sites: `src/Cobol.Net.Compiler/CodeGen/Verbs/SequentialIoEmitter.cs#EmitAssignSources`, `#EmitLinageEvaluators`;
`src/Cobol.Net.Runtime/IO/FileConnector.cs#SetAssignUsing`; `src/Cobol.Net.Runtime/IO/SequentialConnector.cs#SetLinage`.
Do not dispatch before train 10 lands (PB324 is where `EmitAssignSources` lives).
