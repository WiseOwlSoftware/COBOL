**Leads (each still true at this branch's head; none blocks the listing's correctness, each is a use or a reference the
cross-reference does not yet show):**

1. *An index-name's store is classified `Read`.* An index-name's cell is held by the bound tree as its field name
   (`ExpressionBinder.IndexFieldOf`, `BoundIndexRef`), no `Place`, so `SET IX UP BY 1`, `SET IX TO 3` and a PERFORM or SEARCH
   VARYING index have no store position to pair with their occurrence. The fix is the index cell as a place of its own (or the store
   taxonomy asking the index targets), a restructuring of the bound index operand. Witness of the gap:
   `ListingCrossReferenceTests.EachReference_StandsWhereItIsWritten_WithTheUseItsPositionGives` asserts only the position of `SET IX`.
2. *The special registers have no entry.* LINAGE-COUNTER, LINE-COUNTER, PAGE-COUNTER and EXCEPTION-OBJECT are identified by
   `ReferenceResolver.Identify`'s register arms, and no declaration enters them (section 6.7.1's "Identify's arms all record" is
   met for the CAPACITY, DEBUG-ITEM and sum-counter arms only). Each needs an entry where the standard defines it implicitly (a LINAGE
   file's counter at its LINAGE clause, a report's counters at its RD), then the arm records like the others; the oracle's
   `NamesNothing` exemption for the three counter tokens is removed with it.
3. *`BoundReferences` does not enter a tuple.* `BoundSetConditions.Sets` holds each conditional variable's place in a value tuple,
   which `BoundReferences.Enters` does not walk, so the place is in no statement's `Reach`: `StorePositionsOf` asks the places linked
   since the statement's mark beside it for that reason. The sibling: X3.23-1985 USE FOR DEBUGGING's "explicitly references" (`DebugTriggerPlanner`) and
   the USE BEFORE REPORTING control-data reference check (`ReportWriterBinder.CheckControlDataReferences`) read the same `Reach` (a 2002+ statement, so no 1985 debug trigger is lost
   today). The root fix is `BoundReferences` entering value tuples, with a sweep of every bound node holding one.
4. *A whole table stored with no place is classified `Read`.* A table SORT (`BoundTableSort.Storage`) and INITIALIZE's whole dynamic
   table store into the table with no place of the reference (design section 6.7.1, "Store kind": "reports the table item as
   ReadWrite, matched to the statement's occurrence of that table"), and `WholeTable`'s `TableAllPlace` is not linked.
5. *A CALL by literal is not in the CALL graph.* The CALL graph is made of the references to program, program-prototype and
   function-prototype entries; `CALL "LIT"` writes no name (a literal is no slot), so a literal call to a contained program is no
   edge. The binder resolves it (`StatementBinder.NestedCallables`); the edge needs that resolution recorded as a reference to the
   program's entry at the literal.
6. *The statistics' counts of names and uses (section 4.1's table) are not built.*
7. *A `--permissive` reference that resolves an ambiguous name to its first declaration records no occurrence* (a candidate set of

8. *The oracle's corpus is the NIST programs*, every 1985 verb; the 2002-and-later names (the OO group tier's `ClassNames.Lookup`,
