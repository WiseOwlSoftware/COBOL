# PB2848 — LANDED — four I/O-status findings around OPEN, WRITE and record counting

Found by the train 1047 lander's review (step 5b; `E:\COBOL-coord\scratch\reports\train1047-report.md`, finding (e)) on cluster 47B (PB2692, PB2748, PB2751), all PLAUSIBLE (traced in code, not run). The lander had no ids left; the land unit reserved this id and the resume unit of 2026-10-08 21:46 PDT filed it.

## The four findings (each needs its repro before its fix)
1. **Crash.** `CobolFile.ResolveHostPath` (`src/WiseOwl.Cobol.Runtime/IO/CobolFile.cs:375`) calls `Path.GetFullPath`,
   which throws on a malformed host path. Its callers (`FileConnector.cs:98/105`, `FileRegistry.cs:142/159`) run it
   outside OPEN's I/O-status catch, so a bad ASSIGN value is an unhandled .NET exception instead of an OPEN status.
2. **Wrong status.** A record-locking OUTPUT writer opens its host file ReadWrite; on a file the host grants
   write-only access to, OPEN OUTPUT answers 37 (permission) where a write-only open would succeed.
3. **Wrong status.** `SequentialConnector.CountRecords` (`SequentialConnector.cs:431`, called at `:252`, `:989`,
   `:1026`) runs after the flush and can answer 30 for a record that was in fact written.
4. **Order of conditions.** `FileRegistry.WriteSharedInStatement` (`FileRegistry.cs:1546`) checks the condition that
   gives 54 before the one that gives 44, the pre-existing sibling of PB2751's ordering fix.

The I-O status values (§9.1.13) and the OPEN, WRITE and REWRITE general rules decide which status each case owes;
derive each expected value from the text before writing a golden (none of the four values above is from the spec

## Landed (2026-10-10, wave 1051 group C, branch `worktree-wf_4151e8da-91b-3`)

Probes are `E:\COBOL-coord\scratch\w1051c\probes\p2848a.cob` and `p2848d.cob`, and the unit tests below, on the branch's own
build (base `471d0e954`). All four findings reproduce; the third only through the second (see it).

1. **GetFullPath outside OPEN's catch: reproduced, fixed.** `ASSIGN USING NM` with `NM PIC X(40000)` all `a`: `OPEN OUTPUT`
   died with an unhandled `PathTooLongException` out of `FileConnector.AssociationFailure`. `CobolFile.ResolveHostPath` is
   now total: a spelling the host cannot make absolute (too long, a NUL) is returned as written, and the OPEN reports what the
   host says (`35` for INPUT, `30` for OUTPUT; DOC-A.1-73 already promised "never an escaping exception"). Sweep: it is the
   only `GetFullPath` in the runtime's I/O; the four registration sites and both `AssociationFailure` arms share it.
2. **Record-locking OUTPUT writer opened ReadWrite answers `37` on a write-only file: reproduced, fixed.**
   `FileAuthorityPresenceTests.OpenOutput_RecordLockingWriterOnAWriteOnlyFile_IsSuccessful` answered `37` with the fix
   disabled and answers `00` with it. §14.9.27.4 GR3's `37` is insufficient authority to open the file for the mode, and OUTPUT
   creates the file; the read half of the handle is the lock announcement's preference (`HostAccess`), so `OpenWriter` falls back
   to the mode's write-only handle on `UnauthorizedAccessException` (OUTPUT only). EXTEND keeps `37`
   (`OpenExtend_RecordLockingWriterOnAWriteOnlyFile_Is37`): it numbers the records already in the file, which it cannot do
   without reading them. Consequence recorded in DESIGN-runtime-library: such a connector publishes no lock presence on Linux
   and numbers its records by the in-run-unit mint.
3. **`CountRecords` after the flush answers `30` for a written record: reachable only through finding 2, fixed there.** On a
   readable file the auxiliary read open cannot be refused (the writer's own handle holds read-write and its share mode admits
   it). On the write-only handle finding 2 now produces, the count's read open would have been refused with an
   `UnauthorizedAccessException` (not even an `IOException`, so it would have escaped `Write`'s catch) after the flush.
   `ReleaseRecord` therefore counts off the medium only when the handle was granted read (`_writerReads`). A host I/O failure
   while counting a readable file stays a permanent error `30` (§9.1.13.6 item 1); no fix is possible there, the record is
   already released.
4. **`WriteSharedInStatement` reports `54` before `44`: reproduced, fixed, and the REWRITE sibling with it.** Relative file,
   `LOCK ON MULTIPLE RECORDS`, 15 records locked, `WRITE` of a 5-byte record to a 10..20 file `WITH LOCK` answered `54`, and
   the same without `WITH LOCK` `44`. The ceiling (§12.4.5.9.4 GR7) belongs to the lock the statement requests, which is its
   effect on success (§14.9.51.4 GR11; §14.9.35.4 GR12), so DOC-A.1-104 (2) puts it after the statement's own rules, and it must
   still refuse before the file changes. New mechanism `FileConnector.CommitGate`: the registry sets it for a statement that
   requests a NEW lock and every organization's WRITE and REWRITE asks it once at its commit point
   (`RefusedAtCommit()`): `SequentialConnector.WriteRecord`, `WriteAdvancingRecord`, `RewriteRecordSequential`, `RewriteLine`,
   `RelativeConnector.Write`, `Replace`, `IndexedConnector.Write`, `Rewrite`. `RewriteSharedInStatement` had the same
   pre-flight and the same defect (its sibling arm). Determination in docs/CONFORMANCE.md DOC-A.1-104, -154, -155; design in
   DESIGN-runtime-library.
   `cite.py --check` OK: §12.4.5.9.4 GR7; §9.1.13.8 item 4; §14.9.51.4 GR11; §14.9.35.4 GR20, GR12.

- `src/WiseOwl.Cobol.Runtime/IO/CobolFile.cs#ResolveHostPath` (CobolFile.ResolveHostPath) — total; a spelling the host cannot make absolute is its own host path and the OPEN reports the host's refusal. Do not add a second `Path.GetFullPath`.
- `src/WiseOwl.Cobol.Runtime/IO/SequentialConnector.cs#OpenWriter` (SequentialConnector.OpenWriter) — OUTPUT falls back to the mode's write-only handle when the host refuses the lock announcement's read half; `_writerReads` then keeps `ReleaseRecord` from counting the medium. EXTEND stays `37` by design.

A new organization or arm calls `RefusedAtCommit()` after its own rules; `CommitGateDriftTests` is the matrix to extend.
