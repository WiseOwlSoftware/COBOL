# PB767 — OPEN — the documented checkpoint command returns 1, and there are two of it

Found 2026-09-06 in the PB735 implementer's report (NEW DEFECT A). **Re-measured here from scratch on
`9fad13e5`, and the report's harm claim does not hold — see the premise correction.** Filed separately from
[[PB735]] because PB735 is about *what a blind `git add` STAGES* and this is about *the command not running at
all*; the two share the same line of the same briefs, which is why PB735's implementer met it.

## Measured — git 2.55.0.windows.3, a scratch repository built for this note

`E:\Temp\claude\E--CobolSharp\49b17747-ce58-4386-8c49-ecb2ce644f8d\scratchpad\pb767repro` — a fresh `git init`
whose `.gitignore` holds `STATUS.md` and `.claude/settings.local.json`, both files present, one tracked file
committed, two untracked files added. Three runs, `git reset` between each:

```
A: git add -A -- .                                  exit=0   staged: a.txt b.txt out.txt
B: git add -A -- . ":!STATUS.md"                    exit=1   staged: a.txt b.txt out.txt
     The following paths are ignored by one of your .gitignore files:
     STATUS.md
     hint: Use -f if you really want to add them.
C: git add -A -- . ":!.claude/settings.local.json"  exit=1   staged: a.txt b.txt out.txt
     The following paths are ignored by one of your .gitignore files:
     .claude/settings.local.json
```

**A against B is the whole mechanism.** The identical ignored file is present in both runs; the bare directory
pathspec does not name it and git says nothing, while the EXCLUDE item `:!STATUS.md` makes git count the path as
explicitly named, report it as ignored, and return 1. The rule is not "STATUS.md" — it is **any pathspec item,
including a negative one, whose only match is an ignored path**, which run C shows on a second file.

## ⛔ Premise correction — the report says "exit 1, empty index" and that is not what happens

`feedback_validate_the_premise_not_only_the_rule`. The index is updated in every run above: `git add` prints the
ignored-path complaint, sets a non-zero exit status, and **stages everything else anyway**. So the failure is not
a lost stage; it is a **false failure signal on a command that succeeded**, and the harm follows from that:

- a step written `git add … && git commit …` never commits, while the working tree looks staged and correct;
- a step written with the two commands separated commits fine, so the same protocol behaves differently in two
  briefs for a reason nobody can see from the text;
- an agent that reads the exit code or the words *"Use -f if you really want to add them"* has been told its
  checkpoint was refused when it was not — and the checkpoint protocol exists precisely for the case where the
  agent is about to be killed and cannot investigate.

## The fix shape

1. **ONE documented form, written once.** `git add -A -- . ":!.claude/settings.local.json"` followed by
   `git reset -q -- STATUS.md` (which drops a stray *tracked* STATUS.md; `.gitignore` already handles the
   untracked one). Four copies of a command is four chances to have three of them wrong —
   `feedback_one_rule_one_place`. Put the checkpoint routine in ONE place under
   `.claude/skills/workstream/` and have the templates reference it.
2. **A brief lint, because prose is not executable.** A drift test in `Cobol.Net.Tests.Unit` that reads every
   `git add … ":!<path>"` out of `.claude/skills/**` and fails when `git check-ignore -q <path>` succeeds — a
   mechanical oracle (git's own ignore rules), no hand-kept list, and it keeps holding as `.gitignore` moves
   (CLAUDE.md rule 5). ⛔ Fire it once against a fixture that still writes `":!STATUS.md"` before trusting its
   silence (`feedback_green_gates_arent_evidence`); the child process goes through
   `ProcessObserver.ObserveOrThrow`, never a private launcher (see [[PB768]]).
