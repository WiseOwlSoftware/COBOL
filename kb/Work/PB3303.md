# PB3303 — BY REFERENCE FUNCTION F(X) / BY REFERENCE O :: "M" in CALL

Source: `E:/COBOL-coord/scratch/reports/w1097d-PB1551-report.md`, "New defects" item 2 (PB1551 round 2, PR #145). The report states both forms are parse errors at main and labels them SR-14.9.4.3-5 PARTIAL. Code site: `src/WiseOwl.Cobol.Frontend/Grammar/CobolParserCore.g4#callByReference`, which PB1551 changed to `addressIdentifier | predefinedNull | receivingIdentifier | OMITTED`.

## Repro (from the report; not re-run by the filing clerk)
`CALL "S" USING BY REFERENCE FUNCTION F(X)` and `CALL "S" USING BY REFERENCE O :: "M"` (inline method invocation), each COBOL0001.

## Status: suspected, adjudication owed
Harm flags are conservative: the report does not say either source is legal, so `rejects_legal_source` is false. Nobody has decided legality. Clauses to check:
- §14.9.4.3 SR3 (`cite.py --check 14.9.4.3` confirms SR3 and SR5 text): identifier-2 "shall reference an address-identifier or a data item defined in the file, working-storage, local-storage, or linkage section". A function-identifier or inline method invocation is not obviously such a data item, so the refusal may be correct and only the diagnostic (COBOL0001 vs a rule-named code) wrong.
- The CALL general format (Formats 1 and 2) for what identifier-2 may be.
- §8.4.3 for function-identifier and inline method invocation, and whether either is a receiving operand under SR5 (BY REFERENCE and not an address-identifier).

Outcome to record: either the forms are illegal (the fix is a rule-named diagnostic) or legal (rejects_legal_source flips true and the grammar admits them).

## Not the same as
PB258 holds SR-14.9.4.3-5 PARTIAL for the ADDRESS OF arm (fixed by PB1551); PB2145 is invokeArgument duplicating callByReference. No open note tracks function-identifier or inline method invocation BY REFERENCE in CALL.

## Closed (analyses sweep, 2026-10-23)

Adjudicated read-only by an Opus cobol-adjudicator on main e7cf38ce4; accepted by the Mythos session.

Closed 2026-10-23 (open-analyses sweep S4). The legality question is answered: CALL ... USING BY REFERENCE FUNCTION F(X) and BY REFERENCE O :: 'M' are illegal. §14.9.4.3 SR3 limits identifier-2 to an address-identifier or a data item of the file, working-storage, local-storage or linkage section, SR5 makes a BY REFERENCE identifier-2 that is not an address-identifier a receiving operand, and §8.4.3.2.3 SR1 and §8.4.3.4.3 SR1 forbid a function-identifier and an inline method invocation as a receiving operand. Main refuses both (COBOL0001 'unexpected FUNCTION'; COBOL0307 'unexpected ::'), so rejects_legal_source stays false and the four rows stay CONFORMS. The only residue is diagnostic wording: a receiving slot refuses these shapes by grammar fall-through, not with a rule-named code. MOVE 'a' TO FUNCTION UPPER-CASE(X) behaves the same way, and PB1547 already tracks this mechanism for ADDRESS OF in receiving slots. The clerk adds the two CALL shapes and the MOVE shape to PB1547's sibling sweep; this note opens nothing new.

Evidence: Both forms are nonconforming: §14.9.4.3 SR3 requires identifier-2 to reference an address-identifier or a data item defined in the file/working-storage/local-storage/linkage section, SR5 makes a BY REFERENCE identifier-2 a receiving operand, and §8.4.3.2.3 SR1 / §8.4.3.4.3 SR1 forbid a function-identifier / inline method invocation as a receiving operand. Probes probes/pb3303/a3303.cob, b3303.cob on e7cf38ce4: refused (COBOL0001 / COBOL0307). Inventory rows SR-14.9.4.3-3, SR-14.9.4.3-5, SR-8.4.3.2.3-1, SR-8.4.3.4.3-1 are CONFORMS.
