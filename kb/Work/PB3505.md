# PB3505 — DISPLAY of a numeric item follows GnuCOBOL's default form (owner decision PB3467)

## The rule and the decision

ISO §14.9.11.4 GR1: "Any conversion of data required between literal-1 or the data item referenced by identifier-1
and the device is defined by the implementor." Annex A.1 item 56 requires it documented (`docs/CONFORMANCE.md`
DOC-A.1-56). The owner decided (kb/Work PB3467): the DEFAULT conversion of a numeric operand is GnuCOBOL 3.2.0's
default-configuration form; today's digit image (the digits as stored, an unseparated sign overpunched per
`--sign-encoding`) stays available behind a compile option.

## What changes (observed today versus the decided default)

| Item | Value | Today | Decided default (GnuCOBOL 3.2.0 `default`) |
|---|---|---|---|
| `PIC 9(5)V99` | 12.5 | `0001250` | `00012.50` |
| `PIC S9(5)V99` | +12.5 | `000125{` | `+00012.50` |
| `PIC S9(5)V99` | −12.5 | `000125}` | `-00012.50` |
| `PIC S9(3)V99 SIGN LEADING SEPARATE` | −1.5 | (measure) | `-001.50` |
| `PIC 9(3)V99 COMP` | 1.5 | (measure) | `001.50` |
| `PIC 9(3)PP` | 1200 | (measure) | `01200` |

## The implementer's bar

1. **Survey first, the whole category, by running GnuCOBOL** (`cobc -x -std=default` in WSL, reference memory
   cobc-in-wsl; observe behavior, never read its sources), and write the table into DOC-A.1-56 before coding: every
   numeric USAGE (DISPLAY, NATIONAL, BINARY, COMP, COMP-3/PACKED-DECIMAL, COMP-5, BINARY-CHAR/SHORT/LONG/DOUBLE signed
   and unsigned, the floats — which may already match), every SIGN form (none, LEADING, TRAILING, each SEPARATE),
   signed and unsigned integers (does `S9(3)` +5 print `+005`?), leading and trailing P scaling, zero and negative
   zero, `DECIMAL-POINT IS COMMA` (the separator the program declares), a numeric item inside a multi-operand
   DISPLAY (GR6's size is the sum of the converted sizes), DISPLAY ... UPON a mnemonic, and a numeric-EDITED item
   (alphanumeric-class: expected unchanged). Anything GnuCOBOL does that the precedence does not reach (a non-ISO
   extension) is recorded, not copied.
2. **One conversion, one place.** The DISPLAY conversion of a numeric operand is a single runtime/emitter mechanism
   selected by the option (compile-time, like `--sign-encoding`: baked into the emitted program), never a second
   formatter beside the existing one. The existing DOC-A.1-56 forms (a signed non-DISPLAY item's leading `-`, the
   numeric literal as written, PB1643) are re-derived against the survey: if GnuCOBOL's default prints `+` for a
   positive signed binary, that row changes too, under the same decision.
3. **The option.** Name and spell it to the CLI's conventions (`--help`, the option table in the docs, the edition
   matrix if any), document both values in DOC-A.1-56, and default to the GnuCOBOL form at every `--std`.
4. **Goldens.** Every golden whose expected output displays an affected item changes; each new expected value is
   computed from the surveyed rule, not pasted from the new output (spec-oracle). New goldens cover both option values
   across the survey's rows. The NIST/CCVS goldens are fixed by their own expected reports: check what the CCVS
   programs DISPLAY of numeric items before assuming their goldens move.
5. **The differential fuzz harness.** PB3490 folded this latitude out of the survivors (`scripts/differential_fuzz.py`,
   the display-form fold); with the default now matching GnuCOBOL's, revisit the fold (it encoded the old difference)
   and say in the report what it does now.
6. Sweep (rule 4): every other place a numeric item becomes text for a device by implementor conversion — the
   DISPLAY of a figurative or a function result, and anything else DOC-A.1-56's register lists — measured, not
   assumed.

## Code sites (where the conversion lives today)

- `src/Cobol.Net.Compiler/CodeGen/Verbs/AcceptDisplayEmitter.cs#EmitDisplay` — renders each DISPLAY operand.
- `src/Cobol.Net.Compiler/CodeGen/Emit/OperandText.cs#AsTransferString` — the operand's transfer text; a numeric
  field's image reaches the runtime through `CobolNum.FormatDisplay`. ⛔ `OperandText` also serves MOVE and the other
  alphanumeric uses of a numeric item, whose results §14.9.25 fixes; the new form is DISPLAY's GR1 conversion ONLY.
- `src/Cobol.Net.Runtime/Values/Numeric/CobolNum.cs#FormatDisplay` / `FormatDisplaySigned` / `FormatDisplayU` — the
  digit image with the `--sign-encoding` overpunch (DOC-A.1-177), today's DISPLAY output.

## Harm today

Every program that DISPLAYs a scaled or signed numeric item prints a form a COBOL programmer reads wrong (`0001250` for
12.50, `000125{` for +12.50), and 615 of the first overnight fuzz run's 1,141 output differences were this one form.

## Landed (wave 1146, 2026-10-22)

**The mechanism.** DISPLAY's GR1 device conversion of a fixed-point numeric item is now a compile option,
`--numeric-display decimal|digits` (`NumericDisplayForm`, default `decimal` at every `--std`): `CompilerDriver.Options`
→ `EditionContext` → `EmitContext.NumericDisplay`, read by `AcceptDisplayEmitter` alone, which asks the new
`OperandText.AsDeviceString`. The decimal form is ONE runtime composition, `CobolNum.DisplayDecimal` / `DisplayDecimalU`
(`CobolNum.DeviceDecimal.cs`), fed by a native carrier or by an item's character image, so a REDEFINES view and its
native twin print alike. `digits` is today's `FormatDisplay` image, byte-identical to before (re-probed against the
pre-change output of the survey program). MOVE's character image, comparisons and record images were not touched.

**Survey (the bar's item 1).** GnuCOBOL 3.2.0 `cobc -x -std=default` was run over every usage, sign form, P scaling, comma
mode, group, literal, edited, float, function and index operand; the table and the divergences are in
`docs/CONFORMANCE.md` item 56. Findings the note did not predict: `SIGN TRAILING SEPARATE` shows its sign TRAILING in
GnuCOBOL (`001.50-`), which the form copies; COMP-5 / BINARY-* items show their CONTAINER's digits (3, 5, 10, 20), so a
COMP-5 value beyond its PICTURE shows whole — GnuCOBOL 3.2.0 prints `18446744073709551615` for `PIC 9(18) COMP-5` where
kb/Work R13 recorded the cut `446744073709551615` as GnuCOBOL's; the cut is kept as the `digits` form's and R13's golden
became `pb3505_display_comp5_beyond_picture_digits`; a SCALED COMP-5 prints its unscaled integer in GnuCOBOL (the scale is
lost), which is NOT copied. Function results (DOC-A.1-92) and floats keep their own forms.

**Sweep.** The other arms of the dispatch: the four numeric arms of `OperandText.FieldAsString` (native, unsigned-wide,
character-image view, StoreAsImage) and `NonTextBytes` take the form through one `NumericText` / `ImageText`; the
literal, figurative, group, edited, float and function arms are unchanged by design. No other emitter writes a numeric
item to a device (`Console.Write` appears only in `AcceptDisplayEmitter`, and one literal-text line in `StatementEmitter`).
Two inherited citations were wrong in the code and are corrected: `§13.18.40.3 symbol-P operations item b` is
`§13.18.40.4 GR14` (symbol P).

**Goldens.** 200 suite `.out` files (cases and wiseowl) and 45 differential `.out` files changed to the decimal form; each
new value was checked against its old value under an independent digit-signature fold (same digits, same sign count), and
the 29 files that differ in WIDTH (container digits, P zeros, a COMP-5 value past its PICTURE) were read by hand against the
rule. Five new wiseowl tests pin both option values, the comma mode and the container widths; 77 inline expectations in
the Conformance project and one Unit test were re-derived from the pictures. The differential fuzz harness no longer folds
the display form in a run made now (`numeric_display` is recorded per row; a row recorded without it is a digit-image row
and keeps its fold when re-read).
