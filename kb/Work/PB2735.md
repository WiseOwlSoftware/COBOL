**Rule it breaks:** One mechanism per job (DESIGN-architecture-review.md §5.2; dimensions.md item 4, 'two mechanisms for one job'). FragmentParse's own remarks state the rule and the defect class: the fragment copies of these steps disagreed, and both disagreements were defects (PB50 run-time abort, PB54 silent wrong answer).

**Scenario:** FragmentParse calls itself 'THE ONE FRAGMENT RE-PARSE' because three copies of 'lex the text, prime the lexer, normalize the token stream, parse at an edition, null on error' had drifted. The main parse is still a separate copy of the same sequence: Frontend.LexAndParseOnce (Frontend.cs:450-508) builds the CobolLexer, calls retypes.PrimeLexer, runs DebuggingLineRewriter, ZeroTokenRewriter and retypes.Rewrite in that order, then builds CobolParserCore with Edition and CobolWords. FragmentParse.Parse (FragmentParse.cs:57-77) repeats the order with two variations (HideAll for Rewrite, rewriteZero optional) and one difference nothing explains: it puts its error flag on the LEXER as well as the parser, while the main parse leaves ANTLR's default console listener on its lexer. The ordering is load-bearing (DebuggingLineRewriter 'must run before every other rewriter'), and it is stated in two places. The next post-lex stage, such as the arithmetic-operator spacing check PB2017 plans, must be added to both, and a fragment that misses it reads the same text differently from the tree it came from, the PB50/PB54 shape again. CobolKeywordTokens.LexProbe (CobolKeywordTokens.cs:96-123) builds a third lexer with no PrimeLexer at all (no Annex C spelling edition, no COBOL-WORDS plan) and a third error listener, CountingErrorListener (:125-130). FragmentParse.SyntaxErrorFlag's comment says it is 'the one copy'.

**Target:** One token-stream builder in Frontend/Parsing, for example CobolTokenStream.Prepare(text, edition, retypes, prime, DebugLines.Resolve | DebugLines.HideAll, rewriteZero), returning the filled, rewritten stream and a parser factory. Frontend.LexAndParseOnce and FragmentParse.Parse both call it. The step order is written once and the lexer-error policy is decided once. LexProbe uses the same builder (unprimed by an explicit TokenRetypes.None at the edition's spelling) and SyntaxErrorFlag; CountingErrorListener is deleted. This amends §8.4, which names the fragment parser and the pipeline's parse-again loop as separate edition-read sites but does not make them one mechanism.
