# PB2707 — R2 relaunch state and quota sizing

Found 2026-10-08 by the operator relaunching R2 batch 2 (pin 8be230068). Owner, 2026-10-08 ~11:40 PDT: "This seems like
poor planning and something we should consider for future runs."

## What happened (measured)

- Batch 2 (13 shards × 5 dimensions = 65 pairs, width 8) was launched at 08:30 on the owner's decision. Nothing estimated
  its cost first. By 10:02 the account's session meter read 90 % (the window resets at 11:10), so the operator stopped the
  batch with `STOP-r2` to keep work from dying at 100 %. The finders had finished 52 of 65 pairs, and the skeptics
  (three lens skeptics per finding, the stage that decides anything) had not started.
- The designed relaunch is `python scripts/arch/r2_collect.py --out <batch> --launch`, then the Workflow with the
  `launch-args.json` it writes. `wf_r2_review.js` refuses to start without `args.state`, and a workflow script cannot read
  a file, so the operator must pass the state inline. For batch 2 that file was **95,644 bytes on one line**
  (batch 1's first launch: 8,090 bytes, empty state). The bulk is every pair's full `read` list, which repeats the
  shard's file list in every complete pair. The Read tool truncates the one line at about 37 KB, and the Bash output
  limit is about 30 KB.
- The operator split the state by shard group (six launches of 2–3 shards, width 3, 2.6–20.8 KB each,
  `scratchpad\split_r2_args.py`) and transcribed each one into a Workflow call. That took roughly 80 KB of model output
  plus as much context, and every path in it was a transcription risk.

## Fix (rule 5: make the next relaunch automatic)

1. **No state transcription.** The workflow must rebuild its launch plan from disk itself. For example, the script's
   first agent runs `r2_collect.py --out <batch> --plan` and returns a COMPACT plan as structured output. Alternatively,
   `--launch` writes only what is undecided per pair: the files no finder has read (empty for most pairs) and, per lens,
   the finding ids still undecided. A complete pair then costs a few bytes instead of its full read list. Either way the
   operator passes only the batch arguments, and a relaunch is one small call whatever its progress. Keep the invariant
   that a launch never plans from agent returns (the reason the state exists).
2. **Size the batch before launching it.** `r2_inputs.py --batch` (or `--launch`) prints an estimated cost from the
   measured tokens per pair of earlier batches. Batch 1 was 31.2 M subagent tokens for 36 pairs; batch 2's finder phase
   was 18.2 M for 52 pairs. The tool refuses, or splits into sub-batches, a batch that cannot finish inside the current
   session window and the remaining weekly allowance (`budget.py`, with the `model_rules.json` caps). A batch that stops
   halfway pays its finders and decides nothing.
3. A self-test for both: a relaunch with N decided pairs passes O(undecided) bytes; an over-budget batch is refused with
   the estimate shown.

## Landed (w1051y, 2026-10-10)

**No state transcription.** `r2_collect.py --out <batch dir> --launch` builds the PLAN from disk (`plan` / `plan_of`):
one entry per pair with work left, holding only the files no finder read (with their lines), the finder number
reached, the count of findings on disk and, per lens, the findings no skeptic decided; a decided pair is not in it. It
writes `<batch dir>\launch.js`, the template `wf_r2_review.js` with its one plan line (`const A = args`) replaced by
the plan, and the operator's whole call is `Workflow({scriptPath: "<batch dir>\\launch.js"})` with no args. The
template run directly refuses to start (it has no plan), `launch-args.json` is gone, and the workflow tells this
launch's new findings from the plan's by finder number, so it still never plans from agent returns. Self-tests: a
plan with 40 decided pairs is the size of one with 1 (`r2_collect.py`), and the dry run `test_wf_r2_review.mjs` now
runs, for every scenario, the real `r2_collect.py --launch` and the launch.js it writes (1 vs 12 decided pairs: the
same bytes, no agent for them).

**Sizing.** `scripts/arch/r2_cost.py` prices a plan at rates pooled from `model_rules.json` `cost.r2.batches`, each
record measured by `r2_cost.py --measure <batch dir> <Workflow subagent dirs>` from the agent transcripts (the kinds
`budget.py` counts): batch 1 29.4 M tokens (finders 13.2 M, skeptics 15.0 M, clone pass 1.2 M; 36 pairs) and batch 2
52.5 M (finders 22.6 M, skeptics 29.9 M; 65 pairs over seven runs). Pooled: 90.3 tokens per shard line per
dimension, 29,330 per lens verdict, 0.00128 findings per line; about 0.8 M tokens a pair. The room is `budget.py`'s
(`budget.current()`, now shared with its CLI): the session's soft stop less the spent and `--session-reserve`, the
week's headroom with `--borrow-days`. `r2_inputs.py --batch` refuses a batch that cannot finish and prints the
batches to write instead (`<label>a`, `<label>b`, ... one command each: the room left now, then one fresh window
each, then after the weekly reset); `r2_collect.py --launch` re-sizes at launch time and refuses with its
`--launch --shards` parts, removing any stale launch.js. Each new arm was seen red once (a plan that kept decided
pairs and a launch that wrote regardless of fit: three FAILs) before it passed.

**Batch 3 at the meter of 2026-10-10 ~12:00 PDT** (account 2, session ≈ 10.5 %, week ≈ 3.1 %, `--borrow-days 6`):
the 275 pairs left (55 shards, 304k lines) are ≈ 309 M tokens = 193 weekly points: two weeks of the whole quota, in
about ten session windows. Only 8 of the 55 shards have their inputs written (the `tests-scripts-ci` ones); the other
47 wait for `r2_inputs.py --pin ... --projects` to measure the Compiler and test projects' analyzers. Those 8 sized as
batch 3: 40 pairs ≈ 46.8 M tokens = 117 session points, refused, split into 3a (5 shards, 72.1 session points, now)
and 3b (3 shards, 45.0, the next window).
