# PB5857 - the RELATIVE KEY agreement of an external file connector identifies the key item by its name path (every edition)

**Ruling: UPHELD (b), harm under_rejects.** The row `1985-GR-VIII.2.4.4-8` does not close on its inherited verdict. Two programs that describe one external relative file may name RELATIVE KEY items of the same name at DIFFERENT character positions of the external record, and the compiler accepts it: it identifies the item by its name path alone. The checker's confidence: medium (the checker's own ruling was OPEN-READING, leaning to reading 1; the Mythos lane decided it, below). Cause (b): the same at `--std 2023`. Severity MINOR: harm under_rejects only.

**Mechanism 2, decided: the same external data item is the same storage.** `§1985:VIII.2.4.4 GR8` says "the RELATIVE KEY phrase in each associated file control entry must reference that same external data item in each case" (cite.py OK). The checker found the text open between an item identified by its place in the external record and an item identified by its name, and leaned to the first. I decide the first. An external data item is storage the programs of a run unit share; two descriptions that put the key at different character positions describe two different items of the record whatever they are called, and two programs that share one file connector and take the relative record number from different bytes is the fault the rule exists to exclude. The compiler's agreement check for RECORD KEY on an external indexed file already identifies the item by its position; the RELATIVE KEY check uses the same identity (one mechanism, CLAUDE.md rule 4), and a mismatch is refused as the access-mode mismatch is. The 2023 text reaches the same result in its own words (`§2023:14.8.4.2`: the relative key data items "shall refer to the same corresponding storage"; the checker ran that citation, cite.py OK), so the 2023 row is contradicted too.

**What the decision chose between (the checker's two readings, copied), with the evidence for each.**
- **Reading 1, character positions.** An external data item is one "described as part of an external record in one or more programs" (`§1985:III`, the glossary), and `§1985:X.4.5.4 GR2` requires only the same record-name and size, so a same-named subordinate at another position is another part of the record; GR6 makes the key the item that communicates the relative record number to the one shared connector, which only shared storage does. Under it the program breaks GR8 and the compile-time check (which kb/Work PB5069 landed as the 85 refusal of GR8) under-rejects. Pointer, not authority: `§2023:14.8.4.2` states reading 1, and the compiler's own RECORD KEY identity (`FileEntryIdentity.KeyEntry`) already carries the offset. The checker leaned to this reading (medium).
- **Reading 2, name path.** The text never says how an item in one program is the same as one in another, and `ExternalItemIdentity` (record name plus subordinate names) is a consistent rule.

**The point that makes a refusal required.** The checker says a violation is undefined by the text: `§1985:I.1.6` makes the result of a run unit that breaks a rule undefined, not detected ("The results of violating the formats or rules of Standard COBOL are undefined unless otherwise specified in this standard"). Only the project's kb/Work PB5069 determination makes a refusal required: keep that sentence. The fix is settled by that recorded decision on the identity GR8's sameness test uses at 85; the position identity is carried by `ExternalItemIdentity` as `KeyEntry` carries it, at every edition.

**The checker's runs** (`extrk.cob`: `EXT-KEYS IS EXTERNAL` with `REL-KEY` at positions 1 to 4 in the first program and 5 to 8 in the second, both naming `RELATIVE KEY IS REL-KEY` for one EXTERNAL relative file): accepted at 85 and 2023, exit 0, printing `B[SECOND-REC] KEYS[00030002]` (at 2023 also the COBOL0903 obsolete EXIT PROGRAM warning). B reads record 2 while A's key area holds 3.
