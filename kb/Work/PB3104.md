# PB3104 — the Linux gate row of `enqueue.py land` runs outside the gate slot

> ⚙ **flags:** process-only

Related, not edited here: PB3022 item 10 (the targeted leg on both hosts under the same slot) is the planned fix;
PB2877 is related history. Neither records this defect.

**Code site.** `scripts/orchestrator/enqueue.py`, `GATES_WINDOWS` (line ~115) and `run_gates` (line ~279). The Windows row
`build-local.ps1` takes a slot through `run_gate_legs.py` and releases it on exit. The Linux row runs
`bash scripts/linux-gate.sh --nice` directly, and `linux-gate.sh` takes no slot. The module docstring step 3 ("THE GATE on
the merged head, every host in GATES, each under the shared gate slot … so concurrent enqueues queue there and never
beyond it") and `scripts/orchestrator/units/enqueue.md` step 3 ("Start them all at once: each gate takes the shared gate
slot, so at most the cap gate together") state the opposite of what runs.

**Measured 2026-10-12 ~13:55-15:00 PDT.** The enqueue unit started 7 `enqueue.py land` runs at once (wave 1069's
Review-CLEAN branches). All 7 Windows gates were GREEN. Then `gate_slot.py status` showed 0 slots held and 0 waiting while
7 `linux-gate.sh --nice` processes ran together. The Linux "ONE build of Cobol.Net.sln" times were 49 s, 212, 225, 490,
653, 699 and 788 s. The unit leg took 27-38 min.

**Result.** 6 of 7 Linux gates went RED. Four were load alone (HARNESS NON-OBSERVATION: prog.dll killed after 120 s twice,
`COBOLNET_RUN_TIMEOUT_MS`):
- `RelationPairShapeTests.StrongGroupWithAThousandLeaves_CompilesAndComparesInOrder` took 8 m 14 s, 8 m 2 s and 16 m 56 s
  in the run, against 6.96 s in the shared timings store (`.git/cobol-gate-timings/timings.json`), on
  worktree-wf_d63f7207-db5-4, -11 and -23.
- `ActivationResourcesTests.RecursiveFunction_PastTheStack_IsEcProgramResources` took 4 m 37 s and 4 m 32 s, against
  3.77 s in the store, on worktree-wf_d63f7207-db5-17 and -30.
- The same two tests passed on db5-18's Linux gate in the same window.
- Logs: `<worktree>\TestResults\enqueue\linux-gate.log` and `TestResults\linux-gate\conformance.log` in each of those
  worktrees; the enqueue logs `E:\COBOL-coord\scratch\enqueue-db5-*.log`.

**Blocked by it** (Review CLEAN, both reds load-only, no finisher dispatched): worktree-wf_d63f7207-db5-4 (PB3031), -11
(PB2842), -17 (PB2502), -30 (PB2720).

**Fix shape (for the implementer to confirm).**
1. The Linux row runs under the gate slot (`gate_slot.py run --label … -- bash scripts/linux-gate.sh --nice`), or the
   Windows and Linux rows are held under ONE slot acquisition, or PB3022 item 10 moves the Linux leg inside build-local's
   slot.
2. A drift test that every row of `GATES_WINDOWS`/`GATES_LINUX` runs under the slot, so a new host row cannot escape the
   cap.
3. Correct the module docstring and `units/enqueue.md` step 3.

**Separately worth recording (not decided here).** The harness's fixed 120 s run budget is a wall-clock bound under load
(owner rule: a timing failure is a failure; PB3022 forbids fixed time limits in tests).

## Landed (wave 1069 group M)

**Re-probe.** Before the fix, on the branch: the Linux row of `GATES_WINDOWS` was the bare `bash scripts/linux-gate.sh
--nice`, which takes no gate slot, and `linux-gate.sh` acquires none (its one `gate_slot` mention is a comment).

**Fix shape (items 1-3).** In `scripts/orchestrator/enqueue.py` each gate row is now a
`GateRow(host, command, prefix, slot)`, where `slot` is one of two values:
- `own`: the command takes the slot itself. build-local hands the gate to `scripts/run_gate_legs.py`, which acquires it.
- `wrap`: `run_gates` starts the command under `gate_slot.py run --repo <worktree> --label "enqueue <branch>: <host>
  gate" -- …` (`gate_argv`).

The Linux row of `GATES_WINDOWS` is `wrap`. `unslotted(rows, tree)` holds the one slot rule. It refuses:
- a bare row;
- an unknown slot value;
- an `own` claim whose script does not hand the gate to the driver;
- a driver that no longer acquires a slot.

`run_gates` runs NO row while any row is refused. It still sets PB3103's `COBOL_GATE_CLASS=landing` for every row, so
the wrapped Linux row queues as a landing ticket. A live probe, `gate_slot.py run -- bash -c 'uname -s'` on the Windows
host, took a slot and ran the command in WSL (`Linux`) inside the slot's Job object.

**One slot per row, not one held across both.** build-local takes its slot inside `run_gate_legs.py`, after its
audits (PB2524). An outer slot held around it would make that a second slot of the same cap: three concurrent
landings, each holding an outer slot at cap 3, would wait on their inner slots forever. Holding one slot across both
rows would need `run_gate_legs.py` to accept a slot it inherits, a new mechanism outside this note.

**Drift test.** `enqueue.py --self-test` gains three arms:
1. the wrapped row runs under `gate_slot.py run` with the landing class, and its slot is taken before its command
   starts;
2. every row of `GATES_WINDOWS` and `GATES_LINUX` takes the slot;
3. planted unslotted rows are refused, and `run_gates` runs none of the rows.

`LandingPipelineDriftTests` holds these arms by name, and PB3103's landing-class arm with them. With the bare pre-fix
Linux row planted back, arms 1 and 2 went red (`FAIL (2 failure(s))`).

**Docs.** The module docstring step 3, DESIGN-test-build-ci.md §3.17.2 step 3 and the caller list in `gate_slot.py` now
describe the slotted rows. `units/enqueue.md` step 3 was already accurate once the fix landed, so it is unchanged.
