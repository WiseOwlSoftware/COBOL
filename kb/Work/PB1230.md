# PB1230 — LANDED 2026-09-27

## Measured

**constant-entry** — F-SR9-VALUE-NOT-SPEC — the duplicate-constant check compares the folded value, not the written specification

- **Repro:** 01 K CONSTANT AS 5. 01 K CONSTANT AS 2 + 3.  (also: 01 W PIC X(7). 01 K CONSTANT AS LENGTH OF W. 01 K CONSTANT AS 7.)
- **Expected (spec):** Rejected: SR9 requires 'the specification of arithmetic-expression-1, literal-1, data-name-1, data-name-2, or compilation-variable-name-1 shall be the same as specified in the other constant-name' — a literal vs an expression, or LENGTH OF W vs a literal, are different specifications.
- **Observed:** Both compile; DISPLAY K prints 5 / 7. BindConstantEntry: `if (prior.Category != def.Category || prior.Text != def.Text)` — Text is the evaluated value. (5 vs 05 is rejected only because the texts differ.)
- **Code site:** src/Cobol.Net.Compiler/Binding/DataBinder.Constants.cs#BindConstantEntry
- **Clause (adjudicator):** §13.10.3 SR9

**SR-13.10.3-1** (PARTIAL, refuter-corrected where marked) — SR1 (cite OK). AS 0.25 -> 0.25 (golden FRAC=0.25, FCOMP=200); AS -2.5 (sign adjacent, one literal per §8.3.3.3.2) -> -2.5; AS - 2.5 (separated sign = unary operator, an expression) -> -2; AS (0.5) -> 0; AS 1.5E2 (floating literal, single) accepted as literal = 150 while 1.5E2 + 1 is rejected by §7.3.6.2 SR1b. || REFUTED: PARTIAL — The classification half is right: a single numeric literal is not truncated (0.25, -2.5 and 1.5E2 are kept; '- 2.5' and '(0.5)' are expressions). But what the constant carries forward is not literal-1 as written. EvaluateArithmeticOperand returns the NORMALIZED text: the '+' is stripped and a comma decimal separator becomes '.'. BindConstantArithmetic stores that text as the substitution. Under DECIMAL-POINT IS COMMA the stored '1.5' is re-checked as a literal at the reference point and rejected, so a LEGAL program fails to compile. With AS +5 the constant displays '5' while the literal +5 written directly displays '+5', so the constant is not treated 'as if literal-1 were written' (§13.10.4 GR1). The defect is in the SR1 single-literal path the adjudicator cites, and it surfaces through GR1. File it as a defect.

- **Code site:** src/Cobol.Net.Frontend/Expressions/SoleOperand.cs#NumericLiteral; src/Cobol.Net.Frontend/Expressions/CompileTimeExpressionEvaluator.cs#EvaluateArithmeticOperand

## Landed — 2026-09-27, wave-65 implementer F

**Re-probed on the worktree build first (all three reproduced):** `AS +5` → DISPLAY `5` (literal `+5` → `+5`); `AS 1,5`
under DECIMAL-POINT IS COMMA → COBOLNET0895 on `'1.5'` at DISPLAY and MOVE; `AS 5` + `AS 2 + 3`, and `AS LENGTH OF W` +
`AS 7`, both compiled.

**Root:** ONE normalization too many. `CompileTimeExpressionEvaluator.EvaluateArithmeticOperand` returned the
single literal's NORMALIZED text (`SoleNumericLiteral` dropped the `+`; `NumericLiteral.Normalize` rewrote `,` to `.`)
as "the substitution form consumers store", and `ConstantDef.Text` was compared by value for SR9.

**Fix shape:**
- `CtNumber` now carries `Literal` — a single literal EXACTLY AS WRITTEN, or an expression's GR3 integer literal — and
  `IsInteger`; `Text` is gone (renamed so every consumer was revisited at compile time). The evaluator no longer strips `+`.
- `ConstantDef` keeps literal-1 as written in `Text`/`RawText`; `IntegerText` (canonical integer, or null) replaces the
  `IsInteger` bool and is what the three integer positions read (OCCURS bound, PICTURE repetition, subscript C# read).
  `ResolveConstantName` derives the value from the written literal through the ONE `NumericLiteral.Normalize` + `CtNumeric.TryParseLiteral`.
- The procedure consumers already took `k.Text` through `CheckLiteral` (the literal chokepoint) — unchanged, now correct.
  **Sibling arm fixed:** the VALUE-clause arm (`RawValueOperandText`) returned the constant's raw text UN-normalized;
  it now takes it through `NormalizeIfNumericLiteral` exactly as a written literal (`VALUE K`, `K AS 1,5`, comma mode:
  was COBOLNET0895 before, a CS1001 backend crash with only the first half of the fix).
- SR9 compares `ConstantDef.Specification` (the AS operand's written text) through the ONE text-word equality,
  `TextWordSequence.Matches` over `TextWord.MatchesForReplacing` (§7.2.3.4 9) c)) — `CopyProcessor.MatchWords` moved to
  `TextWordScanner.MatchWords` so COPY REPLACING, REPLACE and SR9 share it. ⚠ DETERMINATION: "the same specification" is
  text-word equality — `5`, `05`, `+5` are three specifications; spacing and COBOL-word case are not compared.

**Goldens:** `2002/pb1230_constant_literal_as_written` (comma mode; `+5`, `1,5`, VALUE, COMPUTE, relation, PIC X(KI),
OCCURS KI, subscript, SR9 duplicate differing in spacing/case — 2002/2014/2023 identical) · `negative/pb1230-constant-dup-same-value`
(COBOLNET1547, reject-at 2002 2014 2023). Unit: `TextWordSequenceTests`, `CompileTimeExpressionEvaluatorTests` (`+5`, `IsInteger`).
