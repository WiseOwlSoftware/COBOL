# PB346 - a zero timeout that retried anyway, and the description of it that outlived the fix

**Landed.** Row `GR-14.9.30.4-9` flipped PARTIAL/GAP -> CONFORMS. Design: `docs/COBOLNET_FILES_DESIGN.md` **D8**
(already correct - it was the only place that was).

## What this note originally reported, and what was true on the tree

The report was: `FileRegistry.RetryLoop` covered `Seconds` and `Forever` in ONE default arm that ignored the
evaluated amount and returned `FileStatusCode.Deadlock` unconditionally, so `READ FB RETRY FOR ZERO-SECS SECONDS`
answered '52' where 14.7.9.3 GR4 a) requires the record operation conflict '51'.

**That arm was already split when this note was worked.** `0b1c39bc` (PB142 cluster E) gave `Seconds` its own
no-further-attempt arm on the GR2 clamp and scoped the deadlock to `Forever` on a RECORD conflict. Re-running the
note's own repro on a freshly built `cobol.exe` gives `B-RETRY-0-SECONDS FSB=51`, `B-RETRY-NEG-SECONDS FSB=51`,
`B-RETRY-30-SECONDS FSB=51`, `B-RETRY-FOREVER FSB=52` - every value the spec derives.

## What was still wrong, and is what PB346 actually landed

**1. The fix did not travel.** Five places went on describing the PRE-fix behaviour, and one of them is a
GENERATED registry's source: `StatementBinder.BindRetry`, `FileLockBinder.BindVerbRetry`, `BoundTree.RetryKind`,
`BoundKeyedIo.Retry` and `FileRegistry.ConflictOnLockedRecord` each restated "SECONDS/FOREVER deadlock-bail to 52",
`constructs.json`'s `retry-phrase-2002` row said it in both its description and its citation (and so did the
`ConstructRegistry.g.cs` rendered from it), and `docs/PHASE4_RECONCILIATION.md` said it in three places including
a stale expected-output list for `2023/delete_file_sharing`. The structural repair is not better wording: each of
those five sites now POINTS at `FileRegistry.RetryLoop` instead of restating its outcome, so the next change to
the retry rules cannot leave a description behind it.

**2. `14.9.30.4` GR9 had no test at all on its own subject.** GR9's second and third sentences are delegations -
*"If the RETRY phrase is specified, additional attempts may be made to read the record as specified in the rules
in 14.7.9, RETRY phrase"* and *"The I-O status is set in accordance with the rules for the RETRY phrase"* - and
every RETRY test in the tree reached `RetryLoop` through DELETE FILE, REWRITE or DELETE RECORD. **No test passed a
RETRY phrase to a READ**, on either format, so a read path could have dropped or mis-plumbed its retry arguments
and stayed green. That is why the row sat at PARTIAL with an empty `test-ref` after the code was already right.

## The rule

`--check 14.9.30.4 "The I-O status is set in accordance with the rules for the RETRY phrase"` -> OK 14.9.30.4 9).
`--check 14.9.30.4 "If the RETRY phrase is not specified or the record is not successfully accessed as specified
by the RETRY phrase, the record operation conflict condition exists"` -> OK 14.9.30.4 9).
`--check 14.7.9.3 "the result of the evaluation of arithmetic-expression-1 or arithmetic-expression-2 is negative
or zero, the statement is unsuccessful"` -> OK 14.7.9.3 4) a).
`--check 14.7.9.3 "The implementor shall specify the maximum meaningful value of arithmetic-expression-2"` -> OK
14.7.9.3 2).
`--check 14.7.9.3 "attempt to gain access to a locked resource until the input-output operation has been
completed"` -> OK 14.7.9.3 3).
`--check 9.1.13.8 "an attempt to access a record that is currently locked by another file connector"` -> OK
9.1.13.8 1). `--check 9.1.13.8 "The implementor shall specify under what conditions a deadlock is detected"` -> OK
9.1.13.8 2).

Four forms, three grounds, one landing. GR4 a) (no phrase, or a negative-or-zero arithmetic expression), GR1 (an
exhausted TIMES count) and GR2 (a SECONDS period clamped to this implementation's maximum meaningful value of
ZERO, Annex A.1 item 166) all reach the clause's closing paragraph and therefore 9.1.13.8 item 1's '51'. GR3's
FOREVER alone reaches '52': the holder is a connector of the EXECUTING run unit and can never release while this
statement runs, so *"until the input-output operation has been completed"* would not terminate, which is the
deadlock 9.1.13.8 item 2 leaves the implementor to detect. **Note that GR4 a) does not apply to FOREVER at all** -
FOREVER carries no arithmetic expression - so "zero SECONDS bails to the deadlock" was wrong on two counts, not
one.

## Sweep

`grep -n "RetryLoop(" src/Cobol.Net.Runtime/IO/*.cs` gives five call sites, and every RETRY-bearing verb is one of
them: `DeleteFile` (file sharing '62'), the shared OPEN (`SharedOpenAttempt`, '61'), `ConflictOnLockedRecord`
(READ, both formats, all three organizations, '51'), `RewriteShared` ('51') and `DeleteShared` ('51'). `WriteShared`
takes the phrase and discards it deliberately (14.9.51 GR16 defines no record-operation conflict for WRITE). All
five therefore inherit the single arm; none judges for itself.
