# PB346 — a zero timeout that retries anyway and then reports a deadlock

**Rows:** `GR-14.9.30.4-9`.

## The program

`<lane3 scratch>/out-b1/probe/p4x-retry/p4xretry.cob` — two RELATIVE SELECTs on one host file, both
`SHARING WITH ALL OTHER` and `LOCK MODE IS MANUAL`; seed RRN 1; `OPEN INPUT` on both; `READ FA WITH LOCK`
(FS=00); then on the other connector `READ FB RETRY FOR ZERO-SECS SECONDS` where
`01 ZERO-SECS PIC S9(4) VALUE 0`, and for contrast `READ FB RETRY 0 TIMES`.

Observed: `B-RETRY-0-SECONDS FSB=52` beside `B-RETRY-0-TIMES FSB=51`.

## The rule

§14.9.30.4 GR9 ends *The I-O status is set in accordance with the rules for the RETRY phrase*, and §14.7.9.3
GR4 a) says:

> If the RETRY phrase is not specified or the result of the evaluation of arithmetic-expression-1 or
> arithmetic-expression-2 is negative or zero, the statement is unsuccessful, the appropriate value is placed in
> the I-O status associated with the file connector according to the rules for 9.1.13, I-O status

`--check 14.7.9.3 "the statement is unsuccessful, the appropriate value is placed in the I-O status"` → **OK**.
A zero timeout therefore bypasses the retry machinery entirely and yields the record operation conflict status
'51' (§9.1.13.8 item 1), exactly as `RETRY 0 TIMES` does.

## What the compiler does

`FileRegistry.RetryLoop` (lines 829-844) branches on kind: the `Times` arm runs `for (int i = 0; i < amount &&
...)`, which for `amount <= 0` never executes and correctly returns the first attempt's '51'; the DEFAULT arm
covers `Seconds` **and** `Forever` together, re-checks once and returns `FileStatusCode.Deadlock`
unconditionally, **never consulting `amount`**.

'52' is a defensible implementor deadlock definition for FOREVER or a positive timeout in a single run unit —
§9.1.13.8 item 2 leaves detection to the implementor, and writing that determination down is **PB322** — but
GR4 a) routes the zero/negative case away from retrying at all, so it must not reach the deadlock verdict.

## Sweep

The same arm is shared by OPEN (`OpenShared`), DELETE FILE and the REWRITE/DELETE conflict paths, so **every
RETRY-bearing verb has the same zero/negative-SECONDS hole**; the probe above only happens to reach it through
READ.

## The fix shape

Normalise the retry spec ONCE — `amount <= 0` collapses to `FileRetryKind.None` before `RetryLoop` is entered —
rather than adding a guard per arm. That makes the next RETRY-bearing verb automatic, and it puts GR4 a)'s
predicate in the one place that can see the evaluated value.

**Code site:** `FileRegistry.cs#RetryLoop` (lines 829-844), reached from `#ReadLockGovern` (line 580) and
`#ReadShared` (line 659).
