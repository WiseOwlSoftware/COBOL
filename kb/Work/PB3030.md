# PB3030 — the bit-bearing OCCURS DEPENDING group beside a runtime-length table is still a stage

Filed 2026-10-11 by the train 1060 lander from the wave 1059 group H implementer's lead (new defect 1 of
`E:\COBOL-coord\scratch\reports\w1059h-PB2964-report.md`; the residue PB2964's `## Landed` section names). The lander

**2026-10-13, resume unit: branch `worktree-wf_d63f7207-db5-2` (wave 1069 B) ABANDONED, superseded:** wave 1070 A
cherry-picked all six of its commits onto `worktree-wf_787860dd-104-1`, which lands them. `git range-diff

`tests/conformance/2014/manifest.json`. Nothing on db5-2 is missing from 104-1.

**Shape.** A group whose subordinates are a dynamic-capacity table of dynamic-length elements and an OCCURS DEPENDING
table of USAGE BIT items. Repro `E:\COBOL-coord\scratch\t1060\pb3030_q2.cob` (`--std 2023`): `01 G` holds
`05 TD OCCURS DYNAMIC CAPACITY IN CP` / `10 DD PIC X DYNAMIC LENGTH` and `05 H` / `10 B PIC 1 USAGE BIT` /
`10 TB PIC 1 USAGE BIT OCCURS 1 TO 8 DEPENDING ON N`; `FUNCTION LENGTH(G)` stays the named loud stage COBOL1756
and aborts the run unit, where §15.50.4 7) and §15.14.4 6) define the group's current length (and §8.5.1.6.3 its
layout). DISPLAY / MOVE / CALL of the group take the same stage.

**Code site.** `src/Cobol.Net.Compiler/Binding/Model/DataItem.cs#CurrentExtentComposes` (line 1091):
`c.IsImageCapable ? ... (!c.HasBitDescendant && OdoTableOnOrBeneath(c) ...)` refuses a bit-bearing ODO group, and
`IntrinsicBinder.cs#VariableLengthGroupSum`'s `ImageOrStage` then stages it.

**Why not fixed in PB2964.** The variable-image codec's ODO prefix is counted in characters; this shape needs it in
BIT units (the OdoGroupPlace unit of PB2964's ODO term), a codegen redesign beyond that slice.

## Re-probed and split (w1069 B, 2026-10-12; not landed)

Re-probed on ddee217e3 + w1069 B: `pb3030_q2.cob` still warns COBOL1756 at compile and aborts the run unit with
NotImplementedCobolFeatureException ("the dynamic-capacity table 'TD' has a runtime-length element"). Split from the
w1069 B group as its own mechanism. Design read for the finisher (code sites verified, nothing changed):
- The stage is `IntrinsicBinder.VariableLengthGroupSum` -> `ImageOrStage`, refused because
  `DataItem.CurrentExtentComposes` excludes `c.HasBitDescendant` on the image-capable ODO arm. Admitting it there is
  ONE capability for three consumers in `CodeGen/DataDivision/GroupImageCodec.cs`: `OdoPrefixImage` (CurrentImage and
  AsVarImage), the `OdoFixed` splice in `FromVarImage`, and the `OdoFixed` arm of `ContiguousLayout` + `RecordOdo`.
- All three read `OdoGeometry` (tailStart = member width - ImageWidth x max; character units). The law they must
  share is `OdoModel.WrapGroup`'s (fixed units + count x stride, in BITS when `group.HasBitDescendant` and
  `BitLayout.StartBitOf(group, table) >= 0`, characters = ceiling / 8, `PositionsPerCharacter`): extract it as one
  geometry `OdoModel` returns and both `WrapGroup` and `OdoGeometry` read (note WrapGroup's non-bit arm uses
  `RecordLayout.PhysicalOccurrenceWidth`, the codec `ImageWidth`, which differ for a national element, PB943's trap).
- The hard arm is the record layout: `CobolContiguousLayout`'s ODO tail is whole elements of `Unit` characters, and a
  bit occurrence shares bytes, so a bit tail needs a character-unit component whose occurrence count is NOT the
  component length (`StatesCount`, D-FRA (viii)) - decide that in DESIGN-data-model / D-FRA before coding.
- Expected value for the repro (N = 2, DD(1) = "ab"): TD current image 2 characters; H = B + TB at 1 + 2 bits ->
  ceiling 1 character; LENGTH(G) = 3 (15.50.4 r7 sum; 8.5.1.6.3 layout; 15.50.4 r9 ceiling).

## Branch review R1-1 of wave 1074 A2 answered (2026-10-13)

The reviewer's shape: the bit OCCURS DEPENDING table is a DIRECT member of the variable-length group and CONTINUES a
§8.5.1.6.3 run (`05 DD PIC X DYNAMIC LENGTH LIMIT 5. 05 B PIC 1 USAGE BIT. 05 TB PIC 1 USAGE BIT OCCURS 1 TO 16
DEPENDING ON N.`, `E:\tmp\w1074a2rv\BT2.cob`). Re-probed at b44b46ad6: `DISPLAY G` threw ArgumentOutOfRange
(`"".Substring(0, 0 - …CutAt(__odo))`), at OCCURS 1 TO 8 (`BT1.cob`) it showed `[abA<NUL>]` with LENGTH 3. The
siblings were broken the same way: a CELL-BACKED group of the shape showed `[abP<NUL>]`, and a FILE record of the shape
threw at WRITE (`E:\COBOL-coord\scratch\w1074a2f\before\BT6.cob`, `BT7.cob`).
- Cause: the run is ONE slice at its leader's field (`PhysicalModel.Physical.BitRun`), which packed the whole run at
  the maximum as a Fixed part, while `VarParts` classified the table's EMPTY continuation field as OdoFixed, and
  `FixedImageTail(TB, TB)` measured the table from TB alone (Lead 0), two characters inside a three-character run.
- Fix: `VarParts` classifies a run's leader field by the member the run holds (the continuation contributes nothing),
  and `OdoModel.FixedImageTail` adds `BitLayout.BitsBeforeInRun(holder)` (new, read off `RunsOf`) to the lead, so the
  declared codec, the record layout and the cell window (`VarGroupWindow.OdoOf`) all measure the table from the run's
  first bit. A GROUP-USAGE BIT holder continuing a run and a 9-bit leader are the same law.
- Golden `2014/pb3030_bit_odo_run_continuation` (LENGTH at two counts, DISPLAY, a 9-bit leader, a bit-group holder, a
  GR8 a) MOVE, a cell-backed DISPLAY, a nested CALL at the maximum and a WRITE / READ round trip). The PB3030 golden's
  comment cited GR8 b) for a sending group whose data-name-1 is outside it; GR8 a) governs that case, corrected.
