# PB2877 — Windows and Linux lander gates run concurrently

Owner, 2026-10-09 ~10:25 PDT: "Why don't we run the Windows local and the WSL local gates in parallel? I.e.
Concurrently?" and, on the one-change train that carries this: "I approve this one-change train."

## Measured (train 1049, 2026-10-09)

- The Windows lander gate (`build-local.ps1 -Mode lander`, whole population, no gate slot) ran 10:15:11–~10:19.
- The Linux gate (`scripts/linux-gate.sh` under WSL) was started at 10:17:58, overlapping the Windows gate's last
  ~80 s, and took 351 s: unit 84 s, characterization 8 s, conformance 63 s, guard 69 s. The same legs run alone for
  train 1047y the night before: 87 s, 8 s, 64 s, 70 s — no slowdown from the overlap.
- The two share nothing: linux-gate.sh builds and tests a Linux clone of the committed HEAD under
  `/home/<user>/linux-gate/<name>`, exports nothing into the worktree, and the lander's Windows gate holds no gate slot.
  Running them in sequence cost the sum (~10 min) for the information the longer one (~6 min) gives.

## Landed

- MANDATORY-PRACTICES L10: the Linux gate starts in the background the moment every cluster is committed, concurrently
  with the Windows gate; both GREEN on the same head are required; a commit made to fix either gate's red re-runs both.
  The "Why" column carries the measurement.
- `templates/lander-train-brief.md` step 3b and `templates/lander-brief.md` step 3b say the same.
- **Not changed: I8, the implementer's Linux gate.** Implementer gates share CPU through the gate slot (up to three at
  once); a concurrent WSL build per implementer could oversubscribe the machine, which this lander measurement does not
  speak to. During the batched-gating trial (PB2515, to 2026-10-10 10:00) implementers run no Linux gate at all. Measure
  under the slot cap before changing I8.
