# PB268 — ln 10 re-derived per exponentiation

Found by the arithmetic-wave review fleet over the D-B/D-C/PB194/PB195 working tree, 2026-08-31, and fixed in the change set that landed the wave. Every number below was re-derived independently by the implementer (a 34-digit emulation of `CobolDec.cs` validated against the shipped `pb167` goldens, and 80–120-digit `Decimal` truth) BEFORE the confirming run, and then confirmed by it.

`PowCore` computed `ln10 = LnReduced(Ten, mode)` on entry. Its value depends only on `mode`, of which §11.9.11
offers exactly four — so it is a per-mode constant that was being re-derived unboundedly. The remark above it
argued only against computing it TWICE within one call; it never asked whether it should be computed once per
call forever.

## The count, corrected

PB167's Cost paragraph said three square roots per exponentiation. The general arm performs **six**: three for
ln 10 and three for ln b — and `Ln` calls `LnReduced` on the reduced mantissa, so the two are genuinely separate
developments, not one shared reduction. (After PB269 the near-unit arm uses none at all, so a near-unit base now
costs three.)

## The fix, and the one entry that must NOT be cached

Three `Lazy<CobolDec>` fields, one per cacheable mode. **PROHIBITED is never cached**: ln 10 has no exact SDIDI
form, so §11.9.11.2 r3d requires the development to RAISE EC-SIZE-TRUNCATION every time it is asked for — the
raise IS the observable, and a cached value would answer where the rule requires an exception
(`cite.py --check 11.9.11.2 "If the PROHIBITED phrase is specified and an intermediate value cannot be
represented exactly in SDIDI form"` → OK). Any `CobolRounding` value that is not one of §11.9.11's four develops
uncached rather than borrowing a cache entry whose mode it is not.
