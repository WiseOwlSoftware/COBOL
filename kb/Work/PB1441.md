# PB1441 — LANDED

## The rule (every citation re-run by the registrar through `cite.py --check`)

> Hex-character-sequence-1 shall be composed of hexadecimal digits

`python scripts/spec/cite.py --check 8.3.3.5.3 "…"` → `OK  §8.3.3.5.3 4)  (Syntax rules)`

## Finding — `national-literals` (wrong-answer; rows `SR-8.3.3.5.3-4`)

**Mechanism.** A hexadecimal-national literal whose content contains a non-hexadecimal character does not match NAT_BODY's HEXDIGITS arm, so the lexer silently re-tokenizes it as IDENTIFIER `NX` + STRINGLIT - the same silent-split degradation R03 closed for well-formed NX literals; §8.3.3.5.3 SR4 is never diagnosed and, with an item named NX in scope, the program compiles to a wrong answer.

**Repro.** REPOSITORY FUNCTION ALL INTRINSIC; `01 NX PIC X(4) VALUE "ZZZZ". 01 NA PIC N(4).` `MOVE FUNCTION MAX(NX"00G1") TO NA. DISPLAY "[" NA "]".` (probe n1) -> compiles with no diagnostic, prints [ZZZZ].

**Expected from the spec.** §8.3.3.5.3 SR4: "Hex-character-sequence-1 shall be composed of hexadecimal digits" (§8.3.3.1: the hexadecimal digits are 0-9 and A-F) - NX"00G1" is not a conforming literal and shall be rejected by a diagnostic naming SR4, never read as two operands.

**Observed / reasoning.** n1 prints [ZZZZ] (MAX(NX, "00G1")); without a data item NX the failure surfaces as unrelated diagnostics (n5 COBOLNET1504 argument count, n6 COBOLNET1639 'NX is not a literal'). Fix shape (the R03 doctrine: the token must match so something is left to diagnose): widen the NX (and sibling X, BX) body to any non-delimiter content and report the non-hex character at the same walker as COBOLNET1635. Siblings: HEX_BODY (X"4G", §8.3.3.2.3 SR5) and BOOL_BODY's BX arms (§8.3.3.4.3 r3) share HEXDIGITS.

**Code site.** src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4#NAT_BODY / #HEXDIGITS (also HEX_BODY, BOOL_BODY)

## What the fixer owes

NAT_BODY's NX arm requires HEXDIGITS ([0-9a-f]*, CobolLexer.g4:885); a non-hex body fails the arm and re-tokenizes as IDENTIFIER NX + STRINGLIT with no SR4 diagnostic; HEX_BODY (897) same shape

## Landed (wave 73 group A, 2026-09-29)

The R03 doctrine applied to the content: `CobolLexer.g4`'s `HEX_BODY`, `NAT_BODY` Format 2 and both `BOOL_BODY`
formats are now `<prefix> STR_BODY`, so a prefixed opening delimiter (§8.3.5 5)) always delimits ONE literal token
whatever its content — `NX"00G1"` is a NATLIT, never IDENTIFIER `NX` + STRINGLIT. The repertoire rules are asked of
every literal token by `LiteralScreenPass` through `CobolLiteral.RepertoireViolation` → **COBOLNET2630**, naming the
character and the rule (§8.3.3.5.3 SR4 here; §8.3.3.2.3 SR5 for X, §8.3.3.4.3 SR3 for BX, SR2 for B), BEFORE the
grouping rule, which declines such a literal; every hexadecimal decoder answers "" for it instead of throwing
(`DecodeHex` is now `DecodeHexGroups(…, 2)` — one decoder). The OTHER ARM: a compiler-directive operand is lexed
apart from the unit and was screened by nothing; `>>DEFINE V AS X"GG"` would have decoded to "" silently. The three
rules now have one ordered entry, `CobolLiteral.SyntaxViolation`, asked by `LiteralScreenPass` and by
`CompileTimeExpressionEvaluator` (COBOLNET1619, negative `negative/w73a-directive-hex-literal-non-hex-digit`);
`LiteralScreenDriftTests.LiteralRule_HasOneReportingSite` pins exactly those two callers. `unit:SeparatorRuleTests.PrefixedLiteral_IsOneTokenWhateverItsContent`
is the drift pin that every prefixed literal admits arbitrary content. Negative
`negative/w73a-hex-national-literal-non-hex-digit` (the note's own repro: `MAX(NX"00G1")` beside `01 NX` used to print
`[ZZZZ]`); positive `2002/w73a_prefix_literal_beside_named_item`. Row closed: SR-8.3.3.5.3-4.
