# PB3394 — the planner and the branch survey disagree on a FINDINGS stamp at an older head

**Mechanism.** Two places decide whether a FINDINGS-stamped branch needs a finisher, and they decide it differently.
`prune_worktrees.lifecycle()` sends a branch to its review finisher (DECISION, "the next wave plans it") only when the
stamp covers the tip (`rv.verdict == 'FINDINGS' and rv.covers(row.tip)`). A stamp at a head the branch has since moved
past reads WAITING FOR REVIEW ("one cobol-reviewer reviews it"), which is the enqueue unit's diff-only re-review (owner
2026-10-18 12:10, kb/Work PB3381). `plan_wave.py`'s `findings(r, cls)` inside `plan()` asks only `r.finished and
r.review and r.review.verdict == "FINDINGS"`. It never compares the stamp's head with the branch tip, so it plans a
FINISH-FIRST group (`finisher_pred`) for work that someone has already answered on the branch.

**Repro (2026-10-18 19:52 PDT, the loop's wave unit).** `plan_wave.py --wave 1127 --from-budget --borrow-days 6
--cluster PB3353` planned A, B and C as FINISH-FIRST groups. The 19:37 session probe listed all three branches WAITING
FOR REVIEW:

| group | branch | stamp head | tip | the commits after the stamp |
|---|---|---|---|---|
| A PB3387 | `inbox-guard-stop-hook-20261018` | `11f7b8ab0c0e` | `314d06415` | "PB3387 review R1-1: …" (the one finding) |
| B PB3384 | `nist-chains-tsv-retire-20261018` | `cef5103914fc` | `da45ebee9` | "PB3384 review R1-1, R1-2: …" (both findings) |
| C PB3386 | `notes-pb3263-pb3386-leads-20261018` | `e815db0131fd` | `d63de8a46` | `749a81f44` answers R1-1 and R1-2, then two more lead commits |

Each rendered spec (`msg-w1127-{a,b,c}.txt`, line 10) told a fresh implementer to cut a worktree from main, `git merge`
the branch, answer every finding by its id and re-gate under the shared gate slot (cap 3, kb/Work PB2514). Branch C was
still receiving commits from the attended session while the wave was planned, so its finisher's branch would have
diverged from a live branch. The unit did not launch (its handoff records why), and the dispatch ledger entries were
released.

**Sites:**
- `scripts/orchestrator/plan_wave.py` — `plan()`'s nested `findings(r, cls)` (the FINDINGS arm of the lead selection)
  and `finisher_pred` (the FINISH-FIRST text it selects).
- `scripts/prune_worktrees.py` — `lifecycle()`, the FINDINGS arm that requires `rv.covers(row.tip)`.

**Fix shape.** Write the rule in one place. A FINDINGS stamp makes a review finisher only when it covers the branch tip
(`Review.covers`, the predicate `lifecycle()` already uses). A stamp at an older head is WAITING FOR REVIEW: the
planner leaves the branch to the enqueue unit's re-review and names it in the plan table, never as a group. The simplest
durable shape is for the planner to take each report branch's lifecycle state from `prune_worktrees` instead of
re-deriving it. A self-test pins the 19:52 shape: a DONE report stamped FINDINGS at head X, its branch at a later tip,
gets no FINISH-FIRST group, and both the planner and the survey read it WAITING FOR REVIEW.

**Why it matters.** The finisher is the expensive arm: a worktree, a build and a full gate per branch, inside the gate
slot the landing lane also needs. The re-review it duplicates is one read-only reviewer over the commits since the
stamp.
