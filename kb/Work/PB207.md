# PB207

Registered 2026-08-31 as the DECLARED boundary of [[PB184]]'s landing. **The review fleet then refuted two of
this note's own claims, and the probe that settled them changed what the note is about.**

**THE SHAPE.** `01 BG GROUP-USAGE BIT VALUE B"1010". 05 B1 PIC 1(2). 05 B2 PIC 1(2).` §13.18.63.3 SR10 admits a
boolean literal on a bit group ("Boolean literals in the VALUE clause of a bit group item shall not exceed the
size of the group item"), and §13.18.63.4 GR5 then initializes the group AREA. **This is conforming source.**

**WHY NEITHER LANE CAN ANSWER IT.** Every other group's `ImageWidth` counts CHARACTER positions, so GR5's area
deposit is a character text of that length. A bit-bearing group's `ImageWidth` is
`BitLayout.Characters(ExtentBits(...))` = `ceil(bits/8)` packed characters (design D19 / [[PB43]]) — a different
unit, laid out by the §8.5.1.6.3 walk. And the members do not tile it: `BG` above is 4 bits = **1** character
while `B1` and `B2` are `ceil(2/8)` = **1** character *each*.

### ⚠ TWO CORRECTIONS TO THIS NOTE, both measured (2026-08-31, the review-fleet landing)

1. **It was filed `crashes: false` and characterised as a silent mis-seed. It was a COMPILER CRASH.** The
   multi-member shape above raised an unhandled `System.ArgumentOutOfRangeException` out of
   `GroupValueSlicer.SliceInit` (`Substring` past the end of a 1-character area) — measured on the PB184 tree AND
   independently on `8ca74a3d` in a clean worktree, so the crash predates PB184 and belongs to the older slicer
   lane exactly as the note's ⚠ paragraph said.
2. **"the guarded behavior is right for a single-member bit group and only a multi-member one can observe the
   gap" is FALSE.** Measured: `01 BG GROUP-USAGE BIT VALUE B"1010". 05 B1 PIC 1(4).` displayed `B1` as `1` — ONE
   boolean position — against `1010` for the member-wise twin `01 BH GROUP-USAGE BIT. 05 H1 PIC 1(4) VALUE
   B"1010".` The area text is truncated to the group's 1-character `ImageWidth` **before** it is sliced, so the
   single-member case loses three of its four bits. Both member counts were wrong; only one of them was loud.

### What landed 2026-08-31 (a refusal, not the fix)

Because the two live behaviors were a crash and a silent wrong answer, the boundary is now **staged loud**:
`DataBinder.CheckGroupValueDeclarations` rejects a group-level VALUE on a group with a USAGE BIT descendant with
`DiagnosticCatalog.BitGroupLevelValue` (COBOLNET0899, the `recognized-not-implemented` family), naming this note.
The emitter is kept total independently: `GroupValueSlicer.AreaTextOf` returns null for such a group, so both
lanes fall through to the member-wise composition even if the screen were bypassed.

⛔ **The exclusion is now written ONCE and keyed on the FACT.** It used to be restated in
`GroupImageCodec.ImageInitOfOne` as `item.GroupUsage is not GroupUsage.Bit` — a predicate NARROWER than what it
protects. What switches `DataItem.ImageWidth` from a character sum to the bit walk is `HasBitDescendant`;
GROUP-USAGE BIT is only the commonest way to acquire it. The codec's restatement is deleted and both lanes
inherit `AreaTextOf`'s one predicate.

⚠ **THE FLAGS DESCRIBE WHAT IS OPEN, NOT WHAT WAS FOUND.** They moved from
`wrong_answer/silent, crashes:false` to `rejects_legal_source` alone, and `severity` from MINOR to MAJOR. The
crash and the two silent wrong answers are FIXED — they are recorded in the corrections above so the history is
not lost, but a reader ranking work must see the current harm, which is that conforming source is refused by
name. That is a strict improvement on a crash and on a silent wrong answer, and it is debt this note owns until
the fix lands. (Read the frontmatter as "what does this do to a user's program TODAY".)

**Pin:** `tests/conformance/negative/pb207-bit-group-level-value.cob` — the multi-member shape, asserting the
compiler no longer crashes on it.

**FIX SHAPE (unchanged).** Give the area rule a BOOLEAN-POSITION mode: for a bit group compose the area as `n`
boolean positions (from a `B"…"` literal, the ALL form, or figurative ZERO — SR10's admitted operands), then hand
the codec lane `BitsPack(area, n)` and the slicer lane per-member `BitLayout.RunBits` windows, exactly as the
member-wise path already does. `BitLayout` already owns the §8.5.1.6.3 walk both would need. Not landed with
PB184 because it is a second unit system, not a second call site.

## Batch-b3 extension (lane 3, §13.18.63.4) — 2026-09-04

`GR-13.18.63.4-5` is this note's own rule and is now recorded PARTIAL on its evidence. The lane-3 measurement: the GR5 area deposit is LIVE and correct for the population §13.18.63.3 SR14 admits — a nested group, a figurative group VALUE (`01 G VALUE ALL "*".` fills the whole area), a subordinate OCCURS that TILES the area, and a numeric DISPLAY subordinate that takes the characters under it WITHOUT conversion — and it is refused BY NAME outside it: probe `gr5bit`, `01 BG GROUP-USAGE BIT VALUE B"1010". 05 A PIC 1(2) USAGE BIT. 05 B PIC 1(2) USAGE BIT.` draws COBOLNET0899 naming the §13.18.63.4 GR5 area deposit for a bit-packed group. The row therefore carries exactly this note's residue and closes with it.
