# PB207

Registered 2026-08-31 as the DECLARED boundary of [[PB184]]'s landing. **The review fleet then refuted two of
this note's own claims, and the probe that settled them changed what the note is about.**

**THE SHAPE.** `01 BG GROUP-USAGE BIT VALUE B"1010". 05 B1 PIC 1(2). 05 B2 PIC 1(2).` §13.18.63.3 SR10 admits a
boolean literal on a bit group ("Boolean literals in the VALUE clause of a bit group item shall not exceed the
size of the group item"), and §13.18.63.4 GR5 then initializes the group AREA. **This is conforming source.**

**WHY NEITHER LANE CAN ANSWER IT.** Every other group's `ImageWidth` counts CHARACTER positions, so GR5's area
deposit is a character text of that length. A bit-bearing group's `ImageWidth` is
`BitLayout.Characters(ExtentBits(...))` = `ceil(bits/8)` packed characters (design D19 / [[PB43]]) — a different
unit, laid out by the §8.5.1.6.3 walk. And the members do not tile it: `BG` above is 4 bits = **1** character
while `B1` and `B2` are `ceil(2/8)` = **1** character *each*.

### ⚠ TWO CORRECTIONS TO THIS NOTE, both measured (2026-08-31, the review-fleet landing)

1. **It was filed `crashes: false` and characterised as a silent mis-seed. It was a COMPILER CRASH.** The
   multi-member shape above raised an unhandled `System.ArgumentOutOfRangeException` out of
   `GroupValueSlicer.SliceInit` (`Substring` past the end of a 1-character area) — measured on the PB184 tree AND
   independently on `8ca74a3d` in a clean worktree, so the crash predates PB184 and belongs to the older slicer
   lane exactly as the note's ⚠ paragraph said.
2. **"the guarded behavior is right for a single-member bit group and only a multi-member one can observe the
   gap" is FALSE.** Measured: `01 BG GROUP-USAGE BIT VALUE B"1010". 05 B1 PIC 1(4).` displayed `B1` as `1` — ONE
   boolean position — against `1010` for the member-wise twin `01 BH GROUP-USAGE BIT. 05 H1 PIC 1(4) VALUE
   B"1010".` The area text is truncated to the group's 1-character `ImageWidth` **before** it is sliced, so the
   single-member case loses three of its four bits. Both member counts were wrong; only one of them was loud.

### What landed 2026-08-31 (a refusal, not the fix)

Because the two live behaviors were a crash and a silent wrong answer, the boundary is now **staged loud**:
`DataBinder.CheckGroupValueDeclarations` rejects a group-level VALUE on a group with a USAGE BIT descendant with
`DiagnosticCatalog.BitGroupLevelValue` (COBOLNET0899, the `recognized-not-implemented` family), naming this note.
The emitter is kept total independently: `GroupValueSlicer.AreaTextOf` returns null for such a group, so both
lanes fall through to the member-wise composition even if the screen were bypassed.

⛔ **The exclusion is now written ONCE and keyed on the FACT.** It used to be restated in
`GroupImageCodec.ImageInitOfOne` as `item.GroupUsage is not GroupUsage.Bit` — a predicate NARROWER than what it
protects. What switches `DataItem.ImageWidth` from a character sum to the bit walk is `HasBitDescendant`;
GROUP-USAGE BIT is only the commonest way to acquire it. The codec's restatement is deleted and both lanes
inherit `AreaTextOf`'s one predicate.

⚠ **THE FLAGS DESCRIBE WHAT IS OPEN, NOT WHAT WAS FOUND.** They moved from
`wrong_answer/silent, crashes:false` to `rejects_legal_source` alone, and `severity` from MINOR to MAJOR. The
crash and the two silent wrong answers are FIXED — they are recorded in the corrections above so the history is
not lost, but a reader ranking work must see the current harm, which is that conforming source is refused by
name. That is a strict improvement on a crash and on a silent wrong answer, and it is debt this note owns until
the fix lands. (Read the frontmatter as "what does this do to a user's program TODAY".)

**Pin:** `tests/conformance/negative/pb207-bit-group-level-value.cob` — the multi-member shape, asserting the
compiler no longer crashes on it.

**FIX SHAPE (unchanged).** Give the area rule a BOOLEAN-POSITION mode: for a bit group compose the area as `n`
boolean positions (from a `B"…"` literal, the ALL form, or figurative ZERO — SR10's admitted operands), then hand
the codec lane `BitsPack(area, n)` and the slicer lane per-member `BitLayout.RunBits` windows, exactly as the
member-wise path already does. `BitLayout` already owns the §8.5.1.6.3 walk both would need. Not landed with
PB184 because it is a second unit system, not a second call site.

## Batch-b3 extension (lane 3, §13.18.63.4) — 2026-09-04

## Landed 2026-09-04 — the area rule has TWO UNITS, and the refusal was in front of a rule that already governed

**RE-PROBED FIRST on a freshly built tree (base `62a36759`).** All three shapes still reproduced, byte for byte:
`01 BG GROUP-USAGE BIT VALUE B"1010". 05 B1 PIC 1(2). 05 B2 PIC 1(2).`, its single-member twin, and
`01 G VALUE "AB". 05 B1 PIC 1(8) USAGE BIT.` — every one refused `COBOLNET0899` at the group's line.

### The rule, derived before a line was changed (every citation `cite.py --check`ed)

§13.18.29.4 GR1a: a `GROUP-USAGE BIT` group "is a bit group and also a bit data item; its class and category are
boolean". GR1b: "Unless stated otherwise, a bit group is treated as though it were an elementary data item of
usage bit and class and category boolean described with PICTURE 1(m), where m is the bit length of the group."
So §13.18.63.4 GR5's "group area" for a bit group is **m BOOLEAN POSITIONS** — laid out by §8.5.1.6.3, which
GR1c names — where `DataItem.ImageWidth` reports the `ceil(m/8)` characters it OCCUPIES. GR7 then sends the
literal through §14.6.8, and **the arm is the receiving item's CATEGORY**: §14.6.8.6 for category boolean —
"transferred … into the corresponding boolean positions of the receiving data item, with **zero fill** or
truncation to the right" — against §14.6.8.5's space fill for alphanumeric/national. The note's own FIX SHAPE
was right about the unit and wrong about one detail: the slicer's per-member window is `StartBitWithin`, not a
running sum of `RunBits` (see the sibling below).

### What landed

1. **`GroupValueSlicer.AreaOf`** replaces `AreaTextOf` and returns `GroupArea(Text, Bits)` — the area AND its
   unit. The unit is decided ONCE and both lanes inherit it, which is the same discipline that put the old
   exclusion in one place; a consumer re-deriving "is this a bit group?" is how the codec lane came to carry a
   narrower copy of it in the first place. Width = `AsIfPic!.Length` (= `ExtentBits`) for a bit group,
   `ImageWidth` otherwise; pad = `'0'` / `' '` per §14.6.8.6 / §14.6.8.5.
2. **`GroupValueSlicer.SliceBitInit`** — the record-struct lane's bit twin, placing each member at
   `BitLayout.StartBitWithin` with `WidthBits` per occurrence.
3. **`GroupImageCodec.BitAreaOf`** — ⛔ ONE §8.5.1.6.3 composition for a bit group's area, taking a
   member→carrier function, ridden by the generated `AsBits()`, by `FromBits`, by the compile-time image seed and
   by the GR5 arm. The image lane packs it through `CobolBits.Pack` (the ONE bit-order law, PB203), never a
   second packer.
4. **The `COBOLNET0899` refusal and `DiagnosticCatalog.BitGroupLevelValue` are DELETED.**

### ⛔ THE REFUSAL WAS MIS-ATTRIBUTING HALF ITS OWN POPULATION

Keyed on `HasBitDescendant`, the screen also caught `01 G VALUE "AB". 05 B1 PIC 1(8) USAGE BIT.` — and sat in
FRONT of the SR14 arm that governs it. That program is an ALPHANUMERIC group item (§13.18.29.4 GR3) with a
subordinate that is not usage DISPLAY, i.e. a §13.18.63.3 SR14 violation, and it was being told the compiler had
not implemented something. Non-conforming source named as a compiler gap sends the programmer to wait for a
feature instead of to their own declaration. It now reports COBOLNET1702, and
`tests/conformance/negative/pb207-bit-group-level-value.cob` pins exactly that attribution (measured at all four
editions; at 85 COBOLNET0900 is reported ALONGSIDE it, not instead of it).

### TWO SIBLINGS, both live silent WRONG ANSWERS, found by probing the axis the note held fixed

Neither was in this note; both are the same root cause — the bit-group area composition was written in three
places and only `BitLayout` was right. Both are fixed by (3) above.

- **`AsBits()`/`FromBits` summed the members' widths instead of placing them.** Measured at `62a36759`:
  `01 BG GROUP-USAGE BIT. 05 B1 PIC 1(2) VALUE B"11". 03 B2 PIC 1(2) VALUE B"11".` printed `DISPLAY BG` as
  **four** boolean positions while `FUNCTION LENGTH(BG)` — reading the same walk through `AsIfPic` — answered
  **ten**. A sum is right only while every member is "immediately following … an item of the SAME LEVEL"; B2's
  level number differs, so §8.5.1.6.3 sends it to "the first bit position of the first available byte" and bits
  2–7 are implicit filler. Now `1100000011`, and leg 8 of the golden pins it.
- **A bit group's compile-time IMAGE concatenated its members' packed images.** Measured at `62a36759`:
  `01 K GROUP-USAGE BIT. 05 K1 PIC 1(2) VALUE B"11". 05 K2 PIC 1(2) VALUE B"01". 01 KV REDEFINES K PIC X(1).`
  read `K2` back as `00`, the backing byte being `0xC0` — each member imaged as its own `ceil(2/8)` = 1
  character, so a 2-character composition was truncated to the group's 1-character width and K2's byte fell off.
  PB203's golden could not see it: its bit members are 8 bits wide, where the concatenation and the packing
  happen to agree. Now `1101` / `0xD0`, and leg 7 of the golden pins the VALUE-bearing twin against its
  member-wise control.

### Not taken

- **§13.18.63.3 SR10's size cap** ("Boolean literals in the VALUE clause of a bit group item shall not exceed
  the size of the group item") is [[PB206]]'s, and no golden leg here writes an over-long literal. The area rule
  truncates from the right if one arrives, which keeps the emitter total over source PB206 will reject.
- **A MIXED group** — an alphanumeric group with bit leaves — reaching `ImageInitOf` as a REDEFINES canonical is
  still wrong, and it is a different composition (§8.5.1.6.3 RUNS, which `PhysicalModel` already computes for
  `AsImage` and `ImageInitOf` does not consult). Measured, filed as a new defect, NOT fixed here.
