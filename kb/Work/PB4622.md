# PB4622 - lead from a landed branch's report

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/FunctionValueLane.cs:122` (`FunctionValueLane`), `src/WiseOwl.Cobol.Compiler/CodeGen/Emit/IntrinsicRenderer.cs:798` (`IntrinsicRenderer.RenderFloatNative`)

Wrong-answer class, shares the root of PB4516's classification. `COMPUTE X5 = FUNCTION ABS(DN)` and `FUNCTION FRACTION-PART(F)` with a COMP-2 argument land the shortest decimal, not the item's exact binary value (|-2.5E+40| low digits 00000 vs the item's 73792; FRACTION-PART(5.9999999996) 0.9999999996000000000 vs 0.9999999995999999669). Before PB4516 the bare form landed the expansion and `+ 0` the decimal; now both agree on the decimal: consistent but arguably wrong for the functions whose value is the item's content. Sites per report: FunctionValueLane.cs:122-124 (`anyReal => ApproximateReal`), IntrinsicRenderer.cs:798 (`RenderFloatNative`), 241 (`RealMethod`). Repro `E:\COBOL-coord\scratch\w20261852f\probe4.cob` (as reported, not re-run). Determined in wave 20261870 (below).

**Determination (adjudicator, wave 20261870).** The standard fixes these values exactly. MAX and MIN return "the content of the argument-1" (§15.59.4 1), §15.63.4 1)), MEDIAN of an odd count "the content of the argument" (§15.61.1), and INTEGER, by §15.44.4 1), "the greatest integer less than or equal to the value of argument-1". §15.4.1 leaves a function without an equivalent expression to the implementor only "unless otherwise specified in the function definition". ABS, INTEGER-PART, FRACTION-PART and REM have equivalent expressions whose value over a float item is exactly representable in binary64, and the runtime's binary64 bodies compute it exactly. The owner's 2026-11-04 ruling on PB4569 (exact where the standard defines an exact value) closes §15.4.1's native approximation latitude for them, and GnuCOBOL 3.2.0 agrees: each function equals the item or its written-out expression. The defect is the classification. `FunctionValueLane.Of`'s last arm and `IntrinsicRenderer.RenderNum`'s binary64 dispatch call the binary64 that a NON-floating-math function computes from a float ITEM an approximation (`ApproximateReal`, `NumX.Approximate`), and PB4516 lands every approximation by its shortest decimal. So `MOVE FUNCTION ABS (DN) TO X5` stores 00000 where `MOVE DN TO X5` stores 73792. `FUNCTION FRACTION-PART (F)` stores .9999999996000000000 where `F - 5` stores .9999999995999999669. `FUNCTION MAX (C1)` over FLOAT-SHORT 0.1 stores .1000000014901161200 where C1 stores .1000000014901161193. `FUNCTION MIN (A1)` and `FUNCTION MIN (A1 ONE)` differ. `COMPUTE R ROUNDED MODE IS PROHIBITED = FUNCTION ABS (A1)` takes NOT ON SIZE ERROR where `= A1` raises. SUM, MEAN, RANGE and MIDRANGE over float items land the shortest decimal of the very binary64 that `A1 + A2` lands by its expansion. STANDARD-DECIMAL is already right.

**Owed:** one predicate on `IntrinsicCarrierRules`, asked by the binder and the renderer alike. A binary64 returned value is an approximation only for `IntrinsicSig.Float` or when no binary64 argument is a float item's content. Otherwise it is `CarrierKind.Real` and lands by its exact value. `FunctionValueLane.Of` line 124, `RenderNum` line 242, `RenderFloat` / `RenderFloatNative` (the kind passed in, `FloatToScaled(approximation: false)` in place of `FromDouble`, and `FromBinary64` in the standard-mode arm), and `SendingValueTemp.IsBinary64Approximation` (`HoldsApproximation` only for `ApproximateReal`). NUMERIC_DESIGN (the approximation sentences near lines 140 and 1298) and CONFORMANCE (the PB623/PB1606/PB4516 determination, DOC-A.1-92, DOC-A.1-123) change in the same commit. Golden `15.4.1-Numeric-and-integer-functions/pb4622_float_item_function_value_exact` (2002|2014|2023) with a standard-decimal twin; `pb3268_function_value_lane_matrix` and `FunctionValueLaneDriftTests` move with it. Expected values, the guard rows (ABS of EXP10(-6) stays 0.000001) and the sibling probes: `E:/COBOL-coord/scratch/op-w20261870/a/determination.md`.

**Landed (wave 20261872, group A).** Re-probed on the build (`E:/COBOL-coord/scratch/w20261872a/pa/p4w.cob`, `p6.cob`): `MOVE FUNCTION ABS (DN) TO X5` stored 00000 for 73792, `FRACTION-PART (F)` .9999999996000000000 for .9999999995999999669, `MAX (C1)` .1000000014901161200 for .1000000014901161193, `SUM (A1 A2)` .3000000000000000400 for .3000000000000000444, and `COMPUTE R ROUNDED MODE IS PROHIBITED = FUNCTION ABS (A1)` took NOT ON SIZE ERROR where `= A1` raises. After the fix every row of the determination reads its expected value (p4w T01-T20, p6 M01-M04; the guard `ABS (FUNCTION EXP10 (-6))` stays .0000010000000000000 and STANDARD-DECIMAL (p3) is unchanged).

Fix, one predicate asked in both layers: `IntrinsicCarrierRules.Binary64ResultIsApproximation (floatFamily, anyFloatItemArgument)` is true for the §15.4.1 floating-math family and when no binary64 argument is a float ITEM's content. `FunctionValueLane.Of` (bind time) and `IntrinsicRenderer.RenderFloat` (`AnyFloatItemArgument`) both ask it. A value derived from a float item is `CarrierKind.Real` / `NumX{Real, Approximate: false}`: `RenderFloatNative` lands it through `FloatToScaled(value.Expr, value.Approximate, ...)`, the landing `COMPUTE R = F` takes (with `RealResult`'s NaN screen), the standard-decimal arm lifts it with `CobolDec.FromBinary64` and not `FromApproximation`, and `SendingValueTemp` flags a multi-receiver MOVE's intermediate `HoldsApproximation` only for `FunctionValueLane.ReturnsApproximation` (`ReturnsBinary64Value` still picks the COMP-2 description). As an operand the value keeps the float lane (`ABS (A1) + 0.5` is `A1 + 0.5`, .5999999999999999777).
