# PB523

## Mechanism — linage-clause
linage-margins-evaluated-then-discarded

### Expected, from the standard
GR1: 'The logical page size is the sum of the values referenced by each phrase except the FOOTING phrase.' GR4: 'Integer-3 or the value of the data item referenced by data-name-3 specifies the number of lines in the top margin on the logical page.' GR5 says the same for the bottom margin. GR8: 'Each logical page is contiguous to the next with no additional spacing provided.' 14.9.51.4 GR26a: on page overflow 'the device is repositioned to the first line that may be written on the next logical page'; GR25g: for a WRITE ADVANCING PAGE on a file WITH a LINAGE clause 'the repositioning is to the first line that may be written on the next logical page as specified in the LINAGE clause' - the physical-page form feed is GR25h, the NO-LINAGE case. For p1_margins.cob the logical page is therefore 3 + 2 + 2 = 7 lines: top margin on physical lines 1-3, page body on 4-5, bottom margin on 6-7, the next page starting immediately at 8. AAAA is written on page-1 body line 2 and BBBB on page-2 body line 1, so FIVE lines separate them (page-1 bottom margin 2 + page-2 top margin 3). For p20_topbot2.cob the ADVANCING PAGE write must skip the 2-line top margin of the new page, not emit a form feed.

```
$ python scripts/spec/cite.py --check 13.18.34.4 "Integer-3 or the value of the data item referenced by data-name-3 specifies the number of lines in the top margin on the logical page"
  OK  §13.18.34.4 4)  (General rules)
```

### Observed
`_top` and `_bottom` are assigned at SequentialConnector.cs:133 and read NOWHERE - a grep over the file returns exactly the declaration and that one assignment - so the two clauses are parsed, bound, re-evaluated at every GR6 evaluation point and then dropped on the floor. p1_margins.cob produces the entire file as `\r\nAAAA\r\nBBBB\r\nCCCC\r\n`: no top margin, no bottom margin, and ONE line across the page wrap instead of five. p23_sum.cob reproduces it byte for byte on LINE SEQUENTIAL. p20_topbot2.cob produces `\fAAAA\r\nBBBB\r\n` - a bare form feed where the LINAGE-defined repositioning past a 2-line top margin was required. THE ROOT CAUSE IS A MISREAD RULE, not an oversight: the comment at :96-99 states the model as 'The LINAGE feature is COUNTER-ONLY on the physical stream: each logical page is contiguous to the next with no additional spacing (13.18.34 GR8 - no margin blank lines, nothing emitted at page wrap)'. GR8 forbids spacing ADDITIONAL to the logical page; it does not delete the margins the logical page is defined by GR1/GR4/GR5 to contain. Under the misreading GR4 and GR5 have no content at all and GR1's 'sum ... except the FOOTING phrase' is a sum of one term - which is the tell. This is worse than an unimplemented clause: a program with LINES AT TOP compiles clean and silently prints on a differently-sized page, so a report that must land its totals in a fixed physical band lands them wrong with no diagnostic anywhere. THE FIX IS STRUCTURAL, not a field read: the connector needs a physical-position model (page-relative line, margins included) that Advance() and the two page-transition sites both go through, so that the reposition distance is derived from the logical page rather than from the WRITE's own line count - and the ADVANCING PAGE arm must route through the SAME transition rather than emitting a raw form feed. Pair it with a golden that asserts the BYTES of a TOP/BOTTOM file, since every existing LINAGE test observes only LINAGE-COUNTER and the END-OF-PAGE branches (LinageConformanceTests' own class comment says so) and therefore cannot see this class of defect at all.
