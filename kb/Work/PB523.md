# PB523

## Mechanism — linage-clause
linage-margins-evaluated-then-discarded

### Expected, from the standard
GR1: 'The logical page size is the sum of the values referenced by each phrase except the FOOTING phrase.' GR4: 'Integer-3 or the value of the data item referenced by data-name-3 specifies the number of lines in the top margin on the logical page.' GR5 says the same for the bottom margin. GR8: 'Each logical page is contiguous to the next with no additional spacing provided.' 14.9.51.4 GR26a: on page overflow 'the device is repositioned to the first line that may be written on the next logical page'; GR25g: for a WRITE ADVANCING PAGE on a file WITH a LINAGE clause 'the repositioning is to the first line that may be written on the next logical page as specified in the LINAGE clause' - the physical-page form feed is GR25h, the NO-LINAGE case. For p1_margins.cob the logical page is therefore 3 + 2 + 2 = 7 lines: top margin on physical lines 1-3, page body on 4-5, bottom margin on 6-7, the next page starting immediately at 8. AAAA is written on page-1 body line 2 and BBBB on page-2 body line 1, so FIVE lines separate them (page-1 bottom margin 2 + page-2 top margin 3). For p20_topbot2.cob the ADVANCING PAGE write must skip the 2-line top margin of the new page, not emit a form feed.

```
$ python scripts/spec/cite.py --check 13.18.34.4 "Integer-3 or the value of the data item referenced by data-name-3 specifies the number of lines in the top margin on the logical page"
  OK  §13.18.34.4 4)  (General rules)
```

### Observed
`_top` and `_bottom` are assigned at SequentialConnector.cs:133 and read NOWHERE - a grep over the file returns exactly the declaration and that one assignment - so the two clauses are parsed, bound, re-evaluated at every GR6 evaluation point and then dropped on the floor. p1_margins.cob produces the entire file as `\r\nAAAA\r\nBBBB\r\nCCCC\r\n`: no top margin, no bottom margin, and ONE line across the page wrap instead of five. p23_sum.cob reproduces it byte for byte on LINE SEQUENTIAL. p20_topbot2.cob produces `\fAAAA\r\nBBBB\r\n` - a bare form feed where the LINAGE-defined repositioning past a 2-line top margin was required. THE ROOT CAUSE IS A MISREAD RULE, not an oversight: the comment at :96-99 states the model as 'The LINAGE feature is COUNTER-ONLY on the physical stream: each logical page is contiguous to the next with no additional spacing (13.18.34 GR8 - no margin blank lines, nothing emitted at page wrap)'. GR8 forbids spacing ADDITIONAL to the logical page; it does not delete the margins the logical page is defined by GR1/GR4/GR5 to contain. Under the misreading GR4 and GR5 have no content at all and GR1's 'sum ... except the FOOTING phrase' is a sum of one term - which is the tell. This is worse than an unimplemented clause: a program with LINES AT TOP compiles clean and silently prints on a differently-sized page, so a report that must land its totals in a fixed physical band lands them wrong with no diagnostic anywhere. THE FIX IS STRUCTURAL, not a field read: the connector needs a physical-position model (page-relative line, margins included) that Advance() and the two page-transition sites both go through, so that the reposition distance is derived from the logical page rather than from the WRITE's own line count - and the ADVANCING PAGE arm must route through the SAME transition rather than emitting a raw form feed. Pair it with a golden that asserts the BYTES of a TOP/BOTTOM file, since every existing LINAGE test observes only LINAGE-COUNTER and the END-OF-PAGE branches (LinageConformanceTests' own class comment says so) and therefore cannot see this class of defect at all.

## Landed 2026-09-09 — the logical page became a physical layout

Landed in two checkpoints on one branch: `22042b57` (the killed implementer's restructuring of
`SequentialConnector` into a logical-page physical-position model) and the finisher's continuation of it,
which re-probed that checkpoint on a fresh build before building anything on top of it.

**The fix.** `SequentialConnector` no longer keeps a counter over an untouched print stream. It tracks where
on the current logical page the device sits, page-relative — physical page lines `1 … _top` are the top
margin (§13.18.34.4 GR4), `_top + c` is page-body line `c` (GR2) and `c` IS the LINAGE-COUNTER (GR7),
`… + _pageBody + 1 … + _bottom` is the bottom margin (GR5) — so the device position is exactly
`_top + LinageCounter` plus one bit, `_topMarginPending`, for the one moment the two disagree.
`EmitTopMarginIfPending` materializes that margin and is called FIRST by every travel
(`PositionOnLogicalPage`) and every presentation (`Present`), so no record can reach a page body without it.
`BeginNextLogicalPage` is the ONE page transition, shared by §14.9.51.4 GR25 g)'s ADVANCING PAGE and
GR26 a)'s overflow because the standard writes the same destination for both, and split in three along
§13.18.34.4 GR6 b)'s own sentence: the rest of THIS page (unwritten body lines + bottom margin), the operand
re-evaluation, then exactly ONE line onto the next page — GR8's contiguity is what makes it one. **The
travel is derived from the LOGICAL PAGE, never from the WRITE's own line count.** `Advance`'s form feed
survives only for GR25 h), the NO-LINAGE arm. Both WRITE arms were fixed: the LINE SEQUENTIAL twin now goes
through `EmitLineSequentialRecord`, which presents and then travels one line on the logical page instead of
emitting a bare `WriteLine` — the unfixed half of a two-arm dispatch. The page model dies at CLOSE
(`EndLinagePage`), since GR6 b) 1 and GR7 d) establish it at OPEN OUTPUT and at no other mode.

**The root cause was a misread rule, and it is now written down as one.** The comment that justified the old
model cited GR8 ("each logical page is contiguous to the next with no additional spacing") as licence to drop
the margins. GR8 forbids spacing ADDITIONAL to the logical page; it does not delete the margins GR1/GR4/GR5
define the page to contain. Under the misreading GR4 and GR5 had no content at all and GR1's "sum … except
the FOOTING phrase" was a sum of one term — which was the tell.

**The observability hole is closed structurally.** Every LINAGE test in the tree read LINAGE-COUNTER and the
END-OF-PAGE branches through stdout, and the harness deleted the run directory before anything could look at
the file, so this defect class was invisible by construction. `CobolNetCompiler.CompileRunAndReadFile` now
returns the produced file's bytes, `LinageConformanceTests` grows six `Bytes_*` tests over it (margins +
overflow, the zero-margin identity, AFTER and BEFORE ADVANCING PAGE, the BEFORE-phrase overflow ordering,
and the LINE SEQUENTIAL arm), and the class comment — which stated the counter-only misreading as a property
of the FEATURE — carries the derivation instead.

**Goldens.** `tests/conformance/2023/pb523_linage_margins_on_the_medium.cob` writes two files (the
record-sequential AFTER-ADVANCING arm and the LINE SEQUENTIAL arm), closes them and reads them back AS LINE
SEQUENTIAL, so each DISPLAYed index is a physical line number: A05 / A11 / A12 and B04 / B05 / B11.
`tests/conformance/85/pb523_linage_margins_on_the_medium_85.cob` asserts the same page at the earliest
supported edition; LINE SEQUENTIAL is COBOL-2023 only, so it reads the medium one character at a time and
pins `LEN=0036, A@=0009, B@=0025, C@=0031` against the counter-only reading's
`LEN=0020, A@=0003, B@=0009, C@=0015` — all four values differ, so no arithmetic accident passes it.

**Four NIST goldens moved, and the NIST programs themselves are why.** SQ201M, SQ208M, SQ209M and SQ210M all
write their CCVS report through a `PRINT-FILE` whose FD carries a LINAGE clause with margins, so their
layouts change. Every difference is a blank-line count or a removed form feed; not one PASS/FAIL line and not
one LINAGE-COUNTER value moved. The re-baseline is justified by the CCVS programs' OWN visual-check text,
which the old goldens contradicted and the new ones satisfy exactly: SQ201M asks for 50 body lines "FOLLOWED
BY 16 TOP AND BOTTOM BLANK LINES" (LINAGE 50 TOP 10 BOTTOM 6 — the old golden ran three pages together as
150 consecutive lines); SQ209M for "TWO BLANK LINES SHOULD FOLLOW … IT SHOULD BE THREE LINES BELOW THE
PREVIOUS LINE" (TOP 2 BOTTOM 0); SQ208M for a first page "PRECEDED BY 2 BLANK LINES, AND … FOLLOWED BY 4
BLANK LINES" with succeeding pages "SEPARATED BY 3 BLANK LINES"; SQ210M for pages "SEPARATED BY 5 BLANK
LINES" (TOP 5). ⚠ SQ209M was NOT on the checkpoint's list of goldens to move and was found by grepping the
NIST corpus for a LINAGE FD rather than by trusting the list.

**Rows closed** (batch `pb523-linage-margins-on-the-medium`, GAP 2643 → 2638): GR-13.18.34.4-1, -4, -5, -8
and GR-14.9.51.4-26, all PARTIAL/DIVERGES → CONFORMS. GR-14.9.51.4-26 needed one more fixture than the
margins alone: arm a)'s BEFORE-phrase ordering ("the logical record is presented and the device is
repositioned") had been exercised only by nist:SQ201M and now has `Bytes_OverflowWithBeforePhrase_
PresentsThenRepositions`.

**Two findings outside this mechanism, recorded and not folded in.** (1) §14.9.27.3 SR2 — "the EXTEND phrase
shall be specified only if … the LINAGE clause is not specified in the file description entry" — is not
diagnosed anywhere; `EndLinagePage` is what keeps that source off a stale page model. (2)
`SequentialConnector.CloseCore` writes the print stream's closing newline unconditionally on any connector
that has seen a print-control WRITE, so a file whose LAST write carried a BEFORE phrase ends with one blank
line the program never travelled; `_afterAdvancing` answers two questions at once ("is this a print file"
and "is the current line unterminated"). Both are invisible to every existing gate.
