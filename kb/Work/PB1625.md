# PB1625

Filed 2026-09-26 by the train-63 lander from the w62l (PB1592) implementer's lead 2.

**What.** `src/Cobol.Net.Frontend/Expressions/BitString.cs:15` says its fold operators "mirror the runtime
`CobolNet.Runtime.CobolBool` kernel EXACTLY", and that the ALGORITHM is shared, not the code. The reason given was
that the Frontend could not reference the Runtime assembly. PB1592 (train 63) added the `Cobol.Net.Frontend →
Cobol.Net.Runtime` project reference so the compile-time evaluator uses the runtime's one SDIDI engine
(`docs/COBOLNET_PROJECT_ORG_DESIGN.md` §1.4). That reason is gone, so there are now two §8.8.2 kernels, one per
assembly, kept in step by hand.

**Harm today:** none measured. The two kernels agree (the compile-time boolean tests pin the Frontend copy). It is
`process_only` because the harm is future drift: a §8.8.2 fix landed in one kernel and not the other would make a
`>>IF` boolean expression disagree with the same expression at run time. That is the two-arm shape.

**Fix shape (CLAUDE.md rule 5).** Consolidate `BitString`'s positionwise ops, `Not`, and shifts onto `CobolBool`, or
onto a shared kernel `CobolBool` exposes. Keep `BitString` only as the compile-time value type if its API earns it.
A drift test must pin that no second implementation of the rule-8/9/10 extension semantics exists. Code sites:
`BitString.cs` (the fold operators), `CobolBool` in `src/Cobol.Net.Runtime`.
