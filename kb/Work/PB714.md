# PB714 — SORT/MERGE — the "as if" OPEN that drops half of what it is as-if of

Found 2026-09-05 by the `PB683` implementer (report, "New defects found", (b)) while checking its own
`SortEmitter` comment against GR12/GR15. Confirmed here by following the emitted call to the registry.

## The facts

- **The rules, both checked.**
  - `cite.py --check 14.9.40.4 "SHARING WITH READ ONLY"` → `OK §14.9.40.4 12)`: *"If the file-control entry for
    the file has a SHARING clause with the ALL phrase, the initiation is performed as if an OPEN statement with
    the INPUT phrase and the SHARING WITH READ ONLY phrase had been executed; otherwise, the initiation is
    performed as if an OPEN statement with the INPUT phrase and without a SHARING phrase is executed."*
  - `cite.py --check 14.9.40.4 "the initiation is performed as if an OPEN statement with the OUTPUT and SHARING
    WITH NO OTHER phrases had been executed"` → `OK §14.9.40.4 15)`.
  - MERGE carries the identical pair: `--find` on both texts returns `§14.9.24.4 7) a)` (USING) and
    `§14.9.24.4 12)` (GIVING) alongside the SORT rules. Four rules, one emitter.
  - What the overrides mean: §9.1.15 2) — read only *"restricts concurrent access … to input mode"*, and an
    associating open *"will be unsuccessful if the physical file is associated with another file connector whose
    open mode is other than input"*; §9.1.15 1) — no other *"specifies exclusive access"*, unsuccessful if the
    file is currently open through any other connector. Both `--check`ed OK against §9.1.15.
- **What is emitted.** `src/Cobol.Net.Compiler/CodeGen/Verbs/SortEmitter.cs:98` renders
  `RuntimeApi.FileOpenInput(...)` for the USING transfer and `:130` renders `RuntimeApi.FileOpenOutput(...)` for
  the GIVING transfer — the comments on both lines cite GR12a / GR15a correctly. The renderers
  (`CodeGen/Roslyn/RuntimeApi.cs:873, :877`) produce `CobolFile.OpenInput` / `CobolFile.OpenOutput`, whose bodies
  (`src/Cobol.Net.Runtime/IO/CobolFile.cs:70-73`) are `_reg.Open(name, FileOpenMode.Input|Output, …)` — an entry
  point with **no sharing parameter at all**.
- **Where it is lost.** `FileRegistry.SharedOpenAttempt` (`FileRegistry.cs:797-799`) resolves
  `sharing = sharingOverride ?? (file-control entry's SHARING clause ?? ImplementorDefaultSharing)`. Reached
  through `Open`, `sharingOverride` is null, so the USING file is arbitrated under its OWN clause (`ALL OTHER`,
  the very case GR12 a) singles out) instead of read only, and the GIVING file is arbitrated under whatever it
  declares — never exclusive.
- **The entry already exists and is not used.** `FileRegistry.OpenShared` (`FileRegistry.cs:740`) takes
  `hasSharingOverride` / `sharingOverride` and funnels into the same `OpenCore`; `RuntimeApi.FileOpenShared`
  (`RuntimeApi.cs:924`) renders it. The explicit `OPEN … SHARING` path uses both. Only the implicit opens do not.

## Why it matters

The wrong answer is a MISSING refusal, which is the hardest kind to notice: a second connector opens the sorted
GIVING file while SORT is writing it, `Conflicts` says yes because the registry was told the wrong sharing mode,
and the program reads a half-written result with status `00` where §9.1.13.9 item 1 requires `61`. The same on
the USING side lets another connector open the input file I-O or EXTEND *during* the sort. Nothing is logged and
no golden fails, because every observable is a status that was never produced. It is also the second half of
PB683's own lesson (`feedback_two_arm_dispatch`): PB683 moved governance into `FileRegistry` "where the OPEN's
phrase is visible" — and the SORT/MERGE arm has no phrase to make visible, because the emitter never renders one.

## The fix shape

Render the override the general rules name. `EmitUsingFile` emits `RuntimeApi.FileOpenShared(f, INPUT,
sharing: the file-control entry has SHARING ALL ? ReadOnly : none)` — the GR12 a) / GR7 a) conditional is a
compile-time fact, the file-control entry is in hand at emit time — and `EmitGivingFile` emits
`FileOpenShared(f, OUTPUT, NoOther)` unconditionally (GR15 a) / GR12 a) have no conditional). Prefer the shape
that makes the next implicit OPEN automatic: the four rules are the complete set of "as if an OPEN …
SHARING …" statements in the standard (`cite.py --find "as if an OPEN statement"` returns exactly
§14.9.24.4 7)/12) and §14.9.40.4 12)/15)), so give the emitter ONE `ImplicitOpen(file, mode, sharing)` helper
that both verbs and both directions call, and a drift test asserting no `FileOpenInput`/`FileOpenOutput` renderer
survives in `SortEmitter`. Goldens: a USING file declared `SHARING WITH ALL OTHER` that a second connector tries
to open I-O during the sort (expect 61), and a GIVING file a second connector tries to open INPUT (expect 61) —
both of which pass today for the wrong reason.

## Siblings

MERGE is the same emitter and the same defect, not a separate one: `EmitUsingFile` / `EmitGivingFile` serve both
verbs (`SortEmitter.cs:80, :86, :120`), so one fix closes §14.9.24.4 GR7 a) and GR12 a) with the SORT pair.
Beyond them, sweep the other implicit-OPEN-like initiations for the same dropped phrase — any place codegen
renders a plain `CobolFile.Open*` on behalf of a statement whose general rules describe an "as if" OPEN.

## Landed

Landed 2026-09-06 on `worktree-agent-ad540d53ac29c7d1a` off origin/main `c34f01ad`. The note held on today's tree
in every particular except two spellings: the emitter's methods are `EmitInputFile` / `EmitGivingFile` (the note
called the first `EmitUsingFile`), and the FILE STATUS store the note did not mention was missing from the
implicit OPEN as well — see "What the note did not name" below.

**Reproduced first.** `SORT S ... USING F-IN GIVING F-OUT` with `F-IN` declaring `SHARING WITH ALL OTHER` and a
second connector on the same physical file held `OPEN EXTEND` across the SORT: before, `IN-ST=00` and all three
records sorted; after, the implicit OPEN answers `'61'` and the GIVING file comes out empty.

**The fix is one mechanism.** `SortEmitter.EmitImplicitOpen(file, mode, sharing, ruleComment)` renders every one
of the four *"as if an OPEN statement …"* initiations — `EmitInputFile` and `EmitGivingFile` each serve SORT and
MERGE, so the verb axis needs no arm — and a non-null sharing mode renders `CobolFile.OpenShared`, the same entry
the explicit `OPEN … SHARING` uses, through the same `OpenCore` and the same Table 19. The USING arm's condition
(§14.9.40.4 GR12 a) / §14.9.24.4 GR7 a): *has a SHARING clause with the ALL phrase*) is a compile-time fact of
the file control entry, decided in the emitter; the *otherwise* arm renders the PLAIN entry rather than a
sharing entry with the override switched off, because the standard says the absence of the phrase leaves the
mode *"completely determined by the SHARING clause … in the file control entry"* and the phrase-bearing entry
additionally registers an unregistered connector's record-locking posture (kb/Work PB316's two arms). The GIVING
arm (§14.9.40.4 GR15 a) / §14.9.24.4 GR12 a)) is unconditional `NoOther`.

**Drift is compile-enforced.** `RuntimeApi.FileOpenInput` and `FileOpenOutput` — the two renderers whose whole
defect was the parameter they did not take — are DELETED, with a ⛔ block in their place. No phrase-less
implicit-open renderer survives for a fifth implicit open to reach by accident, which is stronger than the drift
test the fix shape proposed.

**What the note did not name.** The implicit OPEN also skipped `EmitStoreFileStatus`, which the explicit OPEN
does not. §9.1.13.1 sets the I-O status *"during the execution of a … OPEN … statement and prior to the
execution of … any applicable exception processing statements"* and §12.4.5.8.4 GR1 updates the FILE STATUS item
with it, so the USE procedure GR12 a) / GR15 a) invoke ON THE NEXT EMITTED LINE was seeing a stale value. It is
the same half-rendered as-if OPEN and rides the same helper — and it is what makes the `'61'` readable from
COBOL at all.

**What is still not observable.** `SHARING WITH NO OTHER`'s exclusive half cannot be reached from a
single-threaded COBOL program: no statement of the program's runs between the implicit OPEN and the implicit
CLOSE, and every Table 19 *Open request* row whose open mode is OUTPUT is *Unsuccessful open* in all five
columns anyway (§9.1.13.9 1) e)), so the GIVING override cannot change an INCOMING arbitration either. The note's
harm paragraph — a second connector opening the GIVING file *while* SORT writes it — is therefore a
cross-run-unit harm, not a within-run-unit one. The value the emitter now renders is pinned at the registry, on
the exact call it emits, by
`CobolFileLockTests.SortGivingImplicitOpen_TakesNoOther_AndLocksOutEveryOtherConnector_GR15a`.

**Goldens** (all `tests/conformance/2023/`, in the manifest, expected values derived from the spec before they
were observed): `pb714_sort_using_sharing_read_only` (PB714SRO — three legs: the ALL entry refused against an
EXTEND connector `'61'`; the same entry permitted against an INPUT connector, which is what makes the override
READ ONLY and not NO OTHER; and a `SHARING WITH NO OTHER` entry refused against that same INPUT connector, which
is what makes the override CONDITIONAL — legs 2 and 3 differ only in the USING file's SHARING clause and answer
oppositely); `pb714_merge_using_sharing_read_only` (PB714MRO — §14.9.24.4 GR7 a) and GR12 a));
`pb714_sort_giving_open_status` (PB714SGO — §14.9.40.4 GR15 a), plus §14.9.27.4 GR25's *"the file is not
affected"* on the refused implicit OPEN OUTPUT).

**Rows.** None. `inventory_rows` is still empty and no `record_verdicts` batch was written, so **GAP delta 0**.
GR-14.9.40.4-12/15 and GR-14.9.24.4-7/12 are each a THREE-part rule (initiate / transfer / terminate) whose
initiation half is what this evidence covers, and each also carries the EC-SORT-MERGE-FILE-OPEN obligation that
§18.16 leaves checking-off; GR-9.1.15-2's *"subsequent requests … in a mode other than input will be
unsuccessful"* and *"Record locks are in effect"* are unobserved here, and GR-12.4.5.8.4-1 is a rule over every
I-O statement. Recording any of them as CONFORMS would be a verdict without its evidence. The adjudication lane
can take all nine rows with this evidence now on the tree.

**Docs.** `COBOLNET_FILES_DESIGN.md` **D22** (new) states the mechanism, and **D14** is corrected: its sentence
*"those route through `CobolFile.OpenInput`/`OpenOutput` → `Open` → `OpenCore` with no arm of their own"*
recorded the half that was true (they ARE arbitrated) as though it were the whole, which is how the two
overrides went unrendered for as long as they did.
