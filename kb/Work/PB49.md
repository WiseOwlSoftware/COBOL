# PB49 — LANDED — two string-image visitors, now held in their intended relationship

> ⚙ **NAMED BY THE PHASE-B EVIDENCE FILE THAT FOUND [[PB25]], AND NOT BUILT WHEN PB25 LANDED.**
> `docs/rearchitecture/evidence/PHASE-B-15.32-15.44-findings.md` prescribed the fix shape PB25 used *and* the
> guard that should ship with it: "add a drift test asserting every `BoundOperand` leaf renders identically
> through the intrinsic-argument channel and the DISPLAY channel." The fix landed; the guard did not.

## WHY THIS IS THE ROOT CAUSE AND NOT A NICETY

PB25 was not a missing case — it was **one rule written in two places, with only one copy right**.
`OperandText.AsString` (the DISPLAY / MOVE / STRING channel) materialises a figurative constant PCS-aware per
§8.3.3.6.4 GR3 and cites the rule; `IntrinsicRenderer.StrArgVisitor` is a SECOND string-image visitor beside it
that delegates only its `BoundFieldOperand` leaf and answered the literal-shaped leaves itself — so it inherited
neither the figurative arm nor the ALL-literal arm, and legal programs aborted at RUN TIME.

PB25 routed the two offending leaves to `AsString`. **Nothing stops the next leaf from diverging the same way.**
The visitor is exhaustive over `IBoundOperandVisitor<string>`, so a NEW `BoundOperand` leaf is a compile error —
but an existing leaf answered *differently* by the two channels is not, and that is exactly the shape that
produced this defect. `feedback_one_rule_one_place` says the extraction IS the fix; here the extraction is
partial, and only a test can say so.

## ▶ WHAT TO CHECK FIRST

⚠ **The two channels are NOT required to agree on every leaf, and a test that assumed so would be wrong.**
`StrArgVisitor`'s `BoundComputedOperand` arm deliberately re-enters the instance `RenderString` for a nested
string-class intrinsic, where `AsString`'s corresponding arm is a loud stage for a non-intrinsic computed
operand — a real, documented difference. So the guard must be written per-leaf with the intended answer stated,
not as a blanket "these two functions are equal".
⚠ Check the same question for the NUMERIC channels (`OperandText.NumericIntrinsicText` vs `NumericRenderer`)
before writing only the string one — [[feedback_two_arm_dispatch]], and PB25 already found the sibling copy of
its own mistake one layer away in the LENGTH binder.

## ⚙ LANDED 2026-08-06 — `OperandStringChannelDriftTests`

Built exactly as this note required: **per-leaf, with the intended answer stated**, never a blanket "these two
functions are equal". Three buckets, and the third is the one that makes it complete:

- **DELEGATED** — `BoundFieldOperand`, `BoundFigurative`, `BoundAllLiteral` must route to
  `OperandText.AsString`. That is PB25's fix, and re-implementing any of them locally is what rots.
- **DIVERGENT BY DESIGN** — `BoundNumericLiteral` and `BoundBoolOperand` must stay LOUD in the intrinsic-argument
  channel. ⭐ This direction matters as much as the first: "fixing" them into agreement with the DISPLAY channel
  would silently ADMIT an operand §15.3 excludes — the inverse of PB25 and just as quiet.
- **UNCLASSIFIED IS A FAILURE** — every leaf both channels implement must sit in one bucket or the other, so a
  NEW `BoundOperand` leaf forces a decision. Leaving one undecided is precisely how PB25's figurative arm went
  missing.

**PROVEN IN THE FAILING DIRECTION**: re-introducing PB25 (replacing the `BoundFigurative` delegation with a local
literal) reds the guard on that exact row ([[feedback_green_gates_arent_evidence]]).

## ⭐ THE NUMERIC HALF OF THIS NOTE HAD AN ANSWER, NOT A GUARD

The note said to "check the same question for the NUMERIC channels (`OperandText.NumericIntrinsicText` vs
`NumericRenderer`) before writing only the string one". Measured: the compiler has **four**
`IBoundOperandVisitor` implementations — `StrArgVisitor` and `AsStringVisitor` (string), `IsStringVisitor` (a
bool classifier), and `NumericRenderer`. **`NumericRenderer` is the only numeric one**, and
`NumericIntrinsicText` is a helper it is called from rather than a parallel visitor. **There is no numeric twin,
so there is no numeric drift to guard** — the premise was worth checking and did not hold
([[feedback_validate_the_premise_not_only_the_rule]]). A test now asserts the count is exactly one, so if a
second numeric channel ever appears, that answer expires loudly instead of silently.

⚠ Gate: this change is TEST-ONLY — no compiler source altered — so the wave is the unit suite (3992/3992) plus
characterization (33/33). A full battery would measure a tree identical to PB33's, which was ALL GREEN.
