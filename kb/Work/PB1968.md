# PB1968

## Landed (wave 1029, group C — with kb/Work PB2113)

Re-probed: `DISPLAY X (- - 2)` compiled and printed X (2) on main d5fc9c998's build. PB2113 made a subscript an
ordinary parsed `arithmeticExpression` (the SUBSCRIPT-mode token capture is gone), so ExpressionFormationPass's ONE
Table 3 screen reaches it with no subscript arm of its own: COBOLNET1719 at all four editions. Witness:
`negative/pb1968-subscript-unary-unary` (reject-at 85 2002 2014 2023). The same holds for every other formation
screen over a subscript or a keyword-omitted argument list, which are now nodes of the one tree.

Found by wave 1014 group S (PB1455/PB1426 gave ExpressionFormationPass its first SUBSCRIPT-capture arm), filed by the
train-1014 lander. A sibling escape of kb/Work PB158 (landed: Table 3's invalid cells gated in both walkers), which
did not reach subscript captures.

## Rule

§8.8.1.2 4): "The ways in which identifiers, literals, operators, and parentheses may be combined in arithmetic
expressions are summarized in Table 3" (`cite.py --check 8.8.1.2 "Table 3"` -> OK §8.8.1.2 4)); a unary operator
followed by a unary operator is an invalid cell.

## Repro

`scratchpad\w1014s\probe\n7.cob` (orchestrator scratchpad of session e8598e10): `DISPLAY X (- - 2)` compiles and
prints `X (2)` at every edition; expected a refusal (COBOLNET code of the Table 3 screen, `expression-formation-pair`).

## Code site

`src/Cobol.Net.Compiler/Validation/ExpressionFormationPass.cs` has no SUBSCRIPT-capture arm for Table 3 (PB1455's
`ScreenCapturedGroup` screens only the qualifier order), and `src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs#RenderSegment`
takes a fast path that never builds an arithmetic tree. Same blind spot as every bind-time FRAGMENT re-parse: the
pass never sees them, so the fix is the screen at the capture (token run) or a pass over the re-parsed fragment.
