# PB4970 - semgrep verify names DiagnosticCatalog.cs as unreadable

**Sites:** `scripts/semgrep/verify.py#unreadable_files`, `scripts/semgrep/verify.py#WHOLE_FILE_UNREADABLE`,
`scripts/semgrep/verify.py#classify_errors`, `src/WiseOwl.Cobol.Editions/Diagnostics/DiagnosticCatalog.cs`

Observed in an earlier session on 2026-11-07: `python scripts/semgrep/verify.py` failed with an UNNAMED line for
`DiagnosticCatalog.cs`. Re-probe the same day: `semgrep scan --pattern 'class $C { ... }' --lang csharp --json` on that
file alone returns no error, and so does `--config scripts/semgrep/invariants.yml`. A whole-tree run of `verify.py` did
not finish in 600 s on this host. The likeliest mechanism is a per-file Timeout under the whole-tree load, on the largest
C# file. `unreadable_files` counts every error that is not a partial parse as "whole", so a timeout would show up as an
unreadable file.

Expected: reproduce the whole-tree run and record the error's `type`. If it is a timeout, report a timeout as its own
failure with its own message, not as an unreadable file, and fix the cause (semgrep's `--timeout`, or how the run is
split) at its root. If it is a real parse failure, name the file in WHOLE_FILE_UNREADABLE with its first failing member.

**Seen again (2026-11-08, w20261930h-PB4958-report.md).** `python scripts/semgrep/verify.py` FAILed on both PB4958's tree and its base with the same "UNNAMED ... DiagnosticCatalog.cs: semgrep cannot read it at all" line, untouched by that change: the mechanism above is a standing red, not a one-off.
