# PB196 — OVERRIDE is accepted and discarded

## ⛔ The filed premise was wrong, and the probe is why this note says something else

The finding this note was opened from stated: *"OVERRIDE missing from `deleteFileStatement` (CobolIO.g4) and
present in the `cobolWord` alternation → binds as file-name. `rejects_legal_source`."* **Measured 2026-08-31,
none of that holds.**

`CobolIO.g4:513` reads:

```antlr
deleteFileStatement
    : DELETE FILE OVERRIDE? fileName
```

and the probe compiles and runs:

```cobol
DELETE FILE OVERRIDE F-A. DISPLAY "OVR=" A-ST.     *> compiles at --std 2023; prints OVR=00
```

So the phrase is neither missing nor mis-bound as a file-name, and no legal source is rejected. Recorded because
implementing from the filed premise would have "fixed" a grammar that is already correct
([[feedback_validate_the_premise_not_only_the_rule]] — check what the construct can syntactically BE before
believing a finding about it).

## The real defect

`BoundKeyedDeleteFile` (`Binding/Bound/BoundKeyedIo.cs:87`) is

```csharp
public sealed record BoundKeyedDeleteFile(
    FileModel File, IReadOnlyList<BoundStatement>? OnException, IReadOnlyList<BoundStatement>? NotOnException)
    : BoundStatement { public RetrySpec? Retry { get; init; } }
```

— **no `Override`**. The parser consumes the token and the binder drops it on the floor. §14.9.10.4 GR18's
second sentence ("If the OVERRIDE phrase is specified, the file attributes are not checked") therefore has no
carrier below the parse tree, and neither does the distinction GR18's first sentence draws.

## Why it is currently harmless, and why that is not a reason to leave it

Under the [[PB192]] determination COBOL.NET's validated fixed-file-attribute set for DELETE FILE is **empty**, so
OVERRIDE's only specified effect — skipping a check — skips a check that never runs. **The observable behaviour
is right by coincidence, not by construction.** The moment anything is validated (or the [[PB193]] attribute
store lands and this path reuses it), a program that wrote OVERRIDE to opt out of checking will be checked
anyway, silently, and the source will look correct. That is the shape of defect worth fixing before it can bite,
not after.

It is also what holds `GR-14.9.10.4-18` at NOT-IMPLEMENTED: the row cannot move while the phrase has no
representation, whatever the attribute set is.

⚖ **Why the flags say `process_only` and not a harm flag.** The register ranks on what a defect DOES to a user's
program, and by the argument above this one does **nothing** today — so claiming `wrong_answer` would inflate it
past defects that are actively returning wrong values. `process_only` is the honest reading of the register's own
question, and it is NOT a judgement that the defect does not matter: the note is filed precisely because the
harmlessness is contingent on [[PB192]]'s empty set, and the flag must be re-read the moment [[PB193]]'s store
lands.

## Fix

Carry `Override` on `BoundKeyedDeleteFile`, set it in `KeyedIoBinder` from the parse tree, and thread it to the
runtime entry so the (currently empty) validation is genuinely bypassed rather than vacuously satisfied. Golden:
`DELETE FILE OVERRIDE` and plain `DELETE FILE` over a mismatched connector, asserted to agree today and to
DIVERGE the moment a non-empty set exists — plus a bind-level assertion that the phrase reaches the bound tree,
since a runtime-only golden cannot tell "bypassed" from "nothing to bypass". Lands with the cluster-E work.

**Checked and NOT a defect:** `OVERRIDE` also appears in the edition-shared `cobolWord` alternation
(`CobolWords.g4:70`), which would make a file actually NAMED `OVERRIDE` collide with the phrase. It is
unreachable: `OVERRIDE` is §8.9-reserved from 2002 onward, and DELETE FILE is a 2023 statement — the only
edition where `OVERRIDE` is a user word is '85, where the statement does not exist.
