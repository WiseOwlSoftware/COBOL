# PB637 — LANDED — a total argument in a partial function's landing (ANNUITY, SDIDI lane)

Found 2026-09-05 by the `PB254` implementer (report §"New defects" (C)), whose sweep of every `IntArg(` site
against its argument rule left this one flagged rather than classified. Filed as the reading it needs.

## The site

`src/Cobol.Net.Compiler/CodeGen/Emit/IntrinsicRenderer.cs` (`:828` on main after train 5):
`"Annuity" => Dec(RuntimeApi.Intrinsic("AnnuityDec", $"{mode}, {DecArg(ic, 0)}, {IntArg(ic, 1)}"))` — argument-2
through `AsInt`, the narrowing that is correct only for a PARTIAL function (PB254's category rule, now written on
`AsInt`/`AsIntWide` and held by `IntrinsicCarrierAgreementDriftTests`).

## The rule, and the question

§15.9.3 r3: "Argument-2 shall be a positive integer" (`OK §15.9.3 3)`) — sign only, like RANDOM's seed
([[PB636]]). §15.9.4 defines the returned value by an equivalent arithmetic expression over argument-1 and
argument-2 (`cite.py --check 15.9.4 "The equivalent arithmetic expression is"` — run it first) — which, under a
standard arithmetic mode, §15.4.1 r1 makes exact. The question that classifies the argument: does an enormous n
make the RETURNED VALUE incorrect under §15.3 r14 ("an incorrect value for that argument … according to the rules
specified in the function definition"), the way FACTORIAL's unrepresentable result does above 33!? If the
expression's value for huge n is finite and representable (it converges toward argument-1 for |1 + a1| > 1 and
the power term underflows to a defined limit), the argument is TOTAL and the fix is PB636's: an `Int128` intake
and a body that handles the power term without materialising it. If the standard's expression genuinely has no
representable value for some n, the argument is BOUNDED and the narrowing is correct — then say so in the code
comment with the derivation, so the next sweep does not re-flag it.

## Outcome

Either a fix in PB636's shape (goldens at the 19-digit and 31-digit n under armed checking) or a cited comment on
the arm and a row in the BOUNDED table PB254 wrote in `DESIGN-runtime-library.md` §2.7.

## Landed 2026-10-27 (wave 20261027, group C)

Re-probed on the implementer's own build before the fix: `ANNUITY(0, N)` with `N PIC 9(25) VALUE 10^20` under
ARITHMETIC IS STANDARD-DECIMAL stored 0 with checking off and terminated the run unit with EC-ARGUMENT-FUNCTION
under `>>TURN EC-ARGUMENT-FUNCTION CHECKING ON` (the note's p637d/p637e), exactly as filed.

THE CLASSIFICATION (the question the note left open): TOTAL. §15.9.3 r3 is a sign and integer-ness rule, so §15.3
r14 has no incorrect argument value to fire on for a large n (`cite.py --check` of 15.9.3, 15.9.4, 15.3 and
15.4.1 all OK). The value is the returned-value rule's, and §15.4.1 r1 makes the standard-decimal result EQUAL the
equivalent expression's. Two consequences, both measured:

- Rate 0: the expression is `1 / argument-2` (§15.9.4 r1a), representable for every n; 10^20 gives 1E-20.
- Rate > 0: the expression's own `(1 + rate) ** n` leaves the decimal128 range once n·ln(1+rate) passes about
  14 000, which is the EXPRESSION'S size condition (EC-SIZE-OVERFLOW, §8.8.1.5.2 r2, raised inside `CobolDec.Pow`).
  The body already raised it at n = 10^6 (inside `long`); the narrowing made n = 10^20 a different, width-dependent
  condition. **The adjudication's expected value of 0.05 for ANNUITY(0.05, 10^20) is overturned**: 0.05 is the
  mathematical limit, but §15.4.1 owes the value of the written expression, and that expression has none there. A
  small rate keeps a finite value (rate 1E-30, n 10^20 = 1.00000000005E-20), which the narrow intake could not reach.

THE FIX is the CARRIER (PB254/PB636 doctrine, corrected by branch review R1-1): `CobolIntrinsics.AnnuityDec(CobolRounding,
CobolDec, CobolDec)`. The count stays the SDIDI integer the type-6 position intake produced (`IntegerArgUnboundedDec`),
because an SDIDI integer reaches past `Int128` too: the first fix's `Int128` parameter still ended the run unit on
`ANNUITY(0, 10 ** 40)` (EC-SIZE-OVERFLOW from `IntegerArgWideDec`). The `Annuity` arm of `IntrinsicRenderer.RenderDec`
takes `DecArg(ic, 1)`. SIBLING ARM: the dispatch has two ANNUITY lanes,
the SDIDI body (this) and the binary64 body `Annuity(double, double)`, which never narrowed. FACTORIAL's and
COMBINED-DATETIME's `long` Dec bodies stay BOUNDED (their argument rules bound the value).
THE GUARD'S BLIND SPOT, closed: `IntrinsicCarrierAgreementDriftTests.SingleCarrierIntrinsicBodies` paired a body to
its arm by name, so no `…Dec` body (AnnuityDec, FactorialDec) was ever examined; it now maps `{Arm}Dec` onto the arm's
entry (FactorialDec joins Factorial). ANNUITY itself has no native integer parameter any more, so
`IntegerArgumentsThatRideTheSdidi_TakeNoNativeIntake` holds its arm free of any native intake and its body free of any
`long`/`Int128` parameter (the detector's self-test carries the `long`, `Int128` and SDIDI forms).

Goldens: `conformance:cases/15.9.3-Argument-rules/pb637_annuity_total_periods` (checking ON, armed by a
non-positive count; 19-digit, 25-digit and 31-digit n; §15.4.1 NOTE 2's relation; the tiny-rate value; the
size condition on both sides of the 64-bit window) and `.../pb637_annuity_total_periods_unchecked` (the silent-0
leg). No `reject-at:` negative: no syntax is introduced. Unit: `CobolIntrinsicsDecTests.AnnuityDec_*`.
