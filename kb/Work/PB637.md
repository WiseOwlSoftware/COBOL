## The site

`"Annuity" => Dec(RuntimeApi.Intrinsic("AnnuityDec", $"{mode}, {DecArg(ic, 0)}, {IntArg(ic, 1)}"))` — argument-2

## The rule, and the question

§15.9.3 r3: "Argument-2 shall be a positive integer" (`OK §15.9.3 3)`) — sign only, like RANDOM's seed
([[PB636]]). §15.9.4 defines the returned value by an equivalent arithmetic expression over argument-1 and
argument-2 (`cite.py --check 15.9.4 "The equivalent arithmetic expression is"` — run it first) — which, under a
standard arithmetic mode, §15.4.1 r1 makes exact. The question that classifies the argument: does an enormous n
make the RETURNED VALUE incorrect under §15.3 r14 ("an incorrect value for that argument … according to the rules
specified in the function definition"), the way FACTORIAL's unrepresentable result does above 33!? If the
expression's value for huge n is finite and representable (it converges toward argument-1 for |1 + a1| > 1 and
the power term underflows to a defined limit), the argument is TOTAL and the fix is PB636's: an `Int128` intake
and a body that handles the power term without materialising it. If the standard's expression genuinely has no
representable value for some n, the argument is BOUNDED and the narrowing is correct — then say so in the code
comment with the derivation, so the next sweep does not re-flag it.

Either a fix in PB636's shape (goldens at the 19-digit and 31-digit n under armed checking) or a cited comment on
the arm and a row in the BOUNDED table PB254 wrote in `DESIGN-runtime-library.md` §2.7.
