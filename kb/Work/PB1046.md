# PB1046 — OPEN

## Measured
`01 DL TYPE DETAIL … 05 PV COLUMN 5 PIC X(3) SOURCE W.` then `MOVE PV TO W` in the procedure division →
`error COBOLNET1639: 'PV' is not defined — no declaration in this source element gives the name 'PV'` — in the
declaring program itself and in a contained program under `RD RR GLOBAL`. `DataBinder.IsReportSectionOnlyName` reads
only the unit's own reports and is asked only by the CONTROL / PRESENT WHEN / SUM / SOURCE screens.

## What the analyst owes
Derive from §13.15 (report group description entry) and the reference rules whether a printable item's data-name
may be referenced in the procedure division. If yes, it is a rejects-legal-source defect of the name registry
(report-section names never registered); if no, the refusal should cite the rule that confines the name, not
§8.4.2.1's 'not defined', and the contained-program case should say the same. Cite with `--check`. Convert this note
to `kind: defect` with the answer.

### Row SR-13.15.3-7 — PARTIAL (no separate finding; the adjudicator's / refuter's record)

Code location: `src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs#ReportSectionOnlyNames; src/Cobol.Net.Compiler/Binding/ReportGroupResolution.cs`

SR7 has two halves. The first ('The data-name format of the entry-name clause shall be specified when the data-name is referenced in a GENERATE statement, a USE BEFORE REPORTING statement, as a qualifier for a SUM counter, in the UPON phrase ..., or as an operand in a SUM clause') is satisfied by construction: those references resolve by name through ReportGroupResolution and the SUM resolvers, and an unnamed entry has no name to resolve. The second ('The data-name shall not be referenced in any other way') is enforced only incidentally. Report-section names never enter ByName, so a procedure reference fails RESOLUTION: probe sr7move `DISPLAY PX` (PX a printable report item) and sr7grp `DISPLAY D1` (a report group) both draw COBOLNET1639 "'PX' is not defined ... no declaration in this source element gives the name". That is the right verdict under the wrong rule, and the message is false because PX IS declared. The open analysis kb/Work PB1046 owns exactly this ('either the name is referenceable there and the compiler rejects legal source, or it is not and the diagnostic names the wrong rule'), so no new finding is filed here. cite.py --check 13.15.3 'The data-name shall not be referenced in any other way' -> OK §13.15.3 7). PARTIAL: the prohibition is not diagnosed as SR7, and its interaction with §13.18.54 sum-counter references is PB1046's open question.
