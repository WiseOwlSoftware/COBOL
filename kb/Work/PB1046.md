# PB1046 — LANDED

## Measured
`01 DL TYPE DETAIL … 05 PV COLUMN 5 PIC X(3) SOURCE W.` then `MOVE PV TO W` in the procedure division →
`error COBOLNET1639: 'PV' is not defined — no declaration in this source element gives the name 'PV'` — in the
declaring program itself and in a contained program under `RD RR GLOBAL`. `DataBinder.IsReportSectionOnlyName` reads
only the unit's own reports and is asked only by the CONTROL / PRESENT WHEN / SUM / SOURCE screens.

## What the analyst owes
Derive from §13.15 (report group description entry) and the reference rules whether a printable item's data-name
may be referenced in the procedure division. If yes, it is a rejects-legal-source defect of the name registry
(report-section names never registered); if no, the refusal should cite the rule that confines the name, not
§8.4.2.1's 'not defined', and the contained-program case should say the same. Cite with `--check`. Convert this note
to `kind: defect` with the answer.

### Row SR-13.15.3-7 — PARTIAL (no separate finding; the adjudicator's / refuter's record)

Code location: `src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs#ReportSectionOnlyNames; src/Cobol.Net.Compiler/Binding/ReportGroupResolution.cs`

SR7 has two halves. The first ('The data-name format of the entry-name clause shall be specified when the data-name is referenced in a GENERATE statement, a USE BEFORE REPORTING statement, as a qualifier for a SUM counter, in the UPON phrase ..., or as an operand in a SUM clause') is satisfied by construction: those references resolve by name through ReportGroupResolution and the SUM resolvers, and an unnamed entry has no name to resolve. The second ('The data-name shall not be referenced in any other way') is enforced only incidentally. Report-section names never enter ByName, so a procedure reference fails RESOLUTION: probe sr7move `DISPLAY PX` (PX a printable report item) and sr7grp `DISPLAY D1` (a report group) both draw COBOLNET1639 "'PX' is not defined ... no declaration in this source element gives the name". That is the right verdict under the wrong rule, and the message is false because PX IS declared. The open analysis kb/Work PB1046 owns exactly this ('either the name is referenceable there and the compiler rejects legal source, or it is not and the diagnostic names the wrong rule'), so no new finding is filed here. cite.py --check 13.15.3 'The data-name shall not be referenced in any other way' -> OK §13.15.3 7). PARTIAL: the prohibition is not diagnosed as SR7, and its interaction with §13.18.54 sum-counter references is PB1046's open question.

## Landed (w20261501, 2026-10-25) - a report section entry's data-name is refused as a REPORT ITEM, not told "not defined"

**Answer to the analysis.** Refusing is right (13.8.6.2.3, 13.15.3 SR7 - both `cite.py --check` OK), so the rejects-legal-source branch is out; the defect was the message. Re-probed on the w20261501 build before the fix: `MOVE PV TO W`, `DISPLAY DL`, `DISPLAY PV OF DL [OF RR]`, `DISPLAY PV OF RR` in the declaring program, `DISPLAY PV` / `DISPLAY DL` in a contained program under `RD RR GLOBAL`, `FILE STATUS IS PN`, `RELATIVE KEY IS PN` and `OCCURS ... DEPENDING ON PN` (PV and PN printable items) each drew COBOLNET1639 (or COBOLNET0851 for the ODO) "no declaration ... gives the name", false about a name the report section declares. The sum counter control (`ADD 100 TO SC`, `DISPLAY SC`) compiled and ran, as 13.8.6.2.3 1) requires.

**Mechanism.** One lookup, one refusal. `ReportModel.NamedEntries` (read once off the written entries: name, qualification innermost first ending at the 01, sum-counter flag) feeds `DataBinder.ReportEntriesNamed(name, qualifiers)`, which walks the visible reports (own and GLOBAL containers', nearest source element wins, 8.4.6.2.1 rule 3) with the ONE 8.4.2.2.3 SR4 `QualifierWalk` a sum counter's qualification already used (report-name last). `DataBinder.ReportEntryReferenceRefused` reports COBOLNET5092 (cites 13.8.6.2.3 and 13.15.3 SR7) and is asked by the three arms that said "not defined": `ReferenceResolver.ReportUnidentified` (every procedure division identifier), `DataBinder.ResolveClauseOperand` (FILE STATUS, RELATIVE KEY, LINAGE, APPLY COMMIT; the report section's own ODO is exempt via `inReportSection`) and the data-division ODO lookup. `ReportSectionOnlyNames` and `IsReportSubscriptCounter` now read `NamedEntries` instead of re-walking the entries (one place for "which entries carry a name / a SUM").

**Goldens** (cases/13.8.6.2.3-Report-Items, refusals in wiseowl/diagnostics.json at all four editions): `pb1046-report-item-referenced-in-procedure-division`, `pb1046-report-group-referenced-in-procedure-division`, `pb1046-global-report-item-referenced-in-contained-program`, `pb1046-report-item-referenced-by-file-status`, `pb1046-report-item-as-occurs-depending-object`, and the positive control `pb1046_report_sum_counter_in_contained_program` (prints 0100). Unit: `ReportItemReferenceTests` (22 cases incl. the complement scan that names the three arms).

**Row.** SR-13.15.3-7 PARTIAL -> CONFORMS (`closes_rows`).

**Left alone, recorded.** REDEFINES / RENAMES operands naming a report item draw COBOLNET1654 / COBOLNET1655 ("does not name a preceding entry / an item of the record"): true and correctly ruled, not the false "not defined", so they are not arms of this defect. A contained program's own DATA DIVISION clause naming a container's GLOBAL report item still says "not defined": the container's reports are inherited after the contained data division binds (`BinderDriver.BindUnitData`), so `VisibleReports` does not hold them yet (lead in the report).
