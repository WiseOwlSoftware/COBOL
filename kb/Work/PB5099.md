# PB5099 - a re-gate at an unchanged tree re-runs only what did not pass

**Owner (2026-11-09 23:40):** "This makes no sense. If only one test failed, any retry should test only that one case."

**Sites:** `scripts/gate.py` (the run planner and the GREEN record `enqueue.py land` reads), `scripts/build-local.ps1`.

**Found.** Wave 20261972's implementer (PB5060, worktree wf_14a80b82-683-1) finished its change in 13 minutes and then spent
three hours gating one commit, 6bede3198b (tree fc15c9ace5f9e0c108efced6cd679194098a6ab2). Run 000002 ran all of Conformance
(22,783 passed), Characterization (37 passed) and Unit (40,729 passed) and went RED on ONE case,
`ArchReviewFleetDriftTests.EachFleetInstrument_PassesItsSelfTest(file_census_notes.py)`, a HARNESS NON-OBSERVATION (its
process budget ran out under host load; no output was compared). Run 000003 at the SAME tree waited 1,448 s for a slot and then
re-ran the whole population for 58 minutes (Conformance 1,948 s, Unit 891 s) to turn that one case GREEN; `first-classes`
only ordered the red class first. Both `verdict.json` files record `tree` = `head_tree` = `tree_end` = fc15c9ace5.

**The decision.** THE RULE (owner 2026-10-31) asks that every case the merge group runs on Windows already ran green AT THE
PUSHED HEAD on this host under the same toolchain, not that it ran green in one run. So a re-gate whose tree equals an earlier
run's tree (and toolchain) re-runs only that run's reds, non-observations and unrun cases (and any audit or self-test whose
inputs changed, which `self_tests.py --reuse` already does), and the GREEN record names the earlier run's passes it composes
with. A changed tree re-runs everything, as today. Owed: the composition in gate.py's record, `enqueue.py land`'s reading of a
composed record (exit 14 stays the refusal for a tip no record covers), the drift test (a planted two-run composition at one
tree is GREEN; a composition across two trees is refused), and the gate skill and DESIGN-test-build-ci.md text.
