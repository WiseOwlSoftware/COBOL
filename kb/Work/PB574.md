# PB574

## Mechanism
SR1's variable-length-group screen is bypassed by TYPE composition: `01 T TYPEDEF. 05 D PIC X DYNAMIC LENGTH. 01 R TYPE T VALUE "AB".` compiles clean where the byte-equivalent INLINE spelling draws COBOLNET1703

### The refutation this note is written from
Row `SR-13.18.63.3-1` was adjudicated CONFORMS and OVERTURNED to `PARTIAL` by the refuter. Its reasoning, verbatim:

> SR1 names TWO subject shapes and only ONE of them survives TYPE composition -- the [[two_arm_dispatch]] shape the adjudicator's own class doc says the CompositionForest design fixed. MEASURED WRONG-ACCEPTANCE: `01 T TYPEDEF. 05 D PIC X DYNAMIC LENGTH. 01 R TYPE T VALUE "AB".` compiles and runs clean (probe r17_sr1_typedef_varlen), and the same shape with the dynamic-length item one level deeper also compiles (r32_sr1_typedef_varlen_deep). The program is NON-CONFORMING: 13.18.57.4 GR2a (cite.py --check OK) -- "the subject of the entry is a group whose subordinate elements have the same names, descriptions, and hierarchy as the subordinate elements of type-name-1" -- gives R a dynamic-length elementary subordinate, so R IS a variable-length group by 8.5.1.12.1 (cite.py --check OK), and 13.16.3 SR14 (cite.py --check OK) expressly permits TYPE and VALUE in the same entry, so the shape is legal to WRITE and SR1 is the rule that must reject it. The byte-equivalent INLINE spelling `01 R VALUE "AB". 05 D PIC X DYNAMIC LENGTH.` DOES draw COBOLNET1703 (r19_sr1_inline_varlen) -- the exact accept/reject asymmetry between a TYPE reference and its inline spelling that the class doc claims was the first landing's bug and was fixed. SR1's OTHER shape does compose through TYPE (r10 at --std 2014 and r18 both draw 1703 on `01 R TYPE T VALUE "AB"` with a STRONG T), which is what makes this one arm, not the whole rule. ROOT CAUSE, measured, is upstream of this pass: the TYPE clone DROPS the DYNAMIC LENGTH clause -- `MOVE "ABCDE" TO D IN R` then FUNCTION LENGTH(D IN R) prints 1 through a TYPEDEF (r20) but 5 inline (r21), a silent WRONG-ANSWER defect in its own right -- so ReferenceResolver.HasVariableLengthSubordinate is asking a composed tree that no longer carries the fact. That does not rescue the row: the rule is unenforced on a reachable, legal-to-write population. The cited negative pins only the INLINE dynamic-capacity spelling at 2023 (tests/conformance/negative/pb184-group-value-variable-length-subject.cob -- `01 GV VALUE "ABCDE". 05 GB PIC X OCCURS DYNAMIC CAPACITY ...`), so no test covers the composed shape. Everything else the adjudicator claimed re-measured clean: the 8.5.1.12.1 predicate excludes occurs-depending correctly, the strong arm fires at 2002/2014/2023, the Format-2 table carrier reaches SR1 (r11), and IsGroupValueSubject's item.IsGroup narrowing loses nothing.

### Inventory row `SR-13.18.63.3-1` (PARTIAL)
BOTH SUBJECT SHAPES ENFORCED, AND THE PREDICATE STATES THE RULE RATHER THAN A RESIDUE. `Sr1SubjectShape` tests StrongTypeModel.IsStrongGroup then ReferenceResolver.HasVariableLengthSubordinate, the second keyed to 8.5.1.12.1's definition ("a group item whose data description has at least one dynamic-length elementary item or dynamic-capacity table as a subordinate item" -- cite.py --check OK) and NOT to occurs-depending, which is a fixed-length group. MEASURED at the pin: a STRONG TYPEDEF group reference carrying a VALUE draws COBOLNET1703 at --std 2023 and 2002 (probes sr1_strong_group, sr1_strong_2002); a dynamic-capacity table TWO levels below the subject draws it (sr1_varlen_dyncap_deep -- the walk is the whole subtree, not the immediate children); a DYNAMIC LENGTH elementary item under the subject draws it (b_sr1_dynlen_group), and the same group WITHOUT the VALUE compiles clean (b_sr1_dynlen_only, the over-rejection control). The screen runs over CompositionForest, not ConformanceForest, so `01 R TYPE T VALUE "..."` -- where the VALUE and the offending shape come from different entries -- is caught (conformance:negative/pb184-group-value-type-reference), and it fires once per WRITTEN VALUE via DataItem.ValueIsCopied so a SAME AS / TYPE copy does not re-report its source's entry. SCOPE CHECK: the code screens only `item.IsGroup`, which loses nothing -- both shapes SR1 names are by definition group items. EDITIONS: the rule text is under the ALL FORMATS heading and is edition-invariant as written; its two subject shapes are themselves post-85 constructs, so at COBOL-85 the rule has no population (the two negatives are pinned reject-at 2002+ and 2023 respectively for that reason).
