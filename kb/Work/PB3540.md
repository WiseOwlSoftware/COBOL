# PB3540 — EC-FLOW-COMMIT/-ROLLBACK under an active METHOD is not seen

## Lead

EC-FLOW-COMMIT and EC-FLOW-ROLLBACK under an active METHOD are not seen: methods are recursive (§8.6.6) and §9.1.18.6 says
the APPLY COMMIT clause, COMMIT and ROLLBACK "are not permitted in factory and object classes, nor in any of their methods
nor in any runtime elements that they invoke". The recursion arm of the EC-FLOW-* checks reads only
`ProgramTable.AnyRecursiveActive`, and methods are not in the ProgramTable. Both citations were re-run through
`cite.py --check` on 2026-10-22 and returned OK (§8.6.6 heading "Common, initial, and recursive attributes"; the §9.1.18.6
sentence quoted above).

Code site: `src/Cobol.Net.Runtime/Control/ProgramTable.cs#AnyRecursiveActive`.

Repro: a method INVOKEs a program that executes COMMIT while an APPLY COMMIT clause is active. The program's COMMIT runs
with no EC-FLOW-COMMIT. (There is no unit case for the recursion arm today.)

## Landed (wave 1157 B)

Re-probed on the wave 1157 build before the fix: a method INVOKEd from a program with an active APPLY COMMIT clause CALLs a
program that executes COMMIT and ROLLBACK with checking on; no EC-FLOW-COMMIT or EC-FLOW-ROLLBACK was raised, the COMMIT
committed record 1, and the program's own ROLLBACK then restored nothing (`RECORD 1=AAAA`).

Root cause: the recursion arm asked `ProgramTable`, whose nodes are the programs and functions of the run unit, and a method
is no node. A method is a frame on the run unit's `ModuleStack` (the emitted method body pushes it, `OoEmitter.EmitMethod`,
for the §15.65.4 r5 activation), and every other activation pushes there too. The fix puts the recursion fact where every
activation already reports: `ModuleStack.Push` and `PushMain` take `recursive` (a RECURSIVE program, a function, a method:
§8.6.6), `ModuleStack.AnyRecursive` answers it in O(1), and `TransactionControl.FlowForbidden` asks it. The table's scan,
which could not see a method, is deleted. The runtime's shipped surface changed, so the runtime major is 14 and
`RuntimeAbiPinDriftTests` pins the new hash.

Sibling sweep (the arms of the dispatch): COMMIT, ROLLBACK, the activation of an APPLY COMMIT clause and §14.6.13.1.3 item 8's
ROLLBACK all go through `FlowForbidden`, so one change covers the four; object, factory and property methods all push the same
frame through the one `EmitMethod`. The static reach (a COMMIT or ROLLBACK written in a method, §14.9.7.3 SR1) was already
refused (COBOLNET1690) with no golden: `pb3540_commit_in_object_method` and `pb3540_rollback_in_factory_method` now pin the
object and the factory arm.

Goldens: `pb3540_commit_rollback_under_method` (checking on, object method), `pb3540_commit_under_factory_method_unchecked`
(factory method, checking off, the COMMIT commits nothing), `pb3540_ec_flow_apply_commit_under_method` (the activation, on and
off), the two refusals above, and the 2002/2014 refusal `pb3540_commit_under_method_below_2023`. Unit: `ModuleStackInvariantTests`
(`AnyRecursive` follows the frames), `TransactionControlTests` (COMMIT, ROLLBACK, activation and item 8 under a method, and the
negative control of a non-recursive program).

Rows: the six rows moved PARTIAL to CONFORMS (batch `w1157b-pb3540`, GAP 74 to 68) and are in `closes_rows`.

For the next implementer: `src/Cobol.Net.Runtime/Control/ModuleStack.cs#AnyRecursive` is the one answer to "under the control of a
recursive runtime element" (reuse it; never rebuild it from `ProgramTable`, whose nodes omit methods); a new kind of activation
must pass its `recursive` flag to `Push`. `src/Cobol.Net.Runtime/IO/TransactionControl.cs#FlowForbidden` is the one place the
four commit and rollback arms ask it. `src/Cobol.Net.Compiler/CodeGen/Verbs/OoEmitter.cs#EmitMethod` pushes every method's frame.
Trap: the module stack's `Push`/`PushMain` are shipped runtime surface, so changing them raises the runtime major
(`Directory.Build.props`) and the hash pin in `RuntimeAbiPinDriftTests`; run that test once to read the new hash.
