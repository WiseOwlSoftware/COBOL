# PB1946 — LANDED (wave 1008 B)

`OoConformance.ContentValueMismatch` no longer refuses an arithmetic expression into every non-numeric formal. The
expression's VALUE is a numeric sender on Table 16's NONINTEGER row (an expression carries no compile-time integer
guarantee, the principle §15.2 gives a NUMERIC function), asked rule 2 d)'s MOVE question like a numeric literal: Yes
into a numeric-edited formal (edited into the mask), "No" into an alphanumeric or national formal. Both lanes ask it
(CALL through `ParameterConformance.ContentConformanceReason`, INVOKE through `OoBinder`). The store goes through the
receiving category's MOVE store on both carriers: `CallEmitter.ArgText` (new `BoundComputedOperand` arm beside the
numeric-literal arm) and `OoEmitter`'s string-carried arm (`ConvertSource` over the computed operand).
`ContentValueMismatch` also now owns two refusals every value shape needs and the expression arm exposed: a GROUP
formal refuses an expression (§14.9.25.4 GR4's copy has no characters to copy) and a class-pointer or object-reference
formal refuses any value (§14.8.2.3.3's SET paragraph; by code reading, Table 16's fall-through would have admitted a
boolean value there, so the screen is shared by every value shape). Goldens: `conformance:2002/pb1946_content_expression_move_regime` and four negatives
`pb1946-content-expression-into-{alphanumeric,national,group,pointer}`.

Filed 2026-10-03 13:10 PDT by the orchestrator from the verdict recorded in `kb/Work/PB1936` (adjudication, now closed).

## The defect
`CALL ... USING BY CONTENT A + 1` (and the INVOKE lane) into a `PIC ZZ9.99`, `PIC X(4)` or `PIC N(4)` formal is refused
(wave 1006 group A, PB1113). The governing rule admits it: §14.8.2.3.3 rule 2 d) applies the MOVE rules "with the argument
as the sending operand", and an arithmetic expression argument is a numeric value, the same sender category as a numeric
literal (which PB1113 already admits through the MOVE store).

## Fix
In `src/Cobol.Net.Compiler/Oo/OoConformance.cs#ContentValueMismatch`, the `sender.IsExpression` arm: describe the expression as
a numeric sender (the arm `ContentValue.Arithmetic` already carries the noninteger Table 16 row) and ask rule 2 d)'s MOVE
validity question, so a numeric value into a numeric-edited receiver is admitted and edited, and the alphanumeric and national
receivers keep the rows Table 16 refuses (a noninteger numeric value). Both lanes ask it: the CALL lane through
`ParameterConformance.ContentConformanceReason` and the INVOKE lane through `OoBinder`. The store goes through the receiving
category's MOVE store, as `MoveEmitter.ConvertSource` already does for the numeric literal. Golden at the introducing
edition plus the Table 16 negatives; repro `scratchpad/w1006a/gen1113.py` case `ee` (may be gone: rebuild from the PB1936 text).
