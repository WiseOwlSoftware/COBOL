# PB1423 — LANDED

## Landed (wave 1005, group C) - one left-to-right argument order for every function-identifier

**Root cause.** A user-defined function activation is a statement-scoped PRE-op on the shared `DataBinder.PendingPreOps`,
hoisted ahead of the statement that reads its result, while an argument that merely READS state (an identifier, an
arithmetic expression, a nested intrinsic, a subscripted item, a boolean expression) was rendered at the consumer, after
every hoisted activation. So the later argument's activation ran before the earlier argument was evaluated, and the note's
"hoist EVERY argument into ordered temps or none" was the shape: `FUNCTION SUM(A, FUNCTION BUMP(A))` summed the CHANGED A.
Measured on the wave tree before the fix (probe `scratchpad/w1005c/p1423.cob`): EXPR=5010, INTR=15, NEST=5010; after: 4010,
14, 4010. The rule applies to the intrinsic form too (GR1 makes all three name forms "a function-identifier"), so the fix is
not UDF-only.

**Fix (one mechanism, rule 5).** `src/Cobol.Net.Compiler/Binding/Procedure/ArgumentOrder.cs`: a `Window` is opened around one
function's argument list by the ONE intrinsic call point (`IntrinsicBinder.BindIntrinsicCore`) and by the ONE user-defined
activation (`UdfBinder.UdfActivate`); `IntrinsicBinder.BindArgOperand` (the ONE argument binder) records each operand with
the pending pre-op range it registered; when a LATER argument registered pre-ops, every earlier argument whose value is read
at the activation is stored into an intermediate result item by the ONE materializer (`SendingValueTemp.Materialize`, the
§14.9.25.4 GR1 temp; `MaterializeBoolean` for a boolean-expression argument) at the position its own argument finished binding.
Not frozen: literals, compiler temporaries, a BY REFERENCE identifier of a user function (GR6a), a boolean expression of
run-time length. `ArgumentOrderDriftTests` pins the two entries and the one binder. Design: INTERPROGRAM + INTRINSICS docs.

**Goldens.** `conformance:2002/udf_arg_order` (EXPR, INTR, NEST, REF, VAL, SUB, ORD, BOOL legs) + negative
`pb1423-udf-argument-order-at-85`.

**Sibling sweep.** The other arm of "arguments of an activation": CALL USING and INVOKE USING arguments are bound by their own
binders and are not function-identifier arguments (no GR2). Object-property GET ordering against argument order is a separate
mechanism (the outer `OoPendingPropertyOps` wrap runs before every pre-op) and is reported as a lead, not changed here.

### `GR-8.4.3.2.4-2` — PARTIAL (adjudicator + refuter record, verbatim)

All match the spec. conformance:2002/udf_nested_args covers nesting, but its output (sums) cannot observe evaluation ORDER, so no test is named and a test is still needed. || REFUTED: PARTIAL — Left-to-right holds only among function-identifier arguments. ## What the fixer owes

Evaluate arguments in list order: either hoist EVERY argument into ordered temps or none; golden with a side-effecting function in position 2 observed by an expression in position 1.
