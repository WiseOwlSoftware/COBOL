# PB1661 — LANDED

Filed 2026-09-27 by the train-67 lander from the wave-67 N implementer report (`w67n-PB1468-report.md`, new
defect 1). Pre-existing: the implementer measured the same answer on the predecessor build, before PB1468.

**Measured on the train-67 build** (repro `scratchpad\w67n\p7.cob`, `--std 2023`, re-run by the lander):
```
SET I1 TO 3. SET I2 TO 2. SET IDA TO I1.
EVALUATE I1  WHEN I2 … WHEN IDA DISPLAY "I1=IDA" WHEN OTHER …   ->  I1=IDA   (right)
EVALUATE IDA WHEN I2 … WHEN I1  DISPLAY "IDA=I1" WHEN OTHER …   ->  OTHER    (wrong: IDA=I1 is owed)
```
Silent wrong answer: the program compiles clean and takes the wrong branch.

**Rule.** §14.9.13.4 3) a): the subject is "assigned the value and class of the data item" (`cite.py --check`
OK); §8.8.4.2.13 3) pairs an index data item with an index-name, compared by occurrence number.

**Code site.** `src/Cobol.Net.Compiler/Binding/Procedure/SendingValueTemp.cs:108` `Materialize` / `OfPlace` —
the USAGE INDEX clone and its `BoundMove` store — reached from `EvaluateBinder.cs` `BindSubjectValue` (~782), which
materializes a subject read by two or more WHENs. The index-name subject's numeric intermediate (the same family)
was handled by PB1468 (`ConditionBinder.RecordIntermediate`); the index DATA ITEM clone was not.

**What the fixer owes.** The temporary keeps class index and the stored value (a MOVE to a USAGE INDEX item is not
the §14.9.39 SET the store needs to be); golden with both EVALUATE shapes above plus an index-name subject; sweep
every other `Materialize` caller (MOVE's GR1 sending freeze) for the same clone.

## Landed

`SendingValueTemp` stores an index-data-item clone through `BoundSetTo`; witness `conformance:2023/pb1661_evaluate_index_data_item_subject`.
