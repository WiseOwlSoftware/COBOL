# PB361 — a USE statement in a nondeclarative paragraph

**Rows:** `SR-14.9.49.3-1`.

## The programs

All under `<lane3 scratch>/out-b1/probe/sr1/`:

* `outside.cob` — `USE AFTER STANDARD ERROR PROCEDURE ON F1.` written in a NONdeclarative paragraph of a program
  with **no DECLARATIVES at all** → compiles at `--std 2023` with zero diagnostics and runs to completion.
* `second.cob` — a legal declarative section plus a SECOND `USE AFTER STANDARD ERROR PROCEDURE ON F1.` inside
  that section's paragraph DP1 → compiles and runs clean.
* `reach.cob` — `outside.cob`'s statement made reachable by `PERFORM M2.` → still no compile diagnostic; at run
  time it dies with `NotImplementedCobolFeatureException: a COBOL feature that is not yet implemented was reached
  at run time: statement 'USEAFTERSTANDARDERRORPROCEDUREONF1'`.

## The rule

> §14.9.49.3 SR1: A USE statement, when present, shall immediately follow a section header in the declaratives
> portion of the procedure division and shall appear in a sentence by itself

`--check 14.9.49.3 "shall immediately follow a section header in the declaratives portion of the procedure
division and shall appear in a sentence by itself"` → **OK**; §14.3 — *Declarative sections shall be grouped at
the beginning of the procedure division* (`--check 14.3` → **OK**) — fixes what the declaratives portion is, and
§4.2.2 requires the compile-time warning mechanism to indicate violations of the explicit syntax rules. **A
misplaced USE is illegal source, never a missing feature.**

## What the compiler does

`CobolParserCore.g4#statement` (line 657) lists `useStatement` among the ordinary verbs, so every `sentence` in
the division admits one. The ONLY placement check lives in `ProcedureTableBuilder.DeclCollectSection`, which
inspects the FIRST sentence of a declarative SECTION — it can therefore see the *sentence by itself* and
*immediately follows the section header* halves and DOES enforce them (COBOLNET0897, confirmed by probe
`pair.cob`) — but it never runs on any other sentence.

Everything it does not see reaches `StatementBinder.BindStatementCore` and falls out of the bottom arm,
`_ => new BoundUnsupported($"statement '{FirstToken(s)}'")`, which `StatementEmitter` renders as a runtime loud.
**That bottom arm is doing double duty** — *a verb this compiler has not implemented yet* and *a verb that is
illegal HERE* — and the second meaning produces a wrong message and, for unreached code, no message at all. The
carrier conflation itself is **PB236**.

## The fix shape

Make the placement a property of the PARSE POSITION rather than of the fallback: give the declarative section its
own sentence rule so `useStatement` is unreachable from the nondeclarative `statement` alternative. That also
removes the need for the bottom arm to guess, which is why it is preferable to adding a context check in
`BindStatementCore`.

**Code sites:** `CobolParserCore.g4#statement` (line 657) · `StatementBinder.cs#BindStatementCore` (line 419) ·
`ProcedureTableBuilder.cs#DeclCollectSection` (the check that exists).
