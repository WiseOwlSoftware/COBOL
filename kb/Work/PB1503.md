# PB1503 — OPEN

## The rule (every citation re-run through `cite.py --check`)

> 5) If property-name-1 is specified as a data-name in the working-storage section of the containing object definition, the PROPERTY clause shall not be specified in the data description entry of that data-name.

`OK  §11.7.3 5)  (Syntax rules)`

> 6) If the GET phrase is specified, then the method shall have no USING phrase parameters specified in the procedure division header and shall have a single RETURNING phrase. The returning item shall not be an object reference described with the ACTIVE-CLASS phrase.

`OK  §11.7.3 6)  (Syntax rules)`

> 7) If the SET phrase is specified, then the method shall have a single USING parameter specified in the procedure division header and no RETURNING phrase. The USING parameter shall not be an object reference described with the ACTIVE-CLASS phrase.

`OK  §11.7.3 7)  (Syntax rules)`


## Finding — `method-id-paragraph` (under-rejects; rows `SR-11.7.3-6`, `SR-11.7.3-7`)

**Mechanism.** The GET/SET PROPERTY accessor shape (§11.7.3 SR6/SR7) is screened on header PRESENCE only: OoClassTable.Build tests HasUsing/HasReturning booleans, never the number of USING formals, and no site checks whether the accessor's RETURNING item (GET) or USING formal (SET) is an OBJECT REFERENCE ACTIVE-CLASS. The comment promising a formal-count re-check 'at data-bind' has no implementation.

## Finding — `method-id-paragraph` (under-rejects; rows `SR-11.7.3-5`)

**Mechanism.** §11.7.3 SR5 is enforced only as a by-product of an accessor-roster COLLISION in DataBinder.OoBindPropertyClauses: when the PROPERTY clause says WITH NO GET (or WITH NO SET) it synthesizes no accessor of that kind, so an explicit GET (or SET) PROPERTY method for the same data-name never collides and the illegal pair is accepted.

**Expected from the spec.** Compile-time error: §11.7.3 SR5 'If property-name-1 is specified as a data-name in the working-storage section of the containing object definition, the PROPERTY clause shall not be specified in the data description entry of that data-name.' — unconditional; the NO GET/NO SET phrase does not lift it.

**Observed / reasoning.** Both compile clean (rc 0) at 2002 and 2023. The bare-PROPERTY case is rejected COBOLNET0842 (OoSpineTests.PropertyClause_DuplicateExplicitAccessor_0842), which is why the gap is invisible to the existing test.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.Oo.cs#OoBindPropertyClauses (AddAccessor / TryAddMethod collision is the only SR5 test)

## What the fixer owes

Screen SR6/SR7 on the bound header (formal COUNT and the ACTIVE-CLASS descriptor of the one formal / returning item) at the site the comment promises ('at data-bind'), and SR5 as its own rule: an explicit GET/SET PROPERTY method whose property-name is a working-storage data-name carrying ANY PROPERTY clause (WITH NO GET/SET included) is refused, independent of accessor synthesis. Coordinate with PB1273/PB1274 (the PROPERTY clause's own rules and the synthesis-order defect) — same files, one fill unit. Negatives p1_set_two_using and p4_property_noget_plus_explicit_get.
