# PB3587 - the Format-1 CALL cell and the INVOKE literal arm cross a group formal without the sender codec

PB3562 made `OperandText.NonElementaryMoveSender` the one place that decides which representation a group-move sender copies
(section 14.9.25.4 4, "there is no conversion of data from one form of internal representation to another", `cite.py --check` OK).
It fixed MOVE and the Format-2 CALL / INVOKE group-formal arms for a KNOWN formal (`CallEmitter.IsPlainGroupFormal`,
`OperandText.CarrierDiffersFromStorage`). Two channels still skip it.

## One note, not three

The two defects and the PB3562 review lead R1-1 share ONE mechanism: an argument cell is built in the elementary alphabet (operand
text or a bare string) and the plain-group formal reads it as a storage image, without asking the codec. The stale doc sentence in
R1-1 is the description of exactly these two bypasses, so it is corrected in this note's fix (docs in the same change set), not
filed apart.

1. **Format-1 CALL.** `CALL "SUBG" USING BY CONTENT E8` where E8 is `PIC 1(8) USAGE BIT` and SUBG's formal is a plain group of eight
   bit items: the group arrives as `[00110001]` (the text '1' as byte 0x31), and a USAGE NATIONAL argument arrives as mojibake. BY
   REFERENCE is right. The probe (`call.cob`) lived in the PB3562 implementer's scratchpad and was not kept; rebuild it from this
   description. Rule: a BY CONTENT argument is moved to the allocated record without conversion (section 14.2.3 9, "moved to this
   allocated record without conversion", `cite.py --check` OK), a record of the argument's length. Cause: `BoundCallArg.Formal` is
   null for a Format-1 CALL (the formal is not known at bind), so `CallEmitter.WithMoveSending -> ElementarySending ->
   OperandText.AsString` builds elementary text; the cell must carry both alphabets (elementary formals read text, a group formal
   reads the storage image). That is an ABI change in `Runtime/Control/CallAbi.cs` (`MoveSending` / `MoveLanding`), which is why the
   PB3562 slice stopped.
2. **INVOKE BY CONTENT of a national or boolean literal** into a group formal: `OoEmitter` builds `new BoundStringLiteral(slit)` from
   a bare string (`OoEmitter.cs` around line 1757, `CsLiteral(a.StringLiteral)`), so the literal's category is lost at bind and the
   national or boolean literal reaches the group as its alphanumeric characters. Same cell-alphabet family.
3. **Doc (review lead R1-1, low).** `docs/CONFORMANCE.md` D-B3 (landing with PB3562) says the rule is written once in
   `OperandText.NonElementaryMoveSender`, "which every group-move sender channel (MOVE, an implicit MOVE such as WRITE FROM, a CALL /
   INVOKE argument into a group formal) reads". The two channels above do not. Until they do, the sentence is false; after the fix
   it must read true, and a drift test should pin it so the next channel is automatic, not a hand-kept list.

## Fix shape (for the implementer)

Give the call cell one representation that carries both alphabets, or make the Format-1 CALL decide at the callee (the formal is
known there), and route the INVOKE literal through a bound literal that keeps its category. Reuse `StaticUsageOf` and
`CarrierDiffersFromStorage`; add goldens for both channels (national and usage-bit argument, national and boolean literal), editions
2002 and up, plus a drift test over every `CallAbi.MoveSending` producer. No I/O path is reached.

**Sites:** `src/Cobol.Net.Compiler/CodeGen/Emit/CallEmitter.cs`, `src/Cobol.Net.Compiler/CodeGen/Emit/OperandText.cs`,
`src/Cobol.Net.Compiler/CodeGen/Emit/OoEmitter.cs`, `src/Cobol.Net.Runtime/Control/CallAbi.cs`, `docs/CONFORMANCE.md`.

## Landed (2026-10-24, wave 20261024 group C) — the second alphabet, chosen by the activated unit

**Re-probe (own build, Debug).** The Format-1 repro rebuilt from the note (`CALL "SUBG" USING BY CONTENT E8`, E8 `PIC 1(8) USAGE BIT` holding
B"00110001", SUBG's formal a plain group of two `PIC 1(4)` items) showed `G 0011 0000` (BY REFERENCE `G 0011 0001`); a national item
arrived as `䅂 †`. An INVOKE BY CONTENT N"AB" into a plain-group formal answered `??`. The CALL lane through a program-specifier
whose program the activating element cannot see (a program defined later in the same compilation group) failed the same way for a bit
item, a national item and a literal, a boolean-function and a national-function value.
A boolean LITERAL needs no change: it rides `BoundInvokeArg.ContentBool` and, by D-B3, is its '0'/'1' characters on every lane.

**Mechanism.** One: an argument cell is built in the elementary alphabet (text) and the plain-group formal reads it as a storage image.
The activating element of a Format-1 CALL or a run-time-located CALL cannot see the formal, so it states BOTH alphabets in the argument's
`MoveSending`: `StorageImage` (the representation, from the SAME codec a MOVE uses, `OperandText.StorageImageIfDiffers` for places and
literals, `StorageImageConverter` for an evaluated function value read back from its cell) beside the characters; `CobolArgAdapt.Text`
hands a plain-group formal (non-null group atoms), BY CONTENT only, the image. The INVOKE lane knows its formal, so `BoundInvokeArg.StringLiteral`
became the bound literal (category kept) and `OoEmitter`'s group arm sends it through `NonElementaryMoveSender`; a literal into a bit or
national group formal (an elementary item for the MOVE) now takes `MoveEmitter.RecordValue` like the CALL lane. `RuntimeApi.MoveSendingNew`
and `ArgWithValueSending` REQUIRE the second alphabet (null is an answer), so a new producer must decide; `GroupMoveSenderChannelDriftTests`
pins the shape (no hand-built `MoveSending`, every producer states it, the adapter reads it, the INVOKE literal keeps its category).
The stale D-B3 sentence (review lead R1-1) is corrected in `docs/CONFORMANCE.md` to the channels that really read the codec.

**Sibling sweep.** Reference-modified national/bit slices (`NA(2:2)`), a numeric item of usage national, a national group and the function
values at an unseen-formal CALL all answer correctly (probes `call3`, `call2` in the wave scratch). A universal-receiver INVOKE is BY REFERENCE only
(COBOL0866), so it has no BY CONTENT channel. Format-1 CALL admits identifiers only BY CONTENT, so a literal reaches the run-time lane only
through the program-prototype format.

**Goldens.** `cases/14.2-Procedure-division-structure/pb3587_content_group_formal_usage_values` (ten legs: Format-1 bit, national, national slice;
specifier lane bit, boolean function, national, national function, national literal; INVOKE national literals; 2002+) and its negative
`..._below_2002` (USAGE BIT refused at 85, COBOL0900). Unit: `MoveSendingStorageImageTests`.

**For the next implementer.** `src/Cobol.Net.Runtime/Control/CallAbi.cs#MoveSending.StorageImage` is the second alphabet and `CobolArgAdapt.Text` (group atoms non-null, BY CONTENT) the only reader; `OperandText.cs#StorageImageIfDiffers` / `#StorageImageConverter` produce it from `RepresentationOfText`, and `RuntimeApi.MoveSendingNew(characters, image, …)` / `ArgWithValueSending(arg, converter)` require the producer to state it (null is an answer). A new sending producer that must reach the group formal needs no list entry, only a decision at its call. The traps: any change to `MoveSending` or `WithValueSending` is a shipped-surface change (runtime major, `PublicAPI.Shipped.txt`) and a boundary change (`RuntimeAbi.CallAbi`, which is itself a line of `PublicAPI.Shipped.txt`, so both pins in `RuntimeAbiPinDriftTests` move together: raise the numbers, rebuild, re-pin the printed hashes). Format-1 CALL admits only identifiers BY CONTENT, so a literal reaches the run-time lane only through the program-prototype format; a universal-receiver INVOKE is BY REFERENCE only.
