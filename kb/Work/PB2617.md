# PB2617 — `A ** 2` over a fractional base is not exact

Filed by the train 1039b lander from the wave-1039 group G implementer report (`w1039g-PB1900-report.md`, new
defect 2), re-run on train 1039b's build.

**Rule.** §8.8.1.3: "Native arithmetic is an implementor-defined method of evaluating an arithmetic expression"
(`cite.py --check` OK). By CLAUDE.md rule 1 the latitude follows GnuCOBOL, whose `cob_decimal_pow` takes an
integer exponent through an exact `mpz_pow_ui`; PB1900 settled the same question for nested products. PB18 recorded
the scale-0 restriction as a limitation, not as an owner decision.

**Repro.** `E:\COBOL-coord\scratch\w1039g\ppow.cob` (copy in `E:\COBOL-coord\scratch\train1039b\leads\`):
`COMPUTE R = A ** 2` prints `R=126215515697488189772`; `COMPUTE R = A * A` prints the exact `R=126215515697488187881`;
`COMPUTE R = A ** N` (N PIC 9 VALUE 2) also prints `…189772`. The same approximation reaches
`CALL … BY VALUE A ** 2`.

**Code site.** `src/Cobol.Net.Compiler/CodeGen/Emit/NumericRenderer.cs#Power`: the exact integer path requires
`integerOperands` (scale 0); a fractional base goes to the binary64 core.

**Fix shape.** A non-negative integer exponent known at compile time has a compile-time result scale (s * n), so the
power can ride the exact wide lane PB1900 added (`CobolWide`, settled once by `NumericRenderer.Settle`) up to its
digit bound, falling back to the SDIDI beyond it; a run-time integer exponent needs the same rule with a run-time
scale.

# PB2617 — LANDED

## Landed (wave 1042, group G)

**Reproduced on the base build** (`E:\COBOL-coord\scratch\w1042g\ppow.cob`): `COMPUTE R = A ** 2` and `A ** N` printed
`126215515697488189772`; `A * A` printed the exact `126215515697488187881` (A `PIC 9V9(10)` 1.1234567891, R `PIC 9V9(20)`).

**Root cause.** `NumericRenderer.Power` had one exact arm, for a scale-0 base (`integerOperands`); a scaled base to an
integer exponent fell to the binary64 approximation arm (`PowNativeReal` + `FromDouble`), so the three spellings of one
value disagreed. The precedence (CLAUDE.md rule 1) follows GnuCOBOL: `cob_decimal_pow` raises a decimal to an integer
exponent by an exact `mpz_pow_ui` with scale × n; binary64 is for a non-integer exponent only.

**Fix.** The arm is keyed on the exponent's CARRIER (scale 0, neither Dec nor Real: an integer by construction) over a
scaled or Dec base. A literal exponent n ≥ 1 whose digit bound (base digits × n) fits 77 digits is `CobolWide.Pow` as a
`NumX.Wide` of scale base scale × n, settled once at the public entry (`A ** 2` is `A * A`); every other integer exponent
is `CobolIntrinsics.PowNativeDec` (the wide lane at run time, then the `MulToOdd` chain; the reciprocal for a negative
exponent; `CheckPowRule6`). `Power`'s vestigial `expIsNonNegativeLiteral` flag became the literal exponent's VALUE
(`IntegerLiteralValue`, shared with `IntegerValuedLiteral`); `NonNegativeIntegerLiteral` is deleted. Golden
`2023/pb2617_native_integer_power_fractional_base`; `COBOLNET_NUMERIC_DESIGN.md` D19 part (c).

**Sibling sweep.** The integer-base arm keeps its owner-decided past-the-carrier approximation (D19 part a). Every other
`**` consumer renders through `Power` (CALL BY VALUE, relations, intrinsic arguments), so one arm fixed them all.

## Landing

- `src/Cobol.Net.Compiler/CodeGen/Emit/NumericRenderer.cs#Power` — the exact integer-exponent arm over a scaled or Dec base now lives here (keyed on the exponent's carrier: scale 0, no Dec/Real). Reuse `WideOperand` and `RuntimeApi.WidePow`; the literal exponent arrives as `Int128? literalExponent` from `IntegerLiteralValue`, the one literal reader shared with `IntegerValuedLiteral`. Trap: the old `bool expIsNonNegativeLiteral` was discarded (`_ = …`) and the call site tested the literal TEXT with `long.TryParse`, so nothing could use the exponent's value.
- `src/Cobol.Net.Runtime/Intrinsics/CobolIntrinsics.RealArgs.cs#PowNativeDec` — the run-time twin (wide lane, then `MulToOdd` chain, reciprocal for a negative exponent); reuse `CheckPowRule6`. Trap: BigInteger is banned in the runtime (semgrep `cobolnet-no-biginteger`), so exactness rides `CobolWide`.
- `src/Cobol.Net.Runtime/Values/Numeric/CobolWide.cs#TryPow` — square-and-multiply; every square is a factor of the result, so `base digits × n ≤ 77` proves it cannot overflow.
