# PB640 — LANDED — the right COMPUTE, on the wrong side of the call (fixed); the rows moved to PB834, which holds them at PARTIAL for the class object/pointer SET leg outside this mechanism

Found 2026-09-05 by the `PB288` implementer (report §"Two new defects" (2)), which made the crossing land with the
standard's COMPUTE semantics (`RescaleStoreCap` + digit-capacity conformance, DOC-A.1-70's no-phrase disposition)
and measured that the OTHER half of a COMPUTE — the size error condition when checking is enabled — cannot be
raised from where the landing runs. PB288 owns no inventory rows; the two rows its batch verdicted PARTIAL are
claimed HERE, because a PARTIAL row needs an open note (the `DefectiveRowCoverage` gate said so on its tree).

## The rule

§14.2.3 GR9 and GR10, for a numeric formal parameter: the value is transferred as if by "a COMPUTE statement
without the ROUNDED phrase" (`OK §14.2.3 9)`, `OK §14.2.3 10)`) whose receiving operand is a record of the
formal's description. A COMPUTE whose result is "further from zero than permitted for the associated resultant
data item" after radix point alignment is §14.7.5 case 3 (`OK §14.7.5 3)`), and §14.7.5 r4 names the condition:
"if the result of the arithmetic statement is a value further from zero than permitted for the associated
resultant data item, the EC-SIZE-TRUNCATION exception condition is set to exist" (`OK §14.7.5 4)`) — set in the
runtime element that executes the statement, the activating element, since GR9 assigns the transfer to it. With checking off, DOC-A.1-70 (docs/CONFORMANCE.md) is the
documented disposition PB288 landed.

## The mechanism

`src/Cobol.Net.Runtime/Control/CallAbi.cs#Land` performs the transfer on the CALLEE side, at the activated
program's entry, as part of adapting the actual argument to the formal. The caller's `>>TURN EC-SIZE CHECKING ON`
state, its `USE AFTER EXCEPTION CONDITION EC-SIZE` declaratives and its ON EXCEPTION posture are the activating
element's, and are not what is in scope there; the landing therefore has exactly one behaviour — the no-phrase,
checking-off one — regardless of the caller's checking state.

## Repro (to be written as the first golden)

```cobol
       >>TURN EC-SIZE CHECKING ON
       01 BIG PIC 9(31) VALUE 1000000000000000000000000000000.
       ...
           CALL "PB640SUB" USING BY CONTENT BIG      *> formal: PIC S9(9)V9(9)
```

Expected under checking: EC-SIZE-TRUNCATION exists in the calling program before control transfers (a
`USE AFTER EXCEPTION CONDITION EC-SIZE` declarative in the caller fires; with no applicable declarative the
run unit terminates). Observed on PB288's tree: the callee receives +000000000.000000000 and runs.

## Fix shape

Move the numeric crossing's EXECUTION to the activating side, where §14.2.3 GR9 puts it: the caller's CALL emitter
evaluates each BY CONTENT / BY VALUE numeric argument into a temporary of the formal's description through the same
`CobolArgAdapt.Land` primitive (one landing, one place — PB288's), under the caller's checking state, so a case-3
overflow raises EC-SIZE-TRUNCATION exactly as an inline COMPUTE would; the callee then receives an already-conforming
value and `Land` at the callee becomes a no-op check. This needs the formal's description at the call site, which
PB237's program-prototype registry now supplies for a prototyped or nested CALL; for a non-prototyped external CALL
the description is not knowable at the caller and the callee-side landing remains (say so in the design doc as the
one documented residue, and cite §14.2.3's "otherwise" leg). Goldens: the repro above with a declarative (2002+),
its checking-off twin asserting DOC-A.1-70's digits, and a BY REFERENCE control (GR8's view carries no conversion);
`CallAbiNumericCarrierDriftTests` extended so the caller-side and callee-side landings are asserted to be the same
primitive. Then GR-14.2.3-9 / -10 → CONFORMS.

## Landed 2026-09-13 — the crossing's COMPUTE moved to the ACTIVATING side

**Status `landed`: THE MECHANISM IS CLOSED, and both rows moved to `kb/Work/PB834` — the note the
train-31 lander allocated for the reason they stay PARTIAL, which is OUTSIDE this mechanism.** The
implementer left this note at `half` and asked the lander for that allocation; the lander made it, so the
PB829 `half` shape is not needed here.
What remains on GR-14.2.3-9 and -10 is the class OBJECT / class POINTER *SET* leg — a
different bullet of GR9's own three-way list and a different subsystem (the D2 carrier vocabulary), reported as
a new defect by this implementer, not the size-error rule this note is about.

**The fix.** `CallEmitter.LandedForFormal` wraps every BY CONTENT / BY VALUE argument whose corresponding formal
is a fixed-point numeric item in `CobolArgAdapt.LandForFormal<T>` — the ACTIVATING side's GR9/GR10 COMPUTE,
sharing `LandScalar` (and so `Land`) with the callee-side adapters, which become the identity over an
already-landed argument. The checked lane is `CobolNum.StoreOrRaise`, selected at COMPILE time from
`EcState.SizeTruncationChecking`; with checking off the landing is byte-for-byte the one PB288 left.
`BoundCallArg.Formal` carries the correspondence, set in `CallBinder`'s Format-2 conformance loop and in
`UdfBinder.UdfArg`.

**The note's fix shape was right about the side and wrong about the machinery.** No new raise plumbing was
needed: EC-SIZE-TRUNCATION is already a FATAL ambient gate (`EcEmitter.FatalAmbientGates`) and a CALL/INVOKE is
not an `IArithmeticStatement`, so a statement compiled under EC-SIZE checking already carries the try/catch that
sets the last exception status, runs the §14.9.49 F3 selection and honours RESUME — measured before the fix
with `CALL … BY VALUE A * A` over an overflowing intermediate, which already printed
`CAUGHT=EC-SIZE-OVERFLOW`. Emitting the landing INSIDE the argument expression puts the raise before
`ProgramRegistry.CallProgram` is entered, which is §14.9.4.4 GR3 g)'s ordering, and works in an
expression-position activation (a UDF reference) where no statement could be emitted.

**The note's REPRO did not exercise the rule.** `CALL "PB640SUB" USING BY CONTENT BIG` is Format 1 with a
literal program-name, so GR9's FIRST branch applies: the record is "of the same length as the argument" and the
argument "is moved to this allocated record without conversion" — no COMPUTE, so no size error. The COMPUTE
branch is exactly a prototyped program, a NESTED CALL, a method or a function, which is also exactly the set
whose formal the activating element can know; §14.8.2.3.3 rules 1 vs 2 draw the same line. The goldens use
`AS NESTED`.

**The sibling, swept.** The INVOKE lane (GR9's "a method"; §14.8.2.3.3 rule 2 a)) already landed caller-side
but always through the UNCHECKED `CobolNum.Store`, so it was silent under checking too — the two-arm shape.
`OoEmitter`'s three BY CONTENT arms now take `NumericRenderer.StoreExpr(…, raiseOnSizeError:)`; the
numeric-LITERAL arm went through a bare `RuntimeApi.NumStore` and joined the other two, which also gave it the
unsigned-wide lane it was missing.

**A regression the mechanism's own probes could not have caught.** The first guard was
`Pic is { Category: Numeric, IsFloat: false }`, and `PicInfo.IndexItem` answers TRUE to it (category Numeric,
`Digits = 0`) — so a `BY CONTENT` USAGE INDEX argument landed through a zero-digit profile, `value % 10^0`, and
an index of 3 crossed as 0. GR9 puts class index on its SET bullet, not its COMPUTE bullet. The guard is now
`PicInfo.IsClassNumericFixedPoint`, the ONE place that trap is written down (kb/Work R27 had already documented
it for `IsIntegerDescription`, which is now expressed in terms of it), and the row is pinned in
`pb640_call_argument_landing_legs`.
