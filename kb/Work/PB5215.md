# PB5215 - a level-88 condition-name whose conditional variable is a group item accepts a signed numeric literal (88 G-N VALUE -1, VALUE -5 THRU +5): BindCondition screens a condition-name's literals only through the conditional variable's PICTURE, and an alphanumeric group has none

**Sites:**

- `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs` (`BindCondition`, `ScreenValueLiteral`)
- `src/WiseOwl.Cobol.Compiler/Binding/Passes/CheckValueLiteralClassesPass.cs` (`Run`, `ScreenGroupConditionName`, the fix: a group is known only after composition)
- `src/WiseOwl.Cobol.Compiler/Binding/Passes/CheckGroupValueDeclarationsPass.cs` (`GroupSubjectPic`, widened to `internal` so the group VALUE and the group's condition-names build one picture)

**Mechanism.** "A signed numeric literal must have associated with it a signed numeric PICTURE character-string." (§1985:VI.5.15.3 SR2), and a condition-name may be associated with a group ("A condition-name can be associated with any data description entry which contains a level-number except the following", §1985:VI.5.3.4 GR2, whose exceptions do not name a group). A group has no PICTURE, so no signed numeric literal can be associated with its condition-name. `DataBinder.BindCondition` screens each VALUE literal of a condition-name with `ScreenValueLiteral` only when the conditional variable has an operand PICTURE (`parent.OperandPic is { } sp`, a real PICTURE or a bit or national group's as-if PICTURE); for an ordinary alphanumeric group the comment says it "takes no category screen", reasoning that any alphanumeric literal satisfies it. A NUMERIC literal is the case that reasoning misses: it is neither screened for the sign rule nor for category, and is stored as its characters. The same literal in the group's own VALUE clause is refused (COBOL1657), so the two VALUE paths disagree.

**Found by.** The 1985 refuter pass (2026-11-10; records `E:/COBOL-coord/scratch/refute-85/out/r13.json`, probes `probes-r13/c7_grp88.cob`, `c7_grp88run.cob`, `c7_grp88thru.cob`, `c7_group.cob`): a refuter attacked the CONFORMS verdict of the row below, OVERTURNED it, and the repro was rerun on current main for this note.

The row's own probes held for elementary conditional variables: -0 on PIC 9 (COBOL1625), an 18-digit signed literal on PIC 9(18) refused and on S9(18) kept, VALUE -1 on unsigned items in the FD, CD and Linkage Section refused, an ODO element, USAGE INDEX and PIC X items refused.

**Observed (current main, the build at 3d12682fd2, rerun 2026-11-10).** exit 0, no diagnostic; prints `G-N TRUE` and `G [-1]`. Control (`g0.cob`, `01 G VALUE -5.` over the same group): exit 65, `error COBOL1657: data item 'G' (an alphanumeric group item ...): the VALUE literal -5 is numeric but the subject is an alphanumeric group item`.

**Expected (from the 1985 text).** Both 88 entries are refused: their literals are signed numeric, and the conditional variable G has no signed numeric PICTURE character-string (§1985:VI.5.15.3 SR2).

**Fix direction (root cause, CLAUDE.md rule 4).** Give a condition-name of an alphanumeric group the same literal screen the group's own VALUE clause has: `BindCondition` builds the conditional variable's `ValueSubject` for every parent (a group included, as the item-entry path already does for COBOL1657) and passes each literal through `ScreenValueLiteral` with it, instead of skipping the screen when the parent has no operand PICTURE. One screen for both VALUE paths; test a signed literal, an unsigned numeric literal and a THRU range on a group's condition-name.
