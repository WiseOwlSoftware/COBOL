# PB4092 — enabling one EC-SIZE name checks, and raises, the whole EC-SIZE family

**Sites:** `src/WiseOwl.Cobol.Runtime/Values/Numeric/SizeChecks.cs` (`SizeChecks`, new), `src/WiseOwl.Cobol.Runtime/Values/Numeric/CobolFloat.cs` (`InBinary64Range`, `AddChecked`, `SubChecked`, `MulChecked`, `DivChecked`), `src/WiseOwl.Cobol.Runtime/Values/Numeric/CobolNum.cs` (`AddChecked`, `SubChecked`), `src/WiseOwl.Cobol.Runtime/Intrinsics/CobolIntrinsics.RealArgs.cs` (`PowNativeRealChecked`), `src/WiseOwl.Cobol.Runtime/Intrinsics/CobolIntrinsics.Float.cs` (the family wrapper `InBinary64Range`), `src/WiseOwl.Cobol.Runtime/Exceptions/CheckingFlags.cs` (`SizeOverflow`, `SizeUnderflow`, `SizeTruncation`; **Observed.** With `>>TURN EC-SIZE-TRUNCATION CHECKING ON` and nothing else enabled, `IF WS-D * WS-D > 0` (WS-D COMP-2 1.0E200)
raises EC-SIZE-OVERFLOW and ends the run unit. That condition is not enabled. `NumericRenderer.CheckedFor` selects the
checked kernels for any enabled EC-SIZE name, and the checked kernel raises whichever EC-SIZE condition it meets. No
guard asks whether that particular name is enabled. The report compose (PB4031) inherits it through
`ExceptionState.SizeChecking` for PRESENT WHEN and VARYING. Repros: `E:/COBOL-coord/scratch/mythos/w-n1/w20261762d/f1/tr2.cob`
and `tr.cob`.

**Expected (`cite.py --check` OK).** §14.6.13.1.1: "If checking for an exception condition is enabled and an exception
status indicator is set as a result of an exception detected during the execution of a statement, the associated
exception condition is raised". Its NOTE 3: "An exception condition is set to exist only if checking for that condition
is enabled". An overflow when EC-SIZE-OVERFLOW is not enabled takes the not-enabled disposition, which DOC-A.1-70
documents (§14.6.13.1.3 item 8), and is never raised. Enabling EC-SIZE-TRUNCATION checks truncation only.

**Fix.** Decide per exception name, not per family. A checked kernel raises only the conditions whose checking is
enabled (the per-name `CheckingFlags`), and takes the not-enabled disposition for the rest. Sweep every reader of the
family-level size flag (`CheckingFlags.Size`, `EcState.SizeChecking`, `ExceptionState.SizeChecking`). Goldens: each
EC-SIZE name enabled alone, against an overflow, a truncation and a zero divide, in COMPUTE, IF and a report compose.
PB4093 is the store-side sibling.

## Resolution (wave 20261767, group B)

**Re-probe on the build (`E:/COBOL-coord/scratch/mythos/w-n3/w20261767b/p/`, one program per name x statement).** Before the fix,
`>>TURN EC-SIZE-TRUNCATION CHECKING ON` + `IF WS-D * WS-D > 0` ended the run unit with `EC-SIZE-OVERFLOW (fatal)`; the same line under
EC-SIZE-UNDERFLOW, -ZERO-DIVIDE, -EXPONENTIATION and -ADDRESS did too, and the report compose raised EC-SIZE-OVERFLOW from a PRESENT WHEN
under EC-SIZE-TRUNCATION. Two siblings shared the root: a zero divisor / exponentiation violation under ANOTHER name was latched, dropped
and the statement went on with the receiver unchanged (`C=007`), where checking off terminates; and a float overflow into a fixed
receiver under another name left `007` where checking off stores 000.

**Root.** One question, "is some EC-SIZE name enabled?", chose the checked kernels, the Try store and the catches for the whole family.
Checking is per level-3 name (§14.6.13.1.1 NOTE 3). The fix is one value, `SizeChecks` (Overflow, Underflow, Truncation; All for a
SIZE ERROR phrase), carried by `ReceiverContext.Checks`: the binary64 operators (`AddChecked`, `SubChecked`, `MulChecked`,
`DivChecked`, `PowNativeRealChecked`) and the `Int128` sum take it and raise only the conditions in it; the checked landing is chosen
where Truncation is taken; a no-phrase statement's catches take only the names it enables (a zero divisor or an exponentiation violation
not enabled propagates and terminates, DOC-A.1-70); the report compose reads the presenting statement's enablement at run time, one
flag per name. `EcState.SizeCheckRows` is the one table (name, bit, flag) and `SizeChecksDriftTests` holds it against the enum and the
runtime flags. Found and fixed on the way (I9): `FatalAmbientGates` had no EC-SIZE-UNDERFLOW row, so the condition the checked binary64
operators raise reached no declarative.

**Witnesses.** Goldens `14.7.5-SIZE-ERROR-phrase-and-size-error/pb4092_size_checking_is_per_name` (twelve steps, each name against an
overflow, an underflow, a truncation, a zero divide), `13.18.53-SOURCE/pb4092_report_compose_per_name`, the refused-below
`pb4092-turn-size-per-name-85`; `SizeErrorDispositionTests.SizeCondition_OtherNameEnabled_TerminatesLikeCheckingOff` (seven rows),
`FloatResultantTests.CheckedOperations_RaiseOnlyTheConditionsTaken`, `SizeChecksDriftTests`. DOC-A.1-70 and DOC-A.1-179 carry the
determination.
