# PB4772 - a SORT over an SD record holding a message-tag leaf, keyed on another item, compiles with a warning and aborts at run time

**What the report says (the reviewer's words).** R1-8 LEAD (low, not blocking at round 1): src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/SortEmitter.cs:987 A SORT over an SD record holding a message-tag leaf, keyed on another item, compiles with a warning and aborts at run time, although DESIGN 4.2 says MembersOf carries a tag through SORT. It is the same Tier-C deferral pointers have, and its text calls the tag a pointer/object-class leaf.

**R1.** No open note covers it (grep of kb/Work for the member name and key phrase).

**Re-probe (2026-11-05, wave 20261879).** On the build at 1a49d173c, an SD record `01 SREC TYPE T-REC` (a strongly-typed group of a 9(2) key and a USAGE MESSAGE-TAG; a bare level-05 tag is refused by COBOL1724, SR14) sorted on the key through INPUT/OUTPUT PROCEDURE compiled with COBOL1756 ("SORT SD record of 'SREC' with a pointer/object-class leaf ... deferred") and aborted with NotImplementedCobolFeatureException. A pointer leaf did the same: the reviewer's "same Tier-C deferral pointers have" was exact, so the fix covers every slot-carried leaf, not the tag alone.

**Fix.** The sort store carries such a record as its one-way transfer image (the positions the keys read) beside its leaf vector. `CobolSort.ReleaseStatement` takes the vector (`slots`), `SortWork` keeps it resident (a managed reference cannot spill) and the spillable `StoredFrame` carries only a ticket (`Carried`), written to run files behind the sign bit of the character count; `CobolSort.LastReturnedSlots` gives it back and the emitted RETURN stores it with `WithLeaves`. The question is `SortEmitter.HoldsSlots` (a slot leaf, never the image capability), so the later two-way tag image of DESIGN-message-control S4 cannot make the sort drop tags quietly. Admitted: one record description, no SAME RECORD AREA peer, fixed size, INPUT/OUTPUT PROCEDURE form. Still COBOL1756 (a precise reason, `SortBinder.SlotRecordFileTransferReason`): a USING or GIVING file and every MERGE over such a record, because a file record has no managed-slot half; that is the file record codec's mechanism (every READ/WRITE of such a record is Tier-C loud, `GateFileRecordByteSurfacePass`), registered as a lead, not fixed here. Witnesses: `conformance:cases/14.9.40-SORT/sort-sd-record-with-managed-slots` (+ `-refused-2014`), `SortManagedSlotTests`. docs/CONFORMANCE.md D-SWK (f).
