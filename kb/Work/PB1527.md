# PB1527 — OPEN

## The rule and the determination

> 22) … a) The amount of storage allocated … is not necessarily the same for every object reference.

`cite.py --check 13.18.60.4 "not necessarily the same for every object reference"` → OK §13.18.60.4 22). Annex A.1 item 214
requires the amount to be documented, and docs/CONFORMANCE.md §7 row `DOC-A.1-214` documents it: one .NET managed
reference, 8 bytes, which **contributes no character positions to any group image**.

## Repro (re-probed by the registrar, Debug build of `0caa7d5`, `--std 2023`)

Probes `/tmp/adj/adj-w2-a1-s3/probe/or2.cob`, `or3.cob`, `or4.cob`:

```cobol
       01 TG TYPEDEF STRONG.
          05 A PIC X(3).
          05 R USAGE OBJECT REFERENCE ORC.
       01 G TYPE TG.
       01 XX PIC X(20).
       ...
           MOVE "ABC" TO A. MOVE G TO XX.
```

| Probe | Observed |
|---|---|
| `or2` | `FUNCTION BYTE-LENGTH(G)` = `00011`; `MOVE G TO XX` → `[ABC                 ]`, positions 4, 11 and 12 all SPACE — the reference contributed 8 space positions |
| `or4` | `MOVE G TO XJ` (JUSTIFIED) → `[   ABC        ]` — the 11-position image, right-justified |
| `or3` | `STRING G DELIMITED BY SIZE INTO XX` compiles clean, then `NotImplementedCobolFeatureException: … whole-group image of 'G' with a pointer/object-class leaf (no character image) — the Tier-C byte island …` |

So the documented determination ("no character positions") and the code (8 space positions in MOVE and BYTE-LENGTH; a run-time
abort in STRING) disagree, and they disagree with EACH OTHER inside the code. Either the §7 row or the image composer is wrong;
rule 1 decides by §13.18.60.4 + §8.5 group semantics, and the result is ONE group-image rule every consumer (MOVE, STRING,
DISPLAY, BYTE-LENGTH, comparison) reads.
