# PB4007 — CI and every local host run the same tool versions, and those are the latest

**Owner decision, 2026-10-28 ~13:25 PDT (operator session), two messages, quoted:** "CI tooling should match local tooling
versions - always", then "To clarify, CI and local should always be using the latest version". Two requirements follow:
CI and every local host run IDENTICAL versions, and each is the tool's LATEST release (read as the latest stable/GA release,
not a preview, until the owner says otherwise). This settles every tool-version row of PB1957's survey (8 for the Windows
dev box and WSL, 12, 13, 14, 15, 52, 53, 56) as (a), IDENTICAL: no row of that kind may stay (b) or (c). It also replaces a
fixed pin as the policy: PB3308's SDK pin (10.0.403) stays the mechanism, but the version it names must be the latest.

## The failure that prompted it

Pull request #734 (PB3806, PB3991, PB3807; branch `worktree-wf_a5b6fa01-f4e-29`) passed its local gate GREEN, including
the Linux half (run `000001-20261028T184905Z`), and its review was CLEAN. The merge queue then removed it (`failed_checks`,
19:40Z). In merge-group run 40754265548, `Windows script self-tests` went RED on `scripts/spec/impact_store.py --self-test`:

```
FAIL  tidy skips a work directory that vanished between the glob and the stat  (got ([], False), want ([], True))
FAIL  prune skips a temporary file that vanished between the glob and the stat  (got (Pruned(removed=[], busy=[]), False), want (Pruned(removed=[], busy=[]), True))
```

The job's pip resolved `pyyaml-6.0.3-cp312-cp312-win_amd64.whl`, so CI's Windows interpreter is the runner image's Python
3.12. This box runs 3.14.7 and WSL runs 3.14.4. PB3807's self-test sets `Path.stat` to a stub that raises for a "vanished"
name, then asks `young.exists()`. Under 3.14, `Path.exists` is `os.path.exists(self)` (checked here with
`inspect.getsource`), so the stub is never consulted and the answer is True. Under 3.12, `Path.exists` calls `self.stat()`,
gets the stub's error and answers False. The test was correct on every interpreter the local gates have, and wrong on the
one CI has.

The test itself belongs to the #734 finisher: it must take existence through something the stub does not replace. This
note is the local-gate half that the CI invariant (CLAUDE.md Testing) requires: no local leg could run CI's interpreter.

## Acceptance (the shape that makes the next tool automatic, CLAUDE.md rule 5)

1. ONE toolchain manifest in the repository names the exact version of every tool a CI job or a local gate invokes (.NET
   SDK, Python, JDK, pwsh, git, gh, jq, and any other tool a job runs), the way `scripts/install-dotnet-sdk.sh` already
   names the SDK. It is the only place a version is written; `install-dotnet-sdk.sh`'s `DOTNET_SDK_VERSION` and
   `python-resolve.sh`'s 3.12 floor read it or are replaced by it (no second copy, rule 4).
2. **The manifest is kept at the latest release.** A freshness check reads each tool's newest stable release from its
   publisher and, when the manifest is behind, moves it forward in its own change. That change carries the hosts' update
   and is gated and landed like any other, so CI and the hosts move to the new version together. The check runs on a
   cadence the loop owns (a scheduled CI job, or a loop unit), and a manifest behind the latest release for longer than
   that cadence is reported, never silent. Identical is the invariant at every commit; latest holds within one cadence.
3. Every CI job installs those exact versions (`actions/setup-python`, `actions/setup-java`, a pinned pwsh, the SDK
   script) instead of using the runner image's. `windows-latest` is pinned to a named image, as the Linux jobs already are.
4. Every local host meets the manifest: the WSL setup (`scripts/wsl/setup-wsl.sh`) and the cloud setup
   (`scripts/cloud/setup-env.sh`) install from it, and the Windows box is held to it by a check that refuses or repairs a
   mismatch (the gate's preflight, or `scripts/hooks/tooling_check.py`, which already repairs and asks). The gate's
   verdict names the toolchain it ran under.
5. A drift test (a sibling of `DotnetSdkInstallDriftTests`) fails when a CI step invokes a tool the manifest does not name,
   or installs one other than from the manifest. A new tool in CI must then arrive pinned on the day it is added.
6. Each row this closes is marked (a) in PB1957's survey in the same change.

**Sites:** `.github/workflows/build-and-test.yml` (job `windows-self-tests` and every job that runs `python`, `python3`,
`java`, `pwsh`, `gh` or `jq`; the three `runs-on: windows-latest`), `.github/actions/setup-dotnet/action.yml`,
`scripts/install-dotnet-sdk.sh` (`DOTNET_SDK_VERSION`), `scripts/python-resolve.sh` (the 3.12 floor),
`scripts/wsl/setup-wsl.sh`, `scripts/cloud/setup-env.sh`, `scripts/hooks/tooling_check.py`,
`tests/WiseOwl.Cobol.Tests.Unit/DotnetSdkInstallDriftTests.cs`.

NEEDS-OPUS: the manifest's form, and how the Windows box is held to it, are design choices across CI, three host setups and
the gate.

Python 3.15.2 is proven on the scripts: `scripts/self_tests.py` ran all 129 self-tests GREEN under it on Windows (358 s).
Facts the implementation must carry:

- **semgrep cannot run on 3.15 yet:** semgrep 1.18x pins `ruamel.yaml.clib==0.2.15`, which has no cp315 wheel and does not
  build. It runs as a uv tool (`uv tool install semgrep --python 3.14 --managed-python`) on uv's own CPython 3.14.10, apart
  from the project interpreter. The manifest records that exception and its reason, and drops it when upstream ships a 3.15
  wheel.
- **The WSL git PPA was silently off:** the release upgrade to Ubuntu 26.04 had left the git-core source on `noble` with
  `Enabled: no`, so WSL stayed on 2.55 and apt reported nothing. Re-pointed to `resolute` and re-enabled. A host check must
  read the installed version, never trust that a source exists.
- **`scripts/wsl/setup-wsl.sh` hard-codes `uv python install 3.14`** under a comment saying "latest CPython everywhere":
  exactly the second copy this note's manifest removes.
- **Git for Windows refuses to upgrade while any MSYS process runs.** 75 orphaned `tail -F … | grep` Monitor pipelines and
  `lane_watch.sh` loops from sessions that had ended 10-24 to 10-26 were still running, and were terminated. The upgrade
  went through in a moment when no bash ran.
- **The .NET 11 preview** (11.0.100-preview.7) is left on both hosts: it is not a stable release, and the owner has not
  asked for previews.
- A session started before the PATH change keeps its old PATH. Python still resolves to 3.15.2 there, through the install
  manager's `python.exe` alias in WindowsApps, once the legacy 3.14 directories are gone.
