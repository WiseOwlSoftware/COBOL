# PB3885 — const-fold-zero-power-zero: 0 ** 0 with literal operands is constant-folded to 1; the size error condition is never raised

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S3) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\const-fold-zero-power-zero.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\const-fold-zero-power-zero\`.

## Summary

cobc 3.2 folds an exponentiation whose operands are both integer literals at compile time (configuration option
`constant-folding: yes`, the setting of `config/cobol2014.conf`). The folding returns the literal 1 whenever the
exponent is 0, including when the base is 0. The size error condition that ISO requires for a zero base with a
non-positive exponent is therefore never detected: `COMPUTE R = 0 ** 0 ON SIZE ERROR ...` executes the NOT ON SIZE
ERROR phrase and stores 1. The run-time routine for the same operation does detect the case (with
`-fno-constant-folding` the SIZE ERROR phrase is taken), so the compile-time and run-time paths disagree. The same
program under `-fno-constant-folding` shows a second defect (1 stored despite the size error), recorded separately as
`size-error-still-stores-power-zero-result`.

## Minimal test case

Fixed reference format (cobc's default), 11 lines, `records/const-fold-zero-power-zero.cob`:

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. CFPOW0.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 R PIC S9(5) VALUE 77.
       PROCEDURE DIVISION.
           COMPUTE R = 0 ** 0
             ON SIZE ERROR DISPLAY "SIZE ERROR, R=" R
             NOT ON SIZE ERROR DISPLAY "NO SIZE ERROR, R=" R
           END-COMPUTE
           STOP RUN.
```

```

```

## Expected result (per ISO)

ISO/IEC 1989:2023 8.8.1.2 rule 6 a) (checked): "If the value of an expression to be raised to a power is zero, the
exponent shall have a value greater than zero. Otherwise, the EC-SIZE-EXPONENTIATION exception condition is set to
exist and the size error condition is raised." The rules of 8.8.1.2 apply "regardless of the mode of arithmetic that is
in effect" (8.8.1.2, checked), so native arithmetic does not exempt the case.

14.7.5 (checked): the size error condition exists "if the rules for evaluation of exponentiation are violated" (case 1);
with the SIZE ERROR phrase specified, "the values of all of the resultant data items remain unchanged from the values
they had at the start of the execution of the arithmetic statement" (rule 1) and "control is transferred to the
imperative-statement specified in the SIZE ERROR phrase" (rule 3).

Expected output: `SIZE ERROR, R=+00077` (R keeps its initial 77).

Edition: the rule is in the edition `-std=cobol2014` claims. Annex E of the 2023 text (substantive changes since the
previous standard) lists no change to 8.8.1.2 or 14.7.5, and the 2009 committee draft that led to ISO/IEC 1989:2014
(CD 1.2, 2009-08-23) carries rule 6 a) in the same words, numbered 8.8.1.1 6) a) in that text (corrected by the
refuter: the record had numbered it 8.8.1.2 for 2014 too; 8.8.1.2 is the 2023 number).

Edition as recorded by the adjudicator: 2014. `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Class

Wrong output (the size error is not detected; the receiving item is changed; the NOT ON SIZE ERROR phrase runs).

## Our compiler (WiseOwl)

`cobol cfpow0.cob --std 2014 --run` (WiseOwl, built from main 6ed90bd1c): `SIZE ERROR, R=+00077`, exit 0. It matches
the ISO expectation.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/tree.c`, function `cb_build_binary_op`, the constant-folding branch taken when both operands are numeric
  literals (`cb_constant_folding`); in its `switch (op)`, the `case '^'` arm returns the literal 1 when the exponent
  value is 0 (or the base is 1) without testing for a zero base. A fix declines to fold when both the base and the
  exponent are 0 (and when the base is 0 and the exponent negative, which the arm already declines), leaving the
  operation to the run-time routine `cob_decimal_pow` (libcob/intrinsic.c), which detects it.
- The run-time path then needs the fix recorded in `size-error-still-stores-power-zero-result`.

## Draft issue

**Title:** `0 ** 0` with literal operands is constant-folded to 1; the size error condition is never raised

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1), `cobc -std=cobol2014 -x`.

Program (fixed format):

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. CFPOW0.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 R PIC S9(5) VALUE 77.
       PROCEDURE DIVISION.
           COMPUTE R = 0 ** 0
             ON SIZE ERROR DISPLAY "SIZE ERROR, R=" R
             NOT ON SIZE ERROR DISPLAY "NO SIZE ERROR, R=" R
           END-COMPUTE
           STOP RUN.
```

Steps: `cobc -std=cobol2014 -x cfpow0.cob && ./cfpow0`

Observed: `NO SIZE ERROR, R=+00001`.

Expected: `SIZE ERROR, R=+00077`. ISO/IEC 1989:2023 8.8.1.2 rule 6 a) (2014 carries the same rule): "If the value of an expression to
be raised to a power is zero, the exponent shall have a value greater than zero. Otherwise, the EC-SIZE-EXPONENTIATION
exception condition is set to exist and the size error condition is raised." 14.7.5: with ON SIZE ERROR the resultant
item is left unchanged and the SIZE ERROR phrase is executed.

Cause: `cb_build_binary_op` in cobc/tree.c folds `literal ** literal` and returns 1 for any zero exponent without
checking for a zero base. With `-fno-constant-folding` the run-time routine `cob_decimal_pow` detects the case and the
SIZE ERROR phrase is taken (but see the companion report: the receiving item is still set to 1).
