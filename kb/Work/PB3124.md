# PB3124 — landing_measure.py counts a stacked group's failure as a bounce of the PR its ref names

> flags: process-only

Source: enqueue unit 2026-10-13 ~07:36Z.

**Mechanism:** `scripts/orchestrator/landing_measure.py` `complete` takes every failed merge-group run whose head branch matches `/pr-<n>-` as a bounce of PR n (the `mine = [...]` filter near line 482; the docstring near line 444 and the help text near line 588 say "counts only failed merge-group runs as bounces"). GitHub builds each queued PR's merge group ON TOP of the groups ahead of it, so a group `gh-readonly-queue/main/pr-29-<base>` contains the PRs ahead; when one of those fails, the group of every PR behind it fails too and GitHub rebuilds them, but it REMOVES only the failing PR.

**Measured 2026-10-13:** PR #29 (fix-PB3117-lane-no-window) has exactly one AddedToMergeQueueEvent (06:28:02Z) and one RemovedFromMergeQueueEvent with reason `merged` (07:12:00Z); it was never removed for failed checks. Its three failed merge-group runs, 38356876801 (06:28:20Z), 38357100405 (06:30:37Z) and 38358556637 (06:45:47Z), were groups built on PRs #25/#27/#28 ahead, which failed ArchOracleDriftTests.TheRecordedBaseline_IsOneWellFormedManifest (two baselines, kb/Work PB3107). `landing_measure.py complete` printed "completed PR #29: merged 2026-10-13T07:12:00Z, 3 bounce(s)", and the enqueue unit had to name three bounce causes for bounces #29 never had.

**Harm:** the bounce count per landing (the PB3028 measurement and the first-after comparison it feeds) is inflated and misattributed to innocent pull requests, and the bounce-cause classification is asked for bounces that are other PRs'.

**Fix shape (for the implementer to confirm):** count a bounce from GitHub's own attribution, the PR's RemovedFromMergeQueueEvent with reason `failed_checks` (GraphQL `timelineItems(itemTypes:[REMOVED_FROM_MERGE_QUEUE_EVENT])`), keeping the failed runs as evidence; a self-test case with a stacked group that failed because of the PR ahead.

**Related:** PB3028, PB3107, PB3123.

## Recurrence 2026-10-15: a merge_conflict removal has no failed run

**Measured 2026-10-15:** PR #75 (worktree-wf_5579bfb3-423-11, PB3166). GraphQL `timelineItems(itemTypes:[ADDED_TO_MERGE_QUEUE_EVENT, REMOVED_FROM_MERGE_QUEUE_EVENT])` gives Added 17:46:11Z, Removed 18:02:26Z with reason `merge_conflict`, Added 18:35:31Z, Removed 18:48:15Z with reason `merged`. Its only merge-group run is `gh-readonly-queue/main/pr-75-99ef350c6...` (run 38786936537), success, 18:35:51Z to 18:47:51Z. A `merge_conflict` removal builds no merge group, so no failed run exists for it.

The enqueue unit recorded the bounce as its step 6b says (`landing_measure.py record --pr 75 --bounces 1 --bounce-causes conflict`). `landing_measure.py complete` then set `bounces` to the failed-run count, 0, and refused the record: `landing-measure: PR #75: 1 bounce cause(s) name more than the 0 bounce(s)` (the check at about line 158). Every later `complete` would refuse it again, so the record could never complete. It was worked around for the measurement only: `record --pr 75 --merged 2026-10-15T18:48:15Z --ci-wall-s 720 --pre-queue-reds 0` with a note naming this note. The defect itself is untouched.

**What it changes in the fix shape:** counting a bounce from RemovedFromMergeQueueEvent with reason `failed_checks` only still misses this arm. The removal events are the attribution for every bounce: every reason other than `merged` is a bounce (`failed_checks`, `merge_conflict`, and whatever else GitHub reports), and `merge_conflict` maps to the cause `conflict` mechanically. The self-test needs a case with a `merge_conflict` removal and no merge-group run. Sibling to check when it is fixed: `scripts/prune_worktrees.py` reads BOUNCED from its own GraphQL read of the open pull requests, a second reading of the same fact; the two should share one definition.

## Recurrence 2026-10-17: PR #149 landed through its carrier PR #190 (a new arm)

The mechanism is the same: `landing_measure.py complete` attributes merge-group runs to a pull request by the `/pr-<N>-` in the run's `headBranch` (about line 482: `mine = [x for x in runs if re.search(rf"/pr-{r['pr']}-", ...)]`), and that ref names only ONE pull request.

**Measured 2026-10-17:** PR #149 (branch `worktree-wf_ff4f514b-355-37`, kb/Work PB1099) was removed from the merge queue with reason `merge_conflict` at 2026-10-16T22:26:30Z (it conflicted with PR #139 ahead of it, in tests/WiseOwl.Cobol.Tests.Unit/RuntimeAbiPinDriftTests.cs). It was never re-queued: its successor branch `worktree-wf_3c440b32-c7b-7` carried it and landed as PR #190, merged 2026-10-17T21:04:20Z through the merge-group run `gh-readonly-queue/main/pr-190-2f4d2143...` (success, 20:53:54Z to 21:04:19Z).

GitHub then marked PR #149 MERGED at 21:04:21Z with the SAME merge commit as PR #190: `gh pr view 149 --json mergeCommit` and `gh pr view 190 --json mergeCommit` both give `b05001e4c446d69e1833a06f3c3bf84468911f2a`. PR #149's `RemovedFromMergeQueueEvent`/`AddedToMergeQueueEvent` timeline has only the one add (22:22:39Z on 10-16) and the one `merge_conflict` removal; there is no second add.

`landing_measure.py complete` (run by the enqueue unit at about 21:41Z on 2026-10-17) printed
`⚠ landing-measure: PR #149 merged but no successful merge-group run of build-and-test.yml names it — bounces and CI wall recorded as observed, the CI wall UNMEASURED`
and then
`⛔ landing-measure: PR #149: 1 bounce cause(s) name more than the 0 bounce(s)`
(the record carries `"bounces": 1, "bounce_causes": ["conflict"]` from the enqueue unit's step 6b, with a note naming the #139 conflict). The second line is the known merge_conflict arm above. The first is the new arm: a pull request that lands through a carrier pull request has no merge-group run naming it, so its CI wall is reported UNMEASURED although the carrier's run measured it, and nothing in the record says it landed through #190.

**What it adds to the fix shape:** a pull request whose `mergeCommit` equals another pull request's `mergeCommit` landed through that one. `complete` should record `landed_through: <carrier PR>` and take the carrier's merge-group run (or say plainly that the CI wall belongs to the carrier), never report the wall UNMEASURED. The self-test needs a carrier-landed record beside the merge_conflict one.

## Recurrence 2026-10-19: prune_worktrees.py reads a `merged` removal as a bounce

**Measured 2026-10-19:** `python scripts/prune_worktrees.py --brief`, run at about 2026-10-20T02:07Z (19:07 PDT) with the main checkout's `origin/main` not yet fetched past 9dfd2e772, printed `BOUNCED worktree-wf_65e0b527-80e-31 [worktree] — pull request #309 was removed from the merge queue (removed from the queue: merged at 2026-10-20T02:06:24Z; https://github.com/WiseOwlSoftware/COBOL/pull/309): ONE finisher fixes the branch and returns DONE ...`. `gh pr view 309 --json state,mergedAt` gave `MERGED`, `2026-10-20T02:06:24Z`, merge commit 4e51b3db0. After `git fetch origin` the same survey no longer listed it BOUNCED.

**Mechanism:** `scripts/prune_worktrees.py` (the `pull_requests` reader, about lines 622-627) sets the bounce text from the newest RemovedFromMergeQueueEvent whatever its reason, so a `merged` removal reads as a bounce while GraphQL still lists the PR OPEN or the local origin/main is stale, and the survey directs a finisher at a merged branch. This is the sibling the 2026-10-15 recurrence names (two readings of the same fact).

**What it adds to the fix shape:** one shared definition of a bounce (every removal reason except `merged`), used by both `landing_measure.py` and `prune_worktrees.py`; a self-test case with a `merged` removal on a still-OPEN PR. PB3124 carries no `**Sites:**` block, so none was extended here.
