# PB3124 — landing_measure.py counts a stacked group's failure as a bounce of the PR its ref names

> flags: process-only

Source: enqueue unit 2026-10-13 ~07:36Z.

**Mechanism:** `scripts/orchestrator/landing_measure.py` `complete` takes every failed merge-group run whose head branch matches `/pr-<n>-` as a bounce of PR n (the `mine = [...]` filter near line 482; the docstring near line 444 and the help text near line 588 say "counts only failed merge-group runs as bounces"). GitHub builds each queued PR's merge group ON TOP of the groups ahead of it, so a group `gh-readonly-queue/main/pr-29-<base>` contains the PRs ahead; when one of those fails, the group of every PR behind it fails too and GitHub rebuilds them, but it REMOVES only the failing PR.

**Measured 2026-10-13:** PR #29 (fix-PB3117-lane-no-window) has exactly one AddedToMergeQueueEvent (06:28:02Z) and one RemovedFromMergeQueueEvent with reason `merged` (07:12:00Z); it was never removed for failed checks. Its three failed merge-group runs, 38356876801 (06:28:20Z), 38357100405 (06:30:37Z) and 38358556637 (06:45:47Z), were groups built on PRs #25/#27/#28 ahead, which failed ArchOracleDriftTests.TheRecordedBaseline_IsOneWellFormedManifest (two baselines, kb/Work PB3107). `landing_measure.py complete` printed "completed PR #29: merged 2026-10-13T07:12:00Z, 3 bounce(s)", and the enqueue unit had to name three bounce causes for bounces #29 never had.

**Harm:** the bounce count per landing (the PB3028 measurement and the first-after comparison it feeds) is inflated and misattributed to innocent pull requests, and the bounce-cause classification is asked for bounces that are other PRs'.

**Fix shape (for the implementer to confirm):** count a bounce from GitHub's own attribution, the PR's RemovedFromMergeQueueEvent with reason `failed_checks` (GraphQL `timelineItems(itemTypes:[REMOVED_FROM_MERGE_QUEUE_EVENT])`), keeping the failed runs as evidence; a self-test case with a stacked group that failed because of the PR ahead.

**Related:** PB3028, PB3107, PB3123.

## Recurrence 2026-10-15: a merge_conflict removal has no failed run

**Measured 2026-10-15:** PR #75 (worktree-wf_5579bfb3-423-11, PB3166). GraphQL `timelineItems(itemTypes:[ADDED_TO_MERGE_QUEUE_EVENT, REMOVED_FROM_MERGE_QUEUE_EVENT])` gives Added 17:46:11Z, Removed 18:02:26Z with reason `merge_conflict`, Added 18:35:31Z, Removed 18:48:15Z with reason `merged`. Its only merge-group run is `gh-readonly-queue/main/pr-75-99ef350c6...` (run 38786936537), success, 18:35:51Z to 18:47:51Z. A `merge_conflict` removal builds no merge group, so no failed run exists for it.

The enqueue unit recorded the bounce as its step 6b says (`landing_measure.py record --pr 75 --bounces 1 --bounce-causes conflict`). `landing_measure.py complete` then set `bounces` to the failed-run count, 0, and refused the record: `landing-measure: PR #75: 1 bounce cause(s) name more than the 0 bounce(s)` (the check at about line 158). Every later `complete` would refuse it again, so the record could never complete. It was worked around for the measurement only: `record --pr 75 --merged 2026-10-15T18:48:15Z --ci-wall-s 720 --pre-queue-reds 0` with a note naming this note. The defect itself is untouched.

**What it changes in the fix shape:** counting a bounce from RemovedFromMergeQueueEvent with reason `failed_checks` only still misses this arm. The removal events are the attribution for every bounce: every reason other than `merged` is a bounce (`failed_checks`, `merge_conflict`, and whatever else GitHub reports), and `merge_conflict` maps to the cause `conflict` mechanically. The self-test needs a case with a `merge_conflict` removal and no merge-group run. Sibling to check when it is fixed: `scripts/prune_worktrees.py` reads BOUNCED from its own GraphQL read of the open pull requests, a second reading of the same fact; the two should share one definition.
