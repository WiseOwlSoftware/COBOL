# PB99 — LANDED — `VALUE 1.0E12345` / `MOVE 1.0E+400 TO F` → CS0594 from Roslyn; `MOVE 1.2345678901234567890123E+3 TO N` → 1234.56789012345685803008

> ⚙ **flags:** crash (a backend failure, not a COBOL diagnostic), wrong-answer, silent, under-rejects · found
> 2026-08-18 probing [[PB66]]'s literal legs · **landed 2026-08-18** (DEVLOG 1323).

**Measured** (`--std 2023`, before):
```
       01 F1 USAGE FLOAT-LONG VALUE 1.0E12345.        -> CS0594 (backend), no COBOLNET diagnostic
       01 F2 USAGE FLOAT-LONG VALUE 0.0E+5.           -> compiled (SR4: a zero significand requires a zero exponent)
       01 F4 ... VALUE 1.2345678901234567890123456789012345678E+2.   -> compiled (SR2: 1..36 digits — 40 here)
       MOVE 1.2345678901234567890123E+3 TO N1        -> N1 = 1234.56789012345685803008 (binary64), the exact
                                                        value is 1234.5678901234567890123 (8.3.3.3.3 GR5; a MOVE
                                                        is not native arithmetic)
       MOVE 1.2345678901234567890123E+3 TO E1        -> 1.2345678901234570000000000E+03 into PIC 9.9(25)E+99 —
                                                        D21's exact channel defeated at the literal
       PERFORM VARYING N1 FROM 1.0E+3 ...            -> N1 = 999.99999999999999916 (the binary64 1E+23 product)
       ARITHMETIC IS STANDARD-DECIMAL: COMPUTE N1 = 1.2345678901234567890123E+3  -> 17 digits kept (a double
                                                        on the way; 8.8.1.5.2 r1 wants the exact decimal128 operand)
```

**Spec:** §8.3.3.3.3 SR1–SR4 (form), r3 "The maximum permitted value and minimum permitted value of the exponent
is implementor-defined", GR5 "the algebraic product of the value of its significand and … ten to the power of the
exponent"; §8.8.1.3 (native arithmetic is the implementor's method for an arithmetic EXPRESSION / STATEMENT — the
binary64 latitude of numeric design D16 lives there and nowhere else); §8.8.1.5.2 r1 (standard-decimal: operands
converted to the decimal128 intermediate); §13.18.63.3 SR2 (a VALUE within the range the USAGE indicates).

**Mechanism:** the lexer's `FLOAT_BODY` admitted any digit count and any sign; nothing checked SR2/SR3/SR4;
`EmitText.UnscaledLit` rendered every floating literal as a C# double literal (D16 for arithmetic — but every
OPERAND position rode the same NumX), so a value beyond binary64 was Roslyn's error and a long significand
rounded, in MOVE / relation / VARYING / function-argument positions and under STANDARD-DECIMAL alike.

## As built (DEVLOG 1323)

- `NumericLiteral.CheckFloatingPointForm` (SR2/SR3/SR4 → COBOLNET1661) at the ONE normalizer both funnels share
  (`DataBinder.NormalizeNumericLiteral`); `NumericLiteral.TryParseExact` — the ONE exact parser (the binder's
  checks, the renderer, `ValueInitializer.TryParseFloatLiteral` delegate to it); `FitsBinaryFloat`.
- The implementor-defined exponent range (CONFORMANCE.md §7 A.1 item 82; the A.3 item-1 row → Claimed):
  `ExpressionBinder.CheckLiteral` diagnoses a native arithmetic literal beyond binary64 and a standard-decimal one
  beyond decimal128 (`CobolDec.FromParsed` in a try); `ValidateValueCategory` diagnoses a VALUE beyond the FLOAT
  subject's binary form (both funnels — item VALUE and level-88); COBOLNET1661 everywhere, never CS0594.
- `NumericRenderer.LiteralOperandNum` (a `BoundNumericLiteral` — every operand position) and
  `RenderOperandLike` (PERFORM VARYING FROM / BY, whose format admits only identifier / index-name / literal) render
  a floating literal as the EXACT `CobolDec.FromParsed(sig, exp10, mode)` on the Dec lane; `LiteralNum` (a
  `BoundNumLiteral` inside an arithmetic expression / statement) does so under STANDARD-DECIMAL and keeps D16's
  binary64 natively. Every consumer already accepted a Dec operand (the PB84 landing / store funnel; `Real()`
  converts where a binary64 body wants a double). D16's paragraph in COBOLNET_NUMERIC_DESIGN.md is corrected.
- Goldens `2023/pb99_floating_literal_extremes` (36-digit significand + 4-digit exponent into a floating-point
  numeric-edited VALUE; the binary64 / binary32 edges), `pb99_floating_literal_operand_exact`,
  `pb99_floating_literal_standard_decimal`; negatives `pb99-floating-literal-form`, `pb99-floating-literal-range`.
  Inventory SR-8.3.3.3.3-1..4 / GR-8.3.3.3.3-5 → CONFORMS.
- Not this note: `COMPUTE N1 = 1.5E+3 * 2` into a 20-decimal item still lands 3000.000000000000008388608 — the
  in-carrier binary64 product of the float→fixed landing (the CONFORMANCE.md §3 conversion-manner determination;
  the open analysis is [[PB90]]).
