# PB99 — OPEN — `01 F USAGE FLOAT-LONG VALUE 1.0E12345.` / `MOVE 1.0E12345 TO F` → "backend compilation failed: CS0594 Floating-point constant is outside the range of type 'double'"

> ⚙ **flags:** crash (a backend failure with a C# error, not a COBOL diagnostic), under-rejects · found 2026-08-18
> probing [[PB66]]'s literal legs.

**Measured** (`--std 2023`):
```
       01 F1 USAGE FLOAT-LONG VALUE 1.0E12345.        -> CS0594 (backend), no COBOLNET diagnostic
       01 F2 USAGE FLOAT-LONG VALUE 0.0E+5.           -> compiles (SR4: a zero significand requires a zero exponent)
       01 F3 USAGE FLOAT-LONG VALUE -0.0E+0.          -> compiles (SR4: neither part may carry a negative sign)
       01 F4 ... VALUE 1.234567890123456789012345678901234567890E+2.   -> compiles (SR2: 1..36 significand digits — 40 here)
       MOVE 1E10 TO F                                 -> COBOLNET1639 "'1E10' is not defined" (SR2: the significand shall include a
                                                         decimal point — rejected, but as an undefined word, not as the literal-form error it is)
```

**Spec:** §8.3.3.3.3 SR1–SR4 (form), r3 "The maximum permitted value and minimum permitted value of the exponent
is implementor-defined" — COBOL.NET has never documented one (CONFORMANCE.md §7 / Annex A.1); D16 evaluates a
procedure-division floating-point literal as binary64, so the effective maximum is ±308 there — and beyond it the
generated C# double literal overflows and Roslyn, not the compiler, rejects the program.

**Mechanism:** the lexer's `FLOAT_BODY` admits any digit count in either part and any sign; no binder check reads
the form (`ExpressionBinder.CheckLiteral` counts digits only for the 31/18 fixed-point cap; the VALUE funnel
`NormalizeIfNumericLiteral` normalizes separators only); `EmitText.UnscaledLit` renders the text as a C# double
literal verbatim.

**Fix shape:** ONE form check at the ONE normalizer both funnels share (`DataBinder.NormalizeNumericLiteral` →
`NumericLiteral.Normalize`, or a sibling `NumericLiteral.CheckFloatingPointForm`) — SR2 (point present, 1..36
digits), SR3 (≤ 4 exponent digits), SR4 (zero significand → zero exponent, no negative signs) → a new diagnostic;
then the implementor-defined exponent range: document it (CONFORMANCE.md §7 / A.1) and diagnose a literal beyond
it at compile time instead of emitting an overflowing C# literal — natively ±308 (binary64, D16); under
ARITHMETIC IS STANDARD-DECIMAL the intermediate is decimal128 (§8.8.1.5.2 — exponent up to 6144), so the literal
should reach the Dec lane exactly there rather than through a double (a `COMPUTE X = 1.0E+400 / 1.0E+399` that the
mode can represent must not fail). A floating-point numeric-edited receiver with a four-digit exponent
(`PIC 9(3)E+9999`) can hold values no binary64 literal can spell — the exact-decimal literal channel is the same
fix. Sweep: `1E10` should be the literal-form diagnostic, not "not defined".
