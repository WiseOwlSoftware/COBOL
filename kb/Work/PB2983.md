# PB2983 - LANDED (wave 1059 group A)

## Landing (wave 1059 group A, 2026-10-11)

**Re-probe (before):** `01  <U+1000D><U+1000E> PIC X(2) ZZZ.` (two supplementary-plane letters) reported the parser error at
`(5,26)` where `ZZZ` stands in character position 24, and `*> c` after the period reported the gate at `(5,24)`
(`.*>` at positions 23-24): one line, two column units. With a leading TAB the parser said `(5,20)`, character position 18.
**After:** `(5,24)` / `(5,18)`; the continuation, free-form and copybook arms agree (`DiagnosticPositionTests`).

**Rule.** ISO 6.1 1) a): reference format is described "in terms of character positions" (`cite.py --check 6.1 "Reference format is
described in terms of character positions"` -> OK 6.1 1) a)); 6.3.1 numbers the positions; DOC-A.1-157 makes the position
one character, not one UTF-16 unit (PB1966). The diagnostic column is the same unit.

**Fix (the structure, not the symptom - the estimate said "the map converts the parser's index"; the right place is the span
structure).** The source map already converts the parser's UTF-16 index: `LineOrigin.Locate` extends a span one resultant unit
per physical column. What was wrong was the spans' SOURCE column unit: `TextSite.Span` set it to an expanded UTF-16 index
(no tab) or a UTF-16 index of the raw line (`TabMap`), while the gates' `Col` used `PositionAt` (positions). Now:

- `PhysicalLines` keeps a `ColumnMap` (the old `TabMap`; renamed, every caller changed, `ToExpanded` deleted - it had no
  production caller) for every line holding a tab OR a supplementary-plane character, mapping each expanded index to the
  character POSITION of the physical line; the two units of a supplementary character and every space a tab filled map to one position.
- `TextSite(Line, Index, Columns)` loses its `Column` field; `Col(i)` and `Span` ask the map, and `Spans` ends a span wherever the
  physical columns stop running one for one (at each tab, and at each supplementary character: its second unit maps to the same position).
- Nothing else changed: `LineOrigin.Locate`, `OriginWriter` and COPY/REPLACE already carry spans as units-per-position runs.

Sibling sweep: every `Col(text, i)` caller (10) lost its text argument; `DirectiveIndicatorIndex` now returns a position
through the same map; the free-form arm shares `TextSite`. Not reached (named, not hidden): text a stage WRITES (a REPLACE
replacement) takes one span at its start and so counts its own supplementary characters as units after it - the
origin of written text has no source to map.

Goldens: `negative/pb2983-supplementary-letters-parser-error-column` (`(12,24): error COBOL1941`),
`negative/pb2983-supplementary-letters-gate-error-column` (`(11,24): error COBOL2495`),
`DiagnosticPositionTests.FixedForm_SupplementaryCharactersCountOnePosition` (plain, tab), `..._ParserAndGateOnOneLine_NameTheSameUnit`,
`..._FixedFormContinuation_...`, `..._FreeForm_...`, `..._Copybook_...`; unit `PhysicalLinesTests.ColumnMapFollowsTheDefinition_AndNoTabSurvives`
(every line of up to four of {X, TAB, space, supplementary}, against an independent oracle), `CharacterPositionsTests.TheColumnMap_IsInCharacterPositions`.

LEARNED: `Preprocessor/PhysicalLines.cs#ColumnMap` is the ONE index-to-position map (expanded index -> character position of the
physical line; present only where a tab or supplementary character was; `ToPhysical` continues one for one past the end). The
builder's `TextSite` (`ReferenceFormatProcessor.LogicalLineBuilder.cs`) is the only place that turns it into a diagnostic column
(`Col`) AND a span (`Spans`) - never compute a column from a text any other way. The trap: three units were in play (UTF-16
index in the span, character position in the gate, UTF-16 index of the raw line after a tab) and each looked right alone.

# PB2983 — column units disagree for supplementary characters

Filed 2026-10-10 by the train 1055 lander from the wave 1055 B report
(`E:\COBOL-coord\scratch\reports\w1055b-PB1688-report.md`, lead 2; first seen as w1053c lead 2). PB1966 (landed)
made the reference-format AREAS count character positions, not UTF-16 code units; the COLUMN a diagnostic reports was
not unified with it.

**Repro:** a fixed-form line whose Area B holds a word or national literal with a supplementary-plane character
(for example U+1D400) ahead of a syntax error. A parser diagnostic (ANTLR's char index, mapped by the source map)
counts the supplementary character as two columns; a reference-format gate diagnostic on the same line counts it
as one. The two report different columns for one source position.

**Sites:** `src/WiseOwl.Cobol.Frontend/Preprocessor/ReferenceFormatProcessor.LogicalLineBuilder.cs:371` (`TextSite.Col`,
character positions through `CharacterPositions.PositionAt`) against `src/WiseOwl.Cobol.Frontend/Common/SourceLineMap.cs:73`
(`LineOrigin.Locate(int column)`, fed the parser's UTF-16 index).

**Fix shape:** one column unit for every diagnostic: the map converts the parser's code-unit index to a character
position (the PB1966 measure) before it reports, with a golden that puts a supplementary character ahead of both a
parser error and a gate error on one line.
