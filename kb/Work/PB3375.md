# PB3375 — record_verdicts silently blanks a row's notes

Filed 2026-10-18 from wave 1119 group E's report (`E:\COBOL-coord\scratch\reports\w1119e-PB870-report.md`, "New defects"
item 1), the root of PB870's finding. Related: `kb/Work/PB959.md` (landed) documents the behavior as "a statement, not
evidence"; `kb/Work/PB480.md` records it as a trap. It is a trap, not a contract: nothing refuses it.

## What happens

`merged()` (`scripts/spec/record_verdicts.py:138`): for a record that is not witness-only, `source = rec`, so every
statement field including `notes` takes the record's value, and an absent `notes` becomes empty. A non-empty `notes`
(adjudication prose, retired-witness marks) is lost with no message.

## Fix shape (from the report)

Refuse, or require an explicit `notes` restatement, when a record with a verdict would replace non-empty `notes` with
empty. Add a unit test. Check `audit_witness_loss.py` still reads the retirement marks.

## Recurrence 2026-10-24 (PB3665's branch, filed by the operator)

PB3665's round-2 branch review (R2-1, low) found the same loss: the verdict record for `SR-14.9.22.3-1` on
`worktree-wf_17b59ed2-4ae-4` restated CONFORMS without a `notes` field, so `record_verdicts.merged` blanked the row's whole
PB856 adjudication note (4198 of 4214 rows carry notes). Once that branch lands, the row's notes need restoring from
its history, and the fix shape above stands.
