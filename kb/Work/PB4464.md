# PB4464 - a method's OPTIONS FLOAT-BINARY does not reach the method's own data (SUSPECTED, UNPROBED)

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs` `DataBinder.BindEntry` (line 5108 on branch
worktree-wf_7d06ed65-e14-4, PR #1045): `PicInfo.FloatItem(entryUsage, usagePhrases.Endianness is FloatEndianness.Unspecified ?
State.Configuration.Options.FloatBinaryEndianness : usagePhrases.Endianness)`. The method data leg is `OoDataBinder.BindMethodData`
(see the comments at DataBinder.cs:789 and :5365). The model is `OptionsModel.FloatBinaryEndianness`
(`Binding/OptionsModel.cs:39`), set at `Binding/OptionsBinder.cs:74`.

**Suspicion. NOT PROBED: no compile was run for this note.** `State.Configuration` is the class half's slice. A method may carry
its own OPTIONS paragraph; section 11.9.8 (FLOAT-BINARY clause, checked with `cite.py --check 11.9.8`) implies the clause for data
items without an endianness phrase in the scope it governs. If `BindMethodData` binds a method's LOCAL-STORAGE through `BindEntry`
while `State.Configuration` still names the class half, a `FLOAT-BINARY-32` local in a method that says
`OPTIONS. FLOAT-BINARY IS HIGH-ORDER-LEFT.` gets the class's endianness and its REDEFINEd byte image is in the wrong order: a
silent wrong answer in a byte-observable program, the same root as the method-OPTIONS-scope lead that was fixed for other clauses.

**Probe.** A method with `OPTIONS. FLOAT-BINARY IS HIGH-ORDER-LEFT.`, a `FLOAT-BINARY-32` local and a 4-byte alphanumeric REDEFINES
of it, VALUE 1.0, DISPLAY the bytes; compare with the same item in a class whose own OPTIONS carries the clause and with the ISO
GR19a/b order. If confirmed: thread the method's ConfigurationSource into the entry binder instead of reading
`State.Configuration`, and sweep every other OPTIONS clause read through `State.Configuration` on the method path.

## Landed

**Re-probe (wave 20261841, own build: `cobol probe1.cob --source-format free --run`).** A class with no OPTIONS and a method
`M1` carrying `OPTIONS. FLOAT-BINARY DEFAULT IS HIGH-ORDER-RIGHT.`, a `FLOAT-BINARY-32` LOCAL-STORAGE item VALUE 1.5 moved to
`PIC X(4)`: FUNCTION ORD of bytes 1 and 4 printed `64 1` (big-endian), where 11.9.8.3 SR3 with 13.18.60.4 GR19 b) requires
little-endian `1 64`. The suspicion was right: a silent wrong byte order.

**Root.** `DataBinder.BindEntry` read `State.Configuration.Options.FloatBinaryEndianness`, the class half's slice, for every
entry, while `OoDataBinder.BindMethodData` bound the method's own model (`OoMethodSymbol.MethodOptions`, folded over the
class's) and handed it only to the statement binder (`ProcedureBindState.Options`) and the emitter (`EmitContext.Options`).
The data phase had no reader of it. **Fix.** `OoDataBinder.EntryOptions` (`BindingMethod?.MethodOptions ?? Options`) is the data
phase's one answer; `BindEntry` reads it; `EntryOptionsReaderDriftTests` refuses a direct slice read in the entry binder.
**Sweep.** Every reader of an `OptionsModel` field in `src/` (grep on `.Arithmetic`, `.DefaultRounding`,
`.IntermediateRounding`, `.FloatBinaryEndianness`, `.Initialize`): the statement and emission readers go through the scoped
overrides, `StorageFormPass` already prefers `MethodOptions`, and `FloatBinaryEndianness` at `BindEntry` was the only data-phase
reader. **Goldens.** `conformance-suite/cases/11.9.8-FLOAT-BINARY/pb4464_method_options_float_binary` (accept 2014, 2023: a
method that overrides, inherits, folds, an item's own phrase, the object's data) and its refusal below 2014.
