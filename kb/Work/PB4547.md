# PB4547 — search-subscripted-nested-table-refused: COBOL 2023: SEARCH of a nested table does not accept the enclosing table's subscript (SEARCH H (GI): "unexpected (, expecting WHEN")

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

cobc 3.2 refuses a SEARCH statement whose identifier-1 is a table nested in another table and carries the subscript of
the enclosing table (`SEARCH H (GI)`): "syntax error, unexpected (, expecting WHEN". ISO/IEC 1989:2023 allows
identifier-1 to be subscripted at every level except the one being searched. Earlier text forbade any subscript on
identifier-1: ISO/IEC 1989:2002 and the 2009 committee draft that led to 2014 both say "Identifier-1 shall not be
subscripted or reference modified". So the form is established only for COBOL 2023, which GnuCOBOL 3.2 does not claim
to implement. The unsubscripted form `SEARCH H` is accepted and runs. Class: feature missing (COBOL 2023). Fuzz
programs: fz00035 and 9 more (night fuzz-batch-3000-20261103, slice D1).

## Minimal test case

Free reference format.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. SR1.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 T-VALS PIC X(6) VALUE "123789".
01 T REDEFINES T-VALS.
   05 G OCCURS 2 TIMES INDEXED BY GI.
      10 H PIC 9 OCCURS 3 TIMES INDEXED BY HI.
PROCEDURE DIVISION.
    SET GI TO 2
    SET HI TO 1
    SEARCH H (GI)
        AT END DISPLAY "NOT FOUND"
        WHEN H (GI, HI) > 7
            DISPLAY "FOUND " H (GI, HI)
    END-SEARCH
    STOP RUN.
```

## Environment

`cobc (GnuCOBOL) 3.2.0`, WSL2 Ubuntu x86_64. Compiled with `cobc -x -free -std=cobol2014 -o p sr1.cob`; no executable
is produced. The default dialect (`cobc -fsyntax-only -free sr1.cob`) gives the same errors. GnuCOBOL 3.2 has no
COBOL 2023 dialect. Control: the same program with `SEARCH H` (no subscript) compiles and its run prints `FOUND 8`,
exit 0.

## Observed result

Compile, exit code 1:

```text
sr1.cob:12: error: syntax error, unexpected (, expecting WHEN
sr1.cob:14: error: syntax error, unexpected WHEN
sr1.cob:16: error: syntax error, unexpected END-SEARCH
```

## Expected result (per ISO)

Under ISO/IEC 1989:2023 the program is legal and prints `FOUND 8` (G (2) holds 7, 8, 9; the first element greater than
7 is the second).

- §14.9.37.3 2) (checked): "The data description of identifier-1 shall contain an OCCURS clause with an INDEXED phrase
  and identifier-1 shall not be subscripted at the level for which the SEARCH is applicable." The subscript GI is at the
  level of G, not at the searched level of H.
- §14.9.37.3 3) (checked): "Identifier-1 may be contained within one or more other tables, for which the subscripting is
  still required." H is contained in G, so the subscript for G is the one the rule speaks of.
- §14.9.37.3 1) (checked) forbids only reference modification: "Identifier-1 shall not be reference-modified."

Edition: 2023. ISO/IEC 1989:2002 (SEARCH syntax rule 1) and the 2009 committee draft that led to 2014 (the same rule)
read "Identifier-1 shall not be subscripted or reference modified", which forbids the outer subscript. Rules 2 and 3
above appear in the 2023 text and in its 2021 committee draft. Annex E of the 2023 standard lists no SEARCH change, and
no public text of the published 2014 standard was available, so the change cannot be shown to be in 2014. This is a
COBOL 2023 feature request, not a defect against `-std=cobol2014`.

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`, as reported by the adjudicator): compiles with no
diagnostic; the run prints `FOUND 8`, exit code 0 (the unsubscripted control prints the same).

## Fix site

`cobc/parser.y` (read in the GnuCOBOL 3.2 release source (gnucobol-3.2.tar.xz)), rule `search_body`: identifier-1 is
`table_name`, which is a `qualified_word` with no subscript alternative, so a parenthesized subscript after the table
name is a syntax error.

## Vetting (2026-11-04)

Owner decision 2026-11-04: "filed as a feature request indicating it rejects a future dialect feature"; the note keeps `upstream_edition: 2023` and `upstream_class: feature-missing`. Vetted SOUND (refuter agrees) only as a feature request: 14.9.37.3 2) allows identifier-1 to be subscripted except at the searched level and 3) lets it be contained in other tables (cite.py --check OK), but the 2002 text and the 2009 CD say "shall not be subscripted or reference modified", so cobc's refusal is correct for every dialect it has (neither 3.2.0 nor 3.3-dev has a cobol2023 dialect). It is not on the tracker (bugs-313 and 314 differ). The report must say it asks for a future-dialect feature, never a 3.2 bug, and the 2014 edge is unproven (the 2014 FCD was not read). The matching defect on our side is PB4577.


Owner decision, revised 2026-11-04 (asked with this evidence, answered "Treat 2014 as allowing it"): COBOL 2014 allows the enclosing tables' subscripts on identifier-1. The 2002 text (t2002.txt:27472) and the 2009 CD 1.2 (t2009.txt:29403) say "Identifier-1 shall not be subscripted or reference modified"; the later drafts, 202x CD 1.3 (14.9.40.3, p. 794) and 2023 CD2, carry the 2023 rules 2) and 3); and 2023 Annex E, which lists the substantive changes since 2014 including relaxations (E.3, item 43), has no SEARCH entry, so the relaxation came in the final 2014 standard, after the 2009 CD (VCR row 7.13 reads Annex E the same way). The 2014 text itself is not held. So this is a bug against `-std=cobol2014` (refused legal source), reported to `bugs`, and its report states this edition reasoning in its why section. The first decision (a feature request for a future dialect) rested on the 2009 CD and is superseded.

Owner decision, final 2026-11-04 (asked with the 2014 FCD evidence, answered "Revert: 2023-only"): the 2014 cycle's FCD 1.0 (WG4, 2010-07-01, the final committee draft that became ISO/IEC 1989:2014; `E:/COBOL-coord/specs-drafts/t2014.txt` line 32933) still says "Identifier-1 shall not be subscripted or reference modified", like 2002 and the 2009 CD 1.2. The relaxation in 2023's 14.9.37.3 rules 2) and 3) is therefore a 2023 change, and 2023 Annex E omits it: its silence is not proof that a rule was in 2014 (PB4608). This supersedes the revision above, which inferred 2014 from Annex E's silence. So this is a feature request for the 2023 rule (GnuCOBOL has no 2023 dialect, and its refusal is correct for every dialect it has), reported as one that rejects a future dialect's feature, as first decided.
