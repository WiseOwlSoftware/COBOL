# PB216

Found by the cluster-B review fleet on the pre-commit [[PB169]]–[[PB172]] tree, 2026-08-31, and confirmed by
running it. PB169 moved the STATUS literal off the arithmetic funnel and onto
`ExpressionBinder.LiteralOperand` — THE one §8.3.3 literal→operand mapping — and then screened exactly two of
the six shapes that mapping can return (`BoundNumericLiteral` for SR3, `BoundStringLiteral{Value.Length:0}` for
SR4). The rest reached `NumericRenderer`, whose figurative / ALL-literal / boolean arms are LOUD.

**MEASURED BEFORE THE FIX** (`--std 2023`, strict, on the wave tree):

    STOP RUN WITH ERROR STATUS SPACE.        -> compiles clean; run-time NotImplementedCobolFeatureException
                                                "figurative 'S' in a numeric context"           (rc 127)
    STOP RUN WITH ERROR STATUS ALL "5".      -> clean; run-time "bound operand 'BoundAllLiteral'" (rc 127)
    STOP RUN WITH ERROR STATUS B"01".        -> clean; run-time "boolean literal in a numeric context" (rc 127)
    STOP RUN WITH ERROR STATUS B"1" & B"0".  -> clean; the same, via the boolean CONCATENATION fold
    01 KFRAC CONSTANT AS 1.5. … STATUS KFRAC -> clean, exits 1 — SR3 never asked

**⛔ THE REMEDY IS A RENDERING, NOT A SIXTH REJECTION ARM, and getting that backwards would have minted the
very defect PB169 exists to close.** Every citation `cite.py --check`ed:

  * §8.3.3.6.3 SR1 — "A figurative constant may be used whenever 'literal' appears in a format or when a rule
    allows it", with two restrictions: (a) "If the literal is restricted to a numeric literal, the only
    figurative constant permitted is ZERO (ZEROS, ZEROES) without the ALL phrase", and (b) "A figurative
    constant shall not be specified where a syntax rule prohibits it".
  * §14.9.42.3 SR3 — "**If** literal-1 is numeric, it shall be an integer." The CONDITIONAL is the proof that
    literal-1 is NOT restricted to a numeric literal, so SR1 a does not narrow it; SR2/SR3/SR4 prohibit nothing
    about class, so SR1 b does not bite either.
  * §8.3.3.6.4 GR3 NOTE 2 — "For example, when the figurative constant appears in a DISPLAY, **STOP**, STRING, or
    UNSTRING statement, it is one character." The standard names the STOP statement BY NAME and gives the
    length; GR3 b is the rule (one character for anything other than `ALL literal-1`), GR3 c gives
    `ALL literal-1` the length of literal-1.
  * §14.9.42.4 GR5 leaves the VALUE constraint to the implementor, and `docs/CONFORMANCE.md` item 192 already
    publishes this compiler's determination: a non-numeric operand's digit characters decode as an unsigned
    integer, a non-digit position contributing no digit (`CobolNum.FromAlphanumeric`).

So `STATUS SPACE`, `STATUS ALL "5"` and `STATUS B"01"` are CONFORMING SOURCE whose values the published
determination already fixes. The code contradicted the determination — the identical doc-vs-code divergence
PB169.md cites as its own rationale, reproduced one literal shape later inside the change that closed it.

**THE STRUCTURAL ROOT is the two-arm shape, in one method.** The identifier arm got a completeness structure
(`AdmittedStatusItem`, asked through the ONE §8.5.2.1 classifier); the literal arm was two ad-hoc `is` patterns
over a six-shape mapping. That asymmetry IS the defect generator — and it also explains the fourth entry: SR3
and SR4 were written inside the `sp.literal()` PARSE ARM, while §13.10.4 GR1 ("the effect of specifying
constant-name-1 in other than this entry is as if literal-1 … were written where constant-name-1 is written")
routes a constant-name's substituted literal through the `sp.dataReference()` arm. §12.3.7.4 GR11 does the same
for a symbolic character.

**FIXED BY** (landed with the wave):

  * `ControlFlowBinder.ScreenStatusOperand` — ONE screen over the BOUND SHAPE, reached from BOTH parse arms, so
    a constant-name and a symbolic character are screened exactly as the literal they substitute.
  * `NumericRenderer.StatusNum` — the GR5 interpretation of a non-numeric literal-1 of ANY form, through
    `OperandText.AsString`, which is already THE ONE operand→character-image reader and already carries
    §8.3.3.6.4 GR3 b/c (PCS-aware for HIGH-/LOW-VALUE). One arm covers figurative, ALL, symbolic-character,
    boolean, national, hex and concatenation, so the NEXT literal form needs no edit.
  * A NULL arm: §8.3.3.6.2 lists no NULL format — NULL is a predefined address / object reference (§8.4.3.10.1)
    and §8.4.3.10.3 SR1 confines it to an INITIALIZE/SET sending operand, a prototype argument, or a
    pointer-or-object-reference relation condition. It is neither identifier-1 nor literal-1 here.

**MEASURED AFTER**, each value DERIVED from the published determination before the run: `SPACE`/`HIGH-VALUE`/
`LOW-VALUE`/`QUOTE` ⇒ 0 (one character, no digit); `ZERO` and `ALL ZEROS` ⇒ 0; `ALL "5"` ⇒ 5; `ALL "07"` ⇒ 7;
`B"01"` ⇒ 1; `B"1" & B"0"` ⇒ 10; `X"3037"` ⇒ 7; the GOBACK twins the same. `STATUS KFRAC` and `STATUS NULL` are
COBOLNET1704 with their own clauses.

**PINNED BY:** `StopGobackExitCodeTests.FigurativeAllAndBooleanStatusLiterals_RenderUnderTheGR5Mapping` (13
rows) and two new rows on `TheStatusPositionsOwnRules_AreEnforcedAndCited`; negative corpus fixture
`pb216-status-null`.

**Regression posture, stated honestly:** on HEAD `9a89fbd1` these same programs were REJECTED at bind with
COBOLNET0844 citing §8.8.1.1 — a rule that does not govern the position, i.e. the rejects-legal-source defect
PB169 was opened to fix, one literal form over. So the wave did not turn a correct diagnostic into a crash; it
turned an INCORRECTLY-CITED rejection of legal source into an unhandled run-time abort on the same legal
source. Strictly worse, and now neither.
