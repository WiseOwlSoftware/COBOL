# PB307 — a declaration that contradicts its own documentation

## The rule

`cite.py --check 15.75.3` → **OK §15.75.3 4)** (Argument rules): *"If the first reference to this function in the
run unit does not specify argument-1, the seed value is defined by the implementor."* Supporting, all `--check`
OK: §15.75.3 r3, §15.75.3 r5, §15.75.4 r2.

Neither r3 (*"If a subsequent reference specifies argument-1, a new sequence of pseudo-random numbers is
started"*) nor r5 (*"subsequent references without specifying argument-1 return the next number in the current
sequence"*) reaches across a run-unit boundary; both are scoped **inside** the run unit whose first reference r4
governs. So run unit #2 must begin the implementor's sequence, not continue run unit #1's.

## Repro — two run units in ONE .NET process

That configuration is what `Cobol.Net.Runtime` is explicitly built for: `RunUnit.Current` is an `AsyncLocal` *"so
a host that thread-hops or runs run units concurrently each see their own"*, and `RunUnit.Run(Action<RunUnit>)`
exists because *"hosts embedding multiple run units use it"*.

The witness a test should use, at the runtime level:

```csharp
CobolIntrinsics.Random(7);
CobolIntrinsics.Random();
CobolIntrinsics.Random();          // seed-7 sequence now stands at draw 4
RunUnit.ResetCurrent();            // cross the run-unit boundary
double t1 = CobolIntrinsics.Random();
// t1 must NOT equal draw 4 of the seed-7 sequence
```

The assertion needs **no knowledge of the implementor seed**: it is an inequality against a value §15.75.4 r2
makes deterministic. The published determination it discriminates against is `docs/CONFORMANCE.md` A.1 item 144 —
a fresh per-process OS-entropy draw, GnuCOBOL-surveyed.

⚠ **Not reachable through `cobol.exe` or the conformance corpus**, which is why this is a note and not a golden:
`CutRunner` (`tests/Cobol.Net.Tests.Conformance/CompilerUnderTest.cs:78`) starts a separate `dotnet <dll>`
**process** per program, so one process is always one run unit there. Two `.cob` repro programs are held in the
golden lane's scratchpad at `out/statistics/repro/ar-15-75-3-4-run-unit-seed*.cob` and are deliberately not in
`tests/conformance/`.

## Root cause

`src/Cobol.Net.Runtime/Intrinsics/CobolIntrinsics.Float.cs:99` — `private static Random _random = new()`, a
**process-wide** mutable static. `Random()` reads it (`:103`); `Random(long seed)` replaces it (`:119`). Nothing
resets it at a run-unit boundary:

* the emitted driver's `ProgramRegistry.Reset()` (`ProgramEmitter.cs:483`) → `RunUnit.ResetCurrent()`
  (`Control/RunUnit.cs:120`) → `ProgramTable.Reset()` (`Control/ProgramTable.cs:56-63`) clears the program table,
  the EXTERNAL store and the MODULE-NAME stack and **touches no RANDOM state**;
* `RunUnit.Run` (`Control/RunUnit.cs:107-115`) constructs a brand-new `RunUnit` and swaps the `AsyncLocal` without
  touching it either.

## The architectural shape — why the fix is structural, not one more reset call

`RunUnit.cs`'s own summary calls it *"The single owner of all run-unit-lifetime state (ISO §14.6.1 run unit;
DESIGN-runtime-library §2.1). Replaces the five independent process-global static stores"* — and it owns the
program table, the EC engine, the EXTERNAL store, the MODULE-NAME stack, the file registry and the clock.
`_random` is a **sixth** process-global store the consolidation missed, and §15.75.3 r4 is exactly the rule that
makes it run-unit-lifetime state. The field's own doc-comment (`CobolIntrinsics.Float.cs:88-97`) already states
the correct model — *"ONE current pseudo-random sequence per run unit (§15.75.3)"* — so the declaration
contradicts its own documentation, which is why no reader caught it.

**The fix that makes the next case automatic (CLAUDE.md rule 5):** move the sequence onto `RunUnit` beside
`Modules`/`Switches`/`External` and reach it through the existing static facade, then add a drift test asserting
that **no mutable static in `Cobol.Net.Runtime` survives a run-unit boundary** — a structure, not a
hand-maintained list of resets.

## Why AR-15.75.3-4 does not close on a golden either way

The rule delegates the seed VALUE to the implementor and the seed is not observable through any returned value:
§15.75.4 r1 only bounds the result to [0,1) (a different rule, already pinned by `2023/pb65_codomain_clamp`), and
§15.75.4 r2's reproducibility guarantee is stated *"For a given seed value"*, which an unseeded reference does not
supply. The one observable that would discriminate the published determination from a fixed seed is cross-run
variation, which is non-deterministic by construction; a property golden asserting the draws vary would not
discriminate either, since a fixed seed produces varying draws too. The witness is the unit test above.
