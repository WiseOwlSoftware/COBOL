# PB3987 — a bounced branch whose finisher merged main in reads WAITING TO LAND, and the landing lane re-lands it inside the finisher's worktree

**Sites:** `scripts/prune_worktrees.py:702` (`lifecycle`, the BOUNCED test; `live_lock`), `scripts/orchestrator/land_lane.py` (`tick`, `candidates`), `scripts/orchestrator/units/enqueue.md` (step 4), `.claude/skills/workstream/templates/finisher-brief.md`

Searched first: PB3275, PB3628, PB3527 and PB3103 are all `landed`; none is open, so this is its own note. PB3275 is the origin of the
rule that BOUNCED is read only against the head it was observed at.

## Mechanism
- `scripts/prune_worktrees.py` `lifecycle()` (about lines 716-729) reads BOUNCED only `at_head` (the branch tip equals the pull
  request's head). A finisher's first step (finisher-brief.md: bring origin/main in with `merge_drivers.py merge origin/main`) moves
  the tip by a main-merge commit only; the review-stamp test then calls that commit mechanical ("later commits mechanical: main
  merged in"), so the row reads WAITING TO LAND with the old CLEAN stamp, and `land_lane.py tick` starts `enqueue.py land` on a head
  that still carries the red the queue bounced it for, in the worktree the finisher is working in.
- Second half of the same mechanism: a finisher the enqueue unit dispatches with the Agent tool into the branch's EXISTING worktree
  holds no harness worktree lock, so `live_lock` cannot read the row IN FLIGHT (a rolling-wave agent's worktree carries its pid lock).

## Witness
PR #716 (`worktree-wf_f781f6f8-448-20`, PB3869) bounced 2026-10-28T01:17Z on 12 NIST arithmetic reds (merge-group run 40612629630).
Its finisher merged main in (`314ffce67`); at 01:51:35Z the lane started attempt 000272, whose `enqueue.py land` ran `build-local.ps1`
in the finisher's worktree (two builds on one bin/obj). The enqueue unit killed that attempt (taskkill of the land_lane run pid
513660) and locked both finisher worktrees by hand (`git worktree lock --reason ...`). The same happened to
`worktree-wf_aee78301-ec3-5` (PR #714, bounced on a Windows self-test red): WAITING TO LAND after its finisher's main merge
(`490ee3cd4`), locked before the lane started it.

## Harm
No wrong code reaches main (the merge queue would bounce it again), but a known-red head is re-gated and re-queued (CI minutes, a
bounce that delays every pull request queued behind it), and the lane's gate races the finisher's edits and gate.

## Witness 2026-10-28 (clerk, enqueue unit 20261028a): the lane also RETRIES a branch whose worktree a live agent or a hand lock holds

Observed after PB3987 landed (PR #719). Site: `scripts/orchestrator/land_lane.py` `candidates()` lines 1006-1015: the retry arm (a
RETRYABLE last attempt: DIED, exit 12 GATE BUSY, ...) skips only rows whose state is STOPPED, BOUNCED or queue-owned, so a row the
survey reads IN FLIGHT because a live agent or a hand lock holds its worktree (`prune_worktrees.live_lock`) is retried. The reap
comment at lines 973-974 shows why IN FLIGHT is admitted (a runner that committed reads IN FLIGHT while fresh); the arm does not tell
that case from a held lock.

After the enqueue unit killed attempt 000272 (land_lane run pid 513660) and locked the worktree
`E:/COBOL/.claude/worktrees/wf_f781f6f8-448-20` by hand (finisher in flight), the reap recorded 000272 DIED, and the lane started
000274 (02:03:29Z, exit 12 GATE BUSY: the gate 000272 had started kept running DETACHED as pid 463956 after `taskkill /T` of the
runner tree, holding cobol-gate.lock) and 000275 (02:06:55Z: it merged origin/main into the finisher's worktree as `2a8aa6811` and
gated it RED, writing `BLOCKED: enqueue` into the finisher's report). Logs: `E:/COBOL-coord/logs/land-lane-000272-*`, `-000274-*`,
`-000275-*` (the three for worktree-wf_f781f6f8-448-20).

Two lessons for the fix: (a) killing a lane attempt does not stop the lane (DIED is retryable) and does not stop its gate (the gate
runs detached); (b) the only controls that hold a branch are its state (STOPPED/BOUNCED) and the STOP files. The fix belongs with
this note's: a live lock (agent pid or by hand) must hold a branch out of BOTH arms of `candidates()`.

## Fix direction (recorded for the implementer, not decided)
- Keep BOUNCED across commits that are only main merges and DEVLOG stamps (the same mechanical-commit test the review stamp uses)
  until a non-mechanical commit or a `land_lane.py rearm`; and/or
- have the enqueue unit's finisher dispatch lock the worktree (units/enqueue.md step 4, finisher-brief.md) and unlock it on return.

## Acceptance
- A test: a row bounced at head H, then a main-merge-only commit on top, still reads BOUNCED; a non-mechanical commit or a rearm
  reads WAITING TO LAND again. A finisher dispatch leaves the worktree locked until it returns.
