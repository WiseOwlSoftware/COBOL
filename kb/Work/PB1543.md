# PB1543 — LANDED

## Landed 2026-09-27 (wave 67 M)

The separator space of the text-manipulation stage is ONE predicate, `TextWordScanner.IsSeparatorSpace` (and its
`SeparatorSpaces` array) in `src/Cobol.Net.Frontend/Preprocessor/TextWord.cs`: space, tab, CR, LF — exactly the lexer's
`WS` set (`CobolLexer.g4` line 187), so a text-word ends where the lexer's word ends (§8.3.5 1), §7.2.2.5 3), cite.py
OK). It replaced `char.IsWhiteSpace` at every text-word boundary (`TryNext`, `SeparatorFollows`, `EndsCharacterString`),
at the §7.2.3.3 SR2 "preceded by a space" test in `CopyProcessor.ResolveOneCopy`, and the pseudo-text `Trim()` in
`ReadOperand`. Probe `i23c.cob` (w67m `probe/`) now leaves `VALUE P Q` unreplaced (and rejected downstream, as the note
expected) while `P<U+00A0>Q` becomes `"OK5"`. DOC-A.1-23's ⚠ paragraph is replaced by the current state. Witnesses:
`conformance:85/pb1543_nbsp_is_a_text_word_character`, `unit:TextManipulationTextWordTests.UnicodeSpaceLookalike_IsATextWordCharacter`
(U+00A0, U+2003, U+3000). **Sibling sweep** (`grep IsWhiteSpace|.Trim()|Split()` over `Preprocessor/`): the other
stages (ConditionalCompilationProcessor 16 sites, ReferenceFormatProcessor 7, CobolWordsDirectiveProcessor 3, Flag /
LeapSecond 1 each) read directive operands and blank lines, not text-words — reported as a lead, not fixed here.

## The defect as filed

## The rules

> 3) any other character or sequence of contiguous characters from the compile-time coded character set, bounded by separators. The implementor may prohibit the use of one or more characters from outside the COBOL character repertoire in, or as, text-words.

`cite.py --check 7.2.2.5 "any other character or sequence of contiguous characters from the compile-time coded character set, bounded by separators"` → OK §7.2.2.5 3).

> 1) The COBOL character space is a separator. …

`cite.py --check 8.3.5 "The COBOL character space is a separator"` → OK §8.3.5 1). U+00A0 is not the COBOL character space, so
`P<U+00A0>Q` is ONE text-word (or, if the implementor prohibits U+00A0 under §7.2.2.5 3), a diagnostic — A.1 item 23).

## Repro (`/tmp/adj/doc/doc-w1-s1/probe/i23c.cob`; re-probed, `--std 2023`)

```cobol
       REPLACE ==P<U+00A0>Q== BY =="OK5"==.
       01 A PIC X(3) VALUE P Q.
       01 B PIC X(3) VALUE P<U+00A0>Q.
           DISPLAY A "|" B
```

Observed: `OK5|OK5` — the pattern also matched the two text-words `P Q`. Expected: `A` is not replaced (and `VALUE P Q` is then a
compile error), only `B` is.

## Code site

`src/Cobol.Net.Frontend/Preprocessor/CopyProcessor.cs` `TokenizeTextWords` (~l.271) bounds text-words with `char.IsWhiteSpace`.
The separator set must be the §8.3.5 one the lexer uses. Then write DOC-A.1-23 (no character is prohibited in a text-word — the
writer verified that half: `§`, `€`, `@`, `~` all match and replace), which is PB1369's deliverable.

## Sibling sweep

Every other `char.IsWhiteSpace` / `string.Split()` / `Trim()` in the preprocessor stages (ReferenceFormatProcessor, directive
operand parsing, >>DEFINE values) — the COBOL separator is the space (and the separators §8.3.5 lists), never Unicode White_Space.
