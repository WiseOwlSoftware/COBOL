# PB734 — OPEN — a `?` where the page prints a brace

Found 2026-09-06 in the PB695 family-2 implementer's report (NEW DEFECT C), which reported it rather than folding
it into that cluster because it is a brace/bracket defect and not an optional-word one. Verified on main.

## What the standard prints — rendered, not read

`python scripts/spec/clause_page.py 14.9.20.2` → **PDF page 667, printed folio 637**;
`python scripts/render-spec-page.py 667`. On the render the INITIALIZE format's second line is:

```
┌ ╭ ALL           ╮          ┐
│ ┤               ├ TO VALUE │
└ ╰ category-name ╯          ┘
```

— an **outer BRACKET** enclosing an **inner BRACE** whose two alternatives are `ALL` (underlined) and
`category-name`, with `TO VALUE` outside the brace and inside the bracket; `TO` is not underlined, `VALUE` is.
`cite.py --check 14.9.20.2 "category-name"` → **OK §14.9.20.2 (General format)**; the transcription at
`specs/ISO_COBOL.md:24397-24413` matches the render exactly, so the OCR is not the source of this one.

The two metalanguage rules decide it and they say different things about the two delimiters:

- `--check 5.2.6.2 "may be explicitly specified or that portion of the general format may be omitted"` →
  **OK §5.2.6.2 (Brackets)** — the whole phrase may be omitted. That is the `?` the grammar is entitled to.
- `--check 5.2.6.3 "shall be explicitly specified or is implicitly selected"` → **OK §5.2.6.3 (Braces)** — if
  the phrase IS written, one of the brace's alternatives **shall** be specified. §5.2.6.3's escape hatch — *"If
  one of the alternatives contains only optional words, that alternative is the default and is selected unless
  another alternative is explicitly specified"* — does not apply: `ALL` is underlined (a required word,
  §8.3.2.4.3 by complement: `--check 8.3.2.4.3 "may be specified at the user's option"` → **OK §8.3.2.4.3
  (Optional words)**, which is the rule for words that are NOT underlined), and `category-name` is a
  metavariable, not an optional word. **Neither alternative can be the implicit default, so writing `TO VALUE`
  alone spells nothing the format prints.**

## What the grammar spells

`src/Cobol.Net.Frontend/Grammar/Core/CobolData.g4:688-691`:

```
// [ALL | category-name] TO VALUE (§14.9.20)
initializeCategoryToValue
    : (ALL | initializeCategory)? TO VALUE
    ;
```

The comment on `:688` carries the defect as plainly as the rule does — it writes the printed brace as a bracket.
One `?` too many, and it is on the inner group rather than the outer one: `initializeStatement:683` already has
`initializeCategoryToValue?`, which is §5.2.6.2's bracket done correctly, so the inner `?` is pure surplus.

## Measured

Compiler provenance as in [[PB732]] (built at `c34f01ad`; `git diff c34f01ad..HEAD -- src/` touches neither
`Core/CobolData.g4` nor `Binding/Procedure/Verbs/InitializeBinder.cs`). Source
`…\scratchpad\pb734a.cob`: `01 X1 PIC 9 VALUE 5.` / `MOVE 3 TO X1. INITIALIZE X1 TO VALUE. DISPLAY X1.`

- `--std 2023` → **exit 0**, runs, prints `5`. The generated C# is `X1 = (long)(CobolNum.Store(5L, …))` — i.e.
  it behaves exactly as `INITIALIZE X1 ALL TO VALUE.` would.
- `--std 85` → `COBOLNET0831: INITIALIZE ... TO VALUE requires COBOL-2002 (targeting COBOL-85)`. The EDITION
  gate is present and correct; only the shape screen is missing.

The bound shape is where the over-acceptance becomes invisible. `InitializeBinder.Bind`
(`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs:61-62`) builds
`new InitializeSpec(withFiller, toValue is not null, toValue?.initializeCategory() is { } vc ?
InitializeCategoryOf(vc) : null, …)` — a written `ALL` and an omitted choice BOTH produce a null category, so
downstream nothing can tell them apart and no binder check could be written without re-reading the parse tree.

## Where the screen belongs — the grammar

The project's convention: what the FORMAT prints is the grammar's job, what a RULE forbids is the binder's. This
is printed — a brace inside a bracket — so it is the grammar's, and the fix is to delete the `?`:

```
initializeCategoryToValue
    : (ALL | initializeCategory) TO VALUE
    ;
```

The outer optionality is already spelled at `:683`. Ship with a negative golden pinning `INITIALIZE X1 TO VALUE.`
as a syntax error and a positive golden for each arm (`ALL TO VALUE`, `NUMERIC TO VALUE`) so the tightening is
proved not to have eaten a legal spelling.

⚠ **One adjacent relaxation is already in flight and must not be lost by this edit.** `TO` is NOT underlined on
folio 637, so by §8.3.2.4.3 `INITIALIZE X1 ALL VALUE.` is conforming source — and main REJECTS it, because the
grammar writes `TO VALUE` with `TO` required. That is PB695 family 2's territory: its branch
(`worktree-agent-a507a0adb019b9d52:src/…/CobolData.g4:749-751`) already reads `(ALL | initializeCategory)? TO?
VALUE`. **The family-2 report quotes `TO?` as if it were main's text; it is that branch's.** Whichever of the two
lands second must produce `(ALL | initializeCategory) TO? VALUE` — the required choice AND the optional word — or
one change silently undoes half of the other.

## Sweep

`grep -n ")? " src/Cobol.Net.Frontend/Grammar/**/*.g4` over rules whose printed format nests a brace inside a
bracket is the general form of this defect: a `?` applied to the CHOICE instead of to the PHRASE. It is the exact
complement of what `audit_grammar_optional_words.py` measures (that audit asks which optional words a rule
REQUIRES; this asks which required choices a rule made optional), and nothing in the tree measures it today —
which is why the confirmations file had already flagged the site in prose and it still shipped.
