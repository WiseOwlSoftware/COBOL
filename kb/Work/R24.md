# R24 — the FORMATTED-* seconds-argument value channel is Real-blind and Dec-blind: CS1503 under standard modes, fractions dropped, wide values wrapped

> R00 ledger-audit orphan (2026-08-08): F44 + F46 + F57 of `PHASE-B-15.32-15.44-findings.md`, probe-verified OPEN
> against the R10-landed tree (`5312996a`). The probe programs are reproducible from the finding text.

PROBES (2026-08-08):
- STANDARD-DECIMAL + `FORMATTED-DATETIME("YYYYMMDDThhmmss", WS-A + WS-B, 45296)` → raw Roslyn
  `CS1503: cannot convert from 'CobolNet.Runtime.CobolDec' to 'System.Int128'` surfacing as "backend
  compilation failed" on conforming source (the exact-family AsInt path was fixed — FACTORIAL(N + 1) under
  the same mode prints 120 — but RenderFormattedDatetime/Time's own `(long)({sec.Expr})` casts were not).
- `FORMATTED-DATETIME("YYYYMMDDThhmmss.ss+hhmm", 143951, WS-S, 300)` with COMP-2 WS-S = 18867.812479168304
  → `19950215T05142700+0500`: ALL fractional seconds lost (§15.40.4 r1 requires the represented time;
  expected …27.81). The channel never reads NumX.Real, so the double truncates at the cast.
- Ledger F57's wide leg: a 20-digit scaled argument's Int128 unscaled value wraps in the same unchecked cast.
FIX (ledger): ONE Real-and-Dec-aware seconds helper consumed by RenderFormattedTime (a2),
RenderFormattedDatetime (a3) and the CombinedDatetime arm — not three casts.

## LANDED 2026-08-08

**One carrier-total seconds helper + one Int128 widening + one missing Dec arm** — narrower than the note
predicted, because probing first showed two of the ledger's suspects already fixed:

- `CombinedDatetime` was ALREADY correct on all four carriers (PB32's SDIDI landing at `IntrinsicRenderer.Arg`
  de-Decs before the arm; the runtime already took Int128) — probe: `COMBINED-DATETIME(143951, T)` over a
  9(5)V9(15) item gives 143951.452965 exact.
- The offset arguments were ALREADY safe: `ArgInt` funnels into the PB22-unified `AsInt`.
- What remained: (1) the two `(long)({sec.Expr})` seconds casts in RenderFormattedTime/RenderFormattedDatetime
  — replaced by `SecondsArg` (fixed → raw at its own scale; Real → checked `ToScaled` at scale 9, the
  FORMATTED-CURRENT-DATE nanosecond convention; Dec → exact `ToUnscaled` at scale 18, the documented §15.3.3.2
  maximum, CONFORMANCE.md item 202; unsigned-wide → the R10 `DeU` funnel); (2) `CobolDate`'s seconds params
  widened long → Int128 (`EmitFormatted`, `FormattedTime`, `FormattedDatetime`, `SecondsOutOfStandardForm`)
  with an EXACT scale>18 pre-reduction before the decimal split — which also closes F29's divisor-wrap sibling
  (`(decimal)(long)Pow10.AsWide(secScale)` with secScale ≥ 19); (3) **`AsInt`'s missing Dec arm** — F44's true
  root for the DATE argument: a Dec NumX carries Scale 0 BY CONVENTION, so the `Scale == 0` test passed the
  raw CobolDec through to `IntegerArg(Int128)` as CS1503. The arm sits BEFORE the scale test (the PB14/PB32
  lesson, now closed in the last of the carrier dispatches). FACTORIAL's channel never showed it because
  `IntArg` goes through `Arg`, which de-Decs — the two entries funnel to ONE AsInt, so one arm fixes both.

Probes after: float `FORMATTED-TIME("hhmmss.ss", 45296.5)` → `12345650` (fraction survives; §15.3.3.2 keeps
the separator OUT of basic-format data — the ledger's F46 expectation confirmed against the clause);
wide 9(5)V9(15) 45296.5 → `123456` (was the fabricated 022003 — the VALUE is range-checked now, §7.3.17 r5);
STANDARD-DECIMAL expression arguments compile and compute (`20210616T123456`; the F46 offset case prints the
exact D.31.5.7-corrected `19950215T05142781+0500`).
