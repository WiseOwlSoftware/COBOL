# PB4709 — always-integer expression keeps ABS and MAX on the Numeric row

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundTree.cs` (`BoundComputedOperand.EnclosedOperand`, doc only), `docs/INTRINSICS_DESIGN.md` (the result-type shapes table), `src/WiseOwl.Cobol.Compiler/Binding/IntrinsicResultType.cs:354` (`IntrinsicResultType.IsIntegerArgument`), `src/WiseOwl.Cobol.Compiler/Binding/IntrinsicResultType.cs:369` (`IntrinsicResultType.IntegerRowArguments`), `src/WiseOwl.Cobol.Compiler/Binding/IntrinsicArgumentRules.cs:1784` (`IntrinsicArgumentRules.ProvablyIntegral`), `src/WiseOwl.Cobol.Compiler/Binding/IntrinsicArgumentRules.cs:1812` (`IntrinsicArgumentRules.IntegralForm`), `src/WiseOwl.Cobol.Compiler/Binding/IntrinsicArgumentRules.cs:1960` (`IntrinsicArgumentRules.NonIntegralItemsBeneath`, both overloads), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/IntrinsicBinder.cs:840` (`IntrinsicBinder.BindIntrinsicCore`, the `IntegerRowArguments` call)

The same lead is in two PB4635 reports (w20261868f and w20261869a), copied. Shared root, in the reports' words: "15.3 item 6 is read for a parenthesized sole operand only". An always-integer expression other than a parenthesized item or literal (`ABS(I2 + 1)`, `ABS(- I2)`, `MAX(I2 + 1 1)`) keeps ABS and MAX on the Numeric row, so `FACTORIAL(ABS(I2 + 1))` is COBOL1627 and `PERFORM FUNCTION MAX(I2 + 1 1) TIMES` is COBOL1646 (same on main). Site `IntrinsicResultType.IsIntegerArgument`; `IntrinsicArgumentRules.ProvablyIntegral` already reasons term by term.

The w20261868f review (R2-6, pre-existing, not introduced by PB4635) says: `IsIntegerArgument` applies 15.3 item 6 only to a parenthesized sole item or literal, so any other always-integer arithmetic expression still leaves ABS and MAX on the Numeric row; widening the Integer row to every provably-integral expression is a separate mechanism with its own goldens and refusal flips.

## Landed (wave 20261872 group D)

Re-probe on the build: `FACTORIAL(ABS(I2 + 1))` and `FACTORIAL(ABS(- I2))` were COBOL1627, `PERFORM FUNCTION MAX(I2 + 1 1) TIMES` COBOL1646. The fix: `IntrinsicResultType.IsIntegerArgument` asks `IntrinsicArgumentRules.ProvablyIntegral` (now `internal`) for every computed operand, so the Integer row of ABS/MAX/MIN/RANGE/SUM is selected by "an arithmetic expression that will always result in an integer value" (15.3 item 6) as the refusal screen already reads it; the `EnclosedOperand` special case is subsumed. `ProvablyIntegral` also learned an integer-type function term (`IntrinsicType.Integer`), which makes `ABS(FUNCTION INTEGER(S) + 1)` Integer and makes `I2 + 0.5 + FUNCTION INTEGER(S)` refused as never integral (it failed open). Goldens: `cases/15.3-Arguments/pb4709_integer_expression_argument`, refusals `pb4709-abs-non-integral-expression`, `pb4709-integer-function-term-non-integral-sum`.

## Review round 1 (wave 20261872 group D finisher)

R1-1 (blocking, fixed): the Integer row was selected by the VALUE of the argument while the returned value kept the argument's own scale, so `MOVE FUNCTION ABS(I2 + 1.0) TO A10` stored `4.0` (also `ABS(1.5 + 0.5)`, `MAX(I2 + 1.0 1)`, `ABS(I2 * 2.0)`, `SUM(I2 + 1.0 1)`, `ABS(4 / 2)`, `MIN(I2 ** 2.0 3)`). `IntrinsicResultType.IntegerRowArguments` hands a call that resolved to the Integer row its computed arguments in scale-0 form (`IntrinsicArgumentRules.IntegralForm`), called once in the binder. Golden `pb4709_integer_row_scale_zero`. Leads fixed in the same files: R1-2 (a lone literal, bare or parenthesized, is read by FORM, so the two spellings agree; reading the bare one by value was tried and withdrawn, it changed the floating-point literal device image of `pb99_floating_literal_operand_exact`; golden `pb4709-abs-parenthesized-fraction-literal`), R1-3 (a counter register is provably integral; `LINAGE-COUNTER OF F + 0.5` is refused, golden `pb4709-counter-register-non-integral-sum`), R1-4 (`NonIntegralItemsBeneath` walks call arguments), R1-5 (citation of Table 21 re-derived to 15.6), R1-6 (golden comment path).
