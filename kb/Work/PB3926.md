# PB3926 — numval-c-anycase-locale-keywords-not-supported--anycase: NUMVAL-C / TEST-NUMVAL-C: ANYCASE keyword refused ('ANYCASE' is a reserved word, but isn't supported)

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S9) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\numval-c-anycase-locale-keywords-not-supported--anycase.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\numval-c-anycase-locale-keywords-not-supported--anycase\`.

## Summary

GnuCOBOL 3.2 refuses the ANYCASE keyword in the argument list of FUNCTION NUMVAL-C and FUNCTION TEST-NUMVAL-C:
`'ANYCASE' is a reserved word, but isn't supported`, followed by `syntax error, unexpected Identifier, expecting )`.
When a separator comma precedes ANYCASE, the first diagnostic is `syntax error, unexpected comma delimiter, expecting )`.
Both diagnostics come from one cause: the function's argument rule takes one or two expressions and nothing else. The
keyword is in the NUMVAL-C and TEST-NUMVAL-C general formats of ISO/IEC 1989:2002 and of the 2014 committee draft, so
this is a missing feature of the edition `-std=cobol2014` claims. Class: feature missing.

A second defect at the same code site, a WRONG ANSWER found by the refuter (slice S9) and folded in here because one
change in `cob_check_numval` decides both: TEST-NUMVAL and TEST-NUMVAL-C of `"12.50cr"` (lowercase CR) return 6, where
the standard allows CR and DB in either case and so requires 0; NUMVAL and NUMVAL-C of the same string return
-12.50, so cobc disagrees with itself. Program CRDB below.

## Expected result (per ISO)

The program compiles and prints `12.50 0`.

- §15.68.2 (checked) and §15.94.2 (checked): ANYCASE is an optional keyword after argument-1 and the optional
  argument-2 / LOCALE choice.
- §15.68.3 4) a) (checked): "currency is a string of one or more characters matching character for character the
  currency string in argument-2".
- §15.68.3 4) f) (checked): "If the ANYCASE keyword is specified, the matching rules for detecting a currency string in
  argument-1 are as if all uppercase letters in argument-1 and in the currency string were replaced by their
  corresponding lowercase letters". So "usd" in argument-1 matches the currency string "USD".
- §15.68.4 1) and 2) (checked): "The returned value is the numeric value represented by argument-1." and "The currency
  string, if any, and any grouping separators preceding the decimal separator are ignored." NUMVAL-C returns 12.50.
- §15.94.3 1) (checked): "The argument rules for the TEST-NUMVAL-C function are the same as those specified in 15.68";
  §15.94.4 1) a) (checked): "If the content of argument-1 conforms to the argument rules for the NUMVAL-C function",
  the returned value is 0.

Edition: the keyword is in ISO/IEC 1989:2002 and 2014. The 2001-12-04 text headed "ISO/IEC 1989:2002(E)" gives
`FUNCTION NUMVAL-C ( argument-1 LOCALE [ locale-name-1 ] / argument-2 [ ANYCASE ] )` (its clause 15.55.1 of that text), and the 2009
committee draft CD 1.2 that led to 2014 gives the same format for NUMVAL-C (its clause 15.63.1 of that text) and TEST-NUMVAL-C (its
§15.87.1). The 2023 Annex E lists the keyword among the changes that do not affect existing programs: §E.3.3 1)
(checked) "The ANYCASE keyword of the NUMVAL-C function has been clarified to be consistent with the rest of the
standard", which presupposes it. Neither ANYCASE nor these functions are optional elements (§A.4; the 2014 draft's A.4
lists only the LOCALE keyword of TEST-NUMVAL-C). GnuCOBOL's own `cobc/reserved.c` tags ANYCASE as a 2002 word.

Edition as recorded by the adjudicator: 2002 (carried into 2014). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

Second program: `00 00 -12.50 -12.50` twice. §15.67.3 1) (checked), the NUMVAL argument format that TEST-NUMVAL tests
against: "If argument-1 is alphanumeric, CR or DB, if specified, shall be the letters 'CR' or 'DB' in uppercase or
lowercase, or a combination of uppercase and lowercase"; §15.93.4 1) a) (checked): TEST-NUMVAL returns 0 "If the
content of argument-1 conforms to the argument rules for the NUMVAL function"; §15.94.4 1) a) (checked) the same for
TEST-NUMVAL-C and NUMVAL-C. So `"12.50cr"` conforms and both TEST functions return 0. Edition: TEST-NUMVAL and
TEST-NUMVAL-C are not among the Annex E 2023 additions, so they are in the 2014 edition; that its NUMVAL rule also
admits lowercase CR is assumed from the 2023 text and not verified against 2014.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/reserved.c`, the reserved-word table entry for ANYCASE (line 341): token -1, so the scanner reports the word as
  reserved and unsupported.
- `cobc/parser.y`, rule `numvalc_args` (line 19987), used by the `NUMVALC_FUNC` alternative of the function-call rule
  (line 19862) that serves both NUMVAL-C and TEST-NUMVAL-C (`cobc/reserved.c` lines 3692 and 3836 map both names to
  `NUMVALC_FUNC`): it accepts `expr_x` or `expr_x _e_sep expr_x` only. After the second argument only the closing
  parenthesis is accepted, which is why a separator comma before ANYCASE is reported as an unexpected comma delimiter.
- `libcob/intrinsic.c`, `cob_intr_numval_c` (line 4944), `cob_intr_test_numval_c` (line 6287) and the shared `numval`
  (line 1482) take a source field and a currency field only; a case-insensitive currency match needs a flag passed
  through (`libcob/common.h` declares both at lines 2719 and 2761).

- The second defect: `libcob/intrinsic.c`, `cob_check_numval` (line 3298) takes an `anycase` flag and admits a lowercase
  `c`/`d` of CR/DB only when it is set (lines 3490-3522); every caller passes 0 (`cob_intr_test_numval` line 6282,
  `cob_intr_test_numval_c` line 6289). Lowercase CR and DB are always allowed (§15.67.3 1)), so the test should
  not depend on the flag; the flag the ANYCASE keyword needs is the currency-string match (§15.68.3 4) f)).

## Draft issue

**Title:** NUMVAL-C / TEST-NUMVAL-C: ANYCASE keyword refused ("'ANYCASE' is a reserved word, but isn't supported")

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1), x86_64 Linux.

Steps: `cobc -std=cobol2014 -fformat=free -x nvany.cob` with

```cobol

DATA DIVISION.
WORKING-STORAGE SECTION.

01 T PIC 9.
PROCEDURE DIVISION.

STOP RUN.
```

Observed (exit 1, same without `-std`):

```
nvany.cob:8: error: 'ANYCASE' is a reserved word, but isn't supported
nvany.cob:8: error: syntax error, unexpected Identifier, expecting )
```

With a comma before ANYCASE (`"USD", ANYCASE`) the first error is `syntax error, unexpected comma delimiter,
expecting )`.

Expected: the program compiles and prints `12.50 0`. The general format of NUMVAL-C is
`FUNCTION NUMVAL-C ( argument-1 [ LOCALE [ locale-name-1 ] | argument-2 ] [ ANYCASE ] )`, and TEST-NUMVAL-C has the
same arguments (ISO/IEC 1989:2002 and 2014; §15.68 and §15.94 in the 2023 edition). With ANYCASE "the matching rules
for detecting a currency string in argument-1 are as if all uppercase letters in argument-1 and in the currency string
were replaced by their corresponding lowercase letters" (§15.68.3 4) f)), so "usd12.50" with currency "USD" is valid:
NUMVAL-C returns 12.50 and TEST-NUMVAL-C returns 0. The `numvalc_args` rule in parser.y accepts two expressions only,
and the run-time functions have no case-insensitive currency match.

A related wrong answer in the same routine: `FUNCTION TEST-NUMVAL("12.50cr")` and `FUNCTION TEST-NUMVAL-C("12.50cr")`
return 6 (with `"12.50CR"` they return 0), while `FUNCTION NUMVAL` and `FUNCTION NUMVAL-C` of the same string return
-12.50. The NUMVAL argument rules allow CR and DB "in uppercase or lowercase, or a combination of uppercase and
lowercase" (§15.67.3 rule 1), and TEST-NUMVAL returns 0 when argument-1 conforms to them (§15.93.4 rule 1 a); the same
for TEST-NUMVAL-C, §15.94.4). `cob_check_numval` in libcob/intrinsic.c admits lowercase `cr`/`db` only when its
`anycase` argument is set, and every caller passes 0.
