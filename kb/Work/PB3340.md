# PB3340 — APPLY COMMIT on a SEQUENTIAL file

HELD (2026-10-18, the Mythos lane's route in PB3330): proceeds only after the core engine PB3331-PB3336 has landed and the owner has decided the transaction slice's scope. The hold is mechanical: `status: owner` puts "status: owner" in this note's `waiting_on` (`work.py` `cluster_order`), and `plan_wave.py` plans no note with a waiting entry, so no wave dispatches it until the owner's decision sets the status back to open.

> flags: follows PB3330 (named out of scope in PB3338)

## The rule

§9.1.18.2 (`cite.py --check 9.1.18.2` → OK): *"Apart from sort-merge files and report writer files, any type of file on
a mass storage device may be specified."* An APPLY COMMIT clause may therefore name a SEQUENTIAL file on mass storage,
and COMMIT, ROLLBACK and abnormal run-unit termination (§9.1.18.3 to §9.1.18.5) then apply to its changes.

## Why it is its own note

PB3330's engine (`docs/rearchitecture/DESIGN-runtime-library.md` §2.2.1) is paged copy-on-write storage for RELATIVE and
INDEXED. PB3337 builds COMMIT and ROLLBACK on it, and PB3338 makes the compiler accept APPLY COMMIT. A SEQUENTIAL
file is written by streaming, not through that engine, so it has no page ledger to promote or discard. PB3338 records
the gap ("Out of scope, recorded here so it is not lost").

## The design is written — `docs/rearchitecture/DESIGN-runtime-library.md` 2.2.2 (kb/Work PB3426, 2026-10-19)

Implement FROM 2.2.2 (CLAUDE.md rule 2) as CORRECTED on 2026-10-19 after the branch review (kb/Work PB3426 R1-1, R1-2, R2-1) and
held by the executable model `scripts/models/sequential_journal_model.py` (a gate and CI self-test: keep it GREEN at every
change to the protocol, and add to it every row the implementation adds): a transaction's two phases (BASE — the committed
length L, read at the transaction's FIRST APPEND and never at its begin, and the first image of each rewritten record that is
not its own append; REPLACED — after the first capture, or from the start of a
creation: the before file, or no file at all; nothing is journaled after a capture); its holdings (the END, held by every
live transaction; the rewritten ordinals; the whole file once REPLACED); the three files per transaction in the `.wolk-*`
lock directory (`txn-<id>.live`, the holder = the liveness, a `SidecarLockFiles` holder on every host; `txn-<id>.journal`,
the record, readable while live; `txn-<id>.before`); the entry mutex (`EntryMutexByte` through `SidecarRegionLocks` on every
host, because the file may not exist); the five write-ahead rules (R1 the header synced before the first change, R2 the
image before the overwrite, R3 the `L` record synced before the first append and nothing for later ones, R4 the capture's
order — before file, its sync, the `K` record, its
sync, then the truncation or removal — and R5 a refused sync of a handed-over record is fatal); the kept handle under commit
control (closed by a DELETE FILE, opened by a creation; the capture is a COPY, never a rename); COMMIT's three regions with
the directory sync; the settle (litter, retire, rollback) run by the owner or the next entry, and a holder's own unfinished
retirement; a writer whose file a rollback removed creates it again at its next WRITE; LINE SEQUENTIAL and the print stream
COVERED; the `IHostMedium` seam re-running the model's rows over bytes. The list under "What it needs" is what 2.2.2
answers, kept for the record.

## ✅ THE OWNER'S ANSWER — 2026-10-19 15:45 PDT, verbatim: **"option a approved"**

The question, asked by the Mythos lane on 2026-10-19 as part of the tier-2 design (PB3426):

> May the sequential journal be a TRANSIENT file in the file's `.wolk-*` lock directory — existing only from a transaction's
> first change to its COMMIT or ROLLBACK, consumed by the next entry after a crash, describing no attribute of the data file,
> which stays byte-identical to one written without transactions (2.2.2.4) — or does PB802's "no sidecar of any type"
> (2026-09-07, of the `.cbattr` attribute catalog) cover it too, in which case the undo is memory-only (2.2.2.11) and a run
> unit that is killed or loses power leaves its uncommitted sequential changes in the file, unrolled-back, for ever?

The owner asked for the ramifications and alternatives first and was shown four shapes, each with what it costs and what
it loses: **(A)** the durable journal of 2.2.2 — the next entry rolls back a killed or power-lost run unit's changes, other
run units see a dead owner's holdings, at one directory listing per writable OPEN, one record and sync per covered REWRITE
and per transaction's first append, one copy of the file at a capture, and a '30' at the first covered change when the
directory beside the file is not writable; **(B)** memory-only undo — nothing beside the file, ROLLBACK and the runtime's own
abnormal-termination path still restore, but a kill or a power loss leaves the uncommitted changes in the file for ever and
the indexed file beside it would roll back while the sequential one would not; **(C)** the journal in a per-machine or
per-user directory — the promise holds only for the same machine and user, and a reader cannot tell which case it is in;
**(D)** a header inside the file — rejected in 2.2.2.4 for the interchange property. The lane recommended (A): PB802's
words targeted a persistent catalog consulted at every OPEN, the journal has none of the properties that made the catalog
objectionable, and the lock directory with its transient files already exists in the runtime (`SidecarLockFiles`, PB2917,
PB3109). The owner approved (A). PB802 carries the scope clarification; 2.2.2.11 keeps (B), (C) and (D) as rejected, with
their losses, so they are not re-asked. This note is `open` from this change, blocked by PB3338 in the tier-2 chain; the
transaction slice's scope decision (PB3337, PB3420) is a different question and is still the owner's.

## What it needs

- A design section in `DESIGN-runtime-library.md`, written first and followed, covering how a sequential file under
  APPLY COMMIT keeps its last committed state. Examples: the committed length for OPEN OUTPUT and EXTEND (a ROLLBACK
  truncates back to it), and before-images for an I-O REWRITE. It must be crash-consistent in the same sense as
  2.2.1, scoped to the run unit's own changes as 2.2.1.10's transactions are (another run unit's records are never
  committed or restored by this one), and a file not under APPLY COMMIT must pay nothing.
- Decide LINE SEQUENTIAL (an extension) explicitly in `docs/CONFORMANCE.md`, either covered or declined with its
  reason.
- Goldens computed from §9.1.18.3 to §9.1.18.5, and the PB3330 count-based witnesses extended to the sequential path.
