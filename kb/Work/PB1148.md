# PB1148 — OPEN

## The rule
> "an implied transfer of control occurs from the last statement in the procedure to the control mechanism of the last executed controlling statement"
`cite.py --check 14.6.3 "an implied transfer of control occurs from the last statement in the procedure to the control mechanism of the last executed controlling statement"` → `OK  §14.6.3 1)  (Explicit and implicit transfers of control)`

## Measured (adjudicator / refuter evidence, verbatim)
### GR-14.6.3-1 (PARTIAL)
|| REFUTED: PARTIAL — Rule 1 makes the implicit return happen 'from the last statement in the procedure' that is the last in the controlling statement's range. The emitted dispatch instead returns whenever the exit paragraph's pc is followed by pc == exitPc+1. An explicit GO TO from inside the exit paragraph to the paragraph that physically follows it therefore looks like fall-through and returns to the PERFORM. The PERFORM should stay active while control runs the GO TO target, which is outside the range (§14.9.28 treats the range as left). In the probe the target paragraph never runs and the run unit continues after the PERFORM. Nested THRU, sections, TIMES, VARYING re-entry, GO TO out and fall-back-in, SORT, MERGE and USE all behave correctly, so the verdict is PARTIAL. The same `__atExit && __pc == __exitPc + 1` shape in every emitted __Dispatch is the sibling to sweep: GO TO, and also a PERFORM or SORT/MERGE procedure exit, whose next paragraph is the transfer target.
- **Code location (record):** src/Cobol.Net.Compiler/CodeGen/Verbs/ControlFlowEmitter.cs; src/Cobol.Net.Compiler/CodeGen/DispatchEmitter.cs; src/Cobol.Net.Compiler/CodeGen/Verbs/SortEmitter.cs; src/Cobol.Net.Compiler/CodeGen/EcEmitter.cs

## What the fixer owes
Distinguish fall-through from an explicit transfer: the implicit return fires only when the exit paragraph's LAST statement completes, never on a GO TO whose target is exitPc+1. Sweep every `__atExit && __pc == __exitPc + 1` site (PERFORM, SORT/MERGE procedures, USE).

## Finding — `resume-statement` (wrong-answer; rows `GR-14.9.33.4-3`)

**Mechanism.** The out-of-line PERFORM dispatcher's return test `if (__atExit && __pc == __exitPc + 1) return __pc;` cannot distinguish the exit paragraph FALLING OFF its end from a GO TO (or RESUME AT, which is 'as if GO TO') in the exit paragraph transferring to the physically NEXT paragraph, so such a transfer returns to the PERFORM instead

**Repro.** probe/resume-statement/gr3.cob: declarative on F: DISPLAY "D " FS. RESUME AT M3. MAIN SECTION. M1. PERFORM M2. DISPLAY "BACK-IN-M1". STOP RUN. M2. OPEN INPUT F (file absent). DISPLAY "AFTER-OPEN". M3. DISPLAY "M3". STOP RUN. Control without RESUME: probe/resume-statement/goto.cob: M1. PERFORM M2. DISPLAY "BACK-IN-M1". STOP RUN. M2. GO TO M3. DISPLAY "AFTER-GOTO". M3. DISPLAY "M3". M4. DISPLAY "M4". STOP RUN.

**Expected from the spec.** gr3: 'D 35' / 'M3' (then STOP RUN). goto: 'M3' / 'M4'. §14.9.33.4 3) transfers control as if GO TO M3; §14.9.28.4 5) a) puts PERFORM M2's return mechanism 'after the last statement of procedure-name-1', and the GO TO leaves M2 before its last statement runs, so control is at M3, not back in M1.

**Observed / reasoning.** gr3: 'D 35' / 'BACK-IN-M1'. goto: 'BACK-IN-M1'. In __Dispatch(2, 2) the paragraph at pc 2 sets __atExit, the GO TO sets __pc = 3 = __exitPc + 1, and the fall-off test fires. RESUME AT a non-adjacent paragraph lands correctly (gr3b.cob), so RESUME's binder/emitter is faithful and the defect is the dispatcher's GO TO landing shared by GO TO (§14.9.17), RESUME AT (§14.9.33.4 3)), and every other `goto __xfer` transfer - the fix is to let a transfer (`goto __xfer`) bypass the fall-off test (e.g. the fall-through epilogue alone signals 'fell off'), with a drift test that every transfer arm reaches __xfer through the transfer path. Sweep: EXIT PARAGRAPH/SECTION (§14.9.14.4 GR6/GR7) and GO TO DEPENDING land through the same label.

**Code site.** src/Cobol.Net.Compiler/CodeGen/DispatchEmitter.cs:195 (the emitted __Dispatch return test)
