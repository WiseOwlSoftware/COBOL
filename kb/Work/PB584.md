# PB584 — LANDED — two composers for one image, and the seed was the wrong one

Found 2026-09-04 by the `PB207` implementer, which fixed the two sibling composition defects INSIDE a bit group
(`AsBits()`/`FromBits` summing widths instead of placing members; a bit group's compile-time image concatenating
packed member images) and measured that a MIXED group has the same defect one level up. Re-derived on this tree
for this note.

## Repro (`--std 2023`)

```cobol
       01  CTL.
           05  H1  PIC 1(4) USAGE BIT VALUE B"0100".
           05  H2  PIC 1(4) USAGE BIT VALUE B"0001".
           05  H3  PIC X(1) VALUE "B".
       01  CV  REDEFINES CTL PIC X(2).
```

With the REDEFINES alias the group takes the character-image (Tier-B) backing and its seed is composed by
`GroupImageCodec.ImageInitOfOne`'s member-wise group arm: `DISPLAY` of H1/H2/H3 gives `[0100][0000][]` and
`CV(2:1)` is empty. The identical group without the alias (record-struct lane) gives `[0100][0001][B]`.

## The rule

§8.5.1.6.3 (Alignment of data items of usage bit): "Alignment of elementary bit data items and bit group items
within a record, when neither a SYNCHRONIZED clause nor an ALIGNED clause is specified, is at the next bit position
in storage when that item is: — an elementary bit data item immediately following an elementary bit data item or
bit group item of the same level; …" — so H1 and H2 form ONE run of eight bits occupying one byte, and H3 is the
second byte; the record is two bytes, which is exactly what `CV PIC X(2)` describes. §13.18.44.4 GR1: "Storage
association for the subject of the entry starts at the first bit of the data item referenced by data-name-2 and
continues over an area sufficient to contain the number of bits required by the data item referenced by the
subject of the entry." — CV(2:1) must therefore be `B`. (Both quotations copied from `specs/ISO_COBOL.md` at
those headings; a `cite.py --check` on each is the implementer's first step.)

## The mechanism

`PhysicalModel` (`PhysicalChildrenOf`) already computes §8.5.1.6.3's runs and drives `AsImage()` at run time;
`GroupImageCodec.ImageInitOfOne`'s member-wise arm composes the compile-time seed from per-child images without
consulting the runs, so a bit member's image is padded to its own byte and the following members shift. Two
composers, one law. The likely fix is `ImageInitOfOne` consulting `PhysicalModel.PhysicalChildrenOf` and packing
each bit run through `CobolBits.Pack` (PB203's one write-side bit-order law), which is the same composition
`GroupImageCodec.BitAreaOf` (PB207) now performs for a pure bit group — extend it to runs inside a character group
rather than adding a third composer.

**Sibling in the same population:** `ImageInitOfOne`'s elementary arm returns `FigurativeInitializer`'s
`pic.Length` characters for a figurative VALUE (`VALUE ZERO`, `VALUE ALL B"1"`) BEFORE the `Usage.Bit` `BitsPack`
arm, so a figurative on a `USAGE BIT` leaf seeds its carrier width where the packed image is required — suspected
from reading by the PB207 implementer and reachable only through this population; fix and witness it together.

## Goldens

A REDEFINES-aliased mixed group (two runs, a character member between) read member-wise AND through the alias
with `FUNCTION ORD` per byte, expected bytes derived from §8.5.1.6.3 before the run; the same group without the
alias as the control; a figurative VALUE on a bit leaf inside it. PB207's `pb207_bit_group_value` leg 12 is the
pure-bit-group precedent for "seed and `AsImage()` agree byte for byte".

## LANDED — 2026-09-22, wave 44 (group MOVE AND OPERAND RENDERING)

Reproduced exactly as written, on this worktree's own build, before anything was changed — and the sibling
the note suspected "from reading" was real, plus a THIRD arm of the same mechanism nobody had looked at:

```
--std 2023, the note's own declaration
  H=[0100][0000][DLE]  CV bytes 0x40 0x10   (the alias)   required [0100][0001][B], 0x41 0x42
  H=[0100][0001][B]                        (no alias)
a figurative on a bit leaf inside it   VALUE ZERO / VALUE ALL B"1" seeded the CARRIER: bytes 0x30 0x30
the SAME figurative inside a PURE bit group   VALUE ALL B"1" read back 0000 through the alias, 1111 without
a ROOT-level bit leaf behind an alias   VALUE ZERO gave the byte 0x30, not 0x00
```

THE ROOT WAS TWO LAWS EACH WRITTEN TWICE, so the repair is two extractions rather than two patches:

1. **§8.5.1.6.3's RUNS have ONE computation** — `BitLayout.RunsOf`, returning a `BitRunMap` (which member
   LEADS a run, which is in one). `PhysicalModel.BuildPhysicals` owned a private copy and the compile-time
   image seed had NONE, so the record-struct lane packed a mixed group's same-level bit members into one
   byte and the seed gave each its own. Both composers now ask the one map, and
   `BitRunImageDriftTests.BothImageComposers_AskTheOneRunLaw` fails if either stops.
   ⚠ The seed cannot simply walk `PhysicalModel.PhysicalChildrenOf`: `DataBinder.AssignClassOffsets` marks
   every DESCENDANT of a redefines class `IsCanonical = false`, so that walk answers EMPTY for the children
   of a Tier-B canonical — the exact group the seed exists for. What the two share is the LAW, not the list.
2. **A boolean item's VALUE has ONE carrier answer** — `ValueInitializer.BooleanCarrierOf`, the three arms
   the standard writes: a figurative filling the boolean positions (§8.3.3.6.4 GR4 makes the zero format
   "one or more of the boolean character '0'"), a Format-6 `ALL literal-1` repeated to them (GR2), and a
   plain boolean literal zero-padded right (§13.18.63.3 SR10 / §14.6.8.6). THREE lanes answered it and each
   was missing a different arm: the record-struct lane had all three, the bit-run carrier lane had no
   ALL-literal arm, and the image seed reached the generic figurative arm BEFORE its own boolean arm and so
   returned carrier characters where the packed image was required. The USAGE decision — pack or not — is
   now `GroupImageCodec.BooleanImageOf` alone, so the VALUE rules and the storage question are separable.

Measured after, same programs, `--std 2002` and `--std 2023` alike: `[0100][0001][B]` with CV's bytes 0x41
0x42 (ORD 66 and 67), the figurative pair `[0000][1111]` packing to 0x0F, the pure bit group's
`ALL B"1"`/`ZERO` packing to 0xF0, and the root bit leaf's 0x00.

**Goldens.** `tests/conformance/2002/pb584_mixed_bit_group_image.cob` (seven legs: the note's shape, the
no-alias control, a WRITE-then-read round trip proving seed and run time are ONE composition, the figurative
pair, the pure bit group, a root-level leaf, and a THREE-member run crossing a byte with the character
member landing at "the first bit position of the first available byte"), plus
`tests/conformance/negative/pb584-mixed-bit-group-below-2002`.
`tests/Cobol.Net.Tests.Conformance/BitRunImageDriftTests` is the net: six member shapes, each compiled WITH
and WITHOUT the REDEFINES alias and required to read back identically, so a new shape is measured on both
lanes by adding one row.
