# PB2129 — the indexed organization has no index

Found by wave 1026 group E (PB2117, the R0 performance baseline; report `w1026e-PB2117-report.md`), filed by the
train-1026 lander.

## Mechanism

`src/Cobol.Net.Runtime/IO/IndexedConnector.cs` keeps the file's records in a flat list (`_recs`) and answers every
keyed question by walking it:

- `FindRandom` (~line 438): a linear scan that builds a `KeyOf` string for each record it passes.
- `Write` (~line 549): `_recs.Any(...)` scans the whole file once per key to detect a duplicate.
- `Ordered` (~line 789): sorts the whole file on every `ReadSequential`.

A program that loads N records and reads them back does O(N^2) work (O(N^2 log N) for a READ NEXT walk). The output
is correct; the cost grows with the file.

## Repro

`tests/Cobol.Net.Benchmarks/Programs/IDXHOT.cob` with its `LOOP-COUNT` line set to 2000, 4000, 8000 and 16000 runs in
0.86, 2.9, 10.7 and 51 s on our runtime (3.3x then 3.8x per doubling; GnuCOBOL 3.2 grows 1.4x then 1.6x and takes
20 ms at 2,000). `python scripts/arch/perf_baseline.py` reports the ratio as 60x at 2,000 and 330x at 8,000 (record
`docs/rearchitecture/evidence/perf-baseline/354c79ef3312.md`). An indexed file of about 100k records takes more than
ten minutes.

## What the fixer owes

A real index per key of reference (prime and each alternate, duplicates in arrival order per the RECORD KEY and
ALTERNATE RECORD KEY general rules), so random access, the duplicate check and the sequential walk are each
O(log N); `perf_baseline.py --against` the R0 record shows the IDXHOT rows linear, and the existing indexed I/O
goldens and NIST IX* programs stay byte-identical.

## Landed (kb/Work PB3334, wave 1118 group A4)

The indexed organization keeps one B+ tree per key (docs/rearchitecture/DESIGN-runtime-library.md 2.2.1.4): a random READ is
a seek of the key's tree, the duplicate checks are a seek on the key part, and a sequential READ is one seek from the file
position indicator's key value and the prior READ's ordinal — `FindRandom`'s scan, `Write`'s per-key scans and `Ordered`'s
per-READ sort are deleted with the record list. Measured on this build (Debug, wall clock, evidence only, never a test):
IDXHOT at 2 000 / 4 000 / 8 000 / 16 000 / 32 000 records ran 0.29 s / 0.75 s / 1.27 s / 2.21 s / 3.77 s — about 1.7x per
doubling after the first (process start-up dominates 2 000), against the 3.3x and 3.8x recorded here, with the witness sums
N(N+1)/2 and ERR-COUNT 0 at every size. The count-based witness is `IndexedEngineTests.A_statement_writes_pages_bounded_by_its_trees_depth_whatever_the_files_size`
(no statement of a 4 000-record load writes more than 2.2.1.11's bound, and the last statements cost no more than the
earlier ones); PB3336 owns the full performance witnesses (a)-(d). The existing indexed goldens are byte-identical on stdout
(245 cases re-probed). `perf_baseline.py --against` the R0 record was not run (it needs a Release build and a gate run under
the scope `whole`); it is the lander's and PB3336's.
