# PB5847 - the implicit CLOSE of a CANCEL, and of an INITIAL program's EXIT PROGRAM, never stores an I-O status (every edition)

**Ruling: UPHELD (b), harm wrong_answer.** The rows `1985-GR-X.5.3.4-10` and `1985-GR-X.5.4.4-3` do not close on their inherited verdict. The implicit CLOSE of a CANCEL, and of an INITIAL program's EXIT PROGRAM, never stores an I-O status: the FILE STATUS item keeps 10 where 00 is due. The Mythos lane ran it (`iclose.cob` printed `AFTER CANCEL GST=10` and `AFTER INITIAL GST=10`). It is the sibling of kb/Work PB5685 (the same emitted block). The checker's confidence: high. Cause (b): the same at `--std 2023`. Severity MAJOR: a wrong-answer defect is at least MAJOR.

**The checker's evidence (rulings.json, copied).** `§1985:X.5.3.4 GR10`: during an explicit or implicit CANCEL "an implicit CLOSE statement without any optional phrases is executed" for each open internal file; `§1985:X.5.4.4 GR3` makes an INITIAL program's EXIT PROGRAM "equivalent also to executing a CANCEL statement referencing that program". A CLOSE "causes the value of the I-O status associated with file-name-1 to be updated" (`§1985:VII.4.2.4 GR4`), and the FILE STATUS item is always updated to contain the value of the I-O status whenever the I-O status is updated (`§1985:VII.2.5.4 GR1`). A FILE STATUS item that outlives the cancelled program (a GLOBAL item of the container, legal at 1985 because SR2 of the FILE STATUS clause bars only the File and Communication Sections) must therefore read 00 after the CANCEL. Both paths reach ProgramEmitter's CloseFiles() block (`ProgramTable.CancelNode` for CANCEL; `ProgramTable.CallProgram` finally, then `EndInitialActivation`, for the INITIAL EXIT PROGRAM), which calls FileCloseIfOpen per file with no status store, so the item keeps the last explicit statement's 10. The connector itself is closed (the reader's p10d; not re-probed). The run unit's own implicit close at STOP RUN goes through the same block, but its status is unobservable (kb/Work PB5765).

**Sites:**
