# PB2967 — a binary64 result saturates silently into a 16-byte COMP-5 receiver

Filed 2026-10-10 by the train 1056 lander from the wave 1056 C implementer's report
(`E:\COBOL-coord\scratch\reports\w1056c-PB2918-report.md`, lead 3). Independent of PB2918 (A has 30 digits).

**Repro:** `E:\COBOL-coord\scratch\w1056c\var1.cob`: `COMPUTE R = FUNCTION VARIANCE(A, 1) ON SIZE ERROR ...` with
A PIC S9(30) VALUE 10^29 and R PIC S9(19) COMP-5 stores 2^127 - 1 (170141183460469231731687303715884105727) and takes
NOT ON SIZE ERROR. The variance is about 2.5E+57, which no 16-byte container holds. The same statement into a
PIC S9(18) receiver correctly takes ON SIZE ERROR.

**Site:** the float-to-fixed landing for a `BinaryCapacity` receiver (the `CobolFloat` to `CobolNum` store): the
observed value (exactly Int128.MaxValue) says the binary64 value is converted to the Int128 carrier with saturation
before the receiver's capacity test, so the saturated value passes as fitting (to be confirmed at the site).

**Why.** §14.7.5: a result whose value exceeds the largest value the resultant identifier can contain is the size
error condition; a silent clamp with NOT ON SIZE ERROR is a wrong answer. The fix is the same `WideningFits`-first
order PB639 gave the fixed-point landings: test that the binary64 value fits the carrier (and then the receiver)
before converting.

## Landed 2026-10-11 (wave 1059 D)

Re-probed on a fresh build before any edit: `var1.cob` stored 1687303715884105727 (the low digits of 2^127 - 1) and took
NOT ON SIZE ERROR; the PIC S9(18) control raised. The note's guess about the site was right, and the defect is wider
than one function: **three checked landings return the saturated sentinel `Int128.MaxValue`/`MinValue`, and the sentinel
is only ever refused by a receiver whose capacity is SMALLER than the carrier.** A 16-byte COMP-5 receiver's capacity
IS the carrier (`CobolNum.InBinaryRange`: every Int128 is in range), so it accepted the sentinel as a legal value.
Measured on the old build, all `COMPUTE ... ON SIZE ERROR` into `PIC S9(19) COMP-5` (and the unsigned and `V99`
variants): `FUNCTION VARIANCE(A, 1)` (about 2.5E+57), `FUNCTION EXP10(45)`, `A ** 1.5`, a COMP-2 holding 1.0E+40 or
-1.0E+40 (stored -2^127), and `FUNCTION NUMVAL-F("1E+39")` (stored 0469231731687303715) all took NOT ON SIZE ERROR.

**Root fix (the SDIDI lane already had it, PB74).** The in-band sentinel is replaced by the out-of-band raise: past the
Int128 carrier the CHECKED landing throws `CobolSizeError` EC-SIZE-TRUNCATION (`CobolFloat.BeyondCarrier`, §14.7.5
case 3 with no-phrase rule 4), exactly as `CobolDec.ToUnscaledChecked` does, and the statement's size-error catch
already maps it to the flag with the receiver unchanged. Three sites: `CobolFloat.ToScaled` (the
final-transfer landing: `StoreArgs`, `EditedLanding`, `CallAbi.LandChecked`; same name, so the shipped runtime surface
and the ABI pin do not move), the checked
`CobolIntrinsics.FromDouble`/`FromDoubleBounded` (the float intrinsic family, native `**`), and the checked
`CobolIntrinsics.Rescaled` (NUMVAL-F). The saturating form survives as the new `CobolFloat.ToScaledSaturating` (PublicAPI.Unshipped), for the
INTERMEDIATE consumers that have no store (`NumericRenderer.Align`/`AlignRoundedUp` via the new
`RuntimeApi.FloatToScaledIntermediate`; the formatted-time seconds), so a store can no longer ask for a sentinel by
flag. Tests: `CarrierLandingFormTests` (raise vs saturate vs low-order, the exact-oracle sweep, the emitter-signature
drift pin); goldens `2002/pb2967_float_result_wide_binary_receiver_size_error` (eight legs) and
`2014/pb2967_numval_f_wide_binary_receiver_size_error` (five legs), each run against the pre-fix `cobol.exe` first
(every oversized leg STORED there). Docs: NUMERIC_DESIGN landing paragraphs and CONFORMANCE DOC-A.1-70.
