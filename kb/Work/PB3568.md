# PB3568 — VALIDATE's operands are never bound

## Scenario

Fuzz program fz02791 (`THEY_REJECT:13.18.11`): `VALIDATE WS-ALPHA SETTING WS-STATUS`. SETTING is not a reserved word, so it is
read as a third operand, which is undefined. GnuCOBOL refused ("'SETTING' is not defined") and was right. WiseOwl gives only the
COBOL1580 "VALIDATE unsupported" warning and compiles. COBOL1580 documents the non-support of the VALIDATE FACILITY
(`docs/CONFORMANCE.md` §4), but the statement's identifiers remain identifiers.

### Reduced repro (the D2 adjudicator's probe, verbatim: `adj\D2\probes\d2-validate-operands.cob`)

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. D2VOPS.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 WS-A PIC X(5) VALUE "ABCDE".
PROCEDURE DIVISION.
    VALIDATE WS-A NOSUCH-ITEM
    STOP RUN.
```

## Expected (spec)

Each citation was re-run through `python scripts/spec/cite.py --check` from the worktree on 2026-10-23 (all OK).

- §14.9.50.3 1) (OK): "Identifier-1 shall reference a data item described in the file, linkage, local-storage, or
  working-storage section. Identifier-1 shall not be reference-modified."
- §14.9.50.3 2) (OK): "Identifier-1 shall not reference a data item of class index, message-tag, object, or pointer."
- An undefined name violates the general identifier rules (the orchestrator's reading; no separate clause was quoted).

The syntax rules the compiler owes a diagnostic for are those two plus the undefined name. Expected: a compile error for
`NOSUCH-ITEM`.

## Actual (judge e7cf38ce4)

Compile rc 0; the only diagnostic is the COBOL1580 warning; the program runs. Measured by the adjudicator: an undefined name,
a reference-modified operand (`VALIDATE WS-A (1:2)`, which SR1 forbids) and a POINTER operand (SR2) all compile clean.

## Mechanism and code site

`src/Cobol.Net.Compiler/Binding/Bound/StatementBinder.cs:597` (the call) and `:722`: `BindUnsupportedFacility` returns a
`BoundNop` without binding the `dataReference+` operands of `CobolParserCore.g4:1061`.

## Witnesses

fz02791.

## Sibling sweep and golden to require

- MCS SEND and RECEIVE at 2023 go through the same `BindUnsupportedFacility` (the D2 adjudicator did not probe them: they are
  outside the 2014 slice). Every statement that routes to it binds the operands that are identifiers.
- Golden: the repro (an error for the undefined name, plus the COBOL1580 warning for the facility), a reference-modified
  operand and a pointer operand, each refused; a valid `VALIDATE WS-A` still gets only the warning.

## Orchestrator decision

COBOL1580 documents the non-support of the VALIDATE FACILITY (CONFORMANCE.md §4), but the statement's identifiers remain identifiers: an undefined name violates the general identifier rules; §14.9.50.3 SR1 (no reference modification) and SR2 (not a pointer) are syntax rules the compiler owes a diagnostic for. The binder's `BindUnsupportedFacility` returns a nop without binding any operand; sibling arms: MCS SEND/RECEIVE at 2023 through the same path.

## Landed (wave 1157 K)

Re-probed on a fresh build: all four shapes of the note reproduced (an undefined name, a reference-modified operand, a
pointer operand compiled with only COBOL1580), and the MCS siblings did too (an undefined FROM or GIVING operand, an
undefined name inside an ON EXCEPTION phrase, an unknown `RAISING EXCEPTION` name).

**Root.** `BindUnsupportedFacility` is the statement half of "accept inert"; nothing ever read the declined statements'
parse subtrees, so declining the FACILITY had also declined the identifiers. New collaborator
`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/DeclinedFacilityBinder.cs` reads them and builds no node:

- VALIDATE: each identifier-1 resolves through the sending-side resolver (an undefined name is COBOL1639) and is screened
  against SR1 (reference-modified, or not described in a data division section the rule lists: COBOL4777), SR2 (class
  index, object, pointer: COBOL4778) and SR4/SR5 (66-level, ANY LENGTH: COBOL4779). SR3 needs a `VALIDATE-STATUS`
  clause, which COBOL1708 already refuses; SR6 is COBOL1607's.
- MCS RECEIVE/SEND at 2023: the data references resolve (FROM, GIVING, RETURNING), the `CONTINUE AFTER` expression binds,
  the exception phrases' statements bind, and SEND's `RAISING EXCEPTION` name goes through the exception-name funnel
  (COBOL0711 for an unknown name). The SEND `TO` operand is NOT resolved: Format 1 names a message-server-name, which is
  no data item (§14.9.38.3 SR2), and Format 2's message-tag cannot be told apart by the grammar. The message-tag class
  checks (SR1 of RECEIVE, SR4 of SEND, SR2 of VALIDATE) have no item to refuse while USAGE MESSAGE-TAG is itself refused.
- A deferred reference shape (a legal operand whose place this compiler has not built) is taken back off the unbuilt-operand
  ledger: the statement is inert, so "reaching it aborts the run unit" would be false.

**Shape (rule 5).** `StatementBinder` routes every recognize-and-name call through a `BindDeclined…` method that reads the
operands first; `DeclinedFacilityOperandDriftTests` fails a recognize-and-name call outside one and a declined statement
rule whose `dataReference` count differs from the adjudicated roster, so the next declined statement cannot ship unbound.

**Goldens.** `conformance-suite/cases/14.9.50-VALIDATE/pb3568-validate-*` (undefined, ref-modified, report-section item,
pointer, index, object, 66-level, ANY LENGTH: each refused at 2002, 2014 and 2023); the control
`wiseowl/cases/14.9.50-VALIDATE/pb3568-validate-legal-operands-inert`; `wiseowl/cases/14.9.31-RECEIVE` and `14.9.38-SEND`
`pb3568-*` (2023). Codes COBOL4777-4779.

## Landing

- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/DeclinedFacilityBinder.cs#BindValidate` / `#BindReceive` / `#BindSend` own the rule that a declined facility's statement still reads its identifiers; reuse `host.Expr.ResolveSending` (never `ctx.Refs.Resolve`, `ReceivingResolutionDriftTests`) and `host.BindBlocks` for the exception phrases. Trap: a deferred reference shape lands on the unbuilt-operand ledger and the statement funnel would announce "aborts the run unit" for an inert statement, so the collaborator takes it back with `TakeUnbuiltSince`.
- `src/Cobol.Net.Compiler/Binding/Bound/StatementBinder.cs#BindDeclinedValidate` / `#BindDeclinedMcs`: every `BindUnsupportedFacility` call sits in a `BindDeclined…` method (`DeclinedFacilityOperandDriftTests`). Trap: `RefusalNodeDriftTests` rejects `if (!cond) return new BoundNop();`, so a below-edition no-op is written as the positive branch followed by the `return new BoundNop();`.
- `src/Cobol.Net.Editions/Diagnostics/DiagnosticCatalog.cs#ValidateOperandForm` / `#ValidateOperandClass` / `#ValidateOperandDescription` (COBOL4777 to 4779).
- Fixed-form goldens: keep every code line at or under column 72; an overlong DISPLAY line truncates a qualifier name (`SECOND-RE`) and, now that the operands resolve, draws COBOL1639.
