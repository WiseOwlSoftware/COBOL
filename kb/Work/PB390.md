# PB390 — the rule is checked, and then the answer is shipped as a run-time abort

## THE MECHANISM

`BoundUnsupported` is the compiler's carrier for *"recognised but not yet implemented"*; the emitter renders it
as `EmitCore.LoudStmt` (`src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:211`), i.e. a call to
`NotImplemented.Run(feature)`. Several binders use it to deliver a **decided SYNTAX-RULE verdict**. The rule is
correctly evaluated at bind time — the code even carries the SR citation in its message — and then the verdict
is compiled into the program instead of being reported. Three consequences, all measured below:

1. **The compile SUCCEEDS with no diagnostic** and an assembly is produced, so an illegal program on a
   rarely-taken branch **ships**;
2. when the statement is reached the program **aborts with an unhandled .NET exception and a stack trace**,
   with no source location;
3. the message **blames the wrong party** — it tells the user COBOL.NET has not implemented a feature when the
   user's program is illegal.

`grep -rn "new BoundUnsupported(" src/ | wc -l` → **141 sites** on HEAD. At least twenty of them carry a decided
syntax rule rather than an unimplemented feature: `ControlFlowBinder.cs:228, :235` (GO TO), `:304, :308`
(PERFORM / PERFORM THRU), `EcBinder.cs:136` (RESUME AT), `SetBinder.cs:458` (SET condition-name),
`SetAlterBinder.cs:126, :128, :131` (ALTER), `SearchBinder.cs:29, :88` (SEARCH without INDEXED BY),
`SortBinder.cs:75, :86` (SORT INPUT/OUTPUT PROCEDURE), `ReportWriterBinder.cs:65, :92, :102, :123`
(INITIATE/GENERATE/TERMINATE/SUPPRESS), `KeyedIoBinder.cs:299` (START KEY), and the four in
`CorrespondingBinder.cs:54-77`. **The carrier is doing two incompatible jobs** — this is
`feedback_one_mechanism_per_job`, and it is the same mechanism `kb/Work/PB236` (OPEN) already owns for ADD;
PB236's `inventory_rows` do not reach these four, which is why this note exists beside it. Fix them together.

The CORRESPONDING arm carries a second, independent defect: **two code comments assert a shape is impossible and
the premise is false.** `CorrespondingBinder.cs:229-230` says *"A RefModPlace group is impossible — reference
modification resolves only over elementary character items"*, and `Bind`'s comment says the same. Group
reference modification is SUPPORTED and has its own golden
(`tests/conformance/2023/pb70_group_reference_modification.cob`). So SR12's second half ("shall not be
reference-modified") is not checked at all; the shape is refused only because `CorrAccess.Create`'s switch has
arms for `MemberPlace` and `RedefViewPlace` and falls to `_ => null`, producing a STORAGE-shape message that
names neither SR12 nor reference modification. **A comment claiming a case cannot happen is not a check**
(`feedback_a_dead_lookup_is_also_unverified`).

The SR6 message is **also factually wrong**: `SW-ON` *is* a condition-name — a SPECIAL-NAMES switch-status
condition-name (§8.8.4.6) — and its actual defect is precisely what SR6 states, that it is not associated with a
conditional variable. The diagnostic denies the fact the rule turns on.

The PERFORM resolution itself is CORRECT and must not be broken by the fix: it is scoped to the source element,
so a contained program's paragraph and a data-name are both rightly not found, and an INVERTED
`PERFORM P2 THRU P1` range is legal COBOL and is accepted today.

## THE CODE SITES, AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:304` (procedure-name-1) and `:308`
  (procedure-name-2); the GO TO twins at `:228` and `:235`.
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SetBinder.cs:458` (SET condition-name) and the Format-3
  switch-mnemonic sibling in `SetAlterBinder.cs#SwitchBindSet`.
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/CorrespondingBinder.cs:54-77` — four `BoundUnsupported`
  returns — plus the false impossibility comments at `:59-62` and `:229-230` and the `_ => null` arm of
  `CorrAccess.Create`.
* `src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:211` — the one arm that turns all of it into generated
  code.

**Repair (CLAUDE.md rule 5 — the shape, not four edits):**

1. **Separate the two jobs.** A binder that has DECIDED a rule raises `ctx.Edition.Error` with the SR citation
   and the offending operand, at the statement's source location; `BoundUnsupported` keeps only its real job,
   "this language feature is not implemented yet". The sibling arithmetic screens (COBOLNET1675 / COBOLNET1689)
   and `PB128`'s `ScreenResultant` are the existing model.
2. **Add the drift test that keeps them apart** — enumerate every `BoundUnsupported` construction and assert its
   feature string contains no `SR<n>` / `shall` / `unknown` wording (or, better, make the constructor take a
   `Feature` value object that a syntax-rule message cannot be built from). **Make it fail once against the
   twenty sites above.**
3. **Give `CorrAccess.Create` an explicit `RefModPlace` arm** with its own SR12 message instead of a comment
   asserting the case is impossible, and delete both false comments in the same change set.

## LANDED 2026-09-13 — the decided rule is a diagnostic, and the resolution it rides is ONE step

**What was re-measured first, on this worktree's own build, before anything changed.** Every case in this note
still reproduced, with one that had got WORSE than recorded. `MOVE CORRESPONDING G1(1:3) TO G2` no longer
aborted: it COMPILED AND RAN, printing `AFTER ABCDEF` — the whole group moved with the reference modifier
silently DISCARDED. The note recorded a storage-shape abort, which came from `CorrAccess.Create`'s default arm;
kb/Work PB393 then made that factory switch on `Place.Undecorated`, which strips the `RefModPlace` decoration
along with the `OdoGroupPlace` it was after, and the accident that had been standing in for SR12's second half
stopped standing in for it. A wrong answer, produced by the absence of a check a comment said was unnecessary.
The other seven reproduced as written, now carrying PB236's COBOLNET1756 announce — a WARNING saying the
COMPILER is incomplete, on a program that still compiled, still shipped an assembly, and still died at run time.

**The structure.**

1. **ONE procedure-name operand resolution.** `ProcedureTableBuilder.ResolveProcedureOperand(pn, verb, rule)`
   resolves or REPORTS (COBOLNET1639) and returns null; the raw resolver is renamed `ResolveProcedureQuiet` and
   documented as belonging only to the two PRESCANS that are not a statement's own bind (the ALTER switch-field
   prepass, the USE FOR DEBUGGING SORT/MERGE-overlap scan). Eight sites entered it: GO TO, GO TO … DEPENDING,
   PERFORM (SR12), PERFORM THRU (SR13), RESUME AT, ALTER's two operands, and SORT/MERGE INPUT/OUTPUT PROCEDURE.
   The message lives in the ONE check catalog (`StatementValidation.RejectProcedureName`) and composes the three
   facts a call site cannot: the word is declared as a DATA ITEM, resolution was METHOD-LOCAL (§11.7), and the
   caller's own quoted rule. `StatementBinder.OoScopeHint` — a hint that used to ride the run-time abort — is
   deleted, because the hint and the report can no longer be written apart.
2. **SORT's private copy folded in, and stopped lying.** `SortBinder.RejectUnknownProcedure` (PB236's own, the
   only site that had this rule) reported `procedureName(0)` whichever of a THRU pair had failed, so a bad
   second name accused the good first one. Each name now reports itself.
3. **The SET operand rules, both formats.** Format 4's §14.9.39.3 SR6 gets `RejectSetConditionName`, which tells
   the two kinds of condition-name apart (§8.4.4.1) instead of denying the operand is one: a switch-status
   condition-name draws COBOLNET1757 quoting SR6 and pointing at Format 3; a word declaring nothing draws
   COBOLNET1639. Format 3's SR5 sibling moved in the same change set.
4. **SR12's second half is CHECKED, not assumed.** `CheckCorrespondingGroupOperand` takes the **`Place`**, not
   the `DataItem`, and walks its decorators for a `RefModPlace` — the shape `ResolveRecordName` already uses
   (kb/Work PB347), and the only level at which a reference modifier is visible, since `PlaceDecorator.Item`
   answers with the INNER item. Both false-impossibility comments are gone, replaced by what is actually true.

**Why no new diagnostic code.** COBOLNET2015–2017 were allocated and are returned UNUSED. "This source element
defines no such name" is ONE rule (§8.4.2.1), already COBOLNET1639, and the procedure-name space was simply
missing from it — the same argument PB236 made for file-names. The operand refusals are COBOLNET1757, whose
own contract is that the CODE is the identity of the MECHANISM and the MESSAGE carries the rule.

**⚠ DETERMINATION (owner-overturnable), recorded on row `SR-14.9.39.3-6`.** §8.4.4.1 ends its description of the
switch-status kind with "This condition-name may also be used in a SET statement to set the associated switch to
the 'on' or 'off' status", which read alone would ADMIT `SET SW-ON TO TRUE`. Rejected in favour of the
statement's own definition: Format 3's general format, RENDERED FROM THE PRINTED PAGE (PDF p759) rather than
read from the transcription, prints `{ mnemonic-name-1 } … TO { ON | OFF }` with no condition-name alternative,
and Format 4's SR6 excludes the switch kind by name. Nothing that used to RUN is refused by this reading — the
statement aborted the run unit before — so the choice costs no working program either way.

**Evidence.** Eleven probes refused at compile time with the right rule and the right message (before: seven
compiled-and-threw, one compiled-and-ran-wrong). One positive golden at the introducing edition
(`tests/conformance/85/pb390_procedure_and_condition_operands.cob`, expected output derived from GR4/GR6,
§14.9.39.4 and §14.7.6), seven negatives (`tests/conformance/negative/pb390-*`, each verified at every edition
its `reject-at:` names), and `DecidedRuleStageDriftTests` — 22 rows whose every refusal also asserts the ABSENCE
of COBOLNET1756, plus eight LEGAL rows (the inverted THRU range, a SECTION target, a qualified procedure-name,
the level-88 SET, the Format-3 switch set, plain-group CORRESPONDING, a group reference modification) that a
reject-everything compiler would fail. The suite was FALSIFIED once by restoring the PERFORM arm's
`BoundUnsupported`: two rows went red, and green again when it was restored.

**The green test that pinned the broken stage moved with the fix.** `OoSpineTests.Trap10_CrossMethodPerform`
required the RUN to die on `unknown procedure 'PARA-C'`. Its intent — a cross-method PERFORM must never transfer
silently — is right and is kept; its expectation is now the compile-time COBOLNET1639 carrying the §11.7
method-local explanation, and the test is renamed `Trap10_CrossMethodPerform_IsRefusedAtCompileTime`.

**Rows:** `SR-14.9.25.3-12` PARTIAL → CONFORMS, `SR-14.9.28.3-12` and `SR-14.9.28.3-13` DIVERGES → CONFORMS,
`SR-14.9.39.3-6` DIVERGES → CONFORMS. GAP 2501 → 2497. A second batch re-recorded `GR-14.9.17.4-1` and
`GR-14.9.28.4-4` unchanged except for the renamed symbol in their `code-location`.
