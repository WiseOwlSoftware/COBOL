# PB153

Rows: SR-14.9.3.3-4/-5 (one missing feature, both directions), confirmed against the §13.18.60.2 diagram (line 19873). The CALL side's SR14 (restricted program-pointer signature check) is separately blocked on the P13 prototype registry; the DATA-pointer grammar + the ALLOCATE/SET/CALL restriction screens are not.

*(Found by Phase-B batch 8 — §8.8.1 + §14.9.1–14.9.12, 2026-08-29; one adjudicator + one independent refuter per subject. Full forensic evidence: the named rows' `notes` in `tests/version-matrix/traceability-inventory.json`; the raw finding lines in the session scratchpad `pb-batch8/findings.txt`.)*

## Landed 2026-09-02 (cluster D) — both waves

The note framed this as blocked on grammar. **It was two independent mechanisms, and the bigger one needed no
grammar at all.** Annex D.9.2.2 names both sources of a restricted data-pointer: (1) `USAGE POINTER TO
type-name-1`, and (2) `ADDRESS OF identifier-1` where identifier-1 is a strongly-typed group item or another
restricted data-pointer — normative at §8.4.3.11.4 GR2. Source 2 was violable the day strong TYPEDEF landed.
Measured before the fix: `01 TPT TYPEDEF STRONG. 05 F PIC 9(4). 01 V TYPE TPT BASED. 01 P USAGE POINTER.
ALLOCATE V RETURNING P.` bound **clean**.

`grep -rn StrongTypeModel src/Cobol.Net.Compiler` returned NINE consultation sites — MOVE, CALL, ACCEPT, STRING,
REDEFINES, RENAMES, intrinsics, ReferenceResolver — and **ZERO in PtrBinder.cs**. The strong-type use-restriction
network had been built out compiler-wide and the pointer subsystem was never wired into it. That is the shape of
the defect, and it is why the landing is subsystem-scale rather than one screen.

**Model:** `StrongTypeModel.PointerRestriction` / `AddressOfRestriction` / `SameRestriction` / `StrongGroupType`,
reducing both sources to a type NAME. A restriction is to a TYPE, not a member position, so it is deliberately NOT
`SameStrongType` (whose relative-member-path refinement answers a different question).

**Screens, all in the 0869 pointer band where PtrBinder already reports every other §14.9.39/§14.9.3 operand rule:**
§14.9.3.3 SR5 and its SR4 converse on ALLOCATE (both the based form AND the CHARACTERS form — Format 1 specifies no
data-name-1, so a restricted RETURNING can never be satisfied there); §14.9.39.3 SR19 **and** SR20 in BOTH arms of
`BindSetAddress`, which are separate code paths; §14.8.2.3.2's restricted-pointer clause in `CallBinder`, scoped to
the AS-NESTED loop so the deferred cross-program equivalence axis cannot over-reject.

**Two declaration-shape rules the note missed entirely**, both now enforced: §13.18.60.3 SR18 (COBOLNET0881 — a
`TO type-name` entry whose subject lacks TYPEDEF; so `01 P USAGE POINTER TO T.` is *itself* nonconforming) and
§8.5.3.1 (COBOLNET1529 — an elementary STRONG typedef). The SR18 screen keys on `IsElementary`, not `!IsGroup`:
`RegisterTypeDecl` runs while the forest is still being built, so `IsGroup` is false for every group typedef at
that moment and the obvious spelling would have rejected all of them.

⛔ **A corpus defect that would have shipped:** `tests/version-matrix/constructs.json`'s `usage-pointer-to-type-2014`
carried `01 T TYPEDEF STRONG PIC 9(3).` + `01 P USAGE POINTER TO T.` as the construct's canonical witness — doubly
nonconforming, and never exercised, so nothing had ever contradicted it. Rewritten to the only legal shape
SR14+SR18 admit (measured to compile and run).

**Left open, owner-visible:** the row stays `pending` because its EDITION is unverified. Annex E (2014→2023) carries
no pointer entry, which rules out 2023; the dependencies (STRONG TYPEDEF §8.5.3, USAGE POINTER, BASED, ALLOCATE)
are all 2002 in this registry, so the answer is 2002 or 2014 and cannot be settled from the 2023 document alone.
Activating with a guessed number would enshrine it. **No conformance hole is held open by the wait** — a
restricted-pointer program already draws COBOLNET0900 below 2002 through the existing `usage-pointer-2002` and
TYPEDEF gates (measured).
