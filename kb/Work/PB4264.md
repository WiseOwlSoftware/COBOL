# PB4264 — a hand-written .tailor weight can take the numeric lead's primary

**Sites:** `src/WiseOwl.Cobol.Runtime/Collation/TailoringRules.cs` (`TailoringRules.ParseWeight`), `src/WiseOwl.Cobol.Runtime/Collation/CLDR/CldrTailoringBuilder.cs` (`CldrTailoringBuilder.Line`), `src/WiseOwl.Cobol.Runtime/Collation/CollationTable.cs` (`CollationTable`; its NumericLead member arrives with PB107's branch, PR #909). The fix: `src/WiseOwl.Cobol.Runtime/Collation/CollationTable.cs` (`CollationTable.Rebuild`, `CollationTable.RefuseNumericLeadCarrier`), `src/WiseOwl.Cobol.Runtime/Collation/CLDR/CldrTailoringBuilder.cs` (`Slot.ReservesValueBelow`, `Line.Number`, `Line.Assign`, `CldrTailoringBuilder.Build`), documented in the `TailoringRules.cs` class summary; test `tests/WiseOwl.Cobol.Tests.Unit/Collation/CollationTailoringTests.cs` (`Apply_RefusesAWeightAtTheNumericLeadPrimary`, `Apply_RefusesAWeightAtTheLeadOfTheTailoredZero`, `Apply_RefusesATailoredZeroWhoseLeadIsAnUntailoredCharacter`) and `tests/WiseOwl.Cobol.Tests.Unit/Collation/LocaleCollationFailureTests.cs` (`ADigitZeroTailoredAfterALetter_KeepsTheNumericLeadFree`).

> LANDED (wave 20261791, group A; review round 1 widened it). Re-probe on the build: a `.tailor` giving U+E000 the primary
> `Lookup('0').Primary - 1` applied with no error and U+E000 carried the numeric lead's primary. The reviewer's finding
> (R1-1): the same value is reached WITHOUT naming it, by moving the digit zero itself, in both arms: a `.tailor` line
> `U+0030 <P_a + 1>` and a CLDR rule `&a < 0` (the builder numbers an inserted slot `root + 1`) put the zero at P_a + 1, so
> the lead stands on the untailored letter `a` and numbers sort inside the a-words. Fix at the root, one invariant checked at
> the one derivation step: `CollationTable.Rebuild` scans the PRODUCED table's reachable mappings and refuses a table in
> which any character carries `NumericLead.Primary` (`RefuseNumericLeadCarrier`, a `LocaleCollationException` naming the
> file and the entry that carries the value or moved the zero, kb/Work PB2773). The CLDR arm does not depend on the check:
> the builder marks the digit zero's inserted primary slot `ReservesValueBelow` and `Line.Number` leaves the value below it
> unused, so `&a < 0` builds (zero after `a`, lead between them) instead of failing the locale. Not a conformance case: no
> ISO rule governs a `.tailor` file.

A numeric `.tailor` weight written at the value `root - 1` below the digit zero collides with the numeric lead. Nothing
guards it, because the `.tailor` format picks its values by hand (`TailoringRules.cs`). It has the same root as PB107
(numericOrdering): `CollationTable.NumericLead` is the zero's element with primary - 1, and `CldrTailoringBuilder.Line`
reserves the top of each primary gap only for the tailorings it builds, not for hand-written `.tailor` values.

Severity is low and the owner may decline it. Open question left as it stood: `[hiraganaQ on]`
(`CldrLocaleData.cs:228`, `CldrSettings.UnsupportedSettings`). The second lead of that report section, ICU's split of
digit runs past 254 into 254-digit numbers, is covered by PB4223 and is not filed again.
