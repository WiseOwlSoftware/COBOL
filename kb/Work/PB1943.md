# PB1943 — OPEN

Filed by the train-1007 lander from wave 1007 group A's report (`w1007a-PB1271-report.md`, "New defects" item 1).
[[PB1271]] (train 1007) made a repeating SUM entry's counter a table with subscripted references.

## Question

Does reference modification apply to a sum counter? A sum counter is numeric, its usage unspecified (§13.18.54.4);
§8.4.3.3.3 states which data items may be reference-modified. If it is admitted, `CF-T(1:2)` reads the counter's
character image; if not, the diagnostic should name §8.4.3.3.3, not "not defined" — GR5 does declare the name
("the data-name is the name of the sum counter"). Either way the current COBOLNET1639 is a misdiagnosis.
The fixer runs `cite.py --check` on the governing §8.4.3.3.3 sentence before deciding.

## Repro

Any RD with `03 CF-T COLUMN 1 PIC 9999 SUM WS-X` plus `MOVE CF-T(1:2) TO WS-Y` in the procedure division.

## Code site

`src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs#SumCounterFor` — `if (written.RefModCount > 0) return null;`
sends the reference to ordinary resolution, which cannot see a sum counter.

**Outcome: DEFECT CONFIRMED. The misdiagnosis is certain; the acceptance question is IMPLEMENTOR LATITUDE, not spec-controlled.** `MOVE CF-T(1:2) TO WS-Y` (`03 CF-T COLUMN 1 PIC 9999 SUM WS-X`) draws `COBOLNET1639: 'CF-T(1:2)' is not defined - no declaration in this source element gives the name 'CF-T'` at `--std 85`, 2002 and 2023, while `§13.18.54.4 GR5` declares the name ("the data-name is the name of the sum counter") and the control (`control.cob`: `Z=[1234] Y=[OK]`)
resolves it. The message is false whatever the answer. Flags: `rejects_legal_source: true` (holds only on the latitude ground below), `wrong_answer: true` (the `FUNCTION LENGTH(CF-T)` sibling, wrong under any DISPLAY ruling); `kind` flips to `defect`. Siblings, same mechanism (`siblings.cob`): `SOURCE CF-T(1:2)` in a report group entry, `CF-T OF CFG (1:2)`, `CF-T OF R-X (3:)` (report-name qualified) and the receiving `MOVE "56" TO CF-T(3:2)` all draw the same COBOLNET1639.

**Why "the spec controls" fails (refuter; cite.py --check OK for the decision's 17 citations and the refuter's additions).** `§8.4.3.3.3 SR1` admits only "a numeric data item of usage display or national"; the decision took the counter's usage from `§13.18.60.3 SR7/SR13` (derivation step 4: "GR1 changes digits and sign, never usage"). But `§13.18.54.4 GR1` describes the counter separately ("a conceptual data item that behaves as a data item of the category numeric", digits "derived from"
the PICTURE excluding insertion characters, signed whether or not the PICTURE has a sign) and gives no usage; the spec states usage explicitly when a conceptual item is DISPLAY (`§14.9.1.4 GR6/GR7`: DATE etc. are conceptual items "described as ... usage display"; `§3.102`, `§8.4.3.15.4 GR1` PAGE-COUNTER/LINE-COUNTER likewise state none); SR7 covers the report group ITEM, and `§13.18.54.3 SR2` lets the subject have any category receiving a numeric MOVE while GR1 makes the counter numeric (so the
entry's clauses describe the subject, and GR5 separates the counter from it); informative `§D.20.7`: "A sum counter is an internal location, defined automatically". The SIGN SEPARATE image is not stated by GR1 either. So the counter's representation, and with it whether SR1 admits it, is implementor latitude and needs an entry in `docs/CONFORMANCE.md`.

**Precedence (rule 1).** The decision's GnuCOBOL corroboration is WRONG: GnuCOBOL 3.2.0 accepts `CF-T(1:2)` only because it binds the name to the ENTRY's own storage (`gc_refmod.c`: `memcpy (b_20, b_24 + 0LL, 2)` on `f_26 ... /* col 1 CF-T */`, unsigned 4-digit) and never to the counter (`f_27 ... /* SUM CF-T */`, 6-digit signed DISPLAY); `gcunpr.cob` prints `Z=[0000]` though 1234 was summed; `gcnat.cob`: with USAGE NATIONAL on the entry the counter stays numeric DISPLAY (so a NATIONAL counter has no authority). Hence NO GnuCOBOL observation of a reference-modified sum counter (a missing observation is not a negative).
IBM Enterprise COBOL has no Report Writer; Micro Focus sizes the counter "by the PICTURE clause" in character positions and states no usage. Both lean toward a DISPLAY counter of GR1's digits, which would admit reference modification, give `CF-T(1:2)` = `12` and make LENGTH 4.

The fix belongs in the ONE ref-mod path (`ScreenRefModCount` -> `RefModExclusion` -> `ReadRefMod` -> `RefModView`), applied to the counter place after subscripts, with the view the DISPLAY character image of the counter (`RefModView`'s `NumericImagePlace` arm or its counter equivalent over `ReportSumCounterPlace`), sized per GR1's digit count.

## Landed (wave 1037 G, with PB2520) — a reference-modified sum counter is a counter reference

Re-probed before the fix on a fresh build: `refmod.cob` and `siblings.cob` (all five spellings the adjudication lists) drew COBOLNET1639 "not defined" at 85, 2002 and 2023, and the `control.cob` control resolved (`Z=[1234] Y=[OK]`).
**Determination (implementor latitude, per the adjudication and its refuter): the counter is a signed USAGE DISPLAY numeric item.** `§13.18.54.4 GR1` gives the counter a category, a digit count and a sign and no usage; the standard names a usage where it makes a conceptual item one (`§14.9.1.4 GR7`), so the choice is the implementor's and is recorded in `docs/CONFORMANCE.md` A.4.11 together with its consequences (reference modification admitted by `§8.4.3.3.3 SR1`, LENGTH = digits, DISPLAY shows the signed image, a non-digit stored through a modifier is not retained because the counter has no character cell). Struck from the record, as the adjudication required: "the spec controls", SR7/SR13 as the counter's usage rule, the NATIONAL counter, the GnuCOBOL corroboration.
Mechanism, in the ONE reference-modification path: `ReferenceResolver.SumCounterFor` no longer returns null for a reference-modified counter. After the family lookup and the subscripts it runs `ScreenRefModCount` (SR3), `ReadScreenedRefMod` (SR1, the spec, the literal range screen) and `RefModView` over the counter's `ReportSumCounterPlace`, exactly as the item path does. `PicInfo.SumCounterItem` is `Usage.Display` (it was `Usage.Binary`, which `RefModExclusion` would have refused as "a numeric item of BINARY usage"), `SignKind` trailing overpunch.
Found on the way (fixed, I9): the early image-backing facts (`DataBinder.IsImageBackedEarly`) are keyed by DataItem and are recorded by `MoveBinder.MarkRefModStoreImage` / `MarkFillImageStorage` for every numeric DISPLAY ref-mod receiver. The counter's register item now matches that shape, so after `MOVE "00" TO CF-T (1:2)` every LATER `CF-T (3:)` skipped the `NumericImagePlace` wrap and emitted `CobolString.RefMod(long, …)` (CS1503 at the backend). `Place.OwnsStorageCell` (false for the five views over engine state: sum counter, PAGE-COUNTER, CAPACITY, DEBUG-ITEM, EXCEPTION-OBJECT; decorators forward) now gates all three sites, so no image-backing fact is recorded for a view and the wrap is unconditional for it.
Siblings swept: ADDRESS OF (`ResolveForAddressOf`) and the table(ALL) intrinsic argument (`IntrinsicBinder`) read `FindItem` / `SumCounterFamilyFor` and do not take a modifier on a counter; `MOVE SPACE TO CF-T` (pre-2023) was and is the loud `NotImplemented` residue for any item without image backing; PAGE-COUNTER / LINE-COUNTER reference modification (`PB2521`, a parse error) is a frontend question left open there.
Goldens: positive `85/pb1943_sum_counter_ref_mod` (read, group-qualified, report-name-qualified, receiving, omitted length), `2002/pb1943_sum_counter_table_ref_mod` (a repeating counter's subscript then modifier, a SOURCE clause modifier, FUNCTION LENGTH), negative `pb1943-sum-counter-ref-mod-of-ref-mod` (SR3, all four editions).
