**Rule it breaks:** One mechanism per job and no semantics in a renderer (DESIGN-architecture-review section 5.1); section 8.1 point (1): lowering-shaped computations are bound-tree and model types, and the bound tree is the model every backend reads

**Scenario:** The same identification rules are written twice. Identify once at the start (14.6.4 GR7, 14.7.6): BoundCorresponding carries it as bound structure (CorrespondingHoist with a MethodLocal, BoundCorresponding.cs:17-24, built in CorrespondingBinder.cs), while UNSTRING s bound node carries un-identified places and StringEmitter.IdentifyOperands (StringEmitter.cs:331-351) freezes them into __ident locals at emit time and rebuilds three BoundMoves per receiver (Store, DelimiterStore, ZeroFill Retargeted) because BoundUnstringReceiver holds the place beside the moves that target it. Identify again before each store at COBOL-85 (1985 VI.6.19.4 GR2): MOVE CORRESPONDING does it in the binder as re-run pre-op statements (BoundCorresponding.PairIdentification, BoundCorresponding.cs:59-63, PB5767), while INITIALIZE and the debug triggers do it in the emitter (PlaceIdentification.IdentifyInto and IdentifyAgain, PlaceIdentification.cs:148-178; DebugTriggerEmitter.cs:199-208; InitializeEmitter.cs:31, PB5385). Consequences: every bound-tree reader before codegen (BoundReferences, DebugTriggerPlanner, Validation) sees STRING/UNSTRING/INSPECT operands unfrozen while it sees CORRESPONDING s hoisted; each emitter must remember to call Freeze in source order (13 call sites in StringEmitter alone); a second backend behind ICodeGenBackend must re-implement PlaceIdentification s C#-text hoisting to get the same evaluation order; and a verb newly owing GR7 has two precedents to copy.
