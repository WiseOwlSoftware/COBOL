wave 68 group U (the "Sibling lead — debugging lines" section of `kb/Work/PB1088`).

## Finding

**Repro.** `E:\Temp\claude\E--COBOL\eb162d4b-e0bb-4027-b8a0-86fd190d20be\scratchpad\w68u\p\dline85.cob` at
`--std 85`: a program whose SOURCE-COMPUTER paragraph carries `WITH DEBUGGING MODE` and whose PROCEDURE DIVISION has
indicator-`D` lines. The debugging lines are dropped as comments; under the 1985 debug module they are compiled when
the clause is present. Wrong answer, silent.

**Code site.** `src/Cobol.Net.Frontend/Preprocessor/ReferenceFormatProcessor.LogicalConversion.cs:99` (line as of `dbea12428`) always emits the
comment carrier for a `D` line; it never asks the `DebuggingModeDeclared` question PB1088 fixed on the binder side.
The reference-format pass runs before the SOURCE-COMPUTER paragraph is bound, so the fix has to carry the debug lines
forward (for example as a distinct carrier the binder keeps or drops) rather than decide in the text pass.

**Independent root** from PB1088 (which fixed contained-program inheritance of the clause). Related: PB1494 (the
column-7 indicator dispatch is not dialect-gated; `D` is accepted at 2002+ although §6.2.2 no longer lists it).
`docs/CONFORMANCE.md` has no entry for the 1985 debug facility.

## Task brief (research 2026-09-30)

**Premise check.** Right, re-measured: `dline85.cob` (`SOURCE-COMPUTER. X WITH DEBUGGING MODE.` + a `D` line
`DISPLAY "DEBUG-LINE"`) prints `A` `B` at `--std 85` — the debugging line never runs. One correction to the note's
framing: the carrier it asks for ALREADY exists (`ReferenceFormatProcessor.cs#DebugLineCarrier`, `*>` U+FDD0 `DEBUG `,
matched by COPY REPLACING via `TextWord.cs#IsDebugLineCarrierAt`); what is missing is the stage that turns it back
into source. The analysis is **PB1802 B/C**.

**⚖ OWNER DECISION — how the program's clause reaches the debugging lines** (PB1802 B): (1, recommended) a pre-parse
token rewriter (`DebuggingLineRewriter` beside `ZeroTokenRewriter`) that hides a debugging line's tokens unless the
enclosing (or a containing — PB1088) source element's SOURCE-COMPUTER says WITH DEBUGGING MODE; (2) a parse → re-parse
fixed point (precedents `ReservationGateRewriter.ParseToFixpoint`, the GR14 implicit-op fixed point); (3) GnuCOBOL's
text-pass global flag (`cobc/pplex.l`: `[WITH] DEBUGGING MODE` picked up lexically, `cb_flag_debugging_line = 1` from
then on) — cheapest, not per source element.

**⚠ Evidence first (PB1802 question 1).** GnuCOBOL marks the debug facility OBSOLETE (not removed) at 2002
(`config/cobol2002.conf debugging-mode: obsolete`, `>>D` "2002 (only) floating debug line") and unconformable at 2014,

## Decided 2026-09-30 (owner) — kb/Work R56

## Landed (wave 1003 group D)

Re-probed on the wave-1003 build (base 9b764bdc1): the SOURCE-COMPUTER ... WITH DEBUGGING MODE program with one `D` line
printed `A` `B` at `--std 85`; it now prints `A` / `DEBUG-LINE` / `B`.

**Mechanism (owner decision R56, the pre-parse token rewriter).** The carrier already existed; the missing stage is the one
that turns it back into source. `CobolLexer.g4` lexes `ReferenceFormatProcessor.DebugLineCarrier` as the HIDDEN `DEBUG_LINE`
marker (not a comment skip) and the line's text as ordinary tokens; `src/Cobol.Net.Frontend/Parsing/DebuggingLineRewriter.cs`
runs first in `Frontend.LexAndParse` and keeps those tokens (the source unit, or a unit containing it, declares the mode: ISO
12.3.5.4 GR1, checked) or moves them to the `ABSENT_DEBUG_LINE` channel, which the parser, `SeparatorRule` and
`PictureSeparatorPeriodRule` never read. The unit and the clause are read off the tokens (PROGRAM-ID ... END PROGRAM nesting,
the SOURCE-COMPUTER paragraph's `DEBUGGING MODE`), so a contained program inherits (PB1088's rule, on the token side) and a
sibling does not. `FragmentParse` hides every debugging line (the SUBSCRIPT region the fragment text comes from skips them).
**Edition windows (R61):** row `debugging-mode-removed-2002` became `debugging-mode-removed-2014` (obsolete 2002 with the
COBOLNET0903 warning, removed 2014), so a 2002 program with the clause now compiles and its lines run; the NIST `S` / `Y`
letters moved from the debugging kind to the CCVS excluded kind (they were comments and stay comments, whatever the clause says).
**Goldens:** `85/pb1705_debugging_lines_compiled`, `85/pb1705_debugging_lines_per_unit`, `85/pb1705_debugging_lines_copy_replacing`
(+ `PB1705CP.cpy`), `2002/pb1705_debugging_mode_obsolete_2002`; `negative/debugging-mode` now rejects at 2014 and 2023;
`unit:DebuggingLineRewriterTests`. docs: VCR rows 7.9, 7.17, 7.25; CONFORMANCE.md D-DEBUG (the 1985 debug facility entry).
**Sibling sweep:** the other arms of "the text pass decides" are the comment-entry paragraphs (PB1494/PB1758, landed) and the
NIST S/Y letters (done here); copybook-resident `D` lines go through the same classifier. **Not fixed (lead):** a debugging line
inside an open PICTURE clause or an open subscript / reference-modification region stays a comment (PICMODE and SUBSCRIPT keep
their own comment skip); a `D` line standing between the parts of a continued literal becomes the latest logical line.

**Code sites (for orient).**
- `src/Cobol.Net.Frontend/Parsing/DebuggingLineRewriter.cs#Rewrite` — the ONE place a debugging line becomes source or comment (per source unit, read off the tokens); `#DeclaresMode` reads the SOURCE-COMPUTER clause, so a change to `sourceComputerParagraph` / `debuggingModeClause` is a change there. `#HideAll` is the fragment re-lex reading.
- `src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4#DEBUG_LINE` — the hidden marker (spelling held equal to `ReferenceFormatProcessor.DebugLineCarrier` by `DebuggingLineRewriterTests.TheCarrier_IsExactlyTheLexersMarkerToken`); `ABSENT_DEBUG_LINE` is the channel of a comment line. ⚠ TRAP: any predicate that compares a token to its raw previous token by LINE sees the marker as same-line text (`CobolParserCoreBase.cs#IsAtLineStart` did: DB101A `DDEBUG-LINE-TEST-03-A.`).
- `src/Cobol.Net.Frontend/Preprocessor/ReferenceFormatProcessor.LogicalConversion.cs#FixedFormConverter.ConvertLine` — emits the carrier for a `D` line only; the NIST S / Y letters are `LineKind.CcvsExcluded`.
