# PB4932 - the account recorded now claims batches an unknown account billed

**Sites:** `scripts/api_key.py` (`read_run_key`), `scripts/spec/message_batches.py` (`BatchRun.load_key`)

**Report (R1-1 low).** PB4916 records the NAME of the account a run bills in `state.json` (`api_account`) at the run's first API call, so a batch belongs to its creating
account. The reviewer's lead: for a state file written BEFORE the record existed (batches already present, no `api_account`), `load_key` records the account named NOW into that state, which attributes the
earlier batches (created under some unknown account) to it; a later run naming the other account is then refused as a different account and the run is
stranded (its batches are collectable only through the account that created them). The reviewer read this at `scripts/spec/transcribe_pdf.py:254`; PB4886 moved the
function to `BatchRun.load_key` in `message_batches.py` (the clerk confirmed the move on main). Expected: a state with batches and no `api_account` is refused with a message
naming the state file and asking the owner to name the creating account explicitly through a stated flag (never silently adopting the current one), or
`BatchRun.load_key` can ask the server which account owns each batch id. Repro: plant a `state.json` with a batch id and no `api_account`, run `status` with
`--api-account A`, then with `--api-account B`; observe the second refused after the first recorded A. Not run by the clerk.

Source report and lead: `w20261904a-PB4916-report.md`, R1-1.
