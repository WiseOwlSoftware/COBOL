# PB3118 — a FINDINGS-stamped notes branch is promised a finisher no wave can plan

**Sites:** `scripts/prune_worktrees.py` (`findings_open`, `finisher_due`, `lifecycle`, `self_test`), `.claude/skills/workstream/templates/MANDATORY-PRACTICES.md`, `docs/rearchitecture/DESIGN-orchestrator-loop.md`.

## Found (2026-10-12 23:15 PDT, the loop's resume unit)
`prune_worktrees.py` listed six DECISION rows. Two were notes-only branches whose branch review stamped FINDINGS:

- `notes-PB3084-t1065` (w1065z, PB3084 filed): `Review: FINDINGS 2`, stamped 2026-10-12 02:37Z; the survey's text
  then read "DONE 27 h ago and never landed (over 24 h)".
- `notes-PB3116-manifests` (w1070y, PB3116 filed and PB3112 widened): `Review: FINDINGS 3`, stamped 05:49Z; the
  survey's text: "a finisher answers them, and the next wave plans it (plan_wave.py, kb/Work PB3027)".

`python scripts/orchestrator/plan_wave.py --dry-run --budget-points 100 --no-index-regenerate` planned finishers for the
two code branches with FINDINGS or SPLIT reports (PB2077, PB3030) and printed, for both notes branches,
`UNLANDED branches naming no open note (judgment): fix-PB3117-lane-no-window, notes-PB3084-t1065, notes-PB3116-manifests`.

## Mechanism
- `prune_worktrees.lifecycle` (the FINDINGS arm, `rv.verdict == 'FINDINGS' and rv.covers(row.tip)`) promises a
  wave finisher for EVERY such branch.
- `plan_wave.plan` plans a finisher for a report only through the notes it names that are in `open_ids`, the notes of
  `fix_clusters.py --json`. That population is `.agent-fleet.json`'s: `skip_flag: ["blocked", "process_only"]`. A
  notes branch about the process names only `process_only` notes (PB3084, PB3112, PB3116 are all `process_only: true`),
  and a note the branch FILES is not on main at all, so neither is ever in `open_ids`. Measured: `fix_clusters.py --max 5
  --open-status open --json` contains PB2077, PB3030, PB3109 and PB2842, and none of PB3084, PB3112, PB3116, PB2607.
- With no planned finisher, the branch never leaves DECISION; the enqueue unit never fixes a review finding (kb/Work
  PB3027); and the landing lane lands only `Review CLEAN`. Only a resume unit's DECISION step reaches it, and the
  survey's text tells that unit the wave will do it.

## Harm
A register change (a new defect note, a widened one) stays off main while it waits: `work.py next` and every planner
cannot see the note, and its findings (which correct the note's own measurements) wait with it. notes-PB3084-t1065
waited 28 h after its review (stamped 2026-10-11 19:37 PDT). The resume unit of 2026-10-12 answered both branches' five findings by hand.

## Fix shape (one rule, one place)
The survey must state the path that will run, from the planner's own predicate rather than a second guess: the FINDINGS
arm asks `plan_wave` whether any note the report names is in the fix lane's population (the same `open_ids` rule,
exported once). When none is, the text names the notes path instead: a notes-only finding is answered by whoever
decides the row (the enqueue or resume unit, operator tier, no compiler finisher), the branch is re-reviewed, and the
landing lane lands it. Alternatively `plan_wave` plans a notes finisher (`cobol-clerk` tier) for such a branch; either
way exactly one owner, and a drift test that every DECISION text promising "the next wave plans it" names a branch the
planner's dry run actually plans.

## Landed (2026-10-25, fix-lane wave 20261107 group C)

**Re-probe.** The planner half of the note is PB3150's, already landed: `plan` takes the lead of a FINDINGS report the fix
lane cannot see (`process_only`, or filed only on its branch) and plans its finisher; a fixture with no cluster holding the
lead plans it (normal and drain). What still differed was the survey's text: a covered FINDINGS stamp on a report over
`--stale-hours` read "DONE 27 h ago and never landed (over 24 h): land it or record why not" (the stale arm precedes the
FINDINGS arm), so the row sent the reader to land a branch whose findings nobody answered, and the landing refuses it.

**Fix.** `prune_worktrees.findings_open(row)` is the one statement of a covered FINDINGS stamp on a finished, unlanded
report; `finisher_due` and `lifecycle`'s stale arm both read it, so an old report with findings reads the finisher
DECISION text (with its age: the finisher is overdue, the landing is not). MANDATORY-PRACTICES O10 says so.

**The drift test** (`prune_worktrees.py --self-test`): `findings-stamped` is now 30 h old and must read "the next wave
plans it", not "never landed"; and the planner, given the same survey rows with NO cluster holding the lead, plans exactly
that finisher: every DECISION row that promises the next wave plans a finisher is checked against the planner on a real
git history. Mutation: restoring the old stale arm turns it red.
