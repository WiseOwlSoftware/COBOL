# PB1713 — refute the handoff's "next step" before the wave inherits it

## Origin

A LinkedIn commenter (2026-09-28) noted that verdicts get refuters and landed work gets the lander, but the handoff
note's "next step" line is reviewed by nobody. The owner replied publicly that "we'll run it next chance we get".

## What is and is not covered today

- **Designs** get an adversarial review before implementation. On 2026-09-28 PB1708's selection design was rejected
  twice before any code was written.
- **The work list** is computed (`work.py next`, `fix_clusters.py`), not written.
- **The handoff note** (STATUS.md) is stamped (`STATUS-AT: <sha>`, PB1698), so a STALE note is caught. Nothing checks
  that its next step is CORRECT. Inherited spec citations are re-validated (CLAUDE.md rule 1), which covers only part
  of it.

## Experiment

This is an A/B in the shape of the PB1698 stamp scale test.
- **Arm B** adds a read-only refuter pass (`cobol-refuter`) on each STATUS.md next step before it is handed on.
- **Arm A** hands on as today.
- **Metric:** the fraction of successor agents whose first 60 minutes (or first N turns) go toward a next step that
  later proved wrong. The token cost of the refuter is counted against it.

Record the setup, raw JSON and results under `docs/rearchitecture/evidence/fleet-optimization/` (the owner's standing
instruction). Encode it into the public skills only if the result is VETTED.
