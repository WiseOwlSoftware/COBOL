## Finding — compile-time-arithmetic-expressions (silent)

The required §7.3.6.3 GR2 / §7.3.6.2 SR2 implementor documentation (docs/CONFORMANCE.md 'Compile-time arithmetic mode') does not describe the implemented mode: it calls System.Decimal a 'standard' mode chosen for portability, states that division truncates when System.Decimal division rounds its last digit, names a deleted evaluator (EvalConstExpr) and claims a directive-operand GAP that has been closed; and the evaluator reports the SR2 magnitude limit on an over-range expression operand as an SR1b violation.

**Rows:** GR-7.3.6.3-2, SR-7.3.6.2-2

**Repro:**

```
01 C7 CONSTANT AS 2 / 3 * 3.  01 C11 CONSTANT AS 100 / 7 * 7.  DISPLAY C7 C11 -> 2 and 100 (documented truncating division predicts 1 and 99). >>DEFINE V3 AS 2 / 3 * 3 / >>IF V3 = 2 selects. 01 K CONSTANT AS 1234567890123456789012345678901 + 0. -> COBOLNET1547 citing SR1b.
```

**Expected from the spec:** §7.3.6.3 GR2: 'The implementor shall define and document which mode of arithmetic is to be used'; §7.3.6.2 SR2: '... shall also document which intermediate rounding method is used' (both --check OK). The documented mode and rounding must be the implemented ones; the 'standard modes' of the GR2 NOTE are standard-binary/standard-decimal (§8.8.1.5.3, ISO/IEC 60559 decimal128), so System.Decimal must be documented as an implementor-unique mode. Either the doc states round-half-even division, or the evaluator implements the documented truncation -- an owner/implementor choice, but the two must agree; an over-range operand should be diagnosed as the documented SR2 limit.

**Observed:** Probe p1.cob/p2.cob outputs above; CONFORMANCE.md lines ~504-516 in the pinned tree; grep finds no EvalConstExpr symbol (only a comment in CompileTimeExpressionEvaluator.cs:97); ParseLiteral's TryParse failure message cites SR1b.

**Code site:** docs/CONFORMANCE.md (Compile-time arithmetic mode bullet); src/Cobol.Net.Frontend/Expressions/CompileTimeExpressionEvaluator.cs EvalArith ('/' case) and ParseLiteral
