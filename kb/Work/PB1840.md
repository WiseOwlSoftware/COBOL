# PB1840 — LANDED 2026-10-18 (campaign PB3353, wave 1126 group F)

**Determination.** §14.9.51.4 GR25 e)/f) (cite.py --check OK): a BEFORE write presents its line before the advance, an
AFTER write after its own, so a line presented while an earlier write's line is open has no advance between it and
that line: it is at the SAME vertical position, GR25 c)'s zero advance by another route. The position is stated by the
standard, so ISO controls (rule 1) and GnuCOBOL's append (`AB`) is not followed. Represented as ADVANCING 0 is (R54):
a bare carriage return. Documented in docs/CONFORMANCE.md "A line presented onto an open line is the same overprint".

**Fix.** `SequentialConnector.Present` (the one presentation, shared by every WRITE arm and the report writer) writes
the return before a non-empty record when the device is on an open line it has not already returned over. The two
booleans of the old design collapse into one three-state field `DeviceLine { Fresh, Open, Returned }` so "open" and
"returned" cannot disagree; `WriteTravel(0)` moves Open to Returned, so AFTER 0 / BEFORE 0 still write exactly their one
return. The BEFORE amount is irrelevant (a count, 0, PAGE, LINAGE or not), because the return belongs to the
presentation, not to the amount: the PB1027 addendum's `BEFORE ADVANCING PAGE` shape is covered by construction.

**Re-probe (w1126f, own build):** AFTER 1 / BEFORE 1 gave `\nAAAABBBB\n`, AFTER 1 / BEFORE PAGE gave `\nAAAABBBB\f`,
AFTER 1 / BEFORE 0 gave `\nAAAABBBB\r`; after the fix `\nAAAA\rBBBB\n`, `\nAAAA\rBBBB\f`, `\nAAAA\rBBBB\r`.

**Pinned by** `conformance-suite/cases/14.9.51-WRITE/pb1840_before_after_open_line` (all four editions),
`OpenLineOverprintTests` (19 cases; the refused-WRITE paths '44', '71' and the LINAGE violation, each with and without a
USE declarative where the status runs one), and the two existing tests whose expectation encoded the append
(`LinageConformanceTests` LNGBYF, `FileIoDifferentialTests.WriteAdvancingMnemonic_ZeroLineAdvance_RecordAlwaysReleased`).
The whole NIST corpus and the conformance suite (10831 cases) were run on the branch: no other golden changed.

## Landing
- `src/Cobol.Net.Runtime/IO/SequentialConnector.cs#Present` (SequentialConnector.Present) - the ONE presentation of a print line; it writes the overprint return when the device is `DeviceLine.Open`. REUSE it for any new arm that presents a record; never write a record to `_writer` another way. Trap: `WriteTravel(0)` writes the same return and moves the state to `Returned`, so the two must not both test a boolean (the old `_lineOpen` made a BEFORE 0 followed by a BEFORE write double the return).
- `src/Cobol.Net.Runtime/IO/SequentialConnector.cs#WriteTravel` (SequentialConnector.WriteTravel) - the zero advance; `AdvanceLines`, a form feed and `EmitRecordLine` reset the state to `Fresh`.
- Test trap: in a test source the record is moved BEFORE any statement that edits it (`OpenLineOverprintTests.W` runs `pre` after the MOVE), and a lone `\r` in an expected string next to `\r\n` is a return followed by a line end.

Found by the PB1667 implementer (DEVLOG 1816). `WRITE A AFTER ADVANCING 1` leaves A's line open; `WRITE B BEFORE ADVANCING 1` then presents B on that same line. `SequentialConnector.Present` appends, so the bytes are `AB`, which is also what GnuCOBOL writes; `LinageConformanceTests` LNGBYF pins it. Read against §14.9.51.4 GR25 c)/e) (a zero advance is an overprint, which R54 now writes as a carriage return) the standard puts B at the same vertical position, i.e. overprinted from column 1 (`A` CR `B`). The owner decision R54 covers ADVANCING 0 only. To decide: whether a presentation onto an open line returns the carriage first (one rule, then AFTER 0 would not need its own return), and what that does to NIST print goldens and to the GnuCOBOL survey. Code site: `SequentialConnector.Present` / `WriteAdvancingRecord`.
