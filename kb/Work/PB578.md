# PB578

## Mechanism
LINAGE-COUNTER's implicit-increment sentence is modelled nowhere and the argument that it is unobservable has a hole: a USE AFTER STANDARD ERROR declarative can read LINAGE-COUNTER mid-statement

### Inventory row `GR-13.18.34.4-L2.1` (PARTIAL)
THE RESET IS IMPLEMENTED AND TESTED; THE IMPLICIT-INCREMENT SENTENCE HAS NO IMPLEMENTATION AND ITS UNOBSERVABILITY IS A DERIVATION WITH A HOLE. Sentence 1 ('automatically reset to one') is the `lines < 0` arm and the named test pins it. Sentence 2 ('during the resetting ... the value of LINAGE-COUNTER is implicitly incremented to exceed the value specified by integer-1') is modelled nowhere: the arm sets EndOfPage = false and returns. The argument that this costs nothing runs: (a) the only consumer of 'exceeds the page size' is 14.9.51 GR26a's page-overflow condition; (b) its observable effects are the reposition-and-reset (already done) and GR6b3's re-evaluation, which GR6b2 already performs on this same arm (:163); (c) its END-OF-PAGE flag cannot be seen, because 14.9.51.3 SR18 forbids ADVANCING PAGE and END-OF-PAGE in one statement and the compiler enforces it (conformance-test:CobolNet.Tests.Conformance.LinageConformanceTests.Sr18_AdvancingPageWithEop_IsRejected). THE HOLE: step (c) assumes no user code observes LINAGE-COUNTER mid-statement, and a USE AFTER STANDARD ERROR declarative entered from inside this WRITE could. That path is currently unreachable only because of a separate defect (p18_use.cob: the declarative never fires), so the derivation rests on a bug rather than on the language. PARTIAL under 'an unverified edge => PARTIAL'; it is a candidate for the PB386 no-observable-obligation close once the EC path exists.
