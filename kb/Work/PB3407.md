# PB3407 — an unlistable wave scratch drops its findings files without a word

Filed by the operator from PB3381's branch review (R7-2, low, not blocking at round 7; `w1125a-PB3381-report.md`). The
reviewer found it unchanged since round 5, so it predates the round-6 rewrite.

**The mechanism (`scripts/orchestrator/review_findings.py`, on main at 49e1c6b79).** `findings_files` builds its
candidates with `scratch.glob(FINDINGS_NAME)` and `scratch.glob(f"*/{FINDINGS_NAME}")`. `pathlib`'s glob skips a
directory whose listing raises `OSError`. The docstring promises that nothing the reader would hold is dropped ("Nothing
is opened, read or parsed to decide what is one"). That holds for files, which `last_verdict` reads as TORN when it cannot
open them, but not for directories.

**The failure.** The reviewer's repro (`r7/probe7.py` case 6): after `icacls <scratch>/w9 /deny USER:(RD)`,
`findings_files` returns `[]` and `unanswered` returns `[]`, while the file read directly is round 2 FINDINGS. Every hold
that file carries is released without a line saying so. It needs a directory the operator account cannot list, hence low.

**The fix.** Walk the two levels with `os.scandir`, and read a directory that raises `OSError` as a TORN reading of its
own (no branches, a remedy naming the directory) that the survey reports. Alternatively, fail the survey loudly. The
self-test should plant an unlistable wave directory and assert that the survey reports it.
