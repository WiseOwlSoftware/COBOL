# PB771 — the §9.1.15 file lock is SEQUENTIAL-ONLY

Found by the registrar during landing train 18, measured on `main` and on [[PB740]]'s branch, and filed as the
reason [[PB740]]'s three rows are recorded **PARTIAL rather than CONFORMS**.

## The rule

ISO §9.1.15 3): *"The successful opening of a file establishes a file lock for the applicable sharing rules,
thereby preventing other run units from opening that file with incompatible sharing rules."* The clause is
written over *a file* — it is not qualified by organization, and §9.1.15's three sharing modes (`NO OTHER`,
`READ ONLY`, `ALL OTHER`) are declared on the SELECT of any organization.

§9.1.15 addresses two audiences with the one sharing mode: INSIDE the run unit the gate is §14.9.27.4's
Table 19, and OUTSIDE it the gate is the file lock. [[PB740]] landed the second half — `FileLockPosture` derives
the host share mode from the arbitrated sharing mode and the set of connectors Table 19 admitted, and
`FileRegistry.SyncHostPostures` keeps it current. **But only a connector that HOLDS a long-lived host handle can
carry a file lock, and only the sequential organization does.**

## The mechanism

- `RelativeConnector` and `IndexedConnector` hold no host handle at all. They reach the physical file only
  through `RecordFraming.ReadStore` / `WriteStore`, each of which opens, does its work and closes.
- Those handles are taken through `HostFile.OpenAuxiliary` (`src/Cobol.Net.Runtime/IO/FileSupport.cs`), which is
  **fixed at `FileShare.ReadWrite`** and takes no share argument — by design, because an auxiliary handle has to
  admit the access every outstanding handle already holds or the host refuses it. It therefore names no sharing
  mode, and no §9.1.15 rule can reach it.
- The CLOSE-side `WriteStore` is `FileMode.Create`: the whole store is rewritten from this run unit's in-memory
  copy. So a second run unit that opened the same physical file between this run unit's OPEN and its CLOSE has
  its records **silently discarded**, and both sides report '00'.

So a program writing `SHARING WITH NO OTHER` over an INDEXED file is not protected from another run unit, and a
program writing `SHARING WITH ALL OTHER` over one does not interleave with another run unit — it overwrites it.
The in-run-unit half is correct for every organization (Table 19 arbitrates every OPEN, [[PB321]]); it is the
other-run-unit half that is missing.

## Why the rows are PARTIAL

[[PB740]]'s evidence for `GR-9.1.15-1/-2/-3` — `pb740_clauseless_share` at 2002 and 2023,
`FileLockPostureDriftTests`, `OpenTable19Tests` — is **sequential-only**. Recording CONFORMS on it would be a
verdict with a known hole, and a green corpus that never opens a keyed file across two run units would hold that
hole open (`feedback_green_test_can_hold_a_gap_open`). PARTIAL is the honest verdict: what is implemented is
implemented correctly and pinned; the keyed half is this note's.

## What a fix has to decide

The store model is the root, not the derivation: a keyed connector's protection would have to come from a
long-lived handle it does not currently take, or from an explicit lock file. That is a design question for
`DESIGN-runtime-library.md`'s store section and it interacts with owner question 20 ([[PB740]] — whether a
CLAUSE-LESS connector should protect its physical file from other PROCESSES at all), so the two should be
answered together. **Ships with:** a cross-process golden or Unit test per keyed organization, the mirror of
`FileLockPostureDriftTests`' sequential cross-process arm, plus the re-verdict of the three rows to CONFORMS.
