# PB771 — OPEN — two of the four organizations never take a file lock, in any sharing mode

Found 2026-09-06 by the [[PB740]] finisher (report, "New defects (b)", which says *"Worth its own note"*).
Verified against main (`9fad13e5`) and against PB740's branch (`397595e5`, landing train 18) by reading both
trees. ⛔ **Reachability is argued from the code, not measured** — see the reproduction status.

## ⛔ Reproduction status — read this before designing the fix

- **Nothing was compiled or run for this note.** It is a reading of both trees. `feedback_reachability_is_measured_not_deduced`
  says a reachability claim is a probe to run; the probe is named below and is owed before the fix is designed.
- **The probe.** Two COBOL programs (or one program and one shell writer) over the SAME `ASSIGN`ed path,
  `ORGANIZATION IS INDEXED` (and again `RELATIVE`), the first with `SHARING WITH NO OTHER`: run unit A OPENs
  I-O and holds it; run unit B OPENs the same file, WRITEs a record, CLOSEs; A then READs, WRITEs one record of
  its own and CLOSEs; read the physical file. §9.1.15 1) requires B's OPEN to be **unsuccessful**. The two
  predictions to record are (i) B's OPEN status and (ii) whether B's record survives A's CLOSE.
- The sequential organization's twin of this measurement WAS taken — PB740's report records
  *"`SHARING WITH NO OTHER`, external process appends mid-open → SUCCEEDED, file ends `SEEDXXXX`"* before its fix
  and REFUSED after — so the shape of the experiment is established; only the keyed arm is unrun.

## The mechanism on main (`9fad13e5`)

1. `src/Cobol.Net.Runtime/IO/FileSupport.cs:264-266` —
   `public static FileStream OpenAuxiliary(string hostPath, FileMode mode, FileAccess access) =>
   new(hostPath, mode, access, FileShare.ReadWrite, 4096, FileOptions.SequentialScan);`
   No share parameter: the role IS the posture, and the role is *"a SHORT-LIVED stream the runtime opens for its
   own bookkeeping"* (`:255-263`). It is `ReadWrite` for a good and cited reason — [[PB713]]: the path may already
   be held by a connector of this run unit and a narrower request would manufacture an I/O failure the COBOL
   statement never asked for.
2. **`RelativeConnector` and `IndexedConnector` reach the physical file ONLY through that role.**
   `RelativeConnector.cs:119/127/139` and `:478` call `RecordFraming.WriteStore(HostPath, …)`; `:467` calls
   `RecordFraming.ReadStore(HostPath)`. `IndexedConnector.cs:202/211/224/264/785` do the same.
   `RecordFraming.cs:51` and `:76` are both `using var fs = HostFile.OpenAuxiliary(...)` — opened, used, closed.
3. **Neither class holds a stream at all.** `RelativeConnector`'s fields are a `RelativeStore _st` and scalars
   (`:17-35`); `IndexedConnector`'s are its record map; `KeyedConnector` declares no `Stream`. So **between a
   successful OPEN and its CLOSE there is no host handle in existence for these two organizations**, and a host
   handle is the only thing that can say anything to another process.
4. **The arbitration that DOES exist is in-process only.** `FileRegistry` is the Table-19 arbiter and is reached
   through a static registry ([[PB603]] records `CobolFile._reg` as static and its run-unit consequences). It
   answers §9.1.15's first audience — the file connectors of this run unit — and cannot answer the second.
5. **By contrast the sequential organization does hold one**: `SequentialConnector.cs:359/365/398/420` open through
   `HostFile.OpenConnectorStream` / `OpenAppendStream` and keep `_reader`/`_writer` for the life of the OPEN.
   Whether its POSTURE is right is a different defect and is [[PB740]]'s (on main the posture is the
   `SharedStreams` boolean at `FileConnector.cs:168`, which is inverted for `SHARING WITH NO OTHER`); what
   matters here is that the sequential organization has a handle to be right or wrong about and the keyed ones
   have none.

## The wrong answer is bigger than "unprotected", and this is why the note is MAJOR

An absent lock alone would be a missing refusal — an under-rejection. But the keyed store model turns it into a
**silent data loss in both directions**, because the store is a snapshot:

- `ReadStore` at OPEN takes the whole physical file into memory. Every subsequent READ answers from that
  snapshot, so records another run unit writes after our OPEN are invisible to us — a READ that reports `'00'`
  and delivers superseded content, which is [[PB753]]'s harm shape arriving by a different route.
- `WriteStore` at CLOSE opens `FileMode.Create` and rewrites the file from our snapshot plus our own changes
  (`RelativeConnector.cs:478`, `IndexedConnector.cs:264`). **Everything the other run unit wrote is truncated
  away**, and both run units report `'00'` at every step.

Which is why `wrong_answer: true` and `silent: true` and not merely `under_rejects`. ⚠ Both halves follow from
reading the store model and neither is measured; the probe above measures the second one directly.

## The fix shape

The rule to write down once is **"a successful OPEN holds, for the life of that OPEN, a host handle whose share
posture is the file lock §9.1.15 3) requires"** — today it is a property of one organization's implementation
detail. Two admissible structures:

1. ⭐ **The keyed connectors take and hold their own handle.** `OpenCore` opens the physical file once with the
   derived posture, reads the store THROUGH that handle, keeps it for the life of the OPEN, writes the store back
   through it at CLOSE, and releases it there. It reuses PB740's derivation unchanged (`FileLockPosture.For`),
   makes `Reposture` meaningful for these organizations instead of a no-op base call, and removes the two
   `OpenAuxiliary` round trips. ⚠ It must not re-open [[PB713]]: the handle has to be the SAME one the store is
   read and written through, or the second open collides with the first.
2. **The registry holds it on their behalf** — one host handle per physical path in
   `Sharing/PhysicalFileTable`, taken on the first successful OPEN of that path and released with the last CLOSE,
   postured by `FileLockPosture.For`. This puts the lock exactly where the sharing state already lives, covers a
   fifth organization for free, and keeps the connectors' store model untouched. ⚠ It has to interact correctly
   with the sequential organization's OWN handle on the same path (the run unit's effective lock is the
   INTERSECTION of its handles' postures — PB740's design says so), which is the argument for doing 2 for the
   keyed organizations only, or for doing it for all four and deleting the per-connector posture.
   ⛔ Choosing between 1 and 2 is a design decision that belongs in `DESIGN-runtime-library.md` in the same
   change set (CLAUDE.md rule 2 and rule 5).

Whichever shape: **the drift test is the deliverable that keeps it true** — no organization under
`src/Cobol.Net.Runtime/IO` may complete an OPEN without a live host handle carrying its derived posture, measured
through the connectors rather than asserted about them, in the manner of `FileLockPostureDriftTests`. Pair it with
the cross-process probe as a golden for at least `SHARING WITH NO OTHER` × {INDEXED, RELATIVE}, and keep PB740's
sequential legs green as the control.
