# PB3539 — §12.4.6.4.4 GR3 for SAME RECORD AREA under APPLY COMMIT

## Lead and correction

The lead: two files of one SAME RECORD AREA, both under APPLY COMMIT, compile and run (`DataBinder.IoControl.cs`, the SR11
loop, about line 70). Repro as filed: `git show 67069487d:conformance-suite/cases/12.4.6.4-SAME/apply-commit-same-area-shared.cob`
with ORGANIZATION RELATIVE.

Correction after adjudication: that repro opens neither file, so it witnesses no violation of GR3 (the rule is about
execution). The note's `under_rejects` is therefore now false: there is no demonstrated acceptance of an illegal program.

## The rule (each quote re-run through `cite.py --check`, OK)

§12.4.6.4.4 GR3: "The file and record area of a file subject to commit and rollback may not be shared with another such
file or record area unless it has been closed, a commit or a rollback has been executed and the APPLY COMMIT clause for
the file has been deactivated."

- The three exceptions are joined by AND: closed, a commit or rollback executed, AND the clause deactivated. A clause is
  deactivated only in canceled runtime elements and exited initial programs: §12.4.6.3.4 GR5 ("An APPLY COMMIT clause is
  active when the runtime element in which it is contained has been activated and, in the case of canceled runtime
  elements and exited initial programs, has not been deactivated by a COMMIT or ROLLBACK statement."), the COMMIT statement
  (§14.9.7.4 GR3: "The COMMIT statement also deactivates any APPLY COMMIT clauses in exited initial programs and canceled
  runtime elements.") and the ROLLBACK statement (§14.9.36.4 GR6: "Any APPLY COMMIT clauses in exited initial programs or
  canceled runtime elements are deactivated."). So opening two such files one after the other within one activation is NOT
  legal sharing.
- GR3 is a general rule and carries no exception condition. §4.2.2 (OK): "There are general rules in standard COBOL that
  could have been classified as syntax rules. These rules are classified as general rules for the purpose of avoiding
  syntax checking, and do not reflect errors in standard COBOL. An implementation may, but is not required to, flag
  violations of such rules." and "An implementation shall accept the syntax and provide the functionality for all standard
  language elements". §4.4 item 2 (OK): "The results of violating the formats or rules of standard COBOL are undefined
  unless otherwise specified".

## Options (the earlier Option A, a compile-time refusal, is ruled out)

A compile-time refusal is ruled out: §4.2.2 requires the implementation to accept the syntax, and a refusal would reject
source the standard defines as accepted.

Remaining options, for the owner:
- (i) Leave a violation undefined and document it in `docs/CONFORMANCE.md`. Cost: none in code. Only the file states are
  rolled back (§14.9.36.4 GR3 restores "all files and data-items referenced in active APPLY COMMIT clauses"), so a violation
  behaves like an ordinary SAME RECORD AREA.
- (ii) A run-time check at OPEN with an implementor-defined condition (an EC-IMP- name or a 9x status). Cost: per-group,
  per-activation state, plus the canceled-but-not-yet-committed instances.
- (iii) A compile-time warning (§4.2.2 allows flagging). Cost: it fires on programs that never violate GR3 at run time.

Precedence (CLAUDE.md rule 1): the ISO standard leaves it undefined; GnuCOBOL has no APPLY COMMIT (cobc 3.2 rejects the
clause); IBM Enterprise COBOL has no such clause. Adjudicator's recommendation: (i).

## Owner decision (2026-10-23)

Option (i), "Document as undefined" (AskUserQuestion, attended Mythos session). The standard leaves a violation of §12.4.6.4.4 GR3
undefined, the compiler neither refuses nor checks it, and ROLLBACK restores only what §14.9.36.4 GR3 names (`cite.py --check
14.9.36.4` → OK 3)): *"All files and data-items referenced in active APPLY COMMIT clauses are restored to the state they were in at
the execution of the last COMMIT statement"*. A violation therefore behaves like an ordinary SAME RECORD AREA.

Mechanism (the Mythos decision): the row closes through `docs/CONFORMANCE.md` §8 on the `definitional` arm, as the owner extended it
on 2026-10-08 (kb/Work PB1636) to a constraint on the user's run unit that no rule gives a consequence. GR3 constrains the user's
program (`cite.py --check 12.4.6.4.4` → OK 3)), gives no consequence, and §4.4 2) (`--check 4.4` → OK 2)) makes a run unit that
violates it a conforming one with undefined execution. Today's option (i) is the signature, `owner: 2026-10-23`, added to
`derivation.signatures` in `tests/version-matrix/inventory-schema.json`. The §8 row is `DRV-GR-12.4.6.4.4-3`; the inventory row
`GR-12.4.6.4.4-3` went from NEEDS-OWNER-DECISION to CONFORMS through `record_verdicts.py`, and `audit_derivations.py` reports no
findings.
