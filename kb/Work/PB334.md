# PB334 — READ PREVIOUS on a sequential file is a forward read at every edition

**Rows:** `GR-14.9.30.4-19`, `SR-14.9.30.3-7`, `SR-14.9.30.3-10` (as landed — `GR-14.9.30.4-21` and
`GR-14.9.30.4-L4.3` moved to [[PB336]] and [[PB343]], which own what remains of them). Reported by
read-statement p1, p2 and p4 as three mechanisms; it is one dropped field.

## The programs

**a) WRONG ANSWER.** `out-b1/probe/seqprev/SEQPREV.cob` — `ORGANIZATION IS SEQUENTIAL`, records AAAA/BBBB/CCCC;
`OPEN INPUT`; `READ F NEXT RECORD` (AAAA); `READ F NEXT RECORD` (BBBB); `READ F PREVIOUS RECORD`. Observed
`P1 00 CCCC` — record 3, i.e. the NEXT record. `out-b1/probe/prevseq/prevseq.cob` shows the other end of the
same defect: two successive `READ SQF PREVIOUS RECORD` on a three-record file give `READ1=AAA` / `READ2=BBB`
where the second must be the at-end condition.

**b) MISSED EDITION GATE.** The same program at `--std 85` compiles with **no diagnostic at all**, although
READ PREVIOUS is registered as a 2002 introduction (`ConstructRegistry` `read-previous-2002` → COBOLNET0900) and
the KEYED arm rejects it correctly.

**c) SILENT PHRASE DROP.** `READ SQF RECORD KEY IS WS-K` on an `ORGANIZATION SEQUENTIAL` file compiles and runs
(`GOT=AAA`); the RELATIVE twin correctly draws COBOLNET0864 for SR10 (`out-b1/probe/sr10/seqkey.cob` vs
`relkey.cob`).

**d) SILENT BRANCH DROP.** `READ SQF NEXT RECORD INVALID KEY DISPLAY "IK" NOT INVALID KEY DISPLAY "NIK " SQ-REC
END-READ` on a sequential file compiles; the read SUCCEEDS and NEITHER branch runs
(`out-b1/probe/lockcombo/seq7c.cob`).

## The rules

> §14.9.30.4 GR21, *When the file is a sequential file*, rule c): If the file position indicator was established
> by a prior successful READ statement, the first existing record in the physical file whose relative key number
> is greater than the file position indicator if NEXT is specified or implied or is less than the file position
> indicator if PREVIOUS is specified is selected.

`--check 14.9.30.4 "is less than the file position indicator if PREVIOUS is specified"` → **OK**. Rule b) governs
the after-OPEN case — *the first existing record that is selected is made available, regardless of whether NEXT
or PREVIOUS is specified* (`--check 14.9.30.4` → **OK**) — so `prevseq.cob`'s first PREVIOUS correctly gives
AAA and its second must be the at-end condition, '10'. §9.1.7.2 states the same at file level. GR19 makes an
explicit PREVIOUS a sequential read; §14.9.30.3 SR7 bars PREVIOUS only for LINE SEQUENTIAL, so it is legal on a
record-sequential file, and GR20's single-reel/unit mass-storage precondition is satisfied by every disk file
here. For (c), SR10 permits the KEY phrase only under ORGANIZATION IS INDEXED. For (d), Format 1 has no INVALID
KEY phrase at all, so the statement is illegal source; if it is accepted, GR13 c) requires control to reach
imperative-statement-4.

## What the compiler does

`SequentialIoBinder.BindRead` builds `new BoundRead(file, into, atEnd, notAtEnd, UnsupportedOrg(...)) { Lock =
..., Retry = ..., AdvancingOnLock = ... }`. Of the NINE sub-rules `readStatement` can produce it consumes five —
`readInto`, `readAtEnd`, `retryPhrase`, `recordLockPhrase`, `readAdvancingOnLock` — and **`readDirection`,
`readKey` and `readInvalidKey` are never referenced**; `BoundRead` has no member to hold them.
`SequentialConnector.Read` is a strictly forward reader (FillChars / ReadPhysicalLine over a StreamReader).

The KEYED arm reads all three, which is why the SR10 diagnostic LOOKS present when tested on a relative file.
The edition gate inherits the same split: `VersionConformancePass.GateStatement`'s `case BoundKeyedRead kr`
tests `kr.Kind == KeyedReadKind.Previous`, while its sibling `case BoundRead sr` tests only `sr.AdvancingOnLock`
— and that arm's own comment (*this arm is the phrase's first sequential-leg gate*) shows it was visited when
ADVANCING ON LOCK was swept on, and the PREVIOUS half was not carried across. The two-arm dispatch shape, with
the second arm visited and still left incomplete.

**Blast radius.** §14.9.30.3 SR7 has no enforcement anywhere either, so a LINE SEQUENTIAL `READ PREVIOUS` is
likewise accepted and silently read forward — SR7 has no attachment point until the direction exists.

**Code sites:** `SequentialIoBinder.cs#BindRead` (lines 146-164) · `BoundTree.cs#BoundRead` ·
`SequentialConnector.cs#Read` · `VersionConformancePass.cs` (`case BoundRead sr`, line 258).

## The fix shape

Structural, not a flag. `BoundRead` gains the direction; `SequentialConnector` gains a backward walk over the
record ordinals (rules b/c/f of the sequential-file paragraph — it already maintains `_readOrdinal` for the
§9.1.16 lock identity and `_lastReadBlockStart`/`_lineByteOffset` for REWRITE); the edition gate then keys on a
DIRECTION field shared by both READ bound nodes rather than on `BoundKeyedRead` alone; and SR7 and SR10 finally
have something to attach to on this arm. A per-statement patch would leave the third arm missing again. **PB340**
proposes the drift test that covers this whole family: every phrase property on a bound I-O node is consumed by
its emitter.

## Row inherited from PB335 (2026-09-05)

`GR-14.9.30.4-19` — *"An implicit or explicit NEXT phrase or a PREVIOUS phrase results in a sequential read:
otherwise, the read is a random read and the rules for format 2 apply"* — moved here when PB335 landed. The row
recorded TWO independent divergences and PB335 owned only the first: SR9's implied-NEXT test read two of its
three members, so `READ f ADVANCING ON LOCK` on an ACCESS DYNAMIC file bound Format 2. That is fixed (landed with
PB340; `SR-14.9.30.3-9` is CONFORMS).

What is left is divergence (2), which is this note's item (a): `SequentialIoBinder.BindRead` never calls
`r.readDirection()` and `BoundRead` carries no direction member, so on a RECORD or LINE SEQUENTIAL file PREVIOUS
is dropped and GR19 routes a backward read as a forward one. The row closes when this note's structural fix
lands — a direction on both READ bound nodes and a backward walk on `SequentialConnector`.

## Row inherited from PB331 (2026-09-05)

`SR-14.9.30.3-10` — *"The KEY phrase may be specified only if ORGANIZATION IS INDEXED is specified in the file
control entry for file-name-1"* — moved here when PB331 landed. PB331 owned it only for a reason that is now
gone: the KEY phrase could not be written after a lock phrase at all, because the grammar had `readKey?` before
the lock slots, against the printed order of §14.9.30.2. That is fixed, and `2002/pb331_read_lock_brackets`
writes the phrase in all three printed spellings on an INDEXED file.

What is left is exactly this note's mechanism, item (c): `SequentialIoBinder.BindRead` never calls
`r.readKey()`, so on a SEQUENTIAL or LINE SEQUENTIAL file the phrase is parsed and dropped with no diagnostic,
while the relative/indexed arm correctly raises COBOLNET0864. PB331 kept the tree carrying it — the accessor to
read is `ReadStatementContext.readKey()`, whose `dataReference()` is what `KeyedIoBinder.BindRead` already
resolves; the sibling phrases this note also owns are `readDirection()` (NEXT/PREVIOUS) and
`readInvalidKey()`.

## Landed 2026-09-05

**One mechanism, and it was structural.** `readStatement` produces nine sub-rules and this arm consumed five;
the three it never referenced had nowhere to land, because `BoundRead` had no member for any of them. The fix is
the members and the ONE place each rule belongs, not a per-phrase patch:

- **The direction.** `KeyedReadKind` became **`ReadKind`** (§14.9.30.4 GR19's read kind — the direction phrase
  and the format are one fact, which is what GR19 says), it is on **both** READ bound nodes, and both are reached
  through the new **`IBoundRead`**. `VersionConformancePass.GateStatement` now has ONE arm over that interface
  instead of the two it had — so `READ … PREVIOUS` raises COBOLNET0900 at `--std 85` on every organization, and a
  rule written on the read's direction can no longer be written for one organization only.
- **The backward walk.** `SequentialConnector.Read(previous, out image)` implements GR21's "When the file is a
  sequential file" block directly. `TargetReadOrdinal(previous)` is rule b (the indicator established by OPEN
  targets ordinal 1 "regardless of whether NEXT or PREVIOUS is specified") and rule c (one greater / one less)
  in one expression, and it is ALSO the GR9 pre-read conflict target the sharing registry checks — so GR22's
  ADVANCING ON LOCK skip-scan ends at the beginning of file when PREVIOUS is specified. `SeekToOrdinal` is a
  REPOSITION feeding the ordinary read body (arithmetic on a fixed-width file; `RecordFraming.FrameStarts`,
  built lazily on the first backward read, on a RECORD VARYING one), which is what keeps the '04'/'06' length
  rules and the §14.9.35.4 GR5 in-place REWRITE anchor correct after a PREVIOUS. A non-seekable stream is not
  GR20's "single reel/unit mass storage file" and reports '30' rather than reading something else.
- **SR7 and SR10 got attachment points, and SR6 got its second arm.** SR6 and SR10 now live in
  `StatementValidation` as ONE check each, called by BOTH READ binder arms; SR7 is screened in
  `SequentialIoBinder.BindRead`, which is its only possible site. No new diagnostic code was needed for any of
  them: SR7 and the Format-1 membership rule are exactly `COBOLNET1720` (`io-phrase-forbidden-here`, the
  reusable descriptor), and SR10 is the keyed arm's own `COBOLNET0864`. **The reserved range
  COBOLNET1822–COBOLNET1823 went unused.**
- **The INVALID KEY bracket is bound, not dropped.** Format 1 has no such phrase (§14.9.30.2), so it is
  `COBOLNET1720` under strict — but that screen routes through `EditionContext.Removed`, which WARNS under
  `--permissive` and leaves the bind standing, and a standing bind has to MEAN something. §14.9.30.4 GR13c is
  what it means: a successful READ transfers control to the NOT INVALID KEY imperative. `BoundRead.InvalidKey`
  carries it (the keyed arm's own `KeyedInvalidPhrase` splitter, made public rather than copied) and
  `SequentialIoEmitter` renders the NOT arm only — a sequential READ raises no '2x' status, so the INVALID arm
  has no site.

`GR-14.9.30.4-19` DIVERGES → **CONFORMS**. GR19's row recorded TWO independent divergences and it inherited
this note when PB335 landed: (1) SR9's implied-NEXT test read two of its three members, so `READ f ADVANCING ON
LOCK` on an ACCESS DYNAMIC file bound Format 2 — closed by [[PB340]] on landing train 12, and the merged

**Goldens.** `conformance:{2002,2014,2023}/pb334_read_previous_sequential` — the same program at all three

informative and amends the INDEXED d.3 leg; the sequential block prints rule b unamended). Negatives:

`pb334-read-key-sequential-org` (SR10), `pb334-read-not-invalid-key-sequential-org` (Format 1).

**What did not hold on today's tree.** The note's blast-radius sentence said SR7 "has no attachment point until
the direction exists" — correct, and it is the reason the fix had to be structural. Its **fix shape** proposed
that the gate "keys on a DIRECTION field shared by both READ bound nodes"; the shipped shape is stronger — one
ENUM plus one INTERFACE, so the gate has one arm rather than two arms reading a shared field. `PB340`'s drift
test (every phrase property on a bound I-O node is consumed by its emitter) is still owed and still the thing
that would have caught this.
