**Evidence:** `E:\COBOL\.claude\worktrees\wf_eb1fc3a8-908-7\TestResults\build-local\20261008T160750Z-55b39f\not-run-Conformance.txt` lists the `pb66_float_edited_*`, `pb18_native_power_*` and `pb1900_*` conformance goldens as NOT run in leg 1, for a change whose diff is `src/WiseOwl.Cobol.Runtime/Values/Numeric/CobolEdit.Float.cs` and `src/WiseOwl.Cobol.Compiler/CodeGen/Emit/NumericRenderer.cs#Power`. Those goldens compile programs that emit exactly those calls. The implementer ran them by hand (all pass).

**Why it matters:** the impact map only ORDERS (PB1708), so under the scope `whole` the goldens still run in leg 2. Under batched gating (PB2515, the default scope `leg1` since 2026-10-10) the implementer runs leg 1 ONLY, so an under-selecting map means the change met its own most relevant goldens for the first time at the lander's whole-population gate.

**Likely cause (to measure):** the conformance goldens are recorded through one shared corpus-runner test method (`CorpusRunnerTests_P*.EnabledProgram_CompilesStrict_AndMatchesOutIfPresent`), so the map may key the runtime/codegen coverage of a GENERATED program's execution to the test case, not to the runtime methods the compiled program calls (the compiled program runs in a separate assembly the coverage collector may not instrument). Same family as PB1712 (blind to static field reads).

**Code sites:** `scripts/spec/record_impact_map.py`, `scripts/spec/impacted_tests.py`.

## 2026-10-18 (operator): a second occurrence, and it cost a landing

Lead from the Mythos lane's PB3333 finisher (report `w1118a3-PB3333-report.md`, its Finisher section), checked by the
operator.

**What happened.**
- The PB3330 engine's RELATIVE link (PB3333, branch `worktree-wf_14a1e62b-326-20` at `249e467ca`, which also carries
  the B+ tree, PB3332) changed RELATIVE files to the paged format. INDEXED files kept the whole-store format (PB3333:
  "The INDEXED organization keeps the whole-store path until PB3334"; the branch's `IndexedConnector.WholeStore.cs`).
- Its Windows gate was GREEN (run `20261018T175021Z-266291`). That run's `plan.json` reads `map_state: none`, "no
  impact map recorded for the base 6fb6a20f884f or any ancestor", so every case was tier 1. Its
  `not-run-Conformance.txt` holds 346 of the 364 `NistProgram_MatchesGolden` rows, among them every RL row (32:
  `RL101A`-`RL119A`, `RL201A`-`RL211A`, `RL213A`, `RL302M`) and every IX row (40: `IX101A`-`IX121A`,
  `IX201A`-`IX218A`, `IX302M`): none of them ran in leg 1.
- At the landing, the Linux gate (its conformance and guard legs) went RED on 31 NIST programs: 30 RL programs (every
  one of `RL101A`-`RL213A` except `RL119A`, which has no written-file golden and did not fail; the corpus has no
  `RL212A` row) and `IX106A`. `IX106A` failed through its RELATIVE file, not its indexed one: its `tf021.txt` is
  `RL-FR1` (`ASSIGN TO XXXXX021`, `ORGANIZATION IS RELATIVE`), and its indexed file's golden `tf024.txt` did not
  change. Their written-file goldens still held the old whole-store format. The finisher found they fail on Windows
  too, re-recorded the 37 written files (commit `fa66a259f`: `IX106A/tf021.txt` and the 30 RL programs' 36 files,
  every one a relative file), and both gates went GREEN at `46934aa87`.
- The cost was one landing attempt and one finisher cycle. A regression shipped on that path would have reached the
  Linux leg only.

**Same root cause as item 1 above:** no impact map is recorded for the base, so leg 1 holds only the cheapest reach,
and a change to the runtime's file format does not pull in the NIST programs that read and write those files.

**A hypothesis to test, not yet a fact.** The finisher suggests that even with a map, nothing attributes
`src/WiseOwl.Cobol.Runtime/IO/**` to the `NistDifferentialTests` rows, because the NIST programs run the compiled program
out of process, so the impact recorder may never see the runtime's coverage. Test it when a map is recorded:
1. `record_impact_map.py --commit <base>`;
2. ask `impacted_tests.py` for the reach of a change to `src/WiseOwl.Cobol.Runtime/IO/RelativeConnector.cs` (this
   occurrence's change), and of one to `src/WiseOwl.Cobol.Runtime/IO/IndexedConnector.cs` (PB3334 moves INDEXED onto
   the engine next, so the IX programs that write indexed files are the next occurrence's witnesses);
3. check whether the rows of every program that opens a relative file come back, the IX ones included: the witnesses
   are the 30 RL programs above and `IX106A`; `RL119A` and `RL302M`, which have no written-file golden, are not.

If they do not, the fix needs a static rule as well: a change under the runtime's I/O code puts the NIST file I/O and sort modules
(SQ sequential, RL relative, IX indexed, ST sort-merge) in leg 1.

**Harm, restated.** For a runtime file-format change, this gap leaves the local Windows gate blind to the conformance
suite's file I/O programs. Severity stays MINOR because the Linux leg caught it before main, but each occurrence costs
a landing.
