# PB1456 — OPEN

## The rule (every citation re-run by the registrar through `cite.py --check`)

> Whenever the PAGE-COUNTER of a different report is referenced, PAGE-COUNTER shall be qualified explicitly by the report-name associated with the different report

`python scripts/spec/cite.py --check 8.4.2.2.3 "…"` → `OK  §8.4.2.2.3 10)  (Syntax rules)`

## Finding — `qualification` (rejects-legal-source; rows `SR-8.4.2.2.3-9`, `SR-8.4.2.2.3-10`)

**Mechanism.** In the report section, an explicitly qualified reference to ANOTHER report's LINE-COUNTER or PAGE-COUNTER is staged loud as COBOLNET0899 'a counter of another report ... is not yet implemented'. The third sentence of SR9 and SR10 names this reference as the legal spelling. A separate problem is PB1049 (OPEN): in the procedure division, an unqualified counter with several RDs is correctly refused but under the not-yet-implemented code.

**Repro.** probe/qual/h1.cob (--std 2002 and 2023): two RDs R1 and R2 on files P1 and P2. R1's detail line has `03 COLUMN 7 PIC 99 SOURCE LINE-COUNTER OF R2.` and R2's has `03 COLUMN 4 PIC 99 SOURCE PAGE-COUNTER OF R1.` Observed: error COBOLNET0899 "RD 'R1': SOURCE LINE-COUNTER OF R2 - a counter of another report (ISO §8.4.3.15.3 SR2) is not yet implemented" (and the twin for R2). The same program without those two entries (h3) compiles and runs.

**Expected from the spec.** Compiles. Each such column prints the other report's counter as it stands when the line is printed. SR9 and SR10 (--check OK §8.4.2.2.3 9 and 10): "Whenever the LINE-COUNTER [PAGE-COUNTER] of a different report is referenced, LINE-COUNTER shall be qualified explicitly by the report-name associated with the different report". The sentence sits in the report-section half of the rule, and it presupposes that the qualified cross-report reference is legal. §8.4.3.15.3 SR1 admits a counter in a SOURCE clause, and §13.18.53.3 SR4 admits 'a report counter identifier'.

**Observed / reasoning.** Measured with the pinned cobol.exe. The procedure-division and own-report halves work: h3 prints the own-report counters and H1=002 003. CONFORMANCE.md A.4.11 lists only 'several SOURCE/SUM legs' as staged, and no kb/Work note names this leg. PB1049 claims these two rows, but only for the procedure-division misreport. The fixer should extend that note or file a sibling note.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs (report-section SOURCE counter operand: the 'counter of another report' COBOLNET0899 stage; ReportSectionNameIn's own-report-only admission for counters); src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ReportWriterBinder.cs#CounterReportOf (the PB1049 half)

## Finding — `report-counters` (rejects-legal-source; rows `SR-8.4.3.15.3-2`)

**Mechanism.** Counter-to-report resolution in the REPORT SECTION does not implement §8.4.2.2.3 SR9/SR10. A qualified counter of ANOTHER report is staged or rejected. An unqualified counter inside a SOURCE arithmetic-expression is resolved by the procedure-division rule (exactly one report), because the expression is bound through ReportWriterBinder.CounterReportOf with no knowledge of the enclosing RD.

**Repro.** Two RDs R1 and R2 on two files. (a) In R2: `03 COLUMN 1 PIC 99 SOURCE PAGE-COUNTER OF R1.` -> COBOLNET0899 'a counter of another report (ISO §8.4.3.15.3 SR2) is not yet implemented' (rcq3). (b) In R2: `SOURCE (PAGE-COUNTER OF R1 + 100)` -> COBOLNET2144 '... neither a report counter nor a sum counter of this report' (rcq5). (c) In R2: `SOURCE (PAGE-COUNTER + 100)` -> COBOLNET0899 'unqualified PAGE-COUNTER with more than one report', reported with no source location (rcq1). (d) In R2: `SOURCE LINE-COUNTER OF D2` (D2 is a report group) -> 'not yet implemented' instead of the qualification violation (rcq6). Probes under E:\Temp\claude\E--CobolSharp\a700c052-f9e4-4942-84ff-a13c7505d6ec\scratchpad\adj-d2\out\probe\report-counters

**Expected from the spec.** §8.4.2.2.3 SR10 (and the SR9 LINE-COUNTER twin): 'In the report section, an unqualified reference to the PAGE-COUNTER is qualified implicitly by the name of the report in whose report description entry the reference is made. Whenever the PAGE-COUNTER of a different report is referenced, PAGE-COUNTER shall be qualified explicitly by the report-name associated with the different report.' (a) and (b) compile and print R1's PAGE-COUNTER at the moment R2's line is printed. With the program's MOVE 40 TO PAGE-COUNTER OF R1, (a) prints 40 and (b) prints 140. (c) compiles and uses R2's own counter, like the single-RD twin rce1 that prints 103 and the bare `SOURCE PAGE-COUNTER` in the same R2, which already works (rcq7). (d) is a qualification error citing §8.4.2.2.3 SR9, not a not-implemented stage.

**Observed / reasoning.** DataBinder.Reports.BindSourceReference stages any qualifier other than the own report name as ReportSourceOtherReportCounter (RecognizedNotImplemented), and its comment concedes the source is legal. docs/COBOLNET_REPORT_WRITER_DESIGN.md lists 'SOURCE of another report's counter' as staged loud, and no kb/Work note owns it. The FieldComputeSource SR4 screen (ReportSectionNameIn) reads §13.18.53.3 SR4's 'a report counter identifier or a sum counter defined in the current report' as restricting counters to the current report, which contradicts the last sentence of §8.4.2.2.3 SR9/SR10. The procedure-phase expression bind reaches CounterReportOf, which applies only the procedure-division 'exactly one report' rule. PB1049 (open) owns only the diagnostic code and wording for the procedure-division unqualified case, not these report-section rejections.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs#BindSourceReference; src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs (FieldComputeSource SR4 screen / ReportSectionNameIn, COBOLNET2144); src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ReportWriterBinder.cs#CounterReportOf; src/Cobol.Net.Runtime/IO/ReportWriter.cs (FieldCounterSource has no report operand)

## Refuter evidence — row `FMT-8.4.3.15.2` (PARTIAL)

PARTIAL — The parser accepts every spelling of the format, but the binder rejects one legal instance of the qualified form, report-name-1 naming a DIFFERENT report inside a report section SOURCE clause. SR1 allows counters in a SOURCE clause. §8.4.2.2.3 SR9/SR10 state outright that a counter of a different report is referenced by qualifying it with that report's name. DataBinder.Reports.cs BindSourceReference instead raises ReportSourceOtherReportCounter ('a counter of another report ... is not yet implemented', COBOLNET0899), a staged rejection of legal source. The procedure-division forms all work: PAGE-COUNTER IN/OF and LINE-COUNTER IN/OF, as sender, as the PAGE-COUNTER receiver and in conditions. Same-report qualified SOURCE forms also work. So the format is only partly supported and no test pins it.

**Code site.** src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4#dataReference; src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ReportWriterBinder.cs#CounterReportOf

## What the fixer owes

Implement §8.4.2.2.3 SR9/SR10 once for the REPORT SECTION: an unqualified counter is implicitly qualified by the enclosing RD (thread the RD into ReportWriterBinder.CounterReportOf for SOURCE expressions), a qualified one names any report; FieldCounterSource in the runtime needs a report operand. Correct the ReportSectionNameIn reading of §13.18.53.3 SR4, the design doc's 'staged loud' line in COBOLNET_REPORT_WRITER_DESIGN.md, and DIAGNOSTICS. PB1049 owns the procedure-division misreport — land together. Goldens h1, rcq3, rcq5, rcq1; a qualification violation (`LINE-COUNTER OF D2`, a report group) must draw the SR diagnostic, not 'not yet implemented'.
