# PB152

LANDED 2026-09-02 as ONE choke point, `InitialStateBackground`
(`src/Cobol.Net.Compiler/CodeGen/DataDivision/InitialStateBackground.cs`), plus COBOLNET1727 for §11.9.10.3 SR1.

## ⚠ THE NOTE'S HEADLINE WAS STALE AND ITS SCOPING ANALYSIS CARRIED A WRONG PARAPHRASE

Two corrections had to be made before any code was written, and both were only reachable by re-checking:

1. **"ZERO consumers" was FALSE.** kb/Work PB151 (commit 4ae610b7) had already given the clause its first
   consumer — the §14.9.3.4 GR8/GR9 ALLOCATE fill. Implementing this note as written would have re-implemented a
   landed feature. What was actually dead is named below.
2. **The 2026-08-30 fix design paraphrased §11.9.10.3 SR1 as "a one-character alphanumeric OR one-byte hex
   literal".** The rule says "Literal-1 shall specify a one-byte **hexadecimal-alphanumeric** literal", and that
   is a DEFINED TERM: §8.3.3.2.2 gives the alphanumeric literal exactly two general formats — format 1
   (`"…"` / `'…'`) and format 2 (`X"…"` / `X'…'`) — and "hexadecimal-alphanumeric" names FORMAT 2. So a
   one-character quoted literal is **not** admitted however short it is. Implementing the paraphrase would have
   shipped an under-reject. The printed page (PDF 307 / printed folio 277) was rendered and read to settle it;
   the transcription is character-for-character correct, format diagram included.

## What was measured broken (2acbd842)

With `OPTIONS. INITIALIZE ALL TO X"5A".` (0x5A = 'Z') in force:

| shape | expected (§14.6.2.3.2 action 1) | was | now |
| --- | --- | --- | --- |
| `01 A PIC X(4).` no VALUE | `ZZZZ` | four spaces | `ZZZZ` |
| the same item read through a Tier-B REDEFINES window | `ZZZ` + carrier bytes | spaces | correct |
| `INITIALIZE LOCAL-STORAGE SECTION TO …` | fills LS only | filled NOTHING | correct, both directions |
| `01 E IS EXTERNAL PIC X(4).` | NOT filled (GR7) | not filled (by accident — nothing was) | not filled (by rule) |
| `INITIALIZE ALL TO "AB"` | rejected (SR1) | accepted, silently filled with `A` | COBOLNET1727 |
| `INITIALIZE ALL TO HIGH-VALUES` on the ALLOCATE arm | the alphanumeric high value | U+FFFF | U+00FF |

`01 B PIC X(4) VALUE "vv"` correctly showed its VALUE throughout — action 2 was never the problem.

## The three arms, and why only a shared resolver fixes it

"What fills storage that has no VALUE clause" was composed in THREE places and exactly ONE had been fixed:

1. **the ALLOCATE arm** — `PtrEmitter.OptionsFillCharLiteral`, landed by PB151. ⛔ Its decoder was **private to
   the emitter**, so the other two could not have reused it even if someone had tried, and it carried its own
   copy of the §11.9.10.4 GR5 map.
2. **the native-field arm** — `ValueInitializer`'s no-VALUE branch over `PicInfo.DefaultInitializer`. DEAD.
3. **the Tier-B image arm** — `GroupImageCodec`'s fall-through, which seeds the string backing a REDEFINES class
   composes. DEAD, and the one arm PB151 structurally could not reach.

`InitialStateBackground` is now the sole producer of a background seed; `PicInfo.DefaultInitializer` stays the
no-clause baseline it correctly is. Design recorded as `COBOLNET_DATA_MODEL_DESIGN.md` **D23**.

## ⛔ THE FIND THAT WAS NOT IN THE BRIEF: the landed arm disagreed with the compiler

PB151's private GR5 map spelled HIGH-VALUES as **U+FFFF**. The compiler's ONE definition of the alphanumeric
high value is `FigurativeConstants.FillChar`, which under the native sequence is **U+00FF** — and §8.3.3.6.4 GR6
makes it a PROGRAM-COLLATING-SEQUENCE-dependent fact, not a constant at all. One rule, two places, two answers,
and the arm with the private copy was the one that disagreed with the rest of the compiler. Found by writing the
GR5 golden and watching the HIGH-VALUES leg fail against `IF A = HIGH-VALUES`.

The fix is structural, not a value edit: the model now resolves **only literal-1's byte** (where SR1's syntax
check belongs, at bind time) and the figuratives resolve at codegen through the shared definition.
`pb152_options_initialize_arm_agreement` asks all three arms the same HIGH-VALUES question in one program.
⛔ GR5 a is kept SEPARATE from GR5 d: "a string of binary zeros" is the literal zero byte, "the alphanumeric low
value character" is the collating minimum — identical natively, different under a PCS.

## The determination (CONFORMANCE.md + D23)

§11.9.10.4 GR5 makes the fill a CHARACTER; a `long` / `Int128` / `float` / `double` field and an INDEX cell have
no character positions. **Character-formed storage takes the fill; a native-numeric carrier and an index cell
take their zero**, licensed by §13.18.63.4 GR4 c) — a VALUE-less item's content is "undefined and set to a value
that may or may not be allowed for that data item or index". Two carve-outs from RULES: class object /
message-tag / pointer take NULL (GR4 c) states it positively), and USAGE BIT keeps its packed ceil(n/8) zero
seed (D19) because its storage is packed bytes, not character positions.

## Evidence

- **Blast radius:** ZERO changes across 493 positive conformance goldens at their own editions and 459 NIST
  programs. The no-clause path is byte-identical by construction (`FillFor` returns null with no clause) and
  that invariant is a unit test, not an assumption — it covers the entire existing corpus.
- **MAKE IT FAIL ONCE:** reverting the Tier-B image arm alone turned `pb152_options_initialize_tier_b` and
  `pb152_options_initialize_arm_agreement` RED while `pb152_options_initialize_background` stayed GREEN — so the
  goldens attribute to the arm, and the second dead arm cannot be left unfixed unnoticed.
- **Corpus repair:** `tests/conformance/2023/pb151_options_fill.cob` was written `INITIALIZE ALL TO "Q"`, which
  SR1 forbids. Repaired to `X"51"` — 0x51 IS 'Q', so its expected output is unchanged byte for byte. Repairing
  nonconforming source, not bending a golden to fit.
- Seven positive goldens, three negative fixtures, one drift-test class (15 tests).

## What this landing does NOT close, named so the gaps stay visible

- **§14.9.3.4 GR9's first clause — "data items of class object or class pointer in the allocated storage are
  initialized to null" — has NO REACHABLE SUBJECT today, and that is MEASURED, not deduced.** [[PB183]]'s SR14
  screen (landed alongside) confines a pointer usage to level 1/77 or a STRONG type declaration, so the only
  candidate is `01 BP BASED USAGE POINTER.` — and that shape is rejected before ALLOCATE by the pre-existing
  COBOLNET1695 stage ("BASED item 'BP' has a national/bit/pointer-class leaf — the shared byte cell cannot carry
  it", kb/Work PB164 residue). Probed and confirmed. GR-14.9.3.4-9 therefore stays open and closes with PB164's
  residue, not here.
- **The OPTIONS paragraph's OTHER producer-only fields were not swept**: `IntermediateRounding`,
  `FloatBinaryEndianness`, `FloatDecimalEncoding`, `FloatDecimalEndianness`, `EntryConvention` all share this
  note's original shape (parsed, modelled, unconsumed). Registered as [[PB298]].
- **§11.9.10.4 GR3 (SCREEN)** is recorded DOCUMENTED-NON-SUPPORT rather than implemented: the SCREEN SECTION is
  a §4.2.7 optional facility this compiler documents as unsupported (COBOLNET1560). The gap stays visible
  through that existing warning rather than acquiring a second diagnostic, and closes with the section itself.
- A **pre-existing wrong answer found while writing the goldens** and deliberately not fixed here: a
  reference-modified operand compared against the figurative LOW-VALUE/HIGH-VALUE answers wrong when the ref-mod
  length differs from the base item's width. Registered with a full repro as [[PB297]]; the Tier-B golden uses
  `FUNCTION ORD` instead and says why, so no golden rests on the defective construct.
