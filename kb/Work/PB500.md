# PB500

## Mechanism — value-clause-p3
The Format 2 (table) VALUE is implemented only for a SINGLE-DIMENSION table on the entry that carries the OCCURS clause. `ValueInitializer.ResolveTableValueMap` walks one subscript (`spec.From[0]` / `spec.To?[0]`) and has no odometer; `DataBinder.ValidateTableValues` (DataBinder.cs:3209-3219) therefore refuses every other shape with COBOLNET0899 rather than mis-filling. Two legal shapes fall in that refusal — a multi-dimension table VALUE and a VALUE on an item SUBORDINATE to the OCCURS entry — and the second one is also the shape §13.18.63.4 GR16's "or in any entry superordinate to it" clause is about, so GR16's superordinate arm is unreachable too. A third, adjacent refusal (COBOLNET1528, DataBinder.Odo.cs:247) rejects a FORMAT 1 VALUE on or under a dynamic entry with the same GR16 citation.

### Expected, from the standard
§13.18.63.3 SR18: "A data description entry that contains the VALUE clause shall contain an OCCURS clause OR be subordinate to a data description entry that contains an OCCURS clause" — so (b) and (c) are legal. SR20/SR21: "there shall be one subscript-1 [subscript-2] specified for each OCCURS clause for the subject of the entry or superordinate to that entry, specified in the same order as a subscripted reference to the subject of the entry would be specified" — the multi-subscript form of (a) is the form those rules exist to govern. §13.18.63.4 GR12 supplies the odometer: "Consecutive table elements are referenced by incrementing by 1 the subscript that represents the least inclusive dimension of the table. When any reference to a subscript, prior to incrementing it, is equal to the maximum number of occurrences ... that subscript is set to 1 and the subscript for the next most inclusive dimension of the table is incremented by 1." For (a) that gives CELL(1 1)=A, (1 2)=B, (1 3)=C, (2 1)=D, then GR13's reuse gives (2 2)=A, (2 3)=B. For (c), GR16 must derive an initial capacity of 5 from the subordinate VALUE's subscript-2.

### Observed
Measured. The refusals are LOUD and there is no wrong answer, so the harm is confined to legal source being rejected; that is nonetheless debt under CLAUDE.md rule 3, and conformance-test:ValueFormat2Tests.MultiDimension_StagedGap0899 is a GREEN test pinning it (feedback_green_test_can_hold_a_gap_open) that must flip when the odometer lands. FIX SHAPE — prefer the shape that makes the next case automatic: `ResolveTableValueMap` should key on the full subscript TUPLE rather than a single int, with the fill loop an odometer over the dimension list the item's OCCURS chain already provides, and the emitter should index the nested arrays from that tuple. That one change retires (a), (b) and (c) together and makes GR13/GR14/GR15 multi-dimensional for free, because those rules are already expressed in terms of the same map. PREMISE CORRECTION for (d), worth carrying into the note that lands this: GR16 sits in the FORMAT 2 band and every subrule turns on "a TO phrase ... in the VALUE clause", so a FORMAT 1 VALUE on a dynamic entry is not governed by GR16 at all — COBOLNET1528 refuses that source citing a rule that does not reach it, and the correct answer there is simply the §14.6.2.3.2 initial-state capacity (the OCCURS minimum) with every occurrence taking the VALUE per GR9. The same-entry format-2 derivation itself is correct and was measured across all four of GR16's sub-cases (probes gr16_dyn_to, gr16_dyn_below, gr16_dyn_noto, gr16_dyn_max).

## Landed
**2026-09-13, base main 1840778e.** The note's shapes (a), (b) and (c) NO LONGER REPRODUCED — PB505 landed `DataBinder.TableValue.cs` + `TableValueOdometer` in the meantime and retired the COBOLNET0899 refusal exactly as this note's FIX SHAPE paragraph prescribed. Re-probed first: `05 ROW OCCURS 2. 10 CELL PIC X OCCURS 3 VALUES ARE "A" "B" "C" "D" FROM (1 1) TO (2 3).` gives `R1=ABC R2=DAB`, which is GR12's odometer followed by GR13's reuse, the exact answer this note derived; the subordinate and GR16-superordinate shapes likewise. Rows GR-13.18.63.4-12 … -16 were already `CONFORMS`/OK from that landing and needed no re-verdict.

What DID still reproduce is (d), and this landing is the note's own PREMISE CORRECTION carried out. **§13.18.63.4 GR16 is a FORMAT 2 general rule (band GR11–GR16) and does not reach a Format 1 `VALUE IS literal-1`.** §13.18.63 states cross-band application explicitly and in ONE direction only — GR11 ("General rules 1, 2, 3, 4, 5, 6, 7, 8, and 10 above apply"), GR17, GR21 and GR24 all import FORMAT 1 rules INTO a later band, and nothing imports GR12–GR16 back. The syntax rules settle it independently, and this is the argument the note did not have: **§13.18.63.3 SR22** — the rule that keeps GR16b from having no operand — **is itself FORMAT 2** (band SR16–SR23) with no FORMAT 1 counterpart, so on the refusal's reading `05 A PIC X OCCURS DYNAMIC FROM 2 VALUE "Z".` would hit GR16b with no expected capacity to set, a hole the standard would have had to close and did not.

So the COBOLNET1528 refusal at `DataBinder.DynamicResolve` was rejecting legal source (§13.18.38.3 forbids a VALUE on a Format 4 entry nowhere), and it is DELETED — its code is never reallocated. The correct answer needed no new code: capacity is the §14.6.2.3.2 item-6 / §13.18.38.4 GR16 minimum (the OCCURS FROM, zero when absent, cross-checked from the other side by §8.5.1.9.1), and §13.18.63.4 GR9 with §13.18.38.4 GR1 (band "FORMATS 1, 2 AND 4") give every occurrence the value — both already what `ValueInitializer.FieldInit` does.

**The two-arm signature (CLAUDE.md rule 4) was the tell.** The refusal's GROUP arm fired only when the OCCURS carried a TO, so `OCCURS DYNAMIC FROM 3.` with subordinate VALUEs compiled and seeded correctly while `OCCURS DYNAMIC FROM 3 TO 9.` — the same construct, one optional phrase apart — was refused; the ELEMENTARY arm ignored the TO and refused both. Two GREEN tests pinned the refusal (`ValueOnElementaryDynamicEntry_Rejected1528`, `GroupSubordinateValueWithTo_Rejected1528`) and are flipped to positive behaviour tests. A band-scoping sweep over every `13.18.63` citation in `src/` found this to be the ONLY site applying a FORMAT 2 rule to a Format 1 construct.

Golden `tests/conformance/2014/pb500_format1_value_dynamic_table` pins seven shapes, including the absent-FROM zero capacity and the mixed entry where a Format 1 and a Format 2 VALUE sit over one dynamic table and only the latter moves the capacity. Two GAP rows this landing discharges were added to `inventory_rows` and verdicted CONFORMS: **GR-13.18.38.4-16** (the minimum capacity, whose second sentence had never been observable) and **GR-14.6.2.3.2-L2.6** (the initial-state capacity + INITIALIZED occurrences). GAP 2561 → 2559.
