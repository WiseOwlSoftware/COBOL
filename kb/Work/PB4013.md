# PB4013 — COMP-5 with a PICTURE: which range does a VALUE literal answer to?

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs#ValidateNumericValue` (digit-span branch, via `StoredShapeOf`)

**Observed.** `01 F3 COMP-5 PIC 9(4) VALUE 65535.` and `01 F4 PIC S9(4) COMP-5 VALUE -32768.` draw COBOL1625 ("range the PICTURE
indicates"), yet `docs/CONFORMANCE.md` DOC-A.1-208 states COMP-5 owns its full 16-bit container and the runtime stores 65535
there. The direction is over-strict (possibly legal source refused); it shares no root cause with PB3997 (which was
under-strict) but the same site.

**Question owed (adjudicator role, not a clerk).** §13.18.63.3 SR2 reads that a literal "shall be permissible values within the
range indicated by the PICTURE clause or the USAGE clause" (run `python scripts/spec/cite.py --check 13.18.63.3` on the text
before citing). Does "or" admit the wider USAGE range when both are present, or does it select the PICTURE range? Weigh it with
§13.18.60.4 12) (implementor may allow a wider range), PB825's owner decision R13 (follow GnuCOBOL), and what cobc does for the
two sources above.

**Acceptance.**
- An adjudication verdict with checked citations, in this note or an `adjudication` note.
- If the wider range is admitted: `ValidateNumericValue` asks the USAGE band first for a COMP-5 item with a PICTURE, with a
  golden for 65535 and -32768 and the below-edge refusals; otherwise DOC-A.1-208 is corrected to say the PICTURE bounds VALUE.

## Verdict (2026-10-30): the wider range is admitted; the defect is PB4113

A cobol-adjudicator (`E:/COBOL-coord/scratch/adj/PB4013-verdict.md`) ruled DEFECT, rejects legal source; a cobol-refuter
(`PB4013-refute.md`) UPHELD it and AMENDED the reasoning. Every quote was checked with `cite.py --check`.

- COMP-5 is not in ISO/IEC 1989:2023 (a §4.2.10 1) extension). §13.18.63.3 SR2 bounds a VALUE literal by "the range
  indicated by the PICTURE clause or the USAGE clause", and for COMP-5 the compiler's own determination (DOC-A.1-208)
  makes the USAGE's container the range. GnuCOBOL 3.2.0 (re-run under -std default, ibm and mf) and IBM's Programming
  Guide ("Literals specified in VALUE clauses for COMP-5 items can, with a few exceptions, contain values of magnitude up
  to the capacity of the native binary representation") agree, so the "wider range is admitted" branch of this note's
  Acceptance holds.
- The refuter's amendment: ISO does not tie standard COMPUTATIONAL's range to its PICTURE either (§13.18.60.4 GR6 leaves
  it to the implementor); the compiler's refusal of `COMP PIC 9(4) VALUE 65535` rests on DOC-A.1-208, which is unchanged.
- SR2's no-truncation sentence still refuses a digit below the PICTURE's scale (`S99V99 COMP-5 VALUE 1.234`).
- Today only VALUE disagrees: MOVE, arithmetic, SET of an 88, INITIALIZE and comparisons already use the container.

PB4113 carries the fix (`DataBinder.cs#ValidateNumericValue`, whose USAGE-band branch is unreachable behind the PICTURE
digit test), the DOC-A.1-208 sentence for VALUE and the golden scope both passes named.
