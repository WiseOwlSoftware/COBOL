# PB3337 — transactions, COMMIT and ROLLBACK in the runtime

## ✅ THE OWNER'S DECISION — 2026-10-19 18:58 PDT, verbatim: **"Option A"**

**The question, as it was put (the owner, 2026-10-19 ~18:45: "No one is telling me what the options are. I will not decide
without information").** The compiler declines the commit-and-rollback module (ISO Annex A.4.3): the APPLY COMMIT clause is
refused by name (COBOLNET1709) and COMMIT and ROLLBACK are inert, which §14.9.7.4 GR1 and §14.9.36.4 GR1 make correct while
no clause is active; §4.2.7 lets a conforming compiler decline an optional module with documentation, as screen handling and
the message control system are declined. Eleven inventory rows of §9.1.16–9.1.18 sat as GAP because nobody had decided
whether the decline stands or the module is built. The options, each with what it delivers, loses and costs:

- **(A) The whole module — PB3337 (the runtime's transactions for indexed and relative files), PB3338 (the compiler's clause
  and statements), PB3340 (sequential, line sequential and the print stream, the journal the owner approved at 15:45).**
  Delivers §9.1.16–9.1.18 entire: COMMIT and ROLLBACK on every file type, the listed data items saved and restored, rollback
  at abnormal termination, a killed run unit rolled back by the next writer, the implicit `LOCK MODE AUTOMATIC WITH LOCK ON
  MULTIPLE RECORDS` posture; the eleven GAP rows close as CONFORMS and the seven rows CONFORMING only because the clause is
  unreachable (docs/CONFORMANCE.md, A.4.3) become real adjudications. Loses nothing of the module. Costs three serial groups,
  PB3420's estimate 8–12 h of wall clock each, the largest remaining tier of the campaign; it displaces tier 3 this week or
  waits for the quota reset.
- **(B) Keyed files only — PB3337 and PB3338; PB3340 retired.** The same for indexed and relative files. Loses: a clause
  naming a sequential, line sequential or print file is refused although §9.1.18.2 admits any mass-storage file, so a batch
  program with an indexed master and a sequential audit file cannot put both in one unit of work (a partial claim §4.2.7
  requires to be documented as such). Costs two groups; the journal design is already paid for.
- **(C) The decline kept.** The eleven rows close by the owner's decision as documented non-support, like the 48 rows beside
  them: zero GAP here with no implementation. Loses the module (no rollback, no recovery of a killed run unit's changes, no
  automatic multi-record locking); the designs 2.2.1.10 and 2.2.2 stay on the shelf. Costs one notes landing.

**The one question that follows it (asked 2026-10-19 with this decision; the answer is recorded here when given):** when one
COMMIT covers several files under APPLY COMMIT and the medium refuses the commit of one of them, the design states a PER-FILE
commit — files committed one at a time in the order of the run unit's open stores; a refusal at file i leaves the files
before i committed and the files from i on at the previous COMMIT once item 8's unconditional ROLLBACK has run; the program
gets EC-I-O-PERMANENT-ERROR with '30' on the refused file (2.2.1.10's three regions; docs/CONFORMANCE.md's commit row).
The alternative is ALL-OR-NOTHING across files, which needs a durable commit record outside any one file that every file's
recovery consults (a two-phase commit): both designs and both simulators change, since each file's recovery gains a
dependency on a record it does not own — the Mythos lane's unmeasured estimate is one more design memo with its model and a
third to a half more work on PB3337 and PB3340. The spec is silent on a COMMIT that fails part way (§9.1.18.3 says only that
a COMMIT makes the changes permanent); GnuCOBOL has no rollback at all; IBM and Micro Focus get atomicity across files from a
transaction server or a file server's log, not from the compiler. The Mythos lane recommends per file, as designed.

## Mechanism

- `FileRegistry.RegisterCommitControl(name)` (called by the generated activation of a runtime element whose APPLY COMMIT clause
  names the connector, §12.4.6.3.4 GR5's activation): the connector registers the §9.1.16 implicit posture `LOCK MODE IS
  AUTOMATIC WITH LOCK ON MULTIPLE RECORDS` with `PhysicalFileTable`; its OPEN sets nothing in the file (commit control is a
  transaction in the TRANSACTIONS tree, not a property of the file).
- **The transaction** (`PagedStore.Transaction`): begun by the first WRITE, REWRITE or DELETE the run unit executes through a
  connector under commit control on that physical file — its id is DRAWN: the lowest value from page 2's `transaction mint`
  whose liveness byte `HostRegionLocks.TransactionLivenessByte(id)` (2^62 + 2^61 + id mod 2^60) the connector can take
  EXCLUSIVELY through its writable handle (a held byte — a live transaction's or a refused attempt's — is skipped), then
  CLAIMED (`transaction mint` := id + 1 in the store's memory and, under the mutex, in the page-2 claim before any page write;
  round 4, R4-2), and the TRANSACTIONS tree gets id → the POINTER to a new UNDO tree; a first change refused before its page
  2 gives the byte back, since no entry carries the id. Every WRITE, REWRITE and DELETE through a connector under commit
  control inserts into the UNDO tree — keyed (kind, identity), the key the HOLDINGS tree uses (round 5, R5-2) — the
  record's BEFORE-IMAGE under (R, the record's identity) — the whole frame with its ordinal vector, or ABSENT for a created
  record — unless an entry exists (the first image is the one to restore), and a V entry, the entry alone, under (V, the
  key's index + the value's channel bytes) for every unique alternate key value the change frees, in the same statement that
  changes the record (R1-R3 make it as crash-consistent as the data); and it writes the same keys → the transaction id into
  the file's one HOLDINGS tree (its root in the meta page, 2.2.1.4; round 4, R4-1), so the transaction's locks outlive its
  handle. The HOLDINGS tree is the file's INDEX, by identity, of every open transaction's UNDO entries, and a transaction's
  UNDO tree is ITS OWN LIST of its holdings: after every statement the HOLDINGS tree's key set equals the union of the UNDO
  trees' key sets (a drift test, 2.2.1.12), so a value freed by a later change of the same record (X → Y, then Y → Z: the
  image holds X, the holding is V:Y) or by a DELETE of a record the transaction wrote (image ABSENT) is found by COMMIT,
  ROLLBACK and the dead-owner rollback like every other holding, by one walk of the UNDO tree. One transaction per (run unit, physical file); a
  second connector of the run unit on the same file that no APPLY COMMIT names logs nothing.
- `FileRegistry.Commit()` (§14.9.7.4 GR3): for every physical file with a transaction of this run unit —
  `PagedFile.Promote(committing: id)`: the claim carries the id, the SLOT WRITE and the sync after it (sync 2) decide the
  COMMIT and only that sync ANSWERS it (round 5, R5-1: the unacknowledged-COMMIT rule of 2.2.1.10), and the RETIREMENT
  removes the transaction's entry and every holding one walk of its UNDO tree lists, R and V alike (R5-2), and releases the
  UNDO tree's pages — then the liveness byte is given back. Three regions. (1) Refused BEFORE the slot write (the claim,
  sync 1 or the slot write itself): the transaction is intact (the claim is unwound by the next entry's restart rule, the
  run unit's own ROLLBACK's included) and the COMMIT unsuccessful, so the unconditional ROLLBACK of §14.6.13.1.3 item 8
  restores every before-image. (2) The slot write handed to the operating environment and sync 2 LANDED: committed, and
  the COMMIT answers success whatever becomes of the retirement, which the next entry completes. (3) Sync 2 REFUSED, the
  UNACKNOWLEDGED COMMIT: still under the exclusive mutex it has held since its claim, the COMMIT REVERSES — its retirement
  run as the rollback of t (page 2 onto the new base, PROMOTING cleared, `committing` 0, every before-image of t's UNDO
  tree re-applied, the entry and its holdings removed), then an ordinary promotion of that page 2 — and answers
  unsuccessful, so item 8's ROLLBACK finds no transaction on this file; when the reversal is refused too (one of its page
  writes, or its promotion's sync) the store MARKS the file UNACKNOWLEDGED in the run unit's memory, the COMMIT answers
  unsuccessful, and the file is in §9.1.13.1's permanent error (the ROLLBACK bullet says what a ROLLBACK on a marked file
  does). What the program is told: COMMIT and ROLLBACK have no I-O status (§9.1.13.1 sets it only for CLOSE, DELETE, OPEN,
  READ, REWRITE, START, UNLOCK and WRITE), so a refused COMMIT or ROLLBACK raises the fatal EC-I-O-PERMANENT-ERROR for the
  file whose promotion or statement was refused, with '30' in that file's status item — item 8's condition, so its
  unconditional ROLLBACK follows. Files are committed one at a time, in the order of the run unit's open stores, each by
  its own slot write: a COMMIT refused at file i leaves the files before i committed and the files from i on at the
  previous COMMIT once item 8's ROLLBACK has run (PB3338's commit row states the determination; cross-file atomicity is
  the owner's question in PB3330). Then `PhysicalFileTable.ReleaseAllForConnector`
  (the region's READ locks) for each connector under commit control; GR4: a
  connector under commit control that was CLOSEd keeps its handle (the §9.1.15 file lock, "the file lock is removed by the
  COMMIT statement") in a `ClosedUnderCommit` set and releases it here. Status items are the compiler's (PB3338).
- `FileRegistry.Rollback()` (§14.9.36.4 GR3): for every physical file with a transaction of this run unit — ONE statement
  (`PagedStore.ApplyUndo`: one walk of the UNDO tree — every R before-image written back under its identity with its OLD
  ordinals, the alternate trees' composite entries rebuilt from the frame's ordinal vector, ABSENT = delete — and every key
  the walk met, R and V alike, removed from the HOLDINGS tree (R5-2), with the transaction's entry; no promotion, the
  operation is idempotent. The one exception is a file marked UNACKNOWLEDGED (the COMMIT bullet, region 3): under the mutex,
  the reversal again if page 2 still carries t's entry under the flag, then a promotion of page 2 as it stands, and the
  ROLLBACK answers by that promotion's sync — success clears the mark, a refused sync is '30'; a ROLLBACK that finds t's
  entry gone from page 2 without this run unit having rolled it back answers '30' too, since another connector's entry
  completed the landed COMMIT while the owner could not reverse it) — then the region's READ locks are released, the kept handles of
  connectors closed since the last COMMIT are released, and the §9.1.15 last sentence's case (a file not open at the previous
  commit and opened since) releases its file lock. Another run unit's records are never read or written; `ApplyUndo` runs no
  uniqueness check and no lock test, because every identity and unique value it re-inserts is a holding in the file, which
  no writer passes while the owner lives ('51') and none after its death without this rollback having run first, at that
  writer's own lock test or its entry (rounds 3 and 4, R3-1 and R4-1).
- **The transaction's locks are its HOLDINGS, in the file** (2.2.1.10, findings R2-3, R2-4 and R4-1): under the implicit
  posture every WRITE (§14.9.51.4 GR11's implied WITH LOCK), REWRITE and DELETE through a connector under commit control holds
  the record it changed — a DELETE its IDENTITY, which stays in the HOLDINGS tree after the record is gone — and a REWRITE
  or DELETE that frees a unique alternate key value (a key declared without DUPLICATES) holds that VALUE (kind V: the key's
  index + the value's channel bytes). None of this is published in the region or tabled by `PhysicalFileTable` (round 4: a
  region lock dies with its holder's handle, and a holding must outlive it); only the posture's READ locks (GR4) are region
  locks, as today. **The lock test** of READ (not IGNORING LOCK), WRITE, REWRITE and DELETE, at DOC-A.1-104's point (after
  the invalid-key conditions, which ignore locks, GR33/GR42; before the record is touched): the region as today, then — when
  page 2's holdings root is not empty — the HOLDINGS lookup of the identity and, for WRITE and REWRITE, of each unique value
  they would insert. Own transaction through a covered connector → proceed (GR8). Another transaction's (another run unit's,
  or this run unit's through an uncovered connector) → its owner's liveness byte probed AT THE TEST: held → '51' with RETRY
  (GR16); free → the owner died, `ApplyUndo` runs for it there, under the mutex the tester holds and before its own change,
  and the statement's conditions are evaluated again from the invalid-key conditions on ('22' where the rollback re-created
  the identity or re-inserted the value). WRITE thereby gains the lock test REWRITE and DELETE have. Holdings are removed
  only by COMMIT's retirement, ROLLBACK and the dead-owner rollback; the READ locks are released by COMMIT, ROLLBACK and
  termination. The ceilings `RunUnitLockMax`/`ConnectorLockMax` (DOC-A.1-154/155) do not apply to the commit posture's READ
  locks (the host's lock table is the limit; GnuCOBOL imposes none), and a holding is a tree entry with no ceiling but the
  file's; DOC-A.1-152 names the deleted-identity and unique-value circumstances (§9.1.16's implementor latitude). Three
  CONFORMANCE rows are rewritten here.
- **The dead-owner step** (2.2.1.10, round 3's R3-1: at the coherent entry of EVERY statement through a connector with a
  writable handle — `KeyedConnector.BeginStatement` after its page-2 read and after a PROMOTING flag, if set, has been
  resolved by `CompletePromotion`'s restart rule (landed → completed, the entry `committing` names removed; an unlanded
  COMMIT → unwound), so a COMMIT's fate is settled before its transaction is probed; and `PagedFile.Open`'s last step, R6 —
  under the store mutex): when page 2's transactions root is not empty, read the TRANSACTIONS tree, probe the liveness byte of each
  transaction of ANOTHER run unit (this run unit's own are alive), and roll back every transaction whose byte is not held
  (its owner died: §9.1.18.5, kill or power loss) with the same `ApplyUndo`, before the entering statement proceeds, whether
  or not other run units hold the file open; a transaction whose byte is held is left exactly as it stands. The dead owner's
  holdings did not go with its handle — they are pages — and an owner killed AFTER a statement's entry probe is caught at
  that statement's lock test (the bullet above; round 4, R4-1): the entry's probe is the eager form that bounds a dead
  transaction's visible lifetime, the test is the one correctness rests on, and the release order of a dead handle's region
  locks is never assumed. The precedence survey is in 2.2.1.10 (Micro Focus Fileshare: the server holds a dead client's
  locks until it rolls the client back at the first contending access; IBM: a failed holder's locks become RETAINED locks
  answering LOCKED until backout — this engine keeps them in the file). An INPUT connector writes nothing, tests the
  holdings like any READ not IGNORING LOCK, and reads the file as it stands.
- `FileRegistry.CloseAll` at normal termination commits every transaction of the run unit (§9.1.18.5 first sentence) and
  promotes every open store. The runtime's ABNORMAL-termination path (`RunUnit`'s fatal-exception and unhandled-exception
  exit, §14.6.12 and §14.6.13.1.3 item 8) executes the file-only rollback — `FileRegistry.Rollback()` without the data-item
  restore — before the process exits; what it cannot reach (a kill) is the dead-transaction step above.
- `KeyedConnector.CloseCore` under commit control PROMOTES like every CLOSE (R5), releases no record lock and keeps the handle
  in `ClosedUnderCommit`; a ROLLBACK after that CLOSE restores the state at the last COMMIT from the UNDO tree (§14.9.36.4
  GR3), which no promotion changes. There is no "no promotion under commit control" rule and no checkpoint exemption.

## Tests

- COMMIT makes the statements since the last COMMIT survive a simulated power loss (the memory medium loses unsynced writes);
  without COMMIT a process death is rolled back at the first writable statement afterwards — another live run unit's next
  record statement, or the next writable OPEN (§9.1.18.5) — and an INPUT OPEN in the interval reads the file as it stands.
- The dead owner (2.2.1.12's last lock scenario): A under APPLY COMMIT DELETEs K5 (unique alternate key X) with no READ and is
  killed (the test medium and lock host release A's handle: its liveness byte; its K5 and X holdings stay in the file,
  2.2.1.10); B, live, not under commit control, WRITEs K5
  → the entry rolls A back first and the WRITE answers '22'; B WRITEs K7 with X → '22'; B READs K5 → the record as at A's
  last COMMIT; the same with A's REWRITE of K1's unique key X → Y and B's WRITE of K2 with X; a third run unit's INPUT
  reader between the death and B's statement finds K5 absent, after it present; with A alive and idle B's WRITE K5 → '51'.
- COMMIT at each of its points (2.2.1.16, rounds 4 and 5): the owner killed, or REFUSED by the medium (alive, '30'), at
  the claim, at sync 1, at the slot write, at sync 2 and in the retirement. Refused or killed before the slot write: the
  transaction is intact — the next entry (another run unit's statement, or the owner's own unconditional ROLLBACK) unwinds
  the claim and the rollback restores every before-image — and the COMMIT was reported unsuccessful. Sync 2 landed: the
  COMMIT was reported successful (or the owner died untold) and the next entry completes the retirement. Sync 2 REFUSED
  (R5-1): the COMMIT reverses under its own mutex hold and reports failure, and afterwards — through the owner's
  unconditional ROLLBACK, a second run unit's statement injected between the COMMIT's return and that ROLLBACK (it meets
  the reversed state, never a landed COMMIT to complete), the next OPEN, and a power loss keeping any subset of {the
  COMMIT's slot, the reversal's pages, the reversal's slot} — the records are as at the previous COMMIT and the HOLDINGS
  and TRANSACTIONS trees hold nothing of t. The reversal's page write, or its promotion's sync, refused too: the COMMIT
  reports failure, every ROLLBACK reports '30' while the sync is refused and success once one lands, and no run reports a
  ROLLBACK successful while the medium holds the COMMIT's slot as its highest valid slot; the owner killed in either state
  is rolled back in the first and left committed in the second. The power-loss mode gives the same outcomes through R6 (a
  DESCENDANT with the flag, unwound by the fence; the PROMOTION SOURCE, finished by it). In no run is a COMMIT reported
  failed with its transaction committed, or reported successful and then rolled back, or a ROLLBACK reported successful
  and its transaction found committed by any later OPEN.
- What the program is told: a COMMIT refused at each region, and a ROLLBACK refused on a marked file, raise
  EC-I-O-PERMANENT-ERROR for the refused file with '30' in its status item, with and without a USE declarative and a FILE
  STATUS item, and item 8's unconditional ROLLBACK runs; a COMMIT over two files refused at the second leaves the first
  committed (its records survive a simulated power loss) and the second at the previous COMMIT after that ROLLBACK.
- Every holding is found (R5-2): A REWRITEs K1's unique key X → Y then Y → Z, and A WRITEs K8 with W then DELETEs K8, then
  COMMITs (or ROLLBACKs): B's WRITE with Y, and with W, answers '00' (no '51', no loop) and the HOLDINGS tree is EMPTY; the
  same with A killed instead and B's statement rolling A back; and the drift test that after EVERY statement of every
  scenario the HOLDINGS tree's key set equals the union of the UNDO trees' key sets, walked by the test through the trees,
  not through the engine's own enumeration.
- The holder's death at every point of another statement (round 4, R4-1): A (DELETE K5, unique value X, idle) killed after
