# PB3337 — COMMIT and ROLLBACK in the runtime

Implement FROM `docs/rearchitecture/DESIGN-runtime-library.md` §2.2.1.10 and §2.2.1.6 (R5, R6). Follows PB3335 (the engine
complete, `KeyedConnector.cs` and `FileRegistry.cs` settled). The compiler half is PB3338; this group makes the runtime able to
honour it, exercised directly by unit tests until PB3338 emits the calls.

## Mechanism

- `FileRegistry.RegisterCommitControl(name)` (called by the generated activation of a runtime element whose APPLY COMMIT clause
  names the connector, §12.4.6.3.4 GR5's activation): the connector's OPEN sets the meta's UNDER COMMIT CONTROL bit, registers the
  §9.1.16 implicit posture `LOCK MODE IS AUTOMATIC WITH LOCK ON MULTIPLE RECORDS` with `PhysicalFileTable`, and marks that its
  promotions are COMMIT, CLOSE and termination only (no checkpoint).
- `FileRegistry.Commit()` (§14.9.7.4 GR3): for every open store under commit control, `PagedFile.Promote`; then
  `PhysicalFileTable.ReleaseAllForConnector` for each such connector; GR4: a connector under commit control that was CLOSEd keeps
  its handle (the §9.1.15 file lock, "the file lock is removed by the COMMIT statement") in a `ClosedUnderCommit` set and releases
  it here. Status items are the compiler's (PB3338).
- `FileRegistry.Rollback()` (§14.9.36.4 GR3): for every store under commit control, `PagedFile.Rollback` (drop the cache, copy the
  committed slot over the work slot, apply R6's second branch to the ledger), release the record locks, release the kept handles
  of connectors closed since the last COMMIT; the §9.1.15 last sentence's case (a file not open at the previous commit and opened
  since) releases its file lock.
- `FileRegistry.CloseAll` at normal termination promotes every open store (§9.1.18.5 first sentence); abnormal termination writes
  nothing, and the next OPEN's adoption rule (R6) rolls the file back to its committed slot because the bit is set.
- `KeyedConnector.CloseCore` under commit control does NOT promote (R5 as corrected in the design on 2026-10-17): it writes
  the work meta, releases nothing and keeps the handle in `ClosedUnderCommit`; only COMMIT and the run unit's normal
  termination promote such a store, so a ROLLBACK after a CLOSE restores the state at the last COMMIT (§14.9.36.4 GR3). A
  store not under commit control keeps PB3331's CLOSE promotion and checkpoint policy untouched.

## Tests

- COMMIT makes the statements since the last COMMIT survive a simulated power loss (the memory medium loses unsynced writes);
  without COMMIT they do not, and a process death without COMMIT is rolled back at the next OPEN (§9.1.18.5).
- ROLLBACK restores the file to the last COMMIT in O(1) page I/O and releases every record lock; a second run unit sees the
  rolled-back state at its next statement.
- A file CLOSEd under commit control is still refused to a `NO OTHER` opener in another run unit until COMMIT ('61'); COMMIT
  releases it.
- A file not under commit control is unaffected: its checkpoint policy and CLOSE promotion stay as PB3331 witnessed.

## Done when

gate GREEN; PB3338 can emit the calls.
