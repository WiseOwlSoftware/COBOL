## Finding — `sort-statement-p1` (under-rejects; rows `SR-14.9.40.3-6`, `SR-14.9.40.3-14`)

**Mechanism.** Neither SORT format screens a key's CLASS or SHAPE: SortAddFileKeys and SortBindTable classify the key (CollatingSelection.Of) but never refuse boolean/pointer classes or occurs-depending / variable-length groups

**Repro.** Format 1: SD SW 01 SR. 05 K1 PIC X. 05 KB PIC 1 USAGE BIT. -> `SORT SW ASCENDING KB USING IN1 GIVING OU1` rc 0 (probe k6oneKB); `SD SW. 01 SP USAGE POINTER.` + `SORT SW ASCENDING SP ...` rc 0 (k6p01); key KODO = group holding `KODE PIC X OCCURS 1 TO 3 DEPENDING ON CNT` rc 0 (k6oneKODO). Format 2: `SORT TE ASCENDING TB` (TB PIC 1 USAGE BIT) rc 0 (t14cbool); `SORT VE ASCENDING VG` (VG a group holding only `VD PIC X DYNAMIC LENGTH`) rc 0 (t14vg). All --std 2023.

**Expected from the spec.** §14.9.40.3 SR6 c) (no key of class boolean, message-tag, object or pointer) and d) (no variable-length group, occurs-depending-on data item, dynamic-length elementary item or item under a dynamic-capacity table); SR14 c) (no key of class boolean, object or pointer) and d) (no key referencing a variable-length group or occurs-depending group item). Every probe is a compile-time error, named by its arm.

**Observed / reasoning.** SortAddFileKeys' only shape test is `len <= 0` ('has no character image'), which happens to catch dynamic-length items and true variable-length groups (the PB1052 shape) but not an ODO group or a boolean/pointer leaf, whose images exist; SortBindTable has no test at all. kb/Work PB1052 (open) owns SR-14.9.40.3-6's d) arm but records it as a diagnostic-quality defect — the ODO-group arm is an under-rejection and should be added to it; the c) arms and the Format-2 SR14 c)/d) arms are unowned. The shape that makes the next case automatic is ONE key-admissibility predicate (class + shape, parameterised by the format's arm list) called from SortAddFileKeys, SortBindTable (both the KEY-phrase and GR21 paths) and MERGE's §14.9.24.3 twin.

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SortBinder.cs#SortAddFileKeys (lines 469-478); src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SortBinder.cs#SortBindTable (lines 202-237)

## Finding — `sort-statement-p1` (under-rejects; rows `SR-14.9.40.3-6`)

**Mechanism.** RecordLayout.OffsetInRecord's REDEFINES-class branch returns target.ClassOffset without OffsetOf's OCCURS bail, so in any SD with more than one 01 a key under OCCURS is accepted and its written subscript is discarded

**Repro.** SD SW. 01 SR. 05 K1 PIC X. 05 KOCC PIC X OCCURS 2. 01 SR2 PIC X(3). INPUT PROCEDURE releases "a19","b21","c35"; `SORT SW ASCENDING KOCC(2) INPUT PROCEDURE IP OUTPUT PROCEDURE OP` -> --std 2023 rc 0, run prints a19 / b21 / c35 (probe k6multi) — ordered on KOCC(1). Remove the second 01 and the same statement is rejected COBOLNET1757 'SR6b/SR6f' (k6simp).

**Expected from the spec.** §14.9.40.3 SR6 b) 'Key data names shall not be subject to any OCCURS clauses' and f) (no key described by or subordinate to an entry with OCCURS): the statement is a compile-time error however many record descriptions the SD has (SR6 e) makes a second 01 irrelevant to which items may be keys).

**Observed / reasoning.** Every 01 of a multi-record SD is a member of the synthesized REDEFINES class (PB836), so SortAddFileKeys' `OffsetInRecord(root, item) is null` guard reaches the `target.Class is { } cls` branch, which returns ClassOffset (the first occurrence's position) and never walks ancestors for OCCURS; KeyWindowOf then accepts the window. The OCCURS predicate belongs in ONE place ahead of both branches (it is a property of the data description, as SortBinder.KeyUnderInnerOccurs already is for Format 2), not inside the plain walk only. The indexed RECORD KEY path reads the same helper and should be swept (§12.4.5.12 SR1).

**Code site.** src/Cobol.Net.Compiler/Binding/Model/RecordLayout.cs#OffsetInRecord (lines 162-172); src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SortBinder.cs#SortAddFileKeys (line 462)

## Finding — `sort-statement-p1` (under-rejects; rows `SR-14.9.40.3-14`)

**Mechanism.** A Format-2 table-SORT key's subscript is dropped by DataBinder.KeyReference instead of being refused

**Repro.** 01 TBL. 05 TE OCCURS 3. 10 TK PIC 9. 10 TV PIC X. MOVE "3a" TO TE(1) MOVE "1b" TO TE(2) MOVE "2c" TO TE(3). `SORT TE ASCENDING TK(1)` DISPLAY TK(1) TK(2) TK(3) -> --std 2023 rc 0, prints 123 (probe t14b), exactly as `SORT TE ASCENDING TK`.

**Expected from the spec.** §14.9.40.3 SR14 b) 'Key data names shall not be subscripted' — a compile-time error. (§8.4.2.3.3 SR5 d) exempts the table-SORT KEY phrase from the obligation to subscript; SR14 b) turns the exemption into a prohibition.)

**Observed / reasoning.** SortBindTable resolves each key via `DataBinder.KeyReference(dref)` -> (baseName, quals) and SubtreeCandidates; the dataReference's subscript list is never inspected, so the written subscript vanishes without a diagnostic.

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SortBinder.cs#SortBindTable (lines 202-213)

under OCCURS is told SR6 b)/f), not COBOLNET2270's "a table element needs a subscript" (true, and beside the point).
