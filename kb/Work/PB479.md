# PB479 — OPEN — the denominator is short by every "shall" the standard did not number

Found 2026-09-04 by the `PB204` implementer, which closed §2023:8.5.1.12's three conditions and then looked for
the rows that IMPORT them and found half of them missing. Re-derived on this tree for this note.

## The measurement

`tests/version-matrix/inventory/` holds `SR-14.8.2.2-1` and `SR-14.8.2.2-2` — the two
NUMBERED rules of §2023:14.8.2.2 — and **no row at all for §2023:14.8.3.2**. Yet both clauses carry obligations:

```
python scripts/spec/cite.py --check 14.8.2.2 "If either the formal parameter or the argument is a variable length group, the formal parameter and the argument shall be compatible, as described in 8.5.1.12, Variable-length groups."
OK  §2023:14.8.2.2   (Group items)                      <- no ordinal: unnumbered prose, no row
python scripts/spec/cite.py --check 14.8.3.2 "If either the sending or the receiving operand is a variable length group, the sending operand and the receiving operand shall be compatible"
OK  §2023:14.8.3.2   (Group items)                      <- no ordinal: unnumbered prose, no row
python scripts/spec/cite.py --check 14.8.2.2 "If the argument is passed by content, the conformance rules are the same as for a MOVE statement"
OK  §2023:14.8.2.2 2)  (Group items)                    <- numbered: has a row
```

`scripts/spec/extract_rule_catalog.py` lifts a rule from a numbered heading (`## 8.4.3.13.3 Syntax rules`)
and its numbered items (`1)`, `a)`, nested `1.`); a "shall" sentence that stands as plain paragraph text under
a rule heading is not a catalog entry, so `build_inventory.py` never mints a row for it. The consequence is
the one the burn-down metric cannot report on itself: PB204 implemented §2023:14.8.3.2's obligation completely,
with a diagnostic (COBOL1736), goldens and a negative witness, and the GAP did not move for it because
there was nothing to close.

## Why it is a class

Every clause whose obligations are written as prose rather than as a numbered list is affected. `PB284`
measured a different shortening of the same denominator (a heading spelled "General forms", `## FORMAT n`
headings truncating 30 rules) and `PB222` measured what `cite.py` does with unnumbered prose (it stamps the
NEAREST preceding ordinal); this note is the third face of the same fact — the population the burn-down is
measured against is the set of things the extractor RECOGNISES, not the set of things the standard REQUIRES.

## What closes it

1. Measure the class: over `specs/ISO_COBOL_2023.md`, every sentence containing "shall" (and "may"/"is
   permitted" where §2023:5.3 makes those obligations) that lies under a rule heading and is not under a numbered
   marker; report the count per clause. That number is the honest correction to the denominator, and it is
   owner-visible: the GAP goes UP.
2. Decide the row shape with the owner (a bare question): mint rows for unnumbered obligations as
   `<kind>-<clause>-p<n>` (paragraph-ordinal) so the ids are stable and `cite.py`'s ordinal stamping (`PB222`)
   is not inherited into them.
3. Extend `extract_rule_catalog.py` to lift them, re-run `build_inventory.py` (verdicts preserved), and add a
   drift test that the two clauses above have rows — the failure branch fired once by reverting the lift.
4. Re-verdict the new §2023:14.8.2.2 and §2023:14.8.3.2 rows on PB204's evidence.

paragraph). `audit_catalog_coverage.py` and `CatalogCoverageDriftTests.ProseClauses_AreHeldSentenceForSentence` hold an
admitted clause's rows to its text. What this note still owns: step 1 (MEASURE the class — every "shall" in unnumbered
prose under a rule heading, per clause) and the admissions it implies, which are now a data edit per clause with a
recorded reason and a kind (SR or GR per §2023:5.3.1). §2023:14.8.2.2's variable-length-group sentence and §2023:14.8.3.2 are
unnumbered paragraphs under a rule heading, a DIFFERENT shape (a paragraph beside numbered rules in one block) that
`prose_paragraphs` does not yet lift. The sibling concept clauses of §2023:9.1 (§2023:9.1.1–§2023:9.1.10, §2023:9.1.19–§2023:9.1.22) are the same
