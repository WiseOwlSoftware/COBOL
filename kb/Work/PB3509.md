# PB3509 — a carrier's DONE report supersedes the carried branch's FINDINGS report

**Sites:** `scripts/orchestrator/plan_wave.py` (`add_closed_notes`, `closed_by_branch`, the `newest` loop in `plan`),
`scripts/orchestrator/test_plan_wave.py`

## What happens
Wave 1144 (2026-10-22 ~00:05, `plan_wave.py --from-budget --borrow-days 1`) planned 0 groups and printed:

```
awaiting landing (excluded; an `enqueue` unit first): fix-pb3504-antlr-sll-merge-cache: PB3489
```

The branch survey (`prune_worktrees.py`) at the same moment:

```
IN FLIGHT fix-pb3504-antlr-sll-merge-cache — carries fix-pb3489-nested-fn-hang (PB3489), whose review FINDINGS (1)
at 37aafe9c7 are unanswered (round 1 of review-fix-pb3489-nested-fn-hang.jsonl, its last verdict): it lands once
that note's finisher has answered them and landed it (kb/Work PB3381)
```

So the survey waits for PB3489's review finisher, and the planner will never plan it:

1. `add_closed_notes` completes every unlanded report's `notes` with `closed_by_branch(branch)`: every `kb/Work` note
   the branch changed since origin/main whose status on the branch is terminal. fix-pb3504 MERGED fix-pb3489 (its
   same-file predecessor), so PB3489's terminal note is on fix-pb3504 and PB3489 joins the w1141g-PB3504 report's notes.
2. In `plan`, `newest[nid]` takes the newest report naming each lead. The PB3504 report is newer than the
   w1141e-PB3489 FINDINGS report, so `newest["PB3489"]` is the carrier's DONE report.
3. That report is DONE with no findings, so PB3489 lands in `awaiting` under fix-pb3504, and the FINDINGS arm
   (`finisher_pred`'s review arm) never sees the w1141e report.

The comment above `leads` already states the intended rule: "a branch that merely contains it (branch_carrier) does
not [supersede the FINDINGS report], and is named in its finisher's pred instead (review R1-1, R1-2)". The
closed-notes completion (kb/Work PB3473, R2-1) broke it for exactly the same-file-successor case PB3381 is about.

Today fix-pb3489 is still IN FLIGHT by `--min-age` (touched 119 min before the plan), which alone would hold its
finisher (the PB3311 arm) — but that arm also reads `newest`, so once the branch settles nothing changes: the note
stays in `awaiting landing`, the survey keeps holding fix-pb3504, and neither branch ever lands.

## Expected
A note's FINDINGS report is superseded only by a later report ON THE FINDINGS BRANCH'S OWN LINE (its review finisher's
report), never by a carrier's report. `closed_by_branch` should not credit a carrier with notes whose closing commit it
only inherited from a merged predecessor that is not yet landed and carries unanswered findings (or: `newest` skips a
report for a note when that report's branch merely contains another unlanded report's branch naming the note). The
fix lands with a `test_plan_wave.py` case reproducing this exact shape: predecessor DONE + FINDINGS stamp, successor
DONE + CLEAN containing it → the predecessor's review finisher is planned, and the successor is listed waiting on it.

## Sibling sweep owed
Every other reader of `Report.notes` after `add_closed_notes` (the dispatch hold, the drain arm, the unlanded-branch
arm): each may let a carrier absorb a predecessor's unfinished (SPLIT, FINDINGS) note the same way.
