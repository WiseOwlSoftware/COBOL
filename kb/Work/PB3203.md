## Landed (wave 1090 group A, with PB3242, branch `worktree-wf_b14ea906-c69-1`)

The copies named here were already partly gone on the base (PB2807's branch routed the landing check through
`plan_wave.computed_file_set`; `computed_declared` and `record_dispatch_main` no longer existed), but the split policy
remained: `member_callers(repo)` without a cache read the newest COMMITTED index for the landing check and the spec
renderer, `member_callers(REPO, cdir / "member-index", ...)` THE index of the tree for the planner, and
`computed_file_set` and `campaign_clusters` each built fix_clusters' `source_index` from `cfg["ext"]`, which
`landing_check.partitioned` parsed a fourth time. Now ONE function, `plan_wave.declared_sets(repo, policy)`, computes
a note's declared set on ONE explicit `plan_wave.IndexPolicy` (THE index of the tree, `IndexPolicy.of(<coord>)`), and
the planner (`main`), the spec renderer (`make_dispatch_specs.record`) and the landing check (`main`) all pass it;
`member_callers` and `plan_wave.note_file_set` are deleted, and the campaign domain is parsed once
(`coord.CampaignDomain`, whose `partitioned` replaces `landing_check.partitioned`, deleted). The landing check's
regeneration bound is measured and recorded in DESIGN-architecture-review §8.7: 110 s on a cold worktree, paid only
for R3 work no ledger entry records. The §4 oracle was not run: the diff changes scripts and docs only, no input of
the compiler's output.
