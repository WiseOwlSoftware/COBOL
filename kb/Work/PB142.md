# PB142 — the RETRY phrase's conflict-status class rule

**Landed.** Rows `GR-14.9.10.4-6` and `GR-14.9.10.4-15` flipped DIVERGES → CONFORMS. Design:
`docs/COBOLNET_FILES_DESIGN.md` **D8** (the deep-dive had ZERO occurrences of "RETRY" before this, although the
phrase has shipped since Phase 4d) and `docs/COBOLNET_NUMERIC_DESIGN.md` (the round-up landing). Determinations:
`docs/CONFORMANCE.md` §7 Annex A.1 items **165**, **166** and **109**.

## The rule, derived before any code was read

§14.7.9.3 GR4 scopes the whole discipline: it engages only "if the I/O operation is unsuccessful on the first
attempt **because of a file sharing conflict condition or a record operation conflict condition**". When it does,
GR4a and the clause's closing paragraph give the *same* landing — "the appropriate value is placed in the I-O
status … according to the rules for 9.1.13". The status is therefore **a function of the conflict's class**.

§9.1.13.9 (file sharing) defines exactly two values, `61` for OPEN and `62` for DELETE FILE, and **no deadlock
value**. §9.1.13.8 item 2's `52` is a **record**-conflict value whose detection conditions the implementor defines.
§14.9.10.4 GR15b is imperative for `62` ("*The* value … is placed") where the record twin GR6b says only "*A*
value". The asymmetry is the whole design.

## What was measured, and what was fixed

Three defects in one mechanism, `FileRegistry.RetryLoop`. Probes are CLI compile-and-run, before/after:

| probe | before | after | rule |
|---|---|---|---|
| `DELETE FILE F-B RETRY FOREVER` (file open by another connector) | `52` | `62` | §9.1.13.9 item 2 |
| `DELETE FILE F-B RETRY FOR 0 SECONDS` | `52` | `62` | GR4a's zero screen |
| `DELETE FILE F-B RETRY FOR 30 SECONDS` | `52` | `62` | GR2's clamp |
| `OPEN … SHARING WITH NO OTHER RETRY FOREVER` (Table-19 conflict) | `52` | `61` | §9.1.13.9 item 1 |
| `OPEN … SHARING WITH NO OTHER RETRY FOR 0/30 SECONDS` | `52` | `61` | GR4a / GR2 |
| `OPEN INPUT RETRY FOREVER` of an **absent** file | `52` | `35` | **GR4 — not a conflict at all** |

1. **The Seconds/Forever arm never read its amount** and manufactured `FileStatusCode.Deadlock` in place of
   whatever conflict the attempt produced — the classic two-arm shape, with the `Times` arm already correct.
2. **The OPEN arm was the sibling the filed note did not name.** No fixture and no unit test anywhere wrote
   `OPEN` with a RETRY phrase, so it was silently wrong and unpinned.
3. ⚠ **NEWLY FOUND DURING THE FIX, not in the note or the contract.** `RetryLoop` retried and deadlock-bailed on
   *any* non-Success status. GR4 scopes the discipline to the two conflict conditions, so an OPEN of an absent
   file — status `35`, not a conflict — became `52`. This is the widest-reach arm of the three: it needs no
   sharing setup at all, only a RETRY phrase and a missing file. Found by asking what else the attempt closure
   could return, then probing it rather than reasoning about it.

## Why it was a WRONG-ANSWER defect and not two cosmetic digits

§9.1.13.1 keys the exception-name on the status's first digit — `5` → `EC-I-O-RECORD-OPERATION`, `6` →
`EC-I-O-FILE-SHARING`, `3` → `EC-I-O-PERMANENT-ERROR` (`ExceptionCatalog.EcForIoStatus`). A manufactured `52`
therefore raised the **wrong condition**, so a USE declarative or exception-checking PERFORM keyed on the right one
silently did not fire. `2023/pb142_retry_conflict_class_ec` is that handler, and it asserts the exception-name, not
only the status.

## The fix (root cause, one place)

`RetryLoop` now gates on `IsConflict` (§9.1.13.1's own first-digit classification) and routes **every** landing
through the private `ExhaustionStatus`, which returns the conflict's own status with exactly one documented
exception: `RETRY FOREVER` on a record lock is the §9.1.13.8 item 2 deadlock (A.1 item 109). Its six callers
inherit the rule instead of each judging for itself. The dead `if (status == Deadlock) SetStatusOf(…)` line at the
OPEN site is deleted, not left. **Class-scoped, not a blanket removal of `52`**: `2002/file_sharing_seq`
(`READD5=52`) and `2002/file_sharing_mutate` (`REWQFV=52`) — both `RETRY FOREVER` on a *record* conflict — stay
green, which is the proof.

**The A.1 item 166 determination** (maximum meaningful value of arithmetic-expression-2 = **0**, picture
`9(1)V9(0)`) is what makes `RETRY FOR 0 SECONDS` and `RETRY FOR 30 SECONDS` agree by ONE rule rather than by a
special case. Its ground is structural: every lock here is held by a file connector of the executing run unit,
which cannot release while this statement runs, so no positive timeout can change the outcome. ⚠ Recorded in
CONFORMANCE.md §7 *with its ground* so the next maintainer does not "fix" it into a `Thread.Sleep` and hang a
program on a guaranteed failure.

## PB142-B — the round-up, extracted rather than re-derived

§14.7.9.3 GR1 rounds the TIMES count **up to the next whole number**. `SequentialIoEmitter.RetryAmount` rendered
`NumericRenderer.Align(…, 0)`, whose every lane passes `CobolRounding.Truncation`, so `RETRY 1.5 TIMES` emitted 1
re-attempt and `RETRY 0.5 TIMES` emitted 0 — silently degrading to the no-retry case. A grep of the standard for
"rounded up" returns **exactly two** normative sites: this one and ALLOCATE's §14.9.3.4 GR1, which already
implemented it correctly (kb/Work PB151). One rule, two places — so the fix is the extraction, not a second local
ceiling: `NumericRenderer.AlignRoundedUp` is now the one home and both clauses call it.

The mode is `CobolRounding.TowardGreater` (true ceiling), not PtrEmitter's former `AwayFromZero`, which agrees on
positives but rounds −1.5 to −2 where the rule requires −1; both clauses guard their own negatives, so the change
is behaviour-neutral today and simply correct at the next site. ALLOCATE's native-float lane keeps
`CobolPtr.AllocateReal` — a **named** exemption, because it fuses the same ceiling with GR2's ≤ 0 ⇒ NULL and the
storage-not-available outcomes only that statement defines. `NumericRoundUpSiteDriftTests` is the drift test and
was **proven to fail** (pointing `RetryTimes` back at `Align` makes it red by name) before it was trusted.

⛔ **No compile-time screen was added, deliberately.** The original note's "BindRetry adds no integrality/range
check" reads as an ask for a diagnostic. §14.7.9 has only 14.7.9.1/.2/.3 — General, General format, General rules —
and **no Syntax rules clause at all**, so a non-integer or out-of-range arithmetic-expression is LEGAL SOURCE that
GR1/GR2/GR4a define at run time. A screen would be a `rejects_legal_source` regression. Probed: `RETRY 1.5 TIMES`,
`RETRY 0.5 TIMES` and `RETRY WS-N TIMES` all compile and run.
