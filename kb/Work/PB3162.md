# PB3162 — SET binder vs ActivationRelations.MaySet on restricted program-pointers

Source: `E:\COBOL-coord\scratch\reports\w1078b-PB3101-report.md` ("New defects"). PLAUSIBLE, NOT PROBED: no repro exists; the first step is to write one.

- `SetBinder.PointerAssignmentReason` (`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SetBinder.cs:667-682`) passes restricted program-pointers through `PrototypeSignatures.Same`.
- `ActivationRelations.MaySet` compares `RestrictionIdentity` ("TO p" against "TO q"), so it refuses an argument that a SET of the same pair admits.
- Rule as the reporter cites it: §14.8.2.3.3 SET paragraph; §14.9.39.3 SR22 (not re-checked by the clerk; run `cite.py --check` before use).
- Shares its root with PB2464 / PB2495 (a pointer's signature identity) and PB3101 (bind-time vs run-time conformance).

## Re-filed as a defect (analyses sweep, 2026-10-23)

Adjudicated read-only by an Opus cobol-adjudicator on main e7cf38ce4; accepted by the Mythos session.

For restricted program-pointers whose prototypes have no compile-time signature, the compiler's SET rule and the runtime's argument rule give opposite answers for the same pair. SetBinder.PointerAssignmentReason (SetBinder.cs:699-714) compares the prototypes through PrototypeSignatures.Same, which admits a null signature (§12.3.8.4 GR10 c: resolved by the run unit). ActivationRelations.MaySet (src/Cobol.Net.Runtime/Control/ActivationRelations.cs:589-596) compares ActivationDescription.Clauses, which for an unresolved prototype is the pointer's own prototype NAME (DataBinder.ResolveRestrictedPrototypes keeps the name as identity), so 'TO X3162A' never equals 'TO X3162B'. Repro t3162.cob: SET PB TO PA succeeds; passing PA BY REFERENCE (prototype CALL) or BY CONTENT (dynamic CALL) to a TYPE TB formal is EC-PROGRAM-ARG-MISMATCH (fatal under checking). Expected (§14.8.2.3.3 r2; §14.8.2.3.2 'same type'; §14.9.39.3 SR22; §13.18.60.4 GR25 types a program-pointer by its prototype's SIGNATURE): one rule for both paths. Either both defer an unresolved signature to the execution-time resolution, or both compare the signatures the run unit resolves. Fix in the one relation that PB2464/PB2495/PB3101 already share (a pointer's signature identity), plus a golden for both paths.

Evidence: Probe probes/pb3162/t3162.cob (--std 2014, checking on) on a main-equivalent build: TA/TB are TYPEDEF program-pointers restricted to X3162A/X3162B, two REPOSITORY prototypes with no definition in the compilation group (§12.3.8.4 GR10 c), so neither has a compile-time signature. SET PB TO PA is admitted ('set ok'), but CALL U3162 USING BY REFERENCE PA and CALL 'U3162' USING BY CONTENT PA, whose formal is TYPE TB, both raise EC-PROGRAM-ARG-MISMATCH. §14.8.2.3.3 r2 makes the BY CONTENT conformance for a pointer formal 'the same as if a SET statement were performed', so the two verdicts must agree.

Rule: §14.8.2.3.3 r2 (checked); §14.8.2.3.2 (checked); §14.9.39.3 SR22 (checked); §12.3.8.4 GR10 c) (checked)

## Landed (wave 20261032, group A)

Re-probed on the branch's own build: `t3162.cob` (--std 2014, checking on) printed `set ok`, then
`call exc EC-PROGRAM-ARG-MISMATCH` (prototype CALL, BY REFERENCE) and `dyn call exc EC-PROGRAM-ARG-MISMATCH`
(dynamic CALL, BY CONTENT).

**Root.** Two relations answered one question. The SET lane (`SetBinder.PointerAssignmentReason` and every other SET
arm) asks `PrototypeSignatures.Same`, which lets an unresolved signature conform (§12.3.8.4 GR10 c)); the description
lane (`ActivationRelations.MaySet`, which §14.8.2.3.3's BY CONTENT rule reaches, and the BY REFERENCE pointer arm, at
bind time and run time alike) compared the restriction identities exactly, and an unresolved prototype's identity was
its own name, so two of them never matched. **Fix.** An unresolved prototype's identity is now MARKED:
`PrototypeSignatures.ExternalIdentity` (`ActivationDescription.ExternalRestrictionPrefix` + the folded name), given by
`PrototypeSignatureClasses` for a null signature, by `UnclassifiedIdentity` and by
`StatementBinder.ProgramRestrictionIdentityOf` for a name the tables do not hold; and the description lane's pointer
comparisons go through ONE helper, `ActivationRelations.SamePointerRestriction`: equal restrictions, or two restricted
pointers either of which is external. An unrestricted pointer still never matches a restricted one. The §8.5.3.1
equivalence and its key keep exact identities (an equivalence must stay transitive); COBOLNET_OO_DESIGN.md says so.
The function-pointer arm of `MaySet` (SR20) takes the same helper: the sibling with the same disagreement.

t3162 now prints `set ok`, `call ok`, `dyn call ok`. **Golden** `2002/pb3162_external_prototype_pointer_set_and_pass`
(SET, BY REFERENCE and BY CONTENT agree; the control, an unrestricted pointer BY CONTENT into the restricted formal,
still raises EC-PROGRAM-ARG-MISMATCH).
