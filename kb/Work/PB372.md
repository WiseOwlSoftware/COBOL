# PB372 — what the dossier could not show, measured across fifteen subjects

> Raised by adjudication batch b1 (OPEN · READ · RELEASE · RETURN · START · UNLOCK · USE, 184 rules across 15
> subject files, 2026-09-02). Every item below was reported INDEPENDENTLY by at least two subjects; the ones
> reported by five or more are marked ⛔. `kb/Work/PB286` (landed) owned the generator's slug defect and is not a
> live home for these; this note is.

## ⛔ 1. A citation regex cannot see an absence, and an absence is what a conformance review is for

The `source.citing` selector matches files that CITE the subject's clause. **Code that fails to implement a rule
cites nothing**, so the largest finding in a subject is routinely invisible to the dossier:

* `SequentialIoBinder.BindRead` never reads `readDirection()` / `readKey()` / `readInvalidKey()` — three dropped
  phrases, four inventory rows (**PB334**).
* `SequentialConnector.cs` implements no `Start` member at all — the whole sequential START arm (**PB352**).
* `SequentialIoEmitter.EmitFileRegistration` drops a record-less FD; `FileRegistry.RetryLoop` lives under
  §14.7.9 (**PB345**, **PB346**).
* `useStatement` is a plain alternative of `CobolParserCore.g4#statement` and `StatementBinder`'s
  `_ => new BoundUnsupported(...)` fallback carries no §14.9.49 citation, yet together they ARE the SR1 defect
  (**PB361**).
* Four of OPEN's nine syntax rules have NO code; establishing that took a hand sweep of every `BoundOpenMode`,
  `ReportNames`, `.Linage`, `EXTEND()` and `REWIND` site in `src/Cobol.Net.*` (**PB318**).

**Two mechanical probes were proposed by the adjudicators and both are buildable.** (a) For each grammar rule the
subject's statement references, name the bind-site token accessor that READS it, or report *no consumer found* —
which surfaces every dropped phrase without any citation. (b) For each rule, extract the nouns its text names
(REPORT clause, LINAGE clause, access mode, NO REWIND) and search for THOSE, not for the clause number.

## ⛔ 2. The tests list does not say which tests can CLOSE a row

Two distinct traps, reported by six subjects:

* **Legacy differentials read exactly like spec tests.** Every method in `KeyedIoDifferentialTests`,
  `UseDeclarativeDifferentialTests`, `FileIoDifferentialTests` and most of `InterProgramFileDifferentialTests`
  routes through `DifferentialGolden.Assert`, whose golden under `tests/differential/` is **baked from a legacy
  run**. Their XML docs quote real §/GR, so the dossier presents them as coverage. They are the ONLY tests
  covering START's GR8 and GR9.
* **A whole project cannot close anything.** `tests/CobolSharp.Tests.Integration/` (SpecFixTests, FileIoSpecTests,
  ConformanceTests, FileIOTests) tests the LEGACY engine and matches no `test-ref` form in
  `inventory-schema.json`. Four subjects lost time reading it, and one nearly recorded a ref from it.

**Fix:** mark every citing test with its ORACLE (spec-derived / differential-baked / legacy-project) and whether
its project is a legal `test-ref` form. The schema already knows the forms.

## ⛔ 3. `determinations` keys on a § citation, so the rows that DECIDE a verdict are missed

`docs/CONFORMANCE.md` §5's Annex A.4 module table is what makes a rule live or vacuous, and it names modules, not
clauses. Missed rows that decided verdicts in this batch: `A.4.7 File sharing and record locking | Claimed`
(makes OPEN SR8, READ GR22 and every UNLOCK rule in-scope), `A.4.3 Commit and rollback | Not claimed` (decides
OPEN SR7, READ SR5, UNLOCK SR2), `A.4.8 | Not claimed` (decides OPEN SR9), `A.4.11 Report Writer | Partial`
(decides USE SR10/SR11), `§A.3 item 40 SOURCE phrase | Not claimed` (decides four START rows), `§2 row 39 READ
PREVIOUS | Claimed`. A §2 row spelling `14.9.27` without the section sign also defeated the prefix regex.

**And a determination the dossier DID return was stale** — `docs/CONFORMANCE.md` line 111, *the only 07 setter is
CLOSE REEL/UNIT*, untrue since PB141 (**PB317**). A determination a verdict may rest on needs a freshness check
against the code it names.

## ⛔ 4. `register` matches on `spec_refs` only, so a note whose subject is a MECHANISM is invisible

Nine subjects reported an empty or near-empty register block that was misleading. Missed live notes: `PB236` and
`PB237` (the `BoundUnsupported`-as-runtime-throw shape, which four batch-b1 subjects then re-found), `PB159` (the
OPEN citation-drift note, which already owned two of the six wrong clause numbers found here), `PB142`, `A2` (the
SR-enforcement census, which already names ASSIGN USING), `PB140`, `PB179`/`PB183`, and `PB144` — whose TITLE
names the missing SOURCE grammar verbatim while its `inventory_rows` list only §14.9.10 rows.

**Fix:** a second selector over note TITLES and BODIES, and a clause-PREFIX match (`14.9.30.4` matching a note
whose `spec_refs` says `14.9.30`) rather than string equality.

## 5. Truncation is silent about WHAT it dropped, and it dropped the load-bearing rule

`grammar.truncated: N` and `source.citing.truncated: 63` appear with no list. Measured casualties: `readKey` and
`retryPhrase` (the two rules READ's Format-2 ordering defect turns on); `recordKeyClause` and
`alternateKeyClause` (which decide whether record-key-name-1 is writable at all); `lockModeClause` (without which
OPEN SR8's consequent cannot be checked); `ProcedureTableBuilder.DeclHandlerEndPc`, whose own doc comment cites
§14.9.49.4 and which carries this batch's widest USE defect. The cap also spends slots on NOISE — the bare
keyword `START` matched `COMMENT_START` and a comment body; `RETURN` matched every `RETURNING` phrase of CALL.

**Fix:** match rule/token NAMES with word boundaries; prefer rules REFERENCED BY the subject's top-level rule
over lexer tokens; make the cap per-file; and always name what was dropped.

## 6. Annex A.1 / A.3 back-references are not harvested, and an unmet documentation obligation is invisible

The standard's own rules carry them — *(14.9.27, OPEN statement, General rule 10)* — so they are mechanically
extractable. Missed in this batch: A.1 item 129 (OPEN GR10), 130 (GR18), 131 (GR23), 52/76/77 (file sharing),
218 (the USE fatal-I-O action), A.3 items 30/33 (NO REWIND), 39 (READ PREVIOUS), 40 (the SOURCE phrase). Without
them a verdict cannot tell an undischarged REQUIRED documentation obligation from a satisfied one — which is
exactly what **PB322** now owns for six of them.

## 7. Four smaller shapes, each reported twice or more

* **`diagnostics` is empty on subjects with live diagnostics**, because the selector keys on `DIAGNOSTICS.md`
  rows carrying the clause rather than on the clause cited at the `Error()` call site. Missed: COBOLNET0862,
  0863, 0864, 0899, 0900, 1512, 1720, 0715, 0716, 0859, 0897.
* **`tests/version-matrix/constructs.json` is invisible** although it is the SOURCE of the
  `ConstructRegistry.g.cs` rows the dossier DOES list — a citation fixed in the generated file is regenerated
  away (**PB320** item 1).
* **The rule extractor glues the NEXT format heading onto the previous rule's text** (`GR-...-3` ends *FORMATS 1
  AND 2*, `GR-...-13` ends *FORMAT 4*), so a reader who trusts the extract mis-assigns every rule's format scope
  by one. It also mis-segments §14.9.30.4 GR21 badly: `L4.3`'s text absorbs thirteen distinct normative rules —
  two divergent and eleven conforming — under ONE inventory row, which no single verdict can carry honestly.
* **The pinned worktree cannot render the PDF** (`scripts/render-spec-page.py` and `clause_page.py` resolve
  `specs-private/` relative to their own tree), and the figure notes cite the printed FOLIO while the script
  takes the PDF page — a 30-page offset that sends a reader to a search page.

## The one that cost something

Three of the four NEEDS-OWNER-DECISION adjudications assert that `inventory-schema.json` carries exactly ONE
derived selector. **It carries seven**, and `commit-and-rollback-only` had already NAMED and considered their
rows. The dossier's inputs were built from a worktree pinned before the A.4 landing, and nothing in the dossier
records WHICH tree it was built from. **Stamping the pin sha into every dossier is one line and would have
prevented all four.** (**PB371** records the consequence.)

Every one of the 17 batch-b3 subjects reported dossier gaps, and they fall into FOUR shapes that recur across the whole batch rather than 17 unrelated complaints:
