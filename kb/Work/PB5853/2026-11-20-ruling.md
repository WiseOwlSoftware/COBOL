Mechanism: `src/WiseOwl.Cobol.Runtime/IO/ReportWriter.cs#PresentLine` begins with `if (target < 1) target = 1;`, at every edition and for paged and unpaged reports alike. It sets `LineCounter = target` after the clamp, so a computed line 0 is stored as 1, and every later relative line and the final LINE-COUNTER (GR6d) carry the +1. The clamp exists because the engine uses `_physLine == 0` as its "empty page" sentinel ("`_physLine == 0` IS that empty page, not a line zero to advance off"): line number 0 cannot be a real line while 0 also means "nothing printed yet". In this method the line number the text computes and the physical position the device stands at are one variable.

Fix shape: separate the two at the root. LINE-COUNTER and the page model carry the line number the rules compute (0 is legal in a report with no PAGE clause). The "nothing presented on this page/run yet" state becomes its own field, not the sentinel value 0 of `_physLine`/`DeviceLine`. Physical travel maps the computed line to the device: on an empty page the stream rests at the first physical line, so lines 0 and 1 both land there with no advance (the ADVANCING-ZERO determination's empty-page rule, `docs/conformance/4/ADVANCING-ZERO.md`). Every later line travels by its difference from the previous line. That keeps lc0's file byte-identical and changes only LINE-COUNTER. In a paged report a computed line below HEADING is already a syntax-rule violation (SR1 with SR8), so a paged report should keep whatever behaviour its own rules give, decided by its own text and not by this clamp. 2002/2014/2023 must each be read on their own text before their arms change. Goldens at `--std 85`: `lc0` (expect `LC1 0000000002`, `LC2 0000000004`, and the file above) and `rh0` (RH LINE PLUS 0: LC 0/2/4), with `lc1` as the unchanged control.

Reasoning: The text computes the line and leaves nothing to the implementor. INITIATE sets LINE-COUNTER to 0 (§1985:XIII.3.5.6 GR4), and the register's declared range starts at 0 (§1985:XIII.1.2.3). In an unpaged report, rule 4d adds integer-2 to LINE-COUNTER, and integer-2 "may be zero" (SR1). LINE-COUNTER "represents the line number on which the print line is presented" (GR6 of 3.5.6), and rule 6d makes the final setting that line. Reading B in the note relied on SR1's "outside the vertical subdivision of the page" sentence. That sentence fails here: SR1 speaks of the subdivision "as defined by the PAGE clause", and SR8 defines subdivisions only "when the PAGE clause is specified", so an unpaged report has none to fall outside. The report heading's rule 3d computes from "LINE-COUNTER (in this case, zero)" in the same way, which shows the text counts from 0 in an unpaged report. Where line 0 sits on the device is a representation question (implementor's), and its existing answer (the rest position) stands. The value of LINE-COUNTER is not a representation question. A program that DISPLAYs, tests or SOURCEs LINE-COUNTER sees 3 where the text gives 2, so the harm is wrong_answer. It is limited to unpaged reports whose first presented line is LINE PLUS 0. Calibration: medium-high. The note's reading A is the text's literal arithmetic, and reading B's only textual support does not apply without a PAGE clause.
