# PB1931 — LANDED (discharged)

Filed by the train-1005 lander from wave 1005 group C's report (`w1005c-PB1423-report.md`, lead 3). Not re-probed by
the lander.

## The defect

`python scripts/spec/cite.py --check 14.2.3 "occupies"` → `OK §14.2.3 8)`: "If the argument is passed by reference,
the activated runtime element operates as if the formal parameter occupies the same storage area as the argument."
So `SET WP TO ADDRESS OF FORMAL` inside the activated element yields the address of the caller's argument. Today the
formal's carrier is its own object: the pointer handed back compares unequal to the caller's `ADDRESS OF` the
argument, and a BASED item placed at it does not alias the argument (the write raises EC-BOUND-PTR).

**Repro.** `scratchpad/w1005c/p1419e.cob` of the orchestrator session 5ab816c6 (a CALL ... RETURNING a pointer set to
`ADDRESS OF` a BY REFERENCE formal; `IF WP2 = WP` prints DIFF; the BASED write traps EC-BOUND-PTR). A finisher should
copy it into a golden.

**Sites.** `src/Cobol.Net.Runtime/Control/CallAbi.cs` (`CobolArgAdapt` formal carriers) and
`src/Cobol.Net.Runtime/Control/ManagedPointer.cs#SameTarget`.

## Landed (discharged, wave 1034 C)

The note was filed against a tree where a BY REFERENCE formal was a carrier of its own (`CobolArgAdapt` formals), so
`ADDRESS OF formal` could not be the caller's address. It no longer reproduces: PB2087 (`cd7f00c1d`, 2026-10-05) made every
ADDRESS OF-taken formal an AREA formal whose implicit data-address pointer IS the argument's own `StorageCell` area
(`LinkageFormal.IsArea`, `CobolArgAdapt.Area`), and PB2089 (`30800d068`) claimed every BY REFERENCE operand, native numerics
included, onto a cell. The original repro (`p1419e.cob`, the orchestrator session's scratchpad) no longer exists, so the shape
was rebuilt: a CALL ... RETURNING a pointer set to `ADDRESS OF` the formal, compared with `ADDRESS OF` the argument, then a
BASED item placed at it and written.

Re-probed on this wave's build (base `600c0ff70`), every arm prints SAME and the BASED write reaches the argument: an
alphanumeric item, an unsigned and a signed DISPLAY numeric, a binary and a COMP-3 numeric, a group, a table element, a
reference-modified item, a formal forwarded to a second program, a METHOD formal (typed and universal object reference) and a
user-defined FUNCTION formal; also with the caller never taking `ADDRESS OF` the argument itself. BY CONTENT (14.2.3 GR9) stays
DIFF with the argument untouched, as it must. `cite.py --check`: 14.2.3 OK (GR8 "occupies", GR9), 8.8.4.2.16 OK ("same
address"), 8.4.3.11.4 OK (GR1).

Witness: `conformance:2002/pb1931_address_of_by_reference_formal` (the note asked a finisher to turn the repro into a golden).
Sibling sweep: the INVOKE arm (`OoEmitter`) and the FUNCTION arm were probed with the same shape and agree with the CALL arm;
the contained-program GLOBAL-formal forward (PB2096) and the bit item (PB2095) are separate notes, already landed with their
own goldens. Not probed: a callee compiled into a separate assembly (`cobol subs.cob -o subs.dll`, then `cobol main.cob --run` beside
it answered `EC-PROGRAM-NOT-FOUND` on this build, so the shape was not reachable by that route).
