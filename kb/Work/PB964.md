Filed 2026-09-22 by REGISTRAR #10 from the wave-45 group-D lead (PB810 implementer report). The implementer found it
on the `_lineOpen` state its PB864 fix introduced. It **reproduces on main `f503888da` too**, before that fix, on this
registrar's own build (0 warnings / 0 errors). It is not a regression of train 46. It is the same one-flag
line-state model PB864 is splitting, so the fixer should take it on PB864's seam (`cluster`).

## Reproduced

`scratchpad/reg10/lsweld.cob`: `SELECT F1 ASSIGN TO "rg10-weld.txt" ORGANIZATION IS LINE SEQUENTIAL`,
`01 R1 PIC X(5)`:

```cobol
           OPEN OUTPUT F1
           MOVE "AAAAA" TO R1  WRITE R1 AFTER ADVANCING 1 LINE
           MOVE "BBBBB" TO R1  WRITE R1
           MOVE "CCCCC" TO R1  WRITE R1
           CLOSE F1
```

Bytes on disk (`od -c`): `\r \n A A A A A B B B B B \r \n C C C C C \r \n`. That is three lines: an empty one,
`AAAAABBBBB`, then `CCCCC`. **The AAAAA and BBBBB records share one physical line.** Reading the file back with the
same fixed 5-character record happens to split the line again: REC 01 is blank, then AAAAA, BBBBB, CCCCC. So a
round-trip through COBOL.NET HIDES the weld. Any other consumer of the text file (an editor, `wc -l`, a second
program with a different record length, GnuCOBOL) sees one line holding two records.

## Rule

`cite.py --check 14.9.51.4 "If the ADVANCING phrase is not used, automatic advancing shall be provided by the implementor to act as if the user has specified AFTER ADVANCING 1 LINE."` → `OK §14.9.51.4 25)`

`cite.py --check 14.9.51.4 "If the AFTER phrase is used and the BEFORE phrase is not used, the line is presented after the representation of the printed page is advanced"` → `OK §14.9.51.4 25) f)`

The plain WRITE is AFTER ADVANCING 1 LINE, so BBBBB is presented after an advance, on its own line. **Expected** file
content: `\r\n AAAAA \r\n BBBBB …`. The trailing terminator after the last record is PB864's CLOSE question, and this
note does not decide it. GR25 also says ADVANCING is IGNORED "if the physical file does not support vertical
positioning". COBOL.NET honours ADVANCING on line-sequential files: the AFTER write above really does emit the leading
`\r\n`. Having made that choice, it must honour the implicit AFTER 1 LINE as well. Honouring the explicit form but
not the implicit one is the defect.

## Mechanism

`src/Cobol.Net.Runtime/IO/SequentialConnector.cs`, line ≈980:
`if ((_afterAdvancing || page is not null) && !_lineSequential) return WriteAdvancing(image, 1, before: true, page);`.
Once a connector has seen an ADVANCING write, a plain WRITE is promoted, but NOT on a line-sequential file. On such a
file the plain WRITE takes `EmitRecordLine`, which writes `record + \r\n` onto the line the AFTER write left open.
(The promotion it does apply is `before: true`. Whether that is itself GR25's AFTER is worth checking on the
non-line-sequential leg while you are there.)

## What the fixer must do

1. Take this together with PB864, which already separates "has seen a print-control WRITE" from "is the current line
   unterminated". A plain WRITE on a line-sequential file must end an open line first. Make the line state the one
   input that decides it, so every write shape (BEFORE, AFTER, plain, PAGE, mnemonic, LINAGE) asks the same question.
2. Sweep the mixes: AFTER→plain, AFTER→BEFORE, BEFORE→AFTER, PAGE→plain, each on LINE SEQUENTIAL and on RECORD
   SEQUENTIAL with and without LINAGE. Pin the physical bytes, not a COBOL read-back, because the read-back is what
   hid this.
3. Golden at 2023, the only edition with ORGANIZATION LINE SEQUENTIAL (§12.4.5.10.3 GR2 and CONFORMANCE.md
   DOC-A.1-115's "ONE EDITION"). It must read the file as bytes, for example with a second FD over the same
   file with a 1-character record, counting lines. Record GR-14.9.51.4-25 with it.

## Landed (wave 48 group Y, 2026-09-22)

Re-probed on the implementer's own build first (base `ec095d120`, which already carries PB864's `_lineOpen` split):
the LINE SEQUENTIAL repro still wrote `\r\nAAAAABBBBB\r\nCCCCC\r\n`. **The sweep the note asked for widened
the defect:** a plain WRITE after an AFTER write welded on EVERY sequential organization, not only line sequential
- record sequential print file `\r\nAAAAABBBBB…`, LINAGE file the same, and after AFTER ADVANCING PAGE
`\fAAAAABBBBB…` - because the print arm's promotion was `before: true`, a BEFORE placement, which presents on the
open line exactly as the line sequential arm did.

**Fix (one question, every arm):** `SequentialConnector.ImplicitAdvanceIsBefore` (`!_lineOpen`) places the plain
WRITE's ONE advance - §14.9.51.4 GR25 "act as if the user has specified AFTER ADVANCING 1 LINE", one
LINAGE-COUNTER step (§13.18.34.4 GR7). With an AFTER-placed record on an open line the advance comes first
(GR25 f)) and ends that line; with no line open the record-then-terminator shape already lands the record on a
fresh line. The print/LINAGE reroute (`WriteAdvancing(…, before: ImplicitAdvanceIsBefore, …)`) and both line
sequential arms of `EmitLineSequentialRecord` ask it. Unchanged by design: AFTER then BEFORE still presents on the
open line (GR25 e) - no advance precedes a BEFORE presentation; the same line as AFTER ADVANCING 0, GR25 c)), BEFORE
then plain adds no blank line.

Witnesses: `conformance:2023/pb964_ls_plain_write_after_after` (reads the file back through a one-character record
sequential FD, so the weld cannot hide), and byte tests `LinageConformanceTests.Bytes_PlainWriteAfterAnAfterWrite_*`
(RS, RS+LINAGE at 85; LS, LS+LINAGE at 2023), `Bytes_PlainWriteAfterAdvancingPage_*`, `Bytes_LineSequential_EveryPlacementMix`.
GR-14.9.51.4-25 re-verdicted CONFORMS (GAP 2266 -> 2265). Design: `docs/COBOLNET_FILES_DESIGN.md` (the print-stream
paragraph). `FileIoDifferentialTests.WriteAdvancingMnemonic_ZeroLineAdvance_RecordAlwaysReleased` is GREEN on this
base both before and after the fix - it is not this root (no plain WRITE in it).

**Seven NIST goldens encoded the weld and were re-baselined** (`tests/nist/valid/` NC135A, SQ101M, ST137A, ST139A,
ST140A, ST144A, ST147A; `tests/nist/corpus.tsv` marks the six green ones `divergent` with the citation). SQ101M is
the proof: WRT-TEST-GF-19 and GF-20 are plain WRITEs after `WRITE-TEST-LINE`'s AFTER 1 LINE writes, and their own
printed text says "THIS LINE SHOULD BE 2 LINES BELOW AND 1 LINES ABOVE THE BRACKETING WRT-TEST LINES" - the old
golden put it 1 below and 2 above. The ST13x/ST14x goldens welded a `FILE=...` dump record onto the preceding
asterisk or PASS line; the rest of each diff is a blank line moving to the record that actually wrote it. Every
golden differs from the new output only in these shapes (per-case diff, 56 lines over the seven files).
