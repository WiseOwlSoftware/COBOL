# PB509

## Mechanism — blank-when-zero-clause
bwz-gr3-relation-condition - GR3 is honoured only on the MOVE / de-editing path. CobolEdit.DeEdit values an all-spaces image as zero and its EC-DATA-INCOMPATIBLE round trip is run with blankWhenZero, so a blanked BLANK WHEN ZERO item sent to a numeric or numeric-edited receiver is correctly zero. But in a RELATION CONDITION the operand is routed by category before any BLANK WHEN ZERO knowledge is consulted: ConditionRenderer.cs:178-180 takes the first arm whose operand `IsString`, and a numeric-edited item is a string operand, so the entire relation becomes CobolString.Compare of the edited image against the other operand rendered as characters. The numeric branch at :186 is never reached, and nothing on that path asks whether the sender is blanked.

### Expected, from the standard
ISO/IEC 1989:2023 13.18.8.4 GR3 - "If the subject of the entry is a sending data item, the object of an operation is a numeric or numeric-edited data item, and the content of the sending data item is all spaces, the value of the sending data item is considered to be zero." (validated with scripts/spec/cite.py --check 13.18.8.4). WS-PLAIN is the subject of a BLANK WHEN ZERO entry and the sending operand; the object of the relation is WS-ZERONUM, a numeric data item (8.8.4.2.1: "The first operand is called the subject of the condition; the second operand is called the object of the condition"); WS-PLAIN's content is all spaces; so its value is zero and, by 8.8.4.2.4, the comparison is of algebraic values - 0 = 0, TRUE. Both DISPLAYs shall print the -EQ arm.

```
$ python scripts/spec/cite.py --check 13.18.8.4 "If the subject of the entry is a sending data item, the object of an operation is a numeric or numeric-edited data item, and the content of ..."
  OK  §13.18.8.4 3)  (General rules)
```

### Observed
Observed: `REL-NUMITEM-NE` and `REL-EDIT-NE`. The compiler instead applies 8.8.4.2.5 (a numeric integer operand against a class-alphanumeric operand): WS-ZERONUM is rendered as the five characters `00000` and compared against five spaces, so the relation is false. The de-editing arm of the SAME rule is correct in the same program - `MOVE WS-PLAIN TO WS-NN` where WS-NN is PIC S9(3)V99 gives `0000{`, i.e. zero - which is what makes this a one-arm implementation rather than an unimplemented rule. Reading evidence that GR3's reach is wider than MOVE: GR1, one rule earlier in the same subclause, says "receiving operand" where GR3 deliberately says "the object of an operation", and `object of an operation` occurs EXACTLY ONCE in the whole standard (grep of specs/ISO_COBOL.md), so it is not this standard's term of art for a MOVE receiver; the MOVE receiver case is already legislated by 14.9.25.4 GR6d1. If the owner adopts the narrow reading instead, this row closes as CONFORMS and the narrow reading should be recorded as an adjudication so it is not re-derived.
