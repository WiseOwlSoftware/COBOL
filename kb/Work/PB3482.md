# PB3482 — the host-share posture cannot express an INPUT opener that still owes writes

WRONG ANSWER on Windows only, from the implementer report of PB3337 (`E:\COBOL-coord\scratch\reports\w1137a-PB3337-report.md`, `## New defects` 1). PB3337 has landed (PR #351, main 2353545b2), so this note is ready.

**Scenario.** Run unit A: WRITE, CLOSE, OPEN INPUT under ALL OTHER, with its transaction standing. Run unit B: OPEN SHARING READ ONLY INPUT. Windows answers '61' until A's COMMIT or ROLLBACK; Table 19 (section 9.1.15) gives '00'. Linux answers '00'.

**Mechanism.** After the PB3337 R2-1 fix the re-OPEN's handle is ReadWrite only when the kept handle is writable AND `AttachedStore.Transaction != 0`; that transaction-standing arm is the one remaining deviation. The root is `FileLockPosture`, the host-share posture: it has no way to say "an INPUT opener that still owes its transaction's writes", so the mandatory Windows share mode refuses B's read-only share.

**Fix shape.** Fix it at the root in `FileLockPosture` (a posture carrying the owed-writes condition and the share mode it implies), not as a special case in `KeyedConnector.Lock`. Design 2.2.1.10 As built (3) states the deviation and is updated with the fix. Needs a Windows host witness (`[Trait("Host", ...)]`).

**Sites:**
- `src/Cobol.Net.Runtime/IO/KeyedConnector.cs`
- `src/Cobol.Net.Runtime/IO/Sharing/FileLockPosture.cs`
- `docs/rearchitecture/DESIGN-runtime-library.md`

## Landed

Re-probed on a fresh build: `CommitRollbackRuntimeTests.An_input_opener_that_owes_its_transactions_writes_admits_what_Table_19_admits`
(both organizations; B under SHARING WITH READ ONLY INPUT and I-O; COMMIT and ROLLBACK) answered '61' on Windows with the
second attempt disabled, as the note says.

**The root was wider than the note's sites.** A share mode refuses by ACCESS, and Table 19 admits a READ ONLY request beside
an INPUT opener that holds a writable handle; no posture on B's side can say so unless something tells B that the table
admitted the request. Windows carried the table in share modes alone (`RunUnitFileLock.HostOfThisProcess` was null there), so
nothing could. The fix therefore has three parts, none a special case in `KeyedConnector.Lock`:

1. `HandleColumnLockHost` (+ `WindowsByteRangeLocks`, `HostRegionLocks.ColumnRangeStart`): Windows now publishes its Table 19
   column as one exclusive byte of a 2^32-byte range through a read handle of its own, and tests the ranges its row refuses
   (its own column's range around its own byte). `SHARING WITH NO OTHER` publishes nothing (its handle is `FileShare.None`).
2. `FileLockPosture.WhenOwedWritesAreAdmitted`: the second posture (READ ONLY becomes `FileShare.ReadWrite`; the other two
   modes have nothing to yield), proved over the printed table by
   `FileLockPostureDriftTests.EveryNormalOpenCellBesideAnInputOpenerThatOwesWritesIsAdmittedOnceTheReadOnlyPostureYields`.
3. `FileConnector.Open` is two attempts (`OpenOnce`): the second only when the first was refused '61' by the host with the
   request's column HELD and another run unit's INPUT opener holding its column (`RunUnitFileLock.AnotherInputOpenerHolds`;
   only an INPUT opener can owe writes), on a host whose share modes are mandatory. A program outside the protocol that holds
   the file for writing, with no INPUT opener beside it, still refuses the request
   (`FileLockPostureDriftTests.AReadOnlyOpenBesideAnOutsideWriterIsRefusedWhereTheShareModeRefusesIt`, which goes red when the
   INPUT-opener condition is removed).

Design 2.2.1.10 As built (3), the lock-hosts bullets of 2.1, the DOC-A.1-75 determination and the Files design are current.

**Merged with PB3483 (finisher, after the merge queue bounced pull request #360 on a conflict).** PB3483 replaced the
kept column lock's give-back-and-retake by `RunUnitFileLock.Amend` / `Revert` (`IColumnLockHost.Establish`'s `supersedes`) while
Windows still had no column host; with `HandleColumnLockHost` the Windows host joins that contract: a superseding request
publishes its new byte through the kept holder's own handle, and a re-OPEN under SHARING WITH NO OTHER gives the holder
handle way once its row's test passed (its `FileShare.None` handle would be refused by it). The OUTPUT probe beside a kept
holder is a read request that admits only readers (`HostFile.IsWrittenOrExcludedByAnother`, `FileConnector.ProbeHeldByAnother`):
the merged tree otherwise answered '61' to a commit-controlled connector's own re-OPEN OUTPUT under ALL OTHER on Windows
(`CommitRollbackRuntimeTests.A_reopen_is_not_refused_by_the_column_lock_its_own_close_kept`, red under either mutation).
The second attempt of `FileConnector.Open` no longer withholds the kept lock's restoration: the first attempt reverts it and
the second amends it again, with no unlocked instant. `RunUnitFileLockAmendTests` runs on the Windows host too.
