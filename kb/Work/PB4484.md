# PB4484 - comment accuracy, four sites

Filed instead of edited: line numbers in the reports have moved since (PB4472 and PB4469 landed), and the last two need a read of the code path that this registrar pass did
not carry out. Verified on origin/main `0b5581dee` where noted.

1. **STRUCK 2026-11-04 (enqueue unit clerk, on the PB4483 report's word): the comment is accurate now.** PB4483 rewrote the `ParseTokens` summary to state both cases (an expansion of a definition written in this compilation keeps the definition's own lines and columns; one read from the repository carries the EXPANDS entry's line, kb/Work PB4483), re-read on origin/main. Items 2 to 4 stand. Original text: `src/WiseOwl.Cobol.Frontend/Parsing/FragmentParse.cs` ~85, `ParseTokens`'s summary: "Each token keeps its original line/column, so a diagnostic raised while binding the result
   points at the definition's own source line." No longer true for an expansion of a repository-read skeleton: `OoExpansion.cs` ~591-596 sets every token of a published
   expansion to the EXPANDS entry's line and column (PB4469). State both cases.
2. `tests/WiseOwl.Cobol.Tests.Unit/EntryOptionsReaderDriftTests.cs`, `EntryBinderFiles` summary: "a class built over the one DataBinder of its unit (a primary constructor taking
   it ...)". `EntryBinderDeclaration` (`\bclass\s+\w+\s*\(\s*DataBinder\s+\w+`) derives a class only when DataBinder is the FIRST parameter of a PRIMARY constructor; a class that
   takes it second, or in an ordinary constructor, is not scanned. Say "whose primary constructor's first parameter is the DataBinder" (or widen the regex, which is the better fix).
3. `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/OoEmitter.cs` ~377: "each file registers under FileKeyExpr(f): a factory literal, or this.__fkey_X". `BinderDriver.cs` ~1283-1296 gives a
   non-EXTERNAL, non-SD OBJECT-class file its minted `this.__fkey_X` field and an EXTERNAL or SD file a static literal key; the lead says a non-EXTERNAL non-SD factory file
   registers under its minted field. Read `FileKeyExpr` (`EmitCore.cs` ~280) against that and correct the comment to the actual split.
4. `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.Ptr.cs`, the ADDRESS OF arm comment (the lead cites line 147; the file moved): omits the case where `ResolveStorageClaimHead`
   returns null for a container GLOBAL item (`DeclaringDepth != 0`, see `ForceStringCanonical` ~108).

Pure comment edits; the branch that fixes them is the tooling-free lane (inert for the build only if no code line changes).
