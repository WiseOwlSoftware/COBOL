**Rule it breaks:** §15.68.3 r4a (rendered PDF page 895, printed): argument-1 is '... { digit [ , digit ] ... [ . [ digit ] ] | . digit }', where digit is 'a string of one or more of the digits 0 through 9'. Every grouping separator is followed by a digit string. §15.94.4 r1b: TEST-NUMVAL-C reports the position of the first character in error. The ONE-SCAN rule (kb/Work PB60): the value path and the validator share NvScan, so both are wrong together.

**Scenario:** NvScan's digit loop skips a group separator with 'if (allowGroup && c == group && !sawDot && anyDigit) continue;' and never requires the next character to be a digit. TEST-NUMVAL-C('1,.5') returns 0 where §15.94.4 r1b requires 3, the '.' being the first character in error. TEST-NUMVAL-C('1,,2') returns 0 where it requires 3. TEST-NUMVAL-C('1,') returns 0 for content that is not a conforming format. The value twins NUMVAL-C('1,.5') = 1.5 and NUMVAL-C('1,,2') = 12 return a value and never raise EC-ARGUMENT-FUNCTION, so under >>TURN EC-ARGUMENT-FUNCTION CHECKING ON a program meant to terminate continues with a fabricated number. The same holds with DECIMAL-POINT IS COMMA, with the roles swapped ('1..2').

**Target:** In NvScan, a grouping separator records a pending-group state that only a digit clears. The decimal separator, a space, a sign, CR/DB, another separator or the end of the text met while it is pending is the error at that character, or LENGTH+1 when the text ends (r1c: valid but incomplete). The value and validator twins inherit it through the one scan. Add goldens for TEST-NUMVAL-C and NUMVAL-C on '1,', '1,,2' and '1,.5' in both DECIMAL-POINT modes.
