# PB3480 — CLOSE gives back the record locks of a commit-controlled file

WRONG ANSWER, found by the round-3 branch review of PB3337 (`E:\COBOL-coord\scratch\reports\w1137a-PB3337-report.md`, `## Review findings` R3-1, medium). PB3337 has landed (PR #351, main 2353545b2): the commit-and-rollback sites below are on main, so this note is ready.

**Rule.** 14.9.6.4 GR9 (checked by the reviewer): "Except when the file is specified in an APPLY COMMIT clause, the file lock and any record locks associated with the file connector ... are released by the execution of the CLOSE statement". 9.1.16: only COMMIT and ROLLBACK release them for a commit-controlled file.

**Mechanism.** `FileRegistry.SharedClose` (FileRegistry.cs, about line 2148) runs `PhysicalFileTable.ReleaseAllForConnector` on every CLOSE, commit-controlled connectors included. Run unit A, under an active APPLY COMMIT, READs record 1 (locked under the commit posture) and CLOSEs before any COMMIT. Run unit B must then get '51' on record 1, and gets '00'.

**The witness hides it.** `CommitRollbackRuntimeTests.cs` line 586 (the R2-1 witness) asserts that B READs record 1 with '00'. Correct it to '51' in the same change as the fix.

**Hazard once fixed.** The R2-1 change routes the no-transaction INPUT re-OPEN to the non-adopting path, whose `CarryKeptOver` and `GiveBack` dispose the kept region endpoint: a second release of the same READ locks. The fix must make the release single-owner, and a witness must cover CLOSE, re-OPEN, then COMMIT.

**Sites:**
- `src/Cobol.Net.Runtime/IO/FileRegistry.cs`
- `src/Cobol.Net.Runtime/IO/Sharing/PhysicalFileTable.cs`
- `tests/Cobol.Net.Tests.Unit/Store/CommitRollbackRuntimeTests.cs`
