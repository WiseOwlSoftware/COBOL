# PB3480 — CLOSE gives back the record locks of a commit-controlled file

WRONG ANSWER, found by the round-3 branch review of PB3337 (`E:\COBOL-coord\scratch\reports\w1137a-PB3337-report.md`, `## Review findings` R3-1, medium). PB3337 has landed (PR #351, main 2353545b2): the commit-and-rollback sites below are on main, so this note is ready.

**Rule.** 14.9.6.4 GR9 (checked by the reviewer): "Except when the file is specified in an APPLY COMMIT clause, the file lock and any record locks associated with the file connector ... are released by the execution of the CLOSE statement". 9.1.16: only COMMIT and ROLLBACK release them for a commit-controlled file.

**Mechanism.** `FileRegistry.SharedClose` (FileRegistry.cs, about line 2148) runs `PhysicalFileTable.ReleaseAllForConnector` on every CLOSE, commit-controlled connectors included. Run unit A, under an active APPLY COMMIT, READs record 1 (locked under the commit posture) and CLOSEs before any COMMIT. Run unit B must then get '51' on record 1, and gets '00'.

**The witness hides it.** `CommitRollbackRuntimeTests.cs` line 586 (the R2-1 witness) asserts that B READs record 1 with '00'. Correct it to '51' in the same change as the fix.

**Hazard once fixed.** The R2-1 change routes the no-transaction INPUT re-OPEN to the non-adopting path, whose `CarryKeptOver` and `GiveBack` dispose the kept region endpoint: a second release of the same READ locks. The fix must make the release single-owner, and a witness must cover CLOSE, re-OPEN, then COMMIT.

**Sites:**
- `src/WiseOwl.Cobol.Runtime/IO/FileRegistry.cs`
- `src/WiseOwl.Cobol.Runtime/IO/Sharing/PhysicalFileTable.cs`
- `tests/WiseOwl.Cobol.Tests.Unit/Store/CommitRollbackRuntimeTests.cs`

## Landed (wave 1140, group B; kb/Work PB3484 shares the change)

**Re-probe.** Reproduced on the base (62cd0d954): unit A under APPLY COMMIT READs record 1 and CLOSEs; run unit B's READ of record 1 answered '00' where
§14.9.6.4 GR9 and §9.1.16 require '51' (the R2-1 witness in `CommitRollbackRuntimeTests` pinned the '00'; it now pins '51' and a READ of an unlocked record).
**Fix.** `FileConnector.CloseKeepsLocks` (KeyedConnector: under commit control with a handle to keep) is the one decision; `FileRegistry.SharedClose` releases
none of the record locks when it holds, and `KeyedConnector.CloseCore` keeps the handle on the same answer. The kept endpoint is the one owner of the locks
published through it: `PhysicalFileTable.ReleaseThrough` (called by `ReleaseKept` and `CarryKeptOver`), and a re-OPEN that takes a handle of its own moves them
to its endpoint inside the attach's store-mutex hold (`PhysicalFileTable.Rehome`) before the kept handle goes, so the release stays single-owner (the hazard the
note named); a re-OPEN that fails moves them back (`AbandonOpen`, GR25). The registry's COMMIT and ROLLBACK release the unpublished ones by name.
**Witnesses** (`CommitRollbackRuntimeTests`): `A_close_under_commit_control_keeps_its_record_locks_until_the_commit_or_rollback` (both organizations; no re-OPEN
and a second CLOSE '42', re-OPEN INPUT, re-OPEN I-O; COMMIT and ROLLBACK), `A_refused_reopen_leaves_the_kept_record_locks_standing` (mutation-checked: fails with
the rehome-back removed), and the corrected R2-1 witness. Siblings: the SEQUENTIAL organization has no APPLY COMMIT (PB3340), so `CloseKeepsLocks` is false there.

## Landing

- `src/WiseOwl.Cobol.Runtime/IO/FileConnector.cs#CloseKeepsLocks` - the ONE decision that a CLOSE keeps the record locks and the handle (KeyedConnector: under commit control with a handle); the registry's `SharedClose` and `KeyedConnector.CloseCore` both ask it. Trap: decide it BEFORE `c.Close()`, the fields it reads are cleared by the close.
- `src/WiseOwl.Cobol.Runtime/IO/KeyedConnector.cs#Kept.Endpoint` / `ReleaseKept` / `CarryKeptOver` / `Attach` / `AbandonOpen` - the kept endpoint owns the locks published through it; a re-OPEN that takes its own handle moves them (`PhysicalFileTable.Rehome`, inside the attach's mutex hold) before the kept handle goes, and a failed one moves them back. Trap: disposing an endpoint releases every byte it holds, so any give-back of a kept handle that skips the move silently drops the locks from the host while this run unit's table still claims them.
- `src/WiseOwl.Cobol.Runtime/IO/Sharing/PhysicalFileTable.cs#ReleaseThrough` / `Rehome` / `Unpublish` / `Republish` - release, move, unpublish (bytes off the host, table entries kept) or publish again (through the kept handle a failed re-OPEN takes again, PB3483) by ENDPOINT (the connector does not know its registry key); unpublished locks are the registry's, by name.
- `src/WiseOwl.Cobol.Runtime/IO/FileRegistry.cs#_retired` / `Retire` / `ReleaseAllKept` - a connector leaving `_files` holding kept state stays the COMMIT's and ROLLBACK's (ISO 12.4.6.3.4 GR5); `ReleaseAllKept` is the one give-back for COMMIT, ROLLBACK, `CloseAll` and `Reset`. `ReclaimRetired` (called at the OPEN, before the physical file is associated) hands the kept state to the same-name replacement through `KeyedConnector.InheritKept` so its own run units kept handle never refuses it 61; a retired connectors unpublished record locks are released by name through its own `Physical`. Trap: releasing at displacement is WRONG, it turns a CANCEL, CALL, COMMIT sequence into a rollback.
- `tests/WiseOwl.Cobol.Tests.Unit/Store/CommitRollbackRuntimeTests.cs` - the witnesses (`A_close_under_commit_control_keeps_its_record_locks...`, `A_refused_reopen_leaves...`, `A_connector_displaced_by_a_registration...`, `An_instance_file_dropped...`). Trap: a Relative connector's `Opened` reads no page, so only an INDEXED EXTEND re-open can be refused AFTER the attach.
