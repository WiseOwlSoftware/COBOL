# PB2518

Filed from the PB2071 refuter (`E:\COBOL-coord\scratch\w1033-adj\PB2071-refute.md` section 6, probe `r03b`; flags under-rejects, silent). No open note covers it.

**Repro (compiles clean at 85, 2002, 2014, 2023).**

    01 R.
       05 A PIC X(2).
       05 C PIC X.
       05 B REDEFINES A PIC X(2).

**Expected from the spec (cite.py --check OK).** `§13.18.44.3 10)`: "The entries giving the new descriptions of the storage area shall follow the entries defining the area of data-name-2, without intervening entries that define new storage areas." C intervenes. GnuCOBOL 3.2.0 rejects: "REDEFINES must follow the original definition".

**Why the row is wrong.** Inventory row `SR-13.18.44.3-10` is CONFORMS on the note "the ... intervening ... half is the ClassifyRedefinesClasses layout invariant (a redefiner overlays its target's area wherever it stands)". A layout that tolerates the violation is not a diagnosis of it (`§4.2.2`). PB1280's line 107 observed "reaches past intervening storage (SR10)" and its sweep then said SR10 "already had screens", which the refuter shows is false. Site: `src/Cobol.Net.Compiler/Binding/DataBinder.cs#ClassifyRedefinesClasses` and `DataBinder.RedefinesEntry.cs#ScreenRedefinesEntry`. Re-verdict the row with the fix. Related: `PB2071`.

## Landed (2026-10-07, wave 1037 group F)

Re-probed on the wave's own build: the three-entry record, the same shape at level 01 and at level 77, a LINKAGE root, a FILLER
between the pair and a group between the pair all compiled clean.

**Fix.** `DataBinder.RedefinesEntry.cs#ScreenRedefinesEntry` asks SR10 of the resolved pair over the scope the pair was
resolved in (`ResolveRedefines` passes it): `FirstInterveningStorage` returns the first entry between data-name-2 and the
subject that has no REDEFINES clause of its own (a redefinition defines no storage, so several redefinitions of one area stay
legal, SR7), skipping compiler temps and, at top level, roots of another section. COBOLNET2739 (the entry-level rule family)
carries it; no new code. The two arms of the scope are a group's children and the roots of a section (levels 01 and 77); both
are goldened. A CONSTANT entry and a TYPEDEF template are off `Roots`, so they define no storage and do not intervene. The
inventory row's earlier note named the overlay layout as the witness; a layout that tolerates the violation does not diagnose
it, and the row now cites the screen and four goldens. The rule is enforced at every edition, as the neighbouring PB93 SR10
negative already does.

**Sibling found in the same loop and fixed (I9).** `ResolveRedefines` walked `AllItems()` = `Roots` only, so a redefiner
inside a TYPEDEF template was never resolved or screened: with the type unused, an SR8 size violation, an unresolved
data-name-2 and the SR10 gap all compiled clean, and with the type used the clone was screened instead (once per use, at
the template's source position). It now walks `CompositionForest()`, resolves every clone, and screens only written entries
(`ClonedFrom` null), so a type is diagnosed once at its declaration (probe programs S1, S2, R1, R2 in the wave scratch;
`RedefinesTargetTests.RedefinerInsideUnusedTypedef_IsScreenedAtTheDeclaration`, `...UsedTypedef_IsDiagnosedOnce`, negative
`pb2518-redefines-in-unused-typedef`).

Goldens: `conformance:85/pb2518_redefines_only_redefinitions_between` (redefinitions, an 88 and a redefiner's subordinates
between the pair, at group and root level), `conformance:2002/pb2518_redefines_past_non_storage_entries` (CONSTANT and TYPEDEF
between), negatives `pb2518-redefines-past-intervening-storage` and `...-roots`.

## Landing

- `src/Cobol.Net.Compiler/Binding/DataBinder.RedefinesEntry.cs#ScreenRedefinesEntry` — owns every entry-level REDEFINES rule over the resolved pair (SR2, SR3, SR8, SR10, SR13, SR15; COBOLNET2739, SR8 keeps 1539). SR10 reuses `FirstInterveningStorage` over the SAME scope list `ResolveRedefines` resolved in; do not rebuild a second scope walk. Trap: a rule about the pair needs the scope, so the screen takes it as a parameter.
- `src/Cobol.Net.Compiler/Binding/DataBinder.cs#ResolveRedefines` — walks `CompositionForest()` (roots + clones + TYPEDEF templates, which are OFF `Roots`); every item is resolved, only `ClonedFrom is null` entries are screened (the `written` flag). Trap: `AllItems()` is roots only, so any per-declaration rule walked over it silently skips every type declaration; a template root (`Parent is null && IsTypedef`) is skipped here on purpose.
- Corpus trap: a golden that put a REDEFINES after other storage (`2023/pb96_renames_span_over_redefines`) was itself illegal source and had to be reordered; search the corpus for the shape before adding a screen.
