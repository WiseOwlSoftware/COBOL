# PB299 — LANDED — the underscore the lexer would not take

> **✅ LANDED. The FIX is witness cluster A's (`66c85a90`); this note is the citation sweep's INDEPENDENT
> discovery of the same defect, landed with the sweep so the root cause and the complement are on the record.
> Re-measured on the merged tree before writing this (see "Verified, not inherited" below): every shape is legal
> now, and the COBOL-85 rejection is a NAMED edition diagnostic rather than a parse error.**

## The rule

`python scripts/spec/cite.py --check 8.3.2.1 "…"` → **OK §8.3.2.1 (General)**:

> "A COBOL word is a character-string of not more than 63 characters that forms a compiler-directive word, a
> context-sensitive word, an intrinsic-function-name, a reserved word, a system-name, or a user-defined word.
> Each character of a COBOL word that is not a special character word shall be selected from the set of basic
> letters, basic digits, extended letters, and the basic special characters hyphen and underscore. The hyphen or
> underscore shall not appear as the first or last character in such words."

The sentence is one rule with **two** halves, and only the first is usually noticed: the underscore is IN the
word character set, and neither separator may be first **or last**.

## The defect, and why nothing caught it

`CobolLexer.g4`'s `NAME_BODY` (and the `SUB_IDENTIFIER` twin that shares it) admitted no underscore in any of
its alternatives, so an underscore-bearing user-defined word did not lex at all — `01 WS_A PIC X(5).`, a
`>>DEFINE MY_VAR`, a paragraph-name `MAIN_PARA`, and every `EC-USER-A_B` user exception-name (§14.6.13.1.1
spells that suffix out as "basic letters, basic digits, and the hyphen and underscore basic special
characters").

⛔ **The root cause is a WRONG BELIEF written down as fact, resting on a clause that does not exist.**
`docs/rearchitecture/DESIGN-compile-time-expressions.md` recorded that "the deleted tokenizer accepted `_` in a
compilation-variable name and ANTLR does not, so a test using an underscore name was written hyphenated", and
called the ANTLR behaviour **correct COBOL, "§8.3.1.2 — letters/digits/hyphens"**. §8.3.1.2 does not exist
([[PB290]]). So the observed rejection was rationalized by a phantom, the TEST was changed to fit the compiler
rather than the compiler to fit the standard (⛔ CLAUDE.md rule 4: never change valid COBOL to dodge a compiler
bug), and the belief then guarded the defect for as long as anyone read that doc. The doc is corrected in the
citation sweep's change set.

## Verified, not inherited (2026-09-02, on the merged tree)

The sweep's report described this as an OPEN defect. It is not — witness cluster A had already fixed it on
`main`, which the sweep could not see from its base. Re-measured here with the built `cobol.dll` rather than
taken from either report:

* `01 WS_A PIC X(5) VALUE "HELLO".` + `DISPLAY WS_A` at `--std 2023` → compiles, runs, prints `HELLO`.
* `>>DEFINE MY_VAR AS 7` with a `>>IF MY_VAR = 7` arm, a paragraph-name `MAIN_PARA`, and
  `RAISE EXCEPTION EC-USER-A_B` in one program at `--std 2023` → compiles.
* the same first program at `--std 85` → **`COBOLNET0900: the underscore in a COBOL word requires COBOL-2002
  (targeting COBOL-85)`**, i.e. a named edition diagnostic, not `no viable alternative`.

## The shape of the fix, and the hole it closed on the way

`NAME_BODY` is SUPERSET-PARSE / BIND-NARROW, the repo's standing doctrine: the underscore is admitted at every
edition in the lexer and the COBOL-85 rejection is a bind-time gate
(`Constructs.UserWordUnderscore2002` → COBOLNET0900, raised beside the §8.3.2.1 word-LENGTH check in
`VersionConformancePass.VisitCobolWord` — same clause, same visitor). A lexer that refused the character below
2002 would emit an unexplained parse error instead.

⛔ **And "nor last" is now enforced for BOTH separators, which it was not.** NOT-FIRST was structural (every
alternative opens with a letter or a digit); NOT-LAST held only in the alpha-start alternative. The two
digit-start alternatives ended in `*` over the separator class, so `1A-` and `42-X-` were **ACCEPTED** — a
pre-existing hole for the HYPHEN that the underscore would have silently inherited. Factoring the tail into
`fragment NAME_TAIL : [a-z0-9_-]* [a-z0-9]` closes it for both characters in all three alternatives at once,
which is the structural shape rule 5 asks for rather than three parallel edits.
