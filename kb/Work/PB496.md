# PB496

## Mechanism — usage-clause-p1
usage-p1-F9-object-reference-general-format-missing-active-class-interface-name-and-the-only-phrase

### Expected, from the standard
Inside an instance definition, a factory definition, or a method's LINKAGE / LOCAL-STORAGE section, `01 O USAGE OBJECT REFERENCE ACTIVE-CLASS.` and `01 O USAGE OBJECT REFERENCE FACTORY OF ACTIVE-CLASS.` are conforming and shall compile; anywhere else SR16 requires a diagnostic. `01 O USAGE OBJECT REFERENCE C ONLY.` is likewise conforming where class C is defined.

```
(the finding quotes no rule sentence verbatim, so there is nothing to --check; the implementer MUST quote §13.18.60.3 and re-run `cite.py --check` before writing a code comment)
```

### Observed
ACTIVE-CLASS is absorbed by the className arm and then refused as a user word: `01 O USAGE OBJECT REFERENCE ACTIVE-CLASS.` produces COBOLNET0813 "names the unknown class or interface 'ACTIVE-CLASS'" plus COBOLNET0901 "'ACTIVE-CLASS' is a reserved word in COBOL-2023 and cannot be used as a user-defined word" (u_sr16), and the FACTORY OF spelling adds the factory-reference 0899 (u_sr16b). So the phrase SR16 PERMITS cannot be written anywhere, and the placements SR16 FORBIDS are refused for the wrong reason -- the rule is unimplementable in either direction until the phrase parses. The same figure's `[ ONLY ]` tail is missing too: `01 O USAGE OBJECT REFERENCE FOO ONLY.` is COBOL0307 "unexpected 'ONLY'" (u_objref_only). Both belong to the §13.18.60.2 general-format row (part 3 of this subject does not carry it either -- the clause map for this subject is 13.18.60.3 and 13.18.60.4 only, so the FORMAT row lives outside this batch and these two gaps have no adjudicated home yet). NOTE the direction of the risk: this is not a staging decision anyone made -- the words simply are not in the grammar, and the diagnostic a user sees blames their program for using a reserved word.

## Mechanism — usage-clause-p2
objref-only-and-active-class-phrases-missing - `objectReferenceUsage` in Core/CobolOO.g4 has exactly three alternatives (`OBJECT REFERENCE FACTORY OF className`, `OBJECT REFERENCE className`, `OBJECT REFERENCE`), while the §13.18.60.2 general format prints FIVE object-reference forms: bare, `interface-name-1`, `[FACTORY OF] ACTIVE-CLASS`, and `[FACTORY OF] object-class-name-1 [ONLY]`. Two of the general format's own underlined words are therefore absent from the grammar: ONLY and ACTIVE-CLASS. `USAGE OBJECT REFERENCE cls ONLY` dies as a bare COBOL0307 parse error, and `USAGE OBJECT REFERENCE ACTIVE-CLASS` is swallowed by the `className` alternative and reported as an unknown class plus a reserved-word misuse - two diagnostics, neither of which names the phrase the programmer wrote. The rule shape is the one model_the_rule_shape_not_one_case names: GR22 legislates a MATRIX (typed vs universal vs interface vs active-class) x (factory vs instance) x (subclass-admitting vs ONLY), and the grammar models one row of it, so the missing cells are not three more alternatives but a phrase model - an object-reference target (interface-name / object-class-name / ACTIVE-CLASS) plus two independent flags (FACTORY, ONLY) - carried on PicInfo beside ObjectClassName and read by the one SET/INVOKE conformance check that already implements d) 1 b).

### Expected, from the standard
ISO/IEC 1989:2023 §13.18.60.2 general format prints, under OBJECT REFERENCE, the alternatives `interface-name-1`, `[ FACTORY OF ] ACTIVE-CLASS` and `[ FACTORY OF ] object-class-name-1 [ ONLY ]`, and its figure notes list ACTIVE-CLASS and ONLY among the underlined (required) words. §13.18.60.4 GR22 then gives both phrases their semantics independently of the diagram: d) 2 - "If the ONLY phrase is specified: a. If the FACTORY phrase is specified, the object referenced by this data item shall be the factory object of the specified class. b. If the FACTORY phrase is not specified, the object referenced by this data item shall be an instance object of the specified class" (i.e. the specified class exactly, where d) 1 admits a subclass) - and e) - "If ACTIVE-CLASS is specified, the object referenced by this data item shall be of the same class as the object that was used to invoke the method in which this data description entry is specified". §13.18.60.3 SR16 independently scopes ACTIVE-CLASS ("may be specified only in a factory definition, an instance definition, or the linkage or local-storage section of a method definition"), which is a third normative confirmation that the phrase exists. So both spellings are legal COBOL-2002+ source. Required: `USAGE OBJECT REFERENCE cls ONLY` shall bind an object reference restricted to cls exactly - a SET or an INVOKE ... RETURNING of a SUBCLASS instance into it shall be refused where today the unrestricted form accepts it (probe p40 is the case that must FLIP under ONLY) - and `USAGE OBJECT REFERENCE ACTIVE-CLASS`, inside a method definition, shall bind a reference to the invoking object's own class. Where a form is recognized but unimplemented, the honest outcome is the named staged diagnostic the compiler already uses for FACTORY OF (COBOLNET0899), never a parse error and never an unknown-class report against a reserved word.

### Observed
Observed by probe, then read. `Core/CobolOO.g4` line 183 carries the whole rule and its comment says only "USAGE OBJECT REFERENCE [class-name] (ISO §13.18.60.4)" - the omission is not annotated anywhere, so nothing in the tree records that two printed phrases are missing. Because ACTIVE-CLASS falls through `className`, the failure is a MISLEADING pair of diagnostics rather than a clean rejection: COBOLNET0813 tells the programmer the class does not exist and COBOLNET0901 tells them the word is reserved, and neither says 'the ACTIVE-CLASS phrase is not supported'. The general format was cross-checked three ways rather than trusted from the transcription alone (the diagrams are the lossy layer): the figure's own notes enumerate ONLY and ACTIVE-CLASS as underlined, GR22 d) 2 and e) legislate over both by name, and §13.18.60.3 SR16 scopes ACTIVE-CLASS - a general rule and a syntax rule cannot refer to phrases the format does not print. No kb/Work note owns this: the ACTIVE-CLASS hits in the register (PB285, PB365, PB366) are about A.4.10's optional OO items, USE Format 4 operand resolution and factory declarative selection respectively.

## Mechanism — usage-clause-p3
usage-p3/F6 — the ACTIVE-CLASS phrase of USAGE OBJECT REFERENCE is absent from objectReferenceUsage, so the reserved word falls into the className slot of `OBJECT REFERENCE className` and conforming source is refused with TWO diagnostics that both misdescribe it: COBOLNET0813 says the program "names the unknown class or interface 'ACTIVE-CLASS'" (it named no class) and COBOLNET0901 says ACTIVE-CLASS "cannot be used as a user-defined word" (it was not used as one). The parse gap itself is already owned by part 2's finding objref-only-and-active-class-phrases-missing; what is added here is that the refusal happens even in the position 13.18.60.3 SR16 makes legal, and that the messages point the programmer at a defect that is not in the program — the same misleading-0901 shape kb/Work PB283 records for the VALIDATE data-division elements. The ONLY phrase, its neighbour in the same figure, fails the same way with COBOL0307 "unexpected 'ONLY'. A period may be missing at the end of the previous sentence" — again describing a punctuation error that is not there.

### Expected, from the standard
13.18.60.2 prints the object-reference alternatives as `interface-name-1`, `[ FACTORY OF ] ACTIVE-CLASS`, and `[ FACTORY OF ] object-class-name-1 [ ONLY ]`. 13.18.60.4 GR22 e) (cite.py --check OK): "If ACTIVE-CLASS is specified, the object referenced by this data item shall be of the same class as the object that was used to invoke the method in which this data description entry is specified", with e) 1 the factory object of that class and e) 2 an instance object of that class (both cite.py --check OK); GR22 d) 2 (cite.py --check OK for "If the ONLY phrase is specified") narrows the class-named form to the specified class with no subclass. 13.18.60.3 SR16 permits ACTIVE-CLASS in a factory definition, an instance definition, or a method definition's LINKAGE or LOCAL-STORAGE section — which is where q58 puts it. EXPECTED: both programs parse; ACTIVE-CLASS binds a reference typed to the invoking object's class (SET SELFR TO SELF succeeds), and `OBJECT REFERENCE cls ONLY` binds a reference that admits an instance of cls and REFUSES an instance of a subclass. If the semantics are not yet implemented, the conforming interim is a named 0899 in the staging band, as USAGE OBJECT REFERENCE FACTORY OF already gets — never a message asserting the source did something it did not do.

```
$ python scripts/spec/cite.py --check 13.18.60.4 "If ACTIVE-CLASS is specified, the object referenced by this data item shall be of the same class as the object that was used to invoke the m..."
  OK  §13.18.60.4 22)  (General rules)
```

### Observed
Measured at --std 2023 with the pinned compiler; the diagnostics are quoted verbatim above. Grammar by inspection: CobolOO.g4:183-190 `objectReferenceUsage : OBJECT REFERENCE FACTORY OF className | OBJECT REFERENCE className | OBJECT REFERENCE` — three alternatives, no ONLY tail on any of them and no ACTIVE-CLASS alternative; className is a user word, so the reserved ACTIVE-CLASS reaches DataBinder.cs:280's compilation-group class lookup (0813) and the 8.9 reserved-word funnel (0901) simultaneously. The FACTORY OF alternative that DOES exist is itself staged loud (q55/q59: COBOLNET0899), so closing the ACTIVE-CLASS parse gap alone would leave GR22 e) 1 still unreachable. Consequence for the rows: L2.2, L3.1 and L3.2 have no subject at all, and L2.1's FACTORY limb is staged, leaving one of GR22's five lettered sub-rules and one of its two limbs live.
