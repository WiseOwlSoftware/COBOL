# PB5591 - when a mode-scoped USE procedure is "applicable" for the 1985 mandatory AT END / INVALID KEY rules

**Sites:** none (a recorded reading: `ExceptionPhraseRequirement.HasApplicableUse` already implements it, kb/Work PB5413;
the documents that state it are `docs/conformance/3.5/index.md` and `docs/FILES_DESIGN.md` D31(a), changed in the same
landing)

**The question (Q1).** Each 1985 I-O module makes the exception phrase mandatory where no "applicable" (REWRITE:
"appropriate") USE AFTER STANDARD EXCEPTION procedure is specified: "The AT END phrase must be specified if no
applicable USE AFTER STANDARD EXCEPTION procedure is specified for file-name-1" (§1985:VII.4.4.3 SR2), and likewise
§1985:IX.4.5.3 SR7, §1985:VIII.4.5.3 SR5 (READ), §1985:IX.4.7.3 SR3, §1985:VIII.4.7.3 SR3 (START), §1985:IX.4.9.3 SR3,
§1985:VIII.4.9.3 SR3 (WRITE), §1985:VIII.4.3.3 SR2 (DELETE) and §1985:IX.4.6.3 SR3, §1985:VIII.4.6.3 SR4 (REWRITE, "for
which an appropriate USE AFTER STANDARD EXCEPTION procedure is not specified"). A procedure written `USE ... ON INPUT`
(OUTPUT, I-O, EXTEND) runs "for any file open in the input mode or in the process of being opened in the input mode"
(§1985:VII.4.6.4 GR5b; GR5c for output; §1985:VIII.4.8.4 GR5e for extend). Is such a procedure applicable to a statement
whose at end or invalid key condition cannot arise in that mode (a READ under USE ... ON OUTPUT, a WRITE under USE ... ON
INPUT)?

**Reading A (adopted): a mode procedure is applicable to a statement of any file that can be open in that mode.** The
2026-11-12 final adjudication (`kb/Work/PB5413/2026-11-12-held-row-adjudication.md`, amendment 1, sets 6 and 7):
"applicable" binds the procedure to the file ("for which", §1985:IX.4.3.3 SR2: "for which an applicable USE AFTER
STANDARD EXCEPTION procedure is not specified"), the USE rules make a procedure apply by an open mode the file can be in,
and a statement of a file open in that mode does run the procedure (`held-85/set6/p/u-in-in.cob`: a DELETE of a file
open INPUT runs the USE ON INPUT procedure, `USE RAN 49`). EXTEND counts only for a file that can be opened EXTEND
(kb/Work PB5413, landed): "The EXTEND phrase must only be used for files in the sequential access mode"
(§1985:VIII.4.4.3 SR1) and "The EXTEND phrase must only be used for files for which the LINAGE clause has not been
specified" (§1985:VII.4.3.3 SR3).

**Reading B (not adopted): only a mode in which the statement's condition can arise.** The 2026-11-14 final adjudication
(`E:/COBOL-coord/scratch/op-20261114/held-adjudicated.json`, `q1`): the phrase may be omitted only where a procedure can
be the one the general rules require when it is absent, "If the AT END phrase is not specified, a USE AFTER EXCEPTION
procedure must be associated with the file connector referenced by file-name-1, and that procedure is executed"
(§1985:VII.4.4.4 GR10c; §1985:IX.4.5.4 GR10c; "If the INVALID KEY phrase is not specified in the input-output statement, a
USE AFTER EXCEPTION procedure must be associated with the file connector and that procedure is executed",
§1985:IX.1.3.5 GR3, §1985:VIII.1.3.5 GR3), and the condition arises only in the modes the statement executes in ("The
file referenced by file-name-1 must be open in the input or I-O mode at the time this statement is executed",
§1985:VII.4.4.4 GR1); in another mode the statement fails with a logic-error status ("The execution of a READ or START
statement is attempted on a file not open in the input or I-O mode", "The execution of a DELETE or REWRITE statement is
attempted on a file not open in the I-O mode", §1985:IX.1.3.4), governed by "any USE AFTER EXCEPTION procedure
associated with the file connector" (§1985:VII.4.4.4 GR11b), which requires none. Under it, READ and START would be
excused only by INPUT or I-O, REWRITE and DELETE only by I-O, WRITE by OUTPUT, I-O or EXTEND.

Every citation above passes `python scripts/spec/cite.py --check` (run 2026-11-14 for this note;
`E:/COBOL-coord/scratch/op-20261114/records-held/cites-out.txt`).

**Why the standard does not control.** The 1985 text does not define "applicable" or "appropriate": its definitions
section has no entry for either, and the I-O status clause defers the question, "The I-O status also determines whether
an applicable USE AFTER STANDARD EXCEPTION procedure will be executed ... such a procedure may be executed depending on
rules stated elsewhere" (§1985:VII.1.3.5). Two independent final adjudications read the same clauses and reached
opposite answers; both cite text that passes `cite.py --check`, and neither quotes a sentence that settles it. This
registrar searched the 1985 transcription for every use of "applicable USE" and "appropriate USE" (`cite.py --find`,
2026-11-14): each is one of the rules above, the OPEN rule "Any applicable USE AFTER EXCEPTION procedure is executed"
(§1985:VII.4.3.4 GR26b), or the I-O status paragraph; none defines the word. So this is implementor latitude (CLAUDE.md
rule 1: the standard, then GnuCOBOL, then IBM or Micro Focus).

**The choice, reading A, and its grounds.**
1. **CCVS-85 SQ148A.** Reading B would refuse SQ148A at --std 85: a sequential file whose only declarative is USE ...
   ON OUTPUT, with a READ that has no AT END. The validation suite written for this standard treats that program as
   conforming source. The suite is not authority for what the text says, but where the text is silent it is evidence of
   the intended reading, and a reading that turns a validation program into a syntax error rejects source its users
   will have.
2. **GnuCOBOL has nothing.** GnuCOBOL 3.2.0 (`cobc (GnuCOBOL) 3.2.0`, WSL Ubuntu on this host), `cobc -std=cobol85 -x`
   on the adjudicator's Q1 probes (`E:/COBOL-coord/scratch/op-20261114/records-held/gnu/`, log `cobc.log`, `cobc2.log`):
   `t1.cob` (sequential READ, only USE ... ON OUTPUT), `e4.cob` (indexed READ), `s-rw-ran-input.cob` (indexed REWRITE,
   only ON INPUT), `u1.cob` (relative WRITE, only ON INPUT) and `u1-extend-control.cob` (only ON EXTEND) all compile,
   rc=0, with no diagnostic, also under `-Wall`. So do the two controls with NO declarative at all, `t0-nodecl.cob`
   and `u0-nodecl.cob` (rc=0): GnuCOBOL does not enforce the mandatory-phrase rules at all, so it accepts both readings'
   refusals alike and gives no answer to the question. Its run of `t1` prints `AFTER 47` and of `u1` `W1 00` / `W2 DUP
   22`. IBM Enterprise COBOL and Micro Focus were not consulted (no compiler on this host).
3. **The harm comparison.** Reading A, if wrong, accepts a program whose at end or invalid key condition then takes
   the standard's own "no phrase" path at run time (the status is set and no procedure runs). Reading B, if wrong,
   rejects legal source. The project ranks rejecting legal source as the worse harm.

**Run-time half, the implementor's action after a critical status.** The witnesses below run a mode procedure on the
logic-error status its statement raises (47, 48, 49). After a critical status "the implementor determines what action is
taken" (§1985:VII.4.6.4 GR6): WiseOwl COBOL continues with the next executable statement, as after any other status;
`docs/conformance/3.5/index.md` now records it.
