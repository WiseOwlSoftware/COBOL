# PB91 — LANDED — `IF A * B > 5` past 10^38 under EC-SIZE-OVERFLOW checking compared a WRAPPED product

> ⚙ **flags:** wrong-answer, silent, RARE (needs a native product / sum past the Int128 carrier in a condition,
> argument or subscript with EC-SIZE checking enabled) · found 2026-08-18 landing [[PB75]] (which made the SDIDI
> carrier's overflow in the same positions a fatal EC — the native carrier's twin was out of that landing's scope) ·
> **landed 2026-08-18** (DEVLOG 1321).

**Measured (by reading, not yet a repro):** `NumericRenderer` emits `CobolNum.MulChecked` / `AddChecked` /
`SubChecked` (the §14.7.5 case-5 raise) only when `_rcv.InSizeError` — the ReceiverContext an ARITHMETIC statement
under ON SIZE ERROR / EC-SIZE checking renders in. A condition, a function argument or a subscript renders under
`ReceiverContext.None` (InSizeError false), so a native product past 10^38 wraps in binary (item 179 (1) documents
the wrap for the no-phrase / checking-OFF case) — also when `>>TURN EC-SIZE-OVERFLOW CHECKING ON` is in effect,
where §14.7.5 no-phrase rule 3 makes it EC-SIZE-OVERFLOW ("if an arithmetic operation on an intermediate data item
… would cause the new nonzero value to be farther from zero … than is allowed for the intermediate data item")
and §14.6.13.1.3 #4/#5/#7 the dispositions PB75 now gives the SDIDI carrier in those positions.

**Fix shape:** the checked kernels are selected by the STATEMENT's checking state, not only by the arithmetic
statement's phrase — `InSizeError` (or a sibling flag) must be true for every render under an EC-SIZE-enabled
statement (the binder knows: `EcWrap` queries the family for every statement since PB75), so a condition's product
raises `CobolSizeError` and PB75's guard dispatches it. Sweep: `AddChecked`/`SubChecked`/`MulChecked`, `DivideOrThrow`
(a zero divisor in a condition — EC-SIZE-ZERO-DIVIDE — is the same shape), `RescaleEscape` (already loud), the
`Pow` exact arm.

## As built (DEVLOG 1321)

- **THE checked-kernel decision** is `NumericRenderer.Checked => _rcv.InSizeError || (_rcv.Receiverless &&
  ecState.SizeChecking)`: the ON SIZE ERROR / EC-checked ARITHMETIC statement's threaded flag as before, PLUS every
  RECEIVER-LESS render (a relation operand, a function argument, a subscript, a SET amount, a MOVE sender) inside a
  statement whose `EcStatementInfo` enables any EC-SIZE-* name (`EcState.SizeChecking`, the ambient the
  `BoundEcChecked` emitter already sets per statement). `NumericRenderer` now takes the `EcState`.
- **The kernels raise the CONDITION**: `CobolNum.MulChecked / AddChecked / SubChecked` throw `CobolSizeError`
  ("EC-SIZE-OVERFLOW") instead of a bare `OverflowException` — inside an arithmetic statement its try already
  catches `CobolSizeError` (and reads `EcName`); in a non-arithmetic statement PB75's ambient EC-SIZE guard
  dispatches it as the fatal EC (a bare `OverflowException` escaped that guard as a crash). `DivideOrThrow`
  already raised `CobolSizeError("EC-SIZE-ZERO-DIVIDE")`; the checked NUMVAL landing (`CheckedFlag`) follows the
  same decision.
- Checking OFF is unchanged: the wrap item 179 (1) documents, and a zero divisor's 0.

**Evidence:** `2023/pb91_native_overflow_outside_arithmetic` — `A = 10^20 − 1`: `IF A * A > 5` and
`FUNCTION ABS(A * A)` under `>>TURN EC-SIZE-OVERFLOW EC-SIZE-ZERO-DIVIDE CHECKING ON` run the USE declarative
(CAUGHT=EC-SIZE-OVERFLOW) and RESUME AT NEXT STATEMENT continues; `IF 5 / Z > 1` with Z = 0 →
CAUGHT=EC-SIZE-ZERO-DIVIDE; an exception-checking PERFORM's WHEN handler runs (WHEN=EC-SIZE-OVERFLOW); a COMPUTE's
own ON SIZE ERROR still takes precedence (PHRASE=); the checking-OFF twin (probe `scratchpad/pb91/off2.cob`) still
prints the wrapped GT / LE2 with exit 0.
