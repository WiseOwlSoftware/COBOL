# PB4091 — the branch-unit hold misses a live finisher in a carrier worktree

**Sites:** `scripts/orchestrator/plan_wave.py#plan_held` (the branch-unit hold: `unit_of`, `locked_units`, the `holder or unit in locked_units` test), `scripts/prune_worktrees.py#locked`, `scripts/prune_worktrees.py#lifecycle` (the DECISION row).

Searched first: PB3653 and PB2974 (the branch-unit hold and its lock half) are `landed`; PB3987 is open but is the landing
lane's re-land inside a finisher's worktree, not the planner. No open note covers this.

## What happens

- `plan_wave.py` keys a finisher's unit by the BRANCH it finishes (`unit_of(branch)`), and holds the unit when a live agent
  locks that branch's worktree (`locked_units = {unit_of(b) for b in s.locked}`, `s.locked` from `prune_worktrees.locked`).
- A rolling wave's REVIEW finisher does not work in the reviewed branch's worktree. It gets its own worktree and branch,
  merges the reviewed branch into it (`merge_drivers.py merge <branch> --keep`), and answers the findings there. The lock
  it holds is on ITS branch, never on the reviewed one, and it writes no dispatch-ledger entry (the ledger holds the
  wave's group, already answered by the implementer's DONE report).
- So while the review finisher runs, the reviewed branch reads DECISION in the survey ("a finisher answers them, and the
  next wave plans it") and the planner plans a finisher for it. Neither the lock signal nor the ledger signal sees the live
  owner.

## Harm

Two finishers on one finding produce two heads for one branch: one is duplicate Opus work (about 0.16 weekly points
here) and its branch must then be ABANDONED by hand. A loop unit that does not inspect the worktrees launches it.

## The fix (direction)

One rule for "a live agent owns this unit": a live lock on the unit's own worktree, OR a live lock on any worktree whose
branch CONTAINS the unit branch's head (the review finisher's carrier). The planner already reads containment for DONE
carriers (kb/Work PB3150: "a FINDINGS branch that another DONE branch merely contains still gets its finisher, whose pred
names that carrier"); the live-lock half belongs in the same reader, in `prune_worktrees.py` beside `locked`, so the survey's
DECISION row reads IN FLIGHT with the carrier named and the planner holds the unit with the same answer. A self-test with a
fake liveness probe: a locked carrier that contains a FINDINGS head holds the unit; an unlocked one does not; a locked
worktree that does not contain the head holds nothing.
