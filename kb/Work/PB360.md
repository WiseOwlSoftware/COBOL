# PB360 — the silent arm that hides the next registration bug

**Rows:** `GR-14.9.47.4-2`, `GR-14.9.47.4-3` (shared with **PB345**, which owns the registration defect this arm
hides).

## The program

`<lane3 scratch>/out-b1/probe/unlock/b2.cob` — the same legal record-description-less RELATIVE file as `pa.cob`
but with the FILE STATUS clause REMOVED:
`SELECT R1 ASSIGN TO "ulpb.dat" ORGANIZATION IS RELATIVE ACCESS MODE IS RANDOM RELATIVE KEY IS RK.` /
`FD R1 RECORD CONTAINS 5 CHARACTERS.` /
`DISPLAY "BEFORE". UNLOCK R1. DISPLAY "AFTER-UNLOCK-NO-STATUS-CLAUSE". DISPLAY "EXCSTAT=[" FUNCTION
EXCEPTION-STATUS "]".`

Output: `BEFORE` / `AFTER-UNLOCK-NO-STATUS-CLAUSE` / `EXCSTAT=[<all spaces>]`, **exit 0**.

## The rule

> §14.9.47.4 GR3: The execution of the UNLOCK statement causes the value of the I-O status of the file connector
> referenced by file-name-1 to be updated

`--check 14.9.47.4 "causes the value of the I-O status of the file connector referenced by file-name-1 to be
updated"` → **OK**. It is UNCONDITIONAL — it does not depend on a FILE STATUS clause being written, because the
I-O status is a conceptual entity of the connector (§9.1.13.1). GR2 plus §9.1.13.7 item 2 (*A CLOSE or UNLOCK
statement is attempted for a file connector that is not in an open mode*, `--check 9.1.13.7` → **OK**) fix the
value at '42', and a '42' is an unsuccessful I-O completion, so with checking enabled EC-I-O-LOGIC-ERROR is to
exist and any applicable USE declarative is to run. The program should report the 42 or be refused at compile
time — never run to a clean exit 0 having done nothing.

## What the compiler does

`FileRegistry.Unlock` begins `if (!_files.TryGetValue(name, out var c)) return;` — it returns having set no
status and raised nothing. **Every other entry in the same class routes through the loud chokepoint:**

```csharp
private FileConnector Require(string name) => _files.TryGetValue(name, out var c) ? c
    : throw new InvalidOperationException($"file connector '{name}' was never registered — a compiler defect,
      not a program error (kb/Work PB140)");
```

(`FileRegistry.cs:194-197`), measured on `Open` (`a1.cob`), `Close` (`a2.cob`) and `ReadKeyed` (`a3.cob`), all of
which raise it. **Unlock is the one entry left on the old fall-through** — which is exactly why **PB345**'s crash
comes from the NEXT emitted line (`EmitStoreFileStatus`'s `CobolFile.Status`) rather than from the UNLOCK itself,
and why removing the FILE STATUS clause makes the whole defect disappear from view.

## Why this is a separate note from PB345

It is a second, independent hole: **even after the keyed registration is fixed, `Unlock`'s silent arm would keep
any FUTURE missing-connector bug invisible**, and the §1.4 loud-guard doctrine is that nothing is silent. The fix
is one line whose value is that it can never again convert a compiler defect into a clean exit 0.

**Code site:** `FileRegistry.cs#Unlock`.

## Status 2026-09-05 (PB345 implementer): the symptom is masked, the chokepoint hardening remains

PB345 (train 13) materializes the implied record description for a record-less FD, so a legal FD can no longer reach `FileRegistry.Unlock`'s missing-connector arm; `probe/b2.cob` still reproduces as written (exit 0, no status, nothing raised) only because that program has no FILE STATUS clause and EC checking is off. The remaining content of this note is the chokepoint hardening — `Require` instead of `TryGetValue`-and-return on the pre-PB140 silent arm — not the registration.

## Landed 2026-09-23 (wave 56, w56d)

**Re-probe on the wave-56 tree:** the record-less RELATIVE FD now registers (PB345), so `b2.cob` (no FILE STATUS,
checking off) runs `BEFORE` / `AFTER-UNLOCK-NO-STATUS-CLAUSE` / exit 0 — CONFORMANT under §14.6.13.1.1's default —
and the same program under `>>TURN EC-I-O CHECKING ON` terminates `EC-I-O-LOGIC-ERROR (fatal): I-O status 42`, the
§9.1.13.7 item 2 value. The observable symptom was gone; the silent arm was not.

**Fix:** `FileRegistry.Unlock` takes `Require(name)`. The sibling sweep (`grep -n "TryGetValue" FileRegistry.cs`)
found NINE more statement entries on the same pre-PB140 shape, all converted in the same change: the five governed
record verbs `ReadShared` / `ReadKeyedShared` / `WriteShared` / `RewriteShared` / `DeleteShared` INVENTED a '30'
for an unregistered name (PB140's forbidden "silently-invented status"); `Write` / `WriteAdvancing` (the report
writer's surface) and `SetRelativeKey` dropped the call (a dropped RELATIVE KEY makes the next keyed verb act on
the previous record number); `SetStatusOf` dropped a conflict status. The sequential-surface pair routes through
one new `SequentialOf` (miss → `Require`'s throw, keyed connector → `MisroutedVerb`). Deliberately LEFT lenient,
each with its reason already in its summary: `CloseIfOpen` (PB154 — an activation that raised before registering),
`Associate` (falls through to its caller's `Require`), `ExceptionFile` / `OpenModeOf` / `OpenModeIfOpen` /
`LinageCounter` / `LastReadLength` / `CurrentRecord` / `HostPathOf` (read-only queries with a documented
unknown-name answer), and the physical-table walks (`SyncHostPostures`, `SharedClose`).
**Witness:** `FileStatusDisciplineTests.StatementEntry_OnAnUnregisteredName_IsLoud` (a theory over all nine
entries) + `SequentialSurface_OnAKeyedConnector_IsLoud`.
