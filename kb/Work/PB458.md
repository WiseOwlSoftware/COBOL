# PB458 — the two SET formats whose SYNTAX rules were never written, and the bare arm that drops qualification

**Rows:** `SR-14.9.39.3-30`, `SR-14.9.39.3-33`, `SR-14.9.39.3-34`, `GR-14.9.39.4-39`. From the b2 adjudicator
`set-statement-p2` and the b2 refuter's correction of `GR-14.9.39.4-39`. **Every repro below was re-run on the
HEAD `cobol.exe` (base 89044aa0)**; all four reproduce unchanged from the 5fe593a0 pin.

## THE MECHANISM

**One shape, three instances.** §14.9.39 writes each amount-taking format as a CHOICE between a literal and an
arithmetic expression, and puts a *syntax* rule on the literal alternative and a *general* rule on the expression
alternative. COBOL.NET implements only the general rules and lets the literal alternative fall through to them —
so the compile-time screen the standard requires is replaced by a run-time clamp that produces a DIFFERENT value.

* **Format 14 (capacity).** `SetBinder.cs:377-391 DynTryBindSetCapacity` never inspects the amount at all: it
  binds it with `host.Expr.BindIndexWindowExpr(amount)` and hands it to `BoundSetCapacity`;
  `SetEmitter.cs:94-105 EmitSetCapacity` renders one truncating `long __cap = (long)(…)` and calls
  `SetCapacity` / `CapacityUpBy` / `CapacityDownBy`, whose only screen is
  `CobolDynTable.cs:134  long target = n < _min ? _min : n;`. A grep of this tree for a §14.9.39.3 SR30 citation
  finds nothing; the only nearby "SR30" is `DataBinder.Odo.cs`'s §13.18.38.3 SR30 duplicate-register-name check,
  a different rule in a different clause.
* **Format 16 (SET [SIZE OF]).** `SetBinder.cs:402-415 BindSetSize` and `:421-431 DynTrySetSize` both build
  `new BoundSetSize(p, amount, p.Item.DynLengthLimit, checkStorage)` — the declared LIMIT is carried to RUN TIME
  and `CobolDynString.SetSize` (`:49-68`) clamps there.
* **Format 16's bare arm additionally loses qualification.** `[ SIZE OF ]` is a bracket, so the format has two
  arms. The explicit arm resolves the receiver properly. The bare arm's first line is
  `SetBinder.cs:424  if (targets.Count != 1 || targets[0].dataReferenceSuffix().Length != 0) return null;` —
  aimed at subscripts, but `dataReferenceSuffix` also carries QUALIFICATION, so a qualified dynamic-length
  receiver never reaches the dynamic-length peek and falls through to the Format-1 numeric store. One rule, two
  arms, one written (`feedback_two_arm_dispatch`).

**The runtime's own comment records the missing screen as if it existed.** `CobolDynString.cs:45-47` says "The
integer-2 literal form is compile-time bounded by SR34, so these runtime raises pertain to the
arithmetic-expression-5 form", and `docs/CONFORMANCE.md:262` repeats it — "The integer-2 literal form is
compile-time bounded by SR34, so its out-of-range cases are compile diagnostics, not this runtime EC."
Measured false (below). That is the sharpest single fact in this note: a determination in the conformance
document rests on a screen nobody wrote.

### SR30 — Format 14, `05 WS-E PIC 9(3) OCCURS DYNAMIC CAPACITY IN WS-CAP FROM 2 TO 10.` (minimum 2, expected 10)

```
sr30_to_below_min.cob        SET WS-CAP TO 1.        -> CAP=[  2]   exit 0, no diagnostic
sr30_to_above_expected.cob   SET WS-CAP TO 20.       -> CAP=[ 20]   exit 0, no diagnostic
sr30_to_negative.cob         SET WS-CAP TO -1.       -> CAP=[  2]   exit 0, no diagnostic
sr30_upby_negative.cob       SET WS-CAP UP BY -3.    -> CAP=[  2]   a DECREASE from an UP BY
sr30_downby_negative.cob     SET WS-CAP DOWN BY -3.  -> CAP=[  5]   an INCREASE from a DOWN BY
controls: sr30_to_inrange.cob (TO 7 -> CAP=[  7]);  sr30_no_expected.cob (no TO in the OCCURS clause,
          TO 99 -> CAP=[ 99]) — correct, SR30's expected-capacity half is conditioned on TO.
```

**Expected:** each of the five is a compile-time diagnostic naming §14.9.39.3 SR30. The two sign cases are why
this is filed `wrong_answer` and not merely `under_rejects`: the program does not just compile, it runs the
OPPOSITE of what it says.

### SR33 — Format 16's bare arm loses a qualified receiver

```
$ cobol.exe sr33_qualified_bare.cob --std 2023 --run
    01 G.  05 D PIC X DYNAMIC LENGTH LIMIT IS 8.   …   MOVE 'ABCD' TO D OF G.   SET D OF G TO 2.
Unhandled exception. CobolNet.Runtime.NotImplementedCobolFeatureException: … arithmetic into a
non-fixed-point target 'D'
   at _PRG_PSR33QUALIFIEDBAR.__Dispatch(…)

$ cobol.exe sr33_qualified_sizeof.cob --std 2023 --run   # the SAME program with SET SIZE OF D OF G TO 2.
D=[AB] L=2
$ cobol.exe sr33_ok_bare.cob --std 2023 --run            # unqualified bare form
D=[ABC] L=3
```

The isolating pair proves the GUARD, not the qualification, is the cause. **Expected:** `SET D OF G TO 2.` sets
the current length to 2 and prints `D=[AB] L=2`, exactly what the explicit arm already produces. Today it
compiles clean (no diagnostic at all) and terminates on a raw runtime exception — legal source rejected, at the
worst possible moment.

### SR34 — Format 16, `01 D PIC X DYNAMIC LENGTH LIMIT IS 8.`

```
sr34_negative.cob         SET SIZE OF D TO -1.   -> L=0    exit 0, no diagnostic
sr34_over_limit.cob       SET SIZE OF D TO 99.   -> L=8    exit 0, no diagnostic
sr34_over_limit_bare.cob  SET D TO 99.           -> L=8    exit 0, no diagnostic
controls: sr34_at_limit.cob (TO 8 -> L=8, legal);  sr34_no_limit.cob (no LIMIT phrase, TO 99 -> L=99,
          correct — §13.18.19.4 GR2 then makes the maximum implementor-defined)
```

**Expected:** with `LIMIT IS 8`, both `TO -1` and `TO 99` are compile-time diagnostics naming §14.9.39.3 SR34,
in BOTH arms. §14.9.39.4 GR38's clamp-and-signal branch is written for arithmetic-expression-5 alone — for
integer-2 GR38 is unconditional precisely BECAUSE SR34 has already guaranteed the literal is in range. The
compiler substitutes the expression rule for the syntax rule it never wrote, and a program the standard requires
it to reject silently gets a different length.

## THE CODE SITES AND THE SHAPE OF THE REPAIR

| site | arm | repair |
| --- | --- | --- |
| `Binding/Procedure/Verbs/SetBinder.cs:377-391` `DynTryBindSetCapacity` | Format 14 amount | screen the LITERAL alternative against `OccursSpec`'s FROM/TO before binding |
| `CodeGen/Verbs/SetEmitter.cs:94-105` `EmitSetCapacity` | Format 14 emit | unchanged once the screen lands; the runtime clamp stays as GR30's answer for the EXPRESSION alternative |
| `Runtime/Values/Tables/CobolDynTable.cs:122-138` `SetCapacity` | runtime clamp | keep, but stop being the only bound |
| `Binding/Procedure/Verbs/SetBinder.cs:402-415` `BindSetSize` | Format 16 explicit | screen integer-2 against `DynLengthLimit` |
| `Binding/Procedure/Verbs/SetBinder.cs:421-431` `DynTrySetSize` | Format 16 bare | **narrow the guard to SUBSCRIPTS**, or better, delete it and resolve the receiver with the same `ResolveReceiving` the explicit arm uses |
| `docs/CONFORMANCE.md:262` | the determination | stops being false once the screen exists (⛔ this note does NOT edit that file) |

⛔ **Do not write three inline literal tests** (CLAUDE.md rule 5). §14.9.39 has a literal alternative on Format
14's integer-1, Format 16's integer-2 and Format 2's integer amount, and each states its own bound and its own
diagnostic. The structural repair is ONE amount-screen landing at bind time that takes (the literal, the
declared bound triple, the format's rule id) and lets each format name its own rule — the same landing PB459
needs for the *general*-rule side. Written as three `if`s, the next amount-taking format is the fourth copy.

Equally: the `DynTrySetSize` guard must not merely be narrowed to `subscripts only`. Both Format-16 arms must
resolve the receiver through the ONE receiver resolver; a peek that re-implements resolution is the two-arm
shape that produced this bug. And whichever way it lands, a golden for the QUALIFIED bare form ships with it,
or the arms drift apart again.

## LANDED — 2026-09-19 (wave 39, group SET-FORMATS)

**ONE amount screen, not three inline literal tests.** `SetLiteralAmount.Of` answers "is this operand
integer-1 / integer-2?" through `SoleOperand.NumericLiteral` — THE §8.3.3.3.2 rule-2 contiguity reading shared
with DEFINE, CONSTANT, EVALUATE and the relation condition, so a sign written adjacent to the digits is inside
the literal and a separated `TO - 1` stays an arithmetic expression under the general rule. `SetAmountBound`
carries the declared bound triple plus the format's own operand name and rule id, so each call site names its
own rule and the next amount-taking format is a bound rather than a fourth `if`. `COBOLNET2113`.

⚠ **THE NOTE OVERSTATED THE POPULATION, and the correction is part of the landing.** §14.9.39.2 writes a
literal alternative in exactly TWO places — Format 14's `{ integer-1 | arithmetic-expression-4 }` and
Format 16's `{ integer-2 | arithmetic-expression-5 }`. Format 2's amount is `arithmetic-expression-2` with no
literal alternative and no syntax rule at all (the printed figure, and §14.9.39.4 GR4), as are Format 1's
`arithmetic-expression-1` and Format 10's `arithmetic-expression-3`. §5.5 rule 1 is what makes `integer-n` a
LITERAL: "it refers to a fixed-point integer literal that shall be unsigned and nonzero unless otherwise
specified in the associated rules" — SR30's "nonnegative" and SR34's "non-negative" being that
otherwise-specification.

⚠ **TWO OF THE NOTE'S FIVE SR30 MEASUREMENTS NO LONGER HELD ON TODAY'S TREE.** `SET WS-CAP UP BY -3` and
`SET WS-CAP DOWN BY -3` do not invert any more: [[PB459]] landed `EmitSetCapacity`'s `LandAmount` guard, so
GR29's nonnegative-integer condition is enforced at run time and the SET is simply unsuccessful. They are now
COMPILE diagnostics because SR30's nonnegative half is a syntax rule over the literal. The three TO cases
(`TO 1` below the minimum, `TO 20` above the expected capacity, `TO -1`) reproduced exactly as written.

**DETERMINATION (⚠ owner may overturn).** SR30's "if TO is specified" reads as the SET statement's own TO
alternative, not the OCCURS clause's TO phrase. Rejected reading: the OCCURS TO. Why: under it, "not less than
the minimum capacity" — which comes from FROM, not TO — would be conditioned on an unrelated phrase, and the
second half's own "if specified" would be redundant; and UP BY / DOWN BY write a DELTA, which "not less than the
minimum capacity" cannot be about. So UP BY and DOWN BY take the nonnegative half alone.

**Format 16 is ONE bind for BOTH arms.** `DynTrySetSize` is deleted; `BindSetSize` takes the receiving list and
resolves through the same `ExpressionBinder.ResolveReceiving` the explicit arm always used. The deleted guard's
`dataReferenceSuffix().Length != 0` test was aimed at subscripts and also excluded QUALIFICATION; §13.16.3 SR18
leaves an OCCURS clause impossible on a DYNAMIC LENGTH entry, so the subscript half had nothing legal to exclude
and the qualification half was pure loss. `SET D OF G TO 2` now prints `D=[AB] L=2`, identical to the explicit
arm, and is golden-pinned at `conformance:2023/pb458_set_size_qualified_bare`.

**`docs/CONFORMANCE.md`'s determination is now TRUE and names its site.** The sentence "The integer-2 literal
form is compile-time bounded by SR34" rested on a screen nobody had written; it now cites
`SetBinder.BindSetSize` over `SetLiteralAmount` and COBOLNET2113. (The twin claim the note found in
`CobolDynString.cs` is not in this tree any more.)

**A GREEN GOLDEN PINNED NON-CONFORMING SOURCE and was re-derived in the same change set**
(`feedback_green_test_can_hold_a_gap_open`): `conformance:2014/dyn_capacity_bounds` wrote `SET WS-CAP TO 9` over
`FROM 2 TO 4` — a literal above the expected capacity, which SR30 forbids — to demonstrate a RUN-TIME rule
(§8.5.1.9.1, "an upper value … which may be exceeded with a nonfatal exception"). The amount is now written as a
data item, i.e. arithmetic-expression-4, which is the operand that rule is about; the output is unchanged.
