# PB4536 — initialize-table-propagates-filler: INITIALIZE of a table without WITH FILLER copies the first occurrence's FILLER bytes over later occurrences

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

INITIALIZE of a group that contains an OCCURS table, with no WITH FILLER phrase, overwrites the FILLER items of the
second and later occurrences with the content of the first occurrence. ISO excludes FILLER items from INITIALIZE unless
WITH FILLER is written, so those bytes must keep their content. The fault shows only when occurrences differ before the
INITIALIZE: after `MOVE ALL "y" TO T` (every occurrence alike) the result is correct.

## Minimal test case

Free reference format (`-free`).
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. INITFIL2.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 T.
   05 ROW OCCURS 3 TIMES.
      10 FILLER PIC X VALUE "[".
      10 CELL   PIC 9 VALUE 0.
      10 FILLER PIC X VALUE "]".
PROCEDURE DIVISION.
    MOVE "x" TO ROW (2)
    DISPLAY "BEFORE [" T "]"
    INITIALIZE T
    DISPLAY "AFTER  [" T "]"
    MOVE ALL "y" TO T
    INITIALIZE T
    DISPLAY "ALLY   [" T "]"
    STOP RUN.
```

## Environment

cobc (GnuCOBOL) 3.2.0 on WSL2 Ubuntu. Command: `cobc -x -free -std=cobol2014 -o p initialize-table-propagates-filler.cob && ./p`
(cobc issued no diagnostic, compile exit code 0; the host C compiler's `_FORTIFY_SOURCE redefined` warning is an environment artifact of this WSL install; run directly, exit code 0).

## Observed result

```
BEFORE [[0]x  [0]]
AFTER  [[0][0][0]]
ALLY   [y0yy0yy0y]
```
Exit code 0. The second occurrence's two FILLER bytes changed from `x` and space to `[` and `]`.

## Expected result (per ISO)

§14.9.20.4 5) a) 2. excludes FILLER items from the receiving operands: "If the FILLER phrase is not specified, elementary
data items with an explicit or implicit FILLER clause." §14.9.20.4 5) b) 2. makes each occurrence of a table element a
separate possible receiving operand: "If the elementary data item is a table element, each occurrence of the elementary
data item is a possible receiving-operand." Only CELL of each occurrence is set (to zero, its category's default); every
FILLER keeps its content. The rule holds in the 2014 edition the `-std` flag claims (`docs/VERSION_CHANGE_REFERENCE.md` lists no
2014→2023 change to these INITIALIZE rules; its only INITIALIZE row is the new 2023 OPTIONS clause). Expected:
```
BEFORE [[0]x  [0]]
AFTER  [[0]x0 [0]]
ALLY   [y0yy0yy0y]
```

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`) prints the expected output above, with no diagnostic.

## Fix site

cobc/codegen.c: the INITIALIZE code generation initializes the first occurrence of a table and then copies that
occurrence over the remaining ones (`propagate_table`, which emits `memcpy (b_ptr + len, b_ptr, len)`), reached from
`output_initialize` when the table's items qualify for the copy. The copy takes the whole occurrence, FILLER bytes
included, so it is only valid when no item of the occurrence is excluded (WITH FILLER, or an occurrence without FILLER,
REDEFINES or other excluded item). Both functions are present in the GnuCOBOL 3.2 release source (cobc/codegen.c).

cobc (GnuCOBOL) 3.2.0, WSL2 Ubuntu, `cobc -x -free -std=cobol2014 -o p prog.cob && ./p`.

```
01 T.

      10 FILLER PIC X VALUE "[".

      10 FILLER PIC X VALUE "]".
...
    MOVE "x" TO ROW (2)
    INITIALIZE T
    DISPLAY "[" T "]"
```
Observed `[[0][0][0]]`; expected `[[0]x0 [0]]`. ISO/IEC 1989:2014 INITIALIZE general rule 5 a) 2 excludes FILLER items
when WITH FILLER is not specified, and rule 5 b) 2 treats each occurrence separately, so only CELL changes. The generated
code appears to initialize occurrence 1 and copy it whole to occurrences 2 and 3 (codegen.c `propagate_table`), which also
copies the FILLER bytes. When all occurrences already hold the same FILLER content the result is correct.
