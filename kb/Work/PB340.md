# PB340 — the phrase is carried all the way to emission and then dropped

**Rows:** `GR-14.9.30.4-22`.

## The program

`<lane3 scratch>/out-b1/probe/gr22-advlock/pb3gr22.cob` — two RELATIVE connectors on one host file, both
`SHARING WITH ALL OTHER` / `LOCK MODE IS MANUAL` / `ACCESS DYNAMIC`; seed RRN 1 = ALPHA, RRN 2 = BRAVO;
`MOVE 1 TO A-KEY / READ F-A WITH LOCK` ('00'), then
`READ F-B NEXT ADVANCING ON LOCK AT END ... NOT AT END ...`.

Observed: `READA=00` / `ADVB-ST=51`, and **neither phrase branch ran**.

## The rule

> §14.9.30.4 GR22: [with ADVANCING ON LOCK on a file open for file sharing and the record to be made available
> locked by another file connector, the result is] as if the locked record were read and then the same READ
> statement were executed [repeated until an unlocked record is read or end of file is reached]. A record
> operation conflict condition does not exist.

Both `--check 14.9.30.4` → **OK**. RRN 1 is therefore skipped, RRN 2 (BRAVO) is made available, the I-O status is
'00' and the NOT AT END imperative runs. **Status '51' is precisely what GR22 says cannot arise.**
`docs/CONFORMANCE.md` §5 claims Annex A.4.7 (file sharing and record locking) with the note *SHARING/LOCK
MODE/RETRY on every organization*, so this is not a documented-non-support boundary.

## What the compiler does

The two-arm dispatch shape in its purest form: the phrase is carried FULLY up to emission and only the code that
would honour it is missing. `CobolIO.g4#readAdvancingOnLock` parses it; `KeyedIoBinder.BindRead` sets
`BoundKeyedRead.AdvancingOnLock`; `VersionConformancePass` edition-gates on that same property (so a 1985 program
is correctly rejected) — and then `KeyedIoEmitter.EmitRead`'s governance call is
`RuntimeApi.FileReadLockGovern(name, st, RuntimeRecordLock(rd.Lock), retryKind, retryAmount)`: **there is no
advancing-on-lock parameter in that API at all**, and `rd.AdvancingOnLock` appears nowhere in
`KeyedIoEmitter.cs`. The GR22 loop lives only in `FileRegistry.ReadShared`, which begins
`if (!_files.TryGetValue(name, out var c) || c is not SequentialConnector f) { image = ""; return false; }`.

Worse than a missed skip: because `ReadLockGovern` runs AFTER the keyed connector has already advanced its file
position indicator, the '51' path also leaves the FPI moved, which GR10 a) forbids — that half is **PB338**.

## The fix shape

Give the keyed read the same PRE-read governed entry the sequential one has — a keyed `ReadShared` carrying the
advancing-on-lock loop — rather than bolting a parameter onto the post-read `ReadLockGovern`; the sequential arm
already proves the shape, and **PB338**'s peek-then-commit split is the same restructuring.

**And add the drift test this whole family needs:** every phrase property on a `BoundRead` / `BoundKeyedRead` is
consumed by its emitter. That one assertion would have caught this row, **PB317** (OPEN NO REWIND) and
**PB334** (the sequential READ direction) — three rows, three statements, one absent invariant.

**Code sites:** `KeyedIoEmitter.cs#EmitRead` · `FileRegistry.cs#ReadShared`, `#ReadLockGovern` ·
`src/Cobol.Net.Compiler/CodeGen/Roslyn/RuntimeApi.cs#FileReadLockGovern`.
