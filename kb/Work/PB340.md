# PB340 — the phrase is carried all the way to emission and then dropped

**Rows:** `GR-14.9.30.4-22`.

## The program

`<lane3 scratch>/out-b1/probe/gr22-advlock/pb3gr22.cob` — two RELATIVE connectors on one host file, both
`SHARING WITH ALL OTHER` / `LOCK MODE IS MANUAL` / `ACCESS DYNAMIC`; seed RRN 1 = ALPHA, RRN 2 = BRAVO;
`MOVE 1 TO A-KEY / READ F-A WITH LOCK` ('00'), then
`READ F-B NEXT ADVANCING ON LOCK AT END ... NOT AT END ...`.

Observed: `READA=00` / `ADVB-ST=51`, and **neither phrase branch ran**.

## The rule

> §14.9.30.4 GR22: [with ADVANCING ON LOCK on a file open for file sharing and the record to be made available
> locked by another file connector, the result is] as if the locked record were read and then the same READ
> statement were executed [repeated until an unlocked record is read or end of file is reached]. A record
> operation conflict condition does not exist.

Both `--check 14.9.30.4` → **OK**. RRN 1 is therefore skipped, RRN 2 (BRAVO) is made available, the I-O status is
'00' and the NOT AT END imperative runs. **Status '51' is precisely what GR22 says cannot arise.**
`docs/CONFORMANCE.md` §5 claims Annex A.4.7 (file sharing and record locking) with the note *SHARING/LOCK
MODE/RETRY on every organization*, so this is not a documented-non-support boundary.

## What the compiler does

The two-arm dispatch shape in its purest form: the phrase is carried FULLY up to emission and only the code that
would honour it is missing. `CobolIO.g4#readAdvancingOnLock` parses it; `KeyedIoBinder.BindRead` sets
`BoundKeyedRead.AdvancingOnLock`; `VersionConformancePass` edition-gates on that same property (so a 1985 program
is correctly rejected) — and then `KeyedIoEmitter.EmitRead`'s governance call is
`RuntimeApi.FileReadLockGovern(name, st, RuntimeRecordLock(rd.Lock), retryKind, retryAmount)`: **there is no
advancing-on-lock parameter in that API at all**, and `rd.AdvancingOnLock` appears nowhere in
`KeyedIoEmitter.cs`. The GR22 loop lives only in `FileRegistry.ReadShared`, which begins
`if (!_files.TryGetValue(name, out var c) || c is not SequentialConnector f) { image = ""; return false; }`.

Worse than a missed skip: because `ReadLockGovern` runs AFTER the keyed connector has already advanced its file
position indicator, the '51' path also leaves the FPI moved, which GR10 a) forbids — that half is **PB338**.

## The fix shape

Give the keyed read the same PRE-read governed entry the sequential one has — a keyed `ReadShared` carrying the
advancing-on-lock loop — rather than bolting a parameter onto the post-read `ReadLockGovern`; the sequential arm
already proves the shape, and **PB338**'s peek-then-commit split is the same restructuring.

**And add the drift test this whole family needs:** every phrase property on a `BoundRead` / `BoundKeyedRead` is
consumed by its emitter. That one assertion would have caught this row, **PB317** (OPEN NO REWIND) and
**PB334** (the sequential READ direction) — three rows, three statements, one absent invariant.

**Code sites:** `KeyedIoEmitter.cs#EmitRead` · `FileRegistry.cs#ReadShared`, `#ReadLockGovern` ·
`src/Cobol.Net.Compiler/CodeGen/Roslyn/RuntimeApi.cs#FileReadLockGovern`.

## Landed — 2026-09-05

`GR-14.9.30.4-22` → **CONFORMS**. Reproduced first on the merged PB331 base (`READA=00 / ADVB-ST=51` on RELATIVE
and `READXA=00 / ADVXB-ST=51` on INDEXED, neither phrase branch taken); after the fix both read `BRAVO|00`.

**The mechanism is ONE governed FORMAT-1 read, not a per-organization loop.** The note's own fix shape — "give
the keyed read the same PRE-read governed entry the sequential one has" — was the wrong half of the truth and is
corrected here. GR22 needs no pre-read peek on any organization, because the rule's model IS post-read ("as if
the locked record were read and then the same READ statement were executed") and because "A record operation
conflict condition does not exist", so GR10 a)'s unchanged-FPI obligation never applies to it. So
`FileRegistry.ReadShared` became the one governed Format-1 read for sequential, relative and indexed — returning
the I-O status, with the physical step behind `ReadFormat1Step` and the pre-read lock identity behind
`PeekFormat1RecordId` (non-empty only for the sequential walk, which is the only organization that can name the
next record before reading it). The GR22 skip is a single `continue`. GR9's conflict check moved out to
`ConflictOnLockedRecord`, shared with the Format-2 `ReadLockGovern`. `KeyedIoEmitter.EmitRead` routes
`KeyedReadKind.Next`/`Previous` through the shared entry and keeps `ReadLockGovern` for the Format-2 random read,
which is correct for it: no next record to advance to, and no ADVANCING phrase in the Format-2 general format.

**PB338 was NOT taken and was not needed.** Its peek-then-commit split is about the '51' leg's file position
indicator; GR22 has no '51' leg. The keyed Format-1 arm's post-read '51' is unchanged in behaviour by this
landing and still belongs to PB338.

**§14.9.30.3 SR9 came with it (PB335).** `READ f ADVANCING ON LOCK` on an ACCESS DYNAMIC file bound as a
Format-2 random read, because the implied-NEXT test read two of SR9's three members. Without that term the
skip-scan is unreachable for the one spelling SR9 exists to name, so it was inseparable: `SR-14.9.30.3-9` →
**CONFORMS** and PB335 flips to landed with it.

**The drift test this family needed is in.**
`unit:BoundIoPhraseConsumptionDriftTests.EveryPhrasePropertyOfABoundIoNode_IsReadByItsEmitter` asserts that every
phrase property declared by any of the eight bound I-O nodes is read by its emitter; it was proved to fail by
dropping `rd.AdvancingOnLock` once. It cannot see PB334's absent direction FIELD — no reflection over the node
can — so that half still needs its own golden.

**Goldens.** `2002/pb340_advancing_on_lock_relative` and `2002/pb340_advancing_on_lock_indexed` (the repeated
skip, the SR9 spelling, PREVIOUS, both the end-of-file and beginning-of-file tails, each with a plain-READ '51'
control); `negative/pb340-advancing-on-lock-keyed-85` and `negative/pb340-advancing-on-lock-sequential-85` pin
the COBOL-2002 gate (COBOLNET0900) on both arms — nothing exercised it before, because the version-matrix row
for the record-lock family writes `READ … WITH LOCK`.
