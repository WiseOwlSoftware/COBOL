# PB337 — the INTO operand is resolved and never inspected

**Rows:** `SR-14.9.30.3-1`, `SR-14.9.30.3-2`, `SR-14.9.34.3-2`, `SR-14.9.34.3-3`.

## The programs

**READ SR1** (`out-b1/probe/sr1/into2rec.cob`): an FD with TWO record descriptions — `01 REC-A / 05 A-1 PIC X(4)`
and `01 REC-B / 05 B-1 PIC 9(4) COMP` — and `READ SQF INTO WS-NUM` with `WS-NUM PIC 9(4) COMP`. Compiles, prints
`GOT=0000`.

**READ SR2** (`out-b1/probe/sr2/strong.cob`): two record areas in the FD, `01 T1 TYPEDEF STRONG` and
`01 WS-STRONG TYPE T1`; `READ SQF INTO WS-STRONG`. Compiles, prints `GOT=1234`.

**RETURN SR2** (`out-b1/probe/p6/p6.cob`): SD SF with TWO record descriptions — `01 S-REC.` (an alphanumeric
group) and `01 S-NUM PIC 9(6).` (elementary, category numeric) — and `RETURN SF INTO WS-RECV`. Compiles and runs,
printing `INTO=1ONE` / `INTO=2TWO`.

**RETURN SR3** (`out-b1/probe/p7/p7.cob`): `01 TA TYPEDEF STRONG.` + `01 WS-RECV TYPE TA.` with an SD carrying
TWO record areas, neither strongly typed. Compiles and runs. **The control `p8.cob` proves the strong-type
machinery is live:** the explicit `MOVE PLAIN TO WS-RECV` is rejected `COBOLNET1533`.

## The rules

> §14.9.30.3 SR1: The INTO phrase may be specified in a READ statement: [a) when the file description entry
> contains at most one record description entry, or b) when identifier-1 and all record-names are alphanumeric
> group items or elementary items of category alphanumeric or national]

> §14.9.34.3 SR2 and SR3 are the RETURN twins, SR3 adding: if identifier-1 is a strongly-typed group item there
> shall be exactly one record area subordinate to the SD, and it shall be a strongly-typed group item of the
> same type.

`--check 14.9.30.3 "The INTO phrase may be specified in a READ statement"` → **OK**; both RETURN rules
`--check 14.9.34.3` → **OK**. None of the four probes satisfies its rule's arms.

## What the compiler does

Both READ binders resolve the INTO operand with the identical unexamined line and no caller screens it:
`grep -rn 'readInto|ReadInto' src/Cobol.Net.Compiler/` yields exactly those two lines.
`SortBinder.BindReturn`'s INTO arm (lines 261-267) resolves the reference and stores the `Place`; it never reads
`file.Records.Count`, never reads a record's `Pic.Category` or `IsGroup`, and never calls `StrongTypeModel` —
`grep` for `14.9.34.3` over `src` returns only the SR1 message and an SR4 comment.

**The strong-type screens exist and are unreachable from here.** `StrongTypeModel` checks live in `DataBinder`,
`StatementValidation` (line 85, the EXPLICIT MOVE receiver), `ConditionBinder`, `CallBinder`,
`StringUnstringBinder`, `AcceptDisplayBinder` and `ReferenceResolver` — none reachable from READ's or RETURN's
implicit move (GR4 b / GR5 b). So a strongly-typed group can be filled from an alphanumeric record image, which
nothing else in the compiler allows.

**And the one descriptor that would say so is in the frozen legacy engine.** `CBL1704` (*READ INTO target must
be alphanumeric or group*) is DECLARED in `Cobol.Net.Frontend` and reported only from
`src/CobolSharp.Compiler/Semantics/Bound/BoundTreeValidator.cs`.

## A correction to the batch input, recorded because it nearly cost a landed row

The same adjudication finding also reported §14.9.30.3 **SR6** (*None of the phrases ADVANCING, AT END, NEXT, NOT
AT END, or PREVIOUS shall be specified if ACCESS MODE RANDOM is specified*) as having no implementation anywhere
in the greenfield, quoting the comment above the check as if it were a decline. **It is false on today's tree,
and it was re-measured rather than inherited:** `KeyedIoBinder.BindRead` lines 56-66 build the present-phrase
list and call `ctx.Validation.ScreenForbiddenPhrase`, and both of the finding's own probes are REJECTED by this
worktree's freshly built compiler —

```
random_v.cob(28,12): error COBOLNET1720: the AT END / NEXT phrase shall not be specified for a READ statement
                    that references a file whose file control entry specifies ACCESS MODE RANDOM (ISO 14.9.30.3 SR6)
adv_v.cob(28,12):   error COBOLNET1720: the ADVANCING / AT END phrase ... (ISO 14.9.30.3 SR6)
```

`SR-14.9.30.3-6` carries CONFORMS / OK with `conformance:negative/read-phrase-random-access`, landed by
`kb/Work/PB144`, so recording the finding's NOT-IMPLEMENTED verdict would have reversed a closed, tested row on
false evidence. **The record was excluded from batch b1** and the row keeps its verdict. Fourteen other claims
across six findings were re-measured on the same build and all held; this was the only one.

SR6's forbidden-phrase SET is nonetheless relevant here in one way: **PB335** notes that one derived predicate
over `{ADVANCING, AT END, NOT AT END}` would serve SR9's implied-NEXT trigger and SR6's ban alike, replacing the
longhand list ten lines above it.

## The fix shape

ONE *INTO receiver admissibility* validator in `StatementValidation`, called by `SequentialIoBinder.BindRead`,
`KeyedIoBinder.BindRead` and `SortBinder.BindReturn`, so the next INTO-bearing verb inherits the rule instead of
re-deriving it — never two RETURN-local `if`s. It is the sibling of **PB348**, which moves the implicit MOVE
itself to bind time; landing them together means the receiver is screened AND the move is checked by the one
MOVE validator.

**Code sites:** `SequentialIoBinder.cs#BindRead` · `KeyedIoBinder.cs#BindRead` · `SortBinder.cs#BindReturn` ·
`StatementValidation.cs` (where the validator belongs).

## Landed — 2026-09-13, on main 90ec658e (compiler tree 1840778e)

All four rows now CONFORM. **ONE screen, at the ONE place all three INTO arms already funnel through.** The fix
shape in this note said the validator belongs in `StatementValidation`, called by the three binders; the first
half stands and the second was superseded by PB348 (train 20), which landed `MoveBinder.BindIntoPhrase` as the
single site the sequential READ, the keyed READ and the sort RETURN all reach. `CheckIntoReceiver` is therefore
called from THERE, once, and a fourth INTO-bearing verb inherits the rules by construction rather than by an
edit — which is what the note asked for, reached by a shorter route. Two drift tests pin the shape
(`ImplicitMoveConstructionDriftTests.TheIntoReceiverScreen_IsCalledOnlyFromThePhraseBinder` and
`.AnIntoPhraseRulesRow_ReachesOnlyBindIntoPhrase`); both were proved red before being trusted.

**What re-probing on today's tree changed in the note's own account.** The two STRONG-receiver probes no longer
reproduce as written: PB348's bind-time implicit move puts the record area through `CheckStrongMove`, so
`READ … INTO` a strongly-typed group from an ordinary record area is already refused as COBOLNET1533 — the
§14.9.25.3 SR2 rule, not §14.9.30.3 SR2. The rows were still GAPs, because what SR2/SR3 add is a **COUNT**
obligation no MOVE screen can express: `CheckStrongMove` inspects only `FileModel.AreaRecord`, so a file whose
LARGEST record happens to be a strongly-typed group of the right type passed everything while a second record
area sat unseen. The isolating probe for that shape compiled clean, and it is now
`conformance:negative/pb337-read-into-strong-record-areas`, kept deliberately distinct from its PB348 sibling so
that removing either check fails a test. The two ADMISSIBILITY probes reproduced exactly as the note recorded
(`GOT=0001`; `INTO=1ONE` / `INTO=2TWO`).

**The division of labour, stated because it is the part a later reader will want to re-litigate.** Each of
SR2/SR3's two sentences is enforced where it can be decided: the count here (COBOLNET1995), the same-type
sentence by `CheckStrongMove` (COBOLNET1533), because that second sentence is the identical predicate over the
identical pair §14.9.25.3 SR2 applies to the implicit move's sender — the record area. Writing it twice is the
defect shape this repository keeps hitting. And a strongly-typed identifier-1 draws COBOLNET1995 ALONE, not also
the admissibility diagnostic: §13.18.29.4 GR3 excludes a strongly-typed group from the alphanumeric group items,
so SR1 arm b) can never admit one, leaving arm a) — the very count SR2 tests. For that receiver the two rules
impose the same condition and the specific one speaks.

**The root cause was one rule written down twice, and the sweep reached three rules that have nothing to do with
READ or RETURN.** §13.18.29.4 GR3 — what an *alphanumeric group item* IS — lived in `ItemCategory.Admits` as
`item.IsGroup` (the structural conjunct alone) and, separately and completely, in a private
`DataBinder.GroupValue.IsAlphanumericGroup`. The INCOMPLETE copy is the one the existing callers read, so
§12.4.5.2 SR7 (`ASSIGN … USING`) and the record keys of §12.4.5.12.3 SR2 / §12.4.5.6.3 SR2 each admitted a
strongly-typed or variable-length group. `ItemCategory.IsAlphanumericGroup` is now the one spelling, all three
conjuncts, and `ItemCategory.Face` names the two exclusions instead of answering *"not an elementary or group
data item"* for every plain group — false, but unreachable while no group could fail the predicate. Witness:
`conformance:negative/pb337-assign-using-strong-group`.

No edition gate is written and the question was asked: the admissibility rule is an all-editions rule, and the
shapes that make the 2023 wording narrower than its '85 ancestor (an ALPHANUMERIC group item rather than any
group item; category national) cannot be DECLARED below the edition that introduces them, so one predicate is
per-edition-correct by construction. The positive golden `pb337_into_receiver_admissible` ships in all four
edition legs and is the OVER-REJECT guard: its case A is a category-NUMERIC identifier-1 over a single-record
FD, which arm a) admits and a screen reading only arm b) would have rejected.

**Landed with:** FILES design D24 · COBOLNET1994, COBOLNET1995 · goldens `pb337_into_receiver_admissible`
(85/2002/2014/2023) and `pb337-{read,return}-into-not-admissible`, `pb337-{read,return}-into-strong-record-areas`,
`pb337-assign-using-strong-group` · verdict batch `pb337-into-receiver-admissibility` (GAP 2561 → 2557).

**Not closed by this note, and reported as a new finding rather than fixed here:** an FD's multi-01 record-area
sharing is modelled as a synthesized REDEFINES, so a strongly-typed record description beside any second record
description is refused by §13.18.57.3 SR4 / §13.18.44.3 SR14 (COBOLNET1532 / COBOLNET1697) — a declaration-time
rule reporting on a sharing relationship §13.4.2 establishes without a REDEFINES clause. It does not affect this
mechanism's verdicts (SR2/SR3 reject that shape anyway) but it is the wrong diagnosis for it.
