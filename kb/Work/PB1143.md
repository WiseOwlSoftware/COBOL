# PB1143 — LANDED

## Landed (wave w0930-numeric — one bundled commit with the seven siblings of this note)

Re-probed first on the implementer's own build: `MULTIPLY A BY C GIVING R` with A = 1.5, C = 2.25 (both `PIC 9V9(30)`) stored
`…7300173` (a wrapped product); `COMPUTE R = A * C`, Format 1, and the DIVIDE sibling (`PIC 9(10)` ÷ `PIC 9V9(20)` into
`PIC 9(10)V9(10)`) did the same.

**Design correction (rule 5 — the stated scope was "one unchecked multiply").** What decides whether a native operation
leaves the Int128 carrier is a FACT ABOUT THE OPERANDS the renderer did not have: `NumX.Digits`, an upper bound on the
decimal digits of the unscaled value (a field: `PicInfo.UnscaledDigitBound` — a COMP-5 item owns its container range; a
literal: its digit count; the exact sum / difference / negation / product derive theirs). `NumericRenderer.Multiply` now
decides at compile time from N and M: N+M ≤ 38 — a bare multiply; N+M > 38 — the exact 256-bit product on the SDIDI
(`CobolDec.MulToOdd` — 34 digits by ROUND-TO-ODD: an inexact product keeps an odd last digit, so the receiver's ONE rounding
(§14.7.4.3) in any mode equals rounding the exact product; a receiver holds ≤ 31 digit positions. A first draft truncated
and lost the sticky information — ROUNDED AWAY-FROM-ZERO stored …002 for 1 + 2e-30 + 1e-60 — found by the self-review);
unknown bound — `MulChecked` in EVERY statement (a native product never wraps). The same bound drives PB621. `CobolNum.Divide`'s
radix alignment never wraps either (SDIDI `DivToOdd` path past the carrier, one rounding at the result scale; a quotient past
the carrier is EC-SIZE-OVERFLOW).
GnuCOBOL's arbitrary-precision decimal is the precedent where the ISO text leaves the intermediate to the implementor
(14.7.7 r4 a)). Citations (`cite.py --check`): §14.9.26.4 1) OK; §14.7.7 2) a) OK ("shall not contain more than 31 digits" — the
COMPOSITE, not the unscaled product). Golden `2023/pb1143_native_product_beyond_scaled_int128` (exact products, a REAL size
error 9.5 x 9.5, the DIVIDE alignment); units `CobolNumDivideAlignmentTests`; docs CONFORMANCE.md DOC-A.1-123 / -179,
COBOLNET_NUMERIC_DESIGN.md D26.

**Siblings swept:** `NumericRenderer.CombineNative`'s `*` is the ONE product site (COMPUTE, MULTIPLY F1/F2, nested); DIVIDE's
dividend scaling (fixed); `Align`'s widening is `RescaleEscape`-checked already; the store's widening is PB639's.

## Measured (adjudicator / refuter evidence, verbatim)
### GR-14.9.26.4-1 (DIVERGES)
|| REFUTED: DIVERGES — Native Format 1 silently stores a wrong product for legal source whose composite is within the 31-digit cap: the emitter multiplies the two SCALED Int128 values, which overflow and wrap once the scaled digit counts together pass 38. GR1 requires the product of the multiplier and the multiplicand to be stored. The adjudicator probed only small operands.
- **Code location (record):** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ArithmeticBinder.cs#BindMultiply (BoundMultiplyBy)

### GR-14.9.26.4-2 (DIVERGES)
|| REFUTED: DIVERGES — The same Int128 scaled-product overflow happens in Format 2 GIVING: legal operands within the composite cap store a wrapped, wrong product into identifier-3. The test-ref (3*4=12) cannot see it.
- **Code location (record):** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ArithmeticBinder.cs#BindMultiply (BoundMultiplyGiving)

### GR-14.9.26.4-4 (PARTIAL)
|| REFUTED: PARTIAL — MULTIPLY is connected to 14.6.13.2, 14.7.4 and 14.7.5, and the connections behave. But the 14.7.7 link fails at 14.7.7 rule 1 ('any necessary conversion and decimal point alignment is supplied throughout the calculation'): for legal operands inside the 31-digit composite, native MULTIPLY forms the product by an unchecked Int128 multiply of the scaled operands, which wraps. One of the four referenced clauses is violated through MULTIPLY, so the pointer cannot be CONFORMS. The root defect is recorded under GR1/GR2.
- **Code location (record):** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ArithmeticBinder.cs#BindMultiply (host.BindSizeError, RoundingOf); src/Cobol.Net.Compiler/Binding/Validation/StatementValidation.cs#CheckComposite

## What the fixer owes
Form the native product on a carrier wide enough for the composite (or detect overflow and fall to the wide/decimal path) — never an unchecked Int128 multiply. Sweep NumericRenderer's other scaled multiplies (COMPUTE `*`, DIVIDE's scaled dividend) for the same wrap.

## Revisit before implementing (triage 2026-09-29, batch 9)

**Not taken: it is a numeric-engine design question, not a one-line clamp.** Prerequisites: (1) decide how the native lane detects or avoids composite overflow (a wider carrier for the product, an overflow test that falls to the `CobolDec` / wide path, or a compile-time digit-count guard) — read the numeric design doc's lane rules first and update it in the same change; (2) sweep the same unchecked scaled Int128 multiply in COMPUTE `*` and DIVIDE's scaled dividend (the note names them) so one predicate decides "native is exact here"; (3) golden with scaled digit counts past 38 whose composite is within the 31-digit cap, Format 1 and Format 2 GIVING.
