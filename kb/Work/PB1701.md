# PB1701 — OPEN

**Owner, 2026-09-28 ~10:45 PDT:** "Add the rewrite-status-after-every-commit practice and test it."

## The defect

The scale A/B for the stamped handoff (PB1698,
`docs/rearchitecture/evidence/fleet-optimization/2026-09-28-stamped-handoff-scale.md`) found that 3 of 14 finished
implementer branches from waves 65–67 ended with a STATUS.md that did not describe their own last commit. The usual
shape is a small final commit made after the last status rewrite: a gate-red fix, a regenerated DRIFT_RULES index,
a self-review fix. The stamp makes that staleness DETECTABLE; nothing PREVENTS it.

## The mechanism

`status_guard.py` is one generic hook script. It is silent unless the git work tree's top level holds STATUS.md,
and it fails open on any internal error.
- **PostToolUse** after `git commit`: if the stamp is not HEAD, it tells the agent to rewrite STATUS.md now.
- **PreToolUse** before `git commit`: if the stamp is not HEAD, it refuses the commit, so at most one commit is ever
  undescribed.
- **Stop / SubagentStop**: if the stamp is not HEAD, it refuses the stop once; a second stop with `stop_hook_active`
  is let through.

A self-test covers 14 cases. It found a real bug during development: `git commit-tree` matched as a commit.

## The test (owner: "test it")

- **Controlled A/B.** Fresh headless `claude -p` Opus sessions, each in its own sandbox repo, on the same
  multi-commit task: four seeded bugs fixed one per checkpoint commit, then a CONTRIBUTING-driven self-review that
  invites a trailing commit. Both arms get the identical brief stating the rule. GUARD adds the hooks through
  `--settings`. Headless sessions are needed because hooks load at session start, so in-session subagents cannot be
  split into arms.
- **Outcome:** whether STATUS.md's stamp equals HEAD at exit, and how many commits are undescribed.
- **Cost:** turns, tokens, dollars and wall time.
- **Pass/fail:** the task's tests.
- The smoke test first verifies that the hook fires in headless mode.

## Result and owner decision (2026-09-28)

Record: `docs/rearchitecture/evidence/fleet-optimization/2026-09-28-status-guard-ab.md`.
- Two sandbox A/Bs, 40 sessions, ended with 0 stale handoffs in every arm. The sandbox did not reproduce the real
  21 %.
- The state-based per-command reminder cost about +20 % turns and dollars.
- **Owner, verbatim:** "Go with your recommendation for the status guard. We cannot afford a 20% more cost."
  Decided:
  - Deploy only the checks that fire on a real violation: PreToolUse (refuse a commit while STATUS.md is stale,
    registered WITHOUT an `if` filter) and Stop / SubagentStop (refuse to finish while it is stale).
  - The per-command PostToolUse reminder is REMOVED from the script, not disabled.
  - The template wording becomes "after every commit".
  - The real effect is measured in production: the stale-at-finish rate over waves 71+ against the 21 % baseline.

## ⚠ Withdrawn from the public skill; kept as a project experiment (2026-09-28, later the same day)

**Owner:** "The LEARNINGS file should always only contain the final vetted learnings, battle tested and proven
useful. Only those learnings should be encoded into a skill". Asked about what was already public, he chose
"Withdraw now". The guard is NOT vetted: its sandbox A/B was null for staleness, and it is unproven in production.
- It is removed from public agent-fleet in claude-skills v1.11.0.
- The project keeps running it as a LOCAL EXPERIMENT at `scripts/hooks/status_guard.py`, a single copy with no
  wrapper, since the public copy is gone. `.claude/settings.json` points there.
- The production measurement below is what can vet it. Only then does it return to the public skill, as the public
  copy, and this project calls it from the submodule again.

## Deployed (2026-09-28, DEVLOG 1755)

- **Public:** `status_guard.py` is published in agent-fleet as claude-skills **v1.9.0** (520a48b, tagged), with the
  measured reasons in SKILL.md §4 and the README.
- **Project (as first deployed; superseded by the withdrawal section above):** the `tools/claude-skills` pin moved to
  v1.9.0, and `.claude/settings.json` called the guard directly from the submodule's agent-fleet references, with no
  wrapper. Since the withdrawal it calls `scripts/hooks/status_guard.py`. The hooks were registered on:
  - PreToolUse on Bash and on PowerShell, with no `if` filter;
  - Stop;
  - SubagentStop (new).
- **Sibling fixed:** `devlog_staged.py` was registered with `if: Bash(git commit*)`, the same filter the A/B showed
  misses `git add -A && git commit …`. The filter is removed; the script already tests for `git commit` anywhere in
  the command.
- **Wording:** the dispatch spec, the fix-lane brief and MANDATORY-PRACTICES P4 now say "after EVERY commit", and
  tell the agent that the hook refuses a commit or a finish while the handoff is stale.
- **Verified on real trees:** the main checkout (no STATUS.md) is silent on a commit and on Stop. The leftover
  wave-68 U worktree (`wf_e9a82a33-6b6-4`, unstamped STATUS.md) is blocked on Stop with the exact stamp to write.
- **Timing, ⚠ CORRECTED the same day:** the claim that hooks load only at session start, so that the running session
  would be unaffected until a restart, was WRONG. Project settings were picked up mid-session: the guard's Stop check
  fired on the orchestrator itself at ~12:52 PDT. The orchestrator's shell had been left inside U2's worktree by a
  `cd`, and that worktree's STATUS.md did not describe HEAD. The guard was right; the fix was to return the shell
  to the main checkout. It is harmless for the fleet: the old wave-70 agents, whose STATUS files were unstamped,
  had already been stopped, and the remainder workflow's agents now run under the guard. Lesson: settings edits are
  LIVE; plan a hook rollout as immediate.
- **Still open:** production measurement. Compare the stale-at-finish rate of waves 71+ with the 21 % baseline, then
  close this note.

## Rollout (after the test)

- The hook goes into the PUBLIC repo (agent-fleet or automating-agent-guardrails), and this project's
  `.claude/settings.json` calls it directly from the `tools/claude-skills` submodule, with no wrapper (CLAUDE.md
  rule 4, PB1699).
- It is enabled only AFTER wave 70 finishes: its agents' STATUS.md files are unstamped, so the hook would refuse
  their commits.
- MANDATORY-PRACTICES P4 and the briefs say the rule is enforced.
- The result is recorded in the fleet-optimization evidence directory.
