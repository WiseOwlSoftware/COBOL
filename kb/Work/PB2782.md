# PB2782 — the supervisor's soft-cap wind-down was ~100 s late under load

**Found by** the wave 1043 F implementer (PB2200) while chasing the `test_orchestrate_stop.ps1` softcap flake, filed by
the train-1043 lander.

**What was measured.** In the self-test's `softcap` case on a host running several gates, the fake unit reported a
context above the soft cap at once (14:22:19), and `orchestrate.ps1` wrote STOP-UNIT at 14:23:59, about 100 s later.
The fake's 60 s wait for STOP-UNIT expired first, which is the flake train 1043's tooling commit fixed (one
`WaitStopUnit`, a 600 s hang guard). That fix makes the TEST tolerant; it does not explain or bound the supervisor's
delay. For a real unit, every second between the breach and STOP-UNIT is a second in which the unit may start a new
step or launch a fleet the soft cap exists to prevent.

**Code site.** `scripts/orchestrator/orchestrate.ps1`, the context-policy block (the soft/hard wind-down, about
:342-368): it runs inside the event loop, after the checkpoint step, so a slow iteration (the budget/meter read, a
checkpoint write, the event poll interval) delays it.

**Repro.** `E:\COBOL-coord\scratch\w1043f\softcap-debug.ps1` with a debug copy of `testdata/fake-claude.ps1` that
timestamps the breach report and the STOP-UNIT sighting; run it beside a whole-population gate.

**Next step.** Measure where the 100 s goes (time each step of one loop iteration under load). If one step dominates,
move the context-policy check ahead of it or make that step asynchronous; then add a self-test that asserts the
ORDER (no new step after a breach), never a latency bound (no-wall-clock-tests).
