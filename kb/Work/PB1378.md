## Finding — leap-second-directive (rejects-legal-source)

LeapSecondDirectiveProcessor treats 'after the first compilation unit starts' as 'within a compilation unit': insideUnit latches true at the first unit and is never cleared at END PROGRAM / END FUNCTION / END CLASS, and the group's LEAP-SECOND state is ONE bool, so a directive written between two sibling compilation units is rejected (COBOLNET1650) instead of taking effect for the following text

**Rows:** SR-7.3.17.3-1

**Repro:**

```
Two sibling programs in one source: unit LSB1 ... 'END PROGRAM LSB1.' then '       >>LEAP-SECOND ON' then 'IDENTIFICATION DIVISION. PROGRAM-ID. LSB2.' whose procedure does COMPUTE R = FUNCTION SECONDS-FROM-FORMATTED-TIME("hhmmss", "235960"); compile at --std 2023. Probe: scratchpad adj-d2/out/probe/leap-second-directive/b_between.cob.
```

**Expected from the spec:** Compiles clean. §7.3.17.3 SR1 forbids the directive only 'within a compilation unit'; the line after END PROGRAM LSB1 is outside every unit; §7.3.3 SR8 lets a directive appear 'anywhere in a compilation group' except as the directive's own rules restrict; §7.3.4 GR5 makes it apply 'to all of the source text and library text that follows'. So LSB1 runs under the implied OFF (SFFT('235960') = 0 with EC-ARGUMENT-FUNCTION) and LSB2 under ON (SFFT('235960') = 86400).

**Observed:** 'b_between.cob(19,1): error COBOLNET1650: >>LEAP-SECOND shall not be specified within a compilation unit (ISO §7.3.17.3 SR1) - write it before the first IDENTIFICATION DIVISION of the compilation group'. The message states the COBOL-WORDS placement rule (§7.3.10.3 SR1, 'only before the first IDENTIFICATION DIVISION within a compilation group'), which shares CompilationUnitStart; LEAP-SECOND's SR1 is worded differently. The fix needs unit-END tracking in the preprocessor and per-unit LEAP-SECOND state (BindSession/DataBinder.LeapSecond is one group fact today).

**Code site:** src/Cobol.Net.Frontend/Preprocessor/LeapSecondDirectiveProcessor.cs#Process (insideUnit latch, atFirstUnit); src/Cobol.Net.Compiler/Binding/BindSession.cs#LeapSecond

## Finding — propagate-directive (under-rejects)

PROPAGATE-SR1-PLACEMENT-UNCHECKED — PropagateDirectiveProcessor consumes a >>PROPAGATE written INSIDE a compilation unit silently; its doc claims the pre-parse stage cannot see unit boundaries, but the sibling LeapSecondDirectiveProcessor enforces the identical 'shall not be specified within a compilation unit' rule (§7.3.17.3 SR1) in the same layer via CompilationUnitStart.IsAt and COBOLNET1650 — two directives with the same placement rule, one arm fixed (sweep: any other §7.3 directive with a within-unit prohibition).

**Rows:** SR-7.3.21.3-1

**Repro:**

```
probe sr1.cob --std 2023: IDENTIFICATION DIVISION. PROGRAM-ID. PRPSR1. PROCEDURE DIVISION. / '      >>PROPAGATE ON' / MAIN-PARA. DISPLAY "SR1 COMPILED". STOP RUN.
```

**Expected from the spec:** §7.3.21.3 SR1 'A PROPAGATE directive shall not be specified within a compilation unit.' — a compile-time error diagnostic.

**Observed:** Observed: compiles with no diagnostic and runs, printing 'SR1 COMPILED', exit 0.

**Code site:** src/Cobol.Net.Frontend/Preprocessor/PropagateDirectiveProcessor.cs#Process (compare LeapSecondDirectiveProcessor.Process insideUnit arm)

## What the fixer owes (and the sibling sweep)

ONE unit-boundary tracker (start AND end of each compilation unit, nested units included) shared by every directive with a within-unit prohibition (sweep §7.3 for others: COBOL-WORDS SR1 is 'before the first', a different rule); LEAP-SECOND state becomes per-unit (BindSession.LeapSecond keyed by unit). Goldens: LEAP-SECOND between units changes the second unit's bound; PROPAGATE inside a unit rejected.

**Rows claimed:** SR-7.3.17.3-1, SR-7.3.21.3-1
