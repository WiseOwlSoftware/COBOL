Wave 20261867 planned PB4589 as group A, and its implementer found the note already landed. It built the compiler, re-probed, changed nothing and returned DISCHARGED.

**The timeline (2026-11-04, UTC).** The main checkout sat at e90115509. Pull request #1131, which carries PB4589, merged at 21:50:58 and made 68c8e6027. The session probe ran at 21:51 and still ranked PB4589 next. plan_wave.py ran about a minute later. PB4589's DONE report was w20261865b, on branch worktree-wf_e49b9adc-28d-15, and that branch was already on origin/main.

**The suspected mechanism, read from the planner's header but not yet traced through its code.** The AWAITING LANDING rule excludes an open note whose newest DONE report's branch "is not on main yet". The note's status comes from the stale checkout, where PB4589 is still open. The branch's state comes from origin/main, where the branch has landed. Each answer is correct for its own commit, and together they make the note plannable. PB4599 in the same plan was excluded correctly because its pull request had not merged yet.

The stale-checkout guard does not catch this. adopt_main.require_current (PB2699) compares the checkout with the commit the supervisor adopted, and a merge after that adoption passes it.

**Cost.** One implementer (a build and a re-probe) and three reserved codes, COBOL6130 to COBOL6132, which the report returned unused.

**Fix shape.** Have the planner read every fact from one commit: fetch origin/main and read the register at that commit, not from the working tree. Pin it with a test where a note is open in the checkout and landed at origin/main.

**Sites:** scripts/orchestrator/plan_wave.py, scripts/orchestrator/adopt_main.py.
