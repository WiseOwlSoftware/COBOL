# PB287 — LANDED 2026-09-02 (found by [[A13]], fixed in the same change set)

## The defect

`.github/workflows/build-and-test.yml` carried four filters keyed on `Class.Method`:

- the three `matrix-cont-2002/2014/2023` continuity shards (both the Linux and the Windows shard matrix):
  `FullyQualifiedName~VersionMatrixTests.Cobol85Program_StillCompilesAtLaterEdition&DisplayName~NNNN`;
- the **INV-1-STRONG** job (NIST goldens byte-exact at `--std 2023 --permissive`):
  `FullyQualifiedName~NistDifferentialTests.NistProgram_MatchesGolden`.

A `~Class.Method` substring is only ever satisfied by a fully-qualified name that spells that class EXACTLY.
The A13 collection split makes the classes carrying those methods `VersionMatrixTests_P0 … _P11` and
`NistDifferentialTests_P0 … _P5`, so the substring `VersionMatrixTests.Cobol85Program_…` can never occur in
`…VersionMatrixTests_P0.Cobol85Program_…`. **vstest reports a filter that matches nothing as a passing run with
zero tests** — exit 0, no warning, no red.

⛔ **The severity is not the shard matrix, it is INV-1-STRONG.** The sharded conformance leg has a
shard-population job (DESIGN-test-build-ci §3.8) that sums the shards and compares them against the discovered
count, so the three continuity shards going empty would eventually have been caught there. INV-1-STRONG has
**no population guard at all**: it would have gone on printing a green "NIST goldens byte-exact" verdict while
compiling and comparing **zero** of the 349 goldens — the strongest single invariant in CI, silently retired.

## The fix

All four filters key on the **method name alone** (`~Cobol85Program_StillCompilesAtLaterEdition`,
`~NistProgram_MatchesGolden`). Both method names are unique in the tree, so the filter is exact today and
immune to the next re-partition — the class half is the half that moves. The `!~Cobol85Program_…` complement
in `matrix-constructs`, and every bare `~VersionMatrixTests` / `~CorpusRunnerTests` / `~NistDifferentialTests`
filter, are unaffected: a partition class keeps its family name as a PREFIX, so they still select and still
exclude exactly what they did.

Verified rather than argued: CI's shard-population check was re-run locally against the split tree and still
partitions the conformance leg exactly — **349 + 349 + 349 + 1080 + 1354 + 1761 = 5242 = discovered**.

## Why it was found late, and the general rule

This is `feedback_vstest_filter_terms` in a new dress. That lesson was learned from `--filter "~X|~Y"` (a term
missing its `FullyQualifiedName` prefix matches nothing and exits 0); the same silent-green mechanism fires
whenever the *filter text* stops describing the tree, and a `Class.Method` filter is a **latent silent-green
whenever the class can be renamed or split**. Key on whichever half is unique — here, the method.

It also restates `feedback_green_gates_arent_evidence`: INV-1-STRONG had been green on every run, and a green
gate proves nothing when it never looked at what it claims to cover. The countermeasure that works is the one
the shard matrix already has and INV-1-STRONG does not — a population assertion — which is why the A13
StorageForm split kept its `parsed >= 50` bar as a per-partition proportional share rather than dropping it.

## Residue

- INV-1-STRONG still has no population guard of its own; it is protected today only because its filter is now
  correct. Asserting that the run actually saw 349 goldens is the durable fix and is residue of this note.
