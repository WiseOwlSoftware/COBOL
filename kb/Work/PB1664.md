# PB1664 — OPEN (adjudication)

Filed 2026-09-27 by the train-67 lander from the wave-67 P implementer report (`w67p-PB1168-report.md`, new
defect 3). PB1540 made the LINE SEQUENTIAL delimiter the host newline (DOC-A.1-114); the record sequential
PRINT stream kept its fixed CR LF, and the implementer documented that as DOC-A.1-146 (c′) rather than move it.

**The question.** The line end a print-control WRITE emits is implementor-defined. CLAUDE.md rule 1's precedence
for latitude (the spec, otherwise GnuCOBOL, otherwise IBM / Micro Focus) points at GnuCOBOL, which writes `\n` to
a binary-mode sequential file. Today `src/Cobol.Net.Runtime/IO/SequentialConnector.cs:779` `PrintLineEnd = CR LF`
on every host.

**Cost of changing it.** Every NIST and report-writer golden that pins print-file bytes moves; the determination
in `docs/CONFORMANCE.md` DOC-A.1-146 (c′) is rewritten.

**What the adjudicator owes.** Survey GnuCOBOL (and IBM / Micro Focus) on a print file's line end, decide under
rule 1, record it in DOC-A.1-146, and either close this note with the current behavior cited or hand a defect
note (with the golden list) to an implementer.

## Adjudication 2026-10-07 (w1033)

Decision `E:\COBOL-coord\scratch\w1033-adj\PB1664-decision.md`; refuter `PB1664-refute.md` (NOT UPHELD AS WRITTEN: the refuter's amended version is the outcome). Pinned
build `pin-97006f3` (main `97006f310`); probes `PB1664\` (advrs, linrs, rptrs, lsctl), `PB1664-refute\` (rptpg, rptls, lin0, lin0b, varrs). GnuCOBOL sources read from the tarball are GPL and must never be committed.

**Outcome: DEFECT CONFIRMED (implementor-latitude defect: the print stream's line end does not follow GnuCOBOL). Harm: output bytes wrong against the rule-1 determination, not an ISO violation either way;
severity stays MINOR.** `kind` flips to `defect`; `wrong_answer: true` is set as PB1540 (same family) was classified, the bytes being wrong against the rule-1 determination.

**Spec (cite.py --check OK; refuter added more).** ISO does not control the bytes. `§9.1.7.2`: a record sequential record's on-medium form is implementor information; `§14.9.51.4 GR25` and `25) a), h)` fix the
SEMANTICS of advancing (lines advanced, before/after) but not the bytes; `§A.3 37)` makes ADVANCING processor-dependent; `§12.4.5.10.3 GR2` and `§A.1 114)` govern line sequential only; refuter: `§13.4.5.4 GR4`
(report writer logical record structure implementor-defined), `§A.1 159)` (report file record structure, required), `§13.4.5.3 SR4` (a LINE SEQUENTIAL report file is legal), `§14.9.16.4 GR6`, `§14.9.51.4 GR25 c)`
and `GR21`. So CLAUDE.md rule 1's precedence applies: GnuCOBOL decides; `R54` (ADVANCING 0 is a bare CR) is the direct precedent (same spec rule, same GnuCOBOL function `cob_seq_write_opt`).

**GnuCOBOL 3.2 behaviour (source plus probe).** Shape 1, RECORD SEQUENTIAL with WRITE ADVANCING, no LINAGE, not a report file: stays `COB_ORG_SEQUENTIAL`, binary fd (fileio.c 1622), LF per line, FF for PAGE, bare
CR for 0. Shape 2, `FD ... LINAGE`: reclassified LINE SEQUENTIAL (parser.y 6691), text mode "w" (fileio.c 1894-1899; `COB_UNIX_LF` exists only under `_WIN32`, default "0"), so LF on Linux and CR LF on Windows. Shape 3,
`FD ... REPORT IS`: reclassified LINE SEQUENTIAL (parser.y 6820-6821), same as shape 2. Windows GnuCOBOL was not run (a reading of source).

**Pinned build.** `src/Cobol.Net.Runtime/IO/SequentialConnector.cs`: `private const string PrintLineEnd` is CR LF (line 742); the constructor picks it for every connector that is not line sequential (line 712,
`_lineEnd = lineSequential ? LineSequentialDelimiter : PrintLineEnd`); line 304 (writer NewLine), line 994 (CLOSE of an open line), line 1301 (`AdvanceLines`). Report files register via
`FileRegistry.RegisterReport` with `lineSequential: false`. Output identical on Windows and Linux: advrs `\r\n AA \r\n \r\n BB CC \f`, linrs `\r\n AA \r\n BB \r\n`, rptrs `DD \r\n DD \r\n`. Control `lsctl` (the advrs program declared LINE
SEQUENTIAL) is byte-identical to GnuCOBOL on Linux, so only the line END differs.

**Corrected decision (refuter).**
- Expected line ends: shape 1 (record sequential with ADVANCING, no LINAGE, not a report) gets LF on EVERY host. Shapes 2 and 3 (LINAGE, and EVERY report file, LINE SEQUENTIAL ones included) get the HOST newline.
- Unchanged: ADVANCING 0 stays the bare CR (ISO GR25 c) controls, and GnuCOBOL's LINAGE arm is non-conforming); PAGE on shape 1 stays a form feed.
- STRUCK from the decision: "PAGE stays a form feed ... the two compilers already agree" is FALSE for report files (`rptpg`, PAGE LIMIT 5: ours `PH\r\nDD\r\nDD\r\nDD\fPH\r\nDD\r\n`, GnuCOBOL `PH\nDD\nDD\nDD\nPH\nDD\n\n\n\n`, no `\f`:
  `libcob/reportio.c` has no `COB_WRITE_PAGE` and pages with blank lines); and "ADVANCING 0 ... already agree" is FALSE for LINAGE files (`lin0b`: AA AFTER 1 then BB AFTER 0 gives ours `AA\rBB`, GnuCOBOL `AA\nBB\n`).
  Both are sibling divergences, not agreements. The report page advance is filed as `PB2510`.
- Strongest witness for shape 3: `rptls` (a LINE SEQUENTIAL report file, legal under `§13.4.5.3 SR4`): ours `DD\r\nDD\r\n` on Linux, GnuCOBOL `DD\nDD\n`, because `FileRegistry.RegisterReport` hard-codes `lineSequential: false`
  and so bypasses the DOC-A.1-114 delimiter. Pin it.
- Docs: `docs/CONFORMANCE.md` DOC-A.1-159 ("CR LF ... on every host", form feed "whatever the file's ORGANIZATION") becomes false and must be rewritten WITH DOC-A.1-146 (c').

**Fix shape.** Make the line end a property of the file's shape fixed at registration (the report arm has its own registration `RegisterReport`; a LINAGE FD is static and known to the emitter): line sequential, LINAGE and
report connectors take `LineSequentialDelimiter`, a plain record sequential print stream takes LF. One selection site, plus a drift test pinning the three-way mapping.

**Cost (corrected estimate stands; both files agree).** NIST goldens do not move: `NistDifferentialTests.Normalize` folds CR LF and drops a lone CR (lines 130-139); no `.out` golden under tests/conformance,
characterization, version-matrix or differential contains a CR; `pb690_report_line_byte_image_85` skips CR. The only medium-byte assertions are `LinageConformanceTests.AssertBytes` (12 call sites) which rewrites CR LF
only for LINE SEQUENTIAL fixtures: it needs the THREE-way mapping (no-LINAGE print fixtures LNGBY7, LNGBY8 and the PB964 print-stream case expect LF on every host; LINAGE fixtures the host newline).

**Leads.** Record CONTENT on shape 1: `PB2509`. Report page advance (form feed versus GnuCOBOL's blank lines): `PB2510`. Plain WRITE then AFTER 0 on a LINAGE file (`lin0`: both compilers put BB on the line after AA; ours because
`ImplicitAdvanceIsBefore` applies write-then-advance when no line is open, touching `§14.9.51.4 GR25 c)/f)`, not the line end): added to `PB1027`, whose fix removes that mechanism.
