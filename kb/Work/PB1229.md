## Landed — wave 1031 D

Re-probed on a fresh Debug build: `01 K CONSTANT AS ZERO + 1.` and `01 K2 CONSTANT AS ZEROES * 3.` compiled and printed `1 0`; `AS (ZERO)`, `AS - ZERO` and `AS 2 - ZEROS` compiled too. The directive twin was already barred (`>>DEFINE D1 AS ZERO + 1`, `>>IF D1 = ZERO + 1` give COBOLNET1619, §7.3.3 SR10), so only the shared recursion was open.

**Fix (one place):** `CompileTimeExpressionEvaluator.EvalArith` no longer maps `ZERO_ARITH` to 0. It reports COBOLNET1547 through the consumer's `ICtDiagnostics`, citing the consumer vocabulary's `GoverningCitation` (the CONSTANT binder now words it "ISO §13.10.3 SR6, SR7 / §7.3.6.2 SR1b"), and returns null, so every caller of the raw-value recursion inherits §7.3.6.2 SR1b. The directive entry's earlier §7.3.3 SR10 scan stays in front of it: that is a different rule (the master constraint on compiler directives) under a different code (COBOLNET1619).

**Sibling arms checked:** `AS ZERO` alone (the literal-1 arm, `BindConstantStringLiteral`, already COBOLNET1547); the boolean-shift count and the CCE relation operands (both reach arithmetic through `EvaluateDirectiveArithmetic`, already screened); the runtime `ExpressionBinder` and `ConditionBinder` `ZERO_ARITH` arms (legitimate there, §8.3.3.6.3 SR1a).

**Witnesses:** negative `constant-figurative-arith-operand` (reject-at 2002 2014 2023); unit `CompileTimeExpressionEvaluatorTests.Rejects_FigurativeZeroOperand`. The three rows went DIVERGES to CONFORMS in batch `w1031d-pb1229`.
