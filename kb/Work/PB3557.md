# PB3557 — SR1 and SR11 violations are reported under the wrong rule

## Lead (R1-6, low, not blocking at round 1; from the PB3338 report)

src/WiseOwl.Cobol.Compiler/Binding/DataBinder.IoControl.cs:143 SR1 and SR11 violations are reported as an undefined data name (COBOL1639), never under their own rules … the COBOL4709 descriptor text claims an SR1 report no code path makes. (The report's text is elided at "…"; the finisher left it for the clerk.)

The summary in the register title: COBOL1639 says "no declaration in this source element", which is false for a file that
is visible as a GLOBAL file of an enclosing element.

**Sites:**
- `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.IoControl.cs:143` (`DataBinder.BindApplyCommitClause`)
- the COBOL4709 descriptor (diagnostic catalog)
- `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.IoControl.cs` (`ScreenEnclosingFileOperand`, `ResolveApplyCommit`)
- `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs` (`InheritFileNames`, `InheritedGlobalFiles`, `InheritedGlobalRecordAreas`, `ContainerLocalFiles`)
- `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.NonDataNames.cs` (`NonDataDeclarationOf`, `IsVisibleFileName`, `NonDataDeclarationKind.FileName`)
- `src/WiseOwl.Cobol.Compiler/Binding/BinderDriver.cs` (`BindUnitData`: the pre-Bind `InheritFileNames` call, the post-Bind merge into `FilesByName`)
- `src/WiseOwl.Cobol.Editions/Diagnostics/DiagnosticCatalog.cs` (`ApplyCommitClauseRule`, COBOL4709)

## Landed (wave 20261780 H, 2026-10-30)

Re-probed on a Debug build (0/0): `conformance-suite/cases/12.4.6-I-O-CONTROL/pb3338_apply_commit_sr11_global_file.cob` and
`pb3338_apply_commit_sr1_file_of_another_element.cob` (`--source-format free`) both drew COBOL1639 "no declaration in this source
element gives the name 'RELF'" (false for the GLOBAL file, visible by §13.18.27.4 GR1). Two siblings found on the way: a file-name
written where a data item is required (`MOVE 1 TO F1`, `FILE STATUS IS F1`, F1 a file of the same element) drew the same false
"no declaration" wording at every site that asks `NonDataDeclarationOf`; and a GLOBAL RECORD AREA (SR11's second noun) of a
containing GLOBAL FD, named in the clause, drew it too.

**Fix.** Two mechanisms, one root (the name's kind was never asked). (1) `NonDataDeclarationOf`, the ONE answer to what a name
declared as no data item is (PB1906), gained `FileName`: an own SELECT or a containing element's GLOBAL file, which the new
`DataBinder.InheritFileNames` records BEFORE the unit binds (the file twin of `InheritGlobalTypeDecls`; the merge into
`FilesByName` stays after the bind, so an FD still finds only the unit's own SELECT). (2) `ResolveApplyCommit` asks
`ScreenEnclosingFileOperand` of every identifier-1 that resolves to no data item (a local declaration hides the container's name):
a GLOBAL file is SR11 (and the report says it is also outside this FILE-CONTROL, SR1), a GLOBAL record area is SR11, a container's
file with no GLOBAL clause is SR1; one COBOL4709 each. The descriptor now names SR1-SR11. Citations `--check`ed:
12.4.6.3.3 SR1 and SR11 verbatim, 13.18.27.4 GR1 (file-name described with GLOBAL is a global name).

**Witnesses.** The two PB3338 negatives now expect COBOL4709; new `pb3557_apply_commit_sr11_global_record_area`;
`ApplyCommitEnclosingFileTests` (SR11 file, SR11 record area, SR1, undefined word unchanged, local data item hides the global file,
own file shadows it); `NonDataNameReferenceTests` (file-name at a statement, FILE STATUS, and a contained program's GLOBAL / non-GLOBAL
file). Inventory rows SR-12.4.6.3.3-1 and -11: notes restated, witnesses added.

**Found on the way, NOT fixed (outside this mechanism).** A contained program's FILE STATUS / RELATIVE KEY / OCCURS DEPENDING ON naming
a container's GLOBAL DATA item is refused as undefined (COBOL1639 / COBOL0851): the GLOBAL data subtrees are inherited after the
contained data division binds (`BinderDriver.BindUnitData`, `InheritGlobalSubtree`), PB3766's timing for report items, here for data
items; it rejects legal source. Reported in the wave report as a lead.
