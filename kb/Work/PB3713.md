# PB3713 — the LANDED proof uses a merge the real landing would not do

**Sites:** `scripts/prune_worktrees.py:204` (`merges_to_main_unchanged`), `scripts/merge_drivers.py` (`merge_conflicts`, `is_drivers_merge`, `config_args`: the drivers' own definition of a merge, which PB3640 added).

## What happens

`merges_to_main_unchanged(branch, graph)` runs `git merge-tree --write-tree origin/main <branch>` with no merge-driver configuration and
treats a clean merge that leaves main's tree as LANDED. Every real merge in this repository goes through `merge_drivers.py` (PB3610),
which merges the keyed catalogues by key. If another carrier already put a branch's content on main, a plain merge of the branch can still
conflict in a keyed file where the drivers would produce main's tree. That branch never reads LANDED; it stays listed and its worktree is
kept. It errs toward keeping work, so no content is lost, but landed branches pile up in the survey.

Repro (from the PB3640 report): a branch and main that both append different entries to `conformance-suite/wiseowl/diagnostics.json`
where main's text already contains the branch's entry.

## Fix

Run the same merge the landing runs: `merge_drivers.merge_conflicts`' configured `merge-tree` (PB3640 added it as the one definition of a
drivers merge), so the survey and the landing agree on what a clean merge is. Keep a plain git failure a NO (the function's existing
rule: an unproven landing is never LANDED). Self-test arm with the diagnostics.json repro; sweep the other callers of a bare
`git merge-tree` in `scripts/` for the same split definition.
