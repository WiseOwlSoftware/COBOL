# PB3713 — the LANDED proof uses a merge the real landing would not do

**Sites:** `scripts/prune_worktrees.py:204` (`merges_to_main_unchanged`), `scripts/merge_drivers.py` (`merged_tree`, `is_drivers_merge`, `merge_conflicts`, `config_args`: the drivers' own definition of a merge, which PB3640 added), `tests/Cobol.Net.Tests.Unit/MergeDriverDriftTests.cs`.

## What happens

`merges_to_main_unchanged(branch, graph)` runs `git merge-tree --write-tree origin/main <branch>` with no merge-driver configuration and
treats a clean merge that leaves main's tree as LANDED. Every real merge in this repository goes through `merge_drivers.py` (PB3610),
which merges the keyed catalogues by key. If another carrier already put a branch's content on main, a plain merge of the branch can still
conflict in a keyed file where the drivers would produce main's tree. That branch never reads LANDED; it stays listed and its worktree is
kept. It errs toward keeping work, so no content is lost, but landed branches pile up in the survey.

Repro (from the PB3640 report): a branch and main that both append different entries to `conformance-suite/wiseowl/diagnostics.json`
where main's text already contains the branch's entry.

## Fix

Run the same merge the landing runs: `merge_drivers.merge_conflicts`' configured `merge-tree` (PB3640 added it as the one definition of a
drivers merge), so the survey and the landing agree on what a clean merge is. Keep a plain git failure a NO (the function's existing
rule: an unproven landing is never LANDED). Self-test arm with the diagnostics.json repro; sweep the other callers of a bare
`git merge-tree` in `scripts/` for the same split definition.

## Landed (2026-10-25, wave 20261107 group E)

**Re-probe.** The note's repro reproduced on the survey's self-test repository: `key-landed` appended `x` to a keyed
catalogue (`d.json`, `merge=cobol-keyed-object`); another carrier put `x` on main beside its own `y`. A plain
`git merge-tree --write-tree origin/main key-landed` conflicts in `d.json`, so `merges_to_main_unchanged` said NO and
the branch read CHECK, while the drivers merge it to main's own tree. With the old call restored the fixture fails on
exactly that row (negative control run).

**Fix.** `merge_drivers.merged_tree(repo, parents)` is the one definition of a clean merge's tree (`git merge-tree
--write-tree` through `config_args`; None for a conflict a driver declines, a missing ref, unrelated histories).
`is_drivers_merge` (the review's coverage rule) now reads it instead of repeating the command, and
`prune_worktrees.merges_to_main_unchanged` proves a landing with it, so the survey and the landing agree on what merges
clean; a git failure is still a NO. The strict tree comparison is kept (not `is_drivers_merge`, which also accepts a
tree differing from the merge only in a settled ABI pin: that merge DOES change main, so it is no landing proof).
Sibling sweep: `git grep merge-tree` over the repository finds no other bare call (`land_lane.py` foresees through
`merge_conflicts`, held by `MergeDriverDriftTests`); that test now also holds `prune_worktrees.py` to `merged_tree` and
to no `'merge-tree'` of its own. Self-test arms: `merge_drivers.py` ("tree: ..." twice, the PB3713 shape and the None
cases) and `prune_worktrees.py` (`key-landed` LANDED, removed by `--apply`).
