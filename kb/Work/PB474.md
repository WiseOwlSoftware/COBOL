# PB474 — LANDED 2026-09-04 — the guard's `cd` parser did not speak the shell it guards

Found 2026-09-04 when the PB201 continuation implementer (a FRESH agent launched WITHOUT worktree isolation and
told to prefix every shell command with `cd /e/CobolSharp/.claude/worktrees/agent-a3af9f344b373c36c &&`) had all
four of its `dotnet build CobolSharp.sln` attempts refused by `scripts/hooks/fleet_active_build.py`:

> BLOCKED — 5 subagent transcript(s) were written in the last 120s, so a fleet is LIVE in **a working tree that
> could not be determined, so the session-wide rule applies** …

The agent surfaced the block rather than routing around it (correct), did every freeze-safe step, and returned
with its gate un-run. The same instruction shape was live on the PB193 continuation agent.

## The mechanism (re-derived on this tree, not inherited)

`effective_cwd` honours a leading `cd <dir>` — "builds in `<dir>`, not in the payload's cwd" — and
`CD_PREFIX_RE` captured the target `/e/CobolSharp/.claude/worktrees/agent-…` exactly. The defect is the next
line: `pathlib.Path("/e/CobolSharp/…").is_absolute()` is **False on Windows** (rooted, but no drive), so the
guard joined it onto the payload cwd — `Path("E:/CobolSharp") / "/e/CobolSharp/…"` → `E:\e\CobolSharp\…`, a path
that does not exist. `repo_root_of` walked its ancestors (`E:\e\CobolSharp\…`, `E:\e`, `E:\`), found no `.git`,
returned `None`, and `agents_sharing_tree` took the documented UNKNOWN branch: revert to the pre-2026-09-01
session-wide rule, where every foreign live agent denies. With two read-only fleets live (the lane-3 refuters on
the pinned worktree, the golden-lane refuters reading main) that was a permanent deny for any non-isolated
implementer building in its worktree — the exact false denial the 2026-09-01 tree-scoping was written to remove,
reintroduced by the spelling of one path.

The fallback direction is right and stays: an UNKNOWN tree must deny. What was wrong is that a perfectly
determinable tree was reported unknown because the guard parsed a Git-Bash command with Windows path semantics.

## The fix

`native_path()` in the hook: an MSYS drive path (`/e/…`, `/cygdrive/e/…` — one letter, then `/` or end) becomes
`E:/…` on Windows before `pathlib` sees it; a POSIX path that is not a drive (`/tmp/x`) is untouched, and the
function is the identity off Windows. `effective_cwd` calls it on the `cd` target. The self-test (`python
scripts/hooks/fleet_active_build.py --self-test`) gained the failure branch over the REAL fixture worktree — both
spellings must resolve to the worktree, and a main-tree fleet must then NOT deny that worktree's build — plus the
two negative cases. Fired red before the fix (the `cd /e/…` case resolved to `E:\e\…`), green after.

Sibling sweep: `CD_PREFIX_RE` is the only place a command path is interpreted; `repo_root_of` and
`main_repo_root` take paths from the payload and from git's own `.git` file, which are always native. The
worktree-isolation launch mode is unaffected (its payload cwd is native and it cannot `cd`).
