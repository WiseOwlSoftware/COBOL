# PB290 - the inherited citation nobody re-derived

<!-- audit-code-citations: names-phantoms - this note IS the phantom register; every clause number in its
     tables is a QUOTED SPELLING that the standard does not have, which is the point of the note. -->

> **✅ LANDED 2026-09-02 by the citation-repair sweep.** The estimate below was an order out in both
> directions that matter: the §8.3.1.2 family alone was **84 sites**, not ~50, and the sweep's own new tool
> then found **~200 sites over NINE clause numbers the standard does not contain**. The measurement, the
> per-phantom re-derivation and the gate that makes the next one impossible are recorded below the original
> analysis. ⚠ The sweep also found TWO real defects it did not fix; they are [[PB299]] (the lexer admits no
> UNDERSCORE in a COBOL word - rejects legal source) and [[PB300]] (`paddingCharacterClause` parses a
> construct with no ISO anchor and no dialect gate).

Found while landing [[PB263]] / [[PB264]] (2026-09-02): the two doc comments in the file being edited
(`EmitCore.cs`, on `UnscaledLit` and `IntLiteralX`) both cited "ISO §8.3.1.2" for the fixed-point literal digit
cap. Running the check that CLAUDE.md rule 1 requires:

```
$ python scripts/spec/cite.py --check 8.3.1.2 "numeric literal"
FAIL: there is no clause §8.3.1.2 in the transcription
```

This is **the inheriting failure mode named in rule 1**, at scale: the clause number is wrong, the quoted subject
matter is genuinely in the standard, and nobody re-derived the number before it propagated.

## The sweep

`grep -rn "8\.3\.1\.2" --include=*.cs --include=*.md --include=*.json` returns about 50 sites outside
`specs/ISO_COBOL.md`, and they use the dead number for **three unrelated subjects**:

| what the site means | the real clause (all `--check` verified) |
|---|---|
| fixed-point literal / item digit caps (1-31) | **§8.3.3.3.2** "The implementor shall allow for fixed-point numeric literals of 1 through 31 digits in length." |
| alphanumeric literal delimiters, doubled quotes | **§8.3.3.2** Alphanumeric literals |
| figurative constants (ZERO as numeric 0, ALL, fill) | **§8.3.3.6** Figurative constant values |

⛔ **It is already ledgered and was never acted on.** `docs/rearchitecture/DESIGN-SPEC-RECONCILIATION.md` item 54
(line 195) records it verbatim: "§8.3.1.2 does not exist in the spec. §8.3.1 is titled 'General' ... and has NO
numbered subsections; a grep for '8.3.1.2' returns zero hits. The actual digit-position cap lives elsewhere:
§8.3.3.3.2". A ledger entry is not a repair ([[feedback_fix_transcription_errors_immediately]]).

## Why it is more than cosmetic

Two SHIPPED diagnostics carry the dead citation into user-visible output and into `docs/DIAGNOSTICS.md`:

- `COBOLNET0801` - "A fixed-point item/literal exceeds the 31-digit ISO limit.", `"ISO §8.3.1.2"`
- `COBOLNET0802` - "... 18-digit COBOL-85 limit ...", `"ISO §8.3.1.2"`

(`src/Cobol.Net.Editions/Diagnostics/DiagnosticCatalog.cs:70,81`, plus `ConstructRegistry.g.cs:50` and the
`EditionContext.CheckDigitCapacity` message a user actually reads.) A user who follows the citation finds
nothing. `docs/rearchitecture/DESIGN-compile-time-expressions.md:299` additionally uses it to justify a
FACTUALLY WRONG claim about underscores in COBOL words - a claim the PHASE-B findings already flagged as having
caused a test to be rewritten to dodge a compiler bug.

## Fix shape

Mechanical, but it must be done PER SUBJECT, not by a blind replace - the three subjects take three different
clauses, and a single sed would make about a third of the sites confidently wrong in a new way. Sweep the ~50
sites by subject, then add the guard that makes the next one impossible: **a drift test asserting every
`ISO §x.y.z` citation appearing in `src/` and `docs/` resolves against the transcription**, which is exactly what
`scripts/spec/cite.py --check` already answers one at a time. That test is the real deliverable; without it the
next inherited number lands the same way.

## ✅ 2026-09-02 - LANDED: the measurement, and the gate that makes the next one impossible

[[PB159]] named "~10 grep hits" for the nonexistent §8.3.1.2 and [[PB182]] named 18 for §8.8.4.1.1. Both counts
were an order out, because nothing had ever asked the question mechanically. The tool built for [[PB159]]
(`scripts/spec/audit_code_citations.py`, PHANTOM check) asked it across every file in the repository that
carries a citation, and the answer was **~200 sites over nine clause numbers the standard does not contain**.

⛔ **THE §8.3.1.2 PHANTOM WAS STANDING IN FOR FIVE DIFFERENT PROPOSITIONS.** That is the reason a phantom
survives: it accretes meaning. §8.3.1 is titled "General" and is a single sentence with no subclauses, so every
one of these was unfalsifiable where it stood:

| what the site actually meant | the real clause |
|---|---|
| a fixed-point numeric literal's form, and the 1–31 digit range | **§8.3.3.3.2** ("The implementor shall allow for fixed-point numeric literals of 1 through 31 digits in length") |
| both quotation symbols are equal-standing delimiters | **§8.3.3.1** ("may be either apostrophes or quotation marks") |
| an embedded delimiter is doubled | **§8.3.3.2.3 r3** |
| an alphanumeric literal | **§8.3.3.2** |
| figurative constants — the singular/plural formats, ZERO as numeric 0, fill-to-width | **§8.3.3.6.2 / §8.3.3.6.3 r1a / §8.3.3.6.4 r2, r4** |
| the class and category of a LITERAL | **§8.3.3**, to which §8.5.2.1 explicitly delegates |
| the characters of a COBOL user-defined word | **§8.3.2.1** |

Two variants rode along: `kb/Work/PB87.md`'s **§8.3.1.2.3 r1a** → §8.3.3.6.3 r1a, and `SemanticBuilder.cs`'s
`ISO 1989:1985 8.3.1.2` → §8.3.3.6.4 r2 of the standard this compiler is measured against.

**The §8.8.4.1.x family — a whole nonexistent subclause tree.** §8.8.4.1 is "General"; there is no §8.8.4.1.1
through .4. Seventy sites cited them:

| phantom | the proposition | real clause |
|---|---|---|
| §8.8.4.1.1 | a group operand is alphanumeric / compared as an elementary alphanumeric item | §8.5.2.1 + §8.8.4.2.1 ([[PB182]]) |
| §8.8.4.1.2 | the shorter alphanumeric operand is space-extended on the right | **§8.8.4.2.7 r2** |
| §8.8.4.1.3 | pointer relations (= / NOT = / NULL) | **§8.8.4.2.16** |
| §8.8.4.1.4 | the class condition (`IS [NOT] NUMERIC / ALPHABETIC / ALPHABETIC-UPPER / ALPHABETIC-LOWER`) | **§8.8.4.4** |

**The rest**, each re-derived from the standard's own headings: §14.9.62 TERMINATE → **§14.9.46**; §14.2.4

## THE GATE, AND WHY ITS EXCLUSIONS ARE STRUCTURAL

`python scripts/spec/audit_code_citations.py --check` — baseline **ZERO**, `--self-test` proves each of the
three checks fires on a real defect from this sweep and is silent on its repair. Four exclusions, each earned by
a false positive and each documented in the tool:

1. **A `§` is not always a citation of the standard.** The docs point at their own sections ("DESIGN-locale-facility
   §4.4.3", "ADR §1.2.1"), and at other editions ("COBOL-85 §4.3.3"). Neither is checkable here.
2. **A design doc's own heading numbers** are collected per file and skipped.
3. **A phantom being REPORTED as a phantom is not a defect** — the repairs leave behind sentences like "the old
   comment cited a §8.3.3.7 the standard does not have". Flagging those would make the audit red on its own fix
   and would push the next author to DELETE the forensic record to get green: the worst possible incentive.
4. **A citation in quotation marks, or followed by an arrow**, is being NAMED or CORRECTED, not asserted.

Carried from [[PB159]]: **Annex A.4.2 item 9 prints "(14.9.10)" for DISPLAY format 2** in `specs/ISO_COBOL.md`.
§14.9.10 is DELETE; DISPLAY is §14.9.11. Item 1 of the same list ("ACCEPT statement, format 3: screen (14.9.1)")
is correct, so this is not a systematic shift. Whether the printed page or the transcription is wrong needs the
PDF rendered — a spec-reconcile question, not a code one.
