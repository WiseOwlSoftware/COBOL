# PB231

**Rows:** `GR-14.9.3.4-3`, `GR-14.9.3.4-4`, `GR-14.9.3.4-7`, `GR-14.9.3.4-9`

a BASED record with a NATIONAL, USAGE BIT or pointer-class leaf is refused at bind (COBOLNET1695), so ALLOCATE computes no byte quantity, establishes no address and runs no INITIALIZE expansion for data descriptions §13.18.5.3 SR1/SR2 expressly permit.

Rows: GR-14.9.3.4-3 (the byte quantity), -4 (GR4a/b addresses), -7 (the GR7 WITH FILLER ALL TO VALUE THEN TO DEFAULT expansion), -9 (GR9's null-seeding of class-object/pointer items). ONE storage-model boundary, four rules that all stop at it.

MECHANISM (from the rows' own READ evidence). The Step D second gate widened ForceStringCanonical to admit every HasImageByteForm leaf to the shared byte cell, so a BASED record with a COMP / COMP-5 / BINARY-* / PACKED-DECIMAL / COMP-1 / COMP-2 / INDEX leaf is now ordinary cell-backed storage — witness conformance:2023/stepd_based_comp_leaf, which ALLOCATEs `01 R` with S9(4) COMP + S9(3) COMP-3 + COMP-1 leaves, windows the same cell through a second BASED PIC X(8) entry and reads all eight bytes with FUNCTION ORD (FF FE, 12 3D, 3F C0 00 00) — the 2+2+4 sum GR3 demands. THREE LEAF KINDS STILL HAVE NO LAYOUT IN THAT CELL: a NATIONAL position is TWO bytes over a byte-addressed cell (the rows call this RESIDUE-11), a USAGE BIT run is a sub-byte packing, and a pointer-class item is not a byte sequence at all. For those, PtrBindBasedAndAddressables draws the bind-time COBOLNET1695 and nothing downstream runs — witness conformance:negative/pb164-based-national-leaf.

WHY THAT IS REJECTS-LEGAL-SOURCE. §13.18.5.3 SR1/SR2 restrict a BASED subject only to 'shall not be of class object' and 'shall not be a dynamic-length elementary item or a variable-length group', and §14.9.3.3 SR1 asks only for the BASED clause. A national or bit-usage leaf is admitted by both. The precedent is already in the tree: the old negative fixture pb151-based-comp-leaf, which pinned COBOLNET1695 for the COMP shape, was DELETED at the PB164 landing for exactly this reason — it was rejecting legal source. The same argument now applies, unchanged, to the three remaining leaf kinds.

WHAT EACH RULE LOSES. GR3: 'the number of bytes required to hold an item as described by data-name-1' is never computed for such a record, so the two width halves that DO work (the template width; the ODO maximum, conformance:2023/pb80_based_odo_group) can never be reached for it. GR4a/b: no address is established, so neither the RETURNING pointer nor the based item's address is set (the GR5 not-available leg itself is real since PB151 — on notAvail both GR4 addresses hold NULL by construction). GR7: the WITH FILLER ALL TO VALUE THEN TO DEFAULT lowering is exact where it runs (conformance:2002/allocate_initialized) but cannot run over such a record. GR9: null-seeding class-object / class-pointer items inside allocated storage has no realization at all, and since the PB164 landing the reason is no longer 'the cell model' in general — that model now carries every NUMERIC usage — but the pointer-class leaf specifically.

WHAT WOULD CLOSE IT: a cell layout carrying a two-byte national position and a sub-byte bit run (the §8.5.1.6.3 cursor walk already computes bit extents elsewhere — see the CALL bit-alignment screen), plus a pointer-class slot so GR9's null seeding has somewhere to write; then delete COBOLNET1695's three remaining arms and ship positive goldens mirroring stepd_based_comp_leaf for a NATIONAL leaf, a GROUP-USAGE BIT leaf and a POINTER leaf, retiring conformance:negative/pb164-based-national-leaf the way pb151-based-comp-leaf was retired.

SPEC REFS as carried by the rows: §14.9.3.4 GR3, GR4a/GR4b, GR5, GR6, GR7, GR9; §13.18.5.3 SR1/SR2; §14.9.3.3 SR1.

src/Cobol.Net.Compiler/Binding/Passes/StorageFormPass.cs#ForceStringCanonical (the HasImageByteForm admission to the shared byte cell) with src/Cobol.Net.Compiler/Binding/DataBinder.Ptr.cs#PtrBindBasedAndAddressables (the bind-time COBOLNET1695), consumed by src/Cobol.Net.Compiler/CodeGen/Verbs/PtrEmitter.cs#EmitAllocate and src/Cobol.Net.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs#BindAllocateInitialized

## Partially landed — the USAGE BIT third, 2026-09-04

**LANDED:** a BASED / EXTERNAL / ADDRESS-OF record with a `USAGE BIT` leaf (elementary or under
`GROUP-USAGE BIT`) is now ordinary cell-backed storage. **STILL OPEN:** the NATIONAL third and the
pointer-class third — this note stays `open` for those two.

**THE MECHANISM WAS NOT WHAT THE NOTE SAID.** The note read the bit half as "a sub-byte packing the shared
cell does not lay out", i.e. missing machinery. It was not missing: `AssignClassOffsets`' bit-laid arm walks
the §8.5.1.6.3 cursor and `CobolBits.ReadWindow`/`WriteWindow` window the result, both shared by the cell
path already — [[PB203]] built them and opened `ComputeTier` (REDEFINES) to bit leaves, and the CELL gate
was never opened. Two spellings of one law: `ComputeTier` was a DENY-list, `ForceStringCanonical`'s local
`CellCapable` an ALLOW-list, and every widening had to be applied twice. This is the ninth recorded instance
of this repo's two-arm-dispatch shape, on the same pair whose eighth instance the Step D wave had already
fixed once.

**THE FIX IS THE COLLAPSE, not the widening.** `DataBinder.ByteWindowResidueOf(DataItem leaf) -> string?` is
now THE ONE byte-window carriage gate — an allow-list returning the residue clause naming why a leaf is
refused — and both callers route through it, each wrapping the clause in its own surface phrasing. Two
smaller divergences closed with it: a Pic-less leaf and a NATIONAL-usage numeric were denied by the cell and
admitted by REDEFINES. `ByteWindowResidueDriftTests` pins all four surfaces (REDEFINES · EXTERNAL ·
BASED+ALLOCATE · ADDRESS OF) to ONE verdict per leaf, so discharging either remaining residue is a single
edit that opens every surface at once. Its failure branch was fired before being trusted: re-introducing
PB231's exact divergence turns it red naming the two surfaces that drifted.

**Third arm found and fixed in the same sweep:** `PtrBinder.PtrBindAddressOf`'s COBOLNET0869 printed a
HAND-WRITTEN LIST of the reasons a record might not be cell-backed instead of the class's own
`RejectReason`, which its two siblings (`CallMakeExternal`, `PtrBindBasedAndAddressables`) had always
interpolated. The drift test caught it.

**Evidence.** `conformance:2002/pb231_based_bit_leaf` — ALLOCATE over `01 R BASED.` with
`PIC 1(4) BIT + PIC 1(4) BIT + PIC 1(8) BIT + PIC X(2)`, windowed through a second BASED `PIC X(4)`:
`FUNCTION ORD` reads 66 67 90 91, so the two 4-bit runs SHARE byte 0 (§8.5.1.6.3 rule 1), the 8-bit run
takes byte 1, and the `X(2)` starts at byte 2 — §14.9.3.4 GR3's byte quantity is FOUR where a character sum
says five. GR4a and GR4b are observed to address the SAME storage; GR7's `WITH FILLER ALL TO VALUE THEN TO
DEFAULT` is observed over a bit record including an unnamed `1(4) BIT` FILLER run, which takes §14.9.20.4
GR6c's Boolean default "Figurative constant ZEROES". Identical at 2002 / 2014 / 2023; COBOLNET0900 at 85.

**Rows.** `GR-14.9.3.4-3`, `-4`, `-7` re-verdicted with the bit-arm evidence and stay **PARTIAL** (GAP
unchanged — the national and pointer thirds still refuse). `GR-14.9.3.4-9` untouched: its remaining half is
purely the pointer arm.

**What each remaining third needs** (each a distinct storage-model mechanism, not a widening):
- **NATIONAL / RESIDUE-11** — a 2-byte-per-position byte-window overlay (UTF-16BE, the `CobolBits.NatBytes`
  serialization the storage channel already uses), which is ONE residue behind THREE gates: `ComputeTier`,
  the cell forcer, and `GateNationalRecords` (FD/SD records). Collapsing the first two into
  `ByteWindowResidueOf` means the overlay opens both at once; the FD gate is a third caller that should join
  it. ⛔ The SIZE question is settled and must not be re-opened: §13.18.60.4 GR8's "equal to or a multiple of"
  would permit a 1-byte national character, but D-N1/D-N3 chose TWO and `FUNCTION BYTE-LENGTH`, CONVERT and
  CONFORMANCE.md item 33/188 already answer 2 — changing it is an owner decision, not an implementation one.
- **Pointer-class** — `StorageCell.Ref` is a `string`; a pointer/objref leaf has no byte image at all, so
  §14.9.3.4 GR9's null-seeding of class-object/class-pointer items in allocated storage needs a parallel
  object-slot alongside the byte image. The reachable declarations are the ones §13.18.60.3 SR14 does NOT bar:
  a level-1 elementary `USAGE POINTER BASED`, and a BASED item of a STRONG type declaration carrying such
  members.
