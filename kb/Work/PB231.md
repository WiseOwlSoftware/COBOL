# PB231

**Rows:** `GR-14.9.3.4-3`, `GR-14.9.3.4-4`, `GR-14.9.3.4-7`, `GR-14.9.3.4-9`

a BASED record with a NATIONAL, USAGE BIT or pointer-class leaf is refused at bind (COBOLNET1695), so ALLOCATE computes no byte quantity, establishes no address and runs no INITIALIZE expansion for data descriptions §13.18.5.3 SR1/SR2 expressly permit.

Rows: GR-14.9.3.4-3 (the byte quantity), -4 (GR4a/b addresses), -7 (the GR7 WITH FILLER ALL TO VALUE THEN TO DEFAULT expansion), -9 (GR9's null-seeding of class-object/pointer items). ONE storage-model boundary, four rules that all stop at it.

MECHANISM (from the rows' own READ evidence). The Step D second gate widened ForceStringCanonical to admit every HasImageByteForm leaf to the shared byte cell, so a BASED record with a COMP / COMP-5 / BINARY-* / PACKED-DECIMAL / COMP-1 / COMP-2 / INDEX leaf is now ordinary cell-backed storage — witness conformance:2023/stepd_based_comp_leaf, which ALLOCATEs `01 R` with S9(4) COMP + S9(3) COMP-3 + COMP-1 leaves, windows the same cell through a second BASED PIC X(8) entry and reads all eight bytes with FUNCTION ORD (FF FE, 12 3D, 3F C0 00 00) — the 2+2+4 sum GR3 demands. THREE LEAF KINDS STILL HAVE NO LAYOUT IN THAT CELL: a NATIONAL position is TWO bytes over a byte-addressed cell (the rows call this RESIDUE-11), a USAGE BIT run is a sub-byte packing, and a pointer-class item is not a byte sequence at all. For those, PtrBindBasedAndAddressables draws the bind-time COBOLNET1695 and nothing downstream runs — witness conformance:negative/pb164-based-national-leaf.

WHY THAT IS REJECTS-LEGAL-SOURCE. §13.18.5.3 SR1/SR2 restrict a BASED subject only to 'shall not be of class object' and 'shall not be a dynamic-length elementary item or a variable-length group', and §14.9.3.3 SR1 asks only for the BASED clause. A national or bit-usage leaf is admitted by both. The precedent is already in the tree: the old negative fixture pb151-based-comp-leaf, which pinned COBOLNET1695 for the COMP shape, was DELETED at the PB164 landing for exactly this reason — it was rejecting legal source. The same argument now applies, unchanged, to the three remaining leaf kinds.

WHAT EACH RULE LOSES. GR3: 'the number of bytes required to hold an item as described by data-name-1' is never computed for such a record, so the two width halves that DO work (the template width; the ODO maximum, conformance:2023/pb80_based_odo_group) can never be reached for it. GR4a/b: no address is established, so neither the RETURNING pointer nor the based item's address is set (the GR5 not-available leg itself is real since PB151 — on notAvail both GR4 addresses hold NULL by construction). GR7: the WITH FILLER ALL TO VALUE THEN TO DEFAULT lowering is exact where it runs (conformance:2002/allocate_initialized) but cannot run over such a record. GR9: null-seeding class-object / class-pointer items inside allocated storage has no realization at all, and since the PB164 landing the reason is no longer 'the cell model' in general — that model now carries every NUMERIC usage — but the pointer-class leaf specifically.

WHAT WOULD CLOSE IT: a cell layout carrying a two-byte national position and a sub-byte bit run (the §8.5.1.6.3 cursor walk already computes bit extents elsewhere — see the CALL bit-alignment screen), plus a pointer-class slot so GR9's null seeding has somewhere to write; then delete COBOLNET1695's three remaining arms and ship positive goldens mirroring stepd_based_comp_leaf for a NATIONAL leaf, a GROUP-USAGE BIT leaf and a POINTER leaf, retiring conformance:negative/pb164-based-national-leaf the way pb151-based-comp-leaf was retired.

SPEC REFS as carried by the rows: §14.9.3.4 GR3, GR4a/GR4b, GR5, GR6, GR7, GR9; §13.18.5.3 SR1/SR2; §14.9.3.3 SR1.

src/Cobol.Net.Compiler/Binding/Passes/StorageFormPass.cs#ForceStringCanonical (the HasImageByteForm admission to the shared byte cell) with src/Cobol.Net.Compiler/Binding/DataBinder.Ptr.cs#PtrBindBasedAndAddressables (the bind-time COBOLNET1695), consumed by src/Cobol.Net.Compiler/CodeGen/Verbs/PtrEmitter.cs#EmitAllocate and src/Cobol.Net.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs#BindAllocateInitialized
