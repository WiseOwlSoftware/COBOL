# PB170

PB155 widened the §8.8.1.1 class screen to `OperandContext.ArithmeticIndexWindow` (the R29 contexts: SET,
PERFORM/SEARCH VARYING, compound subscripts, compound relation/EVALUATE operands — pinned by
`pb155-set-to-edited`). The PB155 review fleet's refuter measured the arm that widening cannot reach: a
SIMPLE subscript name resolves in `ReferenceResolver.ResolveSubscriptName` → `PositionRead`, which renders
`CobolTable.Occ(<string field>)` directly from the token — `ExpressionBinder.OperandRef` never runs, so no
class screen fires. `T(XE)` with `01 XE PIC X(4)` (or `PIC XXBXX`) compiles clean under STRICT and
digit-decodes the image, while `T(XE + 1)` now draws COBOLNET0844.

WHAT WOULD CLOSE IT: the same category test at the resolver's subscript-name arm (only an integer numeric
item or an index-name is a legal subscript, §8.4.2.2), a negative fixture `T(<PIC X item>)`, and a sweep of
the resolver's other direct-render arms for the same bypass.

*(Found by the PB155 pre-landing review fleet, 2026-08-29 — the runtime-correctness refuter's caveat 1.
Full claims in the session scratchpad `pb155-fleet-confirmed.json`.)*

## Re-verification and correction (2026-08-31, cluster-B implementation wave, tree `9a89fbd1`)

⛔ **TWO CLAIMS IN THE BODY ABOVE DO NOT SURVIVE RE-VERIFICATION, and either would have mis-scoped the fix.**

**(a) The citation is wrong.** "WHAT WOULD CLOSE IT" says "only an integer numeric item or an index-name is a
legal subscript, §8.4.2.2". §8.4.2.2 is **Qualification** and says nothing about subscript operand classes. The
real chain is §8.4.2.3.2 (the subscript general format is exactly `ALL | arithmetic-expression-1 |
index-name-1 [{+|-} integer-1]`, so a bare data-name is admitted ONLY as arithmetic-expression-1) → §8.8.1.1
(which admits only a NUMERIC identifier, a numeric literal, or ZERO) → §8.5.2.1 Table 2 (category alphanumeric
is class ALPHANUMERIC). This is feedback_a_real_clause_can_answer_a_different_question: had it propagated it
would have shipped a §-number answering a different question, in a code comment, under `--check`'s approval.

**(b) The contrast claim is FALSE.** The note says `T(XE + 1)` "now draws COBOLNET0844" and only a SIMPLE
subscript bypasses. Measured on `9a89fbd1`:

    01 XE PIC X(4) VALUE "0002".  MOVE E(XE)     TO R   -> compiled clean, R=B   (digit-decoded)
    01 XE PIC X(4) VALUE "0001".  MOVE E(XE + 1) TO R   -> compiled clean, R=B   (the note says 0844)

`RenderSegment` routes to the screened D18 path only for a slash, a function, an unresolvable name, a **scaled**
operand inside a compound, or a token with no `case` arm. Compoundness alone does not route, and `Pic.Scale` is
0 for an alphanumeric item — so plain `+` renders token-by-token and never reaches the binder either. **A fix
scoped to "the simple arm only" would have left the compound arm digit-decoding and looked green.** Pinned by
`negative/pb170-subscript-alphanumeric-compound`.

**AND THE DEFECT IS WIDER THAN THE SUBSCRIPT.** The same `ResolveSubscriptName` → `PositionRead` path serves
REFERENCE-MODIFICATION bounds (§8.4.3.3.3 SR4 makes both bounds arithmetic expressions): `W(XE:2)` compiled
clean, R=BC. And the index-name fast path returned its field **regardless of position**, so `W(IX:2)` was
admitted although §13.18.38.3 r7's five contexts do not list a ref-mod position. One renderer, two positions,
one answer.

**FIXED BY:** `ReferenceResolver.ScreenPositionOperandClass`, screening the fast path IN PLACE (rerouting to
D18 was considered and rejected — it would materialize a §15.4 temp and a PendingPreOp for every permissive
alphanumeric subscript, changing permissive-lane emitted text), with the `_probing` guard (kb/Work PB157) and
the `--permissive` lane; the index-name fast path gated on `SegmentPosition.Subscript`; and the verdict taken
from the ONE §8.5.2.1 classifier rather than a fifth category switch — which also closed [[PB213]].

`RenderSegment`'s docstring ("the renderer is an optimization over that route, never the arbiter of what is
legal in the position") was FALSIFIED by this defect and is now true again by construction, not by claim: the
fast path asks the same classifier the binder would have asked.
