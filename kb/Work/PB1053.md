# PB1053 — OPEN

## Measured
```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. C40FR.
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
           SELECT F ASSIGN TO "c40.dat" ORGANIZATION IS SEQUENTIAL.
       DATA DIVISION.
       FILE SECTION.
       FD F.
       01 R.
          05 A PIC X DYNAMIC LENGTH LIMIT 5.
          05 KY PIC X(3).
          05 C PIC X DYNAMIC LENGTH LIMIT 5.
          05 FILLER PIC X(2).
       PROCEDURE DIVISION.
           OPEN OUTPUT F
           MOVE "AA" TO A MOVE "KEY" TO KY MOVE "CCCC" TO C
           WRITE R
           CLOSE F
           OPEN INPUT F
           READ F
           DISPLAY "A=[" A "] KY=[" KY "] C=[" C "]"
           CLOSE F
           STOP RUN.
```

prints **`A=[AAKEY] KY=[CCC] C=[C]`**.

## The rule
`cite.py --check 8.5.1.11.2 "behaves in all respects as though it were in fact contiguous with its neighbors"` → OK
(§8.5.1.11.2). The data written is the data READ must return; a record layout that cannot be re-split is not a
contiguous image of the record the program wrote.

## Code site
`CobolVarGroup.FromContiguous` (the take step: the first dynamic member absorbs every byte beyond the fixed run).
Determination D-FRA (`docs/CONFORMANCE.md` §3; `docs/COBOLNET_FILES_DESIGN.md` D27).

## What the fixer owes
A file image from which every member length is recoverable: either persist each dynamic member's length (a prefix
per member, D-FRA amended in CONFORMANCE.md and the files design) or refuse, at bind, a record whose layout the
chosen image cannot invert — the standard leaves the physical form to the implementor, so this is a DESIGN change
recorded as such, surveyed against GnuCOBOL. PB1025's key-within-record logic reads the same take step: sweep it.
