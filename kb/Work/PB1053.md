# PB1053 — LANDED

## Measured
```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. C40FR.
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
           SELECT F ASSIGN TO "c40.dat" ORGANIZATION IS SEQUENTIAL.
       DATA DIVISION.
       FILE SECTION.
       FD F.
       01 R.
          05 A PIC X DYNAMIC LENGTH LIMIT 5.
          05 KY PIC X(3).
          05 C PIC X DYNAMIC LENGTH LIMIT 5.
          05 FILLER PIC X(2).
       PROCEDURE DIVISION.
           OPEN OUTPUT F
           MOVE "AA" TO A MOVE "KEY" TO KY MOVE "CCCC" TO C
           WRITE R
           CLOSE F
           OPEN INPUT F
           READ F
           DISPLAY "A=[" A "] KY=[" KY "] C=[" C "]"
           CLOSE F
           STOP RUN.
```

prints **`A=[AAKEY] KY=[CCC] C=[C]`**.

## The rule
`cite.py --check 8.5.1.11.2 "behaves in all respects as though it were in fact contiguous with its neighbors"` → OK
(§8.5.1.11.2). The data written is the data READ must return; a record layout that cannot be re-split is not a
contiguous image of the record the program wrote.

## Code site
`CobolVarGroup.FromContiguous` (the take step: the first dynamic member absorbs every byte beyond the fixed run).
Determination D-FRA (`docs/CONFORMANCE.md` §3; `docs/COBOLNET_FILES_DESIGN.md` D27).

## What the fixer owes
A file image from which every member length is recoverable: either persist each dynamic member's length (a prefix
per member, D-FRA amended in CONFORMANCE.md and the files design) or refuse, at bind, a record whose layout the
chosen image cannot invert — the standard leaves the physical form to the implementor, so this is a DESIGN change
recorded as such, surveyed against GnuCOBOL. PB1025's key-within-record logic reads the same take step: sweep it.

## Landed (wave 59 E)

Re-probed first on the implementer's Debug build of `df452130e`: `A=[AAKEY] KY=[CCC] C=[C]`, file bytes
`0B 00 00 00 41 41 4B 45 59 43 43 43 43 20 20` — reproduced. After the fix: `A=[AA] KY=[KEY] C=[CCCC]`.

**Design (rule 5 — the estimate "one take step" was wrong).** The take step cannot invert ANY record with two or more
variable-length components (both sides of a fixed member, or side by side), so no split rule over the characters can
be the fix. The fix makes the record's member boundaries travel WITH the record, outside it: determination
**D-FRA (v)** (CONFORMANCE.md §3; COBOLNET_FILES_DESIGN D27). A variable-length group record is sent with its
**extent table** (`RecordExtents`: each component's fixed-run offset and current length — `CurrentExtents()` /
`StorageCell.ContiguousExtentsAt`, `OperandText.RecordAreaExtents`), framed by `RecordFraming` after the length word
(bit 31) in both shapes — `OK §9.1.7.2` "any information the implementor may add to the record on the physical storage
medium", and `OK §12.4.5.11.4 1)` "Any method used shall not be reflected in the record area or the record size" —
carried by the relative store, `KeyedRec`, and the sort store, and handed back as `CurrentRecordExtents` /
`LastReturnedExtents`. `CobolContiguousLayout.Decompose` / `Position` honour it only when the receiving group
CORRESPONDS (`OK §8.5.1.12.2` "Two dynamic-length elementary items correspond if they start at the same relative byte
positions within their groups") and it describes the record received; otherwise the take step. Sibling sweep (the
PB1025 key logic reads the same step): `IndexedConnector.KeyOf` / `AreaKey`, `CobolSort.Key.At`, and every entry that
takes a record-area image (READ KEY, START, DELETE, REWRITE target) now pass the table. Rejected: refusing the layout
at bind (legal source), an in-record length prefix (COBOLNET1562's clause; it would enter the record).

Witness: `conformance:2014/pb1053_dynamic_members_both_sides` (sequential incl. in-place REWRITE, relative, indexed
with a key flanked by dynamic members incl. READ KEY / REWRITE / DELETE / START from the area, SORT RELEASE/RETURN and
USING/GIVING), `conformance:negative/pb1053-dynamic-members-both-sides-at-2002`, `unit:RecordExtentsTests`.
Residual by design: a LINE SEQUENTIAL line and a fixed-length record-sequential block have no frame, so such a file
still splits by the take step (stated in D-FRA (v)).
