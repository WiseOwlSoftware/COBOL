# PB994 — LANDED (w1004c)

## Repro — measured
`scratchpad/reg12/q07_sortrel.cob`: a RELATIVE file (ACCESS SEQUENTIAL) as SORT USING, a line-sequential GIVING →
`q07_sortrel.cob(23,12): error COBOLNET1757: SORT/MERGE USING/GIVING on Relative file 'RPF' (sequential slice;
relative/indexed USING-GIVING — incl. the GR15b relative key 1..n — are the G5 keyed slice)`.

## The rule
`OK  §14.9.40.4 15)` — "For a relative file, the relative key data item for the first record returned has the value 1;
for the second record returned, the value 2; etc." SR12 ("If file-name-2 references a relative or an indexed file, its
access mode shall be sequential or dynamic") presupposes such files are legal operands.

## Code site
`SortBinder` (the "G5 keyed slice" refusal); the emitter's USING/GIVING loops assume a sequential connector.

## What the fixer owes
USING: read a relative/indexed file in its sequential order through the existing keyed connectors. GIVING: write
relative records with the relative key 1..n (GR15 b), indexed records by prime key (an out-of-order key is the INVALID
KEY path the declarative sees). MERGE shares both arms. Goldens for relative and indexed, USING and GIVING.

## Landed — w1004c (fix-lane group C, wave 1004)

**Re-probed first:** `q07_sortrel` shape (a RELATIVE file as SORT USING) was COBOLNET1757 "sequential slice" on the wave's own
build, as filed — and so was every keyed file, legal or not, because `SortMapIoFiles` refused `!f.IsSequential`.

**The refusal was the only block.** The implicit transfers already run through the runtime file facade (`FileReadSharedOk` for
the as-if READ NEXT, `FileWriteShared` for the as-if WRITE), which dispatches on organization exactly as for an explicit
READ NEXT / WRITE, so lifting it needed no new connector — only the bind-time rules the refusal had been masking and the two
organization-specific stores:
 - **SR12 / §12.4.5.5.2 SR1 (and SR-14.9.24.3-13):** `SortMapIoFiles` (the one USING/GIVING mapper of SORT and MERGE) now
   refuses ACCESS MODE RANDOM by name, for USING and GIVING (SR1 covers both phrases; SR12 / SR13 restate it for USING),
   and admits SEQUENTIAL and DYNAMIC keyed files. The rule gets its own enforcement site (it had none; the only refusal was
   the incidental "slice" one).
 - **SR9 / MERGE SR10:** `SortBinder.ScreenIndexedGivingKey` — the first key shall be ASCENDING and lie at the byte location
   and size of the indexed GIVING file's prime record key (`RecordLayout.KeyWindowOf` of both), screened with the lift so the
   over-rejection did not become an under-rejection (as PB994's own 14c extension warned).
 - **GR15 b) / MERGE GR12 b), the relative key sequence 1..n:** `SortEmitter.EmitGivingFile` — under sequential access the
   connector numbers the records; under DYNAMIC access the as-if WRITE names its slot through the RELATIVE KEY item, so a
   running count is stored there and handed to the connector (`FileSetRelativeKey`); after every successful write the record
   number lands in the item (`EmitRelativeKeyStore`, the §14.9.51.4 GR29 a) store), so "the content of the relative key data
   item indicates the last record returned". `EmitInputFile` makes the matching §14.9.30.4 GR25 store for the as-if READ NEXT of
   a relative USING file. An indexed GIVING/USING file needs nothing more: key order is the connector's.
 - **The executed witness PB749 asked for:** golden `2023/pb994_sort_giving_indexed_io_warning` — a SORT GIVING an indexed file
   with an ALTERNATE RECORD KEY WITH DUPLICATES, under `>>TURN EC-I-O-WARNING CHECKING ON` and a USE procedure: the as-if WRITE
   of the one record whose alternate key repeats succeeds with status 02 and the declarative runs once, DURING the SORT, with the
   FILE STATUS item holding 02 (`DECL G=02 EC-I-O-WARNING`), then 00 after the implicit CLOSE.
