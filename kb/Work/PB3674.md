# PB3674 — the session's csharp-ls holds a worktree's SourceGen.dll and breaks later builds there

**Sites:** `src/Cobol.Net.Compiler.SourceGen/Cobol.Net.Compiler.SourceGen.csproj` (the `MoveAsideHeldOutput` target), `scripts/test_held_analyzer_output.py` (new self-test), `tests/Cobol.Net.Tests.Unit/HeldAnalyzerOutputDriftTests.cs` (new).

## What happens

Agents use the LSP tool for C# definitions and references (MANDATORY-PRACTICES P13). The session starts ONE csharp-ls
for it, a child of the session's `claude.exe`, and workflow subagents share it. csharp-ls loads the solution's source
generator, `Cobol.Net.Compiler.SourceGen.dll`, straight from the worktree's `bin\Debug\netstandard2.0\`, and keeps it
loaded until the session ends, long after the agent that asked has returned. Any later build in that worktree has to
copy a fresh `SourceGen.dll` over the held file and fails: `error MSB3027: Could not copy
"obj\Debug\netstandard2.0\Cobol.Net.Compiler.SourceGen.dll" to "bin\Debug\netstandard2.0\Cobol.Net.Compiler.SourceGen.dll".
Exceeded retry count of 10 … The file is locked by …`. The builds that meet it are exactly the ones that run AFTER the
agent: the landing lane's ABI-pin settle (`abi_pin.run_measurement`) and a finisher's gate in the same worktree.

PB3339 recorded this as a "trap" for the operator ("the operator session's csharp-ls holds Cobol.Net.Compiler.SourceGen.dll in
a worktree's bin; a version bump's rebuild cannot copy over it (rename the held file)"). A recorded weak spot is a defect;
it was never filed, and loop units now meet it too.

stopped it (its own child) and re-ran the landing.

## Fix direction

The structural fix keeps the navigation server from holding a build output at all: have csharp-ls load analyzer
assemblies through a shadow copy, or point its workspace at a copy of the source generator outside `bin`, so a held
file is never one a build writes. Failing that, tie the server's life to the agent that needs it (the agent stops it
before it returns), and have every process that builds in a finished agent's worktree (the landing lane, a finisher)
first release or rename a held `SourceGen.dll` it can prove belongs to a finished agent (PB3339's rename, done by a
program rather than remembered). Add a drift test or self-test that builds after the navigation server has loaded the
worktree and asserts the build succeeds. Sweep the other analyzer and generator outputs a long-lived process loads
from `bin` (a test host, a build server) for the same lock.

## Landed (wave 20261107 group D)

**Re-probe.** Reproduced on this build with a real holder: a PowerShell 7 process that `Assembly.LoadFrom`s `bin\Debug\netstandard2.0\Cobol.Net.Compiler.SourceGen.dll` (how csharp-ls loads an analyzer) makes the next build with a fresh output fail exactly as the note records (`MSB3027`/`MSB3021`, "locked by"). Measured on the same held file: it cannot be opened for writing or deleted, but it CAN be renamed.

**Fix, at the root and for every caller at once.** The generator project's `MoveAsideHeldOutput` target (`BeforeTargets="CopyFilesToOutputDirectory"`) runs in EVERY build of the project, so the landing's ABI-pin settle, a finisher's gate and an agent's own build are all covered with no per-caller code: when the fresh obj output's timestamp differs from the file already in bin it deletes the old file and, if that fails because it is held, renames it aside as `<name>.<guid>.held`; the copy then succeeds, the holder keeps its renamed file, and the next build deletes the held copies it can. An unchanged output is left alone (incremental builds stay incremental: verified, bin untouched on a no-op rebuild), and an unrenamable file still fails loudly as before. A delete that does not succeed is the expected case, so MSB3061 is a message (the project builds with warnings as errors). The other fix directions are not needed: stopping the server or shadow-copying through the server's own configuration is outside the repository, and `abi_pin.run_measurement`/`tooling_check.py` need no change because the build no longer meets the lock. Sweep: the only Roslyn component in the solution is this project (`IsRoslynComponent`; one `OutputItemType="Analyzer"` reference), and `HeldAnalyzerOutputDriftTests` requires the target in every project that sets it. Test: `scripts/test_held_analyzer_output.py` (Windows self-test run by the self-test runner and CI's windows-self-tests) builds a scratch copy, loads the output in a real process, asserts the premise (cannot open for write), a fresh-output rebuild succeeds with one held copy and the holder alive, a no-op rebuild changes nothing, and a rebuild after the holder is gone leaves no held copy; mutation-checked (with the target disabled the second arm fails with MSB3027).
