# PB3674 — the session's csharp-ls holds a worktree's SourceGen.dll and breaks later builds there

**Sites:** the C# LSP setup (`scripts/hooks/tooling_check.py`, its `C# LSP (csharp-lsp + csharp-ls)` check, and the
plugin configuration it verifies), `scripts/abi_pin.py#run_measurement` (a build that meets the lock), the landing lane
`scripts/orchestrator/land_lane.py` (the process that builds in a finished agent's worktree), `src/Cobol.Net.Compiler.SourceGen/`
(the analyzer whose output csharp-ls loads from `bin`).

## What happens

Agents use the LSP tool for C# definitions and references (MANDATORY-PRACTICES P13). The session starts ONE csharp-ls
for it, a child of the session's `claude.exe`, and workflow subagents share it. csharp-ls loads the solution's source
generator, `Cobol.Net.Compiler.SourceGen.dll`, straight from the worktree's `bin\Debug\netstandard2.0\`, and keeps it
loaded until the session ends, long after the agent that asked has returned. Any later build in that worktree has to
copy a fresh `SourceGen.dll` over the held file and fails: `error MSB3027: Could not copy
"obj\Debug\netstandard2.0\Cobol.Net.Compiler.SourceGen.dll" to "bin\Debug\netstandard2.0\Cobol.Net.Compiler.SourceGen.dll".
Exceeded retry count of 10 … The file is locked by …`. The builds that meet it are exactly the ones that run AFTER the
agent: the landing lane's ABI-pin settle (`abi_pin.run_measurement`) and a finisher's gate in the same worktree.

PB3339 recorded this as a "trap" for the operator ("the operator session's csharp-ls holds Cobol.Net.Compiler.SourceGen.dll in
a worktree's bin; a version bump's rebuild cannot copy over it (rename the held file)"). A recorded weak spot is a defect;
it was never filed, and loop units now meet it too.

## Witness (2026-10-24, wave 20261032)

The wave unit's session (`claude.exe` PID 7660, session `63eb7a6b`) started csharp-ls PID 48964 at 17:47:12 PDT, when
group F's implementer (worktree `wf_6ffe8083-b46-6`, PB3630) began. At 18:24 PDT, after F had returned DONE and been
reviewed CLEAN, the landing lane's attempt `000092-20261025T012405Z-worktree-wf_6ffe8083-b46-6` merged main cleanly and
ran the ABI-pin settle; its build failed on the held `SourceGen.dll` (log
`E:\COBOL-coord\logs\land-lane-000092-20261025T012405Z-worktree-wf_6ffe8083-b46-6.log`), and PB3673 turned that into a
false `CONFLICT`. At 19:15 PDT `Get-Process … .Modules` still showed PID 48964 holding the worktree's `SourceGen.dll`; the unit
stopped it (its own child) and re-ran the landing.

## Fix direction

The structural fix keeps the navigation server from holding a build output at all: have csharp-ls load analyzer
assemblies through a shadow copy, or point its workspace at a copy of the source generator outside `bin`, so a held
file is never one a build writes. Failing that, tie the server's life to the agent that needs it (the agent stops it
before it returns), and have every process that builds in a finished agent's worktree (the landing lane, a finisher)
first release or rename a held `SourceGen.dll` it can prove belongs to a finished agent (PB3339's rename, done by a
program rather than remembered). Add a drift test or self-test that builds after the navigation server has loaded the
worktree and asserts the build succeeds. Sweep the other analyzer and generator outputs a long-lived process loads
from `bin` (a test host, a build server) for the same lock.
