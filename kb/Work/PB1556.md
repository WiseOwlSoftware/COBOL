# PB1556

Found 2026-09-24 by the golden-lane-2 misc-p28 writer on pin f0d582ccd; **re-probe first**.

## Repro

`<scratchpad 9db39f61…>\gl\held\misc-p28\tests\conformance\85\l1c28_read_numeric_fd_record.cob` (FD record `01 R PIC 9`,
READ) and `l1c28_return_numeric_sd_record.cob` (SD record `01 R PIC 9`, RETURN). `cobol <f> --run --std 85` → Roslyn
CS0029 (cannot convert the record text to the numeric field type), exit 70. Legal: a record description entry may be a
single elementary item; READ/RETURN make the record available in the record area (§14.9.30.4, list item c) — cite.py
mislabels it 13) b), PB1554).

## Code site

`src/Cobol.Net.Compiler/CodeGen/…/SequentialIoEmitter.cs:706` `EmitRecordAreaStore`, called from `SortEmitter.cs:451`
and the READ arms. It assumes the record is a GROUP (alphanumeric image). Sweep every record-area store and load (WRITE
FROM, REWRITE, RELEASE, READ INTO, RETURN INTO) for the same assumption — every record kind (elementary numeric,
national, boolean, pointer) must round-trip through the record area's byte image (the typed-native codec boundary).

**Confirmed (golden-lane-2 misc-p28 refuter):** both repros fail on the pin with CS0029 "Cannot implicitly convert type
'string' to 'long'" (READ at (58,29), RETURN at (78,38)); both are legal source (an elementary 01 record is valid in an
FD or SD; SORT SR6 a) accepts it as a key). Expected output: `7` (READ) and `S2 3/2/1` (RETURN).

## Landed (wave 59 G)

**Re-probed on the worktree build (a4cd820b1):** both held repros failed exactly as recorded — CS0029 at (58,29) /
(78,38). Spec refs corrected: RETURN is §14.9.34 (`14.9.32` is RELEASE; the held draft's `14.9.33` is RESUME).

**Mechanism.** The receiving inverse of the record-area image was written twice, and wrong both times.
`OperandText.RecordAreaImage` → `AsStorageImage` sends every elementary shape's STORAGE bytes, but
`SequentialIoEmitter.EmitImageInto`'s elementary arm decoded only national and character carriers, so a native
numeric record area took a `string` (CS0029). Its twin, `MoveEmitter.EmitGroupToElementaryMove` (§14.9.25.4 GR4, "no
conversion of data from one form of internal representation to another"), decoded a native numeric receiver with
the ZONED parser `StoreDisplay`: measured before the fix, the bytes `00 07` into `PIC 9(4) COMP` read 0000,
`00 12 3C` into `PIC S9(5) COMP-3` read 00000, and a FLOAT-LONG receiver did not compile (CS1503).

**Fix — one decode.** `ReceivingStore.StorageArea(target, area, positions)` is the receiving inverse of
`AsStorageImage`, arm for arm: national → `NatReadWindow`, USAGE BIT → `BitsUnpack`, native numeric (any byte form,
float included) → `NumericRenderer.CarrierOfImage`, every string-backed shape as-is. Both arms call it; each keeps
its own FIT rule (a MOVE's alphanumeric fill; a READ's GR15 record fill, unfitted for a national area).
**Load half:** `AsStorageImage` serialized USAGE NATIONAL only for category national, so the national-form numeric of
§13.18.60.3 SR12 went out one byte per digit (`PIC 9(3) USAGE NATIONAL` wrote `37 38 39 20 20 20`). It now composes
as the group codec does (design D-N7): the character image first, then `NatBytes` for any USAGE NATIONAL item.

**Round-trip sweep (every record kind × every record-area verb), all correct after the fix:** BINARY, PACKED,
COMP-5, FLOAT-LONG, SIGN LEADING SEPARATE, PIC N, national numeric, national numeric-edited, national boolean,
USAGE BIT, USAGE INDEX (R40 8-byte image; CS0029 before) records through WRITE FROM / READ / READ INTO (sequential), WRITE FROM / READ / REWRITE FROM / READ INTO
(relative), RELEASE FROM / RETURN INTO (SD, PACKED key sorts -7, 5, 300). Goldens:
`conformance:85/pb1556_elementary_record_area_85`, `conformance:2014/pb1556_elementary_record_area_2014`. Both
fail on the unfixed compiler (CS0029 / CS1503).
