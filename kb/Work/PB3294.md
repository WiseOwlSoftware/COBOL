# PB3294 — Windows console device decoding in StandardStreams.EnsureUtf8

Source: `E:\COBOL-coord\scratch\reports\w1098b-PB3193-report.md`, "New defects", items 1 and 2 (branch worktree-wf_d588a65b-0ab-2, PB3193, PR #138 merged). The report says both share a root (how the console device is decoded and encoded), so one note. Neither was probed: worktree isolation refused a cmd.exe probe. Harm: suspected and unprobed; wrong_answer is not set.

Rule row: DOC-A.1-1 (ACCEPT statement, conversion of data) exists in `docs/rearchitecture/spec-rule-catalog.json`. The report quotes "delivers characters of the UTF-16 repertoire" against it; that quotation was not re-checked here, and no section number is cited.

Code site (re-verified): `src/Cobol.Net.Runtime/IO/StandardStreams.cs` `EnsureUtf8` (:76).

**1. Interactive console ACCEPT.** The input arm of `EnsureUtf8` runs only under `if (Console.IsInputRedirected)`; an interactive console keeps Console's default decoding, the console's input code page, so characters outside the OEM page may be lost (suspected; needs an interactive console).

**2. Console code page leak.** `Console.OutputEncoding = utf8` calls SetConsoleOutputCP on the console the parent shell shares, so cmd may stay on 65001 after `cobol` or a program exits. Probe given by the report: `cmd /c "chcp 437 & dotnet prog.dll <nul & chcp"`.
