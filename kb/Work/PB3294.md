Code site (re-verified): `src/WiseOwl.Cobol.Runtime/IO/StandardStreams.cs` `EnsureUtf8` (:76).

**1. Interactive console ACCEPT.** The input arm of `EnsureUtf8` runs only under `if (Console.IsInputRedirected)`; an interactive console keeps Console's default decoding, the console's input code page, so characters outside the OEM page may be lost (suspected; needs an interactive console).

**2. Console code page leak.** `Console.OutputEncoding = utf8` calls SetConsoleOutputCP on the console the parent shell shares, so cmd may stay on 65001 after `cobol` or a program exits. Probe given by the report: `cmd /c "chcp 437 & dotnet prog.dll <nul & chcp"`.

## Adjudication 2026-10-25 (mythos lane, pinned main 51103b9a1)

**Final verdict:** DEFECT  
**Checkpoint (full record):** `E:/COBOL-coord/scratch/mythos/adj-20261025/PB3294.json`

**Expected from the spec:** Item 1 (interactive ACCEPT). ISO 14.9.1.4 GR1: 'Any conversion of data required between the device and the data item referenced by identifier-1 is defined by the implementor'; A.1 item 1 makes that conversion required and documented, and 4.2.5 requires each implementor-defined element to be documented. WiseOwl COBOL's documented determination (docs/CONFORMANCE.md DOC-A.1-1) is that 'the device delivers characters of the UTF-16 repertoire' and that alphanumeric and national receivers take the characters with no conversion. So ACCEPT X from an interactive Windows console must store U+20AC and U+4E2D as typed, whatever the console's input code page. On the pinned build it stores '?' for every character outside the console input code page: silent data loss contrary to the documented determination. The same row's clause 'an interactive console's input is decoded by the console' is the hole and must be rewritten with the fix. Item 2 (code page leak). The standard does not govern the host shell's console code page (no clause applies; 14.6.1 run-unit independence concerns run units, not the parent process, and is NOT claimed). The bar is the product bar and the code's own stated rule: StandardStreams' remarks refuse the Console.InputEncoding setter because it 'would also change the code page of a console the parent shell shares', yet the output arm calls the Console.OutputEncoding setter, which does exactly that (SetConsoleOutputCP(65001)) and is never restored. Expected: running a COBOL program or the cobol CLI leaves the console's input and output code pages as it found them. Both items share one mechanism and one fix: the display device (DOC-A.1-59, UTF-8 on a redirected stream) and the ACCEPT device need never change a console code page, because .NET serves a console handle whose Console encoding is UTF-16 (code page 1200) through ReadConsoleW/WriteConsoleW and its setter skips SetConsoleCP/SetConsoleOutputCP for 1200.

## Landed (wave 20261716, group A)

Re-probed on the fix lane's own build before the change: both items reproduced (ACCEPT of U+20AC U+4E2D E U+00E9 under input code page 437 stored `64 64 70 234`; `chcp 437 & dotnet disp.dll <nul` left the output code page at 65001, and so did a run with stdout redirected, because the output arm called the setter whenever ANY handle was a console). Fixed at the one root, one change set: `StandardStreams.EnsureUtf8` no longer calls a console code-page setter. Per handle: a redirected stdin/stdout/stderr gets an explicit BOM-less UTF-8 reader or writer on every platform; a Windows console handle gets `Encoding.Unicode` (`ReadConsoleW`/`WriteConsoleW`, no `SetConsoleCP`/`SetConsoleOutputCP`); a Unix terminal keeps its locale on input and carries UTF-8 on output (managed only). The console encodings are set before the redirected writers because the `Console.OutputEncoding` setter re-creates the console's writers (measured: a writer created after it for a redirected handle carried UTF-16 into the pipe). DOC-A.1-1 and DOC-A.1-59 were rewritten with the fix and gained witnesses. Witnesses (`WindowsConsoleDeviceTests`, on a windowless Windows pseudoconsole, `WindowsPseudoConsole`): the first six cases were run against the old tree and all fail (the stderr-redirected case was added after that run) (`Actual: (437, 65001)`; ORD line missing) and pass on the new one. Sibling sweep: `Console.OutputEncoding =`, `Console.InputEncoding =`, `SetConsoleCP`, `SetConsoleOutputCP` appear nowhere else under `src/`, `tools/`, `scripts/`; `ProcessStateOwnerDriftTests` already holds the writes to this file.
