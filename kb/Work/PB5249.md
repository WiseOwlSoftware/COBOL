# PB5249 - GENERATE report-name never takes a SUM ... UPON subtotal for the report's one detail group: EmitGenerate passes no detail to the runtime, so Fires returns false for every UPON term and the counter misses the summary's addends

**Sites:**

- `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/ReportWriterEmitter.cs` (`EmitGenerate`: passes null as the detail for GENERATE report-name)
- `src/WiseOwl.Cobol.Runtime/IO/ReportWriter.cs` (`Fires`, `GenerateCore`)
- `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundTree.cs` (`BoundGenerate.SummaryDetail`)
- `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ReportWriterBinder.cs` (`BindGenerate`: the report-name arm)
- `src/WiseOwl.Cobol.Runtime/IO/ReportWriter.cs` (`GenerateSummary`, `GenerateWith`, `GenerateCore(detailName, printDetail)`)

**Mechanism.** §1985:XIII.3.20.4 GR11 processes a GENERATE report-name of a report with one detail group "as though a GENERATE data-name statement were being executed", and its step a performs "any subtotalling that has been designated for the detail report group". A SUM ... UPON detail-name term is designated for that detail (§1985:XIII.3.19.4 GR9). `EmitGenerate` passes null for the detail of a GENERATE report-name, and `Fires` returns false for every UPON term when no detail is named, so the subtotal is skipped: the plain SUM terms are added and the UPON terms are not. Crossfoot and roll-forward are right, and so is UPON subtotalling on GENERATE data-name. The code read worked at --std 85; whether the 2023 rules make the same requirement was not checked and is part of the fix.

**Found by.** The 1985 code read, slice 52 (probe `E:/COBOL-coord/scratch/coderead-85/out-pipe/work-slice-52/p2upon.cob`). The other half of that read, the USE procedure seeing totals before the crossfoot, is kb/Work PB5127, landed; the probe now shows it fixed.

**Inventory.** `work.py check` refuses a 1985 rule id in `inventory_rows` (kb/Work PB5094, open), so `inventory_rows` is empty and the rows this note claims are the rule ids below. None of them is recorded: the code read's non-conforming verdicts of slices 36-56 wait in `E:/COBOL-coord/scratch/coderead-85/pipe-for-register.json`.

**Rules (1 claimed; every citation checked with `scripts/spec/cite.py --check`).**

- `1985-GR-XIII.3.19.4-9` - `§1985:XIII.3.19.4 GR9` (read: PARTIAL, harm: wrong-answer): "When the addend is a sum counter defined in the same control footing report group"; `§1985:XIII.3.20.4 GR11`: "as though a GENERATE data-name statement were being executed".

**Repro (`p2upon.cob`).** `RD R1 CONTROLS WS-KEY`, one detail DE-1, a CF with `S-UP PIC -999.9 SUM WS-AMT UPON DE-1` and `S-ALL SUM WS-AMT WS-AMT`; MOVE 1.5 TO WS-AMT, GENERATE R1, DISPLAY; MOVE -0.5, GENERATE DE-1, DISPLAY; TERMINATE. `cobol.exe --std 85 --source-format fixed --run p2upon.cob`.

**Observed (the records-85c build of origin/main f2cf36fd15, rerun 2026-11-10).** `AFTER GEN R1  UP= 000.0 ALL= 003.0`, `AFTER GEN DE1 UP=-000.5 ALL= 002.0`.

**Expected (from the 1985 text).** `AFTER GEN R1 UP= 001.5 ALL= 003.0`, `AFTER GEN DE1 UP= 001.0 ALL= 002.0`, and the footing prints `001.0 002.0`.

**Fix direction (root cause, CLAUDE.md rule 4).** For a report with one detail, GENERATE report-name names that detail to the runtime (the binder knows it: it already refuses the statement when there are two), so one subtotalling path serves both forms; the test is the read's program.
