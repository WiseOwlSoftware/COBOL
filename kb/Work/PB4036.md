# PB4036 — a function's type depends on whether its argument was frozen

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/SendingValueTemp.cs:232`; the swap is `ArgumentOrder.Window.Settle`, the typing is `IntrinsicResultType.Resolve`.
Fix sites: `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundTree.cs` (`BoundIntrinsicCall.ResultType`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/ArgumentOrder.cs` (`Window.Settle`),
`src/WiseOwl.Cobol.Compiler/Binding/IntrinsicResultType.cs` (`IsIntegerOperand`), `src/WiseOwl.Cobol.Compiler/Binding/IntrinsicArgumentRules.cs` (`IntegerViolation`, `UnsignedIntegerViolation`),
`src/WiseOwl.Cobol.Compiler/Binding/Procedure/FunctionValueLane.cs` (`IsInteger`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/IntrinsicBinder.cs` (`FunctionResultLength`).

**What.** After PB3974 a frozen function argument that is an integer arithmetic expression is held in a scale-0 item.
`ArgumentOrder.Window.Settle` puts that temp into the call's `Args`, and `IntrinsicResultType.Resolve` then types the settled
call as Integer; the same call unfrozen (and the Category bound before Settle) is Numeric. So one function call has a
different type depending on whether a LATER argument activates a UDF (which is what freezes the earlier ones).

**Failure scenario.** `FUNCTION f(a * b, udf(...))` and `FUNCTION f(a * b, 1)` bind `f` to different result types, which
reach the receiver's rounding, the category checks and the integer-only contexts differently. No program is known to print
a wrong value yet; the divergence is the defect.

**Fix shape.** Type the call from the arguments as written (before Settle), or have Settle keep the expression's type on the
temp it swaps in; one rule for both arms, with an arm that freezes and one that does not.

## Landed

The call's §15.2 type is `BoundIntrinsicCall.ResultType`, asked once of `IntrinsicResultType.Resolve` when the node is built from the
arguments as written; `Window.Settle`'s `with { Args = ... }` copies it, and every reader (the Integer-position screens, `IsIntegerOperand`,
`FunctionValueLane.IsInteger`, the LENGTH fold) reads the node. `ArgumentOrderDriftTests.ACallsType_IsReadFromTheNode_...` refuses a reader that
re-resolves from `call.Args`; `FunctionTypeSettlementTests` pins the agreement of the plain and frozen forms.
Probe on the base tree: `PERFORM FUNCTION MAX (A * B, 5) TIMES` refused COBOL1646, `PERFORM FUNCTION MAX (A * B, FUNCTION UDF (A)) TIMES`
compiled. Now both are refused: whether an always-integral expression argument is an INTEGER argument of §15.59.1's "All arguments integer" row
(§15.3 type 6) is a separate classifier question, reported as a lead.
