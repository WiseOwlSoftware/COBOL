# PB589 — LANDED — the width rule reads a literal and guesses the rest

Found 2026-09-05 by the `PB230` implementer, which closed §14.6.13.2's incompatible-data rules and found this
one row of §14.9.8 still held open by a mechanism that is not incompatible data at all; neither `PB202` nor
`PB205` owns it, so the row moves here. Re-derived on this tree for this note.

## The rule

```
python scripts/spec/cite.py --check 14.9.8.4 "The number of boolean positions in the value resulting from the evaluation of boolean-expression-1 is the number of boolean positions in the largest boolean item referenced in the expression."
OK  §14.9.8.4 3)
```

A boolean-compute's result width is the width of the largest boolean item the expression references. A
reference-modified operand `B(1:N)` references a boolean item of `N` positions (§8.4.3.3.4 defines the unique
data item the reference modification denotes), not `B`'s declared width.

## The mechanism

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs:206`:

```csharp
private static int RefModLen(Place p) =>
    p is RefModPlace { Length: { } lit } && int.TryParse(lit, out int n) ? n
    : /* the inner item's full length */ …;
```

Both callers (`:188`, the width used to size the result; `:233`, the "is this a one-position boolean" test)
take the inner item's FULL length whenever the ref-mod length is not an integer literal — a data-name, an
arithmetic expression, an omitted length with a non-literal start. The result is then wider than GR3 allows:
a `COMPUTE R = B(1:N) AND C` sizes its value from `B`'s declared width, and the `== 1` test at `:233` answers
false for a one-position slice whose length is written as a data-name.

## Fix shape

The width of a reference-modified boolean operand is a RUN-TIME quantity whenever its length is not a
literal, so the bound expression must carry it as an expression (the same `RefModPlace.Length` text the
emitter already renders for the data access), and the boolean-compute result width becomes a runtime `max`
over the operands' widths — sized once per statement, not per evaluation. The `== 1` test at `:233` becomes a
runtime condition on the same quantity where it is not a literal. Goldens: `COMPUTE R = B(1:N) …` with `N`
smaller than `B`'s width, the expected width derived from GR3 and observed through `FUNCTION LENGTH` of the
result and through a receiver narrower than `B`; the literal-length case as the control.

## Landed (wave 58, 2026-09-23)

Re-probed on the implementer's own build first: `COMPUTE R8 = B8(1:N) B-OR B"1111111"` (N=3, B8 PIC 1(8))
gave `11111110`, `B8(K:)` (K=6) the same, where GR3 gives `11100000`. The sweep found TWO more arms of the
same rule: a `BOOLEAN-OF-INTEGER(3, W)` whose argument-2 is a data-name counted as NO item (`11000010`,
GR3 gives `11000000`), and §8.8.4.3.3 SR1's length-1 screen REJECTED `IF BX(1:M)` as an 8-position operand
(COBOLNET1511 on conforming source). The CALL/INVOKE BY CONTENT boolean argument shared the same width
(`CALL … BY CONTENT B8(1:N) B-OR B"1111111"` into an ANY LENGTH formal arrived `[11111110] LEN=8`).

The estimate was wrong in shape (rule 5): a static `max` over "runtime widths" would re-render the slice's
start/length expressions, and a function argument cannot be rendered twice. So the bind-time `Gr3Width` and
the two `ContentBoolWidth` fields are DELETED and the width is carried at RUN TIME beside the value:
`BooleanRenderer.RenderAtItemWidth` wraps each item leaf `CobolBool.Item` and each literal
`CobolBool.Literal`, the operators' `CobolBoolSized` overloads keep the max, `CobolBool.ToItemWidth` applies
it once — one evaluation per operand, and every operand's width is the length of the value it produced.
COMPUTE Format 2, CALL and INVOKE all render through it. The two STATIC length questions (SR1, SR6's
`BoolResultLength`) read one reader, `StaticBoolRefLength` over `RefModPlace.StaticLength`, which answers
null for a run-time slice; both fail open there, as they already did for a run-time-length function.
Goldens `2002/pb589_bool_refmod_width` (COMPUTE, SR1, SR6, the function arm) and
`2023/pb589_call_content_bool_width` (the CALL arm); negative `pb589-bool-refmod-width-below-2002`.
`GR-14.9.8.4-3` PARTIAL → CONFORMS.
