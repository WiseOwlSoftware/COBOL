**Defect.** The `_fileRemoved` arm of `BeginAppending` begins a START A journal and calls `OpenWriter(FileMode.Append)` with no check
that the path is still absent, and `ResumeRunUnitFileLock` then publishes the file-lock column with no test. The keyed
`CreateTheFileAgain` answers I-O status 30 when another run unit has created a file at the path meanwhile (cited as ISO 9.1.13.6
item 1, "I-O status = 30", verified with `scripts/spec/cite.py --check`). If another run unit does create the file in that window,
the WRITE would append to its file; the clerk did not run that scenario.

**Fix direction.** Probe the path as the keyed twin does and answer 30; add a two-run-unit test for the window. The implementer
should probe the scenario first and set `wrong_answer` from the result.

## Landed (wave 20261712 group B)

Re-probed on this build with the three adjudicated witnesses (`SequentialCommitControlTests`, two-run-unit harness): before the fix
the re-creating WRITE answered `00` over a file another run unit had made (`line` and record sequential; COMMIT and ROLLBACK both
left that run unit's file appended to or deleted), and with the other run unit's file still open the refused-then-succeeding WRITE
left `txn-0.journal` and `txn-0.live` behind (`wrong_answer: true`, silent data loss). Fix: `SequentialConnector.BeginAppending`'s
removed-file arm is now `CreateTheFileAgain`, the keyed twin's decision under the entry mutex the lock test holds: a
`HostFile.Probe` that is not Absent answers `30` (§9.1.13.6 item 1); the creating handle is taken `FileMode.CreateNew`, so a file
made between the probe and the open is refused too; the journal this WRITE began is withdrawn (`SequentialTransactions.Withdraw`)
when it created no file, and left to item 8's ROLLBACK when it did, the connector leaving the file it made (`IJournalData.Release`).
The proceed step of `JournalLockTest` returns a status (`Func<string?>`) so the refusal is `30` directly, not an `IOException` routed
through `ForWriteFailure`. Sibling sweep, the note's last sentence: the keyed `CreateTheFileAgain` probed but then took its handle
`FileMode.OpenOrCreate`, so a file an uncovered OPEN OUTPUT made after the probe would be adopted and its empty store created over
it (the journal's START A then deleting it at ROLLBACK); `KeyedConnector.TakeFileLock` now takes `CreateNew` for that one caller
(`newFileOnly`, through `Lock` and `LockCreating`). Witnesses: `SequentialCommitControlTests.A_write_creating_the_file_again_meets_*`
(five rows), `CommitRollbackRuntimeTests.A_keyed_write_creating_the_file_again_meets_*` (the keyed twin's probe half, four rows),
and `FileCreatedAgainDriftTests` for the `CreateNew` half. Design doc: DESIGN-runtime-library.md 2.2.2.14.

**Branch review round 1, finding R1-1 (the OPEN creation arms, same root).** The OPEN arms that create a file from an absent probe
had the window too, and the report's "no deterministic repro" was wrong for them: `FaultHostMedium.BeforeOperation` lands another
run unit's OPEN OUTPUT exactly between the probe and the creating handle. Re-probed with the old spellings restored (`SequentialCommitControlTests.
An_open_creating_the_optional_file_meets_*` goes red for uncovered I-O, uncovered and covered EXTEND) and read from the review's scenarios
for the rest (`A_covered_open_output_meets_*`, `CommitRollbackRuntimeTests.A_keyed_open_creating_the_file_meets_*`): an uncovered OPEN
I-O of an absent OPTIONAL file truncates the other run unit's file (`OpenAuxiliary(Create)`) and answers '05'; an OPEN EXTEND appends
to it and answers '05'; a covered OPEN adopts it (`OpenOrCreate`) and its ROLLBACK removes the other run unit's file as its own
creation (START A), sequential and keyed. Fix at the root, one mechanism for both organizations: a creation decided on
an Absent probe takes a `FileMode.CreateNew` handle (`SequentialConnector.OpenCore`, `HeldWriteStream`, `OpenReader(creates)`;
`KeyedConnector.LockCreating(newFileOnly)`); the refusal (`HostFile.IsAlreadyExists`) makes `FileConnector.Open` run the OPEN again
(at most two such retries, counted apart from PB3482's one share-mode retry), after the unsuccessful attempt withdrew the journal it began, so the new probe finds the file and
the OPEN is that of an EXISTING file (OUTPUT captures and replaces, I-O and EXTEND open it '00'). The journal withdrawal is now one
rule in `FileConnector.WithdrawWhatTheOpenBegan` for both organizations (the sequential connector never withdrew a refused covered
OPEN's journal before, which would have left a START A for the retry to capture into). Not for an OUTPUT whose probe said
Unauthorized (an unlistable directory): the file may be there and OUTPUT replaces it.

**For the next implementer.** `SequentialConnector.CommitControl.cs#CreateTheFileAgain` owns the sequential re-creation (probe, `TakeHeld(FileMode.CreateNew)`,
then `OpenWriter(FileMode.Append)` which finds that handle as `HeldStream`'s own); reuse `JournalLockTest`'s `Func<string?>` proceed for any
first change that can be refused with a status other than a conflict. Trap: `OpenWriter` goes through `HeldWriteStream`, whose handle is
`OpenOrCreate`, so the `CreateNew` handle must be taken first. `KeyedConnector.cs#TakeFileLock(newFileOnly)` is the one keyed place a
creating handle refuses an existing file, and `FileConnector.cs#Open` is the one place an OPEN is made again over the file that stood up
(`OpenAgain.FileMadeMeanwhile`); a new creating arm passes `CreateNew` from an Absent probe and inherits both.
