**2026-11-15, landed (wave 20262043 group D).**

Re-probe on the Debug build: `p2/cd-invoke-ret-implicit.cob` reproduced COBOL0828. Root cause as filed: `CommunicationSectionBinder.AddSlot` built each implicit CD field as a bare `PicInfo` with no PICTURE clause identity and no `DataItem.PictureText`, while §2002:A.1.2.3 GR16 describes it as `02 data-name PICTURE 9(4)` (STATUS KEY `PICTURE XX`, END KEY `PICTURE X`).

Fix: `AddSlot` builds the field's profile with `PictureAnalyzer.Analyze` from the PICTURE text of the A.1.2.3 description, the way a written entry is bound, and keeps the text in `PictureText`. The conformance test (§2002:14.7.1.2.1) now compares equal PICTURE identities. After the fix the probe prints `5=0042`; the golden `pb5617-cd-implicit-field-by-reference-and-returning` passes TEXT LENGTH as an INVOKE RETURNING item, an INVOKE USING argument and a CALL BY REFERENCE argument, and STATUS KEY as a CALL argument.

Sibling sweep: every implicit field goes through `AddSlot` (the Header and Entry slots of all three formats), so DESTINATION COUNT, STATUS KEY, END KEY, MESSAGE COUNT and the rest take the same path. A grep of `new PicInfo(` over `Binding/` outside the passes shows two other implicit items built without a PICTURE clause identity, not probed here (outside this group's root): `ImplicitRegisters.cs:84` and `FileControlBinder.FileSection.cs:351`.
