# PB5372 - an unrecorded run is found only by the default name

**Sites:** `scripts/fuzz_history.py#unrecorded_runs`, `scripts/fuzz_history.py#defects_of`

## What is wrong

The ledger counts a finding in one of two ways. A recorded night's notes are found by its run id, whatever the id is
(`defects_of`: the id occurs in the note's `source`). A finding from a run the history holds no night for (a run that
stopped early, kb/Work PB4010) is found by `unrecorded_runs`, which searches each note's `source` for the pattern
`fuzz-\d{8}-\d{6}`, the name the harness gives a run directory by default.

A run directory can be named by hand (`differential_fuzz.py --out`, `fuzz_night.ps1 -RunDir`); Night 10 is
`fuzz-batch-3000-20261103`. If such a run stops before it is recorded as a night and a finding is filed from it, the
note's `source` names a run the pattern does not match. The note is then in no night's list and in no "Run of" row, and
the page's totals omit it. Nothing reports the omission.

No note is in that state today: the one hand-named run is a recorded night, so the notes that cite it (54 `source`
fields name it) are matched by its id.

## Why it is not a wider pattern

A wider pattern cannot tell a run from the other `fuzz-` names notes cite. The register's `source` fields also hold
`fuzz-judge-2026...`, `fuzz-vet`, `fuzz-night-5` and `fuzz-summary`, none of which is a run.

## A shape that would close it

State the run as a fact instead of finding it in prose: a `fuzz_run:` frontmatter field on every note the triage files
(`fuzz_triage.py` writes the notes, so it knows the run), read by both `defects_of` and `unrecorded_runs`, with
`work.py check` holding it to a non-empty value on a note whose `source` names the fuzz triage. The date of an
unrecorded run then needs a source of its own (the run's run.json while the directory exists, or a field beside
`fuzz_run`), since a hand-given name states none (kb/Work PB5371).
