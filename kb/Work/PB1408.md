## Finding — `data-address-identifier` (rejects-legal-source; rows `GR-8.4.3.11.4-2`)

**Mechanism.** StrongTypeModel.AddressOfRestriction derives 'the type of identifier-1' wrongly: for a restricted data-pointer operand it returns the pointer's TARGET type (PointerRestriction) instead of the pointer item's own type, and for a strongly-typed SUBORDINATE group it returns the enclosing type declaration's name (TypedItemType of the anchor) instead of the subordinate group's type

**Repro.** 01 T-REC TYPEDEF STRONG. 05 T-X PIC X(2). 05 T-G. 10 T-A PIC X(4). / 01 PT TYPEDEF USAGE POINTER TO T-REC. / 01 PPT TYPEDEF USAGE POINTER TO PT. / 01 S TYPE T-REC. / 01 RP TYPE PT. / 01 PP TYPE PPT. / LINKAGE: 01 BS TYPE T-REC BASED. PROCEDURE: (legal) SET PP TO ADDRESS OF RP  -> refused COBOLNET0869; (illegal) SET ADDRESS OF BS TO ADDRESS OF RP -> accepted, runs; (illegal) SET ADDRESS OF BS TO ADDRESS OF T-G OF S -> accepted, fails only at run time EC-BOUND-PTR. (probes G3 G5 G7)

**Expected from the spec.** §8.4.3.11.4 GR2: ADDRESS OF RP is a restricted data-pointer restricted to the type of RP, i.e. PT, so SET PP TO ADDRESS OF RP (PP restricted to PT) is legal, and SET ADDRESS OF BS TO ADDRESS OF RP (BS strongly typed T-REC) violates §14.9.39.3 SR19 second sentence and shall be rejected at compile time; likewise ADDRESS OF T-G OF S is not restricted to T-REC, so rebasing a T-REC-typed based item onto it shall be rejected at compile time (Annex D.9.2.2: an address 'can only be used to address a based item of the same type').

**Observed / reasoning.** G5 is refused ('the receiving data-pointer is restricted to type PT, so the sender shall be ... restricted to the same type') - legal source rejected; G3 compiles and runs (DISPLAY ACCEPTED) - a T-REC view laid over a pointer cell; G7 compiles and aborts at run time with EC-BOUND-PTR (offset 2 + width 6 over 6). Both directions follow from the one accessor that every consumer (SET F7, CALL/INVOKE AddressConformanceReason, relation) shares, so the fix is one place. (Arm (b)'s exact 'type of' a subordinate strong group is not named by the spec; what is certain is that it is not the whole record's type T-REC.) Related but distinct: open PB665 (SR19 data-name-1 half) and PB1063.

**Code site.** src/Cobol.Net.Compiler/Binding/Model/StrongTypeModel.cs#AddressOfRestriction

## What the fixer owes

Derive the restriction from identifier-1's OWN declared type (TypedItemType of the item, not of its anchor; the pointer item's type, not its target); sweep the other AddressOfRestriction callers.

## Landed (wave 1021 group E)

Re-probed on the worktree build before the change: G5 (`SET PP TO ADDRESS OF RP`, PP restricted to PT) was refused
COBOLNET0869, G3 (`SET ADDRESS OF BS TO ADDRESS OF RP`) and G7 (`SET ADDRESS OF BS TO ADDRESS OF T-G OF S`) compiled.

**Determination.** §8.4.3.11.4 GR2 (cite.py OK) restricts the address to "the type of identifier-1". A restricted
data-pointer is declared only in a type declaration (§13.18.60.3 SR18, cite.py OK: "If type-name-1 is specified, the
TYPEDEF clause shall be specified for the subject of the entry"), so RP always carries a TYPE clause and its type is
that TYPEDEF (PT), never the type its value addresses (T-REC). §14.9.3.3 SR4 already read "the type of data-name-1"
that way (`TypedItemType`). For a strongly-typed group nested in a strong record, Annex D.8.3 (cite.py OK) makes it a
strongly-typed group item and §8.5.3.1's second alternative gives it as its type the declaration plus its relative
position and length, so it is not the whole record's type. GnuCOBOL has no STRONG, so the ISO text decides.

**Fix (one accessor).** `StrongTypeModel.AddressOfRestriction` returns the strong group's type, or for a restricted
pointer `TypedItemType(operand)`; `TypeRestriction` gained `Member` (the subordinate item whose position identifies
its type) and `Key` (the descriptor spelling, used by `OoConformance.DataPointerKey`), and `SameRestriction` compares
position and length for two subordinate members and never equates a member with a whole declaration (`SamePosition`
is shared with `SameType`). `PtrBinder.ScreenBasedReceiverRestriction` (SR19, data-name-1 side) now asks the same
accessor, so a based restricted pointer is of its own type there too. Consumers: SET Format 7 sender and receiver, CALL
and INVOKE address-identifier arguments (`AddressConformanceReason`), the descriptor key.

**Found and fixed in the same files (I9).** `PtrBinder` printed `ADDRESS OF T-G OF S` operands as `T-GOFS` (ANTLR
`GetText()` drops the blanks); every operand text in the file now reads `DataBinder.WrittenText`.

**Sweep.** Other callers of `PointerRestriction` ask what a pointer ITEM may hold (SET receiver and sender, RETURNING,
descriptor of a pointer item), which is the right question; the two `needed` derivations that conflated it with "the
type of" were `AddressOfRestriction` and `ScreenBasedReceiverRestriction`. Goldens: `conformance:2002/pb1408_address_of_restricted_pointer`,
negatives `pb1408-set-address-of-based-from-restricted-pointer-address`, `pb1408-set-address-of-based-from-subordinate-strong-group`,
`pb1408-call-address-of-restricted-pointer-into-target-formal`.
