## Summary

**Three triggers, one defect (folded by the refuters; the other two records are not separate notes).** (1) `SET object-reference TO NULL` (this record, night 5 fz00381; the night attributed it to FUNCTION BYTE-LENGTH, wrongly). (2) `IF objref = objref` on two universal object references: the night-5 witness fz06082 (first filed under the family `picture-implied-from-value-required--object-reference-ice`; the refuter found that deleting both SETs still aborts at the IF). (3) The same `IF R1 = R2` reduced for the family `universal-object-reference-not-supported--compare-ice` (9-line program OBJC below; night-5 witness fz02265 also reaches it). Same root cause for all three: tree.c `cb_tree_category` gives a `CB_USAGE_OBJECT` field `CB_CATEGORY_UNKNOWN`, and `cb_tree_type` aborts in its default arm (lines 1603-1606), called from codegen.c `output_attr` (line 1606). 8.8.4.2.3 5) and 8.8.4.2.15 (`--check` OK) make the comparison legal. The sweep below is corrected: only the comparison with NULL gets an ordinary error; `IF objref = objref` is NOT refused and aborts. One upstream issue carries all three triggers.

cobc 3.2 aborts with "unexpected category: 0" / "tree.c:1606: internal compiler error" (SIGABRT, exit 134) during code
generation of `SET identifier TO NULL` where the identifier is a universal object reference (`USAGE OBJECT
REFERENCE`). The night that found it (fuzz night 5, fz00381) attributed it to FUNCTION BYTE-LENGTH; reduction shows
BYTE-LENGTH is not involved: removing the one `SET WS-BASED-ENTRY TO NULL` line from the witness makes it compile and
print the same six values WiseOwl prints, and `FUNCTION BYTE-LENGTH` of an object reference alone compiles and runs
(8). The internal error needs only the declaration and the SET. `-fsyntax-only` passes; the abort is in codegen.
cobc warns "OBJECTS is not implemented" for the declaration: object orientation as a whole is unimplemented in 3.2
(`SET objref TO objref` and `IF objref = NULL` are refused with ordinary errors, see below, but `IF objref = objref`
reaches the same internal error); this record is the internal error, which a diagnostic should replace.

## Expected result (per ISO)

ISO/IEC 1989:2023, all checked with `scripts/spec/cite.py --check`:

- §13.18.60.4 GR 22): "A data item described with a USAGE OBJECT REFERENCE clause is called an object reference. An
  object reference is a data item of class object and category object-reference." GR 22) b): "If none of the optional
  phrases is specified, this data item is called a universal object reference."
- §14.9.39.3 (SET statement) SR 8): "Identifier-3 shall be any item of class object that is permitted as a receiving
  item." SR 9): "Identifier-4 shall be an object reference; the predefined object reference SUPER shall not be
  specified."
- §8.4.3.7.3 SR 2): "NULL is implicitly described as class object and category object reference, and is not a
  universal object reference."

So `SET WS-OBJ TO NULL` is SET Format 5 (object-reference-assignment) with legal operands. Edition: USAGE OBJECT
REFERENCE and SET Format 5 are object-oriented features introduced in ISO/IEC 1989:2002 and present in 2014, the
edition `-std=cobol2014` claims. The expected result is a compiled program that sets WS-OBJ to null. An implementation
that does not support object orientation is expected to say so with a diagnostic; it is not expected to abort.

Triggers 2 and 3, `IF R1 = R2` on two universal object references, are a legal relation condition: §8.8.4.2.3 5)
(checked): "Identifier-3 and identifier-4 shall reference data items of class message-tag, object, or pointer, and
shall be of the same category"; §8.8.4.2.15 (checked) defines the comparison of operands of class object. Object
orientation is in neither A.3 nor A.4, so it is a required element, and the internal error is a defect even granting
the known OO gap (refuter, S1).

Edition as recorded by the adjudicator: 2014. `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/tree.c`, function `cb_tree_category`, the `CB_TAG_FIELD` branch (lines 1459-1471): an elementary item whose
  usage is `CB_USAGE_OBJECT` has no PICTURE and matches none of the POINTER / PROGRAM-POINTER / PICTURE /
  external-form arms, so it is given `CB_CATEGORY_UNKNOWN` (0), never `CB_CATEGORY_OBJECT_REFERENCE`.
- `cobc/tree.c`, function `cb_tree_type` (lines 1531-1608): it has a `CB_CATEGORY_OBJECT_REFERENCE` case (line 1598),
  unreachable for such a field, and its default arm reports "unexpected category" and calls `COBC_ABORT` (lines
  1603-1606).
- The caller is `cobc/codegen.c`, function `output_attr`, the `CB_TAG_REFERENCE` case (line 1606), reached for the
  MOVE that `cb_emit_set_to` (`cobc/typeck.c`, line 13435) builds for the SET.
A fix gives a `CB_USAGE_OBJECT` field `CB_CATEGORY_OBJECT_REFERENCE` in `cb_tree_category`. (Refuting wave: refusing the SET with a "not implemented" error before codegen is NOT a sufficient fix, because the relation condition `IF objref = objref` reaches the same abort.)

## Draft issue

**Title:** cobc 3.2: internal compiler error tree.c:1606 'unexpected category: 0' on SET object-reference TO NULL and on a relation condition between two object references

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu `gnucobol3 3.2-4build1`), Linux x86_64.

Two programs reach the same internal compiler error.

1. Save as `b3.cob` and run `cobc -std=cobol2014 -fformat=free -x -o b3 b3.cob`:

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. OBJREF.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 WS-OBJ USAGE OBJECT REFERENCE.
PROCEDURE DIVISION.
    SET WS-OBJ TO NULL
    STOP RUN.
```

Observed: after the expected "OBJECTS is not implemented [-Wpending]" warning, `cobc: unexpected category: 0`,
`cobc: tree.c:1606: internal compiler error`, `cobc: aborting codegen for b3.cob, last statement at line 7`, exit 134.
`-fsyntax-only` succeeds.

2. Save as `objc.cob` and run `cobc -std=cobol2014 -fformat=free -x -o objc objc.cob`:

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. OBJC.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 R1 USAGE OBJECT REFERENCE.
01 R2 USAGE OBJECT REFERENCE.
PROCEDURE DIVISION.
IF R1 = R2 DISPLAY "EQ" ELSE DISPLAY "NE" END-IF
STOP RUN.
```

Observed: the two "OBJECTS is not implemented [-Wpending]" warnings, then the same `cobc: unexpected category: 0` /
`cobc: tree.c:1606: internal compiler error`, `aborting codegen for objc.cob, last statement at line 8`, exit 134, in
`-std=cobol2014` and the default dialect; `-fsyntax-only` exit 0. (Comparing an object reference with NULL,
`IF WS-OBJ = NULL`, is refused with an ordinary error instead; the relation of two object references is not refused.)

Expected: both are legal COBOL 2002/2014. SET format 5 (object-reference assignment) with a universal object reference
receiver and NULL sender: ISO/IEC 1989:2023 14.9.39.3 syntax rules 8 and 9, 13.18.60.4 general rule 22, 8.4.3.7.3
syntax rule 2. The relation condition of two object references: 8.8.4.2.3 rule 5 and 8.8.4.2.15. If object references
stay unimplemented, an error diagnostic in place of the internal compiler error. Refusing only the SET would not be
enough, because the IF reaches the same abort.

Cause, the same for both: `cb_tree_category` (tree.c, CB_TAG_FIELD, default level) returns CB_CATEGORY_UNKNOWN for an
item with CB_USAGE_OBJECT (no PICTURE), so `cb_tree_type`, called from `output_attr` in codegen.c (for the MOVE that
`cb_emit_set_to` generates, and for the comparison), reaches its default arm and aborts; its
CB_CATEGORY_OBJECT_REFERENCE case is never reached for a field. Giving such a field CB_CATEGORY_OBJECT_REFERENCE in
`cb_tree_category` covers both.
