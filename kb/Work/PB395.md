# PB395 — a condition that belongs to an operand read, written as a list of statement kinds

## THE MECHANISM

`EcBinder`'s per-statement enablement scan arms EC-DATA-INCOMPATIBLE with exactly one line
(`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.cs:530`):

```csharp
if (node is BoundMove && ctx.EcState.Turn.Enabled("EC-DATA-INCOMPATIBLE", null, line))
    enabled.Add(("EC-DATA-INCOMPATIBLE", null));
```

and its comment scopes it to *"a de-editing MOVE whose numeric-edited sender holds content that is not a
possible result of editing"* — §14.6.13.2 rule **4**. **The condition does not belong to a statement kind.**
§14.6.13.2 rule 2 states it generally, over any *reference to a numeric sending item during the execution of a
statement*, with exactly two exemptions (a class condition, and a VALIDATE statement). Writing the enablement as
a node-TYPE test makes **every other statement structurally incapable of raising it**, and it is precisely the
hand-maintained list CLAUDE.md rule 5 says a structure should replace: the next verb added is silent by default.

The consequences measured here are three arms of one absence:

* **GO TO … DEPENDING** — §14.9.17.4 GR2 states the condition explicitly for this statement; `BoundGoToDepending`
  contributes nothing to the enabled set, so `ControlFlowEmitter.EmitGoToDepending` emits a bare `(int)(…)` read.
* **MOVE's second arm** — §14.9.25.4 GR6 d)1 has TWO sentences. The first (numeric-EDITED sender, must be a
  possible result of editing) is implemented; the second ("Otherwise, if the content of the sending operand
  would result in a false value in a numeric class condition…") is armed nowhere. **Every comment on the flag
  describes the arm that exists** — `EcBinder.cs:528`, `CheckingFlags.cs:47`, the emitter — which is how the
  missing one stayed invisible. Classic two-arm dispatch.
* **The arithmetic verbs** — §14.9.44.4 GR6 points at §14.6.13.2 among five referenced specifications; four of
  the five are implemented and measured on SUBTRACT, and this is the fifth. ADD, SUBTRACT, COMPUTE and MOVE all
  read the same incompatible item in silence.

## THE RULES, QUOTED, EACH `--check`ED ON THIS TREE

* `--check 14.6.13.2 "when the content of a numeric sending item"` → **`OK §14.6.13.2 2)`** — the general rule:
  *"...that is not described with a standard floating-point usage is referenced during the execution of a
  statement and the content of that sending operand would evaluate to false in a numeric class condition, the
  result of the reference is undefined and an EC-DATA-INCOMPATIBLE exception condition is set to exist"*, with
  the two exemptions being a class condition and a VALIDATE statement. Rule 1 says the same for a BOOLEAN sending
  item — a third arm nothing in the tree arms either.
* `--check 14.9.17.4 "If the content of identifier-1 is not numeric, the EC-DATA-INCOMPATIBLE exception
  condition is set to exist"` → **`OK §14.9.17.4 2)`** (GO TO Format 2's own GR2).
* `--check 14.9.25.4 "Otherwise, if the content of the sending operand would result in a false value in a
  numeric class condition"` → **`OK §14.9.25.4 6) 1.`** — the "Otherwise" arm, *"…the EC-DATA-INCOMPATIBLE
  exception condition is set to exist, and the results of the execution of the MOVE statement are undefined."*
* `--check 14.9.44.4 "14.6.13.2"` → **`OK §14.9.44.4 6)`** — SUBTRACT's pointer rule naming Incompatible data
  first among its five referenced specifications.
* Fatality: EC-DATA-INCOMPATIBLE is a level-3 **FATAL** condition, and the compiler's own catalog agrees —
  `src/Cobol.Net.Runtime/Exceptions/ExceptionCatalog.cs:88` registers it `L3(…, EcFatality.Fatal)`. So with
  checking enabled and no applicable declarative, the conforming outcome is an **abnormal run-unit termination**,
  not a quiet result.

## OBSERVED ON HEAD (`89044aa0`), `--std 2023` — all three arms still silent, with live controls

```
$ cobol.exe p5b-ec-incompat.cob --run     # 'AB' group-moved over PIC 99, then, under a column-8
SEL=[AB]                                  # >>TURN EC-DATA-INCOMPATIBLE CHECKING ON:
FELL-THROUGH                              # GO TO PARA-A PARA-B DEPENDING ON W-N.   ← no condition, exit 0
$ cobol.exe p9-turn-sanity.cob --run      # CONTROL: same directive, same column, a de-editing MOVE
EDITED=[A*B]
abnormal run-unit termination: EC-DATA-INCOMPATIBLE (fatal): the content 'A*B' is not a possible result of
  editing into ZZ9 (a de-editing MOVE, ISO §14.6.13.2 rule 4)     ← the machinery IS live in this build
$ cobol.exe p16-sibling-add.cob --run     # the same garbage item read by ADD, same directive
AFTER-ADD [0000] / NE-ONE                 ← read silently as zero

$ cobol.exe ec_incompat_all.cob --run     # >>TURN EC-ALL CHECKING ON; MOVE PIC X(3) "A1B" TO PIC 9(3)
RN=001 EC=[                               ]        ← FUNCTION EXCEPTION-STATUS blank: no condition set
$ cobol.exe ec_incompat_display.cob --run # the same three characters through a numeric-DISPLAY REDEFINES
RN=001 EC=[                               ]
$ cobol.exe ec_control.cob --run          # CONTROL: identical >>TURN form, an out-of-range subscript
abnormal run-unit termination: EC-BOUND-SUBSCRIPT (fatal): subscript 5 is outside 1..3 (ISO §8.4.2.3.4 GR2)
```

The controls are the load-bearing part: the directive parses (a fixed-form `>>TURN` **starts at column 8**; the
first attempt at column 7 was silently ignored, which is why `p9` exists), the EC machinery runs, and the
condition still does not appear. The stored VALUE is expressly undefined by the rule, so `001` is not itself
the defect — **the missing condition is.**

## THE CODE SITES, AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.cs:528-531` — the `node is BoundMove` arming.
* `src/Cobol.Net.Runtime/Exceptions/CheckingFlags.cs:45-47` — `DataIncompatible`, whose own summary repeats the
  de-editing-only scope.
* `src/Cobol.Net.Compiler/CodeGen/Verbs/ControlFlowEmitter.cs#EmitGoToDepending` — the unchecked selector read;
  `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs#BindGoTo`.
* `src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs#ConvertSource` (case `PicCategory.Numeric`) and
  `src/Cobol.Net.Compiler/CodeGen/Emit/NumericRenderer.cs#FieldNumCore` — the store paths that must test the
  sending content.

**Repair (CLAUDE.md rule 5 — hang it on the READ, not on a statement list):** the enablement belongs at the
**numeric/boolean sending-operand decode chokepoint**, the same place that already carries the EC-DATA-NOT-FINITE
float wrap — which IS ambient and is the working model in this codebase. `CobolNum.FromAlphanumeric` already
walks every character and knows which are non-digits, so the condition can be raised from the CHECKED variant of
that decode rather than from a second scan; the two exemptions (class condition, VALIDATE) become explicit
call-site suppressions, which is the right shape because the standard states them as exceptions to a general
rule. Then **delete the `node is BoundMove` test**: with the read instrumented, every statement is covered
automatically, and the next verb needs no list entry. Pair it with a drift test asserting that the same
incompatible item raises under MOVE, ADD, COMPUTE, GO TO … DEPENDING and a subscript reference — five verbs, one
assertion — so "automatic" stays true.

## THE SIBLING SWEEP THE FIXER MUST DO

* **Rule 1's BOOLEAN arm** (`§14.6.13.2 1)`) — same shape, same silence, not measured here; probe it with the
  same technique before assuming it works.
* Every other EC arming written as a node-type test in `EcBinder`'s scan — the same list-shaped mechanism is
  wherever a condition that the standard states over an OPERAND has been attached to a STATEMENT.
* The two exemptions must be honoured when the read becomes ambient, or the fix over-raises: a class condition
  (`IF X IS NUMERIC`) and VALIDATE both READ the operand and must not raise there (they raise instead when
  invalid data is detected during item identification).
* No golden covers the §14.6.13.2 leg for any verb; the SUBTRACT row's cited golden
  (`conformance:85/optional_on_size_error`) exercises the §14.7.5 phrase only.
