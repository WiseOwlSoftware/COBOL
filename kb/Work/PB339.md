# PB339 — a JUSTIFIED receiver gets ten spaces

**Rows:** `GR-14.9.30.4-4`.

## The program

`<lane3 scratch>/out-b1/probe/rdinto-just/pb3rdvj1.cob` — `FD F RECORD IS VARYING IN SIZE FROM 1 TO 20 DEPENDING
ON WS-LEN`, `01 F-REC PIC X(20)`; write the 5-byte record `ABCDE`; then `READ F INTO WS-DEST` with
`01 WS-DEST PIC X(10) JUSTIFIED RIGHT` and, as a control, `READ F INTO WS-PLAIN PIC X(10)`.

Observed: `LEN=0005` / `JUST=[          ]` / `PLAIN=[ABCDE     ]`.

## The rule

§14.9.30.4 GR4 b) makes the implicit MOVE's sender *the current record*, whose size *is determined by rules
specified in the RECORD clause*; §13.18.43.4 GR16 a) fixes that size as the content of data-name-1, which GR15
has just set to 5. Moving a 5-byte alphanumeric sender to a 10-character JUSTIFIED receiver is §13.18.32.4 GR2 —
right-aligned with left space fill — so `WS-DEST` must be `     ABCDE`. Observed: ten spaces, because a
20-character sender hit §13.18.32.4 GR1 and its LEFTMOST ten characters — the whole record — were truncated away.

## What the compiler does

Both READ emitters build the implicit MOVE from the record AREA place:
`SequentialIoEmitter.EmitRead` does `move.Emit(new BoundMove(new BoundFieldOperand(area), [into]))` where
`area = refs.ResolveItem(rd.File.AreaRecord)`, and `KeyedIoEmitter.EmitRead` does the identical thing. The sender
is therefore always `FileModel.AreaRecord.ImageWidth` characters, space-padded by `FileConnector.Fit`, never the
just-read length.

**The emitter's own comment is why this survived:** it argues the two are *observationally identical* — TRUE for
a LEFT-justified receiver, since both space-fill on the right. The discriminator is the receiving item's
JUSTIFIED clause, which reverses which end is truncated.

**Three sites, one mechanism.** The same shape appears a third time in `SortEmitter.EmitReturn`
(`move.Emit(new BoundMove(new BoundFieldOperand(rt.RecordArea), [into]))`), and §13.18.43.4 GR16 names *the READ
or RETURN statement* jointly, so `RETURN ... INTO` on a varying SD carries the identical defect.

## The fix shape

The material is already at each site and already correct: `EmitReadLengthStore` / `SortEmitter` run
`RuntimeApi.FileLastReadLength` / `SortLastReturnedLength` immediately above, so the sender length is in hand.
Make the implicit MOVE take an EXPLICIT SENDER LENGTH — the GR16 byte count, defaulting to the area width on a
fixed-length file — rather than special-casing JUSTIFIED at three call sites. A record-sequential file whose
final physical record is short (the GR14 '04' case) has the same GR16 b) sender size and so the same exposure,
though GR14 leaves the sender's CONTENT beyond n undefined there.

Land it with **PB348**, which moves these same three implicit MOVEs to bind time: the sender-length parameter
belongs on the bound node the two notes create between them.

**Code sites:** `SequentialIoEmitter.cs#EmitRead` · `KeyedIoEmitter.cs#EmitRead` · `SortEmitter.cs#EmitReturn`.

## Landed — 2026-09-06

**One mechanism, three arms.** The sending operand of every `READ … INTO` / `RETURN … INTO` implicit MOVE is now
built in ONE place — `SequentialIoEmitter.IntoSender` — and the three arms (`SequentialIoEmitter.EmitRead`,
`KeyedIoEmitter.EmitRead`, `SortEmitter.EmitReturn`) call it. A variable-length RECORD clause makes the sender a
new `BoundCurrentRecord` operand carrying the record-area place, the file, the resolved DEPENDING place and the
GR4 b) group-move designation; a fixed-length file keeps the plain `BoundFieldOperand(area)`, because its current
record IS the whole area (§13.18.43.4 GR6). `OperandText` renders it once:
`CobolString.RefMod(<record-area image>, 1, <GR16 count>, allowZeroLength: true)` — the ONE record-area channel
sliced by §13.18.43.4 GR16's own two arms, a) the DEPENDING item's content through the same renderer GR13 a)
uses, b) the connector's last-read length (or the sort store's last-returned length for RETURN). Zero is a legal
length there, which is GR16's closing sentence, not a leniency.

**The note undercounted the defect by one half.** §14.9.30.4 GR4 b) says two things about a `RECORD IS VARYING`
FD, and BOTH were wrong. The second is *"If the file description entry contains a RECORD IS VARYING clause, the
implied move is an alphanumeric group move"*, which was not applied at all: `MoveClassifier` classified on the
record area's own level structure, so a FORMAT 2 FD with an elementary `01` **edited** into an alphanumeric-edited
receiver and **converted** into a numeric-edited one. Measured before the fix (`pb339grp.cob`): `READ F INTO
WS-ED PIC XXBXXBXX` → `ED=[12 34 56]` and `INTO WS-NE PIC 999.99` → `NE=[456.00]`; after, `[ABCDE   ]`-shaped
character deposits with no editing and no conversion, per §14.9.25.4 GR4. `MoveClassifier.IsGroupSender` now
honours the designation, falling through to the structural test when it is absent.

**The two variable-length RECORD formats are no longer indistinguishable.** GR4 b) conditions the group-move
designation on the WORD VARYING and §13.18.43.4 GR16 is stated under the FORMAT 2 heading, so a FORMAT 3
`RECORD CONTAINS m TO n` file must not inherit either. `VaryingRecordInfo` gained `VaryingClause`, set from
`rc.VARYING() is not null`; a rule keyed on that word previously had nothing to key on.

**The sweep, per arm.** `SequentialIoEmitter.EmitRead` and `KeyedIoEmitter.EmitRead` both carried the defect and
both are fixed (measured on this worktree: a keyed `READ … NEXT INTO` a `PIC X(12) JUSTIFIED` receiver printed
twelve spaces at `c34f01ad` and `    K01ABCDE` after). `SortEmitter.EmitReturn` likewise (twelve spaces →
`    K01PQRST`). ⛔ **The `… FROM` arms are NOT siblings and were left alone, with evidence:** §14.9.51.4 GR5,
§14.9.35.4 GR7 and §14.9.32.4 GR4 each make the FROM phrase `MOVE identifier-1 TO record-name-1` *"according to
the rules specified for the MOVE statement"* — an ordinary MOVE whose sender is identifier-1's own item and whose
receiver is the record, with no current-record notion anywhere; the byte count actually written is the separate
§13.18.43.4 GR13 rule, already rendered by `VaryingLengthArg`. Probe `pb339frm.cob` confirms the round trip
(`WRITE F-REC FROM WS-SRC` with `WS-LEN = 5` leaves the area `ABCDE`+15 spaces, writes five bytes, and reads back
`     ABCDE` into a JUSTIFIED receiver; `RELEASE S-REC FROM WS-SSRC` at length 8 returns `    K01PQRST`).

**Goldens.** `tests/conformance/{85,2002,2014,2023}/pb339_into_current_record.cob` (PROGRAM-IDs `PB339C1`…`C4`),
seven legs, byte-identical output at all four editions — no Annex E change touches GR4 b), GR16 or §13.18.32.4,
and every construct used is COBOL-85, so there is no edition gate and no gating diagnostic to check. The legs
cover §13.18.32.4 GR2 (a shorter record right-aligned), GR1 (a receiver shorter than the record, leftmost
truncated), the plain left-justified control, the group-move designation, right truncation, GR16 b)'s
no-DEPENDING arm over a two-record FD, and the RETURN twin.
