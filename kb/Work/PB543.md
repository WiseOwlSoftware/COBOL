### Expected, from the standard
`01 IX USAGE INDEX.` then `INITIALIZE IX` is nonconforming under BOTH rules -- INITIALIZE is absent from SR10's list of contexts that may reference an index data item, and class index is absent from §14.9.20.3 SR1's list of classes identifier-1 may be -- so it shall draw a named compile-time diagnostic.

### Observed
It compiles clean and is a silent NO-OP. `SET IX TO 5`, `IF IX = 5` (a relation condition, one of the contexts SR10 names, so the probe reads the item legally), `INITIALIZE IX`, then `IF IX = 5` again -- the TRUE branch fires both times, and neither `IF IX = 0` nor `IF IX = 1` fires (u_sr10_init_obs prints BEFORE=5 then AFTER=5). So the statement the standard forbids is accepted and then does nothing, which is the worst of both: no diagnostic and no effect. This context is NOT on kb/Work PB215's list -- PB215 (status open) names `PERFORM VARYING ... FROM <index data item>` (re-measured clean here as u_sr10_perf), the Report Writer's VARYING, and a compound subscript segment that reaches the D18 materializer (re-measured clean as u_sr10_sub_cmp, `TE(IX / 1)`). INITIALIZE is a fourth site and belongs on that note. The rest of SR10 is the best-modelled rule in this part: `COMPUTE N = IX + 1` (COBOLNET0844), the simple subscript `TE(IX)`, `MOVE IX TO N` (COBOLNET0809), `DISPLAY IX` (COBOLNET1694) and `ADD 1 TO IX` (COBOLNET1675) all reject, while SET, a relation condition and `FUNCTION LENGTH(IX)` are admitted -- the three-axis OperandContextRules table with a throwing discard arm is what makes a new context declare its answer.
