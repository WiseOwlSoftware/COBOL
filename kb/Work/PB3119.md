# PB3119 — a failed `>>DEFINE` leaves a later `>>IF` reporting an undefined variable

Source: the implementer report for PB1616 (branch worktree-wf_76dbe266-f46-3, `E:\COBOL-coord\scratch\reports\w1070h-PB1616-report.md`, "New defects / leads", carried from the reviewed report). No repro path was recorded, so the first step is a repro.

**Observed (per the report):** when a `>>DEFINE` is refused, a later `>>IF` on the same name reports "'X' is not a previously-defined compilation variable".

**Code sites:**
- `src/Cobol.Net.Frontend/Preprocessor/ConditionalCompilationProcessor.cs:682` `ApplyDefine` returns `null` on a malformed DEFINE (`TrySplitDefine` false, ~line 688) and on a compiler-directive-word name (~line 695); the caller at line 452 then records no `CompilationVariableEvent`.
- `src/Cobol.Net.Frontend/Expressions/CompileTimeExpressionEvaluator.cs:322` emits the second, misleading diagnostic.

**Relation:** PB1367 (landed) wrote in `ApplyDefine`'s comment that a malformed line is "not applied, so one malformed line cannot cascade into misleading 'undefined variable' errors". The lead says the cascade still happens, so this is a new note that names PB1367, not an extension of a landed one. PB1352, PB1366, PB1368 and PB1533 (all landed) touch the same method but not this symptom. PB1616 (open, directive-literal screening) is the branch the lead came from, not the same mechanism.

The expected behavior (whether a later reference to a failed DEFINE's name should be silent or report once) needs a spec read by the implementer; none is asserted here.
