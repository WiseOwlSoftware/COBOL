# PB3119 — a failed `>>DEFINE` leaves a later `>>IF` reporting an undefined variable

Source: the implementer report for PB1616 (branch worktree-wf_76dbe266-f46-3, `E:\COBOL-coord\scratch\reports\w1070h-PB1616-report.md`, "New defects / leads", carried from the reviewed report). No repro path was recorded, so the first step is a repro.

**Observed (per the report):** when a `>>DEFINE` is refused, a later `>>IF` on the same name reports "'X' is not a previously-defined compilation variable".

**Code sites:**
- `src/WiseOwl.Cobol.Frontend/Preprocessor/ConditionalCompilationProcessor.cs:682` `ApplyDefine` returns `null` on a malformed DEFINE (`TrySplitDefine` false, ~line 688) and on a compiler-directive-word name (~line 695); the caller at line 452 then records no `CompilationVariableEvent`.
- `src/WiseOwl.Cobol.Frontend/Expressions/CompileTimeExpressionEvaluator.cs:322` emits the second, misleading diagnostic.

**Relation:** PB1367 (landed) wrote in `ApplyDefine`'s comment that a malformed line is "not applied, so one malformed line cannot cascade into misleading 'undefined variable' errors". The lead says the cascade still happens, so this is a new note that names PB1367, not an extension of a landed one. PB1352, PB1366, PB1368 and PB1533 (all landed) touch the same method but not this symptom. PB1616 (open, directive-literal screening) is the branch the lead came from, not the same mechanism.

The expected behavior (whether a later reference to a failed DEFINE's name should be silent or report once) needs a spec read by the implementer; none is asserted here.

## Resolution (landed 2026-10-30, wave 20261769 group D)

Re-probe on the wave's build: `>>DEFINE FOO AS` (and `AS 1 +`, `AS 'A' OFF`) reported the DEFINE, then a second
"'FOO' is not a previously-defined compilation variable" at a later `>>IF FOO = 2`, a third ("'FOO' — all operands of the
compile-time arithmetic expression …") at `>>IF FOO + 1 = 2` and a fourth at `>>IF B"1" AND FOO`: the cascade PB1367 meant
to prevent, in all three operand arms. The spec asserts nothing about recovery after a refused directive (the
refusal is §7.3.11.2's; what follows it is the implementor's), so the choice is the single report. The root: a refused
DEFINE left no trace, so a name it wrote was indistinguishable from one nobody wrote. `ApplyDefine` now returns a refusal as a `DefineEffect` that names the variable. The run keeps a refused set
beside the table (saved and restored by PUSH/POP with it; a refusal adds the name, a later directive clears it), and the
evaluator, built with `isRefusedName`, fails silently on a refused name that resolves to nothing at the four sites that
read a name. The same fact reaches the later stages as a `Refused` `CompilationVariableEvent` on the timeline
(`DefinitionAt` passes over it, `StandingAt` reads it), which closes the sibling arm the probe found: `>>DEFINE W AS 1 +`
then `>>COBOL-WORDS UNDEFINE W` reported "defined before the directive" a second time. A DEFINE in an omitted branch
refuses nothing. `CONSTANT FROM` needs no change: the binder does not run after a preprocessing error. Witnesses:
`conformance-suite/cases/7.3.11-DEFINE/pb3119-define-refused-then-referenced.cob` and the `RefusedDefine_*` tests of
`ConditionalCompilationDefineTests` (once-only with a control over an unwritten name, PARAMETER refusal, redefinition,
omitted branch, PUSH/POP) and the three `LiteralSlot*` tests of `CobolWordsDirectiveTests`.

## Landing

- `src/WiseOwl.Cobol.Frontend/Preprocessor/ConditionalCompilationProcessor.cs#ApplyDefine` — returns a `DefineEffect`; a refusal is `DefineEffect.RefusalOf(name)` (REUSE it for a new refusal arm), the caller `Run` records it in the live refused set AND as a `Refused` timeline event. A directive in an omitted branch refuses nothing. The trap: `TrySplitDefine`'s `Name` is "" until the first word is a valid name, so a nameless line refuses nothing.
- `src/WiseOwl.Cobol.Frontend/Expressions/CompileTimeExpressionEvaluator.cs#IsRefusedName` — the one silent-failure test, asked at each site that reads a name (a new name-reading site must ask it).
- `src/WiseOwl.Cobol.Frontend/Preprocessor/CompilationVariableEvent.cs#StandingAt` — what a later stage asks when a refusal must stay silent; `DefinitionAt` passes over a refused event, so the binder's `CONSTANT FROM` is unchanged.
- `src/WiseOwl.Cobol.Frontend/Preprocessor/CobolWordsDirectiveProcessor.cs#Literal` — the slot reads `StandingAt` and fails silently on a refusal.
