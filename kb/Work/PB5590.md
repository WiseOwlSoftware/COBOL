# PB5590 - plan_wave.py plans a FINISH-FIRST finisher for a review finding on a superseded branch whose note is landed and whose finding is already fixed on main

**Observed (wave 20262040, origin/main ed86914443).** `plan_wave.py --from-budget` planned group A, a sonnet finisher
for PB5501: "FINISH-FIRST: the branch review of w20262027f (PB5501) found 1 finding(s) at head bcd84970ce", telling the
agent to merge `worktree-wf_a85e43d5-80b-21` and answer review finding R1-1 (a relation over a function whose argument
divides by zero still ends the run unit at --std 85).

Every input said the work was finished:
- `kb/Work/PB5501.md` is `status: landed` on main.
- R1-1 itself is fixed on main: commit 2e217802d6 ("PB5501 review R1-1 a COBOL-85 condition whose function argument raises
  a size error is false too") is an ancestor of origin/main, and `ConditionRenderer.SizeErrorGuarded` on main walks every
  operand with `ArithmeticReach`, whose `Visit(BoundIntrinsicCall)` recurses into the arguments.
- `prune_worktrees.py` (the session probe) already classifies the branch DECISION: "PB5501 is already landed: superseded
  (its work reached main through another branch)", and the previous resume unit recorded it ABANDONED on
  `notes-abandon-20261115b` (PR #1684, still in the merge queue when this wave was planned).

The wave unit released group A (`plan_wave.py --release 20262040a`) and launched B to H only; without that, one of the
three gate slots would have spent a finisher's run re-answering a landed finding.

**The mechanism.** `plan_finishers` turns every report `plan_held` gives a finisher (`s.finisher_by_rep`) into a group.
The finding file's open `finding` records put the report there, and nothing asks whether the report's lead note is landed
or whether the branch is superseded, the very test `prune_worktrees.py` line 860 already makes. The planner and the
lifecycle classifier decide the same question in two places and disagree.

**The same root holds PB5569 and PB5554.** The same plan held both as "same-member collision with in-flight work worktree
wf_5f2b837e-b54-1 [DECISION]" on `ConditionRenderer.cs#SizeErrorGuarded`. That branch is one of the four superseded
branches the resume unit recorded ABANDONED. A DECISION branch whose note is landed holds no member.

**Fix direction.** One predicate, "this branch's work is superseded", in one place, used by `prune_worktrees.py`
for its DECISION row and by `plan_wave.py` for both the finisher arm and the in-flight hold, plus a self-test case: a
report with open review findings whose lead note is landed plans no finisher and holds no member. While a recorded
ABANDON waits in the queue, the planner should also read the pending abandon decision (or wait for it), so a decision
already made is not planned over.
