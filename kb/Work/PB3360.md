# PB3360 — the planner reserves codes and records dispatches before it validates its paths

Found by the wave-1115 unit, 2026-10-17 22:23 PDT. Grepped `kb/Work` for `release_dispatch`, `--release`, `phantom`,
`record_dispatch` + `RED`: PB3186 made `make_dispatch_specs.py` the ledger's one writer and does not cover this order.

**What happened.** The unit ran `plan_wave.py --from-budget --borrow-days 6 --scratch E:\\COBOL-coord\\scratch
--stop-file E:\\COBOL-coord\\scratch\\STOP-loop --cluster PB3353` from Git Bash, which delivered the paths as
`E:COBOL-coordscratch` and `E:COBOL-coordscratchSTOP-loop` (drive-relative, no separators). The planner:
1. reserved codes COBOLNET4277-COBOLNET4300 through `alloc.allocate` (`plan_wave.py:1369`), which cannot be returned
   (`alloc.py` has no release), before looking at either path;
2. created `E:\COBOL\COBOL-coordscratch\` (the drive-relative path resolves under the main checkout's working directory,
   `plan_wave.py:1394-1395`) and wrote groups.json, the eight specs and the args file into the main checkout's tree;
3. through `make_dispatch_specs.py` (`main`, lines 103-107), RECORDED all eight groups in
   `E:\COBOL-coord\inflight-groups.json` and only then ran `check_practices.py`, which went RED on the stop file
   ("not a fleet-scoped STOP-<scope> file") and on every spec (no `STOP-<scope>` path).

The unit released the eight entries by hand (`plan_wave.py --release 1115`), deleted the stray directory and re-planned
with correct paths (codes COBOLNET4301-COBOLNET4324). Had it handed off on the RED instead, the phantom entries of groups G
(`src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4` and two more files) and H
(`src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs`) would have held those files as in-flight work for every
later planner and landing check, since a ledger entry never expires (`release_dispatch` docstring, `plan_wave.py:540`).

**The defects.**
- `plan_wave.py` validates `--scratch` and `--stop-file` after it allocates; the one check it makes there (the global
  stop, `plan_wave.py:1397`) also runs after the codes are taken. A non-absolute scratch, a scratch inside the repository,
  or a stop file that is not `STOP-<scope>` should be refused before `alloc.allocate`, by the same predicate
  `check_practices.py` uses for the stop file (one rule, one place).
- `make_dispatch_specs.py` records the dispatch before the practices check and keeps the record on RED. A RED render is
  not a dispatch: record only on GREEN (or release what it recorded when the check fails).

**Failure scenario.** Any wave unit or attended session that mistypes a path, or renders a spec the check refuses for
another reason, and hands off without `--release`, leaves groups the dispatch ledger reports IN FLIGHT forever; the planner
then holds every note touching their file sets as "file-set collision with running work" and the landing check sees an
overlap that does not exist.
