# PB3795 — a full verdict record erases the row's notes

**Sites:** `scripts/spec/record_verdicts.py#merged` (the write rule, line 140; its docstring says "the record's value (absent = empty, as before PB959)"), `tests/version-matrix/traceability-inventory.json` (the rows below), the record schema (`inventory_schema`)

## Measured

The finisher's inventory record for GR-13.18.49.4-3 was a FULL record (verdict restated, so not witness-only) with no
`notes`. `merged` takes `source = rec` for a non-witness-only record and writes an absent statement field as empty, so the
row's forensic prose (the kb/Work PB1300 derivation, its `cite.py --check` and its goldens, at
`traceability-inventory.json:26403`) was erased. Round 1's 15-row witness batch did the same to SR-13.16.3-8/10,
SR-13.18.29.3-1/2/3, SR-13.18.40.3-31, SR-13.18.49.3-7, GR-13.18.49.4-1, GR-13.18.52.4-1, GR-13.18.57.4-1,
GR-13.18.58.4-3, SR-13.18.60.3-2/3, GR-13.18.60.4-1 and SR-14.9.39.3-19. Nothing refuses it: the loss is silent, in a
file whose prose is the only record of why a verdict stands.

Every bug is a pattern (CLAUDE.md rule 4): any record that restates a verdict without a statement field is the same loss.

## Acceptance

- A record that restates a verdict and omits a statement field either keeps the row's value or is refused by `validate`
  naming the field; the rule is written in `merged` and read by `validate` (the docstring says it is THE write rule).
- `audit_witness_loss.py` or a new audit detects a statement field that went from non-empty to empty across a record
  application, so a hand-written record cannot repeat it.
- The 14 rows named above are restored from git history (the prose before the branch's records), with the restoring record.
