# PB3795 — a full verdict record erases the row's notes

**Sites:** `scripts/spec/record_verdicts.py#merged` (the write rule, line 140; its docstring said "the record's value (absent = empty, as before PB959)") and `#validate`, `scripts/spec/inventory_schema.py#statement_losses` (`STATEMENT_FIELDS`, `StatementLoss`, `statement_text`, `Schema.derivation_superseded`, `Schema.has_spec_derived_test`, `Derivation.refusals`), `scripts/spec/audit_witness_loss.py#check` (`Erasure`, `compare_statements`, `history`, `owed_statements`, `restore_records`, `schema_at`, `self_test`), `scripts/spec/normalize_batch.py#normalize`, `scripts/spec/grammar_findings_to_batch.py#convert`, `scripts/spec/derive_verdict_batch.py` (a comment), `docs/rearchitecture/DESIGN-spec-conformance-review.md`, `tests/version-matrix/traceability-inventory.json` (the 25 restored rows)

## Measured

The finisher's inventory record for GR-13.18.49.4-3 was a FULL record (verdict restated, so not witness-only) with no
`notes`. `merged` takes `source = rec` for a non-witness-only record and writes an absent statement field as empty, so the
row's forensic prose (the kb/Work PB1300 derivation, its `cite.py --check` and its goldens, at
`traceability-inventory.json:26403`) was erased. Round 1's 15-row witness batch did the same to SR-13.16.3-8/10,
SR-13.18.29.3-1/2/3, SR-13.18.40.3-31, SR-13.18.49.3-7, GR-13.18.49.4-1, GR-13.18.52.4-1, GR-13.18.57.4-1,
GR-13.18.58.4-3, SR-13.18.60.3-2/3, GR-13.18.60.4-1 and SR-14.9.39.3-19. Nothing refuses it: the loss is silent, in a
file whose prose is the only record of why a verdict stands.

Every bug is a pattern (CLAUDE.md rule 4): any record that restates a verdict without a statement field is the same loss.

## Acceptance

- A record that restates a verdict and omits a statement field either keeps the row's value or is refused by `validate`
  naming the field; the rule is written in `merged` and read by `validate` (the docstring says it is THE write rule).
- `audit_witness_loss.py` or a new audit detects a statement field that went from non-empty to empty across a record
  application, so a hand-written record cannot repeat it.
- The 14 rows named above are restored from git history (the prose before the branch's records), with the restoring record.

## Landed (wave 20261704, group C)

Re-probed on the branch's own tree: `merged(row, {rule-id, verdict, editions})` on GR-4.2.10-1 took `notes` from 2025
characters to 0, and `validate` said nothing. `audit_witness_loss.py --history`, extended to statements, found the loss was not
two landings but FOUR (PR #541, #599, #628 and the grammar/OO merge of 2026-09-30) and 25 rows still blank, not 14: the 16 rows
of w20261505d, SR-14.9.22.3-1/2, SR-14.9.43.3-1, SR-14.9.48.3-2, SR-13.8.6.2.3-1/2 and GR-14.6.11-3/4, GR-14.9.42.4-1. The
same defect is kb/Work PB3375 (landed with this change); the branch tips themselves, not the merge driver, carried the blank.

**Fix (one root, three arms).**
1. THE WRITE RULE. `merged` takes a statement field from the record when the record NAMES it and from the row when it does
   not (`STATEMENT_FIELDS`), the rule the witness fields already had. `validate` refuses a record that writes a statement empty
   over one the row says something in, naming the field (`inventory_schema.statement_losses`), and a record that changes the
   verdict without restating `notes` (their prose argues the old verdict, as the code-location is re-sited).
2. THE AUDIT. `audit_witness_loss.py --check`, which the gate and CI already run, is RED on a `notes` prose / `derivation` /
   `verdict` / `editions` that went from non-empty to empty against the merge-base (`statement_losses`, the same definition the
   writer asks); `--history` lists every erasure and `--restore-batch` emits the full records that give erased `notes` back.
   The one excuse is a `derivation` the row can no longer stand on (`Schema.derivation_superseded`: a spec-derived
   `test-ref` arrived, or the verdict stopped resolving; branch review R1-1). `--history --restore-batch` restores
   erased `notes` only while the row still carries the verdict the prose argued (`Erasure.verdict`; R1-2).
3. THE SIBLING GENERATORS that manufactured the empty key: `normalize_batch.normalize` wrote `rec["notes"] = ""` into every
   record, and `grammar_findings_to_batch.convert` named `notes: ""` for a MATCHES finding; both now omit it. A third site,
   `derive_verdict_batch`, carries the row's notes forward and only its comment changed.
`audit_witness_loss.py --history` also crashed on every old inventory schema (`Schema` could not read the PB3172-era object
shape); `schema_at` now answers None for a schema it cannot read, which the callers already treat as "use the current one".

The 25 rows were restored from the commit before each loss (batch `pb3795-restore-erased-notes`, full records restating each
row's own verdict and editions, the retired-witness marks kept after the prose). Self-tests: `audit_witness_loss.py
--self-test` (statements, writer, restore, normalize), `grammar_findings_to_batch.py --self-test`.
