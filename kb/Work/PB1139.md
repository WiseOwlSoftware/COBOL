## Finding — `sort-statement-p1` (rejects-legal-source; rows `SR-14.9.40.3-3`)

**Mechanism.** The SR3 exception-checking-PERFORM ban is applied to BOTH SORT formats, but SR3 binds Format 1 only

**Repro.** WORKING-STORAGE: 01 TBL. 05 TE OCCURS 3. 10 TK PIC 9. 10 TV PIC X. PROCEDURE: PERFORM SORT TE ASCENDING TK WHEN EC-ALL DISPLAY "EXC" END-PERFORM. --std 2023 -> rc 70 COBOLNET1617 'SORT shall not appear in imperative-statement-1 of an exception-checking PERFORM (ISO §14.9.40.3 SR3)' (probe sr3tblperf).

**Expected from the spec.** §14.9.40.3 prints SR3 under the 'FORMAT 1' sub-heading (SR3-SR12 are Format 1; SR13-SR15 are Format 2), and no other rule restricts where a table SORT may appear. A Format-2 table SORT in imperative-statement-1 is legal and must compile; only a file SORT there draws COBOLNET1617.

**Observed / reasoning.** EcBinder.ExceptionPerform flags `regionA.SelectMany(Descendants<Core.SortStatementContext>)` with no format test; the parse node is shared by both formats (the grammar defers the split to SortBinder). The file-format control (probe sr3fileperf) is correctly rejected.

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.ExceptionPerform.cs#CheckCrossStatementBans (line 321)

## Finding — `sort-statement-p1` (under-rejects; rows `SR-14.9.40.3-3`)

**Mechanism.** No check enforces SR3's input/output-procedure and declarative-procedure bans on a file SORT: GateMergeInSortMergeProc collects exactly those procedure ranges but flags only MERGE and COMMIT/ROLLBACK, and no declarative-context check exists for SORT

**Repro.** SD SW / SD SW2 / FD IN1 / FD OU1; `SORT SW ASCENDING K1 INPUT PROCEDURE IP-1 GIVING OU1` with `IP-1. SORT SW2 ASCENDING J1 USING IN1 GIVING OU1.` -> --std 2023 rc 0 (probe sr3ip); the same inside an OUTPUT PROCEDURE rc 0 (sr3op); a file SORT inside `USE AFTER STANDARD ERROR PROCEDURE ON IN1` rc 0 (sr3decl).

**Expected from the spec.** §14.9.40.3 SR3: a (file-format) SORT statement shall not appear in an input or output procedure, or in a declarative procedure — each probe must be rejected at compile time (a syntax rule, §4.2.2). A table SORT in an input procedure stays legal (control sr3tblip rc 0).

**Observed / reasoning.** VersionConformancePass.GateMergeInSortMergeProc Pass B tests `s is BoundMerge` and `s is BoundCommitRollback` against the prohibited pc ranges; there is no BoundSort arm (and the pass returns early below 2023, whereas SR3 holds at every edition, so a SORT arm cannot simply be added there). EnclosingContext has a declarative predicate but nothing asks it for SORT. The fix shape is the sibling of MERGE §14.9.24.3 SR1, which names the same three regions — one placement rule table for both verbs rather than a third hand-written arm; the static pc-span approximation has the PB812 (open) inverted-range hole, which the fixer should not inherit.

**Code site.** src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs#GateMergeInSortMergeProc (lines 181-221); src/Cobol.Net.Compiler/Binding/Procedure/EnclosingContext.cs

## What the fixer owes

One placement-rule table for SORT SR3 and MERGE §14.9.24.3 SR1 (they name the same three regions) instead of a third hand-written arm: the PERFORM leg in EcBinder.ExceptionPerform.CheckCrossStatementBans (line ~321) must test the FORMAT (file SORT only); the procedure/declarative legs need a BoundSort arm at EVERY edition (VersionConformancePass.GateMergeInSortMergeProc returns early below 2023, and SR3 holds at every edition) plus an EnclosingContext declarative query. Do NOT inherit PB812's numeric pc-span approximation (inverted THRU ranges escape it).
