## Measured (adjudicator / refuter evidence, verbatim)
### [merge-statement-p1] SR1's declarative-procedure ban is enforced for neither MERGE nor SORT: no binder asks ctx.Enclosing.InDeclarative for a sort-merge verb, so a MERGE or SORT inside a DECLARATIVES USE section compiles clean at every edition
- **Rows:** SR-14.9.24.3-1 — harm `under-rejects`
- **Repro:** SELECT F1/F2/F3 sequential, SD S (01 SR. 05 SK PIC X(4). 05 SD1 PIC X(6)). PROCEDURE DIVISION. DECLARATIVES. D1 SECTION. USE AFTER STANDARD ERROR PROCEDURE ON F3. D1P. MERGE S ON ASCENDING KEY SK USING F1 F2 GIVING F3. END DECLARATIVES. MAIN SECTION. M1. STOP RUN.  -> pinned cobol.exe --std 2023 and --std 85: rc=0, no diagnostic (probe mdecl). Same with SORT S ... USING F1 GIVING F3 (probe sdecl).
- **Expected (spec):** A compile-time diagnostic at every edition: §14.9.24.3 SR1 allows MERGE anywhere 'except ... or in a declarative procedure' (cite.py --check OK); §14.9.40.3 SR3 says the same of SORT (--check OK). Annex E.2 item 20 changed only the SORT/MERGE-procedure half at 2023, so the declarative half applies at 85/2002/2014/2023.
- **Observed:** BindMerge / SortBindFile never consult EnclosingContext.InDeclarative (which exists and is used by other rules); the only MERGE placement checks are COBOLNET1615 (exception-checking PERFORM, EcBinder.ExceptionPerform) and COBOLNET1572 (VersionConformancePass.GateMergeInSortMergeProc, 2023 only).
- **Code site:** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SortBinder.cs#BindMerge; src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SortBinder.cs#SortBindFile; src/Cobol.Net.Compiler/Binding/Procedure/EnclosingContext.cs#InDeclarative

### [merge-statement-p1] MERGE's file-name uniqueness rule has no enforcement site: BindMerge maps USING and GIVING lists independently and never checks that a file-name appears once in the statement
- **Rows:** SR-14.9.24.3-7 — harm `under-rejects`
- **Repro:** MERGE S ON ASCENDING KEY SK USING F1 F1 GIVING F3 (mrep1); MERGE S ON ASCENDING KEY SK USING F1 F2 GIVING F1 (mrep2); ... GIVING F3 F3 (mrep3) -> each rc=0 at --std 2023.
- **Expected (spec):** Each rejected at compile time: §14.9.24.3 SR7 'File-names shall not be repeated within the MERGE statement' (cite.py --check OK). The rule covers file-name-1 through file-name-4, so a USING file named again in GIVING is a violation.
- **Observed:** SortMapIoFiles checks only declared / not-SD / sequential for each name; no set-membership test exists in BindMerge (grep).
- **Code site:** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SortBinder.cs#BindMerge; src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SortBinder.cs#SortMapIoFiles

### [merge-statement-p1] SAME AREA / SAME SORT AREA / SAME SORT-MERGE AREA / SAME RECORD AREA membership is never checked against a MERGE's (or SORT's) file-names
- **Rows:** SR-14.9.24.3-11 — harm `under-rejects`
- **Repro:** I-O-CONTROL. SAME AREA FOR F1 F2. + MERGE S ON ASCENDING KEY SK USING F1 F2 GIVING F3 -> rc=0 (msr11a). Likewise SAME SORT AREA FOR S F1 (msr11b), SAME SORT-MERGE AREA FOR S F3 (msr11c), SAME RECORD AREA FOR F1 F3 (msr11d, a USING and a GIVING file) -> rc=0.
- **Expected (spec):** All four rejected: §14.9.24.3 SR11 'No pair of file-names in a MERGE statement may be specified in the same SAME AREA, SAME SORT AREA, or SAME SORT-MERGE AREA clause. The only file-names in a MERGE statement that may be specified in the same SAME RECORD AREA clause are those associated with the GIVING phrase.' (cite.py --check OK). SORT's §14.9.40.3 SR10 (--check OK) is the sibling.
- **Observed:** Only FileModel.SameRecordAreaPeers is modelled (for record-area sharing); nothing in SortBinder or any validation pass reads a SAME clause for the sort verbs.
- **Code site:** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SortBinder.cs#BindMerge; src/Cobol.Net.Compiler/Binding/Model/FileModel.cs#SameRecordAreaPeers

### [merge-statement-p1] Leniency L5 (COLLATING omitted from the COLLATING SEQUENCE phrase) is accepted silently: the typed-native compiler never emits CBL3617/CBL3618 (descriptors only), and docs/CONFORMANCE.md does not list the extension
- **Rows:** FMT-14.9.24.2 — harm `under-rejects`
- **Repro:** SPECIAL-NAMES. ALPHABET AA IS NATIVE. ... MERGE S ON ASCENDING KEY SK SEQUENCE AA USING F1 F2 GIVING F3 -> rc=0, no warning, at --std 2023 and --std 85 (probe ml5).
- **Expected (spec):** COLLATING is underlined (required) in the §14.9.24.2 general format, so the form is a nonstandard extension: §4.2.10 requires that 'Documentation associated with an implementation shall identify nonstandard extensions for which support is claimed' and 'An implementation shall provide a warning mechanism that optionally may be invoked by the user at compile time to indicate use of a nonstandard extension' (both cite.py --check OK §4.2.10 3)). Either a documented, flaggable extension (the grammar comment's intent) or a rejection.
- **Observed:** CobolIO.g4 sortCollatingPhrase writes `COLLATING? SEQUENCE` and its comment claims 'the omission is flagged under strict modes'; grep of src/Cobol.Net.* finds CBL3617/CBL3618 only in DiagnosticDescriptors.cs:700-706 — the flag lived in the legacy DialectStrictnessChecks and was never ported. Shared with SORT (§14.9.40.2).
- **Code site:** src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4#sortCollatingPhrase; src/Cobol.Net.Frontend/Diagnostics/DiagnosticDescriptors.cs#CBL3617
