## Measured

### Finding page-clause — §13.18.39.3 SR5, SR6 (under-rejects; rows SR-13.18.39.3-5, SR-13.18.39.3-6)

**Mechanism.** BindReportDescriptionClauses applies the §13.18.39.4 GR3 defaults but never screens the PAGE integers: no integer-1 <= 9999 check (SR5) and no ascending-order check of integer-3..7 and integer-1 (SR6 second sentence)

**Repro.** RD R PAGE LIMIT 10000 LINES. -> rc=0.  RD R PAGE LIMIT 10 LINES HEADING 5 FIRST DETAIL 3. -> rc=0.  RD R PAGE LIMIT 10 LINES FOOTING 12. -> rc=0.  RD R PAGE LIMIT 10 LINES LAST DETAIL 9 FOOTING 7. -> rc=0. (out13/probe/page-clause/{lim,asc,asc2,asc3}.cob, each with one detail group, pinned cobol.exe --std 2023)

**Expected, from the standard.** §13.18.39.3 SR5 'Integer-1 shall not exceed 9999.' and SR6 'Integer-3, integer-4, integer-5, integer-6, integer-7, and integer-1 shall be greater than zero. Wherever specified, they shall be in ascending order, with equality allowed.' -- all four programs are syntax errors. The zero half of SR6 is already enforced (COBOLNET2386).

**Observed.** IntegerOperandPass.Slots maps ReportPageClauseContext/ReportPageSubclauseContext to Nonzero only; BindReportDescriptionClauses int.Parses the values into ReportModel with no comparison, so the runtime runs from an inverted or over-long page model (e.g. FOOTING beyond the page limit). Sibling of open kb/Work PB1058 (int.Parse overflow crash on the same operands, whose fixer note names '§13.18.39.3' as the range rule to report): the checked integer decoder PB1058 routes these through is the natural home for SR5, and SR6's ordering screen belongs right after GR3's defaults are computed (compare only the SPECIFIED integers, per 'Wherever specified').

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs#BindReportDescriptionClauses; src/Cobol.Net.Compiler/Validation/IntegerOperandPass.cs#IntegerOperandPass.Slots

### Finding page-clause — §13.18.39.4 GR1, GR2 c)/d), GR4; §13.18.35.3 SR6 c); §13.18.57.4 GR8 (under-rejects; rows GR-13.18.39.4-1, GR-13.18.39.4-2, GR-13.18.39.4-4)

**Mechanism.** No compile-time screen confines a report group's absolute lines to the page region its TYPE allows (§13.18.35.3 SR6c against the §13.18.57.4 GR7/GR8 limits built from the PAGE integers), so a page heading below FIRST DETAIL or a report heading above HEADING compiles and prints outside its region

**Repro.** RD R PAGE LIMIT 10 LINES HEADING 3 FIRST DETAIL 5. / 01 TYPE PH LINE 7. / 01 DET TYPE DE LINE PLUS 1. -> rc=0; output: 6 blank lines, 'PH' on line 7, the detail on line 8 (gr1ph.cob).  Same RD with 01 TYPE RH LINE 1 NEXT GROUP NEXT PAGE. -> rc=0; RH printed on line 1, above HEADING 3 (gr4rh.cob).

**Expected, from the standard.** §13.18.39.4 GR2 c) 'No report line will appear higher than this position on the page', GR2 d) '...page heading shall be defined so that it terminates before this line', GR4 (a report heading on a page by itself occupies HEADING..page limit), made operative by §13.18.35.3 SR6c 'Any absolute report lines shall be defined in such a way that no line appears above the upper limit or below the lower limit allowed for the report group' with §13.18.57.4 GR8c (page heading lower limit = FIRST DETAIL - 1) -- both programs are syntax errors.

**Observed.** ScreenReportLineClauses screens §13.18.35.3 SR3/SR5/SR7/SR8 only; the binder computes the page model but no screen compares absolute LINE integers with the per-TYPE upper/lower limits. The runtime then honours the written line numbers. The owning row is §13.18.35.3 SR6c (LINE clause adjudication); reported here because the PAGE clause GR1/GR2/GR4 'shall' halves depend on it.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs#ScreenReportLineClauses

### Finding type-clause-p2 — 13.18.57.4 GR7, GR8; consumer 13.18.35.3 SR6 c) (under-rejects; rows GR-13.18.57.4-7, GR-13.18.57.4-8, GR-13.18.57.4-L2.4)

**Mechanism.** The report-group upper and lower limits of 13.18.57.4 GR7/GR8 exist only as runtime placement/page-fit inputs for body groups; nothing at bind computes any group's limits, so their compile-time consumer 13.18.35.3 SR6 c) ('no line appears above the upper limit or below the lower limit allowed for the report group') is unscreened for every group type, and the RH/PH/PF/RF lower limits (GR8 a/b/c/g) are applied nowhere. Separately, GR8 d)'s LAST CONTROL HEADING integer can only be the 13.18.39.4 GR3c default because the phrase has no grammar surface (recorded, unowned, by the page-clause adjudication).

**Repro.** E:/Temp/claude/E--CobolSharp/a700c052-f9e4-4942-84ff-a13c7505d6ec/scratchpad/adj-d1/out13/probe/type-clause-p2/r2.cob (--std 2002): `RD R PAGE LIMIT 20 LINES HEADING 1 FIRST DETAIL 3. 01 PH1 TYPE PH LINE 5. ... 01 DET TYPE DE LINE PLUS 1.`; E:/Temp/claude/E--CobolSharp/a700c052-f9e4-4942-84ff-a13c7505d6ec/scratchpad/adj-d1/out13/probe/type-clause-p2/r2b.cob: `RD R PAGE LIMIT 20 LINES HEADING 2 FIRST DETAIL 5 LAST DETAIL 10 FOOTING 12. 01 DET TYPE DE LINE 2. ... 01 PF1 TYPE PF LINE 11.`

**Expected, from the standard.** All three absolute lines violate 13.18.35.3 SR6 c): PH LINE 5 is below the PH lower limit FIRST DETAIL-1 = 2 (GR8 c); DE LINE 2 is above the body upper limit FIRST DETAIL = 5 (GR7 c); PF LINE 11 is above the PF upper limit FOOTING+1 = 13 (GR7 e). Each program must be rejected at compile time.

**Observed.** Both compile clean and run: r2 prints PH on line 5 and the details beneath it; r2b prints DE on line 2 and PF on line 11 of each page. grep 'upper limit'/'lower limit' in src/Cobol.Net.Compiler finds only one comment; DataBinder.Reports.cs screens 13.18.35.3 SR3/SR4/SR5/SR7/SR8/SR10 but not SR6.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs (ScreenReportLineClauses -- no SR6 c) arm); src/Cobol.Net.Runtime/IO/ReportWriter.cs#CobolReport.LowerLimit (body groups only)
