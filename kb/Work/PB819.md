# PB819 — LANDED — a screen that reads the resolved category cannot see an unresolved one

Filed 2026-09-09 by the registrar (second pass) from the **PB495 implementer's report**, "New defects" —
`scratchpad/reports/PB495-report.md`. **Re-probed on this worktree's own build at `d3ba5795`, with the sibling
control the report names.**

## The measurement — three spellings, one rule

```
$ cobol.exe p14_group_fp.cob --std 2023        01 G. / 05 A USAGE FUNCTION-POINTER.
p14_group_fp.cob(6,11): error COBOLNET0899: data item 'A': USAGE FUNCTION-POINTER …
                                             <-- COBOLNET0899 ALONE; no COBOLNET1724

$ cobol.exe p14b_group_fp_twin.cob --std 2023  01 G USAGE FUNCTION-POINTER. / 05 A PIC X.
p14b_group_fp_twin.cob(5,8): error COBOLNET0899: data item 'G': USAGE FUNCTION-POINTER …
p14b_group_fp_twin.cob(5,8): error COBOLNET1724: data item 'G' is a GROUP item described with USAGE
                             FUNCTION-POINTER … (ISO §13.18.60.3 SR14)
                                             <-- both

$ cobol.exe p14c_group_ptr.cob --std 2023      01 G. / 05 A USAGE POINTER.
p14c_group_ptr.cob(6,11): error COBOLNET1724: data item 'A' is described with USAGE POINTER at level 05,
                          subordinate to 'G', which is not a type declaration that includes the STRONG phrase …
                                             <-- the CORRECT shape for the subordinate spelling
```

The POINTER sibling reports the placement violation on the subordinate spelling; FUNCTION-POINTER does not. The
asymmetry is between the two *arms of SR14*, not between two rules.

## The rule, quoted, with the `--check` line actually run

```
$ python scripts/spec/cite.py --check 13.18.60.3 "A USAGE clause with the MESSAGE-TAG, OBJECT REFERENCE, POINTER, FUNCTION-POINTER, or PROGRAM-POINTER phrase may be specified only for an elementary data item at level 1 or an elementary data item subordinate to a type declaration that includes the STRONG phrase"
OK  §13.18.60.3 14)  (Syntax rules)
```

## Mechanism

`Sr14PlacementClass` (`src/Cobol.Net.Compiler/Binding/DataBinder.UsageDeclaration.cs`) keys on the item's
**resolved** `PicInfo` category. `PictureAnalyzer.ParseUsage` stages FUNCTION-POINTER loud
(`PictureAnalyzer.cs:554-560`, COBOLNET0899) before `BindEntry`'s picture-less synthesis chain
(`src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindEntry`) can give the item a `Pic`, so `Pic` stays null and
arm B — the ELEMENTARY arm — never sees it. The GROUP arm survives because `Sr14PhraseOf` reads the **written**
`OwnUsage` instead.

The file's own doc comment on `Sr14PhraseOf` already records the asymmetry ("its `Pic` stays null and arm B
never sees it"), so this is a **registered-shape confirmation, not a discovery** — and that is precisely why it
needs a note rather than a comment: a known asymmetry with no owner is indistinguishable from a decision.

## Harm, honestly bounded

Today the compile fails either way (COBOLNET0899 is an error), so the user loses only the second diagnostic.
**It becomes a real under-rejection the moment `USAGE FUNCTION-POINTER` lands** — see [[PB817]], which is
exactly that work — because then the placement rule would be enforced on one spelling and not the other, with
nothing to notice. Sequencing matters: PB817 must not land without this.

## The fix shape

Two arms of one rule shall not read two different sources of truth. Arm B should key on the **written or
inherited usage phrase** — the same thing `Sr14PhraseOf` reads — with the resolved category used only where the
rule genuinely speaks of a category. Then a staged usage and a landed usage take the same path, and PB817's
landing needs no second change here.

## Sibling sweep the fixer owes

Every USAGE phrase SR14 enumerates, against both spellings, as a matrix: MESSAGE-TAG (staged — [[PB544]]),
OBJECT REFERENCE, POINTER, FUNCTION-POINTER (staged — this note), PROGRAM-POINTER. The report that found this
built exactly that matrix and found ONE failing cell; a drift test that asserts the matrix — rather than one
`if` per phrase — is what keeps the next staged usage from re-opening it (`feedback_scan_all_similar`, rule 5).

## 2026-09-09 — a SECOND cell, found by composition in landing train 26

[[PB487]] gave MESSAGE-TAG a `Usage` member and refuses the usage by name (COBOLNET1943, declined non-support,
Annex A.3 item 4). That reproduces this note's cell exactly, by a different route: the usage is refused before
`BindEntry`'s picture-less chain, so its `Pic` is a recovery shape with no SR14 class, `Sr14PlacementClass`
cannot see it, and arm B stays unreachable. Measured on the train-26 merge tree:

```
01 G. / 05 A USAGE MESSAGE-TAG.        -> COBOLNET1943                    (SR14 NOT reported)
01 G USAGE MESSAGE-TAG. / 05 A.        -> COBOLNET1943 + COBOLNET1724     (arm A, from the written clause)
```

So the count in "Sibling sweep the fixer owes" is now TWO staged-or-declined cells, not one, and the sweep's own
prediction is confirmed: the row said MESSAGE-TAG would land in this position and it did. Nothing here is a
regression — the compile fails on both spellings either way, and only the second diagnostic is lost — but it
raises the priority of the fix shape above (arm B keying on the PHRASE), because each new declined or staged
usage now adds a cell rather than sharing one.

`UsageInheritanceDriftTests` carves both cells out through ONE predicate, `KeywordRefused`, which names this
note; the carve-out is where the fixer will find the cells to delete.

## Landed — wave 1019 (group E)

**Re-probed on this build** (`--std 2023`): the note's first cell, `01 G. 05 A USAGE FUNCTION-POINTER.`, is **already fixed** —
USAGE FUNCTION-POINTER gained its bound model (`PicInfo.FunctionPointerItem`, PB452/PB817) so arm B's class-keyed
predicate sees it, and it draws COBOLNET1724 beside COBOLNET1958 on both spellings. The **MESSAGE-TAG cell was live**:
`01 G. 05 A USAGE MESSAGE-TAG.` drew COBOLNET1943 alone while `01 G USAGE MESSAGE-TAG. 05 M PIC X(3).` drew 1943 + 1724.

- **The fix, at the root the note named.** `DataBinder.UsageDeclaration`'s arm B no longer asks the resolved CATEGORY
  (`Sr14PlacementClass` → `PointerObjectClass`, the §13.18.44.3 REDEFINES screen's class predicate); it asks the PHRASE:
  `DataBinder.Sr14PhraseOf(DataItem)` = the written clause's phrase, else the resolved profile's usage
  (`ItemCategory.Sr14PhraseOf(Usage?)`, the one recorded verdict per `Usage` member). A usage the compiler refuses by name binds
  a recovery profile with no class, but its usage is a fact the source states — so a refused keyword takes the path a landed
  one takes. `Sr14PlacementClass` and its drift test (`Sr14ClassPredicateIsTheRedefinesScreensClassPredicate`) are DELETED, not
  shimmed; `Sr14PhraseNameOf` now derives from the same reader and keeps its one "compiler defect" arm for a slot-carried item.
- **The matrix.** `UsageDeclarationPlacementMatrixTests` (Conformance) enumerates `ItemCategory.Sr14PhraseOf` over the whole
  `Usage` enum and asserts both spellings of each phrase draw COBOLNET1724 — a usage added to SR14's population is a row
  without anyone remembering it. `UsageDeclarationPlacementDriftTests.Sr14PhraseReaderAgreesWithTheClassPredicate_ExceptWhereTheUsageIsRefused`
  pins the one population where the phrase and class readers differ (MESSAGE-TAG) and the written-clause-only case.
- **The carve-out is gone.** `UsageInheritanceDriftTests` no longer excuses a refused keyword from the GR1 equivalence
  (`01 G USAGE u. 05 A pic.` ≡ `01 G. 05 A pic USAGE u.`): 82 cells pass with `KeywordRefused` deleted — including MESSAGE-TAG and
  FUNCTION-POINTER over seven pictures. COBOLNET0899 is no longer emitted for any usage keyword, so the second use of the
  predicate (the SR8 test) is covered by the existing SR14/1724 early return.
- **Golden.** `negative/pb819-usage-message-tag-elementary` (`01 G. 05 M USAGE MESSAGE-TAG.` — COBOLNET1943 + COBOLNET1724 at 2023).
