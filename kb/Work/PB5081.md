# PB5081 - at --std 85 six USE FOR DEBUGGING syntax rules are unenforced: debugging sections not together first, PERFORM of a debugging section, a debugging procedure as a subject, a subject named twice, ALL PROCEDURES twice, ALL PROCEDURES with a procedure-name

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/ProcedureTableBuilder.cs` (`FinalizeDebug`, `AddDebugSubject`, `DeclCollectSection`, `ResolveDebugProcedure`; the USE FOR DEBUGGING subject binding near lines 568-586), `src/WiseOwl.Cobol.Compiler/Binding/Validation/StatementValidation.cs#CheckDeclarativesBoundary`.

**Mechanism.** The debugging facility binds each subject without screening the 1985 program-level rules: DeclCollectSection queues each debugging section with no check of its place among the declaratives; CheckDeclarativesBoundary admits PERFORM into every declarative section and never asks IsDebuggingSection; FinalizeDebug adds every pc of a subject with no test that the procedure is outside the debugging sections; AddDebugSubject returns silently on a repeat ("deduplicated so a procedure named twice does not double-fire"), which swallows both the repeated subject and the repeated ALL PROCEDURES; nothing relates ALL PROCEDURES to the other USE FOR DEBUGGING statements. One extra lead in the SR5 record (a section-name subject monitors its paragraphs) belongs to the execution note, not here.

**Found by.** The 1985 `--std=85` draft triage (kb/Work PB4995 item 3): each rule below is a conformance-suite draft that did not MATCH at `--std 85`, and its adjudicator decided COMPILER-DEFECT. Harm and observed text are the records'; nothing here was re-derived.

**Inventory.** The traceability inventory carries no 1985 rows yet, so `inventory_rows` is empty; the rows this note covers are the 1985 rule ids listed below (catalog `docs/rearchitecture/spec-rule-catalog-1985.json`).

**Rules (6; every citation checked with `scripts/spec/cite.py --check`).**

- `1985-SR-XV.3.2.3-1` - `§1985:XV.3.2.3 SR1` (record harm: under-rejects, slice-11): §1985:XV.3.2.3 SR1: "Debugging section(s), if specified, must appear together immediately after the DECLARATIVES header." §1985:III.2: "A debugging section is a section that contains a USE FOR DEBUGGING statement." WITH DEBUGGING MODE is specified, so the statement is compiled (§1985:XV.2.1.3 GR1). In the draft a USE AFTER STANDARD ERROR section stands between the DECLARATIVES header and the debugging section, so the 1985 text forbids the program. NOTE ON THE DRAFT'S LINE: it marks line 10 (the USE AFTER STANDARD ERROR statement of S1); the section the rule constrains is the debugging section S2, lines 13-14, so a conforming diagnostic is as likely there. The compiler reports nothing at any line, so the verdict does not depend on the marked line, but the draft's line needs 13 or 14 before it becomes the rule's test.
- `1985-SR-XV.3.2.3-3` - `§1985:XV.3.2.3 SR3` (record harm: under-rejects, slice-11): §1985:XV.3.2.3 SR3: "Statements appearing outside of the set of debugging sections must not reference procedure-names defined within the set of debugging sections." PERFORM DBG-PARA in the nondeclarative paragraph MAIN-PARA references a paragraph defined in the debugging section DBG-SECT, so the 1985 text forbids the statement. The rule has no PERFORM exception: the one the file USE statement carries ("only with a PERFORM statement") is not in the debugging rule.
- `1985-SR-XV.3.2.3-5` - `§1985:XV.3.2.3 SR5` (record harm: under-rejects, slice-11): §1985:XV.3.2.3 SR5: "Procedure-names defined within debugging sections must not appear within USE FOR DEBUGGING statements." D1-PARA is defined in the debugging section D1, and D2's USE FOR DEBUGGING ON D1-PARA names it, so the 1985 text forbids the program. The draft reads the rule correctly; its control (USE FOR DEBUGGING ON MAIN, a section-name) conforms.
- `1985-SR-XV.3.2.3-6` - `§1985:XV.3.2.3 SR6` (record harm: under-rejects, slice-11): §1985:XV.3.2.3 SR6: "Any given identifier, cd-name, file-name, or procedure-name may appear in only one USE FOR DEBUGGING statement and may appear only once in that statement." USE FOR DEBUGGING ON P1 P1 names the procedure-name P1 twice in one statement, so the 1985 text forbids it. The draft reads the rule correctly; its control (ON P1 P2) conforms.
- `1985-SR-XV.3.2.3-7` - `§1985:XV.3.2.3 SR7` (record harm: under-rejects, slice-11): §1985:XV.3.2.3 SR7: "The ALL PROCEDURES phrase can appear only once in a program." USE FOR DEBUGGING ON ALL PROCEDURES ALL PROCEDURES writes the phrase twice (the general format's ellipsis admits the repetition syntactically, §1985:XV.3.2.2), so the 1985 text forbids the program. The draft reads the rule correctly; its control (one ALL PROCEDURES) conforms.
- `1985-SR-XV.3.2.3-8` - `§1985:XV.3.2.3 SR8` (record harm: under-rejects, slice-12): §1985:XV.3.2.3 SR8: "When the ALL PROCEDURES phrase is specified, procedure-name-1 must not be specified in any USE FOR DEBUGGING statement." The draft reads the rule correctly: debugging section D1 says USE FOR DEBUGGING ON ALL PROCEDURES and debugging section D2 says USE FOR DEBUGGING ON MAIN-PARA (a procedure-name-1), and SOURCE-COMPUTER carries WITH DEBUGGING MODE, so both USE statements are compiled (§1985:XV.2.1.3 GR1). The control (D1 ON OTHER-PARA, D2 ON MAIN-PARA) conforms and compiles.
