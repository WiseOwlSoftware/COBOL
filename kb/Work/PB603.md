# PB603 — LANDED — the implicit CLOSE that does not go through CLOSE

Found 2026-09-05 by the `PB235` implementer while making `FileRegistry.CloseByFormat` the one Table 14
dispatch; re-derived on this tree for this note. `process_only` because a single conforming run unit cannot
observe it — the harm is cross-run-unit contamination in a hosted process (the conformance harness, a host that
runs several run units in one process), which is a hygiene defect of the runtime, not a wrong answer to a
program.

## The rule

```
python scripts/spec/cite.py --check 9.1.16 "all record locks established for a file are released by the execution of an explicit or implicit CLOSE statement for the file"
OK  §9.1.16
```

Run-unit termination performs an implicit CLOSE for every open file (§14.6's termination rules); the standard
gives that implicit CLOSE the same effects as an explicit one, including GR9's lock release.

## The mechanism

`src/WiseOwl.Cobol.Runtime/IO/FileRegistry.cs#CloseAll` (~`:308`) iterates `_files.Values` and calls `c.Close()` on
each connector directly — never `Close(name)` and, since PB235, never `CloseByFormat(name, CloseFormat.Normal)`
— so `SharedClose` (`st.Open.Remove(name)` + `PhysicalFileTable.ReleaseAllForConnector`) does not run. The
static registry keeps the terminated run unit's connectors registered as open, and a later run unit in the same
process arbitrating for the same physical file sees them and reports a file-sharing conflict ('61') against a
program that has ended. Contrast `CloseIfOpen` (§14.9.5 CANCEL's implicit close), which routes through
`Close(name)` and is correct.

## Fix shape

Route `CloseAll` through `CloseByFormat(name, CloseFormat.Normal)` for every open connector, so the implicit
CLOSE is the same dispatch as the explicit one (§14.9.6.4 GR1 hoisted, Table 14 symbol c, GR9's release), and
decide deliberately — in the doc comment — whether the recorded "sequential connectors close unconditionally"
quirk survives or retires. Witness: an in-process harness test that runs two run units against one shared file
and asserts the second opens with '00'; the existing `2002/file_sharing*` goldens as the single-run-unit
controls.

## What this note now holds (added by the PB321 implementer, 2026-09-05)

**`GR-14.9.27.4-22` moved here from `PB321`**, and its verdict stays DIVERGES. PB321 closed the third of that
row's three divergences (a `SHARING WITH NO OTHER` connector was made LESS protected than an undeclared one,
because `FileConnector.SharedStreams` opened its handle `FileShare.ReadWrite` and handed arbitration to a table
that could not see an unshared connector). What remains is (1) the SHARING phrase hoisted to statement scope,
which is **PB316**'s mechanism and in flight on another worktree, and (2) — this note's family — the fact that
`PhysicalFileTable` is a field of `FileRegistry`, one per hosting process, so §9.1.15's *"The successful opening
of a file establishes a file lock … thereby preventing other run units from opening that file with incompatible
sharing rules"* has no cross-run-unit realization at all. PB316's landing closes (1) and leaves (2) here.

**Half of the mechanism above is already fixed, and the fix shape below is what is left.** PB321 made the
physical-file deregistration TOTAL — every successful OPEN now registers in `PhysicalFileTable`, so every close
path must release: `SharedClose` lost its `_connectorShares` gate, and `CloseDisplaced`, `CloseAll` and
`CloseAndDrop` all deregister. `CloseAll` therefore no longer leaves a terminated run unit's connectors
registered as open, so the spurious `'61'` a later run unit in the same process could take is gone. ⛔ **That
does NOT close this note**, and the witness test below must still be written: what remains is the structural
half — `CloseAll` still calls `c.Close()` directly instead of `CloseByFormat(name, CloseFormat.Normal)`, so the
implicit CLOSE is still a second dispatch beside the explicit one (§14.9.6.4 GR1's not-open guard, Table 14's
symbol c, GR9's release), and the "sequential connectors close unconditionally" quirk is still undecided. A
green witness written today would pass for the reduced reason and hold the structural gap open.

## Landed (wave 1095 F, 2026-10-16)

**Re-probe.** The note's "`CobolFile._reg` is static" premise is stale: the registry is `RunUnit.Current.Files`, one
per run unit, and PB321 had already made `CloseAll` deregister. What reproduced on this build, with a unit probe that
is now `RunUnitImplicitCloseDriftTests` (a second `FileRegistry` is a second run unit): an injected close-time
`InvalidOperationException` (through the held-line drain, the report writer's hook on every close path) escaped
`CloseAll` with the failing file and every file after it still open; a closed sequential connector came out of
termination with '42'; and three members (`CloseAll`, `Reset`, `CloseDisplaced`) called a connector's own `Close()`
beside the CLOSE dispatch. The user-level route the registrar found (EBCDIC indexed, U+20AC) was closed by PB1150's
'91' screen, so the failure now needs a defect to reach it; §14.6.11 2) still requires the loop to survive it.

**Fix.** (1) `FileRegistry.CloseAll` closes each file through `CloseIfOpen`, the CLOSE dispatch's own entry
(`CloseByFormat`, Table 14's plain CLOSE row, `SharedClose`), so the implicit CLOSE IS the plain CLOSE and a file not
in the open mode is not touched: the "sequential connectors close unconditionally" behavior is retired. Each close is
guarded; after all of them the failure is rethrown (`ExceptionDispatchInfo`, several as one `AggregateException`),
never swallowed. (2) `FileConnector.Close` runs `CloseCore` even when the drain throws, and ends the run-unit file lock
and the open mode in a `finally`, so a failure no I-O status describes cannot leave a §9.1.15 lock standing against
the next run unit. (3) Sibling arms: `Reset` (run-unit start) runs `CloseAll` for whatever an earlier run unit left
open, instead of closing only the sequential connectors and dropping the keyed ones still open; `CloseDisplaced` uses
`CloseIfOpen`; `SharedClose` takes the connector the dispatch holds and absorbed `DeregisterFromPhysical`.
`RunUnit.Terminate` releases static storage in a `finally`. A Roslyn drift test keeps `CloseByFormat` the only caller
of a connector's `Close()` in `FileRegistry`. Design: `docs/FILES_DESIGN.md`, the close-path paragraph of
the Table 19 section.

**Rows.** `GR-14.6.11-2` PARTIAL → CONFORMS. `GR-14.9.27.4-22` DIVERGES → CONFORMS: its three recorded divergences
were closed by PB321/PB740, PB316 and PB833, and were re-probed here (`2002/pb316_open_group_scope` and
`2002/file_sharing` print their goldens, `RunUnitFileLockDriftTests` passes); the deleted `FileConnector.SharedStreams`
witness is retired. Batch `w1095f/pb603-verdicts.json`; GAP 88 → 86.

**Goldens.** None: no conforming program can observe the change (`process_only`). The failure needs a runtime
defect, and the '42' stamp landed on a connector after its run unit had ended. The four unit tests are the witnesses.

**For the next implementer.**
- `src/WiseOwl.Cobol.Runtime/IO/FileRegistry.cs#CloseByFormat` is the ONLY caller of a connector's `Close()`; every close path (`Close`, `CloseIfOpen`, `CloseAndDrop`, `CloseDisplaced`, `CloseAll`, `Reset`) enters it. Reuse `CloseIfOpen` for any new implicit close; `RunUnitImplicitCloseDriftTests.OnlyTheCloseDispatch_CallsAConnectorsOwnClose` fails otherwise.
- `src/WiseOwl.Cobol.Runtime/IO/FileRegistry.cs#CloseAll` guards each close and rethrows after all are closed; `Reset` runs it, so run-unit start closes leftovers the same way.
- `src/WiseOwl.Cobol.Runtime/IO/FileConnector.cs#Close`: closing bookkeeping (run-unit lock, open mode, permanent error) is in a `finally`; the '30' mapping is `MappedCloseCore`. Trap: the held-line drain runs report-writer code against the AMBIENT run unit's registry, not the one being closed.
- `src/WiseOwl.Cobol.Runtime/Control/RunUnit.cs#Terminate`: static storage resets in a `finally` after `CloseAll`.
