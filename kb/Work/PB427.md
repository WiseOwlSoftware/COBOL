# PB427 — a same-type predicate that is neither of §8.5.3.1's two halves

## The mechanism

SR2's whole content is "a group item of the SAME type", and "same type" is defined in exactly one place —
§8.5.3.1 — by TWO conjoined tests: declaration EQUIVALENCE, and (for subordinate items) the same relative
position and length. `src/Cobol.Net.Compiler/Binding/Model/StrongTypeModel.cs:57-63` implements NEITHER:

```csharp
public static bool SameStrongType(DataItem a, DataItem b)
{
    if (TypeAnchor(a) is not { } ra || TypeAnchor(b) is not { } rb) return false;
    if (!string.Equals(ra.TypeName, rb.TypeName, StringComparison.OrdinalIgnoreCase)) return false;   // :60
    return RelativeMemberPath(a, ra).SequenceEqual(RelativeMemberPath(b, rb), StringComparer.Ordinal); // :62
}
```

Line 60 compares the type-NAME as an ordinal-ignore-case STRING where the rule requires the declarations to be
equivalent, and line 62 compares a member-NAME PATH where the rule requires relative byte-or-bit POSITION and
LENGTH. Both substitutions are measurably wrong, in OPPOSITE directions.

The class doc at `:50-56` states the intended criterion as "the §8.5.3 'same subordinate item in equivalent type
declarations' rule", with the parenthetical "cross-program EXTERNAL equivalence is a follow-up". That phrase is
NOT the normative bullet — it is from §8.5.3.1's informative NOTE (rule 2), which describes what the rules mean
"when two typed items are defined in the same source element". The normative bullet says something else, and the
paraphrase is what licensed the path comparison. This is the CLAUDE.md rule-1 failure mode exactly: a real clause
attached to a claim it does not make.

§8.5.3.1's full equivalence test continues: "…starting at the same relative byte or bit position and having the
same length in bytes or bits. Each pair of corresponding elementary items shall have the same ALIGNED, BLANK WHEN
ZERO, DYNAMIC LENGTH, JUSTIFIED, PICTURE, SIGN, SYNCHRONIZED, and USAGE clauses" (with the two currency /
decimal-point exceptions). The same-type test is that equivalence, OR — for subordinate items — equivalence plus
same relative position and length. A NAME match is one conjunct of one half.

⚠ TRANSCRIPTION DEFECT, reported not fixed: the second bullet reads "the same relative byte pr bit position" in
`specs/ISO_COBOL.md`. "pr" is an OCR slip for "or". It does not change the meaning, and the quotation above is
verbatim as transcribed so the `--check` is honest.

## Expected vs observed — RE-RUN ON HEAD (89044aa0)

    (a) FALSE ADMISSION — a wrong value deposited in user data, silently.
        Outer program: 01 SHAPE-T TYPEDEF STRONG. 05 SA PIC X(6).   01 OUTER-X TYPE SHAPE-T IS GLOBAL.
        Contained program: 01 SHAPE-T TYPEDEF STRONG. 05 SB PIC 9(3). 05 SC PIC 9(3).  01 INNER-Y TYPE SHAPE-T.

        alphabetic characters are deposited into two PIC 9(3) numeric items: exactly the data-integrity breach
        §8.5.3.3's restrictions exist to prevent. (The b2 refuter's own probe `r_sr2_nonequiv_same_name.cob`
        reproduces on HEAD too — rc=0, prints MOVED; the probe above adds the DISPLAYs that show the content.)

    (b) FALSE REJECTION — legal source refused.
        01 NEST-T TYPEDEF STRONG. 05 OUTERG. 10 INNERG. 15 LEAFX PIC X(4).
        01 N1 TYPE NEST-T. 01 N2 TYPE NEST-T.
        MOVE OUTERG OF N1 TO INNERG OF N2
        cobol.exe r_sr2_nested_same_offset.cob --std 2023 --run   rc=70
          error COBOLNET1533: MOVE to strongly-typed group 'INNERG': the sending operand shall be a group item
          of the same type (ISO §14.9.25.3 SR2 / §8.5.3.3)
        EXPECTED: accepted. OUTERG and INNERG are subordinate items in equivalent type declarations (the same
        declaration, in fact), both at relative byte position 0, both 4 bytes long — §8.5.3.1's second bullet is
        satisfied and SR2 is met. The paths differ (`OUTERG` vs `OUTERG.INNERG`), so the path comparison refuses
        it.

    THE MAINLINE IS CORRECT and must stay so: a literal sender (`MOVE "123456" TO P1` -> 1533), a FUNCTION sender
    (-> 1533), a different strong type (-> 1533), a structurally identical UNTYPED group (-> 1533), and the
    same-type positive (`conformance:2002/typedef_strong_ok`). `IsStrongGroup` correctly restricts the gate to
    GROUP receivers per §8.5.3.3. A reference-modified same-type sender is rejected twice over (COBOLNET1647 for
    the ref-mod, 1533 for SR2).

⚠ HARM FLAGS, HONESTLY: `rejects_legal_source` is (b), measured. `under_rejects` is (a) — the source there is
ILLEGAL under SR2 and the compiler runs it, so `wrong_answer` is NOT set even though a user sees corrupted data;
the corruption is downstream of the missing rejection. `silent` marks (a).

## The code site and the shape of the repair

- `src/Cobol.Net.Compiler/Binding/Model/StrongTypeModel.cs:57-63` `#SameStrongType` — both wrong conjuncts;
  `:50-56` the class doc quoting the NOTE as if it were the rule; `:32` `#IsStrongGroup`; `:43` `#TypeAnchor`.
- `src/Cobol.Net.Compiler/Binding/Validation/StatementValidation.cs:79` `#CheckStrongMove` — the caller.

**THE REPAIR IS A TYPE-EQUIVALENCE PREDICATE, NOT TWO PATCHED COMPARISONS** (CLAUDE.md rule 5). §8.5.3.1's
equivalence test is a STRUCTURAL walk — for each elementary item in one declaration, a corresponding item in the
other at the same relative position and length with matching ALIGNED / BLANK WHEN ZERO / DYNAMIC LENGTH /
JUSTIFIED / PICTURE / SIGN / SYNCHRONIZED / USAGE — and it is the SAME predicate every other strong-type
restriction needs (`StrongTypeModel` already routes CALL / ACCEPT / STRING / REDEFINES / RENAMES / intrinsics and
the POINTER restriction network through this file). Write `EquivalentTypeDeclarations(DataItem, DataItem)` once,
have `SameStrongType` be `equivalent(anchors) && (sameAnchorItem || sameRelativeOffsetAndLength)`, and delete the
name/path comparison. Cross-program equivalence then falls out of the same walk instead of being a "follow-up".
The two currency-symbol / decimal-point exceptions in §8.5.3.1 are part of the predicate, not an afterthought.

⚠ **A GREEN TEST PINS THE WRONG CRITERION AND MUST BE REBASELINED WITH THE FIX.**
`TypedefStrongTests.MoveDifferentSubgroupPosition_Rejected1533` states the criterion CORRECTLY in its own
docstring — "by relative POSITION, not just type-name" — while the code it pins does path matching. It passes
only because in its GA/GB fixture path and position happen to agree. Add (b) above as a POSITIVE golden in the
same change set, and a negative whose paths agree but whose positions do not.

## Landed — 2026-09-13, the predicate is §8.5.3.1's, not a stand-in

`StrongTypeModel` now carries ISO §8.5.3.1 whole, as TWO entry points and nothing else:

- **`EquivalentTypeDeclarations(a, b)`** — the clause's own equivalence relation: the same type-name, the same
  presence or absence of the EXTERNAL clause and the STRONG phrase, and, for each elementary item in one
  declaration, a corresponding elementary item in the other at the same relative position and of the same
  length, each pair carrying the same ALIGNED / BLANK WHEN ZERO / DYNAMIC LENGTH / JUSTIFIED / PICTURE / SIGN /
  SYNCHRONIZED / USAGE clauses. It takes a declaration in EITHER form the model holds one — a TYPE-clause
  SUBJECT (whose subtree `ExpandType` cloned through the ONE `CopyEntryDescription`, PB522, so it IS the
  declaration) or a `TypeDecls` TEMPLATE (also fully expanded, because `ExpandTypes` walks the templates) —
  through one three-fact reader (`DeclaredTypeName` / `DeclaredStrong` / `DeclaredExternal`). Geometry comes
  from `BitLayout.StartBitWithin`, the ONE §8.5.1.6.3 cursor walk, so BITS express "the same relative byte or
  bit position" without a second geometry; the PICTURE/SIGN/USAGE conjunct is `PicInfo`'s own record equality,
  so a later analysis axis is covered by construction instead of by a hand-maintained member list.
- **`SameType(a, b)`** — the two alternatives. Whether an item IS its own `TypeAnchor` decides which applies:
  a TYPE-clause subject takes alternative 1 (equivalent declarations, nothing more), a subordinate item takes
  alternative 2 (equivalent declarations PLUS the same relative position and length). A MIXED pair is covered
  by neither and is not of the same type.

`RelativeMemberPath` is deleted. The class doc no longer paraphrases §8.5.3.1's informative NOTE as the rule;
it says outright that the NOTE is what licensed the path comparison.

**Both measured defects are closed, each re-probed on the built `cobol.exe` before and after.** (a) the
non-equivalent same-named pair printed `SB=[ABC] SC=[DEF]` into two `PIC 9(3)` items and is now COBOLNET1533;
(b) `MOVE OUTERG OF N1 TO INNERG OF N2` was rc=70 COBOLNET1533 and now runs, printing `LEAFX2=[WXYZ]`.

**The sibling sweep, and what it found.** Every rule in the standard that says two typed items are "of the same
type" now asks `SameType`:

- §14.9.25.3 SR2 — `StatementValidation.CheckStrongMove`, and through `MoveBinder` every implicit move.
- §8.8.4.2.3 SR1 + §8.8.4.2.12 — `StatementValidation.CheckRelationalOperands`, the ONE relation chokepoint.
- §14.8.2.2 / §14.8.3.2 / §9.3.8.2.3 rule 7 — **the sentence was implemented NOWHERE**, which this note did not
  know and the sweep measured: a plain `01 PLAING. 05 PA PIC X(4).` argument crossed BY REFERENCE into a
  `01 LF TYPE CT-T.` strongly-typed formal of the same width and the program RAN (`CA=[WXYZ]`). One
  `OoConformance.StrongTypeMismatch` now answers for all three, reached from BOTH `DescriptionMismatch` (BY
  REFERENCE, RETURNING, override and prototype signatures) and `ContentMismatch` (BY CONTENT / BY VALUE),
  because §14.8.2.2's sentence follows rules 1 and 2 and qualifies neither. It also completes §8.5.1.12.1's
  "Two fixed-length groups are always compatible, unless they are strongly typed and have different type
  definitions", whose strong half `VariableLengthCompatibility` deliberately leaves to its caller.
- The restricted data-pointer network (§14.9.39.3 SR19/SR20, §14.9.3.3 SR4/SR5, §14.8.2.3.2) compared type
  NAMES, so it inherited the same hole. A restriction now carries a `TypeRestriction` — the name AND the
  declaration it resolves to (`DataBinder.ResolveRestrictedTypes`, the tail of the ONE `ExpandTypes` pass,
  attaches it to `PicInfo.RestrictedTypeDecl`) — and `SameRestriction` compares names always and declarations
  whenever both sides resolved to one. The `asNested` scoping on `CallBinder`'s §14.8.2.3.2 screen is gone with
  the premise that put it there: it existed because the test could not see a separately-declared element's type,
  and now it can.

**The green test that pinned the wrong criterion** — `TypedefStrongTests.MoveDifferentSubgroupPosition_Rejected1533`
— keeps passing and now passes for the reason its docstring always claimed. Its two new companions are what
tell the criteria apart: `MoveSameOffsetDifferentlyNamedSubgroups_Accepted` (paths differ, positions agree →
legal) and `MoveSamePathDifferentPosition_Rejected1533` (paths agree, positions differ → refused, built from two
EQUIVALENT declarations whose grouping differs). `MoveEquivalentSameNamedDeclarationsAcrossElements_Accepted` is
the over-rejection guard, `MoveSameLayoutDifferentPicture_Rejected1533` isolates the PICTURE conjunct, and
`CallArgumentNotSameTypeAsStrongFormal_Rejected` pins §14.8.2.2.

**The paraphrase sweep this note asked for** (in-code paraphrases of a rule that quote a NOTE): the two the grep
found in this subsystem were both in `StrongTypeModel` itself — the `SameStrongType` class doc and
`SameRestriction`'s "cross-program EXTERNAL equivalence is deferred" — and both are rewritten to the normative
text. `DESIGN-data-model.md` sections 2.4 and 2.4.1 and `COBOLNET_DATA_MODEL_DESIGN.md` carried it too and are
corrected in the same change set.

**Goldens:** `conformance:2002/pb427_same_type_by_position` (both alternatives, the comparison arm, and a
cross-source-element equivalent pair crossing by MOVE and as a CALL argument) plus three negatives —
`pb427-same-type-nonequivalent-declarations`, `pb427-strong-group-argument-not-same-type`, and the edition floor
`pb427-same-type-below-2002`.

**What is NOT witnessed here, and why that is not a gap in this row.** §8.5.3.1's currency-symbol and
DECIMAL-POINT IS COMMA exceptions (rows `GR-8.5.3.1-1` / `GR-8.5.3.1-2`) are implemented — `PicInfo` is the
currency-canonicalized, decimal-point-resolved analysis, and `CurrencyString` is exception 1 exactly — but they
are not OBSERVABLE at compile time: §12.3.3 SR1 forbids a contained program its own CONFIGURATION SECTION
(measured: COBOLNET1643), so the two declarations any compile-time same-type test can reach always share one
CURRENCY SIGN and one DECIMAL-POINT setting. They separate only between separately compiled elements sharing an
EXTERNAL strongly-typed record, where §14.8.1 makes the conformance a RUNTIME check. Those two rows stay open
for the adjudication lane.
