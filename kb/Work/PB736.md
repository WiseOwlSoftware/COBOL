# PB736 — OPEN — a flake with a name

Found 2026-09-06 in the PB338 implementer's report, which named it rather than waving it away
(`feedback_gate_on_the_verdict_line`: no "flake" without a name):

> ⚠ **One extra red appeared in the FIRST pre-merge run and is named, not waved away.**
> `GrammarDiagramGeneratorDriftTests.Generator_RunsClean` failed in gate run 1 and passed in runs 2 and 3, and
> passes in isolation in 39 s. It shells out to `pwsh` + `java` (`tools/rr/rr.war`) over every `.g4` fragment
> under a 180 s WALL-CLOCK budget while a battery and a lander share this machine; my diff contains no `.g4`
> file.

The 39 s / three-run observation is **attributed to that report** and not re-measured here (re-running it would
add exactly the load that causes it). What follows is verified against main (`0db46983`).

## The test, in full

`tests/Cobol.Net.Tests.Unit/GrammarDiagramGeneratorDriftTests.cs:20-42`:

```csharp
var psi = new ProcessStartInfo("pwsh", $"-NoProfile -ExecutionPolicy Bypass -File \"{script}\" -Check") { … };
using var p = Process.Start(psi)!;
string stdout = p.StandardOutput.ReadToEnd();        // :35
string stderr = p.StandardError.ReadToEnd();         // :36
Assert.True(p.WaitForExit(180_000), "gen-grammar-diagrams.ps1 -Check timed out (>180s)");   // :37
Assert.True(p.ExitCode == 0, $"… exited {p.ExitCode}\nSTDOUT:\n{stdout}\nSTDERR:\n{stderr}");// :39-40
Assert.Contains("grammar-diagram note", stdout);     // :41
```

Three assertions, and they measure two different things. **:39 and :41 are the drift signal** — the generator
still cleans every fragment to valid EBNF and rr renders it, which is what the class doc says the test is for.
**:37 is a stopwatch**, and it is placed FIRST, so when the machine is loaded the run fails before either drift
assertion is evaluated and the failure message says nothing about the grammar.

What is being timed: `pwsh` starting cold, then — `scripts/gen-grammar-diagrams.ps1:21-23`, `:65-75` — **nine
separate `java -jar tools/rr/rr.war` forks**, one per parser fragment (`CobolWords`, `CobolExpressions`,
`CobolData`, `CobolSpecialNames`, `CobolControlFlow`, `CobolIO`, `CobolReportWriter`, `CobolScreen`, `CobolOO`),
each a JVM start plus a render of every rule in that fragment. Nine JVM starts is the single most
contention-sensitive thing any unit test in this repo does, and 180 s against a measured 39 s is a 4.6× headroom
that a battery plus a lander plus six implementers can eat.

## The precedent is inside the script it runs

`scripts/gen-grammar-diagrams.ps1:76-87` already met this exact failure one layer down and fixed it properly:

> ⛔ **READ WITH RETRY** — the java process has exited but its handle on `$mdFile` is not always released by the
> time PowerShell resumes … Under the comprehensive battery's parallel load that window widened enough to
> FALSE-RED the whole run … It passed on a serial re-run, which is exactly the shape §0 warns about — **and a
> gate that can false-red trains people to ignore reds, so this is hardened rather than documented.**

Same tool, same load, same conclusion — and the hardening stopped at the file handle. The wall clock one frame up
was never asked the same question.

## Why it is worth fixing rather than raising

Raising 180 s to 600 s is the smallest diff and the wrong one: it keeps a load-dependent quantity inside a
correctness assertion, so the test still cannot say what it means. `feedback_measure_the_selectors_complement`
in its process form — a red that can mean either "the grammar broke" or "the machine was busy" carries no
information either way, and the cost is not the rerun, it is that the NEXT real red in this test gets rerun
instead of read.

## The fix shape

Separate the two measurements, in the test:

1. **The drift assertion gets no deadline.** `p.WaitForExit()` (no argument), then `:39`/`:41` unchanged. A
   generator that genuinely hangs is caught by the test host's own per-collection timeout, which is the layer
   that owns "the run wedged".
2. **The budget becomes a reported perf guard, not a failure.** Measure the elapsed time and surface it —
   `ITestOutputHelper` — with a threshold that scales rather than a constant: `180 s × max(1,
   Environment.ProcessorCount / <baseline>)`, or a plain `Skip`-style soft signal. If a hard ceiling is wanted
   it belongs in the benchmark project (`tests/Cobol.Net.Benchmarks`), which exists for exactly this and is not
   in any gate.
3. **Kill the child on the way out.** Today `using var p` disposes the handle without terminating the process,
   so a timeout leaves an orphan `pwsh` (and up to nine `java`) running on the fleet machine — load that makes
   the NEXT run likelier to trip the same budget. Wrap the wait in a `try/finally` that calls
   `p.Kill(entireProcessTree: true)` when the process has not exited.

⚠ **A second, structural hazard in the same block, named as a hypothesis and NOT diagnosed here.** `:35-36` read
`stdout` to end and only then `stderr`, both synchronously, before `WaitForExit`. If the child ever fills the
stderr pipe buffer while the parent is blocked in the stdout `ReadToEnd`, the child blocks on write and the pair
deadlock until :37's budget expires — presenting exactly as a timeout. The script does write to stderr
(`Write-Error` at `:40`, `:67`, `:75`, `:159`) and `java` writes its own diagnostics there, so the path exists;
whether it has ever been taken is unmeasured. `feedback_a_remembered_pattern_is_a_hypothesis` — this matches the
symptom and is not the diagnosis. The fix is the same either way and costs nothing: read one stream
asynchronously (`OutputDataReceived` / `BeginOutputReadLine`) or use `ProcessStartInfo` with both reads on
separate tasks, which removes the hazard whether or not it was the cause.

## Sweep

`grep -rn "WaitForExit(" tests/` — every test that shells out under a constant millisecond budget has this
shape. The invariant worth stating once: **a unit test may assert on a child's exit code and output; a wall-clock
constant is a perf measurement and belongs where perf measurements are read, not inside a correctness gate.**
