# PB173

§13.18.29.4 GR1b makes a bit group an as-if elementary PICTURE 1(m) and §8.4.3.3 gives its ref-mod slice
boolean positions — but the resolver wraps EVERY group ref-mod in GroupImagePlace, whose Read/Write are the
PACKED byte image (`AsImage`/`FromImage`, ceil(m/8) characters), while `RefModPlace.Category` (OperandPic)
answers Boolean and the boolean channel's widths (Gr3Width/RefModLen) count BITS. The units disagree.

PB157's landing posture: the boolean-COMPUTE RECEIVER arm stages COBOLNET0899 (recognized-not-implemented —
legal source, loud, never a bit-into-byte splice), and the relation/COMPUTE SENDING classifications exclude
a ref-mod-of-bit-group so it keeps the byte-consistent GENERAL relation channel it always rode. PB157's
review fleet also measured: PlaceRenderer.Write's ref-mod boolean pad reads RAW Pic (a bit-group slice
would pad with SPACES where §14.6.8.6 wants boolean zeros), and the MOVE surface (MoveReceiverCategory →
rm.Category) has admitted the slice since PB70/PB79 — the same missing model, pre-existing.

WHAT WOULD CLOSE IT: a bit-position slice place for as-if-elementary groups (ref-mod over the UNPACKED bit
string, repack on write — the §8.4.3.3 unique data item), the §14.6.8.6 boolean pad keyed on OperandPic,
the 0899 stage and the channel exclusions removed, and goldens for `COMPUTE G(1:3) = …`, `MOVE B"11" TO
G(1:2)` and `IF G(1:3) = B"101"`.

*(Found by the PB157 pre-landing review fleet, 2026-08-29 — the geometry lens's blocker plus two refuter
measurements; full claims in the session scratchpad `pb157-fleet-confirmed.json`.)*

## Implementation record - 2026-08-31 (burn-down cluster A)

**PROBED FIRST - and the note UNDERSTATES the harm; all four legs were LIVE silent wrong answers, not one
deferral.** On `01 G GROUP-USAGE BIT. 05 GB1 PIC 1(4) VALUE B"1100". 05 GB2 PIC 1(4) VALUE B"1010".`
(`AsBits()` = `11001010`):

| leg | before | spec-derived |
|---|---|---|
| `IF G(1:3) = B"110"` | FALSE - the slice read the PACKED byte 0xCA ref-modded at BYTE offsets, space-padded | TRUE (8.4.3.3.4 GR5a - bit positions 1..3) |
| `MOVE B"11" TO G(1:2)` | `00110001` | `11001010` (positions 1-2 set, tail unchanged) |
| `MOVE B"1" TO G(1:3)` | no further change | zero fill to the right (14.6.8.6) |
| `MOVE ALL ZERO TO G(3:4)` | NO CHANGE AT ALL | boolean zeros at positions 3..6 |

The relation leg is the one the note calls "byte-consistent": that describes the CHANNEL, not the ANSWER.

**FIX - the model, not a guard.** New `BitImagePlace(Place Inner)` beside `GroupImagePlace`;
`ReferenceResolver` dispatches on `IsAsIfElementary && GroupUsage is Bit`; `PlaceRenderer` gains the paired
`Read` (`AsBits()`) and `Write` (`FromBits(...)`) arms. NO new runtime code - `GroupImageCodec.EmitBitMethods`
already emits that pair for every bit group. Because `RefModPlace` sits OVER the new place, its start/length
index the boolean string directly and GR5a is satisfied STRUCTURALLY.
A NATIONAL group deliberately KEEPS `GroupImagePlace`: 13.18.29.4 GR2b's as-if `PICTURE N(m)` is in NATIONAL
positions and `IsCharacterImage` guarantees a national leaf contributes `ImageWidth = Length` characters,
"never byte-doubled". The asymmetry is derived and written into the type's XML doc so the split is not
"simplified" back - two types because they carry two UNITS, which is GR5a's own two-branch sentence.

**BOTH ARMS OF THE PAD, asked explicitly.** `PlaceRenderer.Write`'s ref-mod boolean pad AND `MoveEmitter`'s
`RefModSlice` figurative fill both read raw `Pic` - null for any group - so a bit-group slice space-filled where
14.6.8.6 requires boolean zeros. Both now read `OperandPic`, the ONE category reader. D20's own
consumer-switch sweep list named `RefModPlace.Category` and OMITTED these two write-side sites; that omission is
the defect's origin, and the list now carries both rows.

**CONTAINMENT REMOVED (the model made it unnecessary).** Deleted: `ArithmeticBinder`'s 0899 stage, the
`DiagnosticCatalog.RefModBitGroupSlice` descriptor, and BOTH `ConditionBinder` exclusions. Deletion proof: no
`.err` in the corpus expected the code, so no green test was pinning the gap open; the descriptor carried the
shared 0899 code, so nothing is reallocated.

**PINS.** The golden gap closed in the file that recorded it - D20's "As built" paragraph listed ref-mod
read+write for `pb79_group_usage_national` and omitted it for `pb79_group_usage_bit`, so the legs go there:
read, exact-width store, the 14.6.8.6 SHORT-source pad, the 8.3.3.6.4 GR2 figurative fill (two legs for the
two arms), a 12-bit group whose slice spans the packed-byte boundary, a NESTED bit group, and the COMPUTE
receiver the containment used to stage. Every expected value derived from the spec and written before the
confirming run; all seven matched. Non-regression: `pb79_group_usage_national` is byte-identical, and the whole
940-case conformance corpus is green.

**FRONTMATTER.** `spec_refs` was `[]` on a note making four spec claims. Populated:
13.18.29.4, 8.4.3.3.3, 8.4.3.3.4, 14.6.8.6, 8.5.1.6.3.

## Open question carried forward - FUNCTION BYTE-LENGTH over a bit-group ref-mod

MEASURED after this landing, on the 8-bit `G` above:

    COMPUTE L = FUNCTION LENGTH(G).        -> 0008    (bit positions; consistent with 15.50.4 r1
                                                       and pb79_group_usage_bit's existing LEN=12 leg)
    COMPUTE L = FUNCTION LENGTH(G(1:3)).   -> 0003    (the slice's boolean positions - consistent
                                                       with 8.4.3.3.4 GR5a/GR6)
    COMPUTE L = FUNCTION BYTE-LENGTH(G(1:3)). -> 0003 <- SUSPICIOUS

Three BOOLEAN positions occupy ONE byte (ceil(3/8)), so a BYTE-LENGTH of 3 looks like the character-count
answer surviving into a bit-position world.

NOT ASSERTED AS A DEFECT, deliberately. 15.50 (LENGTH) and 15.14 (BYTE-LENGTH) were NOT derived for the
unique data item of 8.4.3.3.4 GR6, and asserting a verdict from the shape of the number would be exactly the
inherited-citation failure CLAUDE.md rule 1 forbids. It is also NOT a regression from this landing: the
ref-mod LENGTH operand is 3 in both the old character-image world and the new bit-position one, so the value
is unchanged - what changed is the basis it should be computed on.

NEXT STEP: derive 15.14 / 15.50 for a reference-modified bit item, cite the rules, then either fix or record
a determination. The intrinsics take their own path, so this did not block the substrate fix.

## Landing addendum — 2026-08-31, the cluster-A review-fleet fix pass

`status: open -> landed`. Five further arms of this family were found by the review fleet, PROBED, and fixed
in the same pass — every one a place where the BIT-position substrate and some other channel disagreed:

- **`AcceptDisplayEmitter`'s omitted-length ref-mod width** read raw `Pic` (the THIRD arm of the pad family,
  after `PlaceRenderer.Write`'s boolean pad and `MoveEmitter`'s figurative fill). `Pic` is null for a group,
  so the fallback was `ImageWidth` = ceil(m/8) PACKED characters: `ACCEPT XM(3:)` on an 8-bit group computed
  1 - 3 + 1 = -1 and `ACCEPT XM(1:)` computed 1 — undersized at EVERY start, not only past the packed width.
  Measured 11000000 / 10000000 against the 11101010 / 10101010 the explicit-length control gives.
- **`BitImagePlace` had no §13.18.38.4 GR8 current-extent arm on EITHER side**, and the character-unit ODO
  arithmetic was not merely absent but WRONG for sub-byte elements: `fixedChars = PhysicalWidth - elem*max`
  came out NEGATIVE (2 - 1*4 = -2), so the whole bit-group operand rendered as the EMPTY string. The extent is
  now counted in the group's OWN position unit (`OdoGroupPlace.PositionsPerCharacter`, 8 for a bit-bearing
  subtree), the prefix is the table's own placement offset (`BitLayout.StartBitOf`, never `total - elem*max`,
  which charges §8.5.1.6.3 rule 4's trailing filler to the prefix), and the CHARACTER channel takes the
  ceiling. Read and write both mirror the `GroupImagePlace` arm, and the bit arm's output now tracks the
  character twin's position for position.
- **`OperandText.FieldAsString`'s ODO early return stole every bit group with an occurs-depending table into
  the CHARACTER reader** — two alphabets on one operand. The bit test now precedes it and routes through
  `PlaceRenderer.SendingBits`, THE ONE bit reader; the `BoundaryImageChannelTests` allow-list row that
  promised "when [PB173] lands this row is the next one to route" is DELETED, not re-justified.
- **The CALL/INVOKE boundary carried a bit group's OPERAND value into a `FromImage` that reads its PACKED
  image** — silent argument corruption, PRE-EXISTING at 876d8ab0 (measured byte-identical there): 11001010
  crossed BY REFERENCE, arrived as 00110001 (the eight bits of the character '1') and came home as 00110000.
  §14.2.3 GR8 makes the formal occupy "the same storage area", so the carrier is the STORAGE image;
  `CallStringRead` now routes every group through `PlaceRenderer.GroupImage`, the exact mirror of the write
  half. Golden `pb173_bit_group_boundary`.
- **`OperandText.AsStorageImage`'s `RefModPlace` arm had no bit arm**, so `FUNCTION CONVERT(XM(1:3) ANY ANUM
  HEX)` returned 313130 — the '0'/'1' CHARACTERS — where §15.19.3 r7 + §15.19.4 r2 want the packed byte C0,
  and where the UNSLICED twin already returned CA. The ELEMENTARY `USAGE BIT` slice took the same arm and was
  wrong for the same reason (it predates this place entirely); one arm fixes both. A DISPLAY-form boolean
  slice is deliberately NOT packed (§13.18.60.4 GR7) and is pinned as the control.
- **`IntrinsicArgumentRules.StaticUsageOf` matched `IsGroup: false` + raw `Pic`**, so a bit GROUP had no
  static usage and slipped every keyword-keyed §15.19.3 screen: the `PIC 1(8) USAGE BIT` leaf was correctly
  rejected by r5 while the byte-identical group was ADMITTED. It reads `OperandPic` now — the same one-reader
  law, one more site.

⚠ Two REGRESSIONS this pass introduced and caught with its own twin-arm check, recorded because the transparency
rule requires it: widening `CallStringRead`'s group test to `p.Item.IsGroup` made a ref-modded GROUP argument
render `CobolStr.RefMod(...).AsImage()` — `RefModPlace.Item` forwards to the INNER item — turning HEAD's single
CS1061 into two. Both halves now carry an explicit `RefModPlace` arm (§8.4.3.3.4 GR6), which also FIXES the
pre-existing write-half half of that crash: `CALL "S" USING G(1:3)` now round-trips, pinned in the same golden.
