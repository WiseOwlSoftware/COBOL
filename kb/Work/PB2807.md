# PB2807 — no file-set partition between the fix lane and other sessions' dispatches

**Found by:** the loop's wave unit of 2026-10-08 16:24 PDT, while fixing PB2806 (the note-level hold).

**Repro:** with wave 1045 (Mythos, recorded, not launched) in `E:\COBOL-coord\inflight-groups.json`, run
`python scripts/orchestrator/plan_wave.py --from-budget --borrow-days 3 --dry-run` on the PB2806 branch: group C
(PB2101, PB2741, PB2745) has primary file `src/Cobol.Net.Runtime/Control/ProgramTable.cs`, the file wave 1045 B holds
for PB2097. The notes differ, so PB2806's hold does not apply.

**Code site:** `scripts/orchestrator/plan_wave.py#main`, the `if a.cluster:` block that builds `busy` from
`inflight_file_sets` for a campaign only; `plan()` applies `file_set_collisions(g.files, busy)` only when `busy` is
passed.

**Why it is a separate decision:** the design (section 9.1, DESIGN-architecture-review section 8.7) makes the file-set
partition the gate between a CAMPAIGN and the fix lane's trains, and the landing check the guarantee for everything
else. Within the loop, fix-lane waves are serial and same-file groups become successors, so the case never arose. With
two planners it costs a re-plan at landing (the later landing stops). Options: pass `busy` restricted to ledger
groups of OTHER waves (not worktrees, which would defer every group touching a WAITING TO LAND branch's files), or
make a same-file group a successor of the other session's group. Decide with the operator lane design
(project_two_sessions_2026-10-07).

**Premise corrected (2026-10-15, the Mythos session's decision 2, wave 1083 group B).** "Only the landing check catches
it" was wrong: `landing_check.py` stops only an overlap where one side is R3 work (cluster PB2119); fix lane against
fix lane passes it by design, and the merge queue merges the two. The real cost of a fix-lane/fix-lane overlap is a
conflict at the second branch's merge of main: a conflict finisher (MANDATORY-PRACTICES L12) after both groups spent
their implementer and gate. The exit-3 holds of the fix lane on 2026-10-14/15 (23 stops over six branches in
`E:/COBOL-coord/logs/land-lane-*.log`, "PB1682, PB1698, PB1699, PB1701 work by its dispatch ledger") were NOT this
defect: they were the ledger's scraped hand entries and the landing check's union binding, kb/Work PB3186.

**Re-probe (2026-10-15 13:40, main f5fec711b + group A).** `plan_wave.py --budget-points 40 --dry-run` planned group E,
PB3168, on `src/Cobol.Net.Frontend/Preprocessor/ReferenceFormatProcessor.LogicalLineBuilder.cs`, the primary file of
the loop's running wave 1084 group H (PB1804, no report yet): `file_set_collisions` against
`inflight_file_sets` names `dispatched w1084H (PB1804)`, and the planner never asked (`busy` was built `if a.cluster:`
only). Reproduced.

**Decision (Mythos, 2026-10-15; implemented by wave 1083 group B).** ONE rule for both planners: `plan_wave.py` builds
the in-flight set for EVERY plan and reads each owner through the branch survey's lifecycle state
(`classify_inflight`). A group whose files meet FINISHED work (WAITING FOR REVIEW, WAITING TO LAND, ENQUEUED) is
planned as its CONTINUATION (`continuation_pred`: merge that branch first, no `after:`); a group whose files meet
RUNNING work (a ledger group with no report yet; a branch IN FLIGHT, STOPPED, BOUNCED or DECISION) waits, the
collision and the owner's state named. A group's own work never collides (the branch its pred continues, a dispatch or
branch on its own notes). There is no train: the old "the partition defers the wave, never the train" wording is gone.
