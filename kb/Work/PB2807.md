# PB2807 — no file-set partition between the fix lane and other sessions' dispatches

**Found by:** the loop's wave unit of 2026-10-08 16:24 PDT, while fixing PB2806 (the note-level hold).

**Repro:** with wave 1045 (Mythos, recorded, not launched) in `E:\COBOL-coord\inflight-groups.json`, run
`python scripts/orchestrator/plan_wave.py --from-budget --borrow-days 3 --dry-run` on the PB2806 branch: group C
(PB2101, PB2741, PB2745) has primary file `src/Cobol.Net.Runtime/Control/ProgramTable.cs`, the file wave 1045 B holds
for PB2097. The notes differ, so PB2806's hold does not apply.

**Code site:** `scripts/orchestrator/plan_wave.py#main`, the `if a.cluster:` block that builds `busy` from
`inflight_file_sets` for a campaign only; `plan()` applies `file_set_collisions(g.files, busy)` only when `busy` is
passed.

**Why it is a separate decision:** the design (section 9.1, DESIGN-architecture-review section 8.7) makes the file-set
partition the gate between a CAMPAIGN and the fix lane's trains, and the landing check the guarantee for everything
else. Within the loop, fix-lane waves are serial and same-file groups become successors, so the case never arose. With
two planners it costs a re-plan at landing (the later landing stops). Options: pass `busy` restricted to ledger
groups of OTHER waves (not worktrees, which would defer every group touching a WAITING TO LAND branch's files), or
make a same-file group a successor of the other session's group. Decide with the operator lane design
(project_two_sessions_2026-10-07).
