# PB517

## Mechanism — data-description-entry-p1
A level-88 entry with NO condition-name and an ordinary (non content-validation) VALUE clause matches neither Format 3 (where condition-name-1 is required) nor Format 4 (whose value-clause is the 13.18.63 format-5 content-validation form). The grammar's `dataName?` admits it and DataBinder.BindCondition returns early on an unnamed level-88, so the entry is accepted and silently dropped.

### Expected, from the standard
13.16.2 Format 3 is `88 condition-name-1 value-clause .` -- condition-name-1 is not bracketed, so it is required. Format 4 is `88 [ condition-name-2 ] value-clause .` where the value-clause is 13.18.63 format 5 (content-validation-entry), i.e. it must carry the `{ INVALID | VALID }` tail. `88 VALUE 'xxx'.` is neither, and shall be a syntax error.

(the finding quotes no rule sentence verbatim, so there is nothing to --check; the implementer MUST quote §13.16.2 and re-run `cite.py --check` before writing a code comment)

### Observed
Accepted, and the entry vanishes: nothing is registered, so the program compiles as though the line were absent. The neighbouring Format-4 shapes that DO carry the format-5 tail are handled correctly -- `88 VALUE 9 IS INVALID WHEN A = 1.` and `88 GOODV VALUES 1 THRU 5 IS VALID.` are refused by name (COBOLNET1708, goldens conformance:negative/declined-validate-value-format5-anon and -value-format5), so the declined-facility pass sees the anonymous shape but the ORDINARY anonymous 88 falls between the two formats. A missing condition-name in a Format-3 entry is a plausible typo, and silently discarding the condition means every later `IF <name>` fails to resolve or, worse, resolves to a same-named condition elsewhere.
