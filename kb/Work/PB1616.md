Filed 2026-09-26 by the **train-62 lander** from the w61g implementer report (PB1393), lead 2.

## Observation (reported, not re-probed by the lander)
PB1393 put a literal's own §8.3.3 syntax rules (length ≤ 8,191 positions of its class, COBOLNET0814; hexadecimal
grouping, §8.3.3.2.3 SR6 / §8.3.3.5.3 SR5, COBOLNET1635) on every literal TOKEN of the unit's parse tree
(`src/Cobol.Net.Compiler/Validation/LiteralScreenPass.cs`). Literals in a compiler-directive expression
(`>>IF X = "…"`, `>>DEFINE … AS "…"`) are parsed by `DirectiveExpressionFragment`
(`src/Cobol.Net.Frontend/Parsing/DirectiveExpressionFragment.cs:39`) from preprocessor text. That tree is never
walked by the screen, so `>>DEFINE D AS X"414"` or an 8,192-position literal there is accepted.

## Fix direction
The root is the same as PB1393's: one screen per literal token. The directive fragment should ask the same
`CobolLiteral.LengthViolation` / `HexGroupViolation` pair, from its own token stream, reporting through the
preprocessor's diagnostic sink. Do not add a second statement of the rules. Repro: `>>DEFINE D AS X"414"` followed
by `>>IF D = X"41"`. Expected: COBOLNET1635. Actual: compiles clean.
