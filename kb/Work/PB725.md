# PB725 — LANDED — a partially-swept family: three of the six 2023 directives got a gate, three got a HashSet entry

Found by the [[PB688]] implementer (report §N3) while reading the 2023 Foreword; re-measured on main
(`0db46983`) before filing, with the sibling-directive control the report did not run.

## The facts

**What the standard says.** All three are COBOL-2023 additions, and this is mechanically citable in the numbered
annexes — not only in the un-citable Foreword:

- `cite.py --check E.3.3 "PUSH"` → **OK §E.3.3 38)** — *"**PUSH and POP directives.** The PUSH and POP directives
  are added to allow saving and restoration of the state of compiler directives."*
- `cite.py --check E.3.3 "DISPLAY directive"` → **OK §E.3.3 16)** — *"**The DISPLAY directive.** The DISPLAY
  directive allows the display of compile-time information during the compilation of COBOL source."*
- `cite.py --check E.2 "compiler directive words"` → **OK §E.2 5)** — the reservation half; its list is
  COBOL-WORDS · DISPLAY · FLAG-14 · I-O-STATUS-04 · NUM-ED-ZERO-FIG-CONSTANT · POP · PUSH · REF-MOD-ZERO-LENGTH ·
  UPON (`specs/ISO_COBOL.md:42913-42924`).
- The clauses themselves: `--check 7.3.20 "POP directive"` → **OK §7.3.20**, `--check 7.3.22 "PUSH directive"` →
  **OK §7.3.22**, `--check 7.3.12 "DISPLAY"` → **OK §7.3.12**. ⛔ Note the pairing: **§7.3.20 is POP and §7.3.22
  is PUSH**, the reverse of the order the code comment lists them in.

`docs/VERSION_CHANGE_REFERENCE.md` already says the same and already says the gate is not built: row 59 (*DISPLAY
directive · E.3.3 item 16 · 2014→2023 · new-feature-gate `<!-- todo -->`*) and row 81 (*PUSH and POP directives ·
E.3.3 item 38 · 2014→2023 · new-feature-gate `<!-- todo -->`*). A `<!-- todo -->` in a reference doc is not a work
register (CLAUDE.md rule 8) and nothing reads it, which is why the gap survived to a Foreword read.

**What the compiler does, measured.** Fixed-form probes with the directive at **column 8**
(`reference_fixed_form_directive_column8`), compiler on main, sources in `…/scratchpad/reg14/`:

| probe | directive | `--std 85` |
|---|---|---|
| `push85.cob` | `>>PUSH ALL` + `>>DISPLAY "HI"` + `>>POP ALL` | **clean, no diagnostic** (also clean at 2002 and 2023) |
| `d_rmzl.cob` | `>>REF-MOD-ZERO-LENGTH ON` | `COBOLNET0900: >>REF-MOD-ZERO-LENGTH directive requires COBOL-2023 (targeting COBOL-85)` |
| `d_cw.cob` | `>>COBOL-WORDS RESERVE "ZQX"` | `COBOLNET0900: >>COBOL-WORDS directive requires COBOL-2023 (targeting COBOL-85)` |

The control is the point: **the same Annex E.2 item 5 list, three words gated and three not.** This is
`feedback_scan_all_similar` failing on a family that was half-swept, and the reason it half-swept is structural.

**The mechanism.** `src/Cobol.Net.Frontend/Preprocessor/ConditionalCompilationProcessor.cs:40-51`:

```csharp
private static readonly HashSet<string> KnownIgnoredDirectives = new(StringComparer.OrdinalIgnoreCase)
{
    "CALL-CONVENTION", "LISTING", "PAGE", "LEAP-SECOND", "PROPAGATE",
    "FLAG-85", "FLAG-NATIVE-ARITHMETIC", "REF-MOD-ZERO-LENGTH", "TURN", "COBOL-WORDS",
    "PUSH", "POP",   // §7.3.20/§7.3.22 …
    "DISPLAY",       // §7.3.12 …
    "FLAG-02", "FLAG-14",   // …
};
```

A flat set of NAMES with **no edition column**. Membership means "consume it so it does not stray-token", nothing
more. The three gated siblings are gated somewhere else entirely — each has its own downstream processor that
calls the ConstructRegistry (`CobolWordsDirectiveProcessor.cs:58`, `RefModZeroLengthDirectiveProcessor.cs:54`,
`FlagDirectiveProcessor.cs:50`, `LeapSecondDirectiveProcessor.cs:50`), reached because the directive's name is in
the caller's `leaveDirectives` set. A directive with no downstream stage is consumed here and never meets an
edition. The `Run` already carries `_dialectLevel` (`:115`, `:122`) and already uses it for one rule
(`CobolWordRule.LengthViolation`, `:365`), so the plumbing exists and only the shape is missing.

## Why it matters

A user compiling with `--std 85` is asking to be told when the source is not COBOL-85. `>>PUSH ALL` is not
COBOL-85 by any reading — unlike the [[PB724]] case there is no alternative legal interpretation of a `>>` line at
an edition that has no compiler directives at all — so silence is a straight under-rejection of the four-editions
promise (`feedback_four_editions_one_compiler`). It is MINOR only because the directives are no-ops today: the
program still compiles to the same code. It becomes worse the moment `>>PUSH`/`>>POP` acquire real behaviour,
because then an 85 build and a 2023 build of the same source diverge with no diagnostic in either.

Second, smaller observation, recorded and NOT claimed: `>>DISPLAY "HI"` prints nothing at any edition. §7.3.12
says the directive *"transfers data to the source listing or an implementor defined compile-time-device"* and the
code's disposition — no listing is produced, so consume it — is defensible under §7.3.12's "the implementor
defines the stage of processing"; it is named here so the next reader does not mistake it for a second defect
without deriving it.

## The fix shape

⛔ **Do not add three names to a longer flat list.** CLAUDE.md rule 5 — the shape that makes the NEXT case
automatic. `KnownIgnoredDirectives` should stop being a set of strings and become a table keyed by directive name
carrying the **`constructs.json` row id** (or an explicit "no gate: predates 2002" marker) for each recognized
directive, with the consume path calling `ConstructRegistry.Check` exactly the way the four downstream processors
already do. Then a 2023 directive cannot be added to the recognized set without either a row or a written
exemption, and COBOLNET0900 comes out of the one producer that already emits it for the gated three.

Ships with: three `constructs.json` rows (`push-directive-2023`, `pop-directive-2023`, `display-directive-2023`,
`introducedIn: 2023`, `diagnosticCode: COBOLNET0900`, citations §7.3.22 / §7.3.20 / §7.3.12 + §E.3.3 items 38/16 +
§E.2 item 5), the regenerated `ConstructRegistry.g.cs` / `Constructs.g.cs`, three negatives under
`tests/conformance/negative/` carrying `*> reject-at: 85 2002 2014` first lines, and a positive at 2023 for each.
⛔ And the edition-gate sweep (`feedback_edition_gate_sweep`): every existing golden and NIST program that writes
one of these directives below 2023 must move or be split, the way train 14 had to split `pb352_start_sequential`.

## Sweep

Measured on main at the same time, all clean at `--std 85` and therefore in the same family, listed so the fixer
does not stop at three:

- `>>LISTING ON` (§7.3.18), `>>PAGE` (§7.3.19), `>>DEFINE X AS 1` (§7.3.11) — all accepted at `--std 85` with no
  diagnostic. These are **not** 2023 additions, so their correct gate is the 2002 one (the `>>` directive facility
  itself). Deriving that edition is the fixer's first step and it is NOT derivable from Annex E of the 2023
  standard — `docs/VERSION_CHANGE_REFERENCE.md` is the project's source for pre-2023 introductions.
- The remaining consumed-here names with no downstream stage: `CALL-CONVENTION` (§7.3.9), `PROPAGATE` (§7.3.21),
  `FLAG-85`, `FLAG-NATIVE-ARITHMETIC` (the last two are not §7.3 directives at all — non-ISO names in an ISO set,
  worth a separate look).
- The three §E.2 item 5 words that are **not** standalone directives — `I-O-STATUS-04` and
  `NUM-ED-ZERO-FIG-CONSTANT` are FLAG-14 options (`FlagDirective.cs:81`, `:14`) and `UPON` is §7.3.12's own
  required word (rendered format, folio for §7.3.12) — so the nine-word list maps to six directives plus three
  phrase words, and a roster check must not expect nine rows.

## Landed — 2026-09-06

**The defect reproduced exactly, and was FOUR TIMES BIGGER than this note measured.** The note's control ran
three directives; running every `>>` word the compiler recognizes, at all four editions, found ELEVEN ISO §7.3
directives silently accepted at `--std 85` — an edition that has no compiler directives at all: `>>CALL-CONVENTION`
(§7.3.9), `>>DEFINE` (§7.3.11), `>>DISPLAY` (§7.3.12), `>>EVALUATE`/`>>WHEN`/`>>END-EVALUATE` (§7.3.13),
`>>IF`/`>>ELSE`/`>>END-IF` (§7.3.16), `>>LISTING` (§7.3.18), `>>PAGE` (§7.3.19), `>>POP` (§7.3.20), `>>PUSH`
(§7.3.22), `>>SOURCE FORMAT` (§7.3.24), plus `>>FLAG-85` and `>>FLAG-NATIVE-ARITHMETIC` at every edition.

**The root cause was one rule written down in THREE places, not one HashSet.** "A compiler directive is rejected
below its introducing edition" was implemented by (1) `ConstructRegistry.Check` + COBOLNET0900, in five
downstream stages; (2) a hand-rolled `if (dialectLevel < 2002)` with a BESPOKE code, in two more
(`>>TURN` → COBOLNET0875, `>>PROPAGATE` → COBOLNET0883); and (3) nothing at all, for the flat
`KnownIgnoredDirectives` name set and the conditional-compilation switch's own arms. A name set cannot be wrong
about an edition it does not record, which is why the family half-swept and why nothing could have failed.

**The fix is the shape that makes the next directive automatic** (CLAUDE.md rule 5). `constructs.json` rows gained
a `directiveWords` column; `CompilerDirectiveCatalog` (`src/Cobol.Net.Editions/`) inverts it into the word → row
map; `ConditionalCompilationProcessor` calls it ONCE, at the single point a `>>WORD` is recognized (ISO §7.3.2's
one general format, §7.3.3 SR6's one compiler-directive word), and every per-stage gate was DELETED — which also
deleted four byte-identical private `BagSink` copies and the `dialectLevel`/`permissive` parameters of four
stages, none of which needs an edition any more. `>>SOURCE FORMAT` is the one exception, gated in
`ReferenceFormatProcessor` because that stage consumes the line before the driver can see it; same row, same
producer, one stage earlier. Adding a directive is now ONE constructs.json row plus a regen.

**14 new rows.** The twelve §7.3 directives that had none, plus `flag-85-directive-window` and
`flag-native-arithmetic-directive-window` — which are NOT the non-ISO oddities this note guessed: Annex E.2 item
21 records them as removed in 2023 and, by its own "classified as obsolete in the previous COBOL standard",
obsolete at 2014, so they are availability WINDOWS (COBOLNET0900 below 2002, COBOLNET0903 at 2014, COBOLNET0902 at
2023) and they close VCR row 28's two open legs. Their OPERAND syntax is not derivable in-repo — the 2023 text
removed the clauses — so the rows gate the WORD, which is what the removal record supports, and say so.

**The pre-2023 edition edge is DERIVED and the derivation is written into every row** (VCR Table 7 rows 7.19/7.20
discipline; new row 7.21 narrates it): the M2 post-85 feature catalog in `docs/ISO2023_CONFORMANCE_PLAN.md` places
the whole `>>` facility in COBOL-2002, `leap-second-directive-2002` already landed on that derivation (PB65), and
Annex E lists none of them among the 2014→2023 additions. The 2002-vs-2014 split WITHIN that bucket is not
separately derivable and is flagged rather than invented.

**Retired: COBOLNET0875** (`>>TURN`'s bespoke introduction gate) — never reallocate. **Narrowed: COBOLNET0883**,
which now owns only `>>PROPAGATE`'s malformed-operand rule (§7.3.21.2).

**The drift test is spec-derived, not a list.** `CompilerDirectiveCatalogDriftTests` re-derives the roster from
the `#### 7.3.N <WORD> directive` headings of `specs/ISO_COBOL.md`, checks each row cites its own clause (the
PUSH/POP pairing this note warned about is now a test, not a reading), asserts `Frontend.LeftDirectives ⊆` the
catalog, and DRIVES the real text-manipulation stage to prove every recognized word is rejected at 85.

**Sibling arms swept and reported:** the recognized-and-ignored set, the implemented directives, the two
hand-rolled gates, `>>SOURCE FORMAT` in the earlier stage, the unrecognized-word arm (`>>IFF` still survives for
the parser — asserted), and the fixed-form column-8 rule (every golden writes its directives at column 8).

**Not claimed, and still true:** `>>DISPLAY` prints nothing at any edition. §7.3.12.1 sends it "to the source
listing or an implementor defined compile-time-device", not to the run unit's display device, and this
implementation produces no listing and defines no such device; the 2023 golden asserts the ABSENCE deliberately.
§7.3.20.4 GR2's unsuccessful-POP warning is likewise unbuilt residue, recorded on the `pop-directive-2023` row.

[[PB595]] (the `>>TURN`/`>>PUSH`/`>>POP` Format-3 PERFORM containment question, owner decision D20) is untouched
and still open; it now has one gate site to work against instead of three.
