# PB1914 — LANDED (wave 1034 group E)

## Landing

LEARNED: `Preprocessor/ReferenceFormatProcessor.LogicalLineBuilder.cs#EmitDebugging` owns how a `D` line enters the
logical lines (reads it like a source line, so REUSE `Scan`/`NewLine`'s shape for any new line kind; the old
`Emit(string,int)` forgot the literal state). The trap: GnuCOBOL under WSL (`cobc -x -std=cobol85`, with and without
`-fdebugging-line`) settled the rule faster than any reading; the decision between "debugging line is the join target"
and "comment" cannot be made in this walk (the clause is read later), so the builder keeps the debugging line's own
continuation and passes it over only when the line before needs its continuation.

Re-probed on the wave-1034 build (`dc_off.cob`: a literal running to margin R, a `D` line, a `-` continuation, no
WITH DEBUGGING MODE): COBOL0001 `unexpected '"'`, as filed. **Two defects, one root** — the builder's treatment of a `D`
line as an ordinary new logical line with an EMPTY literal state (`Emit(carrier + text)` -> `LiteralState.Outside`):
(1) a `D` line between the parts of a continued literal took the continuation, cutting the literal; (2) a `D` line that
itself opens a continued literal lost the literal (its continuation was appended as loose text — `D    DISPLAY "CCC…` /
`-    "DD".` gave COBOLNET2633 even under WITH DEBUGGING MODE). **Rule (rule 1 precedence: ISO 2023 has no `D` indicator,
the 1985 text is not in the repository, then GnuCOBOL — verified with cobc 3.2.0 under WSL):** without
`-fdebugging-line` GnuCOBOL reads the `D` line as a comment, so the literal joins (`AAAA…TAIL`); with it GnuCOBOL
rejects the program ("continuation character expected"). `LogicalLineBuilder.EmitDebugging` reads the line like a source
line (literal state tracked), discards a blank one, and passes a `D` line over like a comment while the latest logical
line needs its continuation (an open literal, or a floating indicator's) — it keeps a logical line of its own after the
joined one. The WITH DEBUGGING MODE reading of that non-conforming shape is the same join (the clause is read after this
walk), recorded in docs/CONFORMANCE.md D-DEBUG. Witnesses: `conformance:85/pb1914_debugging_line_between_literal_parts`,
`conformance:85/pb1914_debugging_line_continued_under_clause` (no negative below 85: the `D` indicator exists from 85),
`unit:LogicalLineBuilderTests.DebuggingLine_*`.

Filed by the train-1003 lander from wave 1003 group D's report (`w1003d-PB1660-report.md`, new defect 2).

## Finding

**Repro.** At `--std 85`, fixed form: a source line opens a nonnumeric literal that runs to margin R, the next line is
a `D` debugging line, and the line after it is a continuation line (indicator `-`) carrying the rest of the literal.
The continuation joins the DEBUGGING line, not the line that opened the literal, so the literal ends at margin R of the
first line and the debugging line's text gains the tail.

**Code site.** `src/Cobol.Net.Frontend/Preprocessor/ReferenceFormatProcessor.LogicalLineBuilder.cs#Emit`, reached from
`FixedFormConverter.ConvertLine` in `ReferenceFormatProcessor.LogicalConversion.cs` (the `LineKind.Debugging` arm emits
`DebugLineCarrier + area` as a new logical line, which the next continuation line then extends). The behavior predates
PB1705; PB1705 only made the carried line source under WITH DEBUGGING MODE.

**Open question.** ISO §6.5 joins a continuation line to the preceding line, and 2002+ has no debugging indicator
(§6.2.2). Whether the 1985 standard lets a debugging line interrupt a continuation (and if so, which line the
continuation continues) needs the X3.23-1985 text, which is not in the repository. The fixer derives the rule from that
text or from GnuCOBOL (CLAUDE.md rule 1 precedence) before changing the builder, and records the choice in
docs/CONFORMANCE.md.
