### [operations-on-dynamic-capacity-tables] CobolDynTable.FromCurrentImage recreates a dynamic receiving table through SetCapacity, whose minimum clamp keeps stale occurrences instead of creating space-filled ones up to the FROM minimum
- **Rows:** GR-14.6.9.2-2 — harm `wrong-answer`
- **Repro:** 01 GS. 05 SH PIC X(2) VALUE "HH". 05 ST PIC X(3) OCCURS DYNAMIC CAPACITY IN CA FROM 1.  01 GM. 05 MH PIC X(2). 05 MT PIC X(3) OCCURS DYNAMIC CAPACITY IN CM FROM 3.  MOVE "AAA" TO ST(1). MOVE "OL1" TO MT(1). MOVE "OL2" TO MT(2). MOVE "OL3" TO MT(3). SET CA TO 1. MOVE GS TO GM. DISPLAY CM "[" MT(1) "][" MT(2) "][" MT(3) "]". (out/probe/dyncap/p1.cob, line B=)
- **Expected (spec):** CM=3, [AAA][   ][   ] - §14.6.9.2: the receiving table is recreated as a copy of the 1-element sender, then "further elements are created and filled with spaces until the current capacity of the table is equal to its minimum capacity".
- **Observed:** Observed B=  3[AAA][OL2][OL3] under --std 2014 and 2023. FromCurrentImage: SetCapacity(parts.Length) -> shrink arm `_count = n < _min ? _min : n` leaves occurrences 2..3 untouched; the store loop runs only for i < parts.Length. Same result when the receiver's prior capacity exceeds the minimum (shrink to _min, stale tail). Sibling risk: FromCurrentImage also serves the CALL-boundary write-back (CallAbi) and the READ decomposition (FromContiguous) paths.
- **Code site:** src/Cobol.Net.Runtime/Values/Tables/CobolDynTable.cs#FromCurrentImage (SetCapacity shrink/min clamp)

### [operations-on-dynamic-capacity-tables] GR9 variable-length group MOVE transfers corresponding table elements as character images instead of by elementary MOVE rules
- **Rows:** GR-14.6.9.2-2 — harm `wrong-answer`
- **Repro:** 01 GS. 05 SH PIC X(2) VALUE "HH". 05 ST PIC 9(4) OCCURS DYNAMIC CAPACITY IN CA FROM 2.  01 GR. 05 QH PIC X(2). 05 RT PIC 99V99 OCCURS DYNAMIC CAPACITY IN CR FROM 1.  01 FR. 05 FH PIC X(2). 05 FT PIC 99V99 OCCURS 2 TIMES.  MOVE 1234 TO ST(1). MOVE 5678 TO ST(2). MOVE GS TO GR. DISPLAY RT(1) RT(2). MOVE GS TO FR. DISPLAY FT(1) FT(2). (out/probe/dyncap/p2.cob)
- **Expected (spec):** §14.6.9.2: "Correspondingly numbered elements are moved according to the rules of the MOVE statement" - MOVE 1234 to a 99V99 item aligns on the decimal point (§14.9.25.4) giving 34.00, displayed 3400 (5678 -> 78.00, 7800); alternatively, if equal-byte-length elementary elements of different category/scale are not compatible under §8.5.1.12.3, SR9 must reject the MOVE at compile time.
- **Observed:** Compiles clean and displays E=[1234][5678] and F=[1234][5678] (values 12.34/56.78): VariableLengthCompatibility treats any equal-byte-length elementary element pair as compatible, and the runtime carrier (CobolVarGroup Dynamic strings -> FromCurrentImage store / ToFixedImage Store) copies element bytes. Wrong under either reading of element compatibility; the fix is element-wise MOVE for elementary elements (or a narrower compatibility rule plus diagnostic, documented in CONFORMANCE.md).
- **Code site:** src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs#VariableLengthGroupMove; src/Cobol.Net.Runtime/Values/CobolVarGroup.cs#ToFixedImage; src/Cobol.Net.Runtime/Values/Tables/CobolDynTable.cs#FromCurrentImage; src/Cobol.Net.Compiler/Binding/Model/VariableLengthCompatibility.cs#Elements

## What the fixer owes
FromCurrentImage creates fresh space-filled occurrences up to the minimum (not SetCapacity's clamp); MoveEmitter.VariableLengthGroupMove moves element-by-element with the elementary MOVE rules when the tables' elements are elementary. Goldens for both legs.

### Finding — `dynamic-capacity-tables` (silent; rows `GR-8.5.1.9.6-1`)

**Mechanism.** Implicit capacity change by a variable-length-group MOVE (or any FromVarImage receipt) is routed through the explicit-SET primitive SetCapacity, which raises EC-BOUND-SET (gated only on SET nodes) instead of EC-BOUND-OVERFLOW, so the overflow is never reported and GR1's implicit 'already exceeded' exemption is not applied

**Repro.** >>TURN EC-BOUND-OVERFLOW CHECKING ON (and EC-BOUND-SET ON); 01 S. 05 SE PIC 9(3) OCCURS DYNAMIC CAPACITY IN SC. 01 R. 05 RE PIC 9(3) OCCURS DYNAMIC CAPACITY IN RC FROM 1 TO 4. MOVE 7 TO SE (6). SET LAST EXCEPTION TO OFF. MOVE S TO R. DISPLAY "M1=" FUNCTION EXCEPTION-STATUS. DISPLAY RC. (out/probe/dct/p2.cob, --std 2023)

**Expected from the spec.** M1=EC-BOUND-OVERFLOW (padded), RC=0000000006: the MOVE 'recreates or overwrites the receiving table with a copy of the sending table' (14.6.9.2) taking R from capacity 1 to 6 past its expected capacity 4, and 8.5.1.9.6 1) makes EC-BOUND-OVERFLOW exist when 'an operation causes this expected capacity to be exceeded'. A second such MOVE while R is already past 4 is an implicit change after the expected capacity was exceeded, so no exception.

**Observed / reasoning.** Observed M1 blank, RC=0000000006 (the recreation happens; no condition). Generated code: R.FromVarImage(S.AsVarImage()) -> GroupImageCodec DynTable arm -> CobolDynTable.FromCurrentImage -> SetCapacity(parts.Length) -> ExceptionState.BoundSetError (EC-BOUND-SET, 14.9.39.4 GR30), whose checking flag EcBinder binds only on a SET Format 14 node (SetCapacityNames), so inside the MOVE's ambient EC-BOUND-OVERFLOW gate nothing records. The same FromCurrentImage path serves every variable-length-group receipt (READ INTO / activation-boundary copy-back per its PB204 comment), so all of them are silent. Fix shape: FromCurrentImage must be an IMPLICIT change - raise EC-BOUND-OVERFLOW with the first-crossing guard, never EC-BOUND-SET - one implicit-growth raise shared with RefReceiving.

**Code site.** src/Cobol.Net.Runtime/Values/Tables/CobolDynTable.cs#FromCurrentImage; src/Cobol.Net.Runtime/Values/Tables/CobolDynTable.cs#SetCapacity; src/Cobol.Net.Compiler/CodeGen/DataDivision/GroupImageCodec.cs#FromVarImage
