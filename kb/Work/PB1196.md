## Refuter evidence — row `GR-14.7.4.3-2` (PARTIAL)

PARTIAL — Implied TRUNCATION holds for fixed-point receivers only. A floating-point resultant identifier with no ROUNDED phrase gets IEEE round-to-nearest, not truncation: 0.1 into FLOAT-BINARY-32 stores 0.10000000149 (farther from zero than 0.1). FLOAT-RECEIVER HOLE (probes probe/refute-rp/p4.cob, p5.cob, p6.cob, pinned cobol.exe --std 2023): a floating-point resultant identifier (USAGE FLOAT-BINARY-32 / COMP-1 / COMP-2 / FLOAT-LONG) IGNORES the rounding mode entirely - every mode lands the IEEE round-to-nearest-even conversion. Measured: COMPUTE F1 = 0.1 (implied TRUNCATION) -> 0.10000000149 (farther from zero); ROUNDED MODE IS TOWARD-LESSER = 0.1 -> 0.10000000149 (larger than the value); TOWARD-GREATER = 0.7 -> 0.69999998808 (smaller); AWAY-FROM-ZERO = 0.7 -> 0.69999998808 (nearer zero); NEAREST-AWAY-FROM-ZERO = 16777217 (exact tie between 16777216 and 16777218) -> 16777216 (the nearer-to-zero tie); bare ROUNDED 16777217 -> 16777216; NEAREST-TOWARD-ZERO = 16777219 -> 16777220 (the farther tie); PROHIBITED = 16777217 ON SIZE ERROR -> NOT ON SIZE ERROR taken and 16777216 stored; COMPUTE D1 ROUNDED MODE TOWARD-GREATER = 1/3 equals the TOWARD-LESSER result. §14.7.4.3 rules 3-10 speak of 'the resultant identifier' with no floating-point exemption (no normative text found; D.18.3.3 is informative), and CONFORMANCE.md documents no such choice. ArithmeticEmitter passes CobolRounding.Truncation for all-float target sets and the float store never consults the mode. Fixed-point receivers (native, STANDARD-DECIMAL, float source, 31-digit, P-scaled VPP9, DIVIDE/REMAINDER, ADD CORR, DEFAULT ROUNDED on every verb) re-probed correct (p2.cob, p3.cob).
