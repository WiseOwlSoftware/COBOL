# PB5460 - the NIST CLI guard and `NistRunner.Normalize` treat a form feed differently: SQ101M is a false red in the nightly guard since PB2509, and in the in-process gate a page eject compares equal to a line advance

**Sites:** `scripts/guard-verdict.sh` (l.81, `guard_normalize_into`), `tests/WiseOwl.Cobol.Tests.Conformance/NistRunner.cs` (l.96, l.111-113, `Normalize`), and the siblings named below

**Facts read in the code by the Mythos session, 2026-11-12 (main b8cb5f6d51):**
- `scripts/guard-verdict.sh` l.81, `guard_normalize_into`: `sed 's/ *\r//g; s/ *$//; s/COMPUTED=  [0-9]*/COMPUTED=  XXXXXXXXX/'`. It strips spaces before a CR and at a line's end, and nothing before a form feed.
- `tests/WiseOwl.Cobol.Tests.Conformance/NistRunner.cs` l.111-113, `Normalize`: after dropping ` *\r` it calls `.ReplaceLineEndings("\n").Split('\n')`, and `ReplaceLineEndings` turns a form feed into a line break. Its doc comment (l.96) says it is "exactly" `guard_normalize_into`. It is not.
- The nightly's `Guard (WiseOwl COBOL NIST, parallel)` job printed `UNEXPECTED: SQ101M expected MATCH, got DIFF — REGRESSION!` in runs 42387393999 (11-07), 42497371387, 42686567938, 43064817616 and 43270832950 (11-12), each read by the session.

**Reported by the analyst (`E:\COBOL-coord\scratch\reports\nightly-sq101m-triage.md`, with commands, byte dumps and the diff; a claim until the fixer reruns it):**
- Reproduced in WSL at b8cb5f6d with `GUARD_TESTS=SQ101M bash scripts/guard-fast.sh`: `unexpected=1`, `nist=1 audit=1`, with SQ101M alone, so the parallel run plays no part.
- The diff is 8 lines (61, 118, 163, 221, 267, 355, 412, 471), each a line with a page break: `grep -c " \f"` finds 0 in the golden and 8 in the produced output. Adding `s/ *\f/\f/g` to the guard's sed makes the two sides identical.
- Since PB2509 (pull request #1091, merge d966b30ac4; runtime commit 902c96e558, and 76569d92fb which changed both normalizers for CR and left the form feed out of the sed one) the runtime writes each print record whole, so the padding before a page break is in the output. The Guard job was green on 11-01 to 11-03 (d185162f87) and red from 11-04 (69270302d0). The analyst did not bisect by building; the attribution rests on the mechanism and the window.
- The golden and the `corpus.tsv` row are right, the compiler and the runtime are right, and no user program is affected.
- `SQ101M.txt` is the only NIST report golden with a form feed. The written-files arm compares bytes with `cmp` and is not reached.

**Two defects, one root (the rule is written twice and the two copies disagree):**
1. The false red: nine nights of a red nightly that nobody could act on, on the only run of the CLI guard and the GnuCOBOL differential.
2. The blind spot: in the in-process gate (every local gate and every merge group) a runtime that wrote a line break where WRITE ... ADVANCING PAGE owes a page eject would pass. No defect is known to have passed through it.

**Shape (rule 5: the next case automatic):** ONE normalization rule for both sides: spaces before a form feed are trailing spaces of the line and are dropped, and a form feed stays a form feed, never a line break. The two implementations (sed and C#) read ONE table of parity cases, as `tests/version-matrix/derivation-parity-cases.json` does for the derivation register, so a change to either that the other does not make fails a test. The C# doc comment's "exactly" becomes true or goes.

**Sibling sweep the fix owes (a lead, untested):** every other comparator that calls `ReplaceLineEndings` on program output (`CharacterizationCorpus.cs`, `ConformanceSuiteRunner.cs`, `DifferentialGolden.cs` and the rest `git grep ReplaceLineEndings -- tests src` finds): each merges a form feed, NEL, LS and PS into a line break the same way.
