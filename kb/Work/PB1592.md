# PB1592 — OPEN

Filed 2026-09-26 11:36 PDT by the golden-lane-2 lander from the gl2-misc-p2 writer's finding (brief step 2b (c)).

## The question
`docs/CONFORMANCE.md` row DOC-A.1-29 documents the compile-time arithmetic mode (.NET `System.Decimal`, ties to
even, one evaluator `CompileTimeExpressionEvaluator` for CONSTANT AS, `>>DEFINE` and `>>IF`/`>>EVALUATE`) and ends
"2002 onward". The inventory row's editions are 2002,2014,2023, and the compiler uses the same Decimal evaluator at
every edition. `tests/version-matrix/constructs.json` `arithmetic-intermediate-precision-2023` is still
pending/UNCONFIRMED, and `docs/VERSION_CHANGE_REFERENCE.md` row 12 records E.2 item 6 as gate-behavior-by-dialect
(todo).

## Expected, from the standard
```
$ python scripts/spec/cite.py --check E.2 "The mode of arithmetic used in evaluating compile-time arithmetic expressions and the handling of intermediate results is now explicitly implementor defined"
OK  §E.2 6)  (Substantive changes potentially affecting existing programs)
$ python scripts/spec/cite.py --check E.2 "The previous COBOL Standard required the use of an arithmetic mode that is no longer supported"
OK  §E.2 6)
```
So at 2002 and 2014 the mode was PRESCRIBED, and the implementor determination applies from 2023 only; below 2023,
compile-time expressions should follow the prescribed mode. Whether 2002/2014 output actually differs (for example
`15E-28 / 2 * 1E28` gives 7 under a wider exact mode, and `9999999999999999999999999999 * 10` fits in 32 digits)
needed the 2002/2014 text — RESOLVED below from the 2023 text itself.

## Resolved from the 2023 text (2026-09-26, owner: "You have the ISO standard, use it")
The 2002/2014 text is NOT needed to decide the scope — ISO/IEC 1989:2023 names the prescribed mode itself:
```
$ python scripts/spec/cite.py --check E.2 "The previous COBOL Standard required the use of an arithmetic mode that is no longer supported"
OK  §E.2 6)
$ python scripts/spec/cite.py --check E.2 "Standard Arithmetic"
OK  §E.2 21)   — "Obsolete elements … have been removed …: FLAG-85, FLAG-NATIVE-ARITHMETIC, Standard Arithmetic, …"
```
The only arithmetic mode 2023 removed is **Standard Arithmetic** (E.2 21), so the mode §E.2 6) calls "an arithmetic
mode that is no longer supported" is Standard Arithmetic (STANDARD-BINARY survives, obsolete — the NOTE under
8.8.1.4): **at 2002 and
2014, compile-time arithmetic expressions are evaluated in standard arithmetic.** This compiler already implements
2002's `ARITHMETIC IS STANDARD` — at the editions that have it — on the SDIDI decimal engine it shares with
STANDARD-DECIMAL (`OptionsModel.cs`: `ArithmeticMode.Standard` "is NOT a third engine", 34 digits, the SDIDI range,
`NumericRenderer.StandardDecimal`). That is the existing, documented determination of what standard arithmetic IS
here.

**Decision: option (a).** Below 2023 the mode is PRESCRIBED, so the implementor determination DOC-A.1-29 cannot apply
there; `CompileTimeExpressionEvaluator` must evaluate on the standard-arithmetic engine (SDIDI, 34 digits, decimal128
range) at `--std 2002` and `--std 2014`, gated by dialect — VERSION_CHANGE_REFERENCE row 12's
"gate-behavior-by-dialect". DOC-A.1-29 and its inventory row narrow to **2023** (the edition where E.2 6) makes it
implementor-defined), and CONFORMANCE.md's "2002 onward" becomes "2023"; the 2002/2014 behavior is documented as the
prescribed standard arithmetic instead. Witnesses: a 2002 golden whose compile-time expression differs between
System.Decimal (28–29 digits) and the SDIDI (34), e.g. `9999999999999999999999999999 * 10` in a `>>DEFINE`/CONSTANT,
plus the existing 2023 witnesses unchanged.

**2023's latitude — DECIDED 2026-09-26: keep System.Decimal** (owner: "System.Decimal seems a good choice unless
GnuCOBOL strongly suggests something different"). Precedence survey (ISO does not control at 2023 → GnuCOBOL), read
from the GnuCOBOL 3.2 sources in the pinned `tests/external/gnucobol-3.2.tar.xz` (GPL — read, never copied): cobc
folds a binary operation over two numeric literals in `cb_build_binary_op` (`cobc/tree.c` ~5800–5935) with
`cob_s64_t` integers (`atoll` of the literal digits, scales aligned by ×10), folds `/` only for "simple integer
numerics", and otherwise leaves the expression to run time; `cobc/ppparse.y`'s `>>IF` conditions are comparisons
with no arithmetic evaluator found. That is a 64-bit integer SHORTCUT, not a designed arithmetic mode, and it is
narrower than System.Decimal's 28–29 significant digits — it suggests nothing different, so DOC-A.1-29 stands for
2023 as documented, and the survey result is added to its row when the scope narrowing lands. Consequence: TWO
engines by edition (SDIDI where the mode is prescribed, System.Decimal where it is implementor-defined) — the
per-edition split is the standard's own, carried by one evaluator with a dialect-selected arithmetic, never two
evaluators.

## What landed meanwhile
Golden lane 2 landed the 2023 witnesses `conformance:2023/gl2m2_ct_arith_mode` and
`conformance:negative/gl2m2-ct-arith-intermediate-overflow` and recorded the row CONFORMS with its editions
UNCHANGED (2002,2014,2023) — the lander was not to change them. This analysis decides the scope: reconcile
CONFORMANCE.md's "2002 onward" with VERSION_CHANGE_REFERENCE row 12, and either (a) gate the evaluator by dialect
(the 2002/2014 prescribed mode, with its own witnesses) or (b) narrow the row and the determination to 2023 and
record why the prescribed mode is equivalent or unsupported below it. The choice between (a) and (b) turns on the
2002/2014 text; if it cannot be read, it is an owner question under the precedence rule (ISO → GnuCOBOL → IBM/MF).
