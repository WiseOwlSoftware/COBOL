# PB4507 — INTEGER-OF-FORMATTED-DATE refuses a function-identifier as argument-2

**Found:** 2026-11-03 by the first Claude-written fuzz batch (PB4506 smoke, 5 programs), adjudicated WISEOWL-DEFECT by
slice C1. Witness (reduced by the adjudicator, `E:/COBOL-coord/scratch/fuzz-triage/fuzz-batch-smoke-20261103/adj/C1/probes/iofd/iofd.cob`):

```cobol
       01 WS-D PIC X(10) VALUE "2000-03-01".
       01 WS-N PIC S9(9) VALUE 0.
       PROCEDURE DIVISION.
           COMPUTE WS-N = FUNCTION INTEGER-OF-FORMATTED-DATE("YYYY-MM-DD", FUNCTION UPPER-CASE(WS-D))
```

WiseOwl refuses it with COBOL1627 ("argument-2 shall be a DATA ITEM ... a literal or an expression is not admitted").
The same program with `WS-D` itself as argument-2 returns 145792 (2000-03-01, hand-derived).

**The rule.** §15.48.3 3) (checked): "Argument-2 shall be a data item of the same type as argument-1." §8.4.3.2.4 1)
(checked): "A function-identifier references a temporary data item whose value is determined when the function is
referenced at runtime." So a function-identifier returning an alphanumeric value IS a data item of argument-1's type.
§15.3's argument types use "data item" the same way throughout ("Alphanumeric. A data item of the class alphabetic or
alphanumeric or an alphanumeric literal"), and nested function-identifiers are admitted for every one of them; the
rule's force is to exclude a LITERAL (and an expression, which is not a data item).

**The code site.** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/IntrinsicBinder.cs` (the PB58 screen,
`args[1] is not BoundFieldOperand`): it admits only a field operand, so a bound function call is refused with the
literals the screen was written for.

**Sweep.** Every other "shall be a data item" screen in the binder that tests for `BoundFieldOperand` (intrinsic
arguments and statement operands alike) is a candidate for the same mistake; the fix asks one question, "is this
operand a data item (a field reference, a function-identifier's temporary, ...)", in one place, and the screens use it.
Keep the refusal of literals, figurative constants and arithmetic expressions (under-rejecting is the worse failure).

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/IntrinsicArgumentRules.cs` (`IntrinsicArgumentRules.IsDataItem`,
`IntrinsicArgumentRules.PredicateViolation`, `ArgPredicateKind.DataItemOnly`, the `INTEGER-OF-FORMATTED-DATE` row of
`Verified`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/IntrinsicBinder.cs` (`IntrinsicBinder.BindIntrinsicCore`, the
PB58 argument-2 arm deleted; `IntrinsicBinder.CheckArgumentClasses`, the predicate loop reports `DataItemOnly` as a hard error;
`IntrinsicBinder.BindArgOperandCore` and `IntrinsicBinder.IsSoleFunctionIdentifier`, the binder's statement that an argument is a
function-identifier, review R1-1).

## Landed (wave 20261850 A)

Re-probe on the wave's build: the witness above reproduced as COBOL1627 and, after the fix, prints `+000145792` (the integer
date of 2000-03-01, checked against Python's `datetime`). `cite.py --check` OK for 8.4.3.2.4 1), 15.48.3 3), 15.2 5), 15.37.3 3)
and 15.12.3 1).

- **The mechanism.** The "shall be a data item" half of 15.48.3 r3 was a hand-written arm in `BindIntrinsicCore`
  (`args[1] is not BoundFieldOperand`). It is now the `DataItemOnly` argument predicate in the schema row, answered by the ONE
  `IntrinsicArgumentRules.IsDataItem` (a field operand incl. reference modification and a user function's result item, a counter
  register, an address-identifier and a nested or folded function-identifier are data items; a literal, a figurative constant, an ALL
  literal, a boolean and an arithmetic expression are not). A violation stays a hard error under `--permissive`, as the arm's was.
- **The sibling, found by the sweep and fixed (I9).** `DataItemOrLiteralOnly` (FIND-STRING argument-3, 15.37.3 r3; BASECONVERT
  argument-2/3, 15.12.3 r1) barred EVERY nested function, an INTEGER function's temporary included: the same mistake (8.4.3.2.4 GR1
  makes it a data item; 15.2 5) gives an integer function no digits right of the point). It now bars only the arithmetic
  expression; a nested numeric (non-integer) function is still refused by the 15.3 type 6 integer test (8.4.3.2.3 SR11).
  `FIND-STRING(X "ABC" FUNCTION INTEGER(1))` returns 4 and `BASECONVERT("1A" FUNCTION INTEGER(16) 10)` returns 26.
- **Sweep of the other `is not BoundFieldOperand` sites** (`StatementValidation.OperandItem` and `CheckFigurativeAssociation`,
  `MoveOverlap.Classify`, `ConditionRenderer`, `InspectEmitter`, `EvaluateBinder`): each asks an identity or storage question, not
  "is this a data item", and `BindAlgebraicFold` bars a function by 15.43.3 1)'s own words; none changes.
- **Goldens.** `pb4507_iofd_function_identifier_argument_2` (accept 2014), `pb4507_find_string_function_argument_3` and
  `pb4507_baseconvert_function_bases` (accept 2023); negatives `pb4507-iofd-figurative-argument-2`, `pb4507-findstr-numeric-function`
  and `pb2079-baseconvert-expression-base`; retired `pb58-findstr-func` and `pb2079-baseconvert-function-base` (they refused legal source).
