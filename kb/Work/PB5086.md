# PB5086 - at --std 85 the multiple file reel rules are unchecked: OPEN EXTEND of a file in a MULTIPLE FILE TAPE clause and a MERGE naming two files of one reel both compile

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/FileControlBinder.IoControl.cs#ScreenMultipleFileClause` (resolves the file-names and records no reel membership; its comment: "the clause is otherwise parsed and ignored"), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/SortBinder.cs#BindMerge`; the OPEN EXTEND checks (COBOL2372) in StatementValidation have no reel arm (named without a member).

**Mechanism.** 1985 forbids the EXTEND phrase for a multiple file reel and forbids two files of one multiple file reel in a MERGE. The MULTIPLE FILE TAPE clause is bound but its reel membership is never recorded, so neither OPEN nor MERGE can ask.

**Found by.** The 1985 `--std=85` draft triage (kb/Work PB4995 item 3): each rule below is a conformance-suite draft that did not MATCH at `--std 85`, and its adjudicator decided COMPILER-DEFECT. Harm and observed text are the records'; nothing here was re-derived.

**Inventory.** The traceability inventory carries no 1985 rows yet, so `inventory_rows` is empty; the rows this note covers are the 1985 rule ids listed below (catalog `docs/rearchitecture/spec-rule-catalog-1985.json`).

**Rules (2; every citation checked with `scripts/spec/cite.py --check`).**

- `1985-SR-VII.4.3.3-2` - `§1985:VII.4.3.3 SR2` (record harm: under-rejects, slice-06): §1985:VII.4.3.3 SR2: "The EXTEND phrase must not be specified for a multiple file reel." A source program states that a file is on a multiple file reel by naming it in the MULTIPLE FILE TAPE clause: §1985:VII.2.11.1 "The MULTIPLE FILE TAPE clause specifies the location of files on a multiple file reel.", and §1985:VII.2.11.3 GR1 "The MULTIPLE FILE TAPE clause is required when more than one file shares the same physical reel of tape." The draft reads the rule correctly: `MULTIPLE FILE TAPE CONTAINS F1 F2` puts F1 on a multiple file reel and `OPEN EXTEND F1` (line 18) specifies EXTEND for it, so the program violates the syntax rule (§1985:I.1.6: "A conforming source program is one which does not violate the explicitly stated provisions and specifications of Standard COBOL."). The control (`OPEN OUTPUT F1`) conforms and compiles.
- `1985-SR-XI.4.1.3-6` - `§1985:XI.4.1.3 SR6` (record harm: under-rejects, slice-09): §1985:XI.4.1.3 SR6: "No two files specified in any one MERGE statement may reside on the same multiple file reel." Which files reside on one reel is what the I-O-CONTROL clause states: §1985:VII.2.11.3 GR1, "The MULTIPLE FILE TAPE clause is required when more than one file shares the same physical reel of tape." So two file-names of one MERGE statement that one MULTIPLE FILE TAPE clause names violate a syntax rule, decidable from the source text. The draft reads the rule correctly (IN1 and IN2 are both in the clause and both in USING). The rule relates two places, the clause (the draft's line 12) and the MERGE statement (its lines 28-29); a diagnostic at either would be right, and the compiler gives none anywhere. The SORT statement has the opposite rule, so the check is MERGE's alone: §1985:XI.4.4.3 SR7, "The files referenced by file-name-2 and file-name-3 may reside on the same multiple file reel."

**Expected (from the 1985 text).** --std 85 refuses the OPEN EXTEND and the MERGE, at the statement. The deciding words: "The EXTEND phrase must not be specified for a multiple file reel." (§1985:VII.4.3.3 SR2).

**Observed (copied from `1985-SR-VII.4.3.3-2`).** cobol --std 85 --source-format fixed --flag-extensions: exit 0, no diagnostic at all; line 18 (`OPEN EXTEND F1.`) draws nothing. Siblings, each exit 0 with no diagnostic: `MULTIPLE FILE TAPE CONTAINS F1 POSITION 1 F2 POSITION 2.` with `OPEN EXTEND F2.`; `OPEN INPUT F2 EXTEND F1.` under the draft's clause. The neighbouring rule IS enforced at 85: §1985:VII.4.3.3 SR3 (EXTEND with a LINAGE file) gives exit 65, (16,12): error COBOL2372: OPEN EXTEND 'F1' — the file description entry specifies a LINAGE clause, which EXTEND does not admit (ISO §2023:14.9.27.3 SR2). The control compiles and runs (exit 0). Code sites: src/WiseOwl.Cobol.Compiler/Binding/Validation/StatementValidation.cs (the OPEN EXTEND checks, where COBOL2372 is raised) has no multiple-file-reel arm, and src/WiseOwl.Cobol.Compiler/Binding/FileControlBinder.IoControl.cs, ScreenMultipleFileClause, resolves the clause's file-names and records nothing on the file ("the clause is otherwise parsed and ignored").
