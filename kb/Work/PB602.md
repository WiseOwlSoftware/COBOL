# PB602 — LANDED — a decorated place answers "which item" with the item underneath

Found 2026-09-05 by the `PB236` implementer (its report §12 D); the row moves here from PB236 so PB236 can land
whole. Re-derived on this tree for this note.

## Repro (`--std 2023`)

```cobol
       SELECT RLF ASSIGN … ORGANIZATION RELATIVE RELATIVE KEY IS WS-RK.
       01 WS-RK PIC 9(4).
       ...
           START RLF KEY IS = WS-RK(1:2)      *> compiles clean; positions on the number the first two characters spell
```

A key of `12` positions the file at relative record `0` — §12.4.5.13.4 GR1 makes `1` the first legal relative
record number — silently. A `66 ALIAS RENAMES WS-RK.` (no THRU) passes the same screen where the THRU form is
correctly rejected.

## The rule

§14.9.41.3 SR5 (quoted from `specs/ISO_COBOL.md`; `cite.py --check 14.9.41.3 "For relative files, data-name-1, if
specified, shall be the data item specified in the RELATIVE KEY clause in the associated file control entry."`
is the fix's first step). "Shall BE the data item" is an identity over DATA ITEMS; a reference-modified slice is
a different unique data item (§8.4.3.3.4), and a RENAMES alias is a different data item over the same storage.

## The mechanism

`PlaceDecorator.Item => Inner.Item` (`src/Cobol.Net.Compiler/…/Places`): a decorated place — a reference
modification, a RENAMES alias, a view — reports the UNDERLYING item as its `Item`, so every screen written as
"is `place.Item` the required item?" asks about storage where the rule asks about the data item. PB236 measured
it at START's SR5; PB128's `ScreenResultant` (the arithmetic resultant category screen) had already met it and
routed around it by testing `p is not RefModPlace` on the Place rather than the item — a fix at one caller for a
property of the Place model. The real fix is general: a decorated place must answer identity questions as
itself, and the screens that legitimately want the storage item (a few) must ask for it by a differently-named
member.

## Fix shape

Give `Place` two distinct questions — the data item the reference DENOTES (a ref-mod slice, an alias, a view each
denote their own) and the storage item it OCCUPIES — and sweep every `.Item` consumer in the binders to the one
it means (`grep -rn "\.Item\b" src/Cobol.Net.Compiler/Binding`), starting with START's SR5/SR6 and the
CORRESPONDING, arithmetic-resultant and file-key screens; PB128's Place test then collapses into the general
answer. Negative goldens for the START slice and the non-THRU alias (all four editions); positive controls for
the plain RELATIVE KEY item and the legal THRU cases.


## LANDED — 2026-09-21, wave 42 (group MOVE OPERANDS)

`Place` now answers the two questions §13.18.45.4 GR1 writes as two clauses of one sentence — *"all of the data
attributes of data-name-2 become the data attributes of data-name-1 **and the storage area occupied by
data-name-2 becomes the storage area occupied by data-name-1**"*:

* `Place.Item` keeps answering the ATTRIBUTES-and-STORAGE half, unchanged, so every layout, codegen and
  description consumer sees what it saw before;
* `Place.DenotedItem` answers WHICH DATA ITEM — `null` when the reference denotes one no data description entry
  declares. `RefModPlace` overrides it to `null` by §8.4.3.3.4 GR5 (*"Reference modification creates a unique
  data item that is a subset of the data item referenced by identifier-1"*), and the non-THROUGH level-66 alias
  records itself in `Place.DenotesAs`, set by the ONE resolver. The alias is carried as an init-only property
  rather than a new `Place` kind precisely because nothing about the ACCESS changes: a new kind would have to be
  re-handled in every renderer arm to render identically.

Both halves of the note's repro now refuse, and with the rule the program broke:

```
--std 2023  START RLF KEY IS = WS-RK(1:2)   COBOLNET0862 … data-name-1 shall be the RELATIVE KEY item 'WS-RK'
                                            (ISO §14.9.41.3 SR5)          (was: compiled clean)
--std 2023  START RLF KEY IS = RK-ALIAS     the same                       (was: compiled clean)
--std 2023  START IXF KEY IS = IX-KEY(1:2)  COBOLNET0862 … neither a record key of the file nor an item that
                                            begins at the leftmost character position of one … (SR6)
```

POSITIVE CONTROLS, because a screen that refuses everything is not a fix: the plain RELATIVE KEY item and the
prime record key still START successfully and READ the record; `MOVE "WXYZ" TO G-ALIAS` (the THROUGH form, GR2's
alphanumeric group) and `MOVE 7 TO RK-ALIAS` / `ADD 3 TO RK-ALIAS` (the non-THROUGH form, GR1's shared attributes
and storage) all still work — `tests/conformance/85/pb602_start_key_identity`.

THE SWEEP THE NOTE ASKED FOR, done as the note framed it: `PB128`'s `p is not RefModPlace` route-around — a
caller's private copy of §8.4.3.3.4 GR5 — was written out at **twenty** sites across `MoveClassifier`,
`MoveTable16`, `ExpressionBinder` (including `ScreenResultant`, PB128's own), `StringUnstringBinder`,
`IntrinsicArgumentRules`, `IntrinsicBinder`, `NumericRenderer` and `OoConformance`. All twenty now read
`DenotedItem`, and `PlaceDenotedItemDriftTests` holds the roster: every concrete `Place` kind must appear in the
forwarding table or the overriding one WITH THE REASON, the roster must match what the code actually overrides,
and no product source may re-derive the identity question by hand. The detector was proved by failing once — it
found eight sites in `IntrinsicArgumentRules` and `IntrinsicBinder` that the first grep had missed.

⚠ NOT SWEPT, and recorded rather than assumed: the four `RefModPlace or RenamesPlace` tests in
`StatementValidation` and `MoveEmitter` ask a DIFFERENT question (is the operand's storage one contiguous
declared item — a THROUGH alias composes N leaves and its `DenotedItem` is its own alias item, so converting them
would change behaviour). They are named in this landing's report as a lead, not converted blind.

`SR-14.9.41.3-5` is re-verdicted CONFORMS.
