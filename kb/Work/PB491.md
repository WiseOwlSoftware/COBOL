# PB491

## Mechanism — picture-clause-p3
pic-editing-phrase-render-gap - the COBOL-2023 PICTURE EDITING phrase is implemented only for a ONE-CHARACTER literal at a SINGLE character-1 occurrence. PictureAnalyzer.ValidateEditing sets `staged = true` for a literal wider than one character and for a repeated character-1 under a FOR phrase, and raises COBOLNET0899 (ConstructStagedNotImplemented) at 2023, contributing no render rule. Both refused shapes are exactly what Annex D.24 demonstrates, so legal, standard-illustrated source is rejected. The gap is real work, not a decision: the render is variable-width (one occurrence of literal-2/literal-3 plus one character per repetition, 13.18.40.4 GR14's 'es' entry), which is why the fixed-width mask machinery cannot carry it. No kb/Work note owns it today - it lives only in a code comment and in two tests that pin it green.

### Expected, from the standard
ISO/IEC 1989:2023 13.18.40.5 rule 5 with Table 8 ('literal-2 or literal-3 or spaces means one instance of literal-2 or literal-3 or as many spaces as there are characters in literal-2 or literal-3' - a literal of any width), rule 6 first sentence ('The currency symbol, the extended editing sign control symbols, if specified, and the fixed editing sign control symbols + and - are used as the floating insertion symbols'), 13.18.40.3 SR9 (a literal of up to 50 characters is legal) and SR25 (one or two extended editing sign control symbols). Annex D.24 gives the expected images: `PIC L999.99 EDITING "L" FOR NEGATIVE IS "DEBIT "` renders 'DEBIT 123.45' for -123.45 and six spaces then '123.45' for +123.45, and 'PIC LLLL9,88 EDITING "L" FOR NEGATIVE IS "DEBIT "' is a 13-character item (6 for the first L, 3 for the next three, 4 for the numbers).

```
$ python scripts/spec/cite.py --check 13.18.40.5 "The currency symbol, the extended editing sign control symbols, if specified, and the fixed editing sign control symbols + and - are used as..."
  OK  §13.18.40.5 6)  (Editing rules)
```

### Observed
Observed by probe against the standard's own Annex D examples, which is the cheapest available conformance witness for this feature. The gap is currently pinned green by PictureEditingTests.MultiCharLiteral_StagedGap0899 and .FloatingCharacter1_StagedGap0899 - a green test over a loud stage reads as a decision, and no owner decision covers this one, so it must be visible in kb/Work as an open GAP rather than only in a test name.
