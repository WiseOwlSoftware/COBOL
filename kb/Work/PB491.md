# PB491

## Mechanism — picture-clause-p3
pic-editing-phrase-render-gap - the COBOL-2023 PICTURE EDITING phrase is implemented only for a ONE-CHARACTER literal at a SINGLE character-1 occurrence. PictureAnalyzer.ValidateEditing sets `staged = true` for a literal wider than one character and for a repeated character-1 under a FOR phrase, and raises COBOLNET0899 (ConstructStagedNotImplemented) at 2023, contributing no render rule. Both refused shapes are exactly what Annex D.24 demonstrates, so legal, standard-illustrated source is rejected. The gap is real work, not a decision: the render is variable-width (one occurrence of literal-2/literal-3 plus one character per repetition, 13.18.40.4 GR14's 'es' entry), which is why the fixed-width mask machinery cannot carry it. No kb/Work note owns it today - it lives only in a code comment and in two tests that pin it green.

### Expected, from the standard
ISO/IEC 1989:2023 13.18.40.5 rule 5 with Table 8 ('literal-2 or literal-3 or spaces means one instance of literal-2 or literal-3 or as many spaces as there are characters in literal-2 or literal-3' - a literal of any width), rule 6 first sentence ('The currency symbol, the extended editing sign control symbols, if specified, and the fixed editing sign control symbols + and - are used as the floating insertion symbols'), 13.18.40.3 SR9 (a literal of up to 50 characters is legal) and SR25 (one or two extended editing sign control symbols). Annex D.24 gives the expected images: `PIC L999.99 EDITING "L" FOR NEGATIVE IS "DEBIT "` renders 'DEBIT 123.45' for -123.45 and six spaces then '123.45' for +123.45, and 'PIC LLLL9,88 EDITING "L" FOR NEGATIVE IS "DEBIT "' is a 13-character item (6 for the first L, 3 for the next three, 4 for the numbers).

### `PicInfo.Length` under-counts a STAGED multi-character EDITING literal (from the PB492 report, item C)

`PIC NNTNN EDITING "T" IS N"::"` binds `Length` 5 where §13.18.40.4 GR14's 'es' entry counts literal-1's size
(6). No observable harm today — the entry has already failed with COBOLNET0899 and the shape is recovery-grade —
but it is exactly the variable-width render THIS note owns, and PB491's fix must SET this Length rather than
inherit the under-count. Recorded here so the implementer sees it before writing the width computation.

## Landed 2026-09-19

The variable-width render EXISTS, and it is the mechanism the multi-character currency string already needed
rather than a second one. `CobolEdit.Render` produces the LOGICAL image - one character per picture SYMBOL,
which is the image every editing rule of §13.18.40.5 is written about - and `CobolEdit.Materialize` gives each
symbol the width §13.18.40.4 GR14 gives it; `DeEdit` walks the same widths in reverse with a physical cursor.
`ExpandCurrency`/`CollapseCurrency`, the search-based pair that served the currency string alone, are DELETED.

Two shapes stopped being refused:
- a literal wider than one character (Table 8's note, "as many spaces as there are characters in literal-2 or
  literal-3"; SR9 allows 50) - `EditRule.Neg`/`.Pos` are now STRINGS;
- a FLOATING character-1 - §13.18.40.5 rule 6's first sentence lists "the extended editing sign control symbols,
  if specified" among the floating insertion symbols, and `PictureComposition.MarkFloating` knew only three of
  the four kinds. The FOR-phrase character-1 letters now travel to it as their own set (`char1Extended`); the
  IS-form ones stay transparent, because rule 3 makes those SIMPLE insertion symbols.

SIZE follows from GR14's 'es' entry through `PictureAnalyzer.EditingPositions`, the exact shape `currencyExtra`
already had for 'cs'. That also fixes the lead appended to this note from the PB492 report:
`PIC NNTNN EDITING T IS N"::"` binds LENGTH 6, not 5.

MEASURED against Annex D.24's own images: `PIC L999.99 EDITING L FOR NEGATIVE IS "DEBIT "` renders
`DEBIT 123.45` for -123.45 and six spaces then `123.45` for +123.45 (SIZE 12); `PIC LLLL9.99F` with `"("` and
`")"` renders ` (123.45)` (SIZE 9); `PIC LLLL9.99` with `"DEBIT "` is 13 characters, the arithmetic D.24 states
outright. The two GREEN tests that pinned the GAP - `PictureEditingTests.MultiCharLiteral_StagedGap0899` and
`.FloatingCharacter1_StagedGap0899` - are DELETED and replaced by those images.
