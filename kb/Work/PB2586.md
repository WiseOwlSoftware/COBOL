## Repro

`UNSTRING A DELIMITED BY " " INTO B` with `01 A PIC A(5).` compiles clean. ISO 14.9.48.3 SR2 (UNSTRING): "Identifier-1,
identifier-2, identifier-3, and identifier-5 shall reference data items of category alphanumeric or national"
(`cite.py --check 14.9.48.3` OK). ISO 8.5.2.1: "Use of the name of a data class or data category in the rules of COBOL
refers to the category unless class is specifically indicated", and Table 2 lists alphabetic as a category of its own.

Identifier-4 (the INTO receiver) is different: SR4 admits category alphabetic there, so the fix touches only the SR2
operands. STRING (14.9.43.3) has no category rule of this kind; its SR1 is a usage rule. The implementer's report
called this "STRING/UNSTRING"; the lander re-read both clauses and it is UNSTRING only.

## Code site

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/StringUnstringBinder.cs#Sr2OffendingCategory` (about line 536). Its doc
comment keeps PIC A admitted on purpose as "a change of verdict for existing source". Same root shape as PB850: the
model folds PIC A into `PicCategory.Alphanumeric`.

## Why not fixed in PB850

It changes the verdict for source the corpus may carry. Measure the corpus exposure first (the GnuCOBOL differential
and the NIST goldens), then it needs an owner decision: refuse per the standard, or keep it admitted as a documented
extension under `--permissive` only.

## Landed 2026-10-13 (w1072g)

Re-probed on this build first: `UNSTRING A DELIMITED BY ' ' INTO B` (A PIC A), `DELIMITED BY D` (D PIC A), `DELIMITER IN DI`
(DI PIC A) and `UNSTRING A(1:3)` (A PIC A) all compiled clean. The owner-decision question the note raised does not
arise: 14.9.48.3 SR2 is a syntax rule, not implementor latitude, so CLAUDE.md rule 1 (ISO controls) decides, and the corpus
exposure measured zero (no program under tests/ holds both an UNSTRING and a PIC A item).

Root: `Sr2OffendingCategory` matched `PicCategory.Alphanumeric` on the item's PICTURE, which the model also uses for PIC A.
It now takes the PLACE and asks the one category predicate `ItemCategory.IsAlphanumericOrNational(Place)` (group arms
unchanged). Two sibling arms of the same fold fixed in the same change:

- the reference-modified arm, in the OPPOSITE direction: it read the whole item's category, so `UNSTRING NUM(2:3) ...`
  over a PIC 9 item was refused ("category numeric") although 8.4.3.3.4 GR6 c) makes the unique data item category
  alphanumeric (rejected legal source); a slice of PIC A stays alphabetic (GR6's list names no rewrite for it, PB73) and
  is now refused;
- the function arm: FUNCTION CONCAT over all-PIC-A arguments returns an alphabetic value (15.18.4 r3), carried as
  `ResultIsAlphabetic`, and passed `UnstringSenderCategory`.

SR4's identifier-4 keeps category alphabetic (`UnstringReceiverAllowed`). STRING has no category rule (14.9.43.3 SR1 is a
usage rule). Goldens: five negatives `pb2586-unstring-alphabetic-{sender,delimiter,delimiter-in,slice-sender,function-sender}`
and the positive `2023/pb2586_unstring_sr2_category_operands`. Row SR-14.9.48.3-2 re-recorded (caveat closed).
