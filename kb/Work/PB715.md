# PB715 — OPEN — the optional-word audit is blind inside optional groups

Found 2026-09-05 by the `PB695` family-1 implementer (report, "New defect (note-ready paragraph)") after
sweeping six sibling optional words by hand that the audit it was running never mentioned. Re-measured here on
`main` at `c34f01ad`.

## The facts

- **The rule the audit exists to enforce.** `cite.py --check 8.3.2.4.3 "with no effect on the semantics of the
  format"` → `OK §8.3.2.4.3 (Optional words)`: *"Within each format, uppercase words that are not underlined are
  called optional words and may be specified at the user's option with no effect on the semantics of the
  format."* A grammar that DEMANDS an un-underlined word rejects conforming source.
- **The blindness, in the code.** `scripts/spec/audit_grammar_optional_words.py#scan_alternative` (`:205-244`)
  walks an alternative with a group stack; on closing a group whose suffix is `?` or `*` it marks **every token
  inside it** optional (`:224-227`), and its own docstring states this as the design — *"A token may be omitted
  when it carries a `?`/`*` suffix of its own, or when ANY enclosing group does."* `required_tokens` (`:247-284`)
  then keeps only `{w for w, opt in scanned if not opt}`. The two questions are different: *may this PHRASE be
  omitted* (yes) and *may this WORD be omitted while the phrase is present* (the §8.3.2.4.3 question, unasked).
  A word required inside an optional group can therefore never become a candidate.
- **Measured on the current tree.** `CobolSpecialNames.g4:103-105` is still
  `classDefinitionClause : CLASS cobolWord IS? classValueSet (FOR (ALPHANUMERIC | NATIONAL))? (IN cobolWord)?` —
  FOR is demanded whenever the group is present. `python scripts/spec/audit_grammar_optional_words.py --clause
  12.3.7.2` prints **10 candidates and none of them is that FOR** (it lists `alphabetClause` IS,
  `alphabetForPhrase` FOR, `channelClause` IS, `crtStatusClause` IS, `cursorClause` IS, `decimalPointClause` IS,
  `switchOnClause` IS, `symbolicCharacterEntry` IS/ARE, `symbolicCharactersClause` CHARACTERS — every one of them
  a word NOT inside an optional group), and closes `population OK`.
- **Why the class is not rare.** The six siblings PB695 family 1 swept by hand, each invisible for exactly this
  reason: `currencySignClause` WITH · `classDefinitionClause` FOR · `symbolicCharactersClause` FOR ·
  `switchOnClause`/`switchOffClause` STATUS · `implementorSwitchEntry` IS · `CobolIO.g4#collatingForPhrase` FOR.
  The audit reported a clean run over all six while it was reporting fifteen of their neighbours.
- **One thing from the report that did NOT reproduce.** It gives the harm as a rejection —
  `CLASS X IS "0" NATIONAL` refused. On this tree it compiles clean (`--std 2023`, probe
  `…\scratchpad\pb715{a,b}.cob`, both `CLASS DIGITS IS "0" NATIONAL.` and the THROUGH form). The discriminator
  says why that is not good news: `CLASS DIGITS IS "0" ZOTZOT.` **also** compiles clean (`pb715c.cob`), so the
  trailing word is being swallowed by a SPECIAL-NAMES sink rather than spelled — the consequence of the
  blindness on this construct is a silent MIS-PARSE, not a diagnostic. That swallowing is a separate defect,
  **filed as [[PB716]]**: `implementorSwitchEntry` (`CobolSpecialNames.g4:76-78`) makes a bare word a complete
  SPECIAL-NAMES entry, and the trailing NATIONAL is bound as an implementor DEVICE-name (measured) instead of
  applied to the class. The two must be read together — PB716 is why the source this audit fails to flag compiles
  anyway.

## Why it matters

No user program changes because of this note alone — the audit is a gate, not a compiler. But it is the gate
that decides whether the §8.3.2.4.3 sweep is finished, and it answers "clean" for a whole shape of violation.
That is `feedback_measure_the_selectors_complement` exactly: a filter is evidence about what it RETURNED and
never about what it dropped, and `feedback_green_gates_arent_evidence` — a check that never looked at the thing
that changed proves nothing by passing. Fifteen relaxations landed on the audit's authority in the same session
in which six more had to be found by hand; the next sweep will trust the number again.

## The fix shape

Descend into the group instead of writing it off. For each optional group, ask the per-word question separately:
a token inside `( … )?` is omittable only if the group's own alternatives still spell the group's contents with
that token deleted — i.e. run the existing "is this word demanded" test against the GROUP's body as if the group
were a rule of its own, and report a hit as `<rule>#<group>` so the row is addressable. Structurally this is the
`required_tokens` sibling-subsumption test (`:279-284`) applied one nesting level down, so prefer generalizing
that test over adding a second scanner (`feedback_one_mechanism_per_job`). Two things ship with it:

1. **A drift test that fails first.** Fixture grammar with a known required-word-inside-an-optional-group; assert
   the audit reports it, and assert the audit's own count moves. `feedback_prove_the_watchdog_fails`: this gate
   has never once been shown to fire on this shape.
2. **The corrected expectation.** The report warns the candidate list grows grammar-wide once groups are entered
   — 596 parser rules are scanned today and 387 demand at least one token. Every new row is a CANDIDATE, to be
   confirmed against the printed rectangles before any grammar edit (the audit's own closing instruction); the
   growth is the fix working, not a regression, and the burn-down should be sized for it rather than surprised.

## Sweep

The six siblings above are the confirmed population and the fix's first test set. Beyond them, the same
`scan_alternative` optional-marking feeds `closure()` and the noise filters, so re-run the whole audit before and
after and diff the row sets — a row that DISAPPEARS is a bug in the change, a row that appears is the blindness
lifting. Re-check the two structural exclusions in `required_tokens`'s docstring against the new per-group
question: both were earned against top-level tokens and neither has been tested one level in.


## Extended 2026-09-22 by REGISTRAR #11 — a SECOND blindness: a construct whose ANCHOR keyword is itself optional

From wave 46 group H's lead 3 (PB846 implementer report; lander lead H3). The audit's closure starts from the
rules that DEMAND the construct's anchor keyword (`required_tokens` → `anchors = {n for n in rules if tok in
needed[n] …}`, `audit_grammar_optional_words.py` ≈:522). When the printed format makes the anchor optional —
`[ USAGE IS ] { BINARY | … | POINTER … }` — no grammar rule demands USAGE, the anchor set is empty, the closure is
empty, and the construct is reported clean without being examined. That is how PB848's unstressed TO / OF in the
pointer usages went unreported. It is a different mechanism from this note's (a word required INSIDE an optional
group) and the fix belongs in the same change: anchor a construct whose keyword is optional on its first REQUIRED
printed token (or on the clause-title rule), and make the run FAIL — not pass — when a located format with an anchor
keyword produces an empty closure. ⚠ Not re-measured by the registrar: the audit needs the private PDF submodule
(`specs-private`), which this worktree does not initialise; the fixer measures it with `--construct USAGE` before and
after.
