# PB3098 — the reference-modified argument of a method, settled on the text

Written by the Mythos session on 2026-10-12 (operator task w1069y). Every citation below ran through
`python scripts/spec/cite.py --check` on `ddee217e3`.

## The question PB2077 held open

`INVOKE obj "M" USING X(1:5)` where the method's formal is `01 LP PIC X(5)` and `X` is `PIC X(10)`. The typed lane
(an object reference described with a class name) accepts the call and runs it. The universal lane (an object
reference with no class name) raises EC-OO-METHOD. PB2077 asked which lane is right, and whether the unique data item
reference modification creates "has the same PICTURE clause" as the formal. Until now the note was `blocked: true`
on an owner adjudication.

**The derivation.** GR5 and GR6 are the whole definition of the unique data item: it is elementary, it has no
JUSTIFIED clause, and it takes identifier-1's class, category and usage. The standard lists what the item has, and
PICTURE is absent from the list. Where the standard wants a synthesized item to carry a picture, it says so in those
words: an ANY LENGTH item is "treated as though there were n repetitions of the picture symbol in the
character-string in its PICTURE clause" (§13.18.2.4 GR1 b)), a national group is "described with PICTURE N(m)"
(§13.18.29.4 GR2 b)), a bit group with PICTURE 1(m). It does not say that of a reference-modified item. Match rule
3 e) and conformance rule 2 are clause-identity lists, and an item with no PICTURE clause does not have "the same
PICTURE clause" as a `PIC X(5)` formal. So **reading A holds: a reference-modified argument never matches an
elementary formal BY REFERENCE.** It matches a formal that also has none of the listed clauses, an alphanumeric
group of its class (3 c)), and §14.8.2.2 rule 1 then bounds the group's bytes by the slice's evaluated length.

Reading B (the slice is "as if `PIC X(n)`") is an inference from GR2's "as if it were redefined as a data item of class
and category alphanumeric of the same size". That sentence governs identifier-1 of another category, not the unique
data item, and it names a class, a category and a size, never a PICTURE clause. The text does not support it.

**Both lanes ask both relations.** §14.9.23.4 GR7 b) locates the method for every INVOKE by §9.3.6 (the MATCH),
universal or typed; GR7 c) adds the ANY LENGTH ban and conformance for a universal receiver, and §14.9.23.3 SR5 c)
with §14.8.1 asks conformance of a typed receiver at compile time. A typed receiver's descriptions are all static, so
the compiler evaluates the match at compile time too, and a pair that cannot match is a compile-time refusal where
the universal lane raises EC-OO-METHOD. The verdicts are the same relation read at two times.

## Precedence, measured anyway

CLAUDE.md rule 1 stops at the text, which decides. GnuCOBOL 3.2.0 was still probed (WSL, `cobc -x -Wall`,
scratchpad `probe/pb2077_proto.cob`, `pb2077_proto2.cob`), through the one place it applies the same §14.8.2.3.2
rule 2: a program-prototype CALL. It has no answer to the question. Its `check_argument_conformance` reads the
argument's FIELD (identifier-1) and ignores the modifier: `CALL "P5" USING X(1:5)` with `X PIC X(10)` warns "does
not conform", `CALL "P5" USING Y(1:5)` and `Y(1:3)` with `Y PIC X(5)` are silent, and a slice of any length into a
group formal is silent too (the group arm sizes the whole field). IBM Enterprise COBOL has neither program
prototypes nor COBOL methods. Nothing in precedence overturns the text.

## Two points the text leaves open, settled here (recorded in docs/CONFORMANCE.md D-RM1)

1. **A slice whose length is a run-time value, into a group formal.** §14.8.2.2 rule 1 is asked at compile time
   for a typed receiver, and the slice's length is not known then. The standard's own treatment of the one other
   argument whose length moves at run time is the model: "For an argument or formal parameter that is described as
   an occurs-depending group item passed by reference, the maximum length is used" (OK §14.8.2.2). So the compile-time
   rule 1 reads the slice's maximum extent (identifier-1's positions less a static leftmost position, plus one; all
   of them when the leftmost position is not static), and the run-time boundary carries the evaluated length as the
   universal lane does today. The typed-native carrier cannot read past the slice: the write-back store truncates to
   the window.
2. **The ANY LENGTH item in §9.3.6 3 e).** Read literally it lets only an ANY LENGTH argument match an ANY LENGTH
   formal, which empties §13.18.2's purpose for methods. §14.8.2.3.2 d) and e) give the reading the compiler already
   applies on the typed lane: a formal's ANY LENGTH "is considered to match the length of the corresponding
   argument", and an ANY LENGTH argument needs an ANY LENGTH formal. The universal lane never reaches the question:
   GR7 c) refuses the formal.

## What this decision does not change

- A Format 1 CALL with no program prototype asks §14.8.2.3.2 rule 1, a length, so a slice conforms by its length
  there (unchanged, `ParameterConformance`).
- BY CONTENT arguments follow the MOVE rules (§9.3.6 4 d), §14.8.2.3.3 2 d)); a slice moves into an elementary
  formal of its class (unchanged).
- A program-prototype CALL and a user-defined function ask the same §14.8.2.3.2 rule 2 for a BY REFERENCE argument.
  Their slice verdicts are PB2077's sibling sweep, through PB1780's one bind-time entry.
