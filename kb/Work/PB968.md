## Reproduced

`reg11/p42.cob` (a FUNCTION-ID prototype that is never defined, `REPOSITORY. FUNCTION W46HNOF.`):

```cobol
       DECLARATIVES.
       D-NF SECTION.
           USE AFTER EXCEPTION CONDITION EC-FUNCTION-NOT-FOUND.
       D-NF-P.
           DISPLAY "H: " FUNCTION EXCEPTION-STATUS
           RESUME AT NEXT STATEMENT.
       END DECLARATIVES.
       ...
           >>TURN EC-FUNCTION-NOT-FOUND CHECKING ON
           MOVE 1 TO R
           COMPUTE R = FUNCTION W46HNOF(5)
           DISPLAY "E=" R
```

Observed: `H: EC-FUNCTION-NOT-FOUND` then **`E=000000000`**. `reg11/p41.cob` (a NULL function-pointer, `FUNCTION fp(…)`)
gives `H: EC-FUNCTION-PTR-NULL` then **`E=000000000`** the same way. Both name forms share the defect.

## Rule

- `python scripts/spec/cite.py --check 14.9.33.4 "the implicit CONTINUE statement immediately follows the end of the statement that was executing when control was transferred to the exception processing procedure"` → OK §14.9.33.4 2) a)
- `… --check 14.9.33.4 "If the exception condition was raised within a statement within the runtime entity and was not a propagated exception condition, the applicable statement is the one in which the exception condition was raised"` → OK §14.9.33.4 2) a) 1.
- `… --check 14.9.33.4 "for an inline invocation or a function invocation, it is the statement in which the inline invocation or function invocation was specified"` → OK §14.9.33.4 2) a) 2.

Either way (raised in the activating statement for NOT-FOUND / PTR-NULL, or propagated out of a function), the
applicable statement is the COMPUTE, and control resumes AFTER its end. The COMPUTE never stores. **Expected
`E=000000001`.**

## Mechanism (from the source report; the fixer confirms)

The function-identifier's activation is hoisted into a pre-op `BoundSequence` ahead of the carrying statement
(`UdfBinder.UdfWrapCalls`), and `CallEmitter.EmitCall`'s catch arms apply the CALL statement's own rule — "execution
continues at the end of the CALL" (§14.9.4.4 GR3 h) — to that hoisted activation. For a CALL that is right; for a
hoisted function activation the "end of the statement" is the end of the CARRYING statement, so the catch must
leave the carrying statement too, not fall into it with a default result.

## Sibling sweep the fixer owes

- Every hoisted activation that can raise: user FUNCTION by prototype name, by function-pointer, inline method
  invocation (§14.9.33.4 2) a) 2. names inline invocations too), and a function-identifier inside a condition
  (`IF FUNCTION F(1) = 2`), a subscript and a reference-modifier.
- The RESUME AT procedure-name arm (GR3) and the no-RESUME fall-through of a non-fatal EC must be re-checked on
  the same seam.
- A golden per arm at each construct's introducing edition (the fixer derives it from `constructs.json`); the
  defect is behavioural, so no negative is owed.
