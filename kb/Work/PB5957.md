# `BoundReferences` does not enter a value tuple, so the places `BoundSetConditions.Sets` holds are in no statement's reach: the classification asks the links beside the walk for them, and the USE FOR DEBUGGING and USE BEFORE REPORTING checks read the same walk

**Found by** listing step 7b (branch `listing-step-7b-2`, kb/Work PB5925's dated file `2026-11-20-step-7b-2-built`, lead 3 of its list), filed by step 9b so no lead of the listing's design stays in a dated paragraph alone.


`BoundSetConditions.Sets` holds each conditional variable's place in a value tuple which `BoundReferences.Enters` does not walk. The
listing's classification no longer walks the fields (it asks the places the visitor asks, `BoundStores.StorePositionsAmong`); the sibling
readers are X3.23-1985 USE FOR DEBUGGING's "explicitly references" (`DebugTriggerPlanner`) and the USE BEFORE REPORTING control-data
reference check (`ReportWriterBinder.CheckControlDataReferences`), both of which read `Reach` (a 2002+ statement for the first, so no 1985
debug trigger is lost today). **Fix:** `BoundReferences` enters value tuples, with a sweep of every bound node holding one.

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundReferences.cs` (`Enters`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundSetConditions.cs`.
