# PB699 — LANDED — an entry rule that waited for a verb

Found 2026-09-05 by the `PB352`/`PB354` implementer (report §"New defects" b), measured: a program with
`RECORD KEY IS IX-KEY` and `ALTERNATE RECORD KEY IS IX-ALT` both under OCCURS, whose PROCEDURE DIVISION does only
OPEN INPUT and CLOSE, draws zero diagnostics; adding one `READ IXF NEXT` makes both COBOLNET0863s appear.

## The rule

`cite.py --check 12.4.5.12.3 "Data-name-1 and data-name-2 shall not be subject to any OCCURS clauses"` → OK 1);
the ALTERNATE RECORD KEY (§12.4.5.6.3 SR1) and RELATIVE KEY (§12.4.5.13.3 SR1) clauses carry the identical sentence.
They are syntax rules of the FILE-CONTROL entry: the entry violates them whether or not a statement references
the file, and §4.2.2's mechanism must be able to indicate it.

## Fix

Move the screen to the entry: `DataBinder.ResolveFiles`, the post-build pass that already resolves these keys and
already enforces one file-control syntax rule there (`ResolveAssignUsing`, §12.4.5.2 SR7 — PB324's precedent), so
every declared keyed file is screened once at bind regardless of verbs; `KeyedValidateFile`'s `_keyedCheckedFiles`
memo and its verb-driven callers then either go (one rule, one place) or keep only the verb-level rules that
genuinely belong to a statement. Blast radius: every program declaring a keyed file is newly screened — the corpus
sweep (NIST IX/RL programs) before it lands. Negatives at four editions with OPEN/CLOSE only.

## Sibling 2026-09-05 (PB692 implementer): §12.4.5.2 SR10, enforced under the wrong citation and on a verb

`KeyedIoBinder.cs` ≈360 rejects a relative file with ACCESS RANDOM/DYNAMIC and no RELATIVE KEY clause citing "§12.4.5.13 — required for random/dynamic access"; §12.4.5.13 has three syntax rules and none requires the clause. The rule is §12.4.5.2 SR10 (cite OK: "The RELATIVE clause shall be specified if the DYNAMIC or RANDOM phrase of the ACCESS clause is specified"). It sits in `KeyedValidateFile`, so an entry violating it with only OPEN/CLOSE in the procedure division draws nothing — this note's exact shape. Move it with the OCCURS bans and fix the citation in the same change (D18, the entry-rule decision, is the design statement).

## Landed 2026-09-06

Reproduced first on today's tree with this worktree's own `cobol.exe` — the note's shape held exactly, and three
more of the same shape were found by probing the rest of the clause family before choosing where the screen goes:

| probe | entry | with only OPEN/CLOSE | with one READ |
| --- | --- | --- | --- |
| 1 | prime + alternate key under OCCURS | silent | 2 × COBOLNET0863 |
| 2 | RELATIVE, ACCESS RANDOM, no RELATIVE KEY | silent | COBOLNET0863 citing "§12.4.5.13" |
| 3 | RELATIVE KEY inside the file's record | silent | COBOLNET0863 citing "§12.4.5.13 SR3" |
| 5 | ALTERNATE RECORD KEY naming a WORKING-STORAGE item | silent at EVERY verb | silent |
| 6 | RECORD KEY naming an undefined item | — | "indexed file 'IXF' has **no RECORD KEY clause**" (false) |

Probe 5 is the worst of them and was not in the note: `DataBinder.ResolveFiles` dropped an unresolvable
ALTERNATE RECORD KEY clause from `FileModel.AlternateKeys` **silently**, so the file was built with fewer access
paths than the entry declared and every index-aligned list downstream (`AlternateKeyCollations`, the emitter's
key registration, `AltName`'s "a name that failed to resolve has already errored" comment) was out of step with
the written clauses.

**The fix is the structure, not the move.** `src/Cobol.Net.Compiler/Binding/FileControlKeyRules.cs` is ONE table
— one row per rule, carrying its inventory rule-id, its clause, a verbatim span of the printed rule, the
ORGANIZATION whose §12.4.5.1 format carries the clause, the key ROLE, and three predicates — screened from
`DataBinder.ResolveFiles` once per declared file. An ABSENT clause is an operand with a null name, so
"clause required" and "operand breaks a rule" are the same kind of row and there is no second arm.
`KeyedIoBinder.KeyedValidateFile`, its `_keyedCheckedFiles` memo and all five verb call sites are DELETED;
one-report-per-file is now a consequence of where the screen runs. Design statement: `COBOLNET_FILES_DESIGN.md`
**D19** — which PB692 opened on train 14 for the same decision (an entry rule is enforced on the ENTRY, the
converse of D13) while this was being written. The two were MERGED into one section rather than left as two D19s,
which would have been the very duplication the decision is about: PB692's §12.4.5.5.2 SR2 screen stays inline in
`BindFileControl`, this table lives in `ResolveFiles`, and D19 now states the criterion that decides which of the
two a new entry rule joins — *decidable from the clauses alone* versus *needs a resolved data item*.
`FileControlKeyRuleDriftTests` re-derives every row from `specs/ISO_COBOL.md` — clause region AND printed
ordinal — and asserts the table and the traceability inventory name the same rule set, so the next key rule is a
row rather than a new `if`.

Two citations repaired in the same change (`cite.py --check 12.4.5.13 "shall reference an unsigned integer data
item"` FAILS — §12.4.5.13 carries no syntax rules at all): the required-clause rule is **§12.4.5.2 SR10**, and
the unsigned-integer / not-in-a-record rules are **§12.4.5.13.3 SR2 and SR3**.
