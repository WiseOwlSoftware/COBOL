# PB699 — OPEN — an entry rule that waits for a verb

Found 2026-09-05 by the `PB352`/`PB354` implementer (report §"New defects" b), measured: a program with
`RECORD KEY IS IX-KEY` and `ALTERNATE RECORD KEY IS IX-ALT` both under OCCURS, whose PROCEDURE DIVISION does only
OPEN INPUT and CLOSE, draws zero diagnostics; adding one `READ IXF NEXT` makes both COBOLNET0863s appear.

## The rule

`cite.py --check 12.4.5.12.3 "Data-name-1 and data-name-2 shall not be subject to any OCCURS clauses"` → OK 1);
the ALTERNATE RECORD KEY (§12.4.5.6.3 SR1) and RELATIVE KEY (§12.4.5.13.3 SR1) clauses carry the identical sentence.
They are syntax rules of the FILE-CONTROL entry: the entry violates them whether or not a statement references
the file, and §4.2.2's mechanism must be able to indicate it.

## Fix

Move the screen to the entry: `DataBinder.ResolveFiles`, the post-build pass that already resolves these keys and
already enforces one file-control syntax rule there (`ResolveAssignUsing`, §12.4.5.2 SR7 — PB324's precedent), so
every declared keyed file is screened once at bind regardless of verbs; `KeyedValidateFile`'s `_keyedCheckedFiles`
memo and its verb-driven callers then either go (one rule, one place) or keep only the verb-level rules that
genuinely belong to a statement. Blast radius: every program declaring a keyed file is newly screened — the corpus
sweep (NIST IX/RL programs) before it lands. Negatives at four editions with OPEN/CLOSE only.
