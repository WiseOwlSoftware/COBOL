# PB5529 - numeric-literal digit capacity is asked only for a procedure-division literal at the binder: VALUE OF ID IS 1234567890123456789 compiles at --std 85 and a 32-digit literal in any data-division position reaches no 31-digit check

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/ExpressionBinder.cs` (`ExpressionBinder.CheckLiteral`, line 1402; the per-position call is deleted), `src/WiseOwl.Cobol.Compiler/Binding/EditionContext.cs` (`EditionContext.CheckDigitCapacity`), `src/WiseOwl.Cobol.Frontend/Parsing/LiteralScreen.cs` (`LiteralScreen.Run`, `LiteralScreen.NumericLiteralOf`, `LiteralScreen.ScreenDigitCapacity`: asked of the literal NODE, not the token, since a digits-only word is an INTEGERLIT too and a comma-decimal literal is three tokens), `src/WiseOwl.Cobol.Editions/EditionInfo.cs` (`EditionInfo.DigitCapacityExcess`, the one 31/18 split)

**Mechanism.** The edition's digit limit (COBOL0802 at 85) is asked per position, in the procedure division only, by `ExpressionBinder.CheckLiteral`. A literal's digit count is a property of its token, so a position that does not pass the expression binder is never asked: at `--std 85` `VALUE OF ID IS 1234567890123456789` (19 digits) compiles, and a literal of 32 or more digits in any non-procedure position (VALUE, level-88, CONSTANT, ALL) at any edition reaches no check against the 31-digit limit of the standard's numeric literal rule (§2023:8.3.3.3.2; the review's quotation was too short for `cite.py --check`, so the clause is named, not quoted, and must be re-derived before it is). The 85 case is consistency with the implementation's own limit, not a 1985 violation (18 digits is the least a 1985 implementor must allow, §1985:IV.4.2.2.2.2, not re-checked here), as PB5416's held-row adjudication settled.

**Fix direction.** Ask the capacity once at the token, in `LiteralScreen`, where PB4979-era position-blind literal rules already live, and delete the binder's per-position call; same family as PB5416's root (a position-scoped literal rule), a separate mechanism. Witnesses: the 19-digit VALUE OF at 85, a 32-digit VALUE at 2023.

**Found by.** `E:/COBOL-coord/scratch/reports/w20262029c-PB5416-report.md`, "New defects", first item; a redesign of the ExpressionBinder check, outside PB5416's group.

**Landed (w20262039b).** The capacity is asked in `LiteralScreen.Run` of every `numericLiteralCore`, `integerLiteral` and `signedIntegerLiteral` node (fixed-point only), under the one descriptor choice `EditionInfo.DigitCapacityExcess` (COBOL0801 over 31, COBOL0802 over 18 at 85, the same codes as before); the binder's per-position call in `ExpressionBinder.CheckLiteral` is deleted and `EditionContext.CheckDigitCapacity` keeps only the PICTURE subject. Re-probe before: `VALUE OF ID IS 1234567890123456789` at `--std 85` compiled clean; a 32-digit level-88 VALUE drew only COBOL1625. After: COBOL0802 and COBOL0801. Left open (a separate lane): `CompileTimeExpressionEvaluator.WithinLiteralCapacity` still asks the same question of a CONSTANT or directive operand (a CONSTANT literal over 31 digits draws COBOL1547 beside COBOL0801), and a VALUE over capacity also draws the range check's COBOL1625.
