# PB951 — OPEN — one synonym, three productions, one spelling

## Repro — measured, both spellings, same program shape

`scratchpad/reg9/probe/rplus2.cob` and `rword2.cob` (PROGRAM-IDs `R9RPLUS2` / `R9RWORD2`), identical but for the
operand spelling, `cobol.exe <file> --std 2023`:

```
       01  DET-P TYPE DE.
           02  LINE + 1.                                  *> and: LINE PLUS 1.
               03  COLUMN 1 PIC X(1) VALUE "X".
               03  COLUMN + 2 PIC X(1) VALUE "Y".         *> and: COLUMN PLUS 2 …
```

```
$ cobol.exe rplus2.cob --std 2023
  rplus2.cob(13,21): error COBOL0001: unexpected '+'
  rplus2.cob(15,27): error COBOL0001: cannot parse construct near '+'

$ cobol.exe rword2.cob --std 2023
  (no diagnostic, exit 0)
```

The word form compiles; the symbol form is a raw parse error, and the user is told about a TOKEN, not about a
facility. The third clause is the same: `rplus.cob` adds `NEXT GROUP + 2` and draws a third
`COBOL0001: unexpected '+'` at (12,37) — but see **THE NEXT GROUP LEG IS BEHIND PB957** below.

The general formats agree. `specs/ISO_COBOL.md` §13.18.35.2 Format 1 (report-writer) prints
`╭ PLUS ╮ / ╰ +    ╯` as a nested brace pair, and its figure note — a measurement of the printed page — says
*"Within the second alternative, `PLUS` and `+` are a nested brace pair (synonyms, one required)."* §13.18.14.2
Format 1 prints the same pair and its figure note records *"re-rendered at 600 dpi and confirmed to carry no
choice-indicator bars"*; §13.18.37.2 prints it for NEXT GROUP.
⚠ **The fixer still renders the page before writing the grammar** (`scripts/render-spec-page.py`) — CLAUDE.md
rule 1's diagram rule. The SR text alone is dispositive for THIS defect (a synonym is a synonym however the
brace is drawn), which is why the note does not wait on a render; the render decides the *shape* of the
alternation the fixer writes, not whether `+` is legal.

## The code site — one file, three productions

`src/Cobol.Net.Frontend/Grammar/Core/CobolReportWriter.g4`:

```
:137  reportLineOperand    : PLUSWORD integerLiteral | … ;
:145  reportNextGroupClause: NEXT GROUP IS? (PLUSWORD integerLiteral | integerLiteral | NEXT PAGE) ;
:158  reportColumnOperand  : PLUSWORD? integerLiteral ;
```

`CobolLexer.g4` already carries BOTH tokens — `PLUSWORD : 'PLUS' ;` (:690) and `PLUS : '+' ;` (:962) — so the
fix is an alternation per production, not a lexer change. ⭐ **One synonym written down three times is the
defect** (`feedback_one_rule_one_place`): the durable shape is ONE fragment — e.g.
`relativeSign : PLUSWORD | PLUS ;` — referenced by all three, so the next report clause that takes a relative
operand cannot be written with one spelling. A hand-repeated `(PLUSWORD | PLUS)` at three sites reproduces the
defect's own cause.

## ⛔ THE SCREEN-SECTION HALF OF THE LEAD IS FALSE — DO NOT SWEEP IT

Both the PB484 report and the train-44 lander report name *"the screen-section twin in `CobolScreen.g4` (same
pair, plus MINUS / en-dash)"* as part of this mechanism. **It is not.** Measured on this tree,
`CobolScreen.g4:84/:90` already admit all four:

```
screenLineClause   : LINE NUMBER? IS? (IDENTIFIER | PLUS | PLUSWORD | MINUS)? (dataReference | integerLiteral) ;
screenColumnClause : (COLUMN|COL|COLUMNS|COLS) NUMBER? IS? (IDENTIFIER | PLUS | PLUSWORD | MINUS)? … ;
```

and the file's own comment records why `IDENTIFIER` stands where the WORD `MINUS` would (there is no lexer token
for it; the SCREEN module is declined, so everything this rule matches is refused by name at bind). The screen
formats are §13.17.2 Format 2, which prints `MINUS` / `–` as well — and the REPORT format prints neither. Two
different clauses, two different sign vocabularies: the report-writer LINE/COLUMN/NEXT GROUP operands admit
`PLUS` / `+` only. A fixer who sweeps `CobolScreen.g4` from this note is editing a file that is already right.

## The sibling sweep the fixer owes

   `src/Cobol.Net.Frontend/Grammar/Core/*.g4`; today that is exactly the three productions above plus the
   screen pair.
2. A golden at the introducing edition with the `+` spelling in all THREE positions, and the word spelling

   claim, not a parse claim — the fix is only complete if `LINE + 1` and `LINE PLUS 1` produce the same
   placement, which means a positive golden, not a compiles-clean assertion).
3. ⭐ A drift test that asserts every production naming `PLUSWORD` also names `PLUS`, so the next clause cannot
   regress to one spelling. That is what makes the NEXT case automatic (CLAUDE.md rule 5).
