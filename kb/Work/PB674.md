# PB674 — LANDED — a gate that could only be guessed (all three constructs now gated or discharged)

Found 2026-09-05 by the `PB324` implementer (report §"New defects" 2 and 3), which bound the USING phrase for the
first time and had to decide whether to gate it. `blocked: true` because the derivation needs ISO/IEC 1989:2002,
which is not in the tree — the acquisition question [[R28]] already holds for the owner, and [[A1]] and [[PB296]]
record the same dependency for other clauses; `blocked_by` is empty because the blocker is a document, not a note.

## The facts

- §9.1.21 *Dynamic file assignment* (`cite.py --check 9.1.21 "Dynamic file assignment"` → OK) is a concepts clause
  with no edition marking; §12.4.5.2 / §12.4.5.3 carry no FLAG-02 note. The 1985 ASSIGN clause is
  `ASSIGN TO implementor-name-1 …` and the dynamic-assignment facility sits with the 2002-era additions, so the phrase
  is very probably a 2002 introduction — but "very probably" is a hunch, and a gate built on it REJECTS LEGAL SOURCE
  at `--std 85` if the hunch is wrong (CLAUDE.md rule 1 makes the standard the only authority).
- `docs/VERSION_CHANGE_REFERENCE.md` says in its own scope banner that there is no 85→2002 row set and that an
  85↔2002 difference must be derived from the 2002 standard; neither `docs/ISO2023_CONFORMANCE_PLAN.md`'s post-85
  feature catalog nor the version matrix's `introducedIn` tags mention the phrase; `tests/version-matrix/constructs.json`
  has no row for it.
- The implementer therefore did NOT gate it. The compiler accepts the phrase at every edition (the grammar's standing
  superset posture), and `conformance:85/pb324_assign_using_85` pins that acceptance so the decision is visible
  rather than accidental. That golden is a DECISION pinned green — the shape that held a gap open before — and
  must be retired the day the gate lands.

The third face is the one worth the owner's eye: the missing 85→2002 row set is load-bearing. PB324 is the first
case where the absence changed an implementation decision rather than merely slowing one down, and every implementer
who meets an 85↔2002 boundary pays the same discovery cost independently. The four-per-edition-compilers mission
(D13) cannot be finished without the 2002 (and 2014) texts; the doc's own remedy sentence names the fix.

## Fix (once the 2002 text is available)

One `constructs.json` row (`file-assign-using-2002`), one `VersionConformancePass.ParseArm.VisitAssignClause`
predicate firing on the USING child (`src/WiseOwl.Cobol.Frontend/Grammar/Core/CobolIO.g4#assignClause` has both
alternatives), the edition-gate test sweep (gating a construct breaks everything that compiles it below that
edition — sweep the corpus), and the 85 golden converted into a reject case. If the 2002 text shows the phrase is NOT a 2002 introduction, close this note with that citation and
keep the golden.

## Landed 2026-10-17 — wave 1115 group F (the two registrar #13 constructs)

- **START … KEY IS LESS THAN / `<=`: already gated, DISCHARGED.** `START F KEY IS LESS THAN K` and `START F KEY IS <= K` draw
  COBOL0900 ("a reverse-search START KEY operator … requires COBOL-2002"). They landed as kb/Work PB370
  (`start-reverse-operators-2002`, `VersionConformancePass.VisitStartKeyPhrase`, commit 8cad904e5 and its goldens

  `pb370_read_relative_invalid_key`). The registrar's 2026-09-23 probe predates that landing. Not by the R61 dialect-file
  method (GnuCOBOL's `cobol85.conf` carries no key for START operators) but by §14.9.41.4 GR9 b) / GR17 d) and §A.3 item 39.
- **The floating-point numeric literal: under-reject CONFIRMED, FIXED.** `COMPUTE R = 1.5E2` compiled and ran at `--std 85`
  (`0015000` for `PIC 9(5)V99`; the note's `0150000{` was a signed picture). New construct `floating-point-literal-2002`
  (`constructs.json`, VCR row 7.37), COBOL0900 below 2002, also under `--permissive` (an introduction).
  - **Dating (derived, not quoted — the R61 method gave no date, as the 2026-10-05 section hoped it might).** GnuCOBOL 3.2
    accepts the literal at `-std=cobol85` and has no dialect key for it (probed: `cobc -std=cobol85|cobol2002|cobol2014`
    all compile it) — silence, not evidence. The evidence is: IBM's Enterprise COBOL Language Reference lists "Floating-point
    numeric literals" among its IBM EXTENSIONS (beyond the standards it conforms to, the 85 Standard first) and its list of
    2002/2014 standard features has no row for them; none of the 459 NIST CCVS-85 programs writes one; every conformance
    case that writes one was already filed at 2002 or later; the traceability inventory's own `editions` column for
    SR-8.3.3.3.3-1..4 and GR-8.3.3.3.3-5 already read `2002,2014,2023`. The 2002-versus-2014 split is not derivable in-repo,
    so the row takes the provisional 2002 edge (rows 7.31/7.36's reasoning). Overturn in one line when a 1985 or 2002 text is read.
  - **The mechanism (one site, structural).** The gate is asked of the TOKEN in `LiteralScreen.Run` (`GateFloatingPoint`),
    over the new `LiteralTokens.FloatingPointTypes` (`FLOATLIT`, `COMMA_FLOATLIT`; the `FN_SIGNED_*` twins are re-typed to
    them by the lexer), the same position-blind walk that gates the hexadecimal and zero-length literals, so a COMPUTE
    operand, MOVE source, VALUE, level-88 VALUE, relation operand, PERFORM VARYING value and FUNCTION argument are one
    question (probed: six positions, six COBOL0900) and the next grammar position needs no arm. `LiteralScreenDriftTests`
    pins the token set to the lexer's `FLOAT*_BODY` fragments and the construct to one reporting site.
  - **Siblings swept.** Fixed-point literals over 18 digits are already gated (COBOL0802 at 85, probed); the floating-point
    USAGEs and the floating-point numeric-edited PICTURE are their own rows; the other arm of the START half (the forward
    operators NOT LESS / NOT `<`) stays legal at 85 by GR9 a) / GR17 c) and is pinned by PB370's golden.
  - **Corpus effect.** One case moved: `wiseowl/cases/_unassigned/pb248_integer_arg_float_admitted` was `accept: [85]` and
    writes `6.5E1`; it now accepts from 2002. Goldens `8.3.3.3.3-Floating-point-numeric-literals/pb674_floating_point_literal_2002`
