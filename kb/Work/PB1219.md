# PB1219 — OPEN

## Measured

**code-set-clause** — The CODE-SET SR3 a/b record-item screen (DataBinder.CheckCodeSetRecordItems) walks file.Records, which since kb/Work PB345 also holds the IMPLIED record MaterializeImpliedRecord synthesizes for an FD with no record description entries (14.9.30.4 GR6); and BindCodeSetClause sets file.CodeSetRecordClass = (alphabet-name-2 present) unconditionally, even when records.Count == 0. So SR3, whose whole antecedent is 'If there are record description entries associated with the file', is applied to a file that has none, and a legal CODE-SET naming alphabet-name-2 (alone, or with alphabet-name-1 - the combination 13.18.13.4 GR4's second sentence exists for) is refused.

- **Repro:** SPECIAL-NAMES. ALPHABET A-EBC IS EBCDIC ALPHABET N-U FOR NATIONAL IS UTF-16. ... SELECT FN ASSIGN TO "x.dat" ORGANIZATION IS SEQUENTIAL. ... FD FN CODE-SET IS A-EBC N-U RECORD CONTAINS 5 CHARACTERS.  (no 01)  ... OPEN INPUT FN READ FN INTO X CLOSE FN.  --std 2023 -> error COBOLNET1672: CODE-SET: the record item 'FILLER' is not usage NATIONAL ... (ISO 13.18.13.3 SR3 b). Same with 'CODE-SET FOR NATIONAL N-U'. Control: 'CODE-SET IS A-EBC' alone compiles and runs (NOREC-READ=[AB012] after writing AB012 through an EBCDIC FD). Probe files p3.cob / p5.cob / p4.cob under out13/probe/code-set-clause.
- **Expected (spec):** 13.18.13.3 SR3 (--check OK): 'If there are record description entries associated with the file and no SELECT WHEN clauses are specified, either alphabet-name-1 or alphabet-name-2 may be specified, but not both; and: ... b) if alphabet-name-2 is specified, all elementary data items of all record description entries associated with the file shall be described as usage national' - no record description entries, so neither the not-both sentence nor a)/b) applies and the clause is legal. 13.4.5.3 SR3 makes such an FD legal for a sequential/relative file; 13.18.13.4 GR4 sentence 2 (--check OK) expressly contemplates it. The program should compile; READ FN INTO X proceeds per 14.9.30.4 GR6 (--check OK) as though one alphanumeric group record were described, whose alphanumeric data on the medium is in alphabet-name-1's set (13.18.13.4 GR2, --check OK), so after writing AB012 through an EBCDIC-coded FD the READ INTO yields X = 'AB012'.
- **Observed:** Observed with the pinned cobol.exe: p3 (both alphabets) and p5 (FOR NATIONAL only) fail to compile with COBOLNET1672 naming a FILLER item the program never wrote - the implied record. BindCodeSetClause's own not-both check correctly reads the PASSED 'records' list (real entries only, count 0), but the class it hands on (CodeSetRecordClass) and the deferred screen both read the file model, where the implied record sits beside real ones. Two readers of 'the file's record description entries' disagree - the one-rule-two-places shape. Sibling to sweep: any other FD screen that iterates file.Records to enforce a rule conditioned on the PRESENCE of record description entries (e.g. 13.4.5.3 SR-family, REDEFINES/record-size screens) must distinguish written from implied records.
- **Code site:** src/Cobol.Net.Compiler/Binding/DataBinder.CodeSetRecords.cs#CheckCodeSetRecordItems (line ~50); src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindCodeSetClause (file.CodeSetRecordClass assignment, ~line 5054); src/Cobol.Net.Compiler/Binding/DataBinder.cs#MaterializeImpliedRecord (file.Records.Add, line 1652)
