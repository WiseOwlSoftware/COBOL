# R07 — `GOBACK … RAISING` carries no location at all (`BoundRaising` has no such field, unlike its sibling `BoundRais

`GOBACK … RAISING` carries no location at all (`BoundRaising` has no such field, unlike its sibling `BoundRaise`)

> Migrated from the fix queue's RESIDUE block, which never itemised these — so no work list could see them.

## ▶ TRIAGE (2026-08-06) — `wrong_answer` + `silent`, MEASURED

Flagged while fixing the ranker that had been hiding items with no harm flag ([[PB48]]'s sweep).

**What the missing field costs, traced rather than assumed.** `BoundRaise` carries `WithLocation` and
`Location` (`BoundTree.cs`), which `EcEmitter` writes into the run-unit last exception status; that status is
exactly what `FUNCTION EXCEPTION-LOCATION` (§15.30) and `EXCEPTION-STATEMENT` (§15.32) interrogate, and
`EcFunctions.Location`'s own comment records the fallback: "one space when no location information was saved".
`BoundRaising` — the RAISING phrase of GOBACK / EXIT PROGRAM / method return — has no such field at all.

So with `>>TURN … CHECKING ON WITH LOCATION` in effect, a `GOBACK … RAISING EC-…` saves no location and the two
intrinsics return the no-location answer. The program runs, prints a space, and says nothing: **a silently wrong
answer, not a crash** — which is why the flags are `wrong_answer` + `silent` and not `crashes`.

⚠ THREE call sites construct a `BoundRaising` (`EcBinder.EcBindRaising`, its LAST arm, and
`OoBinder.OoBindMethodRaising`) and THREE statements carry one (`BoundGoback`, `BoundExitProgram`,
`BoundMethodReturn`) — [[feedback_two_arm_dispatch]]: adding the field is the easy half.
