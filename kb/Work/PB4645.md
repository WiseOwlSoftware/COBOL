# PB4645 - lead from a landed branch's report

**Sites:** `src/WiseOwl.Cobol.Frontend/Parsing/CobolErrorStrategy.cs` (`CobolErrorStrategy.ResidueRefusal`), `src/WiseOwl.Cobol.Frontend/Cst/ClosedFormats.cs` (`ClosedFormats.OwnerName`)

Misleading-lite, MINOR; pre-existing on the Nov 3 binary. ResidueRefusal uses ClosedFormats.OwnerName(recognizer.Context). Same mechanism as any prediction that fails ahead of the parser. Repro as reported, not re-run.

## Landed (wave 20261868 group E)

Re-probed on a fresh build: `01 W-A MOVE.` and `01 W-A TO.` drew COBOL1941 "'MOVE' is not a clause of the data description entry" with no `for 'W-A'`, while `01 W-A PIC X MOVE.` named W-A. Root cause: the decision at the entry's optional name looks ahead past W-A and dies at MOVE with the parser still before the name, so the context's `dataName()` is not attached and `ClosedFormats.OwnerName(recognizer.Context)` is null. Fix: `OffendingPosition.OwnerName()` is the context's name, and where none is attached the word written after the level-number when only the data-name rule can begin it (`ClosedFormats.EntryNameOnlyWords`, read from the ATN: FIRST(dataName) less the clause starts, the error production's opening not counted) and the parser has not passed it; `ResidueRefusal` calls it. A word that is also a clause start (`01 USAGE DISPLAY MOVE.`) stays unnamed (ambiguous reading). FD, SD and SELECT names are mandatory and attached before any lookahead fails (probed). Goldens: `conformance-suite/cases/13.16-Data-description/pb4645-clause-word-after-an-entry-name` (refused at all four editions, the expected sentence carries `for 'W-A'`); unit `ClosedFormatReservedWordTests.ReservedWordAfterANameOrAClause_IsStillNotAClause` (W-A, FILLER, a level-05 entry, and two unnamed controls). Design: `DESIGN-frontend-grammar.md`, "The entry-name slot".
