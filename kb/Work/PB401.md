# PB401 — a range check that can only fire when it is least needed

## 1. The mechanism

`EvaluateBinder.cs:220-227` routes a THRU pair to `BoundRangeMembership(CheckInvalid: true)` only when

    ctx.EcState.Turn.Enabled("EC-RANGE-INVALID", null, item.Start.Line)
    && lo is BoundStringLiteral { Category: PicCategory.Alphanumeric or PicCategory.National }
    && hi is BoundStringLiteral

Every other range — identifier ends, arithmetic-expression ends, a literal paired with an identifier — falls
to the plain relation pair `left >= lo && left <= hi`, which produces the empty-range BEHAVIOUR that 14.7.8
rule 2 also requires but sets **no exception condition**. So the exception can be raised only in the one case
where a reader of the source can already see the inversion, and never in the case where the bounds are not
known until execution.

The gate is deliberate and the comment above it says so — the rule is read as scoped to LITERAL
alphanumeric/national ranges. That reading is defensible on 14.7.8's own wording, which names literal-1 and
literal-2, and 14.7.8 is shared with the VALUE clause where the endpoints really are literals. **Two things in
the standard point the other way and were not weighed:**

1. The EC sentence of 14.7.8 rule 2 is conditioned on the collating sequence **in effect at runtime** — a
   phrase with no work to do when both ends are compile-time constants.
2. The exception-condition table at 14.6.13.1.6 defines EC-RANGE-INVALID by VALUES, not by operand form.

And 14.9.13.4 GR2 delegates the EVALUATE range wholesale to 14.7.8 while 14.9.13.2's range-expression figure
admits identifier-3/identifier-4 and arithmetic-expression-3/-4 as freely as literal-3/literal-4. Reading rule
2's "literal-1/literal-2" as *excluding* identifiers therefore leaves an identifier-ended alphanumeric range
with no defined collating semantics AND no exception — the one shape where the user cannot see the inversion
by reading the source.

## 3. Expected vs observed — RE-MEASURED ON HEAD (89044aa0)

    $ cobol.exe p26-ec-range-idfirst.cob --run
      BASE=[                               ]
      ID-STATUS=[                               ]
      LIT-STATUS=[EC-RANGE-INVALID               ]                                                [exit 0]

The program declares `01 WS-X PIC X VALUE "C". 01 WS-LO PIC X VALUE "M". 01 WS-HI PIC X VALUE "A".` and, under
`>>TURN EC-RANGE-INVALID CHECKING ON`, runs the IDENTIFIER range `EVALUATE WS-X WHEN WS-LO THRU WS-HI` first
and the LITERAL range `EVALUATE WS-X WHEN "M" THRU "A"` second, printing `FUNCTION EXCEPTION-STATUS` after
each.

**ORDER MATTERS and it is why this defect was nearly missed.** `FUNCTION EXCEPTION-STATUS` is sticky, so the
identifier case must be probed FIRST. The first version of the probe put the literal case first and reported
EC-RANGE-INVALID for both — the sticky carry-over of the literal case's own exception, and no evidence about
the identifier case at all. This is `probe_the_shape_the_subject_hides` exactly: the axis the subject held
fixed had to be flipped before the answer changed.

Expected under the 14.6.13.1.6 reading: both statements have a starting value greater than the ending value in
the runtime collating sequence, so each shall set the nonfatal EC-RANGE-INVALID and each shall then proceed as
if the range were empty; `ID-STATUS` and `LIT-STATUS` shall both read EC-RANGE-INVALID. Expected under the
literal-only reading of 14.7.8 rule 2: only `LIT-STATUS` is required.

The empty-range BEHAVIOUR is correct in both cases — both fall to WHEN OTHER — so the divergence is confined
to the exception condition, which is why the harm is silent rather than a visibly wrong branch.

## 4. The code site and the shape of the repair

- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs:220-227` — the EC gate, with the
  literal-only scoping stated in the comment above it.
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.cs:507` — the EC-RANGE-INVALID carrier remark.
- `CobolString.ThruMember` — the runtime carrier that already computes the inversion at execution time.

**⛔ THIS ROW NEEDS AN OWNER DECISION BEFORE IT NEEDS A DIFF**, and the note is filed open (rather than as a
recorded determination) because the current state is not a *chosen* reading — it is a scope that was set for
one reason and now covers the complement of the case the rule describes. The two coherent resolutions are:

1. **Widen the carrier** to any range whose operands are of class alphanumeric or national, evaluating the
   inversion at run time through `ThruMember` for identifier and arithmetic-expression ends as it already does
   for literals. This is the reading 14.6.13.1.6 and the "in effect at runtime" clause support, and it makes
   the literal case a compile-time-constant special case of the general one rather than the only case.
2. **Record the literal-only scope as a deliberate, cited interpretation** in CONFORMANCE.md, with the
   14.7.8 literal-1/literal-2 wording as its ground and the identifier case named as out of scope.

Either way the current state should not stand unexamined. If (1) is chosen, the shape is a **single
range-admissibility/ordering helper** shared with PB399's class screen and PB398's `IN alphabet-name` thread,
so that the alphabet, the class screen and the EC all attach to one place per range — not three gates asking
three different questions about the same pair.

## 5. The sibling sweep the fixer must do

- **The VALUE clause's THROUGH phrase** takes the same 14.7.8 specification. Whatever scope is chosen for
  EVALUATE has to be the same there, or the one clause that governs both is implemented twice with two answers.
- **`>>TURN` is consulted at BIND time** here (`ctx.EcState.Turn.Enabled(..., item.Start.Line)`), so the gate is
  a static decision even in the widened form; check that a `>>TURN` toggled between two EVALUATE statements in
  one paragraph is honoured per statement.
- **The second missing half of this row is PB398's**: `IN alphabet-name` does not parse, so the sentence of
  14.7.8 rule 2 that names the alphabet's collating sequence is unreachable. Fixing the EC scope without the
  alphabet still leaves the row PARTIAL; the two land together or the row does not move.
- Check the NOT form (`WHEN NOT lo THRU hi`) under the widened gate — GR4 a) 5. inverts the pair to
  `< lo OR > hi`, and the EC is a property of the RANGE, not of the polarity.

## 6. Rows

- **`GR-14.9.13.4-2`** (PARTIAL) — 14.7.8 rule 1 (numeric range, no EC) and rule 2's empty-range outcome are
  realized; two halves of rule 2 are not. (a) the EC is raised only for a string-literal pair, measured above;
