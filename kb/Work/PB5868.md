# PB5868 - after kb/Work PB5856, ACCEPT's decimal conversion still gives a different value by USAGE for text that is invalid past the digits

Noticed on Monday 2026-11-16 by the Mythos lane, sampling the branch of kb/Work PB5856 (`worktree-agent-a3e3e24bad26d7d68`, head 7ea727991c; its implementer registered the same point in its report).

kind: analysis. No harm flag. Severity: MINOR. area: runtime/accept. related: PB5856, PB3513, PB3573.

## What was measured
`E:/COBOL-coord/scratch/my-20261115/accept-comp/acc7.cob` on that branch's build, at `--std 85`, each ACCEPT given the input line `12.50CR`:
- `PIC 9(5)V99` (DISPLAY): `D7=[00012.50]`
- `PIC 9(5)V99 COMP`: `C7=[00000.00]`
- `PIC 9(5)V99 COMP-3`: `K7=[00000.00]`
The window is the same seven characters for all three (that is what PB5856 fixed). The conversion of those characters is not: an item stored as characters stops reading when its last digit position is filled, so the `CR` is never examined; a binary or packed item reads to the end of its window, finds a letter, and holds the whole text invalid, which stores zero.

The program (`acc7.cob`, with its input file `in7.txt`, three lines of `12.50CR`):

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. ACC7.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       77  D7 PIC 9(5)V99.
       77  C7 PIC 9(5)V99 COMP.
       77  K7 PIC 9(5)V99 COMP-3.
       PROCEDURE DIVISION.
       P1.
           ACCEPT D7.
           DISPLAY "D7=[" D7 "]".
           ACCEPT C7.
           DISPLAY "C7=[" C7 "]".
           ACCEPT K7.
           DISPLAY "K7=[" K7 "]".
           STOP RUN.
```

## Why it is not a defect today
The conversion is the implementor's (the ACCEPT rule says "Any conversion of data required between the hardware device and the data item referenced by identifier-1 is defined by the implementor", `§1985:VI.6.5.4 GR1`; cite.py OK), the text is invalid for every usage, and the register states both behaviours: A.1 item 1, points (c) and (d), as the branch of PB5856 rewrote them, after the forms kb/Work PB3513 measured from GnuCOBOL.

## Why it is worth a decision
- The two behaviours were taken from GnuCOBOL when a binary or packed item read the whole record, as GnuCOBOL's does. PB5856 gave every usage the same window because the standard's rule on the size of the transfer requires it, so the binary and packed arm no longer matches GnuCOBOL either: the reason for two conversions is gone and the difference is now this implementation's own.
- A program that changes an item from DISPLAY to COMP-3 changes what an ACCEPT of the same line stores. One conversion of the window's characters, the same for every usage, would remove that, and the register would state one rule.
- What a decision must weigh: which of the two rules the one conversion takes for invalid text (stop when the digits are filled, or invalid as a whole), and the sibling asymmetry of point (d) (surplus leading characters).
