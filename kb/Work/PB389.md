# PB389 — a scalar where the standard prints a tuple, and fifteen rules with nowhere to live

## THE MECHANISM

`§13.18.60.2` prints the OBJECT REFERENCE operand as a choice of three shapes over four independent axes —
**KIND** ∈ {universal, interface-name-1, object-class-name-1, ACTIVE-CLASS} × **FACTORY** present/absent ×
**ONLY** present/absent × the name itself. The compiler models ONE axis. `PicInfo.ObjectClassName`
(`src/Cobol.Net.Compiler/Binding/Model/PicInfo.cs:345`) is a single nullable string: null means universal,
non-null means "some name", and the KIND is *re-derived downstream* by asking the class table twice
(`OoConformance.cs:378` `FindInterface(recvName)`, then `:405` `Find(sendName)`). The grammar matches that
scalar exactly — `src/Cobol.Net.Frontend/Grammar/Core/CobolOO.g4:184-188` is

```antlr
objectReferenceUsage
    : OBJECT REFERENCE FACTORY OF className   // binder-staged COBOLNET0899
    | OBJECT REFERENCE className
    | OBJECT REFERENCE
    ;
```

— no ACTIVE-CLASS alternative, no trailing ONLY. **This is the `model_the_rule_shape_not_one_case` shape**: a
scalar column where the rules name a tuple. It costs three distinct things: (1) ACTIVE-CLASS and ONLY are
**legal COBOL-2002+ that the compiler rejects**; (2) every SET Format-5 syntax rule that DISCRIMINATES on an
unmodelled axis is unlocated — nothing in `src/` cites SR10c, SR12a1, SR12a3, SR12b, SR12c1, SR12c4 or SR14;
(3) the FACTORY-presence rules are not merely absent, they are *protected only by a rejection* — the day the
FACTORY-OF wave lands, `OoConformance.cs:381`'s hard-wired `ImplementsClosure(sc, factory: false)` silently
answers b2's question for b1, and no `PicInfo` field exists to compare FACTORY presence at all.

The same scalar reaches the EXIT/GOBACK RAISING lane through a second door: `raisingClause` is
`RAISING cobolWord+`, so §14.2.1's `[ FACTORY OF ]` in the procedure-division header is a raw parse error and an
interface-name draws COBOLNET0858 — the identifier end and the header end are BOTH closed, so neither alone can
be opened. On top sits a latent message defect: SR5d/SR4d is tested as `ObjectClassName is not { } declared`
("no class name recorded"), which is true of a factory, interface or ACTIVE-CLASS reference too — so the moment
those land, legal operands get rejected as *"a UNIVERSAL object reference"*, naming a rule the program did not
break.

## THE CODE SITES, AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Frontend/Grammar/Core/CobolOO.g4:184-188` — `objectReferenceUsage`, three alternatives where
  §13.18.60.2 prints five shapes.
* `src/Cobol.Net.Compiler/Binding/Model/PicInfo.cs:345, :351, :403` — the one nullable string.
* `src/Cobol.Net.Compiler/Binding/DataBinder.cs:2349-2352` — `FACTORY OF` → COBOLNET0899, and the item is left
  UNTYPED afterwards, so every later statement mentioning it emits a second, misleading diagnostic.
* `src/Cobol.Net.Compiler/Oo/OoConformance.cs:369-412` (`ObjectRefWideningMismatch`, with `:381`'s hard-wired
  `factory: false`) and `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/OoBinder.cs:855-977`
  (`OoBindSetObjectRef`) — the consumers that re-derive the kind because the descriptor does not carry it.
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.cs#EcBindRaising` — the SR5/SR4 band, including the
  `ObjectClassName is not { } declared` test that stands in for "universal".
* `src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4#raisingClause` — `RAISING cobolWord+`, no `[FACTORY OF]`,
  no interface-name.

**Repair (CLAUDE.md rule 5 — the descriptor, not fifteen checks):**

1. Give the model an explicit `ObjectRefDescriptor(Kind, Name, Factory, Only)` where `Kind` ∈ {Universal,
   Interface, ObjectClass, ActiveClass}. Every consumer then ASKS the descriptor instead of re-deriving the kind
   from the class table, and "universal" stops being spelled "no class name recorded" — which retires the latent
   SR5d/SR4d misdiagnosis in the same change.
2. Teach `objectReferenceUsage` the two missing shapes (`[FACTORY OF] ACTIVE-CLASS`, trailing `ONLY`) and
   `raisingClause` the §14.2.1 header shapes (`[FACTORY OF] object-class-name-1`, `interface-name-1`).
3. The fifteen stranded rules then become table lookups over the descriptor — and the relations they need
   already exist: `OoConformance.ConformsTo` (SR12a2), `cur.ConformsTo(tcls)` at `OoBinder.cs:907` (SR12c2),
   `ImplementsClosure(cls, factory:)` already called BOTH ways at `OoConformance.cs:85-86`, and an ACTIVE-CLASS
   operand's containing class is the `host.OoCurrentClass` the SELF arm already reads.
4. **Pair it with a drift test** asserting every §13.18.60.2 descriptor shape round-trips (declare → bind →
   descriptor → diagnostic), so the next axis cannot be dropped silently.
5. Converge the four refusal STYLES on one named stage while the work is in flight: today the same gap is
   presented as COBOLNET0813+0901 (ACTIVE-CLASS), COBOL0307 (ONLY), COBOLNET0899 (FACTORY OF, PROGRAM-POINTER
   TO, FUNCTION-POINTER). Only the 0899s tell the user the truth.

## THE SIBLING SWEEP THE FIXER MUST DO

* Every consumer of `PicInfo.ObjectClassName` (`grep -n ObjectClassName src/`) — each one is a place where a
  kind is being guessed.
* Every `ImplementsClosure(` call site: `:381` is the one hard-wired arm; `:85-86` shows the correct two-arm
  pattern (`feedback_two_arm_dispatch`).
* The refusal-then-cascade shape: a rejected description leaves the item untyped, so `FACTORY OF` and
  `ACTIVE-CLASS` each produce a SECOND wrong diagnostic downstream. Poison the item on refusal so later sites
  stay quiet — this is a general binder rule, not an OO one; sweep the other `RecognizedNotImplemented` sites.
* The USAGE tail family as a whole (`POINTER TO`, `PROGRAM-POINTER TO`, `FUNCTION-POINTER TO`,
  `OBJECT REFERENCE …`): `POINTER TO` has now landed, which is the template for the other two.

## Rows

Seventeen rows, one mechanism. In one clause each:

* **`SR-14.9.39.3-14`** (NOT-IMPLEMENTED) — SR14's subject is an ACTIVE-CLASS-described identifier-3; the phrase
  has no grammar alternative, measured above.
* **`SR-14.9.39.3-L3.1` / `L3.2`** (SR10 c)1./c)2.), **`L6.1` / `L6.2` / `L6.3`** (SR12 b)1./b)2./b)3.) — all
  need an ACTIVE-CLASS sender; unwritable.
* **`SR-14.9.39.3-L5.1`** (SR12 a)1.) and **`L7.1`** (SR12 c)1.) — both turn on the ONLY flag; `ONLY` is a raw
  parse error, and `ObjectRefWideningMismatch` applies the a)2. SUBCLASS relation unconditionally, which is the
  WRONG rule the moment ONLY lands.
* **`SR-14.9.39.3-L5.3`** (SR12 a)3.) — the FACTORY-presence equality; unviolatable today only because the
  FACTORY description is refused, with no field to compare when it is not.
* **`SR-14.9.39.3-L2.1`** (SR10 b)1.) — the factory closure; `OoConformance.cs:381` can only ever ask b)2.'s
  question. **`L2.2`** (SR10 b)2. + the head of c)) is PARTIAL: b)2. CONFORMS and is measured both ways
  (`sr10b2_class_implements` → PONG; `sr10b2_class_not_implements` → COBOLNET0867; the subclass sender walks the
  closure), while c) has no implementation.
* **`GR-14.9.39.4-9`** (PARTIAL) — the reference-placement semantics are right (a reference not a copy, every
  identifier-3, source order), but SR12 enumerates four alternatives for identifier-4 and the compiler cannot
  EXPRESS two of them, so GR9 can never execute for those operands. Its test-ref `conformance:2002/oo_universal`
  has ONE receiver per statement, so the "each … in the order specified" half is pinned by no shipped test —
  adding a multi-receiver row to that golden closes it.
* **`SR-14.9.14.3-5`** (PARTIAL, EXIT) and **`SR-14.9.18.3-4`** (PARTIAL, GOBACK) — one shared `EcBindRaising`:
  the head, a) and d) are enforced (and pinned for GOBACK by `OoSpineTests.GobackRaising_BindViolations_0849`);
  b) (interface-name) and c) (ACTIVE-CLASS) are unreachable from BOTH ends, measured above. For EXIT
  specifically, c) may be vacuous anyway — SR7 confines EXIT PROGRAM to a program procedure division while
  §13.18.60.3 SR16 confines an ACTIVE-CLASS description to a factory/instance definition or a method's
  linkage/local-storage section; say so when the fix lands rather than writing a screen that can never fire.
* **`SR-14.9.39.3-20`** (NOT-IMPLEMENTED) — FUNCTION-POINTER is refused at declaration (COBOLNET0899, measured
  on HEAD), and Format 8 has no SET arm at all: `BindSetTo`'s category re-routes test Pointer, ProgramPointer and
  ObjectReference and stop, so even a declarable function-pointer would fall into the Format-1 arithmetic store.
* **`SR-14.9.39.3-22`** (NOT-IMPLEMENTED) — `PROGRAM-POINTER TO prototype` is loud-staged (measured on HEAD), so
  identifier-7 can never reference a restricted program-pointer. Note for the lander: SR22's signature test and
  SR20's identical sentence for function-prototypes are ONE rule over two carriers — write it once.
* **`SR-14.9.39.3-24`** (NOT-IMPLEMENTED — **and its harm has INVERTED since the pin**) — the restricted
  data-pointer is now declarable and its restriction is enforced for SR19, so SR24's subject EXISTS; the SET
  Format-10 path simply has no STRONG screen, and `SET P1 UP BY 4` over a pointer restricted to a STRONG type
  **compiles and runs silently** (measured above, `sr24_strong_ptr_upby.cob`). This row is now an
  under-rejection in the Format-10 arm, not a declaration gap — it is the one row here that is NOT blocked on the
  descriptor work and can be fixed today, next to the existing `StrongTypeModel.PointerRestriction` calls in
  `PtrBinder.cs:52-78`.
