# PB953 — OPEN — the writer that cannot report what it removed

## The mechanism, in the script's own lines

`scripts/spec/inventory_schema.py:52`

```python
ADJUDICATED = ("verdict", "code-location", "test-ref", "derivation", "editions", "notes")
```

`scripts/spec/record_verdicts.py:219-226`

```python
        before = {k: row.get(k, "") for k in ADJUDICATED}
        for field in ADJUDICATED:
            row[field] = rec.get(field, "")
        row["state"] = schema.state_for(row)
        if any(row[k] != before[k] for k in ADJUDICATED):
            changed += 1
```

Every one of the six fields is **assigned**, never merged, and a field the batch does not carry is assigned the
empty string. The run's own report is `rows changed : N` plus a `RE-ADJUDICATED` list that is computed from the
VERDICT alone (`if had and had != rec["verdict"]`) — so a batch that keeps the verdict and halves the
`test-ref` list prints exactly what a batch that enriched it prints.

## Why this is the dangerous shape

A row whose evidence was ADDED to can be checked: the references resolve or they do not, and
`SpecTraceabilityInventoryDriftTests.EveryTestRef_ResolvesToARealTest` is the gate that decides it. **A row
whose evidence was SUBTRACTED looks exactly like a row that never had more.** There is nothing left to
resolve, nothing dangling, nothing for any gate to contradict — the loss is only visible by diffing the
inventory against an earlier revision, which nothing in the brief or the battery does.
`feedback_verdict_evidence_invariant`: a MISSING observation is not a NEGATIVE one, and here the missing
observation is the row's own witness list.

`derivation` and `notes` are in the same tuple. A re-adjudication batch that carries a verdict and no
derivation ERASES the forensic prose that justified the previous verdict — the one artefact that says WHY a
row reads the way it does.

## It has already happened twice, in one group

Both instances are recorded in [[PB450]] and [[PB594]] and were repaired by `batch-04-evidence-union-repair.json`
and `batch-05`:

- `SR-14.9.39.3-17` — batch 1 left it with PB450's two witnesses alone, dropping three PB449/PB456 test-refs
  and three code-locations, while the note's prose said the batch "only ADDS".
- `SR-14.9.13.3-3` — batch 3 left it with two of five test-refs and one of seven code-locations, and one of
  the survivors was misspelled into `negative/pb398-range-alphabet-numeric`, a case that does not exist.

Measured on this tree, both unions are restored (`SR-14.9.39.3-17` carries four conformance refs;
`SR-14.9.13.3-3` carries five). **The dangling reference was caught only because a later gate ran** — the
predecessor's gate had died inside the Conformance leg and reported the group finished anyway. The SUBTRACTION
was caught by a human reading a diff. That asymmetry is the whole defect.

## Fix shape — the decision the fixer owes, and the one it must not take

⛔ **A resolution check is not the fix.** `record_verdicts.py`'s own header already says reference resolution
"is checked by the C# battery gate `SpecTraceabilityInventoryDriftTests` — deliberately NOT here", and that
check would not have seen either subtraction. The fix is in the WRITE:

1. **Merge-by-default for the two evidence lists.** `code-location` and `test-ref` are sets with a separator
   (`schema.code_location_sep` / `schema.test_ref_sep`); a batch adds to them, and REMOVING a witness takes an
   explicit, named act (a `--replace-evidence` flag, or a `-` prefixed entry) so the removal is a decision
   somebody wrote down. This is the shape every note's prose already ASSUMES ("the batch only adds").
2. **Or, at minimum, a NARROWING REPORT**: for every row, print what the batch removed — `⚠ SR-x-y: test-ref
   3 → 1 (dropped: …)` — and make `--dry-run` show it, so a narrowing is a thing a lander sees before it
   lands rather than a thing a registrar finds in a diff months later. `--dry-run` is already the standard
   step in the brief, so this costs nothing at the point of use.
3. Whichever is chosen, `derivation`/`notes` need the same decision stated explicitly: today a batch that
   omits them wipes them.

⭐ The durable half (CLAUDE.md rule 5): the prose in a dozen notes says "the batch only adds", and the tool has
never done that. Make the tool match the sentence everybody writes, and pair it with a drift test that fails on
a batch which narrows an evidence list without the explicit flag — so "only adds" stays true by construction.
