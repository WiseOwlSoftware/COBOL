## Arm 1 — a BINARY/PACKED image crosses as text (wrong answer, silent)

`reg11/pk.cob`:

```cobol
       01 PK  PIC S9(5) COMP-3 VALUE -42.
       01 CT  PIC S9(5) COMP-3 VALUE -42.
       01 CTX REDEFINES CT PIC X(3).
           ... DISPLAY "LOCAL " FUNCTION ORD(CTX(1:1)) ...         *> the caller's own image
           CALL "W46KP2" USING BY REFERENCE PK
           DISPLAY "PK AFTER " PK
       ...
       LINKAGE SECTION.
       01 L2 PIC S9(5) COMP-3.
       01 L2X REDEFINES L2 PIC X(3).
       PROCEDURE DIVISION USING L2.
           DISPLAY "FORMAL " FUNCTION ORD(L2X(1:1)) ...
           DISPLAY "S2 " L2
           SUBTRACT 1 FROM L2
```

Observed: `LOCAL 1 5 46` (ordinals, i.e. bytes 00 04 2D — correct) · **`FORMAL 1 1 13`** (bytes 00 00 0C) ·
**`S2 00000`** · **`PK AFTER 02303`**. Expected `FORMAL 1 5 46`, `S2 -00042` rendered per the formal's PICTURE,
and `PK AFTER -00043` after the callee's SUBTRACT.

- `python scripts/spec/cite.py --check 14.2.3 "the activated runtime element operates as if the formal parameter occupies the same storage area as the argument"` → OK §14.2.3 8)

Site (source report; the fixer confirms): `CallEmitter.CallStringRead` / `CallStringWrite` go to
`OperandText.FieldImage` (the DISPLAY text), and `ProgramEmitter`'s formal copy-in decodes with `ParseDisplay` over the
ImageWidth window — so an argument whose formal is image-carried (redefined / in a record) is serialized as the
wrong representation both ways. PB327 moved the file channel to `AsStorageImage`; the CALL channel never followed.
kb/Work PB873 (landed) fixed the SIGN of the DISPLAY-image arm only.

## Arm 2 — a pointer has no image at all (legal source refused at run time)

`reg11/k2.cob`: `01 P USAGE POINTER.` `SET P TO ADDRESS OF W` `CALL "R11K2S" USING BY CONTENT P ON EXCEPTION
DISPLAY "ON-EXCEPTION"`, callee `01 L PIC X(8).` → **`ON-EXCEPTION`**, the callee never runs.

- `… --check 14.8.2.3.3 "the formal parameter shall be of the same length as the corresponding argument"` → OK §14.8.2.3.3 1)
  (the rule for a program activated with no program-specifier and no NESTED phrase, when the FORMAL is not of class
  object or pointer — the formal here is PIC X(8), so the pair conforms if the lengths agree).

DOC-A.1-216 documents that a managed pointer slot has "no character image of its own". That leaves this pair
**needing a determination** before it can be fixed: either the implementor-defined pointer representation gets an
8-byte image (CLAUDE.md rule 1's precedence: GnuCOBOL's choice, else IBM / Micro Focus) or the pair is
documented non-support with a compile-time diagnostic rather than a run-time EC. PB873's change turned the former
silent spaces into this EC, which is loud but still a run-time refusal of conforming source.

## Arm 1 — LANDED (wave 52 DA, 2026-09-22)

Re-probed on the wave-52 worktree build first (`reg11/pk.cob`): `FORMAL 1 1 13` · `S2 00000` · `PK AFTER 02303` —
the note held. After: `FORMAL 1 5 46` · `S2 -00042` · `PK AFTER -00043`.

- `cite.py --check 14.2.3 "the activated runtime element operates as if the formal parameter occupies the same storage area as the argument"` → OK §14.2.3 8)
- `cite.py --check 14.2.3 "without conversion"` → OK §14.2.3 9)
- `cite.py --check 14.6.5 "is the content of the data item referenced by that RETURNING phrase"` → OK §14.6.5

**Root.** One carrier, two alphabets. `CobolArgAdapt.Text`'s native-cell arm has delivered the argument's STORAGE
image since PB873, but the image-carried side (`CallEmitter.CallStringRead` → `OperandText.FieldImage`) still spoke
OPERAND text, and every reader of a numeric string carrier (`CallStringWrite`'s PB181 decode/re-encode arm,
`LandScalar`, `ArgDouble`, `Num`'s GR8 view, `StoreReturn`) decoded with the DISPLAY codec. The fix makes the
convention single: a numeric string carrier is the item's record image under the description beside it.
`CallStringRead`/`CallStringWrite` share ONE predicate (`IsImageCarriedNumeric`): read = the window itself, write =
store as it stands (the PB962 zoned arm, now for every byte form — the PB181 decode arm is deleted). The ABI legs use
`ParseImage`/`FormatImage` (+ the float lane); `ParseImage`'s zoned arm IS `ParseDisplay`, so zoned items are
unchanged. A float image-carried item, which had no arm at all, now crosses too.

**Sibling sweep.** INVOKE (`OoEmitter`): the native-formal copy-out into an image-stored argument and the RETURNING
arms wrote `FormatDisplay` digits into a packed window / decoded an image with `ParseDisplay` (now `ValueImage` /
`ImageValue`); a numeric literal into an image-carried formal composed a zoned image (now `NumFormatImage`); a BY
CONTENT numeric argument into an image-carried fixed-point method formal did not COMPILE (the MOVE store rendered the
formal's profile bare in the activating class — CS0103) and is now the §14.8.2.3.3 rule-2a COMPUTE under the
owner-qualified profile. User FUNCTION activation, NESTED BY CONTENT (LandForFormal) and non-prototyped BY CONTENT
measured correct. ReportWriter's CONTROL restore reads and writes through the same pair, so its round trip is intact.

Goldens: `85/pb970_image_carried_binary_packed_argument` (CALL, COMP-3 + COMP, native/redefined × plain/redefined,
BY REFERENCE + BY CONTENT) and `2002/pb970_image_carried_packed_returning_invoke` (RETURNING + INVOKE, every arm).

## Arm 2 — LANDED (wave 53 EB, 2026-09-22)

Re-probed on the finisher's own build (base 37f19e028 + the three arm-1 commits cherry-picked): `reg11/k2.cob` printed
`ON-EXCEPTION` / `BACK`, and the callee never ran. After the fix it prints `IN CALLEE` / `BACK`.

**The rule is GR9's, not GR8's.** §14.9.4.3 SR10 bars a class-pointer identifier BY REFERENCE only
(`cite.py --check 14.9.4.3 "that identifier shall be neither a strongly-typed group item nor a data item of class object or pointer"` → OK 10)).
BY CONTENT, §14.8.2.3.3 1) requires only the same length
(`… 14.8.2.3.3 "the formal parameter shall be of the same length as the corresponding argument"` → OK 1)).
§14.2.3 GR9 then moves the argument "without conversion"
(`… 14.2.3 "That argument is moved to this allocated record without conversion"` → OK 9)).

**The determination** is recorded in `docs/CONFORMANCE.md` §7 DOC-A.1-216 and follows CLAUDE.md rule 1's
ISO → GnuCOBOL → IBM/MF precedence. GnuCOBOL stores a pointer as the machine address in its native binary order, with
NULL as the zero address. Here the image is an address token in this implementation's binary order (big-endian):
- NULL is eight X"00";
- a data pointer is the area's base (k × 2^32) plus its displacement;
- a program or function pointer gets its own base per (category, name).

**ONE codec**, `src/Cobol.Net.Runtime/Control/PointerImage.cs`, defines the image. Its consumer is the CALL boundary,
through `CobolArgAdapt.WithPointerContent`, which `Text` (non-group) and `Num` ask. It is BY CONTENT only, and only
into a formal of the pointer's 8 positions; any other length, BY REFERENCE and BY VALUE stay EC-PROGRAM-ARG-MISMATCH
(`conformance:2002/pb615_unreadable_argument_carrier` still passes).

⚠ **Not done here (a lead for the registrar):** a pointer MEMBER of a shared area still shows PB231's reserved fill
through a byte view. A first cut shadowed the image into the area on every slot store and seeded the composer with
the NULL image. That turned `conformance:2002/pb231_based_pointer_leaf`'s pinned `POST=33 33` into `1 1`. The pin
is a landed decision, and ALLOCATE's space fill would still disagree with a NULL seed. The change was reverted, so it
can go to its own note with owner visibility.

**The other arm of the same pairing.** Under a NESTED or prototyped activation, rule 2d makes the pairing a MOVE.
§14.9.25.3 SR1 refuses that MOVE, but `OoConformance.MoveContentMismatch` asked only Table 16, so the pairing compiled.
Before this fix it failed at run time with the EC. With the image delivery in place it would have run silently. It
now draws COBOLNET1688 at bind.

**Witnesses:**
- `conformance:2002/pb970_pointer_by_content_storage_image`: NULL, address, SAME for equal pointers, the caller untouched, +3/−3 through BINARY-DOUBLE, program pointer, and cross-category NULL;
- `conformance:negative/pb970-pointer-by-content-prototype-alnum-formal`;
- `unit:PointerImageTests` (5).

The sibling sweep covered six pairings:
- INVOKE and a user FUNCTION are rule 2, so they are refused by the same `ContentMismatch`;
- a DYNAMIC LENGTH formal stays refused (it has a fixed-width sender);
- a group formal stays refused (§14.8.2.2 2) MOVE);
- BY VALUE stays refused (GR10 fills by COMPUTE/SET);
- RETURNING is not a pairing that this rule reaches.
