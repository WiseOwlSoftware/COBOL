# PB3646 — no local process runs the Linux self-tests for an inert change

**Sites:** `scripts/linux-gate.sh` (the inert-lane exit near the head of the run), `scripts/self_tests.py`, `.github/workflows/build-and-test.yml` (the `audits` job), `docs/rearchitecture/DESIGN-test-build-ci.md` (3.18).

## What happens

PB2878 added an inert lane: a change confined to `DEVLOG/`, `kb/` and `.obsidian/` runs no tests. In that lane `linux-gate.sh` exits GREEN before any leg, including the `selftests` leg. CI's `audits` job runs `scripts/self_tests.py` on Linux on every event, inert changes included (DESIGN 3.18 says the audits run in every lane). So for an inert change no local process runs the Linux self-tests that CI runs, and CI could fail on code the local gates passed: the CI invariant (CLAUDE.md, kb/Work PB1957).

## Fix direction

Run the selftests leg in the inert lane (it needs no build), or record in PB1957's survey the reason the Linux self-tests cannot be affected by a change confined to inert paths, and pin that with a drift test.

## Source

Report `w20261029a2-PB2878-report.md` (PB2878 part 2, landed in PR #501), review lead R1-2.

## Landing (wave 20261104, group A2)

Re-probed: `linux-gate.sh` exited GREEN in its inert lane before any leg, and `run_gate_legs.py`'s inert lane ended
before the Linux half, while CI's `audits` job runs `self_tests.py` on Linux on every event. The note's second direction
(prove the self-tests cannot be affected by an inert change) is false: they are audits that read the inert paths by
design (the register, the DEVLOG, the skills submodule), which is exactly why the inert watch exempts them. So the first
direction is the fix, at both processes that stand for "tested locally":

- `linux-gate.sh`: the inert lane runs the `selftests` leg in the clone of HEAD (no build, no GnuCOBOL corpus, which moved
  below the lane decision) and ends GREEN or RED on it; `--legs inert` is the same run for a caller that already
  classified the change. A hand run of the gate and the Windows gate's Linux half therefore agree with CI.
- `run_gate_legs.py`: the inert lane (`Gate._inert`) takes a gate slot on a host that runs the Linux half, runs it after
  the audits (`Host.linux_leg(inert=True)`), records it as the Linux half, and ends RED, BUSY or NOT RUN on it exactly as the
  full lane does (`_linux_stopped`, factored from the full lane's inline arm). `_linux_attested` and
  `enqueue.tested_locally` no longer exempt an inert record: it needs a GREEN Linux half like any other on a host that
  runs one, and an inert record from before this change has none (the gate runs again). Measured on this box: 25 s of
  self-tests, 45 s for the whole Linux inert run.

Self-tests: `linux-gate.sh` (`--legs inert` stands alone), `run_gate_legs` (the inert lane's Linux half runs after the
audits under a slot, RED / NOT RUN / BUSY, an old inert record is no evidence), `enqueue` (`tested_locally` arms for an
inert record with and without a Linux half). Drift test: `InertLaneDriftTests.TheInertLane_RunsTheLinuxSelfTests_ThatTheAuditsJobRunsOnEveryEvent`.
DESIGN-test-build-ci.md §3.17.2 and §3.18 say so.

**For the next implementer.** `scripts/linux-gate.sh` inert block (`if [ "$inert" = 1 ]` after `selftests_leg`) and `--legs inert`; `run_gate_legs.py#Gate._inert` and `_linux_stopped` (REUSE for any new Linux-half outcome); `Host.linux_leg(inert=True)`.
