# PB3662 — a landing launched beside its own running gate stops for good

**Sites:** `scripts/orchestrator/enqueue.py` (`tested_locally`), `scripts/orchestrator/land_lane.py` (`decide`, `classify`,
`WAITS`).

## What happens

Since PB3612, `enqueue.py land` gates nothing. It reads the worktree's gate records (`tested_locally`) and refuses a tip
no GREEN record covers with exit 14 UNTESTED. A run that is still going has no `verdict.json`. `tested_locally` counts it
as one more reason ("no verdict file (a gate still running, or one that died)") and returns UNTESTED. `land_lane.decide`
classes exit 14 as STOPPED: it never relaunches that head unless the enqueue unit runs `rearm`. Before PB3612, a
landing that met a running gate got exit 12 GATE BUSY, which the lane retries at the same head once the gate lock is free
(`wait_free`). The PB3612 reader skips that wait, so a running gate became a terminal stop.

## The recorded case (2026-10-24, after a reboot)

`worktree-wf_1973801d-4fe-29` (PB2974, Review CLEAN). The `resume` unit merged main in at 15:50 PDT to bring in the PB3612
gate (PB3660) and started gate run `000005-20261024T225004Z`. The lane saw the new head `5e110b97e92a` at 15:52 and
launched attempt `000087`. That attempt ended at once with exit 14 ("000005-20261024T225004Z: no verdict file"). The gate
read GREEN (Windows, plus a Linux half at the same tree) about ten minutes later. The attempt still read STOPPED until
the operator re-armed it by hand at 16:05 (`land_lane.py rearm worktree-wf_1973801d-4fe-29`).

## The bar for the fix

- A tip whose worktree has a gate RUNNING (the gate lock held) and no recorded GREEN is a WAIT, never UNTESTED: the lane
  retries that head once the gate has written its verdict, as it does for exit 12 and 13. A run with no verdict whose gate
  lock is free is a dead gate and stays a reason for UNTESTED.
- One reader decides "a gate runs here": the gate driver's own (`run_gate_legs.live_gate`, the gate lock). Neither
  `enqueue.py` nor `land_lane.py` copies that check.
- The lane's self-test covers it: an attempt at a head with a live run waits, and the same head relaunches once the run
  writes GREEN, with no `rearm`.

## Landed (2026-10-24, fix-lane wave 20261104 group A, with PB3145)

Re-probed on a planted run (a run directory with no `verdict.json` while a gate ran): `tested_locally` returned UNTESTED
and `land` ended exit 14, which `land_lane.classify` reads STOPPED. Fixed at the one reader: `run_gate_legs.live_gate(lock_path)`
is the worktree's gate lock HELD (`Gate.run` holds it until its verdict file is written; the OS drops it when the gate
dies). Review R1-1 caught the first version, which asked whether the process `gate.pid` names lived: Windows reuses a dead
gate's process id (verified on this box with `explorer.exe`'s pid), so a gate dead at a reboot read as running for ever
and the lane waited with no escalation; the lock cannot be reused. `run_gate_legs.run_dirs` is now THE run listing
(`Gate._runs` is gone, its callers changed). `Tested.running` carries the live gate; `land` step 1c ends exit 12 GATE BUSY
for it (no report line, nothing merged, stamped or queued); `land_lane.gate_lock_free` (exit 12's wait) is the same lock
read, so the lane relaunches the same head the moment the gate ends, with no `rearm`. A run with no verdict whose lock is
free stays a reason for UNTESTED. Self-tests: `run_gate_legs` (live_gate arm: a free lock beside a no-verdict run whose pid
a live process holds is none), `enqueue` (a held lock is 12; a free lock beside a live-pid run is 14; a GREEN run beside a
running gate covers), `land_lane` (exit 12 waits while the lock is held, relaunches once it is free, whatever the pid file
names). The drift tests `LandingLaneDriftTests` and `LandingPipelineDriftTests` hold the new arms by name; the
sentences in MANDATORY-PRACTICES L12, `landing.md`, `units/enqueue.md`, DESIGN-orchestrator-loop.md, DESIGN-test-build-ci.md
and DOC_INDEX.md say what exit 12 now covers.
