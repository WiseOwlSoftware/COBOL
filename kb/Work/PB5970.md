# PB5970 - a NIST case that times out under load is a non-observation, and it reds the gate

**Evidence** (`E:/COBOL-coord/scratch/reports/w20262104pc-PB5950-report.md`, section "Finisher (gate RED at 55eeb0002a)"): `NistProgram_MatchesGolden(SQ224A)`
timed out twice at 120000 ms with the host 98-100% busy; no output was compared. The branch changes only the listing renderers, which no NIST run
reaches. On the finisher's `--no-build` run, Conformance was 28,190/28,193: SQ217A, IC114A and SQ116A were non-observations while the oracle capture and
the audits ran at the same time; SQ224A passed. Re-run alone, all four passed 4/4. Gate logs show the same class in other worktrees: `NistProgram_MatchesGolden`
SQ116A `[4 m 21 s]` (listing-step-6b-r1 run 000001), SQ217A (same run), NC207A `[5 m 9 s]` (listing-step-pb5941 run 000001), SQ224A `[4 m 33 s]`
(listing-step-pb5950 run 000001; its run 000002 went GREEN).

**Why this is a defect, not a retry:** CLAUDE.md says a flake is a `kb/Work` defect fixed at its root, never retried inside the run, and a timeout in a
verdict that compares output decides nothing. Three gates at once on a 32-processor host (the self-test phase reported "90% busy") plus the oracle capture
and audits exceed what a fixed 120000 ms per-case timeout assumes.

**Fix shape:** (1) the harness reports a timeout as its own outcome (not a failed comparison) and the gate re-runs only those cases alone, once, at the
end of the run, recording the retry in the verdict; or (2) the case timeout is derived from a measured calibration case and the host's load, never a
fixed constant; and (3) the gate's slot budget counts the oracle capture and audits, so concurrent gates cannot oversubscribe the host. Pin the choice with
a drift test.
