## Readings I tried, and why each fails

1. **"An integer is a numeric literal, so SRL3.1 (only ZERO for a numeric-restricted literal) applies."** SRL3.1 is an exception to a permission, and the permission covers only positions where the word *'literal'* appears in a format. The quotation marks around 'literal' in that sentence name the generic term. `integer-1` is a separate generic term (§1985:IV.2.1.2), and §1985:III.2 defines it separately. An exception can only narrow the permission it belongs to; it cannot open a position the permission never covered.
2. **"ZERO is a numeric literal with value 0."** It is not. A numeric literal is a character-string built from digits, a sign and a decimal point (§1985:IV.4.2.2.2.2). ZERO is a reserved word, which SRL3.3 calls a distinct character-string. §1985:III.2 requires 'integer' to be "a numeric literal which is an integer".
3. **"SR5 says integer-1 may be zero."** SR5 lifts the "neither signed nor zero" restriction of §1985:III.2 on the integer's value, which makes `0` legal. It says nothing about which tokens may form integer-1.
4. **"1985 admits ZERO in numeric contexts generally."** Every 1985 place that admits ZERO says so in a literal position or with an explicit rule. Arithmetic expressions (§1985:VI.6.3, line 11919) and EVALUATE literal-3 (line 13175) are examples. §1985:B.2.1 (7) lists "ZERO is allowed in arithmetic expressions" as a new 1985 feature. If ZERO already counted as a numeric literal, that addition would have been unnecessary. No such rule exists for integer-1 in WRITE or SEND.

PB5289 does not contradict any of this. Its point (4) took "the figurative ZERO is accepted" from the existing screen as a premise and compared ALL ZERO with it. It never cited §1985:IV.4.2.2.2.3's 'literal' scope or the §1985:III.2 'integer' definition. Its SR5 overturn is correct for `0`, but it does not extend to ZERO, so its `ALL ZERO` acceptance at 85 (the pb5342 witness) falls with the ruling.
