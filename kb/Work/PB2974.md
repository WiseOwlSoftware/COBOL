# PB2974 — a finisher's predecessor branch is held only for the notes its dispatch named

**Found:** the wave 1056 unit (loop, 2026-10-10), planning with
`plan_wave.py --from-budget --borrow-days 6 --scratch E:\COBOL-coord\scratch --stop-file E:\COBOL-coord\scratch\STOP-loop`.

**The defect.** Wave 1053's SPLIT reports each covered one branch carrying several notes: w1053b
(`worktree-wf_8d59ef7b-0cb-2`) PB2588 + PB2727 + PB2729 + PB2773; w1053e (`-0cb-5`) PB2834 + PB2848; w1053f (`-0cb-6`)
PB2548 + PB2833. The operator's wave 1055 dispatched finishers of those branches and recorded them in the dispatch
ledger under only some of each branch's notes: w1055A PB2727, PB2729, PB2773; w1055D PB2848; w1055E PB2548. Their
worktrees (`wf_6f53c0b7-a74-1`, `-4`, `-5`) cherry-picked the whole branches, PB2588, PB2834 and PB2833 included. The
wave 1056 plan then made three more finishers (A PB2588, B PB2834, C PB2833), each told to cherry-pick the SAME
predecessor branch: three agents would have redone work already in flight, and their trains would have landed
duplicate commits against wave 1055's.

**Mechanism.** `scripts/orchestrator/plan_wave.py#plan` (about lines 588-624): `held_by_dispatch` holds a note only when
a ledger group names it (about line 329), and the finisher loop builds one finisher per SPLIT report from
`set(ids) - taken`. When some of a report's ids are held, the report's branch is already being finished, but the
remaining ids still form a finisher over that branch. The file-set partition (`busy`, `file_set_collisions`) that
would have seen the overlap (group A's root `DataBinder.Switches.cs` is in w1055A's planned files) is applied only to
a campaign (`--cluster`), never to the fix lane. Two writers share the blame: `record_dispatch` stores a finisher
group's planned chunk, not every note its predecessor branch carries.

**Workaround applied in wave 1056 (not a fix).** `plan_wave.py --release 1056`, then
`plan_wave.py --record-dispatch PB2588,PB2834,PB2833 --label "w1055 A/D/E finishers: …"` (a 24-hour hand entry), then a
re-plan. That hand entry holds a 225-file set, so it can also hold unrelated groups for its 24 hours.

**What closes it.** A SPLIT report is ONE unit of work: when any of its ids is held by an unanswered dispatch, every
id of that report waits (`waiting`, naming the holder). And a finisher group's ledger entry records every open note
the report's branch carries, so the hold survives the next planner too. A `test_plan_wave.py` check: two SPLIT-report
notes on one branch, one held by a ledger group, plans no finisher for the other.

## 2026-10-15 (wave 1083 B review finisher): still open

The workaround above is gone (`plan_wave.py --record-dispatch` was deleted with the hand ledger, kb/Work PB3186), and the file-set partition now applies to the fix lane too (kb/Work PB2807). That does not close this note: `plan()` never defers a group for an in-flight branch whose report or commit subjects name the group's OWN notes (an earlier attempt), and a finisher that cherry-picked a SPLIT branch carries those notes in its subjects, so the partition does not defer the second finisher of the same branch. The fix is the one above: a SPLIT report is one unit, held whole while any of its ids is held.

## 2026-10-16 (wave 1106, PB3311): the FINDINGS arm now asks the survey; the SPLIT arm does not yet

`plan()` waits a review-FINDINGS finisher whose report's branch the branch survey reads IN FLIGHT (`states`). The SPLIT
and unlanded arms still do not: a just-returned SPLIT branch is IN FLIGHT for `--min-age` after its last touch, so the
survey's state alone would stall every SPLIT finisher for three hours. The cure here needs the distinction PB3311 could
not make from the state alone: a live LOCK or an unanswered ledger dispatch (someone is working) against a recent touch
(someone just stopped).
