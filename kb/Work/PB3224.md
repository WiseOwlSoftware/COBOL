**Rule it breaks:** ISO §14.9.39.3 SR22 applies to EACH identifier-7 of the receiving list (the brace carries an ellipsis); §8.4.3.13.4 GR3 makes only the prototype arm a restricted sender. The code itself claims (SetBinder.cs:1047) that one sender must satisfy every receiver.

**Scenario:** BindSetProgramAddress takes receiverProto = targets[0].Item.Pic.RestrictedPrototypeName (SetBinder.cs:1042). The receivers-among-themselves loop (1043-1054) compares through PrototypeSignatures.Same, which answers true when either side is null, so an UNRESTRICTED first receiver passes against a restricted second one. Both sender arms then ask only receiverProto: the prototype arm skips the check when it is null (1061), and RestrictedReceiverNeedsPrototype(null, ...) returns false (1178). Measured on the pin build (cobol.exe at pin-r2) with prototypes RPAPA (USING PIC X(2)) and RPAPB (USING two COMP items), RP TYPE RPT (PROGRAM-POINTER TO RPAPA), UPP USAGE PROGRAM-POINTER: `SET UPP RP TO ADDRESS OF PROGRAM RPAPB` and `SET UPP RP TO ADDRESS OF PROGRAM "XYZ"` compile clean, while the same two statements with `SET RP UPP` draw COBOL1959 twice. The restricted RP is loaded with an address of the wrong signature or an unrestricted one, so a later CALL RP USING a PIC X(2) argument activates a program with a different parameter list. The function twin BindSetFunctionAddress has the same representative-receiver shape (790-791, 824): a first receiver restricted to an external-repository prototype (no compile-time signature) passes every compare, so `SET F-EXT F-P1 TO ADDRESS OF FUNCTION P2` is not screened against F-P1.

**Measured how:** R2 batch finding `procedure-binding-5--code--f1#1` (pair procedure-binding-5--code), read in the pinned tree at 8be23006851a; skeptics rule upheld, scenario upheld, site upheld.

**Spec:** §14.9.39.3 "If identifier-7 references a restricted program-pointer, identifier-8 shall be the predefined address NULL or shall reference a program-pointer and the program-prototypes associated with identifier-7 and identifier-8 shall have the same signature." (`cite.py --check` passed at collection); §8.4.3.13.4 "When program-prototype-name-1 is specified, the program-address-identifier has the characteristics of a program-pointer restricted to program-prototype-name-1" (`cite.py --check` passed at collection)

**Skeptics' corrections applied:** rule lens: severity "Critical" -> "Warning"

**Target:** Screen SR22 (and SR20 on the function twin) per receiver: for each target, compute the restriction it needs and compare the sender against it, exactly as BindSetProgramPointer and BindSetFunctionPointer already do through PointerAssignmentReason per target. Delete the receivers-among-themselves pre-pass and the single receiverProto. Witness goldens: both receiver orders, with prototype, literal and identifier senders, in tests/conformance/2002.

**Design reference:** §8.3.

## Landed

Re-probed on the branch build before the fix: `SET UPP RP TO ADDRESS OF PROGRAM {RPAPB | "XYZ" | NM}` compiled clean, the same statements with `SET RP UPP ...` drew COBOL1959. Fixed at the root in `SetBinder.BindSetProgramAddress` and `BindSetFunctionAddress`: the single `receiverProto` taken from `targets[0]` is gone. SR22 / SR20 is asked of EVERY receiver against the sender (prototype arm per receiver; `RestrictedReceiverNeedsPrototype` takes the whole receiver list and names the first restricted one), and the receivers-among-themselves check is the order-free `ReceiversDisagreeing` (every pair, because `PrototypeSignatures.Same` conforms on a missing signature and is not transitive). The function twin's GR14 expected-formals count comes from the first receiver that has a compile-time signature. Witnesses: `conformance:cases/14.9.39-SET/pb3224-set-program-address-unrestricted-first-{prototype,literal,identifier}`, `pb3224-set-function-address-external-first`, `pb3224_set_program_address_receiver_order`, `pb3224_set_function_address_receiver_order`. The vendor `SET pp TO ENTRY` spelling stays outside SR22 (documented at `RestrictedReceiverNeedsPrototype`).
