# PB5821 - a contained program's file error runs the container's USE GLOBAL ... ON INPUT declarative for a file the container names in another USE statement, where no declarative qualifies (every edition)

**Ruling: UPHELD (b), harm wrong_answer.** A containing program holds USE GLOBAL ... ON INPUT and USE ... ON FG. A contained program with no declaratives fails to open FG, and the compiler runs the container's GLOBAL INPUT declarative. No declarative qualifies. The checker's confidence: high. Same text and same output at 2023 (cause b). Severity MAJOR is the clerk's choice (a wrong-answer defect is at least MAJOR); the ruling names none.

**Not the question of kb/Work PB5812.** Both USE statements are in one program, the container's, so PB5812's question (whether the USE precedence rules reach across programs, a containing program's USE GLOBAL on the file against the contained program's own USE ON INPUT) does not arise here; the ruling's table says: "Not PB5812's question, because both USE statements are in one program."

**Mechanism 2, ruled** (the ruling's paragraph, unchanged). `§1985:VIII.4.8.4 GR5b` runs the INPUT procedure for any file open or being opened in
the input mode "except those files referenced by file-name-1 in another USE statement specifying the same
condition" (cite.py OK). FG is named in the container's other USE statement, so the INPUT procedure does not apply to
FG. `§1985:X.5.5.4 GR1` says: "The declarative which is selected for execution must satisfy the rules for execution
of that declarative" (cite.py OK). So for the contained program's failed OPEN of FG the container's GLOBAL INPUT
declarative is not a qualifying declarative, the declarative that names FG has no GLOBAL phrase, and GR1c ends the
search: none is executed. The compiler prints `OUTER-GLOBAL-INPUT 35`. The checker found the same at 2023 (rows
`GR-14.9.49.4-5` and `GR-14.9.49.4-6`).

**The checker's evidence.** Both USE statements are in ONE Procedure Division (the container's): USE ON FG (not GLOBAL) and USE GLOBAL ON INPUT. GR5b defines the INPUT procedure's own scope, so the container's INPUT declarative never applies to FG under either of PB5812's readings. When the contained program's OPEN INPUT FG fails, `§1985:X.5.5.4 GR1b` offers only the container's GLOBAL declaratives, and GR1 requires the one selected to satisfy the rules for execution of that declarative: the INPUT one does not (GR5b), the FG one is not GLOBAL. Expected: no declarative runs, status 35 in FS. Observed: the container's GLOBAL INPUT declarative runs for FG. In the container itself the same failure correctly runs only OUTER-NAMED-LOCAL, so the program's own tiers are right and only the outward GLOBAL walk is wrong. Row -5 is GR5b's exception itself; row -4 is GR4.

**Where** (the checker's reading): in `EmitScopeTiers`, with globalOnly=true, `Qualifies(d) = !globalOnly || d.Global` drops the container's non-GLOBAL file-name cases, so the named file falls through to the GLOBAL open-mode tier. It is reached from `EmitRunGlobalUse`. Not an edition switch.
