# PB391 — one rule, two places, five drifted cells

## THE MECHANISM

`§14.9.25.3` SR13 and `§14.9.25.4` GR11 both send the pairing decision to `§14.7.6`, whose **rule 2** requires
that *"the resulting move is valid according to the rules for the MOVE statement"* — i.e. SR10's Table 16.
`src/Cobol.Net.Compiler/Binding/MoveTable16.cs#Refusal` is the ONE home for that question; `PB53` built it
precisely to retire a duplicate, and its own header warns *"asking it in two places is how the two answers
drift"*. `CorrespondingBinder` does not ask it. `CorrespondingBinder.cs:178-198` (`CorrMoveValid`) is a second,
private copy with:

* **no alphabetic row or column** — its own doc-comment admits the fold ("Table 16's alphabetic-only
  prohibitions … are not separable here — those pairs are admitted under the alphanumeric column");
* **no national and no boolean row** — the sender switch ends `_ => false`, so **every national and boolean
  namesake pair is declared non-corresponding**;
* **a receiver axis that is ONE boolean** — `dstIsAlphanumeric = dst.IsGroup || dst.Pic!.Category is
  PicCategory.Alphanumeric` (`:184`) — which folds a National or Boolean receiver into Table 16's
  *"Numeric, Numeric-edited"* column.

So it fails in BOTH directions at once: pairs the table admits are silently dropped, and a pair the table
refuses is silently made. Five cells are measurably drifted, and **every one of the five is decided correctly by
`MoveTable16.Refusal` for the equivalent DIRECT move** — which is the proof that the shared table is right and
the copy is the defect (`feedback_one_rule_one_place`).

**A TRAP THE FIX MUST NOT SPRING.** `§14.7.6` rule 4's class exclusion (index, message-tag, object, pointer) is
NOT applied by `CorrEligible` either (`:160-165` tests `IsTable`, `RedefinesTargetName`, `Renames` and
`Usage.Index` only). A pointer namesake pair is excluded TODAY only *incidentally*, by `CorrMoveValid`'s
`_ => false` default. `MoveTable16.Refusal` **admits** a Pointer × Pointer pair — it screens
Group / Boolean / National / Alphabetic / Numeric and returns null for everything else — so **routing rule 2 to
the shared table without adding rule 4's class test in the same change would convert a silent exclusion into a
silent pointer copy.** Delete the copy AND implement rule 4.

Table 16 itself (`specs/ISO_COBOL.md:25263`, under §14.9.25.3 SR10) gives, for the cells at issue:
Numeric-Integer × Alphabetic = **No**; Alphabetic × Numeric = **No**; Numeric-Integer × Boolean = **No**;
National × National = **Yes**; Boolean × Boolean = **Yes**; Numeric-Noninteger × National = **No**. A pair whose
move is invalid **simply does not correspond** — a silent non-selection, never a diagnostic — so the receiving
item keeps its prior content; a pair whose move is valid MUST correspond and the move must happen.

## THE CODE SITES, AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/CorrespondingBinder.cs:178-198` — `CorrMoveValid`, the copy.
* `…/CorrespondingBinder.cs:129` — `if (!CorrMoveValid(s, d)) continue;`, rule 2's call site.
* `…/CorrespondingBinder.cs:160-165` — `CorrEligible`, rule 4 with the object / pointer / message-tag legs absent.
* `src/Cobol.Net.Compiler/Binding/MoveTable16.cs#Refusal` — the one home the copy should call.

**The fix is DELETION, not repair.** `CorrMoveValid` becomes
`MoveTable16.Refusal(Table16Operand.Of(src), Table16Operand.Of(dst)) is null`, which also picks up the
alphabetic / edited / noninteger axes PB72 completed there and which the copy folds away. **Three things must
survive the swap:**

1. `§14.7.6` rule 2's **silent-skip posture** — a refusal means the pair does not correspond, never a
   diagnostic (the direct-MOVE COBOLNET0819 must NOT start firing from CORRESPONDING);
2. the **≥2002 gate** on the numeric-edited sender's de-editing pair, an edition rule `Table16Operand` does not
   carry;
3. **rule 4's class exclusion added to `CorrEligible` in the SAME change set** — index, message-tag, object and
   pointer — or the deletion introduces a silent pointer copy (measured above). Note `CorrEligible`'s comment
   repeats a false premise ("the 2002+/2014 exclusion classes … have no representation in this data model yet")
   that `PicInfo` contradicts; delete the comment with the fix.

**And a drift test**: assert that the CORRESPONDING pair filter and the direct-MOVE guard agree over a matrix of
category pairs. It is the only thing that keeps two answers to one question from separating again — make it fail
once against the five cells above.

## THE SR8 / SR9 HALF — LANDED 2026-09-13, train 38 lane

**Rule 2's question is not Table 16's question.** §14.7.6 rule 2 says *"the resulting move is valid according to
the rules for the MOVE statement"*, plural, and §14.9.25.3 SR10 — the rule that routes to Table 16 — governs only
*"For all other cases not described in Syntax rules 8 and 9"*. SR8 and SR9 are therefore inside rule 2 and were
BOTH unasked. Both were measured wrong on this tree, and both are fixed:

* **SR8** (`--check 14.9.25.3 "identifier-2 shall reference a numeric or numeric-edited item"` →
  `OK §14.9.25.3 8)`). `01 G1. 05 K USAGE BINARY-LONG VALUE 42.` / `01 G2. 05 K PIC X(5) VALUE "ZZZZZ".` under
  `MOVE CORRESPONDING G1 TO G2` printed `K2=[00000]` — the pair formed and the receiver was overwritten — while
  the identical `MOVE K OF G1 TO K OF G2` was refused `COBOLNET0819` by the same compiler. **After: `K2=[ZZZZZ]`,
  and the numeric and numeric-edited receivers the rule names still pair** (`K2=[00042]`, `P2=[    7]`).
* **SR9** (`--check 14.9.25.3 "these groups shall be compatible groups as specified in 8.5.1.12"` →
  `OK §14.9.25.3 9)`). A variable-length-group namesake opposite an elementary one, in either direction, formed a
  pair whose implied MOVE asks for a whole-group character image the pair can never have: the program reached the
  RUN TIME and threw `NotImplementedCobolFeatureException`, where the written MOVE of the same two items is
  refused `COBOLNET1931`. **After: both directions are silent non-selections and the receiver keeps its content,
  while a COMPATIBLE group × group namesake still descends and moves its members.**

**The shape.** `MoveTable16.DataItemRefusal(DataItem sender, DataItem receiver)` is the whole of §14.9.25.3's
validity question over two data items, in SR order — SR8, then SR9, then SR10's table — and
`CorrRule2MoveValid` is ONE call to it, so the next MOVE syntax rule reaches CORRESPONDING without an edit.
Neither rule is written twice: SR8's item-keyed test is the new `ShapeRefusal(DataItem, Table16Operand)` overload
and the pre-existing `ShapeRefusal(BoundOperand, Table16Operand)` entry now DELEGATES its data-item leg to it
(the figurative arms SR7/SR6 stay there, since a data item can never be a figurative constant); SR9's relation
moved out of `StatementValidation.CheckVariableLengthMove` into `MoveTable16.VariableLengthRefusal`, which reads
the ONE `VariableLengthCompatibility` module and leaves `CheckVariableLengthMove` holding only the MOVE
statement's framing — which operand shapes unwrap to a data item, which name goes in the message, and
COBOLNET1931 itself. `CorrRule2MoveValid` reads it SILENTLY, because rule 2 makes an invalid move a pair that
does not correspond rather than a diagnostic. SR1's class half is deliberately NOT in the chain: §14.7.6 rule 4
already excludes those four classes on BOTH sides, earlier and more broadly than SR1's sender-only wording.

**Which arm was fixed: all three, and two of them by the spec rather than by an edit.** `CorrEligible` and the
descent are shared by MOVE, ADD and SUBTRACT CORRESPONDING. SR8 and SR9 are MOVE syntax rules, and §14.7.6
rule 3 — *"both of the data items are numeric"* — is strictly stronger than SR8's receiver requirement and
excludes a variable-length group outright, so the two arithmetic verbs were already right. Measured, not assumed:
`ADD`/`SUBTRACT CORRESPONDING` leave the `BINARY-LONG` × `PIC X(5)` namesake unpaired before AND after, and still
pair `BINARY-LONG` × `PIC 9(5)` (42 added, then 42 subtracted).

**The drift test grew two positions, not two cases.** `CorrespondingRule2DriftTests` now carries a `Binary-long`
and a `Variable-length-group` position — neither is a Table-16 row, which is exactly why the table could not
decide them — and asserts the binder's filter equals `MoveTable16.DataItemRefusal` on all 144 cells, plus a
`TheBoundAndItemKeyedShapeEntriesAnswerTogether` theory pinning that the two `ShapeRefusal` entries return the
same string for every modeled pair (the two-arm split this fix could have re-created). Verified to FAIL 18 of 40
against the pre-fix filter.

**Goldens:** `tests/conformance/2002/pb391_corresponding_rule2_sr8_binary` (SR8's introducing edition — the
