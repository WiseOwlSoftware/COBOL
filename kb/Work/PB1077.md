# PB1077 — OPEN — `BindFileControl` registers a FileModel per SELECT with no pairing and no uniqueness test: a SELECT with NO file description entry compiles clean and its first 

## Rule text (every citation re-run by the registrar)
- `python scripts/spec/cite.py --check 12.4.5.2 "A given file-name may be specified in only one SELECT clause within a factory, function, object, or program"` → `OK  §12.4.5.2 2)  (Syntax rules)`
- `python scripts/spec/cite.py --check 12.4.5.2 "For each file-name specified in a SELECT clause, there shall be a file description entry or a sort-merge file description entry in the file section"` → `OK  §12.4.5.2 3)  (Syntax rules)`

### Adjudicator finding (file-control-entry, harm crashes)
- **Mechanism:** file-control-entry-sr3-no-fd-pairing: BindFileControl registers a FileModel for every SELECT and nothing checks that an FD or SD attached to it, so a SELECT with no file description entry compiles clean and its first I-O statement aborts the run unit
- **Repro:** SELECT F1 ASSIGN TO "a.dat". SELECT F2 ASSIGN TO "b.dat". with FILE SECTION containing only FD F1 (01 R1 PIC X(10)); PROCEDURE DIVISION: OPEN OUTPUT F2 CLOSE F2. (probe/fce/sr3open; without the OPEN: probe/fce/sr3nofd)
- **Expected (spec):** §12.4.5.2 SR3: 'For each file-name specified in a SELECT clause, there shall be a file description entry or a sort-merge file description entry in the file section ...' - a compile-time error naming F2, at every edition.
- **Observed:** Pinned cobol.exe, --std 2023 and --std 85: compiles with no diagnostic; at run time OPEN OUTPUT F2 throws System.InvalidOperationException 'file connector SR3OPN::F2 was never registered - a compiler defect, not a program error (kb/Work PB140)' from FileRegistry.Require; process exit 3762504530. Without a reference to F2 the program compiles and runs clean (under-rejects). Distinct from landed PB345 (FD present, no record descriptions).
- **Code site:** src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindFileControl (FileModel registration, FilesByName) with no post-BindFileSection pairing screen; src/Cobol.Net.Runtime/IO/FileRegistry.cs#Require is where it surfaces
- **Clause (adjudicator):** 12.4.5.2 SR3

### Adjudicator finding (file-control-entry, harm under-rejects)
- **Mechanism:** file-control-entry-sr2-duplicate-select: BindFileControl writes FilesByName[name] = file and _files.Add(file) with no test for an earlier entry of the same file-name, so a second SELECT of one file-name is accepted and silently replaces the first in the name map
- **Repro:** SELECT F1 ASSIGN TO "a1.dat". SELECT F1 ASSIGN TO "b1.dat". FD F1. 01 R1 PIC X(10). PROCEDURE: OPEN OUTPUT F1 MOVE "X" TO R1 WRITE R1 CLOSE F1. (probe/fce/sr2open; organization-conflicting variant probe/fce/sr2dup_diff)
- **Expected (spec):** §12.4.5.2 SR2: 'A given file-name may be specified in only one SELECT clause within a factory, function, object, or program.' - a compile-time error on the second SELECT F1 at every edition.
- **Observed:** Compiles clean exit 0 at --std 2023 and 85; the run writes b1.dat only (the LAST entry won FilesByName) while _files still holds both models; the sequential/relative conflicting pair also compiles clean.
- **Code site:** src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindFileControl (`_files.Add(file); ... FilesByName[name] = file;`)
- **Clause (adjudicator):** 12.4.5.2 SR2

## What the fixer owes
SR2 at registration (`BindFileControl`, before `FilesByName[name] = file`); SR3 as one post-`BindFileSection` pass over `_files` asking whether an FD/SD attached. Both at every edition. Sweep: the OO factory/object halves that bind a class-level FILE-CONTROL twice (PB1076) must not trip SR2 falsely.
