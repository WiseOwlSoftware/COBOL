## Why nothing caught it

Three independent layers each had a reason not to look:

1. **The implementer's own checkpoint rule is a blanket stage.** `.claude/skills/workstream/templates/
   implementer-brief.md:9` (and the live dispatch copy,
   `E:\Temp\claude\E--CobolSharp\a9d94900-79fe-4a38-89f0-921976861543\scratchpad\fixlane-implementer-brief.md:7`)
   says: *"After EVERY mechanism and every gate run: `git add -A -- . ":!.claude/settings.local.json"` + `git
   commit -m "WIP checkpoint: …"`"*. `git add -A` stages a conflicted file exactly as happily as a clean one,
   and the protocol's whole point is that it runs often and unattended.
2. **The lander's per-row routine resolves conflicts by judgement and never re-checks.**
   `.claude/skills/workstream/templates/lander-train-brief.md:9` and
   `.claude/skills/workstream/templates/lander-brief.md:9` both say *"`git apply -3 --check`, then `git apply
   -3` … Resolve conflicts by reading both sides against the spec and the implementer's report — never by taking
   a side blindly."* Correct instruction, no verification step: nothing asks whether the resolution left markers.
3. **No test reads the file.** The wave-local gate is a filtered `dotnet test`; `audit_grammar_optional_words.py`
   is invoked by hand and by no test in `Cobol.Net.Tests.Unit`, so a Python `SyntaxError` in it is invisible to
   every gate the project runs per commit. A broken tool reads as a silent tool.

`feedback_green_gates_arent_evidence`: three green gates, none of which ever looked at the file that broke.

## The fix — three places, smallest to largest

1. **Implementer brief, the checkpoint line** (`implementer-brief.md:9`): make the stage-and-commit
   `git add -A … && git diff --cached --check && git commit …`. `git diff --cached --check` reports a staged
   *"leftover conflict marker"* and exits non-zero, so the checkpoint that would have shipped `c6460d0f` fails
   instead. One clause, in the rule that already runs on every sub-step.
2. **Both lander briefs, step 1** (`lander-train-brief.md:9`, `lander-brief.md:9`): after each cluster's
   `git apply -3` and before its checkpoint commit, `git diff --check` on the working tree and
   `git grep -n "^<<<<<<< \|^>>>>>>> "` over the applied paths. A cluster that fails it is DROPPED from the train
   by the rule already written there, not carried.
3. **A tree-wide drift test in `Cobol.Net.Tests.Unit`** — the layer that makes 1 and 2 unnecessary to remember.
   Enumerate `git ls-files` (not a filesystem walk), read each text file, fail on any line matching
   `^<<<<<<< `, `^=======$` (only in company with one of the others — a bare `=======` is a legal Markdown
   setext rule) or `^>>>>>>> `, and name every offending path and line in the failure message.
   `feedback_green_gates_arent_evidence` applies to the new test too: make it fail once, against a fixture
   holding a marker line, before trusting its silence.

⭐ **The GnuCOBOL exclusion the fix shape asked for is not needed, and knowing why matters.** The dispatch's
premise was that `tests/external/gnucobol/` carries marker lines as test data and must be excluded. The data half
is TRUE — exactly two files carry them, `tests/external/gnucobol/tests/testsuite` (4 lines) and
`tests/external/gnucobol/tests/testsuite.src/syn_misc.at` (4 lines, the first at `:6450` — GnuCOBOL's own
`syn_misc` cases feed marker-shaped text to their compiler on purpose). But the whole directory is **gitignored**
(`.gitignore:72`, `tests/external/gnucobol/`) and `git ls-files tests/external/gnucobol` returns **0 paths**, so
a `git ls-files`-scoped sweep never sees them and a hand-maintained exclusion list would be a dead lookup
(`feedback_a_dead_lookup_is_also_unverified`). Scope the test to tracked files and the exclusion is structural.
Do NOT write it as a `Directory.EnumerateFiles` walk with a skip-list — that is the version that needs the list,
rots when the corpus moves, and is the shape rule 5 tells us not to choose.

## Sweep

The generalization is not "check for markers"; it is **"every checkpoint protocol that stages blindly needs one
mechanical assertion about what it staged"**. The same `git add -A` line is the reason
`feedback_fleet_litter_check_status_before_add` exists (fleet litter landing in a commit) — two different
failures, one blanket stage. Both are closed by the same edit: an assertion between the add and the commit.
