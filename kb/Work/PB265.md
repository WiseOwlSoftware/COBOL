# PB265 — the register's gates cannot tell YAML from not-YAML

Registered from battery #40's rider verification (DEVLOG entry 1420, commit `6cd228b6`), which found **four
register notes whose `title:` had never been valid YAML** — and found them by reading, not by any gate. This
note is the gate-shaped statement of that finding, filed by the arithmetic-wave implementer 2026-08-31 after
reproducing it deliberately.

## Measured, both directions, 2026-08-31

Two probe notes were added to `kb/Work/`, measured, and removed.

**Direction 1 — the gate is HAPPIER than YAML.** A note whose title is an unquoted scalar carrying `": "`:

```yaml
title: ZZPROBE2 — a title with a colon: and text after it
```

```
$ python scripts/spec/work.py check
✓ 320 work items, all well-formed

$ python -c "yaml.safe_load(frontmatter)"
YAML FAILS: ScannerError mapping values are not allowed here
```

The register's own checker calls a note well-formed that no YAML parser will load. This is the exact shape of
the four notes commit `6cd228b6` repaired by hand.

**Direction 2 — the gate MIS-READS what YAML reads correctly.** A note whose title is a quoted scalar wrapped
over two lines, which is how a long title is naturally written and which YAML loads whole:

```yaml
title: "probe — a note whose title carries a colon: like this one, and which wraps
  onto a second line the way a long title does"
```

`yaml.safe_load` returns the full string. `work.py load()` returns
`'probe — a note whose title carries a colon: like this one, and which wraps'` — the continuation line has no
colon, so `if ":" not in line: continue` drops it without a word. **So the register cannot hold a wrapped
title**, which is a real constraint nobody has been told about: the titles in this register run to 300+
characters and are all written on one enormously long line because of a limitation nothing documents.

## Why this is a register-integrity defect, not a style complaint

`kb/Work.base` — the Obsidian Bases view that CLAUDE.md and MEMORY.md both call **the same list** as
`work.py next` — is consumed by a REAL YAML parser. So the two halves of the register's UI disagree about which
notes exist and what their fields say, and only one half has a gate. A note that fails to parse there is
invisible in the view while `work.py next` ranks it: the same asymmetry as
[[feedback_measure_the_selectors_complement]] (`work.py next` hid nine harmful items for months) and
[[feedback_green_gates_arent_evidence]] (a check that never looked at what changed).

## Both readers, and why the duplication was deliberate

- `scripts/spec/work.py` `load()` — `re.search(r"^---\n(.*?)\n---", t, re.S)` then a per-line
  `partition(":")`, `.strip().strip('"')`, `[a, b]` list split.
- `tests/Cobol.Net.Tests.Unit/DefectiveRowCoverageDriftTests.cs` `ParseNote` — the same shape in C#
  (`^(?<key>[a-z_]+):[ \t]*(?<value>.*?)[ \t]*$`, Multiline), with a doc comment stating the choice outright:
  *"Deliberately NOT a YAML parser … pulling a YAML dependency in to read three fields would put the two readers
  on different grammars — the drift this gate exists to prevent, reproduced in the gate."*

⚖ That reasoning is sound about the two READERS and silent about the WRITER. Keeping both consumers on one
lenient grammar does prevent them drifting from each other; it does nothing to keep either of them aligned with
the grammar the notes are actually written in and the Bases view actually parses. The missing assertion is a
third thing, not a fourth reader: **is this file YAML at all?**

## Proposed fix shape — ⛔ DELIBERATELY NOT IMPLEMENTED IN THE ARITHMETIC WAVE (2026-08-31 scope decision)

Prefer (A); (B) is the fallback if a dependency is unwelcome.

**(A) One validating parse, at the one place that already walks every note.** Add to `work.py check` a real
`yaml.safe_load` of each note's frontmatter block whose ONLY job is to fail loudly with the file name and the
parser's own message. Keep the existing lenient reader for the fields — the point is not to change what is read,
it is to assert that what was read could also have been read by the parser the view uses. Then extend it one
step further and compare: where the lenient reader and the YAML parser disagree on a scalar (the wrapped-title
case), that is also a failure, because it means the register says two different things about one note.

**(B) If PyYAML is unwelcome as a dependency**, a dedicated drift test asserting the frontmatter's SHAPE
mechanically instead: every non-blank line either matches `^[a-z_]+: ` or is a continuation indented by two
spaces belonging to a quoted scalar; a `key: value` whose value is unquoted contains no `": "`; every quoted
scalar's quotes balance across its continuation lines. This is weaker — it re-derives a YAML subset by hand,
which is the thing rule 5 warns about — but it needs no dependency and catches both measured directions.

Either way the gate must be proved to FAIL once before it is trusted ([[feedback_prove_the_watchdog_fails]]):
re-adding the ZZPROBE2 shape above is the exact reproduction, and it takes one file.

⚠ One premise checked and REJECTED while measuring: CRLF line endings do NOT hide a note. `work.py load()`'s
`^---\n` anchor looks CRLF-fragile, but `pathlib.read_text` opens in universal-newline mode, so a CRLF note
loads normally (probed: 320 items with a CRLF note present). Recorded so the next reader does not chase it.
