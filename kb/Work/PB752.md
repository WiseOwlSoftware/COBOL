# PB752 — OPEN — two fatal-challenge legs with no population assertion

Found 2026-09-06 by the `PB708` implementer (report, "New defects" (2)), which checked the CI shard matrix
before assuming and filed these two rather than folding them in. **Verified against main (`0a24276f`) by
reading the workflow; nothing was run and nothing was renamed.**

## The two unguarded legs, at main's line numbers

**`inv1-strong-2023`** — job at `:340`, *"INV-1-strong (golden battery byte-exact @ 2023 --permissive)"* — its
one step, `:365`:

```yaml
run: dotnet test tests/Cobol.Net.Tests.Conformance/Cobol.Net.Tests.Conformance.csproj --filter "FullyQualifiedName~NistProgram_MatchesGolden" --logger "trx;LogFileName=inv1-strong.trx" --results-directory TestResults/${{ runner.os }}-inv1-strong
```

**`legacy-oracle`** — job at `:432`, *"Legacy-oracle bake-verify cross-check (opt-in — nightly / manual)"*,
gated `if: github.event_name == 'schedule' || github.event_name == 'workflow_dispatch'` (`:434`) — its one step,

```yaml
run: dotnet test tests/Cobol.Net.Tests.Conformance/Cobol.Net.Tests.Conformance.csproj --no-build --filter "FullyQualifiedName~DifferentialTests&FullyQualifiedName!~NistDifferentialTests" --logger "trx;LogFileName=legacy-oracle.trx" --results-directory TestResults/${{ runner.os }}-legacy-oracle
```

Neither step reads its own output. Neither job has a companion assertion step. vstest answers a filter that
matches nothing with a **passing run of zero tests** — exit 0, no warning, no red — so either leg reports success
having compiled and compared **nothing** (`feedback_vstest_filter_terms`, measured against this very workflow by
[[PB287]]).

## The contrast that makes it a defect rather than an omission

The sharded Conformance matrix uses a filter too — `:136` (Linux, `greenfield-conformance`) and `:263` (Windows,
`windows-conformance`), both `--filter "${{ matrix.filter }}"` — and it is protected, twice over:

1. each shard captures its own executed count from vstest's own line, `:139` and `:266`:
   `grep -Eo 'Total:[[:space:]]+[0-9]+' shard.log | tail -1 | grep -Eo '[0-9]+' > count.txt`, published as an
   artifact (`:141-145`, `:268-272`);
2. the **`conformance-population`** job — `:288-289`, *"Conformance shard population guard"*, `needs:
   [greenfield-conformance, windows-conformance]` — re-discovers the population and asserts the sum, `:313-331`:

```bash
disc=$(dotnet test … --no-build --list-tests 2>/dev/null | grep -cE '^    CobolNet\.Tests\.Conformance\.')
… if [ "$sum" -ne "$disc" ]; then echo "::error::POPULATION MISMATCH ($os): shards executed $sum of $disc discovered tests …"
```

So the workflow already knows the rule, already has the idiom, and already has one job whose entire purpose is
enforcing it. **The two single-purpose legs are the ones the rule was never extended to** — and both are legs
whose whole value is the claim that a large population was exercised: `inv1-strong-2023`'s own header comment
(`:333-336`) calls the NIST golden battery *"the roadmap's fatal-challenge criterion"*, and `legacy-oracle`'s
(`:425-431`) calls its live-legacy cross-check *"the whole point of keeping the legacy engine alive through the
rearchitecture"*.

## Why it is MINOR and process-only, and where that could be wrong

`process_only: true` — no COBOL program's behavior changes. `silent: true` — the failure mode is a green check.
MINOR rather than MAJOR because the filters are **exact today** (PB287 verified `NistProgram_MatchesGolden` and
`Cobol85Program_StillCompilesAtLaterEdition` are unique method names in the tree, so they survive re-partition),
which makes this latent rather than live.

⚠ **The severity is a judgement about likelihood, not about consequence, and the consequence is large.** If it
does fire, the observable is a fatal-challenge criterion reporting success over zero of 349 goldens — PB287
called that *"the strongest single invariant in CI, silently retired"* and rated the same shape MAJOR while it
was live. A lander that finds evidence a rename is imminent (a partition of `DifferentialTests`, a rename of
`NistProgram_MatchesGolden`) should raise this, not re-argue it.

⚠ `legacy-oracle` additionally runs only on `schedule` / `workflow_dispatch` (`:434`), so a silent zero-test run
there is seen by fewer people and on a slower cadence — worse for detection, not better.

## The fix shape

Two admissible shapes; the report names both and they are not equivalent.

1. ⭐ **`scripts/filter_population.py`** — PB708's guard, the ONE place the "did this filter select anything"
   rule is to live. **Not on main today**; it is on branch `worktree-agent-a6d2907b763ee0741` (landing train 17).
   ⛔ It needs `python` and a built test project and **nothing else** — in particular it does NOT need the spec
   submodule, which matters here because both these jobs check out `submodules: false` (inv1-strong `:346`,
   legacy-oracle `:439`), the same constraint that keeps the citation audits out of CI ([[PB159]]). A negated
   term must be probed through its POSITIVE form (asking vstest for `!~X` returns everything and would call a
   stale exclusion live) — which is the whole reason `legacy-oracle`'s two-term filter needs the helper rather
   than a hand-rolled check.
2. **A `Total: N` floor from the step's own log** — `set -o pipefail`, `| tee`, then the same
   `grep -Eo 'Total:[[:space:]]+[0-9]+'` the shard legs already run at `:139`/`:266`, asserting `N >= 1`.
   ⚠ **A floor of 1 is much weaker than what the shard matrix has.** `conformance-population` compares the sum
   against a re-discovered population; `N >= 1` only proves the filter was not *completely* dead. For
   inv1-strong the honest bar is PB287's own sentence — *"asserting that the run actually saw 349 goldens"* — so
   the number should come from a discovery, not from a hand-maintained constant (CLAUDE.md rule 8: no
   hand-maintained lists where a structure belongs).

⛔ **Prove it fails once** (`feedback_green_gates_arent_evidence`): push a branch with `Zz` appended inside one
filter and confirm the leg goes RED, then revert. PB287's lesson is that this leg had been green on every run
while covering nothing, so a guard that has never been red is exactly the evidence that is missing.
