# PB4462 - semgrep is blind over most of the data binder, and verify.py does not say so

**Sites:** `scripts/semgrep/verify.py` (it reads the `results` of `semgrep scan --json` and ignores `errors[]`),
`scripts/semgrep/invariants.yml` (every `wiseowl-cobol-*` invariant rule), `scripts/semgrep/baseline.json`,
`src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs` (semgrep reports `PartialParsing` over old lines 14-4851 / 16-5194 on the
pre-extract file, and 16-4635 at the PB2355 head), `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.Reports.cs`,
`src/WiseOwl.Cobol.Compiler/Binding/DataBinder.Constants.cs`.

**What is wrong.** Semgrep's C# grammar cannot parse most of these three files; it reports `PartialParsing` and scans only the
spans it could read. `verify.py` compares rule COUNTS with `baseline.json` and never looks at `errors[]`, so a rule that matches
nothing in an unparsed span reads exactly like a rule that matches nothing in a clean one. Every architectural invariant (raw
diagnostic code literals, no-BigInteger, no-decimal, the rest) therefore under-counts across the data binder. The counts then move
for the wrong reason: PB2352 re-baselined `wiseowl-cobol-raw-diagnostic-code-literal` 225 -> 229 because 19 literals moved from an
unparsed file into parseable pass files (the dispatch said "must not increase"); PB2355's DEVLOG blamed 225 -> 226 on an
"interpolated string with an ellipsis" when the `COBOL1512` line is byte-identical at `FileControlBinder.cs:266` and the real
cause is the same parse gap (review R1-3). The guard fails silent in both directions: code that leaves the file looks like new
debt, and a violation added inside the span is never seen. PB175 recorded the same lesson for `ProcedureTableBuilder.cs` (one
small span) and proposed that `verify.py` fail on any `PartialParsing`; it was never done and the span is now thousands of lines.
The invariants the rules guard go blind, so `process_only` is false.

**Repro.** `semgrep scan --config scripts/semgrep/invariants.yml --json src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs`, read `errors[]`.

**Fix shape.** (1) `verify.py` fails (or fails above a span count baselined in `baseline.json`) on any `PartialParsing` error,
naming file and line span. (2) Bisect the construct semgrep's C# parser trips on in these files and either shape the code so it
parses or enforce the same invariants there with a Roslyn-based check. (3) Re-derive the raw-code-literal baseline once the files
parse, so the number is a measurement, not a floor.

## As landed (2026-11-02)

**What the re-probe showed.** The note's repro reproduced and was wider than three files: the old scan (`results` 278, `errors`
160) failed to read 213 product files in part and 5 wholly (`ReportSectionBinder.cs`, `VersionConformancePass.cs`,
`ConditionalPhrases.cs`, `Frontend.cs`, `BTree.cs`), across every project. The constructs semgrep's C# grammar cannot read are
valid C# 11-14 the product writes on purpose: a primary-constructor class header (every verb binder), a list pattern with a slice
designation, `extension` members, `allows ref struct`, a raw interpolated string. After a failure early in a class it drops a span
to the next member it can read (`DataBinder.cs` 14-4492). The data binder's three files named here were three of 213.

**The mechanism, found by experiment.** semgrep parses a file only when a rule needs the parse or has a hit. A single
`pattern-regex` rule is matched over the file's text and a hit inside an unread span is still reported (the regexes and an
independent Python pass agree on all 248 raw-code-literal hits, file by file, including the 18 inside `DataBinder.cs`'s unread
span); a `patterns:` block, even of regexes, parses first; a file that fails to parse at all ("Syntax error") loses every hit
to every rule. So the AST rules (`no-decimal`, `no-persistent-byte-storage`, `raw-diagnostic-code-literal`) and the one `patterns:`
regex rule (`integer-n-parsed-outside-host-value`) were the blind ones; the other five regex rules were not.

**Fix.** `scripts/semgrep/invariants.yml`: all nine rules are one `pattern-regex` (the three AST rules rewritten to match the same
declarations and calls, the `patterns:` rule's `pattern-not-regex` a lookahead). `scripts/semgrep/verify.py`: check 0 refuses a
rule that is not one `pattern-regex`; check 1 fire-tests every rule in `testdata/Violations.cs` and in the new
`testdata/Unparsed.cs` (a file semgrep reads only in part); check 2 reads `errors[]` (a `PartialParsing` span is counted and listed
by `--gaps`; anything else fails, naming the file) and compares the files semgrep cannot read at all with `WHOLE_FILE_UNREADABLE`
(the five, each with its first failing member; a stale or missing entry fails); `--self-test` covers the pure parts and runs in
CI's audits (no semgrep needed). The five files are named, not reshaped: they are valid C# and a lint tool's parser does not
decide the code (CLAUDE.md rule 4); a violation added to one fails `verify.py` loudly (the dropped hit surfaces as the file's
"Syntax error").

**Determination (owner decision pending; branch review R1-4).** The owner's requirement of 2026-11-02 was that `verify.py` fail
on a `PartialParsing` error over a guarded file and that the files it cannot parse become parseable or be named as an exception.
The landed check COUNTS a `PartialParsing` span (210 files, 467 spans) and does not fail on it, because every rule is now one
`pattern-regex` and was measured to match across an unread span (the Python pass and semgrep agree on all 248 raw-literal hits,
file by file); only a wholly unreadable file is fatal, and the five are named in `WHOLE_FILE_UNREADABLE`. Making the 210 files
parseable means rewriting valid C# 12-14 for a lint parser (CLAUDE.md rule 4 forbids it); the alternative is to make a span fatal
and name all 210 files, which names a blind spot that no longer exists. Overturn = make `classify_errors` return the spans as
fatal and extend the exception list. The owner confirms or overturns this.

**Sibling reader (branch review R1-1).** `scripts/arch/r2_inputs.py` (`run_semgrep`), which feeds the R2 review fleet, read only
`results` too, so a file semgrep rejects wholly showed its finders "no invariant hit". It now reads `errors[]` through
`verify.py`'s helpers (`is_partial_parse`, `error_path`, `describe_error`), names every wholly unreadable file in the shard
input's `semgrep_unread`, and stops on any other error (a timeout, a rule error).

**Re-measured.** `wiseowl-cobol-raw-diagnostic-code-literal` 230 -> 248 hits (the 18 the blind span hid, all in `DataBinder.cs`:
COBOL0898 x6, COBOL1625 x4, COBOL1530 x2, COBOL1537 x2, COBOL1532 x2, COBOL1536, COBOL1538); the other three counts are unchanged
(43, 3, 2). I9: the 11 sites whose descriptor already exists (COBOL1625 `ValueNumericOutOfRange`, which nothing referenced;
COBOL1571 x3, COBOL1627, COBOL1664 x3) now name it, so the baseline is 237. The remaining 237 sites carry 86 codes, none with a
catalog descriptor: that is PB4463's campaign (re-measured there), not a slice of this one.
