# PB3533 — the kept state is matched to its file by path only

## Lead (round-1 review lead R1-4, low; sibling of the vanished-file arm PB3493 fixed)

The kept state is matched to the file by PATH only (`src/Cobol.Net.Runtime/IO/KeyedConnector.cs:146`,
`TakeFileLock`). Every run-unit table (`StoreTable`, `PhysicalFileTable`, the kept state) keys a physical file by its
absolute path (`HostFile.PhysicalFileComparer`, kb/Work PB2748, `PhysicalFileIdentityDriftTests`). On a host that lets a
file be unlinked under an open handle (Linux), a file removed outside the run unit and then recreated at the same path is
present at the re-OPEN, so `TakeFileLock` adopts the kept handle (the unlinked inode) and `Attach` reuses the kept store.
The ending decision PB3493 applies to the absent arms is not applied when the path names a different physical file.

The review finisher answered it as a redesign beyond the branch (branch `worktree-wf_31aba3ec-d06-2`), so it is filed here.

### Repro (Linux)

Program A (APPLY COMMIT): OPEN I-O, WRITE 7, CLOSE (the state is kept). Outside the run unit, `rm` the file and create a
new file at the path holding record 2. Then A: OPEN I-O answers `00`, READ 2 answers `23`, READ 7 answers `00` (the removed
file's records are visible), and a COMMIT writes to the unlinked inode and is lost.

## Fix shape (for the implementer)

Telling a file removed and recreated at the same path from the kept one needs a host file identity (device and inode on
Linux, volume serial and file index on Windows) beside the path, as the key of the kept state and of the run-unit tables,
compared at `KeyedConnector.TakeFileLock` (KeyedConnector.cs:146) and at the `Attach` that reuses the kept store. Decide it
in the design (`docs/rearchitecture/DESIGN-runtime-library.md` section 2.2.x) before the code.
