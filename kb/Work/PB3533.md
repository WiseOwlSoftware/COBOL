# PB3533 — the kept state is matched to its file by path only

## Lead (round-1 review lead R1-4, low; sibling of the vanished-file arm PB3493 fixed)

The kept state is matched to the file by PATH only (`src/Cobol.Net.Runtime/IO/KeyedConnector.cs:146`,
`TakeFileLock`). Every run-unit table (`StoreTable`, `PhysicalFileTable`, the kept state) keys a physical file by its
absolute path (`HostFile.PhysicalFileComparer`, kb/Work PB2748, `PhysicalFileIdentityDriftTests`). On a host that lets a
file be unlinked under an open handle (Linux), a file removed outside the run unit and then recreated at the same path is
present at the re-OPEN, so `TakeFileLock` adopts the kept handle (the unlinked inode) and `Attach` reuses the kept store.
The ending decision PB3493 applies to the absent arms is not applied when the path names a different physical file.

The review finisher answered it as a redesign beyond the branch (branch `worktree-wf_31aba3ec-d06-2`), so it is filed here.

### Repro (Linux)

Program A (APPLY COMMIT): OPEN I-O, WRITE 7, CLOSE (the state is kept). Outside the run unit, `rm` the file and create a
new file at the path holding record 2. Then A: OPEN I-O answers `00`, READ 2 answers `23`, READ 7 answers `00` (the removed
file's records are visible), and a COMMIT writes to the unlinked inode and is lost.

## Fix shape (for the implementer)

Telling a file removed and recreated at the same path from the kept one needs a host file identity (device and inode on
Linux, volume serial and file index on Windows) beside the path, as the key of the kept state and of the run-unit tables,
compared at `KeyedConnector.TakeFileLock` (KeyedConnector.cs:146) and at the `Attach` that reuses the kept store. Decide it
in the design (`docs/rearchitecture/DESIGN-runtime-library.md` section 2.2.x) before the code.

## Landed (wave 1157, group C)

**Sites:** `src/Cobol.Net.Runtime/IO/Sharing/HostFileIdentity.cs` (new), `IO/Sharing/OfdRegionLocks.cs`, `IO/FileSupport.cs`,
`IO/KeptFile.cs`, `IO/FileConnector.cs`, `IO/KeyedConnector.cs`, `IO/IndexedConnector.cs`, `IO/RelativeConnector.cs`,
`IO/StoreTable.cs`, `IO/FileRegistry.cs`.

**Re-probe (Linux, the unfixed runtime, commit 6df15af12).** The ten new witnesses failed on the unit leg under WSL, and
nothing else (35588 passed): the replaced file's re-OPEN kept the transaction (`TransactionOf` 1, not 0); a re-OPEN of a
file another run unit holds under SHARING WITH NO OTHER answered '00' (it adopted the kept handle on the removed file)
where '61' is due; and a second connector of the run unit opening the path read the removed file's record 2 (`0002A002`,
not the new file's `0002B002`). On Windows the kept handle's share mode admits no delete, so the host refuses the
replacement.

**Fix (DESIGN-runtime-library.md 2.2.1.7 and 2.2.1.10).** The host's identity of a physical file
(`PhysicalFileIdentity`: `statx`'s device and inode on Linux, `FILE_ID_INFO`'s volume serial and 128-bit file id on
Windows; `HostFileIdentity`, now the runtime's one `statx` binding, which `OfdRegionLocks` reads too), asked through
`HostFile.IdentityOf(handle)` and `HostFile.IdentityAt(path)`.
- The kept state: `KeptFile.Identity` is taken from the CLOSE's handle, and an OPEN that finds a PRESENT file asks
  `FileConnector.EndWhatWasKeptOfAnotherFile` first, before the write probe, the file lock and the body read any of the
  kept state; `KeptFile.IsOfTheFileAt` false ends it (`ReleaseKept`) - PB3493's decision for a kept file that is not
  there - whatever the OPEN then answers (§14.9.27.4 GR25 is about the file the path names). It ends rather than retires
  because `PhysicalFileTable` holds one physical file per path. `KeptIsOfAnotherFile` is renamed `KeptIsOfAnotherPath`
  (the ASSIGN USING case of PB3494, unchanged).
- The sibling arm, the run unit's store table: `StoreTable` entries carry the identity of the file their store was opened
  on; an attachment (or a creation) through a handle on another file at the path gets a store of its own, and `Detach` is
  by store. `FileRegistry.TransactionHolders` tells a file's transaction by its store, not its path, so the COMMIT reaches
  both files' transactions.

**Witnesses.** `CommitRollbackRuntimeTests.A_reopen_of_a_file_replaced_outside_the_run_unit_ends_what_the_close_kept`,
`...An_unsuccessful_reopen_of_a_file_replaced_outside_the_run_unit_ends_what_the_close_kept` ('39', '61'),
`...Two_connectors_on_a_path_whose_file_was_replaced_each_reach_their_own_file`;
`PhysicalFileIdentityDriftTests.TheHostIdentity_TellsTheFileAHandleHoldsFromTheOneMadeAtItsPathSince` (both hosts);
`CrossRunUnitKeyedStoreDriftTests.AFileMadeAtAPathSinceGetsAStoreOfItsOwn`.

**Left as it is (recorded in 2.2.1.7).** Table 19's arbitration and the record-lock table (`PhysicalFileTable`) are still
keyed by the path alone, so two physical files at one path in one run unit are arbitrated, and their record locks held,
as one file's there.
