# PB777 — OPEN — an ungated phrase, and an edition claim with no derivation behind it

Filed 2026-09-06 by the registrar from the [[PB732]] implementer's report (`…\a9d94900…\scratchpad\reports\
PB732-report.md`, "New defects" (a)), re-derived against main rather than inherited.

⚠ **Naming, so the landing note does not go stale.** On main the phrase is an INLINE optional tail of
`valueClause`, not a named rule. [[PB732]] (train 19) extracts it as **`valueClauseFalsePhrase`**; whoever fixes
this on a tree that has train 19 will find it under that name and should put the predicate there.

⚠ **Derived by reading; not probed here.** No built `cobol.exe` exists in this worktree. [[PB732]]'s report
carries the measurement — *"`88 CN1 VALUE 1 WHEN SET TO FALSE IS 0.` compiled at `--std 85` with no
COBOLNET0900"* — and the code below is why. The implementer should re-run it before fixing.

## The two-arm contrast, on one grammar rule

`src/Cobol.Net.Frontend/Grammar/Core/CobolData.g4`, the condition-name arm of `valueClause` (`:642-673`), ends in
three optional tails:

```
:664      (IN IDENTIFIER)?
:665      (WHEN? SET? TO? FALSE_ IS? literal)?          ⛔ NO PREDICATE — this note
:672      ({is2002()}? validateValidPhrase)?            ✔ gated, with its reason in the comment above it
```

Five lines apart, on the same alternative, one gated and one not. The gated one even says why (`:670-671`:
*"`{is2002()}?` at the left edge of the optional block: VALID is a user-defined word at COBOL-85 (§8.9)"*), and
the ungated one carries a long, careful comment (`:646-662`) about which of its words are underlined and in what
ORDER the brackets print — every word of it correct, and none of it about editions.
`feedback_two_arm_dispatch`, and this time both arms are visible in one screenful.

The recognition side is the same shape.
`src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs:885-887`:

```csharp
public override object? VisitValueClause(CobolParserCore.ValueClauseContext ctx)
{
    if (ctx.valueClauseTablePhrase().Length > 0) _p.Check(Constructs.ValueTableFormat2002, "the Format 2 (table) VALUE clause");
```

One arm, for the Format 2 table phrase. Nothing for the Format 3 FALSE phrase.

## The rule, mechanically checked

`python scripts/spec/cite.py --check`:

- `13.18.63.2 "literal-4"` → **OK §13.18.63.2** (General formats): the Format 3 bracket is
  `[ WHEN SET TO <u>FALSE</u> IS literal-4 ]`.
- `13.18.63.4 "the value of literal-4 from the FALSE phrase is placed in the associated conditional-variable"` →
  **OK §13.18.63.4 20)** — the phrase's only effect, and only through the SET statement.
- `14.9.39.3 "If the FALSE phrase is specified, the FALSE phrase shall be specified in the VALUE clause of the
  data description entry for condition-name-1"` → **OK §14.9.39.3 7)** — the SET side of the same coupling.

⚠ The dispatch that produced this note cited *"§14.9.39 SR7"* for the same sentence and so does
`SetBinder.cs:459`; the checked clause is **§14.9.39.3 7)**. A `--check` of `14.9.39.3 "WHEN SET TO FALSE"` FAILS
— the SET rules never spell the phrase that way — which is the reason the number had to be re-derived rather
than copied (CLAUDE.md rule 1).

## ⛔ Premise correction — NOTHING in the repository derives the 2002 date

The dispatch said to *"confirm in `docs/VERSION_CHANGE_REFERENCE.md` and the 2002 change list"*. **Neither
confirms it, and that is the more important half of this note.**

- `grep -n -i "false" docs/VERSION_CHANGE_REFERENCE.md` → **two hits, both unrelated prose** (rows 7.16 ENTER and
  7.17 USE FOR DEBUGGING). **The VCR carries no row for this phrase.**
- `grep -n "WHEN SET\|SET TO FALSE\|FALSE phrase" tests/version-matrix/constructs.json` → **nothing.** No
  construct row, so no `ConstructRegistry` entry, so `_p.Check(...)` has nothing to call even if the visitor arm
  existed.
- The 2023 standard cannot supply the date. Annex E covers 2014→2023 only — the limitation the repository
  already records twice, at `constructs.json:1388` (*"Annex E covers 2014-2023 only, so the 2002 edge is derived
  from the ORDER reserved-word row … not from an E-list entry"*) and in the sibling arm's own row (below).
- The reserved-word axis is unavailable here: FALSE is §8.9-reserved at COBOL-85 already (EVALUATE's
  TRUE/FALSE), so `reserved-words.json` cannot date the PHRASE.

What the repository DOES have is two unsourced sentences in the compiler asserting the answer:

- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SetBinder.cs:454` — *"TO FALSE needs the 2002 `WHEN SET TO
  FALSE` …"*
- `:459` — `return new BoundUnsupported("SET condition-name TO FALSE (the VALUE … WHEN SET TO FALSE phrase,
  COBOL-2002+, ISO §14.9.39 SR7)");` — a sentence a USER can read, carrying an edition claim with no derivation
  and a clause number this note has just corrected.

So the defect has two layers and the second is the blocker for the first:

1. **The phrase is accepted at `--std 85`** while the compiler asserts it is a 2002 element — an ungated
   introduction (`under_rejects`, `silent`).
2. **The claim itself is unrecorded**, so the gate cannot be written until it is DERIVED and the derivation is
   written down. `feedback_a_dead_lookup_is_also_unverified`: a date nothing checks has never been contradicted.

## The precedent for the derivation, in the same general format

`tests/version-matrix/constructs.json:1753` / `src/Cobol.Net.Editions/ConstructRegistry.g.cs:156`:

```
new("value-table-format-2002", "the Format 2 (table) VALUE clause", 2002, null, null, "COBOLNET0900",
    "ISO 13.18.63.2 Format 2 (table); a COBOL-2002 addition (derived - COBOLNET_DATA_MODEL_DESIGN.md;
     the 2023 Annex E VALUE rows are numeric-edited only, the A1 gap D18)")
```

That is the shape this note needs, for the same clause's Format 3: a construct row whose `vcr` field states the
derivation and names where it was made, an introduction edition, COBOLNET0900, and a `VisitValueClause` arm
beside the existing one. The Format 2 arm of §13.18.63.2 was dated by derivation and recorded; the Format 3
FALSE phrase of §13.18.63.2 was not.

## Fix shape

1. **Derive the introduction edition and record it** — a VCR row plus the `constructs.json` row, `vcr` field
   citing the derivation exactly as `value-table-format-2002` does. This is the first work item, not the last.
2. **Gate the phrase at the left edge** — `({isNNNN()}? valueClauseFalsePhrase)?` in `CobolData.g4`, matching
   `validateValidPhrase` five lines below. ⛔ `feedback_left_edge_predicates`: the predicate steers prediction
   only at the left edge of the alternative; mid-alternative it lets the alt be chosen and then throws.
3. **The `VisitValueClause` arm** beside the table-phrase one, so the diagnostic is a named COBOLNET0900
   introduction rather than a parse error (the recognition-fired posture `:640` already describes for Format 2).
4. **The `new-construct` edition-gate sweep** — `constructs.json` row, the version-matrix cells, and the
   corpus sweep the skill mandates. ⛔ `feedback_edition_gate_sweep`: gating a construct breaks everything
   compiling it below that edition — [[PB732]]'s report already flags that
   `tests/conformance/85/pb732_value_symbolic_character` was deliberately NOT extended with a FALSE phrase for
   exactly this reason, so check the 85 corpus for existing FALSE-phrase uses before landing.

## ⚠ The other arm of the same feature, so the fix is not half a feature

`SetBinder.cs:459` makes `SET condition-name TO FALSE` — the phrase's ONLY consumer, per §13.18.63.4 GR20 — a
`BoundUnsupported` deferral at **every** edition. So today the phrase is accepted below the edition that
introduced it AND unusable at the editions that have it. Gating the phrase without noticing that leaves a
program at `--std 2023` able to WRITE `WHEN SET TO FALSE` and unable to USE it. Whether the SET side is in scope
is the implementer's call, but the note must not be closed claiming the feature works
(`feedback_spec_scopes_not_tests` — the fix is scoped by the spec, not by what a test happens to reference).
