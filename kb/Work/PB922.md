# PB922 — LANDED — the compiler says a name the standard declares does not exist

Source: the `PB449-finisher` report, "New defects" items 1 and 3. Re-measured here, both statements.

## The measurement

`<scratch>/reg7/probe/p_excobj_move.cob`, `--std 2023`:

```
p_excobj_move.cob(7,12): error COBOLNET1639: 'EXCEPTION-OBJECT' is not defined — no declaration in this
source element gives the name 'EXCEPTION-OBJECT', so the statement's reference identifies no resource
(ISO §8.4.2.1 …). Check the spelling, or declare the item.
p_excobj_move.cob(7,12): error COBOLNET0809: a MOVE operand shall not be of class object …
p_excobj_move.cob(7,22): error COBOLNET0901: 'EXCEPTION-OBJECT' is a reserved word in COBOL-2023 and cannot
be used as a user-defined word (ISO §8.9)
```

`<scratch>/reg7/probe/z_excobj_add.cob`, `ADD 1 TO EXCEPTION-OBJECT`, the same pair (1639 + 0901).

Read the two together: *"the name is not defined — declare it"* and *"the name is reserved — you may not
declare it"*. The user is given an instruction the next diagnostic forbids. And the advice is wrong
twice over, because the correct answer is neither: the name IS defined, by the standard, and the statement
is illegal for a third reason entirely.

## The rule

```
$ python scripts/spec/cite.py --check 8.4.3.6.3 "EXCEPTION-OBJECT"
OK  §8.4.3.6.3 1)  (Syntax rules)
    1) EXCEPTION-OBJECT shall not be specified as a receiving operand.
```

SR1 is a rule about **every** receiving operand in the language, not about SET. It presupposes the name is
known everywhere — which is the point: EXCEPTION-OBJECT is a predefined object reference (§8.4.3.6), so
`MOVE U TO EXCEPTION-OBJECT` is refused BY SR1, with SR1's words, and `MOVE EXCEPTION-OBJECT TO U` (a
SENDING use) is legal source that today gets the same false "not defined".

```
$ python scripts/spec/cite.py --check 8.9 "reserved word"
OK  §8.9   (Reserved words)
```

COBOLNET0901 is the reserved-word funnel firing because the general resolver did not recognise the name —
it is a SYMPTOM of the same hole, not a second defect.

## The code sites

* ⛔ **A THIRD spelling test** sits in `src/Cobol.Net.Compiler/Binding/Validation/VersionConformancePass.cs`

  `feedback_one_rule_one_place`: the extraction is the fix, and the fix is that the RESOLVER knows the
  predefined registers, so every caller inherits it.

### A SECOND consequence the gate caught, and its root fix

Teaching the resolver the name made the general SENDER arm of `OoBindSetObjectRef` claim EXCEPTION-OBJECT,
because that arm probes-then-resolves and its own comment said "EXCEPTION-OBJECT below is a legal alternative"
— i.e. the register reached its arm only by FAILING to resolve. So `SET <typed-receiver> TO EXCEPTION-OBJECT`
was screened against §14.9.39.3 SR12's closed list and REFUSED AT COMPILE TIME, where the register is implicitly
UNIVERSAL (SR2) and a typed receiver is answered by the RUN-TIME narrow check in the emitter (§9.3.8.2 —
EC-OO-UNIVERSAL on failure). Caught by `OoSpineTests.SetTypedFromExceptionObject_WrongClass_EcOoUniversal` at
the whole-assembly gate. The fix is the ORDER, not a special case: the predefined register is classified BEFORE
the general lookup, which is exactly what `SetFormatSelection.KindOf` already does on the receiving side. Two
expectations were also updated to the unified code (`conformance:negative/pb456-set-exception-object-receiver`
and `OoSpineTests.RaiseObject_BindViolations`'s SET row): ONE RULE, ONE CODE is the point of COBOLNET2196, so
COBOLNET0848 no longer answers for §8.4.3.6.3 SR1.
