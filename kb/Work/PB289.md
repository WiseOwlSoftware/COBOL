# PB289 - LANDED: the expression half of PB264's landing-scale fault

## Landed (wave 1039, group G)

**Re-probed on the base build** (`CALL "S" AS NESTED USING BY VALUE ONE / THREE` into a `PIC S9(5)V9(20)` formal, ONE and THREE `PIC 9`):
the formal received `0.33333333333333000000` (the receiver-less quotient's 14 guard digits; the note's "6 digits" was the SDIDI landing floor for the other
shapes). The INVOKE sibling (`INVOKE OBJ "FRAC" USING BY CONTENT (ONE / THREE)`) answered the same 14 digits, and a nested product past the `Int128` carrier
(PB1900) crossed as 10000000 for 1.

**Root cause.** `CallEmitter.ArgText`'s computed-operand arm (and `OoEmitter`'s two INVOKE expression sites) rendered the argument RECEIVER-LESS
(`ReceiverContext.None`), so the expression was evaluated before, and independent of, the formal's description — while §14.2.3 GR9's second branch and GR10 make the
crossing "a COMPUTE statement without the ROUNDED phrase" into a record of that description. PB165 has since landed `BoundCallArg.Formal` — the structure this note
waited for — so no second lookup is needed.

**Fix.** `ReceiverContext.Of(PicInfo, …)` is the ONE derivation of the context of a resultant of a given description (scale, floating-point-ness, integer-digit
capacity); the arithmetic statements' `RcvFor` now calls it too (the same rule was written twice), and `CallEmitter.ArgText` / `OoEmitter.FormalValue` render a computed
argument as the FINAL TRANSFER into the formal (`outermost: true`): the quotient lands at the formal's fraction digits with the implied TRUNCATION, a floating-point formal
evaluates in binary64, and a nested wide product is rounded once at the formal's scale. A call whose activating element does not know the formal (GR9's first branch,
`Formal == null`) keeps the receiver-less render — there is no resultant description. `COBOLNET_INTERPROGRAM_DESIGN.md` records the rule.

**Sibling sweep.** `CallEmitter.ArgText` (CALL lane, user-defined function reference), `OoEmitter` INVOKE content-expression sites (the float-formal arm and
`MethodNumericContent`) — fixed. The remaining receiver-less renders (`PtrEmitter`, `SetEmitter`, `KeyedIoEmitter`) are value-semantics consumers with no formal.

**Pinned by** `conformance:2002/pb289_argument_expression_lands_at_formal_scale` (CALL BY VALUE / BY CONTENT, a nested wide product, an exact product, and the INVOKE twin).

## Landing

- `src/Cobol.Net.Compiler/CodeGen/Roslyn/ReceiverContext.cs#Of` — the ONE derivation of the context of a resultant of a given PICTURE (scale, float, integer-digit capacity, float-edited); `ArithmeticEmitter.RcvFor`, `CallEmitter.ArgText` and `OoEmitter.FormalValue` all call it. REUSE it for any new "evaluate an expression for a known description" site.
- `src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs#ArgText` (computed-operand arm) — renders the expression as the FINAL TRANSFER (`outermost: true`) into the formal when `BoundCallArg.Formal` is a numeric item; null `Formal` (GR9's first branch) keeps `ReceiverContext.None`. Trap: `BoundComputedOperand` clears `_outermost` for its child (PB129) — render the inner `BoundExpr` directly.
- `src/Cobol.Net.Compiler/CodeGen/Verbs/OoEmitter.cs#FormalValue` — the INVOKE twin (the float-formal arm and `MethodNumericContent`).
- Open sibling found, not fixed: `A ** 2` over a fractional base is a binary64 approximation (see PB1900's Landing), so `CALL … BY VALUE A ** 2` still shows binary64 digits past the 16th.

## Original note

Split out of [[PB264]] at its landing (2026-09-02). PB264's second fault was that a BY VALUE argument landed at
`ReceiverContext.None`'s working scale rather than the formal parameter's. **The LITERAL half is fixed** - a
compile-time literal is now rendered exactly and never lands at all - **but the EXPRESSION half remains**, and it
is the half that needs a structure this wave did not have.

## The residue, stated exactly

`src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs`, the `BoundComputedOperand` arm:

```csharp
NumX x = num.Landed(NumericRenderer.DeU(num.Render(expr.Expr, ReceiverContext.None)), ReceiverContext.None);
```

`ReceiverContext.None` gives `Landed` `WorkingScale(NumvalScaleFloor)` = 6 fraction digits. An argument such as
`BY VALUE A ** 2` or `BY VALUE A / B` whose value has more than 6 fraction digits loses them BEFORE the callee's
own §14.2.3 GR10 conformance ("a COMPUTE statement without the ROUNDED phrase", against a formal that may hold
20 fraction digits) ever runs. The truncation is invisible: the callee cannot tell a value that arrived short
from one that was always short.

⚠ **Not yet measured with a run.** PB264's measured rows were all literals. This note claims the mechanism, read
from the code, and owes a probe before its golden's expected value is written
([[feedback_reachability_is_measured_not_deduced]]). The probe is a contained callee with a
`PIC S9(5)V9(20)` BY VALUE formal and `CALL ... AS NESTED USING BY VALUE 1 / 3`.

## Why it is blocked

Landing at the FORMAL's scale requires the resolved corresponding formal at the emitter, and `BoundCallArg` is
`(Mode, Place, Value, Omitted)` - it has no `Formal`. Carrying `DataItem? Formal` on `BoundCallArg` is exactly
[[PB165]] leg A's spine, which also serves §14.8.2.3.3's unchecked CONTENT/VALUE conformance arm, §14.2.3 GR9
regime 2, and GR12's forwarding. Fixing the scale here with a second, local lookup would be the parallel
mechanism that spine exists to prevent, so this rides PB165 rather than pre-empting it.

Note the carrier half of PB264's fault IS fixed independently: the cell is now `ManagedPointer<Int128>` with a
widening conversion, so an expression argument no longer wraps - it only loses sub-6-digit fraction.
