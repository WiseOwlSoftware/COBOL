# PB289 - the expression half of PB264's landing-scale fault

Split out of [[PB264]] at its landing (2026-09-02). PB264's second fault was that a BY VALUE argument landed at
`ReceiverContext.None`'s working scale rather than the formal parameter's. **The LITERAL half is fixed** - a
compile-time literal is now rendered exactly and never lands at all - **but the EXPRESSION half remains**, and it
is the half that needs a structure this wave did not have.

## The residue, stated exactly

`src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs`, the `BoundComputedOperand` arm:

```csharp
NumX x = num.Landed(NumericRenderer.DeU(num.Render(expr.Expr, ReceiverContext.None)), ReceiverContext.None);
```

`ReceiverContext.None` gives `Landed` `WorkingScale(NumvalScaleFloor)` = 6 fraction digits. An argument such as
`BY VALUE A ** 2` or `BY VALUE A / B` whose value has more than 6 fraction digits loses them BEFORE the callee's
own §14.2.3 GR10 conformance ("a COMPUTE statement without the ROUNDED phrase", against a formal that may hold
20 fraction digits) ever runs. The truncation is invisible: the callee cannot tell a value that arrived short
from one that was always short.

⚠ **Not yet measured with a run.** PB264's measured rows were all literals. This note claims the mechanism, read
from the code, and owes a probe before its golden's expected value is written
([[feedback_reachability_is_measured_not_deduced]]). The probe is a contained callee with a
`PIC S9(5)V9(20)` BY VALUE formal and `CALL ... AS NESTED USING BY VALUE 1 / 3`.

## Why it is blocked

Landing at the FORMAL's scale requires the resolved corresponding formal at the emitter, and `BoundCallArg` is
`(Mode, Place, Value, Omitted)` - it has no `Formal`. Carrying `DataItem? Formal` on `BoundCallArg` is exactly
[[PB165]] leg A's spine, which also serves §14.8.2.3.3's unchecked CONTENT/VALUE conformance arm, §14.2.3 GR9
regime 2, and GR12's forwarding. Fixing the scale here with a second, local lookup would be the parallel
mechanism that spine exists to prevent, so this rides PB165 rather than pre-empting it.

Note the carrier half of PB264's fault IS fixed independently: the cell is now `ManagedPointer<Int128>` with a
widening conversion, so an expression argument no longer wraps - it only loses sub-6-digit fraction.
