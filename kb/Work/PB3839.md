# PB3839 — native NUMVAL-F's value depends on its receiver

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Bound/IntrinsicCarrierRules.cs#ReturnsExactParse` (and `ExactParseFunctions`, the renamed `ValueFixedByDefinition`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/FunctionValueLane.cs#Of`, `src/WiseOwl.Cobol.Compiler/CodeGen/Emit/IntrinsicRenderer.cs#RenderNum` (the deleted `case "NumvalF"`, the `MaxScaled` / `MinScaled` arm), `src/WiseOwl.Cobol.Compiler/CodeGen/Emit/IntrinsicRenderer.cs#RenderDec` (and `StandardValueFixedByRule`), `src/WiseOwl.Cobol.Compiler/CodeGen/Roslyn/ReceiverContext.cs#WorkingScale` (the deleted `FloatWorkingScale`, `FloatScaleFloor` and `MoveSender`), `src/WiseOwl.Cobol.Compiler/CodeGen/Roslyn/ReceiverContext.cs#FloatLanding`, `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/MoveEmitter.cs#SenderContext`, `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/ArithmeticEmitter.cs#IntDigitsOf`, `src/WiseOwl.Cobol.Runtime/Intrinsics/CobolIntrinsics.Exact.cs#NumvalFDec` (the deleted `NumvalF` and `Rescaled`; `NumvalFDouble` kept for ACCEPT), `src/WiseOwl.Cobol.Runtime/Intrinsics/CobolIntrinsics.cs#FromDouble`, `src/WiseOwl.Cobol.Runtime/PublicAPI.Unshipped.txt`, `docs/CONFORMANCE.md` (the DOC-A.1-92 NUMVAL-F paragraph and the DOC-A.1-81 function clause), `docs/NUMERIC_DESIGN.md`, `docs/INTRINSICS_DESIGN.md`

## Owner decision

2026-10-26, approving the fix: "yes. We should always be consistent with ourself barring an explicit requirement
differently" (a standing rule), after asking "how the ISO spec says the behavior should be and how GnuCobol handles it".
Under the standing rule "We always strive to fix the root causes, never simply making the diagnostic pass".

## The spec

- §15.69.4 2): under native or standard-binary arithmetic "the returned value is an approximation of the numeric value
  represented by argument-1"; 3): under standard-decimal "the returned value is the numeric value represented by
  argument-1".
- §15.4.1: under native arithmetic "the characteristics and representation of the returned value are defined by the
  implementor" (the same-value-for-every-instance sentence is stated for the standard modes).
- §14.9.8.4 2) stores "the value obtained" by §14.7.4's single rounding at the receiver's scale.

So the native digits are implementor latitude, and CLAUDE.md rule 1 sends latitude to GnuCOBOL, then to self-consistency.

## Measured (GnuCOBOL 3.2 -std=cobol2014 under WSL; WiseOwl main 2026-10-26)

| Statement | GnuCOBOL | WiseOwl |
|---|---|---|
| NUMVAL-F("0.12340000000001") ROUNDED MODE AWAY-FROM-ZERO into 9V9(4) | 0.1235 | 0.1234 |
| NUMVAL("0.12340000000001"), same | 0.1235 | 0.1235 |
| NUMVAL-F("1.2340000000001E-1"), same | 0.1235 | 0.1234 |
| into FLOAT-LONG | 0.12340000000001 | 0.12340000000001 |
| DISPLAY FUNCTION NUMVAL-F(...) | 000000.12340000000001 | 0.12340000000001 |

WiseOwl gives one reference two values (the full value to DISPLAY and a float receiver, a 9-place truncation to a
fixed-point one) and rounds twice (truncate at the working scale, then round at the receiver's): the receiver-shape
dependence DOC-A.1-92's own NUMVAL paragraph rejects.

## Fix

One value for NUMVAL-F on every channel, the exact parse (the SDIDI NUMVAL already uses), so a fixed-point receiver
rounds it once; the binary64 stays only where the receiver is floating-point (one conversion of the exact value).
Rewrite DOC-A.1-92's NUMVAL-F paragraph to the new determination, citing §15.69.4 2), §15.4.1 and the GnuCOBOL
precedent. This also retires PB624's arm (the receiver-shape test it describes) — close PB624 in the same landing if
the arm is gone. Sweep every intrinsic whose value is chosen by its receiver's shape (`Receiver.Real` /
`Receiverless` tests in the emitter, `FloatWorkingScale` readers) for the same inconsistency.

## Acceptance

- Every row above matches GnuCOBOL's value; the same NUMVAL-F reference yields one value in DISPLAY, a fixed-point
  receiver (every ROUNDED mode, scales 0, 4, 9, 12, a trailing-P receiver), a float receiver and an operand position.
- A golden derived from the rules, not from either compiler; a drift test that fails if any intrinsic's value again
  depends on the receiver's shape.

## Landing (wave 20261711 group B)

**Re-probe on the wave's build (main 1b6af36e5):** every row of the table reproduced (`COMPUTE R4 ROUNDED MODE AWAY-FROM-ZERO` of
NUMVAL-F `0.12340000000001` and `1.2340000000001E-1` stored 0.1234; NUMVAL stored 0.1235). The sweep the note asked for found two more
receiver-dependent values, one inside the slice and one outside: **MAX / MIN** (fixed) landed a receiver-bound selection at the receiver's
own scale, so `MAX(0.12345 0.1)` into `PIC 9V99` ROUNDED MODE AWAY-FROM-ZERO stored 0.12 where §14.7.4.3 rule 3 owes 0.13, and
**MEAN** (not fixed, see below).

**Determination (every citation `cite.py --check` OK):** §15.69.4 2) approximation under native arithmetic; §15.69.4 3) the value itself
under standard-decimal; §15.4.1 "the characteristics and representation of the returned value are defined by the implementor"; §14.7.4.1
and §14.7.4.3 2)-10) the one rounding at the resultant. The approximation WiseOwl COBOL chooses is r3's value, the exact parse, as an SDIDI,
for every mode, channel and receiver: `IntrinsicCarrierRules.ReturnsExactParse` (the renamed `ValueFixedByDefinition`, now a set of three)
routes NUMVAL, NUMVAL-C and NUMVAL-F to `RenderDec`'s one arm ahead of the mode dispatch; the `RenderNum` arm that tested the receiver is
deleted with its two runtime bodies (`NumvalF`, `Rescaled`), `ReceiverContext.MoveSender` (its only reader) and `FloatWorkingScale` /
`FloatScaleFloor` (no remaining reader: the float family lands at the receiver's own scale since PB3829). A floating-point receiver
converts the exact decimal once and lands it as any decimal sender (a MOVE rounds to nearest, a COMPUTE truncates, CONFORMANCE.md item 81).
PB624's arm (the receiver-shape test with no mode guard) is gone with it.

**Consequences recorded in CONFORMANCE.md item 92:** `DISPLAY FUNCTION NUMVAL-F("5E+30")` prints the 31 exact digits (was `5E+30`);
`COMPUTE F = FUNCTION NUMVAL-F("1.5E-12")` into a COMP-2 stores what `COMPUTE F = 0.0000000000015` stores (1.4999999999999999E-12, the
truncated neighbour; was the nearest, 1.5E-12); a native argument past decimal128's range (`1E+7000`) is the §14.7.5 case 5 size error
condition instead of a binary64 Infinity / a saturated value. Goldens: `pb3839_numval_f_one_value` (28 legs, each failing on the old
compiler for the reason its comment names; measured on a build of the base commit), `pb3839_numval_f_beyond_the_sdidi`,
`pb3839_max_min_round_once`, the negative `pb3839_numval_f_below_2002`; `pb60_numvalf_native_channels` and `pb251_numval_native_value_fixed`
re-derived (their old expected values were the retired determination). Drift: `ReceiverShapeReaderDriftTests` (the receiver members
`IntrinsicRenderer` reads are a closed, justified set; the exact-parse functions have no `RenderNum` arm).

**Left open (a lead for the registrar):** `MeanScaled` (`IntrinsicRenderer.cs#RenderNum`) still reads `num.Receiver.Scale` / `Rounding` for its
quotient's working scale `max(receiver scale, sum scale + 1, 6)`, so `DISPLAY FUNCTION MEAN(0.00000001 0 ... 0)` (20 arguments, mean 5E-10)
prints 0.000000000 while `COMPUTE R12 = ...` stores 0.000000000500 and `COMPUTE R2 ROUNDED MODE AWAY-FROM-ZERO = ...` stores 0.00 where the
rule owes 0.01: the quotient is truncated at a receiver-dependent scale before the receiver's rounding mode sees it. The cure is the SDIDI
quotient (`MeanDec`, 34 digits, the standard modes' body) for every mode, a restructuring of the cross-aligning native arm beyond this slice.
