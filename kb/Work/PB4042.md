# PB4042 — set-condition-name-figurative-space-refused: -std=cobol2014: SET condition-name TO TRUE is refused when the 88 VALUE is SPACE and the item is numeric-edited

Filed 2026-10-29 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-20261028-210601`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

Under `-std=cobol2014`, cobc 3.2 refuses `SET condition-name TO TRUE` when the condition-name's VALUE is the figurative
constant SPACE and the conditional variable is numeric-edited: "invalid SET statement". The VALUE clause itself is
accepted (the same figurative constant in the data description entry compiles), and the same SET with the alphanumeric
literal `"     "` in place of SPACES compiles and runs. ISO places the literal into the conditional variable "according
to the rules for the VALUE clause", not by the MOVE statement's rules, so the MOVE-only prohibition of SPACE into a
numeric-edited item does not apply. The refusal does not depend on the dialect: every `-std` tried refuses it, and
LOW-VALUE in place of SPACES is refused the same way. Class: rejects legal source. Fuzz program fz01175 (night
fuzz-20261028-210601).

## Minimal test case

Free reference format.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. SETSP.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 E PIC Z(5) VALUE "  123".
   88 E-BLANK VALUE SPACES.
PROCEDURE DIVISION.
    SET E-BLANK TO TRUE
    DISPLAY "[" E "]"
    STOP RUN.
```

## Environment

`cobc (GnuCOBOL) 3.2.0`, Ubuntu package `gnucobol3 3.2-4build1`, WSL2 Ubuntu (Linux 6.18.54.1-microsoft-standard-WSL2
x86_64). Compiled with `cobc -x -free -std=cobol2014 -o setsp setsp.cob`; no executable is produced, so nothing is run.
Controls: the same program with line 6 written `88 E-BLANK VALUE "     ".` compiles and its run prints `[     ]`; with
line 6 written `88 E-BLANK VALUE LOW-VALUE.` it is refused with the same message; the unchanged program is also refused
under `-std=default`, `-std=mf`, `-std=ibm`, `-std=cobol85` and `-std=cobol2002`, although under `-std=mf` the statement
`MOVE SPACES TO E` compiles (with a warning).

## Observed result

Compile, exit code 1:

```text
setsp.cob:8: error: invalid SET statement
```

## Expected result (per ISO)

The program is legal; it compiles and prints `[     ]` (five spaces).

- §8.3.3.6.3 1) (checked): "A figurative constant may be used whenever 'literal' appears in a format or when a rule
  allows it", so SPACES is a valid literal-2 of the format 3 (condition-name) VALUE clause.
- §8.3.3.6.4 1) (checked): "Otherwise, when a figurative constant represents a character value, the figurative constant
  represents an alphanumeric character value." SPACE here is of class alphanumeric.
- §13.18.63.4 19) (checked): "The characteristics of a condition-name are implicitly those of its conditional
  variable." E-BLANK has the category of E, numeric-edited.
- §13.18.63.3 7) (checked): "If the item is of category numeric-edited and the literal is of class alphanumeric or
  national, the class of the literal shall conform to that of the data item": an alphanumeric literal is allowed for
  the numeric-edited conditional variable E (cobc accepts this VALUE clause).
- §8.3.3.6.4 2) (checked): "when this figurative constant is specified in a VALUE clause or in association with a
  fixed-length data item", the string is repeated to the item's size: five spaces.
- §14.9.39.3 6) (checked): "Condition-name-1 shall be associated with a conditional variable." E-BLANK is. No other
  syntax rule of SET format 4 restricts the literal.
- §14.9.39.4 6) (checked): "If the TRUE phrase is specified, the literal in the VALUE clause associated with
  condition-name-1 is placed in the conditional variable according to the rules for the VALUE clause". The VALUE
  clause's rules, not the MOVE statement's, govern the store.
- The diagnostic's argument is the MOVE statement's §14.9.25.3 5) (checked): "the move of an alphanumeric figurative
  constant (SPACE, QUOTE, HIGH-VALUE, LOW-VALUE, ALL "literal", or ALL symbolic-character) to either a numeric item or a
  numeric-edited item is prohibited". That is a syntax rule of the MOVE statement; no SET statement is written here as
  a MOVE, and §14.9.39.4 6) names the VALUE clause rules instead.

Edition: 2014. The 2002 standard and the 2009 committee draft for ISO/IEC 1989:2014 (CD 1.2) give the SET rule in the
same words (their SET general rule 5); CD 1.2's VALUE syntax rule 4 requires alphanumeric literals for an item of class
alphanumeric, which a numeric-edited item is; and its MOVE syntax rule 5 ("The figurative constant SPACE shall not be
moved to a numeric or numeric-edited item") is, as in 2023, a rule of the MOVE statement only. cobc's SET refusal is
not the dialect option `move-figurative-space-to-numeric` (which `-std=cobol2014` sets to `error` for MOVE): the SET
check refuses before that option is consulted, in every dialect.

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`): compiles with no diagnostic; the run prints `[     ]`,
exit code 0. On the fuzz program fz01175 it compiles and prints `SPACE-SEND [     ]` for the statement that follows.

## Fix site

`cobc/typeck.c`: `cb_emit_set_true` (and `cb_emit_set_false`) emit the store as `cb_build_move` of the VALUE literal;
`validate_move`, called with `is_value` 0, reaches its figurative-constant arm (SPACE, LOW-VALUE, HIGH-VALUE, QUOTE) with
a numeric or numeric-edited target and, when the current statement is SET (`STMT_SET` or `CB_CS_SET`), goes to its
`invalid:` label, which prints "invalid SET statement". That branch is taken before the `cb_move_fig_space_to_numeric`
check, so no dialect setting changes it. The VALUE-clause path (`is_value` 1) already admits SPACE for a numeric-edited
item.

## Draft issue

**Title:** -std=cobol2014: SET condition-name TO TRUE is refused when the 88 VALUE is SPACE and the item is numeric-edited

Environment: GnuCOBOL 3.2.0, WSL2 Ubuntu x86_64; `cobc -x -free -std=cobol2014 -o setsp setsp.cob`.

Program:

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. SETSP.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 E PIC Z(5) VALUE "  123".
   88 E-BLANK VALUE SPACES.
PROCEDURE DIVISION.
    SET E-BLANK TO TRUE
    DISPLAY "[" E "]"
    STOP RUN.
```

Observed: `setsp.cob:8: error: invalid SET statement`, exit code 1. With `88 E-BLANK VALUE "     ".` the program
compiles and prints `[     ]`. `VALUE LOW-VALUE` is refused the same way, and the refusal is the same under every
`-std` tried (default, mf, ibm, cobol85, cobol2002, cobol2014).

Expected: the program compiles and prints `[     ]`. ISO/IEC 1989:2023 §14.9.39.4 rule 6 (SET general rule 5 in the
2002 standard) places the condition-name's literal in the conditional variable "according to the rules for the VALUE
clause", and the VALUE clause allows SPACE for a numeric-edited item (§13.18.63.3 rule 7, §8.3.3.6.3; cobc accepts the 88
entry itself). The MOVE statement's prohibition of SPACE into a numeric-edited item (§14.9.25.3 5)) applies to MOVE, not
to SET. The check in `validate_move` reached from `cb_emit_set_true` could use the VALUE-clause rules (`is_value`) for
this store.
