# PB2919 — byte 0xFF has two characters

Filed 2026-10-10 by the train 1052 lander (phase 1b) from the wave 1052 E implementer's report
(`E:\COBOL-coord\scratch\reports\w1052e-PB2698-report.md`, lead B).

**Repro:** `E:\COBOL-coord\scratch\w1052e\dbg3.cob`. `01 G. 05 S PIC S9(9) COMP-5.` with `01 GX REDEFINES G PIC X(4)`;
`MOVE -2 TO S` then `IF GX = X"FFFFFFFE"` answers "not equal"; `MOVE X"FFFFFFFE" TO HX` (the same layout over T) then
`IF GX = HX` answers "images differ", although S and T hold the same value.

**Where.** The binary codec renders its bytes through `CobolNum.BinaryBytes`
(`src/Cobol.Net.Runtime/Values/Numeric/CobolNum.Image.cs`, about line 374), which maps each byte with
`StorageByte.ToChar` (`src/Cobol.Net.Runtime/Values/Text/StorageByte.cs`, line 45:
`b == 0xFF ? NativeCollatingSequence.HighValue : (char)b`, HighValue = U+FFFF). A hexadecimal alphanumeric literal maps
byte 0xFF to U+00FF. So the one storage byte has two character images depending on who wrote it, and every comparison,
MOVE or INSPECT through the alphanumeric view of a binary item whose bytes include 0xFF (every negative two's-complement
value) disagrees with the literal that spells the same bytes.

**Decide first (adjudication inside the fix).** Which image is the byte's: the HIGH-VALUE mapping exists so that
`MOVE HIGH-VALUE` into a binary item's view round-trips; the literal mapping is the hexadecimal literal's own rule
(§8.3.3.2, hexadecimal-alphanumeric literals). One mapping, used by the codec, the literal and HIGH-VALUE alike, is the
fix; the choice and its consequence for HIGH-VALUE go into CONFORMANCE.md. Sweep every other `StorageByte.ToChar` /
`FromChar` caller (packed, zoned sign nibbles, pointers) for the same split.


**Landed 2026-10-10 (wave 1056 D).** Re-probed on a fresh build first: `E:\COBOL-coord\scratch\w1052e\dbg3.cob` printed
`not equal` / `images differ` / `T is -2` / `S = T`; after the fix it prints `equal` / `same image` / `T is -2` / `S = T`.

**The adjudication.** One of the two mappings had to give. The storage-byte law (byte 0xFF is U+FFFF) cannot move: imaging
a binary 0xFF as U+00FF turns `IF REC = HIGH-VALUES` false after `MOVE HIGH-VALUES TO REC` (PB1759 step 0, owner R52). So
the HEXADECIMAL LITERAL moves. `cite.py --check 8.3.3.2.4 "each of which has the bit configuration specified by one
occurrence of hex-character-sequence-1"` is OK (§8.3.3.2.4 GR4 in this text): X"hh" is the character whose bit
configuration is hh, and the character whose DISPLAY byte is 0xFF is the law's U+FFFF. IBM, Micro Focus and GnuCOBOL agree
(X"FF" equals HIGH-VALUE; CLAUDE.md rule 1's precedence). This REVERSES a consequence sentence R52 and DOC-A.1-31 carried
("the literal `X"FF"` stays U+00FF") and the DOC-A.1-95 example (`ORD(X"80FF0041")` = 129, 256, 1, 66 is now 129, 65536, 1,
66): the owner should know; U+00FF stays writable as the literal `"ÿ"` or `FUNCTION CHAR(256)`.

**Mechanism and siblings.** `CobolLiteral.DecodeHexGroups` (the one alphanumeric hex decoder, perChar = 2) images each pair
through `StorageByte.ToChar`; a national group (perChar = 4, NX) is a UTF-16 code unit and is unchanged. Two private copies
of the pair-to-character mapping were folded into it: `CopyProcessor.DecodeHexadecimal` (the COPY library-text name;
deleted, now `CobolLiteral.DecodeHexDigits`) and `OptionsBinder.OneByteHexAlphanumeric` (the OPTIONS INITIALIZE fill byte,
a bare `(char)b`). Swept and clean: every other `StorageByte.ToChar/ToByte` caller (CobolNum.Image binary and packed,
PointerImage, CobolBits, RawBytes, FileCharacterSet) already routes through the law; `RecordFraming` and
`SequentialConnector` read Latin-1 text only to hand it to `FileCharacterSet.FromChannel` (the law).

**Witnesses.** Golden `2002/pb2919_hex_literal_ff_is_the_storage_byte` (REDEFINES of a COMP -2 against X"FFFFFFFE", the
same value through two items, `ALL X"FF"` as binary -1 and as HIGH-VALUES, X"FF" = HIGH-VALUE with ORD 65536, U+00FF not
HIGH-VALUE); unit `StorageByteLawDriftTests.HexAlphanumericLiteralPairsAreImagedByTheStorageByteLaw` (all 256 pairs, both
quote forms, `Decode`, `DecodeHexDigits`), `HexNationalLiteralGroupsAreCodeUnitsNotBytes`, and the drift scan now covers
`Cobol.Net.Frontend`. Six goldens that pinned the old literal were re-derived (`2002/l1c01_native_ordinal_positions_wide`,
`2002/l1c12_hex_alphanumeric_every_group`, `2023/pb1093_alphabet_high_value_tail`,
`2023/pb1759_high_value_is_the_highest_native_character`, `2023/pb329_line_sequential_charset_2023`,
`2023/pb3_ord_collating_tail`): where the program meant the character U+00FF it now spells `"ÿ"`, and each gained an X"FF"
leg with the new value. No new negative: hexadecimal alphanumeric literals below COBOL-2002 are already refused
(COBOLNET0900), which this change does not touch. The traceability-inventory note on DOC-A.1-95's row (PB1397) still
says U+00hh; inventory text changes only through a verdict batch, and no row's verdict moves.
