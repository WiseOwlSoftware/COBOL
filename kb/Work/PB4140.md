# PB4140 — prune_worktrees.lifecycle makes a FINISHED report whose lead note is terminal (rep.lead_terminal) the branch D

**Sites:** `scripts/prune_worktrees.py:849` (`lifecycle`).

Lead of the enqueue unit (2026-10-30 ~18:55Z). In `lifecycle` (prune_worktrees.py:849):

    if rep.lead_terminal:
        return 'DECISION', (f'{rep.name}: {rep.status}, but {rep.lead} is already landed: superseded (its work reached main through another branch); ...

fires for ANY finished report whose lead note is landed or retired (`reports.py:314`, `lead_terminal`), before the CLEAN-stamp and
unique-commit tests run. So a reviewed follow-up the operator files under an already-landed lead never reads WAITING TO LAND.

**Witness (2026-10-30 ~18:55Z):** `tooling-suite-partitions` (report `w20261772a-PB2527-report.md`, `Review: CLEAN` at b57ee378b, one
unique commit raising the conformance suite to 32 partitions, which two other branches' reds wait on) read DECISION; so did
`tooling-semgrep-1183` (`w20261772b-PB4007`).

**Fix:** "superseded" is true only when nothing unique remains: decide `lead_terminal` AFTER the coverage test, i.e. a report
reviewed CLEAN at the tip (`stamp_covers`) with commits that are not register-only (`unreviewed_since` / the branch's unique
non-register commits) is WAITING TO LAND, not DECISION; keep DECISION for a terminal lead with no unique commits. Pin with a survey
self-test of a terminal lead plus a CLEAN stamp plus one unique commit. (`reports.py` only supplies `lead_terminal`; if it is
changed, list its members with `python scripts/arch/source_units.py scripts/orchestrator/reports.py`.)

Harm: process only (no harm flag).

**Recurrence 2026-11-09 (worktree-wf_30df8fbb-94c-1, PB5044 follow-up), with a second cost.** A DONE branch carrying a
unique self-test witness under the landed lead PB5044 read DECISION "superseded". A resume unit decided "land" and handed
off `next_unit: enqueue`. `next_unit.py` rule 2 honours `enqueue` only while rule 5 (`enqueue_work`) finds agent work,
and rule 5 does not count a DECISION row, so the supervisor ran a SECOND resume unit (18:53) on the same row instead of the
enqueue unit. It would have kept doing so, since a CLEAN review stamp does not move the row (the `lead_terminal` arm is
read first). That second resume broke the loop by hand: a diff-only cobol-reviewer re-review of the conflict merge
f14ed081a8 (CLEAN, stamped), then `enqueue.py land` directly (PR #1432). The fix above removes both costs. Its pinning
self-test should also show that `next_unit` picks enqueue (or that the landing lane lands it) for such a row, so a decided
DECISION can never bring the resume unit back.
