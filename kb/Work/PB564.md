# PB564

## Mechanism — value-clause-p4
An unresolvable cobolWord operand in a VALUE clause is not rejected at bind; it is carried through as raw text and emitted into the generated C# as a bare identifier, so the user receives a Roslyn CS0103 instead of a COBOL diagnostic. The VALUE pipeline is raw-text based by design (DataBinder.ExtractValue returns the operand's source text and the emitter interprets it against the item's category), and a constant-name operand is meant to substitute its literal through DataBinder.Constants.ConstantValueRawText with an unresolved name rejected as COBOLNET1547; that rejection does not fire on either the Format-1 or the level-88 path. This is the sweep sibling of the Format-5 VALID hole -- fixing the grammar guard alone would still leave every misspelt or undeclared constant-name operand crashing the backend -- and it is the mechanism that turns that hole from a silent mis-parse into a crash.

### Expected, from the standard
13.10.3 SR2 / 13.10.4 GR1 admit an integer constant-name where a literal is written, 'as if [the] literal were written'; a name that resolves to no compile-time constant is not conforming source and must be rejected with a COBOL diagnostic (the project's own COBOLNET1547, documented for exactly this case in the DataBinder.Constants design comment). No input may reach the Roslyn backend as an undeclared C# identifier.

### Observed
MEASURED on both the Format-1 and the condition-name paths: the operand text is mangled into a C# name ('FOOBARL') and the compile fails with a raw CS0103, which tells the user nothing about their COBOL. The true owner of this rule is the VALUE-operand constant-name resolution (13.18.63.3 SR2 / 13.10.3 SR2), outside this part's rule set; it is filed here because GR24's row is the one it was found through and because the two defects share a repro.
