# PB327 — what the byte-addressed record area cannot express

**Rows:** `GR-14.9.27.4-5`, `GR-14.9.30.4-15`. Three subjects (open p3, read p2, start p2) each met the same
wall from a different rule; the wall is one.

## Part 1 — GR5's one-record-area guarantee, unavailable for a legal EXTERNAL FD record

`FD EF IS EXTERNAL.` with `01 P-REC. 05 N-PART PIC N(5) USAGE NATIONAL.` in two programs of one run unit fails
to compile: `DiagnosticCatalog.ExternalRecordNotCellBacked` — *EXTERNAL record ... cannot be cell-backed ...
recognized but not yet implemented*. Contrast `conformance:2002/oo_external_file_shared`, whose `PIC X(10)`
record works.

> §14.9.27.4 GR5: The successful execution of an OPEN statement makes the associated record area available to
> the runtime element. If the file connector associated with file-name-1 is an external file connector, there is
> only one record area associated with the file connector for the run unit.

`--check 14.9.27.4 "there is only one record area associated with the file connector for the run unit"` →
**OK**. The rule places NO restriction on the record's categories or usages.

The shared cell is byte-addressed, so a two-bytes-per-position national leaf, a USAGE BIT leaf and the
pointer/object classes cannot ride it: `DataBinder.Linkage.cs#ForceStringCanonical`'s `CellCapable` predicate
refuses them and `CallMakeExternal` then rejects the program.

## Part 2 — the national space fill of §14.9.30.4 GR15

> ... a trailing space is defined to be the national space character [for a national record area]

`--check 14.9.30.4 "a trailing space is defined to be the national space character"` → **OK**. The rule's other
two parts conform and are pinned by CA15: a short record is right-padded, and an over-length line-sequential
record truncates, succeeds with '06', and leaves the remainder for the next READ. `FileConnector.Fit` pads with
U+0020 unconditionally and the connector has no national branch at all — its streams are opened with
`Encoding.Latin1`. The leg could not even be exercised: `probe/natpad/NATPAD.cob` (`01 L-REC PIC N(5)` on a LINE
SEQUENTIAL file) is refused COBOLNET0899 at compile time.

## Part 3 — a national record key, so START's national legs have never executed

`probe/start-p2-f/p2f.cob` — an indexed file whose prime key is `05 IX-PRIME PIC N(4)`, with
`START IXF KEY IS EQUAL TO IX-PRIME WITH LENGTH 2` — fails: `error COBOLNET0899: national data in a file record
... the record codec is single-byte and the national character is two bytes`.

> §12.4.5.12.3 SR2: Data-name-1 and data-name-2 shall reference a data item of category alphanumeric or category
> NATIONAL within a record description entry associated with the file-name

`--check 12.4.5.12.3 "category alphanumeric or category national"` → **OK**, so a national prime key is legal
source. §14.9.41.4 GR13 then makes arithmetic-expression-1 *the number of national character positions* for such
a key, and GR17 e) routes the comparison through §8.8.4.2.9 rather than §8.8.4.2.7. Neither leg has ever
executed. The START rows themselves are owned by **PB355**/**PB357**/**PB358**; this note owns the reason they
cannot be closed.

## Landed — 2026-09-05

The fix was the two-byte record codec, as the Disposition below predicted, and it closed all three parts at
once. **`AsImage()`/`FromImage()` is a group's STORAGE face**, and NATIONAL was the last leaf kind shipping its
carrier instead of its bytes (a numeric leaf already contributed its radix-2/BCD/IEEE bytes, a `USAGE BIT` run
its §8.5.1.6.3 packing). It now contributes two UTF-16BE bytes per position through the ONE serializer
`CobolBits.NatBytes` and its inverse `NatReadWindow` — the pair the Tier-B window, the EXTERNAL/BASED cell seed
and CONVERT's raw-storage channel already ride. The width authority moved with it: `RecordLayout.PhysicalWidth`
/ `OffsetOf` and `PhysicalModel.BuildPhysicals` read `ByteWidth`, which IS `ImageWidth` for every other leaf
kind — so the change is byte-identical for national-free programs, and `ImageWidth` stays the CARRIER authority.

- **Part 1 (EXTERNAL FD record).** `ExternalRecordNotCellBacked` no longer applied when this landing started —
  PB231 had already opened the cell — so the wall on today's tree was `GateNationalRecords` alone. That gate is
  now `DataBinder.GateFileRecordByteSurface`, the THIRD caller of `ByteWindowResidueOf`, exactly as PB231's
  paragraph on that predicate instructed. Witness `conformance:2002/pb327_national_fd_record`.
- **Part 2 (§14.9.30.4 GR15).** `FileConnector.FitRecord` is the ONE record-area fit and pads a national area
  with the national space's two bytes `00 20`; `TrimRecordEnd` is the write-side inverse. The emitter tells the
  connector which area it has (`EmitNationalAreaRegistration` → `CobolFile.RegisterNationalArea`), reading the
  record's OPERAND category so an elementary national record and a GROUP-USAGE NATIONAL one answer alike.
  Witness `conformance:2002/pb327_national_line_sequential_fill`.
- **Part 3 (national record key).** The key window registers in BYTES (`pk.ByteWidth`), the START key operand
  goes through the ONE storage channel, and §14.9.41.4 GR13's LENGTH is scaled from national POSITIONS to bytes
  at the one place the two units meet. Witness `conformance:2002/pb327_national_record_key`. The START ROWS
  themselves stay with **PB355/PB357/PB358** — this note owned only the reason they could not be closed.
- **Rows re-verdicted:** `GR-14.9.27.4-5` PARTIAL → CONFORMS, `GR-14.9.30.4-15` PARTIAL → CONFORMS (GAP
  2830 → 2828).

**What the landing also had to decide, and it is a determination change the owner should see.** A group's
OPERAND value is its image, so an ALPHANUMERIC group containing a national leaf now MOVEs, compares and
DISPLAYs as its bytes. §13.18.29.4 GR2's own NOTE states that consequence — "Without the GROUP-USAGE NATIONAL
clause, the content of such a group item would be treated as category alphanumeric, possibly leading to
corruption or invalid handling of data" — and names the remedy, which is now implemented: a national group
keeps its character alphabet through a generated `AsNat()`/`FromNat()` face and a `NatImagePlace`, exactly as a
bit group keeps its boolean alphabet through `AsBits()`/`FromBits()`. It also removed a real disagreement:
`FUNCTION LENGTH(G)` answered 8 for `01 G. 05 A PIC X(2). 05 N PIC N(3).` while `MOVE G TO R` moved five
characters. `docs/CONFORMANCE.md` DOC-A.1-57's "one sanctioned width divergence" is gone with it — a
variable-length group's displayed width now EQUALS `FUNCTION LENGTH` — and `pb164_vlg_display` was re-derived.

## Follow-up 2026-09-05 — the record-area CATEGORY selector was reading the WIDEST description (found by [[PB329]])

`EmitNationalAreaRegistration` decided §14.9.30.4 GR15's record-area category from `FileModel.AreaRecord`, the
WIDEST record description. For this note's own golden shape — `01 L-REC PIC N(4).` beside `01 L-BYTES PIC X(8).`
— that selected the ALPHANUMERIC sibling and registered nothing, so `2002/pb327_national_line_sequential_fill`
never exercised the national path it was written to pin: its WRITE shed one 0x20 through `string.TrimEnd` and
left a SEVEN-byte line ending in half a national position (the exact trap this note's header describes), and the
READ then re-padded it ALPHANUMERICALLY back to the same eight bytes — so the golden was green on the right
bytes for the wrong reason. It surfaced only when §14.9.51.4 GR23's character-set test needed the same flag and
refused the write with '71'. The selector now fires when ANY of the FD's record descriptions is national, which
§13.18.33.4 GR3 licenses ("Multiple level 1 entries subordinate to a FD or SD entry represent implicit
redefinitions of the same area") and §14.9.51.4 GR21/GR22 require (they key the trailing-space rule on
*record-name-1*). The golden's expected output is unchanged and its physical line is now the four bytes
`00 43 00 44` the header claims. ⚠ Residual, recorded not fixed: the flag is per-CONNECTOR while GR21/GR22 are
per record-name-1, so an FD describing one area both ways answers national for both.

## Disposition

The staging is LOUD and documented (`docs/DIAGNOSTICS.md`'s COBOLNET0899 `national-data` row lists *national
keys* explicitly), so nothing here is silent — but it is not a DECLARED non-support either: `docs/CONFORMANCE.md`
§A.3 items 41-42 declare only that NATIONAL-KEY COLLATING is not claimed (COBOLNET1584), which is a narrower
statement than *a national key cannot be written*. Recorded as `residue` because the fix is the two-byte record
codec, not any of these three rules; whoever lands that codec closes all three at once.
