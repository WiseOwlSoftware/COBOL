# PB4480 - dead arms and unwitnessed codes behind PB4463's descriptors

Read on origin/main `ae067404f`; every site below still reads as described.

1. **COBOL5996 is unreachable.** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/IntrinsicBinder.cs` (`BindFunctionResult`, the `sig.Name is "CHAR" && nationalArg` arm,
   message "FUNCTION CHAR takes an integer operand"). Per the PB4463 reports COBOL1627 refuses the same argument first (probe `FUNCTION CHAR (N)` with `N PIC 9V9`, and
   `CHAR (1.5)`). Fix: delete the arm and its descriptor, or delete the earlier screen, whichever the probe shows is the owner of the rule; keep one.
2. **COBOL1503 is unreachable.** `IntrinsicBinder.cs` ~666 (`sig.RemovedIn is { } gone`) reports `DiagnosticCatalog.IntrinsicFunctionRemoved`, but no
   `IntrinsicCatalog` row carries `RemovedIn` (PB2620 measured 0 of 94), so the code has no golden and no path. PB2620 (open) already owns the window-verdict
   unification and the permissive-severity divergence for this arm; the dead arm is its precondition. Decide there: delete the arm until a row needs it, or keep it with a
   fixture catalog row that drives it in a unit test.
3. **Codes no test or refusal golden asserts.** A grep of `conformance-suite` and `tests` (excluding `tests/doc-facts`) finds no mention of COBOL5996, COBOL5979
   (any-length subject not in header, ISO 13.18.2.3 SR3/SR4, `LinkageBinder.cs`), COBOL5998 (PERFORM WHEN unknown file), COBOL0894 or COBOL1503. Each needs a refusal golden
   (rule, `refuse-at`, `expect: COBOLnnnn`), written from the spec rule with `cite.py --check`, or its arm is item 1/2's dead code. A drift test "every catalog descriptor
   is asserted by some golden or carries a reason" would make the next case automatic.
4. **Band descriptors.** COBOL0808, 1504, 1514, 1516, 1546, 0897, 0890-0892, 1511 and 0844 each cover several rules under one code (PB4463's landed note names the
   bands). Split a band per rule when a rule needs its own golden or message (the COBOL1512 pattern); do it with item 3, not separately.
