# PB237

**Rows:** `SR-14.9.4.3-16`, `GR-14.9.4.4-7`, `GR-14.9.4.4-9`, `SR-14.9.5.3-3`, `GR-14.9.5.4-1`, `FMT-14.9.5.2`

**GR-14.9.4.4-9 ADOPTED FROM PB238 (2026-09-05), AND CLOSED AT LANDING TRAIN 4.** PB238 closed GR9's two
implementable legs — a)2's non-receivable-identifier leg (a constant-name is literal-2, an object property takes
§14.9.4.3 SR20's carve-out) and b)'s literal mode (derived from the formal, not from the copy-out skip). What
kept the row PARTIAL on PB238's own tree was leg (c), and leg (c) is THIS note's mechanism: GR9 reads the
CORRESPONDING FORMAL, and with no §12.3.8.2 PROGRAM specifier no source could declare a program-prototype, so a
formal existed only under AS NESTED. The row moved here rather than holding PB238 open, because PB238's own
mechanism was landed and a defective row must name the note that can actually close it. ⛔ On the MERGED tree
the leg is witnessed: `2002/pb237_program_prototype` declares `PROGRAM SCALE-IT AS "PB237MUL"`, `PB237MUL` is
`PROCEDURE DIVISION USING BY VALUE LK-V RETURNING LK-R`, and the keyword-less `CALL SCALE-IT USING WS-N` prints
`SCALED =0004` with `UNCHG  =0002` — the caller's operand is unchanged, which is true only if GR9 b) derived
BY VALUE from the PROTOTYPE's formal (`ResolvePrototype` → `callee ??= proto2.Signature` →
`calleeFormals` → `Gr9BareLiteralMode`), and §14.2.3 GR10 then kept the callee's stores off the caller. The
row is re-verdicted CONFORMS at landing train 4 with both goldens as its `test-ref`.

no source can declare a program-prototype-name — the REPOSITORY grammar has no §12.3.8.2 PROGRAM specifier — so `CALL … AS <prototype>` is COBOLNET0899, a prototype CANCEL target is a RUN-time NotImplemented, and one unsupported CANCEL target silently discards the legal targets beside it.

Rows: SR-14.9.4.3-14, SR-14.9.4.3-16, GR-14.9.4.4-7 (CALL), SR-14.9.5.3-3, GR-14.9.5.4-1 (CANCEL). ONE absent declaration surface, five rule rows.

MECHANISM (from the rows' own READ evidence). `repositoryEntry : FUNCTION ALL INTRINSIC | FUNCTION functionName INTRINSIC? | CLASS className | INTERFACE interfaceName | PROPERTY propertyName ;` (CobolParserCore.g4:366) has no program-specifier, so no source this compiler parses can DECLARE the name every one of these rules takes as its subject. CallBinder.BindCall consequently rejects the entire non-NESTED AS arm with DiagnosticCatalog.CallAsPrototypeName (COBOLNET0899, category RecognizedNotImplemented) whose text quotes SR16 verbatim, then returns BoundNop. CallBinder.BindCancel has literal and dataReference arms only, so a prototype name arrives as a dataReference, fails ctx.Refs.Resolve, and becomes `BoundUnsupported($"CANCEL target '{dref.GetText()}'")` → StatementEmitter.cs:211 `Visit(BoundUnsupported n) { _ctx.Writer.Line(LoudStmt(n.Feature)); return false; }` → EmitCore.cs:93 LoudStmt → `NotImplemented.Run(...)`: a RUN-time failure naming nothing about prototypes, with no diagnostic channel touched.

PER-ROW RESIDUE.
- SR-14.9.4.3-16 (cite.py OK, §14.9.4.3 16, FORMAT 2): the obligation is to RESOLVE program-prototype-name-1 against the REPOSITORY and reject a name that is not there. No code does that because no name can be there. conformance:negative/pb46-call-as-prototype-name pins the loud NON-SUPPORT, not the rule — a green test holding a gap open.
- SR-14.9.4.3-14 (cite.py OK, rule 14): needs BOTH operands and neither exists — a restricted program-pointer (`USAGE PROGRAM-POINTER TO program-prototype-name-1`, §13.18.60 GR25) is refused at declaration (tests/conformance/negative/program-pointer-restricted), and the prototype name is unparseable. BindCall's only program-pointer logic is `if (place.Item.Pic?.Category is PicCategory.ProgramPointer) isPointerTarget = true;` — no signature model anywhere on the CALL path.
- GR-14.9.4.4-7 (FORMAT 2): with AS present and NESTED absent the prototype determines the called program's characteristics — its externalized name (§12.3.8), its SR14/SR25 signature, and the BY REFERENCE/BY VALUE mode of each formal that GR9 then consults. The arm binds no prototype at all.
- SR-14.9.5.3-3: CANCEL must validate that program-prototype-name-1 names a REPOSITORY prototype; BindCancel has no third arm and no registry lookup, so there is no subject to validate and no diagnostic to fire.
- GR-14.9.5.4-1: two of the rule's three identification forms ARE matched — identifier-1's CONTENT read at execution (a BoundFieldOperand rendered `({OperandText.AsString(dynamic, num)}).Trim()`), and literal-1 decoded through CobolLiteral.Decode with ConcatFolder.Fold for §8.8.3.3 GR3 — and §8.3.2.2 2)a)'s implementor-defined word mapping IS realized by ProgramTable.NameEquals (OrdinalIgnoreCase) plus the emit-site Trim (a COBOL word cannot contain a space, so the Trim is a word-mapping step, not a value change). Only program-prototype-name-1 is absent.

SECOND, INDEPENDENT DEFECT ON THE SAME PATH, carried here because it is the same statement and the same line: CallBinder.cs:242's `return new BoundUnsupported(...)` sits INSIDE the per-target loop, so ONE unsupported target discards the whole statement including targets already accumulated in `targets` — `CANCEL "A" <prototype-name>` loses the perfectly legal "A" cancel, silently at compile time and loudly only at run time. That is the `silent` flag; fix the loop even if the registry lands later.

WHAT WOULD CLOSE IT: the P13 program-prototype registry — the §12.3.8.2 PROGRAM specifier in repositoryEntry, a prototype signature model, CALL … AS <prototype-name> binding with §14.8.2/§14.8.3 conformance, an SR14 signature comparison for restricted program-pointers, a BindCancel arm resolving against the registry with its own diagnostic — plus a positive golden per row and negatives for a name not in the REPOSITORY and for a signature mismatch. Ground rule 6 keeps every one of these rows NOT-IMPLEMENTED rather than DOCUMENTED-NON-SUPPORT: program prototypes are mandatory 2002+ surface, not an Annex A.4 optional module, so no docs/CONFORMANCE.md §4 licence covers them.

SPEC REFS as carried by the rows: §14.9.4.3 SR14/SR16 (both cite.py OK); §14.9.4.4 GR7; §12.3.8.2 program-specifier; §13.18.60 GR25; §14.9.5.3 SR3; §14.9.5.4 GR1 with §8.3.2.2 (spec lines 4756-4764, the 1)/2)a)/2)b) split); §7.3.4 GR2 (CALL-CONVENTION, which is unimplemented, so 2)a) is the arm that applies).

## FMT-14.9.5.2, attached here by the registration wave

CANCEL's general format has three brace alternatives and the third is `program-prototype-name-1`, which has NO production: a bare prototype word falls into `dataReference`, `ctx.Refs.Resolve` fails, and `CallBinder.BindCancel` returns `BoundUnsupported`, emitted as `NotImplemented.Run(...)` — a RUN-time failure, not a compile diagnostic. That is one mechanism with this note's: no source can declare a program-prototype-name because the REPOSITORY grammar has no §12.3.8.2 PROGRAM specifier, so every prototype-shaped operand in every statement lands on the same staged-loud path. The row's second, SEPARABLE residue stays attached to it: `cancelTarget+` with two or more operands has no golden (`recursive_ws.cob` carries a single target), and the comma-separator half was probed and REFUTED — `CANCEL "A", "B".` parses, because `COMMA_SEP` skips a comma-space before the parser sees it.

## Landed — 2026-09-05

**LANDED: the program-prototype registry, whole.** All five rows this note now owns are CONFORMS
(`SR-14.9.4.3-16`, `GR-14.9.4.4-7`, `SR-14.9.5.3-3`, `GR-14.9.5.4-1`, `FMT-14.9.5.2`). The sixth row the
implementer's branch still carried here, `SR-14.9.4.3-14`, is a DIFFERENT mechanism — the RESTRICTED
PROGRAM-POINTER, a DATA DIVISION usage feature — and landing train 4 reassigned it to **`PB609`**, which owns it
in its own `inventory_rows`. See "Reassigned residue" below.

**What landed.** `CobolParserCore.g4#repositoryEntry` gained §12.3.8.2's program-specifier
(`PROGRAM programPrototypeName repositoryAsPhrase?` — kb/Work PB303 later folded `repositoryAsPhrase` into
the shared `externalizedNamePhrase`, and `BindProgramSpecifier`'s literal screen into the shared
`Binding/ExternalizedName.Screen`; the rules and the diagnostic are unchanged), gated 2002+ by the new
`repository-program-2002`
constructs.json row through `VersionConformancePass.ParseArm.VisitRepositoryEntry` beside its CLASS / INTERFACE /
PROPERTY siblings. `DataBinder.BindProgramSpecifier` collects the written specifiers and enforces §12.3.8.3 SR1
(repeated specifications shall be identical) and SR2 (literal-3's class), inheriting into contained units beside
its REPOSITORY siblings. `BinderDriver.BuildProgramDefinitionTable` + `ProgramPrototypesOf` resolve them through
§12.3.8.4 GR10 and register §8.4.6.8's specifier-free spelling (a containing program definition's program-name),
which is also how §12.3.8.3 SR15's "this specifier is ignored" is realized. `CallBinder` consumes the table at
BOTH reference sites through ONE `ResolvePrototype` lookup and ONE `BarePrototypeWord` shape test. Design doc
`docs/COBOLNET_INTERPROGRAM_DESIGN.md` **D6** records the whole pipeline.

**Two findings that changed the fix from what this note predicted.**

1. **The rendered §14.9.4.2 Format 2 (PDF page 619) puts the word `AS` INSIDE the optional bracket:**
   `CALL ⎡{identifier-1 | literal-1} AS⎤ {NESTED | program-prototype-name-1}`. So Format 2 has TWO spellings, and
   the second — `CALL <program-prototype-name-1>` with no target operand and no `AS` — is spelled exactly like
   Format 1's `CALL identifier-1` and already parses. **No `callStatement` grammar change was needed**; the
   discrimination is semantic and is done by probing the data reference first. §14.9.4.4 GR3 b)'s third bullet
   ("If neither identifier-1 nor literal-1 is specified, program-prototype-name-1 determines the externalized
   program-name") exists precisely for that spelling, and the g4 comment above `callStatement` had paraphrased the
   format with the bracket DROPPED — corrected in the same change set.
2. **This note's "SECOND, INDEPENDENT DEFECT" no longer existed.** The per-target
   `return new BoundUnsupported(...)` inside `BindCancel`'s `foreach` was already gone: PB130 and PB154 rewrote
   the loop to report-and-`continue`, so `CANCEL "A" <prototype>` had not been discarding "A" for some time. The
   `silent` flag is retired. Re-probed on the base tree (`408e360f`): a prototype CANCEL target drew
   `COBOLNET1639` (§8.4.2.1 not defined) at COMPILE time, not the run-time `NotImplemented.Run` the note
   describes.

**Reproduction on the base tree, before the fix** (built `cobol.exe` at `408e360f`):
`REPOSITORY. PROGRAM PROTO-CE AS "PB237CE".` → `error COBOL0001: unexpected 'PROGRAM'`;
`CALL "X" AS SOMEPROTO` → `error COBOLNET0899` (the staged non-support, now retired).

**Diagnostics.** `COBOLNET1760` `program-prototype-undeclared` — the ONE §14.9.4.3 SR16 / §14.9.5.3 SR3 rejection
for both verbs, a PERMANENT conformance verdict. `COBOLNET1761` `repository-program-specifier` — §12.3.8.3
SR1/SR2. The 0899-staged `CallAsPrototypeName` descriptor is DELETED (its text asserted that no source can declare
a program-prototype-name, which is no longer true), and `conformance:negative/pb46-call-as-prototype-name` was
rewritten from pinning that staging to pinning the SR16 rejection.

**Goldens.** `conformance:2002/pb237_program_prototype` (both Format-2 CALL spellings; a specifier with and
without `AS literal-3`; GR9 b)'s formal-decides BY VALUE mode with §14.2.3 GR10's no-writeback observed; SR25 →
§14.8.3 RETURNING conformance; a two-target CANCEL reaching a program through its prototype; §14.9.5.4 GR3's
initial-state effect on the next call; §8.4.6.8's containing-program spelling from a contained program, whose
call §14.9.4.4 GR3 f) refuses with EC-PROGRAM-RECURSIVE-CALL routed to ON EXCEPTION). Negatives:
`pb46-call-as-prototype-name`, `pb237-cancel-prototype-undeclared`, `pb237-repository-program-literal-class`,
`pb237-repository-program-inconsistent`, `pb237-call-prototype-argument-count`.

## Reassigned residue — `SR-14.9.4.3-14`, owned by `PB609` since landing train 4

SR14 compares TWO signatures and now exactly one of its operands exists. The prototype's signature is in hand
(`ProgramPrototype.Signature`, from §12.3.8.4 GR10 a)); the RESTRICTED PROGRAM-POINTER is not. That half is a
DATA DIVISION usage feature with its own rules and its own rows — §13.18.60 GR25 (`USAGE PROGRAM-POINTER TO
program-prototype-name-1`, still staged loud at declaration by `DiagnosticCatalog.ProgramPointerRestricted`),
§13.18.60.3 SR19 ("If program-prototype-name-1 is specified, the TYPEDEF clause shall be specified for the subject
of the entry" — so the obvious spelling `01 P USAGE PROGRAM-POINTER TO T.` is itself nonconforming, exactly as its
already-implemented data-pointer twin §13.18.60.3 SR18 is), plus the SET and `ADDRESS OF PROGRAM` screens. It is
the SIBLING ARM of the restricted DATA-pointer that PB153 landed: `StrongTypeModel.PointerRestriction` answers only
for `PicCategory.Pointer`'s `RestrictedTypeName`, and `PicCategory.ProgramPointer` has no carrier at all. That is
the two-arm-dispatch shape, and it got its own note rather than a second mechanism in this one: `PB609` owns
`SR-14.9.4.3-14` from landing train 4 onward.
