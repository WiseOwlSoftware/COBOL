# PB5616 - the toolchain probe called a tool that did not answer "absent"

**Sites:** `scripts/toolchain.py` (`_run`, `installed`, `compare`, `check`), `scripts/gate_host.py` (`HostTools`, `Host.toolchain`),
`scripts/gate.py` (`Gate._gate`), `scripts/gate_reuse.py` (`PassCarry.reusable`, `PassCarry.rederive`),
`scripts/gate_verdict.py` (`NOT_RUN_CAUSES`), `scripts/gate_fake_host.py` (`FakeHost.toolchain`),
`scripts/linux-gate.sh#toolchain_report`, `scripts/hooks/tooling_check.py` (`toolchain_line`, `check`, `self_test`).

**What happened.** On 2026-11-15 08:38Z a gate on the Windows dev box ended

    === BUILD-LOCAL GATE: NOT RUN [toolchain] — this host's tools are not toolchain.env's: dotnet-sdk absent (toolchain.env
    10.0.404). Install the manifest's versions ... nothing ran (run 000004-20261115T083827Z) ===

(record: `E:\COBOL\.claude\worktrees\agent-a60a037ae8d133427\TestResults\build-local\000004-20261115T083827Z\verdict.json`).
The three gate runs minutes before it on the same host and tree recorded `dotnet-sdk 10.0.404`, and the next run found it
again: the SDK was never absent. The host was under heavy load (three gate slots, some forty agents running compiler
probes). The worker that hit it re-ran the gate.

**Root cause.** `toolchain._run` returned None when `shutil.which` found nothing, when `subprocess.run(..., timeout=60)`
timed out, and on any `OSError` or `SubprocessError`; `installed` turned None, and also an answer that carried no
version, into None; and `compare` printed every None as "absent". Four different facts (not on PATH; did not answer in
60 s; failed to start; answered something that is not a version) were reported as one, the wrong one, and the gate told
the operator to install a tool that was installed. The evidence that would have said which it was was thrown away, so
the flake cannot be root-caused from its record.

**The fix (this landing, the first half).** The probe keeps what happened, as a value every caller must handle:
`toolchain.Probe` is `Answered(text, exit_code)`, `NotOnPath()`, `TimedOut(limit_s)` or `NoStart(error)`, and
`installed` answers `Reported(version, fact, unread)`. Only "not on PATH" is ABSENT. A tool on PATH whose version could
not be read is UNREAD and still fails the check (an unresolved version never passes), under its own name:

    dotnet-sdk absent (not on PATH)
    dotnet-sdk did not answer within 60 s
    dotnet-sdk could not start: <the OS error>
    dotnet-sdk answered no version: "<first 200 characters of its output>", exit <code>

`toolchain.py check` exits 1 for an absent or mismatched tool (install the manifest's version) and 3
(`EXIT_UNREAD`) when the only failures are unread versions. The gate (`Host.toolchain` answers `HostTools(cause, tools)`)
stops `NOT RUN [toolchain]` with the install advice for the first, and `NOT RUN [toolchain-unread]`, a new ENVIRONMENT row
of `gate_verdict.NOT_RUN_CAUSES`, for the second: it names the tool and what happened, says the tool is not shown to be
missing, and gives no install advice. `linux-gate.sh` maps check's exit 3 to the same tag; `enqueue.py`, the landing lane
and `--await` read it through `read_verdict` and the one table, so they needed no change. The SessionStart readiness check
says UNREAD, not ASK-OWNER, for an unread tool.

**Not done, on purpose.** No retry was added and the 60 s limit (`toolchain.PROBE_LIMIT_S`) was neither raised nor
removed: either would be a guess at a cause nobody has seen.

**The open half (why the status is `half`).** The cause of the 08:38Z occurrence itself is still unknown: it may have
been the 60 s limit on a loaded host, a failed process start, or an error from `dotnet` itself. With the fact now in the
verdict line and its record, the next occurrence of `NOT RUN [toolchain-unread]` says which, and that occurrence is fixed
at ITS root under this note (a new finding beside it, `kb/Work/PB5616/<date>-<slug>.md`, with the record's path). The note
flips to `landed` with that fix.
