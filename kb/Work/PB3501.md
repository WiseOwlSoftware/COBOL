# PB3501 — the two-attempt Open over kept record locks is unwitnessed

Lead R1-1 (low) of the branch review of PB3482 (PR #360). `src/Cobol.Net.Runtime/IO/FileConnector.cs` about line 868: merge 7120a09ac composes the two-attempt `FileConnector.Open` with main's kept record-lock endpoint (`Lock` gives the kept handle back; `AbandonOpen` and `RetakeKeptHandle` rehome the record locks; the second attempt rehomes them again). Traced by hand it is correct, since each attempt is a whole abandoned re-OPEN, but no test pins it.

**Failure scenario.** Run unit A: commit-controlled, writes, CLOSE, re-OPEN INPUT (owes writes). Run unit B: APPLY COMMIT, SHARING WITH READ ONLY, OPEN I-O beside A (second attempt), REWRITE record 3, CLOSE (kept handle ReadWrite share, record lock 3), re-OPEN INPUT: the first attempt is refused by A's writable handle after the kept handle was given back, `AbandonOpen` retakes it and `Attach` rehomes lock 3, the second attempt succeeds. A regression in either half (`RetakeKeptHandle` not republishing, or `_givenBack` left set between attempts) lets run unit C READ record 3 with 00 instead of 51, and no test fails.

**Fix shape (MANDATORY-PRACTICES I11).** Add a `CommitRollbackRuntimeTests` case for that sequence asserting C gets 51 on record 3 after B's second-attempt re-OPEN, and 00 after B's COMMIT. Take the expected values from the governing clause (`cite.py --check` it first). Sibling gaps: PB3497 (not-retaken arm), PB3498 (refused second attempt).

**Sites:**
- `src/Cobol.Net.Runtime/IO/FileConnector.cs`
- `tests/Cobol.Net.Tests.Unit/Store/CommitRollbackRuntimeTests.cs`

## Landed

Re-probed: the behaviour was already right (the merge of PB3482 under PB3480/PB3484 composes correctly, as the lead traced by
hand); the witness was missing. `CommitRollbackRuntimeTests.A_two_attempt_reopen_over_a_kept_handle_keeps_the_record_locks_it_was_closed_with`
(both organizations) builds the lead's sequence: run unit A (commit control) changes a record, is CLOSEd and re-OPENed INPUT, so
it owes writes through a writable handle; run unit B (commit control, SHARING WITH READ ONLY, LOCK MODE automatic with multiple
records) OPENs I-O beside it (the second attempt), READs record 2 (a record lock) and REWRITEs record 3 (its transaction), is
CLOSEd and re-OPENed INPUT. The `ColumnRequestLog` seam counts the re-OPEN's host requests: replace, restore, replace (the first
attempt refused after the kept handle was given back, the retake, the second attempt) on a host with mandatory share modes, one
elsewhere. A third run unit then reads record 2 ('51', §9.1.16) and record 3 ('51', the holding) and record 1 ('00'); B's COMMIT
makes records 2 and 3 readable and record 3 holds B's value. Mutation-checked: with the record-lock rehome removed from the
attach, or the retake removed from `AbandonOpen`, the case fails.

One expected value differs from the lead's text: the lead's third run unit READs record 3, which B REWROTE; that answers '51' by
the transaction's HOLDING alone (liveness byte), not by a record lock. The case adds record 2, which B only READ, so the
record-lock endpoint is witnessed on its own; and the third run unit must take part in record locking (a LOCK MODE clause, which
SHARING WITH ALL OTHER requires of a file not under APPLY COMMIT, §14.9.27.3 SR8) to meet a record lock at all.

For the next implementer: `tests/Cobol.Net.Tests.Unit/Store/CommitRollbackRuntimeTests.cs#A_two_attempt_reopen_over_a_kept_handle_keeps_the_record_locks_it_was_closed_with` is the model for a two-attempt OPEN over a kept state; `ColumnRequestLog` counts the attempts. Traps: a third run unit meets a record lock only if it takes part in record locking (a LOCK MODE clause), and a connector holding more than one record lock needs LOCK MODE automatic with MULTIPLE RECORDS (`RegisterSharing(..., multiple: true)`), else its REWRITE releases the lock of the record it read.
