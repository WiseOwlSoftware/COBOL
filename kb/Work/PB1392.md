## Finding — `complex-combined-conditions` (under-rejects; rows `FMT-8.8.4.11.2`)

**Mechanism.** The COBOL-2023 XOR/EXCLUSIVE-OR introduction gate (Constructs.LogicalXorOperator2023) fires only from VersionConformancePass.VisitLogicalXorExpression; the EVALUATE partial-expression spine's own XOR tier (grammar partialXorExpression, bound by ConditionBinder via BindFlatSequence '^') has no gate arm, so the 2023-only operator is silently accepted below 2023 in that position (a two-arm dispatch with one arm gated).

**Repro.** 01 A PIC 9 VALUE 1. 01 B PIC 9 VALUE 2. PROCEDURE DIVISION. EVALUATE A WHEN > 5 XOR B = 2 DISPLAY "W1" WHEN OTHER DISPLAY "W2" END-EVALUATE. -- pinned cobol.exe --std 2014 (probe/ccc/g4.cob).

**Expected from the spec.** COBOLNET0900 (the logical XOR/EXCLUSIVE-OR operator requires COBOL-2023), exactly as the full-condition spelling IF A = 1 XOR B = 9 receives at --std 85/2002/2014: §E.3.2 4) records 'Logical operators have been enhanced to include 'EXCLUSIVE-OR' and 'XOR'' as a 2023 change.

**Observed / reasoning.** Compiles clean at --std 2014 and prints W1; the full-condition form is gated (probe g1.cob). VersionConformancePass has no VisitPartialXorExpression override.

**Code site.** src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs#VisitLogicalXorExpression; src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4#partialXorExpression

## What the fixer owes

Gate the construct from ONE place that sees every XOR token in a condition (both logicalXorExpression and partialXorExpression, or the token itself), and add an EditionGate drift arm so a new XOR-bearing rule cannot escape. Negative golden: `EVALUATE TRUE WHEN A = 1 XOR B = 2` at --std 2014.
