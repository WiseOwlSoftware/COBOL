# PB2882 — a landing-gate valley measured but not removed

**Source:** PB2880 (wave 1050 A, measured 2026-10-09 with the counter API; report w1050a-PB2880-report.md), lead 2.

**Measured:** self-test long poles set the implementer's pre-slot audit phase: landing_check.py --self-test 93-174 s (a serial git chain on one scratch repository), gate_slot.py 65-108 s, prune_worktrees.py 57-103 s, and filter_population.py --self-test 89-166 s in the post-build half.

**Code site:** `scripts/orchestrator/landing_check.py:276` (`self_test`); `scripts/orchestrator/gate_slot.py`, `scripts/prune_worktrees.py`, `scripts/filter_population.py` (their `--self-test` arms).

**What closes it:** One root cause across the four: serial process chains inside a self-test. One note covers them (one mechanism, one note). Measure each arm's chain, then share or parallelize the fixture setup; the implementer's audits stay ahead of its gate slot (fail fast, PB2523).

**Rule:** none (process tooling, no ISO clause).

## Re-measured after PB2914 (2026-10-10, wave 1051 V) — what remains

PB2914 took these long poles off the implementer gate's path rather than shortening them: an implementer gate now
REUSES the recorded PASS of every self-test whose inputs its change did not touch (a `src/`-only change re-ran 2 of 69
in 10 s, a `kb/Work` edit 4 of 69 in 10 s), every self-test that does run takes a place in one machine-wide budget,
and the lander runs them all beside its legs. Shortening the chains themselves was not cheap in that change (each is a
fixture redesign of its own self-test), so it remains here. Measured on a quiet host, the whole phase 32-wide
(`python scripts/self_tests.py`, 69 ran in 71-76 s): the twelve `test_orchestrate_*.ps1` parts 48-75 s each,
`landing_check.py --self-test` 52.7 s (one serial git chain over one scratch repository), `gate_slot.py --self-test`
36.8 s. Where it still costs:
- the LANDER's gate and CI run every one, beside the legs (the lander's whole phase is about 75 s against ~4 min of
  legs, so it is off its critical path today);
- an implementer whose change touches a script a long pole reads (e.g. `scripts/orchestrator/orchestrate.ps1`, read
  by all twelve parts) pays the poles again;
- the Unit leg re-runs several self-tests through C# drift tests that check their arms by name (`GateSlotDriftTests`,
  `GateLegDriftTests`, `SelfTestDiscoveryDriftTests`, `LandingLeaseDriftTests`, …) under the harness's 120 s
  per-process budget, where `gate_slot.py --self-test` measured 85-96 s under fleet load (kb/Work PB2897): a timeout
  there is retried once and then fails the Unit test as a `HarnessNonObservation`. Shortening `gate_slot.py`'s chain is
  the root; a drift test that reads the runner's recorded arm lines instead of re-running the self-test would remove the
  duplicate run.

**Sibling (train 1052 lander, 2026-10-10; wave 1051 V report `E:\COBOL-coord\scratch\reports\w1051v-PB2914-report.md`, "New defects"):** `scripts/gate_slot.py` `_GUARD_S = 90.0` (about line 696; used at about lines 717 and 735) is a per-event HANG guard inside its own self-test that raises `AssertionError` when an arm has not seen its event in 90 s, which the runner reports as RED, not HANG. Since PB2914 (train 1052) the self-test run is bounded by the shared budget, so this guard is the remaining place where a slow host reads as a failure; shortening `gate_slot.py`'s chain (the root above) and making the guard's expiry a HANG are the fix.

## Sibling: the orchestrator self-tests serialize on WMI (train 1053 lander, 2026-10-10)

**Source:** wave 1053 A's report (`E:\COBOL-coord\scratch\reports\w1053a-PB1941-report.md`, "New defects" 2) and
wave 1053 G's (`w1053g-PB2695-report.md`, "New defects" 2), one root. Three of 53A's gates and one of 53G's ended
`SELF-TESTS RED … NO LEG RAN` on 900 s timeouts of the `test_orchestrate_*.ps1` parts. Those gates ran on base
`471d0e954`, before PB2914's machine-wide budget and recorded-PASS reuse reached main (train 1052), so 53G's "pool not
rationed across gates" half is PB2914's mechanism and is closed there. What PB2914 does not touch is a long pole of a
different kind inside the orchestrator parts themselves:

**Measured (53A, 2026-10-10 15:0x PDT):** host CPU 26 % while about 100 pwsh orchestrator self-test processes ran; one
`Get-CimInstance Win32_Process` took 8.8 s. Each `test_orchestrate_*.ps1` part and `coord.py#process_table`
(`scripts/orchestrator/coord.py` line 174; the query at line 180 enumerates every Win32_Process with its CommandLine)
go through the one WMI provider, which serializes them, so wall-clock grows while the CPUs idle. A timed-out test took
up to 1717 s to be reaped (`scripts/self_tests.py`, `TIMEOUT_S`).

**What closes it (this half):** the orchestrator parts must not enumerate processes through WMI per assertion: one
process snapshot per test (or a fake `process_table` the parts inject, as they already fake `wt.exe`), and
`coord.py#process_table` reading the table once per call site that needs it. Repro: run four implementer gates whose
changes touch `scripts/orchestrator/orchestrate.ps1` (so the parts are not reused) and read each gate's
`=== SELF-TESTS:` line and the host CPU.
