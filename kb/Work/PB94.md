# PB94 — LANDED — `01 V PIC 9 VALUE "abc".` failed in the C# backend; `01 X PIC X(2) VALUE 12.` compiled clean

> ⚙ **flags:** crashes (a compiler-internal failure surfaced to the user as `error CS0103: The name 'abcL' does not
> exist`), under-rejects, silent · found 2026-08-18 writing [[PB82]]'s entry-cursor test · **landed 2026-08-18**
> (DEVLOG 1319).

**Measured (before)** (`scratchpad/pb82/val.cob`, `val2.cob`, `--std 2023`):
- `01 V PIC 9 VALUE "abc".` → exit 70, "backend compilation failed … CS0103: The name 'abcL' does not exist" — the
  alphanumeric literal was rendered as a numeric initializer.
- `01 W PIC 99 VALUE "7".` → accepted, `W=07`; `01 X PIC X(2) VALUE 12.` → accepted, `X=12`;
  `01 A PIC 9(3) VALUE SPACES.` → accepted, `000` (the fill silently dropped); `VALUE ALL "1"` on `PIC 9(3)` → CS1003.

**Spec:** §13.18.63.3 SR2 — "If the category of the subject of the entry is numeric, all literals in the VALUE
clause shall be numeric and shall be permissible values within the range indicated by the PICTURE clause or the
USAGE clause"; SR4 — "If the item is of category alphabetic, alphanumeric, or alphanumeric-edited literals in the
VALUE clause shall be alphanumeric literals". Both are ALL FORMATS syntax rules at every edition (the condition-name
VALUEs of Format 3 included); the first case is a REJECT that must never reach the backend (rearch exit criterion
9). CCVS-85's only quoted VALUE on a numeric picture (`NC107A`: `PICTURE 999 VALUE "000" BLANK WHEN ZERO`) is a
numeric-EDITED item (§13.18.8 GR2), where SR6/SR7 admit it — consistent with the rules.

**Mechanism (as found):** `DataBinder.ValidateValueCategory` carried the national (SR5) and boolean (SR10) halves and
"an N/B literal seeds only its own category"; the numeric-subject CLASS test and the alphanumeric-subject class test
were missing (the numeric RANGE half, `ValidateNumericValue`, existed — `PIC 9 VALUE 123` was rejected).

## As built (DEVLOG 1319)

`ValidateValueCategory` returns the raw text to STORE and grows two legs, both **COBOLNET1657** (`ValueLiteralClass`):
- SR2 (numeric subject): an alphanumeric literal or `ALL "…"` — error strict; under `--permissive` a digits-only
  content (ALL digits repeated to the digit width, §8.3.3.6.4 GR2) is stored as that NUMBER with a warning, and a
  content that is not numeric in form is an error on both axes (no more `abcL`); a character figurative (SPACE /
  QUOTE / HIGH-VALUE / LOW-VALUE) — error strict, ZERO with a warning saying so under `--permissive` (a native
  numeric item holds no character fill). Figurative ZERO stays legal.
- SR4 (alphabetic / alphanumeric / alphanumeric-edited subject): a numeric literal — error strict; under
  `--permissive` its characters as MOVE would store them, with a warning.
- The four call sites (the item VALUE, the 88 single values, the 88 THROUGH range) store what the validator returns,
  so the permissive rewrite reaches the initializer and the condition tests through the ONE funnel.

**Evidence:** negatives `pb94-value-alphanumeric-on-numeric`, `pb94-value-numeric-on-alphanumeric`,
`pb94-value-nonnumeric-on-numeric` (1657, all editions); `ValueLiteralClassTests` (7 permissive rows with their
values, the both-axes error, 5 legal shapes incl. `PIC 999 VALUE "000" BLANK WHEN ZERO`, the 88 on a numeric
variable). Inventory SR-13.18.63.3-2 and -4 → CONFORMS.
