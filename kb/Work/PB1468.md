## Finding — `simple-relation-conditions-p1` (under-rejects; rows `GR-8.8.4.2.1-6`, `GR-8.8.4.2.1-8`)

**Mechanism.** F2 — no comparability screen for the §8.8.4.2.1 'Comparisons are defined for' list: CollatingModel.ForComparison sends every numeric-vs-alphanumeric/national pair to the alphanumeric arm and CheckRelationalOperands has no arm for class pairs outside the list, so comparisons the standard does not define compile clean and run as an undocumented extension

**Repro.** 01 N1 PIC 9(3)V9 VALUE 12.5. 01 NC PIC 9(4) COMP VALUE 12. 01 X4 PIC X(4) VALUE "0125". 01 XC PIC X(4) VALUE "0012". 01 IDX1 USAGE INDEX. 01 NI PIC 9(3). …  IF N1 = X4 …, IF NC = XC …, IF IDX1 = NI …, IF IDX1 = 3 …, IF I1 = X4 … (I1 an index-name)  -> all compile clean at 85/2002/2014/2023; run prints Y for N1 = X4 and NC = XC. Also accepted: COMP-3 / FLOAT-LONG / literal 1.5 / arithmetic expression `NI + 1` against an alphanumeric item; a non-integer numeric against a numeric-edited item. (probe srel1/gen.py, srel2/und.cob)

**Expected from the spec.** §8.8.4.2.5: 'The numeric integer operand shall be an integer literal or an integer numeric data item of usage display or national' — a non-integer, COMP, COMP-3, float or arithmetic-expression operand vs an alphanumeric/national operand is not a defined comparison. §8.8.4.2.13: 'Relation tests may be made only between' two index-names, an index-name and a numeric item/literal, an index data item and an index-name or another index data item — IDX1 = NI, IDX1 = 3, IDX1 = X4 and I1 = X4 are not. Each is class-distinguishable at compile time, so §4.2.2 requires at least the warning mechanism to flag it; CONFORMANCE.md documents no extension.

**Observed / reasoning.** No diagnostic at any edition. The defined cases (integer DISPLAY vs alphanumeric, index-name vs numeric) evaluate correctly, so the fix is a screen over the class/usage pair at the ONE checkpoint, not a semantics change. The index half overlaps §8.8.4.2.13's own rows in part p2.

**Code site.** src/Cobol.Net.Compiler/Binding/CollatingModel.cs#CollatingModel.ForComparison (numeric-vs-alphanumeric falls through to Alphanumeric unconditionally); src/Cobol.Net.Compiler/Binding/Validation/StatementValidation.cs#CheckRelationalOperands (no comparability arm)

## Finding — `simple-relation-conditions-p2` (crashes; rows `GR-8.8.4.2.13-2`, `GR-8.8.4.2.13-3`)

**Mechanism.** The §8.8.4.2.13 'Relation tests may be made only between' pairing restriction has NO enforcement: StatementValidation.CheckRelationalOperands (the one checkpoint every relation reaches — IF, EVALUATE, PERFORM UNTIL, SEARCH WHEN) screens boolean, strongly-typed and Format-3 operands but has no arm for class INDEX, so an index-name or index data item is accepted opposite any partner. An index-name vs an alphanumeric operand compiles clean and aborts the run unit; an index data item vs a numeric literal/item/ZERO/alphanumeric compiles clean and is silently evaluated.

**Repro.** 01 T1. 05 E1 PIC X(4) OCCURS 5 INDEXED BY I1.  01 XA PIC X VALUE "3".  01 N3 PIC 9 VALUE 3.  01 IDA USAGE INDEX.  PROCEDURE: SET I1 TO 3. SET IDA TO I1. then separately (a) IF I1 = XA DISPLAY "Y" ELSE DISPLAY "N" END-IF -> compiles with no diagnostic, run throws NotImplementedCobolFeatureException 'computed expression in a string context' (same with IF I1 = "3"; --std 85 and 2023); (b) IF IDA = 3 / IF IDA = N3 / IF 3 = IDA -> compile clean, print Y; IF IDA = ZERO -> N; IF IDA = XA -> compiles clean, prints N. Probe sources: E:\Temp\claude\E--CobolSharp\a700c052-f9e4-4942-84ff-a13c7505d6ec\scratchpad\adj-d2\out\probe\srcp2\r1..r7.cob (pinned adj-d2 cobol.exe).

**Expected from the spec.** §8.8.4.2.13: 'Relation tests may be made only between 1) two index-names … 2) an index-name and a numeric data item or numeric literal … 3) an index data item and an index-name or another index data item.' §8.8.4.2.1 item 8 defines comparisons involving indexes only through that list. Every probe pair (index-name vs alphanumeric item/literal; index data item vs numeric literal, numeric item, ZERO or alphanumeric item) is outside the list, so each shall draw a compile-time diagnostic at every edition (85/2002/2014/2023); none shall compile, and none shall reach run time.

**Observed / reasoning.** CheckRelationalOperands (StatementValidation.cs ~1430) contains CheckFormat3Relation, the figurative-association check, the boolean COBOLNET0844 arm and the strong-group arms — nothing asks IntrinsicResultType.OperandCategory / the item's class for INDEX. The index-name binds as BoundComputedOperand(BoundIndexRef) (ExpressionBinder.FieldOperand) and the index data item is admitted by OperandContextRules' ArithmeticIndexWindow row (§13.18.60.3 SR10 lists 'a relation condition'); both screens answer WHERE an index may appear, not WHAT it may be compared with. With an alphanumeric partner the relation takes the string arm and OperandText's LoudValue('string', 'computed expression in a string context') throws at run time — the exact crash shape R16 (landed) removed from DISPLAY/MOVE/STRING. Fix shape: an index-class arm in the ONE relation checkpoint keyed on §8.8.4.2.13's three rows (so EVALUATE subject/object pairs, SEARCH WHEN and PERFORM UNTIL inherit it), a new diagnostic, and a drift test enumerating the operand-class pairs.

**Code site.** src/Cobol.Net.Compiler/Binding/Validation/StatementValidation.cs#CheckRelationalOperands; src/Cobol.Net.Compiler/CodeGen/Emit/OperandText.cs (LoudValue 'computed expression in a string context' ~536); src/Cobol.Net.Compiler/Binding/Procedure/ExpressionBinder.cs#OperandContextRules
