# PB3842 — The GnuCOBOL differential net is required by a dispatch spec and nothing checks that it ran

**Sites:** `scripts/gnucobol_differential.py` (whole: the change adds a new member and its call sites in this file), `.claude/skills/workstream/make_dispatch_specs.py` (whole: the change adds a new member and its call sites in this file), `scripts/orchestrator/review_findings.py` (whole: the change adds a new member and its call sites in this file)

The dispatch spec of PB3829 required running the GnuCOBOL differential on the new cases as a regression net. The implementer report, the PB3829 note and the DEVLOG entry record no run, and the five new or renamed goldens (`pb3829_rounded_bounded_function_modes`, `pb3829_random_fraction_rounded_store`, `pb3829_remainder_float_sender`, `pb3829_float_edited_small_magnitude`, `pb65_bounded_returned_value_landing`) stay portable: unverified. The review caught it only because a reviewer read the spec against the report.

The mechanism: an instruction in a rendered dispatch spec that has an observable result (a differential run) is checked by reading, not by a script, so an implementer can skip it and a CLEAN review can pass without noticing. Sweep: every other must-run line the spec renderer emits (grep `make_dispatch_specs.py` for differential and its siblings) and whether the report template or `review_findings.py` demands the evidence line.

## Acceptance

- A report that omits the evidence line for a required net (or states why it cannot run) is refused by the report check; the check reads the same list the spec renderer emits.
- PB3829's five goldens have a recorded differential run, or a recorded reason a case is not portable.
- Fix the root cause, never simply making the diagnostic pass; be consistent with ourselves barring an explicit requirement differently.
