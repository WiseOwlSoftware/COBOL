# PB608 — OPEN — one code, two rules

Surfaced 2026-09-05 by the train-3 lander's cross-cluster code-collision check (which found the train's own
codes clean and this one pre-existing at `408e360f`); re-derived on this tree for this note.

## The measurement

```
grep -n '"COBOLNET1535"' src/Cobol.Net.Editions/Diagnostics/DiagnosticCatalog.cs
471:        "COBOLNET1535", "strong-compare-ordering", EditionSeverity.Error,
476:        "COBOLNET1535", "typedef-renames-staged", EditionSeverity.Error,
```

Two descriptors with different slugs and different rules share the code. The lander also named COBOLNET1573;
checked here: that code has ONE descriptor (`external-file-status-consistency`, `:1095`) and the second hit is a
comment at `:1690` recording that COBOLNET1576 was renumbered FROM a bare literal that had collided with 1573 —
already resolved, not a duplicate.

## Why it matters

`docs/DIAGNOSTICS.md` is generated from the catalog and lists both rows under one code; a negative golden's
`.err` that pins `COBOLNET1535` proves either rule fired; the process review's central id allocation exists
exactly because two allocations of one number cost a renumbering pass each time. Nothing asserts catalog-wide
code uniqueness today — `DiagnosticRegistryDriftTests` checks other invariants — so the next collision is as
silent as this one was.

## Fix shape

Renumber one of the two onto a fresh code from the central pool (the orchestrator allocates; `typedef-renames-
staged` is the newer descriptor and the likelier candidate), sweep every reference (`grep -rn "1535"` over
`src/`, `tests/`, `docs/`, `kb/`, every `.err` file), regenerate `docs/DIAGNOSTICS.md`, and add the uniqueness
assertion to `DiagnosticRegistryDriftTests` — fired once against the current catalog before the renumbering so
the failure branch is observed.
