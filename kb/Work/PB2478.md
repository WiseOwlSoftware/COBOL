# PB2478 — the quota estimator assumes one account

Owner, 2026-10-07 13:17 PDT: a second Claude Code session, logged into a second Max 20x account (`CLAUDE_CONFIG_DIR=C:\Users\brent\.claude-acct2`), runs every Opus/Sonnet dispatch, the orchestrator loop and the landings (the OPERATOR); the first account's session keeps Mythos work. The owner seeded the second config dir by hand. Owner 13:36 PDT: account 2's week resets Saturday 2026-10-10 10:00 PDT and must be spent to 100 % before then, so every hour the tooling stops dispatch wrongly is quota lost.

**Model:** Opus (tooling with self-tests). All six notes are one mechanism (the account is a parameter of the coordination tooling, never an assumption) and are dispatched as one group.

## Defect

- `scripts/orchestrator/model_rules.json` `weekly_reset` is one value (`weekday 6, 03:00 America/Los_Angeles`), and
  `budget.py week_start()` derives the week from it. Account 2's `/usage` (2026-10-07 13:34) says the week resets
  **Sat Oct 10 09:59** and the session at 15:09. Between Saturday 10:00 and Sunday 03:00 the estimator still counts
  the old week's spend, so the loop holds while the real meter is at 0 % (lost quota); after a Sunday reset it
  believes a fresh week that account 2 does not have.
- `E:\COBOL-coord\readings.json` entries carry no `account`; both sessions record into the same list, so a reading
  of account 1 (86 % at 13:08) and of account 2 (0 % at 13:26) sit side by side and the newest wins, whichever
  account it belongs to.
- The telemetry spend since the anchor (`telemetry_events`, the OTel sink at `~/.claude/telemetry`) is not filtered by
  account, so the idle-or-busy Mythos session's tokens inflate the operator's estimate (the safe direction, but it
  stops dispatch early).

## Shape (rule 5: the next account is automatic)

An `accounts` table in `model_rules.json` (per account: name, config dir, weekly reset weekday/hour/minute/tz, caps if
they differ), the account resolved from `CLAUDE_CONFIG_DIR` (unset = the default account); `budget.py --record` stamps
the account and the estimate reads only that account's readings; the telemetry spend is filtered by the OTel attribute
that identifies the account (check what the sink records: `user.account_uuid`, `user.email`, or the session id mapped
to the config dir's `projects` transcripts). Self-test cases: a Saturday-10:00 reset; two accounts' readings
interleaved; another account's telemetry ignored. Update `DESIGN-orchestrator-loop.md` (rule 6).


## Landed (branch acct2-tooling, wave 1033 group T)

- `scripts/orchestrator/account.py` (new) is the one resolver of the Claude account: config dir (`CLAUDE_CONFIG_DIR` or
  `~/.claude`), the global config that names the signed-in account (`<dir>/.claude.json` when the variable is set,
  `~/.claude.json` when not), the account id and email, and the row of `model_rules.json` `accounts.list` (account1:
  default dir, Sunday 03:00; account2: `~/.claude-acct2`, Saturday 10:00, America/Los_Angeles). An unknown config dir
  is an error. `--self-test` (15 checks).
- `budget.py`: the week starts at the account's reset; `--record` stamps `account`; the anchor is that account's newest
  reading (an unstamped reading anchors nothing and is counted in `unstamped_readings`); telemetry is filtered on
  `user.account_uuid` (the attribute the sink records on every `api_request`, measured 2026-10-07: account 1
  `5ea56c9c…`, account 2 `c1d721cb…`); `--account NAME`. `test_budget.py` 42/42 (the Saturday-10:00 reset, interleaved
  readings, another account's telemetry ignored, a per-account cap); the new test crashes on the pre-change budget.py.
- Siblings (the same "newest reading of any account" arm): `next_unit.py`'s meter age and `ledger_plan.measure_pacing`
  read only the running account's readings; `units/meter.md` refuses to record a usage page signed into another
  account; `usage_report.py --account-uuid` and a per-account event count.

### Operator data point and the calibration refit (2026-10-07, same branch)

Operator, 14:54 PDT: account 2's real `/usage` read session 24 % (resets 15:10), week 6 % (resets Sat 10:00), while the
running (pre-change) `budget.py` estimated session 122.6 % and week 24.5 % and HELD the loop. Measured on this branch:
the account filter is NOT what explains it. Account 2's OWN telemetry (`user.account_uuid` c1d721cb…; the operator's
`organization.id`/`user.email` mapping names the same events) between its 0 % reading (13:26-13:34) and the 14:54
reading counted 9,481,140 Opus, 108,118 Sonnet and 646,023 Haiku tokens of the counted kinds, which the 2026-10-04
constants (Opus 400,000 per point, fitted to Workflow-reported tokens, never to telemetry) turned into 25.4 points and
a 127 % session: a four-fold overcount on one account's own spend (account 1's estimate over-ran its meter too).
Haiku had no rate and was priced at the Opus fallback.

Refit (`model_rules.json` `calibration`, date and source restated): every rate x4 (Opus 1.6 M, Sonnet 4 M, Fable and
Mythos 640 k), Haiku at its own price-ratio rate (12 M), `session_pct_per_weekly_pct` measured 4.0 (24 / 6); the
planner's `cost` tokens x4 so a planned wave costs the same points (`test_plan_wave.py`'s golden unchanged).
`test_budget.py` section 8 replays the two readings and the spend: the live constants estimate week 6.0 % / session
24.1 % and GO; the old constants HOLD. The estimator's arithmetic tests use a fixed fixture calibration, so a later
refit never rewrites them. One interval on one account is a thin fit (whole-percent meter): refit when two readings
of one account bracket more spend (design D6/D7).
