# PB1551

Found 2026-09-24 by the golden-lane-2 misc-p19 refuter (pin f0d582ccd). `SET NULL TO O` is rejected, but with the
code for a different rule, so no negative can witness SR-8.4.3.7.3-1 (the draft `negative/l1c19-null-as-receiving-operand`
is HELD until this lands).

Code site: `src/Cobol.Net.Compiler/Binding/.../SetFormatSelection.cs:230-233` — the predefined-object-reference arm
(EXCEPTION-OBJECT → COBOLNET2196) is not reached for NULL, SELF, SUPER. Fix: one receiving-operand check for every
predefined reference, each citing its own rule (`cite.py --check`), then re-witness SR-8.4.3.7.3-1 and the SELF sibling.

Second witness blocked by the same mechanism (golden-lane-2 misc-p20): SR-8.4.3.9.3-2's NULL leg — the draft
`negative/l1c20-property-of-null` pins COBOLNET0901 and is HELD; the row lands with only its universal-reference
negative (COBOLNET0843) until this note lands, then re-witness the NULL leg.

Third witness blocked (golden-lane-2 misc-p23): SR-8.4.3.13.3-4 — `MOVE PP TO ADDRESS OF PROGRAM "X"` draws
COBOLNET0901 and the SET form draws the generic COBOL0201, neither naming the rule that forbids ADDRESS OF PROGRAM as a
receiving operand. The fix is ONE receiving-operand check for every non-receivable identifier form (predefined object
references AND program/function addresses), each citing its own rule.

## Task brief (research 2026-09-30)

**Re-measured on `4a1dda60e`: reproduces** (`SET NULL TO O` → COBOLNET0901 "'NULL' is a reserved word"). Shared design:
kb/Work PB1782 step 1 — this is the FIRST task of that mechanism.

- **Spec (cite-checked):** §8.4.3.7.3 SR1 "NULL shall not be specified as a receiving operand" (OK 1)); §8.4.3.8.3 SR2
  "This identifier format shall not be specified as a receiving operand" (OK 2)); §8.4.3.6.3 SR1 "EXCEPTION-OBJECT shall
  not be specified as a receiving operand" (OK 1)); §8.4.3.13.3 SR4 "This identifier format shall not be specified as a
  receiving operand" (OK 4), ADDRESS OF PROGRAM); §8.4.3.4.3 SR1 "Inline method invocation shall not be specified as a
  receiving operand" (OK 1)); §8.4.3.5.3 SR2 "An object-view shall not be specified as a receiving operand" (OK 2)).
- **Change:** `ExpressionBinder.ResolveReceiving` gets ONE table keyed by the identifier FORM (predefined object
  reference NULL / SELF / SUPER / EXCEPTION-OBJECT, predefined address NULL, program-address, function-address,
  inline invocation, object-view, function-identifier, constant-name, LINAGE-COUNTER), each row with its own
  `DiagnosticCatalog` descriptor and cite-checked rule; the SET target loops (`OoBinder.OoBindSetObjectRef`,
  `SetFormatSelection.cs` ~222-234) resolve their targets through it (that deletes PB1008's duplicate). Until PB1425 2a
  lands, NULL/SELF/SUPER reach the screen only where the grammar already parses them as a receiver — make the
  reserved-word check defer to the table for those three words in a receiving position (the `IsExceptionObjectRegister`
  pattern) rather than report §8.9. Drift test: every form of the table's key enum has a row.
- **Goldens (2002):** negatives, one per row: `SET NULL TO O`, `SET SELF TO NULL` (in a method), `SET SUPER TO NULL`,
  `MOVE X TO SELF`, `INITIALIZE SELF`, `ACCEPT SELF`, `MOVE PP TO ADDRESS OF PROGRAM "X"` (SR-8.4.3.13.3-4), `SET
  EXCEPTION-OBJECT TO O` — and the HELD drafts `negative/l1c19-null-as-receiving-operand` and
  `negative/l1c20-property-of-null` re-pinned to the new codes.
- **Size:** half slot. Must land BEFORE PB1425 2a.

## Rows received 2026-10-05 from kb/Work PB1425 (w1021a)

PB1425 landed the identifier tier (every identifier format in every SENDING and object position, Format 7's
identifier-3 included). Its two RECEIVING rows are this note's mechanism and move here: **SR-8.4.3.8.3-2** ("This
identifier format shall not be specified as a receiving operand" — SELF / SUPER) and **SR-8.4.3.5.3-2** ("An object-view
shall not be specified as a receiving operand"). Today SET Format 5's receivers and INVOKE RETURNING refuse a view by
SR2 (COBOLNET2871, `objectViewReceiver`), and so does the ONE receiving chokepoint for the view of a qualified item
written as a chain (`MOVE X TO A OF G AS C`, `ExpressionBinder.ReceivingFormBar`); every other receiving position
(`MOVE X TO SELF`, `MOVE X TO U AS C`, `INITIALIZE SELF`, `SET SUPER TO NULL`, `ACCEPT SELF`) takes a plain
`dataReference` and refuses them as a parse error (COBOL0001 / COBOLNET0901), never by the rule. The fix is the superset
parse of those receiving positions plus the one receiving-operand check this note describes.
