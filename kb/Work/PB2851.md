# PB2851 — worktree removal ignores uncommitted paths

Found 2026-10-08 ~21:50 PDT by the operator, verifying for the owner that main held all finished work.

## Measured

- 21:28 `python scripts/prune_worktrees.py --brief` printed for `worktree-wf_8750e914-ee4-4` (wave 1047 E, PB1928 lead):
  "DONE, but PB1928 is already landed: superseded … 6 commit(s) ahead; … **1 uncommitted path(s) in its worktree**".
- The train-1047 lander's report (`scratch/reports/train1047-report.md`, "Worktrees to remove (all landed)") listed
  ee4-4, and by ~21:31 the land unit (session 56ff458d) had removed the worktree and deleted the branch. The uncommitted
  path went with it; nothing records what it was.
- Its committed work is on main (every added line verified against 495e8fb6f). The path was most likely the per-machine
  `.claude/settings.local.json` (tracked, with a local `skillOverrides` edit), the only uncommitted path in EVERY other
  worktree that night (agent-a23dab…, agent-a2fd4c…, agent-a720d…, ee4-1) — but that is inference, not evidence.
- Owner rule (memory never-lose-work, 2026-10-07): a worktree is removed only after ALL its work is committed and landed.

## Fix

1. One removal path (prune_worktrees.py `--apply`, which units and the operator both use): refuse a worktree whose
   `git status --porcelain` shows any path other than `.claude/settings.local.json`, printing the paths; the unit then
   commits, moves or explicitly discards each (named in the branch's kb/Work record) before removal.
2. Record what was removed (branch, head, porcelain) in the unit's milestone, so a removal is auditable.
3. Self-test: a planted untracked file blocks removal; a settings.local.json-only worktree is removed.
