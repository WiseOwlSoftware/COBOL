# PB3835 — the exit-12 wait does not read a STARTING gate

**Sites:** `scripts/orchestrator/land_lane.py#gate_lock_free`, `scripts/orchestrator/land_lane.py#wait_free`

## The defect

`enqueue.py land` answers exit 12 (GATE BUSY) from THREE sources once PB3707 lands: the worktree's gate lock, a Linux
gate of the tree (PB3649), and a gate run that is STARTING (`run_gate_legs.gate_phase`: spawned, its child alive, the
lock not yet taken; PB3707). The lane's wait, `gate_lock_free`, reads only the first two. For a STARTING gate it
returns free at once, the lane relaunches the landing, and the landing answers exit 12 again: churn until the gate
takes its lock or `START_WINDOW_S` (60 s) passes. It is bounded and harmless today, and it is a second reader of
"is a gate coming?" that disagrees with the landing's: one question with two answers (rule 5, one rule in one place).

## Fix

The wait and the landing read ONE predicate: the landing's own "is a gate running or coming in this worktree" reader
(the one exit 12 is answered by), called from `gate_lock_free`, so a new exit-12 source cannot be missed by the wait
again. A drift arm in land_lane's self-test asserts the wait reads every source exit 12 is answered by.

## Acceptance

- A STARTING run (spawn record naming a live child, no lock) keeps the wait waiting; a dead child or a run past the
  window ends it.
- `gate_lock_free` contains no reader of its own that the landing's exit-12 decision lacks, and vice versa.
