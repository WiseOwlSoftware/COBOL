# PB773 — OPEN — the last two members of the format↔organization family

Filed 2026-09-06 by the registrar, from [[PB692]]'s landed residue paragraph and [[PB742]]'s sweep. Both name
these rules; neither CLAIMS them, and a residue sentence inside a landed note is not an open item — the same
reasoning [[PB752]] was filed under.

## ⚠ Provenance — this note was DERIVED BY READING, not probed

There is no built compiler in this worktree (`src/Cobol.Net.Cli/bin/Debug/net10.0/cobol.exe` does not exist) and
building was out of scope for this pass. Every claim below is decidable from the four files quoted, in the manner
of [[PB751]] and [[PB752]]. **The implementer's first act should be the probe this note does not carry**: an SD
file whose SELECT writes `ACCESS MODE IS RANDOM` or `ORGANIZATION IS INDEXED … RECORD KEY IS K`, at each
edition.

## The rules, mechanically checked

`python scripts/spec/cite.py --check`:

- `12.4.5.2 "Format 3 shall be specified only for a sequential file or a report file"` → **OK §12.4.5.2 11)**:
  *"Format 3 shall be specified only for a sequential file or a report file. The associated file description
  entry shall not be a sort-merge file description entry."*
- `12.4.5.2 "Format 4 shall be specified only for a sort-merge file"` → **OK §12.4.5.2 13)**, and
  `12.4.5.2 "The associated file description entry shall be a sort-merge file description entry"` → **OK
  §12.4.5.2 13)** — the SAME rule, both sentences: *"Format 4 shall be specified only for a sort-merge file. The
  associated file description entry shall be a sort-merge file description entry."*

**Both rules have TWO obligations**, exactly as [[PB742]] warns for SR8/SR9: an ORGANIZATION half and an
FD-vs-SD half. Do not close either on its first sentence.

## Why the FD/SD half is the operative one — the format geometry, read out of §12.4.5.1

Format 4 (sort-merge), printed in full, is:

```
SELECT [ OPTIONAL ] file-name-1
ASSIGN { TO { device-name-1 | literal-1 } … [ USING data-name-1 ] | USING data-name-1 }
[ [ ORGANIZATION IS ] SEQUENTIAL ] .
```

That is the WHOLE format. Format 3 (sequential) is a strict superset of it — it adds ACCESS MODE, FILE STATUS,
LOCK MODE, `ORGANIZATION [LINE|RECORD] SEQUENTIAL`, RECORD DELIMITER, RESERVE and SHARING, every one optional.
So the file control entry ALONE can never distinguish Format 3 from Format 4: a bare `SELECT F ASSIGN TO "x".`
is a legal spelling of both. **The discriminator is the file description entry** — SD means Format 4, FD means
Format 3 — which is why the second sentence of each rule is the one that decides anything, and why the check
cannot live in the clause loop that reads the SELECT.

The enforceable content, restated once: *a file described by an SD may carry ONLY the Format-4 clause set; a
file described by an FD is not a sort-merge file.* Every Format-3-only clause on an SD breaks SR11 sentence 2;
every key clause on an SD breaks SR8 or SR9 sentence 2 (those are [[PB742]]'s).

## ⛔ Premise correction — "no code site" is wrong; "no ENFORCEMENT site" is right

Both rules ARE written into the compiler. Neither is checked.

**SR13 is named, and its non-enforcement is deliberate and recorded.**
`src/Cobol.Net.Compiler/Binding/FileControlKeyRules.cs:201-205`:

```
// A sort-merge file is described by an SD; §12.4.5.1 Format 4 carries no key clause at all. An SD whose
// SELECT nonetheless writes ORGANIZATION INDEXED breaks §12.4.5.2 SR8/SR13, NOT a key clause's own rule,
// so this screen has nothing true to say about it and stays silent rather than saying the wrong thing.
if (file.IsSortMerge) return;
```

That comment is correct about its own scope and is the best possible evidence for this note: the ONE screen that
sees every file control entry after the data forest is indexed identifies the violation by rule number and then
declines it, because no other site owns it. `feedback_a_dead_lookup_is_also_unverified` in its purest form — the
rule has been looked at, named, and never enforced.

**SR11 is quoted verbatim, as a DERIVATION.** `src/Cobol.Net.Compiler/Binding/DataBinder.cs:913-915`, inside
[[PB692]]'s §12.4.5.5.2 SR2 screen:

```
// put both sequential phrases in the ORGANIZATION clause, that clause is written only in the
// Format-3 file control entry, and §12.4.5.2 SR11 says "Format 3 shall be specified only for a
// sequential file or a report file".
```

SR11 is used there to prove that LINE SEQUENTIAL is *"a sequential file"* for a DIFFERENT rule's purposes. It is
never tested.

## Where the screen has to live, and why it is not where the clauses are read

`FileModel.IsSortMerge` is set in exactly one place — `DataBinder.cs:1204`, as the SD entry binds — and
`BindFileControl` (`DataBinder.cs:411`, `:810-…`) has already read and captured every SELECT clause by then. So a
screen keyed on "this entry wrote a Format-3-only clause AND its description entry is an SD" cannot run in the
clause loop; it has to run after both halves are known. That is `ResolveFiles` (`DataBinder.cs:1426`), which is
already where `FileControlKeyRules.Screen(file, Edition)` is called (`:1449`) with `IsSortMerge` populated.

## ⛔ Fix shape — NOT "one table row each", and this is the rule-5 point

The dispatch that produced this note said *"one table row each"*. **Measured against the table, that is wrong**,
and shrinking the design to fit it would build the wrong structure.

`FileControlKeyRules`' row type (`FileControlKeyRules.cs:52-62`) is
`(RuleId, Clause, Citation, RuleText, Organization, Role, Applies, Violated, Message)` and its `Violated`
predicate takes a `FileKeyOperand` — *one key operand* of the entry (`:34`). Every existing row is a statement
about a RECORD KEY / ALTERNATE RECORD KEY / RELATIVE KEY data-name. **SR11 and SR13 are statements about the
ENTRY'S CLAUSE SET versus the KIND OF ITS FILE DESCRIPTION ENTRY.** They have no key operand, and `Organization`
is the wrong axis: SR13 is about a file that HAS no organization in the enum's sense. Forcing them into
`FileKeyOperand` would need a fourth `FileKeyRole` meaning "not a key at all", which is the shape the file's own
header says it exists to avoid (`:26-29`).

Two honest options, and the choice is a design decision the implementer should record in
`docs/COBOLNET_FILES_DESIGN.md` beside D19 (the criterion `FileControlKeyRules.cs:84-89` already states for
which screen a new entry rule joins):

1. **Widen the table with an entry-level rule kind** whose subject is the entry rather than an operand — a
   second `Rules` array, or a discriminated row whose `Violated` takes only `FileModel`. This is the shape that
   makes the NEXT case automatic: it gives SR11, SR13, **SR12** (LINE SEQUENTIAL excludes RESERVE, still
   homeless — see the sweep) and [[PB742]]'s SR8/SR9 one home, and `FileControlKeyRuleDriftTests` already
   re-derives every row's `RuleText` from `specs/ISO_COBOL.md`, so the guard against an inherited clause number
   comes free.
2. A sibling screen beside it — cheaper, and it re-creates the two-mechanisms-for-one-job shape
   (`feedback_one_mechanism_per_job`) the table was built to end.

⛔ **Read [[PB742]]'s landed shape FIRST.** SR8 and SR9 are the same kind of rule as SR11/SR13 (a format ↔
organization/SD consistency rule with no key operand), so whatever structure train 19 gives them is the
structure these two join — and if train 19 solved SR8/SR9 with an inline check rather than a structure, THAT is
the moment to build the structure rather than add a third inline site (CLAUDE.md rule 5).
