# PB3934 — byte-length-separator-comma-refused: `FUNCTION BYTE-LENGTH (x, PHYSICAL)` / `FUNCTION LENGTH (x, PHYSICAL)` refused: "unexpected comma delimiter, expecting PHYSICAL or )"

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S10) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\byte-length-separator-comma-refused.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\byte-length-separator-comma-refused\`.

## Summary

**Note (refuter): the edition, 2014, is derived rather than quoted** (PHYSICAL is absent from the 2009 draft's BYTE-LENGTH format and from the 2023 Foreword's list of new features); see the Expected result section.

GnuCOBOL 3.2 refuses `FUNCTION BYTE-LENGTH (X, PHYSICAL)`: `syntax error, unexpected comma delimiter, expecting
PHYSICAL or )`. Without the comma, `FUNCTION BYTE-LENGTH (X PHYSICAL)` compiles. §5.2.8 lets the separator comma
appear anywhere a separator space is used in a general format, and the BYTE-LENGTH general format has a separator
space between argument-1 and PHYSICAL. The comma form is legal, so this is a defect. `FUNCTION LENGTH (X, PHYSICAL)`
fails the same way. GnuCOBOL's own TRIM rule accepts the comma before LEADING and TRAILING, so only the LENGTH and
BYTE-LENGTH rule lacks the optional separator. The semicolon form `(X; PHYSICAL)` compiles.


```
    7 >     DISPLAY FUNCTION BYTE-LENGTH (X, PHYSICAL)
```

Without the comma (`bly.cob`): compile exit 0 with `warning: PHYSICAL argument for LENGTH functions is not
implemented [-Wpending]`; run exit 0, output `3`. With a semicolon (`semi.cob`): compile exit 0, with the same
warning. In `sib.cob`, `FUNCTION LENGTH (X, PHYSICAL)` gets the same `unexpected comma delimiter` error, and
`FUNCTION TRIM (X, LEADING)` raises none.

## Expected result (per ISO)

The program compiles and prints `3`.

- §5.2.8 (checked): "The separators comma and semicolon may be used anywhere the separator space is used in general
  formats and other syntactic specifications. In the compilation group, these separators are interchangeable."
- §15.14.2 (checked), general format: `FUNCTION BYTE-LENGTH ( argument-1 [ PHYSICAL ] )`. A separator space
  separates argument-1 and PHYSICAL, so a separator comma may take its place.
- §15.14.4 1) (checked): "The returned value is an integer that is the length of argument-1 in number of bytes."
  §15.14.4 7) (checked) defines PHYSICAL for a variable-length group. X is not one, so with or without PHYSICAL the
  value is 3.

Edition: §5.2.8 has the same wording in the 2002 text and in the 2009 committee draft that became the 2014 edition
(both: "The separators comma and semicolon may be used anywhere the separator space is used in general formats").
The PHYSICAL phrase is not in the 2009 draft's BYTE-LENGTH format. Annex E and the Foreword's change list of the 2023
edition do not name it, and GnuCOBOL's own reserved-word table dates PHYSICAL to 2014 ("2014, note: only listed as
argument for LENGTH FUNCTIONS"). So the edition is 2014, derived rather than quoted. GnuCOBOL accepts the PHYSICAL
phrase under `-std=cobol2014`. If PHYSICAL is placed at 2023 instead, the defect stands there unchanged, and under
`-std=cobol2014` it is the same parse failure on a phrase the dialect accepts.

**Edition 2014 is DERIVED, not quoted (refuter's correction).** PHYSICAL is absent from the 2009 draft's BYTE-LENGTH format and is not in the 2023 Foreword's list of new features; the repository holds no 2014 text. 2014 follows from those two facts and from cobc's own reserved-word table dating PHYSICAL to 2014.

Edition as recorded by the adjudicator: 2014 (PHYSICAL derived at 2014; 5.2.8 unchanged since 2002). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Class

GNUCOBOL-DEFECT: legal source refused. A separator comma, which §5.2.8 makes interchangeable with the separator
space, is not accepted between argument-1 and PHYSICAL.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/parser.y`, rule `function` (line 19835). The alternative `LENGTH_FUNC TOK_OPEN_PAREN length_arg PHYSICAL
  TOK_CLOSE_PAREN func_refmod` (line 19857) has no optional separator between `length_arg` and `PHYSICAL`.
  `trim_args` (line 19947) writes `expr_x _e_sep LEADING` / `expr_x _e_sep TRAILING`, and `_e_sep` (line 18590)
  is empty, `COMMA_DELIM` or `SEMI_COLON`.
- `cobc/scanner.l` (lines 602 to 606 for DECIMAL-POINT IS PERIOD, 627 to 640 for DECIMAL-POINT IS COMMA) returns
  `COMMA_DELIM` for a comma when `inside_bracket` is set, so inside the parentheses the comma reaches the parser as
  a token.
- Fix: `length_arg _e_sep PHYSICAL`.
