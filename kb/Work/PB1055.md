## Landed — w1004c (fix-lane group C, wave 1004)

**Re-probed first:** the note's `nest.cob` warned COBOLNET1756 and aborted at run time, as filed.

**Derived (every § through `cite.py --check`).** §14.9.40.3 SR13 — "Subscripting shall be specified in accordance with
8.4.2.3" — and §8.4.2.3.3: SR5 e) lets "the subject of a SORT statement that references a table" omit its subscripting
and says that with a rightmost ALL "the number of subscripts is equal to one less than the number of OCCURS clauses";
SR6 makes that ALL "equivalent to omitting the rightmost or only subscript in this context"; SR3 still demands one
subscript per OCCURS clause otherwise. What the subject omits is the TABLE'S OWN level (the one the statement sorts), so
it writes one subscript for each ENCLOSING table, outermost first.

**One reading, one screen.** `ReferenceResolver.ReadTableSubjectSubscripts` is `ReadSubscripts(tableSubject: true)`: the
same empty-parentheses screen, subscript renderer and SR4 index-name association every reference gets, with
`InterpretSubscripts` dropping a rightmost `ALL` and `ScreenTableSubjectArity` (COBOLNET2097, the SR3 mechanism)
comparing the count with `SubscriptArity - 1`. The old binder never read the written list at all, so `SORT E(2)` (legal)
and `SORT E` (illegal: too few) drew the same deferral. Now: `SORT E(2)` / `E(2, ALL)` / `E(I + 1)` sort ROW(2) / ROW(I+1)'s
E; `SORT E`, `E(1, 2)`, `E(1, 2, 3)` and `SORT ROW(1)` (a subscript on a one-level table: an element, not a table) are
refused by name. `SORT TE(1)` was an edge the note called unsettled; SR5 e)'s second sentence (subscripts = OCCURS count
less one) settles it as an error, and it is now refused rather than silently sorting the whole table.

**The table's whole-table path** is `ReferenceResolver.BuildTablePath(table, outer)` — the structural path the
`table(ALL)` argument and a dynamic table's capacity register already use — carried in `TableSortStorage.TypedArray`
(an enclosing dynamic-capacity level is reached through its receiving accessor, since the sort writes). The occurrence
count is `CurrentOccurrenceCount(table, outer)`, so a nested dynamic table sorts ITS OWN occurrence's capacity. The
C# text `ArrayPath` and the binder's private `SortArrayPath` (which silently emitted a wrong path for an outer
dynamic-capacity level) are deleted.

Witnesses: `conformance:2002/pb1055_table_sort_nested_subject` (single, ALL, data-name subscript, group elements with a
KEY, three levels), `conformance:2014/pb1055_table_sort_nested_dynamic`, `conformance:negative/pb1055-table-sort-subject-subscripts`
(COBOLNET2097 at 2002/2014/2023). Row closed: SR-14.9.40.3-13 (batch `w1004c/batch-A.json`).
