# PB2021 — LANDED (CONFORMS, w1033): is `SET ADDRESS OF x DOWN BY 32` legal in any edition?

The flip `run_misc:14097` has two source files. Its caller.cob was adjudicated as a correct rejection (§13.7.3 4): a LINKAGE
item referenced without USING). Its callee.cob also fails, with COBOL0001 "unexpected 'DOWN'", on a statement of the shape
`SET ADDRESS OF x DOWN BY 32`. The adjudicator did not decide it: in ISO 2023 §14.9.39, UP BY and DOWN BY appear only in Format 2
(index-names) and Format 14 (a dynamic-capacity table), so the form is most likely a GnuCOBOL or vendor extension (pointer
arithmetic), but the older editions were not checked (the repository holds only the 2023 text), and the 2002 and 2014 SET
statements had pointer formats whose UP BY / DOWN BY wording must be read in `docs/VERSION_CHANGE_REFERENCE.md` and the
historical-revisions sources before the answer is written.

Deliverable: the verdict per edition (CONFORMS / DIVERGES / DOCUMENTED-NON-SUPPORT) with `cite.py`-checked clauses, a
`docs/CONFORMANCE.md` entry if it is a documented non-support, and, if any edition makes it legal, the grammar fragment under
the version predicate (CLAUDE.md rule 3: no legal source rejected). The parse error's wording should name the actual rule either
way.

## Adjudication 2026-10-07 (w1033)

**Outcome: CONFORMS, NO DEFECT. Closed as landed; no code change.** `SET ADDRESS OF x UP|DOWN BY n` is not legal in any edition and the pinned build rejects it at 85, 2002, 2014 and 2023, also with `--permissive` and in the exact GnuCOBOL `run_misc.at:14097` callee shape (`COBOL0001: unexpected 'DOWN'` / `'UP'`, exit 65). The baseline classification `run_misc:14097 DEFAULT_DIALECT WE_REJECT_THEY_ACCEPT` is correct: GnuCOBOL's acceptance is a non-ISO extension. No latitude, no owner decision.

**Spec (cite.py --check OK; the refuter re-ran all 13 and added more).**
- No SET format admits it: `§14.9.39.2` Format 2 (index-arithmetic) receives `index-name-3`; Format 14 (dynamic-capacity-table) receives `data-name-2` (`§14.9.39.3 SR29`, a CAPACITY-phrase item); Format 10 (data-pointer-arithmetic) receives `identifier-9` (`SR23`: category data-pointer) and has no ADDRESS OF arm, unlike Format 7 (`ADDRESS OF data-name-1`, SR18, GR13). The refuter rendered PDF pages 759-761: the transcription is faithful.
- `ADDRESS OF x` cannot be identifier-9: the only identifier form `ADDRESS OF identifier-1` is the `§8.4.3.11` data-address-identifier (GR1: class pointer, category data-pointer) but `§8.4.3.11.3 SR5` "This identifier format shall not be specified as a receiving operand", and identifier-9 is a receiving operand (`§14.9.39.4 GR20`, `§14.6.7`); informative `§D.9.2.1`: the receiving ADDRESS OF in a SET "is not a data-address-identifier, but a syntactical notation for setting the address of a based item to the value specified by the sending operand", which exists only in Format 7. Either way the form fails (a closed dilemma).
- `§4.2.2` requires only that a general-format violation can be indicated; accepting it would be a `§4.2.10 1)` nonstandard extension (GnuCOBOL's position), which rule 1 does not adopt.
- Per edition: 2014: `§E.2`/`§E.3.3` have no entry for SET data-pointer arithmetic (only `E.3.3 17)`, the dynamic-length SIZE format); 1985: no data-pointers, ADDRESS OF or BASED (the build gates them with COBOLNET0900; `pos-ptr.cob` at 85); 2002: the 2002 text is NOT in the repository, so this is a MISSING observation, not a negative (informative corroboration: Micro Focus marks its Format 5 data-pointer-arithmetic with ISO2002 and its receiver is only `{pointer-name-3 ...}`; GnuCOBOL's `cobol85` dialect rejects the form). Re-check if the 2002 text is ever added to `specs-private`.
- Refuter's extra reading: the printed `§13.18.5.4 GR2` cross-reference ("SET statement, General rules 17, 18, and 19", PDF p. 406) with `§8.6.5` ties the based item's implicit pointer to Format 10 literally; it does not overturn (general rules define meaning, `§5.3.3`; syntax is the formats and SRs, `§5.2.1`, `§5.3.2`; GR17 is a program-pointer rule). It is a stale cross-reference, a defect in the standard, not the compiler.

**Code.** `src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4#setIndexStatement` (line ~1839): `SET dataReference+ ( UP | DOWN ) BY arithmeticExpression`, one shape for Formats 2 and 10 re-routed by receiver category in the binder (`PtrTryBindSetUpDown`); `ADDRESS` is a reserved token that cannot start a `dataReference`, so the parse fails at UP/DOWN. `setAddressStatement`/`setAddressReceiver` (`(ADDRESS OF?)? dataReference`) is the only rule with a receiving `ADDRESS OF`, and only before `TO`. Probes: `pos-ptr.cob` (`SET P TO ADDRESS OF W. SET P UP BY 4. SET ADDRESS OF LREC TO P.`) prints `EFGH` then `ABCD` at 2002+; `--flag-extensions` changes nothing.

**Residue (no defect; MINOR diagnostics and comments, for whoever next edits these files).**
1. Diagnostic wording: `unexpected 'DOWN'` meets `§4.2.2` but names a token, not the rule. The refuter's home for the named diagnostic is the EXISTING COBOLNET2112 ("no SET general format admits this receiving operand list (ISO §14.9.39.2)", from `SetFormatSelection.ReportNoFormat`, already given to `SET N UP BY 1` with PIC 9(4) in `num-up.cob`) with `§8.4.3.11.3 SR5` added, not a new code: let `setIndexStatement`'s receiver also parse `ADDRESS OF? dataReference` and refuse it in the binder by name (cf. `docs/CONFORMANCE.md` row 40 on generic SOURCE-phrase parse errors).
2. Sibling diagnostic: `move-to-adr.cob` (`MOVE P TO ADDRESS OF LREC`) is rejected with COBOLNET0901 "'ADDRESS' is a reserved word ... cannot be used as a user-defined word (ISO §8.9)", naming the wrong rule; the governing rule is `§8.4.3.11.3 SR5`.
3. Comment fidelity (I9): the comment above `setIndexStatement` reads `// SET dataReference+ UP/DOWN BY arithmeticExpression (COBOL-85 §14.9.39 Format 2)`; §14.9.39 is the 2023 numbering and the rule also carries Format 10 (cite `§14.9.39.2` Formats 2 and 10).
