## 2026-10-17: the capacity question is answered; the baseline row remains (operator, account 2)

kb/Work PB3339 (owner 2026-10-17: "Reading the entire file into memory as a design requirement is a fatal flaw, IMO") landed
on main in pull request #201 (merge 3f3e0514a). SORT and MERGE now keep their records in bounded memory, write sorted runs
to temporary files and merge them k-way. The memory limit is configurable and the work-file directory is documented
(`docs/CONFORMANCE.md` §3 D-SWK). `SortWorkBoundTests` and `SortWorkSpillConformanceTests` witness it, and
`SortWorkBoundDriftTests` refuses an unbounded store. So this note's decision (document a capacity limit, or design a
spill path) is made: the spill path. The OutOfMemoryException it feared is gone. PB3339 was filed without naming this
note; its branch review caught the duplicate.

What remains is this note's first step as a permanent row of the performance baseline:
- A SORT and a MERGE benchmark program in `tests/WiseOwl.Cobol.Benchmarks/Programs/`, scaled by LOOP-COUNT like IDXHOT.
- One size that fits the memory limit and one several times larger (it spills).
- Measured by `scripts/arch/perf_baseline.py`: time as its other generated-program rows are, with the external
  comparison against GnuCOBOL 3.2 at 1x, 2x and 4x, whose growth ratio names the complexity class. Also PEAK
  memory, which the script does not measure today. Its in-process rows record BenchmarkDotNet's
  `BytesAllocatedPerOperation` (perf_baseline.py:16, :265), and its process rows record wall and CPU only (:403).
  Allocated bytes cannot witness PB3339's bound: a regression that keeps the in-memory run alive after spilling
  allocates the same bytes per record. So the process rows of these programs gain the child's peak resident set
  (`getrusage` `ru_maxrss` under WSL; `Process.PeakWorkingSet64` on Windows). The record must show the spilling
  size's peak near the configured limit, not proportional to the input (review R1-1, 2026-10-17).
- The record (`docs/rearchitecture/evidence/perf-baseline/`) gains the rows, and `--self-test` still proves the compare
  can fail.

This note lands when those rows are in the baseline (`status: landed`, closes_rows_reason unchanged).

## Landed (wave 1117 group B)

The performance baseline now has the rows this note asked for, recorded in
`docs/rearchitecture/evidence/perf-baseline/a13ede547992.md` (product commit a13ede547992, 2 sessions, repeat 5;
the R0 record `354c79ef3312.md` stays the architecture review's R0 reference):
- `tests/WiseOwl.Cobol.Benchmarks/Programs/SORTHOT.cob` (a SORT through an INPUT and an OUTPUT PROCEDURE of N scrambled
  80-byte records) and `MERGEHOT.cob` (a MERGE of four sequential files), each with its witness computed from its
  header formula (count N, key sum N(N-1)/2, no key out of order), in `GeneratedProgramBenchmarks`' `[Params]`.
- `scripts/arch/perf_baseline.py` times a program with an SD entry twice, derived from the source: under the 128M
  default (every scale in memory) and as `<program>-SPILL` under 4M (sorted runs, merged), the limit given to both
  implementations (`WISEOWL_COBOL_SORT_MEMORY`, `COB_SORT_MEMORY`), at 1x, 2x and 4x against GnuCOBOL 3.2.
- Every whole process (cold compile, host-OS run, both implementations under WSL) gains a `peak/` row: the child's
  own peak resident set (`wait4`'s `ru_maxrss`; `GetProcessMemoryInfo`'s peak working set), compared with the same
  noise band as a time. The self-test fires on a planted +50 % peak and proves the measure sees a child's own 256 MiB.
- The record shows the bound: above the start-up floor, ours SORTHOT-SPILL holds 32.8 / 39.3 / 42.1 MiB and
  MERGEHOT-SPILL 39.5 / 39.4 / 38.2 MiB at 100,000 / 200,000 / 400,000 records, while the in-memory cases grow
  51.9 / 78.1 / 125.0 and 57.9 / 81.2 / 133.8 MiB. SORTHOT-SPILL's small rise is uncollected garbage, not retention:
  1,600,000 records sort under `DOTNET_GCHeapHardLimit` = 20 MiB.
- The WSL leg had been broken since PB2528: the stage carries the Windows ReadyToRun runtime, which Linux .NET refuses
  (BadImageFormatException). The leg now deploys the runtime the compiler deploys on Linux beside each program.
