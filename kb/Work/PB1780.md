The standard defines TWO relations over one pair of descriptions, and the universal path needs both:
1. **MATCH** (§9.3.6, resolution): decides whether a method is BOUND at all; failure is EC-OO-METHOD after the
   INHERITS walk. Through a universal receiver every argument is BY REFERENCE (SR6), so match rule 3 applies, and
   3 e) is a clause-IDENTITY list. A group has no PICTURE (and none of the listed clauses), so two alphanumeric
   groups MATCH whatever their sizes and a group does NOT match an `X(n)` (which has a PICTURE clause).
2. **CONFORMANCE** (§14.8.2 / §14.8.3, asked of the BOUND method by §14.9.23.4 GR7 c), failure EC-OO-UNIVERSAL;
   asked at bind time on every typed lane by §14.9.23.3 SR5 c) / §14.9.4.3 SR25 / §8.4.3.2.3 SR13): the
   by-reference group rule 1 (formal bytes ≤ argument bytes), the §14.8.2.3.2 identity list, the §14.8.2.3.3
   COMPUTE / SET / MOVE regime, the §14.8.3.3 SET / identity regime for RETURNING.

## What the code does today (`file#member`)

- Bind-time relation, typed lanes: `src/Cobol.Net.Compiler/Oo/OoConformance.cs#DescriptionMismatch` (BY REFERENCE,
  §14.8.2.3.2 + §14.8.2.2 rule 1), `#ContentMismatch` (BY CONTENT identifier), and FOUR per-shape literal/expression
  arms with their own admission lists: `#ContentNumericLiteralMismatch` (admits only a fixed-point numeric or an
  alphanumeric formal, and only an unsigned integer into the latter), `#ContentArithmeticMismatch` (refuses a float
  formal), `#ContentBooleanMismatch` (refuses a national formal "on purpose"), `#ContentAlphanumericLiteralMismatch`.
- CALL and function lanes ask them through ONE entry: `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ParameterConformance.cs#CheckArgument`
  / `#ContentConformanceReason`.
- The INVOKE lane does NOT use that entry: `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/OoBinder.cs#OoBindInvocationArg`
  calls the OoConformance pieces directly and adds INVOKE-only refusals that are not rules (the "fixed-point⇄float
  CONTENT conversion is not carried across INVOKE … a documented marshalling residue" refusal; the BY VALUE refusal
  "header BY VALUE formals are a later slice"; the Tier-C group refusal for a strongly-typed group with an object leaf).
- Run-time relation, universal lane: `OoConformance.ConformanceDescriptor` renders each side to a string
  (`S:n:J`, `N:…`, `O:<SignatureKey>`, `G:…`, `V:…`, `P:…`, and the `T:!` sentinel for every other category);
  `src/Cobol.Net.Compiler/CodeGen/Verbs/OoEmitter.cs#EmitCobolInvokeCase` emits `__a[i].Descriptor != "<formal>"`
  as the §9.3.6 MATCH test (and a descriptor inequality on RETURNING as GR7 c)'s EC-OO-UNIVERSAL). String equality is
  used for MATCH, although match rule 3 e) is not equality of the string the typed comparator's CONFORMANCE projects:
  a group is keyed `S:<width>:N` exactly like `PIC X(<width>)`.
- The drift guard between the two representations is `tests/Cobol.Net.Tests.Unit/PictureClauseIdentityDriftTests.cs#ConformanceDescriptor_AgreesWithTheComparator_OverEveryCarriedPair`
  — a matrix over elementary PICTUREs only; groups, pointers, object references, strong types and the
  as-if-elementary groups are outside it (kb/Work PB1576).

## The gap, named once

The defects are not twelve independent bugs. They are (a) the INVOKE lane's private copy of CALL's argument
entry, (b) literal/expression arms that carry hand lists instead of asking the COMPUTE/SET/MOVE question the
identifier arm already asks (`MoveTable16.Validity`), and (c) a run-time representation (a string) that can only
answer "equal", asked a question (§9.3.6 MATCH) that is not equality of the CONFORMANCE projection — so each new
category or clause needs a new key and a new documented "delta".

## Proposed single structure (rule 5 — the shape that makes the next case automatic)

1. **`ActivationDescription`** — a small immutable record in `src/Cobol.Net.Runtime/Control/` (the compiler already
   references the runtime): class, category, the §9.3.6 3 e) clause facts (ALIGNED, ANY LENGTH, BLANK WHEN ZERO,
   DYNAMIC LENGTH + LIMIT, JUSTIFIED, the PICTURE-clause identity key incl. currency STRING / DECIMAL-POINT IS COMMA /
   LOCALE external identification, SIGN, USAGE), group facts (alphanumeric group width, as-if-elementary usage and
   positions, strong-type identity, the §8.5.1.12 variable-length signature), pointer restriction, object-reference
   descriptor (kind, class/interface name, FACTORY, ONLY), passing mode (BY REFERENCE / BY VALUE) and OPTIONAL.
   The compiler builds it from a `DataItem` in ONE place (replacing `ConformanceDescriptor`); the emitter serializes
   it as a `static readonly` per method case (no string keys).
2. **Two pure relations over it, in the runtime, used by both phases:** `ActivationRelations.Matches(invocation,
   formal, mode)` = §9.3.6 match rules 1–7 plus the "exact match" criteria (needed only when overloading lands —
   D9 declines it, so today a boolean suffices), and `ActivationRelations.ConformanceViolation(argument, formal,
   mode)` = §14.8.2 / §14.8.3 (by-reference identity + group rule 1 + strong type + variable-length compatibility;
   the by-content/value COMPUTE / SET / MOVE regime delegates to the SAME Table-16 / SET predicate the compiler's
   `MoveTable16` and `ObjectRefAssignmentMismatch` use — those move to (or are mirrored by) a runtime-hosted pure
   table so there is ONE copy).
3. **One bind-time entry for every activation**: `ParameterConformance.CheckArgument` gains the INVOKE site
   (`ActivationSite` carries the `invokedWith` receiver description that §14.8.2.3.2 rule 4 / §14.8.2.3.3's
   ACTIVE-CLASS alternatives need); `OoBindInvocationArg` keeps only what is INVOKE-specific (SR9/SR10 mode
   selection, SELF/NULL/address arguments) and asks the entry for conformance. The literal/expression arms become
   "describe the sender, ask the relation": a numeric literal is described per §9.3.6's literal paragraph (DISPLAY,
   one '9' per digit, sign and decimal separator kept), an arithmetic expression as a COMPUTE sender, a boolean
   expression as a boolean sender.
4. **Carrier residues are emitter work, not rules**: the fixed⇄float BY CONTENT conversion on INVOKE (PB1113) and
   the strong-group-with-object-leaf crossing (PB1116) are carried in `OoEmitter` (the CALL lane already carries
   the float conversion — `conformance:2023/pb238_call_format2_operands`), never refused by the binder.
5. **Drift test that keeps it automatic**: one unit test enumerates the `ActivationDescription` fields by reflection
   and asserts each is read by `Matches` or `ConformanceViolation` (or is listed with the §-clause that makes it
   irrelevant) — PB1576's "every axis" becomes structural, and `ConformanceDescriptor_AgreesWithTheComparator` is
   deleted with the string it guarded (rule 4: no parallel representation survives).

No shims: `ConformanceDescriptor`, `CobolInvokeArg.Descriptor` (string), the four `Content*Mismatch` literal arms and
`OoBinder`'s carrier refusals are deleted in the change that replaces them; every caller moves.

## Progress (wave 1011, group C)

Decomposition item 4 (PB1051, method BY VALUE) is LANDED: the passing mode is `OoFormal.ByValue`, compared by
`MethodConformanceMismatches` (rule 1); the INVOKE lane asks the formal's mode (GR6 b)) and binds a BY VALUE argument through
the BY CONTENT arms. A universal invocation never matches a BY VALUE formal (all arguments BY REFERENCE, SR6), written as an
unconditional `break` in the `__CobolInvoke` case — when item 6's structured description arrives the passing mode is already a
field of the formal it describes.
