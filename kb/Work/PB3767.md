# PB3767 — the report-entry refusal needs a `!Symbols.TryResolve` guard

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/ReferenceResolver.cs#ReportUnidentified` (the `ReportEntryReferenceRefused` call, now guarded by `DataItemsAmbiguousBeforeReportEntry`; the COBOL1639 text counts the report entries of the data items' tier), `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.Reports.cs#DataItemsAmbiguousBeforeReportEntry` and `#ReportEntriesInTierOf` (the one order and the wording count), `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs#ResolveClauseOperand` (reads the same order), `conformance-suite/cases/13.8.6.2.3-Report-Items/pb3767-ambiguous-reference-sharing-a-report-entry-spelling.cob`, `pb3767-qualified-reference-reaching-only-a-report-entry.cob` and `pb3767-local-report-entry-nearer-than-ambiguous-global-data-items.cob` (with their refusals in `conformance-suite/wiseowl/diagnostics/`)

On PB1046's branch (PR #596, worktree-wf_1341dc87-1c4-11) the report-entry refusal in `ReportUnidentified` fires before the ambiguity arms with no guard that the name has no ordinary-data candidate. An AMBIGUOUS ordinary reference whose spelling a report entry also carries is therefore told only that it names a report item (COBOL5092) instead of the true ambiguity (COBOL1639 "does not uniquely identify"). The sibling constant-name and condition-name arms both guard with `!Symbols.TryResolve`. Harm: a misleading message on a refused program. Fix: the same guard, plus a golden of an ambiguous ordinary reference sharing a spelling with a report entry.

(2026-10-25, PB1046 review R1-1, severity low, not blocking at round 1.)

## Landing (2026-10-30, wave 20261783 group B)

Re-probed on the current tree: two `PV` data items under G1 and G2 plus a REPORT SECTION entry `PV`, then `MOVE PV TO W`, drew COBOL5092. The fix is NOT the `!Symbols.TryResolve` guard this note proposed: a data item of the same spelling that the written qualifiers do not reach (`PV OF DET-1`, DET-1 the report group) must still draw COBOL5092, and `!TryResolve` would have told that reference "declared, but not under the given qualifier". The guard is the one count the data division's clause operands and OCCURS DEPENDING ON already take before they ask `ReportEntryReferenceRefused`: `QualifiedCandidates(...).Count <= 1`, since more than one data item reached is §8.4.2.2.3 SR1's ambiguity (COBOL1639). The siblings (`DataBinder.ResolveClauseOperand`, `DataBinder.Odo`) were swept and already count first. Goldens: the ambiguity (COBOL1639) and its counterpart, the qualified reference reaching only the report entry (COBOL5092).

### Review round 1 (R1-1 blocking, R1-2 lead)

R1-1: the count `QualifiedCandidates(...).Count <= 1` was depth-blind. OUTERP's two GLOBAL `PV` items and a report entry `PV` of the contained INNER: §8.4.6.2.1 3) a) makes INNER's report entry the referenced item, so COBOL5092 stands; the first fix told COBOL1639 (reproduced on the branch build, then fixed). The order now lives in ONE place, `DataBinder.DataItemsAmbiguousBeforeReportEntry` (ambiguity first unless a report entry of a NEARER source element exists), read by `ReferenceResolver.ReportUnidentified` and by `DataBinder.ResolveClauseOperand` (the swept sibling). Golden `pb3767-local-report-entry-nearer-than-ambiguous-global-data-items` (COBOL5092 at 85/2002/2014/2023). The clause-operand sibling has no golden: a contained program's file-control clauses bind BEFORE the container's globals are inherited (the PB3766 mechanism), so no tier span can reach `ResolveClauseOperand` today and the change there is behaviour-neutral until that is fixed.
R1-2: the COBOL1639 text now counts the report entries of the data items' source element (`ReportEntriesInTierOf`).
