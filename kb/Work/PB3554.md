# PB3554 — whose USE procedure runs for a foreign file's refusal

## Lead (the implementer's, verbatim from the PB3338 report)

Lead: with EC-I-O checking on, the foreign-file arm's `__IoCheckEc` runs THIS element's open-mode USE tiers (`USE AFTER ERROR ON I-O`, §14.9.49.4 GR6 b) "any file open in the I-O mode") for another element's file, while with checking off the foreign arm runs no USE procedure. Either reading may be right; the on/off asymmetry is a question for the owner. Site: `TransactionEmitter.EmitStatement` Foreign(), `UseTierEmitter.EmitScopeTiers`.

Repro (the report's witness): `CommitRollbackRefusalWitnessTests` ForeignProgram plus `USE AFTER ERROR ON I-O` in the contained program.

## The rule (checked with `cite.py --check 14.9.49.4`, OK)

The clerk's check found the quoted rule at §14.9.49.4 GR6 item d), not b): "d) If I-O is specified, the associated procedure is
executed when the condition described in the USE statement occurs for any file open in the I-O mode or in the process of
being opened in the I-O mode, except those file…" (the check output truncates the sentence). The adjudicator reads the full
item from the spec before settling.

## Readings for an adjudicator to settle before the owner is asked

- Reading 1: the executing element's open-mode USE applies to a foreign file's refusal. "any file open in the I-O mode"
  names no element, so a file open in I-O mode in another element is within it. The checking-off arm then runs no USE
  procedure where it should, and is the arm to change.
- Reading 2: it does not apply. A USE declarative belongs to the source element that declares it, and applies to the files
  that element describes or names; another element's file is not one of them, so the checking-on arm runs a procedure it
  should not, and is the arm to change.

Either reading makes the on/off asymmetry a defect in one arm. No reading is chosen here; the adjudication decides it from
the full text of the item and §14.9.49.4's other rules, and only a residue that the standard leaves open goes to the owner.

## Adjudication 2026-10-25 (mythos lane, pinned main 51103b9a1)

**Final verdict:** DEFECT  
**Checkpoint (full record):** `E:/COBOL-coord/scratch/mythos/adj-20261025/PB3554.json`

**Expected from the spec:** A refused COMMIT or ROLLBACK is told as an input-output statement's fatal status (docs/CONFORMANCE.md A.4.3 determination (a)). Format 1 USE selection follows the I-O status, not EC checking: §14.6.13.1.1 'if checking for EC-I-O exception conditions is not enabled, there is no link between EC-I-O exception conditions and I-O status values' and its NOTE 1 'I-O status indicators are always enabled and cannot be turned off'; §9.1.13.1 'The I-O status also determines whether an applicable exception processing statement is executed'; §9.1.12 2) names format 1 USE declaratives as applicable exception processing. The candidate declaratives are those of the element that contains the statement (§14.9.49.4 GR4 a)), which is the element executing COMMIT or ROLLBACK, followed by its containers' GLOBAL ones (GR4 b)). Among them, GR6 a) runs a file-name USE 'when the condition described in the USE statement occurs', and GR6 b)-e) run an open-mode USE for 'any file open in the I-O mode' (and the other modes). No rule limits the open-mode phrase to files the element describes. Reading 1 therefore holds: the executing element's format 1 USE applies to another element's refused file with or without checking. The file-name tier applies when the element names the file (for example a containing element's GLOBAL file), and the open-mode tier applies by the file's open mode. The checking-on arm is right and the checking-off arm, which runs no USE at all, is the defect. After such a declarative the run unit continues as in the own-file arm (a declarative ran or a FILE STATUS item exists), and item 8's ROLLBACK follows the declarative.

## Landed (wave 20261712 A)

Re-probed on a fresh build before the fix: the adjudication's witnesses, written as `ForeignCover` cases of
`CommitRollbackRefusalWitnessTests` (both keyed organizations, COMMIT and ROLLBACK), failed 20 of 20 with checking off:
the contained program's `USE AFTER STANDARD ERROR PROCEDURE ON I-O` (and `ON KF` for the containing element's GLOBAL
file) never ran, and with no FILE STATUS item the run unit terminated although a declarative covered the status.

Fixed at the root: the plain format 1 hook is now ONE method, `SequentialIoEmitter.EmitPlainIoCheck` (the item 8
question, `__IoCheck`, item 8's ROLLBACK, the RESUME transfer), used by `EmitUseHook`'s own-file arm and by
`EmitForeignFileIoCheck`'s checking-off branch, so the two arms cannot drift. The foreign branch returns the "no
declarative ran" test, and `TransactionEmitter` terminates under DOC-A.1-103 only when none ran and no element gives the
file a FILE STATUS item. The checking-on arm is unchanged (`__IoCheckEc` already selected the tiers). Basis: format 1
selection follows the I-O status, not EC checking (§14.6.13.1.1 and its NOTE 1), the candidates are the executing
element's declaratives and its containers' GLOBAL ones (§14.9.49.4 GR4), and GR6 b)-e) name no element.

Witnesses: `unit:CommitRollbackRefusalWitnessTests.A_refused_commit_or_rollback_of_another_elements_file_reaches_the_executing_elements_declaratives_with_or_without_checking`
(the open-mode and file-name tiers with and without a FILE STATUS item, the open-mode tier with checking on, and a
declarative ending in RESUME AT, whose trace shows item 8's ROLLBACK before the transfer). No golden: a refused COMMIT
needs the fault-injecting medium, which the conformance suite cannot drive (as for PB3338 and PB3542-PB3544).
