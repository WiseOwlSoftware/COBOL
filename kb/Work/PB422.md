# PB422 — MOVE's three source-shape rules: one skipped by placement, one absent, one filed under the wrong rule

Three defects, one mechanism family: §14.9.25.3 has rules that key on the SHAPE of the sending operand, not on a
Table-16 category pair, and the compiler has no place to put them. Two are written inside the Table-16 loop, one
is not written at all, and one is routed to an edition registry that does not fit it.

## (1) SR8 — the group receiver escapes, because the check sits below the GR4 group filter

`MoveBinder.MoveCategoryLegality` computes `senderBinaryFamily` ONCE before the loop
(`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/MoveBinder.cs:203-204`), then opens each iteration with

```csharp
foreach (var t in targets)                                                     // :206
{
    if (MoveReceiverCategory(t) is not { } recvCat) continue;   // group receiver — GR4 exempt   :208
    ...
    if (senderBinaryFamily && recvCat is not (PicCategory.Numeric or PicCategory.NumericEdited))  // :211
```

`MoveReceiverCategory` (:152-160) returns null for an alphanumeric group by its
`_ when t.Item.OperandPic is null => null` arm (:159). The `continue` at :208 is the §14.9.25.4 GR4
conversion-free group move — a correct exemption for SR10/Table 16 and for NOTHING ELSE — so the SR8 arm eight
lines below is never asked about a group receiver.

`MoveTable16`'s own class doc says where these rules belong
(`src/Cobol.Net.Compiler/Binding/MoveTable16.cs:77-80`): "⚠ WHAT STAYS WITH THE CALLER: the SOURCE-SHAPE rules
that are not about categories at all — §14.9.25.3 SR7 …, and SR8 (the fixed-width binary family). Those key on
the bound operand's SHAPE, not on a Table-16 position". The design is right; the PLACEMENT contradicts it. SR7
escapes the same fate only by luck: the boolean receivers it screens are elementary items or BIT GROUPS, and a
bit group carries an as-if picture (§13.18.29.4 GR1b) that survives the filter.

## (2) SR6 — no implementation exists anywhere

The sender switch in the same method maps EVERY figurative constant to `new Table16Operand(PicCategory.Group)`
by its `_ =>` default (:197, comment "figuratives (SR7 below) / errors — category-exempt"), and
`MoveTable16.Refusal` returns null for a Group operand on either side, so a figurative sender is category-exempt
by construction. Even if it were not, Table 16 would AFFIRMATIVELY ADMIT the move: §14.9.25.4 GR7's Table 17
gives ZERO against an alphabetic receiving operand the category ALPHANUMERIC, and Table 16's Alphanumeric row ×
Alphabetic column is "Yes". SR6 is a source-shape prohibition that no category table can express — the exact
mirror of the SR7 arm sitting eight lines away at :222.

## (3) SR5 — a multi-character digit-only ALL literal is filed under the 2023 removal, and that mis-gates three editions

SR5's exception has NO length qualifier, and Annex E.2 item 1 bullet 1's exception text is word-for-word the
same, so `ALL "57"` is INSIDE what SR5 permits. What actually bars it is §8.3.3.6.3 SR3, which carries no edition
gate at all. `MoveBinder`'s own class doc cites §8.3.3.6.3 SR3 as the reason and then routes the case to the
`ConstructRegistry` row `move-alphanumeric-figurative-removed-2023` via the
`all is not { IsDigitOnly: true }` eligibility test at :136. Because the removal row is edition-gated and SR3 is
not, an unconditionally illegal program is ACCEPTED at 85 / 2002 / 2014 and under `2023 --permissive`, and at
2023 strict it is rejected under a diagnostic that names SR5's removal and asserts "permitted through 2014" — a
claim about THIS shape that is false at every edition.

## The code sites and the shape of the repair

- `MoveBinder.cs:206-216` — the loop; `:208` the group `continue`; `:211-216` the SR8 arm; `:222-229` the SR7
  arms; `:203-204` `senderBinaryFamily`. `MoveBinder.cs:152-160` — `MoveReceiverCategory`.
- `MoveBinder.cs:197` — the figurative-exempting sender default; the SR6 arm is ABSENT.
- `MoveBinder.cs:77-82` (the `MoveFigurativeEditionGates` class doc stating the SR3 reasoning) and `:136` (the
  `all is not { IsDigitOnly: true }` eligibility); `src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs`
  `#GateMove`; `src/Cobol.Net.Editions/ConstructRegistry.g.cs` row `move-alphanumeric-figurative-removed-2023`.

**THE REPAIR IS STRUCTURAL, NOT THREE MOVED LINES** (CLAUDE.md rule 5). Give the source-shape rules their OWN
pass over `targets`, ABOVE the Table-16 gate — SR6, SR7 and SR8 together — so the NEXT such rule added is
screened automatically instead of depending on whether its receiver kind happens to carry a picture. SR6's arm is
the mirror of SR7's: `source is BoundFigurative { Kind: 'Z' }` against a receiver whose `OperandPic.IsAlphabetic`
is true, exactly as SR7 is `source is BoundFigurative { Kind: not 'Z' }` against a boolean receiver. Pair the
pass with a DRIFT TEST that a GROUP receiver reaches every source-shape screen, so "automatic" stays true.

For (3), SEPARATE THE TWO RULES: an edition-invariant §8.3.3.6.3 SR3 check on the ALL literal's length against a
numeric or numeric-edited receiver, leaving the SR5 removal row to the shapes SR5 actually names. ⚠ The 85
acceptance is currently pinned GREEN by
`tests/Cobol.Net.Tests.Conformance/MoveEditionDifferentialTests.cs:102`
`AllDigitMultiCharacter_RepeatTruncate_At85_Sr3Provisional`, whose own NAME records that it is provisional — a
green test holding the gap open. It must be rebaselined in the same change set.

## The sibling sweep the fixer must do

- Every other verb whose syntax rules include a source-shape prohibition evaluated inside a per-target loop that
  begins with a group/category `continue`. The `MoveReceiverCategory(...) is not { } ... continue` idiom is the
  thing to grep for; any rule placed after it inherits the GR4 exemption whether or not GR4 reaches it.
- Every `ConstructRegistry` row whose in-code justification cites a rule with NO edition gate. The SR5/SR3 mix-up
  is that shape: an edition-gated registry row standing in for an edition-invariant rule mis-gates every edition
  the row does not name, in BOTH directions.
- SR7's own group-receiver leg: it is correct today only because bit and national groups carry as-if pictures.
  Once the source-shape pass exists, assert that fact rather than relying on it.
