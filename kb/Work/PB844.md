# PB844 — LANDED — `MOVE "Q" TO <PIC ZZZ9>` answered `   0` and raised nothing

Source: the `PB415` implementer report, item (a), which reported the value and asked for the Table 16
derivation. The derivation is done here and it moves the finding: the VALUE is undefined by the standard, so the
defect is the MISSING exception condition, not the digits.

## Repro — re-run on this tree

`scratchpad/reg4/probe/p40_move_q_checked.cob` (PROGRAM-ID `R4P40`), `--std 2023 --run`, with
`>>TURN EC-DATA-INCOMPATIBLE CHECKING ON` as the first line:

```
LIT-NE=[   0] ES=[                               ]      MOVE "Q"  TO <PIC ZZZ9>
ITM-NE=[   0] ES=[                               ]      MOVE <PIC X "Q"> TO <PIC ZZZ9>
ITM-NUM=[000] ES=[                               ]      MOVE <PIC X "Q"> TO <PIC 9(3)>
```

All three complete normally with `FUNCTION EXCEPTION-STATUS` spaces. (`p09_move_alnum_to_numed.cob` shows the
same value without the TURN, beside the control `MOVE 42 TO NE` -> `[  42]`.)

## The rules, quoted

```
$ python scripts/spec/cite.py --check 14.9.25.3 "Table 16"
  OK  §14.9.25.3 10)  (Syntax rules)
      10) For all other cases not described in Syntax rules 8 and 9, table 16, Validity of types of MOVE statements, specifies the validity of the move.
```

Table 16's `Alphanumeric` row gives `Yes` under `Numeric, Numeric-edited`, so the move is VALID and a diagnostic
would be wrong.

```
$ python scripts/spec/cite.py --check 14.9.25.4 "When the sending operand is described as alphanumeric or national, the sending operand is treated as if it were an unsigned integer of category numeric"
  OK  §14.9.25.4 6) 3.  (General rules)
$ python scripts/spec/cite.py --check 14.9.25.4 "Otherwise, if the content of the sending operand would result in a false value in a numeric class condition, the EC-DATA-INCOMPATIBLE exception condition is set to exist"
  OK  §14.9.25.4 6) 1.  (General rules)
```

So the sender is an unsigned integer of one digit whose content is `Q`; `Q` is false in a numeric class
condition; therefore EC-DATA-INCOMPATIBLE is set to exist and the results of the MOVE are undefined. Printing
`   0` is a permitted result. NOT raising is not.

## Expected vs observed

Expected (checking on): EC-DATA-INCOMPATIBLE exists — fatal, so the statement's results are undefined and a
declarative or the default action runs. Observed: no condition, no declarative, a fabricated zero, silently.

## Code site

`src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs#ConvertSource` (the numeric and numeric-edited receiver
arms) and the checking gate `EcEmitter.cs:178` `("EC-DATA-INCOMPATIBLE", "DataIncompatibleChecking")`. The gate
and the runtime predicate both exist (PB230 built them for the fixed-point sending item, §14.6.13.2 rule 2);
what is missing is the ALPHANUMERIC-SENDER arm calling them — the class-condition test on the sender's
characters before it is valued.

## Sibling sweep the fixer owes

* The same GR6 d) 3 conversion is performed by every verb that takes an alphanumeric sender into a numeric
  receiver: `COMPUTE`/arithmetic operands (§8.8.1.1 bars them, so check), `INITIALIZE ... REPLACING`,
  `STRING`/`UNSTRING` counters, and the `SET ... TO` arithmetic arm (see kb/Work PB212).
* The FIGURATIVE-constant leg (GR6 d) 3 b) is a separate replication rule and must not be swept into the
  literal leg.
* Goldens: one positive (`MOVE "12" TO <PIC 9(3)>` -> 012, no condition) beside the negative, or the fix will
  be pinned by a test that only ever sees the failing case.

## Landed — 2026-09-13 (folded into kb/Work PB426)

**SAME MECHANISM, MEASURED BEFORE FOLDING.** This note's repro was re-run on the fix worktree and reproduced
exactly (`MOVE "Q" TO <PIC ZZZ9>` → `   0`, `FUNCTION EXCEPTION-STATUS` spaces, under
`>>TURN EC-DATA-INCOMPATIBLE CHECKING ON`). It is §14.9.25.4 GR6 d) 1 where PB426 is GR6 d) 3 — the same
sentence's two halves about the same operand, implemented in the same decode and reached from the same emit
sites — so the two were fixed as one change (numeric design D25).

`CobolNum.FromAlphanumericSending` is the checked read, the exact twin of `ParseImageSending` (§14.6.13.2 rule 2,
kb/Work PB230): it raises the fatal EC-DATA-INCOMPATIBLE when checking is enabled and the sender's content
"would result in a false value in a numeric class condition", delegating that predicate to the ONE
class-condition implementation `CobolClass.IsNumeric` (§8.8.4.4.4 GR3 n) 2 — "consists entirely of the characters
0, 1, 2, 3, …, 9", including its zero-length answer) rather than writing the test a second time. All three of
this note's probes now terminate the run unit abnormally naming EC-DATA-INCOMPATIBLE.

**The arm, not the decode, is what got the check.** GR6 d) 1 is a MOVE rule: its scope is GR6 d)'s own, "when a
numeric or numeric-edited item is the receiving item". So the checked read is emitted through a new
`SendingRef.MoveToNumeric` context and a new `SendingRefRules.AlphanumericChecked` reading — set by MOVE and by
every statement whose own rules transfer "according to the rules for the MOVE statement" into such a receiver
(§14.9.48.4 GR11 c), UNSTRING INTO), and by nothing else. ⚠ Wiring it into the shared decode instead would abort
legal source: `COMPUTE R = <PIC X "Q"> + 1` under `--permissive` is not a MOVE and the standard asks nothing of
its content there. That over-raise guard is
`MoveAlphanumericSenderTests.AnArithmeticOperandIsNotAMove_AndRaisesNothing`, and it was PROVEN to fail once —
the first version of it used an alphanumeric receiver, a class condition and a literal subscript and was VACUOUS
(none of the three reaches the decode at all; it stayed green with the checked read wired in unconditionally).

**The sibling sweep this note asked for.** The UNSTRING counters are covered (both numeric arms of the UNSTRING
receiver dispatch now take the checked, capped decode). §8.8.1.1 bars an alphanumeric arithmetic operand under
strict conformance, so `COMPUTE` has no obligation here — measured and left unchecked deliberately, per above.
The FIGURATIVE leg (GR6 d) 3 b) was kept out of the literal leg exactly as this note required: it replicates
across the RECEIVER's digit positions and takes `CobolNum.DigitMagnitude`, which applies no size rule and no
check. `INITIALIZE ... REPLACING` and `SET ... TO` (kb/Work PB212) were NOT swept — see the report's new-defect
paragraph.

**Positive control beside the negative**, as this note required: `2002/pb426_alnum_sender_data_incompatible`
runs with checking ON over all-digit senders and asserts that nothing is raised (`MOVE "12" TO PIC 9(3)` → 012).
`negative/pb844-ec-data-incompatible-turn-below-2002` pins the edition floor: the request to CHECK is
COBOL-2002 (§7.3.25), while the MOVE itself is legal COBOL-85.

Row `GR-14.9.25.4-6` (PB426's) carried this divergence in its notes and is re-verdicted CONFORMS with it.
