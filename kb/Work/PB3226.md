**Sites:**
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/StringUnstringBinder.cs:194-218` (StringUnstringBinder.BindUnstring delimiter loop)
- `src/Cobol.Net.Compiler/Binding/Procedure/ExpressionBinder.cs:363-365` (ExpressionBinder.SymbolicOperand)

**Rule it breaks:** ISO §14.9.48.4 GR7 gives the collapse of contiguous delimiters to the ALL phrase only, and GR8 requires that two contiguous delimiters leave the current receiving area space-filled. A bare symbolic character is a figurative constant without the word ALL: BoundAllLiteral.BeginsWithAll is false for exactly this case (BoundTree.cs, kb/Work PB110).

**Scenario:** ExpressionBinder.SymbolicOperand binds a bare symbolic-character as BoundAllLiteral { BeginsWithAll = false }, because its value semantics are the ALL fill. StringUnstringBinder.BindUnstring line 217 is meant to undo the grammar ambiguity where `DELIMITED ALL "0"` parses as the figurative ALL literal, but it rewrites EVERY BoundAllLiteral delimiter into a plain literal with all = true without asking BeginsWithAll. Measured on the pin build with SYMBOLIC CHARACTERS COMMA-CH IS 45 and SRC PIC X(8) VALUE "A,,B": `UNSTRING SRC DELIMITED BY COMMA-CH INTO X1 X2 X3` displays [A  ][B  ][   ], while the same statement with DELIMITED BY "," displays [A  ][   ][B  ], which is what GR8 requires. The program compiles clean and silently shifts every field after a run of contiguous delimiters. A CSV or fixed-separator parser that names its separator through SYMBOLIC CHARACTERS gets wrong data.

**Measured how:** R2 batch finding `procedure-binding-5--code--f1#4` (pair procedure-binding-5--code), read in the pinned tree at 8be23006851a; skeptics rule upheld, scenario upheld, site upheld.

**Spec:** §14.9.48.4 "When any examination encounters two contiguous delimiters, the current receiving area shall be space-filled if it is described as alphabetic, alphanumeric, or national; or zero-filled if it is described as numeric." (`cite.py --check` passed at collection); §14.9.48.4 "When the ALL phrase is specified, one occurrence or two or more contiguous occurrences of literal-1 (figurative constant or not) or the content of the data item referenced by identifier-2 are treated as if they were only one occurrence" (`cite.py --check` passed at collection)

**Target:** Line 217 sets all = true only when the BoundAllLiteral was written with the word ALL (BeginsWithAll true). A bare symbolic character becomes a one-occurrence delimiter of its literal value, with all left as the phrase states. Add a golden that pins both spellings (bare symbolic character and ALL symbolic character) against contiguous delimiters, then sweep the other consumers that turn a BoundAllLiteral into a phrase flag. INSPECT (InspectBinder.cs:316, 373) was checked and keys on the written ALL token, so it is not a sibling.

**Design reference:** PB110.

**Also found, already fixed on main** (the branch review of notes-PB1754-r2b4b-20261016 (R1-1 to R1-3) and of notes-PB1754-r2b5b-20261016 (R1-1 to R1-5)): `procedure-binding-5--code--f2#4` (pair procedure-binding-5--code; skeptics rule upheld, scenario upheld, site upheld): UNSTRING refused a reference-modified numeric, numeric-edited or alphanumeric-edited sender, delimiter or DELIMITER IN item, because SR2 was asked of the base item's category, not the §8.4.3.3.4 unique item's. PB2586 fixed it on main after the pin (4b7966db0: StringUnstringBinder.Sr2OffendingCategory asks ItemCategory.IsAlphanumericOrNational(place)), so it sets no harm flag here and names no site; it stays on `r2_ids` only so the batch filer never files it again (kb/Work PB3259). It had been merged into this note on overlapping StringUnstringBinder.BindUnstring sites.

**Landed (wave 1111 F).** Re-probed on the Debug build: `SYMBOLIC CHARACTERS COMMA-CH IS 45`, sender `"A,,B"`, `UNSTRING SRC DELIMITED BY COMMA-CH INTO X1 X2 X3` displayed `[A  ][B  ][   ]` against `[A  ][   ][B  ]` for `DELIMITED BY ","`. Fix at the root, `StringUnstringBinder.BindUnstring`: the BoundAllLiteral-to-literal rewrite now sets the delimiter's ALL flag from the written `ALL` token OR `BoundAllLiteral.BeginsWithAll` (`all |= allLit.BeginsWithAll`), so a bare symbolic character is one occurrence of its character and only the ALL phrase collapses contiguous delimiters (§14.9.48.4 GR7, GR8; `cite.py --check` OK for both). Sweep: INSPECT (`InspectBinder` 316/373) already keys on the written ALL token (`BeginsWithAll`); no other consumer turns a BoundAllLiteral into a phrase flag (`grep BoundAllLiteral src`: the other users are value renderers). Golden `14.9.48-UNSTRING/pb3226_unstring_symbolic_delimiter` (four spellings: bare symbolic, literal, ALL symbolic, ALL literal; numeric middle receiver zero-filled by GR8). No diagnostic code used.
