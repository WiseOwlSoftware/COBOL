# PB256

**Rows:** `RV-15.93.4-1`, `RV-15.93.4-L2.4`, `RV-15.95.4-L2.5`

The NUMVAL-family scanners take their mode and flag decisions as PARAMETERS and every test supplies them as literals, so the compiler arm that computes them is untested — and where the scanner must choose between two readings of a rule, it chooses in silence.

ROWS: RV-15.93.4-1 and RV-15.93.4-L2.4 (§15.93.4 r1, TEST-NUMVAL's three legs and its digit-cap sub-notes) and RV-15.95.4-L2.5 (§15.95.4 r1 b item 5, TEST-NUMVAL-F's fifth-exponent-digit position).

⛔ FINDING 1 — A NORMATIVE TENSION RESOLVED WITH NO RECORD, and it changes the answer. §15.69.3 r5 makes embedded spaces IGNORED everywhere outside the significand ('Embedded spaces in argument-1 are ignored except between the first numeric digit and the last digit that precedes a letter E' — --check OK), while r1's figure draws the exponent `n` as a contiguous one-to-four-digit run with [space-string] only before and after it. The two readings give DIFFERENT answers for an exponent written with an interior space, and they land squarely on this rule's 'more than four significant digits' count. `TEST-NUMVAL-F("1E+1 2345")`: the code answers 6 — the digit loop exits at the space with ed=1, the trailing-space skip advances to '2', and `if (i != n) return Pos()` reports it — where the r5 reading makes the exponent 12345, five digits, and §15.95.4 r1b item 5 requires the position of its FIFTH digit, 9. `pendingSpace` implements r5's exception for the significand and NOTHING implements it for the exponent. Nothing in NvfScan, its comments, the design docs or any test records that the choice was made. Either reading may be defensible; an undocumented one is not.

⛔ FINDING 2 — THE COMPILER ARM HAS NO TEST, ON ANY OF THE THREE FUNCTIONS. `TestNumvalScannerTests.CommaMode_SwapsSeparatorRoles` calls `CobolIntrinsics.TestNumval("1,5", commaMode: true)` — the flag is a LITERAL, so it exercises the runtime scan and never `ctx.Data.DecimalPointIsComma → IntrinsicRenderer.CommaFlag → the emitted named argument`. `TestNumvalScannerTests.DigitCap_FollowsArithmeticMode` calls `TestNumval(d40, digitCap: 34)` — the cap arrives as a LITERAL, no arithmetic mode is in scope in a unit test, and the name asserts exactly what the test does not measure (feedback_green_gates_arent_evidence). No conformance golden compiles TEST-NUMVAL or TEST-NUMVAL-F under `OPTIONS. ARITHMETIC IS STANDARD-DECIMAL` at all; the property is proven live only through SIBLINGS (`2023/pb60_numval_standard_decimal`, `2023/numvalf_decimal_comma_and_spaces`). Same for the NATIONAL edge both records flagged: correct by construction (`OperandText.FieldAsString:249-250` hands the scan the UTF-16 image, one char per national position, so 'C'/'R', ' ' and the ASCII digits are the same code units) but unmeasured in both directions.

⛔ FINDING 3 — A RULE LEG ADJUDICATED IN NO RECORD. RV-15.93.4-L2.4's own rule text carries THREE parts — sub-note 4, then 'c) Otherwise, (FUNCTION LENGTH (argument-1) + 1).', then the NOTE enumerating leg c's three error kinds (zero-length, all spaces, 'valid characters but incomplete, such as the string " +."'). Its notes and test-ref address only the digit cap; leg c) was argued on RV-15.93.4-1, whose rule text STOPS at leg b) and does not contain it. Leg c) is therefore adjudicated NOWHERE. (On the refuter's own read leg c) is CORRECT — `NvScan:621` returns n+1 for a digit-free scan that ran off the end, and all three NOTE kinds trace: "" → 1, "    " → 5, " +." → 4 — so this is an unadjudicated part, not a wrong answer. It still needs its record and its golden.)

FOURTH, SMALLER: RV-15.93.4-1's leg-c width evidence was output-shaped and could not discriminate — golden N10's verdict 32 is 32 for ANY width >= 32 — and the property was re-derived on other evidence (`CobolString.Fit` pads or truncates every alphanumeric store to the declared width; `2023/pb33_numval_family_digit_cap`'s TEST-31 = 0 over `S31 PIC X(44)` exercises a padded 12-space tail end to end). The conclusion survives; the cited proof did not, and the row's test-ref should say so.

WHAT IS SETTLED AND MUST NOT BE RE-LITIGATED: RV-15.93.4-L2.4's third ground — that `NumericRenderer.StandardDecimal` also fires for `ArithmeticMode.Standard`, so plain ARITHMETIC IS STANDARD gets a cap no sub-note authorises — is now a stated determination rather than a widening: `ArithmeticModes.NumvalDigitCap` (OptionsModel.cs:81) names the 2002 STANDARD mode at 34 'because it routes to the same SDIDI engine' (PB198). And the standard-binary halves both records price are PB198's recorded decline.

FIX SHAPE: decide the exponent-space reading against §15.69.3 r5 and record it (a comment at the loop plus a CONFORMANCE.md determination if the figure's reading wins); add STANDARD-DECIMAL conformance goldens for TEST-NUMVAL and TEST-NUMVAL-F so the flag-producing arms are measured end to end; and adjudicate §15.93.4 leg c) in the record that carries its text.

VERIFIED LIVE AT HEAD (read-only): NvfScan:714-720 unchanged; CommaFlag/DigitCapFlag are still the compiler-side arms and the two unit tests still pass literals.

## Mechanism

src/Cobol.Net.Runtime/Intrinsics/CobolIntrinsics.Exact.cs#NvScan and #NvfScan take commaMode / digitCap / anycase as parameters; the compiler arms that compute them are src/Cobol.Net.Compiler/CodeGen/Emit/IntrinsicRenderer.cs#CommaFlag (:792), #AnycaseFlag and #DigitCapFlag (:815-817). The silent choice is NvfScan's exponent run at Exact.cs:714-720 (`while (i < n && char.IsAsciiDigit(text[i])) { if (++ed > 4) return new(Pos(), …); … }`), contiguous by construction, where §15.69.3 r5's embedded-space exception is implemented for the SIGNIFICAND alone via `pendingSpace`

## Lineage

PB33/PB34 (landed) built the digit caps, PB60 (landed) made the validators and the value paths ONE scan, PB198 (landed) made the cap mode-derived through ArithmeticModes.NumvalDigitCap. Each landing tested the scan; none tested the arm that feeds it.
