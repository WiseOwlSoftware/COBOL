# PB435 — a passing check that never looked at what it claims to check

## 1. THE MECHANISM

`tests/Cobol.Net.Tests.Conformance/PerformFormat3Tests.cs:50-52` carries a two-line comment spelling out SR15's
bare-plus-FILE-paired reading — "a BARE exception-name coexisting with a FILE-paired instance of the SAME name
(a bare occurrence is not 'in conjunction with a file-name', so the repeat is illegal)" — and then a body that is
a **verbatim copy** of `MultiFileDeleteInImp1_Rejected1613`'s at `:87-89`:

    // :51-52   BareAndFilePairedSameName_Rejected1600
    AssertRejects(ProgFiles("    PERFORM\n        DELETE FILE F1 F2\n    WHEN EC-SIZE DISPLAY \"x\"\n    END-PERFORM.\n    STOP RUN."), "COBOLNET1613");

    // :88-89   MultiFileDeleteInImp1_Rejected1613
    AssertRejects(ProgFiles("    PERFORM\n        DELETE FILE F1 F2\n    WHEN EC-SIZE DISPLAY \"x\"\n    END-PERFORM.\n    STOP RUN."), "COBOLNET1613");

Both the `AssertRejects` source argument and the expected diagnostic code are identical strings. The compiled
source contains no duplicated exception-name at all — one WHEN phrase, one exception-name — so the assertion the
test's NAME promises (`…_Rejected1600`) is never made; the test asserts `COBOLNET1613`, the multi-file DELETE
ban, twice over. It passes, so nothing flags it.

The SR15 arm the name claims is therefore uncovered. The neighbour test `DuplicateExceptionName_Rejected1600`
(`:45-47`) covers only the bare+bare case (`WHEN EC-SIZE … WHEN EC-SIZE …`), which the `files.Distinct()` clause
alone would catch; the arm that needs the `files.Any(f => f is null)` clause has no test.

## 2. THE RULE, QUOTED, WITH ITS `--check` LINE

    python scripts/spec/cite.py --check 14.9.28.3 "All instances of an exception-name shall be specified only once in a format 3 PERFORM statement unless done so in conjunction with different file-names"
    OK  §14.9.28.3 15)  (Syntax rules)
        15) All instances of an exception-name shall be specified only once in a format 3 PERFORM statement
            unless done so in conjunction with different file-names.

⚠ Its neighbour SR14 constrains the FILE-NAME, not the exception-name, and shares none of this wording — checked
separately so the fragment cannot be confused for it:

    python scripts/spec/cite.py --check 14.9.28.3 "If file-name-1 or file-name-2 is specified in a WHEN phrase"
    OK  §14.9.28.3 14)  (Syntax rules)

A test named for the bare-plus-paired arm shall compile a program in which one exception-name appears both bare
and FILE-paired, and shall assert `COBOLNET1600`.

## 3. EXPECTED vs OBSERVED — RE-RUN ON HEAD (89044aa0)

**The COMPILER is right; only the test is wrong.** Verified on HEAD:

           PERFORM
              ADD 1 TO N
           WHEN EC-I-O-AT-END
              DISPLAY "A"
           WHEN EC-I-O-AT-END FILE F1
              DISPLAY "B"
           END-PERFORM

    $ cobol.exe .../pf_sr15_bare_plus_paired.cob --std 2023 --run
    exit 70
    error COBOLNET1600: exception-name 'EC-I-O-AT-END' is specified more than once without a distinct
    file-name (ISO §14.9.28.3 SR15)

And the duplication is confirmed by reading `PerformFormat3Tests.cs:50-52` against `:87-89` on this tree — the
two `AssertRejects` arguments are byte-identical, as is the expected code. No compile is needed to see it, and
the suite cannot see it either, because both tests pass.

**The cost is not a wrong answer today — it is an UNGUARDED RULE tomorrow.** If the
`files.Any(f => f is null)` clause in `CheckSr14Sr15`
(`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.ExceptionPerform.cs:228`) were ever removed or
weakened, the whole suite would stay green: `DuplicateExceptionName_Rejected1600` would still pass on the
`files.Distinct().Count() != files.Count` clause, and this test never compiled a program with a repeated
exception-name in the first place.

`process_only: true` is set deliberately and is the honest label: on THIS tree the item does nothing to a user's
program. It is filed as a `defect` rather than an `analysis` because there is a concrete, decidable repair.

## 4. THE CODE SITE AND THE SHAPE OF THE REPAIR

* `tests/Cobol.Net.Tests.Conformance/PerformFormat3Tests.cs:50-52` — the mislabelled test
* `tests/Cobol.Net.Tests.Conformance/PerformFormat3Tests.cs:87-89` — the test it was copied from
* `tests/Cobol.Net.Tests.Conformance/PerformFormat3Tests.cs:45-47` — the bare+bare test, which is correct
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.ExceptionPerform.cs:224-231` — the rule it should be
  guarding, whose two clauses are the two arms of SR15

Replace the body with the probe program above and assert `COBOLNET1600`. Then, following rule 5, make the class
of defect impossible rather than fixing the instance: **a test whose name ends `_RejectedNNNN` shall assert
`NNNN`.** That is a mechanical invariant over the test source (a reflection-driven assertion in the conformance
suite's own fixture, or a small CI check), and it converts "someone must notice a copy-paste" into a gate.

## 5. THE SIBLING SWEEP

* ⛔ **Every `AssertRejects` test in `tests/` whose asserted diagnostic code does not match the code in its own
  NAME.** This is a mechanical scan and it is the point of the note — this one was found by reading two tests
  side by side, which does not scale.
* **Every pair of tests with byte-identical `AssertRejects` source arguments.** A duplicated source string with
  two different names is the same copy-paste with the code accidentally right; a duplicated string with the same
  code (as here) is one test doing nothing. Both are worth listing.
* **The other SR15/SR14 arms.** `CheckSr14Sr15` has four decision paths (SR14's bare-instance clause, SR15's
  null-file clause, SR15's duplicate-file clause, and the pass-through). Confirm each has a test that fails when
  its clause is removed — the standing project rule that a green gate proves nothing if it never looked at what
  changed.
* **The Format-3 behaviour tests.** `PerformFormat3BehaviorTests.WhenOther_HandlesUnnamedCondition` is the same
  species of unguarded green (see **PB438**): it writes `RESUME NEXT STATEMENT` inside the WHEN OTHER, which
  forces the identical observable under both readings of the rule it claims to cover.
