# PB534

## Mechanism — picture-clause-p2
The picture's case fold is a blanket `picture.ToUpperInvariant()` in ExpandRepeats (PictureAnalyzer.cs:381) plus `char.ToUpperInvariant(raw)` in the currency-symbol scan (:73-79) and in CanonicalCurrencyMask (:370). For basic letters that is exactly 8.1.3.2 GR3's case-insensitive treatment and is correct. But it is applied to EVERY character including a currency symbol that is not in the COBOL character repertoire, and there ToUpperInvariant silently DEFINES an equivalence between two distinct compile-time coded characters. 12.3.7.3 SR20 permits that only as implementor-defined behaviour, which 4.2.16 then requires the implementation to document -- and docs/CONFORMANCE.md documents no such thing.

### Expected, from the standard
ISO/IEC 1989:2023 13.18.40.3 SR3 (cite --check OK): 'The equivalence between uppercase and lowercase letters appearing as occurrences of a currency symbol in character-string-1 is as specified in 12.3.7, SPECIAL-NAMES paragraph, Syntax rule 20. The equivalence between uppercase and lowercase letters appearing as picture symbols other than currency symbols in character-string-1 is as specified in 8.1.3, COBOL character repertoire, General rule 3.' 12.3.7.3 SR20 (cite --check 12.3.7.3 OK): 'If the character specified as the currency symbol is not a character in the COBOL character repertoire, any equivalence between that character and any other character in the computer's compile-time coded character set is defined by the implementor. In all other cases, compile-time equivalence to that currency symbol is determined as specified in 8.1.3.' 8.1.3.2 GR3 a) (cite --check 8.1.3.2 OK): basic letters elsewhere in the compilation group 'are treated in a case-insensitive manner', with the folding done from uppercase TO LOWERCASE per Annex C. So the behaviour COBOL.NET has is LEGAL -- but only as a defined implementor choice, which has to be stated.

```
$ python scripts/spec/cite.py --check 13.18.40.3 "The equivalence between uppercase and lowercase letters appearing as occurrences of a currency symbol in character-string-1 is as specified ..."
  OK  §13.18.40.3   (Syntax rules)
```

### Observed
The delegated half that is derivable was measured and is right: the case-insensitive treatment of ordinary picture symbols holds at all four editions (`pic s9(3)v99 comp-3` + `pic zz9`, MOVE 12.5 / 12 -> [01250][ 12] at --std 85/2002/2014/2023), and a lowercase spelling of a declared basic-letter currency symbol binds (`PIC wwww9` under CURRENCY SIGN "W" -> [  W12]). What is missing is the STATEMENT of the implementor-defined half, and the probe shows it is not academic -- two distinct characters are conflated with no diagnostic and no documentation, and a program relying on it is portable to no other processor. Two cheap repairs, either acceptable: state in docs/CONFORMANCE.md that compile-time equivalence for a non-repertoire currency symbol is the invariant-culture simple uppercase mapping (and note the Annex C fold direction difference), or narrow the fold so a non-repertoire currency symbol is matched by identity and only basic letters are case-folded -- the latter is the smaller conformance surface and is what 8.1.3.2 GR3's 'basic letters' wording actually scopes.

### Repro
Pinned compiler, --std 2023. SPECIAL-NAMES `CURRENCY SIGN IS "<U+00B5>" WITH PICTURE SYMBOL "<U+00B5>".` (MICRO SIGN) and `01 W1 PIC <U+039C><U+039C><U+039C>9.` written with GREEK CAPITAL LETTER MU -- a different character of the compile-time coded character set -- compiles rc=0 and MOVE 12 renders [ <U+00B5>12], byte-identical to the same program written with the declared MICRO SIGN (probes .../probe/pic-p2/sr3e and sr3f). ToUpperInvariant('<U+00B5>') is '<U+039C>', so the two collapse to one key in the CURRENCY SIGN SET dictionary.
