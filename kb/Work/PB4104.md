# PB4104 — GnuCOBOL: MOVE to numeric-edited: a '0' or '/' insertion symbol inside a Z or * string is not replaced (PIC ZZ0ZZ with 12 gives '  012')

Found by patcher D while proving the patch for the drafted ticket `numeric-edited-comma-insertion` (kb/Work PB4041): its
probe `~/gc-fix/numeric-edited-comma-insertion/_repro/neprobe.cob` (WSL) printed `  012`, `  /12` and `**012` for its
cases A8, A9 and B1. Recorded nowhere before this note. Re-run and reduced for this filing on 2026-10-30.

## Summary

In a MOVE to a numeric-edited item, GnuCOBOL leaves a simple insertion symbol `0` or `/` that is embedded in a
zero-suppression string (`Z` or `*`) as the insertion character, even when every digit position to its left was
suppressed. `PIC ZZ0ZZ` receiving 12 shows `  012` where the standard requires `   12`; `PIC ZZ/ZZ` shows `  /12`
(`   12`); `PIC **0**` shows `**012` (`***12`); `PIC **/**` shows `**/12` (`***12`). Rule 7 of the editing rules makes
an embedded simple insertion symbol part of the suppression string, so it is replaced like a suppressed digit. The
same pictures with `B` or `,` in that position are edited correctly (`   12`), and so is the floating form `$$0$$` on
3.3-dev (`  $12`; 3.2.0 gives ` $012`, which the dev line has fixed). Present in 3.2.0 and 3.3-dev r5751, under
`-std=cobol2014` and the default dialect, with no diagnostic. Class: wrong output.

## Minimal test case

Free reference format (`-fformat=free`), file `~/gc-notes/PB4104/zsins.cob` (WSL). E4, E5 and E6 are controls.

```cobol

PROGRAM-ID. ZSINS.

WORKING-STORAGE SECTION.

01 E2 PIC ZZ/ZZ.
01 E3 PIC **0**.
01 E4 PIC ZZBZZ.
01 E5 PIC ZZ,ZZ.
01 E6 PIC $$0$$.
01 E7 PIC **/**.
PROCEDURE DIVISION.
MOVE 12 TO E1 DISPLAY "[" E1 "]"
MOVE 12 TO E2 DISPLAY "[" E2 "]"
MOVE 12 TO E3 DISPLAY "[" E3 "]"
MOVE 12 TO E4 DISPLAY "[" E4 "]"
MOVE 12 TO E5 DISPLAY "[" E5 "]"
MOVE 12 TO E6 DISPLAY "[" E6 "]"
MOVE 12 TO E7 DISPLAY "[" E7 "]"
MOVE 123 TO E1 DISPLAY "[" E1 "]"

```

## Expected result (per ISO)

Lines 1, 2, 3 and 7 shall be `[   12]`, `[   12]`, `[***12]` and `[***12]`.

- §13.18.40.5 7) (checked): "Zero suppression with replacement is indicated by specifying a string of one or more
  identical zero-suppression characters. Any of the simple insertion editing symbols embedded in this string or to the
  immediate right of this string are part of the string."
- §13.18.40.5 3) (checked): "Character-1 and the symbols 'B', '0', '/', ','" are the simple insertion editing symbols,
  so `0` and `/` are covered exactly as `B` and `,` are.
- §13.18.40.5 7) a) (checked): "the corresponding replacement character is placed into any character position
  immediately preceding whichever of the following is encountered first", the first being the first nonzero numeric
  character. In `ZZ0ZZ` with 12 the digit positions hold 0, 0, 1, 2 and the first nonzero is the fourth character
  position, so positions 1 to 3, the embedded `0` included, receive the replacement character.
- §13.18.40.5 7) (checked): "If the symbol 'Z' is used, the replacement character is the character space; if the
  symbol '*' is used, the replacement character is the character asterisk."
- §13.18.40.5 6) (checked) states the same membership rule for a floating insertion string, which 3.3-dev already
  applies (line 6); line 8 shows the insertion character is kept once a nonzero digit stands to its left.
- §13.18.40.4 15) (checked), the VALIDATE format check, states the same content for the edited item: a '0' position
  holds "the character zero if the symbol '0' is neither part of floating insertion editing nor of zero suppression
  with replacement editing; otherwise, the character zero or, if no significant numeric character appears to its left,
  the corresponding floating insertion character or replacement character respectively", and the '/' entry says the
  same of the slant.

wrong-output: a legal MOVE to a legal numeric-edited item stores the wrong characters, with no diagnostic. The editing
rules are unchanged since COBOL-85, so every `-std` is affected.

## Fix site

- 3.3-dev r5751: `libcob/move.c`, `optimized_move_display_to_edited`, the `case '0': case '/':` arm (about line 1228).
  It replaces the symbol only `if (suppress_zero && prev_float_char)`, so it handles a floating insertion string and
  falls through to `*dst = c` for a `Z` or `*` string. The `','` / `'.'` arm of the same loop writes `*dst = pad` when
  `suppress_zero` holds and there is no floating character, and the `'B'` arm writes `pad` or a space; the `'0'` / `'/'`
  arm lacks the corresponding branch. Inferred fix: write `pad` when `suppress_zero` holds, a `Z` or `*` has been met
  to the left, and no decimal point has been met (`!have_decimal_point`, the guard the `Z` and `*` arms already use).
  The condition must not be bare `suppress_zero`: a `0` or `/` left of every digit position (as in `PIC 0ZZ` or `/ZZ`)
  is plain simple insertion and is kept. It also needs the decimal-point guard: when every digit position is a `Z` or
  `*` and the value is not zero, §13.18.40.5 7) b) (checked: "If the value is not zero, the result is the same as if
  the zero suppression with replacement were defined only to the left of the decimal point position") keeps a `0` or
  `/` right of the point, and `suppress_zero` is still set there. `PIC ZZ.Z0Z` receiving .05 gives `  .005` on both
  versions today, which is correct; without the guard it would become `  .0 5`. That is the converse of PB4041 (a `,`
  left of the string wrongly replaced), whose drafted patch adds a `have_zero_suppression` flag to the same loop, so the
  two fixes fit together. The `','` arm has no decimal-point guard either, so it is not the model to copy as it stands:
  3.3-dev gives `  .0 5` for `PIC ZZ.Z,Z` receiving .05 where the standard gives `  .0,5` (a separate lead, not part
  of this record).
- 3.2.0 (`libcob/move.c`, `cob_move_display_to_edited`, about line 1033) has the same shape: `case '0': case '/':
  *dst = c;` with no suppression branch.
- Not built or tested; the site is read from the source and matches the observed output.

## Draft issue

**Title:** MOVE to numeric-edited: '0' or '/' inside a Z or * string is not replaced (PIC ZZ0ZZ with 12 gives "  012")

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1) and 3.3-dev r5751, x86_64 Linux.

Steps: `cobc -std=cobol2014 -fformat=free -x zsins.cob && ./zsins` (the default dialect gives the same) with the
attached `zsins.cob` (the program above).

Observed: `ZZ0ZZ` and `ZZ/ZZ` receiving 12 show `  012` and `  /12`; `**0**` and `**/**` show `**012` and `**/12`.
`ZZBZZ` and `ZZ,ZZ` show `   12` as expected, and so does `ZZ0ZZ` with 123 (` 1023`).

Expected: `   12`, `   12`, `***12`, `***12`. ISO/IEC 1989:2023 §13.18.40.5 editing rule 7 (unchanged from 2014):
"Any of the simple insertion editing symbols embedded in this string or to the immediate right of this string are
part of the string", and rule 3 names '0' and '/' among the simple insertion symbols. So the embedded '0' or '/'
takes the replacement character while every digit position to its left is suppressed, as 'B' and ',' already do.
3.3-dev applies the same rule to floating insertion (`$$0$$` gives `  $12`; 3.2.0 gave ` $012`).

Where: `libcob/move.c`, `optimized_move_display_to_edited`, `case '0': case '/':` replaces the symbol only when
`prev_float_char` is set. It needs a zero-suppression branch like the one in the ',' arm, limited to symbols right of the
first Z or * (so a leading `0ZZ` keeps its zero) and left of the decimal point (so `ZZ.Z0Z` receiving .05 keeps
`  .005`, as rule 7 b) requires for a nonzero value).
