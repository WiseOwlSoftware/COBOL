# PB251

**Rows:** `RV-15.4.1-2`, `RV-15.4.1-L2.2`

The intrinsic argument intake is five seams with different value semantics, and Landed truncates every SDIDI-carried argument at a 6-digit working-scale floor — invoking a §15.4.1 latitude that §15.67.4 r1 withdraws.

ROWS: RV-15.4.1-2 (§15.4.1 NOTE 1 item 2 — an EAE's result is implementor-defined if one or more ARGUMENTS are) and RV-15.4.1-L2.2 (the closing sentence: 'When a numeric or integer function does not have an equivalent arithmetic expression, its returned value is implementor-defined UNLESS OTHERWISE SPECIFIED IN THE FUNCTION DEFINITION').

FINDING 1 — THE SINGLE-SEAM PREMISE IS FALSE, AND THE FILE SAYS SO (RV-15.4.1-2). The adjudication rested on 'IntrinsicRenderer.Arg/RawArg/DecArg is the ONE argument intake for the numeric channel'. The same file carries at least five intakes with DIFFERENT value semantics: `Arg` (:450), `RawArg`/`DecArg`/`DecOf` (:511/:515/:522), `Dbl`/`DblOf` (:712/:525) for the binary64 lane, `IntArg → AsInt` (:716/:734) which RESCALES TO 0 WITH TRUNCATION for the integer positions, and `RawArgPairs` (:771) for the selection family — plus `Str`/`StrArgList` for the string channel. A rule about what happens to an argument cannot be verified from one of them.

FINDING 2 — Arg IS NOT A PASS-THROUGH. `Arg` is `Landed(num.AsNum(...))`, and `NumericRenderer.Landed` (:721-728) is `if (x.Real && StandardDecimal) x = new NumX(DecOperand(x), 0, Dec: true); if (!x.Dec) return x; int ws = rcv.WorkingScale(ReceiverContext.NumvalScaleFloor); return new NumX(RuntimeApi.DecToUnscaledIntermediate(x.Expr, ws.ToString(), CobolRounding.Truncation), ws);` — a TRUNCATION at a floor of 6 (ReceiverContext.cs:61). The note's load-bearing sentence — 'it renders an argument WITHOUT redefining its value' — is refuted at the exact line it cites.

FINDING 3 — THE FLOOR APPLIES THE LATITUDE THE FUNCTION DEFINITION WITHDRAWS (RV-15.4.1-L2.2's Correction 1). §15.4.1's closing sentence ends 'unless otherwise specified in the function definition', and §15.67.4 r1 is exactly such a specification, stated for EVERY mode with no arithmetic-mode qualification: 'The returned value is the numeric value represented by argument-1' (--check OK, specs/ISO_COBOL.md:32588). NUMVAL has no EAE, so the exception removes the implementor's latitude under NATIVE arithmetic too. Under native the compiler takes it anyway: `IntrinsicRenderer.cs:236-239` renders NUMVAL at `ws = num.Receiver.WorkingScale(ReceiverContext.NumvalScaleFloor)`, and docs/CONFORMANCE.md item 92 states the consequence in its own words — 'a genuinely receiver-less reference (DISPLAY of the bare call) renders at the 6-digit floor. Fraction digits beyond the working scale truncate — the §15.4.1 native-arithmetic latitude.' §15.67.3 r3 admits 31 digits under native, so `DISPLAY FUNCTION NUMVAL("0.1234567")` owes 0.1234567 and renders 0.123456. The cited golden pb60_numval_one_scan cannot see it: its CM/MV legs use a 9-fraction-digit receiver, so the floor never binds. This is the a_real_clause_can_answer_a_different_question shape — the §15.4.1 native sentence is real and is being used to license a truncation a different clause forbids.

WHAT WAS TRACED AND DID NOT MOVE THE VERDICT (RV-15.4.1-2's refuter): `FUNCTION INTEGER-PART(FUNCTION SECONDS-PAST-MIDNIGHT)` keeps the §15.80.3 r3 scale-7 tick carrier through Landed's identity arm for exact Int128, and `FUNCTION MAX` over a mixed RANDOM/fixed list routes to the PB65 SDIDI selection arm — so no over-definition of an implementor-defined argument was found, which is why both rows are PARTIAL and not DIVERGES.

RV-15.4.1-L2.2's OTHER half — SQRT under the same 'unless otherwise specified' exception, where §15.84.4 r2 fixes the value at 34 digits — is CLOSED at HEAD by PB116 (`alwaysDec` names "Sqrt"; `RenderDec:668 "Sqrt" when num.StandardDecimal => SqrtDec`; `CobolIntrinsics.Dec.cs:184-189 SqrtDec` carries the §15.84.3 r2 guard) and is carried in the stale-verdict note, not here.

FIX SHAPE: the NUMVAL working scale must come from the FUNCTION's own §15.67.3 r3 digit capacity, not from a receiver floor, in the receiver-less and text channels; and the five intakes need one documented contract each (what each preserves) plus a drift test that a new intake declares which one it is.

VERIFIED LIVE AT HEAD (read-only): `IntrinsicRenderer.cs:450`, `NumericRenderer.cs:721-728` and `ReceiverContext.cs:61` are unchanged.

## Landed — 2026-09-05

**The root cause was the CARRIER, not the floor.** §15.4.1's closing sentence is a CONDITIONAL — "When a numeric
or integer function does not have an equivalent arithmetic expression, its returned value is implementor-defined
unless otherwise specified in the function definition" (`--check` OK) — and §15.67.4 r1 / §15.68.4 r1 are exactly
such a specification, written once with no arithmetic-mode qualification (`--check` OK on both). So NUMVAL and
NUMVAL-C have no implementor latitude over their VALUE in ANY mode; §15.4.1 leaves the implementor only "the
characteristics and representation of the returned value" (`--check` OK). **No compile-time working scale can
serve that**: a scaled `Int128` temporary holds *i* + *ws* digits for an argument with *i* integer digits and
§15.67.3 r3 admits *i* = 31, so the only *ws* safe for every conforming argument is 7 — while
`NUMVAL("0.123456789")` needs 9. The representation that works is the SDIDI, whose exponent is carried at run
time; it was already the standard-mode representation (PB60) and is a documented native intermediate carrier
(PB69/PB273). `IntrinsicRenderer.RenderNum` now routes `Numval`/`NumvalC` to `RenderDec` **before** the
arithmetic-mode dispatch, and the native working-scale `case "Numval"` / `case "NumvalC"` arms are gone.

**Measured on this worktree's own `cobol.exe`, before → after:**

| probe | before | after | owed by |
|---|---|---|---|
| `DISPLAY FUNCTION NUMVAL("0.1234567")` | `0.123456` | `0.1234567` | §15.67.4 r1 |
| `DISPLAY FUNCTION NUMVAL("0.123456789")` | `0.123456` | `0.123456789` | §15.67.4 r1 |
| `DISPLAY FUNCTION NUMVAL-C("$0.1234567", "$")` | `0.123456` | `0.1234567` | §15.68.4 r1 |
| `COMPUTE R PIC 9(9) = FUNCTION NUMVAL("0.1234567") * 10000000` | `001234560` | `001234567` | §15.67.4 r1 |
| `COMPUTE S PIC 9(9) = FUNCTION NUMVAL(A) * 1000000000`, A = `"0.123456789"` | `123456000` | `123456789` | §15.67.4 r1 |

**A receiver was never the protection the item-92 determination assumed.** It bounds the STATEMENT's result, not
an OPERAND's precision — which is why the two COMPUTE rows above were wrong answers with a perfectly ordinary
`PIC 9(9)` receiver, and why the finding is much wider than the receiver-less DISPLAY the note's FIX SHAPE named.

**FINDING 2 (`Arg` is not a pass-through) is answered structurally, not by moving the floor.**
`ReceiverContext.NumvalScaleFloor` is renamed `SdidiLandingScaleFloor`: it was never a §15.67 rule — the family
has no working scale — and the name alone kept a truncating native lane looking spec-derived. Its ONE consumer is
`NumericRenderer.Landed`, where it is an implementor choice for a value-semantics landing with no receiver scale.

**FINDING 1 (the five-seam premise) is answered by making every seam declare itself.** `IntrinsicRenderer`'s
"Argument rendering" banner now defines the vocabulary — EXACT · LIFTED · ALIGNED · LANDED · INTEGRAL ·
APPROXIMATED · PREDICATE, each defined by what the intake does to the argument's VALUE — and all 18 intakes carry
an `INTAKE(<class>)` remark. `IntrinsicArgumentIntakeContractDriftTests` reads the renderer source, finds every
member that calls `num.AsNum(` (comments stripped — the banner itself spells that token), and fails if one
declares nothing, so a SIXTH seam is a red test rather than a hole in a hand-kept list. It also pins that `Arg`
is the ONLY LANDED intake and that the NUMVAL family has no compile-time working scale left. The guard was
**proved red once** by removing `RawArg`'s marker.

**Duplication swept in the same change set.** With the native arms gone, `CobolIntrinsics.Numval`, `.NumvalC` and
`.NumvalCLocale` (the Int128 value projections) were unreachable from generated code — measured, not assumed:
`grep '"Numval"|"NumvalC"|"NumvalCLocale"' src/Cobol.Net.Compiler` shows only catalog rows and the emitter's
`NumvalDec`/`NumvalCDec`/`NumvalCLocaleDec` calls. All three are deleted; their unit assertions were re-pointed at
the surviving SDIDI twins, and the inventory's `#Numval` / `#NumvalC` code-locations at the same. Leaving a second
unreachable projection of one rule is precisely the shape that produced this defect: PB60 fixed the standard-mode
projection of the NUMVAL family and left the native one wrong for a year.

**One latent trap closed while re-pointing.** The four SDIDI bodies defaulted `digitCap` to 34 while every Int128
body and every TEST- validator defaulted to 31, harmless only while the Dec bodies were standard-mode-only. Routing
native NUMVAL through them would have silently admitted a 34-digit argument under §15.67.3 r3's 31-digit cap. All
four now default to 31 = `ArithmeticModes.DefaultDigitCap`, so the family has ONE convention: the omitted cap is
the NATIVE cap and the emitter names the cap exactly when the mode's differs. `pb33_numval_family_digit_cap`'s
`NUMVAL-34=` leg is the regression net that proves it — it would have returned the value instead of the §15.3 r14
default 0.

**Goldens.** `tests/conformance/2023/pb251_numval_native_value_fixed.cob` (PB251NVNAT) is the NATIVE twin of
`pb60_numval_standard_decimal`: fifteen of its lines are byte-identical to the standard-decimal golden's for the
same references — the row's rule stated as a test — plus I31/D31 (31 digits at either end of the decimal
separator, the two ends no single working scale can serve at once), C32 (the r3 cap → §15.3 r14's default 0) and
RAWF (NUMVAL-F's §15.69.4 r2 approximation, the contrast that must NOT move).
`tests/conformance/2023/pb251_implementor_defined_argument.cob` (PB251IDARG) is RV-15.4.1-2's owed runtime
evidence: RANDOM and SECONDS-PAST-MIDNIGHT in argument positions, with deterministic consequences of each
argument's own domain rule.

**Rows re-verdicted** in the same change set: RV-15.4.1-2 PARTIAL → CONFORMS and RV-15.4.1-L2.2 PARTIAL →
CONFORMS (batch `pb251-numval-value-fixed-by-definition`; GAP 2906 → 2904). `docs/CONFORMANCE.md` item 92 and
`docs/COBOLNET_NUMERIC_DESIGN.md` are current with the new determination. No diagnostic code was needed
(COBOLNET1768 / COBOLNET1769 remain free).

**What the note said that did NOT hold on today's tree:** its line numbers had all drifted (`IntrinsicRenderer.cs:450`
was 458, `NumericRenderer.cs:721-728` was 850-857, `ReceiverContext.cs:61` was right), and its FIX SHAPE scoped the
harm to "the receiver-less and text channels" — the COMPUTE probes above show a fixed-point receiver is no
protection, so the fix had to be the carrier for every channel rather than a receiver-shape branch.
