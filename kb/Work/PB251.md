# PB251

**Rows:** `RV-15.4.1-2`, `RV-15.4.1-L2.2`

The intrinsic argument intake is five seams with different value semantics, and Landed truncates every SDIDI-carried argument at a 6-digit working-scale floor — invoking a §15.4.1 latitude that §15.67.4 r1 withdraws.

ROWS: RV-15.4.1-2 (§15.4.1 NOTE 1 item 2 — an EAE's result is implementor-defined if one or more ARGUMENTS are) and RV-15.4.1-L2.2 (the closing sentence: 'When a numeric or integer function does not have an equivalent arithmetic expression, its returned value is implementor-defined UNLESS OTHERWISE SPECIFIED IN THE FUNCTION DEFINITION').

FINDING 1 — THE SINGLE-SEAM PREMISE IS FALSE, AND THE FILE SAYS SO (RV-15.4.1-2). The adjudication rested on 'IntrinsicRenderer.Arg/RawArg/DecArg is the ONE argument intake for the numeric channel'. The same file carries at least five intakes with DIFFERENT value semantics: `Arg` (:450), `RawArg`/`DecArg`/`DecOf` (:511/:515/:522), `Dbl`/`DblOf` (:712/:525) for the binary64 lane, `IntArg → AsInt` (:716/:734) which RESCALES TO 0 WITH TRUNCATION for the integer positions, and `RawArgPairs` (:771) for the selection family — plus `Str`/`StrArgList` for the string channel. A rule about what happens to an argument cannot be verified from one of them.

FINDING 2 — Arg IS NOT A PASS-THROUGH. `Arg` is `Landed(num.AsNum(...))`, and `NumericRenderer.Landed` (:721-728) is `if (x.Real && StandardDecimal) x = new NumX(DecOperand(x), 0, Dec: true); if (!x.Dec) return x; int ws = rcv.WorkingScale(ReceiverContext.NumvalScaleFloor); return new NumX(RuntimeApi.DecToUnscaledIntermediate(x.Expr, ws.ToString(), CobolRounding.Truncation), ws);` — a TRUNCATION at a floor of 6 (ReceiverContext.cs:61). The note's load-bearing sentence — 'it renders an argument WITHOUT redefining its value' — is refuted at the exact line it cites.

FINDING 3 — THE FLOOR APPLIES THE LATITUDE THE FUNCTION DEFINITION WITHDRAWS (RV-15.4.1-L2.2's Correction 1). §15.4.1's closing sentence ends 'unless otherwise specified in the function definition', and §15.67.4 r1 is exactly such a specification, stated for EVERY mode with no arithmetic-mode qualification: 'The returned value is the numeric value represented by argument-1' (--check OK, specs/ISO_COBOL.md:32588). NUMVAL has no EAE, so the exception removes the implementor's latitude under NATIVE arithmetic too. Under native the compiler takes it anyway: `IntrinsicRenderer.cs:236-239` renders NUMVAL at `ws = num.Receiver.WorkingScale(ReceiverContext.NumvalScaleFloor)`, and docs/CONFORMANCE.md item 92 states the consequence in its own words — 'a genuinely receiver-less reference (DISPLAY of the bare call) renders at the 6-digit floor. Fraction digits beyond the working scale truncate — the §15.4.1 native-arithmetic latitude.' §15.67.3 r3 admits 31 digits under native, so `DISPLAY FUNCTION NUMVAL("0.1234567")` owes 0.1234567 and renders 0.123456. The cited golden pb60_numval_one_scan cannot see it: its CM/MV legs use a 9-fraction-digit receiver, so the floor never binds. This is the a_real_clause_can_answer_a_different_question shape — the §15.4.1 native sentence is real and is being used to license a truncation a different clause forbids.

WHAT WAS TRACED AND DID NOT MOVE THE VERDICT (RV-15.4.1-2's refuter): `FUNCTION INTEGER-PART(FUNCTION SECONDS-PAST-MIDNIGHT)` keeps the §15.80.3 r3 scale-7 tick carrier through Landed's identity arm for exact Int128, and `FUNCTION MAX` over a mixed RANDOM/fixed list routes to the PB65 SDIDI selection arm — so no over-definition of an implementor-defined argument was found, which is why both rows are PARTIAL and not DIVERGES.

RV-15.4.1-L2.2's OTHER half — SQRT under the same 'unless otherwise specified' exception, where §15.84.4 r2 fixes the value at 34 digits — is CLOSED at HEAD by PB116 (`alwaysDec` names "Sqrt"; `RenderDec:668 "Sqrt" when num.StandardDecimal => SqrtDec`; `CobolIntrinsics.Dec.cs:184-189 SqrtDec` carries the §15.84.3 r2 guard) and is carried in the stale-verdict note, not here.

FIX SHAPE: the NUMVAL working scale must come from the FUNCTION's own §15.67.3 r3 digit capacity, not from a receiver floor, in the receiver-less and text channels; and the five intakes need one documented contract each (what each preserves) plus a drift test that a new intake declares which one it is.

VERIFIED LIVE AT HEAD (read-only): `IntrinsicRenderer.cs:450`, `NumericRenderer.cs:721-728` and `ReceiverContext.cs:61` are unchanged.

## Mechanism
