# PB2142 — the permission classifier and whole-tree deletions

## What happened (wave 1025, 2026-10-07 ~01:40 PDT)

Group B's Opus implementer (PB2110, Cut 2) merged group A cleanly and then ran
`git rm -r -q src/CobolSharp.Compiler src/CobolSharp.Runtime src/CobolSharp.CLI tests/CobolSharp.Tests.Unit
tests/CobolSharp.Tests.Integration` in its worktree. The Claude Code auto-mode permission classifier refused it as
"Irreversible Local Destruction", then refused a read-only follow-up on the same task. The agent STOPPED instead of
routing around the block (MANDATORY-PRACTICES P12) and returned BLOCKED with every remaining code site measured
(`E:\COBOL-coord\scratch\reports\w1025b-PB2110-report.md`). The lander landed A alone (train 1025, `86f33fd7d`).

The attended session then performed the `git rm -r` itself on branch `pb2110-cut2` (commit `36441a24c`, 231 files,
74,493 deletions, plus the five solution entries) and dispatched a finisher (wave 1027) that merges that branch. The
deletion is reversible in practice: every file is in history and the archive tag `legacy-byte-engine-final` is created on
main's last pre-delete commit after the finisher's train lands.

## Why it matters beyond this one cut

R69 §3 mandates dead and obsolete code removal (the Delete program PB2119), and PB2112 and the R3 move-and-rename waves
also remove or move whole trees. Each will meet the same classifier. Today the only working shape is the one used here:
the attended session performs the destructive git step on a branch and a subagent finishes from it. That costs an
attended turn per deletion and makes the orchestrator loop unable to run a Delete wave unattended.

## Owner decision

1. **A scoped permission rule** in the owner's `.claude/settings.local.json` (never staged) allowing `git rm -r` for paths
   under `.claude/worktrees/` — a worktree branch, where every removal is a commit away from recovery; or
2. **The attended-session step stays the rule**: the Delete wave's brief gains a named orchestrator step ("the orchestrator
   removes the tree on a branch; the implementer finishes"), written into `.claude/skills/architecture-review` and the
   public `architecture-audit` skill's Delete wave text, and the orchestrator loop never runs a Delete wave unattended.

Until decided, option 2 is what happens (it is what wave 1027 does).

## Decided 2026-10-07 (owner): option 1, implemented as a scoped permission hook

"A scoped permission rule allows git rm -r under .claude/worktrees/." A `permissions.allow` entry sees only the command text and
never the working directory, so the scoped form is `scripts/hooks/worktree_rm_allow.py`, a PreToolUse hook on Bash and PowerShell
that returns `permissionDecision: allow` (honoured ahead of the auto-mode classifier) only for ONE `git [-C <dir>] rm -r …` command
(an optional `cd <dir> &&` prefix, nothing chained after), run in a directory under `<repo>/.claude/worktrees/`, with every path
inside that worktree and no `-f`/`--force`. Everything else returns no decision, so the normal flow is unchanged; a deny from
`forbidden_commands.py` still wins. Self-test `scripts/hooks/test_worktree_rm_allow.py` (24 cases, both branches) runs in CI's
audits job beside the other hook tests. Owner, minutes later: "Work trees should only be removed after we have committed all
their work as appropriate" and "I do not want to accidentally lose useful work" — recorded in MANDATORY-PRACTICES O10 and P12:
without `-f`, git refuses to remove a file whose content is not committed, so the grant keeps every removal one commit from
recovery; worktrees are pruned only when MERGED or LANDED, never dirty, locked, recent or UNLANDED.
