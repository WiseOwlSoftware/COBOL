# PB1546 — OPEN

## Repro

`python scripts/spec/work.py --help | head` and `python scripts/spec/gen_ledger.py --help | head` →
`UnicodeEncodeError: 'charmap' codec can't encode character '⛔'` from `encodings/cp1252.py`, raised inside
`argparse … print_help`. Unpiped (a real console) or with `PYTHONIOENCODING=utf-8` both work.

## Mechanism

When stdout is not a console, Python on Windows encodes with the locale code page (cp1252); the help text (the module
docstring) carries ⛔, →, — and friends. Several scripts already call `sys.stdout.reconfigure(encoding="utf-8")`
(`audit_annex_a1.py`, `audit_catalog_coverage.py`, `audit_code_citations.py`, `audit_derivations.py`,
`audit_doc_citations.py`, …) — the fix exists, copied per script, and 40 `ArgumentParser` scripts are not all covered.

## Fix shape (rule 4/5: one mechanism, not 40 copies)

One shared helper (e.g. `scripts/spec/_console.py::utf8_stdio()`) called by every entry point — or
`PYTHONUTF8=1` set once for the repo's tooling — plus a drift test that runs `--help` of every `scripts/spec/*.py`
with a piped stdout under a non-UTF-8 locale and fails on any exception.

## 2026-10-16 — MERGED: PB2615 and PB2915 are this mechanism (retired into this note)

PB1546, PB2615 and PB2915 are one mechanism: a script's argparse help carries non-ASCII text (⛔, ⭐, →) and `--help`
crashes with `UnicodeEncodeError` on a cp1252 stdout (a pipe on Windows), because the script reconfigures stdout to
UTF-8 only AFTER `parse_args()` (which prints the help and exits) or never. PB2615 and PB2915 are `status: retired`;
their evidence is folded in here.

**Verified 2026-10-16 on origin/main 0c53cc440** (`PYTHONIOENCODING= PYTHONUTF8=0 python <s> --help 2>&1 | tail -1`):
- `scripts/spec/work.py` CRASHES (`'⛔'`): `parse_args()` at line 1132, `sys.stdout.reconfigure` at 1134.
- `scripts/filter_population.py` CRASHES (`'⛔'`): `parse_args()` at 312, reconfigure at 314.
- `scripts/spec/gen_ledger.py` does NOT crash any more (it reconfigures at 1380, before `parse_args()` at 1394).
- 107 scripts under `scripts/` call `reconfigure`; 11 argparse scripts never do.

**From PB2615** (filed by the train 1039b lander from `w1039x-PB2611-report.md`): `PYTHONIOENCODING=cp1252 python
scripts/filter_population.py --help` exits 1 on '⛔'. PB2611 fixed `scripts/spec/record_impact_map.py` alone
(`stream.reconfigure(encoding="utf-8")`, line 228); the siblings were not swept. Its scan found
`scripts/collation/generate-collation-table.py`, `scripts/collation/pack-cldr-collation.py`,
`scripts/unicode/generate-grapheme-table.py` (and `train_measure.py`, since replaced by `landing_measure.py`, which
reconfigures both streams before it parses); `filter_population.py` builds its help another way, so a text scan
under-counts: the sweep must RUN every script's `--help` under cp1252. Re-measured 2026-10-11 (PB3028's review
finisher, wave 1064 C2): `gen_ledger.py` and `ledger_plan.py` were fixed by moving the reconfigure before the parser;
a sweep still found 31 argparse scripts failing `--help` with stdout to a pipe, among them `filter_population.py`,
`gate_plan.py`, `work.py`, `impacted_tests.py` and nine `scripts/spec/audit_*.py` and repair scripts.

**From PB2915** (found 2026-10-10 by the operator with `work.py --help` and `gen_ledger.py -h` piped into `head`, and by
the w1051z implementer with `filter_population.py --help`, code site `scripts/filter_population.py:312`): the cause is
the console encoding (cp1252 when stdout is a pipe), not the help text; the module docstrings used as
`description=__doc__` carry ⛔ and ⭐. Sweep of 2026-10-10 (branch w1051v-pb2914): 10 argparse scripts under `scripts/`
and `.claude/skills/` with non-ASCII text never call `sys.stdout.reconfigure`. A census on 2026-10-10 (main 316a9d731)
found about 25 hand-copied `reconfigure` calls, each written differently (stdout only, stderr only, with or without
`errors="replace"`, at import time or inside `main`), plus `PYTHONIOENCODING`/`PYTHONUTF8` set by three test
harnesses (`tests/_shared/PythonInstrument.cs`, `scripts/self_tests.py`, `scripts/arch/test_wf_r2_review.mjs`).
**Owner direction (2026-10-10 18:12 PDT):** "this would work if the compiler startup (plus likely test cases) set the
console output encoding to UTF-8": the encoding is set at STARTUP, in the program, and by the test cases that launch
it; the environment variable alone does not do it. The compiler already does this in
`src/Cobol.Net.Runtime/IO/StandardStreams.cs#EnsureUtf8` (kb/Work PB899), called first by `cobol`
(`src/Cobol.Net.Cli/Program.cs#Main`) and by every RUN program (`ProgramTable.RunMain`).

### Fix shape (merged; rule 5, one place)

ONE shared Python helper, the scripts' counterpart of `EnsureUtf8` (stdout and stderr, once per process, safe on a
host with no console), called as the FIRST statement of every script entry point, before `parse_args()` (or before the
parser is built, where the parser prints at construction). Every hand-copied `reconfigure` call is replaced by it in
the same change (CLAUDE.md rule 4: no second mechanism stays behind). The test harnesses that launch scripts keep
setting UTF-8 for the child, as the owner's "plus likely test cases" asks. A drift test finds every argparse script
that reconfigures after `parse_args()` or not at all (an AST scan), AND runs `--help` of each under a cp1252 stdout
requiring exit 0 (the scan alone under-counts, as PB2615 found).
