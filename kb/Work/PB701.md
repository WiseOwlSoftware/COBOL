# PB701 — LANDED (w1045d, with PB2693) — one file order for many key orders

Found 2026-09-05 by the `PB341`/`PB342` implementer (report §"New defects" 1), probed with
`<a9d94900 scratch>\PB341\probe\pb341c.cob`: release `01/AA/PP` and `02/BB/PP`; REWRITE 01's first alternate to
`BB`. In memory the first alternate's walk is `02,01` (§14.9.35.4 GR24 b) and the second's is `01,02` (GR24 a) —
both correct; after CLOSE and OPEN INPUT the first alternate's walk is `01,02` — the repositioning is gone, no
record lost, no exception, a deterministic result. `blocked: true` (until w1045d) because the remedy is an on-disk format
choice; `blocked_by` is empty because the blocker is the owner, not a note.

## The rule

§14.9.30.4 GR26 (`cite.py --check` → OK 26)): "records having the same duplicate value in an alternate record key
that is the key of reference are made available in the same order, or, in the case of PREVIOUS, in the reverse
order, in which they are released by execution of WRITE statements, or by execution of REWRITE statements that
create such duplicate values"; §14.9.35.4 GR24 a) (→ OK 24))
freezes an untouched key's order across a REWRITE. Those orders are properties of the physical file's index for
EACH key, and the standard gives no licence to lose one across a CLOSE/OPEN.

## The mechanism

`src/Cobol.Net.Runtime/IO/IndexedConnector.cs#PersistOrder` derives one physical sequence from the per-key orders
(one edge per adjacent pair of a duplicate set, Kahn's algorithm, prime ordinal as the tie-break); a reload can only
give every key the file's own order. Acyclic constraint graphs — every pure-WRITE file and most single-REWRITE
histories — round-trip exactly; the cyclic residue does not. `RecordFraming.cs#WriteStore`/`#ReadStore` frame a
bare sequence of images with no per-record metadata slot. Since [[PB802]] the store DOES open with a header, but that
header is the §9.1.6 FIXED file attributes and is the wrong home for this: the per-key release ordinals change on
every REWRITE, and a fixed file attribute does not.

## ⛔ Bare question for the owner

Should the indexed store's on-disk format carry the per-key release ordinals (a per-record metadata slot in the
framing, or a companion index file), so that every per-key duplicate order survives CLOSE/OPEN — a format change
for every existing indexed data file, with a migration — or does the acyclic-only guarantee stand as a documented
determination (an A.1-style statement of the physical-file limitation)? Survey what the sidecar-keeping and
index-file-keeping implementations do before deciding; GnuCOBOL's indexed backend keeps a real index structure.

## Landed 2026-10-08 (w1045d, with kb/Work PB2693)
The per-key release ordinals are now ON DISK: store format 4 frames each indexed record with its ordinal vector and
the header carries the release mint (`RecordFraming`), and `PersistOrder` is deleted, so every per-key duplicate order
survives CLOSE/OPEN, the cyclic case included
(`unit:CrossRunUnitKeyedStoreDriftTests.EachKeysDuplicateOrder_SurvivesTheClose_WhenNoSingleRecordOrderCarriesThem`).
⚠ The question above is settled by the spec and by a standing owner rule, so it needed no owner decision (checked
again by the train 1045 lander). The format half: §14.9.30.4 GR26 requires every alternate key's duplicates to be
made available in the order of their release by WRITE or by a REWRITE that creates the duplicate value, and it
makes no exception for a CLOSE and OPEN between the release and the read. The second option (an acyclic-only
guarantee as a documented determination) would therefore return a wrong answer in the cyclic case. It is not an
implementation latitude, and the per-key ordinals have to be on disk (option 1, a per-record slot in the framing).
The migration half: CLAUDE.md rule 4 (owner, 2026-09-28) sets no backward-compatibility requirement, so there is no
migration, and a format-3 store opens as Foreign with file status '39' (`docs/rearchitecture/DESIGN-runtime-library.md`).
