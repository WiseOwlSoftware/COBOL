# PB1321 — OPEN — the re-code does not consume the error

## Measured (`srchc.cob`, `--std 2023`)
```cobol
           SEARCH E
             AT END DISPLAY "END"
             NOT AT END DISPLAY "NOT-END"
             WHEN E (IX) = "A" DISPLAY "A"
           END-SEARCH.
```
```
srchc.cob(10,14): error COBOLNET2269: unexpected 'NOT'. SEARCH … NOT AT END: ISO §14.9.37.2 prints two SEARCH
  formats and each has an AT END phrase alone — there is no NOT AT END phrase. …
srchc.cob(10,25): error COBOL0001: unexpected 'DISPLAY'
```

## Mechanism
The re-code (PB446, and PB396/PB412 before it) rewrites the FIRST syntax error's code and text from parser state
in the error strategy. After the re-coded report, ANTLR's recovery still has to resync. It deletes `NOT AT END`,
lands on `DISPLAY` with a state that does not expect it, and reports again. The first error was "handled" only
in its message, not in recovery. `src/Cobol.Net.Frontend/Parsing/CobolErrorStrategy.cs` is the site. The same
sequence follows every re-code that recognizes a whole misplaced PHRASE: GO TO's shapes (PB412), the IF/EVALUATE
statement-block re-codes (PB396) and the PB510 spelling re-code (COBOLNET2418).

## What the fixer owes
- When a re-code recognizes a phrase, recovery consumes the whole phrase, up to the next token the enclosing rule
  can accept (here `WHEN`). Two ways to do it: single-token deletion extended to the phrase, or a recovery set the
  re-code supplies.
- One mechanism in the error strategy, used by every re-code, not per-verb patches.
- A negative golden per re-coded family asserting the EXACT diagnostic set, so the cascade cannot come back.
- Coordinate with PB906 (COBOL0307 winning over a precise diagnostic) and PB657 (a bare COBOL0001 at a reference
  position). All three are the parse layer's "which diagnostic survives" question.
