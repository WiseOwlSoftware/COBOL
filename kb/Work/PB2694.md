**Wave kind:** defect-for-fix-lane. Found by the wave-1042 group H implementer (PB2638) and filed by the train 1042b lander.

**Sites:**
- `src/Cobol.Net.Compiler/CodeGen/Verbs/ArithmeticEmitter.cs:61` (ArithmeticEmitter.EmitGiving, the shared multi-receiver `ReceiverContext`)
- `src/Cobol.Net.Compiler/CodeGen/Verbs/ArithmeticEmitter.cs:83`, `:102`, `:230` (the other multi-target `new ReceiverContext(targets.Max(t => ScaleOf(t.Place)), …)` sites)
- `src/Cobol.Net.Compiler/CodeGen/Verbs/ArithmeticEmitter.cs:314` (RcvFor, the single-receiver path that DOES carry FloatEdited through `ReceiverContext.Of`)

**Rule it breaks:** §14.7.4.3 (the arithmetic store into each resultant identifier rounds or truncates the arithmetic value as that receiver's mode says) and §14.6.8.4 rule 1 (a nonzero value stored into a floating-point edited item is normalized). The quotient must carry the digits the FLOAT-EDITED receiver needs, which the scale hint of the widest fixed-point receiver plus 14 guard digits does not.

**Scenario (from the implementer's report, not re-measured by the lander):** `01 FE PIC +9.99E+99. 01 X PIC 9V99. 01 HUGE PIC 9(25) VALUE 3E24.` then `COMPUTE FE ROUNDED, X = 1 / HUGE` stores FE = +0.00E+00 where +3.33E-25 is owed. With FE as the ONLY receiver PB2638's fix gives +3.33E-25 (golden `tests/conformance/2023/pb2638_float_edited_rounded_store`, case 15). Cause: the multi-receiver sites build one `ReceiverContext` from `targets.Max(ScaleOf)` without the FloatEdited flag, so `NumericRenderer.Divide` takes the scale-hint arm, not the SDIDI round-to-odd arm PB2638 added for a float-edited outermost quotient.

**Fix direction:** the shared context must carry "some receiver is float-edited" (or each receiver its own context, as `RcvFor` does); shares its root with PB2638's Divide fix. Sweep every `new ReceiverContext(` in ArithmeticEmitter for the same omission.

**Landed (wave 1052 group D):** re-probed on a fresh build: `COMPUTE FE ROUNDED, X = 1 / HUGE` stored +0.00E+00 (and so did the NESTED shape `1 / HUGE + 0`, with FE the only receiver too). ROOT CAUSE is wider than the float-edited receiver: a multi-receiver `COMPUTE` rendered a root QUOTIENT once for the receiver set at the widest scale plus 14 guard digits (truncated), so EVERY receiver stored from a cut quotient -- `COMPUTE X ROUNDED MODE IS NEAREST-EVEN = 0.125000..0125` stored .12 (.13 owed: the cut quotient read as an exact tie) and a PROHIBITED tail past the guard digits passed as exact. FIX: (1) a product OR quotient at the root of a multi-receiver COMPUTE renders PER RECEIVER (`ArithmeticEmitter.EmitCompute`, as `MULTIPLY/DIVIDE GIVING` always did) from once-evaluated operands; (2) `ReceiverContext.OfSet` is the one rule for the receiver-SET context (five hand-written copies in ArithmeticEmitter deleted), carrying `FloatEdited` when any receiver is; (3) `NumericRenderer.Divide` forms a NESTED quotient on the SDIDI by round-to-odd whenever the context is `FloatEdited` (it was the outermost quotient only). Golden `2023/pb2694_multi_receiver_root_quotient` (7 cases, spec-derived). Sibling sweep: EmitInPlace/EmitMultiplyGiving/EmitDivide already rendered finals per receiver; EmitGiving values are sums (no quotient); ReportWriterEmitter SUM counters are Int128 registers, never float-edited. LEAD, not fixed: `DIVIDE 1 BY HUGE GIVING FE REMAINDER R` -- 14.9.12.4 GR6c defines the subsidiary quotient by "the same number of digits and the same decimal point location as" identifier-3, which a floating-point edited item does not have; the emitter uses the mask hint scale (quotient +0.00E+00, remainder 1.00): needs an adjudication of what the subsidiary quotient is for such a receiver.
