# PB5542 - GENERATE and USE BEFORE REPORTING continue with the first candidate of an Ambiguous report-group match instead of stopping at the refusal

**Sites:**

- `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ReportWriterBinder.cs#BindGenerate` (the `ReportGroupResolution.Resolve(...) != Match.None` test)
- `src/WiseOwl.Cobol.Compiler/Binding/Procedure/ProcedureTableBuilder.cs#DeclBindUse` (the USE BEFORE REPORTING arm: `match == ReportGroupResolution.Match.None || group is null`)
- `src/WiseOwl.Cobol.Compiler/Binding/ReportGroupResolution.cs#Resolve` (returns `Match.Ambiguous` after `ReportGroupReferenceAmbiguous`)

**Mechanism.** `ReportGroupResolution.Resolve` reports the ambiguity (`ReportGroupReferenceAmbiguous`) and returns `Match.Ambiguous` with the first candidate in `report`/`group`. Both callers test only `Match.None`, so an `Ambiguous` result is treated like `Found`: GENERATE goes on to check the kind and bind a `BoundGenerate` on the first candidate, and USE BEFORE REPORTING goes on to its SR9 duplicate check and records the first candidate. Any later diagnostic or table entry is then built on a group the program did not name uniquely, so a second, cascading diagnostic can follow the one real refusal. kb/Work PB5524 fixed the same shape in `ReportSectionBinder.ResolveUponDetail` (return at `Match.Ambiguous`) and its test pins one COBOL code only; these two callers are its siblings, left by that change because they sit in files it did not touch (its report, LEAD 1).

**Expected.** At `Match.Ambiguous` the binder stops with the one refusal already issued (§2023:8.4.2.2.3 SR1 as the diagnostic's own text cites), exactly as PB5524 does; a test per caller asserts one error code and no cascade.

**Fix direction.** Make the Ambiguous verdict a stop at each caller, preferably by giving `Resolve`'s consumers one shape (a refusal result that carries no group) so the next caller cannot continue on a first candidate by omission. Sweep every other `ReportGroupResolution.Resolve` caller for the same test.
