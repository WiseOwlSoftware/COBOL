# PB280 — the three owner questions the A.1 DOC-row shape left open

> ⚙ **Raised by the landing of the Annex A.1 DOC-row closing shape (2026-09-02).** The mechanism landed with its
> OBSERVABLE arm only, and each question below is a place where answering it myself would have moved the owner's
> burn-down on the owner's own definition. Every one is stated as a bare question with its options and the
> consequence of each, so it can be answered in one word.

## Q1 — does a "Not provided." determination on an A.1-**optional** item close as CONFORMS, or as DOCUMENTED-NON-SUPPORT?

**Options:** `CONFORMS` · `DOCUMENTED-NON-SUPPORT`.

**Consequence.** One answer settles **~30 items** (A.1 has 30 optional elements) and becomes a
`derived-verdicts` selector in `inventory-schema.json` rather than thirty adjudications — the PB198 mechanism.
`CONFORMS` closes them as ordinary rows; `DOCUMENTED-NON-SUPPORT` makes each an owner decision requiring `notes`,
which is a slower path but the one the schema already reserves for a declined element.

**The evidence on both sides, measured rather than argued.** Exactly two §7 rows literally open with
"**Not provided.**", and they are exactly the two A.1-`optional` items in the back-fill: **item 127**
(OBJECT-COMPUTER computer-name and implied equipment configuration — "there is ONE object computer, the .NET
runtime") and **item 206** (USAGE BINARY-CHAR/-SHORT/-LONG/-DOUBLE wider range than the GR12 minimum — "each usage
holds exactly the GR12 minimum range"). For CONFORMS: both are *positive, observable answers* to A.1's question,
not declines of a facility, and routing them to an owner-only verdict makes that verdict an agent's default escape
hatch. For DOCUMENTED-NON-SUPPORT: A.1's preamble says "— Optional: The element may be provided at the
implementor's option" and "— Documentation required: **If the element is provided by the implementor**, the
implementor's user documentation shall document the element…", so for a not-provided optional element the
documentation duty does not arise at all; and `inventory-schema.json`'s own `DOCUMENTED-NON-SUPPORT.meaning`
already names "4.2.7 for an OPTIONAL element" as one of its three grounds and states the verdict is
"An OWNER decision (never an agent's)".

**Held pending the answer:** `DOC-A.1-127` and `DOC-A.1-206` were **dropped from the back-fill** and remain
verdict-less GAPs. Both §7 determinations stay exactly as written — the register is not waiting on this, only the
two inventory rows are. Neither carried a covering test, so no burn-down movement is being withheld: answering
`CONFORMS` re-records them as two more CONFORMS-but-untested rows.

## Q2 — may a DOC row whose only location is its §7 anchor — nothing in the compiler to observe — close on the register gate alone?

**Options:** `yes, close it` · `no, it stays a GAP` (what landed).

**Consequence.** This is **a widening of the definition of DONE**, and that is why the arm is not landed.
`DESIGN-spec-conformance-review.md` §1(a) requires "a located implementation (a traceability link into
`src/Cobol.Net.*`), OR a recorded **owner documented-non-support decision** (optional modules only, per §4.2.16)".
A register-only row has neither: its one `code-location` is `docs/CONFORMANCE.md#DOC-A.1-<n>`, and its verdict is
CONFORMS, not DOCUMENTED-NON-SUPPORT. Answering `yes` means amending §1(a) with a third arm naming the register
determination explicitly — the owner's completion metric, redefined — and the amendment lands in the same change
set as the arm.

**Why it is not landed, measured.** All 37 back-fill rows carry a greenfield `src/Cobol.Net.*` site, so the arm
would have had **zero instances**: speculative generality that relaxes a gate before a case for it exists. And its
own negative claim ("there is nothing in the compiler to observe") is cross-checkable for only **13 of 222** items
— greenfield source cites exactly thirteen distinct A.1 items in `implementor item N` comments, a convention no
gate enforces — so for the other 209 the claim would be contradicted by nothing *and confirmed by nothing*. A
MISSING observation standing in for a NEGATIVE one is precisely what `feedback_verdict_evidence_invariant`
forbids.

**Today's behaviour, so the cost of `no` is visible:** such a row stays a GAP forever, whatever its test-ref.
When a real item needs the arm, the honest shapes are (a) amend §1(a) as above, or (b) require the §7 row to name,
in a machine-readable cell, the *reason* nothing is observable — the unclaimed A.4 module row in §5, or the
§4.2.3 interaction the owner recorded as unclaimed — and have the gate RESOLVE that reference, which is the
discipline `DOCUMENTED-NON-SUPPORT.requires: ["notes"]` already imposes.

## Q3 — is this repository's `docs/CONFORMANCE.md` the §4.2.16 user documentation, and may a row discharge its obligation BY REFERENCE?

Two halves of one question about what the register IS. §4.2.16: "An implementation shall satisfy the user
documentation requirements specified in 4.2.3, 4.2.4, 4.2.5, 4.2.6, 4.2.10, 4.2.12, and 4.2.13 **by specification
in at least one form of documentation**", and "Documentation requirements **may be met by reference to other
documents**, including those of the operating environment and other COBOL implementations."

**Q3a — does `docs/CONFORMANCE.md`, as shipped in this repository, count as "the implementor's user
documentation"?** Options: `yes` · `no, it must also be published in a customer-facing form first`.
**Consequence:** every mechanism that landed treats the repo file as that form. If it is not, then 222 rows would
close against an artifact that does not exist yet, **and the gate cannot tell** — it resolves an anchor into the
file, and the file is there.

**Q3b — may a §7 row discharge its obligation BY REFERENCE — naming the .NET / Unicode / OS document instead of
stating the value locally — and still close?** Options: `yes` · `no, the value must be stated locally`.
**Consequence:** several of the remaining 163 obligations are answered entirely by the host (item 20 case mapping,
item 12 bits per byte, item 144's unseeded seed), so the answer materially changes the cost of finishing the
register. But a by-reference row states **no value**, so no test can pin it and the gate can only check that a row
exists — which collides with Q2: a by-reference row is very often exactly a row with nothing to observe.

## What this note does NOT hold up

The mechanism itself. The computed anchor, `implementation-pattern`, the anchored-file alternation, the §7 re-key,
the `Pinned by` agreement check and the 37-record back-fill all landed; **18 rows closed and 19 came back
CONFORMS-but-untested** (item 87 among them — the orchestrator refused the back-fill's close of it because its
only candidate test asserts two fraction digits where the determination claims seven-then-zeros, which is the
`Pinned by` check's own lesson applied one notch harder: a test that names the right function still has to assert
the claim). Only the two `inventory_rows` above wait on Q1, and Q2/Q3 shape the *remaining* 183 rows rather than
anything already recorded.
