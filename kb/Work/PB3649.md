# PB3649 — the landing lane waits on the wrong lock after a Linux BUSY

**Sites:** `scripts/orchestrator/land_lane.py` (`wait_free`, `gate_lock_free`), `scripts/orchestrator/enqueue.py` (the exit 12 message), `scripts/linux-gate.sh` (`begin_gate`, the BUSY verdict).

## What happens

PB3310 made `linux-gate.sh` print `LINUX GATE: BUSY` when another Linux gate of the same tree runs; `enqueue.py` reads that as exit 12. But `wait_free` for exit 12 probes only the Windows gate driver lock, and the `enqueue.py` message still says another gate holds the worktree's gate lock. So the lane never waits on what a Linux BUSY waits on: it either retries into BUSY again or treats the branch as free at once. The related lead is the same mechanism: `TestResults/linux-gate` is keyed per tree by design (the planner's newest-run contract), so two hand runs on one tree now get BUSY instead of sharing it, and nothing tells the user which gate holds it.

## Fix direction

Give exit 12 one meaning per source: have `wait_free` probe the Linux owner file (under `GATES_ROOT`) as well as the Windows lock, word the `enqueue.py` message from the source that was busy, and add `land_lane` and `enqueue` self-test cases for a Linux BUSY.

## Landing (wave 20261104, group A2)

Re-probed by reading both ends: `land_lane.wait_free(EXIT_GATE_BUSY)` probed only the Windows gate lock, while the Windows
gate ends BUSY (exit 3) when its Linux half finds a Linux gate of the tree running, which `enqueue.gate_once` turns into
exit 12 with a message that always said the Windows gate lock was held. Exit 12 now has one meaning per source, named
and waited on.

- **The wait asks both holders.** `linux-gate.sh --probe` (new; `probe_tree`, no SDK or interpreter needed, nothing
  cloned, reaped or emptied) answers the same BUSY line a second gate would get (exit 3, now naming the running gate's pid
  AND start time: `busy_line`, the one wording `begin_gate` shares) or `linux-gate probe: FREE` (exit 0).
  `run_gate_legs.Host.linux_gate_holder` runs it (a Windows host with no WSL is asked nothing; a probe that hangs or
  cannot answer reads as no holder, because a retry that meets BUSY again touches nothing while a wait that never ends
  costs the branch). `land_lane.gate_lock_free` is free only when the gate lock is free AND no Linux gate runs; `wait_free`
  passes the probe through so a self-test plants it (the real one starts WSL).
- **The message is worded from the source.** `enqueue.gate_once` quotes the gate's own verdict line, which names the
  Linux half's BUSY and the running gate, instead of asserting the Windows lock.
- **The related lead** (two hand runs on one tree get BUSY and nothing says which holds it) is the pid and start time in
  the BUSY line.

Self-tests: `linux-gate.sh --self-test` (the BUSY line, `--probe` busy / free / never-gated tree creating nothing),
`run_gate_legs` (`linux_gate_holder` with a stand-in process: busy, free, not-answered, hung, cannot start, no WSL),
`land_lane` (free gate lock + a Linux gate running is not free and names its pid; gone is free), `enqueue` (a Linux-half
BUSY is exit 12 with a Linux message). `LandingPipelineDriftTests` holds `busy_line` and `probe_tree` in `linux-gate.sh`.
Docs: enqueue.py module doc, land_lane.py module doc, `units/enqueue.md`, `landing.md`, DESIGN-orchestrator-loop.md,
DESIGN-test-build-ci.md.

**For the next implementer.** `scripts/linux-gate.sh#probe_tree` and `busy_line` (the one BUSY wording), `run_gate_legs.py#Host.linux_gate_holder` (the one asker; inject `run`/`which`/`say` in a self-test, never start WSL), `land_lane.py#gate_lock_free` (free only when BOTH the gate lock and the Linux gate are). `bash scripts/linux-gate.sh --probe` through the hook-guarded Bash tool is refused as "too complex"; run it from PowerShell.
