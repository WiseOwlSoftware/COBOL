### Observed
PARSE ERROR. MEASURED at --std 2023: `FROM (+1) TO (+3)` is `error COBOL0001` (probe b_sr19_signed, rc 65) -- a generic parse failure the user cannot map to any rule. The rule's PROHIBITION is enforced correctly, and also only by the grammar's shape: `FROM (1.5)` is COBOL0001 "unexpected '1.5'" (sr19_noninteger_subscript) and `FROM (K)` naming a level-78 constant is COBOL0309 "A literal value is expected here, not a data-name" (sr19_word_subscript) -- neither names SR19. THIS IS A GRAMMAR-WIDE PATTERN, NOT A VALUE-CLAUSE ONE: `occursBound` uses the same `integerLiteral`, so `01 T PIC X OCCURS +3.` is also a parse error, "no viable alternative at input 'OCCURS+'" (c_occurs_signed). The structural fix is to give `integerLiteral` an optional sign once, where every integer-literal position inherits it, rather than patching this one call site -- and to pair it with a drift test over the integer-literal positions so the next one is automatic. Practical frequency is low (few programs write `+1` as a subscript), which is why this is filed at low severity, but it is legal source rejected with an unmappable error.
