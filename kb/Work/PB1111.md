- **Expected (spec):** G2=5004. §14.7.6 rule 6: a pair corresponds only if 'The name of each data item that satisfies the above conditions is unique after application of the implied qualifiers' (cite.py --check 14.7.6 -> OK §14.7.6 6)); uniqueness of a name is uniqueness of REFERENCE (§8.4.2.2.1 'Qualification is used to allow unique reference of user names', --check -> OK). 'DU OF G1' and 'FF OF G1' each identify two data items (a FILLER level contributes no qualifier), so DU and FF do not correspond; BB and CC do.
- **Observed:** Prints G2=5134: DU (1) and FF (3) are moved. CorrMatch builds srcCount and dstByName from CorrMembers(...), which has already filtered through CorrEligible (OCCURS / REDEFINES / class exclusions) and dropped nameless-group subtrees, so the excluded namesake is invisible to the rule-6 duplicate count. The code comment reads rule 6 as 'a duplicated ELIGIBLE name on EITHER side'; the rule's subject is the eligible item but its predicate is the uniqueness of that item's NAME under the implied qualifiers, which every same-named data item at that qualification level defeats. Same shape on the D2 side (dstByName) and for ADD/SUBTRACT CORRESPONDING. Fix shape: count every named subordinate that the implied qualified reference would match (all Children with that CobolName at the level, plus names reachable through FILLER / nameless groups) before applying rules 4/5; the pairing then asks CorrEligible of the unique item. Interpretive note for the registrar: the alternative reading (unique among the items satisfying rules 1-5) is what the code implements; the §8.4.2.2.1 reading is preferred because 'unique after application of the implied qualifiers' is the vocabulary of qualification, but a GnuCOBOL survey would confirm latitude if any.
- **Code site:** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/CorrespondingBinder.cs#CorrMatch (srcCount / dstByName built from CorrMembers); CorrespondingBinder.cs#CorrMembers

## What the fixer owes
Rule 6 asks whether the NAME is unique after the implied qualifiers — a question over EVERY subordinate namesake, not over CorrMembers' filtered set. Count uniqueness on the unfiltered subordinate forest, then apply rules 1/4/5. Sweep every CORRESPONDING consumer (MOVE, ADD, SUBTRACT) — they share CorrespondingBinder.CorrMatch.
