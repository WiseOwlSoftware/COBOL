**Witness.** `E:/COBOL-coord/scratch/w20261863b/probe3.cob`: with A = 999999999999999, PIC S9(18), `COMPUTE R31 = A * A * A / (A * A)` stores ...998; GnuCOBOL and the value are ...999. No power is involved, and `A ** 3 / A ** 2` gives the same result. The nested form (`... * 1`) is exact.

**Mechanism.** `NumericRenderer.cs#Divide` ends in `DecDivToOdd(DecOperandExact(a), DecOperandExact(b))`, and `CombineCore`'s exact arm takes only `op == "/" && NestedQuotient`. `CobolWide.TryQuotientDec` already takes the exact dividend, with a `jam` (round-to-odd) flag in `Round34Wide`.

**Decide first.** `docs/NUMERIC_DESIGN.md` (D19) and DOC-A.1-123 document the current lane. Derive the answer from the ISO text, then the precedence of CLAUDE.md rule 1 (GnuCOBOL gives ...999), before changing the code or the document.

**The golden hole.** PB4569 rewrote T10 of `conformance-suite/cases/A.1-Implementor-defined-language-element-list/pb69_native_power_past_the_carrier.cob` from `A ** 3 / A ** 2` to the nested `A ** 3 / A ** 2 * 1`, so no golden pins the final-transfer behavior that D19 states. The fix adds one.

**Landed (wave 20261865, group A).** Re-probed on the build: `COMPUTE R31 = A * A * A / (A * A)` (and the `A ** 3 / A ** 2`, `/ (A * A)`, `/ A ** Y` forms) stored ...998; `A ** 3 / A` stored ...000 where ...001 is owed (the same image residue). The decision was taken from ISO 8.8.1.3 (native arithmetic is implementor-defined), then CLAUDE.md rule 1: GnuCOBOL's `cob_decimal_div` shifts the EXACT dividend and truncates, so the final-transfer quotient divides the operands' exact values. Fix: `NumericRenderer.ExactFinalQuotient` (new) takes both operands as `ExactOperand`, and `CobolExact.DivToOdd` (new) forms the exact quotient on the wide form (`CobolWide.TryQuotientDec`, widened with a divisor scale and a `jam` flag so the 34-digit result is round-to-odd) or, past 77 digits, over the operands' round-to-odd images (DOC-A.1-123's determination). Two arms reach it: `Divide`'s last line (a final transfer over a wide operand, a floating-point edited resultant) and `CombineCore`'s exact arm (a final-transfer quotient over a run-time-scaled exact value, which lowered both operands before). `RuntimeApi.DecDivToOdd` has no caller and is deleted.

Siblings, the same mechanism reached through another door, fixed in the same change: the several-receiver COMPUTE's root quotient and product rendered their operands settled (`COMPUTE R R2 = A * A * A / (A * A)` stored ...998 in both receivers; `keepWide` now); `DIVIDE` / `MULTIPLY ... GIVING` with a FUNCTION operand whose value is an exact wide intermediate (`DIVIDE FUNCTION ABS (A * A * A) BY FUNCTION ABS (A * A) GIVING R`); and `DIVIDE ... GIVING Q REMAINDER R` over such operands (quotient ...998 and remainder 997999900000000000; the carried arm now takes them exact, and the subsidiary quotient joins the back-multiply as an exact value so the 45-digit product is not rounded to the SDIDI's 34, ISO 14.9.12.4 7)).

**Not fixed (a lead in the report):** `DIVIDE FUNCTION ABS (A * A * A + 7) BY 1000 GIVING R REMAINDER R2`, where the quotient itself passes 34 digits (a size error at R with the remainder still stored, DOC-A.1-70): the subsidiary quotient is an SDIDI of 34 digits, so the remainder is the dividend less the truncated quotient times the divisor. Forming it on the wide form is a redesign of the subsidiary quotient.
