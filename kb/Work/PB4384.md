# PB4384 - a semicolon inside an embedded block is still judged as COBOL

**Sites:** `src/WiseOwl.Cobol.Frontend/Parsing/EmbeddedBlockReading.cs:65` (`EmbeddedBlockReading.Read`, the `if (t.Channel != TokenConstants.DefaultChannel) continue;` that leaves a HIDDEN token where it is), `src/WiseOwl.Cobol.Frontend/Parsing/ProgramText.cs` (`ProgramText.Holds`, which excludes only `ABSENT_DEBUG_LINE` and `EMBEDDED_BLOCK_TEXT`).

**Read at:** commit a4f54e0a4 (tip of `worktree-wf_ca25d124-0aa-10`, PR #971); not on main 4aff86e01 yet.

The lexer rule `SEMICOLON : ';' -> channel(HIDDEN)` puts a semicolon with no space after it on the HIDDEN channel precisely so `SeparatorRule.Violations` can judge it (section 8.3.5 separator rules). `Read` skips every non-default token of a block, so that semicolon keeps channel HIDDEN, `ProgramText.Holds` is true for it, and `Violations` judges SQL text as COBOL. That contradicts `docs/CONFORMANCE.md` 3.2 item 4 and DESIGN-frontend-grammar 3.9 (a block's text draws no COBOL diagnostic of its own). What the user sees: a separator diagnostic on a `;` inside `EXEC SQL ... END-EXEC`. The code path was verified by reading; the exact code and text were not probed, so the implementer writes the repro first (for example `EXEC SQL SELECT A;B INTO :W-H FROM T END-EXEC.`).

Fix direction: move every token of a block, whatever its channel, onto `EMBEDDED_BLOCK_TEXT`, with a unit row for the semicolon.
