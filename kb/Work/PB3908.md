# PB3908 — evaluate-condition-name-subject-and-object--condition-name-subject-crash: cobc segfault: EVALUATE condition-name WHEN relation-condition ('unknown (signal)', Please report this!)

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S6) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\evaluate-condition-name-subject-and-object--condition-name-subject-crash.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\evaluate-condition-name-subject-and-object--condition-name-subject-crash\`.

## Summary

cobc 3.2 ends with a segmentation fault ("unknown (signal)", "Please report this!", exit 139) when an EVALUATE's
selection subject is a condition-name and the matching WHEN object is a relation condition (`EVALUATE IS-TWO WHEN
N = 2`). That program is legal (Table 15: Condition object with Condition subject). The same subject with an
identifier object (`EVALUATE IS-TWO WHEN N`), a combination Table 15 forbids, passes `-fsyntax-only` with no
diagnostic and then crashes cobc during code generation. Both come from cobc treating a condition-name subject as a
data operand for a value comparison. Class: crash. Split from `evaluate-condition-name-subject-and-object` (the
refusal of a condition-name object), which shares the missing condition-subject case.

Free reference format (`-fformat=free`), 13 lines, written for this record while reducing the family's fuzz witnesses

## Expected result (per ISO)

`evcB.cob` is legal and prints `MATCH`: IS-TWO is false (N is 1) and `N = 2` is false, the truth values match.

- §14.9.13.3 7) b) (checked): "Condition-2 or the words TRUE or FALSE appearing as a selection object shall correspond
  to condition-1 or the words TRUE or FALSE in the set of selection subjects."
- §14.9.13.3 10) (checked) and Table 15 (rendered from the printed page, 2023 PDF page 650): row "Condition", "Y"
  under the subject column "Condition".
- §14.9.13.4 3) e) (checked): "Any selection subject specified by condition-1 is assigned a truth value according to
  the rules for evaluating conditional expressions."
- §14.9.13.4 4) a) 3. (checked): "If the truth value of the selection subject and selection object match, the result
  of the analysis is true."

`evcG.cob` violates a syntax rule and shall be refused with a diagnostic: Table 15, row "[NOT] identifier", is blank
under "Condition" ("A space indicates an invalid combination"), and §14.9.13.3 7) a) (checked): "Identifiers,
literals, or expressions appearing within a selection object shall be valid operands for comparison to the
corresponding operand in the set of selection subjects". Either way a compiler crash is a defect.

Edition: 2014. The 2009 committee draft that became ISO/IEC 1989:2014 (CD 1.2) has the same syntax rule 7) b) and the
same Table 16 (rendered, draft page 475). The 2002 text carries the same syntax rule 7) b).

Edition as recorded by the adjudicator: 2014 (also 2002). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Class

GNUCOBOL-DEFECT: crash (compiler segmentation fault) on legal source of edition 2014; the illegal variant is also
accepted by `-fsyntax-only` under `-std=cobol2014`.

## Our compiler (WiseOwl)

WiseOwl COBOL (built from main 6ed90bd1c), `cobol evcB.cob --std 2014 --source-format free -o evcB.dll`, then
`dotnet evcB.dll`: compile exit 0, run exit 0, output `MATCH`. On `evcG.cob`: compile exit 65,
`evcG.cob(9,1): error COBOL1634: the selection subject is a condition and the selection object 'N' is an identifier;
ISO §14.9.13.3 SR10 Table 15 marks that combination invalid.`

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/typeck.c`, `evaluate_test`: for a subject that is not the word TRUE or FALSE and an object that is not a
  level-88 reference, it builds the "Regular comparison" `subject = object`. With a condition-name subject that hands a
  level-88 reference to the comparison as a value operand; the crash follows from there (in `cb_build_cond` /
  `cb_build_cond_default` for the relation object at the end of the statement, in code generation for the identifier
  object). The crash frame itself was not captured (no debugger available); the location is inferred from the source
  path and from cobc's own abort messages ("at line 12", the END-EVALUATE; "aborting codegen").
- The fix is the same missing case as in the companion record: a condition-1 subject must be classified as a
  condition (compare truth values with a condition object), and a value object paired with it refused per Table 15.
  `cobc/parser.y`, `evaluate_subject`, keeps the subject as a plain expression.
