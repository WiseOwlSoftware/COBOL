# PB948 — OPEN — the probe cannot see the allocator

Source: the **train-43 lander report** §5, which records it as a fact for the next reader rather than as a
defect: *"The 'next free diagnostic code' is COBOLNET2203, not the 2197 a mechanical probe reports … so
`session-probe`'s catalog-ceiling answer sits BELOW the allocator."* DEVLOG 1625 says the same, and plan §0's
live-state bullet now carries the sentence. **Three prose copies of one number is the defect, not the fix.**

## Measured here

```
$ grep -rhoE 'COBOLNET[0-9]{4}' src/ | sort -u | tail -1
COBOLNET2196
$ grep -hoE '"COBOLNET[0-9]{4}"' src/Cobol.Net.Editions/Diagnostics/DiagnosticCatalog.cs | tr -d '"' | sort -u | tail -1
COBOLNET2196
```

`scripts/session-probe.ps1` takes `nextFree = max(srcGrepMax, catalogMax) + 1`, so on this tree it answers
**COBOLNET2197**. Plan §0 says the next free code is **COBOLNET2203**: train 43's central allocation ran
COBOLNET2176–2202, six were used (2176, 2177, 2186, 2187, 2191, 2196) and the rest were RETURNED —
2178–2185, 2188–2190, 2192–2195, **2197–2202** — and returned codes are never reused. **The probe's answer is
six codes inside the returned band**, and 2197 is the very first of them.

## Why the script cannot be right as written

Its own header already names this class of failure twice:

> 2. Diagnostic band — the next-free claim is the CEILING of BOTH scans (the 1573/1518 collision lesson).

and

> an emitted code = an orphan (reserved-but-never-emitted at the ceiling) worth reconciling before allocating.

Both guards compare the two **observable** ceilings against each other. Neither can see the third number, because
the allocator's high-water mark **is not written down anywhere a script can read**: a returned code leaves no
trace in `DiagnosticCatalog.cs`, none in `src/`, none in `docs/DIAGNOSTICS.md` (which is generated FROM the
catalog). It exists only as English in plan §0 and in a DEVLOG entry, and plan §0 is live state that the next
train rewrites.

`kb/Work/PB608` (open) is the same family arriving from the other side — COBOLNET1535 and COBOLNET1573 each
defined TWICE in the catalog — and its note already records COBOLNET1576 as having been renumbered away from a
collision with 1573. A returned code handed out twice is exactly how that collision is produced.

## The shape the fix should take

CLAUDE.md rule 5: **never a hand-maintained list where a structure belongs.** The high-water mark and the
returned band are DATA, and the only durable home for them is the catalog itself or a small register beside it
that `session-probe.ps1` and every allocator read:

* the allocator records the range it claimed and the codes it returned;
* `session-probe.ps1` reports `max(srcGrep, catalog, allocatorHighWater) + 1` and says which of the three won,
  so a reader can see when the allocator is ahead;
* a drift test asserts that no code in the returned band appears in `DiagnosticCatalog.cs` — the arm that makes
  "never reused" true rather than remembered, and the arm to prove RED once before trusting
  (`feedback_green_gates_arent_evidence`).

⚠ **`kb/Work/PB294` is the reason this needs its own gate rather than trust:**
`DiagnosticRegistryDriftTests.EveryEmittedCode_IsACatalogDescriptor` is recorded there as effectively vacuous, so
today nothing mechanical would notice a reused code until two descriptors shared it.

## The sibling sweep the fixer owes

Every OTHER number that a session-probe line computes from a scan while the authority lives in prose. Read
`scripts/session-probe.ps1` top to bottom and, for each reported figure, ask: **can this scan see the thing that
actually decides the answer?** Named starting points from this pass: the next-free ID for `kb/Work/PB*.md`
(which IS derivable from the register and therefore fine) and the VCR todo count. Add each that cannot to this
