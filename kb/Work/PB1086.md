### Adjudicator finding (repository-paragraph, harm under-rejects)
- **Mechanism:** There is no §8.13 external repository: the REPOSITORY specifiers are never checked for resolvability, and each consumer substitutes its own reading - program prototypes resolve at run time against the run-unit registry (no details), functions draw COBOLNET1505 only at a use, classes/interfaces COBOLNET0813/0859 only at a use, properties the generic diagnosis only at a use. None of it is documented (Annex A.1 items 66, 161, 162 have no CONFORMANCE.md row).
- **Repro:** out/probe/repo/sr10.cob (--std 2023): REPOSITORY. FUNCTION NOSUCHFN FUNCTION ALIASFN AS "NOSUCH-EXT" PROGRAM NOSUCHPG CLASS NOSUCHCL INTERFACE NOSUCHIF PROPERTY NOSUCHPR. with nothing of those names anywhere; PROCEDURE DIVISION displays RAN. sr6.cob: PROGRAM NOSUCHPG + CALL NOSUCHPG ON EXCEPTION DISPLAY "NOT-FOUND".
- **Expected (spec):** §12.3.8.3 SR6/SR9/SR16: there SHALL be external-repository information for the named class / interface / property; SR10/SR14: the function / program name shall be an in-group prototype, a PREVIOUS in-group definition, or one with external-repository information. With no external repository none of the six names has information, so sr10.cob is nonconforming at every specifier. §8.13 requires the implementor to provide a mechanism to update the external repository and to flag prototype/definition differences from it (Annex A.1 item 66, required + documented); GR6/GR9 require the class/interface details to come from the specifier 'together with the external repository' (A.1 items 161/162, required + documented).
- **Observed:** sr10.cob compiles clean and prints RAN; sr6.cob prints NOT-FOUND at run time. The program arm's determination ('this implementation's external repository is the run unit's program registry', BinderDriver.ProgramPrototypesOf / PrototypeSignatures) supplies a callee but no DETAILS, so GR10 c)'s signature-driven behaviour (GR9 b) BY VALUE default, §14.8 conformance) silently falls back for any separately compiled program; the function arm refuses the same situation (COBOLNET1505) and the class arm refuses it at the use - three readings of one clause. kb/Work PB989 (open) owns only the 'previously' half of GR10/GR11. This needs an owner decision (implement §8.13's repository and its two mechanisms, or document a determination for A.1 items 66/161/162 and check each specifier against it) before a fix can be derived.
- **Code site:** src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindDeclarations (specifiers recorded, never resolved); src/Cobol.Net.Compiler/Binding/BinderDriver.cs#ProgramPrototypesOf; src/Cobol.Net.Compiler/Binding/BinderDriver.cs#UserFunctionsOf; src/Cobol.Net.Compiler/Binding/Procedure/Verbs/UdfBinder.cs#UdfBindCall; src/Cobol.Net.Compiler/Oo/OoNameResolution.cs#Resolve; docs/CONFORMANCE.md §7 (no A.1-66/161/162 rows)

### Finding — `cobol-words` (rejects-legal-source; rows `GR-8.3.2.2-L2.1`)

**Mechanism.** No cross-compilation-unit resolution for OO definitions: the compiler resolves REPOSITORY class/interface specifiers only against definitions in the SAME compilation group (OoClassTable), references no other COBOL.NET assembly at compile time, and provides no external-repository mechanism (§8.13), so an object-class-name (and with it interface-, method- and property-names) is externalized only inside its own compilation group — while outermost program-names and user-function-names DO cross units (runtime sibling-module probe, prototypes)

**Repro.** out/probe/extern: `cobol EXCLS.cob -o EXCLS.dll` (CLASS-ID. EXCLS. FACTORY with METHOD-ID. HELLO.), then exmain.cob `REPOSITORY. CLASS EXCLS.` + `INVOKE EXCLS 'HELLO'` -> error COBOLNET0823: INVOKE: 'EXCLS' is neither a resolvable data item nor a class this source element may reference. The program/function twins in the same directory (CALL 'exsubp', FUNCTION EXFN via IS PROTOTYPE) compile and run.

**Expected from the spec.** An object-class-name is externalized to the operating environment (§8.3.2.2); a class-specifier naming a class not in the compilation group takes its signature from the external repository (§8.13, §12.3.8), whose update mechanism the implementor shall provide — so the program should compile and print HELLO FROM EXCLS, or the implementation must document the mechanism by which it does not (owner decision if declined).

**Observed / reasoning.** COBOLNET0823 at compile time; RoslynBackend adds only the runtime assembly as a MetadataReference; no CONFORMANCE.md row answers §8.13's two mandatory mechanisms. Needs an owner decision on the external-repository surface before a fixer can land it; register as a defect/analysis note tied to §8.13.

### Finding — `cobol-compilation-group` (silent; rows `GR-10.6.3-1`)

**Mechanism.** Compiling a program or function PROTOTYPE generates no external-repository information: the implementation's external repository is the run-unit program registry, ProgramEmitter skips prototypes when registering modules, and there is no persisted repository nor either §8.13 user mechanism (update / flag differences), so a prototype's signature is usable only by callers inside the same compilation group.

**Expected from the spec.** §10.6.3 GR1: 'Compilation of a program prototype definition or a function prototype definition generates information required for the external repository, as specified in 8.13, External repository.' §8.13: 'Whether the information is taken from a prototype or a definition, the information stored in the external repository about the signature of a program or a function is the same.', 'The implementor shall provide a mechanism that allows the user to specify whether to update the external repository when a compilation unit is compiled.' and '... whether to flag differences in prototypes and definitions in the compilation group from the information in the external repository.' - compiling proto_only.cob should (when the user asks for an update) record CGPO's signature in the external repository, and a later compilation naming CGPO should obtain those details.

The in-group half conforms (conformance:2002/udf_prototype). Whether to realise the repository as a persisted per-directory signature store or an assembly-metadata record is a design choice (docs/COBOLNET_INTERPROGRAM_DESIGN.md is the deep-dive to extend); §8.13's two mechanisms are required either way.
