# PB4598 — relative-rewrite-keeps-old-record-length: RELATIVE file, variable-length records: REWRITE keeps the old record length

Filed 2026-11-04 from the second review of fuzz night 10's draft n10-relative-delete-rewrite (the PB4539 ticket), whose reviewer found this defect in the same function while probing it and asked that it be filed separately. Vetted the same day: the rule re-derived and every quote checked with cite.py, the Annex A entries ruled out, the repro re-run on 3.2.0 and 3.3-dev, the ticket cache and kb/Work searched. Upstream status `unreported`: the owner has not yet decided to report it. The probe programs are local (`~/gc-notes/PB4598/varrw.cob`, `varsh.cob`, `varsq.cob` under WSL): the minimal program below is the repro.

## Summary

For a RELATIVE file with `RECORD IS VARYING ... DEPENDING ON LN`, cobc 3.2.0 and 3.3-dev store each record's length in a size word in front of the slot. `REWRITE` never writes that word: it rewrites the data bytes and leaves the length the record had before. A later `READ` returns the old length in LN, so a record grown from 2 to 6 bytes reads back as 2 bytes, and one shrunk from 6 to 2 reads back as 6. This happens in random, dynamic and sequential access, and the REWRITE reports status 00. Class: wrong output (the file's data is changed silently).

## Minimal test case

Free reference format.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. VARRW.
ENVIRONMENT DIVISION.
INPUT-OUTPUT SECTION.
FILE-CONTROL.
    SELECT F ASSIGN TO "varrw.dat"
        ORGANIZATION IS RELATIVE
        ACCESS MODE IS RANDOM
        RELATIVE KEY IS RK
        FILE STATUS IS FS.
DATA DIVISION.
FILE SECTION.
FD F RECORD IS VARYING IN SIZE FROM 1 TO 8 CHARACTERS
     DEPENDING ON LN.
01 REC PIC X(8).
WORKING-STORAGE SECTION.
01 RK PIC 9(2) VALUE 0.
01 FS PIC XX VALUE SPACES.
01 LN PIC 9(2) VALUE 0.
PROCEDURE DIVISION.
    OPEN OUTPUT F
    MOVE 1 TO RK MOVE 2 TO LN MOVE "AB" TO REC WRITE REC
    CLOSE F
    OPEN I-O F
    MOVE 1 TO RK
    MOVE 6 TO LN MOVE "CDEFGH" TO REC
    REWRITE REC
    DISPLAY "REWRITE " FS
    CLOSE F
    OPEN INPUT F
    MOVE 1 TO RK MOVE 0 TO LN MOVE SPACES TO REC
    READ F
    DISPLAY "READ " FS " LN=" LN " [" REC "]"
    CLOSE F
    STOP RUN.
```

## Environment

`cobc (GnuCOBOL) 3.2.0` and `cobc (GnuCOBOL) 3.3-dev.0` (r5751, tarstamp Oct 29 2026 09:31:09 UTC, run through the `cobc-dev`/`run-dev` wrappers that set `LD_LIBRARY_PATH` to the dev runtime), WSL2 Ubuntu x86_64. Compiled with `cobc -x -free -std=cobol2014 -o varrw-32 varrw.cob` and run as `./varrw-32` after `rm -f varrw.dat`. `-Wall` adds no cobc diagnostic (3.2.0 prints gcc's `_FORTIFY_SOURCE redefined` note on every compile, with or without it); the default `-std` gives the same output.

## Observed result

The program compiles with no cobc diagnostic (exit 0; the packaged 3.2.0 prints gcc's `_FORTIFY_SOURCE redefined` note on every compile, 3.3-dev prints nothing) and prints, on 3.2.0 and 3.3-dev alike (run exit 0):

```text
REWRITE 00
READ 00 LN=02 [CDEFGH  ]
```

The data file after the run (`od -An -tx1 varrw.dat`) shows the size word still 2 and the new data behind it:

```text
 02 00 00 00 00 00 00 00 43 44 45 46 47 48 20 20
```

The shrinking case (`varsh.cob`: WRITE LN 6 "ABCDEF", REWRITE LN 2 "XY") prints `READ 00 LN=06 [XY      ]`, size word `06`. The sequential-access case (`varsq.cob`: ACCESS SEQUENTIAL, WRITE LN 2 "AB", then READ, REWRITE LN 6 "CDEFGH") prints `READ 00 LN=02 [CDEFGH  ]`, size word `02`. Both versions agree on all three programs. The dynamic-access case (`vardy.cob`, the refuter's `varrw` with `ACCESS MODE IS DYNAMIC`, `~/gc-notes/refute-PB4598/vardy.cob`) prints `REWRITE 00` / `READ 00 LN=02 [CDEFGH  ]` with size word 02, on 3.2.0 and r5751, every compile and run exit 0. WiseOwl prints LN=06.

## Expected result (per ISO)

The program prints `REWRITE 00` and then `READ 00 LN=06`, with REC beginning `CDEFGH`. The standard does not fix REC's last two bytes (both implementations leave spaces), so the `[CDEFGH  ]` text in the observed line is not itself the defect.

- §14.9.35.4 21) (checked): "For a file accessed in either random or dynamic access mode, the operating environment logically replaces the record identified by the relative key data item specified for file-name-1"; the record that replaces it is the one REWRITE releases (§14.9.35.4 4), checked: "The successful execution of the REWRITE statement releases a logical record to the operating environment").
- §13.18.43.4 13) and 13) a) (checked): "During the execution of a RELEASE, REWRITE, or WRITE statement, the number of bytes in the record is determined by the following conditions: a) If data-name-1 is specified, by the content of the data item referenced by data-name-1." LN is 6 at the REWRITE, so the released record is 6 bytes.
- §14.9.35.4 18) (checked), under RELATIVE AND INDEXED FILES: "The number of bytes in the record referenced by identifier-1, the runtime representation of literal-1, or the record referenced by record-name-1 may differ from the number of bytes in the record being replaced." Only a record sequential file requires equal lengths (§14.9.35.4 16), checked: "For a record sequential file, if the number of bytes ...").
- §13.18.43.4 15) (checked): "If data-name-1 is specified, after the successful execution of a READ or RETURN statement for the file, the contents of the data item referenced by data-name-1 will indicate the number of bytes in the record just read." The record just read is the 6-byte record, so LN is 06.

The sequential-access case follows from rule 5 of §14.9.35.4 ("the operating environment logically replaces the record that was accessed by the READ statement") and the same 13.18.43.4 rules.

Edition: 2014. The 2009 committee draft CD 1.2 (`t2009.txt`) has the same rules: RECORD clause 13.18.42 rules 13) a) and 15) (lines 19466-19489) and REWRITE 14.9.33 rules 17) and 20) (lines 29267-29287). The 2002 text (`t2002.txt`) has the RECORD rule 15 and the REWRITE "may differ" rule in the same words (lines 18120, 27337). The published 2014 text was not checked; the 2014 reading is inferred from the 2009 CD and the 2023 text, which agree.

## Our compiler

WiseOwl COBOL (`--std 2014 --source-format free --run`, main build of 2026-11-03): prints `READ 00 LN=06 [CDEFGH  ]` for varrw, `LN=02 [XY      ]` for varsh and `LN=06 [CDEFGH  ]` for varsq, exit 0. Correct.

## Fix site

`libcob/fileio.c`, `relative_rewrite` (r5751 lines 3396-3433; the name is on line 3397, line 3431 is only the data `COB_CHECKED_WRITE`, the return is on 3432 and the closing brace on 3433). `cob_rewrite` (line 6963) sets `f->record->size` from the DEPENDING ON item before it calls the organization's rewrite. In the random/dynamic arm, `relative_rewrite` then reads the slot's size word INTO `f->record->size`, overwriting the new length with the old one, and writes only `f->record->data` (`f->record_max` bytes) after it. In the sequential arm it seeks back `f->record_max` bytes, to just past the size word, and again writes only the data. Neither arm ever writes the size word. `relative_write` (line 3335) writes both the size word and the data. The fix is to read the stored size word into a local variable, seek back to the slot start (`off` in the random arm, `-(record_max + sizeof size)` in the sequential arm), and write `f->record->size` and then the data, as `relative_write` does. The size word must be written only after the empty-slot test (a stored size of 0 gives `COB_STATUS_23_KEY_NOT_EXISTS`, PB4539's fix). Applied alone, the change makes REWRITE of a deleted or never-written slot create the record. The refuter built this fix in a copy of the r5751 tree (libcob only, `~/gc-notes/refute-PB4598/patch.py`). Probe `varemp.cob` (WRITE keys 1 and 3, DELETE key 1, REWRITE key 1 "WXYZ" and key 2 "PQRS" with LN 4, then READ each) then prints `REWRITE1 00` / `REWRITE2 00` / `READ1 00 LN=04 [WXYZ    ]` / `READ2 00 LN=04 [PQRS    ]`, where stock 3.2.0 and r5751 print `READ1 23` and `READ2 23`. That breaks §14.9.35.4 21) ("If the file does not contain the record specified by the key, the invalid key condition exists") and §14.9.35.4 14) ("no logical record updating takes place"), both checked. With PB4539's size-0 test on the local variable (`patch2.py`), all five probes are correct: `varemp` gives REWRITE1/2 23 and READ1/2 23, `varrw`, `vardy` and `varsq` give LN=06, and `varsh` gives LN=02. So the fix is built and checked by the refuter on five probes, together with PB4539's empty-slot test.

## Draft issue

**Title:** RELATIVE file with variable-length records: REWRITE does not update the record length (READ after REWRITE returns the old length)

Environment: GnuCOBOL 3.2.0 (and 3.3-dev r5751 of 2026-10-29), WSL2 Ubuntu x86_64; `cobc -x -free -std=cobol2014 -o varrw varrw.cob`.

Program: the VARRW program above (RELATIVE, ACCESS RANDOM, `RECORD IS VARYING IN SIZE FROM 1 TO 8 CHARACTERS DEPENDING ON LN`; WRITE key 1 with LN 2 "AB", REWRITE key 1 with LN 6 "CDEFGH", READ key 1).

Observed (exit code 0, no diagnostic): `REWRITE 00` / `READ 00 LN=02 [CDEFGH  ]`; the file's size word for slot 1 is still 2. Shrinking (LN 6 to LN 2) reads back LN=06, and ACCESS SEQUENTIAL (READ then REWRITE) behaves the same.

Expected: `READ 00 LN=06`, with REC beginning `CDEFGH` (the standard does not fix REC's last two bytes; both implementations leave spaces). ISO/IEC 1989:2023 §13.18.43.4 13) a): during a REWRITE the number of bytes in the record is determined "by the content of the data item referenced by data-name-1"; §14.9.35.4 18): for relative and indexed files the new record "may differ from the number of bytes in the record being replaced"; §13.18.43.4 15): after a READ, data-name-1 "will indicate the number of bytes in the record just read".

Fix site (observed): `libcob/fileio.c`, `relative_rewrite`. The random/dynamic arm reads the stored size word into `f->record->size`, overwriting the length `cob_rewrite` took from DEPENDING ON, and both arms write only the data bytes, never the size word. The fix is to read the old size word into a local variable and write `f->record->size` before the data, as `relative_write` does, but only after the empty-slot test (stored size 0 gives status 23, PB4539): applied alone, it would make REWRITE of a deleted or never-written slot create the record.
