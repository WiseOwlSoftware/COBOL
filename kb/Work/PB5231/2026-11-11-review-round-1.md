**R1-1 (high): the trace never judged a module imported from a warm `__pycache__`.**
- *Scenario* (`pyc_probe.py`): the generator imports an undeclared `lib/helper.py`. With no cache the run is refused. Once
  any process has left `lib/__pycache__/helper.*.pyc`, the import opens only that .pyc, which is untracked, and stats the
  source, which raises no audit event. The run passed and was recorded. Then an edit to `helper.py` left the target "up to
  date" at a stale digest (`m.json` read `1 1` while the generator really wrote `1 2`). On the real tree, every module
  `generate.py` imports reached it only as a .pyc, so no import of the generator was judged.
- *Fix (a), at run time:* at its end the TRACER lists every module the run loaded, with the file it came from and its
  source (`importlib.util.source_from_cache` for a .pyc). `undeclared` judges a module's source like an opened path. A module
  loaded from inside the repository with no tracked source (a sourceless .pyc, an untracked module, a compiled extension) is
  a failure that names it.
- *Fix (b), static:* `static_check` (part of `buildgraph.py check`) resolves the program's import closure through
  `inert_lane.import_closure`, the reader `code_readers` uses. That closure covers every import, a lazy one included,
  resolved through each `sys.path` edit of the chain. A module outside the declared inputs is a finding, decided before any
  run. `inert_lane`'s `_import_closure` and `_static_dir` became public (`import_closure`, `static_dir`, and the extracted
  `static_names`), and every caller changed. The closure named `scripts/scratch_repo.py`, which the self-tests import
  lazily, so it is now declared with that reason.

**R1-2 (medium): any read of the generator's program by a Conformance source counted as "through the dependency".**
- *Scenario* (`audit_probe.py`): a test that runs `generate.py --check` reads the inventory, the catalogs and the ISO text,
  none of them in Conformance's key. The audit filed that read under `through` and stayed GREEN.
- *Fix:* the program is reached through the dependency only at its ONE hand-off site, the source that names both the
  variable (`WISEOWL_COBOL_GATE_SUITE`) and the own-generation mark (`GENERATED-OWN  conformance-suite`). Today that source
  is `SuiteManifest`. Any other source that runs or reads the program is an undeclared read, reported as "reads every input
  of conformance-suite, and none is in this target's key". A dependent assembly with no such site is a finding.
- *Inside the gate the fallback cannot stand.* `SuiteManifest.GenerateOnce` records `GENERATED-OWN  conformance-suite` in the
  harness observation log when it was handed nothing. The gate reads each dependent host's `<run>/<asm>.observations.log`
  after the hosts (`_check_generated`). The mark there is RED (`GENERATED BY THE HOST`), and no pass is recorded.
- *Which runs are keyed:* only the gate's. Its hosts run the handed suite, so the key a pass is recorded under is that
  suite's digest. A hand `dotnet test` or a CI run generates its own suite, records the mark in its own log, and records no
  pass in the store. `--rederive` of a run that predates the hand-off is the one exception, named here as a residue: such a
  run's Conformance host generated its own suite from the run's recorded tree, and a re-derived pass is keyed on the digest
  the store records for that tree. It is right only to the extent the generator is deterministic, which the three-run proof
  below shows.
