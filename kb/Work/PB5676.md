# PB5676 - COBOL0823 misstates why INVOKE of an unexpanded parameterized class is refused

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/OoBinder.cs#OoBindByReceiver` (the INVOKE receiver tail that reports `DiagnosticCatalog.InvokeMethodNameInvalid` after `Compiler.Oo.OoNameResolution.Lookup(..., Want.Class)` finds no class and no formal parameter); the parameterized ground the other arms state comes from the USAGE OBJECT REFERENCE (COBOL0813) and USE AFTER EXCEPTION OBJECT (COBOL0859) screens.

**The refusal is right; its wording is not.** Determination `D-PARAMETERIZED-UNEXPANDED` (`docs/conformance/3/`, kb/Work PB5625 reading A) refuses, at every edition, a reference outside the REPOSITORY paragraph to a parameterized class or interface that the REPOSITORY lists without the EXPANDS phrase. The USAGE OBJECT REFERENCE arm (COBOL0813) and the USE AFTER EXCEPTION OBJECT arm (COBOL0859) state that ground: "'P18PC' is a parameterized class or interface (its CLASS-ID / INTERFACE-ID paragraph has a USING clause), which may be specified only in the REPOSITORY paragraph — reference an expansion of it, declared with the EXPANDS phrase". The INVOKE arm instead says the name is "neither a resolvable data item nor a class this source element may reference", which is false for a class the REPOSITORY lists and names no ground the user can act on. The defect is the wording and the missing ground, not the refusal. (The §2023 citation at `--std 2002` is PB4950's, as for the other two arms.)

## The fix

The INVOKE arm reports the same ground COBOL0813 and COBOL0859 give (one message for every operand position that names an unexpanded parameterized class or interface), and a negative golden pins the text at 2002 and 2023. Sweep the other positions a class-name can take (`NEW` on an object reference typed by it, a method's RETURNING/USING `OBJECT REFERENCE`, `TYPE`-style references, a conformance check in SET) for the same generic message.
