## Row `GR-9.1.13.2-3` — PARTIAL (editions 85,2002,2014,2023 (E.2 item 15: the 2023 text only clarifies WHEN '04' is set))

Rule (cite.py --check 9.1.13.2 "A READ statement is successfully executed but the physical record from the file is shorter than or longer than the minimum or maximum length" -> OK §9.1.13.2 3)); its statement-level twin is §14.9.30.4 GR14 (record sequential). SequentialConnector.Read: shortLong = IsVarying ? len<VaryMin || len>VaryMax : len<RecordWidth; the record is delivered (Fit truncates on the right) and the READ is successful. Line sequential is excluded (its conditions are '06'/'09'), keyed files carry record sizes in the framed store header so a mismatch is the OPEN's '39' (§14.9.27.4 GR10; kb/Work PB802), never a READ-time '04'. Probe out/probe/iostat-04 (RECORD VARYING 1..20 written, read through VARYING 3..10): 15-byte record -> 04 truncated to 10, 2-byte record -> 04, 5-byte -> 00, then 10: both the longer and shorter legs verified. Golden io_status_04 pins the fixed-length short final record. || REFUTED: PARTIAL — Only the RECORD VARYING leg is verified. For a fixed-length record-sequential file the physical record length is not kept: the reader slices the byte stream in its own RecordWidth chunks, so a physical record LONGER than the reader's maximum is never seen as one record and never gets '04' - it is delivered as several records each reported '00'. The code comment 'a longer-than-max record cannot occur (the frame is read in RecordWidth chunks)' is a deduction that measurement refutes. The cited golden io_status_04 pins the same fragmentation on the short side (two 5-byte physical records merged into one 10-byte record reported '00').

## What the fixer owes

Decide (and document in CONFORMANCE.md, the file-format determination) how a fixed-length record-sequential physical record's LENGTH is known — a record frame, or the documented rule that a fixed file is a stream of max-length records — and make READ report '04' when the physical record's length differs from the fixed length, as the VARYING arm already does. The golden io_status_04 currently PINS the merged-short-record behaviour; re-derive it from the rule. Goldens: a long and a short physical record in a fixed file.

## Landed (wave 67, w67p)

Decided and documented rather than re-framed: `docs/CONFORMANCE.md` DOC-A.1-146 (a) now states that a
fixed-length record sequential file records NO record boundaries — §9.1.7.2 makes the length "determined by any
information the implementor may add to the record on the physical storage medium", and this format adds none
(GnuCOBOL's fixed-length format, CLAUDE.md rule 1; PB802's no-sidecar decision) — so the physical record IS the
next integer-1 bytes of the READING description. A physical record is then never longer than the maximum by
definition, and shorter only at the end of the file: the '04'. The code comment that deduced "cannot occur" now
cites that determination (`SequentialConnector.ReadRecord`). The golden `2002/io_status_04` is re-derived: it
displayed the record area beyond the bytes read, which §14.9.30.4 GR14 makes UNDEFINED, and now shows only the
bytes read; it gains a leg writing one 15-byte record and reading it as a 10-byte '00' record and a 5-byte '04'
record. Re-probed: pf.cob (20 bytes read through RECORD CONTAINS 10) → two '00' records, as the determination
requires.
