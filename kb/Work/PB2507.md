# PB2507

Filed by the w1033 clerk from the PB1643 decision (`E:\COBOL-coord\scratch\w1033-adj\PB1643-decision.md` section 4, "Lead, same family, different site") and refuter (section 3.2).
The decision says it "needs its own kb/Work note or the same change set" as `PB1643`; it is filed separately and the two should land together.

**Observed (pinned build `pin-97006f3`, DECIMAL-POINT IS COMMA; `PB1643\dpf.cob`, emitted `dpf.g.cs:43,45`).** `DISPLAY FUNCTION NUMVAL("1,5")` prints `1.5` (GnuCOBOL 3.2.0: `00000001,5`);
`FUNCTION MAX(1,5 2,25)` prints `2.25` (GnuCOBOL: `2,25`); `MAX(X Y)` likewise. The refuter (`PB1643-refute.md` section 3.2): none of the intrinsics folds at compile time (ABS, MIN, SUM, REM and
even `MAX(3 7)` are run-time calls), so the fix cannot be a literal-only change, and `DISPLAY 1,5` and `DISPLAY FUNCTION ABS(1,5)` must agree.

**Expected.** `§12.3.7.4 GR14` (cite.py --check OK per the decision): with the clause the decimal separator is the comma; every run-time separator the standard itself produces follows it (`§15.3.3.2`
time formats, NUMVAL arguments). `§14.9.11.4 GR1` leaves the device conversion to the implementor, so as for PB1643 the precedence order applies and GnuCOBOL decides (the comma).

**Site.** `src/Cobol.Net.Runtime/Values/Numeric/CobolNum.cs#FormatFunctionText` (line 846; `FormatFunctionText(Int128, int, bool deSign)` has no comma parameter) and
`src/Cobol.Net.Runtime/Values/Numeric/CobolDec.cs#ToFunctionText` (line 858). `docs/CONFORMANCE.md` DOC-A.1-92 fixes "a decimal point followed by exactly the result's scale" and does not
mention DPC: amend it with the fix. Not affected (agree in both compilers): a PICTURE-less float, `FUNCTION SQRT` (via `CobolFloat.Display`).

## Landed - 2026-10-08 (wave 1042 group F)

Re-probed on the wave-1042 build (`E:\COBOL-coord\scratch\w1042f\p2507.cob`): `NUMVAL("1,5")` printed `1.5`, `MAX(1,5 2,25)` / `MAX(X Y)` `2.25`, `ABS(N)` `1.50`,
`SUM(X Y)` `3.75`, `REM(7,5 2)` `1.5`, `NUMVAL-C("1.234,5")` `1234.5`, and the folded `HIGHEST-ALGEBRAIC(X)` / `LOWEST-ALGEBRAIC(N)` `9.99` / `-9.99` -- confirmed, and wider
than the note: the FOLD and the materialized temporary were two more arms of the same spelling.

- **Mechanism.** The literal form of a numeric function value is built in ONE runtime place, `CobolNum.FormatFunctionText` (`CobolDec.ToFunctionText` delegates), and the
  decimal point was a hard-coded `.`. It now takes `commaMode`; the emitter passes the EVALUATING unit's mode on every lane that writes the text:
  `OperandText.NumericExprText` (the native call and the SDIDI call; `NumericRenderer.UnitDecimalPointIsComma` is the one CodeGen reader of the unit's mode),
  the materialized §15.4 temporary (`DataItem.FunctionValueSeparator`, set by `SendingValueTemp.Materialize`, replacing the `IsFunctionReturnedValue` bool so the temporary
  cannot say "function value" without saying how to spell it), and the compile-time fold (`IntrinsicBinder.BindIntrinsicCore` sets the folded literal's `DecimalSeparator`, so
  `BoundNumericLiteral.Image` -- PB1643's mechanism -- spells it). `RuntimeApi.NumFormatFunctionText` / `DecFunctionText` take the mode as a REQUIRED parameter. The compile-time C#-facing
  radix (`AlgebraicRanges.Decimalize`) keeps the default `.`: it is never COBOL source.
- **Sibling arm fixed in the same function.** `FormatFunctionText` negated the signed value to take its magnitude, so `Int128.MinValue` printed `--1701...`; it now uses the unsigned
  magnitude (`CobolDec.UAbs`), the PB2641 mechanism.
- **Determination.** `docs/CONFORMANCE.md` DOC-A.1-92 gained the separator arm (the comma, GnuCOBOL 3.2's, on every lane); a float result keeps `CobolFloat.Display` (agrees in both compilers).
- **Pins.** Goldens `85/pb2507_function_result_decimal_comma` (NUMVAL, MAX, SUM, REM, NUMVAL-C, INTEGER, contained program), `2023/pb2507_function_result_decimal_comma_native`
  (ABS, folded algebraic extremes), `2023/pb2507_function_result_decimal_comma_standard_decimal` (SDIDI lane); `FunctionTextDecimalPointTests` (the `--permissive` MOVE of a noninteger function,
  one receiver and two, plus the no-clause control); `FunctionTextImageTests`; `DecimalPointModeDriftTests` allowlist. No negative: no edition below 85 and the rule does not differ by edition.
