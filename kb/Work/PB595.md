# PB595 — OPEN — a flat ban the owner recorded, and nothing enforces it

Reported by the golden-lane round-3 `misc-p3` writer (it is what forced the refuter to overturn
`GR-14.9.28.4-22`: the draft golden wrote the banned construct in two of its arms, so the fixture was not legal
COBOL and the arms were moved to AFTER `END-PERFORM`). **Re-probed by the lander before this note was filed.**

## The rule and the decision

`specs/ISO_COBOL.md` §7.3.25.3 SR5 — *"A TURN directive shall not be specified within an exception processing
PERFORM statement."*

`docs/COBOLNET_REARCHITECTURE_PLAN.md` §6 **D20** (2026-07-19) settles the reading:

> ✅ **FLAT BAN, SUPPRESSIBLE WARNING.** A `>>TURN` written anywhere lexically within a format-3 PERFORM —
> `imperative-statement-1` included, not just the handler phrases — draws a suppressible conformance warning
> citing §7.3.25.3 SR5; the program still compiles (§4.2.2 requires only an optionally-invoked warning for
> syntax-rule violations), and §14.9.28.4 GR14 sentence 4's semantics are still implemented for the accepted
> case. Use **ONE shared lexical-containment predicate** for TURN/PUSH/POP (singular-mechanism rule) — do not
> build a second region-partitioned predicate.

The decision even records the REJECTED narrow reading so it is not re-litigated. Everything is settled; only the
implementation is missing.

## The repro (this tree, 2026-09-05, `--std 2023`)

```cobol
       PERFORM
       >>TURN EC-OVERFLOW-STRING CHECKING ON
               STRING "ABCDEFG" DELIMITED BY SIZE INTO WS-D
           WHEN EC-OVERFLOW-STRING
               DISPLAY "C-WHEN"
           END-PERFORM.
           DISPLAY "DONE"
```
```
C-WHEN
DONE
exit 0
```

**No diagnostic of any kind.** Expected: a suppressible conformance warning citing §7.3.25.3 SR5, the program
still compiling and still printing `C-WHEN` / `DONE`.

## Why it is worth more than a warning's weight

The construct is not inert. §14.9.28.4 GR14 brackets the statement in an implicit `PUSH ALL` + `TURN … OFF ALL`
… `POP ALL`, so a user's `>>TURN … ON` inside that bracket is unwound at `END-PERFORM` while a reader expects it
to persist — §7.3.25.4 GR6's "checking remains enabled for every qualifying procedure division statement that
follows" is exactly the expectation the bracket defeats. Silence here means the surprise is delivered at run
time, in exception-checking state, which is the hardest thing in this language to debug backwards.

## The shape D20 already chose

⛔ **One shared lexical-containment predicate for TURN, PUSH and POP** — not three call sites and not a
region-partitioned second mechanism. `>>PUSH` and `>>POP` carry the sibling bans (§7.3.20.3 SR4, §7.3.22.3 SR4,
both worded "exception checking PERFORM"), and D20's own rationale turns on the two phrasings being drafting
synonyms, so one predicate answering "is this directive lexically inside a Format-3 PERFORM" serves all three.
Add its drift test in the same change set so a fourth directive of the shape is automatic.

⚠ A related staged-GAP finding from the same writer belongs to whoever takes this: the SR16 code path's comment
names a diagnostic code that is no longer emitted, so the staged sub-GAP's only record points at nothing. Verify
and re-word it while in the file — a staged GAP whose sole record is a comment naming a removed diagnostic is an
undocumented silent acceptance.
