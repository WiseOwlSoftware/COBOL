# PB595 — LANDED — a flat ban the owner recorded, and nothing enforced it

Reported by the golden-lane round-3 `misc-p3` writer (it is what forced the refuter to overturn
`GR-14.9.28.4-22`: the draft golden wrote the banned construct in two of its arms, so the fixture was not legal
COBOL and the arms were moved to AFTER `END-PERFORM`). **Re-probed by the lander before this note was filed.**

## The rule and the decision

`specs/ISO_COBOL.md` §7.3.25.3 SR5 — *"A TURN directive shall not be specified within an exception processing
PERFORM statement."*

`docs/COBOLNET_REARCHITECTURE_PLAN.md` §6 **D20** (2026-07-19) settles the reading:

> ✅ **FLAT BAN, SUPPRESSIBLE WARNING.** A `>>TURN` written anywhere lexically within a format-3 PERFORM —
> `imperative-statement-1` included, not just the handler phrases — draws a suppressible conformance warning
> citing §7.3.25.3 SR5; the program still compiles (§4.2.2 requires only an optionally-invoked warning for
> syntax-rule violations), and §14.9.28.4 GR14 sentence 4's semantics are still implemented for the accepted
> case. Use **ONE shared lexical-containment predicate** for TURN/PUSH/POP (singular-mechanism rule) — do not
> build a second region-partitioned predicate.

The decision even records the REJECTED narrow reading so it is not re-litigated. Everything is settled; only the
implementation is missing.

## The repro (this tree, 2026-09-05, `--std 2023`)

```cobol
       PERFORM
       >>TURN EC-OVERFLOW-STRING CHECKING ON
               STRING "ABCDEFG" DELIMITED BY SIZE INTO WS-D
           WHEN EC-OVERFLOW-STRING
               DISPLAY "C-WHEN"
           END-PERFORM.
           DISPLAY "DONE"
```
```
C-WHEN
DONE
exit 0
```

**No diagnostic of any kind.** Expected: a suppressible conformance warning citing §7.3.25.3 SR5, the program
still compiling and still printing `C-WHEN` / `DONE`.

## Why it is worth more than a warning's weight

The construct is not inert. §14.9.28.4 GR14 brackets the statement in an implicit `PUSH ALL` + `TURN … OFF ALL`
… `POP ALL`, so a user's `>>TURN … ON` inside that bracket is unwound at `END-PERFORM` while a reader expects it
to persist — §7.3.25.4 GR6's "checking remains enabled for every qualifying procedure division statement that
follows" is exactly the expectation the bracket defeats. Silence here means the surprise is delivered at run
time, in exception-checking state, which is the hardest thing in this language to debug backwards.

## The shape D20 already chose

⛔ **One shared lexical-containment predicate for TURN, PUSH and POP** — not three call sites and not a
region-partitioned second mechanism. `>>PUSH` and `>>POP` carry the sibling bans (§7.3.20.3 SR4, §7.3.22.3 SR4,
both worded "exception checking PERFORM"), and D20's own rationale turns on the two phrasings being drafting
synonyms, so one predicate answering "is this directive lexically inside a Format-3 PERFORM" serves all three.
Add its drift test in the same change set so a fourth directive of the shape is automatic.

⚠ A related staged-GAP finding from the same writer belongs to whoever takes this: the SR16 code path's comment
names a diagnostic code that is no longer emitted, so the staged sub-GAP's only record points at nothing. Verify
and re-word it while in the file — a staged GAP whose sole record is a comment naming a removed diagnostic is an
undocumented silent acceptance.

## LANDED — 2026-09-21 (wave 42, group C)

D20 is implemented as ONE lexical-containment predicate over recorded directive SITES, and it decides all three
bans — §7.3.25.3 SR5 (TURN), §7.3.22.3 SR4 (PUSH) and §7.3.20.3 SR4 (POP). Note the clause pairing: the note's
own sentence gave PUSH §7.3.20.3 and POP §7.3.22.3, which is REVERSED — `cite.py --check` on both put POP at
§7.3.20.3 SR4 and PUSH at §7.3.22.3 SR4, and the code and the diagnostics carry the checked pairing.

**Why a SITE list and not a tree walk.** A compiler directive is removed by the preprocessor and appears in no
parse tree, so "lexically inside this statement" is a question about POSITIONS.
`Frontend.Preprocessor.DirectiveSiteProcessor` records each position-ruled directive's `(Line, Word)` on the
FINAL text — the one frame in which a directive line number and a parser token line number are the same number
(every stage after the conditional-compilation driver is line-count preserving, hazard H3) — and the binder tests
each site against the Format-3 PERFORM's own `[Start.Line, Stop.Line]` span in `CheckDirectiveBans`, beside the
other region-B cross-statement bans. `>>PUSH` / `>>POP` used to be consumed by the conditional-compilation
driver, which runs before COPY has settled the line frame and therefore cannot name the resultant line a
directive ended on; they are now in `Frontend.LeftDirectives` and consumed by the site stage instead. That is a
position-only change: their §7.3.20 / §7.3.22 directive-state semantics were unimplemented before and are
unimplemented now, and the stage is where they land.

**The diagnostic** is `COBOLNET2187`, an `EditionSeverity.Warning` (suppressible by code through the
`--suppress` family), one row per banned directive so each violation quotes ITS OWN rule rather than an
intersection of the three. Nested Format-3 PERFORMs report a contained directive ONCE: the rule is about the
directive, not about each enclosing statement.

**The message was corrected against the standard before it shipped.** The draft said GR14's bracket "unwinds"
the directive at END-PERFORM — but GR14 reads "An implicit PUSH ALL followed by TURN OFF ALL is assumed at the
end of imperative-statement-1. Immediately preceding the END PERFORM phrase, there is an implicit POP ALL …", so
the POP restores the state as of the END of imperative-statement-1, which INCLUDES a directive written inside
imperative-statement-1 (D20 itself records that the narrow reading noted its "specified survival"). The shipped
message therefore states only what the rules state: a directive in a WHEN or FINALLY phrase is discarded by that
POP ALL, and one in imperative-statement-1 competes with the implicit TURN directives GR14 assumes around it.

Witnesses: `tests/conformance/2023/pb595_turn_inside_format3_perform` (the "still compiles, still runs" half —
`L1=WHEN` proves GR14's own semantics are unaffected, `L2=CONTINUED` proves the violation did not reject) and
the six `ExceptionCheckingPerformDirectiveBanDriftTests` pins, including the CONTROL (the same three directives
written before the PERFORM and after END-PERFORM draw nothing) and the table/scanner agreement pin, so a fourth
position-ruled directive is one row in two places and no new mechanism. No negative fixture: the program is
ACCEPTED, and the below-2023 gate for the whole statement is already witnessed by
`conformance:negative/pb441-f3-perform-below-2023`.

Rows closed: `SR-7.3.25.3-5`, and the two PUSH/POP siblings the one predicate also answers — `SR-7.3.22.3-4`
and `SR-7.3.20.3-4` (GAP 2335 → 2332).

**The related finding this note carried was a STALE COMMENT, not a silent acceptance — and the difference was
measured, not deduced.** It is not the SR16 path (that one emits COBOLNET1601 at its own site, exactly as its
comment says) but `ResolveWhenOperands`' open-mode arm, whose comment said the runtime match was "covered by the
one COBOLNET0899 raised at the top of EcBindExceptionPerform". That diagnostic is indeed raised nowhere on the
Format-3 path any more (`grep -rn "COBOLNET0899" src/ --include=*.cs`) — but the reason is that the sub-form is
IMPLEMENTED, not deferred: §14.9.28.4 GR17 sends the match to "General rules 3a to 3g of the USE statement", and
`ControlFlowEmitter` emits `WHEN EXCEPTION INPUT | OUTPUT | I-O | EXTEND` as the GR3b tier-1 arm
(`IsIoName(__ec) && __f is not null && OpenModeOf(__f) == <mode>`). Probed on this tree: a READ past
end-of-file inside `PERFORM … WHEN EXCEPTION INPUT … END-PERFORM` runs the handler (`MODE-WHEN`, exit 0). The
comment is re-worded to the measured truth, and `COBOLNET_CONDITIONS_EXCEPTIONS_DESIGN.md` D12's staged list —
which contradicted its own decision (c) in the same section — drops the open-mode entry. Nothing to register:
the first draft of this paragraph asserted a gap the code does not have, which is the failure mode this project
calls "a remembered pattern is a hypothesis".
