# PB957 — OPEN — a documented decline with no owner and fourteen rows

## Repro — measured, both spellings

`scratchpad/reg9/probe/rword.cob` (PROGRAM-ID `R9RWORD`), `cobol.exe rword.cob --std 2023`:

```
       01  DET-P TYPE DE NEXT GROUP PLUS 2.
           02  LINE PLUS 1. …
```

```
  rword.cob(12,8): error COBOLNET0899: RD 'R-P': the NEXT GROUP clause (ISO §13.18.37) is not yet implemented
```

Delete the clause and the identical program compiles clean (`rword2.cob`, exit 0, no diagnostic). The `+`
spelling adds a parse error on top (`rplus.cob(12,37): error COBOL0001: unexpected '+'`) because
`reportNextGroupClause` admits only the WORD — that half is [[PB951]]'s mechanism and the same one-line
alternation fixes it, but it is unreachable until this note lands.

## Rule and posture

The clause is printed at §13.18.37.2 (`NEXT GROUP IS { integer-1 | {PLUS|+} integer-2 | NEXT PAGE [WITH RESET] }`,
figure note: *"Both the outer and the inner delimiters are braces — exactly one alternative shall be selected in
each"*), with seven syntax rules and six general rules. Two `--check`ed here:

```
$ python scripts/spec/cite.py --check 13.18.37.3 "PLUS and + are synonyms"
OK  §13.18.37.3   (Syntax rules)      2. PLUS and + are synonyms.
```

**The posture is DOCUMENTED, and documented is not owned.** `docs/CONFORMANCE.md` A.4.11 (Report Writer,
*Partial*) names *"the NEXT GROUP clause"* in its "Staged LOUD (COBOLNET0899 band)" sentence, alongside seven
other report-writer items. So the compiler's conformance statement is honest — and the work register has no
note for it, which is how it can sit at fourteen GAP rows with nothing ranking it. Every one of
`FMT-13.18.37.2`, `SR-13.18.37.3-1…7` and `GR-13.18.37.4-1…6` is verdict `''`, state `GAP`, and was owned by
NO note before this one (measured against every `inventory_rows:` list in `kb/Work/`).

⚠ For the register, not for this note's fixer: the other seven items in that same A.4.11 sentence should each
be checked for an owner the same way. That is a question about the register's coverage, not a new work list —
the list already exists, in the conformance statement, and `DefectiveRowCoverageDriftTests` cannot see these
rows because an UNADJUDICATED row is not a defective one.

## What the fix is

§13.18.37.4's six general rules decide where the NEXT body group begins after this one is presented — the same
`ReportWriter` vertical-position machinery [[PB565]] and [[PB484]] just made coherent (`SubsequentTarget`, the
per-presentation anchors, `LINE-COUNTER` holding the last line PRINTED per §13.18.35.4 GR1). This is the next
increment on that engine, not a new one, which is why those two notes are in the `cluster`: an implementer who
has just read that code closes this cheaply, and one who has not will re-derive it.

⭐ The `WITH RESET` phrase is part of the printed format and part of the feature (CLAUDE.md rule 3 — the
COMPLETE clause, not the part a test references): it resets PAGE-COUNTER, so it is bound up with
§8.4.3.15.3's counter rules that [[PB429]] landed. A landing that implements integer-1/PLUS integer-2 and
stages `NEXT PAGE WITH RESET` loud is a new, smaller decline — which is debt, and an owner decision, not a
default.

## Goldens the fix owes

One positive at the introducing edition driving all three alternatives (absolute, relative in BOTH spellings —
`PLUS 2` and `+ 2` — and `NEXT PAGE [WITH RESET]`), every printed line DERIVED from §13.18.37.4 before the run;
one negative per syntax rule that can be violated in source; and the edition gate below the introducing
edition.
