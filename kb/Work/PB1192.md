## Finding — `write-statement-p2` (crashes; rows `GR-14.9.51.4-29`)

**Mechanism.** RelativeConnector has no highest permitted relative record number: RelativeConnector.Write's random/dynamic arm tests only `key < 1` for §14.9.51.4 GR29 b)'s '34', so any positive key is accepted, and RelativeConnector.Persist sizes its frame array as `new string?[_st.Highest]` — a large key kills the run unit at CLOSE with System.OverflowException (and a key in the millions allocates that many slots at every CLOSE).

**Repro.** SELECT RV ASSIGN TO 'r.dat' ORGANIZATION RELATIVE ACCESS RANDOM RELATIVE KEY RK FILE STATUS FS. 01 RK PIC 9(18). OPEN OUTPUT RV. MOVE 999999999999999999 TO RK. WRITE RVR. DISPLAY FS. CLOSE RV. (E:/Temp/claude/E--CobolSharp/a700c052-f9e4-4942-84ff-a13c7505d6ec/scratchpad/adj-d1/out/probe/write-p2/pe.cob)

**Expected from the spec.** The key exceeds the highest relative record number permitted for the file (an implementation limit that must at least be what the store can represent), so the WRITE is unsuccessful with I-O status '34', nothing is written, and the CLOSE completes normally (§14.9.51.4 GR29 b) last sentence; §14.9.51.4 GR15).

**Observed / reasoning.** Measured: WRITE reports '00'; CLOSE throws an unhandled System.OverflowException from RelativeConnector.Persist and the run unit dies, leaving a 20-byte file.

**Code site.** src/Cobol.Net.Runtime/IO/RelativeConnector.cs#RelativeConnector.Write; src/Cobol.Net.Runtime/IO/RelativeConnector.cs#RelativeConnector.Persist

## Finding — `write-statement-p2` (crashes; rows `GR-14.9.51.4-20`)

**Mechanism.** No sequential WRITE arm can produce I-O status '34': FileStatusCode.PermanentBoundary has one producer in the runtime (RelativeConnector.Write, GR29 b)), no sequential write path catches IOException, and CONFORMANCE.md defines no externally-defined boundary for a sequential physical file as §9.1.13.6 item 3 requires the implementor to specify. IoStatusClass.WriteBoundary (the SORT GR15 / MERGE GR12 implicit-WRITE terminator) therefore tests for a sequential '34' nothing emits.

**Repro.** Any sequential WRITE loop against a file on a full volume (or a quota-limited directory): OPEN OUTPUT F. PERFORM UNTIL FS NOT = '00' WRITE F-REC END-PERFORM. DISPLAY FS. — reasoning from the code, not probed (needs an exhausted medium).

**Expected from the spec.** The first WRITE past the implementor-defined boundary is unsuccessful with '34', the loop ends and DISPLAY shows 34 (§14.9.51.4 GR20; §9.1.13.6 item 3), and the implementor documents how the boundary is defined.

**Observed / reasoning.** By reading: SequentialConnector.Write/WriteAdvancing/EmitLineSequentialRecord write through a StreamWriter with no IOException handling, so an exhausted medium surfaces as an unhandled System.IO.IOException (killing the run unit) or, if the failure lands in the CLOSE flush, a '30' on the CLOSE — never '34' on the WRITE.

**Code site.** src/Cobol.Net.Runtime/IO/SequentialConnector.cs#SequentialConnector.Write; src/Cobol.Net.Runtime/IO/SequentialConnector.cs#SequentialConnector.WriteAdvancing; src/Cobol.Net.Runtime/IO/FileStatus.cs#FileStatusCode.PermanentBoundary

## Finding — `write-statement-p3` (crashes; rows `GR-14.9.51.4-33`, `GR-14.9.51.4-42`)

**Mechanism.** Relative and indexed files have no externally-defined boundary, so GR33 b)'s and GR42 d)'s '24' is never produced. RelativeConnector.Write accepts any RRN of 1 or more, and IndexedConnector.Write has no size test; grep finds BoundaryViolation only on RelativeConnector's RELATIVE KEY digit-overflow arm (GR33 c). The store's real ceiling is RecordFraming.WriteStore: it writes a 4-byte gap tag for EVERY empty relative slot up to the highest RRN, into a MemoryStream flushed through `(int)composed.Length`. A WRITE past that ceiling is reported '00' and fails later, at CLOSE. §9.1.13.5 4) requires the implementor to specify the boundaries, and docs/CONFORMANCE.md has no such determination. Separately, a relative key below 1 gets '34' (GR29 b's explicit sentence). GR33 b) with §9.1.13.5 4) would make a relative boundary violation '24', and §9.1.13.6 3) confines '34' to sequential files. The standard contradicts itself here and no determination records which sentence governs, which matters because '34' does not take the INVALID KEY branch and '24' does.

**Repro.** out/probe/write-statement-p3/rel2.cob: RELATIVE, ACCESS RANDOM, RELATIVE KEY RKD PIC 9(12); OPEN OUTPUT; MOVE 5000000 TO RKD; WRITE; CLOSE. Then rel1.cob: MOVE 0 TO RKD; WRITE D-REC INVALID KEY ... NOT INVALID KEY ...

**Expected from the spec.** §9.1.13.5 4) (--check OK): '24' when 'an attempt is made to write outside the externally-defined boundaries of a physical relative or indexed file. The implementor specifies the manner in which these boundaries are defined.' §14.9.51.4 GR33 b) and GR42 d) say the same for WRITE. A defined, documented boundary (for example the largest RRN, or the store size the framing can hold) must produce '24' AT THE WRITE, with the INVALID KEY branch and no record released. It must not be a '00' followed by a failure at CLOSE. The key<1 status needs a CONFORMANCE.md determination choosing between GR29 b)'s '34' and GR33 b)/§9.1.13.5 4)'s '24'.

**Observed / reasoning.** Measured: rel2 gives 'OK 00' / 'CLOSE 00' and a 20,000,024-byte store for ONE record (4 bytes of gap tag per empty slot). rel1 with RKD=0 gives 'Z 34' and runs neither the INVALID KEY nor the NOT INVALID KEY branch. Reasoned, not run because of its memory and disk cost: a key in the high hundreds of millions (legal for PIC 9(9) and wider) makes the frame list and the MemoryStream exceed Int32/2 GB, so CLOSE throws (OutOfMemory / 'Stream was too long') after the WRITE reported '00'. Indexed files hit the same MemoryStream ceiling as the record count grows. The harm label 'crashes' rests on that reasoning; the measured part is a '00' where a documented boundary would give '24'.

**Code site.** src/Cobol.Net.Runtime/IO/RelativeConnector.cs#Write; src/Cobol.Net.Runtime/IO/IndexedConnector.cs#Write; src/Cobol.Net.Runtime/IO/RecordFraming.cs#WriteStore

## What the fixer owes

Define and DOCUMENT (CONFORMANCE.md, the §9.1.13.5 4) / §9.1.13.6 3) determinations) a boundary per organization — the largest RRN / store size RecordFraming.WriteStore can represent (it writes a 4-byte gap tag per empty slot through `(int)composed.Length`), an indexed record-count/size ceiling, and a sequential medium-exhaustion mapping (catch IOException on the write paths → '34') — and test it AT THE WRITE, with the INVALID KEY branch for '24' and no record released. IoStatusClass.WriteBoundary (SORT GR15 / MERGE GR12's implicit-WRITE terminator) tests for a sequential '34' nothing emits — it becomes live. ⚠ OWNER VISIBILITY: the key<1 status is a contradiction in the standard (GR29 b)'s '34' vs GR33 b)/§9.1.13.5 4)'s '24' vs §9.1.13.6 3) confining '34' to sequential files) — record the determination; it matters because '34' does not take INVALID KEY.

**Mechanism.** The two required 'externally-defined boundaries' determinations (Annex A.1 items 107 and 108) are neither made nor documented, and the statuses they govern have no producer: '24' for a relative/indexed WRITE outside the file's boundaries (IndexedConnector.Write has no '24' arm; §14.9.51.4 GR42 d / GR33 b) and '34' for a sequential WRITE outside them (§14.9.51.4 GR20). The one host event that a surveyed implementation classes as such a boundary (GnuCOBOL: out-of-space/file-too-large -> 34) reaches the sequential WRITE as an uncaught IOException (see the first finding).

**Repro.** Code search: grep -rn 'PermanentBoundary\|"34"\|BoundaryViolation' src/Cobol.Net.* -> RelativeConnector.cs:373 ('24', RRN digits) and :386 ('34', key<1) only; docs/CONFORMANCE.md has no DOC-A.1-107 / DOC-A.1-108 entry; tests/version-matrix/traceability-inventory.json rows DOC-A.1-107 and DOC-A.1-108 are GAP. A behavioral repro needs a size-limited volume (device full) - not runnable on this host.

**Expected from the spec.** Annex A.1 107)/108) require the implementor to define and document 'the manner in which the boundaries of a file are defined' for '24' and '34'; §9.1.13.5 4) and §9.1.13.6 3)/4) a) then set '24' (invalid key, relative/indexed) or '34' (permanent error, sequential) when a WRITE crosses them. Precedence (CLAUDE.md rule 1): the ISO text leaves the manner to the implementor, so GnuCOBOL's choice (space exhausted / file-size limit on WRITE -> 34 for sequential) is the candidate, documented in CONFORMANCE.md.

**Observed / reasoning.** Reasoned from the code search plus the absence of the determinations; the sequential half's observable today is a crash (unhandled IOException), the keyed half surfaces as '30' at CLOSE when the store cannot be persisted.
