## Landed (wave 20261868 F)

Re-probe on the wave's build: `FIND-STRING(X9 "ABC" (I2))` compiled and printed `0007` (reproduced). After the fix it is refused,
COBOL1627 "argument-3 is an arithmetic expression, not an integer data item or integer literal, ISO 15.37.3 r3"; the bare item and
the bare literal still return 7, and `BASECONVERT("1A" 16 (10))` is refused the same way. `cite.py --check` OK for 15.37.3 3),
15.37.4 2), 15.12.3 1), 8.8.1.2 1), 8.4.3.2.3 8).

- **The mechanism.** `BindArgOperandCore` mapped a bound expression through `OperandOf`; the expression binder drops grouping
  parentheses, so `(I2)` became I2's `BoundNumRef` and `(3)` the literal 3, and a "data item or literal" position could not see an
  arithmetic expression. The argument binder now asks the written shape (`SoleOperand.Unparenthesized`, the activation arm's
  question) and wraps such a parenthesized sole item or literal as the `BoundComputedOperand` it is. The activation arm had it
  since PB3760; this is the intrinsic arm.
- **Siblings.** Every other bound shape was already a computed operand (`OperandOf` default). The other `OperandOf` callers are
  statement operands with their own sole-shape arms (PB1935 `CompoundOperand`), not intrinsic arguments. Parenthesized
  alphanumeric items as string-function arguments (`TRIM((X9))`, `LENGTH((X9))`, `INTEGER-OF-FORMATTED-DATE(... (WD))`) are now
  refused too, by their own class and data-item rules, because they are arithmetic expressions.
- **Goldens.** `pb4635_parenthesized_numeric_arguments` (accept 2023; numeric positions keep working with parentheses); negatives
  `pb4635-findstr-parenthesized-item` and `pb4635-baseconvert-parenthesized-literal`.
- **Review round 1 (R1-1, R1-2).** The first wrap bound a parenthesized sole item with the function-argument context, which
  suspends the section 8.8.1.1 class screen, so `ABS((X9))` over a PIC X item digit-decoded. An argument that is not a sole
  unparenthesized operand is now bound through the screened `BindExpr` (COBOL0844 for an alphanumeric, numeric-edited, group, index,
  pointer or boolean item); the same change closes the pre-existing sibling `ABS(X9 + 1)`, which digit-decoded under STRICT. The
  wrapped operand also lost the function's Integer result type (`IsIntegerOperand` answers false for a computed operand), so
  `PERFORM FUNCTION MAX((I2) 1) TIMES` was COBOL1646 and `FACTORIAL(ABS((I2)))` was refused as a numeric function. `IntrinsicResultType`
  now reads an argument through `IsIntegerArgument` (section 15.3 item 6: a parenthesized integer item or literal is an arithmetic
  expression that always yields an integer); the shared `IsIntegerOperand` is unchanged because the relation screen and PERFORM
  TIMES want an integer ITEM (PB1935). Goldens added: `pb4635-abs-parenthesized-alphanumeric`, `pb4635-abs-compound-alphanumeric`
  (COBOL0844) and the FACTORIAL (INTTYPE) and PERFORM TIMES lines of `pb4635_parenthesized_numeric_arguments`.
- **Review round 2 (R2-1, R2-2, R2-3).** Rounds 1 and 2 made a parenthesized item an arithmetic expression everywhere, and three
  readers needed the parentheses to be transparent. R2-1: a parenthesized class-boolean item is also "a boolean expression enclosed
  in parentheses" (8.8.2; 8.4.3.2.3 SR8 lists both alternatives), so `INTEGER-OF-BOOLEAN((BB))` is legal again: new
  `OperandContext.GroupedFunctionArgument` with a fourth axis, `BooleanOperandAdmitted`, read by both class-screen doors
  (`ClassScreenAdmits`); `ABS((BB) + 1)` stays refused (COBOL0844). R2-2: the DISPLAY image of a selecting function's returned
  value is implementor-defined (15.4.1) and goes to GnuCOBOL (DOC-A.1-92), whose parser makes `(I3)` the identifier, so
  `FunctionDeviceText.Field` describes `BoundComputedOperand.EnclosedOperand` as the item or literal (`ABS((I3))` shows `+03`).
  R2-3: under `--permissive` the string-argument visitor renders the enclosed item, the coercion the bare spelling got, instead of
  dying in its loud arm. Goldens: `pb4635_parenthesized_boolean_argument`, `pb4635_parenthesized_argument_description`, negative
  `pb4635-abs-boolean-arithmetic-expression`; unit test `ParenthesizedIntrinsicArgumentPermissiveTests`. Leads left open: a
  compound numeric argument at a string position under `--permissive` (`TRIM(I2 + 1)`) still dies in the loud arm, on main too;
  and an always-integer expression other than a parenthesized sole item or literal (`ABS(I2 + 1)`) keeps ABS and MAX on the
  Numeric row (15.3 item 6; `IntrinsicArgumentRules.ProvablyIntegral` already reasons term by term).
- **Review round 3 (R3-1, R3-2, R3-3).** R3-1 (blocking): the wrapper hid the item from CONCAT's and BASECONVERT's usage rules, so
  `CONCAT((I3) "A")` printed `0LA` and `BASECONVERT((F2) 10 16)` printed `19`, where the bare spellings are COBOL1627 and COBOL1642. Both
  positions say "data item or literal" (15.18.3 r1, 15.12.3 r1) but declared no shape predicate, because the class kind (`'c'`, the
  unscreened argument-1) admits class numeric. The `CONCAT` tail and `BASECONVERT` argument-1 now carry `DataItemOrLiteralOnly`, and
  `IntrinsicArgumentRules.IsCoercible` makes the violation an error in every mode at a character-reading position (an integer position,
  FIND-STRING argument-3 and the BASECONVERT bases, keeps its `--permissive` coercion: the expression has a value to coerce, a character
  position needs an image it does not have). R3-3: a parenthesized class-boolean item is now a `BoundBoolOperand` (`BoundBoolRef`), the
  boolean expression 8.8.2 calls it, so `LENGTH((BB))`, `BYTE-LENGTH((BB))` and `CONCAT((BB) "A")` are refused as `BB B-AND BC` is, while
  `INTEGER-OF-BOOLEAN((BB))` is unchanged; the predicate refuses a boolean expression too. R3-2 (lead, `--permissive` only): answered
  no change, see the DEVLOG. Goldens: `pb4635_unparenthesized_data_item_arguments` (accept 2023; the legal side of the new rows) and the
  refusals `pb4635-concat-parenthesized-item`, `pb4635-concat-parenthesized-boolean-item`, `pb4635-baseconvert-parenthesized-argument-1`,
  `pb4635-length-parenthesized-boolean-item`; unit test `AParenthesizedItemAtACharacterReadingPosition_IsAnErrorEvenUnderPermissive`.
