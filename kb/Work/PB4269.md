# PB4269 — no GREEN on a guess: an unattributed tier runs whole in leg 1

**Sites:** `scripts/gate_plan.py` (`plan_assembly`, `LEG_ONE_BUDGET`, the module docstring's tier list), `docs/rearchitecture/DESIGN-test-build-ci.md` (the batched-gating section).

## The decision

The operator session 8904f374 asked the owner this, after PRs #880 and #894 bounced out of the merge queue on cases
their GREEN gates had left out: "Batched gating (PB2515) fills leg 1 with the cheapest 2% of tests whenever the gate
can't trace which tests a change affects (for example, when the impact map is stale or a whole file is treated as
changed). Should the local gate instead run every test in that unattributed set before reading green?" The owner chose
**"Run the whole tier (Recommended)"**: a gate with weak attribution runs every case in that tier locally, and those
gates get slower until the attribution holes are closed.

This amends PB2515 (batched gating) for the unattributed case only. Where the impact map does attribute the change by
method, leg 1 stays what it is: the attributed tiers plus the budgeted cheapest slice of the rest.

## What it means in the planner

`gate_plan.plan_assembly` orders tier 1 by `(rank, cost, index)` and admits cases while their recorded time stays within
`LEG_ONE_BUDGET` (0.02 of the assembly's test-seconds). When a change cannot be attributed, that order picks cases by
DURATION, not by what the change reaches. That happens when `every_tier1` is set (no map, a grammar input, a file the
map never saw), and when a hunk is taken at file level because the map drifted (`impacted_tests.drifted_change`).
PR #880's gate ran the cheapest 2 % of 19,609 tier-1 conformance cases, and the 11 the change broke were not among them
(PB2696). A change the map attributes BY METHOD keeps the budget, as the decision says, even when the changed method is
one every compile runs (PB2696's cause 2): that tier is attributed, not a superset the map could not narrow.

After this decision, a plan whose change is unattributed puts ALL of tier 1, and every genuinely new 0u case, in leg 1,
exempt from `LEG_ONE_BUDGET`, `LEG_ONE_UNKNOWN_BUDGET` and the collection cap. The verdict line says why the leg is
whole, so a slow gate names the hole that made it slow.

## Landing (2026-10-31, operator session 8904f374, branch tooling-pb4269-whole-tier)

- `scripts/spec/impacted_tests.py`: `Reach.drifted` names each changed file `drifted_change` took at the file level
  (a file the map knows, in the drift; a file it never saw stays an `every_tier1` reason). Self-test arms cover all
  three cases.
- `scripts/gate_plan.py`: `whole_tier_reason(reach)` gives the one reason (every_tier1 first, then drifted, else ""),
  `build_plan` puts it in the plan (`whole_tier`, `drifted`) and in every assembly's `Context.whole_tier`, and
  `plan_assembly` admits tier 1 and 0u whole when it is set. `summary_lines` prints `tier 1 runs WHOLE in leg 1`. There
  are nine self-test arms: the budget and the cap do not cut it, tiers 2 and 3 stay in leg 2 under a drifted map, 0u is
  admitted whole, it holds with no timings, the reason's order, and end to end through `build_plan` both ways.
- `scripts/run_gate_legs.py`: the verdict line's plan note ends `; tier 1 whole (kb/Work PB4269): <reason>`.
- Docs: `DESIGN-test-build-ci.md` (the leg-1 rule and the plan schema), `gate_plan.py`'s module doc, CLAUDE.md
  (Testing), plan §0 GATE POLICY, the `gate` skill, MANDATORY-PRACTICES I1, the implementer dispatch spec.
- **The cost, measured before landing:** of the 41 gate plans the worktrees wrote between 2026-10-28 and 2026-10-31,
  19 had an `every_tier1` reason, with a median tier 1 of 89 % of the population. Those gates now run nearly the whole
  population. 9 more planned against a nearest (drifted) map and run whole only when a changed file is in the drift.
  The reasons, by count: a grammar, build or source-generator input (8), a file new since the map's commit (5), a
  non-C# input under src/ (5), unattributed test data (1). Closing those holes is what makes these gates fast again:
  PB4270 (record maps from the event that changes main) shrinks the "new since the map" and drift share.

## Measures

- The gate's time on changes the map cannot attribute, before and after (`landing_measure.py`, the gate records).
- The merge-queue reds whose failed cases a GREEN local gate had listed as not run (PB4271's classifier). This decision
  should take that count to zero for unattributed plans. A remaining case is a hole in attribution (PB4228, PB2696)
  that a declared scope must close.
