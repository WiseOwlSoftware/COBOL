# PB3465 — settings.local.json makes every worktree collide with every other

> ⚙ **flags:** process-only · silent

Source: the wave 1134 unit (2026-10-20), reading `plan_wave.py --from-budget --borrow-days 6 --cluster PB3353`'s
table (log `E:\COBOL-coord\scratch\plan-wave-unit.log`).

## Symptom

The plan held the top of `work.py next` and two others for a reason that names no work:

```
PB3337: file-set collision with in-flight work worktree wf_5b092cc6-8b9-2 (worktree-wf_5b092cc6-8b9-2) [IN FLIGHT]
        (.claude/settings.local.json): it waits until that work finishes (then continues it) or is decided
PB3460: ... the same, (.claude/settings.local.json)
PB1278: ... the same, (.claude/settings.local.json)
```

Every agent worktree has `.claude/settings.local.json` modified (`git status --short` in `wf_5b092cc6-8b9-1`, `-2` and
`-5` each prints only ` M .claude/settings.local.json`). It is never work: `prune_worktrees.py` already excludes it
(`SETTINGS = ':!.claude/settings.local.json'   # always dirty in an agent's worktree, never work`), and the landing
excludes it (MANDATORY-PRACTICES, `git add -A -- . ":!.claude/settings.local.json"`).

## Mechanism

`inflight_file_sets` (`scripts/orchestrator/plan_wave.py`, source 1 of its docstring) adds each worktree's uncommitted
and untracked files (`loose = changed_files(git, "HEAD", cwd=path)` plus `ls-files --others`) with no exclusion, so
every worktree owns `.claude/settings.local.json`. A finisher group then inherits the files of the branch it continues
(`carried`, the `g.files |= carried` step before the partition check), which brings that path into its own set, and
`collision` meets it against every other worktree's set on that one path. The partition holds the group "until that
work finishes". It reads as a real hold, so no one sees it (`silent`); the cost is that the campaign's top note
(PB3337, `next` rank 1) is not planned at all.

## Fix (root cause, one rule in one place)

The "never work" path list belongs in ONE place that `prune_worktrees.py`, `plan_wave.inflight_file_sets` (and the
landing check, `landing_check.py`, which reads the same `uncommitted` meta) all read. Today `prune_worktrees.SETTINGS`
is a git pathspec string; make it a single named constant (or function) both readers apply, delete the duplicate, and
add a drift test: a fake worktree whose only change is `.claude/settings.local.json` owns no file set, and a finisher
continuing it collides with nothing. Sweep for other readers of worktree dirt (`status_delta.py`, the survey) that
need the same exclusion.

## Secondary observation (verify before acting)

The same plan labelled `worktree-wf_5b092cc6-8b9-2` IN FLIGHT and listed it as "UNLANDED, naming no open note"; the
previous handoff says `-8b9-2` is contained in `-8b9-5` (PB3441, enqueued as PR #332). Once this defect is fixed that
worktree should classify as finished/enqueued work; if it still reads IN FLIGHT, that is a separate defect next to
PB3464.

## Landed (operator, 2026-10-20, by hand beside the loop, dispatch hold `w1134z`)
The never-work rule was written SIX times, in three shapes: `prune_worktrees.SETTINGS` (a pathspec),
`checkpoint.IGNORED_DIRTY`, `enqueue.py` twice (a suffix test), `next_unit.repo_state` (a suffix test, the settings
file only), and `plan_wave._NOT_PRODUCT` (a prefix test that held `STATUS.md` and `TestResults/` but not the settings
file, which is the defect). The planner's copy was the only one missing the file.
- `coord.NEVER_WORK = (".claude/settings.local.json", "STATUS.md", "TestResults/")` is the one list (an entry ending in
  `/` is a directory). `coord.is_work(path)`, `coord.porcelain_work(lines)` (a rename by its new path) and
  `coord.NEVER_WORK_PATHSPECS` are its three readings. Every reader uses one of them, and the five copies are deleted.
  `plan_wave._names` (behind `changed_files` and the untracked listing, so behind `landing_check.py` too) calls
  `is_work`.
- Tests (`test_plan_wave.py`, 312/312): the fake-git fixture now has the settings file modified in both worktrees, as
  every agent worktree does. It is in no owner's set, and a group declaring it plus a real file collides with nothing.
  `is_work` is checked on the three entries, a backslash path, and three look-alikes that ARE work (`src/STATUS.md`,
  `.claude/settings.json`, `docs/TestResults.md`). `porcelain_work` is checked on renames both ways. Mutation:
  removing the settings file from NEVER_WORK fails exactly those three checks.
- Swept: the other `git status` / `ls-files --others` readers in `scripts/` are scoped to their own paths (the oracle
  capture, the member index, line endings, impacted-test ordering, devlog fixtures). None asks whether a worktree holds
  work. `status_delta.py` (the public base skill) reads `.agent-fleet.json`, which already lists the settings file.

## Finisher (landing gate RED, 2026-10-20): a test-isolation race on main, fixed on this branch
The landing gate on `dd00817a6` went RED on four `FixedFileAttributeFormatTests` cases (the three
`AnIndexedKeyTableDisagreementIsAConflict` rows and `TheNumberOfAlternateKeysIsItsOwnRequirement`: '39' expected, '00'
read). The branch touches no runtime or test code. Cause, already on main since `cf9c85914` (PB3334, 2026-10-18):
`IndexedEngineTests.The_keycheck_opt_out_drives_the_files_trees_by_key_number` sets the process-wide
`COBOLNET_KEYCHECK=OFF`, and every `new FileRegistry()` / `CobolFile.Init()` reads it, but the class was outside the
`[Collection("process-globals")]` that `FixedFileAttributeFormatTests` (the other writer, and the one class asserting a
key-table '39') belongs to. The trx shows the opt-out case at 15:41:14.862 and the four reds inside the next 40 ms. Both
classes run in every leg 1 (IndexedEngineTests is a `Host=ReFS` witness), so any gate could hit it. Fix:
`IndexedEngineTests` joins `process-globals`. Sweep: the other eight test classes that set an environment variable
either are in that collection or set a variable private to the test (`CN-CC-TEST-*`, `WISEOWL_PB807_PARAM`,
`COBOLNET_TEST_LOCALE_PROBE_*`, `PB985-CACHE-PARAM`, `COBOL_SWITCH_34` read only by its own class); no other class
asserts a key-table '39'.
