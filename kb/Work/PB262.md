# PB262

Found by COMPREHENSIVE BATTERY #40 (tree `6f8461d9`, 2026-08-31, artifacts `scratchpad/battery-40`). Four legs
green; the GnuCOBOL differential returned **1 per-case flip**, against an owed list whose stated prediction was
**zero movement in every bucket in both directions**.

**The compiler is RIGHT. The EVIDENCE was wrong — again, and in the same shape as [[PB209]].**

```

    FLIP     syn_subscripts:23   WE_ACCEPT_THEY_REJECT -> AGREE_REJECT   error COBOLNET0844: item 'I' of class alph
```

Totals moved **573 / 473 / 206 / 71 → 573 / 473 / 207 / 70** — AGREE_REJECT +1, WE_ACCEPT_THEY_REJECT −1,

The case's own `AT_SETUP` title is **"Non-numeric subscript"**. Its shape (described, not reproduced — GPL) is a
`PIC X` elementary used as the subscript of a `PIC X OCCURS 10` table, in both a bare `T(I)` and a compound
`T(I + 1)` position.

## The compiler's new verdict is SPEC-CORRECT — a divergence→AGREE convergence, i.e. a FIX

Citations re-derived and `--check`ed here rather than inherited from the diagnostic text (CLAUDE.md rule 1):

- **§8.4.2.3.2** general format — a subscript is exactly three alternatives: `ALL`, `arithmetic-expression-1`, or
  `index-name-1 [{+|-} integer-1]`. The item carries no `INDEXED BY`, so the only admissible reading is
  arithmetic-expression-1.
- **§8.8.1.1**: *"An arithmetic expression may be an identifier referencing a numeric data item, a numeric
  literal, the figurative constant ZERO (ZEROS, ZEROES), such identifiers, figurative constants, and literals
  separated by arithmetic …"* — a `PIC X` item is not one.
- **§8.5.2.1 Table 2** puts category alphanumeric in class ALPHANUMERIC.
- **§8.4.2.3.4 GR2** (*"The value of a subscript shall be a positive integer"*) is the runtime half and does not
  rescue the syntactic one.

So the source is not conforming, the rejection is correct, and **GnuCOBOL rejects it too** — the flip is a
convergence onto their verdict on a case they ship as a NEGATIVE test. This closes an under-reject: before the
batch the compiler accepted it and digit-decoded the alphanumeric bytes into an occurrence number.

## ⛔ THE DEFECT: the owed list named two positions in its heading and measured one in its evidence

`kb/Work/PB169.md` → *THE OWED-DIFFERENTIAL LIST FOR BATTERY #40*, bucket 8, verbatim:

> ### Bucket 8 — PB170's **subscript / ref-mod** class screen over NON-NUMERIC names. **Expected movement: ZERO.**
> Inherited from the review fleet's own instrument rather than re-measured here, and labelled as such: a scan of
> all 3,136 programs … found the only **refmod bound** resolving to a non-numeric-class or group name to be
> `syn_move:453 STRUCTURE1(CONST4:2)` …

The heading claims **subscript / ref-mod**. The evidence sentence measures **refmod bounds only**. Bucket 2 is
titled *"reference-modification bounds that are NAMES"* and enumerates five refmod cases; it never enumerates a
subscript case either. **Across the whole list, the subscript position — the position `ScreenPositionOperandClass`
was written for — is never swept once.** The screen has two arms and the owed list measured one, which is
[[feedback_two_arm_dispatch]] appearing in the EVIDENCE rather than in the code.

⛔ **And the refutation is again a case TITLE.** PB209's was *"REDEFINES: with OCCURS"*; this one is
*"Non-numeric subscript"*. A sweep that had reached the subscript position at all would have hit it on the
keyword. That is twice in two consecutive batteries that a pre-declared empty blast radius was falsified by a
case named after the exact shape.

**This is worse than PB209 in one specific way, and that is why it is MAJOR.** PB209's sweep was an ad-hoc shell
one-liner. This list was written *deliberately, in this repository, as the remedy for PB209* — it opens by
rejecting its own predecessor as "a list of cases that MENTION the construct, not of cases whose verdict can
move", and by warning that slack in an owed list "will swallow up to 32 genuine regressions without anyone
noticing". It then carried a bucket whose slack was a whole syntactic position. The list's honesty about bucket 8
being **inherited rather than re-measured** is the one thing that worked: it labelled the weak row, and the weak
row is the one that broke.

## What would close it

1. **Re-derive bucket 8 by MEASUREMENT, per position.** The owed list needs one row per (screen site × syntactic
   position), not per screen — `ScreenPositionOperandClass` takes a `SegmentPosition` parameter with two members,
   and the list must have a bucket per member or it cannot be complete by construction.
2. **The structural half — the one that makes the next list automatic rather than careful.** A new bind-time
   rejection's reach is a COMPILE question, and `corpus_sweep.py --codes` already answers it exactly; what is
   missing is that nothing REQUIRES a wave to run it before pre-declaring a blast radius. The candidate shape:
   an owed list is generated from `--codes` over the *previous* battery's report plus the diagnostics the wave
   adds, so a bucket cannot be written by hand at all. ⚠ Note the honest limit — `--codes` can only see a code
   that already fires, so for a screen that is brand new the pre-battery answer needs the wave's own build.
3. Register whether battery #40's baseline should be regenerated to encode this row. It almost certainly should
   (the verdict is correct and intended), but — the [[PB209]] precedent — rewriting the baseline in the same
   breath as discovering the list was wrong destroys the only record that it happened.
