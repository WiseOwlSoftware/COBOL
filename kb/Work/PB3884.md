## Summary

**Corrected by the refuter (class and edition text).** The defect survives only on the 4.2.6 compile-time-warning ground: STANDARD-COMPARE is an optional, processor-dependent element (2023 A.4.9 11); the 2009 draft's A.4.8 9)), and with checking off the run-time stop on the fatal EC-ORDER-NOT-SUPPORTED is the implementor's choice (14.6.13.1.3 8), checked), so the only departure is the missing warning. The record's 2014 reasoning rested on 2023-only wording: the 2009 CD 1.2 (the draft toward 2014) A.3 14) and the 2002 text A.3 8) read `The implementor is required to accept the syntax and set the EC-ORDER-NOT-SUPPORTED exception condition to exist when support is not provided` (2023 A.3 25) says `need not accept`). So for `-std=cobol2014` a warning is needed and a compile-time refusal alone is not enough: the sentence below that the default dialect's `is not implemented` error `would be enough` is wrong for 2014. The text below was written before this correction; where it differs, this paragraph governs.

Record text as adjudicated:

GnuCOBOL 3.2 under `-std=cobol2014` compiles a reference to the standard intrinsic function STANDARD-COMPARE with no
diagnostic, and the run ends at the call with `libcob: error: attempt to use non-implemented function`, exit code 1.
The default dialect refuses the same source at compile time (`FUNCTION 'STANDARD-COMPARE' is not implemented`): the
`-std=cobol2014` (and `-std=cobol2002`) word list re-activates a function that cobc's own table marks as not
implemented. Verdict: GNUCOBOL-DEFECT. Class: compiles but is not implemented at run time (no compile-time warning for an unsupported processor-dependent element). Edition: 2014.

## Expected result (per ISO)

Two conforming outcomes, and cobc under `-std=cobol2014` gives neither.

STANDARD-COMPARE is a processor-dependent element. §A.3 25) (checked): "The STANDARD-COMPARE intrinsic function, the
EC-ORDER-NOT-SUPPORTED exception condition, and the ORDER TABLE clause in the SPECIAL-NAMES paragraph are dependent upon
an implementation of ISO/IEC 14651:2020. The implementor need not accept the syntax or set the EC-ORDER-NOT-SUPPORTED
exception condition to exist when support for ISO/IEC 14651:2020 is not provided."

1. If support is claimed: §15.85.3 5) (checked) uses the default table 'ISO 14651_2020_TABLE1' when no ordering-name
   is given, and §15.85.4 6) (checked) returns "<" "if argument-1 is less than argument-2". "A" sorts before "B" at
   the first level of that table, so the run displays `[<]` and then `END`.
2. If support is not claimed: §4.2.6 (checked): "An implementation shall provide a warning mechanism at compile time to
   indicate use of syntactically-detectable processor-dependent language elements not supported by that
   implementation." and "The implementor is not required to produce executable code when unsupported
   processor-dependent language elements are used." So a compile-time warning (or a refusal) is required; the run-time
   abort alone would be allowed after it.

Observed: no compile-time diagnostic of any kind (also with `-fsyntax-only -Wall`), and an executable that aborts. The
departure is the missing §4.2.6 compile-time warning. The default dialect's
`FUNCTION 'STANDARD-COMPARE' is not implemented` would satisfy §4.2.6; `-std=cobol2014` loses it.

Edition: STANDARD-COMPARE is not a 2023 addition: Annex E (§E.1, checked) lists every 2023 addition as
added (§E.3.3 22), checked), and STANDARD-COMPARE is not among them. (Derived; the repository holds no 2014 text, and
docs/VERSION_CHANGE_REFERENCE.md row 7.19 derives 2002 as its first edition. That the 2014 text also made it
processor-dependent and carried the counterpart of the §4.2.6 warning requirement is assumed from the 2023 text and not
verified against 2014.)

Citations inherited from the night records: The slice's §15.85.4 4), §15.85.3 5) and §15.85.4 1) check; §15.85.3 5) is used, with §15.85.4 6) for the result. The slice's needs_judgment (witness fz03857 names both STANDARD-COMPARE and BOOLEAN-OF-INTEGER) is resolved by reducing each function to its own program; BOOLEAN-OF-INTEGER has its own record. A.3 25) narrows this family's ISO ground from 'required function not implemented' to 'no compile-time warning for an unsupported processor-dependent element' (§4.2.6).

Edition as recorded by the adjudicator: 2014. `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Fix site (GnuCOBOL 3.2 source, read observationally)

In `gnucobol-3.2` (read observationally; identifiers only):

The function is declared in the compiler's intrinsic table as known but not implemented, and libcob carries only a
stub, but the `-std=cobol2014` word list re-activates it, so the compile-time refusal that cobc has for such functions
never fires:

- `cobc/reserved.c`, `function_list[]`, the `STANDARD-COMPARE` entry (line 3774): its `active` member is `CB_FEATURE_NOT_IMPLEMENTED`.
- `cobc/tree.c`, `cb_build_intrinsic` (line 7030): a function whose entry is `CB_FEATURE_NOT_IMPLEMENTED` is refused with
  `FUNCTION '%s' is not implemented`. This is the diagnostic the default dialect prints.
- `config/cobol2014.words`: line 535 `not-intrinsic-function: DIALECT-ALL`, then line 608 `intrinsic-function: STANDARD-COMPARE`
  (`config/cobol2002.words` has the same pair, line 534 and line 598).
- `cobc/reserved.c`, `change_intrinsic` / `set_intrinsic_mode` (line 4979): the DIALECT-ALL deactivation moves the
  entry from `CB_FEATURE_NOT_IMPLEMENTED` to `CB_FEATURE_DISABLED`; the later activation then moves it from
  `CB_FEATURE_DISABLED` to `CB_FEATURE_ACTIVE`. The function's own FIXME comment (line 4981) names this
  not-implemented, disabled, active sequence as unhandled. After it, `cobc -std=cobol2014 --list-intrinsics` reports
  the function as implemented ("Yes") and `cb_build_intrinsic` accepts it.
- `libcob/intrinsic.c`, `cob_intr_standard_compare` (line 7145): calls `error_not_implemented` (line 3135), which sets
  `EC-IMP-FEATURE-MISSING` and calls `cob_fatal_error (COB_FERROR_FUNCTION)`; `libcob/common.c`, `cob_fatal_error`
  (line 9109) prints `attempt to use non-implemented function` and ends the run with exit code 1.

Two fixes are possible, and they are independent: (a) make `set_intrinsic_mode` keep `CB_FEATURE_NOT_IMPLEMENTED`
through a DISABLED-then-ACTIVE sequence, so that every dialect refuses the function at compile time, as the default
dialect already does; (b) implement `cob_intr_standard_compare`. Because STANDARD-COMPARE is processor-dependent (A.3 25), fix (a) alone, a compile-time diagnostic, is a conforming outcome for an implementation that does not claim ISO/IEC 14651 support.

The same mechanism covers all six functions of this group (BOOLEAN-OF-INTEGER, CHAR-NATIONAL, EXCEPTION-FILE-N,
EXCEPTION-LOCATION-N, INTEGER-OF-BOOLEAN, STANDARD-COMPARE; records in this directory), so fix (a) is one change
for all of them and one upstream ticket can carry all six repros.

**Title:** FUNCTION STANDARD-COMPARE compiles under -std=cobol2014 with no compile-time warning; the run aborts with 'attempt to use non-implemented function'

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1), Linux x86_64.

Steps:

    cobc -std=cobol2014 -fformat=free -x -o stc stc.cob
    ./stc

with stc.cob:

```
IDENTIFICATION DIVISION.
PROGRAM-ID. STC.
PROCEDURE DIVISION.
    DISPLAY "[" FUNCTION STANDARD-COMPARE("A", "B") "]"
    DISPLAY "END"
    STOP RUN.
```

Observed: the compile succeeds with no diagnostic (also with -fsyntax-only -Wall). The run prints nothing from the
DISPLAY statement and ends with exit code 1:

    libcob: error: attempt to use non-implemented function

Without -std (default dialect), the same source is refused at compile time:
`stc.cob:4: error: FUNCTION 'STANDARD-COMPARE' is not implemented`. `cobc -std=cobol2014 --list-intrinsics` lists STANDARD-COMPARE as
implemented ("Yes"); plain `cobc --list-intrinsics` lists it as "No".

Expected: FUNCTION STANDARD-COMPARE (ISO/IEC 1989 15.85) is a processor-dependent element (Annex A.3
item 25: it depends on ISO/IEC 14651). An implementation either supports it, and then the run displays `[<]` ("A"
before "B" in the default 14651 table, 15.85.4 rule 6) and `END`, or does not, and then 4.2.6 requires a compile-time
warning for its use ("An implementation shall provide a warning mechanism at compile time to indicate use of
syntactically-detectable processor-dependent language elements not supported by that implementation"). Under
-std=cobol2014, cobc gives no warning and produces an executable that aborts. The default dialect's
"FUNCTION 'STANDARD-COMPARE' is not implemented" would be enough.

Cause, as far as we can see: config/cobol2014.words (and cobol2002.words) first deactivates all functions with
`not-intrinsic-function: DIALECT-ALL` and then activates STANDARD-COMPARE; set_intrinsic_mode in cobc/reserved.c turns the
not-implemented entry into disabled and then into active (its FIXME notes this), so cb_build_intrinsic's
"is not implemented" check is bypassed and the call is generated against the libcob stub cob_intr_standard_compare, which calls
error_not_implemented. Either keeping the not-implemented state through that sequence (compile-time refusal in every
dialect) or implementing the function would remove the run-time abort. The same applies to BOOLEAN-OF-INTEGER,
CHAR-NATIONAL, EXCEPTION-FILE-N, EXCEPTION-LOCATION-N, INTEGER-OF-BOOLEAN and STANDARD-COMPARE.
