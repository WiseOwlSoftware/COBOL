# PB1464 — LANDED (wave 1005 D)

**Landed, at the resolution seam the note named — not by reordering `primaryCondition`.**
`SoleOperand.Unparenthesized` (Frontend; the OPPOSITE reading of `SoleOperand.Primary`, which stays "not enclosed in
parentheses" for §8.8.4.7.3 SR2) strips the parentheses that enclose a whole operand, and
`ConditionBinder.ConditionOperandExpression` is the one read of it for the bare-operand classifier
(`AnalyzeBareOperand`: level-88, switch-status, misqualified condition-name), the boolean-operand predicate and binder
(`IsBooleanValueOperand`, `BindBoolOperandValue`) and the not-a-condition report (`RefuseNonCondition` now names the item
the parentheses enclose). `IF (X1)`, `IF NOT (X1)`, `IF ((X1))`, `IF (S1-OFF)`, `IF NOT (S1-ON)`, `IF (BW)`, `IF NOT (BZ)`,
`IF X = 1 AND (X1)` (which had been read as the abbreviated relation `X = (X1)` and drew COBOLNET1639), `WHEN (X1)` and
`PERFORM UNTIL (X1)` all bind, at 85 for the level-88 and switch forms and 2002 for the boolean one.
A class-name stays parenthesis-opaque (`(MY-CLASS)` is no class condition), and a parenthesized non-condition is still
COBOLNET2318 (negative `pb1464-parenthesized-non-condition`).

**The relation-operand sibling, found by the sweep and fixed in the same change.** `IF (BW) = BZ` and `(BW) = (BW)` were
COBOLNET0844 "not a numeric operand": `ComparisonOperandOf` read the parenthesized boolean item as the arithmetic
expression the grammar spells. §8.8.2 lists "a boolean expression enclosed in parentheses" as a boolean expression, so
`ConditionBinder.EnclosedBooleanOperand` (one reading, asked by `ComparisonOperandOf` and EVALUATE's `BindValueOperand`,
the two operand binders that answer one question, PB224) binds it as the boolean operand it encloses; an enclosed
non-boolean operand stays an arithmetic expression (§8.8.1.1, as the comment on the sole-function arm says).
`COBOLNET2318`'s catalogued text now says parentheses change nothing.

**Not done, by the standard's own wording:** `A = B AND (C)` with C an ordinary numeric item still reads `(C)` as the
object of the carried relation. §8.8.4.12.1 defines abbreviation only where "no parentheses are used within such a
consecutive sequence", so that reading is outside the standard's definition; changing it would reject source GnuCOBOL
and IBM accept, and no note asks for it.

**Evidence.** `pb1464_parenthesized_bare_conditions` (85), `pb1464_parenthesized_boolean_operands` (2002; includes
`EVALUATE (BW) WHEN BZ`), negative `pb1464-parenthesized-non-condition`.

## Finding — `simple-boolean-condition` (rejects-legal-source; rows `FMT-8.8.4.3.2`)

**Mechanism.** primaryCondition orders comparisonExpression before `LPAREN condition RPAREN`, so a parenthesized BARE operand -- `(BW)`, `(X1)` -- is taken as a parenthesized arithmetic valueOperand, and the bare-operand classifier does not look through the parentheses: a parenthesized simple boolean condition and a parenthesized condition-name are refused at every edition

**Repro.** 01 BW PIC 1 VALUE B"1". 01 BZ PIC 1 VALUE B"0". 01 X PIC 9 VALUE 1. 88 X1 VALUE 1. ... IF (BW) DISPLAY "T5" ELSE DISPLAY "F5". IF NOT (BZ) DISPLAY "T6" ELSE DISPLAY "F6". IF (X1) DISPLAY "T1" ELSE DISPLAY "F1". (p2.cob/p3.cob at 2023; p4.cob `IF (X1)` / `IF NOT (X1)` at --std 85)

**Expected from the spec.** §8.8.2: 'a boolean expression enclosed in parentheses' is a boolean expression, so `(BW)` is boolean-expression-1 of §8.8.4.3.2; independently §8.8.4.11.3 Table 5 lets '(' be followed by a simple-condition and a simple-condition be followed by ')'. Expected T5, T6, T1 (and at --std 85, T1 / F2 for the condition-name).

**Observed / reasoning.** error COBOLNET2318: '(BW)' is used as a condition, but it is a literal, a figurative constant, a function reference or an arithmetic expression (also '((BW))', '(BZ)', '(X1)' -- the latter at --std 85 as well). Parenthesized forms that CANNOT be an arithmetic operand -- `(BW B-AND BZ)`, `(A = B)` -- parse via the LPAREN condition RPAREN arm and work, which is why only the bare-operand shape fails. Fix at the resolution seam (the bare-operand analysis / BindSoleOperandCondition should unwrap a parenthesized sole operand to the same classification it gives the bare one -- condition-name, switch-status, boolean item), not by reordering the alternative (the DEVLOG-621 lesson about re-predicting the shared comparison rule). No kb/Work note found for this (searched kb/Work for 2318 / parenthesized condition-name).

## Refuter evidence — row `FMT-8.8.4.6.2` (PARTIAL)

PARTIAL — A switch-status condition written in parentheses is legal: §8.8.4.2.1 says 'The inclusion in parentheses of simple conditions does not change the simple condition truth value.' (cite.py --check found it in §8.8.4.2.1, not §8.8.4.1). The pinned compiler rejects IF (S1-OFF) and IF NOT (S1-ON) with COBOLNET2318, which says the operand is 'a literal ... or an arithmetic expression' and cites §8.8.4.2.1, the clause that permits the construct. The bare form, lower-case spelling, AND/OR combinations, (S1-OFF AND X-ONE), EVALUATE subject ALSO, and inheritance by a nested program all compile and run correctly at 85 and 2023. The rejection is not specific to switches: (X-ONE), a parenthesized level-88 name, fails the same way. The root cause is the shared path for a parenthesized single-operand condition (§8.8.4.2.1), and the fix belongs there. It still rejects legal source that uses this format.

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SetAlterBinder.cs#SwitchCondOf; src/Cobol.Net.Compiler/Binding/Bound/BoundAlterSwitches.cs#BoundSwitchCondition
