# PB3389 — a stored `blocked` goes stale when a blocker lands ahead in the queue

**What happened (2026-10-18).** Branch `notes-pb3382-crash-matrix-close-20261018` filed PB3382 with `blocked: true`,
`blocked_by: ["PB3333"]`. Its landing checks passed locally on a base without PB3333 on main, and it entered the merge
queue as PR 256. PB3333 landed first, in PR 255. The merge group for PR 256 (run 39165818032, base 6e2244f3d) then ran
the audits job's `work.py check`, which refused "PB3382.md: blocked is True but its blocked_by ['PB3333'] have all
landed or retired — set `blocked: false`". The queue removed PR 256 at 21:03Z. A clerk commit (`b38d4bd0b`) set the
flag, and the branch now needs a fresh review before it can land again. About four hours passed between the bounce
and the fix.

**Why the local gate could not see it.** The check's verdict on a branch depends on the state of OTHER notes, so it
can change between the local run and the merge group without the branch changing. CLAUDE.md's CI invariant holds
that a CI red is also a defect in the local process. Here the local process cannot see the future order of the queue,
so the fix belongs in the schema, not in the gate.

**Root cause (rule 5).** For a note whose `blocked_by` names notes, `blocked` is a stored copy of a fact the
register can compute: the note is blocked exactly while one of them has not landed or retired. `work.py` already says
so (lines 489-493: "`blocked:` IS A SECOND SPELLING OF `blocked_by:`, AND THEY DRIFTED") and answers the drift with a
check that holds the flag to the list. But a check whose verdict depends on OTHER notes' status can flip with no change
to the branch, which is exactly what a merge queue does. 177 notes carry `blocked: true` today.

**The one case the flag carries information.** `blocked: true` with `blocked_by: []` is legal and means the note is
blocked on something that is not a note (`work.py` line 493, honoured by `cluster_order`). Two open notes use it
today: PB670 (blocked on the owner) and PB296 (blocked on a document). Deriving the flag from the list alone would
unblock both, and `work.py next` and `plan_wave.py` would hand PB670, an owner decision, to a fix-lane implementer.

**The fix.** `work.py` derives `blocked` whenever `blocked_by` names notes (one function, read by `next`,
`cluster_order`, the views and `check`), and the stored flag is deleted from those notes in the same change. A
non-note blocker gets an explicit marker that says what it is: a `blocked_on:` field naming the owner or the document,
or a decision note that `blocked_by` names, which PB670 and PB296 are converted to in the same change. The stale-flag
rule of `check` then goes away, because nothing is left to drift, and a blocker landing ahead of its dependent in the
queue changes nothing on the dependent's branch. One reader outside `work.py` must follow: the public base's
`fix_clusters.py` skips a note by its stored frontmatter (`.agent-fleet.json` `skip_flag: ["blocked", ...]`), so the
derived value has to reach it. Either `work.py` writes a generated field that no person edits, or the base's skip rule
learns `blocked_by` (a public change: the owner sees the exact text first). `kb/Work.base`'s views read the same value.
A self-test pins two cases: a note whose only blocker lands reads unblocked with no edit, and a note with a non-note
blocker stays blocked. Other stored fields that are derivable get the same audit (`closes_rows` against the landing is
not one of them: it records a decision).

**Two more witnesses (2026-10-19, enqueue unit).** (a) PR #268's pull request run 39202733274 at cc441f527 failed on PB3383 and PB3385 (`blocked_by: ["PB3334"]`), which PB3334 had landed ahead of it in the queue; the account-1 session fixed it by hand in c1421bf44. (b) PR #275 (`notes-pb3275-pb3409-leads-20261018`), run 39209418316, failed on PB3410 and PB3411 (`blocked: true`, `blocked_by: ["PB3336"]`) after PR #268 merged at 2026-10-19T06:19:53Z as 0eba56a75, while the clerk branch was landing. The note was filed blocked, which was true when the leads were written; PB3336 landed within the hour. Both fixes were hand commits, and the second one held a finished clerk branch out of the merge queue.

**Recurrence (2026-10-23).** Pull request #444 (branch `notes-leads-pb3568`) bounced from the merge queue: merge-group run 40016718769, job `audits`, step `work.py check`. PB3593 and PB3594 were `blocked: true` with `blocked_by: [PB3568]`, and PB3568 landed as #441 at 20:04:14Z, 28 s after #444 was queued behind it; the branch's own gate had seen PB3568 open. Fixed on the branch at af26fa018 by hand-unblocking. The rule that refuses it is at `scripts/spec/work.py:641` (`if bool(it.get("blocked")) != bool(still):`).
