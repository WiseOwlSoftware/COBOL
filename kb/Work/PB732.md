reported only the numeric arm and only the level-88 spelling, and explicitly noted the path is PRE-EXISTING —

So the harm splits by the SUBJECT's category, not by the format:

- **numeric subject** → the word survives `NormalizeIfNumericLiteral`, the emitter appends the `L` suffix for a
  numeric literal, and Roslyn is the first thing in the pipeline to notice. The user gets a C# error naming a C#
  identifier that is not in their program. `crashes` in the register's sense: an internal-error-shaped exit
  where a diagnostic belongs.
- **alphanumeric subject** → the word is silently promoted to an alphanumeric literal OF ITS OWN SPELLING. A typo
  for a constant-name, a mis-remembered symbolic-character, a word from a copybook that failed to expand — each
  becomes the seven-character string `NOSUCHW` and the program runs and answers. `wrong_answer` + `silent`.

## What the standard prints

§13.18.63.2 Format 3 (`cite.py --check 13.18.63.2 "literal-2"` → **OK §13.18.63.2 (General formats)**) writes the
condition-name operands as `literal-2 [ {THROUGH|THRU} literal-3 ]` and Format 1 writes `VALUE IS literal-1`.
Every §13.18.63.3 rule that reaches them says *literal* — SR26 a) "*the value of literal-2 shall be less than the
value of literal-3*", SR27 "*The value of literal-4 shall not be equal to the value of any occurrence of
literal-2*". A bare user word is a literal in exactly one way: §13.10.3 SR2 —
`--check 13.10.3 "constant-name-1 may be used anywhere that a format specifies a literal"` → **OK §13.10.3 2)** —
*"Except in a compiler directive, constant-name-1 may be used anywhere that a format specifies a literal of the
class and category of constant-name-1"*, and the §12.3.7 SYMBOLIC CHARACTERS route the binder already implements
beside it. **A word that names neither is a reference to nothing**, and §8.4.2.1 —
`--check 8.4.2.1 "In order to use a resource, a statement shall contain a reference that uniquely identifies that
resource"` → **OK §8.4.2.1 (General)** — is the rule it violates. §4.2.2 —
`--check 4.2.2 "shall"` → **OK §4.2.2 (Acceptance of standard language elements)**, second paragraph: *"An
implementation shall provide a warning mechanism that optionally may be invoked by the user at compile time to
indicate violations of the general formats and the explicit syntax rules of standard COBOL"* — is the obligation
to say so. (Quoted as TEXT, not as a ¶ number: `DiagnosticCatalog.UndefinedReference`'s neighbouring comment cites
"§4.2.2 ¶3" for this sentence, which is ¶2 as the clause is transcribed. Not this note's subject; noted so the
next reader does not inherit the ordinal.)

## The mechanism — one arm, two callers

`src/Cobol.Net.Compiler/Binding/DataBinder.cs:3504-3516`:

```csharp
private string RawValueOperandText(Core.ValueClauseOperandContext op) =>
    op.nonNumericLiteral()?.concatenationExpression() is { } ce ? ConcatFolder.Fold(...).RawText
    : … allLiteral … : … figurativeConstant().cobolWord() …
    : SymbolicValueRawText(op) is { } rawBare ? rawBare
    : ConstantValueRawText(op) is { } konst ? konst
    : NormalizeIfNumericLiteral(op.GetText());      // ← the sink
```

The chain probes five ways for an operand to BE a literal — a §8.8.3 concatenation, `ALL` over a concatenation,
`ALL symbolic-character`, a bare symbolic character, a constant-name — and when every probe returns null it falls
through to **`op.GetText()`**. There is no sixth arm asking whether the word resolved to anything; the raw
spelling becomes the value. `ExtractValue` (`:3388-3405`) ends the same way (`item.GetText()`), which is why the
ITEM VALUE (probe b/d) fails identically to the level-88 set.

Both callers reach it: `BindCondition` (`:2537-2595`, `RawValueOperandText` at `:2563`, `:2564` and `:2587` for
the singleton, low and high operands) and the item-VALUE funnel at `:2806`. `ValidateValueCategory` runs on the
result and does not save it — the raw text `NOSUCHW` reads as an alphanumeric value against a PIC X subject, and
it never sees the numeric case at all.

⛔ **This is the R30 shape, at a site the R30 fix does not cover.** `DiagnosticCatalog.UndefinedReference`
(`COBOLNET1639`, `src/Cobol.Net.Editions/Diagnostics/DiagnosticCatalog.cs:1842-1848`) already exists, already
cites §8.4.2.1/§8.4.2.2, and its comment (`:1470-1476`) records the same discovery in the PROCEDURE DIVISION:
"*MOVE NO-SUCH-NAME TO X and DISPLAY NO-SUCH-NAME compiled with zero diagnostics, exit 0 … Reported at the ONE
chokepoint (Resolve's undefined arm)*". The VALUE clause resolves its operands itself and never calls
`ReferenceResolver.Resolve`, so the chokepoint has no jurisdiction here. `feedback_two_arm_dispatch`: R30 fixed
the statement arm of "a word that names nothing"; the data-division arm was never asked about.

## The fix shape

Give `RawValueOperandText` its missing last arm rather than a second mechanism: when the operand reduces to a
`dataReference` (the shape `SymbolicValueRawText` already walks) and neither the symbolic-character table nor the
constant table claims it, report `DiagnosticCatalog.UndefinedReference` at the operand's cursor and return a
poison value the emitter never writes. `ExtractValue`'s tail is the same edit. **Do NOT screen in the grammar** —
`valueClauseOperand : unaryExpression | nonNumericLiteral` is right, because a constant-name IS spelled as a word
and only the symbol tables can tell the two apart; this is a rule the binder enforces, not a shape the format
prints.

Ship with negatives pinning both arms (`VALUE NOSUCHW` on a numeric subject and on an alphanumeric one, plus the
THRU high-operand form, which probe c shows takes a separate code path through `valueClauseRange`) and one
positive golden proving a real constant-name and a real symbolic character still bind — the five probe arms above
the sink are exactly what a careless screen would break.

## Sweep

  `:3404`, `:3600` (the Format-2 table phrase's literal list) and `DataBinder.Reports.cs:518` (the report-section

- The wider pattern is "a binder that resolves a name itself instead of through `ReferenceResolver.Resolve`".
