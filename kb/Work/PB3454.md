# PB3454 — the follow-on question to the transaction-scope decision

## ✅ THE OWNER'S ANSWER — 2026-10-19 (through the session's question prompt after the 18:58 PDT scope decision; read at 19:55 PDT), verbatim: **"Per file (Recommended)"**

The question was put as one bare choice with the two options below, the per-file one marked recommended. The owner chose it.
**What it means:** the design stands as written — one COMMIT commits its files one at a time, in the order of the run unit's
open stores; a refusal at file i leaves the files before i committed and the files from i on at the previous COMMIT once
item 8's unconditional ROLLBACK has run; the program gets EC-I-O-PERMANENT-ERROR with '30' on the refused file
(DESIGN-runtime-library.md 2.2.1.10's three regions; docs/CONFORMANCE.md's commit row states the determination). Nothing in
2.2.1.10, 2.2.2 or the two simulators changes; no durable commit record outside any one file is built. PB3337 and PB3340
implement it as designed; this note is `landed` as an answered decision.

The question lives in `kb/Work/PB3337.md` (its decision section, "The one question that follows it"); this note is the register
item that carries it, so `python scripts/spec/work.py next` and `kb/Work.base` can see it. The text below is PB3337's, verbatim.

> when one COMMIT covers several files under APPLY COMMIT and the medium refuses the commit of one of them, the design states a PER-FILE
> commit — files committed one at a time in the order of the run unit's open stores; a refusal at file i leaves the files
> before i committed and the files from i on at the previous COMMIT once item 8's unconditional ROLLBACK has run; the program
> gets EC-I-O-PERMANENT-ERROR with '30' on the refused file (2.2.1.10's three regions; docs/CONFORMANCE.md's commit row).
> The alternative is ALL-OR-NOTHING across files, which needs a durable commit record outside any one file that every file's
> recovery consults (a two-phase commit): both designs and both simulators change, since each file's recovery gains a
> dependency on a record it does not own — the Mythos lane's unmeasured estimate is one more design memo with its model and a
> third to a half more work on PB3337 and PB3340. The spec is silent on a COMMIT that fails part way (§9.1.18.3 says only that
> a COMMIT makes the changes permanent); GnuCOBOL has no rollback at all; IBM and Micro Focus get atomicity across files from a
> transaction server or a file server's log, not from the compiler. The Mythos lane recommends per file, as designed.

## The options, as PB3337 states them

- **PER FILE (the current design).** Delivers: the design and both simulators as written; no dependency between files'
  recovery. Loses: a refusal at file i leaves the files before i committed, so one COMMIT can end half applied. Costs: nothing
  beyond the planned PB3337 and PB3340 work.
- **ALL-OR-NOTHING across files.** Delivers: one COMMIT either applies to every file or to none. Loses: each file's recovery
  gains a dependency on a record it does not own. Costs: a durable commit record outside any one file that every file's
  recovery consults (a two-phase commit); both designs and both simulators change; the Mythos lane's unmeasured estimate is one
  more design memo with its model and a third to a half more work on PB3337 and PB3340. PB3337 states no other cost.

## Standing

Answered (above): the per-file design stands by the owner's decision. This note never blocked PB3337 or PB3340; PB3337 records
the answer beside the question, and this note is `landed`.
