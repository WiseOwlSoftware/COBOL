# PB452 — two mandatory SET formats have no surface, and one is misfiled as a declined module

Lane-3 adjudication batch b2, group g7-set-a. **Every repro below was re-run on HEAD `89044aa0`**; all still
reproduce. (The registrar's b2 correction closed the *Format 6* sibling — `SET … ATTRIBUTE` now draws
COBOLNET1707 as of `60bf02d7`. Neither format in this note was touched by that landing.)

## 1. THE MECHANISM

`setStatement` (`src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4:1177-1189`) lists eleven alternatives.
**Neither Format 8 nor Format 15 is among them**, and they are absent in two different ways.

**Format 15 (numeric-content)** has no production, no phrase and no binder arm. `CONTENT`,
`FARTHEST-FROM-ZERO`, `NEAREST-TO-ZERO`, `IN-ARITHMETIC-RANGE`, `FLOAT-INFINITY`, `FLOAT-NOT-A-NUMBER` and
`FLOAT-NOT-A-NUMBER-SIGNALING` appear **nowhere** under `src/Cobol.Net.Frontend/Grammar/` (measured:
`grep -rn "FARTHEST\|NEAREST-TO-ZERO\|IN-ARITHMETIC-RANGE\|FLOAT-NOT-A-NUMBER" src/Cobol.Net.Frontend/Grammar/`
→ nothing). The five value words exist only as reserved-word rows, so the user cannot even spell them as
user-defined words: there is no workaround and no signal.

**Format 8 (function-pointer-assignment)** is stopped one level earlier. `functionPointerUsage`
(`Grammar/Core/CobolData.g4:550-552`) parses `FUNCTION_POINTER (TO cobolWord)?` as a superset, `PicInfo`'s
**`Usage`** enum has a `FunctionPointer` member (`Binding/Model/PicInfo.cs:115-118`) purely so the 2014
introduction gate fires — but `PicCategory` has no such member, so no data item ever carries the category and no
`SET` can reach it. Every `USAGE FUNCTION-POINTER` declaration is staged loud at the *declaration*, so Format 8
is unreachable through its operands.

⛔ **AND THE ABSENCE IS MISFILED, WHICH IS THE HALF THAT PROPAGATES.**
`src/Cobol.Net.Compiler/Binding/IntrinsicArgumentRules.cs:471-475` reads:

    // Table 2 collapses all THREE pointer categories into class Pointer. PicCategory has no
    // FunctionPointer member because USAGE FUNCTION-POINTER is documented non-support (COBOLNET1564,
    // Annex A.3) — the category is unreachable BY CONSTRUCTION, not silently unclassifiable; …

Every clause of that justification is false, and each was checked mechanically rather than reasoned about:

* **Annex A.3 does not contain function-pointer.** Measured over the whole list (spec lines 34861-35010):
  `awk 'NR>=34861 && NR<=35011' specs/ISO_COBOL.md | grep -i function-pointer` → nothing.
* **Annex A.4 does not either.** A.4's *entire* SET inventory is three items — format 6 (A.4.2 item 24),
  format 14 (A.4.4 item 3), formats 11/12 (A.4.9 item 9). Neither format 8 nor format 15 appears, so neither
  can be declined under §4.2.7.
* **The diagnostic actually issued is COBOLNET0899**, the staged-loud "recognized but not yet implemented"
  band — not the COBOLNET1564 non-support band the comment names.
* **`docs/CONFORMANCE.md` §4's documented-non-support enumeration does not carry function-pointer** either.

This is the `a_real_clause_can_answer_a_different_question` shape: a comment justifying an omission by naming a
real annex that says something else. It then reads as a **settled owner decision** to every reader downstream,
which is exactly why nobody re-derived it.

## 3. EXPECTED vs OBSERVED — RE-RUN ON HEAD 89044aa0

    # Format 8 — the operand cannot be declared, so the statement is unreachable
    cobol e1_fp_decl.cob --std 2023 --run       # 01 FP1/FP2 USAGE FUNCTION-POINTER TO FPROTO ; SET FP1 TO FP2
      (5,8): error COBOLNET0899: data item 'FP1': USAGE FUNCTION-POINTER (ISO §13.18.60 — a function-pointer data item)
      (6,8): error COBOLNET0899: data item 'FP2': …
    cobol e2_fp_bare.cob --std 2023 --run       # the same without the TO phrase → the same pair
      expected (GR14): compiles; identifier-13's address is stored into each identifier-12 in order; a
      mismatched signature or a non-NULL non-function address sets EC-FUNCTION-PTR-INVALID, changes no data
      item and terminates the statement

    # Format 15 — a raw ANTLR cascade, at every edition the format exists in
    cobol h4_content_of.cob --std 2023 --run    # 01 WS-F USAGE FLOAT-LONG ; SET CONTENT OF WS-F TO FLOAT-INFINITY
      (13,16): error COBOL0001: no viable alternative at input 'SETCONTENT'
      (13,16): error COBOL0001: cannot parse construct near 'CONTENT'
      (13,32): error COBOL0001: unexpected 'TO'
      (14,12): error COBOL0001: unexpected 'DISPLAY'
    cobol f15_farthest_numeric.cob   → the same cascade
    cobol f15_infinity_float.cob     → the same cascade
    cobol f15_nan_signaling.cob      → … plus `missing token before 'SIGN'` / `unexpected 'NEGATIVE'`
    cobol f15_nearest_range.cob      → … plus `missing token before 'IN-ARITHMETIC-RANGE'` / `unexpected 'POSITIVE'`
      expected (GR32): `SET CONTENT OF N TO FARTHEST-FROM-ZERO` over `01 N PIC S9(4)V99` prints +9999.99;
      with `SIGN NEGATIVE`, -9999.99; IN-ARITHMETIC-RANGE takes whichever of the item bound and the
      arithmetic-mode bound is closer to zero

The `USAGE FLOAT-BINARY-64` / `FLOAT-LONG` declarations in the same files compile, so the **receivers are
supported and only the statement is missing**.

**Editions, derived from the standard and not from the code:** Annex E records exactly one SET-statement change
from the previous edition (E.3.3 item 17, dynamic-length elementary items), and none of `FUNCTION-POINTER`,
`CONTENT`, `FARTHEST-FROM-ZERO`, `NEAREST-TO-ZERO`, `IN-ARITHMETIC-RANGE` or the NaN words is among E.2's
newly-reserved-in-2023 list — so both formats existed at 2014. The 2023 standard cannot settle 2002 and this
note does not claim it.

## 4. THE CODE SITES AND THE SHAPE OF THE REPAIR

| arm | file:line |
|---|---|
| `setStatement` — no F8, no F15 alternative | `CobolParserCore.g4:1177-1189` |
| `BindSet`'s dispatch — no arm for either | `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SetBinder.cs:24-70` |
| F8 stopped at the declaration | `Grammar/Core/CobolData.g4:550-552` + `Binding/Model/PicInfo.cs:115-118` (`Usage.FunctionPointer`, no `PicCategory` twin) |
| **the false justification** | `src/Cobol.Net.Compiler/Binding/IntrinsicArgumentRules.cs:471-475` |
| the value computation F15 needs, already present | `Binding/Procedure/Verbs/IntrinsicBinder.cs` — `FUNCTION HIGHEST-ALGEBRAIC` / `LOWEST-ALGEBRAIC` / `SMALLEST-ALGEBRAIC` with their IN-ARITHMETIC-RANGE screens |

⛔ **Land the misfiling FIRST, before either feature** (CLAUDE.md rules 1 and 4). A comment asserting that a
mandatory element is a documented non-support item under a named annex is the exact thing that stops anyone from
re-deriving it, and it costs one line to correct. It should say what is true: the category is absent because
function prototypes are P13 work, the diagnostic is the 0899 staged-loud band, and Annex A.4 does **not** list
the format — so this is a GAP, not a disposition.

Then:

1. **Format 15 is a statement surface over an existing computation, not a new capability.** Annex D.32 documents
   the `HIGHEST-ALGEBRAIC` / `LOWEST-ALGEBRAIC` / `SMALLEST-ALGEBRAIC` intrinsics and this format as
   alternatives to each other, and those intrinsics already implement the IN-ARITHMETIC-RANGE screen. The
   production, a `SetContentKind` on the bound node, and one binder arm reusing that computation is the shape —
   **not** a fresh value calculator. Its class-condition twin (the same seven words after `IF`) is [[PB225]],
   which must be swept with it so the two surfaces share one evaluator.
2. **Format 8 needs `PicCategory.FunctionPointer` and the P13 prototype signature**, because SR20's last
   sentence ("The function-prototypes associated with identifier-12 and identifier-13 shall have the same
   signature") and GR14's EC-FUNCTION-PTR-INVALID both need a signature to compare. Do not add the category
   without it — `a_dead_lookup_is_also_unverified`.
3. **Annex A.1 items 174 and 176 land in the same change set** as their general rules — a required
   implementor-definition with no documentation row is not "implemented".

## 5. THE SIBLING SWEEP THE FIXER MUST DO

* Every other omission justified by "documented non-support" in a code comment: the same inherited-citation
  shape can be anywhere the phrase appears. Grep for `Annex A.3` and `A.4` in `src/` and re-derive each against
  the annex, mechanically, the way §1 did.
* `PicCategory` also has no `MessageTag` member, and the same "no member ⇒ unreachable by construction"
  reasoning is written at `IntrinsicArgumentRules.cs:64` and `IntrinsicBinder.cs:1340`. That one **is** covered
  by a real A.3 disposition (item 4) — see [[PB453]] — but the reasoning pattern is identical and should be
  re-read at the same time.
* The reserved-word rows for the five Format-15 value words already exist
  (`src/Cobol.Net.Editions/ReservedWords.Table.cs`); adding the production must not disturb their edition
  gating — run the edition-gate sweep (`feedback_edition_gate_sweep`).
* `constructs.json` gains a row for each format when it lands, with its introduction edition.

## 6. ROWS

* **`GR-14.9.39.4-14` / `-15`** (Format 8) — NOT-IMPLEMENTED. Rests on `e1_fp_decl` / `e2_fp_bare`: the operand
  is refused at declaration with COBOLNET0899, so the general rules are unreachable; GR15 additionally owes
  Annex A.1 item 174, measured absent from `docs/CONFORMANCE.md`.
* **`GR-14.9.39.4-32` / `-33` / `-34` / `-35` / `-36`** (Format 15) — NOT-IMPLEMENTED. Rest on the measured
  COBOL0001 cascade for every one of the five value legs, against a compiling `FLOAT-BINARY-64` / `FLOAT-LONG`
  receiver in the same file; GR34/GR35 additionally owe Annex A.1 item 176, measured absent.

Neither format is optional: A.4's complete SET inventory is three items and includes neither, and A.3 contains
neither. Both are §4.2.16 conformance surface.
