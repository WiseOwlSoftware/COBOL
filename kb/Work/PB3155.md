# PB3155 — a landing's Linux reds never reach tier 0a of the finisher's re-gate

> ⚙ **flags:** process-only

Source: `w1076a-PB2921-report.md` "## Finisher", bullet "Why the Windows gate missed both", item (b) (filed by the clerk, 2026-10-14). Items (a) and (c) of that bullet: (a) is the same mechanism as PB3112 and went into its body; (c) is the batched-gating design (the landing's Linux whole-population legs caught it before CI) and is not filed.

**The mechanism.** Tier 0a, "red at the previous gate", takes its reds from build-local's own previous run: `scripts/gate_plan.py` `read_previous_run` (called from the `--previous-run <dir>` argument, `gate_plan.py:740` and `:767` as of origin/main 70ab2a49e; verify before editing), fed by `scripts/build-local.ps1`. It never reads `TestResults/linux-gate/*.trx`, where the landing's Linux gate (`scripts/linux-gate.sh`) leaves its reds. So when a landing stops on a Linux red, the finisher's re-gate has no such red in its previous Windows run, tier 0a is empty of them, and leg 1 does not run the very tests that failed. The finisher must run them by hand to know the fix worked. This is a CI-invariant leak path (PB1957): the one signal that names the red is dropped between the Linux gate and the re-gate.

**The evidence** (branch `worktree-wf_d289834a-bf8-1`, w1076a / PB2921, 2026-10-14). The landing stopped `=== ENQUEUE: GATE RED (Linux) on 739b86210141` with `LINUX GATE: RED (unit conformance)`. Both reds were the branch's own (main 8e17ea04d is CI-green; neither file differs on main):

- `NulByteDriftTests.NoTrackedTextFileContainsANulByte` (golden `conformance-suite/cases/_unassigned/pb546_odo_national_tail.out` pinned raw UTF-16BE bytes, two NULs);
- `IntrinsicFunctionDifferentialTests.StagedLoudResidue_FailsLoud_NeverWrong` (pinned as a loud stage a shape PB3030 had closed on the branch).

The finisher's re-gate, run 20261014T104510Z-ae3675, read `=== BUILD-LOCAL GATE: LEG 1 ONLY (batched gating, PB2515): GREEN`, and "neither fixed test was in leg 1, so both were run on the gate's build" by hand (NulByteDriftTests 4/4 Passed, StagedLoudResidue 1/1 Passed). Both reds also sit in leg 2 for tiering reasons (PB3112 for the first; no impact map for the second), so tier 0a was the only route by which a re-gate could have run them.

**Fix direction** (the finisher's, not designed here): feed the landing's Linux trx reds into tier 0a, so a re-gate's leg 1 runs every case that was red at the last Linux gate of that branch. An implementer decides where the reds are read (build-local.ps1 passing the linux-gate trx directory, or `read_previous_run` taking both sources) and pins it with a drift test that fails if a gate input directory with trx reds is not read by the planner. Do not add a shim over `--previous-run`: change the callers (CLAUDE.md rule 4).

**Sites:** `scripts/gate_plan.py` (`previous_gates`, `read_reds`, `TRX_WRITERS`, `audit_trx_writers`, `build_plan`, the CLI), `scripts/run_gate_legs.py` (`Host.plan`), `scripts/linux-gate.sh` (a comment at its results directory), `tests/Cobol.Net.Tests.Unit/GateLegDriftTests.cs`, `docs/rearchitecture/DESIGN-test-build-ci.md` §3.14.2.

## Landed (wave 20261026, group C2)

**Re-probe** (this worktree, before the fix): a `Failed` result for
`NulByteDriftTests.NoTrackedTextFileContainsANulByte` planted in `<worktree>/TestResults/linux-gate/unit.trx`, and a
listing holding it with 50 other cases. `gate_plan.py` planned it tier 1, legs `[2]`: not in leg 1. After the fix the
same probe plans it tier 0a, in leg 1, and the summary prints `red keys (tier 0a) — linux gate …: 1`.

**Fix.** ONE reader of a worktree's previous gates, `gate_plan.previous_gates(worktree, previous)`: build-local's
previous run (`--previous-run`, chosen by `run_gate_legs.Gate.previous_run`) gives the timings and its reds; the Linux
gate's newest run, `<worktree>/TestResults/linux-gate/` (`LINUX_GATE_RESULTS`; linux-gate.sh empties it first, so it
holds only the newest run), gives its reds only, since another host's durations would mis-time this host's plan. The
gate driver (`run_gate_legs.Host.plan`) and the CLI (`--worktree`, default the script's own) both plan from it, and
`build_plan` takes the reds by source, records each source's count in the plan (`"reds"`: its red keys and how many
name a case discovered on this host, so a red whose display name differs between hosts is visible) and prints it. No shim over
`--previous-run`: its one caller in the driver changed. Every live tool that writes a trx file into a worktree is a row
of `gate_plan.TRX_WRITERS`: the gate (its previous run), the Linux gate (its newest run) and the battery (nothing: it
runs in its own detached worktree at a batch head). `GateLegDriftTests.EveryTrxWriter_IsARedSourceOfThePlan_OrSaysWhyNot`
runs `gate_plan.py --audit-trx-writers` and is red when a live tool writes a trx file with no row, when a row's tool is
gone, or when a row names a results directory its tool never writes.

**Tests.** `gate_plan.py --self-test`: six new arms (no previous gate on either host; a passing Linux run adds no red;
both hosts' reds under their own labels; the Linux gate gives no timings; a Linux-only red, renumbered by a partition
change, is tier 0a in leg 1 and counted; the writers audit's three findings). The drift test above.

**Same mechanism:** PB3184 (filed separately from PB3165's finisher; the same reader) lands with this change.

**Not covered here, by design:** a merge-queue BOUNCE's reds live in GitHub's CI run, not in the worktree (a reader
would download them); the Linux gate's `selftests` and `guard` legs write no trx (a self-test whose inputs change
re-runs at the next gate anyway).
