# PB3155 — a landing's Linux reds never reach tier 0a of the finisher's re-gate

> ⚙ **flags:** process-only

Source: `w1076a-PB2921-report.md` "## Finisher", bullet "Why the Windows gate missed both", item (b) (filed by the clerk, 2026-10-14). Items (a) and (c) of that bullet: (a) is the same mechanism as PB3112 and went into its body; (c) is the batched-gating design (the landing's Linux whole-population legs caught it before CI) and is not filed.

**The mechanism.** Tier 0a, "red at the previous gate", takes its reds from build-local's own previous run: `scripts/gate_plan.py` `read_previous_run` (called from the `--previous-run <dir>` argument, `gate_plan.py:740` and `:767` as of origin/main 70ab2a49e; verify before editing), fed by `scripts/build-local.ps1`. It never reads `TestResults/linux-gate/*.trx`, where the landing's Linux gate (`scripts/linux-gate.sh`) leaves its reds. So when a landing stops on a Linux red, the finisher's re-gate has no such red in its previous Windows run, tier 0a is empty of them, and leg 1 does not run the very tests that failed. The finisher must run them by hand to know the fix worked. This is a CI-invariant leak path (PB1957): the one signal that names the red is dropped between the Linux gate and the re-gate.

**The evidence** (branch `worktree-wf_d289834a-bf8-1`, w1076a / PB2921, 2026-10-14). The landing stopped `=== ENQUEUE: GATE RED (Linux) on 739b86210141` with `LINUX GATE: RED (unit conformance)`. Both reds were the branch's own (main 8e17ea04d is CI-green; neither file differs on main):

- `NulByteDriftTests.NoTrackedTextFileContainsANulByte` (golden `conformance-suite/cases/_unassigned/pb546_odo_national_tail.out` pinned raw UTF-16BE bytes, two NULs);
- `IntrinsicFunctionDifferentialTests.StagedLoudResidue_FailsLoud_NeverWrong` (pinned as a loud stage a shape PB3030 had closed on the branch).

The finisher's re-gate, run 20261014T104510Z-ae3675, read `=== BUILD-LOCAL GATE: LEG 1 ONLY (batched gating, PB2515): GREEN`, and "neither fixed test was in leg 1, so both were run on the gate's build" by hand (NulByteDriftTests 4/4 Passed, StagedLoudResidue 1/1 Passed). Both reds also sit in leg 2 for tiering reasons (PB3112 for the first; no impact map for the second), so tier 0a was the only route by which a re-gate could have run them.

**Fix direction** (the finisher's, not designed here): feed the landing's Linux trx reds into tier 0a, so a re-gate's leg 1 runs every case that was red at the last Linux gate of that branch. An implementer decides where the reds are read (build-local.ps1 passing the linux-gate trx directory, or `read_previous_run` taking both sources) and pins it with a drift test that fails if a gate input directory with trx reds is not read by the planner. Do not add a shim over `--previous-run`: change the callers (CLAUDE.md rule 4).
