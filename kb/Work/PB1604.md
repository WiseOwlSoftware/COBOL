Filed 2026-09-26 by the **train-61 lander** from the w61f implementer report (PB1276/PB1277).

## Repro
```
FD F RECORD IS VARYING IN SIZE.
01 R. 05 A PIC X(2). 05 T OCCURS DYNAMIC FROM 2 TO 5. 10 E PIC X(3).
```
→ `VaryMax` = 2 while `VaryMin` = 8: every WRITE of R is out of range.

## Mechanism
`src/Cobol.Net.Compiler/Binding/Model/FileModel.cs#MaxDynamicExtent` takes a table's maximum from
`item.OccursSpec?.Max ?? 0`, and `DataBinder.Odo.cs:70` binds `Max = 0` for OCCURS DYNAMIC (no integer-5), so the
table adds nothing to the maximum. §13.18.43.4 8) b) (`OK §13.18.43.4 8)` in the w61f report) sizes the maximum
record from the maximum size of each item, and §8.5.1.9 gives a dynamic-capacity table an implementor-defined
MAXIMUM CAPACITY when TO integer-5 is absent (here `TO 5` is present and is still ignored).

## To close
Needs a maximum-capacity determination for `OCCURS DYNAMIC` without `TO` (shared with PB1410, which has no runtime
maximum either: only the constant `MaxOccurrences`), then one maximum read by both the record-sizing model and the
runtime. Not PB1277's unit (its landing was the byte model).

## Retired 2026-09-26 (w62n implementer) — the premise is impossible source
- **The repro does not compile.** On the w62n build (base bbbf81896) the note's program draws
  `p.cob(13,11): error COBOLNET1526: OCCURS DYNAMIC on 'T': a dynamic-capacity table shall not be defined in the
  FILE SECTION (ISO §8.5.1.9.1)`, and so do the three other routes a description reaches a file record by: a
  `TYPE` clause (whole record, or a subordinate group), `SAME AS`, and an SD record. The rule is
  `OK §8.5.1.9.1 3)` — "it may be defined in any place, other than the file section, in which a fixed-capacity
  table may be defined" (restated by Annex D.3.7: "except in the file section"). COBOLNET1526
  (`DataBinder.DynamicResolve`) predates the arm: it landed in DEVLOG 657 (a456bf809), and the dynamic-table arm
  of `FileModel.MaxDynamicExtent` was added later by PB981 (8af541fff) — dead from its first day. The w61f
  "VaryMax 2 < VaryMin 8" was the arm's arithmetic, observed on source the compile already refused.
- **The note's rule reading was also off:** TO integer-5 is not a maximum. §8.5.1.9.1 calls it the EXPECTED
  capacity, which "may be exceeded with a nonfatal exception"; the MAXIMUM capacity is always the implementor's
  (DOC-A.1-60, `CobolDynTable.MaxOccurrences`), TO or not. Had a record been able to hold one, GR8 b) would have
  sized it at that maximum, not at 5. No determination is needed, and PB1410 (the runtime resource bound) is
  untouched.
- **What changed:** the unreachable dynamic-capacity-table arms of the record-sizing family were removed rather
  than "fixed", because each one computed an answer for source that cannot exist: `FileModel.MaxDynamicExtent`
  (+ its `PerOccurrenceMax` helper), the `IsDynamic` term of `FileModel.HasVaryingTableBeneath` (the GR8 a) twin),
  and the `IsDynamicTable` test in `RecordLayout.ContiguousPlaceOf` (the key-window walk). The invariant is stated
  once, on `MaxDynamicExtent`, and pinned by `OccursDynamicGuardTests.FileSectionDynamicTable_EveryRoute_Rejected1526`
  (TYPE whole-record, TYPE subordinate, SAME AS, SD). `docs/COBOLNET_FILES_DESIGN.md` §"implied RECORD clause"
  and the D25 paragraph no longer claim a record counts a dynamic table.
- **The green test that held the arm:** `RecordSizeModelTests.DynamicCapacityTable_CountsItsMinimumCapacityInTheMinimum`
  (PB1277) asserted VaryMin 8 for exactly this illegal record — its helper checked PARSE errors only, so the
  COBOLNET1526 binder error never reached it. The test is removed, the helper now asserts the source binds
  clean, and the witness is retired from GR-13.18.43.4-8 by batch `w62n-PB1604-batch.json` (row stays CONFORMS;
  GAP unchanged).
