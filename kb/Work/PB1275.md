## Measured

### Finding property-clause — ISO/IEC 1989:2023 §8.4.3.9.3 SR5/SR6; §13.18.42.4 GR2 (object/pointer/index branch) (rejects-legal-source; rows GR-13.18.42.4-2, GR-13.18.42.4-1)

**Mechanism.** An object-property reference is refused in any SET statement (BoundSetObjectRef / BoundSetPointer are outside OoBinder's store-polarity taxonomy), so the object/pointer/index branch of the implicit SET method is unreachable and an object property cannot be a SET sender

**Repro.** Class OBJECT WS `01 R USAGE OBJECT REFERENCE PROPERTY.`; client with REPOSITORY `PROPERTY R.`: `SET R OF A TO A.` -> COBOLNET0843 'the object-property reference 'R' OF 'A' occurs in a statement (BoundSetObjectRef) outside the classified store taxonomy'. Same for `01 Q USAGE POINTER PROPERTY.` with `SET Q OF A TO ADDRESS OF W.` (BoundSetPointer), and for `SET B TO R OF A.` (the property as the SENDER). Probes gr1_objref, gr1_pointer, gr1_objref_get_set.

**Expected, from the standard.** §8.4.3.9.3 SR6: the object property 'may be specified wherever a data item with that description would be valid as a receiving item' (SR5 the same for sending); SET is the statement that stores an object reference or a pointer, and §13.18.42.4 GR2 spells the implicit setter for exactly those classes as `SET data-name TO LS-data-name`. Expected: `SET R OF A TO A` then `IF R OF A = A` -> SAME; `SET B TO R OF A` compiles.

**Observed.** OoBinder.cs:~54 refuses any statement type not classified in BoundStores with 0843; the two SET bound nodes that carry object references and pointers were never added, so the only way to exercise the object/pointer setter is from inside the class. The GET branch is reachable through a relation condition (probe gr1_objref_get -> SAME), which is why GR1 is affected only on the SET-sender path.

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/OoBinder.cs (store taxonomy, ~line 54)

**Mechanism.** An object-reference-valued property in SET Format 5 (as sender or receiver) is refused because BoundStores.StoreKindOf returns null for BoundSetObjectRef, so OoWrapPropertyOps cannot classify the polarity and stages COBOLNET0843

**Expected from the spec.** Both compile: SR5/SR6 — the property 'may be specified wherever a data item with that description would be valid' as a sending / receiving item, and an object reference of class CPA8 is a valid SET Format 5 sender and receiver (§14.9.39). `SET A TO INNER OF B` runs the GET only (GR1); `SET INNER OF B TO A` runs the SET only (GR2).

**Observed / reasoning.** BoundStores.cs:272 `public StoreKind? Visit(BoundSetObjectRef n) => null;` — the taxonomy hole OoWrapPropertyOps (:49-:57) turns into a loud stage. Siblings to sweep: every other `=> null` Visit in BoundStores is the same refusal for a property operand in that statement.

### Refuter evidence — row `SR-8.4.3.9.3-3` (PARTIAL)

PARTIAL — SR3 requires a GET only when the property is 'used as a sending item'. BoundStores classifies a STRING INTO receiver (and the Into-only case) as ReadWrite, so OoWrapPropertyOps demands a GET for an occurrence that §14.9.43.3 SR10 names as 'the receiving operand' and nothing else. A WITH NO GET property used as the STRING INTO target is legal source: it is a receiving-only use, which §8.4.3.9.4 GR2 serves with temp-2 and no GET. The compiler rejects it with COBOLNET0843 citing SR3. The true sending half is enforced: MOVE, DISPLAY, IF (including a non-first OR operand), PERFORM UNTIL, EVALUATE subject, INSPECT TALLYING and REPLACING, ADD TO, SUBTRACT FROM and COMPUTE all raise 0843. The other write-only uses of a NO-GET property are accepted and run (MOVE TO, ACCEPT FROM DATE, INITIALIZE, UNSTRING INTO, ADD GIVING, COMPUTE =). The rule's sending condition is therefore over-applied on the STRING arm, which rejects legal source. [editions as adjudicated: 2002, 2014, 2023 (the object property is part of the OO facility introduced by ISO/IEC 1989:2002; absent from X3.23-1985)]

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/OoBinder.cs#PropertyGet; src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs#OoTryBindPropertyReference
