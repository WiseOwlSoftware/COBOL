# PB5816 - at --std 85 UNSTRING from a zero-size sender runs neither overflow phrase, where the 1985 rule makes it an overflow

**What is wrong.** At `--std 85`, `UNSTRING OG INTO WX WITH POINTER WP` where `OG` is an OCCURS DEPENDING ON group at count 0 (a zero-size sender) and `WP` is 1 runs neither ON OVERFLOW nor NOT ON OVERFLOW (`unz.cob`: `X=[QQQ] P=01`). `§1985:VI.6.27.4 GR17` makes a pointer value "greater than the size of the data item referenced by identifier-1" an overflow, and 1 is greater than 0. The 2023 zero-length guard is applied with no edition test: `StringEmitter.EmitUnstring` wraps the whole statement in `if (src.Length != 0)` at every edition (kb/Work PB1184, from `§2023:14.9.48.4 GR2`). Cause (a): at 2023 the result is right. I ran `unz.cob` at `--std 85` with the tracked probe runner: it printed `X=[QQQ] P=01` and then `OVERFLOW-B`, so neither phrase of the first UNSTRING ran. Harm: wrong_answer. The checker's confidence: high.

**Why the program is legal.** `OCCURS 0 TO 8 DEPENDING ON` is legal at 1985 (`§1985:VI.5.8.3 SR5`: integer-1 may be zero), and the group's size as a sender with the count 0 and the object outside the group is zero (`§1985:VI.5.8.4 GR3a`). 1985 has no zero-length rule; GR17a makes a POINTER value above the size of identifier-1 an overflow when the UNSTRING is initiated, so 1 > 0 gives ON OVERFLOW. The same program with the count 1 and POINTER 2 gives `OVERFLOW-B` at both editions, so only the zero-length guard differs. The control `stz.cob` (STRING into the zero-size receiver) overflows correctly at `--std 85`: no sibling there. `StringUnstringBinder.cs` is among the pin's changed files, and the reader's observation on 1df234fa72 matches the pin.
