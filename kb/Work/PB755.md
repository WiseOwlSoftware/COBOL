# PB755 — OPEN — a `?` on an UNDERLINED word

Found 2026-09-06 in the PB695 family-3 implementer's report (NEW DEFECT A), which reported it rather than folding
it into that cluster because TIGHTENING is the opposite direction from PB695's mechanism (PB695 relaxes words the
page prints plain; this one restores a word the page prints underlined) and needs its own negative golden.
Verified independently on main at `0a24276f`.

## What the standard prints — rendered and MEASURED, not read

`python scripts/spec/clause_page.py 12.4.5.9.2` → **PDF page 355, printed folio 325**;
`python scripts/render-spec-page.py 355`. The LOCK MODE clause's only general format is

```
             ╭ MANUAL    ╮ ┌                           ╭ RECORD  ╮ ┐
LOCK MODE IS ┤           ├ │ WITH LOCK ON [ MULTIPLE ] ┤         ├ │
             ╰ AUTOMATIC ╯ └                           ╰ RECORDS ╯ ┘
```

**The underline was re-measured off the PDF's vector rectangles as second reader**, not inherited from the
report and not taken from the transcription. Every word's box and every horizontal rule within −4..+6 pt of it,
raw, no threshold:

| word | box (x) | rule found under it | cover |
|---|---|---|---|
| `LOCK` (first) | 86.56–112.03 | 87.96–111.07 @ gap 0.81 | **90.8%** |
| `MODE` | 115.12–144.04 | — no rule overlaps the box at all | **0.0% — PLAIN** |
| `IS` | 146.38–155.14 | — | **0.0% — PLAIN** |
| `WITH` | 251.70–278.69 | — | **0.0% — PLAIN** |
| `LOCK` (second) | 281.78–307.24 | 283.11–306.22 @ gap 0.96 | **90.8%** |
| **`ON`** | **311.09–325.35** | **312.52–324.43 @ gap 0.96** | **83.5% — UNDERLINED** |
| `MANUAL` / `AUTOMATIC` | 172.06–214.02 / 172.05–230.11 | 173.40–213.08 / 173.40–229.19 | 94.6% / 96.1% |

`ON` is a two-letter word, the population this toolchain has been burned by (`figure_extract.py`'s own docstring
records the 9.0 pt width floor that once silently mis-read every two-letter required word), so it was read off
the RAW rules rather than from any census. `python scripts/spec/figure_extract.py 355 --band 150 260` agrees
independently: *"underlined (REQUIRED per 5.2.2), 7 distinct: AUTOMATIC, LOCK, MANUAL, MULTIPLE, ON, RECORD,
RECORDS"*. So does the transcription's own figure note (`specs/ISO_COBOL.md:13591`): *"`LOCK` (both occurrences),
`MANUAL`, `AUTOMATIC`, `ON`, `MULTIPLE`, `RECORD`, and `RECORDS` are underlined in the printed standard (required
words); `MODE`, `IS`, and `WITH` are printed without underlines."* Three independent readings, one answer.

The rule that decides it:

- `cite.py --check 5.2.2 "They are shown in uppercase and underlined in general formats"` → **OK §5.2.2
  (Keywords)** — *"Keywords are reserved words or context-sensitive words. They are shown in uppercase and
  underlined in general formats. They are required in order to select the functionality associated with that
  keyword …"*. Underlined ⇒ REQUIRED.
- `--check 8.3.2.4.3 "uppercase words that are not underlined are called optional words"` → **OK §8.3.2.4.3
  (Optional words)** — the complement, and it is what licenses `WITH?`, not `ON?`.
- `--check 5.2.6.2 "may be explicitly specified or that portion of the general format may be omitted"` → **OK
  §5.2.6.2 (Brackets)** — the outer bracket is what makes the whole `WITH LOCK ON … RECORDS` phrase omittable,
  and the inner `[ MULTIPLE ]` is what makes `MULTIPLE?` correct. Neither bracket touches `ON`.

## What the grammar spells

`src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4:107-114` on main, verbatim:

```
// COBOL-2002 LOCK MODE clause (ISO §12.4.5.9): MANUAL / AUTOMATIC (no EXCLUSIVE), with an optional
// single/multiple record-lock granularity.
lockModeClause
    : LOCK MODE IS? (MANUAL | AUTOMATIC) lockOnPhrase?
    ;
lockOnPhrase
    : WITH? LOCK ON? MULTIPLE? (RECORD | RECORDS)
    ;
```

Four of the five decisions in `lockOnPhrase` are right — `WITH?` (plain), `LOCK` (underlined), `MULTIPLE?`
(bracketed), `(RECORD | RECORDS)` (a plain brace, exactly one). The fifth, `ON?`, is the defect: a `?` on a word
the page underlines.

⚠ **Where the family-3 branch differs, and why it does not overlap.** `worktree-agent-a334880f747b22665`
(train 17) relaxes `lockModeClause` to `LOCK MODE? IS? …` — MODE, correctly, is PLAIN on folio 325. That change
is in the OTHER rule and the OTHER direction; `lockOnPhrase` is untouched on that branch and still reads `ON?`.
The two edits do not collide, and landing family 3 neither fixes nor worsens this one.

## Why it matters

§4.2.10 3) makes an extension conformant only when the implementation DOCUMENTS it, and nothing documents this
one — there is no leniency descriptor, no dialect gate, no `docs/` row. What the compiler has instead is a
private dialect: source written `WITH LOCK MULTIPLE RECORDS` compiles here and is a syntax error everywhere
else, so the acceptance is a migration trap pointing the wrong way. It is the exact complement of the PB695
family — that campaign asked which OPTIONAL words a rule REQUIRES; this asks which REQUIRED words a rule made
optional — and `audit_grammar_optional_words.py`, now at 0 candidates, is structurally blind to it: the audit
scans for a required token that the page prints plain, never for a `?` on a token the page underlines.

## The fix shape

Delete the `?`:

```
lockOnPhrase
    : WITH? LOCK ON MULTIPLE? (RECORD | RECORDS)
    ;
```

Nothing downstream reads the token — `DataBinder.MapLockMode` selects on `lm.AUTOMATIC()` and
`lm.lockOnPhrase()?.MULTIPLE()`, the underlined words — so the tightening is confined to the parser.
Ship with a NEGATIVE golden pinning `WITH LOCK MULTIPLE RECORDS` as a syntax error and a POSITIVE golden for the
fully written `WITH LOCK ON MULTIPLE RECORDS` (and its `WITH` omitted, which stays legal), so the tightening is
proved not to have eaten a printed spelling. The positive belongs at `--std 2002`, the edition the clause is
introduced at.

## Sweep — the general form, which nothing in the tree measures

A `?` on an UNDERLINED word is the mirror image of PB734's `?` on a printed BRACE, and of PB695's missing `?` on
a plain word. All three are the same question asked of one rule — *does this ANTLR operator match the
delimiter/underline the page prints?* — and only one third of it has a mechanical measure today. The audit
already extracts every general format's words WITH their underline state
(`figure_extract.py` + `audit_grammar_optional_words.py`'s 320 measured formats); the missing direction is one
inversion of the same join: for each rule, every token it makes OPTIONAL that the format prints UNDERLINED. That
belongs in `audit_grammar_optional_words.py` as a second candidate class rather than in a hand-kept list, and it
would have caught this, PB756 and PB758 in one run.
