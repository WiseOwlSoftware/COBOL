## Measured

### Finding typedef-clause — ISO/IEC 1989:2023 §13.18.58.3 SR2 (under-rejects; rows SR-13.18.58.3-2)

**Mechanism.** SR2 recursion is checked only as a side effect of per-REFERENCE expansion: ExpandType starts an empty 'expanding' set per referencing item and nulls TypeRefName before testing, so a recursive type declaration that no storage item expands first is never rejected

**Repro.** WORKING-STORAGE with only: 01 T TYPEDEF. 05 A PIC X. 05 B TYPE T.   (or 01 T TYPEDEF TYPE T.   or 01 T1 TYPEDEF. 05 A TYPE T2. 01 T2 TYPEDEF. 05 B TYPE T1.)  PROCEDURE: DISPLAY "OK". STOP RUN.  cobol.exe x.cob --run  (probes out13/probe/typedef-clause/td03bnoref, td18selfnoref, td19indirnoref)

**Expected, from the standard.** Compile-time rejection. §13.18.58.3 SR2: 'The description of the subject of the entry, including its subordinate items, shall not contain a TYPE clause that directly or indirectly references this type definition' -- a property of the declaration, independent of any reference.

**Observed.** All three compile clean and print OK. The same declarations ARE rejected (COBOLNET1530) once a WORKING-STORAGE item references the type (td01self, td02indir, td03selfroot) because AllItems() walks Roots before TypeDecls, so the storage item's expansion reaches the template member while its TypeRefName is still set. Fix shape: detect cycles on the type-declaration reference graph (each template's own TypeRefName plus every member's) as a declaration-time check, or seed 'expanding' with the enclosing type declaration when expanding a template member.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.cs#ExpandTypes; #ExpandType

### Row SR-13.18.49.3-3 — PARTIAL (no separate finding; the adjudicator's / refuter's record)

Code location: `src/Cobol.Net.Compiler/Binding/DataBinder.cs#ExpandSameAs; src/Cobol.Net.Compiler/Binding/DataBinder.cs#CloneItem`

SR3 (--check 13.18.49.3 -> OK 3)). Three legs: (a) chain cycle - the `expanding` set / ReferenceEquals(target,item) test (SameAsMutualCycle_Rejected1557: 01 A SAME AS B / 01 B SAME AS A); (b) data-name-1 IS a group to which the subject is subordinate - the subject-ancestor walk (SameAsOfOwnAncestor_Rejected1557); (c) indirect through subordinates - CloneItem re-expands a copied subordinate's pending SAME AS in its new position, where the ancestor walk catches it: probes p06_sr3 (`01 R. 05 A SAME AS G.` / `01 G. 05 B SAME AS R.`) and q08_sr3sub (three-entry variant) -> COBOLNET1557 citing SR3; no infinite recursion. All legs rejected with 1557. || REFUTED: PARTIAL — The SR3 cycle check is expansion-ORDER dependent: CloneItem re-enters ExpandSameAs with a fresh empty expanding set and ExpandSameAs nulls SameAsName before recursing, so when the subordinate entry is expanded first the cycle is silently truncated. `01 G. 05 X PIC X. 05 Y SAME AS H. 01 H SAME AS G.` (H's data-name-1 G contains a SAME AS referencing the subject H - an SR3 violation) raises NO COBOLNET1557; the program is refused only by a cascade COBOLNET0881 (PICTURE required) on the truncated PIC-less clone of Y. Reversing the declaration order (H first) yields the correct 1557. The adjudicator's probes only covered the orders that work.
