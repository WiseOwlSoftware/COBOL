# PB4084 — PowerShell entry scripts parse a Python tool's stderr as part of its answer

**Sites:** `scripts/start-session.ps1` (`$acctOut = & python @acctArgs 2>&1`, then `ConvertFrom-Json`),
`scripts/account-profile.ps1` (`--seed-plan`'s `2>&1`, then `ConvertFrom-Json`; `--seed-check` printed as is),
`scripts/orchestrator/autostart.ps1` (`adopt_main.py adopt ... 2>&1`, whose LAST line is said as the adoption's outcome),
`scripts/session-probe.ps1` (`ruleset.py check 2>&1`, whose FIRST line is printed as the queue's state, and
`gate_slot.py status 2>&1`, whose first line is the failure's report: a stderr line ahead of the answer takes its place;
review R2-3 of PB4046)

**What is wrong.** Each one captures a Python tool with `2>&1` and treats the whole capture as the tool's answer. PB4046
found the same shape in the supervisor's `Invoke-Py`, where a stderr line from a tool that SUCCEEDED made its JSON answer
unreadable. There it is fixed: stdout is the answer, and stderr is said and never parsed. These four scripts do it by
hand. A Python warning on stderr makes `start-session.ps1` throw on the account JSON (no restart session starts) and
`account-profile.ps1` throw on the seed plan. In `autostart.ps1` it replaces the adoption line it reports.

**Fix direction.** One rule in one place: a small dot-sourced PowerShell helper that runs a Python tool and returns its
stdout, saying its stderr. The supervisor's `Invoke-Py` and these four use it. A drift test then refuses a `2>&1` capture
of a Python tool that is parsed. `scripts/python-resolve.ps1` is the existing dot-sourced Python helper and a candidate home.
