# PB186

Registered from the PB164 Step D review fleet's out-of-wave disposition (finding R-a). The four
SortEmitter windowed-key findings were KILLED as filed — the fleet's refuters proved the arm is unreachable
today — and this note preserves the one true half of them rather than letting a killed finding erase a latent
defect.

**THE ARM.** `src/Cobol.Net.Compiler/CodeGen/Verbs/SortEmitter.cs`, `TableCompare`'s elementary switch:

```csharp
{ Category: PicCategory.Numeric, IsFloat: false } when k.StoreAsImage =>
    $"{RuntimeApi.NumParseImage(pa, k.ProfileName)}.CompareTo({RuntimeApi.NumParseImage(pb, k.ProfileName)})",
```

`NumParseImage` is the SIGNED image lane. Its unsigned twins exist and are used elsewhere —
`CobolNum.ParseImageU` / `ParseImageU128`, added to the runtime and `RuntimeApi` by the Step D arm-1
dissolution and consumed by `NumericRenderer`'s windowed arms — but this call site never gained the dispatch on
the profile's signedness that every other windowed decoder now carries. A key whose item is an UNSIGNED
`PIC 9(19..38) COMP-5` (a `ulong` or `UInt128` carrier, item 208's container rule) holding a value at or above
2^63 / 2^127 therefore decodes to a NEGATIVE `long`/`Int128` and sorts before every smaller value — the exact
lane defect the review wave caught and fixed in `FormatImage(UInt128)` (the F11 half), one call site away.

**WHY IT IS LATENT, AND WHY THAT IS NOT A REASON TO LEAVE IT.** `StoreAsImage` is true only for a
REDEFINES-classed / whole-group-aliased leaf, and `SortBinder` rejects a classed item as a key outright, so no
program reaches this expression today ([[feedback_reachability_is_measured_not_deduced]] — the fleet's refuters
measured that, they did not deduce it). But the guard is in a DIFFERENT file from the defect, it is not pinned
by anything, and the whole direction of PB164 has been to widen exactly such screens: the day SortBinder admits a
classed key — or the day a table element's key becomes image-backed — this returns a wrong ORDER with no
diagnostic. That is a wrong answer, not a formatting question: §14.9.40.4 GR8 (`--check` OK) compares key data
items "according to the rules for comparison of operands in a relation condition", and for a NUMERIC key those
rules are §8.8.4.2.4's algebraic comparison — the same derivation that made PB164 wave 2's IEEE sort key decode
to a `double` instead of comparing raw big-endian bytes.

**FIX SHAPE:** dispatch on the profile the way the other windowed decoders do (the `KeyColumns.Build` ByteForm
dispatch that PB164 wave 2 built for the IEEE key is the model), so the unsigned lane is reached by
construction; then add the signedness axis to whatever pins the sort-key decode, and — the part that makes the
latency go away — pin the SortBinder screen that currently holds this unreachable, so a future widening of it
fails a test instead of shipping the wrong order.
