# PB4523 — basic-time-format-fraction-separator: Feature request (COBOL 2023): basic time format with fractional seconds (hhmmss.sss) without the decimal separator in the data

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

In a BASIC time format with fractional seconds (`hhmmss.sss`), ISO/IEC 1989:2023 says the decimal separator is part of
the format but does not appear in the data. libcob 3.2 writes the separator into the value FORMATTED-TIME and
FORMATTED-DATETIME return, and SECONDS-FROM-FORMATTED-TIME and TEST-FORMATTED-DATETIME require it in their argument.
FORMATTED-TIME therefore returns one character too many, and a basic value without the separator is read as invalid.
Class: feature missing, edition 2023. The 2014 lineage is not decisive: the committee draft that led to
ISO/IEC 1989:2014 (CD 1.2, 2009) carries the same "does not appear" sentence, but its normative clause 15.3.1.4 also
has Table 22, which "summarizes permissible date and time formats and the values that may be associated with them" and
gives `051427.812479168` for `hhmmss.sssssssss`, with a note saying the separator is used "in both formats and the
associated data". libcob follows that table. In 2023 the table is an informative annex, so the normative sentence
governs alone. Fuzz night 2026-11-03, signature OUTPUT_DIFFERS:15.40.

## Minimal test case

Free reference format (`-free`).
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. BASFRAC.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 WS-SECS PIC 9(5)V999 VALUE 45296.125.
01 WS-NUM  PIC 9(5)V999 VALUE 0.
01 WS-POS  PIC 99 VALUE 0.
PROCEDURE DIVISION.
    DISPLAY "FT  [" FUNCTION FORMATTED-TIME ("hhmmss.sss" WS-SECS) "]"
    DISPLAY "LEN " FUNCTION LENGTH
        (FUNCTION FORMATTED-TIME ("hhmmss.sss" WS-SECS))
    COMPUTE WS-NUM = FUNCTION SECONDS-FROM-FORMATTED-TIME
        ("hhmmss.sss" "123456125")
    DISPLAY "SFT " WS-NUM
    COMPUTE WS-POS = FUNCTION TEST-FORMATTED-DATETIME
        ("hhmmss.sss" "123456125")
    DISPLAY "TST " WS-POS
    STOP RUN.
```

## Environment

cobc (GnuCOBOL) 3.2.0 on WSL2 Ubuntu. `cobc -x -free -std=cobol2014 -o p prog.cob && ./p` (no diagnostic other than the
distribution's `_FORTIFY_SOURCE` redefinition notice). cobc 3.2 has no `-std=cobol2023`; the request is for the 2023
behaviour.

## Observed result

```
FT  [123456.125]
LEN 000000010
SFT 00000.000
TST 07
```
Exit code 0.

## Expected result (per ISO)

ISO/IEC 1989:2023 §15.3.3.2: "The decimal separator does not appear in the data associated with a basic common time
format with fractional seconds representation." §15.3.3.6.1 NOTE 1 gives a basic value without it: "The value
"1014278124Z" interpreted according to the format 'hhmmss.ssssZ'" is 10:14:27.8124 UTC. §15.41.4 rule 1: "The returned
value is a representation of the standard numeric time contained in argument-2 according to the format in argument-1."
§15.79.4 rule 1 takes S as "the portion of argument-2 corresponding to the seconds subfield of argument-1".
§15.92.4 rule 1: "If no format problems or range problems occur during the evaluation of argument-2 according to the
format in argument-1, the value returned is zero."
Expected output under the 2023 rules:
```
FT  [123456125]
LEN 000000009
SFT 45296.125
TST 00
```
The extended format (`hh:mm:ss.sss`) keeps its separator in the data, and cobc handles that format as the standard says.
Edition: 2023 only. In the 2014 lineage (CD 1.2) the same sentence stands beside a normative Table 22 whose basic
fractional example values carry the separator, so a 2014 implementation that writes it follows part of its own
standard; 2023 moved those examples to an informative annex (where they still show the separator, without normative
force). This is therefore a request to follow 2023, not a bug against `-std=cobol2014`.

## Our compiler

WiseOwl COBOL (fresh judge) prints the expected output above: `FT  [123456125]`, `LEN 000000009`, `SFT 45296.125`,
`TST 00`.

## Fix site

libcob/intrinsic.c (read in a 3.3-dev tree; the function names are unchanged since 3.2): `add_decimal_digits` always writes
`COB_MODULE_PTR->decimal_point` before the fraction digits, with no test of `format.with_colons`; `test_decimal_places`
(called by `test_formatted_time`) always calls `test_char (decimal_point, ...)`; `seconds_from_formatted_time` reads the
fraction from offset 7 in a basic format, which assumes a separator at offset 6. `cob_valid_time_format` already parses the
separator correctly as part of the format.

## Draft issue

**Title:** Basic time format hhmmss.sss: the decimal separator is written to and required in the data

As posted (owner-reviewed, 2026-11-04):

In a basic time format with fractional seconds, such as `hhmmss.sss`, the decimal separator is part of the format but not of the data, so 12:34:56.125 is `123456125`. libcob puts the separator into the data: FORMATTED-TIME, FORMATTED-DATETIME and FORMATTED-CURRENT-DATE return one character too many, and SECONDS-FROM-FORMATTED-TIME and TEST-FORMATTED-DATETIME reject the correct value.

### To reproduce

`basfrac.cob` (attached) formats 12:34:56.125 with `hhmmss.sss` and reads `123456125` back:

~~~~
       IDENTIFICATION DIVISION.
       PROGRAM-ID. BASFRAC.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 WS-SECS PIC 9(5)V999 VALUE 45296.125.
       01 WS-NUM  PIC 9(5)V999 VALUE 0.
       01 WS-POS  PIC 99 VALUE 0.
       PROCEDURE DIVISION.
           DISPLAY "FT  [" FUNCTION FORMATTED-TIME
               ("hhmmss.sss" WS-SECS) "]"
           DISPLAY "LEN " FUNCTION LENGTH
               (FUNCTION FORMATTED-TIME ("hhmmss.sss" WS-SECS))
           COMPUTE WS-NUM = FUNCTION SECONDS-FROM-FORMATTED-TIME
               ("hhmmss.sss" "123456125")
           DISPLAY "SFT " WS-NUM
           COMPUTE WS-POS = FUNCTION TEST-FORMATTED-DATETIME
               ("hhmmss.sss" "123456125")
           DISPLAY "TST " WS-POS
           STOP RUN.
~~~~

    cobc -std=cobol2014 -x basfrac.cob && ./basfrac

### What happens

3.2.0 and 3.3-dev r5751 both print

~~~~
FT  [123456.125]
LEN 000000010
SFT 00000.000
TST 07
~~~~

`basfrac2.cob`, attached, shows the same for the standard's example `1014278124Z` (`hhmmss.ssssZ`), for a combined date and time format and for FORMATTED-CURRENT-DATE; only its extended-format control is right.

### What should happen

`basfrac` should print:

~~~~
FT  [123456125]
LEN 000000009
SFT 45296.125
TST 00
~~~~

ISO/IEC 1989:2023 15.3.3.2: "The decimal separator does not appear in the data associated with a basic common time format with fractional seconds representation." The same rule is in the 2014 FCD, 15.3.1.2.1.2; 2002 has none of these functions.

ISO 8601 keeps the decimal sign in a basic time (`hhmmss,ss`, example `232050,5`; ISO/WD 8601-1 of 2016-02-16, clause 4.2.2.4); ISO/IEC 1989 15.3.3.2 takes it out, and for these functions that rule controls.

### Why it happens

In `libcob/intrinsic.c`, `cob_valid_time_format` and `parse_time_format_string` keep `with_colons` for basic and extended, but the separator code ignores it. `add_decimal_digits` always writes `COB_MODULE_PTR->decimal_point`, `test_decimal_places` always expects it, and `seconds_from_formatted_time` reads a basic fraction from offset 7, one past where it starts. The three `cob_intr_formatted_*` functions make the returned item as long as the format string, and `cob_intr_seconds_from_formatted_time` copies that many characters of argument-2 for a time format, whatever its size.

### Proposed fix

The attached `n10-formatted-time-basic-fraction.patch` (against 3.3-dev r5751) makes `add_decimal_digits` write the separator and `test_decimal_places` expect it only for an extended format, and makes `seconds_from_formatted_time` read a basic fraction from offset 6. A new `time_format_data_length` gives the data length, used for the FORMATTED-* results and for how much of argument-2 SECONDS-FROM-FORMATTED-TIME copies for a time format. With the patch both programs print the expected output.

This changes values that existing programs and stored data may hold, in every dialect: for a basic format with fractional seconds the FORMATTED-* functions return one character less, and a value with the separator that an earlier release wrote, such as `123456.125` for `hhmmss.sss`, is now rejected (SECONDS-FROM-FORMATTED-TIME returns 0 with EC-ARGUMENT-FUNCTION, TEST-FORMATTED-DATETIME returns 7). An argument-2 shorter than its time format is now rejected with EC-ARGUMENT-FUNCTION where r5751 read past it. The patch adds a NEWS item under "Changes that potentially effect recompilation of existing programs"; it does not tie the change to a dialect option.

It adds test 1100 "FUNCTION FORMATTED-TIME basic fractional seconds" to `run_functions.at`, corrects five tests that expected the separator in basic data, and adds ChangeLog entries. `make check`: 1373 expected, 9 skipped, 0 failed (1372 unpatched); the new test fails without the patch.
