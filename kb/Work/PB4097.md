# PB4097 — another run unit reads a dead transaction's uncommitted changes

## What happens

A run unit with `APPLY COMMIT` changes a file after its last COMMIT and is killed. Until some run unit opens the file
for writing (which performs the deferred rollback), another run unit that opens it INPUT reads the dead transaction's
uncommitted change with I-O status `00`. The reader uses no IGNORING LOCK and no sharing phrase. The same reader, on the
same file, after the same death, sees two different files depending on whether an unrelated run unit wrote in between.

Reproduced on main 802352531 (adjudicator) and again by the refuter, with main's compiler and Debug runtime:

    RELATIVE (probe committer.cbl: APPLY COMMIT ON KF RLF; COMMIT after REL 1 "R-ONE"; then REL 7 "R-SEVEN"; killed)
      owner alive:  reader  OPEN 61 61 / IDX END 61 / REL END 61
      owner killed: reader  OPEN 00 00 ... REL 0001 R-ONE / REL 0007 R-SEVEN / REL END 10   <- wrong answer
                    readerig (READ ... IGNORING LOCK): the same                                 <- wrong answer
                    readerio (OPEN I-O): REL 0001 R-ONE / REL END 10                         <- the rollback happens here
                    reader  (again): REL 0001 R-ONE / REL END 10                             <- now correct
    SEQUENTIAL (seqcommit2.cbl: COMMIT after S-ONE, S-TWO; then OPEN I-O, READ, REWRITE "S-CHANGED"; killed)
      owner alive:  seqreader OPEN 61 / SEQ END 61
      owner killed: seqreader OPEN 00 / SEQ S-CHANGED / SEQ S-TWO / SEQ END 10              <- wrong answer
                    seqextend OPEN-EXTEND 00                                                 <- the rollback happens here
                    seqreader OPEN 00 / SEQ S-ONE / SEQ S-TWO / SEQ END 10                   <- now correct

## The rules (each checked with `python scripts/spec/cite.py --check` on 2026-10-30, OK)

- §9.1.18.5: "When a run unit terminates abnormally, all file changes made since the previous commit or, if none, the
  beginning of the run unit are rolled back for all files for which there are active APPLY COMMIT clauses." The same
  clause: "In both cases all file and record locks are then released". The rollback comes first; the locks go after it.
  No interval exists in which the dead run unit's locks are gone and its uncommitted changes are still in the file.
- §9.1.18.3: "so that they will remain in that state even in the event of subsequent abnormal termination". Abnormal
  termination keeps exactly what was committed.
- §9.1.17: "The files and data are protected from the activity of other run units that wish to access any of the same
  records and data during the execution of that set of program instructions."
- §9.1.16: "While locked by a given file connector, a record is not accessible to another file connector in the same or
  a different run unit, except by the execution of a READ statement with the IGNORING LOCK phrase." And: "The implementor
  may specify circumstances other than a locked logical record that result in the return of a locked record status."
- §9.1.13.9 1) a): "An attempt is made to open a physical file that is currently open by another file connector in the
  sharing with no other mode." (I-O status 61.)
- §9.1.13.8 1): "I-O status = 51. The input-output statement is unsuccessful due to an attempt to access a record that is
  currently locked by another file connector."

Why it is not latitude: the implementor-defined default sharing mode (§9.1.15) and default record locking
(§12.4.5.9.4 1) b) 2.) decide which locks THE READER sets. They cannot change what the file holds after §9.1.18.5's
rollback. Annex D.2.5, which the design cited, is informative; its sentence covers a LIVE "current run unit", the
"with all other" or "with read only" sharing modes AND a read "with the ignoring lock phrase", and tolerates a value read
BEFORE a rollback, never one read after it. An externally killed process reaches §9.1.18.5 because it is not a normal
termination (§14.6.11's commit never ran) and because of §9.1.18.3's durability promise; DOC-A.1-75 already documents
that a dead run unit is rolled back (the refuter, point 4).

## The conforming behavior (the fix design is the implementer's, from DESIGN-runtime-library.md)

From the moment the owner dies, every access by another run unit sees the rolled-back state, or is refused. It never
sees the dead transaction's uncommitted change with a successful status.

- **Preferred:** complete the dead owner's rollback before any other run unit observes the file: at the reader's OPEN,
  or at its first statement that meets the dead holding. That is §9.1.18.5's end state. It covers every path below,
  the IGNORING LOCK read included (IGNORING LOCK bypasses locks; it does not undo a rollback §9.1.18.5 already made).
- **Fallback, only where the reader cannot perform the rollback** (its host or permissions): refuse as the still-standing
  locks would. In the probe the dead RLF was opened OUTPUT with no SHARING clause, i.e. SHARING WITH NO OTHER
  (DOC-A.1-77), and §9.1.18.5 keeps the file lock until after the rollback, so the reader gets `61` at OPEN
  (§9.1.13.9 1) a)), exactly as when the owner is alive. `51` at the READ (§9.1.13.8 1)) applies only where the dead
  connector's sharing mode admitted the reader's OPEN (SHARING WITH ALL OTHER, the posture DOC-A.1-152 documents), as a
  circumstance the implementor documents under §9.1.16; it does not rest on §14.9.30.4 GR9, which needs record locking
  enabled on the reader (WiseOwl's default reader has none, DOC-A.1-153). Under this form an IGNORING LOCK read of a dead
  holding still needs the rollback, since GR12 lets it past the locks.

## Landed (2026-11-01, wave 20261808 group B)

**Re-probed on the branch before the fix** (probes `E:/COBOL-coord/scratch/w20261808b/probe/`, `drive.ps1 keyed|seq`): the keyed
reader printed `REL 0007 R-SEVEN` with the owner killed, the sequential one `SEQ S-CHANGED`; both reproduced. After the fix the
reader prints `REL 0001 R-ONE / REL END 10` and `SEQ S-ONE / SEQ S-TWO`, with `readerig` (IGNORING LOCK) the same, and the
live-owner `OPEN 61` unchanged.

**The root.** The dead-owner step (§9.1.18.5's rollback) was the privilege of a connector with a WRITABLE handle; a reader was
told to read the file "as it stands" (D.2.5). Now every access settles first. **Keyed:** a connector with no writable handle
runs the step through a handle opened for the purpose (`KeyedConnector.SettleDeadOwnersBeside`: a scratch store adopted through a
new read/write handle under the exclusive mutex taken through it, `RollBackDeadOwners`, promotion), at its OPEN
(`SettleDeadOwnersOfTheOpen`: its own handle goes back first, because a mandatory share mode refuses a writer beside INPUT's
`READ ONLY` handle) and at its statement's coherent entry (`Enter`, the shared mutex let go for the step;
`KeyedStore.FindDeadOwner` reads the TRANSACTIONS tree only when page 2 names a transaction). **Sequential:** the OPEN INPUT runs
the entry step (`FileConnector.EnterPhysicalFile`; a lock directory the process cannot list is '37' there as for a writable OPEN),
and a READ that tests no lock (IGNORING LOCK, ADVANCING ON LOCK) settles the dead transactions all the same
(`SequentialConnector.SettleDeadTransactions`, asked by `FileRegistry.JournalConflict`). A holder a reader meets dead at its lock
test (it died after the entry's probe) is refused '51' (`KeyedConnector.HoldingsGate`). Refusal where the reader cannot write
the file: '37' at the OPEN, '30' at an entry, never the dead change. The fallback statuses are the OPEN's host-refusal statuses
rather than the note's '61'/'51': nobody holds a lock any more, so §9.1.13.9 1) and §9.1.13.8 1) name no holder; §14.9.27.4 GR3
and §9.1.13.6 1) name the refusal.
