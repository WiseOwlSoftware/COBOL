# Landing, 2026-11-16: the external data item's identity is the record, the item's own name and its storage

**Re-probe before the fix** (`run_probe.py`, `r1-group-differ.cob`, on a Debug build of main ed7d9b6d97): exit 65,
COBOL1575 at (37,54), at `--std 85` and `--std 2023`, as the note says; the control `r1-same-ctrl.cob` printed `B[SECOND-REC]`.
**After:** `r1-group-differ` exit 0, `B[SECOND-REC]`, at 85 and 2023. `r1-name-differ.cob` (another item name at the same
characters) and PB5857's other-positions case are still COBOL1575.

**Shape.** `DataItem.ExternalItemIdentity` is the external record's externalized name (`DataItem.ExternalizedRecordName`, the one
spelling of `§2023:13.18.22.4 GR5`, which `LinkageBinder`'s cell keying now reads too), the item's own name, the occurrence a
2002 subscript selects, and its offset and width. The names of the groups between are gone (`§1985:X.4.5.4 GR2`). The item's
name stays, as PB5857 decided: "that same external data item" (`§1985:VIII.2.4.4 GR8`) is a named description entry. Every
reader asks the one member: the RELATIVE KEY (COBOL1575) and FILE STATUS (COBOL1573) agreement and the externality checks in
`ExternalFileConnectorRules.Check`, the PADDING segment of `FileEntryIdentity`, and the run-time descriptor `OoEmitter` emits.

**Sibling fixed.** The record part was the root's data-name, so two programs whose records are named KA and KB and both write
`AS "PB5888KEYS"` (one external record by GR5) were refused, and two records of one data-name with different `AS` literals
were taken as one. It is now the externalized name.

**Goldens.** `cases/VIII.2.4@1985-ACCESS-MODE-CLAUSE/pb5888-external-relative-key-groups-differ-85` (accepted, `B[SECOND-REC]
KEY[0002]`) and `cases/12.4.5-File-control/pb5888-external-relative-key-record-as-literal` (2023, accepted, the same output).
