# PB941 — LANDED — the two directives that save and restore nothing

## Landed (wave 49, 2026-09-22)

Re-probed on the implementer's own build first: `d2` printed `INSIDE` / `AFTER-POP-NO-CHECK` (the OFF escaped the
region), `d3` aborted on EC-BOUND-SUBSCRIPT, `d6` printed `NO-WARNING` with no diagnostic — the note held in full.
After the fix `d2` aborts exactly as `d3` does, and `d6` draws COBOLNET2297 on its `>>POP TURN` line.

The shape is the one this note asked for, and it is ONE mechanism, not TURN-only save code:
`DirectiveStateStack` (Frontend/Preprocessor) owns the PUSH/POP pairing — a stack per pushable directive ROW,
`PUSH ALL` fanning out to `CompilerDirectiveCatalog.PushableRows` (derived from the PUSH row's own
`excludedDirectives`, i.e. §7.3.22.4 GR2's five), a POP removing the most recent save, and GR2's "unsuccessful"
answered by `Apply`. Every stage that HOLDS directive state runs an instance and registers a carrier: the normalizer
(SOURCE FORMAT), the conditional-compilation driver (DEFINE — the whole table, "all instances" — and its running
FLAG options), the post-COPY stages (TURN, REF-MOD-ZERO-LENGTH, FLAG-02, FLAG-14 as revocable event timelines;
COBOL-WORDS and LEAP-SECOND as group-prefix values taken where the first unit begins). `DirectiveSiteProcessor`
records the final text's ops, blanks the lines and issues the one warning (COBOLNET2297, the A.1 item 140
mechanism, `docs/CONFORMANCE.md` DOC-A.1-140). `DirectiveStateRegistry` accounts for every pushable directive, and
`DirectiveStateStackTests` is the drift gate the note asked for (registry == pushable set; every carrier a real
stage; every `DirectiveResults` member claimed; every carried row a PUSH/change/POP case). Golden
`2023/pb941_push_pop_directive_state` (TURN both directions, nesting, the unsuccessful POP, DEFINE, SOURCE FORMAT).
Design: `DESIGN-frontend-grammar.md` §3.6.1.

The six SR-7.3.20.3 / SR-7.3.22.3 rows stay with `PB929` as this note recorded. The implicit PUSH ALL / POP ALL of
§14.9.28.4 GR14 is still modelled for TURN only — reported as a lead, not fixed here.

Source: the **PB395 (exception checking + PERFORM ranges) implementer report**, "New defects" item 2, which
reports `>>PUSH ALL … >>POP ALL` around a `>>TURN` as compiling clean and restoring nothing, and says in terms

§7.3.22.4 GR1 saves the named directive's state; GR2 saves ALL of them bar the five listed; GR3 keeps the pushed
directive's effect active. §7.3.20.4 GR1 restores the named one, GR3 restores all of them, and **GR2 requires a
warning when the POP has nothing to restore** — which Annex A.1 item 140 states as an implementor obligation:

> 140) POP directive (warning mechanism for an unsuccessful POP directive). **This item is required.** This item
> shall be documented in the implementor's user documentation. (7.3.20, POP directive, General rule 2)

An A.1 item marked *required* is not a latitude. `DOC-A.1-140` is claimed here for that reason.

## Why the harm flags say `wrong_answer`

A `>>PUSH ALL` wrapping a region that turns checking OFF is the IDIOMATIC use of the directive — it is what a
programmer writes to suppress a check locally without disarming the rest of the compilation group. Today the
suppression **escapes the region** and runs to the end of the source element (and, since §7.3.22.4 GR2 covers
every directive, so does an escaped `>>SOURCE FORMAT`, `>>DEFINE`, `>>LEAP-SECOND`, `>>CALL-CONVENTION` or
`>>REF-MOD-ZERO-LENGTH`). The consequence is a program that silently does not raise an exception condition it was
written to raise — a wrong answer produced by a construct whose whole purpose is to be scoped.

## The code site, and the shape the fix should take

`DirectiveSiteProcessor` — the Frontend stage **train 43's cluster 3 added** (`PB395`), which is already where
these lines are consumed and where the directive SITES are produced ahead of `TurnDirectiveProcessor`. The state
to push and pop is `TurnState`, plus every other per-directive state the frontend threads.

⛔ **CLAUDE.md rule 5 applies here, and the estimate in the source report ("the stage belongs there") understates
it.** §7.3.22.4 GR2's subject is *the state of ALL of the directives* — it is a rule about a SET, not about
`>>TURN`. A fix that pushes and pops `TurnState` alone satisfies the probe above and leaves the other directives
exactly as broken, and does it in a shape where the NEXT directive to gain state is silently omitted again
(`feedback_model_the_rule_shape_not_one_case`). The supportable shape is **one directive-state container the
frontend already threads, with save/restore as operations on the container**, so a new directive joins by being
in the container rather than by being remembered — paired with a drift test that asserts every directive the
catalog knows (minus GR2's five) is in the pushed set. That test is also the only thing that can make GR2's
exclusion list true rather than asserted.
