# PB5412 - at --std 85 a FROM or INTO operand that names exactly the record area by reference modification, by a subscripted one-occurrence table or by a 66 RENAMES of the whole record compiles: StorageSharing.IsRecordAreaOf answers false for every such form (READ, RETURN, WRITE, REWRITE, RELEASE)

**Sites:**

- `src/WiseOwl.Cobol.Compiler/Binding/Model/StorageSharing.cs#IsRecordAreaOf`
- `src/WiseOwl.Cobol.Compiler/Binding/Validation/StatementValidation.cs#CheckPhraseOperandIsNotRecordArea`
- `src/WiseOwl.Cobol.Compiler/Binding/Validation/StatementValidation.cs#CheckIntoReceiver`
- `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/MoveBinder.cs#BindFromPhrase`

**Mechanism.** Every FROM and INTO phrase asks `StatementValidation.CheckPhraseOperandIsNotRecordArea` (COBOL6827, in force below 2023 by `RecordAreaRule.InForce`), which asks `StorageSharing.IsRecordAreaOf`. That predicate counts a record of the file (or of a SAME RECORD AREA peer) and a subordinate at offset 0 of the record's full width, and answers false for any reference-modified operand, any operand under an OCCURS, and a level-66 RENAMES alias, a choice `docs/FILES_DESIGN.md` D31(b) states. Each of those forms can denote exactly the record area: `R1 (1:10)` of a 10-character record, `R1-E (1)` where `01 R1-T. 05 R1-E OCCURS 1 TIMES PIC X(10)` redefines it, `R1 (1:)`, and `66 ALLR RENAMES first THRU last`. The rule forbids "the same storage area" whatever the reference names it by, so the five statements accept the area the rule refuses. Ten readers reported the same mechanism under ten rules.
