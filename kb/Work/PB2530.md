# PB2530 — the lander's leg is never ordered longest first

## Measured (w1033 gate performance diagnosis, `E:\COBOL-coord\scratch\reports\w1033-perf-gate-report.md` section 2)

`simulate.py` replays measured per-test durations onto 32 workers and reproduces real makespans (247 s modeled vs
255 s measured). With Server-GC durations, 24 corpus partitions and the 8-way `OptionalWordSubsetDriftTests` split
(both landed by kb/Work PB2526/PB2527): **188 s in name order, 118 s longest first** (the floor, sum/32, is 117 s).
The remaining single-collection poles are about 100 s each (`IntrinsicFunctionDifferentialTests`,
`UsageInheritanceDriftTests`), so their start time decides the wall.

## Site

`scripts/run_gate_legs.py#Gate._plan` returns no plan in lander mode ("no plan (lander)", DESIGN-test-build-ci
section 3.14.1); with no handshake `tests/_shared/GateLegs.cs#GateTestFramework` is xunit's framework exactly, so
`GateCollectionOrderer` never runs and collections start in xunit's UniqueID order. The implementer plan already orders
leg 2 longest first, timed from the shared timings store every gate publishes to (kb/Work PB2527), so the durations
the lander would need already exist at `<git common dir>/cobol-gate-timings/timings.json`.

## Shape (an owner decision: it changes the lander contract of section 3.14.1)

Give the lander a ONE-leg plan: every case in leg 1, collections longest first from the shared timings store, handed
through the same handshake and checked by the same identity and population checks — never a selection, no fail-fast,
no slot. The alternative (an orderer in the no-handshake path) would change what an IDE and CI run, and is rejected.
Measure the lander's whole-Conformance wall before and after on the same host, arms alternated.
