# PB4539 — relative-delete-rewrite-empty-slot-succeeds: RELATIVE file: DELETE and REWRITE of a deleted or empty slot return status 00 instead of 23

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

For a RELATIVE file in random or dynamic access, DELETE and REWRITE of a relative record number whose slot holds no
record (a record already deleted, or a slot never written inside the file's extent) succeed with I-O status 00 instead
of raising the invalid key condition with status 23. The REWRITE also does not create the record: a following READ of
the same key returns 23.

## Minimal test case


## Expected result (per ISO)

§14.9.10.4 4): for a relative file in random or dynamic access the DELETE "logically removes from the physical file that
record identified by the content of the relative key data item"; "If the physical file does not contain the record
specified by the key, the invalid key condition exists" (the same sentence closes §14.9.10.4 3) and 4)). §14.9.35.4 21):
the REWRITE "logically replaces the record identified by the relative key data item"; "If the file does not contain the
record specified by the key, the invalid key condition exists." §14.9.35.4 21) continues: "the I-O status in the rewrite file connector is set to the
invalid key condition '23'" (DELETE's invalid key condition for a missing record is the same status). After the first DELETE record 1 no longer exists, so the second DELETE and the REWRITE are invalid key
conditions and the READ finds no record. These rules are in the 2014 edition (relative files are a 1985 feature, no change
listed in `docs/VERSION_CHANGE_REFERENCE.md`). Expected:
```
DELETE 1   00
DELETE 2   23
REWRITE    23
READ       23
```

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`) prints the expected output above, with no diagnostic.

## Fix site

libcob/fileio.c `relative_delete` and `relative_rewrite` (random/dynamic arm): each seeks to the slot and reads its
record-size prefix, returning 23 only when that read fails (past end of file). A slot whose size prefix is 0 (deleted, or
never written) is not tested, so `relative_delete` writes size 0 again and returns 00, and `relative_rewrite` writes the
data while leaving the size 0 and returns 00. `relative_read` does treat size 0 as "no record", hence the READ's 23.
Confirmed in the GnuCOBOL 3.2 release source (libcob/fileio.c).

## Draft issue

**Title:** RELATIVE file: DELETE and REWRITE of a deleted or never-written record return status 00, not 23

As posted (owner-reviewed, 2026-11-04):

For a RELATIVE file in RANDOM or DYNAMIC access, DELETE and REWRITE of a record number whose slot is empty, because the record was deleted or never written, give I-O status 00 and take the NOT INVALID KEY branch, and the REWRITE stores no record; READ of the same key gives 23.

### What happens

3.2.0 and 3.3-dev r5751 both print

~~~~
DELETE 1   00
DELETE 2   00
REWRITE    00
READ       23
~~~~

and the same with `-std=cobol2002`, `-std=cobol85` and the default dialect. `delhole.cob`, attached, shows the same for a slot that was never written, and `deltwice.cob` shows that the INVALID KEY phrase is not taken (`SECOND DELETE OK 00`).

### What should happen

The second DELETE and the REWRITE give status 23, run their INVALID KEY phrase and change nothing in the file. DELETE general rule 4 (ISO/IEC 1989:2023 14.9.10.4) and REWRITE general rule 21 (14.9.35.4) make this the invalid key condition, and then, by 9.1.14, "execution of the input-output statement that recognized the condition is unsuccessful and the file is not affected". The same rules are in the 2002 final draft and the 2014 FCD (REWRITE rule 20 there).

### Why it happens

In `libcob/fileio.c`, `relative_read` treats a record-size word of 0 as an empty slot, but `relative_rewrite` (random and dynamic access) and `relative_delete` return 23 only when the size word cannot be read, past the end of the file.

### Proposed fix

The attached `n10-relative-delete-rewrite.patch` (against 3.3-dev r5751) makes `relative_delete` and `relative_rewrite` return `COB_STATUS_23_KEY_NOT_EXISTS` before writing anything when the size word for the key is 0. Both leave the file offset where it was before the patch, so later READ NEXT and READ PREVIOUS return the same records. It adds the testsuite case "DELETE / REWRITE of a missing RELATIVE record" to `run_file.at`, with ChangeLog entries. `make check`: 1373 expected, 9 skipped, 0 failed (1372 unpatched); the new test fails without the patch.

Other behavior changes:

- A program with a USE procedure for the file now runs it where it continued silently.
- A program with no FILE STATUS clause, no INVALID KEY phrase and no USE procedure now stops with `libcob: error: record key does not exist (status = 23)`, as it does today for any other status 23.
- In sequential access, a DELETE after the program has moved the RELATIVE KEY to an empty slot now gives 23 instead of 00.
- A zero-length record, which WRITE stores as an empty slot with status 00 (a separate defect), now gives 23 at DELETE and REWRITE, as at READ.
