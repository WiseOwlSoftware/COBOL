## What a user sees today (after train 1021)

PB1425 admitted a subscripted identifier-3 (`BAL OF AR(I)`). The property's wrap puts the GET before the whole statement
and the SET after it, and both render identifier-3 lazily, so a receiving property whose object is selected by a
run-time value reached two different objects. The train landed a NARROW REFUSAL instead of that wrong answer: a
RECEIVING property (GR2 write-only or GR3 read-modify-write) whose identifier-3 contains a data-name subscript or
argument (a `SUB_IDENTIFIER` token) or a function-identifier is refused with COBOLNET0899
`receiving-reference-shape-not-implemented` (`OoBinder.OoWrapPropertyOps`; the flag is
`DataBinder.OoPendingPropertyOp.SelectedByValue`, set by `ReferenceResolver.SelectsByValue`). Before PB1425 the same
shape drew COBOLNET2096. A literal subscript (`MOVE 3 TO BAL OF AR(2)`) and every SENDING reference stay admitted.
Negative golden: `tests/conformance/negative/pb1425-property-receiver-selected-by-value.cob`. Closing this note
removes that refusal (`rejects_legal_source`) and fixes the unsubscripted sibling below (`wrong_answer`).

## The rule

- §14.7.7 4) b) (checked: `cite.py --check 14.7.7 "Item identification for the receiving data items is done as each
  data item is accessed"`): the intermediate result "is stored in or combined with and then stored in each single
  resulting data item in the left-to-right order", and a receiver is identified as it is reached.
- §14.9.2.4 1): Format 1's initial evaluation is only the operands before TO; the sum is stored as the new value of
  identifier-2, so `BAL OF AR(I)` is identified after I has been stored (I = 2), and its value is read then.
- §14.9.25.4 1) (checked): "Item identification for identifier-2 is performed immediately before the data is moved to
  the respective data item."
- §8.4.3.9.4 3): a property that both sends and receives is ONE temporary; its GET and its SET are the same property
  of the same object, so they cannot reach two different objects.

Expected therefore: GET AR(2) (20), add 1, SET AR(2) to 21; AR(1) untouched. For the sibling: the second `BAL OF D`
is combined with the value the first store left (101), giving 102. §8.4.3.9.4 GR1/GR3 do not name the moment of the
GET, so the sibling wants an adjudication line; the subscripted case does not (the GET and the SET reaching different
objects is wrong under any reading).

## Code site

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/OoBinder.cs#OoWrapPropertyOps`: every pending property op of a
statement puts its Prelude and GET BEFORE the whole bound statement and its SET AFTER it
(`new BoundSequence([.. pre, core, .. post])`). The receiver is the lazily rendered Place of identifier-3
(`ReferenceResolver.ObjectProperty.cs#ResolveObjectProperty`, the `Resolve(objRef)` arm).

## The fix shape (why the train did not land it)

The review proposed snapshotting the object reference into a temp in the prelude for the ReadWrite polarity. That
makes the GET and SET agree but identifies AR(I) at the START of the statement (AR(1), giving AR1=11), which
§14.7.7 4) b) also forbids. The correct shape interleaves each receiving property's Prelude + GET + SET with ITS OWN
target's store inside the statement: `BoundAddTo` / `BoundAddGiving` / SUBTRACT / MULTIPLY / DIVIDE / `BoundCompute`
carry `IReadOnlyList<Receiver> Targets`, MOVE carries its receivers, and the property wrap would attach per-receiver
steps (and skip the SET for a receiver whose store raised SIZE ERROR). That changes the bound receivers and their
emission plus the wrap: more than one mechanism, over the train's ~60-line limit. When it lands, delete the
`SelectedByValue` refusal and turn the negative golden into a positive one at 2002.

## Sweep to do with the fix

- Every multi-receiver arithmetic statement (ADD / SUBTRACT / MULTIPLY / DIVIDE Format 1 and GIVING, COMPUTE) and
  MOVE with a receiving property whose identifier-3 depends on an earlier receiver.
- SIZE ERROR on a property receiver: the SET should not run for the receiver that stays unchanged.
- A chained receiving property (`P OF Q OF AR(I)`): the inner GET is a sending op hoisted to the statement's start.
