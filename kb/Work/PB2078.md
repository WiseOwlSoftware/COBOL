## What a user sees today (after train 1021)

PB1425 admitted a subscripted identifier-3 (`BAL OF AR(I)`). The property's wrap puts the GET before the whole statement
and the SET after it, and both render identifier-3 lazily, so a receiving property whose object is selected by a
run-time value reached two different objects. The train landed a NARROW REFUSAL instead of that wrong answer: a
RECEIVING property (GR2 write-only or GR3 read-modify-write) whose identifier-3 contains a data-name subscript or
argument (a `SUB_IDENTIFIER` token) or a function-identifier is refused with COBOLNET0899
`receiving-reference-shape-not-implemented` (`OoBinder.OoWrapPropertyOps`; the flag is
`DataBinder.OoPendingPropertyOp.SelectedByValue`, set by `ReferenceResolver.SelectsByValue`). Before PB1425 the same
shape drew COBOLNET2096. A literal subscript (`MOVE 3 TO BAL OF AR(2)`) and every SENDING reference stay admitted.
Negative golden: `tests/conformance/negative/pb1425-property-receiver-selected-by-value.cob`. Closing this note
removes that refusal (`rejects_legal_source`) and fixes the unsubscripted sibling below (`wrong_answer`).

## The rule

- §14.7.7 4) b) (checked: `cite.py --check 14.7.7 "Item identification for the receiving data items is done as each
  data item is accessed"`): the intermediate result "is stored in or combined with and then stored in each single
  resulting data item in the left-to-right order", and a receiver is identified as it is reached.
- §14.9.2.4 1): Format 1's initial evaluation is only the operands before TO; the sum is stored as the new value of
  identifier-2, so `BAL OF AR(I)` is identified after I has been stored (I = 2), and its value is read then.
- §14.9.25.4 1) (checked): "Item identification for identifier-2 is performed immediately before the data is moved to
  the respective data item."
- §8.4.3.9.4 3): a property that both sends and receives is ONE temporary; its GET and its SET are the same property
  of the same object, so they cannot reach two different objects.

Expected therefore: GET AR(2) (20), add 1, SET AR(2) to 21; AR(1) untouched. For the sibling: the second `BAL OF D`
is combined with the value the first store left (101), giving 102. §8.4.3.9.4 GR1/GR3 do not name the moment of the
GET, so the sibling wants an adjudication line; the subscripted case does not (the GET and the SET reaching different
objects is wrong under any reading).

## Code site

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/OoBinder.cs#OoWrapPropertyOps`: every pending property op of a
statement puts its Prelude and GET BEFORE the whole bound statement and its SET AFTER it
(`new BoundSequence([.. pre, core, .. post])`). The receiver is the lazily rendered Place of identifier-3
(`ReferenceResolver.ObjectProperty.cs#ResolveObjectProperty`, the `Resolve(objRef)` arm).

## The fix shape (why the train did not land it)

The review proposed snapshotting the object reference into a temp in the prelude for the ReadWrite polarity. That
makes the GET and SET agree but identifies AR(I) at the START of the statement (AR(1), giving AR1=11), which
§14.7.7 4) b) also forbids. The correct shape interleaves each receiving property's Prelude + GET + SET with ITS OWN
target's store inside the statement: `BoundAddTo` / `BoundAddGiving` / SUBTRACT / MULTIPLY / DIVIDE / `BoundCompute`
carry `IReadOnlyList<Receiver> Targets`, MOVE carries its receivers, and the property wrap would attach per-receiver
steps (and skip the SET for a receiver whose store raised SIZE ERROR). That changes the bound receivers and their
emission plus the wrap: more than one mechanism, over the train's ~60-line limit. When it lands, delete the
`SelectedByValue` refusal and turn the negative golden into a positive one at 2002.

## Sweep to do with the fix

- Every multi-receiver arithmetic statement (ADD / SUBTRACT / MULTIPLY / DIVIDE Format 1 and GIVING, COMPUTE) and
  MOVE with a receiving property whose identifier-3 depends on an earlier receiver.
- SIZE ERROR on a property receiver: the SET should not run for the receiver that stays unchanged.
- A chained receiving property (`P OF Q OF AR(I)`): the inner GET is a sending op hoisted to the statement's start.

## Partly landed - 2026-10-07 (wave 1034 group D, PB2073 + PB2078)

Re-probed on the wave-1034 build: `f3` (`ADD 1 TO I, BAL OF AR(I)`) and `m1` (`MOVE 2 TO BAL OF AR(I), I`) were refused
COBOLNET0899, `f3b` (`ADD 1 TO BAL OF D, BAL OF D`) printed `TWICE 00101` -- confirmed. The note's shape was right and
is built: a property is its data item's stand-in, so its GET and SET go around ITS access and store.

- **Mechanism.** `DataBinder.OoClaimInterleavedReceiver` (called by `ExpressionBinder.ReceiverOf` for every arithmetic
  receiver, by `ArithmeticBinder` for the DIVIDE REMAINDER receiver and by `MoveBinder.Bind` for the written MOVE) marks the
  property op; `OoBinder.OoWrapPropertyOps` gives a marked op a `ReceiverBracket` (identifier-3's Prelude and the GET, the SET)
  under the new `BoundReceiverBrackets` node (`EcBinder` stamps and queries it like a `BoundSequence`), and
  `ReceiverBracketEmitter.Receive` -- called by `MoveEmitter.Emit` per target and by `ArithmeticEmitter.GuardedStore`, which
  now takes the receiver place -- emits them around that receiver, skipping the SET for a receiver whose store raised a size
  error. An unplaced bracket fails the compile. `ReceiverBracketDriftTests` pins the claim sites and the funnels.
- **Fixed (wrong answers).** `ADD 1 TO I, BAL OF AR(I)` -> AR(2) 21 (AR(1) untouched); `MOVE 2 TO BAL OF AR(I), I` -> AR(1)
  2 then I 2; `ADD 1 TO BAL OF AR(I) ON SIZE ERROR MOVE 2 TO I` -> AR(1) unchanged and not assigned; `ADD 1 TO BAL OF D, BAL OF D`
  -> 102 (also SUBTRACT, MULTIPLY, DIVIDE, COMPUTE, ADD GIVING, DIVIDE REMAINDER, MOVE with repeated receivers). Golden
  `2002/pb2078_property_receivers_in_turn`; the negative `pb1425-property-receiver-selected-by-value` is replaced by
  `negative/pb2078-property-receiver-selected-by-value-accept` (the shape that is still refused).
- **Residue (why the note stays open).** Every statement whose emitter does not store its receivers one at a time keeps the
  statement-level GET before and SET after, and the COBOLNET0899 refusal of a receiver selected by a run-time value (`OoBinder.
  OoWrapPropertyOps`, `op.SelectedByValue && !op.Interleaved`). The next statements to join the contract are the ones with a
  receiver loop or a store funnel: INITIALIZE, STRING / UNSTRING, INSPECT, ACCEPT, SET, READ / RETURN INTO (an implicit MOVE
  built through `MoveBinder.BindMoveOf`, which does not claim), CALL / INVOKE RETURNING: each binder claims through
  `OoClaimInterleavedReceiver` and each emitter store goes through `ReceiverBracketEmitter.Receive`; the unplaced-bracket
  check names a forgotten call. A separate, pre-existing instance of the same family: for those statements the SET also runs
  after the statement's own phrase bodies (`READ f INTO P NOT AT END DISPLAY P` reads P before the SET).

## Landed - 2026-10-08 (wave 1039 group A2)

Re-probed on the wave-1039 build (`E:/COBOL-coord/scratch/w1039a2/p/gen.py`, 15 probes): INSPECT TALLYING `BAL OF AR(I)`, STRING
and UNSTRING `POINTER` / `TALLYING IN` `BAL OF AR(I)`, a plain `ACCEPT NM OF AR(I)`, `CALL ... RETURNING BAL OF AR(I)`, `INVOKE ...
RETURNING BAL OF AR(I)` and `SET I, BAL OF AR(I) TO IX` drew COBOLNET0899 -- confirmed. The sweep found five wrong answers of the
same family: `UNSTRING Y DELIMITED BY "," INTO I NM OF AR(I)` stored into AR(2) (the wave-1037 bracket re-rendered identifier-3
at the store, though §14.6.4 7) identifies every UNSTRING operand first); `INSPECT NM OF AR(I) TALLYING I ... REPLACING` SET
AR(2) (§14.9.22.4 GR6); `PERFORM VARYING BAL OF AR(1) FROM 1 BY 1 UNTIL BAL OF AR(1) > 3` never ended (the SET ran after the
whole loop, so each UNTIL read the old value); `STRING ... WITH POINTER BAL OF D NOT ON OVERFLOW DISPLAY BAL OF D` and `CALL ...
RETURNING BAL OF D NOT ON EXCEPTION DISPLAY BAL OF D` showed the old value (the SET ran after the phrase bodies).

- **Mechanism.** A receiving property identifies ONE object: `OoBinder.OoWrapPropertyOps` evaluates identifier-3 once, with its
  Prelude, into an identified-object temporary (`DataBinder.OoCreateIdentifiedObjectTemp`, a `BoundSetObjectRef` step) and
  both accessors invoke on it (§14.6.4; §8.4.3.9.4 GR3). That makes the statement-level shape exactly §14.6.4 7)'s
  identification at the start, so the `SelectedByValue` flag, `ReferenceResolver.SelectsByValue` / `NamesAValue` and the
  COBOLNET0899 refusal are deleted. `ReceiverBracketEmitter` gains the second timing: `Identify(receivers)` opens the brackets as
  the statement's first operation, `Receive` closes one with its store (opening it only if not identified), `Settle(receivers)`
  closes them at one moment.
- **Placement per statement.** Identified as stored: SET Format 1 (§14.9.39.4 GR2), the PERFORM VARYING induction variable at
  each set and augment (§14.9.28.4 GR12), the SEARCH VARYING item at each increment (§14.9.37.4 GR3 b)), with the arithmetic
  statements and every MOVE as before. Identified at the start and SET with the store, before the phrase bodies: STRING (INTO,
  POINTER), UNSTRING (INTO, DELIMITER IN, COUNT IN, POINTER, TALLYING), CALL (BY REFERENCE arguments and RETURNING, at a successful
  return; §14.9.4.4 GR3 a); the one receiver list is `BoundCallProgram.Receivers`). Statement-level, which is exact for them:
  INSPECT (its claim is removed: no phrase body, GR6), ACCEPT from a device, INVOKE RETURNING (§14.9.23.4 GR7 a)), SET Format 5
  (GR9 states no per-receiver identification) and the pointer formats.
- **Goldens.** `2002/pb2078_property_receivers_identified` (every residue shape plus the five sibling wrong answers, values
  derived in its header). The negative `negative/pb2078-property-receiver-selected-by-value-inspect-tally` is retired: the
  shape is legal and no longer refused. `ReceiverBracketDriftTests` pins the claimants, the start-identifying emitters and the
  one identified object. Not in the golden: a plain ACCEPT from the console (the conformance harness supplies no stdin; probe
  p4 shows it accepted into AR(1)).
- **Not changed (PB1275's determination).** STRING INTO stays a receiving-only property (§14.9.43.3 SR10, §8.4.3.9.4 GR2): no
  GET, so the positions STRING does not write come from the temporary, not from the property.
