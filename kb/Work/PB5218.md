**The decision (owner, 2026-11-10: "This is precisely what the Unix make and Windows MSBuild utilities are for. They rerun
only what is required due to changes."; "Yes, proceed with the PB5207 redesign").** PB5207 stage 1, built:
- **Targets.** `unit`, `conformance` and `characterization` are declared in `scripts/build_targets.json` as path patterns, and
  every entry names its reader. Each target's KEY (`buildgraph.key`) is the sha256 of its name, its facets (platform,
  configuration, toolchain) and the `git ls-tree -r` entries of the tracked paths its inputs match, minus `@inert` and
  `@tooling-lane`. PB5205's single `population_key`, `population_digest`, `populations_green`, `_composed` and the
  whole-run match in `carry` are DELETED. The keys are per target and nothing sits beside them.
- **One store.** `<git common dir>/cobol-build-store/<target>/<key>.json`. A target is up to date exactly when the store holds
  a pass at its key; the gate asks nothing else. A pass recorded in worktree A is up to date in worktree B at the same
  content. Only proven passes are recorded (`Gate.record_passes`): a green host, an EXACT population, and a tree unchanged
  while the gate ran.
- **The gate.** Per target: up to date starts no host. The others run, less what an earlier RED run of this worktree passed
  at that key (PB5099's rule; the per-case evidence stays in the worktree's run directories in this stage). The build runs
  only when a target or the post-build self-tests (a change that touches a script) need it. The verdict line names each
  target as ran or up to date, with the run and worktree of the pass. `--rederive` records the passes it proves EXACT.
- **Folded in from PB5205's review** (`E:/COBOL-coord/scratch/review-w20261988-a.jsonl`). R1-1: an arm shows that a run RED
  for an audit AND the post-build self-tests keeps its targets' passes, and that the next gate builds and runs the
  post-build self-tests again. R1-2: `--rederive`'s residue is now stated exactly, in the record, the docstring and the design
  section: an uncommitted edit made during the run and undone at ANY time before the re-derivation.

**The finding the brief did not anticipate: a records-only change re-runs Conformance, and must.** The suite's generator
refuses a test that names a rule the inventory lacks, and it reports per-edition completeness from the inventory. Every
Conformance host runs it first (`SuiteManifest.GenerateOnce`), and a refusal fails the whole suite. So the inventory is a
true input of `conformance`. The dry computation below shows records-85b re-running Unit AND Conformance, not Unit alone.
Leaving the inventory out of Conformance's key would be exactly the false green this stage must not have. Stage 2 should
split the generator into its own target and key Conformance on its OUTPUT (the generated manifests' digest), not on the
inventory. Then a records change whose manifests are unchanged re-runs nothing in Conformance: Bazel's cut-off on an
unchanged output.

**Also fixed (found in this change): a REUSED answer ignored the toolchain.** `Gate.reusable` matched tree and base only and
runs before the toolchain check, so a GREEN measured under other tools answered a re-gate. It now requires the record's
toolchain to be this host's, the rule a target's key already has. A new arm proves it, and it fails on the old driver.

**Remaining work (each needs an id; none was allocated here).**
1. **The dynamic proof per target.** CI's Linux test steps run each whole-assembly `dotnet test` under `inert_lane.py
   watch`, which fails a run that opens an inert or tooling-lane path. Extend it with `--target <name>`. The watched set
   becomes, in addition, every tracked path the target's inputs do not match (`buildgraph.Target.matches`), and a directory
   listing is judged as `Classification.is_watched` judges it. `.github/workflows/build-and-test.yml` passes each shard's
   target. A shard of assembly X then fails when it opens a tracked path outside X's declared inputs. That judges the static
   audit's residue: bare root references, computed paths, and what a started process reads. It was not built here because
   the workflow is a Unit input (CiArtifactDriftTests), so changing it re-runs the whole Unit population, and the watch can
   be proved only in a merge group.
2. **Per-case evidence in the store** (PB5205's cross-worktree item): the passed case names per target and key, so a RED's
   retry composes across worktrees too.
