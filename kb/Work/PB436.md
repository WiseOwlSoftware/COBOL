# PB436 — one dispatch, two arms, and only one arm written to the rule

## 1. THE MECHANISM

`ControlFlowEmitter.EmitVarying`'s TEST BEFORE arm emits, for every non-innermost level
(`src/Cobol.Net.Compiler/CodeGen/Verbs/ControlFlowEmitter.cs:309-316`):

    EmitBefore(k + 1);
    // §14.9.28 GR13e ('85 6.20.4 GR10(d)1): the OUTER variable augments FIRST, THEN the inner
    // re-initializes from its CURRENT FROM value — `AFTER B FROM A` must see the augmented A
    // (NC201A PFM-TEST-F4-23: 3+2+1 = 6 iterations, not 3+3+2).
    set.AugmentSetTarget(levels[k].Var, down: false, num.RenderOperandLike(levels[k].By));
    InitVaryingTarget(v, levels[k + 1]);

Augment the OUTER variable, THEN re-initialize the inner one from its FROM operand's CURRENT contents. GR13 e) 2
orders the two the other way round: reset FIRST, augment SECOND. The order is invisible whenever the AFTER
level's FROM is a literal or an independent item, and it decides the whole iteration set whenever the FROM reads
the level to its left — i.e. exactly the ordinary triangular `AFTER B FROM A` idiom.

**The SAME METHOD's TEST AFTER arm is CORRECT** (`:320-338`). GR13 c) 4 is the ONE place in GR13 that states the
increment BEFORE the reset, and that arm implements exactly it — measured. So one construct now follows two
different rules and only one of them is the rule the code cites. This is the project's most reproducible defect
shape: a dispatch with two arms, only one arm written to the rule.

**The swap is DELIBERATE and load-bearing on a NIST golden.** The comment above pins it to
NC201A PFM-TEST-F4-23 ("ORDER OF INITIALISATION OF VARYING IDENTIFIERS", ANSI-REFERENCE "VI-114 6.20.4
GR10(d)1"), which does assert exactly 6 for exactly this program. Per CLAUDE.md rule 1 the ISO text is the
oracle and the NIST corpus is a regression NET, never authority. There is no determination in
`docs/CONFORMANCE.md` recording the choice — that file carries determinations for the FINALLY-on-the-fatal-path
and RESUME-NEXT-skips-WHEN-COMMON questions in this same clause and nothing for this one.

**The reason the swap survived is documented drift.** The class doc-comment of `PerformVaryingDifferentialTests`
already CLAIMS the spec order ("the spec's exact reset/augment ordering (inner condition true ⇒ reset inner
variable, augment the one to its left)") while every test in that class is an `AssertSameAsLegacy` legacy-oracle
differential — so nothing ever measured the claim. The doc says one thing and the code does the other.

## 2. THE RULE, QUOTED, WITH ITS `--check` LINES

GR13 e) 2's true-branch, verbatim:

    python scripts/spec/cite.py --check 14.9.28.4 "the induction variable associated with the current condition is set to its initialization value"
    OK  §14.9.28.4 13)  (General rules)

    python scripts/spec/cite.py --check 14.9.28.4 "the condition to the left of the current condition becomes the current condition"
    OK  §14.9.28.4 13)  (General rules)

⚠ Both fragments land in GR13 — the rule number this note cites — but GR13 is a long rule with lettered
sub-steps, and `--check` cannot resolve a SUB-step. The two fragments above are e) 2 a. and e) 2 b.; the sibling
sub-step that states the OPPOSITE order is c) 4, and it is checked separately so the two cannot be confused:

    python scripts/spec/cite.py --check 14.9.28.4 "all induction variables to the right of the false condition are set to their initialization values"
    OK  §14.9.28.4 13)  (General rules)

What "its initialization value" READS, and when — GR12's per-use item identification:

    python scripts/spec/cite.py --check 14.9.28.4 "Item identification for identifier-3, identifier-4, identifier-6, identifier-7, index-name-2, and index-name-4 is done each time"
    OK  §14.9.28.4 12)  (General rules)

and GR13's closing paragraph, which makes the change immediate:

    python scripts/spec/cite.py --check 14.9.28.4 "all changes to the induction variable, the variables associated with the augment value, and the variables associated with the initialization value have immediate effect"
    OK  §14.9.28.4 13)  (General rules)

Together: the reset of B reads A **before** A is augmented.

## 3. EXPECTED vs OBSERVED — RE-RUN ON HEAD (89044aa0)

Still reproduces. HEAD `cobol.exe`, `--std 2023`.

           01 A PIC 9(4) VALUE 0.  01 B PIC 9(4) VALUE 0.  01 N PIC 9(4) VALUE 0.
           PERFORM VARYING A FROM 1 BY 1 UNTIL A > 3
                     AFTER B FROM A BY 1 UNTIL B > 3
               ADD 1 TO N   (and record the pair)
           END-PERFORM

    $ cobol.exe .../gr13e2_order.cob --std 2023 --run
    exit 0
    N=0006
    A=0004 B=0004
    T=(1,1)(1,2)(1,3)(2,2)(2,3)(3,3)

**Required by GR13 e), hand-computed from the rule text:** A=1, B:=A=1 (13 a, left-to-right). cond-1 false ⇒
cond-2 current. cond-2 false three times (B=1,2,3), so the body runs 3× and B reaches 4; cond-2 true ⇒ (a) B is
set to its initialization value — the CURRENT content of A, still 1 — then (b/c) A is augmented to 2. Second
pass: B=1,2,3 (3 bodies), then B:=A=2, A:=3. Third pass: B=2,3 (2 bodies), then B:=A=3, A:=4; cond-1 true, end.
**Eight executions, pairs (1,1)(1,2)(1,3)(2,1)(2,2)(2,3)(3,2)(3,3), A=4, B=3.**

The divergence compounds with depth, re-measured on HEAD:

    $ cobol.exe .../gr13e_3lvl.cob --std 2023 --run
    exit 0
    N=0004 A=0003 B=0001 C=0003      (GR13 e) gives 7 executions)

**The TEST AFTER counterpart CONFORMS — re-measured on HEAD as the contrast:**

    $ cobol.exe .../gr13c_after_dep.cob --std 2023 --run
    exit 0
    N=10 I=4 J=4
      source: PERFORM WITH TEST AFTER VARYING WI FROM 1 BY 1 UNTIL WI > 3 AFTER WJ FROM WI BY 1 UNTIL WJ > 3

N=10 = 4+3+2+1 is exactly the 13 c) 1-4 derivation. And the TEST BEFORE twin of that same program:

    $ cobol.exe .../gr13e_before_dep.cob --std 2023 --run
    exit 0
    N=06 I=4 J=4                     (13 e) requires N=08 I=4 J=3)

I re-ran the four programs above at `--std 2023` on HEAD. The adjudicator measured the identical results at
`--std 85`, `2002`, `2014` and `2023` on the pinned build; the edition-independence is structural — `EmitVarying`
has no edition arm at all.

**Nothing else in GR13 e) diverges:** the "another AFTER phrase to the right" walk, the body+augment leaf, the
fact that levels further right are NOT reset when an outer level augments, the zero-trip case and the negative
augment (NOTE 5) all match the rule.

## 4. THE CODE SITE AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Compiler/CodeGen/Verbs/ControlFlowEmitter.cs:309-316` — the TEST BEFORE arm (the defect)
* `src/Cobol.Net.Compiler/CodeGen/Verbs/ControlFlowEmitter.cs:320-338` — the TEST AFTER arm (the correct twin)
* `src/Cobol.Net.Compiler/CodeGen/Verbs/ControlFlowEmitter.cs:348-360` — `InitVaryingTarget`
* `tests/…/PerformVaryingDifferentialTests.cs` — the class whose doc-comment claims the spec order while every
  test in it is a legacy-oracle differential

The mechanical change is small — swap the two calls at `:314-315`, leaving the TEST AFTER arm exactly as it is —
but **the change that matters is a written decision plus a test that can see it**, and neither exists today:

1. ⛔ **This needs an owner determination, and it is stated here as one.** At `--std 2023` — the default, and the
   edition the mission names — the standard's text pins 8 and the compiler gives 6, so 2023 is a divergence
   outright. Whether the 85 / 2002 / 2014 compilers should keep the NIST order is an EDITION question that
   cannot be settled from the 2023 standard alone: it needs the pre-2023 text or an owner call. The fix must
   therefore land either **uniformly** (re-adjudicating the NIST golden NC201A PFM-TEST-F4-23) or
   **edition-gated**, and the choice must be written down.
2. **Pair it with a SPEC-DERIVED golden whose AFTER level's FROM is the outer induction variable** — the only
   shape that can tell the two orders apart. Every existing test in the area is either a legacy differential or
   uses literal FROM operands (`Varying_ThreeLevels_OmittedBy` is spec-pinned but all three FROMs are literals,
   so it is blind to this).
3. **If the divergence is kept at any edition, publish it in `docs/CONFORMANCE.md`** beside the two other
   §14.9.28.4 determinations already there. A code comment is not a determination.

**Corroborating detail for whoever adjudicates the standard-defect question:** GR13's own step cross-references
are provably unedited in the printed standard — c) 3 and c) 4 both direct execution back to step 13 a, which
would re-initialize every induction variable and never terminate (operationally the target must be c) 1), and
e) 2 d refers to sub-steps by letters where e)'s own steps are printed 1. and 2. All three were verified against
the canonical PDF (pages 717-718), so they are the standard's own text and not transcription damage. That is
evidence for reading e) 2's ORDER with the same caution — and all the more reason for a written determination
rather than a code comment.

* **Every other place a NIST golden is the recorded oracle for a behaviour the 2023 text decides.** The comment

  potential undeclared standard-defect disposition.
* **Every doc-comment that CLAIMS a spec behaviour over a body of legacy-oracle differentials.**
  `PerformVaryingDifferentialTests`'s class comment is the exemplar; the pattern is a claim nothing measures.
* **`InitVaryingTarget`'s other caller** — the TEST AFTER arm's `:331` reinit — takes the same helper and is

* **Edition gate sweep**, if the fix is edition-gated: gating a BEHAVIOUR (not a construct) at an edition
  boundary is the shape that breaks everything compiling below it; run the full NIST corpus and the GnuCOBOL
  differential, not the wave filter.

## 7. LANDED

**Fixed uniformly, at every edition, in the one place the rule belongs.**
`ControlFlowEmitter.EmitVarying`'s TEST BEFORE arm now emits, where the inner `while` exits,

    InitVaryingTarget(v, levels[k + 1]);                       // GR13 e) 2 a.
    set.AugmentSetTarget(levels[k].Var, down: false, ...);     // GR13 e) 2 b. + c.

and the method's doc-comment now derives the whole nest from e)'s current-condition machine rather than
asserting a conclusion: the `while` tests ARE "the current condition is evaluated"; entering the next inner
loop IS e) 2's false-branch a.; the innermost body+augment IS its false-branch b.; and the code that runs
when an inner loop exits IS its TRUE branch, in the rule's order. Because the nest is generated by one
recursion, the repair is level-count-agnostic (2, 3 and 7 levels all measured) and is shared by the inline
and out-of-line spellings, which GR4 requires to function identically.

**The arms, named.** TEST BEFORE vs TEST AFTER: only TEST BEFORE was wrong; the TEST AFTER arm implements
GR13 c) 4 — the one sub-step of GR13 that states the increment BEFORE the reset — and was re-derived and
re-measured at two and three levels, unchanged (10 bodies = 4+3+2+1). Its comment now cites c) 4 and says
the asymmetry is deliberate, so the next reader does not "fix" it into symmetry. Inline vs out-of-line:
one lowering, and the golden writes the same nest both ways. Numeric vs index-name induction variable:
`InitVaryingTarget` is shared, so both moved together; the golden measures an index-name nest too.

**Measured after the fix** (`--std 85`, `conformance:85/pb436_varying_after_from_outer`, every value
hand-computed from the rule BEFORE the run and matched exactly): out-of-line and inline both give 8 bodies
`(1,1)(1,2)(1,3)(2,1)(2,2)(2,3)(3,2)(3,3)` with A=4 B=3; three chained levels give 7 bodies
`(111)(112)(121)(122)(212)(221)(222)` with A=3 B=2 C=2; an index-name nest repeats the two-level answer
with IX=4 JX=3; TEST AFTER gives 10 with I=4 J=4.

**The owner-level consequence, discharged where §4 item 1 asked for it.** The order is UNIFORM — no edition
gate. `docs/VERSION_CHANGE_REFERENCE.md` records no change to §14.9.28 across the four editions, so an
edition split would have had to be invented rather than cited, and process rule 1 makes the 2023 text the
oracle for all four. The rule text was re-verified against the canonical PDF page 718, which carries it as
prose with **no figure** (`get_images`/`get_drawings` both empty) — the transcription is faithful.
NIST NC201A PFM-TEST-F4-23 is therefore re-adjudicated: its golden now records `FAIL* PFM-TEST-F4-23` with
`COMPUTED= 8 / CORRECT = 6` and a `001 TEST(S) FAILED` footer, and NOTHING else in NC201A changed
(byte-diff: two hunks). The determination is in `docs/CONFORMANCE.md` §3 beside the other two §14.9.28.4
determinations, as §4 item 3 required.

**A gate mechanic had to move for that to be honest.** NC201A is the ONLY one of 364 goldens carrying a
CCVS failure, and `scripts/guard-verdict.sh` scored ANY non-zero report footer as a REGRESSION. That check
sits after a byte-exact match with the golden, so it could only ever fire on a golden defect — it was a
BASELINE audit living in the run path, and it would have turned the conforming compiler red. The allowance
now comes from the golden's own footer, and the baseline audit moved to
`CorpusManifestTests.GoldensCarryingACcvsFailure_AreExactlyTheDeclaredCcvsDefects`, stated as a SET EQUALITY
in both directions against the `CCVS-DEFECT` marker in `tests/nist/corpus.tsv` — so a golden cannot quietly
acquire a failure, and a declaration cannot outlive the golden that earned it.

**The doc that claimed what nothing measured** (§1's last paragraph) is corrected:
`PerformVaryingDifferentialTests`'s class comment now says explicitly that every FROM operand in it is a
LITERAL, that the ordering is therefore invisible to it, and which golden does measure it.

**Sibling sweep results.** PB439 (`lv.From is BoundNumRef` where GR3 says "an identifier") touches the same
helper but is a DIFFERENT mechanism — an operand-KIND question in the binder, not an ordering one — and was
left alone; `InitVaryingTarget` moved as a whole, so both its callers keep whatever GR3 behaviour they had.
PB441 (GR14's TURN OFF ALL window vs imp-5's compiled-in EC-SIZE guard) is a different subsystem
(codegen/exceptions) and a different statement format, and was left alone. Grep for other comments citing a
pre-2023 ANSI rule number or a NIST test id as the JUSTIFICATION for a behaviour (§5 item 2) found this one
and no other survivor.

Rows `GR-14.9.28.4-13` and `GR-14.9.28.4-L3.2` re-verdicted CONFORMS by batch
`pb436-gr13e2-reset-before-augment` (2 of 2 accepted; GAP 2481 → 2479).
