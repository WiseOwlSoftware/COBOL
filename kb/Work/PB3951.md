# PB3951 — FUNCTION LENGTH(FUNCTION ABS(S)) answers 30 where GnuCOBOL 3.2.0 answers the size of its temporary (7)

`FUNCTION LENGTH(FUNCTION ABS(S))` is 30 here (PB1398's S9(30) item), where GnuCOBOL's answer is the size of the
temporary that holds the function value (7 for the report's `S`). The standard leaves the storage of a function's returned
value to the implementor (precedence per CLAUDE.md rule 1: ISO controls first, otherwise GnuCOBOL). First recorded as a "lead
for the registrar" in PB3514's body, where no work list sees it.

## Acceptance
- Decide which size LENGTH reports for a numeric function's value (adjudicate against the spec's A.1 items and GnuCOBOL),
  make `NumericReturnedValuePic` and `BindLengthFold` answer it, and pin it with a golden; sweep the other numeric
  functions whose value LENGTH reads (SUM, MAX, MIN, MEAN, INTEGER).

## Landed (wave 20261728, group D)

**Re-probe.** The note reproduced on the wave's own build: `LENGTH(FUNCTION ABS(S))` and every other numeric function were 30. A matrix of
about eighty lines over every function shape and argument usage was run against `cobc` 3.2.0 (WSL) and agreed with the note: GnuCOBOL's
LENGTH of a numeric function is the size of the temporary DISPLAY already shows, per function and per argument (7 for `ABS(S9(5)V99)`,
5 for a COMP-3 argument, 4 for `INTEGER(S)`, 8 for `DATE-OF-INTEGER`...). Adjudicated, not just fixed: ISO §15.4.1 leaves the
temporary's representation to the implementor (A.1 item 92), so CLAUDE.md rule 1's precedence gives it to GnuCOBOL, as PB3514 had already
decided for DISPLAY, and PB3514 had left this question open on purpose (DOC-A.1-92: "the LENGTH of a returned-value item is a separate
decision").

**The fix is one item asked two questions.** `FunctionValueField` (PB3514) is the temporary DISPLAY shows; it now also answers `ByteLength`
(a copied argument's image width, a literal's digits and sign position, DATE-OF-INTEGER's 8, the 4-byte / 8-byte / DISPLAY item the value
describes, 8 for a binary64). `IntrinsicBinder.FunctionResultLength` no longer folds a fixed S9(30) width: every numeric or integer function
result (and a folded literal) goes to the runtime as a `BoundIntrinsicCall`, and the renderer's first LENGTH / BYTE-LENGTH arm, ahead of the
float-lane routing, reads the field `FunctionDeviceText.Field` builds. `FunctionDeviceText.IsNumericFunctionResult` is the one predicate both
sides share. The catalog column `DeviceForm` therefore decides a function's size as it decides its text, and the next function is automatic
(`FunctionDeviceFormDriftTests.TheLengthOfANumericFunctionIsTheLengthOfTheTemporaryDisplayShows`). `NumericReturnedValuePic` had one reader and
is deleted; `FunctionValuePic` / `IntegerFunctionValuePic` remain as the nominal items IN-ARITHMETIC-RANGE reads (the drift test's reader list
shrank to match). The LENGTH of a numeric function is now evaluated at run time and DISPLAYs as a computed value (`000000007`), as GnuCOBOL's
does. Sweep: BYTE-LENGTH shares the arm; the string-result arm and the index arm are unchanged; the CALL BY CONTENT argument is a different
mechanism (no LENGTH).

**Not copied (DOC-A.1-92, pinned by `pb3951_length_of_numeric_function_result_not_copied`).** A binary64 result is 8 bytes where GnuCOBOL's
temporary has 38 to 96 digits; a DISPLAY temporary is its true digit count where GnuCOBOL's is a GMP estimate (`-9223372036854775808` is 19,
cobc 20); a folded `LENGTH(LENGTH(X))` is the literal's own field (1).

**Witnesses.** `conformance:cases/15.50.4-Returned-value-rules/pb3951_length_of_numeric_function_result` (2014, 2023; forty-seven lines identical
to cobc), `..._not_copied` (2002 to 2023), the negative `pb3951_length_of_abs_below_2014`, the updated `pb1398_length_of_function_result`, and
`FunctionDeviceTextTests` (the byte rows). `closes_rows: []` (no inventory row was claimed; RV-15.50.4-3, RV-15.14.4-1 and DOC-A.1-92 stay CONFORMS).
