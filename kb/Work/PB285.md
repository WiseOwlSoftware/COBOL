# PB285 — the A.4.10 row now describes this compiler

## The decision

`docs/CONFORMANCE.md` §5 row **A.4.10** changes from **Not claimed** to **Partial**, itemized:

| A.4.10 item | element | disposition |
|---|---|---|
| 1 | CLASS-ID INHERITS, repetition of object-class-name-2 (§11.3) | **not claimed** — refused COBOLNET0849 at pass-1 |
| 2 | INTERFACE-ID INHERITS, repetition of interface-name-2 (§11.6) | **SUPPORTED** |
| 3 | Parametric polymorphism (§9.3.5.3) | **not claimed** — refused COBOLNET0822 |

The OO **core** is mandatory surface and is claimed separately; only these three items are optional.

## Why — the row made a false statement about the shipping compiler

§5's own preamble defines *Not claimed* as **"the module's syntax is not accepted"**. The compiler accepts and
compiles multi-base `INTERFACE-ID … INHERITS`:

- `src/Cobol.Net.Frontend/Grammar/Core/CobolOO.g4:77` parses `INHERITS FROM interfaceName+`, with an in-grammar
  comment calling the asymmetry deliberate: *"INHERITS repetition is SUPPORTED (C# interface lists are native —
  the deliberate asymmetry with the class-side single-inheritance restriction)"*.
- `src/Cobol.Net.Compiler/Oo/OoClassTable.cs` carries the **full base list**, resolves every base, and enforces
  §11.6.3 **SR2** (unknown base), **SR3** (cycle) and **SR6** (a base named twice) with **COBOLNET0840** — the
  SR6 leg literally cites "ISO §11.6 SR6".
- `OoInterfaceSymbol.AllPrototypes()` walks the whole multi-base closure.

The row's own stated evidence — *"multi-base INHERITS rejects COBOLNET0849"* — is true of the **class** side only
(`OoClassTable`, item 1). One measurement was generalised across an asymmetry the grammar comment describes in
so many words.

## The ground this rests on

**CLAUDE.md rule 6 — a conformance claim must describe the CURRENT compiler.** §4.2.7 makes user documentation
the instrument by which an implementor identifies the optional elements supported; documentation that declines an
element we ship is not a conservative error, it is a wrong statement in the §4.2.16 conformance record, and
§4.2.7's second sentence is precisely the mechanism for a partial claim ("**Partial**" in this table = the
supported / not-supported split is itemized).

**The owner-decision protocol of 2026-08-30** — follow what the surveyed model implementations do, ask only on
significant considerations — settles the shape without a prompt: this is not a choice about what to build, it is
a correction of the record to match what is built. Nothing about the compiler changes.

**It was already known and logged, which is why leaving it open was the harder position to defend.**
`docs/rearchitecture/PHASE-13-plan-vs-spec-review.md` finding **U21** already proposed exactly this — *"item 1
not claimed → 0849; item 2 claimed — interface INHERITS repetition is supported; item 3 not claimed → 0822"* —
and its disposition still reads *"unverified — Wave I re-verify"*. `docs/COBOLNET_OO_SLICE_BRIEFS.md` records the
asymmetry as a decision "to ratify in passing"; it was never ratified. **The owner is being informed of this
correction rather than asked for it**, and may reverse it — the reversal would be a compiler change (removing
`interfaceName+`), not a documentation change.

## What it forces in the derived-verdict lane, and what it does NOT

The derived selector `oo-optional-items-only` covers **items 1 and 3 only**, and stamps **three** rows —
`SR-8.4.3.8.3-5`, `SR-11.3.3-7`, `GR-11.3.4-4` — each of which turns solely on a **plurality of CLASS-side**
INHERITS bases.

⛔ **`SR-11.6.3-6` and `SR-11.6.3-5` are therefore NOT selected.** SR-11.6.3-6 (*"A given interface-name shall not
appear more than once in an INHERITS clause"*) is an **implemented** rule; its honest verdict is
CONFORMS-but-untested and it is ordinary work for the adjudication lane. Its text is verbatim parallel to the
selected `SR-11.3.3-7` and it matches the selector's pattern, so an `interface-name` exclusion is the only thing
holding it out — and the drift test asserts its absence, with this note as the reason. Before this decision that
exclusion rested on an agent's reading of the code *against* the owner's row, which is not a footing a derived
verdict may stand on. It now rests on the row.

⚠ **AND THE IMPLEMENTED PATH HAS NEVER BEEN CONTRADICTED.** There is **zero** `INTERFACE-ID … INHERITS` coverage
anywhere in `tests/` — single-base or multi-base; every `INHERITS FROM` in the tree is CLASS-ID
(`feedback_a_dead_lookup_is_also_unverified`). A claim we now make in the conformance record is carried entirely
by unexercised code. The first interface-INHERITS tests are owed with the CONFORMS-but-untested rows.

**Item 3 contributes ZERO rows, and that is a finding rather than an oversight.** All seven §9.3.5.3 rules define
the **method resolution signature**, which MANDATORY rules consume — §8.4.6.5 (*"The methods declared in an
object class definition shall have unique method resolution signatures within that object class definition"*) and
§11.7.3 SR3/SR4 (OVERRIDE must match *"the same method resolution signature"*). §9.3.5.3 scopes the optionality
to the FEATURE and grants latitude over the resolution ALGORITHM, never over whether the signature exists. This
compiler implements a **degenerate** signature — the method NAME alone, enforced by COBOLNET0822 — so those seven
rows want per-row adjudication, arguably **DIVERGES** against §11.7.3 SR3, and must never carry this stamp.

## Three consequences — the first CORRECTED at landing, two left OPEN deliberately

1. **§2 row 45 — CORRECTED 2026-09-02, in the landing change set.** It read *"Parametric-polymorphism method
   resolution | 11.x | **Claimed** | Single-dispatch OO method resolution over the class table"*. Annex A.3
   item 45 applies only *"When parametric polymorphism is provided in object orientation"* (`--check` → OK),
   and item 3 is Not claimed — so row 45 could not be Claimed: it was describing the DEGENERATE signature
   (method name alone, COBOLNET0822) as if that discharged the item. It is now **N/A**, which is the
   disposition §2's own header defines for "a property of an unsupported facility", with the note saying it
   becomes a real disposition if item 3 is ever claimed. PHASE-13 U21 recorded the same contradiction. A
   conformance claim contradicting another conformance claim in the same document is not a "separate
   correction" to schedule — CLAUDE.md rule 6 makes it part of the change set that discovered it.
2. **COBOLNET0849 is a bare string literal with no `DiagnosticCatalog` row and no `DIAGNOSTICS.md` entry, and it
   is SHARED with three unrelated EC-OO RAISING legs** in `EcBinder`. An `.err` pinning the bare number can pass
   on the wrong check, so any A.4.10 witness must additionally assert the message TEXT names §11.3.2 and A.4.10
   until the code is de-collided.
3. **COBOLNET0822's message cites "ISO §12063"**, which is not a clause of ISO/IEC 1989:2023 — it is a stale spec
   LINE number. The correct clause is §9.3.5.3, and there is no negative fixture for 0822 at all.

Also measured while deciding this, and correctly kept out of the stamp: `[object-class-name-1 OF] SUPER`
(FMT-8.4.3.8.2) has **no grammar surface** — `objectReference : dataReference | NULL_ | SELF | SUPER` admits bare
SUPER only — which leaves the single-base-reachable `SR-8.4.3.8.3-4/-6` and `GR-8.4.3.8.4-4` as genuine open
NOT-IMPLEMENTED rows, not module-licensed ones.
