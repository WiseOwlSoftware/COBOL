# PB1544 — OPEN

## The rules

`cite.py --check 8.3.3.6.3 "A figurative constant may be used whenever 'literal' appears in a format or when a rule allows it"` → OK §8.3.3.6.3 1).

## Repro (scratch `fc1.cob`, and `/tmp/adj/doc/doc-w1-s6/probe/p182/sy6.cob`; `--std 2023`)

```cobol
       SPECIAL-NAMES.
           SYMBOLIC CHARACTERS SA IS 66.
       PROCEDURE DIVISION.
           DISPLAY FUNCTION ORD(SPACE)
           DISPLAY FUNCTION ORD(QUOTE)
           DISPLAY FUNCTION ORD(SA)
```

Observed: `error COBOLNET1639: 'SA' is not defined` at the third line (the first two compile). Expected: compiles; `ORD(SA)` is 66.

## Mechanism

The intrinsic-argument binder resolves a bare word as a data-name and never consults the SPECIAL-NAMES symbolic-character table,
which the other literal positions (MOVE, DISPLAY, VALUE) do. The fix is ONE literal-operand resolver shared by every literal
position (the figurative-constant table plus the symbolic characters), so the next literal position gets both kinds automatically.

## Sibling sweep

Every operand position the grammar spells `literal` but binds through a data-name path: user-defined function arguments (kb/Work
PB1418 owns that binder), CALL … BY CONTENT literal, INSPECT / STRING / UNSTRING literals, EVALUATE WHEN.

**Code site (located 2026-09-27).** `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/IntrinsicBinder.cs#BindArgOperand`; also `src/Cobol.Net.Compiler/Binding/Procedure/ExpressionBinder.cs#RefExpr`, `src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs#SymbolicOf` (code). BindArgOperand substitutes a non-numeric constant-name (ConstantOf) but has no SymbolicOf arm, so a bare symbolic-character word falls to BindFunctionArgumentExpr -> ExpressionBinder.RefExpr (no symbolic arm) -> COBOLNET1639; FieldOperand (ExpressionBinder:338) does consult SymbolicOf

## Re-probe 2026-10-05 (wave 1020 D) — the headline is fixed, the ROOT is not, and the note stays OPEN

`FUNCTION ORD(SA)` (SA `SYMBOLIC CHARACTERS SA IS 66`) now compiles and prints 66: kb/Work PB1577 landed an arm in
`IntrinsicBinder.BindArgOperand` for it (`ctx.Data.SymbolicOf`). That is a THIRD copy of the same chain, not the "ONE literal-operand
resolver shared by every literal position" this note asks for, and the sibling sweep it lists still reproduces. MEASURED on this
build (probes `E:\COBOL-coord\scratch\w1020d\p\a3.cob`, `a4.cob`, `--std 2023`), in CALL Format 2 (`CALL "SUB" AS NESTED USING ...`):

    01 KT CONSTANT AS "A".            SYMBOLIC CHARACTERS SA IS 66.
    CALL "SUB" AS NESTED USING BY CONTENT KT   -> COBOLNET0844 'constant-name KT substitutes a literal ... not a numeric operand'
    CALL "SUB" AS NESTED USING BY CONTENT SA   -> COBOLNET1639 'SA is not defined'
    (the keyword-less `USING KT` arm substitutes the constant: CallBinder.cs ~line 410 `host.Expr.ConstantOperand(bare)`, no symbolic arm)

`literal-2` of Format 2 BY CONTENT admits a figurative constant (8.3.3.6.3 SR1) and a constant-name (13.10.3 SR2), and a symbolic
character is a figurative constant (12.3.7.4 GR11). The same chain (`ConstantOperand` then `SymbolicOf`) is written separately at
`ExpressionBinder.FieldOperand`, `IntrinsicBinder.BindArgOperand` (two arms), `InspectBinder` (two arms, ~line 405-413) and
`CallBinder`'s keyword-less arm only; BY CONTENT / BY VALUE arms (`CallBinder.cs` ~262-290, ~330-360) and INVOKE's twins have neither.
The symbolic operand is a `BoundAllLiteral` in `FieldOperand` and a `BoundStringLiteral` in the other two, which the one resolver must
reconcile. WHAT THE FIXER OWES: `ExpressionBinder.LiteralAliasOperand(dref)` = the one chain, called by every site above, with
SR23 (14.9.4.3: BY VALUE literal-2 numeric) asked of a symbolic or non-numeric constant at BY VALUE, a negative per arm, and a drift
test that no binder writes `SymbolicOf(` or `ConstantOf(` outside it. Not done in wave 1020 D: it is a six-binder redesign.
