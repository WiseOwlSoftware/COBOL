# PB3240 — a note writer states CRLF explicitly, and the writer audit accepts it

Filed 2026-10-16 by the enqueue unit's clerk.

**Where.** `scripts/arch/file_census_notes.py` lines 545, 571, 740 and 814 (on origin/main) open kb/Work notes with
`open(path, "w", encoding="utf-8", newline="\r\n")`: every note it files or merges is CRLF in the working tree.
`scripts/line_endings.py`'s WRITERS audit (kb/Work PB3029) only checks that a text-mode write STATES `newline=` (its
`--fix-writers` added `newline="\n"` to writers that lacked one), so an explicit `newline="\r\n"` passes it.

**Witness.** Branch `notes-PB1754-r2b4a-20261016` (the R2 batch 4a filing, Mythos lane, head e5e7c0a25): its landing
stopped `=== BUILD-LOCAL GATE: RED - LINE ENDINGS RED ===` (run 20261016T110730Z-166a9a,
`E:\COBOL\.claude\worktrees\notes-PB1754-r2b4a-20261016\TestResults\enqueue\windows-gate.log`):
`0 index · 26 working tree · 0 writers`; the 26 files were exactly the notes it filed or merged (PB2624, PB2723, PB2724,
PB3212-PB3234). The index was LF (git normalized on add), so `line_endings.py --fix` cleared it with no commit; the next
filing run writes CRLF again.

**Harm.** Process only: every R2 batch filing's landing goes RED on the line-endings audit until hand-fixed; no user
program affected.

**Fix shape (rule 4).** The four sites write LF (`newline="\n"`); the WRITERS audit refuses any `newline=` value other
than `"\n"` or `""` for a text-mode write (sweep `scripts/` and `.claude/` for other explicit CRLF writers: on 2026-10-16
the only ones are these four), with a self-test case for an explicit CRLF `newline=`.
