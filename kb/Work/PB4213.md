# PB4213 — an UNPARTITIONED group is planned beside running work its population meets

**Sites:** `scripts/orchestrator/plan_wave.py` (`plan`, `main`), `scripts/orchestrator/units/wave.md`.

## What happened

At 09:36 PDT on 2026-10-31 the wave unit of wave 20261784 (campaign PB2911) ran `plan_wave.py --from-budget
--cluster PB2911`. It planned three groups: A (PB1253, `ReportWriter.cs`), B (PB1654) and C (PB107, `Normalizer.cs`).
B carried the `UNPARTITIONED` warning, because PB1654's `**Sites:**` line read `none`. PB1654 is an audit of the
`.Pic is { }` / `.Pic is null` tests under `src/WiseOwl.Cobol.Compiler/Binding/`, 95 sites in 48 files that day. Its
heaviest file is `DataBinder.cs` (16 sites). The Mythos branch `worktree-wf_34371f8b-c21-12` (PB3557) was RUNNING and
edits `DataBinder.cs`, `DataBinder.IoControl.cs`, `DataBinder.NonDataNames.cs` and `BinderDriver.cs`. The planner's
rule (PB3670: an empty set holds nothing and is held by nothing) planned B beside it anyway.

The owner's rule, recorded after wave 20261030 cost a finisher on 2026-10-24, is to dispatch no plan that shows an
UNPARTITIONED group: give the note its `**Sites:**` block and re-plan. A wave unit cannot follow that rule and its own
text together. The unit text says to change the plan only with a reason in the handoff and to re-run the planner rather
than edit `groups.json`. A re-run plans B again, because the planner has no way to leave a group out. The unit therefore
released B (`plan_wave.py --release 20261784b`) and launched the Workflow with a trimmed copy of the args
(`E:\COBOL-coord\scratch\wf-args-w20261784-launched.json`, groups A and C).

## Repro

    python scripts/orchestrator/plan_wave.py --dry-run --from-budget --borrow-days 0 --cluster PB2911

Run this on a checkout where PB1654 still declares `**Sites:** none` and a running branch edits a Binding file. The
table prints group B with the UNPARTITIONED warning and no hold. This change set gives PB1654 a glob site block, so the
repro on the tip of this change shows PB1654 held behind c21-12 (named as `DataBinder.cs`) instead.

## The fix's shape

1. The planner never puts an UNPARTITIONED group into a wave a loop unit launches. It lists the group under `waiting`
   with the reason `needs a **Sites:** block (kb/Work PB4213)`, the same way it lists a note waiting on a predecessor.
   The group's budget then goes to the next candidate. This makes the owner's rule mechanical, and no wave unit has to
   trim a plan by hand.
2. `units/wave.md` states what a wave unit does with a group the planner still flags, so the unit text and the owner's
   rule agree.
3. Sweep the open notes whose `**Sites:**` line reads `none` although the work changes files under a campaign root.
   On 2026-10-31 these were PB1654 (fixed here), PB4193 (`docs/rearchitecture/DESIGN-test-build-ci.md`, under the
   `docs` root) and PB3950 (a golden under `conformance-suite/`). Give each its site block, or record why `none` is
   true. `work.py check` could refuse a `none` line that names a path under a campaign root.
4. A self-test arm in `scripts/orchestrator/test_plan_wave.py`: a campaign with one note whose set is empty plans no
   group for it and names it waiting.

## In this change

PB1654's `**Sites:**` line now names its population as a sweep (`src/WiseOwl.Cobol.Compiler/Binding/**/*.cs`, read by
`work.note_sites` as a glob, kb/Work PB3721), so the planner holds it while running work meets any Binding file it
audits, and plans it once that work lands.
