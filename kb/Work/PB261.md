# PB261

**Rows:** `GR-14.9.7.4-3` · `GR-14.9.7.4-4` · `GR-14.9.7.4-5`

The registration wave stamped COMMIT's three substantive general rules **DOCUMENTED-NON-SUPPORT** under Annex
A.4.3, and all three **stay a GAP** for the witness the schema requires. Unlike the screen module, this one
carries an explicit self-report of the gap in the very document that licenses it.

## The licence, verified rather than inherited

* **A.4.3 item 4** "COMMIT statement 14.9.7" (and item 2, the IO-CONTROL `APPLY COMMIT` clause; item 3, the
  EC-FLOW-APPLY-COMMIT / -COMMIT / -ROLLBACK conditions). Cross-references checked: §14.9.7 IS the COMMIT
  statement and §14.9.36 IS ROLLBACK.
* **A.4.1**: the module's associated syntax rules, general rules, other rules, exception conditions and I-O
  status values are optional with it, "even if not explicitly listed" — which is what carries the licence from
  the named statement to GR3/GR4/GR5.
* `docs/CONFORMANCE.md` **§5**: `A.4.3 | Commit and rollback | Not claimed`; **§4 item 2**: "Commit and rollback
  (E.3.2 item 2 / A.3 items 6–7): `COMMIT`, `ROLLBACK`. No transaction manager."

## ⛔ The gap §4 declared about itself — ⚠ SUPERSEDED 2026-09-02, see the dated section below

> ⛔ **THE QUOTE BELOW IS NO LONGER IN `CONFORMANCE.md` AND WAS WRONG WHEN IT WAS.** It is kept because this
> note's whole original argument rests on it and deleting it would hide why the argument was wrong. Wave H HAD
> landed for the two statements when this was written; §4's preamble had not been updated, this note inherited
> the stale sentence, and both are corrected in the 2026-09-02 change set.

§4's own preamble did not claim the recognize-and-warn posture for this facility:

> "SCREEN handling (item 4) is recognized at compile time and reported with the named COBOLNET1560 warning per
> §4.2.6; MCS, **COMMIT/ROLLBACK**, and VALIDATE (items 1–3) are today **a generic parse error** — their named
> recognize-and-warn diagnostics (the COBOLNET1560 band) are the tracked PHASE-13 Wave H code half, after which
> every row here meets the §4.2.6 warning mechanism / §4.2.13 obsolete flagging."

So the documented non-support is honest about being one step short: the construct is refused, but by a *generic*
parse error rather than a diagnostic that names the facility. A user who writes `COMMIT` learns that something
is wrong with their syntax, not that this implementation does not provide commit and rollback. That is the
difference the witness has to measure, and it is why these three rows cannot close on the licence alone.

## What is owed

1. A negative fixture proving a `COMMIT` (and, by the same rule, a `ROLLBACK` and an `APPLY COMMIT` clause) is
   **refused**, with the diagnostic actually emitted recorded as-is — the honest witness for today's posture.
2. When PHASE-13 Wave H lands the named COBOLNET1560-band diagnostic, the fixture becomes the witness for the
   §4.2.6 mechanism and these rows close. Until then the fixture pins a generic refusal, which is a
   corroborating regression net and **not** grounds to close: the row's requirement is a test proving the
   DOCUMENTED behaviour happens, and the documented behaviour is the named warning.
3. `GR-14.9.7.4-4` deserves its own line because it is the only one of the three whose absence has a
   *file-lifetime* consequence rather than a statement-level one: GR4 requires a CLOSE on a commit-subject file
   to DEFER its file-lock release until a later COMMIT performs it, and `FileRegistry.SharedClose` releases
   unconditionally on every close with no deferral list anywhere in `src/Cobol.Net.Runtime/IO`. With the
   facility declined there is no way to write a program that observes the difference — but that is a
   *consequence* of the decline, and if `APPLY COMMIT` ever becomes recognized-and-warned rather than a parse
   error, this is the rule whose absence stops being unobservable first.

## 2026-09-02 — the VERDICT is no longer this note's, the row count is 25, and THIS NOTE'S PREMISE WAS STALE

The derived selector **`commit-and-rollback-only`** now owns the A.4.3 **verdict** for every rule the module
conditions — **25 rows** from the ONE determination in `CONFORMANCE.md` §5, held by
`DerivedVerdictDriftTests.NoCommitAndRollbackConditionedRow_Diverges`. This note's original three are inside that
set and their verdict is now re-derived rather than trusted. **The note keeps the WITNESS debt, and
`inventory_rows` widens to the selector's full set** so ownership is explicit.

⛔ **THE PREMISE IN THIS NOTE'S OWN TITLE WAS FALSE, AND SO WAS THE SENTENCE IT RESTED ON.** It said "§4 item 2
itself records that COMMIT is today a generic parse error with its named recognize-and-warn diagnostic still
owed". **Wave H landed for the statements.** `CobolParserCore.g4` gates
`{facilityWord("COMMIT")}? commitFacilityStatement` / `{facilityWord("ROLLBACK")}? rollbackFacilityStatement`,
and `StatementBinder.BindCommitRollback` emits `DiagnosticCatalog.CommitRollbackUnsupported` — **COBOLNET1579**,
Warning — at **every** site; COBOLNET1690 additionally errors on the SR1/SR2 source positions.
`tests/conformance/2023/wave_h_facilities_inert.cob` exercises it and says so in its header. §4's preamble
carried the stale sentence and is corrected in the same change set.

**The debt is therefore SMALLER than this note recorded and differently shaped — but it is not discharged, and
two thirds of it is in the half nobody had measured.**

**(a) The APPLY COMMIT CLAUSE is the real gap, and it owns 17 of the 25 rows.** `grep APPLY
src/Cobol.Net.Frontend/Grammar/*.g4` returns **nothing**: there is no I-O-CONTROL `APPLY COMMIT` surface at any
edition, so `APPLY COMMIT ON F` is an **unnamed syntax error** — a user learns their syntax is bad, not that this
implementation declines commit and rollback. ([[PB137]] finding 5 proved this loud: "COMMIT is a hard token
`genericClause` cannot span".) Closing those 17 rows needs a grammar fragment (pre-authorized) whose binder
routes through the existing `BindUnsupportedFacility` mechanism — **not** a parallel helper
(`feedback_one_mechanism_per_job`) — plus a fixture asserting the named code rather than a generic error. An
interim fixture pinning the GENERIC refusal is a corroborating regression net and explicitly **not** grounds to
close: the row's requirement is a test proving the DOCUMENTED behaviour happens, and the documented behaviour is
the named warning. That point of this note survives intact.

**(b) ⛔ THE WHOLE RECOGNIZE-AND-WARN BAND IS UNWITNESSED, and this is the blocking prerequisite** — shared with
[[PB260]] and [[PB283]]. Across all of `tests/`, COBOLNET1560 appears once, 1578 twice, 1579 once and 1580 zero
times, and **every one of those is a source COMMENT, not an assertion**. The `.out` goldens capture stdout only
(the `pb137_commit_inert` header says the warnings "go to the non-failing compile channel"), and `.err` files
exist only for rejected cases. So COBOLNET1579 could stop firing tomorrow and nothing would go red — the
reachability was assumed, not measured (`feedback_reachability_is_measured_not_deduced`). **That, and not a
missing implementation, is why not one of the 25 rows can close today even though the statement half is
implemented.** The first fixture to write is the one that proves the band fires at all.

**(c) The exception-condition half, unmeasured in either direction.** `ExceptionCatalog` registers
EC-FLOW-APPLY-COMMIT / EC-FLOW-COMMIT / EC-FLOW-ROLLBACK as L3 Fatal 2023 with **zero setting sites**, so
`>>TURN EC-FLOW-COMMIT CHECKING ON` and `RAISE EC-FLOW-COMMIT` compile happily against a facility that does not
exist — the EC-SCREEN shape of [[PB260]], verbatim.

⚠ **§4 item 2 did not name the element it declines.** It read "Commit and rollback (E.3.2 item 2 / A.3 items
6–7): COMMIT, ROLLBACK. No transaction manager." — two STATEMENTS, omitting the APPLY COMMIT clause that owns 17
of the 25 rows and the whole EC-FLOW family. Neither cross-reference repairs it (E.3.2 item 2 is prose naming no
syntax; A.3 items 6–7 name only processor-dependence). Since DOCUMENTED-NON-SUPPORT `requires: notes` and those
notes point at §4 item 2, seventeen rows would have been stamped on documentation that never mentioned their
element — against §4.2.7 and A.4.1. §4 item 2 now enumerates the clause and the three exception conditions.

⚠ **A genuine defect in the STANDARD, of the [[PB260]] shape inverted.** §9.1.18.7 and §12.4.6.3.4 GR3/GR4 set
**EC-FLOW-APPLY**, a name with **no row** in the §14.6.13.1.6 table and not listed by A.4.3 item 3 — and the
index sends it to §12.3.8 REPOSITORY. The table's EC-FLOW-APPLY-COMMIT entry describes BOTH the invocation case
(which §12.4.6.3.4 GR3/GR4 assign to EC-FLOW-APPLY) and the address-change case, which is positive evidence that
EC-FLOW-APPLY is the standard's own slip for EC-FLOW-APPLY-COMMIT. A.4.1's "even if not explicitly listed" is
load-bearing here, not decoration.

⚠ **And §9.1.16–§9.1.18 have NO catalog rows at all** — the concept clause that defines this very facility is

## 2026-09-02 — the three statement rows are witnessed; the 22 APPLY COMMIT rows are not

The golden lane landed the witness. **Three of the 25 rows are now state=OK — `GR-14.9.7.4-3`, `GR-14.9.7.4-4`,
`GR-14.9.7.4-5`; 22 remain GAP**, and every one of them belongs to the I-O-CONTROL `APPLY COMMIT` clause
(§12.4.6.3) and the EC-FLOW family, which have no grammar surface at any edition. The note stays **open**.

**This is the one row family the STANDARD compels rather than the project's own posture.** A.3 item 6 makes the
commit/rollback facility processor-dependent and §4.2.6 paragraph 3 makes the compile-time warning **mandatory**,
so `COBOLNET1579` is a conformance obligation and not a courtesy. That is why the witness had to exist.

⚠ **The golden pins INERTNESS only, and says so in its own header.** `conformance:2023/pb261_commit_facility_witness`
prints `BEFORE` / `N=3` / `AFTER` — and `N=3` is what a CONFORMING processor prints too: with no active APPLY
COMMIT clause, §14.9.7.4 GR1 and §14.9.36.4 GR1 (and §14.9.36.4's NOTE) make both verbs a `CONTINUE`. The `.out`
therefore **cannot discriminate**. The discriminating evidence is the mandatory warning, and it rides the
non-failing compile channel that no `.out` reads — so it is asserted by
`DocumentedNonSupportWitnessTests.CommitRollbackFacility_NamedNonSupportWarning_PinnedToSpec`, which measures two
`warning COBOLNET1579` lines, one per verb, at `(34,5)` COMMIT and `(36,5)` ROLLBACK. Without that test the row
would have closed on bytes that prove nothing.

`docs/CONFORMANCE.md` §4 item 2 is the user documentation these three rows' `notes` point at, and it names the
APPLY COMMIT clause and the three EC-FLOW conditions — the repair this note made on 2026-08-31 — so the 22 rows
that remain are documented even while they are unwitnessed.
