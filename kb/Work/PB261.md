# PB261

**Rows:** `GR-14.9.7.4-3` · `GR-14.9.7.4-4` · `GR-14.9.7.4-5`

The registration wave stamped COMMIT's three substantive general rules **DOCUMENTED-NON-SUPPORT** under Annex
A.4.3, and all three **stay a GAP** for the witness the schema requires. Unlike the screen module, this one
carries an explicit self-report of the gap in the very document that licenses it.

## The licence, verified rather than inherited

* **A.4.3 item 4** "COMMIT statement 14.9.7" (and item 2, the IO-CONTROL `APPLY COMMIT` clause; item 3, the
  EC-FLOW-APPLY-COMMIT / -COMMIT / -ROLLBACK conditions). Cross-references checked: §14.9.7 IS the COMMIT
  statement and §14.9.36 IS ROLLBACK.
* **A.4.1**: the module's associated syntax rules, general rules, other rules, exception conditions and I-O
  status values are optional with it, "even if not explicitly listed" — which is what carries the licence from
  the named statement to GR3/GR4/GR5.
* `docs/CONFORMANCE.md` **§5**: `A.4.3 | Commit and rollback | Not claimed`; **§4 item 2**: "Commit and rollback
  (E.3.2 item 2 / A.3 items 6–7): `COMMIT`, `ROLLBACK`. No transaction manager."

## ⛔ The gap §4 declares about itself

§4's own preamble does not claim the recognize-and-warn posture for this facility yet:

> "SCREEN handling (item 4) is recognized at compile time and reported with the named COBOLNET1560 warning per
> §4.2.6; MCS, **COMMIT/ROLLBACK**, and VALIDATE (items 1–3) are today **a generic parse error** — their named
> recognize-and-warn diagnostics (the COBOLNET1560 band) are the tracked PHASE-13 Wave H code half, after which
> every row here meets the §4.2.6 warning mechanism / §4.2.13 obsolete flagging."

So the documented non-support is honest about being one step short: the construct is refused, but by a *generic*
parse error rather than a diagnostic that names the facility. A user who writes `COMMIT` learns that something
is wrong with their syntax, not that this implementation does not provide commit and rollback. That is the
difference the witness has to measure, and it is why these three rows cannot close on the licence alone.

## What is owed

1. A negative fixture proving a `COMMIT` (and, by the same rule, a `ROLLBACK` and an `APPLY COMMIT` clause) is
   **refused**, with the diagnostic actually emitted recorded as-is — the honest witness for today's posture.
2. When PHASE-13 Wave H lands the named COBOLNET1560-band diagnostic, the fixture becomes the witness for the
   §4.2.6 mechanism and these rows close. Until then the fixture pins a generic refusal, which is a
   corroborating regression net and **not** grounds to close: the row's requirement is a test proving the
   DOCUMENTED behaviour happens, and the documented behaviour is the named warning.
3. `GR-14.9.7.4-4` deserves its own line because it is the only one of the three whose absence has a
   *file-lifetime* consequence rather than a statement-level one: GR4 requires a CLOSE on a commit-subject file
   to DEFER its file-lock release until a later COMMIT performs it, and `FileRegistry.SharedClose` releases
   unconditionally on every close with no deferral list anywhere in `src/Cobol.Net.Runtime/IO`. With the
   facility declined there is no way to write a program that observes the difference — but that is a
   *consequence* of the decline, and if `APPLY COMMIT` ever becomes recognized-and-warned rather than a parse
   error, this is the rule whose absence stops being unobservable first.
