# PB506

## Mechanism — value-clause-p2
THE REPORT-SECTION (FORMAT 4) VALUE LANE HOLDS ONE OPERAND AND ROUTES IT THROUGH THE SOURCE CLAUSE'S IMPLICIT MOVE. Two defects, one lane. (1) src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs:161 declares `FieldValueSource(string Raw)` -- a single operand -- built at :543 from :440's `ExtractValue(value)`, which returns the first valueItem's GetText. The Format-4 operand LIST is never modelled, so no count can be compared with the repetition count (SR35) and no operand after the first can be distributed (13.18.63.4 GR23). (2) src/Cobol.Net.Compiler/CodeGen/Verbs/ReportWriterEmitter.cs:129-159 FieldImage turns that FieldValueSource into `move.ConvertSource(source, f.PrintItem)` -- the conversion path of the SOURCE clause's implicit MOVE -- under a comment citing "ISO 13.18.53.4 GR1; a VALUE item per 13.18.63". 13.18.53.4 GR1 is about identifier-1 of a SOURCE clause and says nothing about a VALUE literal: a real clause answering a different question. A MOVE edits; a VALUE initialization does not, so an alphanumeric-edited printable item gets its literal EDITED.

### Expected, from the standard
SR35 (13.18.63.3): "If the VALUE clause has more than one operand, the entry shall be a repeating entry or shall be subordinate to a repeating entry. The number of operands of the VALUE clause shall be equal to the number of repetitions of the repeating entry or the same number multiplied by the number of repetitions of any number of successive repeating entries at higher levels than the repeating entry." (cite --check OK) 13.18.63.4 GR23 fixes the behaviour of the legal case: "If the VALUE clause has more than one operand, successive operands are assigned to successive repeating printable items, horizontally and then vertically, as applicable, in that hierarchy. If no further operands remain, assignment begins again from the first operand." (cite --check OK) -- so v35b shall print `AAA BBB CCC`, and v35c (3 repetitions, 2 operands) and v35a (a non-repeating entry with 3 operands) shall be diagnosed. SR34 makes SR11 apply to Format 4, and SR11's second sentence is "Editing characters in a picture character-string for an alphanumeric-edited or national-edited data item do not cause editing of the initial value when the data item is initialized." (cite --check OK); 13.18.63.4 GR21 delegates GR7, "Each literal is aligned in the associated data item in accordance with 14.6.8 ... except that initialization is not affected by a JUSTIFIED clause and no editing takes place." (both cite --check OK) -- so `PIC XXBXX VALUE "AB CD"` shall print `AB CD`, not `AB  C`.

### Observed
MEASURED at --std 2023. v35b is LEGAL SOURCE and prints the first operand three times: the second and third literals never reach the model, so the wrong answer is silent and the illegal-count case is indistinguishable from the legal one. The editing defect is localized to the report lane by the working-storage control (w11a), which stores `AB CD` unedited -- the divergence is FieldImage's MOVE routing, not the VALUE decoder. The pre-2002 legs could not be measured: the multiple-COLUMN vehicle is introduction-gated to 2002 (COBOLNET0900) and the OCCURS vehicle for a repeating report entry is refused COBOLNET0899 (d35_report_occurs), so multiple COLUMN is today the only reachable repeating shape and it is the one that answers wrongly. The working-storage lane rejects its analogous shape (a bare multi-literal Format-1 VALUE, COBOLNET1585, w1a) -- the report lane simply has no counterpart.

## Mechanism — value-clause-p4
A Format-4 VALUE clause with more than one operand is collapsed to a single string before it ever reaches the report model, and that one string is then emitted into every repetition of the entry. DataBinder.ExtractValue takes `value.valueItem().FirstOrDefault()` and, for an ordinary literal list, returns `item.GetText()` -- the concatenated token text of ALL the operands, quote characters included. The report binder calls that same helper (DataBinder.Reports.cs:440) and stores the result in `FieldValueSource(string Raw)`, a model record with room for exactly one scalar, so there is nowhere for a per-repetition operand list to live even if ExtractValue were fixed. The emitter then renders that one value once per COLUMN in the entry's column list. The Format-1 sibling of the very same glue IS caught -- DataBinder.cs:2404-2409 raises COBOLNET1585 when a data-item VALUE has more than one operand -- so the check exists and the report arm was simply never given it: the classic two-arm dispatch. Because 13.18.63.3 SR35 already requires a multi-operand entry to be a repeating entry (its own row is already recorded DIVERGES in the sibling part), the correct shape is a per-repetition operand list on the field model, cycled by GR23's own wrap-around sentence -- the structure that makes the next repetition vehicle (report-group OCCURS, multiple LINE) automatic rather than a second special case.

### Expected, from the standard
13.18.63.4 GR23: 'If the VALUE clause has more than one operand, successive operands are assigned to successive repeating printable items, horizontally and then vertically, as applicable, in that hierarchy. If no further operands remain, assignment begins again from the first operand.' (a) columns 1/6/11 = 'AAA' / 'BBB' / 'CCC'. (b) columns 1/6/11 = 'AAA' / 'BBB' / 'AAA'. (c) is not conforming source under 13.18.63.3 SR35 (a multi-operand VALUE requires a repeating entry) and should be rejected, never stored.

### Observed
MEASURED, compiling CLEAN at STRICT --std 2023 with no diagnostic: (a) prints 'AAA  AAA  AAA' -- the second and third operands are silently discarded and the first is replicated. (b) prints 'AAA  AAA  AAA'. (c) prints 'XX"YY' -- the raw text `"XX""YY"` was decoded with the doubled quote read as an escaped quote, which is what proves the collapse is a GetText() glue rather than a first-operand selection; in the X(3) cases the glued 'AAA"BB"C' is simply truncated to 'AAA' by the PICTURE, which is why they read as a replication.
