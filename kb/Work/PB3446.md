# PB3446 — plan_wave.py's stale-stamp arm ignores whether the report covers the tip

> ⚙ **flags:** process-only

Source: wave 1131 group F (PB3114, PR #308), branch review finding R1-1, severity low.

**Code site.** `scripts/orchestrator/plan_wave.py:1037`. The planner's new stale-stamp arm reads only the review stamp's coverage of the tip, never whether the REPORT covers the tip. For a FINDINGS-stamped DONE report followed by commits no report describes, the planner says "WAITING FOR REVIEW ... one cobol-reviewer reviews them (the enqueue unit's diff-only re-review)", while `prune_worktrees.lifecycle()` reads the same branch DECISION ("commits since the report's HEAD that no report describes"). No reviewer is ever dispatched for a DECISION row, so the planner names an action that never happens. That contradicts `review_coverage`'s docstring claim that the planner and `lifecycle()` never disagree on one branch.

**Fix direction.** One reader of "does the report cover the tip", shared by the planner arm and `lifecycle()` (one mechanism per job), with a drift test that runs both over the same branch states and asserts the same state.

## Landed

Re-probe (wave 20261031 A, carried to wave 20261106 A by cherry-pick): for a FINDINGS-stamped DONE report followed by
a commit no report describes, the planner's stale-stamp arm said WAITING FOR REVIEW while `prune_worktrees.lifecycle()`
read DECISION ("1 commit(s) since the report's HEAD ... no report describes"); the new self-test branch
`findings-resumed` was red before the fix. Fix: `prune_worktrees.report_since(head, tip)` is the one report-coverage
rule (the survey's `Row.report_since` calls it), and `prune_worktrees.Coverage` (replacing `review_coverage`, one lazy
graph of the survey's tips) answers both questions, `.review(stamp, branch)` and `.report(head, branch)`.
`plan_wave.plan(report_covers=...)` keeps WAITING FOR REVIEW only where the report covers the tip and says RESUMED
(IN FLIGHT or a DECISION, no reviewer, no finisher) where it does not; `plan_wave.main` wires both callables from the
same `Coverage`. Drift test: `prune_worktrees.py --self-test` runs `lifecycle()` and `plan_wave.plan` over the same
three FINDINGS branches and asserts the planner says WAITING FOR REVIEW exactly where the survey does.
DESIGN-orchestrator-loop.md section 9 item 2 names both readers.
