# PB1745 — CRLF shell scripts survive a forward merge

## What happened

PB1719 (wave 72 G) added `*.sh text eol=lf` to `.gitattributes` after the first worktree run of the Linux gate found
`*.sh` checked out CRLF under `core.autocrlf=true` (kb/Work PB1732, "Two defects of the gate itself"). The wave-73
implementer worktrees were cut before that rule and fast-forwarded past it (base `86cdf4456`). A merge or fast-forward
rewrites only the files it changes, so the existing CRLF working copies stayed: group C counted 24 `.sh` files that
`git ls-files --eol` shows as `w/crlf attr/text eol=lf`. `wsl -d Ubuntu ... bash scripts/linux-gate.sh` then failed
at once with `set: -: invalid option` in groups C, E and F. Each fixed it by hand (`rm` the file, then
`git checkout -- "*.sh"`).

## Harm

Loud, not silent: the gate prints no `=== LINUX GATE:` verdict, so it cannot pass as green. Cost is one failed run and
a manual repair per worktree, and a lander that reads NOT RUN as an environment fault could skip the leg.

## Fix direction (for the owner of the gate tooling)

Either `scripts/linux-gate.sh` refuses early with a named message when its own tracked copy has CRLF endings in the
working tree (it cannot run far under CRLF, so the check belongs in a small launcher or in the PowerShell/Bash caller),
or the dispatch step that merges a worktree forward runs `git add --renormalize` / re-checks-out `*.sh`. One mechanism,
chosen once, with a drift test that plants a CRLF copy.
