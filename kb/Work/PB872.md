# PB872 — OPEN — one violation, two diagnostics, whenever the item is in the LINKAGE SECTION

Source: the `PB504` implementer report, "New defects" item 1.

## Repro — re-run on this tree, with its control IN THE SAME PROGRAM

`scratchpad/reg5/p5_lk.cob` (PROGRAM-ID `REG5P5`), `--std 2023`. The program declares the SAME illegal shape —
a picture-less elementary item with an alphanumeric VALUE at level 01 — once in WORKING-STORAGE and once in
LINKAGE, so the control and the subject are one compilation:

```
p5_lk.cob(6,8): error COBOLNET0881: data item 'WSA': a PICTURE clause shall be specified ...
p5_lk.cob(8,8): error COBOLNET0881: data item 'LKA': a PICTURE clause shall be specified ...
p5_lk.cob(8,8): error COBOLNET0881: data item 'LKA': a PICTURE clause shall be specified ...
```

`WSA` once. `LKA` twice, at the same line, the same column, with identical text. The duplication is not in the
gate — it is in the forest the gate walks.

## Observed, in the code

```
src/Cobol.Net.Compiler/Binding/DataBinder.cs:750             _roots.Add(item);        // unconditional: no EntrySection test
src/Cobol.Net.Compiler/Binding/DataBinder.Linkage.cs:190     LinkageRoots.AddRange(BindEntries(entries, rootNames, EntrySection.Linkage));
src/Cobol.Net.Compiler/Binding/DataBinder.cs:5433            return Roots.Concat(LinkageRoots).SelectMany(Walk).Concat(TypeDecls.Values.SelectMany(Walk));
```

`BindEntries` returns the roots it just appended to `_roots`; `CallBindLinkage` appends that same list to
`LinkageRoots`; `DeclaredForest()` concatenates both. Each linkage root and its whole subtree is therefore
walked twice.

The method's own summary comment, six lines up at `DataBinder.cs:5379`, states the invariant that is violated:

```
/// the LINKAGE forest (<see cref="LinkageRoots"/>, kept OFF <c>Roots</c>), and the TYPEDEF templates
/// (<see cref="TypeDecls"/>, also OFF <c>Roots</c>)
```

TYPEDEF templates really ARE kept off `_roots` (the `rootIsTemplate` arm at `DataBinder.cs:740` calls
`RegisterTypeDecl` INSTEAD of `_roots.Add`); linkage roots are not, and nothing asserts the difference. This is
`feedback_a_dead_lookup_is_also_unverified` in a doc comment: a stated invariant nothing tests.

## The rule

Not an ISO semantic rule — §4.2.2's diagnostic mechanism reporting one violation twice. Nothing in the compiler
is made to answer a wrong value by it; the harm is entirely in the message stream, which is why this is MINOR.
It is filed because it is a one-line structural defect whose blast radius is EVERY gate written over the forest,
and because a duplicate error is how a user learns to stop reading the error list.

```

```

Five walks: the ALIGNED gate, the PICTURE-required gate (COBOLNET0881, measured above), the USAGE-declaration
gate, the Step-14g version-conformance data-attribute gates, and the PICTURE-composition forest. Every one of
them double-fires on a LINKAGE item today; only the PICTURE-required one was measured, because one measured arm
is enough to prove the forest and the other four follow by construction.

### Why only ONE of the five gates showed it

`DataBinder.Aligned.cs#CheckAlignedClauses` ends its error arm with `item.IsAligned = false;` — so the second
visit hits `if (!item.IsAligned) continue;` and says nothing. The mutation that makes that gate idempotent is
also what hides the double-walk from it. `CheckPictureRequired` has no such mutation, which is why COBOLNET0881
is the arm that prints twice. **Do not read the other gates' silence as evidence they are unaffected** — it is
evidence about their mutation, not about the forest (`feedback_reachability_is_measured_not_deduced`), and a
gate that gains a non-mutating arm tomorrow starts double-reporting with no change to its own code.

`process_only: true` is set for the register's purposes — no user PROGRAM computes a different answer — but the
duplicated line is in the compiler's user-visible output, which is why this is filed as a defect rather than as
an observation.

## Code site and the shape of the fix

`src/Cobol.Net.Compiler/Binding/DataBinder.cs#DeclaredForest`. The fix is at the SOURCE of the duplication, not
at the concat: `BindEntries` should not add a LINKAGE root to `_roots` (it already knows the `EntrySection` — it
is passed in and, per `kb/Work/PB858`, thrown away), which makes the doc comment true. The alternative — a
`Distinct()` on the concat — papers over it and leaves `Roots` itself wrong for every other reader.

**Pair it with the drift test that makes the invariant real** (CLAUDE.md rule 5): a unit test asserting
`Roots.Intersect(LinkageRoots)` is empty and that `DeclaredForest()` has no repeated reference, over a program
with a working-storage root, a linkage root, an FD record and a TYPEDEF.
