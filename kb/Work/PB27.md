# PB27 — LANDED — the §A.4.9 non-support leaks, re-measured; all three bullets were wrong in different ways

> ⚙ **flags:** silent · under_rejects
> The locale module's documented non-support (`COBOLNET1518`, owner-ratified 2026-07-03) is correct and loud for
> the FUNCTION forms — 33 of that batch's 36 NOT-IMPLEMENTED rows are that one ratified disposition and are NOT
> defects. This note tracked three claimed leaks. **Every one of them was measured on 2026-08-07 and none was
> what the entry said it was.**

## ⛔ ①  "THE LOCALE CLAUSE IS SILENTLY ACCEPTED" — STALE. It is loud, and was ALSO printing a FALSEHOOD.

[[PB25]] landed `localeClause` and the clause has diagnosed correctly ever since. But the measurement turned up
what the entry could not have known, because it stopped at "is it silent?":

```
SPECIAL-NAMES. LOCALE FRENCH IS "fr_FR".
  ⛔ COBOLNET1518: the SPECIAL-NAMES LOCALE clause is in the optional locale module …   ✅ true
  ⛔ COBOLNET0901: 'LOCALE' is a reserved word in COBOL-2023 and cannot be used as a
                  user-defined word (ISO §8.9)                                          ⛔ FALSE
```

**`LOCALE` is not a lexer token**, so §12.3.7's `localeClause` matches the clause's own KEYWORD through
`cobolWord`, and the §8.9 funnel read it as a user-defined word. The program uses it as no such thing. A true
diagnostic and a false one, printed together — and the false one tells the reader to rename something they never
named.

**FIX:** the funnel already carries this exact exemption for `ENTRY-CONVENTION`'s value slot and for
`EXCEPTION-OBJECT` in an object reference — a keyword grammar-matched as `cobolWord` so the funnel can decide by
CONTEXT. LOCALE joins them, **position-exact**, because the clause's three `cobolWord` slots are three different
kinds of word (§12.3.7 general format: `LOCALE locale-name-1 IS { external-locale-name-1 | literal-4 }`):

| slot | what it is | funnel |
|---|---|---|
| [0] `LOCALE` | the clause KEYWORD — a use OF the reserved word | exempt |
| [1] locale-name-1 | a genuine USER-DEFINED word | **stays funneled** |
| [2] external-locale-name-1 | an IMPLEMENTOR name (§12.3.7 GR5 leaves its values to the implementor) | exempt |

Exempting the whole clause would have hidden a real §8.9 violation in slot [1]. Both directions are pinned by
`SpecialNamesLocaleEditionTests`.

⛔ **WHY NO GATE SAW IT: a negative fixture's `.err` names ONE code.** `pb25-special-names-locale-a49` asserted
COBOLNET1518 was PRESENT and had no way to ask whether anything else was, so it stayed green through the entire
defect ([[feedback_green_test_can_hold_a_gap_open]]). The new assertion is a `DoesNotContain` — the shape a
fixture cannot express.

## ⛔ ②  THE `ArgKinds` ROW WAS WRONG — AND SO WAS THE LINE ABOVE IT, WHICH THE ENTRY DID NOT NAME.

The entry named `LOCALE-TIME`. `LOCALE-DATE` is the preceding line in the catalog with the **identical** wrong
value, `"is"` — argument-1 as an integer ([[feedback_scan_all_similar]]):

- **§15.52.3 r1** — "Argument-1 shall be of class alphanumeric or national and shall be **8** character positions"
- **§15.53.3 r1** — "Argument-1 shall be of class alphanumeric or national and shall be **6** character positions"
- normative **Table 21** agrees with both: `Anum1 or Nat1, Loc2`

Both rows are now `"ss"`. `LOCALE-TIME-FROM-SECONDS` (`"ns"`) and `LOCALE-COMPARE` (`"sss"`) were already right —
checked, not assumed.

⚠ **ANNEX D DISAGREES AND DOES NOT GOVERN.** D.31.4.2 describes argument-1 as "a date in standard date form
(YYYYMMDD)", which reads as an integer and is very likely where `'i'` came from. **Annex D is marked
`(informative)`** and the front matter calls it an explanation of features. A concepts annex is not a rule.

⚙ **The column is DEAD for these rows today** — `Bind = Unsupported`, so COBOLNET1518 fires first at every
`--std` (measured with both an integer and a spec-correct alphanumeric argument). That is exactly why it was
never contradicted: [[feedback_a_dead_lookup_is_also_unverified]]. [[PB1]] is the standing proof of the cost of
the opposite mistake — an `ArgKinds` column ENFORCED as written, without re-derivation, rejected 12 legal corpus
programs.

## ⛔ ③  THE `IntroducedIn 2002` CLAIM IS UNCHANGED, BECAUSE ITS OWN PREMISE IS REFUTED BY THE SPEC.

The entry argued `LOCALE-TIME-FROM-SECONDS` belongs to the 2014 date/time package because "argument-1 is in
standard numeric time form (§15.5.5) — **a form no 2002 function produced**". That premise is false:

> §15.80.1 — "The **SECONDS-PAST-MIDNIGHT** function returns a value in **standard numeric time form** …"
> §15.80.3 r1 — "The returned value is in standard numeric time form."

and `SECONDS-PAST-MIDNIGHT` is catalogued 2002. The citation was real, the rule was real, and the PREMISE did not
hold — [[feedback_validate_the_premise_not_only_the_rule]] for the second time in this one note.

⚠ **AND THERE IS NO AUTHORITY EITHER WAY IN THE 2023 STANDARD.** §8.11 lists the intrinsic function NAMES with no
edition data; Annex E lists only 2014→2023 changes and does not mention this function; `IntroducedIn` for
intrinsics is hand-assigned in `IntrinsicCatalog`. Deciding 2002-vs-2014 needs ISO/IEC 1989:2002 or :2014, which
this repo does not hold. **The field is LIVE** — at `--std 85` it prints `COBOLNET1502: … was introduced by
ISO/IEC 1989:2002`, a factual claim to the user — so it is not free to guess at. **Disposition: no change, and
the refuted argument recorded here so it is not re-run.** Revisit only with a copy of the 2002 or 2014 standard.
