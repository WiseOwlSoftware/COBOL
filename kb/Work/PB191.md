# PB191 — LANDED — the CURRENT-DATE / WHEN-COMPILED offset determination

> ⚙ **Authority:** the owner protocol of 2026-08-30 ("confirm to what the other model COBOL implementations do;
> ask if there are significant considerations") plus the owner's explicit answer of 2026-08-30 via
> AskUserQuestion — **"True offset"**. Recorded as plan item **D-A…D-G / D-D**. ⛔ Not to be re-litigated.

## The question this closes

Inventory rows `RV-15.21.3-1` and `RV-15.99.3-1` both sat at NEEDS-OWNER-DECISION carrying the same bare
question: *on a host whose local UTC offset is +14:00, what shall CURRENT-DATE (and WHEN-COMPILED) return in
character positions 17–19?*

§15.21.3 r1 fixes positions 18–19 at **"00 through 13"** when position 17 is `+` and **"00 through 12"** when it
is `–`; §15.99.3 r1 carries that table character for character. Both bounds are exceeded in practice:

- **`+`:** UTC+14:00 is a shipping zone on both target platforms — IANA `Pacific/Kiritimati`, Windows
  `Line Islands Standard Time`, whose display name is "(UTC+14:00) Kiritimati Island". Read off the host zone
  table for this note rather than inherited from the earlier record.
- **`–`:** no host zone is below −12:00, but `COBOLNET_CLOCK` parses a `DateTimeOffset` **directly**, and that
  type's offset range is ±14:00 — so −13:00 and −14:00 are reachable and the departure is **symmetric**. An
  earlier row note asserted the minus branch "cannot exceed 12 because no TimeZoneInfo zone is below −12:00";
  that is true of the HOST ZONE TABLE and false of the value the function reports. Struck.

## Why no alternative conforms

For such a clock the rule's table names **no in-range value at all**, so every candidate behaviour departs from
something:

| Candidate | What it violates |
|---|---|
| emit `14` | leaves positions 18–19's stated range |
| clamp to `13` | misreports what §15.21.1 calls "the … local time differential factor provided by the system on which the function is evaluated" |
| write `0`/`00`/`00` | asserts position 17's "the system … does not have the facility to provide the local time differential factor" — false; the system has it, and it is 14 hours |

**The determination: report the true offset.** It is the only candidate that states nothing untrue, and it keeps
the value usable as an offset by the program that receives it. Every citation above was re-run with
`scripts/spec/cite.py --check` for this note, not carried over.

## What landed

- **One determination, two rows.** One formatter serves both functions (`CobolDate.Format21`), so the rows share
  the determination in their notes rather than each getting its own — but the sharing is **proved, not assumed**:
  the compile-time bake (`IntrinsicBinder.CompileClock`) and the run-time read (`RunUnit.Current.Clock`) are
  independent seams, and `WhenCompiled_AndCurrentDate_AgreeOnPositions17To21_UnderOneClock` pins both to one
  instant and requires the same 21 characters.
- **`docs/CONFORMANCE.md` §3** gains the determination bullet: both signs, Kiritimati named, the three-way
  no-conforming-option argument, and the §4.2.6 / §4.2.7 documentation ground.
- **Verdicts:** `RV-15.21.3-1` and `RV-15.99.3-1` NEEDS-OWNER-DECISION → **DOCUMENTED-NON-SUPPORT**, both with
  test-refs. GAP 3659 → 3657.
- **Tests, and what makes them more than "14 comes out".** `CurrentDateOffsetDeterminationTests` re-derives the
  whole §15.21.3 r1 position table **from the rule text** and requires the set of out-of-range position spans to
  be **exactly `{18-19}`** across the fixtures and **empty** for every offset the rule admits — so the
  determination's SCOPE is what is pinned, and a regression that broke positions 15–16 or 20–21 at an extreme
  offset fails even while the headline value still looks right. `CurrentDateOffsetPinTests` runs a real COBOL
  program under `COBOLNET_CLOCK` at +14:00, −14:00, +13:00, +05:45, +00:00 and −09:30.
- **Two stale sentences struck from the row notes.** The clock-seam claim ("CurrentDate() reads
  `DateTimeOffset.Now` directly … an identity the seam split breaks") predates R21 and is now the opposite of the
  truth — `CurrentDate()` reads `RunUnit.Current.Clock.Now()` and `ClockSeamDriftTests` forbids the direct read
  coming back. And the minus-branch claim above.

## Found on the way (and fixed here)

Adding a second mutator of the process-global `IntrinsicBinder.CompileClock` **raced immediately** with
`WhenCompiledStampTests`: green in isolation, red in the full run, the older test reading the newer test's
injected clock. Both classes now carry `[Collection("process-globals")]`, the collection [[PB126]] established
for exactly this. Worth recording because the race was found by the gate rather than by inspection — a new test
that touches a shared static is a concurrency change, not only a coverage change.
