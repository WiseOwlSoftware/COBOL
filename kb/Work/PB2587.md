## Repro

`E:\COBOL-coord\scratch\w1039c\mv.cob` (the compile-time GR10 a) lane): BY CONTENT `PIC X(4)` "ABCD" into a
`PIC X(6) JUSTIFIED RIGHT` formal arrives `ABCD  ` (a MOVE gives `  ABCD`); `PIC S9(3)` -12 into `PIC X(4)` arrives
`01K ` (a MOVE gives `012 `).

## Rule

ISO 14.2.3 GR9, for a program with a program-specifier: the allocated record has the formal's description and is
filled by "a COMPUTE statement without the ROUNDED phrase" if the formal is numeric, "otherwise, a MOVE statement".
ISO 14.9.25.4 6): "If the sending operand is described as being signed numeric, the operational sign is not moved".
Both checked with `cite.py --check` by the implementer.

## Code sites

`src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs#LandedForFormal` lands only numeric formals;
`src/Cobol.Net.Runtime/Control/CallAbi.cs#CobolArgAdapt.Text` adopts the argument image. The run-time lane PB2549 added
(`ProgramTable.LandArguments`, `BoundaryItem.Land`) registers only numeric formals' carriers, so it needs the MOVE leg
too: one landing for both lanes, as PB2549 did for the COMPUTE.

## Landed (wave 1042 group B, 2026-10-08)

Re-probed on the w1042b build: `mv.cob` printed `J GOT [ABCD  ]` and `X GOT [01K ]`; a second probe
(`E:/COBOL-coord/scratch/w1042b/rt.cob`) showed the run-time-located lanes wrong too (`ABCD  `, a 9(4) argument into
`PIC ZZ,ZZ9` as `1234  `), and so was every CALL to a program defined AFTER the caller in the same source:
§12.3.8.4 GR10 a) takes the details only from a definition "specified previously in the same compilation group", so
such a CALL is GR10 c)'s, located at run time. `OK §14.2.3 9)` "otherwise, a MOVE statement"; `OK §14.9.25.4 6)`
"the operational sign is not moved"; `OK §14.9.25.4 4)` "as if it were an alphanumeric to alphanumeric elementary
move".

Fix, one receiving half for both lanes: `MoveEmitter.CharacterStore` is now the store the MOVE statement's
`ConvertSource` uses for every non-numeric elementary receiver, and GR9's record goes through it. When the activating
element knows the formal (`BoundCallArg.Formal`), `CallEmitter.MovedFormal` + `MoveEmitter.RecordValue` perform the
MOVE (GR4's group move for a group argument) and the record crosses as a character cell; this replaced the two
literal/expression-only arms PB1113 and PB1946 had added. When it does not, the site states the MOVE's SENDING half
for each BY CONTENT argument (`CobolArg.Sending`, a `MoveSending` from `CallEmitter.WithMoveSending`), every unit
registers a compiled record builder for each non-numeric elementary formal (`MoveLanding`, from
`MoveEmitter.MovedRecord`), and `ProgramTable.LandArguments` applies it for a program the element has a
program-specifier for (GR9's first regime stays "without conversion"). One formal test for both lanes:
`CallEmitter.IsMovedFormal`. Sibling arms fixed on the INVOKE lane (a JUSTIFIED fast path, a literal, a figurative
fill into an edited formal and a group argument now take the same record), and the boolean-expression store is shared
(`CallEmitter.BooleanArgumentRecord`). `CallEmitter.RegisteredBoundary` dropped a formal that stated only a landing.

Witness: `conformance:2002/pb2587_content_move_leg` (CALL, function and INVOKE lanes; the first-regime contrast row
U1) and `BoundaryItemLandingTests` (four new facts). GR-14.2.3-9 re-verdicted CONFORMS with these witnesses (batch
`w1042b-pb2587-gr9-move-leg`).
