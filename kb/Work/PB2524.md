# PB2524 — the audits hold the gate slot

## Measured (w1033 gate performance diagnosis, `E:\COBOL-coord\scratch\reports\w1033-perf-gate-report.md` section 1)

From the `verdict.json` timings of 22 implementer gates on 2026-10-07 (the run directory is created after the slot is
taken, so the in-slot split is direct): total wall ~1,200 s (218-1,674); slot wait ~600 s (0-1,013); **inside the slot,
prepare (12 audits + corpus fetch) ~230 s (94-358)**, build ~10 s, legs ~330 s, post-legs ~5 s. The slot is held about
430-940 s and **35-45 % of that is the audits**: twelve Python processes run serially on one core while the slot queue
waits. Timed serially at 25 % host load the audits are 113.7 s (DOC CITATIONS 95.4 s, CITATIONS 12.5 s, the other ten
5.8 s); under gate load 150-350 s. The slot queue is therefore mostly other gates' audits.

## Mechanism

`scripts/run_gate_legs.py#Gate.run` takes the slot (`Host.take_slot`) and THEN `_gate` runs `Host.audits` (PB2523 moved
them before the build, but still inside the slot). The audits read only the tree: no build output, no test result, no
shared resource the slot protects (the slot caps concurrent builds and test legs, DESIGN-test-build-ci section 3.14.6).

## Shape

Run the audits before the slot is taken, in the gate's own process, under the worktree's gate lock: the slot is taken
only for the build and the legs. A red audit still ends an implementer gate RED with no leg run (PB2523's fail-fast),
and in lander mode (no slot) it is still merged into the one verdict. Self-test arm: the FakeHost records the order of
`audits` and `take_slot`, and the gate is RED when an audit is red. Docs: DESIGN-test-build-ci section 3.14.3 and
3.14.6, the gate skill, MANDATORY-PRACTICES I1.
