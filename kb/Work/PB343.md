# PB343 — an indexed rule enforced on a relative file

**Rows:** `GR-14.9.30.4-L4.3` (shared with **PB334**, which owns the sequential half of the same rule).

## The program

`<lane3 scratch>/out-b1/probe/relprev/relprev.cob` — `ORGANIZATION IS RELATIVE`, `ACCESS MODE IS DYNAMIC`,
`RELATIVE KEY IS RK`; write RRNs 1,2,3 = AAAA/BBBB/CCCC; CLOSE; `OPEN INPUT`;
`READ F PREVIOUS RECORD ... AT END / NOT AT END`.

Observed: `REL-PREV-AFTER-OPEN AT-END` with FS=10.

## The rule

> §14.9.30.4 GR21, *When the file is a relative file*, rule b): If the file position indicator was established by
> a prior successful OPEN or START statement, the first existing record that is selected is made available,
> regardless of whether NEXT or PREVIOUS is specified.

`--check 14.9.30.4 "the first existing record that is selected is made available, regardless of whether NEXT or
PREVIOUS is specified"` → **OK**. `OPEN INPUT` sets the FPI (§14.9.27.4 GR14), so the READ PREVIOUS makes RRN 1
available: NOT AT END taken, record AAAA, FS=00.

## What the compiler does

`RelativeConnector.ReadSequential:206-207` is

```csharp
if (previous && _positioner == 'O') slot = null;   // READ PREVIOUS immediately after OPEN -> at end
                                                    // (2023; VERSION_CHANGE_REFERENCE row 29)
```

That behaviour is correct for the **INDEXED** organization, where rule d.3 says exactly this, and it is what
Annex E.2 item 22 amended. But **Annex E is INFORMATIVE** (`specs/ISO_COBOL.md:42847-42848`: `## Annex E` then
`(informative)`) and item 22 carries no organization qualifier; the amendment landed in the indexed block only.
The relative and sequential blocks still say rule b), verbatim and unconditionally.

The same reasoning applies to the sequential block, but there PREVIOUS is dropped entirely (**PB334**), which
happens to make PREVIOUS-after-OPEN accidentally right and PREVIOUS-after-READ wrong.

## Evidence that the mis-attribution is spreading rather than being contained

`tests/CobolSharp.Tests.Integration/SpecFixTests.cs:652` pins *the RELATIVE-file analog of
ReadPrevious_AfterOpen_RaisesAtEnd* while citing `ISO §14.9.30 GR21 d.1`, and `:695` cites `GR21 d.2` for another
relative case — d.1/d.2/d.3 are the INDEXED block's rules and answer a different question. Those two citations
are also listed in **PB320**'s sweep.

## If the owner wants the other answer

Making the relative and sequential blocks follow the indexed rule anyway — on the reading that E.2 item 22
intended all three and the amendment was editorially incomplete — is a decision to record with its own citation,
not a silent inheritance from a row of `VERSION_CHANGE_REFERENCE`. Raise it as a `status: owner` note if the
fixer reaches that conclusion; the normative text as it stands does not support the current behaviour.

**Code site:** `RelativeConnector.cs#ReadSequential` (lines 206-207).

## Landed — 2026-09-09

**Re-probed first on a worktree build of today's tree and the mechanism held**, though the code had MOVED: the
carve-out is no longer `ReadSequential:206-207` but `RelativeConnector.SelectSequentialSlot`, where PB338's
peek/read split put it (`if (previous && _positioner == 'O') return null;`). A rebuilt probe — RRNs 1/2/3 =
AAAA/BBBB/CCCC, `CLOSE`, `OPEN INPUT`, `READ F PREVIOUS` — printed `A-AT-END FS=10` where relative rule b) owes
`A-OK FS=00 RK=0001 REC=AAAA`.

**The rule, re-derived rather than inherited.** `--check 14.9.30.4 "the first existing record that is selected
is made available, regardless of whether NEXT or PREVIOUS is specified"` → OK 14.9.30.4 21) b).
`--check 14.9.27.4 "the file position indicator for that file connector is set to 1"` → OK (GR14 — the indicator
after OPEN INPUT/I-O on a relative file). `--check 14.9.41.4 "the file position indicator is set to the relative
record number of the first logical record in the file whose key satisfies the comparison searching the file
sequentially"` → OK (GR9 a); GR9 b) is the reverse search, GR11/GR12 are FIRST/LAST). Those three settle the
shape of the fix: **rule b) is direction-BLIND, and it is the whole rule for an inclusive indicator.** A relative
START can only ever leave the indicator on an EXISTING record (an unsatisfied comparison is GR9 c)'s invalid key,
which invalidates it), so the only inclusive indicator that can name an empty slot is OPEN's 1 over a file whose
lowest RRN is higher — and there "the first existing record" is that lowest RRN whichever direction was written.
Reading rule b) as "inclusive, but still searching in the statement's direction" fails exactly that case, so it
is not what "regardless" can mean.

**The fix.** `SelectSequentialSlot` now branches on `_inclusive` FIRST: one ascending walk from the indicator
serves both directions under rule b), and only the rule c) arm consults `previous`. The `_positioner` char went
with it — it moved in lockstep with `_inclusive` and existed only to enforce the indexed carve-out, so keeping
it would have left a second field answering one question (and a dead one, which is worse: nothing contradicts a
lookup nobody reads). `IndexedConnector` keeps ITS `_positioner`: there the carve-out is rule d.3 and correct.

**The sweep found two more copies of the same mis-attribution, and both are fixed here.**

1. `src/CobolSharp.Runtime/IO/RelativeFileHandler.cs#ReadPrevious` — the LEGACY engine, which is still the
   differential oracle until P15, carried the identical arm (`if (_currentRecord == 0) return FileStatus.AtEnd;`)
   under the identical wrong citation, "ISO §14.9.30 GR21 d.1". An oracle that encodes a wrong rule manufactures
   false flips, so it is now `return ReadNext(recordBuffer);` — rule b) delegating to the one copy of the forward
   selection, rule d)'s '14' RELATIVE KEY overflow test included. Its START arm's "GR21 d.2" citation is now
   rule b) too.
2. `tests/CobolSharp.Tests.Integration/SpecFixTests.cs` — the two tests the note named. That project drives the
   LEGACY compiler, so `ReadPrevious_Relative_AfterOpen_RaisesAtEnd` was a GREEN test holding the defect open in
   both engines at once; it is now `ReadPrevious_Relative_AfterOpen_MakesTheFirstRecordAvailable` expecting
   `GOT 11`. `ReadPrevious_Relative_AfterStartEqual_ReturnsTheEqualSlot` asserted the right ANSWER under the
   wrong rule (d.2) and keeps its expectation with rule b) as its citation.

**No edition parameter, and that is a derivation, not an omission.** Annex E is INFORMATIVE (`## Annex E` then
`(informative)`) and E.2 item 22 names no organization, but the amendment it describes exists only in GR21's
indexed sub-rule d.3. The relative block's rule b) reads identically in 2002, 2014 and 2023, so the three
per-edition copies of the golden assert the SAME expected output rather than differing by edition.
`docs/VERSION_CHANGE_REFERENCE.md` row 29 now carries that scope in the row itself — it was the vector by which
the indexed rule reached this connector — and `docs/COBOLNET_FILES_DESIGN.md` records both legs as landed.

**Goldens.** `conformance:{2002,2014,2023}/pb343_read_previous_relative` (PROGRAM-IDs PB343R2/PB343R4/PB343R3)
and `conformance:negative/pb343-read-previous-relative-85` (COBOLNET0900 — the third organization for the one
`IBoundRead` gate arm, alongside PB334's sequential negative and the indexed
`EditionGateDiagnosticTests.ReadPrevious_At85_Registry0900_Not0860`). Every expected value is computed from the
rules above: R1 = rule b) after OPEN; R2 = rule c) then rule e)/GR24; R3–R6 = rule c) both ways plus rule f);
**S1/S2 = the SPARSE file, which is what makes "regardless" falsifiable** (lowest record at RRN 5, so OPEN's
indicator of 1 names an EMPTY slot and only a direction-blind rule b) can make PREVIOUS and NEXT agree — a
dense file cannot tell rule b) from a backward walk that merely includes the indicator); T1/T2 = rule b)'s START
leg, forward and reverse (GR9 a)/b)); E1 = rule e) on an empty file. The middle field of each line is the
RELATIVE KEY item, which GR25 makes the RRN of the record made available.
