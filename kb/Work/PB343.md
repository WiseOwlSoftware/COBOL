# PB343 — an indexed rule enforced on a relative file

**Rows:** `GR-14.9.30.4-L4.3` (shared with **PB334**, which owns the sequential half of the same rule).

## The program

`<lane3 scratch>/out-b1/probe/relprev/relprev.cob` — `ORGANIZATION IS RELATIVE`, `ACCESS MODE IS DYNAMIC`,
`RELATIVE KEY IS RK`; write RRNs 1,2,3 = AAAA/BBBB/CCCC; CLOSE; `OPEN INPUT`;
`READ F PREVIOUS RECORD ... AT END / NOT AT END`.

Observed: `REL-PREV-AFTER-OPEN AT-END` with FS=10.

## The rule

> §14.9.30.4 GR21, *When the file is a relative file*, rule b): If the file position indicator was established by
> a prior successful OPEN or START statement, the first existing record that is selected is made available,
> regardless of whether NEXT or PREVIOUS is specified.

`--check 14.9.30.4 "the first existing record that is selected is made available, regardless of whether NEXT or
PREVIOUS is specified"` → **OK**. `OPEN INPUT` sets the FPI (§14.9.27.4 GR14), so the READ PREVIOUS makes RRN 1
available: NOT AT END taken, record AAAA, FS=00.

## What the compiler does

`RelativeConnector.ReadSequential:206-207` is

```csharp
if (previous && _positioner == 'O') slot = null;   // READ PREVIOUS immediately after OPEN -> at end
                                                    // (2023; VERSION_CHANGE_REFERENCE row 29)
```

That behaviour is correct for the **INDEXED** organization, where rule d.3 says exactly this, and it is what
Annex E.2 item 22 amended. But **Annex E is INFORMATIVE** (`specs/ISO_COBOL.md:42847-42848`: `## Annex E` then
`(informative)`) and item 22 carries no organization qualifier; the amendment landed in the indexed block only.
The relative and sequential blocks still say rule b), verbatim and unconditionally.

The same reasoning applies to the sequential block, but there PREVIOUS is dropped entirely (**PB334**), which
happens to make PREVIOUS-after-OPEN accidentally right and PREVIOUS-after-READ wrong.

## Evidence that the mis-attribution is spreading rather than being contained

`tests/CobolSharp.Tests.Integration/SpecFixTests.cs:652` pins *the RELATIVE-file analog of
ReadPrevious_AfterOpen_RaisesAtEnd* while citing `ISO §14.9.30 GR21 d.1`, and `:695` cites `GR21 d.2` for another
relative case — d.1/d.2/d.3 are the INDEXED block's rules and answer a different question. Those two citations
are also listed in **PB320**'s sweep.

## If the owner wants the other answer

Making the relative and sequential blocks follow the indexed rule anyway — on the reading that E.2 item 22
intended all three and the amendment was editorially incomplete — is a decision to record with its own citation,
not a silent inheritance from a row of `VERSION_CHANGE_REFERENCE`. Raise it as a `status: owner` note if the
fixer reaches that conclusion; the normative text as it stands does not support the current behaviour.

**Code site:** `RelativeConnector.cs#ReadSequential` (lines 206-207).
