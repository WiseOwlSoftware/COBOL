# PB4412 - The margin-R note asks about omitted lines

**Sites:** `src/WiseOwl.Cobol.Frontend/Parsing/CobolErrorListener.cs` (`CobolErrorListener.NoteMarginRCut`, `CobolErrorListener.ReportMarginRCut`),
`src/WiseOwl.Cobol.Frontend/Common/MarginRCut.cs` (`MarginRCut`), and the conditional-compilation stage under `src/WiseOwl.Cobol.Frontend/Preprocessor/` that omits lines.

PB4372 (review R1-1) taught the between-lines arm to skip a tokenless line that holds program text, because a later stage omitted it. Residual: a line whose ONLY text is past margin R and which sits inside an omitted branch (a false `>>IF` branch, ISO 7.3.16.4) or is a debugging line without debugging mode is still asked about, because no stage tells the listener which blank lines were omitted. The result is a spurious note on a line the compiler never read.

**Fix shape:** the CC stage records its omitted origins (every line origin it drops, branch and debugging alike) and the locator refuses them, so the next omission kind is automatic. Pair it with a golden for a margin-R-only line inside a false `>>IF` branch and one for a debugging line without debugging mode.

**The omission is recorded where the stage that drops the line knows it, not in a list the listener keeps.**
(1) Text stages: the conditional-compilation driver marks the origin of every ordinary line it omits (`LineOrigin.AsOmitted()`, ISO
7.3.16.4 GR 3 and 7.3.13.4 GR 4); the mark rides the origin through COPY, REPLACE and NIST (`LineOrigin.From`, `OriginWriter`), and
`FixedFormAreas.MarginRCutAt` answers null for a marked line, so the next text stage that drops a line is one `AsOmitted()` call.
(2) The debugging line is not a text-stage fact: whether a `D` line is source is the unit's `WITH DEBUGGING MODE` (ISO 12.3.5.4 GR 1),
decided by `DebuggingLineRewriter` on the tokens after the line map exists. So `Hide` now moves the MARKER to the ABSENT_DEBUG_LINE
channel too (a line with no text token was invisible), `AbsentLines` names the hidden lines between two tokens, and the listener asks
both. The note's "debugging line" arm needed one more root fix: a debugging line whose program-text area is blank was DISCARDED by the
logical conversion (6.5 2), so the rewriter never saw it; its slot now holds the bare carrier (`LogicalLineBuilder.EmitDebugging`), a
line of the same effect on the join target and the literal state, found by the rewriter and decided by the mode (pinned by
`ABlankDebuggingLine_BetweenTheLinesOfALiteral_StillContinuesIt`). With the mode the line stays source and the note stays
(`ADebuggingLineWithTextOnlyPastMarginR_WithDebuggingMode_IsAskedAbout`).

**Found in the same files (I9): a blank line lost its origin.** The control of the first test (the same line in the branch the directive TAKES)
gave no note either, before and after the fix above. A block of ONE empty line between two directives went through
`ExpandCopiesOneLevel` with no content for `OriginWriter` to name its only piece by, so the piece was named `("", 0)`, a line of no file,
and every question about it (cut, omission) found no format map; and a final empty piece took the origin of the piece BEFORE it. Fixed at
both: `ExpandCopiesOneLevel` hands a one-empty-line block back as it stands, and the writer names an empty trailing piece by the empty
input piece it was written for (`OriginWriter.Write`, `Finish`; `OriginWriter_AnEmptyInputPiece_KeepsItsOwnOrigin`). Before: a past-margin-R
line alone between directives in a TAKEN branch (or a lone blank line there) drew no note at all.
