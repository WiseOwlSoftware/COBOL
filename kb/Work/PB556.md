# PB556

## Mechanism — value-clause-p2
A FORMAT-3 VALUE AT A NON-88 LEVEL IS GLUED INTO THE FORMAT-1 RAW-VALUE CHANNEL. src/Cobol.Net.Compiler/Binding/DataBinder.cs:2975-2993 ExtractValue takes the first `valueItem` and returns `item.GetText()`; a `valueItem` may itself BE a `valueClauseRange` (CobolData.g4:641-644), so `VALUE 1 THRU 5` yields the raw string `1THRU5` and `VALUE "A" THRU "C"` yields `"A"THRU"C"`. The level-number is never consulted -- no site in src/ screens the VALUE format against the level -- so the Format-1 emitter receives a Format-3 body. For a NUMERIC subject that string is emitted as a numeric initializer and the Roslyn backend rejects the generated C#; for an ALPHANUMERIC subject it is decoded and truncated to the picture width, storing garbage. The `WHEN SET TO FALSE` tail (CobolData.g4:622) is dropped at any level, so the second Format-3-only phrase is accepted in silence too.

### Expected, from the standard
SR33 (13.18.63.3): "Formats 3 and 5 may be specified only when the level-number of the subject of the entry is 88." (cite --check OK) A VALUE clause carrying a THROUGH phrase or a WHEN SET TO FALSE phrase on a level-01/05/77 entry is therefore nonconforming source and shall be diagnosed at compile time with a named diagnostic. Under no reading may it reach the code generator: a syntax-rule violation is a compile-time reject, never a backend failure and never a silently stored value.

```
$ python scripts/spec/cite.py --check 13.18.63.3 "Formats 3 and 5 may be specified only when the level-number of the subject of the entry is 88"
  OK  §13.18.63.3 33)  (Syntax rules)
```

### Observed
MEASURED at --std 85, 2002, 2014 and 2023 -- the behaviour is edition-invariant because ExtractValue carries no version predicate. Two distinct harms from one cause: a numeric subject crashes the compiler (the user sees Roslyn error text naming a generated .g.cs file, with no COBOL diagnostic at all), and an alphanumeric subject compiles clean and holds the source text of the range instead of a value. The neighbouring case IS handled -- a bare multi-literal Format-1 VALUE is rejected COBOLNET1585 (w1a_ws_multi_literal) -- which shows the guard belongs exactly where the range case falls through.

## Landed 2026-09-20 — wave 41 (E)

RE-PROBED FIRST on this worktree's own `dotnet build CobolSharp.sln -c Debug`: all three harms still reproduced
exactly as written — `01 X PIC 9 VALUE 1 THRU 5.` failed the whole Roslyn compilation (`CS1002: ; expected` plus
two CS1519s, no COBOL diagnostic at all), `05 X PIC XXX VALUE "A" THRU "C".` compiled clean and stored the glued
source text `"A`, and `01 X PIC 9 VALUE 1 WHEN SET TO FALSE IS 0.` was accepted with the phrase dropped in
silence. A fourth shape the note had not measured does the same: `01 X PIC XX VALUE "AA" IN AL1.` — the
`IN alphabet-name-1` phrase is written only in formats 3 and 5 too.

FIXED AT THE ONE PLACE, as a SET rather than three conditions. `DataBinder.ConditionOnlyPhraseOf` names the
VALUE-clause phrases that exist only in format 3 or format 5 — the THROUGH phrase, `IN alphabet-name-1`,
`WHEN SET TO FALSE IS literal-4`, `{IS INVALID | ARE VALID}` — and `BindEntry`'s VALUE arm, which binds only
non-88 entries, reports COBOLNET2167 and binds nothing when one appears. §13.18.63.3 SR33 names FORMATS, and the
grammar admits every format through one rule on purpose (formats 3 and 5 share their literal / THROUGH list), so
a phrase added to that rule tomorrow is screened by adding one line here. That is the difference between this
rule staying true and its next arm being invisible the way these four were.

The VALID / INVALID arm is in the set and cannot be observed today: `DeclinedFacilityPass` refuses every A.4.14
content-validation surface by name (COBOLNET1708) in a pass that runs before the binder, at any level. It is
listed anyway — SR33 governs formats 3 AND 5, and writing only the reachable half is how a rule's other arm goes
missing.

GOLDENS: `tests/conformance/negative/pb556-value-through-at-non-88` (the crashing numeric twin),
