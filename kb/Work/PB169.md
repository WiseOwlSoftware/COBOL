# PB169

`ControlFlowBinder.BindTerminationStatus` (shared by STOP RUN and GOBACK — CallBinder's GOBACK arm) binds the
`statusPhrase` literal with the plain arithmetic entry `host.Expr.BindExpr(l)`, so a non-numeric literal-1 hits
ExpressionBinder.NumLiteral's §8.8.1.1 screens. `STOP RUN WITH ERROR STATUS "ABEND"` is conforming source —
§14.9.42.3 SR3 ("If literal-1 is numeric, it shall be an integer") presupposes the non-numeric form, SR4 bars
only a zero-length literal, and GR5 passes literal-1 to the operating system under implementor-defined
constraints. The rejection is not a regression (pre-PB155 the quoted text reached IntLiteralX and emitted
`"ABEND"L` — an undiagnosable Roslyn splat), but the diagnostic now cites a rule that does not govern the
position, which reads as an adjudicated determination and hides the real gap.

WHAT WOULD CLOSE IT: route the STATUS operand through its own non-arithmetic entry (the
`BindByValueExpr`/`BindFunctionArgumentExpr` precedent — both exist because "the §8.8.1.1 numeric-operand
screen does not apply" at their sites), decide the runtime meaning of a non-numeric exit status per GR5
(CONFORMANCE.md determination — the OS exit code is an int on both hosts, so the mapping is the decision), and
a golden or a correctly-cited rejection.

*(Found by the PB155 pre-landing review fleet, 2026-08-29; the refuters established the no-regression half.
Full claims in the session scratchpad `pb155-fleet-confirmed.json`.)*

## Re-verification and correction (2026-08-31, cluster-B implementation wave, tree `9a89fbd1`)

⛔ **THE NOTE ABOVE UNDER-STATES THE DEFECT BY HALF.** It names only `literal-1`. §14.9.42.3 SR2 (and GOBACK's
§14.9.18.3 SR6) also admit **an identifier** — "an integer data item **or a data item with usage display or
usage national**" — and the identifier arm went through the same arithmetic funnel. Measured, not derived:

    STOP RUN WITH ERROR STATUS "ABEND".         -> COBOLNET0844 "an alphanumeric literal is not a numeric operand"
    STOP RUN WITH ERROR STATUS WS-CODE.         -> COBOLNET0844 "item 'WS-CODE' of category alphanumeric ..."
      (01 WS-CODE PIC X(3) VALUE "007".)
    GOBACK WITH ERROR STATUS "ABEND".           -> COBOLNET0844 (the shared binder, the same rejection)

The identifier arm is the LARGER half of the rejects-legal-source surface, and `BindTerminationStatus`'s own doc
comment already said the position takes "an integer literal or a display/national/integer data item" — the code
rejected two of the three shapes its documentation promised.

**AND THE POSITION'S OWN RULES WERE UNENFORCED IN THE OTHER DIRECTION.** While §8.8.1.1 stood in for them,
nothing checked SR3/SR7 (a numeric literal-1 shall be an integer), SR4/SR8 (no zero-length literal) or
§13.18.38.3 r7 (the STATUS phrase is not one of the five index-name contexts). `STATUS ""`, `STATUS 1.5` and
`STATUS <index-name>` all compiled clean. The screen that WAS there rejected the legal shapes and admitted the
illegal ones, at once.

**Not an undecided question.** GR5 leaves the value constraint implementor-defined, and `docs/CONFORMANCE.md`
item 192 already published this compiler's determination ("a non-integer display/national operand is interpreted
numerically"). The code contradicted the published determination — a doc-vs-code divergence, not an open design
choice — so the landing implements the published mapping (`CobolNum.FromAlphanumeric`) and sharpens item 192's
wording to say explicitly that a NON-NUMERIC LITERAL takes the same reading.

✅ **THE OWNER QUESTION IS SETTLED — the survey was run 2026-08-31 and the consensus supports the published
mapping.** The question was: the item-192 mapping sends `STOP RUN WITH ERROR STATUS "ABEND"` to exit code **0**,
indistinguishable from NORMAL termination, which arguably defeats the programmer's intent on an ERROR status.
Under the `feedback_survey_compilers_on_latitude` protocol, the implementor-defined slot was surveyed before
being re-opened, and the survey found NO distinguishable-exit consensus to move to:

  * **GnuCOBOL 3.2, read behaviourally from its own sources (GPL — behaviour only, no text reproduced).** Its
    `stop_returning` production binds the phrase to ONE integer: with an operand present it hands that operand to
    `cob_stop_run`, cast to `int`; with the operand ABSENT it substitutes 1 for ERROR and 0 for NORMAL.
    `cob_stop_run(status)` then does `exit(status)`. There is no arm anywhere that maps "the operand is not
    numeric" to a distinguished exit — the operand's VALUE is the whole rule, exactly as item 192 says. A
    non-numeric operand yields whatever its digit extraction yields, and 0 when there are no digits.
  * **GnuCOBOL's own testsuite pins only the operand-LESS forms** (`run_misc:5345` NORMAL ⇒ 0, `run_misc:5363`
    ERROR ⇒ 1 — both AGREE_ACCEPT against us today). It contains no case with a non-numeric status operand, so
    it asserts nothing about the question in either direction.
  * **Vendor documentation (web survey, 2026-08-31)** turned up no compiler that gives a non-numeric status
    operand a distinguished exit. The one datum that points anywhere is a mainframe practice of mapping the
    status VALUE onto a user abend code (`STOP RUN … STATUS 1234` → U1234) — which is again "the value is
    passed", the same rule, not a non-numeric special case.

**Determination: item 192 stands as published, and this row is closed.** ERROR-with-a-non-numeric-literal
exiting 0 is a CONSEQUENCE of the value mapping, not a separate unaddressed rule, and every surveyed compiler
takes the same shape. Refining it would make COBOL.NET the outlier on a slot the standard hands to the
implementor. No behaviour changed on the strength of this survey.

**FIXED BY:** `ControlFlowBinder.StatusOperand` — the position's own operand builder on the `CountOperand`
model (NOT a fifth `OperandContext` member: the slot admits no arithmetic EXPRESSION at all, so routing it
through the expression spine would repeat the category error) — plus `TerminationStatus.Value` widened to
`BoundOperand`, `NumericRenderer.ExitStatus` over `StatusNum`, and **COBOLNET1704** carrying SR2/SR3/SR4.

⚠ **THE WIDENING SHIPPED WITH THREE HOLES, ALL CLOSED IN THE SAME LANDING** (the cluster-B review fleet found
them before the batch battery ran): the literal arm screened two of the six shapes the ONE §8.3.3 mapping can
produce, so a figurative / ALL / boolean literal compiled clean and CRASHED at run time ([[PB216]]); the SR2
identifier screen read `Pic` guarded by `IsGroup` and rejected a ref-modified display operand and a GROUP-USAGE
NATIONAL group, both of which SR2 admits ([[PB217]]); and SR3 sat inside the literal PARSE ARM, so a
constant-name substituting a non-integer literal skipped it ([[PB216]]).
