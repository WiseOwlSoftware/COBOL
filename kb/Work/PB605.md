# PB605 — OPEN — the sibling PB10 did not sweep

Found 2026-09-05 by the `PB233` implementer while probing the note's stated repro (a UDF miss while evaluating a
CALL argument), which could not be constructed because the argument position rejects the function-identifier
outright. Re-derived on this tree for this note.

## Repro (`--std 2023`)

```cobol
           CALL "CALLEE" USING BY CONTENT FUNCTION SOMEFN(W-X)
               ON EXCEPTION DISPLAY "ON"
           END-CALL
```

→ `error COBOLNET0899: CALL … USING BY CONTENT BYCONTENTFUNCTIONSOMEFN(W-X): an expression operand belongs to
the program-prototype CALL (ISO §14.9.4.2 Format 2), which the AS phrase selects. Format 1's BY CONTENT admits
'{ identifier-2 } …' only.` — two defects in one line: the rejection, and a message that prints the phrase with
its separators dropped.

## The rule

§14.9.4.2 Format 1's BY CONTENT admits `{ identifier-2 }`; §8.4.3.1.2 (`OK §8.4.3.1.2` — the identifier general
format) makes a function-identifier one of the forms an identifier takes; §8.4.3.2.3 SR1 (`cite.py --check
8.4.3.2.3 "receiving operand"` → `OK §8.4.3.2.3 1)`) bars a function-identifier only from a RECEIVING operand. A
BY CONTENT argument is a sending operand (§14.8.2.2 rule 2: "the conformance rules are the same as for a MOVE
statement" with the argument as sender), so Format 1 admits it. `kb/Work/PB10` landed exactly this reasoning for
WRITE/REWRITE/RELEASE … FROM and INITIALIZE … BY (see the header of
`tests/conformance/2023/pb10_function_identifier_sending.cob`); the CALL argument position is the sibling it
did not sweep.

## The mechanism

The COBOLNET0899 arm in the CALL binder's USING-operand screen (`CallBinder`), which classifies any non-plain
operand under BY CONTENT as a Format-2 "expression operand". A function-identifier is an identifier, not an
arithmetic expression; the screen must admit it under Format 1 BY CONTENT (and BY VALUE, where §14.9.4.2 writes
`arithmetic-expression-1` — a function-identifier qualifies there too) and bind it through the same
`UdfBinder.UdfWrapCalls` hoist every other sending position uses. Fix the message's operand rendering in the
same change (it joins the phrase tokens without separators).

## Goldens

A positive at 2002+ (`CALL … USING BY CONTENT FUNCTION F(W)` with a prototype-declared UDF, the callee
displaying what it received, expected values derived from the UDF's definition), the BY VALUE twin, and the
negative for a function-identifier in a RECEIVING position of the same statement (`RETURNING FUNCTION …`,
§8.4.3.2.3 SR1) so the admit/reject boundary is pinned from both sides.
