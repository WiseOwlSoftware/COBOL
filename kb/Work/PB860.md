what §9.1.13.9 describes.

## Code site, on this tree

`src/Cobol.Net.Runtime/IO/FileConnector.cs:567` — `catch (IOException) { s = FileStatusCode.PermanentError; }`,
with three more `PermanentError` mappings at :574, :575, :661-662.

## Shape of the fix

A host-capability classification in `HostFile` that distinguishes a sharing violation from a permanent error —
Windows `ERROR_SHARING_VIOLATION` (0x20) / `ERROR_LOCK_VIOLATION` (0x21), Unix `EWOULDBLOCK`/`EAGAIN` — and
NEVER an `OSPlatform` literal at the call site (kb/Work PB795). The classification is one function; the mapping
table then reads it.

## Sibling sweep the fixer owes

* The CLOSE, READ and WRITE paths have their own `catch (IOException)` clauses with the same blindness — every
  one of them is a status decision.
* `GR-9.1.13.9-2` (the conflicting-mode arm) is the same rule's other leg and is also GAP.
* kb/Work PB833 owns §9.1.15 2)'s missing Linux/macOS lock; this note is about the STATUS a refusal answers,
  not about whether the refusal happens, and the two must not be merged.

## Landed — 2026-09-22 (wave 45, group D)

**Re-probed on the wave-45 worktree's own build** with the new `SharingRefusalStatusTests` and the classification
forced off (a throwaway env-var hook, removed before the checkpoint): **15 × '30'** — all three organizations ×
INPUT/I-O/EXTEND/OUTPUT (12), plus DELETE FILE on all three (3). After the fix: 19/19 green on Windows.

**Fix — one host classification, two statuses.** `HostFile.IsSharingRefusal(IOException)` (FileSupport.cs) is the
ONE place the host's own words are read: Windows `0x80070020`/`0x80070021` (`ERROR_SHARING_VIOLATION` /
`ERROR_LOCK_VIOLATION`), Unix `EWOULDBLOCK` as the raw errno .NET's `flock` refusal carries (11 Linux, 35 BSD) — the
per-host errno is chosen inside HostFile, never at a call site (PB795). `FileConnector.Open` maps it to '61'
(§9.1.13.9 1)) ahead of the '30' residue; `FileStatusCode.ForDeleteFileFailure` maps it to '62' (§9.1.13.9 2)).

**Sibling sweep — the DELETE FILE arm was wrong on BOTH hosts, differently.** Windows refused the delete and
answered '30'; a Unix unlink never consults open handles, so DELETE FILE deleted a file another run unit held open
and answered '00'. `HostFile.IsHeldByAnother` (an exclusive READ request, `FileMode.Open`, nothing created or
truncated) now asks the host before the delete, inside `FileRegistry.DeleteFile`'s RETRY loop beside
`OpenByAnotherConnector` (another run unit CAN close mid-loop). The other `catch (IOException)` sites were read
and are not status decisions about a sharing refusal: `Close` (a flush/persist failure), `KeyedConnector.Reposture`
and `SequentialConnector.OpenReader/OpenWriter` (re-postures of an ALREADY-OPEN connector, restoring the held
posture), `RecordFraming` (header parse probes), `StandardStreams`.

`FileStatusDisciplineTests.DeleteFileFailure_MediumRefusalIs37_OtherIs30` had pinned `0x80070020` as its "other → '30'"
case — a green test holding this defect open; it now pins '62' for it and uses `ERROR_DISK_FULL` for the residue.

**Linux leg:** not run locally (the worktree sandbox refuses `wsl`); the tests assert only measured host facts
(`HostCapability.Sharing.EnforcesExclusiveAccess`, the refusal the test itself provokes), so CI's Linux leg is the
proof the lander must read. Not PB833: this is the STATUS a refusal answers, not whether it happens.
