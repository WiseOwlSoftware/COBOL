# PB2497 — LANDED

Filed by the train-1034b lander from the wave-1034 group B report (PB244, `E:\COBOL-coord\scratch\reports\w1034b-PB244-report.md`,
new defect 2).

**Mechanism.** PB244 split the current-extent capability three ways (`DataItem.CanCompose`: one-way image, carrier, record).
`RecordImageCapable` excludes an OCCURS DEPENDING table whose elements are variable-length groups, because a record read back is
decomposed by a fixed component list (`CobolContiguousLayout.Decompose`) and the record's own length cannot say how many
occurrences it holds (the elements have no fixed width). WRITE, REWRITE, RELEASE, READ, RETURN and a sort or indexed key over such
a record therefore stay loud.

**Open determination (owner-visible).** The READ side needs a count source: the record's extent table when it travelled with the
record (D-FRA (v), `RecordExtents`), else the DEPENDING item's value at the start of the READ (§13.18.38.4 GR8). Which one governs,
and what happens when they disagree, must be decided before the fix; record it in `docs/CONFORMANCE.md`.

**Repro.** `E:\COBOL-coord\scratch\w1034b\p\t2.cob`. **Sites.** `src/Cobol.Net.Compiler/Binding/Model/DataItem.cs#RecordImageCapable`,
`CobolContiguousLayout.Decompose` (runtime).

record and that arrives without extents has no count source; that residue is the determination to record in `docs/CONFORMANCE.md`.

**Design input for the finisher (not decided here).** The record's `CobolContiguousLayout` lists the OCCURS DEPENDING
table's element components at the table's MAXIMUM (`GroupImageCodec.ContiguousLayout`, the `OdoTable` arm). A record
written with N occurrences carries an extent table of `prefix + N × perElement` components, so
`RecordExtents.Describes` (`fixedAt.Count != Count`) refuses it, and the take step cannot place the elements. The
layout can state the table's geometry instead: the first component of occurrence 1, the components and fixed width
per occurrence, and the maximum. `Describes` / `Decompose` / `Position` / `ToFixedForm` then read N from the extent
table's own count, `(Count − prefix) / perElement`, and an OCCURS DEPENDING table needs no other count source while the
extents travel. With no extent table (a fixed-form file, D-FRA (vi), or a record from another description), the
§13.18.38.4 GR8 reading quoted above applies. The DEPENDING item inside the record, before the table (SR22), is a
count source in the received fixed prefix. That residue, and a DEPENDING item outside the record, are the
determination to record in `docs/CONFORMANCE.md`. The carrier side is already in place: `FromVarImage` takes the
`__odo` receiving count and loops to it, and a slice the carrier does not hold is the §14.9.25.4 GR9b excess part.

## Landing (w1045c, 2026-10-08)

**Re-probe.** On base `685b44315`, `E:\COBOL-coord\scratch\w1042c\p\t2.cob` still compiled clean and aborted at `WRITE REC`

**Determination (D-FRA (viii), docs/CONFORMANCE.md §3; the open question above).** A READ / RETURN takes the
occurrence count from three sources, in this order. (1) The record's extent table, when it travelled and describes
the record: the table states the count by the number of components it describes (`OdoTail.CountFrom`). (2) The
maximum, for the fixed form of a file of fixed-length records. (3) Otherwise data-name-1: the record is decomposed at
the maximum (§13.18.38.4 GR8 b, the receiving area), which places a data-name-1 the record holds itself before the
table (§13.18.38.3 SR20), and is then decomposed again at data-name-1's clamped value. A data-name-1 outside the
record keeps its value from the start of the statement (GR8 a). When the extent table and data-name-1 disagree, the
extent table governs, because it describes the characters actually received.

**Fix shape.** `CellOdoTail` became `OdoTail` (Values/), the one geometry of the trailing OCCURS DEPENDING table for
a cell's window and for a record layout. `CobolContiguousLayout(…, OdoTail Odo)` has two arms. With `Comps` = 0
(fixed-image elements) the table is the layout's last component. With `Comps` > 0 the components are listed at the
maximum; `AtCount(n)` gives the record's layout at n occurrences and `Stated` gives the layout at the count the
extent table describes. `Decompose(…, count)`, `StatesCount`, `ExtentsOf/ExtentsFrom` (sliced), `ToFixedForm`,
`MediumImage/MediumExtents` and `Position` all go through it. The generated `FromContiguousImage` returns `bool`
and takes `__odo`; `StorageCell.StoreContiguousAt` does the same for a cell. `PlaceRenderer.WriteVarGroupContiguous`
emits `if (!X.FromContiguousImage(r, e, ff)) X.FromContiguousImage(r, null, ff, <clamped data-name-1>)` for a
group whose ODO table has variable-length elements. `DataItem.RecordImageCapable`, `CanCompose`, the
`CurrentExtentUse` enum and `TierCIsland`'s record arm were deleted, so every consumer asks
`CurrentExtentImageCapable`. **Which arm:** both storage arms, the declared struct (`GroupImageCodec`) and the
cell-backed window (`StorageCell`, an EXTERNAL record), and every record consumer: WRITE, READ, RELEASE / RETURN,
the indexed key, and the fixed form.

**For the next implementer.**
- `src/Cobol.Net.Runtime/Values/CobolContiguousLayout.cs#AtCount/#Stated/#StatesCount`: every public method of a
  `Comps > 0` layout delegates to the layout at a count. Never read `FixedAt` of such a layout as one record's.
- `src/Cobol.Net.Runtime/Values/OdoTail.cs#CountFrom`: the inverse of `CutComponents`. Reuse it; do not divide
  component counts by hand.
- `src/Cobol.Net.Runtime/Control/StorageCell.cs#LayoutOf/#ContiguousExtentsAt`: a tail with `Comps > 0` adds NO
  component. Its components are already among the cell's.
- `src/Cobol.Net.Compiler/CodeGen/DataDivision/GroupImageCodec.cs#RecordOdo`: the one place a declared group's
  layout learns its table. It replaced `OdoTailWidth`.
- `src/Cobol.Net.Compiler/CodeGen/Roslyn/PlaceRenderer.cs#WriteVarGroupContiguous`: the two-pass landing. The trap:
  the count must be read AFTER the first decomposition, or a data-name-1 inside the record is the previous record's.
