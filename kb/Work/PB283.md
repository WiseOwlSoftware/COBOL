## The posture SPLITS, and §5's one-line row hid it

**Item 9, the VALIDATE STATEMENT — already recognized and named; no compiler change needed.**
`CobolParserCore.g4` gates `{facilityWord("VALIDATE")}? validateFacilityStatement`, `StatementBinder` binds it to
`BindUnsupportedFacility(DiagnosticCatalog.ValidateFacilityUnsupported)` = **COBOLNET1580**
`validate-facility-unsupported`, Warning, at 2002/2014/2023, and at `--std 85` VALIDATE stays a user-defined word
(pinned by `tests/conformance/negative/user-word-validate.cob`). It binds to `BoundNop` — accepted-inert.

**Items 1–8 and 10 — the eight data-division elements plus the exception family, which carry 56 of the 74 rows —
have NO surface at all**, and for three of them the diagnostic that does fire names the wrong problem:

- `dataDescriptionClause` has no arm for CLASS, DEFAULT, DESTINATION, INVALID, PRESENT WHEN, VARYING or
  VALIDATE-STATUS. PRESENT WHEN and VARYING exist ONLY in `CobolReportWriter.g4`, in their report-group forms.
- **DESTINATION, VAL-STATUS and VALIDATE-STATUS have no lexer token at all** — they are reserved words only
  (`ReservedWords.Table.cs`) — so writing one yields **COBOLNET0901 "'DESTINATION' is a reserved word"**, which
  tells the user nothing about the declined facility and actively misdirects.
- `valueClause` has no VALID/INVALID phrase, so the Format-5 content-validation entry
  `88 X VALUES 1 THRU 5 IS VALID` is a bare parse error.
- **EC-VALIDATE and all five level-3 names are DECLARED in `ExceptionCatalog` with ZERO setting sites**, so
  `>>TURN EC-VALIDATE CHECKING ON` and `RAISE EC-VALIDATE-CONTENT` compile clean against a facility that does not
  exist. §14.6.13.1.1 licenses *raising* nothing for an unimplemented optional element — but it does **not**
  license silently accepting the NAME. This is the EC-SCREEN shape of [[PB260]], repeated verbatim.

## ⛔ AND THE STATEMENT'S OWN WITNESS IS NOT MEASURED EITHER — the harness cannot express it

The only fixture, `tests/conformance/2023/wave_h_facilities_inert.cob`, deliberately routes 1578/1579/1580 to the
non-failing compile channel and asserts only that the surrounding program runs and prints `COUNT=3/END`. **It
would stay green if COBOLNET1580 were deleted tomorrow.** Across all of `tests/`, COBOLNET1560 appears once, 1578
twice, 1579 once and 1580 zero times — and every one of those is a source COMMENT, not an assertion. The negative
corpus matches `.err` ERROR codes and nothing else, so the entire 1560/1578/1579/1580 recognize-and-warn band has
**no assertion mechanism at all**.

**So fixture (0) is the prerequisite for everything else in this note and for [[PB260]] and [[PB261]] too**: give
the negative corpus a `*> warn-at:` header alongside `reject-at`, or add a compile-diagnostics assertion in
`tests/Cobol.Net.Tests.Conformance` using the existing `EditionHarness.CompileFull(...) → (ok, errors, warnings)`
seam. **Prove it fails once** (`feedback_green_gates_arent_evidence`) — it would be the first assertion in the
repository that the band fires at all.

## ⚠ ONE OBLIGATION THE STAMP MUST NOT BE READ TO RELEASE

`SR-13.18.62.3-9` is *"The words VAL-STATUS and VALIDATE-STATUS are equivalent."* Both words are in the §8.9
reserved-word list **independently of A.4.14**, and RELATION and NONE are context-sensitive words tied to the
VALIDATE-STATUS and DEFAULT clauses. Reserving them is an EDITION-level obligation that survives the decline, and
no inventory row covers it — the `--std 85` leg of fixture 2 is the only thing that would catch a regression
there. "DOCUMENTED-NON-SUPPORT on the equivalence rule" reads like licence to drop the words. It is not.

## Two things deliberately NOT in the 74

- **The §13.18.11 CLASS clause** (5 rows). Its whole content is VALIDATE content-validation, yet **Annex A.4 never
  lists it** — grepped A.4 entire: zero hits for "CLASS clause" and "13.18.11" — and it is the only VALIDATE
  clause with no "obsolete feature" NOTE, while `CONFORMANCE.md` §4 item 3 nonetheless names it a validation
  clause. If it is **not** optional, A.4.1 obliges us to ACCEPT `CLASS IS NUMERIC`, and there is no CLASS arm in
  `dataDescriptionClause`, so we would be rejecting mandatory syntax. That is an open adjudication, not a derived
  row.
- **Five format-scoped rules the predicate shape cannot reach** — `SR-13.18.41.3-1`, `SR-13.18.63.3-36`,
  `SR-13.18.63.3-38`, `SR-13.18.63.3-39`, `GR-13.18.63.4-24`. They are printed under a "FORMAT 2" or "FORMAT 5"
  heading and are text-silent (`GR-13.18.63.4-24` reads, in full, *"General rule 18 applies."*). The catalog does
  not carry the format band, so no sound predicate reaches them; see [[PB284]], which owns the extractor repair.
  They are solely conditioned and they are still blank.

## One defect in the STANDARD, and one in the transcription

A.4.14 **item 9 prints "VALIDATE statement (13.18.64)"** — repeating item 8's VARYING number — when the VALIDATE
statement is §14.9.50. Checked at the source in both the markdown and the canonical PDF: both read 13.18.64, so
this is a defect in the standard, the second instance of the [[PB260]] shape, not a transcription error. The
element is named unambiguously by its text, so the licence holds. Separately, `specs/ISO_COBOL.md`'s index
rekeyed the PDF's page numbers to clauses and got **all six EC-VALIDATE entries wrong** — pointing at §14.9.40
(SORT) and §13.18.57 (the TYPE clause) instead of §14.9.50.4 and §13.18.64.4.
