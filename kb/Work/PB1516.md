## Row `GR-9.1.13.4-2` — PARTIAL (editions 2002,2014,2023 (status '14' has no 1985 counterpart in the repository's edition model; the 2023 text carries no change note for it - E.2 silent))

Rule (cite.py --check 9.1.13.4 "the number of significant digits in the relative record number is larger than the size of the relative key data item described for the file" -> OK §9.1.13.4 2)). RelativeConnector.ReadSequential: after selecting the next slot, if the RRN's digit count exceeds _keyDigits it returns '14', marks the read unsuccessful and invalidates the FPI (§14.9.30.4 GR21 relative rule d). Probe out/probe/iostat-rel: RELATIVE KEY PIC 9, records 1-9 plus slot 10 written through a dynamic connector; the 10th sequential READ -> R10-END=14 (AT END taken, '1' family), 11th READ runs neither branch ('46'). No spec-derived golden pins '14' (search of tests/conformance *.out found none) -> test-needed. Editions: the rule's 2023 text is authoritative; the pre-2002 availability is the repository's constructs model, not derivable from Annex E. || REFUTED: PARTIAL — The '14' check is disabled for any RELATIVE KEY item with no PICTURE. KeyedIoEmitter.EmitRegistration passes digits = file.RelativeKeyItem?.Pic?.Digits ?? 0, and RelativeConnector.ReadSequential treats _keyDigits==0 as 'no RELATIVE KEY clause' (if (_keyDigits > 0 && ...)). A BINARY-CHAR/SHORT/LONG UNSIGNED key is a legal unsigned integer relative key (§12.4.5.13.3 SR2), so a sequential READ of a record whose RRN cannot be held in it reports '00' and stores a truncated RRN in the key. PIC-bearing keys (DISPLAY and COMP) are correct.

## What the fixer owes

Pass the relative key's CAPACITY, not its PICTURE digit count: for a no-PICTURE binary integer the capacity is its type's maximum (BINARY-CHAR UNSIGNED 255, BINARY-SHORT UNSIGNED 65535, …), and 'no RELATIVE KEY clause' must be a separate flag rather than digits == 0. Sweep the WRITE/START/random-READ '24'/'23' arms that read the same _keyDigits. Golden: BINARY-CHAR UNSIGNED key, sequential READ of RRN 256 → '14'.

## Analysis 2026-09-29 (batch 8, not landed)

Reproduced on the pinned build: file W (RELATIVE KEY PIC 9(4), RANDOM) writes records 254-256; file R on the same file, ACCESS SEQUENTIAL, `RELATIVE KEY RK` = `BINARY-CHAR UNSIGNED`; four READs give `00 00 00 10` where the third (RRN 256 > 255) is owed `14` (§9.1.13.4 2)). Cause is wider than the note says: `PicInfo.BinaryItem` gives BINARY-CHAR `Digits` 3, so `KeyedIoEmitter` passes 3 (not 0) and `RelativeConnector` compares `slot.ToString().Length > _keyDigits` — a DIGIT-COUNT test, which cannot express a capacity of 255 (256 also has 3 digits). The fix is a capacity, not a digit count: `PicInfo` needs one integer-capacity answer (BinaryCapacity items: the container range; others 10^Digits-1), `KeyedIoEmitter` passes it, and `CobolFile/FileRegistry/RelativeConnector.RegisterRelative` take a `long relativeKeyMax` (long.MaxValue = no RELATIVE KEY clause) in place of `relativeKeyDigits`. Both `_keyDigits` sites (ReadSequential ~318, sequential WRITE ~388) change. Cost: about 60 test call sites pass a digit count (`4`, `0`) and every one changes with the signature (no shim); the `.g.cs` files under tests/conformance are generated. A golden: the repro above.

## Correction 2026-09-29 (batch 9) — the analysis above is superseded; a capacity fix was built, measured and REVERTED

The premise of this note is wrong on two counts. (1) The check is NOT disabled for a PICTURE-less key: `PicInfo.BinaryItem` gives BINARY-CHAR Digits 3 / SHORT 5 / LONG 10 / DOUBLE 19-20 (documented implementor choice), so `KeyedIoEmitter` passes 3, not 0, and the digit test fires at RRN 1000. (2) The rule the note wants enforced is written in DIGITS, not capacity: §9.1.13.4 2) "the number of significant digits in the relative record number is larger than the size of the relative key data item", §14.9.30.4 GR21 d) the same, and §14.9.51.4 GR29 c) for WRITE -> '24'. RRN 256 has 3 significant digits and the item's size is 3 digits, so `14` is NOT owed at 256; the spec gives a PICTURE-less binary item a RANGE (§13.18.60.4 GR12 table: BINARY-CHAR UNSIGNED 0 <= n < 256), never a digit size, so its digit size is implementor-defined and ours is 3. A capacity implementation (`PicInfo.IntegerCapacity`, `long relativeKeyMax` through `RegisterRelative` — built, 51 test call sites rewritten, repro then printed `00 00 14`) turns 256 into `14`, which no clause states; it was reverted rather than landed. What IS true: RRN 256 read into a BINARY-CHAR UNSIGNED key succeeds and stores 256 into a key that holds 0..255 — a size/truncation question for the MOVE of the RRN into the key item, not the `14`/`24` rule. Next step is an adjudicator re-probe of GR-9.1.13.4-2 against the digit reading (expected CONFORMS), and, if the owner wants the capacity reading, an explicit determination in docs/CONFORMANCE.md first. Left open pending that.
