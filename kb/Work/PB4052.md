# PB4052 — the queue watch requeues a pull request whose CI is still running, and the cancelled run then reads as a bounce

## Sites

- `scripts/orchestrator/queue_facts.py#_required_runs` (called from `queue_facts.py#read`) keeps only the check-runs of the
  REQUIRED contexts (`ruleset.required_contexts`: `ci-gate`). `.github/workflows/build-and-test.yml` job `ci-gate` has
  `needs: [changes, supersede, audits, guard, …, toolchain-cache]`, so GitHub creates no `ci-gate` check-run on the head until
  every other job has ended. While `audits` runs, `PullRequest.checks` is EMPTY, and nothing tells the watch that work is running.
- `scripts/orchestrator/land_lane.py#watch_step`: with no check-run, `running` is empty and `ends` falls back to the attempt's
  `ended` (the enqueue); once `QUEUE_GRACE_MIN` (10) minutes have passed since the ENQUEUE, the read is STALLED, and with no
  check-run there is no run to re-run (`run == 0`), so read 1 goes "straight to read 2's remedy": REQUEUE.
- `scripts/orchestrator/enqueue.py#requeue` closes and reopens the pull request. The reopen fires a new `pull_request` run on the
  same head, and `build-and-test.yml`'s `concurrency:` (`group: ${{ github.workflow }}-${{ github.ref }}`, `cancel-in-progress:
  ${{ github.event_name == 'pull_request' }}`) CANCELS the run already in flight. The requeue never asks whether a run is in
  progress.
- `queue_facts.py#PullRequest.red` / `#CheckRun.failed` then read the cancelled run's `ci-gate` (it runs, reports
  `ci-gate FAILS — audits=cancelled`, conclusion failure) as the newest `ci-gate` check-run on the head until the NEW run's
  `ci-gate` exists, about one audits-duration later. `land_lane.py#watch_step` ends the watch as LEFT ("BOUNCED"), and
  `scripts/prune_worktrees.py`'s lifecycle reads the branch BOUNCED: the enqueue unit's finisher.

## Witness (PR #760, branch `worktree-wf_e06e2377-556-4`, head 12efd4325, 2026-10-29)

| 19:05:22 | `prune_worktrees.py`: "BOUNCED — pull request #760's required check ci-gate FAILED on its head before the merge queue took it (failure, workflow run 40934707576) … ONE finisher fixes the branch" |

The branch has no defect: its local gate was GREEN (run `000002-20261029T184137Z`) and its first CI run was cancelled by the lane,
not failed. `audits` ran 11 min 31 s on this branch (it changes `scripts/orchestrator/`, and the audits job runs every discovered script
self-test); the six other `pull_request` runs between 17:25Z and 19:05Z took 3 to 4.5 min. So any branch whose pre-`ci-gate` work runs longer than
`QUEUE_GRACE_MIN` after the enqueue gets its CI cancelled and restarted, and then reads BOUNCED. `landing-measurements.jsonl`
records it as the first read-1 `requeue` (#760, `not-queued`); earlier stalls (#596) took read 1's `rerun` path because a
check-run existed.

## Consequence

A CI run thrown away (11.5 min here) and the landing delayed by a second full run; the branch reads BOUNCED, so the enqueue
unit dispatches a finisher (an Opus transcript) for a branch with nothing to fix, and the bounce record blames the branch. Had the
watch not ended at LEFT, read 2 would have fired one grace after read 1 and cancelled the second run the same way.

## Direction (not a fix)

ONE notion of "the head's checks' work is still running" that does not depend on the required context's check-run existing:
`queue_facts.read` reads the head commit's workflow runs (or every check-run in the rollup, not only the required ones), and
`watch_step` counts any unresolved one as running and dates "work ended" from the newest of them. `enqueue.requeue` refuses, touching
nothing, while a run on the head is in progress (a close and reopen cancels it). A required check-run whose run was cancelled because a
newer run on the same head superseded it is not red. Pair it with `--self-test` arms (no required check-run but a run in progress is
WATCHING; requeue refuses with a run in progress; a superseded cancelled `ci-gate` is not BOUNCED).

## Recurrence (2026-10-29 afternoon, five pull requests in 45 minutes)

From about 20:15Z every `pull_request` run's `audits` job took about 22 minutes (its "Script self-tests" step: kb/Work PB4072,
`review_lane.py --self-test` waits out two 600 s sleeps on Linux), so EVERY landing outlived the grace and the watch requeued
it. The landing lane's log (PDT): #773 (`564-28`) and #774 (`564-3`) requeued 15:14 and read BOUNCED 15:18; #775 (`564-19`)
requeued 15:23, BOUNCED 15:28; #776 (`tooling-pb4054`) requeued 15:28, BOUNCED 15:33; #777 (`564-18`) requeued 15:53, BOUNCED
15:58. Run 40967509020 (#777): `audits` started 22:39:59Z, still running at the requeue (22:53:57Z), CANCELLED; its `ci-gate`
failed "audits=cancelled" at 22:55:40Z. None of the five had a defect: #773 to #776 entered the queue on the reopen's run and
merged, and the survey called each BOUNCED for one tick.

## Fix (landed, operator 2026-10-29)

- `queue_facts.py#_head_runs` (replaces `_required_runs`) reads every context's newest check-run on the head, ONLY from the
  newest workflow run of each workflow there (`workflowRun{databaseId workflow{databaseId}}` joined the query): a superseded
  run's check-runs are history, so its cancelled `ci-gate` is no red. The required contexts' stay `PullRequest.checks`; the
  others are the new `PullRequest.others`, `head_runs` is both, and each unresolved one carries its job's status. `describe`
  says what still runs ("no required check-run on the head yet; still running: audits").
- `land_lane.py#watch_step` reads `pr.head_runs`: any check still running holds the watch; the grace counts from the newest
  check-run's end; read 1 re-runs the stuck check's run, else any check's (a run that completed), and goes straight to the
  requeue only when the head has no check-run at all.
- `enqueue.py#requeue(repo, number, head, ...)` refuses, touching nothing, while `gh run list --commit <head>` shows a run not
  completed, or when it cannot be read. `WatchEffects.requeue` takes the head.
- Self-test arms: `queue_facts.py` (PR #777's shape: a superseded run's FAILED `ci-gate` is no red, the newer run's jobs are
  `others` with their job status, another workflow's run and an app's suite are read, `describe` names the running job),
  `land_lane.py` 14 (a required check with no check-run while `audits` runs is WATCHING with no remedy; once it ends the grace
  counts from its end and read 1 re-runs its run), `enqueue.py` (the requeue refuses with a run in progress or unreadable runs,
  and checks the runs before the close). `DESIGN-orchestrator-loop.md` §4.9's table says the same.
- Sibling sweep: `enqueue.py#requeue` is the only code that closes or reopens a pull request (`grep -rn '"reopen"' scripts`);
  `PullRequest.red`, `.entering` and `.bounced` read `checks` (the required contexts), now free of superseded runs, so the
  survey's BOUNCED row and the driver-file hold (`enqueue.driver_file_holders`) are corrected by the same read.
