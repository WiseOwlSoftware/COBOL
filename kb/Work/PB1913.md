# PB1913 — LANDED

## Landed (wave 1004, group D)

Re-probed on the wave's own build with the filed shape (a subscript split across a `D` line under WITH DEBUGGING MODE):
the `D` line was dropped as a comment (`A(1` + `+ 2` + `)` read `A(1)`), and the PICTURE twin (`01 X PIC` / `D  X(5)`)
read the next line as the picture string. **The design the note asked for ("emit the marker in PICMODE and SUBSCRIPT as
in the default mode") cannot work as written, and the reason shaped the fix:** the line's text decides the LEXER's own
mode (a `)` that closes the subscript, the string that ends PICMODE), so lexing it before the keep/comment decision
gives a wrong lex for whichever answer the decision turns out to be. The fix therefore keeps the decision where it was
and makes the lex repeatable: PICMODE and SUBSCRIPT skip the line and leave a `DEBUG_LINE_IN_REGION` marker
(`PIC_DEBUG_LINE` / `SUB_DEBUG_LINE`, a virtual token); `DebuggingLineRewriter.Rewrite` returns the FIRST such line whose
unit declares the mode; `Frontend.LexAndParse` blanks its carrier (`WithCarrierBlanked`, same columns and offsets) and lexes
again, until none is left. Only the first per pass, because the tokens after a skipped source line were lexed without it.
The fragment re-parses (`FragmentParse`, `ReparseArgs`) need no unit mode at all: they read a slice of the FINAL text, in
which every remaining carrier is a comment line, so `HideAll` is exactly right (the note's "pass the per-unit decision to
the fragment readers" is unnecessary — the decision is already in the text).
Witnesses: `conformance:85/pb1913_debugging_lines_in_open_regions` (clause: `A(1 + 2)`, `A(W-I + 1)` re-read by the
fragment parser, and a `D` line that IS the picture string) and `…_comment` (no clause: the comment reading of the same
lines), `unit:DebuggingLineRewriterTests`. Before the fix the first golden did not compile (COBOL0307 at the VALUE).
docs: DESIGN-frontend-grammar §1 (the debugging-line paragraph), CONFORMANCE.md's debug-module row.


Filed by the train-1003 lander from wave 1003 group D's report (`w1003d-PB1660-report.md`, new defect 1), found by the
PB1705 implementer while carrying debugging lines through the lexer.

## Finding

**Repro.** At `--std 85`, a program whose SOURCE-COMPUTER paragraph says `WITH DEBUGGING MODE` and whose PROCEDURE
DIVISION splits a subscript across a debugging line:

```
           MOVE A(1
      D    + 2
           ) TO B.
```

The `D` line is source under the clause (ISO §12.3.5.4 GR1 scopes the clause to the unit; owner decision R56/R61 for
the 1985 debug module), so the subscript is `1 + 2`. Today the line is dropped as a comment and the subscript is `1`.
The same holds for a debugging line inside an open PICTURE character-string.

**Code site.** `src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4` — the `PIC_COMMENT` (PICMODE) and `SUB_COMMENT`
(SUBSCRIPT mode) skip rules match the `*>` that begins the DEBUG_LINE carrier, so no `DEBUG_LINE` marker is emitted in
those modes and `src/Cobol.Net.Frontend/Parsing/DebuggingLineRewriter.cs#Rewrite` never sees the line. The comment on
`DEBUG_LINE` in the lexer states the limit.

**Why it was not fixed in PB1705.** The re-lexed fragments (`src/Cobol.Net.Frontend/Parsing/FragmentParse.cs`, and
`IntrinsicBinder.ReparseArgs`) read the text of a SUBSCRIPT region again in their own lexer and today hide every
debugging line (`DebuggingLineRewriter.HideAll`) so the two lexes agree. Keeping the line in the main lex needs the
unit's mode known to both fragment readers too — a change beyond the PB1705 slice.

## What the fixer owes

Emit the marker in PICMODE and SUBSCRIPT as in the default mode, pass the per-unit mode decision to `FragmentParse` and
`ReparseArgs` (or decide before the fragment is cut), and add an 85 golden with a subscript and a PICTURE split by a
`D` line, with and without the clause.
