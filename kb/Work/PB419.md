# PB419 — the resume point the multi-target expansion has nowhere to put

Adjudicated in lane-3 batch b2 (`initialize-statement` part 2, finding INIT-P2-F5), which recorded the
divergence honestly as **NOT REPRODUCED** and its reachability as an owed probe. **That probe was run here, on
HEAD 89044aa0, and it reproduces.** The note upgrades the finding from reasoned to measured.

## 1. The mechanism

`InitializeBinder.Bind` (`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs:64-67`) walks
`ini.dataReferenceList().dataReference()` in parse order and appends **each target's whole expansion into one
flat `actions` list** before the next. `BoundInitialize` (`Binding/Bound/BoundInitialize.cs:17`) carries one
`Actions` list with no target boundary, and `InitializeEmitter.Emit` renders it as one straight-line run
inside one statement site.

`RESUME … NEXT STATEMENT` is realized through `ResumeSignal`, which `DispatchEmitter.EmitRunUseBody`
(`CodeGen/DispatchEmitter.cs:282-296`) converts to a target pc, or to `-1` meaning "normal completion" — which
the `__RunUse` / `__IoCheck` callers turn into falling through **past the verb site**. The verb site is the
only granularity there is. So when a declarative resumes NEXT STATEMENT out of the *first* identifier-1's
expansion, control lands after the whole INITIALIZE and every remaining identifier-1 is skipped.

The standard says the opposite, and says it in a rule written specifically for this case: the resumption point
is the **next implicit INITIALIZE**, because each identifier-1 behaves as a separate INITIALIZE statement.
The RESUME statement's own rule makes room for that explicitly — its resumption point is the end of the
statement that was executing *unless general rules associated with the applicable statement specify
otherwise*, and general rule 3 of the INITIALIZE clause is exactly such a rule.

```
$ python scripts/spec/cite.py --check 14.9.20.4 "If more than one identifier-1 is specified in an INITIALIZE statement, the result of executing this INITIALIZE statement is the same as if a separate INITIALIZE statement had been written for each identifier-1"
OK  §14.9.20.4 3)  (General rules)

$ python scripts/spec/cite.py --check 14.9.20.4 "processing resumes at the next implicit INITIALIZE statement, if any"
OK  §14.9.20.4 3)  (General rules)

$ python scripts/spec/cite.py --check 14.9.33.4 "the implicit CONTINUE statement immediately follows the end of the statement that was executing when control was transferred to the exception processing procedure unless general rules associated with the applicable statement specify otherwise"
OK  §14.9.33.4 2) a)  (General rules)
```

Both sentences of the INITIALIZE general rule resolve to the same rule number, which is correct — they are one
rule. The RESUME rule is what makes the INITIALIZE rule operative rather than decorative, and it is the clause
the adjudication did not cite.

## 3. Expected vs observed — MEASURED on HEAD

The probe the adjudication owed. Two identifier-1 operands; a checked exception raised inside the **first**
target's expansion; a declarative that resumes NEXT STATEMENT; the second target's value read afterwards.
`run/misc/g4_gr3_resume.cob`, compiler at 89044aa0, `--std 2023 --run`:

```cobol
       01 T.
          05 E OCCURS 3 TIMES.
             10 EN PIC 9(3) VALUE 111.
       01 P2  PIC 9(3) VALUE 222.
       01 SUB PIC 9(2) VALUE 9.            *> out of range for a 3-occurrence table
       PROCEDURE DIVISION.
       DECLARATIVES.
       D-SEC SECTION.
           USE AFTER EXCEPTION CONDITION EC-BOUND-SUBSCRIPT.
       D-P.
           DISPLAY "DECL-RAN"
           RESUME AT NEXT STATEMENT.
       END DECLARATIVES.
       MAIN SECTION.
       M.
       >>TURN EC-BOUND-SUBSCRIPT CHECKING ON
           INITIALIZE EN (SUB) P2
           DISPLAY "P2=" P2
```

```
$ cobol g4_gr3_resume.cob --std 2023 --run
exit=0
DECL-RAN
P2=222            ← OBSERVED.  EXPECTED: P2=000
```

The declarative ran, resumed NEXT STATEMENT, and control left the whole INITIALIZE — `P2`, the second
identifier-1, was never initialized and still holds its declared value.

**Control, same program with `SUB` in range so no exception is raised** (`run/misc/g4_gr3_ctrl.cob`):

```
$ cobol g4_gr3_ctrl.cob --std 2023 --run
exit=0
EN1=000 P2=000    ← both targets initialized, in source order
```

So the multi-target expansion itself is correct (general rule 3's *first* sentence, which the pinned run also
measured); what fails is the resumption point, and the control proves `P2=000` is exactly what the second
implicit INITIALIZE produces when it is allowed to run. The two runs differ in one byte of `SUB`.

## 4. The code site and the shape of the repair

* `.../Verbs/InitializeBinder.cs:64-67` `Bind` — the flat per-target append, no marker between targets.
* `.../Binding/Bound/BoundInitialize.cs:17` `BoundInitialize` — one `Actions` list, no target boundary.
* `.../CodeGen/DispatchEmitter.cs:282-296` `EmitRunUseBody` — `ResumeSignal` → target pc, `-1` = fall through
  past the verb site.
* `.../CodeGen/Verbs/InitializeEmitter.cs:20-23` `Emit` — renders `Actions` as one flat run.

**This is a shape question, not a patch (CLAUDE.md rule 5).** The resume protocol addresses statement sites;
the standard says each identifier-1 *is* a statement. The expansion needs a per-identifier-1 boundary the
resume protocol can land on — sub-sites within the bound node, or one bound node per target chained at the
statement level — which is the same structure general rule 3's first sentence already asserts exists. Note
that the same rule shape recurs across the statement family (INITIATE, TERMINATE, VALIDATE, DELETE FILE and
OPEN all have a per-operand resumption rule), so whatever boundary is introduced should be the one those
verbs can reuse rather than an INITIALIZE-only marker.

Pair it with a drift test built on the probe above: it is a two-line source change away from being a golden,
and nothing in the suite currently looks at the post-RESUME state of a multi-target INITIALIZE.

## 5. The sibling sweep the fixer must do

* **Every statement with a per-operand resumption rule.** The INITIATE, TERMINATE, VALIDATE, DELETE FILE and
  OPEN clauses each carry a rule of the same shape ("processing resumes at the next implicit … statement");
  each is presumably bound to one statement site the same way. Measure them with the same probe shape before
  assuming any of them is fine — "nothing reads this" is a probe, not a conclusion.
* **Both resume paths.** `EmitRunUseBody` and `EmitUseMachinery` both convert a resume signal; a boundary that
  only one of them honours is the two-arm defect again.
* **The exception-checking PERFORM's WHEN arm** reaches RESUME NEXT STATEMENT by a different route than a
  declarative; both must land on the same boundary.
* Editions: the RESUME statement is COBOL-2002+, so the second sentence has no COBOL-85 arm even though the
  row's first sentence does.
