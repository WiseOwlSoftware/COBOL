# PB74 — LANDED 2026-08-17 — `COMPUTE X5 = 10 ** 100 ON SIZE ERROR …` under STANDARD-DECIMAL ran NOT ON SIZE ERROR and stored 0

> ⚙ **flags:** wrong-answer, silent · found 2026-08-17 while scoping PB60's SDIDI Dec branch (the
> NUMVAL-F Dec projection of `"1E+40"` lands through this exact store).

**Measured repro** (`--std 2023`, `OPTIONS. ARITHMETIC IS STANDARD-DECIMAL.`, `01 X5 PIC 9(5) VALUE 12345.`):
`COMPUTE X5 = 10 ** 100 ON SIZE ERROR DISPLAY "SE" NOT ON SIZE ERROR DISPLAY "NOSE X5=" X5` prints
`NOSE-100 X5=00000`; `10 ** 40` likewise; `10 ** 30` correctly prints `SE-30`; `10 ** 37` into
`9(5)V99` prints `NOSE-37 Y5=0000000`. The receiver is OVERWRITTEN with 0 where §14.7.5 storing rule 1
requires it unchanged and the SIZE ERROR imperative run.

**The charge:** §14.7.5 case 3 — "if, after radix point alignment and any applicable rounding
specifications, the result of an arithmetic statement is further from zero than permitted for the
associated resultant data item" — the size error condition exists; with the phrase, rule 1: the
resultant items remain unchanged and control goes to the imperative. §8.8.1.5.2 keeps 10¹⁰⁰ inside the
SDIDI's range (adjusted exponent ≤ 6144), so the intermediate is fine — the defect is entirely at the
final transfer.

**Mechanism:** `CobolDec.ToUnscaled(scale, mode)`'s WIDENING arm — "keep only digits a ≤38-digit
store could ever use" — does `sig %= 10^max(0, 38 − shift)` and, when nothing survives, `return 0`.
`CobolNum.TryStore(CobolDec, …)` then capacity-checks that 0, passes it, and stores it; the edited
checked path (`ArithmeticEmitter.StoreArith` → `DecToUnscaled` → `EditTryFormat`) sees the same 0.
The unchecked `Store` deliberately keeps low-order digits (implementor truncation semantics, matching
the Int128 path's `RescaleStoreCap`) — that half is fine; the CHECKED half must see the overflow.
**Fix shape:** one checked projection beside the unchecked one (`ToUnscaledChecked` — throws
`CobolSizeError` EC-SIZE-TRUNCATION when the widened magnitude exceeds the 38-digit carrier, exactly
as `RescaleChecked` does on the Int128 path); `TryStore(CobolDec)` and every checked-path
`DecToUnscaled` emission ride it. Golden: `10 ** 100` / `10 ** 40` / edited-receiver legs + the
NUMVAL-F `"1E+40"` twin, each with SIZE ERROR and an unchanged-receiver proof.

> ✅ **LANDED 2026-08-17 (same session it was found):** `CobolDec.ToUnscaledChecked` (the checked §14.7 final
> transfer — a magnitude past the Int128 carrier raises `CobolSizeError` EC-SIZE-TRUNCATION; the unchecked
> `ToUnscaled` keeps its low-order-digit disposition for MOVE / no-phrase stores), ridden by
> `CobolNum.TryStore(CobolDec)` and by the emitter's checked numeric-edited transfer
> (`RuntimeApi.DecToUnscaledChecked` in `ArithmeticEmitter.StoreArith`'s `Aligned(true)` Dec arm). Sweep: the
> three PROHIBITED raises (`Round34Wide`, `RoundFromRemainder`, `CobolNum.RescaleChecked`) now carry
> EC-SIZE-TRUNCATION (§14.7.4.3 r7 / §11.9.11.2 r3d) instead of the default OVERFLOW — measured wrong via
> EXCEPTION-STATUS before. Measured after: P100/P40/P30/P37/PE100/PF40 all SE with the receivers unchanged,
> ECOV/PROH/INEXACT = EC-SIZE-TRUNCATION. Goldens `pb74_sdidi_store_size_error` (10 rows) +
> `pb74_sdidi_intermediate_prohibited_ec` (3 rows); unit: two PB74 tests in `CobolDecRoundingTests`. Gates:
> Conformance 852/852 (Arithmetic|Corpus|Numeric|Standard|Rounded|Size|Exception|SpecTraceability|Edited) ·
> Unit 43/43 (the two Dec classes) · characterization 33/33. Design: `COBOLNET_NUMERIC_DESIGN.md` D3. DEVLOG 1291.
