# PB3408 — a relative findings path in a stamp reads TORN from another directory

Filed by the operator from PB3381's branch review (R7-3, low, not blocking at round 7; `w1125a-PB3381-report.md`).

**The mechanism (`scripts/orchestrator/review_findings.py`, on main at 49e1c6b79).** `stamp(report, findings_file)`
writes `stamp_line(v, findings_file)`. For a FINDINGS verdict, that line ends with `{findings_file}` exactly as the
caller passed `--findings`, so a relative path is written into the report as a relative path. Since round 6, the branch
survey reads every stamped path (`findings_files`' `also`), resolved against the survey's own working directory.

**The failure.** A survey run from a directory other than the one the stamp was written from finds no file at the
relative path. It reads the file as gone, which is a tear, so it holds that note's branches. Its remedy says to restore
the file, not that the stamped path is relative. This is a hold, never a release. The reviewer checked all 49 stamped paths
then live: all were absolute and present, hence low.

**The fix.** `stamp` writes `findings_file.resolve()` (or refuses a relative path), and the remedy for a stamped path that
is gone names the stamp and the report it is in. The self-test should stamp with a relative path and assert that the
report carries the absolute one.
