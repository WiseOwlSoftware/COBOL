# PB225

**Rows:** `GR-8.8.4.4.4-3`

§8.8.4.4.4's seven FLOATING-POINT class conditions have no binder arm: `IF F IS FLOAT-INFINITY` (and FLOAT-NOT-A-NUMBER/-QUIET/-SIGNALING, IN-ARITHMETIC-RANGE, NEAREST-TO-ZERO, FARTHEST-FROM-ZERO) lexes as an ordinary user word, falls through ConditionBinder.BindComparison's className arm to a DIAGNOSTIC-FREE BoundConditionError, and the program compiles CLEAN then dies at the condition's first evaluation.

Rows: GR-8.8.4.4.4-3 (PARTIAL, state GAP; code-location ConditionBinder.cs#BindComparison; CobolClass.cs#IsInCodedSet; ConditionRenderer.cs).

WHAT THE ROW SAYS (reused, not re-derived): "STILL MISSING — the float class conditions g)–m): FARTHEST-FROM-ZERO / FLOAT-INFINITY / FLOAT-NOT-A-NUMBER(-QUIET/-SIGNALING) / IN-ARITHMETIC-RANGE / NEAREST-TO-ZERO have no binder arm (a loud parse/bind failure, never a wrong answer) — PARTIAL on those alone." Items a) (alphabet-name) landed with PB109; b/c/d (PB64 T5), e (BOOLEAN), f (class-name), n (NUMERIC) are recorded live elsewhere and are NOT this note's scope.

MECHANISM, LOCATED: ConditionBinder.BindComparison's `cmp.className()` arm (:474–:524) is a five-way resolve ending in a diagnostic-free `BoundConditionError` at :524, rendered by ConditionRenderer as `EmitText.LoudValue("bool", …)`. The seven words have no lexer token (CobolLexer.g4), so `className`'s `cobolWord` alternative (CobolExpressions.g4:162–168) swallows them and the UserClasses lookup (:500) cannot match — and ReservedWords.Table.cs reserves all seven at 2014+, so no user CLASS declaration can substitute. ONE mechanism, seven spellings.

REFINEMENT OF THE ROW'S OWN WORDING (measured at the site, this session): the row calls it "a loud parse/bind failure". It is a BIND fall-through with NO diagnostic — the program COMPILES CLEAN and throws NotImplementedCobolFeatureException at the condition's first evaluation. That is PB109's measured posture on the identical arm, and it is why the flag is `crashes`, not `rejects_legal_source`.

RESIDUE / WHAT WOULD CLOSE IT: one `BoundFloatClassCondition(operand, kind, not)` reached from the same arm — the shape PB109 already proved for the coded-set case — with the operand screen riding the existing `CheckClassConditionOperand`, plus goldens over each of the seven spellings and the NOT form. Because there is no lexer token, the arm must key on the word text (or the seven words must become tokens); either way the fix is ONE arm, not seven.

FRAMING CHECK (no licence exists): docs/CONFORMANCE.md §4's documented non-support facilities are MCS, COMMIT/ROLLBACK, VALIDATE and SCREEN only — none covers the class condition; §2 A.3 item 1 CLAIMS the standard floating-point usages, so no DOCUMENTED-NON-SUPPORT reconciliation is available here.

SPEC REFS AS CARRIED BY THE ROW / ITS LINEAGE NOTE (PB109, not re-derived): §8.8.4.4.2 format 1's class list; §8.8.4.4.4 GR3 items g)–m); §8.8.4.4.4 GR1 (zero-length false) and GR2 (NOT); §8.8.4.4.3 SR3 (the operand usage rule).

## Mechanism

src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#BindComparison — the `cmp.className()` arm, :474–:524. The arm resolves, in order: the four keyword classes (`kind` 'N'/'A'/'U'/'L' → BoundClassCondition, :477–486); the §8.8.4.4.3 SR2 LOCALE-alphabet refusal (`ctx.Data.IsLocaleAlphabet`, COBOLNET1669, :492–498 — PB64 T5); a SPECIAL-NAMES user CLASS via `ctx.Data.UserClasses.TryGetValue` (:500–505); and PB109's alphabet-name coded-set arm (`ctx.Data.Alphabets` / `NationalAlphabets` → `BoundCodedSetClassCondition`, :510–522). Everything else reaches `return new BoundConditionError($"class condition '{cls.GetText()}'")` at :524 — NO `Edition.Error` on that path — which `src/Cobol.Net.Compiler/CodeGen/Emit/ConditionRenderer.cs` renders as `EmitText.LoudValue("bool", …)`, i.e. the staged-loud posture PB109 measured (NotImplementedCobolFeatureException at the condition's first evaluation; the program compiles clean). The six/seven float words reach that fall-through because `className : NUMERIC | ALPHABETIC | ALPHABETIC_LOWER | ALPHABETIC_UPPER | cobolWord` (src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4:162–168) and src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4 defines NO token for any of them (measured: zero hits for FLOAT_INFINITY / FLOAT_NOT_A_NUMBER / IN_ARITHMETIC_RANGE / FARTHEST / NEAREST_TO in the lexer grammar), so each arrives as `cobolWord` and takes the UserClasses lookup that can never match — while all seven ARE reserved 2014+ in src/Cobol.Net.Editions/ReservedWords.Table.cs (:186, :200, :202, :203, :204, :231, :287), so a user cannot even declare a SPECIAL-NAMES CLASS by those names to route around it. The reserved-word table's only enforcement site (src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs:130–145) governs `>>DEFINE COBOL-WORDS` alone and never fires here.

### What this note said, and what the compiler does

The body above records a BIND fall-through with no diagnostic — "the program COMPILES CLEAN and throws
NotImplementedCobolFeatureException at the condition's first evaluation". **That is no longer what happens.**
`scratchpad/reg9/seven.py` compiles the same one-line program for each of the seven words over
`01 F1 USAGE FLOAT-LONG.`, at two editions:

```
--std 2023   FLOAT-INFINITY                 rc=65  error COBOLNET0901: 'FLOAT-INFINITY' is a reserved word in
                                                   COBOL-2023 and cannot be used as a user-defined word (ISO §8.9)
             FLOAT-NOT-A-NUMBER             rc=65  COBOLNET0901 (same)
             FLOAT-NOT-A-NUMBER-SIGNALING   rc=65  COBOLNET0901 (same)
             FARTHEST-FROM-ZERO             rc=65  COBOLNET0901 (same)
             IN-ARITHMETIC-RANGE            rc=65  COBOLNET0901 (same)
             NEAREST-TO-ZERO                rc=65  COBOLNET0901 (same)
             FLOAT-NOT-A-NUMBER-QUIET       rc=70  error COBOLNET1639: class condition
                                                   'FLOAT-NOT-A-NUMBER-QUIET': the word names neither an
                                                   alphabet-name nor a class-name declared in the SPECIAL-NAMES
                                                   paragraph … (ISO §8.8.4.4.2; §8.4.2.1)
--std 2002   all seven                      rc=70  COBOLNET1639 (the words are not reserved below 2014, so
                                                   `IF F1 IS <word>` really IS an undeclared class-name there —
                                                   the right answer at that edition, NOT part of this defect)
```

So the harm is **`rejects_legal_source` at 2014 and 2023**, not a crash: legal COBOL is refused at compile
time, and the user is told the word is reserved rather than that the facility is unimplemented. `crashes` is
cleared — nothing reaches evaluation any more.

### The one asymmetry, and it is the fixer's first trap

Six of the seven have a lexer token; FLOAT-NOT-A-NUMBER-QUIET has none, and `CobolLexer.g4:289-291` says so
deliberately, citing this note: *"⚠ FLOAT-NOT-A-NUMBER-QUIET is reserved too but has NO token here: its only
surface is the §8.8.4.4 class condition (kb/Work PB225), Format 15 does not offer it, and a token nothing
reads is a lookup nothing has ever contradicted."* That is why its refusal comes out of a different
diagnostic. `tests/version-matrix/reserved-words.json` carries all seven identically
(`r85:false, r2002:false, r2014:true, r2023:true`), so the TABLE is right and the LEXER is one word short —
the token lands with the fix, not before it (`feedback_a_dead_lookup_is_also_unverified`).

### The fix shape CHANGED under this note, and that is the good news

The body above proposes `BoundFloatClassCondition` reached from `ConditionBinder.BindComparison`'s five-way
resolve. **That arm no longer exists.** [[PB571]] + [[PB590]] + [[PB649]] (train 44, DEVLOG 1630) extracted
§8.8.4.4.2's alternative list — which had been written down FOUR times — into ONE table,
`src/Cobol.Net.Compiler/Binding/ClassConditionModel.cs`, deleted the duplicate `classCondition` grammar rule,
and made EVALUATE name `className`. So each missing alternative is now exactly **one grammar alternative + one
`ClassConditionModel.Alternatives` row + one `ConditionRenderer.RenderClass` arm**, and
`ClassConditionTableDriftTests` fails loudly if any of the three is missed. ⭐ That is why all seven are ONE
note and not seven: the table is what makes them one mechanism. Re-read the landed design before starting —
implementing this against the note's older description would re-introduce a second list.
