# PB3873 — cobc-crash-self-call: cobc 3.2 segfaults on CALL ... USING to a program of the same source that has no USING parameters (cb_check_conformance)

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S1) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\cobc-crash-self-call.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\cobc-crash-self-call\`.

## Summary

cobc 3.2 dies on SIGSEGV ("unknown (signal)", exit 139) while compiling a Format 1 `CALL "name" USING arg` when
`name` is a program already defined in the same compilation unit (the calling program itself, or an earlier program
in the same source file) and that program's PROCEDURE DIVISION header has no USING phrase. The fuzz nights met it
through programs that CALL themselves (11 of 12 witnesses on nights 2-5 crash the same way). The crash is in the
compile-time argument-conformance check, so `-fsyntax-only` crashes too, and it happens under every `-std`
(`cobol2014` and the default dialect were run). A CALL without USING, or to a program with at least one formal
parameter, does not crash. The same counting loop also misreports the argument count when the target has one or more
formal parameters (second program below).

## Minimal test case

Free reference format (`-fformat=free`), 8 lines, `records/cobc-crash-self-call.cob`:

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. SELFCALL.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 WS-A PIC X.
PROCEDURE DIVISION.
    CALL "SELFCALL" USING WS-A
    STOP RUN.
```

The same crash without a self-call (`records/cobc-crash-self-call--other-program.cob`, free format): program `SUB1`
(no USING) followed in the same file by `MAIN1`, whose procedure division is `CALL "SUB1" USING WS-A` / `STOP RUN`.

Same site, wrong count (`records/cobc-crash-self-call--count.cob`, free format): `SUB2` has
`PROCEDURE DIVISION USING LK-A`; `MAIN2` in the same file does `CALL "SUB2" USING WS-A WS-B` (two arguments).

## Environment

- `cobc (GnuCOBOL) 3.2.0`, Ubuntu package `gnucobol3 3.2-4build1`, WSL2 Ubuntu on Windows 11.
- `cobc -std=cobol2014 -fformat=free -x -o m1 m1.cob`
- `cobc -std=cobol2014 -fformat=free -fsyntax-only m1.cob` (same result)
- `cobc -fformat=free -x -o m1d m1.cob` (default dialect: same crash, after the `-Wdialect` warning "CALL to own
  PROGRAM-ID used" and the note "assuming RECURSIVE attribute")

## Observed result

```
unknown (signal)

cobc: aborting compile of m1.cob at line 8 (PROGRAM-ID: SELFCALL)
cobc: Please report this!
Segmentation fault         cobc -std=cobol2014 -fformat=free -x -o m1 m1.cob
```
exit code 139. The other-program variant: identical text at line 13 (PROGRAM-ID: MAIN1), exit 139.

The count variant compiles (exit 0) with `n3.cob:16: warning: expecting up to 1 arguments, but found 3
[-Wrepository-checks]`; the CALL passes two arguments.

Witnesses reproduced (all exit 139, same message): n2-fz01044, n2-fz01046, n2-fz02316, n3-fz00277, n3-fz00278,
n3-fz01964, n3-fz03773, n4-fz00213, n5-fz00194, n5-fz03719. n4-fz03337 no longer reaches the CALL: cobc stops
earlier on `FUNCTION HIGHEST-ALGEBRAIC` of a national item (exit 1), a different matter, not part of this record.

## Expected result (per ISO)

ISO/IEC 1989:2023, all checked with `scripts/spec/cite.py --check`:

- §14.9.4.3 SR 25), under FORMAT 2 only: "The rules for conformance specified in 14.8.2, Parameters and 14.8.3,
  Returning items apply." For Format 1 (this program) no syntax rule relates the arguments to the called program's
  formal parameters.
- §14.9.4.4 GR 3) d): "If the resources are available and the program being called is a COBOL program, the rules for
  conformance specified in 14.8.2, Parameters and 14.8.3, Returning items apply. If a violation of these rules is
  detected, the EC-PROGRAM-ARG-MISMATCH exception condition is set to exist" — for Format 1 the argument count
  (§14.8.2.1: "The number of arguments in the activating element shall be equal to the number of formal parameters in
  the activated element") is a run-time check.
- §14.9.4.4 GR 3) f): "If the program being called is in the active state and that program does not have the
  recursive attribute, the EC-PROGRAM-RECURSIVE-CALL exception condition is set to exist" — the self-call is a
  run-time exception, not a compile-time error.

Edition: the CALL statement with USING exists in every edition; EC-PROGRAM-RECURSIVE-CALL and EC-PROGRAM-ARG-MISMATCH
exist from ISO/IEC 1989:2002, so the rules above apply to 2014 (`-std=cobol2014`). The program is legal source; the
expected compile result is success (a warning about the argument mismatch is the implementor's choice). Whatever the
legality, a compiler crash is a defect: an error, if any, is a diagnostic.

For the count variant: two arguments are passed, so a diagnostic that reports a count should say 2.

Edition as recorded by the adjudicator: 2014. `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Class

Crash (compiler segfault). Count variant: wrong diagnostic text (same loop).

## Our compiler (WiseOwl)

`cobol.exe m1.cob --std 2014 --source-format free -o m1.dll`: compiles, exit 0. `dotnet m1.dll`: "abnormal run-unit
termination: CALL 'SELFCALL': program is already active and has no RECURSIVE attribute (ISO §14.9.4.4 GR3f —
EC-PROGRAM-RECURSIVE-CALL)", exit 1 (GR 3) f), no ON EXCEPTION phrase). The other-program variant compiles and runs,
exit 0.

## Fix site (GnuCOBOL 3.2 source, read observationally)

`cobc/typeck.c`, function `cb_check_conformance` (called from the `call_body` action in `cobc/parser.y` when the
target is a literal, a constant, a prototype or a program that `try_get_program` resolves through
`cb_find_defined_program_by_name`). The first loop (lines 3705-3710) visits arguments only while
`param_num <= program->num_proc_params` and is the only place that sets `last_arg`. With `num_proc_params == 0` it
does not run, `last_arg` stays NULL, and the excess-argument branch (lines 3713-3721) walks `CB_CHAIN (last_arg)` and
reads `CB_VALUE (last_arg)`: a NULL dereference. The same branch starts `num_params` at `param_num` (one past the last
matched parameter) and then adds one per remaining chain element after `last_arg`, which over-counts by one: the
"found 3" for two arguments. A program defined later in the file (for example a contained program) is not yet known to
`cb_find_defined_program_by_name`, so the check is skipped and nothing crashes.

## Draft issue

**Title:** cobc 3.2 segfaults on CALL ... USING to a program of the same source that has no USING parameters (cb_check_conformance)

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu `gnucobol3 3.2-4build1`), Linux x86_64.

Steps: save the program below as `m1.cob` and run `cobc -std=cobol2014 -fformat=free -x -o m1 m1.cob` (also with
`-fsyntax-only`, and with the default dialect).

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. SELFCALL.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 WS-A PIC X.
PROCEDURE DIVISION.
    CALL "SELFCALL" USING WS-A
    STOP RUN.
```

Observed: `unknown (signal)` / `cobc: aborting compile of m1.cob at line 8 (PROGRAM-ID: SELFCALL)` / `cobc: Please
report this!`, exit 139 (SIGSEGV). The same happens for `CALL "SUB1" USING WS-A` when `SUB1` is an earlier program in
the same file whose PROCEDURE DIVISION has no USING phrase.

Expected: the program compiles. ISO/IEC 1989:2023 (and 2014) applies the parameter-conformance rules to a Format 1 CALL
at run time (14.9.4.4 general rule 3d, EC-PROGRAM-ARG-MISMATCH), and a call to an active non-recursive program is the
run-time exception EC-PROGRAM-RECURSIVE-CALL (14.9.4.4 general rule 3f). A warning about the extra argument is fine; a
crash is not.

Cause: in `cobc/typeck.c` `cb_check_conformance`, `last_arg` is only set inside the first loop, which does not run
when the called program has no formal parameters; the "more arguments than parameters" branch then follows
`CB_CHAIN (last_arg)` with `last_arg == NULL`. The same branch also over-counts by one: a call with two arguments to a
program with one parameter warns "expecting up to 1 arguments, but found 3".
