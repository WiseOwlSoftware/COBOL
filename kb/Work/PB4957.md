# PB4957 - a truncated message still delivers a tag from beyond the capacity

**Sites:** `src/WiseOwl.Cobol.Runtime/Messaging/AsyncMessaging.cs` (line 119, `TagOf`), `src/WiseOwl.Cobol.Runtime/Messaging/PeerFrame.cs` (line 16, `MessageBody.Truncated`)

**Report (round-1 review LEAD, low; left for the clerk because AsyncMessaging.cs is not a file the PB4744 finisher changed).** `TagOf` takes the message's first slot whatever position it came from, and `MessageBody.Truncated` cuts the image to the capacity but keeps every slot. So a too-long message received into an elementary message tag sets the tag to a tag that lay beyond the 8 positions D-MCS-LENGTH says identifier-1 receives (docs/CONFORMANCE.md D-MCS-LENGTH: an elementary message tag is an 8-position message whose tag travels as its one slot).

Expected (to be adjudicated, not decided here): `Truncated` drops the slots that start beyond the capacity (or `TagOf` checks the slot's position against the capacity), with a two-process test that sends a message longer than 8 positions to an elementary tag receiver. Sweep `MessageBody.Truncated`'s other readers.
