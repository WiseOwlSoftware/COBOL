# PB3846 — `COMPUTE X = 1 + ALL ZERO` fails with a bare COBOL0001 at every edition

**Sites:** `src/WiseOwl.Cobol.Frontend/Grammar/Core/CobolExpressions.g4#primaryExpression`, `src/WiseOwl.Cobol.Frontend/Parsing/ZeroTokenRewriter.cs#Rewrite`, `src/WiseOwl.Cobol.Frontend/Parsing/ZeroTokenRewriter.cs#WrittenWord`, `src/WiseOwl.Cobol.Compiler/Binding/Procedure/ExpressionBinder.cs#ZeroOperand`, `src/WiseOwl.Cobol.Compiler/Binding/Procedure/ExpressionBinder.cs#BindPrimary`, `src/WiseOwl.Cobol.Compiler/Binding/Procedure/ExpressionBinder.cs#NonNumericInNumericContext`, `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs#RewrittenAllZeroRawText`, `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs#RawValueOperandText` (the grammar rule the note first named, `arithmeticFactor`, does not exist: the arm is `primaryExpression`'s; `ComputeZeroOperand` is unchanged, it already reads through `NonNumericInNumericContext`)

Repro: `E:/COBOL-coord/scratch/mythos/w20261707c/r2/z7.cob`, `COMPUTE X = 1 + ALL ZERO`, a bare COBOL0001 cannot-parse at 85, 2002, 2014 and 2023. PB3830 round 2 made a SOLE `ALL ZERO` right side read through `ExpressionBinder.ComputeZeroOperand` (new in PR 658, not yet on main; the one arithmetic-operand reading, PB1415 gate: accepted at 85, COBOL0902 at 2002+), but the arithmetic factor in the grammar does not admit `ALL ZERO` inside a larger expression, so `ADD ALL ZERO TO X` (COBOL0902) and `COMPUTE X = ALL ZERO` are handled and `1 + ALL ZERO` is not. Spec: §8.3.3.6.3 1) a) (the ALL phrase), PB1415's determination for the 85 edge. Verify each citation with `cite.py --check` before use.

## Acceptance

- `COMPUTE X = 1 + ALL ZERO` compiles at 85 as PB1415 rules and draws COBOL0902 at 2002, 2014 and 2023; golden and refusal in the PB3830 style, plus the operand position sweep (left, right, parenthesised, unary).
- Fix the root cause, never simply making the diagnostic pass; be consistent with ourselves barring an explicit requirement differently.

## Landed (wave 20261720, group B) — the arithmetic zero takes its optional ALL

**Re-probe** (this branch's base `deae52c90`, `E:/COBOL-coord/scratch/w20261720b/probe.py`): `COMPUTE X = 1 + ALL ZERO`,
`ALL ZERO + 1`, `1 + (ALL ZERO)`, `- ALL ZEROS`, `2 * ALL ZERO + 3`, `2 ** ALL ZERO`, `IF X + ALL ZERO = 7`,
`T(ALL ZERO + 1:2)` and `PERFORM VARYING ... BY ALL ZERO + 1` were each a bare COBOL0001 at 85, 2002, 2014 and 2023, and
`(ALL ZERO) + 1` a COBOL2269; the sole forms (`COMPUTE X = ALL ZEROES`, `ADD ALL ZERO TO X`) were already right (85
accepted, COBOL0902 from 2002).

**Mechanism.** Two halves, both on the way in. `ZeroTokenRewriter` decides "arithmetic" by the ZERO's neighbours, and
for `1 + ALL ZERO` the left neighbour is the ALL, so the ZERO stayed figurative; for `ALL ZERO + 1` it was rewritten but
`primaryExpression` had only a bare `ZERO_ARITH` arm, so `ALL ZERO_ARITH` matched nothing. §8.3.3.6.2 Format 1 prints the
figurative as `[ALL] ZERO` (ALL not underlined, an optional word), and §8.8.1.1 admits "the figurative constant ZERO
(ZEROS, ZEROES)" as an arithmetic operand, so the ALL is part of the operand, never its context.

**Fix.** The rewriter reads the left context past a written ALL (`Rewrite`, `AdjacentIndex`); `primaryExpression`'s arm
is `ALL? ZERO_ARITH`; and `ExpressionBinder.ZeroOperand` is now the one numeric reading of the figurative ZERO for both
parse forms (the sole figurative-constant node through `NonNumericInNumericContext`, and the primary through
`BindPrimary`), asking `FigurativeAssociation.GateAllZeroAsNumeric` when ALL was written. `ZeroTokenRewriter.WrittenWord`
gives back the spelling (`ALL ZEROS`) for the message, since the rewritten token's text is "0". **Sibling found by the
sweep:** a level-88 VALUE list whose ALL ZERO is followed by a signed literal (`88 C VALUE ALL ZERO -5`) now parses
through the new arm, and its raw text `ALL0` reached the C# backend (CS0103 'ALL0L'); `DataBinder.RewrittenAllZeroRawText`
reads it as the written figurative, so the VALUE clause's own gate refuses it from 2002 as for `VALUE ALL ZERO`. The
compile-time evaluator already refuses the ZERO_ARITH primary (COBOL1547 / COBOL1619), so `CONSTANT AS 1 + ALL ZERO`
and `>>IF V + ALL ZERO = 1` are refused there, as their bare-ZERO twins are.

**Goldens** (`conformance-suite/cases/8.3.3.6-Figurative-constant-values/`): `pb3846_all_zero_in_expression_85` (ten
legs: right, left, both parenthesised sides, unary, exponent, product, a relation operand, a ref-mod position and the
88 VALUE list), and the 2002-2023 COBOL0902 refusals `pb3846-all-zero-in-expression` and
`pb3846-value-list-all-zero-signed`; unit theories `CobolLexerModeDriftTests.AllZero_InAnArithmeticPosition_IsRewrittenPastTheAll`
and `AllZero_OutsideAnArithmeticPosition_StaysFigurative`. Design: DESIGN-frontend-grammar §7 (the rewriter
paragraph, whose stale "still incomplete" sentence was rewritten); VCR Table 7 row 7.28.
