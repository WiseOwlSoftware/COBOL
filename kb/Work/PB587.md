# PB587 — OPEN — a legal entry that produces no item

Found 2026-09-05 by the `PB485` implementer, which needed exactly this shape as the over-rejection guard for
its entry-format screen (a format-1 entry whose only clause is a VALUE clause looks like a condition-name
entry to a screen that reads the body before the level) and could only register it PENDING. Re-derived on
this tree for this note.

## Repro

```cobol
       01  W  VALUE "AB".
       ...
           DISPLAY W          *> expected: AB
```

`cobol … --std 2023` → the backend fails: `error CS0103: The name 'W' does not exist in the current context`.
The registered witness is `tests/conformance/2023/pb485_value_only_format1.cob` (PROGRAM-ID `PB485P4`), in the
2023 manifest's PENDING list with `.out` = `AB` and the derivation in its header; enable it with the fix.

## The rule

§13.16.3 SR9 (quoted by the PB485 implementer and `cite.py --check`ed there): "The PICTURE clause may be omitted
for an elementary item when an alphanumeric, boolean, or national literal that is not a zero-length literal is
specified in the data-item format of the VALUE clause. A PICTURE clause is implied as follows: a) if the literal
is alphanumeric, 'PICTURE X(length)' …" — with b) and c) for boolean (`PICTURE 1(length)`) and national
(`PICTURE N(length)`). Re-run `python scripts/spec/cite.py --check 13.16.3 "The PICTURE clause may be omitted
for an elementary item when an alphanumeric, boolean, or national literal that is not a zero-length literal is
specified in the data-item format of the VALUE clause"` as the first step of the fix.

## The mechanism

`src/Cobol.Net.Compiler/Binding/DataBinder.cs` `BindEntry`: an entry with no PICTURE clause, no USAGE clause and
no subordinate entries produces no `DataItem` (it is neither an elementary item with a picture nor a group), yet
the entry's name is still known to the procedure division, so references bind to a name the emitter never
declared. The fix is at the one place the entry's PICTURE is derived: when SR9's precondition holds (elementary,
no PICTURE, data-item-format VALUE with a non-zero-length alphanumeric / boolean / national literal), synthesize
the implied `PicInfo` from the literal's category and length before the rest of `BindEntry` runs, so every
downstream consumer sees an ordinary elementary item. A zero-length literal or a numeric literal without a
PICTURE stays what it is today (SR9 does not apply; check what diagnostic that case gets and that it is a named
rejection, not a backend crash — the same shape one clause over).

## Goldens

Positive per literal category (alphanumeric, boolean `B"…"`, national `N"…"`) with `FUNCTION LENGTH` read-outs
deriving the implied picture's length from the literal; the existing PENDING witness moved to `enabled`; a
negative for the zero-length literal and for a numeric literal with no PICTURE, each with the rule that rejects
it cited.
