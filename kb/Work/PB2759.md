**Rule it breaks:** one rule in one place / one mechanism per job (DESIGN-architecture-review §5.2; dimensions.md 4 'one rule written in two places'); §12.4.5.9.4 GR7's two ceilings ('53' run unit, '54' connector) and §9.1.16's 'locked by a given file connector' identity are each one rule

**Scenario:** PhysicalFileTable.LockRecord (92-105) and PreflightNewLock (141-153) each count the connector's locks with the same loop and test the same two ceilings in the same order; every mutating caller (FileRegistry.WriteShared 1452/1459, RewriteShared 1489/1498, PreflightReadLock 1245 then ApplyPostReadLockActions 1264) runs the preflight and then LockRecord, whose returned status is discarded at all four call sites (694, 1264, 1459, 1498), so the ceiling is evaluated twice per lock and LockRecord's own ceiling arm answers nobody. The connector-owner test string.Equals(owner, name, OrdinalIgnoreCase) is spelled at PhysicalFileTable 95, 100, 110, 115, 124, 135, 149 and again at FileRegistry 1261-1262 (RecordLockHeldBeforeRead), and FileRegistry tests 'is this a new lock' itself with st.RecordLocks.ContainsKey (1244, 1487). A change to either rule - making the GR7 maxima an implementor setting (the comments at 69-72 call them 'implementor max'), or keying ownership on the connector rather than its name string - must find every site; a missed one re-creates the two-arm shape (a lock granted past the ceiling, or a self-held lock read as another connector's and answered '51').
