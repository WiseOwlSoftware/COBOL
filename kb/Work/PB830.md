# PB830 — OPEN — a sink kept for two DELETED clauses, never gated to the edition that had them

Filed 2026-09-09 by the registrar (third pass) while re-measuring **PB487's** report item (c)
(`scratchpad/reports/PB487-report.md`), which listed `SOURCE-COMPUTER. IBM-370 WIBBLE WOBBLE.` among the
`genericClause` catch-alls. **It is not one.** Measured on this worktree's own
`dotnet build CobolSharp.sln -c Debug` (exit 0) at `094739b3`, and **re-measured unchanged at `35f86874`**
after train 26 landed — PB487's closure of the data-description catch-all did not reach this mechanism, which
is the point of filing it separately.

## Repro — measured, both paragraphs

```
$ cobol p7_conf.cob    --std 2023 --run     # SOURCE-COMPUTER. IBM-370 WIBBLE WOBBLE.
CONF-GENERIC=[OK ]
$ cobol p7_objcomp.cob --std 2023 --run     # OBJECT-COMPUTER. IBM-370 WIBBLE WOBBLE.
OBJCOMP-GENERIC=[OK ]
```

No diagnostic, no warning, exit 0, program runs.

## The rule

```
$ python scripts/spec/cite.py --check 4.2.2 "An implementation shall provide a warning mechanism that optionally may be invoked by the user at compile time to indicate violations of the general formats and the explicit syntax rules of standard COBOL."
  OK  §4.2.2   (Acceptance of standard language elements)
```

§12.3.5.2's general format is `SOURCE-COMPUTER. [ computer-name-1 [ WITH DEBUGGING MODE ] ] .` and §12.3.6.2's
is the OBJECT-COMPUTER equivalent with its two named clauses. Both are closed; `WIBBLE WOBBLE` is in neither.

## Mechanism — not `genericClause`, a `~DOT` sink

```antlr
// CobolParserCore.g4:420
sourceComputerParagraph
    : SOURCE_COMPUTER DOT ((computerName computerAttributes?)? DOT)?
    ;

// CobolParserCore.g4:497
computerAttributes
    : ({!objectComputerClauseAhead()}? ~DOT)+
    ;
```

`computerAttributes` consumes **every token up to the period**, stopping only where
`objectComputerClauseAhead()` sees one of OBJECT-COMPUTER's two standard clauses. The grammar's own comment at
`:424-432` states the intent plainly and correctly:

> *"`computerAttributes` stays the token SINK for the deleted '85 clauses (MEMORY SIZE, SEGMENT-LIMIT —
> `VisitComputerAttributes`' token scan), reachable only behind a name; it stops at PROGRAM and CHARACTER so the
> two standard clauses are recognized, never swallowed."*

**The intent is right and the gating is missing.** MEMORY SIZE and SEGMENT-LIMIT are X3.23-1985 clauses DELETED
in later editions. A sink for them belongs behind an edition predicate; this one has none, so at `--std 2023`,
`2014` and `2002` the compiler silently absorbs both the deleted clauses AND anything else written in their
place. That is `feedback_four_editions_one_compiler` exactly: the per-edition behavior exists, the **gating
diagnostic** does not.

## ⛔ The finding that matters most — two CONFORMS rows that never tested this

`FMT-12.3.5.2` and `FMT-12.3.6.2` are both `verdict: CONFORMS`, `state: OK` in
`tests/version-matrix/traceability-inventory.json`. `FMT-12.3.5.2`'s row reads:

```
code-location: src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4#sourceComputerParagraph
test-ref:      conformance:2023/pb78_object_computer_optional_name
notes:         kb/Work PB78 (2026-08-18): SOURCE-COMPUTER. [computer-name-1] . — the name is optional …
```

The witness is about the **computer-name being OPTIONAL**. It is a true and useful witness, and it says nothing
whatever about whether the format's TAIL is closed. A green witness answering a different question is
`feedback_a_real_clause_can_answer_a_different_question` and `feedback_green_gates_arent_evidence` in one row —
and because the verdict is CONFORMS, `DefectiveRowCoverageDriftTests` cannot see the rows and no work note
claimed them until this one. `feedback_green_test_can_hold_a_gap_open`: a green that reads as a decision.

**This note deliberately does NOT flip the two verdicts.** A FMT row's verdict is a claim about the WHOLE
general format, and the honest re-verdict needs the same per-format audit PB829 §"the shape of each fix"
prescribes (render the printed page, model what is missing, then close). Flipping on this measurement alone
would trade a false CONFORMS for an unevidenced PARTIAL. **Recommended when the audit is done: PARTIAL, with a
witness that a non-clause word run is DIAGNOSED — not merely that the legal clauses parse.** Recording that
will move GAP by +2; that is the ledger becoming true, not a regression.

## Expected

At `--std 2002/2014/2023`: a diagnostic naming the unrecognized text and §12.3.5.2 / §12.3.6.2 (for MEMORY SIZE
and SEGMENT-LIMIT specifically, the better diagnostic names the clause and says it was deleted after COBOL-85 —
the shape `VersionConformancePass` already uses for other deleted constructs). At `--std 85`: MEMORY SIZE and
SEGMENT-LIMIT accepted as today, arbitrary words still diagnosed.

## Code sites

* `src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4:420` (`sourceComputerParagraph`), `:439`
  (`objectComputerParagraph`, which embeds the same `computerName computerAttributes?` pair before its two
  modelled clauses), and `:497` (`computerAttributes` itself).
* `VisitComputerAttributes`' token scan — the binder-side consumer that already walks these tokens and is
  therefore the natural place for the named diagnostic (it can see exactly what was absorbed).
* The edition gate belongs with the other deleted-construct gates in `VersionConformancePass`
  (`ParseArm.VisitSourceComputerParagraph` / `VisitObjectComputerParagraph` — the latter already exists for
  PB78's `computer-name-optional-2002` recognition gate, so the arm is written and only the predicate is new).

## Relationship to PB829

`kb/Work/PB829` is the `genericClause` catch-all family (six sites, seven general formats). This is a different
mechanism — a `~DOT` sink with a documented purpose — and a different harm profile, because its two rows are
already claimed CONFORMS. They are siblings under one heading ("an alternative that matches an unbounded token
run inside a closed general format") and should be fixed in the same campaign, not merged into one note.
