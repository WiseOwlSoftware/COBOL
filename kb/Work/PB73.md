# PB73 — LANDED 2026-08-18 — Two Table-16/ref-mod derivations left open by the PB72 landing, both adjudicated and landed

**Adjudication 1 (2026-08-18) — YES, a NUMERIC-typed function is Table 16's Noninteger sender.** §8.4.3.2.4 GR1: an
intrinsic's temporary item has "the description and category specified by the definition of that intrinsic function
in Clause 15"; §15.2 item 5 gives an INTEGER function "an operational sign and no digits to the right of the decimal
point" and item 4 gives a NUMERIC function only "an operational sign" — the type is a per-function (per-call, for
the twenty argument-dependent rows) STATIC classification, and §8.4.3.2.3 SR11 states the governing principle for
the integer-operand positions: "A numeric function shall not be specified where an integer operand is required, even
though a particular reference of the numeric function might yield an integer value." Table 16 splits the numeric ROW
on exactly that classification, so a numeric function is the Noninteger row (moves only to numeric / numeric-edited)
and an integer function the Integer row (alphanumeric and national receivers legal — item 92's `MOVE FUNCTION
ORD("A") TO PIC X(10)` → 66 stands). §15.4.1's native latitude covers the temporary's REPRESENTATION, not its §15.2
type. Landed: `MoveBinder`'s intrinsic-sender arm sets `IsNonInteger` from the ONE `IntrinsicResultType.IsIntegerOperand`
reader; strict → COBOLNET0819, `--permissive` → a warning and the former admission (the item-92 literal text). GnuCOBOL
(a runtime `cob_move` for any intrinsic source, no static Table-16 screen) accepts the move as an extension — the
permissive axis is where that leniency lives. Recorded on CONFORMANCE.md item 92.

**Adjudication 2 (2026-08-18) — NO: GR2 does NOT make a display-form boolean's ref-mod view alphanumeric — and the same
reading REVERSES PB72's alphabetic erasure.** §8.4.3.3.4 has two separate rules: GR2/GR3 ("operated upon for purposes of
reference modification as if it were redefined as a data item of class and category alphanumeric / national of the same
size") govern the OPERATION — the positions counted — and GR6 governs the RESULT: "the same class, category, and usage as
that DEFINED for identifier-1, except that" an EXHAUSTIVE list — alphanumeric-edited → alphanumeric, national-edited →
national, numeric / numeric-edited → alphanumeric or national. That list names neither boolean nor alphabetic; had GR2
already made every display-form non-alphanumeric item alphanumeric, every entry in it would be redundant. The COBOL-85
lineage settles the structure: 85's operated-as-alphanumeric rule listed "numeric, numeric edited, alphanumeric edited or
alphabetic" while its class/category rule listed only the first three (IBM's Language Reference still carries both
sentences), so an alphabetic slice has always been alphabetic. GR1 gives "a boolean position" to a boolean item in either
form (GR5a: character positions unless the usage is bit) — the asymmetry the note weighed is the BIT form's positions, not
a category rewrite. Consequences, all landed: `RefModPlace.CategoryOf` keeps boolean (unchanged code — the adjudication is
recorded in its NOTE); `Table16Operand.Of(Place)` carries the ALPHABETIC rider through a view again, so `MOVE A-ITEM(1:2)
TO a-boolean` (PB72's admitted RA leg — letters into a boolean item) and `MOVE A-ITEM(1:2) TO PIC 9` are Table 16 "No"
cells like their unsliced twins; `INTEGER-OF-BOOLEAN(BITS(1:6))` over a display-form item is legal (class boolean —
golden `pb19_argument_class_batch5` had pinned it, and would have gone red under the other reading); GnuCOBOL's
any-slice-is-alphanumeric reading is the `--permissive` leniency (a warning) beside the numeric-function text admission
(`Table16Operand.Lenient`). PB72's note carries the correction.

**1. Does a NONINTEGER-scaled intrinsic result fall in Table 16's Noninteger row as a MOVE sender?**
`MOVE FUNCTION SQRT(2) TO PIC X` is admitted today (the computed-sender arm carries
`IsNonInteger: false` deliberately — MoveBinder's comment names this note). §15.4 places a returned
value in "a temporary elementary data item"; if that item's description has a nonzero scale, SR10's
Noninteger × Alphanumeric "No" cell would refuse the move — but §15.4.1 makes the temporary's
characteristics implementor-defined under native arithmetic, and the item-92 function-as-text
determination (CONFORMANCE.md) documents rendering a function result as text in its literal form,
which reads as a deliberate admission. Deciding "refuse" flips item 92's examples; deciding "admit"
should be RECORDED on item 92 as the determination's Table-16 consequence. Survey GnuCOBOL/IBM before
deciding (follow-GnuCOBOL on split latitude).

**2. Does §8.4.3.3.4 GR2 make a ref-mod view over a DISPLAY-FORM boolean item alphanumeric?**
GR2 redefines a usage-DISPLAY item whose category is "other than alphanumeric" as class-and-category
alphanumeric for reference modification; a PIC 1 (no USAGE BIT) item is usage display, category
boolean. The landed `RefModPlace.CategoryOf` keeps the view BOOLEAN per GR6's base case (the PB20
reading — correct for the usage-BIT view under GR5a in every reading). The GR2-feeds-GR6 derivation
(GR1 + SR5's closed class lists) that the PB72 landing applied to ALPHABETIC-ness would make the
display-form boolean view alphanumeric too. Observability is narrow (Table-16 boolean cells and class
conditions); the adjudication should re-derive GR2/GR6 for the boolean case and either overturn the
CategoryOf arm with a golden or record why boolean is distinguishable (GR1 names boolean POSITIONS
explicitly, which alphabetic never gets — a genuine asymmetry the eventual ruling must weigh).
