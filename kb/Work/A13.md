# A13 — THE BATTERY IS RUN SERIALLY, AND ITS LARGEST LEG MAY BE SINGLE-THREADED (owner-raised 2026-08-03, restating a 

- THE BATTERY IS RUN SERIALLY, AND ITS LARGEST LEG MAY BE SINGLE-THREADED (owner-raised 2026-08-03, restating a standing directive)
- ⛔ **The owner's standing requirement is that tests run as CONCURRENTLY as correctness allows, and that a commit does not re-run cases no change can reach.** Two distinct wastes, one measured and one not. **(a) THE LEGS WERE RUN ONE AFTER ANOTHER BY HAND** — Conformance (~14 min) → Unit (~2 min) → characterization → guard → differential — because plan §0's caution "run the long legs ONE AT A TIME" was being read as "never overlap anything". **§0's actual hazard is narrower and is stated there**: a leg that REBUILDS must not overlap a `--no-build` leg, because it swaps assemblies mid-run (that is how a Conformance run once produced no verdict at all). Three independent `--no-build` test assemblies cannot do that to each other. **(b) ⭐ MEASURED 2026-08-03, AND IT IS THE BIGGER ONE BY FAR.** xUnit **2.9.2** parallelizes at TEST-COLLECTION granularity and by default each test CLASS is one collection, so a class's tests run **SERIALLY ON ONE THREAD**. Measured with `python scripts/profile-test-parallelism.py <run.trx>` over the trx `scripts/battery.sh` already emits, so the profile costs nothing extra: **the greenfield UNIT assembly ran 3,634 tests across 63 classes in 210 s wall for 279 s of total test time — an average concurrency of 1.3× on a 32-core box.** And it is ONE class: **`StorageFormEquivalenceTests` is 6 tests totalling 210 s** — the entire wall clock of the leg sits in a single collection while 31 cores idle. Splitting that one class into six would cut the Unit leg from ~210 s to ~35 s. ⭐ **AND THE CONFORMANCE ASSEMBLY — the ~13-minute pole of the whole battery — IS WORSE: 4,180 tests across 109 classes in 783 s wall for 2,583 s of test time, 3.3× on 32 cores.** ⛔ **`VersionMatrixTests` is 2,015 tests running SERIALLY for 780.2 s — i.e. essentially the ENTIRE 783 s leg is one class on one thread.** `NistDifferentialTests` is next at 349 tests / 317.3 s, then `CorpusRunnerTests` at 412 / 78.2 s. ⚠ **I had named `NistDifferentialTests` as "the obvious suspect" before measuring, and it is the SECOND one, not the first** — the arithmetic was plausible and wrong, which is exactly why this register requires the measurement. **THE WORK, when it is scheduled:** split those three classes into multiple collections (xUnit v2's only lever — either genuine class splits or `[Collection]` attributes assigning theory partitions to distinct collections). Bounded by the next-largest class each time, the Conformance leg should fall from ~783 s toward ~320 s and then ~80 s; the Unit leg from ~210 s to ~35 s. **This is deliberately NOT done in the instrument wave** — it is a test-organisation refactor with its own re-baselining risk and deserves its own change set and its own before/after profile.

- tail -N` into a `&&` chain. (b) the measured per-class duration profile of the Conformance leg, then a decision: split the dominant theory classes into separate collections (the only lever xUnit v2 offers) or move to xUnit v3. **(c) TWO FURTHER SERIAL COSTS FOUND WHILE MEASURING, both deferred DELIBERATELY rather than added late to an already-large change set:** ① the NIST leg is **throughput-bound on `dotnet` cold-start** — the compile phase alone is ~150 s of a ~600 s leg and observed effective concurrency was ~7 of 32 lanes, so the real lever is a **persistent run/compile host**, not more parallelism (this is why the 40→9 grouping bought no time; see A12d). ② both guards' baseline-cleanliness sweep spawns **~1,100 subprocesses** (365 goldens × 3 greps) for what is one `awk` pass; on Windows that is a minute per gate, paid on every comprehensive run. Neither is hard; both want a verified before/after diff rather than a late edit.
