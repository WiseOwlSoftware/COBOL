# A13 — HALF — the battery is run serially, and its largest leg WAS single-threaded

- THE BATTERY IS RUN SERIALLY, AND ITS LARGEST LEG MAY BE SINGLE-THREADED (owner-raised 2026-08-03, restating a standing directive)
- ⛔ **The owner's standing requirement is that tests run as CONCURRENTLY as correctness allows, and that a commit does not re-run cases no change can reach.** Two distinct wastes, one measured and one not. **(a) THE LEGS WERE RUN ONE AFTER ANOTHER BY HAND** — Conformance (~14 min) → Unit (~2 min) → characterization → guard → differential — because plan §0's caution "run the long legs ONE AT A TIME" was being read as "never overlap anything". **§0's actual hazard is narrower and is stated there**: a leg that REBUILDS must not overlap a `--no-build` leg, because it swaps assemblies mid-run (that is how a Conformance run once produced no verdict at all). Three independent `--no-build` test assemblies cannot do that to each other. **(b) ⭐ MEASURED 2026-08-03, AND IT IS THE BIGGER ONE BY FAR.** xUnit **2.9.2** parallelizes at TEST-COLLECTION granularity and by default each test CLASS is one collection, so a class's tests run **SERIALLY ON ONE THREAD**. Measured with `python scripts/profile-test-parallelism.py <run.trx>` over the trx `scripts/battery.sh` already emits, so the profile costs nothing extra: **the greenfield UNIT assembly ran 3,634 tests across 63 classes in 210 s wall for 279 s of total test time — an average concurrency of 1.3× on a 32-core box.** And it is ONE class: **`StorageFormEquivalenceTests` is 6 tests totalling 210 s** — the entire wall clock of the leg sits in a single collection while 31 cores idle. ⭐ **AND THE CONFORMANCE ASSEMBLY — the ~13-minute pole of the whole battery — IS WORSE: 4,180 tests across 109 classes in 783 s wall for 2,583 s of test time, 3.3× on 32 cores.** ⛔ **`VersionMatrixTests` is 2,015 tests running SERIALLY for 780.2 s — i.e. essentially the ENTIRE 783 s leg is one class on one thread.** `NistDifferentialTests` is next at 349 tests / 317.3 s, then `CorpusRunnerTests` at 412 / 78.2 s. ⚠ **I had named `NistDifferentialTests` as "the obvious suspect" before measuring, and it is the SECOND one, not the first** — the arithmetic was plausible and wrong, which is exactly why this register requires the measurement. **THE WORK, when it is scheduled:** split those three classes into multiple collections (xUnit v2's only lever — either genuine class splits or `[Collection]` attributes assigning theory partitions to distinct collections). **This is deliberately NOT done in the instrument wave** — it is a test-organisation refactor with its own re-baselining risk and deserves its own change set and its own before/after profile.

## (b) DONE 2026-09-02 — the split landed, the TAIL is gone, and the predicted 10× did NOT arrive

**The mechanism** is `tests/_shared/TestPartitioning.cs` + `TestPartitionAudit`, designed for the NEXT case rather
than these four: a theory-heavy class becomes an abstract generic base `Family<TSlot>` holding the test bodies
ONCE, its `[MemberData]` sources slice the full row set `index % Partitions`, and each partition is a one-line
`sealed class Family_P3 : FamilyBase<Slot3>;` that xUnit schedules as its own collection. It rests on static
members of a CLOSED generic type being per-type-argument — **proved with a standalone probe on xunit 2.9.2 /
runner 2.8.2 BEFORE any real class was touched** (3 partitions over 9 rows → 9 tests, 3 per partition, each
asserting its own slot; open-type resolution would have given 27 tests and 18 failures). Design: DESIGN-test-build-ci §3.11.

**⛔ THE TAIL IS GONE AND THE PREDICTION WAS STILL WRONG — say so.** This note predicted the Conformance leg would
fall "toward ~320 s and then ~80 s". It fell to **600 s**. The split did exactly what it was designed to do —
collection concurrency **2.7× → 17.4×**, and all twelve version-matrix partitions now *span the whole run
together* instead of one class owning it while the others idle, which is the definition of a balanced leg with no
tail left to cut. The wall barely moved because **the premise was wrong**: `sum-of-test-time ÷ wall` measures
COLLECTION concurrency, not CORE utilisation, and the 31 "idle" cores were never idle — a single COBOL.NET
compile is internally parallel (Roslyn `Emit`) and a NIST row spawns a `dotnet` child that is too. The proof is in
the after-profile itself: the SAME work now reports **10469 s of test time instead of 1948 s (5.4×)**, i.e. every
partition's *elapsed* time inflated because the extra collections found contention, not idle silicon. At 17.4×
(Conformance) + 6.5× (Unit) ≈ 24 concurrent threads on **24 physical cores**, the box is saturated.

**WHAT REMAINS, and why it is not more partitioning.** The class-split lever is EXHAUSTED — a thirteenth partition
has nowhere to run. The leg is now bounded by the WORK, which is the lever **(c)① above already names**: a
persistent compile/run host to amortise `dotnet` cold-start, measured at ~150 s of a ~600 s leg and the same
reason the guard's 40→9 regrouping bought nothing. Secondary: `maxParallelThreads`/GC tuning, unmeasured. This
note stays **half** because its stated acceptance bar — no single collection above ~90 s — is measurably not met
and cannot be met by this lever, not because the split is unfinished.

**The invariant is gated, and the gate was proved failing.** A partitioned family FAILS OPEN: delete one partition
class and its rows are simply never run, with a green leg and a plausible test count. `TestPartitionAudit`
(`TestPartitionCoverageDriftTests`, one per assembly) discovers every family BY SHAPE — no registration to forget
— and checks four things: an empty row source, slot indices ≠ {0…Partitions−1}, an empty partition over a
non-empty source, and union ≠ source as a multiset. ⭐ **It went RED on its first real run before any deliberate
break** — Roslyn emits a nested `<>O` delegate-cache class inside a generic type that caches a lambda, and a
nested type inherits the enclosing generic parameter *with its constraints*, so every family produced a phantom
family; the discovery filter now excludes compiler-generated and nested types on principle. Both structural checks
were then fired deliberately (a partition class commented out → the slot-set violation plus "87 row(s) NEVER RUN"
naming the exact dropped rows; a slice count desynced from the const → `Slice`'s own range guard throws first).

**⛔ AND IT FOUND A LIVE CI DEFECT, WHICH IS THE REASON THIS COULD NOT HAVE BEEN A QUIET REFACTOR.** A partition
class is `VersionMatrixTests_P0`, so `~VersionMatrixTests` still selects it and `!~VersionMatrixTests` still
excludes it — but a `Class.Method` filter can never match, and **vstest answers a filter matching nothing with a
SILENT GREEN**. Two CI filters were keyed that way: the three continuity shards, and the INV-1-STRONG job
(`~NistDifferentialTests.NistProgram_MatchesGolden`), which has **no population guard** and would have gone on
reporting success over ZERO goldens. Both are now keyed on the method name alone, which is unique in the tree and
immune to the next re-partition. CI's shard-population check was re-run locally against the split tree and still
partitions exactly: **349+349+349+1080+1354+1761 = 5242 = discovered**.
