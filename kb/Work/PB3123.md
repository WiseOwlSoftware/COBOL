# PB3123 — the DEVLOG number is stamped before GitHub orders the merge queue

> flags: process-only

Source: coordinator measurement 2026-10-13. Grep of kb/Work found no open owner: PB3025 (landed) says `enqueue.py` stamps "so number order is enqueue order", which is the assumption this note shows false at the queue.

**Measured 2026-10-13:**
- `enqueue.py` stamped worktree-wf_76dbe266-f46-3 as Entry 1990 (23:07 PDT) and worktree-wf_787860dd-104-11 as Entry 1991 (23:08 PDT). It enabled auto-merge on PR #25 at 06:11:22Z and PR #26 at 06:11:26Z (GitHub timeline `auto_merge_enabled`).
- Both PRs show `added_to_merge_queue` at the same second, 06:13:25Z (after their own pull_request checks), and GitHub placed #26 first: merge-group refs `gh-readonly-queue/main/pr-26-1a904f19...` and `pr-25-53788e78...` (#25's group built on #26's).
- #25's merge-group run 38355538654 failed the audits job's step "DEVLOG — the landing carries exactly one new, stamped entry file (devlog.py check)": "devlog check: DEVLOG/1990-pb1616-...md: number 1990 is not above the base's newest entry 1991 (a stale number after a rebase): re-stamp it". GitHub removed #25 from the queue at 06:30:32Z (failed_checks). The same run also failed `ArchOracleDriftTests.TheRecordedBaseline_IsOneWellFormedManifest` (two manifests); that half is PB3107's.
- 2026-10-13, second instance: PR #31 (worktree-wf_787860dd-104-3, PB3109) carried stamped entry 1994; #29 (entry 1995) and #30 (entry 1996) merged ahead of it at 07:12:00Z; its merge-group run 38360587401 (07:06:15Z) failed ONLY the audits job's step 'DEVLOG — the landing carries exactly one new, stamped entry file (devlog.py check)' (=== DEVLOG CHECK: REFUSED ===), and GitHub removed it at 07:19:53Z (failed_checks). The enqueue unit re-armed it with no branch commit (land_lane.py rearm); enqueue.py re-stamped it as 1998 and it merged at 07:34:05Z. Cost: one extra merge-group cycle, about 28 minutes. The same run passed the conformance legs with one arch-oracle manifest.

**Mechanism:** the queue order is decided by GitHub when each PR's checks complete, not by `enqueue.py`. `devlog.py stamp` allocates the number from `alloc.py` before the PR exists, and `devlog.py check` in the merge_group run (`MG_BASE`) requires the number above the base's newest. Any two landings reaching the queue close together bounce the lower-numbered one whenever GitHub orders it second; each bounce costs a finisher, a review round and a full CI run.

**Code sites:** `scripts/devlog.py` (`stamp`, `check`, `unstamp_overtaken`); `scripts/orchestrator/enqueue.py` (the queue step); the merge_group DEVLOG step in `.github/workflows`.

**Fix shapes for the implementer to decide (none picked here):** number at the moment of queue entry under one lock; or serialize enabling auto-merge so a PR is enabled only after the previous one shows `added_to_merge_queue`; or a check rule that admits a unique number below the base's newest when it was allocated before the base's entry.

## Landed (wave 1071 group X, with PB3107)

**Re-probe (base 3b1261dfe).** `gh run view 38360587401 --log-failed`: `devlog check: DEVLOG/1994-pb3109-….md: number
1994 is not above the base's newest entry 1996`; the base held 1996 before PR 30 reached main, so a merge group's
`base_sha` is the head of the group queued ahead of it. A new `devlog.py --self-test` arm built the stacked trees as
the queue does (a merge commit of each branch onto the group ahead) and failed on the old rule with that same message.

**The decision (DESIGN-test-build-ci.md §3.17.2 step 4 and DESIGN-test-build-ci.md §3.17.4).** Of the note's three shapes: numbering at queue
entry is impossible (a pull request's content is fixed before GitHub orders the queue); serializing auto-merge was
rejected because a bounced pull request re-enters behind later-stamped ones. The rule changed instead: number order
is STAMP order. `devlog.py check` holds a new entry above every entry of the tree it was STAMPED on (the first parent
of the commit in base..rev that added its file, read with renames off: `stamp_floor`, through `range_check`, the one
committed-range entry point) and unique on the landing's tree (`lint`), never above the group's base. A stamped entry
keeps its number for good, so `unstamp_overtaken` (its only job was the old rule) is deleted and `enqueue.py`'s
`_stamp` stamps only a pending entry. Self-test 44/44: both queue orders pass; a twin number across two queued branches
and a hand number below its own stamp tree are refused.

**For the next implementer.**
- `scripts/devlog.py#range_check` is the one committed-range entry point (run_check and the self-test use it);
  `stamp_floor` finds the OLDEST commit in base..rev adding a file of the entry's number (renames off, so a retitle
  keeps the stamp's floor). `check(..., stamped_on)` falls back to the base's newest only for a pure-tree caller.
- The trap: a merge group's `base_sha` is the head of the group ahead of it, not main; any rule "above the base" is
  a rule about queue order. Build stacked trees with merge commits (`devlog.py --self-test`'s `group()`) to test one.
- `scripts/orchestrator/enqueue.py#_stamp` stamps only a pending entry; there is no re-stamp.
