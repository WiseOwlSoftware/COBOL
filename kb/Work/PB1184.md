# PB1184 — OPEN

## The rule (every citation re-run by the registrar through `cite.py --check`)

> 2) If the data item referenced by identifier-1 is a zero-length item, execution of the UNSTRING statement terminates immediately.

`python scripts/spec/cite.py --check 14.9.48.4 "…"` → `OK  §14.9.48.4 2)  (General rules)`

## Finding — `unstring-statement-p2` (wrong-answer; rows `GR-14.9.48.4-2`, `GR-14.9.48.4-15`)

**Mechanism.** UNSTRING has no zero-length-sender termination: EmitUnstring's initiation range test `if (ptr < 1 || ptr > src.Length) ovf = true` runs unconditionally (even with no POINTER phrase, ptr = 1), so a zero-length identifier-1 is reported as the GR15 a) overflow instead of terminating immediately per GR2 - ON OVERFLOW runs and, under >>TURN, EC-OVERFLOW-UNSTRING is set to exist.

**Repro.** 01 WS-D PIC X DYNAMIC LENGTH. 01 A1 PIC X(4) VALUE "1111". ... MOVE "" TO WS-D  UNSTRING WS-D DELIMITED BY "," INTO A1 ON OVERFLOW DISPLAY "OVF" NOT ON OVERFLOW DISPLAY "NOVF" END-UNSTRING  (also with WITH POINTER P = 1 TALLYING IN T). Pinned cobol.exe --std 2023 and --std 2014 print OVF in both forms (probe p1, out/probe/unstring-p2).

**Expected from the spec.** §14.9.48.4 GR2: 'If the data item referenced by identifier-1 is a zero-length item, execution of the UNSTRING statement terminates immediately.' No overflow condition exists (GR15 a) is stated over identifier-7's value, which does not exist without a POINTER phrase, and GR2 ends execution before any GR15 test), so OVF must not be displayed and EC-OVERFLOW-UNSTRING must not be set; A1, P, T unchanged (already correct). Reading question for the fix (record it in CONFORMANCE.md): 'terminates immediately' also bypasses GR17's NOT ON OVERFLOW transfer, which is stated 'after completion of the transfer of data according to the other general rules' - the natural reading is that neither imperative runs.

**Observed / reasoning.** Observed 'GR2 OVF' / 'GR2B OVF'. Code: src/Cobol.Net.Compiler/CodeGen/Verbs/StringEmitter.cs EmitUnstring emits `if (__unsPtr < 1 || __unsPtr > __unsSrc.Length) __unsOvf = true;` with no preceding zero-length check and no gating on s.Pointer; the runtime kernel UnstringExtract is never reached. Sibling to sweep: STRING (§14.9.43.4) has its own zero-length provisions - check the sibling arm.

**Code site.** src/Cobol.Net.Compiler/CodeGen/Verbs/StringEmitter.cs#EmitUnstring (the GR15a initiation block, line ~117)

## What the fixer owes

Emit the GR2 zero-length test ahead of the GR15 a) initiation block (StringEmitter.EmitUnstring ~117) and gate GR15 a) on the POINTER phrase. Record in CONFORMANCE.md the reading that 'terminates immediately' also bypasses GR17's NOT ON OVERFLOW (neither imperative runs). Sibling: STRING's own zero-length provisions (§14.9.43.4). Golden p1 at 2014 (DYNAMIC LENGTH sender).
