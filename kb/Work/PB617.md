# PB617 — LANDED (wave 70 A) — the additive walk sees items, not literals

Found 2026-09-05 by the `PB248` implementer (report §"New defects" B), which fixed the float-ITEM and E-form-
LITERAL arms of the integer-argument screen and measured this shape as a different missing capability;
re-derived on this tree for this note.

## Repro (`--std 2023`)

```cobol
           DISPLAY FUNCTION CHAR(1.5 + 1)      *> compiles clean; 2.5 reaches the runtime
           DISPLAY FUNCTION CHAR(1.5)          *> COBOLNET1627 (PB248)
```

## The rule

§15.3's integer-argument definition (type 6, `cite.py --check 15.3 "an arithmetic expression that will always
result in an integer value"` — run first): `1.5 + 1` is an arithmetic expression whose value is 2.5, never an
integer; §15.15.3 r1 makes CHAR's argument an integer. The screen at bind must reject it or, where the
expression's value is not static, the runtime must apply §15.3 rule 14's EC-ARGUMENT-FUNCTION posture (PB383's
substituted-result table) — but a literal-only expression IS static.

## The mechanism

`IntrinsicArgumentRules.CollectAdditive` (PB248's always-integral expression walk) accumulates data items and
tests their descriptions through `PicInfo.IsIntegerDescription`; a `BoundNumLiteral` operand has no arm, so a
literal's fraction contributes nothing and `1.5 + 1` is classified integral. The bare-literal path goes through
`HasNonIntegralValue` (on `NumericLiteral.TryParseExact`) and rejects; the expression path never reaches it.

## Fix shape

Fold the additive spine's literals: an arm in `CollectAdditive` that feeds each `BoundNumLiteral` through the
same `HasNonIntegralValue` test, and — the one-step-further case — a constant fold of a literal-only spine
(`ConditionBinder.SoleNumLiteral`'s family) so `1.5 + 0.5` (= 2, integral) is admitted and `1.5 + 1` rejected
on VALUE, not on the presence of a fraction. Positive goldens for `CHAR(1.5 + 0.5)` and `CHAR(3 - 1)`, negatives
for `CHAR(1.5 + 1)` and `CHAR(F + 1)` where `F` is COMP-2 (the latter is PB248's arm — the control), all four
editions.

## Landing (wave 70 group A)

**Re-probed on the wave-70 build** (base `dbea12428`): `DISPLAY FUNCTION CHAR(1.5 + 1)` compiled clean and ran —
the note reproduced. After: `COBOLNET1627: FUNCTION CHAR argument-1 is an arithmetic expression whose literal terms
sum to 2.5 and whose every other term is an integer, so its value is never an integer — ISO §15.3 type 6 …`.

**Fix — a third witness in the ONE always-integral screen, not a second screen.**
`IntrinsicArgumentRules.CollectAdditive` now fills an `AdditiveSpine`: the item net it always kept, PLUS the exact
signed sum of every literal-only term (`ExactValue` — an exact rational fold over +, −, ×, ÷, unary − and an integral
literal exponent ≤ 64) and a `RestIntegral` flag cleared by any term the fold cannot value and `ProvablyIntegral`
cannot prove (an integer item, or +, −, ×, power over such terms). `NotAlwaysIntegral` refuses when the item arms
found no witness, `RestIntegral` holds and the constant is not an integer — the value is then constant + integer for
EVERY valuation. So `1.5 + 1`, `W-I + 0.5`, `(1.5)`, `3 / 2 + 1`, `W-S - W-S + 0.5` are refused on VALUE; `1.5 + 0.5`,
`W-I + 1.5 + 1.5`, `0.5 * 138`, `2 ** 6 + 4` are admitted; `W-S * 2 + 65.5`, `W-I / 2 + 0.5`, `1 / 0 + 0.5` fail open
(sound, not complete). ⚠ DETERMINATION: the fold is the ALGEBRAIC value, not a mode-rounded intermediate — type 6's
"will always result in an integer value" is a property of the expression.

**For the next implementer.** `src/Cobol.Net.Compiler/Binding/IntrinsicArgumentRules.cs#NotAlwaysIntegral` owns all
three §15.3 type-6 expression witnesses (root quotient, scaled/float additive leaf, literal constant);
`ExactValue` / `ProvablyIntegral` are the helpers to REUSE for any "always an integer" question. Trap:
`ProvablyIntegral` must stay in step with `NonIntegralItemsBeneath` — a subtree it proves integral skips the opaque
marking.

**Goldens.** `conformance:85/pb617_integer_arg_literal_constant` (admitted half, ORD(CHAR(n)) round trips 065–069),
`conformance:negative/pb617-integer-expr-literal-sum` (reject-at 85 2002 2014 2023, COBOLNET1627), unit
`IntegerArgumentConstantWitnessTests` (18 shapes). Batch `w70a-pb617`: AR-15.3-6 stays CONFORMS with the third arm and
its witnesses recorded (GAP unchanged).
