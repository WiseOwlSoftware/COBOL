# PB488

## Mechanism — data-description-entry-p2
F8 — BindCondition is a VALUE decoder with no eligibility screen: it captures the level-88 entry's literals and hangs the Condition88 off whatever DataItem the caller handed it, and the caller hands it `stack.Peek()` unconditionally. So §13.16.3 SR24's association requirement and ALL EIGHT of its exclusions are unimplemented, and two of the failures are worse than permissive. (i) A level-66 entry never enters the level stack, so an 88 written after a RENAMES entry silently steals the PRECEDING elementary item as its conditional variable — the condition-name the user wrote over the renamed range tests a different item. (ii) An 88 with an empty stack is dropped without a word and surfaces only as a RUN-TIME NotImplementedCobolFeatureException. The eight exclusions are a SET of item shapes, so the fix is one screen over the candidate conditional variable, not eight scattered tests.

### Expected, from the standard
ISO/IEC 1989:2023 §13.16.3 SR24 (cite-checked): "Format 3 or 4 is used for each condition-name. Each condition-name requires a separate entry with level-number 88. The condition-name entries for a particular conditional variable shall immediately follow the entry describing the item with which the condition-name is associated. A condition-name may be associated with any data description entry that contains a level-number except the following: a) Another level 88 entry. b) A level 66 entry. c) An alphanumeric group containing items with a usage other than display. d) A group containing items described with a JUSTIFIED or SYNCHRONIZED clause. e) A data item of the class index, message-tag, object, or pointer. f) A data item described with the ANY LENGTH clause. g) A type declaration described with the STRONG phrase, or a group item subordinate to such a type declaration. h) A variable-length group." Every repro above except a) is nonconforming and shall be rejected at compile time.

### Observed
Measured one probe per leg; not one is rejected. Exclusion a) is the only one satisfied, and structurally: BindEntries never pushes an 88 onto the stack, so `stack.Peek()` is always the last non-88 entry and consecutive 88s correctly share one conditional variable. Everything else compiles, and in most legs the condition then EVALUATES, so the illegal declaration produces an answer. Two legs are actively misleading rather than merely permissive: b) the level-66 case, where BindEntries' `if (lvl == 66) { ... BindRenames(entry); continue; }` (DataBinder.cs ~652-663) leaves the stack untouched, so the following 88 binds to the previous elementary item — the probe proves it by making the VALUE match B rather than the renamed span; and the 'immediately follow' requirement, where `if (stack.Count > 0)` (~639) drops an orphan 88 silently and the reference later becomes a run-time NotImplementedCobolFeatureException 'condition ORPHAN', i.e. a compile-time syntax rule reported, if at all, as a run-time crash. BindCondition (DataBinder.cs:2105) contains no test of the parent's shape at all — its only parent-dependent logic is the §13.18.63 SR29/SR31 boolean/national VALUE screens.

## Mechanism — usage-clause-p1
usage-p1-F1-level-88-entry-bound-without-screening-its-clause-list-or-its-conditional-variables-class

### Expected, from the standard

## Landed — 2026-09-13

**COBOLNET1976 / COBOLNET1977; `src/Cobol.Net.Compiler/Binding/DataBinder.ConditionName.cs` (new) +
`DataBinder.BindEntries` + `BindPipeline`.** ISO §13.16.3 SR24's association sentence and all eight of its
lettered exclusions now have a site, and it is ONE site.

**The root cause was the ASSOCIATION, not the screen.** `BindEntries` handed `BindCondition` `stack.Peek()`, and
`stack.Peek()` is not what SR24's subject is: the rule says the condition-name entries "shall immediately follow
the entry describing the item with which the condition-name is associated". The two readings coincide for every
entry that opens or extends the level hierarchy and DIVERGE exactly for the entries that never enter the stack —
a level-66 alias, a §13.10 constant entry, and the start of a section — which is where both wrong answers lived.
`BindEntries` now tracks `lastDescribed`, the rule's own subject; `BindRenames` returns its alias so the 66 case
reaches exclusion b) instead of being stepped over; and a level-88 entry with no preceding entry describing a
data item draws COBOLNET1977 instead of being dropped silently (`if (stack.Count > 0)`) and surfacing as a
run-time `NotImplementedCobolFeatureException`. ⛔ The §13.18.57.3 SR2 screen that shares the arm (a TYPE-clause
entry shall not be followed immediately by a level-88 entry) was reading the same wrong cursor and is corrected
by the same change.

**The eight exclusions are ONE TABLE.** `DataBinder.Sr24Exclusions` carries one row per lettered exclusion, in
the standard's order, holding the standard's words; `ConditionalVariableExclusion` returns the first matching row
and COBOLNET1976 names the letter and quotes it. A ninth exclusion is a row.
`ConditionNameAssociationDriftTests` (6 tests) asserts the table is exactly a–h and exercises every predicate,
including a) — which the binder cannot reach, because no `DataItem` in the forest carries level 88, and which is
therefore verified there or nowhere. The rows reuse rather than re-state: e) resolves its class question through
§13.18.60.3 SR4's own `Sr4PhraseOf` (SR4's six USAGE phrases produce exactly SR24 e)'s four classes, and
§13.18.60.3 SR11 states the same prohibition in the other direction, so ONE screen closes both rows); g) shares
`UnderStrongTypeDeclaration` with §13.18.60.3 SR14, whose second arm is the same words (the `Sr14` prefix was
dropped when the predicate gained its second caller); h) delegates to
`ReferenceResolver.HasVariableLengthSubordinate`, which IS §8.5.1.12.1's definition.

**It had to be a POST-BIND PASS.** Four of the eight exclusions (c, d, g, h) ask about the conditional
variable's SUBORDINATES, and a condition-name on a GROUP is written BEFORE that group's subordinate entries — so
at `BindCondition` time `parent.Children` is still empty and a screen there would answer "not a group, no
excluded member" for exactly the shapes the rule is about. The association is RECORDED where source order is
known and ADJUDICATED once the forest is complete, which is also what carries the two shapes
`ConformanceForest` cannot reach: a level-66 alias (it lives on `Renames66`, not in the tree) and an association
with no item at all.

**Over-rejection is this screen's real hazard, and it was measured, not assumed.** All 80 corpus programs
(conformance + NIST) that write a level-88 entry were recompiled: none draws COBOLNET1976 or COBOLNET1977. Two
positive goldens pin the shapes the rule does NOT exclude — `2023/pb488_condition_name_associations_ok` (nine
legs: consecutive 88s sharing one variable, an all-DISPLAY alphanumeric group, an 88 after a 66 alias elsewhere,
an ELEMENTARY member of a STRONG type declaration, an occurs-depending-on group, a fixed OCCURS table, a
national group) and `85/pb488_condition_name_associations_ok_85` for the ungated edition axis. Twenty negatives
`negative/pb488-*`, one per arm, each verified to carry its diagnostic at every edition its `reject-at` names.
