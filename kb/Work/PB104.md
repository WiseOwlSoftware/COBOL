> with `GraphemeCluster.cs`, `GraphemeEnumerator.cs`, `GraphemeBreaker.cs`, `README.md`; "follow UAX #29 behavior

## The integration decision the brief forced (section 8 [1], stated and tested — never silently reinterpreted)

The brief asked the collation engine to "normalize input (NFC), segment into grapheme clusters, build keys per
cluster" before building keys. That is not how UCA collation works, and doing it would break the conformance
battery: (a) UCA is defined over NFD and the engine decomposes on demand — an NFC pass would only be undone;
(b) a collation CONTRACTION may span a cluster boundary — Thai SARA E + KO KAI are two clusters and one contraction
(the prevowel reorders), Czech `ch` is two clusters and one letter — so per-cluster elements are wrong;
(c) a UTS #10 key is level-major (all primaries, then all secondaries …), so concatenated per-cluster keys are not
the text's key. `KeysAreNotPerCluster_ContractionsCrossClusterBoundaries` pins all three; the engine keys whole
texts and the key cache ([[PB106]]) caches whole-text keys. What segmentation IS to collation and normalization:
clusters are stable under NFC/NFD (`Segmentation_IsStableUnderNormalization`) and a cluster-safe truncation keeps a
collation prefix where a code-unit cut loses an accent (`ClusterSafeTruncation_KeepsACollationPrefix`) — the
`Truncate` API and README §2 say so.
