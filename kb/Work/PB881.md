Source: the `PB416` report, "New defects" item 2.

## The rule

```
$ python scripts/spec/cite.py --check 13.18.15.3 "Neither the data item described by the subject of the entry nor any data item subordinate to the subject of the entry shall be specified as a receiving data item"
  OK  §13.18.15.3 2)  (Syntax rules)
      2) Neither the data item described by the subject of the entry nor any data item subordinate to the
      subject of the entry shall be specified as a receiving data item.
```

The rule is stated over "a receiving data item" — the STATEMENT is irrelevant to it — so a per-verb check is
the wrong shape and a per-verb omission is the predictable result.

## The code site

* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/InspectBinder.cs:122` and `:283` — `ctx.Refs.Resolve`
* the ACCEPT receiver path, same call

`ExpressionBinder.ResolveReceiving` is where COBOLNET1548 is raised. **The remedy is the ROUTING, not a check
per verb** (memory `change_the_dispatch_not_the_callers`): every verb that names a receiving operand resolves
it through the one entry, and the entry is the only thing that knows SR2.

## The sibling sweep — this is the measurement the fixer owes

Grep `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/` for `Refs.Resolve` and, for each hit, ask whether the
operand is RECEIVING. INSPECT (two sites) and ACCEPT are the two the PB416 implementer found; STRING,
UNSTRING, SET, ALLOCATE, the report-writer stores and the I-O record areas are the obvious candidates to
measure, because SR2's other half (`kb/Work` PB871's DYNAMIC-LENGTH finding) already showed that
`STRING`/`UNSTRING`/`ACCEPT`/`INITIALIZE` each reach a receiving operand by their own route.
**Add a drift test** that no binder under `Verbs/` calls `Refs.Resolve` for an operand the bound node marks
receiving — without it the next verb added inherits the hole.
