# PB2964 — LENGTH of a bit-bearing group with a runtime-length subordinate is a named stage

Filed 2026-10-10 by the train 1056 lander from the wave 1056 F implementer's report
(`E:\COBOL-coord\scratch\reports\w1056f-PB2818-report.md`, new lead 1). Same family as PB2818 (dynamic-capacity
tables of USAGE BIT elements), a different mechanism.

**Repro:** `E:\COBOL-coord\scratch\w1056f\c4.cob` line 19, `DISPLAY FUNCTION LENGTH(G) " " FUNCTION LENGTH(F)` at
`--std 2014`: G holds USAGE BIT items and a dynamic-capacity table (a runtime-length subordinate). The program
compiles to the named stage COBOL1756, which aborts the run unit when reached.

**Site:** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/IntrinsicBinder.cs` about line 2409
(`VariableLengthGroupSum`): `if (group.HasBitDescendant) return Stage("a group holding USAGE BIT items and a
runtime-length subordinate — its fixed extent is a §8.5.1.6.3 layout, not a sum")`, and `ImageOrStage` refuses the
image path for the same groups (`!group.HasBitDescendant`).

**Why it is a defect.** §15.50 (LENGTH) and §15.14 (BYTE-LENGTH) define the function's value for any data item; the
group's current length exists at run time. The fixed extent of a bit-bearing group is a §8.5.1.6.3 LAYOUT (bit runs
packed into bytes), so it cannot be summed member by member — but after PB2818 a dynamic-capacity table is out-of-line
storage that starts a byte of its own (BitLayout.RunMember / SharesByteWith), so the group's length is the laid-out
fixed part (`ByteWidth`, which already folds the bit runs) plus each runtime-length subordinate's current extent. The
fix is to compute the fixed part from the layout, not to refuse.

## Landed 2026-10-11 (w1059 H)

Re-probed on the wave build: `c4.cob` (the note's repro) and a USAGE BIT group with a dynamic-length subordinate both
reached COBOL1756 at LENGTH and BYTE-LENGTH. The fix is the one the note named: `IntrinsicBinder.VariableLengthGroupSum`
no longer stages a bit-bearing group. `DataItem.ByteWidth` already folds the bit runs (`BitLayout.ExtentBits`), and every
runtime-length subordinate (a dynamic-capacity table, a dynamic-length leaf) is a whole-byte item that starts on a byte
boundary and leaves the next item on one (`BitLayout.SharesByteWith`), so taking its counted extent out of the byte total
leaves the fixed part exactly. `ImageOrStage` lost its `!HasBitDescendant` conjunct: the current-extent image composer
already composes bit runs (a table of elements holding a bit item and a dynamic leaf displays and now measures).
Determination (docs/CONFORMANCE.md DOC-A.1-61): a dynamic-capacity table of bit elements counts capacity times the
ceil(n / 8) element length (15.50.4 rule 7c, 8.5.1.12.3 "the byte length of their elements"), so three 1-bit occurrences
are 3 bytes, the length PB2818 already gives the table's storage.
Golden `2014/pb2964_length_bit_variable_group`. Sweep: the other `HasBitDescendant` stage in the file was the
OCCURS DEPENDING arm (PB2498); the image composer's own limit on a bit-bearing ODO group is the residue the wave report
names (the unit test `StagedLoudResidue_FailsLoud_NeverWrong` now pins that shape).
