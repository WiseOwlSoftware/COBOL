# PB2964 — LENGTH of a bit-bearing group with a runtime-length subordinate is a named stage

Filed 2026-10-10 by the train 1056 lander from the wave 1056 F implementer's report
(`E:\COBOL-coord\scratch\reports\w1056f-PB2818-report.md`, new lead 1). Same family as PB2818 (dynamic-capacity
tables of USAGE BIT elements), a different mechanism.

**Repro:** `E:\COBOL-coord\scratch\w1056f\c4.cob` line 19, `DISPLAY FUNCTION LENGTH(G) " " FUNCTION LENGTH(F)` at
`--std 2014`: G holds USAGE BIT items and a dynamic-capacity table (a runtime-length subordinate). The program
compiles to the named stage COBOLNET1756, which aborts the run unit when reached.

**Site:** `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/IntrinsicBinder.cs` about line 2409
(`VariableLengthGroupSum`): `if (group.HasBitDescendant) return Stage("a group holding USAGE BIT items and a
runtime-length subordinate — its fixed extent is a §8.5.1.6.3 layout, not a sum")`, and `ImageOrStage` refuses the
image path for the same groups (`!group.HasBitDescendant`).

**Why it is a defect.** §15.50 (LENGTH) and §15.14 (BYTE-LENGTH) define the function's value for any data item; the
group's current length exists at run time. The fixed extent of a bit-bearing group is a §8.5.1.6.3 LAYOUT (bit runs
packed into bytes), so it cannot be summed member by member — but after PB2818 a dynamic-capacity table is out-of-line
storage that starts a byte of its own (BitLayout.RunMember / SharesByteWith), so the group's length is the laid-out
fixed part (`ByteWidth`, which already folds the bit runs) plus each runtime-length subordinate's current extent. The
fix is to compute the fixed part from the layout, not to refuse.
