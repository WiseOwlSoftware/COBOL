# PB5147 - CM102M intermittently hangs in the merge group

**Sites:** `tests/WiseOwl.Cobol.Tests.Conformance/CommunicationCcvsTests.cs:54` (`CM102M_ReportsNoFailure`); the communication runtime (the queues, the terminal ENABLE/RECEIVE path).

**Evidence (2026-11-10).**
- PR #1465, merge-group run 42841304077 (14:44 UTC), Windows shard 3/7: bounced.
- PR #1463, merge-group run 42835167709 (15:20 UTC), Windows shard 3/7: failed, then merged on a re-queue.
- Both show the same signature: `HarnessNonObservationException`, both attempts TimedOut after 120000 ms, the process used about 31.2-31.5 s of its own CPU, and the host was 13-15 % busy across the attempt (4 logical processors). So the program spins for about 30 s, then waits idle until it is killed.
- The merge groups between 12:03 and 13:49 UTC that day passed.

**Candidates to investigate, not the established cause.** PB5107 (commit dfcee3d953, "a RECEIVE on a disabled I-O terminal gets no message until ENABLE", merged as dd1c10bd8e at about 11:59 UTC) and PB4736 (the queues moved to the paged store, with mcs.lock). A spin followed by an idle wait fits a poll loop that never sees its message, or a lock wait; neither is confirmed.

**Class.** CLAUDE.md classes a flake as a kb/Work defect fixed at its root, never retried. This is that defect. Re-queueing is not the answer.

**Held.** Branch `worktree-wf_82a7f4cd-626-20` (PR #1465) is held until the fix lands.

**Owed.** Reproduce under load on a 4-processor host, find what the 30 s of CPU is spent on (stack sampling), fix the cause, and add a structural guard (not a longer wall-clock limit).
