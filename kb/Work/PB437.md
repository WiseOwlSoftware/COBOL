# PB437 — a capability limit shipped as a rejection, in one of two adjacent operand slots

## 1. THE MECHANISM

GR12 requires a BY operand to be re-evaluated per augment and an AFTER level's FROM per outer augment (GR13 e) 2).
The binder implements that for DATA-ITEM operands by rendering them inline at each site — measured correct. But
when the operand carries a FUNCTION reference (a user-defined function, or a data item whose SUBSCRIPT contains
one) the activation lands on the statement-level pending list, whose cardinality would then be wrong, and
`ControlFlowBinder.BindVaryingLevel` calls `UdfStagePerEvaluationResidue`, which raises `COBOLNET1509` as an
**ERROR** — `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:398-405`:

    BoundExpr from = host.Expr.BindIndexWindowExpr(exprs[0]);                       // :398
    if (!firstLevel)
        host.Udf.UdfStagePerEvaluationResidue(fromMark,
            "a PERFORM VARYING AFTER level's FROM operand (re-evaluated per outer augment, §14.9.28 GR13e.2)");
    …
    host.Udf.UdfStagePerEvaluationResidue(byMark,
        "a PERFORM VARYING BY operand (evaluated per augment, §14.9.28 GR12)");     // :404-405

**The refusal is not a spec rule and does not claim to be.** The SAME construct is accepted in the FIRST-level
FROM (`:398` with `firstLevel: true` — no residue call) and in the UNTIL condition (which rides
`UdfAttachPerEvaluation`), and the diagnostic text says outright that it is a capability limit: "requires an
activation cardinality this implementation does not yet realize for that operand position … move the reference
to a preceding COMPUTE". The doc-comment on `BindVaryingLevel` (`:386-391`) states the same taxonomy
deliberately — per-evaluation for the condition, statement-hoisted for the first-level FROM, LOUD for the rest.

Two GREEN tests pin the refusal as though it were a decision — `conformance:negative/pb17-function-subscript-
varying-by` (the source and its `.err` both live in `tests/conformance/negative/`) and
`UdfInvocationTests.PerEvaluationResidueOperands_1509` — and the kb/Work note whose body describes the debt,
**PB17**, is `status: landed` with `rejects_legal_source: false` (verified on this tree). So the ONE work
register had no open row for it until this note.

## 2. THE RULES, QUOTED, WITH THEIR `--check` LINES

The obligation the operand must satisfy (and does):

    python scripts/spec/cite.py --check 14.9.28.4 "Item identification for identifier-3, identifier-4, identifier-6, identifier-7, index-name-2, and index-name-4 is done each time"
    OK  §14.9.28.4 12)  (General rules)

That a function-identifier stands where an identifier stands:

    python scripts/spec/cite.py --check 8.4.3.2.4 "A function-identifier references a temporary data item whose value"
    OK  §8.4.3.2.4 1)  (General rules)

    python scripts/spec/cite.py --check 8.4.3.1.1 "An identifier is a sequence of character-strings and separators used to reference a data item uniquely"
    OK  §8.4.3.1.1   (General)

§8.4.3.1.2 prints THREE general formats for an identifier — Format 1 is a function-identifier, Format 2 is a
qualified-data-name-with-subscripts, Format 3 is reference-modification — so a subscripted data item and a
function-identifier are both identifiers, and both stand at identifier-4 / identifier-6 in the 14.9.28.2
varying-phrase figure. This is the same reasoning the project used to LAND kb/Work PB86 for the
`PERFORM … TIMES` count, where the same slot's SR2 text was held to admit an integer-type function.

⚠ The subscript spelling in the repro makes the rejection unambiguous even for a reader who wants to argue
§14.9.28.3 SR2's "described in the data division" against a bare function-identifier: `W-E` **is** described in
the data division, and only its SUBSCRIPT contains the function.

and it fires only on the function-bearing path.

## 4. THE CODE SITE AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/UdfBinder.cs:333` — `UdfStagePerEvaluationResidue`
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:398-405` — its two call sites here
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/UdfBinder.cs:302-309` — `UdfWrapCalls`, the once-per-statement
  hoist, and the doc-comment that names the exact operand positions the hoist is EXACT for
* `tests/conformance/negative/pb17-function-subscript-varying-by.cob` + `.err`, and
  `UdfInvocationTests.PerEvaluationResidueOperands_1509` — the two tests that pin the refusal
* `kb/Work/PB17.md` — `status: landed`, `rejects_legal_source: false`; its body describes this debt

**The mechanism the fix needs already exists.** `BoundUdfEvaluated` / `UdfAttachPerEvaluation` is exactly the
"attach the activations to the site that re-evaluates, not to the statement" carrier, and the UNTIL condition in
this same function already uses it (`:406-407`). The repair is to give the augment site and the re-initialize
site their own per-evaluation carriers the way the condition has one — **not** to widen the statement-level
hoist, and **not** to keep the refusal.

⛔ **Follow rule 5 on the shape.** Today `BindVaryingLevel` decides an operand's evaluation cardinality by
POSITION, in prose, with three hand-written cases (condition ⇒ per-evaluation, first-level FROM ⇒ hoisted,
everything else ⇒ loud). Each new operand window will add a fourth hand-written case. The structural answer is
one evaluation-WINDOW value carried with the bound operand — the window IS the rule (GR12's own sentence
enumerates which operands are re-identified per use) — so a new operand position picks up the right carrier
automatically. Pair it with a drift test that asserts each varying-phrase operand slot's window.

⚠ **Two tests will change from green-passing to needing rewrite**, and that is correct: a green test pinning a
loud-stage reads as a DECISION. The negative conformance case and the unit test must be re-pointed at what the
compiler should now do (compile, and produce one activation per augment), not deleted silently.

## 5. THE SIBLING SWEEP

* **Every other `UdfStagePerEvaluationResidue` call site.** Each is the same trade — a refusal standing in for a
  carrier — and each is a place where legal source is rejected today. Grep for the method; the PERFORM VARYING

* **Every operand slot whose spec text says "is done each time".** GR12's sentence lists identifier-3,

* **`kb/Work/PB17`'s other residue.** PB17 is landed with `rejects_legal_source: false`, and its body describes
  a debt that IS a false reject. Re-read it: if any of its other described residues are still live, they are in
  the same position — described in a landed note, invisible to `work.py next`. That is the measured-selector
  hazard, not a filing quibble.
* **Whatever the emitter does once these compile.** `ControlFlowEmitter.EmitVarying` renders the augment and the
  re-init inline; a per-evaluation carrier must land INSIDE the loop at both `:306`/`:314` (augment) and `:315`/
  `:331` (re-init), and the TEST AFTER arm has its own copies of both.
