## Landed 2026-09-02 (cluster D)

**The 13-cell producibility question was MEASURED**, one probe program per cell through the real compiler, not
deduced. Ten of Table 3's thirteen invalid cells are already hard parse errors; two more — (ident,'(') and its
sibling — cannot form as an arithmetic PAIR at all, because COBOL's reference syntax reads a `(` after an
identifier as a subscript or reference-modifier. **Exactly one cell was producible: (unary, unary)**, plus §8.8.2
Table 4's (B-NOT, B-NOT). Screening the other twelve would have been dead code.

**Two premises in the analysis did not survive checking, and both changed the fix.**

1. *"The screen cannot be dialect-gated, therefore it cannot be in the grammar."* — `--permissive` softens exactly
   one verdict: `EditionSeverityPolicy.For` maps `ConstructAvailability.Removed` to Warning and nothing else. An
   invalid symbol pair was never legal at any edition, so there is no permissive arm to write. The argument for a
   post-parse screen had to be found elsewhere.
2. *"A tightened `unaryExpression` still admits `- - 2` via signedNumericLiteral, so fix both arms."* — the real
   constraint is sharper and points the other way. §8.3.3.3.2 rule 2 makes a numeric literal a *character-string*
   whose sign is "the leftmost character of the literal", so `- -2` is Table 3's **permissible** (unary, literal)
   pair while `- - 2` is the invalid (unary, unary) one. **Measured: in the default lexer mode both spellings emit
   MINUS MINUS INTEGERLIT** (the SIGNED_INTEGERLIT/SIGNED_DECIMALLIT twins exist only in FUNCTION-argument and
   SUBSCRIPT regions). No CFG tier can separate them, and a tier rejecting both would reject legal source. Token
   POSITIONS do carry it — which is why the rule is a post-parse screen that reads adjacency off the token stream,
   and why `unaryExpression`'s self-recursion is now documented as deliberate rather than removed.

`ArithmeticFormationRules` (frontend, the `BooleanExpressionResolver` pattern) owns both tables' one live cell;
`ExpressionFormationPass` is the compiler's per-parse-tree invocation, a THIRD sibling after
VersionConformancePass and FlagConformancePass on the same "orthogonal axis ⇒ separate pass" precedent. The
frontend consumer calls it at the top of `EvaluateArithmeticOperand`, **before** `SoleNumericLiteral` — the third
evaluating arm the note did not name, which toggled the sign through a stacked chain and folded `- - 5` to 5.

Also corrected: the grammar comment above `booleanExpression` asserted Table 4 was enforced "STRUCTURALLY" while
`booleanFactor : B_NOT booleanFactor` self-recursed — a green-looking claim holding the gap open.

Corpus population newly rejected: **measured at zero** (the only two corpus hits for stacked signs are inside a
comment and a string literal).
