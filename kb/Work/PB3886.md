# PB3886 — size-error-still-stores-power-zero-result: ON SIZE ERROR is executed for 0 ** 0 but the receiving item is still set to 1

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S3) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\size-error-still-stores-power-zero-result.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\size-error-still-stores-power-zero-result\`.

## Summary

When both operands of an exponentiation are 0 at run time, GnuCOBOL 3.2 sets EC-SIZE-EXPONENTIATION and executes the
ON SIZE ERROR phrase, but it also stores the value 1 into the receiving item. ISO requires the receiving item to keep
the value it had at the start of the statement when the size error condition occurs and the SIZE ERROR phrase is
specified. The run-time routine returns the value 1 alongside the exception instead of an invalid (NaN) result, so the
store routine stores it.

## Minimal test case

Fixed reference format (cobc's default), 12 lines, `records/size-error-still-stores-power-zero-result.cob`:

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. SEPOW0.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 Z PIC S9(5) VALUE 0.
       01 R PIC S9(5) VALUE 77.
       PROCEDURE DIVISION.
           COMPUTE R = Z ** Z
             ON SIZE ERROR DISPLAY "SIZE ERROR, R=" R
             NOT ON SIZE ERROR DISPLAY "NO SIZE ERROR, R=" R
           END-COMPUTE
           STOP RUN.
```

## Expected result (per ISO)

ISO/IEC 1989:2023 8.8.1.2 rule 6 a) (checked): a zero base requires an exponent greater than zero, "Otherwise, the
EC-SIZE-EXPONENTIATION exception condition is set to exist and the size error condition is raised."

14.7.5 (checked), the size error condition exists "if the rules for evaluation of exponentiation are violated" (case 1),
and when the SIZE ERROR phrase is specified, rule 1: "If the size error condition occurred during the arithmetic
operations specified by the arithmetic statement, the values of all of the resultant data items remain unchanged from
the values they had at the start of the execution of the arithmetic statement."

Expected output: `SIZE ERROR, R=+00077`.

Edition: Annex E of the 2023 text lists no change to 8.8.1.2 or 14.7.5; the 2009 committee draft that led to
ISO/IEC 1989:2014 (CD 1.2) carries both rules (its 14.7.4 holds the "remain unchanged" text). The requirement holds for
`-std=cobol2014`.

Edition as recorded by the adjudicator: 2014. `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Class

Wrong output (the receiving item is changed although the size error condition exists and the SIZE ERROR phrase is
specified).

## Our compiler (WiseOwl)

`cobol sepow0.cob --std 2014 --run` (WiseOwl, built from main 6ed90bd1c): `SIZE ERROR, R=+00077`, exit 0. It matches
the ISO expectation.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `libcob/intrinsic.c`, function `cob_decimal_pow`: in the zero-exponent branch, the zero-base case calls
  `cob_set_exception (COB_EC_SIZE_EXPONENTIATION)` and then falls through to set the result to 1 with scale 0. The
  branch for a negative base with a non-integer exponent, a few lines below, marks the result invalid
  (`COB_DECIMAL_NAN`) as well as setting the exception; the 0 ** 0 branch does not.
- `libcob/numeric.c`, function `cob_decimal_get_field`: it refuses to store only a NaN result, so the 1 is stored.
  Marking the 0 ** 0 result NaN makes the store skip the receiving item. (The NaN path there replaces any exception
  other than EC-SIZE-ZERO-DIVIDE with EC-SIZE-OVERFLOW, so a patch should also keep EC-SIZE-EXPONENTIATION there.)
- `cobc/codegen.c`, function `output_level_2_ex_condition`, generates the test that sends control to the SIZE ERROR
  phrase from the EC-SIZE exception code after the store; that is why the phrase runs although the store happened.

## Draft issue

**Title:** ON SIZE ERROR is executed for 0 ** 0 but the receiving item is still set to 1

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1), `cobc -std=cobol2014 -x`.

Program (fixed format):

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. SEPOW0.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 Z PIC S9(5) VALUE 0.
       01 R PIC S9(5) VALUE 77.
       PROCEDURE DIVISION.
           COMPUTE R = Z ** Z
             ON SIZE ERROR DISPLAY "SIZE ERROR, R=" R
             NOT ON SIZE ERROR DISPLAY "NO SIZE ERROR, R=" R
           END-COMPUTE
           STOP RUN.
```

Steps: `cobc -std=cobol2014 -x sepow0.cob && ./sepow0`

Observed: `SIZE ERROR, R=+00001`.

Expected: `SIZE ERROR, R=+00077`. ISO/IEC 1989:2014 (and 2023) 8.8.1.2 rule 6 a) makes 0 ** 0 a size error
(EC-SIZE-EXPONENTIATION), and 14.7.5 rule 1 for the SIZE ERROR phrase: "the values of all of the resultant data items
remain unchanged from the values they had at the start of the execution of the arithmetic statement."

Cause: `cob_decimal_pow` (libcob/intrinsic.c) sets EC-SIZE-EXPONENTIATION for 0 ^ 0 but returns 1 rather than a NaN
result, and `cob_decimal_get_field` stores every non-NaN result. The negative-base, non-integer-exponent case in the same
function already returns NaN.
