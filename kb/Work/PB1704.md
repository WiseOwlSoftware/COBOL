# PB1704 — LANDED (2026-09-28)

**Owner, 2026-09-28 ~12:35 PDT, after the orchestrator found group C hung only when asked:** "We just wasted 1.5
hours waiting for nothing. Fix that".

## The defect

Wave 70 (`wf_ae05e6d0-c50`) had two agents hang the same way:
- **C (`impl-C-PB1117`):** its last transcript record is at 11:02:54 PDT, a successful tool result, after which it
  read the report template.
  - It had committed PB1117, PB1174 and PB1268, and its gate was GREEN: Conformance 4,291 including the corpus and
    NIST legs, Unit 29,694, Characterization 33.
  - It never produced another token.
- **U2 (`impl-U2-PB1238`):** the same shape at 12:20:16.

The session meter read 37 % and the weekly meter 32 %, so neither was a quota block. Three gaps let it happen:
- **Nothing watched.** The orchestrator noticed only when the owner asked, 87 minutes after C stopped.
- **Nothing could act on one agent.** A workflow cannot stop one of its own agents, and TaskStop on the agent id
  fails ("No task found").
- **Nothing gave up.** The rolling wave's final remainder train waits for every implementer, so one hung call held
  the whole wave.

## Measured thresholds

Measured over 150 agent transcripts (about 27,800 silences between records):
- **Waiting on the model:** p99 30 s, p99.9 94 s.
- **Inside a tool call:** maximum 585 s (the `timeout 580` gate wait; shell tools cap at 600 s).

So a stall is more than 10 min waiting on the model, or more than 12 min inside one tool call. By that rule C would
have been flagged at about 11:13, not at 12:29.

## The fix

- **Detect: `stall_watch.py`**, public claude-skills v1.10.0, `agent-fleet/references/`.
  - It reads the workflow journal (started without a result means pending) and each pending agent's LAST record
    timestamp, not the file mtime (PB1702).
  - It exits, which wakes the orchestrator, the moment an agent crosses a threshold.
  - Verified live: its first run flagged exactly C (89 min) and U2 (12 min), and left the working lander alone.
- **Procedure: MANDATORY-PRACTICES O8.** The watchdog runs in the background beside every fleet workflow. On a
  stall, let the others finish, stop the workflow, and dispatch the remainder from the stalled agent's branch.
- **Backstop: the per-implementer ceiling** in `wf_rolling_wave.js` (`implementer_ceiling_min`, default 240) and in
  public `rolling-wave.js` (`implementerCeilingMin`).
  - A `setTimeout` race records an implementer still running at the ceiling as `STALLED`, and the wave moves on.
    `setTimeout` is permitted in workflow scripts, verified by a probe workflow.
  - Landers are excluded: a timed-out lander could still be pushing when the next train starts.
  - Simulated with a never-returning agent: the pre-fix script hangs; the fixed one finishes, records U as
    STALLED, and lands a train. The PB1703 death case still passes.
- **Check:** `check_practices.py` requires the ceiling and the rejection handling in `wf_rolling_wave.js`, and O8
  in MANDATORY-PRACTICES.

## Wave 70's own recovery

The running workflow predates this fix. After train 70's lander finishes, the orchestrator stops the workflow and
dispatches the remainder:
- a finisher for U2 from its stamped branch;
- a lander for U + U2, I and C. C's branch is gate-green, and its PB1069 goes to the next wave.
