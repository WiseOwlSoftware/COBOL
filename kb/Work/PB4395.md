## What §13 says and what was built

PIPELINE-REVIEW.md §13 (owner-approved as written, PB4334 decision 3): "a **tooling** change (`scripts/`, `.github/`,
`tools/`, `.claude/`, any `*.py`/`*.ps1`/`*.sh`) runs the audits and the self-tests whose recorded inputs it touches".
Step 3 (PB4326, judgment call 2) kept the full legs for a tooling-only diff and named the no-build lane step 5's. Step 5
(PB4328, `gate.py`) built two lanes, `inert` and `full` with a `tooling` flag (`inert_lane.Lane`), so a tooling-only
change runs the build and the whole Windows population (about 5 minutes) plus the self-tests. Step 11 (PB4334) then wrote
CLAUDE.md to match the code: "runs what a code change runs and, beside it, the script self-tests". Measured on main,
2026-10-25 to 2026-11-01: 45 of 244 merges that were not docs/notes-only touched tooling only.

## Why C# tests read scripts/ (measured at 55d93dbb4)

92 C# files under `tests/` name `scripts/`; 41 only in a comment. About 51 read or run a script, in two kinds:

1. **The compiler's own generators and spec extractors (about 17 classes, 182 cases, 112 s summed test time per Unit
   run):** `ReservedWordsDriftTests`, `ContextSensitiveWordsDriftTests`, `CobolWordsDriftTests`,
   `OperandListKeywordDriftTests` (gen-reserved-words.ps1, gen-cobol-words.ps1), `ConstructRegistryDriftTests`,
   `CompilerDirectiveCatalogDriftTests` (gen-constructs.ps1), `DiagnosticRegistryDriftTests` (gen-diagnostics-doc.ps1),
   `CatalogCoverageDriftTests`, `SpecTraceabilityInventoryDriftTests`, `AnnexA2UndefinedListDriftTests`,
   `AnnexA3RegisterDriftTests`, `DerivedVerdictDriftTests`, `SortWorkTraceabilityDriftTests` (scripts/spec/),
   `ArchCensusDriftTests` (arch/census.py), `TrackedTreeScopeDriftTests` and others. These scripts PRODUCE compiler data,
   and three more scripts run inside the build itself (Sites). A change to one of them is a compiler change: it belongs in
   the code lane, and the C# test that checks its output is rightly a compiler test.
2. **The pipeline testing itself from the compiler's test assembly (about 29 classes, 156 cases, 226 s summed test time
   per Unit run):** `GateLegDriftTests`, `GateSlotDriftTests`, `InertLaneDriftTests`, `LandingLaneDriftTests`,
   `LandingPipelineDriftTests`, `LandingMeasureDriftTests`, `MergeDriverDriftTests`, `ReviewLaneDriftTests`,
   `SelfTestDiscoveryDriftTests`, `SelfTestFixtureDriftTests`, `FilterPopulationGuardDriftTests`,
   `TestLegReportDriftTests`, `PerfBaselineSelfTestDriftTests`, `LinuxGateDriftTests`, `PythonInterpreterDriftTests`,
   `ToolchainManifestDriftTests`, `DotnetSdkInstallDriftTests`, `SparseCheckoutDriftTests`, `ScriptLayeringDriftTests`,
   `ScriptStandardStreamsDriftTests`, `GitBatchDriftTests`, `HeldAnalyzerOutputDriftTests`, `RuntimeAbiPinDriftTests`,
   `ExternalCorpusFetchTests`, `ExternalCorpusPopulationDriftTests`, `CiBoundsDriftTests`, `CiHarnessLogDriftTests`,
   `CitationAuditSelfTestDriftTests`, `HostWitnessTraitDriftTests`, and `tests/_shared/GateLegAudit.cs`. They test Python,
   shell and workflow tooling, not the compiler. They live in the Unit assembly because, before `self_tests.py` (PB2563)
   discovered and ran every script's `--self-test`, the Unit population was the one place every gate and CI was sure to
   run, so a pipeline rule got its "drift test" there. That reason is gone.

The cost of kind 2 is double: every COMPILER gate runs 156 pipeline cases it has no use for, and a TOOLING change cannot be
checked without a C# build. That second cost is why the §13 lane was not built: without a build, these cases would first
run in the merge group, and THE RULE ("every case the merge group runs on Windows already ran green at the pushed head")
would be false.

## The change

1. **Move kind 2 into the scripts' own self-tests.** Each class's arms become arms of the `--self-test` of the script it
   checks (or of the one script that owns the rule), reading the `.cs`, `.csproj`, workflow and doc files as text where an
   arm checks a C#-side fact (no build needed). Delete each C# class in the same change (CLAUDE.md rule 4: no forwarders).
   The self-tests already run in the tooling lane (PB4326) and in CI's `audits` and `windows-self-tests` jobs.
2. **Keep kind 1 in C#, and make its scripts code.** A path the build runs (the three csproj `Exec` steps) or a generator
   whose output a compiler test checks is a CODE path for the lane, though it is also tooling: the lane runs the code lane
   plus the self-tests for it. State this as ONE list in `inert_lane.py` (beside `TOOLING_READS`), with a drift arm that
   finds every csproj `Exec` of a script and every C# test that runs a script and refuses one not on the list.
3. **Build the third lane.** `inert_lane.Lane` gains the tooling lane: every changed path is tooling (`TOOLING_UNDER`,
   `TOOLING_SUFFIXES`) and none is on the code list of item 2, a `TOOLING_READS` entry that a compiler test reads (the
   grammar, `tests/_shared/TestRepo.cs`, `docs/CONFORMANCE.md`), `.gitattributes` or `toolchain.env` (a new SDK or new
   checkout bytes changes the compiler's tests). `gate.py` runs the audits with the self-tests for it and joins them, as
   the inert lane does: no corpus fetch, no slot, no build. Its record says `lane: tooling`.
4. **Docs.** CLAUDE.md "Testing" takes §13's tooling clause back verbatim; THE RULE needs no widening once item 1 has
   landed, since no Windows C# case reads a tooling-lane path any more. Update DESIGN-test-build-ci.md section 0 and the
   gate skill in the same change.

**Acceptance.** A planted tooling-only change (`scripts/orchestrator/steer.ps1`) gates in the tooling lane with no build
and a GREEN verdict; a change to `scripts/gen-reserved-words.ps1` or `scripts/gen-grammar-diagrams.ps1` gates in the code
lane; the Unit population no longer holds the kind-2 classes, and the self-tests hold every arm they had (count them before
and after). Measure the tooling lane's wall (expected: the audits, about 40 s, plus the self-tests that changed).
