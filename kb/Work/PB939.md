# PB939 — OPEN — the VALUE screen is keyed on the SUBJECT and blind to the LITERAL

Source: the **PB415 (INITIALIZE) implementer report**, "New defects" item 1, and the same fact recorded a second
time inside **`kb/Work/PB933`**'s body as *"⚠ Also found, NOT this note's mechanism and reported for filing"*.
It has been sitting in a note's PROSE, where no work list can see it — the exact shape CLAUDE.md rule 8 names.

## Observed, MEASURED on this tree

`<scratch>/reg8/probe/c_valnull_num.cob`, `--std 2023`:

```
       01 N PIC 9(4) VALUE NULL.
       01 A PIC X(4) VALUE NULL.
       …
           DISPLAY "N=[" N "]"
           DISPLAY "ALEN=" FUNCTION LENGTH(A)
```

```
N=[0000]
ALEN=4
```

Compiles clean — **no diagnostic at any edition** — and the numeric item acquires a defined initial value. The
alphanumeric item is initialized to four U+0000 characters. PB415's report adds the consequence: with
`INITIALIZE … ALL TO VALUE` over the numeric case the run unit **aborts**, so this acceptance is the only reason
PB933's divergence was reachable at all, and the note therefore carries a latent crash.

## Expected, from the standard

```
$ python scripts/spec/cite.py --check 8.4.3.10.3 "it may be used only as a sending operand in an INITIALIZE or a SET statement"
  OK  §8.4.3.10.3 1) a)  (Syntax rules)
      a) If the class of the associated data item is pointer, it may be used only as a sending operand in an
         INITIALIZE or a SET statement; as an argument in a program-prototype format CALL statement, a
         function-prototype form …
```

The rule is an **enumeration of every context in which the predefined address NULL may be written**, and a VALUE
clause is in it at NO class. §8.4.3.10.1 makes NULL a *predefined address*, not a literal, and §13.18.63.2
Format 1 takes `literal-1`. So the acceptance is not a leniency that happens to be wrong for a numeric item; it
is wrong for every class, including the pointer class its own screen was written for.

## Why this is NOT `PB515`, and why it was nearly filed there

`PB515` (open) is *"There is no VALUE-by-CLASS screen at the data description entry"* — §13.16.3 SR10, the rule
that bars a VALUE clause on a data item of class index, message-tag, object or pointer. **PB515 asks which
SUBJECTS may carry a VALUE. This note asks which LITERALS a VALUE may carry**, and the two populations do not
meet: an implementer who lands PB515's class-keyed screen in full still accepts `01 N PIC 9(4) VALUE NULL.`,
because `PIC 9(4)` is class numeric and passes every one of SR10's four exclusions. PB415's own report reaches
the same conclusion and PB933's body says it outright: *"`PB515` covers the class-index/message-tag/object/
pointer VALUE screen but not this population."* One note per mechanism; `cluster:` hands both to one implementer.

## The code site

`src/Cobol.Net.Compiler/Binding/DataBinder.cs` — the VALUE screen that already emits **COBOLNET2168** for
`USAGE POINTER VALUE NULL`. It keys on the USAGE of the entry and never asks what the literal token IS, so the
figurative-address spelling walks past every other usage. The fix belongs beside the existing screen, on the
LITERAL, and the natural shape is the one `FigurativeConstants.Classify` already provides (PB933 arm 1 made that
the single reader) — ask the classifier whether the operand is the predefined address, and refuse it wherever
§8.4.3.10.3 SR1 a) does not list a VALUE clause, i.e. everywhere.

## The sibling sweep the fixer owes

CLAUDE.md rule 4 — every bug is a pattern. The question "does this screen ask about the literal or only about the
subject?" applies to the **other** predefined-reference spellings the same table admits. Sweep at minimum:

* `VALUE NULL` on every usage the entry can carry (DISPLAY, COMP, NATIONAL, BIT, INDEX, OBJECT REFERENCE) — three
  of those are PB515's population and must agree with it rather than double-report.
* the other §8.4.3 predefined references (`SELF`, `SUPER`, `EXCEPTION-OBJECT`, `NULL` as an object reference) in a
  VALUE clause, each of which has its own enumerating syntax rule in §8.4.3.
* the condition-name (Format 3) and REPORT SECTION (Format 4) VALUE positions, which are the two writing
  positions **PB921** proved a single-arm screen misses.
