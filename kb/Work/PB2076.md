# PB2076 — the RETURNING match is a class test, not the MOVE/SET validity §9.3.6 rules 6/7 ask

Found by the train 1021 review of cluster D (finding 3); verified 2026-10-05 on `43fd36bd8` (train1021 tree).
Pre-existing: base `17924fbb4` had the same class test (`OoConformance.ReturningMatchClass`), which
`ActivationRelations.ReturningMatches` re-expressed.

## Spec

- §9.3.6 7) (cite.py OK): "If the invocation specifies a returning item and the returning item is not usage OBJECT
  REFERENCE, POINTER or INDEX, there shall be a corresponding specification in the invoked method that may be a
  sending item in a MOVE statement with the returning item as the receiving item." 6) is the SET twin.
- §14.9.25.3 10) (OK) and Table 16: Numeric Noninteger -> Alphanumeric is "No"; Numeric -> Boolean is "No"; SR2 (a
  strong group receiver needs a same-type group), SR8 (binary-char/short/long/double sender needs a numeric or
  numeric-edited receiver) and SR9 (variable-length groups compatible) are part of "may be a sending item in a MOVE".
- §9.3.6 6) (OK): no matching method anywhere up the INHERITS chain -> EC-OO-METHOD.

## Repro

returning `PIC 9V99` into a `PIC X(4)` and into a `PIC 1(4)` receiver. Expected `HANDLED=EC-OO-METHOD` twice; actual

## Code site

`src/Cobol.Net.Runtime/Control/ActivationRelations.cs` `ReturningMatches` / `SetClass` (L131-141): only the SET-class
string is compared. The compiler's Table 16 lives in `src/Cobol.Net.Compiler/Binding/MoveTable16.cs`
(`Table16Operand`, `MoveRule`), which the runtime cannot reference.

## Why it is not a train-sized fix

The question needs Table 16 (plus SR2/SR8/SR9) at RUN TIME, between two descriptions compiled independently. Doing it
right is a second mechanism: either move the Table-16 matrix (the category x category validity, the integer/noninteger
split and the source-shape rules) into the runtime so the compiler's `MoveTable16` and `ActivationRelations` read ONE
table, with the `ActivationDescription` carrying the `Table16Operand` axes (category, alphabetic, edited, noninteger,
binary-fixed-width), or carry a compile-time-derived validity class per description and a drift test pinning it to
`MoveTable16`. Either is a restructure of where the MOVE-validity rule lives (CLAUDE.md rule 5: one rule in one
place), not a one-arm fix. Sibling to check in the same change: rule 6's SET arm (an index returning item into a
pointer receiver, a program-pointer into a data-pointer) — SetClass already separates those categories, so verify it
against §14.9.39.3 rather than assume.
