# PB77 — LANDED 2026-08-18 — `MOVE FUNCTION NUMVAL-F("5E+30") TO PIC V9(9)` stored 884105727; the float family's MOVE did the same past 1.7×10³⁸

> ⚙ **flags:** wrong-answer, silent, RARE (needs a sending value ≥ 1.7×10^(38 − receiver scale)) · found
> 2026-08-17 while landing PB60's native NUMVAL-F row.

**Measured repro** (`--std 2023`, native): `MOVE FUNCTION NUMVAL-F("5E+30") TO V9` with `01 V9 PIC V9(9)` →
`884105727`; `… TO X5` with `01 X5 PIC 9(5)` → `03715`. Both are the low-order digits of `Int128.MaxValue`
(170141183460469231731687303715884105727), not of the value. §14.9.25.4 GR6 / §14.6.8: a MOVE aligns by
decimal point and truncates — the low-order digits of 5×10³⁰ at either scale are all zero, so the correct
stores are `000000000` and `00000`.

**Mechanism:** the sender lands at the receiver's scale through a SATURATING rescale — `CobolIntrinsics.Rescaled`
(the NUMVAL-F Int128 route a MOVE sender takes, `ReceiverContext.MoveSender`) and `CobolFloat.ToScaled` (the
float family's route: `MOVE FUNCTION EXP10(40) TO X5` takes it) both clamp to `Int128.MaxValue` past the
carrier — and the MOVE store then keeps `v % 10^Digits`, i.e. the SENTINEL's low digits. PB13's argument
("a saturated value still exceeds the receiver's capacity and raises the size error") is true for an
ARITHMETIC store, which has a capacity CHECK; a MOVE has TRUNCATION, and truncation of the sentinel is garbage.
**Landed (2026-08-18, DEVLOG 1310):** the root cause was ONE landing form for TWO landings — the raise-shaped
saturation (PB13, correct for a store whose capacity check RAISES) used by a truncating store too. Every carrier now
has the two forms the SDIDI carrier already had (PB74's `CobolDec.ToUnscaledChecked` / `ToUnscaled`), chosen by the
LANDING: checked (ON SIZE ERROR / EC-SIZE, and every intermediate consumer) saturates; unchecked (MOVE — §14.6.8.2
r4; the no-phrase arithmetic store — §14.6.13.1.3 item 8, CONFORMANCE.md item 70; INVOKE BY CONTENT) keeps the
LOW-ORDER digits. Native exact family: `CobolIntrinsics.Rescaled(…, checkedLanding)` — the unchecked arm is
`CobolNum.RescaleStoreCap`; NUMVAL / NUMVAL-C / NUMVAL-F carry the flag. Float family: `CobolFloat.ToScaled`
(checked) / `ToScaledUnchecked` (unchecked; one `RoundScaled` inside the carrier, `LowOrderDigits` — the double's
exact ±m·2^e expansion rounded by the ONE `CobolNum.RoundDiv` kernel over BigInteger — past it) and
`CobolIntrinsics.FromDouble(…, checkedLanding)`. The emitter NAMES the landing everywhere: `RuntimeApi.FloatToScaled`
takes `bool checkedLanding` with no default; `NumericRenderer.StoreArgs(…, checkedLanding)` from `ecState.SizeErrVar`
(arithmetic — the edited-receiver `Aligned(checkedPath)` Real arm had ignored its own flag) or `false` (`StoreExpr`:
MOVE, INVOKE); the quantizer / NUMVAL renders carry the ONE `NumericRenderer.CheckedFlag`. Measured (golden
`pb77_move_past_the_carrier`, sixteen rows, every value derived by exact arithmetic): NUMVAL-F("5E+30") → V9(9)
000000000, 9(5) 00000; NUMVAL-F("-1234567890123456789012345678901E+3") → S9(5) -01000; NUMVAL's 31-digit
significand → 78901; a COMP-2 1.0E+40 → 90752 / 000000000 / 0000000303786028427003666890752 / ZZZZ9 90752; a
COMP-2 -2.5E+40 → -73792; the same values through no-phrase COMPUTE (including `FUNCTION ABS` of the COMP-2, i.e.
`FromDouble`'s unchecked form, and an edited receiver); and under ON SIZE ERROR all three still fire with the receiver
left alone. `CarrierLandingFormTests` (22) pins the kernels and greps the sites. Verdicts GR-14.6.8.2-{1,2,4} and
GR-14.6.13.1.3-8 → CONFORMS (GAP 4015 → 4011). The item-92 second row is a legitimate second row (the A.1 audit
allows several rows per item), not a numbering defect. **Not moved:** the in-carrier float→fixed manner (the binary64
product's own rounding — 8.2 → 8.2, 1.15 → 1.14) is now documented on CONFORMANCE.md §3 and its exact-vs-shortest
question is [[PB90]].

**Original fix shape:** the MOVE landing needs the exact low-order digits, never a sentinel — a store-cap rescale (the
`CobolNum.RescaleStoreCap` discipline: drop the digits above 38 BEFORE the multiply) for the exact route, and
for the binary64 route the low digits of the double's exact decimal expansion at the receiver's scale (or a
documented item-92 determination that an out-of-carrier float MOVE stores zeros — decide, record on
CONFORMANCE.md, then implement; survey GnuCOBOL first, follow-GnuCOBOL on split latitude).
