# PB5885 landing

`BoundStores.StoresInto`, the one answer to "what does this statement store into" that `ReportWriterBinder.CheckControlDataStores`
asks of every statement of a USE BEFORE REPORTING procedure, now counts the stores an input-output statement makes through its file
connector without naming the item. Its caller passes `PlaceBuilder.ConnectorStores`, which places them by `FileConnectorStore`
(record area, FILE STATUS, RELATIVE KEY, DEPENDING ON), and each I-O arm of the visitor says which its verb makes: READ (both
organizations) the record area of every record description of the file and of a SAME RECORD AREA file (§2023:14.9.30.4 GR13),
the FILE STATUS item (§2023:9.1.13.1, §2023:12.4.5.8.4 GR1), the RELATIVE KEY item (§2023:14.9.30.4 GR25) and the DEPENDING ON item
(§2023:13.18.43.4 GR15); RETURN the record area (§2023:14.9.34.4 GR3) and the DEPENDING ON item; OPEN, CLOSE, WRITE, REWRITE,
DELETE, DELETE FILE, START and UNLOCK the FILE STATUS item; a sequential-access WRITE of a relative file the RELATIVE KEY item
(§2023:14.9.51.4 GR29 a)); SORT and MERGE what their implicit READ of each USING file and as-if WRITE of each GIVING file store
(§2023:14.9.40.4 GR9). The property-temp query (`StoreKindOf`) and the debug query (`DirectStoreOf`) pass no connector: an item
the statement does not name is no property temp and no operand the statement explicitly references.

The note's sweep: RECEIVE, ACCEPT, STRING, UNSTRING, INSPECT, SEARCH, PERFORM VARYING, SET and INITIALIZE already classified every
receiver they store (no change). A CALL BY REFERENCE argument stays uncounted: whether the called program alters it is not known
from the source element, so the rule refuses only the certain stores.
