# PB4530 — relative-read-previous-skips-records: RELATIVE file: consecutive READ PREVIOUS skip records (5, 4, 1 instead of 5, 4, 3, 2, 1)

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

On a RELATIVE file in dynamic access, consecutive `READ ... PREVIOUS RECORD` statements skip records. With records 1
to 5 present and record 5 just read, the first READ PREVIOUS returns record 4 (correct), the second returns record 1
(records 3 and 2 are skipped), and the third reports at end. ISO selects the nearest existing record whose relative
record number is less than the file position indicator each time: 4, 3, 2, 1, then at end.

## Minimal test case

Free reference format (`-free`).
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. RELPREV.
ENVIRONMENT DIVISION.
INPUT-OUTPUT SECTION.
FILE-CONTROL.
    SELECT F ASSIGN TO "relprev.dat"
        ORGANIZATION IS RELATIVE
        ACCESS MODE IS DYNAMIC
        RELATIVE KEY IS RK
        FILE STATUS IS ST.
DATA DIVISION.
FILE SECTION.
FD F.
01 R PIC 9.
WORKING-STORAGE SECTION.
01 RK PIC 9.
01 ST PIC XX.
PROCEDURE DIVISION.
    OPEN OUTPUT F
    PERFORM VARYING RK FROM 1 BY 1 UNTIL RK > 5
        MOVE RK TO R
        WRITE R
    END-PERFORM
    CLOSE F
    OPEN INPUT F
    MOVE 5 TO RK
    READ F RECORD
    DISPLAY "KEY 5 " R " " ST
    PERFORM 5 TIMES
        READ F PREVIOUS RECORD
            AT END DISPLAY "PREV AT END " ST
            NOT AT END DISPLAY "PREV " R " KEY " RK " " ST
        END-READ
    END-PERFORM
    CLOSE F
    STOP RUN.
```

## Environment

cobc (GnuCOBOL) 3.2.0 on WSL2 Ubuntu. `cobc -x -free -std=cobol2014 -o p prog.cob && ./p`, run in an empty directory.

## Observed result

Exit code 0:
```
KEY 5 5 00
PREV 4 KEY 4 00
PREV 1 KEY 1 00
PREV AT END 10
```
The PERFORM runs READ PREVIOUS five times; the third execution reaches at end, and the fourth and fifth follow an
unsuccessful READ, so they are unsuccessful with status 46 and run neither phrase (§2023:14.9.30.4 21), as expected).

## Expected result (per ISO)

§2023:14.9.30.4 21) c), for a relative file: "If the file position indicator was established by a prior successful READ
statement, the first existing record in the physical file whose relative key number is greater than the file position
indicator if NEXT is specified or implied or is less than the file position indicator if PREVIOUS is specified is
selected." §2023:14.9.30.4 21) f): "If a record is made available, the file position indicator is set to the relative
record number of the record made available." So each READ PREVIOUS makes available the nearest existing record below
the last one read (the same "first ... in the reading direction" wording that makes READ NEXT return the nearest
record above), and the at end condition exists once no record precedes it (§2023:14.9.30.4 21), status '10'). The PREVIOUS
phrase is in the 2014 edition (since 2002). Expected output:
```
KEY 5 5 00
PREV 4 KEY 4 00
PREV 3 KEY 3 00
PREV 2 KEY 2 00
PREV 1 KEY 1 00
PREV AT END 10
```

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`) compiles it with no diagnostic and prints the expected
six lines, exit 0.

## Fix site

libcob/fileio.c, `relative_read_next`, the `COB_READ_PREVIOUS` arm (read in the GnuCOBOL 3.2 source): before
scanning it steps the file offset back by `relsize * 2`, and after a record is made available the `moveback` step
moves the offset back by a further `relsize`, so the next READ PREVIOUS starts its own `relsize * 2` step one slot too
low and skips records (the skip-empty-slot loop also steps by `relsize * 2`). After the random READ of record 5 the
offset is at the end of record 5; the first READ PREVIOUS reads record 4 and leaves the offset at the start of record
3, and the second steps back two slots from there, to record 1.

## Further witness (2026-11-04)

The vetting of PB4595 found a second symptom of the same READ PREVIOUS offset. In sequential access, READ NEXT three times and then READ PREVIOUS gives R002; a following `REWRITE` of "XXXX" returns status 00, yet it writes XXXX over slot 1's size word at byte 0, so R002 is unchanged. §2023:14.9.35.4 5) (checked with `cite.py --check`) says "the operating environment logically replaces the record that was accessed by the READ statement", so R002 should be replaced. The cause is the READ PREVIOUS moveback offset, as in this note. Probe: `~/gc-notes/PB4595/relrwp.cob` (WSL). WiseOwl is correct.
