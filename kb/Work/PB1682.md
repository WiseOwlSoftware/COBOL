# PB1682 — OPEN

Filed 2026-09-28 by the train-69 lander's review (lander-train-brief step 5b) of the wave-69 Y finisher's PB1427
NULL operand model. Pre-existing (main's compiler at 99731d52c gives the same 1634), not introduced by the train:
PB1427 moved NULL off `figurativeConstant` onto its own `predefinedNull` arm of `nonNumericLiteral`, and this
classifier still reads the whole `nonNumericLiteral` node as a literal.

**What happens.**

```
       01 P USAGE POINTER.
       ...
           EVALUATE NULL
             WHEN "A" DISPLAY "A"
             WHEN OTHER DISPLAY "O"
           END-EVALUATE
```

→ `COBOLNET1634: the selection subject is a literal and the selection object '"A"' is a literal; ISO §14.9.13.3
SR10 Table 15 marks that combination invalid` plus the correct `COBOLNET0869` (§8.8.4.2.3 SR5). The first is a
false reason: the subject is an identifier. The source is still refused; a legal pairing (`EVALUATE NULL WHEN P`
with P a pointer) compiles and runs correctly (EQ), so no legal source is lost today.

**Rule.** §8.4.3.1.2 Format 8 makes NULL an identifier (predefined-address); §14.9.13.3 SR10 Table 15 classifies
subjects/objects by identifier / literal / expression.

**Code site.** `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs#OperandKindOf` (~l.376:
`if (vo.nonNumericLiteral() is not null) return EvaluateObjectOperand.Literal;`) — it should answer Identifier for
`vo.nonNumericLiteral().predefinedNull()`. `PredefinedNullContextDriftTests`' "every literal decoder decides
predefinedNull" fact does not cover this classifier (it keys on decoders that read the figurative arm); extend it.
