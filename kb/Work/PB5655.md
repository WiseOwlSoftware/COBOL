# PB5655 - 2014 default intermediate rounding of the compile-time standard-decimal mode

**The lead (PB5575 report).** "2014 default intermediate rounding (§2014:D.16.1 says truncation; compiler uses away-from-zero):
CompileTimeArithmetic.cs StandardDecimalMode.Rounding; belongs to a 2014 adoption note." No 2014 adoption note exists in `kb/Work` (grep of open notes for
D.16, NearestAwayFromZero and StandardDecimalMode, 2026-11-15), and PB5575 is about the 2002 mode, so the 2014 lead is filed here, beside it.

**What the spec says (every quotation run through `cite.py --check`, verdict OK).**
- Informative, `§2014:D.16.1`: "If the INTERMEDIATE ROUNDING clause is not specified, INTERMEDIATE ROUNDING IS TRUNCATION is implied." (and the paragraph
  before it, "This default is unchanged in this International Standard, and is also the default for standard-binary and standard-decimal arithmetic").
  Annex D of 2014 is a list of changes from the previous edition, not a rule.
- Normative, `§2014:11.9.9.2 GR4` ("If standard-decimal arithmetic is in effect") `a)`: "If the INTERMEDIATE ROUNDING clause is not specified, the
  NEAREST-AWAY-FROM-ZERO phrase is implied." (verdict OK at GR4a, label mode: 2014 has no rule catalog). The 2023 text, `§2023:11.9.11.2 GR3` a), prints
  the same, and it is the citation `CompileTimeArithmetic.StandardDecimal`'s summary carries.
- The two intermediate-rounding rule clauses `§2014:8.8.1.3.1.3.1` ("If INTERMEDIATE ROUNDING IS NEAREST-AWAY-FROM-ZERO is specified or implied, a standard
  intermediate data item shall be rounded to 31 digits ...") and `§2014:8.8.1.3.1.3.4` (the same for TRUNCATION, "specified or implied") both say "or
  implied", which is the 2014 text's own tension; 2014 also rounds to 31 digits there where the mode keeps 34 (the report's PB5575 finisher R1-2 note records
  "2014 (34 digits, away-from-zero)").

**Reading (a clerk's, for the adjudicator to confirm or overturn).** The normative GR4 a) controls over the informative annex (CLAUDE.md rule 1: the spec
controls; an Annex D summary that disagrees with the rule it summarises is the defect, which would be a lead for `docs/` only, since the standard's text is not
ours to correct). If the adjudicator confirms, the compiler is right, this note closes with no code change except the missing 2014 citation in the summary
of `CompileTimeArithmetic.StandardDecimal` (it cites 2023 only for a mode it runs at 2014) and a line in `docs/conformance/` recording the choice, so the
next reader does not reopen it. If the adjudicator finds 8.8.1.3.1.3.4's "implied" TRUNCATION (31 digits) controls for the 2014 compile-time arithmetic, the
change is `StandardDecimalMode.Rounding` (a constant) and its `Enter`/`Apply` arms, with a golden at `--std 2014`.

**Sites:**
- `src/WiseOwl.Cobol.Frontend/Expressions/CompileTimeArithmetic.cs` (`CompileTimeArithmetic.StandardDecimal`, `CompileTimeArithmetic.StandardDecimalMode.Rounding`)

**Sibling sweep.** Every other place the standard-decimal default rounding is chosen at 2014 (the run-time `ARITHMETIC IS STANDARD-DECIMAL` engine's
default intermediate rounding, the OPTIONS paragraph's INTERMEDIATE ROUNDING default): they must agree with whatever the adjudicator decides, and the
2014 edition's own text (not 2023's) is what the 2014 compiler stands on.
