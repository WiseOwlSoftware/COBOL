# PB442 — what these three rows are missing is EVIDENCE, not a fix

⚠ **This is an `analysis` note on purpose.** None of the three rows carries a measured wrong answer. Each is
PARTIAL because an obligation the rule states cannot be shown to hold on this tree: an unverified edge the
implementation itself labels staged, a scope word applied two ways with nothing written down, and two table
cells whose receiver the compiler refuses outright. A fixer cannot act on any of them until an owner or a
determination settles what the answer should be — which is precisely why they are recorded here rather than
inside another note's prose.

## 1. GR17 — one scope word, two readings, both implemented

**THE MECHANISM.** GR17's own scope is "during the execution of imperative-statement-1". §14.6.13.1.4 item 2 and
§14.6.13.1.3 item 4 phrase the same gate LEXICALLY, as does GR15, and GR14's implicit TURN is a DIRECTIVE
spliced into imp-1's TEXT. The implementation applies BOTH readings, inconsistently:

* a raise inside a paragraph reached by an OUT-OF-LINE PERFORM issued from imp-1 **is** intercepted by the WHEN
  (a dynamic reading);
* a raise inside a CALLed element is **not** (a lexical/activation reading, via
  `ExceptionState.TrimPerformTo`, `src/Cobol.Net.Runtime/Exceptions/ExceptionState.cs:784-788`, whose
  doc-comment calls the cross-activation reading "a documented STAGED item", and
  `src/Cobol.Net.Runtime/Control/ProgramTable.cs:260-262`, which snapshots and trims the frame depth at every
  activation boundary).

Neither branch is pinned by a test and neither is published in `docs/CONFORMANCE.md`.

**THE RULE, QUOTED, WITH ITS `--check` LINES.**

    python scripts/spec/cite.py --check 14.9.28.4 "If during the execution of imperative-statement-1 an exception condition associated with a WHEN phrase is raised"
    OK  §14.9.28.4 17)  (General rules)

    python scripts/spec/cite.py --check 14.9.28.4 "Any USE declarative that would normally match the exception condition is ignored"
    OK  §14.9.28.4 17)  (General rules)

    python scripts/spec/cite.py --check 14.6.13.1.4 "the executed statement is within imperative-statement-1"
    OK  §14.6.13.1.4 2)  (Nonfatal exception conditions)

**MEASURED ON HEAD (89044aa0), `--std 2023` — the two readings side by side:**

    (dynamic) PERFORM  DISPLAY "IMP1-HEAD"  PERFORM SUBP  DISPLAY "IMP1-TAIL"
              WHEN EC-USER-DEMO  DISPLAY "WHEN"  END-PERFORM …
              SUBP.  DISPLAY "IN-SUBP"  RAISE EXCEPTION EC-USER-DEMO  DISPLAY "SUBP-AFTER".
    $ cobol.exe .../gr17_ool_from_imp1_turn.cob --std 2023 --run     (with >>TURN EC-ALL CHECKING ON)
    exit 0
    IMP1-HEAD / IN-SUBP / WHEN / SUBP-AFTER / IMP1-TAIL / DONE      <- the WHEN DID intercept

    (lexical) PERFORM  CALL "F3CALE"  DISPLAY "AFTER-CALL"
              WHEN EC-USER-DEMO  DISPLAY "WHEN-IN-CALLER"  END-PERFORM …
              (F3CALE raises EC-USER-DEMO)
    $ cobol.exe .../gr17_cross_call.cob --std 2023 --run
    exit 0
    IN-CALLEE / CALLEE-AFTER-RAISE / AFTER-CALL / DONE              <- the WHEN did NOT intercept

I also re-ran the no-`>>TURN` variant on HEAD (`gr17_ool_from_imp1_noturn`: IMP1-HEAD / IN-SUBP / SUBP-AFTER /
IMP1-TAIL / DONE — the WHEN does not fire, because GR14's implicit TURN is keyed to imp-1's textual extent and
SUBP's lines are outside it). That third measurement is worth recording on its own: the WHEN's reach depends on
whether checking happens to be enabled at the raise site, which is a THIRD axis on top of the two readings.

**WHAT IS ESTABLISHED AND WHAT IS NOT.** The tier machinery and the "USE declarative is ignored" half hold — the
raise-site funnel consults the frame stack first and only falls to the USE tiers when no frame matched, and
`ControlFlowEmitter.ClassifyOperand`'s tiers 0..6 are a faithful rendering of the USE statement's own match
hierarchy, sorted by tier then source order. What is NOT settled is the scope word. ⛔ The adjudicator justified
the CALL behaviour by quoting the LEXICAL wording of §14.6.13.1.4 item 2 and then dismissed the code's own
staged-item comment as "an overstatement" — but that same lexical wording contradicts the OUT-OF-LINE behaviour
the compiler actually has. **A rule whose scope is decided two different ways in one implementation, with no
determination and no test, is PARTIAL.**

**WHAT WOULD CLOSE IT:** an owner determination naming ONE reading, published in `docs/CONFORMANCE.md`, plus two
spec-derived goldens — the out-of-line-from-imp-1 case and the cross-CALL case — pinning it. If the lexical
reading is chosen, the out-of-line behaviour must change; if the dynamic one, `TrimPerformTo`'s trim must go and
the staged-item comment with it.

## 2. GR1 — the range boundary at an ACTIVATION boundary

**THE MECHANISM.** GR1's second sentence puts a CALLed element's statements in the range — a CALL is a transfer
of control in the range — and the ONLY carve-out the sentence states is an EXIT PROGRAM or GOBACK in the SAME
INSTANCE OF THE SAME SOURCE ELEMENT as the PERFORM. `TrimPerformTo` deliberately narrows that at every activation
boundary, and its own doc-comment names THIS rule as a staged item.

    python scripts/spec/cite.py --check 14.9.28.4 "The range includes all statements that are executed as the result of a transfer of control in the range of the PERFORM statement"
    OK  §14.9.28.4 1)  (General rules)

    python scripts/spec/cite.py --check 14.9.28.4 "except for statements executed as the result of a transfer of control by an EXIT PROGRAM or GOBACK statement specified in the same instance of the same source element"
    OK  §14.9.28.4 1)  (General rules)

**WHAT IS ESTABLISHED.** The four sentences the adjudicator probed do hold as measured (a non-consecutive
statement reached by GO TO stays in the range and the return still happens at the exit paragraph; a declarative
executed as a result of a statement in the range runs and returns INTO the range; GOBACK and EXIT PROGRAM
exclusions both behave). ⚠ **The adjudicator's `gr1_exit_program_in_range` probe does not reach the open edge:**
its PERFORM and its EXIT PROGRAM are both in the CALLEE, i.e. the same source element — the sentence's
CARVE-OUT, not its cross-activation case. I re-read that probe's source on this tree and confirm it.

**WHAT IS NOT.** The cross-activation "in range" reading is unverified and the implementation labels it staged.
No wrong answer is charged here — the observable consequence is charged to GR17 in §1, and this row's PARTIAL is
the evidence-burden downgrade of the same open reading. **The two rows close together or not at all**, which is
why they are one note.

## 3. GR-14.9.25.4-7 — two of Table 17's cells have no reachable receiver

**THE MECHANISM.** The rule makes a figurative constant's category depend on the RECEIVING operand's category,
and that structure IS the implemented one (`FigurativeConstants.FillChar`'s
`bool pinned = cat is PicCategory.National or PicCategory.Boolean` steers HIGH-/LOW-VALUE away from the
alphanumeric program collating sequence to the category's own sequence; `MoveEmitter.ConvertSource` passes the
receiver's category in).

    python scripts/spec/cite.py --check 14.9.25.4 "Table 17"
    OK  §14.9.25.4 7)  (General rules)
        7) Alphanumeric, boolean, national, and numeric literals belong to the categories alphanumeric, boolean,
           national, and numeric, respectively. The category of figurative constants when used in the MOVE
           statement depends …

**NOT VERIFIABLE, TWO WAYS — re-measured on HEAD:**

    01 NEN PIC ZZ9 USAGE NATIONAL.   01 NED PIC ZZ9.
    MOVE HIGH-VALUE TO NEN … MOVE HIGH-VALUE TO NED …

    $ cobol.exe .../gr7_numed_national.cob --std 2023 --run
    exit 70
    error COBOLNET0899: national-form numeric data (a numeric or numeric-edited PICTURE ZZ9 with USAGE NATIONAL
    - national digits) is recognized but not yet implemented (Phase 4a residue) - data item 'NEN'
    error COBOLNET0902: MOVE of an alphanumeric figurative constant (SPACE/HIGH-VALUE/LOW-VALUE/non-digit ALL)
    to a numeric or numeric-edited item was removed in COBOL-2023 … - MOVE HIGH-VALUE TO NEN
    error COBOLNET0902: … - MOVE HIGH-VALUE TO NED

1. The HIGH-VALUE / LOW-VALUE / QUOTE row's usage-qualified lines require a NUMERIC-EDITED receiver of usage
   NATIONAL, and that receiver is refused outright by `COBOLNET0899` (staged residue). `FillChar`'s `pinned` test
   admits only National and Boolean PICTURE categories, so even if the receiver existed, a numeric-edited item of
   usage national would take the ALPHANUMERIC extreme where the table makes the figurative NATIONAL — **the row
   has no code behind it either way.**
2. That row's Numeric and Numeric-edited cells are reachable only BELOW 2023, since §14.9.25.3 SR5 removed the
   move at 2023 (`COBOLNET0902`, firing above); their pre-removal fill is a provisional character-image deposit
   that no spec-derived test pins.

Three of the table's four blocks ARE verified (the ALL literal-1 rows by
`conformance:2023/pb71_all_national_boolean_figurative`, which computes its expectations from the rule rather
than an oracle; the SPACE/ZERO row's Boolean and National cells; the HIGH-VALUE row's National cell). ⚠ The
category dispatch itself is established by READING `FillChar`, not by measurement, because a NATIONAL HIGH-VALUE
and an ALPHANUMERIC one cannot be separated by VALUE — determination D-N3 pins both to the same code point. That
is a second, independent reason this row is PARTIAL rather than CONFORMS.

**WHAT WOULD CLOSE IT:** landing national-form numeric data (the `COBOLNET0899` residue) makes cell (1)
measurable; a below-2023 golden makes cell (2) measurable; and a probe that separates the two HIGH-VALUE
categories by something other than value — a comparison under a non-native program collating sequence — would
retire the reading-not-measuring caveat.
