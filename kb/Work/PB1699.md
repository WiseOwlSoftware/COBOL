# PB1699 — OPEN

**Owner, 2026-09-28 ~10:20–10:25 PDT:** "Keep the skills in the skills repo up to date with our latest processing.
LinkedIn readers have a link to that repo and may examine it at anytime." Then: "Plus we should be self-hosting the
skills, where applicable."

## The defect

Each generic practice is written twice today: once in this repo's `.claude/skills/*`, and once, generalized, in the
public `brent-tools` plugin. The public copy is reached only through a prose "Generic base:" pointer, and the plugin is
not installed here. The earlier reason not to install it, a collision between its `review` and ours, does not hold:
plugin skills are namespaced (`brent-tools:review`).

So every improvement made here has to be hand-ported, and public v1.6.0 was already missing DEVLOG 1746's authorization
arg and DEVLOG 1749's stamped handoff. That is CLAUDE.md rule 5's "hand-maintained list where a structure belongs",
across two repos.

## The fix (design)

1. **Enable the plugin at project scope.** `.claude/settings.json` gets `extraKnownMarketplaces` (GitHub
   BrentRector/claude-skills) and `enabledPlugins: brent-tools@brentrector-claude-skills`, so a fresh clone and cloud
   sessions get it too.
2. **Overlays, not copies.** Each project skill with a public base (workstream → agent-fleet, gate → test-gate,
   review → review, spec-lookup → spec-oracle) opens by invoking its base. It then keeps ONLY what is
   project-specific: commands, paths, kb/Work, push-main, the owner's dated decisions and measurements. Generic text
   that duplicates the base is deleted here, after confirming the base carries it.
3. **One source per generic script.** Where the project script is the public script plus project configuration
   (orient.py, fix_clusters.py, status_delta.py, the rolling-wave workflow), the public repo becomes the source. It is
   brought in as a pinned git submodule, and the project passes only its configuration. The submodule is public, so CI
   needs no credentials. Where a project script has diverged for a project reason, the divergence is documented and a
   drift check compares the shared part.
4. **Drift test.** A check (in `check_practices.py` or CI) fails when a project overlay restates a rule its base
   carries verbatim, or when the pinned submodule is behind the plugin version the settings name.
5. **The loop.** A practice improved here is written into the PUBLIC base first, then consumed. That makes "keep the
   public repo current" automatic rather than a chore.
