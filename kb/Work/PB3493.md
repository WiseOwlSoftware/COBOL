# PB3493 — OPEN OUTPUT re-OPEN releases the kept state before its own handle is taken

Lead R1-1 of the branch review of PB3483 (`E:/COBOL-coord/scratch/reports/w1140d-PB3483-report.md`).

`src/WiseOwl.Cobol.Runtime/IO/KeyedConnector.cs` about line 276: an OPEN OUTPUT re-OPEN releases everything the CLOSE under commit control kept (`Lock(create: true)` -> `ReleaseKept`) BEFORE its own handle and store are taken. An OUTPUT that is then unsuccessful (a third run unit opening in the `HeldByAnotherHandle` window, a refused store creation) leaves the kept state gone and the transaction as a death leaves it, against §14.9.27.4 GR25 (an unsuccessful OPEN leaves the file unaffected). Pre-existing on Linux; PB3483 makes it reachable on Windows by removing the self-refusal: `_kept` is null after `ReleaseKept`, so `RetakeKeptHandle` and `TryRestoreKeptFileLock` become no-ops. `TryRestoreKeptFileLock` also says the OUTPUT created the file anew, which an unsuccessful one did not.

**Fix shape.** Take the OUTPUT's own handle and store first and release the kept state only once the OPEN has succeeded. Witness: a third run unit holds the file during the OUTPUT re-OPEN, and the kept transaction must survive the refusal.

**Sites:**
- `src/WiseOwl.Cobol.Runtime/IO/KeyedConnector.cs`

## Landing

Re-probed on the wave-1141 build (`CommitRollbackRuntimeTests.A_reopen_output_whose_creation_is_refused_keeps_the_kept_state`, both organizations, the
medium refusing the creation at its second write and at its first sync): before the fix the OPEN answered '30' and the kept transaction was gone
(`TransactionOf` 0, expected the CLOSE's id), so another run unit's writable OPEN rolled it back as a death's. Evidence:
`E:/COBOL-coord/scratch/w1141b/probe-baseline-evidence.log`.

**Fix.** `KeyedConnector.Recreate` (reached from `Attach(create: true)` when the connector holds kept state): the new, empty store is made in a
store of its own (`NewStore`, not in the run unit's table) through the OPEN's own handle, beside the kept attachment; `TakeFileLock` no longer
adopts the kept handle for a creation, and `Lock` no longer releases the kept state before it takes the handle. `PagedFile.Create` already undoes a
refused creation, so a refusal leaves the kept transaction, record locks, file lock and handle as the CLOSE left them
(§14.9.27.4 GR25), and `AbandonOpen` runs as for any unsuccessful re-OPEN. A landed creation gives the kept state back (`ReleaseKept`) and registers
the created store (`StoreTable.AttachCreated(host, created)`, `AttachCreated` per organization). The failures that leave the previous file gone are the final
sync's, after the truncation, and a refusal whose undo the medium refused too (review R1-1): `PagedFile.Create` reports `replaced` (`KeyedStore.FileReplaced`), the previous file is gone
and the kept state ends with it. `TryRestoreKeptFileLock`'s comment no longer says an unsuccessful OUTPUT created the file anew.

**Siblings swept (the other arms of "the kept state ends before the OPEN is known to succeed").** `KeyedConnector.ReleaseKept` has four callers: the
registry's COMMIT/ROLLBACK/run-unit end, `Recreate`, and the two absent-OPTIONAL arms of `OpenCore`. The absent OPTIONAL I-O/EXTEND arm released the kept
state inside `Lock(create: true)` before its handle; it now releases after the handle is taken. The absent OPTIONAL INPUT arm (found in the same
file, fixed here, I9) attached beside the kept store without releasing it, so the table entry kept the removed file's store: it releases first now
(`A_reopen_of_an_optional_file_that_vanished_ends_what_the_close_kept`; effective on a host that lets a file be removed while a handle stands, so
Linux; Windows refuses the removal and the case asserts that).

Tests: `A_reopen_output_whose_creation_is_refused_keeps_the_kept_state` (4), `A_reopen_output_whose_final_sync_is_refused_is_restored_by_the_rollback` (its name and its ROLLBACK expectation since kb/Work PB3492)
(2), `A_reopen_output_that_lands_ends_what_the_close_kept` (2), `A_reopen_of_an_optional_file_that_vanished_ends_what_the_close_kept` (4).
