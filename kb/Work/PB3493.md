# PB3493 — OPEN OUTPUT re-OPEN releases the kept state before its own handle is taken

Lead R1-1 of the branch review of PB3483 (`E:/COBOL-coord/scratch/reports/w1140d-PB3483-report.md`).

`src/Cobol.Net.Runtime/IO/KeyedConnector.cs` about line 276: an OPEN OUTPUT re-OPEN releases everything the CLOSE under commit control kept (`Lock(create: true)` -> `ReleaseKept`) BEFORE its own handle and store are taken. An OUTPUT that is then unsuccessful (a third run unit opening in the `HeldByAnotherHandle` window, a refused store creation) leaves the kept state gone and the transaction as a death leaves it, against §14.9.27.4 GR25 (an unsuccessful OPEN leaves the file unaffected). Pre-existing on Linux; PB3483 makes it reachable on Windows by removing the self-refusal: `_kept` is null after `ReleaseKept`, so `RetakeKeptHandle` and `TryRestoreKeptFileLock` become no-ops. `TryRestoreKeptFileLock` also says the OUTPUT created the file anew, which an unsuccessful one did not.

**Fix shape.** Take the OUTPUT's own handle and store first and release the kept state only once the OPEN has succeeded. Witness: a third run unit holds the file during the OUTPUT re-OPEN, and the kept transaction must survive the refusal.
