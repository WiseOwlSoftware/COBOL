# PB232

**Rows:** `GR-14.9.4.4-10`

`ENTRY-CONVENTION` is parsed into OptionsModel and read by nothing but the edition gate, so a program naming a convention this implementation gives no meaning to is silently activated with the COBOL convention.

Row: GR-14.9.4.4-10 ('Control is transferred to the called program in a manner consistent with the entry convention specified for the program.' — `cite.py --check 14.9.4.4` OK, General rules 10, printed under the FORMAT 2 heading).

THE REFERENT, chased and re-validated on the row rather than assumed: §11.9.7.4 GR4c (`cite.py --check 11.9.7.4 "In all other cases, the entry convention is COBOL"` → OK, General rules 4 c); GR2 — when COBOL is specified the naming and mapping of program-names are per §8.3.2.2 and 'other aspects of the entry convention are implementor-defined'; GR3 — an entry-convention-name-1's meaning is implementor-defined; §11.9.7.3 SR1 permits the clause only in a class / function / function-prototype / interface / program-prototype definition or a program definition NOT contained within another program.

WHAT IS RIGHT. On the only reachable Format-2 arm — AS NESTED, since the prototype arm is NOT-IMPLEMENTED — the callee is by SR15 a contained or COMMON program, which §11.9.7.3 SR1 forbids from carrying ENTRY-CONVENTION, so its convention is COBOL by GR4c; and COBOL.NET realizes exactly that with one uniform entry ABI, `ICobolProgram.Call(CobolArg[] args, ManagedPointer? returning)` reached through ProgramTable.CallProgram, with the §8.3.2.2 name mapping case-insensitive via ProgramTable.NameEquals (OrdinalIgnoreCase) and the name trimmed at the call site.

THE DEFECT. An ENTRY-CONVENTION clause that IS written — legally, on an outermost program definition, where SR1 permits it — is parsed, stored into OptionsModel.EntryConvention, and then read by nobody. The program is silently activated with the COBOL convention whatever it asked for. §11.9.7.4 GR3 makes the meaning of entry-convention-name-1 implementor-defined, and the honest posture for a convention this implementation defines no meaning for is a targeted diagnostic naming it, not silence: a silently-ignored calling convention produces a clean compile and a wrong ABI at the boundary. (The row's other half — that the prototype arm, where a program-prototype definition may legitimately declare a foreign convention, does not exist — belongs to the program-prototype-registry note, not this one.)

WHAT WOULD CLOSE IT: consume OptionsModel.EntryConvention — at minimum a targeted COBOLNET diagnostic naming an entry-convention-name-1 for which this implementation defines no meaning (the honest §11.9.7.4 GR3 posture) — plus a docs/CONFORMANCE.md determination recording that COBOL is the only convention realized, with a negative fixture for a named foreign convention and a positive one for an explicit `ENTRY-CONVENTION IS COBOL`.

SPEC REFS as carried by the row: §14.9.4.4 GR10 (cite.py OK); §11.9.7.4 GR2/GR3/GR4c (GR4c cite.py OK); §11.9.7.3 SR1; §8.3.2.2; §14.9.4.3 SR15.

## Mechanism

src/Cobol.Net.Compiler/Binding/OptionsBinder.cs:64 (`return m with { EntryConvention = ec.GetText() };`) into src/Cobol.Net.Compiler/Binding/OptionsModel.cs:30 (`public string? EntryConvention { get; init; }`) — and the ONLY other references anywhere in src/ are src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs:1534-1535 (the 2014 introduction gate) and :1980 (the reserved-word exemption). Nothing in CodeGen or Runtime reads it; the uniform ABI it silently falls back to is src/Cobol.Net.Runtime/Control/CallAbi.cs#ICobolProgram.Call reached through ProgramTable.CallProgram
