# PB712 — OPEN — one printed ADVANCING phrase, two spelled ones

Reported 2026-09-05 by the `PB686` implementer (report, "NEW DEFECT found on the way") as a runtime defect:
`WriteBeforeAndAfter` discards an end-of-page condition raised by the BEFORE advance, because the second
`AdvanceLinageCounter` call resets `EndOfPage` unconditionally. **The premise was validated first, and it does
not hold as filed** — the statement that reproduces it is not a spelling §14.9.51.2 prints. The defect is real
and it is one level up, in the grammar. This note is that defect; the end-of-page loss is recorded here as its
consequence.

## The facts

**What the standard prints.** Rendered off the canonical PDF, not read from the transcription
(`python scripts/spec/clause_page.py 14.9.51.2` → PDF page 815, printed folio 785;
`python scripts/render-spec-page.py 815`). Format 1's advancing phrase is ONE optional bracket:

```
[  { | BEFORE | }  ADVANCING  { { identifier-2 | integer-1 } [ LINE | LINES ]  |  { mnemonic-name-1 | PAGE } }  ]
   { |  AFTER | }
```

The choice indicators — the `|` bars — enclose **only the words BEFORE and AFTER**. `ADVANCING` and the whole
operand group sit OUTSIDE them, inside the single bracket. `cite.py --check 5.2.6.4 "one or more of the
alternatives contained within the choice indicators shall be specified"` → OK: braces + bars means one or more of
the enclosed alternatives, each at most once, in any order. The enclosed alternatives here are two WORDS.
So the format spells `BEFORE ADVANCING 4 LINES`, `AFTER ADVANCING 4 LINES` and `BEFORE AFTER ADVANCING 4 LINES`
(or `AFTER BEFORE …`) — **one `ADVANCING`, one operand**, always.

Three independent confirmations that both words together is the intended reading and that one operand governs
both:

- `cite.py --check 14.9.51.3 "The BEFORE and AFTER phrases shall not both be specified if the PAGE phrase is
  specified"` → `OK §14.9.51.3 17)` — SR17 restricts the combination, which presupposes it.
- `cite.py --check 14.9.51.4 "If the AFTER phrase is used and the BEFORE phrase is also used"` → `OK §14.9.51.4
  25) f)`; GR25 a)–d), the rules both e) and f) defer the advance amount to, read **identifier-2 / integer-1 /
  mnemonic-name-1 / PAGE** — a single operand. Two operands would leave GR25 a)–d) undefined.
- `cite.py --check E.3.3 "BEFORE"` → `OK §E.3.3 2)`: *"**BEFORE and AFTER phrases.** Both BEFORE and AFTER are
  allowed together in WRITE ADVANCING."* — singular, "in WRITE ADVANCING", new at COBOL-2023.

**What the compiler spells.** `src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4:518-529`:

```
writeBeforeAfter   : writeAdvancePhrase writeAdvancePhrase? ;
writeAdvancePhrase : (BEFORE | AFTER) ADVANCING? ( PAGE | (dataReference | integerLiteral | literal) (LINE | LINES)? ) ;
```

That is the whole PHRASE repeated — its own `ADVANCING` and its own operand each time. It is not the printed
format, in either direction.

**Measured** (solution built at `c34f01ad`; `src/Cobol.Net.Cli/bin/Debug/net10.0/cobol.exe`, probes in
`E:\Temp\claude\E--CobolSharp\49b17747-ce58-4386-8c49-ecb2ce644f8d\scratchpad\pb712{a,b,c}.cob`, all `FD LPF
LINAGE IS 4 LINES`):

| probe | statement | `--std 2023` result |
|---|---|---|
| **a** | `WRITE P-REC BEFORE ADVANCING 4 LINES AFTER ADVANCING 0 LINES …` (the PB686 repro; **not** a printed spelling) | compiles and runs → `NO-EOP` / `LC=001` |
| **b** | `WRITE P-REC BEFORE AFTER ADVANCING 4 LINES …` (**the** printed spelling of the combination) | `error COBOL0001: no viable alternative at input 'AFTER'` |
| **c** | legal single `BEFORE ADVANCING 4 LINES` that overflows, then `AFTER ADVANCING 1 LINE` | `EOP-1` / `LC1=001` / `NO-EOP-2` / `LC2=002` — **correct** |

So: the ONE legal spelling of the combination is rejected outright (`rejects_legal_source`), a spelling the
standard does not print is accepted (`under_rejects`), and the end-of-page loss PB686 measured **does not
reproduce with conforming source** (probe c) — it is reachable only through probe a's unspellable form.
Probe a is also correctly edition-gated (`--std 85` → `COBOLNET0900 … requires COBOL-2023 … Annex E.3.3 item 2`),
which is what makes the over-acceptance invisible: the gate proved the *edition* was checked, so the *spelling*
never was.

**The consequence, for the record.** `SequentialConnector.WriteBeforeAndAfter` (`:480-491`) takes
`beforeLines` **and** `afterLines` — two operands, the grammar's shape — and calls `AdvanceLinageCounter` twice;
that method opens with `EndOfPage = false;` (`:188`), so the second call erases the first's verdict.
`cite.py --check 14.9.51.4 "When an end-of-page condition occurs, the WRITE statement is successful"` → `OK
§14.9.51.4 27)`, and GR28 (`--check 14.9.51.4 "the end-of-page condition does not occur, then after execution of
the input-output operation, control is transferred to imperative-statement-2"` → `OK §14.9.51.4 28)`) makes the
NOT branch conditional on the condition not occurring, so an
`AT END-OF-PAGE` branch is skipped where GR27 b) requires it. Under the printed format there is one operand and
one advancing amount, so the two-call path — and this bug with it — cannot arise. Fix the spelling and the
sticky-flag question changes shape rather than needing an answer; do not fix the flag and leave the grammar.

## Why it matters

A conforming COBOL-2023 program that writes `BEFORE AFTER ADVANCING n` — the only spelling Annex E.3.3's new
feature has — is refused with a bare `no viable alternative`, and there is no other way to write it. In the
other direction the compiler defines a private dialect (two ADVANCING operands) that no other implementation
accepts and the standard cannot interpret, and that dialect silently drops an end-of-page condition. Both halves
come from the same root: a general format with CHOICE INDICATORS over two WORDS was transcribed into the grammar
as REPETITION of the whole phrase. This is `feedback_spec_diagrams_render_pdf` and
`feedback_model_the_rule_shape_not_one_case` in one construct — the shape of the rule, not the count of cases.

## The fix shape

Spell the choice-indicator group, not a repetition:

```
writeBeforeAfter : (BEFORE AFTER? | AFTER BEFORE?) ADVANCING? ( PAGE | (dataReference | integerLiteral | literal) (LINE | LINES)? ) ;
```

— one `ADVANCING`, one operand, both words in either order, each at most once (§5.2.6.4). Then the bound node
carries ONE amount plus two booleans, `RuntimeApi`'s `WriteAdvance` descriptor and
`FileRegistry.WriteBeforeAndAfter` (`FileRegistry.cs:395`) lose their second amount, and
`SequentialConnector.WriteBeforeAndAfter` implements GR25 e)/f) over a single operand. SR17 (PAGE excludes the
combination) and the existing 2023 introduction gate both keep working; the gate must key on the pair of words,
not on a second phrase that no longer exists. Goldens: the three printed spellings, both word orders, the SR17
rejection, and the `LINAGE`/end-of-page case probe c already covers — plus a negative pinning
`BEFORE ADVANCING n AFTER ADVANCING m` as the syntax error it is, so the private dialect cannot come back.

## Sweep

Every general format whose figure note says the choice indicators are **enclosed by braces** — 15 of them,
`grep -c "braces enclosing choice indicators" specs/ISO_COBOL.md`, plus this one, whose note is worded
differently (`grep -n "enclosed by \*\*braces\*\*"`). For each, ask the question this one failed: does the
grammar repeat the enclosed WORDS, or does it repeat the whole PHRASE around them? WRITE's sibling groups
(`writeAtEndOfPage`, `writeInvalidKey`) are bracket-with-bars groups and were relaxed correctly on 2026-07-19,
which is the pattern that makes the braces case look already-handled. The mechanical form of this sweep belongs
next to `audit_figure_structure.py`: a figure note that declares choice indicators is a testable claim about the
rule that spells it.
