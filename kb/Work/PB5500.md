# PB5500 - a tree kill that returns before the tree is gone

**Sites:** `scripts/process_job.py` (`ProcessJob.kill`, `_terminate_and_await`, `_hold_members`, `_await`, `_self_test`);
`docs/rearchitecture/DESIGN-test-build-ci.md` (the self-test HANG paragraph).

**What was wrong.** `ProcessJob.kill()` (kb/Work PB5098) was `TerminateJobObject` (POSIX: `killpg(SIGKILL)`) followed by
`popen.wait()` on the ROOT. Both kill calls only request the end; each member then terminates on its own schedule. So kill()
returned as soon as the root was reaped, while an orphaned grandchild could still be running and still hold the handles it
inherited. In the self-test the grandchild inherited the root's stdout, `out2.txt`; the `with ProcessJob` block ended, the
self-test's own file closed, and `TemporaryDirectory` cleanup's unlink met `WinError 32` because the grandchild still had the
file open. The defect is the tool's CONTRACT, not the test's cleanup: every caller that kills a tree and then reads, moves or
deletes its output (gate.py `_captured` and `run_host`, self_tests.py's HANG stop) raced the same way, reading output an
orphan could still be writing.

**Reproduced** (E:\COBOL-coord\scratch\op-20261113\w20262026a\repro.py: a root plus a grandchild that inherits the output
file, kill(), then `os.remove`). Idle host: 0 of 50. Under CPU load (2 x cores busy processes, load.py): 16 of 50, 14 of 40,
12 of 30. A control with no process holding the file: 0 of 40. **Waiting for `alive()` (the job's pid list) to read empty after the
kill was NOT enough: 18 of 50 still held** - Windows drops a process from the job's pid list before it closes that process's
handles, so the pid list cannot be the "gone" signal. (Restart Manager's RmGetList named no holder at the moment of the
failure: the holder was already past the point RM sees.)

**Fix (landed).** kill() returns only once every member is gone, bounded by `KILL_BOUND_S = 30` s, past which it raises
OSError naming the surviving pids. Windows: before `TerminateJobObject`, open a `SYNCHRONIZE | PROCESS_QUERY_LIMITED_INFORMATION`
handle to every listed member (checked with `IsProcessInJob`, so a pid reused outside the job is not held; a failed check
raises), terminate, and `WaitForMultipleObjects` on them (a process object is signaled only after its handle table is run
down); re-read the members and repeat until a pass holds nothing new, so a process started between the hold and the
terminate is caught while it is still listed. POSIX: after reaping the root, wait until `alive()` is empty (a zombie has
closed its descriptors and `alive()` reads it as dead, PB5206). The first fix attempt opened `SYNCHRONIZE` only;
`IsProcessInJob` then failed with access denied and was read as "not a member", so nothing was held and the repro still
failed (58 of 100). That is why a failed `IsProcessInJob` now raises instead of skipping.

**Residual (named, not hidden).** A process a member starts in the instant between the last member read and
`TerminateJobObject`, which the job also drops from its list before the re-read, is not waited on. The window is the length of
one pid-list read; it needs a member forking during its own kill.

**Evidence.** After the fix, the repro under load: 0 of 100; the self-test looped 30 times under load: 0 RED of 30
(loop-after.log). New self-test GREEN on Windows and in WSL. The arm "a member the kill does not end fails kill() loudly,
naming its pid" stubs the kill primitive to end only the root (Windows `_k32.TerminateJobObject`, POSIX `os.killpg`): with the
pre-fix kill() swapped in (oldkill.py) it is RED on both Windows and WSL ("kill() returned with a member still running"), with
the fix GREEN. It asserts on the exception, not on a clock: the survivor never dies, so the 0.5 s bound is reached on any host.
