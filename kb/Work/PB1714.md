# PB1714 — the stall watchdog trusted the scheduler

## Origin

A LinkedIn commenter (2026-09-28) observed that silence-based detection only watches the agents, while the 16-hour
wave-68 outage (PB1703) was the SCHEDULER reporting "running". The owner approved adding the check.

## Defect (the public `agent-fleet/references/stall_watch.py`, ≤ v1.13.0)

- `pending()` treated only `result` as closing an agent. The journal's `failed` record, written when an agent dies on
  an API error, left the agent "pending", so its silence was reported as "waiting on the model". Replaying wave 68
  (`wf_e9a82a33-6b6`) did flag it, but for that wrong reason.
- With every agent finished or failed, nothing was checked at all. A scheduler hung with nothing in flight (PB1703's
  shape, or any future one) was invisible.

## Fix (claude-skills v1.13.1, commit 897b2b5)

- `failed` closes the agent, which is reported as FAILED (dead).
- **IDLE:** when no agent is in flight and no agent transcript has a record newer than `--idle` seconds (default
  600), the watchdog exits 3. Idleness is counted from the agents' own record timestamps (journal records have
  none), and in live mode from the watch's start at the earliest.
- The orchestrator stops the watcher on the workflow's completion notice. Otherwise IDLE is one harmless false
  wake-up.

**Evidence (replayed with `--once`):**
- wave 68: U and Y are FAILED, and IDLE fires;
- the running design workflow `wf_08642598-d3c` (the reviser in flight): not flagged;
- the finished `wf_921daa77-5b7`: IDLE, which is the expected benign case;
- live mode with `--idle 4` on the finished workflow: exits after 5 s, counted from the watch start.

## Landed (2026-09-28)

The owner pushed v1.13.1 to the public repo, and the project pins `tools/claude-skills` at v1.13.1 (DEVLOG 1768).
Orchestrators run the watchdog straight from the pin, with no project copy.
