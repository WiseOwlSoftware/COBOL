# PB400 — the classifier in front of Table 15 answers three questions wrongly

Everything downstream of EVALUATE's classifier is right: the Table-15 matrix is exact and self-checking, the
diagnostic is raised at the correct stage, and the `&&`/`||` composition realizes GR4 b)–d) faithfully. What is
wrong is the classifier itself, in three independent directions, and two of them put a **crash into a program
built from conforming source**.

## 1. Direction A — SR6's boolean reclassification is built on one side only

SR6 is a symmetric pair. a) a TRUE/FALSE **subject** with a one-boolean-character expression **object**
reclassifies the object to condition-2. b) a TRUE/FALSE **object** with a one-boolean-character expression
**subject** reclassifies the subject to condition-1. Arm a) works. Arm b) does not exist:
`EvaluateBinder.SubjectCondition` (`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs:244-267`)
reaches a condition only through `subject.classCondition()` or a level-88 resolved through `ConditionOf` —
neither of which a boolean elementary item can take — so it returns null, the subject stays a value, the TRUE
object binds as a standalone condition, and the emitted program dies at run time. That is the two-arm-dispatch
shape in the two arms the standard itself prints as a) and b) of one rule.

Underneath both sits a deeper absence: the "results in one boolean character" LENGTH test that SR6 turns on is
implemented nowhere, and `EvaluateBinder` says so in its own remark at `ObjectOperandKind`
(`EvaluateBinder.cs:124-131`). Both classifiers therefore return null for any boolean operand
(`EvaluateBinder.cs:105` and `:131`), and because a null on either side suppresses the Table-15 diagnostic
entirely (`ScreenPairing`, `EvaluateBinder.cs:88`), the `Boolean-expression` row of Table 15 is a second
permanently unreachable row. The conservative abstention is the right trade for now and PB47 records it; **arm
b)'s run-time crash is not part of that trade** — it is legal source compiled into a program that cannot run.

## 2. Direction B — a SIGNED sole numeric literal is classified as an arithmetic expression

GR1 settles the literal-vs-expression question outright, and 8.3.3.3.2 rule 2 settles what a signed literal is:

    python scripts/spec/cite.py --check 14.9.13.4 "If an operand of the EVALUATE statement consists of a single literal, that operand is treated as a literal, not as an expression"
      -> OK  §14.9.13.4 1)  (General rules)
    python scripts/spec/cite.py --check 8.3.3.3.2 "A literal shall not contain more than one sign character"
      -> OK  §8.3.3.3.2 2)  (Fixed-point numeric literals)

A sign, if used, is the leftmost character **of the literal** — so `-5` consists of a single literal and GR1
makes it a literal. The compiler classifies it as an ARITHMETIC EXPRESSION on both sides, and the cause is
written down in the code: `OperandKindOf` (`EvaluateBinder.cs:140-146`) reaches
`EvaluateObjectOperand.Literal` only through `ConditionBinder.SoleNumLiteral` → `SolePrimary` →
`SoleOperand.Primary`, whose own doc-comment states that any operator, **unary sign**, or enclosing paren gives
the node more than one child and stops the descent — and justifies that with 8.8.4.7.3 SR2, the
abbreviated-combined-relation reduction. **That is a different question.** For the abbreviated relation a
leading sign is an operator; for GR1 it is part of the literal. One shared helper, two questions, and GR1 gets
the wrong answer. This is the `one_rule_one_place` shape: the extraction is the fix.

Two consequences, both measured, and they point in opposite directions:

- **Non-conforming source is silently accepted.** Table 15's literal × literal cell is blank, and the
  unsigned form is correctly refused — but the signed form is not.
- **Legal source CRASHES at run time.** `EVALUATE WS-A WHEN -5` over `01 WS-A PIC X(2)` is Table-15
  identifier × literal = 'Y', and it dies, because the operand was bound as a computed expression instead of
  the `BoundNumericLiteral` that `BindValueOperand`'s own 8.8.4.2.1 arm exists to produce (a sole numeric
  literal against an alphanumeric operand participates as its WRITTEN character form).

## 3. Direction C — a switch-status condition-name cannot be an EVALUATE selection subject

Table 15 marks subject = Condition × object = TRUE-or-FALSE permissible, and GR3 e) assigns such a subject a
truth value. A **level-88** condition-name in that position compiles and runs. A **switch-status**
condition-name in the identical position is refused. The asymmetry is the proof this is a switch-status hole
and not a general EVALUATE limitation, and it is a two-arm dispatch with one arm fixed:
`EvaluateBinder.ObjectOperandKind` (`EvaluateBinder.cs:134`) routes the OBJECT through
`ConditionBinder.BareOperandAsCondition` — the only helper that recognises a switch-status condition-name —
while `SubjectOperandKind` (`EvaluateBinder.cs:99-112`) asks only `classCondition()` and `SubjectCondition()`
(level-88), so the switch condition falls through to `OperandKindOf` → `Identifier` and Table 15 rejects it.
This is what keeps `GR-14.9.39.4-5` (SET switch → the truth value a condition-name yields) off CONFORMS: there
is legal COBOL in which the effect that rule promises can never be observed.

    python scripts/spec/cite.py --check 14.9.39.4 "The status of each external switch associated with the specified mnemonic-name-1 is modified"
      -> OK  §14.9.39.4 5)  (General rules)
    python scripts/spec/cite.py --check 14.9.13.3 "The permissible combinations of selection subject and selection object operands are indicated in Table 15"
      -> OK  §14.9.13.3 10)  (Syntax rules)
    python scripts/spec/cite.py --check 14.9.13.4 "Any selection subject specified by condition-1 is assigned a truth value according to the rules for evaluating conditional expressions"
      -> OK  §14.9.13.4 3) e)  (General rules)

## 6. The code site and the shape of the repair

- `EvaluateBinder.cs:244-267` — `SubjectCondition`, the missing SR6 b) arm.
- `EvaluateBinder.cs:99-112` / `:116-134` — `SubjectOperandKind` / `ObjectOperandKind`, the asymmetric pair.
- `EvaluateBinder.cs:105` / `:131` — the two `IsBooleanValueOperand → return null` abstentions.
- `EvaluateBinder.cs:88` — `ScreenPairing`, where a null on either side suppresses the diagnostic.
- `EvaluateBinder.cs:140-146` — `OperandKindOf`, and through it `ConditionBinder.SoleNumLiteral` →
  `SolePrimary` → `SoleOperand.Primary`, the helper answering the wrong question.

**Repair shape, per CLAUDE.md rule 5 — three structural moves, not five `if`s.**
(i) **Split the "sole literal" question from the abbreviated-relation reduction.** `SolePrimary` answers
8.8.4.7.3 SR2's question ("a single data item not enclosed in parentheses") and must keep doing so; GR1 needs a
separate predicate that admits a leading sign. One helper cannot serve both, and the doc-comment on the
existing one already says which question it answers.
(ii) **Make the two classifiers ONE.** `SubjectOperandKind` and `ObjectOperandKind` differ today in which
condition forms they recognise, and every such difference is a Table-15 asymmetry waiting to be found. Extract
a single `ClassifyOperand(kind: subject|object)` that asks the condition question through the *same*
`BareOperandAsCondition` on both sides, then maps to the column/row enum — and pair it with a drift test that
asserts the two sides recognise the same condition forms, so the next condition kind added is automatic.
(iii) **Implement SR6's one-boolean-character length test once**, and let both classifiers consult it; that
retires the two abstentions, makes the `Boolean-expression` row of Table 15 reachable, and removes arm b)'s
crash as a side effect rather than as a special case.

## 7. The sibling sweep the fixer must do

- **`ConditionBinder.ComparisonOperandOf`** takes the same `SoleNumLiteral`/`SolePrimary` descent, so plain
  relation conditions and the VALUE-clause range are siblings of Direction B — check `IF WS-A = -5` over a
  `PIC X` item before assuming the crash is EVALUATE-shaped.
- **Every other consumer of `BareOperandAsCondition`** — the abbreviated-relation path uses it too; ask which
  callers see a switch-status condition-name and which do not.
- **SEARCH ALL's WHEN and the `IF`/`PERFORM UNTIL` condition spine** — a switch-status condition-name is legal
  in all of them; `r5e.cob` shows `PERFORM UNTIL W-OFF` and a bare `IF W-OFF` working, so the hole really is
  the EVALUATE subject alone, but confirm rather than assume.
- **Both Table-15 drift tests** (`EvaluateOperandCombinationsDriftTests`) are over the TABLE, not over the
  CLASSIFIER; whatever replaces the two classifiers needs a test of its own or this note's defect recurs
  invisibly behind a green matrix check.
