# PB4100 — refmod-out-of-range-refused-at-compile-time--checking-on: literal reference-modification out of bounds refused at compile time with EC-BOUND-REF-MOD checking enabled

A lead from patcher B of the PB3838 tier 6 patch drafting (2026-10-30): `refmod_checks` turns a literal ref-mod
out of bounds into a hard error without testing whether EC-BOUND-REF-MOD checking is enabled, the sibling of PB3905
(literal subscript). Unprobed when given; this filing wrote the programs and probed both versions (below). Upstream
status `unreported`. Evidence, outside git on one machine: WSL `~/gc-notes/PB4100/` (sources also in
`E:\Temp\claude\E--COBOL\f044f739-1f07-4182-ae14-c9f6d8bd784b\scratchpad\pb4100\`).

## Summary

A reference modifier whose literal leftmost position or length lies outside the item (`S(5:1)` or `S(3:3)` on
`PIC X(4)`) is legal syntax: the syntax rules require only arithmetic expressions, and a position outside the item is
the run-time exception condition EC-BOUND-REF-MOD (fatal). The standard lets an implementation refuse to produce
executable code for a fatal condition it detects at compile time only when checking for it is not enabled. cobc 3.2.0
and 3.3-dev r5751 refuse the reference ("offset of 'S' out of bounds: 5", "length of 'S' out of bounds: 3", exit 1) also
when checking is enabled by `>>TURN EC-BOUND-REF-MOD CHECKING ON`, `-fec=EC-BOUND-REF-MOD` or `-debug`, where the
standard requires a program whose run terminates abnormally at the reference. Unlike the subscript case (PB3905),
`-frelax-syntax-checks` does not soften the error. With a variable offset (the control) cobc does generate the check and
libcob ends the run, as required.

With checking not enabled the compile-time refusal is implementor latitude (§14.6.13.1.3, the paragraph after rule 8):
the `rmo.cob` plain run below is NOT-A-DEFECT.

## Minimal test case

Free reference format (`-fformat=free`), `rmot.cob` (offset out of bounds):

```cobol
>>TURN EC-BOUND-REF-MOD CHECKING ON
IDENTIFICATION DIVISION.
PROGRAM-ID. RMOT.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 S PIC X(4) VALUE "ABCD".
PROCEDURE DIVISION.
    DISPLAY "[" S(5:1) "]"
    DISPLAY "CONTINUED"
    STOP RUN.
```

`rmlt.cob`: the same with `PROGRAM-ID. RMLT.` and `DISPLAY "[" S(3:3) "]"` (length out of bounds). `rmo.cob` and
`rml.cob`: the two without the directive line. `rmvt.cob` (control): `rmot.cob` with `01 P PIC 9 VALUE 5.` and
`DISPLAY "[" S(P:1) "]"`.

## Expected result (per ISO)

ISO/IEC 1989:2023, each citation checked with `python scripts/spec/cite.py --check` on 2026-10-30:

- §8.4.3.3.3 4) (OK): "Leftmost-position and length shall be arithmetic expressions." No syntax rule bounds their value.
- §8.4.3.3.4 5) b) (OK): "Evaluation of leftmost-position shall result in a positive nonzero integer less than or equal
  to the number of positions in the data item referenced by identifier-1." 5) c) (OK): "The sum of leftmost-position and
  length minus the value one shall be less than or equal to the number of positions in the data item referenced by
  identifier-1." And in 5) (OK): "If the evaluation of leftmost-position or length results in a non-integer value, a
  zero value, or a value that references a position outside the area of identifier-1, the EC-BOUND-REF-MOD exception
  condition is set to exist."
- §14.6.13.1.6, Table 13 (OK): `EC-BOUND-REF-MOD | Fatal | Reference modifier out of bounds`.
- §7.3.25.4 6) (OK): with the ON phrase "checking for the exception condition associated with exception-name-1 is
  enabled for the procedure division statements and procedure division headers that follow in the compilation group".
- §14.6.13.1.3 7) (OK): "If checking for the exception condition is enabled, execution of the run unit is terminated
  abnormally as specified in 14.6.12, Abnormal run unit termination." The paragraph after rule 8) (OK): "If checking is
  not enabled for a fatal exception condition and the exception condition is detected by the compiler, the implementor
  is not required to produce executable code."

With checking enabled the program is legal: it compiles, and its run terminates abnormally at the first DISPLAY before
anything is displayed (§14.6.4 (OK): "Unless otherwise specified, item identification is done for an identifier as the
first step in the evaluation of that identifier and the identifiers within a statement are evaluated in left to right
order as the first operation of the execution of that statement."). The compile-time refusal is permitted only with checking not enabled. A compile-time warning is
not forbidden.

Edition: 2014. The 2009 committee draft that became ISO/IEC 1989:2014 (CD 1.2, `std.txt`) has ref-mod syntax rule 4)
and the general rule "If the evaluation of leftmost-position or length results in a noninteger value or a value that
references a position outside the area of identifier-1, the EC-BOUND-REF-MOD exception condition is set to exist."
(the 2023 text adds "a zero value"; both cases here are outside the area), the compile-time paragraph in the same words,
and, read by word position on the CD PDF (`STD.BK.pdf` page 445; the OCR text is row-shifted and shows "NF"),
`EC-BOUND-REF-MOD Fatal Reference modifier out of bounds`.

## Fix site (GnuCOBOL 3.3-dev r5751 source, read observationally)

- `cobc/typeck.c`, `refmod_checks` (called from `cb_build_identifier`): under "Compile-time check", a literal length
  `< 1` or greater than the item, a literal offset `< 1` or greater than the item, and a literal offset plus length past
  the end each call `cb_error_x` and return, without testing `CB_EXCEPTION_ENABLE (COB_EC_BOUND_REF_MOD)` and without
  a `cb_relaxed_syntax_checks` fallback.
- Under "Run-time check" the same function emits `cob_check_ref_mod_detailed` (with `abend` 1) only when the offset or
  length is not a literal (or the item is UNBOUNDED / ANY LENGTH), so a literal reference never gets the check.
- The 3.2 source has the same structure (`refmod_checks`, `cobc/typeck.c` lines 2388-2514 of the 3.2 tree read here:
  the compile-time check from line 2429, the run-time check under `CB_EXCEPTION_ENABLE (COB_EC_BOUND_REF_MOD)` from
  line 2479).
- The fix inferred: when `CB_EXCEPTION_ENABLE (COB_EC_BOUND_REF_MOD)`, report the literal case as a warning and emit
  the run-time check for it too; keep the error when checking is not enabled. The same shape as the subscript fix
  drafted for PB3905. Not built or tested.

## Draft issue

**Title:** (comment on bugs #1271) Literal reference-modification out of bounds refused at compile time although EC-BOUND-REF-MOD checking is enabled

**Versions:** GnuCOBOL 3.2.0 (Ubuntu `gnucobol3 3.2-4build1`) and 3.3-dev r5751 (CI snapshot 3.3-dev.138 of
2026-10-29), x86_64 Linux.

`rmot.cob` (free format):

```cobol
>>TURN EC-BOUND-REF-MOD CHECKING ON
IDENTIFICATION DIVISION.
PROGRAM-ID. RMOT.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 S PIC X(4) VALUE "ABCD".
PROCEDURE DIVISION.
    DISPLAY "[" S(5:1) "]"
    DISPLAY "CONTINUED"
    STOP RUN.
```

`cobc -std=cobol2014 -fformat=free -x -o rmot rmot.cob`, both versions: `rmot.cob:8: error: offset of 'S' out of
bounds: 5`, exit 1. The same with `S(3:3)` (`error: length of 'S' out of bounds: 3`), with `-fec=EC-BOUND-REF-MOD` or
`-debug` in place of the directive, and with `-frelax-syntax-checks`. With a variable offset (`01 P PIC 9 VALUE 5.`,
`S(P:1)`) the program compiles and libcob stops the run with `offset of 'S' out of bounds: 5, maximum: 4`, as expected.

**Expected:** with checking enabled the program compiles (a warning is fine) and the run ends abnormally at the first
DISPLAY. ISO/IEC 1989:2023 (the 2014 committee draft has the same rules): the syntax rules require only arithmetic
expressions (8.4.3.3.3 rule 4); a position outside the item sets EC-BOUND-REF-MOD (8.4.3.3.4 rule 5), which is fatal
(14.6.13.1.6, Table 13); with checking enabled the run unit is terminated abnormally (14.6.13.1.3 rule 7). The
implementor may decline to produce executable code only "If checking is not enabled for a fatal exception condition
and the exception condition is detected by the compiler" (the paragraph after 14.6.13.1.3 rule 8), so without checking
the current error is fine.

**Where:** `refmod_checks` in `cobc/typeck.c` reports the literal cases with `cb_error_x` before it looks at
`CB_EXCEPTION_ENABLE (COB_EC_BOUND_REF_MOD)`, and its run-time check is emitted only for a non-literal offset or length.
With checking enabled the literal case could be a warning plus the same `cob_check_ref_mod_detailed` call. This is the
reference-modification counterpart of case 2 of this ticket (the literal subscript).
