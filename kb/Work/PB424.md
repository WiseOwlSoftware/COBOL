# PB424 — two live MOVE diagnostics missing from the catalog

## The mechanism

`docs/DIAGNOSTICS.md` pairs each emitted code with its id, descriptor, severity, ISO clause and title. Two codes
that MOVE emits are not in it:

- **COBOLNET0809** — the class-operand error, raised for §14.9.25.3 SR1 when an index data item or an index
  FUNCTION appears as either MOVE operand (`MoveBinder.MoveFigurativeEditionGates`).
- **COBOLNET0819** — the category error, raised for SR7 (a non-boolean figurative into a boolean receiver), SR8
  (the BINARY-CHAR/-SHORT/-LONG/-DOUBLE sender) and SR10 (every Table-16 refusal, via `MoveTable16.Refusal`)
  (`MoveBinder.MoveCategoryLegality`).

This is a GAP in the catalog, not a convention that the 08xx band is undocumented: their immediate neighbours
0801, 0802, 0855, 0869, 0875, 0878, 0881, 0883, 0898 and 0899 are all present. COBOLNET1533 — the SR2 strong-move
rejection — is documented, with its clause and title, which is precisely why a reader consulting the catalog for
this subject sees ONE MOVE row and no hint that MOVE's two workhorse rejections exist.

The user-visible cost is that the two most common MOVE errors this compiler emits cannot be looked up. The
process cost is measured, not hypothetical: the pre-computed dossier handed to the b2 adjudication for this
subject listed exactly one diagnostic, and a reader trusting that section rather than probing would have recorded
a false NOT-IMPLEMENTED on SR1, SR7 or SR8. It is filed against the CATALOG rather than the harvester because the
catalog is the thing that is wrong.

## The obligation

Not a spec obligation in itself — §14.9.25.3 SR1/SR7/SR8/SR10 require the rejection, and the rejection happens.
It is a project-doctrine obligation: CLAUDE.md rule 6, "Keep the docs CURRENT in the same change set … Every doc
except `DEVLOG.md` describes the CURRENT compiler", plus the catalog's own contract, which already pairs
COBOLNET1533 / `strong-move-mismatch` / Error / `ISO §14.9.25.3 SR2` / "MOVE to/from a strongly-typed group
requires a group of the same type." (`docs/DIAGNOSTICS.md:90`).

## The code site and the shape of the repair

- `docs/DIAGNOSTICS.md` — the two rows are absent. Emitting sites:
  `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/MoveBinder.cs#MoveFigurativeEditionGates` (0809, :95 and the
  index-FUNCTION leg) and `#MoveCategoryLegality` (0819, :213, :223, :228, plus `MoveTable16.Refusal`).
- Add both rows in the catalog's existing shape. 0819 carries THREE distinct rules (SR7, SR8, SR10/Table 16), so
  it needs either three descriptor rows or one row whose clause column names all three — write whichever the
  catalog's existing multi-rule codes already do rather than inventing a third convention.

**THE REPAIR THAT MAKES THE NEXT CASE AUTOMATIC** (CLAUDE.md rule 5): a hand-maintained catalog beside a compiler
that emits codes from source WILL drift again — 0809 and 0819 are two of 211, and nothing measured the
difference. The structural fix is a drift test that enumerates the `ctx.Edition.Error("COBOLNET####"` /
`.Warning(` call sites in `src/` and asserts every distinct code appears in `docs/DIAGNOSTICS.md` (and, in the
other direction, that every documented code is still emitted somewhere). Make it FAIL once before trusting it
(memory: `green_gates_arent_evidence`) — deleting one row must turn it red.

## The sibling sweep the fixer must do

Run that enumeration ONCE by hand as part of this fix and document EVERY code it finds missing, not just these
two. The two were found only because one adjudication happened to probe the subject they belong to; the
complement was never measured (memory: `measure_the_selectors_complement`). Sweep both directions — a documented
code no longer emitted is the same drift wearing the other face.
