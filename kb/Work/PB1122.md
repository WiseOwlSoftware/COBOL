# PB1122 — LANDED

## The rule
> "or a fatal exception occurs within the scope of the declarative"
`cite.py --check 14.6.13.1.2 "or a fatal exception occurs within the scope of the declarative"` → `OK  §14.6.13.1.2 1)  (Normal completion of a declarative procedure)`

## Measured (adjudicator / refuter evidence, verbatim)
### GR-14.6.13.1.2-1 (PARTIAL)
|| REFUTED: PARTIAL — Only the statement half holds. Normal completion is decided solely by whether __Dispatch falls off its end (DispatchEmitter.EmitRunUseBody returns -1). Nothing records that a fatal exception occurred within the scope of the declarative. A fatal exception that is handled inside the declarative's scope (a second declarative that RESUMEs AT NEXT STATEMENT) therefore lets the first declarative be treated as completing normally, which contradicts the second half of 14.6.13.1.2 1).
- **Code location (record):** src/Cobol.Net.Compiler/CodeGen/DispatchEmitter.cs#EmitRunUseBody; src/Cobol.Net.Compiler/CodeGen/EcEmitter.cs#EmitArgOrPlain; src/Cobol.Net.Compiler/CodeGen/EcEmitter.cs#EmitRaise

## What the fixer owes
Record 'a fatal exception occurred within this declarative's scope' on the ExceptionState frame the declarative opens, and have DispatchEmitter.EmitRunUseBody return not-normal when it is set, whatever the fall-off. Golden: a USE AFTER EC-USER declarative whose body raises a checked fatal EC handled by a second declarative with RESUME AT NEXT STATEMENT.


## Re-verified 2026-09-30 (exceptions-group research, main `4a1dda60e`) — premise RIGHT, consequence NARROWER

The model gap is real: `DispatchEmitter.EmitRunUseBody` returns `-1` on every fall-off and nothing records a fatal
raise inside a declarative's scope. But the note's implied consequence ("the first declarative is treated as
completing normally" ⇒ a wrong answer at the raise site) holds only where a rule KEYS ON normal completion.
§14.9.49.4 13) b) (`cite.py --check 14.9.49.4 "If the exception condition is fatal, execution continues as specified
in 14.6.12, Abnormal run unit termination"` → OK §14.9.49.4 13) b)) disposes of a fatal condition's Format-3 USE
procedure by FATALITY after it runs, normal or not; 13) a) continues a nonfatal one. MEASURED: `p1122.cob` (nonfatal
EC-USER-A selecting D1; D1's checked subscript fault RESUMEd by D2) prints `D1-START / D2 EC-BOUND-SUBSCRIPT / D1-END /
MAIN-AFTER` — correct under 13) a); `p1122f.cob` (the same with a fatal EC-SIZE-OVERFLOW) prints the same three lines
then terminates abnormally — correct under 13) b). The OBSERVABLE surfaces are SORT (§14.9.40.4 17)) and MERGE
(§14.9.24.4 7) b) 1. and its GR12 siblings). The full model is **kb/Work PB1761**.

## PB1122-B landed 2026-10-01 (wave 1001 group A, w1001a) — the note is closed

Re-probed first on the main checkout's pre-change binary: a MERGE whose GIVING file `BAD-F` fails its implicit OPEN
(status 30) and selects declarative D-BADF, which falls off its end after a checked EC-BOUND-SUBSCRIPT that D-SUB
RESUMEs, CONTINUED the MERGE (`OUT-G` = A B C D) where §14.6.13.1.2 1) + §14.9.24.4 GR12 a) terminate it — reproduced.
(The brief's SORT shape is unreachable here: a SORT's implicit transfers over sequential files have only FATAL
unsuccessful statuses, which terminate regardless, and SORT GIVING over an indexed file is COBOLNET1757 — a separate
open item in the keyed-slice, not this note. MERGE GIVING's fatal-OPEN cell is the one that turns on normal completion.)

Built as briefed, over Task A's `DispatchResult`:

- `ExceptionEngine` keeps a run-unit stack of open DECLARATIVE activation records: `EnterDeclarative(owner)` returns a
  token, `LeaveDeclarative(token)` closes it and anything above it (the emitted `finally`), `DeclarativeNotNormal(token)`.
  Two marks, one site each: `Set(…, fatal: true)` (the raise funnel; `SetIo` goes through it) marks EVERY open record —
  "occurs within the scope" is dynamic across PERFORM and CALL, read as RAISED (checking enabled, §14.6.13.1.1) — and
  `MarkDeclarativesNotNormal(__useActive)`, which `EcEmitter.EmitResume`'s GR1 no-op arm (PB1160) calls, marks only the
  RESUME's own program's records.
- `DispatchEmitter.EmitRunUseBody` (EC-model form): a DECLARATIVE id (`__id < DeclCount`) opens a record and, falling off
  its end, answers `DispatchResult.NotNormal` when it was marked, else `Normal`; the exception-checking PERFORM's
  handler ids and a method's all-handlers invoker take token −1 / the old text, so a declarative-free group is
  byte-identical.
- Consumers decide `NotNormal` explicitly: new `DispatchResult.FinishesStatement` (Normal/NoHandler/NotNormal) replaces
  the `r is Normal or NoHandler` test in `ExceptionEngine.NonfatalIfEnabled` (without it a not-normal fall-off would
  have thrown `RaiseResumeSignal`); `ForHandledWarning` maps `NotNormal` to `HandledNonfatal`; `EmitSelection`, the F3
  tiers and the Format 4 selector need no edit (they compare `ResumeNext` / `NoHandler` / `SuppressesFatal`); the
  SORT/MERGE hook already jumped on `TerminatesSortMerge`. The BEFORE REPORTING hook ignores `__RunUse`'s result.

After: the three-leg golden `conformance:2002/pb1122_declarative_fatal_in_scope_merge` prints L1 `A B C D` (a declarative
that completes normally BYPASSES the bad GIVING file — the control that stops an always-terminate mutant passing), L2

engine (marks, nesting, the −1 token, owner-scoped RESUME mark). Readings recorded in docs/CONFORMANCE.md §3; design:
COBOLNET_CONDITIONS_EXCEPTIONS_DESIGN.md "The declarative dispatch-result protocol" and "RESUME control flow". Row closed:
GR-14.6.13.1.2-1.
