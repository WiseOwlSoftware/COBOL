# PB423 — a premise that was true once, an omission that outlived it

## The mechanism

`MoveBinder.MoveFigurativeEditionGates` opens with the §14.9.25.3 SR1 class screen and states, in a comment, why
only ONE of the rule's four classes is screened
(`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/MoveBinder.cs:91-92`):

```csharp
// Message-tag/object/pointer classes cannot reach a bound MOVE yet (their usages are compile-gated
// skeletons, W2 track B) — this check gains those arms when their phases land.
if (source is BoundFieldOperand { Place.Item.Pic.Usage: Usage.Index } sIdx)      // :93
```

`src/Cobol.Net.Compiler/Binding/Model/PicInfo.cs` contradicts the premise in its own XML docs: `Usage.Pointer` is
documented "LIVE (Phase-4b increment 1)", `Usage.ProgramPointer` "LIVE (P10 Step 7)" and `Usage.ObjectReference`
"LIVE (the Phase-3 OO spine)". `ConstructRegistry` dates `usage-pointer-2002`, `usage-program-pointer-2002`,
`usage-object-reference-2002` and `usage-function-pointer-2014`, and `conformance:2002/based_pointer` exercises a
live USAGE POINTER end to end. So the pointer and object arms of SR1 are simply ABSENT, excused by a premise that
stopped being true several phases ago. The same premise is repeated at
`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/CorrespondingBinder.cs#CorrEligible` for the §14.7.6 rule-4 class
list.

This is not merely a missing diagnostic. With no screen the operands fall through to the ordinary paths: a
pointer sender reaches the alphanumeric store, where the `ManagedPointer` carrier is rendered by its CLR
`ToString`, and a NULL sender reaches Roslyn, which rejects the GENERATED C# and surfaces a compiler-internal
error to the user in place of a COBOL diagnostic. Only class message-tag has no representation in the data model,
so its arm is untestable rather than wrong — that is the one part of the comment still true.

§8.5.2.1's Table 2 maps class Pointer to the categories data-pointer, function-pointer and program-pointer, and
class Object to object-reference. SR1 therefore bars USAGE POINTER, USAGE PROGRAM-POINTER, USAGE FUNCTION-POINTER
and USAGE OBJECT REFERENCE from EITHER MOVE operand position, in either direction, whatever the other operand is.
SET, not MOVE, is the verb for these classes. §14.7.6 rule 4 is the CORRESPONDING sibling of the same closed
list.

⚠ HARM FLAGS, HONESTLY: every shape above is ILLEGAL source under SR1, so no LEGAL program is given a wrong
answer, and `wrong_answer` is NOT set. The harm is that the missing screen lets an illegal program RUN and
deposit `CobolNet` into a user's item without a word (`under_rejects` + `silent`), and that one leg surfaces a
compiler-internal error instead of a diagnostic. It is filed MAJOR on that combination and on the fact that the
sibling was already found and landed once (below).

## The code sites and the shape of the repair

- `MoveBinder.cs:86-111` — the SR1 screen: the index arms and the stale comment at `:91-92`.
- `CorrespondingBinder.cs#CorrEligible` (`:153-165`, the premise repeated at `:156-157`) — §14.7.6 rule 4.
- `src/Cobol.Net.Compiler/Binding/Model/PicInfo.cs` — the LIVE usage docs that contradict the premise.

**THE REPAIR IS ONE OPERAND-CLASS SCREEN, NOT FOUR MORE ARMS IN MoveBinder** (CLAUDE.md rule 5). "The class of
identifier-N shall not be one of <closed list>" is a rule SHAPE that recurs across statements, and this compiler
already has three unrelated implementations of it (MOVE's 0809, the R16 index screen's 1637, and nothing at all
for DISPLAY until PB148 landed `ScreenOperandClass`). The arm to add is a call from MOVE and from
`CorrEligible` into that ONE class screen, keyed on `PicCategory`/`Usage` and taking the statement's closed list
as data — so a usage going live can never again leave a per-verb list stale. Note that "class pointer" spans
THREE categories (data-pointer, function-pointer, program-pointer), so the list is a category SET, not a usage
special-case: a scalar usage test would miss FUNCTION-POINTER exactly as this one missed the others.

## The sibling sweep the fixer must do

- **The DISPLAY arm of this same omission was already found and landed as `kb/Work/PB148` on 2026-08-29**
  ("pointer/program-pointer/object items print their CLR carrier text (SR1 enforced nowhere)"). The MOVE arm was
  not swept with it. That is the sweep CLAUDE.md rule 4 asks for, missed once already — so this fix must sweep
  the WHOLE closed-list family, not just MOVE.
- Every other statement whose syntax rules name the same closed class list: the CORRESPONDING phrase (§14.7.6
  rule 4, already named above), and every verb whose operand rules say "shall not be of class …". Grep the spec
  for that phrase rather than guessing which verbs have it.
- Every in-code comment asserting that a USAGE "cannot reach" a bound statement. That premise class is
  self-invalidating — it is written when a feature is staged and never revisited when the feature lands. A grep
  for "cannot reach" / "compile-gated skeleton" over `src/` is the mechanical sweep, and each hit is either a
  live gap or a comment to delete.

## LANDED 2026-09-19 — SR1 is one sentence about both operand positions, so it is one core

**Re-probed first, on this worktree's own build, and ONE HALF OF THE NOTE NO LONGER HELD.** The note says the
stale premise "is repeated at `CorrespondingBinder#CorrEligible` for the §14.7.6 rule-4 class list". It is not:
`kb/Work/PB391` had already replaced that arm with `ItemCategory.IsIndexMessageTagObjectOrPointer`, the one
four-class population, and the false comment with a past-tense record of it. `SR-14.9.25.3-13` is therefore
untouched here, exactly as the note's Rows section anticipated.

Everything else reproduced, at `--std 2023` and `--std 2002` alike:

* `MOVE P TO Y` (a `USAGE POINTER` sender into `PIC X(8)`) — `rc=0`, `Y=[CobolNet]`: the CLR type name of the
  pointer carrier, deposited into a user's alphanumeric item with no diagnostic anywhere.
* `MOVE NULL TO P` — `rc=70`, `error CS0029: Cannot implicitly convert type 'string' to
  'CobolNet.Runtime.ManagedPointer'`, a Roslyn message about GENERATED C# in place of a COBOL diagnostic.
* `MOVE P TO Q`, `MOVE R TO S` (program-pointers) and `MOVE G TO H` (object references) — all accepted silently.

**The mechanism was the two-arm dispatch with one arm fixed** (`feedback_two_arm_dispatch`, this repository's
most reproducible defect shape). SR1 — *"The class of identifier-1 **or identifier-2** shall not be index,
message-tag, object, or pointer"* — is ONE sentence about BOTH positions. `kb/Work/PB416` had already routed the
SENDING arm through `IntrinsicArgumentRules.ClassOf`, the one §8.5.2.1 Table-2 reader; the RECEIVING arm was
still `t.Item.Pic is { Usage: Usage.Index }`, one hand-written usage, under the comment this note is titled for.
**Which arm did the fix touch? Both, through one core.**

1. **`MoveTable16.Sr1ClassRefusal(CobolClass?, string?)`** is SR1 itself, asked of one operand's class whatever
   position it occupies, over the rule's WHOLE closed list. Class POINTER spans all three of its Table-2
   categories (data-pointer, function-pointer, program-pointer), which is why the question is asked of the CLASS:
   a usage test would have missed FUNCTION-POINTER exactly as the old one missed the others.
2. **`SenderClassRefusal` and the new `ReceiverClassRefusal(Place)`** are its two framings — the reader shape
   this class already uses, because `InitializeBinder` needs the TEXT (§14.9.20.3 SR4's hypothetical MOVE) where
   `MoveBinder` reports COBOLNET0809 about the MOVE the programmer wrote.
3. **The refusal names the rule the programmer wants instead**: §13.18.60.3 SR9/SR8 for a data- or
   program-pointer (both list a SET statement and not a MOVE), and SET for an object reference.
4. **The stale comment is deleted**, and the premise class it belongs to was swept: `grep -rni "cannot reach|
   compile-gated skeleton|have no representation in this data model"` over `src/` leaves no live gap of this
   kind in the binder (the two remaining hits in `IntrinsicArgumentRules` and `CorrespondingBinder` are
   belt-and-braces and past-tense respectively; `VersionConformancePass`'s `RECORD SEQUENTIAL` hit is a real
   grammar gap and is registered in the implementer report).

**MESSAGE-TAG needs no arm and gets none, said out loud.** `CobolClass` has no member for it: the MCS facility
is declined (`docs/CONFORMANCE.md` §4) and `PictureAnalyzer.ParseUsage` refuses the usage by name (COBOLNET1943),
so no operand of that class can be bound. What replaces the arm is a drift test:
`unit:MoveOperandClassDriftTests.EverySr4UsageIsRefusedInBothOperandPositions` walks every usage §13.18.60.3 SR4
names — exactly the six that produce SR1's four classes — and asserts each is refused in BOTH positions with the
SAME text, and that a usage with no bound `PicInfo` answers null in both. The moment MESSAGE-TAG gains a model
the test fails rather than the screen silently narrowing. It was PROVED to fail against the old receiving arm
(restored temporarily: 4 rows red — Pointer, ProgramPointer, FunctionPointer, ObjectReference).

**Tests.** `conformance:negative/pb423-move-pointer-sender` and
`conformance:negative/pb423-move-pointer-receiver` (COBOLNET0809, reject-at 2002 2014 2023 — USAGE POINTER is a
COBOL-2002 element); `conformance:2002/pb423_move_operand_class_admitted` is the COMPLEMENT
(`feedback_measure_the_selectors_complement`) — it declares the very items SR1 bars and references them only
where §13.18.60.3 SR9 and §8.8.4.2.16 admit them, so a widening of the class list shows up as a red rather than
as rejected legal source; plus `MoveOperandClassDriftTests.AnAdmittedClassPassesInBothOperandPositions` over six
admitted categories.

**A LATENT DEFECT IN A SECOND STATEMENT SURFACED WITH THE WIDENING, AND IS FIXED IN THE SAME CHANGE SET.**
§14.9.20.3 SR4 has TWO paragraphs: *"For each of the categories data-pointer, function-pointer, message-tag,
object-reference, and program-pointer specified in the REPLACING phrase, a **SET** statement … shall be valid"*
and *"For each of the **other** categories … a **MOVE** statement … shall be valid."*
`InitializeBinder.CheckReplacingMoveValidity`'s per-category loop already honoured that split
(`InitializeCategories.Table16Receiver` answers null for the five), but the SR1 CLASS screen was hoisted ABOVE
the loop as "asked once" — correct while the only class it could refuse was INDEX, which is not one of
INITIALIZE's thirteen category-names, and wrong the moment the pointer and object arms landed. Two conformance
goldens went RED and named it: `2002/pb415_initialize_replacing_set_form` and
`2014/pb415_initialize_function_pointer` are `INITIALIZE g REPLACING DATA-POINTER DATA BY PTR` — exactly the
shape SR4's first paragraph and §14.9.20.4 GR4 describe — refused as an invalid MOVE. The hoist stays (one
message per REPLACING item, since §5.2.6.4 makes a category-name a SET) and is now guarded by the paragraph
that owns it. Both goldens are green again and their `.out` files are unchanged, so they are the gate on it.
