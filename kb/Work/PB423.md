# PB423 — a premise that was true once, an omission that outlived it

## The mechanism

`MoveBinder.MoveFigurativeEditionGates` opens with the §14.9.25.3 SR1 class screen and states, in a comment, why
only ONE of the rule's four classes is screened
(`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/MoveBinder.cs:91-92`):

```csharp
// Message-tag/object/pointer classes cannot reach a bound MOVE yet (their usages are compile-gated
// skeletons, W2 track B) — this check gains those arms when their phases land.
if (source is BoundFieldOperand { Place.Item.Pic.Usage: Usage.Index } sIdx)      // :93
```

`src/Cobol.Net.Compiler/Binding/Model/PicInfo.cs` contradicts the premise in its own XML docs: `Usage.Pointer` is
documented "LIVE (Phase-4b increment 1)", `Usage.ProgramPointer` "LIVE (P10 Step 7)" and `Usage.ObjectReference`
"LIVE (the Phase-3 OO spine)". `ConstructRegistry` dates `usage-pointer-2002`, `usage-program-pointer-2002`,
`usage-object-reference-2002` and `usage-function-pointer-2014`, and `conformance:2002/based_pointer` exercises a
live USAGE POINTER end to end. So the pointer and object arms of SR1 are simply ABSENT, excused by a premise that
stopped being true several phases ago. The same premise is repeated at
`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/CorrespondingBinder.cs#CorrEligible` for the §14.7.6 rule-4 class
list.

This is not merely a missing diagnostic. With no screen the operands fall through to the ordinary paths: a
pointer sender reaches the alphanumeric store, where the `ManagedPointer` carrier is rendered by its CLR
`ToString`, and a NULL sender reaches Roslyn, which rejects the GENERATED C# and surfaces a compiler-internal
error to the user in place of a COBOL diagnostic. Only class message-tag has no representation in the data model,
so its arm is untestable rather than wrong — that is the one part of the comment still true.

    python scripts/spec/cite.py --check 8.5.2.1 "object-reference"
    OK  §8.5.2.1   (General)
        | Object | Object-reference |

    python scripts/spec/cite.py --check 14.7.6 "message-tag"
    OK  §14.7.6 4)  (CORRESPONDING phrase)
        4) Neither data item contains an OCCURS, REDEFINES, or RENAMES clause or is of class index,
           message-tag, object, or pointer.

§8.5.2.1's Table 2 maps class Pointer to the categories data-pointer, function-pointer and program-pointer, and
class Object to object-reference. SR1 therefore bars USAGE POINTER, USAGE PROGRAM-POINTER, USAGE FUNCTION-POINTER
and USAGE OBJECT REFERENCE from EITHER MOVE operand position, in either direction, whatever the other operand is.
SET, not MOVE, is the verb for these classes. §14.7.6 rule 4 is the CORRESPONDING sibling of the same closed
list.

⚠ HARM FLAGS, HONESTLY: every shape above is ILLEGAL source under SR1, so no LEGAL program is given a wrong
answer, and `wrong_answer` is NOT set. The harm is that the missing screen lets an illegal program RUN and
deposit `CobolNet` into a user's item without a word (`under_rejects` + `silent`), and that one leg surfaces a
compiler-internal error instead of a diagnostic. It is filed MAJOR on that combination and on the fact that the
sibling was already found and landed once (below).

## The code sites and the shape of the repair

- `MoveBinder.cs:86-111` — the SR1 screen: the index arms and the stale comment at `:91-92`.
- `CorrespondingBinder.cs#CorrEligible` (`:153-165`, the premise repeated at `:156-157`) — §14.7.6 rule 4.
- `src/Cobol.Net.Compiler/Binding/Model/PicInfo.cs` — the LIVE usage docs that contradict the premise.

**THE REPAIR IS ONE OPERAND-CLASS SCREEN, NOT FOUR MORE ARMS IN MoveBinder** (CLAUDE.md rule 5). "The class of
identifier-N shall not be one of <closed list>" is a rule SHAPE that recurs across statements, and this compiler
already has three unrelated implementations of it (MOVE's 0809, the R16 index screen's 1637, and nothing at all
for DISPLAY until PB148 landed `ScreenOperandClass`). The arm to add is a call from MOVE and from
`CorrEligible` into that ONE class screen, keyed on `PicCategory`/`Usage` and taking the statement's closed list
as data — so a usage going live can never again leave a per-verb list stale. Note that "class pointer" spans
THREE categories (data-pointer, function-pointer, program-pointer), so the list is a category SET, not a usage
special-case: a scalar usage test would miss FUNCTION-POINTER exactly as this one missed the others.

## The sibling sweep the fixer must do

- **The DISPLAY arm of this same omission was already found and landed as `kb/Work/PB148` on 2026-08-29**
  ("pointer/program-pointer/object items print their CLR carrier text (SR1 enforced nowhere)"). The MOVE arm was
  not swept with it. That is the sweep CLAUDE.md rule 4 asks for, missed once already — so this fix must sweep
  the WHOLE closed-list family, not just MOVE.
- Every other statement whose syntax rules name the same closed class list: the CORRESPONDING phrase (§14.7.6
  rule 4, already named above), and every verb whose operand rules say "shall not be of class …". Grep the spec
  for that phrase rather than guessing which verbs have it.
- Every in-code comment asserting that a USAGE "cannot reach" a bound statement. That premise class is
  self-invalidating — it is written when a feature is staged and never revisited when the feature lands. A grep
  for "cannot reach" / "compile-gated skeleton" over `src/` is the mechanical sweep, and each hit is either a
  live gap or a comment to delete.
