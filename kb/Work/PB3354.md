# PB3354 — one log, two handles, buffered child

Filed 2026-10-18 by the clerk from the enqueue unit's leads (`E:\COBOL-coord\scratch\enqueue-unit-20261018-leads.md`, Lead A),
measured 2026-10-18 ~01:05Z. Grep of kb/Work for `land_lane` with overwrite, buffer, PYTHONUNBUFFERED and "attempt log" found
no open note. Harm: observability (the lane's own evidence is damaged); no wrong answer in a user program.

## Mechanism and sites
`scripts/orchestrator/land_lane.py` `spawn` (~line 304) and `run_attempt` (~line 556).
- `spawn` opens the attempt log `ab` and hands that handle to the RUNNER as its stdout. `run_attempt` opens the same log a
  second time and hands THAT handle to `enqueue.py land`. On Windows, Python's append mode is the CRT's emulation (seek to
  end before each write in the process that opened the fd); the runner's stdout is an inherited OS handle with its own file
  pointer, still at 0. So the closing `print(f"land lane: attempt ... ended exit {rc}: ...", flush=True)` is written at
  offset 0 and overwrites the first ~100 bytes of enqueue.py's output.
- Repro: `head -c 160` of every completed `E:\COBOL-coord\logs\land-lane-*.log` starts with the runner's line followed by the
  tail of a truncated line. In `land-lane-worktree-wf_71ab13ab-689-17-20261017T233907206592Z.log`: `land lane: attempt ...
  ended exit 0: ENQUEUED`, then `66 — 2026-10-17 16:49 PDT — PB3339: ...` (the rest of a line that began `## Entry 21`); the
  same in the 689-23 and 689-33 logs.
- Second half, same handle path: `enqueue.py` runs with stdout a FILE, so Python block-buffers it. A running attempt's log
  reads 0 bytes for its whole life (the 29a-5 and 29a-8 logs were 0 bytes 13 minutes into their attempts, both alive in
  `scripts/linux-gate.sh`); when it ends, enqueue.py's own lines land AFTER its children's output (the 689-17 log prints
  `=== DEVLOG CHECK` and `=== LANDING CHECK` before `enqueue: Windows gate: ...`), so the log's order is not the run's order.

## Fix direction
One handle and unbuffered children. `spawn` gives the runner no log stdout (its child gets the log explicitly, as
`run_attempt`'s docstring already says it must); `run_attempt` writes its end line through the same append handle after the
child returns; the child runs with `PYTHONUNBUFFERED=1` (or `-u`), so the log is live and in order. Witness: a unit test that
runs `run_attempt` on a stub argv printing a known first line and asserts the log begins with it and ends with the runner's
line.

Sibling sweep owed: every other place a detached runner and its child share one log by two opens (the supervisor's unit logs,
`gate_slot.py run`, `orchestrate.ps1`'s background tasks).
