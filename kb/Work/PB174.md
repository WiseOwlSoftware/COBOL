# PB174

Found during PB164 wave 2 (the FLOAT-BINARY endianness landing). §13.18.60.2's USAGE general format gives
every STANDARD binary floating-point usage (FLOAT-BINARY-32/-64/-128) an optional trailing
endianness-phrase (`HIGH-ORDER-LEFT | HIGH-ORDER-RIGHT`), and the standard decimal usages an optional
encoding-phrase + endianness-phrase. The grammar's usage rule (`Core/CobolData.g4` ~434) carries the bare
usage keywords only, so a data description entry that states its own endianness — legal 2014+ source —
fails to parse. (Confirm the exact general format against the PRINTED page before implementing: render the
PDF, per the lossy-diagram rule.)

**The landing shape is already built.** PB164 wave 2 put the one derivation in `PicInfo.FloatItem(usage,
FloatEndianness)`: the OPTIONS FLOAT-BINARY model supplies the IMPLIED phrase (§11.9.8.3 SR2/SR3), our
documented default is HIGH-ORDER-LEFT (SR1; CONFORMANCE.md A.1 item 48), and the result rides
`PicInfo.FloatLittleEndian → ProfileInitializer → NumProfile.FloatLittleEndian → the IEEE image lanes`
(§13.18.60.4 GR19a/b). The per-item phrase is by definition MORE specific than the implied one — thread it
from the parse into the same factory argument (item phrase if present, else the OPTIONS model) and every
consumer widens automatically. Sweep: the grammar fragment + version predicate + constructs row +
edition-gate tests per the new-construct skill; `NumericByteFormDriftTests.FloatBinaryEndianness_…` pins
the derivation and gains the per-item rows; a golden with mixed per-item/implied endianness discriminates
via FUNCTION ORD byte reads (`pb164_float_hor_image` is the pattern). The decimal usages' phrases stay
moot while FLOAT-DECIMAL-16/-34 are COBOLNET1564 documented non-support.

## Landed 2026-09-02 (cluster D)

Reproduced first: `01 F USAGE FLOAT-BINARY-32 HIGH-ORDER-LEFT.` was `COBOL0307: unexpected 'HIGH-ORDER-LEFT'`.
The printed §13.18.60.2 diagram was rendered (PDF p.533 = printed 503) and matches the transcription cell for cell.

**The tail went on the CLAUSE, not the keyword** — `usageClause : (USAGE IS?)? usageKeyword binarySign?
noSignPhrase? floatFormatPhrase*`. That placement is the whole point: `DataBinder.UsageKeyword` derives the
canonical keyword from the `usageKeyword` node, so a phrase inside it would glue to
`"FLOAT-BINARY-32HIGH-ORDER-LEFT"` and fall to `PictureAnalyzer.ParseUsage`'s internal-error arm — the failure that
method's own doc comment already records for bare `BINARY-CHAR SIGNED`. `encodingPhrase`/`endiannessPhrase` moved
into `CobolData.g4` so ONE rule pair serves §11.9.8, §11.9.9 and §13.18.60.2, and `FloatFormatPhrase` (OptionsModel)
is its binder-side twin so the token→enum mapping stayed singular instead of becoming copy #2.

`*` with a binder duplicate screen is the exact expression of §5.2.6.4's bracketed choice indicators (zero or more,
each at most once, any order). Three screens, all in one block where `entryUsage` is resolved: COBOLNET1716
(endianness-phrase off the five standard float usages, §13.18.60.2 + GR19c/d), COBOLNET1717 (encoding-phrase off
FLOAT-DECIMAL-16/-34, GR20a), COBOLNET1718 (a repeated phrase, §5.2.6.4).

The item's phrase now WINS over the OPTIONS-implied one — not by preference but by §11.9.8.3 SR2/SR3's own wording
("in which an endianness-phrase is not specified") — merged as one null-coalesce at the single `PicInfo.FloatItem`
call site, so every downstream consumer widened with zero further edits.

Also landed: `UsageFamilies` writes §3.166/§3.167's two usage families down ONCE (four rules key on those exact
sets); `USAGE FLOAT-DECIMAL-16 BINARY-ENCODING` now fails at the NAMED non-support stage (COBOLNET1564) instead of
as a raw parse error; and CONFORMANCE.md A.3 row 18 was corrected — it claimed the endianness-phrase as
**Claimed (native)** while the phrase did not parse at all.

**Drift test paired with the structure** (rule 5): `UsageFloatFormatPhraseDriftTests` reads the `usageKeyword`
inventory out of the `.g4` and fails until a new usage says which of the two phrases the printed diagram gives it.
Proven to fail once before being trusted (removed a row and flipped a classification → 3 red).
