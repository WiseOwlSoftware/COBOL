# PB174

Found during PB164 wave 2 (the FLOAT-BINARY endianness landing). §13.18.60.2's USAGE general format gives
every STANDARD binary floating-point usage (FLOAT-BINARY-32/-64/-128) an optional trailing
endianness-phrase (`HIGH-ORDER-LEFT | HIGH-ORDER-RIGHT`), and the standard decimal usages an optional
encoding-phrase + endianness-phrase. The grammar's usage rule (`Core/CobolData.g4` ~434) carries the bare
usage keywords only, so a data description entry that states its own endianness — legal 2014+ source —
fails to parse. (Confirm the exact general format against the PRINTED page before implementing: render the
PDF, per the lossy-diagram rule.)

**The landing shape is already built.** PB164 wave 2 put the one derivation in `PicInfo.FloatItem(usage,
FloatEndianness)`: the OPTIONS FLOAT-BINARY model supplies the IMPLIED phrase (§11.9.8.3 SR2/SR3), our
documented default is HIGH-ORDER-LEFT (SR1; CONFORMANCE.md A.1 item 48), and the result rides
`PicInfo.FloatLittleEndian → ProfileInitializer → NumProfile.FloatLittleEndian → the IEEE image lanes`
(§13.18.60.4 GR19a/b). The per-item phrase is by definition MORE specific than the implied one — thread it
from the parse into the same factory argument (item phrase if present, else the OPTIONS model) and every
consumer widens automatically. Sweep: the grammar fragment + version predicate + constructs row +
edition-gate tests per the new-construct skill; `NumericByteFormDriftTests.FloatBinaryEndianness_…` pins
the derivation and gains the per-item rows; a golden with mixed per-item/implied endianness discriminates
via FUNCTION ORD byte reads (`pb164_float_hor_image` is the pattern). The decimal usages' phrases stay
moot while FLOAT-DECIMAL-16/-34 are COBOLNET1564 documented non-support.
