# PB490

## Mechanism — picture-clause-p3
pic-suppression-string-simple-insertions - the set of SIMPLE INSERTION editing symbols is written down as a hand-maintained pair {',', 'B'} in the two places that consume it, so the other two ('0' and '/') are not treated as part of a zero-suppression or floating-insertion string. ISO 13.18.40.5 rule 3 defines the simple insertion symbols as B, 0, '/', ',' (plus character-1 when literal-1 is given); rules 6 and 7 both say 'Any of the simple insertion editing symbols embedded in this string or to the immediate right of this string are part of the string'. CobolEdit.Format's pass-2 suppression loop has `case ',' or 'B': output[i] = asteriskFill ? '*' : ' ';` and no case for '0' or '/', so those positions keep their insertion character even when no significant numeric character stands to their left; CobolEdit.FindFloatingPlacement repeats the same partial set (`else if (inZone && p is ',' or 'B' && output[i] == ' ') lastSuppressed = i; else if (inZone) break;`) so a '0' or '/' also TERMINATES the floating zone and the floating symbol lands too far left. The fix is structural, not two more cases: one shared predicate 'is a simple insertion symbol of this picture' (B, 0, '/', ',' and every declared EDITING character-1) read by pass 1's insertion switch, pass 2's suppression walk and FindFloatingPlacement, plus a drift test that fails if the three disagree.

### Expected, from the standard
ISO/IEC 1989:2023 13.18.40.5 rule 7 (zero suppression) and rule 6 (floating insertion): the embedded simple insertion symbols are part of the string, so every position of the string that precedes the first significant digit takes the replacement character (space for 'Z', asterisk for '*') or, for a floating string, the floating insertion character. `PIC ZZ/ZZ` with 12 shall render '   12'; `PIC ZZ0ZZ` with 12 shall render '   12'; `PIC ++/++9` with 5 shall render '    +5' (rule 6a: a single occurrence of the sign immediately preceding the first character position for which no floating insertion editing is specified, spaces before it) and with -5 '    -5'. 13.18.40.4 GR15 corroborates from the format-validation side, for '/' and identically for '0': the position is checked to contain 'the character slant or, if no significant numeric character appears to its left, the corresponding floating insertion character or replacement character respectively'. Both pictures are admitted by 13.18.40.6 Table 10 (the 'B 0 /' column is x against both the 'Z *' rows and the floating '+ -' rows, and vice versa), so this is legal source.

### Observed
Observed by probe, not deduced. Read the code first: CobolEdit.Format's pass 2 switch handles 'Z', '*', floating '+'/'-'/currency, ',' or 'B', '.', '9' and nothing else, so a '0' or '/' falls through untouched while `suppressing` stays true; FindFloatingPlacement's zone walk admits only ',' and 'B' as zone continuations and breaks on anything else, which is why the '+' in `++/++9` lands at index 1 instead of index 4. Both call sites are inside the ONE editor, so every store into a numeric-edited receiver (MOVE, arithmetic, ACCEPT, STRING, VALUE initialization, the group image codec) carries the defect, and DeEdit's round-trip verification is derived from the same Format, so it cannot detect it either. No spec-derived test covers zero suppression or floating insertion at all - the coverage is NumericEditedDifferentialTests, a legacy differential, and the legacy engine shares the same treatment, which is why the net stayed green.

## Mechanism — picture-clause-p3
pic-alphanumeric-edited-editing-rules-dropped - a two-arm dispatch with only one arm fixed. The PICTURE EDITING phrase (COBOL-2023) is analyzed once, for every category, and PictureAnalyzer stores the resolved rules on PicInfo.EditingRules for BOTH the alphanumeric arm and the numeric-edited arm. Every numeric-edited emit site threads them into the runtime (RuntimeApi.EditsArg -> CobolEdit.Format(... edits:)); the alphanumeric-edited emit path has no such parameter anywhere - RuntimeApi.EditFormatAlphanumeric(value, maskLiteral) takes only the mask, CobolEdit.FormatAlphanumeric(source, picture) has no edits parameter, and its `_ => picture[i]` default copies the character-1 LETTER into the edited image. All three call sites (MoveEmitter, AcceptDisplayEmitter, StringEmitter) drop PicInfo.EditingRules on the floor. The structural fix is to give the alphanumeric formatter the same EditRule[] channel the numeric one has - or better, one Format entry point that takes the mask plus the rules and dispatches on category - so a new emit site cannot forget it.

### Expected, from the standard
ISO/IEC 1989:2023 13.18.40.4 GR7 admits character-1 as an alphanumeric-edited item's insertion ('at least one symbol A or one symbol X, and at least one instance of character-1 or one of the symbols from the set B, 0, /'), 13.18.40.5 Table 7 gives category alphanumeric-edited SIMPLE INSERTION, and 13.18.40.5 rule 3 says simple insertion editing 'results in the insertion character occupying the same character position in the edited item as the associated symbol occupies in character-string-1'. The insertion character is literal-1, ':'. `PIC XXTXX EDITING "T" IS ":"` receiving "ABCD" shall render AB:CD.

Observed by probe and confirmed by reading the emit path: grep of EditingRules over src/Cobol.Net.* returns one producer (PictureAnalyzer) and seven numeric-edited consumers, none of them the alphanumeric path; RuntimeApi.EditFormatAlphanumeric's signature is (value, maskLiteral) with no third argument. NOTE a spec-internal wrinkle that does NOT change the expected result: 13.18.40.6's note maps 'es' precedence onto the NON-FLOATING currency symbol, whose Table 10 column carries no 'x' against the 'A X' row, which would make character-1 unplaceable in an alphanumeric picture - but GR7 explicitly names character-1 as an alphanumeric-edited constituent, so the picture is legal and the compiler is right to accept it; only the rendered image is wrong. If the owner reads Table 10 as governing instead, the correct behaviour is a diagnostic, never the silent ABTCD.

## Landed — 2026-09-09

Both mechanisms are fixed at the root, and the fix is the STRUCTURE the note asked for rather than four more
`case` labels.

**One definition of the set.** `CobolEdit.SimpleInsertionSymbols` (`"B0/,"`), `IsSimpleInsertionSymbol(char,
grouping)` and `TrySimpleInsertion(char, EditRule[]?, out char)` are §13.18.40.5 rule 3 written down once, and
FOUR consumers read it: `Format`'s pass 1 (place the insertion character), `Format`'s pass 2 (a member of a
zero-suppression string takes the replacement character), `FindFloatingPlacement` (a member of a floating string
is a landing position) and `FormatAlphanumeric`. The compiler's `PictureComposition.MarkFloating.Embedded` — a
THIRD copy the note did not name, found by the sibling sweep — reads `IsSimpleInsertionSymbol` too, so the
compile-time floating-string detector and the runtime editor cannot disagree about what a string contains.
`CobolEditSimpleInsertionDriftTests` derives its masks FROM the set (not from a literal list), and the drift was
re-injected once to prove the tests fail: 7 of 24 red, green again on revert.

**The membership test was missing entirely, and that was a second wrong answer the note did not have.** Rules 6
and 7 say "embedded in this string or to the immediate right of this string" — never to the LEFT — and
§13.18.40.6 Table 10 admits `B 0 /` and `,` before a `Z`. Pass 2 blanked every `,`/`B` it met while
`suppressing` was still true, so `PIC ,ZZ9` MOVE 1 rendered `   1` where the standard requires `,  1`
(§13.18.40.4 GR15: "the character comma if the symbol ',' is neither part of floating insertion editing nor of
zero suppression with replacement editing"). Pass 2 now carries an `inString` flag set by the first Z / `*` /
floating member.

**A PICTURE EDITING character-1's FORM decides its class, and it is not readable off the rendered characters.**
`EditRule` gained `SimpleInsertion`: the IS form is rule 3 simple insertion, the FOR form is rule 5 FIXED
insertion ("When character-1 is used, and is not a simple insertion character, it represents literal-2, or
literal-3 as the insertion characters"). `Neg == Pos` is an unsound proxy — a FOR phrase may name the same
literal on both sides, and `PIC ZT9 EDITING "T" IS ":"` MOVE 5 must render `  5` while
`PIC ZU9 EDITING "U" FOR NEGATIVE IS ":" POSITIVE IS ":"` MOVE 5 must render ` :5`.

**The alphanumeric arm's dispatch was changed, not its callers.** `RuntimeApi.EditFormatAlphanumeric` now takes
the `PicInfo` and renders the mask together with `PicInfo.EditingRules` — the alphanumeric twin of
`EditFormatFor` — so an emit site cannot pass one without the other. MoveEmitter, AcceptDisplayEmitter and
StringEmitter pass the item. `PIC XXTXX EDITING "T" IS ":"` MOVE "ABCD" renders `AB:CD`.
