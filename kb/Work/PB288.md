# PB288 - the CALL argument rescale wraps instead of raising

Found by the EDGE PROBE of the [[PB263]] / [[PB264]] landing (2026-09-02), while checking that the new exact
literal rendering could not explode on a large exponent. **Pre-existing and NOT caused by that landing** - the
probe below was run in BOTH notations and they wrap IDENTICALLY, and the fixed-point spelling has always taken
this path.

## Measured, 2026-09-02, at HEAD (after PB263/PB264)

```cobol
01 LC PIC S9(9)V9(9).            *> the callee's formal
CALL "P9C" AS NESTED USING BY CONTENT 1000000000000000000000000000000
CALL "P9C" AS NESTED USING BY CONTENT 1.0E+30
```

```
C=87399551400673280{
C=87399551400673280{
```

Both rows are the same wrapped number. The literal is 10^30 - legal at COBOL-2002+ (§8.3.3.3.2 admits 1 through
31 digits) - and the value the callee displays is unrelated to it, with no diagnostic anywhere.

## The site and the root cause

`src/Cobol.Net.Runtime/Control/CallAbi.cs`, `CobolArgAdapt.Num<T>` (and the same shape in `NumValue<T>`):

```csharp
() => T.CreateTruncating(CobolNum.Rescale(ReadNumericCell(np)!.Value, callerScale, formalScale, CobolRounding.Truncation)),
```

`CobolNum.Rescale`'s widening arm is `value * Pow10Wide(toScale - fromScale)` - an UNCHECKED `Int128` multiply.
The argument crosses correctly as unscaled 10^30 at scale 0; rescaling it to the formal's scale 9 asks for 10^39,
which exceeds `Int128.MaxValue` (about 1.7e38) and wraps silently. The value is destroyed inside the ABI, after
the caller rendered it exactly and before the callee's own `CobolNum.Store` digit-capacity truncation could apply
the §14.2.3 GR9/GR10 "COMPUTE statement without the ROUNDED phrase" rule that governs the fill.

The high-order truncation the standard DOES sanction is `Store`'s `v %= Pow10Wide(receiver.Digits)`, which is a
decimal-digit truncation of a correct value. A binary wrap of the intermediate is not that rule and is not any
rule: it is arithmetic overflow of an implementation carrier.

## Fix shape

The rescale that feeds a formal is a value-semantics transfer with no capacity check downstream, so it is the
same situation `NumericRenderer.Landed` already names - "EC-SIZE-OVERFLOW past the carrier ... never the modular
low-order digits a STORE may use". Route the CALL adapt path's rescales through a CHECKED widening (the
`CobolNum.Widen` posture: loud past the documented Int128 intermediate, per CONFORMANCE.md §4.2.16) rather than
the unchecked multiply, and let the §14.2.3 fill rule then do the digit-capacity truncation on a correct value.

⚠ Scope note: `CobolNum.Rescale` is shared by many paths, so the checked form belongs at the CALL adapt call
sites (or as a `RescaleChecked` sibling - one already exists for the edited-receiver case) rather than as a
change to `Rescale` itself. Sweep `Num`, `NumValue`, `Text`, `TextValue` and `StoreReturnNum` together: all five
read the caller cell through the same pair and all five can be handed an out-of-lane magnitude.

Golden owed: the probe above, in both notations, asserting a raised size condition rather than a wrapped value.

## Landed - 2026-09-05

**REPRODUCED FIRST, on this worktree's own `cobol.exe`.** The note's probe still wrapped identically after
train 4 (PB233/PB237/PB238): `REF=87399551400673280{` for both notations. Two things in the note did NOT hold.
(1) `Text`, `TextValue` and `StoreReturnNum` carry NO widening rescale at all - they format through
`CobolNum.FormatDisplay` at the ARGUMENT's own description, whose digit cap is decimal (`CobolNum.Image.cs`
`mag %= Pow10Wide(item.Digits)`), so the sweep the note asked for closes at three sites, not five. (2) The
`BY VALUE` arm was NOT "the same shape": it wrapped to a DIFFERENT wrong value (-123822295304634368 against
the view's +873995514006732800), which is the tell that the two arms were never one rule.

**THE FIX IS NOT THE ONE THE NOTE PROPOSED, AND THE SPEC IS WHY.** The note asked for a CHECKED widening -
loud past the `Int128` intermediate, the `CobolNum.Widen` posture. But 14.2.3 GR9 (the NESTED/prototyped
branch) and GR10 both say the crossing to a numeric formal IS "a COMPUTE statement without the ROUNDED phrase"
whose receiving operand is a data item of the FORMAL's description. That makes an over-capacity argument
14.7.5 case 3 - "after radix point alignment ... further from zero than permitted for the associated resultant
data item" - i.e. a RECEIVER overflow, not 14.7.5 case 5's intermediate-range overflow. With no SIZE ERROR
phrase and EC-SIZE checking off, case 3's disposition is this implementation's documented determination
`CONFORMANCE.md` DOC-A.1-70: execution continues and the receiver takes the result's LOW-ORDER digits at its
own scale. Raising would have made the CALL crossing disagree with the very COMPUTE the standard says it is.

**ROOT CAUSE, AND THE EXTRACTION.** `CobolArgAdapt.Land` is now the ONE numeric landing of this ABI, and every
numeric arm goes through it. It composes the two halves that were each independently missing:

- the scale alignment widens with STORE semantics (`CobolNum.RescaleStoreCap`, the low-order digits) instead of
  the unchecked `CobolNum.Rescale` - this is the wrap the note found;
- the result is conformed to the formal's picture (`CobolNum.Store`) BEFORE the closing `T.CreateTruncating`,
  which is itself a BINARY truncation to the carrier. `NumValue` already had this half and `Num` never did, so
  an 18-digit argument viewed through a `PIC S9(4)V99` formal arrived as -9838.16 where the low-order digits
  are +5678.00. That second defect was invisible from the note's probe and is the reason a checked widening
  alone would not have fixed the mechanism.

The float lane had the SAME two-arm split with the arms swapped: `NumValue` composed
`CobolFloat.ToScaledUnchecked` with `Store` and was right, `Num` did not and was wrong. All four rows now
agree. GR11 is what licenses applying the formal's description inside the GR8 aliasing view: "references to
data-name-1 ... are resolved in accordance with their description in the linkage section".

**SIBLING SWEEP.** `Int128.Abs` THROWS on `Int128.MinValue`, and both widening siblings called it -
`RescaleStoreCap` and `RescaleEscape`. The value is reachable through this very ABI (`ReadNumericCell`'s R10
bits contract hands a 16-byte unsigned carrier's top-half content across as exactly that `Int128`), so routing
the per-access CALL landing through `RescaleStoreCap` would have converted a wrong answer into a crash. Both
are fixed: the store arm pre-reduces modulo 10^38 (lossless - a 39-digit magnitude always takes the cap
branch), the escape arm writes its bound on the signed value. `RescaleStoreCap`'s cap TEST also became a
power-of-ten compare instead of a digit-count division loop, because the CALL view re-lands on every reference
to the formal.

**SHIPPED.** `tests/conformance/2023/pb288_call_argument_scale_landing.cob` + `.out` (registered, enabled) -
nine rows whose expected values are derived in the file's header from 14.2.3 GR9/GR10 + 14.7.5 case 3 +
DOC-A.1-70, including the two inline comparator rows that make "the crossing IS that COMPUTE" testable and an
in-capacity control row. PROVEN TO DISCRIMINATE: on the pre-fix runtime six of the nine rows are red and the
three comparator/control rows are unchanged. Plus
`CallAbiNumericCarrierDriftTests.TheGr8ViewAndTheGr10Copy_LandIdentically` and two `CobolNum` unit tests (the
MinValue survival of both arms, and an equivalence sweep of the O(1) cap against the low-order-38-digit
reference across six shifts and fourteen signed seeds). Inventory: NOT recorded here. The evidence earns GR-14.2.3-9
and GR-14.2.3-10 a PARTIAL, not a CONFORMS - GR9's non-prototyped branch, its ANY LENGTH / DYNAMIC LENGTH
legs and its SET/MOVE conversion legs are unverified, and GR10's class-object/pointer SET leg is refused at
bind by the BY VALUE formal-carrier diagnostic - and `DefectiveRowCoverageDriftTests` requires every PARTIAL
row to be claimed by an OPEN note's `inventory_rows`, which a landed note cannot be. The prepared batch is in
the PB288 report for the orchestrator to land with an allocated note id; GAP is unchanged either way, because
PARTIAL does not close a row.

**STILL OPEN, OUTSIDE THIS MECHANISM** (reported for the orchestrator to file): the INLINE arithmetic store
path has the same widening wrap - `COMPUTE WC = 1000000000000000000000000000000` into a `PIC S9(9)V9(9)`
receiver still stores -123822295.304634368 where DOC-A.1-70 says 0 - because `ArithmeticEmitter` renders
`CobolNum.Rescale` for the final transfer. And the CALL crossing never raises EC-SIZE-TRUNCATION when EC-SIZE
checking IS enabled, because the conversion GR9 assigns to the ACTIVATING element is performed callee-side,
where the CALL statement's checking state is not in scope.
