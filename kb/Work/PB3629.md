# PB3629 — the in-process host entry leaves the run unit's files open

Filed by the clerk from the branch review of PB3194 (branch `fix-pb3194-linux-gate-clones`), report
`E:\COBOL-coord\scratch\reports\w20261026c4-PB3194-report.md`, "R2-1 LEAD" (medium, not blocking at round 2) and the finisher's
"Lead, too large for this slice (P7)". Not re-probed by the clerk. Searched `kb/Work` for COI.dat, SCRATCH-LEFT and the run-unit
implicit-CLOSE mechanism: no note covers it (PB603 and PB1532 are the runtime's own `CloseAll` paths, both landed).

**Site.** `tests/Cobol.Net.Tests.Unit/CommitRollbackRefusalWitnessTests.cs` line 468 (`Run`): it compiles the program, loads it,
and runs `Task.Run(() => entry(ref trace))` through the program's host entry (`Call`). It returns after `entry` returns or throws
`RunUnitEndedException`, with the run unit's files still open: `COI.dat`, `COR.dat`, `CR[IR][IR]n.dat`, `CF[IR][IR]0.dat`, 20 handles
in one run. PB3194's new `ScratchDirectory.Remove` reports them through `HarnessLog.ReportLeft` (`SCRATCH-LEFT`), and the next test
host reaps the directory, so nothing leaks, but the handles stay open in the host until it ends.

**Repro (Windows).** `dotnet test tests/Cobol.Net.Tests.Unit --filter FullyQualifiedName~CommitRollbackRefusalWitness`, then
`grep SCRATCH-LEFT <temp>/cobolnet-harness-observations.log`.

**Spec.** `cite.py --check 14.6.11` finds §14.6.11 (Normal run unit termination) GR2: an implicit CLOSE without phrases is executed
for each file in the open mode, for all open files in the run unit, even when an error occurs during the closing. So a program run
as a run unit owes the close. Open: whether a program activated through the host entry of a loaded assembly (not as the main
program of `cobol run`) is a run unit that has terminated at all when `entry` returns, or whether the TEST must end the run unit
(the runtime's `CloseAll` at run-unit termination) after reading the trace. That is the question to settle first: if the entry
returns without terminating the run unit, the test is wrong; if the run unit has terminated, the runtime misses the close on the
host-entry return and `RunUnitEndedException` paths, which is a runtime defect to reclassify.

**To settle.** Decide which arm; then fix at the root (the test ends the run unit through the one runtime termination call, or the
runtime closes on that path), and pin it so `SCRATCH-LEFT` is empty after the `CommitRollbackRefusalWitness` cases. Sweep the other
in-process host-entry harnesses (`KeyedClosePermanentErrorWitnessTests` and any `Task.Run(() => entry(` caller) for the same.

**Expected from the spec:** A program activated through its host entry by a .NET host is under the control of a non-COBOL activating element: its GOBACK terminates the program and returns to the host (14.9.18.4 GR2; GR1 a) 'execution continues in the activating element in an implementor-defined fashion'); only a GOBACK in a program NOT under a calling element acts as STOP (GR3). The COBOL/non-COBOL relationship is implementor-defined (14.6.1), and docs/CONFORMANCE.md DOC-A.1-167 defines it: GOBACK returns to the host, and the run unit ends when RunUnit.Run's body returns (or at process exit for the ambient run unit); STOP RUN or a run-unit fatal ends it at the host boundary. So when entry() returns, the run unit has NOT terminated, and 14.6.11 2) (implicit CLOSE of every open file) and 9.1.18.5 (normal termination commits) are not yet owed. The test owns ending the run unit and never does: it activates in the ambient run unit of a Task.Run flow (RunUnit.Current) and drops it. The runtime's RunUnitEndedException path already performs the 14.6.11 closes.

**Citations checked:**
- OK  §14.9.18.4 1) a)  (General rules) If the activating runtime element is a non-COBOL element, execution continues in the activating element in an implementor-defined fashion.
- OK  §14.9.18.4 2)  (General rules) The execution of an GOBACK statement causes the executing program to terminate, and control to return to the calling statement.
- OK  §14.9.18.4 3)  (General rules) If a GOBACK statement is executed in a program that is not under the control of a calling runtime element, the program operates as if executing a STOP statement
- OK  §14.6.1   (Run unit organization) the requirements for the relationship and interaction between the COBOL and the non-COBOL modules are defined by the implementor
- OK  §14.6.11 2)  (Normal run unit termination) These implicit close statements shall be executed for all open files in the run unit
- OK  §9.1.18.5   (Run unit termination) When a run unit terminates normally, all file changes are permanently committed.
