Filed by the w1033 clerk from the PB1664 decision (`E:\COBOL-coord\scratch\w1033-adj\PB1664-decision.md` section 6, "Sibling lead (NOT decided here; it needs its own note)") and refuter
(`PB1664-refute.md` section 3). Both files say it needs its own adjudication, so it is an analysis.

**Observed.** On shape 1 (ORGANIZATION RECORD SEQUENTIAL, WRITE ... ADVANCING, no LINAGE, not a report file; probe `PB1664\advrs.cob`, compare `gc-run.txt` with `wo-run.txt`):
- GnuCOBOL 3.2.0 writes the FULL fixed-length record: `AA` followed by 6 spaces for an 8-byte record.
- The pinned build (`pin-97006f3`) strips trailing spaces from every print-stream record (`docs/CONFORMANCE.md` DOC-A.1-146 (c'): "each record is presented as its characters less trailing spaces").
- On shapes 2 (LINAGE) and 3 (report) both compilers strip, because GnuCOBOL treats those files as line sequential.
- Refuter, wider than trailing spaces: with RECORD VARYING (probe `PB1664-refute\varrs.cob`, output `extra-run.txt`) GnuCOBOL writes a 4-byte length header inside the print stream
  (`\n \0 003 \0 \0 AAA \n \0 002 \0 \0 BB \n`); the pinned build writes `\r\n AAA \r\n BB \r\n`. GnuCOBOL's shape 1 is a record sequential file, fixed or framed, plus line-control bytes.

**Spec status (cite.py --check OK per the decision).** `§14.9.51.4 GR21`'s trailing-space strip is stated for a LINE SEQUENTIAL file only; `§9.1.7.2` leaves a record sequential record's on-medium form to the implementor, so
this is latitude and the precedence order applies (ISO silent, so GnuCOBOL). A record sequential file of fixed-length records has a `§13.18.43` record size, and the strip bypasses that size.

**Owed.** One adjudication that decides padding and framing together (the refuter's instruction), then the fix with `PB1664` or after it (same site family `src/Cobol.Net.Runtime/IO/SequentialConnector.cs`), and a rewrite of
DOC-A.1-146 (c'). Related: `PB1664`.

## Re-filed as a defect (analyses sweep, 2026-10-23)

Adjudicated read-only by an Opus cobol-adjudicator on main e7cf38ce4; accepted by the Mythos session.

The record sequential print stream (ORGANIZATION SEQUENTIAL, WRITE ... ADVANCING, no LINAGE, not a report file) writes each record less its trailing spaces and writes a variable-length record unframed, so the file is neither the record of §13.18.43's record size nor the record sequential medium form DOC-A.1-151 (a) documents. Repro probes/pb2509/advrs.cob: main writes AA and BB as two bytes each; GnuCOBOL 3.2.0 writes each 8-byte record whole. Repro probes/pb2509/varrs.cob: main writes 'AAA' and 'BB' bare; GnuCOBOL frames each record with its length header. ISO does not fix the bytes (§9.1.7.2; GR21's strip is stated for line sequential files only), so CLAUDE.md rule 1's precedence decides, as it decided the line end in PB1664. Determination (padding and framing together, as the refuter asked): a fixed-length record is written at its full record size, trailing spaces included (GnuCOBOL); a variable-length record is framed, because GnuCOBOL frames it and because DOC-A.1-151 (a) already makes the 4-byte little-endian prefix the one variable-length record sequential form of this implementation - write that prefix, not libcob's header, so one framing rule serves every record sequential file. Line controls (LF, FF for PAGE, bare CR for ADVANCING 0, PB1840's overprint) are unchanged. Fix site: src/Cobol.Net.Runtime/IO/SequentialConnector.cs:1460 (TrimRecordEnd on the print arm) and the frame encoder RecordFraming.EncodeFrameHead; rewrite DOC-A.1-146 (c'); goldens for both shapes; check NistDifferentialTests.Normalize and LinageConformanceTests.AssertBytes for trailing-space folding. Still held by PB3420 tier 3 (blocked_by unchanged); this sweep only turns the owed adjudication into a defect with its expected bytes. Harm classified wrong_answer as PB1664 and PB1540 were (bytes wrong against the rule-1 determination, not an ISO violation).

Evidence: Re-measured 2026-10-23 with the refuter's own sources (probes/pb2509): advrs (RECORD SEQUENTIAL, 01 PR PIC X(8), WRITE ... ADVANCING) - e7cf38ce4 writes '\nAA\n\nBB\rCC\f', GnuCOBOL 3.2.0 (-std=default) writes '\nAA      \n\nBB      CC      \f' (each record its full 8 bytes); varrs (RECORD VARYING 1 TO 8 DEPENDING ON) - ours '\nAAA\nBB\n', GnuCOBOL frames each record ('\n \0 003 \0 \0 AAA \n \0 002 \0 \0 BB \n'). The trailing-space strip at SequentialConnector.cs:1460 (TrimRecordEnd) is §14.9.51.4 GR21's LINE SEQUENTIAL rule applied to a record sequential file; §9.1.7.2 leaves the record sequential on-medium form to the implementor, so rule-1 precedence goes to GnuCOBOL. Our own DOC-A.1-151 (a) says every variable-length record sequential file is framed by the 4-byte prefix, which this print stream also bypasses. (The BB/CR/CC difference is PB1840's landed ISO determination, not this note.)
