**Observed.** On shape 1 (ORGANIZATION RECORD SEQUENTIAL, WRITE ... ADVANCING, no LINAGE, not a report file; probe `PB1664\advrs.cob`, compare `gc-run.txt` with `wo-run.txt`):
- GnuCOBOL 3.2.0 writes the FULL fixed-length record: `AA` followed by 6 spaces for an 8-byte record.
- The pinned build (`pin-eb06ac4`) strips trailing spaces from every print-stream record (`docs/CONFORMANCE.md` DOC-A.1-146 (c'): "each record is presented as its characters less trailing spaces").
- On shapes 2 (LINAGE) and 3 (report) both compilers strip, because GnuCOBOL treats those files as line sequential.
- Refuter, wider than trailing spaces: with RECORD VARYING (probe `PB1664-refute\varrs.cob`, output `extra-run.txt`) GnuCOBOL writes a 4-byte length header inside the print stream
  (`\n \0 003 \0 \0 AAA \n \0 002 \0 \0 BB \n`); the pinned build writes `\r\n AAA \r\n BB \r\n`. GnuCOBOL's shape 1 is a record sequential file, fixed or framed, plus line-control bytes.

this is latitude and the precedence order applies (ISO silent, so GnuCOBOL). A record sequential file of fixed-length records has a `§13.18.43` record size, and the strip bypasses that size.

## Re-filed as a defect (analyses sweep, 2026-10-23)

Adjudicated read-only by an Opus cobol-adjudicator on main 3205a4ac7; accepted by the Mythos session.

The record sequential print stream (ORGANIZATION SEQUENTIAL, WRITE ... ADVANCING, no LINAGE, not a report file) writes each record less its trailing spaces and writes a variable-length record unframed, so the file is neither the record of §13.18.43's record size nor the record sequential medium form DOC-A.1-151 (a) documents. Repro probes/pb2509/advrs.cob: main writes AA and BB as two bytes each; GnuCOBOL 3.2.0 writes each 8-byte record whole. Repro probes/pb2509/varrs.cob: main writes 'AAA' and 'BB' bare; GnuCOBOL frames each record with its length header. ISO does not fix the bytes (§9.1.7.2; GR21's strip is stated for line sequential files only), so CLAUDE.md rule 1's precedence decides, as it decided the line end in PB1664. Determination (padding and framing together, as the refuter asked): a fixed-length record is written at its full record size, trailing spaces included (GnuCOBOL); a variable-length record is framed, because GnuCOBOL frames it and because DOC-A.1-151 (a) already makes the 4-byte little-endian prefix the one variable-length record sequential form of this implementation - write that prefix, not libcob's header, so one framing rule serves every record sequential file. Line controls (LF, FF for PAGE, bare CR for ADVANCING 0, PB1840's overprint) are unchanged. Fix site: src/WiseOwl.Cobol.Runtime/IO/SequentialConnector.cs:1460 (TrimRecordEnd on the print arm) and the frame encoder RecordFraming.EncodeFrameHead; rewrite DOC-A.1-146 (c'); goldens for both shapes; check NistDifferentialTests.Normalize and LinageConformanceTests.AssertBytes for trailing-space folding. Was held by PB3420 tier 3 until the owner released it on 2026-11-03 (see below); this sweep only turns the owed adjudication into a defect with its expected bytes. Harm classified wrong_answer as PB1664 and PB1540 were (bytes wrong against the rule-1 determination, not an ISO violation).

Evidence: Re-measured 2026-10-23 with the refuter's own sources (probes/pb2509): advrs (RECORD SEQUENTIAL, 01 PR PIC X(8), WRITE ... ADVANCING) - 3205a4ac7 writes '\nAA\n\nBB\rCC\f', GnuCOBOL 3.2.0 (-std=default) writes '\nAA      \n\nBB      CC      \f' (each record its full 8 bytes); varrs (RECORD VARYING 1 TO 8 DEPENDING ON) - ours '\nAAA\nBB\n', GnuCOBOL frames each record ('\n \0 003 \0 \0 AAA \n \0 002 \0 \0 BB \n'). The trailing-space strip at SequentialConnector.cs:1460 (TrimRecordEnd) is §14.9.51.4 GR21's LINE SEQUENTIAL rule applied to a record sequential file; §9.1.7.2 leaves the record sequential on-medium form to the implementor, so rule-1 precedence goes to GnuCOBOL. Our own DOC-A.1-151 (a) says every variable-length record sequential file is framed by the 4-byte prefix, which this print stream also bypasses. (The BB/CR/CC difference is PB1840's landed ISO determination, not this note.)

Rule: §9.1.7.2 ('In record sequential files the length of each record is determined by any information the implementor may add to the record on the physical storage medium', checked); §14.9.51.4 GR21 (the strip, line sequential only, checked)

## Landed (wave 20261851, group B)

Re-probed on the branch build before the fix (the refuter's two probes, `advrs.cob` and `varrs.cob`): the shape-1 print stream wrote LF AA CR BB CR FF CC LF (the strip) and LF AAA LF BB LF (no frame head). The determination above is implemented as written, at the ONE predicate both the line end and the record's form ask, `SequentialConnector.IsRecordPrintStream` (a record sequential file with a record description and no LINAGE clause): `WriteAdvancingRecord` no longer calls `TrimRecordEnd` for it, writes a fixed-length record whole (`FitRecord` at the GR13 length), and for RECORD VARYING emits the DOC-A.1-151 (a) frame head inside `Present` (after the overprint return, so the head is part of the record) with the record's extent table, which `WriteAdvancing` now receives (the print-control WRITE used to drop it). The LINAGE and report arms keep GR21's strip (GnuCOBOL reclassifies both LINE SEQUENTIAL); the line controls are untouched. After: each fixed record is its whole 8 bytes (AA and six spaces), and each varying record is its 4-byte little-endian length word then its bytes. Witnesses: `conformance:cases/14.9.51-WRITE/pb2509_record_sequential_print_stream_form` and `PrintStreamLineEndConformanceTests` (whole record, controls between whole records, framed varying record, refused length writes no frame, LINAGE and line sequential still strip). DOC-A.1-146 (c') rewritten. `CompilerUnderTest.Normalize` folds trailing spaces of DISPLAY stdout only, never a print-stream file, and `LinageConformanceTests.AssertBytes` asserts LINAGE bytes that are full-width or text, so neither hides the change (`NistDifferentialTests.Normalize` the note names no longer exists).
