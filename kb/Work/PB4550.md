# PB4550 — report-varying-clause-not-implemented: Feature request: report writer VARYING clause (announced by -Wpending); its counter is "not defined" when the SOURCE clause precedes VARYING, and prints wrong values when VARYING comes first

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

Under `-std=cobol2014`, cobc 3.2 announces the report writer VARYING clause as not implemented (-Wpending) and refuses a reference to its counter written before the VARYING clause in the same entry: `COLUMN 1 4 7 ... SOURCE IS WS-E (RPT-I) VARYING RPT-I` gives "'RPT-I' is not defined". With the clauses in the other order (`VARYING RPT-I SOURCE IS WS-E (RPT-I)`) the program compiles with the same -Wpending warning, but each detail line prints `00 00` where `11 22 33` is expected. The VARYING clause defines its data-name as a temporary counter, set to 1, 2, 3 for the repetitions. Class: feature missing. Fuzz programs: fz00636, fz00638, fz01342, fz01343, fz02046, fz02048 (night fuzz-batch-3000-20261103, slice D2).

## Environment

`cobc (GnuCOBOL) 3.2.0`, WSL2 Ubuntu x86_64. Compiled with `cobc -x -free -std=cobol2014 -o p vary.cob` (`-fsyntax-only` gives the same diagnostics); no executable is produced, so nothing is run.

## Observed result

Compile, exit code 1:

```text
vary.cob:19: error: 'RPT-I' is not defined
   17 | PAGE LIMIT IS 20 LINES.
   18 | 01 RPT-DET TYPE IS DETAIL LINE PLUS 1.
   19 > 05 COLUMN 1 4 7 PIC 99 SOURCE IS WS-E (RPT-I) VARYING RPT-I.
   20 | PROCEDURE DIVISION.
   21 | MOVE 11 TO WS-E (1)
vary.cob:19: warning: RW VARYING clause is not implemented [-Wpending]
rc=1
```

With line 19 written `05 COLUMN 1 4 7 PIC 99 VARYING RPT-I SOURCE IS WS-E (RPT-I).` (the clauses in the other order), cobc prints only the -Wpending warning and exits 0. The run exits 0, and vary.out holds `00 00` on each of its two detail lines (followed by the blank lines that fill the page), not `11 22 33`.

## Expected result (per ISO)

The program is legal, in either clause order, and the report file holds two detail lines `11 22 33`: RPT-I is 1, 2 and 3 for the three column repetitions, so each picks the next table element. The rules are quoted from ISO/IEC 1989:2023; the report writer VARYING clause is in COBOL 2002 and Annex E of 2023 lists no report writer change from 2014.

- §2023:13.18.64.2 (checked): "<u>VARYING</u> { data-name-1"
- §2023:13.18.64.3 (checked): "a multiple LINE or multiple COLUMN clause"
- §2023:13.18.64.3 (checked): "Data-name-1 shall not be defined elsewhere in the source element"
- §2023:13.18.64.3 (checked): "This definition of data-name-1 may be referenced only within the current entry or a subordinate entry"
- §2023:13.18.64.4 (checked): "Each entry containing a VARYING clause establishes an independent temporary integer data item"
- §2023:13.18.64.4 (checked): "For the first occurrence, the value of arithmetic-expression-1 is moved to data-name-1. If the FROM phrase is absent, 1 is moved to data-name-1"
- §2023:13.18.64.4 (checked): "If the BY phrase is absent, 1 is added to data-name-1"

## Our compiler

WiseOwl COBOL (fresh judge, `cobol vary.cob --std 2014 --source-format free -o vary.dll`) compiles it with no diagnostic; `dotnet vary.dll` exits 0 with vary.out holding `11 22 33` twice. The same holds with the clauses in the other order.

## Fix site

cobc/parser.y `data_varying`: it calls CB_PENDING ("RW VARYING clause") and builds a field for the word only when the word has not been seen before (`CB_WORD_COUNT ($1) == 0`; a TODO notes that the ISO rules differ). The SOURCE operand earlier in the same entry has already referenced the word, so no counter is defined and the reference fails. When VARYING comes first the counter is defined, but its initial value is 0 (`cb_zero`), not 1, and it does not step through the column repetitions, so the output is wrong.
