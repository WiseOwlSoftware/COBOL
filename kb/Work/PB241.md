# PB241

**Rows:** `SR-14.9.9.3-2`

bare `CONTINUE` and `CONTINUE AFTER 0 SECONDS` are emitted through two different paths and no golden ever compares them, so §14.9.9.3 SR2's entire content — the equivalence — is unpinned.

Row: SR-14.9.9.3-2 ('If the AFTER phrase is not specified, then the statement is processed as if an AFTER phrase were specified with arithmetic-expression-1 specified as zero.' — `cite.py --check 14.9.9.3` OK, SR 2).

DERIVED EXPECTATION. Bare CONTINUE must be EXACTLY equivalent to `CONTINUE AFTER 0 SECONDS`, which by GR1 means (a) no suspension, (b) no exception — 0 is not less than zero, so EC-CONTINUE-LESS-THAN-ZERO cannot be set even under CHECKING ON — and (c) execution continues with the next executable statement. The failure shape to look for is a bare CONTINUE behaving OBSERVABLY differently from the AFTER-0 spelling under some ambient state.

WHAT THE STATIC READ SAYS, and it says the code is right. BindContinue returns BoundNop for the bare form and StatementEmitter emits nothing, so control falls to the next emitted statement. The two spellings were COMPARED rather than assumed: the AFTER-0 leg emits `CobolTiming.ContinueAfter((double)(0L), true)` (checked-in generated output, tests/conformance/2023/continue_after.g.cs), and ContinueAfter with 0.0 takes neither the `seconds < 0.0` arm nor the `secs == 0` sleep — it returns having touched nothing. Under `>>TURN … CHECKING ON WITH LOCATION` the AFTER form additionally wraps itself in ExceptionState.EnterStatement("CONTINUE", loc, …) / ExitStatement (exception_statement_ambient.g.cs:151-156), but that pair is SAVE-and-RESTORE and touches only _stmtName/_stmtLoc/_stmtLocNames, and nothing raises between them — so LastStatement/LastLocation are identical afterwards to what a bare CONTINUE leaves, and FUNCTION EXCEPTION-STATEMENT / EXCEPTION-LOCATION cannot tell the spellings apart. EcBinder gives BoundNop no EC wrapper and BoundContinueAfter one, but since neither can raise, that is not observable either. Checked for asymmetry elsewhere and found none: ProcedureTableBuilder.DeclIsTrivialExit tests `st.continueStatement() is not null`, true for BOTH forms, so it mis-classifies them equally.

WHY THE ROW IS STILL PARTIAL. The rule's entire content is an EQUIVALENCE between two spellings, and no test pins it. conformance:2023/continue_after does NOT contain a bare CONTINUE at all — its PROCEDURE DIVISION is DISPLAY "A" / `CONTINUE AFTER 0 SECONDS` / DISPLAY "B" / `CONTINUE AFTER WS-N SECONDS` / DISPLAY "EC=" … — so it pins only the AFTER-0 leg; the bare leg at 2023 is exercised by conformance:2023/ec_range_search (SEARCH WHEN bodies) and 2023/pb86_perform_times_function_count, which pin only consequence (c). Consequence (b) — the bare leg raising nothing even under CHECKING ON — and the equivalence itself have no golden anywhere. Nothing would fail if a future change gave BoundNop an EC wrapper or an ambient EnterStatement. 'Nothing raises' is a reachability claim, and reachability is measured, not deduced. (One earlier test-ref was also removed on this row as MISATTACHED: conformance:85/wavef_dbg_proc cannot exercise 2023-only text, since there is no AFTER phrase at edition 85.)

WHAT WOULD CLOSE IT: one 2023 golden under `>>TURN EC-CONTINUE-LESS-THAN-ZERO CHECKING ON WITH LOCATION` that executes `CONTINUE.` and then `CONTINUE AFTER 0 SECONDS.`, DISPLAYing FUNCTION EXCEPTION-STATUS, FUNCTION EXCEPTION-STATEMENT and FUNCTION EXCEPTION-LOCATION after each, and asserting the two triples are byte-identical (and that EXCEPTION-STATUS is empty after both).

SPEC REFS as carried by the row: §14.9.9.3 SR2 (cite.py OK); §14.9.9.4 GR1; §14.9.9.1; Annex E.3.3 item 14 (specs/ISO_COBOL.md:43957 — the AFTER phrase is a 2023 addition, so this SR has no 85/2002/2014 leg).

## Mechanism

src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs#BindContinue (:57-62 — `if (cont.arithmeticExpression() is not { } secs) return new BoundNop();`) into src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:147 (`public bool Visit(BoundNop n) => false;`, which writes nothing), versus the AFTER arm's `CobolTiming.ContinueAfter((double)(0L), true)` wrapped by src/Cobol.Net.Runtime/Exceptions/ExceptionState.cs#EnterStatement/ExitStatement (:79-88) and given an EC wrapper by EcBinder.cs:379-381 that the BoundNop does not get
