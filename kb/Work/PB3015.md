## Root causes (mechanisms, not symptoms)

1. **Two gates for one population.** The lander builds and runs the whole population on the dev box (saturated: plan §0
   "the next lever is less WORK, never more partitions"), then CI's Linux legs again under WSL on the same box, then
   `push-main.sh` holds the landing lease while CI runs the same population a third time on 20 runners. The local runs
   exist because CI was once not read (PB796: main red 29 h) and a CI red cost a landing; both are solved by making CI the
   gate mechanically, not by running CI's work locally first.
2. **Load-sensitive checks inside the per-landing gate.** Six drift-test files carry seven fixed time limits (owner rule
   2026-09-25: no wall-clock tests) and all 68 script self-tests run at every lander gate beside the legs; with the
   Windows and WSL gates concurrent they go red (8 of 14 RED events), and each red is a 7–53 min re-run plus attribution.
3. **Serial landing under a lease held through CI.** The lease is held 25–106 min per train including the ~15 min CI
   wait, so trains serialize at about one per hour; that fixed cost made 4–6-cluster trains rational (PROCESS-REVIEW
   2026-09-04), which made a red first run likely (4 of 6) and every in-train fix re-gates every cluster.
4. **The lander does everything** — bring in, verify, lease, gate ×2, oracle, review, fix reds, DEVLOG, push, measure
   — 150–220 turns per train; the quadratic cost law produced 10 landers for 6 trains.

## Proposal (an owner decision; on approval the design goes into `DESIGN-test-build-ci.md` §3 and `DESIGN-orchestrator-loop.md` §3–4)

- **P1 CI is THE whole-population gate; the box runs leg 1 only — for landers as for implementers.** Removes the 41 %
  and the load reds (each CI job has its own runner). The population check (§3.14.4) already runs in CI.
- **P2 Landing = GitHub's merge queue on `main`** (public repository: free). A PR per train or per cluster enters the
  queue; GitHub builds the speculative merge group, the workflow runs on the `merge_group` event (to be added beside
  `push`/`pull_request`), `ci-gate` stays the required check, and main advances in order. Replaces `push-main.sh`'s
  lease-held CI wait and `landing_lease.py` (the queue serializes). A bounced PR costs nothing on main; its branch goes
  to a finisher and re-enters.
- **P3 Reviews run on the implementer branch when it returns DONE** (a reviewer step in the rolling wave), never inside
  the lander's critical path.
- **P4 In-train reds eject by default**; with per-cluster PRs the question disappears.
- **P5 Load-sensitive checks leave the local gate:** script self-tests and time-limited drift tests run in CI's audits
  job (53 s, its own runner) and locally only when their inputs changed (PB2914's rule for every gate, not only the
  implementer's); no test keeps a wall-clock limit.
- **P6 Conflict-free hot files**, so queued PRs do not collide: one file per DEVLOG entry under `docs/devlog/` with
  `DEVLOG.md` generated (rule 6 unchanged: one entry per landing, descending); `DRIFT_RULES.md` and `kb/Work.base`
  generated in CI or verified-generated; plan §0 edited by the loop's units only.

**Expected effect:** lander minutes about −57 % (the gate windows and the CI wait leave the lander), trains of 1–3
become cheap, the first landing of a day lands within one 13-min CI cycle of the first DONE branch, no WSL gate, no
lease, no push-main. The bound becomes CI's cycle (merge groups batch several PRs per cycle). Risks: queued PRs that
touch the same generated file bounce (P6 is the answer); the `guard` job (12.8 min) becomes the long pole and can be
sharded; GitHub's 20-concurrent-job limit for public repositories serializes CI runs beyond one at a time.

**What it supersedes (each an owner decision to re-decide):** PB2515 batched gating PERMANENT (P1 generalizes it);
PB2514 gate cap 3 (kept for leg-1 gates); PB2537 landing lease, PB1732 WSL Linux gate, `push-main.sh` and the CI
invariant of 2026-10-04 (P2 replaces the mechanism; the invariant becomes "a PR bounced by the queue is a defect fixed on
its branch before re-enqueue"); MANDATORY-PRACTICES L2/L3/L10/L11; lander-train-brief steps 2b/3/3b/6/7; `units/land.md`;
`wf_rolling_wave.js`'s train prompt (PB3016).

**Constraint from the operator (2026-10-11 11:19 PDT), part of the design:** this box's working and temp drive `E:` is
ReFS; CI's Windows runner is NTFS; they delete differently (the PB2917 race, an open racing a DeleteFile reading
delete-pending as access denied, reproduced here in 20 of 7,200 probes and may not reproduce on NTFS, which deletes
POSIX-style). So the local leg 1 cannot hand every Windows race to CI: the Windows file-system race witnesses stay in
the local leg 1, PB1957's local-vs-CI survey lists the filesystem, or one CI Windows leg runs on ReFS / a Dev Drive.

## Owner questions (asked one at a time, in this order)

- Q1 (asked 2026-10-11 ~11:20 PDT) Approve P1 + P2 (CI as the whole-population gate; a merge queue as the landing)?
  **Owner, verbatim:** "I don't want the CI / CD to be the first, maybe only tests run on the code changes. We need
  local testing to confirm the targeted charges are correct. THe CI / CD should primarily ensure no regression on the
  remaining codebase. Another consideration, local runs are free. Github runs cost action". Read as the principle the
  design must keep: **local testing of the TARGETED change comes first for every change** (the implementer's leg 1 and
  the lander's leg 1 over its clusters' own tests, likely reds and reached cases), **CI is the regression net over the
  rest of the codebase**. Fact for the cost consideration: `BrentRector/COBOL` is PUBLIC (`gh repo view`: visibility
  PUBLIC), and GitHub-hosted standard runners are free for public repositories; only larger runners or a private
  repository bill minutes. P1 is re-stated to the owner in those terms as Q1a; P2 becomes Q1b.
- Q1a Keep the local targeted gate (leg 1) FIRST for every change, including the lander's train, and let CI be the
  whole-population regression net — so the lander's local whole-population run and the WSL copy of CI's Linux legs
  go, except the Windows file-system race witnesses, which stay in leg 1 (the ReFS constraint)?
  **Owner 2026-10-11 ~11:30 PDT: "Yes (Recommended)"** — DECIDED: the lander's local gate is the targeted leg (its
  clusters' own tests, the likely reds, the Windows file-system race witnesses that reproduce only on this box's ReFS
  drive); the lander's local whole-population run and the WSL copy of CI's Linux legs are removed; CI stays the
  whole-population regression net on the pushed head. The implementer's leg-1 gate is unchanged.
- Q1b Landing through a GitHub merge queue (CI runs once per merge group, which batches several trains; no landing
  lease, no push-main CI wait), or keep `push-main.sh` with the lease?
  **Owner 2026-10-11 ~11:33 PDT: "GitHub merge queue (Recommended)"** — DECIDED: one pull request per landing enters
  the merge queue on `main`; the workflow runs on `merge_group`; `ci-gate` stays the required check; main advances in
  order; `landing_lease.py`, `push-main.sh`'s CI wait and the `ci/**` branches are retired.
- Q2 DEVLOG shape under P6: one file per entry with `DEVLOG.md` generated?
  **Owner 2026-10-11 ~11:36 PDT: "Yes, one file per entry (Recommended)"** — DECIDED: `DEVLOG/NNNN-<slug>.md` per
  landing, numbered by `alloc.py devlog`; a script renders the descending narrative as a view (the kb/Work pattern); a
  CI check refuses a landing that adds no entry file; rule 6 unchanged (one entry per landing on main, newest first).
- Q3 PR granularity: per cluster, or per train of 2–3?
  **Owner 2026-10-11 ~11:40 PDT: "One PR per finished branch (Recommended)"** — DECIDED: every finished implementer
  branch is its own pull request; the loop reviews it, rebases it, runs the targeted local gate, verifies its DEVLOG
  entry file and enqueues it; GitHub tests the queued pull requests together per merge group and lands them in order; a
  CI red bounces one branch to a finisher while the others land. The train, the lander role and `train_apply.py`'s
  assembly step retire; the loop's `land` unit becomes the `enqueue` unit.

- Q4 (the owner's own question, ~12:45 PDT, verbatim): "doesn't think mean many (all?) of the Linux only failures that
  we caught in WSL runs now aren't found until CI (very late)". Answer from the evidence: yes — 3 of 38 clusters on
  2026-10-10 had Linux-only reds, all in their own tests (52F locale golden, 52B lock-race fix, 1055 D host-path length),
  each caught by the WSL run before a CI round trip. Correction put to the owner: the targeted leg runs on BOTH hosts
  (Windows natively, Linux under WSL, leg 1 only on each) in the implementer's gate and at enqueue; only the
  whole-population regression run is CI's; until the Linux leg-1 run exists the land units keep today's WSL gate.
  **Owner: "Yes, both hosts, leg 1 (Recommended)"** — DECIDED (DESIGN-test-build-ci §3.17.3; PB3022 item 10). The Mythos GO of 12:34 that
  dropped the WSL gate for land units was CHANGED at 12:37 (operator mailbox 20261011-123658).
