# PB5635 - the digit-capacity rule is written twice

**Sites:**
- `src/WiseOwl.Cobol.Frontend/Expressions/CompileTimeExpressionEvaluator.cs:143` (`CompileTimeExpressionEvaluator.WithinLiteralCapacity`)
- `src/WiseOwl.Cobol.Frontend/Parsing/LiteralScreen.cs:145` (`LiteralScreen.ScreenDigitCapacity`)
- `src/WiseOwl.Cobol.Editions/EditionInfo.cs:40` (`EditionInfo.DigitCapacityExcess`)
- `tests/WiseOwl.Cobol.Tests.Unit/LiteralDigitCapacityDriftTests.cs` (new: the drift test of the fix direction)

**Mechanism.** kb/Work PB5529 (landed) made the digit capacity of a fixed-point numeric literal one question, asked at the
literal's node in `LiteralScreen.Run` under the one descriptor choice `EditionInfo.DigitCapacityExcess` (COBOL0801 over
31, COBOL0802 over 18 at 85). `CompileTimeExpressionEvaluator.WithinLiteralCapacity` (called at lines 115 and 264) is a
second copy of the same rule: it counts the digits of a literal in a constant entry or directive expression against the
evaluator's own `_literalDigits` and reports under `CtDiagCode.ArithmeticRule` with its own text citing §2023:8.3.3.3.2. Two
copies of one rule drift (CLAUDE.md rule 4 and 5): when the 85 limit or the code set changes, the evaluator keeps the old
limit.

**Fix direction.** Have the evaluator ask `EditionInfo.DigitCapacityExcess` (or drop its check where `LiteralScreen` has
already screened the same node, so one literal draws one verdict), delete `_literalDigits` and the second message, and add
a drift test that no other file counts `IsAsciiDigit` digits against a literal limit. Witness: a 19-digit and a
32-digit literal in a CONSTANT entry and in a `>>DEFINE` operand at 85 and 2023, each drawing exactly one diagnostic.
