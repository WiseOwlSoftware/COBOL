## Finding — `dynamic-capacity-tables` (crashes; rows `GR-8.5.1.9.6-2`)

**Mechanism.** The maximum capacity is only the constant MaxOccurrences; a growth that exhausts runtime resources below it dies with an uncaught .NET OutOfMemoryException instead of the fatal EC-BOUND-TABLE-LIMIT

**Repro.** >>TURN EC-BOUND-TABLE-LIMIT CHECKING ON; 01 N PIC 9(10) VALUE 1000000000. 01 T. 05 E OCCURS DYNAMIC CAPACITY IN K. 10 F00..F39 PIC 9(18) (40 fields). DISPLAY "BEFORE". SET K TO N. DISPLAY "AFTER K=" K. (out/probe/dct/p5c.cob, --std 2023)

**Expected from the spec.** Abnormal run-unit termination on the fatal EC-BOUND-TABLE-LIMIT (or its USE declarative runs): 8.5.1.9.6 2) - the condition 'shall exist when an operation attempts to increase the capacity ... to a value higher than the maximum capacity of the table based on the resources available at runtime'; 8.5.1.9.1 defines the maximum capacity as the limit 'imposed by the implementor and by current resource availability'. For the SET path 14.9.39.4 GR30 additionally leaves the capacity unchanged.

**Observed / reasoning.** Observed 'BEFORE' then the .NET runtime's 'Out of memory.' - process killed, no COBOL condition. GrowTo tests only newCount > MaxOccurrences (0x3FFFFFFF); Array.Resize and the seeding loop are not guarded, whereas the sibling CobolDynString and CobolPtr catch OutOfMemoryException and raise their COBOL conditions. The fixed-limit arm conforms (p5a: E(2000000000) -> EC-BOUND-TABLE-LIMIT fatal). Fix shape: catch the allocation failure in GrowTo (the one growth primitive both implicit and explicit paths share) and raise BoundTableLimitError with the capacity unchanged.

**Code site.** src/Cobol.Net.Runtime/Values/Tables/CobolDynTable.cs#GrowTo

## What the fixer owes

CobolDynTable.GrowTo translates allocation failure (and any implementor maximum) into the fatal EC-BOUND-TABLE-LIMIT; document the implementor maximum (Annex A.1).
