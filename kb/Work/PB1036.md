## Landed 2026-09-24 (w59c, branch worktree-agent-a7a6a133f2e06c321)
Re-probed first on the w59c Debug build of `df452130e`: `fopen.cob` (this note's repro) printed `AFTER GS=41`, the
`merge-p2/m4` shape printed `R BBB / R AAA / R CCC`, a SORT inside an input procedure ran to completion, and an SD
`VARYING 2 TO 5` RELEASE at 1 and 9 released both — all four conditions unraised. After the fix: `DECL
EC-SORT-MERGE-FILE-OPEN / AFTER GS=00`, `DECL EC-SORT-MERGE-SEQUENCE`, `DECL EC-SORT-MERGE-ACTIVE`, and two
`DECL EC-SORT-MERGE-RELEASE`.

**One mechanism, the one the other families use.** Four `CheckingFlags` fields, four `ExceptionEngine` helpers
(`FatalIfEnabled`), four `EcEmitter.FatalAmbientGates` rows, and `EcBinder.QueryFor` arms for BoundSort /
BoundMerge (plus -ACTIVE / -RELEASE on BoundRelease and -ACTIVE on BoundReturn). Every raise is `CobolSort`'s, at the
point the rule names: `Init` (-ACTIVE, before the store is touched), `ReleaseStatement` / `ReturnStatement` (-ACTIVE
ahead of EC-FLOW-*; the record-range test of §13.18.43.4 GR14 b)/GR19 b), with the DEPENDING ON slice moved into the
runtime so EC-BOUND-REF-MOD cannot pre-empt it), `Release` (§14.9.40.4 GR12 b) / §14.9.24.4 GR7 b) against the READ
size), `FileNotOpen` (per file, SORT per phase, MERGE at statement start) and a per-stream scan in `Merge`.

**Design call (the w56d lead), recorded as docs/CONFORMANCE.md §3 D-SMA:** (a) -ACTIVE wins over EC-FLOW-RETURN /
EC-FLOW-RELEASE when both are enabled (§14.6.13.1.1 leaves it undefined); (b) a condition the SORT/MERGE statement
raised ITSELF is disposed of by the verb (§14.6.13.1.3 2)) — declarative, statement terminated, run unit continues.
"Itself" is a runtime fact, so `CobolSort` MARKS it: its five statement entries (Init, FileNotOpen, the implicit
Release, Sort, Merge) run under an exception filter that sets `CobolFatalException.RaisedBySortMerge`, and the SORT/
MERGE guard (`EcEmitter.VerbDisposes`) re-throws only unmarked conditions — so an EC-LOCALE-* from a locale-collated
key is the verb's too, while a RELEASE/RETURN statement's raise or a procedure statement's keeps 5)/7). (A first cut
keyed on the EC-SORT-MERGE family name; the gate's DefectiveRowCoverage red over the residual it left on
GR-14.6.13.1.3-2 is what moved it to the mark.) (c) checking off keeps every pre-PB1036 behaviour. The statement
body after `Init` became `try … finally { Close }` so a raise the guard disposes of never strands a store in a
procedure phase (which would raise -ACTIVE against the next, innocent SORT).

**Sibling found in the same switch and fixed:** `QueryFor` had NO SORT/MERGE arm at all, so the EC-I-O family was
never asked for the implicit transfers' files — `>>TURN EC-I-O CHECKING ON` over `SORT … USING <missing>` ran no
EC-I-O declarative and PB993's `__verbRule` arm was unreachable. The arms now ask EC-I-O per USING/GIVING file
(golden case H: `IO=EC-I-O-PERMANENT-ERROR`).
