### Row SR-13.18.57.3-3 — PARTIAL (no separate finding; the adjudicator's / refuter's record)

Code location: `src/Cobol.Net.Compiler/Binding/DataBinder.cs#CheckStrongTypeDeclarations; src/Cobol.Net.Compiler/Binding/Model/StrongTypeModel.cs`

'If type-name-1 is described with the STRONG phrase, the subject of the entry shall not be renamed in whole or in part.' CheckStrongTypeDeclarations draws COBOLNET1532 for any RENAMES whose range touches a strongly-typed item. Probes: `66 RN RENAMES A.` (part) -> 1532; `RENAMES A THRU B` (whole) -> 1532; the same over a WEAK type compiles and runs ('PQ'). Since SR6 confines a STRONG subject to level 1 or a strong record, and a RENAMES works within one record, 'in part' is fully covered. cite.py --check OK. probes under out13/probe/type-clause-p1/ (pinned adj-d1 cobol.exe, --std 2023 unless noted) || REFUTED: PARTIAL — One question decides both SR3 and SR6: is an item typed through a non-STRONG TYPEDEF whose own entry is `TYPE S` (S STRONG) strongly typed? Literally (§8.5.3.1: 'described with a TYPE clause that references a type declaration specifying the STRONG phrase'; SR3/SR6 'If type-name-1 is described with the STRONG phrase') it is NOT; via §13.18.58.4 GR3 ('All other data description clauses ... are assumed by data defined using the type-name') it assumes TYPE S and IS. The compiler answers it BOTH ways: ExpandType sets item.StrongType = template.TypedefStrong (false for S2) and gates SR6 on template.TypedefStrong, but CopyEntryDescription then does `to.StrongType |= from.StrongType` (true), so the item is treated as strong for SR3/RENAMES and every strong-use restriction. Probes: sr6_strong_via_chain (`01 S2 TYPEDEF TYPE S.` + `01 G. 05 Y TYPE S2.`) COMPILES and runs -> a StrongType item at level 05 in an ordinary group, no SR6 diagnostic; sr3_renames_strong_chain (`01 X TYPE S2.` + `66 RN RENAMES SA.`) -> COBOLNET1532. Under either reading one of the two rules is wrong (literal: SR3 over-rejects legal RENAMES; GR3: SR6 misses the level screen). The adjudicator probed only direct `TYPE S`; the indirect-chain edge is unverified and the compiler's own model is self-contradictory there, so CONFORMS cannot stand. Direct cases (part/whole/THRU into strong member of a strong record) correctly reject.
