**Site.** `src/WiseOwl.Cobol.Runtime/Values/Numeric/CobolDec.cs` line 124, `ExactDigits`. It formats every finite binary64 with the
767-digit exact formatter ("E766") to keep 38 digits and a sticky bit. It now runs on every float operand of standard-decimal
arithmetic and relations (`FromBinary64`) and on every binary64 sender of a floating-point numeric-edited store in EVERY arithmetic
mode (`FromBinary64ToOdd` via `FormatFloatStore` / `TryFormatFloat(double)`).

**Claim.** The PB1606 report called the path cold, but the cost was not measured, and the native-mode MOVE path is not cold. The
reviewer measured about 4 us a lift.

**To settle.** Measure it with a BenchmarkDotNet witness, then replace the string round trip with an integer-arithmetic exact
expansion (the 53-bit mantissa and the binary exponent give the 38 digits and the sticky bit directly), pinned by a differential
against the current formatter over a corpus of doubles. Related: PB1606 (the landing that widened the callers). Not a duplicate of
PB3018, which concerns the operand lift digit count of the Dec lane, not the cost of the binary64 expansion.

## Adjudication 2026-10-25 (mythos lane, pinned main 51103b9a1)

**Final verdict:** TEST-GAP  
**Checkpoint (full record):** `E:/COBOL-coord/scratch/mythos/adj-20261025/PB3627.json`

**Expected from the spec:** No rule of the standard bears on speed. Section 8.8.1.5.1 makes the float-to-SDIDI conversion mechanism implementor-defined, and 8.8.1.5.2 lets implementors use 'the method or methods' they choose so long as the results equal decimal128's. docs/CONFORMANCE.md (the PB1606 paragraph) already records the determination: the binary64's EXACT value, rounded once to 34 digits (FromBinary64), or kept as a 38-digit round-to-odd significand (FromBinary64ToOdd). So a replacement must give the same (38-digit significand, exponent, sticky) triple for every finite binary64, which makes it a behavior-neutral change. PROMPT.md section 4 item 3 makes performance a review criterion but sets no number. The PB2117 performance baseline (scripts/arch/perf_baseline.py, tests/WiseOwl.Cobol.Benchmarks/Programs) has no floating-point program, so no recorded band is broken. The path is slow and nothing watches it, which makes this a TEST-GAP under the brief, not a DEFECT.

**Citations checked:**
- OK §8.8.1.5.1 (General) The mechanisms for conversion of data items described with a usage of float-short, float-long, or float-extended into standard-decimal intermediate data items are defined by the implementor.
- OK §8.8.1.5.2 (Standard-decimal intermediate data item) Implementors can use the method or methods, and whatever format or formats they choose.

**Repro and observed:** Ran on pinned main 51103b9a1 with src/WiseOwl.Cobol.Cli/bin/Debug/net10.0/cobol.exe --run. The program loads the ReadyToRun Release runtime, byte-identical to bin/ReadyToRun/win-x64. Files are under E:/COBOL-coord/scratch/mythos/adj-20261025/PB3627/. Each figure is per statement over 2,000,000 iterations, two runs each. perf1.cob (native arithmetic): MOVE FLOAT-LONG TO PIC +9.9(15)E+99 (FormatFloatStore(double) -> FromBinary64ToOdd -> ExactDigits) took 3715/3235 ns. MOVE fixed S9(6)V9(6) TO the same receiver took 450/365 ns. MOVE FLOAT-LONG TO -9(6).9(6) (CobolFloat.ToScaledUnchecked, integer arithmetic) took 620/455 ns. perf2.cob (ARITHMETIC IS STANDARD-DECIMAL): COMPUTE D = F + 1 (CobolDec.FromBinary64) took 3030 ns against 65 ns for COMPUTE D = DX + 1 with a fixed operand, about 45x. IF F > DX took 2790 ns. So ExactDigits is about 2.8-3.3 us a lift, close to the reviewer's 4 us. It is ~85% of a float-edited MOVE in the default mode and nearly all of a float operand's cost in standard-decimal arithmetic. Feasibility check: intexact_check.py runs the integer expansion (Decompose to man*2^e2; e2>=0 gives man<<e2 and, past 38 digits, (man<<(e2-s))/5^s; e2<0 gives q=(man*5^(k-s))>>s with sticky = the low s bits nonzero, s = digits-38). Against the exact Decimal(binary64) it had 0 mismatches over 304,005 doubles (4,005 edges: every power of two, every 10^i and its neighbours, the subnormal and maximum limits, plus 300,000 doubles uniform by bit pattern). The BenchmarkDotNet witness project is written (bench/Program.cs, with a C# differential against the shipped FromBinary64ToOdd) but was NOT run: scripts/hooks/fleet_active_build.py refuses dotnet build in a scratch directory while sibling adjudicators are live.

**Action:** Witnesses to write. (1) A BenchmarkDotNet class tests/WiseOwl.Cobol.Benchmarks/Numeric/BinaryLiftBenchmarks.cs. It measures FromBinary64, FromBinary64ToOdd and FormatFloatStore(double) on a 64-value typical corpus and a 64-value uniform-by-bits corpus, with FromApproximation and CobolFloat.TryExactScaled as baselines. bench/Program.cs is the draft. (2) A FLOATHOT.cob perf-baseline program (the perf1/perf2 shapes), so perf_baseline.py records a band for the float lift. (3) A unit differential test that pins the new expansion against an exact reference ('E766' text or BigInteger ExactRatio) for every power of two, every 10^i and its neighbours, the subnormal and maximum limits, and a seeded uniform-by-bits corpus, comparing (Sig, Exp, Sticky). With the witnesses in place, replace ExactDigits' string round trip with the integer expansion. intexact_check.py proved it exact over 304,005 doubles. Build it on CobolFloat.Decompose (make it internal), which is already the runtime's ONE exact decomposition of a binary64, so the runtime keeps one mechanism, not a formatter-based twin (PROMPT.md section 4 item 4). The UInt128 lanes (e2>=0 with bit length <=127; e2<0 with k<=31) need no BigInteger. Keep FromBinary64 and FromBinary64ToOdd's contracts unchanged and update their doc comments, which name 'E766'.
