# PB462 — the "fail loud" arm does not compile

**Row:** `GR-14.9.39.4-6` (SET Format 4/5 — *the literal in the VALUE clause … is placed in the conditional
variable according to the rules for the VALUE clause*). From the b2 adjudicator `set-statement-p5` and its
refuter. **Re-run on the HEAD `cobol.exe` (base 89044aa0)**; reproduces unchanged.

## THE MECHANISM

`SetEmitter.EmitSet` (`SetEmitter.cs:174-201`) dispatches on the conditional variable's PICTURE category. A
GROUP conditional variable has no `PicInfo`, so `pic?.Category` is `null`, no arm matches, and control reaches
the default:

```csharp
SetEmitter.cs:198
    _ => LoudValue("string", $"SET condition '{cond.Name}' over a group parent"),
```

`EmitCore.LoudValue` (`EmitCore.cs:96`) takes the C# type as a **string** and renders
`NotImplemented.Value<string>(…)`. The receiver, however, is the group's generated **record struct**, so the
emitted assignment is a C# type error and the BACKEND COMPILATION fails. The user gets a Roslyn error pointing
into generated C# — not a COBOL diagnostic, and not even the intended loud runtime failure.

**The pattern is general, and that is the finding.** `LoudValue`'s type argument is a hand-written literal at
every call site, so *every* site that hardcodes `"string"` for a receiver that may be a group or a struct
carries the same latent Roslyn error. `ConditionRenderer.cs:288` is a second such site
(`LoudValue("string", …)` for a boolean relation operand).

**A group conditional variable is legal beyond argument.** §14.9.39.4 GR6 names the case explicitly, and the
only rule anywhere on what may BE a conditional variable excludes four ELEMENTARY classes and never a group.
Worse, because the only way to reach a zero-length conditional variable is a group with a zero ODO, GR6's own
"If the length of the conditional variable is zero, the SET statement leaves it unchanged" sentence is
UNREACHABLE behind this failure — a rule that cannot be exercised at all.

## THE RULES, QUOTED, EACH `--check`ed ON THIS TREE

* `--check 14.9.39.4 "If the TRUE phrase is specified, the literal in the VALUE clause associated with
  condition-name-1 is placed in the conditional variable according to the rules for the VALUE clause"` →
  **OK §14.9.39.4 6) (General rules)**. The same rule continues "…except that when the conditional variable is
  an alphanumeric group item, bit group item, or national group item to which a table is subordinate, its length
  is determined as specified in 13.18.38, OCCURS clause", and ends "If the length of the conditional variable is
  zero, the SET statement leaves it unchanged." — a `--check` of that last sentence also returns
  **OK §14.9.39.4 6)**, the same rule.
* `--check 13.18.60.3 "An elementary data item of class index, message-tag, object, or pointer shall not be a
  conditional variable"` → **OK §13.18.60.3 11) (Syntax rules)**. Re-derived, not inherited: it bars four
  ELEMENTARY classes and says nothing about groups.
* `--check 14.9.39.4 "If more than one literal is specified in the VALUE clause, the conditional variable is set
  to the value of the first literal that appears in the VALUE clause."` → **OK §14.9.39.4 6)**, the same rule —
  and this half IS implemented correctly (`SetEmitter.cs:178` takes `cond.Values[0].Low`).

The generated statement is `CV = NotImplemented.Value<string>("SET condition 'CV-YES' over a group parent");`.

**Expected.** `SET CV-YES TO TRUE.` places the first VALUE literal in the group by the VALUE-clause rules, with
the group's length determined per the OCCURS clause for the ODO case, so `gr6-groupcv` prints `CV=[ABC]` and
`gr6-groupodo` prints `CV3=[ABC]` for a length-3 group and leaves it unchanged at `WS-N = 0`. Today neither
program compiles.

## THE CODE SITES AND THE SHAPE OF THE REPAIR

| site | today |
| --- | --- |
| `CodeGen/Verbs/SetEmitter.cs:186-199` | the `pic?.Category` switch; `null` (group) falls to `:198` |
| `CodeGen/Verbs/SetEmitter.cs:198` | `LoudValue("string", …)` — a hardcoded C# type against a record-struct receiver |
| `CodeGen/Emit/EmitCore.cs:96` `LoudValue(string csType, string feature)` | the type is a caller-supplied literal, so it can disagree with the receiver |
| `Binding/Procedure/Verbs/SetBinder.cs:442` `BindSetCondition`, `Binding/Model/Condition88.cs:24` `Values` | the bind side, correct |

⛔ **Two repairs, and the smaller one alone is not enough** (CLAUDE.md rule 5):

1. **Implement the group arm.** It is not an exotic shape — the rule names it. The store is a width-determined
   character store into the group's image, with the width coming from the OCCURS clause for a subordinate table
   (and zero length meaning "leave unchanged"). That also unblocks GR6's zero-length sentence, which no test can
   reach today.
2. **Make `LoudValue` incapable of this.** A "fail loud" placeholder whose type is a hand-typed string can
   always disagree with its receiver, and when it does the failure lands on USER source as a Roslyn error — the
   one failure mode the project forbids. Derive the C# type from the receiver (the place/`DataItem` already
   knows it) instead of accepting it as text, so the next unimplemented arm fails loud at RUN time as designed.
   The sweep is "every `LoudValue` whose type argument is not derived from the receiver".

The two together also close the door on the general rule: any emitter switch over `pic?.Category` that has a
`_ =>` arm should be asked what the `null` (group) case does.
