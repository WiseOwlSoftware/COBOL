# PB986 — LANDED (wave 1011 B)

## Repro — measured
`scratchpad/w48z/pcorr4.cob`: `01 SRC. 05 S0 … 05 SG. 10 S1 … 10 N1 … 05 S2 PIC X(3). 05 ST OCCURS 2. 10 S4 PIC X.
05 SR PIC X(2). 05 S3 PIC X(3).` then `66 SALIAS RENAMES SG THROUGH S3.` →
`pcorr4.cob(15,8): error COBOLNET1655: 'SALIAS' RENAMES SG THRU S3: the record's leaves do not tile the alias's storage window`.

## The rule
`OK  §13.18.45.3 3)` — "Data-name-1, data-name-2 and data-name-3 shall not be subject to any OCCURS clauses."
SG and S3 (data-name-2/-3) are not subject to an OCCURS; ST lies strictly INSIDE the window. Nothing in §13.18.45 bars a
table inside the renamed range, so the source is legal and SALIAS's window is the contiguous storage SG … S3.

## Code site
`DataBinder.cs` ≈5779, the RENAMES tiler's walk: `leaves.Add((n, Offset(n), n.ImageWidth, n.Occurs ?? 1))` — an elementary
leaf under an OCCURS GROUP carries no `Occurs` of its own, so S4 is counted once where the window holds two occurrences
and the tile falls one byte short.

## What the fixer owes
Multiply each leaf by the product of the OCCURS counts on its ancestors inside the window (or tile by storage extent,
not by leaf enumeration). Sweep every other walk that sizes a window by enumerating leaves (`GroupValueSlicer`, the
MOVE CORRESPONDING alias path PB966 added). Golden: pcorr4 at 2002 (RENAMES THRU over a table-bearing window, then
MOVE / DISPLAY through the alias). ⚠ The lead's D-CORR66 survey (how GnuCOBOL/IBM/MF treat MOVE CORRESPONDING over a
66 alias) is unmeasured; it is not filed separately — PB966's determination stands until an owner asks for it.

## Landed 2026-10-04 (wave-1011 implementer B)

**Re-probe (own build of 28fc8a7f9).** The note's shape (a table group inside `RENAMES SG THROUGH S3`) was refused
COBOLNET1655 "does not tile the alias's storage window".

**Mechanism.** The RENAMES tiler (`DataBinder.cs`, the THRU arm of the post-build RENAMES pass) modelled every
elementary item as one contiguous run `(offset, width, own occurrences)`. A leaf under an OCCURS GROUP is not one
run: it recurs at the GROUP's stride (`05 ST OCCURS 2. 10 S4. 10 S5.` is S4 S5 S4 S5, so S4 is two cells two bytes
apart), and a leaf with its own OCCURS under an OCCURS group is a run per group occurrence. The walk now carries the
enclosing table groups and adds one run per combination of their occurrences that the WINDOW reaches (occurrence
ranges computed arithmetically from the window, so a large table elsewhere in the record is never expanded);
`RenamesSpanPart` gained `Outer` (the 1-based occurrence of each enclosing table group, outermost first), and
`ReferenceResolver.PlaceForRenames` builds each part's cell place with `part.SubscriptsFor(own)` (the group
subscripts, then the leaf's own). A dynamic-capacity table is not entered: SR8 (`RenamesRangeFault`) bars it from every
legal range.

**Sweep.** The other walks that touch a RENAMES window: `RenamesInfo.IncludedElementaryItems` (§13.18.45.4 GR2
MEMBERSHIP for §14.7.6 / PB966 — declaration order, each table item once, correct by definition), `AliasAtoms`
(reads `Span`, so it follows), `BitLayout.StartBitOf/RunBits` (bit leaves only, relative offsets); `GroupValueSlicer`
slices a group VALUE and never meets an alias. `rg "Occurs \?\? 1" src` lists the remaining leaf-width sums: all
per-item storage widths, none a window tiler.

**Witness.** `conformance:2002/pb986_renames_through_table_window` — a 27-character window with a one-level table
group, a table group whose leaf has its own OCCURS, and a two-level table, read through the alias, then written
through it (the characters land in every cell); expected text derived from §13.18.45.4 GR2's storage order.
