# PB374 — the MCS module is named at its STATEMENTS and silent everywhere else

Found by witness cluster B2's two-arm sweep and **re-measured at the landing** with the built `cobol.dll`, not
carried from the report — the screen half of the original finding had already been closed by [[PB260]] in the
meantime, and this note is what actually remains.

## The measurement (2026-09-02, `--std 2023`)

| source | today |
|---|---|
| `>>TURN EC-MCS-ABNORMAL-TERMINATION CHECKING ON` | **compiles clean, exit 0, no diagnostic** |
| `01 WS-TAG USAGE MESSAGE-TAG.` | `COBOL0001: no viable alternative at input 'MESSAGE-TAG'` (twice) |
| `SEND` / `RECEIVE` | `COBOL1578 mcs-facility-unsupported` — named, accepted inert |

So one module has three postures: named-and-inert at the statements, SILENT at the exception-names, and a
GENERIC parse error at the data item. That is the non-uniformity `docs/CONFORMANCE.md` §4's preamble describes,
with MCS now the last item that still has it — items 2, 3 and 4 were made uniform by [[PB260]] and by witness
cluster B2.

## Why each half is a defect

**The exception-names.** §14.6.13.1.1: "The implementor is not required to raise any exception conditions for
level-3 exception-names that are associated with optional language elements … that the implementor has not
implemented." That licenses raising NOTHING; it does not license ACCEPTING the name. The five EC-MCS names sit
in `ExceptionCatalog` with zero setting sites, so a `>>TURN`, a `RAISE`, a `USE AFTER EXCEPTION CONDITION` or a
`PERFORM … WHEN` on one compiles against a facility that does not exist and quietly never fires — a catalogued
name with a reader and no setter reads as implemented support to every consumer that can see it. This is the
IDENTICAL defect COBOL1710 closed for EC-VALIDATE and the EC-FLOW commit family, and COBOL1707 closed for
EC-SCREEN.

**The data item.** `MESSAGE-TAG` is the MCS module's USAGE (§13.18.60). A bare `COBOL0001` tells the user
nothing about WHY, while the same module's statements are named — so a program that declares a message tag and
never sends learns less than one that sends.

## ⛔ The posture is NOT the one the other three modules took, and that is the whole difficulty

MCS is **Annex A.3 item 4 — PROCESSOR-DEPENDENT**, not Annex A.4 optional. Its licence is §4.2.6, which is
accept-and-WARN and makes the compile-time warning mechanism mandatory; it is not A.4.1's "shall accept the
syntax … only when support is claimed". So the fix is **not** to add EC-MCS as a row in
`EcNameResolution.DeclinedEcFamilies` beside EC-SCREEN and EC-VALIDATE — those rows REFUSE, and refusing a
processor-dependent element would be the wrong posture, not merely a stricter one. What is owed is the
accept-inert WARNING (COBOL1578's channel) at both surfaces:

1. an exception-name arm that **warns** for the EC-MCS family and lets the name resolve, and
2. a `MESSAGE-TAG` usage surface that parses and draws COBOL1578 rather than a parse error.

⚠ The refusal table's row shape is still the right structure to reuse — it already carries a DESCRIPTOR per row
and the seam reads the descriptor's severity, so an accept-inert row is a Warning-severity descriptor and
nothing else changes. That is why the table was built this way (CLAUDE.md rule 5).

⚠ And a warning needs an assertion: `DocumentedNonSupportWitnessTests` records that **COBOL1578 is the one
non-support warning nothing in `tests/` asserts**, so whatever lands here owes that assertion too
(feedback_green_test_can_hold_a_gap_open).

## Extended 2026-09-24 by REGISTRAR 14c (lane-3 batch d1-14c, pinned tree `68bbdb00f`)

A THIRD MCS surface (finding, receive-statement, under-rejects): CobolParserCoreBase.facilityWord gates the 2023 asynchronous-messaging RECEIVE/SEND arms on RESERVATION, not on INTRODUCTION. RECEIVE is reserved at 85 (the 1985 communication module) and at 2023, so at `--std 85` the 2023-only §14.9.31.2 format (`RECEIVE FROM WS-TAG GIVING WS-MSG WS-LEN CONTINUE AFTER 1 SECONDS …`) is recognized and warned as COBOL1578 naming the 2023 Annex A.3 item 4 facility — the wrong facility and the wrong edition — while 2002/2014 give a parse error. constructs.json has no MCS-statement row (only receive-as-user-word / end-receive-as-user-word). Needs an introduction gate on the MCS statement arms (a constructs.json row + the version predicate). The witness this note owes for COBOL1578 is also what the owner question PB1198 needs.

**Finding (`receive-statement`, under-rejects; rows `FMT-14.9.31.2`).** facilityWord gates the 2023 MCS RECEIVE/SEND format on RESERVATION, not on INTRODUCTION: RECEIVE is reserved at 85 (communication module) and 2023, so the 2023-only asynchronous-messaging general format is recognized, named as the 2023 Annex A.3 item 4 facility, and compiled at --std 85

**Repro.** out/probe/receive-statement/legal.cob: `RECEIVE FROM WS-TAG GIVING WS-MSG WS-LEN CONTINUE AFTER 1 SECONDS ON EXCEPTION DISPLAY "EXC" NOT ON EXCEPTION DISPLAY "OK" END-RECEIVE` compiled with `cobol legal.cob --std 85`

**Expected from the spec.** The §14.9.31.2 format belongs to the asynchronous messaging facility, which the 2023 standard lists as a new general enhancement (Foreword) and in Annex E.3.2 item 1 ('A method of allowing communication between run units via messages is provided'); it is not COBOL-85 source, so an --std 85 compile should reject it with an introduction/edition diagnostic (as 2002/2014 already do by parse error), not accept it under a warning that cites the 2023 Annex A.3 item 4. Caveat for the owner: at 85 RECEIVE is the verb of the (also unsupported) communication module, so a §4.2.6-style 'not diagnosing syntax inside unsupported syntax' argument could be raised — but the diagnostic still names the wrong facility and edition.

**Observed / reasoning.** --std 85: `warning COBOL1578: The asynchronous messaging facility (SEND/RECEIVE, ISO §14.9.31/§14.9.38) is a processor-dependent element (§4.2.6; Annex A.3 item 4) ...`, compile succeeds. --std 2002/2014: `error COBOL0001: cannot parse construct near 'FROM'`. CobolParserCoreBase.facilityWord returns reservedHere(keyword) only; no introduction check exists for the MCS statement arms, and constructs.json has no MCS-statement row (only receive-as-user-word / end-receive-as-user-word).

**Code site.** src/Cobol.Net.Frontend/Parsing/CobolParserCoreBase.cs#facilityWord; src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4#statement (the {facilityWord("RECEIVE")}? / {facilityWord("SEND")}? arms)
