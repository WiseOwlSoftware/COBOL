# PB3379 — a branch has no owning orchestrator, so two lanes work it at once

Found by the operator (account 2), 2026-10-18 08:55 PDT. Grepped `kb/Work` for `one orchestrator per`,
`another orchestrator`, `owning orchestrator`, `two orchestrators`. Nothing matches. PB3157 is two runs of ONE
orchestrator on one branch.

**The rule.** One orchestrator per note and per branch. The loop's scope (steer file section 00 item 5) and the Mythos
lane's decision of 2026-10-18 03:18 both give PB3330's engine groups to the Mythos lane: "the loop stays off PB3330".

**What happened.**
1. The Mythos lane's wave 1118 runs under `wf_14a1e62b-326` (account 1). Its rolling wave reviews each DONE branch in
   its own slot and dispatches its own review finishers.
2. Group A2 (PB3332, branch `worktree-wf_14a1e62b-326-3`) returned DONE. `prune_worktrees.py` listed it WAITING FOR
   REVIEW, because its report had no review stamp yet.
3. The loop's enqueue unit reviews every WAITING FOR REVIEW branch. At 08:20 it reviewed this one at `0614ebe91`:
   - 7 findings, in `E:\COBOL-coord\scratch\review-worktree-wf_14a1e62b-326-3.jsonl`;
   - it stamped `w1118a2-PB3332-report.md` `Review: FINDINGS 7 enqueue-review-…-r1`.
4. The Mythos workflow's own review of the same branch wrote `E:\COBOL-coord\scratch\w1118\review-w1118-a2.jsonl` at
   08:56.

   would also have been routed to Sonnet by `plan_wave.choose_model` (PB2294), against the lane's Opus-only plan. The

**The bar for the fix.**

  groups; it also records the dispatching lane. `prune_worktrees.py` reports the owner beside the lifecycle state.

  lane explicitly: a report written for it, like the operator's and the Mythos lane's clerk reports.
