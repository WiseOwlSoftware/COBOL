# PB3707 — the gate run directory has no state between "made" and "holds the lock"

**Sites:** `scripts/run_gate_legs.py` (`launch_and_follow`, `Gate.run`, `live_gate`, `gate_running`, `lock_running`, and new: `write_spawn`, `read_spawn`, `write_pid`, `run_age_s`, `gate_starting`, `gate_phase`, `watch`), `scripts/orchestrator/enqueue.py` (`tested_locally`, which reads a no-verdict run through `gate_phase` over `live_gate`).

## What happens

`launch_and_follow` makes the run directory and spawns the child. The child takes the gate lock and writes `gate.pid` only inside
`Gate.run`, after interpreter start and imports. Two readers judge the interval between the two moments with different rules, and
both are wrong in one case:

1. **A landing in the window (UNTESTED instead of BUSY).** `live_gate` reads a free lock as "no gate runs". `enqueue.tested_locally`
   in the sub-second window sees the new run, no `verdict.json`, a free lock, and reports "no verdict file (a gate that died)":
   `land` ends exit 14 UNTESTED and the enqueue unit dispatches a finisher to gate a tip whose gate is about to run (its own gate then
   reads BUSY). Run-level repro: start `build-local.ps1` in a worktree and run `enqueue.py land` for it in the same second.
2. **A gate that dies before the lock (running forever).** `gate_running` returns True for a run with no `gate.pid`, since it cannot tell
   it from a gate not started. A child that dies before `Gate.run` (an import error, a killed process) leaves a run with neither
   `gate.pid` nor `verdict.json`, and `watch`/`--await` wait on it with no end (`AWAIT_PENDING_EXIT` only after the caller's limit).

## Fix direction

Give the run directory an explicit starting state: the launcher records the spawn (its child's pid and the time) in the run directory,
and the child's first act under the lock replaces it with `gate.pid`. A reader then decides by three facts: the lock is held (running),
the spawn record is younger than a bounded start-up time and the child process named by it is alive (starting), else the gate died.
Do not decide by a pid alone (PB3662 R1-1: Windows reuses pids). `live_gate`'s docstring ("held exactly while a gate runs") must state the
window until this lands. Self-test arms for both cases: a run directory with a live spawn record and a free lock reads starting; one with a
dead child reads died, within the bounded time.

## Landed (2026-10-25, fix-lane wave 20261703 group A, with PB3717 and PB3724)

Re-probed on planted run directories (no build needed: the defect is in the scripts). A young run with a free lock read
"a gate that died" in `tested_locally` (so `land` ended exit 14 and a finisher was dispatched), and a run with no `gate.pid`
read as running for ever in `gate_running`/`watch`. Fixed at the one place both readers share, a three-state reading of a run:
`gate_phase(run, live)` is RUNNING when the gate lock is held by a gate writing the run, STARTING when it is not held but the
run has no `gate.pid`, is younger than `START_WINDOW_S` (60 s, read from the UTC stamp in the run's name, so no gap lies
between the directory and any record of it) and the launcher's `gate.spawn` (the child's pid; `launch_and_follow` writes it
right after the spawn, `write_pid` replaces it under the lock) names a live process, else DIED. A pid is never trusted alone
(PB3662 R1-1); a reused one costs at most the window. `tested_locally` reads STARTING as a verdict still owed (exit 12 GATE
BUSY, never 14), `watch` PENDING, and a child that died before its lock reads DIED at once, not after the window. Review
lens found two races fixed in the same change: the child's `write_pid` must not die if it unlinks the spawn record while the
launcher has it open (Windows), and a launcher that cannot write the record says so and goes on. Self-tests: `run_gate_legs`
(the await arm: fresh, spawned-live, orphan, aged and bogus-name runs; the launcher arm: the record names the spawned child),
`enqueue` (a STARTING run is exit 12; the same run with a dead child is UNTESTED). Docs: DESIGN-test-build-ci.md section 3.14.12
and section 3.17.2 step 3, the `enqueue.py` module doc, `live_gate`'s docstring.
