## Finding — `object-property` (under-rejects; rows `SR-8.4.3.9.3-7`, `SR-8.4.3.9.3-6`, `GR-8.4.3.9.4-2`)

**Mechanism.** §8.4.3.9.3 SR7 is never checked: nothing compares the GET property method's RETURNING description with the SET property method's USING description, so mismatched explicit accessors compile and the property temp (modelled on the GET RETURNING item) is passed to a SET formal of a different description

**Expected from the spec.** A compile-time diagnostic: SR7 'The data description of the item specified in the RETURNING phrase of the get property method shall be the same as the data description of the item specified as the USING parameter of the set property method.'

**Observed / reasoning.** OoClassTable checks only the §11.7.3 SR6/SR7 header shapes (GET: no USING + one RETURNING; SET: one USING + no RETURNING); no site compares the two descriptions, and ReferenceResolver's `model = get?.Binding!.Returning ?? set!...` silently picks the GET's.

**Code site.** src/Cobol.Net.Compiler/Oo/OoClassTable.cs#Build (accessor shape checks ~:355-:365); src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs#OoTryBindPropertyReference (:140)

## Landed 2026-10-03 (wave-1005 implementer E)

Re-probed on a fresh Debug build: p11 reproduced (compiled clean, ran `SET:00005` / `00000`).

**Fix.** New `OoConformance.ValidatePropertyAccessorPairs` (called from `BinderDriver` right after `ValidateOverrideSignatures`, once every class's formals have bound) asks the ONE identical-description check, `OoConformance.DescriptionMismatch` in pair mode, of each (GET RETURNING item, SET USING formal) pair AS THE CLASS SEES IT: the roster lookup walks INHERITS (§9.3.6), so a GET in the base and a SET in the subclass (or the reverse) are a pair at the subclass. The instance and the FACTORY roster are separate interfaces and each is paired on its own. A mismatch is the new COBOLNET2727 (`property-accessor-description-mismatch`), positioned at the accessor the class wrote. `OoClassTable.Build` stays what the note named it to be, the header-shape check: the formals do not exist at pass 1, so the comparison could not live there.

**Spec (cite.py --check OK).** §8.4.3.9.3 SR7.

**Goldens.** `conformance:negative/pb1450-property-accessor-descriptions-differ` (GET PIC 9(5), SET PIC X(3), one class) and `conformance:negative/pb1450-property-accessors-split-across-inheritance` (GET inherited, SET in the subclass); the identical explicit pair is `conformance:2002/oo_property_explicit_ref`, unchanged and green.
