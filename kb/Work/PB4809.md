# PB4809 — the shortest round-trip conversion of a float result into a fixed-point receiver (held)

**Status: held by the owner, not scheduled.** Nothing changes until the owner reopens it. Reopen it when a real program, a
user report or a migration hits the surprise below.

**Today's rule (owner 2026-11-05, PB4731 and PB4751; NUMERIC_DESIGN D16; CONFORMANCE.md DOC-A.1-123).** If an
expression has a float item operand or a float receiver, the whole expression is evaluated in IEEE binary64. Its result
is stored by its exact binary value. A fixed-point receiver without ROUNDED truncates that value, so a binary64 value
just below a decimal boundary loses the last digit:

- `ZF FLOAT-LONG VALUE 0`, `R PIC 9V9(6)`: `COMPUTE R = ZF + FUNCTION EXP10 (-6)` stores 0.000000. Binary64 10**-6 is
  0.000000999999999999999954..., so truncation gives 0.000000. GnuCOBOL 3.2 stores 0.000001.
- `A1` and `A2` FLOAT-LONG 0.1 and 0.2, `R PIC S9V9(19)`: `COMPUTE R = A1 + A2` stores +0.3000000000000000444.

**The held option.** Convert a binary64 result to decimal by the SHORTEST decimal string that reads back to the same
binary64 value (.NET's round-trip `double.ToString("R")`), then store that decimal under the receiver's normal truncation
or ROUNDED rules. The two examples would store 0.000001 and +0.3000000000000000400.

- **For it:** it matches what a reader expects of a value written as 1E-6, and closes the GnuCOBOL difference in the
  first example. Native arithmetic "is an implementor-defined method of evaluating an arithmetic expression" (§2023:8.8.1.3,
  cite.py-checked), so either form conforms. (§2023:8.8.1.5.1, which PB4731 also cites for the float-to-decimal conversion,
  governs standard-decimal arithmetic only, and is not the authority under native arithmetic.)
- **Against it:** it hides the true binary value, so a fixed-point receiver no longer holds what the arithmetic actually
  produced. It adds a second conversion rule to keep apart from MOVE and DISPLAY of a float item. And the programmer
  already has two exact remedies: ROUNDED, or fixed-point items for values that must be exact.

**If reopened, the work is:** one conversion point (the binary64-to-decimal store into a non-float receiver, every
statement and the SUM/ABS/RANGE intrinsic lane alike). Also: a sweep of MOVE and DISPLAY of float items for the same
choice, a NUMERIC_DESIGN D16 amendment, DOC-A.1-123 rewritten, the user guide's
[floating-point page](../../docs/manual/user-guide/floating-point.md) updated, and goldens for both examples plus a
ROUNDED case.
