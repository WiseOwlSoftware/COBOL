# PB411 — one screen that rejects a shape SR6 admits, and one dispatch arm that never reaches the screen at all

**Rows:** `SR-14.9.18.3-6`, `SR-14.9.18.3-7`, `SR-14.9.18.3-8`. The three rules share ONE enforcement site, so
they share one note. All measurements re-run on this worktree's HEAD `cobol.exe` (base 89044aa0).

## MECHANISM 1 — the screen rejects an alphanumeric group, which SR6 admits (rejects legal source)

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs#AdmittedStatusItem` (`:182-195`) is the
completeness structure for SR6's two alternatives. Its first line is

```csharp
if (p.Item.OperandPic is not { } pic) return false;
```

An alphanumeric group item has no elementary picture, so `OperandPic` is null and the operand is rejected
before either alternative is asked. The comment at `:192-194` states the intent correctly — "a data item WITH
USAGE DISPLAY OR NATIONAL, whatever its category" — but a group never reaches it.

That is the alternative the group satisfies. §8.5.2.1: "An alphanumeric group item is treated as though it had a
usage of display." An alphanumeric group therefore IS a data item with usage display, and SR6's second
alternative admits it. The inconsistency is visible inside the screen itself: a GROUP-USAGE NATIONAL group *is*
admitted (`:189`/`:194` via its usage), on exactly the reasoning that admits the alphanumeric one.

⚠ This is the "a real clause can answer a DIFFERENT question" shape. §8.5.2.1 does give an alphanumeric group
the class alphanumeric with no elementary description — a true statement about CLASS — and SR6's second
alternative is about USAGE, not class.

## MECHANISM 2 — the method arm never reaches the screen (under-rejects SR6, SR7, SR8 and the edition gate)

`Binding/Procedure/Verbs/CallBinder.cs#BindGoback:494` forks to `OoBinder.cs#OoBindMethodGoback` when
`host.InMethod`. That method (`:1045-1051`) reads `g.dataReference()` and `g.raisingPhrase()` and **never reads
`g.statusPhrase()`** — the phrase is silently discarded. `ControlFlowBinder.cs#BindTerminationStatus` (`:78`),
the single place SR6/SR7/SR8 are enforced (via `ScreenStatusOperand` `:130` and `IsIntegerLiteralText` `:200`),
is unreachable in a method context. The same drop swallows the COBOL-2023 introduction gate.

`OoBindMethodGoback`'s own doc comment (`:1043-1044`) asserts that "the RETURNING/GIVING and 2023 status
phrases" stage loud in a method. That is true of RETURNING/GIVING (`:1047-1049` returns a `BoundUnsupported`)
and false of the status phrase — `docs_current_state_only`.

## THE SHAPE OF THE REPAIR

⛔ Do not add a `p.Item.OperandPic is null → is it an alphanumeric group?` special case at `:184`, and do not
copy `BindTerminationStatus` into `OoBindMethodGoback` (CLAUDE.md rule 5).

- **Mechanism 1** is a classifier gap, not a status-phrase gap: `AdmittedStatusItem` needs a USAGE answer for a
  group item, which the one §8.5.2.1 classifier should give it (`IntrinsicArgumentRules.ClassOfPlace` is
  already consulted at `:186` for pointer/object). Give the classifier the group-usage answer once and every
  position that asks "is this a data item with usage display" gets it — this is the same defect shape
  [[PB169]] and [[PB217]] exist to close, one group kind over.
- **Mechanism 2** is a dispatch gap: the method fork at `CallBinder.cs:494` hands the whole
  `GobackStatementContext` to a second binder that re-decides which phrases exist.
  `change_the_dispatch_not_the_callers` — the phrase decoding (RETURNING, RAISING, STATUS) belongs on ONE path
  that both arms share, with the arms differing only in what they do with the decoded parts. Then a phrase
  added to the grammar cannot be silently dropped by one arm again. Pair it with a drift test that every
  sub-context of `gobackStatement` is read on both arms.

## THE SIBLING SWEEP

1. **STOP RUN** carries mechanism 1 verbatim (§14.9.42.3 rule 2 is SR6's twin, and the diagnostic text already
   cites both). Fix once, prove both.
2. **A GREEN TEST HOLDS MECHANISM 1 OPEN and must be re-baselined, not preserved.**
   `tests/Cobol.Net.Tests.Conformance/StopGobackExitCodeTests.cs:234`
   (`TheStatusPositionsOwnRules_AreEnforcedAndCited`) carries an `InlineData` row asserting that a group status
   operand draws COBOLNET1704, and `:187`
   (`RefModAndNationalGroupStatusOperands_AreAdmittedBySR2`)'s doc comment states that the alphanumeric group
   stays rejected. `tests/conformance/negative/pb169-status-group-identifier.{cob,err}` is the corresponding
   negative fixture. All three pin the wrong answer (`feedback_green_test_can_hold_a_gap_open`) and all three
   must flip with the fix.
3. **The other method-arm phrases**: `OoBindMethodGoback:1047` also rejects `GOBACK RETURNING` inside a method
   as unsupported. That is a separate question ([[PB407]] covers whether the phrase belongs in the grammar at
   all) but it lives at the same site and should be re-examined in the same change.
4. **Every other `InMethod` fork.** The mechanism is "a second binder re-reads the parse context and misses a
   sub-context"; grep `host.InMethod` and check each fork against the phrases its grammar rule can carry.
5. Edition sweep: after the fix the method arm must draw COBOLNET0900 at 2002/2014, exactly as the program arm
   does — that is the cheapest single assertion proving both arms now share the path.

## Landed — 2026-09-13

Both mechanisms fixed at the ONE place each belongs, re-probed on this worktree's own `cobol.exe`.

**Mechanism 1 — the classifier, not the screen.** `ItemCategory.UsageOf(DataItem)` is new and is THE ONE
§8.5.2.1 usage reader: `OperandPic?.Usage ?? (IsAlphanumericGroup(item) ? Usage.Display : null)`. It sits beside
`ItemCategory.IsAlphanumericGroup`, which was already the ONE spelling of §13.18.29.4 GR3 / §3.11's
definition-by-exclusion, so the four group kinds are settled with no hand-list and the STRONGLY-TYPED and
VARIABLE-LENGTH groups — which §3.11 excludes from "alphanumeric group item" by name, and for which the standard
states no usage at all — answer `null` rather than being invented an answer. `AdmittedStatusItem` asks it, and so
the SAME change fixes both verbs at once (the screen is shared).

Swept siblings, both of which wrote the same rule down their own way:
- `SendingValueTemp.UsageOf` was `inner.Pic?.Usage ?? Usage.Display`, which gave a reference-modified
  GROUP-USAGE NATIONAL group's §8.4.3.3.4 GR6 intermediate the usage DISPLAY beside the category NATIONAL
  `RefModPlace.Category` already answered — one item, two usages. Now the reader, with DISPLAY kept only as the
  fallback for the shapes §8.5.2.1 states nothing for. PROBED (`scratchpad/PB411/probe/refmodgrp.cob`): the
  intermediate's VALUE is unchanged by the correction, so this half is an inconsistency removed, not a wrong
  answer fixed — said plainly rather than counted as a second repro.
- `RecordLayout.UsageOfItem` was `OperandPic?.Usage ?? OwnUsage ?? Display`, giving `01 G USAGE COMP.` the answer
  BINARY for §14.9.41.3 SR6 b) 2.'s comparison, which §13.18.60.4 GR1 settles outright — "Unless the
  GROUP-USAGE clause is also specified or implied, the USAGE clause applies only to each elementary item in the
  group and not to the group itself". Now the reader, with the `OwnUsage` tail surviving only for the excluded
  group kinds.
- `IntrinsicArgumentRules.StaticUsageOf` is deliberately NOT changed and now says so in its own comment: it asks
  whether the argument has a statically fixed REPRESENTATION for the §15.19.3 keyword screens, not what usage the
  item has, and a group's storage is its leaves'. Stated so neither reader is mistaken for a duplicate.

**Mechanism 2 — the dispatch, not a second copy.** `CallBinder.DecodeGobackPhrases` reads `gobackStatement`
ONCE, before the §14.9.18.4 GR2/GR4 fork, into a `GobackPhrases` record (RETURNING and RAISING as parse contexts
— what the arms DO with them genuinely differs; STATUS already bound and screened, because §14.9.18.3's syntax
rules carry no context qualifier). `OoBinder.OoBindMethodGoback` now takes that record and NEVER sees the parse
node, so an arm cannot read past a phrase it does not know about. The status phrase is screened and then INERT in
a method, which is the standard's own division: GR7, GR8, GR9 and GR10 each open "If the GOBACK … is executing in
a main program", and a method is never one — so there is nothing to carry onto `BoundMethodReturn`.

The COBOL-2023 introduction gate lost its `!InMethodDefinition` exclusion in
`VersionConformancePass.VisitGobackStatement`. The asymmetry with the two gates above it is the rule's own: those
exclude a method because GR4 makes a method's GOBACK a different statement MEANING, while this one asks whether
the SYNTAX existed in the targeted edition — and §14.9.18.2 is the one general format both arms are written in.

**The green tests that held it open are flipped, not preserved.** The `TheStatusPositionsOwnRules` row asserting
COBOLNET1704 for an alphanumeric group moved to `RefModAndGroupStatusOperands_AreAdmittedBySR2` (renamed from
`RefModAndNationalGroup…`) with an expected exit code, on BOTH verbs plus a slice of the group;
`tests/conformance/negative/pb169-status-group-identifier` is DELETED and replaced by
`pb411-status-strongly-typed-group`, which pins a shape SR2 genuinely excludes. New:
`GobackStatusArmParityTests` (the same statement compiled in a program and in a method, verdicts compared — the
form that makes a one-arm fix fail), `GobackPhraseDecodeDriftTests` (every sub-rule of `gobackStatement` is read
by the ONE decode; the method arm never names the parse node; every decoded phrase is consumed),
`tests/conformance/2023/pb411_goback_status_operand_and_method_arm` and
`tests/conformance/negative/pb411-goback-status-in-method-below-2023`.

**Rows.** `SR-14.9.18.3-6/-7/-8` → CONFORMS. The STOP twins `SR-14.9.42.3-2/-3/-4` — which were at GAP with no
verdict, claimed by no note, and are the SAME screen — are closed CONFORMS in the same batch: the note's own
sibling sweep says "fix once, prove both", and leaving the twin of a rule unadjudicated after fixing it is how
the two verbs would come to disagree again.

**Not touched, deliberately:** the §14.9.18.3 SR1 GLOBAL-declarative rule and the SR5 RAISING LAST placement rule
([[PB409]]/[[PB410]]), and the RAISING staging [[PB408]] rewrote — a different operand at the same statement.
EXIT PROGRAM / METHOD / FUNCTION carry NO status phrase in §14.9.14.2's four general formats, so the
termination-status sites are exactly STOP RUN and GOBACK and there was no third arm to sweep.
