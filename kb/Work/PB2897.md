# PB2897 — a self-test's hang guard is read as a red under load

The implementer gate `20261010T174351Z-7d925b` (worktree `E:\COBOL\.claude\worktrees\w1051z-pb2515`, a change to
gate scripts and docs only) ended `=== BUILD-LOCAL GATE: RED — SELF-TESTS RED — fail-fast … NO LEG RAN`:

    self-test scripts/orchestrator/landing_check.py --self-test: RED (exit 124) in 901.7s   ⛔ TIMED OUT after 900 s
    self-test scripts/orchestrator/test_orchestrate_stop.ps1: RED (exit 124) in 923.7s      ⛔ TIMED OUT after 900 s

The same audit run had `test_orchestrate_steer.ps1` GREEN at 851.8 s and `test_orchestrate_handoff.ps1` at 807.2 s,
and `gate_slot.py --self-test` at 248.6 s (PB2880 measured 65-108 s). The host showed 87 `pwsh` and 58 `python`

on SIX timeouts (landing_check.py 905.7 s; test_orchestrate_handoff 928.3 s, core 960.6 s, stop 975.0 s, steer

… NO LEG RAN`. Each red re-gate starts another full audit run, so the load feeds itself. A lander's audits run the same
runner (beside its legs, kb/Work PB2880), so a lander gate under the same load would be RED too.

Sibling, same root (a wall-clock budget deciding a verdict under load): `GateSlotDriftTests` runs `gate_slot.py
--self-test` through `PythonInstrument.Run` with the harness's 120 s budget (`COBOLNET_RUN_TIMEOUT_MS`); measured
back to back on this loaded host the self-test took 85 s at main's `471d0e954` and 96 s with this branch's two new
arms, and one run under heavier load hit `TimedOut … 120000 ms` twice (HarnessNonObservation, not a red verdict).

## Why it is a defect

A gate red that is not a red costs a whole re-gate (and here a gate's audits are about 15 minutes of wall time), and
it teaches agents to re-run reds. The guard is a HANG guard (`scripts/self_tests.py#TIMEOUT_S = 900`, line 76: "A
self-test that runs longer than this is RED"), but the slowest self-tests already take 10-14 minutes under the load a
wave produces, so it fires on slowness. The owner's no-wall-clock rule (feedback no_wall_clock_tests) is the
standard: a time bound may catch a hang, never decide a verdict on speed.

## Leads (the code sites)

- `scripts/self_tests.py:76` `TIMEOUT_S` and its use at line ~270 (`subprocess.run(..., timeout=TIMEOUT_S)`).
- The long poles: the `scripts/orchestrator/test_orchestrate_*.ps1` family (300-850 s under load) and
  `landing_check.py --self-test`. PB2880 measured the same family at 65-108 s for gate_slot.py on a quieter host.
- Options to weigh: a hang guard that measures PROGRESS (output silence) rather than total time; the audits sharing a
  bounded pool across worktrees (they left the slot in PB2524); or the slow self-tests made fast at the root.

Found by: wave 1051 group Z (PB2515), not fixed there: a different mechanism (the self-test runner and the audits'
concurrency), outside that group's gate-default change.
