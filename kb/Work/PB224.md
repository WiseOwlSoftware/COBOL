# PB224

Found by the cluster-B review fleet on the pre-commit [[PB169]]–[[PB172]] tree, 2026-08-31. The wave's own
thesis is that a rule must be declared once and guarded from outside; these are the guards, and all three had a
hole of the shape `feedback_green_gates_arent_evidence` names — a check that passes without having looked at
what it claims to cover.

## 1. `OperandWalkCoverageTests.Covered` memoized the VISIT, not the VERDICT

`if (!seen.Add(rule)) return true;` — "a cycle cannot be the reason a leaf is uncovered" — extends silently to a
rule that was visited, found UNCOVERED, and then ABSORBED. `alt.Any(r => … Covered(r, …))` stops at the first
member that answers true, leaving the rejected one in `seen`, and the next query for that rule answers `true`.
A hole then reports as covered.

⚠ **LATENT, and latent is not fixed.** Measured on today's grammar: no `Covered` call returns false at all, so
nothing is ever absorbed and `seen` never holds a rejected rule. It becomes live the moment an operand rule
grows an alternative that places an uncovered rule reference BEFORE a covered one. Fixed by memoizing the
RESULT: a rule still in progress is seeded optimistically (so a genuine cycle keeps the old behaviour) and the
real verdict overwrites the seed on the way out.

## 2. `NoScreenKeysOnAHandWrittenContextList` could not match its own witness

The regex was `context\s+is\s+OperandContext\.[A-Za-z]+(\s+or\s+OperandContext\.[A-Za-z]+)+` over ONE file. Three
independent holes, and the first is decisive:

  * **ARITY.** The `+` requires at least one `or`. The defect the docstring literally names — the `BindPrimary`
    intrinsic screen [[PB172]] fixed — was `if (context is OperandContext.Arithmetic && call is …)`: a SINGLE
    member, no `or`. **The guard could not have fired on the defect it was written for.**
  * **SCOPE.** It read `ExpressionBinder.cs` alone, so the same shape in `ReferenceResolver` or any other binder
    was invisible.
  * **IDENTIFIER NAME.** It required the parameter to be spelled `context`.

Fixed to any identifier, one member or many (`or`-chains and `is not` included), across every `.cs` under
`Binding/`. **PROVED TO FAIL BEFORE BEING TRUSTED**, and the first attempt at the proof is worth recording: a
tripwire written as `if (position is CobolNet.Binding.Procedure.OperandContext.Arithmetic)` did NOT trip,
because the fully-qualified spelling defeats the pattern. Re-written as the plain `OperandContext.Arithmetic`
form in `ReferenceResolver.cs`, the fact went red naming the file and the match — so the arity fix and the scope
fix are both demonstrated, and the residual (a fully-qualified reference still evades it) is known rather than
assumed.

## 3. `TheThreeAxes_AreWhatTheClausesSay` was four hand-written `InlineData` rows

Its sibling `EveryOperandContextMember_DeclaresItsTwoAxes` is genuinely total (it enumerates `Enum.GetValues`),
but the VALUES fact was not: a fifth `OperandContext` member could take any axis values it liked — including the
r7 and SR10 columns transposed, the hazard the design doc warns about and [[PB215]] measures — and this fact
stayed green. Fixed by driving the Theory from `Enum.GetValues` and looking each member up in a named expected
map, so a member without a row FAILS with a message that names the three clauses to read. The expectations stay
hand-written on purpose: they are the CLAUSES, and deriving them from the table under test would measure
nothing. Proved by removing the `CallByValue` row: the fact went red with the intended message.

## Also landed here: the last two copies of the sole-primary descent

[[PB172]] collapsed four copies of the "is this expression a single unparenthesized primary?" walk into
`ConditionBinder.SolePrimary`. Two survived, and they survived because they were OUT OF REACH: the fifth was
`IntrinsicBinder.SoleDataReference(FunctionArgumentContext)`, an independently-written tier-by-tier list-pattern
version that agreed with the others by coincidence; the sixth was `CompileTimeExpressionEvaluator.SoleDataRef`,
in `Cobol.Net.Frontend`, which cannot reference the compiler. The descent reads PARSE TREES and nothing else, so
the shared body moved DOWN to `CobolNet.Frontend.Expressions.SoleOperand` and both layers now read it. The
boundary decides §8.8.4.7.3 SR2, §8.8.1.1's sole-vs-compound split and the §7.3.11 directive operand at once —
six near-duplicates around that is a drift hazard whichever way they currently agree.

And `EvaluateBinder.BindValueOperand` is now arm-for-arm identical to
`ConditionBinder.ComparisonOperandOf`: §14.9.13.4 GR2 makes an EVALUATE comparison behave "as if" the
corresponding relation condition were written, so the two operand binders answer ONE question, and they differed
in the ORDER of their sole-* short-circuits (harmless, since the alternatives are disjoint — they agreed by
luck) AND in the tail, where EVALUATE built a raw `BoundComputedOperand` while the relation side routes through
`IntrinsicBinder.OperandOf`. That tail difference is not cosmetic: `OperandOf` surfaces a user-function result
temp as a FIELD operand so the temp's cloned category (§8.4.3.2.4 GR1) drives the class dispatch, and a raw
computed wrapper would compare an alphanumeric result NUMERICALLY. For every other shape `OperandOf` returns the
identical node, so the emit floor is unchanged.
