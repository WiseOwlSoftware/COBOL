# PB2485 — LANDED

Filed 2026-10-07 by the train-1035 lander from the wave-1033 group A implementer report (`w1033a-PB833-report.md`,
new lead 3).

**Shape.** `tests/Cobol.Net.Tests.Unit/RunUnitFileLockDriftTests.cs` proves the PB833 lock over 768 pairs by opening
one file through two `FileRegistry` instances in ONE process. That reaches the same kernel path as two processes on
Linux (an open-file-description lock conflicts across descriptions regardless of process) and on Windows (share modes
are per handle), so the theorem is sound as far as it goes. What it cannot see: a lock released when its holder
PROCESS exits without a CLOSE (§9.1.15, "The file lock is removed by an explicit or implicit CLOSE statement" — the
implicit CLOSE at run-unit end), a `CALL "SYSTEM"` child inheriting the description (`O_CLOEXEC` is the guard in
`src/Cobol.Net.Runtime/IO/Sharing/OfdRegionLocks.cs#Open`), and the compiled program path (`FileConnector.Open` from
generated code) rather than the registry API.

**Witness wanted.** A characterization test that compiles two small COBOL programs, starts the first holding a file
`SHARING WITH READ ONLY` (waiting on a signal file), runs the second's `OPEN EXTEND` and asserts its '61', then ends
the first without a CLOSE and asserts the second's retry is '00'. Run on Windows and in the Linux gate.

Owner 2026-10-17: addressed in the SORT and file I/O campaign (kb/Work PB3353).

**Landed.** `tests/Cobol.Net.Tests.Unit/RunUnitProcessBoundaryTests.cs` (18 cases, two real processes) with the new
instrument `tests/_shared/LiveProcess.cs`. The re-probe found no defect: the lock is refused with 61 / 62 across a process
boundary through every handler, and it comes back with the holder's CLOSE, its run unit's implicit CLOSE, an abnormal end
and a kill, and a child started while it is held does not keep it. `CALL "SYSTEM"` is not a compiler built-in, so the
child case starts the child from the holding process instead. See the DEVLOG entry of the landing.
