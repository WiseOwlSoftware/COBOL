# PB3855 — a stored groups-file body must re-render, or be refused by name, never by the once-check

**Sites:** `scripts/orchestrator/groups.py` (`requirements_text`, `as_group_json`), `.claude/skills/workstream/check_practices.py` (the PB3777 once-check)

## The defect

PB3777's fix (f65890a33, branch worktree-wf_5c017902-6f0-7) makes `requirements_text` state one lead-in per campaign and
number each requirement after it. A groups file planned BEFORE that fix stores the old rendering in its `body`: the
same 64-character clause before every requirement. Re-rendering that stored body by hand (a retry on the same file, as
for the waves w20261711-w20261715 under E:\COBOL-coord\scratch\op\w-pb3852*) exits 1: `PB3777: states twice: the
branch reviewer raises a finding when your branch lacks it)`. A fresh plan renders the new form; only a hand re-render
of a stored body is affected.

## Acceptance

- A groups file carries what is needed to re-render its requirements with the CURRENT renderer (the campaign and the
  requirement texts, not a pre-rendered sentence), so a re-render of any stored file yields a spec that passes
  `check_practices.py`; or the stored form is versioned and an old one is refused with a message naming the re-plan.
- A self-test seen RED first: a groups file in the pre-PB3777 shape re-renders GREEN (or is refused with the named
  re-plan message), never with the once-check's bare refusal.
- Sweep: the other renderer-built fragments stored in a `body` (replay clause, predecessor, SITES FOLLOW THE DIFF,
  DEPENDENCY SUCCESSOR) have the same property.
- Standing owner rules: fix the root causes, never simply making the diagnostic pass; always be consistent with
  ourselves barring an explicit requirement differently.
