# PB5077 - at --std 85 a FROM or INTO operand naming the file's own record area is accepted: READ INTO, WRITE FROM, REWRITE FROM, RELEASE FROM and RETURN INTO never compare the two storage areas

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Model/RecordAreaRule.cs` (`RecordAreaRule`), `src/WiseOwl.Cobol.Compiler/Binding/Model/StorageSharing.cs` (`StorageSharing`), `src/WiseOwl.Cobol.Compiler/Binding/Validation/StatementValidation.cs` (`StatementValidation`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/MoveBinder.cs` (`MoveBinder`, `FromPhraseRules`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundTree.cs` (`IntoPhraseRules`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/SequentialIoBinder.cs` (`BindWrite`, `BindRewrite`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/KeyedIoBinder.cs` (`BindWrite`, `BindRewrite`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/SortBinder.cs` (`BindRelease`), `src/WiseOwl.Cobol.Editions/Diagnostics/DiagnosticCatalog.cs` (`DiagnosticCatalog`).

**Mechanism.** 1985 forbids the receiving or sending area of the FROM/INTO phrase to be the file's record area ("must not reference the same storage area"; READ, RETURN: identifier-1 and the record area; WRITE, REWRITE, RELEASE: record-name-1 and identifier-1). Each binder binds the phrase as an implicit MOVE through the MOVE binder and asks nothing about the two operands' storage, though StorageSharing.MayShare exists. One missing screen across five statements and three file organizations.

**Found by.** The 1985 `--std=85` draft triage (kb/Work PB4995 item 3): each rule below is a conformance-suite draft that did not MATCH at `--std 85`, and its adjudicator decided COMPILER-DEFECT. Harm and observed text are the records'; nothing here was re-derived.

**Inventory.** The traceability inventory carries no 1985 rows yet, so `inventory_rows` is empty; the rows this note covers are the 1985 rule ids listed below (catalog `docs/rearchitecture/spec-rule-catalog-1985.json`).

**Rules (11; every citation checked with `scripts/spec/cite.py --check`).**

- `1985-SR-VII.4.4.3-1` - `§1985:VII.4.4.3 SR1` (record harm: under-rejects, slice-06): §1985:VII.4.4.3 SR1: "The storage area associated with identifier-1 and the record area associated with file-name-1 must not be the same storage area." The draft reads the rule correctly: `READ IN-FILE INTO IN-REC` (line 17) names as identifier-1 the 01 record of IN-FILE itself, which is that file's record area, so the program violates the syntax rule (§1985:I.1.6: "A conforming source program is one which does not violate the explicitly stated provisions and specifications of Standard COBOL."). The control (`INTO WS-REC`, a Working-Storage item) conforms and compiles. The 2023 standard dropped this syntax rule for a note on overlapping operands (§2023:14.9.30.4), which is the reading the compiler applies at 85.
- `1985-SR-VIII.4.5.3-1` - `§1985:VIII.4.5.3 SR1` (record harm: under-rejects, slice-07): §1985:VIII.4.5.3 SR1: "The storage area associated with identifier-1 and the record area associated with file-name-1 must not be the same storage area." In READ REL-FILE INTO REL-REC (line 18) identifier-1 is REL-REC, the only record of REL-FILE, so its storage area is the file's record area: the rule forbids the statement.
- `1985-SR-IX.4.5.3-1` - `§1985:IX.4.5.3 SR1` (record harm: under-rejects, slice-02): §1985:IX.4.5.3 SR1: "The storage area associated with identifier-1 and the record area associated with file-name-1 must not be the same storage area." In `READ IFILE RECORD INTO IREC` (line 22) identifier-1 is IREC, the record description of IFILE, whose storage area IS the record area associated with file-name-1. The statement violates the syntax rule and the draft is right to expect a refusal at line 22. Its control reads INTO a Working-Storage item.
- `1985-SR-VII.4.5.3-1` - `§1985:VII.4.5.3 SR1` (record harm: under-rejects, slice-07): §1985:VII.4.5.3 SR1 (as amended by X3.23a-1989 and X3.23b-1993): "Record-name-1 and identifier-1 must not reference the same storage area." In REWRITE F1-REC FROM F1-REC (line 17) record-name-1 and identifier-1 are the one data item, so they reference the same storage area and the rule forbids the statement.
- `1985-SR-VIII.4.6.3-1` - `§1985:VIII.4.6.3 SR1` (record harm: under-rejects, slice-07): §1985:VIII.4.6.3 SR1 (as amended by X3.23a-1989 and X3.23b-1993): "Record-name-1 and identifier-1 must not reference the same storage area." In REWRITE REL-REC FROM REL-REC (line 19) record-name-1 and identifier-1 are the one data item, so the rule forbids the statement.
- `1985-SR-IX.4.6.3-1` - `§1985:IX.4.6.3 SR1` (record harm: under-rejects, slice-03): §1985:IX.4.6.3 SR1 (as amended by X3.23a-1989 and X3.23b-1993), second sentence: "Record-name-1 and identifier-1 must not reference the same storage area." In `REWRITE IREC FROM IREC` record-name-1 and identifier-1 are one data item, the plainest case of the same storage area, so the statement violates an explicit syntax rule (§1985:I.1.6: "A conforming source program is one which does not violate the explicitly stated provisions and specifications of Standard COBOL."). The draft reads the rule correctly (it quotes the printed wording, "must not refer to"; the amended sentence says the same).
- `1985-SR-VII.4.7.3-1` - `§1985:VII.4.7.3 SR1` (record harm: under-rejects, slice-07): §1985:VII.4.7.3 SR1 (as amended by X3.23a-1989 and X3.23b-1993): "Record-name-1 and identifier-1 must not reference the same storage area." WRITE OUT-REC FROM OUT-REC names one data item as both operands, the plainest violation. The draft's own form, WRITE OUT-REC FROM OUT-FLD with OUT-FLD the only item subordinate to OUT-REC and of its whole size (10 characters at offset 0), names the identical storage area under another name and is forbidden for the same words.
- `1985-SR-VIII.4.9.3-1` - `§1985:VIII.4.9.3 SR1` (record harm: under-rejects, slice-08): §1985:VIII.4.9.3 SR1 (as amended by X3.23a-1989 and X3.23b-1993): "Record-name-1 and identifier-1 must not reference the same storage area." The draft is right about the rule, but its program and its control both also omit the INVALID KEY phrase that §1985:VIII.4.9.3 SR3 requires when no USE procedure applies ("The INVALID KEY phrase must be specified if an applicable USE AFTER STANDARD EXCEPTION procedure is not specified for the associated file-name."), so the control was not a conforming program. The repro below adds INVALID KEY to isolate SR1 (violating line 19; the control is the same program with FROM WS-REC); the compiler accepts it, so the case stands as a defect.

**Expected (from the 1985 text).** --std 85 refuses a FROM or INTO operand that shares storage with the file's record area, at the phrase. The deciding words: "Record-name-1 and identifier-1 must not reference the same storage area." (§1985:IX.4.6.3 SR1).

**Landed.** Re-probe on the build: all eleven repro programs compiled at `--std 85` with exit 0 and no diagnostic. The note said the rule is 1985's; the 2002 text prints it for all five statements (§2002:14.8.29.2 SR2, 14.8.30.2 SR2, 14.8.32.2 SR1, 14.8.33.2 SR1, 14.8.47.2 SR4; cite.py OK), so the screen runs below COBOL-2023 (COBOL6827, `RecordAreaRule.InForce`) and the 2014 reading is a determination in docs/CONFORMANCE.md section 3.5.
