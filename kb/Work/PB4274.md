# PB4274 — one spelling for a test's name: the trx logger's

**Sites:** `scripts/test_population.py` (`trx_spelling`, `spelled_as_trx`, `check`, `Population.defective`),
`scripts/gate_plan.py` (`name_key`), `tests/_shared/GateLegs.cs` (`GateNameKey.TrxSpelling`, `GateNameKey.Of`),
`scripts/run_gate_legs.py` (`_verdict`).

## The stop

`enqueue.py land worktree-wf_2201113e-54d-26` stopped `GATE RED (Windows) on ecc64a97de64`. The run
`TestResults/build-local/000002-20261031T234522Z` ran every case and every case passed, on both hosts (Conformance
20,406/20,406, Unit 39,088/39,088, Characterization 36/36), yet printed
`=== POPULATION Unit: RED — 4 NEVER RAN · 4 NOT IN THE POPULATION`. The four were the theory cases whose argument holds a
supplementary-plane character: `NormalizerTests.SpanForm_EqualsTheStringForm` with U+1D15E and with U+1D165 U+1D16D
(PB107, bfe8edf8d, cc23d04ca), and `WordCharacterEveryEditionTests` with U+1E900 (PB4234, dad1b6d23), all on main.

## What each tool spells (measured from the tools, not inferred)

- **xunit's argument formatter** (xunit.execution 2.9.2, `ArgumentFormatter.EscapeString`) writes a string argument
  with C escapes: `\\`, `\"`, the named controls, any other C0 control as `\x{0:x2}`, and a LONE surrogate as
  `\x{0:x4}` (`x\xd800y`). A valid surrogate pair, a supplementary character, stays literal.
- **`dotnet test --list-tests`** prints that display name as UTF-8: the 4-byte sequence of U+1E900 (`360 236 244 200`
  in listing-Unit.txt).
- **The trx logger** (the SDK's `Microsoft.VisualStudio.TestPlatform.Extensions.Trx.TestLogger.dll`,
  `RemoveInvalidXmlChar` / `ReplaceInvalidCharacterWithUniCodeEscapeSequence`) replaces every UTF-16 code unit matching
  `[^\x09\x0A\x0D\x20-\uD7FF\uE000-\uFFFD]` with `\u{0:x4}`, in `UnitTest name` and `UnitTestResult testName` alike. A
  supplementary character is two surrogate code units, so it becomes the twelve characters `\ud834\udd5e`. A lone
  surrogate never reaches it (xunit already wrote `\xd800`), which is why `x\xdc00` matched.

## Root cause

`test_population.check` compared the two multisets by raw string, and the two tools spell the same case differently
exactly when the name holds a code unit outside XML's character range. The same split cut through every other place a
trx name meets a listed or in-process name: `gate_plan.name_key` keyed the previous gate's reds (tier 0a) and the shared
timings store from the trx, and the plan's cases from the listing, so a red supplementary-plane case was never put first
in the next gate, and its duration was dropped from the store as no longer discovered.

It hid until PB4269 (5d6433285) because a leg-1-only gate's population is STOPPED early, and the verdict ignored a
stopped population whole: `NOT IN THE POPULATION` printed in 15 leg-1-only runs across the worktrees and every one stayed
GREEN. PB4269 made an unattributable change (here a grammar file, `CobolLexer.g4`) run tier 1 whole in ONE leg, which
demands an exact population, so any such branch would have gone red the same way.

## The fix

- ONE SPELLING: `test_population.trx_spelling` states the trx logger's rewrite once (a supplementary character as its
  two escaped surrogates). It is the identity on a trx name. `check` compares both sides in it. The rewrite cannot be
  inverted (the logger escapes no backslash), so two listed names it spells alike are an ERROR that names both, never a
  merged count. The literal text that xunit writes as `\\ud834` stays distinct from the character.
- `gate_plan.name_key` starts from `trx_spelling`, and `GateNameKey.Of` (the test hosts' key) applies the same rewrite
  (`GateNameKey.TrxSpelling`), so plan keys, identity records, reds and timings are one key in both languages
  (`GateLegDriftTests` arm 1 runs both over the new supplementary, lone-surrogate, U+FFFF and literal-escape cases).
- `Population.defective`: a stopped run still answers RAN TWICE and NOT IN THE POPULATION. Only NEVER RAN waits for
  the run to finish. The gate's verdict and the plan leg's read it.
- Self-tests: `test_population.py --self-test` (a supplementary pair, a lone surrogate, U+FFFF, the literal escape
  text, the literal text not standing in for the character, the two-names-one-spelling error, a stopped run's foreign
  name), `gate_plan.py --self-test` (the key; a supplementary case's trx duration published and read for its listed
  name), `run_gate_legs.py --self-test` (a leg-1-only gate with a foreign definition is RED). Re-checked against the
  real run: `test_population.py check --listing listing-Unit.txt --trx leg-1-Unit.trx` reads EXACT 39,088/39,088.

## Why CI never saw it (the CI invariant, PB1957 rows 47 and 50)

CI ran the population check over Conformance's shards only (`conformance-population`). Unit and Characterization ran
as whole projects with no population check, under a workflow comment that said none was needed. So the one
population check never read a Unit trx in CI, and main's CI stayed green (run 41254749772 on 3003138e) with these cases
present. This is PB1957's reverse direction (row 50: a local-only check CI lacks). A check defect could show on any
branch's whole-tier gate and never on main. The branch that first carried this fix (`worktree-wf_2201113e-54d-26`)
also added a population assertion for Unit and Characterization to two CI jobs. **That part did not land.** On
2026-10-31 the owner ruled out added build and CI time and relaxed the CI-must-pass-if-local-passed rule. The owner
also adopted the pipeline redesign (kb/Work PB4323), whose step 5 (PB4328) deletes `test_population.py` and replaces
the plan with the whole population, and whose step 7 (PB4330, in flight) is rewriting that workflow file. The spelling
rule (`trx_spelling`, `GateNameKey.TrxSpelling`) is the part the new gate must keep, because a whole-population run
meets these names on every code gate.

**How it landed (operator session 8904f374, branch `tooling-pb4274-trx-spelling`).** It was split out of
`worktree-wf_2201113e-54d-26`, whose PB4240 half the branch review refused (it implemented the folding direction the
owner reversed on 2026-10-31). It went on its own because two front-end campaign branches (PB4230, PB4302) gated RED
only on this. It answers that review's two low findings on PB4274: the escapes are written as ASCII text in
DESIGN-test-build-ci.md, this note and `GateLegs.cs` (R1-2), and both spellings take a compiled-regex fast path before
the per-character rewrite (R1-3). It closes kb/Work PB4338, the same defect filed from the PB380 report.
