## Suspected defect

⚠ This note describes PB322's group M branch (`worktree-wf_49d7e2da-ea4-2`, head `467e14020`), which train 1013 DROPPED
on a CI guard red (`kb/Work/PB1955`). It is not on main yet, and the defect becomes real when PB322 lands. Land it with
PB322, or as PB322's immediate follow-up.

PB322's determination E-extended (`docs/CONFORMANCE.md` DOC-A.1-103 on that branch, §9.1.13.1) makes a fatal I-O status
that no FILE STATUS clause, applicable USE procedure or ON EXCEPTION phrase covers terminate the run unit. The one site
on that branch is the after-hook `SequentialIoEmitter.EmitUseHook` (src/Cobol.Net.Compiler/CodeGen/Verbs/SequentialIoEmitter.cs:53),
which ends in `CobolFile.TerminateOnUncoveredFatalStatus`. Every OPEN/CLOSE/READ/WRITE/REWRITE/DELETE/START/UNLOCK and
DELETE FILE emitter calls it (SequentialIoEmitter, KeyedIoEmitter), and SORT/MERGE implicit transfers call it with
`verbDisposes: true` (SortEmitter.cs:548, the verb's own rule, §14.9.40.4 GR17 / §14.9.33.4 GR2, by design).

`src/Cobol.Net.Compiler/CodeGen/Verbs/ReportWriterEmitter.cs` never calls it: the report file's transfers happen inside
the report engine (`EmitTerminate` l.895 `…Terminate(…)`, and the INITIATE/GENERATE engine calls), so a fatal status
there, with no FILE STATUS clause, neither runs the USE procedure path nor terminates — the program continues silently.

Repro (the implementer's, not yet run by the lander): a REPORT file whose ASSIGN names a file in a missing directory,
no FILE STATUS clause, no USE procedure; INITIATE/GENERATE/TERMINATE continue. Re-probe first: if the report file's OPEN
statement already terminates through the OPEN hook, the probe must instead fail a later report write (a file closed
under the report) to reach the engine's own transfers.

## Fix shape

One after-hook for every statement that transfers a report file's records — the report engine's write path reports its
status through the same `EmitUseHook` call the WRITE statement makes (the report writer's implicit WRITE is a WRITE of
the report file), never a second termination site.

## Retired (wave 1045 group H): the behavior is the documented determination, not a defect

**Re-probed on this build.** `E:\COBOL-coord\scratch\w1045h\p1956\rw1.cob` opens a report file, INITIATEs, CLOSEs the
file under the active report, then GENERATEs and TERMINATEs with no FILE STATUS clause: the program continues
(`CLOSED / AFTER GENERATE / AFTER TERMINATE`, exit 0). `rw2.cob` adds a FILE STATUS clause, which still reads `00`.
`rw6.cob` adds a USE procedure for the report file, which does not run. That is what the note describes. The note's
premise, that DOC-A.1-103 makes this terminate, does not hold:
- **The standard.** `cite.py --check 9.1.13.1 "The value of the I-O status is set during the execution of a CLOSE,
  DELETE, OPEN, READ, REWRITE, START, UNLOCK or WRITE statement"` → OK. INITIATE, GENERATE and TERMINATE are not on
  that list. Unlike MERGE (`cite.py --check 14.9.24.4 "Each record is written as if a WRITE statement without any
  optional phrases had been executed"` → OK §14.9.24.4 12)) and SORT, no rule of §14.9.16.4 or §14.9.46.4 makes a
  report line a WRITE "as if" executed. The action after a fatal condition is the implementor's (§9.1.13.1: "The
  implementor may either continue or terminate the execution of the run unit", checked OK).
- **The precedence (CLAUDE.md rule 1).** The ISO leaves the choice to the implementor, so GnuCOBOL decides it.
  GnuCOBOL 3.2 (WSL, measured 2026-10-08 on rw1/rw2/rw6) continues past the same GENERATE and TERMINATE with no
  FILE STATUS clause, with one (it stays `00`), and with a USE procedure (it does not run).
- **The determination already in force.** DOC-A.1-159 (`docs/CONFORMANCE.md` §7) says a report line the writer
  cannot write is refused (`'91'`), "GENERATE is not among the statements §9.1.13.1 lists as setting an I-O status,
  so the FILE STATUS item is not stored by it", and the refused line leaves a blank line in the report file.
  `conformance:85/pb690_report_line_byte_image_85` pins this: a fatal `'91'` from a GENERATE in a program with
  neither a FILE STATUS clause nor a USE procedure, and the run continues.

The SORT/MERGE precedent (kb/Work PB2700) diverged from GnuCOBOL only because the standard makes those transfers
"as if" statements. The report writer has no such text.

**Change made.** DOC-A.1-103 now states its scope: the report writer's transfers do not ask its question, and the
row cites the GnuCOBOL measurement. `conformance:85/pb690_report_line_byte_image_85` is added to its witnesses, so a
later reading cannot file this note again.

If the owner wants a report line that cannot be written to end the run instead, that is a new owner decision against
DOC-A.1-159 and the rule-1 precedence, and it would be filed as `kind: decision`.
