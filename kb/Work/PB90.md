# PB90 — OPEN — which fixed-point value does a binary64 become inside the carrier: the exact expansion, the shortest round-trip decimal, or (today) the rounded double product?

> ⚙ **flags:** none — a documented implementor latitude whose current answer is self-consistent, found 2026-08-18
> landing [[PB77]] (which fixed only the PAST-the-carrier landing and deliberately left this alone).

**Measured** (`CobolFloat.ToScaled(v, scale, Truncation)` — the MOVE landing inside the Int128 carrier): the double
product `v × 10^scale` is formed in binary64 and truncated. A COMP-2 holding 8.2 (exactly 8.199999999999999289…)
moves 8.2 into PIC 9V9 because 8.2 × 10 rounds to 82.0 in binary64; a COMP-2 holding 1.15 (exactly
1.149999999999999911…) moves 1.14 into PIC 9V99 because 1.15 × 100 = 114.99999999999999 in binary64. So the manner is
"the exact expansion, except that a product within half an ulp below an integer rounds up to it" — a coin flip that
depends on the receiver's scale, not a rule a COBOL programmer can state.

**Spec:** §14.6.8.2 r1 (an intermediate / standard-float sender is "treated as if it had been converted to a fixed-point
value") and r2 (a FLOAT-* item: "the implementor defines the manner in which the value is converted to a fixed-point
value"), then r4 truncation. §15.4.1 makes the float family's returned value implementor-defined; CONFORMANCE.md item
92 says it IS a binary64. The literal reading of r1 for a standard-float sender is the EXACT expansion (8.2 → 8.1);
r2 permits any documented manner for FLOAT-LONG (which is the same `double` here, item 22).

**The three candidates:** (a) the exact expansion everywhere — `CobolFloat.LowOrderDigits` already computes it for
every finite double, so the change is removing the carrier test in `ToScaledUnchecked`/`ToScaled` — literal r1,
user-hostile (8.2 → 8.1), consistent with a GnuCOBOL that converts through mpf exactly; (b) the shortest round-trip
decimal (`CobolFloat.Display`'s value) then r4 — the value the user SEES is the value that moves (8.2 → 8.2, 1.15 →
1.15, `EXP10(25)` → 00000 low digits), consistent with item 92's "the function and an item holding its value agree";
(c) today's rounded product. **Owner decision D-follow-GnuCOBOL applies:** measure GnuCOBOL 3.x's
`cob_decimal_set_double` on `MOVE <COMP-2 8.2> TO PIC 9V9`, `<COMP-2 1.15> TO PIC 9V99`, `<COMP-2 1.0E+25> TO PIC
9(5)` (no cobc is installed here — WSL apt or a CI container), then pick between (a) and (b) accordingly; (c) is the
option to leave only if the survey shows the split is three-way. Whatever lands re-baselines the float goldens that
happen to sit on the coin flip and updates the CONFORMANCE.md §3 float→fixed bullet.
