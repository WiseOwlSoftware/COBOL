# PB688 — OPEN — a 2002 organization served to the 1985 compiler

Found 2026-09-05 by the `PB329` implementer (report §"New defects" N1), measured on its own `cobol.exe`: any program
with `SELECT F … ORGANIZATION IS LINE SEQUENTIAL` compiled `--std 85` → clean, no diagnostic.

## The facts

§9.1.7.2 (`cite.py --check 9.1.7.2 "line sequential"` → OK) draws the record-sequential / line-sequential
distinction; ANSI X3.23-1985 has no line sequential organization (its sequential organization is the record
sequential one). `tests/version-matrix/traceability-inventory.json` already carries `GR-14.9.30.4-16`'s editions as
`2002,2014,2023`, and `docs/COBOLNET_FILES_DESIGN.md` says in terms *"ORGANIZATION LINE SEQUENTIAL is not a COBOL-85
organization: rejected at 85. The exact introduction edition is …"* — the intent is stated and the gate is absent:
`grep -ri "line.sequential" src/Cobol.Net.Editions` returns only an unrelated `DiagnosticCatalog` comment; there is
no `constructs.json` row. Same family as [[PB674]] (a gate the 85↔2002 ledger cannot derive) — but here the
1985 text's silence IS derivable: the 1985 standard's ORGANIZATION clause lists SEQUENTIAL, RELATIVE and INDEXED
only, which the version reference records, so this one does not wait on the 2002 text.

## Fix

One `constructs.json` row (`file-organization-line-sequential-2002`, introducedIn 2002 — confirm the edition from
`docs/VERSION_CHANGE_REFERENCE.md` before writing it), one `VersionConformancePass` arm on the organization clause,
the edition-gate sweep over the corpus (every 85 golden that names the organization is either moved or made a reject
case), a negative at 85 and acceptance at 2002. The per-edition mission (D13) is false for every line-sequential
program until then.
