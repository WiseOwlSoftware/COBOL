# PB688 — LANDED — a 2023 organization served to the 1985, 2002 and 2014 compilers

Found 2026-09-05 by the `PB329` implementer (report §"New defects" N1), measured on its own `cobol.exe`: any program
with `SELECT F … ORGANIZATION IS LINE SEQUENTIAL` compiled `--std 85` → clean, no diagnostic.

## Landed — 2026-09-05

**The edition in the original note was WRONG, and re-deriving it is most of what this landing did.** The note said
"2002 introduction … the exact introduction edition is not derivable from the 2023 spec", inherited from
`docs/COBOLNET_FILES_DESIGN.md`, which said the same. It IS derivable, from the 2023 spec's own **Foreword**: the
list of the main changes this third edition makes over ISO/IEC 1989:2014 names **"Line Sequential file
organization"**. So the organization is a **COBOL-2023 introduction** and does not exist at 2002 or 2014 either.
What made it look underivable is that Annex E carries no item for it and `VERSION_CHANGE_REFERENCE.md` no row —
the two places a reader checks. (`cite.py` cannot validate a Foreword citation: it searches numbered clause
regions only, and the Foreword is not one. The clause citations below all `--check` OK.)

`ORGANIZATION IS LINE SEQUENTIAL` is a *phrase*, not a fourth organization: §9.1.6 and §9.1.7.1 still name exactly
three organizations — `cite.py --check 9.1.7.1 "There are three file organizations: sequential, relative, and
indexed"` → OK — and §9.1.7.2 splits the sequential one into its record- and line-delimited types, which is the
`{ LINE | RECORD }` inner choice of the §12.4.5.10.2 general format. The rule the gate is keyed to is
§12.4.5.10.3 GR2 — `cite.py --check 12.4.5.10.3 "The LINE SEQUENTIAL phrase specifies that the file organization
is line sequential"` → OK 12.4.5.10.3 2).

**The fix is one construct row and one parse-arm.** `tests/version-matrix/constructs.json` gains
`file-organization-line-sequential-2023` (`introducedIn: 2023`, COBOLNET0900 — no new code was minted; an edition
gate is the existing 0900 family), and `VersionConformancePass.ParseArm.VisitOrganizationClause` fires on the
clause's RECOGNITION, next to its 14g.4 siblings SHARING / LOCK MODE / file COLLATING SEQUENCE. Recognition, not
the bound `FileModel`, because a SELECT that also fails to bind would otherwise drop the 0900 with the discarded
model (DEVLOG 724). **`organizationClause` has TWO grammar parents** — the file control entry (`CobolIO.g4`) and
the FD clause list (`CobolData.g4`) — the repo's most reproducible defect shape; the ONE arm covers both, and a
negative golden pins each.

**The edition-gate sweep is most of the diff, and it exposed a second fact.** Thirteen corpus programs below 2023
named the organization. Ten of them are report-writer / OO goldens that observe their report by re-reading the
report file through a second SELECT with `ORGANIZATION IS LINE SEQUENTIAL` — and **COBOL.NET's report writer frames
a report file as CRLF-delimited text whatever its ORGANIZATION is** (measured: `rw-suppress.rpt` is
`\r\n\r\n\r\nGROUP-1\r\n…`), while the record-sequential connector reads fixed-size records. So below 2023 there is
no legal way to read a COBOL.NET report file back at all, and those goldens are 2023 programs: nine moved from
`tests/conformance/2002/` to `tests/conformance/2023/`. The `pb329_line_sequential_charset` copies at 2002 and 2014
are identical to the 2023 copy modulo PROGRAM-ID and file names and were deleted — no edition below 2023 can
express them. `negative/pb485-level-77-file-section` uses the organization incidentally (it only OPENs and CLOSEs)
and was converted to record sequential so its single reject reason stays COBOLNET1746.

**The one program that had to stay below 2023 lost nothing.** `85/pb326_flow_report_unconditional` exists to pin
§14.9.49.4 GR10's unconditional half *at the oldest edition* ("COBOL-85 has no `>>TURN` directive at all"), so it
could not move. Its read-back is gone and `N=1` carries the evidence alone: §14.9.49.4 GR8/GR9d run the USE BEFORE
REPORTING procedure once per PRESENTATION of the group, so `WS-N` **is** the count of presented detail lines — the
read-back was observing at the file what the declarative already observes at the source.

**MEASURED on the built `cobol.exe`.** Before: `SELECT F ASSIGN TO "pb688.txt" ORGANIZATION IS LINE SEQUENTIAL`
compiled clean at `--std 85` (exit 0, `.dll` emitted). After: `COBOLNET0900: ORGANIZATION LINE SEQUENTIAL requires
COBOL-2023 (targeting COBOL-85)` at 85, 2002 and 2014; clean at 2023. The FD-position clause gates identically.

**Row:** `GR-12.4.5.10.3-2` closes CONFORMS (GAP −1). The landing also re-pointed FOURTEEN rows other notes own:
the nine moved goldens' `test-ref`s, and `GR-14.9.30.4-15`, `GR-14.9.30.4-16`, `GR-14.9.51.4-23` and
`DOC-A.1-115`, whose `editions` were `2002,2014,2023` — an inherited claim that could not be true — and are now
`2023`. `GR-14.9.51.4-23` arrived with the `origin/main` merge (it was verdicted after this branch forked) and
only the gate could see it: `SpecTraceabilityInventoryDriftTests.EveryTestRef_ResolvesToARealTest` named its two
dead refs, and a SECOND batch — never a hand edit to the JSON — cleared them.

## The original finding

§9.1.7.2 draws the record-sequential / line-sequential distinction; ANSI X3.23-1985 has no line sequential
organization. `grep -ri "line.sequential" src/Cobol.Net.Editions` returned only an unrelated `DiagnosticCatalog`
comment; there was no `constructs.json` row and no gate. Same family as [[PB674]] (a gate the 85↔2002 ledger cannot
derive) — except that this one turned out to need no older standard at all.
