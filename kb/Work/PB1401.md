# PB1401 — LANDED (wave 65 E)

## The rule (every citation re-run by the registrar through `cite.py --check`)

**GR-8.5.2.12-6**

> A numeric function. …

`python scripts/spec/cite.py --check 8.5.2.12 "A numeric function."` → `OK  §8.5.2.12 6)  (Numeric category)`

## Finding — `class-and-category-of-data-items-and-literals-p2` (crashes; rows `GR-8.5.2.12-3`, `GR-8.5.2.12-4`, `GR-8.5.2.12-5`, `GR-8.5.2.12-6`, `GR-8.5.2.12-7`)

**Mechanism.** The class-condition renderer reads identifier-1's category ONLY through a BoundFieldOperand, so a category-numeric operand that binds as a computed operand — LINE-COUNTER, LINAGE-COUNTER, PAGE-COUNTER (BoundComputedOperand over BoundLinageCounterRef / BoundReportCounterRef) and a numeric or integer function-identifier — is either dereferenced as a null field (FARTHEST-FROM-ZERO / NEAREST-TO-ZERO / IN-ARITHMETIC-RANGE: compiler NullReferenceException) or classified NON-numeric and sent down the string arm (NUMERIC on a counter: OperandText.AsString's LoudValue, a run-time NotImplementedCobolFeatureException). The binder's SR6/SR8 screen already knows these operands are category numeric; the emitter has a second, narrower category reader.

**Repro.** FD PFILE LINAGE IS 10 LINES. ... OPEN OUTPUT PFILE. WRITE PR FROM "A". IF LINAGE-COUNTER IS NUMERIC DISPLAY "Y" ELSE DISPLAY "N" END-IF. (compiles at 85 and 2023, throws NotImplementedCobolFeatureException 'computed expression in a string context' at run time) — and IF LINAGE-COUNTER IS IN-ARITHMETIC-RANGE ... / IF PAGE-COUNTER IS NEAREST-TO-ZERO ... / IF FUNCTION INTEGER(3.5) IS IN-ARITHMETIC-RANGE ... / IF FUNCTION SQRT(4) IS NEAREST-TO-ZERO ... each crash the compiler with NullReferenceException at ConditionRenderer.RenderInArithmeticRange:717 / RenderExtremeClass:685. Probe sources: out/probe/cc2/g85.cob, k1-k5.cob, k21-k22.cob, f13.cob, f14.cob (pinned adj-d2 cobol.exe).

**Expected from the spec.** §8.5.2.12 items 3-7 make each of these operands a category-numeric data item; §8.8.4.4.3 SR6 ('If FARTHEST-FROM-ZERO, IN-ARITHMETIC-RANGE, or NEAREST-TO-ZERO is specified, identifier-1 shall reference a data item whose category is numeric') and SR8 (NUMERIC on an item 'whose category is numeric') make every repro conforming source. Expected: clean compiles; LINAGE-COUNTER IS NUMERIC -> TRUE ('Y') by §8.8.4.4.4 GR3 n) 1. (a counter's content is a valid unsigned integer), PAGE-COUNTER IS NOT NUMERIC -> 'N'; LINAGE-COUNTER / LINE-COUNTER / FUNCTION INTEGER(3.5) IS IN-ARITHMETIC-RANGE -> TRUE by GR3 l); FARTHEST-/NEAREST-TO-ZERO answered by GR3 g)/m) against the operand's declared capacity (LINAGE-COUNTER sized by the LINAGE page size per §8.4.3.14.4 GR1; the report counters per the documented PIC 9(18) shape).

**Observed / reasoning.** Measured with the pinned compiler: the four SR6 phrases over a counter or function-identifier abort the compile with System.NullReferenceException (`var pic = f.Place.Item.OperandPic!` / `fld!` — RenderClass passes `fld!` where `fld = c.Operand as BoundFieldOperand` is null); `IF LINAGE-COUNTER IS NUMERIC`, `IF LINE-COUNTER IS NUMERIC` and `IF PAGE-COUNTER IS NOT NUMERIC` compile clean and throw at run time because `numericCategory = fld is not null && ...` is false and the operand is rendered through OperandText.AsString, whose BoundComputedOperand arm is EmitText.LoudValue('computed expression in a string context'). `IF FUNCTION SQRT(4) IS NUMERIC` happens to answer Y via the string arm. The same counters compute correctly in COMPUTE/ADD and HIGHEST-ALGEBRAIC (R26), so the category model is right and only this renderer's private reader is narrower — a one-rule-two-places shape (binder SR6/SR8 screen vs ConditionRenderer.StringCategoryOf over a field).

**Code site.** src/Cobol.Net.Compiler/CodeGen/Emit/ConditionRenderer.cs#ConditionRenderer.RenderClass (fld = c.Operand as BoundFieldOperand; numericCategory), #RenderExtremeClass (line ~685), #RenderInArithmeticRange (line ~717); operand shapes from src/Cobol.Net.Compiler/Binding/Procedure/ExpressionBinder.cs:333/411 (BoundLinageCounterRef) and src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ReportWriterBinder.cs:270 (BoundReportCounterRef)

## What the fixer owes

Read the operand's category from the bound operand's result description (a BoundComputedOperand carries one) in RenderClass / RenderExtremeClass / RenderInArithmeticRange; sweep every ConditionRenderer arm that casts to BoundFieldOperand. Goldens: each counter and a numeric function under each numeric class test.

## Landed (wave 65 group E)

**Re-probed first on the wave-65 build** (base `1dd1b63a7`): `IF LINAGE-COUNTER IS NUMERIC` threw
`NotImplementedCobolFeatureException: computed expression in a string context` at run time; `IF LINAGE-COUNTER IS
IN-ARITHMETIC-RANGE` and `IF FUNCTION INTEGER(3.5) IS IN-ARITHMETIC-RANGE` crashed the COMPILER with a
NullReferenceException at `ConditionRenderer.RenderInArithmeticRange:717` — the note reproduced exactly.

**The rule was written in two places and both read the operand only as a data-item reference.**
- The BINDER screen (`ConditionBinder.CheckClassConditionOperand`) handed every non-field operand a null category,
  so §8.8.4.4.3 SR4/SR5/SR6 failed open over counters and functions. It now asks
  `IntrinsicResultType.OperandCategory` of EVERY operand (the one reader already answers numeric for a register
  and the §15.2 type for a function), gives a function its §15.2 implicit usage (display / bit / national), and
  `ClassConditionModel.Violates` states SR3's function sentence ("If identifier-1 is a function-identifier, it
  shall reference an alphanumeric or national function") by the function's type. `IF FUNCTION UPPER-CASE(A) IS
  NEAREST-TO-ZERO` (SR6), `IF FUNCTION SQRT(4) IS ALPHABETIC` (SR4) and `IF FUNCTION SQRT(4) IS alphabet-name`
  (SR3) are now refused — each used to compile.
- The RENDERER (`ConditionRenderer.RenderClass`) asks the same reader, and a computed category-numeric operand
  goes to `RenderComputedNumericClass`, which asks each question of the operand's VALUE, evaluated ONCE (the new
  runtime `CobolValueClass`, and `CobolFloatClass` for a binary64 function result): NUMERIC per GR3 n) 1. (true;
  finite for binary64), FARTHEST-/NEAREST-TO-ZERO per g)/m) against the capacity of the item the operand references,
  IN-ARITHMETIC-RANGE per l) against the mode's intermediate extremes.
- The capacities are ONE statement each in `AlgebraicRanges`: `OfCounterRegister` (moved out of
  `IntrinsicBinder.LinagePageCapacity`, which re-resolved the LINAGE data-name by its bare name and read `items[0]`
  — it now reads the qualified `LinageOperand.Item`) serves both the HIGHEST/LOWEST/SMALLEST-ALGEBRAIC folds and the
  class conditions; `OfFunctionReturnedValue` states the function temporary's capacity (CONFORMANCE.md DOC-A.1-92,
  extended: binary64 / SDIDI / the §15.4 temporary's S9(30) or S9(21)V9(9)).

Goldens: `conformance:2014/pb1401_computed_numeric_class` (every counter and function leg of all four numeric
alternatives, plus a RANDOM leg proving single evaluation), `conformance:85/pb1401_computed_numeric_numeric` (the
NUMERIC legs at the operands' introducing edition), negatives `pb1401-function-nearest-to-zero-not-numeric`
(2014/2023, COBOLNET2216), `pb1401-numeric-function-alphabetic` and `pb1401-numeric-function-alphabet-name` (all
editions, COBOLNET0844 / COBOLNET2202). Rows GR-8.5.2.12-3..7 re-verdicted CONFORMS (batch
`w65e-pb1401-pb1466`).

Sibling sweep: every consumer of `BoundClassCondition` (`UsageCollectionPass`, `ConditionBinder`,
`ConditionRenderer`) and every `fld!` arm of `RenderClass` — the float-only arms are unreachable for a computed
operand because SR7 now refuses it at bind; the renderer's remaining non-field numeric shape is loud. The
alphabet-name-1 test over a COUNTER (legal by SR3 under the documented PIC 9(18) shape) still reaches
`OperandText.AsString`'s computed arm — that is kb/Work PB1199's mechanism (a counter in a character context),
left to it.
