# PB194 — the mode SET is written down twice and the two copies disagree

Found in the PB146 survey; **re-verified against the current tree and measured 2026-08-31** rather than accepted
from the finding.

## The two spellings

`ARITHMETIC IS STANDARD` (COBOL-2002, obsolete 2014, removed 2023) routes to the **same CobolDec/SDIDI decimal
engine** as `STANDARD-DECIMAL` — `NumericRenderer.cs` says so in a comment and encodes it:

```csharp
// NumericRenderer.cs  — the CORRECT spelling
internal bool StandardDecimal => ctx.Data.Options.Arithmetic is ArithmeticMode.StandardDecimal or ArithmeticMode.Standard;

// ExpressionBinder.cs CheckLiteral — also correct
if (ctx.Data.Options.Arithmetic is ArithmeticMode.StandardDecimal or ArithmeticMode.Standard)
```

Two sites in `IntrinsicBinder.cs` write the **other** set:

```csharp
// :2380  (SMALLEST-/LARGEST-ALGEBRAIC, the USAGE arm)
bool standardDec = ctx.Data.Options.Arithmetic == ArithmeticMode.StandardDecimal;
if (farthestExp > (standardDec ? 6145 : 308) || closestExp < (standardDec ? -6176 : -324))

// :2433  (the same screen, the PICTURE/edited arm)
bool standardDecimal = ctx.Data.Options.Arithmetic == ArithmeticMode.StandardDecimal;
int modeFarthest = standardDecimal ? 6145 : 308;
int modeClosest  = standardDecimal ? -6176 : -324;
```

Under `ARITHMETIC IS STANDARD` those two screens take the **native** branch and measure the argument against
binary64's ≈1E+308 / 4.9E−324 while every value in that compilation is actually a decimal128 SDIDI intermediate
(≈1E+6145 / 1E−6176). An argument that the engine handles exactly is diagnosed as out of range, and the
diagnostic's own text then says "outside the **native (binary64)** intermediate's range" in a program that
selected a standard mode — so the message misdescribes the compilation as well.

## Measured

At `--std 2014` with `OPTIONS. ARITHMETIC IS STANDARD.`, `IF 1.0E+400 > X` **compiles and runs** (prints `BIG`,
with the expected COBOLNET0903 obsolescence warning) — i.e. `CheckLiteral` correctly treats STANDARD as
decimal128. The two `IntrinsicBinder` sites, in the same compilation, would have used 308/−324 for the same mode.
One arithmetic mode, two contradictory bounds, decided by which file the code path happened to reach.

## Why this is `wrong_answer` + `silent`

The screen is a compile-time diagnostic, so the failure is not a wrong runtime value but a **wrongly rejected or
wrongly accepted argument** with no indication that the mode was misread — and its sibling paths keep working,
which is what makes it silent. It is exactly [[feedback_one_rule_one_place]]: the mode set is one rule written
down in more than one place, and the extraction IS the fix.

## The fix shape (not a third literal)

Give the mode set **one named home** — the decimal-engine predicate is already spelled twice correctly, so hoist
it (e.g. onto `ArithmeticMode` or the options model as `IsStandardDecimalEngine`) and have all four sites read
it. Then a **drift test** that fails when any `Arithmetic ==` / `Arithmetic is` comparison outside that one
accessor names `StandardDecimal` — otherwise the fourth copy is one edit away. Sweep for siblings before
fixing: this is a two-arm dispatch of the kind that has bitten five times ([[feedback_two_arm_dispatch]]), and
only two arms have been counted so far.
