# PB194 — the mode SET is written down twice and the two copies disagree

Found in the PB146 survey; **re-verified against the current tree and measured 2026-08-31** rather than accepted
from the finding.

## The two spellings

`ARITHMETIC IS STANDARD` (COBOL-2002, obsolete 2014, removed 2023) routes to the **same CobolDec/SDIDI decimal
engine** as `STANDARD-DECIMAL` — `NumericRenderer.cs` says so in a comment and encodes it:

```csharp
// NumericRenderer.cs  — the CORRECT spelling
internal bool StandardDecimal => ctx.Data.Options.Arithmetic is ArithmeticMode.StandardDecimal or ArithmeticMode.Standard;

// ExpressionBinder.cs CheckLiteral — also correct
if (ctx.Data.Options.Arithmetic is ArithmeticMode.StandardDecimal or ArithmeticMode.Standard)
```

Two sites in `IntrinsicBinder.cs` write the **other** set:

```csharp
// :2380  (SMALLEST-/LARGEST-ALGEBRAIC, the USAGE arm)
bool standardDec = ctx.Data.Options.Arithmetic == ArithmeticMode.StandardDecimal;
if (farthestExp > (standardDec ? 6145 : 308) || closestExp < (standardDec ? -6176 : -324))

// :2433  (the same screen, the PICTURE/edited arm)
bool standardDecimal = ctx.Data.Options.Arithmetic == ArithmeticMode.StandardDecimal;
int modeFarthest = standardDecimal ? 6145 : 308;
int modeClosest  = standardDecimal ? -6176 : -324;
```

Under `ARITHMETIC IS STANDARD` those two screens take the **native** branch and measure the argument against
binary64's ≈1E+308 / 4.9E−324 while every value in that compilation is actually a decimal128 SDIDI intermediate
(≈1E+6145 / 1E−6176). An argument that the engine handles exactly is diagnosed as out of range, and the
diagnostic's own text then says "outside the **native (binary64)** intermediate's range" in a program that
selected a standard mode — so the message misdescribes the compilation as well.

## Measured

At `--std 2014` with `OPTIONS. ARITHMETIC IS STANDARD.`, `IF 1.0E+400 > X` **compiles and runs** (prints `BIG`,
with the expected COBOLNET0903 obsolescence warning) — i.e. `CheckLiteral` correctly treats STANDARD as
decimal128. The two `IntrinsicBinder` sites, in the same compilation, would have used 308/−324 for the same mode.
One arithmetic mode, two contradictory bounds, decided by which file the code path happened to reach.

## Why this is `wrong_answer` + `silent`

The screen is a compile-time diagnostic, so the failure is not a wrong runtime value but a **wrongly rejected or
wrongly accepted argument** with no indication that the mode was misread — and its sibling paths keep working,
which is what makes it silent. It is exactly [[feedback_one_rule_one_place]]: the mode set is one rule written
down in more than one place, and the extraction IS the fix.

## The fix shape (not a third literal)

Give the mode set **one named home** — the decimal-engine predicate is already spelled twice correctly, so hoist
it (e.g. onto `ArithmeticMode` or the options model as `IsStandardDecimalEngine`) and have all four sites read
it. Then a **drift test** that fails when any `Arithmetic ==` / `Arithmetic is` comparison outside that one
accessor names `StandardDecimal` — otherwise the fourth copy is one edit away. Sweep for siblings before
fixing: this is a two-arm dispatch of the kind that has bitten five times ([[feedback_two_arm_dispatch]]), and
only two arms have been counted so far.

## FIXED 2026-08-31 (the arithmetic wave) — and the note's own harm flags were WRONG

### Re-measured on THIS tree before fixing, both arms

At `--std 2014`, `01 EA PIC 9(3)E+999.` with `DISPLAY FUNCTION HIGHEST-ALGEBRAIC(EA)`:

| mode | result |
|---|---|
| `OPTIONS. ARITHMETIC IS STANDARD.` | **rejected** — `COBOLNET1660: … outside the native (binary64) intermediate's range` |
| `OPTIONS. ARITHMETIC IS STANDARD-DECIMAL.` | compiles; prints `999E+999` |

⛔ **So the harm is a HARD REJECTION of conforming source, and this note's frontmatter said
`rejects_legal_source: false`** (it claimed `wrong_answer` + `silent`, reasoning about a screen that could go
either way). The screen is an `Error`, and the reachable direction is the refusing one. The register ranks on
what a defect DOES to a user's program, so the flag was ranking this below where it belonged — recorded here
because [[feedback_measure_the_selectors_complement]] is exactly about a filter being evidence only about what
it returned.

### The fix: the mode set has ONE home now

`ArithmeticModes` (the existing per-mode fact table, which already held `NumvalDigitCap`) gains
`IsDecimalEngine`, `IntermediateExponentRange` and `IntermediateName` — each a switch total over
`ArithmeticMode`, so a fifth mode is a compile-or-test failure rather than a silent fall-through. All four sites
read them: `NumericRenderer.StandardDecimal`, `IntrinsicBinder`'s float-USAGE arm, `IntrinsicBinder`'s
float-EDITED arm, and — by deletion — `ExpressionBinder.CheckLiteral`, whose copy of the set disappeared
entirely when owner decision D-B made the literal range mode-independent ([[PB156]]).

STANDARD-BINARY's bounds are recorded too, from §8.8.1.4.2 NOTE 3 (±(2\*\*16384 − 2\*\*16271) ≈ 1.19E+4932;
"the smallest positive nonzero value is 2\*\*-16494" ≈ 6.5E−4966 — `cite.py --check` PASSED). The mode is
unreachable (declined at bind), and the entry exists for the same reason `NumvalDigitCap`'s 35 does: a table
with a hole answers a question it has never been asked.

### The twin-arm answer, stated

The two `IntrinsicBinder` sites are NOT equally live. The float-EDITED arm reads a PICTURE, which can name any
exponent width, so the drift was observable there — that is the measurement above. The float-USAGE arm compares
a CARRIER's extremes, and every carrier declarable today (binary32 ±38/−45, binary64 ±308/−324, decimal ±28)
passes under every reachable mode, so its drift was **latent**: correct-by-accident, never contradicted, exactly
[[feedback_a_dead_lookup_is_also_unverified]]. It is fixed and covered by the table test, not by a golden,
because no COBOL program can currently reach it — said out loud so nobody later reads a green golden as
evidence about that arm.

⚠ Two sites deliberately NOT moved. `IntrinsicBinder:2353/:2360` compare against `StandardDecimal` /
`StandardBinary` alone, and that is SPEC-CORRECT: §15.43.3 / §15.83.3 rules 2 and 3 say "If **standard-decimal**
arithmetic is in effect …" and "If **standard-binary** arithmetic is in effect …", naming one mode each, with
rule 4 handing native's restrictions to the implementor — ARITHMETIC IS STANDARD is named by none of them. This
note's proposed drift test ("fails when any comparison outside that one accessor names StandardDecimal") would
have forced those two to move and would have been wrong to; the guard that landed instead is narrower and
mechanical: **the SDIDI exponent bound `6145` may appear in exactly one file**
(`ArithmeticModeTableTests.TheSdidiExponentBounds_AreWrittenDownExactlyOnce`), which is what stops the fourth
copy the note correctly predicted.
