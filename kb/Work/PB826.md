# PB826 — OPEN — one column, two conventions, and no mechanism keeping them equal

Filed 2026-09-09 by the registrar (third pass) from the **PB452 implementer's report** §13 item (2) —
`scratchpad/reports/PB452-report.md`. **Re-measured on this worktree's own
`dotnet build CobolSharp.sln -c Debug` (exit 0) at `094739b3`, and the re-measurement REFUTES the lead's
premise**, which is why this is filed as `analysis` and not as a defect.

## ⛔ Premise correction — the cap the lead says is unenforced IS enforced

The report states: *"nothing enforces the §13.18.40.4 GR13 b cap that makes them interchangeable"*. Measured on
`scratchpad/registrar3/probe/p2_floatedit.cob` (PROGRAM-ID `PBR826`), `--std 2023`:

```
01 FE5 PIC +9.9(3)E+9(5).
  → error COBOLNET1658: invalid floating-point numeric-edited PICTURE +9.9(3)E+9(5) - data item 'FE5':
    the exponent shall be +9, +99, +999 or +9999 (ISO 13.18.40.4 GR13 b)
```

```
$ python scripts/spec/cite.py --check 13.18.40.4 "The exponent shall be '+9', '+99', '+999', '+9999', or '+9(n)' where n = 1, 2, 3, or 4."
  OK  §13.18.40.4 13)  (General rules)
$ python scripts/spec/cite.py --check 13.18.40.3 "For floating-point data items of category numeric-edited, the number of digit positions in the significand shall range from 1 through 36."
  OK  §13.18.40.3 15)  (Syntax rules)
```

The significand cap is enforced in the same analyzer (`PictureAnalyzer.cs:681-731`, the per-string Table 10
validation). So **both screens the interchangeability argument rests on exist and fire**, and the four-digit
exponent confines the EDITED arm's reachable `farthestExp` to `[9,45] ∪ [99,135] ∪ [999,1035] ∪ [9999,10035]`
exactly as `OptionsModel.cs:130-136` claims. The behaviour is correct today. What the lead really found is
underneath that.

## What is actually true, and why it is worth a note

**1. The column IS read under two conventions, and this is documented but not enforced.**
`ArithmeticModes.IntermediateExponentRange` (`src/Cobol.Net.Compiler/Binding/OptionsModel.cs:150-157`) returns
`(Farthest, Closest)`; its own doc comment (`:130-136`) says:

> *"⚠ AND THE COLUMN IS READ UNDER TWO CONVENTIONS. `IntrinsicBinder`'s float-EDITED arm supplies
> `intDigits + fm.MaxExp` (the strict upper bound above); its float-ITEM arm supplies the carrier's EXACT
> magnitude exponent ({28, 38, 308}). Nothing separates them today … If the ITEM arm ever gains a TRUE
> decimal128 carrier row it must be written 6144, its exact magnitude exponent, NOT 6145."*

That instruction is addressed to a future reader of a comment. `ArithmeticModeTableTests` pins the table's
VALUES to the spec (`IntermediateExponentRange_PinnedToSpec`, `StandardAndStandardDecimal_AreOneEngine…`,
`IsDecimalEngine_AndExponentRange_AreTotalOverEveryArithmeticMode`) and pins nothing about the two readings. A
row added under the wrong convention is off by exactly one decade and every existing test stays green.

**2. The float-ITEM arm carries a THIRD hand-list, and its `_` arm is the trap.**
`IntrinsicBinder.cs:2455-2459`:

```csharp
var (farthestExp, closestExp) = pic.Usage switch
{
    Usage.Float or Usage.FloatShort or Usage.FloatBinary32 => (38, -45),
    Usage.FloatDecimal16 or Usage.FloatDecimal34          => (28, -28),
    _                                                     => (308, -324),
};
```

This is a hand-maintained per-usage table of carrier extremes, distinct from `IntermediateExponentRange` and
from `PicInfo`, and its default arm gives **every unlisted usage binary64's bounds**. A carrier wider than
binary64 landing under any usage not named above inherits `(308, -324)` and passes the §15.83.4 r1
IN-ARITHMETIC-RANGE screen it should fail — a silent under-reject followed by a folded extreme that is
binary64's, not the carrier's. This is precisely the *"hand-maintained list where a structure belongs"*
CLAUDE.md rule 5 names.

**3. Its latency is real but INCIDENTAL, and that is the finding.** Measured on
`scratchpad/registrar3/probe/p2_carriers.cob` (PROGRAM-ID `PBR826B`):

```
01 F128 USAGE FLOAT-BINARY-128.  → error COBOLNET1564 … not supported by COBOL.NET (Annex A.3 item 17)
01 D34  USAGE FLOAT-DECIMAL-34.  → error COBOLNET1564 … not supported by COBOL.NET (Annex A.3 item 19)
01 FX   USAGE FLOAT-EXTENDED.    → accepted, folded, and (308,-324) is right for its carrier
01 F64  USAGE FLOAT-BINARY-64.   → accepted, folded, and (308,-324) is right
```

So the `_` arm is safe **only because a DIFFERENT subsystem declines the two wide carriers at bind**. The
comment at `:2385-2391` says the arm is *"LATENT: it fires only if a wider carrier (a true binary128, say) ever
lands, and then automatically"* — measured true, and the word "automatically" is the part that is not: when
binary128 lands (Annex A.3 item 17 is a declared non-support, not a permanent one), it will fall into `_` and
inherit binary64's bounds unless someone remembers to add the row. `feedback_reachability_is_measured_not_deduced`
cuts both ways here: the arm is unreachable today, by measurement, and the thing keeping it unreachable is not
the arm.

The rule the two arms are screening against, `--check`ed on this tree:

```
$ python scripts/spec/cite.py --check 8.8.4.4.4 "IN-ARITHMETIC-RANGE"
  OK  §8.8.4.4.4 3) d) 2.  (General rules)
      l) If IN-ARITHMETIC-RANGE Is specified, the condition is true if the numeric content of the data item
         referenced by identifier-1 is neither farther from zero nor closer to zero than is permitted for the
         form of an intermediate data item …
```

⚠ Note the `rule_path` label: the text is item **l)** of rule **3)**, and `cite.py` prints `3) d) 2.` — the
mis-lettering below the rule ordinal that the second-pass registrar recorded (kb/Work PB779's territory). The
`--check` verdict and the RULE ordinal are sound; quote the SENTENCE, and write the citation as **§8.8.4.4.4 GR3
l)**, which is how both existing call sites already spell it.

## Shape of the answer (a design question, not a patch)

One convention plus an explicit adapter. Either:

* **(a)** make the column the carrier's EXACT magnitude exponent everywhere (6144, not 6145) and give the EDITED
  arm a `< bound + 1` comparison, or
* **(b)** keep the strict-upper-decade convention and give the ITEM arm an adapter that converts a carrier's
  exact exponent into the same convention,

and in either case **derive the carrier extremes from ONE table keyed on the carrier**, not from a `switch` in
the binder — the `PicInfo.Truncation` refactor `IntrinsicBinder.cs:2493` already did for the BinaryCapacity
family is the precedent, together with `AlgebraicFoldContainerAgreementTests`, which is the drift test shape this
needs. Pair whichever is chosen with a test that asserts the two readings agree over the reachable set, so
"interchangeable" stops being a paragraph.

⚠ **`ArithmeticModes.IntermediateExtremes` — the second table PB452 adds, and the
`IntermediateExtremes_AgreeWithTheDecadeBoundsTheyAreNot` test whose `<=` the report cites as evidence — is NOT
on `main` at `094739b3`.** PB452 lands with train 26. Whoever takes this item re-reads that test first: it is the
nearest thing to the missing invariant and may already be half of it.
