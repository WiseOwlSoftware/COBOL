# PB1199 — OPEN

## The rule
§8.4.2.2.2 Format 8 is the qualified-report-counter reference (`{PAGE-COUNTER | LINE-COUNTER} {IN | OF} report-name`),
an identifier form; §8.4.2.2.3 SR9:

> 9) LINE-COUNTER shall be qualified each time it is referenced in the procedure division if more than one report description entry is specified in the source element. …

`python scripts/spec/cite.py --check 8.4.2.2.3 "LINE-COUNTER shall be qualified each time it is referenced in the procedure division"` → `OK  §8.4.2.2.3 9)  (Syntax rules)`

Nothing restricts a report counter from a DISPLAY operand (a sending position); the compiler itself admits
`MOVE LINE-COUNTER OF R1 TO WS-LC`.

## Measured
`probe/suppress-statement/gr3.cob` (the adjudicator's RD R1 program) with its `MOVE LINE-COUNTER OF R1 TO WS-LC.`
replaced by `DISPLAY "LC=" LINE-COUNTER OF R1.` (registrar copy `f49c…/scratchpad/r14c/probe/lcdisp.cob`),
`cobol lcdisp.cob --std 2023 --run`:

```
Unhandled exception. CobolNet.Runtime.NotImplementedCobolFeatureException: COBOL.NET: a COBOL feature that is not yet implemented was reached at run time: computed expression in a string context
   at CobolNet.Runtime.NotImplemented.Value[T](String feature)
```

## Code sites
- `src/Cobol.Net.Compiler/Binding/Procedure/ExpressionBinder.cs` ~333-337: `LinageFileOf(dref) … new BoundComputedOperand(new BoundLinageCounterRef(lcf))` and `host.Rw.CounterExpr(dref) is { } rcx ? new BoundComputedOperand(rcx)`.
- `src/Cobol.Net.Compiler/CodeGen/Emit/OperandText.cs` ~535: `Visit(BoundComputedOperand n) => EmitText.LoudValue("string", "computed expression in a string context")` — its comment's premise ("what reaches this arm is … an arithmetic expression in a string position, which no general format admits") is false for the counters.

## What the fixer owes
Give the report counters (and LINAGE-COUNTER, bound through the same BoundComputedOperand arm — sweep it) a
string/DISPLAY rendering (an unsigned integer image, as DISPLAY of any numeric integer item), or bind them as a
typed place rather than a computed operand so every sending position (DISPLAY, STRING, INSPECT, comparisons) sees an
identifier. Then make the loud arm unreachable by construction for anything but a true arithmetic expression. Golden
at 85 (report writer) with DISPLAY of LINE-COUNTER / PAGE-COUNTER / LINAGE-COUNTER.

### Finding — `identifier` (crashes; rows `FMT-8.4.3.1.2`)

**Mechanism.** Identifier Formats 10/11 (LINAGE-COUNTER, LINE-COUNTER, PAGE-COUNTER) are bound as BoundComputedOperand, and OperandText's string channel renders any BoundComputedOperand as a loud NotImplemented stub, so every string-rendering context compiles clean and aborts at run time

**Repro.** FD F1 LINAGE 10. 01 R1 PIC X(10). ... OPEN OUTPUT F1 MOVE "X" TO R1 WRITE R1 WRITE R1 DISPLAY "LC " LINAGE-COUNTER. (cobol --std 85 --run). Report twin: RD RPT1 PAGE LIMIT 60 LINES ... INITIATE RPT1 GENERATE DETAIL-LINE DISPLAY "PC " PAGE-COUNTER OF RPT1 / DISPLAY LINE-COUNTER / MOVE PAGE-COUNTER OF RPT1 TO WA (WA PIC X(4)).

**Expected from the spec.** 8.4.3.15.3 SR1: 'In the procedure division, PAGE-COUNTER and LINE-COUNTER may be referenced in any context where an integer data item may appear'; LINAGE-COUNTER is likewise a procedure-division identifier (8.4.3.14). DISPLAY identifier-1 (14.9.11) shows the counter's digits (e.g. LC after OPEN + 2 WRITEs = the current line, 3 with this implementation's MOVE path which reads 03); MOVE of an unsigned integer to PIC X(4) moves its digit string left-justified (14.9.25.4). The program runs to STOP RUN.

**Observed / reasoning.** Clean compile; run aborts NotImplementedCobolFeatureException 'computed expression in a string context'. Generated C#: System.Console.WriteLine("LC " + NotImplemented.Value<string>("computed expression in a string context")) and WA = CobolString.Store(NotImplemented.Value<string>(...), 4). ExpressionBinder (dref.LINAGE_COUNTER() arm ~:332) wraps the counter as new BoundComputedOperand(new BoundLinageCounterRef(...)); OperandText.AsStringVisitor.Visit(BoundComputedOperand) is loud on the stated premise that 'an arithmetic expression in a string position, which no general format admits' is the only thing reaching it - false for Format 10/11 identifiers. The numeric channel works (MOVE LINAGE-COUNTER TO N PIC 99 -> 03). pb429's golden routes every read through MOVE to a numeric item, which is why it never saw this. Sweep: every AsString consumer (DISPLAY, MOVE/STRING/INSPECT alphanumeric senders, relation vs alphanumeric) is a sibling. No kb/Work note owns it (R16 is the index-name twin, landed).

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/ExpressionBinder.cs (LINAGE_COUNTER/LINE_COUNTER/PAGE_COUNTER arms, ~:332); src/Cobol.Net.Compiler/CodeGen/Emit/OperandText.cs#AsStringVisitor.Visit(BoundComputedOperand) ~:535

### Finding — `linage-counter` (crashes; rows `GR-8.4.3.14.4-1`)

**Mechanism.** linage-counter-character-context-crash: the binder wraps the LINAGE-COUNTER register as BoundComputedOperand(BoundLinageCounterRef), and OperandText.AsString's entry intercepts only intrinsic-call and BoundBinary computed operands, so every character-context use of the register falls to AsStringVisitor.Visit(BoundComputedOperand) = EmitText.LoudValue("computed expression in a string context") -- compiled clean, thrown at run time.

**Repro.** FD LPF LINAGE IS 9 LINES. 01 P-REC PIC X(4). WORKING-STORAGE: 01 WX PIC X(5). PROCEDURE: OPEN OUTPUT LPF. WRITE P-REC FROM "AA". DISPLAY LINAGE-COUNTER. (likewise MOVE LINAGE-COUNTER TO WX / STRING LINAGE-COUNTER DELIMITED SIZE INTO WX / IF LINAGE-COUNTER = WX). cobol T3.cob --std 85|2023 --run -> Unhandled NotImplementedCobolFeatureException: computed expression in a string context. Probes: scratchpad adj-d2/out/probe/linage-counter/{g2,g3,T1,T2,T3}.cob.

**Expected from the spec.** §8.4.3.14.4 GR1: LINAGE-COUNTER "references a temporary unsigned integer data item of class and category numeric"; §13.18.34.4 GR7 d) + c)3 put its value at 2 after OPEN OUTPUT and one WRITE without ADVANCING. DISPLAY (§14.9.11.3 SR1 excludes only message-tag, object, pointer), a MOVE to an alphanumeric item, a STRING sending operand and a relation with an alphanumeric operand all accept a numeric integer item, so each shall use the value 2 in the item's unsigned-integer character image (digit count per the documented page-size capacity determination), never trap.

**Observed / reasoning.** Compiles with no diagnostic at 85 and 2023; the numeric paths (MOVE to PIC 9(4) prints 0002, IF LINAGE-COUNTER = 2) work, the four character paths throw at run time. Sibling to sweep, not probed here: FieldOperand wraps LINE-COUNTER/PAGE-COUNTER (host.Rw.CounterExpr) in the same BoundComputedOperand, so DISPLAY LINE-COUNTER likely hits the same arm; R16 (landed) closed the index-name member of this family with a bind-time diagnostic instead of a rendering. Fix shape: one numeric-register arm at AsString's entry (render the NumX through the unsigned-integer text path used for numeric intrinsics), not a per-register special case.

**Code site.** src/Cobol.Net.Compiler/CodeGen/Emit/OperandText.cs#AsString (entry intercepts, ~line 56-83) and #AsStringVisitor.Visit(BoundComputedOperand) (~line 535); src/Cobol.Net.Compiler/Binding/Procedure/ExpressionBinder.cs#FieldOperand (~line 332)
