# PB4396 — one file, one step

**Owner decision (2026-11-01, operator session).** "I continue to fail to understand why we do not do all work operating
on a file in one step. PB4395 edits the same files as steps 8 and 11, then do all three together." Then, asked whether the
planner should make that its rule (notes that share files in ONE group sized by the turns an implementer can hold, a note
filed against a file in flight joining that branch, only true overflow chained and a chain landing as one branch; groups
bigger and possibly longer than an hour), or keep the 4-note cap and land each chain link as it goes clean, the owner chose
**"One step per file"**.

## Why one file's work took several steps

Three rules, each an earlier owner decision, combined into it:

1. **The group cap** (`wave.max_notes_per_group` = 4, kb/Work PB3704, owner 2026-10-25: "so a group lands within the
   hour"). A file with more than 4 open notes became several groups.
2. **Same-file successors** (plan_wave.py item 4, MANDATORY-PRACTICES O2, kb/Work PB3670): a group whose claim meets
   another's on any file is a separate implementer that runs `after:` it, one link per wave (`wave.links_per_chain` = 1,
   kb/Work PB3638).
3. **Nothing is held** (kb/Work PB3381, owner 2026-10-18): each link reviewed CLEAN lands at once, and the next link's
   pull request merges on top.

So each link built, gated, reviewed and landed the same files again, and each fresh implementer re-oriented on them.
The campaign planner did the same with `blocked_by` (a note waiting on another planned note ran after it as a
successor), and so did the operator by hand: PB4395 was filed `blocked_by` the in-flight steps 8 and 11 on the same
files, which would have gated, reviewed and landed them twice.

## The change

1. **One group per file family.** Notes whose claims meet on any file (inflight.collision, unchanged) are ONE group.
   Size it by the turns an implementer holds (the turns fit in `max_notes_per_group_source`, kb/Work PB3718's
   predicted-turns sizing), not by a 4-note count, under the implementer's turn cap with a margin. Retire
   `max_notes_per_group` or make it the turns limit, and update its `_source`.
2. **Join in-flight work.** A planned note whose claim meets an in-flight branch (the dispatch ledger, unlanded
   branches) is planned ONTO that branch: a continuation in its worktree once its current agent returns, never a separate
   branch behind it. A note's `blocked_by` on work that shares its files is planned the same way (the combination answers
   it).
3. **Overflow lands as one branch.** Only work one implementer cannot hold is chained, and the chain continues ON ONE
   BRANCH (each link continues the previous link's worktree). It lands once, when the last link is reviewed CLEAN. A link
   reviewed CLEAN that a later link will carry is IN FLIGHT, not WAITING TO LAND. This replaces PB3381's "nothing is
   held" for same-file chains: the owner chose one step over landing each link early.
4. **The checker and the practice.** `check_practices.py` refuses two groups whose claims meet (the same reader), with
   no `after:` exception; MANDATORY-PRACTICES O2 and rolling-wave.md describe the one-step rule with this decision as its
   reason, and the history of PB3381 and PB3704 goes to the DEVLOG.

**Acceptance.** A planted register with 7 notes on one file plans ONE group (or one chain on one branch when the
predicted turns exceed the cap); a note on a file an in-flight branch holds is planned onto that branch; a planted chain's
first link reviewed CLEAN is IN FLIGHT until the last link is CLEAN. Measure gates, reviews and landings per file family
for a day of waves before and after.

**Order.** This note shares `.claude/skills/workstream/templates/MANDATORY-PRACTICES.md` with the combined branch of
steps 8 and 11 and PB4395 (worktree-wf_01545e8c-f44-1, the Mythos lane). Under this rule it joins that branch, as a
continuation on it if the implementer cannot hold all of it.

## Landed (w20261810e, one branch with PB4395 and steps 8 and 11 of PB4323)

1. **One group per file family, sized by turns.** `plan_partition` absorbs a group whose claim meets a placed group's
   (`collision`, unchanged) into it, a finisher's notes, branches and pred included, and unites the groups of the wave
   one claim meets, while the result fits `clusters.notes_cap`: model_rules.json `wave.turns_per_group` 65 +
   `wave.turns_per_note` 20.5 per note (turns_by_group_size.py's fit) under `wave.turn_budget_fraction` 0.75 of the
   implementer's turn cap, 11 notes at today's cap. `wave.max_notes_per_group` is retired, with every reader
   (`run_fix_clusters`, `campaign_clusters`, the ledger's estimate). `plan_fill` no longer absorbs by primary file:
   the partition's one rule does it.
2. **Join in-flight work.** A group meeting a FINISHED branch is planned onto it (`continuation_pred`, `continues`), and a
   blocker whose work rides on a branch it continues counts as answered; RUNNING work still holds it until it returns.
3. **Overflow lands as one branch.** What the group size cannot hold is `Group.overflow`: its notes wait, naming the
   group whose branch the next wave continues. `continues` and `overflow` reach groups.json and the dispatch ledger,
   and `prune_worktrees.chain_links` reads a WAITING TO LAND branch that a live dispatch continues, or whose dispatch
   left a pending overflow, IN FLIGHT (`chain`), so the chain lands once.
4. **The checker and the practice.** `check_practices.claims_meet` refuses two meeting groups with no `after:`
   exception; MANDATORY-PRACTICES O2, rolling-wave.md, the workstream SKILL.md and DESIGN-orchestrator-loop section 9
   state the rule; PB3381, PB3670 and PB3704's history is in the DEVLOG entry.

**Acceptance, as tests.** test_plan_wave.py 9d: seven notes on one file plan ONE group under the live rules, and at a
3-note size one group of 3 with an overflow of 4 that waits naming group A's branch; PB3528, PB4352, PB3746 and PB3653
read two meeting finishers as one finisher continuing both branches; prune_worktrees' self-test plants a ledger whose
dispatch continues `wpred` and one whose overflow is pending, and reads the CLEAN `wpred` IN FLIGHT both ways while
its carrier lands. The measurement (gates, reviews and landings per file family over a day of waves, before and after)
is the operator's, after the landing.
