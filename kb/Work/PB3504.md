# PB3504 — nested function calls in an EVALUATE operand hang the parser

## Scenario (`--std 2014 --source-format free`, legal source)

```cobol
01 N PIC S9(8).
...
EVALUATE FUNCTION ABS(FUNCTION ABS(FUNCTION ABS(FUNCTION ABS(N)))) WHEN 1 CONTINUE END-EVALUATE
```

**Expected:** compiles (ISO §14.9.13.2 admits arithmetic-expression-1 as a selection subject; ABS is §15.6).
**Observed:** the compile does not finish (killed at 30 s and at 60 s).

## Measured (wall clock, one run each, the same build)

| Shape (depth = nested ABS calls) | Result |
|---|---|
| `EVALUATE f WHEN 1`, depth 2 / 3 / 4 / 5 / 6 | 2.0 s / 5.6 s / **> 60 s** / **> 60 s** / **> 60 s** |
| `EVALUATE N WHEN f` (selection object), depth 4 | **> 30 s** |
| `EVALUATE TRUE WHEN f = 1` (condition object), depth 4 | **> 30 s** |
| `EVALUATE N WHEN f THRU 9` (range), depth 4 | **> 30 s** |
| `EVALUATE ((((N + 1) + 1) + 1) + 1) WHEN 1` (parentheses, no function) | 1.7 s |
| MOVE / COMPUTE / IF `f = 1` / DISPLAY / PERFORM UNTIL `f = 1` / CALL USING `f`, depth 4 | 1.9 s each |
| The same subjects with a syntax error inside (`ABS(N FROM 1)`), depth 3 / 4 | 4.4 s / **> 60 s** |

A stack sample of the depth-6 subject (dotnet-stack) shows the parse thread in
`ParserATNSimulator.AdaptivePredict` from `CobolParserCore.evaluateSubject()`, in `ComputeTargetState` →
`HasSLLConflictTerminatingPrediction` → `ATNConfigSet.Add`, deep in `PredictionContext.MergeArrays` /
`MergeSingletons`. So the time is ANTLR's prediction itself, not the compiler's code (PB3489 was the compiler's own
re-simulation, and is fixed separately).

## Why (as filed, before the measurements under "Landed": the grammar was NOT the cause)

`evaluateSubject` (CobolControlFlow.g4) lists `valueOperand`, `{boolExprAhead()}? booleanExpression` and `condition`;
the WHEN object lists `valueRange`, `valueOperand`, the boolean expression, `condition` and `partialExpression`. All
of them reach a function-identifier, and a bare operand is both a value and a condition, so ONE adaptive prediction
at the subject has to read the WHOLE operand (to the WHEN) before it can choose. Each nested argument list inside
that prediction carries every alternative of `functionArgument` (a boolean expression, an arithmetic expression …)
in each of the outer alternatives, and the merged prediction contexts grow with every level. A statement whose
operand position has ONE alternative (MOVE, COMPUTE, IF's condition) predicts each inner decision locally and stays
flat. Parentheses alone stay flat (1.7 s), so the multiplier is the function-argument alternatives.

## Harm

A compiler hang on a legal program: a build that never finishes and never says why. Four nested function calls in
any EVALUATE operand are enough, and three already cost seconds.

## Direction (as filed; superseded under "Landed": no grammar change)

The fix is grammatical and belongs in `docs/rearchitecture/DESIGN-frontend-grammar.md` (rule 2): bound the
EVALUATE operand decision so it does not have to look through the operand. The alternative order of both rules is
load-bearing (PB842, PB1412, PB2722, PB398 record why), so a reshape must keep every parse they pin. Candidates to
weigh: left-factor the shared operand prefix out of the alternatives (one operand rule followed by the tail that
decides value, boolean or condition, with the classification moved to the binder, as `EvaluateBinder.ClassifyPair`
already does for a bare word), or make `functionArgument`'s alternatives cheaper to predict. Never a timeout.
Then a drift test that counts prediction work at depths 1 to 6 (the ANTLR profiler's `DecisionInfo` SLL/LL lookahead
totals, or the compiling thread's warm allocation per depth as PB3489's `ResidueWalkNestingTests` measures it; a count
of merged configurations cannot see a stack blow-up), never a wall clock (PB1590), plus the sibling sweep: every
statement whose operand position lists overlapping alternatives (`callArgument`, `argument`, SEARCH WHEN, the
INITIALIZE / SET operand lists), measured at depth 1, 3 and 6, legal and illegal.

## Landed — the cause is ANTLR's, and so is the fix

The owner asked (2026-10-21 ~22:20 PDT) whether this was an ANTLR bug or a grammar problem, since a grammar change
made only to dodge a tool defect would be a workaround. Measured, in order:

1. **The prediction is short; its bookkeeping is not.** ANTLR's profiler on the EVALUATE subject's decision: one
   invocation, lookahead 10 tokens at depth 2 and 14 at depth 3, as many ATN transitions, pure SLL, no LL fallback —
   yet 328 ms → 4,019 ms. At the decision's DFA states the configuration sets hold 464–524 configurations and the
   graph of their prediction contexts has 94 → 277 → 361 distinct nodes at depths 1–3, while the stack PATHS that graph
   stands for grow 47 K → 754 K → 12 M. Time followed paths, not nodes.
2. **Not the compiler, not the C# port.** The parser's serialized ATN and the exact token stream run on ANTLR's own
   `ParserInterpreter` (no compiler code): C# 4.13.1 0.56 s → 1.2 s → 6.0 s at depths 1–3; the Java reference runtime
   4.13.2 0.8 s at depth 3, 13.0 s at depth 4 and `OutOfMemoryError` in `PredictionContext.mergeSingletons` at depth 5.
3. **The defect.** Counters in a source build of the runtime: closure calls grew slowly (0.63 M → 1.10 M) while merges
   (0.8 M → 31.6 M) and contexts created (0.30 M → 24.9 M) multiplied, and merge-cache hits did not. Interning the
   contexts after each token changed nothing, which put the merges outside the reach computation:
   `PredictionMode.HasSLLConflictTerminatingPrediction`, in pure SLL mode when configurations carry semantic
   predicates (this grammar's operand rules do: `{boolExprAhead()}?`, `{boolArgAhead()}?`), copies the configuration
   set with the predicates removed and calls `ATNConfigSet.Add(config)` — `Add(config, null)`: every merge of
   configurations that differ only by predicate runs WITHOUT a merge cache and re-merges each shared subgraph once
   per path. Upstream `dev` (February 2026) still has it in both runtimes; issue antlr/antlr4#2737 ("parsing time
   grows exponentially with addition of nested parenthesis", open since 2020) is plausibly the same class.
4. **The fix: one argument.** The copy loop gets a `MergeCache` (Java: `DoubleKeyMap`), as every other merge in the
   simulator has. Alone, on pristine 4.13.2: the EVALUATE repros compile in ~2 s at depths 4, 6 and 10 (as MOVE does),
   the error variants answer in ~0.5 s; Java: depth 4 198 ms, depth 5 160 ms, depth 10 360 ms.

**What landed.** The owner directed (2026-10-21 ~22:40–22:55 PDT) that we fork ANTLR into WiseOwlSoftware, use the fork's
patched build until upstream releases the fix, build the matching 4.13.2 C# runtime (never published to nuget.org),
and submit the fix upstream. So: the fork https://github.com/WiseOwlSoftware/antlr4, branch
`wiseowl/4.13.2-sll-predicate-merge-cache` (tag `4.13.2` + the fix, C# and Java); the package
`Antlr4.Runtime.Standard 4.13.2-wiseowl.1` in the repo-local feed `nuget-feed/` (README there: provenance, rebuild,
exit); `nuget.config` maps that one package to the feed; `Directory.Packages.props` pins it. No grammar change.
Witness: `EvaluateNestedOperandPredictionTests` — the compiling thread's allocation at depths 1–3 after a warm-up
(fixed 169 KB · 48.2 MB · 30.6 MB; pristine 4.13.2 169 KB · 192 MB · 2,335 MB; the bound, third level ≤ 3× the
second, passes at 0.6 and fails at 11), plus six-deep operands in the subject, a WHEN object, a condition object and
a THRU range compiling. Docs: DESIGN-frontend-grammar.md §3.5 item 3a, COBOLNET_DESIGN.md §1.4, DOC_INDEX. The
upstream pull request and the return to an upstream release are tracked in kb/Work PB3507.
