# PB2691 — the bit-group arm of the variable-length pair conversion

## What was found (w1042 C, PB2496, landed in train 1042)
PB2496 made MOVE and the relation condition convert a pair of compatible variable-length groups of DIFFERENT shapes
through their two `GroupAtom` shapes (`CobolVarGroup.Reshape`/`Compare`). A group whose items are USAGE BIT has no
atoms: `VariableLengthCompatibility.GroupAtoms` returns null for it, so `PlaceRenderer.VarGroupInShape` passes the
carrier through unchanged and `CobolVarGroup.CompareInLayout` compares under ONE layout. For two bit groups whose
variable-length components sit at different relative positions, that is the ordinal hand-over PB2496 removed for
character groups (where it was a measured wrong answer: `p\s1.cob` printed `x  a` where the spec gives `xa dd`).

## Status of the evidence
Not probed. The implementer kept the old behaviour deliberately (`p\b1.cob` exercises two SAME-shape bit groups and
passes). The first step is a probe: two compatible bit groups, different component positions (a DYNAMIC LENGTH
bit item before vs after a fixed bit item), MOVE then DISPLAY and compare; derive the expected values from §14.6.9.2
and §8.5.1.12.2 before running it.

## Site
`src/Cobol.Net.Compiler/Binding/Model/VariableLengthCompatibility.cs#GroupAtoms` (line ~186, the null for a bit
group); `src/Cobol.Net.Compiler/CodeGen/Roslyn/PlaceRenderer.cs#VarGroupInShape`;
`src/Cobol.Net.Runtime/Values/CobolVarGroup.cs#CompareInLayout`. Fix shape if it reproduces: bit atoms (bit counts
instead of bytes) in the one atom builder, so bit groups take the same Reshape/Compare path.

## Landed 2026-10-08 (w1045f)

**Re-probed first, on this worktree's build (base 685b44315).** `E:\COBOL-coord\scratch\w1045f\p\b2.cob` (two variable-length
groups after an 8-bit leader, a dynamic-capacity table opposite a fixed one) printed `G2=[x  a]`, `G1=[xzz] C1=2`, `NE` —
the ordinal hand-over PB2496 removed for character groups. Expected (§14.6.9.2, §14.6.9.3, §8.8.4.2.17) and now printed:
`G2=[xa dd]`, `G1=[xpqzz] C1=2`, `EQ`. The sweep found three more arms of the same mechanism:
- `p\b4.cob` (two 1-bit items, then a DYNAMIC LENGTH item, opposite a 2-bit item then one) was REFUSED (COBOLNET1931 /
  COBOLNET2492: "starts at relative byte position 1 and the other group has no dynamic-length item there"): the atom
  builder counted each bit leaf as its own byte, so legal source was rejected. Now `LT`, `A=01 D=[abc] Y=[y ]`, `EQ`.
- `p\b5.cob` (a fixed group with a 4-bit run and a fixed table opposite a 4-bit item and a dynamic table) was refused
  the same way; now moves and compares both ways.
- `p\b6.cob` (a Format 2 CALL AS NESTED passing such a group to a formal of the other shape) CRASHED the compiler:
  `InvalidOperationException: variable-length formal 'G2' has no §8.5.1.12 atoms` (`ProgramEmitter.FormalAtoms`). Now
  the formal sees `IN=[xa dd]`.

**Root cause.** `VariableLengthCompatibility.GroupAtoms` returned null for any group with a USAGE BIT descendant, and
the atom builder (`Atoms`, which `Mismatch` reads directly) laid each bit leaf as `ceil(n/8)` bytes of its own. §8.5.1.6.3
packs same-level bit items into shared bytes and puts whatever follows "at the first bit position of the first available
byte", so a run of bit items is ONE byte-aligned slice — the slice `PhysicalModel` already gives the run in the carrier.

**Fix shape.** The atom builder asks the ONE run law (`BitLayout.RunsOf`): a run that is not byte-granular
(`BitLayout.IsByteGranular`) is ONE fixed atom of `BitLayout.RunCharacters` bytes (the same helper `PhysicalModel` now
uses for the run leader's slice), and a byte-granular run's members keep their per-item atoms. `GroupAtoms` is null only
for a non-group and for a group with a dynamic-capacity table packed into a run that is not byte-granular, which has no
relative byte position: `Mismatch` refuses every pair of it (⚠ DETERMINATION, §8.5.1.12.2 "they occupy the same relative
byte positions", §8.5.1.12.1 rule 1). With every operand shape statable, the one-layout fallback is deleted:
`CobolVarGroup.CompareInLayout` / `Positional`, `CobolContiguousLayout.ComponentOffsets`, `RuntimeApi.VarGroupCompareInLayout`
/ `VarGroupComponentOffsets`, `PlaceRenderer.VarGroupComponentOffsets` and `VarGroupWindow.RunFixedAt`; `VarGroupOperand`
returns a non-null shape and `VarGroupInShape` takes two.

**For the next implementer.**
- `src/Cobol.Net.Compiler/Binding/Model/VariableLengthCompatibility.cs#Atoms` — the ONE §8.5.1.12 atom builder; bit
  members go through `BitLayout.RunsOf` first (a `Sink` accumulates atoms, items and `Unplaced`). Never test
  `HasBitDescendant` to give up on a group again.
- `src/Cobol.Net.Compiler/Binding/Model/BitLayout.cs#RunCharacters` / `#IsByteGranular` — reuse for any byte accounting
  over a bit run; `PhysicalModel.BuildPhysicals` reads `RunCharacters` too.
- `src/Cobol.Net.Compiler/CodeGen/Roslyn/PlaceRenderer.cs#VarGroupOperand` / `#VarGroupInShape` — shapes are non-null now;
  a null `GroupAtoms` means the binder already refused the pair.
- Trap: a dynamic-capacity table of USAGE BIT elements does not compile at all (CS0029 in the generated field); the
  `Unplaced` refusal was chosen for that unreachable shape, and should be revisited when it compiles.

**Goldens.** `tests/conformance/2014/pb2691_vlg_bit_member_shapes` (PB2691BIT + nested PB2691SB); negatives
