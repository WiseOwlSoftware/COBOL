# PB4102 — libcob 3.3-dev: SIGSEGV on MOVE ZERO, or a MOVE of any alphanumeric operand, to a floating-point numeric-edited item (PIC 9.99E+99), so a default-dialect program that declares one crashes before its first statement

Found 2026-10-30 by patcher D (PB3838 tier 6) while testing the floating-numeric-edited patch; re-run and recorded by
recorder B the same day. Evidence, outside git on one machine: WSL `~/gc-notes/PB4102/` (the repro programs `fpecrash.cob`,
`z1.cob` to `z9.cob` and the generated C of `z6.cob`), the original repro
`E:\COBOL-coord\scratch\mythos\gc-file\drafts\floating-numeric-edited\fpecrash.cob`.

## Summary

On GnuCOBOL 3.3-dev r5751 a program that declares `01 F PIC 9.99E+99.` in WORKING-STORAGE and is compiled with the
default dialect ends with SIGSEGV (exit 139) before its first statement: the default dialect initialises storage
(`defaultbyte: init`), which moves ZERO to the item, and that move crashes in libcob. The same crash happens on an
explicit `MOVE ZERO TO F`, `MOVE 0 TO F` or `INITIALIZE F` under `-std=cobol2014`. GnuCOBOL 3.2.0 does not crash on
any of these: it prints "libcob: error: cob_move_display_to_edited: invalid PIC character E" and continues (the
unimplemented edited move, PB3900). The crash is not limited to ZERO: a MOVE of any alphanumeric operand, zero or not
(`MOVE X TO F` with `01 X PIC X VALUE "1"`, `MOVE "123" TO F`), which ISO permits (Table 16), crashes the same way. This
is a regression on the development line, and a distinct defect from PB3900: a MOVE from a numeric operand (`MOVE 1 TO F`,
`MOVE V TO F`, a packed-decimal, binary or numeric-edited operand) does not crash on 3.3-dev. The crash path is the
alphanumeric-source arm of `cob_move`, `indirect_move (cob_move_alphanum_to_display, ...)`, which receives the item's
encoded exponent scale; figurative ZERO reaches it through `cob_move_all`. It needs an exponent of two or more digits:
`PIC 9.99E+9` (scale 2) does not crash, `PIC 9.99E+99` (scale 101) and `PIC 9.99E+999` (scale 1001) do.

## Observed result

printed), stderr:

```

attempt to reference invalid memory address (signal SIGSEGV)

```

3.3-dev, `fpecrash.cob`, `-std=cobol2014` (no storage initialisation): prints `START`, exit 0. With
`-std=cobol2014 -fdefaultbyte=init` it crashes like the default dialect.

3.3-dev, `z1.cob`, `-std=cobol2014`: stdout `START`, then the same SIGSEGV message, exit 139. The same with
`MOVE 0 TO F` (cobc generates `cob_move (&cob_all_zero, &f_1)` for it) and with `INITIALIZE F`. No crash with
`MOVE 1 TO F`, `MOVE 123.45 TO F` or `MOVE V TO F` (`V PIC 9 VALUE 0`): those print "libcob: error:
optimized_move_display_to_edited: invalid PIC character E" and a wrong value, exit 0 (PB3900).

3.3-dev, alphanumeric operands, `-std=cobol2014` (refuter, 2026-10-30): `xc.cob` (`MOVE "123" TO F`) prints `START`,
then the same SIGSEGV message, exit 139; so do `MOVE X TO F` with `01 X PIC X VALUE "1"` and with `01 X PIC X(3) VALUE
"123"`. A numeric operand does not crash: `MOVE P TO F` (`P PIC 9 PACKED-DECIMAL VALUE 1`), `MOVE B TO F` (`B PIC 9 COMP
VALUE 1`), `MOVE N TO F` (`N PIC 9V99 VALUE 0`) and `MOVE E2 TO F` (`E2 PIC 9.99E+99`) each print the
optimized_move_display_to_edited error and `[0.0000` followed by a NUL byte, exit 0. The exponent width decides it:
`MOVE ZERO` to `PIC 9.99E+9` (attribute scale 2) or `PIC 99.9E+9` (scale 1) does not crash, to `PIC 9.99E+999` (scale
1001) it does. `01 F PIC 9.99E+99 VALUE ZERO.` under the default dialect does not crash (no initialising MOVE; it
displays `[0000000]`); the same item inside a group (`01 G. 05 F PIC 9.99E+99.`) crashes. `-std=cobol2002`, `ibm` and
`mf` do not initialise the item and run `fpecrash.cob` to exit 0.

3.2.0, the control: `fpecrash.cob` default dialect, stdout `START`, stderr "libcob: error: cob_move_display_to_edited:
invalid PIC character E", exit 0. `z1.cob` `-std=cobol2014`: stdout `START` and `[0.00000]`, the same stderr line, exit 0.
`xc.cob`: stdout `START` and `[3.00000]`, the same stderr line, exit 0.

## Expected result (per ISO)

All three programs are legal and run to STOP RUN. `fpecrash.cob` prints `START`; `z1.cob` prints `START` and
`[0.00E+00]`; `xc.cob` prints `START` and `[1.23E+02]`.

ISO/IEC 1989:2023, each citation checked with `scripts/spec/cite.py --check`:

- §13.18.40.4 13) b): "To define a floating-point numeric-edited item, characters-string-1 shall consist of two parts,
  separated without any spaces, by the symbol 'E'." "The significand shall be a valid character-string for either a
  numeric item or a numeric-edited item for a fixed-point result." "The exponent shall be '+9', '+99', '+999',
  '+9999', or '+9(n)' where n = 1, 2, 3, or 4." `9.99` is a valid fixed-point numeric-edited significand and `+99` a
  valid exponent.
- §13.18.40.6 (Precedence rules), Table 10, rendered from the printed pages 459-460 (PDF pages 489-490): row 'E' has
  an 'x' under '.' and '9'; row '+' (exponent) has an 'x' under 'E'; row '9' has an 'x' under '.', '9', 'E' and the
  exponent '+'. Every symbol order in `9.99E+99` is permitted.
- §14.6.8.4 2): "Alignment and zero fill or truncation take place as described in the general rules and editing rules
  in 13.18.40, PICTURE clause." (Rule 1, the normalisation, applies only to a non-zero value.)
- §13.18.40.5 8) (Editing rules, "Zero value of a floating-point edited item"): "If the value to be edited into a
  floating-point edited item is zero, then after editing all digit positions of the significand and all digit
  positions of the exponent shall be zero; the sign of the significand, if present, shall be positive; and the sign of
  the exponent shall be positive." Zero edits as `0.00E+00`.
- §14.9.25.3 10): "For all other cases not described in Syntax rules 8 and 9, table 16, Validity of types of MOVE
  statements, specifies the validity of the move." Table 16 marks Alphanumeric to "Numeric, Numeric-edited" Yes, so
  `MOVE "123" TO F` is legal. §14.9.25.4 6) d) 3.: "When the sending operand is described as alphanumeric or national,
  the sending operand is treated as if it were an unsigned integer of category numeric with the following
  characteristics" (c: as many digits as the literal has characters), so `"123"` is the value 123 and, normalised by
  §14.6.8.4 1), edits as `1.23E+02`.

Edition: the floating-point numeric-edited PICTURE was introduced in ISO/IEC 1989:2002 and is in 2014, the edition
`-std=cobol2014` claims (the edition evidence is in PB3900). Whatever the run time does with an unimplemented PICTURE,
a segmentation fault in a legal program is a defect; on the default dialect it hits programs that never reference the
item.

## Fix site (GnuCOBOL 3.3-dev r5751 source, read observationally)

- `cobc/tree.c`, `cb_build_picture`, the `PIC_FLOATING_EDITED` case (lines 3927-3952): the PICTURE's scale encodes
  the exponent range, `scale += digits_exponent` (99 for `+99`). For `9.99E+99` the generated attribute is
  `{COB_TYPE_NUMERIC_EDITED, digits 3, scale 101, COB_FLAG_IS_FP}` (`a_2` in the generated `z6.c.h`; 3.2.0 generates the
  same attribute), and the item's size is 7.
- `libcob/move.c`, `cob_move_all` (line 1553): MOVE ZERO to a numeric-edited item (not `COB_FIELD_IS_NUMERIC`) builds an
  alphanumeric temporary of `dst->size` zeros and calls `cob_move`, whose default arm (the arm every alphanumeric
  source takes) sends it to a numeric-edited destination through `indirect_move (cob_move_alphanum_to_display, ...)`
  (lines 2039-2051).
- `libcob/move.c`, `indirect_move` (line 1486): for a `COB_TYPE_NUMERIC_EDITED` destination the rewritten function
  builds the intermediate numeric-display field from the destination's digits (3) and scale (101), ignoring
  `COB_FLAG_IS_FP`. The destination-attribute intermediate came with the `optimized_move_display_to_edited` rework,
  libcob/ChangeLog 2024-05-30 ("indirect_move: when the destination field is numeric-edited ... the attributes need to
  generated to match destination attributes") and 2024-07-10 ("fixed bug when calculating scale of the intermediate cob
  field", after r5285); bug #1008 (r5290) and the 2024-11/2024-12 entries are later fixes to the same rework.
- `libcob/move.c`, `cob_move_alphanum_to_display` (line 304): with that intermediate, `size = COB_FIELD_SIZE (f2) -
  COB_FIELD_SCALE (f2)` is 3 - 101 = -98, so `while (count-- > size)` skips 105 digits through a 7-byte source and
  walks off the end of the buffer. This is the inferred crash frame (no debugger was available); it accounts for every
  observation: numeric sources take `cob_move_display_to_display` (or the packed and binary converters), which do not
  crash, every alphanumeric source takes `cob_move_alphanum_to_display`, which does, and with a one-digit exponent
  (`+9`, scale 2) `size` is 3 - 2 = 1, so there is no overrun and no crash (refuter's prediction, confirmed by run).

A fix keeps the encoded exponent scale out of `indirect_move`'s intermediate field for a floating-point edited
destination (test `COB_FLAG_IS_FP`), or, until libcob implements the floating-point edited move (PB3900, FR #199), has
the move report "not implemented" without touching memory.

## Draft issue

**Title:** libcob 3.3-dev: SIGSEGV on MOVE ZERO or MOVE of an alphanumeric item to a floating-point numeric-edited item (PIC 9.99E+99); default dialect crashes before the first statement

**Body:**

Environment: GnuCOBOL 3.3-dev r5751 (CI snapshot 3.3-dev.138 of 2026-10-29), x86_64 Linux. GnuCOBOL 3.2.0 does not
crash.

Save as `fpecrash.cob` (fixed format) and run `cobc -x fpecrash.cob && ./fpecrash`:

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. FPECRASH.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 F PIC 9.99E+99.
       PROCEDURE DIVISION.
           DISPLAY "START"
           STOP RUN.
```

Observed (3.3-dev): no compile diagnostic; the program prints nothing and ends with "attempt to reference invalid
memory address (signal SIGSEGV)", exit 139. With `-std=cobol2014` it prints START; with `-std=cobol2014
-fdefaultbyte=init` it crashes again, so the crash is in the storage initialisation. `MOVE ZERO TO F`, `MOVE 0 TO F`
and `INITIALIZE F` crash the same way under `-std=cobol2014`, and so does any alphanumeric sending operand, zero or
not (`MOVE "123" TO F`, or `MOVE X TO F` with `01 X PIC X VALUE "1"`). A numeric sending operand (`MOVE 1 TO F`,
packed-decimal, binary) does not crash, and neither does MOVE ZERO to `PIC 9.99E+9` (one exponent digit). GnuCOBOL
3.2.0 prints "libcob: error: cob_move_display_to_edited: invalid PIC character E" and continues.

Expected: START (and `0.00E+00` after MOVE ZERO, `1.23E+02` after MOVE "123"). PIC 9.99E+99 is a floating-point
numeric-edited item (COBOL 2002 and 2014; ISO/IEC 1989:2023 13.18.40.4 general rule 13 b, 13.18.40.6 Table 10,
14.6.8.4, 13.18.40.5 editing rule 8; an alphanumeric to numeric-edited MOVE is valid per 14.9.25 Table 16). If the
edited move stays unimplemented (feature-requests #199), a run-time message, as 3.2 gives, rather than a crash.

Cause, as far as we can tell from the source (no debugger at hand): cobc encodes the exponent range in the scale (the
attribute is digits 3, scale 101, COB_FLAG_IS_FP). An alphanumeric source goes `cob_move` (default arm) ->
`indirect_move (cob_move_alphanum_to_display, ...)`, and MOVE ZERO reaches the same arm through `cob_move_all`;
`indirect_move` for a numeric-edited destination builds its intermediate
field with the destination's digits and scale. In `cob_move_alphanum_to_display`, `size = COB_FIELD_SIZE (f2) -
COB_FIELD_SCALE (f2)` is then -98 and the `while (count-- > size)` loop runs past the end of the source.
