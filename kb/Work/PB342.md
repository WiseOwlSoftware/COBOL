# PB342 — a duplicate position in the file position indicator

**Rows:** `GR-14.9.30.4-L2.1`, `GR-14.9.30.4-L2.2` — §14.9.30.4 GR21's indexed rules d.1 and d.2. Both found by
the batch-1 refuter; the adjudication had NOTICED the modelling error under d.2 and closed with *no divergence
was demonstrable*. The construct that demonstrates it is one START and one READ.

## The rules

> d.1: If NEXT is specified or implied, the record to be made available is the first existing record in the
> physical file whose key of reference value is greater than or equal to the key value in the file position
> indicator.

> d.2: If PREVIOUS is specified and the previous operation on the file was a START statement, the first existing
> record in the physical file whose key of reference value is less than or equal to the key value in the file
> position indicator.

Both `--check 14.9.30.4` → **OK**.

## The two spec facts that fix what those mean under a duplicate-permitting alternate key

**1. After a START the file position indicator holds a KEY VALUE ONLY.**

> §14.9.41.4 GR17 e) 1.: The file position indicator is set to the value of the key of reference in the first
> logical record whose key satisfies the comparison

`--check 14.9.41.4` → **OK**. §14.9.30.4 GR32 says the same of a random READ, and GR21 rule g) sets it to *the
value of the current key of reference of the record made available*. **The standard never puts a duplicate
POSITION in the file position indicator** — which is exactly why rules e) and f) have to say *the record that was
made available by that prior READ statement* instead of consulting it.

**2. Within one duplicate set the logical order is release order** — GR26 (**PB341**).

So under rule d) *the first existing record whose key-of-reference value >= FPI* can only mean the
FIRST-RELEASED record of the equal-key set, and *first* in d.2's reverse direction the LAST-RELEASED.

## What the compiler does

`IndexedConnector` stores the FPI as the PAIR `(_fpiKey, _fpiArrival)` — the ARRIVAL of the record START happened
to land on (`IndexedConnector.cs:474-476`) — and `ReadSequential`'s forward arm compares that pair
(`PositionCompare`, lines 293-297), so **after a REVERSE START the forward walk resumes at the LAST duplicate and
silently loses every earlier one**. The reverse arm accepts `c < 0 || (_inclusive && c == 0)` over the same pair
(lines 262-268), so **a forward START lands on the FIRST duplicate and READ PREVIOUS hands that same first
duplicate back** — the rest of the duplicate set, which d.2 requires to be traversed in reverse, is unreachable
from a START.

A wrong record delivered to a legal program, in both directions, silently.

## The fix shape

The FPI carries a KEY VALUE, and the position within a duplicate set is derived from the RELEASE ORDER the
duplicate set itself defines — which is what **PB341** builds. Land PB341 first (the per-key release ordinal),
then make `PositionCompare` compare key values and resolve ties by that ordinal in the direction the rule names,
rather than by a stored arrival that records where a previous statement happened to stop.

**Code sites:** `IndexedConnector.cs#ReadSequential`, `#Start`, `#PositionCompare`, `#Ordered`.

## Landed

Landed 2026-09-05 with PB341, in one change set: re-probing showed ONE mechanism (the release-order model of
`IndexedConnector` and the file position indicator built on it), one code site, one gate.

The pre-fix behaviour was worse than this note recorded. Probe `pb342a.cob` (01/PP, 02/PP, 03/PP released in that
order): a forward `START KEY IS NOT LESS` on the alternate key then `READ PREVIOUS` answered 01 and then AT END -
02 and 03 unreachable; a reverse `START KEY IS NOT GREATER` then `READ NEXT` answered 03 and then AT END. In the
four-record shape of the golden the reverse START + forward walk skipped straight from the duplicate set to the
next key value, losing two records silently.

The fix: `_fpiArrival` is gone. The connector now holds `_fpiKey` - THE file position indicator, a KEY VALUE and
nothing else (14.9.41.4 GR17 e) 1., `--check` OK 17)) - and, separately, `_readOrdinal`, the release ordinal under
the key of reference of the record made available by the prior READ, which is what 14.9.30.4 GR21 rules e)/f)
name ("the record that was made available by that prior READ statement", `--check 14.9.30.4` -> OK 21)) instead of
consulting the indicator. `ReadSequential` branches on `_positioner`: under rule d) (previous operation an OPEN or
a START) `PositionCompare` returns the KEY comparison alone, so the walk enters a duplicate set at the end GR26
names for its own direction - first-released forward, last-released backward - whichever direction the START
searched in; under rules e)/f) it resolves ties by `_readOrdinal`. `_inclusive` was deleted: it was a second copy
of `_positioner != 'R'`.

This depended on PB341's per-key ordinal, which is why the two landed together: the tie-break under rules e)/f)
has to be the ordinal for the KEY OF REFERENCE, not a per-record number.

Rows `GR-14.9.30.4-L2.1` and `GR-14.9.30.4-L2.2` re-verdicted DIVERGES -> CONFORMS, pinned by
`tests/conformance/2023/l1_start_dup_set_entry.cob` (L1STD01), whose two legs are exactly the two arms - a
forward START walked backward and a reverse START walked forward - plus the existing
`l1_read_alt_dup_walk.cob`. L1STD01 was run against the pre-fix connector first and is red on it.
