# PB3325 — review finishers are not in the dispatch ledger

## Source

`E:\COBOL-coord\scratch\reports\w1101a-PB3198-report.md` (wave 1101 A), as relayed by the Mythos session of 2026-10-16/17.

## Repro

While a wave's own review finisher (`fix-<letter>-r<n>`) runs on a DONE-with-FINDINGS branch, run any planner
(`plan_wave.py`, the Mythos session's or the loop's): it offers a duplicate finisher for that branch, and the survey reads the
branch DECISION. On 2026-10-16 the planner offered a finisher for PB3198 (wave 1101 A) in the plans of waves 1102, 1103 and
1104 while wave 1101's review finishers were running; the Mythos session recorded a hand hold (ledger entry 1101AR1) as a
stop-gap.

## Harm

A foreseeable duplicate dispatch (two finishers on one branch) unless a session holds it by hand (memory rule
prevent-known-failures). Process only.

## Code site

`.claude/skills/workstream/templates/wf_rolling_wave.js`, `fixFindings` (about lines 166-175): it calls `agent(...)` for the
`fix-<letter>-r<n>` finisher and never calls `record_dispatch`, so `<coord>/inflight-groups.json` holds no entry for it and
`held_by_dispatch` (`plan_wave.py`) does not hold the note.

## Fix shape

When the wave dispatches a review finisher, `record_dispatch` an entry (slug `w<wave><letter>-r<n>`, the group's notes and
file set); drop it at that agent's result. `held_by_dispatch` then holds the note.

That one mechanism also makes the premise of the file-set partition true (second instance, below): `plan()` skips an
in-flight owner whose notes meet the group's (`plan_wave.py` about line 1082, `and not x.notes & set(g.notes)  # ...
(the hold decided those)`), which is right only while the ledger holds every live dispatch of those notes. The self-test
(`scripts/orchestrator/test_plan_wave.py`) covers both shapes: a review finisher on the reviewed branch itself (wave
1101 A) and one in a new live-locked worktree that merged the reviewed branch and has no report yet (wave 1110 A). In
both, no group is planned for the lead. Sweep the other agents that work on a reviewed branch outside the ledger (a
hand-run finisher, a successor started by hand) for the same gap.

## Second instance, 2026-10-17 (wave 1110 A, PB3339; folded in from kb/Work PB3345, retired)

The operator's attended rolling wave (run wf_426911b7-4eb, `review_fix_rounds` 2) stamped `FINDINGS 2` on
`worktree-wf_426911b7-4eb-1` (head 7436bd054) at 13:43 PDT. Its review finisher ran in a NEW isolated worktree,
`wf_426911b7-4eb-4` (`locked claude agent wf_426911b7-4eb-4 (pid 336512)`), merged the reviewed branch (96abc48ce) and
committed its fix (064bcff3f). At 13:58, `plan_wave.py --dry-run --budget-points 5 --no-index-regenerate` still planned a
PB3339 finisher ("notes PB3339 (lead PB3339); model: PB3339 already attempted 2 times without landing"), and
`prune_worktrees.py --brief` read the reviewed branch DECISION. The window closed when the finisher rewrote the report
for its own branch (round 2 CLEAN at 76d216b5c); no duplicate was dispatched.

Four readings let the group through, and each assumes the ledger holds the live work:
1. `plan_wave.answers` released the ledger group `w1110 A` on the implementer's own report, and nothing was recorded for
   the review finisher (this note's code site).
2. `prune_worktrees.owned` counts only a branch IN FLIGHT by its own lifecycle; the reviewed worktree had no lock (its
   implementer had returned) and its finished report covered its tip.
3. `branch_carrier` names only the branch of a FINISHED report, so the live finisher's branch, which had no report yet,
   was no carrier. (PB3311's review R1-1 made a contained branch unowned for a finished carrier, which can be a same-file
   successor of another note.)
4. The file-set partition saw the live worktree in `busy` (RUNNING, its commit subjects naming PB3339) and skipped it
   because its notes meet the group's, on the premise "the hold decided those".
