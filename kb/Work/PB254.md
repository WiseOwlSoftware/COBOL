# PB254

**Rows:** `RV-15.90.4-1`, `RV-15.91.4-1`

IntegerArg's long narrowing answers 'the date is valid' for every out-of-range argument to the two TEST- date validators — a total function swept into a partial function's landing.

ROWS: RV-15.90.4-1 (§15.90.4 r1) and RV-15.91.4-1 (§15.91.4 r1) — the identical renderer arm, the identical hole; the two rows' refuters found it independently and each named the other as the sibling.

MECHANISM, read end to end in the rows' own notes and re-confirmed at HEAD. `CobolIntrinsics.cs:139` is `public static long IntegerArg(Int128 v) => v >= long.MinValue && v <= long.MaxValue ? (long)v : Exceptions.ExceptionState.ArgumentError($"the intrinsic integer argument {v} is outside the range the function can represent (ISO §15.3)")`; `ExceptionState.cs:248` throws `CobolFatalException` when EC-ARGUMENT-FUNCTION checking is ENABLED and otherwise `return 0`. For the two TEST- validators 0 IS a verdict — §15.90.4 r1d / §15.91.4 r1c, 'the date is valid' — so for any argument-1 above long.MaxValue the body is NEVER CALLED and the compiler answers VALID where r1a requires 1 ('the year is not within the range 1601 to 9999' / 'less than 1 601 000 or greater than 9 999 999'). With checking on it instead terminates the run unit fatally on conforming source.

CARRIER-INDEPENDENT, measured not assumed (RV-15.91.4-1's refuter opened all three lanes): `RenderDec` has no `TestDateYyyymmdd`/`TestDayYyyyddd` case and `alwaysDec` does not list them, so under `--arithmetic standard-decimal` control falls to the same native switch arm and, for an SDIDI-carried argument, through `AsInt`'s Dec arm into the same `IntegerArg`. The FLOAT lane repeats the cut at ±9.2e18 via `RealArgs.cs#TryIntegerArg`.

THE ARGUMENT IS CONFORMING, so no §15.3 latitude covers it. §15.90.3 r1 / §15.91.3 r1 require only 'an integer', and every witness is one: a 20-digit integer literal (§8.3.3.3.2 requires 1..31 digits be accepted), a 19..31-digit integer data item (`PicInfo.cs:371` types a field `Digits > 18 ? "Int128" : "long"`), or an integer arithmetic expression — the repo documents that last witness reaching IntegerArg intact at `CobolIntrinsics.cs:129` (the PB22 remarks: `FUNCTION INTEGER-OF-DAY(P * 100 + 62)` with `P PIC 9(18) VALUE 184467440737115466` evaluates 18446744073711546662). §15.3 rule 14 sets EC-ARGUMENT-FUNCTION only when evaluation 'results in an incorrect value … according to the rules specified in the function definition', and §15.90.4/§15.91.4 are TOTAL over the integers — classifying an out-of-window value is the function's whole purpose — so there is nothing to raise on.

WHY NO GOLDEN CAUGHT IT: `tests/conformance/2002/intrinsics_test_validators.cob` was read line by line by both refuters — all seven TEST-DATE cases are 8-digit literals (20240229, 16001231, 20241301, 20240001, 20230229, 20240431, 16000230) and NOT ONE exceeds 99 999 999; of J1-J6 only J5 (1600100) is a leg-a case and it is the LOWER bound. Leg a's UPPER half has zero coverage on either function, and it is exactly where the defect lives.

THE FIX IS AT THE VALIDATORS, NEVER AT THE SHARED NARROWING: widen the two intakes to Int128, or range-test before narrowing so an out-of-window value saturates to its r1a verdict. Closing goldens: one case above 99 999 999 and one above long.MaxValue, on each function, plus a checking-ON leg.

VERIFIED LIVE AT HEAD (read-only): `IntrinsicRenderer.cs:269-270` still reads `DateFn(sig.RuntimeMethod, IntArg(ic, 0))`; `CobolIntrinsics.cs:139-143` unchanged.

## Landed — 2026-09-05

**Re-probed first, on this worktree's own freshly built `cobol.exe`, and the note's mechanism did not hold as
written.** The note says the body "is NEVER CALLED and the compiler answers VALID" on the native lane. It is
called: `IntegerArg`'s checking-off `return 0` substitutes for the ARGUMENT, not for the result, and
`TestDateYyyymmdd(0)` answers 1 — the RIGHT code, because r1a is one arm covering both directions and the
saturated 0 lands in its lower half. The wrong-answer half of this defect is the FLOAT lane, which the note
treated as a footnote: `TestDateYyyymmddReal` read `TryIntegerArg(…) ? body : 0` and that literal `: 0` IS
§15.90.4 r1d, "the date is valid" — `FUNCTION TEST-DATE-YYYYMMDD(FBIG)` with `FBIG COMP-2 = 1.0E19` printed
`00`. The other half is the CHECKING-ON lane, which is a crash, not a wrong answer: `>>TURN
EC-ARGUMENT-FUNCTION CHECKING ON` with `PIC 9(19) VALUE 9999999999999999999` gave *abnormal run-unit
termination: EC-ARGUMENT-FUNCTION (fatal)* on conforming source. Both are fixed; the native lane's coincidence
is gone rather than relied on.

**The fix is at the validators, and the shape of it is a rule about ARGUMENTS, not about arms.** A §15 integer
argument whose function definition places no constraint on its VALUE is TOTAL — the returned-value rule answers
for every integer — so §15.3 rule 14 has no "incorrect value … according to the rules specified in the function
definition" to key on, and PB22's narrowing landing manufactures an exception condition the standard does not
define. `CobolDate.TestDateYyyymmdd` / `TestDayYyyyddd` now take `Int128` and answer r1a before any conversion
(past the guard the value is eight / seven digits, so the `int` narrowing is exact); the renderer arm takes the
WIDE intake; `TestDateYyyymmddReal` / `TestDayYyyydddReal` classify by r1a on the VALUE, so ±∞ and every
magnitude past the window answer 1 with no narrowing at all, and a NaN — the one input that is the value of no
integer — routes to the shared §15.3 raise site and substitutes the documented implementor-defined result **1**,
never the 0 that would report a non-date as a valid date.

**Sibling swept: FIND-STRING argument-3.** §15.37.3 r3 is "argument-3 shall be an integer data item or integer
literal" and nothing more, and §15.37.4 r2/r3 answer for every integer, so it is the same class. Measured before
the fix: `FIND-STRING(hay ndl START AFTER 9999999999999999999)` returned **1**, and **10** under `LAST`, where
r3 requires zero. `CobolIntrinsics.FindString`'s `skip` is now `Int128`. kb/Work R08 had removed the same
narrowing ONE LEVEL DOWN — an `(int)` cast inside that body — and left the `Int128`→`long` one at the intake;
`find_string_skip_domain` stops at `PIC 9(18)`, one order of magnitude below where the defect lived.

**The structure, so the next case is automatic (rule 5).** The intake width is no longer a property of the arm
that happens to render an argument; it is derived from the runtime body's DECLARED carrier — `Int128` means
total, `long` means the argument rules bound it — and
`IntrinsicCarrierAgreementDriftTests.EveryTotalIntegerArgument_TakesTheWideIntake` re-derives that pairing by
reflection over the shipped signatures and fails when an arm and its body disagree. It was proven RED IN BOTH
DIRECTIONS on the shipped renderer before being trusted, and it caught a real accidental widening of the
`DateOfInteger`/`DayOfInteger`/`IntegerOfDate`/`IntegerOfDay` arm during this very change set — the arm where
§15.5.2 genuinely bounds the domain and the §15.3 landing is right.

**Goldens.** `tests/conformance/2002/pb254_total_integer_arguments.cob` pins r1a's UPPER half on every carrier
an integer argument can arrive on (9-digit literal, the EXCLUSIVE boundary falling through to r1b, a 19-digit
literal, `PIC 9(19)` and `PIC 9(31)` items, the §15.3 type-6 arithmetic-expression witness `P*100+62 = 2⁶⁴ +
1 995 046`), the whole program under `>>TURN EC-ARGUMENT-FUNCTION CHECKING
ON` with an ARMED CONTROL leg — a checking-ON golden proves nothing if the directive is inert, so `ARMED`
raises the condition deliberately from `INTEGER-OF-DAY`, whose §15.5.2 argument form IS bounded, and the `USE
AFTER EXCEPTION CONDITION` declarative reports it. `tests/conformance/2023/find_string.cob` gains `EXHAUST3`,
`WIDESKIP` and `WIDELASTSKIP`.

⛔ **The FLOAT carrier is NOT in the strict golden, and that is a train-6 reconciliation, not a gap.**
This note was written before kb/Work PB248 landed. PB248 re-derived §15.3 type 6 as "an integer data item
or an always-integral arithmetic expression" and a floating-point item is neither, so strict now REFUSES it
(COBOLNET1627) — the same reversal that retired `2023/pb21_float_arg_integer_family`. The float twins are
therefore reachable only under `--permissive`, and the wrong-answer half of THIS defect is witnessed where
they live: `FloatIntegerArgumentPermissiveTests.Pb254TotalDateValidators_UnderPermissive_AnswersR1a…`
(1.0E19 → 01 on both functions, with an in-window control owing 00 so a body answering 1 for everything
would fail too), beside PB21’s and PB2’s programs, which moved for exactly the same reason.
