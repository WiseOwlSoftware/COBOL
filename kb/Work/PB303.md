# PB303 — the AS phrase the grammar's own comment says it accepts

MEASURED, not read: run against the worktree's built `cobol.exe` while landing the golden lane.

## The rule

§11.10.2 Format 1, the PROGRAM-ID paragraph (`specs/ISO_COBOL.md:12020`):

```
PROGRAM-ID. program-name-1 [ AS literal-1 ] [ IS { COMMON | {INITIAL|RECURSIVE} } PROGRAM ] .
```

with the transcription's own figure note: *"PROGRAM-ID, AS, COMMON, INITIAL, and RECURSIVE are underlined in the
printed standard (required words)."*

* `cite.py --check 11.10.3 "Literal-1 shall be an alphanumeric literal or a national literal and shall be neither
  a figurative constant nor a zero-length literal"` → **OK §11.10.3 1)**
* `cite.py --check 11.10.4 "Literal-1, if specified, is the name of the program that is externalized to the
  operating environment"` → **OK §11.10.4 1)**
* `cite.py --check 15.65.4 "it is implementor defined what form of the module name is returned"` → **OK
  §15.65.4 4)**

## Observed

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. ASPRB85 AS "ASPRBX".
       PROCEDURE DIVISION.
       MAIN-P.
           DISPLAY "OK".
           STOP RUN.
```

| `--std` | result |
|---|---|
| 2023 | exit 70 — `error COBOLNET0901: 'AS' is a reserved word in COBOL-2023 and cannot be used as a user-defined word (ISO 8.9)` |
| 2014 | same |
| 2002 | same |
| 85 | **compiles and prints OK, exit 0** |

Expected: accepted at 2002/2014/2023; rejected at 85, whose PROGRAM-ID paragraph has no AS phrase. **It is
exactly inverted.**

## Root cause, read

`src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4:115-147`:

```
programIdParagraph     : PROGRAM_ID DOT programName (IS? programIdAttributes PROGRAM?)? DOT ;
programIdAttribute     : commonProgramAttribute | literalAttribute | dataReferenceAttribute ;
literalAttribute       : STRINGLIT | INTEGERLIT ;
dataReferenceAttribute : cobolWord ;
```

There is **no `AS` token in the rule**, although the rule's own comment on line 112 states the format it means to
accept: *"ISO 11.4.2: PROGRAM-ID. program-name [AS literal] [IS {COMMON|INITIAL|RECURSIVE} PROGRAM]."* So `AS`
falls through `dataReferenceAttribute` → `cobolWord`, i.e. it is parsed as a **user-defined word**, and
`VersionConformancePass` then reports `COBOLNET0901` against it (`AS` is reserved from 2002 — `ConstructRegistry`
row `user-word-as-2002`). That is the inversion: at 85, where `AS` *is* user-definable, the accidental `cobolWord`
parse succeeds and the STRINGLIT lands in `literalAttribute`, so `BinderDriver.MakeUnit`'s `name = asName` path is
reachable **only at the edition where the AS clause is illegal**.

## Sibling sweep (CLAUDE.md rule 4) — it is missing from EVERY id paragraph the standard gives one

| paragraph | spec | grammar |
|---|---|---|
| PROGRAM-ID (Formats 1 and 2) | §11.10.2 | `CobolParserCore.g4:116` — no AS |
| FUNCTION-ID (Formats 1 and 2) | §11.5 (`ISO_COBOL.md:11463`, `:11468`) | `CobolParserCore.g4:105` — `FUNCTION_ID DOT programName (IS? PROTOTYPE)? DOT`, no AS |
| CLASS-ID | `ISO_COBOL.md:11127`, `:11367` | `Core/CobolOO.g4:42` — no AS |
| INTERFACE-ID | `ISO_COBOL.md:11166`, `:11502` | `Core/CobolOO.g4:76` — no AS |
| REPOSITORY paragraph | — | `CobolParserCore.g4:360-361` carries the rationale *"The `AS external-name` phrase is deferred (avoids reserving AS as a keyword)"* |

That REPOSITORY rationale is **stale**: `AS` is already a lexed token and is already used by CALL Format 2
(`CobolParserCore.g4:1060`, `callAsPhrase : AS cobolWord`). The token exists; only the id paragraphs never got it,
and the note explaining why is no longer true.

## Why it was never seen

`grep -rniE '^ *(PROGRAM-ID|FUNCTION-ID|CLASS-ID|INTERFACE-ID)\..* AS +"' tests/ --include=*.cob` returns
**nothing**. No program in the tree carries an id-paragraph AS clause, which is why `RV-15.65.4-4` is unmeasured.

## What this does to RV-15.65.4-4, and the OWNER question underneath it

`RV-15.65.4-4` stays a **GAP**, but for a different and worse reason than the golden lane's writer proposed. The
writer framed it as a §4.2.5 documentation mismatch — `MODULE-NAME` reporting the AS literal where
`docs/CONFORMANCE.md` §7 item 135 documents the PROGRAM-ID name. That is not what happens: **the compiler cannot
compile an AS-bearing program at 2002+, so no `r4` form is returned at all** and the documented determination is
not contradicted by any reachable behaviour. Rejecting legal source is the defect to register (CLAUDE.md rule 3);
the `r4` FORM question only becomes answerable once the AS clause parses.

The repro program is held in the golden lane's scratchpad at
`out/exception-module/repro/l1_module_name_as_clause.cob` with a `.out` carrying the DOCUMENTED-determination
expectation (`CUR=[L1MNAS01]`). It is deliberately **not** in `tests/conformance/` and has no manifest entry,
because its expectation is unsettled.

**Two questions the fix has to answer, and only the second is an agent's:**

1. **Owner:** once `PROGRAM-ID. X AS "Y"` parses, does `FUNCTION MODULE-NAME` report `X` (as
   `docs/CONFORMANCE.md` §7 item 135 documents today) or `Y`? §15.65.4 r4 permits either; A.1 item 135 makes the
   choice required and required-to-be-documented, so whichever is chosen, one of the two artifacts changes.
2. **Structural, and it is the same root:** `BinderDriver.MakeUnit` overwrites the unit name with the AS literal —
   `name = asName;   // PROGRAM-ID name AS "literal" — the externalized name (ISO 11.10.4 GR1)` — so ONE field
   serves both `program-name-1` and the externalized literal. §11.10.4 GR1 keeps them distinct: *"Program-name-1
   names the program declared by this program definition. Literal-1, if specified, is the name of the program
   that is externalized to the operating environment."* `Node.Name` is also what `CALL`/`CANCEL` match on, so
   collapsing them means `CALL "L1MNAS01"` would not find `PROGRAM-ID. L1MNAS01 AS "L1MNASX"`. The fix that makes
   the next case automatic is a **separate externalized-name field** on the unit, not a second overwrite.

Also unenforced on this path: §11.10.3 SR2, *"Literal-1 shall not be specified in a program that is contained
within another program"* — it has no visible check, and it cannot acquire one until the phrase parses.

## `inventory_rows` corrected 2026-09-03

This note claimed **`RV-15.65.4-4`** until the round-2 golden writer `singles` drew that row and found the claim
misplaced. RV-15.65.4-4 is a MODULE-NAME **returned-value** rule that merely PERMITS the AS form among four
(*"The implementor may return the name as specified in the program-id, function-id, or method-id paragraph. They
may also return the name as specified in the AS clause …"*) — it is satisfied whichever name is returned, and it
closed CONFORMS on `conformance:2023/pb36_module_name_invoke_activation` in the golden lane's round-2 batch. What
this defect actually defects is the rows where the AS phrase is REQUIRED TO PARSE: the PROGRAM-ID **general
format** (`FMT-11.10.2`), the syntax rule about literal-1 that cannot be enforced while the phrase has no
surface (`SR-11.10.3-1`), and the general rule that gives literal-1 its meaning (`GR-11.10.4-1`) — the three the
note's own `cite.py --check` lines already pin. The §11.5 FUNCTION-ID / CLASS-ID / INTERFACE-ID / REPOSITORY
siblings this note's sweep table lists join the claim when their rows are verdicted; claiming unverdicted rows
now would be over-claiming, and the owner question above is unchanged either way.
