# PB3875 — libcob-aborts-on-unhandled-invalid-key: Run unit terminated on non-fatal I-O status 1x/2x when the file has no FILE STATUS clause (ISO requires continuing)

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S1) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\libcob-aborts-on-unhandled-invalid-key.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\libcob-aborts-on-unhandled-invalid-key\`.

## Summary

When an input-output statement ends with an invalid key condition (I-O status 21, 22, 23) or an at end condition
(status 10), the statement has no INVALID KEY / AT END phrase, no USE declarative applies and the file has no FILE
STATUS clause, a program compiled by cobc 3.2 prints `libcob: error: <text> (status = NN)` and terminates the run unit
with exit code 1. ISO requires control to pass to the end of the statement: these statuses are non-fatal, and the
implementor's option to terminate applies only to fatal statuses (3x, 4x, 7x, implementor-fatal 9x). With a FILE STATUS
clause the same program continues (status 22 displayed, exit 0), so the termination is keyed to the presence of the
FILE STATUS clause, which the standard does not make a condition. The nights met it as status 21 on a sequential-access
WRITE (fz01437) and status 23 on START (fz02836); the same handler also ends the run on status 22 (duplicate key) and on
status 10 (READ at end), shown below.

## Minimal test case

Free reference format (`-fformat=free`), `records/libcob-aborts-on-unhandled-invalid-key.cob`:

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. IKEY.
ENVIRONMENT DIVISION.
INPUT-OUTPUT SECTION.
FILE-CONTROL.
    SELECT F ASSIGN TO "ikey.dat" ORGANIZATION INDEXED
        ACCESS RANDOM RECORD KEY F-KEY.
DATA DIVISION.
FILE SECTION.
FD F.
01 F-REC.
   05 F-KEY PIC X.
PROCEDURE DIVISION.
    OPEN OUTPUT F
    MOVE "A" TO F-KEY
    WRITE F-REC
    WRITE F-REC
    DISPLAY "AFTER WRITE"
    CLOSE F
    STOP RUN.
```

At-end variant, free format, `records/libcob-aborts-on-unhandled-invalid-key--at-end.cob`: a sequential file `F`
(`01 F-REC PIC X`) is opened OUTPUT and closed (empty), opened INPUT, `READ F` (no AT END), `DISPLAY "AFTER READ"`,
`CLOSE F`, `STOP RUN`.

## Environment

- `cobc (GnuCOBOL) 3.2.0`, Ubuntu package `gnucobol3 3.2-4build1`, WSL2 Ubuntu on Windows 11.
- `rm -f ikey.dat; cobc -std=cobol2014 -fformat=free -x -o ikey ikey.cob && ./ikey`
- Control: the same program with `FILE STATUS FS` added to the SELECT and `01 FS PIC XX` in WORKING-STORAGE
  (`ikeyfs.cob`), run the same way.
- `rm -f atend.dat; cobc -std=cobol2014 -fformat=free -x -o atend atend.cob && ./atend`
- Witnesses: n3-fz01437, n3-fz02836 and the night-3 probe programs, same command.

## Observed result

```
libcob: error: record key already exists (status = 22) for file F ('ikey_dat' => ikey.dat)
libcob: warning: implicit CLOSE of F ('ikey.dat')
```
exit code 1; "AFTER WRITE" is not displayed. Control (`ikeyfs`): `AFTER WRITE 22`, exit 0.

At-end variant: `libcob: error: end of file (status = 10) for file F ('atend_dat' => atend.dat)`, the implicit CLOSE
warning, exit 1; "AFTER READ" is not displayed.

Witnesses: n3-fz01437 `libcob: error: key order not ascending (status = 21) ...`, exit 1; n3-fz02836 `FIRST OK`,
`LAST OK`, then `libcob: error: record key does not exist (status = 23) ...`, exit 1. The night-3 probe with a FILE
STATUS clause (probe-n3-B3-p2) runs to the end: `W 00`, `W 21`, `W 21`, `S 23`, exit 0.

## Expected result (per ISO)

ISO/IEC 1989:2023, all checked with `scripts/spec/cite.py --check`:

- §9.1.14 4): "If the INVALID KEY phrase is not specified in the input-output statement and there are no applicable
  exception processing statements, control is transferred to the end of the input-output statement."
- §14.9.30.4 GR 24) d) (READ): "If the AT END phrase is not specified in the input-output statement, any applicable at
  end exception processing statements are executed. If there are no applicable at end exception processing
  statements, control is transferred to the end of the READ statement."
- §9.1.12: the applicable exception processing statements are PERFORM ... WHEN phrases and USE declaratives; the FILE
  STATUS clause is not among them, and neither is anything else that its absence would change.
- §9.1.13.1: "Certain classes of I-O status values indicate fatal exception conditions. These are: any that begin with
  the digit 3, 4, or 7, and any that begin with the digit 9 that the implementor defines as fatal." Only for those
  does the implementor choose to "either continue or terminate the execution of the run unit".
- §14.6.13.1.6, the exception table: "EC-I-O-INVALID-KEY | NF | I-O status "2x"" and "EC-I-O-AT-END | NF | I-O status
  "1x"" (NF: nonfatal).

Expected output of the minimal program: `AFTER WRITE`, exit 0 (the second WRITE leaves status 22 and the file
unchanged). At-end variant: `AFTER READ`, exit 0.

Edition: the rules are in the 2023 text; for 2014, the edition `-std=cobol2014` claims, Annex E of the 2023 standard
lists the only change to this processing between 2014 and 2023 as the execution of mode declaratives (§E.2 19) a):
"INVALID KEY processing. If an INVALID KEY phrase is not specified and an invalid key condition occurs, any declarative
that specified INPUT, OUTPUT, I-O, or EXTEND would not have been executed. It will now be executed."), which does not
apply to a program with no declaratives. The continuation to the end of the statement is therefore the 2014 rule as
well (the project's VERSION_CHANGE_REFERENCE row 25 reaches the same determination). Not 2023-only. The refuter
confirmed it from the 2009 committee draft (CD 1.2) under that text's own numbers, which differ from the 2023 ones
cited here: its 9.1.13 rule 4 and READ general rule 21 d) continue at the end of the statement, and its 9.1.12 names
only 3x, 4x and implementor-defined 9x as fatal.

Edition as recorded by the adjudicator: 2014. `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Class

Wrong output: the run unit is terminated (exit 1, remaining output lost) where the standard continues.

## Our compiler (WiseOwl)

`cobol.exe ikey.cob --std 2014 --source-format free -o ikey.dll`, `dotnet ikey.dll`: `AFTER WRITE`, exit 0. At-end
variant: `AFTER READ`, exit 0. Night 3 probe of fz01437: `W 00/21/21`, START 23, exit 0.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/codegen.c`, function `output_error_handler` (lines 11039-11100), which emits the "Default Error Handler"
  (`cb_standard_error_handler`, created in `cobc/tree.c` line 2030): after any mode declaratives, it emits
  `cob_fatal_error (COB_FERROR_FILE)` whenever the file's `flag_select_features` lacks `COB_SELECT_FILE_STATUS`
  (lines 11091-11092). It does not look at the status class, so non-fatal 1x and 2x statuses end the run.
- It is reached from `output_ferror_stmt` (codegen.c lines 8290-8319) through `output_file_error` (lines 7804-7840)
  whenever `cob_exception_code` is set and the statement's own phrase did not handle it.
- `libcob/common.c`, function `cob_fatal_error`, case `COB_FERROR_FILE` (from line 9015), maps the status to the
  message ("key order not ascending", "record key already exists", "record key does not exist", "end of file") and
  stops the run.
A fix limits the emitted `cob_fatal_error (COB_FERROR_FILE)` to fatal statuses (first digit 3, 4, 7, or a 9x the
implementor declares fatal), or makes it a dialect option off for the ISO dialects.

## Draft issue

**Title:** Run unit terminated on non-fatal I-O status 1x/2x when the file has no FILE STATUS clause (ISO requires continuing)

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu `gnucobol3 3.2-4build1`), Linux x86_64.

Steps: save as `ikey.cob`, `rm -f ikey.dat`, `cobc -std=cobol2014 -fformat=free -x -o ikey ikey.cob && ./ikey`.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. IKEY.
ENVIRONMENT DIVISION.
INPUT-OUTPUT SECTION.
FILE-CONTROL.
    SELECT F ASSIGN TO "ikey.dat" ORGANIZATION INDEXED
        ACCESS RANDOM RECORD KEY F-KEY.
DATA DIVISION.
FILE SECTION.
FD F.
01 F-REC.
   05 F-KEY PIC X.
PROCEDURE DIVISION.
    OPEN OUTPUT F
    MOVE "A" TO F-KEY
    WRITE F-REC
    WRITE F-REC
    DISPLAY "AFTER WRITE"
    CLOSE F
    STOP RUN.
```

Observed: `libcob: error: record key already exists (status = 22) for file F ('ikey_dat' => ikey.dat)`, then the
implicit CLOSE warning; exit 1; `AFTER WRITE` is never displayed. Adding `FILE STATUS FS` to the SELECT makes the
program continue (status 22, exit 0). A READ at end (status 10) with no AT END phrase behaves the same way.

Expected: `AFTER WRITE`, exit 0. ISO/IEC 1989:2023 9.1.14 rule 4: "If the INVALID KEY phrase is not specified in the
input-output statement and there are no applicable exception processing statements, control is transferred to the end
of the input-output statement." For READ, 14.9.30.4 general rule 24d says the same for AT END. Status 1x and 2x are
nonfatal (EC-I-O-AT-END and EC-I-O-INVALID-KEY are NF in the 14.6.13.1.6 table); 9.1.13.1 lets the implementor
terminate the run unit only for fatal statuses (3x, 4x, 7x, implementor-fatal 9x). The FILE STATUS clause is not one of
the "applicable exception processing statements" of 9.1.12, so its absence should not change the control flow. The
2014 standard has the same rules under other numbers (the 2023 Annex E lists no change to them): in the committee
draft toward 2014, the continuation is rule 4 of its 9.1.13 and READ general rule 21 d), and its 9.1.12 names only
3x, 4x and implementor-defined 9x statuses as fatal.

Where: `cobc/codegen.c` `output_error_handler` emits `cob_fatal_error (COB_FERROR_FILE)` for every file without
`COB_SELECT_FILE_STATUS`, regardless of the status class; a fix could restrict it to fatal statuses, at least under the
ISO dialects.
