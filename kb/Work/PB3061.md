# PB3061 — the audit phase does not stop at its first RED, and a re-run self-test does not say why

**Measured 2026-10-11 14:06–15:03 PDT, wave 1062 (six implementers of the PB3015 campaign, Mythos session), owner:
"wave items seem to take unnecessarily long".** Per agent: 46–50 min wall, 157–209 turns, 105–146 shell calls; about
half the wall time was model latency (median 7 s per turn) and half tool time. Of the tool time the gate's SELF-TESTS
audit was the largest single item: 5–7 min in every first gate (365 s, 307 s, 535 s), bounded by its slowest
self-test — `landing_check.py --self-test` 210–362 s, `prune_worktrees.py` 135–219 s, `train_apply.py`,
`landing_oracle.py`, the `test_orchestrate_*.ps1` 100–190 s each — while the build took 30–50 s and leg 1 about
2.5 min. Agents A (PB2987+PB3025) and B (PB3022) each had `CITATIONS: RED` at 19–23 s and received the verdict 5–7 min
later, after the self-tests finished. The host was at 96 % CPU (17 dotnet, 21 pwsh, 18 python, 3 testhost processes);
`gate_slot.py --self-test` stretched from 89 s to 218 s between the first and the last agent's first gate.

## Defects (scripts/run_gate_legs.py, scripts/self_tests.py)

1. **No stop at the first RED.** `Host.audits()` runs the eight AUDITS concurrently and joins EVERY future
   (`as_completed` to the end) before it returns the reds, so the implementer's "fail fast on the audits" (kb/Work
   PB2523) is fail-fast only relative to the build and the legs: a red CITATIONS audit (23 s) still waits for the
   SELF-TESTS audit (5–9 min). The lander's gate must go on (its one run shows every red of the train); the
   implementer's must stop at the first red and stop the audits still running, including the self-test runner's
   child processes (a killed parent would leave them running and holding budget places until they finish).
2. **A re-run says nothing about why.** `Runner.run` reports a self-test REUSED with the PASS it reused, but a self-test
   that RUNS prints only `GREEN in Ns`: nothing says whether no PASS was recorded at all (first run on this platform /
   Python), or which of its recorded inputs changed (`Deps.changed` computes the list and `PassStore.find` throws it
   away). Without it nobody can shrink a slow self-test's inputs or see that a branch touching one shared file re-runs
   fifty of them. The wait for a budget place is likewise unreported, so the machine-wide budget (`BUDGET_CAP` =
   `os.cpu_count()` places, kb/Work PB2897) cannot be judged against the gate slot's cap of 3 from a gate log.
3. **The slow self-tests themselves** (landing_check 6 min, the orchestrate PowerShell tests 2–3 min each) are what
   the phase costs once (1) and (2) hold; what they read and where their seconds go is the measurement item (2)
   produces. This item is decided from that measurement, never before it (owner: no unnecessary re-runs).

## Fix, in order

- (1) `audits(stop_on_red=True)` for the implementer: on the first non-zero exit, terminate every audit still running
  as a PROCESS TREE (Windows `taskkill /T`, POSIX process group) and return; the lander passes `stop_on_red=False`.
  The self-tests already completed have recorded their PASS, so the stopped run loses nothing a re-gate re-runs.
  Self-test arm: a planted red audit returns before a planted slow one finishes, and the slow one's process is gone.
- (2) The console line of a self-test that ran says WHY it ran — `first run (no PASS recorded for this platform and
  Python)` or `re-run: N inputs changed — a, b, c (+k)` — and how long it waited for a place; the verdict line carries
  the total wait and the budget's width. Self-test arms for both.
- (3) After (2) has reported one fleet gate: shrink or restructure the self-tests whose inputs or seconds the data
  names; measured, in its own change.

**Timing (owner 2026-10-11 15:05: "make the changes in order at the appropriate time to not lose any work or
unnecessarily rerun any"):** branch from wave 1062 group B's head once it returns DONE — PB3022 is already rewriting
both scripts, and a change to the runner re-runs every self-test once (`self_test_inputs.py`: the RUNNER is a STATIC
input of every self-test), which B's landing already causes, so landing (1) and (2) in B's train costs no extra
re-run. (3) follows the first measured fleet gate, after PB3024 (group C, `landing_check.py`) has landed.

## Landing (2026-10-11, items 1 and 2; item 3 open — hence `half`)

Branch `gate-failfast-PB3061`, cut from wave 1062 group B's head (PB3022, `4c87131c3`, SPLIT at its turn cap with a
green gate) so it lands as that branch's successor: B already rewrites both scripts, and its runner change re-runs
every self-test once anyway, so this change adds no re-run of its own.
- `scripts/run_gate_legs.py`: `Host.audits()` runs the audits `audit_commands()` names; the first non-zero exit calls
  `_Live.stop_all()`, which stops every audit still running as a process tree (`_stop_tree`: `taskkill /T /F`, or the
  POSIX process group `start_new_session` gave it) and marks it so its exit is reported `--- audit X: STOPPED after
  Ns ---`, never RED; a process that starts after the stop is stopped in `_Live.add`. Self-test arm: a planted slow
  audit with a grandchild and a planted red one — the red is the only reason, the slow one is STOPPED and its
  grandchild is gone (`detached.pid_alive`).
- `scripts/self_tests.py`: `PassStore.lookup()` returns the reusable PASS or WHY there is none (`first run: no PASS
  recorded for <platform>, Python <v>` · `re-run: N input(s) changed since the newest PASS — a, b, c (+k more)`);
  `Runner.run_one` measures the wait for a budget place apart from the run; the console line carries both and the
  verdict line the budget's width and total wait. Fleet arms: the re-run after an edited import names that import;
  a fresh store says `first run`.
- `docs/rearchitecture/DESIGN-test-build-ci.md` sections 3.14.3 (step 3) and 3.14.10 carry both rules.
- Item 3 waits for the first fleet gate whose log carries the why-lines and the wait, and for PB3024 (group C,
  `landing_check.py`) to land.
