# PB3314 — a residual Publish-exhaustion race in the lock-file host (not yet root-caused)

> ⚙ **flags:** wrong-answer · silent

**Found by** the w1095i (PB1099) landing finisher while it measured the PB3313 fix. The finisher's scratch harness has the
shape of `RegionLocksDriftTests.TwoWaitingHoldsBothGetTheByteInTurn`: two `SidecarRegionLocks` endpoints over one file, a
barrier, and waiting exclusive holds of `HostRegionLocks.StoreMutexByte`. For the thread whose hold answers non-Ok, it records
every first-chance exception (`E:\tmp\fin-w1095i\DiagRegionRaceTests.cs`, `rundiag.sh`, `tally.sh`, run under WSL against
origin/main `2ece4453f` with the PB3313 `FileSupport.cs` overlaid). With the fix in place, the harness ran 24,000 + 48,000 +
48,000 + 128,000 rounds with 0-24 CPU burners. One hold in those 248,000 rounds still answered `Unavailable`, in run `c`
(8 processes x 6,000 rounds, 24 burners). Its exception trail had no `EEXIST`, so it is not PB3313's mechanism:
- one `FileNotFoundException at File.GetUnixFileMode` (no lock directory yet);
- the sharing refusals of its own probe and of the other endpoint's live `r4000000000000100-X-…` file, then its own CLOSE's
  `rmdir` refused "Directory not empty" (the conflict, and the backoff after it);
- then EIGHT `FileNotFoundException`s, one per `Publish` attempt, each "Could not find file '…/.wolk-…/pending-<guid>'"
  thrown from `SafeFileHandle.Open`, with no further `GetUnixFileMode` miss between them.

So `Publish` (`src/WiseOwl.Cobol.Runtime/IO/Sharing/SidecarLockFiles.cs:96-120`) exhausted `PublishAttempts` (8) and returned null,
and `SidecarRegionLocks.Hold` (`SidecarRegionLocks.cs:96`) answered `Unavailable`.

**Open questions.** Run `c`'s first-chance stacks were cut at the throwing frame, and runs `d` and `e` (176,000 rounds, with
full stacks and a `dirNow` flag) did not recur it. So it is unmeasured which open threw: `HostFile.OpenLockHolder`'s
`CreateNew` (`FileSupport.cs:378`; an `ENOENT` there means the directory vanished after `CreateLockDirectory` found it), or
`HostFile.ProbeLockFile` of the just-created pending file (`FileSupport.cs`, `FileMode.Open`, so the pending file itself
vanished). It is also unmeasured what removes the directory or the file eight times in a row while the other endpoint holds
nothing. The next step is the same harness with `dirNow` and full stacks, run long enough to recur it (about 1 in 250,000
rounds) on an otherwise idle machine. The burners must not run beside other branches' Linux gates. Then fix the mechanism at
its root rather than raising `PublishAttempts`.

**Harm.** Same shape as PB3313, at about 1/150 of the rate measured before it (1 in 248,000 rounds against 14 in 24,000): `KeyedConnector.HoldStoreMutex` runs the
statement unprotected, and the gate's 25-round witness fails about once in 10,000 runs.

## Root cause (measured, w1115d)

The note's harness, with `Publish` instrumented and a first-chance handler that lists the lock directory, recurred it
twice in about 7,000,000 rounds (16 processes x 100,000 rounds beside 24 niced CPU burners, WSL, 32 cores). The eight
`FileNotFoundException`s are `HostFile.OpenLockHolder`'s `CreateNew` (frames `Interop.ThrowExceptionForIoErrno <
SafeFileHandle.Open < HostFile.OpenLockHolder < SidecarLockFiles.Publish`), not `ProbeLockFile`'s (its `Gone` arm logged
nothing in 3,200,000 rounds), and at each one the lock directory EXISTED and listed EMPTY. The sequence: both endpoints
published, saw each other's live file and closed; the sibling's `rmdir` ran first (the other endpoint's `Directory.Delete`
answered `DirectoryNotFoundException`); the surviving endpoint backed off and came back to publish.

A directory in the middle of its `rmdir` is not yet gone. `vfs_rmdir` marks the inode dead and unhashes the name only
afterwards; while the remover is preempted between the two steps the name still answers `stat`, `GetUnixFileMode` and a
listing (.NET reads the dead directory's `ENOENT` as the end of the directory, so it lists empty), while every creation
inside it answers `ENOENT`. A micro-experiment (`E:\COBOL-coord\scratch\w1115d\t1\P.cs`: one thread makes and removes a
directory, one stats it and creates inside it; 8 processes beside 24 burners, 20 s each) measured the window directly:
2,400 to 8,200 episodes per process in which `stat` succeeded while creation failed, up to 17 ms long and 240
consecutive refusals. `Publish`'s eight attempts were separated by `Thread.Yield()`, microseconds, so all eight fell
inside one window and it returned null: `SidecarRegionLocks.Hold` answered `Unavailable` and the store mutex went
untaken. The note's open guess (a tester reaping the pending file) is refuted: `SidecarRegionLocks.Look` lists only
`r<offset>-*` and never touches a pending file.

## Fix

`SidecarLockFiles.Publish` paces its retries by TIME (`RetryPauseCeiling`): the first retry is immediate, every later one
sleeps a jittered span up to twice the longest before it, to 128 ms, over 12 attempts (about 0.6 s at the ceiling, far
past the measured window, spent only when the race does not end). The old count of immediate tries was the defect: a
lost race that repeats has not finished. Sibling arm: `HostFile.CreateLockDirectory` read "a name that stats" as "a
directory exists"; with pacing, a regular FILE at the lock directory name would have retried through the whole schedule,
so its probe now reads `FileAttributes.Directory` and a file falls through to the creation, whose `EEXIST` stands
(`IsClosingSiblingRace`) and is answered at once as the host refusing the lock directory.

## Landing

- `src/WiseOwl.Cobol.Runtime/IO/Sharing/SidecarLockFiles.cs#Publish` owns the retry rule; `RetryPauseCeiling(int retry)` is the
  schedule (asked directly by a test; reuse it for any other bounded host-race retry). The trap that cost the turns: the
  first-chance trail names the throw site of a CAUGHT exception, so `CreateNew` and `ProbeLockFile` look alike until the
  frames are printed, and a dead directory lists empty.
- `src/WiseOwl.Cobol.Runtime/IO/FileSupport.cs#HostFile.CreateLockDirectory` probes with `File.GetAttributes` (directory or
  not), not `GetUnixFileMode`.
- Tests (`RegionLocksDriftTests`): `ARepeatedLostPublicationRaceIsPacedByTime_NotRetriedAtOnce` (the schedule; red with the
  old immediate tries), `EveryPublicationSucceeds_BesideASiblingThatClosesAndReopensTheLockDirectory_OnAnOversubscribedHost`
  and `EveryPublicationSucceeds_BesideATesterThatReapsPendingFilesWithoutPause` (the contract under the load that opens the
  window and under the reaping tester, repetition witnesses), `AFileAtTheLockDirectoryName_IsUnavailableAtOnce_NotARetriedRace`
  (the host refusal).
