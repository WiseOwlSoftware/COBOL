# PB171

ConditionBinder binds the sign-condition operand with `host.Expr.BindOperandExpr(operands[0])`; the walk
matches `Core.LiteralContext` / `DataReferenceContext` / `ArithmeticExpressionContext` but the grammar's
`valueOperand : arithmeticExpression | nonNumericLiteral` (Core/CobolExpressions.g4) delivers a BARE
`NonNumericLiteralContext` — no arm matches, the queue drains, and the documented fallback returns
`BoundNumLiteral("0")`. `IF "ABC" IS POSITIVE` / `IF SPACE IS NEGATIVE` therefore compile clean and evaluate
`0 > 0` — the silent-degradation shape the fallback's own comment warns about, on source the §8.8.1.1 screen
exists to reject. The comment credits `ArithmeticSendingOperandDriftTests` with pinning the walk's coverage,
but that test only compares the four arithmetic operand rule bodies to each other and never looks at
`comparisonOperand`/`valueOperand`.

WHAT WOULD CLOSE IT: a NonNumericLiteralContext arm in the walk routing through the same NumLiteral screens
(0844 for a non-ZERO figurative / string / hex / national / boolean; ZERO → 0), a negative fixture
`IF "ABC" IS POSITIVE`, and the drift test extended to every rule the walk serves.

*(Found by the PB155 pre-landing review fleet, 2026-08-29. Full claims in the session scratchpad
`pb155-fleet-confirmed.json`.)*

## Re-verification and correction (2026-08-31, cluster-B implementation wave, tree `9a89fbd1`)

⛔ **THIS NOTE CARRIED NO `spec_refs` AT ALL, AND THE CODE COMMENT IT RELIES ON CITED THE WRONG CLAUSE.**
`ExpressionBinder`'s walk justified its breadth-first shape with "a sign condition's operand is the WHOLE
expression, ISO §8.8.4.3". §8.8.4.3 is the **SIMPLE BOOLEAN CONDITION** ("Boolean-expression-1 shall reference
only boolean items of length 1") — a real clause answering a different question, sitting on the exact line this
defect lived on. The sign condition is §8.8.4.7, whose SR1 says what the comment needed: "Arithmetic-expression-1
shall be any single numeric data item described with a usage other than a standard floating-point usage, or any
form of arithmetic expression." The FACT was right; the clause was not. Both repaired in the landing, and the
`spec_refs` above are now populated — an empty `spec_refs` is how the wrong § went unchallenged.

MEASURED on `9a89fbd1` (every one compiled CLEAN under STRICT and evaluated a constant zero):

    IF "ABC" IS POSITIVE   -> false (0 > 0)      IF SPACE IS NEGATIVE  -> false
    IF X"36" IS POSITIVE   -> false              IF ALL "5" IS POSITIVE -> false
    IF "1" & "2" IS POSITIVE -> false            IF ZERO IS ZERO       -> TRUE, but only by accident of the drain

⚠ **TWO CURRENT BEHAVIOURS ARE RIGHT BY ACCIDENT**, which is why the landing carries a POSITIVE golden and not
only rejections: `IF ZERO IS ZERO` is true and `IF ZERO IS NOT POSITIVE` is true **because the drain returned
0**, not because ZERO was recognized. §8.8.1.1 names ZERO as the one admissible figurative, so both must stay
true for the right reason. `pb171_sign_condition_operands` pins them, along with `IF A - B IS NEGATIVE` — the
breadth-first property (NC250A IF--TEST-55/56) a depth-first leaf grab would break.

**FIXED BY:** a `NonNumericLiteralContext` arm in `BindOperandExprCore`, routed through the SPLIT-OUT
`NonNumericInNumericContext` (the ONE numeric-context reading of that node — copying the dispatch would have
made a second hand-maintained literal list, which is DA3's defect); the silent
`return new BoundNumLiteral("0")` fallback replaced with a `BoundExprError`; and the guard the fallback
CREDITED but which never looked at `comparisonOperand` replaced by `OperandWalkCoverageTests`, which enumerates
from the `.g4` every rule the walk serves and asserts each alternative reaches an arm. That test was made to
FAIL once, with the new arm removed, before it was trusted (feedback_green_gates_arent_evidence — a coverage
test that has never failed is the exact thing this defect was hiding behind).
