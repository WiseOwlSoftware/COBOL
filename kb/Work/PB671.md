`cite.py --check 12.4.5.9 "…no record locks are set by the execution of I-O statements through the associated file
connector"` → FAIL and `--check 12.4.5.9.4` on the same text → `OK §12.4.5.9.4 1) a)`, and wrote its own new comment

## The shape

The LOCK MODE clause's general rules are §12.4.5.9.4 (`OK §12.4.5.9.4 1) a)`); the existing comments cite the
clause heading §12.4.5.9 with a GR number, which the audit's phantom scan accepts (the clause exists) and its
misfiled scan cannot test (no quoted fragment). [[PB616]] is the same family in `§12.3.7 GR14a` (should be
§12.3.7.4), [[PB591]]/[[PB597]] the prose and wrong-number faces, [[PB607]] the doubled sub-clause.

## Fix

Rewrite each `§12.4.5.9 GRn` in `src/Cobol.Net.Runtime/IO/FileRegistry.cs` and `Sharing/PhysicalFileTable.cs` as
`§12.4.5.9.4 GRn` with a verbatim fragment beside it (run `cite.py --check` on each, and re-derive the GR NUMBER —
the general rules' numbering may not match what the comment assumed); then extend `audit_code_citations.py` with the
structural check PB616 asks for — a `§X.Y.Z GRn` / `SRn` reference where §X.Y.Z is a clause HEADING whose rules live
in a `.3`/`.4` sub-clause is a finding — so the class closes rather than the instance. Sweep the whole tree with the
new check in the same change set and fix what it finds (PB616's eleven sites included).

**Re-probe.** The note's "dozen comments" had mostly been repaired by later work (PB669, PB2848 wrote the parent-clause
note at the end of `FileRegistry.cs` and qualified their own citations). On this tree the residue was: `FileRegistry.cs`

design doc's SR2 pair. All rewritten to `§12.4.5.9.4` / `§12.4.5.9.3`; every rule NUMBER re-derived against the standard.

**A wrong rule number the clause fix exposed.** `PhysicalFileTable.LockRecord` and `RewriteSharedInStatement` cited
"GR8 self-access" for the idempotent re-lock. §12.4.5.9.4 GR8 is "The setting of a record lock is part of the operation of
an I-O statement"; the re-access rule is §9.1.16 ("A locked record may be re-accessed by the same file connector that holds
the lock"), which has no GR numbering, so the citations now quote it. The unit test `SelfRelock_IsIdempotent_GR8` lost the
ordinal from its name. `cite.py --check` OK on every fragment: §12.4.5.9.4 1) a), 3), 4), 5), 6), 7); §12.4.5.9.3 2);
§9.1.16.

**The extension items (R2 batch-2 triage).** The `OpenNoRewind` cref in `FileRegistry.Associate`'s doc named a member that
does not exist: `OpenTape`. `FileStatusCode` is now described as the §9.1.13 vocabulary of every organization with each
constant naming every statement that sets it: 37 is OPEN (§9.1.13.6 item 6 a) and DELETE FILE (§14.9.10.4 GR16, GR17), 43 is
DELETE RECORD and REWRITE (§9.1.13.7 item 3), 53/54 are READ, WRITE and REWRITE. `CobolFile.cs:353/362` joined the rewrite.

**The audit extension was NOT made, and why (determination).** The note asked for a check that flags `§X.Y.Z GRn` when
§X.Y.Z is a heading whose rules live in a `.3`/`.4` child. Measured on this tree with the audit's own machinery: 861 sites
in `src/`, 2,336 across every scanned file, and the sampled ones are correct: this repository deliberately writes a rule
block's clause BOTH ways (`audit_code_citations.py`: `_alias`, and `citation_corpus.code_files`'s "this repository deliberately
writes a rule block's clause both ways"), and the standard does so itself: Annex A.1 item 153 cites
"(12.4.5.9, LOCK MODE clause, General rule 1)" and §14.9.30.4 GR7 says "the rules specified in 12.4.5.9, LOCK MODE clause"
(`cite.py --check` OK on both). The mechanical defect shapes are already covered: a QUOTED fragment filed under the heading
is `audit_doc_citations.py`'s misfiling scan, a rule ordinal past the block's top is RULE, and a message string a user reads
is DIAG-UNQUALIFIED (gating, zero findings). What no mechanical check can see is a real ordinal beside the wrong rule
(the GR8 above), so that half of the note's fix is a convention change for the owner, not an implementation gap: flipping
it would be a 2,336-site tree-wide rewrite that belongs ahead of every other branch (feedback_finisher_never_widens). PB616
(`§12.3.7 GR14a`, the same family) is untouched by this landing.
