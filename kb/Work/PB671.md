# PB671 — OPEN — a clause one level short, a dozen times

Found 2026-09-05 by the `PB321` implementer (report §"New defects" C), which validated
`cite.py --check 12.4.5.9 "…no record locks are set by the execution of I-O statements through the associated file
connector"` → FAIL and `--check 12.4.5.9.4` on the same text → `OK §12.4.5.9.4 1) a)`, and wrote its own new comment
with the corrected clause and verbatim text.

## The shape

The LOCK MODE clause's general rules are §12.4.5.9.4 (`OK §12.4.5.9.4 1) a)`); the existing comments cite the
clause heading §12.4.5.9 with a GR number, which the audit's phantom scan accepts (the clause exists) and its
misfiled scan cannot test (no quoted fragment). [[PB616]] is the same family in `§12.3.7 GR14a` (should be
§12.3.7.4), [[PB591]]/[[PB597]] the prose and wrong-number faces, [[PB607]] the doubled sub-clause.

## Fix

Rewrite each `§12.4.5.9 GRn` in `src/Cobol.Net.Runtime/IO/FileRegistry.cs` and `Sharing/PhysicalFileTable.cs` as
`§12.4.5.9.4 GRn` with a verbatim fragment beside it (run `cite.py --check` on each, and re-derive the GR NUMBER —
the general rules' numbering may not match what the comment assumed); then extend `audit_code_citations.py` with the
structural check PB616 asks for — a `§X.Y.Z GRn` / `SRn` reference where §X.Y.Z is a clause HEADING whose rules live
in a `.3`/`.4` sub-clause is a finding — so the class closes rather than the instance. Sweep the whole tree with the
new check in the same change set and fix what it finds (PB616's eleven sites included).
