# PB3416 — the permanent-error replay rule lives in two places for REWRITE and DELETE

A lead from the PB3336 branch review (PR #268, merged as 0eba56a75; report
`E:\COBOL-coord\scratch\reports\w1118a6-PB3336-report.md`, `## Review findings`). Severity low, dimension duplication.

**Code sites** (re-read on origin/main 0eba56a75):
- `src/Cobol.Net.Runtime/IO/FileRegistry.cs:1662` (REWRITE) and `:1717` (DELETE): the guard
  `target.Length > 0 && c.PermanentErrorInEffect is null` ("the condition outranks the conflict (NoLockQuestion)").
- `src/Cobol.Net.Runtime/IO/FileConnector.cs:712-713` `MutationTargetRecordId`: returns `""` when `MutationOpenModeGuard()`
  is not null, i.e. while the permanent error is replayed. So `target.Length > 0` already implies the permanent error is
  not in effect, and the second operand of both guards can never change an outcome.
- `FileRegistry.cs` ~:1286 `RecordLocksGovern` (through `NoRecordIsLocked` and `AnotherRunUnitMayLock`): both guards run
  after it, and it still asks the host's presence byte for a statement on a permanently errored connector.

**Harm.** None user-visible shown (no wrong status): the rule is written in two places, so a change to one drifts from the
other (CLAUDE.md rule 4, one rule one place).

**Repro.** Read the two guards beside `MutationTargetRecordId`. Re-check:
`git grep -n "PermanentErrorInEffect is null" origin/main -- src/Cobol.Net.Runtime/IO/FileRegistry.cs`.

**Sequencing.** PB2749 (open, blocked on PB2759, PB3353 campaign) extracts the record-lock governance skeleton from
FileRegistry and its item (b) is the PB1541 permanent-error guard on `WriteShared` only. The same extraction is the natural
place to land this: one governance type with one permanent-error rule. If PB2749 lands first, re-measure this note against
the extracted type and close it when the duplicate guard is gone.

## Landed (wave 1129, group E)

Re-probed on the branch build: the two guards `target.Length > 0 && c.PermanentErrorInEffect is null` could not change an
outcome (`MutationTargetRecordId` answers "" under the condition), and the note's third observation was real and
measurable: the record-lock governance (`RecordLocksGovern` through `NoRecordIsLocked` and `AnotherRunUnitMayLock`) asked
the host's presence byte, through `PhysicalFileTable.AnotherRunUnitHoldsLocks`, for a REWRITE or DELETE on a permanently
errored ALL OTHER connector. A region-lock host that counts `HeldByAnother` showed it: all five REWRITE and DELETE cells
asked the host while the condition was in effect (the READ cells already asked none).

Fix: `FileRegistry.PermanentErrorOutranksLocks` is the one writing of "a permanent error in effect asks no §9.1.16 lock
question"; `NoLockQuestion` (the READ peeks) and the new `MutationTarget` (the REWRITE and DELETE target, which asks it before
`RecordLocksGovern`) both begin with it, and the two guards in `RewriteSharedInStatement` and `DeleteSharedInStatement` are
deleted. Tests: `PermanentErrorOutranksLocksDriftTests` (structure) and `PermanentErrorOutranksRecordLockTests` (25 cells: the
three organizations, the holder in the same run unit and in another on both region hosts, REWRITE and DELETE: the '51'
control, a RETRY phrase, nothing changed, the lock kept, CLOSE ending the condition; and the counting host over every governed
READ, REWRITE and DELETE). PB2749's witness (c) now describes the code the extraction moves.

## Landing

- `src/Cobol.Net.Runtime/IO/FileRegistry.cs#PermanentErrorOutranksLocks` — the one writing of "a permanent error in effect asks no §9.1.16 lock question"; `NoLockQuestion` (READ peeks) and `MutationTarget` (REWRITE/DELETE target) both begin with it. REUSE it for any new governed verb; never test `PermanentErrorInEffect` beside it. Trap: `FileConnector.MutationTargetRecordId` already answers "" under the condition, so a guard after it is dead, but `RecordLocksGovern` BEFORE it still asks the host's presence byte, which is why the precedence must come first.
- `tests/Cobol.Net.Tests.Unit/PermanentErrorOutranksRecordLockTests.cs#CountingHost` — a delegating `RegionLocks` host (through `HostRegionLocks.Forcing`) that counts `HeldByAnother`: the way to witness "the host is asked nothing"; REUSE it. Traps: `FileRegistry.Reattempt` pauses only for a holder outside the run unit (no pause for two connectors of one run unit), and a sequential-access REWRITE needs a successful READ immediately before it (an unsuccessful '51' REWRITE is a statement: the next one is '43', GR5 before GR11, `FileConnector.SequentialMutationTarget`); a sequential file has no way back to record 1 but a CLOSE and OPEN (`Reaim`).
- `src/Cobol.Net.Runtime/IO/FileConnector.cs#SequentialMutationTarget` — the review's R1-1: the sequential-access arms of `MutationTargetRecordIdCore` (sequential, relative, indexed) named `LastReadRecordId` whatever the previous statement, so the registry's lock check ('51', and RETRY waits) ran ahead of the connector's own '43' gate. They now name the record only after a successful READ. REUSE it for any new sequential-access mutation arm.
