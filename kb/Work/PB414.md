# PB414 — one lowering, two arms, one bare `break` — and one clause number carried by all ten sites

## 1. The mechanism

14.9.19 states the NEXT SENTENCE transfer TWICE, once per arm: GR4 governs it in the THEN phrase, GR6 in the
ELSE phrase. The compiler implements both through ONE node and ONE lowering — `BoundNextSentence` →
`goto __sent{pc}_{k};` — and the binder does not record which arm the node came from, so **the two arms cannot
diverge behaviourally and they share the same defect**.

`DispatchEmitter.EmitParagraphBody` (`src/Cobol.Net.Compiler/CodeGen/DispatchEmitter.cs:305-317`) sets

    bool needLabels = sentences.Any(ContainsNextSentence);            // :305
    dispatchState.SentenceEndLabel = needLabels && !last ? $"__sent{pc}_{k}" : null;   // :310

so the **LAST sentence of every paragraph gets a NULL label**. `StatementEmitter.Visit(BoundNextSentence)`
(`src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:199-208`) then takes its else-branch and emits
`__pc = CurrentPc + 1; break;` (`:206-207`). That bare `break` is meant for the dispatcher's `switch`, but an
inline PERFORM lowers to a C# `while`, so **the break binds to the LOOP**: control resumes at the statement
following END-PERFORM — inside the same sentence the rule says to leave.

This is the identical emitter mistake PB405 measures for EXIT PARAGRAPH / EXIT SECTION and PB403 measures for
`BoundExitPerform`'s fallback arm. Four statements, one wrong idiom for "leave the dispatcher".

**A second finding, in the citations rather than the behaviour.** A sweep of the whole tree for `14.9.19 GR`
returns TEN sites and every one says GR6; GR4 is cited NOWHERE in `src/`, `tests/`, `kb/` or `docs/`. Most of
those sites describe the sentence-boundary label or the node itself — i.e. BOTH arms — so GR6 is not merely
incomplete there, it is the wrong citation for what the site implements. The test site is the sharpest:
`RedefinesSubscriptedViewDifferentialTests.cs:86-88` documents itself as covering GR6 and its two cases put
NEXT SENTENCE in the THEN phrase both times — the first executes it (GR4), the second is never reached because
the condition is false and the ELSE arm runs (GR5). Its summary line "Both branches exercised" is true of the
IF branches and false of the NEXT SENTENCE placements. This is CLAUDE.md rule 1's exact failure mode: not an
invented citation but an INHERITED one, propagated from a bound-node comment into an emitter comment, a kb
diagram, two rows of a kb lookup table and a shipped test's doc comment.

The citation error is not only bookkeeping. **NEXT SENTENCE in an ELSE phrase — the single construct GR6
actually governs — has NO test anywhere in `tests/`.** The only line in the non-NIST tree pairing ELSE with
NEXT SENTENCE (`RedefinesSubscriptedViewDifferentialTests.cs:103`) puts the NEXT SENTENCE in the THEN arm.

Both GR4 and GR6 end "control is transferred to an implicit CONTINUE statement immediately preceding the next
separator period", which is the obligation being violated: **every statement remaining in the current sentence
after the IF must be skipped.** A code site implementing the shared transfer must cite both; a site or test
exercising the THEN arm must cite GR4; GR6 alone is correct only for the ELSE arm, which is the one arm nothing
in the tree exercises.

## 3. Expected vs observed — RE-MEASURED ON HEAD (89044aa0), both arms and the control

    $ cobol.exe h1-gr4-inline-last.cob --std 2023 --run       # GR4, THEN arm
      BAD-TAIL
      P2
      warning COBOLNET0903: the NEXT SENTENCE phrase is obsolete as of COBOL-2023 (warning only)  [exit 0]

`MAIN-P.` is one sentence: `PERFORM UNTIL K > 3 / ADD 1 TO K / IF K = 2 NEXT SENTENCE END-IF / END-PERFORM /
DISPLAY "BAD-TAIL".` followed by `PARA-2. DISPLAY "P2".` The separator period is after `BAD-TAIL`, so GR4
requires `BAD-TAIL` to be skipped and the expected output is `P2` alone. Observed: `BAD-TAIL` then `P2`.

    $ cobol.exe h2-gr6-inline-last.cob --std 2023 --run       # GR6, ELSE arm — IF K NOT = 2 CONTINUE ELSE NEXT SENTENCE
      BAD-TAIL
      P2                                                                                          [exit 0]

    $ cobol.exe h3-control-two-sent.cob --std 2023 --run      # the control: a SECOND sentence follows in the paragraph
      S2
      P2                                                                                          [exit 0]

The control is what pins the trigger exactly. Its paragraph has a following sentence, so `needLabels && !last`
is true, the label is planted, and the emitted transfer is a C# `goto` — which does leave the loop correctly,
so `BAD-TAIL` is properly skipped and `S2` runs. The generated bodies differ in exactly that one token:

    h1 (last sentence):   if (K == 2L) { __pc = 1; break; }   ...  __pexit0: ; WriteLine("BAD-TAIL"); __pc = 1; break;
    h3 (two sentences):   if (K == 2L) { goto __sent0_0; }    ...  __pexit0: ; WriteLine("BAD-TAIL"); __sent0_0: ; WriteLine("S2");

**Why the b2 adjudication missed it — two halves, each verified, never conjoined.** Its probe b1 put the NEXT
SENTENCE inside an inline PERFORM but in a paragraph with a FOLLOWING sentence (label present → a `goto`, which
works); its probe p14 put it in a LAST sentence but at paragraph level (no enclosing loop). Only the
conjunction fails.

**A safety claim in the code comment is also false as written.** `DispatchEmitter`'s remark that a missed
container would emit a goto with no label — a loud backend compile failure, never a silent misjump — does not
hold: `needLabels` gates BOTH the label and the goto, so a missed container yields the silent
`__pc = pc + 1` paragraph fall-through instead of a compile error. (No container IS missed today: the
`[BoundNode]` roots other than `BoundStatement` are `BoundExpr`/`BoundOperand`/`BoundBoolExpr`/
`BoundCondition`/`BoundPerformControl`/`BoundSetTarget`, none of which holds statements, so
`BoundVisitorGenerator.IsStatementBearing`'s pruning
(`src/Cobol.Net.Compiler.SourceGen/BoundVisitorGenerator.cs:241`) is safe. The comment is wrong about WHY.)

## 4. The code site and the shape of the repair

- `src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:199-208` — `Visit(BoundNextSentence)`, the `goto` arm at
  `:204` and the `break` arm at `:206-207`.
- `src/Cobol.Net.Compiler/CodeGen/DispatchEmitter.cs:305-317` — `EmitParagraphBody`, where `needLabels && !last`
  denies the last sentence a label.
- `src/Cobol.Net.Compiler/CodeGen/DispatchEmitter.cs:327-330` — `ContainsNextSentence` / `HasNextSentence`, the
  drift-proof container discovery (correct; it recurses over the generated `StatementChildren()`).
- `src/Cobol.Net.Compiler/Binding/Bound/BoundTree.cs:107` and `:736` — the node docs carrying the GR6 citation.
- `src/Cobol.Net.Frontend/Grammar/Core/CobolControlFlow.g4:366` — `nextSentenceStatement`.

**The repair is structural, and it is the same one PB405 names.** Plant a sentence-end label for EVERY
sentence including the last — the paragraph fall-through becomes a labelled landing — so NEXT SENTENCE is
**always** a `goto` and never a bare `break`. That makes the next loop-shaped container automatic instead of
one more special case, and it removes the `needLabels`/`!last` conjunction that is the actual bug. Landing this
alongside PB405's per-paragraph dispatcher-exit label is the same edit seen from two statements.

**The citation repair is part of the same change set** (rule 6): re-cite the shared sites as GR4 and GR6 by arm
rather than GR6 alone, correct the test's doc comment to GR4/GR5, and correct the two kb tables. Ten sites,
enumerated:

    src/Cobol.Net.Compiler/Binding/Bound/BoundTree.cs:107, :736
    src/Cobol.Net.Compiler/CodeGen/DispatchEmitter.cs:298
    src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:201

## 5. The sibling sweep the fixer must do

- **PB405 and PB403 are the same emitter defect** through EXIT PARAGRAPH, EXIT SECTION, `BoundExitPerform`'s
  fallback arm and (measured on HEAD, and owned by the GO TO lane) GO TO. Fix the idiom, not the four sites.
- **Every OTHER container that can hold a NEXT SENTENCE in a last sentence.** The b2 evidence covers inline
  PERFORM; an EVALUATE WHEN arm and a SEARCH body in the last sentence of a paragraph are the same shape and
  were probed only in non-last sentences (`b2-nextsent-in-evaluate`, the `h4`/`h5`/`h6`/`h7` family). C#
  `switch` is also breakable, so the EVALUATE case is a live candidate, not a formality.
- **`RedefinesSubscriptedViewDifferentialTests` asserts through `DifferentialGolden`**, whose committed golden
  is BAKED from the legacy engine (bake mode asserts cobolnet == legacy, then writes the `.out`). It is a
  regression net with a legacy-derived expectation and **cannot close either row** — the goldens this fix needs
  are spec-derived `tests/conformance/<edition>/` cases: one per arm, each inside an inline PERFORM in the last
  sentence of a paragraph, plus the two-sentence controls.
- **The ELSE-arm coverage hole must be closed regardless of the fix** — GR6's own construct has no test at all
  today, so even correct behaviour there is verified by nothing the project owns.
- Editions: NEXT SENTENCE is legal at all four; 4.2.12 requires an implementation to support archaic elements
  and to identify them, and COBOLNET0903 fires as a warning at 2023 only. The b2 sweep measured that across
  `--std 85/2002/2014/2023`; the fix must not change it.
