# PB3121 — self-name scope: the screen and the registry disagree

Source: the implementer report for PB2495 (PR #26), `E:\COBOL-coord\scratch\reports\w1070f-PB2495-report.md`, "New defects", item 2.

**Repro:** `E:\COBOL-coord\scratch\w1070f\probe\mutual2.cob`: two PROTOTYPE programs PS1 and PS2, each declaring a typedef `USAGE PROGRAM-POINTER TO` a prototype (PS1's typedef names PS1 itself, PS2's names PS2). Not re-run by the clerk; see the report for the observed result.

**Code sites:**
- `src/Cobol.Net.Compiler/Binding/DataBinder.cs:5595` the scope screen admits `UnitSelfName` (`CobolNames.Same(UnitSelfName, restrictedPrototypeName)`); `UnitSelfName` is set at `BinderDriver.cs:651` and declared at `DataBinder.Linkage.cs:174`.
- `src/Cobol.Net.Compiler/Binding/BinderDriver.cs:1145` `ProgramPrototypesOf` registers a name only from `data.ProgramSpecifiers` (written specifiers) plus the containing-program entries, so a unit's own name with no written specifier is not registered. The screen and the registry answer "is this name in scope" differently.

**Relation:** PB2626 (open, unify the session facts a DataBinder is seeded with) does not mention `UnitSelfName`; this is a second-copy symptom of the same shape, so the implementer reads PB2626 first. PB2495 (landed) is where it was found.

Spec: none recorded by the report or an existing note. The code comment near `BinderDriver.cs:1150` cites section 8.4.6.8; the implementer must run `python scripts/spec/cite.py --check` on it before relying on it.

Flag note: rejects_legal_source is set from the report reading (the repro draws a refusal); the clerk did not re-run it, the implementer confirms or clears it.

## Landed (wave 1071 group E)

**Re-probe on the base tree (77f10dfb2).** `mutual2.cob`: `error COBOLNET1959: SET 'B' TO 'A' ... do not have the same
signature` — PS1's formal TO PS1 resolved to no signature, because `ProgramPrototypesOf` held PS1 only under a written
specifier; with `REPOSITORY. PROGRAM PS1.` written in each prototype the same program prints `done`. The disagreement
ran BOTH ways: a contained program's `USAGE PROGRAM-POINTER TO <container>` drew COBOLNET1958 from the TO-phrase screen
(it asked only the unit's own name and the written specifiers) although the registry always held the container; and
`CALL <own-name>` in a RECURSIVE program drew COBOLNET1639 (the word not in the registry, so read as a data name).
`rejects_legal_source` confirmed.

**Determination.** §8.4.6.8's "a containing program definition" includes the element's OWN program definition:
§8.4.6.6 is the same sentence over functions, and its "the containing function definition" can only be the function's
own, since a function definition contains no other source unit (§10.2: only "a program definition for an outermost
program, including its nested programs"). §12.3.8.3 SR15 already states the self and container cases as one
consequence. Recorded in `docs/COBOLNET_INTERPROGRAM_DESIGN.md` D6.

**Fix.** `BinderDriver.ContainingDefinitions(unit)` — the unit, then each program containing it — is the ONE set:
`ProgramPrototypesOf` registers every program member LAST (which is also SR15's "specifier ignored"),
`UserFunctionsOf` takes its function member as the self entry and skips a self-naming specifier (SR11), and
`BindUnitData` seeds `DataBinder.ContainingDefinitionNames` (replacing the single `UnitSelfName`) from it for the
TO-phrase screen. `SpecifiesItself` is deleted. Sibling found and fixed: `DataBinder.Ptr`'s `IsUserFunction` admitted
a PROGRAM's own name as a user function; it now asks `UnitIsFunction` too.

**Goldens.** `conformance:2002/pb3121_containing_definition_scope` (self-restricted prototypes, a RECURSIVE self-CALL
by prototype word, a contained program's TO <container>, a non-recursive self-CALL raising EC-PROGRAM-RECURSIVE-CALL
into ON EXCEPTION); `conformance:negative/pb3121-sibling-program-not-in-prototype-scope` (a SIBLING nested program's
name is not in scope: COBOLNET1958).
