# PB3103 — land a branch the moment it is ready, not when its wave ends

## Found (2026-10-12, the operator; owner-approved design)
The owner asked for the change after the operator measured wave 1069 (main `ddee217e3`): group D (PB3031) was stamped
`Review: CLEAN` at 12:34 PDT and groups E (PB2502) and F (PB2842) by 13:05, and all three read WAITING TO LAND in
`prune_worktrees.py --brief` while groups G and H were still running. They land only after the wave unit ends and
`next_unit.py` (rule 6: `branches_pending` with status DONE -> `enqueue`) starts an `enqueue` unit, whose step 3 runs
`enqueue.py land` for every WAITING TO LAND row. Two costs:
- **Ready work idles.** A branch that finishes early waits for the slowest group of its wave (hours), then for the
  enqueue unit's gates on both hosts and the merge group's CI.
- **The machine alternates between two half-idle phases.** During a wave nothing lands; during the enqueue unit no
  implementer runs, and that unit spends most of its time blocked on gates and the merge queue.
- **A landing gate queues behind implementer gates.** `scripts/gate_slot.py` is one FIFO counting semaphore (cap 3), so
  a landing's gate can wait behind up to three implementer gates although landing is the measure
  (feedback landing-is-the-measure, owner 2026-10-10).

The owner chose (AskUserQuestion, 2026-10-12): **"Supervisor lane (Recommended)"** — a deterministic background landing
lane in the supervisor, landing gates first in the slot queue; filed as one note, built as one branch, landed alone,
then measured against wave 1069. The rejected alternative (the wave unit's model runs `enqueue.py land` as branches
come back CLEAN) puts every landing log into a long Opus transcript on every wave.

## Fix shape (one branch; no other change rides it)
1. **`scripts/orchestrator/land_lane.py`** (new; deterministic, no model; a `--self-test` the self-test runner
   discovers). `tick`: read the branch survey (`prune_worktrees` imported, never re-parsed from its text), and for each
   WAITING TO LAND row, in the order the survey lists them, that is not already being landed, start
   `python scripts/orchestrator/enqueue.py land <branch>` detached, logging to `<coord>\logs\land-lane-<branch>-<stamp>.log`,
   and record the attempt (branch, head sha, pid, log) under `<coord>\land-lane\`. Reap finished attempts: read the
   log's `=== ENQUEUE: ` verdict line and record the outcome. Never relaunch a branch whose last attempt at the SAME
   head ended in a verdict only an agent or the operator can change (CONFLICT 4, GATE RED 5, a DEVLOG refusal 6, a
   stale oracle baseline 7, UNREVIEWED 11, a permission refusal): that row waits for the `enqueue` unit, and a new head
   (a finisher's commit, reviewed) makes it eligible again. The waits a script can see end are retried at the same
   head: the landing check's exit 3 (the branch shares a file with earlier-dispatched in-flight work, kb/Work PB2701)
   once that work is no longer in flight, and exit 2 (main moved under every attempt) or 9 (GitHub refused the push,
   the PR or the queue) once, as `enqueue.md` step 3 already says. QUEUE NOT ACTIVE (exit 8) stops every new attempt
   and is named to the operator. Mid-wave landing meets exit 3 more often than the enqueue unit did, because a wave's
   other groups are still in flight: the self-test plants that case. `status`: the in-flight and finished attempts, one line
   each, for the `enqueue` unit and the operator. The lane dispatches no agent and decides nothing a script cannot.
2. **The supervisor runs the lane** (`scripts/orchestrator/orchestrate.ps1`): while ANY unit runs, a `land_lane.py tick`
   every few minutes as a background process, never on the event loop (the `Write-Checkpoint` pattern, kb/Work PB2590),
   and never fatal to the unit. It stops starting attempts once STOP or STOP-UNIT exists (a running `enqueue.py land`
   finishes; it is idempotent). The `LEDGER PUBLISH OWED` notice follows each merged landing as today.
3. **Landing gates first** (`scripts/gate_slot.py`): a gate that `enqueue.py land` starts (it runs the gate at Normal
   priority) takes the next free slot ahead of every waiting implementer gate; the cap is unchanged, so the machine's
   total gate load is the same. FIFO holds within each class. The self-test proves the order with a planted queue.
4. **The `enqueue` unit keeps the judgment** (`scripts/orchestrator/units/enqueue.md`): step 3 no longer runs
   `enqueue.py land` itself; it reads `land_lane.py status` and sends each stopped attempt to step 4 (a finisher) or to
   the handoff exactly as the step lists the exits today. Steps 2 (reviews), 4 (finishers), 5 (leads), 6 (prune) and 6b
   (landing records) are unchanged. `next_unit.py` starts an `enqueue` unit when there is agent work (WAITING FOR REVIEW,
   BOUNCED, a stopped lane attempt, leads to file) or landing records to complete, not merely because a handoff lists
   DONE branches the lane is landing.
5. **The rules and the design move with it**: MANDATORY-PRACTICES O11 (the loop's landing LANE lands every WAITING TO
   LAND branch; the `enqueue` unit handles reviews, finishers and leads; the attended session still lands nothing
   while the loop runs), `docs/rearchitecture/DESIGN-orchestrator-loop.md` (the lane beside the unit) and
   `docs/rearchitecture/DESIGN-test-build-ci.md` (the gate slot's two classes), with a drift test that the supervisor
   starts the lane and that `enqueue.md` step 3 runs no `enqueue.py land` of its own.

## Measure (after it lands)
`landing_measure.py summary`: DONE -> enqueued -> merged per pull request for the first waves after the lane, against
wave 1069's landings (which went through the enqueue unit). The expected gain is that a branch finishing early lands
within its own gate and CI time, and that the wave-plus-landing cycle loses most of its landing phase.

## Landed (wave 1069 group L, branch worktree-wf_1ce5d560-43a-1)
Re-probed first: `next_unit.py` with a DONE handoff chose `enqueue` ("finished branches waiting: w9a"),
`units/enqueue.md` step 3 ran `enqueue.py land` itself, and `gate_slot.py` served one FIFO with no class. The five
items, exactly as above:
- `scripts/orchestrator/land_lane.py` (new): `tick` (reap, survey, launch detached `land_lane.py run` per eligible
  branch), `status`, `collect`, `clear-halt`; `decide` holds the retry table (exit 3 once `landing_check.py` passes on
  the branch's range; 2, 9 or a DIED runner once; 8 halts every attempt and mails the operator; anything else STOPPED
  at that head until a new head); `agent_work` is next_unit.py's reader. A retry follows the lane's attempt record,
  because a run that commits makes the survey read the branch IN FLIGHT. `--self-test` (30 checks) plants every case
  and runs a real detached runner.
- `orchestrate.ps1`: `Start-LaneTick` / `Complete-LaneTick` (background, one at a time, never fatal), at each unit's
  start and every `-LandLaneSeconds` (300).
- `gate_slot.py`: `ticket-<seq>-landing.lock`; landing tickets served first, FIFO within each class, cap unchanged;
  `enqueue.py run_gates` sets `COBOL_GATE_CLASS=landing`; arm 11 and `GateSlotDriftTests`.
- `units/enqueue.md` step 3 reads `land_lane.py status`; `next_unit.py` rule 6 (`enqueue_work`) starts an enqueue unit
  only for agent work, or DONE branches while the lane has no survey in 30 min.
- MANDATORY-PRACTICES O11/L1/L2, DESIGN-orchestrator-loop.md §4.9 (new) and rule 6, DESIGN-test-build-ci.md §3.14.6;
  `LandingLaneDriftTests`.
