# PB3113 — land_lane.pid_alive trusts a reused pid

**Sites:** `scripts/orchestrator/land_lane.py` (`runner_alive`, `reap`, `tick`, `self_test`), `scripts/orchestrator/coord.py` (`process_command`, `_self_test`).

> ⚙ **flags:** process-only

Source: `w1069l-PB3103-report.md`, "New defects".

`scripts/orchestrator/land_lane.py#pid_alive` accepts any live Python process with the runner's recorded pid. If Windows reuses that pid for another Python process, the landing attempt reads RUNNING until the unrelated process exits. That stalls the supervisor's landing lane (PB3103, landed PR 18).

**Fix shape (for the implementer to confirm).** Compare the process start time (or a command-line marker) recorded with the pid. Related open notes with the same pid-liveness shape in other helpers: PB3032 (`_pid_alive`, `OpenProcess`), PB3061 (`gate_slot._pid_alive`).

## Landed (wave 20261107 group D)

**Re-probe.** Reproduced on this build with two real processes (`land_lane.py --self-test` arm 10b): a live Python process that holds the recorded pid but is not the runner read ALIVE under the old `pid_alive` (any Python image), so `reap` never marked the attempt DIED and the branch stayed RUNNING until the stranger exited.

**Fix.** The pid says WHICH process; the attempt record says WHAT it must be. The runner is `land_lane.py run <attempt record>` (started by `launch` through `detached.spawn_detached`), so `land_lane.runner_alive(attempt)` is true only while the process with the recorded pid is a Python whose command line names that attempt's own record path (`coord.process_command`, the one single-process command-line reader beside `process_name`; case-normalised on Windows). A reused pid carries another command line and reads dead; `reap` marks the attempt DIED as for any other dead runner. No second field is recorded (a start-time token would need a clock read at launch that can miss a fast runner); the record path is already unique per attempt. `tick`'s `alive` collaborator now takes the attempt record; `coord._self_test` pins `process_command`. Sibling sweep: the other pid readers named by the note are different mechanisms (`coord.loop_state` and `prune_worktrees.live_lock` read an image name for a lock holder; `gate_slot._pid_alive` is a handle wait) and stay with PB3032/PB3061; none reads an attempt's runner.
