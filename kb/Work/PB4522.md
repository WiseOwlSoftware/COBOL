# PB4522 — seconds-from-formatted-time-fraction-stale-scale: SECONDS-FROM-FORMATTED-TIME with fractional seconds returns a wrong value that depends on the previous call

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

SECONDS-FROM-FORMATTED-TIME returns a wrong value for a time with fractional seconds whenever an earlier call in the
run left a different scale behind: the whole seconds are taken at the scale of the previous result, not at scale 0.
In one run, `("hh:mm:ss.s" "00:00:01.5")` first gives 1.5 (right), then `("hh:mm:ss.ss" "00:00:01.50")` gives 0.6
instead of 1.5, `("hh:mm:ss.ssssss" "23:59:59.999999")` gives 8640.899999 instead of 86399.999999, and the first call
repeated gives 0.500001 instead of 1.5. The number of fraction digits is not the trigger: the same calls in another
order give other wrong values. Class: wrong output. Fuzz night 2026-11-03: fz00991.

## Minimal test case

Free reference format (`-free`).
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. SFTFRAC.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 WS-NUM PIC 9(5)V9(9) VALUE 0.
PROCEDURE DIVISION.
    COMPUTE WS-NUM = FUNCTION SECONDS-FROM-FORMATTED-TIME
        ("hh:mm:ss.s" "00:00:01.5")
    DISPLAY "F1 " WS-NUM
    COMPUTE WS-NUM = FUNCTION SECONDS-FROM-FORMATTED-TIME
        ("hh:mm:ss.ss" "00:00:01.50")
    DISPLAY "F2 " WS-NUM
    COMPUTE WS-NUM = FUNCTION SECONDS-FROM-FORMATTED-TIME
        ("hh:mm:ss.ssssss" "23:59:59.999999")
    DISPLAY "F6 " WS-NUM
    COMPUTE WS-NUM = FUNCTION SECONDS-FROM-FORMATTED-TIME
        ("hh:mm:ss.s" "00:00:01.5")
    DISPLAY "F1 " WS-NUM
    STOP RUN.
```

## Environment

cobc (GnuCOBOL) 3.2.0 on WSL2 Ubuntu. `cobc -x -free -std=cobol2014 -o p prog.cob && ./p` (no diagnostic other than
the distribution's `_FORTIFY_SOURCE` redefinition notice).

## Observed result

```
F1 00001.500000000
F2 00000.600000000
F6 08640.899999000
F1 00000.500001000
```
Exit code 0.

## Expected result (per ISO)

§15.79.4 rule 1 (2014 and 2023): the returned value is "((H * 3600) + (M * 60) + S)", where "S is the portion of
argument-2 corresponding to the seconds subfield of argument-1". §15.3.3.2 makes the fraction digits part of that
subfield: a fractional-seconds time format has "at least one lowercase 's' character representing a digit in the
decimal fraction portion of the seconds subfield". Nothing in the rule depends on an earlier call. Expected:
```
F1 00001.500000000
F2 00001.500000000
F6 86399.999999000
F1 00001.500000000
```

## Our compiler

WiseOwl COBOL (fresh judge) prints the expected values for the F1, F2 and F6 calls of the fuzz program; the repeated
F1 line was added by the refuter and not run on WiseOwl.

## Fix site

libcob/intrinsic.c (read in a 3.3-dev tree), `seconds_from_formatted_time`: in the branch for `format.decimal_places != 0`
it sets `seconds_decimal->value` to the whole seconds but does not set `seconds_decimal->scale` (the other branch sets it
to 0), so `cob_decimal_add` uses the scale the decimal was left with by an earlier use.

## Vetting (2026-11-04)

Verdict SOUND (to be reported); the refuter agrees. Rule 15.79.4 1) (the seconds subfield S in ((H * 3600) + (M * 60) + S)) with the format rule of 15.3.3.2 for fractional seconds; both cite.py --check OK. 3.2.0 and 3.3-dev print identical wrong values (F2 0.6, F6 8640.899999, repeated F1 0.500001): intrinsic.c seconds_from_formatted_time sets the decimal value without setting its scale in the decimal_places != 0 branch, an uninitialized scale no latitude covers. No tracker ticket names SECONDS-FROM-FORMATTED (the ChangeLog's 2020 "fix bug #886" is not today's bugs-886). The function is in the 2009 CD, so the 2014 claim holds.
