# PB2522 — the campaign lane starves behind model-written handoffs

The owner asked on 2026-10-07 16:50 PDT "why is PB2108 taking so long. It's been hours". PB2151, the last open note of
the legacy-retirement cluster PB2108, was SPLIT off by wave 1030 at 05:40 PDT as ready work; it was dispatched only
at 14:31, by the attended operator after the owner asked at 14:28 what blocked the retirement. In between, every
orchestrator start logged `campaign lane: cluster PB2108, 1 open note(s), 1 ready`, and every unit was a fix-lane
`wave`, `land` or `resume`.

## Mechanism

`scripts/orchestrator/next_unit.py#choose` returns, in order: an owner question; **the last handoff's `next_unit`**;
the meter; repo state; resume/land; and only then `campaign_choice(cluster, …)` — the rule that alternates campaign
waves with fix-lane waves (DESIGN-orchestrator-loop.md, kb/Work PB2120 rule 7). A unit's handoff is written by the
model, which names the next unit from what IT sees ("a wave should run the finishers …"); a model that says `wave`
therefore overrides the alternation every time, and the campaign rule is unreachable for as long as handoffs name a
unit — which today was always.

## Shape (rule 5: make the next case automatic)

The alternation is the supervisor's rule, not the model's: when the handoff names a generic `wave` and the cluster has a
ready note and the last wave-type unit was not a campaign, `choose` picks `campaign` (keeping the handoff's reason in the
log); a handoff may still name `land`, `resume` or an owner question, which outrank both. Test in next_unit's
self-test: a handoff naming `wave` with a ready campaign note after a fix-lane wave yields `campaign`. Also make the
starvation visible: the supervisor logs `campaign PB… ready for N h, last campaign wave at …` when a ready note has
waited more than one wave.

## Landing - 2026-10-07 (wave 1037 group Q)

Landed as the shape above, at its root and one step wider (rule 5).

- **The campaign rule decides every wave-type choice** (`next_unit.py#choose`, `#base_choice`, `#campaign_choice`):
  rules 2 to 7 pick the unit (`#base_choice`, unchanged), and when that unit is `wave` or `campaign`, from a handoff or
  from rule 7, the campaign rule picks its lane. The handoff's reason is kept in the choice's reason
  (`campaign PB...: 1 ready note(s): ...; the handoff named wave: ...`). A handoff's `land`, `resume`, `meter` and an
  owner question still win. Without `--cluster` the output is byte-identical (`test_orchestrate.ps1` 8b, 8c).
- **More than one campaign** (the dispatch's R2/R3 question): `-Cluster A,B` (comma-separated, because `pwsh -File`
  passes `-Cluster A,B` as ONE string) and a repeatable `--cluster`; the ready leads take campaign turns least recently
  run first, still alternating with fix-lane waves; a lead's lane ends when its cluster lands while the others go on.
  The JSON names the chosen lead in `cluster`, the supervisor substitutes it into the wave prompt and records it in
  `units.jsonl`.
- **Starvation is visible**: with `--cluster` every choice but an owner question carries `campaigns` (each lead's lane
  state, which the supervisor records in that unit's `units.jsonl` line) and `starved` (a ready lead that has waited
  through more than one wave-type unit since its own last campaign wave, measured from that record). The supervisor
  logs `campaign <lead> ready for N h (W wave-type unit(s)), last campaign wave at T` at every choice until the turn
  comes. A record gap (every line written before this change) under-reports, never over-reports.
- **The lane's end was also starved**: the `landed` signal came only from rule 7, so a loop whose handoffs always named a
  unit never learned its cluster had landed (the live loop still logged `campaign lane: cluster PB2108, 1 ready` at
  20:30 with PB2108 landed). `campaigns` is now on every choice, so the end is seen at the next unit.
- `units/common.md` tells a unit that `wave` names a wave, not its lane.

Evidence: `test_orchestrate.ps1` gained 8c (the handoff cases), 8d (round-robin, a landed lead among two), 8e
(starvation, its under-report rule) and supervisor cases (two leads named at start, the chosen lead in the prompt and
`units.jsonl`, a landed lead among two, the starvation log line). Run against the pre-change scripts the new checks failed (141/158 of the first version, among them
`a handoff naming wave after a fix-lane wave, with a ready campaign note: campaign: got 'wave  '`); after: 160/160.
A probe against a copy of the live coordination state (handoff "OPERATOR 20:40: run a fix-lane WAVE now",
`--cluster PB2108 --cluster PB1754 --cluster PB2119`) chose `campaign PB1754` with `PB2108: landed`.

## For the next implementer

  `units.jsonl` (`campaigns`, `cluster`, `started_at`). `#ran_campaign` treats a campaign line without `cluster` (written
  before this change) as the run of every lead.
- A lead that is itself a note of another lead's cluster (PB2119 inside PB1754) is planned twice if both are passed:
  pass one of them (DESIGN-orchestrator-loop section 9.1).
