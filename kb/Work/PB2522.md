# PB2522 — the campaign lane starves behind model-written handoffs

The owner asked on 2026-10-07 16:50 PDT "why is PB2108 taking so long. It's been hours". PB2151, the last open note of
the legacy-retirement cluster PB2108, was SPLIT off by wave 1030 at 05:40 PDT as ready work; it was dispatched only
at 14:31, by the attended operator after the owner asked at 14:28 what blocked the retirement. In between, every
orchestrator start logged `campaign lane: cluster PB2108, 1 open note(s), 1 ready`, and every unit was a fix-lane
`wave`, `land` or `resume`.

## Mechanism

`scripts/orchestrator/next_unit.py#choose` returns, in order: an owner question; **the last handoff's `next_unit`**;
the meter; repo state; resume/land; and only then `campaign_choice(cluster, …)` — the rule that alternates campaign
waves with fix-lane waves (DESIGN-orchestrator-loop.md, kb/Work PB2120 rule 7). A unit's handoff is written by the
model, which names the next unit from what IT sees ("a wave should run the finishers …"); a model that says `wave`
therefore overrides the alternation every time, and the campaign rule is unreachable for as long as handoffs name a
unit — which today was always.

## Shape (rule 5: make the next case automatic)

The alternation is the supervisor's rule, not the model's: when the handoff names a generic `wave` and the cluster has a
ready note and the last wave-type unit was not a campaign, `choose` picks `campaign` (keeping the handoff's reason in the
log); a handoff may still name `land`, `resume` or an owner question, which outrank both. Test in next_unit's
self-test: a handoff naming `wave` with a ready campaign note after a fix-lane wave yields `campaign`. Also make the
starvation visible: the supervisor logs `campaign PB… ready for N h, last campaign wave at …` when a ready note has
waited more than one wave.
