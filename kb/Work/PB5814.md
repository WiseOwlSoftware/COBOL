# PB5814 - at --std 85 ADD and SUBTRACT CORRESPONDING evaluate the group operand's subscripts afresh for each pair, where the 1985 text as amended requires once at the start; the documented determination D-CORR85 is wrong for these two verbs

**What is wrong.** `ADD CORRESPONDING TG (JJ OF G2) TO G2` (`addc.cob`): the pair `JJ` stores into the subscript's own data item, so a later pair moves to another element of `TG`. At `--std 85` the compiler re-identifies `TG (JJ OF G2)` for every pair, and the program prints `AA=100 JJ=2 BB=400`. The 1985 text as amended evaluates the subscript once, as the first operation of the statement, so `BB OF G2` receives `BB OF TG (1)` and the program prints `AA=100 JJ=2 BB=200`, which is what `--std 2023` prints. Cause (a): an 85 arm is wrong. The checker rated the mechanism medium before the ruling below. Harm: wrong_answer. SUBTRACT CORRESPONDING takes the same `perPair` switch and is the sibling this note covers; it was not probed (a lead nobody has checked).

**Mechanism 3, ruled, with what it overturns (the ruling's paragraph, copied).** `§1985:IV.4.3.8` as amended reads: "Unless otherwise specified by
the rules for a statement, any subscripting and reference modification are evaluated only once as the first
operation of the execution of that statement." (cite.py OK; the sentence is Amendment 1's, X3.23a-1989, applied in
place in the transcription, kb/Work PB5045.) MOVE CORRESPONDING does specify otherwise: "The results are the same as
if the user had referred to each pair of corresponding identifiers in separate MOVE statements"
(`§1985:VI.6.19.4 GR1`), so its per-pair evaluation at 85 stands. ADD and SUBTRACT CORRESPONDING specify nothing, so
the general sentence governs them: once, at the start. `docs/conformance/3/D-CORR85.md` (kb/Work PB5185) held that
for ADD and SUBTRACT "the standard leaves the choice to the implementor" and took GnuCOBOL's per-pair behaviour.
Its premise is wrong for the amended text, and where the standard controls CLAUDE.md rule 1 never reaches GnuCOBOL.
So: at `--std 85` ADD and SUBTRACT CORRESPONDING evaluate the group operands' subscripts once; D-CORR85 is corrected
for those two verbs and keeps MOVE; and the two cases that pin the per-pair result
(`pb5185_add_corresponding_subscript_per_pair`, `pb5185_subtract_corresponding_subscript_per_pair`) are re-derived
with the fix.

**What the fix must correct.** The determination `docs/conformance/3/D-CORR85.md` (for ADD and SUBTRACT; MOVE stays) and the two conformance cases `pb5185_add_corresponding_subscript_per_pair` and `pb5185_subtract_corresponding_subscript_per_pair`, which pin the per-pair result. This note edits none of them: the fix does, in its own change set.

**The checker's reasoning.** ADD's rules (`§1985:VI.6.6.4 GR3`, `§1985:VI.6.4.3`) state no exception for format 3; MOVE CORRESPONDING's "separate MOVE statements" sentence is MOVE's alone. D-CORR85 says ADD and SUBTRACT CORRESPONDING "at 1985 print no statement about identification time" and so falls back to GnuCOBOL; that premise is false, since the `§1985:IV.4.3.8` sentence is that statement. Under the 6.4.6 multiple-results model a sending operand is also part of the initial evaluation, so that model gives 200 as well. I ran `addc.cob` at `--std 85` with the tracked probe runner: `AA=100 JJ=2 BB=400`.
