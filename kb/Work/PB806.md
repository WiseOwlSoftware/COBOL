# PB806 — OPEN — the directive operand column is per-ROW and three of these directives share a row

Filed 2026-09-09 by the registrar from the PB794 implementer's report (§10, N1), which was never filed as a
note. Re-measured on main at `d497f3c7` with this worktree's own build, and extended: the report named
`>>ELSE` / `>>END-IF` / `>>END-EVALUATE`; the row-level cause and the two inventory rows are added here.

## Reproduced on main

`cc_else_junk.cob` (fixed form; the directive indicator is in column 8 — column 7 is the indicator area):

```cobol
       PROCEDURE DIVISION.
       MAIN-PARA.
       >>IF 1 = 1
           DISPLAY "A".
       >>ELSE JUNK
           DISPLAY "B".
       >>END-IF JUNK
           STOP RUN.
```

`cobol --std 2023 cc_else_junk.cob` → **exit 0, zero diagnostics.** `cc_eval_junk.cob`, the same shape with
`>>EVALUATE TRUE` / `>>WHEN 1 = 1` / `>>END-EVALUATE JUNK` → **exit 0, zero diagnostics.**

## The rule

`cite.py --check 7.3.16.2 "END-IF"` → **OK, §7.3.16.2** (General format). The whole printed format is:

```
>> IF constant-conditional-expression-1 [ text-1 ]
[ >> ELSE [ text-2 ] ]
>> END-IF
```

`>>ELSE` takes no operand at all (text-2 is a separate SOURCE LINE, not part of the directive line — §7.3.16.4
GR1: *"Text-1 and text-2 are not part of the IF compiler directive line"*, and §7.3.16.3 SR3/SR5 say `>>ELSE`
and `>>END-IF` *"shall begin on a new line and shall be specified entirely on that line"*). `>>END-IF` takes
none. `cite.py --check 7.3.13.2 "END-EVALUATE"` → **OK, §7.3.13.2**: `>> END-EVALUATE` closes the format with
no operand either.

What may follow a directive is closed by §7.3.3 — `cite.py --check 7.3.3 "an optional inline comment"` → **OK,
§7.3.3 3)**:

> 3\) When the reference format is fixed-form, a compiler directive shall be written in the program-text area
> and may be followed only by space characters and an optional inline comment.

and SR4 says the same for free-form. **Only spaces and an inline comment.** `JUNK` is neither, so the three
lines above are non-conforming source this compiler accepts in silence: `under_rejects`, `silent`.

## The code site, and why this is not a widening of [[PB794]]

[[PB794]] put the operand question at the ONE recognition point —
`src/Cobol.Net.Frontend/Preprocessor/ConditionalCompilationProcessor.cs:213`:

```csharp
CompilerDirectiveCatalog.Check(keyword, _edition, sink);          // may this word head a >> line?
CompilerDirectiveCatalog.CheckOperand(keyword, rest, _edition, sink);   // may these words follow it?
```

and gave every `constructs.json` directive row a `directiveOperand` column that is a TOTAL partition of
`words` / `text` / `stage`. That works because the column keys on the ROW — and **the row is the DIRECTIVE
FAMILY, not the word**:

```json
"if-directive-2002":       { "form": "stage", "owner": "ConditionalCompilationProcessor", … }
"evaluate-directive-2002": { "form": "stage", "owner": "ConditionalCompilationProcessor", … }
```

`form: stage` is a declared no-op — *"a downstream stage parses this operand"* — and it is TRUE for one word of
each row and FALSE for the others. `if-directive-2002` covers `>>IF` (operand: a constant-conditional-
expression, genuinely parsed by `EvaluateCceText`), `>>ELSE` (no operand) and `>>END-IF` (no operand);
`evaluate-directive-2002` covers `>>EVALUATE` (a selection subject, parsed), `>>WHEN` (a selection object,
parsed) and `>>END-EVALUATE` (no operand). The switch below reads `rest` in the parsing arms and **ignores it
entirely** in `case "ELSE":` (`:225`), `case "END-IF":` (`:232`) and `case "END-EVALUATE":` (`:269`) — those
arms only push, flip or pop a `Frame`.

⛔ **So the fix is a shape change, not a value change**: one row, three words, three different operand shapes,
and no column on the row can say that. That is why this is its own item and not a wider [[PB794]] — filing it
as "set `operandRequired: false`" would be a value edit to a column that cannot express the fact.

## Shape of a fix

**Make the operand column per-WORD.** The catalog already knows every spelling that can head a `>>` line
(`CompilerDirectiveCatalog`), and PB794's own `directiveOperand` vocabulary (`words` with a closed choice /
`text` with `operandRequired` / `stage` with an owner) is already expressive enough for each of the three
words separately — `>>ELSE`, `>>END-IF` and `>>END-EVALUATE` are `{"form": "text", "operandRequired": false,
"operandPermitted": false}`, the shape [[PB794]] already needed for the bare `>>LISTING` case and did not have
a word to hang on. The choice is between splitting the row per word and adding a per-word sub-map to the row;
**prefer whichever makes the NEXT multi-word directive automatic** (CLAUDE.md rule 5) — today's population is
two rows and six words, and `>>WHEN OTHER` is a seventh spelling with yet another shape.

Pin it with the catalog-DERIVED witness [[PB794]] already built —
`CompilerDirectiveCatalogDriftTests.EveryClosedOperandDirective_DiagnosesAMalformedOperand` drives every
closed-operand row through the real stage with a malformed spelling built from its own row, plus its
complement. Extend it to iterate WORDS rather than rows, prove it RED on `>>ELSE JUNK` first
(`feedback_green_gates_arent_evidence`), and keep the complement so a checker that rejected everything could
not pass.

## Sweep the fixer must do

- ⛔ **Every word of a multi-word directive row, not the three named here.** `>>WHEN` and `>>WHEN OTHER` share
  `evaluate-directive-2002` with `>>EVALUATE`; `>>WHEN OTHER`'s operand shape (`OTHER` and nothing else) is a
  fourth shape on that one row. Derive the population from the catalog rather than from this note's list.
- **The `stage` arm generally.** `form: stage` currently means BOTH *"a stage parses this and will diagnose"*
  and *"nobody checks"*, and only the row's prose distinguishes them. Any fix that leaves that ambiguity intact
  leaves the next unchecked stage-owned operand silent — `feedback_a_dead_lookup_is_also_unverified`.
- **A trailing inline comment must still be accepted** on all six spellings (§7.3.3 SR3/SR4). [[PB794]]'s
  `CompilerDirectiveLine` already strips it quote-aware; re-use that, never a second slicing.

## Inventory rows

`FMT-7.3.16.2` (IF directive) and `FMT-7.3.13.2` (EVALUATE directive) are both **GAP** on main and are claimed
here. Neither can go CONFORMS while three of the six words in those two formats accept operands the format does
not write; conversely, a fix that also implements `>>IF` / `>>EVALUATE` / `>>WHEN` operand syntax is what closes
them. No verdict changes with this filing — the rows were already GAP and no `record_verdicts` batch is needed.
