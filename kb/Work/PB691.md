# PB691 — LANDED — the third arm of a drop fixed twice

Found 2026-09-05 by the `PB334` implementer (report §"New defects" 1) by a MECHANICAL sweep over `CobolIO.g4`: for
every I-O statement rule, which sub-rules does each binder arm consume? `writeStatement`'s `writeInvalidKey` is
consumed by the keyed arm only. Probe `<a9d94900 scratch>\PB691\probe\seqwik.cob` (ORGANIZATION SEQUENTIAL,
`WRITE SQ-REC INVALID KEY DISPLAY "W-IK" NOT INVALID KEY DISPLAY "W-NIK" END-WRITE`) printed `DONE 00` at every
edition and under `--permissive`: compiled clean, neither branch ran, no diagnostic on either severity axis.

## The rule

§14.9.51.3 SR2 (`cite.py --check 14.9.51.3 "If the organization of the write file is sequential, format 1 shall be
specified"` → OK 2)), and §14.9.51.2 Format 1 has no INVALID KEY bracket. ⚠ **That diagram is load-bearing — the
whole prohibition is read off it — and the OCR's known bias is toward FALSELY RESTRICTIVE syntax, i.e. exactly
this direction, so it was RENDERED, not trusted:** `scripts/render-spec-page.py 815 816` (printed pages 785–786).
Format 1 (sequential) carries WRITE / FROM / BEFORE-AFTER ADVANCING / retry-phrase / WITH LOCK / the AT
END-OF-PAGE group / END-WRITE and **no INVALID KEY at all**; Format 2 (random) carries the
`INVALID KEY … | NOT INVALID KEY …` choice group and no ADVANCING. The transcription is faithful here. It is a
better citation than READ's, whose
rule is a chain (§12.4.5.5.2 SR2 → §14.9.30.3 SR8 → §14.9.30.4 GR19). The program is illegal source and §4.2.2
requires the indication; under `--permissive` the bind must stand and mean something — §9.1.14's final rule item 2
runs the NOT INVALID KEY imperative on a successful completion
(`cite.py --check 9.1.14 "If the I-O status indicates a successful completion, control is transferred to the end
of the input-output statement or to the imperative-statement specified in the NOT INVALID KEY phrase if it is
specified"` → OK 2)).

## Landed

**The screen.** `SequentialIoBinder.BindWrite`'s sequential leg (after the `keyedIo.BindWrite` reroute) calls
`ctx.Validation.ScreenForbiddenPhrase(true, …, "WRITE", "a file with sequential organization",
"ISO §14.9.51.3 SR2")` — the ONE severity seam, `COBOLNET1720`, **no new diagnostic code** (COBOLNET1854–1855 stay
free). Measured after: `error COBOLNET1720` at `--std 85/2002/2014/2023` strict; `warning` + `W-NIK` + `DONE 00`
under `--permissive`.

**The bind, which the screen alone would not have given.** `BoundWrite` gained `KeyedInvalidKey? InvalidKey` and
`SequentialIoEmitter.EmitWrite` renders it, because *tolerating* a phrase obliges the compiler to give it the
meaning §9.1.14 states. The INVALID arm is provably dead here — §9.1.13.5's four invalid-key statuses `'21'`–`'24'`
each name a relative or indexed file — but the NOT INVALID arm is **live**, and dropping it was the wrong-answer
half of the defect. The status is snapshotted from the connector immediately after the write, before the FILE
STATUS store and the USE hook, so a declarative or a phrase body writing the same file cannot move it; the local
is emitted only when the phrase is present, so a legal Format-1 WRITE renders unchanged.

**One §9.1.14 renderer.** `EmitInvalid` moved from `KeyedIoEmitter` (private) to `SequentialIoEmitter` (the
declared home of the file-I/O common services `KeyedIo` consumes) and its four keyed call sites now read
`SeqIo.EmitInvalid(…)`. `KeyedIoBinder.KeyedInvalidPhrase` became `internal` for the same reason. A second copy on
the sequential side is exactly the shape that produced this defect.

**The sibling the sweep found, fixed the same way.** `SequentialIoBinder.BindRewrite` — PB144's §14.9.35.3 SR2
first arm — screened the phrase but still **dropped** it, on the recorded reasoning that "there is no `'2x'`
invalid-key condition for it to carry". True of the INVALID arm, false of the NOT INVALID arm. Measured before:
`--permissive` printed `DONE 00` and never `R-NIK`. `BoundRewrite` gained the same member and
`SequentialIoEmitter.EmitRewrite` the same render. `BoundStores` walks the new lists on both arms, as it already
did for `BoundKeyedWrite`/`BoundKeyedRewrite`; `UsageCollectionPass` and `EcBinder` need no change, because nested
phrase bodies reach them through the **generated** `BoundStatementTree.StatementChildren` (which reads every
property via the semantic model, so the new member is walked by construction) and `BoundWrite`/`BoundRewrite` were
already in `EcBinder`'s I-O enumeration.

**The rest of the sweep, for the record.** `deleteStatement` on a sequential *organization* is a hard
`COBOLNET0865` with no bind (§14.9.10.3 SR1); `startStatement` on one is a loud `BoundUnsupported`; the keyed
DELETE (sequential *access*) and keyed REWRITE (relative + sequential access) arms already screened **and** bound.
`readStatement`'s sequential `readInvalidKey` is [[PB334]]'s, in flight on its own branch, and was deliberately
not touched here.

**Goldens.** `tests/conformance/negative/write-invalid-key-sequential-org.cob` (PB691N1) and
`write-not-invalid-key-sequential-org.cob` (PB691N2, the NOT-alone grammar alternative — the arm a `--permissive`
program actually writes), both `*> reject-at: 85 2002 2014 2023`, both `.err` = `COBOLNET1720`, both registered
in the negative manifest. Four behavioural tests in `SequentialFileIoSpecTests`: the WRITE NOT-arm at all four
editions under `--permissive` (expected `W-NIK\nW=00` — status `'00'` by §9.1.13.2 item 1, the NOT arm by
§9.1.14 item 2, the INVALID arm silent by §9.1.14's "the INVALID KEY phrase is ignored, if specified"), the
REWRITE twin, the NOT-alone spelling, and the strict rejection swept across all four editions.

**⛔ The D9 corpus sweep was RUN, not reasoned.** A record-name → FD → SELECT-organization mapping over all 459
NIST programs finds **77** `WRITE … INVALID KEY` sites and **zero** of them on a sequential-organization file
(every one is INDEXED or RELATIVE). All 459 then compiled at `--std 85` with the screened compiler and **not one**
drew `COBOLNET1720`; the detector was proved able to report it first, against a seeded program. The `~Nist`
conformance leg is byte-identical across the change: `Passed! Failed: 0, Passed: 352, Total: 352`, before and
after.

`SR-14.9.35.3-2` gains the NOT-arm behavioural test-ref; `GR-14.9.30.4-28`, `GR-14.9.41.4-6` and
