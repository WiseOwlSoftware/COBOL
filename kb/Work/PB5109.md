# PB5109 - a shared file never holds a branch

**Owner (2026-11-10):** "Why the fuckery are we STILL holding because two things edit the same file? That is what MERGE is
to resolved." "This is at least the 5th time I've said that." "Why the fuck are you still trying to second-guess git? If a
merge conflict occurs, we can address the proper change then."

**What happened.** On 2026-11-09 the landing lane held two branches with exit 16, DRIVER FILE QUEUED, behind #1444:
notes-pb5099 and worktree-wf_14a80b82-683-1 (PB5060, reviewed CLEAN). `enqueue.driver_file_holders` (kb/Work PB3642) held
a branch whenever another open pull request entering the merge queue changed a file that a merge driver covers, because
GitHub builds merge groups with plain git and no driver. It judged by file NAME, never by an actual merge. Worse, Mythos
found that #1444 never touched PB5099.md or PB5060.md at all: #1444 has 141 files, GitHub lists the first 100
(`FILES_LISTED`), and the guard read a cut-off list as "changes every driver file". So both holds were false.

**The decision (owner).** Nothing predicts a merge conflict. A branch is stamped and queued whatever other open pull
requests change. If a merge group does conflict, GitHub bounces the pull request, the landing lane classifies the red as
MERGE, and a finisher fixes it then (the existing bounce path, MANDATORY-PRACTICES L12).

**Fix (landed with this note).** Deleted `enqueue.driver_file_holders`, `EXIT_DRIVER_FILE_QUEUED` (exit 16), the
queue-entry lock that existed only to make the guard's look race-free (`QUEUE_ENTRY_LOCK_NAME`, `take_queue_entry_lock`,
`land(entry_wait_s=)`), `land_lane.driver_files_free` and exit 16's WAITS entry, with their self-tests. New self-test: a
branch whose driver-merged files an open pull request IN the queue changes too is stamped and queued, and no file list is
asked for. Shape checks in both files refuse a file-overlap reader or a queue-entry lock coming back. The docs that
described exit 16 (DESIGN-orchestrator-loop.md, DESIGN-test-build-ci.md, the enqueue unit, the workstream skill's landing
reference and MANDATORY-PRACTICES L12) now say a shared file never holds a branch.

**Sibling still standing.** `landing_check.py` refuses two in-flight branches that edit the same MEMBER (PB2118, PB4452).
That check is member-level, not file-level, so it is not this defect; whether it should also give way to the merge is
an owner question, not a change made here.
