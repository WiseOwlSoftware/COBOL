# PB434 — two bans that belong in the one ban site, and are not in it

## 1. THE MECHANISM

`EcBinder.ExceptionPerform.cs#CheckCrossStatementBans` (`:237-304`) already OWNS the per-region bans for this
statement. It builds the regions once (`:240-246`) — region A = imperative-statement-1, region C = the WHEN
phrases, region D = the WHEN phrases plus the FINALLY body — and then walks each with `Descendants<T>`:

    var finallyBody = p.performFinally() is { } f ? f.statementBlock() : [];          // :244
    var regionD = whenBodies.Concat(finallyBody).ToList();                            // :245
    …
    foreach (var _ in whenBodies.SelectMany(Descendants<Core.GoToStatementContext>))  // :296 — region C, GO TO
        ctx.Edition.Error("COBOLNET1608", …);
    foreach (var _ in regionD.SelectMany(Descendants<Core.RaiseStatementContext>))    // :301 — region D, RAISE
        ctx.Edition.Error("COBOLNET1611", …);

**GR16's ban is not there.** Region D already contains the FINALLY body and is already being walked; the missing
screen is a SECOND predicate over the list `:245` builds, restricted to `finallyBody`. Nothing screens
imperative-statement-5 for the transfer-out statements the rule forbids — GO TO, EXIT PARAGRAPH, EXIT SECTION,
GOBACK, EXIT PROGRAM — although every one of them is statically detectable in the walk already running over that
subtree. The project's own F3 design doc calls this requirement "a syntax rule"
(`docs/rearchitecture/evidence/PHASE-13-c5-perform-format3-DESIGN.md:333`) and the ban table has no row for it —
so the doc and the code disagree.

**SR8's `with` half is enforced only structurally, by the grammar's shape.** `CobolControlFlow.g4:113-116` gives
`UNTIL EXIT` its own alternative with no `WITH TEST` prefix, and the in-line comment there claims exactly that
("SR8 forbids TEST here"). Nothing anywhere implements the `or UNDER` half: `BindPerformControl`'s EXIT arm
(`ControlFlowBinder.cs:345-351`) returns `PerformForever()` with no ancestor walk and no enclosing-PERFORM state,
and `VersionConformancePass.VisitPerformUntil` (`:633`) — the only other reader of that alternative — checks the
EDITION, not the nesting. **Where the stopping point falls decides the fix's shape:** "under" means within the
PERFORM's RANGE, and GR1 puts statements reached by a transfer of control in the range, not merely lexically
nested ones — so a parse-tree ancestor walk catches only two of the three shapes.

## 4. THE CODE SITE AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.ExceptionPerform.cs:237-304` — the ONE ban site;
  `:244-245` builds `finallyBody` / `regionD`; `:296` and `:301` are the two existing predicates
* `src/Cobol.Net.Frontend/Grammar/Core/CobolControlFlow.g4:113-116` — `performUntil`, SR8's structural half
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:345-351` — the UNTIL EXIT bind arm
* `src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs:633` — `VisitPerformUntil`, edition only
* `docs/rearchitecture/evidence/PHASE-13-c5-perform-format3-DESIGN.md:333` — the doc that already states GR16's
  ban and must gain its table row in the same change set (rule 2)

**GR16** is small and belongs where its siblings are: one new predicate over `finallyBody` at `:301`'s
neighbourhood, one new diagnostic in the `COBOLNET1608` / `COBOLNET1611` family. Two scope decisions the fixer
must make deliberately rather than by omission:

* **EXIT PERFORM is expressly permitted by GR16's third sentence and must stay permitted.**
* **STOP RUN terminates the run unit rather than transferring control within it** and is the one member of the
  family that deserves an owner call before it is banned.

**SR8's "under"** is the expensive half and the reason this note is not two notes. `PerformForever` is produced
by a binder that has no idea what encloses it, and the enclosing relation the rule needs is dynamic. The
structural answer is to give the binder the enclosing-PERFORM context it lacks — an ambient "innermost enclosing
PERFORM control shape" that the inline path can push/pop lexically, PLUS the procedure-table range relation for
the out-of-line case. ⛔ A fix that walks only the parse tree closes (a) and (b) and leaves (c) open: that is the
smallest diff, not the right shape.

## 5. THE SIBLING SWEEP

* **Every other region-D obligation.** Region D exists and holds exactly one predicate (RAISE). Read GR21 and
  every §14.9.28.3 rule that scopes to imp-2..5 and check which of them have a row in this method.
* **Every other "or under" / "within the range of" rule in the standard.** SR8 is not the only rule whose scope
  is a PERFORM's RANGE rather than its lexical extent; whatever mechanism answers "is this statement under that
  PERFORM" will serve them, and building it as a one-off for SR8 wastes it.
* **The bare-`COBOL0001` enforcement pattern.** SR8's enforced half is delivered as a parse error naming no
  rule. Sweep for other syntax rules the grammar enforces STRUCTURALLY: each one is a place where a user gets
  "no viable alternative" instead of a rule citation, and the F3 design's superset posture (bind and diagnose
  specifically, rather than fail to parse) is the project's stated preference.
* **Edition sweep for GR16.** Format 3 is 2023-only (Annex E.3.3 item 36), so a new GR16 diagnostic cannot fire
  below 2023 — but confirm the gate ordering, so a pre-2023 program gets `COBOLNET0900` and not the new code.

## 6. ROWS

* `GR-14.9.28.4-16` — PARTIAL. Sentences 1, 3 and 4 conform and were re-measured (the `__f3fin{n}` label sits
  before the FINALLY block and after the frame pop, so a normal fall-through, an EXIT PERFORM in imp-1 and an
  EXIT PERFORM in a handler all arrive at imp-5; an EXIT PERFORM inside imp-5 emits the jump to `__f3end{n}`).
  Sentence 2 is not enforced — measured above.
* `SR-14.9.28.3-8` — PARTIAL. The "with … TEST BEFORE/TEST AFTER" arm is enforced structurally by the grammar
  (measured); the "or under" arm is not enforced in any of its three shapes, and the out-of-line shape needs the
  range relation rather than an ancestor walk.
