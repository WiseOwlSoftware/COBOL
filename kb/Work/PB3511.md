# PB3511 — fall-off-the-end inside a PERFORM returns instead of the implicit GOBACK

## Scenario (fuzz program fz00481, `WE_HANG:14.9.17`)

Confirmed on a fresh build of origin/main at fd407980f, `--std 2014 --source-format free`. GnuCOBOL printed one line and
exited 0; WiseOwl printed two lines and then looped forever (the loop is the CONSEQUENCE: the wrong return re-entered
the main paragraph's later PERFORMs, one of which is a genuine infinite loop by the standard). On main the program still
prints two lines and hangs.

Related: PB1148 (the implicit return firing on a GO TO, landed), PB3491 (GO TO … DEPENDING out of range, landed), PB405
(the one dispatcher exit).

### Reduced repro

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. MIN481.
PROCEDURE DIVISION.
MAIN-PARA.
    PERFORM P1
    DISPLAY "AFTER PERFORM"
    STOP RUN.
P1.
    DISPLAY "P1"
    GO TO P3.
P2.
    DISPLAY "P2".
P3.
    DISPLAY "P3".
```

WiseOwl (main fd407980f): `P1`, `P3`, `AFTER PERFORM`, exit 0.
GnuCOBOL 3.2 (`cobc -x -free -std=cobol2014`, WSL): `P1`, `P3`, exit 0.

## Expected (spec)

Each citation was re-run through `python scripts/spec/cite.py --check` on 2026-10-22 and returned OK.

- §14.9.28.4 GR1 (OK): "The range of a PERFORM statement consists logically of all those statements that are executed
  as a result of executing the PERFORM statement through execution of the implicit transfer of control to the end of the
  PERFORM statement." The GO TO leaves P1; P1's end (the exit of the range) is never reached, so the implicit return to
  the PERFORM never happens.
- §14.6.3 item 3 (OK): "There is also no next executable statement after the last statement in a source element when
  the procedure in which it appears is not being executed under the control of some other COBOL statement in that source
  element … In these cases, an implicit GOBACK statement without any optional phrases is executed." P3 is not under the
  control of the PERFORM (its range is P1 alone), so after P3's last statement the program executes an implicit GOBACK:
  expected output is exactly `P1` then `P3`, and "AFTER PERFORM" is never printed.

## Mechanism (read in `src/Cobol.Net.Compiler/CodeGen/DispatchEmitter.cs`, about lines 170 to 197)

Every `__Dispatch(startPc, exitPc)` is `while ((uint)__pc < (uint)__N) { switch (__pc) { … } … } return __pc;`. When
control runs past the LAST paragraph (`__pc == __N`) the loop ends and the method RETURNS `__pc`: right for the
outermost call (`Main` runs `__Dispatch(EntryPc, topExit)` and falls through as the implicit GOBACK) but wrong for a
nested call made by a PERFORM, because that return is read as the PERFORM's completion and execution resumes after the
PERFORM statement. The dispatcher has no notion of "fell off the end of the source element" distinct from "reached the
exit of the range".

## Fix shape (for the implementer)

Root-cause shape to require (rules 4 and 5): a nested dispatch that reaches `__N` must execute the implicit GOBACK of
§14.6.3 (the same path an explicit GOBACK takes: the `ProgramReturn` signal `Main` catches), never return to its
performer. The same question exists for every nested dispatch form: a PERFORM inside a declarative's `__RunUse`, an OO
method's `__MDispatch`, a function, and a program whose last paragraph is reached inside a PERFORM THRU. Sweep all of
them; add goldens for the program case and for a method/function case.

## Second witness: PERFORM THRU with the exit never reached (slice B, fz04138)

Slice B found `OUTPUT_DIFFERS:14.9.28` (fz04138) with NO GO TO: `PERFORM P2 THRU P1` where P1 is written BEFORE P2 and P2 is
the last paragraph of the program. Same mechanism as above (`DispatchEmitter` returns `__pc` at `__N`). Repro, copied
verbatim from `E:\Temp\claude\E--COBOL\6152fc0c-4ad8-43af-8091-47da881f4100\scratchpad\adj\B\probes\src\perfthru.cob`:

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. PERFTHRU.
PROCEDURE DIVISION.
MAIN-PARA.
    PERFORM P2 THRU P1
    DISPLAY "AFTER PERFORM"
    STOP RUN.
P1.
    DISPLAY "P1".
P2.
    DISPLAY "P2".
```

WiseOwl (main fd407980f) prints `P2` and then `AFTER PERFORM`. GnuCOBOL prints only `P2` (with its
`-Wsuspicious-perform-thru` warning).

Spec (each re-run through `cite.py --check` on 2026-10-22):
- §14.9.28.4 GR6 (OK): "There is no necessary relationship between procedure-name-1 and procedure-name-2 except that a
  consecutive sequence of operations is to be executed beginning at the procedure named procedure-name-1 and ending with
  the execution of the procedure named procedure-name-2." The findings file paraphrased this as "procedure-name-2 may
  precede procedure-name-1"; that wording is not in the standard (the check failed on it), so the note quotes the real text.
- §14.9.28.4 GR5 b) (OK): "If procedure-name-2 is specified, the return mechanism is after the last statement of
  procedure-name-2."

Control runs from P2 off the end of the program and never reaches the return point after P2. The adjudicator's caveat,
recorded as two readings of §14.6.3 item 3:
- Reading 1: item 3 is worded for a procedure "not being executed under the control of some other COBOL statement"; P2 IS
  in the range of the PERFORM, so item 3 does not fire and the standard names no next executable statement at all.
- Reading 2: running off the end of the source element is the implicit GOBACK of item 3 regardless.
Under either reading, returning to the PERFORM and printing `AFTER PERFORM` contradicts GR5 b), because the return
mechanism sits after P2's last statement and execution never gets there. Which reading governs is not decided here; the
implementer takes it to the adjudication lane if the choice changes the expected output beyond "no AFTER PERFORM".

## Golden to require

The reduced program above with expected output `P1`/`P3` and exit 0 (spec-derived, matches GnuCOBOL); a second case where
the fall-off happens two PERFORM levels deep; the fz00481 shape (its first line only, then exit 0); and a third case, the
`PERFORM P2 THRU P1` program of the second witness, with expected output `P2` and no `AFTER PERFORM`.
