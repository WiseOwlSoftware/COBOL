# PB46 — HALF LANDED — the BY CONTENT operand is one rule written twice, and one copy is now right

> ⚙ **FOUND WHILE SWEEPING [[PB45]], AND THE FIRST READING OF IT WAS WRONG.** The PB45 peel sweep put
> `FUNCTION SQRT(W-Z)` into seventeen statement shapes; `CALL "SUB" USING FUNCTION SQRT(W-Z) W-Z` came back
> `COBOL0001: no viable alternative at input 'FUNCTION'`. The obvious filing — "CALL USING refuses a
> function-identifier, same family as the arithmetic verbs" — **is false**, and checking the premise before the
> rule is what caught it ([[feedback_validate_the_premise_not_only_the_rule]]).

## ⛔ THE SHAPE I MEASURED IS ILLEGAL SOURCE — THE REJECTION IS CORRECT

§14.9.4.2 **Format 1** writes USING as `[BY REFERENCE] {identifier-2}… | BY CONTENT {identifier-2}…` — both arms
are identifier-2, and §14.9.4.3 **SR3** confines identifier-2 to "an address-identifier or a data item defined in
the file, working-storage, local-storage, or linkage section", while **SR5** makes a BY REFERENCE identifier-2 a
RECEIVING operand. A function's returned value lives "in a temporary elementary data item" (§15.4), which is in
none of those sections, and §8.4.3.2.3 SR1 bars a function-identifier as a receiving operand outright. **So
`CALL "SUB" USING FUNCTION SQRT(X)` is not legal COBOL and must be rejected.** Only the DIAGNOSTIC is poor (a raw
`COBOL0001 no viable alternative`, uncited) — that is a separate, lesser matter.

## ⛔ THE REAL DEFECT IS NARROWER AND IS IN A DIFFERENT ARM — BY CONTENT

Every citation `cite.py --check`ed. **CALL Format 2** (§14.9.4.2, program-prototype) and **INVOKE**
(§14.9.23.2) both write their operand group as:

| phrase | the standard's operands | the grammar's rule |
|---|---|---|
| `[BY REFERENCE]` | `identifier-2` / `identifier-3` **, or `OMITTED`** | `dataReference` |
| **`[BY CONTENT]`** | **`arithmetic-expression-1` · `boolean-expression-1` · identifier · literal** | `(dataReference \| literal)` |
| `[BY VALUE]` | `arithmetic-expression-1` · identifier · literal | `arithmeticExpression` ✅ |

`callByContent : BY? CONTENT (dataReference | literal)` and `invokeArgument`'s `BY CONTENT (dataReference |
literal)` **omit `arithmetic-expression-1` and `boolean-expression-1`**, which BY VALUE — the very next line in
the same grammar file — gets right. So this is rejected in both verbs and accepted one phrase over:

```cobol
CALL "SUB" AS PROTO USING BY CONTENT FUNCTION SQRT(W-Z)     *> arithmetic-expression-1: legal, refused
CALL "SUB" AS PROTO USING BY CONTENT (W-A + 1)              *> arithmetic-expression-1: legal, refused
INVOKE OBJ "M" USING BY CONTENT FUNCTION SQRT(W-Z)          *> same, refused
```

**Root cause is the PB45 shape exactly** — ONE operand rule written once per verb, and every copy short in a
different way ([[feedback_one_rule_one_place]], [[feedback_two_arm_dispatch]]: the BY VALUE arm was fixed/written
correctly and the BY CONTENT arm beside it never was).

## ⚠ TWO OVER-ACCEPTANCES IN THE SAME RULES — do not fix one direction only

- `invokeArgument`'s bare arm is `dataReference | literal`, but a bare operand means BY REFERENCE implied, and
  BY REFERENCE admits only `identifier-3 | OMITTED` — **a literal is wrongly accepted there.**
- **`OMITTED` is missing from `invokeArgument`'s BY REFERENCE arm** although §14.9.23.2 prints it (the CALL side
  has it). Legal source refused.

## ▶ WHAT TO CHECK FIRST

⚠ **Derive CALL Format 1 vs Format 2 separately — they are NOT the same rule**, and `callArgument` currently
serves both. Format 1 has NO BY VALUE at all and admits only identifier-2 in both of its arms; Format 2 is the
one with the expression operands. A single flattened `callArgument` cannot express that, so check whether the
by-format split is the restructuring this needs rather than four more alternatives (CLAUDE.md rule 5).
⚠ Sweep `procedureDivisionUsing` / the DATA DIVISION `USING` clause for the same short copy before fixing one.

## ▶ PREMISE RE-VERIFIED FROM THE GENERAL FORMAT (2026-08-06) — and it adds a distinction the note lacked

Read off the rendered §14.9.4.2 diagram rather than the prose, because a general format is a DIAGRAM and this
note turns on exactly what its BY CONTENT branch admits:

- **CALL Format 2** (program-prototype) BY CONTENT: `arithmetic-expression-1` · `boolean-expression-1` ·
  `identifier-4` · `literal-2`. BY VALUE: `arithmetic-expression-1` · `identifier-4` · `literal-2`.
- **CALL Format 1** (program-name) BY CONTENT: `{ identifier-2 } …` **ONLY**.

The grammar has ONE rule for both — `callByContent : BY? CONTENT (dataReference | literal)` — so it is
simultaneously TOO NARROW for Format 2 (no expression) and, if widened naively, TOO WIDE for Format 1.

⛔ **AND THE FORMATS ARE NOT DISTINGUISHABLE AT PARSE TIME.** Both are `CALL {identifier|literal} USING …`; what
selects Format 2 is whether the called name resolves to a program-prototype declared in the REPOSITORY — a
SEMANTIC question, exactly the D2 shape. So this is the repo's parse-wide/bind-narrow doctrine: widen
`callByContent` (and `invokeArgument`'s BY CONTENT) to admit the expression operands, and let the BINDER reject
an expression under BY CONTENT when the call is Format 1. A grammar-only fix would trade one rejection of legal
source for one acceptance of illegal source.

⚠ Do NOT widen by adding `arithmeticExpression` alone: it already subsumes `dataReference` and numeric literals,
so the alternation needs care to avoid an ambiguity with the existing `literal` arm, and `boolean-expression-1`
is a separate channel (`booleanExpression`) that the BY VALUE arm does NOT carry — the two phrases differ, and
the note's table is right that only BY CONTENT takes a boolean expression.

## ⚙ MEASURED 2026-08-06 — the note is right that this rejects legal source, and wrong twice about the details

**① THE CALL HALF IS UNREACHABLE, so it is not the actionable part.** §14.9.4.2 **Format 2** is the
program-prototype CALL, and the REPOSITORY paragraph grammar has entries for `FUNCTION`, `CLASS` and
`INTERFACE` **and none for `PROGRAM program-prototype-name`** — `DiagnosticCatalog` says so out loud
("signature matching needs the program-prototype registry (P13)"). So no source this compiler can parse selects
Format 2, and widening `callByContent` would ONLY make illegal **Format 1** source parse: Format 1's BY CONTENT
is `{ identifier-2 } …` and nothing else (read off the rendered general format). **Trading a rejection of legal
source for an acceptance of illegal source is not a fix.** The CALL half is BLOCKED on the prototype registry,
not on grammar work — [[feedback_validate_the_premise_not_only_the_rule]], the same shape as PB46's own opening
correction.

**② THE INVOKE HALF IS REAL, AND THE SYMPTOM IS NOT THE PREDICTED PARSE ERROR.** §14.9.23.2 has ONE format and
its BY CONTENT branch admits `arithmetic-expression-1 | boolean-expression-1 | identifier-5 | literal-2`
(rendered format), while `invokeArgument` admits `(dataReference | literal)`. Measured:

```
INVOKE O "TAKE" USING BY CONTENT N + 1.
  ⛔ COBOLNET0828: INVOKE "TAKE": 2 USING argument(s) for 1 formal parameter(s) … GR3
INVOKE O "TAKE" USING BY CONTENT N.        ✅ TAKE GOT=000E
```

It does not fail to parse — **it silently splits into TWO arguments** and surfaces as an arity diagnostic about
a rule the program does not violate. A wrong count reported against §14.9.23.4 GR3 is a worse failure than a
parse error, because the message sends the reader at the method signature.

## ▶ THE REMAINING WORK IS FOUR LAYERS, and that is why it is not a grammar one-liner

1. **Grammar** — `invokeArgument`'s BY CONTENT to `(nonNumericLiteral | arithmeticExpression)`; `nonNumericLiteral`
   FIRST, since `arithmeticExpression` already subsumes `dataReference` and numeric literals.
   ⚠ `boolean-expression-1` needs the `{boolExprAhead()}?` predicate, the proven `primaryCondition` pattern —
   `booleanExpression`'s leaf is `valueOperand`, so an unguarded alternative is ambiguous with the arithmetic one.
2. **`BoundInvokeArg`** — it carries `Place? Source, string? NumericLiteral, string? StringLiteral` and has **no
   slot for a computed expression**.
3. **`OoBindInvokeArg`** — a new arm, with §14.8.2.3.3's per-formal-category CONTENT conformance (COMPUTE rules
   for a numeric formal) applied to an expression rather than to a literal or an item description.
4. **`OoEmitter`** — three per-category arms (`OoEmitter.cs` ~715/721/726/751) each branch on
   `Source` vs `NumericLiteral` vs `StringLiteral`; each needs the expression case.

⚠ Do NOT land 1 alone: it would turn today's misleading arity error into a bind-time "argument form not yet
carried across INVOKE", which is a better message for the same rejection of legal source — an improvement, but
still a GAP, and a GAP is an owner decision ([[feedback_no_deferral_default]]).

## ⚙ THE INVOKE HALF LANDED 2026-08-06 — and both regressions it caused were mine, in the way the note predicted

`invokeArgument`'s BY CONTENT is now `(literal | arithmeticExpression)`, `BoundInvokeArg` carries a
`ContentExpr`, `OoBindInvokeArg` has an expression arm applying §14.8.2.3.3 rule 2a (COMPUTE rules ⇒ a
category-numeric formal), and `OoEmitter` renders it through the same `NumStore` rescale the identifier CONTENT
arm uses.

⛔ **THE FIRST CUT SILENTLY DESTROYED THE IDENTIFIER PATH, AND MY OWN COMMENT HAD WARNED ABOUT IT.** I wrote
`(nonNumericLiteral | arithmeticExpression)` with a note citing `feedback_grammar_precedence`, then walked
straight into it: **`arithmeticExpression` SUBSUMES `dataReference`**, so `BY CONTENT A` began matching the
expression arm and lost the §14.9.23.3 SR9/SR10 object-data rules, the §14.8.2.3.2 conformance check and the
ref-mod handling — while `BY CONTENT "XY"` stopped binding at all because the literal arm keys on `literal`, not
`nonNumericLiteral`. **Two regressions, neither visible as a compile error**, caught by probing all ten argument
shapes rather than only the one being fixed ([[feedback_probe_the_shape_the_subject_hides]]).
The repair: keep `literal` first, drop `dataReference` from the alternation entirely, and recover the identifier
case IN THE BINDER from a sole-dataReference expression — the reduction `ConditionBinder` and `IntrinsicBinder`
already use, now SHARED rather than copied a third time ([[feedback_one_rule_one_place]]). The grammar cannot
express "a reference, unless it is part of an expression" without the ambiguity that caused the defect.

## ▶ WHAT REMAINS OPEN, and why each is not a deferral of convenience

⚠ **`boolean-expression-1` under BY CONTENT.** The §14.9.23.2 format admits it and the grammar does not. It is a
SEPARATE VALUE CHANNEL (`BoundBoolExpr`, D-B1 — a '0'/'1' string world that never enters the numeric or string
channels), so it needs the `{boolExprAhead()}?` predicate on the grammar alternative plus a boolean marshaling
path through `BoundInvokeArg`/`OoEmitter`. Adding it to the alternation unguarded is ambiguous with the
arithmetic arm, because `booleanExpression`'s leaf is `valueOperand`.
⛔ **The CALL half stays BLOCKED, and not on effort.** §14.9.4.2 Format 2 is the program-prototype CALL and the
REPOSITORY grammar has no `PROGRAM program-prototype-name` entry, so no parseable source selects it; Format 1's
BY CONTENT is `{ identifier-2 }` only. Widening `callByContent` would trade a rejection of legal source for an
acceptance of illegal source. Blocked on the program-prototype registry (P13).
