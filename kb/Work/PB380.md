# PB380 — a one-shot whose loser does not wait

**Sites:** `src/WiseOwl.Cobol.Runtime/Collation/CollationRuntime.cs` (`CollationRuntime.Initialize`, `CollationRuntime.ConfigureCache`, `CollationRuntime.s_initLock`, `CollationRuntime.s_initialized`, `CollationRuntime.s_hostConfigured`); `tests/WiseOwl.Cobol.Tests.Unit/Collation/CollationRuntimeInitializeTests.cs` (the guard)

Surfaced by the PB377 implementer's sibling sweep (`grep -rn "CompareExchange" src`, 2026-09-03):
`src/WiseOwl.Cobol.Runtime/Collation/CollationRuntime.cs:74`.

```csharp
public static void Initialize()
{
    if (Interlocked.CompareExchange(ref s_initialized, 1, 0) != 0) return;   // returns while the winner is still working
    if (!s_hostConfigured) CollationKeyCache.DefaultConfig = CacheConfig.FromEnvironment();
    ...
}
```

The flag is set before the work, so a second caller racing the first returns immediately and may read
`CollationKeyCache.DefaultConfig` (and `IsInitialized`, which says `true`) before the winner has assigned it from
the environment; that caller's caches would be sized by the compiled-in default rather than the configured one.
Same family as PB377 — a CAS-guarded one-shot whose loser is not synchronised with the winner — but a different
shape: nothing is dropped, the loser just does not wait.

## Why an analysis and not a defect (yet)

Reachability is unmeasured (memory: `reachability_is_measured_not_deduced`): it needs two run units initialising
the collation runtime concurrently in one process, which the sweep did not probe. Measure it first — a harness
that starts N run units in parallel with `COBOL_COLLATION_CACHE` set to a distinguishable size and asserts every
cache saw it; a static constructor or a first-call path may already serialise the callers and make this moot.

Also recorded here because it is the second note in one day that the register could not classify: the harm is a
RESOURCE one (a cache smaller or, in PB377's case, larger than configured), and the harm vocabulary
(`wrong_answer` · `crashes` · `rejects_legal_source` · `under_rejects` · `silent` · `process_only`) has no
resource/time axis, so PB377 had to be filed provisionally as wrong-answer and this one as an analysis. If this is
confirmed, the structural fix (rule 5) is that axis — one flag in `work.py`'s `HARM_FLAGS`, the `Fix next` filter
in `kb/Work.base` (the drift test pairs them), and the README of the register — not a third misfiling.

## What closes it

Measured reachable → becomes `kind: defect`, and the remedy is to publish the flag AFTER the work with losers
waiting on it (or a `Lazy<T>` / static initialiser owning the whole body), plus a drift test in the PB377 shape.
Measured unreachable → the mechanism that serialises the callers is named here and the note closes as
`landed` with that proof.

## Re-filed as a defect (analyses sweep, 2026-10-23)

Adjudicated read-only by an Opus cobol-adjudicator on main e7cf38ce4; accepted by the Mythos session.

CollationRuntime.Initialize (src/WiseOwl.Cobol.Runtime/Collation/CollationRuntime.cs:72-79) sets s_initialized by CompareExchange BEFORE it assigns CollationKeyCache.DefaultConfig from the environment, so a concurrent caller returns at once, sees IsInitialized == true, and reads the compiled-in CacheConfig.Default (8192 keys) instead of COBOL_COLLATION_CACHE. Repro: probes/pb380/harness, 69% of 3000 trials of 32 concurrent run-unit constructions. Harm is a resource one (a per-collator key cache, created once per process through a ConditionalWeakTable, can be sized from the default for the life of the process; results stay correct), reachable only by a host that constructs run units on parallel threads. Also s_hostConfigured is a plain bool read across threads. Fix (rule 5): one Lazy<T>/LazyInitializer-owned body so losers wait and the flag is published after the work, with a drift test in PB377's shape; the harness becomes the unit test.

Evidence: Measured reachable on e7cf38ce4: harness probes/pb380/harness (32 threads behind a Barrier each run the public RunUnit() ctor, which calls CollationRuntime.Initialize, then read CollationKeyCache.DefaultConfig; COBOL_COLLATION_CACHE=777; the one-shot reset by reflection between trials) saw a stale 8192 in 2061 of 3000 trials (6565 stale reads), every one while IsInitialized was already true. ## Landed (wave 20261791)

Re-probed on the wave build: `CollationRuntimeInitializeTests` (16 threads behind a `Barrier`, 300 trials, the latch reset by
reflection, `COBOL_COLLATION_CACHE=777`) read the stale 8192 in 808 of 4800 post-`Initialize` reads against the old body.
Fix at the root: `Initialize` takes `s_initLock`, does the work (the environment's `CacheConfig`, unless the host configured
one) and only then publishes `s_initialized` (`Volatile.Write`); losers block on the lock and return with the
configuration in place; the fast path is a `Volatile.Read` of the latch. `ConfigureCache` takes the same lock, so
`s_hostConfigured` is no longer a plain bool read across threads. The warm-up stays outside the lock, by the winner alone
(`Warmup` re-enters `Initialize` and creates a run unit, whose constructor does too). Guard: the two tests of
`tests/WiseOwl.Cobol.Tests.Unit/Collation/CollationRuntimeInitializeTests.cs`.

## Review round 1 (wave 20261792)

R1-1 (test flakiness): the guard reset the latch, then the host flag, then `DefaultConfig` as separate bare writes, so a
`new RunUnit()` of a test in another (parallel) xunit collection could win the latch between them and have its configured
size overwritten by the test. The reset and the restore now run as ONE step under the runtime's own `s_initLock`
(`SetOneShotState`, the latch written last), so a foreign winner finishes before the reset or starts after it, and reads
the process-global `COBOL_COLLATION_CACHE` the test set. R1-2 (Sites): the paragraph above now names `ConfigureCache`,
the lock and the two fields.
