# PB3494 — kept transaction state is the connector's, not the physical file's

Lead R1-2 of the branch review of PB3483 (`E:/COBOL-coord/scratch/reports/w1140d-PB3483-report.md`).

`src/Cobol.Net.Runtime/IO/FileConnector.cs` about line 361: `Associate` may change `HostPath` (ASSIGN USING data-name, §12.4.5.3 GR3 b) between the CLOSE under commit control and the re-OPEN, and nothing releases or separates the kept state then. `TakeRunUnitFileLock` Amends the kept lock on the OLD file (`RunUnitFileLock._as.HostPath`) and the new file gets no column lock; `RetakeKeptHandle` opens the CURRENT `HostPath` with the old handle's access and share. The root pre-exists in PB3337: `TakeFileLock` adoption and `Attach` reuse `AttachedStore` whatever the path.

**Fix shape.** Key the kept state by the physical file: when `Associate` changes `HostPath` while state is kept, decide against §9.1.18 and §12.4.5.3 what happens to the transaction on the old file (cite-check the clauses first), then end or carry it deliberately.

**Sites:**
- `src/Cobol.Net.Runtime/IO/FileConnector.cs`
- `src/Cobol.Net.Runtime/IO/KeyedConnector.cs`
- `src/Cobol.Net.Runtime/IO/Sharing/RunUnitFileLock.cs`

**Second witness 2026-10-21 (w1140b-PB3484-report.md, `## New defects`).** A re-OPEN with a different dynamic ASSIGN after a CLOSE under commit control adopts the OLD file's kept handle and store. Repro `E:/COBOL-coord/scratch/w1140b/probe_dyn.cs.txt`: seed two Relative files (host1 with records, host2 with 3), declare the file under commit control with a dynamic ASSIGN, OPEN I-O on host1, read record 1, CLOSE, OPEN I-O on host2. The OPEN answers '00' and `HostPathOf("F")` is host2, yet READ of record 5 answers '00' with host1's record 5; host2 has 3 records, so the expected status is '23'. A wrong answer. Site `KeyedConnector.cs#TakeFileLock` / `#Attach`; the fix needs the kept state keyed by physical file, the PB3337 redesign this note already names. `InheritKept` does not widen it (it requires the same physical file).

## Landing

Re-probed on the wave-1141 build (`CommitRollbackRuntimeTests.A_kept_state_stays_with_the_physical_file_its_connector_is_associated_away_from`,
both organizations, the dynamic ASSIGN of the second witness): before the fix a READ of record 5 of the second file (three records) answered '00' with the
FIRST file's record (the OPEN had adopted the kept handle and store), expected '23'. Evidence:
`E:/COBOL-coord/scratch/w1141b/probe-baseline-evidence.log`.

**Decision (§12.4.5.3 GR3 b, §14.9.7.4 GR3/GR4, §14.9.36.4 GR3, §9.1.16; citations checked with `cite.py --check`).** The changes a connector made to the
first file are changes to a file its APPLY COMMIT clause names, whichever file the connector is associated with next, and the file's locks are released
only by the COMMIT or ROLLBACK (the file is "closed and not reopened"). So the transaction on the first file is CARRIED, not ended: it stays the
COMMIT's and the ROLLBACK's, its record locks and file lock stand against other run units, and the connector's OPEN of the second file is an
ordinary OPEN of that file.

**Fix (the kept state keyed by the physical file).** `KeptFile` (new, `IO/KeptFile.cs`) is what a CLOSE under commit control keeps: the handle, endpoint,
file lock, and now the physical file's identity (`HostPath`, `Physical`, `Store`, `Table`) and the restoring trees (`Restoring`), with the operations the registry
needs (`OpenTransaction`, `CommitTransaction`, `RollbackTransaction`, `Release`). The connector holds it in `_kept` as before; `KeyedConnector.TakeKept` hands it to
the registry, which already kept displaced connectors' state (`FileRegistry._retired`, PB3484) - that list now holds `KeptFile`s, so a displaced connector and a
re-associated one are ONE mechanism (`Retire`). `FileRegistry.Associate` retires the state when the association moved to another file
(`KeyedConnector.KeptIsOfAnotherPath`); COMMIT and ROLLBACK find it through `TransactionHolders` (one per physical file); a refused ROLLBACK or COMMIT of it is
told through the file-name's connector; `ReclaimRetired` hands it back to the connector of the same name that opens the same file again (`InheritKept(KeptFile)`).
Root cause found on the way: `IndexedConnector.Restoring` read the connector's `_st` for the frame slots when it RAN, so a ROLLBACK after the connector
had left the store could not decode the before-images; it is bound to the store it is asked for.

**Siblings swept.** `Retire` (displacement/drop) and `Associate` (re-association) were the two ways a connector stops being the keeper; both go through
`TakeKept`. `InheritStore`/`NewStore`/`AttachCreated` are per-organization and both organizations carry them. The Table 19 column amended on the old
file (the note's first part) was the same root: `KeptFileLock` is null on the connector after the retire, so the OPEN takes its column on the new file.

Tests: `A_kept_state_stays_with_the_physical_file_its_connector_is_associated_away_from` (6: COMMIT, ROLLBACK and "back" for both organizations),
`A_refused_rollback_of_a_file_its_connector_was_associated_away_from_is_told_through_the_file_name`.

## Review finisher, round 1 (2026-10-22)

R1-2: `TransactionHolders` put every retired state first, which is not the order of the open stores once `Associate` retires a
state whose connector stays registered. `StoreTable` now stamps `KeyedStore.OpenOrder` and the holders are sorted by it
(`A_commit_takes_a_retired_files_transaction_at_its_place_in_the_order_of_the_open_stores`, which also covers R1-5's refused
COMMIT of an associated-away state told through the file-name). R1-3: the store-mutex hold has one home,
`HostRegionLocks.HoldStoreMutex`/`InStoreMutex`; `KeyedConnector.InTransactionMutex`, `KeptFile.InMutex` and `KeptFile.GiveBack`'s
inline copy are gone.
