## Expected from the spec

§13.18.60.4 GR25 (`python scripts/spec/cite.py --check 13.18.60.4 "restricted program-pointer"` is OK for general rule 25):
"If program-prototype-name-1 is specified, this data item is a restricted program-pointer. A restricted program-pointer
shall contain only the predefined address NULL or the address of a program with the same signature …". The INITIALIZE
REPLACING value reaches PP1 through the implicit SET of §14.9.20.4 ("If the category of a receiving-operand is
data-pointer, function-pointer, message-tag, object-reference, or program-pointer, the implicit statement is:", checked
with `cite.py --check`), and §14.9.20.3 SR4 ("a SET statement with identifier-2 as the sending operand and an item of the
specified category as the receiving operand shall be valid", checked) makes SET's rule bind: §14.9.39.3 SR22 ("If
identifier-7 references a restricted program-pointer, identifier-8 shall be the predefined address NULL or shall
reference a program-pointer and the program-prototypes associated with identifier-7 and identifier-8 shall have the same
signature", located with `cite.py --find`). Whether SR4's "valid" reaches a restricted receiver, whose prototype is not
named by the phrase, is the implementer's reading to cite.

PB935 (landed) put the SET … TO ENTRY refusal in; its note names this INITIALIZE form as outside its group (PB935.md:106) and
PB3686 owns the CALL RETURNING lane. This is the third lane of one root.

## Acceptance

- The repro is refused with a diagnostic naming GR25, and a restricted-to-same-prototype value, the predefined NULL and an
  unrestricted-to-unrestricted INITIALIZE stay accepted.
- A negative golden `conformance-suite/cases/13.18.60-USAGE/` (or beside the pb935 goldens) pins the refusal; sweep the other
  receiving positions of a program-pointer (MOVE, SET, INITIALIZE VALUE/REPLACING, CALL RETURNING, ENTRY) and record each.

## Landed (wave 20261720, group F)

Re-probe on the wave tree (cobol.exe from the worktree build): the repro compiled clean, and so did its two siblings, a
restricted DATA-POINTER (`INITIALIZE RP REPLACING DATA-POINTER DATA BY UQ`) and a FUNCTION-POINTER restricted to another
prototype; an OBJECT-REFERENCE pair of unrelated classes passed the binder and died in Roslyn as CS0030. One root: GR6b's
`InitializeSetFrom` (the implicit SET of §14.9.20.4 GR4) was built without asking the receiver's own SET rules, and the
phrase-level check (SR4, `CheckSetFormCategoryAgreement`) only sees categories. Fix: `SetBinder.ScreenImplicitSet`, asked per
elementary receiver in `InitializeBinder.ElementaryAction`: data-pointer through `PtrBinder.ScreenPointerReceiverRestriction`
(SR19, COBOL0869), program-/function-pointer through `PointerAssignmentReason` (SR22/SR20, COBOL1959), object reference
through `OoConformance.ObjectRefAssignmentMismatch` (SR12, COBOL0867). One diagnostic per receiver, not per occurrence.
Goldens: `cases/14.9.20-INITIALIZE/pb3817_initialize_replacing_restricted_program_pointer` (accepted: same prototype, NULL,
unrestricted both ways, a group mixing both kinds) and the four `pb3817-initialize-replacing-*` refusals.
Sweep of the other receiving positions: SET (the model, SR19/20/22 and PB935/PB3224), MOVE (a pointer is no MOVE receiver,
PB423), INITIALIZE VALUE / bare (NULL only), CALL RETURNING (PB3686, landed), the single `InitializeSetFrom` constructor.
