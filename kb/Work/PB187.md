# PB187

Registered from the PB164 Step D review fleet's out-of-wave disposition (finding R-b). The fleet KILLED the
finding as filed — "UnifyCrossing OO crossing: out of scope — register note instead" — and the F8 sweep then
classified BOTH of its occurrences as this one item rather than widening them under a mechanical pass.

**THE TWO ARMS, and they are the same rule written down twice** ([[feedback_one_rule_one_place]]):

- `src/Cobol.Net.Compiler/Binding/Passes/StorageFormPass.cs`, `UnifyCrossing`: when the two sides of a
  method/prototype (or interface/implementation) crossing disagree about whether the item is string-carried, it
  promotes the native side to `CharImage` — but ONLY for
  `{ Category: Numeric, IsFloat: false, Usage: Usage.Display }`, returning false for everything else with the
  comment "only the display-numeric pair can diverge; anything else conformance-blocked".
- `src/Cobol.Net.Compiler/CodeGen/Verbs/OoEmitter.cs`, `OoUnivImageBridged` / `OoUnivUnbox` / `OoUnivRebox`:
  the D-U6a box/unbox bridge hand-rolls the SAME union, so it bridges exactly the pairs the pass reconciles.

**WHY THE PREMISE IS NOW FALSE.** "Anything else conformance-blocked" was true while `ComputeTier` arm 1
rejected every float / COMP-5 / BINARY-* / INDEX leaf from a REDEFINES or EXTERNAL/BASED class: a formal could
not BE a windowed float. The arm-1 dissolution (this landing) removed that block, so a `USAGE COMP-1` LINKAGE
item that is a REDEFINES-class member is now `CharImage(Numeric)` while the prototype's plain `USAGE COMP-1`
formal stays `NativeFloat`. `UnifyCrossing` sees the disagreement, hits the `IsFloat: false, Usage: Display`
screen and returns false, leaving the two descriptors permanently unreconciled — which is precisely the state
the pass exists to prevent.

**THE DERIVED CONSEQUENCE — UNMEASURED, AND MEASURING IT IS STEP ONE.** With the descriptors unreconciled the
caller boxes by ITS OWN descriptor (`OoUnivRebox` → `(object?)local`, a boxed `float`) while the callee unboxes
by its own (`OoUnivUnbox` → `OoStringCarried(item)` is true → `(string)box!`), so the crossing should throw
`InvalidCastException` at run time on source the standard admits. **The source really is legal**, and the route
to it is written into the standard: §14.2.2 SR1 (`--check` OK) bars a BASED or REDEFINES clause on the FORMAL's
own entry, and its NOTE 2 says in as many words that "a data item defined subsequently in the linkage section
can specify REDEFINES data-name-1" — so a plain `USAGE COMP-1` formal becomes a member of a shared-storage class
by being REDEFINED, and picks up the window without ever carrying the clause itself. That much is a code
reading, not a probe: **write the probe first**
([[feedback_reachability_is_measured_not_deduced]]) — a class whose method formal is a windowed COMP-1 invoked
through the universal dispatch — and record what actually happens before choosing the fix. The alternative
outcome (the emitter refuses earlier with a loud) would make this a rejects-legal-source item instead of a
crash; either way it is a defect.

**FIX SHAPE.** Do not add a float arm to two hand-rolled unions. `UnifyCrossing`'s question is "can these two
descriptors agree on ONE crossing form?", and since PB164 the answer is derivable: every `HasImageByteForm`
item has a byte image, so the reconciliation is "promote the native side to the image form" for the whole
predicate, not for one usage. `OoUnivImageBridged` should then ask the pass's own result rather than re-deriving
it — the F8 sweep's finding that these two sites hold one rule in two places is the actual bug, and the
`DisplayUsageUnionDriftTests` inventory (which lists both occurrences with this note beside them) is what will
catch the next copy.
