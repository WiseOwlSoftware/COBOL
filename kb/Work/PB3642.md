# PB3642 — the merge queue does not run the merge drivers

**Sites:** `scripts/orchestrator/enqueue.py` (`land`: step 4 and 4a, `open_pull_requests`, `driver_file_holders`, `take_queue_entry_lock`, `open_predecessors`, `EXIT_DRIVER_FILE_QUEUED`, `QUEUE_ENTRY_LOCK_NAME`; `self_test`), `scripts/orchestrator/land_lane.py` (`WAITS`, `driver_files_free`, `wait_free`, `self_test`), `scripts/orchestrator/queue_facts.py` (`PullRequest.entering`, `self_test`), `tests/Cobol.Net.Tests.Unit/MergeDriverDriftTests.cs`.

## What happens

PB3610 added `scripts/merge_drivers.py` (keyed JSON catalogues, work notes, the ABI pin merge by driver) and routed every local merge of main through it (`enqueue.merge_main`, `prune_worktrees.mechanical`). GitHub's merge queue builds its merge-group commits server-side with plain git, with none of those drivers. Two queued pull requests that touch one driver-covered file therefore conflict or bounce inside the queue even though each merged cleanly through the driver locally. The implementer of PB3610 recorded this as its open lead 1.

## Fix direction

Either serialize landings whose changed paths match a `DRIVERS` pattern in the landing lane (never two such pull requests in the queue at once), or move the merge into a form the queue honours. Pin whichever with a drift test that maps every `DRIVERS` pattern to the guard.

## Landed (wave 20261107 group D)

**Re-probe.** GitHub builds the merge group server-side with plain git (the `merge_group` event in `.github/workflows/build-and-test.yml` only runs CI on that commit), so no `merge.<name>.driver` configuration reaches it; the premise holds by construction (`merge_drivers.config_args` passes the drivers on the command line of each LOCAL merge only). The workflow itself needs no change: the queue cannot be given the drivers, so the fix is the first direction the note names, serialization.

**Fix.** `enqueue.py land` waits instead of queueing a second pull request that changes a driver-covered file. Step 4a (after the merge of main, before the DEVLOG stamp) asks `driver_file_holders(wt, base, branch, gh=gh)`, the ONE reader: the branch's own changes since its merge base with origin/main, filtered by `merge_drivers.covered_by_driver` (so a new `DRIVERS` entry is guarded with no new line), against the files GitHub lists for every OTHER open pull request into main (`open_pull_requests`, now shared with `open_predecessors`; a list cut off at `FILES_LISTED` may hide any file and holds the branch for all its driver-covered files). A shared file ends exit 16 `DRIVER FILE QUEUED — #n changes <file>` (new `EXIT_DRIVER_FILE_QUEUED`): nothing stamped, pushed or queued, no report line. The wait ends when the other pull request merges; the next `land` merges main in through the drivers (so the merged change is already in the branch) and queues on top. A branch with no driver-covered file never asks GitHub; GitHub unreadable is exit 9 (retried once). Two landings that the lane starts side by side cannot both look and both queue: `take_queue_entry_lock` takes a repository-wide OS lock (`<git common dir>/cobol-queue-entry.lock`, released by every outcome with the land lock) from before the loop to the queueing; a holder past `QUEUE_ENTRY_WAIT_S` is exit 2 NOT QUEUED (retried once). The landing lane retries exit 16 at the same head once the same reader finds no sharing pull request (`WAITS`, `driver_files_free` through `wait_free`), never the enqueue unit's. Self-tests: one branch changing the sample file of EVERY `DRIVERS` pattern is held by a pull request listing each, only that file named; other files, the branch's own pull request, a cut-off list, an unreadable GitHub, the lock, and the queued-after-merge path; the lane's wait/relaunch arm. Drift test `MergeDriverDriftTests.TheLanding_WaitsForAnOpenPullRequestThatSharesADriverFile` holds the wiring and the arms. Docs: DESIGN-orchestrator-loop 4.9 table, DESIGN-test-build-ci step 4, units/enqueue.md, landing.md, MANDATORY-PRACTICES L12.

**Review round 1 (R1-1, blocking).** The first reader held a branch on EVERY open pull request listing a shared driver file, a BOUNCED one included, although the conflict arises only inside a merge group and a bounced pull request re-enters only through a fresh `land` of a new head (which merges main through the drivers first): one unfixed bounce would have held every later landing of a catalogue file, silently and without escalation. `driver_file_holders` now keeps only a pull request that ENTERS the queue, by `queue_facts.PullRequest.entering` (in the queue, or auto-merge on, and not bounced, not conflicting with main, no failed required check), read through `queue_facts.read`, the one reader of those facts; a pull request the facts do not name is still held, and facts GitHub cannot answer are a problem (exit 9 at `land`), never an empty hold. Self-tests: `queue_facts` (`entering` over every state), `enqueue` (bounced, DIRTY and red hold nothing; in the queue, auto-merge on, auto-merge after a push following a removal and an unnamed pull request hold; facts unreadable; a `land` past a bounced holder queues), `land_lane` (`wait_free` exit 16 is free once the holder is bounced).
