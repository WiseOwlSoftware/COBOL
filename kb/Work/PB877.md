# PB877

## The repro — battery #77's GnuCOBOL differential regression

`run_initialize:298` flipped AGREE_ACCEPT → WE_REJECT_THEY_ACCEPT on main at `ccf03eed` (train 35). The
program is `E:\Temp\gcdiff_fj5q8581\run_initialize_298\prog.cob`; its second test writes

```cobol
       01 G.
         02 G2          OCCURS 3.
           03 X         PIC 9.
           03 Y.
             04 Y-REC   OCCURS 5.
              05  Y1    PIC 9 VALUE 9.
              05  Y2    PIC X VALUE 'Y'.
           03 Z         PIC X VALUE 'Z'.
       …
           MOVE 2       TO X(1)
           INITIALIZE Y (X(1)).
```

and draws

```
prog.cob(26,12): error COBOLNET0899: receiving operand 'Y(X(1))' names a declared item in a reference
shape COBOL.NET does not yet implement as a receiver
```

while `INITIALIZE Y (2)` on line 17 of the same program is accepted.

## The mechanism — one half of §8.4.2.3.3 SR2 was never written down

`INITIALIZE` is only the MESSENGER. PB416 (train 35) routed identifier-1 through
`ExpressionBinder.ResolveReceiving`, the one receiving chokepoint, so the statement started sharing the
reference resolver every other verb already used; INITIALIZE's old private resolver did not. The hole it
walked into is in `ReferenceResolver`, on the path EVERY reference takes, sending and receiving alike.

`ReferenceResolver.InterpretSubscripts` splits a reference's subscript group into one segment per subscript
with `SplitSubscriptTokens`, whose PB136 declaration-informed rule decides whether a depth-0 `'('` after an
identifier BEGINS A NEW SUBSCRIPT or belongs to that identifier as its own subscript list. The predicate it
was given is

```csharp
name => ResolveUnqualified(name) is { IsTable: false }      // split
```

and `DataItem.IsTable` is `Occurs is not null || IsDynamicTable` — "does THIS entry carry an OCCURS clause".
§8.4.2.3.3 SR2 asks a wider question: a subscript may be written when the entry "shall contain an OCCURS
clause **or shall be subordinate to** a data description entry that contains an OCCURS clause". `X` is
`PIC 9` under `02 G2 OCCURS 3` — subordinate to a table, so `X(1)` is a legal identifier and, per §8.8.1.1 +
§8.4.3.1.2 Format 2, a legal `arithmetic-expression-1`, the second alternative of §8.4.2.3.2's `subscript`
diagram. The predicate answered "not a table", the `'('` started a NEW segment, and `Y (X(1))` was read as
TWO subscripts on a one-dimensional reference. §8.4.2.3.3 SR3's arity check then failed and the resolver
returned null.

## Two arms, and only one of them is loud

The split is shared, so the defect is shared — but the two sides of a statement report it differently:

- **RECEIVING** — `ResolveReceiving`'s PB70 guard turns the resolver's null into the loud COBOLNET0899 above.
  Legal source is REJECTED. Measured: `MOVE "Q" TO Y2 OF Y-REC (X(1), 2)`.
- **SENDING** — nothing guards it. `DISPLAY Y2 OF Y-REC (X(1), 2)` and `MOVE Y2 OF Y-REC (X(1), 2) TO W`
  COMPILE CLEAN and abort at RUN TIME with
  `NotImplementedCobolFeatureException: reference 'Y2OFY-REC(X(1), 2)'` — the wrong stage under §4.2.2, and
  the worse of the two.

## What closes it

The SR2 predicate, written once. `DataItem` grows `SubscriptArity` / `SubscriptLevels()` / `IsTableElement`
(the SR3 count, the SR3 order, the SR2 admission) beside `IsTable`, and the split predicate, `AccessPath`,
`OdoModel.SubscriptPositionOf` and `IntrinsicBinder`'s table(ALL) walk all read them instead of re-writing
the ancestor walk. The LEGAL shape needs no new diagnostic: with the segment kept whole, the renderer's
existing PB201 route (`PositionRead` → `AccessPath(item, [])` → null for a subscript-requiring name) already
sends it to the D18 materializer, where `subscriptExpressionFragment : arithmeticExpression EOF` and the ONE
`ExpressionBinder.BindExpr` bind it — the same binder the sending side uses. The 0899 staging for this shape
needs no deletion because it was never a stage: it is the generic receiving catch-all, and it stops firing
when the shape resolves.

`GR-8.4.2.3.4-1` is recorded CONFORMS with its b) arm ("arithmetic-expression-1") evidenced by five
goldens, and none of them wrote an identifier that carries its own subscripts — a green row over an open
hole. Its witness list gains this note's golden.

## Landed — 2026-09-13, worktree `agent-ad205149948869b76`, base `ccf03eed` (train 35)

Reproduced on this tree exactly as written, then fixed at the rule.

**The predicate.** `DataItem` gained `IsTableElement` (§8.4.2.3.3 SR2's admission test, `SubscriptArity > 0`),
`SubscriptArity` (SR3's count) and `SubscriptLevels()` (SR3's outermost-first order), each beside `IsTable`
with a ⛔ note saying which question each answers. `ReferenceResolver.CannotBeSubscripted` is the ONE
declaration-informed `'('` predicate and all THREE `SplitSubscriptTokens` callers now pass it —
`InterpretSubscripts`, `SubscriptSegments` (which had its own identical wrong copy, and a doc-comment
CLAIMING they shared a rule) and `IntrinsicBinder`'s table(ALL) split (which passed none, so the
pre-PB136 join stood there). The SR3 arity walk was written five times; `AccessPath`, `BuildAccessPath`,
`OdoModel.SubscriptPositionOf`, `IntrinsicBinder` and `DataBinder.Reports.ControlOperandShapeViolation`
(§13.18.16.3 SR3's "subject to any OCCURS clauses", the same question under another name) all read the
`DataItem` members now. The fifth was found by the drift test, not by reading.

**The wrong stage, found while probing the negative.** A subscript on a non-table item, and a wrong
subscript COUNT, were BOTH decidable at the resolver and neither was decided: the receiving chokepoint
promised `MOVE 1 TO PLAIN (1)` was "a reference shape COBOL.NET does not yet implement" (COBOLNET0899 — the
PB489 shape, a promise about permanently illegal source) while the identical SENDING reference compiled
clean and aborted at run time, where §4.2.2 requires a compile-time mechanism.
`ReferenceResolver.ScreenSubscriptArity` now reports SR2 as **COBOLNET2096** and SR3 as **COBOLNET2097** at
the one resolution site, reached from both `ResolveImplCore` (data-name references) and `ResolveForItem`
(condition-name references, whose subscripts identify the occurrence of the conditional variable — SR2 names
that case itself). It fires ONLY on a reference that writes subscripts: SR5's seven exceptions are about
OMITTING the list and belong to the binders that know the context.

**Evidence.** `tests/conformance/85/pb877_subscripted_subscript.cob` (PB877SUBSCRIPT) — the differential's
own two INITIALIZE lines plus one line per receiving family (MOVE, ADD, COMPUTE, STRING, UNSTRING), the
sending arm, a relative subscript, a ref-mod leftmost position, an intrinsic-function argument and a nested
`SEARCH ALL T-E (T-N (1), TX)` whose value discriminates the outer occurrence; every expected value derived
from the rules before the run. Negatives `pb877-subscript-on-non-table-item` (2096) and
`pb877-subscript-count-mismatch` (2097), rejected at all four editions.
`SubscriptAdmissionDriftTests` pins the predicate, its single definition, the single arity walk and both
screen call sites. Rows: `FMT-8.4.2.3.2`, `SR-8.4.2.3.3-2`, `SR-8.4.2.3.3-3` GAP → CONFORMS and
`GR-8.4.2.3.4-1` refreshed with the shape witness its five value witnesses never had (GAP 2456 → 2453).
