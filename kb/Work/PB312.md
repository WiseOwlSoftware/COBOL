# PB312 — the annex is where a reader looks for worked date examples, and both are traps

Annex D is **informative**; the normative rule governs. Neither of these is a compiler defect and no verdict
changes. They are registered because they are live traps: a future golden taking its expected value from Annex D
would assert a wrong answer with a citation that `--check`s clean.

## D.31.5.2 — the week date is one week early

`cite.py --check 15.3.1.7 "The first week of a given year is the week that includes January 4 of that year."` →
OK. January 4 1995 is a Wednesday, so week 01 runs Monday January 2 to Sunday January 8; February 15 is 44 days
after January 2 = 6 whole weeks + 2 days, i.e. **week 07, day 3**.

* correct: basic `1995W073`, extended `1995-W07-3` (day-of-week 3 = Wednesday, per §15.3.1.7's *"a value from 1
  through 7 inclusive, representing Monday through Sunday respectively"*)
* Annex D.31.5.2 prints `1995W063` and `1995-W06-3`

**Cross-checked against the canonical PDF at page index 1196, which prints the same wrong values** — so
`specs/ISO_COBOL.md` is faithful and the error is in the published standard. COBOL.NET renders week 07 and is
correct. `tests/conformance/2023/l1_fdt_returned_value_combination.cob` (landed by the golden lane) asserts the
normative `1995W073` / `1995-W07-3` and spells the contradiction out in its own header so the value cannot be
"corrected" back.

⛔ A second-order trap the same file walked into once: an early draft of that golden ALSO took D.31.5.2's `.8124`
as the justification for its four-digit-fraction leg — an oracle from the very table its own header declares
erroneous ten lines earlier. That appeal was deleted and the leg now uses an argument exact at four digits, so the
value follows from §15.3.3.2 alone.

## D.31.5.7 — the worked example the standard's own rules reject

Annex D.31.5.7, canonical PDF page index 1198: *"given as the first argument the format `"YYMMDDThhmmss.ss+hhmm"`
… the returned value would be `"19950215T05142781+0500"`"*.

`cite.py --check 15.3.1.2 "The basic calendar date format contains eight characters"` → OK: a calendar date format
has **four** `Y` characters, so `"YYMMDD"` is not a date format and `"YYMMDDThhmmss.ss+hhmm"` is not a combined
format. **The annex's own stated returned value begins with a four-digit year, which its own format string cannot
produce.**

COBOL.NET rejects the example with `COBOLNET1631` (§15.40.3 r2 — argument-1 shall be a combined date and time
format), and that rejection is **conforming**: the annex is informative and self-inconsistent. This resolves the
adjudicator's flag on `RV-15.40.4-1` that *"the standard's own worked example is rejected by this
implementation"* — the CONFORMS verdict stands. `kb/Work/R24` already refers to *"the exact D.31.5.7-corrected
19950215T05142781+0500"*, so the correction was known in the register but had never been asserted by a
FORMATTED-DATETIME golden; `tests/conformance/2023/l1_fdt_utc_adjust_vs_offset_direct.cob` now runs the example
with the year field restored and records why in its header.

## Disposition

No code change and no verdict change. If the project ever files defect reports against the standard, these two are
candidates; until then the value of this note is that the next reader of Annex D finds the warning before the
golden.
