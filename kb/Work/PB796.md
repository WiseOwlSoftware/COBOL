## The mechanism — a loop that ends one step before the answer

The landing protocol is written down in four places, and all four stop at the push:

| site | last thing it says about a landing | what it never says |
|---|---|---|
| `templates/lander-brief.md` step 5 | `git push origin HEAD:main` — "Report the sha you pushed" | anything about the run that push starts |
| `templates/lander-train-brief.md` step 6 | `git push origin HEAD:main` … "Report every sha you pushed, in order" | same |
| `workstream/SKILL.md` §3 | landers "`git fetch origin && git rebase origin/main && git push origin HEAD:main`" | same |
| `gate/SKILL.md` "Per accumulated batch / pre-merge — comprehensive" | full Conformance + characterization + GnuCOBOL differential + `guard-fast.sh` | that every one of those runs on ONE host |

⛔ **And the one instrument every session does read was blind by construction.** `scripts/session-probe.ps1`
already carried a `ci :` line — but it answers *"is the workflow ENABLED?"* and nothing else (added 2026-08-06,
when GitHub's Actions outage let five pushes queue nothing). Its own comment states the hazard exactly, and has
since the day it was written:

> the battery is NOT a superset of CI: it is Windows/DEBUG only, so the Linux legs and the Release configuration
> are verified by CI and by nothing else.

The workflow was **active** for the whole window. So the probe printed nothing, and "nothing" read as fine —
`feedback_green_gates_arent_evidence` and `feedback_reachability_is_measured_not_deduced` in one line: a check
that only speaks when a *different* condition holds is not evidence about this one.

## The harm, stated plainly

Every push in the window — **trains 10 through 20 and the battery/ledger commits between them** — landed on
`main` reporting a green gate, and the project's own CI said red for all of it. Nobody noticed for **two days**,
and the owner found it, not an agent. Three things follow:

1. **The claim in every one of those DEVLOG entries and lander reports is narrower than it reads.** "Battery green"
   meant *Windows, Debug, this box*. It never meant Linux, and it never meant Release.
2. **A Linux-only regression had 29 hours and 20 pushes to hide behind.** `FileLockPostureDriftTests` is
   FILE-I/O semantics — `kb/Work` PB343/PB344/PB355 (the next three items `work.py next` ranks) are all `io`.
3. **The instruments were not silent by accident, they were silent by design** — no step, script or skill in the
   loop had CI's conclusion as an input. That is the defect; the two red tests are `PB795`.

## The fix — the shape that makes the NEXT case automatic (CLAUDE.md rule 5)

⛔ Not "remember to check CI". The rule is written into the four places the loop actually reads, once each, and
the mechanical half is the probe:

1. **The obligation lands on the agent that creates the condition.** Both lander briefs gain a numbered step
   AFTER the push — wait for the run on the pushed sha, report its conclusion, and treat a red as a BLOCKING
   finding attributed by job / step / failing test. A lander that pushes is the only actor who knows which sha to
   watch, so putting the step anywhere else needs someone to remember; here it cannot be skipped without skipping
   a numbered step.
2. **The report carries it, so the orchestrator cannot land the next train over a red.** Both REPORT blocks now
   demand the run id and its conclusion — the same reason `SKILL.md` §3's collision-free sites work
   (`kb/Work/PB784`): the datum is required by the artifact the next actor reads.
3. **The probe prints the verdict UNCONDITIONALLY, green included.** A line that appears only on failure is one
   more thing whose absence must be interpreted; a line that always states the conclusion is positive evidence
   (`feedback_prove_the_watchdog_fails`). It degrades to `gh unavailable — CI verdict UNREAD (do not infer green)`
   with no CLI, no network or no runs — never to silence.
4. **"Comprehensive" is redefined where it is defined.** `gate/SKILL.md` and plan §9 both described the battery
   as the comprehensive gate; both now name CI's Linux leg and the Release build as part of it, with the `gh`
   command. `feedback_one_rule_one_place`: two sites stating one rule is how they drift, so they were edited
   together in this change set.

⚠ **What this fix does NOT do, said out loud.** There is no drift test that fails when a future brief drops the
step — the briefs are prose in `.claude/skills/`, and nothing in CI parses them. The mechanical half is the probe
line, which makes a red *visible at every session start* even if a brief is rewritten badly. A stronger form (a
required status check on `main`, so a red push cannot be built on) is an OWNER decision about branch protection
and is not taken unilaterally here.

## LANDED-2 — 2026-09-06 — the gate, the script, the protection

Four commits, each landed through the new script itself: `e7ec4280` (the workflow) · `124ad6d7` (the script and
every doc site) · `cf6e65d9` (the session-probe line) · `fe870320` (plan §0), plus this note.

### What `ci-gate` is, and why nothing else could be the required check

`ci-gate` is the terminal job of `.github/workflows/build-and-test.yml`: `if: always()`, `needs:` **every** other
job, PASSING only when each needed result is `success` or `skipped`. The pass set is a WHITELIST, so `failure`
and `cancelled` fail by name and any result value GitHub adds later fails by construction; and the job refuses to
report at all if it sees fewer than five needed jobs, so it can never pass over an empty population
(`feedback_verdict_evidence_invariant`).

⛔ **No other check name in the file can be required, and the reason is measured.** On `5bf5a7f1` the conformance
jobs' check runs are named
`Greenfield conformance (Linux, sharded) (corpus-nist, FullyQualifiedName~CorpusRunnerTests|FullyQ…` — the shard
AND its filter text are inside the name, so any shard edit renames the context, and a required context that stops
reporting blocks `main` forever. Worse, every matrix job is *skipped* on a docs-only push, and a required check
reads "skipped" as "never reported" — blocked forever again.

### Where the doc-only list went

`paths-ignore` is gone; the trigger is now `branches: [ main, 'ci/**' ]`. The identical six-entry list lives in
the first job, `changes` — **one copy, with no trigger-side twin to drift against**
(`feedback_one_rule_one_place`) — which diffs `github.event.before .. github.sha` with `git diff --name-only`
(checkout is `fetch-depth: 0` with `filter: blob:none`: commits and trees, not history's blobs — the job runs in
**9–12 s**) and outputs `run_matrix`. Every other job carries `needs: changes` and
`if: needs.changes.outputs.run_matrix == 'true'`.

⚠ **A correction to the brief that specified this work**, made because implementing it as written would have
defeated the requirement. The brief said "a zero `before`, a force push or a new branch ⇒ `code=true`". But
`push-main.sh` pushes every landing to a FRESH `ci/<short-sha>` branch, so `before` is all zeros on **every
landing**, and that rule would have run the full matrix for every docs-only landing — the case the job exists to
spare. When `before` is unusable and the ref is not `main`, the base is therefore `merge-base(origin/main, sha)`:
precisely "what this push proposes to add to main". Only when no base can be established at all does it fall
through to `code=true`, and an EMPTY diff is `code=true` as well — a missing observation is not a negative one.

`changes` also carries the **already-verified short-circuit**: `push-main.sh` proves a sha on `ci/<sha>` and then
fast-forwards THAT SAME SHA onto main, so without it every landing would pay for the matrix twice — the exact
waste the owner flagged on 2026-08-08 over a single spent run. A check run is attached to the COMMIT, so a green
`ci-gate` on the sha is a verdict on that exact tree whatever branch earned it. Measured on the main-branch run
of `124ad6d7`:

```
run_matrix=false (code=true verified=true): 9 path(s) outside the doc-only list, e.g. .claude/skills/gate/SKILL.md;
BUT ci-gate already succeeded on 124ad6d7131a65f44ecf10e3a28c0344f5864904 (1 green check run(s)) — same commit,
same tree
```

That run (34073460139) finished in **21 s** with all eight matrix jobs `skipped`. Any failure of the lookup
leaves `verified=false` and the matrix runs.

`cancel-in-progress` is now `${{ github.event_name == 'pull_request' }}`. ⛔ Under a required per-commit check a
cancelled run leaves its sha **permanently unlandable**, and `cancelled` is exactly the row a human skim reads as
"not a failure" — this note already counts SIX of them inside the 29-hour window. A pull_request run is
superseded the moment its head moves, so cancelling that costs no coverage.

### The drift test — a gate cannot block a red it is not wired to see

`ci-gate` only blocks a red it is `needs:`-wired to see, so a job added later without that wiring would be a job
whose failure lands on main silently: this note's own shape, one level down. The `changes` job therefore reads
the workflow file and asserts every job id appears in `ci-gate`'s `needs` list, on every event including
docs-only pushes. ⭐ **All three of its branches were exercised before it shipped, not assumed**
(`feedback_prove_the_watchdog_fails`):

```
[1] real workflow            -> rc=0   drift: ci-gate needs all 9 other jobs — ,changes,guard,
    greenfield-conformance,greenfield-unit,windows-conformance,conformance-population,inv1-strong-2023,
    windows-build-test,legacy-oracle,
[2] guard dropped from needs -> rc=1   ::error::ci-gate does not need: guard — a job the gate cannot see is a
    red that cannot block a landing
[3] unparseable jobs block   -> rc=1   ::error::the job-id scan found 0 jobs in
    .github/workflows/build-and-test.yml — the SCANNER is broken, not the workflow
```

The `Decide` step was likewise extracted from the YAML and run against real history before the commit:
`d00b58ff..1ec771a2` (the ledger commit) → `run_matrix=false`; `9fad13e5..1ec771a2` → `run_matrix=true`,
"324 path(s) outside the doc-only list"; a `pull_request` event → `true`; a zero `before` on `main` → `true`,
"no usable base".

### `scripts/push-main.sh` — the protocol as a mechanism, not as prose

The first landing of this note fixed the loop by adding a numbered step to two brief templates and a paragraph to
two skills, and said out loud that nothing parses those briefs. This replaces them:

    push the VERIFIED sha to ci/<short-sha> → find the run for that exact sha → gh run watch --exit-status
      → GREEN: git push origin <sha>:main (fast-forward only), delete the branch
      → RED:   print the failing jobs (job, step) and exit non-zero, main UNTOUCHED

- ⭐ **Idempotent**, because a full-matrix run is ~25–30 min and an agent's command timeout is 10: a sha already
  carrying a green `ci-gate` skips straight to the main push, and a run in flight is re-attached to.
- ⛔ **The VERIFIED sha is pushed by name, never `HEAD:main`.** The first draft used `HEAD:main`, and over a
  30-minute wait a lander that commits in its own worktree would move HEAD — landing an unverified commit on the
  back of another commit's green run, the precise failure this script exists to make impossible. It now warns
  when HEAD has moved and lands `$SHA`.
- Fast-forward is checked **before** a run is spent, with the rebase command in the refusal; never `--force`.
- `gh run watch` exiting non-zero is **not** read as a red — a dropped connection exits non-zero too. The run's
  conclusion is re-read authoritatively, and then the CHECK the protection reads is asserted separately: a green
  run and a green `ci-gate` check run are two different statements.
- ⛔ **No run is a failure, never a pass.** With `paths-ignore` gone every push to `ci/**` starts a run, so "no
  run for my sha" no longer means "docs-only" — it means the workflow did not fire.
- It then waits for the run its own main push started and reports that too — literally the thing this note is
  about.
- `scripts/push-main.ps1` is a SHIM over the `.sh`, deliberately unlike the `build-local.{sh,ps1}` twins: a
  second copy of the landing protocol is a second place for it to drift, which is the defect this note IS.

⭐ **All FOUR actors that push to main were swept** (`feedback_scan_all_similar`), not the two the brief named:
`lander-brief.md`, `lander-train-brief.md`, `golden-lander-brief.md` and `registrar-brief.md`. The last two had
no CI step at all and would have been refused outright on their first landing; both also gained the
run-id-and-conclusion REPORT datum.

### What does NOT hold

- ⛔ **Branch protection has no drift test, and cannot have one** — it is server state, not a file. The
  `session-probe.ps1` `gate :` line is the whole guard, and it is only read by a human or an agent at session
  start; nothing FAILS if the protection is removed. That is a genuinely weaker guarantee than the workflow half,
  which `changes` drift-checks on every push.
- ⚠ **`ci-gate` is only as good as its `needs:` list, and the drift check only as good as its parser.** The check
  reads a single-line `needs: [ … ]` form and says so loudly if that form is gone; a future editor who reformats
  it as a block list gets a red, not a silent pass. That is the safe direction, but it is a red for the wrong
  reason.
- ⚠ **A run that never starts still blocks a landing rather than passing it** — correct, but it means a GitHub
  Actions outage (as on 2026-08-06) now blocks landings outright instead of merely leaving them unverified.
  `push-main.sh` fails with "no workflow run appeared … main NOT touched"; the escape hatch is an owner decision
  to lift the protection, not anything an agent may do.
- ⚠ **The `pull_request` trigger is unchanged and untested by this work.** No PR was opened; the PR path is
  reasoned about (it always runs the full matrix, `changes` returning `code=true` for any non-push event) and
  measured only through the `event=pull_request` arm of the extracted `Decide` step.
