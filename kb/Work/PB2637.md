**Rule it breaks:** performance: a compile-time-constant computation repeated per evaluation on an emitted path (DESIGN-architecture-review §4 item 5, §5.4; review dimensions.md 3), and one format language parsed in one place (§5.1): the binder's DateTimeFormatGrammar recognizes the literal and the compiler calls CobolDate.FormatFractionDigits on it at compile time (IntrinsicRenderer.cs:407 via RuntimeApi.DateFormatFractionDigits), then the runtime parses the same literal again on every call

**Scenario:** ISO §15.38.3, §15.39.3, §15.40.3, §15.41.3, §15.48.3, §15.79.3 and §15.92.3 rule 1 each read "Argument-1 shall be a national or alphanumeric literal", so the format of FORMATTED-CURRENT-DATE, FORMATTED-DATE, FORMATTED-DATETIME, FORMATTED-TIME, INTEGER-OF-FORMATTED-DATE, SECONDS-FROM-FORMATTED-TIME and TEST-FORMATTED-DATETIME is fixed at compile time. Yet every call runs CobolDate.Tokenize(format) (CobolDate.cs:259-311), which allocates a List<Seg> and grows it (for "YYYYMMDDThhmmss.ssssss", 9 segments: the list plus backing arrays of 4, 8 and 16, four allocations), then EmitFormatted (CobolDate.cs:329-409) scans the segment list three more times with LINQ Any, allocates a StringBuilder, one string per numeric field from int.ToString("00") (seven for that format) plus `new string('0', s.Width)` as the fraction's format string, and the result: about sixteen allocations per FORMATTED-DATETIME call, of which the tokenization and the format-string allocations are a pure function of the literal. Analyze (CobolDate.cs:586-699) re-tokenizes likewise for the three analyzing functions. A batch program that stamps 1,000,000 records with FUNCTION FORMATTED-DATETIME re-parses the same literal 1,000,000 times.

**Measured how:** R2 batch finding `runtime-values-1--performance--f1#3` (pair runtime-values-1--performance), read in the pinned tree at 8be23006851a; skeptics rule refuted, scenario upheld, site upheld. Measurement: allocation count read from the pinned code at a stated input, the format "YYYYMMDDThhmmss.ssssss" (9 segments): Tokenize 4 allocations (List<Seg> and arrays of 4, 8, 16), EmitFormatted 1 StringBuilder plus 7 field strings plus 1 fraction format string plus the result, so about 14-16 heap objects per FORMATTED-DATETIME call, every one of the tokenizer's a recomputation of a compile-time literal (ISO §15.40.3 r1). No R0 baseline row (354c79ef3312) exercises a date-format function, so the wall-time share is unmeasured.

**Target:** The format is parsed once: the emitter passes a precompiled format (the segment array, built by the ONE tokenizer and held in a static readonly field of the generated program, or a runtime cache keyed by the literal) and EmitFormatted writes digits into one buffer (string.Create or a stackalloc span with int.TryFormat and the invariant culture) instead of a string per field; Analyze reads the same precompiled segments. One parse of the §15.3 format language serves the binder's recognizer, the compile-time FormatFractionDigits and the runtime, which lands with the §8.3 (3) DateTimeFunctions extraction (PB2370; CobolDate's own extraction PB2346).
