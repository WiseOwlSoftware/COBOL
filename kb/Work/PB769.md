# PB769 — OPEN — a backlog view that shows finished work, and a guard built not to look at it

Found 2026-09-06 in the PB735 implementer's report (NEW DEFECT C), which met it while correcting the sibling
views and deliberately left this one alone. Verified against main (`9fad13e5`) by reading the view and counting
its population.

## The view, verbatim

`kb/Work.base`:

```yaml
  - type: table
    name: Analyses (§11 backlog)
    filters:
      and:
        - 'kind == "analysis"'
    order: [id, status, area]
    sort:
      - property: status
        direction: ASC
```

One clause. The word *backlog* is in the view's NAME and in no part of its filter.

## MEASURED — the population it misreports

Counting `kind: analysis` notes on main by frontmatter `status:`

```
open   71
landed 18      ← every one of these is listed in "Analyses (§11 backlog)"
half    1
retired 0
       ---
        90
```

The eighteen: `A3`, `A12b`, `A12c`, `A12d`, `A12e`, `A14`, `PB90`, `PB108`, `PB143`, `PB260`, `PB261`, `PB281`,
`PB283`, `PB469`, `PB695`, `PB702`, `PB724`, `PB737`. **One row in five of the backlog is finished work** — and
the view sorts by `status` ASC, so `half` and `landed` sort ahead of `open` and the finished rows sit at the TOP.

`retired` is at zero on main today; the register's first retirement (PB588 → [[PB736]]) is on PB735's branch and
has not landed, so that arm of the problem arrives WITH PB735 rather than existing now.

## Why the guard cannot catch it

`work.py check`'s only assertion about `kb/Work.base` today is `check_base_agrees` (`scripts/spec/work.py:229-253`),
which reads the **Fix next** view's harm-flag line and nothing else. PB735's change set adds a second
assertion — `TERMINAL_STATUSES`, "a view that filters out ANY terminal status filters out ALL of them" — and adds
`status != "retired"` to the three open-work views (`Fix next`, `Blocked`, `Open but no harm flag set`, which on
main still filter `status != "landed"` alone). That guard is scoped, on purpose and correctly for its own job, to
views that filter on status at all; `Everything` legitimately does not, and the Analyses view is the second
member of that set by accident rather than by decision. So the new guard will be green over this view forever.

`feedback_measure_the_selectors_complement`, one level up from where it usually bites: the guard is evidence
about the three views it CHECKED and says nothing about the two it SKIPPED, and the two were never separated
into "must not filter status" and "forgot to".

## Harm

`process_only`, and small — nobody gets a wrong compile out of it. What it costs is the thing CLAUDE.md rule 8
bought by collapsing five registers into one: **a derived view that a reader trusts.** A backlog overstating
itself by 20% is the same failure mode as the plan §0 duplicate table that "rotted into listing landed items as
open", which is quoted in rule 8 as one of the reasons the register exists.

## The fix shape

1. **The view states its own claim in its filter**: add `status != "landed"` and `status != "retired"` to
   `Analyses (§11 backlog)`. Two lines.
2. ⭐ **Make the next view automatic instead of remembered** (CLAUDE.md rule 5). Widen PB735's guard from "a view
   that hides ANY terminal status hides ALL of them" to the structural rule **"a view that has a `filters:` block
   at all is a work list, and a work list shows no terminal item"**. `Everything` has no `filters:` block, so it
   is excluded BY CONSTRUCTION rather than by being named — no list to maintain, and a fifth view added next
   month is covered the day it is written.
   ⚠ Its trade-off, stated so the choice is deliberate: a future view that deliberately shows landed items (a
   "landed this week" report) would have to be granted an exception, and granting it should be a visible edit to
   the guard rather than a silent omission from it. That is the direction of error this register wants.
3. **It lands with PB735 or after it, never before** — the `TERMINAL_STATUSES` tuple this widening builds on is
   in PB735's change set, and `kb/Work.base` plus `scripts/spec/work.py` must land in the same commit or
   `work.py check` fails either way (PB735's report says so of its own pair).
4. ⛔ **Fire it once** (`feedback_green_gates_arent_evidence`): with the guard in, delete one of the two new
   filter lines and watch `work.py check` go red, then restore it.
