# PB2936 — record locks and the store mutex do not bind across run units off Linux and Windows

Filed 2026-10-10 by the train 1052 lander (phase 2) from the wave 1052 B implementer's report
(`E:\COBOL-coord\scratch\reports\w1052b-PB2484-report.md`, "New defects" item 1). Phase 1b wrote it into PB2660 as a
residue paragraph; PB2660 is `landed`, so the defect was invisible to `work.py next` and moves here.

**Where.** PB2660 (landed, train 1042) made the cross-run-unit RECORD locks and the store mutex of a shared RELATIVE or
INDEXED file real host locks: one byte per record key (hashed) and one store byte, taken through
`src/Cobol.Net.Runtime/IO/Sharing/HostRegionLocks.cs` — `Hold` (about line 102), `HeldByAnother` (about line 113) and
`Release` (about line 127). Each arm has an expression on Windows (`LockFileEx`) and on Linux (open file description
locks, `OfdRegionLocks.Available`) only; on every other Unix (macOS, the BSDs) `Hold` and `HeldByAnother` answer
`OfdRegionLocks.Result.Unavailable` and `Release` does nothing, so the run unit keeps only the guarantees it can keep
alone. PB2484 (train 1052) gave the §9.1.15 FILE lock a lock-file expression on those hosts
(`SidecarColumnLockHost`, one holder file per run unit), but a record byte cannot use a per-holder file.

**Failure scenario (§9.1.16, §9.1.13.8 1)).** On macOS, run unit A opens a RELATIVE file `SHARING WITH ALL OTHER`,
`LOCK MODE IS MANUAL`, and `READ ... WITH LOCK`s record 1; run unit B's `READ ... WITH LOCK` of record 1 answers I-O
status `00` where §9.1.13.8 1) requires `51` ("an attempt to access a record that is currently locked by another file
connector"), and B's REWRITE and WRITE succeed and race A's store writes with no store mutex: lost updates, silently.

**Repro.** PB2660's two-process probe, run on a macOS host: `E:\COBOL-coord\scratch\w1040u\probes\lka.cob` +
`lkb.cob`, driven by `l2.ps1` (B starts 3 s after A). Expected `B READ-LOCK 1 FS=51`; on macOS the lock is not taken.
CI has no macOS leg, so no gate sees it; a unit witness can force the "neither Linux nor Windows" arm the way
`RunUnitFileLock.Take(host, ...)` forces the sidecar host.

**Fix shape (a design, beyond the PB2484 slice).** A host expression for hashed record bytes and the store byte where
open file description locks are absent: classic `fcntl(F_SETLK)` POSIX record locks are process-scoped (a second
handle's close in the same process drops them), so either a per-process lock-service that owns one descriptor per
physical file and reference-counts its holders, or `flock`-based per-record lock files. Record the choice in
`docs/rearchitecture/DESIGN-runtime-library.md` and CONFORMANCE.md; until then the honest behavior on such hosts is to
refuse `SHARING WITH ALL OTHER` for a keyed file at OPEN (a file-sharing conflict, §9.1.13.9) rather than grant
sharing it cannot police — that interim choice is itself an owner decision.
