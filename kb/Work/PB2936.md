# PB2936 — record locks and the store mutex do not bind across run units off Linux and Windows

Filed 2026-10-10 by the train 1052 lander (phase 2) from the wave 1052 B implementer's report
(`E:\COBOL-coord\scratch\reports\w1052b-PB2484-report.md`, "New defects" item 1). Phase 1b wrote it into PB2660 as a
residue paragraph; PB2660 is `landed`, so the defect was invisible to `work.py next` and moves here.

**Where.** PB2660 (landed, train 1042) made the cross-run-unit RECORD locks and the store mutex of a shared RELATIVE or
INDEXED file real host locks: one byte per record key (hashed) and one store byte, taken through
`src/Cobol.Net.Runtime/IO/Sharing/HostRegionLocks.cs` — `Hold` (about line 102), `HeldByAnother` (about line 113) and
`Release` (about line 127). Each arm has an expression on Windows (`LockFileEx`) and on Linux (open file description
locks, `OfdRegionLocks.Available`) only; on every other Unix (macOS, the BSDs) `Hold` and `HeldByAnother` answer
`OfdRegionLocks.Result.Unavailable` and `Release` does nothing, so the run unit keeps only the guarantees it can keep
alone. PB2484 (train 1052) gave the §9.1.15 FILE lock a lock-file expression on those hosts
(`SidecarColumnLockHost`, one holder file per run unit), but a record byte cannot use a per-holder file.

**Failure scenario (§9.1.16, §9.1.13.8 1)).** On macOS, run unit A opens a RELATIVE file `SHARING WITH ALL OTHER`,
`LOCK MODE IS MANUAL`, and `READ ... WITH LOCK`s record 1; run unit B's `READ ... WITH LOCK` of record 1 answers I-O
status `00` where §9.1.13.8 1) requires `51` ("an attempt to access a record that is currently locked by another file
connector"), and B's REWRITE and WRITE succeed and race A's store writes with no store mutex: lost updates, silently.

**Repro.** PB2660's two-process probe, run on a macOS host: `E:\COBOL-coord\scratch\w1040u\probes\lka.cob` +
`lkb.cob`, driven by `l2.ps1` (B starts 3 s after A). Expected `B READ-LOCK 1 FS=51`; on macOS the lock is not taken.
CI has no macOS leg, so no gate sees it; a unit witness can force the "neither Linux nor Windows" arm the way
`RunUnitFileLock.Take(host, ...)` forces the sidecar host.

**Fix shape (a design, beyond the PB2484 slice).** A host expression for hashed record bytes and the store byte where
open file description locks are absent: classic `fcntl(F_SETLK)` POSIX record locks are process-scoped (a second
handle's close in the same process drops them), so either a per-process lock-service that owns one descriptor per
physical file and reference-counts its holders, or `flock`-based per-record lock files. Record the choice in
`docs/rearchitecture/DESIGN-runtime-library.md` and CONFORMANCE.md; until then the honest behavior on such hosts is to
refuse `SHARING WITH ALL OTHER` for a keyed file at OPEN (a file-sharing conflict, §9.1.13.9) rather than grant
sharing it cannot police — that interim choice is itself an owner decision.

## Landing (wave 1056 A)

Re-probed on this build: `RegionLocksDriftTests` and the two `CrossRunUnit*DriftTests` classes now run every scenario on
the host of the machine AND on a lock-file host forced through `HostRegionLocks.Forcing`; before the change the
"neither Linux nor Windows" arm answered `Unavailable` for every request, which is the note's silent data loss. The
interim refusal at OPEN (an owner decision) was not needed: the sharing is policed.

- ⛔ The fix shape chosen is the note's second option made per-holder, not per-record: **a held byte is a lock file**
  (`r<byte as 16 hex digits>-<S|X>-<guid>`) in the physical file's `.wolk-*` lock directory, on the same
  `SidecarLockFiles` primitive as the §9.1.15 columns (`src/Cobol.Net.Runtime/IO/Sharing/SidecarRegionLocks.cs`).
  One file per record per holder, never one shared file per record: a shared file would have to be deleted by its
  releaser while another run unit opens the same name (the lock-file/unlink race), and per-holder names make every
  name one holder's for ever. `fcntl(F_SETLK)` was rejected as in PB2484 (process-owned, variadic on Apple arm64).
- RE-ARCHITECTED (CLAUDE.md rule 5): the estimate "a design beyond the PB2484 slice" meant the byte API had to stop
  being keyed on a `SafeFileHandle`. A connector now holds ONE `RegionLocks` endpoint (`HostRegionLocks.Open`, made by
  `IRegionLockHost`): `HandleRegionLocks` (Windows `LockFileEx`, Linux OFD — the old code, moved) or
  `SidecarRegionLocks`. `FileConnector.RecordLockHandle`/`RecordLockHandleWritable` became `RecordLocks`;
  `KeyedConnector`, `SequentialConnector`, `PhysicalFileTable` and `KeyedStoreTable.MutexHolder` carry the endpoint;
  `OfdRegionLocks.Result` became the top-level `RegionLockResult`. Adding a host is one class and one line.
- Semantics: exclusive refused by any other live holder, shared by an exclusive one, the asker skips its own file;
  publish-then-test (two simultaneous exclusive requests are never both Ok); a waiting hold retries with jitter; an
  unobservable holder is `Held` to a non-waiting hold and `Unavailable` to a waiting one (determination in DOC-A.1-75).
- Witnesses: `RegionLocksDriftTests` (the contract over both hosts: exclusive/shared, dispose, waiting hold, 100-round
  simultaneous race, wire names, sweep of a dead leftover, unobservable holder, unwritable directory, host choice,
  seam scoping); `CrossRunUnitKeyedStoreDriftTests` and `CrossRunUnitSequentialLockDriftTests` (`51` across run units,
  RETRY outside the mutex, no lost update, duplicate-key walk) with a `RegionHostKind` parameter.
  Trap: the `HostCarriesRegionLocks` guards are gone, so these tests no longer skip on a host without byte-range locks.
- Not done, by design: no macOS CI leg exists, so the macOS-specific part (Apple's kernel `flock` behaviour) is
  witnessed only through the managed lock-file host on Windows and Linux.
## Finisher after train 1056b ejected the branch (operator, 2026-10-11 ~02:40 PDT)

Owner 2026-10-11 ~02:05: "Finish tonight". Train 1056b ejected cluster A (`t1056b-lander-report.md`) for two
mechanisms; both are fixed at the root on `worktree-wf_8f6c2cfa-5a7-1` after a merge of main (f91823991).

- **The timing red** (`SidecarColumnLockHostDriftTests.ManyTestersSweepingOneDeadFileNeverRefuseEachOther`, round 11
  `Refused, Refused, Held, Refused` under the loaded lander gate, green alone). Where share modes are mandatory a lock
  file deleted while another tester's probe has it open stays listed, DELETE-PENDING, and every open of it is "access
  denied" -- the answer of an unobservable holder. `ProbeLockFile` asked again five times, 1 ms apart, and the lander's
  stress harness showed no bound and no listing can tell the two apart. Fix: no name a prober reads is deleted in place.
  `SidecarLockFiles.Retire` renames the file to `gone-<guid>` (a wire value no tester probes) before deleting it, for
  the sweep (`Observe`), an abandoned publication and a holder's CLOSE; a Unix unlink is atomic and unchanged. The
  probe asks once: "access denied" is always an answer. The window is an open that RACES the delete (the lander's
  harness: 75 % of the denied opens found the name already unlisted; a probe merely held open across the delete does
  not reproduce it on this ReFS volume, which deletes the name at once), and an open that races a rename finds the file
  or no file. Witness: `TestersSweepingOneDeadFileNeverReadItAsUnobservable` (8 testers sweep one dead file, 300
  rounds, not one probe may answer `Unobservable`): with `Retire` deleting in place 20 probes did (RED); with the fix 0,
  three runs out of three (about 0.45 s each).
- **The review finding** (a lock directory the user may enter but not list). `Directory.EnumerateFileSystemEntries`
  threw `UnauthorizedAccessException`, which `SidecarColumnLockHost.Establish` and `SidecarRegionLocks.Hold` mapped to
  `Unavailable`: an OPEN granted where 9.1.15 2) refuses ('61') and a READ WITH LOCK given a record 9.1.13.8 1) refuses
  ('51'). Fix: the listing's denial is unobservable as a whole (`TestOthers` refuses a row that refuses any column;
  `Look` answers `Conflict.Unobservable`). Sibling found on the way and fixed: a lock file copied only its directory's
  read and write bits, so in a directory whose owner bits lack read the holder could not probe its own file, `Publish`
  answered null and the OPEN was granted with no lock; `OpenLockHolder` now always keeps the owner's own read and write.
  Witnesses (Unix modes, nothing witnessed as root): `ALockDirectoryThatCannotBeListedRefusesAndLeavesNothing` (search
  only, and write plus search) and `RegionLocksDriftTests.ALockDirectoryThatCannotBeListed_IsHeldForTheNonWaiting_
  AndUnavailableForTheWaiting`.
- The macOS lead stays as the lander wrote it: no macOS CI leg exists, so Apple's `flock` semantics are taken from
  .NET's source (the lock-file host runs on every machine in the unit tests).
