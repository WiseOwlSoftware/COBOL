# PB238

**Rows:** `SR-14.9.4.3-17`, `SR-14.9.4.3-20`, `SR-14.9.4.3-23`, `GR-14.9.4.4-8`, `GR-14.9.4.4-9`

a Format-2 BY VALUE argument is bound as an arithmetic expression and crosses as `ManagedPointer<long>` with a hard-coded 18 digits, so a 19+-digit or unsigned-container identifier-4 truncates — while the boolean-expression-1 channel is refused outright and GR9a2's non-receivable identifier and SR20's object-property operand have no arm at all.

Rows: SR-14.9.4.3-17 (identifier-4 and every identifier inside arithmetic-expression-1 / boolean-expression-1 is a SENDING operand), SR-14.9.4.3-20 (mode transitivity, 'except when identifier-4 is an object property'), SR-14.9.4.3-23 (literal-2 shall be numeric, or its corresponding formal is BY VALUE), GR-14.9.4.4-8 (Format 2's operand classification), GR-14.9.4.4-9 (GR9's mode derivation from the corresponding formal). ONE arm of one binder, five rules.

THE CONTRAST THAT LOCATES THE DEFECT. CallBinder's BY CONTENT arm REDUCES BEFORE IT CLASSIFIES, exactly as GR8 requires: `ConditionBinder.UnwrapBareBool(cBool)` collapses an operator-free booleanExpression to its bare valueOperand; `var cDref = byContent.dataReference() ?? ConditionBinder.SoleDataReference(cArith)` recovers a lone identifier that arrived inside an arithmeticExpression node; `cLit` is tested BEFORE `cArith`; and only the residual expression binds through IntrinsicBinder.OperandOf(host.Expr.BindExpr(cax)). The grammar comment at callByContent records the same intent and the alternation order (`literal | dataReference | arithmeticExpression`) is what preserves it. conformance:2023/pb46_call_format2_as_nested pins all three shapes distinctly under AS NESTED (`BY CONTENT N`, `BY CONTENT 42`, `BY CONTENT N + 1` / `N * 2 - 3`; .out GOT 000E / 004B / 000F / 000G over `01 N PIC S9(4) VALUE 5`). THE BY VALUE ARM HAS NO COUNTERPART: `callByValue : BY? VALUE arithmeticExpression` binds unconditionally as `new BoundComputedOperand(host.Expr.BindByValueExpr(byValue.arithmeticExpression()))` — a lone identifier-4 or literal-2 IS regarded as an arithmetic expression, precisely what GR8 forbids.

DEFECT 1 — THE WRONG ANSWER (GR-14.9.4.4-8). CallEmitter.ArgText's BoundComputedOperand case emits `new CobolArg({mode}, ManagedPointer<long>.Cell((long)({x.Expr})), 18, {x.Scale})` — the operand's own digit count is replaced by the LITERAL 18 and its carrier by `long`. CobolArgAdapt.TextValue/Text build their NumProfile from `args[i].Digits`, so they see 18 rather than the item's picture, and a 19+-digit or unsigned-container BY VALUE identifier-4 truncates through the long lane with no diagnostic. The tell is already in the tree: CheckByValueClass has to unwrap `operand.Expr is BoundNumRef { Place: … }` to recover the identifier-ness GR8 says should never have been lost, and only for the SR22 class screen.

DEFECT 2 — ONE THIRD OF SR17's OPERAND SET IS REFUSED. CallBinder's boolean arms raise DiagnosticCatalog.CallContentOperandFormat with the in-code text 'the boolean value channel does not yet cross a CALL boundary (the INVOKE side landed as PB46's BoundInvokeArg.ContentBool; the CALL argument model has no counterpart)' and return BoundNop, so no identifier inside a boolean-expression-1 is ever classified at all. Legal Format-2 source is rejected.

DEFECT 3 — GR9's TWO UNSERVED LEGS (GR-14.9.4.4-9). PB131 landed the formal-mode derivation: `USING BY VALUE A B` against `BY VALUE LA BY REFERENCE LB` passes B by reference and the callee's writeback is VISIBLE (golden pb131_gr9_formal_mode pins the arm that used to be the DIVERGES — the old transitive mode passed B detached and the store was silently lost); the keyword-less literal/expression parse and bind BY CONTENT semantics (9a2's literal leg, PB130); and BY is optional before all three keywords. What remains: (a) 9a2's non-receivable-identifier leg — the bare arm resolves through `host.Expr.ResolveReceiving` (:250), so an identifier NOT permitted as a receiving operand draws an unsupported operand instead of passing BY CONTENT as 9a2 requires; (b) a bare literal whose corresponding formal is BY VALUE binds Content-mode — the VALUE outcome happens by the copy-out skip, not by 9b's mechanism, so it is right by accident and will not survive a change to the copy-out; (c) prototype formals do not exist, so only AS NESTED reaches a formal at all (that leg is the program-prototype-registry note's).

DEFECT 4 — SR20's CARVE-OUT IS UNMODELLED. 'except when identifier-4 is an object property': BoundStores exists for the §8.4.3.9.4 desugar and the CALL argument path never consults it. (PB131 did land what this row originally named: the unsanctioned mode threading is gone on both sides — Format 2's bare receiving-permitted identifier derives its mechanism from its own formal, and Format 1's BY VALUE arm is rejected outright, so BY VALUE is transitive under no path.)

DEFECT 5 — SR23 IS ENFORCED WITHOUT BEING NAMED. The expression spine bottoms out at `primaryExpression : numericLiteral | ZERO_ARITH | functionCall | dataReference | LPAREN arithmeticExpression RPAREN`, so `CALL 'P' USING BY VALUE 'ABC'` does not parse (and the figurative ZERO is correctly admitted through ZERO_ARITH per §8.3.3.6.3 SR1a) — the standard's verdict is right, but delivered as a raw ANTLR 'no viable alternative' with no COBOLNET code and no cited rule, and no fixture positive or negative reaches it (a grep of tests/ for 14.9.4.3 finds only SR16's pb46-call-as-prototype-name and SR22's pb6-call-by-value-alphanumeric). SR23's second subject — 'or its corresponding formal parameter is specified with the BY VALUE phrase' — is unreachable for the same reason as GR9 leg (b).

WHAT WOULD CLOSE IT: classify a BY VALUE operand the way the BY CONTENT arm does (sole-dataReference / literal recovery before the expression bind) so the argument carries the item's own Digits/Scale/carrier; a ContentBool slot on BoundCallArg mirroring BoundInvokeArg.ContentBool; a 9a2 arm that probes rather than resolve-receives; a 9b arm that sets Value mode from the formal; an SR20 consult of BoundStores; and an SR23 bind-time diagnostic. Goldens: a scaled and a 19+-digit PIC item passed BY VALUE and read back in the callee, a boolean-expression-1 under AS NESTED, a bare non-receivable identifier, and a negative for a non-numeric literal-2 expecting the named SR23 code.

SPEC REFS as carried by the rows: §14.9.4.3 SR17/SR20/SR22/SR23 (cite.py OK on their rows); §14.9.4.4 GR8/GR9a1/GR9a2/GR9b; §8.4.3.9.4; §8.3.3.6.3 SR1a; §8.3.2.4.3 (a non-underlined format word is optional); §14.2.3 GR9/GR10.

## Mechanism

src/Cobol.Net.Compiler/Binding/Procedure/Verbs/CallBinder.cs#BindCall — the BY VALUE arm at :227-232 (`new BoundComputedOperand(host.Expr.BindByValueExpr(byValue.arithmeticExpression()))`, with no sole-dataReference/literal recovery), the boolean refusals at :203-205 and :276-277 (DiagnosticCatalog.CallContentOperandFormat), and the bare arm's ResolveReceiving at :250 — landing in src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs#ArgText's BoundComputedOperand case (:351-363), which emits `new CobolArg(mode, ManagedPointer<long>.Cell((long)(expr)), 18, scale)`; grammar `callByValue` at CobolParserCore.g4:1092
