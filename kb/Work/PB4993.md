# PB4993 - lineage slice 2: the change record and its recording path

docs/rearchitecture/DESIGN-spec-conformance-review.md §10.2, slice 2. `inventory-schema.json` gains the `next` field of an older edition's row (`kind`, `to`, `edition`,
`bridge`, `reason`, `source`; its evidence is the citation of the row and of each `to` rule, read from their
catalogs and never stored, each `cite.py --check`ed) and the catalog
gains each rule's `status` (normal or obsolete, read from the edition's text by `extract_rule_catalog.py`: a fact
of the rule, never of the store). A KEPT row may carry no verdict fields of its own (its chain's
newest row holds them). `record_verdicts.py --edition 1985` is the one writer. A derived batch turns the audit run's
upheld SAME answers (state `E:/COBOL-coord/scratch/audit-1985/state-route`, `results.json` CARRIES: 759 rules) into KEPT
records, the way the 2023 derived batches record (`derive_verdict_batch.py`).

**State after PB4992 (wave 20261926, group A).** In place: the change record's shape and validator
(`lineage.next_errors`, `NEXT_KINDS`, `NEXT_KEYS`), the KEPT rule's refusal of its own verdict, `record_verdicts.py
--edition 1985` (validates with the edition's `adjudicated` fields, `editions.of` in the schema; writes through the store; a 1985 KEPT
dry-run probe validated), and `lineage.py kept-batch --state DIR --out FILE` (the audit's CARRIES rules as KEPT
records). `status` LEFT the store in PB4992 (a catalog fact, as this note says) and is not yet in the 1985 catalog.
Still to do: (1) the 1985 catalog's `status` (§1985:I.1.5.2.3 defines an obsolete element; the text marks each by a
sentence "… is an obsolete element in Standard COBOL" in the element's section and lists them at XVII-81; a WHOLE-element
section (ALTER, ENTER, DATA RECORDS, LABEL RECORDS, VALUE OF, RERUN, MULTIPLE FILE TAPE, the Identification Division
comment paragraphs) marks every rule of the section, but a PARTIAL one (GO TO's optional procedure-name, the STOP literal,
OPEN REVERSED, MEMORY SIZE in OBJECT-COMPUTER) needs the rule-level reading, a design question to settle first);
(2) `next`'s kinds and keys as data in `inventory-schema.json` (today they are `lineage.py` constants);
(3) record the kept batch from the audit run and re-verdict.

**Decision on the obsolete standing (Mythos session, 2026-11-08, settling the design question above; revised after
review w20261927a R1-1).** The authority is the standard's own enumerated list, §1985:C.1 (the obsolete language
element list, 18 entries), which §1985:I.1.5.2.3 defines; the in-section sentences ("... is an obsolete element in
Standard COBOL") restate it. The list is held ONCE as data beside the 1985 catalog extractor, one entry per list item:
its number, its name, the term that names it (ALTER, RERUN, REVERSED, the literal of STOP, the optional
procedure-name-1 of GO TO format 1, MEMORY SIZE, the KEY phrase of DISABLE and ENABLE, ALL literal with a numeric or
numeric edited item, double character substitution, ...) and the sections it appears in. The marking is decided PER
SECTION, never by the kind of element, because several whole elements have no section of their own:
OWN or SHARED is DERIVED from the section's heading (OWN when it names the entry's term), never held in the data, so
the two cannot disagree (review R2-1). The lists below are examples; the data names every section:
- an OWN section (one whose heading names the element: the ALTER statement, the ENTER statement, the Sequential I-O
  DATA RECORDS, LABEL RECORDS and VALUE OF clauses, the DATE-COMPILED paragraph, the Debug and
  Segmentation modules) marks every rule of the section obsolete;
- a SHARED section (one that also holds current syntax: Relative and Indexed I-O-CONTROL beside SAME, the Sequential
  I-O-CONTROL paragraph, the Relative and Indexed FD rules, VI 3.2 where AUTHOR, INSTALLATION, DATE-WRITTEN and
  SECURITY stand beside PROGRAM-ID, OPEN, STOP, GO TO, OBJECT-COMPUTER, DISABLE, ENABLE) marks obsolete only the
  syntax and general rules that name the entry's term. Its general format stays current even where it carries the
  obsolete syntax: the obsolete part is the subject of the marked rules, and what a later edition does to the format
  is the format's own `next` record (CHANGED), never its status.
- The status names its list entry (`obsolete: C.1(n)`), so a diagnostic and the conformance statement cite it.
A drift test holds the data to the text: every one of the 18 entries resolves to at least one rule; every "is an
obsolete element" sentence in the transcription falls in a section some entry names (the Sequential MULTIPLE FILE
TAPE and RERUN sections, the Sort-Merge SD and the Report Writer I-O-CONTROL and FD included); no general format of
a SHARED section is marked; and no rule outside an entry's sections is marked. A later edition with its own obsolete list gets its own data file read by the same code, no
edition branch.

## Landing
- `inventory-schema.json#next` — the change record's keys and kinds; a kind is its flags (`to`, `reason`, `chained`), and exactly one kind is chained (KEPT). Read it through `Schema.next`; never spell a kind.
- `scripts/spec/element_standing.py#apply` — a rule's archaic or obsolete standing is decided per section (OWN by heading, else SHARED: SR/GR naming a term), through the one call both catalog arms make; `status` lives in the catalog, never the store. An edition's lists are one data file, `spec-element-standing-<edition>.json` (`STANDING_OF`).
- `scripts/spec/audit_batch.py#kept_records` — the audit's CARRIES rules as KEPT records with no `reason` (`audit_batch.py kept-batch`); record with `record_verdicts.py --edition 1985`. Never import the audit from `lineage.py`: the view a compiler test runs imports the lineage.
- `scripts/spec/inventory_schema.py#Schema.next` — read when first asked, so a history reader joining main's 2023 inventory under a schema that predates `next` loads (the WITNESS LOSS audit, gate run 000001); add a new schema part the same way when only one reader needs it.
