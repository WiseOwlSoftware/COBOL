# PB4993 - lineage slice 2: the change record and its recording path

docs/rearchitecture/DESIGN-spec-conformance-review.md §10.2, slice 2. `inventory-schema.json` gains the `next` field of an older edition's row (`kind`, `to`, `edition`,
`bridge`, `reason`, `source`; its evidence is the citation of the row and of each `to` rule, read from their
catalogs and never stored, each `cite.py --check`ed) and the catalog
gains each rule's `status` (normal or obsolete, read from the edition's text by `extract_rule_catalog.py`: a fact
of the rule, never of the store). A KEPT row may carry no verdict fields of its own (its chain's
newest row holds them). `record_verdicts.py --edition 1985` is the one writer. A derived batch turns the audit run's
upheld SAME answers (state `E:/COBOL-coord/scratch/audit-1985/state-route`, `results.json` CARRIES: 759 rules) into KEPT
records, the way the 2023 derived batches record (`derive_verdict_batch.py`).

**State after PB4992 (wave 20261926, group A).** In place: the change record's shape and validator
(`lineage.next_errors`, `NEXT_KINDS`, `NEXT_KEYS`), the KEPT rule's refusal of its own verdict, `record_verdicts.py
--edition 1985` (validates with the edition's `adjudicated` fields, `editions.of` in the schema; writes through the store; a 1985 KEPT
dry-run probe validated), and `lineage.py kept-batch --state DIR --out FILE` (the audit's CARRIES rules as KEPT
records). `status` LEFT the store in PB4992 (a catalog fact, as this note says) and is not yet in the 1985 catalog.
Still to do: (1) the 1985 catalog's `status` (§1985:I.1.5.2.3 defines an obsolete element; the text marks each by a
sentence "… is an obsolete element in Standard COBOL" in the element's section and lists them at XVII-81; a WHOLE-element
section (ALTER, ENTER, DATA RECORDS, LABEL RECORDS, VALUE OF, RERUN, MULTIPLE FILE TAPE, the Identification Division
comment paragraphs) marks every rule of the section, but a PARTIAL one (GO TO's optional procedure-name, the STOP literal,
OPEN REVERSED, MEMORY SIZE in OBJECT-COMPUTER) needs the rule-level reading, a design question to settle first);
(2) `next`'s kinds and keys as data in `inventory-schema.json` (today they are `lineage.py` constants);
(3) record the kept batch from the audit run and re-verdict.

**Decision on the obsolete standing (Mythos session, 2026-11-08, settling the design question above).** The authority
is the standard's own enumerated list, §1985:C.1 (the obsolete language element list, 18 entries), which
§1985:I.1.5.2.3 defines; the in-section sentences ("... is an obsolete element in Standard COBOL") restate it. The
list is held ONCE as data beside the 1985 catalog extractor, one entry per list item: its number, its name, its
sections (locators), and, for a PARTIAL element only, the term that names it (REVERSED, the literal of STOP, the
optional procedure-name-1 of GO TO format 1, MEMORY SIZE, the KEY phrase of DISABLE and ENABLE, ALL literal with a
numeric or numeric edited item, double character substitution). The extractor writes each rule's `status` from it:
- a WHOLE element (a statement, a clause, a paragraph, a module: ALTER, ENTER, DATA RECORDS, LABEL RECORDS, VALUE OF,
  RERUN, MULTIPLE FILE TAPE, the five Identification Division paragraphs, the Debug and Segmentation modules) marks
  every rule of its sections obsolete;
- a PARTIAL element marks obsolete only the syntax and general rules of its sections that name its term. A general
  format that also carries current syntax (OPEN, STOP, GO TO, OBJECT-COMPUTER, DISABLE, ENABLE) stays current: its
  obsolete part is the subject of the marked rules, and what a later edition does to the format is the format's own
  `next` record (CHANGED), never its status.
- The status names its list entry (`obsolete: C.1(n)`), so a diagnostic and the conformance statement cite it.
A drift test holds the data to the text: every one of the 18 entries resolves to at least one rule, every
"is an obsolete element" sentence in the transcription falls in a section some entry names, and no rule outside an
entry's sections is marked. A later edition with its own obsolete list
gets its own data file read by the same code, no edition branch.
