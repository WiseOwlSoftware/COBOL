# PB3331 — the page layer and the generation ledger

Implement FROM `docs/rearchitecture/DESIGN-runtime-library.md` §2.2.1, sections 2.2.1.4 (the PAGE and META layouts, the
POINTER), 2.2.1.6 (rules R1-R6, as corrected on 2026-10-17 after the round-1 review) and 2.2.1.12 (the drift tests), not from
this note. This note is the register entry.

## The first deliverable: the simulator and its cases, before the engine (PB3330's Route from 2026-10-18)

This group's FIRST deliverable is the deterministic fault-injecting page medium of 2.2.1.12, `MemoryPageMedium`: an
in-memory `IPageMedium` that logs every write and sync, can lose every unsynced write, tear a page, serve an older version
of a page, and interleave two run units at every step. With it come the executable cases, written FROM THE DESIGN TEXT
BEFORE the engine's logic exists: rules R1-R6 of 2.2.1.6, and the crash points of 2.2.1.16 and the interleavings of
2.2.1.17 WHOSE PATHS THE PAGE LAYER OWNS (a changing statement, a promotion, the retirement, the fence, growth, creation,
the sync points, and the two-run-unit rows ordered by the store mutex, the stamps and the PROMOTING flag), each expected
result taken from the section's text (and from the spec rule the section cites), never from what an engine does. The
rows whose paths a LATER core group builds - the record statements' lock tests and lock publication, the alternate-key
and relative statements, the connectors' coherence (PB3333, PB3334, PB3335) - are written in the same commit as PENDING
rows (the next paragraph), and the group that builds the path turns each into a running case in its own landing (its
Tests section names them: "the PENDING rows of 2.2.1.16 and 2.2.1.17 that this group's paths cover"). That commit holds the medium and the cases and no `PagedFile` logic. Where a case shows the design text
wrong, incomplete or self-contradictory, the implementer stops, corrects 2.2.1 in the same branch (CLAUDE.md rule 2: the
doc moves with the change) and reports the correction; one implementer round per correction, and no prose-only review
round is dispatched on the design. Only then is `PagedFile` written against the cases.

The cases that concern the held transaction slice (COMMIT, ROLLBACK, the dead-owner step and the holdings: PB3337,
`status: owner`), and the rows a later core group's path owns (above), are written in the same commit as PENDING cases: each row carries its expected result from the design
text and is not run by the gate (no `Skip`: a pending row is not yet a test, and the gate counts a skipped case). PB3337,
when it proceeds, turns the held slice's rows into running cases first, and each core group (PB3333, PB3334, PB3335) turns
the rows its own paths cover in its own landing (their Tests sections say so).

## Mechanism

A new folder `src/Cobol.Net.Runtime/IO/Store/` holding the engine's lowest layer, used by nothing in the connectors yet
(PB3333 is the first caller):

- `IPageMedium` — read page n / write page n / sync / page count / set page count, over 4 096-byte pages. Two implementations:
  `HandlePageMedium` (production: `RandomAccess.Read`/`Write`/`FlushToDisk` through a connector's `SafeFileHandle`, one page per
  call) and, under `tests/`, `MemoryPageMedium` (an in-memory page array that logs every write and sync, and can LOSE every
  unsynced write, KEEP them, TEAR one named page, or SERVE AN OLDER VERSION of one named page — the crash simulator of 2.2.1.12).
- `PageHeader` / `PageKind` / `PagePointer` — the 32-byte header (kind, flags, entries, CRC-32C checksum over bytes 0..3 and 8..4095,
  generation, self, next), one encoder and one decoder; the 12-byte POINTER (page number + the generation of the write it
  names, 2.2.1.6 R3); a read through a pointer verifies checksum, `self` and generation == the stamp, and a page that fails is
  a TORN read, surfaced as a typed result, never an exception swallowed.
- `MetaPage` — the format-6 meta layout of 2.2.1.4 (magic `CBNFSTR` + version 6 at offset 32 — 5 is the whole-store header —, the §9.1.6 attributes in format 4's
  descriptor encoding, generation, release mint, page count, transaction mint, the four root POINTERS, committed generation —
  the slot's BASE — the `stamp mint` (the highest generation CLAIMED, round 3), the flags byte whose bit 0 is PROMOTING,
  `committing` (the transaction id a COMMIT's promotion commits, round 4: set by the claim, carried by the slot write,
  cleared by the retirement or an unwind; 0 for every promotion of this group) and the holdings root (PB3337's tree; 0 here);
  the per-key descriptors from offset 169), encoder and decoder; `Describes(path)` reads pages 0 and 1 through `HostFile.OpenAuxiliary`, takes the
  valid slot with the higher generation, and answers `StoreFormat` {Empty, Described, Foreign} so
  `KeyedConnector.FixedAttributeConflict` and `SequentialConnector`'s keyed-store check can move to it in PB3333/PB3334 (a
  format-4 file is Foreign: '39', no reader kept).
- `Ledger` — the set of pages allocated since the committed generation (page → last-write generation, state ∈ {fresh,
  released, freed}), persisted as a small tree of PB3332's engine; until PB3332 lands it is an in-memory map plus a page-array
  serialization so this group's crash matrix can run (that serialization is replaced, not wrapped, by PB3332). It does not list
  its own pages.
- `PagedFile` — the RESERVATION (a statement reserves its pages first: released pages, then one batch of the lowest FREE-tree
  pages sized to the statement's bound, then growth; nothing is allocated once the ledger is being written), the R1-R4 write
  discipline (`WritePage` refuses a page that EITHER slot's tree references — there is no in-place rewrite; a freed page is
  quarantined; a released page is reusable one statement later), the GENERATION CEILING (`GenerationCeiling` = 4 096: a
  statement whose generation — its CLAIM — would pass the base + 4 096 promotes first; a ledger past 1 024 pages promotes at
  the next statement), the CLAIM (2.2.1.7, rounds 3 and 4: a changing statement claims in the store's memory — every mint
  it will advance, `stamp mint`, `transaction mint`, `release mint`, and its own last claim, which a refused statement
  leaves raised — and, under the mutex, writes page 2 with them, roots and `generation` unchanged, BEFORE its first page
  write; the next claim is one above the highest of the generation last seen, page 2's mint and the own last claim; every
  page 2 the store writes is written from that memory; the caller's entry raises its next claim above a mint it finds moved
  and resolves a PROMOTING flag it finds set; a NO OTHER statement's claim is the memory alone, which its CLOSE's promotion
  carries to page 2), `Promote(committing)` (R5: the claim with PROMOTING and `committing` — 0 for every promotion but
  PB3337's COMMIT; for the fence, page 2 rewritten to the ADOPTED meta at F — then sync,
  then BOTH slots read and the meta written into the committed slot holding the lower valid generation, sync, then the
  RETIREMENT statement — the promoted ledger's released and freed pages moved into the FREE tree, the promoted ledger's OWN
  pages recorded as `freed` (R4: the committed slot references them until the next promotion), its fresh entries dropped, a
  page the retirement reserved for itself fresh, page 2 written with the promotion's generation as its base and the flag
  clear; CLOSE syncs once more after it), `CompletePromotion` (R5's restart rule, round 4, for a flag left by a dead OR a
  refused promoter: both slots read; a slot naming page 2's generation → the promotion landed and is completed — the syncs
  run, the retirement claims above the dead one's mint and removes the entry `committing` names, PB3337's; no slot and
  `committing` 0 → `Promote` runs again from the claim; no slot and `committing` set → UNWOUND: page 2 rewritten with the
  flag clear and `committing` 0, nothing else written), `Open` (R6,
  run by the caller under the store mutex: the three slots read and validated, the committed meta C = the valid committed slot
  with the higher generation G, '30' when neither validates; the work slot classified as a DESCENDANT (base = G), the
  PROMOTION SOURCE (base < G, generation = G: the retirement never landed) or FOREIGN; a DESCENDANT adopted when every listed
  `fresh` page verifies and REJECTED otherwise; then, through the store's first WRITABLE handle, the FENCE: `Promote` (its `committing` = C's when C is adopted, 0 when W is: a DESCENDANT's nonzero value is an unlanded COMMIT's claim, unwound) of the
  adopted meta at generation G + 4 097 with its retirement, which also reclaims a rejected DESCENDANT's readable ledger (its
  listed pages and its own) into the FREE tree — an INPUT handle adopts in memory and writes nothing; the dead-owner step is
  PB3337's and this group reads an empty TRANSACTIONS tree), `Create` (`SetLength` to three pages, then the three meta
  pages), and `IoCounters` (pages read, pages written, syncs, per statement) for PB3336's witnesses.

## Tests

- The crash matrix of 2.2.1.12, every row and column, with the expected cell the section states: {a CLOSE then an OPEN;
  process death after a statement; process death mid-statement; process death between a promotion's slot write and its
  retirement; a fence landed and its retirement did not; power loss with every write durable; power loss losing the last k
  writes; a torn fresh page; a torn work slot; a torn committed slot; both committed slots torn; an OPEN while another handle
  holds the file; an INPUT OPEN of a crashed file then a writable OPEN in another run unit while the reader is live; a death
  mid-statement in one run unit, a completed statement of another live run unit, then a power loss keeping the dead pages
  and losing the live ones (round 3, R3-4); a promoter's death between its claim and its retirement's page 2 while another
  run unit is live, then that run unit's statement} × {no transaction; a transaction open at the crash — the transaction
  column lands with PB3337} → the adopted meta and a consistent file, both committed slots and page 2 naming it after a
  writable OPEN; '30' for both committed slots torn; the committed meta for the R3-4 row; the completed promotion plus the
  live statement for the promoter's-death row. Every row of 2.2.1.17's interleaving tables and every row of 2.2.1.16's
  crash-point table that this group's paths own
  (the statement, the promotion, the fence, creation, growth) is a case too, and so is every row of its round-4
  refused-statement table for those paths (the run unit alive after the refusal, then its next statement, CLOSE, OPEN and
  another store's statement).
- R1: no write targets a page the committed OR the work tree references (the medium's write log, both trees walked after
  every statement).
- R2: the ledger lists exactly the pages allocated since promotion with their last generation and state; a released page is
  reused only by a later statement; no allocation after the ledger write starts; the 4 097th statement after a promotion
  promotes before it claims.
- R3: a page served at an older version under a stamped pointer is refused as torn; the medium's write log never records one
  (page, generation) pair twice — across a rejection and a restart, across a death mid-statement and a restart, and across
  a death mid-statement in one run unit and the next statement of another on the same open file (two `PagedFile`s over one
  `MemoryPageMedium`, the second claiming above the first's mint); a changing statement under the mutex writes page 2 twice
  (the claim before its first page write, roots unchanged; the completion last); a NO OTHER store's statement refused at
  its n-th write and then its CLOSE: the retirement's stamps lie above the refused claim (round 4, R4-3), and the power-loss
  variant that keeps the retirement's page 2 and loses the page the refused statement stamped rejects the work slot at the
  next OPEN; no mint on page 2 (`stamp mint`, `transaction mint`, `release mint`) ever decreases across the write log.
- R4: a page freed at generation G is not allocated before G's promotion, the promoted ledger's own pages included (after a
  CLOSE and ten WRITEs no write targets a page the committed meta's ledger root reaches).
- R5: every page the committed slot names was synced before the slot was written; two consecutive promotions write different
  slots; a promotion reads both slots before it chooses (two stores promoting in turn never overwrite each other's committed
  meta); every promotion is followed by its retirement (page 2 on the promotion's base, PROMOTING clear) before any further
  statement; the restart: the promoter dies after its claim, its first sync, its slot write, its second sync and some
  retirement pages, and another store's next statement completes the promotion before its own work; the same with the
  promoter REFUSED at each point (alive, '30', round 4): the next entry completes a landed promotion and runs an unlanded
  one again; with a nonzero `committing` and an empty TRANSACTIONS tree, an unlanded one is unwound (page 2 unflagged,
  `committing` 0) and a landed one completed — PB3337's COMMIT exercises the same rule with a transaction.
- The golden hex dump of an empty relative and an empty two-key indexed store (the three meta pages); the checksum catches one
  flipped bit in every page kind; `self` catches a page read from the wrong offset.
- A medium that refuses the n-th write of a statement leaves the file at the previous statement (atomicity).

  the work tree's pages the committed tree lacks, released referenced by neither, freed only by the committed one);

  retirement order; every operation of every page-layer path (a coherent statement, a NO OTHER statement, growth,

- **What the cases found in the engine:** a released page reused for the ledger's own chain kept its released entry
  (the ledger listed its own page as reusable, and the next statement overwrote a live page).
- **What the cases found in the design (2.2.1 corrected in the same branch):** the checksum must cover bytes 0..3 as
  well as 8..4095; the paged format is version 6 (5 is the whole-store header since PB1099) with the magic at offset 32;
  only an ALTERNATE key's descriptor carries a root; creation is a promotion of the empty store decided by one durable
  write (SetLength to three pages first left the old store adoptable after a death; SetLength to zero first, the next
  draft, destroyed the previous store at every refusal against §14.9.27.4 GR25 — branch review R1-3); a superseded

  the next fence's window); a restarted retirement writes its claim first; a rejected history's grown pages are reused

## Landing — for the next implementer

- `src/Cobol.Net.Runtime/IO/Store/PagedFile.cs#Begin` / `PageStatement` — the ONE statement path: `Begin(pageBound)` →
  `Write`/`Release`/`SetPrimeRoot`/`SetAlternateRoot` → `Complete` (or `Abandon` on a torn read). REUSE it for every
  tree (PB3332); never write a page around it. The trap: the bound is the statement's OWN pages; the FREE and LEDGER

  invalid key condition at a DELETE (§14.9.10.4 GR3/GR4 give a DELETE that condition only for a missing record;
  `PendingStoreCases` carries both cells). A promotion, CLOSE and OPEN never answer it.
