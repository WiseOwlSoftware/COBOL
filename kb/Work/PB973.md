## Reproduced

`reg11/i3n.cob`:

```cobol
       METHOD-ID. SETV.
       DATA DIVISION.
       LINKAGE SECTION.
       01 N PIC 9(3).
       PROCEDURE DIVISION USING N.
           MOVE N TO V
```

→ `error: backend compilation failed (generated C# at i3n.g.cs)` · `(26,39): error CS1628: Cannot use ref, out, or in
parameter '__N' inside an anonymous method, lambda expression, query expression, or local function` · the same at
`(40,32)`. rc=70. The generated code:

```csharp
    private const int __N = 1;   // paragraph count (all methods — one pc space)
    public virtual void SETV(ref long __N, bool __omitted0)
        long N = __omitted0 ? 0L : __N;      // LINKAGE formal N copy-in
        int __MDispatch(int __startPc, int __exitPc)
            while ((uint)__pc < (uint)__N)   // meant the const; binds the ref parameter
```

`N` is an ordinary user-defined word; no rule forbids it as a data-name in a method's linkage section. OO design D1:
an emitted-code compile error is an emitter bug.

## Cause and what the fixer owes

The emitter derives the ref-parameter name by prefixing `__` to the COBOL name, in the SAME identifier space as its own
`__`-prefixed synthesized members (`__N`, and every other uppercase `__X` the emitter declares at class or method
scope). The fix is structural, not a rename of `__N`: formal-derived C# names must come from a namespace that cannot
collide with emitter-reserved names (one naming authority — `NamingConvention` — with a drift test that enumerates
the emitter's reserved identifiers and proves no COBOL word can map onto one). Sweep: every `__`+name derivation
(program LINKAGE formals, function formals, RETURNING, BY VALUE, local-storage) and formals named like any other
synthesized member. OoEmitter.cs:276 is the class-const site the source report named.

## Landed (wave 51, group E)

Re-probed on the implementer's build of `5963d9ca0`: `i3n.cob` → the same two CS1628 errors, rc 70. After: `V=007`.
The fix is the NAMING AUTHORITY, not a rename of `__N`: every synthesized C# name that embeds a user-defined word is
now built by `NamingConvention` from a family with a NON-EMPTY tag — the method formal's `ref` parameter is
`__formal_<WORD>` (was the untagged `"__" + WORD`), and the six sibling derivations (`__addr_`, `__fkey_`, `__cap_`,
`__dbg_`, `__new_`, `__sum_`) moved there from `DataBinder.Ptr`/`BinderDriver`/`DataBinder.Odo`/`DataBinder`/
`OoBinder.InlineInvocation`/`DataBinder.Reports`. A user word never sanitizes to a leading `__` (§8.3.2.1 — `OK`), so
a tagged family can only meet a fixed `__X` name that starts with its tag. `SynthesizedNameFamilyDriftTests` (Unit)
proves (1) every family has a non-empty tag and the families are prefix-free, (2) no emitter-fixed `__X` string
literal in the compiler enters a family, (3) no code site builds `"__" + …`, and the two interpolated `$"__{stem}…"`
sites are adjudicated fixed stems. Sibling sweep: program/function LINKAGE carriers are positional (`__lnkpN`), the
universal-invoke slots positional (`__pN`/`__oN`), `__omittedN` positional — none word-derived. The report SUM counter
name also gained `Sanitize` (a hyphenated RD name spelled `__sum_RPT-A_0`, not a C# identifier; that CsName is
read by no emitter today — its profile is `Uid`-keyed and `ReportSumCounterPlace` addresses the engine by counter
id — so no observable change).
