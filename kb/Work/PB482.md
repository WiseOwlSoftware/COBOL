# PB482 — LANDED — legal source reaches a runtime loud

Found 2026-09-04 by the `PB205` implementer while sweeping `DataBinder.KeyReference`'s callers; re-derived
on this tree for this note.

## Repro

```cobol
       05 WS-CELL PIC 99 OCCURS 3.
       ...
       02 COLUMN 7 PIC 999 SUM WS-CELL(2).
```

Compiles clean; at run time the report's SUM addend delegate throws `NotImplementedCobolFeatureException:
report R-1: SUM addend not resolvable to storage (ISO §13.18.54.3 SR5)`. The program is legal and the
addend's value is `WS-CELL(2)`; it never runs.

## The rule

```
python scripts/spec/cite.py --check 13.18.54.3 "without the subscripting normally required"
OK  §13.18.54.3 4)
```

SR4's "without the subscripting normally required" governs only the report-section `data-name-1` form (a
sum counter referenced from a report group); SR5's `identifier-1` addend is an identifier in §8.4.3.1's
sense and may be subscripted like any other. The bind site, `BindSumClause` in
`src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs`, captures the addend through `KeyReference`, which keeps
the base name and qualifiers only, so the subscript never reaches the emitter and the emitter's addend
delegate finds no storage for a table item and throws.

## Fix shape

Thread subscript expressions from the data division: capture the addend as a written reference (PB205's
`ControlOperandRef` shape, extended to carry subscript expressions rather than only integer-literal
reference-modification bounds), resolve it at emit time through the ordinary subscript machinery
(`ReferenceResolver` — the same route a procedure-division `identifier` takes), and drop the loud. This is a
larger machine than PB205's literal ref-mod because the subscript may be an arithmetic expression or an
index-name evaluated at GENERATE time, not at bind. Goldens: a SUM over a subscripted addend with a literal
subscript, with an index-name, and with an `IX + 1` expression, each expected value derived from
§13.18.54.4's accumulation rules; the negative side is unchanged (a subscript on the report-section
data-name-1 form stays rejected).

### The rule, quoted

**The rule, re-derived.** `cite.py --check` on every citation below. §13.18.54.3 SR1 names three addend forms and
says "the SUM keyword may appear more than once"; SR5 is "If the addend is identifier-1, it shall specify a
numeric data item not defined in the report section"; SR7 is "Data-name-2 shall be the name of a detail. It may
be qualified only by a report-name". §8.4.3.1.2 **Format 2** makes an identifier a
*qualified-data-name-with-subscripts*, which is why the subscript is part of the operand and the note is right
that it can only be evaluated where the ordinary subscript machinery lives. §8.4.3.3.4 GR6 c) — "the categories
numeric and numeric-edited are considered class and category national if the usage is national; otherwise they
are considered class and category alphanumeric" — is what makes a REFERENCE-MODIFIED addend illegal rather than
merely unimplemented: SR5 asks for a numeric data item and a ref-mod cannot produce one. §13.18.54.4 GR1 gives
the ENTRY one counter and GR7 c) 2) attaches each UPON phrase to ITS SUM group. The printed general format was
rendered (PDF p487): `SUM` underlined, `OF` not — §8.3.2.4.3's optional word — the addend brace repeats, and the
whole `SUM OF … [UPON …]` group repeats. The transcription is faithful.

**The shape of the fix.** `ReportSumAddend` is the WRITTEN reference (parse context + base name + qualifiers),
captured by the one helper `SumAddendRef`, and its VALUE is bound in the PROCEDURE phase by
`ReportWriterBinder.BindReportGroupClauses` through the ONE `ExpressionBinder.BindExpr` — the `PRESENT WHEN` /
`VARYING` precedent, which already carried a report-section parse context across the phase boundary — and
rendered by the ONE `NumericRenderer`. That is what makes a literal, an index-name and an `IX + 1` subscript all
work without a second copy of the subscript machinery. `ResolveSumAddend` is the ONE arm choice (SR4's
report-section data-name-1 → the rolled-total staging; SR4 g)'s report-name-qualified form → the cross-report
staging, which was previously DEAD CODE because `dataReference` swallows the `OF` qualifier before
`sumOperand`'s own `OF reportName` alternative can see it; SR5's identifier-1 → resolution + the CATEGORY screen
nothing had ever performed). `UponDetailRef` + `ResolveUponDetail` give SR7 its screen and resolve through the
report-group funnel (`ReportGroupResolution`), which now has THREE consumers instead of two. The entry binder
collects EVERY `reportSumClause` of the entry into ONE `ReportSumModel` whose `Terms` each carry their own UPON
list (GR1 + SR1 + GR7 c) 2)), and the runtime's `SumEntry` holds a list of `SumTerm`s instead of one delegate
and one filter — `AddSum` registers the counter, `AddSumTerm` one group. Grammar: `SUM OF? sumOperand …`.

**Diagnostics:** COBOLNET2045 (SR5 — not a numeric data item, ref-mod included) and COBOLNET2046 (SR7 — not a

returned to the pool. The two cross-report stagings ride the shared COBOLNET0899 `recognized-not-implemented`
family (`report-sum-rolled-total`, the new `report-sum-upon-cross-report`).
