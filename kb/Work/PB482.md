# PB482 — OPEN — legal source reaches a runtime loud

Found 2026-09-04 by the `PB205` implementer while sweeping `DataBinder.KeyReference`'s callers; re-derived
on this tree for this note.

## Repro

```cobol
       05 WS-CELL PIC 99 OCCURS 3.
       ...
       02 COLUMN 7 PIC 999 SUM WS-CELL(2).
```

Compiles clean; at run time the report's SUM addend delegate throws `NotImplementedCobolFeatureException:
report R-1: SUM addend not resolvable to storage (ISO §13.18.54.3 SR5)`. The program is legal and the
addend's value is `WS-CELL(2)`; it never runs.

## The rule

```
python scripts/spec/cite.py --check 13.18.54.3 "without the subscripting normally required"
OK  §13.18.54.3 4)
```

SR4's "without the subscripting normally required" governs only the report-section `data-name-1` form (a
sum counter referenced from a report group); SR5's `identifier-1` addend is an identifier in §8.4.3.1's
sense and may be subscripted like any other. The bind site, `BindSumClause` in
`src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs`, captures the addend through `KeyReference`, which keeps
the base name and qualifiers only, so the subscript never reaches the emitter and the emitter's addend
delegate finds no storage for a table item and throws.

## Fix shape

Thread subscript expressions from the data division: capture the addend as a written reference (PB205's
`ControlOperandRef` shape, extended to carry subscript expressions rather than only integer-literal
reference-modification bounds), resolve it at emit time through the ordinary subscript machinery
(`ReferenceResolver` — the same route a procedure-division `identifier` takes), and drop the loud. This is a
larger machine than PB205's literal ref-mod because the subscript may be an arithmetic expression or an
index-name evaluated at GENERATE time, not at bind. Goldens: a SUM over a subscripted addend with a literal
subscript, with an index-name, and with an `IX + 1` expression, each expected value derived from
§13.18.54.4's accumulation rules; the negative side is unchanged (a subscript on the report-section
data-name-1 form stays rejected).


## The SECOND operand of the same clause, bound by the same reducing helper — measured 2026-09-13 by REGISTRAR #5

Row `SR-13.18.54.3-7` added to this note's `inventory_rows` (GAP, no verdict, no claimant before this
extension).

The `PB489` implementer report reported that `BindSumClause` captures **both** of the SUM clause's operand
families with a helper that throws away the part that decides the answer: `DataBinder.Reports.cs:755` binds each
addend with the bare `KeyReference(op.dataReference())` (this note's subject — the subscript is dropped), and
`:757` binds the `UPON` detail-names with the raw first-word reduction
`up.cobolWord()?.GetText() ?? up.GetText()`, so a qualified detail-name loses its qualifier. The report asked the
registrar to fold this into `kb/Work/PB205`; PB205 is **landed**, so folding an open defect into it would hide
it from `work.py next`. It belongs here instead: one method, one commit, one fixer.

### Measured — the UPON qualifier is dropped, and the answer is WRONG

`scratchpad/reg5/p8_upon.cob` (PROGRAM-ID `REG5P8`), `--std 2023 --run`. Two report descriptions, `R-ONE` and
`R-TWO`, each with a detail group named `D-LINE`. `R-ONE`'s control footing carries

```cobol
03 COLUMN 1 PIC 999 SUM WS-AMT UPON D-LINE OF R-TWO.
```

and the program GENERATEs `D-LINE OF R-ONE` only, never R-TWO's:

```
reg5p8a.txt (R-ONE):        reg5p8b.txt (R-TWO):
  05                          (empty)
  005
```

Expected `000` — the counter names R-TWO's detail, which is never generated. Observed `005`: the qualifier was
discarded and the UPON bound to `R-ONE`'s OWN `D-LINE`. Compiles clean, runs clean, prints a number that is not
the sum it was asked for. **Silent wrong answer on legal source.**

### The rule, quoted

```
$ python scripts/spec/cite.py --check 8.4.3.3.3 "Because the references to data items are restricted to identifiers, where data-name-n is used in a general format or syntax rule, then reference-modification is not permitted."
  OK  §8.4.3.3.3 5)  (Syntax rules)
```

and, decisive for this operand, §13.18.54.3 SR7 read in place at `specs/ISO_COBOL.md`:

> 7\) Data-name-2 shall be the name of a detail. **It may be qualified only by a report-name.**

The standard admits exactly one qualifier on data-name-2 and the binder admits none — so the ONLY qualification
the rule permits is the one that is silently dropped. (The control probe `scratchpad/reg5/p7_sum.cob` confirms
the ADDEND's qualification IS kept — `SUM WS-AMT OF WS-R` answers `009` — which is why this arm went unnoticed:
the two operands are bound four lines apart by two different helpers with opposite behaviour.)

### Code site

`src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs:755` (the addend, this note's original subject) and `:757`
(the UPON detail-name). The SOURCE clause five lines above at least refuses a subscripted or reference-modified
operand as recognized-not-implemented (`ReportSourceSubscripted`); the SUM clause's two operands do neither —
they reduce and continue.

The fix for `:757` is one call to `DataBinder.ClauseDataName` (a report-name-qualified lookup), not a second
reducing helper; the fix for `:755` is this note's existing Fix shape. Doing `:757` alone leaves the addend
broken and vice versa, and both are in the same `foreach`.
