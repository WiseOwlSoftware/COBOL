# PB4545 — dynamic-length-clause-not-supported: -std=cobol2014: the DYNAMIC LENGTH clause is refused ("syntax error, unexpected DYNAMIC")

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

Under `-std=cobol2014`, cobc 3.2 refuses the DYNAMIC LENGTH clause of a data description entry (a dynamic-length
elementary item, ISO/IEC 1989:2014) with "syntax error, unexpected DYNAMIC". Class: feature missing. Fuzz programs:
fz00252 and 10 more (night fuzz-batch-3000-20261103, slice D1).

## Minimal test case

Free reference format.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. DL1.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 D PIC X DYNAMIC LENGTH LIMIT IS 10.
PROCEDURE DIVISION.
    MOVE "HELLO" TO D
    DISPLAY "[" D "]"
    STOP RUN.
```

## Environment

`cobc (GnuCOBOL) 3.2.0`, WSL2 Ubuntu x86_64. Compiled with `cobc -x -free -std=cobol2014 -o p dl1.cob`; no executable
is produced, so nothing is run.

## Observed result

Compile, exit code 1:

```text
dl1.cob:5: error: syntax error, unexpected DYNAMIC
```

## Expected result (per ISO)

The program is legal and prints `[HELLO]`.

- §2023:13.18.19.1 (checked): "The DYNAMIC LENGTH clause specifies that the length of a data item can vary at runtime."
  §2023:13.18.19.2 (checked) gives the format `DYNAMIC LENGTH [ dynamic-length-structure-name-1 ] [ LIMIT IS integer-1 ]`.
- §2023:13.18.19.3 1) (checked): "The character-string specified in that PICTURE clause shall be one instance of the
  picture symbol 'N', or 'X'." D is PIC X.
- §2023:13.18.19.4 2) (checked): "Integer-1 specifies the maximum number of characters that can be contained by the subject
  of the entry." The limit is 10.
- §2023:8.5.1.10.4 (checked): "If a dynamic-length elementary item is a receiving operand and is not reference-modified, the
  new value becomes the content of the item." D holds the five characters HELLO and is displayed as `[HELLO]`.

Edition: 2014. Dynamic-length elementary items are in ISO/IEC 1989:2014; §E.3.3 17) (checked) records only a 2023
enhancement to them: "The SET statement was enhanced to allow the setting of the length of a dynamic-length elementary
item."

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`): compiles with no diagnostic; the run prints `[HELLO]`,
exit code 0.

## Fix site

`cobc/parser.y` (read in the GnuCOBOL 3.2 release source (gnucobol-3.2.tar.xz)), rule `data_description_clause`: none of its alternatives is a DYNAMIC LENGTH clause (the DYNAMIC token
is used only by ASSIGN DYNAMIC, ACCESS MODE DYNAMIC and OCCURS DYNAMIC); the field structure in `cobc/tree.h` has no
dynamic-length attribute.

## Upstream state

Unreported; tracker not yet searched. NEWS and TODO do not mention DYNAMIC LENGTH.

## Vetting (2026-11-04)

Verdict WRONG as a defect (step 1) and DUPLICATE, ended. DYNAMIC LENGTH is an optional element of Annex A.4 (A.4.5 1), cite.py --check OK) that cobc does not claim, so a refusal is within 4.2.7 and not a defect; the same mechanism is already feature-requests #109 (accepted). This also reverses a verdict nights 7-9 had each reached (LATITUDE on THEY_REJECT:13.18.19), which is the case for PB4582. Retired with `upstream_status: duplicate` and that ticket.

Environment: GnuCOBOL 3.2.0, WSL2 Ubuntu x86_64; `cobc -x -free -std=cobol2014 -o p dl1.cob`.

Program:


makes the sent value its content and length (§2023:8.5.1.10.4). If the feature is not planned for 3.x, a diagnostic that
names DYNAMIC LENGTH as not implemented (as cobc already does for OCCURS DYNAMIC) would state the gap.
