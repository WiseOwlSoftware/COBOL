## The measurement

`registrar2/probe/relprev2.cob` (the PB343 implementer's own repro, copied verbatim from
`scratchpad/PB343/relprev2.cob`), an empty RELATIVE file, `OPEN INPUT`, then two
`READ … PREVIOUS … AT END … NOT AT END` statements:

```
$ cobol.exe relprev2.cob --std 2023 --run
S1-OK FS=00 RK=0005 REC=EEEE
S2-OK FS=00 RK=0005 REC=EEEE
E1-AT-END ES=10
E2-AFTER ES=46          <-- neither imperative ran
```

The first READ ends at end ('10') and takes the AT END imperative. The second READ — the one whose predecessor
was unsuccessful — sets '46' and falls straight through to the statement after the READ, with the record area
undefined (§14.9.30.4 GR18, NOTE 6). Nothing is reported.

## The two readings, and why this is an adjudication

**Reading A — GR21 means all of GR24.** Then the AT END imperative must run, and the compiler is wrong today.
The cost of Reading A is GR24 a): it would overwrite GR21's own '46' with '10', so the status the standard just
required would not be observable — and the probe above shows `ES=46` is exactly what a program reads.

**Reading B — GR21 means GR24's control transfer only (c) and d)), not its status assignment.** Then the AT END
imperative must still run; only a)'s '10' is displaced by GR21's '46'. **Note that Reading B does NOT license
the current behaviour either.**

**Reading C — the compiler's, unwritten as such.** `KeyedIoEmitter` branches to AT END only for the '1x' family
and treats every other unsuccessful status as exception processing. The comment at the site says so:

> "'1x' (10/14, the at-end family, §9.1.13.4) → AT END imperative; any other unsuccessful status takes NO branch
> (exception processing, §9.1.14 final rule item 1)"

That is a citation to a rule about a **different condition** — §9.1.14 governs the invalid key condition, not
the at end condition — which is the exact shape `feedback_a_real_clause_can_answer_a_different_question`
describes and the shape that produced PB343 itself. Whoever adjudicates must decide between A and B and record
the determination where the code is, with a `--check`ed citation.

## Code site

- `src/Cobol.Net.Compiler/CodeGen/Verbs/KeyedIoEmitter.cs:169-190` — the '1x' test and the comment above.

## Landed — 2026-09-22 (wave 45, group D)

**Re-probed on the wave-45 worktree's own build** (`dotnet build CobolSharp.sln -c Debug`, 0/0, base `8fe62bd1f`):
a sequential file and a RELATIVE file, each empty, two `READ … AT END … NOT AT END` with a `USE AFTER STANDARD
ERROR` declarative — `S-E1-AT-END 10`, `DECL FS=46`, `S-AFTER 46` (and the relative twin). The '46' READ runs the
declarative and neither phrase. Unchanged behaviour after the landing; what changed is the ground it stands on.

**DETERMINATION — Reading C, re-grounded.** Neither A nor B: GR24's actions are conditioned on its own first words
(`cite.py --check 14.9.30.4 "If, during the execution of the READ statement, the at end condition exists, the
following occurs in the order specified"` → OK §14.9.30.4 24)), and '46' is not the at end condition — it is a
LOGIC ERROR (`--check 9.1.13.7 "I-O status = 46. A sequential READ statement is attempted"` → OK §9.1.13.7 6);
§9.1.13.1 "Logic error. The input-output statement was unsuccessfully executed as a result of an improper sequence
of input-output operations" → OK). GR13 therefore governs (`--check 14.9.30.4 "If neither an at end nor an invalid
key condition occurs during the execution of a READ statement, the AT END phrase or the INVALID KEY phrase is
ignored"` → OK §14.9.30.4 13); GR13 b) → §9.1.12). GR21's pointer to GR24 has content only for the conditions GR24
names. Recorded at `docs/CONFORMANCE.md` §4; harm flags cleared in this change set as the note required.

**The wrong citation is gone, and so is the per-site comparison.** The status → condition decision is now ONE table,
`src/Cobol.Net.Compiler/CodeGen/Verbs/IoStatusClass.cs` (`Successful` / `Unsuccessful` / `AtEnd` / `InvalidKey`,
§9.1.13.2 / §9.1.13.4 / §9.1.13.5), consumed by BOTH READ arms (`SequentialIoEmitter.EmitRead`,
`KeyedIoEmitter.EmitRead`), every INVALID KEY / NOT phrase / END-OF-PAGE success guard / ON EXCEPTION site, and both
generated hooks (`__IoCheck`, `__IoCheckEc`) — 17 sites, generated C# byte-identical.
`IoStatusClassDriftTests` forbids a first-character status comparison anywhere else under `CodeGen`. The two
comments that justified the READ branch from §9.1.14 (KeyedIoEmitter) and a bare §9.1.13.1 (SequentialIoEmitter),
and RuntimeApi's §9.1.13.4 citation for "successful", now cite the clauses that say so.

**Sibling sweep (the table the note asked for).** Every phrase an unsuccessful status can drive is one of the
three classes: AT END ⇐ '1x' (READ, and the SORT/MERGE USING input read's hook), INVALID KEY ⇐ '2x' (READ,
WRITE, REWRITE, DELETE, START), ON EXCEPTION ⇐ any non-'0x' (DELETE FILE). Every other unsuccessful status — '3x',
'4x' (GR21's '46', START's '47', …), '5x', '6x', '7x', '9x' — takes no phrase and reaches §9.1.12.

**Golden:** `tests/conformance/85/pb810_read_46_takes_no_at_end` (PROGRAM-ID `PB810R46`) — sequential, relative
(after an unsuccessful START — GR21's other leg) and indexed, so both emitter arms. No negative: the behaviour is
edition-invariant and 85 is the floor.
