# PB4513 — Report Writer with OVERLAPPING controls (CONTROLS ARE WS-REGION WS-KEY, one inside the other) corrupts the user's control item at a control break: save-current and restore-prior are interleaved per control

**Found:** 2026-11-03 by the Sonnet-written fuzz batch; adjudicated WISEOWL-DEFECT (Opus adjudicator, billed to the API key), and its reduced repro re-run on a judge built from main 3c8b2845c (`fuzz_triage.py verify`) still shows it.

**The adjudicator's finding.** With overlapping controls (CONTROLS ARE WS-REGION WS-KEY, WS-REGION inside WS-KEY) a control break leaves the user's WS-KEY corrupted after GENERATE: reduced repro t15 prints 'AFTER [EAQRS]', expected 'AFTER [WEQRS]' (cobc right); the corrupted prior then causes a spurious later break (fz00554 line 13). Cause: the save-current and store-prior steps are interleaved per control, so the second control's 'current' is read after the first control's prior was stored into the shared bytes. Witnesses fz00554, fz01963, fz01962. Not in kb/Work (searched overlap x control). The signature's other programs (fz00553, fz01257, fz02668) differ only by cobc's SUM-counter name (record report-sum-counter-name-refers-to-printable-item, carried by 14.9.16).

**The rule** (each marked checked by the adjudicator; re-run `cite.py --check` before writing one into code): §13.18.16.4 r4 a) 'When the printing of each control footing has been accomplished, the control data items are restored from the prior controls to their new current values' (checked via --find of the rule text); §13.18.16.3 SR6 'Two or more instances of data-name-1 in the same clause may, however, refer to the same physical data item or to overlapping data items'

**Sites:** `src/WiseOwl.Cobol.Runtime/IO/ReportWriter.cs` (`SaveCurrentRestorePriors`, the ONE two-pass save-current / store-prior step; its callers are `GenerateCore`'s control-break arm and `Terminate`'s GR3a)

**Sweep.** Every bug is a pattern: the fix asks its question in one place, and the arms named above (and the siblings the finding lists) are checked by a test that asserts the OUTPUT VALUE derived from the rule, never copied from either compiler.

**Landed.** Re-probed on the branch build: the repro printed `AFTER [EAQRS]` (expected `WEQRS`). The save-current and store-prior steps of the control break and of TERMINATE GR3a are now ONE helper, `SaveCurrentRestorePriors`, in two passes (all currents read first, then all priors stored), so overlapping controls (SR6) cannot corrupt each other's saved value. Witness: `conformance-suite/cases/13.18.16-CONTROL/pb4513_control_overlap_restore` (accepted at 85, 2002, 2014 and 2023; the Report Writer CONTROL clause is in the module from 85, so no program is refused below it). Sweep: `Get()` on a control appears only in the helper and in the first-GENERATE priors snapshot (`c.Prior = c.Get()`, no Set between), so there is no sibling.

## Landing

`src/WiseOwl.Cobol.Runtime/IO/ReportWriter.cs#SaveCurrentRestorePriors` owns the control break's and TERMINATE GR3a's save-current / store-prior step; reuse it for any new site that swaps control items to their priors, and never read a control's `Get()` after another control's `Set()` (overlapping controls share bytes, SR6). The trap: the conformance harness compares normalised output, so the CRLF a Windows `--run` prints is not a diff.
