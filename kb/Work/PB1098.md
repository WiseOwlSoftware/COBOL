# PB1098 — OPEN — a RELATIVE or INDEXED store opened I-O through a SEQUENTIAL file description succeeds (the PB802 non-conflict), its first READ returns the store HEADER as a rec

## Rule text (every citation re-run by the registrar)
- `python scripts/spec/cite.py --check 12.4.5.10.3 "The file organization is established at the time a physical file is created and cannot subsequently be changed"` → `OK  §12.4.5.10.3 1)  (General rules)`

## The refuters' measurement (rows GR-12.4.5.10.3-1/-4/-5, batch 14a)
First half holds: MapOrganization maps each phrase, `RecordFraming.WriteHeader` stamps the organization, `KeyedConnector.FixedAttributeConflict` answers '39' for relative↔indexed and sequential→keyed OPENs. But a RELATIVE (and an INDEXED) store opened I-O through a SEQUENTIAL FD answers '00', its first READ returns the header bytes, and REWRITE overwrites them; the file then opens as RELATIVE/INDEXED only with '39'. PB802 (owner decision, GnuCOBOL's spirit, no sidecar) contemplated INPUT and EXTEND through a sequential FD — not an I-O REWRITE over the header; §14.9.27.4 GR10's latitude governs which attributes OPEN validates, not whether a later program may rewrite the organization. The relative↔indexed swap is probe-only (no golden); RRN identity and key identity are otherwise verified (see the rows).

## What the fixer owes
The sequential view of a keyed store must never expose or overwrite the header: either the sequential connector skips the framing header of a keyed store (and refuses OPEN I-O/OUTPUT on one with a '39' conflict, keeping PB802's INPUT/EXTEND stance), or OPEN I-O through a sequential FD of a keyed store is a fixed-attribute conflict. Stay within PB802 (no sidecar). Golden pinning the relative↔indexed swap and the I-O REWRITE.
