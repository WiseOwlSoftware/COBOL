# PB613 — LANDED — one rule, two bodies, now one

Found 2026-09-05 by the `PB238` implementer (report §14 b), which closed the COMPLETENESS gap between the two
copies and filed the physical unification rather than forcing two currencies into one helper mid-mechanism.
Re-derived on this tree for this note.

## The rule

§14.9.4.4 GR8 — `cite.py --check 14.9.4.4 "An argument that consists merely of a single identifier or literal is
regarded as an identifier or literal rather than an arithmetic or boolean expression"` → OK §14.9.4.4 8) — and
INVOKE's equivalent under §14.9.23.4. Two grammar facts make the reduction load-bearing: `arithmeticExpression`
subsumes a `dataReference` and every numeric literal, and the `{boolExprAhead()}?`-gated `booleanExpression`
subsumes both in turn (its leaf is `valueOperand`, which is `arithmeticExpression | nonNumericLiteral`).

## The mechanism

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/CallBinder.cs#Gr8Classify` and
`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/OoBinder.cs:463-490` (`OoBindInvokeArg`'s inline block) both
unwrap an operator-free boolean node to its bare `valueOperand` (both legs) and recover a sole `dataReference`.
The INVOKE copy additionally folds a sole NUMERIC literal out of an expression node through
`ConditionBinder.SoleNumLiteral`; the CALL copy leaves that to `CallEmitter.ConstLiteralText`/`NumericArgText`
at emit time. Two bodies for one rule is how the CALL copy came to lack the `nonNumericLiteral` leg for a year
(a `"AB"` argument reaching the boolean node on a LATER argument's B-operator staged a run-time loud on
conforming source — PB238's sixth defect); the next divergence is invisible until a shape hits one arm.

## Fix shape

One reduction in `ConditionBinder` (its three helpers already live there) returning the union of both
currencies (`LiteralContext` and `NonNumericLiteralContext` + raw text), consumed by both call sites; a drift
test asserting the two sites read the same body (the `TheLevelNumberRuleIsWrittenOnce` pattern: a file may
implement GR8 only if it names the shared helper). Witnesses: PB238's `pb238_call_format2_operands` (S6) and
the INVOKE twin of the same argument list.

- **One reduction.** `ConditionBinder.ReduceArgument(literal, reference, boolExpr, arith)` returns an `ArgumentOperand`
  (the written literal, the nonnumeric literal written or recovered from an operator-free boolean node, the sole numeric
  literal's text, the identifier, the genuine boolean expression and the arithmetic operand). Every CALL spelling (BY
  CONTENT, BY VALUE, keyword-less) and every INVOKE argument (`OoBindInvocationArg`) asks it; `CallBinder.Gr8Classify`
  and `OoBinder`'s inline block are deleted. The bound-tree twin, `Gr8ArgumentLiteral` (a literal recovered from a bound
  expression), is unchanged.
- **Found and fixed on the way (I9): the keyword-less CALL argument was dispatched on its parse node before it was
  reduced.** `CALL "S" AS NESTED USING N B1 B-AND B2`: the look-ahead puts N in a boolean node on the second argument's
  B-AND, and the boolean arm passed it BY CONTENT, so the callee's `MOVE 42 TO X` never reached N (measured `N=0001`;
  §14.9.4.4 GR8 + GR9 a) 1. require BY REFERENCE, `N=0042`). The keyword-less argument is now reduced once, before its
  shape is dispatched: an identifier takes the identifier arm (GR9's mode, the SR3 test, constant-names and
  keyword-omitted functions alike), a recovered literal takes GR9's mode and is asked §14.9.4.3 SR23 when the formal is
  BY VALUE (it was not), and a recovered numeric literal crosses as literal-2. INVOKE was already right (`N=0042`; its
  mode reads the reduced identifier). The dead BY VALUE `vBareLit` arm (no boolean alternative reaches it) is deleted.
- **Goldens.** `conformance:2002/pb613_gr8_one_reduction` (G1-G5: the CALL and INVOKE lanes, BY REFERENCE, BY VALUE and
  BY CONTENT, and PB613's `INVOKE ... USING 7 "AB" N` twin, `7AB0005`); negative `pb613-bare-literal-by-value-formal`
