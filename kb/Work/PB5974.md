# PB5974 - the rolling wave gates and lands per branch; the owner's rule is one train per wave

## The owner's rule
Stated three times, most recently 2026-11-19 about 21:45: "Why are we running so many tested repeatedly for no benefit? We
should group fixes and run tests for the group. This is not the first time I've said it. You are using a very inefficient
design" (earlier: 2026-10-08, 2026-09-13 and 2026-09-27). Implementers and review rounds may run in parallel on their own
branches; every READY branch is merged into ONE train branch; the train takes ONE gate and ONE `enqueue.py land`.

## What the machinery does
`plan_wave.py --cluster PB5925` on 2026-11-20 (dry run) planned 8 groups for the listing cluster's 13 open notes. The
rendered implementer spec (`.claude/skills/workstream/templates/dispatch-spec-implementer.md`, the GATE and LINUX GATE
sections) tells every implementer to run `build-local` on its own branch, and `wf_rolling_wave.js` hands each CLEAN branch to
the landing lane separately (its header: the train "went with the lander", kb/Work PB3016, PB3023). Eight groups are eight
whole-population gates (about 10 to 45 minutes each, PB5970: three at once saturate the host and red NIST cases on timeouts)
and eight merge-queue runs.

## Fix shape
A wave mode in which the implementer commits and returns without a gate (its inner loop: the build and the tests its change
names), the review runs on the branch, and a train step merges every CLEAN branch into one train branch, runs the cheap
audits, ONE gate and ONE `enqueue.py land`; a red in the train is classified to its branch by the gate's per-case record and
fixed there. The implementer spec's GATE section, check_practices.py and the rolling-wave reference change with it.
Plan size follows: a cluster's notes are packed into as few branches as the file partition allows.
