# PB864 — OPEN — one flag, two questions, one spurious line

Source: the `PB523` implementer report, item B. Carried as an unfiled lead since train 27.

## The mechanism

`_afterAdvancing` is set by a print-control WRITE and read in two places:

* `src/Cobol.Net.Runtime/IO/SequentialConnector.cs:815` (`Write`) — to force line orientation, where the question
  is "has this connector seen a print-control WRITE";
* `CloseCore` (`if (_afterAdvancing) ...`) — to write the closing `\r\n`, where the question is "is the current
  line unterminated".

For an AFTER write the second is true, because the record is presented last. For a BEFORE write the record's own
advance already terminated the line, so CLOSE writes one more.

## Repro (from the source report; re-run is owed with a byte comparison)

`LINAGE IS 2 LINES LINES AT TOP 3 LINES AT BOTTOM 2`, three `WRITE ... BEFORE ADVANCING 1 LINE` ->
`\r\n\r\n\r\nAAAA\r\nBBBB\r\n x6 CCCC\r\n\r\n`; the last pair is spurious. Pinned today — with an
explicit warning comment saying it is NOT derived from the standard — by
`LinageConformanceTests.Bytes_OverflowWithBeforePhrase_PresentsThenRepositions`.

## Why no gate sees it

Both the NIST comparison base and the corpus comparison base end with `TrimEnd('\n')`, so a trailing blank line
is invisible to every existing witness. That is the second half of the finding: the byte-level assertion has to
be written for the fix to be checkable at all (`feedback_green_gates_arent_evidence`).

## The rule

§14.9.51.4's presentation rules put the record and the advance in a defined order; nothing in them adds a
terminator at CLOSE. The `LINAGE` end-of-page machinery that shares this flag is GR26:

```
$ python scripts/spec/cite.py --find "LINAGE clause is specified in the file description entry"
  §14.9.51.4 26)  (General rules)
      26) If the LINAGE clause is specified in the file description entry of the associated file, an end-of-page condition occurs when the lines written by a WRITE statement do not fit within the ...
```

## Shape of the fix

Split the flag into the two questions it is answering (`_sawPrintControlWrite` and `_lineOpen`), set each where
it belongs, and let `CloseCore` read only the second. Then correct
`LinageConformanceTests.Bytes_OverflowWithBeforePhrase_PresentsThenRepositions`, whose current expectation
encodes the defect, and give it a byte assertion that does not trim.

## Sibling sweep the fixer owes

* Every other reader of `_afterAdvancing` (grep) — each must say which question it is asking.
* The same "is the line open" question exists for a non-print sequential file whose last record was written
  without a terminator, and for the report writer's own CLOSE path.
