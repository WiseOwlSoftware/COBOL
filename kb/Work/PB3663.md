## The owner's words (2026-10-24, attended operator session 0a5c7c77)

The operator asked: "Should the loop record an impact map automatically each time it picks up a new main commit?" It
recommended recording one at each adoption, about 25 minutes at low priority inside a gate slot. The owner answered at
about 17:10 PDT: "Yes, record the impact map automatically".

## Why (measured 2026-10-24)

- No impact map exists. `E:\COBOL\.git\cobol-impact` is absent, and every gate of the day printed `every case tier 1: no
  impact map recorded for the base … or any ancestor`.
- Without a map, leg 1 cannot aim at the change. It runs the change's own edited tests (tier 0u), the reds (0a), the
  host witnesses (0h), the sweeps (0c) and the drift rules (0d), and after those the cheapest slice of everything. Gate
  000004-20261024T221346Z on `worktree-wf_1973801d-4fe-29` (PB2974) ran 36,802 of 38,134 Unit cases and 10,207 of 18,394
  Conformance cases in leg 1. That is the cheapest ~1,500 recorded seconds per assembly, whether or not the change can
  reach those cases. A case the change reaches whose recorded time puts it in leg 2 runs only in CI, which is a gap in
  the CI invariant (PB1957).
- The on-demand rule is out of date. PB1709 was retired by the owner's decision PB1708 (2026-09-28: no per-commit maps,
  recorded on demand) when every local gate ran the whole population and the map only ordered it. Batched gating
  (PB2515, 2026-10-10) made leg 1 the only local run, so the map now decides what a gate runs locally. Nothing ever asked
  for a map on demand. This decision supersedes PB1709's retirement.

## The bar

1. **Recorded at adoption.** After `adopt_main.py` fast-forwards the checkout to a CI-green main commit (PB2699), the
   supervisor starts `record_impact_map.py --commit <adopted sha>` DETACHED, at BelowNormal, inside a gate slot (the
   recorder already holds one). It never blocks a unit or the landing lane. One recording runs at a time. An adoption
   while one runs coalesces to the newest adopted sha, which records after the running one ends; stale shas never queue.
   A documentation-only adoption (`impacted_tests.py`'s "documentation-only drift" against the newest map) records
   nothing.
2. **Loud on failure.** A `=== IMPACT MAP: FAILED … ===` verdict goes to the supervisor log and the operator's mailbox
   with its line, and the next adoption tries again. A missing map is never silent.
3. **Bounded store.** The store keeps the newest maps that any live worktree's base can still use, and the older ones are
   pruned. Size it from a measurement; a map is about 5 MB compressed (§3.13).
4. **Measured use, the real bar.** `gate_plan`'s `map …` line is recorded per gate. The change reports the fraction of
   implementer gates whose plan read `exact` or `documentation-only drift` over the first day of waves, before and after.
   ⛔ **Expect the staleness rule to defeat it.** `impacted_tests.py` uses a map only at the branch's exact base or one
   that differs from it only in documentation. A branch that merges main gets a new base that no map may match yet, and
   main moves at about 1.6 landings an hour while a recording takes 18.7–25 minutes. If the measurement shows most gates
   still falling back to tier 1, re-design under CLAUDE.md rule 5. One option: use the nearest ancestor map for the files
   unchanged between it and the base (their line ranges still describe the tree), and put only the changed files' reach
   in tier 1. Update §3.13 in the same change. Never stop at "the recorder runs".
5. **The docs follow the code.** §3.13's "the map ORDERS the gate; it never SELECTS it" and the gate skill's "recorded
   ON DEMAND … never per commit (kb/Work PB1709)" describe the pre-PB2515 gate. Restate them in the change that lands
   this: under batched gating, leg 1 is the local run, so the map's tiers decide which cases it holds. Do the same for
   CLAUDE.md's Testing paragraph ("impact maps are recorded on demand, never per commit") and design section 4.10.
6. **A drift test** pins the hook: an adoption that moves the checkout starts or coalesces exactly one recording, and a
   self-test arm covers the coalesce, the documentation-only skip and the failure report.

## Evidence: PB3666's bounce (2026-10-24, filed by the operator)

PB3666 (wave 20261105) passed its local gate (run 000002, leg 1 GREEN, Linux half GREEN) with no impact map, so the two goldens its change reaches, `pb53_by_content_move_rules` and `pb72_table16_admitted_cells` (both move non-boolean text into a boolean item), sat in leg 2 and never ran locally. Merge-group run 40161872886 failed both on both hosts and bounced PR #548; a finisher updated them to the owner's determination D-B5. Leg 1 is the cheapest slice of each assembly when no map exists, so a regression in a test the change reaches, but whose recorded time puts it in leg 2, reaches CI: the CI-invariant gap this note's recorder closes. Add this case to the note's measured bar (a gate with the map puts both goldens in leg 1).

## Landed (wave 20261704, group A)

**Re-probe on a fresh build (7d769bcc1).** No impact map existed (`E:\COBOL\.git\cobol-impact` absent) and all 72 gate plans on
the owner's machine read `map none`. The first real recording through the existing recorder took 13.6 minutes (814 s) and wrote a
**25.2 MB** map (the design said about 5 MB): 48,426 probe entries, 57,270 tests. It ended `=== IMPACT MAP: FAILED ===`: the
recorder's own watchdog reported eight `UniversalCrossingShapeDriftTests` theory rows "listed but never recorded", because
`--list-tests` truncates a long display name with `···` and xunit's own name, which the recorder reads, is the full one. Run by
the loop's lane, that watchdog would have failed every recording. The recorder also wrote the map non-atomically.

**What landed (bars 1-6).**
1. *Recorded at adoption.* `adopt_main.adopt` asks `impact_lane.request` once, for the commit it adopted (ADOPTED) or found current
   (CURRENT); never for KEPT or a dry run; a lane that raises cannot hide the adoption or the supervisor's restart trigger. The
   lane starts ONE detached worker (`impact_lane.py work`, `scripts/detached.py`) that runs the recorder at BelowNormal inside the
   recorder's own gate slot, coalesces to the newest requested commit, and skips a commit with a map, a commit served by a map in
   documentation only, and a commit whose recording already failed. Proven end to end: the lane recorded `315f9eb98` into a trial
   store (RECORDED, 867.9 s, 56,930 tests, watchdog green with the name fix).
2. *Loud on failure.* A recording that does not end RECORDED (the FAILED line, no verdict, a recorder that would not start, a worker
   that died or raised) posts to the operator's mailbox once per commit and shows in every later adoption line until one succeeds.
3. *Bounded store.* `impact_store.prune` keeps the newest 4 maps (100 MB, sized from the measured 25.2 MB) plus the map serving each
   live worktree's base, removes dead recorders' temp files and work directories, and reports a file it could not remove.
4. *Measured use, and the staleness rule defeated and replaced (rule 5).* Under the old rule a map older than the base by more than
   documentation was STALE and put every test in tier 1; main moved 44 landings in the 5.9 hours after the replay map was recorded.
   `impact_store.nearest` now serves a base from the map whose tree differs from it in the fewest source files, whatever its age or
   ancestry; a change to a file the two share is attributed by line range, one to a file that differs is taken at the file level.
   Replay of those 44 landings: all 44 served (1 exact, 43 nearest; the old rule: 1), 18 of the 22 code-changing landings
   attributed. Two rules that fell back for no reason a test can see were fixed on the way (the `PublicAPI.*.txt` baselines and
   `RuntimeAbi.pin` are data a test may read; a finalizer beside test-reached code does not make a file unattributable). `impact_lane.py measure --since` reports the
   share of implementer gates that read a map, for the first day of waves after this lands.
5. *Docs.* CLAUDE.md Testing, the gate skill, DESIGN-test-build-ci sections 3.13, 3.14.2 and 3.14.8, DESIGN-orchestrator-loop section 4.10.1,
   DOC_INDEX and the plan's gate paragraph state the rule; the retired phrases are held out by `ImpactMapLaneDriftTests`.
6. *Drift test and self-tests.* `ImpactMapLaneDriftTests` pins every arm of the three new self-tests and the one trigger.

**PB3666's case.** Replayed with `gate_plan.py` against a recorded map (base `3425b2ee7`, head `04a34e2a5`), PB3666's own change
first put EVERY test in tier 1: it edits `RuntimeAbi.pin`, which the earlier rule took for "a non-C# input under src/". The pin
is measured by `scripts/abi_pin.py` and read by `RuntimeAbiPinDriftTests`; the build's version is `Directory.Build.props`, a
structural input. Treated as data a test may read (with the public-API baselines), the change is attributed: Conformance tier 1
is 6,642 of 18,832 cases and leg 1 holds 1,935 (12,638 when unattributed), and both `pb53_by_content_move_rules` and
`pb72_table16_admitted_cells` are in leg 1. Leg 1 still orders tier 1 cheapest first within `LEG_ONE_BUDGET`, so a change that
reaches nearly everything (17,515 of 18,580 Conformance tests for one replayed landing) runs the cheapest slice of what it
reaches, as the design measured in 2026-09 (DESIGN-test-build-ci.md section 3.13); that budget is the gate planner's, and this note
does not change it.
