# PB2613 — a void SPLIT report is counted as an attempt and as a predecessor

## What happened (2026-10-08, wave 1038 then wave 1039)

Wave 1038 (run `wf_dc000831-c97`) was dispatched at about 00:06 PDT. At 00:06:39 the supervisor created
`scratch\STOP-loop`, because the dispatching unit's context had passed its 150k cap. All eight implementers found the stop file at their
first step check and returned `SPLIT` with no commits, no edits and no probe. Their reports
(`scratch\reports\w1038{a,a2,b,c,e,f,g}-*.md`) each say "not started" in free text, and their worktrees
(`wf_dc000831-c97-1` … `-8`) sat at base `44a1b5eac`. The next wave unit removed those eight base-only worktrees and
re-planned. The plan for wave 1039 then showed two effects:

1. **Model escalation from void attempts.** `plan_wave.py#attempts` is `sum(1 for r in reports if nid in r.ids)`,
   so it counts every report that names the note, whatever the report did. `choose_model` escalates to Opus when that
   count reaches `model_rules.json` `opus_when.failed_attempts_at_least`. Group A (PB1470, PB1544) had been planned as
   Sonnet in wave 1038 and was planned as Opus in wave 1039 ("PB1470 already attempted 2 times without landing").
   The only new "attempt" was w1038a's void SPLIT. PB2097 and PB2078 went from "2 times" to "3 times" the same way.
2. **FINISH-FIRST against a deleted branch with nothing on it.** Groups C, A2, D, E and F were fresh clusters in wave
   1038 and became finishers in wave 1039. Each `pred` told the implementer that its predecessor's branch
   `worktree-wf_dc000831-c97-N` "is ABSENT: its landed part is already on main, so orient from the report only".
   Nothing from that branch had landed, and the branch held nothing. The implementers coped (w1039d's report:
   "finisher after w1038f's stop-file SPLIT (it did no work)"), but each paid turns reading a void report, and the
   `pred` text stated something false.

## Root cause

A report's identity is its status word (`STATUS_WORD`: DONE · SPLIT · DISCHARGED · BLOCKED · NOT STARTED). A SPLIT
that stopped at a note boundary after real work and a SPLIT that found the stop file before its first step share the
same word. The planner has no field that says the report did no work. The wave result already carries `base` and
`head` per implementer, and `head == base` is exactly "no commits", but that never reaches the report file the planner
reads.

## Fix shape (not started)

- Make "did no work" a structured fact of the report, written by the implementer template from `head == base` (for
  example a `**Work:** none` line that `plan_wave.py` parses), or let `wf_rolling_wave.js` stamp it from the result.
  Never infer it from prose.
- A void report is neither an attempt (`attempts`) nor a predecessor (`finisher_pred`): the planner falls back to the
  next-newest report for each note it names, so a chain such as w1038a → w1020d's SPLIT on `wf_b3526bdd-e0d-4` is
  kept.
- `test_plan_wave.py` gets a case for each arm: one void SPLIT between two real reports leaves the attempt count and
  the predecessor unchanged.
