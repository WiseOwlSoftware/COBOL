# PB802 — LANDED — fixed file attributes are validated from the FILE'S OWN FORMAT, not from a catalog

## ✅ THE OWNER'S ANSWER — 2026-09-07, verbatim

> **"Let's match GNUCobol's implementation in spirit. No sidecar of any type."**

The question arose after [[PB793]] (owner question 22, EBCDIC code-names) re-decided the code-set half of Annex
A.1 item 129: with the code set no longer a constant, the whole determination was re-read, and COBOL.NET's
fixed-file-attribute validation was compared with GnuCOBOL's. Ours rested on a **`.cbattr` catalog sidecar**
written beside every data file this processor created ([[PB193]]); GnuCOBOL has **no catalog at all** and
validates only what the physical file format itself encodes. NTFS alternate data streams were raised as a
"less visible" home for the same catalog and were **rejected with it** — "no sidecar of any type" is the whole
of the answer, and a stream hanging off a file is a sidecar that also does not survive a copy to any other
filesystem.

This note keeps `kind: decision` and flips `status: owner` → `landed` in the change set that implements it, the
[[PB146]] / [[PB793]] convention for a decided decision. No separate defect note was opened.

## The rule, and the latitude it grants

`cite.py --check 14.9.27.4 "The implementor defines which of the fixed-file attributes are validated during the
execution of the OPEN statement"` → **OK, §14.9.27.4 10)**. GR10's own third and fourth sentences are the whole
licence:

> The implementor defines which of the fixed-file attributes are validated during the execution of the OPEN
> statement. The validation of fixed-file attributes may vary depending on the organization or storage medium of
> the file.

`cite.py --check A.1 "OPEN statement (validation of fixed file attributes)"` → **OK, §A.1 129)** — required, and
required to be documented. `cite.py --check 9.1.13.6 "39"` → **OK, §9.1.13.6 7)**: *"The OPEN or DELETE FILE
statement is unsuccessful because a conflict has been detected between the fixed file attributes and the
attributes specified for that file in the source unit."*

## What was measured BEFORE anything changed

The measurement is the reason this is a re-architecture and not a deletion, and two of its four findings
contradicted the framing the question arrived with.

1. **`RecordFraming`'s store level carried NO header.** `WriteStore`/`ReadStore` wrote and read a bare sequence
   of 4-byte little-endian length-prefixed frames (gap tag `0xFFFFFFFF`), and nothing else — no organization
   tag, no record type, no record sizes, no key table. It is used ONLY by `RelativeConnector` and
   `IndexedConnector`. So for those two organizations "what the format encodes" was, before this change,
   *almost nothing*, and matching GnuCOBOL's indexed key check meant putting the key table into the format —
   which is exactly where GnuCOBOL keeps it (a real ISAM file's header), and is not a sidecar.
2. ⛔ **Variable-length record sequential ALREADY carries its record boundaries in the data, and always did.**
   `RecordFraming.WritePrefix` / `PrefixLength` / `FrameStarts` put the same 4-byte prefix in front of every
   record of a RECORD VARYING record-sequential file (`SequentialConnector.cs:690`, `:928`, `:870`). The premise
   the dispatch flagged as the risk — *"if only the catalog knows where the record boundaries are, the format
   cannot round-trip variable-length records at all"* — is **false on this tree**: the catalog never held a
   record boundary, and **no format change was needed for sequential files.** §9.1.7.2 already licenses that
   prefix ("such as record length headers") and §12.4.5.11.4 GR5 grants the method.
3. **Fixed-length record sequential is plain bytes; line sequential is delimiters.** Neither encodes any §9.1.6
   attribute, which is what the old determination already said about sequential record sizes and why it was
   right to.
4. **GnuCOBOL's behaviour, from its READ-ONLY GPL testsuite** (`tests/external/gnucobol/tests/testsuite.src/run_file.at`
   — behaviour only; never its sources or its formats): exactly two status-39 cases.
   `variable-length SEQUENTIAL data integrity` (line 89) points a `RECORD VARYING FROM 5 TO 500` FD at a plain
   XML text file and expects `OPEN ERROR: 39` — the record-length header does not parse. `INDEXED undeclared
   keys` (line 7104) puts three FDs declaring three, two and one keys on one physical file created with three,
   expects '39' on the one whose key table disagrees, and opens it under `COB_KEYCHECK=OFF` (line 7270).

## The determination that landed

**The validated set is exactly what each organization's PHYSICAL FORMAT ENCODES** — one rule, from which the
per-organization answer is *derived* rather than listed, so a new organization or a changed format brings its
own answer with it. Written out in `docs/COBOLNET_FILES_DESIGN.md` **D10** (which REPLACES the sidecar
decision — the old text is gone, not kept beside it) and `docs/CONFORMANCE.md` row `DOC-A.1-129`:

- **record sequential, fixed-length records → nothing; line sequential → nothing.** §9.1.7.2 puts those lengths
  in the data and in the reading program, and §9.1.13.2 items 3, 5 and 7 answer every resulting disagreement
  with the SUCCESSFUL '04', '06' and '09'. Unchanged from the previous determination, and for the same reasons.
- **record sequential, RECORD VARYING → the record-length header must PARSE.** A first prefix naming more bytes
  than the file holds is not a framed file, so the declared VARIABLE record type contradicts the medium: '39'.
  A prefix that parses but is outside the RECORD clause's bounds is NOT a conflict — that is item 3's '04' on
  the READ, which a '39' at the OPEN would make unreachable. Fewer than four bytes states nothing.
- **RELATIVE and INDEXED → the framed store's HEADER**: organization, record type, minimum and maximum logical
  record size, and the key table (window, DUPLICATES, SUPPRESS WHEN, collating-sequence fingerprint). A store
  with no readable header is refused '39' — loud, where reading it as frames would be a silent misread. A
  zero-byte file is the one tolerated exception: it holds no records and states no attribute.
- **the key check has a runtime opt-out, `COBOLNET_KEYCHECK=OFF`** — GnuCOBOL's `COB_KEYCHECK=OFF` under this
  repository's naming. `COBOLNET_`, never `COBOL_`: `SwitchStore.Prefix` is `COBOL_`, so a `COBOL_KEYCHECK`
  would fall inside the external-switch family. Read ONCE per run unit in `FileRegistry`'s constructor and
  registered in `RuntimeConfig` (whose drift test enforces registration).
- **the code set is still NOT validated**, on [[PB793]]'s ground and not on the old "its value is constant" one.

## ⚠ Two owner-visible consequences, stated rather than decided silently

1. **The framed store's header is a FORMAT CHANGE to relative and indexed data files.** A file written by an
   earlier build has no header and is now refused with '39' instead of being silently misread. That is why the
   header is REQUIRED rather than optional: a tolerated headerless variant would be a second format and a silent
   one. Sequential formats are untouched — plain bytes stay plain bytes, line sequential stays plain text, and a
   varying record-sequential file carries only the per-record prefix it always carried.
2. **[[PB193]]'s original reproduction loses its '39'.** A RELATIVE file reopened INPUT through a SEQUENTIAL or
   LINE SEQUENTIAL FD now answers '00', because the sequential organization's format encodes nothing for the
   relative store to contradict. GnuCOBOL answers the same. The reverse direction survives (a plain sequential
   file through a RELATIVE or INDEXED FD is still '39' — no store header), and `RecordLayoutNotice` still reports
   the byte-count disagreement on stderr. Golden `85/open_fixed_attribute_conflict` step 3 is re-derived from
   '39' to '00' and says why in its own comment.

## Landed

`FixedFileAttributes` is no longer a catalog: it is the store header's **value type and codec** plus
`Conflicts`, the ONE place GR10's comparison is written. `SidecarPath`, `Load`, `Store`, `Remove`, the
`key=value` text format and `MediumFixesRecordLayout` are **deleted** — no `.cbattr` path is constructed,
written or read anywhere in `src`, `tests` or `scripts`, and the name survives only in prose recording its
removal (this note, [[PB193]], [[PB684]], D10, `DOC-A.1-129`, and the two guard scripts' comments saying why
they no longer sweep it). `HostFile.OpenAuxiliary` keeps its role but has no sidecar to serve; `FileRegistry.DeleteFile` no longer
removes a second file, so the physical file is the only thing DELETE FILE destroys.

GR10's site stays on `FileConnector.Open`, before `OpenCore` (GR25), and asks ONE virtual —
`FileConnector.FixedAttributeConflict` — whose three overrides ARE the three answers above: the base ("this
format encodes nothing"), `SequentialConnector`'s varying-prefix parse, and `KeyedConnector`'s store-header
comparison. That is a better shape than the catalog's: under the sidecar every organization's answer came from
one uniform record and the per-organization rule had to be re-stated as a hand-kept `MediumFixesRecordLayout`
switch; now each organization states what its own format encodes, in the file where that format lives.

This also closes [[PB684]] by removing its subject: `FixedFileAttributes.Store`'s four empty catches are gone
with the sidecar, so an unwritable catalog can no longer leave the PREVIOUS file's attributes in force.

**Pinned by** `85/open_fixed_attribute_conflict` (re-derived: PART A relative, PART B sequential, and a new
PART C for the varying record-sequential header parse and its '04' boundary), `2023/open_fixed_attribute_conflict_ix`
(unchanged expectations — the key table moved from the sidecar into the store header and the answers did not

the zero-byte tolerance, and the `COBOLNET_KEYCHECK=OFF` opt-out, which no golden can set).
