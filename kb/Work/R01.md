# R01 — LANDED — the constant substituted its literal everywhere except where a function took it

> Migrated from the fix queue's RESIDUE block, which never itemised these — so no work list could see them.

## ⛔ MEASURED

```
FUNCTION UPPER-CASE(K-TEXT)   ⛔ COBOLNET0844: constant-name 'K-TEXT' substitutes a literal of category
                                 Alphanumeric and is not a numeric operand (ISO §8.8.1.1 / §13.10.3 SR2)
FUNCTION UPPER-CASE("abcdef") ✅ compiles
```

with `01 K-TEXT CONSTANT AS "abcdef".` — and **§13.10.4 GR1 makes those two lines the same program**: "the
effect of specifying constant-name-1 in other than this entry is as if literal-1 … were written where
constant-name-1 is written". §13.10.3 SR2 admits it "anywhere that a format specifies a literal of the class and
category of constant-name-1", and an intrinsic argument is such a position for whatever class the function's own
§15.x rule admits.

## ▶ CAUSE — one arm short in the argument path

`IntrinsicBinder.BindArgOperand` handles an `OMITTED` argument, a phrase word and a written non-numeric literal,
then falls through to `host.Expr.BindFunctionArgumentExpr(...)` — the §8.8.1.1 **numeric-expression** bind. A
constant-name resolves there (`ExpressionBinder.RefExpr`), and that path is correct to demand class numeric,
because an arithmetic operand must be. **The argument was never an arithmetic expression**; its legality comes
from the function's §15.x argument rule, which the file's own comment two lines below says in as many words for
DATA items. The constant just never got the same treatment.

The fix is one arm ahead of the expression path: a SOLE data reference naming a NON-numeric constant becomes a
`BoundStringLiteral` of the constant's own category — the textual, class-preserving substitution GR1 describes.

⚠ **A NUMERIC CONSTANT DELIBERATELY FALLS THROUGH, and assertion 8 of the golden is why.** The expression path
already substitutes it correctly, and it must keep participating in arithmetic: `FUNCTION MAX(K-NUM + 1, 2)` is
an EXPRESSION argument, not a bare literal, and only that path can bind it. Routing every constant through the
new arm would have traded one rejection of legal source for another.

## ⚙ THE SWEEP BOUNDED IT RATHER THAN WIDENING IT

`MOVE K-TEXT TO R`, `IF K-TEXT = "abcdef"`, `INSPECT` and `DISPLAY K-TEXT` **all already substituted correctly**
(measured). So this is not the substitution mechanism being broken — it is the ARGUMENT path alone, exactly as
the note's title said. Recording the negative result matters as much as the positive one: it is what makes
"argument positions" the scope rather than a guess.

## ⭐ AND THE REJECTION DIRECTION IMPROVED WITHOUT BEING TOUCHED

`FUNCTION SQRT(K-TEXT)` was rejected before and is rejected now — but the reason changed from the
numeric-expression path's *"is not a numeric operand (ISO §8.8.1.1)"* to
`COBOLNET1627: FUNCTION SQRT argument-1 is of class alphanumeric; ISO §15.3 requires class numeric
(§15.84.3 r1)` — the function's OWN argument rule, which is the rule the source actually violates. That screen
is [[PB52]]'s, landed an hour earlier; the two changes met without either being written for the other.

## ▶ PINNED

`r01_constant_name_intrinsic_argument` — 8 assertions, built as PAIRS (constant vs the literal it substitutes),
because that equality IS GR1 and is a stronger claim than either value alone; plus the national constant, two
further string functions, and the numeric-constant-in-an-expression case that the fix must not capture.
Negative `r01-constant-name-wrong-class-argument` (SQRT of an alphanumeric constant, COBOLNET1627).
