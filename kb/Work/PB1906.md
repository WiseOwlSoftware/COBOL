# PB1906 — OPEN

Filed 2026-10-01 by the gl4 (witness-reuse) golden-lane lander, from the gl4-misc-p5 validator's observation on the
negative `tests/conformance/negative/l1-typedef-name-no-storage.cob` (landed in the same train).

**Repro.** That negative, at `--std 2002`, `2014` or `2023`: `01 T IS TYPEDEF PIC X(5).` then `MOVE "A" TO T`.
Rejecting it is right — §13.18.58.4 2) "A type declaration has no storage associated with it" (cite.py --check
13.18.58.4 → OK 2)), so the receiving operand identifies no data item (§8.4.2.1, "a statement shall contain a reference
that uniquely identifies that resource"). The CODE is right (COBOLNET1639, which the golden pins). The MESSAGE is
wrong: `'T' is not defined — no declaration in this source element gives the name 'T' … Check the spelling, or declare
the item.` T IS declared, as a type-name, and the advice sends the user hunting a typo.

**Code sites (the same defect shape PB1266 fixed for index-names and PB567 for condition-names).**
- `src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs#ReportUnidentified` (the `candidates.Count == 0` arm, about
  line 336): it screens screen-names, alphabet-names, index-names and condition-names before saying "not defined",
  but not `DataBinder.TypeDecls` (`DataBinder.cs:201`).
- `src/Cobol.Net.Compiler/Binding/DataBinder.cs#ResolveClauseOperand` (about line 2193) writes its own "no declaration
  … gives the name" text for clause operands and screens none of those kinds.

**Why it was not fixed in the landing.** Two sites already word the same verdict separately, and the honest fix is
ONE "what is this name declared as, if not a data item" query that both ask (screen, alphabet, index, condition,
type), with a unit test per kind. That is a diagnostics restructuring, beyond a golden-lane lander's slice (I9).
