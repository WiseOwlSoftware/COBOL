# PB1906 — LANDED (wave 20261769 B)

## Landing — one query of what a non-data name is declared as, asked by every refusing site

**Re-probe** on 802352531: the note's negative (`conformance-suite/cases/13.18.58-TYPEDEF/l1-typedef-name-no-storage.cob`)
still drew `'T' is not defined — no declaration in this source element gives the name 'T' … Check the spelling`. The
sweep (`E:/COBOL-coord/scratch/w20261769b/p/d1.cob`, `d2.cob`, `d4.cob`) found the same lie at four more places: a
type declaration's member (`MOVE "A" TO M`, `M OF T`), every non-data kind at a file clause operand (`FILE STATUS IS
T | AL | KC | C-ON | M OF T`, `RELATIVE KEY IS IX`: "no declaration in this source element gives the name"), a type-name
as an OCCURS DEPENDING ON object (COBOL0851 "is not defined"), and a type declaration's level-88 (`IF M-ON`, and SET
Format 4's "no level-88 entry … declares it").

**Fix.** `DataBinder.NonDataDeclarationOf` is the one answer (screen entry, alphabet-name, constant-name, index-name,
condition-name, type-name, a type declaration's member or condition-name; §13.18.58.4 GR1 and GR2, `cite.py --check`
OK 1) and 2)), and `NonDataDeclaration.DeclaredAs` the one wording. `ReferenceResolver.ReportUnidentified` keeps its
kind-specific arms (screen COBOL2364, index COBOL1637, condition-name PB567's text) and words every other kind through
it; `ResolveClauseOperand`, the ODO object (`DataBinder.Odo.cs`) and `StatementValidation.RejectSetConditionName` ask
it too. Codes are unchanged. Found on the way and fixed here (I9): a reference to a constant-name whose entry was
refused drew "is declared as a constant-name … not as a data item" (a cascade); it is now the refused-declaration
consequence COBOL2364 at a statement (a statement must still answer for its refusal, the COBOL2362 ledger) and nothing
at a clause operand.

# PB1906 — as filed

Filed 2026-10-01 by the gl4 (witness-reuse) golden-lane lander, from the gl4-misc-p5 validator's observation on the
negative `conformance-suite/cases/13.18.58-TYPEDEF/l1-typedef-name-no-storage.cob` (landed in the same train).

**Repro.** That negative, at `--std 2002`, `2014` or `2023`: `01 T IS TYPEDEF PIC X(5).` then `MOVE "A" TO T`.
Rejecting it is right — §13.18.58.4 2) "A type declaration has no storage associated with it" (cite.py --check
13.18.58.4 → OK 2)), so the receiving operand identifies no data item (§8.4.2.1, "a statement shall contain a reference
that uniquely identifies that resource"). The CODE is right (COBOL1639, which the golden pins). The MESSAGE is
wrong: `'T' is not defined — no declaration in this source element gives the name 'T' … Check the spelling, or declare
the item.` T IS declared, as a type-name, and the advice sends the user hunting a typo.

**Code sites (the same defect shape PB1266 fixed for index-names and PB567 for condition-names).**
- `src/WiseOwl.Cobol.Compiler/Binding/ReferenceResolver.cs#ReportUnidentified` (the `candidates.Count == 0` arm, about
  line 336): it screens screen-names, alphabet-names, index-names and condition-names before saying "not defined",
  but not `DataBinder.TypeDecls` (`DataBinder.cs:201`).
- `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs#ResolveClauseOperand` (about line 2193) writes its own "no declaration
  … gives the name" text for clause operands and screens none of those kinds.

**Why it was not fixed in the landing.** Two sites already word the same verdict separately, and the honest fix is
ONE "what is this name declared as, if not a data item" query that both ask (screen, alphabet, index, condition,
type), with a unit test per kind. That is a diagnostics restructuring, beyond a golden-lane lander's slice (I9).
