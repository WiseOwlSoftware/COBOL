# PB218

Found by the cluster-B review fleet on the pre-commit [[PB169]]–[[PB172]] tree, 2026-08-31. [[PB171]] added to
`ExpressionBinder.NonNumericInNumericContext` a comment and a diagnostic suffix quoting §8.3.3.6.3 SR1 a —
"without the ALL phrase" — justified by a claim about the grammar that is **false**:

> "the grammar routes the bare word to ZERO() and every ALL form to allLiteral()"

`figurativeConstant` lists `ALL ZERO` as its OWN alternative (alongside `ALL SPACE`, `ALL HIGH_VALUE`, …), and
ANTLR generates one context type with an accessor per token across all alternatives, so for `ALL ZEROS` BOTH
`fig.ALL()` and `fig.ZERO()` are non-null. The screen's first arm was `if (fig.ZERO() is not null) return
new BoundNumLiteral("0")`, so the ALL form took the admitted arm and the quoted bar enforced nothing.

**MEASURED BEFORE THE FIX** (`--std 2023`, strict): `IF ALL ZEROS IS POSITIVE … ELSE …` compiled clean, ran,
and printed `F` — i.e. it bound to the constant 0 and evaluated `0 > 0`.

## The bar DOES bind here — derived, not inherited

The review split on whether SR1 a's antecedent holds at this position, so it was re-derived from the text. All
three `cite.py --check` clean:

  * §8.3.3.6.3 SR1 a — "If the literal is restricted to a numeric literal, the only figurative constant
    permitted is ZERO (ZEROS, ZEROES) **without the ALL phrase**."
  * §8.8.4.7.3 SR1 — "Arithmetic-expression-1 shall be any single numeric data item described with a usage other
    than a standard floating-point usage, or any form of arithmetic expression." So a sign condition's operand
    IS an arithmetic expression and §8.8.1.1 governs it.
  * §8.8.1.1 — "An arithmetic expression may be an identifier referencing a numeric data item, **a numeric
    literal**, the figurative constant ZERO (ZEROS, ZEROES), such identifiers, figurative constants, and
    literals separated by arithmetic operators …". The LITERAL an arithmetic expression may contain is
    restricted to a numeric literal, which is exactly SR1 a's antecedent; and the figurative §8.8.1.1 names is
    the bare word, never `ALL ZERO`.

Both rules converge on the same answer, so `ALL ZEROS` is not an admissible arithmetic operand and the screen
must reject it. ⚠ The reachable witness is the SIGN CONDITION, not `COMPUTE`: `COMPUTE N = ALL ZEROS + 1` does
not reach this screen at all — `ZeroTokenRewriter` retypes a `ZERO` token adjacent to an arithmetic operator as
`ZERO_ARITH`, and `primaryExpression` has no `figurativeConstant` alternative, so that spelling is a parse
error. Two of the four reviewers cited it; it is wrong and is recorded here so it does not propagate.

**FIXED BY:** `if (fig.ZERO() is not null && fig.ALL() is null)` in
`ExpressionBinder.NonNumericInNumericContext`, plus a diagnostic that states the rule instead of alluding to it,
plus the false grammar claim replaced by the measured mechanism.

**BLAST RADIUS, MEASURED NOT ARGUED.** Two corpus programs contain `ALL ZERO` in a position that could plausibly
reach the screen, and both still compile: `tests/conformance/2023/pb157_compute_bit_group.cob`
(`COMPUTE H = ALL ZERO` — the BOOLEAN channel, where §8.3.3.6.4 GR4 gives ZERO "one or more of the boolean
character '0'", not a numeric reading) and `tests/nist/programs/NC250A.cob:1678` (`IF ALL ZEROES = ZERO-D` — a
RELATION condition, where the literal is not restricted to a numeric literal and SR1 a's antecedent fails). In
the GnuCOBOL differential corpus, 9 of 1,323 cases contain `ALL ZERO`; 7 are already rejected and the two
AGREE_ACCEPT ones are a MOVE (`run_file:446`) and a SCREEN SECTION `FROM` clause (`syn_screen:221`) — neither is
a numeric context. Expected differential movement: **zero**.

**PINNED BY:** negative fixture `pb218-all-zero-sign-condition` (reject-at 85/2002/2014/2023, COBOLNET0844).

## Also landed here: the `positionRule` thread, half fixed and half declared

The same review found that `BindOperandExpr(node, positionRule)` consumed its clause at exactly ONE of the
walk's five arms — the bare `NonNumericLiteralContext` — so `IF "ABC" IS POSITIVE` named §8.8.4.7.3 SR1 while
the WRAPPED spelling of the same literal, and every data-item operand, cited §8.8.1.1 alone. That is a
diagnostic-COMPLETENESS inconsistency across the three delegating rows, not a wrong-clause defect: §8.8.1.1
genuinely does govern an arithmetic operand, so nothing cites a rule the programmer did not break.

The cheap half is threaded (`NumLiteral(l, positionRule)`); the remaining two arms — `BindExprCore` and
`RefExpr`, which would need the clause carried through the whole expression spine — are DECLARED in the funnel
entry table of `docs/rearchitecture/DESIGN-binder-bound-tree.md` rather than left to be rediscovered, so the
next rule added to a delegating row knows what it inherits.
