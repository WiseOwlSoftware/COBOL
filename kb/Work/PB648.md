# PB648 — OPEN — a dead lookup is an unverified one

Found 2026-09-05 by the `PB623` implementer (report §"New defects" (2)). `Pow10.AsDouble(-2)` fell out of its
table into a loop that ran zero times and returned 1, so `PIC 9(9)PP` stored a value 10² too large and then
truncated it to zeros; PB623 deleted `AsDouble` and handles a negative scale explicitly in `TryExactScaled`. The
same shape survives in `Pow10.AsWide` (`src/Cobol.Net.Runtime/Values/Numeric/Pow10.cs:25`–`:29`, and the sibling
loop at `:39`): `for (int i = 0; i < n; i++) r *= 10;` for `n < 0` returns 1.

## Why it is a defect with no repro

§13.18.40.3 rule 14 bounds PICTURE digit positions at 1 through 31 (`cite.py --check 13.18.40.3 "the number of
digit positions described by character-string-1 shall range from 1 through 31"` — PB623 ran it, OK), and a
trailing-`P` receiver's scale is NEGATIVE, so "n ≥ 0" is an assumption every caller can violate and one caller
already did. No caller reaches `AsWide` with a negative scale today (PB623's sweep left `AsDouble` with zero
callers and `AsWide`'s callers all pass a PICTURE scale after normalisation) — which is precisely the state in
which nothing contradicts the table ([[a_dead_lookup_is_also_unverified]]).

## Fix

`AsWide` (and the `:39` sibling) throw `ArgumentOutOfRangeException` for `n < 0` with the invariant in the message,
plus a unit row in `CarrierLandingFormTests` (or `Pow10Tests`) asserting the throw and the table's edge (`n = 38`,
the carrier's last power); a caller that legitimately needs 10^|n| as a divisor uses the five-cofactor form PB623
introduced (`FiveAsWide`) with the sign handled where the scale is known. One-line fix, one test, no behaviour
change for any conforming program.
