# PB776 — OPEN — a gate command that names nothing, in the document that defines the gate

Filed 2026-09-06 by the registrar. **⛔ Both premises of the dispatch that produced this note are wrong, and the
defect underneath them is larger than either.**

## ⛔ Premise correction 1 — the location is not §7

§7 (*"Backfill findings & roadmap refinements"*) is `docs/COBOLNET_REARCHITECTURE_PLAN.md:2906-3002` and contains
none of these blocks. All eight bare-filter blocks are in **PART II — LIVE-PHASE EXECUTION DETAIL** (`:3100`),
under **PHASE-14** (`:3102`); the ninth `--filter` in that part is under PHASE-16 (`:4222`). The plan's §-numbered
front matter is not where its gate commands live.

## ⛔ Premise correction 2 — a bare `--filter X` is VALID and selects tests

The dispatch said a `--filter X` with no `FullyQualifiedName~` *"matches nothing and exits 0"*. **Measured, not
inherited** — VSTest 18.10.0, against the already-built
`tests/Cobol.Net.Tests.Unit/bin/Debug/net10.0/Cobol.Net.Tests.Unit.dll` (discovery/execution only; nothing built,
nothing written):

```
--TestCaseFilter:DiagnosticRegistryDriftTests            → 5 tests listed   (property-less term defaults to FullyQualifiedName~)
--TestCaseFilter:FullyQualifiedName~DiagnosticRegistryDriftTests → the same 5
--TestCaseFilter:~DiagnosticRegistryDriftTests           → "Incorrect format for TestCaseFilter Error: Invalid Condition" — selects nothing
```

So the bare form is fine, and rewriting these blocks to add `FullyQualifiedName~` would fix **nothing**. The
malformed form is the LEADING TILDE (`feedback_vstest_filter_terms`, whose measured instance was `~X|~Y`), and no
block here uses it.

## The real defect, and its measurement

```
--TestCaseFilter:VcrStatusDriftTests   →  "No test matches the given testcase filter"
                                          no Passed!/Failed! line
                                          EXIT 0
```

A well-formed filter term naming a test that does not exist runs zero tests and **succeeds**. And three of the
names the plan's PHASE-14 gate blocks pass are exactly that. Verified with
`grep -rl "class <Name>" tests --include=*.cs` and then with a bare `grep -rn "<stem>" tests --include=*.cs`,
which returns **zero lines** for each:

| plan line | filter | verdict |
|---|---|---|
| `:3292` | `"VersionMatrixTests\|EditionGateDiagnosticTests\|CorpusRunnerTests"` | all three exist ✔ |
| `:3311` | `VcrStatusDriftTests` | ⛔ **no such class anywhere in `tests/`** |
| `:3331` | `Inv1StrongGoldenTests` | ⛔ **no such class** |
| `:3333` | `NistDifferentialTests` | exists ✔ (`tests/Cobol.Net.Tests.Conformance/NistDifferentialTests.cs`) |
| `:3353` | `DiagnosticRegistryCoverageTests` | ⛔ **no such class** (the nearest real name is `DiagnosticRegistryDriftTests`, in Unit) |
| `:3354` | `CorpusRunnerTests` | exists ✔ |
| `:3375` | `"VersionMatrixTests\|VersionBehaviorMatrixTests\|Inv1StrongGoldenTests"` | ⛔ two live terms carry one **dead** one — the [[PB708]] shape exactly: the leg still prints a verdict line and the dead term is never named |
| `:3443` | `"NistDifferentialTests\|CorpusManifestTests"` | both exist ✔ |

**Eight blocks, three distinct dead names, four blocks affected.** `:4253`'s
`--filter Category=BackendContract` is a TRAIT filter, valid syntax and a different question (whether the trait
is applied anywhere is not measured here) — it is **not** counted above.

## What each dead block was supposed to prove

This is why it is not cosmetic. Each dead filter sits under a `**Why:**` naming an exit criterion:

- `:3331` — *"decision #10 (RATIFIED) — INV-1-strong at the default edition is a G7 exit criterion; the shipping
  default must be behaviorally executed before G8."* Its verify command is `--filter Inv1StrongGoldenTests`. ⛔
  [[PB752]] records that the CI leg for the same subject filters on `FullyQualifiedName~NistProgram_MatchesGolden`
  — so the SUBJECT is tested and only the plan's name for it is wrong, which is the most dangerous version: the
  block looks confirmable and is not.
- `:3353` — *"exit criterion #4 — 'every diagnostic descriptor ≥1 case.' Closes the false-green class where a
  registered code has no test and can silently rot."* A verify block for a false-green class, which is itself a
  false green.
- `:3375` — *"exit criterion #3 + #2"*, the INV-3 behavior-variant leg, *"the currently-weakest leg of
  four-compilers-in-one"*. Two of its three terms are live, so this one prints `Passed!` and reads clean.
- `:3311` — the VCR-status drift step, whose stated purpose is *"a stale ledger becomes structurally
  impossible"*.

## Fix shape

1. **Re-derive each of the three names against `tests/`, do not guess.** `Inv1StrongGoldenTests` →
   check [[PB752]]'s `NistProgram_MatchesGolden`. `DiagnosticRegistryCoverageTests` → `DiagnosticRegistryDriftTests`
   is the nearest real name but is a DIFFERENT assertion (catalogue/doc sync, not descriptor coverage) — if the
   coverage test genuinely does not exist, the correct repair is to say so in the block, not to point it at a
   test that answers a different question (`feedback_a_real_clause_can_answer_a_different_question`).
   `VcrStatusDriftTests` → establish whether the VCR drift assertion exists under another name or was never
   written; `scripts/gen-vcr.ps1 -Check` on the line above it may be the whole guard.
2. **Route the blocks through `scripts/build-local.{ps1,sh}`**, whose `scripts/filter_population.py` call
   ([[PB708]], landed) probes EVERY term and exits non-zero on a dead one. That is what turns this from a defect
   fixed once into a defect that cannot recur — the plan's commands would then fail loudly the next time a test
   is renamed, instead of quietly passing (CLAUDE.md rule 5: prefer the shape that makes the next case
   automatic).
3. ⚠ **Do NOT "fix" these by adding `FullyQualifiedName~`.** Per the measurement above that changes nothing, and
   an edit that looks like a fix while the dead names survive is worse than the current state.

`feedback_green_gates_arent_evidence`: after the repair, run one corrected block and confirm it prints a
`Passed!` line with a nonzero test count — a verify block that still runs zero tests has not been fixed.
