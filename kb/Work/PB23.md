# PB23 — LANDED — a raw CLR exception where §15.3 requires EC-ARGUMENT-FUNCTION

> ⚙ **flags:** crashes
> `INTEGER-OF-FORMATTED-DATE("YYYYWwwD", "9999W527")` passes every §15.3.1.7 subfield rule — so §15.48.3 r4 is MET
> and §15.48.4 r1 demands a returned value — and then `CobolDate.Analyze`'s `ISOWeek.ToDateTime` reconstructs past
> `DateTime.MaxValue` and throws **`System.ArgumentOutOfRangeException`**. §15.3 rule 14 (covering an incorrect
> value "for that argument OR FOR THE RETURNED VALUE") permits only EC-ARGUMENT-FUNCTION or the
> implementor-defined result, never a CLR fault.
> ⚠ **THE WINDOW IS TWO DAYS WIDE, NOT ONE — and this CORRECTS THE ALREADY-LANDED ROW `AR-15.79.3-5`**, which
> cited only day 7. **Confirmed by measurement:** 9999-12-31 *is* ISO 9999-W52-5, so W52-6 and W52-7 are
> 10000-01-01 and 10000-01-02.

## ⛔ THE SWEEP FOUND THE BLAST RADIUS IS THREE INTRINSICS, NOT ONE

The crash is in the **shared** `Analyze`, which every formatted-date/time intrinsic calls, so the raw CLR fault
escaped all three — measured, not inferred:

| call | before | after |
|---|---|---|
| `INTEGER-OF-FORMATTED-DATE("YYYYWwwD","9999W526"/"…27")` | **`ArgumentOutOfRangeException`** | EC-ARGUMENT-FUNCTION (0 with checking off) |
| `TEST-FORMATTED-DATETIME("YYYYWwwD","9999W526")` | **`ArgumentOutOfRangeException`** | `0` |
| `SECONDS-FROM-FORMATTED-TIME("YYYYWwwDThhmmss","9999W527T101112")` | **`ArgumentOutOfRangeException`** | `36672` |

Both week formats reach it (`YYYYWwwD` and `YYYY-Www-D`). ✅ **The sibling construction sites are NOT reachable,
and that was measured rather than assumed** — `"99990231"` → 7, `"9999366"` → 7, `"9999W531"` → 7 are all rejected
at the right character, because the range table already correlates day-with-month and day-of-year-with-year. Only
the ISO-week site can overflow, because only there is the *combination* out of range while every subfield is in.

## ⛔ THE THREE FUNCTIONS MUST NOT AGREE — THAT IS THE WHOLE DESIGN OF THE FIX

The tempting fix — have `Analyze` report an error position — is **wrong**, and would have silently broken
TEST-FORMATTED-DATETIME. `9999W526` is **valid**: §15.3.1.7 requires only year 1601–9999, week 01–52/53, day 1–7,
and all three hold. So the signal must be *distinct from* the format-validity result:

- **INTEGER-OF-FORMATTED-DATE raises.** §15.48.4 r1 makes the result "the integer date form equivalent", and
  §15.5.2 caps that at "the value of FUNCTION INTEGER-OF-DATE (99991231), which is 3,067,671". There is no
  equivalent, so §15.3 rule 14's "incorrect value … **for the returned value**" arm applies exactly.
- **TEST-FORMATTED-DATETIME returns 0.** §15.92.1 tests validity "according to the specified format", and
  §15.92.4 requires any non-zero answer to be "the ordinal character position at which the first error … was
  detected" — **no CHARACTER of `9999W526` is in error**; the identical `'6'` in `2009W526` is valid. The defect
  is a property of the whole date, which that return type cannot express.
- **SECONDS-FROM-FORMATTED-TIME returns its seconds.** §15.79.4 reads only the time subfields.

⚖ **Recorded as an INTERPRETATION, with the alternative named.** §15.92.4's "format problems **or range problems**"
could be read as covering the composite overflow (returning 8). It was decided against on the structural argument
above. The external oracle is **silent** — the GnuCOBOL corpus exercises `1601W531`→7 and `2009W531`→0 (both of
which we match) but has no case at the 9999 boundary. If the owner prefers the other reading, the single place to
change is `TestFormattedDatetime`'s `out _`.

## ✅ LANDED

`ISOWeek.ToDateTime` is gone from `Analyze`. §15.3.1.7 fixes week 1 as "the week that includes January 4", so its
Monday is computed directly and every later day is a plain integer offset — **the arithmetic cannot overflow**,
which matters because the input is legal and no range-table tightening could have prevented the fault. The result
is then bounds-checked against `MaxIntegerDate` (§15.5.2) on **every** path, not just the week one, so the
calendar and ordinal paths stop depending on their range expressions each staying right ([[feedback_one_rule_one_place]]).

**Tests.** Golden `tests/conformance/2023/pb23_week_date_beyond_integer_date_form` (13 sections, EC checking ON,
each value derived from the spec before the run) · `CobolDateIntegerDateRangeTests` (24 cases), whose centrepiece
is an **equivalence proof over >200,000 week dates spanning 1601–9999** that the hand-derived arithmetic matches
`ISOWeek` everywhere `ISOWeek` can express an answer — with a population assertion so it cannot pass vacuously. A
hand-derived calendar is exactly the thing that is right at the boundary tested and wrong three centuries away.

**⛔ AND THE INVENTORY'S OWN NAMED TEST GAP IS CLOSED.** `RV-15.48.4-1` recorded that *nothing* exercised a
COMBINED format for this function and that "Annex D.31.5.8's own worked example … is the obvious fixture and is
absent". The golden now carries D.31.5.8's and D.31.5.9's examples verbatim — `"YYYYMMDD"/"19950215"` and
`"YYYYMMDDThhmmss.ss+hhmm"/"19950215T05142781+0500"` both → 143951; `"hhmmss.ss+hhmm"/"05142781+0500"` and its
combined form both → 18867.81 — so the §15.48.4 / §15.79.4 NOTE that the other half "does not impact the returned
value" is verified by TEST rather than by code reading.

**Inventory:** `AR-15.48.3-4`, `AR-15.48.3-5`, `RV-15.48.4-1` and `AR-15.79.3-5` all moved **DIVERGES → CONFORMS**
with test-refs, through `scripts/spec/record_verdicts.py` (verdicts are never hand-written). **GAP 3907 → 3903.**
Each of those rows had said "ONE ROOT CAUSE, ONE FIX … do not triple-count", and that turned out to be exactly
right.
