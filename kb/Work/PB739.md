# PB739 — a shared EXTEND connector appends at a byte offset captured at OPEN, so the second connector's record eats the first

Found 2026-09-06 by the `PB713` implementer (report, "New defects (a)") while proving the shared-EXTEND OPEN.
`GR-14.9.51.4-19` was deliberately left GAP for it: PB713's fix made the shared `OPEN EXTEND` succeed, and this
note is what the WRITEs through it then do.

## The facts

- **Reproduced**, on the PB713 tree (so this is not PB713), with
  `E:\Temp\claude\E--CobolSharp\a9d94900-79fe-4a38-89f0-921976861543\scratchpad\PB739\probe\pb713g19.cob`
  (`PB713G19`) — three `SELECT`s on `"pb713g19.dat"`, `ORGANIZATION IS SEQUENTIAL`; a plain seeding connector,
  then `FA` and `FB` both `SHARING WITH ALL OTHER` / `LOCK MODE IS MANUAL`. Seed `SEED`, `OPEN EXTEND FA`,
  `OPEN EXTEND FB`, `WRITE AAAA` through A, `WRITE BBBB` through B, close both, read back:

  ```
  A-EXT=00  B-EXT=00  A-W=00  B-W=00
  R1=SEED  R2=BBBB  R3=BBBB  R4=BBBB      ← only two records exist; AAAA is gone
  od -c pb713g19.dat →  S E E D B B B B
  ```

- **The whole matrix was measured, not deduced** (`…\PB739\probe\pb739mx.cob`, `PB739MX`) — two shared EXTEND
  connectors interleaving one write each over a one-record file, per organization and framing:

  | shape | records after | verdict |
  |---|---|---|
  | record sequential, fixed width | 2 (`SEED`, `BBBB`) | **`AAAA` LOST** |
  | line sequential | 2 (`SEED`, `BBBB`) | **`AAAA` LOST** |
  | record sequential, `RECORD IS VARYING` | 2 (`SEED`, `BBBBB`) | **`AAAA` LOST** |
  | relative | 2 (`SEED`, `BBBB`), and **both** connectors returned `R-K = 0002` | **`AAAA` LOST + a duplicate key** |
  | indexed | 3 (`K002`, `K004`, `K006`) | correct — the shared `IndexedStore` is the medium |

## The rules

- §14.9.51.4 GR19 — *"If two or more file connectors for a sequential file add records by sharing the physical
  file after opening it in extend mode, the added records follow the records present in the physical file when
  it was opened, but are otherwise in an undefined order."* Only the ORDER between the two connectors is
  undefined; both records shall be there. (`cite.py --check 14.9.51.4 …` → `OK §14.9.51.4 19)`)
- §14.9.51.4 GR12 — *"The successful execution of a WRITE statement releases a logical record to the operating
  environment."* Both WRITEs reported '00', so both records were promised to the operating environment.
- §14.9.51.4 GR29 a) — for a relative file, *"If the physical file is shared and the open mode is extend, the
  record numbers are not necessarily consecutive. Otherwise, they are consecutive."* The number is therefore
  derived at the moment of the release, from the file, not from a base captured at OPEN — and GR31 says the same
  from the other side: *"the relative key values returned are ascending, but not necessarily consecutive."*
- §9.1.15 item 3 — *"The sharing with all other mode allows concurrent access to a physical file through other
  file connectors specifying input, I-O, or extend mode"*, and §14.9.27.4 Table 19's ALL OTHER/EXTEND ×
  ALL OTHER/EXTEND cell is a *Normal open*. The shape is legal; the loss is ours.
- §9.1.16 — *"While locked by a given file connector, a record is not accessible to another file connector in
  the same or a different run unit"* — so the ordinal a sequential connector reports for the record it just
  released is a lock IDENTITY, and two connectors reporting the same ordinal lock the wrong records.

## The mechanism

`SequentialConnector.OpenCore`'s `FileOpenMode.Extend` arm builds its writer over a .NET `FileMode.Append`
`FileStream`. .NET's Append seeks to the end ONCE, at open, and then writes from that stream's own position; it
is not the host's atomic append. Two connectors therefore hold two writers both anchored at the same offset,
each `StreamWriter` buffers its record, and the later flush (here `CLOSE FB`) overwrites the earlier one.

`RelativeConnector` is the same defect one layer up: `OpenCore`'s extend arm sets
`_seqNext = (_slots.Count == 0 ? 0 : _slots.Keys.Max()) + 1` at OPEN and `Write` releases into `_slots[_seqNext]`.
Both connectors capture 2 over a one-record file, and `_slots[2] = rec` replaces rather than appends.

`IndexedConnector` is correct, and for the reason that names the fix: its release ordinal is minted from the
SHARED `IndexedStore` at the moment of the write, and its key is the program's own value.

## What it costs a user

Silent data loss on a successful status, in the exact multi-connector shape the sharing feature exists for. A
batch that appends through two connectors keeps whichever record was flushed last and reports '00' for both.

## Landed

**2026-09-06.** One rule, in the one place each organization keeps its shared medium: **the position AND the
identity of a released record are read from the shared medium at the moment of the release, never from
per-connector state captured at OPEN.**

- **`HostFile` gained its third role** — `OpenAppendStream(path, sharedConnector)`. .NET's `FileMode.Append` is
  not the host's atomic append: it seeks to the end once, at open. An exclusive connector keeps that handle byte
  for byte (nothing else can be writing — its `FileShare.Read` posture forbids it); a §9.1.15 participant gets
  `SharedAppendStream`, which repositions at the physical end before every write, over an UNBUFFERED handle.
- **`SequentialConnector.ReleaseRecord`** is now the ONE place a sequential record is released, reached by all
  three write arms — the two print-control arms never minted an ordinal at all, and a plain WRITE on a print or
  LINAGE file reroutes THROUGH one of them, so the arm that skipped it was the arm those files always take. For a
  participant it flushes (§14.9.51.4 GR12) and mints the ordinal from
  `PhysicalFileTable.State.ReleasedOrdinal`, the per-physical-file mint, seeded by a shared `OPEN EXTEND` from
  the records already present and reset by a shared `OPEN OUTPUT`.
- **`RelativeConnector`'s captured `_seqNext` is gone.** `NextSequentialSlot()` is `Max(store.Highest,
  _lastReleasedSlot) + 1`, which is all four sentences of GR29 a) in one expression: 1 after OUTPUT, highest+1
  after EXTEND, consecutive when nothing else releases, ascending-with-gaps when something does. The clamp is not
  redundant — a sibling connector open I-O may DELETE the top record (§14.9.10.4 GR5), lowering the highest
  EXISTING number below one this connector already used, and GR29 a) still requires ascending.
- **`RelativeStore`'s map is exposed `IReadOnlyDictionary`**, with `Put`/`Remove`/`Clear` maintaining `Highest`.
  The invariant is structural rather than a convention: there is no second way to change the store, so the
  high-water mark cannot be left stale. (`Highest` is maintained rather than scanned because a
  `SortedDictionary` has no O(1) maximum and an n-record append would have been O(n²).)
- **`FileConnector.SharedStreams` is derived** from the new `SharedPhysical` (the physical file's shared state),
  so §9.1.15 participation and the state it grants are one fact, not two — a connector that participates but
  holds no shared state can no longer be expressed. `SharedExtendOpenDriftTests`' one-writer guard is re-pointed
  at it and now also asserts the property has no setter.

**Goldens.** `tests/conformance/2023/pb739_shared_extend_write` (`PB739EXW`) and
`tests/conformance/2002/pb739_shared_extend_write` (`PB739E02`), split by edition floor because
`ORGANIZATION IS LINE SEQUENTIAL` is COBOL-2023 (PB688) while `SHARING`/`LOCK MODE` are COBOL-2002. Each runs the
two-connector interleave on every organization and framing it admits, plus the exclusive control; the relative
leg displays R-KA=0002 / R-KB=0003 and the indexed leg releases K006 through A and then K004 through B, which
GR38 permits because it measures the high key "through that file connector".

**Guards.** `tests/Cobol.Net.Tests.Unit/SharedExtendWriteDriftTests.cs` — 27 cases over
(organization × framing × spelling), the exclusive control, the print-control arm, the `RelativeStore`
high-water invariant, a static ban on `FileMode.Append` outside `HostFile`, and the append stream's own
contract. Proved red on the pre-fix behaviour at **17 of 27** (the six loss rows, the six ordinal rows, both
relative rows, the print arm and the two append-role facts), with the exclusive control and the indexed rows
green on both trees.
