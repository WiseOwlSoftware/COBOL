# PB907 — OPEN — a rule that names a KIND, asked as a C# type test

Source: the `PB425` report, "New defects" item 1 — re-derived here, because the report's own supporting
quotation is not in the standard (see **The citation the report inherited** below).

## The measurement

`<scratch>/reg7/probe/x5_alias_varlen.cob`, `--std 2023`, on this tree's build:

```cobol
       01 SRC.
          05 S1 PIC X(3) VALUE "ABC".
          05 S2 PIC X(3) VALUE "DEF".
       66 SALIAS RENAMES S1 THROUGH S2.
       01 DST.
          05 D1 PIC X(1) OCCURS DYNAMIC CAPACITY IN CAPN.
       PROCEDURE DIVISION.
           MOVE SALIAS TO DST
```

```
x5_alias_varlen.cob(12,12): error COBOLNET1931: MOVE involving the variable-length group 'DST': the sending
operand is not a group item: a variable-length group may move only to or from a compatible GROUP
(ISO §8.5.1.12.1) — ISO §14.9.25.3 SR9 requires the two groups to be compatible as specified in §8.5.1.12
```

**THE CONTROL IS WHAT MAKES THIS A DEFECT AND NOT A TASTE.** `x6_group_varlen.cob` is the same program with
`66 SALIAS RENAMES …` deleted and `MOVE SRC TO DST` in its place — an ordinary fixed group:

```
x6_group_varlen.cob(11,12): error COBOLNET1931: MOVE involving the variable-length group 'DST': the
dynamic-capacity table 'D1' of 'DST' occupies relative byte position 0 and the other group has no table
there (ISO §8.5.1.12.1 rule 1 / §8.5.1.12.2) …
```

Two different messages for two senders the standard classifies identically. The second is the §8.5.1.12.2
COMPATIBILITY answer — the question SR9 actually asks. The first is a claim about the sender's KIND, and it
is false. `x4_alias_fixed.cob` closes the triangle: `MOVE SALIAS TO DST2` with `01 DST2 PIC X(6)` prints
`DST2=[ABCDEF]`, so the alias is a perfectly good MOVE sender everywhere except this screen.

and the sentence the screen contradicts, read from §13.18.45.4 (RENAMES, General rules) in full:

> 2) When the THROUGH phrase is specified, data-name-1 **defines an alphanumeric group item** that includes
> all elementary items starting with data-name-2 … and concluding with data-name-3 …

So a THROUGH alias IS a group item for every rule that says "group item", and GR9's antecedent ("both …
are group items") is satisfied by `(SALIAS, DST)`. Whether the pair is COMPATIBLE is §8.5.1.12.2's question
and the answer may still be no — but it has to be ASKED, and the user has to be told the real reason.

## The code site

Both screens take the structural route:

* `src/Cobol.Net.Compiler/Binding/Validation/StatementValidation.cs#CheckVariableLengthMove` — the site that
  emits COBOLNET1931's "the sending operand is not a group item" arm.
* `src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs#VariableLengthGroupMove` — the emitter twin, which
  selects GR9's route on the same test, so even a screen that passed would take GR4's plain group move.

`Item.IsGroup` is a STRUCTURE question ("does this entry have subordinates"); §14.9.25.4 GR9 and
§13.18.45.4 GR2 are CATEGORY questions ("is this a group item"). A level-66 entry has no subordinates and
answers `false` to the first while the standard answers `true` to the second. This is
`feedback_model_the_rule_shape_not_one_case` in one predicate.

## The sibling sweep the fixer owes

`grep -rn "IsGroup" src/Cobol.Net.Compiler/` and, for each site, ask which of the two questions the rule it
implements is asking. Registrar #6 filed **PB878** for the §14.9.25.3 askers that ask a SUBSET of Table 16;
