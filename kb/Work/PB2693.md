# PB2693 — two consequences of the reloading keyed store

## What was found (w1042 D, PB2660, landed in train 1042)
PB2660 made a keyed connector whose sharing posture admits another writer (SHARING WITH ALL OTHER) reload the whole
store when the store's generation moved, under a byte-range store mutex, and read and write it positionally
(`RandomAccess`) through its own handle. Two consequences were left:

1. **Duplicate-key walk across a foreign reload (wrong answer, cross-run-unit only).** `IndexedConnector.Fill`
   rebuilds the store from file order and so renumbers the release ordinals the duplicates of an alternate key are
   ordered by. A connector partway through such a walk keeps `_readOrdinal` (the prior READ's record's release
   ordinal), which after another run unit's write may name a different place in the new numbering, so the next READ
   NEXT may skip or repeat a record. §14.9.30.4 GR26 (`cite.py --check` OK) makes duplicates of an alternate key available in the order in which WRITE statements released them, the order the
   records were released; a reload must keep each record's ordinal (persist it with the frame) rather than derive
   it from file position. Repro (expected, not yet probed): run unit A opens an INDEXED file with an alternate key
   WITH DUPLICATES I-O, READs the first of three duplicates; run unit B WRITEs a record whose key sorts earlier in
   file order; A's READ NEXT should return the second duplicate.
2. **RESERVE integer-1 is inert for RELATIVE and INDEXED.** The keyed store handle's buffer is never used, because
   store I/O is positional (`FileSupport.cs#OpenConnectorStore` still sizes `InputOutputAreaBuffer(areas)`). The
   determination DOC-A.1-164 in `docs/CONFORMANCE.md` describes the keyed arm as sizing that buffer; re-determine it
   (RESERVE is implementor-defined in effect) and drop the dead sizing, or route the reads through it.

## Landed 2026-10-08 (w1045d)
**Re-probe on the w1045d build.** The note's WRITE repro does NOT reproduce: a new record is released last under every
key, so a reload numbers it after every existing record and the walk is undisturbed. The same mechanism DOES fail on
another run unit's DELETE of an EARLIER-released record (two `FileRegistry` instances are two run units):
`unit:CrossRunUnitKeyedStoreDriftTests.ADuplicateKeyWalk_KeepsItsPlace_AcrossAnotherRunUnitsChange("delete")` —
A reads `0002D` (first of D2, D3, D4 under the alternate key), B deletes `0001A`, A's READ NEXT returned `0004D` and
skipped `0003D` (expected `0003D`, `0004D`; §14.9.30.4 GR21 f) 1., GR26). After the fix all three changes pass.

**Fix 1 — the ordinals are the file's (store format 4).** `RecordFraming` carries each indexed record's release-
ordinal vector in its frame (key count × 8 bytes, prime first) and the release mint in the header (offset 28);
`IndexedConnector.Fill` keeps them (never renumbers from file position) and `PersistFrames` writes them, in release
order. `PersistOrder` (the topological order) is deleted: its cyclic residue, kb/Work PB701, is gone with it
(`unit:CrossRunUnitKeyedStoreDriftTests.EachKeysDuplicateOrder_SurvivesTheClose_WhenNoSingleRecordOrderCarriesThem`).
⚠ DETERMINATION: this answers PB701's owner question with its first option (a per-record slot in the framing), with
no migration — CLAUDE.md rule 4, no backward-compatibility requirement; a version-3 store is Foreign ('39').

**Fix 2 — RESERVE for RELATIVE and INDEXED.** The areas were the store handle's stream buffer, which no store byte
passed through. They are now `KeyedConnector._areas`, allocated by the OPEN that takes the file lock, and every load
and persist passes through them (`ReadThroughAreas` / `WriteThroughAreas`); the handle is unbuffered. DOC-A.1-164
re-determined; DOC-A.1-107 (boundary RRNs 536 870 887 / 888 under the 36-byte header) and DOC-A.1-146 (d) corrected.
