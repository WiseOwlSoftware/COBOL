# PB172

R29 introduced ONE window context for every §13.18.38.3 r7 position. PB155 widened the §8.8.1.1 DATA-ITEM
screen to it safely — a sole data reference short-circuits through FieldOperand before OperandRef, so only
compound (arithmetic) operands reach the screen in comparand positions. The INTRINSIC-result screen at
BindPrimary has no such short-circuit: a sole `FUNCTION LOWER-CASE(X)` relation comparand and an arithmetic
`FUNCTION LOWER-CASE(X) + 1` term arrive identically, so the widening rejected legal comparisons (six NIST
IF-suite programs, pb101_alphabet_locale_pcs, 2002/char_national — measured by the PB155 wave gate) and was
reverted to Arithmetic-only. CONSEQUENCE: an alphanumeric/national/boolean function in a genuinely-arithmetic
window position — `SET IX TO FUNCTION LOWER-CASE(X)`, `PERFORM VARYING V FROM FUNCTION REVERSE(X)`,
`T(FUNCTION CURRENT-DATE)` (compound form) — compiles clean under STRICT and dies at run time in the numeric
renderer, the wrong-stage family.

WHAT WOULD CLOSE IT: split the context — Comparison (relation/EVALUATE comparands: ConditionBinder,
EvaluateBinder) vs the arithmetic index windows (SET, VARYING, subscripts: SetBinder, ControlFlowBinder,
SubscriptSegments, PtrBinder, ReportWriterBinder) — apply BOTH §8.8.1.1 screens in the arithmetic split, and
sweep each R29 call site to the correct member; negative fixtures for the SET/VARYING function shapes.

*(Found landing kb/Work PB155, 2026-08-29 — the review fleet's guard-widening finding was correct for data
items and measurably wrong for intrinsic results; the wave gate's NIST leg caught the over-reach.)*

## Re-verification and correction (2026-08-31, cluster-B implementation wave, tree `9a89fbd1`)

⛔ **THE "CRASH AT RUN TIME" CLAIM IS REFUTED FOR THE SHAPES THE NOTE NAMES.** Measured:

    SET IX TO FUNCTION LOWER-CASE(X)            -> compiled clean AND RAN to completion. No crash.
    SET IX UP BY FUNCTION REVERSE(X)            -> compiled clean AND RAN to completion. No crash.
    PERFORM VARYING V FROM FUNCTION REVERSE(X)  -> compiled clean, loop STARTED AT V=0000 and ran to 0003.

These are **silent wrong answers**, not crashes: the alphanumeric result reaches
`NumericRenderer`'s alphanumeric arm and digit-decodes through `CobolNum.FromAlphanumeric`, so "DCBA" becomes
0 rather than raising. The harm flags should read `wrong_answer` / `silent`, not `crashes`. The one genuine
CRASH found in this area is a different shape and now has its own note — [[PB214]], `EVALUATE X WHEN X"6162"`,
which dies with an unhandled `NotImplementedCobolFeatureException`.

⛔ **THE NOTE'S PRESCRIBED DESIGN WAS NOT FOLLOWED, and the fixture that proves why is in the landing.** The
note says to SPLIT `OperandContext` into Comparison vs the arithmetic windows and "sweep each R29 call site to
the correct member" — a ten-site hand classification, which is precisely how a two-arm dispatch is created. It
also mis-frames the rule: **the boundary is SOLE-vs-COMPOUND, not statement-vs-statement.**
`IF FUNCTION LOWER-CASE(X) = Y` is legal and `IF FUNCTION LOWER-CASE(X) + 1 = Y` is illegal **in the same
statement kind**, so no per-statement context member can express it.

**FIXED BY** (an engineering choice, stated rather than slipped in): adding the missing SOLE-FUNCTION
short-circuit beside the three that already existed in `ConditionBinder.ComparisonOperandOf` and
`EvaluateBinder.BindValueOperand` (sole data ref → sole numeric literal → **sole function call**), which is
what finally makes the widening safe — a sole function comparand no longer reaches the screen, a compound one
does. With that in place the screen keys on `OperandContextRules.Rules().NumericClassScreen` instead of one
enum member, and the eight genuinely-arithmetic window sites gain it **with no per-site edit at all**. The
screen also now reads the CLASS (`IntrinsicArgumentRules.CandidateClasses` → `IntrinsicResultType.Resolve`)
rather than `ResultCategory`, which the classifier's own PB124-wave-5b note documents as insufficient for
§15.2 item 6 index functions — widening a screen that carried a known hole would have spread it to eight sites.

`negative/pb172-relation-compound-alphanumeric-function` is the fixture that discriminates between the two
designs: the note's context split would fail it.

⚠ THE RE-ATTEMPTED WIDENING IS THE ONE THAT BROKE SIX NIST IF PROGRAMS. Their shape is distilled into
`tests/conformance/2023/pb172_sole_function_operand` so the ~2-minute wave gate catches an over-reach that
previously took the full NIST leg; the NIST leg still runs for the batch.
