# PB41 — OPEN — a SCALED numeric subscript / ref-mod position uses its UNSCALED storage

> ⚙ **flags:** wrong-answer · silent
> **FOUND WHILE DESIGNING [[PB17]]'s COMPILER TEMP, NOT BY LOOKING FOR IT.** D18 specifies the temp as
> `Scale: 0`. Asking what that truncation would do to a NUMERIC-typed function result led to the question
> "what does the compiler do with a scaled subscript TODAY", and the answer is: it uses the raw storage.

**MEASURED (2026-08-04, at `f9983805`, the battery-green tree):**

```cobol
01 W-G.
   05 W-E PIC 9(2) OCCURS 5 TIMES.
01 W-S PIC 9V9 VALUE 2.0.
...
    MOVE 22 TO W-E (2)
    MOVE W-E (W-S) TO W-R
    DISPLAY "SCALED=" W-R
```

```
SCALED=00          <- expected 22
```

The emitted C# names the mechanism outright:

```csharp
private long W_S = 20L;                                     // W-S  — unscaled storage of 2.0
W_R = (long)(CobolNum.Store(CobolTable.At(W_G.W_E, CobolTable.Occ(W_S)), 0, _P_3));
```

`CobolTable.Occ(long)` is `value => value`, and `ReferenceResolver.ResolveSubscriptName` never consults
`Pic.Scale`. So the occurrence number is **20**, `CobolTable.At` finds it outside `1..5`, and the benign
scratch slot reads `00`. Compiles clean, runs to completion, prints the wrong answer.

## ⛔ THE SPEC MAKES THIS A VALUE QUESTION, NOT A STORAGE QUESTION

Every citation below `cite.py --check`ed.

| # | clause | what it gives |
|---|---|---|
| 1 | **§8.4.2.3.2** | a subscript may be `arithmetic-expression-1` |
| 2 | **§8.8.1.1** | "An arithmetic expression may be an identifier referencing a numeric data item" ⇒ a `PIC 9V9` item is a legal subscript |
| 3 | **§8.4.2.3.4 GR1b** | "If arithmetic-expression-1 is specified, the subscript is **the result of the evaluation** of arithmetic-expression-1. If the evaluation of arithmetic-expression-1 does not result in an integer, the EC-BOUND-SUBSCRIPT exception condition is set to exist." |

So the subscript is the item's **VALUE** (2.0), which IS an integer, and the correct answer is `W-E(2)` = 22.
The unscaled storage 20 is an artifact of the representation, never the value.

⚠ **AND THE SIBLING POSITION HAS THE SAME RULE WITH A DIFFERENT EC.** `RenderSegment` serves reference
modification too, and **§8.4.3.3.4 rule 5)c)** says "If the evaluation of leftmost-position or length results in
a non-integer value, a zero value, or a value that references a position outside the area of identifier-1, the
**EC-BOUND-REF-MOD** exception condition is set to exist." One rule shape, two EC names — so the fix must be
POSITION-AWARE, not a single `Occ` that always names EC-BOUND-SUBSCRIPT.

## ⚖ WHY THIS IS PART OF [[PB17]] AND NOT A SEPARATE LATER FIX

D18 materializes a function-identifier subscript into a compiler temp and reads it back through this same
channel. Choosing D18's literal `Scale: 0` temp would bake this exact truncation into the NEW path: a
NUMERIC-typed function (`W-E(FUNCTION SQRT(2))`) would silently index occurrence 1 instead of setting
EC-BOUND-SUBSCRIPT per GR1b. The temp's description cannot be settled without settling the integrality rule,
so the two land together — and the data-name half is the pre-existing sibling the sweep (CLAUDE.md rule 4)
turns up. See [[feedback_one_rule_one_place]].

## ✅ LANDED 2026-08-04 — with [[PB17]], in one change set

**The fix is ONE ordinal-position read**, `ReferenceResolver.PositionRead`, rendering `CobolTable.Occ(path, scale)`
for a subscript and `CobolString.RefModPosition(path, scale)` for a ref-mod position over the shared
`CobolNum.HasFraction`/`PositionOf` arithmetic — two wrappers ONLY because the positions name different Table 13
conditions. The position kind travels as a `SegmentPosition` parameter, never as renderer state, because
`RenderSegment` is re-entrant through `ReadRefMod`. A scale-0 item keeps the exact previous text, so the emitted C#
for ordinary subscripts is byte-identical. Canonical in `COBOLNET_DATA_MODEL_DESIGN.md` **D18**.

⚠ **THE CASE THE FIRST SHAPE WOULD HAVE MISSED — a COMPOUND segment.** GR1b tests the integrality of THE RESULT,
not of each operand: `W-E(W-P + W-Q)` with `W-P = W-Q = 1.5` has the integral result 3.0 and is legal, while
de-scaling each operand first gives `1 + 1 = 2` **and** raises the condition twice on source that never violated
it. Such a segment routes to D18's temp and the rule applies once, where the standard applies it.

**MEASURED:** `SCALED=22` · `COMPOUND=33` · `RMSCALED=[BC]`; and with checking ON, a non-integer value raises
**EC-BOUND-SUBSCRIPT** and **EC-BOUND-REF-MOD** respectively, for BOTH the scaled-data-name and the numeric-function
forms. Goldens `tests/conformance/2023/pb41_scaled_position.cob` and `pb41_position_not_integer.cob`.

## ✅ THE THREE UNMEASURED SIBLING CHANNELS — ALL PROBED, ALL CLEAN

The note previously listed these as open, with the instruction to probe rather than claim. Measured at the landing
tree, none is a PB41 sibling:

| channel | measured | why |
|---|---|---|
| `SET` an index FROM a scaled item | `SETIDX=22` — correct | the index takes the VALUE, not the storage |
| a `PERFORM VARYING` bound compared against a scaled item | `VARYING=02` — correct | an ordinary relation, already value-based |
| `OCCURS … DEPENDING ON` a scaled item | **rejected**, `COBOLNET0852` | **§13.18.38.3 SR17** "Data-name-1 shall describe an integer" — illegal SOURCE, so there is no runtime value question to get wrong |

The ODO row is the interesting one: it looked like the same shape and is a different KIND of rule — a syntax rule,
already enforced. Both `SET`/`VARYING` rows are pinned by `pb41_scaled_position`.
