# PB635 — LANDED — the wrong question at the float dispatch

Found 2026-09-05 by the `PB254` implementer (report §"New defects" (A)) while widening FIND-STRING's argument-3
intake; not fixed there because the dispatch it lives in is `RenderFloat`'s, which PB253 restructured on the same
day (train 6 row 1), and because adding a `FindStringReal` body would encode the wrong shape.

## Repro (`--std 2023`; `<a9d94900 scratch>/PB254/probe5.cob`)

```cobol
       01 FL USAGE FLOAT-LONG.
       ...
           COMPUTE FL = 1.0E19
           MOVE FUNCTION FIND-STRING(WS-HAY WS-NDL START AFTER FL) TO WS-P
```

```
error CS0117: 'CobolIntrinsics' does not contain a definition for 'FindStringReal'
```

The emitted line — `FindStringReal((double)(CobolNum.FromAlphanumeric(WS_HAY)), (double)(CobolNum.FromAlphanumeric(WS_NDL)),
CobolFloat.Sending((double)(FL)))` — is wrong three ways at once: a runtime body that does not exist, the two
string arguments converted to `double`, and the LAST/ANYCASE phrases dropped.

## The rule

§15.37.3 r1: "Argument-1 shall be a data item or literal of class alphabetic, alphanumeric, or national"
(`OK §15.37.3 1)`) — the function has no binary64 carrier at all; its only numeric argument is argument-3, an
integer (§15.37.3 r3, `OK §15.37.3 3)`), and a floating-point item at an integer position is either admitted by
§15.3 type 6 (PB248's screen decides) or rejected there — never a reason to move the whole call to the float lane.

## The mechanism

`src/Cobol.Net.Compiler/CodeGen/Emit/IntrinsicRenderer.cs`, `RenderNum` (`:159` on main after train 5):
`if (AnyRealArgument(ic) && sig.RuntimeMethod != "Factorial") return RenderFloat(...)`. The predicate asks "is ANY
argument floating" where the question is "is any argument IN A NUMERIC-CARRIER POSITION floating". Every function
whose catalog row mixes string-class positions with a trailing integer is exposed: FIND-STRING, SUBSTITUTE, CONVERT,
BASE-CONVERT, STANDARD-COMPARE — unswept, and `Factorial` is already a hand-written exception to the same predicate,
the shape [[one_rule_one_place]] warns about.

## Fix shape

Derive the predicate from the catalog: `AnyRealArgument` over the positions whose declared argument class is
numeric (the `IntrinsicCatalog` row already names each position's class — PB248's screen reads it), so a
string-position argument can never trip it and the `Factorial` exception disappears into the same derivation
(FACTORIAL's one position is an integer whose float form the screen rejects). Drift test: for every catalog row
with a string-class position, a program passing a FLOAT-LONG in its trailing integer position compiles to a call
of the row's own runtime method (or is rejected by PB248's screen with COBOLNET1627), never to a `...Real` name;
the emitted C# is the assertion, as in PB253's `StandardModeReturnedValueContainerDriftTests`. Goldens: FIND-STRING,
SUBSTITUTE and BASE-CONVERT with a float trailing argument at 2023 — positive where §15.3 type 6 admits the value
(an integral float, e.g. 2.0E0), negative where it does not.

## Landed 2026-09-05 (worktree `agent-a4746f1d6ac9931a9`, base `68c2836e`)

**Reproduced, but only under `--permissive`** — and the note's own repro line did not say so.
**The harm flags are corrected with this landing:** because PB248 rightly refuses this source under
strict, `rejects_legal_source` is FALSE — no conforming program was ever rejected. What the defect
did is CRASH the compiler (`crashes: true`) on the `--permissive` migration lane, which is the lane
these bodies live in and the only lane the call reaches the renderer from. PB248's §15.3
type-6 screen landed in train 5 and REJECTS a floating-point item at an integer position under strict
(COBOLNET1627), so `probe1.cob --std 2023` never reaches the renderer; `--permissive` warns, binds, and then
`error CS0117: 'CobolIntrinsics' does not contain a definition for 'FindStringReal'`.

**The mechanism, and the note's fix shape corrected.** The note proposed asking `AnyRealArgument` "over the
positions whose declared argument class is numeric". That does not fix its own repro: FIND-STRING's argument-3
IS a numeric position (§15.3 type 6), so the predicate would still have been true and the call would still have
moved WHOLE to the float lane. The real fault is that entering the lane is a fact about the ARGUMENT RUN —
`RenderFloat`'s body converts EVERY argument through one binary64 conversion — so the precondition is that every
position have a binary64 value at all. `IntrinsicArgumentRules.ArgumentRunIsAllNumeric(name, argCount)` derives
it from the SPEC-VERIFIED `Verified` schema (`Admissible(kind) is [CobolClass.Numeric]` — §15.3 types 6 and 10)
and fails OPEN on an unscreened function, an undeclared position and the `'p'` negative-list kind, so it can only
ever take a call OUT of the lane on a cited rule.

⚠ **It is a question about the POSITION, and asking the OPERAND's class would have been wrong.** Under
`--permissive` the DA6 leniency admits an alphanumeric operand at a numeric position and digit-decodes it, so
`FUNCTION MOD(<PIC X item> <COMP-2>)` has a non-numeric OPERAND at a numeric POSITION and must keep the float
lane; reading the operand would have routed it to the exact `Int128` arm and reopened PB2's CS1503.

**The Factorial exception did NOT disappear** — the note predicted it would, on the premise that "FACTORIAL's one
position is an integer whose float form the screen rejects", which is true under strict only. It is a CODOMAIN
exclusion (33! is ~8.7e36; no `FromDouble` tail carries it), not an argument-class one, so it survives as the
declared set `IntrinsicRenderer.FloatLaneExempt` with its citation attached, read by
`IntrinsicRealArgDriftTests` and constrained by
`IntrinsicFloatLaneArgumentRunDriftTests.EveryFloatLaneExemption_IsACodomainExemption`.

**The sweep found TEN functions, not the five the note named.** The note listed FIND-STRING, SUBSTITUTE, CONVERT,
BASE-CONVERT and STANDARD-COMPARE. The last four are ALPHANUMERIC-result rows, so `RenderNum`'s first arm sends
them to `RenderString` and they never see the float dispatch — they were never exposed. The real population is
every NUMERIC/INTEGER-result row with a non-numeric §15.3 position, measured by neutering the new precondition
and reading the drift test's failure branch: FIND-STRING, ORD, INTEGER-OF-BOOLEAN, NUMVAL-F, TEST-NUMVAL,
TEST-NUMVAL-C, TEST-NUMVAL-F, INTEGER-OF-FORMATTED-DATE, SECONDS-FROM-FORMATTED-TIME, TEST-FORMATTED-DATETIME —
ten CS0117s, each on `--permissive` source.

**Why nothing saw them.** `IntrinsicRealArgDriftTests` exempted the `'s'` and `'b'` kinds outright, reasoning that
"those reject a float at bind time, so no `…Real` body can be reached" — a STRICT-only premise;
`CheckArgumentClasses` warns and binds under `--permissive`. FIND-STRING was excluded a second way, by a
hand-written `.Where(m => !m.EndsWith("String"))` with no reason attached, which removed exactly one method:
`FindString`. Both filters are now the derived `ArgumentRunIsAllNumeric`, so the guard and the compiler cannot
disagree about who is in the set.

**Verification.** New `IntrinsicFloatLaneArgumentRunDriftTests` — population derived from the schema, probe is the
emitted C#, failure branch fired on all ten; `FloatIntegerArgumentPermissiveTests.Pb635FindString_*` (the four
LAST × ANYCASE combinations over ONE float argument-3 answering 10/4/4/7, plus the fixed-point control at 7 —
§15.37.4 r1/r2/r4) and its strict-rejection sibling; negative golden `pb635-find-string-float-skip`.
