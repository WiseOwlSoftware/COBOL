# PB363 — the predicate is already written, four methods short of its callers

**Rows:** `SR-14.9.49.3-10`, `SR-14.9.49.3-11`.

## The programs

`<lane3 scratch>/out-b1/probe/sr9-11/`, both derived from `tests/conformance/2002/rw_suppress.cob` (whose RD
declares `CONTROL IS WS-GRP`):

* `sr10.cob` replaces the USE BEFORE REPORTING paragraph body with
  `TERMINATE R-SUP. INITIATE R-SUP. GENERATE DET-A.` → compiles at `--std 2023` with **zero diagnostics**.
* `sr11.cob` replaces it with `MOVE 9 TO WS-GRP. ADD 1 TO WS-GRP.` (WS-GRP is the report's control data item) →
  compiles with **zero diagnostics**.

## The rules

> SR10: The GENERATE, INITIATE, or TERMINATE statements shall not appear in a paragraph within a USE BEFORE
> REPORTING procedure.

> SR11: A USE BEFORE REPORTING procedure shall not alter the value of any control data item.

Both `--check 14.9.49.3` → **OK**; §4.2.2 requires the compile-time indication. `docs/CONFORMANCE.md` §5 lists
A.4.11 Report Writer as **Partial** with the RW nucleus and USE BEFORE REPORTING implemented, so these rules are
in CLAIMED scope, not declined-module debt.

## What the compiler does — and what it already has

`ReportWriterBinder.BindGenerate`, `BindInitiate` and `BindTerminate` each validate their own operand against
§14.9.16 / §14.9.21 / §14.9.46 and **never ask where they are being bound**.

Yet the SAME FILE's `BindSuppress` already computes exactly the predicate SR10 needs, for §14.9.45.3 SR1:

```csharp
ctx.Table.Declaratives.FirstOrDefault(d => d.ReportGroup is not null
    && ctx.BindCursor >= d.StartPc && ctx.BindCursor <= d.EndPc)
```

rejecting a misplaced SUPPRESS with COBOLNET1581. SR10 is the CONVERSE of that same expression, and SR11 needs it
plus a store-target test — for which `ReportModel.Controls` (`DataBinder.Reports.cs`) and
`Binding/Bound/BoundStores.cs`'s `StoreKind` visitor are already present.

## The fix shape

Rather than pasting the expression a fourth time, lift it to a named helper on the bind context — *the Format-2
declarative enclosing the bind cursor, or null* — and have `BindSuppress`, `BindGenerate`, `BindInitiate`,
`BindTerminate` and the SR11 walk all read it. One rule in one place, so the next Report-Writer verb inherits the
restriction instead of forgetting it. **`SR10`'s runtime twin is §14.9.49.4 GR10 (PB326), which is the same
question asked of a GENERATE reached at run time through a PERFORM rather than written in the paragraph** — the
two together are the whole of the before-reporting range restriction, and they should land as one.

**Code sites:** `ReportWriterBinder.cs#BindGenerate` (line 73), `#BindInitiate` (line 59), `#BindTerminate`
(line 96) — the missing checks; `#BindSuppress` (line 115) — the existing mechanism.
