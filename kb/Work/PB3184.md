# PB3184 — Linux-gate reds are invisible to the next Windows gate's tier-0a

Source: lead 2 (second half) of `w1080g-PB3165-report.md` ("## Finisher"), filed by the enqueue unit 2026-10-15.
Grepped `kb/Work/` for `previous red`: PB1529, PB1953, PB2515 and PB3022 item 8 describe previous reds going to leg 1
(tier 0a) from the worktree's own previous run; none covers a red that only the Linux gate saw. PB3022 item 10 (the
targeted leg on both hosts, still open) would make Linux run leg 1 inside the one gate and shrink this, but it does not
change where `read_previous_run` looks, so this stays its own note.

## What happens

`scripts/run_gate_legs.py:360` (`plan`) takes REDS only from this worktree's own previous build-local run
(`gate_plan.read_previous_run(previous)`; the source comment says "REDS only ever from this worktree's own previous
run"). When the landing's Linux gate (`linux-gate.sh`, the enqueue's CI-Linux legs) fails a case, that red lives in
`TestResults/linux-gate/` and never enters the next Windows gate's tier 0a. The finisher's re-gate therefore plans the
failing case by the ordinary tier rules, and it can be left in leg 2 (not run) while the verdict reads GREEN.

## Instance

PB3165 (2026-10-15): the Linux unit leg failed
`CapacityRegisterReferenceDriftTests.TheCapacityRegisterNameLookup_IsWrittenInExactlyOnePlace`. The finisher's Windows
re-gate (run 20261015T175907Z-b45c0c) did not run it ("NOT RUN there"); the finisher re-ran the red leg by hand under
WSL. Together with PB3112 (the sample that kept it out of leg 1) the case was invisible to the local gate twice.

## Fix direction

One reader of "previous reds" that also takes the reds named by the landing's Linux gate record for the same branch
(its `unit.trx` / `characterization.trx` / `conformance.trx`), plus a self-test: a Linux-only red recorded for the
branch lands in tier 0a of the next plan. Take it with PB3022 item 10 so the two hosts share one reds source.

## Site

`scripts/run_gate_legs.py:360`; `scripts/gate_plan.py` `read_previous_run`; `scripts/linux-gate.sh` (its result
files).

**Sites:** the same as PB3155's (`scripts/gate_plan.py`, `scripts/run_gate_legs.py`).

## Landed with PB3155 (wave 20261026, group C2)

The same mechanism as PB3155, fixed once there: `gate_plan.previous_gates` is the one reader of a worktree's previous
gates, and it reads the Linux gate's newest run (`TestResults/linux-gate/*.trx`) beside build-local's previous run, so a
Linux-only red is tier 0a of the next Windows gate. PB3155's "Landed" section carries the probe, the fix and the tests.
