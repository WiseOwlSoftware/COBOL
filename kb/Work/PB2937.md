# PB2937 — a parameterized skeleton's procedure statements and bound-arm edition gates are never asked

**Found:** wave 1053 group A (PB1941 + PB2051), report `E:\COBOL-coord\scratch\reports\w1053a-PB1941-report.md`,
"New defects" 1 and 3 (one root), filed by the train 1053 lander.

**The defect.** PB2051 made a parameterized class or interface definition bind as itself for its environment and data
divisions and its method headers (`OoDriver.BindParameterized`), so the definition rules and every data-description
rule reach an unexpanded skeleton. Two arms stayed out:

1. **Procedure statements.** `BindParameterized(OoClassSymbol)` calls `BindClassData` only; no `BindClassBody` runs on a
   skeleton, so a statement-level violation in a skeleton method (a MOVE between incompatible categories, an undeclared
   data-name) is reported only when some program expands the definition, and never when none does. Harm: silent
   under-reject of nonconforming source. The OO deep-dive records the boundary as D12 determination 6.
2. **Bound-arm edition gates.** `VersionConformancePass` walks the table's classes only: `BinderDriver.cs` builds
   `GroupBindContext(tree, units, classes, oo.InterfaceData, session)` (about line 179) from the emitted classes, not
   the skeleton units, so a bound-arm edition gate never sees a skeleton's data (the parse-arm gates still fire).

**Why it was not done in PB2051.** A skeleton's formals stand where an object-class-name or interface-name is
permitted (§11.3.4 GR6, §11.6.4 GR4), and binding statements needs a description kind for them: the implementer
measured a body-bind experiment in which a universal stand-in for a formal is too strict (a literal INVOKE argument,
`SUPER` over a formal base). The shape is an `ObjectRefKind.Formal` (61 `ObjectRefKind.` sites) plus arms in
`OoBinder.OoPredefinedSearchRoot` (SUPER / `X OF SUPER` over a formal base) and the INVOKE class-name receiver
(`OoBinder.cs` about line 402).

**Repro.** `E:\COBOL-coord\scratch\w1053a\p\legal.cob` (formals in every data and header position, exit 0) with one
nonconforming MOVE added to a skeleton method: compiles with exit 0 at `--std 2023`; the same MOVE in an ordinary class
is rejected.

**Code sites.** `src/Cobol.Net.Compiler/Oo/OoDriver.cs` `BindParameterized` (about line 47; `BindClassBody` about line
161); `src/Cobol.Net.Compiler/Binding/BinderDriver.cs` (the `GroupBindContext` construction, about line 179);
`src/Cobol.Net.Compiler/Oo/OoBinder.cs` (about line 402).

**What closes it.** A formal description kind, then the skeleton's statements bound as the table's classes are (result
dropped, as `BindParameterized` drops its data bind), and the edition pass given the skeleton units; a negative golden
per arm (a statement violation and an edition violation inside an unexpanded skeleton) and the existing expansions
unchanged. PB1784's `OoDefinitionRules` decomposition shares the root (every rule asked of every definition kind).

**Rule:** §9.3.8.2.4 (a parameterized class is used "as if the actual parameter classes or interfaces were
substituted"), §12.3.8.4 GR5; the rules a statement violates are the statements' own.

## Progress — wave 1071 group E (arm 2 landed; arm 1 OPEN)

**Arm 2 (bound-arm edition gates) — fixed.** Re-probe on 77f10dfb2: an unexpanded `CLASS-ID. EDSK USING T.` with
`01 Y USAGE FLOAT-BINARY-64.` in its OBJECT data compiled clean at `--std 2002`; the same entry in a plain class is

`conformance:negative/pb2937-skeleton-data-edition-gate`, `conformance:negative/pb2937-interface-formal-edition-gate`.

## Landed (wave 1072 group B) — arm 1

**Re-probe on 2da05a28a + w1071e.** `w1071e/oo/ed.cob` at `--std 2023` compiled clean: the skeleton's `MOVE C TO
UNDECLARED-NAME` and `MOVE ALL "12" TO N` were never asked. After: COBOL1639 and COBOL0902, as in a plain class.
`w1053a/p/legal.cob` is NOT legal: an expansion of it (`w1072b/p/exp.cob`, `CLASS LGX EXPANDS LGHOLD USING BB EE IF1`)
refuses line 58 `SET ONE TO X` (SR12 a)1.: an ONLY receiver takes only an ONLY sender) and line 60 `SET ITEM TO ANY1`
(a universal sender into a typed receiver) in EVERY expansion, so the skeleton now refuses exactly those two and
nothing else; the five false refusals the universal stand-in drew (lines 37, 68, 69, 70, 72) are gone.

**Fix shape (D12 determination 6 rewritten).** `ObjectRefDescriptor.Formal` is an AXIS of the object-class-name /
interface-name alternative (§11.3.4 GR6), not a fifth kind. Rule: a question that turns on WHICH class the formal names
is the expansion's; every other one is the skeleton's. (a) SET-style pairs ask the runtime table with the formal side
standing for the most favourable actual (`OoClassTable.SetOperands`); (b) identical descriptions admit a pair differing
only in a name a formal may take (`ObjectRefDescriptor.TurnsOnFormal`); (c) a statement that selects a method through a
formal binds its operands' own rules and is then `BoundDeferredToExpansion`, through the new expansion-deferral ledger
(`EditionContext.NoteExpansionDeferred`, kept by `StatementBinder.BindStatement`). The skeleton symbol records its
written superclass (`Base`, so SUPER binds) or its formal one (`FormalBaseName`). `BinderDriver.Bind` binds every
skeleton body after the emitted classes; `VersionConformancePass` walks them.

**Siblings found and fixed.** `IntrinsicBinder.KeywordOmittedFunction` read a CLASS-NAME spelled like a zero-argument
intrinsic as the function (`INVOKE PI "NEW"` with `CLASS PI` drew COBOL1543; a formal `E` the same); it now yields
to a class, interface or formal name in scope (§8.3.2.1). The golden `2002/pb2051_parameterized_definition_binds_itself`
carried the same illegal `SET LEFT-ONE TO L` (ONLY from not ONLY); L is now `A ONLY`.

**Goldens.** `conformance:2002/pb2937_skeleton_bodies_bind_as_themselves` (every deferred position, a written superclass,
the PI class; prints PI-OK / PB2937-OK), `conformance:negative/pb2937-skeleton-statement-rule` (COBOL1639),
`conformance:negative/pb2937-skeleton-only-receiver` (COBOL0867),
`conformance:negative/pb2937-skeleton-nested-edition-gate` (COBOL0902).

**Branch review round 1 (wave 1072 review finisher).** Two findings, one funnel (`StatementBinder.BindStatement`).
R1-1: a compound statement (IF, EVALUATE, inline PERFORM) around a statement whose object property was deferred drew a
false COBOL2362, because the nested refusal node (the deferral's shadow) stayed on the refusal ledger after the nested
funnel took the deferral. The refusal ledger is now TAKEN per statement like the unbuilt and deferral ledgers
(`EditionContext.TakeRefusalsSince`). R1-2: a deferral in a compound statement's OWN operands (an IF condition through
a formal) replaced the whole statement, so its branches vanished from the edition pass (`IF ITEM :: "SZ" = 1 MOVE ALL
"12" TO CNT2 END-IF` compiled clean). `BoundDeferredToExpansion` now keeps what the verb binder built (`Bound`), and the
generated `StatementChildren` walk reaches the branches. Repros `w1072b/r/*.cob` (`gen.py`, `run.sh`).
