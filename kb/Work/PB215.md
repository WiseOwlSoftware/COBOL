# PB215

Found while landing the PB169-PB172 burn-down cluster (2026-08-31), by a MEASURED over-reach rather than by
reading: the cluster's first attempt derived index-data-item admissibility from the §8.8.1.1 class screen
("class index is not class numeric"), and eight NIST programs went red on `SET IN1 TO IDN1` -- IC106A, IC107A,
IC207A, IC208A, NC131A, NC133A, NC135A, NC236A. Every one is a SET statement, which §13.18.60.3 SR10 names
outright.

**THE TWO LISTS ARE DIFFERENT, AND THAT IS THE DEFECT.** Both were cite.py-checked:

  * §13.18.38.3 r7 (index-NAME): "as a subscript; in the VARYING phrase of a PERFORM statement; in the VARYING
    phrase of a SEARCH statement; in the SET statement; as an operand in a relation condition."
  * §13.18.60.3 SR10 (index DATA ITEM): "a SEARCH or SET statement, a relation condition, an intrinsic function
    argument, an inline method invocation argument, the USING phrase of a procedure division header, or the
    USING phrase of a CALL or INVOKE statement."

A SUBSCRIPT and PERFORM VARYING are on r7's list and NOT on SR10's. An intrinsic argument and a CALL USING
phrase are on SR10's and not on r7's. `OperandContext.ArithmeticIndexWindow` was built to name r7's list, and
it therefore CANNOT express SR10's -- so the third axis added by the cluster (`IndexDataItemAdmitted`) is set
`true` for the whole window, which keeps SET/SEARCH/relation correct and leaves these residual sites admitting
an index data item the standard does not list there:

  * `PERFORM VARYING V FROM <index data item>` / `BY <index data item>` (ControlFlowBinder.cs:398/403)
  * the Report Writer's `VARYING` FROM/BY (ReportWriterBinder.cs:48-49)
  * a COMPOUND subscript segment that actually REACHES the D18 materializer. ⚠ CORRECTED 2026-08-31 (cluster-B
    review): the bullet's original exemplar `E(IDX + 1)` was WRONG and would have sent a fixer to a shape that
    is already closed. `+` is renderable, so that segment stays on the token-renderer fast path and each name
    goes through `ResolveSubscriptName` → `ScreenPositionOperandClass`, which rejects class INDEX — measured:
    COBOLNET0844 under strict. The residual is the segments the fast path HANDS OFF, and three of the five
    hand-off exits are ORDER-DEPENDENT (the renderer walks tokens left to right, so a name reached BEFORE the
    exit is screened on the fast path and the residual does not arise): only the depth-0 slash pre-check and
    `IsFunctionBearing` pre-empt the screen unconditionally. The real exemplars are `E(IDX / 1)` and
    `E(FUNCTION INTEGER(IDX))`; `E(2 ** IDX)` reaches the exit only because `IDX` follows the `**`.

**AXIS B HAS A RESIDUAL TOO, AND IT WAS UNREGISTERED** (added 2026-08-31; the note was written entirely about
§13.18.60.3 SR10 and the index DATA item). The SAME `ArithmeticIndexWindow` row
(`src/Cobol.Net.Compiler/Binding/Procedure/ExpressionBinder.cs:127` — `=> (true, false, true)`) also sets
`IndexNameScreen = false`, which exempts the index-NAME screen at the Report Writer's VARYING. §13.18.38.3 r7
(cite.py OK) names "the VARYING phrase of a PERFORM statement" and "the VARYING phrase of a SEARCH statement" —
the Report Writer's VARYING (§13.18.64) is NOT on the list. MEASURED 2026-08-31, not deduced: a report group
with `05 COLUMN 1 5 9 PIC 9 SOURCE IS RV-A VARYING RV-A FROM IXR BY 1`, `IXR` an `INDEXED BY` index-name,
compiles CLEAN at `--std 2023` strict (rc=0, no COBOLNET1637). Same cause as the axis-C residuals: one enum
member serves sites the two rules list differently. Closing it needs the same split.

⚠ This is the PRE-EXISTING behaviour, not a regression: before the cluster, `ExpressionBinder`'s private
operand-class switch had no index arm at all, so an index data item was admitted in EVERY arithmetic position
(that hole is [[PB213]], closed). The cluster closed it wherever a context could answer; these three sites are
what one enum member cannot separate.

WHAT WOULD CLOSE IT: give the r7 window its SR10 split -- a second member for the sites r7 lists and SR10 does
not (subscript, PERFORM VARYING) and a THIRD for the site NEITHER lists (the Report Writer's VARYING, which is
on no clause's list and therefore needs both screens on) -- with all THREE clause lists written into
`OperandContextRules.Rules()` so the difference is declared rather than inferred, and a negative fixture per
residual site. ⛔ Measure each site before flipping it: the over-reach above is what happens when a context list
is derived instead of read, and the SIMPLE subscript is already screened correctly in `ReferenceResolver`
(SR10's silence on subscripts is enforced there), so only the COMPOUND segment needs the new member on axis C.
`OperandContextRulesTests.TheThreeAxes_AreWhatTheClausesSay` now enumerates `Enum.GetValues`, so a new member
cannot be added without its three axes being read off the standard (kb/Work PB224).

## Landed — 2026-09-22 (wave 52)

RE-PROBED first on the worktree's own build (all four residuals reproduced): `PERFORM VARYING V FROM IDX BY IDX`
ran V=02/04/06; `E(IDX / 1)` read occurrence 2; RW `VARYING K FROM IXR` and `FROM IDX` both printed `2  3  4`.
⚠ The note's `E(FUNCTION INTEGER(IDX))` exemplar is NOT a residual: the argument binds under FunctionArgument
(SR10 lists "an intrinsic function argument") and INTEGER's own class rule rejects it (COBOLNET1627).

THE SPLIT. `OperandContext` now has two index rows, each read off the clauses: `ArithmeticIndexWindow` (SET ·
SEARCH · relation — on r7's AND SR10's lists; index-name exempt, index data item admitted) and the new
`ArithmeticIndexNameWindow` (subscript segment · PERFORM VARYING FROM/BY — r7's list only; index data item takes
§8.8.1.1's class screen, COBOLNET0844). The Report Writer's VARYING (§13.18.64.2, plain arithmetic expressions)
is on NEITHER list and binds through `BindExpr` — its row IS `Arithmetic`'s, so it needs no member.

THE OTHER ARM. The PERFORM VARYING/AFTER induction variable was resolved through SET's receiver, which applies no
class screen by design, so `PERFORM VARYING IDX …` varied an index data item silently and a PIC X induction
variable compiled clean and died at run time. It now takes the ONE receiving-side screen
(`ExpressionBinder.ScreenResultant`) under §14.9.28.3 SR2 — COBOLNET1675.

**Train 52 composition (lander).** PB212 (cluster DB) landed the SAME arm in the same train as a row of the ONE
operand-class screen (`OperandPositions.PerformVaryingIdentifier`, COBOLNET2120, §14.9.28.3 SR2). The two arms
conflicted at one line of `ControlFlowBinder.PerformVarying.cs`; the lander kept the operand-class screen (it also
serves SR5 a) through `PerformVaryingIdentifierFromIndex`) and dropped the `ScreenResultant` call, so the
varied identifier draws COBOLNET2120, not COBOLNET1675: the two `negative/pb215-perform-varying-target-*` goldens
expect COBOLNET2120 and COBOLNET1675's description no longer names PERFORM VARYING.
