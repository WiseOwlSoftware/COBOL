# PB5187 - at --std 85 a numeric item with P scaling compared with a nonnumeric operand compares the scaled digit image (1200 for PIC 99PP) where 1985 compares an alphanumeric item of the item's size (12)

**Sites:**

- `src/WiseOwl.Cobol.Compiler/CodeGen/Emit/ConditionRenderer.cs` (`RenderRelationalCore`, `ComparisonText`)
- `src/WiseOwl.Cobol.Compiler/CodeGen/Emit/OperandText.cs` (`AsString`, `AsItemSizeTemporary`)

**Mechanism.** §1985:VI.6.3.1.1.2 GR1 compares a numeric operand with a nonnumeric one as though it were moved to an alphanumeric item "of the same size as the numeric data item (in terms of standard data format characters)". `ConditionRenderer.RenderRelationalCore` renders the numeric operand through `OperandText.AsString(deSign: true)`, the digit image with the P positions as zeros, at every edition; for PIC 99PP holding 1200 that image is 1200, four characters, where the item's size is two characters, so the relation compares 1200 at --std 85 while MOVE PP TO a two-character item and a compare of that item gives 12. kb/Work PB5106 (landed) is the group-operand sibling.

**Found by.** The 1985 code read (2026-11-10; its records are `E:/COBOL-coord/scratch/coderead-85/for-register.json`): each rule below was read against the code sites it names and probed at `--std 85`, and found non-conforming. Verdict, harm, evidence, repro and observed text are the records'; the rows' verdicts are recorded on another branch.

**Inventory.** `work.py check` refuses a 1985 rule id in `inventory_rows` (kb/Work PB5094, open), so `inventory_rows` is empty and the rows this note claims are the rule ids of the list below.

- `1985-GR-VI.6.3.1.1.2-1` - `§1985:VI.6.3.1.1.2 GR1` (record verdict: PARTIAL, harm: wrong-answer). Checked: §1985:VI.6.3.1.1.2 GR1: "the numeric operand is treated as though it were moved to an elementary alphanumeric data item of the same size as the numeric data item (in terms of standard data format characters), and the content of this alphanumeric data item were then compared to the nonnumeric operand". Code sites read: src/WiseOwl.Cobol.Compiler/CodeGen/Emit/ConditionRenderer.cs#RenderRelationalCore; src/WiseOwl.Cobol.Compiler/CodeGen/Emit/OperandText.cs#AsString; src/WiseOwl.Cobol.Compiler/CodeGen/Emit/OperandText.cs#FieldAsString; src/WiseOwl.Cobol.Compiler/Binding/RelationComparability.cs#Breach; src/WiseOwl.Cobol.Compiler/Binding/Validation/StatementValidation.cs#CheckGeneralRelationComparability. Code read: No kb/Work note owns the fix (PB5106 owns the group sibling, §1985:VI.6.3.1.1.2 GR2, and names no site). §1985:VI.6.3.1.1.2 GR1: "the numeric operand is treated as though it were moved to an elementary alphanumeric data item of the same size as the numeric data item (in terms of standard data format characters), and the content of this alphanumeric data item were then compared to the nonnumeric operand". RenderRelationalCore implements it, for every edition alike, as CobolString.Compare over OperandText.AsString(operand, deSign: true): the numeric operand's unsigned digit image, one character per digit position, compared under the program collating sequence with space extension of the shorter operand. That equals the 1985 result for an unsigned item, for an item with an embedded sign and for a SIGN SEPARATE item (the 1985 temporary is one character longer, a trailing space the shorter-operand extension supplies anyway), and a numeric literal compares as its digits. Probed at --std 85: 9(3) value 7 equals X(3) "007" and X(5) "007"; S9(3) value -7, embedded and TRAILING SEPARATE, equals "007" and "007 "; "007" = 007 is true and "007" = 7 is false; 9(3) > "006" is true. What is NOT implemented is the 1985 size of the temporary for a scaled integer: there is no edition arm. §1985:VI.5.9.4 GR8: "The scaling position character 'P' is not counted in the size of the data item", so a PIC 99PP item is 2 standard data format characters and the temporary is 2 characters long, while the move sends the four digits 1200 (§1985:VI.6.19.4 GR4: "all digit positions specified with this symbol are considered to have the value zero and are counted in the size of the sending operand"), which the alphanumeric receiver truncates on the right to "12". The compiler compares the four-character "1200", the 2023 temporary ("the same length in terms of character positions as the number of digits in the integer"), at 85 too. The row's change record names exactly this case as the 1985/2023 difference. The witness compares 9(3) and S9(3) SIGN LEADING SEPARATE items with literals and an X(4) item; it has no scaled operand.

**Repro (`1985-GR-VI.6.3.1.1.2-1`).** `cobol.exe rel2.cob --std 85 --source-format fixed --run`

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. REL2.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  PP  PIC 99PP VALUE 1200.
       01  T2  PIC XX.
       01  T4  PIC X(4).
       PROCEDURE DIVISION.
       P1.
           MOVE PP TO T2.

           ELSE

               DISPLAY "EQUAL 1200"
           ELSE
               DISPLAY "NOT EQUAL 1200".

           STOP RUN.
```

**Expected (from the 1985 text, the record's).** MOVE TO XX=[12] MOVE TO X(4)=[1200] / EQUAL 12 / NOT EQUAL 1200 / T2 EQUAL 12. §1985:VI.6.3.1.1.2 GR1: "the numeric operand is treated as though it were moved to an elementary alphanumeric data item of the same size as the numeric data item (in terms of standard data format characters)"; PP is 2 standard data format characters (§1985:VI.5.9.4 GR8: "The scaling position character 'P' is not counted in the size of the data item"), so the comparison is the one T2 = "12" makes after MOVE PP TO T2, and "12" against "1200" is unequal ("the shorter operand were extended on the right by sufficient spaces").

**Observed (the record's).** exit 0: MOVE TO XX=[12] MOVE TO X(4)=[1200] / NOT EQUAL 12 / EQUAL 1200 / T2 EQUAL 12. The relation compares the four-digit image 1200 at --std 85 (the same output as --std 2023); the compiler's own MOVE PP TO T2 followed by T2 = "12" is true.

**Fix direction (root cause, CLAUDE.md rule 4).** Render the numeric operand of a mixed comparison at the item's size in standard data format characters (the P positions are not characters of the item) at the editions whose rule says so, in AsString's one caller for relations.
