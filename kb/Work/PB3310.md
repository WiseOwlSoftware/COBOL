# PB3310 — concurrent landings of one branch share the Linux gate's snapshot

## Found (operator c95c0b86, 2026-10-16 16:57 PDT, on a Mythos report)
Mythos reported: "Gate slot 1 held 7 h by a hung Linux gate (pid 311180, notes-leads-enqueue-20261016d)". Measured:
- The Windows process chain was `nohup` (301328, 10:00:26) → `enqueue.py land notes-leads-enqueue-20261016d --lane clerk`
  (328496, 10:00:26) → `gate_slot.py run … -- bash scripts/linux-gate.sh --nice` (311180, 10:06:24) → `bash` (315108,
  10:15:30) → WSL.
- The branch was ALREADY ON MAIN. It had merged as pull request #127 at 10:34 PDT (8c38c297c), through another

- Inside WSL, the stuck run's Unit leg `dotnet test …Cobol.Net.Tests.Unit.csproj` (326373) had no children and sat in
  `futex_do_wait` for 6 h 41 min. An orphaned `dotnet test tests/Cobol.Net.Tests.Conformance --no-build --list-tests
  --filter FullyQualifiedName~AcceptDifferentialTests` (500468, reparented to init) was in `futex_do_wait` for 6 h 35 min.
  Both processes' working directories read `/home/brent/linux-gate/notes-leads-enqueue-20261016d/… (deleted)`.
  Evidence file: `E:\COBOL-coord\scratch\evidence-hung-linux-gate-20261016d.txt`.
- The operator stopped the Windows tree (taskkill /T on 328496 after re-reading its command line), and the WSL

## The mechanism
1. **No per-branch exclusion in `scripts/orchestrator/enqueue.py#land`.** The landing lane (`land_lane.py`) records the
   attempts it starts itself (one pid per branch). A unit that runs `enqueue.py land` by hand, here through `nohup`,
   is not one of those attempts, so two runs on one branch can proceed together. They race on the worktree (merge,
   DEVLOG stamp, push) and on everything the gates write.
2. **`scripts/linux-gate.sh` lines 199–201** key per-run state on the tree alone:
   `out="$tree/TestResults/linux-gate"; rm -rf "$out"` and `snap="$HOME/linux-gate/$(basename "$tree")"; rm -rf "$snap"`.
   The second run deletes the first run's WSL clone, and its logs, while the first is still testing in them. A `dotnet
   test` whose working tree vanished then deadlocks instead of failing.
3. **No ceiling.** `gate_slot.py` lets a slot be held forever, and nothing surfaces a slot held far past its leg's
   measured wall: about 6 minutes for the Linux gate, here 6 h 40 min. The owner's peer session noticed it, not a
   tool.

## Fix shape (one change; PB3194 is the same snapshot lifecycle and lands with it)
- `enqueue.py land` takes an exclusive per-branch lock (in the coord dir, holding the pid and start time) and refuses
  a second run with its own outcome line, `=== ENQUEUE: REFUSED (another land of <branch> runs: pid …) ===`. A lock
  whose pid is dead is taken over.
- `linux-gate.sh` gives each run its own snapshot and log directory, keyed on the run (for example
  `<tree basename>-<run id>`), and removes that snapshot on exit (`trap`). This also answers PB3194's leak.
- `gate_slot.py status` and session-probe flag a slot held longer than N times its leg's measured wall, with N
  derived from the gate's own timing records rather than a fixed limit. The flag is surfaced only, never a kill:
  the decision stays with the operator (feedback: verify the pid before a kill).
- Drift test: two concurrent `linux-gate.sh` dry runs on one tree get distinct snapshot paths, and a second
  `enqueue.py land` on a locked branch prints the REFUSED line.

## Landed (wave 20261030, group E)
Re-probe on a current tree: the snapshot half (mechanism 2) was already fixed by PB3194, whose gate directory is keyed by
the run's pid and removed on every exit path; the NOT RUN-as-red half (the 2026-10-22 witness) by PB3527 (exit 12 BUSY).
What remained, and is now fixed at its root:
1. **`enqueue.py land` takes a per-worktree land lock** (`<git dir>/cobol-land.lock`, `gate_slot.ExclusiveLock`, an OS
   lock freed when its holder dies, so a dead run is "taken over" with no pid bookkeeping) before it first reads the
   worktree. A second run ends `=== ENQUEUE: REFUSED — another land of <branch> runs (<holder>) ===`, **exit 13**, with
   nothing touched, no report line and no finisher; the landing lane waits on the same lock (`WAITS`, `wait_free`). The
   lock is per worktree rather than a file in the coord dir: a branch is checked out in exactly one worktree, and the
   lane already locates the gate lock that way.
2. **`linux-gate.sh` runs one gate per tree**: `begin_gate` checks, under an flock, for a RUNNING gate of the same tree
   and answers `=== LINUX GATE: BUSY — … ===` (exit 3, the driver's BUSY reading; enqueue.py reads it as exit 12) before
   it empties `TestResults/linux-gate`, which the first run was still writing (that directory is the planner's "newest
   run" contract, so it stays one per tree).
3. **`gate_slot.py status` flags a long hold**: each released hold's duration is recorded per kind in `holds.json`, and a
   held slot older than 5 times the median of its kind (at least 5 recorded) reads `LONG HOLD`; `session-probe.ps1`
   prints those lines. Surfaced, never a kill.
Self-tests: `gate_slot.py` arm 12, `enqueue.py` (the land-lock arm and the Linux BUSY reading), `land_lane.py` (exit 13),
`linux-gate.sh --self-test` (BUSY, another tree, an ended gate); drift: `LandingPipelineDriftTests`,
`GateSlotDriftTests`.
