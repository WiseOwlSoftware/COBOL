# PB838 — OPEN — the audits see quotations, and the failure mode is a claim with no quotation

Source: the `PB355` implementer report, "New defects" item 1; the same hole is named independently by the
`PB366` report (item b, a "RESOLVED" line in a deep-dive that paraphrases a clause) and the `PB492` report
(item A, `MoveEmitter`'s §14.9.25.4 "GR5"/"GR6c"). CLAUDE.md rule 1 names this exact failure mode — a citation
is INHERITED rather than invented.

## The hole, demonstrated

```
$ python scripts/spec/cite.py --check 13.4.2 "each of these record description entries is a description of the same storage area"
  FAIL: §13.4.2 exists but does NOT contain ...
$ python scripts/spec/cite.py --check 13.18.33.4 "Multiple level 1 entries subordinate to a FD or SD entry represent implicit redefinitions of the same area"
  OK  §13.18.33.4 3)  (General rules)
```

Nine code and doc sites asserted "multi-01 FDs share one area (ISO §13.4.2)" while **both audits sat at zero
findings**, because none of the nine carried a quotable fragment: each was a clause number followed by an
em-dash-introduced assertion. PB355 repaired those nine. What is not repaired is the audit.

## Known survivors, for the fixer's first pass

* `src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs` — "§14.9.25.4 GR5" for the editing path and "GR6c" for
  JUSTIFIED. GR5 is de-editing only (`cite.py --check 14.9.25.4 "De-editing takes place only when the sending
  operand is a numeric-edited data item"` -> `OK §14.9.25.4 5)`); the editing rule is GR6 and the alignment rule
  GR6 a). The same spellings recur in `AcceptDisplayEmitter`, `StringEmitter` and `PicInfo`.
* `src/CobolSharp.Compiler/Semantics/DataItemClassifier.cs:189` cites "ISO §13.18.63 GR10" for what is SR10
  (`cite.py --check 13.18.63.3 "If the category of the subject of the entry is boolean, literals in the VALUE
  clause shall be boolean literals."` -> `OK §13.18.63.3 10) (Syntax rules)`). Legacy oracle, slated for deletion
  at P15 — listed for completeness, not for urgency.

## Shape of the fix (structural, not a list)

`scripts/spec/audit_code_citations.py` and `audit_doc_citations.py` today answer "does this quotation appear in
this clause". They need a second question: "does this clause REFERENCE carry any `--check`able quotation at all
in its vicinity". A reference followed by an assertion and no quotation is a finding of its own class
(`UNQUOTED CLAIM`), reported separately from a wrong quotation so the two are not confused. Pair it with a
drift test that plants one unquoted claim and asserts the audit reports it — the gate must fail once before its
silence is evidence (`feedback_green_gates_arent_evidence`).

## Harm

`process_only` in the sense that no user program misbehaves — but this is the mechanism by which a wrong rule
reaches goldens and code, which is how PB355's nine sites and two CA10 citations happened. Severity MAJOR for
that reason.

  number and no quotation — PB366's report asks for exactly this measurement.

## A SECOND blindness of the same auditor, measured 2026-09-13 by REGISTRAR #5

From the `PB390` implementer report. This note's subject is a citation attached to a PARAPHRASE; the same
auditor is blind to a second shape, and that shape is live in SHIPPED DIAGNOSTIC TEXT — the one place a wrong
clause number reaches a user directly.

**A citation that omits the SUBCLASSIFYING subclause is invisible.** `audit_code_citations.py` keys on a
`§N.N.N.N` reference beside a quotable fragment. These three are in diagnostic strings a user reads:

```
src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SearchBinder.cs:29
    "SEARCH table '{tableName}' without INDEXED BY (ISO §14.9.37 SR1)"
src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ReportWriterBinder.cs:65
    "INITIATE '{...}' — not a report description entry (ISO §14.9.21 SR1)"
src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs:55
    "EVALUATE: more WHEN objects than subjects (ISO §14.9.13 SR)"
```

`§14.9.37` is the SEARCH statement's clause; its syntax rules are `§14.9.37.3`. `§14.9.13 SR` names no rule at
all. The audit reports zero findings on all three.

**And the first of them is WRONG, not merely unqualified:**

```
$ python scripts/spec/cite.py --check 14.9.37.3 "The data description of identifier-1 shall contain an OCCURS clause with an INDEXED phrase"
  OK  §14.9.37.3 2)  (Syntax rules)
$ python scripts/spec/cite.py --check 14.9.37.3 "Identifier-1 shall not be reference-modified."
  OK  §14.9.37.3 1)  (Syntax rules)
```

The message says SR1. SR1 is the reference-modification rule. The INDEXED-phrase rule is SR2. A user who looks
it up reads a rule about something else — which is exactly the harm this note is about, one step closer to the
user than a code comment.

**What the auditor should gain, stated as a rule rather than as three fixes:** any `§`-reference in a STRING
LITERAL that reaches `DiagnosticCatalog` or a `BoundUnsupported` message must resolve to a clause the citation
checker can address — i.e. it must carry the subclause, and the rule number it names must exist in that
subclause. That is mechanically decidable from the literal alone (the clause hierarchy is in
`specs/ISO_COBOL.md`), needs no quotable fragment, and it is the population with the highest cost per error.
`kb/Work/PB390` carries the eight sites and their correct rule numbers; this note carries the auditor.
