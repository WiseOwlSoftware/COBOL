# PB5907 - a literal zero factor times a numeric function or a floating-point item: refused under a standard arithmetic, admitted natively

Filed from the reviewer's round-5 lead of wave 20262097 group A (kb/Work PB5886). The reviewer's words, unchanged:

> **Summary.** The round-5 fail-closed DigitBound arms (BoundIntrinsicCall numeric -> NotBounded, BoundNumRef floating-point -> NotBounded) overflow at the leaf even under a literal zero factor, which CollectAdditive reads as the constant 0 (its k.Sign == 0 arm), so an argument whose value is the same integer under every arithmetic is refused under STANDARD-DECIMAL (and the 2002 STANDARD) and admitted natively: the ARITHMETIC clause changes a verdict that §2023:15.3 AR6 makes a property of the value, and the diagnostic blames 34 significant digits for a term multiplied by 0. Before this round the numeric call fell to the (0, cap) default and the argument was admitted.

> **Scenario.** N PIC 9(3) VALUE 2: COMPUTE R = FUNCTION MOD (0 * FUNCTION SQRT (N) + 5, 3) is refused COBOL1627 'whose intermediate FUNCTION SQRT (N) needs more than the 34 significant digits' exit 65 under ARITHMETIC IS STANDARD-DECIMAL at --std 2023 (run r5zsd-001), while the same program without the OPTIONS paragraph prints 0002 (run r5znat-001), both under E:/COBOL-coord/scratch/my-20261115/w20262097/review-w20262097-a/runs. The value is 5 for every valuation. The same holds for 0 * F + 5 over a COMP-2 F. A contrived shape: no printed value is wrong, legal source is refused only under a standard arithmetic.

> **Fix.** In DigitBound's BoundBinary arm, bound a product with a literal zero factor as (0, 0, null) before walking the other factor (CollectAdditive's zero-factor rule), so the two walks agree on what is a term; add the leg to IntegerArgumentConstantWitnessTests.
