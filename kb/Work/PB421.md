# PB421 — a grammar alternative with no general format behind it, answered by generated code instead of a diagnostic

## The mechanism

`src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4` line 1016 defines

```antlr
moveReceivingPhrase
    : TO dataReferenceList
    | (CORRESPONDING | CORR) dataReference TO dataReference      // :1018  ← this one
    ;
```

and line 1007 defines `moveStatement`'s second alternative as `MOVE moveSendingOperand moveReceivingPhrase`.
Composed, those two admit `MOVE <sending-operand> {CORRESPONDING|CORR} id-3 TO id-4`. Alternative 1 of
`moveStatement` (`MOVE (CORRESPONDING | CORR) dataReference TO dataReference`, :1006) already carries the whole
of Format 2, so :1018 has no legal shape behind it at all — it is pure over-acceptance, not a second spelling of
anything.

What makes it a defect rather than a harmless dead alternative is the STAGE at which the shape is answered.
`MoveBinder.Bind` (`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/MoveBinder.cs:33-36`) tests
`move.CORRESPONDING()` on the STATEMENT context — null here, because the token sits inside the receiving phrase —
then asks for `move.moveReceivingPhrase()?.dataReferenceList()`, which is also null on this alternative, and
falls through to `new BoundUnsupported("MOVE CORRESPONDING / unsupported MOVE form")` (:36).
`StatementEmitter.Visit(BoundUnsupported)` (`src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:211`) renders that
as `EmitCore.LoudStmt`. So the compiler reports NOTHING, emits a program, and the program aborts at run time with
a message saying a COBOL feature "is not yet implemented" — about source the standard has no format for. The
loud-stage mechanism is being used as a parser's error handler.

## The rule, quoted, with its `--check` lines

§14.9.25.2 has exactly two general formats.

    python scripts/spec/cite.py --check 14.9.25.2 "CORRESPONDING"
    OK  §14.9.25.2   (General formats)
        Format 2 (corresponding):

    python scripts/spec/cite.py --check 14.9.25.2 "identifier-3"
    OK  §14.9.25.2   (General formats)
        MOVE ┤               ├ identifier-3 TO identifier-4

    python scripts/spec/cite.py --check 14.9.25.2 "MOVE"
    OK  §14.9.25.2   (General formats)
        MOVE ┤              ├ TO { identifier-2 } …

Format 1 is `MOVE {identifier-1 | literal-1} TO {identifier-2} …`; Format 2 is
`MOVE {CORRESPONDING | CORR} identifier-3 TO identifier-4`. Neither places a CORRESPONDING/CORR phrase AFTER a
sending operand. The b2 adjudicator verified the printed diagram (PDF p.694 rendered, per CLAUDE.md rule 1,
because the diagram is load-bearing) and found the transcription at `specs/ISO_COBOL.md:25216-25230` matches the
printed page — so the extra alternative is not inherited from a lossy OCR'd diagram; it was written.

## Expected vs observed — RE-RUN ON HEAD (89044aa0)

EXPECTED: rejected at compile time as a syntax error.

    cobol.exe fmt_send_corr.cob --std 2023 --run
    rc=3762504530
    Unhandled exception. CobolNet.Runtime.NotImplementedCobolFeatureException: COBOL.NET: a COBOL feature that
    is not yet implemented was reached at run time: MOVE CORRESPONDING / unsupported MOVE form

`fmt_send_corr.cob` is `01 A PIC X(4) VALUE "ABCD". 01 G1. 05 F1 PIC X(3) VALUE "XYZ". 01 G2. 05 F1 PIC X(3).` /
`MOVE A CORRESPONDING G1 TO G2 / DISPLAY "REACHED" / STOP RUN.` Compilation succeeds and emits no diagnostic; the
failure is in the emitted program, and "REACHED" never prints. The literal-sender spelling reproduces
identically:

    cobol.exe fmt_lit_corr.cob --std 2023 --run      (MOVE "Q" CORR G1 TO G2)
    rc=3762504530   ... NotImplementedCobolFeatureException: MOVE CORRESPONDING / unsupported MOVE form

The rest of the format surface IS enforced, which localises this to one alternative: a literal in the receiving
position is a clean parse error (`COBOL0308 A data-name is expected here, not a literal`), and
`MOVE CORRESPONDING G1 TO G2 G3` — a second identifier-4 Format 2 does not have — is a parse error.

## The code site and the shape of the repair

- `src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4:1016-1019` — `moveReceivingPhrase`, second alternative at
  :1018. **DELETE IT.** That is the whole repair, and it is the RIGHT repair rather than the smallest one: with
  the alternative gone the shape becomes a parse error, which is the right stage and produces the right message,
  and Format 2 is wholly owned by `moveStatement`'s first alternative (:1006). A binder guard would leave the
  grammar claiming a shape the language does not have and would put the diagnostic one phase too late.
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/MoveBinder.cs:35-36` — the fall-through. After the deletion the
  `moveReceivingPhrase()?.dataReferenceList() is not { }` arm becomes unreachable for this shape; keep it as the
  defensive arm it is, but its message should stop naming "MOVE CORRESPONDING", which is now handled at :33-34.
- A NEGATIVE golden is owed with the fix — there is no test covering the over-acceptance today.

## The sibling sweep the fixer must do

Every OTHER statement rule whose phrase-level sub-rule can compose with its own statement-level alternative to
admit a shape no general format has. The shape to look for is exactly this one: a statement rule with two
alternatives where alternative 1 spells a whole format and a sub-rule of alternative 2 re-spells part of the same
format. Grep for sub-rules mentioning `CORRESPONDING | CORR` (ADD and SUBTRACT also have CORRESPONDING formats)
and, more generally, for any `*Phrase` rule that names a statement-selecting keyword. The drift shape worth
adding is a test that every alternative of every statement rule is reachable from at least one legal-source
golden — an unreachable alternative is either dead or an over-acceptance.
