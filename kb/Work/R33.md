# R33 — adjudicate: an AMBIGUOUS unqualified name resolves FIRST-MATCH (ResolveUnqualified list[0]) instead of demanding qualification

> Found 2026-08-08 while fixing R31: `ResolveUnqualified` is documented "(first match; COBOL requires
> qualification to disambiguate)" and returns `list[0]` when several declarations share the name.

§8.4.2.2.1: "Qualification of a user-defined name is required unless one of the following is true: 1) No
other name has the identical spelling. …" (items 2–6 are narrow outs: REDEFINES/VARYING context, unreferenced
type subordinates, same-group implicit qualification, in-section paragraph names). An unqualified reference
to a multiply-declared name outside those outs is ILLEGAL — today it silently binds to whichever declaration
was registered first, which is a WRONG-ANSWER shape (the program compiles and reads/writes a different item
than another compiler would pick, or than the author intended).

⚠ CONSEQUENCE OF THE CURRENT SHAPE: R30's COBOLNET1639 ambiguity arm ("N declarations share the name …")
is DEAD CODE — Resolve's unqualified leg never returns null for ambiguity, so the arm cannot fire
([[a_dead_lookup_is_also_unverified]]: it has never been contradicted because nothing reaches it).

ADJUDICATE BEFORE FIXING: enforcing §8.4.2.2.1 items 1–6 precisely (especially item 5's same-group implicit
qualification) is a real algorithm, and the leniency may be load-bearing across NIST/corpus programs that
share names benignly. Measure the corpus blast radius first; the strict behavior likely wants the dialect
gate ([[dialect_two_axes]] — a strictness-axis diagnostic, suppressed under --permissive).
