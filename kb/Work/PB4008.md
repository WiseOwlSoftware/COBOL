# PB4008 — a liveness check that never asks whether the process has exited

## What happened

Pull request #738 changes only `kb/Work` notes, `CLAUDE.md` and a DEVLOG entry, and the merge queue removed it (failed_checks,
20:58Z). In run 40765533118, `Windows script self-tests` went RED on one check of `scripts/orchestrator/impact_lane.py
--self-test`:

```
FAIL  a dead worker's pid is not alive  (got True, want False)
```

The arm starts a worker, then `worker.kill()` and `worker.wait()`, and asks `worker_alive({"worker": {"pid": worker.pid}})`.
The `Popen` object still holds the process handle at that point; the arm's `finally` closes it later.

## The mechanism

`impact_lane.worker_alive` decides liveness from two reads. `coord.process_name(pid)` takes the name from the process
snapshot (`coord._nt_snapshot`). `coord.process_command(pid)` reads the command line, and an UNREADABLE command line ('')
reads as alive, by design, so that a live worker is never started beside another (PB3113's rule, copied from
`land_lane.runner_alive`). Neither read asks the operating system whether the process has EXITED.

On Windows, a process that has exited while another process still holds a handle to it keeps its process object. It can still
appear in a snapshot under its image name, `python.exe`, and its command line can no longer be read, because its address
space is gone. Both reads then say "alive". Whether the snapshot still lists it at the moment of the check is timing.
On this host the arm passed 3 of 3 runs under Python 3.12 (uv) and 3 of 3 under 3.15.2 on 2026-10-28, so it is a race the
runner loses and this box wins, not an interpreter difference (PB4007).

PB3973 fixed the other end of the same pair of reads: a just-SPAWNED child whose command line Linux has not set yet.
This is the just-EXITED end.

## The fix the repository already has

`scripts/gate_slot.py#_pid_alive` asks the right question: on Windows `OpenProcess(SYNCHRONIZE |
PROCESS_QUERY_LIMITED_INFORMATION)` and `WaitForSingleObject(h, 0)`, which reports an exited process as dead while a
handle keeps its object; on Linux `kill(pid, 0)` plus the zombie state from `/proc/<pid>/stat`. `scripts/detached.py#pid_alive`
already forwards to it. So the job has two mechanisms (CLAUDE.md rule 4): the exit-state probe in gate_slot, and the
snapshot-plus-command-line reading in the lanes.

**Acceptance:** one liveness question, asked in one place. A pid is alive only when that exit-state probe says it is running;
the command-line identity check (PB3113: a reused pid is a stranger) applies only to a running process. A self-test arm that
is deterministic on every host fails on the old code: it holds an open handle to an exited child (a `Popen` not yet closed,
as this arm has) and asserts that the pid is dead, with no timing involved. Sweep every caller of `coord.process_name` and
`coord.process_command` that decides liveness.

**Sites:** `scripts/orchestrator/impact_lane.py#worker_alive`, `scripts/orchestrator/land_lane.py#runner_alive`,
`scripts/orchestrator/coord.py#process_name`, `scripts/orchestrator/coord.py#process_command`,
`scripts/orchestrator/coord.py#_nt_snapshot`, `scripts/orchestrator/coord.py#runs_python`,
`scripts/orchestrator/coord.py#_exited_but_listed_arm`, `scripts/gate_slot.py` (imports `detached.pid_alive`; `_pid_alive`
deleted), `scripts/run_gate_legs.py` (imports `detached.pid_alive`), `scripts/detached.py#pid_alive`.

**Witness, 2026-10-29.** This defect bounced a notes-only pull request out of the merge queue: PR #755's second
merge-group run (40922224350, `Windows script self-tests`) failed `impact_lane.py --self-test` on exactly the arm named
above, `FAIL a dead worker's pid is not alive (got True, want False)`, after the same file was GREEN in the run before
it. A flake that fails an unrelated landing is a CI-invariant breach (CLAUDE.md, THE CI INVARIANT); see PB4046 for its
sibling in `test_orchestrate_adopt.ps1` that bounced the same pull request.

**Witness, 2026-10-30.** Third bounce: PR #801 (`worktree-wf_f1d1c695-17b-4`, a fix-lane branch that touches none of
these files) left the merge queue on merge-group run 41004518958 (job `Windows script self-tests`, 04:48Z): the same
check, `FAIL  a dead worker's pid is not alive  (got True, want False)`, 1 of 134 self-tests red. The operator re-landed
it by hand at about 09:02 PDT.

## Fix (landed, operator 2026-10-30)

One liveness question, asked in one place:

- `scripts/detached.py#pid_alive` IS the probe now (its body moved from `gate_slot._pid_alive`, which is deleted, and the
  forwarder it was is gone): Windows asks `WaitForSingleObject(h, 0)` of a `SYNCHRONIZE` handle, Linux `kill(pid, 0)`
  and the zombie state. `gate_slot.py` and `run_gate_legs.py` import it from `detached`; `gate_slot.py` imports
  `kill_tree` at the top too, as the import cycle that kept it local is gone. A process that exists but is not ours to
  open reads as RUNNING on both systems and the probe never raises (the branch review, R1-1 and R1-2): POSIX `EPERM`
  from `kill(pid, 0)` (another user's process, such as pid 1, once raised `PermissionError` out of every lane) and
  Windows `ERROR_ACCESS_DENIED` from the open (which read dead) both mean the pid exists; the caller tells a stranger
  by name and command line.
- `scripts/orchestrator/coord.py#process_name` returns None unless `pid_alive` says the process RUNS, so
  `process_command` (which asks it first) and `loop_state` (the supervisor lock) inherit the answer: a listing that
  still names an exited process no longer reads as a live one.
- `coord.runs_python(pid, mark)` is the ONE rule by which a lane tells its own detached process from a dead one and
  from a stranger on a reused pid (PB3113): `land_lane.runner_alive` and `impact_lane.worker_alive` each wrote it out,
  and now each calls it.

**The deterministic arm** (`coord.py --self-test`, `_exited_but_listed_arm`) makes the state, never waits for it: a
Python child exits on EOF while its object is still kept. On Windows the `Popen` keeps the handle after `wait()` and the
listing names the pid as the CI runner's snapshot did (this host's snapshot drops an exited process at once: 0 of 20
listed, measured 2026-10-30); on Linux `os.waitid(..., WEXITED | WNOWAIT)` returns at the exit and leaves the zombie,
which keeps its /proc name with an empty command line. Measured against main's `coord.py` on both: Windows `name='python.exe'
cmd='' reads-alive=True`, WSL `name='python3' cmd='' reads-alive=True`; on this branch both read dead (GREEN).

**Sweep.** Every caller of `coord.process_name` and `coord.process_command` that decides liveness goes through the
probe (`runner_alive`, `worker_alive`, `loop_state`, and `review_lane.py`, which takes `land_lane.runner_alive`).
`process_table` (mailbox.py's watcher check) matches a command line, which an exited process does not have. The two
PowerShell readers of the supervisor lock (`orchestrate.ps1` `Take-Lock`, `stop.ps1` `Get-Running`) read
`Get-Process -Id`, a listing: they belong to the open PB3032 (pid aliasing and reuse of the same lock), which now names
this reason too. `docs/rearchitecture/DESIGN-orchestrator-loop.md` §16.7 listed a `pid_alive` in `land_lane.py` that
PB3113 had renamed `runner_alive`: corrected.
