# PB670 — LANDED — an edition the runtime could not see (owner determination 2026-10-23, option (i))

Found 2026-09-05 by the `PB321` implementer (report §"New defects" B), measured at `--std 85` on
`<a9d94900 scratch>/PB321/probe/p3.cob`. `blocked: true` because the choice is an implementor determination in the
family PB322 already holds for the owner; `blocked_by` is empty because the blocker is the owner, not a note.

## The facts

File sharing is a COBOL-2002 introduction (Annex A.4.7; the compiler gates the SHARING clause at 2002 —
`negative/sharing_below_2002.cob`, COBOLNET0900), `GR-14.9.27.4-4`'s own adjudication says "at 1985 only the
Table-18/Table-20 half of GR4 applies", and `FileStatus.cs` calls the 5x/6x family "the COBOL-2002 file-sharing /
record-locking status family". After PB321 every OPEN is arbitrated by Table 19 (`OK §14.9.27.4 4)`), and the
runtime has no edition by design — edition gating happens at bind — so the arbitration cannot vary by `--std`
without a new seam (the natural one is a flag on the run-unit prologue's `CobolFile.Init()`, whose correctness
across separately compiled CALLed programs is itself a decision). Nothing in the corpus exercises it: the full
CorpusRunner across all four editions and the 375 NIST cases are green either way.

## ⛔ Bare question for the owner

At `--std 85`, when a second file connector opens a physical file that another connector already holds open in a
conflicting mode and neither carries a sharing specification (1985 has none), should the compiler (i) permit the
open, as 1985's silence allows; (ii) refuse it with the platform-dependent `30` the OS handle gave before PB321; or
(iii) refuse it with the deterministic `61` it gives now, a status 1985 does not define? The answer is recorded in
`docs/CONFORMANCE.md` beside A.1 item 77 (PB322's determination A) and, if it is (i) or (ii), lands as the runtime
edition seam above with an 85 golden; if (iii), the current behaviour is documented and this note closes.

## Update 2026-10-04 (w1013m, PB322 landed) — the question is sharper, still the owner's

PB322 determination A landed: a connector with no sharing specification is SHARING WITH READ ONLY for `OPEN INPUT` and SHARING WITH
NO OTHER for `OPEN OUTPUT` / `I-O` / `EXTEND` (docs/CONFORMANCE.md DOC-A.1-77, DOC-A.1-131), and the runtime is edition-blind, so option
(iii) of the question above is now literal for EVERY clause-less pair at `--std 85`: two clause-less I-O connectors on one file answer
'61' where they answered '00' before (the I-O + I-O and EXTEND pairs the old undetermined-mode quantifier admitted). The one
conformance golden that exercised it, `85/pb143_shared_visibility`, MOVED to `2002/` and now declares SHARING WITH ALL OTHER (SHARING is
a COBOL-2002 clause, so no 85 source can say it). Measured for the decision: cobc 3.2 (WSL) answers `00` for two I-O opens of one
file in one run unit at `-std=cobol85`, `cobol2002` and `ibm` alike (GnuCOBOL arbitrates across processes with fcntl, never inside
one), so option (i) is also what the rule-1 precedent does at 85. The seam, if the owner chooses (i) or (ii), is one line in
`FileRegistry.SharedOpenAttempt` reading `FileConnector.Edition`.

## Landed (wave 20261024, group A2)

Option (i), implemented as the structure the next case needs, not as the one-line row the estimate named. The estimate ("a DialectBehavior row read by SharedOpenAttempt") proved too small: the in-run-unit Table 19 loop is only one of three places that refuse a clause-less sibling. (1) The OS share mode of the first connector's handle (`FileLockPosture.OfSharingMode`) refuses a sibling that Table 19 would admit unless the posture admits every sibling, so the 85 default mode is ALL OTHER (`ImplementorDefaultSharing(mode, edition)`). (2) The cross-run-unit column lock (`RunUnitFileLock`) refuses an in-process sibling like any other holder (OFD and handle locks do not know a process's own descriptors), so `FileConnector.Open` takes none at 85. (3) The keyed `StoreTable.AttachCreated` threw `InvalidOperationException` for an OPEN OUTPUT beside a holder (PB754's guard: the arbitration was assumed), an escaping exception from an OPEN, so a creation beside holders now replaces the path's store at 85 (`arbitrated: false`) and stays loud from 2002. A host refusal by a process outside the run unit answers `30` at 85 (`61` is undefined there). One read for all of it: `DialectBehavior.FileSharingFacility` (ChangedIn 2002; VCR row 7.39, a derived edge; ISO basis §9.1.15 "a mode completely specified by the implementor" and §A.4.1 "exception conditions, and I-O status values are also optional" with the optional module A.4.7) through `FileConnector.SharingFacilityInEffect`. `DialectBehaviors.Row.VcrRow` became a string (a Table 7 row is `7.39`), so the runtime major is 15.

Witnesses: `conformance:wiseowl/cases/A.1-Implementor-defined-language-element-list/pb670_cobol85_no_sharing_facility` (statuses identical to cobc 3.2 `-std=cobol85`), `SharingFacilityEditionTests` (every pair of opens in every organization at 85 and at 2002, the outsider's `30` and `61`, a second run unit, two EXTENDs, the created file under a holder, GR5 visibility) and the NIST 85 corpus (364 programs, unchanged). DOC-A.1-77 and DOC-A.1-131 gained the COBOL-85 band (batch `w20261024a2-PB670`).

Trap: a host refusal met there is the WRITER's (held, answered at its next WRITE or CLOSE), not the opener's.

Trap: any change that narrows a per-frame check to a counter needs every writer of the medium to move the counter (truncation is a writer).
