# PB670 — OPEN, BLOCKED ON THE OWNER — an edition the runtime cannot see

Found 2026-09-05 by the `PB321` implementer (report §"New defects" B), measured at `--std 85` on
`<a9d94900 scratch>/PB321/probe/p3.cob`. `blocked: true` because the choice is an implementor determination in the
family PB322 already holds for the owner; `blocked_by` is empty because the blocker is the owner, not a note.

## The facts

File sharing is a COBOL-2002 introduction (Annex A.4.7; the compiler gates the SHARING clause at 2002 —
`negative/sharing_below_2002.cob`, COBOLNET0900), `GR-14.9.27.4-4`'s own adjudication says "at 1985 only the
Table-18/Table-20 half of GR4 applies", and `FileStatus.cs` calls the 5x/6x family "the COBOL-2002 file-sharing /
record-locking status family". After PB321 every OPEN is arbitrated by Table 19 (`OK §14.9.27.4 4)`), and the
runtime has no edition by design — edition gating happens at bind — so the arbitration cannot vary by `--std`
without a new seam (the natural one is a flag on the run-unit prologue's `CobolFile.Init()`, whose correctness
across separately compiled CALLed programs is itself a decision). Nothing in the corpus exercises it: the full
CorpusRunner across all four editions and the 375 NIST cases are green either way.

## ⛔ Bare question for the owner

At `--std 85`, when a second file connector opens a physical file that another connector already holds open in a
conflicting mode and neither carries a sharing specification (1985 has none), should the compiler (i) permit the
open, as 1985's silence allows; (ii) refuse it with the platform-dependent `30` the OS handle gave before PB321; or
(iii) refuse it with the deterministic `61` it gives now, a status 1985 does not define? The answer is recorded in
`docs/CONFORMANCE.md` beside A.1 item 77 (PB322's determination A) and, if it is (i) or (ii), lands as the runtime
edition seam above with an 85 golden; if (iii), the current behaviour is documented and this note closes.
