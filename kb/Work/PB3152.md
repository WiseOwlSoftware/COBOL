## Mechanism

- `parse_report` collects `ids` from every PB id in the report's HEADER, the lines before its first `## ` heading
  (`for i, line in enumerate(lines): if i > 0 and line.startswith("## "): break`), plus the file name's lead. A mention
  in a `## ` section body is already dropped. w1075z's header holds a "why this branch exists" paragraph whose line 11
  names PB3101 ("Its finisher would have started PB3101") and whose line 12 names PB3146, so it yields `['PB3150',
  'PB3101', 'PB3146']` (measured with `plan_wave.load_reports`).
- `plan()`'s `newest` loop (`scripts/orchestrator/plan_wave.py`, the `for r in reports: for i in r.ids: if i in
  open_ids` block) keys each OPEN id on the newest report that mentions it, so w1075z becomes PB3101's newest
  report, and its FINDINGS verdict files PB3101 into `finisher_by_rep[w1075z]`.
- PB3150's unseen-lead arm (the `newest_of_branch` loop, same function) then skips w1075z because
  `r.path in finisher_by_rep`, so the report's real lead is never planned.
- The group is built from `ids` (PB3101), so its note, files, model and same-file `after:` are PB3101's.

The `newest` keying is on main too: any FINDINGS or SPLIT report whose HEADER merely mentions another open note (a
merge note, a "not started" aside about a different group, a cross-reference in a summary paragraph) can capture that
note's finisher.

**Two more consumers read `Report.ids` the same way (mention taken as ownership), both in `plan_wave.py`:**
- `attempts(nid, reports)` counts every report whose ids hold `nid`, and `choose_model` escalates a note to Opus once
  that count reaches `model_rules.json`'s `failed_attempts_at_least`. w1075z counts as an attempt at PB3101 although no
  agent worked on it, so a note that is only mentioned is escalated as "already attempted N times without landing".
- `held_by_dispatch` releases a note held in the dispatch ledger for a running group as soon as ANY newer report's ids
  hold it (`mine & set(r.ids)`). A report that only mentions the note releases it before its real dispatch has
  reported, so the planner plans that note again: the double dispatch PB2806 closed.

## Fix direction

Give a report the notes its group was DISPATCHED with, as a field separate from the ids its header mentions: the
dispatch ledger `inflight-groups.json` already records each group's `notes` (`held_by_dispatch` reads them), and a
report the ledger does not know (an attended branch's) has its file name's lead, which is always one of them. Then `newest`, `attempts` and `held_by_dispatch` read that field, never every id the header mentions, and a
report's finisher is planned under its own lead. Regression tests in `scripts/orchestrator/test_plan_wave.py`, each
with the mention in the report's HEADER (a mention in a `## ` body is already ignored, so a test that puts it there
passes on the unfixed planner and witnesses nothing):
- a FINDINGS report whose header mentions another open note plans one finisher under its own lead, and leaves the
  mentioned note to its own report;
- the mention does not count as an attempt at the mentioned note in `choose_model`;
- the mention does not release the mentioned note from the dispatch ledger.

The natural fixer is `plan-wave-drain`'s review finisher (PB3150, the same function; I9).
