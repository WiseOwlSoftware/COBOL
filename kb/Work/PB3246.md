# PB3246 — staged RAISING propagation vs the GR17 termination (UNPROBED)

Filed 2026-10-16 by the enqueue unit's clerk. Source: `E:\COBOL-coord\scratch\reports\w1084f-PB1177-report.md`, "New defects" and its "Order" bullet. **The claim is unverified: the finisher did not probe it.** The harm flags above are placeholders until a probe.

**Claim.** When a declarative both staged a RAISING propagation (a `GOBACK ... RAISING`) and, by the same activation,
triggers the GR17 termination, the staged propagation stays staged and is never consumed at that site. The report found
this on the CALL arm (existing behaviour) and the INVOKE arm (the method path runs the GR17 check before the pickup, as in
CALL, so it inherits it): if a method's declarative both staged a RAISING propagation and ended a SORT, the propagation
stays staged.

**R1.** PB100, PB1119, PB1121, PB1425 and PB2504 mention GOBACK RAISING; none records this interaction (PB1121 item 1 covers
`EmitRaisingStage` for an object status; PB1119 covers the automatic-propagation exclusions). A probe may show it belongs
to one of them: then fold it there and close this note.

**To verify.** Write the COBOL probe (a CALLed program and a method whose declarative stages `GOBACK RAISING` while the same
activation triggers the GR17 termination, for example by ending a SORT), derive the expected behaviour from the propagation
rules in the spec and the GR17 clause (`cite.py --check` each), then adjudicate. Code sites: the CALL and INVOKE emitters'
GR17-check-then-pickup order, found from `CallEmitter.EmitRaisingStage` (PB1121).

## Re-filed as a defect (analyses sweep, 2026-10-23)

Adjudicated read-only by an Opus cobol-adjudicator on main e7cf38ce4; accepted by the Mythos session.

A RAISING propagation staged by a declarative that also triggers the §14.9.40.4 GR17 SORT termination is not consumed at its CALL. It stays staged and is raised at the activator's next activating statement, which is the wrong statement. Mechanism: ProgramTable.CallProgram (src/WiseOwl.Cobol.Runtime/Control/ProgramTable.cs:622) runs SortFiles.AfterActivationReturn() right after inst.Call returns, and that throws SortTerminationSignal before the CALL site's emitted EmitPropagationPickup (CallEmitter.cs:108/153) can run. The note's report says the INVOKE arm (OoEmitter.cs:2043, SortAfterActivationReturn before the pickup) has the same order; it was not probed separately. Expected per §14.9.18.4 GR1 b) (the condition is raised in the activating runtime element, with execution continuing as the activating statement's rules specify) and GR17: EC-SIZE-OVERFLOW is raised in A at CALL B, its declarative runs there, and the SORT is terminated. Nothing is raised at CALL C. Fix: take the staged propagation before the GR17 signal leaves the activation boundary (the pickup ahead of AfterActivationReturn, or the signal carrying the staged condition to the SORT landing), on the CALL and INVOKE arms together, with a golden for each.

Evidence: Probe probes/pb3246/w3246.cob (--std 2014, checking on) on a main-equivalent build. The control, a plain CALL B whose declarative ends in GOBACK RAISING EXCEPTION EC-SIZE-OVERFLOW, raises it in A at the CALL ('A caught EC-SIZE-OVERFLOW', then 'after plain CALL'). The same CALL from a format 1 SORT's INPUT PROCEDURE terminates the SORT (GR17) with no raise in A ('after SORT, status=EC-SIZE-ZERO-DIVIDE'), and the staged EC-SIZE-OVERFLOW is then raised at the NEXT, unrelated CALL C ('in C', 'A caught EC-SIZE-OVERFLOW').

Rule: §14.9.18.4 GR1 b) (checked); §14.9.40.4 GR17 (checked)

## Landed (2026-10-27, wave 20261027 group B) - the activating site picks up, THEN terminates the SORT

**Re-probe (both arms).** `E:\COBOL-coord\scratch\w20261027b\w3246.cob` (CALL) and `i3246.cob` (INVOKE of a method with the same
declarative) both reproduced the adjudication: from a format 1 SORT's INPUT PROCEDURE the activator's `A caught
EC-SIZE-OVERFLOW` did not print at the CALL (the INVOKE); it printed after `next CALL` / `next INVOKE`, at the activator's
next activation. So the INVOKE arm "inherits it" as the note's report claimed, and it is the same mechanism.

**Root cause.** Two sites asked §14.9.40.4 GR17's question (`SortFileTable.AfterActivationReturn`, which throws
`SortTerminationSignal`) in the wrong place relative to the propagation pickup: the CALL lane asked it inside
`ProgramTable.Activate` (before the call site's emitted pickup could run) and the INVOKE lane emitted it before the pickup in
`OoEmitter.EmitInvocationReturned`. The termination unwinds the rest of the SORT's range, so the pickup never ran and the staged
condition stayed staged for the activator's next pickup.

**Fix.** One activation tail for both lanes: `CallEmitter.EmitActivationReturned` emits the pickup and THEN the GR17 question
(`EmitPropagationPickup` is private now); `EmitCall` (both its paths) and every INVOKE form call it, `OoEmitter.EmitInvocationReturned`
(a one-line forwarder after the change) is deleted, and `ProgramTable.Activate` no longer asks the question (the host boundary,
`CallFromHost`, which emits no pickup, asks it itself). Order per §14.9.18.4 GR1 b) ("after the result ... is returned") then
§14.9.40.4 GR17.

**Golden.** `14.9.40-SORT/pb3246_sort_terminated_after_raising_pickup` (accept 2002): a CALL and an INVOKE arm in one program,
expected values derived from the two rules.

**For the next implementer.**
- `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/CallEmitter.cs#EmitActivationReturned` - the ONE tail of an activating statement (pickup, then the GR17 question); call it from any new activating verb, never `EmitPropagationPickup` or `SortAfterActivationReturn` alone. Trap: the GR17 throw unwinds the rest of the SORT range, so anything an activation owes its activator must come BEFORE it.
- `src/WiseOwl.Cobol.Runtime/Control/ProgramTable.cs#Activate` - no longer asks the GR17 question; `CallFromHost` does (it emits no pickup).
- `src/WiseOwl.Cobol.Runtime/IO/SortFileTable.cs#AfterActivationReturn` - pending state is cleared by `Remove` when the SORT statement ends, so a skipped ask (a RESUME AT leaving the range) leaves nothing stale.
