**Mechanism.** Group-valued property references are staged COBOLNET0899 'later refinement': when the GET RETURNING / SET USING item is a group, OoTryBindPropertyReference refuses instead of building the §8.4.3.9.4 temp over the group description

**Repro.** pinned cobol.exe --std 2002 E:/Temp/claude/E--CobolSharp/a700c052-f9e4-4942-84ff-a13c7505d6ec/scratchpad/adj-d2/out/probe/objprop/p10.cob: class CPA10 with METHOD-ID. GET PROPERTY GRP ... PROCEDURE DIVISION RETURNING LK-R (01 LK-R. 05 R1 PIC X(3). 05 R2 PIC X(3).) moving 'ABCDEF'; driver `MOVE GRP OF A TO W` (W PIC X(6)) -> COBOLNET0899 + COBOLNET1639

**Expected from the spec.** Compiles and displays ABCDEF: GR1 'temp-1 ... data description ... the same as the data description of the item specified in the RETURNING phrase', and SR5 lets the property appear 'wherever a data item with that description would be valid as a sending item' — a group is a valid MOVE sender. Same for receiving (GR2/SR6) and read-modify-write (GR3).

**Observed / reasoning.** ReferenceResolver.cs:152 `if (model.IsGroup) { Error(OoGroupValuedProperty ...) ; return null; }` (DiagnosticCatalog 0899 RecognizedNotImplemented, DIAGNOSTICS.md 'oo-group-valued-property'); the probe path also returns null for a group model. No kb/Work note owns it.

**Code site.** src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs#OoTryBindPropertyReference (:152-:158); src/Cobol.Net.Compiler/Binding/DataBinder.Oo.cs#OoCreatePropertyTemp

## What the fixer owes

## Landed 2026-10-03 (wave-1005 implementer E)

Re-probed on a fresh Debug build: p10 reproduced (COBOLNET0899 + COBOLNET1639 for every `GRP OF A`).

**Fix.** `ReferenceResolver.OoTryBindPropertyReference` no longer refuses a group-valued model, in the committing path or in the probe path (the probe used to answer null for a group, which also hid a group property from `IsObjectPropertyReference`). The ONE temp constructor, `DataBinder.CreateCompilerTemp`, already deep-clones a group model (the §8.4.3.2.4 GR1 group RETURNING result), so no new temp code was needed: `OoWrapPropertyOps` wraps the group temp with the GET (sending), the SET (receiving) or both around ONE temp (read-modify-write). `DiagnosticCatalog.OoGroupValuedProperty` and its DIAGNOSTICS.md row are deleted (the id 0899/`oo-group-valued-property` is retired, never reused); `kb/Spec/Lookup/Diagnostics.md` and `docs/COBOLNET_OO_SLICE_BRIEFS.md` no longer call the case staged.

**Spec (cite.py --check, all OK).** §8.4.3.9.4 GR1, GR2 and GR3 give temp-1 and temp-2 the accessor's data description; §8.4.3.9.3 SR5 and SR6 admit the property "wherever a data item with that description would be valid" as a sending / receiving item, and a group is valid in MOVE, INSPECT and DISPLAY.

**Golden.** `conformance:2002/pb1448_group_valued_property` — sending (`MOVE GRP OF A TO W`), receiving (`MOVE "456XYZ" TO GRP OF A`, the SET runs and the GET does not) and read-modify-write (`INSPECT GRP OF A REPLACING ALL "X" BY "Z"`, GET then SET) over a group with a numeric and an alphanumeric leaf, the trace lines proving which accessor ran.

**Rows.** GR-8.4.3.9.4-1, -2 and -3 close (CONFORMS). SR-8.4.3.9.3-5 and SR-8.4.3.9.3-6 stay OPEN under PB1275, which already claims them: their other defect is an object-reference-valued property as the SET statement's sender or receiver (`BoundStores.StoreKindOf` has no `BoundSetObjectRef` arm), and that mechanism is PB1275's, outside this slice. GR-8.4.3.9.4-2's second defect (temp-2 modelled on the GET's description) is moot now that PB1450 enforces §8.4.3.9.3 SR7.
