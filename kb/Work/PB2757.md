**Rule it breaks:** LineSequentialEncoding (class summary: the connector streams a byte CHANNEL, one char per medium byte, so framing and REWRITE/START byte anchors stay byte-exact) and SequentialConnector's own field comments (_readOffset/_lineByteOffset: 'Latin1 - one byte per character'); NextFrame's BOM skip presumes the reader did NOT consume the BOM; §14.9.30.4 makes available the record on the medium; §9.1.7.2 the record sequential record is the bytes the implementor framed

**Scenario:** Measured on .NET 10.0.12: new StreamReader(stream, Encoding.Latin1, detectEncodingFromByteOrderMarks: true, n) over the bytes FF FE 41 00 42 00 E9 20 returns 3 chars (U+0041 U+0042 U+20E9, CurrentEncoding utf-16), and over EF BB BF C3 A9 0A returns U+00E9 U+000A (utf-8, BOM consumed). (1) A RECORD SEQUENTIAL file of 8-byte records whose first field is PIC S9(4) COMP = -2 (big-endian FF FE, NumericByteFormDriftTests) is written correctly and READ back as UTF-16LE: FillChars(buf, 8) consumes 16 bytes, every record is garbage, _readOffset (counted in chars) stops matching the medium, and a REWRITE overwrites the wrong block - all with status '00'. FE FF (UTF-16BE) and EF BB BF starts do the same. (2) A LINE SEQUENTIAL UTF-8 file with a BOM (which LineSequentialEncoding says is 'accepted and is not record data'): the reader strips the BOM and decodes UTF-8 itself, so NextFrame's StartsWith(Bom) never matches, _lineByteOffset/_lastLineStart are 3 bytes short (a REWRITE overwrites the BOM and shifts the line), and FromChannel re-decodes already-decoded text: 'e-acute' (C3 A9) arrives as U+00E9, a lone UTF-8 lead byte, so the record area receives the escape U+DCE9 and the READ answers '09' instead of '00'. No test writes a BOM or a FFFE/FEFF-leading record (grep of tests/ for the BOM bytes finds only SourceEncodingDriftTests)

**Measured how:** R2 batch finding `runtime-io-3--code--f3#1` (pair runtime-io-3--code), read in the pinned tree at 8be23006851a; skeptics rule upheld, scenario upheld, site upheld.

**Spec:** §14.9.30.4 "is made available in the record area" (`cite.py --check` passed at collection); §9.1.7.2 "In record sequential files the length of each record is determined by any information the implementor may add to the record on the physical storage medium" (`cite.py --check` passed at collection)

**Target:** OpenReader passes detectEncodingFromByteOrderMarks: false - the channel is always Latin-1 one-char-per-byte and the BOM rule stays NextFrame's alone (the ONE place DOC-A.1-115's BOM determination is applied); a conformance golden writes a fixed record whose first bytes are X'FFFE' and a UTF-8-BOM line sequential file with a non-ASCII record and READs/REWRITEs both; sweep the runtime for other StreamReader constructions over a COBOL medium (TailoringRules reads a collation source, not a COBOL file, and is out of scope)

## Landing

**Landed (wave 1048 A).** Re-probed on the worktree's own build before the fix, with the golden
`conformance:2023/pb2757_medium_bytes_not_bom_sniffed` as the probe: a fixed record sequential file opening X'FFFE'
(PIC S9(4) COMP = -2) read `RS1 04  6707` with every record garbled and its REWRITE '44'; the X'FEFF' and X'EFBBBF'
openings were garbled the same way; the UTF-8-BOM line sequential file read `LS1 09 WRONG` and its in-place REWRITE
answered '44'. After: every record reads back as written with '00', each REWRITE replaces in place, and the line
sequential BOM is skipped and kept. Fix: `SequentialConnector.OpenReader` builds its `StreamReader` with
`detectEncodingFromByteOrderMarks: false`, so the channel is always Latin-1, one char per medium byte, and the ONE
byte-order-mark rule stays `NextFrame`'s (DOC-A.1-115 (b)). Sweep: the only other `StreamReader` constructions in
`src/Cobol.Net.Runtime` are in `Collation/TailoringRules.cs` (a collation tailoring source, not a COBOL medium, out of
scope); the relative and indexed organizations read their media through byte streams.

For the next implementer:
- `src/Cobol.Net.Runtime/IO/SequentialConnector.cs#OpenReader` is the ONE spelling of the read handle; never re-enable
  BOM detection there, since it re-decodes the whole medium and breaks every byte anchor. BOM handling belongs to
  `#NextFrame` only.
- Trap: a literal X'FF' in a golden reads back as HIGH-VALUE (U+FFFF) through a fixed file (DOC-A.1-31), so build
  X'FFxx' bytes from a PIC S9(4) COMP value instead of comparing an X'FF' literal.
