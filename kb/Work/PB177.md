# PB177

Found 2026-08-30 by the PB176 skeptic round (two read-only adversarial agents over the GroupImage guard;
their full analyses are in the DEVLOG-1399 session's task outputs — the load-bearing claims are restated
here). All PRE-EXISTING; PB176 changed none of these paths. One family: the boundary copy-in/copy-out
image paths were built before the image predicate and never gained it.

**A — OO method group formals / RETURNING, NO gate at all (CS1061):** `OoEmitter` emits
`{root}.FromImage({param})` and `{formal}.AsImage()` for method LINKAGE formals and RETURNING items with
no image-capability consult; `DataBinder.Oo` adds formals unscreened. The `OoConformance`/`OoBinder`
IsImageCapable checks run at INVOKE/override time — the METHOD BODY emits unconditionally, so a method
declaring `01 G. 05 A PIC X. 05 N USAGE INDEX.` as a formal fails BACKEND compilation (the struct gets
no image methods: ElementImageCapable false and no variable-length subordinate either).

**B — CallStringWrite's fall-through (CS0029), the write twin of PB176:** it guards on IsImageCapable
but falls through to `PlaceRenderer.Write(p, value)`, which for a group MemberPlace renders
`_G = <string>;`. A CALLED program with a non-image-capable group LINKAGE formal (INDEX leaf) gets
`_G = __lnkp0.Value;` — uncompilable — while its read twin correctly stages the loud. Same exposure via
ReportWriterEmitter's `CONTROL IS <group>` write.

**C — the bind-side half, missing screens:** §14.9.4.3 SR12's variable-length-group argument screen is
gated `!isReturning && !formatTwo`, so Format-2 (AS NESTED / prototype) CALL arguments and RETURNING
items are unscreened; INVOKE arguments have no SR12 equivalent anywhere. DERIVE FIRST what the spec
actually requires per form (§14.9.4.3 / §14.8.2 / the INVOKE rules) — the screens may be spec-required
rejections, not just defensive. Also: the binder screens dynamic-CAPACITY under REDEFINES
(COBOLNET1525, §13.18.44 SR5) but has NO screen for DYNAMIC LENGTH under REDEFINES — derive §13.18.44's
rules for it (an IntrinsicBinder comment asserts SR17 bars dynamic items under REDEFINES; validate with
cite.py, then either screen it or admit it deliberately).

**D — a FOURTH missing screen, same family (added 2026-08-31 by the PB164 Step D review fleet, its finding
R-d; PRE-EXISTING).** `StringEmitter.WriteImage` (`src/Cobol.Net.Compiler/CodeGen/Verbs/StringEmitter.cs`)
stages the §14.9.43.3 SR1 loud for a STRING INTO receiver that is not usage display — but the guard reads
`if (p is not RedefViewPlace && !p.Item.StoreAsImage && p.Item.Pic is not { Category: Alphanumeric })`, so a
WINDOWED or image-stored receiver SKIPS the screen entirely and falls through to a raw
`PlaceRenderer.Write(p, imageExpr)`. SR1 (`--check` OK) is unambiguous — "all identifiers, except identifier-4,
shall be described implicitly or explicitly as usage display or national" — so `STRING … INTO` a `COMP-5`
identifier-3 is ILLEGAL SOURCE, and since the arm-1 dissolution made such an item windowed the compiler now
accepts it and writes the characters straight over its bytes. **Under-rejects, silently.** The screen was
correct while the two conditions coincided (only a display item could be image-stored); it is the DIGIT/BYTE
and CHARACTER/WINDOW axis separation, again. Fix with C's screens: the SR1 test belongs on the ITEM's
description (usage display or national), never on how its storage happens to be carried.

**WHAT WOULD CLOSE IT:** the boundary paths consult the SAME predicate every operand path consults —
A: gate the method-body formal image round-trip (loud or bind-reject per the derived spec rule);
B: CallStringWrite's fall-through stages the loud like its read twin (the eighth two-arm instance);
C: the derived screens, each with negative fixtures; D: the SR1 screen re-expressed on the description with a
negative fixture (`STRING "AB" DELIMITED SIZE INTO <a windowed COMP-5 item>`). Sweep every
`.AsImage()`/`.FromImage(` spelled outside PlaceRenderer (the ONE-reader law in GroupImage's doc) — PB178
carries the AsStorageImage instance.

## Implementation record - 2026-08-31 (burn-down cluster A)

**EVERY ARM PROBED ON THE CLEAN TREE BEFORE ANY EDIT.** Results, including two the note got wrong:

- **A (LIVE, as filed but for a DIFFERENT shape).** THE NOTE'S OWN REPRO IS DEAD: `PicInfo.IndexItem` is
  `(Numeric, Usage.Index)` and `ByteForm` maps `Usage.Index => Binary`, so `HasImageByteForm` is TRUE and an
  INDEX-leaf group has been image-capable since R40 - the note names `05 N USAGE INDEX` as its crash shape
  twice and both would compile clean. The LIVE shapes are the POINTER/object-class leaf and the VARIABLE-LENGTH
  group. Measured: a CLASS whose METHOD declares `01 G. 05 P USAGE POINTER. 05 GA PIC X(4).` as a formal and is
  NEVER INVOKED gave `CS1061` on `FromImage` (OoEmitter's copy-in) and on `AsImage` (its copy-out).
- **B (LIVE, exactly as filed).** A sub-PROGRAM compiled ALONE whose `PROCEDURE DIVISION USING G` names a
  pointer-leaf group: `CS0029: Cannot implicitly convert type 'string' to '_PRG_...._T_0'` at ProgramEmitter's
  formal copy-in. Separate compilation is why the caller-side `ArgText` screen gives it no cover.
- **C - one third is NOT A DEFECT, and the derivation reverses the note's suggested fix.** 14.9.4.3 SR12 sits
  under the printed FORMAT 1 heading and names identifier-2 only, so `CallBinder.ScreenCallOperand`'s
  `!isReturning && !formatTwo` gate is SPEC-CORRECT on BOTH conjuncts, and 14.9.23.3 SR1-SR17 contains no
  variable-length prohibition at all - an SR12 clone at INVOKE would REJECT LEGAL SOURCE. Left alone,
  deliberately, with a comment naming the printed FORMAT 1 heading so the next reader does not "fix" it.
  What IS missing there is the 8.5.1.12 COMPATIBILITY relation (see the gated remainder below).
- **D - DISSOLVED, measured across SEVEN receiver shapes.** The note says `StringEmitter.WriteImage`'s
  `StoreAsImage` guard lets a windowed COMP receiver skip the 14.9.43.3 SR1 screen and be accepted silently.
  It does not: a BIND screen (COBOLNET1626) already rejects on the ITEM'S DESCRIPTION - which is exactly the
  fix leg D asks for. Probed and rejected: native COMP-5, native COMP, windowed COMP, windowed PACKED-DECIMAL,
  windowed COMP-1, a COMP-5 leaf under a whole-group operand, and an FD-record COMP-5 leaf; a windowed
  usage-DISPLAY `PIC 9(4)` is correctly ACCEPTED, since SR1 admits usage display. The emitter guard is an
  unreachable backstop, so it is left as written rather than gold-plated - but the measured fact is LOCKED by
  the negative fixture `pb177-string-into-windowed-comp`, because the bind screen still carries the same
  `StoreAsImage` conjunct and a future promotion of a non-display leaf must fail there loudly.

**FIXES LANDED.**
- **A** - `OoEmitter`'s three sites route through `PlaceRenderer` (`WriteFullGroupImage` for the copy-in,
  `GroupImage` for the copy-out and the RETURNING delivery) via a new `MethodRootPlace` helper, since a method's
  LINKAGE/LOCAL roots are C# LOCALS and there was no `Place` to hand the renderer. The Tier-B REDEFINES
  canonical arm is deliberately NOT rerouted: its storage is the string backing local at the CLASS width (a
  wider level-01 redefiner needs the full backing, 13.18.44.3 SR8), not the canonical view's width - the risk
  the cluster analysis flagged, resolved by leaving the correct path alone.
- **B** - `CallStringWrite` DROPS its own `&& p.Item.IsImageCapable`, so every non-`RedefViewPlace` group goes
  to `WriteFullGroupImage` and the ONE writer's arm order stages the loud. The read/write lockstep the comment
  claimed is now STRUCTURAL. `V59ImagePredicateDriftTests` was updated deliberately (it demanded TWO spellings
  of the predicate in `CallEmitter`, one per half - and the two were NOT in lockstep, which is the defect); it
  now asserts the read half guards and the write half DELEGATES.
- **C / SR17** - `DataBinder` gains `Sr17Shape`, screened per WRITTEN ENTRY on BOTH sides beside SR12/SR14 and
  before the dissolve loop, as COBOLNET1698, AND the class TIER is set Rejected. The tier matters on its own:
  `StorageFormPass.Classify` returns `DynamicString` for an `IsDynamicLength` item BEFORE its Tier-B view arm,
  so the gap was a SILENT MIS-MODEL, measured - `01 A PIC X(8) VALUE "ABCDEFGH". 01 B REDEFINES A. 05 D PIC X
  DYNAMIC LENGTH.` compiled clean and `MOVE "ZZ" TO D` left A unchanged: two storages for the one area
  13.18.44.4 GR1 defines.
- **C / 13.18.16.3** - ONE `ControlOperandShapeViolation` screen, one arm per rule, as COBOLNET1699. THREE
  rules were unscreened, not one: SR3 (operand subject to an OCCURS) and SR5 (an occurs-depending table
  subordinate) compiled and RAN silently; SR7 (a variable-length group) compiled and staged a runtime loud
  where a SYNTAX rule demands a compile-time rejection. PREMISE CHECK: the cluster analysis proposed only
  SR7, but an occurs-DEPENDING table does NOT make a group variable-length - 8.5.1.12.1 defines that term over
  dynamic-length elementary items and dynamic-CAPACITY tables - so SR7 does not reach the ODO shape and a
  screen written for it alone would have left SR5 open.
- **Three miscitations repaired** (CLAUDE.md rule 1's inherited-citation failure, live in shipping message
  text): `DataBinder.Reports` and `ReportWriterEmitter` both cited 13.18.16.3 SR3 - which is "Data-name-1
  shall not be subject to any OCCURS clauses" - for an unresolvable operand (really 8.4.2.1) and for a
  float/INDEX one (really an implementation limit under 13.18.16.4 GR3); and COBOLNET1525 cited 13.18.44 SR5
  for the dynamic-CAPACITY case, but SR5's own sentence is about occurs-depending tables (COBOLNET0855's rule).
  1525 is now NARROWED to the entry that IS itself a dynamic-capacity table - which NO syntax rule literally
  names - and cites what actually decides it: 13.18.44.4 GR1's storage association against 8.5.1.9.1's
  "may vary during execution". `ContainsDynamicTable` became dead and was deleted.

**PINS.** Golden `pb177_method_group_boundary` - a method whose formal AND RETURNING span PIC X, S9(4) COMP,
S9(5) PACKED-DECIMAL, COMP-1 and USAGE INDEX (the regression net proving the note's INDEX repro really is

**GATED REMAINDER - arm C item 2, unchanged and NOT improvised.** 14.9.4.3 SR25 -> 14.8.2.2/14.8.3.2 ->
8.5.1.12 ADMIT a variable-length group across a Format-2 CALL / CALL RETURNING / INVOKE boundary subject to a

## Landing addendum — 2026-08-31, the cluster-A review-fleet fix pass

`status: open -> landed`. The GATED REMAINDER above is UNCHANGED but is no longer tracked here: it is
[[PB204]], `kind: defect`, `status: open`, `rejects_legal_source: true`. It is not an owner question — the
no-deferral rule makes implementation the default and the campaign order is the director's call — and its
interim posture was VERIFIED loud at the landing (`error COBOLNET1688 … a variable-length group has no fixed
record window … deferred`), never silent and never a backend failure.

Four review-fleet findings landed against arm C's own work in the same pass:

- **The §13.18.16.3 SR3 arm read `n.Occurs is not null`**, which is the FIXED physical capacity and NULL for a
  Format-4 dynamic-capacity table — so BOTH dynamic shapes escaped the new compile-time screen (the table
  itself and any leaf beneath it) and reached the ReportWriterEmitter runtime loud. SR7 structurally cannot
  cover the first: §8.5.1.12.1 defines "variable-length group" over items SUBORDINATE to the group. Now
  `n.IsTable`, with `pb177-control-dynamic-table` and `pb177-control-dynamic-subordinate` as witnesses.
- **`CONTROL IS <index item>` is illegal source** — §13.18.60.3 SR10 closes the set of contexts in which an
  index data item may be referenced explicitly, and §8.4.5 makes a data-division clause naming a data item
  exactly such a reference. It was a runtime loud; now **COBOLNET1700** at bind, witness
  `pb177-control-index`. The FLOAT half of that same guard stays loud and is NOT a syntax violation — the
  prior-control RESTORE channel has no float arm — and the emitter's message now says so, per limb, instead
  of describing one limb for three.
- **The §13.18.44.3 SR5 citation repair was itself one-sided.** SR5 is FOUR sentences; the repair read the
  fourth and concluded "NO syntax rule literally names" the OCCURS-bearing data-name-2. Sentence 1 names it
  outright, over EVERY OCCURS format — and the plain fixed-OCCURS object (`05 T PIC X(3) OCCURS 4. 05 R
  REDEFINES T PIC X(12).`) was screened NOWHERE and compiled clean. Now **COBOLNET1701** per written entry;
  COBOLNET1525 is narrowed to the SUBJECT that is itself a dynamic table, the one side no syntax rule names.
  Four witnesses now stand either side of the 1525/1698/1701 boundaries.
- **`pb177-control-occurs` established its SR3 premise with a level-01 OCCURS**, which §13.18.38.3 SR1a
  forbids outright — a witness leaning on a second, unscreened gap. Re-authored onto an 05-level entry; the
  three reject-at-85 CONTROL witnesses also swapped `GOBACK` for `STOP RUN` so no leg is rejected at 85 for a
  reason other than its own rule.
