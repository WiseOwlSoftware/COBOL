# PB3084 — the lifecycle survey takes prose for a branch field

## Found (2026-10-11 19:25 PDT, the loop's land unit for train 1065)
`python scripts/prune_worktrees.py --brief` (and `session-probe`) listed
`WAITING FOR REVIEW worktree-wf_aba5c7ac-b61-2 — w1062g-PB3061-report.md: Status DONE, no review stamp`. That report's
header field is `Branch: gate-failfast-PB3061`, and that branch landed in train 1063 (`cb957b73c G PB3061 items 1 and 2`).
Its Notes paragraph, still inside the header (everything before the first `## `), says "so B's branch
`worktree-wf_aba5c7ac-b61-2` is HELD and lands THROUGH this one". The land unit's step 2 would have dispatched an Opus
`cobol-reviewer` on group B's branch, whose content reached main inside group G.

## Mechanism (`scripts/prune_worktrees.py`, `BRANCH_FIELD` and `newest_report`)
`BRANCH_FIELD = (?i)\bbranch\b[\s:*`(]*(<name>)` matches the word `branch` followed by ANY word, at any position in the
header. `newest_report` treats every match as a branch the report is ABOUT (`branch in named`). Probed on today's
reports (the regex applied to each header exactly as `report_index` cuts it):

| report | names its header field gives | what `BRANCH_FIELD.findall` returns |
|---|---|---|
| `w1062g-PB3061-report.md` | `gate-failfast-PB3061` | `gate-failfast-PB3061`, `was`, `worktree-wf_aba5c7ac-b61-2` |
| `w1064g-PB3077-report.md` | `plan-report-branch-PB3077` | `beside`, `from`, `plan-report-branch-PB3077` |
| `w1064a-PB2987-report.md` | `worktree-wf_7ea6bc1f-05f-1` | `worktree-wf_7ea6bc1f-05f-1` |

`was`, `beside` and `from` are harmless only because no branch has those names; the prose mention of a real branch is
the defect. The docstring's own example (w1037r's report naming `landing-lease` as its BASE) was fixed by preferring the
field over a bare word, but a prose `branch `x`` still reads as a field.

## Harm
- A land unit dispatches a reviewer (an Opus transcript) on a branch whose work is already on main; its CLEAN stamp
  would then make the branch WAITING TO LAND and the landing lane would run `enqueue.py land` on work main already
  holds (a merge that conflicts with G's later edits to the same files, or an empty pull request).
- The wrong state is always a NON-landed one. `lifecycle` decides LANDED by content (`row.content in LANDED_CONTENT`)
  before it reads `row.report`; the report only chooses among the other states. With the field rule b61-2 reads
  DECISION from its own `w1062b-PB3022-report.md` (Status SPLIT), not LANDED: its work reached main inside train 1063
  as G's patch, which no content class saw (it was never a train-manifest member, so `carried()` cannot class it).
- The reverse direction is the same rule: any report that mentions another branch in its header prose (a predecessor,
  a held branch, a contained one) can be the "newest report" for that branch and give it the wrong lifecycle state.

**Containment is not part of this defect (resume unit, 2026-10-12).** The review (R1-1) asked whether a predecessor
landed THROUGH a successor can ever read LANDED. It can, for every landing since the trains: `contained()` reads a
branch whose tip is an ancestor of a waiting carrier's tip IN FLIGHT ("contained in X: its work lands through that
branch"), and since kb/Work PB3023 a landing is a merge commit, so once the carrier lands the predecessor's tip is on
main and the content test reads it LANDED. Only a train-era patch landing escaped both; b61-2 was one, and it is gone
(`git branch --list worktree-wf_aba5c7ac-b61-2` is empty on 2026-10-12).

## Fix shape (one rule, one place)
kb/Work PB3077 (landed) gives `plan_wave.py` a field-position `BRANCH_FIELD`: `(?im)(?:^|·)[ \t]*\**branch:\**\s*`?(<name>)`
— the start of a header line, or after the template's `·` separator. `prune_worktrees.report_index` already reuses
`plan_wave`'s reader "never forked"; the survey must reuse that same field rule instead of keeping a second, looser one
(delete `prune_worktrees.BRANCH_FIELD`; use `plan_wave.BRANCH_FIELD.findall`).

**The field-position rule governs, and two notes said otherwise (review R1-2).** kb/Work PB2607's fix shape read the
branch "the way prune_worktrees' BRANCH_FIELD already does", with ONE reader for planner and survey, and PB3077's sweep
kept the survey's wider `\bbranch\b` rule "for membership, not identity". Both readings are wrong for the same reason:
a header that MENTIONS a branch (w1062g's Notes naming b61-2) is not ABOUT it, and treating a mention as membership hands
the mentioned branch the report's state, the harm above. PB2607 now points here for the one-reader item (its branch
half landed with PB3077). The landing that fixes this note also corrects PB3077's sweep sentence (a landed note's record
of a rule the fix deletes). Before switching, measure every report
header under `<coord>\scratch\reports` for the forms the survey's docstring names (`Branch: x`, `**branch:** `x``,
`(branch x)`): a form the field rule does not cover is either added to the ONE rule in `plan_wave` or shown unused. Pair
it with a drift test that the two modules share one object (`prune_worktrees` holds no regex of its own for the field),
and a case built from `w1062g`'s header: its newest-report match is `gate-failfast-PB3061` only.

## Third occurrence (enqueue unit 2026-10-15): a prose bullet above the first heading

`notes-PB3040-PB3160-20261014` (an ANCESTOR of `design-PB3160-conformance-suite`, landing through it) was listed WAITING
FOR REVIEW under `w1080y-PB3160-report.md`. That report's header is about `design-PB3160-conformance-suite` (its
`Branch:` field), but line 22, above the first `## ` heading, is the prose bullet "- Contains branch
`notes-PB3040-PB3160-20261014` (its report w1080z was withdrawn: this landing carries it)", which `BRANCH_FIELD`
(`scripts/prune_worktrees.py` line 471) reads as a branch field. Harm this time: the enqueue unit was told to dispatch a
reviewer at the notes branch's tip 27f1be507, and a reviewer that stamps CLEAN there would overwrite the design
branch's own `Review: FINDINGS 4 ... 81a3cd56c` stamp in the same report. The enqueue unit did not dispatch it
(containment checked with `git merge-base --is-ancestor`). Same mechanism; the fix (the field-position rule) must reject
a `branch <name>` inside a bullet or sentence anywhere in the header, and the self-test list gains this header
(`w1080y-PB3160`, line 22).

rule, shared with `plan_wave.BRANCH_FIELD`) must also reject a `branch <name>` that sits inside a sentence of the
header line; the self-test case list gains this header (`w1071f-PB3120`, line 4).
