# PB3263 — PB3160 slice notes have no site block

**Mechanism.** PB3242 made a note's declared file set its structured site blocks (a bold `Code site` / `Site` / `Sites` label's paragraph and list). The PB3160 slices (PB3172, PB3173 and their siblings) carry only `**Prerequisites:**` / `**Scope:**` prose, so they declare nothing and two slices that touch the same files collide silently in `plan_wave.py`.

**Repro.** `python scripts/arch/member_index.py --note PB3172` lists no sites. Source: report `w1090a-PB3242-report.md`, lead 1.

**Second population: the PB3353 campaign (wave 1117, 2026-10-18 02:20 PDT).** `plan_wave.py --cluster PB3353` planned eight groups and six of them (C PB320, D PB604, E PB671 + PB707, F PB675, G PB680, H PB700) with `file_set: []`: `make_dispatch_specs.py` recorded `0 files` for each in `inflight-groups.json`, and their specs' root reads "the files the notes name". The same run deferred PB1278 and PB1253 for a `docs/CONFORMANCE.md` collision and PB2220, PB2775, PB2750, PB2752, PB2171 and PB3251 for `DataBinder.cs` / `BinderDriver.cs`, because those notes declare sites; the six with none were checked against nothing. A census of PB3353's open blockers through `work.note_sites` (scratch script `E:\COBOL-coord\scratch\w1117-sites-census.py <repo> PB3353`): 42 open, **30 with no site block** (PB320 PB604 PB670 PB671 PB675 PB680 PB700 PB707 PB722 PB804 PB822 PB870 PB1154 PB1563 PB1571 PB1587 PB1603 PB1629 PB1636 PB1840 PB1880 PB1917 PB2485 PB2500 PB2503 PB2509 PB2510 PB2512 PB2556 PB3350), 12 with one. Most are notes filed before PB3242 defined the block. The harm is a wasted landing, not a wrong answer: two groups that edit one file both run, and the second to land stops on a conflict and takes a finisher; the partition also stops protecting the in-flight work these groups meet.

**Third population: the PB3330 engine (wave 1118, 2026-10-18), and the landing check it stopped.** At 05:00
`plan_wave.py` recorded every wave-1118 group with `0 files`, because their notes' code sites were files the engine
had not yet created. At 15:28 `enqueue.py land` on `worktree-wf_14a1e62b-326-32` (PB3334, reviewed CLEAN) ended exit
3. The branch also closes the R3 notes PB2222 and PB2342, and with its own group's set empty, `landing_check.py` bound
the whole branch to those two notes' sets, "computed now". It then stopped on "R3 work (PB2222, PB2342) changed 4
file(s) outside its declared file set": `RecordFraming.cs`, `RuntimeAbiPinDriftTests.cs`, `DyingPageMedium.cs`,
`PendingStoreCases.cs` (log `E:\COBOL-coord\logs\land-lane-worktree-wf_14a1e62b-326-32-20261018T220807307653Z.log`,
line 10). The message told the reader to file "a member_index hole", which was not the cause. The Mythos lane
unblocked it by hand at 15:45: it declared each wave-1118 group's `file_set` from its branch's diff (A4 92 files, A5
59, A6 134; wave 1123 B 32; wave 1125 A 21), re-rendered the specs and upserted the dispatch ledger. So a reviewed
branch waited about 20 minutes on bookkeeping, and the same empty set reached a new place: the landing check, besides
the planner's partition.

**Fix shape (widened: one rule for every campaign, so the third campaign is automatic).** (1) The planner treats an empty declared set as UNKNOWN, never as "collides with nothing": it plans such a group only alone on its subsystem or names it in the plan table as unpartitioned (`plan_wave.py`, `collision_set`), so the silence ends. (2) `work.py check` refuses an open note that names a campaign in `cluster:` (PB3160, PB3353, any later one) and declares no site block, instead of a rule per cluster. (3) Backfill a `**Sites:**` paragraph in each note listed above and in the PB3160 slices (each slice's author knows its files from `DESIGN-conformance-suite.md` section 13); a note whose implementer lands it first needs none. (4) The landing check treats an empty recorded set the same way,
as UNKNOWN: it re-declares the group's set from the branch's own diff before checking (the Mythos lane's hand fix,
made mechanical), and it never stops a branch on another note's computed set for that reason. Its stop message names
the real cause, an empty recorded set, not a member_index hole.
