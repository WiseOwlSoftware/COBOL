# PB3263 — PB3160 slice notes have no site block

**Mechanism.** PB3242 made a note's declared file set its structured site blocks (a bold `Code site` / `Site` / `Sites` label's paragraph and list). The PB3160 slices (PB3172, PB3173 and their siblings) carry only `**Prerequisites:**` / `**Scope:**` prose, so they declare nothing and two slices that touch the same files collide silently in `plan_wave.py`.

**Repro.** `python scripts/arch/member_index.py --note PB3172` lists no sites. Source: report `w1090a-PB3242-report.md`, lead 1.

**Second population: the PB3353 campaign (wave 1117, 2026-10-18 02:20 PDT).** `plan_wave.py --cluster PB3353` planned eight groups and six of them (C PB320, D PB604, E PB671 + PB707, F PB675, G PB680, H PB700) with `file_set: []`: `make_dispatch_specs.py` recorded `0 files` for each in `inflight-groups.json`, and their specs' root reads "the files the notes name". The same run deferred PB1278 and PB1253 for a `docs/CONFORMANCE.md` collision and PB2220, PB2775, PB2750, PB2752, PB2171 and PB3251 for `DataBinder.cs` / `BinderDriver.cs`, because those notes declare sites; the six with none were checked against nothing. A census of PB3353's open blockers through `work.note_sites` (scratch script `E:\COBOL-coord\scratch\w1117-sites-census.py <repo> PB3353`): 42 open, **30 with no site block** (PB320 PB604 PB670 PB671 PB675 PB680 PB700 PB707 PB722 PB804 PB822 PB870 PB1154 PB1563 PB1571 PB1587 PB1603 PB1629 PB1636 PB1840 PB1880 PB1917 PB2485 PB2500 PB2503 PB2509 PB2510 PB2512 PB2556 PB3350), 12 with one. Most are notes filed before PB3242 defined the block. The harm is a wasted landing, not a wrong answer: two groups that edit one file both run, and the second to land stops on a conflict and takes a finisher; the partition also stops protecting the in-flight work these groups meet.

**Third population: the PB3330 engine (wave 1118, 2026-10-18), and the landing check it stopped.** At 05:00
`plan_wave.py` recorded every wave-1118 group with `0 files`, because their notes' code sites were files the engine
had not yet created. At 15:28 `enqueue.py land` on `worktree-wf_14a1e62b-326-32` (PB3334, reviewed CLEAN) ended exit
3 on "R3 work (PB2222, PB2342) changed 4 file(s) outside its declared file set (computed now)": `RecordFraming.cs`,
`RuntimeAbiPinDriftTests.cs`, `DyingPageMedium.cs`, `PendingStoreCases.cs` (log
`E:\COBOL-coord\logs\land-lane-worktree-wf_14a1e62b-326-32-20261018T220807307653Z.log`, line 10). The mechanism, read
from `landing_check.py` (about lines 193-206), is not the empty recorded set. The branch also closes the R3 notes
PB2222 and PB2342, and NO dispatch-ledger group named them, so they were `unrecorded`. Their declared set was then
computed now from those notes' sites (`declared_for(unrecorded)`), which predate the engine's files. The check charges
work to notes per commit (`commit_work`, PB2703, PB3180), so the commits naming both PB3334 and the R3 notes charged the
engine files they touched, files that already existed at the base, to the R3 work, outside that computed set. The
PB3334 group's empty recorded set was never consulted. The message told the reader to file "a member_index hole",
which was not the cause either. The Mythos lane unblocked it by hand at 15:45: it upserted group A4 with notes
`[PB3334, PB2222, PB2342]` and 92 files (and declared every wave-1118, 1123 B and 1125 A group's `file_set` from its
branch's diff), which moved the R3 notes into the ledger's `recorded` arm. A reviewed branch waited about 20 minutes
on bookkeeping.

**The cost on the second population, 2026-10-18 18:17.** Wave 1126 C (PB1587, one of the 30 notes listed above with
no site block) was recorded at 14:02 with `0 files`, so the planner saw no collision with the in-flight engine of wave
1118. Its branch `worktree-wf_e873df80-6b5-22` landed as PR #265 and conflicted with the engine's `-326-19` in six
files, including `IndexedConnector.WholeStore.cs`, which the engine deletes. The Mythos lane then needed a fourth
merge round on `-326-19`. The landing check could not have stopped it: it partitions only when the shared file is R3
work on one side (`landing_check.py` docstring, item 2), and neither side's shared files were. Its dispatch order
would have been inverted anyway (PB3392).

**Why it is in cluster PB3353 (operator, 2026-10-18 20:05).** Wave 1127 of the campaign could not launch. Five of its
eight groups had empty file sets, so the planner could not tell which of them met the engine's in-flight files or
`docs/CONFORMANCE.md`, and the unit released them all (report `w1127z-PB3394-report.md`). The campaign cannot plan
safely until the planner reads an empty set as unknown, so this note is the campaign's prerequisite. It belongs in
one `plan_wave.py` group with PB3392, PB3394, PB3114 and PB3369, which share that file. The owner's 2026-10-17
scope covers it: "let's also include all fix-lane work required to put all this work to bed".

**Fix shape (widened: one rule for every campaign, so the third campaign is automatic).** (1) The planner treats an empty declared set as UNKNOWN, never as "collides with nothing": it plans such a group only alone on its subsystem or names it in the plan table as unpartitioned (`plan_wave.py`, `collision_set`), so the silence ends. (2) `work.py check` refuses an open note that names a campaign in `cluster:` (PB3160, PB3353, any later one) and declares no site block, instead of a rule per cluster. (3) Backfill a `**Sites:**` paragraph in each note listed above and in the PB3160 slices (each slice's author knows its files from `DESIGN-conformance-suite.md` section 13); a note whose implementer lands it first needs none. (4) The landing check's `unrecorded` arm: an R3 note
that a recorded group's branch closes (an implementer fixed it on the way, MANDATORY-PRACTICES I9) is checked against
that group's recorded set, never against a set computed now from sites that predate the group's own new files, and an
empty recorded set reads UNKNOWN and is named so, never "collides with nothing". The stop message names the arm it
came from instead of a member_index hole. A self-test pins the 15:28 shape: a recorded group whose commits also close
two unrecorded R3 notes and touch files that already existed at the base (the check stops only on those, `existed` via
`cat-file -e base:path`).


## Landed (wave 1131 G, branch `worktree-wf_65e0b527-80e-17`)

Re-probed on the branch's base `c82c9213f`: `work.note_sites` found no site block in 198 open notes naming 218
clusters, 24 of them in PB3353 and 6 in PB3160; `plan_wave.inflight_file_sets` dropped a ledger group recorded with no
files, and `plan()` met an empty group set with nothing. Each item of the fix shape, as built:

1. **The planner reads an empty set as UNKNOWN** (`plan_wave.collision`, the one meeting rule; `subsystems`). Two known
   sets meet on a shared file. An empty set (a group whose notes declare no file under a campaign root, a dispatch the
   ledger recorded with none) meets the other side on a shared SUBSYSTEM, the notes' `area:` (case-folded), and meets
   everything when that is unknown too. A meeting by subsystem waits even for finished work (a continuation would merge
   an unrelated branch). Within a wave an unknown group is planned alone on its subsystems, by the same rule: it follows
   EVERY group it meets, waits for a later wave when they lie in two chains, and a later group that meets it follows it
   (review finding w1131g R1-1: following only the LAST group ran it beside an earlier one in another chain). A 0-file dispatch stays in flight with its notes (the branch survey's
   in-flight slugs see it too). A finisher's set includes the files of the branch it continues. The plan table and the
   spec name the group `UNPARTITIONED` and ask for a `**Sites:**` paragraph. The external-repository slices owner carries
   its notes, so it has subsystems. `test_plan_wave.py` section 12.
2. **`work.py check` refuses a note filed into a cluster without a site block** (`sites_problems`), from
   `SITES_REQUIRED_FROM` = PB3443 (the next unallocated id when it landed) on, and names no campaign: any cluster is a
   campaign once an operator runs it. A `decision` note is exempt; `**Sites:** none (why)` declares a note that changes
   no code file (`NoteSites.declared`). A rule over every open note would have refused 198 at once, most in idle
   clusters; those stay readable as UNKNOWN. The registrar brief asks for the block.
3. **Backfill**: 27 open notes of the running campaigns (PB3353: PB670 PB1636 PB2509 PB2510 PB2512 PB2556 PB3337 PB3338
   PB3340 PB3350 PB3369 PB3372 PB3382 PB3383 PB3385 PB3392 PB3410 PB3411 PB3414 PB3415 PB3438; PB3160: PB3178 PB3179
   PB3319 PB3320 PB3321 PB3322) got a `**Sites:**` block from their own text; PB3353 is left with its two decision notes
   only. The rest of the original 30 had landed. PB3382, PB3385, PB2512, PB3369, PB3372 and PB3383 landed on main (PRs
   #302, #303, #304, #305, #306, #311) while this branch waited to land; merging main in, their blocks were rewritten to
   name the files those landings changed.
4. **The landing check** (`landing_check.py` arm 1): an R3 note no entry records that the landing's own recorded
   dispatch closed on the way is checked against that dispatch's recorded set, never a set computed now; a consulted
   group recorded with no files is UNKNOWN, named in a warning, never a stop; the stop names the arm its set came from
   instead of "a member_index hole". Self-test PB3263a-d pins the 15:28 shape.
