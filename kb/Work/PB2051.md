# PB2051 — LANDED — a parameterized definition binds as itself for its data, environment and headers

## Repro

`E:\COBOL-coord\scratch\w1019d2\p\skel_unbound.cob`, `--std 2023`: a `CLASS-ID. CSKEL INHERITS FROM BASE USING ELT.`
whose OBJECT WORKING-STORAGE holds `01 G. 05 B BASED PIC X.` compiles with exit 0. The same entry in an ordinary
class or program draws COBOLNET2404 (§13.16.3 SR16: "The level number of such data description entries shall be
1 or 77"). A skeleton REPOSITORY entry is not asked either: `FUNCTION ABS INTRINSIC` in the skeleton at
`--std 2002` compiles.

## Code site

`src/Cobol.Net.Compiler/Oo/OoExpansion.cs#Expand` keeps every parameterized definition in `skeletons` and out of
the class table; the only per-skeleton check is the formal-parameter screen in `AddSkeleton` (which since kb/Work
PB1744 also declares the parameter-names through a throwaway `DataBinder.DeclareParameterNames`). No binder binds
the skeleton's data division, procedure division or REPOSITORY, so every syntax rule over those elements is asked
only of an expansion, and a skeleton nothing expands is never asked at all.

## Why it is not fixed in place

It is a redesign beyond group D2's slice: binding a skeleton needs its formals treated as opaque class names
(§11.3.4 GR6: a parameter-name may stand only where an object-class-name or interface-name is permitted) so the
body can bind without an actual. It shares the root with kb/Work PB1784 (the definition-rule layer over every
parsed definition, skeletons included) and the skeleton half of kb/Work PB1505; the fix should land with or after
PB1784's layer so that one pass visits every parsed definition.
