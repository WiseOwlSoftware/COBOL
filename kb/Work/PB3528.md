## What happens

Wave unit 1150 (2026-10-22 ~13:05) ran
`plan_wave.py --from-budget --borrow-days 0 --cluster PB3353` and a fix-lane `--dry-run`: both planned **0 groups**.
The previous handoff expected the planner to plan the finishers of the two SPLIT branches of wave 1141:

- `worktree-wf_31aba3ec-d06-1`: report `w1141a-PB3338-report.md`, Status SPLIT (PB3338, PB3492);
- `worktree-wf_31aba3ec-d06-2`: report `w1141b-PB3493-report.md`, Status SPLIT (PB3493, PB3494).

`plan()` builds a finisher group for each (the `FINISH_STATUSES` arm), then runs THE FILE-SET PARTITION. A finisher
is exempt only from the branch it CONTINUES (`x.branch in g.continues`). Each SPLIT branch is idle past `--min-age`,
so `prune_worktrees` reads it DECISION, which `classify_inflight` treats as RUNNING. The two branches both change
`docs/CONFORMANCE.md` (and `docs/rearchitecture/DESIGN-runtime-library.md`), so:

- PB3338's finisher meets d06-2 [DECISION] → waits;
- PB3493's finisher meets d06-1 [DECISION] → waits.

Neither is ever planned. The SPLIT branches stay DECISION rows indefinitely, and every note whose file set touches
`docs/CONFORMANCE.md` (PB1278, PB3340, PB3460, PB3499, PB3513, PB3497, PB3501, PB3518 in this run) waits behind them
too. The planner's text says a DECISION owner is "unlanded work no session has decided ... the collision names it,
so the operator decides it", but the planner itself has already decided these two: a SPLIT report means "plan its
finisher" (kb/Work PB2575). The loop therefore cannot make progress without a hand decision, and nothing tells the
operator that the deadlock is mutual.

(Other holds in the same run are not this defect: PB3338 also meets `worktree-wf_8c44feac-62f-3` [IN FLIGHT] on
`tests/version-matrix/traceability-inventory.json`, and PB3493 meets `worktree-wf_36fbfc86-472-1` [DECISION], which
is to be abandoned once `notes-pb1278-abandon-20261022` (#393) merges.)

## Expected

A branch whose newest report is SPLIT or NOT STARTED, for which this plan builds a finisher, is work the planner has
decided, not undecided work. Two such finishers that share files are related work on the same files: the second is a
successor (`after:`) of the first, merging its branch, exactly as two same-file fix-lane groups are chained. A
finisher planned this wave must not be held by another branch that this same wave is also finishing.

## Where

`scripts/orchestrator/plan_wave.py`, `plan()`: the partition block (`met = {o: x for o, x in busy.items() ...}`)
and `classify_inflight` (DECISION → RUNNING). Fix shape: before the partition, collect the branches every planned
finisher continues; an in-flight owner whose branch is in that set is not RUNNING to the other groups of this wave,
and a group meeting it links as a successor of the finisher that continues it (the chain rule already used for
same-file groups). Pair it with a `test_plan_wave.py` case: two SPLIT reports on two DECISION branches sharing one
file plan two chained finishers, not zero.
