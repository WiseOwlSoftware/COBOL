## What happens

Wave unit 1150 (2026-10-22 ~13:05) ran
`plan_wave.py --from-budget --borrow-days 0 --cluster PB3353` and a fix-lane `--dry-run`: both planned **0 groups**.
The previous handoff expected the planner to plan the finishers of the two SPLIT branches of wave 1141:

- `worktree-wf_31aba3ec-d06-1`: report `w1141a-PB3338-report.md`, Status SPLIT (PB3338, PB3492);
- `worktree-wf_31aba3ec-d06-2`: report `w1141b-PB3493-report.md`, Status SPLIT (PB3493, PB3494).

`plan()` builds a finisher group for each (the `FINISH_STATUSES` arm), then runs THE FILE-SET PARTITION. A finisher
is exempt only from the branch it CONTINUES (`x.branch in g.continues`). Each SPLIT branch is idle past `--min-age`,
so `prune_worktrees` reads it DECISION, which `classify_inflight` treats as RUNNING. The two branches both change
`docs/CONFORMANCE.md` (and `docs/rearchitecture/DESIGN-runtime-library.md`), so:

- PB3338's finisher meets d06-2 [DECISION] → waits;
- PB3493's finisher meets d06-1 [DECISION] → waits.

Neither is ever planned. The SPLIT branches stay DECISION rows indefinitely, and every note whose file set touches
`docs/CONFORMANCE.md` (PB1278, PB3340, PB3460, PB3499, PB3513, PB3497, PB3501, PB3518 in this run) waits behind them
too. The planner's text says a DECISION owner is "unlanded work no session has decided ... the collision names it,
so the operator decides it", but the planner itself has already decided these two: a SPLIT report means "plan its
finisher" (kb/Work PB2575). The loop therefore cannot make progress without a hand decision, and nothing tells the
operator that the deadlock is mutual.

(Other holds in the same run are not this defect: PB3338 also meets `worktree-wf_8c44feac-62f-3` [IN FLIGHT] on
`tests/version-matrix/traceability-inventory.json`, and PB3493 meets `worktree-wf_36fbfc86-472-1` [DECISION], which
is to be abandoned once `notes-pb1278-abandon-20261022` (#393) merges.)

## Expected

A branch whose newest report is SPLIT or NOT STARTED, for which this plan builds a finisher, is work the planner has
decided, not undecided work. Two such finishers that share files are related work on the same files: the second is a
successor (`after:`) of the first, merging its branch, exactly as two same-file fix-lane groups are chained. A
finisher planned this wave must not be held by another branch that this same wave is also finishing.

## Where

`scripts/orchestrator/plan_wave.py`, `plan()`: the partition block (`met = {o: x for o, x in busy.items() ...}`)
and `classify_inflight` (DECISION → RUNNING). Fix shape: before the partition, collect the branches every planned
finisher continues; an in-flight owner whose branch is in that set is not RUNNING to the other groups of this wave,
and a group meeting it links as a successor of the finisher that continues it (the chain rule already used for
same-file groups). Pair it with a `test_plan_wave.py` case: two SPLIT reports on two DECISION branches sharing one
file plan two chained finishers, not zero.

## Landed

Operator, 2026-10-22 ~14:00 PDT. `plan()` in `scripts/orchestrator/plan_wave.py`: before the partition loop it maps
each branch to the group of this wave that continues it (`finisher_of`). In the partition, an in-flight owner whose
branch another group of this wave continues is no longer a hold: the group links after that group once it is placed,
and the owner leaves `met`. The earlier of two such finishers goes ahead; the later becomes its successor (`after:`) and
merges its branch. A branch no group of this wave continues still holds, unchanged. The module docstring's partition
paragraph states the rule.

Witness: `test_plan_wave.py` (PB3528 block) plans two SPLIT reports whose branches share `docs/CONFORMANCE.md`: both
finishers are planned, the second after the first, neither waits; and an undecided branch this wave does not finish
still holds a group on its files. Red before the fix (both PB5 and PB9 waiting), 332/332 after. On the live state
(`--cluster PB3353 --dry-run`, 13:5x): wave 1151 plans A (PB3338 + PB1278, PB3460, PB3492, d06-1's finisher), A2 after
A (PB3493 + PB3494, d06-2's finisher) and A3–A6 behind them, 1.62 of 6.00 points; before the fix it planned 0 groups.

Finisher, 2026-10-22: the landing (land_lane attempt 20261022T210722Z, `enqueue.py land` at e14563d6fc88) stopped GATE
RED on the Linux self-tests leg alone: the witness above got PB5's finisher as the successor (`after` empty on PB9,
PB5's letter A2). Root cause: `load_reports` sorted by `(wave, mtime)` only; the fixture's two reports tie on both
(`returned()` stamps one mtime), so `sorted`'s stability left them in `Path.glob` order, the directory enumeration
order: the name on NTFS, a hash order on ext4. That order decides each note's newest report, the order finisher groups
are built in and so which of two chained finishers leads: the plan depended on the host. Fix: the file name is the
third sort key, making the order total. Witness: a check reads the reports through a reversed `Path.glob` and expects
name order (red without the fix on Windows as well, 333/333 with it). Sibling sweep over every `st_mtime` and every
unsorted `glob`/`iterdir`/`listdir` in `scripts/orchestrator/`, `scripts/prune_worktrees.py` and the workstream skill:
`self_tests.py`'s PASS lookup breaks its mtime tie by path, the rest are order-insensitive (sums, deletions, counts).
One sibling elsewhere, `scripts/arch/r2_inputs.py` `perf_input`, picks the newest performance baseline by mtime,
which a checkout sets: filed as PB3532.

Follow-up (branch review R1-1, branch `fix-pb3528-one-sided-meeting`): a meeting can be ONE-SIDED, the earlier group
meeting the later finisher's branch while the later finisher never meets the earlier group's. The exemption now records
that the not-yet-placed finisher must follow the group (`must_follow`), and the finisher links after it when placed, so
the two never run beside each other. Test: red before the follow-up (both planned in parallel), 338/338 after.
