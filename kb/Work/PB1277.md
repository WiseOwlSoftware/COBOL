## Measured

### Finding record-clause — 13.18.43.4 GR3, GR8, GR9 (and so 13.18.43.3 SR3/SR4) (wrong-answer; rows GR-13.18.43.4-3, GR-13.18.43.4-8, GR-13.18.43.4-9)

**Mechanism.** The §13.18.43.4 GR8 byte count is not computed in bytes. FileModel.MinRecordSize and MaxRecordSize are built on DataItem.ImageWidth, whose elementary arm returns pic.Length (character positions) for a NATIONAL item, stored at 2 bytes per character (D-N1). MinRecordSize is also a second recursion that re-sums leaves, so it ignores the §8.5.1.6.3 bit packing that ImageWidth's group arm applies. The runtime counts bytes correctly, so the binder and the connector disagree.

**Repro.** out13/probe/record-clause/p8.cob: FD F1 RECORD IS VARYING IN SIZE FROM 16 TO 40. 01 R1. 05 A PIC X(10). 05 C PIC N(5). (BYTE-LENGTH 20) -> COBOLNET2010 'describes 15 bytes'. p10.cob: RECORD IS VARYING IN SIZE FROM 1 TO 12 over 01 R2 PIC N(10) (20 bytes) -> compiles clean. p7.cob: RECORD CONTAINS 10 over PIC N(10) -> compiles clean. p9.cob: RECORD IS VARYING IN SIZE DEPENDING ON L over 01 R2 PIC N(10), L=12, WRITE -> FS=00. p11.cob: RECORD IS VARYING IN SIZE DEPENDING ON L over 01 R2. 05 B1 PIC 1(3) USAGE BIT. 05 B2 PIC 1(3) USAGE BIT. (BYTE-LENGTH 1), L=1 and L=2 -> FS=44 both.

**Expected, from the standard.** GR3: size is 'the number of bytes required to store the logical record, regardless of the types of characters used'. p8 compiles (20 >= 16). p10 and p7 are rejected under SR4/SR3 (20 > 12, 20 > 10). p9: GR9 min = 20 bytes, so L=12 answers 44 (GR14 a). p11: record is 1 byte (GR4), min = max = 1, so L=1 answers 00.

**Observed.** Legal source rejected (p8). Illegal source accepted (p10, p7). A national file accepts short records (p9). For the bit record, min 2 > max 1, so no WRITE of that file can ever succeed (p11).

**Code site.** src/Cobol.Net.Compiler/Binding/Model/FileModel.cs#MinRecordSize, #MaxRecordSize, #VaryMin; src/Cobol.Net.Compiler/Binding/Model/DataItem.cs#ElementaryImageWidth (national: return pic.Length); consumers src/Cobol.Net.Compiler/Binding/RecordClauseRules.cs#Screen

### Finding sort-merge-file-description-entry — §13.4.6.4 GR1; §13.18.43.4 GR1/GR3/GR8; §13.18.43.3 SR3/SR4 (rejects-legal-source; rows GR-13.4.6.4-1)

**Mechanism.** Record-size rules measure a record in carrier character positions (DataItem.ImageWidth) instead of bytes, so a national record counts half its size against the RECORD clause integers

**Repro.** SELECT SRT ASSIGN TO "srt.tmp". SD SRT RECORD IS VARYING IN SIZE FROM 6 TO 8 CHARACTERS. 01 SRT-REC. 05 SK PIC N(4). PROCEDURE DIVISION. STOP RUN.  -> rejected COBOLNET2010 "describes 4 bytes, which is fewer than the integer-2 = 6". Converse: SD SRT RECORD CONTAINS 5 CHARACTERS over PIC N(5) compiles and runs (BYTE-LENGTH(SRT-REC)=10); VARYING FROM 1 TO 5 over N(5) compiles. FD F1 RECORD CONTAINS 5 over PIC N(5) compiles too.

**Expected, from the standard.** §13.4.6.4 GR1 "The number of characters is specified in terms of bytes"; §13.18.43.4 GR1/GR3: record sizes are bytes "regardless of the types of characters used". Under D-N1 (2 bytes per national position) N(4)=8 bytes, so FROM 6 TO 8 is legal (accept); N(5)=10 bytes violates SR3 against CONTAINS 5 and SR4 against TO 5 (reject COBOLNET2010).

**Observed.** FileModel.MaxRecordSize = item.ImageWidth and MinRecordSize sums ImageWidth; RecordLayout.PhysicalWidth documents that ByteWidth differs from ImageWidth exactly for national. The alphanumeric twin (PIC X(10) under CONTAINS 5) is rejected correctly, so the screen is live and only its unit is wrong. Both harms: a legal national record is refused, and an oversize one is accepted. The SORT key screen (COBOLNET0874) already counts in bytes, so the two checks disagree on the same record.

**Code site.** src/Cobol.Net.Compiler/Binding/Model/FileModel.cs#MaxRecordSize, #MinRecordSize (consumed by RecordClauseRules.Screen, and by VaryMin/RecordMax)
