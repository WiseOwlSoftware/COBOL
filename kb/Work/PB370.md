# PB370 — the witness debt batch b1 leaves behind

**Rows:** `GR-14.9.27.4-25`, `GR-14.9.30.4-29`, `GR-14.9.41.4-9`, `GR-14.9.41.4-L2.1`, `GR-14.9.49.4-5`,
`GR-14.9.49.4-11`, `GR-14.9.49.4-15`.

⚠ **These are not defects in the compiler.** Every one was derived from the rule text, probed, and found to
behave as the rule requires. They are held open because a verdict needs its evidence: a rule verified by an
agent's probe and by nothing on disk is one refactor away from being unverified again. They are this batch's
input to the golden lane, and each row below names exactly what its golden must assert.

## Group A — the witness on disk asserts something WEAKER than the rule

**`GR-14.9.49.4-15`** (EXCEPTION-OBJECT references the exception object on entry to a Format-4 declarative). GR15
is an IDENTITY claim — §8.8.4.2.15 makes the relation true *if the object referenced by identifier-3 is the same
object that is referenced by identifier-4*. `conformance:2002/oo_ec_raise_object` asserts only
`IF U NOT = NULL DISPLAY "REGISTER-SET"`, and its golden line `REGISTER-SET` is satisfied by ANY non-null object —
so a regression that set the register to the WRONG object (SELF, a fresh instance, the activating program's
object) would keep the golden green. **The golden must compare EXCEPTION-OBJECT against the very object RAISEd.**

**`GR-14.9.30.4-29`** (a Format-2 relative READ sets the FPI from the RELATIVE KEY item; the invalid-key leg).
`conformance:2002/file_sharing` covers the SUCCESS leg only; the invalid-key leg is covered only by the
legacy-baked `KeyedIoDifferentialTests`. **The golden must read a non-existent RRN and assert '23' plus the
INVALID KEY imperative.**

**`GR-14.9.27.4-25`** (the OPEN a-b-c-d ordering: status stored, then the level-3 EC-I-O condition, then the
Format-3 PERFORM frame, then the USE tiers). Verified by probe — an absent non-optional file with a `USE AFTER
STANDARD EXCEPTION PROCEDURE ON FN` runs the declarative and reports 35 and does not create the file; the same
OPEN inside `PERFORM ... WHEN EC-I-O-PERMANENT-ERROR ... END-PERFORM` runs the WHEN body and NOT the declarative.
`conformance:2023/f3_perform_handler_turn_off_all` covers the Format-3 machinery but not the OPEN-specific
ordering. **The golden must be that pair of programs, in one file, with both orderings asserted.**

## Group B — the only witness is legacy-baked, so it characterizes rather than derives

**`GR-14.9.49.4-5`** (a file-scoped USE takes precedence over a mode-scoped one). Re-measured on the pinned
binary across the plain `__IoCheck` path, the EC `__IoCheckEc` path, the outward GLOBAL walk, all four mode
phrases each with a control run, the multi-file operand form, `--std 85` and `2023`, and inside a FUNCTION
definition; the complement (an inner MODE declarative beating an outer GLOBAL FILE one, GR4 a) holds too. The
only witness, `UseDeclarativeDifferentialTests.FileScope_BeatsModeScope_OneDeclarativeOnly`, asserts against a
`DifferentialGolden` baked from the legacy oracle. **The golden must write the two declaratives in the
mode-before-file source order and assert the file-scoped one runs.**

**`GR-14.9.41.4-9`** (the relative START comparison is numeric, and the reverse search finds the LARGEST RRN
satisfying `<` / `<=`). Measured on a file with RRN 2/4/6: `KEY > 4` → REC-6; `KEY < 5` → REC-4 (**not** the
lowest, which is what proves the reverse search); `NOT GREATER 5` → REC-4; `NOT LESS 5` → REC-6; `KEY = 3` → '23'
+ INVALID KEY. **The golden must include the `< 5` case, because it is the only one that distinguishes a reverse
search from a forward one.**

**`GR-14.9.41.4-L2.1`** (§14.9.41.4 GR17 e) 1. — the FPI is set to the key VALUE of the first record satisfying
the comparison, with the record's key on the LEFT of the comparison). Measured on keys AAA100/BBB200/CCC300:
implicit EQUAL → BBB200; `> BBB200` → CCC300; `< BBB999` → BBB200 (the largest key below); `>= AAA000 WITH LENGTH
3` → AAA100. **The golden must include the partial-key leg and the reverse leg.**

## Group C — the adversarial shape cannot be built today

**`GR-14.9.49.4-11`** (where several exception conditions occur in one statement, the FIRST in order of
evaluation is the one dispatched). There is no explicit *first condition* latch: the property is EMERGENT — every
raise site dispatches inline at the point the condition occurs, and a fatal raise throws out of the statement, so
the first condition in evaluation order is the one that reaches `__EcDispatch`; `__af.Dispatched` additionally
guarantees one dispatch per raise across nested guards. ⚠ **The property is not robust to the adversarial
shape:** a statement whose FIRST condition is nonfatal and whose LATER one is fatal would dispatch on the later
one, and nothing prevents it — because an enabled NONFATAL condition raised from a runtime site never dispatches
at all (`ExceptionState.Set` only records the last exception status; the nonfatal ambient gates
EC-DATA-CONVERSION / EC-BOUND-OVERFLOW set a flag and nothing more). Whether a nonfatal condition must run the
declarative is §14.6.13.1.4's rule, not GR11's — **so this row is blocked on that separate question, and the
golden cannot be written before it is answered.** Recorded here rather than as a defect because GR11's own
sentence is satisfied by everything currently reachable.
