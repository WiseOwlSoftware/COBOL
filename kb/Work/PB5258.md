# PB5258 - note readers that skip the addenda

Since PB5110 a note is its file plus `kb/Work/<id>/*.md`, read through `work.note_text`. PB5110 converted
`groups.group_requirements`; sibling readers still open `<id>.md` alone, so a requirement, site or finding an owner
or reviewer added as an addendum is invisible to them.

1. `scripts/orchestrator/clusters.py:247` (`declare_fix_lane`): `texts = [(work_dir / f"{n['id']}.md") ...]` is the
   fix lane's declared-set reader (called at `plan_wave.py:1134`); the campaign lane (`plan_wave.py:1119`) folds the
   addenda, the fix lane does not. PB5110's finisher stated that the remaining `<id>.md` readers in
   `scripts/orchestrator` read frontmatter only; this site is a counterexample (review R3-1, medium). Effect: an
   addendum that adds a **Sites:** member to an open note does not enter the note's collision set.
2. `tools/claude-skills/skills/agent-fleet/references/orient.py:165` (and `fix_clusters.py:194` when run by hand) read one
   file per note, so an addendum is invisible to an implementer's orientation. That tree is the owner's skills repo
   (not in this checkout): the fix there is an addendum-aware reader, or a call of this repo's `work.note_text`; the
   change needs the owner's repo, so it is reported to the owner, not edited here.

**Fix direction:** one reader, `work.note_text`, for every consumer of a note's prose; then a drift test that no
script under `scripts/orchestrator` opens `kb/Work/<id>.md` for its body except through it.

**Sites:** `scripts/orchestrator/clusters.py:247` (`declare_fix_lane`), `scripts/orchestrator/plan_wave.py:1134` (`<footer>`)
