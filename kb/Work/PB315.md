# PB315 — one rule, written twice, agreed on by neither

Found by the LANDER while landing witness cluster A (2026-09-02), by applying its 49-record batch and running the
gate the writer itself tells you to run. Fixed in the same commit.

## The two arms

`tests/version-matrix/inventory-schema.json` → `kinds.DOC.anchor-exempt-verdicts` = `["DOCUMENTED-NON-SUPPORT"]`.
The rule it encodes is Annex A.1's own preamble: an A.1 item *is not required if the optional or
processor-dependent feature is not implemented*. A DOC row whose verdict DECLINES the facility therefore owes no
§7 determination to anchor and has nothing implemented to observe — it owes only its WITNESS test.

Both sides implement that rule, and only one of them reads it:

| | |
|---|---|
| C# `SpecTraceabilityInventoryDriftTests.DerivedState` | `if (AnchorObliged(r, s) && (!IsAnchored(r, s) \|\| !IsObservable(r, s))) return "GAP";` ✅ |
| Python `Schema.state_for` | `if (anchor := self.anchor_for(row)) is not None: …` ❌ |

`anchor_for` is a *function of the row* and is non-`None` for **every** DOC row; `anchor_obliged` is the
verdict-sensitive predicate. So the Python writer charged the anchor and observability costs to declined rows
that the schema data exempts, and such a row could never reach `OK` — it was required to carry a location the
same schema forbids it to claim.

⛔ The comment on the C# `AnchorObliged` asserts the invariant that was false: *"The exempt verdicts are DATA on
the kind (`anchor-exempt-verdicts`), so this side and the Python writer read ONE rule."* They did not. This is
`feedback_two_arm_dispatch` in its purest form — and `feedback_one_rule_one_place`: the exemption WAS extracted
into `anchor_obliged`, and one caller simply never switched to it.

## Why it stayed invisible

The disagreement is unobservable while no declined DOC row has a spec-derived test-ref: both sides derive `GAP`,
for different reasons. Lane 2a's derived selector stamped `DOC-A.1-84/-85/-86/-173` DOCUMENTED-NON-SUPPORT on
2026-09-02 and left them without witnesses, so the two engines still agreed. Witness cluster A's batch supplied
the witnesses — and the gate went red naming three rows:

```
3 row(s) whose stored state is not the derived one over 4311 inventory row(s):
 DOC-A.1-84: state 'GAP' but the schema derives 'OK' from verdict 'DOCUMENTED-NON-SUPPORT'
 DOC-A.1-85: state 'GAP' but the schema derives 'OK' from verdict 'DOCUMENTED-NON-SUPPORT'
 DOC-A.1-173: state 'GAP' but the schema derives 'OK' from verdict 'DOCUMENTED-NON-SUPPORT'
```

⭐ The drift test earned its keep exactly here: the writer was wrong, the reader was right, and the only thing
that could tell them apart was a test that recomputes rather than trusts.

## The fix

`Schema.state_for` now guards on `self.anchor_obliged(row)`, mirroring the C# line for line. Re-applying the
identical batch closed the three rows (`GAP 3410 → 3407`) and the drift test passes over all 4311 rows.

⚠ `DOC-A.1-86` stays a GAP, correctly: it carries the declined verdict but no witness test yet. That is the
clause the fix deliberately does NOT relax.

## Sweep — and the THIRD arm it found

`grep -rn "anchor_for\|anchor_obliged" scripts/ --include=*.py`: `record_verdicts.validate` (line 142) already
asked `anchor_obliged`; `is_observable` uses `anchor_for` to exclude the anchor itself from the location match
(correct usage). The C# side has no twin defect — `DerivedState` and `MisanchoredRows` both ask `AnchorObliged`.

⛔ **But the grep was not the whole population.** Running `audit_annex_a1.py --check` after the `state_for` fix
produced three NEW findings for the same reason in a *different file*: `check_pins` enumerates every DOC
inventory row with a spec-derived `test-ref` and demands a matching §7 row, without asking whether the row's
verdict CLAIMS a determination —

```
⛔ inventory DOC-A.1-84 closes on [...] but CONFORMANCE.md §7 carries no row for item 84
```

— which is precisely backwards for a withdrawn item: §7 must carry **no** row for it, and the audit's own
`DOC-A.1` token check would have flagged one if it did. Same fix (`if not schema.anchor_obliged(row): continue`),
same rule, third site. **The lesson is that the grep found the sites naming the predicate, and the third arm was
the site that should have named it and never did** — `feedback_scan_all_similar` measured over the CONSUMERS of
the rule, not over the callers of the helper.

## The self-test was silently vacuous too

`audit_annex_a1.py --self-test` then failed on two cases — and that failure was correct. Its fabricated inventory
rows carried only `rule-id` and `test-ref`, no `kind` and no `verdict`, so under the new predicate every one of
them was exempt *by accident* and two checks stopped testing anything. The fixtures are now real DOC rows with a
verdict, plus a new case pinning the exemption itself (`a DECLINED item closing on its witness needs no §7 row`)
against the claiming-row control that proves the check still fires. `--self-test` is ALL GREEN with every check
proven able to fail — which is the only thing that makes the `--check` green above worth reading
(`feedback_green_gates_arent_evidence`).
