# PB3526 — a held gate lock is not a red gate

## What happened (2026-10-22 12:29–12:30 PDT)

The Mythos session ran `enqueue.py land` on PB3511's branch `worktree-wf_8c44feac-62f-10` at 12:29; the loop's landing
lane (`land_lane.py` attempt `20261022T193024308865Z`) started its own at 12:30:24. One gate held the worktree's gate
lock; the other's `build-local` ended NOT RUN ("another gate holds this worktree's gate lock",
`scripts/run_gate_legs.py`), and `enqueue.py` printed `=== ENQUEUE: GATE RED (Windows) ===` and recorded BLOCKED.

## Mechanism

`scripts/orchestrator/enqueue.py` step 3 (`land`): every `(host, green, line)` the gates return that is not green becomes
`blocked(branch, wt, "BLOCKED: enqueue — the <host> gate is not GREEN …")` and `EXIT_GATE` — NOT RUN included. A NOT RUN
for a held lock says nothing about the branch; it says another run is gating the same tree.

## Harm

A healthy branch is stamped BLOCKED, and a BLOCKED report is exactly what makes a finisher dispatcher act (PB3379's
recurrence of the same morning: two finishers on this branch). The duplicate `enqueue.py land` is itself the PB3379
ownership gap; this note is the separate defect that the second run's failure is reported as the branch's failure.

## The bar for the fix

- `enqueue.py` tells a lock-held NOT RUN apart from a red (from the gate's own verdict, never a text guess if a structured
  verdict exists: `run_gate_legs.py`'s `verdict.json`) and ends with its own exit (busy: another run gates this tree),
  writing NO BLOCKED line; `land_lane.py` treats that exit as "retry later", never as a stop.
- Sweep (rule 4): every other NOT RUN cause the gate reports (malformed gate settings, an unlistable population) is
  classified on purpose — a NOT RUN the branch caused may block; one the environment caused may not.
- A test in `test_enqueue.py` pins: a lock-held NOT RUN writes no BLOCKED and returns the busy exit.

## Landing (wave 1150 group A, with PB3527; review round 1's finisher)

PB3527's branch fixed this as its mechanism 2 (one verdict reader): the gate driver's verdict for a held gate lock is
`BUSY` (exit 3), `run_gate_legs.read_verdict` is the one reader of a verdict line, and `enqueue.py land` ends a BUSY
gate `GATE BUSY`, exit 12, with no `BLOCKED:` report line; the landing lane retries it at the same head once the
worktree's gate lock is free (`land_lane.WAITS`, `wait_free`). Its self-test pins it (`enqueue.py`: "land: a gate BUSY
... is exit 12, never a red: no report line").

The sweep the bar asks for (review R1-1 found it missing): every other NOT RUN cause, classified on purpose
(`run_gate_legs.NOT_RUN`): malformed shared gate settings (at the start or while the gate queued: the coordination
directory's file), a failure of the gate driver itself, a population that could not be listed after a GREEN build,
the Linux gate's host with no WSL, no runnable Python or no .NET SDK, a gate that printed no verdict line at all, and a
gate row refused for running outside the shared slot. Each measured nothing about the branch, so none may block it:
`read_verdict` reads NOT RUN as NOT RUN (it used to fold it into RED), `run_gates` reports a missing verdict line and the
slot refusal as NOT RUN, and `land` ends `GATE NOT RUN (<host>)`, exit 2 (usage or state), with no report line: the lane
retries it once, and a second at the same head is the operator's handoff (`units/enqueue.md` step 3), never a
finisher's. A red the branch caused (RED, RED/INCOMPLETE, LEG 1 ONLY: RED, BUILD FAILED, a GREEN line with a non-zero
exit) still blocks, exit 5. Witnesses: `run_gate_legs.py` ("the one verdict reader ..."), `enqueue.py` ("land: a gate
NOT RUN ... is exit 2, never a red", "gate rows: ... a gate that printed no verdict line measured nothing: NOT RUN").
