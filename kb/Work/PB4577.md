# PB4577 - SEARCH of a nested table with the enclosing table's subscript is accepted below COBOL 2023

**What is wrong.** `SEARCH H (GI)`, where `H` is a table nested in `G` and `GI` is the subscript of the enclosing table, compiles with no diagnostic and runs at `--std 85`, `2002` and `2014`, and at 2023. Only the 2023 text allows it: §14.9.37.3 2) (`cite.py --check` OK) "identifier-1 shall not be subscripted at the level for which the SEARCH is applicable" bans the searched level's subscript alone, and 3) (OK) "Identifier-1 may be contained within one or more other tables, for which the subscripting is still required." The 2002 text and the 2009 committee draft (CD 1.2) say "Identifier-1 shall not be subscripted or reference modified" (`E:/COBOL-coord/specs-drafts/t2002.txt:27472` and `t2009.txt:29403`; draft text outside the tracked tree, so not `cite.py`-checkable). A conforming 85, 2002 or 2014 compiler must therefore refuse the form, and GnuCOBOL 3.2.0 does (PB4547).

**Repro** (free format; found by fuzz night 10's vetting of PB4547, probe `E:/COBOL-coord/scratch/fuzz-vet/step2/f1-misc/PB4547/prog85.cob`; `--std 2014 --source-format free` accepts the source of PB4547 as it stands, and `--std 85` needs a paragraph name before the first statement):

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. SR1.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 T-VALS PIC X(6) VALUE "123789".
01 T REDEFINES T-VALS.
   05 G OCCURS 2 TIMES INDEXED BY GI.
      10 H PIC 9 OCCURS 3 TIMES INDEXED BY HI.
PROCEDURE DIVISION.
MAIN-PARA.
    SET GI TO 2
    SET HI TO 1
    SEARCH H (GI)
        AT END DISPLAY "NOT FOUND"
        WHEN H (GI, HI) > 7
            DISPLAY "FOUND " H (GI, HI)
    END-SEARCH
    STOP RUN.
```

Observed: no diagnostic, the run prints `FOUND 8`, exit 0, at `--std 85`, `2002` and `2014`. Expected at 85 and 2002: COBOL2075 refuses `SEARCH H (GI)`; at 2014 the same, on the CD's wording.

**Root.** COBOL2075 (`SearchIdentifier1Operand`, `src/WiseOwl.Cobol.Editions/Diagnostics/DiagnosticCatalog.cs` about line 4622) is written from the 2023 SR2/SR3 wording and `ResolveSearchTable` applies it at every edition: it bans only subscripts beyond the superordinate count (`operand.SubscriptCount > superordinate`), an upper bound that is right for 2023 and too permissive below it. The golden `pb3365_search_nested_dynamic_table` is `accept: [2014]` and uses both spellings (identifier-1 with the enclosing subscript, and bare), so it asserts the over-permissive reading at 2014 too.

**Open question, to settle first.** The 85 and 2002 edge is established by the 2002 text for 2002 (the 1985 wording was not read here). The 2014 edge is not: 2023 Annex E lists no SEARCH change, which by the version change reference (VCR row 7.13) would mean 2014 already has the 2023 SR2/SR3, while the 2009 CD that led to 2014 still has the old sentence. Obtain the 2014 FCD (or an equivalent 2014 text) before gating 2014; if 2014 matches 2023 the gate is 85 and 2002 only and the title above narrows to those. The version matrix (`docs/VERSION_CHANGE_REFERENCE.md`, `docs/VERSION_TEST_MATRIX_DESIGN.md`) records the edge once decided, per the architectural commitment that editions are four compilers.

**Fix shape.** Edition-gate the enclosing-table subscript on identifier-1 (a version predicate in `ResolveSearchTable`, the way other edition rules are gated), with a message naming the edition's rule; re-point the golden to `accept: [2023]` plus a `refuse-at` case per edition below it; sweep the sibling `SEARCH ALL` format (`CheckSearchAllFormat2`) and every other place that reads identifier-1's subscript count. A design correction updates `docs/CONFORMANCE.md` D-SRCH-DYN and the SEARCH row of the version matrix in the same change.
