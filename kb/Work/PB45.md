# PB45 — OPEN — three more positions that refuse a function-identifier

> ⚙ **FOUND WHILE MEASURING [[PB26]], NOT BY LOOKING FOR THEM.** The PB26 probe put `FUNCTION LOG10(0)` into one
> statement kind after another to see where the EC gate fired. THREE of the statements never got as far as
> the gate — they refused the reference outright. Same family as DA4 and [[PB17]]: **§8.4.3.1.2 Format 1 makes a
> function-identifier an identifier**, so it is admissible wherever a format writes `identifier-n` in a SENDING
> position (§8.4.3.2.3 SR1 bars only RECEIVING operands).

**MEASURED (2026-08-05, at `d88170ab`):**

| # | source | result | required |
|---|---|---|---|
| 1 | `ADD FUNCTION SQRT(W-Z) TO W-R` | **`COBOL0001: no viable alternative at input 'ADDFUNCTION'`** — a PARSE error | accepted |
| 2 | `EVALUATE TRUE / WHEN FUNCTION SQRT(W-Z) > 0` | compiles clean, **`NotImplementedCobolFeatureException: EVALUATE TRUE/FALSE paired with a value WHEN object`** at RUN TIME | accepted |
| 3 | `INSPECT W-U TALLYING W-N FOR ALL FUNCTION LOG10(W-Z)` | **`COBOL0001: no viable alternative at input 'ALLFUNCTION'`** — a PARSE error | accepted |

## ⛔ BOTH ARE LEGAL SOURCE

Every citation `cite.py --check`ed.

**Case 1 — ADD.** §14.9.2.2 Format 1 is `ADD { identifier-1 | literal-1 } … TO { identifier-2 [rounded] } …`.
§14.9.2.3 **SR2** requires identifier-1 to "reference numeric data items" — and a numeric function-identifier does
exactly that: §15.4 puts the returned value "in a temporary elementary data item" and §15.2 items 5–6 make integer
and numeric functions "of the class and category numeric". identifier-1 is a SENDING operand (identifier-2 is the
receiver), so §8.4.3.2.3 SR1 does not bar it. **The rejection is at the PARSER**, which is where DA4's four
STRING/UNSTRING positions were rejected too — that entry's own words: "the rejection happened a whole stage
earlier than the string-context renderer DA2 fixed."

**Case 3 — INSPECT.** §14.9.22 writes its TALLYING comparand as `identifier-n | literal-n`, the same sending
position, so the same §8.4.3.1.2 chain admits a function-identifier. Rejected at the PARSER like case 1 — and the
two together are the reason the sweep note below says the question is whether the grammar expresses "an operand"
once or once per verb.

**Case 2 — EVALUATE.** §14.9.13 admits a condition as a WHEN object when the selection subject is TRUE/FALSE, and
`FUNCTION SQRT(W-Z) > 0` is a relation condition. A plain `WHEN W-Z > 0` under `EVALUATE TRUE` works, so the
subject/object pairing is implemented; it is specifically a relation **whose left operand is a
function-identifier** that is not recognised as a condition and falls to the value-object arm's
`BoundConditionError`. The wrong-stage family again: compiles clean, throws at run time.

## ▶ WHAT TO CHECK FIRST

⚠ **Do NOT assume these share one fix.** Case 1 is a grammar-level refusal and case 2 is a bind-level
misclassification; they share a CAUSE-SHAPE (a position that forgot function-identifiers), not a code path.
⚠ **And sweep the whole arithmetic family before fixing ADD alone** — SUBTRACT/MULTIPLY/DIVIDE write the same
`identifier-n` operands in their formats, so the ADD parse rule is unlikely to be the only one. [[PB26]]'s own
lesson applies: this is a per-position hand-list, and the question is whether the grammar expresses "an operand"
once or once per verb.

## ⛔ THE SWEEP FOUND IT FAMILY-WIDE, NOT THREE POSITIONS

The note warned "sweep the whole arithmetic family before fixing ADD alone". It was worse than the entry filed:
**every arithmetic verb, in every format**, rejected a function-identifier — ADD, SUBTRACT, MULTIPLY, DIVIDE (both
operand positions) — while COMPUTE accepted it because its RHS is an `arithmeticExpression`.

**Root cause: ONE RULE WRITTEN FOUR TIMES.** `addOperand` / `subtractOperand` / `multiplyOperand` /
`divideOperand` were each `dataReference | literal`, and all four omitted `functionCall`. `inspectChar` was a
fifth copy with the same omission. Exactly [[feedback_one_rule_one_place]].

## ✅ LANDED — grammar AND binder, because the grammar alone shipped a SILENT WRONG ANSWER

⛔ **THE HALF-FIX IS THE PART WORTH REMEMBERING.** Adding `functionCall` to the grammar made the source parse —
and produced the WRONG VALUE. `ExpressionBinder.BindOperandExprCore` walks the operand wrapper breadth-first
looking for something bindable, and had **no `FunctionCallContext` arm**, so it descended INTO the call and bound
its ARGUMENT: `ADD FUNCTION SQRT(W-Z) TO W-R` with `W-Z = 4` added **four** instead of **two**. It compiled and
printed a plausible number. Caught only by checking the value against the spec-derived answer
([[feedback_verify_output_is_correct]]). `InspectBinder` needed the same arm, where the missing case surfaced as a
MISLEADING diagnostic — "a numeric literal is not a valid INSPECT literal" for something neither numeric nor a
literal.

**MEASURED** (golden `tests/conformance/2023/pb45_function_in_sending_operands`, `FUNCTION SQRT(4)` = 2):
`ADD-TO=3` · `ADD-GIVING=11` · `SUB-GIVING=7` · `MUL-GIVING=18` · `DIV-INTO=4` · `DIV-BY=4` · `COMPUTE=2` (the
control) · `INSPECT-TALLY=3` · `INSPECT-REPL=[xyxyxy   ]`.

## ⚖ WHY FOUR RULES AND NOT ONE — A RECORDED CONSTRAINT, NOT A PREFERENCE

Collapsing them into one `arithmeticSendingOperand` was tried and **reverted**: the FROZEN legacy compiler shares
this grammar and reads `.dataReference()` / `.literal()` off `AddOperandContext` and friends BY NAME, so both a
collapse and an alias break its build — the same freeze that holds D10 until **PHASE 15 CUT 2** deletes legacy.
The change is therefore ADDITIVE (the standing grammar discipline), and `ArithmeticSendingOperandDriftTests` pins
the four alternative sets IDENTICAL so they cannot drift while they must stay separate. **Collapse at CUT 2 and
delete that test with them.** The same test asserts the RECEIVING rules do NOT admit one (§8.4.3.2.3 SR1), so a
careless "add functionCall everywhere" edit fails.

## ✅ THE FORMER OPEN HALF — CLOSED 2026-08-05. THE CAUSE WAS AN UNLICENSED GRAMMAR REPETITION

⛔ **BOTH OF MY EARLIER DIAGNOSES WERE WRONG, IN OPPOSITE DIRECTIONS, AND THE TOKEN DUMP SETTLED IT.** I first
wrote "a BIND-level misclassification, not a grammar gap" (refuted below), then replaced it with "that points at
the SUBSCRIPT lexer mode — `SQRT(` is a subscript trigger". **The lexer was never involved.** A token dump of the
failing shape and of `IF FUNCTION SQRT(W-Z) > 1` — which has ALWAYS worked — returns **byte-identical, entirely
DEFAULT-mode** streams:

```
FUNCTION IDENTIFIER(SQRT) LPAREN IDENTIFIER(W-Z) RPAREN GT INTEGERLIT(1)
```

No `SUB_*` token anywhere, in either. **This is the THIRD time an entry has named a lexer-mode root cause that a
token dump refuted** ([[PB8]] is the standing precedent, and §0 carries it as a warning). The rule earned here:
*the discriminator being a parenthesis does not implicate the lexer — parentheses are also a PARSER decision.*

**THE ACTUAL MECHANISM (from the parse tree, not from reading the grammar).** `evaluateWhenGroup` was
`NOT? evaluateWhenItem+`, and the tree showed that `+` splitting one selection object into TWO items:

| # | item | bound as |
|---|---|---|
| 1 | `FUNCTION SQRT` | a bare zero-argument function-identifier — a **valueOperand** |
| 2 | `(W-Z) > 1` | a relation whose left operand is a **parenthesised arithmetic expression** |

The argument parenthesis was PEELED off the function and re-read as a separate object. Item 1 is then a VALUE
object under an `EVALUATE TRUE` subject, which is exactly the `BoundConditionError` at `EvaluateBinder.cs`
("EVALUATE TRUE/FALSE paired with a value WHEN object") — the run-time throw, faithfully reporting the tree it
was handed.

⭐ **WHY THE PARENTHESIS WAS THE DISCRIMINATOR, PRECISELY.** Where BOTH readings are viable ANTLR takes the greedy
one, which is why `DISPLAY`, `STRING`, `INSPECT`, nested function arguments and multi-operand `ADD` never peeled
(all measured — see the sweep). Here the greedy reading **dies**: once the item ends there is no way to consume
the trailing `> 1`. So the only surviving `valueOperand` path was the peel — and `valueOperand` precedes
`condition` in `evaluateWhenItem`, so ANTLR preferred it. `FUNCTION PI > 1` worked because with no parenthesis
there is nothing to peel, alt 2 dies outright, and `condition` wins. **The `+` supplied the VIABILITY; the
alternative order merely picked the winner.**

## ⛔ THE FIX IS THE ARITY — AND §14.9.13.2 SAYS SO ON THE PRINTED PAGE

The general format (rendered from the PDF, printed folio 618, and matching the transcription exactly):

```
{ { WHEN selection-object [ ALSO selection-object ] … } … imperative-statement-1 } …
```

**Selection objects repeat ONLY through ALSO** — which is `evaluateWhenPhrase`'s own loop — never by
juxtaposition. §14.9.13.3 SR2 fixes the count against the subjects, and the 900-dpi figure note records the
object brace as "a single pair of braces spanning ten stacked alternatives — exactly one shall be selected".
`evaluateWhenItem+` was a **superset the standard never licensed**, and the binder had given it an invented,
uncited meaning ("additional items AND in (a faithful reading of consecutive operands)") — a semantics that could
only ever fire on a misparse. Both are gone: `evaluateWhenGroup : NOT? evaluateWhenItem`.

✅ **The note's warning against reordering was CORRECT and is untouched.** `condition` before `valueOperand` would
retarget `EVALUATE X / WHEN <level-88>` (a VALUE subject, where §14.9.13.4 GR4a6 makes the same name an equality
operand) — and Table 15 makes the object's legality depend on the SUBJECT, which no context-free order can
express. The arity fix needs no reordering, and `EvaluateSelectionObjectArityDriftTests` now PINS the order so a
future "obvious" reorder fails with that reasoning in the message.

## ⛔ THE GOLDEN FOUND A SECOND, INDEPENDENT DEFECT AT THE SAME SITE — `EVALUATE TRUE / WHEN <level-88>`

Writing the spec-derived golden (rather than one scoped to the reported symptom) exposed a live defect the report
never mentioned: **`EVALUATE TRUE / WHEN VALID-CODE` — one of the commonest idioms in COBOL — threw the SAME
run-time error.** Pre-existing, NOT a regression: a bare condition-name has no parenthesis to peel, so it already
lost to `valueOperand` under the old `+`.

**Table 15 (§14.9.13.3 SR10)** admits ONLY *Condition*, *TRUE/FALSE* or *ANY* against a TRUE/FALSE subject —
never identifier-2 — and §8.8.4.1.2 makes a bare condition-name a condition. But it arrives through the
`valueOperand` arm because **a bare word is equally a condition-name and an `arithmeticExpression`, and only the
RESOLVED SYMBOL can tell them apart**. That is why the classification cannot live in the grammar at any
alternative order, and now lives in `EvaluateBinder.BindWhenItem` — asking the question through
`ConditionBinder.BareOperandAsCondition`, EXTRACTED from the abbreviated-relation path rather than copied, so
level-88, switch-status (§8.8.4.6) and simple-boolean (§8.8.4.3) objects all resolve through the one rule
([[feedback_one_rule_one_place]]).

⚠ **The legacy oracle already handled this case and greenfield did not** — and the GnuCOBOL differential is
structurally blind to it, because the program COMPILES either way. A runtime-output defect with a clean compile
is exactly the hole §0 records in that net.

## ⛔ THE SWEEP — THE PEEL IS CONFINED TO EVALUATE, AND THAT IS MEASURED, NOT ASSUMED

A generic detector (a `functionCall` that took NO argument list while a `(` still stands to its right) over 17
statement shapes, before and after:

| position | before | after |
|---|---|---|
| `EVALUATE … WHEN`, and with `ALSO` | **PEELED** (2 sites) | ok |
| `IF` / `PERFORM UNTIL` / `DISPLAY` list / `STRING` list / `INSPECT` / `MOVE` / `COMPUTE` | ok | ok |
| nested function arguments (`FUNCTION MAX(FUNCTION SQRT(X) 4)`) | ok | ok |
| `ADD`, one operand and two | ok | ok |

So no general `functionCall` restructure was warranted. ⚠ `CALL "S" USING FUNCTION SQRT(X)` also fails, and it is
**NOT this defect and NOT a defect at all** — §14.9.4.3 SR3/SR5 make Format 1's identifier-2 a RECEIVING operand
confined to the file/working-storage/local-storage/linkage sections, so a function result (a temporary, §15.4) is
genuinely inadmissible there. The real gap that probe exposed is narrower and is filed separately as [[PB46]].

## THE ORIGINAL CHARACTERISATION, KEPT FOR THE RECORD

| WHEN object | result |
|---|---|
| `W-Z > 1` | ✅ parses as a condition |
| `W-Z > 1 AND W-Z < 9` | ✅ |
| **`FUNCTION PI > 1`** (no argument, **no parentheses**) | ✅ |
| **`FUNCTION SQRT(W-Z) > 1`** | ❌ |
| `FUNCTION SQRT(W-Z) = 2` | ❌ (operator-independent) |
| `FUNCTION SQRT(W-Z) > 1 AND W-Z < 9` | ❌ (AND-chain-independent) |

⭐ **THE DISCRIMINATOR IS THE ARGUMENT PARENTHESIS, NOT THE FUNCTION-IDENTIFIER** — this half was RIGHT, and the
characterisation table above is what made the fix findable. ⛔ **The inference drawn from it was WRONG:** "that
points at the SUBSCRIPT lexer mode — `SQRT(` is a subscript trigger". **REFUTED by the token dump** (see the
closed-half section at the top): both shapes lex entirely in DEFAULT mode and the lexer was never touched. A
parenthesis is *also* a parser decision, and here it was one — the `evaluateWhenItem+` repetition.

▶ **"NEXT STEP IS A TOKEN DUMP, NOT AN EDIT" — DONE, AND IT PAID.** The dump refuted the hypothesis the entry
itself proposed, which is the third time in this project ([[PB8]] being the precedent §0 carries).
