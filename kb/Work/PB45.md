# PB45 — OPEN — three more positions that refuse a function-identifier

> ⚙ **FOUND WHILE MEASURING [[PB26]], NOT BY LOOKING FOR THEM.** The PB26 probe put `FUNCTION LOG10(0)` into one
> statement kind after another to see where the EC gate fired. THREE of the statements never got as far as
> the gate — they refused the reference outright. Same family as DA4 and [[PB17]]: **§8.4.3.1.2 Format 1 makes a
> function-identifier an identifier**, so it is admissible wherever a format writes `identifier-n` in a SENDING
> position (§8.4.3.2.3 SR1 bars only RECEIVING operands).

**MEASURED (2026-08-05, at `d88170ab`):**

| # | source | result | required |
|---|---|---|---|
| 1 | `ADD FUNCTION SQRT(W-Z) TO W-R` | **`COBOL0001: no viable alternative at input 'ADDFUNCTION'`** — a PARSE error | accepted |
| 2 | `EVALUATE TRUE / WHEN FUNCTION SQRT(W-Z) > 0` | compiles clean, **`NotImplementedCobolFeatureException: EVALUATE TRUE/FALSE paired with a value WHEN object`** at RUN TIME | accepted |
| 3 | `INSPECT W-U TALLYING W-N FOR ALL FUNCTION LOG10(W-Z)` | **`COBOL0001: no viable alternative at input 'ALLFUNCTION'`** — a PARSE error | accepted |

## ⛔ BOTH ARE LEGAL SOURCE

Every citation `cite.py --check`ed.

**Case 1 — ADD.** §14.9.2.2 Format 1 is `ADD { identifier-1 | literal-1 } … TO { identifier-2 [rounded] } …`.
§14.9.2.3 **SR2** requires identifier-1 to "reference numeric data items" — and a numeric function-identifier does
exactly that: §15.4 puts the returned value "in a temporary elementary data item" and §15.2 items 5–6 make integer
and numeric functions "of the class and category numeric". identifier-1 is a SENDING operand (identifier-2 is the
receiver), so §8.4.3.2.3 SR1 does not bar it. **The rejection is at the PARSER**, which is where DA4's four
STRING/UNSTRING positions were rejected too — that entry's own words: "the rejection happened a whole stage
earlier than the string-context renderer DA2 fixed."

**Case 3 — INSPECT.** §14.9.22 writes its TALLYING comparand as `identifier-n | literal-n`, the same sending
position, so the same §8.4.3.1.2 chain admits a function-identifier. Rejected at the PARSER like case 1 — and the
two together are the reason the sweep note below says the question is whether the grammar expresses "an operand"
once or once per verb.

**Case 2 — EVALUATE.** §14.9.13 admits a condition as a WHEN object when the selection subject is TRUE/FALSE, and
`FUNCTION SQRT(W-Z) > 0` is a relation condition. A plain `WHEN W-Z > 0` under `EVALUATE TRUE` works, so the
subject/object pairing is implemented; it is specifically a relation **whose left operand is a
function-identifier** that is not recognised as a condition and falls to the value-object arm's
`BoundConditionError`. The wrong-stage family again: compiles clean, throws at run time.

## ▶ WHAT TO CHECK FIRST

⚠ **Do NOT assume these share one fix.** Case 1 is a grammar-level refusal and case 2 is a bind-level
misclassification; they share a CAUSE-SHAPE (a position that forgot function-identifiers), not a code path.
⚠ **And sweep the whole arithmetic family before fixing ADD alone** — SUBTRACT/MULTIPLY/DIVIDE write the same
`identifier-n` operands in their formats, so the ADD parse rule is unlikely to be the only one. [[PB26]]'s own
lesson applies: this is a per-position hand-list, and the question is whether the grammar expresses "an operand"
once or once per verb.
