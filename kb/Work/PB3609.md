# PB3609 — a MERGED branch reads IN FLIGHT for three hours

**Sites:** `scripts/prune_worktrees.py` (`lifecycle`, the `fresh` / `--min-age` branch near `touched = …`).

## Found

`prune_worktrees.py` gives a branch whose content is `MERGED` or `LANDED` the state LANDED only when it is
`not fresh and not row.dirty`; a merged branch touched within `--min-age` (180 minutes) falls through to `IN FLIGHT,
touched N min ago`. At ~16:00 PDT on 2026-10-23, 13 of the 20 rows the survey printed IN FLIGHT were already merged
(their pull requests #439, #444–#455 MERGED, 0 commits ahead of origin/main). The survey is what the session probe, the
operator and the loop's planner read as "what is not on main yet", so the backlog looked three times its size and a
reader could not see which branches were truly waiting.

## The fix

The age guard protects DELETION (a worktree an agent may still be using), not the classification. But MERGED alone
(the tip is an ancestor of origin/main) is not "its work landed": a branch created from main a moment ago, with no
commit of its own yet, is MERGED too, and today only the age guard keeps such an attended or hand-made worktree IN
FLIGHT (branch review R1-2 of the filing). So the state LANDED, whatever the age, needs EVIDENCE THAT THE BRANCH CARRIED
WORK: a commit of its own that main now contains (its tip differs from the commit it was created at, read from the
branch's reflog `branch: Created from …` entry, or a merged pull request whose head it is). A merged branch with no such
evidence stays IN FLIGHT while fresh, as now. `--apply` skips a LANDED row that is fresh or dirty, saying so (`LANDED,
kept: touched N min ago`). Self-test cases: a branch whose one commit merged, touched one minute ago, reads LANDED and
survives `--apply`; a branch just created from main, with no commit, reads IN FLIGHT.

## Branch review R2-1 (low), filed 2026-10-24 from w20261023c-PB3608-report.md

The reflog answer to R1-2 is sound (`refs/heads/<branch>` logs its `branch: Created from origin/main` entry, and
`prune_worktrees` already reads branch reflogs for `age_min`), but two details of "The fix" are loose:

- (a) The alternative evidence, a merged pull request whose head the branch is, is not readable in `prune_worktrees` today:
  `lifecycle()` gets `prs` from `queue_facts.read`, whose query is `pullRequests(states:OPEN ...)` (`queue_facts.py`
  line 48), and the git-only lifecycle has `prs=None`. Either widen the query to merged pull requests (and say what the
  git-only path does) or drop the alternative.
- (b) "Its tip differs from the commit it was created at" is weaker than the stated criterion "a commit of its own that main
  now contains": a fresh branch fast-forwarded to newer main (`git merge origin/main`, no commits of its own) differs from its
  creation commit yet carries no work. Test for a commit reachable from the tip, not from the creation commit, whose author
  is not main's history (for example `git rev-list <created>..<tip>` containing a non-merge commit not on first-parent
  main at creation time), and add a self-test case for the fast-forwarded branch.

## Recurrence 2026-10-24: the landing lane launched `enqueue.py land` on a merged branch

The harm is wider than the backlog count. At 16:33:08 PDT on 2026-10-24 the loop's landing lane started `enqueue.py land`
on `worktree-wf_1973801d-4fe-29` at 5e110b97e (attempt `land-lane-000088-20261024T233307Z`), 14 minutes after its pull
request #512 merged (23:18:57Z) and with 0 commits ahead of origin/main. The enqueue unit had re-armed the branch at that
head before the owner's reboot (`<coord>/land-lane/rearm/`). `land_lane.rearm_hold` holds a re-arm whose survey row is
in `QUEUE_OWNED` (`ENQUEUED`, `NOT QUEUED`, `LANDED`), but the survey read the merged branch `IN FLIGHT, touched 42 min
ago` (this note's defect), so the hold did not apply and the attempt ran until exit 6 NO ENTRY. With this note's fix the
row reads LANDED and the existing hold covers it; the fix's self-test should include the lane's view: a re-armed
branch whose head main contains is not a candidate (`land_lane.candidates`), and its re-arm record is dropped rather
than held (today a LANDED re-arm lingers until `prune_worktrees.py --apply` removes the branch, and `rearm_hold` names
the queue as its owner, which is wrong for a merged branch).
