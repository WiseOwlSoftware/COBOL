# PB5308 - at --std 85 the ENTER statement compiles to nothing for any language-name (ENTER FORTRAN SUBRTN.), so a routine the program expects to run never runs; the implementor choice is not to provide ENTER, which the compiler must refuse

**Sites:**

- `src/WiseOwl.Cobol.Compiler/Validation/VersionConformancePass.cs` (`VisitEnterStatement`)
- `src/WiseOwl.Cobol.Compiler/Binding/Bound/StatementBinder.cs` (`BindStatementCore`)

**Mechanism.** Language-name-1 "is specified by the implementor" (§1985:VI.6.12.3 SR1), and an implementation "may include the ENTER statement or not, at the option of the implementor" (§1985:I.1.5.2.5.5). Under either choice the present behaviour breaks SR1: if ENTER is provided, the only language WiseOwl can specify is COBOL (SR3's return word), so ENTER FORTRAN must be refused; if it is not, every ENTER is refused. The compiler accepts ENTER with any word and executes nothing, so the program runs as if the other-language routine had run. ISO 2023 has no ENTER (deleted in 2002), so by CLAUDE.md rule 1 GnuCOBOL decides, and GnuCOBOL refuses ENTER: the statement is not provided at --std 85, as docs/CONFORMANCE.md section 3.7.1 now records. This answers kb/Work PB4995's ENTER question. kb/Work PB5178 holds ENTER's routine-name syntax, which a refused ENTER makes moot. VCR Table 7 row 7.16 ("comment-equivalent") changes with the fix. The row `1985-SR-VI.6.12.3-3` (ENTER COBOL after other-language text) stays held until this lands, because it closes only when no other-language text can be compiled in-line.
