# PB660 — LANDED — BOTH halves of a uniqueness rule, neither of which was enforced

Found 2026-09-05 by the `PB303` implementer (report §"New defects" D-1), measured at `--std 2023` on its tree
while giving every unit two names; pre-existing (the declared-name twin reproduces on main without any AS phrase).

## Repro (`--std 2023`; one compilation group)

```cobol
       IDENTIFICATION DIVISION.  PROGRAM-ID. P3DUPA AS "P3DUPX".
       PROCEDURE DIVISION.  DISPLAY "FIRST".  GOBACK.  END PROGRAM P3DUPA.
       IDENTIFICATION DIVISION.  PROGRAM-ID. P3DUPB AS "P3DUPX".
       PROCEDURE DIVISION.  DISPLAY "SECOND".  GOBACK.  END PROGRAM P3DUPB.
       IDENTIFICATION DIVISION.  PROGRAM-ID. P3MAIN.
       PROCEDURE DIVISION.  CALL "P3DUPX".  GOBACK.  END PROGRAM P3MAIN.
```

Compiles, exit 0, prints `FIRST`. Two outermost `PROGRAM-ID. P3DND.` definitions (no AS phrase) behave the same.

## The rule

§8.3.2.2: "Within a run unit, all instances of a given name that is externalized to the operating environment shall
identify the same kind of entity or item" (`OK §8.3.2.2 2)`) — two program definitions with one externalized name
are two entities under one name; the compilation group is the compiler's whole view of the run unit it produces,
and a duplicate it can see is a duplicate it must report. §8.4.6.3's uniqueness sentence is the CONTAINED-program
half and appears enforced (a second contained program with the same name is refused); the OUTERMOST half has no
check on either axis.

## The mechanism

`src/Cobol.Net.Compiler/Binding/BinderDriver.cs#BuildProgramDefinitionTable` — `map.TryAdd(...)` returns false for
the second definition and nothing reads the result; `src/Cobol.Net.Runtime/Control/ProgramTable.cs#Register` /
`ResolveVisible` rule 4 — the first `_order` match wins with no uniqueness assertion on `CallName`. One fix at the
bind-time table covers both the declared and the externalized axis, since PB303 keys the table on both names.

## Fix shape

At `BuildProgramDefinitionTable`, a duplicate outermost definition — same declared name, or same externalized name,
case per the name kind (declared: case-insensitive; externalized: ordinal, per PB303's determination) — is a
compile-time error naming both definitions and the rule (one descriptor; the next free code); the runtime
`Register` keeps a debug assertion so a duplicate arriving from separately compiled assemblies (outside the
compiler's view) is at least loud. Negatives at 2002/2014/2023: the declared-name pair, the externalized-name pair,
and a declared/externalized cross (`PROGRAM-ID. P3DUPX.` beside `PROGRAM-ID. P3DUPB AS "P3DUPX".`); positive control:
a contained program reusing an outermost name where §8.4.6.3 permits it (measure first). Sweep: FUNCTION-ID,
CLASS-ID and INTERFACE-ID definitions through the same table for the same two axes.

## Landed 2026-09-22 (wave 44D)

RE-PROBED EVERY AXIS FIRST, and the note was wrong about one of them. Measured on this worktree's own build of
`2f6b38c61`:

| shape | before |
|---|---|
| two outermost `PROGRAM-ID. P3DUPA/P3DUPB AS "P3DUPX".` + `CALL "P3DUPX"` | exit 0, printed `FIRST` |
| two outermost `PROGRAM-ID. P3DND.` + `CALL "P3DND"` | exit 0, printed **`SECOND`** |
| `PROGRAM-ID. P3DUPX.` beside `PROGRAM-ID. P3DUPB AS "P3DUPX".` | exit 0, printed `PLAIN` |
| two CONTAINED programs of one name in one container | exit 0, printed the FIRST |
| an outermost `PROGRAM-ID. PBSAME.` beside `FUNCTION-ID. PBSAME.` | exit 0, **both ran** |

⛔ **The note claimed the CONTAINED half "appears enforced (a second contained program with the same name is
refused)". It is not, and was not.** Row 4 above is the measurement. The note also inherited a case determination
PB303 does not contain ("externalized: ordinal, per PB303's determination" — PB303 records no determination about
case at all), so that is re-derived below rather than carried. And the registrar was emitting
`ProgramRegistry.Register("P3DND", …)` TWICE under one path, which is why the declared-name pair printed the
SECOND while the AS pair printed the FIRST: `_byPath` overwrote, `_order` did not.

THE RULE, RE-DERIVED. The note cited §8.3.2.2's FIRST sentence ("shall identify the same kind of entity or item")
for the same-kind case, which that sentence does not decide — two programs ARE the same kind of entity. The
sentence that decides it is the NEXT one, which the note did not quote: *"Except for method-names and
property-names, when two or more source elements identify something with the same externalized name, they refer
to the same instance"* — two distinct definitions cannot be ONE instance. The first sentence then earns its place
on the CROSS-KIND pair (a program and a function), which the note never considered and which was also accepted.
§8.4.6.3's own sentence governs the contained scope. Every citation here was re-run through `cite.py --check`.

ONE CHECK, TWO SCOPES: `BinderDriver.CheckDefinitionNameUniqueness`, run in `BindProcedures` BEFORE either group
table is built, because both tables silently keep the first definition and drop the second.

- **COBOLNET2213** — the group-wide EXTERNALIZED namespace: outermost program definitions + function definitions
  keyed by `ExternalizedName`. One code, two messages, because §8.3.2.2 states one rule over one population in
  two sentences.
- **COBOLNET2214** — §8.4.6.3's per-outermost-program scope, over each root's whole containment subtree
  ("directly or indirectly"). A separate code because a containee's name is not externalized at all.

SIBLING SWEEP (which arm did I fix?). ⛔ **EVERY DEFINITION NAMESPACE POLICED ONLY ITSELF, so nothing ever
compared a definition of one KIND against a definition of another.** That is the pattern, and it is wider than
the note: CLASS-ID (COBOLNET0820) and INTERFACE-ID (COBOLNET0840) were enforced under §8.4.6.4's own explicit
sentences; FUNCTION-ID by COBOLNET1508 — keyed on the declared WORD and citing **§8.4.6.6, the scope of
function-prototype-NAMES, a real clause that says nothing about uniqueness** (the inherited-citation failure this
project keeps finding); PROGRAM-ID by nothing at all. Measured: `PROGRAM-ID. PBXBOTH.` beside
`CLASS-ID. PBXBOTH.` compiled clean too. §8.3.2.2's list item 1 names all four in ONE sentence, so
`CheckDefinitionNameUniqueness` now walks all four from one enumerator (`ExternalizedDefinitions`, fed from
`ctx.Units` and `ctx.Session.OoClasses`).

WHAT IT DELIBERATELY DOES NOT RESTATE. §8.4.6.4 owns class-name and interface-name uniqueness on the declared
WORD, so a class/class or class/interface pair sharing a word is skipped here and stays COBOLNET0820/0840's —
one fault, one diagnostic. A pair whose WORDS differ and whose `AS` literals coincide is §8.3.2.2's alone and
nothing else in the compiler looked at it; 2213 has it. 1508 likewise keeps only the clash §8.4.6.7 genuinely
owns (a REPOSITORY `FUNCTION word` entry names the WORD, so two definitions sharing a word are ambiguous even
under different `AS` literals) and fires only when the externalized names did NOT already collide. Prototype
units are excluded by the rule: §10.6.2 SR2 and SR3 each legislate FOR the pair — “If a compilation group
contains both a {program|function} definition and a {program|function} prototype definition with the same
externalized name, the signatures of these two compilation units shall be the same”.

⚠ **DETERMINATION — the comparison is CASE-INSENSITIVE**, the same `OrdinalIgnoreCase` `ProgramTable.NameEquals`
resolves a CALL with and both group tables already used. §8.3.2.2 leaves the mapping to the implementor ("The
implementor defines the formation and mapping rules of these names"); what is not optional is that the bind-time
check and the run-unit resolver agree, or source this check passes still resolves to the wrong definition.

THE COMPLEMENT IS PINNED AS HARD AS THE REFUSALS, because a wider check would reject legal source:
`tests/conformance/2002/pb660_definition_name_scopes.cob` has two outermost programs EACH containing a `PB660IN`
(§8.4.6.3's scope is one outermost program) and two outermost programs sharing the declared word `PB660PW` under
`AS "PB660X1"` / `AS "PB660X2"` (§8.3.2.2 makes the EXTERNALIZED name unique, and the AS phrase decouples it from
the word). `DefinitionNameUniquenessTests` carries the same complement plus a prototype/definition pair, and is
proven red on both loops.
