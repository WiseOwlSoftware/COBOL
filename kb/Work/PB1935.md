# PB1935 — OPEN

Filed by the train-1005 lander from wave 1005 group D's report (`w1005d-PB1668-report.md`, lead 2). Group D did not
land in train 1005 (dropped on a composition red), but this lead concerns code on main.

## Question

§8.8.4.12.1 (`cite.py --check 8.8.4.12.1 "no parentheses"` → `OK §8.8.4.12.1`) describes the abbreviation as a
consecutive sequence of relation conditions combined "with no parentheses". The binder reads `(C)` in
`A = B AND (C)` as the abbreviation's object (an implied `A = C`). Group D called it implementor latitude and noted
that GnuCOBOL and IBM accept it; the standard's own text seems to decide it.

**Verdict needed.** Whether `(C)` there is (a) a refused non-condition (C is a data item, not a condition), (b) an
abbreviated object as today, or (c) latitude; cite the rule, and if it is a defect, the golden and the negative.

**Site.** `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#BindSoleOperandCondition`.

## Adjudication 2026-10-07 (w1033)

Decision `E:\COBOL-coord\scratch\w1033-adj\PB1935-decision.md`; refuter `PB1935-refute.md` (OVERTURNED: the refuter's version is the outcome). Pinned build `pin-97006f3` (main `97006f310`); probes `PB1935\`, `PB1935-refute\` (`r1arith`, `r3a`..`r3d`, `r7*`).

**Outcome: DEFECT CONFIRMED, narrower than the note.** The decision said CONFORMS-NO-DEFECT; the refuter shows that for a CHARACTER subject a parenthesized numeric `(C)` is accepted where `§8.8.4.2.5` excludes it. Flags: `under_rejects: true`, `silent: true`, `wrong_answer: false` (the standard defines no value for that comparison), `rejects_legal_source: false`; `kind` flips to `defect`.
The note's original suspicion (`A = B AND (C)` reads `(C)` as an abbreviated object although `§8.8.4.12.1` says "no parentheses") does NOT hold for a NUMERIC subject.

**What stands (both files).** For a numeric subject and numeric C, "no parentheses are used within such a consecutive sequence" in `§8.8.4.12.1` means condition-level parentheses (the elements Table 5 counts, `§8.8.4.12.3 SR2`); `(C)` is an arithmetic expression (`§8.8.1.1`) and so a legal `arithmetic-expression-2` object (`§8.8.4.2.1`, `§8.8.4.2.2`, rendered PDF p. 217); `A = B AND (C)` means `A = B AND A = (C)` (`§8.8.4.12.4 GR1`). cite.py --check OK for all ten of the decision's citations. Refuter battery (A=3,B=1,C=3,D=5,E=0; `r1arith.out`) gives the spec value in
every numeric case (`(C) + 0`, `((C))`, `A = 1 OR (D) OR 3`, `A NOT = 3 OR (C)`, `A < D AND > (B)`, `E = 1 OR (ZERO)`, XOR, `(FUNCTION INTEGER(C))`, ...); condition-level parentheses are refused (`A = 1 OR (C = 4) OR 3`, `(A = 1 OR 2) OR 3` COBOLNET2318; `A = 1 OR (< C)` COBOL0001; `A = 1 OR (C = 4 OR 3)` is T, correct: the abbreviation lies wholly inside the parentheses). `ConditionBinder.BindPrimary` gives a parenthesized condition a new `AbbrevCarry`.

**The defect (character subject; `cite.py --check` OK per the refuter).** `§8.8.4.2.1` item 6 (`"Two operands where one is a numeric integer and the other is class alphanumeric or national"`) is the only numeric/character pair the closed list defines; `§8.8.4.2.5` (rendered PDF p. 219): "The numeric integer operand shall be an integer literal or an integer numeric data item of usage display or national". An arithmetic expression is neither: `(C)` and `(3)`
are only `arithmetic-expression-2`; `§8.8.1.2 GR1` makes the parenthesized value "a single operand", not a data item of usage display. The pinned compiler states the same rule in COBOLNET2532 ("a non-integer, COMPUTATIONAL, packed, floating-point or arithmetic-expression operand has no defined comparison with it").
Observed with A and B PIC X and C PIC 9 VALUE 3, NO diagnostic at 85/2002/2014/2023:

The build is inconsistent with its own rule: `(C + 0)` is refused as an arithmetic expression but `(C)`, `((C))` and `(3)` pass as if they were the bare item or literal. GnuCOBOL 3.2 accepts all these shapes (a net only; non-ISO).

**Mechanism and site.** `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#ComparisonOperandOf` (line 1390) correctly declines the sole-data-reference short-circuit for `(C)`; it falls to `IntrinsicBinder.OperandOf(host.Expr.BindExpr(expr))`; `BindExpr` drops the grouping parentheses and `OperandOf` (`IntrinsicBinder.cs:222-228`) maps the resulting `BoundNumRef` to a `BoundFieldOperand` and a `BoundNumLiteral` to a `BoundNumericLiteral` (the comment scopes that arm to "a user-function result temp" but nothing restricts it); then
`RelationComparability.IsNumericIntegerOperand` sees an integer display item or literal and admits the pair. The fault is NOT in the abbreviated carry at `BindSoleOperandCondition` (967); it is in the operand mapping shared by the full and the abbreviated relation, so a fix there covers `A = (C)`, `A = B OR (C)` and the mirror `(C) = A`.

**Goldens.** Negative: r3a, r3b, r3c refused with COBOLNET2532 at every edition. Positive: the whole `r1arith` battery stays accepted with values unchanged, with `r3d` (`A = C`) staying legal.

**Incidental (diagnostic quality only).** `IF A = ('Y')` and `A = 1 OR (< C)` (r2c) are rejected with the generic `COBOL0001: cannot parse construct near 'A'` where `A = (C)` with an alphanumeric C gets the precise COBOLNET0844 (`§8.8.1.1`). Rejection is correct; only the wording is weak.
