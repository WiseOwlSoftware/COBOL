# PB3339 — the SORT/MERGE store is in memory only

> flags: owner decision · architecture · sibling of PB3330

## Owner, 2026-10-17 (verbatim)

Ruling on PB3330's keyed files: "Reading the entire file into memory as a design requirement is a fatal flaw, IMO".
The operator swept the runtime for the same pattern (CLAUDE.md rule 4: every bug is a pattern) and found this one.

## The defect (measured on origin/main)

- `SortStore.Records` (the internal store class in `src/Cobol.Net.Runtime/IO/SortFileTable.cs:17`) is a `List<StoredFrame>`, and each RELEASE
  and USING transfer appends one record image to it. `CobolSort` (`src/Cobol.Net.Runtime/IO/CobolSort.cs:8`, "The
  in-memory sort/merge store") sorts it with `Array.Sort` over an index (`:378`) into a second full list (`:383`), and
  a MERGE builds one more (`:419`).
- Nothing writes to disk. The store's size is the sum of its record images (UTF-16 strings in memory, so about twice
  the file bytes), plus the sorted copy. A SORT of an input bigger than the available memory therefore ends in
  OutOfMemoryException, which kills the run unit. A batch SORT over a multi-gigabyte file is ordinary COBOL work.
- The other sweep results are not defects. The sequential organizations stream through their handle, and the
  collation loaders read locale data files, not user files.

## What other implementations do

GnuCOBOL 3.2 (`tests/external/gnucobol-3.2.tar.xz`):
- `libcob/common.c:525` bounds the sort's memory with `COB_SORT_MEMORY`, default 128M (`config/runtime.cfg:341`),
  in chunks of `COB_SORT_CHUNK`, default 256K (`:524`).
- `libcob/fileio.c` writes sorted runs to temporary files (`cob_create_tmpfile` :7835, `cob_get_sort_tempfile` :7865)
  and merges them (:8038-8142).

## The bar

- Memory is bounded by a documented, configurable limit, independent of the input size. Runs that exceed it are sorted
  in memory, written to temporary files, and merged k-way. Temporary files are removed on every exit path, and their
  directory is documented and configurable.
- The ordering rules stay exactly as they are: the KEY classes and collating sequences (§14.9.40.4 GR5), DUPLICATES IN
  ORDER (a stable sort, so run order and merge tie-break preserve release order), MERGE's input-order rules, and the
  RETURN / GIVING phases (kb/Work PB349).
- A file that fits in memory pays no disk cost.
- A measured test shows a SORT whose input is several times the configured limit completing within that memory, plus a
  drift test that refuses an unbounded store.
- Document the limit and the temporary-file location in `docs/CONFORMANCE.md`, next to the sort store's other
  implementor-defined items, and in the design doc (`docs/COBOLNET_DESIGN.md` §SORT/MERGE and
  `DESIGN-runtime-library.md`), in the same change.

## Route

This is a well-known algorithm (external merge sort), so the fix lane takes it: one Opus implementer, from a design
section it writes first in the design doc and follows. It is independent of PB3330's storage engine. Reuse PB3330's
temporary-file or page layer only if that layer has landed first, and never wait for it.

## Landed (wave 1110 A, 2026-10-17)

**Re-probe.** At 5ee921375 the store was as measured: `SortStore.Records` a `List<StoredFrame>` appended by every
RELEASE and USING transfer, `SortCore` an index `Array.Sort` copied into a second full list, `MergeCore` a third list,
and no write to disk anywhere. The structure is the defect (an OutOfMemoryException needs an input larger than the
host's memory), so the re-probe is the code and the bound test below, which fails on the old store by construction.

**The fix (design written first: COBOLNET_DESIGN §8.2 "The sort-merge store is an EXTERNAL MERGE SORT in BOUNDED
MEMORY", DESIGN-runtime-library §2.2, docs/CONFORMANCE.md §3 D-SWK).** The records of an executing SORT/MERGE live in
`SortWork` (`src/Cobol.Net.Runtime/IO/SortWork.cs`): one in-memory chunk charged a resident estimate per record, sealed
at `COBOLNET_SORT_MEMORY` (default 128 MiB, GnuCOBOL's default; floor 64 KiB) into a stably sorted run (SORT) or into
each USING stream's run (MERGE) on a temporary file (`SortRunFile`, `HostFile.CreateSortWork`, the fifth HostFile role:
delete-on-close on Windows, unlinked at creation elsewhere, in `COBOLNET_SORT_TMPDIR` or the host temp directory).
Runs of one level merge F at a time (`SortMemory.FanIn`, 2..16), always the last F, so release order is kept; the
sequence phase is in memory when nothing was written (no disk cost) and otherwise a k-way merge (`SortMergeCursor`)
whose tie goes to the earliest run, the one rule that gives §14.9.40.4 GR3 a)/b) and §14.9.24.4 GR4 a)/b). The key
comparison moved, unchanged in its lanes, to `SortKeyColumns` (slot-based: one slot per chunk record or per run head).
`CobolSort.Init` now takes the key descriptors (the store orders runs while the release phase runs), so `Sort` and
`Merge` lost theirs: a shipped-surface change, runtime major 8 to 9 (main's PB1099 took 8 first; the landing finisher's merge raised it over that), ABI pin re-pinned over both surfaces (798F06B49EB99D03). GR6's MERGE
order check runs as records arrive (while checking is enabled) and `Merge` raises it, for the first stream in statement
order, before any merge. The incremental sequencing a RELEASE or RETURN triggers runs under the statement's
`RaisedBySortMerge` mark (§14.6.13.1.3 2)). A work-file I-O failure is a `CobolImplementorFatalException` naming the
directory and `COBOLNET_SORT_TMPDIR`.

**Witnesses.** `SortWorkBoundTests` (unit): a SORT of 20,000 records under the 64 KiB floor (the input at least eight
times the limit) returns the stable order computed by LINQ, its MEASURED peak resident bytes within the limit, more than
eight runs written, the work directory empty after `Close`; a GIVING rewind from disk runs; numeric DESCENDING plus
national keys through runs; a three-stream MERGE keeping input-file order; GR6 on a stream already on disk naming
record 5001; the UTF-16 repertoire (U+FFFF, a lone surrogate, U+0000) and the extent table with its layout object
through a run file; no disk for a fit; a missing directory stopping loudly. `SortWorkBoundDriftTests`: the only record
fields of the sort-merge types are the bounded three (`SortWork._chunk`, `SortRun._records`, `SortMergeCursor._head`),
and the chunk grows only behind the limit test. `SortWorkSpillConformanceTests` (conformance, own process): a SORT of
30,000 records GIVING two files and a MERGE of them back, at 64K and at the default, print the same spec-derived lines,
and the work directory is empty afterwards; a missing work directory ends the run unit naming it.
