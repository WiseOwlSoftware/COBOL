# PB5328 - an upload that hangs decides the verdict, as an upload that fails did before PB3140

**Sites:** `.github/actions/upload-results/action.yml` (the three attempts), `.github/workflows/build-and-test.yml` (the
`Upload test results` steps of `linux-shard`, line 659, and `windows-shard`, line 740, and the job `timeout-minutes`: 15 for
`linux-shard` at line 565, 20 for `windows-shard` at line 674), the drift test `CiArtifactDriftTests`.

## What the files say today

Read in full in the worktree at origin/main 6f80ff6692:

- `action.yml` tries `actions/upload-artifact@v7` three times (30 s, then 90 s apart) under `continue-on-error: true` and,
  when all three fail, warns and passes (its header comment, kb/Work PB3140). A failed attempt is handled.
- Nothing bounds an attempt that never returns. The action has no timeout input on any attempt (`grep timeout` of the file
  finds nothing), and both callers' `Upload test results` steps carry no `timeout-minutes`. The only bound is the job's own
  `timeout-minutes`, and a job cancelled at that limit has no failed step: GitHub reports it `cancelled`.

## What happened

All figures were read by the controller from the GitHub API between 20:30Z and 21:10Z on 2026-11-11.

- githubstatus.com: the incident "Impact across multiple GitHub products including Actions, Pages, and Copilot products",
  created 20:48:12Z. The Actions component read major_outage at 21:02Z and operational at 21:08Z.
- Merge-group runs 43093640955 (PR #1511), 43093642718 (PR #1512) and 43094625899 (PR #1513) each completed `failure` at
  about 21:00Z. Every non-green job was `cancelled` with no failed step, at its job time limit.
- Run 43094625899 "Linux shard 1/5": steps 1 to 13 succeeded (Build, Unit, Characterization, Conformance, INV-1-strong, the
  last ending 20:22:30Z). Step 14 "Upload test results" was in_progress from 20:22:30Z; the job was cancelled 20:35:04Z.
- Run 43094625899 "Windows shard 1/7": Conformance succeeded at 20:24:04Z; "Upload test results" was in_progress from
  20:24:04Z; the job was cancelled 20:40:05Z.
- Run 43093640955 "Linux shard 2/5" (job 130777099579): tests succeeded by 20:18:40Z; the upload was in_progress from
  20:18:40Z; the job was cancelled 20:28:47Z.
- In all three runs `ci-gate` still read `queued` after the run read `completed failure`.

## Why it matters

Every test in those jobs had passed. The artifact service decided the verdict again, which is what PB3140 set out to
prevent: PB3140 covered an upload that fails, and this is the sibling where it hangs. A hung upload also costs each job the
rest of its time limit (12 to 16 minutes in the sampled jobs, read from the timestamps above), and the merge queue removes
the pull request.

## Fix

Bound each upload attempt so a hang becomes a failed attempt, which the existing retry-then-warn path handles. The
implementer chooses the mechanism after checking what a composite action step and `actions/upload-artifact` support. The
drift test `CiArtifactDriftTests` gains the bound, so a fourth caller or a fourth attempt cannot omit it.

**Open question for the implementer (not a decision):** a shard's TRX is an input of `ci-gate`'s name check, so a real
artifact outage still fails `ci-gate`. With the bound it fails quickly and with a message that names the missing artifact,
where today it fails at the job's time limit with no message. The implementer decides whether that is the intended
behavior or whether the name check also needs a rule for an outage.
