# PB530

## Mechanism — picture-clause-p2
The ISO 13.18.40.6 precedence-rule table walk was never written, and PictureAnalyzer.Analyze's symbol loop tests MEMBERSHIP only -- no code anywhere reads a picture symbol's POSITION. PictureAnalyzer.cs:152-155 says so in as many words ('The SR2/13.18.40.6 precedence-rule validation (symbol ORDER/multiplicity -- PIC 99.99.99 etc.) is a separate self-contained table walk, queued (adversarial-review minor, DEVLOG 595)'), and no kb/Work note owns it (grep of kb/Work for 'Table 10' returns only PB66, an EXTFLOAT note; for 'precedence' only expression-precedence notes PB156/PB158/PB195/PB370/PB46/PB91). The consequence is that FOUR 13.18.40.3 syntax rules -- every rule in this clause that constrains WHERE a symbol may stand -- have no implementation at all: SR25 ('+'/'-' shall be leftmost or rightmost, and with two extended editing sign control symbols the first EDITING phrase shall be for the leftmost symbol), SR26 (the currency symbol shall be leftmost or rightmost, with the enumerated optional neighbours), SR27 (no more than one of: a '+' string, a '-' string, a currency string, a '*' string, a 'Z' string), SR29 (for floating insertion, at least one insertion symbol to the left of the decimal point position). The harm is not only the missing diagnostic. The single place that DOES notice a floating string, PictureAnalyzer.cs:274-279, is `foreach (char fsym in new[] { '+', '-', cs }) { ... if (fc >= 2) { floatingExtra = fc - 1; floatChar = fsym; break; } }` -- the `break` takes the FIRST symbol occurring twice or more and never looks for a second string, which is exactly the shape SR27 exists to forbid. So for a two-floating-string picture the compiler does not merely fail to reject: it computes DigitPositions from one run and ignores the other, and every downstream consumer (the SR14 capacity gate, MOVE geometry, FUNCTION LENGTH, the edited image) is derived from a shape the standard does not define. This is the 'model the rule shape, not one case' fix: a position-and-multiplicity walk over the expanded string, driven by the 13.18.40.6 tables, not four hand-written predicates -- one structure that makes the remaining Table 10/11 rows automatic.

### Expected, from the standard
Each of the four pictures shall be rejected with a named diagnostic. ISO/IEC 1989:2023 13.18.40.3 SR25: 'The symbol '+' or the symbol '-', when used, shall be either the leftmost or the rightmost symbol in character-string-1. When extended editing sign control symbols are used and two are specified, the first occurrence of the EDITING phrase shall be for the leftmost symbol in character-string-1 and the second occurrence shall be for the rightmost symbol in character-string-1.' SR26: 'For fixed editing sign control, the currency symbol, when used, shall be either the leftmost symbol in character-string-1, optionally preceded by one of the symbols '+' or '-', or the rightmost symbol in character-string-1, optionally followed by one of the symbols '+', '-', 'CR', or 'DB'.' SR27: 'No more than one of the following may be specified in character-string-1: a string of two or more symbols '+'; a string of two or more symbols '-'; a string of two or more currency symbols; a string of one or more symbols '*'; a string of one or more symbols 'Z'.' with NOTE 5 naming '+++$$$' invalid by name. SR29: 'For floating insertion, at least one insertion symbol shall be specified to the left of the decimal point position.' All four validated with scripts/spec/cite.py --check 13.18.40.3.

### Observed
All eleven illegal pictures compile clean and produce an edit mask. The rule's own worked examples were run as the false-rejection control and every one is accepted and edited CORRECTLY -- SR26 NOTE 4's six strings ('$999+' -> [$012+], '+999$' -> [+012$], '+$999' -> [+$012], '999$+' -> [012$+], '+$$99' -> [+ $12], '$$99+' -> [ $12+] on MOVE 12), SR27 NOTE 5's valid '+$$$' -> [+$12], and SR29's legal '$$.$$' -> [$1.50] on MOVE 1.5 -- so this is a pure under-rejection with no legal-source cost, and a position walk can be added without regressing anything measured here. SR25's second sentence is the one leg where the accepted program also produces a visibly different image from the conforming spelling ([)001.50(] vs [(001.50)]), because the binder pairs each EDITING phrase to its character-1 BY NAME and the source order the rule constrains is never consulted. I deliberately did NOT charge `PIC 99L99` with a single mid-string extended sign symbol against SR25: sentence 1 names only '+' and '-' and sentence 2 is conditioned on TWO symbols, so a single mid-string extended symbol is a 13.18.40.6 Table 8/10 question outside this part.
