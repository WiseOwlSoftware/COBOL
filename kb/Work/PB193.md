# PB193 — OPEN never validates a fixed file attribute, and its set cannot be defined as empty

Split out of [[PB192]] (plan item D-E) so that the DELETE FILE determination does not carry a claim it cannot
support. The two statements looked like one question and are not.

## The obligation

`cite.py --check A.1 "OPEN statement (validation of fixed file attributes)"` → **OK, §A.1 129)**:

> 129) OPEN statement (validation of fixed file attributes). This item is required. This item shall be documented
> in the implementor's user documentation. (14.9.27, OPEN statement, General rule 10)

Like A.1 item 50 for DELETE FILE, it is required AND required to be documented. Unlike item 50, **it cannot
honestly be discharged as the empty set.**

## Why not empty, when DELETE FILE's is

DELETE FILE destroys the file; nothing downstream depends on the connector's description having been right, so
validating nothing costs the program nothing (and the survey found the implementations agree). **OPEN is the
opposite**: the whole point of the check is that everything after it — record length, key structure, code set —
reads the physical file through the connector's description. The survey was unanimous the OTHER way here; among
the attributes implementations validate on OPEN are the key count, the maximum record size and the key
descriptors (GnuCOBOL), and IBM validates a set of seven. Defining ours as empty would mean a program that opens
a file under a contradicting FD gets **silently wrong data** instead of '39' — which is why this note carries
`silent` and `under_rejects` and PB192 does not.

## What is missing

`FileRegistry` has **no persisted physical-attribute catalog**. A COBOL.NET data file on the host is bytes; the
organization, record size, record type and code set the file was CREATED with are nowhere recorded, so there is
nothing for GR10 to compare a connector against. The work is therefore not "add a check" but "give the file
model a durable attribute store", and only then:

- decide and document the validated SET (A.1 item 129), which per §14.9.27.4 GR10 may vary by organization or
  storage medium;
- return **'39'** on a mismatch (§9.1.13.6 item 7);
- pin it with goldens per organization, both directions (mismatch → '39'; match → success), and a case proving
  the attributes SURVIVE process exit — an in-memory catalog would pass a single-process golden while leaving the
  real case, a file written by an earlier run, unprotected.

## Landed

The store landed, and with it the determination. `FixedFileAttributes` is a **persisted fixed-file-attribute
catalog**: a sidecar beside each data file (`<file>.cbattr`) holding the §9.1.6 attributes COBOL.NET records,
written at the two moments §14.9.27.4 makes the OPEN statement CREATE the file — GR18's OUTPUT and GR17's absent
OPTIONAL I-O/EXTEND, which is where §9.1.6 fixes them — and removed with the file by DELETE FILE.
`FileConnector.Open` performs GR10's comparison BEFORE `OpenCore` (GR25 leaves an unsuccessful OPEN's file
unaffected, and the creation arms truncate) and returns `FileStatusCode.FixedAttributeConflict` `'39'`
(§9.1.13.6 item 7). Both OPEN dispatch arms reach it — the plain `FileRegistry.Open` and the sharing-active
`SharedOpenAttempt`.

A **header inside the data file was rejected**: it would stop line-sequential files being plain text and make
every file written by an earlier build unreadable. The sidecar is additive and travels with the file.

**The A.1 item 129 determination**, defined in ONE place (`FixedFileAttributes.Conflicts` with its
`MediumFixesRecordLayout`, the twin of `FileRegistry.ValidateFixedFileAttributes` for GR19) and documented at
`docs/CONFORMANCE.md` row `DOC-A.1-129`: **the validated set VARIES BY ORGANIZATION**, which GR10's third
sentence says in so many words that it may — "The validation of fixed-file attributes may vary depending on
the organization or storage medium of the file." COBOL.NET validates exactly what the file's own storage
FIXES:

- **every organization** — the ORGANIZATION itself, §9.1.6's "primary attribute", of which §9.1.6 names
  exactly three ("There are three organizations: sequential, relative, and indexed"), so the recorded value
  is SEQUENTIAL, RELATIVE or INDEXED and §9.1.7.2's record-/line-sequential distinction is NOT part of it;
- **RELATIVE and INDEXED** — additionally the record type, the minimum and maximum logical record size and
  (indexed) the key count and each key's window, DUPLICATES, SUPPRESS WHEN value and collating sequence,
  because those stores' structure IS those attributes and a disagreeing description cannot interpret them;
- **SEQUENTIAL** — nothing further. §9.1.7.2 puts a sequential file's record lengths in the data and in the
  reading program ("In record sequential files the length of each record is determined by any information the
  implementor may add to the record on the physical storage medium (such as record length headers)" —
  COBOL.NET adds none to a fixed-length one), and §9.1.13.2 items 3, 5 and 7 answer the resulting
  disagreement with the SUCCESSFUL '04', '06' and '09' rather than a refused OPEN.

⚠ **The uniform set was wrong, and measured wrong.** The first landing validated every recorded attribute
for every organization and folded the record delimiter into the organization. That rejected legal source on
this repository's own corpus: six conforming programs went red — `2002/io_status_04`, `2002/rw_suppress`,
`2002/rw_suppress_bare`, `2002/rw_present_when`, `2002/oo_object_report` and
`2023/declined_rw_present_varying_control` — every one of them the write-a-file-then-read-it-back idiom, and
`rw_suppress` degraded into an INFINITE READ loop (OPEN '39' → READ '47' → neither AT END nor NOT AT END →
the `PERFORM UNTIL WS-EOF = 1` never terminates). `2002/io_status_04` is the proof from the standard's own
side: it exists to demonstrate §9.1.13.2 item 3's '04', which a '39' at the OPEN makes unreachable. The
uniform set was also a SECOND MECHANISM for a job `RecordLayoutNotice` already does. The three §9.1.6
attributes outside the set for every organization are excluded because this processor cannot give them
two different values, not because checking was skipped: the code set (§13.18.13.4 GR7 makes it native with
no CODE-SET clause and GR2/GR6 the named alphabet's with one, and COBOLNET1672 refuses every alphabet whose
correspondence is not the identity), the physical record sizes (no blocking; BLOCK
CONTAINS is inert under A.3 item 5), and the RECORD DELIMITER clause (no compiler surface — and the
delimiter distinction that IS realized is a sequential-organization attribute, outside the set above). §9.1.6's own last
sentence is answered NO — shareability is not a fixed file attribute here; a sharing mode is established per
file connector (§14.9.27.4 GR21–GR23) and arbitrated live (§9.1.15 Table 19).

**A file whose attributes are not recorded is not a conflict.** An external tool's file, or one written before
the catalog existed, states nothing for GR10 to compare, so nothing about it is validated — rejecting it would
turn a missing implementor artifact into a rejection of legal programs. `RecordLayoutNotice` is the ONE
mechanism for a sequential record-size disagreement — on a recorded file as much as an unrecorded one,
because the sequential validated set stops at the organization — and is now documented as such.

**Probe** (`<scratch>/PB193/probe/probe1.cob`): a RELATIVE file of 10-byte records reopened INPUT through a
LINE SEQUENTIAL 40-byte FD gave `OPEN-READ-ST=00` and an empty record; it now gives `39`, and the following
READ is `47` (§9.1.13.7 item 7).

**Pinned by** `85/open_fixed_attribute_conflict` — BOTH arms of the determination at the OLDEST edition the
rule applies to: part A over a RELATIVE subject (organization · record size · record type · the matching
control · EXTEND · GR18's re-establishment) and part B over a SEQUENTIAL one (a wider record description
opens '00' and the second READ delivers §9.1.13.2 item 3's '04', while a RELATIVE description over the same
file is still '39') —
`2023/open_fixed_attribute_conflict_ix` (prime-key window and key count) and
`FixedFileAttributeCatalogTests` — which locks what a single-process golden cannot see: the catalog's bytes are
on DISK, an unrecorded or malformed or future-version catalog (an unrecognized organization or record type
included) never manufactures a '39', DELETE FILE takes the catalog with the file across the whole success
family, a sequential file still RECORDS the sizes it does not validate, and
`TheMediumClassification_CoversEveryOrganizationTheConnectorsCanRecord` is the drift guard on GR10
sentence 3's one exercise point.

Rows `GR-14.9.27.4-10` and `DOC-A.1-129` are both OK, and so are `GR-12.4.5.12.4-3` and
`GR-12.4.5.6.4-3` — the two normative rules that say an indexed file's key descriptions, their relative
locations and the NUMBER of alternate keys "shall be the same as that used when the physical file was
created". Neither states a consequence where it is written; GR10's conflict condition is the mechanism that
detects a violation, so until the catalog landed both rules had no effect at all. This also lands **Part 1 of [[PB329]]**, which stays open
for its Part 2 (I-O status '09', the line-sequential character set, row `GR-14.9.30.4-16`) — a different
mechanism.
