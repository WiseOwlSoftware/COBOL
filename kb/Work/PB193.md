# PB193 — OPEN never validates a fixed file attribute, and its set cannot be defined as empty

Split out of [[PB192]] (plan item D-E) so that the DELETE FILE determination does not carry a claim it cannot
support. The two statements looked like one question and are not.

## The obligation

`cite.py --check A.1 "OPEN statement (validation of fixed file attributes)"` → **OK, §A.1 129)**:

> 129) OPEN statement (validation of fixed file attributes). This item is required. This item shall be documented
> in the implementor's user documentation. (14.9.27, OPEN statement, General rule 10)

Like A.1 item 50 for DELETE FILE, it is required AND required to be documented. Unlike item 50, **it cannot
honestly be discharged as the empty set.**

## Why not empty, when DELETE FILE's is

DELETE FILE destroys the file; nothing downstream depends on the connector's description having been right, so
validating nothing costs the program nothing (and the survey found the implementations agree). **OPEN is the
opposite**: the whole point of the check is that everything after it — record length, key structure, code set —
reads the physical file through the connector's description. The survey was unanimous the OTHER way here; among
the attributes implementations validate on OPEN are the key count, the maximum record size and the key
descriptors (GnuCOBOL), and IBM validates a set of seven. Defining ours as empty would mean a program that opens
a file under a contradicting FD gets **silently wrong data** instead of '39' — which is why this note carries
`silent` and `under_rejects` and PB192 does not.

## What is missing

`FileRegistry` has **no persisted physical-attribute catalog**. A COBOL.NET data file on the host is bytes; the
organization, record size, record type and code set the file was CREATED with are nowhere recorded, so there is
nothing for GR10 to compare a connector against. The work is therefore not "add a check" but "give the file
model a durable attribute store", and only then:

- decide and document the validated SET (A.1 item 129), which per §14.9.27.4 GR10 may vary by organization or
  storage medium;
- return **'39'** on a mismatch (§9.1.13.6 item 7);
- pin it with goldens per organization, both directions (mismatch → '39'; match → success), and a case proving
  the attributes SURVIVE process exit — an in-memory catalog would pass a single-process golden while leaving the
  real case, a file written by an earlier run, unprotected.

## Current state, stated accurately

`docs/CONFORMANCE.md` §3's '39' bullet now says this outright: DELETE FILE is conforming by definition, **OPEN is
an unimplemented gap and is tracked, not documented as a determination**. Writing a deferral as if it were a
definition is the worse of the two errors §7's preamble warns about, and doing it here would also be false —
the set is not empty, it is unimplemented.

Row `GR-14.9.27.4-10` is the inventory's carrier; it stays a GAP until the store lands.
