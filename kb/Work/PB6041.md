# PB6041 - a refused clause operand is judged again by the statements and rules that use it

**Repro (train E's build, eafbd52fe2, 2026-11-21):** `python scripts/orchestrator/run_probe.py --root <scratch> --std 85
--exe <cobol.exe> --compile-only E:/COBOL-coord/scratch/w20262131/coderead/out/work-1985-c04/r1_ambiguous.cob`:

    r1_ambiguous.cob(12,32): error COBOL1639: RELATIVE KEY 'RK' does not uniquely identify a data item — 2 declarations match ...
    r1_ambiguous.cob(45,12): error COBOL0862: START on 'REL-FILE': data-name-1 shall be the RELATIVE KEY item '(none)' (§1985:VIII.4.7.3 SR4)

The same second error followed every refused RELATIVE KEY of the read (r1 ambiguous, r2 wrong qualifier, r3 out of order,
r4 two hierarchies, r5 subscripted COBOL2024, r7 its own record COBOL0863 where it named the refused item 'RK', r8 an 85
condition-name rival), at --std 85, 2002 and 2023 alike (2002 and 2023 cite §2023:14.9.41.3 SR5). The path consults no
edition, so 2014 is the same.

**The sweep (probes `E:/COBOL-coord/scratch/w20262132j/src/s1..s8`, the same build):** the mechanism is any rule or
statement that judges a clause operand by its resolved item, with no way to tell "refused" from "absent" or "not a key":
- READ KEY IS and START KEY IS against a RECORD KEY or ALTERNATE RECORD KEY named ambiguously: COBOL0864 (§1985:IX.4.5.3 SR2,
  §2023:14.9.30.3 SR11) and COBOL0862 "neither a record key of the file ..." (SR6); START with no KEY phrase: a COBOL1756
  "not implemented" warning for GR15's prime key (s1, s2).
- START with no KEY phrase on a relative file whose RELATIVE KEY was refused: COBOL0862 "this file control entry has no
  RELATIVE KEY clause", which it has (s7).
- An EXTERNAL file whose RELATIVE KEY (s3, 85 and 2023), LINAGE (s5, 85 and 2023) or FILE STATUS (s4, 2023) operand was
  refused: COBOL1624 "shall be an external data item" about a name that identifies no item; and the run unit's RELATIVE KEY
  and FILE STATUS agreement rules compared a refused describer's missing item with the others'.
- Not affected: RECORD … DEPENDING ON (s6, its users read the item only when it resolved), PADDING CHARACTER (its external
  rule already asks `Item: not null`), WRITE, REWRITE and DELETE (no key judgment), r6's stand-alone RELATIVE KEY (a
  placement refusal; the key still resolves and START names it).

**Fix (root):** the file model says which clause operands were refused, and every user asks before it judges.
`FileModel.RelativeKeyRefused` is set when the resolution leaves no item and when one of the clause's own syntax rules
(`FileControlKeyRules.Screen`, its RelativeKey role) refuses the resolved item; `FileModel.RecordKeyClauseRefused` reads the
refusal marks the RECORD KEY and ALTERNATE RECORD KEY clauses (and their SOURCE operands) already carried;
`FileModel.FileStatusRefused` names the existing invariant (a written operand with no item was reported). START
(`KeyedIoBinder.BindStart`) returns `BoundRejected.OnRefusedClause` (new: a refusal whose report is at the clause, outside
the statement, so it is not on the per-statement ledger; the compile-wide backstop stays) before SR4/SR5, SR6 and GR8/GR15;
READ continues with the default key of reference, as its SR10 refusal does; `ExternalFileConnectorRules.Check` asks the
external rules only of a resolved item and skips an agreement group with a refused describer.

**Tests:** `tests/WiseOwl.Cobol.Tests.Conformance/RefusedFileClauseOperandTests.cs` (28 cases, fixed form): each program
breaks one rule and its error list is exactly that one refusal, at 85 and at the other editions it is legal at.
