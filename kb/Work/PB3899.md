# PB3899 — floating-insertion-edits-untruncated-value: libcob 3.2: MOVE with high-order truncation into a numeric-edited item reads the truncated digit at the leading sign/currency position (zero suppression, floating insertion and BLANK WHEN ZERO wrong)

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S5) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\floating-insertion-edits-untruncated-value.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\floating-insertion-edits-untruncated-value\`.

## Summary

When a MOVE to a fixed-point numeric-edited item truncates high-order digits, GnuCOBOL 3.2 aligns the sending digits
as though the picture's leading sign or currency position (a fixed `+`, `-` or currency symbol, or the first symbol
of a floating insertion string) were a digit position. The sending digit aligned with that position is one ISO
truncates, but libcob reads it, and when it is nonzero it switches off zero suppression and marks the value as
nonzero. The edited result then shows leading zeros that should be suppressed, puts a floating sign at the leftmost
limit instead of before the first nonzero digit, and stores digits where BLANK WHEN ZERO requires spaces. Without
truncation (or when the truncated digit aligned with that position is 0) the same pictures edit correctly.

The night records grouped three further programs under this family; they are other mechanisms, decided separately
below (Split).

## Expected result (per ISO)

ISO/IEC 1989:2023, each citation checked with `scripts/spec/cite.py --check`:

- §14.6.8.2 rule 5): "If the receiving operand is a fixed-point numeric-edited item, further alignment, zero fill or
  truncation, and transfer of digits take place as described in the general rules and editing rules in 13.18.40".
- §13.18.40.4 rule 14): "+ - CR DB These symbols represent the character position(s) into which the editing sign
  control character(s) is (are) placed during editing." and "A currency symbol represents character positions into
  which the currency string will be placed during editing." A fixed sign or currency position is not a digit position.
- §13.18.40.5 rule 6) (floating insertion): "The second floating symbol represents the leftmost limit of the numeric
  data that may be stored in the item." "If truncation occurs, the value of the data that is used for editing is the
  value after truncation". "Any of the simple insertion editing symbols embedded in this string or to the immediate
  right of this string are part of the string." 6) a): a single occurrence of the replacement character is placed
  "into the character position(s) immediately preceding whichever of the following is encountered first: the first
  nonzero numeric character in the item ...", and the positions before it contain spaces.
- §13.18.40.5 rule 7) a) (zero suppression): the replacement character is placed "into any character position
  immediately preceding whichever of the following is encountered first" (the first nonzero numeric character ...).
- §13.18.8.4 rule 1): "the content of the data item is set to all spaces when the item is a receiving operand and the
  value being stored is zero."

So, line by line: `-(6)9` holds six digits; 2010004 truncates to 010004 and edits as `  10004`. `+Z9` holds two
digits; 105 truncates to 05 and edits as `+ 5`. `$$9` holds two digits; 05 edits as ` $5`. `-B-B-B9` holds three
digits at positions 3, 5 and 7; -12345 truncates to -345, the first nonzero digit is at position 3, the embedded B at
position 2 is part of the floating string, so the sign goes there: ` -3 4 5`. `+99 BLANK WHEN ZERO` holds two digits;
100 truncates to 00, the value stored is zero, the item is all spaces: `   `.

Edition: floating insertion, zero suppression and BLANK WHEN ZERO are 1985 features; `docs/VERSION_CHANGE_REFERENCE.md`
records no change to these editing rules between 2014 and 2023, so the rules apply to `-std=cobol2014`.

Edition as recorded by the adjudicator: 2014. `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Fix site (GnuCOBOL 3.2 source, read observationally)

`libcob/move.c`, function `cob_move_display_to_edited` (line 878):

- The counter loop (lines 916-946) adds every leading `+`/`-` (`count_sign`, line 930) and every leading currency
  symbol (`count_curr`, line 928) to `count`, the number of integer digit positions, including a fixed sign or
  currency symbol and the first symbol of a floating string, neither of which holds a digit.
- `src = max - COB_FIELD_SCALE (f1) - count` (line 947) therefore starts one sending digit too far left.
- In the editing loop the `'+'`/`'-'` case (from line 977) and the currency branch (default arm, line 1082) read a
  sending digit at that leftmost position and, when it is nonzero, clear `is_zero` and `suppress_zero` (lines 981,
  1082) before writing the pad character there (lines 993, 1087). The cleared flags stop zero suppression on the
  following `Z` / floating positions, keep the floating sign at the leftmost limit, and defeat the BLANK WHEN ZERO
  test (line 1116).

A fix counts one fewer digit position for a floating string and none for a fixed sign or currency symbol (or skips the
sending digit at such a position without letting it affect `is_zero` / `suppress_zero`). The `ChangeLog` entries for
this function (bug #220, 2016 and 2018; "several optimizations", 2022) concern floating-versus-fixed distinction, not
truncation.

## Draft issue

**Title:** libcob 3.2: MOVE with high-order truncation into a numeric-edited item reads the truncated digit at the leading sign/currency position (zero suppression, floating insertion and BLANK WHEN ZERO wrong)

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu `gnucobol3 3.2-4build1`), Linux x86_64.

Steps: save as `fitrunc.cob`, run `cobc -std=cobol2014 -fformat=free -x -o fitrunc fitrunc.cob && ./fitrunc`.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. FITRUNC.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 S7 PIC 9(7) VALUE 2010004.
01 S3 PIC 9(3) VALUE 105.
01 S5 PIC S9(5) VALUE -12345.
01 SH PIC 9(3) VALUE 100.
01 E1 PIC -(6)9.
01 E2 PIC +Z9.
01 E3 PIC $$9.
01 E4 PIC -B-B-B9.
01 E5 PIC +99 BLANK WHEN ZERO.
PROCEDURE DIVISION.
    MOVE S7 TO E1
    DISPLAY "[" E1 "]"
    MOVE S3 TO E2
    DISPLAY "[" E2 "]"
    MOVE S3 TO E3
    DISPLAY "[" E3 "]"
    MOVE S5 TO E4
    DISPLAY "[" E4 "]"
    MOVE SH TO E5
    DISPLAY "[" E5 "]"
    STOP RUN.
```

Observed: `[ 010004]`, `[+05]`, `[$05]`, `[- 3 4 5]`, `[+00]`.

Expected: `[  10004]`, `[+ 5]`, `[ $5]`, `[ -3 4 5]`, `[   ]`. Each receiver is too small, so the high-order digits
are truncated (2010004 -> 010004, 105 -> 05, -12345 -> -345, 100 -> 00), and ISO/IEC 1989 edits the value after
truncation (13.18.40.5 rule 6: "If truncation occurs, the value of the data that is used for editing is the value
after truncation"; the second floating symbol is the leftmost digit limit). A fixed sign or currency symbol is not a
digit position (13.18.40.4 rule 14). Zero suppression and floating insertion stop at the first nonzero digit
(13.18.40.5 rules 6a and 7a); BLANK WHEN ZERO blanks the item when the value being stored is zero (13.18.8.4 rule 1).
The same receivers fed 010004, 05, 05 and -345 print the expected results.

Cause: in `cob_move_display_to_edited` (libcob/move.c) the counter loop counts a fixed leading sign or currency
symbol, and the first symbol of a floating string, as an integer digit position, so `src` starts one digit to the
left; the `+`/`-` and currency cases then read that (truncated) digit and, when it is nonzero, clear `is_zero` and
`suppress_zero`.
