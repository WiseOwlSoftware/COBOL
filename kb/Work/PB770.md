# PB770 — OPEN — the alphanumeric ALPHABET arm was never given the national arm's validator

Found 2026-09-06 while adjudicating battery #59's differential flip on `syn_definition:1849`
(`AGREE_REJECT -> WE_ACCEPT_THEY_REJECT`). **It was not introduced by a landing** — it was *exposed* by one.
That distinction is measured below, and it is the reason this note exists rather than a revert.

## What the flip actually was

GnuCOBOL's `syn_definition.at:1849` ("ALPHABET definition") expects rc 1 with
`prog.cob:7: error: duplicate character values in alphabet 'TESTME': x'00', A, B`:

```cobol
       SPECIAL-NAMES.
           ALPHABET TESTME IS
                    'A' THROUGH 'Z', x'00' thru x'05';
                    x'41' ALSO x'42', ALSO x'00', x'C1' ALSO x'C2'.
           ALPHABET FINE
                    'A' also 'B' also 'C' also 'd' also 'e' ALSO 'f',
                    'g' also 'G', '1' thru '9', x'00'.
```

Two independent facts, both measured:

1. **The program IS illegal.** `cite.py --check 12.3.7.3 "A given character shall not be specified more than
   once in that ALPHABET clause."` -> `OK §12.3.7.3 14) a)`. In `TESTME`, `x'00'` is specified by
   `x'00' thru x'05'` and again by `ALSO x'00'`; `x'41'`/`x'42'` are 'A'/'B', already inside `'A' THROUGH 'Z'`.
   GnuCOBOL's three names are exactly right. So accepting it is an **under-rejection**.
2. **Our old rejection was for the wrong reason, and the fix that removed it was correct.** The pinned BEFORE
   compiler (`.claude/worktrees/lane1-pin-4af4132c`) failed at `prog.cob(10,21): COBOL0001: unexpected ''A''` —
   the second clause's missing `IS`. `IS` is an **optional word**: rendered off the canonical PDF
   (`python scripts/render-spec-page.py 321`, printed folio 291, "where alphabet-name-clause is:"), the rules
   fall on `ALPHABET`, `ALPHANUMERIC`, `NATIONAL`, `LOCALE`, `NATIVE`, `STANDARD-1`, `STANDARD-2`, `UCS-4`,
   `UTF-8`, `UTF-16`, `THROUGH`, `THRU` and `ALSO` — and on **neither `IS` nor `FOR`**. §5.2.3 therefore makes
   `ALPHABET FINE 'A' ALSO 'B' …` conforming source that we were rejecting. `d09374e2` (PB695 family 1,
   train 15 `de37157c`) relaxed it correctly.

**Proof the under-rejection predates the relaxation** — insert the optional word the BEFORE compiler demanded and
compile the *identical* duplicates with the BEFORE compiler:

```
$ sed 's/ALPHABET FINE/ALPHABET FINE IS/' prog.cob > prog_is.cob
$ lane1-pin-4af4132c/.../cobol.exe prog_is.cob --std 2023 -o b.dll     # -> no diagnostics
$ battery-43/.../cobol.exe        prog_is.cob --std 2023 -o a.dll      # -> no diagnostics
```

Both accept. `AGREE_REJECT` in the baseline was **coincidental agreement**: we rejected legal syntax and the
verdict column could not tell that apart from rejecting an illegal alphabet. A `rejects_legal_source` defect was
holding an `under_rejects` defect invisible — `feedback_green_test_can_hold_a_gap_open`, in the differential.

## The real defect: one arm of a two-arm dispatch was never built

`src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs` builds a literal-phrase alphabet twice — the
**national** arm in `AlphabetBindNationalLiteralPhrase` (`:1045`, operands via `AlphabetOperandsNational`
`:1126`) and the **alphanumeric** arm inline in `AlphabetBind` (`:829`, table at `:897`, operands via
`AlphabetOperands` `:1172`). The national arm validates its rules. The alphanumeric arm validates none of them.

| §12.3.7.3 SR14 rule | NATIONAL arm (c-series) | ALPHANUMERIC arm (b-series) |
|---|---|---|
| a) a given character at most once | **not implemented** — `:1053` `// SR14a duplicate — first wins` | **not implemented** — `:905` `// SR14a duplicate — first wins (diagnostic later)` |
| ordinal within the native set | `COBOLNET0898`, cites SR14 c1 (`:1138`) | via the **CLASS** clause's `LiteralChars`, misfiled (below) |
| noninteger literal shall be of the right class | `COBOLNET0898`, cites SR14 c2 (`:1145`) | **not implemented** |
| one character when THROUGH/ALSO | `COBOLNET0898`, cites SR14 c3 (`:1092`) | **not implemented** — the entry is silently `continue`d |

The alphanumeric arm's `// SR14a duplicate — first wins (diagnostic later)` is the defect writing itself down:
the deferral was deliberate and the diagnostic never came. `feedback_two_arm_dispatch`, fifth instance.

### Four measured legs

All probes `--std 2023` against the battery-#59 compiler
(`.claude/worktrees/battery-43/src/Cobol.Net.Cli/bin/Debug/net10.0/cobol.exe`), sources in
`E:\Temp\claude\E--CobolSharp\49b17747-ce58-4386-8c49-ecb2ce644f8d\scratchpad\b59\probe\`.

**(a) SR14 a) — duplicates, silently accepted.** `'A' 'A'` · `'A' ALSO 'A'` · `'A' THRU 'Z' x'41'` ·
`x'00' THRU x'05' 'Q' ALSO x'00'` — every one compiles clean. Control: `'A' 'B' 'C'` (no duplicate) also
compiles, so the probe is not measuring a dead path.
`cite.py --check 12.3.7.3 "A given character shall not be specified more than once in that ALPHABET clause."` -> OK.

**(b) SR14 b)3 — a multi-character THROUGH/ALSO operand is silently DROPPED, not diagnosed.**
`ALPHABET ALF IS 'AB' ALSO 'C'` and `ALPHABET ALF IS 'AB' THRU 'C'` both compile clean. `:916-925` guards the
range expansion with `operands[0].Length == 1 && operands[1].Length == 1` and then `continue`s — so the whole
entry vanishes from the table with no diagnostic, where the national twin raises COBOLNET0898.
`cite.py --check 12.3.7.3 "Each alphanumeric literal, when a THROUGH or ALSO phrase is specified, shall be one
character in length."` -> OK.

**(c) SR14 b)2 — a noninteger numeric literal is accepted.** `ALPHABET ALF IS 1.5 ALSO 4` compiles clean.
`cite.py --check 12.3.7.3 "Each noninteger literal shall be an alphanumeric literal."` -> OK.

**(d) SR14 b)1 — the range check exists but is MISFILED as a CLASS-clause violation.**
`ALPHABET ALF IS 0 THRU 5` reports:

```
error COBOLNET1671: CLASS : the ordinal 0 does not exist in the native character set (65 536 characters) — ISO §12.3.7.3 SR17 b2
```

There is no CLASS clause in that program. `AlphabetOperands` (`:1180`) calls the CLASS clause's
`LiteralChars(lit)` (`:1304`) with `className` unset, so the ALPHABET path inherits the CLASS descriptor
(`ClassClauseViolation`), the CLASS message text with an empty name, and **the CLASS clause's rule number**.
The rule that governs an ALPHABET ordinal is SR14 b)1, not SR17 b)2 —
`cite.py --check 12.3.7.3 "Each numeric literal shall be an unsigned integer and shall have a value within the
range of one through the maximum number of characters in the native alphanumeric character set."` -> OK,
and `--check 12.3.7.3 "…SR17 b2 text…"` lands under rule 17, a different clause about a different construct.
This is `feedback_a_real_clause_can_answer_a_different_question` shipped as a user-visible diagnostic.

### Two legs that are WRONG ANSWERS, not merely under-rejections

**(e) An unrecognized `code-name-1` is silently reinterpreted as the characters of its own spelling.**
`AlphabetOperands`' word arm (`:1181-1191`) ends `_ => t` — an unknown word becomes its own text, and the
builder assigns each of its letters a collating position. Measured, and it is the whole story of battery #59's
`run_misc:5406`:

```cobol
           ALPHABET A-ASC IS ASCII
           SYMBOLIC CHARACTERS Z1 IS 49 IN A-ASC
           …  MOVE Z1 TO Z   DISPLAY "[" Z "]"
```
prints `[,]`. GnuCOBOL's testsuite expects the program to print nothing (ASCII position 49 is `'0'`). We build an
alphabet whose first four positions are `A`, `S`, `C`, `I` — the letters of the word `ASCII` — and read
position 49 out of *that*. `cite.py --check 12.3.7.3 "The implementor shall specify the names supported for
code-name-1 and code-name-2 in the ALPHABET clause, if any."` -> `OK §12.3.7.3 15)`: an unsupported code-name is
a source error to be diagnosed, and a bare word is not a literal at all (SR14 b)2), so the literal-phrase reading
is not even available to fall back on. Measured on the BEFORE compiler too (`prog_chars.cob`, `CHARACTERS`
spelled in full) — same `,` and `ð`. Pre-existing; train 15 only widened the spellings that reach it.

**(f) A legal ordinal above 255 is masked to 8 bits, from unambiguously legal source.**
`:904` is `int code = c & 0xFF;` over a `new ushort[256]` table, while `LiteralChars` admits ordinals `1..65536`
and the compiler's own COBOLNET1671 text calls the native set "65 536 characters".
`cite.py --check 12.3.7.4 "The ordinal number of a character within the native character set, if the literal is
numeric."` -> `OK §12.3.7.4 7) 1. a.` Probe, with a control that proves the mechanism can move an order:

| probe | alphabet | compare | result | native order |
|---|---|---|---|---|
| control | `'9' THRU '0'` | `'9' < '0'` | `A-LOW` (true) | false — the reversal IS applied |
| **mk1** | `305 THRU 300` | `'0' < '+'` | `A-LOW` (**true**) | **false** — `'+'`=0x2B < `'0'`=0x30 |

Ordinals 300..305 should name U+012B..U+0130, which are *unspecified* characters that must keep their native
relative order; instead `(char)(300-1) & 0xFF` = 0x2B, so `'+'`…`'0'` were reversed. Legal source, no
diagnostic, silently wrong collating sequence — which then flows into every `SORT`, every relational comparison
under `PROGRAM COLLATING SEQUENCE`, and every `SEARCH ALL`. This is what makes the note MAJOR and
`wrong_answer: true`; legs (a)–(d) alone would be `under_rejects` only.

## Why it matters

`ALPHABET` is a *definition* clause: everything downstream — `PROGRAM COLLATING SEQUENCE`, `SORT … COLLATING`,
`CODE-SET`, `CLASS … IN`, `SYMBOLIC CHARACTERS … IN`, `STANDARD-COMPARE` — reads the table this arm builds. A
typo'd character, a vendor code-name, or an ordinal past 255 does not fail; it produces a **different program**
that runs to completion with the wrong answer. The national arm proves the project already knows the shape of
the right validator; only the alphanumeric arm was left with `// diagnostic later`.

Inventory rows this covers, all currently `GAP` with an empty verdict and unclaimed by any note:
`SR-12.3.7.3-14` (the whole SR14 family), `SR-12.3.7.3-15` (code-name support) and `GR-12.3.7.4-7`
(the literal-phrase construction rules). They are named here rather than claimed in `inventory_rows:` because
they are unverdicted, not defectively verdicted; verdict them in the change set that lands the fix.

## The fix shape

**One operand decoder and one table builder, parameterised by class — not two arms that drifted.** The national
arm is the correct one; the alphanumeric arm is the copy that was never finished. `feedback_one_rule_one_place`:

1. Give the alphanumeric arm its own operand decoder beside `AlphabetOperandsNational`, or better, make ONE
   `AlphabetOperands(entry, national)` that enforces the b-series and the c-series from a single table keyed on
   the phrase — SR14 b)1/c)1 (ordinal range), b)2/c)2 (literal class), b)3/c)3 (one character under
   THROUGH/ALSO), b)4/c)4 (total count). A new diagnostic id for the alphanumeric side, or extend COBOLNET0898's
   descriptor to name the phrase; **do not** reuse `ClassClauseViolation`.
2. Delete the `_ => t` word fallback. A word in an alphabet definition is `code-name-1` (SR15) or a figurative
   constant (GR10) — nothing else. Anything unrecognized is a diagnostic naming the supported code-names, and
   `CONFORMANCE.md` gains the SR15 statement of what those are (today: none beyond NATIVE / STANDARD-1 /
   STANDARD-2 / UCS-4 / UTF-8 / UTF-16 / LOCALE, which are keywords, not code-names).
3. Implement SR14 a) in `Assign` on **both** arms: the `pos[code] != sentinel` / `pos.ContainsKey(c)` test that
   today silently returns is exactly the duplicate detection — it needs an `Edition.Error` beside the `return`,
   naming the character, and the "first wins" behaviour stays as the recovery posture.
4. Decide the alphanumeric table's width against `charset_utf16`. Either the repertoire is 256 and `LiteralChars`
   must reject an ordinal above it (then COBOLNET1671's "65 536 characters" text is wrong too), or it is 65 536
   and `pos`/`repByPos` must be sparse like the national builder's `Dictionary<char, ushort>`. It cannot be both,
   and today it is: the range check says 65 536 and the table says 256. **This is an owner-visible design
   question, not a patch** — the answer decides whether leg (f) is a bounds diagnostic or a wider table.

Goldens: the four (a) duplicate spellings including the cross-notation `'A' … x'41'` pair; (b) both multi-char
operand forms; (c) the noninteger literal; (d) an out-of-range ordinal asserting the *ALPHABET* wording and
SR14 b)1 (a negative that would have caught the misfiling); (e) `ALPHABET A IS ASCII` rejected by name; (f) the
`305 THRU 300` collation probe, whichever way item 4 is decided. Plus the positive control `'A' 'B' 'C'`, so a
regression that rejects everything cannot read as green.

## Sweep

- **The other `_ => t` fallback.** `AlphabetOperandsNational` (`:1147-1160`) has the identical word arm. Its
  literal path validates, but an unknown *word* takes the same silent-reinterpretation route. Same fix.
- **Every `LiteralChars` caller.** `:344`, `:360` (CURRENCY literal-7/-8), `:1180` (ALPHABET), `:1224`/`:1227`
  (CLASS). Only the CLASS callers pass `className`, so every other caller that trips the ordinal branch gets the
  CLASS message and the CLASS rule number. Ask of each: does this construct's rule number appear in a
  diagnostic that belongs to a different construct?
- **Mechanical form.** A diagnostic descriptor's `spec_refs` and the clause cited in the *message body* it is
  raised with should agree; where they cannot (a shared helper), the helper must take the clause as a parameter.
  That is checkable by `audit_code_citations.py` and is the general answer to the (d) misfiling.
- **The transcription's own SYMBOLIC CHARACTERS figure note is still wrong** and `CobolSpecialNames.g4:142`
  claims it was repaired. `specs/ISO_COBOL.md:12467` says "`SYMBOLIC` and `CHARACTERS` … are underlined in the
  printed heading"; the `<pre>` above it writes only `<u>SYMBOLIC</u>`, and the rendered folio 292
  (`render-spec-page.py 322`) sides with the `<pre>`. Not this note's defect, but it is a live falsely-restrictive
  claim sitting one line from the format, and a code comment asserting a repair that did not land.
