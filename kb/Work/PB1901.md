# PB1901 — LANDED (wave 1009, group C) — the classification half REFUTED, the crash half fixed

## Landed

**Re-probed.** `FUNCTION UPPER-CASE(G)` over a strongly-typed group with a `USAGE POINTER` leaf compiled and aborted at run time
(`NotImplementedCobolFeatureException: whole-group image of 'G' with a pointer/object-class leaf …`); over a strong group of
display leaves it compiled and ran (`ABCD`).

**The note's rule was the wrong clause (feedback_a_real_clause_can_answer_a_different_question).** §8.5.2.1 gives a strongly-typed
group the class and category of its TYPE-NAME (`cite.py --check 8.5.2.1 "Both the class and the category of a strongly-typed group
item are the type-name specified in the TYPE clause"` -> OK) — but an intrinsic function's ARGUMENT is governed by §15.3 item 2:
"Strongly-typed group items are treated as though they were of class and category alphanumeric, unless they are prohibited as
arguments of a function" (`cite.py --check 15.3 …` -> OK). UPPER-CASE's argument is Table 21's `Anum1`, §15.97.3 r1 does not prohibit
a strong group, and the four functions that do (MAX, MIN, ORD-MAX, ORD-MIN) already carry `ArgPredicateKind.NotStrongGroup`. So
accepting the display-leaf group was CORRECT, `ClassOfItem`'s Alphanumeric answer for a strong group is the §15.3 reading, and the
"classification change" the note proposed (a new `CobolClass` member that would reach `MoveTable16` and the relation gates) would have
REJECTED legal source. No classification change was made; `ClassOfItem`'s comment now records why.

**The crash half was the one-way group image.** A strong group holding a pointer/object leaf is a legal operand whose character image
is its STORAGE image with each such leaf as its 8 reserved placeholder positions, eight SPACES, never the reference
(CONFORMANCE.md A.1 items 56 and 214, D-SLOT) — the image DISPLAY and a MOVE's sending group already read (kb/Work PB244). An intrinsic
function's string argument is the same kind of consumer (it reads the characters and never reads them back), but
`IntrinsicRenderer.StrArgVisitor` asked the two-way `OperandText.AsString`, whose group arm refuses the pointer-bearing group. The
arm DISPLAY carried alone became one reader, `OperandText.AsTransferString`, and DISPLAY, the string-argument visitor and CONVERT's
`StorageArg` (the sibling: `CONVERT(G ANY …)` hit the same refusal) all ask it.

Goldens: `conformance:2002/pb1901_strong_group_pointer_leaf_string_argument` (`UPPER-CASE(G)` = `AB` + 8 spaces + `CD`, `REVERSE(G)`,
`LENGTH(UPPER-CASE(G))` = 12, and the plain strong group) and the boundary `conformance:negative/pb1901-strong-group-numeric-argument`
(`ABS(G)`: a strong group is alphanumeric only where §15.3 type 2 says so), plus the CONVERT sibling
`conformance:2023/pb1901_convert_any_pointer_strong_group` (`CONVERT(G ANY ANUM HEX)` = `61622020202020202020`). The sibling rule PB1527's STRING
half stands as filed.

## The note as filed

Filed 2026-10-01 by the train-1001 lander from the wave-1001 group D implementer report
(`w1001d-PB1233-report.md`, new defect 1).

**Repro.** `scratchpad/w1001d/p/qv_function.cob` (session eccdd4e4): `FUNCTION UPPER-CASE(G)` where `G` is a
strongly-typed group (`TYPEDEF STRONG`) holding a `USAGE POINTER` leaf compiles clean and aborts at run time in the
Tier-C whole-group image island; the same call over a strong group of display leaves is accepted.

**Rule.** §8.5.2.1: "Both the class and the category of a strongly-typed group item are the type-name specified in
the TYPE clause in the data description of the group item" (`cite.py --check 8.5.2.1` → OK). A function argument
that §15 requires to be of class alphanumeric or national therefore cannot be a strongly-typed group.

**Code site.** `src/Cobol.Net.Compiler/Binding/IntrinsicArgumentRules.cs#ClassOfItem`: the group arm returns
`Alphanumeric` for every non-bit, non-national group, strong or not. Same root as kb/Work PB244's STRING / UNSTRING
legs, which wave 1001 D fixed in `StringUnstringBinder.Sr1Offence` / `Sr2OffendingCategory` (train 1001).

**Why it was not fixed in wave 1001.** A new `CobolClass` member for "type-name" reaches `MoveTable16` and the
relation gates, where a strong group IS a legal MOVE sender (§14.9.25.3), so the fix is a classification change
with a sweep over every consumer of `ClassOfItem`, not a one-line arm.
