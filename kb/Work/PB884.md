## The mechanism

`DataBinder.Reports.cs#BindReportEntry` is called integer-2 times by the format-3 replay, and it carries many
`Edition.Error` sites: the SR17 conflict above, the VARYING SR1 check, the non-DISPLAY printable item, the
missing-PICTURE report, and PB565's own SR35/SR6 operand-count screen. **Every one of them multiplies.**

## The remedy

A "report this entry's own syntax rules ONCE" boundary in the replay — the syntax rules are properties of the
WRITTEN entry, the replay produces OCCURRENCES of it. The natural shape is to split `BindReportEntry` into a
screen-the-entry step that runs once and a materialise-this-occurrence step that runs integer-2 times; a
de-duplicating diagnostic sink would hide the symptom and leave the next rule to multiply again.

## The sibling sweep

PB565's note says the VERTICAL (LINE) axis is still refused and will land later — **it will replay the same
way**, so the boundary must be built before it, not after. Any other place a bound entry is constructed more
than once from one source entry (the `SAME AS`/`TYPE TO` expansions, `OCCURS` in the data division proper) is
the same question; none of those currently carry `Edition.Error` calls, which is why this is MINOR and
process-only rather than a wrong answer.

## Rows

No row is claimed. `SR-13.15.3-17` is a GAP row but the RULE is implemented and correct — what is wrong is the
multiplicity, which is not what that row measures. Claiming it would make a GAP row look owned by a note that
does not close it.
