# PB912 — OPEN — a capability limit wearing a rule's clothes

Source: the `PB432` report, "New defects" item 3. **The report's repro does not reach the defect** — see
below — so this note is built from a probe that does.

## The measurement

`<scratch>/reg7/probe/g4_eval_udf.cob`, `--std 2023`. `UFPICK` is a user-defined function
(`FUNCTION-ID. UFPICK.`) declared in the REPOSITORY paragraph:

```cobol
           EVALUATE FUNCTION UFPICK(S) IS ALPHABETIC
              WHEN TRUE DISPLAY "ALPHA"
              WHEN FALSE DISPLAY "NOTALPHA"
           END-EVALUATE
```

```
g4_eval_udf.cob(11,12): error COBOLNET1509: a function reference in an EVALUATE selection subject
(evaluated once per statement, §14.9.13.4 GR3 — this lowering re-binds subjects per WHEN) requires an
activation cardinality this implementation does not yet realize for that operand position
(ISO §8.4.3.2.4 GR1/GR6a; §14.9.28 GR12/GR13 / §14.9.13) — move the reference to a preceding COMPUTE
[the same line, again — one per WHEN]
```

**The control**, `g5_eval_udf_value.cob`: the same user function as a plain VALUE subject,
`EVALUATE FUNCTION UFPICK2(S) WHEN "AB  " …` → prints `HIT`. So the refusal is not about user functions,
not about EVALUATE, and not about this program — it is about ONE subject shape.

⚠ **Two probes that did NOT reach it, recorded so the next reader does not repeat them.**
`EVALUATE FUNCTION LENGTH(FUNCTION TRIM(S)) > 1 …` draws `COBOL0001: unexpected '>'` — that is the
GRAMMAR's `evaluateSubject : booleanLiteral | valueOperand (IS? NOT? classCondition)?`, i.e. **PB842**'s
defect (a relation-condition subject is unmodelled), not this one.
`EVALUATE FUNCTION TRIM(S) IS ALPHABETIC …` prints `ALPHA` — an INTRINSIC does not enter `UdfBinder.Pending`,
so only a user-defined function stages the residue. `Pending.Count <= mark` at
`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/UdfBinder.cs:375` is the reason, and it is why the note
names a `FUNCTION-ID` program as the repro.

## The rule

```
$ python scripts/spec/cite.py --check 14.9.13.4 "truth value"
OK  §14.9.13.4 3)  (General rules)
    3) At the beginning of the execution of the EVALUATE statement, each selection subject is evaluated and
       assigned a value, a range of values, or a truth value as follows:
```

GR3 assigns a CONDITION subject its truth value **once, at the beginning of the statement**, exactly as it
assigns a value subject its value. The activation window is therefore STATEMENT-SCOPED for both, and the
cardinality §8.4.3.2.4 GR1/GR6a asks for is one activation — which this implementation already realizes for
the value subject (**PB394** landed that: the slot binds the subject once and materializes it). The
condition arm was left behind. So the operand window the message says cannot be realized IS realized, ten
lines away, for the sibling subject kind.

## The code site

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs:408` and `:488` — the two surviving
`UdfStagePerEvaluationResidue` calls. `:408` is the `pair.Subject is EvaluateSubjectOperand.Condition` arm
and is what the probe hits; `:488` is the partial-expression object arm. The missing piece is the
condition→boolean-operand bridge in the bound tree: a condition subject has no "one materialized truth
value" carrier the way a value subject has its intermediate result item.
