# R51 — the text model for a modern Unicode-era COBOL

**Asked 2026-09-29** (owner, in the PB1093 discussion): "What is the best design for a modern implementation of
COBOL given the prevalence of Unicode?" — answered with the layered design below; owner: **yes**.

## The decision

1. **Text in memory is Unicode by default.** Alphanumeric and NATIONAL items hold CHARACTERS, not bytes:
   `PIC X(10) VALUE "héllo"` holds five characters. NATIONAL stays UTF-16 (a supplementary character takes two
   positions — documented, with a validity check so no operation splits a surrogate pair). Collation is ordinal
   (code-point order) by default, locale collation (LC_COLLATE, §8.3.3.6.4) as the opt-in; normalization is an
   explicit intrinsic, never silent.
2. **Bytes and characters meet at ONE law, applied wherever a byte becomes a character or back** (as built; the first proposal was a per-leaf record codec, replaced after measurement — PB1759 step 0, design D29): **byte 0xFF is the character U+FFFF (HIGH-VALUE); every other byte b is the character U+00bb; a character's byte is its low byte.** Numeric byte forms (binary, packed, IEEE, pointer, bit), national UTF-16BE pairs and the fixed-record file medium all cross through it (`StorageByte`, `FileCharacterSet.ToChannel/FromChannel`), so no layout knowledge is needed at the medium and a REDEFINES numeric view of the same bytes reads 0xFF as a number. Hex literals `X"FF"` stay U+00FF in memory.
3. **The external encoding is explicit per device.** Source, DISPLAY, ACCEPT, environment and LINE SEQUENTIAL
   files default to UTF-8. Fixed-length record files (sequential, relative, indexed, sort, report) default to a
   single byte per alphanumeric character position (ISO 8859-1) because UTF-8 makes a record's byte length vary
   and breaks record-number positioning; the FD CODE-SET clause (§13.18.13) selects any other encoding, and
   Unicode inside such records is NATIONAL.
4. **HIGH-VALUE / LOW-VALUE are the extremes of the collating sequence** (§8.3.3.6.4 GR6/GR7; §12.3.7.4 GR8/GR10),
   which for the native UTF-16 alphanumeric repertoire is U+FFFF / U+0000 (R52), and cross a byte medium as that
   medium's extreme byte.

## What ISO and GnuCOBOL say (measured 2026-09-29)

ISO §8.1.2: the implementor specifies the alphanumeric and national character sets and their encoding; §3.129 the
native collating sequence is implementor-defined; §13.18.13 CODE-SET converts at the medium — the layered design is a
conforming implementor choice. GnuCOBOL 3.2 (`cobc/reserved.c`, `typeck.c`, `codegen.c`): alphanumeric is a 256-value
byte model, HIGH-VALUE `0xFF`, LOW-VALUE `0x00`, no file conversion. Precedence (CLAUDE.md rule 1): ISO controls; the
latitude here is answered by the owner's Unicode requirement rather than GnuCOBOL's byte model, and is documented
(docs/CONFORMANCE.md DOC-A.1-31 / DOC-A.1-115, and design doc COBOLNET_FILES_DESIGN D29).

## Supersedes

R47 in part: R47's "one byte per character, a character above U+00FF is REFUSED" stays for FIXED-RECORD files with
no CODE-SET (except HIGH-VALUE, R52); for LINE SEQUENTIAL files the default becomes UTF-8 (PB1760).

## Landing (2026-09-29)

Implemented by PB1759 (the storage-byte law and HIGH-VALUE U+FFFF) and PB1760 (the per-file encoding; LINE SEQUENTIAL UTF-8). Item 2's mechanism is the storage-byte law above (D29 records why the per-leaf codec was rejected); items 1, 3 and 4 are as decided. Item 4 on a CODE-SET medium: HIGH-VALUE is written as the coded character set's highest code unit (`CodeSetConversion.HighUnit`). Item 3, fixed-record files: one byte per alphanumeric position (ISO 8859-1) plus the law; LINE SEQUENTIAL: UTF-8 (BOM skipped on read, none written; invalid UTF-8 -> status 09 with the bytes kept). The accepted cost is generalized: a real U+00FF that passes through ANY byte (the medium or a byte-form storage position) returns as HIGH-VALUE (DOC-A.1-31).
