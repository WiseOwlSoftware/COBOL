# PB686 — LANDED — the boundary is a recorded determination

Found 2026-09-05 by the `PB673` implementer (report §"New defects" 2), which deliberately kept its LINAGE goldens
away from the boundary so they would not pin a contested reading. Adjudicated and landed 2026-09-05.

## The two readings

§14.9.51.4 GR26 (`cite.py --check 14.9.51.4 "an end-of-page condition occurs when the lines written by a WRITE
statement do not fit within the"` → OK): arm a) as printed says the page end is reached *"when the associated
LINAGE-COUNTER is equal to or exceeds the page size"*; arm b) requires the counter *"equal to or exceeds the footing
start and is less than the page size"*. Read literally, `counter == page size` is arm a) (overflow). The code
(`src/Cobol.Net.Runtime/IO/SequentialConnector.cs#AdvanceLinageCounter`) reports OVERFLOW only when the post-advance
counter is GREATER than the page body, so `counter == page size` is a FOOTING end-of-page.

**The printed text is not a transcription defect.** Both arms were re-read from the PDF text layer at printed
page 792 (PDF page 822) and match `specs/ISO_COBOL.md` word for word. The contradiction is the standard's.

## THE DETERMINATION (2026-09-05)

**Both arms are evaluated on the counter the write's advancing operation produces, and the boundary is STRICT:
`counter > page size` is arm a); `footing start ≤ counter ≤ page size` is arm b).** The current code is correct
and stays; what changes is that the reading is now RECORDED rather than argued in a comment —
`docs/CONFORMANCE.md` §4, "DETERMINATION — the §14.9.51.4 GR26 a)/b) boundary at LINAGE-COUNTER = page size".

**Why the literal reading is rejected.** It is not a matter of taste: three other rules die under it.

1. **§13.18.34.4 GR2** (`--check 13.18.34.4 "specifies the number of lines that may be written or spaced on the
   logical page"` → OK) makes all `page size` lines writable. Under arm a) read literally, a write whose counter
   lands ON the page size is pushed to the first line of the NEXT page, so the line NUMBERED page size can never
   receive a record — an N-line body would hold at most N−1 written lines, on every page, forever. **And that is
   true of a file with no FOOTING phrase at all**, which is the arm a FOOTING-only fixture cannot see.
2. **§13.18.34.4 GR3** (`--check 13.18.34.4 "The footing area is the area of the page body between the footing
   start and the page size, inclusive."` → OK) puts that same line INSIDE the footing area, which arm b)'s
   "less than the page size" clamp then excludes. b) could never fire on the last line GR3 gives it.
3. **GR26's own lead sentence** conditions the whole rule on lines that "do not fit within the current page body".
   A record landing on the last body line fits.

**Corroboration from the other side.** §13.18.34.4 GR7 c) 1 (`--check 13.18.34.4 "the value of LINAGE-COUNTER is
implicitly incremented to exceed the value specified by integer-1"` → OK) is the standard's own device for making
arm a) fire on ADVANCING PAGE, and it says the counter is incremented to **exceed** integer-1 — not to equal it.
Equality would have sufficed had equality been the trigger.

**The phase question the earlier note posed** ("is the counter the line ABOUT to be written or the line just
written?") has no answer that saves the printed text, and that is worth recording so it is not re-litigated:

- Read on the counter BEFORE the write's advance, arm a)'s ACTIONS come out exactly right for both the AFTER and
  the BEFORE phrase — but arm b) then misses any `ADVANCING n > 1` that jumps INTO the footing area from below it
  (page 5, footing 4: from counter 3, ADVANCING 2 prints on line 5 and neither arm fires), contradicting b)'s own
  lead ("causes printing or spacing within the footing area").
- Read on the counter AFTER the advance, arm b) is right and arm a) is the GR2/GR3 disaster above.

So the arms are not phase-consistent as printed, and the determination keeps the one reading under which GR1, GR2,
GR3, GR7 c) 2/3/4 and GR26's lead sentence are all true, at the cost of the "equal to" in a) and the upper clamp
in b). Note that under the determination a) and b) remain a clean PARTITION of `[footing start, ∞)` — which is
plainly what the printed clamp in b) was trying to express.

## The survey does not split (2026-08-30 standing answer)

- **IBM Enterprise COBOL for z/OS 6.3 Language Reference (WRITE statement).** Footing END-OF-PAGE: the write
  "causes the value in the LINAGE-COUNTER special register to equal or exceed the value specified in the WITH
  FOOTING phrase of the LINAGE clause" — **no upper clamp at all**. Page overflow: "a WRITE statement, if
  executed, would cause the value in the LINAGE-COUNTER to **exceed** the number of lines for the page body".
  That is this determination, comparison for comparison.
- **Micro Focus Visual COBOL, LINAGE clause.** "The footing area is composed of the area between footing-line and
  page-lines, **inclusive**."
- **GnuCOBOL.** Documented as passing the NIST CCVS-85 suite with no failures. That suite decides the question on
  its own — see below — so its behaviour at the boundary is fixed by it.

## NIST CCVS SQ201M decides it empirically, in this repo

`tests/nist/programs/SQ201M.cob` uses `LINAGE IS 50 LINES WITH FOOTING AT 45` and, on the end-of-page branch,
performs `PRINT-FOOTING` **6 times** — the program's own text calls them "6 FOOTING LINES" and asserts "50 LINES
SHOULD PRINT IN THE PAGE BODY". Each footing line reports the counter it saw. The canonical golden
`tests/nist/valid/SQ201M.txt` reads:

```
THIS IS LINE 001 OF 6 FOOTING LINES.  LINAGE-COUNTER SHOULD BE 45.  LINAGE-COUNTER IS 45.
...
THIS IS LINE 006 OF 6 FOOTING LINES.  LINAGE-COUNTER SHOULD BE 50.  LINAGE-COUNTER IS 50.
```

Under the literal reading the fifth footing write (counter 50 == page size) would overflow, reposition and reset
the counter, and the sixth line would report 1 against a required 50. SQ201M is in
`tests/Cobol.Net.Tests.Conformance/corpus-green-baseline.txt` and is green, so the compiler already answers the
way the standard body's own validation suite requires. **This is corroboration, never the authority** (CLAUDE.md
rule 1) — the derivation above is what decides — but it removes any doubt that the determination is the
industry's reading.

## Found on the way, NOT fixed here (its own note)

`WriteBeforeAndAfter` calls `AdvanceLinageCounter` twice, and that method opens with an unconditional
`EndOfPage = false`. So the SECOND advancing operation of a COBOL-2023 `WRITE … BEFORE ADVANCING n AFTER
ADVANCING m` silently discards an end-of-page condition raised by the FIRST. Measured on this tree with
`LINAGE IS 4 LINES` and `WRITE P-REC BEFORE ADVANCING 4 LINES AFTER ADVANCING 0 LINES`: the page overflows
(`LINAGE-COUNTER` reads 001 afterwards, so the GR7 c) 4 reposition happened) and the `NOT AT END-OF-PAGE` branch
runs. §14.9.51.4 GR27 requires control to transfer to imperative-statement-1. Silent wrong answer, outside this
adjudication's mechanism.
