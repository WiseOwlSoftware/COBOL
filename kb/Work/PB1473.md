## Finding — `subscripts` (under-rejects; rows `SR-8.4.2.3.3-6`)

**Mechanism.** The Format-2 (table) SORT binder never reads the WRITTEN subscripts of data-name-2: SortBindTable consumes only ResolveTableOperand(...).Item (TableOperand's subscript count is unread), so §8.4.2.3.3 SR6's 'rightmost or only subscript' position for ALL is never screened

**Repro.** 01 T2. 05 R2 OCCURS 2. 10 E2 PIC 9 OCCURS 3.
PROCEDURE DIVISION. SORT E2(ALL, 1) DESCENDING. DISPLAY T2. STOP RUN.  (--std 2023)

**Expected from the spec.** Compile-time refusal: §8.4.2.3.3 SR6 admits ALL in a SORT statement only 'as the rightmost or only subscript of a table in the table format of a SORT statement'; §14.9.40.3 SR13 'Subscripting shall be specified in accordance with 8.4.2.3, Subscripts.' ALL in the first of two positions is neither.

**Observed / reasoning.** Compiles with only a COBOLNET1756 deferral WARNING ('SORT of table E2 nested under another OCCURS (deferred)') and aborts at run time on NotImplementedCobolFeatureException - identical to the LEGAL twin `SORT E2(1, ALL)`. The nested-subject deferral is kb/Work PB1055 (open, rejects-legal-source, owns SR-14.9.40.3-13); this is a separate mechanism - PB1055's fix binds the outer subscripts but nothing in SortBindTable checks where ALL stands, so the illegal spelling would then compile and sort. Fix shape: read the subject's segments once (the SubscriptSegmentsOf reading ResolveTableOperand already performs) and screen ALL-position and count per SR3/SR5 e)/SR6 in the SORT arm; land with PB1055.

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SortBinder.cs#SortBindTable; src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs#ResolveTableOperand

## What the fixer owes

Read the subject's segments once (the SubscriptSegmentsOf reading ResolveTableOperand already performs) and screen ALL's position and the subscript count per SR3 / SR5 e) / SR6 in the SORT arm. Land WITH PB1055 (which binds the outer subscripts). Negative golden.
