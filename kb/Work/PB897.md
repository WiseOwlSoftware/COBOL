# PB897 — LANDED — a script that removes the thing it is about to fail to produce

Source: the `PB405` report, "New defects". This is the note behind the "two `ExternalCorpusPopulation` reds
are the known worktree shape" sentence every implementer brief carries — **a known red that every agent is
told to ignore is a gate that has stopped gating** (memory `green_gates_arent_evidence`).

## The code site, read on this tree

`scripts/fetch-gnucobol-tests.ps1`, the EXTRACT block:

```powershell
if (Test-Path $DestDir) { Remove-Item $DestDir -Recurse -Force }      # <-- destroys first
New-Item -ItemType Directory -Force -Path $DestDir | Out-Null

$tar = Get-Command tar -ErrorAction SilentlyContinue
if (-not $tar) { Write-Error "tar not found on PATH (needed to unpack .tar.xz)."; exit 1 }

& tar -xf $ArcPath -C $DestDir --strip-components=1 "gnucobol-$Version/tests"
if ($LASTEXITCODE -ne 0) { Write-Error "extraction failed (exit $LASTEXITCODE)"; exit 1 }
```

Two independent faults, and BOTH must be fixed:

1. **`$ArcPath` is a drive-letter path.** GNU tar parses `E:\...` as `host:path` and tries to connect to
   host `E` — `Cannot connect to E: resolve failed`, exit 128. Which `tar` is on PATH is an accident of the
   agent's environment (Git-for-Windows ships GNU tar; Windows ships bsdtar as `System32\tar.exe`), so the
   failure is per-machine and looks like flakiness.
2. **The destination is removed BEFORE the extraction is known to work.** A failure therefore leaves
   `tests/external/gnucobol` EMPTY rather than stale, and the two `ExternalCorpusPopulationDriftTests` fail
   for every subsequent run until someone notices.

## ⛔ The repair the fixer must NOT make

`--force-local` fixes fault 1 for GNU tar and is REJECTED by bsdtar, so it converts a failure on one machine
into a failure on the other. The repair is either to probe the tar flavour (`tar --version` naming
`bsdtar` vs `GNU tar`) or — better, because it needs no probe — to `Push-Location` to the archive's
directory and pass a RELATIVE archive name, which neither implementation misreads.

Fault 2 is fixed independently: extract into a temporary directory and swap it in only on success, so a
failed fetch leaves the previous corpus intact and the drift tests keep measuring something real.

## Repro

`bash scripts/build-local.sh "~Drift"` in a fresh worktree on a machine whose PATH `tar` is GNU tar.

None — this is tooling, not a spec rule.

## Landed — 2026-09-19 (wave 39, group CORPUS-FETCH-AND-GUARD)

Re-probed on this worktree before any edit, and the note held: with Git-for-Windows' GNU tar first on PATH the
script destroyed a seeded `tests/external/gnucobol` and then failed — `/usr/bin/tar: Cannot connect to E: resolve
failed`, exit 128, destination left with 0 entries. `--force-local` was re-confirmed as the WRONG repair
(`tar.exe: Option --force-local is not supported`, bsdtar exit 1), and a bare archive name from the archive's own
directory was confirmed to work on BOTH (exit 0 each).

**A THIRD fault surfaced once the first two were out of the way, and it is the one that actually kept the corpus
empty here:** Git-for-Windows' GNU tar cannot read a `.tar.xz` at all — it execs an `xz` binary it does not ship
(`tar (child): xz: Cannot exec: No such file or directory`, exit 2). So even a correctly-spelled invocation
fetched nothing on that host. Fixing only the note's two faults would have left the gate red.

The repair, all in `scripts/fetch-gnucobol-tests.ps1`, is one function — `Invoke-CorpusExtraction`, the ONLY place
the corpus tree is replaced: extraction lands in a staging directory and is swapped in only after tar exited 0 AND
the payload was verified non-empty (nothing is deleted before its replacement exists; a failed swap restores the
previous tree); the archive is named RELATIVE to its own directory under `Push-Location`, which neither tar
misreads; and the tar is chosen by ATTEMPTING the extraction down an ordered candidate list (`Get-TarCandidates`:
Windows' System32 bsdtar first, then every `tar` on PATH, case-insensitively deduped) rather than by trusting
`Get-Command` — capability MEASURED, not deduced, which the staging directory makes free. Every failure prints one
`FETCH FAILED: <cause>` line naming each candidate and its exit code, and exits non-zero.

⛔ The two-arm sweep: **both** `scripts/build-local.ps1` and `scripts/build-local.sh` fetch the corpus, and the sh
arm discarded the exit code with `|| true` while the pwsh arm read `$LASTEXITCODE`. Both now capture it, print the
cause with the exit code, set `RC=1`, and append `— EXTERNAL CORPUS FETCH FAILED, POPULATION UNMEASURED` to the
verdict line: a gate that could not measure its population no longer reads as green, and the reds are
ATTRIBUTABLE instead of ignorable.

Witness: `scripts/fetch-gnucobol-tests.ps1 -SelfTest` drives the real `Invoke-CorpusExtraction` over a synthetic
**`.tar.xz`** (the format that exposed fault 3 — a plain `.tar` fixture would have passed on the broken host) in a
temp sandbox, asserting the FAILURE branches preserve the prior corpus, and `ExternalCorpusFetchTests`
(tests/Cobol.Net.Tests.Unit) runs it and asserts the individual check lines so a self-test reduced to its happy
path cannot keep printing PASS. **Proved failing first:** with the two faults re-introduced the self-test reports
`FETCH SELF-TEST: FAIL (4 of 10 checks)` and the fact reports `Failed: 1` — under bsdtar too, since delete-first is
tar-independent. After the fix the real fetch succeeds in the environment that broke it (36 autotest .at files,
exit 0) and the self-test is 10/10 under both tar flavours.

The four workstream brief templates and `.claude/skills/workstream/SKILL.md` no longer call the two population
reds "the known worktree shape": they are environmental ONLY when a `FETCH FAILED:` line names the cause.
`docs/rearchitecture/DESIGN-test-build-ci.md` §3.10 carries the fetch as an instrument-gate row.
