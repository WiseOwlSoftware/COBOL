# PB208

Found 2026-08-31 while measuring [[PB188]]'s reachability — the Format 2 (table) VALUE turned out to be the one
path that reaches the emitter with an unvalidated literal, and measuring it exposed a second, larger defect.

**MEASURED** on 8ca74a3d, at `--std 2023` **strict**, compiling CLEAN with no diagnostic at all:

```cobol
01 G.
   05 A PIC X(2) VALUE "AA".
   05 B PIC 9(4) COMP OCCURS 2 VALUE "0012" FROM (1) TO (2).
   05 C PIC X(2) VALUE "CC".
01 R REDEFINES G PIC X(8).
```

`B(1)`/`B(2)` display `0000`, and the group's bytes are `65 65 00 00 00 00 67 67` — **the table VALUE is gone**.

**TWO INDEPENDENT DEFECTS, one shape.**

1. **The literal is never screened.** `DataBinder.ValidateTableValues` checks only SR18–SR22 (the subscript
   rules); the per-occurrence literals from `BuildTableValueSpecs` never pass through
   `ValidateValueCategory`, which is where §13.18.63.3 SR2 ("If the category of the subject of the entry is
   numeric, all literals in the VALUE clause shall be numeric") lives. SR2 is an ALL FORMATS rule, so it governs
   format 2 as squarely as format 1 — the format-1 path rejects this literal (COBOLNET1657) and the format-2
   path accepts it silently. The [[feedback_two_arm_dispatch]] shape again, on the VALUE clause's two formats.
2. **`GroupImageCodec.ImageInitOf` ignores `TableValues` entirely.** It reads `item.RawValue`, which is null for
   a table VALUE (the two carriers are mutually exclusive on `DataItem`), and falls through to the zero
   encoding. So for ANY image-stored leaf — a Tier-B REDEFINES member, an EXTERNAL cell, a BASED record, an OO
   backing — a format 2 VALUE is silently discarded, whatever its literal. §13.18.63.4 GR12 ("A format 2 VALUE
   clause initializes a table element to the value of literal-1") is simply not implemented on that lane; the
   record-struct lane implements it in `ValueInitializer.TableValueInit` **for an ELEMENTARY table only** —
   `FieldInit` guards that route `item.TableValues is { Count: > 0 } && !item.IsGroup`, so a GROUP entry carrying
   a format 2 VALUE is unimplemented on BOTH lanes. **This half is independent of the literal's category** and is
   the wrong-answer core.

**NOT a duplicate of [[PB188]].** PB188 is the seed WIDTH of an image-stored leaf; this is the seed being absent.
⛔ **Correction 2026-08-31 (the review fleet):** this note used to add "PB188's arms were proved dead … precisely
because this path never reaches them". That is wrong, and it is wrong in a way that matters — half 1 of THIS note
(the missing SR2 screen) is exactly what keeps PB188's arm ALIVE. `ImageInitOf` never gets that far, but
`ValueInitializer.InitializerFor` does: `TableValueInit` feeds it the raw quoted text as `rawOverride`, so a
promoted numeric-**DISPLAY** leaf (`AddNumericDisplayLeaves`) reaches PB188's width arm with quotes intact and
its answer changed. Measured, with a golden — see PB188's correction. What `ImageInitOf`'s blindness kills is the
COMP half of the population, not the whole of it.

**FIX SHAPE.** (1) Route the format 2 literals through `ValidateValueCategory` in `ValidateTableValues`, per
occurrence, with the same strict/permissive posture the format 1 path has — one screen for both formats.
(2) Teach `GroupImageCodec.ImageInitOfOne` the `TableValues` carrier so an image-stored table composes its
per-occurrence images from the SAME `ResolveTableValueMap` the record-struct lane uses (GR12–GR15 — the map is
already extracted and static). Pin byte-level through a REDEFINES `X` view with `FUNCTION ORD`, and pin the
FOLLOWING member's offset so a displacement can never come back.

## LANDED 2026-09-04 — both halves, and the fix shape held

**HALF 1 — the format-2 literals now ride the ONE screen.** The four checks that made up the format-1 VALUE
screen sat INLINE at their call site in `BindEntry` (`ValidateValueCategory`, then `ValidateNumericValue`, then
the VCR-86 `ConstructRegistry` gate, then the VCR-34 COBOLNET1570 size check), which is exactly why a second
carrier could arrive and be screened by none of them. They are now one funnel, `DataBinder.ScreenValueLiteral`,
and `ValidateTableValues` calls it PER OCCURRENCE-LITERAL, storing the text it returns — so the `--permissive`
numeric rewrite reaches the emitter's per-occurrence `rawOverride` exactly as it reaches `item.RawValue`.
§13.18.63.3 SR2 is an ALL FORMATS rule and SR16 carries SRs 10–15 into format 2 ("Syntax rules 10, 11,12,13,14,and
15 above apply"); both re-checked with `cite.py --check`. Measured, same source, `--std 2023`:

| | before | after |
|---|---|---|
| strict | *(no diagnostic at all)* — `B1=0000 B2=0000`, group `65 65 00 00 00 00 67 67` | `error COBOLNET1657 … Format 2 VALUE FROM (1)` |
| `--permissive` | *(no diagnostic)*, seed absent | `warning COBOLNET1657`, `B1=0012 B2=0012`, group `65 65 00 0C 00 0C 67 67` |

**HALF 2 — `ImageInitOf` learned the `TableValues` carrier.** `ImageInitOf`'s
`Occurs is n and > 1 ? StrRepeat(one, n)` composed ONE occurrence image and repeated it, and `ImageInitOfOne`
read only `item.RawValue` (null for a table VALUE), so every occurrence took the VALUE-LESS default and the seed
was discarded for any leaf the aliasing put on the image lane. It now composes per-occurrence images from the
SAME `ValueInitializer.ResolveTableValueMap` the record-struct lane uses (now `internal static` — one map, GR12–GR15
read once), through an `ImageInitOfOne` `rawOverride` parameter mirroring `InitializerFor`'s. Every image-stored
backing inherits it, because `ImageInitOf` is THE seeder for all of them since the PB164 consolidation.

**THE ONE PREDICATE.** Both emit lanes now guard the shape with `!item.IsGroup` at a point where the forest
exists — `ValueInitializer.FieldInit` already did, `GroupImageCodec.ImageInitOf` now does.

**⚠ WHAT THIS NOTE CLAIMED THAT DID NOT HOLD.** The fix shape said the group leg could be closed by making
`ValidateTableValues` reject a group subject. It cannot: that method runs at ENTRY BIND, where `Children` is
still empty and `IsGroup` is FALSE for every subject. The conjunct was written, built, and MEASURED to change
nothing (`05 GT OCCURS 2 VALUE "ABCD" FROM (1) TO (2).` still printed spaces), then removed rather than shipped
as a dead guard. A GROUP entry's format-2 VALUE is a group-level VALUE — SR16 carries SR13/SR14 onto it, its
subject screen is `CheckGroupValueDeclarations` (which already reads BOTH carriers) and its area deposit is
`GroupValueSlicer.AreaTextOf` — so it belongs to the group-level VALUE mechanism [[PB206]]/[[PB207]] own, not
here. Filed as a defect paragraph in the PB208 report rather than fixed across a mechanism boundary.

**GOLDENS.** `tests/conformance/2023/pb208_table_value_image_seed.{cob,out}` (PB208TVI) — GR12/GR13 byte-level
through a REDEFINES `X` view with `FUNCTION ORD` plus the FOLLOWING member's offset, and GR13/GR14/GR15 on the
image lane. Proved able to fail: with the `ImageInitOf` arm reverted it reds in FOUR places
(`D=[0000][0000]`, `DB=[1][1][1][1]`, and all three alphanumeric groups blank).
`tests/conformance/negative/pb208-table-value-alphanumeric-on-numeric.{cob,err}` (PB208N1) — the SR2 screen,

`Format1AndFormat2_ScreenTheSameLiteralAlike` (nine literal/picture pairs × strict and permissive, comparing the
two lanes' VERDICTS rather than one code, so a rule wired into only one lane reds there), the edition sweep

**[[PB188]]'s fixture moved.** Its header said "when PB208 lands, this fixture moves behind `--permissive`";
there is no permissive lane in the corpus manifest, so instead its literals became NUMERIC (`VALUE 12` / `VALUE
45`) and the program is now conforming. The width pin is untouched — PB188's own point was that the CCVS-leniency
arm and the numeric arm are ONE encode, so a numeric literal reaches the same `NumFormatImage` with the same
profile, and all four expected lines are byte-for-byte unchanged.
