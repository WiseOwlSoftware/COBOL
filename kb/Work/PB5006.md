# PB5006 - a Python instrument starved under gate load reads as a red

**Found.** In wave 20261930 group h the gate went RED twice on `TrackedTreeScopeDriftTests` (its `s_indexed` Lazy,
`PythonInstrument.Run(ObservationBudget.OneProcess, ... "drift_rules.py", "--scopes")`, line 43) with a timeout. The
script costs 6 s standalone and 2.7 s of CPU; the budget is `ObservationBudget.OneProcess`, one 120 s unit (a multiple of
13 to 32 for load by the design's own arithmetic, `tests/_shared/ObservationBudget.cs`). Three gates on one host starved
it past 120 s: a non-observation reported as a failure, which the timing rule says is a failure (the observer is the
harness's, so the cure is its budget or its scheduling, never a retry loop in the test).

**Owed.** Find why a 2.7 s-CPU process outruns 120 s (the instrument's priority under `-Priority BelowNormal`, the
Python start-up reading the whole tracked tree, or a lock shared across the three gates), and either carry the cost in
the budget's rule (PB3108 states children and parallelism; a script that walks the tree states its tree) or remove the
walk the test pays for. If PB3108's rule already covers wall-clock budgets for Python instruments, close this by
extending that note's site list instead.

**Sites:** `tests/_shared/PythonInstrument.cs` (`PythonInstrument.Run`), `tests/_shared/ObservationBudget.cs` (`ObservationBudget`), `tests/WiseOwl.Cobol.Tests.Unit/TrackedTreeScopeDriftTests.cs` (`TrackedTreeScopeDriftTests`)
