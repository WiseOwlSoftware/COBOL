# PB4578 — initialize-category-to-value-ignores-category: INITIALIZE g <category> TO VALUE behaves as ALL TO VALUE

Filed 2026-11-04 from the vetting of fuzz night 10's PB4559, whose vetter found this second defect on the same statement while probing it: the category-name in `INITIALIZE g <category> TO VALUE` is accepted and then ignored. The vetter's refuter reproduced it on 3.2.0 and 3.3-dev and found no tracker ticket. Upstream status `unreported`: the owner has not yet decided to report it. The probe programs are git-ignored and local (`E:/COBOL-coord/scratch/fuzz-vet/step2/f2-rejects/PB4559/var/r3-r6.cob` and `.../refute/mkini.py`): the minimal program below is the repro.

## Summary

Under `-std=cobol2014`, cobc 3.2.0 accepts `INITIALIZE R ALPHANUMERIC TO VALUE` but sets every item that has a VALUE clause, whatever its category, as if `ALL TO VALUE` had been written. Only the items whose category is the one named are receiving operands under the standard. The same happens for `NUMERIC TO VALUE`, `ALPHABETIC TO VALUE`, `NUMERIC-EDITED TO VALUE` and for `ALPHANUMERIC TO VALUE THEN REPLACING NUMERIC DATA BY 7` (which should give `[AByy07]`). Class: wrong output.

## Minimal test case

Free reference format.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. INI1.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 R.
   05 X1 PIC X(2) VALUE "AB".
   05 A1 PIC A(2) VALUE "CD".
   05 N1 PIC 9(2) VALUE 12.
PROCEDURE DIVISION.
    MOVE "zz" TO X1
    MOVE "yy" TO A1
    MOVE 99 TO N1
    INITIALIZE R ALPHANUMERIC TO VALUE
    DISPLAY "[" R "]"
    STOP RUN.
```

## Environment

`cobc (GnuCOBOL) 3.2.0` and a 3.3-dev tree (tarstamp 2026-10-29), WSL2 Ubuntu x86_64. Compiled with `cobc -x -free -std=cobol2014 -o p ini1.cob` and run as `./p`. Control: `INITIALIZE R ALL TO VALUE` prints `[ABCD12]` on every version, as the standard requires.

## Observed result

The program compiles with no diagnostic, exit code 0, and prints (3.2.0 and 3.3-dev alike):

```text
[ABCD12]
```

The same text is printed for `NUMERIC TO VALUE`, `ALPHABETIC TO VALUE` and `NUMERIC-EDITED TO VALUE`.

## Expected result (per ISO)

The program prints `[AByy99]`: only X1, whose category is alphanumeric, is a receiving operand and takes its VALUE; A1 (alphabetic) and N1 (numeric) are not named and keep `yy` and `99`.

- §14.9.20.4 5) c) 1. (checked): a possible receiving operand is a receiving operand if "The VALUE phrase is specified, the category of the elementary data item is one of the categories specified or implied in the VALUE phrase", and one of a), b) or c) holds (here b: a data-item format VALUE clause). The category of A1 and N1 is not specified in the phrase, so they are not receiving operands.
- §14.9.20.4 2) (checked): "If ALL is specified in the VALUE phrase it is as if all of the categories listed in category-name were specified", so a named category restricts the set and ALL does not.

Edition: 2014. The 2009 committee draft that became the 2014 edition has the same category-name rule (the vetter rendered its printed page 490 and 2023 PDF page 667).

## Our compiler

WiseOwl COBOL (`--std 2014 --source-format free`): prints `[AByy99]` for `ALPHANUMERIC TO VALUE`, `[zzyy12]` for `NUMERIC TO VALUE` and `[zzCD99]` for `ALPHABETIC TO VALUE`, exit code 0 (PB415 landed).

## Fix site

`cobc/codegen.c`: `deduce_initialize_type` (about line 4729) and `output_initialize_one` (about line 5520) test only that `p->val` is non-NULL and `f->values` is set, and never compare the category held in `p->val` with the field's category. The parser (`cobc/parser.y`, `_initialize_value`) stores the category, so the information is there when the check runs. The same two functions serve the REPLACING half (`initialize_replacing_item`), where PB4512 had noted a related symptom without filing it.
