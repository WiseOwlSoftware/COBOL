# PB3491 — GO TO … DEPENDING ON out of a PERFORM range loses the transfer

## Scenario (reduced from fuzz program fz01959; `--std 2014 --source-format free`)

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. FUZZ.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 WS-INDEX PIC 9 VALUE 0.
PROCEDURE DIVISION.
MAIN-PARA.
PERFORM PARAGRAPH-A
STOP RUN.
PARAGRAPH-A.
MOVE 1 TO WS-INDEX
GO TO PARAGRAPH-B DEPENDING ON WS-INDEX.
PARAGRAPH-B.
DISPLAY "JUMPED FROM A WITH INDEX 1"
DISPLAY "UNREACHABLE B"
STOP RUN.
```

**Spec-derived expected output** (§14.9.17.4 GR2, `cite.py --check 14.9.17.4` OK: "When a GO TO statement
represented by format 2 is executed, control is transferred to procedure-name-1, etc., depending on the value of
identifier-1 being 1, 2, … , n"; the PERFORM range of §14.9.28.4 GR1 "includes all statements that are executed as the
result of a transfer of control in the range of the PERFORM statement"): WS-INDEX is 1, so control goes to
PARAGRAPH-B, which prints two lines and stops:

```
JUMPED FROM A WITH INDEX 1
UNREACHABLE B
```

**Observed** (build of main 62cd0d954, 2026-10-21): no output at all, exit code 0. The transfer is dropped, the
PERFORM of PARAGRAPH-A ends, MAIN-PARA's STOP RUN runs.

GnuCOBOL 3.2 prints the two lines (the fuzz row's GnuCOBOL side, and the differential's whole point: the row said
the compilers disagree, the standard says which is right).

## The shape, measured (five variants, same build)

| Variant | Output |
|---|---|
| as above (GO TO B DEPENDING, target outside the performed paragraph) | **nothing, exit 0** |
| `GO TO PARAGRAPH-B PARAGRAPH-C DEPENDING ON WS-INDEX` (two targets) | nothing, exit 0 |
| `GO TO PARAGRAPH-B.` (format 1, same place) | correct |
| `PERFORM PARAGRAPH-A THRU PARAGRAPH-C` (target INSIDE the range) | correct |
| no PERFORM (MAIN-PARA falls into PARAGRAPH-A) | correct |

So the loss needs all three of: the format-2 GO TO, an active PERFORM whose range the statement is in, and a
selected target outside that range. Harm: a WRONG ANSWER with no diagnostic — the classic "dispatch paragraph"
(`GO TO P1 P2 P3 DEPENDING ON code`) inside a performed paragraph skips the selected branch and the program goes
on as if nothing was selected.

## Mechanism (read, not yet fixed)

`src/Cobol.Net.Compiler/CodeGen/Verbs/ControlFlowEmitter.cs` `EmitGoToDepending`: sets `__pc` in the selector
switch and leaves with `dispatch.TransferJump()`. The format-1 GO TO (`StatementEmitter.Visit(BoundGoTo)`) and the
ALTERed GO TO (`AlterSwitchEmitter`) leave with `EmitterState.ExplicitTransferOut`, which first clears `__atExit`
— the flag the PERFORM return mechanism reads to tell "control left the exit paragraph by completing it" from "an
explicit transfer out of the range" (its doc comment cites §14.9.28.4 GR5). The DEPENDING form is an explicit
transfer too and must go through the same one place (one mechanism per job, kb/Work PB405's lesson for this very
statement). Two arms of one dispatch, one of them wrong: **sweep every `TransferJump()` / `TransferOut(` caller that
renders a GO TO-class transfer** (RESUME AT already uses `ExplicitTransferOut` through `ResumeTransfer`; EXIT
PARAGRAPH / EXIT SECTION / NEXT SENTENCE are completions and correctly do not).

## Fix shape (for the implementer)

- One rendering for every explicit transfer out of a paragraph: `EmitGoToDepending` renders the in-range jump
  through `ExplicitTransferOut`-equivalent clearing (the selector switch sets `__pc`, so the JUMP half must clear
  `__atExit` before `goto` — add the explicit-jump half beside `TransferJump` rather than open-coding the flag).
- Goldens (spec-derived, never copied from GnuCOBOL): the five variants above in one conformance case per edition
  the construct exists in (85/2002/2014/2023), plus the ALTERed and format-1 twins in the same file so the three
  arms stay aligned; and a case where the DEPENDING GO TO is the LAST statement of the performed paragraph with an
  in-range selector (the `__atExit` corner the doc comment describes).
- Drift test: every emitter site that renders a transfer of control out of a paragraph goes through the one
  explicit-transfer rendering (a reflection or source scan over `TransferJump(` callers, as PB405 pinned its idiom).

## Why the fuzz saw it

The differential (PB3463/PB3488) classified fz01959 `OUTPUT_DIFFERS:14.9.17`: WiseOwl's output was empty, GnuCOBOL's
had the two lines. Of 1,141 OUTPUT_DIFFERS rows in the run this is the one confirmed WiseOwl wrong answer in the
first triage pass (evidence record `docs/rearchitecture/evidence/fleet-optimization/2026-10-21-differential-fuzz-overnight.md`).
