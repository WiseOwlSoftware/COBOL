## A. USE AFTER EXCEPTION OBJECT naming a parameterized interface listed in REPOSITORY without EXPANDS: a defect in the 2002 text; WiseOwl refuses the reference, as a recorded determination

**What 2002 says.** No syntax rule forbids it: §2002:14.8.45.2 SR17 asks only that the operand be "the name of an interface specified in the REPOSITORY paragraph", §2002:12.2.7.3 GR7 says interface-name-2 "may be used throughout the scope of the containing environment division", and §2002:12.2.7.2 SR7 in fact REQUIRES the parameterized interface to be listed in the same REPOSITORY paragraph before it can be expanded. But no rule gives the unexpanded name a meaning as an interface: §2002:9.3.13 calls it "a generic or skeleton interface" and says an interface "that functions as a non-parameterized interface" is created "When it is expanded by substituting specific class-names or interface-names as actual parameters"; the only creation rule is §2002:12.2.7.3 GR8 (EXPANDS); and §2002:9.3.7.1.3 defines the use of a parameterized interface by treating it "as if the actual parameter classes or interfaces were substituted for the parameters", of which an unexpanded reference has none. §2002:14.8.45.3 GR13b selects the declarative when the raised object "is described with an IMPLEMENTS clause that references interface-name-1", which again needs a class that implements the skeleton, a use 2002 does not define.

**Decision.** The 2002 text grants the use in general words (GR7) and defines it nowhere: that is a defect in the standard, and it is recorded as one (`docs/conformance/`, a `D-` determination), not coded around. WiseOwl REFUSES a reference to an unexpanded parameterized interface outside the REPOSITORY paragraph at every edition. At 2023 the standard requires it (§2023:12.3.8.4 GR7: "interface-name-1 may be specified only in the REPOSITORY paragraph"); at 2002 it is this implementor's determination for a construct the edition leaves without meaning, taken because the alternative is to invent semantics (what an object reference typed by a skeleton conforms to, what class implements it) that no edition states. GnuCOBOL and IBM Enterprise COBOL have no parameterized interfaces, so the precedence of CLAUDE.md rule 1 offers nothing below the ISO text. The 2023 sentence is used as a pointer to what the committee later wrote, never as the 2002 rule.

**The reading not taken.** §2002:9.3.13's third paragraph ("When a parameterized interface is specified in the REPOSITORY paragraph, a new interface (an instance of a parameterized interface) is created based on the specification of the parameterized interface") can be read to create an instance from a specifier without EXPANDS. It is not taken because the next paragraph identifies an instance by "the same actual parameters", so an instance without actual parameters is not a thing the clause describes. The owner may overturn this determination; overturning it means implementing the raw reference at 2002 (and 2014 if its text matches).

**Consequences.**
- Row `2002-SR-14.8.45.2-17`: SR17 itself is enforced. Verdict CONFORMS on witnesses at `--std 2002` that (1) accept USE AFTER EXCEPTION OBJECT naming a non-parameterized interface listed in REPOSITORY and (2) refuse a name the REPOSITORY does not list. The skeleton case is the determination's, with its own refusal witness at 2002.
- The refusal's stated ground is still wrong at 2002: COBOL0859's text cites §2023 rules at `--std 2002`. That is an instance of PB4950 (a diagnostic citing another edition's clause) and stays a defect there; the 2002 ground is the determination.

## B. A numeric or boolean item of USAGE NATIONAL is class numeric or class boolean in 2002, never class or category national

**What 2002 says.** §2002:8.5.2: "Each data item and each literal has a class and a category" (one of each). §2002:8.5.2.9 item 1 puts in category numeric "An elementary data item described as numeric by its PICTURE character-string and not described with a BLANK WHEN ZERO clause", and §2002:8.5.2.4 item 1 does the same for boolean; neither is conditioned on usage. Table 3 of §2002:8.5.2 gives class Numeric to category Numeric with no usage condition, and where usage DOES move the class it says so: "Numeric-edited (if usage is national)". The USAGE clause confirms that usage national does not decide the category: §2002:13.16.58.2 SR11 requires such an item to have "a picture character-string that describes a boolean, national, national-edited, numeric, or numeric-edited data item", and §2002:13.16.58.3 GR2 says the clause is about representation: "It does not affect the use of the data item". And a rule of the edition names the combination outright: §2002:13.16.22.3 GR4 lists "class national" and, separately, "class numeric with usage national".

**The conflict.** §2002:8.5.2.7 item 3 lists as category national "An elementary data item explicitly or implicitly described as usage national". Read literally it gives a PIC 9 USAGE NATIONAL item two categories, against the opening sentence of 8.5.2, and makes GR4's separate list entries one. It also contradicts Table 3 itself, which keeps a numeric-edited item of usage national in category numeric-edited.

**Decision.** In 2002 a PIC 9 item of USAGE NATIONAL is category numeric and class numeric; a PIC 1 item of USAGE NATIONAL is category boolean and class boolean. §2002:8.5.2.7 item 3 is a defect in the 2002 text (recorded in `docs/conformance/`) and is read as covering only an item whose PICTURE leaves it national, where it adds nothing to item 1. Where a rule asks for class or category national, such an item does not qualify; where a rule speaks of usage national as a representation ("class numeric with usage national"), it does.

**Consequences.** The compiler's refusals of a numeric or boolean USAGE NATIONAL item where class national is required (COBOL1546, COBOL1627) follow the decided reading. Each row this reading decides is re-judged under it at `--std 2002`, on its own rule's words: `2002-AR-15.21.2-1`, `2002-RV-15.40.3-1`, the numeric-national leg of `2002-AR-15.41.2-1`, `2002-GR-12.3.4.6.3-3`, `2002-GR-12.3.4.6.3-5`, `2002-SR-14.8.39.2-1`, `2002-SR-14.8.37.2-6`, `2002-GR-14.8.37.3-13`, `2002-AR-15.51.2-2`. The reading is decided; a row closes only on its own witness.

## C. SET of an index outside its table's range: the normative rules govern, and the compiler DIVERGES from them at 2002 when checking is enabled (new defect PB5674)

**What 2002 says.** §2002:14.8.35.3 GR2a.1: a subscript is determined from arithmetic-expression-1 as §2002:8.4.1.2 describes, and "otherwise the execution of the SET statement is unsuccessful and the content of the receiving operand is unchanged"; §2002:8.4.1.2.3 GR2 makes a value "greater than the highest permissible occurrence number" (or below one) the EC-BOUND-SUBSCRIPT exception condition. §2002:14.8.35.3 GR3b, for UP BY and DOWN BY: "otherwise the EC-BOUND-SUBSCRIPT exception condition is set to exist, the execution of the SET statement is unsuccessful, and the content of the receiving operand is unchanged"; GR3a says the same of an arithmetic-expression-2 that is not an integer. EC-BOUND-SUBSCRIPT is fatal (§2002:14.5.12.1.5, Table 14: "Subscript out of bounds").

**How the informative annex fits.** §2002:F.2 item 121 ("The result of setting an index can be outside of the range of the associated table") is in an informative annex and states no requirement. It is also true of a 2002 program by the normative text alone: §2002:14.5.12.1 says "By default, checking is not enabled for any exception condition" and that a condition a general rule says exists "is raised only if checking for that exception condition is enabled", and for a fatal condition whose checking is not enabled §2002:14.5.12.1.2 says "the implementor defines whether or not execution will continue, how it will continue, and how any receiving operands are affected". So there is no conflict to settle: with checking NOT enabled the result is implementor-defined (and an index outside the range is a permitted result); with checking ENABLED GR2a.1 and GR3b apply as written.

**Decision.**
1. Checking not enabled (the default): implementor-defined. WiseOwl continues and stores the value (the reported S2=11, U2=15, U3=05). This is recorded as a determination in `docs/conformance/` (the 2002 item is Annex A's "Fatal exception condition ... checking for that condition is not enabled"), with the survey CLAUDE.md rule 1 asks for.
2. Checking enabled (`>>TURN EC-BOUND-SUBSCRIPT CHECKING ON`): the SET shall be unsuccessful, the index unchanged and EC-BOUND-SUBSCRIPT raised. **The compiler does not do this: defect PB5674.** Measured in this session on the build of main 24372b7b17 (`E:/COBOL-wt/coderead85-tree-d`): `E:/COBOL-coord/scratch/my-20261115/pb5625/set_index_checked.cob` at `--std 2002` prints `S1=03 S2=11 S3=31 S4=26 S5=10` and runs no declarative; the rules require `S1=03`, the declarative, `S2=03`, the declarative, `S3=03`, the declarative, `S4=03`, `S5=10`. The control `set_index_control.cob` (same directive and declarative, an out-of-range subscript REFERENCE) prints `EC EC-BOUND-SUBSCRIPT`, so the directive works and the silence is the SET statement's.

**Consequences.** Rows `2002-GR-14.8.35.3-2` and `2002-GR-14.8.35.3-3` are DIVERGES naming PB5674 until it lands, and move from this note to PB5674. In the 2002 text EC-BOUND-SUBSCRIPT is named only in 8.4.1.2.3 and in SET's GR3a and GR3b, so the sibling arms are SET format 1 (through 8.4.1.2) and both rules of format 2; PERFORM VARYING has no such rule in 2002 (F.2 item 93 agrees). Whether 2014 and 2023 word SET differently is for PB5674's fix to read in each edition's own text.

## D. LOWER-CASE and UPPER-CASE with no locale in effect: 2002 does not state the correspondence; Annex D is not the functions' rule; the Unicode simple case mappings are WiseOwl's documented choice

**What 2002 says.** §2002:15.45.3 RV2 gives the source of the correspondence only when a locale is in effect ("the correspondence of uppercase to lowercase letters is determined from locale category LC_CTYPE"); RV4 of each function leaves a letter unchanged when it has no corresponding letter (§2002:15.45.3 RV4, §2002:15.78.3 RV4) without saying what the correspondence is when no locale is in effect. Annex D is normative, but for something else: it "shows the mapping of uppercase letters to lowercase letters in the COBOL character repertoire" (§2002:D), and its one use in the body is the equivalence of letters in source text (§2002:8.1.2.1 GR3: "folding from uppercase to lowercase in accordance with the case mapping described in Annex D"). No rule of 15.45 or 15.78 refers to it, and the functions act on data in the computer's coded character set, not on COBOL words.

**Decision.** With no locale in effect the correspondence is not specified by 2002: implementor latitude, to be documented. WiseOwl uses the Unicode simple case mappings (`ToUpperInvariant`, `ToLowerInvariant`), which is what Annex D's own NOTE 1 tells implementors to use beyond the annex's list (§2002:D.2.1: "Implementors should use the case mappings in UnicodeData.txt if additional characters are added to the set of extended letters as implementor extensions"). The 65 uppercase and 104 lowercase letters that have a Unicode pair and no Annex D pair are therefore changed by design, not by defect. `docs/conformance/3/D-CASE-MAPPING.md` is extended to say this for 2002, with the survey rule 1 asks for (GnuCOBOL first, then IBM or Micro Focus), each line measured or marked as unmeasured.

**A check the recording must run first** (it can fail): on the probe output the answer pass kept (`E:/COBOL-coord/scratch/op-20261114/read-2002/out-answer/probes-a-15/`), every pair Annex D lists maps as the annex lists it. If one does not, that pair is a defect and gets its own note; the decision above covers only letters the annex does not pair.

**Consequences.** Rows `2002-RV-15.45.3-4` and `2002-RV-15.78.3-4`: CONFORMS on a 2002 witness that shows a letter with no pair in the documented correspondence returned unchanged, with the determination cited.
