# PB4838 - a FILE record (FD) with a message-tag, pointer or object leaf has no managed-slot half: every READ/WRITE and SORT USING/GIVING and MERGE over a slot SD record stay COBOL1756 Tier-C; needs an owner decision

**What the report says (the reviewer's words).** New defects 1. A FILE record (FD) with a message-tag/pointer/object leaf has no managed-slot half: every READ/WRITE of it and SORT USING/GIVING and MERGE over a slot SD record stay COBOL1756 Tier-C (GateFileRecordByteSurfacePass doc; SortBinder.SlotRecordFileTransferReason). Share root: the file record codec (RecordStructEmitter transfer image has no FromImage). Needs an owner decision on what a file holds for a tag/pointer (placeholder bytes) before USING/GIVING can be completed. OWNER DECISION NEEDED, as the report words it; this note decides nothing.

**R1.** kb/Work PB4772 (landed) is the SD arm; no open note covers the FD slot record by grep of SlotRecordFileTransferReason.

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Passes/GateFileRecordByteSurfacePass.cs` (`GateFileRecordByteSurfacePass`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/SortBinder.cs` (`SortBinder.SlotRecordFileTransferReason`), `src/WiseOwl.Cobol.Compiler/CodeGen/DataDivision/RecordStructEmitter.cs` (`RecordStructEmitter`).

Filed from a review lead of a merged fix-lane branch (wave 20261879 to 20261882) by the enqueue clerk; the lead's claim is the reviewer's, not adjudicated here. Harm flag: the lead says these statements are refused as a Tier-C deferral (COBOL1756); whether the source is legal is the implementer's call, so the flag follows the rule that a deferral of legal source is debt (CLAUDE.md rule 3).

**Wave 20261885 group E returned BLOCKED, 2026-11-06 (report `E:/COBOL-coord/scratch/reports/w20261885e-PB4838-report.md`; no commits, COBOL6346-COBOL6348 returned unused).** It reproduces. A `01 FREC TYPE T-REC` strong typedef (9(2) plus USAGE POINTER) in an FD compiles clean, and OPEN OUTPUT / WRITE aborts the run with NotImplementedCobolFeatureException. SORT USING over an SD record of the same type draws the COBOL1756 warning and aborts on reaching the statement.

The source is legal for a tag or pointer leaf: §13.18.60.3 SR14 admits both under a strong type, and SR15 forbids only USAGE OBJECT REFERENCE in the file section. So this note's title overstates the FD arm for an object leaf. §13.18.60.4 GR9 leaves a message tag's value to the implementor. (All three checked with `cite.py --check` by the wave unit.) The `rejects_legal_source` flag is the clerk's inference, and the operator was asked to check it: neither form is refused at compile time, the harm is an abort at run time. The flag is left as filed, because the hold takes the note out of Fix next either way; whoever answers the question should correct it.

**Held for the owner (status `owner`).** The report says the precedence rule gives no answer: ISO leaves it open, and GnuCOBOL and IBM persist raw address bytes, which a managed reference cannot do (the report's claim, not re-verified here). D-SLOT settles only the WRITE placeholder. The READ half (FromImage, RETURN, SORT GIVING, MERGE, REWRITE, indexed and relative files) is undetermined. The question, as the implementer put it: may a file carry the D-SLOT placeholder (8 spaces per leaf) on WRITE, and after READ, RETURN or SORT GIVING should the slot leaf be NULL (its proposal, since the placeholder has no inverse) or left unchanged?

**The owner's decision (2026-11-06, AskUserQuestion, "Round-trip").** A file carries the leaf's 8-position address token, and READ, RETURN and SORT GIVING decode it back to the same reference within the run unit.

- **POINTER family:** WRITE stores the `PointerImage` token that DOC-A.1-216 already defines. READ decodes it. A.1 item 216's clause "one-way (never decoded back into a reference — no conforming pairing needs it)" changes in the fix's change set, and the allocator gains the inverse.
- **Message tag:** the same mechanism. No GnuCOBOL or IBM precedent exists for it, and §13.18.60.4 GR9 leaves its representation to the implementor. A.1 item 212's "inside a group those 8 positions read as spaces" changes with it.
- **A token from another run unit:** it keeps its image, and dereferencing it raises an exception. It never reads as NULL. The fix's design names the exception from the spec.
- **The precedence evidence:** the operator ran `cobc -std=cobol2002` and `-std=cobol2014` (GnuCOBOL 3.2.0) on a WRITE then READ of a record holding a USAGE POINTER leaf, and the value read back equalled the value written. This corrects the report's premise that no precedent could apply: the raw bytes cannot be copied, but the token has the same shape and the round trip is reachable. IBM's behaviour was not checked and is not needed, because GnuCOBOL answers first (CLAUDE.md rule 1). The `-std=default` run agreed; only the two pinned runs count.
- **An object leaf:** outside the question asked. §13.18.60.3 SR15 forbids the USAGE OBJECT REFERENCE clause in the file section, while a STRONG type declared elsewhere can bring such a leaf in. The fix decides legality from the spec first; if that leaves a choice the owner has not made, it comes back as a question.

The `rejects_legal_source` flag above is still the clerk's inference; the fix corrects it, since the harm is a run-time abort rather than a compile-time refusal.

The owner test requirement for the fix: WRITE, READ and REWRITE of the FD record at every FILE STATUS path, SORT USING/GIVING and MERGE with a slot SD record, and a short and a long record, with expected bytes from the determination. Add a same-run round trip that compares equal, and a token from another run unit that raises on dereference.
