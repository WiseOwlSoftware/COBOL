# PB4981 - a rounding mode changes the exponent's kind

**Sites:** `src/WiseOwl.Cobol.Compiler/CodeGen/Emit/NumericRenderer.cs:1538` (inside `NumericRenderer.Power`).

**Report (R2-1, low per the reviewer; a wrong answer).** Pre-existing, not introduced by PB4923's diff (same output from the E:/COBOL checkout build). Under
`ROUNDED MODE TRUNCATION` or `AWAY-FROM-ZERO`, a non-integer literal exponent over an intrinsic base is rendered as an INTEGER exponent (0.7 turns into `0L`, or 1 into the base itself),
so `Power` takes the exact integer arm. `ROUNDED` (default mode) and a direct item base are correct. The cause is not yet traced (read line 1538 first). Probe: a COMPUTE with `ROUNDED MODE TRUNCATION` of `FUNCTION <intrinsic> ** 0.7` against the same without the mode and against an item base.

## Retired: the probe overran column 72 (wave 20261925, group B)

Not a defect. The reviewer's probe `E:/COBOL-coord/scratch/review-w20261921-f/p5.cob` writes `COMPUTE RR ROUNDED MODE TRUNCATION = FUNCTION MAX (M M2) ** 0.7` (and the AWAY-FROM-ZERO twin) on one fixed-format line of 74 characters. Columns 73 to 80 are the identification area (ISO reference format: text there is not program text), so the compiler read the exponent as `0` and `** 1.5` as `** 1`: a literal exponent of 0 or 1, which IS the exact integer arm. The item-base line (`M ** 0.7`) was short enough, which is why "a direct item base is correct". Re-probed on the build with the statements split inside column 72 (`E:/COBOL-coord/scratch/w20261925b/a/p84.cob`) and in free format (`p85.cob`; the intrinsic bases ABS, SQRT, MAX, INTEGER and MAX over a float item, the modes TRUNCATION, AWAY-FROM-ZERO, TOWARD-GREATER and NEAREST-EVEN): every result is the binary64 power rounded in the receiver's mode (2 ** 0.7 = 1.6245047927 is 1.62450479 truncated and 1.62450480 away from zero; SQRT(2) ** 0.7 = 1.2745606273 is 1.27456062 and 1.27456063; 2 ** 1.5 = 2.8284271247 is 2.82842712 and 2.82842713). Instrumenting the renderer showed the literal reaching `Power` already bound as `0` (`BoundNumLiteral("0")`), not the exponent being re-kinded. Nothing to fix; the lesson for a probe is to keep fixed-format lines to column 72.
