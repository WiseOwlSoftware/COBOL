# PB1246 — OPEN

## Measured

**level-number** — Record-description level-1 start never screened: DataBinder.BindEntries roots whatever entry arrives on an empty nesting stack, so a WORKING-STORAGE / LOCAL-STORAGE / LINKAGE / FD / SD record whose first entry is level 2-49 compiles silently

- **Repro:** WORKING-STORAGE SECTION.
       05 A PIC X VALUE "A".
       05 B PIC X VALUE "B".
       PROCEDURE DIVISION. DISPLAY A B STOP RUN.   (also FD F. 05 R PIC X(4).) -> pinned cobol.exe compiles clean at --std 85/2002/2014/2023 and prints AB
- **Expected (spec):** A compile-time error: "A record description entry consists of a set of data description entries, the first of which shall have level-number 1" (§13.11.1) and "The level-number 1 identifies the first entry in each record description" (§13.18.33.4 GR1); §4.2.2 requires the violation be diagnosed. The type-declaration arm (COBOLNET1529) and report-group arm (ReportGroupBefore01) already refuse the same shape.
- **Observed:** BindEntries: `while (stack.Count>0 && stack.Peek().Level >= nestLevel) stack.Pop(); if (stack.Count == 0) { ... _roots.Add(item) }` - an empty stack roots the item at its own level (5) with no check that it is 1 (or 77). LevelNumberPass screens only the section's permitted SET, not the position. Sibling observed while probing (not this rule's row): `01 G. 05 A. 03 B.` binds B under G beside A at unequal levels, which §8.5.1.3.2 ('immediately subordinate ... numerically equal level-numbers') forbids - same stack walk, same missing screen. Also the report-group arm's refusal carries the COBOLNET0899 NotImplemented band code rather than a family code.
- **Code site:** src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindEntries (stack.Count == 0 root arm, ~line 833); natural home src/Cobol.Net.Compiler/Validation/LevelNumberPass.cs
- **Clause (adjudicator):** §13.18.33.4 GR1 / §13.11.1

**level-number** — Level-number spelling not screened for digit count: the grammar takes any INTEGERLIT and LevelNumberPass tests only the parsed value, so a three-or-more-digit spelling such as 001 is accepted as level 1

- **Repro:** WORKING-STORAGE SECTION.
       001 A PIC X VALUE "A".
       PROCEDURE DIVISION. DISPLAY A STOP RUN.  -> compiles clean at 85/2002/2014/2023, prints A
- **Expected (spec):** §8.3.2.2.13: "A level-number, expressed as a one-digit or two-digit number"; §13.18.33.3 SR3 permits only the 01-09 leading-zero spelling. `001` is not a level-number, so the entry lacks the level-number §13.18.33.3 SR1 requires - a compile-time diagnostic is owed.
- **Observed:** levelNumber : INTEGERLIT; INTEGERLIT : INT_BODY = [0-9]+. VisitLevelNumber does int.TryParse(text) and Arm.Permits(level) - the value 1 is permitted, the text length is never examined. The existing twelve-digit negative is rejected only because its VALUE is out of range.
- **Code site:** src/Cobol.Net.Compiler/Validation/LevelNumberPass.cs#LevelNumberPass.VisitLevelNumber
- **Clause (adjudicator):** §13.18.33.2 / §8.3.2.2.13 / §13.18.33.3 SR1, SR3

### Finding — `levels` (under-rejects; rows `GR-8.5.1.3.2-3`)

**Mechanism.** The BindEntries level-nesting walk has no failure branch for an entry that pops the level stack to EMPTY with a level-number other than 1 (or 77): such an entry is silently made a record ROOT. So an entry written as a subdivision of a level-77 item, or a working-storage/local-storage/linkage 'record' whose first entry is 02-49, compiles clean instead of being diagnosed.

**Repro.** WORKING-STORAGE SECTION.
01  R.
    05  A PIC X VALUE "A".
77  X PIC X VALUE "X".
    05  B PIC X VALUE "B".
PROCEDURE DIVISION.
    DISPLAY FUNCTION LENGTH(R)
    DISPLAY B
    STOP RUN.
(also: `77 X PIC X. 05 Y PIC X.`, and a WORKING-STORAGE whose first entry is `05 Y PIC X.`) -- pinned cobol.exe --std 85 and --std 2023 --run: compiles clean, prints 1 / B.

**Expected from the spec.** A compile-time diagnostic (§4.2.2 syntax-rule violation). §8.5.1.3.2: level-77 entries 'are not subdivisions of other items, and are not themselves subdivided'; §13.13: 77 items are used 'provided they do not need to be further subdivided'; and an entry that is not a subdivision must begin a record description, whose first entry 'shall have level-number 1' (§13.11.1; §8.5.1.3.2 'level-numbers for records start at 1'; §13.18.33.4 GR1). The §13.5.2 working-storage general format admits only 77-level, constant, record-description and type-declaration entries, so `05 B` here is none of them.

**Observed / reasoning.** DataBinder.BindEntries computes nestLevel (77 -> 1), pops `while (stack.Peek().Level >= nestLevel)`, and `if (stack.Count == 0)` registers the item as a root unconditionally. After a 77 (pushed with Level 77) any 02-49 entry pops it and becomes a root; the same arm accepts a section whose first entry is 05. LevelNumberPass screens only the per-section level SET and the (level, body format) pair, never the position of a level within the sequence. No diagnostic exists for §13.11.1's first-entry rule (grep of src for 13.11.1 finds only UsageDeclaration comments). The only shape rejected is a PICTURE-less 77 followed by a subordinate, incidentally, via COBOLNET0881 (§13.16.3 SR8). Edition-independent (85 and 2023 measured).

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindEntries (nesting pop + `if (stack.Count == 0)` root arm, ~lines 829-846); the natural home is src/Cobol.Net.Compiler/Validation/LevelNumberPass.cs (a sequence check over the section's entries: a root-opening entry must be level 1 or 77, and nothing may follow a 77 at 02-49)

#### `GR-8.5.1.3.2-1` — PARTIAL (adjudicator + refuter record, verbatim)

Rule (cite.py --check 8.5.1.3.2 OK: 'Three types of entries exist for which there is no true concept of level' / '1) Entries that specify elementary items or groups introduced by a RENAMES clause.'). The binder's BindEntries walk handles lvl==66 BEFORE the nesting stack: BindRenames records the alias on the owning record and `continue`s, so a 66 entry neither opens nor closes a group and is never numerically compared to 1-49 levels (66 > 05 would otherwise nest it). The 66 is also the 'entry describing the item' for a following 88 (SR24 b exclusion) without entering the stack. Probe p1 (pinned cobol.exe, --std 2023): `01 G. 05 GA PIC X VALUE "Y". 88 GA-YES ... 05 GB PIC X VALUE "Z". 66 GR RENAMES GA THRU GB. 01 H. ...` -> FUNCTION LENGTH(G)=2, DISPLAY GR='YZ', following record H unaffected (LENGTH 2) - spec-expected. The level-66 <-> renames-format pairing is LevelNumberPass (§13.18.33.4 GR2b). Covering test pb485_level_number_legal_forms (COBOL-85) writes `66 R-ALL RENAMES H10 THRU H2.` after record H followed by 77/88/01 entries and asserts R-ALL='XYZPQ' and the later items intact - expected values derived from the spec. || REFUTED: PARTIAL — The levelless half holds. BindEntries takes lvl==66 before the nesting stack, so a 66 neither opens nor closes a group. But the adjudicator's evidence also leaned on the renames-format pairing (§13.18.33.4 GR2b: a 66 'may be used only as described by the renames format'), and the constraints that make a 66 legitimately levelless are not enforced. (1) SR2 placement: a 66 written in the middle of a record, followed by a further 05, compiles silently, and the 05 is re-attached to the still-open record (LENGTH(R)=2). (2) SR5: a 66 after a 77 attaches to the 77 as its 'owning record', because _lastRoot counts a 77 as a record. `66 RX RENAMES X` over a 77 compiles and runs. BindRenames' _lastRoot model treats a 77 as a record, and a 77 is exactly the entry that has no record. Those defects belong mainly to the sibling rules §13.18.45.3 SR2/SR5, but they show that the 66's 'no concept of level' is modelled as 'transparent to the stack', not as 'a trailing alias of the preceding 01 record'. The golden pins only the legal trailing-66 shape.
