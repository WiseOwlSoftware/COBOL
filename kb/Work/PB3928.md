# PB3928 — universal-object-reference-not-supported--feature: object references: SET, IF ... = NULL and RAISE identifier refused for USAGE OBJECT REFERENCE items

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S9) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\universal-object-reference-not-supported--feature.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\universal-object-reference-not-supported--feature\`.

## Summary

GnuCOBOL 3.2 accepts the declaration `USAGE OBJECT REFERENCE` with the warning `OBJECTS is not implemented
[-Wpending]`, then refuses every statement that uses such an item as an object reference:
`SET R2 TO R1` gives `invalid source for MOVE`, `IF R2 = NULL` gives `invalid expression: unfinished expression`, and
`RAISE R2` gives `'R2' is not an object-reference`. Universal object references, SET format 5, relation conditions on
class object and RAISE identifier-1 are in ISO/IEC 1989:2002 and 2014 and are not optional elements, so this is a
missing feature of the edition `-std=cobol2014` claims. Class: feature missing. Two neighbouring behaviours have their
own records: the internal compiler error on comparing two object references
(`universal-object-reference-not-supported--compare-ice`) and the refusal of the declaration written without the word
USAGE (`universal-object-reference-not-supported--usage-word-required`).

## Minimal test case

Free reference format (`-fformat=free`), 12 lines, written for this record. The fuzz witnesses of nights 2 to 5
(fz01313, fz02199, fz02219, fz03171, fz03198) reduce to one of its three statements.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. OBJF.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 R1 USAGE OBJECT REFERENCE.
01 R2 USAGE OBJECT REFERENCE.
PROCEDURE DIVISION.
SET R2 TO R1
IF R2 = NULL DISPLAY "NULL" END-IF
RAISE R2
DISPLAY "AFTER"
STOP RUN.
```

File: `E:\COBOL-coord\scratch\op\pb3838\records\universal-object-reference-not-supported--feature.cob`.

The program is legal: R1 and R2 are universal object references at level 1 in working-storage (§13.18.60.3 14),
§13.18.60.4 22) b)); `SET R2 TO R1` is SET format 5 (§14.9.39.3 8), 9)); `R2 = NULL` compares two operands of class
object (§8.8.4.2.15; NULL is of class object, §8.4.3.7.3 2)); `RAISE R2` names an object reference that is not the
predefined NULL or SUPER (§14.9.29.3 2)).

## Expected result (per ISO)

The program compiles and prints `NULL` then `AFTER`. ISO/IEC 1989:2023, each citation checked with
`scripts/spec/cite.py --check`:

- §13.18.60.2: the USAGE clause general format has `OBJECT REFERENCE` with optional interface, ACTIVE-CLASS or class
  phrases (verified on the printed page).
- §13.18.60.4 22): "A data item described with a USAGE OBJECT REFERENCE clause is called an object reference. An object
  reference is a data item of class object and category object-reference." 22) b): "If none of the optional phrases is
  specified, this data item is called a universal object reference."
- §13.18.63.4 4): "data items of class message-tag, class object, and class pointer are initialized to null". R1 is
  null at the start.
- §14.9.39.3 8): "Identifier-3 shall be any item of class object that is permitted as a receiving item." 9):
  "Identifier-4 shall be an object reference; the predefined object reference SUPER shall not be specified." So
  `SET R2 TO R1` sets R2 to null.
- §8.8.4.2.15: "An operand of class object may be compared with another operand of class object." and "The relation
  'identifier-3 = identifier-4' has a true value if the object referenced by identifier-3 is the same object that is
  referenced by identifier-4". §8.4.3.7.3 2): "NULL is implicitly described as class object and category object
  reference". `R2 = NULL` is true; the program prints `NULL`.
- §14.9.29.3 2): "Identifier-1 shall be an object reference; the predefined object references NULL and SUPER shall not
  be specified." §14.9.29.4 2): "If identifier-1 is specified, EXCEPTION-OBJECT is set to reference the object
  referenced by identifier-1. If there is no applicable declarative, processing continues with the statement following
  the RAISE statement." The program has no declaratives, so it prints `AFTER`.

Edition: object references, SET format 5, comparisons of class object and RAISE identifier are object-oriented
features introduced in ISO/IEC 1989:2002. The 2001-12-04 text headed "ISO/IEC 1989:2002(E)" has `OBJECT REFERENCE` in
its USAGE format and the RAISE statement (its clause 14.8.28 of that text); the 2009 committee draft CD 1.2 that led to 2014 has the RAISE
statement (its clause 14.9.28 of that text) with the same syntax rule 2) and general rule 2) as 2023. Neither the 2009 draft's
optional-element list (its A.4.9: multiple inheritance only) nor 2023's (§A.4.10: multiple inheritance and parametric
polymorphism) names them.

Edition as recorded by the adjudicator: 2002 (carried into 2014). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

FEATURE-MISSING (edition 2002, carried into 2014): object references are declared but unimplemented in every statement
that uses them. cobc's own `-Wpending` warning announces it.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/parser.y`, rule `conflict_usage` (line 8269): accepts `OBJECT REFERENCE` and calls `CB_PENDING ("OBJECTS")`
  after setting `CB_USAGE_OBJECT`.
- `cobc/tree.c`, function `cb_tree_category`, the `CB_TAG_FIELD` default-level branch (lines 1459-1471): a field with
  `CB_USAGE_OBJECT` and no PICTURE gets `CB_CATEGORY_UNKNOWN`, never `CB_CATEGORY_OBJECT_REFERENCE`. That category
  reaches `cobc/typeck.c`, function `validate_move` (line 10749): its switch on the source category (line 11420) has no
  arm for it and its default arm reports "invalid source for MOVE" (line 11593), for the MOVE that `cb_emit_set_to`
  (line 13421) builds for the SET.
- `cobc/parser.y`, rule `figurative_constant`: NULL is its `TOK_NULL` alternative (line 19791, yielding `cb_null`, with
  a source comment questioning its validity in all uses). NULL handling itself works: `IF P = NULL` on a `USAGE
  POINTER` item compiles and prints `NULL` (the refuter's probe `refute/_s9extra/ptrnull.cob`). The condition `R2 =
  NULL` fails because `expr_chk_cond` (`cobc/typeck.c` line 5422) counts `cb_null` as a pointer and refuses a
  pointer/non-pointer mix, and an OBJECT REFERENCE field never gets `flag_is_pointer`; the relation is then left
  unreduced and `build_expr_finish` (line 5843) reports "invalid expression: unfinished expression" (line 5852).
  (Corrected by the refuter: the record had blamed the expression reducer's handling of NULL.)
- `cobc/parser.y`, rule `raise_body` (line 15733): the `identifier` alternative always reports "'%s' is not an
  object-reference", whatever the identifier's usage (the source comment says object orientation is absent).
- libcob has no object or exception-object run-time support to call.

## Draft issue

**Title:** object references: SET, IF ... = NULL and RAISE identifier refused for USAGE OBJECT REFERENCE items

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1), x86_64 Linux.

Steps: `cobc -std=cobol2014 -fformat=free -x objf.cob` with

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. OBJF.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 R1 USAGE OBJECT REFERENCE.
01 R2 USAGE OBJECT REFERENCE.
PROCEDURE DIVISION.
SET R2 TO R1
IF R2 = NULL DISPLAY "NULL" END-IF
RAISE R2
DISPLAY "AFTER"
STOP RUN.
```

Observed (exit 1, same without `-std`):

```
objf.cob:5: warning: OBJECTS is not implemented [-Wpending]
objf.cob:6: warning: OBJECTS is not implemented [-Wpending]
objf.cob:8: error: invalid source for MOVE
objf.cob:9: error: invalid expression: unfinished expression
objf.cob:11: error: 'R2' is not an object-reference
```

Expected: the program compiles and prints `NULL` and `AFTER`. Universal object references (USAGE OBJECT REFERENCE with
no class phrase), SET identifier-3 TO identifier-4 on object references, the comparison of two operands of class object
(NULL is of class object) and RAISE identifier-1 are COBOL 2002 and 2014 features, not optional elements (ISO/IEC
1989:2023 13.18.60.4 GR 22, 14.9.39.3 SR 8-9, 8.8.4.2.15, 8.4.3.7.3 SR 2, 14.9.29.3 SR 2, 14.9.29.4 GR 2: "If there is
no applicable declarative, processing continues with the statement following the RAISE statement"). Object references
are initialized to null (13.18.63.4 GR 4), so `R2 = NULL` is true.

Notes for a fix: a USAGE OBJECT REFERENCE field is given category CB_CATEGORY_UNKNOWN by `cb_tree_category` (tree.c),
so `validate_move` (typeck.c) refuses it as a MOVE source; `raise_body` (parser.y) refuses every identifier; and
`expr_chk_cond` (typeck.c) treats NULL as a pointer and refuses to compare it with a field that is not a pointer (an
OBJECT REFERENCE field never gets `flag_is_pointer`), whereas `IF P = NULL` on a USAGE POINTER item compiles and works.
