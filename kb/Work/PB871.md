# PB871 — LANDED — the dynamic-length receiving store exists in exactly one emitter

Source: the `PB463` implementer report, "New defects" item A. The report named five verbs; the re-measurement
below CONFIRMS three of them, REFUTES two, and adds a fourth arm the report did not derive. Only the measured
arms are claimed here.

## Repro — re-run on this tree

`scratchpad/reg5/p2_dyn.cob` (PROGRAM-ID `REG5P2`), `--std 2023 --run`, with
`01 WS-x PIC X DYNAMIC LENGTH LIMIT IS 8.` receivers and `01 WS-S PIC X(10) VALUE "ABCDEFGHIJ".`:

```
MOVE    LEN=0008 [ABCDEFGH]      <- correct: the new content, truncated at the maximum
STRING  LEN=0008 [XYCDEFGH]      <- WRONG: STRING "XY" ... INTO an item holding 8 characters
UNSTRNG LEN=0001 [A]             <- WRONG: UNSTRING WS-S INTO the item
ACCEPT  LEN=0001 [2]             <- WRONG: ACCEPT ... FROM DATE
INSPECT CT =008                  <- correct (INSPECT as a SENDER reads the current length)
```

`scratchpad/reg5/p3_dyn.cob` (PROGRAM-ID `REG5P3`), the two receiving arms the report also named:

```
INSP-R  LEN=0008 [ABZDEFGH]      <- correct: INSPECT REPLACING preserves the length and replaces in place
INIT    LEN=0000 []              <- WRONG (derived, see below): INITIALIZE of the same item
```

`FUNCTION LENGTH` is the length witness in all three programs.

## The rule, quoted

```
$ python scripts/spec/cite.py --check 8.5.1.10.4 "If a dynamic-length elementary item is a receiving operand and is not reference-modified, the new value becomes the content of the item"
  OK  §8.5.1.10.4   (Operations on dynamic-length elementary items)
      If a dynamic-length elementary item is a receiving operand and is not reference-modified, the new value becomes the content of the item. The new length of the dynamic-length elementary item is determined by the length of new content.

$ python scripts/spec/cite.py --check 8.5.1.10.4 "If the maximum length is reached, the value is truncated on the right as necessary."
  OK  §8.5.1.10.4   (Operations on dynamic-length elementary items)
```

The clause is written over "a receiving operand", not over MOVE: every verb that stores into the item owes it.
So the three measured arms should read `STRING LEN=0002 [XY]`, `UNSTRNG LEN=0008 [ABCDEFGH]` (the sending item
truncated at the maximum) and `ACCEPT LEN=0006` (the six-character DATE image), and each of them instead stores
through the PICTURE's **one** character position — `STRING` writing two characters over a length the store never
updated, `UNSTRING` and `ACCEPT` writing exactly one.

## The INITIALIZE arm is a DERIVATION, and the derivation is printed here so the fixer does not re-do it

`INITIALIZE` of an alphanumeric item is an implicit `MOVE SPACES`. §8.5.1.10.4's own sentence routes the
figurative sender's length to §8.3.3.6, General rule 3:

```
$ python scripts/spec/cite.py --check 8.3.3.6.4 "When a figurative constant represents a string of one or more characters and the length of the string is not specified in the rules for the context in which the figurative constant is used"
  OK  §8.3.3.6.4 3)  (General rules)

$ python scripts/spec/cite.py --check 8.3.3.6.4 "When a figurative constant is other than ALL literal-1, the length of the string is one character."
  OK  §8.3.3.6.4 3)  (General rules)
      b) When a figurative constant is other than ALL literal-1, the length of the string is one character.
```

GR2 — the repeat-to-the-receiver's-size rule — is written for "a fixed-length data item, literal, or
intermediate result" and so does not reach a dynamic-length receiver; GR3 b) does, and gives the sender length
ONE. §8.5.1.10.4 then makes the new length 1, content a single space. Measured: `LEN=0000`, content empty —
which is the answer §8.5.1.10.4 reserves for a sender whose length is ZERO. Claimed, but flagged as derived
rather than differentially confirmed: the fixer should re-read GR2/GR3 before pinning a golden on it.

## What the report claimed and the measurement REFUTES

`INSPECT` is listed in the PB463 report as a fourth broken arm. It is not: as a sender it reads the current
length (`CT = 008`, not 1), and `INSPECT ... REPLACING` preserves the length and replaces in place
(`[ABZDEFGH]`). Nothing is owed there, and a fixer who "fixes" INSPECT will break it.

## Code site — why this is ONE mechanism and not four bugs

```
$ grep -rn "IsDynamicLength|DynStore|DynMaxSize" --include=*.cs src/Cobol.Net.Compiler/CodeGen/
  DataDivision/GroupImageCodec.cs   (the image codec)
  DataDivision/ValueInitializer.cs  (the VALUE seeder)
  ProgramEmitter.cs:135             (the field declaration)
  Roslyn/RuntimeApi.cs:199          (DynStore itself)
  Verbs/MoveEmitter.cs:130, :420    (the ONLY receiving-store arm)
```

`StringEmitter.cs`, `AcceptDisplayEmitter.cs`, `InspectEmitter.cs` and `InitializeEmitter.cs` contain NO
occurrence of any of the three names. The receiving-store dispatch is not a dispatch: it is one `if
(item.IsDynamicLength) return RuntimeApi.DynStore(...)` written twice inside `MoveEmitter`, and every other verb
falls through to the fixed-width store that the PICTURE's one character position describes.

**The shape of the fix is the structure, not the four call sites** (CLAUDE.md rule 5): a single
`ReceivingStore(DataItem target, string valueExpr)` helper that owns §8.5.1.10.4 — the dynamic arm, the
zero-length-sender arm and the truncate-at-maximum arm — with `MoveEmitter`'s two sites re-pointed at it, plus a
drift test asserting that no emitter under `CodeGen/Verbs` stores into a `DataItem` by any other route. Fixing
STRING, UNSTRING and ACCEPT one at a time leaves the next receiving verb broken by default.

## Landed 2026-09-22 (wave 46 group M)

**Re-probed first** on this worktree's build at `8fe62bd1f` (probe `w46m/p871.cob`, PROGRAM-ID `W46P871`): exactly the
note's numbers — `STRING LEN=0008 [XYCDEFGH]`, `UNSTRNG LEN=0001 [A]`, `ACCEPT LEN=0001`, `INIT LEN=0000 []`. A second
probe added the shape the note did not try: STRING into an EMPTY dynamic-length item OVERFLOWED at the first
character and stored nothing.

**Two of the note's four arms were re-verdicted, and one expected value was wrong.**

* **INITIALIZE is CORRECT and is not touched.** The note derived "LEN 1" from 8.3.3.6.4 GR3b and flagged it as
  unconfirmed; the rule it did not read is INITIALIZE's own:
  `cite.py --check 14.9.20.4 "When a dynamic-length elementary item is initialized, its length is set to zero."` ->
  `OK 14.9.20.4 7)`, applied under DETERMINATION D-DL1 (docs/CONFORMANCE.md 3; kb/Work PB418), which also names
  GR3b as the reason GR7 is necessary. `LEN=0000` is the specified answer.
* **STRING is NOT a replacement, so the expected `LEN=0002 [XY]` was wrong.** 14.9.43.4 GR7: "only the portion of
  the data item referenced by identifier-3 that was referenced during the execution of the STRING statement is
  changed" — `XYCDEFGH` at length 8 IS the answer for that probe. The STRING defect is elsewhere: GR6/GR8 bound the
  transfer by "the number of character positions in" identifier-3, and the emitter used the CURRENT length, so an
  empty (or short) item could not be written past its current end.
* **UNSTRING (14.9.48.4 GR11c/d) and ACCEPT format 2 (14.9.1.4 GR6) are confirmed** — both transfer "according to the
  rules for the MOVE statement", 14.9.25.4 GR8 routes a dynamic-length receiver of a MOVE to 8.5.1.10.4, and each
  stored through its OWN copy of the fixed-width arm at the PICTURE's one position (13.18.19.3 SR1). ACCEPT format 1
  (the device) had the same one-character width.

Citations re-run for this landing (all `OK`): 8.5.1.10.4 (both sentences the note quotes, plus "treated as a
fixed-length data item whose length is the dynamic-length elementary item's current length"), 8.5.1.10.1,
13.18.19.3 SR1, 14.9.25.4 GR8, 14.9.48.4 GR11 (b and c), 14.9.1.4 GR3 and GR6, 14.9.43.4 GR7 and GR8, 14.9.39.4 GR39,
14.9.20.4 GR7.

**Fix — the structure the note asked for (rule 5).** `CodeGen/Verbs/ReceivingStore.cs` is THE elementary character
receiving store: `Characters(target, sendingChars, width)` returns `DynStore` for a dynamic-length receiver and the
fixed-width aligned store otherwise. Every verb emitter that stored characters into an elementary receiver now calls
it — `MoveEmitter` (the Convert arm's alphanumeric, national and dynamic stores, and the group-sender arm), UNSTRING's
`MoveString` (which also gains the NATIONAL receiver its alphanumeric arm lacked — SR4 admits one and it fell to a
loud refusal), both ACCEPT formats, and `OoEmitter`'s BY CONTENT boolean argument copy (a formal's MOVE store,
14.8.2.3.3 rule 2d). `ReceivingStoreDriftTests` fails if any emitter under `CodeGen/Verbs` spells either store itself.

**DETERMINATION D-DL2** (docs/CONFORMANCE.md 3): where a statement's rules are written over a receiving operand's
SIZE — STRING GR6/GR8, UNSTRING GR11b, ACCEPT format 1 GR3/GR4 — a dynamic-length receiver's size is its MAXIMUM size
(8.5.1.10.1). STRING keeps GR7: the working image is the current content space-widened to the maximum (the
character 14.9.39.4 GR39 gives a grown position), and the new length is the old content's extended through the last
position written. Rejected reading: the current length (an empty item is unwritable). `ReceivingStore.DynamicReceivingSize`
is the emitters' one reader and `StringUnstringBinder.StrUnstrReceiveSize` the binder's.

**Goldens.** `conformance:2014/pb871_dynamic_length_receivers` (PB871DYNLENRECEIVERS, the introducing edition; also
passes at 2023): UNSTRING with and without DELIMITED BY plus DELIMITER IN, ACCEPT FROM DAY-OF-WEEK / DATE lengths, and
STRING into a longer item, an empty one, through a grown gap with POINTER, and past the maximum (OVERFLOW).
`conformance:negative/pb871-dynamic-length-receiver-2002` (COBOLNET0900 at 85 and 2002).

**Sibling sweep, measured or reasoned per verb.** INSPECT (sender and REPLACING) was already correct, as the note
said. READ/RETURN INTO and WRITE/REWRITE/RELEASE FROM build a `BoundMove` and so already reached `MoveEmitter`. CALL
RETURNING / INVOKE RETURNING into a dynamic-length receiver and XML/JSON GENERATE INTO were NOT measured here and are
reported as a lead rather than claimed.
