# PB4188 — a review lead is dropped when its bare id matches another findings file's lead

**Sites:** `scripts/orchestrator/review_findings.py` (`with_leads`, line ~522, and `LEAD_ID`, line ~518: the regex `\bR\d+-\d+\b` the dedupe reads).

**The defect (read in the file).** `with_leads` writes each lead under the report's `## Review findings` section once: it collects the ids `LEAD_ID` finds in the section and skips a lead whose bare id (`R<k>-<n>`) is already named. Ids are numbered PER findings file, and one report collects leads from more than one file (the wave review `review-w20261776-a.jsonl` and the lane review `review-worktree-wf_adb70c0b-786-1.jsonl`). A different lead with the same bare id is skipped without a word, and the clerk that reads the section (units/enqueue.md step 5) never sees it.

**Witness.** The PB4147 report itself: the lane review's R1-1 (the `reach_of` lead, now PB4187) never reached the report's section, because the wave review's R1-1 (a different lead) already named that id; the lane review's lead appeared only as R2-1 after a second round. Filed through R2-1 for that reason. The branch did not change `review_findings.py`.

**Fix direction.** Key the dedupe on the lead's text (or on findings file plus id), never on the bare id alone; the section then holds each distinct lead once and a re-stamp still adds nothing. Prefix the written id with its findings file's wave or lane tag if two files can emit the same id. A `--self-test` arm plants two files whose R1-1 differ. Sweep the other readers of `LEAD_ID` and of the section for the same assumption that an id is unique across files.
