# PB779 — OPEN — the rule-1 gate certifies our own errata as normative text, and rejects a correct citation of a general format

Filed 2026-09-06 by the registrar. Every number, command and output below was measured on this worktree's
`specs/ISO_COBOL.md` (47239 lines) against `scripts/spec/cite.py` as it stands; nothing is inherited.

**TWO MEASURED FACTS, one tool, opposite directions.** Part A is the gate failing OPEN — a citation that is
wrong passes. Part B is the same gate failing CLOSED — a citation that is right is rejected, and the tool's
own remedy sentence then pushes the writer to replace it. They are filed as one note because they are one
text-matching path (`clauses()` + `norm()`), one fix commit and one self-test file; splitting them would put
two halves of `cite.py`'s matching contract in two places, which is the failure this register exists to end.

# ─────────── PART A — the gate fails OPEN ───────────

## Reproduction — verbatim

```
$ python scripts/spec/cite.py --find "TO FALSE"
    ... 7 genuine hits (§7.3.16.4, §13.18.63.2/.3/.4, §14.6.13.2) ...
§G.2 3)  (List of errors)
    - WHEN SET TO FALSE phrase

8 occurrence(s)
```

That last hit is **not in Annex G**. Its text is `specs/ISO_COBOL.md:47009`, a line of the alphabetical INDEX
under the `### W` heading at `:46998`:

```
47008  - WHEN phrase [8.8.4.2.13](#section-8-8-4-2-13), [13.18.63.3](#section-13-18-63-3), ...
47009  - WHEN SET TO FALSE phrase
47010    - VALUE clause [13.18.63](#section-13-18-63)
```

Annex G proper is `:44078` (`# Annex G`) through `:44123`; `## BIBLIOGRAPHY` is `:44124` and `## Index` is
`:44147`. §G.2's own heading is `### G.2 List of errors` at `:44096` and its genuine content ends with item 3 —
`cite.py --check G.2 "It is planned to review and replace such instances by the term"` → **OK §G.2 3)**, the
"Physical file" item, which is the real thing the `3)` in every bogus hit above is pointing at.

## ⛔ The harm: a citation minted from `--find` then PASSES `--check`

This is CLAUDE.md rule 1's named inheritance failure, with the tool itself as the origin instead of a queue entry:

```
$ python scripts/spec/cite.py --check G.2 "WHEN SET TO FALSE phrase"
OK  §G.2 3)  (List of errors)
    - WHEN SET TO FALSE phrase
$ echo $?
0
```

A writer who runs `--find` to locate a phrase, copies the `§G.2 3)` the tool prints, and then dutifully runs
`--check` on it as rule 1 demands, gets **OK, exit 0** — and ships a citation to text that is not normative and
in Annex G's case is not even part of the standard. `scripts/spec/audit_code_citations.py` does not catch it
either: its spec-backed leg is the PHANTOM check only (`:44-48`, `:62`), which asks whether the clause EXISTS —
and §G.2 does exist.

Three further certifications, each measured, showing the region is not merely "the index":

```
$ python scripts/spec/cite.py --check G.2 "Merriam-Webster"                → OK §G.2 3)   [BIBLIOGRAPHY :44133]
$ python scripts/spec/cite.py --check G.2 "is un-underlined, which per"    → OK §G.2 3)   [our OWN addendum :47190]
$ python scripts/spec/cite.py --check 16.2.2.2 "Language element lists"    → OK §16.2.2.2 1)  [Annex A's title :34197]
```

The second is the worst of them. `:47069` opens `# Addendum — corrections applied to this transcription`, this
project's own errata log, whose `## Defects recorded but NOT corrected` section (`:47183`) records transcription
defects in the first person. `--check G.2` certifies those sentences as §G.2 text. The third shows the same
mechanism reaching a **normative body clause**: §16.2.2.2 is `##### 16.2.2.2 General rule` at `:34175`, the
FactoryObject method's general rule, and its region runs past `## Annex A`.

## The mechanism, quoted from the code

`scripts/spec/cite.py:38` — the clause-heading pattern requires a dotted-decimal or annex-letter NUMBER:

```
HEADING = re.compile(r"^#{2,6}\s+([0-9]+(?:\.[0-9]+)*|[A-Z](?:\.[0-9]+)+)(?:\s+(.*?))?\s*$")
```

`scripts/spec/cite.py:56-61` — a region's END is the START of the next line that matches THAT pattern, and for
the last one it is end-of-file:

```
def clauses(lines):
    heads = [(m.group(1), m.group(2) or "", i) for i, l in enumerate(lines) if (m := HEADING.match(l))]
    return [(n, t, s, heads[k + 1][2] if k + 1 < len(heads) else len(lines))
            for k, (n, t, s) in enumerate(heads)]
```

`## Index`, `### W`, `## BIBLIOGRAPHY`, `## Annex A` and `# Addendum` carry no clause number, so **none of them
is a boundary**. `--find` (`:87-96`) and `--check` (`:104-113`) both scan `range(s, e)` over that region, and
`rule_path` (`:64-76`) walks BACK from the hit to `start`, which is how an index line 2913 lines below Annex G
acquires the ordinal `3)` from G.2's own third item.

Measured span of the final region: **§G.2 = lines 44096-47239, 3144 lines**, of which 3093 are the Index and 23
the Bibliography.

Each annex row is small in line count — the annex title, `(normative)`/`(informative)`, the group title and an

⚠ The complement is CLEAN and worth recording so the fix does not "improve" it: the front matter before the
first clause (`§1` at `:1199`) belongs to no region at all, because `clauses()` starts at the first heading. The
defect is one-sided — regions run off their END, never their start.

## The fix shape — and the correct implementation already exists next door

⛔ Do NOT add "the Index" to a list of excluded regions. `scripts/spec/extract_rule_catalog.py` solved the same
problem structurally and its answer is the one to copy: it keeps a second pattern
`ANY_HEADING = re.compile(r"^#{1,6}\s+\S")` (`:51`) and closes the current block on **any** heading, taking a new
block only when the heading is also numbered — `:275-281` and `:502-508`:

```
        if ANY_HEADING.match(line) and not HEADING.match(line):
            flush()
            cur = None
            continue
```

So the region-boundary rule is written down in two places in `scripts/spec/` and only one of them is right
(`feedback_one_rule_one_place`). The fix is for `cite.py` to end a region at the next heading of ANY level — the
Index, the Bibliography, an annex title and the Addendum then bound nothing and are cited by nothing — which
makes the NEXT unnumbered section automatic instead of needing a new exclusion (CLAUDE.md rule 5). The stronger
form is to lift the boundary rule into one shared helper both scripts import, since a third copy is how this
recurs.

**Self-test, and make it fail once first** (`feedback_green_gates_arent_evidence`). `WITH DUPLICATES phrase`
occurs EXACTLY ONCE in the transcription, at `:47012`, and only as an index term:

```
$ python scripts/spec/cite.py --find "WITH DUPLICATES phrase"
§G.2 3)  (List of errors)
    - WITH DUPLICATES phrase
1 occurrence(s)                                   ← today, exit 0
```

After the fix it shall print `NO CLAUSE contains …` and exit 1, and `--check G.2 "WITH DUPLICATES phrase"` shall
FAIL. Pin BOTH, plus a positive control (`--check G.2 "It is planned to review and replace such instances by the
term"` stays OK) so the fix cannot be "make G.2 empty".

⚠ Do not build the self-test on a phrase that merely LOOKS index-only: `norm()` strips punctuation, so
`--find "Week-of-year subfield"` (index line `:47002`) also matches the prose "week-of-year subfield" in
§15.3.1.7 and would pass for the wrong reason (`feedback_probe_the_shape_the_subject_hides`).

# ─────────── PART B — the gate fails CLOSED ───────────

## ⛔ `--check 14.9.41.2 "WITH LENGTH"` FAILS, and the citation is CORRECT

Measured on this worktree, no build required:

```
$ python scripts/spec/cite.py --check 14.9.41.2 "WITH LENGTH"
FAIL: §14.9.41.2 exists but does NOT contain 'WITH LENGTH'
      run --find to locate the text and get the clause it is really in
$ echo $?
1
```

§14.9.41.2 is the START statement's general format (`##### 14.9.41.2 General format`,
`specs/ISO_COBOL.md:28107`), and it prints the phrase — `specs/ISO_COBOL.md:28115`:

```
│ <u>KEY</u> relational-operator ┤                   ├ [ WITH <u>LENGTH</u> arithmetic-expression-1 ] │
```

## The mechanism — `norm()` turns the markup into a WORD, it does not delete it

`scripts/spec/cite.py:49-51`:

```
def norm(s: str) -> str:
    """Compare on words only — dashes, quotes and spacing are typography, not content."""
    return re.sub(r"\s+", " ", re.sub(r"[^\w\s]", " ", s)).strip().lower()
```

Every non-word character becomes a SPACE. `<`, `/` and `>` are non-word; **`u` is not**. So the tags do not
vanish, they leave a one-letter word behind, measured on line 28115:

```
norm(line)          == 'u key u relational operator with u length u arithmetic expression 1'
norm('WITH LENGTH') == 'with length'        →  'with length' in norm(line)  →  False
```

The docstring's own premise is what fails: `<u>` is typography, not content, and `norm()` treats it as content.

⛔ **And it is the §5.2.2 markup that does it.** `cite.py --check 5.2.2 "Keywords are reserved words or
context-sensitive words"` → **OK**: *"Keywords are reserved words or context-sensitive words. They are shown in
uppercase and underlined in general formats."* The underline is the transcription's ONLY record of
keyword-vs-optional-word, so it is exactly the markup a general format must carry — and it splits precisely the
phrase a general-format citation is likeliest to quote: a keyword with a plain word beside it.

## The blind spot is 311 clauses wide, not one line

Measured over `specs/ISO_COBOL.md` (47239 lines):

| measurement | count |
|---|---|
| lines carrying a `<u>` tag | **1402** |
| lines where a plain word abuts an underlined word (`\w\s+<u>` or `</u>\s+\w`) — the splitting shape | **533** |
| clauses containing at least one `<u>` line | **311** of 2618 |

Three more correct citations that FAIL today, each measured:

```
$ python scripts/spec/cite.py --check 12.4.5.14.2 "RESERVE integer-1"      → FAIL   (line prints `<u>RESERVE</u> integer-1`)
$ python scripts/spec/cite.py --check 14.9.40.2 "WITH DUPLICATES IN ORDER" → FAIL   (line prints `[ WITH <u>DUPLICATES</u> IN ORDER ]`)
$ python scripts/spec/cite.py --check 14.9.41.2 "WITH LENGTH"              → FAIL   (above)
```

The markup-bearing spellings of the same three all pass, which is how each was confirmed to be genuine text:
`--check 12.4.5.14.2 "<u>RESERVE</u> integer-1"` → **OK §12.4.5.14.2**; `--check 14.9.40.2 "WITH
<u>DUPLICATES</u> IN ORDER"` → **OK §14.9.40.2**; `--check 14.9.41.2 "WITH <u>LENGTH</u> arithmetic-expression-1"`
→ **OK §14.9.41.2**.

⚠ Both of the other two are live subjects of this register — §14.9.40.2 is [[PB704]]/[[PB764]]'s SORT duplicates
phrase and §12.4.5.14.2 is the RESERVE clause of [[PB781]] — so this is not a corner of the standard nobody
cites.

## ⛔ The harm: the tool's FAIL text instructs the writer to REPLACE a correct citation

Part A mints a wrong citation and blesses it. Part B does the inverse and is quieter, because the failure is
**advice**. `cite.py:116-117` prints, on every FAIL:

```
FAIL: §14.9.41.2 exists but does NOT contain 'WITH LENGTH'
      run --find to locate the text and get the clause it is really in
```

"the clause it is really in" is a false premise here: the text IS really in §14.9.41.2. A writer obeying
CLAUDE.md rule 1 — *"A citation you did not run `--check` on is not a citation"* — is told by the gate itself
that a correct §/GR is wrong, and the three ways out are all worse than what they started with:

1. **Re-point the citation.** `--find "WITH LENGTH"` finds the phrase in the prose of other clauses, so the
   writer files the general format under a clause that merely mentions it. That is
   `feedback_a_real_clause_can_answer_a_different_question` manufactured by a tool.
2. **Quote the markup.** `--check 14.9.41.2 "WITH <u>LENGTH</u> arithmetic-expression-1"` → **OK**, and the
   citation now carries `<u>` tags into a code comment or a note — a quotation of the transcription's HTML rather
   than of the standard. `docs/rearchitecture/backlog-probe-sweep-2026-08-09.json` already holds at least five
   such recorded citations (`:212`, `:374`, `:453`, `:477`, `:485`, e.g.
   `--check 15.14.2 "<u>FUNCTION</u> <u>BYTE-LENGTH</u> ( argument-1 [ <u>PHYSICAL</u> ] )"`).
3. **Weaken the quote to an un-underlined fragment.** This is the measured, most common form.
   `kb/Work/PB697.md:32` cites the very same clause as `cite.py --check 14.9.41.2 "record-key-name"` — a bare
   operand name, which proves the clause exists and proves nothing about the phrase under discussion. A citation
   that cannot quote its own keyword has stopped being evidence.

The same avoidance is visible in test code: `tests/Cobol.Net.Tests.Conformance/OptionalWordSubsetDriftTests.cs:125-127`
records the load-bearing fact about this exact phrase in PROSE — *"Printed folio 754 underlines LENGTH and leaves
WITH plain"* — beside a row (`:727`) whose clause is `"14.9.41.2"`, rather than as a checkable quotation. The
underlining is the whole basis of the row and it is the one thing `--check` cannot be asked about.

⚠ **Neither `audit_code_citations.py` nor `audit_doc_citations.py` can see either arm.** The code audit's only
spec-backed leg is PHANTOM — *"the citation names a clause the standard does not have"* — and §G.2, §14.9.41.2
and §12.4.5.14.2 all exist. Its own docstring says so: *"IT NEEDS `specs/ISO_COBOL.md` FOR THE PHANTOM CHECK
ONLY."* A wrong citation of a real clause and a rejected correct one are both invisible to it by construction.

## The fix shape for Part B — strip the tags on BOTH sides, and prove the strip is symmetric

Delete `</?u>` from the string **before** `norm()` sees it, in the ONE place `norm()` is defined, so `--find` and
`--check` inherit it together (they are the two callers, `:90` and `:110` — `feedback_two_arm_dispatch`: this is
a dispatch with two arms and the strip must not be written into one of them).

⛔ **Strip the NEEDLE as well as the LINE, and that is not optional.** The repository already holds citations
whose quoted text contains the tags (the five `backlog-probe-sweep` rows above). Stripping only the spec line
would turn every one of them from OK into FAIL — a fix that breaks the citations it was built to protect.
Simulated over the real file, `norm(re.sub(r"</?u>", "", s))` on both sides:

| citation | today | with the symmetric strip |
|---|---|---|
| `--check 14.9.41.2 "WITH LENGTH"` | FAIL | **OK** |
| `--check 12.4.5.14.2 "RESERVE integer-1"` | FAIL | **OK** |
| `--check 14.9.40.2 "WITH DUPLICATES IN ORDER"` | FAIL | **OK** |
| `--check 15.61.2 "<u>FUNCTION</u> <u>MEDIAN</u> ( { argument-1 } ... )"` | OK | **OK** |
| `--check 15.14.2 "<u>FUNCTION</u> <u>BYTE-LENGTH</u> ( argument-1 [ <u>PHYSICAL</u> ] )"` | OK | **OK** |

⚠ Strip `<u>`/`</u>` ONLY — not "HTML tags" generally. The transcription's general formats are inside
`<pre style="line-height:1">` blocks and carry `<a id=…>` anchors; a broad tag-stripper would start deleting
content the standard does have, and `line-height:1` is itself a recorded silent-failure trap
(`feedback_render_dont_reason`). The underline tag is the one piece of markup §5.2.2 forces into the text.

## Self-tests for BOTH arms — and make each one fail first (`feedback_green_gates_arent_evidence`)

Part A, the fail-open arm:

- `--find "WITH DUPLICATES phrase"` shall print `NO CLAUSE contains …` and exit 1. Measured today: it prints
  `§G.2 3)` and exits 0, and the phrase occurs EXACTLY ONCE in the whole transcription, at `:47012`, as an index
  term. ⚠ Do not substitute a phrase that merely LOOKS index-only: `norm()` strips punctuation, so
  `--find "Week-of-year subfield"` (index line `:47002`) also matches the prose "week-of-year subfield" in
  §15.3.1.7 and would pass for the wrong reason (`feedback_probe_the_shape_the_subject_hides`).
- `--check G.2 "WHEN SET TO FALSE phrase"` shall FAIL.
- Positive control, so the fix cannot be "make §G.2 empty":
  `--check G.2 "It is planned to review and replace such instances by the term"` stays **OK §G.2 3)**.

Part B, the fail-closed arm:

- `--check 14.9.41.2 "WITH LENGTH"` shall pass. It fails today.
- `--check 15.14.2 "<u>FUNCTION</u> <u>BYTE-LENGTH</u> ( argument-1 [ <u>PHYSICAL</u> ] )"` shall STILL pass —
  the regression guard for the symmetric strip. It passes today, so run it against a one-sided strip once and
  watch it go red before trusting it.
- Negative control, so the strip cannot become "delete every `u`":
  `--check 14.9.41.2 "WITH LENGTHY"` shall FAIL, and a phrase that genuinely is not in the clause shall stay
  FAIL.

Both arms belong in the same self-test file as [[PB308]]'s, for the reason given under Links.
