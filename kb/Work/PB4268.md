# PB4268 — the BoundDeferredToExpansion exception opens with the construct's text

**Sites:** `src/WiseOwl.Cobol.Compiler/CodeGen/StatementEmitter.cs#Visit` (the `BoundDeferredToExpansion` overload: `$"{n.Construct}: a statement of an unexpanded parameterized definition ..."`),
`src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/OoBinder.cs#OoBindSetObjectRef` (records `SET … TO {sname}` as `BoundDeferredToExpansion.Construct`),
`tests/_shared/ElidedMessageOpening.cs#Source` (the head regex), `tests/WiseOwl.Cobol.Tests.Unit/DiagnosticOpeningElisionDriftTests.cs`.

**The defect (a lead from the PB4212 branch review, R1-1, low).** "R1-1 LEAD (low, not blocking at round 1): src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/OoBinder.cs:1983 The report says the sibling sweep left only mid-sentence labels and registry titles, but OoBinder records `SET … TO {sname}` as BoundDeferredToExpansion.Construct, and StatementEmitter.Visit(BoundDeferredToExpansion) (StatementEmitter.cs:288) puts that string at the head of its InvalidOperationException. That is the same class as FileRegistry.MisroutedVerb, a message raised only by a pipeline defect, which this branch did repair. The widened ElidedMessageOpening.Source cannot see it, because the head is a `{n.Construct}` hole followed by a colon."

**Fix direction.** Repair the message as the branch did FileRegistry.MisroutedVerb (the same class, raised only by a pipeline defect), and make the drift test able to see a head that is a `{n.Construct}` hole followed by a colon.
