# R13 — adjudicate: DISPLAY of a BinaryCapacity item holding a beyond-picture value shows the picture-digit image, not the value

Opened while landing R10's COMP-5 half (2026-08-08), deliberately NOT folded into it (it is a latitude
question, not a defect). `DISPLAY W` for `01 W PIC 9(18) COMP-5` holding 2^64−1 prints the picture-digit image
`446744073709551615` (the value mod 10^18, via `CobolNum.FormatDisplay` / `FormatDisplayU`), while
`MOVE W TO BIG PIC 9(20)` then `DISPLAY BIG` prints the full `18446744073709551615`. The same VALUE displays
two ways depending on the route — coherent under the documented rules (the DISPLAY conversion is
implementor-defined, §14.9.11.4 GR1; the MOVE into a NUMERIC receiver transfers the algebraic value,
§14.9.25.4 GR6d item 2 — not GR6a, which governs an alphanumeric/national receiving operand and does not
apply to `PIC 9(20)`),
but in tension with the R10 owner decision that the item OWNS its full container range.

**To adjudicate (survey_compilers_on_latitude):** what do IBM Enterprise COBOL (TRUNC(BIN)), Micro Focus and
GnuCOBOL print for DISPLAY of a COMP-5 item holding a beyond-picture value? If the survey says full value,
decide whether DISPLAY (and only DISPLAY — the GR6d move path is spec-fixed) should render the container value,
then re-derive the R10 golden's display expectations and CONFORMANCE.md item 56/59 wording. The GnuCOBOL
differential may surface this on its own as a per-case flip; attribute it here if it does.

**SURVEY COMPLETE 2026-08-08** (web research workflow `wf_1d8f1ced-bfc`; IBM evidence from the Enterprise
COBOL 6.4 Programming Guide PDF read directly, TRUNC section pp. 419–421): **the vendors are SPLIT.**
- **IBM**: DISPLAY prints the **FULL container value, always** — COMP-5 is handled as if TRUNC(BIN) were in
  effect regardless of the TRUNC subopt (strong).
- **GnuCOBOL** (default dialect, binary-truncate yes): DISPLAY prints the value **TRUNCATED to the PICTURE
  digits** (strong) — i.e., OUR current behavior.
- **Micro Focus**: storage is explicitly untruncated (container capacity); the DISPLAY rendering itself was
  not directly evidenced (weak).
ADJUDICATION RESULT: no vendor consensus exists, both behaviors are defensible under §14.9.11.4 GR1's
implementor latitude, and our current picture-digit image matches GnuCOBOL's default while IBM prints the
container value. **The tension with the R10 owner decision ("the item OWNS its full container range") makes
this an OWNER call, now fully informed** — flip to IBM-style full-value DISPLAY (re-deriving the R10 golden
+ CONFORMANCE item 56/59 wording), or keep the GnuCOBOL-style status quo and record it as the documented
determination. Until decided, the status quo stands.

## LANDED 2026-08-08 (OWNER DECISION: follow GnuCOBOL)

The owner decided: **follow GnuCOBOL** — DISPLAY of a BinaryCapacity item holding a beyond-PICTURE value
renders the PICTURE-digit image (the value modulo 10^digits), the existing behavior, now a documented
determination instead of an accident. No tension with R10 remains: the item still OWNS its full container
range (storage, arithmetic, relations, and the spec-fixed §14.9.25.4 GR6d MOVE path all carry it); only
the §14.9.11.4 GR1 display CONVERSION renders the description's digit positions. Recorded as
CONFORMANCE.md **§7 item 56** (A.1's "DISPLAY statement (data conversion)", required + documented — one
more obligation discharged, 18 of 199); the deliberately-unpinned display is now pinned by the golden
`comp5_display_beyond_picture` (both legs: the truncated DISPLAY and the full value via MOVE). The
owner's broader preference — on implementor latitude where the vendors split, follow GnuCOBOL — is
saved to session memory for future adjudications.

The R10 golden deliberately avoids pinning a bare DISPLAY of a beyond-picture value so this question stays
open without a golden rewrite.
