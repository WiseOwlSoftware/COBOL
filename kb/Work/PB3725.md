# PB3725 — merge times are recorded only by the enqueue unit

**Sites:** `scripts/orchestrator/landing_measure.py` (`complete`), `scripts/orchestrator/units/enqueue.md` (step that runs `complete`), `scripts/orchestrator/land_lane.py` (`tick`, `watch_queue`: the lane's tick and queue watch) and `scripts/orchestrator/orchestrate.ps1` (the supervisor's queue watch, which already polls each queued pull request), `scripts/orchestrator/progress.py` (`progress`: the merged count).

## What happens

At 11:13 and 11:23 on 2026-10-25 the campaign unit's PROGRESS line read "landings since the unit started: enqueued 5, merged 0" while PRs #565 (17:52Z), #566 (17:55Z) and #567 (18:04Z) had merged; the Mythos lane reported it too (mailbox 20261025-111421). Their landing records carried `merged: None`. The only caller of `landing_measure.py complete`, which reads each pull request's merge time, CI wall and bounces, is the enqueue unit (units/enqueue.md:95). PB3639 moved landing into the lane, which ticks inside every unit, so after 10:05 no enqueue unit ran and nothing completed the records. The operator ran `complete` by hand at about 11:30 (it filled #565 to #568: CI wall 13.8, 12.8, 12.2 and 2.5 minutes). PB3639 moved the landing and left its measurement behind: rule 4's sibling sweep.

## Fix direction

Complete a record where the merge is seen: the lane's tick or the supervisor's queue watch runs `complete` for a pull request it sees leave the queue, so the record never depends on which unit runs. Remove the enqueue unit's own call once that holds (one caller). Self-test: a pull request that merges while only a campaign unit runs has its merged time at the next tick, and the PROGRESS line counts it.
