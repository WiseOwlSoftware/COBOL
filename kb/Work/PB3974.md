# PB3974 — an EVALUATE arithmetic-expression subject is held at S9(21)V9(17)

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/SendingValueTemp.cs` (`SendingValueTemp`: `IntermediatePic`, `ValueOperandPicOf`, `OfComputed`),
`src/WiseOwl.Cobol.Compiler/Binding/Procedure/ExpressionExtent.cs` (`ExpressionExtent`, `ExactExtent`),
`src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs` (`EvaluateBinder`, the subject-temporary intake).

Filed 2026-10-28 by the enqueue unit's clerk from the PB3953 implementer's lead, carried unchanged. Not re-probed by the
clerk; the repro file `E:/COBOL-coord/scratch/w20261728f/i3.cob` lived in the reviewed branch's scratch and may be gone.

## Repro (measured by the PB3953 implementer)

`BIG` is a wide numeric item; the program is `EVALUATE BIG * BIG WHEN 1 ... WHEN BIG * BIG ... WHEN OTHER`. The second
`WHEN` compares the subject with the same expression and must select, yet the statement takes OTHER: the subject's
temporary (the `SendingValueTemp` intermediate, S9(21)V9(17)) truncates the product past 21 integer digits, so the
temporary no longer equals the exact expression the WHEN object evaluates.

## Mechanism (the report's)

The same fixed-width intermediate PB3268 narrowed for a function subject (landed: `EVALUATE FUNCTION PI` compared at nine
places) still bounds an arithmetic-expression subject at 21 integer digits. Its own root, not shared with PB3953 (the
38-digit window of a function argument) and not covered by PB3268's landing (a function-valued subject).

Fix at the root: the subject temporary of an arithmetic-expression subject carries the expression's own width, a golden
for the repro above, and a sweep of every other `SendingValueTemp` user that holds an expression (the siblings PB3268's
landing listed).

## Landed

**Re-probe (own build, 2026-10-28).** The repro `i3.cob` printed `1-EXACT 2-OTHER 3-OTHER 4-OTHER 5-EXACT` (cases 2-4 wrong:
A * B * C at 30 digits and BIG * BIG at 36, against their own expression). A wider probe showed the fraction side too:
`SM * SM` at 24 fraction digits was held at 17 and took `WHEN 0`.

**Root cause.** `SendingValueTemp.IntermediatePic` ended in `ValueOperandPic` (S9(21)V9(17)) for every value no receiver
bounds, and an ARITHMETIC EXPRESSION is such a value: the hold kept 21 integer and 17 fraction digits of a product the
un-hoisted expression evaluates exactly (§14.9.13.4 GR3 c) assigns the subject "a numeric value according to the rules for
evaluating an arithmetic expression"; GR4 a) 6. compares that value).

**Fix.** `ExpressionExtent` states the integer digits and the scale of an expression of `+`, `-`, `*`, unary minus, literals
and fixed-point items (a mathematical bound: a sum is below 10^(max+1), a product below 10^(i+j); no carrier rule is
restated), and `SendingValueTemp.ValueOperandPicOf` holds the subject in the item of exactly those digits. A value past the
38-digit scaled carrier has no item, so the expression stays un-hoisted (`Materialize` answers null, as for a
variable-length group); an expression with a quotient, a power or a function in it keeps the 21 + 17 item (residual: a
width no bound states). Sibling arms swept: the one other holder of an arithmetic expression, `ArgumentOrder`'s frozen
function argument, shares the `Materialize` path and is fixed with it (`COMPUTE R = FUNCTION MAX(BIG * BIG, T(FUNCTION
MIN(1 2)))` stores the whole product); the MOVE, INVOKE and SET holders carry function values and character text, never an
expression; the subscript temporary (`SegmentTempPic`) is a saturated integer position, a different item.

**Goldens.** `cases/14.9.13-EVALUATE/pb3974_evaluate_expression_subject_width` (nine EVALUATEs, every edition; no negative,
the change rejects no source) and the unit tests `ExpressionExtentTests`.
