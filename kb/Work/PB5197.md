# PB5197 - at --std 85 a WRITE outside the bounds of RECORD CONTAINS integer-4 TO integer-5 is unsuccessful with status 44 and the record is not written: BindRecordClause stores Format 3 in FileModel.Varying like Format 2

**Sites:**

- `src/WiseOwl.Cobol.Compiler/Binding/FileControlBinder.FileSection.cs` (`BindRecordClause`)
- `src/WiseOwl.Cobol.Compiler/Binding/Model/FileModel.cs` (`RecordSizeVaries`)
- `src/WiseOwl.Cobol.Runtime/IO/SequentialConnector.cs` (`OutsideVaryingBounds`)

**Mechanism.** §1985:VII.1.3.5 gives status 44 (a boundary violation) for a record outside the bounds of the RECORD IS VARYING clause only; Format 3 (RECORD CONTAINS integer-4 TO integer-5) only documents the smallest and largest record sizes. `BindRecordClause` stores a Format 3 clause in the same `FileModel.Varying` as Format 2, `RecordSizeVaries` passes the integers to the connector as a range, and `OutsideVaryingBounds` answers 44 at every edition, the 2023 rule. At --std 85 a WRITE of a 2- or 6-character record under 3 TO 5 fails with 44 and the record is lost.

**Found by.** The 1985 code read (2026-11-10; its records are `E:/COBOL-coord/scratch/coderead-85/for-register.json`): each rule below was read against the code sites it names and probed at `--std 85`, and found non-conforming. Verdict, harm, evidence, repro and observed text are the records'; the rows' verdicts are recorded on another branch.

**Inventory.** `work.py check` refuses a 1985 rule id in `inventory_rows` (kb/Work PB5094, open), so `inventory_rows` is empty and the rows this note claims are the rule ids of the list below.

Code read: No kb/Work note owns the fix (none found). §1985:VII.1.3.5 lists the logic-error values of a sequential file: 41 (OPEN of a file in the open mode), 42 (CLOSE of a file not in the open mode), 43 (REWRITE not preceded by a successfully executed READ), 44, 46 (a sequential READ with no valid next record after an unsuccessful or at end READ), 47 (READ on a file not open in the input or I-O mode), 48 (WRITE on a file not open in the output or extend mode) and 49 (REWRITE on a file not open in the I-O mode). Seven conform at --std 85, each probed: FileConnector.Open gives 41 (OPEN OUTPUT, INPUT and I-O of an open file); FileConnector.Close and FileRegistry.CloseCell give 42 (never opened, closed twice, after a failed OPEN); SequentialConnector.Rewrite gives 49 through MutationOpenModeGuard (not open, INPUT, OUTPUT, EXTEND) and then 43 when PrevOpWasSuccessfulRead is false (no READ, a second REWRITE, after an at end READ); SequentialReadGuard gives 47 through ReadOpenModeGuard (not open, OUTPUT, EXTEND) and 46 after an unsuccessful READ (after at end, and again after the 46); SequentialConnector.Write gives 48 (not open, INPUT, I-O). 44 conforms for its two 1985 causes: OutsideVaryingBounds refuses a WRITE or REWRITE outside a RECORD IS VARYING range (7 and 2 characters under FROM 3 TO 6: 44, DEPENDING ON item unchanged) and RewriteRecordSequential refuses a REWRITE whose size differs from the record read (44, record unchanged on re-read). What does not conform is a third cause the 1985 list does not have: BindRecordClause stores a Format 3 clause (RECORD CONTAINS integer-4 TO integer-5) in the same FileModel.Varying as Format 2, RecordSizeVaries passes its integers to the connector as the range, and OutsideVaryingBounds then answers 44 at every edition, so at 85 a WRITE of a record shorter than integer-4 or longer than integer-5 is unsuccessful and the record is not stored. That is §2023:13.18.43.4 GR19, which 1985 does not have: 1985 item 44 1) names only "the RECORD IS VARYING clause", and for Format 3 §1985:VII.3.8.4 GR14 says "the size of each data record is completely defined in the record description entry"; no 1985 rule makes that WRITE unsuccessful, and the row's change record names this difference. The witness shows the USE procedure run with 42 on the second CLOSE.

**Expected (from the 1985 text, the record's).** WRITE 2 UNDER 3 TO 5 00 / WRITE 4 UNDER 3 TO 5 00 / WRITE 6 UNDER 3 TO 5 00, with three records in the file. §1985:VII.1.3.5 gives 44 two causes only: "1) An attempt is made to write or rewrite a record that is larger than the largest or smaller than the smallest record allowed by the RECORD IS VARYING clause of the associated file-name, or 2) An attempt is made to rewrite a record to a sequential file and the record is not the same size as the record being replaced." The file has a Format 3 RECORD clause, for which §1985:VII.3.8.4 GR14 says "However, in this case, the size of each data record is completely defined in the record description entry", and no rule of §1985:VII.3.8.3 or §1985:VII.4.7.4 makes the WRITE unsuccessful (the Amendment 2 paragraph of §1985:VII.3.8.4 GR10 speaks of integer-2 and integer-3, Format 2). The unsuccessful WRITE is the later rule §2023:13.18.43.4 GR19 ("If the number of bytes in the logical record to be written is less than integer-4 or greater than integer-5").

**Observed (the record's).** exit 0, no compile diagnostic; the run displays WRITE 2 UNDER 3 TO 5 44, WRITE 4 UNDER 3 TO 5 00, WRITE 6 UNDER 3 TO 5 44, and the file holds the one 4-character record (04 00 00 00 '4444'). --std 2023 prints the same lines.

**Fix direction (root cause, CLAUDE.md rule 4).** Keep the two formats apart on the FileModel (a Format 3 range is documentation at the editions whose rule says so) and let the connector check only a Format 2 range there; the choice is the binder's, read once.
