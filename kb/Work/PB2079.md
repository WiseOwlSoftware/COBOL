# PB2079 — LANDED (wave 1034 C)

Found 2026-10-05 by the train 1021 cluster-C verifier while sweeping review finding C-2 (the address-identifier
argument of CONVERT / BASECONVERT). Pre-existing on base `17924fbb4` for the data-item shapes; the ADDRESS OF shape
became reachable when 41047d883 admitted an address-identifier as a function argument.

## Rule

ISO/IEC 1989:2023 §15.12.3 r1 (`cite.py --check` OK): "Argument-2 and argument-3 shall be positive nonzero numeric
integer literals or data items with unequal values in the range 2 to 16."

## Repros (E:/COBOL-coord/scratch/train1021/verify/C/probe/)

- `f2b4.cob` — `FUNCTION BASECONVERT("1A" A 10)`, `A PIC X(2) VALUE "16"`: compiles clean at `--std 2023` and prints
  `R=26`. Expected: refused at compile time (argument-2 is not a numeric data item).
- `f2b3.cob` — the same with `P USAGE POINTER` as argument-2: `error: backend compilation failed … CS1503: Argument 1:
  cannot convert from 'CobolNet.Runtime.ManagedPointer' to 'System.Int128'` (a crash in the generated C#, not a COBOL
  diagnostic).
- `f2b2.cob` — `BASECONVERT("1A" ADDRESS OF X 10)`: compiles, then `NotImplementedCobolFeatureException:
  address-identifier as a numeric operand` at run time.

## Code site

`src/Cobol.Net.Compiler/Binding/IntrinsicArgumentRules.cs#DeliberatelyUnscreened` lists BASECONVERT as unscreened
because argument-1's rule is usage-keyed, and so argument-2 and argument-3 lost their class screen too, although
r1's second sentence is an ordinary class rule ("numeric integer literals or data items"). The catalog row
(`IntrinsicCatalog.cs`, `"sii"`) already declares them integer kinds. `IntrinsicBinder.CheckBaseConvertArgs` screens only
STATIC literal bases.

## Fix direction

Screen argument-2 and argument-3 through the ONE argument-class screen (class numeric, and the §15.3 r6 integer
test through `IntrinsicResultType.IsIntegerOperand`), leaving argument-1 to `CheckBaseConvertArgs`. Either give
BASECONVERT a schema whose argument-1 kind is unscreened and whose argument-2/-3 kinds are `'i'`, or screen the two
positions in `CheckBaseConvertArgs`. Update the `DeliberatelyUnscreened["BASECONVERT"]` text in the same change.
Goldens: one negative per shape (alphanumeric item, USAGE POINTER item, ADDRESS OF), each reject-at 2023.

## Landed (wave 1034 C)

All three repros reproduced on the wave's build (`R=26`; CS1503; NotImplemented) and now draw COBOLNET1627 at bind.
`cite.py --check 15.12.3 "positive nonzero numeric integer literals or data items with unequal values in the range 2 to 16"`
OK (rule 1); `15.6` Table row `BASECONVERT | Anum1 or Nat1, Int2, Int3` OK; `15.3` r6 (Integer) OK.

- **The row.** `IntrinsicArgumentRules.Verified["BASECONVERT"]` is now `Schema("§15.12.3 r1", [UnscreenedKind, 'i', 'i'])`
  with the `DataItemOrLiteralOnly` predicate on both bases (the rule says "literals or data items", so a nested function
  or expression is neither, as for FIND-STRING's §15.37.3 r3). `UnscreenedKind` is the new DECLARED no-class-set kind, so
  argument-1 (a usage rule, `CheckBaseConvertArgs`) keeps its ordinal. The `DeliberatelyUnscreened` BASECONVERT entry is
  deleted, and so is CONCAT's, which was in BOTH tables with a stale "STILL unscreened" claim (its `'c'` row screens r1).
  `NoFunction_IsBothVerified_AndDeliberatelyUnscreened` and
  `EveryVerifiedPositionKind_HasADisposition_AndUnscreenedOnesAreOnlyBaseConvertArgument1` keep both true.
- **Found on the way and fixed (I9): the `--permissive` coercion reached a pointer.** `CheckArgumentClasses.Report` downgraded
  every class violation to a warning under `--permissive`, so `BASECONVERT("1A" P 10)` and `FUNCTION ABS(P)` warned and then
  died in Roslyn (CS1503) exactly as strict mode used to. A pointer or object-reference operand holds nothing to render or
  decode, so the violation stays an error (`IsDigitDecodable`, the same predicate the §8.8.1.1 operand screen asks).
- **The fractional literal base.** `2.5` is now caught by the schema's integer test (COBOLNET1627); `CheckBaseConvertArgs`
  keeps only what the value test cannot see ("2.0" has an integral value but is not an integer LITERAL, §8.3.3.3.2), so
  one literal draws one diagnostic. `pb59-baseconvert-noninteger-base.err` moved COBOLNET1642 -> COBOLNET1627.
- **Goldens.** Negatives `pb2079-baseconvert-alphanumeric-base`, `-pointer-base`, `-address-of-base`, `-function-base`
  (reject-at 2023, COBOLNET1627) and the positive `2023/pb2079_baseconvert_data_item_bases` (numeric DISPLAY and binary data
  items as bases: 255 / FF / 1010, derived from §15.12.4 r1).
- **Sweep.** The other `DeliberatelyUnscreened` functions (BYTE-LENGTH, LENGTH, CONVERT, the ALGEBRAIC three, DISPLAY-OF,
  NATIONAL-OF, MODULE-NAME, EXCEPTION-FILE/-N) take no operand whose rule is a class the table could carry that a bespoke arm
  does not already enforce (read each row's reason); the Table 21 integer-position drift test now covers BASECONVERT.
