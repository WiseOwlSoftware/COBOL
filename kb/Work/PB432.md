# PB432 — one operand slot that is both too wide and too narrow, and one level binder that screens nothing

## 1. THE MECHANISM

Two halves of one omission, in two files.

**(a) The slot's TYPE.** `CobolControlFlow.g4:118-131` types both operand slots as `arithmeticExpression`:

    performVarying
        : (WITH? TEST (BEFORE | AFTER))?
          VARYING dataReference FROM arithmeticExpression
          (BY arithmeticExpression)?
          UNTIL condition
          performVaryingAfter*

where the general format prints brace groups — `{identifier-3 | index-name-2 | literal-1}` for FROM and
`{identifier-4 | literal-2}` for BY. One substitution makes the slot simultaneously **wider** (any additive /
multiplicative / power expression is admitted) and **narrower** (a figurative constant is not). The narrowing is
not the grammar shape but the token rewriter: `CobolExpressions.g4:243-249` gives `primaryExpression` a
`ZERO_ARITH` arm rather than a `figurativeConstant` arm, and `src/Cobol.Net.Frontend/Parsing/ZeroTokenRewriter.cs`
mints `ZERO_ARITH` purely by ADJACENCY to `+ - * / **` or a grouping paren. A bare FROM/BY operand has no such
neighbour, so the `ZERO` token survives and no alternative matches it. The widening was deliberate — the comment
at `src/Cobol.Net.Compiler/CodeGen/Emit/NumericRenderer.cs:93` says the binder types these `BoundExpr` "for
convenience" — and the ZERO loss looks like its unnoticed cost.

**(b) The level binder screens NOTHING.**
`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:392-406` is the ONE function that binds an
induction level, and every operand goes straight through:

    if (host.Set.SetTargetOf(dref) is not { } var) return null;           // :396 — no index-name test
    BoundExpr from = host.Expr.BindIndexWindowExpr(exprs[0]);             // :398 — no category/sign/scale screen
    BoundExpr by = exprs.Length > 1 ? host.Expr.BindIndexWindowExpr(exprs[1]) : new BoundNumLiteral("1");  // :403

No arm asks whether the induction variable is an index-name, whether the FROM operand resolved to an index-name,
whether an operand is an integer data item, whether a FROM literal is positive, or whether a BY literal is zero.
So all seven lettered obligations of SR4 a/b/c, SR5 a/b/c and SR6 are missing **from one site**. The premise of
SR5 is not even computed. The compiler already owns the classifier this needs: the sibling rule SR2 routes every
`PERFORM … TIMES` count through `IntrinsicResultType.IsIntegerOperand` and emits `COBOLNET1646`
(`ControlFlowBinder.cs:420-433`, kb/Work PB86, landed) — so the missing work is a screen at `BindVaryingLevel`,
one call away, not a new mechanism.

## 3. EXPECTED vs OBSERVED — RE-RUN ON HEAD (89044aa0)

Every case still reproduces. `--std 2023`, HEAD `cobol.exe`.

**(a) LEGAL SOURCE REJECTED.**

    $ cobol.exe .../pf_zero_varying_from.cob --std 2023 --run
    exit 65
    error COBOL0001: no viable alternative at input 'ZERO'
      error COBOL0001: unexpected 'ZERO'
      source: 01 I PIC 9(4) VALUE 9.  PERFORM VARYING I FROM ZERO BY 1 UNTIL I > 3 …

Expected: compiles, I initialised to 0. ⚠ The rejection's second line — "A data-name is expected here, not a
literal" in the pinned build, "unexpected 'ZERO'" on HEAD — names no rule either way, and the pinned wording was
actively **wrong**, since a numeric literal IS legal in that slot.

**THE ISOLATING PROBE, re-run on HEAD** — one token of adjacency flips the outcome, which names the mechanism
rather than guessing at it:

    $ cobol.exe .../pf_zero_plus_varying.cob --std 2023 --run
    exit 0
    N=0004 I=0004
      source: PERFORM VARYING I FROM ZERO + 0 BY 1 UNTIL I > 3 …

`ZERO + 0` parses; bare `ZERO` does not. The gate is `ZeroTokenRewriter`, not the grammar shape.

**(b) ILLEGAL SOURCE ACCEPTED.**

    $ cobol.exe .../pf_varying_expr.cob --std 2023 --run
    exit 0
    I=0023 N=0003
      source: 01 A PIC 9(4) VALUE 2. 01 B PIC 9(4) VALUE 3.
              PERFORM VARYING I FROM A + B BY B * 2 UNTIL I > 20 …    (no diagnostic at any --std)

**(c) SR4 / SR5 / SR6 — measured one at a time**, table `01 T. 05 E PIC X(4) OCCURS 10 INDEXED BY IX1 IX2.`,
`01 NI PIC 9(4)V99 VALUE 1.5.`, `01 II PIC 9(4) VALUE 2.` Re-run on HEAD:

    SR4 b)  PERFORM VARYING IX1 FROM 0   BY 1 UNTIL IX1 > 3   -> exit 0, N=0004  (pf_sr4b_from_zero)
            — the index sits at the OUT-OF-RANGE value 0 for a whole iteration.
    SR4 c)  PERFORM VARYING IX1 FROM 1   BY 0 UNTIL N   > 3   -> exit 0, N=0004  (pf_sr4c_by_zero)
    SR5 a)  SET IX2 TO 1 / PERFORM VARYING NI FROM IX2 BY 1 UNTIL NI > 3
                                                              -> exit 0, N=0003 NI=000400  (pf_sr5a)
    SR6     PERFORM VARYING I FROM 1 BY 0 UNTIL I > 5 … IF N > 10 EXIT PERFORM …
                                                              -> exit 0, N=0011  (pf_sr6_by_zero)

SR6 is the one that changes a program's outcome rather than merely its legality: `BY 0` is a guaranteed
non-terminating loop, and the probe only returns because a counter guard was planted in the body — N=11 proves
the loop was still running when the guard fired. That is the whole reason the standard forbids the literal.
I re-ran SR4 b), SR4 c), SR5 a) and SR6 on HEAD; SR4 a) (`FROM NI` / `BY NI`, non-integer identifiers) and
SR5 c) (`BY 1.5` against an index-name FROM) I confirmed by READING `BindVaryingLevel` — there is no screen of
any kind at `:396-406`, so no operand shape can be rejected there.

## 4. THE CODE SITE AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Frontend/Grammar/Core/CobolControlFlow.g4:121-123`, `:129-130` — the FROM/BY slots
* `src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4:243-249` — `primaryExpression`'s `ZERO_ARITH`-only arm
* `src/Cobol.Net.Frontend/Parsing/ZeroTokenRewriter.cs` — the adjacency sets and the rewrite loop
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:392-406` — `BindVaryingLevel`, no screen
* `src/Cobol.Net.Compiler/Binding/IntrinsicResultType.cs` — `IsIntegerOperand`, the classifier to reuse

⛔ **The two halves of (a) MUST be fixed together.** Narrowing the slot to the printed brace group without adding
a figurative arm leaves `FROM ZERO` broken; adding the figurative arm without narrowing leaves `FROM A + B`
accepted. The right shape is **ONE named operand rule** — `{identifier | index-name | numeric-literal-including-
the-figurative-ZERO}` — shared by the VARYING level and every AFTER level, in place of the two
`arithmeticExpression` slots. That rule then becomes the ONE place SR3, SR4, SR5 and SR6 hang their screens, and
the `performTimes` count operand (`:110`) is its obvious next client.

For (b): **`BindVaryingLevel` takes the level's ROLE, not four loose arguments.** Today it receives
`(dref, exprs, cond, firstLevel)` and cannot express "this level's variable is an index-name" or "this level's
FROM resolved to an index-name" — the two premises SR4 and SR5 key on. Give it the resolved variable KIND and the
resolved FROM KIND, and all seven lettered obligations become predicates over those two, in one place.

⛔ **SR4 and SR5 are TWO ARMS OF ONE QUESTION** — which POSITION holds the index-name (SR4: the VARYING/AFTER
position; SR5: the FROM position) — written in ONE binder function that screens neither. A fix that screens the
VARYING position and not the FROM position is this project's most reproducible defect shape. Ask which arm you
fixed.

## 5. THE SIBLING SWEEP

* **`performTimes` (`CobolControlFlow.g4:109-111`) is the second route to the same user-visible loss.**
  `PERFORM ZERO TIMES` is a parse error on HEAD (measured: `COBOL0001 no viable alternative at input
  'PERFORMZERO'`). ⚠ Its cause is NOT what the adjudication recorded — see the report; on HEAD the rule is
  `(integerLiteral | functionCall | dataReference) TIMES`, three arms, none of which admits a figurative
  constant. The claim there is weaker than for VARYING (integer-1 is an integer literal, not a plain numeric
  one), but a fixer must decide it deliberately rather than inherit it.
* **Every other operand slot typed `arithmeticExpression` where the figure prints a brace group.** The FROM/BY
  slots are one instance; grep the grammar for `arithmeticExpression` in a slot whose format prints
  `{identifier | literal}` and check each against its figure.
* **Every other bare-figurative operand position that only `ZeroTokenRewriter`'s adjacency can reach.** The
  rewriter is the gate, so every slot fed by `primaryExpression` inherits the hole. `ZERO` is accepted in
  COMPUTE, ADD, MOVE and in a relation in the same program, which is why a user has every reason to expect it
  here.
* **The Report Writer's `VARYING` FROM/BY** (`ReportWriterBinder.cs:48-49`) is the other client of the same r7
  index window (see the OPEN note PB215) and will inherit whatever operand rule replaces `arithmeticExpression`.
* **`SetTargetOf` callers.** If the repair teaches `BindVaryingLevel` the variable's KIND, check every other
  `host.Set.SetTargetOf` site for the same missing premise.

## 6. ROWS

* `SR-14.9.28.3-3` — PARTIAL. The PROHIBITION half holds (an alphanumeric literal in either slot is rejected,
  because `primaryExpression` has no `nonNumericLiteral` arm; a legal non-INTEGER numeric literal is still
  correctly admitted where no index-name is involved). The ADMISSION half is narrower than the rule: the
  figurative ZERO that §8.3.3.6.3 SR1 a) permits is refused outright. PARTIAL rather than DIVERGES because the
  prohibition half is genuinely implemented.
* `SR-14.9.28.3-4` — NOT-IMPLEMENTED. All three lettered sub-rules absent at `BindVaryingLevel`; no diagnostic
  code exists for any of them (the diagnostics dossier's only §14.9.28.3 entry is `COBOLNET1646`, which is SR2).
* `SR-14.9.28.3-5` — NOT-IMPLEMENTED. The rule's PREMISE (an index-name in the FROM phrase) is never computed,
  so none of a)/b)/c) can fire.
* `SR-14.9.28.3-6` — NOT-IMPLEMENTED. Decidable entirely at compile time (it constrains a LITERAL), and the
  check is one `is BoundNumLiteral { } l && l.Value == 0` at `:403`. Note the overlap with SR4 c): where the
  varied item is an index-name, `BY 0` violates both rules and neither fires.
