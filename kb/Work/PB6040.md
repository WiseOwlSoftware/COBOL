# PB6040 - the bare-ordinal designator is unread

**Sites:** `scripts/spec/citation.py` (`LOOSE_RULE`, `loose_designator`).

**Where it stands.** About 138 lines (`git grep -nE "§[0-9]{4}:[0-9A-Z.]+ [0-9]{1,2}([ ,;.]|$)" -- src tests docs
conformance-suite` at branch train85e-e2-cite), for example the comments of BoundTree.cs line 1550 (`§2023:14.6.4 7;`),
DataItem.cs line 109 (`§2023:9.3.6 3 e)`), ConditionBinder.cs line 1985 (`§2023:8.4.2.2.1 1,`) and RecordLayout.cs
(`§2023:8.5.1.9.1 2`, named by PB4976).

**What is wrong.** `LOOSE_RULE` reads a rule named in words (`rule 2`), by its printed label (`2)`) and, since PB6035's
branch, by the abbreviation `r<n>` (`r3d`). A bare number after the locator (`§2023:14.6.4 7`) is none of these, so
RESOLVE reads the citation as the bare clause and the rule it names is checked by nothing.

**Why it was not done with PB4976.** A bare number after a citation is also ordinary prose (`§2023:8.5 2 items`,
`§2023:13.18.40.3 12 characters`), so the reader needs a rule for telling the two apart (for example: the number is a
rule ordinal only when the catalog's clause has a numbered rule list and the word after it is no noun), measured on the
138 sites before it gates; that is its own design step.

**Fix.** Add the arm to `LOOSE_RULE` with that rule and a self-test planting both readings; run
`audit_code_citations.py --canonicalize` over the sites (the canonicalizer is safe on message text, PB6035) and
`--write-baseline --grow` for the stricter checker.
