## What landed (each re-probed on the build first, each cross-checked)

- **`<<<<` (quaternary relation)** — re-probe: `ja` reported "116 quaternary (<<<<) relation(s) applied as identities";
  `ぁー` vs `ァー` compared −1 where the host ICU compares 0. Now `CollationElement.Quaternary` (0 on every root
  element), a fourth `Line` and `BuildElement` slot in `CldrTailoringBuilder`, `CollationTable.HasQuaternary`, and a
  level 4 in `Collator` when the collation is Shifted or the table has the weights: Hiragana before Katakana at
  `-u-ks-level4` (JIS X 4061 4.4.10.2 (3), the rule file's own comment), equal through level 3 as ICU has it.
  **Sibling found in the same builder and fixed (I9):** `p|x` became the contraction p+x with p's elements as of the
  rule's moment, so ja's `ァ|ー` (ァ is placed later by `&ぁ<<<<ァ`) carried a stale ァ — now p's final elements are
  read when the table is planned (`Builder.PrefixedElements`); the pair is in the ICU cross-check corpus.
- **`[caseLevel on]` / `-u-kc-true`** — `CollationOptions.CaseLevel`: the case level sits between level 2 and 3 at any
  strength, ICU's participation rule, the tertiary weight without the case prefix; `Collator.ActiveLevels` is the one
  list `Compare` and `GetKey` both walk; `CollationKey` keeps levels by number. Against the host ICU: `IgnoreNonSpace` is
  primary strength + case level, 1,444 pairs agree. cu.xml (`[caseLevel on]`) loads with nothing unsupported.
- **`[numericOrdering on]` / `-u-kn-true`** — `CollationOptions.NumericOrdering`: a maximal run of General_Category Nd
  digits is one number (lead, significant-digit count, digits). The digit set is the TABLE's Unicode data: the
  generator writes the 77 runs of ten (format 3; the runtime reads format 3 only). 20,000 random pairs agree with the
  host ICU (`CompareOptions.NumericOrdering`). Deliberate difference: a run past 254 digits is ONE number here, ICU
  splits it into 254-digit numbers (a 255-digit number sorts before a 254-digit one there) — UTS #35 words it "numeric value".
- **The ~6 ms rebuild** — measured stage by stage (115 builds): the Builder constructor's pool scan 2.7 ms, the pool
  copy through a delegate 1.8 ms, `Line.Number` over every root ~1.5 ms, two `ToArray` 0.5 ms, copies and closure 0.7 ms.
  Fixed at the causes (roots once per base table; sparse numbering; `ElementRemap` lookup arrays; one pool array):
  Spanish 7.9 ms / 10.5 MB → 0.66 ms / 2.1 MB, a rule-less collation is the root table at 2 KB. All 143 locale tables
  fingerprint identical before and after. Neither option this note listed was taken: an overlay cannot share a pool whose
  weights renumber, tertiary headroom changes the numeric `.tailor` scale.
- **The NFD allocation** — pooled working arrays, `string.Create`, and a span form into the caller's `stackalloc`: the
  accented-text normalization 520 → 42 B per text, a mixed-script comparison 130 B → 0.

## Open — the one owner question: `[hiraganaQ on]` / `-u-kh-true`

CLDR's own `bcp47/collation.xml` marks `kh` `deprecated="true"` ("Hiragana to be sorted before all non-variable on
quaternary level"); ICU 53+ ignores it; no CLDR collation file uses it. Implementing it needs the Script property
(Hiragana is not a Unicode block: U+3041–3096 and U+309D–309F, but also parts of Kana Supplement/Extended), which the
pinned `data/unicode/` does not carry — a `Scripts.txt` input and a format-4 table section, plus a level-4 rule for the
Hiragana elements under Shifted. Rule 3 allows a deferral only by owner decision, so the question is:
**implement `hiraganaQ` (pin Scripts.txt, format 4), or decline it as a deprecated key that stays reported-unsupported
in `Unsupported`?** Until answered it is reported per collation, never silently dropped.
