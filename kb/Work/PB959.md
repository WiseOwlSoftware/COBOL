Filed 2026-09-22 by the ORCHESTRATOR from wave 44's group-D result, **after re-deriving the mechanism from the
script rather than accepting the report's account of it**.

## The mechanism, read from the code

`scripts/spec/record_verdicts.py:222-224`:

```python
before = {k: row.get(k, "") for k in ADJUDICATED}
for field in ADJUDICATED:
    row[field] = rec.get(field, "")
```

Every adjudicated field — **including `code-location` and `test-ref`** — is assigned by blind overwrite. Two
consequences follow, and the second is worse than the first:

1. A batch that lists FEWER witnesses than the row already carries **narrows** it. The batch author sees "I added
   my witness"; the row loses every witness the author did not happen to re-type.
2. `rec.get(field, "")` means a batch that OMITS the field entirely sets it to the **empty string**. Evidence is
   not merely narrowed, it is erased, by a record that never mentioned the field at all.

`changed` is incremented when any adjudicated field differs, so a narrowing and a widening are indistinguishable
in the script's own output. **There is no gate that can detect a batch that subtracts witnesses**, because the one
check in this area — `SpecTraceabilityInventoryDriftTests.EveryTestRef_ResolvesToARealTest` — deliberately checks
RESOLUTION, not COUNT: it fires when a surviving reference points at nothing, and is silent when a valid reference
is removed.

## Measured instances

Wave 44's group D found it inside its own change set, with both notes' prose claiming the batches "only ADD":

| row | after the batch | had been |
|---|---|---|
| `SR-14.9.39.3-17` | 2 test-refs, 1 code-location | 5 test-refs, 4 code-locations |
| `SR-14.9.13.3-3`  | 2 test-refs, 1 code-location | 5 test-refs, 7 code-locations |

It also left one reference (`negative/pb398-range-alphabet-numeric`) pointing at a case that does not exist —
caught only because the resolution drift test *would* have fired had that group's earlier gate completed. A sweep
of all 3,830 conformance references found that to be the only dangling one, so the resolution check is doing its
job; it is the SUBTRACTION that nothing watches. Both rows were repaired in-flight by a follow-up batch.

## Why this is MAJOR rather than cosmetic

The traceability inventory is the instrument that defines "done" for this project (§0: v1.0 = the inventory at
zero GAP). A row whose witnesses have been silently removed still reads CONFORMS and still counts as closed — it
simply no longer has the evidence that justified closing it. This is
[[feedback_verdict_evidence_invariant]] at the level of the tool that maintains the evidence: a missing
observation presented as a settled one. Every batch applied since this behaviour existed is suspect, and the
damage is invisible in every artifact derived from the inventory, including the owner's ledger.

## Fix shape (design, not yet implemented)

1. **Merge by default.** `code-location` and `test-ref` are SETS. Union the batch's values with the row's, and
   require an explicit `"replace-witnesses": true` (or a `--replace` flag) for the rare case of removing one.
   This makes the next batch safe without asking every author to remember.
2. **Make a narrowing loud.** Whatever the merge policy, when a write reduces the witness count, print
   `⚠ NARROWED <rule-id>: test-ref 5 → 2` and count it separately from `changed`. A silent subtraction is the
   whole defect; the diagnostic is worth more than the policy.
3. **Gate the count, not only the resolution.** A drift test that fails when a row's witness count decreases
   without an explicit replace marker — the sibling of `EveryTestRef_ResolvesToARealTest`, measuring the axis that
   check deliberately does not.
4. **Audit the damage.** The inventory is in git; walk its history for rows whose witness count fell, and re-verdict
   those rows. Until that runs, the size of the existing loss is unknown — and "unknown" is the honest word.

⛔ Do not implement 1 before 2. Measuring the narrowings that are already happening is what tells us how big the
audit in 4 has to be; a merge-by-default landed first would hide the evidence of its own necessity.

## Landed — wave 45 group G (2026-09-22)

In the order the note demanded: diagnostic, then policy, then the audit.

1. **The diagnostic first.** `inventory_schema.witness_losses` is now THE definition of a narrowing, asked by
   both the writer and a new gate, `scripts/spec/audit_witness_loss.py --check` (merge-base with main vs the
   working tree; wired into `build-local.{sh,ps1}` and `battery.sh` PHASE -1). Proved RED before the policy
   changed: the planted SR-14.9.39.3-17 batch applied through the OLD writer printed `rows changed: 1` and
   nothing else, and the check then reported `8 unexcused ... RED`. `--self-test` proves every arm.
   Point 3's "drift test" is this Python gate rather than a C# `[Fact]`: the count can only be judged against a
   BASE revision, which the C# gate has no notion of.
2. **Then the policy** (`record_verdicts.merged`). Witnesses UNION; a witness leaves only by a named
   `retire-witnesses` + `retire-reason`, marked `retired-witness: <ref> (<reason>)` in `notes`; any other loss is
   refused whole. The EVIDENCE rules (requires, anchor, derivation refusals) are asked of the row as it will be
   written, so a record naming one new test no longer has to re-type the rest. Two refinements the history
   forced, both beyond this note's sketch:
   · **A re-adjudication RE-SITES `code-location`.** 1,105 of the 1,714 historical removals were a verdict
     change replacing the DEFECT site a PARTIAL row names with the IMPLEMENTING site of the CONFORMS record that
     closed it; a blind union would present the defect site as implementation evidence. `test-ref` never re-sites.
   · **A witness-only record** (no verdict, no statement field) adds witnesses and restates nothing, so a batch
     re-applied on a merged tree cannot silently revert another train's re-adjudication of the same row.
   Statement fields (`verdict`, `editions`, `notes`, `derivation`) are still restated by a full record, so an
   omitted `notes` still blanks it — a statement, not evidence; the `requires` check guards the verdicts that
   need one.
3. **Then the audit.** `--history` walked all 270 inventory commits: 1,714 witness removals — 1,105 re-sites,
   256 code-locations and 353 test-refs lost silently. Replayed under the new rule (retirements and re-sites
   stay excused; a lost code-location is owed only while the row keeps the verdict it was lost under; a removal
   a SHAPE rule compelled — `docs/CONFORMANCE.md` bare or `#7`, a test-ref on a derivation-closed row — is not
   owed), 541 references on 306 rows were owed. 180 no longer resolve (tests and symbols renamed since) and
   cannot come back; the remaining **361 (228 test-ref, 133 code-location) on 207 rows** were restored by the
   witness-only batch `PB959-restore-owed-witnesses.json`. No row changed state (GAP 2276 → 2276).

The size of the pre-existing loss is therefore no longer "unknown": 361 restored, plus 180 that had already
rotted past restoring.
