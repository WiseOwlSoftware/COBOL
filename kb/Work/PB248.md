# PB248

**Rows:** `AR-15.90.3-1`, `AR-15.91.3-1`, `AR-15.100.3-1`, `AR-15.100.3-2`, `AR-15.100.3-4`

The 'i' integer-argument screen has no floating-point arm, so a COMP-2 item and an E-form literal slide into every integer argument position and are silently truncated.

ROWS: AR-15.90.3-1 (TEST-DATE-YYYYMMDD r1), AR-15.91.3-1 (TEST-DAY-YYYYDDD r1), AR-15.100.3-1 (YEAR-TO-YYYY r1), AR-15.100.3-2 (r2), AR-15.100.3-4 (r4). All five are §15.3 type 6 ('an arithmetic expression that will always result in an integer value or an integer data item').

MECHANISM, from the rows' own READ notes and re-measured at HEAD. `IntrinsicArgumentRules.Violation` opens `if (kind == 'i' && IntegerViolation(op) is { } notInteger) return notInteger;`. `IntegerViolation` has exactly four arms and a `_ => null` fail-open: a nested NUMERIC function (§8.4.3.2.3 SR11), a `BoundFieldOperand` whose `Pic is { Category: PicCategory.Numeric, Scale: > 0, Usage: not Usage.Index }`, a `BoundNumericLiteral` with `HasNonZeroFraction`, and PB124's `NotAlwaysIntegral` expression screen. `PicInfo.FloatItem(usage)` constructs `(PicCategory.Numeric, Length: 0, Digits: 0, Scale: 0, Signed: true)` — so a COMP-1/COMP-2/FLOAT-SHORT/FLOAT-LONG/FLOAT-EXTENDED/FLOAT-BINARY-*/FLOAT-DECIMAL-* item is admitted by `Admissible('i') = [CobolClass.Numeric]` AND misses the `Scale: > 0` arm. `PicInfo.IsFloat` (:379) exists and is consulted elsewhere (INITIALIZE's §14.9.20 category matching keys on `IsAlphabetic` the same way); it is not consulted here. SECOND PROVABLE SHAPE, from AR-15.90.3-1's refuter: `HasNonZeroFraction` opens `if (text.Contains('E') || text.Contains('e')) return false;` with the in-code justification 'an E-form literal is left to the runtime', so the LITERAL arm is disarmed for every floating-point literal, and the grammar admits one directly in the argument region (`CobolExpressions.g4:536 numericLiteralCore : FLOATLIT`; `CobolLexer.g4:807 FN_SIGNED_FLOATLIT` covers the sign-adjacent form inside a FUNCTION-argument region).

WHAT IT DOES. `01 F USAGE COMP-2 VALUE 20240229.9.` then `FUNCTION TEST-DATE-YYYYMMDD(F)` compiles clean, renders through `IntrinsicRenderer.cs:127 if (AnyRealArgument(ic) …) return RenderFloat(ic, RealMethod(...))` into `CobolIntrinsics.RealArgs.cs#TestDateYyyymmddReal`, whose `TryIntegerArg` TRUNCATES with `(long)Math.Truncate(v)`, and answers 0 — 'the date is valid' — on an argument that is not an integer. `FUNCTION TEST-DATE-YYYYMMDD(2.02402295E7)` does the same from a literal needing no PicInfo at all. `FUNCTION YEAR-TO-YYYY(85, F)` with F holding 23.6 windows as though 23 were written. EC-ARGUMENT-FUNCTION is never set, not even under `>>TURN EC-ARGUMENT-FUNCTION CHECKING ON`, which §15.3 rule 14 requires ('If the evaluation of an argument results in an incorrect value for that argument … the EC-ARGUMENT-FUNCTION exception condition is set to exist'). §15.3's latitude is over the RESULT when checking is off, not over whether the condition is set.

FAN-OUT. The whole 'i' kind is affected, not the five rows: CHAR, FACTORIAL, DATE-OF-INTEGER, INTEGER-OF-DAY, TEST-DATE-YYYYMMDD, TEST-DAY-YYYYDDD, YEAR-TO-YYYY and every other `Uniform('i', …)` / `Schema(… ['i','i','i'])` row. The shape is STATICALLY decidable from a datum the method already holds.

AR-15.100.3-4's OTHER half is NOT this note's and is NOT open: its refuter found r4 firing SPURIOUSLY on the float carrier for a reference that omits argument-3, because `RealArgs.cs` had one method filling `baseYear = 0`. At HEAD `CobolIntrinsics.RealArgs.cs:120` and `:124` are TWO overloads (`YearToYyyyReal(double yy, double off = 50)` calling the two-argument `CobolDate.YearToYyyy(y, o)`, and the three-argument twin) — the PB65 'omitted-ness is the ARITY, never a value' discipline propagated. That half is carried in the stale-verdict note, not here.

VERIFIED LIVE AT HEAD (read-only): IntegerViolation's four arms carry no `IsFloat` test; `HasNonZeroFraction:1199` still returns false for any 'E'/'e' text.

CLOSING EVIDENCE OWED: an `IsFloat` arm plus an E-form-literal arm in `IntegerViolation`, negative fixtures for BOTH shapes on at least two 'i' functions, and a drift test asserting every `Uniform('i')`/'i'-positioned row rejects a float item.

## Landed

Landed 2026-09-05. **THE GOVERNING TEXT IS §15.3 TYPE 6 ITSELF, NOT §5.5** — the note's own framing needed
correcting before the code could be. §5.5 2)b)2. says exactly the right thing ("a **fixed-point** numeric data
item … whose description does not include any digit positions to the right of the radix point", `--check` OK) and
it is tempting to lead with it, but §5.5 2) scopes itself to "a syntax rule" and §5.3.1 says "Except for intrinsic
functions, rules are categorized as syntax rules and general rules. Intrinsic functions have argument rules and
returned value rules **instead**" (`--check` OK). §15.15.3 r1 is an ARGUMENT rule, so §5.5 corroborates here and
does not govern. The argument that does govern is PB40's, applied to the arm PB40's primitive could not see: type
6 admits "an arithmetic expression that will always result in an integer value **or** an integer data item", and a
floating-point item is neither — §14.6.8.3 sets its content to "the algebraic value of the sending operand"
(`--check` OK), so its DECLARED value set contains non-integers and no reference to it is provably integral. ⚠ The
asymmetry is real and is recorded in the fixtures: for `PERFORM … TIMES` §14.9.28.3 is a SYNTAX RULES subclause,
so there §5.5 2) governs directly.

**ONE PRIMITIVE, FOUR SITES.** `PicInfo.IsIntegerDescription` is now the only place the question is answered, and
`IntrinsicArgumentRules.NonIntegralItemReason` adds only the prose. Its readers:

1. `IntegerViolation`'s bare-item arm (the shape the note named).
2. `HasNonIntegralValue` — the LITERAL arm, rebuilt on `NumericLiteral.TryParseExact` (already documented as "the
   ONE exact parser the binder's range checks, the standard-decimal literal operand and the VALUE initializer
   share") so the test is on the literal's VALUE for the fixed-point AND floating forms alike. `1.0E2` = 100 stays
   admitted; `2.02402299E7` = 20240229.9 is rejected. `LiteralIntegerMagnitude` was rebuilt on the same parser,
   which also un-disarmed the quotient screen for an E-form divisor.
3. **A THIRD SITE THE NOTE DID NOT NAME** — the always-integral EXPRESSION walk. `CollectAdditive` and its
   opaque-marking twin recognized a scale>0 item and nothing else, so `FUNCTION CHAR(F + 1)` slid through exactly
   as `FUNCTION CHAR(F)` did. Both halves had to be widened together: widening only the leaf arm would fire
   SPURIOUSLY on `F - (F * 1)`, which nets to zero only because the other walk marks `F` opaque. The float witness
   also needs no granularity test — a float profile carries Scale 0, so `|coeff| % 10^0` is zero for every
   coefficient and the fixed-point test would have disarmed the arm entirely.
4. **A SIBLING OUTSIDE THE INTRINSIC SCREEN**, found by the rule-4 sweep: `IntrinsicResultType.IsIntegerOperand`,
   documented as "the ONE 'is this operand an integer' classifier … and so does every statement rule that says
   'shall be an integer'", carried the same scale-only arm. `PERFORM … F TIMES` over a COMP-2 holding 3.7
   compiled clean and iterated three times (§14.9.28.3 SR2), and every all-integer-arguments row selected the
   INTEGER result type for a floating-point argument (§15.2 type 5). Its LITERAL arm was re-derived and left
   ALONE: §8.3.3.3.2's closing sentence is "An integer literal is a fixed-point numeric literal that contains no
   decimal point", and §8.3.3.3.3 r2 requires a floating literal's significand to "include a decimal point", so
   the existing `!Contains('.')` test is the standard's own definition and already excludes the whole floating
   form.

**TWO LANDED GOLDENS PINNED THE DEFECT AND WERE RE-DERIVED** (`green_test_can_hold_a_gap_open`).
`2023/pb21_float_arg_integer_family` derived its legality as "a COMP-2 item is … class numeric, and §15.3's
INTEGER type resolves through CLASS numeric — the integer-ness is a VALUE property, not a class the argument
screen can reject on". That premise contradicts the landed PB40 reading of the same clause, which rejects a
`PIC 9V9` operand at an integer position for the reason that would admit a COMP-2 one; the two could not both be
right, exactly as the 'i'/'n' numeric-edited pair could not on 2026-08-02. Its real subject was a CRASH (a raw
Roslyn CS0117 from a missing runtime member) and PB2's was the sibling CS1503 — **both paths are still reached
under `--permissive`**, so both still need a guard. They moved to
`conformance-test:FloatIntegerArgumentPermissiveTests`, which asserts the strict rejection, the permissive
warning, and the invariant they really carried: the float lane's values equal the fixed-point lane's. `pb2`'s MOD
pair took integer operands in the corpus (§15.64.3 r1 is "shall be integers"); its REM pair stayed floating,
because §15.77.3 r1 is "shall be of class numeric" and that reading of the header is correct.

**⛔ OWNER-VISIBLE:** this REVERSES the disposition two landed goldens recorded. Nothing legal was newly rejected
that the surveyed reading admits — `--permissive` still accepts every one of those programs with a warning — but
the strict verdict for a floating-point operand at an integer argument position changed from ACCEPT to REJECT.

Rows re-verdicted PARTIAL → CONFORMS: `AR-15.90.3-1`, `AR-15.91.3-1`, `AR-15.100.3-1`, `AR-15.100.3-2`,
`AR-15.100.3-4` (GAP 2906 → 2901). `AR-15.100.3-1` also owed its r1 REJECT edge, which had a disposition and no
evidence; `conformance:2002/pb248_year_to_yyyy_arg1_domain` pins both arms under `>>TURN EC-ARGUMENT-FUNCTION
CHECKING ON` with the accepted values derived from §15.100.4. `AR-15.100.3-4`'s spurious-reject half was
re-measured at HEAD and was already repaired by PB65's two-overload split — a stale verdict, not a live defect.

No new diagnostic code: a floating-point operand at an integer position is the SAME rule as a scaled one, so it
takes the same COBOLNET1627 (and the PERFORM sibling its existing COBOLNET1646). The drift test
`IntrinsicArgumentClassDriftTests.EveryIntegerArgumentPosition_RejectsAFloatingPointItem` walks the `Verified`
schema table rather than a list of functions, so a new `Uniform('i', …)` row and a new float `Usage` member are
both swept automatically; it was run against the pre-fix predicate and FAILED on all ten float usages before
passing on the fix, and its companion fact pins the ADMITTED half so the arm cannot be widened into a rejecter of
legal source.
