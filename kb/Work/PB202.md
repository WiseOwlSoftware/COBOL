# PB202

Found 2026-08-31 during the cluster-A burn-down, while deriving the GR8 sending rule for [[PB178]]'s new
`PlaceRenderer.SendingGroupImage`. PRE-EXISTING; the PB178 landing did not touch this arm.

## The rule, read in full

`cite.py --check 13.18.38.4` on both halves:

- **GR8a** — "If the data item referenced by data-name-1 is outside the group, only that part of the table
  area that is specified by the value of the data item referenced by data-name-1 at the start of the
  operation will be used."
- **GR8b** — "If the data item referenced by data-name-1 is included in the same group **and the group data
  item is referenced as a sending operand**, only that part of the table area that is specified by the value
  of the data item referenced by data-name-1 at the start of the operation will be used in the operation.
  **If the group is a receiving operand, the maximum length of the group will be used.**"

⇒ On the SENDING side the two arms AGREE: current extent, inside or outside. The inside/outside split exists
only on the RECEIVING side, which `PlaceRenderer.WriteGroupImage` already gets right
(`OdoGroupPlace { DependingInside: false } => ReceiveInto(...)`, else the maximum).

## The defect

`PlaceRenderer.Read(GroupImagePlace g)` gates the sending slice on `g.Inner is OdoGroupPlace
{ DependingInside: false }`, so a depending-INSIDE group falls to `GroupImage(g.Inner)` — the MAXIMUM image.

**MEASURED** (an 8-character extent, `01 G. 05 NN PIC 9 VALUE 2. 05 GT OCCURS 1 TO 5 DEPENDING ON NN PIC
X(3).` with GT(1..3) = ccc/ddd/eee, so the GR8 extent is 1 + 2x3 = 7):

| reference | depending INSIDE | depending OUTSIDE (control) |
|---|---|---|
| `MOVE G TO OUT` | `2cccddd` — correct | `cccddd` — correct |
| `G(1:10)` | `2cccdddeee` — **reads 3 characters of the unused table area** | `cccddd    ` — stops at the extent |

The plain MOVE path is right in both columns because `OperandText.FieldAsString` takes `SendingImage(odo)`
with NO `DependingInside` test — so the tree already contains BOTH spellings of this rule, and only the
ref-mod read carries the wrong one. The two-arm shape again, between two files.

## Before fixing, derive the missing premise

The read site's own comment argues that a position past the count is EC-BOUND-REF-MOD "not a read of the
unused area", which presumes a reference-modification of the group counts as the group being "referenced as a
sending operand" in GR8b's sense. That premise is UNDERIVED and it is the whole question — §8.4.3.3's
reference-modification rules, not §13.18.38, decide what the ref-mod base is. Derive that FIRST and cite it;
if it holds, the fix is to drop the `DependingInside: false` conjunct from the READ arm only (leaving
`WriteGroupImage`'s split alone, where GR8b's second sentence puts it), and the golden is the table above.

## Scope note

Deliberately NOT fixed with cluster A. It is adjacent to `SendingGroupImage` (which is why it was found) but
it is a distinct rule on a distinct path, and it needs the ref-mod-as-sending-operand derivation above — an
improvised scope decision is exactly what the burn-down contract forbids.
