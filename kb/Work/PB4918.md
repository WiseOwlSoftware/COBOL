# PB4918 - a review stall is counted from the report, not from the agent's return

**What happened.** On 2026-11-07, wave 20261905 posted `STALL w20261905d (PB4838): 15 min on its branch review` at 11:26
and `STALL w20261905g (PB4744): 18 min on its branch review` at 11:46. Neither branch was in review. In each case the
report already said `DONE`, but the implementer was still running, waiting on a gate it had launched at its tip after a
last DEVLOG-only commit (impl-D: report written at 11:09, last tool call 6 minutes before the check). The rolling wave starts a
branch's review only when its implementer returns, so no reviewer existed yet. The operator checked each mail by hand from the
wave's agent states before closing it.

**Cause.** `scripts/orchestrator/progress.py` (`progress`) classifies a group whose newest report is `DONE` with no review
stamp as `unreviewed`, and starts its clock at `r.path.stat().st_mtime`, the time the report file was last written. The
implementer brief has the agent write its report and then gate the tip it reports (the gate line is filled in once the verdict
arrives), so the mtime can be the moment the report was first written, minutes before the agent returns. The
15-minute `REVIEW_STALL_MIN` then runs out during the implementer's own gate.

**Harm.** A false STALL mail per affected group. Each one costs the operator a check, and a real stuck review gets harder to
tell from a false one. It also skews lever 5 of PB4888, the "round-1 FINDINGS rate" and review timings in the PROGRESS line.

**Fix.** Start the review clock when the review could have started: when the implementer returned, which the wave records (the
agent's end in the wave's state, or the review lane's own start record), not at the report's mtime. Until the implementer
returns, count the group as `running`, under `RUNNING_STALL_MIN`. Add a self-test case: a DONE report whose agent is still
running is not a review stall.

**Sites:** `scripts/orchestrator/progress.py` (`progress`, `REVIEW_STALL_MIN`).
