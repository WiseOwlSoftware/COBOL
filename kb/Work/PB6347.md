# PB6347 — a hook that blocks the turn end near its timeout, and a session start that takes 12 s and fills 11 KB of context

**Sites:** `.claude/settings.json` (the `hooks` block), `scripts/hooks/unpushed.py` (whole: the 41-line Stop hook), `scripts/hooks/inbox_guard.py` (`live_status`, `decide`), `scripts/orchestrator/mailbox.py` (`status`), `scripts/orchestrator/coord.py` (`process_table`), `scripts/hooks/session_start.py` (`main`, `probe`, `tooling`), `scripts/session_probe.py` (`work_check`, `branches`), `scripts/hooks/tooling_check.py` (`check`)

**What the transcripts show** (a scan of the 50 newest sessions, 2026-11-24 to 2026-11-27):

| hook event | recorded runs | result |
|---|---|---|
| Stop | 2 | both `hook_cancelled`, `timedOut`, about 37.3 s each |
| SessionStart:startup | 31 | median 11.9 s, maximum 40.0 s |
| SessionStart:compact | 2 | median 19.5 s |

The SessionStart `additionalContext` is about 11.2 KB, about 2.8k estimated tokens resident in every session from its first turn.

**The hooks** (`.claude/settings.json`):

- `Stop` (line 99) has two commands, each with `timeout: 30`: `python "$CLAUDE_PROJECT_DIR/scripts/hooks/unpushed.py"` (line 104) and `python "$CLAUDE_PROJECT_DIR/scripts/hooks/inbox_guard.py"` (line 109).
- `SessionStart` (line 30, matcher `startup|resume|clear|compact`) has one command, `python "$CLAUDE_PROJECT_DIR/scripts/hooks/session_start.py"` (line 36), `timeout: 300`.

**Which Stop hook times out.** The transcript attachments of the two timeouts do not name the command, and both scripts ran in under 0.3 s on the tree at 19:20 on 2026-11-27 (`inbox_guard.py` 0.26 s, `unpushed.py` 0.11 s), so the timeouts are load-dependent and the scripts alone do not settle it. Each has an unbounded read that a busy machine (a gate running, hundreds of processes) can stretch:

- `scripts/hooks/inbox_guard.py:35-50` (`live_status`) calls `mailbox.status` (`mailbox.py:349`, `table = coord.process_table()`), and `coord.process_table` (`coord.py:479-485`) reads the kernel snapshot and then each process's command line (`_nt_command_line`, `coord.py:450`): 528 processes on this machine, 0.09 s idle, one OS call per process with no bound of its own. It is the likelier of the two; it also reads the whole mailbox listing (`mailbox.py:336-348`) and `mailbox.stale` (`inbox_guard.py:47`) on every turn end.
- `scripts/hooks/unpushed.py:24-27` runs `git log --oneline @{u}..HEAD` with `timeout=30`, the same 30 s as the hook's own timeout in `settings.json`, so a stalled git (the 55k-file checkout under a running build) consumes the whole hook budget and the harness cancels the hook first.

Neither bounds itself below the hook timeout, and a Stop hook that is cancelled at the timeout makes the turn end wait the full 30 s or more for nothing.

**Where the SessionStart time goes** (timed section by section on 2026-11-27, `scripts/session_probe.py` `SECTIONS`, :364): the probe's sections already run concurrently (`session_start.py:228-240`, PB5939), so the hook takes as long as the slowest read. Two sections hold nearly all of it: `branches` (`session_probe.py:237`, runs `scripts/prune_worktrees.py --brief`) 11.6 s and `work_check` (`session_probe.py:202`, runs `scripts/spec/work.py check` over 5382 notes) 10.3 s; the next, `inventory`, is 2.6 s, and the other sixteen total about 11 s (run concurrently, so they hide behind the two). A whole run was 13.2 s here, 13.7 s for the probe alone. `branches` is also the largest block of the output (2970 of the probe's 5408 characters).

**Where the 11 KB goes** (one run, 8.4k characters on this tree, 11.2 KB in the transcripts where the permission-mode line is longer): the skills block (`session_start.py:176`, `WORK_SKILLS` and the lane text) about 1 KB; the probe about 5.5 KB; the tooling check (`tooling_check.py:200`) about 2 KB,. Everything in the skills block, the lane text and the tooling OK lines is a fact the session can read from CLAUDE.md, the skill list or the command that prints it.

**Fix direction.**

1. No hook blocks the turn end near its timeout. Each Stop hook bounds its own work well below the hook's timeout (a few seconds), and on exceeding it ends silently with a one-line warning, as `inbox_guard.decide` already does for a failure of the hook itself. `unpushed.py` takes a `timeout` of a few seconds, not the hook's 30. `inbox_guard.py` reads the process table once per session start into a cache (the watcher's pid is stable for the session) and re-checks only that the pid is alive, instead of snapshotting every process at every turn end.
2. The SessionStart output is trimmed to what the session cannot compute itself: the lines that need action (a red nightly, an undecided branch, an open message, a malformed register, an ASK-OWNER tooling line) and one line saying everything else is fine. The skills block, the OK lines and the standing advice go. The session runs `python scripts/session_probe.py` for the rest when it wants it.
3. The slow parts are cached or made asynchronous. `branches` and `work_check` read inputs that change only on a commit or a branch event: cache each result keyed by the tree's HEAD and the register's last modification (the way the gate keys its targets) and reuse it; or run them in the background after the hook returns and let the first turn read the result from a file. A `compact` start re-reads what the session already holds, so it needs the shortest of the three outputs.

The hooks themselves are not changed in this note's filing.
