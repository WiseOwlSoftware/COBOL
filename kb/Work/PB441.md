# PB441 — the checking-off window is realized twice for imp-2..4 and only once for imp-5

## 1. THE MECHANISM

GR14 puts an implicit PUSH ALL + TURN OFF ALL at the end of imperative-statement-1 and the implicit POP ALL
immediately before the END-PERFORM phrase; GR16 puts imperative-statement-5 (FINALLY) BEFORE that phrase. So
imp-5 executes **inside** the TURN OFF ALL window, exactly as imp-2/3/4 do.

The compiler realizes that window in two places, and imp-5 gets only one of them. Its emitted shape is
`ControlFlowEmitter.EmitExceptionPerform:111-122`:

    __f3fin{n}: ;   // implicit CONTINUE preceding FINALLY
    var __ckfin{n} = ExceptionState.PushAllCheckingOff();   // GR14 implicit PUSH ALL + TURN OFF ALL
    try { <imp-5 emitted INLINE> }
    finally { ExceptionState.PopAllChecking(__ckfin{n}); }   // GR14 implicit POP ALL

`ExceptionState.PushAllCheckingOff()` (`src/Cobol.Net.Runtime/Exceptions/ExceptionState.cs:219-224`) sets
`_checking = default` — a RUN-TIME flag record. But the EC-SIZE guard is not read from that record at run time;
it is **compiled in at emit time**. `ArithmeticEmitter.EmitArith:291-292` decides the emitted shape from
`EcEmitter.EnabledSizeNames()` (`EcEmitter.cs:275-277`), which reads `ecState.Info.Enabled` — the region
`EcBinder.EcWrap` computed for the F3 PERFORM statement at the PERFORM's OWN line, i.e. BEFORE the GR14 floor —
and the EC-SIZE family is put into that region for EVERY statement by the ambient rule at
`EcBinder.cs:414-422` ("⛔ THE EC-SIZE FAMILY IS AMBIENT FOR EVERY OTHER STATEMENT TOO").

**Two-arm dispatch, and this is the arm nobody looked at.** The WHEN / OTHER / COMMON bodies are emitted as
SEPARATE synthetic pc-range cases and therefore escape the enclosing checked region entirely; imp-5 is emitted
INLINE inside the F3 PERFORM statement's own `EcWrap` region and inherits its guard. The generated C# shows both
arms of one program side by side — see §3.

the consequence explicit: with checking off, only the OPERATION's results are undefined; the run unit is not
terminated. The required outcome for the repro below is therefore that the ADD stores an undefined value and
execution continues.

## 3. EXPECTED vs OBSERVED — RE-RUN ON HEAD (89044aa0)

Still diverges. HEAD `cobol.exe`, `--std 2023`.

          >>TURN EC-SIZE-TRUNCATION CHECKING ON
           01 N PIC 9 VALUE 5.
           MAIN-PARA.
               PERFORM
                   DISPLAY "IMP1"
               WHEN EC-USER-DEMO
                   DISPLAY "WHEN"
               FINALLY
                   ADD 9 TO N
                   DISPLAY "FIN " N
               END-PERFORM
               DISPLAY "DONE"
               STOP RUN.

    $ cobol.exe .../gr14_ambient_off_in_finally.cob --std 2023 --run
    exit 1
    IMP1
    abnormal run-unit termination: EC-SIZE-TRUNCATION (fatal): size error and not resumed
    (ISO 14.7.5; 14.6.13.1.3 #5/#7)

**Required:** the ADD is inside the GR14 TURN OFF ALL window, so no exception condition is raised — "FIN 4" and
"DONE" print and the run unit ends normally.

**THE OTHER ARM, same program shape, one region over — measured on HEAD as the contrast:**

           PERFORM
               RAISE EXCEPTION EC-USER-DEMO
               DISPLAY "IMP1-AFTER"
           WHEN EC-USER-DEMO
               DISPLAY "WHEN"
               ADD 9 TO N
               DISPLAY "AFTER-ADD " N
           END-PERFORM

    $ cobol.exe .../gr14_ambient_off_in_handler.cob --std 2023 --run
    exit 0
    WHEN
    AFTER-ADD 4
    IMP1-AFTER
    DONE

The handler's ADD truncated to 4 and execution continued — which is what GR14 requires, and what imp-5 does not
get.

**The generated C# names the cause exactly.** In the FINALLY program's `.g.cs`, imp-5 carries the full
compiled-in guard inside the very region the runtime push was supposed to disable:

    :96   var __ckfin0 = ExceptionState.PushAllCheckingOff();   // GR14 implicit PUSH ALL + TURN OFF ALL
    :99   bool __sizeErr0 = false;
    :105  if (!CobolNum.TryStore(CobolNum.AddChecked(N, 9L), 0, _P_0, CobolRounding.Truncation, out var __sv0))
              { __sizeErr0 = true; __sizeEc2 = "EC-SIZE-TRUNCATION"; }
    :108  catch (CobolSizeError __cse3) { __sizeErr0 = true; __sizeEc2 = __cse3.EcName; }
    :113  if (__sizeErr0 && (__sizeEc2 == "EC-SIZE-TRUNCATION"))  …
    :122  finally { ExceptionState.PopAllChecking(__ckfin0); }   // GR14 implicit POP ALL

while the handler program's `.g.cs` for the identical ADD is:

    :146  N = (long)(CobolNum.Store(((Int128)(N) + (9L)), 0, _P_0, CobolRounding.Truncation));

A bare store, no guard. The runtime `PushAllCheckingOff()` at `:96` cannot gate a guard that was baked into the
emitted code.

Format 3 is 2023-only (Annex E.3.3 item 36), so there is no edition axis. I re-ran both programs on HEAD and read
both generated files; the other five sentences of GR14 I did not re-measure — the adjudicator located and checked
all six, and the four that conform (the `!Enabled(ec, file, imp1Line)` precondition on the implicit TURN, LOCATION
riding the synthetic event, WHEN OTHER seeing only enabled conditions, and a `>>TURN OFF` inside imp-1 winning)
are unaffected by this defect's site.

⚠ **A GREEN golden holds the gap open.** `conformance:2023/f3_perform_handler_turn_off_all` picks the
EC-BOUND-REF-MOD family, which uses a per-reference runtime gate and therefore does NOT leak — so the suite is
green over the arm that works. `docs/CONFORMANCE.md` records two OTHER §14.9.28.4 determinations and nothing for
this, and a grep of `kb/Work` for imp-5 / FINALLY found only PB3, an unrelated landed ORD defect.

## 4. THE CODE SITE AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Compiler/CodeGen/Verbs/ControlFlowEmitter.cs:111-122` — imp-5 emitted INLINE, wrapped only by
  the runtime push/pop
* `src/Cobol.Net.Compiler/CodeGen/EcEmitter.cs:539-549` — `EmitRunF3`, which does the same push/pop around
  imp-2/imp-4 (and works, because those bodies are separate pc cases)
* `src/Cobol.Net.Compiler/CodeGen/EcEmitter.cs:275-277` — `EnabledSizeNames()`, reading `ecState.Info.Enabled`
* `src/Cobol.Net.Compiler/CodeGen/Verbs/ArithmeticEmitter.cs:291-292` — the compile-time decision
  `if (sizeErr is null && ecSize.Count == 0) { emitStores(false); return; }`
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.cs:414-422` — the ambient EC-SIZE family rule
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.cs:315` — `EcWrap`, which fixes the region at the
  PERFORM statement's own line
* `src/Cobol.Net.Compiler/Binding/TurnState.cs#WithAllDisabledFrom` — the BIND-time floor, spliced at the FIRST
  HANDLER's line

⛔ **The repair is not "also push at run time" — it already does that, and it does not help.** The defect is that
GR14's window is realized by TWO different mechanisms and imp-5 is inside only one of them:

* the **bind-time** floor (`WithAllDisabledFrom`) splices an EC-ALL OFF at the first handler's line, which is
  what makes a compiled-in guard disappear for imp-2/3/4;
* the **run-time** push (`PushAllCheckingOff`) covers whatever the emitted code still consults dynamically.

Following rule 5 and "one mechanism per job": **imp-5's statements must be bound under the same GR14 floor as
imp-2/3/4**. Today the floor is keyed at the FIRST HANDLER's line, and the FINALLY body's lines are inside that
range — so the floor is failing to reach imp-5 for a specific reason a fixer must find and state (the likeliest
is that `EcWrap` fixes the F3 PERFORM statement's own region from the statement's line, before the floor exists,
and imp-5 is emitted inside THAT region rather than under its own). The right shape is that the region a
statement is emitted under is the region computed at THAT statement's line — not the enclosing statement's —
which also makes the next ambient family automatic instead of needing its own carve-out.

⚠ A fix that special-cases EC-SIZE inside `EmitExceptionPerform` closes this measurement and leaves every other
COMPILED-IN ambient gate open. Ask which families are decided at emit time from `ecState.Info` and which are
gated at run time; only the second kind is covered by the push today.

## 5. THE SIBLING SWEEP

* ⛔ **Every ambient EC family whose guard is decided at EMIT time.** EC-SIZE is one; `EcEmitter` also carries
  the EC-ARGUMENT-FUNCTION ambient statement gate and the EC-RANGE-PERFORM-VARYING bind-time capture
  (`ControlFlowBinder.cs:382`, see **PB439**). For each, ask: does the GR14 window switch it off inside imp-5?
  Each "no" is this same defect.
* **Every other place imp-5 is treated as inline rather than as a handler region.** `dispatch.SetF3Region(
  F3Region.Finally, n)` at `ControlFlowEmitter.cs:113` says the emitter KNOWS imp-5 is a distinct region;
  compare what `EmitRunF3` does for imp-2/3/4 with what the inline path does, item by item.
* **GR21** ("the results are as if these statements were specified in a format 2 PERFORM statement") governs
  imp-2..5 alike and is the rule the frame POP before FINALLY implements — check whether imp-5's other
  handler-region properties survive the inline emission too.
* ⛔ **Re-audit the covering golden.** `conformance:2023/f3_perform_handler_turn_off_all` chose the one EC family
  that cannot show the defect. The fix must add a golden using an EMIT-TIME-gated family (EC-SIZE-TRUNCATION is
  the measured one) in BOTH imp-2 and imp-5, so the two arms are pinned side by side and neither can drift.
