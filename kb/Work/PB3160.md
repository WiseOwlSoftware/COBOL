# PB3160 — one complete conformance suite per edition, modernized

> flags: process-only · owner direction · design first (CLAUDE.md rule 2)

## Source

The owner, 2026-10-14 ~14:50 PDT (operator session 7e5a828b), verbatim: "Separately, I think we should evolve all
test cases to separate suites for each COBOL specification version, more or less positioning them as conformance
tests equivalent to the NIST tests. However, we need not use the NIST structure as that is a 40+ year old designs. We
can modernize"

Context: the same day a commercial inquiry asked to license the test and sample programs as compiler test cases or
AI training data (kb/Work PB3159 holds the licensing side).

## What exists today (measured 2026-10-14 at main c29af1704)

- `tests/conformance/{85,2002,2014,2023}/` hold 2,371 positive goldens (418 · 856 · 246 · 851) and
  `tests/conformance/negative/` holds 2,677 negative fixtures (the ledger's corpus row at c29af170).
- A positive golden is filed under ONE edition directory and compiled at that edition only:
  `ConformanceCorpus.PositiveOptions` passes `DialectLevel: int.Parse(edition)`
  (`tests/Cobol.Net.Tests.Conformance/CorpusRunnerTests.cs`). So the 2014 directory holds the 2014 additions, not a
  2014 suite: nothing runs an 85-filed golden at 2014 and compares its output.
- ⚠ `docs/VERSION_TEST_MATRIX_DESIGN.md` §5 says "Each program compiles/runs at ≥ its edition". The runner does not
  do that for the positive corpus. The design work below either implements it or corrects the doc (rule 6).
- NIST CCVS85 (364 programs, `tests/nist/`) covers COBOL-85 only. `VersionMatrixTests`
  `Cobol85Program_StillCompilesAtLaterEdition` crosses the green NIST set with 2002/2014/2023, but CHECK-ONLY (parse,
  edition validation, bind; no run, no output match).
- Negative fixtures already name every edition that must reject them (`*> reject-at:` header).
- The traceability inventory (`tests/version-matrix/traceability-inventory.json`, 4,347 rows) ties rules to witnesses.

## The direction

Four complete suites, one per edition, each covering every rule of that edition (inherited ones included), and
positioned as conformance suites in the NIST CCVS's role, with a modern structure instead of CCVS's (large
multi-test programs, X-card substitution, printed report pages).

## Next (the operator, attended)

A design for the owner's review before any test moves, extending the canonical test-matrix design
(`docs/VERSION_TEST_MATRIX_DESIGN.md`; one canonical doc per subsystem, `docs/DOC_INDEX.md`). The operator's starting
sketch, for the owner to accept or change: one case per rule citing its ISO clause and inventory rows; one source tree
whose per-case metadata states the editions that must accept (with expected output) and reject (with the expected
diagnostic class); the four suites GENERATED from it; machine-readable results (JUnit XML or JSON); and a runner that
drives any compiler (GnuCOBOL, IBM, Rocket), not only WiseOwl COBOL.

## Owner answers (the design's brief)

1. **Who runs the suites: ANY COBOL compiler** (owner, 2026-10-14, answering "Who should be able to run the
   per-edition conformance suites?" with "Any COBOL compiler (Recommended)", whose stated meaning was: like NIST's
   suite, each test's expected result is an output or a kind of rejection, never a WiseOwl error code; small adapters
   run it against WiseOwl COBOL, GnuCOBOL and in principle IBM or Rocket; it can be licensed on its own). So a negative
   case's expectation is a rejection CLASS, and WiseOwl's own diagnostic codes live outside the suite's cases.
2. **How: "A: one tree, generated"** — one compiler-neutral test per rule, filed by ISO clause, generated into four
   complete per-edition suites, run by a harness with per-compiler adapters.
3. **The case format, the tree and its location (this repository, a folder with its own LICENSE), the Python harness
   and its verdicts, and the migration**: "Looks right", each, as presented.
4. **Priority: "Pilot now, rest after GAP"** — the mechanical move and one pilot clause now; the clause-by-clause
   completion waits for zero GAP and zero known defects (the work held under kb/Work PB2911).
5. **Review: "Also have Mythos review the design"** — the owner's approval for that Mythos dispatch.

6. **The written design: "approved"** (owner, 2026-10-14, revision 2, after Mythos's review was folded in).
7. **No gate spent on a known failure** (owner, 2026-10-14 ~21:25, on the first form of S2's guard, which let a branch crossing the move fail its gate and sent a finisher): "I don't understand why we know that a branch will fail its gate, then run it anyway so the gate subsequently gets fixed. That is a waste of tokens and cycles". The move now lands at a quiet point (the loop's drain, then the converter re-run on the merged tree), and the guard for a branch outside the loop is a generator refusal run as a gate audit, red in seconds before the build (design §9, §13 S1a and S2).

The design: `docs/rearchitecture/DESIGN-conformance-suite.md` (APPROVED). Its implementation is the PB3160 campaign,
one note per slice of the design's §13, ordered by `blocked_by` (`python scripts/spec/work.py next --cluster PB3160`):
PB3172 (S0a) through PB3179 (S4). This note stays open until the pilot (PB3178) has measured the cost and the
remaining clauses are filed as held campaign notes.
