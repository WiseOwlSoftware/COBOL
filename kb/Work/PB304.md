# PB304 — one arm of a three-arm dispatch names the wrong function's rule

## The rules, both real and both distinct

* `cite.py --check 15.77.3 "The value of argument-2 shall not be zero."` → **OK §15.77.3 2)** (REM, argument rules)
* `cite.py --check 15.64.3 "The value of argument-2 shall not be zero."` → **OK §15.64.3 2)** (MOD, argument rules)

Identically worded, different rules of different functions. That is precisely why the raise site has to name its
own one — a real clause answering a different question is the shape
`feedback_a_real_clause_can_answer_a_different_question` names.

## Observed

`src/Cobol.Net.Runtime/Intrinsics/CobolIntrinsics.Dec.cs:71`, inside **`RemDec`**:

```csharp
if (b.Sig == 0) return CobolDec.From(ModZeroDivisor(), 0);
```

`ModZeroDivisor()` raises `ArgumentError("MOD with a zero divisor (ISO §15.64.3 rule 2)")`
(`CobolIntrinsics.Exact.cs:102-103`); the detail string is carried into `CobolFatalException`
(`ExceptionState.cs:248-254`) and surfaced. It must call `RemZeroDivisor()` — `Exact.cs:107-108`, which produces
`"REM with a zero divisor (ISO §15.77.3 rule 2)"`, the string the exact and binary64 carriers already produce.
`Dec.cs:58` (`ModDec`) is correct: this is the one-arm-of-a-multi-arm-dispatch shape on the copy-paste axis
(`feedback_two_arm_dispatch`).

## Repro

Any REM whose zero-divisor check fires **on the SDIDI carrier**, i.e. with an arithmetic-expression argument
(ISO §15.3 argument type 6), which `IntrinsicRenderer.cs:682` routes to `RemDec`:

```cobol
       OPTIONS.
           ARITHMETIC IS STANDARD-DECIMAL.
       …
       01 AM PIC S9(9) VALUE -12.
       01 Z  PIC S9(9) VALUE 0.
       >>TURN EC-ARGUMENT-FUNCTION CHECKING ON
           COMPUTE R = FUNCTION REM(AM + 1, Z).
```

Same shape as the working golden `conformance:2023/pb32_dec_carrier_intrinsic_argument`, which reaches `ModDec`
with a non-zero divisor.

## Why nothing can see it

* `IntrinsicCarrierAgreementDriftTests.ZeroDivisor_RaisesFromBothCarriers` parametrises only `ModScaled`/`ModReal`
  and `RemScaled`/`RemReal`. Its assertion `Assert.Contains(fn == "MOD" ? "15.64.3" : "15.77.3", exact.Message)`
  is **exactly** the check that would catch this — and the Dec carrier is outside its reach. The test's own name
  says "BothCarriers" while three bodies exist.
* `NoRealBody_AnswersADomainGuardWithALiteral` reads only `CobolIntrinsics.RealArgs.cs`.
* The new golden cannot see it either: `EC-ARGUMENT-FUNCTION` is raised correctly and the detail string is not
  observable through standard COBOL, so `conformance:2023/l1_mod_rem_zero_divisor` prints `CAUGHT` either way.

## The fix, and the shape that makes the next case automatic

1. `Dec.cs:71` → `return CobolDec.From(RemZeroDivisor(), 0);`
2. Widen `IntrinsicCarrierAgreementDriftTests` to enumerate `CobolIntrinsics.Dec.cs` as a **third** carrier, and
   turn its per-function clause assertion into a rule over all carriers: *each raise site names its OWN clause*.
   Then the next carrier added cannot repeat this. A hand-added third parametrisation would not.
