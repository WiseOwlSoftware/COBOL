# PB398 — EVALUATE's selection-object figure lost two alternatives in transcription to grammar

## 1. The mechanism

`evaluateWhenItem` (`src/Cobol.Net.Frontend/Grammar/Core/CobolControlFlow.g4:196-201`) is exactly four
alternatives — `valueRange | valueOperand | condition | ANY` — and the printed general format of 14.9.13.2
stacks **ten** alternatives inside one select-exactly-one brace. Two of them were dropped on the way into the
grammar, and neither drop is a missing convenience: each one makes a whole family of rules unreachable.

**(a) partial-expression-1 has no alternative at all.** None of the four can begin with a bare relational
operator, a class condition with its identifier removed, or a sign condition with its identifier removed —
which is precisely the shape 14.9.13.3 SR5 *defines* a partial-expression to be. `EVALUATE WS-N WHEN > 5` is
not an exotic dialect extension; it is the first shape SR5's own list names and the ordinary way to write a
threshold arm, and it dies in the parser. Five rules fall on this one absence — SR5 (the definition), SR8 (the
rewrite), 14.9.13.4 GR4 a) 2. (the execution semantics), SR7 d) (the correspondence restriction plus the
"would a conditional expression result" well-formedness test) and SR6 e) (the subject reclassification that
applies only when the object *is* a partial expression). It also leaves one of Table 15's nine rows
permanently unreachable: `EvaluateOperandCombinations` carries a `PartialExpression` row
(`src/Cobol.Net.Compiler/Binding/EvaluateOperandCombinations.cs:26`) that no operand can ever classify into —
a dead lookup, and therefore an unverified one.

**(b) range-expression's trailing `[ IN alphabet-name-1 ]` phrase is absent.** `valueRange` is transcribed as
`valueOperand (THRU | THROUGH) valueOperand` (`src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4:37-39`)
with the phrase simply gone. The IN phrase is the **only** way a program can say which collating sequence
orders an alphanumeric or national range; without it 14.7.8 rule 2 leaves that ordering "defined by the
implementor". So the omission both rejects legal source and removes the user's only lever over an otherwise
implementor-defined result. 14.9.13.3 SR3, whose entire content is a constraint *on* that phrase, has no code
site to live at.

## 3. Expected vs observed — RE-MEASURED ON HEAD (89044aa0), both parts

    $ cobol.exe p01-partial.cob --run          # 01 WS-N PIC 9(3) VALUE 7. EVALUATE WS-N WHEN > 5 ...
      p01-partial.cob(8,19): error COBOL0001: no viable alternative at input 'WHEN>'
      p01-partial.cob(8,19): error COBOL0001: cannot parse construct near '>'

Expected: SR5 classifies `> 5` as a partial-expression; SR7 d) permits it against an identifier subject; SR8
rewrites the pair to condition-2 `WS-N > 5` with the subject treated as TRUE; GR4 a) 2. evaluates it. WS-N is
7, so the first WHEN is selected and the program prints `GT5`. Observed: two parse errors, no executable.

    $ cobol.exe p03-in-alphabet.cob --run      # ALPHABET MY-ALPHA IS STANDARD-1; WHEN "A" THRU "M" IN MY-ALPHA
      p03-in-alphabet.cob(12,32): error COBOL0001: no viable alternative at input 'IN'
      p03-in-alphabet.cob(12,32): error COBOL0307: unexpected 'IN'. A period may be missing ...
      p03-in-alphabet.cob(13,16): error COBOL0001: unexpected 'DISPLAY'
      p03-in-alphabet.cob(14,14): error COBOL0307: unexpected 'WHEN'. A period may be missing ...
      p03-in-alphabet.cob(16,12): error COBOL0306: unexpected 'END-EVALUATE' ...

Expected: SR3 permits alphabet-name-1 here (both literals are class alphanumeric and STANDARD-1 defines an
alphanumeric collating sequence); GR2 delegates to 14.7.8, whose rule 2 makes MY-ALPHA the ordering; `"C"`
collates between `"A"` and `"M"`, so the program prints `IN-RANGE`. Observed: a parse error at `IN` and a
four-diagnostic cascade behind it — itself evidence that the failure is in the parser, not a later screen.

## 4. The code site and the shape of the repair

- `src/Cobol.Net.Frontend/Grammar/Core/CobolControlFlow.g4:196-201` — `evaluateWhenItem`, four alternatives.
- `src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4:37-39` — `valueRange`, no trailing IN phrase.
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs:149` — `BindWhenItem`, no partial-expression arm.
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs:215-231` — the `valueRange` arm, which has
  no alphabet parameter to carry even if the grammar produced one.
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs:116-134` — `ObjectOperandKind`, which never
  returns `EvaluateObjectOperand.PartialExpression`.

**Do not fix this as three separate implementations.** SR8 *is* the mechanism: splice the selection subject in
front of partial-expression-1 to form condition-2 and treat the subject as TRUE. Add one alternative to
`evaluateWhenItem` and **one arm in `BindWhenItem` that performs the SR8 rewrite**, and GR4 a) 2. (evaluate the
resulting conditional expression), SR7 d) (well-formedness — the rewrite either produces a conditional
expression or it does not) and SR6 e) (the subject becomes an identifier) all become computable from that one
rewrite instead of needing three checks. For the IN phrase, thread the alphabet through `valueRange` into
`BoundRangeMembership`/`CheckedRelational` as a collating-sequence parameter rather than a boolean — the same
parameter the VALUE clause's THROUGH phrase needs, since 14.7.8 says the two share this specification.

## 5. The sibling sweep the fixer must do

- **`valueClauseRange` is the twin** (`CobolExpressions.g4:42-44`) and 14.7.8's opening sentence says its
  specification "applies to THROUGH phrases specified in the VALUE clause and the EVALUATE statement". If the
  IN phrase is added to `valueRange` only, the two ranges diverge on the one rule that says they must not.
- The alphabet must reach `CobolString.ThruMember` and `ConditionBinder.CheckedRelational`, which today order
  by the implementor default; a range under a locale-associated alphabet takes LC_COLLATE (14.7.8 rule 2).
- Landing the partial-expression alternative **makes two Table 15 rows live for the first time**
  (`Partial-expression`, and `Boolean-expression` once PB400's length test lands). `ScreenPairing`
  (`EvaluateBinder.cs:86-95`) declines whenever either classifier returns null, so the new arm must also teach
  `ObjectOperandKind` to return `PartialExpression`, or the row stays dead and the drift test stays green over
  a column nothing can reach.
- Edition gate: partial-expression and the national class are 2002 additions; the IN alphabet-name phrase
  likewise. Adding a grammar alternative changes what parses at `--std 85`, so run the edition-gate sweep.
