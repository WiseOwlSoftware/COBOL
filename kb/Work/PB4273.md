# PB4273 — model assembly plus one assembly per backend

**Owner, 2026-10-31 (Mythos session):** proposed implementing the code generator in a separate DLL so generators can
be substituted behind one interface; after the trade-offs were weighed (and the owner corrected that
`InternalsVisibleTo`, not a public API, gives a backend assembly the model's internals), the owner said "file it".

**Sites:** `src/WiseOwl.Cobol.Compiler/WiseOwl.Cobol.Compiler.csproj` (whole: the model and code-generation sources
leave it); `src/WiseOwl.Cobol.Compiler/CodeGen/ICodeGenBackend.cs` (`BackendFactory`, which moves to the CLI's
composition root); `src/WiseOwl.Cobol.Cli/WiseOwl.Cobol.Cli.csproj` (whole: references each backend);
`WiseOwl.Cobol.sln` (whole: the new projects); `docs/rearchitecture/DESIGN-backend-abstraction.md` (§3.2, §4);
`docs/rearchitecture/DESIGN-architecture-review.md` (§8.1). The files that move are computed from the namespace
layers of DESIGN-architecture-review §8.1 (compiler.model and compiler.codegen), never listed by hand.

**The shape.**
- `WiseOwl.Cobol.Model`: the bound tree, `Place`, the model types, `RuntimeMembers`, `CsNames` (the
  `compiler.model` layer of DESIGN-architecture-review §8.1). Its types stay `internal`; it grants
  `InternalsVisibleTo` to the backend assemblies and the test project. The assemblies are not strong-named, so a
  grant is one csproj line.
- **The model is Roslyn-agnostic** (owner, 2026-10-31: "Ideally, the Model is also Roslyn-agnostic"):
  `WiseOwl.Cobol.Model.csproj` carries NO `Microsoft.CodeAnalysis` package reference, so a Roslyn use in a model
  type is a compile error, not a review finding. Build-time-only analyzers and the visitor source generator
  (`WiseOwl.Cobol.Compiler.SourceGen`, referenced as `OutputItemType="Analyzer"`) are allowed: they never ship,
  as the runtime's `PublicApiAnalyzers` reference (`PrivateAssets="all"`) already shows. On main 2026-10-31 the
  one Roslyn use among the model and bound-tree types is `DataItem.cs:1495-1496` (`SyntaxFacts`, the `@keyword`
  spelling), which PB4272 removes.
- `WiseOwl.Cobol.Compiler`: the binders, validation and the driver; it too should reference no Roslyn package once
  PB4272 lands (`StatementBinder.cs:10`, `CompilerDriver.cs:214` are the only uses), leaving
  `WiseOwl.Cobol.Backend.Roslyn` the ONE assembly that loads Roslyn, so the direct-IL path never does; it references the model and grants NOTHING to a
  backend, so a backend cannot reach `DataBinder`, `ReferenceResolver` or any binder state: a new seam leak is a
  compile error, not a drift-test finding (CLAUDE.md rule 5: the next case is automatic).
- `WiseOwl.Cobol.Backend.Roslyn`: `RoslynBackend` and the emitters; references the model and Roslyn only.
  `WiseOwl.Cobol.Backend.Cil` (DESIGN-backend-abstraction §3.2): the same, with Mono.Cecil, referencing the model
  rather than the whole compiler (correct §3.2, which says it references `WiseOwl.Cobol.Compiler`).
- The CLI is the composition root: it references every backend and `--backend roslyn|cil` chooses one. NO run-time
  DLL loading: the contract is the whole bound tree, the runtime ABI and the CLR naming, not the interface signature,
  so backends ship in lockstep with the compiler; a loaded plugin would work against trimming and Native AOT and run
  whatever DLL is on disk inside the compiler, with no third-party backend requirement to justify it.

**Why last, and why not earlier with a temporary grant.** Moving the Roslyn backend out before the leaks are gone
needs either a broken build or `InternalsVisibleTo` from the whole compiler assembly to the backend, which exposes the
binder too and enforces nothing. Landed after PB4272 and PB2293's extractions, the move compiles only when the seam is
clean, and it supersedes the reflection half of PB4266's contract test (keep whatever the type system cannot express,
e.g. no C# fragment strings on a node). The `Binding.Model → Frontend.Generated` edge must be gone first (PB2398),
or the model assembly would need the parser.
