# PB3388 — IX216A's OPEN EXTEND status failed once on Linux

**The observation.** The landing lane's Linux gate for branch `notes-pb-nist-impact-leg1-20261018` (a notes-only
branch, attempt `20261018T203051277678Z`, head `c95af8611`, which merged main at 13:31 PDT, before PR 255 landed the
keyed-store engine) went red on one test out of 17,812:

    Failed CobolNet.Tests.Conformance.NistDifferentialTests_P5.NistProgram_MatchesGolden(testName: "IX216A") [6 m 22 s]
    Expected: ···"PEN EXTEND: EXP: 05 PASS  OPEN-TEST-GF-01"···
    Actual:   ···"PEN EXTEND: EXP: 05 FAIL* OPEN-TEST-GF-01"···

The program expected I-O status 05 from an OPEN EXTEND of an optional file that is not present, and got something
else. The log is kept at `E:\COBOL-coord\scratch\evidence\ix216a-linux-red-c95af8611-conformance.log`. The branch
changes no code. No other Linux gate log kept in a worktree names IX216A, and the five campaign branches that landed
after it (PRs 257-261) passed their Linux gates, so the failure depends on timing or on the environment. The project rule is that a red that passes alone is a defect to root-cause, never a flake to
re-gate past.

**What is known.** `NistRunner` runs each program in its own GUID-named temporary directory
(`NistRunner.cs` line 29), so a leftover file from another program or another concurrent gate is not the obvious
cause. 6 m 22 s is the elapsed time the runner reported for the test. Since this run, PR 255 (PB3333) replaced the
indexed file's store, so the code path that failed may no longer exist on main. That is a question to answer by
measurement, not to assume.

**What to do.**
1. Derive the expected status from the spec first (the OPEN statement's general rules for EXTEND of an OPTIONAL file
   that is not present, and the I-O status table, with `cite.py --check`), and read IX216A's OPEN-TEST-GF-01 to see
   which file organization and which preceding steps it uses.
2. Reproduce on Linux at the current main: run IX216A in a loop, under load (beside a gate), and with the program's
   predecessors from `corpus.tsv`. Also run it at `c95af8611`, to know whether the engine's arrival changed the odds.
3. Fix the root cause, with an exception-path test that pins the 05 status under the condition the repro found
   (MANDATORY-PRACTICES I11). If it no longer reproduces at main after a measured number of runs, record the count
   and the reason the old path could fail, then close the note with that evidence.

## Landed (wave 1129, group A)

**Root cause (the mechanism is reproduced; the one red's RETRY line is not retained).** Not the runtime: the harness. The Linux
run's `cobolnet-harness-observations.log` (where every retry is recorded) was not kept, so that the red run retried is inferred
from its duration, not read; the failure signature itself is reproduced exactly. `ProcessObserver.ObserveOrThrow` retries a child that did
not complete (the 120 s budget killed it), on the ground that "nothing was learned, so no result is discarded". That ground is
false for a program that writes. IX216A's OPEN EXTEND of an absent OPTIONAL indexed file creates the file (§14.9.27.4 GR17,
checked with `cite.py`: "the OPEN statement creates the file", then the status is set to '05'); the killed first attempt had
created `xxxxx025.txt` in the run directory, and the retry, run in the same directory, found the file PRESENT and answered 00,
so `OPEN EXTEND: EXP: 05 FAIL* OPEN-TEST-GF-01`. Evidence: the red test's duration is 6 m 22 s, more than the 120 s budget plus
the serialized retry, and on a current build the compiled IX216A run twice in one directory prints exactly `OPEN EXTEND: EXP: 05
FAIL* OPEN-TEST-GF-01 ... IX-3; 1.3.4 (1) D; STATUS AFTER OPEN EXTEND` on the second run (the first run passes). The keyed-store
engine did not change the odds: the retry hazard does not depend on the engine.

**Fix.** `tests/_shared/RunDirectoryState.cs` captures the run directory before the first attempt (files up to 1 MiB by content,
larger by length and write time) and `ObserveOrThrow(..., runDirectory:)` restores it before the retry, or raises the
non-observation when a large file the killed attempt changed cannot be restored. The three call sites that run `dotnet <dll>`
(`CutRunner.RunExit`, `AcceptDifferentialTests.AcceptRun`, `CobolNetTestBase.RunAssembly`) name their directory; the drift test
`EveryRunOfACompiledProgram_NamesItsRunDirectory` keeps it so. Sibling arm: `scripts/guard-fast.sh`'s serial re-observation
already re-runs in a fresh `mktemp` directory (`guard-run-group.sh`). Tests: `ProcessObservationDriftTests` (a retry restores a
created file, an in-place rewrite and a subdirectory; an unrestorable large file raises; no `runDirectory` leaves the directory
alone).

## Landing

- `tests/_shared/ProcessObservation.cs#ProcessObserver.ObserveOrThrow` owns the retry; pass `runDirectory:` for any program that
  writes files. The helper to REUSE is `RunDirectoryState` (Capture / Restore); never copy a run directory whole (the runtime
  assembly beside every program is 3.7 MB and ~17,000 runs would pay it).
- `tests/Cobol.Net.Tests.Unit/ProcessObservationDriftTests.cs#WritingProbe`: a per-OS script whose first attempt writes and hangs and
  whose retry reports the leftovers; the marker that tells the attempts apart lives OUTSIDE the run directory, or the restoration
  would erase it. `cmd.exe` and `sh` quoting traps are avoided by writing the script to a file.
- Trap: a Linux red's `cobolnet-harness-observations.log` (in the temp directory) is the evidence that a retry happened; copy it
  into `E:\COBOL-coord\scratch\evidence` with the red log.
