# PB954 — OPEN — the second diagnostic, and it is false

## Repro — measured

`scratchpad/reg9/probe/pic.cob` (PROGRAM-ID `R9PIC`), `cobol.exe pic.cob --std 2023`:

```
       01  W-BAD PIC 9V9V9.
       01  W-N   PIC 9(4) VALUE 1.
           ADD W-BAD TO W-N.
```

```
  pic.cob(5,8): error COBOLNET1934: invalid PICTURE 9V9V9 — data item 'W-BAD': the symbol 'V' appears 2 times
      — each of the symbols 'CR', 'DB', 'E', 'S', 'V', '.' may appear only once in character-string-1
      (ISO §13.18.40.3 SR12 b)
  pic.cob(9,12): error COBOLNET0844: item 'W-BAD' of category alphanumeric is not a numeric operand:
      ISO §8.8.1.1 admits only an identifier referencing a NUMERIC data item, a numeric literal, or the
      figurative constant ZERO in an arithmetic expression. --permissive accepts it as a digit-decoding extension
```

The first is right and complete. The second tells the user their item is **of category alphanumeric** — a
statement about a program in which every symbol of the picture is `9` or `V`. The user reads it as a second,
independent problem and goes looking for a data description that does not exist. `feedback_green_test_can_hold_a_gap_open`'s
cousin: a diagnostic whose text is an ASSERTION ABOUT THE SOURCE, derived from a placeholder that was never an
analysis of the source.

## Where the placeholder is made, and what it says about itself

`src/Cobol.Net.Compiler/Binding/Model/PicInfo.cs:926-928`

```csharp
    public static PicInfo Recovery(int length = 1) =>
        new(PicCategory.Alphanumeric, Usage.Display, Length: Math.Max(1, length), Digits: 0, Scale: 0, Signed: false)
        { IsRecovery = true };
```

and its own summary (`:919-925`) says what it is for: *"The compile has already errored -- this value only
keeps the doomed emit pass crash-free."* **`IsRecovery` is the flag that says "this category is not an
analysis", and it exists precisely so a later reader can ask.** Measured on this tree, the whole codebase reads
it at four sites (`grep -rn IsRecovery src/ --include=*.cs` → 8 hits, four of them the definitions/comments in
`PicInfo.cs`): `DataBinder.cs:2333`, `:5483`, `:5508` — all three about USAGE — and nothing else.

The reader that prints the false sentence is `src/Cobol.Net.Compiler/Binding/Procedure/ExpressionBinder.cs:505-517`:

```csharp
        if (rules.NumericClassScreen
            && !IntrinsicArgumentRules.IsArithmeticOperandClass(new BoundFieldOperand(p)))
        {
            string what = NonNumericOperandKind(p);      // "item 'W-BAD' of category alphanumeric"
            …ctx.Edition.Error("COBOLNET0844", …);
```

`IsArithmeticOperandClass` is the ONE §8.5.2.1 Table-2 classifier ([[PB170]]'s extraction), and it is correct:
handed a profile that says *alphanumeric*, it answers *not a numeric operand*. The defect is not in the
classifier and not in the message — it is that a profile which is **not an analysis** was handed to a screen
whose whole output is an analysis.

## ⭐ SAME ROOT CAUSE AS [[PB453]], WHICH FIXED ONE READER AND LEFT THE SHAPE

PB453 hit this through the other factory, `PicInfo.MessageTagRecovery()`, and the fix it landed is recorded in
that factory's own summary (`PicInfo.cs:930-945`) — in the compiler's words:

> ⛔ IT CARRIES THE WRITTEN USAGE, AND THAT IS THE WHOLE POINT … The profile is still a recovery placeholder —
> `IsRecovery` is set and its category is NOT an analysis of anything … but the USAGE is a FACT the source
> states, and hiding it made every later screen answer about a category the item does not have. … and the
> §8.8.1.1 arithmetic screen (COBOLNET0844, "of category alphanumeric is not a numeric operand", the
> diagnostic's words again). **Both are false about the program.**

That is this defect, named, in the same file, for the MESSAGE-TAG arm — and repaired by routing ONE screen
(`SetFormatSelection`) through the usage instead. The PICTURE-recovery arm still reaches COBOLNET0844 exactly
as described. `feedback_two_arm_dispatch` / `feedback_scan_all_similar`: the arm that was fixed is the one the
group's subject walked through.

## Fix shape — the structural answer, not a fourth `IsRecovery` test

⛔ Adding `|| pic.IsRecovery` at the 0844 site is the small diff and it reproduces the cause: the next screen
that reads a category will print the next false sentence. The shape that makes the NEXT case automatic
(CLAUDE.md rule 5) is a SUPPRESSION at the delivery point — an item whose profile `IsRecovery` has already
produced its own diagnostic, so every CATEGORY-DERIVED diagnostic about that item is redundant by construction
and should be dropped where diagnostics are emitted, once, rather than asked at each screen. The fixer decides
between:

1. a chokepoint in the diagnostic sink keyed on the operand's item (`Edition.Error` already takes the
   cursor/place — the place knows its `DataItem`), or
2. making the screens take a TOTAL "category-of-record" accessor that returns *unknown* for a recovery profile,
   so a screen physically cannot ask a placeholder for a category.

Either way it is ONE decision in ONE place, and it is pinned by a drift test that asserts no second
category-derived diagnostic follows a recovery-producing entry error.

## The sibling sweep the fixer owes — every recovery factory, every category reader

Recovery factories in `PicInfo.cs`: `Recovery()` (:926), `MessageTagRecovery()` (:947). Readers to sweep: every
caller of `OperandCategory` / `NonNumericOperandKind` / `IsArithmeticOperandClass` and every diagnostic whose
text contains the words *"of category"*. The probe above is the minimum witness; a second one should drive the
MOVE screen (§14.9.25.3 Table 16) and a relation condition from the same bad item, because those are the two
other high-traffic category readers. Each false second diagnostic is a NEGATIVE golden asserting that exactly
ONE diagnostic is produced — `.err` files that pin a count, not just a code.
