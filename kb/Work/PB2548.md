## Why it was not fixed in the train

Each resolver WRITES resolved state onto the item, and a template has no storage (§13.18.58.4 GR2), so the fix is a
screen-only pass over the template members (the `ScreenRedefinesClause` shape), not a widened walk. DEPENDING ON may
name an item OUTSIDE the type declaration, which needs its own design reading before a template can be screened for
it. Same mechanism as PB2071: one note for the three resolvers.

## Landed (wave 1051 group E, branch worktree-wf_4151e8da-91b-5)

**Re-probe (own build).** `E:\COBOL-coord\scratch\w1037b\s1.cob` (RENAMES) and `s2.cob` (KEY) compiled clean; `s3.cob`
(DEPENDING ON NOSUCH) still does, by determination below.

**The fix is a forest, not three patches.** The note proposed "a screen-only pass over the template members". The
measured shape is simpler and closes the next case too: `DataBinder.ClauseResolutionForest()` is `AllItems()` + each
template's root + `TemplateItems()`, and `RenamesOwners`, `OccursKeyResolve`, `OdoResolve`'s clause pass and `DynamicResolve`
walk it. Writing resolved state onto a template is harmless (a clone's `OccursSpec` and `RenamesInfo` are its own, fresh,
resolved per clone; `ClassifyRedefinesClasses` still builds no class for a template), and a used template's error is not
doubled because `EditionContext.AddOnce` drops the same words at the same position. `TemplateClauseResolutionDriftTests`
pins the list.

**Determination: a DEPENDING ON counter the declaration does not define is not an error in an unused template.** §13.18.57.4
GR1 (cite.py OK): the effect of a TYPE clause "is as though the data description identified by type-name-1 had been coded in
place of the TYPE clause", and §8.4.2.2.1 rule 5 (cite.py OK) resolves a data-name in a data description entry clause among the
groups superordinate to the subject, so a counter the type does not hold may be a sibling of the use site (`2002/
pb2548_template_clauses_resolve` pins it). The clone reports an unsupplied counter (COBOL0851) as before. What a declaration
alone decides IS asked of it now: SR16's bounds, a counter that resolves inside the declaration or in the program (SR17
integer, SR2, SR1(b)/SR10 nesting, SR22 trailing, the REDEFINES area) and an ambiguous counter. SR18/SR21 (the record's
GLOBAL / EXTERNAL attributes) and SR20's cross-record arm (the area a record shares with another) read the placement, so
they stay with the clone; SR20 inside the declaration is asked.
`DynamicResolve` asks a declaration SR28 (FROM < TO, COBOL1522) only: the CAPACITY register is minted per placed table
(SR30; §13.18.58.4 GR2 gives a declaration no storage).

**Sibling sweep.** The other readers of `AllItems()` in the binder: `ExpandTypes`' own passes (they build the clones),
`CheckStrongTypeDeclarations`' implicit-redefinition arm (FD records only) and `ClassifyRedefinesClasses` (a class is storage;
the template REDEFINES clause rules are PB2071's separate loop) keep the roots deliberately. The strong-RENAMES screen
(§13.18.57.3 SR3, COBOL1532) shares `RenamesOwners`, so a template that renames a strongly-typed member is refused too.
No template pass writes a class, a register or a layout.

**Goldens.** Negatives `pb2548-template-renames-unresolved` (COBOL1655), `-key-unresolved` (COBOL2353),
`-odo-counter-not-integer` (COBOL0852), `-dynamic-from-to` (COBOL1522, 2014+); positive
`2002/pb2548_template_clauses_resolve` (a valid RENAMES THRU + KEY template, and a counter the use site supplies).
