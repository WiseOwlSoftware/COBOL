# PB3478 — private Tmp and TryDelete copies survive the FileHarness consolidation

Low DUPLICATION lead from the implementer report of PB3471 (`E:\COBOL-coord\scratch\reports\w1136c-PB3471-report.md`, `## New defects` LEAD 1). ## Landing

Re-probed on this build: all 17 private copies were present (plus a private `Delete(params string[])` in
`RunUnitImplicitCloseDriftTests`). The sibling sweep found the same job written inline in eleven more test sites (a
unique `.dat`/`.txt` host path from `Guid.NewGuid()`, `PerformFormat3IoConflictAndSortTests.HostPath`, and
`CompiledProgramCache.TryDeleteFile`, an exact copy of `FileHarness.TryDelete`); all are converted, no forwarder remains.
The copies had drifted (IOException only versus also UnauthorizedAccessException, one with a file-name guard), which is the
cost the note predicted. The structure that keeps it fixed is `FileHarnessOneHomeDriftTests` (a unique-host-name line and any
`try` that is only `File.Delete` with empty catches, a private helper's body or inline in a `finally`, fail the sweep; a
fixture test proves the detectors trip). Branch review round 1 found the first draft matched only the helper-method shape
and left 85 inline copies (three drifted catch sets) in 45 files; all converted to `FileHarness.TryDelete`. The
`.cob` and temp-directory builders are a different job and untouched.

Next implementer: a test that needs a temp host path or a best-effort delete calls `FileHarness.Tmp(tag)` or
`FileHarness.TryDelete(path)` (`tests/_shared/FileHarness.cs`); `FileHarnessOneHomeDriftTests` is red when a private copy
comes back.
