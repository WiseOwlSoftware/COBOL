# PB228

**Rows:** `GR-14.9.2.4-1`, `GR-14.9.2.4-2`, `GR-14.9.2.4-3`

no golden anywhere runs an ADD under `ARITHMETIC IS STANDARD-DECIMAL`, so the second paragraph of §14.9.2.4 GR1/GR2/GR3 — the whole standard-decimal equivalence, including the operand order it fixes — is pinned by nothing.

Rows: GR-14.9.2.4-1 (Format 1, ADD … TO), -2 (Format 2, ADD … GIVING), -3 (Format 3, ADD CORRESPONDING). Each rule is two paragraphs; the FIRST paragraph of each is implemented and pinned by spec-derived value goldens, and the SECOND paragraph of each — the same sentence three times — has no evidence at all.

WHAT IS PINNED (first paragraphs, kept here so the note is not read as doubting them). GR1: NumericRenderer.Fold seeds `acc = xs[0]` and folds `CombineCore(acc, "+", xs[i])` ascending — exactly 'in the order in which they are specified in the ADD statement' — and StoreArith reads the receiver as a sending operand and stores receiver+value back; with more than one receiver the fold is Snapshot-ed into a temp so `ADD A TO B A C` cannot poison later receivers (§14.7.7 GR4 + NOTE 3), and Fold saves/restores the ambient `_rcv` so the initial evaluation is receiver-INDEPENDENT (GR4a's 'placed in an intermediate data item'). The code computes `identifier-2 + initial-evaluation` where GR1 prints the reverse; that is not a defect — addition is commutative in Int128, in CobolDec (decimal128 add is commutative and correctly rounded) and in IEEE binary64. Values: conformance:2002/ca6_binary_operand_composite (`ADD BL TO F`, 5+3=8 into PIC 9(11)V9(13)) and conformance:2023/pb45_function_in_sending_operands (`ADD FUNCTION SQRT(W-Z) TO W-R` → ADD-TO=0003). GR2: the TO operand is folded into `addends` (BindAdd:33-34, appended AFTER the operand list — which is the printed operand order, operand-2 LAST) and only the GIVING operands become receivers; EmitGiving computes one value for the receiver SET and Snapshots it before the store loop; the harvested TO operand still passes the §8.8.1.1 sending screen (`host.Expr.BindExpr` is `BindExprCore(node, OperandContext.Arithmetic)`, ExpressionBinder.cs:584). Values: conformance:2023/ca4_giving_composite (1+2=3, also proving TO may be omitted), pb45 (`ADD FUNCTION SQRT(W-Z) TO W-Q GIVING W-R` → ADD-GIVING=0011 = 2+9), conformance:2023/pb66_float_edited_picture (`ADD 1 0.5 GIVING E4` → `ADD      [ 15.000E-01]`). GR3: CorrespondingEmitter.Emit:21-47 is `string op = c.Verb is CorrVerb.Add ? "+" : "-"` then `StoreArith(p.Target, num.Combine(num.FieldNum(p.Target), op, num.FieldNum(p.Source), rcv), c.Rounding)` — target on the left, source on the right, exactly 'added to and stored in corresponding items in identifier-5'. Values: conformance:2014/corresponding_rounded_mode (SRC.P=1.25, SRC.Q=1.21 into PIC 9V9 receivers → 1.2/1.2 truncated, 1.3/1.2 rounded, derived from the rule plus §14.7.4) and CorrespondingDifferentialTests.AddCorresponding_RoundedAppliesToEachPair (an AssertOutput whose expectation is derived in a comment from §14.7.4.3 r1, with AssertSameAsLegacy only alongside).

THE GAP. Each second paragraph reads 'When standard-decimal arithmetic or standard-binary arithmetic is in effect, the result … is equivalent to (operand-11 + … + operand-1n [+ operand-2])'. STANDARD-BINARY is rejected outright at bind (DataBinder.cs:318-320, COBOL0806; docs/CONFORMANCE.md A.3 row 2 'Not claimed'), so that arm has no implementation by decision. STANDARD-DECIMAL DOES exist — but only as NumericRenderer.CombineCore's single shared `if (StandardDecimal)` branch, and NO tests/conformance/**/*.cob names both ADD and STANDARD-DECIMAL: 2014/arithmetic_standard_decimal is a COMPUTE, pb84_standard_decimal_intermediate_consumers is DIVIDE/REMAINDER, pb157_compute_sdidi_sole is a COMPUTE. The ADD leg is code-shared and never exercised, in any of its three formats. What that costs specifically: the operand ORDER the paragraph fixes (operand-2 LAST) is invisible under native Int128 addition, which is commutative — it becomes observable only under SDIDI, i.e. exactly the unexercised lane, so BindAdd:33-34's correct append order is protected by nothing.

A SECOND EVIDENCE FACT ON GR3, worth keeping: tests/Cobol.Net.Tests.Conformance/CompilerUnderTest.cs:115 declares `CobolNetCompiler(int dialectLevel = 85)`, so every AddCorresponding_* xunit case runs at COBOL-85 ONLY, and conformance:2014/corresponding_rounded_mode is 2014-gated (it writes ROUNDED MODE IS). GR3 has value evidence at 85 and 2014 and NONE at 2002 or 2023, although the rule has no edition delta (Annex E lists no ADD change).

WHAT WOULD CLOSE IT: three `ARITHMETIC IS STANDARD-DECIMAL` goldens whose SDIDI answer differs from the native Int128 one — a multi-addend `ADD … TO` whose intermediate needs more than the receiver's digits, an `ADD … TO … GIVING` whose operand-2-last order is load-bearing, and an `ADD CORRESPONDING` whose per-pair result differs — plus one 2002 or 2023 ADD CORRESPONDING value golden to span the editions GR3 claims.

SPEC REFS as carried by the rows: §14.9.2.4 GR1, GR2, GR3 (each second paragraph); §14.7.7 GR4 + NOTE 3; §14.7.4.3 r1; §8.8.1.1; §8.8.1.3 (native arithmetic); Annex A.3 row 2 (STANDARD-BINARY not claimed).

## Mechanism

src/Cobol.Net.Compiler/CodeGen/Emit/NumericRenderer.cs#CombineCore — ONE `if (StandardDecimal)` branch lifting every operand through DecOperand/CobolDec, shared by every arithmetic verb with no per-verb arm (`grep -rn StandardDecimal` shows the single branch); the ADD side reaching it is ArithmeticEmitter.cs#EmitInPlace / #EmitGiving and CorrespondingEmitter.cs#Emit, bound by ArithmeticBinder.cs#BindAdd (:29-47) and CorrespondingBinder.cs#BindAddCorresponding (:25-29)

## Landing (wave 1091 I, 2026-10-16)

**Re-probed on the wave-1091 tree: the compiler was already right; only the evidence was missing.** A probe with
X = 10**30 (PIC S9(31)), Y = -(10**30), Z = 0.0004 under `ARITHMETIC IS STANDARD-DECIMAL` gave every value the
second paragraphs require, and the composite-of-operands cap (§14.7.7 GR2, a NATIVE-only rule) is correctly not applied
there (the same statements without the OPTIONS paragraph stop on COBOL0805). No code changed.

WHY THESE VALUES. An SDIDI keeps 34 digits (§8.8.1.5.2), each addition is a correctly rounded decimal128 one
(§8.8.1.5.3) under the implied NEAREST-AWAY-FROM-ZERO (§11.9.11.2 GR3a), so X + Z (35 digits) rounds back to X and the
grouping decides the result. Note that the obvious 34-digit design does not compile: ISO caps a fixed-point item at 31
digits (COBOL0801), so the order has to be made visible by CANCELLATION (X then Y) of a 31-digit pair around a
4-decimal residue, or by a round-up carry into the receiver's units digit (the CORRESPONDING pair).

Goldens: `2014/pb228_add_standard_decimal` (PB228ASD: GR1 TO-1/TO-2, GR2 GIV-1/2/3 with operand-2 last, GR3 CORR
...0005 vs native ...0004), `2002/pb228_add_corresponding_values` (PB228ACN: GR3/GR5 native at 2002), negative
`pb228-add-standard-decimal-below-2014` (reject-at 85 2002, COBOL0900). SIBLING SWEEP: the SUBTRACT twins
(§14.9.44.4 GR1/GR2 second paragraphs) were CONFORMS but their grouping was pinned only by a probe and by values exact
in every order; `2014/pb228_subtract_standard_decimal_order` (PB228SSD) now pins both. SUBTRACT CORRESPONDING's
printed `(operand-1 - operand-2)` contradiction is GR-14.9.44.4-3's recorded resolution and was not re-litigated.
Batch `w1091i-PB228` (E:\COBOL-coord\scratch\w1091\w1091i\pb228-verdicts.json): GR-14.9.2.4-1/-2/-3 PARTIAL → CONFORMS,
witness-only additions on GR-14.9.44.4-1/-2; GAP 97 → 94.
