# PB5039 - cite.py prints a shape citation.parse refuses

**Mechanism.** `scripts/spec/cite.py#check` and `#find` print the matched list entry after the clause, as `OK  §<edition>:<clause> <n>)`. `scripts/spec/citation.py#parse` refuses that string ("'N)' is not a rule designator"), while `scan` silently reads only the clause. So the tool's own output is not a citation the tooling accepts, and agents paste it into comments (CLAUDE.md rule 1: the failure mode is inheriting).

**Repro (run on main 9935e755b6, 2026-11-09).**
`python scripts/spec/cite.py --check "§2023:E.3.2" "Asynchronous messaging"` prints
`OK  §2023:E.3.2 1)  (Possibly affecting because of the addition of new words or names)` followed by the matching list text. Pasting `§2023:E.3.2 1)` into a comment gives a string `parse` refuses.

**Extent.** About 7,600 lines carry the `<clause> <n>)` shape: kb 3,673, conformance-suite 1,997, src 1,010, tests 636, docs 321. `audit_code_citations.py` therefore cannot refuse the shape (CITATION) without a tree-wide rewrite first.

**Relation to PB4976.** PB4976 (open) lists individual wrong-form sites (`§2023:8.5.1.9.1 2`, `§2023:8.3.2.1 1)`) and asks for a tree audit; it does not name cite.py's output as the cause. This note is the root of that part: the generator emits the shape.

**Needed (a tooling decision).** One option: cite.py prints the canonical `SR n` / `GR n` when the matched region is a rules block, and `item N` (or the bare clause) otherwise; rewrite the tree once, alone because it is tree-wide; then add the CITATION refusal to `audit_code_citations.py` so the next case is automatic (CLAUDE.md rule 5). The rule designator for each existing site is re-derived with `cite.py --check`, never guessed.
