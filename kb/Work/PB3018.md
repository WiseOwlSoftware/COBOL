# PB3018 — unsigned-wide lift on the NATIVE Dec lane rounds at 34 digits

Filed 2026-10-11 by the train 1059 lander from `E:\COBOL-coord\scratch\reports\w1059c-PB2966-report.md` (lead 2);
not re-probed by the lander.

**Site.** `NumericRenderer.DecOperand` (src/Cobol.Net.Compiler/CodeGen/Emit/NumericRenderer.cs ~line 776): the
`{ U: true }` arm always emits `RuntimeApi.DecLiftRoundedUnsigned` (CobolDec.FromUnsigned, 34-digit rounding), while
a signed operand is lifted exactly up to `ExactLiftDigits`, which is 38 under NATIVE arithmetic
(`NativeDecExactDigits`, the Dec lane's wide scratch, DOC-A.1-82, kb/Work PB1510). Since PB2966 (train 1059) moved
the `DeU` funnel after the lane decision in `CombineCore`, an unsigned-wide operand of a NATIVE statement that
carries a Dec operand reaches this arm directly, so an unsigned value of 35 to 38 digits is rounded where the same
value in a signed container would be exact. (Before PB2966 a value of 2^127 or more was a size error there, and a
16-byte unsigned item's digit bound of 39 already took the rounding arm, so the observable change is confined to
values in [2^127, 2^128) and to unsigned items whose declared digit bound is 38 or fewer.)

**Question to settle (a determination, not only a fix).** Under NATIVE arithmetic the Dec lane's exactness is
implementor-defined (DOC-A.1-82). Either the unsigned arm honours `ExactLiftDigits` (a wide unsigned exact lift,
`CobolDec` carries 38 digits exactly in its scratch) or DOC-A.1-82 records that an unsigned-wide operand on the
native Dec lane rounds at 34. Both arms of `DecOperand` should answer from one predicate (`LiftRounds`, PB2965).
Repro to write: NATIVE, `COMPUTE R = W + D` with W unsigned 16-byte holding a 36-digit value and D a Dec-lane
operand (e.g. a STANDARD-DECIMAL function result), compared against the signed twin.

## Landed 2026-10-12 (wave 1069 A) - the observable defect DISCHARGED, the two-statement predicate unified

**Re-probe on the wave-1069 build: no behavioral difference exists.** The note's premise is that a signed operand "of up to 38
digits" lifts exactly where the unsigned arm rounds. The signed operands that lift exactly are those whose digit BOUND
(`PicInfo.UnscaledDigitBound`) is at most 38 - DISPLAY, packed and ordinary binary items of at most 31 digits - and the
unsigned-wide carrier is only a 16-byte BINARY-CAPACITY container, whose bound is 39 (it owns [0, 2^128)); a SIGNED 16-byte
container owns 39 digits as well and rounds identically. Measured: a 36-digit value (X"0017C6E3BFD70FDEEAEC417172DCBAC0") in
`PIC 9(31) COMP-5` and in `PIC S9(31) COMP-5`, `COMPUTE R = W + 0.0E+0` under NATIVE arithmetic: both land
123456789012345678901234567890123500 (34 digits), and the DISPLAY control keeps all 31 digits. The note's "unsigned items whose
declared digit bound is 38 or fewer" does not exist.

**What was still wrong was the shape.** `DecOperand` answered the unsigned case in its own first arm and `LiftRounds` carried a
matching `x.U ||`: one rule written twice, so the next carrier whose bound is provable would have diverged. `DecOperand` now
asks `LiftRounds` first for EVERY carrier and the carrier only selects the rounding twin (`FromUnsigned` / `FromParsed`);
an unsigned operand whose bound is within `ExactLiftDigits` would lift exactly through `DecOperandExact`. The determination is
recorded in DOC-A.1-82 (docs/CONFORMANCE.md) and pinned by golden
`2023/pb3018_native_dec_lane_wide_binary_operand_signed_and_unsigned_agree`.

**Sites (for the next implementer).**
- `src/Cobol.Net.Compiler/CodeGen/Emit/NumericRenderer.cs#DecOperand` / `#LiftRounds`: LiftRounds is the one predicate; the carrier only chooses the
  rounding twin (`RuntimeApi#DecLiftRoundedUnsigned` / `DecLiftRounded`). `SdidiOperandLiftDriftTests.TheExactOperandLift_HasOnlyTheRoundToOddConsumers`
  allow-lists the one guarded pass-through line by its text.
- Trap: `PicInfo.UnscaledDigitBound` is 39 for every 16-byte binary container, signed or unsigned, so no unsigned-wide operand can have a provable bound of 38.
