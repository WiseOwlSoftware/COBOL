# PB1908 — STRING overlap: decide, document and pin (the PB1907 shape)

**Sites:** `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/StringEmitter.cs` (`StringEmitter.EmitString`, `StringEmitter.ReadOperand`, `StringEmitter.ReadsStorageOf`, `StringEmitter.StringSending`), `src/WiseOwl.Cobol.Compiler/Binding/Model/StorageOverlap.cs` (`StorageOverlap.MayShareStorage`, the data-item overload), `docs/CONFORMANCE.md` (D-STR1 to D-STR4), `docs/STRING_OPS_DESIGN.md` (D4), `docs/DESIGN.md`, `tests/WiseOwl.Cobol.Tests.Unit/StringLiveReadDriftTests.cs`, `tests/WiseOwl.Cobol.Tests.Unit/SpecTraceabilityInventoryDriftTests.cs` (`TheRowsClosedOnADerivation_AreTheEnumeratedPopulation`)

Found by wave 1002 group B (PB1907's UNSTRING part) and filed at the train-1002 landing.

## The case

Row `GR-14.9.43.4-10` (§14.9.43.4 GR10, Annex A.2 item 60: a STRING whose sending, delimiter, receiving or pointer
operands occupy the same storage — the result is undefined) is verdicted CONFORMS with NO witness. §4.4 2) makes a
run unit that allows it a conforming one. The owner's PB1907 decision (2026-10-01: "determine what the
best/appropriate/current behavior we provide judged against what other implementations do in each case, document
our behavior … then produce a golden"; and "Follow GnuCOBOL, except WRITE length") covers it, but no wave-1002 group
carried STRING.

## What is known

- Code site: `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/StringEmitter.cs` `EmitString` (~line 31). It keeps a receiver
  IMAGE and reads the senders from storage, so a sender that overlaps the receiver reads its pre-statement value;
  libcob (`cob_string_append`) appends in place, so a later sender overlapping the receiver reads what earlier
  senders wrote. That is a candidate measurable difference; not yet measured.
- Shares its root (`StringEmitter`) with D-UNS1..4 (`docs/CONFORMANCE.md` §3.1). The may-share predicate to ask
  is the one PB1911 settles.
- Repro: not yet written. Measure with a built cobc 3.2 under WSL (`tests/external/gnucobol-3.2.tar.xz`; the
  wave-1002 scratch scripts `run_cobc1.sh` show the recipe).

## Closing shape

As PB1907: measure ours and GnuCOBOL's on each sub-case (sender/receiver, delimiter/receiver, pointer/receiver),
follow GnuCOBOL where it measurably differs, write D-STR rows beside D-UNS in `docs/CONFORMANCE.md` §3.1, pin with a
golden at edition 85, record the verdict with a test-ref.

## Landing (wave 20261760, group B)

Measured on cobc 3.2.0 under WSL against this build, every sub-case of the closing shape. Before the change WiseOwl COBOL
read every sending operand and identifier delimiter once, before the first character moved, so a STRING whose later
sender or delimiter shared storage with the receiver differed from libcob (`cob_string_append` moves into
`string_dst->data` and reads `src->data` and the delimiter's storage on every call): sender/receiver (`STRING "XY" R(1:2)
R(3:2) INTO R`: ours `XYABCDGHIJKL`, libcob `XYXYXYGHIJKL`), delimiter/receiver (`x12x34ghijkl` against `x12defghijkl`)
and a FUNCTION whose argument is the receiver (`xyABCDEF` against `xyXYCDEF`). Pointer/receiver already agreed
(`cob_string_init` reads the pointer once, `cob_string_finish` stores it last), and so did a single sender overlapping its
own transfer (glibc's `memcpy` moves it as a snapshot).

The fix is the UNSTRING shape: `StringEmitter.EmitString` stores the working image into identifier-3 before each transfer
(after the first) whose sender or delimiter `StorageOverlap.MayShareStorage` cannot prove disjoint from it, and reads that
operand again; a function operand whose argument may share the receiver's storage is rendered inline and runs once at its
transfer. A STRING over disjoint operands emits what it always did. Documented as D-STR1 to D-STR4 beside D-UNS1 to D-UNS4,
pinned by five goldens (`pb1908_string_overlap_{sender,delimiter,pointer,linkage,function}`) and
`StringLiveReadDriftTests`; 1,350 random STRING statements over one record (reference-modified senders, delimiters and
pointers of the receiver) ran identical on both compilers.

Row `GR-14.9.43.4-10` closes on the goldens. It had been signed on a derivation (kb/Work PB1636, DRV-GR-14.9.43.4-10, "any
behavior conforms"); a row with a spec-derived test may not also carry one (design doc 1.1 refusal 1), so the
derivation left with this change (its register row, its place in the enumerated population) and its argument stays the
reason the behavior is a free choice. The predicate asked is `StorageOverlap.MayShareStorage`, the one kb/Work PB1911
keeps; PB1911 still owns moving UNSTRING off `StorageSharing.MayShare`.

Review round 1 (R1-1, R1-2): the first sending's operands, and any function the walk proves disjoint, are identified up
front in statement order (§14.6.4 7; §14.9.49.4 GR11; kb/Work PB3261) - only a later sending's function that may share
identifier-3's storage stays inline (D-STR4). `ReadsStorageOf` now walks arithmetic arguments and the reference-modifier
positions of a function result, so a function over disjoint working storage is never moved past the identifier-3 read.
Pinned by `conformance:cases/14.9.43-STRING/pb1908_string_function_order` and five more `StringLiveReadDriftTests`.
