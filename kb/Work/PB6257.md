**Scenario:** Which carrier (scaled Int128, wide, whole-aligned exact, SDIDI, SDIDI quotient, binary64) a call computes on is the order of about fifteen if-arms in IntrinsicRenderer.RenderNum (lines 106-264, each commented with which arm must precede which), fed by eight INTAKE(PREDICATE) helpers (AnyDecOrRealRaw, AnyDecRaw, AnyRealArgument, AllRealArguments, AnyFloatItemArgument, AnyApproximateArgument, AlignedOperands, SelectionPastReceiverHeadroom) that each re-render every argument through num.AsNum and throw the text away. The bind-time intermediate item (§2023:14.9.25.4 GR1) needs the same answer before rendering, so FunctionValueLane.Of re-derives it with its own visitor and three runtime-body-keyed sets (NativeSdidiBodies, NativeSdidiBodiesWithExactResult, NativeSdidiBodiesWithWholeResult) restating RenderDec's arm labels; FunctionValueLaneDriftTests regex-parses RenderDec's body out of IntrinsicRenderer.cs to keep them equal, and IntrinsicRealArgDriftTests anchors on the first switch in the file, which is why RenderNum's standard-mode arms are written as an if-chain on purpose (line 130). A new arm or a reordering changes the render without changing the prediction: PB4980 (a multi-receiver MOVE of ANNUITY (MEDIAN (T (ALL)) 3) gave receivers values that differed from the single-receiver result), PB4923, PB4979 and PB5893 were each this disagreement. The four routing tables the renderer keeps for itself (StandardValueFixedByRule and EquivalentExpressionUnaryArms keyed on the runtime body, WholeRangeBodies, ExactListBodies) are spec classifications of functions (which have an equivalent arithmetic expression, which values a rule fixes) that a second backend behind ICodeGenBackend would have to copy.
