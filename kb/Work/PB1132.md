# PB1132 — LANDED (w67q)

## The rule
> "The address of each based item is set to null"
`cite.py --check 14.6.2.3.2 "The address of each based item is set to null"` → `OK  §14.6.2.3.2 5)  (Initial state)`

## Measured (adjudicator / refuter evidence, verbatim)
### [initial-and-last-used-states-of-data] A cached-singleton program (neither INITIAL nor RECURSIVE) re-initializes its LOCAL-STORAGE at each activation by reassigning LS root fields in the emitted Call entry, but the implicit data-address pointer of a BASED entry (__addr_<name>, an instance field declared by OoEmitter.EmitPointerBackings) is never part of that loop. So a LOCAL-STORAGE BASED item keeps the previous activation's address, and a LINKAGE BASED item (same instance-field shape) does too.
- **Rows:** GR-14.6.2.3.2-L2.5 — harm `wrong-answer`
- **Repro:** Main: CALL "LSBSUB" twice. LSBSUB (no INITIAL/RECURSIVE): LOCAL-STORAGE 01 LB PIC X(3) BASED. LINKAGE 01 KB PIC X(3) BASED. PROCEDURE: IF ADDRESS OF LB = NULL DISPLAY "LB=NULL" ELSE DISPLAY "LB=HELD"; same for KB; ALLOCATE LB; ALLOCATE KB; GOBACK. Source: E:\Temp\claude\E--CobolSharp\a700c052-f9e4-4942-84ff-a13c7505d6ec\scratchpad\adj-d1\out\probe\ls-based\lsb.cob, run with --std 2002 and --std 2023.
- **Expected (spec):** LB=NULL, KB=NULL, LB=NULL, KB=NULL. LOCAL-STORAGE is automatic data (§13.6.4 GR1), and automatic data is placed in the initial state on every activation (§14.6.2.3.2), which includes action 5, 'The address of each based item is set to null.' §8.6.5 also ends a local-storage based association at the end of that section's life cycle, and ends a linkage-section one 'at the end of the execution of the runtime element'.
- **Observed:** Both editions print LB=NULL, KB=NULL, LB=HELD, KB=HELD. The generated p2.g.cs shows the Call entry resetting LA/LD/LV ('LOCAL-STORAGE ... initial state each activation') while '__addr_LB' and '__addr_KB' remain instance fields that nothing reassigns. The WORKING-STORAGE BASED arm is correct: last-used between plain activations, NULL after CANCEL, and for a RECURSIVE unit NULL through __ResetStatics (golden pb154_cancel_initial ADDR=NULL). INITIAL and RECURSIVE units are unaffected because they get a fresh instance per activation. A reference through the stale address after the first activation's storage is freed would read freed or foreign storage where the spec requires EC-DATA-PTR-NULL (§13.18.5.4 GR3). Sweep hint: every other per-activation instance field of the LS or linkage shape that the Call-entry LS loop skips, such as LS ADDRESS-OF addressable cells and LS index cells outside IndexDeclarationsUnder, should be checked against the same rule.
- **Code site:** src/Cobol.Net.Compiler/CodeGen/ProgramEmitter.cs#EmitCallMethod (the `!unit.Initial && !unit.Recursive && LocalStorageRoots.Count > 0` re-init block); src/Cobol.Net.Compiler/CodeGen/Verbs/OoEmitter.cs#EmitPointerBackings (declares __addr_<name> = ManagedPointer.Null as an instance field)

## What the fixer owes
Add every LOCAL-STORAGE BASED item's address backing to ProgramEmitter.EmitCallMethod's re-init block (and the same for any other automatic-storage re-init site — methods, functions). Golden: SET ADDRESS OF a LOCAL-STORAGE BASED item in call 1; call 2 tests it for NULL.

## Landed — 2026-09-27, wave 67 Q (branch `worktree-wf_475f7239-eda-5`)

**One per-activation seed for both arms.** `OoEmitter.PtrActivationSeed` became `ActivationPointerSeeds(data, roots)` and `ProgramEmitter.EmitCallMethod`'s cached-singleton entry calls it over the LOCAL-STORAGE roots and the non-formal, non-RETURNING LINKAGE roots: a BASED item's `__addr_X` → NULL (§14.6.2.3.2 action 5, `cite.py` OK 5)), an ADDRESS-OF-taken record's `StorageCell` → a fresh cell at its initial image (§8.6.4). A program LS cell is no longer `readonly` (`EmitPointerBackings`). The linkage leg follows the method arm: §8.6.5 ends a linkage-section based association "at the end of the execution of the runtime element", so the next activation starts at NULL. `ActivationStorageReseedDriftTests` (Unit) pins it over the generated C#: every LS/LINKAGE pointer or cell member is assigned in `Call`, none is readonly, and the WORKING-STORAGE twin (static, last-used) is not touched.
