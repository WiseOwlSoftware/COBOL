# PB4491 - the signature graph is structural for an elementary pointer formal and nominal for a member

**Rule.** `python scripts/spec/cite.py --check 10.6.2 "the signatures of these two compilation units shall be the same"` -> OK
10.6.2 2): a program definition and a program prototype definition of one externalized name have the same signatures.
Two pointer formals whose TO phrases name different prototypes (`TO Q1`, `TO Q2`) are different types (8.5.3.1: type
equivalence by type-name; the rule PB4107 applied inside a strong-group member).

**Observed.** PB4442 moved every pair-mode conformance check (override, IMPLEMENTS, property accessor pair, interface pair) to
compare the TO phrase by the prototype it names. What stays is the signature graph itself: `PrototypeSignatures.SameDescription`
asks `ActivationRelations.SignatureDifference(..., pointersBySignature: true)`, which reads an ELEMENTARY pointer formal by its
signature class (`PrototypeSignatureClasses`, the bisimulation PB2464 / PB2495 built so two mutually recursive prototypes have one
signature), while a strong-group MEMBER pointer compares by name (PB4107). So the §10.6.2 SR2 pair `PX` (prototype `USING TO Q1`,
definition `USING TO Q2`, one signature class) is admitted by `_unassigned/pb2495_pointer_type_in_signature_checks`, and the same
pair written as group members is refused (`10.6-COBOL-compilation-group/pb4107-group-formal-pointer-two-names`, COBOL1513).

**Fix direction (a design decision, flagged to the owner by the report).** Make the graph nominal for the pointer's TO phrase and
retire the bisimulation of `PrototypeSignatureClasses`: this REVERSES PB2495 (mutually recursive prototypes were given one
signature class so a SET between their pointers is legal) and must say which relation 8.13 / 10.6.2 SR2 require of an elementary
restricted pointer formal, class or identity. It shares its root with PB2103's canonical identity of a prototype. The change
moves `PrototypeSignatures.SameDescription`, `ActivationRelations.SignatureDifference` (its `pointersBySignature` arm), the
drift test that pins the one asker (`PrototypePointerTypeDriftTests`) and `SignatureIdentityDriftTests`, and rewrites the
`_unassigned/pb2495_pointer_type_in_signature_checks` legs that assert the admission. If the adjudication keeps the structural
reading, the golden of the group-member case must be re-argued instead, and this note closes by recording that.

## Landed (wave 20261849, group C)

**Adjudication: the spec decides, no owner decision.** §8.13 (`cite.py --check 8.13 "the description of the parameters of the
source unit"` OK) makes the signature the description of the parameters; §13.7.3 SR2 (OK 13.7.3 2)) asks the prototype's formals
to "match the description of the formal parameters" of the definition. The description of a formal `USAGE PROGRAM-POINTER TO Q1`
is that USAGE clause, and docs/CONFORMANCE.md D-RP1 (PB4107, the ISO reading, no latitude) compares a TO phrase by the prototype
it names wherever "the same ... USAGE clauses" is asked, including §14.8.2.3.2's BY REFERENCE pass (OK 14.8.2.3.2 4): "both shall
be restricted and of the same type"). The structural reading is inconsistent with that determination: it admitted a prototype
`USING TO Q1` for a definition `USING TO Q2`, so every caller checked against the prototype passed the definition a pointer its
formal refuses BY REFERENCE, and it made two prototypes that name each other one signature, so a SET admitted by §14.9.39.3 SR22
put into a pointer TO P2 a program that a call through that pointer would hand a pointer TO P1 for its formal TO P2. The nominal
reading is the only one under which the prototype stands in for the definition. It REVERSES PB2495's verdict for mutually naming
prototypes (now two signatures, SR22 refuses the SET) and retires PB3101's partition refinement, which existed only to find that
fixed point.

**Re-probe (cobol.exe on base 32d4e4db1).** `conformance-suite/cases/_unassigned/pb2495_pointer_type_in_signature_checks`
compiled and ran (`px null` / `content null`): the SR2 pair PX (prototype TO Q1, definition TO Q2) was admitted, and the
`CALL PX USING A` passed a pointer TO Q1 BY REFERENCE into the definition's TO Q2 formal unchecked. After the fix the same
source draws COBOL1513 at (45,20).

**Fix.** A pointer formal's description is its USAGE clause for every asker: `ActivationRelations.SignatureDifference` lost its
`pointersBySignature` parameter and arm, `OoConformance.SignatureDifference` and `PrototypeSignatures.SameDescription` the flag,
and `PrototypeSignatures.DescriptionKey` keys `Clauses`, never `ContentRestriction`. The key therefore reads no other identity, so
"the same signature" is a comparison of text: `PrototypeSignatureClasses` (Classify / Admit / blocks / provisional identities),
`BindSession.SignatureClasses`, `BoundCompilation.SignatureClasses`, `StatementBinder.SignatureClasses`, the provider's and
`RepositoryCheck`'s instances and `PrototypeSignatures.CanonicalIdentity` are deleted. What a pointer may CONTAIN (§13.18.60.4
GR25, the SET relation's alone) is `PrototypeSignatures.Identity`, `SIG <hex>` of the namespace and `SignatureKey`, stamped by
`PrototypeSignatures.StampContentRestrictions` from `BinderDriver.ResolvePointerRestrictions` and `RepositoryCodec.Decode`. The
content identities change, so call ABI 6 (`abi_pin.py bump --call-abi`). Sibling arms: the function-prototype pair (§10.6.2 SR3)
shares the code and is pinned by its own refusal; the strong-group member arm already read by name (PB4107); the pair-mode arms
already did (PB4442).

**Goldens.** `10.6-COBOL-compilation-group/pb4491_prototype_pointer_formal_one_prototype` (accepted at 2002: the definition names
the prototype through `REPOSITORY PROGRAM QQ AS "Q1"` and another type-name; `px null`), refusals
`pb4491-prototype-pointer-formal-two-names` (COBOL1513, 2002/2014/2023) and `pb4491-function-prototype-pointer-formal-two-names`
(COBOL1513, 2014/2023). Rewritten for the reading: `_unassigned/pb2495_recursive_prototype_signature` (PS1, PS2 and PS3 are one
signature because every formal names PS3), `pb2495-recursive-prototype-signature-mismatch` (now the mutually naming pair, COBOL1959),
`_unassigned/pb2495_pointer_type_in_signature_checks` (lost the SR2 pair), `12.3.8-REPOSITORY/pb3121_containing_definition_scope`
(the two self-naming prototypes are two signatures; the SET leg sets each pointer to NULL). Unit: `PrototypeSignatureClassesTests`
deleted; `SignatureIdentityDriftTests` (a key holds no identity; TO PBASE vs TO QBASE and QODD vs QEVEN are two signatures),
`PrototypePointerTypeDriftTests.NoSignatureDescriptionReadsWhatAPointerMayContain` with its fail proof,
`PointerRestrictionRelationsTests.TwoPrototypesOfOneSignature_AreTwoDescriptions_AndOneSetClass`.

**Branch review R1-1 (review finisher, wave 20261849 group C).** The first cut compared the TO phrase but not the type
declaration a TYPED pointer formal references, so a prototype `USING TYPE T1` was admitted for a definition `USING TYPE
T9`, both `TO Q1`, and the accepted golden pinned it, though a direct CALL of the definition with an argument of type T1
draws COBOL1688 (§14.8.2.3.2 4), OK; §8.5.3.1 "when they have the same type-name", OK). §8.13 (OK) puts "type declarations
required for the description of parameters and returning items" in the signature, so `PrototypeSignatures.SameDescription`
compares `ActivationDescription.PointerType` (`PrototypeSignatures.PointerTypeOf`; null for an untyped FUNCTION-POINTER TO
formal, which differs from a typed one) and `PrototypeSignatures.DescriptionKey` keys it; the pair-mode relation does not,
since §9.3.8.2.3 rules 3 / 6 (OK 9.3.8.2.3 3)) list only the clauses. Goldens: the accepted golden spells T1 on both sides;
refusals `pb4491-prototype-pointer-formal-two-type-names` (COBOL1513, 2002/2014/2023) and
`pb4491-function-prototype-pointer-formal-typed-untyped` (COBOL1513, 2014/2023); `_unassigned/pb2495_recursive_prototype_signature`'s
PSDEF pair now spells T3 on both sides; `SignatureIdentityDriftTests` gains QPTRT. Sites: `PrototypeSignatures.SameDescription`,
`PrototypeSignatures.PointerTypeOf` (new), `PrototypeSignatures.DescriptionKey`.
