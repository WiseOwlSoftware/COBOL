# PB5324 - `--apply` reports a failed delete of a branch it had just deleted

**Sites:** `scripts/prune_worktrees.py#apply` (the loop over `doomed`: the `r.origin` arm calls `delete_origin`, the
local arm calls `drop_remote`) and `scripts/prune_worktrees.py#drop_remote`.

## What happened

The survey (a dry run with a fetch, then `--apply --no-fetch` two minutes later) held two LANDED rows for one branch:

```
LANDED          origin/worktree-wf_82a7f4cd-626-20 [origin] — MERGED: its work is on main; --apply deletes it
LANDED          worktree-wf_82a7f4cd-626-20 [worktree] — MERGED: its work is on main; --apply deletes it
```

The second row kind is the one kb/Work PB3413 added: a branch of origin whose tip is neither the local branch's tip nor
an ancestor of it is a row of its own, named `origin/<branch>`. `--apply` then printed:

```
deleted origin/worktree-wf_82a7f4cd-626-20
could not delete origin/worktree-wf_82a7f4cd-626-20: error: unable to delete 'worktree-wf_82a7f4cd-626-20': remote ref does not exist
error: failed to push some refs to 'htt
removed 24 branches and their worktrees
```

After it, `git fetch --prune origin` and `git branch -r` showed no `worktree-wf_82a7f4cd-626-20` on origin: the branch
was deleted, once, and the second line reports a failure that did not happen.

## Why it matters

kb/Work PB3409 removed this same line for a branch origin had deleted BEFORE the apply (it prunes the stale tracking refs
first), for the reason its text gives: a `could not delete` line beside a real one hides the real one. This is the
sibling it did not reach: the ref goes stale DURING the apply, because two rows of one survey name the same branch of
origin and each arm deletes it.

## The mechanism, as far as it was read

`apply` walks `doomed` in the survey's order. The `origin/<branch>` row takes the `r.origin` arm (`delete_origin`, which
printed `deleted`); the local row then removes its worktree and branch and calls `drop_remote`, which pushes a second
delete of the branch the first arm removed. Not verified: why `drop_remote`'s own guard (it keeps a remote branch that
holds commits the local one did not) let the second push go out. The implementer reproduces it in the script's
self-test before changing anything: one landed local branch, origin's copy moved on past it and also landed.

## The fix

The apply knows which branches of origin it has deleted in this run; a later row that names one of them has nothing
left to delete and says nothing. The self-test gains the two-row case and asserts that the output holds one `deleted
origin/<branch>` line and no `could not delete` line. The count in `removed N branches` is checked in the same case: it
must count the branch once.
