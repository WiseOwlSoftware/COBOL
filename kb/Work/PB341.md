# PB341 — a scalar where the rules name a set of duplicate sets

**Rows:** `GR-14.9.30.4-26`, `GR-14.9.30.4-32`.

## The programs

**Sequential retrieval** (`out-b1/probe/gr26-altorder/pb3gr26.cob`): an indexed file with `RECORD KEY R-KEY`,
`ALTERNATE R-A1 WITH DUPLICATES`, `ALTERNATE R-A2 WITH DUPLICATES`; WRITE 01/AA/PP then 02/AA/PP; walk on R-A2
(`START KEY NOT LESS` + `READ NEXT`) → 01, 02. Then read 01 by prime key, `MOVE "BB" TO R-A1`, REWRITE; walk on
R-A2 again → **observed 02, 01**.

**Random retrieval** (`out-b1/probe/gr32-firstdup/pb3gr32.cob`): same file, same REWRITE;
`MOVE "PP" TO R-A2 / READ F KEY IS R-A2` returns KEY=01 before and **observed KEY=02 after**.

## The rules

§14.9.30.4 GR26 makes the retrieval order of duplicates under an alternate key of reference the order *in which
they are released by execution of WRITE statements, or by execution of REWRITE statements that create such
duplicate values*; GR32 makes the random read return *the first record in a sequence of duplicates that was
released*. §14.9.35.4 GR24 a) settles which REWRITEs may move a record:

> When the value of a specific alternate record key is not changed, the order of retrieval when that key is the
> key of reference remains unchanged

and GR24 b) confines the last-positioning to *that specific alternate record key*. The REWRITE here changed R-A1
only and created no new R-A2 duplicate, so both the R-A2 walk and the R-A2 random read must still answer 01 then
02.

## What the compiler does

`KeyedRec` carries a single `Arrival` (`KeyedStoreTable.cs`), `IndexedConnector.Ordered(keyIndex)` uses it as the
tie-break for EVERY key, `ReadRandom` picks the minimum `Arrival` among matches, and `IndexedConnector.Rewrite`
collapses the whole alternate loop into ONE bool:

```csharp
if (newValue != KeyOf(target.Image, i) || nowSup != wasSup) altChanged = true;
...
if (altChanged) target.Arrival = _nextArrival++;
```

This is a scalar standing where the rules name a SET: the standard's *set of duplicates* and *logical position
within the set of duplicates* (§14.9.30.4 GR21 f) are PER KEY OF REFERENCE, so the position has to be a VECTOR —
one release ordinal per alternate key — not one per record. The WRITE path is accidentally safe because a fresh
arrival is globally monotone and therefore consistent for all keys simultaneously; only REWRITE can drive the
per-key orders apart, which is why the single number survived.

**It is also PERSISTENT.** `CloseCore` writes the store `_recs.OrderBy(r => r.Arrival)` and `Load` re-numbers
1..n in file order, so a REWRITE-induced misordering of one key is baked into the physical file for every key at
the next CLOSE.

## The fix shape

Give `KeyedRec` a per-key release-ordinal array (the prime slot unused); `Write` assigns the next ordinal for
every key; `Rewrite` re-stamps ONLY the keys whose value or suppression state actually changed — it already
computes that per key in the same loop and throws the per-key answer away. `Ordered()` / `ReadRandom` then read
the ordinal for the key of reference. The same change closes §14.9.35.4 GR24 a)/b) and the §14.9.30.4 GR21 f)
duplicate-set walk, and it is a prerequisite for **PB342**, which needs a duplicate-set position the FPI can
name.

**Code sites:** `IndexedConnector.cs#Rewrite`, `#Ordered`, `#ReadRandom`, `#CloseCore`, `#Load` ·
`KeyedStoreTable.cs#KeyedRec`.

## Landed

Landed 2026-09-05 on the PB341 fix-lane worktree, together with PB342 - one mechanism, one code site, one gate.

`KeyedRec.Arrival` became `KeyedRec.Ordinals`, a VECTOR of release ordinals: slot 0 the prime key, slot `i + 1`
the i-th alternate. `Write` stamps ONE fresh ordinal into every slot (the record is released under every key at
the same instant, ISO 14.9.51.4 GR40). `Rewrite` now runs TWO passes over the alternate keys - pass 1 validates
only, so an early '22' cannot leave a half-repositioned record, and pass 2 re-stamps ONLY the keys whose value or
SUPPRESS WHEN state actually changed (14.9.35.4 GR24 a) keeps an untouched key's order; b) puts the record last
in the changed key's duplicate set, which one ordinal off the monotone mint does for all changed keys at once).
`Ordered(keyIndex)` and `ReadRandom` tie-break on THAT key's ordinal.

Two siblings fell out of the same discarded per-key fact and were fixed with it:

- The "did this key change" test was `newValue != KeyOf(target.Image, i)` - an ORDINAL string compare where
  GR24's closing sentence says *"The comparison used for determining changes to the key is based on the collating
  sequence for the file according to the rules for a relation condition"* (`--check 14.9.35.4` -> OK 24). Under a
  12.4.5.7 alphabet two collating-equal byte strings would have counted as a change and repositioned the record.
  It is `KeyEq` now, and there is ONE definition of "changed" (the local `AltChanged`) that GR24 a), GR24 b),
  GR24's SUPPRESS WHEN sub-rules and 9.1.13.2 2 c) all read.
- REWRITE reported '02' whenever an alternate key value duplicated another record's, changed or not. 9.1.13.2
  2 c) is *"the record just written CREATED a duplicate key value for at least one alternate record key for which
  duplicates are allowed"* (`--check 9.1.13.2` -> OK 2)) - an unchanged key that already duplicated created
  nothing. `duplicateAlt` is now gated on `AltChanged(i)`.

The persistence half is fixed too: `CloseCore` writes `PersistOrder()`, a topological order of the per-key
duplicate orders (one edge per adjacent pair of a duplicate set, Kahn, ties broken by the prime ordinal - the
record's own release order, which is never re-stamped), so a reload - which can only give every key the file's
own order - reproduces every key's order at once. With no REWRITE repositioning this IS release order, so the
on-disk shape of every existing corpus file is unchanged.

RESIDUE, and it is a NEW defect rather than this one: the per-key orders can be made mutually CYCLIC (rewrite one
record's key A into another record's duplicate set while both stay duplicates under key B), and then no single
sequence of record images can carry them - the physical framing has one order and the model has one per key.
`PersistOrder` appends the cyclic residue in release order, losing one key's repositioning across a CLOSE.
Carrying every case needs the per-key ordinals in the physical file, which this framing has no slot for.

`tests/conformance/2023/l1_rewrite_alt_key_order.cob` (L1RWA01 - the REWRITE legs, the random read and the
CLOSE/OPEN survival) and `tests/conformance/2023/l1_start_dup_set_entry.cob` (L1STD01). Both were run against the
pre-fix connector first and are red on it.
