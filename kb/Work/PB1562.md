# PB1562

Found 2026-09-24 by the w59e (PB1053) implementer, a different root cause from PB1053; **first derive from §13.18.43.3
(RECORD clause Format 1) whether a record with dynamic-length members is legal under a fixed-length RECORD clause at
all** — if not, the defect is an UNDER-REJECT and the fix is the diagnostic; if it is, the record must round-trip.
Repro: FD F in `<scratchpad 9db39f61…>\w59e\p1\fixedfmt.cob`. Suspected site: `FileModel.ImpliesVariableFormat` / `IsOutOfLineRecord`.

## Landed (bundle w0930-io)

**Derivation.** §13.18.43.3 SR3 bounds a record description by its MAXIMUM (§13.18.43.4 GR8 b), and PB1276 already gave a
dynamic-length item its maximum size (§8.5.1.10.1) as GR8 b)'s number; `RecordClauseRules` nevertheless skipped every
record holding one ("GR8 has nothing to sum"). So the note's first arm holds for the repro — two unbounded dynamic members
describe up to 2,147,483,585 bytes, far above `RECORD CONTAINS 20` — and the screen was an UNDER-REJECT (COBOLNET2010 now,
SR3 and both SR4 arms; minimum = dynamic items at zero length, §8.5.4 item 4). The second arm also holds for the LEGAL
variant (LIMIT-bounded members totalling 19 bytes): its records must round-trip, and read back mis-split because
`ImpliesVariableFormat` required an ABSENT RECORD clause, so an explicit Format 1 clause gave the file plain 20-byte blocks
that cannot carry the extent table of D-FRA (v). `ImpliesVariableFormat` no longer reads the clause: a file with a
variable-length record frames its records (integer-1 stays the area width and the maximum, SR3 keeping every description
within it). Goldens `conformance:2014/pb1562_variable_group_under_fixed_record_clause` and negatives
`pb1562-record-contains-unbounded-dynamic`, `pb1562-record-varying-range-unbounded-dynamic`,
`pb1562-record-varying-range-below-dynamic-minimum` (COBOLNET2010 at 2014 and 2023). D-FRA (iv)/(v) amended.

## Review finding fixed (w0930 train review, finisher 2026-09-30) — the design above CHANGED
**What the review found.** The landing above made an explicit Format 1 file whose record holds a DYNAMIC LENGTH item register as
VARIABLE (header `RV 3/20`, framed records). A second program describing the same file as `RECORD CONTAINS 20` over `PIC X(20)` —
the SAME §9.1.6 fixed attributes (record type, size) — got OPEN '39' on a relative file and read the framing bytes as data on a
sequential one. §13.18.43.4 GR6 ("Format 1 is used to specify fixed-length records") and §9.1.6 make type and size attributes every
program shares; GR2's "control information required by the operating environment" is information the file's type and size
determine, never one program's record description (the second program's record has no dynamic member).
**The corrected design (D-FRA (vi), docs/CONFORMANCE.md §3).** `ImpliesVariableFormat` requires an absent RECORD clause again, so an
explicit Format 1 file is plain integer-1 blocks in every organization. A record holding variable-length members is carried in its
FIXED FORM (`CobolContiguousLayout.ToFixedForm`): every member at the position it has when it holds its MAXIMUM size
(§13.18.43.4 GR8 b)), space padded; a READ takes each member back at that width and drops the trailing padding
(`Decompose(..., fixedForm)`). Exact round trip for every member that does not end in a space; **the one stated loss is a trailing
space** (padding in a fixed-size field, as §14.9.51.4 GR21 for a line sequential record) — exactness for every value is
information-theoretically impossible in integer-1 bytes (20 bytes cannot hold two dynamic lengths and their content). Mechanism: ONE
place on the way out (`FileConnector.FixedForm`, asked by the registry's governed WRITE / REWRITE and `IndexedConnector.AreaKey`),
ONE on the way in (the READ landing's `fixedForm` flag), `FileModel.FixedFormRecords` the one predicate, `RecordExtents` carries its
layout, an indexed RECORD KEY a dynamic member precedes registers as a plain window at its fixed-form offset. **Found and fixed in the
same files (I9):** `RewriteLengthArg` sent `PhysicalWidth` (the fixed run, 3) for a variable-length record in a fixed file, refusing a
REWRITE that filled integer-1 with '44'. The 20-byte-accepted / 21-byte-rejected negatives are unchanged. Goldens
`conformance:2014/pb1562_fixed_clause_file_second_description` (sequential, relative, indexed, REWRITE, dynamic elementary record,
each read by the writing description and by a plain `PIC X(n)` one) and the amended `pb1562_variable_group_under_fixed_record_clause`;
unit `FixedFormRecordTests`.
