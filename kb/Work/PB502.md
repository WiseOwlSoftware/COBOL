# PB502

## Mechanism — data-description-entry-p3
The `IN alphabet-name-1` phrase of a condition-name VALUE range is recognized by the grammar and then dropped on the floor. CobolData.g4's valueClause carries `(IN IDENTIFIER)?` at the end of the condition-name arm, but BindCondition reads only `range.valueClauseOperand(0)` and `(1)` and stores the pair as raw text; no alphabet is recorded on Condition88, and RenderCondition88 renders the membership test with the program's default collating argument. A range written IN a non-native alphabet is therefore evaluated in the native sequence -- silently, and in BOTH directions (a range that should be non-empty tests false, and one that should be empty tests true).

### Expected, from the standard
13.18.63.4 GR18: 'The manner of determining the range of values specified by the THROUGH phrase is described in 14.7.8, THROUGH phrase.' 14.7.8 rule 2: 'When the IN alphabet-name phrase is specified, the collating sequence used for range evaluation is the collating sequence defined by that alphabet ... The range of values includes all values collating at the starting value and all successive ascending values in the applicable collating sequence up to and including all values collating at the ending value. When the value of literal-1 is greater than the value of literal-2 in the collating sequence in effect at runtime, the EC-RANGE-INVALID exception condition is set to exist, and ... execution proceeds as if the range of values were empty.' Under ALPHA-REV the characters Z..A occupy ordinals 1..26, so P is 11th, M is 14th and D is 23rd. p19 ("P" THRU "D") is the ascending range 11..23, which contains M -> A-RNG=T (observed F). p20 ("D" THRU "P") is inverted, 23 down to 11 -> EC-RANGE-INVALID and an empty range -> A-RNG=F (observed T). Both answers are wrong, in opposite directions.

### Observed
Read: `(IN IDENTIFIER)?` at CobolData.g4 valueClause L623 with no listener; BindCondition's range arm keeps only the two operand texts; Condition88 has no alphabet member; RenderCondition88 passes ctx.CollateArg / ctx.NatCollateArg, i.e. the program-level sequence. Measured: the three probe runs above, whose control isolates the phrase as the only difference. NOTE ON OWNERSHIP: the primary rows are 13.18.63.4 GR18 and 14.7.8 (and 13.18.63.3 SR31, the unchecked syntax rule on which alphabets are legal here), all outside this subject; GR-13.16.4-3 is listed because 'range of values associated with the condition-name' is the constituent this defect corrupts, and it is one of the reasons that row is recorded PARTIAL rather than CONFORMS.

## Mechanism — value-clause-p3
The Format 3 `IN alphabet-name-1` phrase is parsed and then discarded. The grammar carries it (`(IN IDENTIFIER)?` at CobolData.g4:539) but `DataBinder.BindCondition` walks only `value.valueItem()`, `Condition88` has no alphabet member, and `ConditionRenderer.RenderMembershipTest` takes `ctx.CollateArg` — the PROGRAM collating sequence — unconditionally. So the range is evaluated in the wrong sequence, and because nothing resolves the name, an alphabet-name that was never declared is also accepted.

### Expected, from the standard
§13.18.63.4 GR18 defers to §14.7.8: "When the IN alphabet-name phrase is specified, the collating sequence used for range evaluation is the collating sequence defined by that alphabet", and "The range of values includes all values collating at the starting value and all successive ascending values in the applicable collating sequence up to and including all values collating at the ending value." In REV the ordinals are Z=1, Y=2, X=3, so "Z" THRU "X" is ascending and contains "Y" — Y-TRUE. The observed Y-FALSE is the answer for the NATIVE sequence, where "Z" > "X" makes the range inverted and (per the same clause) empty. Separately, §13.18.63.3 SR31 — "Alphabet-name-1 may be specified only when the literals specified in the THROUGH phrase are of class alphanumeric or national ... alphabet-name-1 shall reference an alphabet that defines an alphanumeric collating sequence" — requires the name to be resolved and class-checked, so NOSUCHALPHABET must be a diagnostic.

### Observed
Measured, with a control that flips the axis the subject holds fixed (feedback_probe_the_shape_the_subject_hides): naming the SAME alphabet through PROGRAM COLLATING SEQUENCE proves the collating machinery, the alphabet table and the range renderer all work, so the only missing link is the binder never carrying the per-VALUE-clause alphabet. FIX SHAPE: give Condition88 an alphabet-name member filled in BindCondition, resolve it through the existing alphabet resolver (with the SR31 class check and the undeclared-name diagnostic), and have RenderMembershipTest choose that alphabet's collate argument over ctx.CollateArg — the per-range collate argument is already a parameter of the emitted CobolString.Compare / ThruMember calls, so no new runtime surface is needed. Note the rest of GR18 CONFORMS: numeric ranges (§14.7.8 rule 1) and the native-sequence inverted-range EC-RANGE-INVALID sentence both measured correct (probes gr18_numeric, gr18_ec). A national THROUGH range is separately staged loud (COBOLNET0899 at DataBinder.cs:2124, cited to SR31) and should land in the same change set, since it is the same missing carrier seen from the national side.
