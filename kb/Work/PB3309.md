# PB3309 — a lane for the API credit

## The owner (operator session c95c0b86, 2026-10-16, verbatim)
- "We also have $200 in api use credit to be used before nov 4."
- "I linked acct 1 to my wise owl software org so it got the credit. I could not find a way to link acct 2 the same
  way. All I could do is add it as a member but it's credit didn't apply"

## What was measured
- Account 2's billing page (claude.ai/settings/billing, read 2026-10-16 ~16:15 PDT) says: "Your Max 20x plan includes
  $200 USD in API credits each month. None of your API organizations can be linked. Create one to start receiving
  credits.", followed by a **Create organization** button. So account 2's own monthly credit is still unclaimed. The
  page offers a new organization of its own, not a link to the one account 1 already uses. Creating it is an owner
  action.
- Exchange rate, from the telemetry sink (`scripts/telemetry/usage_report.py --account-uuid c1d721cb-…`, UTC day
  2026-10-16): about $300–340 of API-priced cost (`cost_usd`) for account 2. Over the same span its meter moved
  about 12 weekly points (80 % at 03:39, 92 % at 15:23 PDT). So one weekly point of a Max 20x account is worth about
  $25–30 at API prices, and the $200 credit buys about 7 points, roughly 7 loop-hours at today's pace. Why a point
  costs so much: the API bills cache reads, which the agents use heavily (the largest row, 259 M cache-read tokens,
  was $127), while the subscription meter's calibration counts only input, output and cache writes
  (`model_rules.json` `calibration.counted_token_kinds`).

## What the lane needs
1. **Owner, once:** a Claude Code config dir signed in to the WiseOwl Software API organization: an API key, or
   `/login` with the Console account, in a dedicated `CLAUDE_CONFIG_DIR` such as `~/.claude-api`. No session ever
   handles the key; it is the owner's sign-in, like account 2's (`model_rules.json` `accounts.seed.never`).
2. **An account row of kind `api`** in `model_rules.json` `accounts.list`: its config dir, a dollar cap (the credit,
   less a margin) and an `until` (2026-11-04). The budget for it is measured spend: the sum of the telemetry's
   `cost_usd` since the credit started, not a weekly percentage.
3. **Attribution.** First measure one API-key session's `api_request` events: do they carry `user.account_uuid`, or
   only `organization.id`? `budget.py` counts an event without `user.account_uuid` against EVERY account ("it cannot
   be attributed, and over-counting only holds early"). So if API-key events lack it, the API lane's spend would also
   be charged to both Max estimates. The fix is to attribute by `organization.id` where it is present.
4. **When to spend it.** As overflow, when both Max accounts are held (a `hold-day` under the even pace, or a
   `stop-week`), before 2026-11-04. A run that bypasses the Max accounts while they have headroom would waste the
   credit's deadline advantage.

## Blocked
Blocked on the owner's step 1 (no session may create or handle an API key). Once the config dir exists, steps 2–3
are one implementer's work: account.py, budget.py and the telemetry attribution, plus the design doc's accounts
section (`docs/rearchitecture/DESIGN-orchestrator-loop.md` §2.1).
