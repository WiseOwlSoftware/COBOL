# PB3643 — append-only prose files conflict at landings

**Sites:** `scripts/merge_drivers.py` (`merge_file`, `union_text`, `conflict_hunks`, `hunk_kind`, `history_hunks`, `main`, `self_test`), `tests/WiseOwl.Cobol.Tests.Unit/MergeDriverDriftTests.cs` (`TheSelfTests_DeclareEveryArm`), `docs/rearchitecture/DESIGN-test-build-ci.md` (3.17.2 step 3).

## What happens

PB3610's measurement of 487 landing logs found prose docs among the files landings stop on: `DESIGN-runtime-library.md` 5 times and `CONFORMANCE.md` 2. Both are append-only prose, where two branches each append a section. `merge_drivers.py` has drivers for keyed JSON, work notes and the ABI pin, but none for these, so each such landing still costs a finisher cycle.

## Fix direction

Measure the current rate with `python scripts/merge_drivers.py --conflicts`. If it holds, add a union driver for append-only prose (git `merge-file --union` is already used for note bodies) to `DRIVERS`, restricted to files whose edits are appends, and let `--check` and `MergeDriverDriftTests` pin it.

## Source

Report `w20261029b-PB3610-report.md` (PB3610, landed in PR #496), new defect 2.

## Retired 2026-10-25 (wave 20261107, group H): the premise is false, and the measurement is now a command

The fix direction was conditional ("if the rate holds, add a union driver for append-only prose, restricted to files whose
edits are appends"). The rate holds (`merge_drivers.py --conflicts E:/COBOL-coord/logs`: `DESIGN-runtime-library.md` 5 and
`CONFORMANCE.md` 2 of 541 landing logs), but the condition does not: these files are NOT append-only where they conflict.

`python scripts/merge_drivers.py --hunks docs/CONFORMANCE.md docs/rearchitecture/DESIGN-runtime-library.md docs/rearchitecture/DESIGN-test-build-ci.md`
replays every merge in history that touched the file (git's line merge of the merge base and the two parents, `--diff3`)
and classifies each conflict hunk by whether its base section is empty (both sides inserted at one place) or not (both
sides changed text the base already held):

| file | merges both parents changed | conflicted | insertion hunks | revision hunks |
|---|---|---|---|---|
| `docs/CONFORMANCE.md` | 199 | 17 | 1 | 31 |
| `docs/rearchitecture/DESIGN-runtime-library.md` | 59 | 22 | 1 | 79 |
| `docs/rearchitecture/DESIGN-test-build-ci.md` | 50 | 6 | 1 | 5 |

So 45 conflicted merges hold 3 insertions and 115 revisions: the branches revised the same paragraph of a mechanism (the
re-OPEN's kept-lock paragraphs of 2.2.1.8 and 2.2.1.10, across PB3480, PB3482, PB3483, PB3498) or the same Annex A.1
register row, each into a different final text. Three candidate drivers were judged against 32 conflicted merges (as the first walk listed them) of
the first two files (the last two as prototypes that were run and are not kept):

- **Union (`git merge-file --union`, the work-note body rule):** by construction it keeps both rewrites of a revised
  paragraph, the stale text beside its replacement, in documents that must describe the CURRENT compiler (CLAUDE.md rule
  6); not run, because 115 of 118 hunks are such revisions. The work notes can accept it because a note's body is a dated
  narrative.
- **Insertion-only (keep both where the base section is empty, else decline the file):** resolved 1 of 32, and in a
  different order from the person's resolution.
- **Word-level three-way merge of the conflicting hunks:** resolved 9 of 32, 6 identical to the person's resolution and 3
  not: it kept text the person had removed (merges `1fbec0fc6` and `90fc2692c`, `DESIGN-runtime-library.md`). A wrong
  prose merge passes every gate, which is worse than the conflict a finisher resolves.

Such a conflict is a decision about what the text now says, so it stays the finisher's (exit 4). Kept: `--hunks` (the
classification, with `conflict_hunks` and `hunk_kind`, self-tested and pinned by `MergeDriverDriftTests`), and the module
docstring and `DESIGN-test-build-ci.md` section 3.17.2 step 3 stating that prose has no driver and why, so the idea is
measured again rather than rebuilt. The same-paragraph conflicts are the parallel-groups-on-one-file class the planner's
partition owns (PB3640, PB3670), not the merge's.

Review round 1 (R1-1): the first walk used git's default history simplification and undercounted (it dropped merges
TREESAME to one parent and varied with the other paths asked about); the table above is the `--full-history`, one-walk-per-path
count. The word-level and insertion-only trials were run on the first walk's 32 merges; the larger set changes no conclusion.
