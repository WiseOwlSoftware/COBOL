# PB2152 — the oracle's first catch

**Measured 2026-10-07 04:45 PDT on main `f9bcff6d4`** (after trains 1028 and 1029): `python scripts/arch/compare_oracle.py`
against the committed baseline `docs/rearchitecture/evidence/arch-oracle/f620ccf6d43d.manifest.json` printed
`=== ARCH-ORACLE: DIFFERENT — 39 of 7361 cases differ (baseline f620ccf6d43d, new f9bcff6d46e3) ===`. The differing cases:
35 `CSHARP nist/...` rows (NC220M, NC221A, NC224A, NC244A, NC245A, NC246A, NC248A among them) and four `DIAGNOSTICS` rows:
`negative/l1c08-entry-name-subscripted`, `negative/l1c17-paren-not-delimiting`,
`negative/pb1372-cobol-words-undefined-picture-syntax-withdrawn`, `negative/pb1455-subscript-before-qualifier`. Three
cases were ADDED by the trains (`corpus/2002/pb2113_subscript_expressions_and_arguments`, `corpus/85/pb2113_subscript_list_separators`,
`negative/pb1968-subscript-unary-unary`, `negative/pb2113-keyword-omitted-arguments-85`): additions are expected.

Every gate was GREEN on both trains (Windows and Linux, the NIST leg at 364 programs), so the PROGRAM OUTPUT is unchanged and the
C# differences are shape, not behavior — exactly the class the oracle exists to catch (DESIGN-architecture-review §4: "a refactor
can change behavior through registration order, static initialization or a shared cache while every test stays green"). The four
diagnostic differences are the serious ones: §4 item 2 requires the same codes, severities, positions and messages, and the
negative fixtures' assertions are coarser than the oracle's hash, so a changed message or position passes the gate and fails
the contract. D10 (PB2113) replaced the hand-rolled subscript parsers with grammar rules, which is the likely origin of all four.

## The work (one Opus implementer; cluster `PB2108`, so `plan_wave.py --cluster PB2108` plans it)

1. Both sides' blobs: capture the baseline commit into a detached worktree (`git worktree add --detach <path> f620ccf6d43d`, then
   `python scripts/arch/capture_oracle.py` there) and copy its `TestResults/arch-oracle/f620ccf6d43d/` beside main's
   `f9bcff6d46e3/`; then `python scripts/arch/compare_oracle.py --diff` shows every hunk. (PB2116's design: blobs are local and
   gitignored; the manifest is the record.)
2. Classify each of the 39 by mechanism, not one by one: the emitted-C# hunks (a subscript or reference-modification expression
   rendered differently after D10? the unified `sendingOperand` binding path after PB2114?) and the four diagnostic hunks (code,
   severity, position or message changed?). Write the classes into this note's Landing section.
3. A diagnostic that got WORSE (a less specific code, a position off the construct, a message that names the wrong thing) is a
   `kind: defect` note for the fix lane (ids from the orchestrator's block), cited to the rule the negative fixture witnesses; a
   diagnostic that got BETTER is explained here and the fixture's expectation tightened so the gate would catch the next change.
   An emitted-C# difference that is a pure re-rendering with identical semantics is explained by class; one that is not is a
   defect note.
4. Re-record the baseline on the explained tree: `python scripts/arch/capture_oracle.py --record` (the manifest is committed;
   `ArchOracleDriftTests` pins it), and state in the DEVLOG entry the 39 cases by class.
5. The process gap that let this through: the lander brief did not run the oracle after a train. Fixed in the same commit that
   files this note (`lander-train-brief.md` step 3c, MANDATORY-PRACTICES L11, `check_practices.py`): a lander runs
   `compare_oracle.py` after its gate, explains every difference in the train's DEVLOG entry by class, re-records the baseline
