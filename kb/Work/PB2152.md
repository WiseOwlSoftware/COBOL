# PB2152 — the oracle's first catch

**Measured 2026-10-07 04:45 PDT on main `f9bcff6d4`** (after trains 1028 and 1029): `python scripts/arch/compare_oracle.py`
against the committed baseline `docs/rearchitecture/evidence/arch-oracle/f620ccf6d43d.manifest.json` printed
`=== ARCH-ORACLE: DIFFERENT — 39 of 7361 cases differ (baseline f620ccf6d43d, new f9bcff6d46e3) ===`. The differing cases:
35 `CSHARP nist/...` rows (NC220M, NC221A, NC224A, NC244A, NC245A, NC246A, NC248A among them) and four `DIAGNOSTICS` rows:
`negative/l1c08-entry-name-subscripted`, `negative/l1c17-paren-not-delimiting`,
`negative/pb1372-cobol-words-undefined-picture-syntax-withdrawn`, `negative/pb1455-subscript-before-qualifier`. Three
cases were ADDED by the trains (`corpus/2002/pb2113_subscript_expressions_and_arguments`, `corpus/85/pb2113_subscript_list_separators`,
`negative/pb1968-subscript-unary-unary`, `negative/pb2113-keyword-omitted-arguments-85`): additions are expected.

Every gate was GREEN on both trains (Windows and Linux, the NIST leg at 364 programs), so the PROGRAM OUTPUT is unchanged and the
C# differences are shape, not behavior — exactly the class the oracle exists to catch (DESIGN-architecture-review §4: "a refactor
can change behavior through registration order, static initialization or a shared cache while every test stays green"). The four
diagnostic differences are the serious ones: §4 item 2 requires the same codes, severities, positions and messages, and the
negative fixtures' assertions are coarser than the oracle's hash, so a changed message or position passes the gate and fails
the contract. D10 (PB2113) replaced the hand-rolled subscript parsers with grammar rules, which is the likely origin of all four.

## The work (one Opus implementer; cluster `PB2108`, so `plan_wave.py --cluster PB2108` plans it)

1. Both sides' blobs: capture the baseline commit into a detached worktree (`git worktree add --detach <path> f620ccf6d43d`, then
   `python scripts/arch/capture_oracle.py` there) and copy its `TestResults/arch-oracle/f620ccf6d43d/` beside main's
   `f9bcff6d46e3/`; then `python scripts/arch/compare_oracle.py --diff` shows every hunk. (PB2116's design: blobs are local and
   gitignored; the manifest is the record.)
2. Classify each of the 39 by mechanism, not one by one: the emitted-C# hunks (a subscript or reference-modification expression
   rendered differently after D10? the unified `sendingOperand` binding path after PB2114?) and the four diagnostic hunks (code,
   severity, position or message changed?). Write the classes into this note's Landing section.
3. A diagnostic that got WORSE (a less specific code, a position off the construct, a message that names the wrong thing) is a
   `kind: defect` note for the fix lane (ids from the orchestrator's block), cited to the rule the negative fixture witnesses; a
   diagnostic that got BETTER is explained here and the fixture's expectation tightened so the gate would catch the next change.
   An emitted-C# difference that is a pure re-rendering with identical semantics is explained by class; one that is not is a
   defect note.
4. Re-record the baseline on the explained tree: `python scripts/arch/capture_oracle.py --record` (the manifest is committed;
   `ArchOracleDriftTests` pins it), and state in the DEVLOG entry the 39 cases by class.
5. The process gap that let this through: the lander brief did not run the oracle after a train. Fixed in the same commit that
   files this note (`lander-train-brief.md` step 3c, MANDATORY-PRACTICES L11, `check_practices.py`): a lander runs
   `compare_oracle.py` after its gate, explains every difference in the train's DEVLOG entry by class, re-records the baseline
   in the train commit, and drops a cluster whose difference it cannot explain.

## Landing (wave 1030 A, 2026-10-07)

Re-measured on `3f0604783` (code-identical to `f9bcff6d4`) against a fresh capture of `f620ccf6d43d` (which reproduced
the recorded manifest hash for hash): 39 of 7,361 cases differ, as the note says, but the split it gave was wrong —
**31 CSHARP (15 corpus goldens, 16 NIST programs, not 35 NIST), 4 DIAGNOSTICS, 4 ADDED**. By class:

- **Whitespace inside a rendered position (29 CSHARP: 13 corpus, all 16 NIST).** `_IX_1  +  1` became `_IX_1 + 1`.
  The token renderer (`ReferenceResolver.RenderSegment`) appends `" + "` per operator; the retired SUBSCRIPT-mode
  token run carried its own spacing, the parse node's leaf tokens (PB2113) carry none. Identical C# semantics
  (each of the 29 files is equal to its baseline once runs of spaces collapse to one).
- **A parenthesized subscript after a non-table name goes to the expression binder (1 CSHARP, `pb136_subscript_expressions`).**
  `DOG (XCOUNTER (- YCOUNTER + 3))`: the inner '(' is now the reference paren `REF_LPAREN` (PB2113), for which the token
  renderer deliberately has no arm (GROUPING-PAREN-ONLY), so the segment takes the D18 route — the expression binder
  plus a position temporary, integrality tested once on the result (ISO §8.4.2.3.4 1) b)). Same value; the
  temporaries renumber. Neutral, and PB2151 moves every position onto that route.
- **A user-defined function's argument inside a subscript is a BY REFERENCE operand (1 CSHARP, `pb17_function_subscript`).**
  `W-E (FUNCTION PB17PICK(W-X))`: the argument is now a `functionCall` node, so `DataBinder.ScanByReferenceOperands`
  (PB2087) sees it and W-X moves onto a `StorageCell` that crosses with its area, exactly as the same argument does
  outside a subscript (ISO §14.2.3 8): the formal "occupies the same storage area as the argument"). BETTER: the
  scan used to miss it only because the subscript was a flat token run.
- **A cascading second parse error (3 DIAGNOSTICS: `l1c08-entry-name-subscripted`, `l1c17-paren-not-delimiting`,
  `pb1372-cobol-words-undefined-picture-syntax-withdrawn`).** WORSE, and FIXED here rather than filed (I9): each
  gained `COBOL0307: unexpected ')'` after its one real error. The integer inside `A(1)` / `X(3)` resynchronized as a
  level-number once the reference paren became its own token, and `DISPLAY (W-S)` recovered by single-token deletion
  of the '(' alone, orphaning the ')'. ISO §8.3.5 4) ("parentheses may appear only in balanced pairs") makes a group
  one unit: `CobolErrorStrategy.ConsumeUntil` now consumes a group it meets while resynchronizing whole (stopping at
  the separator period or end of file) and `SingleTokenDeletion` never deletes a '('. All three streams are back to
  the baseline's, no other negative fixture's stream moved, and `ParseRecoveryParenGroupTests` (Unit; red on the old
  strategy, green on the new) asserts the COUNT the fixtures' substring match cannot.
- **A position corrected (1 DIAGNOSTICS, `pb1455-subscript-before-qualifier`).** `DISPLAY X (E (1) OF T)` now reports
  COBOLNET2776 at column 29, where `OF` is written; the SUBSCRIPT-mode capture reported 30. BETTER; the fixture's
  `.err` now expects `(23,29): error COBOLNET2776`, so a position regression fails the gate.
- **4 ADDED** — PB2113's and PB1968's new goldens and negatives.

**Re-recorded.** On the implementer's branch the re-recorded baseline (`a468b3dd1676`, the commit carrying the fix)
compared IDENTICAL. Main had meanwhile re-recorded twice (trains 1031 and 1031b, `ef2b7cb6250c`, with the cascade still
in it), so the train-1033 lander measured this fix against `ef2b7cb6250c` on the train's tree — the three cascade
negatives (`l1c08-entry-name-subscripted`, `l1c17-paren-not-delimiting`, `pb1372-cobol-words-undefined-picture-syntax-withdrawn`)
lose exactly their spurious `COBOL0307 unexpected ')'` and nothing else of this note's moved — and re-recorded the
baseline on the train's tree in the train's own commit (DEVLOG entry 1919).
