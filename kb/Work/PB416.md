# PB416 — four operand screens INITIALIZE never asks, at the one place identifier-1 is resolved

Adjudicated in lane-3 batch b2 (`initialize-statement` part 1). **All four repros re-measured on HEAD
89044aa0**, each with the control that isolates it.

## 1. The mechanism

All four rules live at one place — `InitializeBinder.BindInitializeTarget`
(`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs:90-136`) and the REPLACING loop in
`Bind` (`:44-62`) — and none of them is asked there.

* **Syntax rule 1 (identifier-1's class) is unwritten.** Of the nine COBOL classes the rule admits eight and
  excludes exactly one — index — so the whole rule is one predicate at the one place identifier-1 is
  resolved. What *looks* like coverage is a different rule answering a different question:
  `InitializeItemCategory` (`:233`) returns null for `{ Usage: Usage.Index }`, which is general rule 5's
  step a1 exclusion of items **contained in** identifier-1 from the receiver set. Applied to identifier-1
  *itself* that exclusion converts a syntax error into a **silent no-op**. The exclusion's own behaviour is
  correct and must survive the fix — which is precisely why syntax rule 1 needs its own screen rather than a
  widening of the exclusion.
* **Syntax rule 4 (the implied MOVE must be valid) is unwritten, and the table it needs already exists.**
  `MoveTable16.Refusal` (`src/Cobol.Net.Compiler/Binding/MoveTable16.cs:88`) is the single home of the move
  validity table; its four call sites are `MoveBinder.cs:235`, `MoveBinder.cs:245`, `OoBinder.cs:757` and
  `AcceptDisplayBinder.cs:107`. `InitializeBinder` is not among them, and `InitializeEmitter` synthesises a
  `BoundMove` directly (`InitializeEmitter.cs:46`), so `MoveBinder`'s checks are structurally unreachable from
  here. Every refused cell that an explicit MOVE rejects, `INITIALIZE … REPLACING` accepts and stores.
  Because syntax rule 4 is stated per **category**, not per actual receiver, the check is a pure bind-time
  screen of each (category, sender) pair and needs no receiver walk at all.
* **Syntax rule 5 (no RENAMES on identifier-1) is written, cited and DEAD.**
  `StatementValidation.CheckInitializeTargetRenames` (`Validation/StatementValidation.cs:180-186`) raises
  COBOLNET0835 quoting the rule. Its **only** call site is `InitializeBinder.cs:112`, inside the failure arm of
  `if (ctx.Refs.Resolve(dref) is not { } place)` — it runs only when the reference does **not** resolve. A
  66-level RENAMES entry *does* resolve; it falls through to the `cursor is null` arm at `:130` and becomes an
  `InitializeErrorAction`, i.e. a run-time `NotImplementedCobolFeatureException` with a misleading message.
  The check belongs on the RESOLVED path — the resolved `DataItem.Renames` field is already what the general
  rule 5 a3 subtree walk consults twenty lines below, so the rule and its data are in the same method and only
  the arm is wrong.
* **Syntax rule 7 (identifier-1 IS the receiving operand) is honoured as a designation and not as a
  consequence.** identifier-1 resolves to a Place and every expanded store writes through it, and a
  function-identifier is correctly refused there. But making identifier-1 the receiving operand subjects it to
  the receiving-operand prohibitions, and INITIALIZE asks none of them. The clearest case:
  `DataBinder.Constants.cs:96 RejectConstantStore` (COBOLNET1548) implements the CONSTANT RECORD prohibition
  and has a negative golden proving it fires for MOVE — and INITIALIZE never consults it, so a structured
  constant is silently destroyed at run time.

## 4. The code site and the shape of the repair

* `.../Verbs/InitializeBinder.cs:90-136` `BindInitializeTarget` — where the class screen and the
  receiving-operand screen belong, and where the RENAMES call site is on the wrong arm (`:112` vs the resolved
  path at `:120`/`:135`).
* `.../Verbs/InitializeBinder.cs:44-62` `Bind` — the REPLACING loop, the missing `MoveTable16.Refusal` call site.
* `.../Binding/MoveTable16.cs:88` `Refusal` — the screen, with four callers, none of them INITIALIZE.
* `.../Binding/Validation/StatementValidation.cs:180-186` — the dead check.
* `.../Binding/DataBinder.Constants.cs:96` `RejectConstantStore` — the receiving-operand screen INITIALIZE
  never asks; `.../Binding/Procedure/ExpressionBinder.cs:709-710` is the chokepoint that does ask it.
* `.../CodeGen/Verbs/InitializeEmitter.cs:46` — the direct `BoundMove` synthesis that bypasses `MoveBinder`.

**The structural repair (CLAUDE.md rule 5), not four patches.** Syntax rules 1, 5 and 7 are all *screens on
identifier-1 at the moment it is resolved*, and syntax rule 7 is not one check but a *funnel*: the standard's
receiving-operand prohibitions are a set that will keep growing. Give `BindInitializeTarget` the same
receiving-operand funnel `ExpressionBinder` already uses for a resolved Place, rather than bolting a second
CONSTANT RECORD test onto INITIALIZE — then the next prohibition is automatic. Syntax rule 4 is the other
half: one call to `MoveTable16.Refusal` per (category, sender) pair in the REPLACING loop, which needs no
receiver walk because the rule is stated per category.

## 5. The sibling sweep the fixer must do

* **The other arm of the same dispatch.** `MoveTable16.Refusal`'s callers are MOVE, OO argument passing and
  ACCEPT/DISPLAY. Ask which verbs *synthesise* a move without going through `MoveBinder` — INITIALIZE is one;
  check the rest of `CodeGen/Verbs` for the same shape.
* **The explicit-MOVE sibling gap, found on the way and MEASURED on HEAD:** `MOVE ZERO TO <PIC A(4)>` is
  accepted too — probe `run/misc/g4_move_zero_alpha.cob`, `exit=0`, `AB=[0000]`. The figurative-ZERO
  prohibition is unimplemented **on the explicit MOVE path as well**; `MoveTable16`'s own header leaves that
  shape rule to `MoveBinder`, and `MoveBinder` does not have it. That belongs to §14.9.25.3's own rows, not
  to this note's — recorded here so the fixer does not "discover" it a second time.
* **Every receiving-operand prohibition, not just CONSTANT RECORD.** Whatever `ExpressionBinder`'s receiving
  chokepoint asks, INITIALIZE must ask; enumerate them once when the funnel lands.
* **The dead-call-site pattern.** `CheckInitializeTargetRenames` is a check wired to a branch that cannot reach
  its subject. Grep `StatementValidation` for other checks whose only call site sits in a failure arm — a
  check nothing can reach has never been contradicted.
