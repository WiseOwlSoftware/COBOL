## The owner's question and decision

The owner, 2026-10-25 ~11:10 PDT: "I do not understand why I'm reading occasional output suggesting that we serialize some parts … I thought that issue was precisely what branches were for. Why can't we parallize using multiple branches then merge". The operator explained that branches isolate the work but not the merge, that the planner serializes only two groups on one member and a change that rewrites what the others touch, and proposed measuring wave 20261107's two same-file pairs, which PB3696's gap let run side by side. The owner: "letting that result decide."

- **D (`500-4`, PB3113 group) and H (`500-9`, PB3643 group), planned to share `merge_drivers.py#DRIVERS`.** Neither edited `DRIVERS`; their `merge_drivers.py` changes merge cleanly (`git merge-tree`). So the member partition reasoned about the wrong units. The conflicts come from points every change touches by rule and never declares: a script's single `self_test()` (MANDATORY-PRACTICES: a fix ships its test) and the design-doc paragraph of its mechanism (CLAUDE.md rule 6: docs current in the same change). Each conflict costs a CONFLICT finisher, a re-gate, a review of the finisher's diff and another trip through the queue (PR #505 on 2026-10-24 was the same shape).

## Two queue conflicts resolved before they bounced (2026-10-25 ~20:59-21:26Z, the loop's enqueue unit)

The enqueue unit simulated the merge queue in order (each entry's head merged with `git merge-tree` onto the previous result, starting from origin/main) and found two entries that would conflict with one ahead of them. GitHub marked #586 UNMERGEABLE. Instead of waiting for the `merge_conflict` removal, it sent each one ONE conflict finisher, which merged the queued predecessor's head through `merge_drivers.py merge --keep`. One re-review per branch then covered only the merge.

- **#580 (D, `500-26`) behind #579 (H, `500-24`).** The conflict was in `docs/rearchitecture/DESIGN-test-build-ci.md` §3.17.2 step 3, after "… a hand resolution is not." (merged-file lines 2274-2290). It is one hunk in which BOTH sides rewrote the same base sentence, so it is revise/revise, not the insert/insert the simulated merge suggested. A union would have kept the trailing "What is left in conflict is real (…" clause twice. The finisher resolved it by hand, ordering the paragraphs drivers, PB3643, PB3714, then the closing clause. The finisher took 10 min (20:59:44-21:09:46Z: about 2 for the merge and 8 for the gate, GREEN on both hosts). The review was CLEAN at `c9848c707`.
- **#586 (E, `500-20`) behind #576 (C, `500-21`).** The conflict was in `.claude/skills/workstream/templates/MANDATORY-PRACTICES.md`, the O10 row, one table row of about 4 KB on ONE line (merged-file line 106). Both sides edited different sentences of it: E for PB3713 and PB3409, C for PB3118. The finisher applied the three edits once each to the base row; C's O2 and O11 edits merged as written. A key-based driver cannot resolve this (the file is prose) and a line-level merge cannot either (the row is one line). A three-way merge at word or sentence level within the line would have, because the edits did not overlap. The finisher took about 12 min (21:14:03-21:25:50Z, about 9 of them the gate, GREEN on both hosts).

A third append point, then: a long single-line markdown table row (MANDATORY-PRACTICES' rows) is shared by every change that states a practice. Two edits that do not overlap still conflict there, because git compares lines. Both finishes ran while the predecessor was still in the queue, so each branch now carries its predecessor's stamped DEVLOG entry and lands after it (exit 15). The bounce, its finisher, a second gate of the bounced head and its trip back into the queue were all avoided.

## Fix direction (branches and merge, the owner's model)

1. **Insert/insert hunks resolve themselves where both sides only added lines at one place.** PB3643's classifier (`merge_drivers.py --hunks`, `hunk_kind`) already tells an insert/insert hunk from a revise/revise one. For a test arm (an independent block in `self_test`), keeping both insertions is correct by construction; the merge queue's CI then runs the merged tests. Either give the drivers an insert-only resolution scoped to that, or restructure the self-tests so two additions never land at one place (one function per case, collected by a registry), whichever makes the next case automatic (rule 5).
2. **Prose.** PB3643 measured 37 insert/insert and 89 revise/revise conflict hunks over `CONFORMANCE.md`, `DESIGN-runtime-library.md` and `DESIGN-test-build-ci.md`, and refuted a general prose driver. The D/H case, read as insert/insert from the simulated merge, proved revise/revise when it was resolved (the measurement below), and the E/C case was a single-line row; decide from that same history whether an insert-only resolution (refusing every revise/revise hunk) would have matched the person's resolutions, and adopt it only if it would.
3. **Measure.** Conflicts per landing among same-file parallel groups, before and after, from the landing records and the land-lane conflict briefs.
4. **See a queue conflict before GitHub removes the entry.** The enqueue unit's 2026-10-25 simulation (`E:/COBOL-coord/scratch/tmp/simulate_queue.sh`: the queue's entries in order, each merged with `git merge-tree` onto the previous result) was done by hand. The landing survey should do it on every tick, through the merge drivers, and list such an entry as a stopped row (a FORESEEN CONFLICT, with the entry ahead it conflicts with) so its finisher runs while the predecessor is still in the queue. A `merge_conflict` removal records no failed run, so today nothing reads it (kb/Work PB3772).

Any resolution a driver makes stays visible to the review's coverage rule (`prune_worktrees.mechanical`, `is_drivers_merge`), and a revise/revise hunk always stays a conflict for a finisher.
