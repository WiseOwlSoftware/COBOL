# PB3510 — the binder overflows the stack on ODO DEPENDING ON an ancestor group

## Scenario (fuzz program fz01530, `WE_CRASH:no-code`, clause 8.5.1.11)

Confirmed on a fresh build of origin/main at fd407980f (`cobol.exe` built 2026-10-22 09:25 PDT), `--std 2014
--source-format free`. GnuCOBOL 3.2 refused the fuzz original:
`fz01530.cob:6: error: group item 'WS-VARYING-LEN' cannot have PICTURE clause`. WiseOwl dies with "Stack overflow."

### Reduced repro (crashes; `rc 3221225725`, "Stack overflow." in under 1 s)

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. MINC1.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 WS-G.
   05 WS-H.
      10 WS-T OCCURS 1 TO 5 TIMES DEPENDING ON WS-G PIC X.
PROCEDURE DIVISION.
MAIN-PARA.
MOVE "A" TO WS-T(1)
DISPLAY WS-G
STOP RUN.
```

The fuzz original is the same shape with the PICTURE fault added (`01 WS-VARYING-LEN PIC S9(4)` followed by a level-05
ODO entry, so the "elementary" item becomes the ODO group AND data-name-1): it crashes the same way.

## Expected (spec)

Two syntax rules are violated and the compiler must report them and stop; it must never crash on any input. Each
citation below was re-run through `python scripts/spec/cite.py --check` on 2026-10-22 and returned OK.

- §13.18.38.3 SR17 (OK): "Data-name-1 shall describe an integer." A group item is not an integer data item.
- §13.18.38.3 SR20 (OK): "The data item defined by data-name-1 shall not occupy a byte position within the range of the
  first byte position defined by the data description entry containing the OCCURS clause and the last byte position
  defined by the record description entry containing that OCCURS clause." The containing group occupies every such
  position.
- fz01530's extra fault, §13.18.40.3 SR1 (OK): "The PICTURE clause may be specified only at the elementary level." WiseOwl
  already reports this as COBOLNET2191 when the subordinate entry is a FIXED OCCURS or a plain item; see the sibling table.

Both SR17 and SR20 already have diagnostics: COBOLNET0852 (SR17, `src/Cobol.Net.Compiler/Binding/DataBinder.Odo.cs`
about line 422) and COBOLNET0857 (SR20; variants c2 and c3 below print it). Neither reaches the user here because the
crash comes first.

## Mechanism (read in `src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs`)

`WrapIfOdoGroup(Place place, DataItem item)` (about line 1161) wraps a GROUP whose subtree holds an occurs-depending
table by resolving the table's depending item: `ResolveItem(dep)` → `PlaceForItem(dep, [])` → (dep is a group that
contains the same table) → `WrapIfOdoGroup(dep)` → `ResolveItem(dep)` … with no termination. The stack trace repeats
`PlaceForItem → ResolveItem → WrapIfOdoGroup → PlaceForItem` 964 times from `ExpressionBinder.ResolveReceiving` (the
MOVE's receiver). The assumption "data-name-1 lies outside the group" is SR20's rule, which the resolver relies on
without the data binder having enforced it before the procedure division is bound.

## Fix shape (for the implementer)

Root-cause shape to require (CLAUDE.md rules 4 and 5): the OdoModel must never record a `Depending` link to an item that
violates SR17/SR20 (an ancestor of the table, an item inside the table, a non-integer), so no consumer can cycle: the
diagnostics fire in the data binder and the spec's `Depending` is left unset (or the unit's binding stops at the data
division errors). A cycle guard inside WrapIfOdoGroup alone is a workaround and is not acceptable. Sibling sweep: every
consumer of `OccursSpec.Depending` (grep; `SendingValueTemp.cs` and `NumericRenderer.cs` also name WrapIfOdoGroup).

## Sibling probe results (same build; all four written by the Mythos session, in the scratchpad)

| Variant | DEPENDING ON names | Result on main |
|---|---|---|
| c1 (above) | the group containing the table (an ancestor) | **Stack overflow** |
| c2 | an item INSIDE the table (`05 T OCCURS … DEPENDING ON N. 10 N PIC 9.`) | COBOLNET0853 (SR2) + COBOLNET0857 (SR20) — correct |
| c3 | an item AFTER the table in the same record | COBOLNET0856 + COBOLNET0857 — correct |
| c4 | an item BEFORE the table in the same record (legal) | compiles and runs (the lock error seen once was this session's own orphan process, not the compiler) |
| fixed OCCURS under a PIC'd parent (no DEPENDING) | — | COBOLNET2191 (§13.18.40.3 SR1) — correct |

So the crash needs exactly: DEPENDING ON naming an ANCESTOR of the table (c1), with or without a PICTURE on that ancestor.

## Golden to require

A conformance case that expects COBOLNET0852 and COBOLNET0857 (and COBOLNET2191 for the fz01530 shape) and no crash;
plus a drift test that every `OccursSpec.Depending` consumer cannot see an ancestor-of-the-table depending item.

## Why the fuzz saw it

The differential (PB3463/PB3488) classified fz01530 `WE_CRASH:no-code`: GnuCOBOL refused the program with a
diagnostic, WiseOwl crashed with no diagnostic code at all. The evidence record and the DEVLOG entry are added by a
later pass.
