# PB42 — LANDED 2026-08-04 — a SUBSCRIPT or REF-MOD position containing `**` or a decimal literal compiles clean and throws

> ⚙ **FOUND BY THE [[PB17]] SWEEP, NOT BY LOOKING FOR IT** (CLAUDE.md rule 4 — every bug is a pattern). PB17 fixed
> ONE token the segment renderer could not render (a function-identifier). The sweep asked what ELSE its
> `default:` arm drops, and two of the four answers turned out to be plain legal arithmetic.

**MEASURED (2026-08-04, on the PB17/PB41 tree, before the fix):**

```cobol
01 W-G.
   05 W-E PIC 9(2) OCCURS 9 TIMES.
01 W-I PIC 9 VALUE 2.
...
    MOVE W-E (W-I ** 2) TO W-R      *> -> NotImplementedCobolFeatureException: reference 'W-E(W-I ** 2)'
    MOVE W-E (2.0)      TO W-R      *> -> NotImplementedCobolFeatureException: reference 'W-E(2.0)'
```

Both compile clean and throw at RUN TIME — the PB7/DA7/PB17 **wrong-stage** family, with PB17's own exception
message.

⚠ **`**` LOOKED HANDLED AND WAS NOT.** `SUB_POWER` appears in `RenderSegment`'s new compound-segment predicate
but in **no `case` arm**, so a `**` segment only ever worked by accident: when an operand happened to be SCALED,
the [[PB41]] compound rule diverted the whole segment to the materializer before the renderer reached the `**`
token. With unscaled operands — the ordinary case — it fell to `default:` and died. **A probe that measures only
the scaled shape reports this as working.**

## ⛔ BOTH ARE LEGAL SOURCE

Every citation `cite.py --check`ed.

| # | clause | what it gives |
|---|---|---|
| 1 | **§8.4.2.3.2** | a subscript may be `arithmetic-expression-1`; **§8.4.3.3.3 SR4** the same for a ref-mod position |
| 2 | **§8.8.1.1** | "An arithmetic expression may be an identifier referencing a numeric data item, **a numeric literal**, the figurative constant ZERO …, such identifiers, figurative constants, and literals **separated by arithmetic operators**" |
| 3 | **§8.3.2.4.2** | `**` IS an arithmetic operator — "Arithmetic operator - exponentiation" |
| 4 | **§8.4.2.3.4 GR1b** | the subscript is "the result of the evaluation"; a non-integer result sets EC-BOUND-SUBSCRIPT |

So `W-E(2.0)` is occurrence **2** — 2.0 IS an integer value — and only `W-E(2.5)` raises. The decimal literal was
never an error; it was an unrendered token.

## ✅ THE FIX IS [[PB17]]'S OWN MECHANISM, WIDENED BY EXACTLY THE CLAUSES ABOVE

D18's route already exists: *a segment the token renderer cannot render is re-parsed through the isolated
`subscriptExpressionFragment` rule and bound by the ONE `ExpressionBinder.BindExpr`*. Only the GATE was narrower
than the principle — it asked "is this FUNCTION-bearing?" instead of "can the renderer render this?". It now asks
the second question, so `**` and a decimal literal take the same route.

⛔ **AND `**` COULD NOT HAVE BEEN FIXED THE OTHER WAY.** There is no C# infix `**`; a `case` arm would have to
hand-write `Math.Pow` plus §8.8.1.2's arithmetic-mode semantics into a `StringBuilder` — precisely the "third
expression compiler" D18 rejects. The token renderer stays a token renderer.

⚠ **THE OTHER TWO REJECTED TOKENS STAY REJECTED, and that is a spec reading, not an omission.** `SUB_STRINGLIT` —
an alphanumeric literal is not an arithmetic expression under §8.8.1.1, so it is illegal in the position.
`SUB_ALL` — legal ONLY in the §8.4.2.3.3 r6 positions, not as a general subscript. Neither is admitted by the
widened gate. **They should be BIND-time diagnostics rather than run-time throws**, which is the residue this note
leaves behind: the position is right, the stage is not. See [[feedback_no_deferral_default]].
