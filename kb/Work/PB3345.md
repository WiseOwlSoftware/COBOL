# PB3345 — a live review finisher's carrier does not hold its reviewed branch's findings

Filed 2026-10-17 by the operator (account 2, session c95c0b86). A sibling of kb/Work PB3311 (landed), which closed the
case where the finisher works on the reviewed branch itself.

## Harm

Two agents answer the same review findings. The second merges the reviewed branch, redoes the first one's fix and leaves
two competing branches for one note, which costs a finisher's and a reviewer's tokens and ends as an O10 DECISION row.
Nothing reports it: the plan reads as a normal finisher group.

## What happened (2026-10-17, wave 1110, PB3339)

The attended session's rolling wave (`wf_rolling_wave.js`, run wf_426911b7-4eb, `review_fix_rounds` 2) finished group A
on `worktree-wf_426911b7-4eb-1` (head 7436bd054). Its branch review (round 1) stamped `FINDINGS 2` into
`w1110a-PB3339-report.md` at 13:43 PDT. The wave's own review finisher (`fixFindings`) then started in a NEW isolated
worktree, `wf_426911b7-4eb-4` (`locked claude agent wf_426911b7-4eb-4 (pid 336512)`), merged the reviewed branch
(96abc48ce) and committed its fix for both findings (064bcff3f).

At 13:58, `python scripts/orchestrator/plan_wave.py --dry-run --budget-points 5 --no-index-regenerate` still planned
group B, a finisher for PB3339 ("notes PB3339 (lead PB3339); model: PB3339 already attempted 2 times without landing"),
and `prune_worktrees.py --brief` read `worktree-wf_426911b7-4eb-1` as DECISION ("a finisher answers them, and the next
wave plans it").

## Mechanism

Three readings combine, all in `scripts/orchestrator/plan_wave.py` and `scripts/prune_worktrees.py`:

1. **The dispatch is answered.** `plan_wave.answers` releases the ledger group `w1110 A` once its own report
   (`w1110a`) is written after the group's `at`. The implementer wrote it, so the hold ends before the review finisher
   starts, and the rolling wave records no ledger group for its review finisher.
2. **The reviewed branch has no owner.** `prune_worktrees.owned` (line 698) counts only branches IN FLIGHT by their own
   lifecycle. The reviewed worktree has no lock (its implementer returned), and its FINISHED report covers its tip, so
   `lifecycle` reads it DECISION before it reaches the `--min-age` freshness test.
3. **A live carrier is not a carrier.** `branch_carrier` (plan_wave.py:333) names only the branch of a FINISHED report
   that contains the branch. The review finisher writes its report only when it returns, so while it runs its branch is
   no carrier, and the FINDINGS arm (`if findings(r, cls) and r.branch in owned`, line 967) plans the finisher.

PB3311's review R1-1 made a CONTAINED branch unowned on purpose: a finished carrier can be a same-file successor of
another note, which says nothing about who answers this branch's findings. That reasoning holds for a finished carrier.
It does not hold for a LIVE one: a live agent that merged the reviewed branch either answers the findings or carries
them to its own review, and a finisher planned now competes with it either way.

## Fix shape

- One rule: the FINDINGS arm waits, with the reason in `waiting`, when the reviewed branch is contained in a branch
  that is IN FLIGHT by its own live lock (`prune_worktrees.lifecycle`'s first arm). Once that agent returns, its report
  decides as today: it supersedes the FINDINGS report, or its branch becomes the carrier `finisher_pred` names.
- Alternatively, or as well, the rolling wave records its review finisher in the dispatch ledger (one writer:
  `plan_wave.record_dispatch`), keyed so that `answers` releases it only on that finisher's own report. Pick one
  mechanism, not two (feedback one_mechanism_per_job), and say which in the fix.
- A self-test in `scripts/orchestrator/test_plan_wave.py`: a FINDINGS report on branch R, a live-locked worktree whose
  branch contains R and has no report yet, and no group planned for R's lead.

## Sweep

The same three readings apply to every agent that merges a reviewed branch into its own new worktree: a finisher a loop
wave planned (its pred merges the branch first) and a same-file successor (`after:`) while it runs. Check that each is
held by its ledger group until its own report, and cover the case in the self-test.
