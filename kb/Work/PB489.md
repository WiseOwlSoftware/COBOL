# PB489

## Mechanism — linage-clause
linage-operand-first-word-only

### Expected, from the standard
p17_qual.cob is LEGAL source - 8.4.2.2.3 SR2 permits qualification even where it is not needed, and here it IS needed - so data-name-1 is GRP-B's SZ = 9, the write to line 5 of a 9-line page body stays inside it, and the program must print NO-EOP with LINAGE-COUNTER 5. p21_ambig.cob must be REJECTED at compile time: SZ is non-unique and explicitly referenced, so 8.4.2.2.3 SR1 requires qualification. p22_lcindata.cob must be REJECTED: 13.18.34.4 GR7b says LINAGE-COUNTER may be referenced only in procedure division statements, and this is a file description entry. p16_sub.cob must be REJECTED under 13.18.34.3 SR1.

### Observed
p17_qual.cob prints `EOP` and `LC=001` - the compiler used GRP-A's SZ = 3, so the ADVANCING 4 write overflowed a page the programmer never asked for; the OF qualifier was accepted by the grammar and thrown away by the binder, and the wrong item was chosen SILENTLY, with no diagnostic at any stage. p21_ambig.cob prints the identical `EOP` / `LC=001` - the ambiguous reference was resolved by taking `llist[0]` rather than being rejected - which is the same first-match lookup seen from the other side and proves the two symptoms are one mechanism. p22_lcindata.cob compiles clean and dies at OPEN with 'LINAGE operand \'LPF\' is not resolvable to storage': for the register alternative the first cobolWord is the FILE-NAME QUALIFIER, so the binder recorded the file name as the data-name and the diagnostic names a word the programmer never used as a data item. p16_sub.cob discards the subscript the same way. ALL FOUR ARE ONE LINE OF CODE: `d.cobolWord()` takes the head of a dataReference and assumes the rest is noise, and the resolver then assumes the head is unique. This is the FILE STATUS capture pattern being reused past the point where it holds - the binder's own comment at DataBinder.cs:1097-1099 says so ('a data-name keeps only the base word (the FILE STATUS capture pattern)') - and the pattern is wrong wherever the name can be qualified. THE FIX IS STRUCTURAL: the LINAGE operand should carry the qualifier list (the RECORD KEY path at DataBinder.cs already models exactly this - RecordKeyQualifiers plus FindQualified - so the mechanism exists and is not being reused), resolution should go through a qualified lookup that REPORTS an ambiguous or unresolved name, and the register alternatives must be rejected at the clause rather than silently reinterpreted. SWEEP THE SIBLINGS: every other FD clause bound by the same 'keep the base word' shortcut - FILE STATUS, RECORD VARYING ... DEPENDING ON (DataBinder.cs:1176-1178, `ByName.TryGetValue(vn)` then `vlist[0]`), RELATIVE KEY (:1175) - has the same two defects and none was probed here.

## Mechanism — linage-clause
linage-counter-receiver-has-no-named-arm

### Expected, from the standard
The statement is illegal and shall be rejected with a diagnostic naming the rule that forbids it: 8.4.3.14.3 SR2 makes LINAGE-COUNTER unusable as a receiving operand, and 13.18.34.4 GR7b gives the reason - only the input-output control system may change its value. This is a permanent property of the language, not a feature awaiting implementation.

```
(the finding quotes no rule sentence verbatim, so there is nothing to --check; the implementer MUST quote §13.18.34.4 and re-run `cite.py --check` before writing a code comment)
```

### Observed
The compile fails, which is the right OUTCOME, but the message is `COBOLNET0899: receiving operand 'LINAGE-COUNTER' names a declared item in a reference shape COBOL.NET does not yet implement as a receiver (COBOLNET_DESIGN 1.4 - rejected rather than dropped)`. A user reads that as 'this will work in a later version' and files a request; a future implementer reads it as a GAP to close and would make illegal source compile. The rule that actually forbids it is never named anywhere in the compiler - a grep for 8.4.3.14.3 or for the receiving restriction returns nothing. THIS IS THE TWO-ARM-DISPATCH SHAPE WITH THE THIRD ARM MISSING, and the arms sit in the same twenty lines: ResolveReceiving screens LINE-COUNTER with a rule-citing rejection and PAGE-COUNTER with a correctly-labelled not-yet-implemented, while LINAGE-COUNTER - the only one of the three that is flatly illegal as a receiver - has no arm at all and inherits the catch-all. The catch-all is doing its job (kb/Work PB70's chokepoint: never drop a receiver silently); what is missing is the arm above it. Fix: add the LINAGE-COUNTER arm beside the LINE-COUNTER one, citing 8.4.3.14.3 SR2 / 13.18.34 GR7b, with a negative conformance test - and while there, check the same three registers on the OTHER receiving surfaces (arithmetic resultants, SET, INSPECT REPLACING, the CORRESPONDING receiver walk), since only the MOVE path was probed here.
