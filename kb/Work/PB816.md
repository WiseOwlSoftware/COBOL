# PB816 — OPEN — the arithmetic form of SET never asks whether the pointer is restricted

Filed 2026-09-09 by the registrar (second pass) from the **PB389 implementer's report**, "Residues and new
defects" (2) — `scratchpad/reports/PB389-report.md`, which names it *"the one row here that was never blocked on
the descriptor and can be fixed on its own"*. **Re-probed on this worktree's own build at `d3ba5795`.**

## The measurement

```
$ cobol.exe p09_setup_strong.cob --std 2023 --run
DONE
exit=0
```

`registrar2/probe/p09_setup_strong.cob`:

```cobol
01 REC-T IS TYPEDEF STRONG.
   05 R-A PIC X(4).
01 PTR-T IS TYPEDEF USAGE POINTER TO REC-T.
01 P1 TYPE PTR-T.
01 HOLDER TYPE REC-T.
…
    SET P1 TO ADDRESS OF HOLDER      *> correctly accepted (same type)
    SET P1 UP BY 4                   *> SR24 forbids this — accepted and executed
    SET P1 DOWN BY 2                 *> likewise
```

**The positive control that makes the screen's absence specific, not general:** the Format-7 arm DOES enforce
the neighbouring rule. `registrar2/probe/p09b_ptrto.cob`, the same declaration written directly:

```
$ cobol.exe p09b_ptrto.cob --std 2023 --run
p09b_ptrto.cob(7,8):  error COBOLNET0881: data item 'P1': USAGE POINTER TO REC-T declares a RESTRICTED
                      data-pointer, and the TYPEDEF clause shall be specified for the subject of such an entry
                      (ISO 13.18.60.3 SR18) …
p09b_ptrto.cob(11,12): error COBOLNET0869: 'P1': ADDRESS OF 'HOLDER' is a RESTRICTED data-pointer of type
                      'REC-T' … so the receiver shall be a data-pointer restricted to the same type
                      (ISO 14.9.39.3 SR20) …
```

So the binder knows perfectly well that `P1` is restricted — it says so, by type name, in the sibling
statement's diagnostic — and the arithmetic form never asks.

## ⛔ PREMISE CORRECTION — the inventory row's evidence is stale

`SR-14.9.39.3-24`'s recorded notes say:

> THE RULE'S SUBJECT CANNOT BE DECLARED. … MEASURED (probe g4_ptr_to_type …): `01 P1 USAGE POINTER TO T-A.` →
> `COBOL0307: unexpected 'TO'.` … With no restricted data-pointer declarable, identifier-9 can never be 'a
> data-pointer restricted to a type described with the STRONG phrase' and the rule has no input.

That is no longer true. [[PB153]] landed the `POINTER TO type-name-1` tail, and §13.18.60.3 SR18 (enforced, as
COBOLNET0881 above) makes the **TYPEDEF spelling the conforming one** — which is precisely the spelling the
probe uses. The rule's subject exists, the statement compiles, and SR24 is simply unwritten. The row's verdict
(`NOT-IMPLEMENTED`, state GAP) is unchanged by that correction; its **reason** changes from "no subject" to
"subject present, screen missing", and that is what a fixer needs to know.

## Code site

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/PtrBinder.cs:52-78` — beside the existing
`StrongTypeModel.PointerRestriction` calls. The Format-10 (UP BY / DOWN BY) arm passes through with no STRONG
screen at all.

## Sibling sweep the fixer owes — this is the FOURTH arm of one rule family

The restricted-data-pointer type-safety family is written down in at least four places, and each was fixed
separately:

- `PtrBinder.BindSetAddress`, both ADDRESS-OF directions — enforced ([[PB153]]).
- `SetBinder.BindSetPointer`, the plain `SET p TO q` form — **unscreened**, [[PB548]].
- `SET ADDRESS OF <untyped based item> TO <restricted pointer>` — **unscreened**, [[PB665]].
- Format 10's arithmetic form — **unscreened**, this note.

`feedback_one_rule_one_place`: four notes on one rule is the register telling you the rule belongs in ONE
predicate that every SET arm calls, not in a fifth `if`. Whoever takes any one of them should read the other
three first.
