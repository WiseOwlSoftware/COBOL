**Rule it breaks:** ISO 13.18.43.4 GR3/GR4 (record size includes implicit filler and the byte the last item ends in) over the 8.5.1.6.3 bit placement, as this compiler determined it in kb/Work PB1277 (MinRecordSize: ByteWidth laid out by the one 8.5.1.6.3 walk, never a re-summation of rounded bit leaves); MaxRecordSize doc states it IS DataItem.ByteWidth, never a second summation

**Scenario:** For a record holding a DYNAMIC LENGTH member, MaxDynamicExtent (FileModel.cs:564-567) takes its third arm and sums MaxDynamicExtent of each non-redefining child; an elementary bit child answers its own ByteWidth = Characters(n), so two same-level PIC 1(3) USAGE BIT items count 2 bytes where the 8.5.1.6.3 walk (BitLayout rule 1, which MinExtent and ByteWidth use) shares one byte. MEASURED with the built CLI (main Debug build of 2026-10-15; the arm is textually identical on the pin): FD F RECORD CONTAINS 11 over 01 R. 05 B1 PIC 1(3) USAGE BIT. 05 B2 PIC 1(3) USAGE BIT. 05 D PIC X DYNAMIC LENGTH LIMIT 10. is refused COBOLNET2010 record R describes 1 to 12 bytes (the min 1 shows the shared byte, the max 12 double-counts it), while the same record with 05 D PIC X(10) compiles clean under RECORD CONTAINS 11. The same wrong maximum feeds VaryMax/RecordMax (implied Format 2), the SR4 upper arm, RecordLayout.ContiguousPlaceOf and the fixed-form REWRITE length (SequentialIoEmitter.RewriteLengthArg).
