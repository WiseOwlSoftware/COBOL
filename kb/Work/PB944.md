# PB944 — LANDED — the bit byte reaches the receiver undecoded

Source: the **PB394 (MOVE operands) implementer report**, "New defects" item 2, which states it is **independent
of `PB896`** (whose zero-length arm the same report measured as correct here: with `N = 0` the receiver reads
`[   ]`, three spaces).

## Observed, byte-exact (`g2_bitgrp_num.cob`, `--std 2023`)

```
       01 N PIC 9 VALUE 1.
       01 BG.
          05 BE PIC 1 USAGE BIT OCCURS 0 TO 8 DEPENDING ON N.
       01 R-NUM PIC 9(3) VALUE 777.
       01 R-ALN PIC X(3) VALUE "QQQ".
       …
           MOVE B"1" TO BE(1)
           MOVE BG TO R-NUM
           MOVE BG TO R-ALN
```

`od -c` of the program's own output:

```
N U M = [ 302 200     ]   L E N = 3
A L N = [ 302 200     ]   L E N = 3
N U M - I S - Z E R O
```

`302 200` is the UTF-8 encoding of **U+0080** — a C1 control character. So a `PIC 9(3)` numeric item ends up
holding U+0080 and one space: **two characters where three digit positions are owed**, `FUNCTION LENGTH` still
answers 3, and `IF R-NUM = ZERO` is **TRUE**. 0x80 is the byte whose high bit is the one bit that was set, so the
bit group's storage byte is reaching the receiver without any conversion at all. The alphanumeric receiver takes
the same image, which is why this is not a numeric-decoding defect alone.

⚠ **The original report's repro under-states it.** `DISPLAY "BITNZ=" R-NUM` renders U+0080 as nothing on a
console, so the finding was recorded as "displays as nothing". The item is not empty; it holds a control
character in a numeric picture. Reported as a correction rather than carried forward.

## Expected, from the standard

```
$ python scripts/spec/cite.py --check 14.9.25.4 "Bit group items and national group items are treated as elementary items in the MOVE statement"
  OK  §14.9.25.4 4)  (General rules)
      4) Any move in which the sending operand is either a literal or an elementary item and the receiving item
         is an elementary item is an elementary move. Bit group items and national group items are treated as
         elementary items in the MOVE statement …
```

GR4 makes this an **elementary** move of a class-boolean sender (the bit group is "treated as an elementary item
of usage bit described with PICTURE 1(m)", §13.18.29.4 GR1) into a numeric receiver. §14.9.25.3's Table 16 is
then the authority on whether that pair is admitted **at all**. Exactly one of two outcomes is conforming:

* Table 16 admits it → the store is a defined conversion, and the receiver holds digits.
* Table 16 does not → the statement is refused by a NAMED diagnostic at compile time.

**Neither of those is "store the storage byte and carry on."** Whichever Table 16 says, today's behaviour is
wrong, which is why this is a defect note and not an adjudication — the same standard `kb/Work/PB921` was written
to.

## LANDED — 2026-09-22, wave 49 — ⚠ THE HEADLINE WAS CONFORMING; THE SIBLING SWEEP WAS NOT

Re-probed byte-exact on the wave-49 worktree's own build: `NUM=[C2 80 20 20]` — U+0080 followed by TWO spaces
(three positions, not the "U+0080 and one space" the note recorded), identically before and after this landing.

**The note's premise does not hold.** Its `BG` is declared `01 BG. 05 BE PIC 1 USAGE BIT OCCURS …` with NO
GROUP-USAGE clause, and §13.18.29.4 GR3 — "If a GROUP-USAGE clause is not specified or implied for a group item
that is not strongly typed and is not a variable-length group, that group item is an alphanumeric group item"
(`cite.py --check 13.18.29.4` OK GR3) — makes it an ALPHANUMERIC group, not a bit group. GR4's bit-group
sentence never reaches it: `MOVE BG TO R-NUM` is GR4's group move, "an alphanumeric to alphanumeric elementary
move, except that there is no conversion", and the receiving area takes the group's one storage byte (0x80) and
two alphanumeric spaces. That is the conforming store; `IF R-NUM = ZERO` over that content is §14.6.13.2's
incompatible data. The GENUINE bit group (`GROUP-USAGE BIT`) into a numeric receiver is already refused
COBOLNET0819 on Table 16's Boolean row, now witnessed by `conformance:negative/pb944-bit-group-to-numeric`.

**The sweep the note owed found three real defects, all fixed here** (the other halves of GR4's sentence):
(1) a GROUP-USAGE NATIONAL group into a NUMERIC receiver decoded its UTF-16BE BYTES as digits —
`NumericRenderer.FieldNumCore` read every group through the image alone; it now asks the one group value reader
`PlaceRenderer.SendingGroupValue`, which `OperandText.FieldAsString` also asks (§14.9.25.4 GR6 d) 3: N"12" →
012). (2) GR4's group move into a USAGE NATIONAL elementary receiver re-encoded the sending CHARACTERS
(`"AB"` → `"AB  "`), a conversion GR4 forbids; the area now takes the bytes (41 42 20 20 → U+4142 U+2020, D-N1).
(3) The same into a USAGE BIT receiver left the letter `A` in the boolean carrier; the packed byte is now
unpacked (`010`). `MoveEmitter.EmitGroupToElementaryMove` fits the image to the receiver's `ByteWidth` and
decodes the receiver's representation from it. Also: a zero-length bit group's GR3 ZERO into a character
receiver (PB943's filter). Witness: `conformance:2002/pb943_group_sender_conversions` (L4–L6).
