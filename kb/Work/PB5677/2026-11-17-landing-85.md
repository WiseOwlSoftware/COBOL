# Landing, 2026-11-17: at COBOL-85 a figurative constant whose character is a digit moves as a number

**Re-probe before the fix** (`run_probe.py`, the triage program `p5677.cob` of `E:/COBOL-coord/scratch/my-20261115/triage85/g2`,
`--std 85`, on a build of main 5459e4e876): `LV NV=55555 NE=[555555]`. A wider probe showed the same fault in every
noninteger and edited receiver: `S9(3)V99 SIGN TRAILING SEPARATE` held `555555` (its sign position a digit), `$$9.99`
`555555`, and the native carriers took the image's bytes: `9(3)V99 COMP-3` 353.53, `9(3)V99 COMP` 8926794.77.

**The rules** (each checked with `cite.py --check`, OK):
- `§1985:VI.6.19.4 GR3`: "All other figurative constants belong to the category alphanumeric" (all but ZERO and SPACE).
- `§1985:IV.4.2.2.2.3`: the figurative's string "is repeated character by character on the right until the size of the
  resultant string is greater than or equal to the number of character positions in the associated data item".
- `§1985:VI.6.19.4 GR4b3`: "data is moved as if the sending operand were described as an unsigned numeric integer", and
  GR4b: "alignment by decimal point and any necessary zero filling takes place".

So with LOW-VALUE "5" the sender into `9(3)V99` is the integer 55555, stored 555.00 (image 55500); into `ZZ9.99` (six
character positions) 555555, edited 555.00; into `$$9.99` $55.00; into the signed separate item 55500+. The nonnumeric
literal "55555" already moved that way, and so did a digit-only ALL literal (kb/Work PB5176).

**The fix.** `MoveEmitter.AllLiteralNumber` became `MoveEmitter.FillNumber`, the one decider of the number a fill sends to
a numeric or numeric-edited receiver: the digit-only ALL literal as before, and at 85 a HIGH-VALUE, LOW-VALUE or QUOTE whose
character (`FigurativeConstants.FillChar` under the program collating sequence) is a digit, at the 1985 width (the item's
character positions) and scale 0. `ElementaryStore`, `ConvertSource`'s two fill guards and `IsNumericOperand` all ask it,
so a figurative that sends a number takes the conversion and one that does not keeps the image fill. A fill of a character
that is no digit sends no number: the content of a numeric item holding it is not a value and the image fill is kept
(GnuCOBOL's, by CLAUDE.md rule 1).

**After:** `LV NV=55500 NE=[555.00]`; the wider probe `NS=55500+ NI=555 NP=555.00 NB=555.00 NEB=[$55.00]`.

**Witness.** `conformance:cases/VI.6.19@1985-MOVE-STATEMENT/pb5677_figurative_digit_to_noninteger_85` (new), added to
`1985-GR-VI.6.19.4-3` and `1985-GR-VI.6.19.4-4` (whose stored account gains the PB5677 paragraph and the site
`MoveEmitter.cs#FillNumber`).

**What stays open here.** 2002 and 2014: `§2002:14.8.24.3 GR4` and `§2014:14.9.24.3 GR6d3b` treat the figurative as an
unsigned integer "the same as the number of digits in the receiving operand", which gives 555.00 too, but the ALL literal's
2002 arm (kb/Work PB5351) is open beside it and 2002 is frozen, so `FillNumber`'s figurative arm is 85 only and the note
stays open for those editions, its row `2002-GR-14.8.24.3-4` unchanged.
