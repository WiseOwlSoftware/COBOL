# PB4562 — generate-detail-qualified-by-report-name-refused: GENERATE detail-name OF report-name is refused: "'DET IN RPT' is not defined"

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

cobc 3.2 refuses a GENERATE statement whose detail report group name is qualified by its report-name (`GENERATE DET OF RPT`) with "'DET IN RPT' is not defined". `GENERATE DET` compiles. The standard allows the qualification. Class: rejects legal source. Fuzz programs: fz00031 (night fuzz-batch-3000-20261103, slice D4).

## Minimal test case

Free reference format.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. GQ1.
ENVIRONMENT DIVISION.
INPUT-OUTPUT SECTION.
FILE-CONTROL.
    SELECT RPT-FILE ASSIGN TO "gq1.out".
DATA DIVISION.
FILE SECTION.
FD RPT-FILE REPORT IS RPT.
WORKING-STORAGE SECTION.
01 AMT PIC 9(3) VALUE 7.
REPORT SECTION.
RD RPT.
01 DET TYPE DETAIL LINE PLUS 1.
   05 COLUMN 1 PIC 9(3) SOURCE AMT.
PROCEDURE DIVISION.
    OPEN OUTPUT RPT-FILE
    INITIATE RPT
    GENERATE DET OF RPT
    TERMINATE RPT
    CLOSE RPT-FILE
    DISPLAY "DONE"
    STOP RUN.
```

## Environment

`cobc (GnuCOBOL) 3.2.0`, WSL2 Ubuntu x86_64. Compiled with `cobc -x -free -std=cobol2014 -o p gq1.cob`; when an executable is produced it is run as `./p` under `timeout 10`. Control: `GENERATE DET` compiles and the report file holds `007`.

## Observed result

```text
gq1.cob:19: error: 'DET IN RPT' is not defined
```

## Expected result (per ISO)

The program is legal, prints `DONE`, and the report file holds the one detail line `007`.

- §2023:14.9.16.3, syntax rule 1 (checked): "Data-name-1 shall name a detail report group. It may be qualified by a report-name.".

Edition: 2014. The 2009 committee draft (CD 1.2) carries the same syntax rule for GENERATE.

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`): compiles with no diagnostic; the run prints `DONE`; the report file holds `007`, exit code 0.

## Fix site

`cobc/tree.c`, function `cb_ref_internal`, case `CB_TAG_FIELD`: a qualifier is resolved by the field's parents and then by a file or CD (`field_is_in_file_record`, `field_is_in_cd_record`); a report-name is never accepted as the qualifier of a report group, so the reference is undefined (the logic was read in the 3.3-dev tree; the same functions are present in the 3.2 `tree.c`, and the 3.2.0 binary gives the error above). `cobc/parser.y` `generate_body` passes a `qualified_word`.

## Draft issue

**Title:** A detail or sum counter qualified by its report-name is "not defined": GENERATE DET OF R1, TOT OF R1

As posted (owner-reviewed, 2026-11-04):

cobc does not accept a report-name as the qualifier of a detail report group or a sum counter. `GENERATE DET OF R1` gets "'DET IN R1' is not defined", so when two reports each have a detail named DET, neither can be generated.

### To reproduce

`gq2.cob` (attached, free format):

~~~~
IDENTIFICATION DIVISION.
PROGRAM-ID. GQ2.
ENVIRONMENT DIVISION.
INPUT-OUTPUT SECTION.
FILE-CONTROL.
    SELECT RPT-FILE ASSIGN TO "gq2.out".
DATA DIVISION.
FILE SECTION.
FD RPT-FILE REPORT IS R1 R2.
REPORT SECTION.
RD R1.
01 DET TYPE DETAIL LINE PLUS 1.
   05 COLUMN 1 PIC X(2) VALUE "R1".
RD R2.
01 DET TYPE DETAIL LINE PLUS 1.
   05 COLUMN 1 PIC X(2) VALUE "R2".
PROCEDURE DIVISION.
    OPEN OUTPUT RPT-FILE
    INITIATE R1 R2
    GENERATE DET OF R1
    GENERATE DET IN R2
    GENERATE DET IN R2
    TERMINATE R1 R2
    CLOSE RPT-FILE
    DISPLAY "DONE"
    STOP RUN.
~~~~

    cobc -x -free -std=cobol2014 -fno-diagnostics-show-caret -o gq2 gq2.cob

### What happens

3.2.0 and 3.3-dev r5751 both stop with

~~~~
gq2.cob:20: error: 'DET IN R1' is not defined
~~~~

With `GENERATE DET` on line 20 the error is "'DET' is ambiguous; needs qualification". The attached `gq1.cob` (one report, `GENERATE DET OF RPT`), `gq3.cob` (a sum counter, `ADD TOT OF R1 TO W`) and `gq6.cob` (`SOURCE TOT OF R1` inside RD R1) get the same "not defined" error.

### What should happen

The program should display `DONE` and write `R1`, `R2`, `R2` to `gq2.out`. ISO/IEC 1989:2023 14.9.16.3 syntax rule 1: "Data-name-1 shall name a detail report group. It may be qualified by a report-name." The general format of a qualified data-name in 8.4.2.2.2 ends with an optional `IN`/`OF` file-name or report-name, so a sum counter can be qualified the same way wherever it can be referenced, for example in the procedure division (13.8.6.2.3) and in a SOURCE clause of its own report (13.18.53.3 syntax rule 4). The rules are the same in 2002 and in the 2014 FCD.

### Why it happens

In `cobc/tree.c`, `cb_ref_internal` matches a qualifier against the item's parents and then against a file or CD (`field_is_in_file_record`, `field_is_in_cd_record`). There is no check for a report, so a report-name is never consumed as a qualifier. And `cb_field.report` is set only by `finalize_report` at the end of the RD, so items of the RD being parsed have no report yet.

### Proposed fix

The attached `n10-generate-detail-of-report.patch` (against 3.3-dev r5751) adds `field_is_in_report` beside the file and CD checks in `cb_ref_internal`. For the RD being parsed, it looks for the item's record on the report's `records` chain, which `report_group_description_entry` in `parser.y` now sets at the RD's first entry, not at its end. A qualified name thus resolves to the item its unqualified name would, so nothing else changes. cobc does not check 13.18.53.3 rule 4, so `SOURCE TOT OF R1` in RD R2 now compiles, as `SOURCE TOT` already does when the name is unique. `USE BEFORE REPORTING DET OF R2` now compiles too.

With the patch, `gq1` writes `007`, `gq3` displays `W = 0021` (7 + 14) and `gq6` prints its footing as `   7        7`.

It adds the testsuite case "Report items qualified by report-name" to `run_reportwriter.at`, with ChangeLog entries. `make check`: 1373 expected, 9 skipped, 0 failed (1372 unpatched); the new test fails without the patch. The NIST suite gives the same results with and without it.
