## Measured

### Finding renames-clause — ISO/IEC 1989:2023 §13.18.45.3 SR3, SR5, SR6 (under-rejects; rows SR-13.18.45.3-5, SR-13.18.45.3-3, SR-13.18.45.3-6)

**Mechanism.** F-operand-identity: ResolveRedefines resolves RENAMES data-name-2/-3 through SubtreeCandidates(root, …), whose candidate set includes the record ITSELF, and then applies no screen to WHAT the resolved operand is. So the level-1 / level-77 bar (SR5), the OCCURS bar on the operands and their ancestors (SR3), and the CONSTANT RECORD bar (SR6) are all missing. (Levels 66 and 88 are rejected only because they are off the storage tree, under the SR4 message.)

**Repro.** scratchpad adj-d1/out13/probe/renames-clause/sr5l1.cob: `01 R. 05 A PIC X(2) VALUE "AB". 66 X1 RENAMES R.` + DISPLAY X1 -> compiles and prints AB (2023 and 85). Also sr5l77.cob (RENAMES a 77) -> ZZ; sr5ptr01.cob (RENAMES a 01 POINTER) accepted; sr3occ.cob (`05 A PIC X OCCURS 3`, `66 X1 RENAMES A`) -> warning COBOLNET1756 only, then aborts at run time with NotImplementedCobolFeatureException; sr3thru.cob (data-name-3 OCCURS 3) -> prints CDAAA; sr6.cob (`01 R CONSTANT RECORD.` then `66 X1 RENAMES A THRU B`) -> prints ABCD.

**Expected, from the standard.** Each program is rejected at compile time. §13.18.45.3 SR5: 'Neither data-name-2 nor data-name-3 shall refer to an entry that is described with level-number 1, 66, 77, or 88.' SR3: 'Data-name-1, data-name-2 and data-name-3 shall not be subject to any OCCURS clauses.' SR6: 'Neither data-name-2 nor data-name-3 shall refer to an entry within a record whose data description entry includes the CONSTANT RECORD clause.'

**Observed.** No diagnostic is raised for a level-1/77 operand, for an operand that has an OCCURS clause or is subordinate to one, or for an operand in a CONSTANT RECORD. The OCCURS case turns into a run-time abort, and the other cases compile to aliases no edition defines. This is separate from open note PB986, which owns SR3's OVER-rejection (an OCCURS group strictly inside the window is refused by the tiler). The OCCURS screen has to test the operand and its ANCESTORS only, never the items between the endpoints, or it would re-create PB986.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.cs#ResolveRedefines (the `foreach (var ren in root.Renames66)` block) and src/Cobol.Net.Compiler/Binding/DataBinder.cs#SubtreeCandidates (`itself included`)

### Finding renames-clause — ISO/IEC 1989:2023 §13.18.45.3 SR11 (under-rejects; rows SR-13.18.45.3-11)

**Mechanism.** F-extent-order: the SR11 ordering check is written as `endOff(dn3) < startOff(dn2)` and cites §13.18.45.4 GR2. It therefore rejects only a data-name-3 lying entirely before data-name-2. It never tests SR11's two actual conditions: that dn3 does not BEGIN before dn2, and that dn3's END is strictly AFTER dn2's end.

**Repro.** scratchpad adj-d1/out13/probe/renames-clause/sr11sub.cob: `01 R. 05 G. 10 A PIC X(2) VALUE "AB". 10 B PIC X(2) VALUE "CD". 05 C PIC X(2) VALUE "EF". 66 X1 RENAMES G THRU A.` + DISPLAY "[" X1 "]" -> compiles and prints [AB] (2023 and 85). Also sr11pre.cob (B THRU G) -> [CD]; sr11pre2.cob -> [CDGH]; sr11redef.cob (A THRU A2, A2 REDEFINES A) -> [AB].

**Expected, from the standard.** All four are rejected. §13.18.45.3 SR11: 'The beginning of the storage area described by data-name-3 shall not precede the beginning of the storage area described by data-name-2. The end of the storage area described by data-name-3 shall follow the end of the storage area described by data-name-2. NOTE Data-name-3, therefore, cannot be subordinate to data-name-2.' The correct test is startOff(dn3) >= startOff(dn2) AND endOff(dn3) > endOff(dn2).

**Observed.** The existing test is a strict subset of SR11. An alias whose data-name-3 is subordinate to data-name-2, starts before it, or has the same extent is accepted, and it silently takes a window that differs from what the programmer wrote.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.cs#ResolveRedefines (`if (endOff < startOff)` block)

### Finding renames-clause — ISO/IEC 1989:2023 §13.18.45.3 SR2 (under-rejects; rows SR-13.18.45.3-2)

**Mechanism.** F-SR2-placement: BindEntries sends a level-66 entry to BindRenames, which attaches it to _lastRoot and leaves the level stack untouched. Nothing requires the RENAMES entries to FOLLOW the record's last entry, so a 66 written in the middle of a record is accepted, and later subordinates still join the record. A 66 written after a 77 attaches to the 77 as if it were a record.

**Repro.** scratchpad adj-d1/out13/probe/renames-clause/sr2mid.cob: `01 R. 05 A PIC X(2) VALUE "AB". 66 X1 RENAMES A. 05 B PIC X(2) VALUE "CD".` + DISPLAY X1 "|" B -> compiles and prints AB|CD (2023 and 85). sr5l77.cob: `77 Z PIC X(2). 66 X1 RENAMES Z.` -> accepted.

**Expected, from the standard.** Rejected. §13.18.45.3 SR2: 'All RENAMES entries referring to data items within a given record shall immediately follow the last data description entry of the associated record description entry.' A level 01-49 entry after a 66, before the next 01/77/FD/SD, breaks this. A 66 after a 77 has no associated record description entry.

**Observed.** No placement diagnostic exists. A trailing 66 after a later record, naming an earlier record's items, is rejected only indirectly, through SR4's 'not an item of the record' (COBOLNET1655).

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindEntries (the `if (lvl == 66)` arm) and src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindRenames
