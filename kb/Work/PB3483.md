# PB3483 — the share-mode window in KeyedConnector.Lock

From the implementer report of PB3337 (`E:\COBOL-coord\scratch\reports\w1137a-PB3337-report.md`, `## New defects` 2, carried from round 1). PB3337 has landed (PR #351, main 2353545b2), so this note is ready.

**Mechanism.** The fallback in `KeyedConnector.Lock` gives the kept handle back on any `IOException`, including another run unit's refusal. A re-OPEN refused '61' by a third party therefore loses the kept handle, and with it the file lock the commit-controlled connector must keep until COMMIT or ROLLBACK. The round-2 `RetakeKeptFileLock` retakes the column lock but does not close the window between the give-back and the retake.

**Fix shape.** Tell a sharing violation apart from other IOExceptions and keep the kept handle across the attempt instead of releasing it first. The witness must fail without the fix (PB3481 R3-2 records one that did not).

**Sites:**
- `src/Cobol.Net.Runtime/IO/KeyedConnector.cs`
- `src/Cobol.Net.Runtime/IO/Sharing/RunUnitFileLock.cs`

## Landed

**Re-probe (Windows, this build).** The note reproduced as written: A (APPLY COMMIT, SHARING WITH ALL OTHER) wrote record 7 and was CLOSEd; B opened I-O beside A's kept handle; A's re-OPEN under SHARING WITH READ ONLY answered '61' (B's write handle and A's own kept one both refuse the new share mode), and a third run unit's writable OPEN then rolled A's live transaction back (its REWRITE of record 7 answered '23', the record gone): the give-back in `KeyedConnector.Lock` was never undone, so the liveness byte went with the handle and the file lock with it.

**Mechanism, two arms.** (1) The handle: `Lock` gave the kept handle back on ANY `IOException`. It now does so only for `HostFile.IsSharingRefusal`, records the handle it gave away, and `AbandonOpen` takes it again (`KeyedConnector.RetakeKeptHandle`: the same access and share mode, attached to the store as an OPEN attaches its own, the liveness byte held again) for EVERY unsuccessful ending after the swap, not only the second refusal: a refused adoption (a '30' after the swap) lost it the same way, found by the sibling sweep. (2) The column lock: the re-OPEN gave the kept column lock back, took its own and, when unsuccessful, took the kept one again, two instants in which another run unit's OPEN against the kept column was admitted. `RunUnitFileLock.Amend` replaces the kept lock on its own hold (`IColumnLockHost.Establish`'s `supersedes`: the OFD host adds the new byte to the same description, the sidecar host publishes a second holder file, the old goes only when the request is admitted), and `Revert` puts the old column back, untested, when the OPEN is unsuccessful; `RetakeKeptFileLock` and `RunUnitFileLock.Retake` are gone. The share-mode window itself (a handle that refuses the new one cannot be beside it) stays and is named in DESIGN-runtime-library.md 2.2.1.10 As built (3).

**Found and fixed in the same files (I9).** `OPEN OUTPUT` of a connector whose CLOSE kept its handle was refused '61' by that handle on a host whose share modes are mandatory (`FileConnector.TakeRunUnitFileLock`'s OUTPUT probe counted the connector's own kept handle as another's); `FileConnector.HeldByAnotherHandle` lets the keyed connector give the handle back for the question and take it again when another handle holds the file. PB3481 R3-2 (the retake witness could not fail) is answered by reshaping `An_unsuccessful_reopen_leaves_the_kept_file_lock_standing`.

**Witnesses.** `CommitRollbackRuntimeTests`: `A_reopen_refused_by_another_run_unit_keeps_the_kept_handle_and_its_transaction`, `An_unsuccessful_reopen_after_the_handle_swap_gives_the_kept_handle_back` (both fail with the retake call removed: '23' for '51'), `A_reopen_output_is_not_refused_by_the_handle_its_own_close_kept`, `A_reopen_output_refused_by_another_run_unit_keeps_the_kept_state`; `RunUnitFileLockAmendTests` (both column hosts, a racing run unit at the entry of every establishment, with its control).
