# PB355 — the record-area slice the connector never receives

**Rows:** `GR-14.9.41.4-17`.

## The program

`<lane3 scratch>/out-b1/probe/start-p2-e/p2e.cob` — an indexed file, `RECORD KEY IX-PRIME PIC X(4)` in
`01 IX-REC`, plus a sibling `01 IX-REC2` whose `05 IX-GEN PIC X(2)` occupies the key's leftmost TWO character
positions (the §14.9.41.3 SR6 b) generic-key shape); records `AB01` and `AB99` written. `OPEN INPUT`;
`MOVE "AB01AAAA" TO IX-REC`; `START IXF KEY IS EQUAL TO IX-GEN WITH LENGTH 4`.

Observed: **INVALID KEY taken, FS=23.**

## The rule

> §14.9.41.4 GR17 a): The specified key is set up by moving the relevant parts of the record area into a
> temporary data area.
> b): The length of this temporary area is considered to be the length specified in the LENGTH clause, if
> specified, or else the length of record-key-name-1, if specified, or else the length of data-name-1.

`--check 14.9.41.4 "The specified key is set up by moving the relevant parts of the record area into a temporary
data area"` → **OK**. The SOURCE of the temporary area is **the record area** at the key of reference's positions
(a) — data-name-1 is not named there; the LENGTH clause only sets how LONG that area is (b). With LENGTH 4 the
temporary area is the prime key's four record-area characters, `AB01`, so record AB01 satisfies EQUAL: FS=00 and
the following READ NEXT delivers AB01.

## What the compiler does

`IndexedConnector.Start` (lines 453-454) computes

```csharp
string value = operand.Length >= compareLength ? operand[..compareLength]
                                               : operand.PadRight(compareLength, ' ');
```

— when the LENGTH exceeds data-name-1's own width the missing characters are **invented as spaces** instead of
being read from the record area, so the search key becomes `AB  ` and matches nothing. Upstream,
`KeyedIoEmitter.EmitStart` (line 353) hands the runtime only
`OperandText.AsString(BoundFieldOperand(sta.Operand))` — data-name-1's own content — so **the record-area slice
the rule names is never available to the connector at all.**

## Why nothing currently written can see it

The two readings of GR17 a) coincide for every LENGTH <= data-name-1's width, which is why probe `start-p2-d` D2
and `conformance-test:KeyedOffsetSpecTests.Start_KeyOperandInSiblingRecord_MatchesByBytePosition` both pass.

## The reading, stated because the divergence is entirely inside it

An alternative reading of a) — *move data-name-1 into a temporary area whose length b) fixes*, i.e. an
alphanumeric MOVE with space fill — would make the shipped behaviour correct. **The text does not support it:**
a) names *the record area* and not data-name-1; its plural *parts* exists for the SOURCE-phrase concatenated key
of §12.4.5.12.4 GR2 (**PB358**); and GR13 calls arithmetic-expression-1 the count of characters *used as a
partial key*, which is a PREFIX OF THE KEY rather than a padded copy of a shorter operand. The fixer settles it
from the text; if it finds the standard genuinely ambiguous, that is a `status: owner` note, not a silent choice.

## The fix shape

At the EMIT boundary, not in the padding expression: pass the key of reference's record-area slice (or the record
image plus the key geometry) alongside the count, so the connector can build the temporary area GR17 a)
describes. That is the same boundary **PB354** part 4 must cross to stop sending a converted text rendering, and
the two land together.

**Code sites:** `IndexedConnector.cs#Start` (lines 453-454) · `KeyedIoEmitter.cs#EmitStart` (line 353).
