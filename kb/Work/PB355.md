# PB355 — the record-area slice the connector never receives

**Rows:** `GR-14.9.41.4-17`.

## The program

`<lane3 scratch>/out-b1/probe/start-p2-e/p2e.cob` — an indexed file, `RECORD KEY IX-PRIME PIC X(4)` in
`01 IX-REC`, plus a sibling `01 IX-REC2` whose `05 IX-GEN PIC X(2)` occupies the key's leftmost TWO character
positions (the §14.9.41.3 SR6 b) generic-key shape); records `AB01` and `AB99` written. `OPEN INPUT`;
`MOVE "AB01AAAA" TO IX-REC`; `START IXF KEY IS EQUAL TO IX-GEN WITH LENGTH 4`.

Observed: **INVALID KEY taken, FS=23.**

## The rule

> §14.9.41.4 GR17 a): The specified key is set up by moving the relevant parts of the record area into a
> temporary data area.
> b): The length of this temporary area is considered to be the length specified in the LENGTH clause, if
> specified, or else the length of record-key-name-1, if specified, or else the length of data-name-1.

`--check 14.9.41.4 "The specified key is set up by moving the relevant parts of the record area into a temporary
data area"` → **OK**. The SOURCE of the temporary area is **the record area** at the key of reference's positions
(a) — data-name-1 is not named there; the LENGTH clause only sets how LONG that area is (b). With LENGTH 4 the
temporary area is the prime key's four record-area characters, `AB01`, so record AB01 satisfies EQUAL: FS=00 and
the following READ NEXT delivers AB01.

## What the compiler does

`IndexedConnector.Start` (lines 453-454) computes

```csharp
string value = operand.Length >= compareLength ? operand[..compareLength]
                                               : operand.PadRight(compareLength, ' ');
```

— when the LENGTH exceeds data-name-1's own width the missing characters are **invented as spaces** instead of
being read from the record area, so the search key becomes `AB  ` and matches nothing. Upstream,
`KeyedIoEmitter.EmitStart` (line 353) hands the runtime only
`OperandText.AsString(BoundFieldOperand(sta.Operand))` — data-name-1's own content — so **the record-area slice
the rule names is never available to the connector at all.**

## Why nothing currently written can see it

The two readings of GR17 a) coincide for every LENGTH <= data-name-1's width, which is why probe `start-p2-d` D2
and `conformance-test:KeyedOffsetSpecTests.Start_KeyOperandInSiblingRecord_MatchesByBytePosition` both pass.

## The reading, stated because the divergence is entirely inside it

An alternative reading of a) — *move data-name-1 into a temporary area whose length b) fixes*, i.e. an
alphanumeric MOVE with space fill — would make the shipped behaviour correct. **The text does not support it:**
a) names *the record area* and not data-name-1; its plural *parts* exists for the SOURCE-phrase concatenated key
of §12.4.5.12.4 GR2 (**PB358**); and GR13 calls arithmetic-expression-1 the count of characters *used as a
partial key*, which is a PREFIX OF THE KEY rather than a padded copy of a shorter operand. The fixer settles it
from the text; if it finds the standard genuinely ambiguous, that is a `status: owner` note, not a silent choice.

## The fix shape

At the EMIT boundary, not in the padding expression: pass the key of reference's record-area slice (or the record
image plus the key geometry) alongside the count, so the connector can build the temporary area GR17 a)
describes. That is the same boundary **PB354** part 4 must cross to stop sending a converted text rendering, and
the two land together.

**Code sites:** `IndexedConnector.cs#Start` (lines 453-454) · `KeyedIoEmitter.cs#EmitStart` (line 353).

## Landed — 2026-09-13

**Re-probed first.** The note's repro still reproduced on today's tree (probe `p2e.cob` rebuilt against this
worktree's `cobol.exe`): `START IXF KEY IS EQUAL TO IX-GEN WITH LENGTH 4` over a record area holding
`AB01AAAAAA` took INVALID KEY with `FS=23`. The note's line numbers had drifted (the connector's `Start` sits at
623 and the emitter's call at 384 after PB327/PB342/PB356/PB771), and `EmitStart` had already moved from
`OperandText.AsString` to `OperandText.AsStorageImage` — still data-name-1's own content, so the defect the note
describes was intact.

**The reading, settled from the text.** GR17 a) names the RECORD AREA as the source and GR16 names the key
("The key specified in the KEY phrase, or that shares a leftmost character with the data item specified in the
KEY phrase, becomes the key of reference" — `--check 14.9.41.4` OK). GR17 b) fixes only the LENGTH of that area.
The alternative reading the note stated is not supported, exactly as the note argued; no owner decision was
needed.

**The fix, at the one place the rule belongs.** `KeyedIoEmitter.EmitStart` renders
`OperandText.RecordAreaImage(ReferenceResolver.RecordArea(file))` into `RuntimeApi.FileStartIndexed`, and
`IndexedConnector.Start(int keyIndex, string op, string keyedRecordImage, int compareLength)` builds the first
temporary area as `KeyOf(Fit(keyedRecordImage), keyIndex)[..compareLength]` — **the same extraction the random
READ (§14.9.30.4 GR32) and DELETE (§14.9.10.4 GR3) already make from the same image**, so a SOURCE-phrase key's
several "parts" (§12.4.5.12.4 GR2) would fall out with no second mechanism. Nothing is padded any more: GR14
bounds `compareLength` by the key's own span and `KeyOf` pads the AREA, which is the only fill the model admits.
`CobolFile.StartIndexed` / `FileRegistry.StartIndexed` / `RuntimeApi.FileStartIndexed` renamed the parameter to
say what it now carries.

**Structural correction (CLAUDE.md rule 5).** START built its comparand out of data-name-1 partly because the
record area was not something a verb could ask for: five consumers each wrote
`file.AreaRecord is { } ar ? ResolveItem(ar) : null`. That is now `ReferenceResolver.RecordArea(FileModel)`, and
the two keyed emitter sites, the sequential READ emitter and the READ/RETURN `INTO` binders all call it.

**Measured after.** The probe answers `OK ST=00` + `GOT=[AB01][REC-01]`, the spec-derived expectation. The
alphanumeric golden's A3 arm is the wrong-ANSWER leg: `KEY IS > GN-PFX WITH LENGTH 4` over area prime `AB50`
answered `REC-01` before (because `"AB01" > "AB  "`) and answers `REC-99` now — confirmed by rebuilding the
defect and re-running the golden.

**Goldens:** `conformance:2002/pb355_start_length_past_operand` (A1–A4 the divergent arms incl. the silent wrong
record, A5–A6 the complement, A7 GR14's bound) and `conformance:2002/pb355_start_length_national_past_operand`
(GR13's national unit; the pad was not even a character there). Structure: `unit:StartTemporaryKeyAreaDriftTests`,
whose failure branch was driven against the restored defect before it was trusted.

**Row:** `GR-14.9.41.4-17` DIVERGES → CONFORMS (GAP 2533 → 2532). The note's "unverified national branch of e)"
did NOT hold on today's tree — a national key is no longer refused, and the national golden witnesses it.

**Docs:** `docs/COBOLNET_FILES_DESIGN.md` gained the GR17 a) bullet and the one-record-area-resolution bullet.
En route, nine inherited `§13.4.2` citations for "multi-01 FDs share one area" were re-derived: §13.4.2 is the
file description entry's GENERAL FORMAT and says no such thing. The rule is §13.18.33.4 GR3 ("Multiple level 1
entries subordinate to a FD or SD entry represent implicit redefinitions of the same area"), with §13.18.43.4
GR5 a) for the size; every code and doc site was corrected.
