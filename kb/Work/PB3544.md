# PB3544 — the SORT transfer hook rolls back under SORT control

## Defect

`src/Cobol.Net.Compiler/CodeGen/Verbs/SortEmitter.cs:615` `EmitTransferUse` (`verbDisposes`) also emits
`RollbackOnFatal`. A fatal status on a RELATIVE or INDEXED USING or GIVING file therefore rolls back under SORT control. It
also bypasses `FlowForbidden`, so no EC-FLOW-ROLLBACK is raised.

The rules (each re-run through `cite.py --check`, OK):
- §14.6.13.1.3 item 2: "If the executed statement is a MERGE or SORT statement, then the rules for those statements apply."
  Item 8 is never reached under SORT or MERGE.
- §14.9.36.4 GR2: "If this statement is attempted to be executed under the control of a recursive runtime element or a
  file SORT or MERGE statement, then the exception condition EC-FLOW-ROLLBACK is set to exist."

The adjudication read the code on branch `worktree-wf_e05cc4a3-4db-1` (wave 1154's APPLY COMMIT branch, in flight). The fix
follows that branch and belongs to the same cluster as PB3542.

**Sites:**
- `src/Cobol.Net.Compiler/CodeGen/Verbs/SortEmitter.cs:615 (EmitTransferUse, verbDisposes)`

## Landed (wave 1156 A)

§14.6.13.1.3 item 8's ROLLBACK is now ONE rule, written once in `SequentialIoEmitter`: `Item8Applies` (where it can apply: never on a SORT/MERGE implicit transfer, item 2; never where the statement's ON EXCEPTION phrase processes the condition, item 1 and §14.9.10.4 GR20 c); never on a success arm; an explicit statement only for a file that `FileModel.IsCommitControlled`), `EmitItem8Question` (asked AT THE RAISE, before any declarative: `CobolFile.RollbackDueOnFatal(name, checkingEnabled)`, the emitter passing the raised condition's bit in the statement's checking mask) and `EmitItem8Rollback` (run after the declarative and BEFORE a RESUME transfers control or DOC-A.1-103 ends the run unit). Every hook arm (the `__IoCheckEc` arm, the EC-model `__IoCheck` arm, the plain arm, the no-declaratives arm) and the foreign-file arm of a refused COMMIT/ROLLBACK (`EmitForeignFileIoCheck`) consume it; `TransactionEmitter` no longer writes the call. `TransactionControl.RollbackOnFatal()` executes the ROLLBACK statement's general rules (`Execute`, shared with `Rollback`), so GR1 and GR2 hold for it, and every input-output statement on a file under commit control declares EC-FLOW-ROLLBACK (`EcBinder.NodeKindRaises`). `Item8RollbackSiteDriftTests` pins the one site.

Re-probed first: a '35' on a RELATIVE USING file under APPLY COMMIT rolled back under the SORT (WS-COUNT 0001, record 2 absent), and a '47' from a READ in the SORT's input procedure rolled back with no EC-FLOW-ROLLBACK. Fixed: the transfer hooks (`verbDisposes`) emit no item 8 (`pb3544_item8_not_on_a_sort_transfer`), and an explicit statement in an input or output procedure attempts the ROLLBACK statement, which raises EC-FLOW-ROLLBACK with checking on (`conformance:cases/14.9.36-ROLLBACK/pb3544_item8_rollback_in_sort_procedure_ec_flow`) and rolls nothing back with it off (`pb3544_item8_rollback_in_sort_procedure_unchecked`; `unit:TransactionControlTests.Item_8_under_a_forbidding_control_raises_ec_flow_rollback_or_rolls_nothing_back`). The other two controls GR2 names are witnessed end to end too: a MERGE output procedure (`pb3544_item8_rollback_in_merge_output_procedure_ec_flow`) and a recursive runtime element (`pb3544_item8_rollback_under_recursive_element_unchecked`).
