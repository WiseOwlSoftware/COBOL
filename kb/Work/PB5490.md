# PB5490 - the gate keys a run to the tree it hashes but builds with an incremental build that trusts file timestamps, so it can record a stale binary's results under the head's key (a false-green class)

UNVERIFIED LEAD: re-probe before fixing.

**Lead, verbatim (review of PB5478, w20262023a-review-r1, lead R1-1, `scripts/gate.py:833`; `review-w20262023-a.jsonl`).** "LEAD (gate defect): the gate keys a run to the tree it hashes but builds with an mtime-trusting incremental dotnet build, so it can record test results of binaries that do not match that tree; run 000002-20261114T041256Z recorded the old TestsTreeWalks guard under head 079351831d key d0d4926b, and run 000003 carried 40,867 of its passes"

**Failure scenario, verbatim.** "A source file is restored with Copy-Item (mtime preserved, older than the dll): Host.build runs dotnet build, Csc is skipped as up to date, the hosts run the stale dll and the run is recorded at the head tree key. If the stale content is GREEN where the head content is RED, the record is a false green that carry() and the store then trust, and the merge group does not rerun Windows Debug cases the store shows passed. Here the stale content was red (2 walk-guard cases), so it showed; the opposite direction is silent."

**Fix direction, verbatim.** "Make the build input the tree, not mtimes: e.g. record a digest of the compiled source set into the build (or a per-project content stamp) and force a rebuild when it differs from the gated tree, or build with --no-incremental when the tree differs from the last built tree; plus a gate self-test that restores an older-mtime source and expects a rebuild."

**Occurrence (from the operator's list):** run 000002-20261114T041256Z of worktree agent-acd85fd67b03c858e (a file restored with Copy-Item kept its old timestamp). The reverse case would be a silent false green.
