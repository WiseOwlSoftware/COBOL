# PB1007 — LANDED

## The divergence
A function-identifier sent BY CONTENT is transferred "as for a MOVE" into the formal (§14.8.2.3.3 2)). The MOVE of the
same function value produces `[3   ]` (the §15.4 returned value's own PICTURE, moved to alphanumeric); the INVOKE
path's temporary is a fixed 30-digit numeric PICTURE, so the moved image is the temporary's digits, not the value's.

## What the fixer owes
One definition of "the temporary data item holding a function's returned value" (§15.4) used by MOVE, CALL/INVOKE BY
CONTENT and the MOVE multi-receiver hoist — measure the hoist for the same divergence first (the lead names it as the
same root). Golden: the INVOKE and the MOVE side by side, numeric and integer functions.

## Landed 2026-09-22 (wave 54 group C) — one temporary, moved as the function, for MOVE and INVOKE

**Re-measured on main `57d36e4c6` (train 50, which carries PB923, is not on main yet):** the INVOKE half still
draws COBOLNET0828 for both `BY CONTENT FUNCTION TRIM(X)` and `BY CONTENT FUNCTION INTEGER(N)` (PB923's scope).
**The hoist half the note asked to measure first DOES diverge on main, as a wrong answer:** `MOVE FUNCTION
INTEGER(N) TO R2 R3` (PIC X(4), N = 3.7) stored `[0000][0000]` where `MOVE FUNCTION INTEGER(N) TO R1` stores
`[3   ]`; so did `INTEGER-PART(-12.5)`, `ORD("A")` and `MOVE FUNCTION INTEGER(N) TO IX TE(IX)`.

**Fixed at the root — ONE definition of the §15.4 temporary.** `SendingValueTemp.OfComputed` describes an INTEGER
function's temporary at scale 0 (`IntegerFunctionValuePic`; §15.2 item 5 through the one
`IntrinsicResultType.IsIntegerOperand` reader) and flags every numeric function's temporary
`DataItem.IsFunctionReturnedValue`; `OperandText`'s field image — the ONE text reader every character store,
text comparison and STRING/INSPECT sender goes through — renders a flagged item in DOC-A.1-92's literal form. So the
MOVE hoist, an EVALUATE subject and PB923's INVOKE MOVE-lane temporary (all `SendingValueTemp.Materialize`) move the
value as the function does. Witnesses: `conformance:85/pb1007_function_temporary_character_receivers`,
`conformance:negative/pb1007-numeric-function-two-character-receivers` (a NUMERIC function is still refused into
character receivers — the flag legalizes nothing), and
`SendingValueOnceDriftTests.MaterializedIntegerFunction_MovesAsTheFunctionDoes` (hoisted vs single-receiver, five
integer functions × alphanumeric / JUSTIFIED / national / numeric-edited / numeric receivers).

**The INVOKE lane (after train 50 brought PB923 to main, merged into this branch).** Re-measured first:
`INVOKE O "M" USING BY CONTENT FUNCTION INTEGER(N)` into `PIC X(4)` still drew COBOLNET0828. PB923's arm kept a
NUMERIC-typed function on the expression arm as a named residue, because the temporary moved wrongly; that guard is
gone — every non-folded intrinsic takes rule 2 d)'s MOVE lane over the same `SendingValueTemp` temporary, and the
conformance question is the ONE chain's (`OoConformance.ContentMismatch` → `MoveContentMismatch` → Table 16): an
INTEGER function crosses into alphanumeric / JUSTIFIED / national / numeric-edited formals exactly as the MOVE stores it
(`INV-X=[3   ]`, `[12  ]`, `INV-N=[66  ]`, `INV-E=[  -12]`), and a NUMERIC function is refused with the MOVE's own
SR10 message. The diagnostic now quotes the argument as written (`FUNCTION NUMVAL("3.7")`, not run together).
Witnesses: `conformance:2002/pb1007_invoke_content_integer_function` (INVOKE and MOVE side by side),
`conformance:negative/pb1007-invoke-content-numeric-function-alnum-formal` (COBOLNET0828),
`SendingValueOnceDriftTests.InvokeContentIntegerFunction_StoresWhatTheMoveStores`.
