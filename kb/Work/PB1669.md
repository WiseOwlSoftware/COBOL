# PB1669 — LANDED

Filed 2026-09-27 by the train-68 lander from the wave-68 T implementer report (`w68t-PB1401-report.md`, new
defect 2).

**Repro.** `scratchpad/w68t/p/c1.cob` with `--std 2023 --permissive`: `IF BZ B-OR (BW)` is COBOL0001. The same
source compiles strict (PB1465 narrowed the lexer's SUBSCRIPT trigger to words the compile admits as user words).

**Rule.** §8.8.2 6) (`cite.py --check 8.8.2` OK): "The permissible combinations of operands, operators, and
parentheses in a boolean expression are specified in Table 4" — a left parenthesis may follow B-AND / B-OR / B-XOR.
§8.3.2.1 1) (`cite.py --check 8.3.2.1` OK §8.3.2.1 1)): "Reserved words shall not be used as user-defined words".
Migration mode admits the operators as legacy data-names, but it may not thereby reject the standard spelling.

**Code sites.** `src/Cobol.Net.Frontend/Parsing/TokenRetypes.cs#ReservedNonDataNames` / `#PrimeLexer` and
`src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4#OnDefaultLParen`: at lex time the word cannot be told from a
data-name, so the decision has to move to where it can be (the parser sees the operator position).

**What the fixer owes.** Decide `(`-after-operator by position, not by the word's reservation status, in migration
mode too; a permissive-mode golden for the c1 shape; confirm a legacy data-name `B-OR (1)` (subscripted) still
parses under --permissive.

## Landed (wave 1005 group B)

Re-probed on the wave-1005 build: `IF BZ B-OR (BW)` with `--std 2002 --permissive` was COBOL0001 (the legacy table `05 B-OR PIC 9 OCCURS 3` with
`B-OR(2)` compiled, with the COBOLNET0901 warning). It now prints `C1 T`; the legacy table still subscripts, also beside an undeclared
B-AND operator that takes a parenthesis (`L2 F`).

**The note's fix shape ("decide by position, in the parser") was not the root.** The word's reading is not a matter of position — `DISPLAY BZ B-OR (1)`
puts the same word after an operand where a data-name is legal — it is a matter of whether the PROGRAM DECLARES the word, which is
exactly what the §8.9 reservation gate already finds (`ReservationGateRewriter`, `CobolParserCoreBase.gatedDeclaration`, filled under
`--permissive` for a reserved word it admits). So the lexer's SUBSCRIPT-trigger set is now "the words the edition reserves (`--permissive`
off) minus the words the program declares" (`TokenRetypes.ReservedNonDataNames(edition, declared)`; it used to be "minus the words
`AdmitsAsUserWord` admits", which under `--permissive` was every reserved word), and when a parse finds a declaration that changes that set
(`TokenRetypes.LexesDifferentlyFrom`) `Frontend.LexAndParse` lexes and parses the text again with the word declared (a loop over an attempt
with its own `DiagnosticBag`; a program that declares no reserved word parses once). `ReservationGateRewriter.ParseToFixpoint` now seeds its
freed set from the caller's retypes, so a later round ADDs to the words an earlier attempt found. Non-permissive compiles compute the identical
set as before (a free word's trigger stays on; a reserved word's stays off).
**Goldens:** `BooleanOperatorPermissiveTests` (Conformance; permissive at 2002/2014/2023: the operator with a parenthesis, and the declared
legacy table beside it) — the corpus runner is strict-only, so the permissive witness is a test class like `FormatOneVendorCallPermissiveTests`;
`2002/pb1465_boolean_paren_after_operator` is the strict twin. Docs: DESIGN-frontend-grammar §3.3b (the trigger narrowing).
**Sibling sweep:** the other lexer-time decision a program's declarations could change is the same trigger set for the §8.9 gated FREE words
(retyped to IDENTIFIER after lexing; their trigger was never off, so they need no second lex).

**Code sites (for orient).**
- `src/Cobol.Net.Frontend/Parsing/TokenRetypes.cs#ReservedNonDataNames` / `#LexesDifferentlyFrom` — the per-compile trigger set and the re-lex test.
- `src/Cobol.Net.Frontend/Pipeline/Frontend.cs#LexAndParse` — the attempt loop; `#LexAndParseOnce` is the former body.
