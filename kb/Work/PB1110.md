## Measured (adjudicator / refuter evidence, verbatim)
### [alignment-and-transfer-of-data-into-data-items] binary32 double rounding: every float-receiver landing (MOVE float arm, arithmetic float store) converts a non-same-usage sender to a correctly-rounded binary64 FIRST and then casts that double to float, so a binary32 receiver (FLOAT-BINARY-32, FLOAT-SHORT, COMP-1) is rounded twice instead of once
- **Rows:** GR-14.6.8.3-2, GR-14.6.8.3-1 — harm `wrong-answer`
- **Repro:** 01 B32 USAGE FLOAT-BINARY-32. 01 R PIC 9V9(23). 01 SRC PIC 9V9(16) VALUE 1.0000000596046448. ... MOVE 1.0000000596046448 TO B32 MOVE B32 TO R DISPLAY R (also MOVE SRC TO B32; MOVE 1.0000000596046448E0 TO B32; COMPUTE B32 = SRC; same with USAGE FLOAT-SHORT / COMP-1). Pinned cobol.exe --std 2023 and 2014: every leg prints 100000000000000000000000. Contrast: 01 V32 USAGE FLOAT-BINARY-32 VALUE 1.0000000596046448E0 prints 100000011920928955078125. Programs: E:/Temp/claude/E--CobolSharp/a700c052-f9e4-4942-84ff-a13c7505d6ec/scratchpad/adj-d1/out/probe/alignment/p3.cob, p4.cob
- **Expected (spec):** §14.6.8.3 rule 2 (cite.py OK): the algebraic value is converted 'in a manner consistent with the specifications of ISO/IEC 60559:2020, Clauses 3 and 5' - one correctly-rounded conversion under roundTiesToEven. 1.0000000596046448 lies above the binary32 midpoint 1+2^-24 = 1.000000059604644775390625, so the stored value is 1+2^-23 = 1.00000011920928955078125, printed 100000011920928955078125 in PIC 9V9(23). For FLOAT-SHORT/COMP-1 (rule 1: 'the content of the receiving operand is set to the algebraic value') the same nearest-binary32 value is the only reading consistent with the documented binary32 representation (DOC-A.1-207).
- **Observed:** Stores 1.0. Rounding the exact value to binary64 lands EXACTLY on the binary32 midpoint (the excess 2.46e-17 is below half a binary64 ulp), and the (float) cast then ties to even -> 1.0. The arithmetic landing's own comment says 'ROUNDED is a no-op (the receiver holds the exact algebraic value)', a premise true only for binary64. The VALUE-clause lane parses the literal straight to binary32 and gets the right answer, so the MOVE/COMPUTE and VALUE landings of one literal disagree. Single-rounding cases (0.1, 16777217, 16777219) are right, which is why no golden caught it. Binary64 receivers are correct (ScaledToDouble is correctly rounded).
- **Code site:** src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs float arm (FloatStoreSingleChecked(NumericRenderer.Real(...)) / FloatStoreDecChecked(..., IsSingle)); src/Cobol.Net.Runtime/Values/Numeric/CobolFloat.cs StoreSingleChecked(double) and StoreChecked(CobolDec,bool) ((float)src.ToDouble()); src/Cobol.Net.Compiler/CodeGen/Verbs/ArithmeticEmitter.cs float RECEIVER landing ((float)(Real(value))). Fix shape: one correctly-rounded ScaledToSingle / CobolDec.ToSingle conversion from the exact scaled/decimal value, used by every binary32 landing (MOVE, arithmetic store, CALL/INVOKE BY CONTENT crossings) plus a drift test over the landings.

## What the fixer owes
Convert a decimal/fixed sender DIRECTLY to binary32 with one correct rounding (a decimal→binary32 conversion, never via a double), in the MOVE float arm AND the arithmetic float-receiver landing (ArithmeticEmitter ~476) — the two-arm dispatch. Golden at 2002 with a value whose double-then-float rounding differs from the single rounding (the finding's repro), one per landing.
