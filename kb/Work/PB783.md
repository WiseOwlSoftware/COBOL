# PB783 — OPEN — the checkpoint protocol's only artefact cannot travel with the work it checkpoints

Filed 2026-09-06 by the registrar. Every count, command and quotation below was measured on this worktree today;
the one item taken on report rather than measured is called out as such.

## The rule that makes it impossible

`.gitignore:140`, under the comment at `:139`:

```
139  # Lander/implementer checkpoint files — a worktree artifact, never part of a landing (DEVLOG 1441).
140  STATUS.md
```

Measured:

```
$ git check-ignore -v STATUS.md
.gitignore:140:STATUS.md	STATUS.md
```

So the file is excluded from every commit **by design** — and the design's own justification ("never part of a
landing") is about the LANDING, not about the checkpoint branch. The two were conflated, and the cost is that a
WIP checkpoint commit on a worktree branch cannot carry it either.

Reproduced on this worktree with a probe `STATUS.md` present, using the exact add the briefs mandate:

```
$ git add -An -- . ":!.claude/settings.local.json"        # the checkpoint add, dry run
$ echo $?
0                                                          # exit 0, and STATUS.md is NOT among the paths
$ git add -n STATUS.md                                     # naming it explicitly
The following paths are ignored by one of your .gitignore files:
STATUS.md
hint: Use -f if you really want to add them.
$ echo $?
1
```

Both arms are wrong for a checkpoint. The first **silently** omits it — the agent sees exit 0 and believes it
checkpointed. The second refuses. There is no third arm short of `-f`.

## ⛔ The consequence: the checkpoint lives in a directory, and directories get deleted

`STATUS.md` therefore exists ONLY as an untracked file inside one worktree directory. It is not on the branch, it
is not on the remote, and it is reachable by exactly one path: `<that worktree>/STATUS.md`. Measured on this repo
right now:

| measurement | count |
|---|---|
| `git worktree list` entries (including the main checkout) | **28** |
| `worktree-agent-*` branches | **29** |
| **agent branches with NO worktree directory** — their checkpoint is gone | **5** |
| live worktrees holding no `STATUS.md` at all | **13** of 28 |

The five orphaned branches are not empty; each carries real work whose checkpoint no longer exists:

```
worktree-agent-a111d7b477cd7bef0   1a38e08b  PB699: final gate verdict recorded in the report
worktree-agent-a2a769db59770443a   13fb6ea7  Merge origin/main (0a24276f) into PB739: SequentialConnector's two ADVANCING arms …
worktree-agent-a6d2907b763ee0741   cc317993  Merge remote-tracking branch 'origin/main' …
worktree-agent-a730df678efe557d2   fad53cf2  Merge origin/main (train 14) into PB338: FileRegistry doc-comment conflict merged …
worktree-agent-afd009143d4907f70   03b59a1d  Golden lane round 3: 59 goldens for 44 rows; GAP 2969 -> 2925
```

A fresh agent handed any of those branches gets the commits and no `NEXT`, no `BLOCKED`, no `GATE` verdict, no
batch-file path and no allocated-codes list — every field §1 of the skill says the checkpoint carries.

## Why the protocol does not save you — the skill never says WHERE

`.claude/skills/workstream/SKILL.md` is the operational SSOT for this, and both of its relevant sections name the
file without naming its location.

§1 (`:18-30`), the checkpoint table:

> | implementer (worktree) | `git commit -m "WIP checkpoint: …"` on the worktree branch **after every mechanism and
> every gate**, plus `<worktree>/STATUS.md` with `DONE` … `NEXT` … `BLOCKED` … `GATE` … | one mechanism |

and, at `:27`:

> **A killed agent is replaced by a FRESH agent that reads the checkpoint** (`STATUS.md` + `git log`, or the
> `.jsonl`).

§5 (`:135-142`), the restart procedure, step 3:

> `git worktree list` + dirt per worktree (`git -C <wt> status --short -- . ':!.claude/settings.local.json'`) +
> `STATUS.md` per worktree → who is near done.

⛔ **The two sections disagree with each other, and neither is wrong on its face.** §1 pairs `STATUS.md` with
"the worktree branch", so a reader takes the checkpoint to be *on the branch*; §5 enumerates it *per worktree
directory*, which is where it actually is. Only §5's reading works, and it works only while the directory
survives. Nothing in either section says the file is gitignored, that a WIP commit cannot carry it, or that a
replacement agent must be given the OLD worktree's absolute path — which is precisely the instruction the
orchestrator had to supply by hand nine times.

`feedback_one_rule_one_place`: one fact ("where the checkpoint is") written down twice, in two incompatible
shapes.

## ⛔ Not [[PB767]], and the two must be fixed together

[[PB767]] is the same file and a different mechanism: `git add -A -- . ":!STATUS.md"` **exits 1 and stages
nothing**, because an EXCLUDE pathspec item makes git count an ignored path as explicitly named. Its subject is
the exit code of the add; the fix is the pathspec spelling, and it is already written up with the four brief
sites (`SKILL.md:98` among them). This note's subject is that the checkpoint is not in the commit AT ALL, which
is true of the corrected add too — PB767's own remedy (`git add -A -- . ":!.claude/settings.local.json"` then
`git reset -q -- STATUS.md`) leaves `STATUS.md` exactly as unreachable as before. **Landing PB767 does not close
this, and closing this would make PB767's `git reset` line moot** — so whichever lands second should re-read the
other, and they should land in one change set to `SKILL.md`.

## Fix shape — one of two, and the choice is the owner's or the next orchestrator's

Both make the checkpoint reachable without a directory; they differ in what they cost the landing.

1. **Commit the checkpoint on the worktree branch.** Un-ignore it, or (better, because it needs no `.gitignore`
   change and no `-f`) write it to a TRACKED path the landing strips — e.g. `kb/Work/.checkpoints/<branch>.md` or
   a `checkpoint/` prefix — so the WIP commit carries it and a fresh agent reads it with
   `git show <branch>:<path>`, from anywhere, with no worktree at all. The lander's existing
   "strip the checkpoint" step is where it comes back out, and that step already exists in every brief. ⛔ Pair
   it with a drift test, or the next brief re-introduces an untracked path (CLAUDE.md rule 5): assert that a
   `worktree-agent-*` branch tip either carries the checkpoint path or is a landing merge.
2. **Keep it untracked and make the protocol honest about it.** `SKILL.md` §1 and §5 both state, in the same
   words, that `STATUS.md` is gitignored, lives at `<worktree>/STATUS.md`, is unreachable once the directory is
   removed, and that a restart dispatch MUST carry the old worktree's absolute path in the brief. Then §5 gains a
   step: never `git worktree remove` a branch that has not landed. This is cheaper and strictly weaker — it
   cannot recover the five branches above, and it keeps a hand-carried path in every dispatch.

⚠ Option 1 is the shape that makes the NEXT restart automatic; option 2 makes this restart survivable. The
register's own bias (rule 5) is option 1, but the `.gitignore` comment at `:139` cites DEVLOG 1441 as the reason
the file is ignored, so **read that entry before un-ignoring anything** — the landing-hygiene requirement it
records is real and option 1 must keep satisfying it.
