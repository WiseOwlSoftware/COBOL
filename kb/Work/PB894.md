## The sibling sweep

Every IDENTIFICATION DIVISION attribute the standard gives to BOTH a program and a function: PROTOTYPE is
the one found. `AS literal-1`, the OPTIONS paragraph's per-element clauses and the END markers are the
others to check. The structural remedy is for `programIdAttribute` and `functionIdParagraph` to share one
attribute production rather than each carrying its own list — the shape that makes the next attribute
automatic.

**The feature, not the parse.** A program prototype definition is a whole §10.6.1 source unit, so writing the
paragraph was the smallest part:

  `IS PROTOTYPE` tail is ONE rule, `prototypePhrase`, shared with `functionIdParagraph` (the note's structural
  remedy). `BinderDriver.MakeUnit` reads that one node for either unit kind.
* **§10.6.2 SR4 a)–f)** — `PrototypeUnitRules.ScreenBody` (COBOLNET2272), ONE screen for program, function AND
  method prototypes. The sibling sweep found the function arm had NONE of it (a function prototype's
  WORKING-STORAGE and statements compiled and vanished) and the method arm (`OoClassTable`) had two of six with a
  partial section list; both now call the one screen.
* **§10.6.1 shape** (COBOLNET2274): never contained, never containing, end marker required. **§10.6.2 SR1**
  (COBOLNET2273): prototypes precede every other source unit — neither kind was ordered before.

  `CheckPrototypeSignaturePairs` now pairs by EXTERNALIZED name and compares with `PrototypeSignatures.Same`

* **§12.3.8.4 GR10 b)** — `BuildProgramDetailsTable` layers in-group prototype definitions behind definitions
  (a) then b)); a CALL through a REPOSITORY prototype whose only in-group source is a prototype definition is now
  arity/description-checked (negative `pb894-call-via-prototype-definition-arity`, COBOLNET1684).
