# PB332 — the audit that returns a clean zero for the whole compiler

**Rows:** `FMT-14.9.41.2`, `FMT-14.9.49.2` (`FMT-14.9.30.2` is owned by **PB331**, which repairs the same
grammar rule). Found independently by three adjudication subjects — read p1, start p1, use p1.

## The rule that governs all of them

> §5.2.3: Optional words are reserved words or context-sensitive words. They are shown in uppercase and not
> underlined in general formats. They may be written to add clarity ...

> §8.3.2.4.3: Within each format, uppercase words that are not underlined are called optional words and may be
> specified at the user's option with no effect on the semantics of the format

Both `--check` → **OK**; §5.2.2 confines *required* to the underlined keywords, and §4.2.2 obliges the
implementation to accept the standard language elements.

## The three statements

**READ — `ADVANCING ON LOCK`.** `python scripts/spec/figure_extract.py 722` reconstructs the printed format with
underlining measured from the PDF's vector rectangles and prints `_ADVANCING_ ON _LOCK_` — ADVANCING and LOCK
underlined, ON not. `READ SQF NEXT RECORD ADVANCING LOCK ...` → `error COBOL0001: missing token before 'LOCK'`
(`out-b1/probe/lockcombo/seq5.cob`); `ADVANCING ON LOCK` compiles (`seq6.cob`). The grammar writes
`readAdvancingOnLock : ADVANCING ON LOCK ;` with ON as a bare token. **The extractor is not simply
under-reporting underlines on that page:** the same run marks IGNORING, LOCK, NO, KEY, INVALID, NOT, END,
PREVIOUS, INTO, READ, END-READ, ADVANCING as underlined and RECORD, WITH, IS, AT, the KEY after INVALID, and
NEXT as bare — an internally discriminating result. Every other optional word on that page is already handled
correctly in the same file (`RECORD?`, `WITH? LOCK`, `KEY IS?`, `AT? END`, `INVALID KEY?`), so this is one
missed word, not a policy.

**START — `WITH LENGTH`, and its inverse.** §14.9.41.2 prints `[ WITH LENGTH arithmetic-expression-1 ]` with
LENGTH underlined and WITH NOT underlined — verified by rendering PDF page 784 (printed folio 754) at 600 dpi,
not taken from the OCR. `START IXF KEY IS = IX-KEY LENGTH 3 INVALID KEY ...` is rejected: COBOL0001 *missing
token before 3*, then a COBOL0001/COBOL0306 cascade (`out-b1/probe/fmt/prb.cob`). The grammar writes
`startWithLength : WITH LENGTH arithmeticExpression`. **The same phrase carries the inverse error:**
`startKeyPhrase : KEY IS? comparisonOperator? dataReference (startWithLength)?` makes relational-operator
optional, which the rendered diagram does not — so `START IXF KEY IS IX-KEY` (no operator) compiles and runs
(`out-b1/probe/ix-ops/prb.cob`). The comment defending it cites §14.9.41 for a bracketing the printed format
does not carry, and §14.9.41.4 GR15 supplies the implied EQUAL only when the whole KEY PHRASE is omitted, never
when only the operator is. The operator-set half of that phrase is **PB333**.

The rest of START's format was checked against the same 600-dpi render and is correct: the plain outer bracket
over FIRST/KEY/LAST, the choice indicators on the INVALID group, the un-underlined KEY of INVALID KEY, and
`[ END-START ]`.

**USE — two of four optional words in Format 1, and one in Formats 3 and 4.** §14.9.49.2's figure notes measure
the underlining: in Format 1 `USE`, `GLOBAL`, `EXCEPTION`, `ERROR`, `INPUT`, `OUTPUT`, `I-O`, `EXTEND` are
underlined while `AFTER`, `STANDARD`, `PROCEDURE` and `ON` are not; in Formats 3 and 4 `AFTER` is not
underlined. All five of these are legal and all five are rejected COBOL0001
(`out-b1/probe/fmt-optwords/`, `fmt-f3/`, `fmt-f4/`):

```
USE ERROR PROCEDURE ON F1.          USE AFTER STANDARD ERROR ON F1.
USE EXCEPTION CONDITION EC-ALL.     USE EC EC-ALL.        USE EXCEPTION OBJECT CF4A.
```

The grammar writes `USE GLOBAL? AFTER STANDARD? (EXCEPTION | ERROR) PROCEDURE ON? useOnTarget` — STANDARD and ON
optional, AFTER and PROCEDURE mandatory. **Its own comment shows the reasoning that produced the split:**
STANDARD and ON were relaxed because *the CCVS suite and mainstream compilers write both* spellings — i.e. the
optional-word set was derived from what the witness corpus happens to contain rather than from §8.3.2.4.3, so
the two words no witness omitted stayed required. The corpus is a regression net, never the authority.

## The root: the audit that exists to find this class returns zero

`python scripts/spec/audit_grammar_optional_words.py` (main tree, PDF present) reports *grammar files scanned:
11 · parser rules: 544*, then **statements with a located general format: 0** and **0 candidate(s)**; with
`--statement READ` it says *no general-format page found for statement READ*. Its docstring says it locates the
page from the markdown's `14.9.N.2 General format` heading and its enclosing page anchor — and the de-paging
removed those anchors (`clause_page.py`'s own docstring records the same breakage in the grammar-conformance
workflow). Until it is repaired, every optional-word finding is hand-work, and the compiler has a silently-green
gate over 544 rules.

## The fix shape

Repair the audit FIRST (it is the thing that makes the next case automatic), then let it drive the sweep. For
USE, the optional words of a format are a PROPERTY of the format: make each `useStatement` alternative carry
every non-underlined word as optional (`AFTER? STANDARD? ... PROCEDURE? ON?` / `AFTER?` on Formats 3 and 4) and
let the alternatives disambiguate on the UNDERLINED keywords, which they still can — CONDITION/EC and OBJECT/EO
are lexer keywords immediately after EXCEPTION, so `USE EXCEPTION F1.` is unambiguously Format 1. Pair it with a
drift test asserting that, for each format, every optional-word subset parses to the same bound declarative.

**Code sites:** `CobolIO.g4#readAdvancingOnLock`, `#startWithLength`, `#startKeyPhrase` ·
`CobolControlFlow.g4#useStatement` (line 273) · `scripts/spec/audit_grammar_optional_words.py`.

## Landed 2026-09-05

**The audit first, because it is the thing that makes the next case automatic.** Three blind spots, all measured:

* the clause→format locator. `statement_pages()` read the markdown's `<a id="page-N">` anchors; de-paging deleted
  every one of them, so 0 formats were located and `0 candidate(s)` was printed with exit 0. There is already ONE
  clause→page resolver — `clause_page.py` — so the audit's private locator is gone and `clause_page.index()` is
  now the primitive with `resolve()` a filter over it: one document-ordered pass returns every numbered heading,
  which also answers "what comes NEXT", and that is what bounds a general format's extent across a page break.
* `render_figure.headings()`, the shared heading test, dropped **89 real clause headings**: 87 second-level
  headings print the NUMBER alone on its line with the title laid out separately (`4.1`, `5.2`, `6.3` — including
  `5.2 General formats`, the clause that DEFINES underlining), and 2 end in a non-bold Symbol glyph (`7.3.23`,
  and `15.78.2 General format` itself). The bold test now ignores spans carrying no letters or digits, and a
  heading may be its number alone.
* the format→grammar link. Rules were selected by "mentions the statement keyword", which can never see a
  statement's HELPER rules — `readAdvancingOnLock` never writes READ and `startWithLength` never writes START, so
  **PB331's defect was structurally invisible to the tool built to find it**. Rules are now selected by CLOSURE:
  the anchor rules plus every rule that nothing OUTSIDE the closure references. Structural, not a hand list.

Then the matcher, which was wrong in three more ways: `{facilityWord("RECEIVE")}?` in the `statement` dispatch
made that 200-alternative rule an anchor and dragged 233 rules in (actions and predicates are now blanked with
the comments); the optional test was "is the next character `?`", which reads a required word inside `( … )?` as
required, so optionality is now read from the alternative's paren structure; and two structural exclusions — a
single-token alternative in a multi-alternative rule is a NAME alternative (`cobolWord`'s `| RECEIVE |`,
`readDirection`'s `NEXT | PREVIOUS`), and a rule whose whole body is one token referenced only as `X?` already
permits the omission (`timesKeyword`). 25 parser rules written `name : alt ;` on one line were never parsed at
all (572 → 596 rules).

**The population assertion is the point.** Declared-vs-located, anchored, measured-word and rule counts are
checked and a shortfall EXITS NON-ZERO. It fired twice for real causes during the change (15.78.2 unresolved;
5.2 measuring zero words) before both were fixed. §5.2 is excluded structurally — it is the only
general-format-titled clause that has sub-clauses, because it is the clause defining the notation.

Measured now: **320 general formats declared, 320 located, 320 measured, 596 parser rules, 45 candidates, exit 0**
(was: 0 located, 0 candidates, exit 0). Proof it catches what it exists to catch: with PB331's landed
`ADVANCING ON? LOCK` reverted in memory to `ADVANCING ON LOCK`, `required_tokens` reports ON as demanded and the
READ closure reaches `readAdvancingOnLock`.

**Then the grammar, from what the audit found.** Each measurement was re-confirmed against the raw rectangles and
the 600 dpi render before the rule moved.

* `startWithLength : WITH? LENGTH arithmeticExpression` — WITH is not underlined on printed folio 754.
* `startKeyPhrase : KEY comparisonOperator dataReference startWithLength?` — the note's inverse finding. The
  operator carries no brackets on the printed page, and §14.9.41.4 GR15 supplies the implied EQUAL only when the
  whole KEY PHRASE is omitted; `START IXF KEY IS IX-KEY` used to compile and run. The outer `IS?` went with it
  (every `comparisonOperator` alternative absorbs its own leading IS, §8.8.4.2.2, so it only admitted `KEY IS IS
  = K`). The operator SET stays PB333's.
* `useStatement` Format 1 becomes `USE GLOBAL? AFTER? STANDARD? (EXCEPTION | ERROR) PROCEDURE? ON? useOnTarget`
  and Formats 3/4 take `AFTER?`. Format order became load-bearing in the process and now says so: `useOnTarget`'s
  `fileName+` accepts any cobolWord and CONDITION/EC/OBJECT/EO are context-sensitive words `cobolWord` admits, so
  Formats 3 and 4 are listed BEFORE Format 1 and first-match-wins settles it.

**Goldens.** `2002/pb332_start_length_optional_with` (L1 without WITH, L2 with, N1 without the phrase at all —
the N1 leg is what proves LENGTH was honoured rather than dropped) · `85/pb332_use_optional_words` (Format 1 with
none of the four optional words beside one with all four) · `2023/pb332_use_ec_after_optional` (Format 3, AFTER
omitted, in the long and the SR12 `EC` spellings, each identified by FUNCTION EXCEPTION-STATUS) ·
`negative/pb332-start-length-word-required` · `negative/pb332-use-format1-needs-exception-or-error` ·
`negative/pb332-start-key-needs-operator`, all three rejecting at every edition.

**The drift test the fix shape asked for** is `OptionalWordSubsetDriftTests`: for each format it writes EVERY
SUBSET of the optional words and demands byte-identical output (§8.3.2.4.3). A power set, not two spellings —
because two hand-picked spellings are exactly what let the CCVS-derived split survive. Proved to fail: with
`WITH?` reverted the start-with-length row goes red on the no-optional-words spelling.

**Rows.** `FMT-14.9.41.2` and `FMT-14.9.49.2` stay `DIVERGES` on residue this note never owned — PB333's operator
SET and the `SR-14.9.41.3-7` decline on one, PB365's Format-4 interface-name arm on the other — so both notes now
carry the FMT row in their `inventory_rows` and `DefectiveRowCoverageDriftTests` keeps a live owner for each.
GAP is unchanged at 2802: both rows were already GAP and both remain so.

**What did NOT hold on today's tree.** `readAdvancingOnLock` and the doubled `RECORD` were already fixed by
PB331, as expected. `USE AFTER STANDARD ERROR PROCEDURE F1.` (ON omitted) already compiled — `ON?` was one of the
two words the old comment had relaxed. Everything else the note recorded reproduced exactly.
