# PB3395 — a plan that cannot launch leaves its groups held in the dispatch ledger

**Mechanism.** `make_dispatch_specs.main()` renders every spec, then records every group in the dispatch ledger
(`record`, through `plan_wave.record_dispatch`, the one writer: kb/Work PB3186), and only then runs
`check_practices.py`. `plan_wave.main()` prints `RED` and exits 1, but the ledger entries stay. A RED plan can never
be dispatched (`dispatch_guard.py` and the unit rules refuse it). Even so, the next `plan_wave.py` reads its groups as
dispatched: "PBnnnn: held by dispatch w1127d, which has no report yet: re-planning it would dispatch the same work twice
(plan_wave.py --release that dispatch if it was aborted)". The notes stay out of every plan until someone runs
`--release`.

**Repro (2026-10-18 19:45 PDT, the loop's wave unit).** From Git Bash, `plan_wave.py --from-budget --borrow-days 6
--scratch E:\\COBOL-coord\\scratch --stop-file E:\\COBOL-coord\\scratch\\STOP-loop --cluster PB3353` delivered the
paths as `E:COBOL-coordscratch`, a drive-relative path. The planner accepted it and wrote `groups.json`,
`wf-args-w1127.json` and eight specs into `E:\COBOL\COBOL-coordscratch\`, inside the main checkout. `check_practices.py`
then went RED on the stop file ("'E:COBOL-coordscratchSTOP-loop' is not a fleet-scoped STOP-<scope> file"), and the
ledger kept w1127a-h (PB3387, PB3384, PB3386, PB2485, PB2500, PB2503, PB2509, PB2510 and PB2556). The re-plan with
correct paths planned only four other groups, because those eight notes were "held by dispatch". `plan_wave.py
--release 1127` cleared them, and the stray directory was deleted by hand.

**Sites:**
- `.claude/skills/workstream/make_dispatch_specs.py` — `main()`: render, `record`, then `check_practices.py`.
- `scripts/orchestrator/plan_wave.py` — `main()`: writes `groups.json` and the args file, calls `MAKE_SPECS`, and
  reports RED. Its `--scratch` and `--stop-file` are taken as given.

**Fix shape.** (1) A plan that fails its own check leaves the ledger as it found it. Either record only after
`check_practices.py` is GREEN, or release the wave's fresh entries when it is RED, and name what was released.
(2) `plan_wave.py` and `make_dispatch_specs.py` refuse a `--scratch` or `--stop-file` that is not absolute
(`pathlib.Path.is_absolute()` is false for `E:COBOL-coordscratch`) or that lies inside a git working tree, before
anything is written. A self-test pins both: a RED plan changes no ledger entry, and a drive-relative scratch is refused
with nothing written.
