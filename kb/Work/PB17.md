# PB17 — OPEN — a function-identifier as a SUBSCRIPT or a REF-MOD position compiles clean and throws

⚙ **RE-MEASURED 2026-08-04 AT `b21b81d4`. Both shapes reproduce EXACTLY as filed** — which is worth saying,
because the last three entries measured did not:

```
MOVE W-E(FUNCTION INTEGER(3)) TO W-R      -> compiles clean; at RUN TIME:
    NotImplementedCobolFeatureException: reference 'W-E(FUNCTION INTEGER(3))'
MOVE W-A(FUNCTION INTEGER(3):2) TO W-R    -> same, 'W-A(FUNCTION INTEGER(3):2)'
```

The PB7/DA7 **wrong-stage** family: legal source that compiles clean and throws.

## ⛔ ONE OF THE THREE INHERITED CITATIONS WAS WRONG

`cite.py --check` rejected **§8.4.2.3.3**: the clause exists (Subscripts / Syntax rules) and says nothing about
arithmetic expressions — its eight rules are about qualification, OCCURS, subscript COUNT and ALL. The third
wrong inherited citation in one session (after §13.18.27 for GROUP-USAGE and §15.15.3's own chain).

**The corrected chain, every link `--check`ed:**

| # | clause | what it gives |
|---|---|---|
| 1 | **§8.4.3.1.2** Format 1 | a function-identifier IS an identifier |
| 2 | **§15.4** | "The evaluation of a function produces a returned value in a temporary elementary data item" |
| 3 | **§15.2** items 5–6 | integer and numeric functions are "of the class and category numeric" |
| 4 | **§8.8.1.1** | "An arithmetic expression may be an identifier referencing a numeric data item" ⇒ 1+2+3 make a numeric function-identifier a legal arithmetic expression |
| 5 | **§8.4.2.3.2** + **§8.4.2.3.4 GR1b** | a subscript may be `arithmetic-expression-1`; GR1b evaluates it |
| 6 | **§8.4.3.3.3 SR4** | "Leftmost-position and length shall be arithmetic expressions" |

## ⚖ AND THE PREMISE THAT COULD HAVE KILLED IT — CHECKED, IT HOLDS

§8.4.3.2.3 **SR11** bars a numeric function "where an integer operand is required" and **SR12** bars an integer
function "where an unsigned integer is required". If a subscript were such a position, the finding would
evaporate and the compiler's refusal would be right. **It is not.** §8.4.2.3.2's format says
`arithmetic-expression-1`, and **§8.4.2.3.4 GR1b sets EC-BOUND-SUBSCRIPT when the expression does not evaluate
to an integer** — a runtime exception condition that would be unnecessary if the position required an integer
syntactically. SR14 confirms it from the other side: it has to impose "only numeric literals or arithmetic
expressions whose result is a positive integer" as a SPECIAL restriction for a BY REFERENCE bit item, which
would be redundant if subscripts were already so constrained. **Both shapes are legal source.**

## ⛔ THE ENTRY'S STATED FIX IS WRONG, AND SO WAS MY FIRST REPLACEMENT FOR IT

The entry says "the durable fix is the segment renderer". Reading `ReferenceResolver.RenderSegment` confirms the
ROOT CAUSE — its `default:` arm literally lists `FUNCTION` among the token types it cannot render — but the fix
does not belong there. `RenderSegment` is a **hand-rolled expression compiler over flat SUBSCRIPT-mode tokens
that emits C# text at BIND time**; adding a FUNCTION arm means hand-writing intrinsic rendering into a
StringBuilder, i.e. a third expression compiler beside `ExpressionBinder` and `IntrinsicRenderer`.

⚠ **And the obvious re-architecture is BLOCKED BY AN OWNER RULING, not by taste.** `RefModPlace.Start`/`Length`
are documented as "the D10 TRANSITIONAL carrier … they become `BoundExpr` when PHASE 15 removes the SUBSCRIPT
lexer mode", deliberately the same shape as `RefModSpec` "so PHASE 15 migrates both in one move rather than
leaving a second, differently-shaped ref-mod behind". **D10 is relocated to PHASE 15 §"CUT 2.5"**, blocked
because the frozen legacy compiler still shares `SUB_*`/`SubscriptEntryContext` until Cut 2 deletes it. Pulling
the `BoundExpr` migration forward would create precisely the second ref-mod shape the design forbids.

## ✅ THE DESIGN: THE STANDARD ALREADY SAYS "TEMPORARY DATA ITEM" — USE THE ONE TEMP MECHANISM

**§15.4: "The evaluation of a function produces a returned value in a temporary elementary data item."** So
materialize it:

1. Bind the function-identifier through the ONE intrinsic pipeline → a `BoundIntrinsicCall`.
2. Synthesize a temp through **`DataBinder.CreateCompilerTemp`** — already documented as "THE ONE synthesized-
   compiler-temp constructor (property-reference temps, user-function result temps)".
3. Register a pending op storing the call into the temp before the carrying statement, drained into a
   `BoundSequence` by `StatementBinder` — **the exact pattern `ReferenceResolver.OoTryBindPropertyReference`
   already uses** for §8.4.3.9 object-property references.
4. The subscript segment then renders as an ordinary data-name — which `ResolveSubscriptName` already handles.

**Why this is the durable shape and not a workaround:** no new carrier, no second ref-mod, no grammar change, no
D10 conflict (when D10 lands, the temp path is deleted with the rest of the string carrier), and it reuses a
mechanism `ReferenceResolver` is ALREADY a client of. It also makes the NEXT case automatic — the same route
serves any segment form `RenderSegment` cannot render, not just `FUNCTION`.

⚠ **The sweep this opens:** `RenderSegment`'s `default:` arm also rejects `SUB_STRINGLIT`, `SUB_DECIMALLIT` and
`SUB_ALL`. Each needs its own adjudication (ALL is legal only in the §8.4.2.3.3 r6 positions; a decimal literal
subscript is legal source that GR1b then faults at run time via EC-BOUND-SUBSCRIPT). Do NOT route them blindly —
that is the PB1 lesson about enforcing an unaudited table.
