# PB846 — LANDED — the table SORT's KEY phrase is mandatory in the grammar and optional in the standard

Source: the `PB445` implementer report and its finisher report ("New defect found outside this mechanism"). The
finisher additionally CORRECTED the false half of `SortBinder`'s comment (it claimed the data model did not
capture the OCCURS KEY phrase; it always had), so what remains is exactly the grammar arity and the GR21 wiring.

## Repro — re-run on this tree

`scratchpad/reg4/probe/p10_sort_table_no_key.cob` (PROGRAM-ID `R4P10`), `--std 2023`:

```cobol
       01 T.
          05 TE OCCURS 5 ASCENDING KEY IS TK INDEXED BY IX.
             10 TK PIC 9.
       ...
           SORT TE
           DISPLAY "S=" TK(1) ...
```
```
(15,12): error COBOL0001: unexpected 'DISPLAY'
```

The parser consumes `SORT TE` and then demands the key phrase the source is entitled to omit.

## The rules, quoted

```
$ python scripts/spec/cite.py --check 14.9.40.3 "The KEY phrase may be omitted only if the description of the table referenced by data-name-2 contains a KEY phrase"
  OK  §14.9.40.3 15)  (Syntax rules)
$ python scripts/spec/cite.py --check 14.9.40.4 "If the KEY phrase is not specified, the sequence is determined by the KEY phrase in the data description entry of the table referenced by data-name-2"
  OK  §14.9.40.4 21)  (General rules)
```

SR15 makes the omission legal exactly when the table's OCCURS clause carries a KEY phrase; GR21 says what it
then means.

## Code sites

* `src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4:820` — `sortKeyPhrase+` on the Format-2 (table) alternative.
  It must become `sortKeyPhrase*`, with SR15 enforced at bind (the omission is legal ONLY with a table KEY
  phrase, so the screen moves from the grammar to the binder, where it can name the real rule).
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SortBinder.cs` — the GR21 arm reads `OdoModel.KeyItems` /
  `OccursSpec.Keys` (already in significance order after PB445).

## Sibling sweep the fixer owes

* `SEARCH ALL` takes its keys from the same `OccursSpec.Keys` (kb/Work PB446 owns the SEARCH grammar) — the two
  consumers must agree on significance order and on the ASCENDING/DESCENDING flag per key.
* MERGE has no table format, so it is NOT a sibling here; say so in the change set so the next reader does not
  look for one.
* A golden for each arm: keys from the statement, keys from the table, and the SR15 negative (no KEY phrase in
  either place -> a named diagnostic, not a parse error).

## Landed — 2026-09-22, wave 46 group H, worktree `wf_f206ae6d-3b7-1`, base `8fe62bd1f`

Re-probed first on this worktree's build: `SORT TE` (table with `ASCENDING KEY IS TK`) was still `COBOL0001:
unexpected 'DISPLAY'`. The printed Format 2 was RENDERED (PDF p776 / folio 746): the KEY phrase is BRACKETED
there and BRACED in Format 1.

* `CobolIO.g4#sortStatement` — `sortKeyPhrase+` → `sortKeyPhrase*`. MERGE has no table format, so `mergeKeyPhrase+`
  is correct and was left alone (said in the rule's comment so nobody looks for a sibling).
* `SortBinder.SortBindTable` — with no statement KEY phrase: §14.9.40.3 SR15 is screened on the RESOLVED table
  (no OCCURS KEY phrase → a named COBOLNET1757 statement-operand rejection citing SR15, not a parse error), and
  §14.9.40.4 GR21 takes the keys from `OccursSpec.Keys` / `OdoModel.KeyItems` — the ONE ordered model SEARCH ALL
  reads (PB445), so significance order and per-key direction agree between the two consumers by construction.
  Both key sources now build through one `TableSortKey` helper (the member-path rule cannot drift between them).
* `SortBinder.SortBindFile` — Format 1's braced at-least-one KEY phrase screened beside it, so the grammar
  relaxation cannot leak into the file sort.
* Goldens: `2002/pb846_sort_table_occurs_keys` (single key; DESCENDING-major/ASCENDING-minor table keys; the
  statement-KEY arm unchanged); negatives `pb846-sort-table-no-key-anywhere` (SR15, 2002+),
  `pb846-sort-file-no-key` (Format 1, all editions), `pb846-sort-table-key-omitted-below-2002` (COBOLNET0870 at 85).
* Rows: SR-14.9.40.3-15 and GR-14.9.40.4-21 re-verdicted CONFORMS (GAP 2276 → 2274). FMT-14.9.40.2 (the whole
  SORT general format) is NOT claimed — it needs a verdict over every phrase of both formats, not this one.
