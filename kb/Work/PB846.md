# PB846 — OPEN — the table SORT's KEY phrase is mandatory in the grammar and optional in the standard

Source: the `PB445` implementer report and its finisher report ("New defect found outside this mechanism"). The
finisher additionally CORRECTED the false half of `SortBinder`'s comment (it claimed the data model did not
capture the OCCURS KEY phrase; it always had), so what remains is exactly the grammar arity and the GR21 wiring.

## Repro — re-run on this tree

`scratchpad/reg4/probe/p10_sort_table_no_key.cob` (PROGRAM-ID `R4P10`), `--std 2023`:

```cobol
       01 T.
          05 TE OCCURS 5 ASCENDING KEY IS TK INDEXED BY IX.
             10 TK PIC 9.
       ...
           SORT TE
           DISPLAY "S=" TK(1) ...
```
```
(15,12): error COBOL0001: unexpected 'DISPLAY'
```

The parser consumes `SORT TE` and then demands the key phrase the source is entitled to omit.

## The rules, quoted

```
$ python scripts/spec/cite.py --check 14.9.40.3 "The KEY phrase may be omitted only if the description of the table referenced by data-name-2 contains a KEY phrase"
  OK  §14.9.40.3 15)  (Syntax rules)
$ python scripts/spec/cite.py --check 14.9.40.4 "If the KEY phrase is not specified, the sequence is determined by the KEY phrase in the data description entry of the table referenced by data-name-2"
  OK  §14.9.40.4 21)  (General rules)
```

SR15 makes the omission legal exactly when the table's OCCURS clause carries a KEY phrase; GR21 says what it
then means.

## Code sites

* `src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4:820` — `sortKeyPhrase+` on the Format-2 (table) alternative.
  It must become `sortKeyPhrase*`, with SR15 enforced at bind (the omission is legal ONLY with a table KEY
  phrase, so the screen moves from the grammar to the binder, where it can name the real rule).
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SortBinder.cs` — the GR21 arm reads `OdoModel.KeyItems` /
  `OccursSpec.Keys` (already in significance order after PB445).

## Sibling sweep the fixer owes
