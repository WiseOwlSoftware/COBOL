# PB3405 — the survey and the wave look for findings files in different places

Filed by the operator from PB3381's branch review (round 4 lead, low, not blocking; `w1125a-PB3381-report.md`, "Review
findings"), which PB3381 left open (`kb/Work/PB3381.md`: "the survey reads wave findings files only under
`<coord>/scratch` while the wave reads its own `--scratch`").

**The mechanism (on main at 49e1c6b79).** `scripts/orchestrator/review_findings.py` `findings_files(scratch, also)` lists
`review-*.jsonl` in the coordination scratch and in each directory directly under it, plus the paths report stamps name
(`also`). `prune_worktrees.py` calls it with the coordination scratch. The rolling wave reads and writes a group's file
under the wave's own `scratch` argument, which `plan_wave.py --scratch` can put anywhere. If that is not under
`<coord>/scratch` and a review finisher rewrote the group's report without its Review line (`carrying_findings`'s
docstring notes that a review finisher rewrites the report with no Review line), the file is in no place the survey
looks. The wave still reads the predecessor's findings and briefs the successor's reviewer from them. The survey reads
none, so `carrying_findings` does not hold the successor. In the `capped` case that is a release: the successor's
reviewer was told to leave the predecessor's findings to the predecessor's own finisher, so the successor's CLEAN says
nothing about them, and the landing lane can land them unanswered.

**The fix.** One place for the files, or one list of places. Either `plan_wave.py` refuses a `--scratch` outside
`<coord>/scratch` (the wave scratch is always `<coord>/scratch/w<wave>`), or the dispatch ledger records each wave's
scratch and `findings_files` reads that list as well. The self-test should plant a wave scratch outside the coordination
scratch with an unstamped FINDINGS file and assert that the survey holds the successor exactly as the wave does.

## 2026-10-31 — the same blind spot in the review lane's lease reading

Added by the clerk from `resume-20261030-review-lease-gap.md` (the previous loop unit's finding). `review_lane.standing` and
`review_lane.plan_review` find a reviewer's `start` record only through `review_findings.findings_files`, which lists
`<coord>/scratch/review-*.jsonl` and `<coord>/scratch/*/review-*.jsonl`. The Mythos wave w-g7 writes
`<coord>/scratch/mythos/w-g7/review-w20261780-<x>.jsonl`, two levels down, so the lane sees no lease from the wave's
reviewer. Once the report is `REPORT_GRACE_MIN` (5) minutes old, `plan_review` starts its own round-1 reviewer of the same
head.

**Observed (2026-10-31Z).**
- `worktree-wf_34371f8b-c21-2` @ be53df75b: wave reviewer `w20261780c-review-r1` started 03:08:16Z, verdict FINDINGS
  03:17:59Z. Lane run 000022 started 03:17:06Z and recorded the same R1-1 (medium) and R1-2 (low).
- `worktree-wf_34371f8b-c21-6` @ 8dfabe73b (PB4155/PB4160): wave reviewer `w20261780g-review-r1` started 03:31:42Z; lane
  run 000023 started 03:36:39Z.
- The resume unit ended both lane runs by hand (their claude children), about 03:40Z.

**Fix direction.** `findings_files` reads every wave scratch (one place for the files or one list of places, for example
the dispatch ledger's recorded `--scratch`), as the fix above already says. The self-test plants a wave scratch two levels
down with a `start` record and asserts the lane leases it. The masked-FINDINGS harm this duplicate causes is PB4194.

**Sites:** `scripts/orchestrator/review_findings.py` (`findings_files`), `scripts/orchestrator/review_lane.py` (`standing`, `plan_review`).
