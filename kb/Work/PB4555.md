# PB4555 — set-index-to-arithmetic-expression-refused: -std=cobol2014: SET index-name TO arithmetic-expression (and SET index-name UP BY arithmetic-expression) is refused ("syntax error, unexpected +")

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

cobc 3.2 refuses an arithmetic expression as the sending operand of SET Format 1 (index-assignment): `SET IX TO N + 3` gives "syntax error, unexpected +"; `SET IX UP BY N + 3` (Format 2) gives the same. ISO/IEC 1989:2002, 2014 and 2023 allow arithmetic-expression-1 / arithmetic-expression-2 there. Class: rejects legal source. Fuzz programs: fz00520, fz01226, fz01929 (slice D3).

## Minimal test case

Free reference format.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. SET1.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 N PIC 9 VALUE 2.
01 T.
   05 E PIC 9 OCCURS 9 TIMES INDEXED BY IX.
PROCEDURE DIVISION.
    MOVE "123456789" TO T
    SET IX TO N + 3
    DISPLAY E (IX)
    STOP RUN.
```

## Environment

`cobc (GnuCOBOL) 3.2.0`, WSL2 Ubuntu x86_64. Compiled with `cobc -x -free -std=cobol2014 -o set1.x set1.cob` (the same diagnostics under `-fsyntax-only`); no executable is produced.

## Observed result

Compile, exit code 1:

```text
set1.cob:10: error: syntax error, unexpected +
```

Variant set2 (`SET IX TO 1` then `SET IX UP BY N + 3`): `set2.cob:11: error: syntax error, unexpected +`, exit code 1.

## Expected result (per ISO)

The program is legal and prints `5` (IX refers to occurrence N + 3 = 5, which holds the digit 5).

- §14.9.39.2 (checked): "arithmetic-expression-1". Format 1 (index-assignment): `SET {index-name-1 | identifier-1} ... TO {arithmetic-expression-1 | index-name-2 | identifier-2}`.
- §14.9.39.3 (checked): "If identifier-1 references a data item of class index, arithmetic-expression-1 shall not be specified.". The only restriction on arithmetic-expression-1 concerns an index data item receiver; IX is an index-name.
- §14.9.39.4 (checked): "index-name-1 is set to a value causing it to refer to the table element that would correspond in occurrence number to that expression". General rule 2 a) 1. c.

Edition: 2014. The Format 1 arithmetic-expression-1 operand and the Format 2 arithmetic-expression-2 operand are in the 2002 text (cobolv200112, 14.8.35.1) and in the 2009 draft of 2014 (CD 1.2, 14.9.35.1).

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`): compiles with no diagnostic; the run prints `5`, exit code 0 (set2 prints `6`).

## Fix site

`cobc/parser.y`, rules `set_to` (`target_x_list TO x`) and `set_up_down` (`target_x_list up_or_down BY x`): the sending operand is an `x` (identifier or literal), not an arithmetic expression; `cb_emit_set_to` and `cb_emit_set_up_down` in `cobc/typeck.c` would need an expression operand. The two parser.y rules read the same in the 3.2 source; typeck.c was read in the 3.3-dev tree.

## Draft issue

**Title:** Accept an arithmetic expression in SET index TO, SET index or pointer UP / DOWN BY (COBOL 2002/2014)

As posted (owner-reviewed, 2026-11-04):

cobc refuses an arithmetic expression in `SET index-name TO`, `SET index-name UP BY / DOWN BY` and `SET data-pointer UP / DOWN BY`. A single operand works; any operator is a syntax error. This is a request to accept it; the attached patch implements it.

### To reproduce

`setexpr.cob` (attached):

~~~~
       IDENTIFICATION DIVISION.
       PROGRAM-ID. SETEXPR.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  N  PIC 9 VALUE 2.
       01  T  VALUE "ABCDEFGHI".
           05  E  PIC X OCCURS 9 TIMES INDEXED BY X Y.
       01  P  USAGE POINTER.
       01  C  PIC X BASED.
       PROCEDURE DIVISION.
           SET X Y TO N + 3
           DISPLAY E (X) E (Y)
           SET X UP BY N * 2
           DISPLAY E (X)
           SET X DOWN BY N - 1
           DISPLAY E (X)
           SET P TO ADDRESS OF T
           SET P UP BY N * 3
           SET ADDRESS OF C TO P
           DISPLAY C
           STOP RUN.
~~~~

    cobc -std=cobol2014 -x setexpr.cob && ./setexpr

### What happens

3.2.0 and 3.3-dev r5751 both stop with

~~~~
setexpr.cob:11: error: syntax error, unexpected +
setexpr.cob:13: error: syntax error, unexpected *
setexpr.cob:15: error: syntax error, unexpected -
setexpr.cob:18: error: syntax error, unexpected *
~~~~

each followed by its source excerpt. The result is the same with `-std=cobol2002`, `default`, `ibm` and `mf`. As a workaround, `SET X TO FUNCTION INTEGER (N + 3)` works on both.

### What should happen

Under `-std=cobol2002` and `-std=cobol2014` the program should print `EE`, `I` and `H` (occurrences 5, 9 and 8), then `G` (6 bytes into T). ISO/IEC 1989:2023 14.9.39.2 gives Formats 1, 2 and 10 (data-pointer-arithmetic) an arithmetic-expression operand. By general rule 2 a) 1. c. of 14.9.39.4, "index-name-1 is set to a value causing it to refer to the table element that would correspond in occurrence number to that expression"; by general rule 20, the pointer moves by that many bytes. The formats are the same in 2002 (where Format 10 is Format 9) and in the 2014 FCD.

### Why it happens

In `cobc/parser.y`, `set_to` (`target_x_list TO x`) and `set_up_down` (`target_x_list up_or_down BY x`) take an `x`, a single operand, not the `exp` that subscripts and COMPUTE use. The code behind them, `cb_emit_set_to` (`cb_build_move`) and `cb_emit_set_up_down` (`cb_build_add` / `cb_build_sub`), already handles an expression.

### Proposed fix

The attached `n10-set-index-expression.patch` (against 3.3-dev r5751) gives both rules a new `set_x`: an `exp`, or one of the non-arithmetic forms of `x`. The grammar stays conflict-free; a single operand compiles to the same C. In `typeck.c`, the new `cb_check_set_arith_expr` accepts a non-constant expression only for an index-name, or a data-pointer after UP BY / DOWN BY (syntax rules 1 to 4 and 23), and marks it `BOP_RESOLVE_AS_INTEGER`, as `cb_build_identifier` does for a subscript. Two things to weigh: a non-integer result is truncated, as for a subscript or a single operand, instead of raising EC-BOUND-SUBSCRIPT or EC-SIZE-ADDRESS; and one UP BY may still mix index-names and pointers, as it may with a single operand.

Patched, `setexpr` prints that output. The patch adds the testsuite cases "SET index / pointer by arithmetic expression" to `run_misc.at` and "SET TO / UP BY arithmetic expression, invalid target" to `syn_set.at`, with ChangeLog entries. `make check`: 1374 expected, 9 skipped, 0 failed (1372 unpatched); the new tests fail without the patch. The NIST suite results are unchanged.
