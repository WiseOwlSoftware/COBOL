# PB3936 — national-literal-as-integer-of-formatted-date-format-refused: National-literal format refused by FORMATTED-DATE / FORMATTED-TIME / INTEGER-OF-FORMATTED-DATE: "FUNCTION 'FORMATTED-DATE' has invalid date/time format"

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S10) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\national-literal-as-integer-of-formatted-date-format-refused.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\national-literal-as-integer-of-formatted-date-format-refused\`.

## Summary

GnuCOBOL 3.2 refuses `FUNCTION FORMATTED-DATE (N"YYYYMMDD", 1)` with `FUNCTION 'FORMATTED-DATE' has invalid date/time
format`. The same format as an alphanumeric literal, `"YYYYMMDD"`, compiles and gives the right answer. ISO/IEC 1989
lets argument-1 of these functions be "a national or alphanumeric literal" (§15.39.3 1)), and a national argument
makes the function national (§15.39.1). The functions and that rule are in the 2014 edition that `-std=cobol2014`
claims. The compile-time format check reads the national literal's stored bytes as single-byte characters, so no
national format can pass. `FORMATTED-TIME (N"hhmmss", 0)` and `INTEGER-OF-FORMATTED-DATE (N"YYYYMMDD", D)` fail the
same way. Legal source is refused, so this is a defect. The family is named for INTEGER-OF-FORMATTED-DATE, but the
night-6 witness and the minimal program use FORMATTED-DATE. All the ISO 8601 date and time functions share one check.

## Expected result (per ISO)

The program compiles and prints `OK`.

- §15.39.3 1) (checked): "Argument-1 shall be a national or alphanumeric literal." 2): its content shall be a date
  format. 3): argument-2 is in integer date form.
- §15.39.1 (checked): the function type follows argument-1, and a national argument gives a national function
  (table row `| National | National |`).
- §15.39.4 1) (checked): "The returned value is a representation of the date contained in argument-2 according to the
  format in argument-1."
- §15.3.1.2 (checked): "The basic calendar date format contains eight characters: four uppercase 'Y' characters
  representing the year subfield" with two 'M' and two 'D'. `YYYYMMDD` is that format whether it is written as an
  alphanumeric or a national literal.
- §15.5.2 (checked): the integer date form is "based on a starting date of Monday, January 1, 1601", so integer date 1
  is 16010101.
- The siblings: §15.41.3 1) (checked, FORMATTED-TIME) and §15.48.3 1) (checked, INTEGER-OF-FORMATTED-DATE) have the
  same "national or alphanumeric literal" rule. §15.48.3 3) (checked) requires INTEGER-OF-FORMATTED-DATE's argument-2
  to be "a data item of the same type as argument-1", which `sib.cob` meets with a PIC N item.

Edition: FORMATTED-DATE, FORMATTED-TIME and INTEGER-OF-FORMATTED-DATE, each with "Argument-1 shall be a national or
alphanumeric literal" and the Alphanumeric/National type table, are in the 2009 committee draft that became the 2014
edition (§15.35, §15.37 and §15.44 there). The 2023 Foreword's list of added or enhanced functions does not include them, and
Annex E records no change. These are 2014 features.

Edition as recorded by the adjudicator: 2014 (unchanged in 2023). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/tree.c`, `cb_build_intrinsic` (starts line 6990). For any `iso_8601_func` (line 931: FORMATTED-CURRENT-DATE,
  FORMATTED-DATE, FORMATTED-DATETIME, FORMATTED-TIME, INTEGER-OF-FORMATTED-DATE, SECONDS-FROM-FORMATTED-TIME,
  TEST-FORMATTED-DATETIME) it calls `valid_const_date_time_args` (line 990, called at line 7069).
  `try_get_constant_data` (line 976) returns the literal's raw stored data, and `valid_format` (line 943) passes it
  to `cob_valid_date_format` / `cob_valid_time_format` / `cob_valid_datetime_format`, which read single-byte
  characters. A national literal's stored data is national code units, so the check fails. A fix converts a national
  literal's content to its alphanumeric spelling before the check, or checks it as national.
- `libcob/intrinsic.c`, `cob_intr_formatted_date` (line 6537), and likewise `cob_intr_formatted_time` (6579),
  `cob_intr_formatted_datetime` (6671) and `cob_intr_integer_of_formatted_date` (6877). They copy the format with
  `copy_data_to_null_terminated_str` and always build the result with `const_alpha_attr`. Once compilation accepts
  the national form, these routines also need to read a national format and return a national result, as §15.39.1
  requires.

## Draft issue

**Title:** National-literal format refused by FORMATTED-DATE / FORMATTED-TIME / INTEGER-OF-FORMATTED-DATE: "FUNCTION 'FORMATTED-DATE' has invalid date/time format"

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1), x86_64 Linux.

Steps: `cobc -std=cobol2014 -fformat=free -x fdm.cob && ./fdm` with

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. FDM.
PROCEDURE DIVISION.
    IF FUNCTION FORMATTED-DATE (N"YYYYMMDD", 1) = N"16010101"
        DISPLAY "OK"
    ELSE
        DISPLAY "WRONG"
    END-IF
    STOP RUN.
```

Observed: `fdm.cob:4: error: FUNCTION 'FORMATTED-DATE' has invalid date/time format` (exit 1); the same without
`-std`. The same program with alphanumeric literals (`"YYYYMMDD"`, `"16010101"`) compiles and prints `OK`.
`FUNCTION FORMATTED-TIME (N"hhmmss", 0)` and `FUNCTION INTEGER-OF-FORMATTED-DATE (N"YYYYMMDD", D)` with `D PIC N(8)`
fail with the same message.

Expected: the program compiles and prints `OK`. ISO/IEC 1989:2014 (§15.39.3 in the 2023 edition) for FORMATTED-DATE:
"Argument-1 shall be a national or alphanumeric literal". A national argument-1 makes the function national
(§15.39.1). FORMATTED-TIME (§15.41.3) and INTEGER-OF-FORMATTED-DATE (§15.48.3) have the same rule.

In `cobc/tree.c`, `valid_const_date_time_args` takes the literal's raw data from `try_get_constant_data` and validates
it with the single-byte `cob_valid_*_format` routines, so a national literal never passes. The runtime routines in
`libcob/intrinsic.c` (`cob_intr_formatted_date` and siblings) also always return an alphanumeric field and will need
national handling.
