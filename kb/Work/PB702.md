## Landed 2026-09-06

Both rows are now `CONFORMS`, recorded through one `record_verdicts.py` batch (2 records submitted, 2 accepted,
GAP 2820 → 2818 of 4371 — the delta equals the rows meant, per the per-record-drop hazard the script's doctrine
names).

**`GR-14.9.35.4-24`.** The row was re-derived from the printed rule rather than from the finding, and it carries
SIX obligations, not two: a) and b), the two SUPPRESS WHEN sub-rules, the collating-sequence change test, and the
closing pair ("Any number of records may have the same alternate key value equal to its key suppression value
without requiring the DUPLICATES phrase", "Key entries that are suppressed shall not cause a duplicate key
condition to exist"). `conformance:2023/l1_rewrite_alt_key_order` (PB341) already pinned a), b) and the collating
sentence. `tests/conformance/2023/altkey_suppress_when.cob` was read as the note asked and does NOT cover the
REWRITE transitions — it exercises WRITE-time suppression plus the READ/START access path (§12.4.5.6.4 GR6) and
never rewrites a key into or out of its suppression value. So a sibling golden was written:
`tests/conformance/2023/l1_rewrite_alt_key_suppress.cob` (`PROGRAM-ID. L1RWSUP`), with two alternate keys — one
`WITH DUPLICATES SUPPRESS WHEN "XX"`, one with NO `DUPLICATES` phrase and `SUPPRESS WHEN "ZZ"` — and five legs:
a baseline pair of walks; a REWRITE that ENTERS suppression (the access path is withdrawn); a REWRITE that LEAVES
it (the path is restored and GR24 b) puts the record LAST in the duplicate set it had been FIRST in on release);
two REWRITEs that put two records at the suppression value of a key with no `DUPLICATES` phrase (both `'00'`, not
the `'22'` a real duplicate raises); and a CLOSE/re-OPEN that shows both survive the physical file. **All twenty
expected lines were computed from the standard and written before the first run, and the compiler matched them
byte for byte** — so the row is CONFORMS on measurement, not on a reading.

**Editions.** a), b) and the collating sentence: 85 / 2002 / 2014 / 2023 (ALTERNATE RECORD KEY and DUPLICATES are
ungated here, the clause carries no edition marker, Annex E lists no change to §14.9.35 — the band the sibling
rows `GR-14.9.30.4-26` and `GR-14.9.30.4-32` were landed at on the same golden). The two SUPPRESS WHEN sub-rules
and the closing pair are 2023-ONLY and therefore vacuous, not unverified, below it: SUPPRESS WHEN is a COBOL-2023
addition (`cite.py --check E.3.3 "The SUPPRESS WHEN phrase may be specified as part of the ALTERNATE RECORD KEY
clause"` → OK, item 42) gated by the `alternate-key-suppress-when-2023` construct row (COBOLNET0900 below 2023).
The row's `notes` carry the `EDITIONS AS ADJUDICATED` sentence saying so, PB659/PB672's convention for a rule
whose sub-rules straddle editions.

**`SR-12.4.5.2-7`.** Both halves ("shall reference an alphanumeric data item"; "shall not be subordinate to the
file description entry for file-name-1", `cite.py --check 12.4.5.2` → OK, rule 7) are one site,
`DataBinder.ResolveAssignUsing`, and both were re-measured on this tree rather than trusted:
`cobol pb324-assign-using-not-alphanumeric.cob --std 85` → COBOLNET1810, `cobol pb324-assign-using-in-own-record.cob
--std 2023` → COBOLNET1811. The two negative goldens carry `*> reject-at: 85 2002 2014 2023`, so the rejecting arm
is asserted at every edition; the ACCEPTING arm — the complement a rejection test can never measure — is
`conformance:2023/pb324_assign_using_dynamic` and `conformance:85/pb324_assign_using_85`, both naming a
WORKING-STORAGE `PIC X(20)` outside the FD. All four refs are on the row.
