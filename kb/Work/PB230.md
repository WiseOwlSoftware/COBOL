# PB230

**Rows:** `GR-14.9.2.4-6`, `GR-14.9.8.4-1`, `GR-14.9.8.4-3`, `GR-14.9.12.4-3`

`>>TURN EC-DATA-INCOMPATIBLE CHECKING ON` is inert for every arithmetic statement — EcBinder gates the condition on `node is BoundMove`, so `ADD 1 TO N` over a DISPLAY item holding 'AB1' continues silently where §14.6.13.2 rule 2 makes the condition exist.

Rows: GR-14.9.2.4-6 (ADD's pointer rule — §14.7.4, §14.7.5, §14.7.6, §14.7.7 and §14.6.13.2), GR-14.9.8.4-1 (COMPUTE arm (a), 'within the constraints specified in 14.6.13.2'), GR-14.9.8.4-3 (COMPUTE's boolean form, 'subject to 14.6.13.2'). ONE literal type test, three rules that import the condition and never get it.

MECHANISM, re-verified live at HEAD. EcBinder.EcWrap:530 reads `if (node is BoundMove && ctx.EcState.Turn.Enabled("EC-DATA-INCOMPATIBLE", null, line))`. The comment above it scopes the family to §14.6.13.2 rule 4 — a de-editing MOVE whose numeric-edited sender holds impossible content — and EcEmitter.cs:150 carries the same MOVE-only note. No other node kind can contribute the family, so no ADD, no COMPUTE, no SUBTRACT/MULTIPLY/DIVIDE and no CORRESPONDING form is even made CHECKABLE for it.

WHY THAT IS SHORT OF THE RULE. §14.6.13.2 rule 2 (re-read in full at specs/ISO_COBOL.md:21630-21664 on the GR-14.9.2.4-6 row) makes EC-DATA-INCOMPATIBLE exist whenever the content of a NUMERIC sending item that is not standard-floating-point 'is referenced during the execution of a statement' and would fail a numeric class condition. An ADD's identifier-1 qualifies; its Format-2 identifier-2 qualifies; and per rule 2's NOTE 2 ('The content of a data item is not referenced when the data item is a receiving operand, UNLESS that data item is also a sending data item') so does the Format-1 identifier-2 read that ArithmeticEmitter.EmitInPlace emits as `num.FieldNum(r.Place)`. A COMPUTE's arithmetic-expression-1 and its boolean form's operands qualify the same way.

THE OBSERVABLE. With `>>TURN EC-DATA-INCOMPATIBLE CHECKING ON`, `ADD 1 TO N` where N is PIC 9(3) DISPLAY holding 'AB1' does NOT set the condition. CobolNum's DISPLAY decode contributes no digit for a non-digit position (documented at CobolNum.cs:630-639 — conforming while checking is OFF, because the result is then undefined) and execution continues silently with a fabricated value. That is a program which explicitly asked to be checked and was not.

THE CORRESPONDING LEVEL IS SHORT TOO. §14.7.6's last paragraph — 'For any statement with the CORRESPONDING phrase, if any of the implied statements would set the EC-DATA-INCOMPATIBLE exception condition to exist, [it] is set to exist after all of the implied statements are completed' — is unreachable for ADD CORRESPONDING for the same EcWrap reason. So §14.9.2.4 GR6's pointer rule is short on this one leg TWICE, statement-level and CORRESPONDING-level, while its other four legs ARE genuinely wired: §14.7.4 ROUNDED through ExpressionBinder.RoundingOf per receiving operand and per CORR statement with the ROUNDED MODE IS edition gate inside it (conformance:2014/corresponding_rounded_mode); §14.7.5 SIZE ERROR's two-phase shape in ArithmeticEmitter.EmitArith:225-275 — phase-a evaluation failures leave every receiver unchanged, phase-b per-receiver TryStore failures leave only that receiver unchanged — pinned on ADD specifically by conformance:85/phrase_order_arithmetic and conformance:85/optional_on_size_error; §14.7.7 rule 2 as StatementValidation.CheckComposite and rule 4 + NOTE 3 as the Snapshot one-initial-evaluation discipline.

WHAT ELSE THESE ROWS ALREADY HAVE, so the note is not read as doubting them. GR-14.9.8.4-1's other named gaps were discharged by PB157: conformance:2014/pb157_compute_sdidi_sole pins a SOLE fixed-point data item AND a sole fixed-point literal under ARITHMETIC IS STANDARD-DECIMAL, each ROUNDED into a narrower receiver (2.25 → 2.3 both ways, where production-side alignment would answer 2.2), and the standard-binary NOTE is unreachable by decision (COBOLNET0806 rejects ARITHMETIC IS STANDARD-BINARY as obsolete). GR-14.9.8.4-3 was moved off DIVERGES by PB157 — Gr3Width, BoolExprAllLengthOne/RefModLen and the EmitComputeBoolean store width now read OperandPic, so a bit GROUP contributes its as-if 1(m) boolean positions instead of 0; conformance:2023/pb157_compute_bit_group's W8 mixes a 6-position bit group with a 3-position elementary and pins 11011000 where the old Gr3Width-0 bug answered 11000000, beside the truncate-into-1(3), zero-fill-into-1(8) and multi-target legs — and its bit-position-substrate half was retired by PB173 (BitImagePlace IS §8.4.3.3.4 GR5a's bit positions, carrying the §13.18.38.4 GR8a current-extent arm on both read and write, pinned by conformance:2023/pb79_group_usage_bit).

ONE RESIDUE THAT IS NOT THIS MECHANISM, carried so it is not lost: GR-14.9.8.4-3 also names RefModLen's NON-LITERAL ref-mod length still falling back to the inner item's FULL length. That is a ref-mod length defect, not an EC one; if the director prefers it filed with the ref-mod family (open PB202/PB205 are adjacent but neither owns it) it should move, and this note keeps only the §14.6.13.2 leg of that row.

WHAT WOULD CLOSE IT: widen the EcWrap gate from `node is BoundMove` to any statement carrying a fixed-point numeric SENDING reference — a precise 'references a DISPLAY/packed numeric sender' filter is better than a node-kind list, since the node-kind list is what produced this defect — add the §14.7.6 last-paragraph aggregation for the CORRESPONDING forms, and ship goldens turning EC-DATA-INCOMPATIBLE checking on around (i) an ADD over an item holding non-numeric content, (ii) a COMPUTE over the same, (iii) an ADD CORRESPONDING where one implied statement would set it.

SPEC REFS as carried by the rows: §14.6.13.2 rules 1/2/4 and NOTE 2; §14.9.2.4 GR6; §14.9.8.4 GR1a, GR3; §14.7.4, §14.7.5, §14.7.6 (last paragraph), §14.7.7 rules 2 and 4 + NOTE 3; §8.4.3.3.4 GR5a; §13.18.38.4 GR8a; §8.8.2 rule 9.

## The DIVIDE row, merged in (GR-14.9.12.4-3 — the same `EcBinder` gate, found independently)

ROW: GR-14.9.12.4-3 (PARTIAL — GR3 is DIVIDE's pointer rule at §14.7.4 / §14.7.5 / §14.7.7 / §14.6.13.2, adjudicated as 'is each referenced mechanism actually wired to DIVIDE').

THREE OF THE FOUR ARE WIRED, and the fourth's neighbour has since landed. ROUNDED (§14.7.4) reaches DIVIDE through ExpressionBinder.RoundingOf per receiver, pinned by RoundedDifferentialTests.DivideGivingRounded_ModeIs (`DIVIDE 10 INTO 25 GIVING R ROUNDED MODE IS NEAREST-EVEN` asserted = 002 — a hand-derived spec value, AssertOutput not AssertSameAsLegacy). SIZE ERROR (§14.7.5) is ArithmeticEmitter.EmitArith's two-phase shape, pinned by OnSizeErrorDifferentialTests.DivideByZero_FiresOnSizeError_ReceiverUnchanged and ExceptionConditionConformanceTests.SizeError_ZeroDivide_DeclarativeSeesPreciseName_ReceiverUnchanged. §14.7.7 is StatementValidation.CheckComposite plus the Snapshot discipline — and its rule 4b leg, reported broken by this row's refuter, is now correct: PB129 landed per-receiver `GuardedStore`, and rows GR-14.9.12.4-4/-5 read 'every receiver's compute+store sits in its own try … a raise at one receiver proceeds to the next resulting data item per 14.7.7 r4b', with conformance:2014/pb129_store_discipline as evidence.

THE ONE LIVE RESIDUE. §14.6.13.2 rule 2 makes EC-DATA-INCOMPATIBLE exist whenever the content of a NUMERIC sending item that is not standard-floating-point 'is referenced during the execution of a statement' and would fail a numeric class condition — with exactly two carve-outs (the class condition itself, and VALIDATE). It is not MOVE-specific; rule 4 IS ('the sending operand of a de-editing MOVE statement'). EcWrap implements only rule 4: the hoist at EcBinder.cs:530 tests `node is BoundMove` before it even consults the >>TURN state, so no DIVIDE, ADD, SUBTRACT, MULTIPLY, COMPUTE or comparison can ever contribute the condition.

WHAT THAT DOES TO A USER PROGRAM. Under `>>TURN EC-DATA-INCOMPATIBLE CHECKING ON`, `DIVIDE A INTO B` where A is PIC 9(3) DISPLAY holding 'AB1' does NOT set the condition: CobolNum's DISPLAY decode contributes no digit for a non-digit position (conforming while checking is OFF, because the result is then undefined by the standard) and execution continues silently with a fabricated value. The program asked for the check, the compiler accepted the directive, and the check does not exist — the declarative or handler the programmer wrote never runs. Silent, and invisible to output sampling.

WHAT CLOSES IT: widen the EcWrap gate from `node is BoundMove` to any statement carrying a fixed-point numeric SENDING reference (or a precise 'references a DISPLAY/packed numeric sender' filter), keeping rule 4's separate de-editing arm; then a golden turning EC-DATA-INCOMPATIBLE checking ON around a DIVIDE over an item holding non-numeric content, plus its ADD twin. ⛔ Sweep, do not patch DIVIDE: this is ONE rule written in ONE place and the fix changes the predicate, not the call sites — GR-14.9.2.4-6 records the identical shortfall for ADD, so the two close together or not at all.

SPEC REFS (carried from the row): §14.9.12.4 GR3 (--check OK on 'Additional rules and explanations relative to this statement are given in'); §14.6.13.2 rules 2 and 4; §14.7.4, §14.7.5, §14.7.7 (rule 4 a)/b) --check OK on 'processing proceeds to the next resulting data item to the right').

**Merged mechanism:** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.cs#EcWrap — the hoist is gated at EcBinder.cs:530 on `if (node is BoundMove && ctx.EcState.Turn.Enabled("EC-DATA-INCOMPATIBLE", null, line)) enabled.Add(("EC-DATA-INCOMPATIBLE", null));`, with the comment at :528 scoping it to §14.6.13.2 rule 4's de-editing MOVE. Rule 2 — the broad one — has no wiring at all.
