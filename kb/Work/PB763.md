## ⛔ Premise correction — the exit code is not the defect, and the real one is worse

The report states the script *"exits 0, and no test reads it"*, and concludes *"a loud ⛔ that exits 0 and has no
test is not a gate"*. The first half is true of the DEFAULT run and false of `--check`, and the correction
sharpens the finding rather than softening it.

`:836-838` already has the non-zero path, and **`changed` is in it**:

```python
if args.check:
    return 1 if (gaps or unrecognised or added or removed or changed or unexplained
                 or heading_labels or flattened_tails) else 0
```

**Measured: `python scripts/spec/extract_rule_catalog.py --check` exits 1 on main today.** So the check is not
missing. It is **never invoked**:

- `grep -rn "extract_rule_catalog" .github/ scripts/ tests/` returns **zero invocations**. Every hit is a
  doc-comment reference or a Python import: `audit_catalog_coverage.py:35` imports symbols from it;
  `build_inventory.py:72`, `extract_annex_a2.py:150` and `inventory_schema.py:726` only name it inside a
  *"catalog not found — Run: python scripts/spec/extract_rule_catalog.py"* error string;
  `CatalogCoverageDriftTests.cs` and `SpecTraceabilityInventoryDriftTests.cs:272` mention it in prose and in a
  failure message.
- `.github/workflows/build-and-test.yml` does not mention it. `scripts/build-local.ps1`, `scripts/build-local.sh`
  and `scripts/battery.sh` run `audit_code_citations.py --check` and **not** this one — and `battery.sh:46`
  carries the exact warning this note re-earns: *"⛔ AND THERE ARE TWO OF THEM, BECAUSE ONE OF THEM RAN FOR
  MONTHS WITH NOBODY READING IT."*

⭐ **A red gate that nothing runs is worse than a missing gate**, because the repo LOOKS instrumented: the code
is there, it is correct, it returns the right status, and a reader auditing for coverage finds it and stops.
`feedback_green_gates_arent_evidence` — a passing check proves nothing if it never looked at what changed; this
one is not even passing, it is not being asked.

## ⛔ Second correction — the manifest's `ordinals` has exactly one reader, and it is this script

A first pass at this note recorded that `spec-unharvested-rule-blocks.json` is read only by
`extract_rule_catalog.py`. That was a grep on the literal filename and it was **wrong**:
`audit_catalog_coverage.py:132-135` reads the same manifest through the imported `UNHARVESTED` constant. Checked
properly, the conclusion survives in a narrower and more useful form:

- `audit_catalog_coverage.py` reads only `info["disposition"]` and `info["kind"]`. **It never reads
  `ordinals`**, so the 23 → 21 drift is invisible to it as well.
- And it is **equally ungated** — `grep -rn "audit_catalog_coverage" .github/ scripts/*.sh scripts/*.ps1 tests/`
  returns nothing.

So the count that measures whether the P14 **denominator** is short has exactly one consumer, in a script no
gate invokes, alongside a second catalog critic no gate invokes either. Recorded as a correction rather than
quietly fixed, because the wrong version was the more alarming one and a later reader deserves the real shape.

## The drift is real, and its cause is already adjudicated

`docs/rearchitecture/spec-unharvested-rule-blocks.json`, `blocks["9.3.6"]` (*"Method invocation"*) declares
`"ordinals": 23`, `"disposition": "rules"`, `"kind": "GR"`, admitted 2026-08-04 under [[PB29]]. The extractor
now measures **21**, and the reason is known: [[PB698]] (landed) repaired 23 nested-list sub-items transcribed at
column 0 across 14 clauses — **§9.3.6 among them, by name** — so two of §9.3.6's former top-level ordinals became
sub-items. The measurement is right and the manifest is stale. This is a real, correct, un-collected signal, not
a false alarm — which makes it the ideal first subject for the gate.

## The fix shape

⛔ **Not "make the default run exit non-zero."** The default run is a GENERATOR — it writes the 2.2 MB catalog
`build_inventory.py` and `inventory_schema.py` depend on — and failing it would break regeneration for everyone
who legitimately runs it while a drift is open. `--check` is already the right seam.

1. ⭐ **Wire `extract_rule_catalog.py --check` into a gate that actually runs.** Two sites, and the repo's own
   architecture picks between them: `scripts/build-local.{sh,ps1}` and `scripts/battery.sh` already run
   `audit_code_citations.py --check` and are the established home for spec-side Python gates — add it there,
   beside the audit whose comment warns about exactly this failure. If it is wanted every build rather than
   every gate run, the C# battery is the precedent (`CatalogCoverageDriftTests.cs` already re-implements catalog
   critics in C# for that reason, and `record_verdicts.py` states the doctrine explicitly: a predicate that must
   keep holding as the tree changes belongs to something that runs every build). ⛔ **Do not implement it in
   both** — that is the duplication CLAUDE.md rule 5 forbids, and the same doctrine `record_verdicts.py` cites.
   While wiring it, add `audit_catalog_coverage.py` to the same line or record why it stays manual; two ungated
   critics is the finding, not one.
2. **Then correct `blocks["9.3.6"].ordinals` to 21**, with the reason written into its `why` in the same
   style the existing entry uses — a PB698 adjudication (two ordinals became sub-items at the repaired
   indentation), not a number nudged until the tool stopped complaining.
3. ⛔ **ORDER IS THE DELIVERABLE, not a nicety.** Wire the gate FIRST and watch it go **red on the live §9.3.6
   drift**, then correct the manifest and watch it go green. `feedback_prove_the_watchdog_fails`: a monitor is a
   gate, and its failure branch must fire once before its silence means anything. Correcting the manifest first
   would destroy the only free, real, already-present failure this gate will ever get handed —
   `feedback_green_gates_arent_evidence` in one move.

## Sweep

- **The class is "a spec-side Python critic with a `--check` mode that no gate invokes."** Measured against the
  three gate scripts: `audit_code_citations.py --check` IS wired (`build-local.ps1:19`, `build-local.sh:25`,
  `battery.sh:52`); `extract_rule_catalog.py --check` and `audit_catalog_coverage.py` are **not**. Any further
  `scripts/spec/*.py` gaining a `--check` should be wired in the same commit — that is the drift rule this note
  earns, and it is one line in an existing script rather than a new register (CLAUDE.md rule 8).
- **Not this note, and deliberately excluded**: [[PB698]] is LANDED and its repair is correct — the drift is its
  true consequence, not a regression in it. [[PB718]] and [[PB719]] are the same transcription family one level
  up and explicitly *"move no catalog row, so no drift test can see it"* — a different hole (nothing to
  measure) from this one (measured, printed, uncollected). [[PB29]] is the landed campaign that admitted §9.3.6
  to the manifest in the first place; its `why` text is the model for the corrected entry.
