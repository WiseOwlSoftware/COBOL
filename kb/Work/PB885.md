# PB885 — LANDED 2026-09-22 — a reference the binder parses, keeps the name of, and throws the subscript away

Source: the train-35 lander report, "Findings for the register" item 2 (named in the guard's own comment so
the next reader would find it) — and the train-34 lander passed the same shape through unverified.
**Re-measured here rather than trusted.**

## The measurement

`<scratch>/reg6/probe/q48_report_odo_sub.cob` (PROGRAM-ID `R6Q48`), `--std 2023 --run`:

```cobol
WORKING-STORAGE SECTION.
01 WS-T.
   05 WS-TE PIC 9 OCCURS 3 TIMES.
REPORT SECTION.
01 DTL TYPE IS DETAIL.
   02 LINE 1.
      03 COLUMN 1 PIC X OCCURS 1 TO 3 TIMES
         DEPENDING ON WS-TE (2) STEP 2 VALUE "A".
PROCEDURE DIVISION.
    MOVE 2 TO WS-TE (2)
```

Compiles clean (`rc=0`) and `r6q48.txt` holds:

```
A A A
```

**THREE occurrences where `WS-TE (2)` is 2 and two are owed.** No diagnostic at any `--std`, no run-time
condition. The subscript is gone, so the DEPENDING operand is not the item the program wrote.

## The code site

`src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs:778` — `ReportOccursOf`'s `KeyReference` keeps the
name and discards the subscript list the grammar's `dataReference` produced.

**The converse arm in the same file is right**: PB482's COBOLNET2046 refuses a subscripted `UPON` operand.
One file, two report-section operand readers, one of them silent — the two-arm dispatch shape
(memory `two_arm_dispatch`), and this is the arm nobody fixed.

## What the fix has to decide (and cite)

Whether §13.18.38.3's DEPENDING operand may be subscripted at all is the first question, and it is a SPEC
question, not a code question: if it may, the subscript must be BOUND and evaluated per GR; if it may not, the
refusal is COBOLNET2046's, spelled for this operand. **Either answer is a fix; silently dropping it is
neither.** Derive it from §13.18.38.3 and §13.18.38.4 before touching the binder, and pin the answer with a
golden at the introducing edition plus a negative.

## The sibling sweep

Every REPORT SECTION clause that takes an identifier operand and reads it with a bespoke helper rather than
the procedure-division reference resolver: SUM (`SUM WS-A`, PB882/PB883), UPON (refused), SOURCE (PB852),
PRESENT WHEN, VARYING, LINE/COLUMN's own relative operands, CONTROL. The general probe is the same in each
case — write the operand WITH a subscript and see whether the compiler refuses it, honours it, or forgets it.

## Landed — 2026-09-22 (wave 46 L, with PB853)

RE-PROBED FIRST on this worktree's own build (base `8fe62bd1f`): `q48_report_odo_sub.cob` still compiled clean
and printed `A A A` — three repetitions where `WS-TE (2) = 2` owes two.

THE SPEC QUESTION THE NOTE POSED, ANSWERED: §13.18.38.3 SR2 is an ALL-FORMATS rule —
`cite.py --check 13.18.38.3 "Data-name-1 and data-name-2 shall not be subscripted."` → `OK §13.18.38.3 2)` —
so the operand may NOT be subscripted and the fix is a refusal, not a binding. `ReportOccursOf` now captures
data-name-1 through `ClauseDataName`, the ONE data-name-n screen the FD clauses and file-control keys already
used (COBOLNET2024, whose descriptor now names the OCCURS phrases), and `ResolveReportOccursDepending` resolves
through `ResolveClauseOperand` (survivor-counting, silent for a refused operand) instead of the report binder's
first-match `LookupQualified`.

THE OTHER ARM, which the note's sweep did not name: the DATA-DIVISION OCCURS clause captured the same operand
with `dataReference()?.GetText()`. Measured: `DEPENDING ON CNT OF G1` became the undefined `CNTOFG1` — LEGAL
SOURCE REJECTED (COBOLNET0851) — and `DEPENDING ON WS-TE (2)` drew "not defined" instead of SR2. The KEY capture
dropped a subscript in silence (SR2/SR5) and `CAPACITY IN CAP3 (1)` silently defined a register spelled
`CAP3(1)` (SR31). All three now go through `ClauseDataName`; `OccursSpec.DependingQualifiers` carries the
qualifiers and `OdoResolve` resolves a qualified data-name-1 through `QualifiedCandidates`. ⚠ DETERMINATION: a
QUALIFIED `CAPACITY IN` operand is refused too — data-name-3 is DEFINED by the phrase (SR30), and a defining
occurrence is a bare data-name. `OccursOperandCaptureDriftTests` pins that no binder file captures an operand by
gluing its tokens, and that `KeyReference`'s callers are the named report operands whose rules permit or screen
what it drops.

Goldens: `85/pb885_odo_depending_qualified` → `[AA]`, `2002/pb885_report_depending_qualified` → `[A A]`
(§13.18.38.4 GR7/GR13 with CNT OF G1 = 2, CNT OF G2 = 3); negatives `pb885-report-depending-subscripted`
(2002+), `pb885-odo-depending-subscripted`, `pb885-occurs-key-subscripted` (all editions),
`pb885-capacity-subscripted` (2014+).
