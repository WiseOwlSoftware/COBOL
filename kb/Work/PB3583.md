# PB3583 — LANDED — contained() spawned one git merge-base per pair of branches

`scripts/prune_worktrees.py` `contained()` asked, for every candidate row and every carrier row,
`git merge-base --is-ancestor <candidate tip> <carrier tip>`: R × C processes. The survey runs in the session probe, the
loop's planner and every `--brief`, and its self-test runs it over many scenarios: in a `GIT_TRACE2` of the self-test,
1,746 of its 4,636 git processes were these sha-to-sha ancestry calls (PB3582), on Windows about 50 ms each.

## The fix

One `git rev-list <carrier tip> ^refs/remotes/origin/main` per carrier, read into a set; a candidate is contained when
its tip is in a carrier's set. Exact, not an approximation: a candidate is never MERGED (`LANDED_CONTENT`; `classify()`
reads `--is-ancestor <branch> origin/main`), so its tip is no ancestor of origin/main, and it is an ancestor of a carrier
tip exactly when it is one of the commits that tip has beyond origin/main. No candidate, no git call at all.

Measured: see the landing's DEVLOG entry (git processes and seconds of the self-test, before and after).
