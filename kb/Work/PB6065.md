# PB6065 - the writer, the planner and the stored-record check each decide from the decision, not the row's state

One mechanism: a decision about a row is acted on without asking `Schema.state_for` whether the row is already OK.

1. `lineage_reads.py#own_stored_errors` (line 1297) refuses a stored own verdict whose rule's read decides
   `own-verdict-from-pointer` when it carries no test-ref, "an own verdict from a read carries no test-ref of its own", even when
   a derivation closes the row (`state_for` OK).
2. `lineage_reads.py#unwitnessed` plans every `OWN_VERDICT_FROM_POINTER` decision refused for evidence without reading the row's
   state, so a rule already closed on a test or a derivation is still planned by `widen`. The decisions loop in `bare_kept` has the
   same blindness (a KEPT row closed on its own derivation is added back from a read decision, refused only `NO_OWN_WITNESS`),
   the stored record that used to win the dedup (`out.get(rule_id)`) being gone.
3. `record_verdicts.py#validate`, chained branch (line ~472), runs `statement_losses` on the re-recorded row, so re-classifying an
   older-edition CHANGED row that holds a verdict as KEPT is refused both ways: `next_errors` refuses the verdict kept (a KEPT rule
   holds no verdict) and the loss check refuses it blanked. The deadlock was in `audit_witness_loss`; the branch moved it into the
   writer.
4. Neither the format test in `own_problems` (granted, line ~757) nor the dedup in `stored_errors` (line ~1482) is pinned:
   reverting either leaves `test_reads.py` PASS (19 cases, 140 expectations), both mutants verified to load (PB5754 R2-1).

Fix in one change: the planner and the stored-record check skip a decision whose row state is OK, the writer lets a CHANGED to
KEPT re-classification drop the verdict it can no longer hold, and a test pins each.

**Sites:** `scripts/spec/lineage_reads.py` (`own_stored_errors`, `unwitnessed`, `bare_kept`, `own_problems`, `stored_errors`),
`scripts/spec/record_verdicts.py#validate`, `scripts/spec/test_reads.py`.
