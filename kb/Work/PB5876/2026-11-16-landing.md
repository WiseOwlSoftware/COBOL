# Landing, 2026-11-16: an OCCURS DEPENDING ON object is an implicit reference, asked by the LINKAGE screen

**Re-probe before the fix** (`run_probe.py`, `lk_odo.cob`, `--std 85`): exit 0, `S L1E1=A`, `S L1=` (LN read as zero).
**After:** COBOL2746 at `DISPLAY L1`, at `--std 85` (citing `§1985:X.5.1 GR4`, `§1985:IV.4.4.1`) and at `--std 2023`
(citing `§2023:13.7.3 SR4`, `§2023:8.4.5`).

**2023 from its own text.** `§2023:8.4.5`: "An implicit reference in a procedure division statement occurs when the name
of the data item is not written in that procedure division statement and it contributes to, or is affected by, the
execution of the statement", so SR4's "may be referenced within the procedure division" reaches it as 1985's does
(2014 `§2014:8.4.4`, 2002 `§2002:8.4.4` the same). kb/Work PB1249's reading (written references only) is overturned.

**Shape.** The objects asked are the ones the operand's PLACE evaluates: `OdoDependence.ExtentObjects` (the
occurs-depending group extents of the one `Rebind` walk, split from the GR7 bound tests, which ride a path only when
EC-BOUND-ODO can be enabled, so the verdict never depends on a compile option), asked by
`NameResolution.ScreenImplicitLinkageReferences` in `ReferenceResolver.ResolveImplCore` beside the explicit screen; a
reference the explicit screen refused is not refused twice. Sibling arms found by probe (`lk_odo2.cob`, `lk_odo3.cob`): a
WORKING-STORAGE table DEPENDING ON the Linkage item (refused by the same screen), a reference-modified operand (same),
and SEARCH, whose end is the table's current number of occurrences (`SearchBinder.SearchDepending`, now screened). An
element reference `L1E (1)` is not refused. COBOL2746's explicit wording now cites the edition's own rule (1985: no BASED).

**Goldens.** 1985: `pb5876-linkage-odo-object-not-referenceable` (refused) and `pb5876-linkage-odo-object-using-operand`
(the control, `S L1=ABC`). 2023: `cases/13.7-Linkage-section/pb5876-linkage-odo-object-search` (refused at 2014, 2023).

**Left as a lead (another site):** the file clause operands (`FileModel.ClauseOperandItems`: FILE STATUS, RELATIVE KEY,
LINAGE, RECORD DEPENDING) in a non-operand Linkage record are implicit references of every I/O statement on the file;
`lk_odo3.cob`'s `OPEN OUTPUT F1` with `FILE STATUS IS LFS` in such a record compiles (exit 0). No I/O-statement funnel
asks it.
