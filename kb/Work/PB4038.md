# PB4038 — a unit's handoff is checked against the schema only after the unit has ended

## What happened

The enqueue unit that started at 19:18 on 2026-10-28 landed its work, wound down on the owner's STOP and wrote
`handoff.json`. Its `next_unit_reason` was 426 characters long. `scripts/orchestrator/handoff.schema.json` caps that
field at 400 (`"next_unit_reason": {"type": "string", "maxLength": 400}`). The supervisor's `Test-Json` refused the
file, `orchestrate.ps1` copied it to `E:\COBOL-coord\logs\20261028-191807-enqueue.handoff.invalid.json`, synthesized a
`split`/`resume` handoff in its place, and logged:

```
[2026-10-28 20:24:51] unit 'enqueue' ended: exit 0, handoff synthesized (invalid), 3998 s, 173 calls — FAILURE 1 of 3
```

Every other field was valid (summary 737 of 900). Two more such units in a row would have tripped the circuit breaker
and stopped the loop for a unit that did its job. The synthesized handoff also replaces the unit's own `next_unit`
choice and its reasoning with a generic resume.

## The mechanism

1. **The caps live only in the schema.** `scripts/orchestrator/units/common.md` tells every unit to write "JSON valid
   against scripts/orchestrator/handoff.schema.json, `summary` at most 900 characters". It states the one cap a unit is
   most likely to exceed, and says nothing about `next_unit_reason` (400), `owner_question.question` (1200) or
   `context` (2000). A unit can only learn those caps by opening the schema, which no unit prompt asks it to do.
2. **No unit checks its own handoff.** Validation runs once, in the supervisor, after the unit's process has exited
   (`orchestrate.ps1`, the `Test-Json -SchemaFile $Schema` after the unit ends). At that point the model that could fix
   a 26-character overrun is gone, so a recoverable mistake becomes a unit failure.

## Sweep

`E:\COBOL-coord\logs` held 41 `*.handoff.invalid.json` files on 2026-10-29:

| Count | Schema violation | Units |
|---|---|---|
| 1 | `next_unit_reason` over 400 | the 2026-10-28 enqueue unit above |
| 40 | `meter_reading: null` | failed `meter` units, the last on 2026-10-27 17:38 |

The 40 meter files are the same mechanism. `units/meter.md` step 3 says "Write the handoff with `meter_reading` and
`next_unit` null" and, on an unreadable page, "`outcome: failed`". Units read the sentence as "both null". The schema
types `next_unit` with `null` in its enum but `meter_reading` as an object only, so every failed meter unit's handoff is
invalid. The meter is a read-only unit (kb/Work PB2665), so these did not move the breaker; they still turned an
honest "could not read the page" handoff into a set-aside file.

## Fix shape

1. **One check, run by the unit.** Give the loop one handoff validator that prints each violation by JSON path and
   limit (for example `python scripts/orchestrator/handoff.py check <file>`, or the same `Test-Json` the supervisor
   runs), and have the supervisor call the same code, so the unit and the supervisor cannot disagree. `units/common.md`
   makes running it the unit's last step before it ends its turn: on a violation, fix the file and re-run.
2. **No cap restated in prose.** `common.md` names the checker instead of any number, so the next cap added to the
   schema needs no prompt edit. A drift test fails if a unit prompt states a `maxLength` that differs from the schema.
3. **The meter's failure shape.** `units/meter.md` step 3 says to OMIT `meter_reading` when no reading was taken. (The
   alternative, allowing `null` in the schema, makes the field's absence and its null mean the same thing twice.)
