# PB2088 — cell-backed stores are O(area width)

Filed 2026-10-05 by the train-1022 lander from the w1022a implementer report (PB2087, lead 2).

**Mechanism.** `StorageCell.Ref` (`src/Cobol.Net.Runtime/Control/StorageCell.cs`) is an immutable `string`. A store into
any member of a cell-backed area goes through `CobolString.WindowInto`, which builds a new string of the whole area's
width. Before PB2087 only EXTERNAL records, BASED/ALLOCATEd areas and ADDRESS-OF-taken records lived in a cell. Since
PB2087 (train 1022), every group or character item that a program passes BY REFERENCE on a CALL or to a user-defined
function, and every group/REDEFINED/addressed LINKAGE formal, lives in one, so large records passed to subprograms pay this
on every store.

**Measurement (w1022a, 2M iterations of one 10-character store plus a compare, median of 3, 62 ms startup subtracted).**
Record-struct storage (before): about 111 ns per iteration at every width. Cell storage (after): 20 characters about
172 ns (+61 ns), 2,000 about 400 ns (+289 ns), 32,000 about 6.86 us (+6.7 us). Bench:
`E:\COBOL-coord\scratch\w1022a\bench\`.

**Repro.** A 32,000-character WORKING-STORAGE record passed `CALL "S" USING REC`, then a loop of `MOVE "X" TO F1 OF REC`
in the caller: each MOVE costs microseconds where a struct field store costs nanoseconds.

**Fix direction (not designed yet).** A mutable image for cells, for example a `char[]` (or pooled buffer) behind
`StorageCell` with the `string` view materialized only where a whole-image read needs it. First measure the record sizes
real programs pass (the NIST and GPL corpora give a distribution), then decide whether the mutable image applies to every
cell or only above a width threshold. Code sites: `StorageCell.cs` (`Ref`), `CobolString.WindowInto`, every Tier-B window
writer that reaches `ref cell.Ref`.
