# PB1091 — OPEN — the SPECIAL-NAMES ordinal operands have no one decoder: `int.TryParse` treats an unsigned integer above Int32.MaxValue as 'not an integer', so `SwitchBindSymbol

### Adjudicator finding (special-names-paragraph-p1, harm silent)
- **Mechanism:** The literal-operand decoder asks int.TryParse for the ordinal, so an unsigned integer beyond Int32 falls through to the CLASS arm and is refused under the 'noninteger literal shall be alphanumeric/national' rule instead of the ordinal range rule it violates (ALPHABET SR14 b1/c1; the CLASS clause's SR17 b2/c2 shares the decoder and the misattribution)
- **Repro:** SPECIAL-NAMES. ALPHABET AL IS 99999999999999.   /  ALPHABET AL FOR NATIONAL IS 99999999999999.  /  CLASS CL IS 99999999999999.  (--std 2023)
- **Expected (spec):** §12.3.7.3 SR14 b)1 / c)1: the literal is a numeric literal that is an unsigned integer outside 1..65,536 - a range violation of b1/c1 (SR17 b2 for CLASS). The diagnostic should name that rule.
- **Observed:** COBOLNET1906 'ALPHABET AL: 99999999999999 - each noninteger literal shall be an alphanumeric literal (ISO §12.3.7.3 SR14 b2)' (c2 on the national arm; 'SR17 b3' for CLASS). The program is still refused, so no wrong program is produced; the harm is a diagnostic false about the source (an integer called noninteger), the PB789/PB791 shape. Fix: parse the digit string with a width-independent test (all digits after an optional sign) before the class arm, or use a BigInteger/long parse.
- **Code site:** src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs#LiteralPhraseOperand
- **Clause (adjudicator):** §12.3.7.3 SR14 b)1, c)1 (and SR17 b)2, c)2)

### Adjudicator finding (special-names-paragraph-p2, harm under-rejects)
- **Mechanism:** SPECIAL-NAMES ordinal operands are decoded with `int.TryParse`, so an unsigned integer above Int32.MaxValue is treated as 'not an integer'. SwitchBindSymbolic then `continue`s past the symbolic character with NO diagnostic (the SR16 e/f ordinal rules go unenforced, and the program compiles clean). LiteralPhraseOperand (CLASS and ALPHABET) falls through to the class rule and refuses the integer as a 'noninteger literal' (SR17 b3/c3, SR14 b2), which names the wrong rule.
- **Repro:** Pinned adj-d1 cobol.exe, --std 2023 (and 85 for the alphanumeric arm). (a) `SPECIAL-NAMES. SYMBOLIC CHARACTERS BIG IS 99999999999.` with `DISPLAY 'OK'` compiles clean and prints OK (probe SA1; SA15 uses 4294967297; SA16 is the FOR NATIONAL form; SA17 adds `ALPHABET STD IS STANDARD-1` and `IN STD`). Adding `MOVE BIG TO X` (SA2) draws a false COBOLNET1639 "'BIG' is not defined". (b) `CLASS C1 IS 99999999999.` (CA1) draws COBOLNET1671 '99999999999 — each noninteger literal shall be an alphanumeric literal (SR17 b3)'. CA2 draws the FOR NATIONAL form under c3, and CA3 the IN STD form. The sibling outside this part is `ALPHABET A1 IS 99999999999.` (AL7): COBOLNET1906 '... noninteger literal ... (SR14 b2)'.
- **Expected (spec):** §12.3.7.3 SR16 e)2 (cite.py --check OK 16) 2.): 'When the IN phrase is not specified, the ordinal position specified by integer-1 shall exist in the native alphanumeric character set'. With e)1, f)1 and f)2, this makes (a) a syntax-rule violation that requires a COBOLNET1670 diagnostic naming SR16 e2 (or e1/f1/f2), as ordinal 65537 already gets. For (b), SR17 b)2 / c)2 (cite.py --check OK 17) 2.): 'Literal-5, if numeric, shall be an unsigned integer and shall have a value within the range of one through the maximum number of characters in the native alphanumeric character set'. 99999999999 is a numeric unsigned integer, so the violated rule is b2/c2's range, not b3/c3 ('Each noninteger literal ...'). For the ALPHABET sibling it is SR14 b1/c1, not b2.
- **Observed:** DataBinder.Switches.cs SwitchBindSymbolic: `if (!int.TryParse(ords[i].GetText(), out int ordinal)) continue;`, which is a silent skip. The name never registers, and a reference to it then reports 'not defined'. LiteralPhraseOperand: `if (int.TryParse(text, out int ordinal)) { ...ordinal rules... }`. On overflow control reaches `OperandLiteralClass(lit) == r.LiteralClass` and reports the class rule r.Rule(r.ClassItem). The grammar's INTEGERLIT is unbounded, and IntegerOperandPass explicitly defers the SYMBOLIC CHARACTERS integer-1 range to SwitchBindSymbolic ('§12.3.7.3 SR16's own rule, reported by DataBinder.SwitchBindSymbolic'), so no other pass catches it. Fix shape: ONE ordinal decoder for the SPECIAL-NAMES paragraph that parses INTEGERLIT arbitrarily wide (BigInteger, or a saturating long compare) and returns 'out of range' rather than 'not a number'. SwitchBindSymbolic and LiteralPhraseOperand both call it, so no arm can keep its own Int32 parse (two-arm-dispatch shape).
- **Code site:** src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs#SwitchBindSymbolic (the int.TryParse ... continue in the per-name loop); src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs#LiteralPhraseOperand (the int.TryParse gate before the ordinal rules)
- **Clause (adjudicator):** §12.3.7.3 SR16 e)1, e)2, f)1, f)2; SR17 b)2, c)2 (sibling SR14 b)1/c)1)
