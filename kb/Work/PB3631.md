## Landing 2026-11-07 (wave 20261921 group A) — DISCHARGED AS A DEFECT, LANDED AS A WITNESS

**Re-probe on the build (Debug, 0/0).** The arm is real and the code is right. Instrumenting `RetakeKeptHandle` over the new sweep showed
21 cases where the retake's `Attach` failed with a non-empty `unpublished` list (and 25 where it failed with none: the adoption
itself refused). The suspected wrong answer does not occur: another run unit and the run unit's own other connector meet '51' on the
kept record in every case. Mutation check: with `PhysicalFileTable.Republish` commented out, the witness fails (B READ 1 answers '00' instead of '51') for both organizations, so the arm is pinned. No code change.

**Why the earlier witnesses missed it.** The OPEN's `Attach` moves the record locks to its own endpoint (`CarryKeptHoldings`) only after the
adoption's page reads; an INPUT OPEN makes no medium read after that unless `SettleDeadOwnersOfTheOpen` finds a dead run unit's
transaction (`KeyedStore.FindDeadOwner`), whose settle through a handle of its own the OPEN's exclusive handle refuses. The witness
`CommitRollbackRuntimeReplacedFileTests.A_reopen_refused_at_any_read_whose_retake_cannot_adopt_the_store_leaves_the_kept_record_locks_standing` builds that
dead owner and sweeps "refuse the k-th read and every later one" over every k.
