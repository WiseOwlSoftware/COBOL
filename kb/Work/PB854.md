# PB854 — LANDED — the end-of-page condition exists and its exception conditions do not

Source: the `PB526` implementer report, item (a).

## Repro — re-run on this tree, with its control

`scratchpad/reg4/probe/p17b_ec_io_eop.cob` (PROGRAM-ID `R4P17B`), `--std 2023 --run`: a `LINAGE IS 3 LINES WITH
FOOTING AT 2` file, `>>TURN EC-I-O-EOP CHECKING ON` as the first line, a `USE AFTER EXCEPTION CONDITION
EC-I-O-EOP` declarative, and three WRITEs with NO END-OF-PAGE phrase:

```
DONE ES=[                               ]        <- the declarative never ran; EXCEPTION-STATUS is spaces
```

Control `p17c_eop_phrase_control.cob` — the same file and the same WRITEs with an `AT END-OF-PAGE` phrase:

```
EOP-PHRASE-RAN
DONE
```

So the end-of-page CONDITION is detected and delivered to the phrase; only the EXCEPTION conditions are absent.

## The rule, quoted

```
$ python scripts/spec/cite.py --check 14.9.51.4 "If the end-of-page condition was caused by the action in General rule 26a, the EC-I-O-EOP-OVERFLOW exception condition is set to exist."
  OK  §14.9.51.4 27)  (General rules)
      a) If the end-of-page condition was caused by the action in General rule 26a, the EC-I-O-EOP-OVERFLOW exception condition is set to exist. If the end-of-page condition was caused by the action in General rule 26b, the EC-I-O-EOP exception condition is set to exist.
```

GR27 c) and d) — the exception-checking PERFORM and the USE declarative as the ALTERNATIVE to an END-OF-PAGE
phrase — are therefore unreachable in full.

## Observed, in the code

```
$ grep -rn "EC-I-O-EOP" src/ --include=*.cs
src/Cobol.Net.Runtime/Exceptions/ExceptionCatalog.cs:113:        L3("EC-I-O-EOP", EcFatality.Nonfatal);
src/Cobol.Net.Runtime/Exceptions/ExceptionCatalog.cs:114:        L3("EC-I-O-EOP-OVERFLOW", EcFatality.Nonfatal);
```

Two catalog rows and nothing else: no `IoMaskNames` entry, no raise site.

## Code site

`src/Cobol.Net.Runtime/IO/SequentialConnector.cs#PositionOnLogicalPage` sets `EndOfPage = true` on both arms
(GR26 a) and GR26 b)) and says nothing to the EC layer; `src/Cobol.Net.Runtime/Exceptions/ExceptionCatalog.cs`
(the `IoMaskNames` array). The two arms are already distinguished at that site, which is exactly what GR27 a)
needs to choose between the two names — so this is a small, well-shaped piece of work: two mask entries and one
`FileConnector.SetIoCondition` call with a SUCCESSFUL status on each arm.

## Sibling sweep the fixer owes

* Every other nonfatal I-O condition that rides a SUCCESSFUL status the same way (EC-I-O-IMP, the LINAGE
  family) — the channel is shared, so check which of them have mask bits and which do not.
* `FUNCTION EXCEPTION-STATUS` inside an AT END-OF-PAGE phrase reads a stale name today; a golden should pin the
  name inside the phrase as well as the declarative.
* The RELATIVE/INDEXED connectors do not present pages and must NOT gain the raise — say so in the change set.

## Landed — 2026-09-22 (wave 45, group D)

**Re-probed on the wave-45 worktree's own build** (`w45d/p/p854.cob`, the p17b shape plus an EC-I-O-EOP-OVERFLOW
declarative and a phrase leg): BEFORE `W1 … W4`, `PHRASE ` + spaces, `DONE ES=[spaces]` — no declarative, and
EXCEPTION-STATUS empty inside the phrase. AFTER: `DECL-EOP EC-I-O-EOP` after W1, W2 and W4, `DECL-OVF
EC-I-O-EOP-OVERFLOW` after W3 (the overflow), `PHRASE EC-I-O-EOP` with no declarative for W5.

**Fix.** `SequentialConnector` records WHICH end-of-page condition at the one place GR26's two arms are decided
(`PositionOnLogicalPage`: overflow → `ExceptionCatalog.IoEopOverflow`, footing → `IoEop`; `EndOfPage` is now
derived from it) and `WriteSucceeded()` returns '00' with that name through `SetIoCondition` — the rule-named
condition channel PB526 built for EC-I-O-LINAGE, now carrying a successful status too. Both WRITE arms that can
travel a page return through it, and each resets the name at entry. `ExceptionCatalog.IoMaskNames` gains the two
names (append-only); `IsEndOfPage` names them for the hook. GR27 b)–d)'s precedence: the WRITE hook now passes the
END-OF-PAGE phrase as its condition-phrase flag, and `__IoCheckEc`'s SUCCESS arm returns before the F3/USE dispatch
for an EOP name when the phrase is present — after the condition is SET, so EXCEPTION-STATUS reads it inside the
phrase (the note's second sibling).

**Sibling sweep.** Every catalogued EC-I-O level-3 name now has a mask bit, and
`TurnStateTests.EveryCataloguedEcIoName_HasAMaskBit` fails for any future catalogue row without one. The other
success-status condition, EC-I-O-WARNING, rides §9.1.13.1's '0x' correspondence and already had its bit. RELATIVE
and INDEXED connectors present no page and gained no raise. GR27 c) (the exception-checking PERFORM's WHEN) was
measured, not assumed: the WHEN takes it and the matching USE is ignored.

**Goldens:** `2002/pb854_write_eop_exception_conditions` (PB854EOP — a), b), d), both names), `2023/pb854_eop_perform_when`
(PB854WHN — c), a 2023 construct), `negative/pb854-eop-use-name-below-2002` (reject-at 85, COBOLNET0878).
