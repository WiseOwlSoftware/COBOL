# PB2918 — the SDIDI lift of a >34-digit container value

Filed 2026-10-10 by the train 1052 lander (phase 1b) from the wave 1052 E implementer's report
(`E:\COBOL-coord\scratch\reports\w1052e-PB2698-report.md`, lead A).

**Repro:** `E:\COBOL-coord\scratch\w1052e\sd1.cob` (`OPTIONS. ARITHMETIC IS STANDARD-DECIMAL.`; `S PIC S9(19) COMP-5`
whose storage is set to `X"80000000000000000000000000000000"` through a redefining `PIC X(16)`, i.e. -2^127, a
value the binary container holds although its PICTURE allows 19 digits). `COMPUTE R = S + 1`, whose result is a valid
value of R's container, reports a size error.

**Where.** The standard-decimal operand path renders a binary item through `NumericRenderer.DecOperand`
(`src/WiseOwl.Cobol.Compiler/CodeGen/Emit/NumericRenderer.cs`, about line 753) into `CobolDec.From(unscaled, scale)`
(`src/WiseOwl.Cobol.Runtime/Values/Numeric/CobolDec.cs`, line 23), which accepts any Int128. A 39-digit significand breaks
the invariant CobolDec's `Int128.Abs` / significand sites assume (at most 34 digits, the decimal128 coefficient), and
the next operation reads it as an overflow. PB2698 (train 1052) fixed the native-lane ABS of `Int128.MinValue`; this is
the SDIDI lane's sibling, left because it is a different mechanism (the lift, not the function).

**Rule.** §14.7.5 (SIZE ERROR phrase and size error condition): a size error is the RESULT's, after the arithmetic;
an operand the container holds is not one. What the standard-decimal intermediate does with an operand wider than its
34 digits is an implementor determination (the SDIDI intermediate's precision), to be written into CONFORMANCE.md
beside DOC-A.1-179.

**Fix shape.** One place: the lift of a binary operand into the decimal128 intermediate decides an over-wide value once
(round to 34 digits per the intermediate's rule, or raise EC-SIZE at the lift by a recorded determination), instead of
constructing a CobolDec that violates its own invariant. Add a guard in `CobolDec.From` (or a checked twin) so the
invariant is enforced where it is assumed, and a golden at 2023 with the repro's cases.

## Landing

**Landed 2026-10-10 (wave 1056 C).** Re-probed on a fresh build before any edit (`w1056c/sd1.cob` under the
coordination scratch directory): `COMPUTE R = S + 1` took ON SIZE ERROR exactly as filed. The rule is not an
implementor determination: ISO §8.8.1.5.2 r1 (cite.py --check OK) says an operand that "cannot be expressed exactly in an
SDIDI" is ROUNDED under §11.9.11 (PROHIBITED gives EC-SIZE-TRUNCATION, §11.9.11.2 r3d, cite.py --check OK), and the SDIDI's
own range (§8.8.1.5.2 r2) is decimal128's, so a 39-digit container value is neither a size error at the lift nor an exact
lift. Two roots, one change set:

1. **The lift (`NumericRenderer.DecOperand`).** The exact `CobolDec.From` put the 39-digit significand into the
   intermediate unrounded. `DecOperand` now lifts an operand whose `NumX.Digits` bound is 1..34 exactly and every other
   fixed-point operand (a 16-byte container: bound 39; an unknown bound: 0) through `CobolDec.FromParsed(v, -scale, mode)`,
   the existing rounding funnel, which is `Int128.MinValue`-safe. It holds in EVERY mode: a NATIVE statement with a Dec
   operand (float literal, integer power) evaluates on the same lane (DOC-A.1-82), and `S + 0.5E0` hit the same defect
   there (and `S + S * 0.5E0`, whose result no container holds, stored a wrapped value with NOT ON SIZE ERROR, a
   wrong-answer sibling the note did not name). The round-to-odd consumers (`DecMulToOdd`, `DecDivToOdd`) keep the exact
   lift through the new `DecOperandExact`, on purpose (a pre-rounded operand would be rounded twice). The unsigned-wide
   arm: `CobolDec.FromUnsigned` (new, in `PublicAPI.Unshipped.txt`) lifts a `UInt128` operand of a relation or a function
   argument by the same rule; before, `IF U > A + B` with U = 2^128-1 failed loudly in `CobolNum.Widen`.
2. **The landing (`CobolDec.ToUnscaledCore`).** After the lift the sum -170141183460469231731687303715884100000 still
   took the size error: the checked landing counted digits (`> 38`), refusing every 39-digit value Int128 holds (and
   `Int128.Abs(MinValue)` threw). It now asks `CobolNum.WideningFits`, the one carrier-fit predicate every widening shares
   (MinValue-safe by construction), where the rule had been written a second time as a digit count.

Witnesses: goldens `2023/pb2918_sdidi_lift_of_wide_binary_container`, `2023/pb2918_sdidi_lift_prohibited`,
`2023/pb2918_native_dec_lane_wide_binary_operand`; `CobolDecWideLiftTests` (per mode, MinValue, unsigned maximum, the
landing); the drift test `SdidiOperandLiftDriftTests` (no emit site spells the exact lift outside `DecOperandExact`, which
has only the two round-to-odd consumers). Docs: `NUMERIC_DESIGN.md` D27; `CONFORMANCE.md` DOC-A.1-179 (3).

**Found and left (determinations or other mechanisms, reported as leads, not fixed here):** (a) under STANDARD-DECIMAL the
non-aligning exact-family functions (ABS, SIGN, INTEGER, INTEGER-PART, FRACTION-PART) keep their Int128 arm for an
all-fixed-point argument by D3's "exact residue" determination, so `FUNCTION ABS(S)` of -2^127 is still the PB2698 size
error where §15.4.1 r1 and §8.8.1.5.2 r1 would give the rounded SDIDI; (b) `CombineCore` funnels an unsigned-wide ARITHMETIC
operand through `DeU` (loud above 2^127-1) under STANDARD-DECIMAL as well, and the SDIDI to `Int128` landing cannot express
an unsigned 16-byte receiver value in [2^127, 2^128); (c) a binary64 list-body result (`FUNCTION VARIANCE(A, 1)` over a
30-digit A, about 2.5E+59) stored into a `PIC S9(19) COMP-5` receiver saturates to 2^127-1 with NOT ON SIZE ERROR
(`w1056c/var1.cob`; independent of this change: A has 30 digits).
