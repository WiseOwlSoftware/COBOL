# PB5190 - at --std 85 a condition-name VALUE nonnumeric literal longer than its conditional variable compiles, and SET to TRUE stores a truncated value whose condition is then false: ValueSubject.ForConditionName carries no size

**Sites:**

- `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs` (`BindCondition`, `ValidateValueCategory`)
- `src/WiseOwl.Cobol.Compiler/Binding/ValueSubject.cs` (`ForConditionName`)

**Mechanism.** §1985:VI.5.15.3 SR3 requires every nonnumeric literal of a VALUE clause not to exceed the size the PICTURE indicates, and the 1985 sentence reaches the condition-name entry (its numeric half already does: 88 NC VALUE 123 under PIC 99 is COBOL1625 at 85). `DataBinder.BindCondition` passes `ValueSubject.ForConditionName`, which carries no size, a choice derived from the 2023 words (kb/Work PB598), so `88 XC VALUE "ABC"` under PIC X compiles at --std 85; SET XC TO TRUE stores one character and XC is then false.

**Found by.** The 1985 code read (2026-11-10; its records are `E:/COBOL-coord/scratch/coderead-85/for-register.json`): each rule below was read against the code sites it names and probed at `--std 85`, and found non-conforming. Verdict, harm, evidence, repro and observed text are the records'; the rows' verdicts are recorded on another branch.

**Inventory.** `work.py check` refuses a 1985 rule id in `inventory_rows` (kb/Work PB5094, open), so `inventory_rows` is empty and the rows this note claims are the rule ids of the list below.

**Rules (1; every citation checked with `scripts/spec/cite.py --check`).**

- `1985-SR-VI.5.15.3-3` - `§1985:VI.5.15.3 SR3` (record verdict: PARTIAL, harm: under-rejects). Checked: §1985:VI.5.15.3 SR3: "All numeric literals in a VALUE clause of an item must have a value which is within the range of values indicated by the PICTURE clause, and must not have a value which would require truncation of nonzero digits. Nonnumeric literals in a VALUE clause of an item must not exceed the size indicated by the PICTURE clause.". Code sites read: src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs#ScreenValueLiteral; src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs#ValidateNumericValue; src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs#ValidateValueCategory; src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs#BindCondition; src/WiseOwl.Cobol.Compiler/Binding/ValueSubject.cs#ForElementary; src/WiseOwl.Cobol.Compiler/Binding/ValueSubject.cs#ForConditionName. Code read: No kb/Work note owns the fix. §1985:VI.5.15.3 SR3: "All numeric literals in a VALUE clause of an item must have a value which is within the range of values indicated by the PICTURE clause, and must not have a value which would require truncation of nonzero digits. Nonnumeric literals in a VALUE clause of an item must not exceed the size indicated by the PICTURE clause." Implemented at 85 for a data item: every VALUE literal passes ScreenValueLiteral; ValidateNumericValue refuses a numeric literal with a nonzero digit outside the PICTURE's digit positions on either side (COBOL1625), and ValidateValueCategory refuses a nonnumeric literal longer than the size ValueSubject.ForElementary takes from the PICTURE, for alphabetic, alphanumeric and alphanumeric edited items (COBOL1740) and for numeric edited items (COBOL1570); neither arm has an edition test. Implemented for the numeric literals of a condition-name too (BindCondition sends each literal and both ends of a THRU range through the same funnel). Not implemented at 85: the nonnumeric literal of a condition-name. BindCondition passes ValueSubject.ForConditionName, which carries no size, so the size sentence never reaches it. That choice was derived from the 2023 words "of an elementary item" and "an explicit PICTURE clause" (§2023:13.18.63.3 SR4); the 1985 sentence has neither word. The 1985 rule reaches the condition-name entry: its first sentence speaks of "All numeric literals in a VALUE clause", and only the condition-name format takes more than one literal; §1985:VI.5.15.4 GR1 a says the same way "all literals in the VALUE clause must be numeric"; and §1985:VI.5.15.5 GR1 gives the entry its PICTURE: "The characteristics of a condition-name are implicitly those of its conditional variable." The compiler already reads the first sentence that way at 85 (88 NC VALUE 123 on PIC 99 is COBOL1625), and both sentences use the same words, "in a VALUE clause of an item". Probed at --std 85: refused are 123 in PIC 9(2), 1.25 in 9V9, 12.5 in 9(2), 1230 in 99PP, .012 in PP99, 12345 in 9(4) COMP, 10000 in 9(4) BINARY, -1000 in S9(3) PACKED-DECIMAL, -100 in S99, "ABC" in X(2), A(2) and X(2) JUSTIFIED, "ABCD" in XBX, "1234" in ZZ9, "12/345" in 99/99, oversize literals on table elements, and 88 values 123, 1 THRU 100 and 1.5 on PIC 99; accepted are 012, 1.20, 1200, .0012, 0012.00, -99, a shorter nonnumeric literal and ALL "ABC" in X(2); accepted and not legal are 88 VALUE "cd" on PIC X, 88 VALUE "a" THRU "zz" on PIC X and 88 VALUE "1234" on PIC ZZ9. The witness is PIC ZZ9 VALUE "1234", refused with COBOL1570.

**Repro (`1985-SR-VI.5.15.3-3`).** `cobol.exe <file> --std 85 --source-format fixed --run`

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. VAL88.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  XV PIC X VALUE "c".
           88  XC VALUE "cd".
       PROCEDURE DIVISION.
       P1.
           SET XC TO TRUE.
           IF XC DISPLAY "XC TRUE" ELSE DISPLAY "XC FALSE".
           STOP RUN.
```

**Expected (from the 1985 text, the record's).** A diagnostic at line 6 and no object program: §1985:VI.5.15.3 SR3 "Nonnumeric literals in a VALUE clause of an item must not exceed the size indicated by the PICTURE clause." The literal "cd" has two characters; the PICTURE that indicates the size is the conditional variable's, PIC X, by §1985:VI.5.15.5 GR1: "The characteristics of a condition-name are implicitly those of its conditional variable."

**Observed (the record's).** exit 0, no diagnostic (none with --flag-extensions either); the program runs and displays XC FALSE: SET XC TO TRUE stores one character and the condition it set is false. In the same position a numeric literal that does not fit is refused at 85 (01 NV PIC 99 with 88 NC VALUE 123 draws COBOL1625), so the two sentences of the rule are applied to different subjects.

**Fix direction (root cause, CLAUDE.md rule 4).** Give ForConditionName the conditional variable's size at the editions whose rule bounds it, so ValidateValueCategory applies the one size check to both entry kinds.
