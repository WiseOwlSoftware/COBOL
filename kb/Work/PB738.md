# PB738 — BLOCKED ON THE OWNER — the standard itself is the defective source

`blocked: true`, `blocked_by: []` — the blocker is the owner, not a note. **Mark for the ledger's owner card.**

Found 2026-09-06 while registering the PB721 registrar's finding. That registrar confirmed the sites in the PDF
content stream at 600 dpi; **this note re-derives the population independently and exhaustively**, because a
count is the part of a finding most likely to be inherited.

## The five sites, and the proof they are the PRINTED text

The transcription (`specs/ISO_COBOL.md`, HEAD `0db46983`):

**Verification 1 — visual, off the canonical PDF.** `python scripts/spec/clause_page.py 14.9.10.4` → PDF page
636 / folio 606; `python scripts/render-spec-page.py 637` renders folio **607**, where GR15 b) is printed, in the
document's own typeface, as:

> b) The valu62’ is placed into the I-O status associated with file-name-1 to indicate the file operation
> conflict condition.

The same rendered page shows GR13 with straight quotes (`'41'`) and GR14 with curly ones (`‘05’`), and folio 606
GR7 a) prints `filename-1` where every neighbour prints `file-name-1` — so the DELETE FILE rules carry more than
one typesetting defect, and the transcription inherits them all correctly.

**Verification 2 — mechanical and exhaustive, off the PDF's content stream.** A scan of all 1261 pages for
`[A-Za-z]\d\d['’]` (the shape a dropped `<letter><space><opening-quote>` leaves behind) returns **8 matches**:
the five above (PDF pages 637, 638, 638, 710, 726) and three benign ones — `binary64'` on 538 (the ISO/IEC 60559
format name), `'external-ref01'` and `'external-ref02'` on 1154 (literals inside an example program). **The
population is exactly five.** Script: `…\scratchpad\pdfscan.py`.

The dropped run is identical at every site: a letter, a space, and an OPENING single quotation mark — `e ‘`,
`o ‘`, `r ‘`. The closing quote always survives. That is a typesetting/kerning fault in the published document,
not an OCR fault and not a transcription fault.

## The recovered readings are corroborated by the standard itself

- **'62'** — `cite.py --check 9.1.13.9 "62"` → **OK §9.1.13.9 2)**: *"I-O status = 62. A file sharing conflict
  condition exists because a DELETE FILE statement is attempted on a physical file and that physical file is
  currently open by another file connector."* GR15 b) is the file-sharing-conflict arm of DELETE FILE. Exact fit.
- **'06'** — `--check 9.1.13.2 "I-O status = 06"` → **OK §9.1.13.2 5)**: *"A READ statement for a line sequential
  file has successfully executed but a line delimiter or the end-of-file has not been detected."* §14.9.30.4 GR15
  is the line-sequential READ rule and its surviving tail reads *"indicating that the line delimiter or
  end-of-file was not…"*. Exact fit.
- **'05' / '37'** — `--check E.3.3 "Setting of I-O status '05', '37', '39', '41', and '62'"` → **OK §E.3.3 35)**:
  *"The DELETE FILE statement has been added, as a result these file statuses may be set by this new
  statement."* Three of the five recovered values named together, in the annex describing the very statement
  three of the five sites belong to. ⚠ The dispatch pointed at "E.3.3 item 35" and it holds — but
  `cite.py --check E.3.3 "35"` matches an unrelated line (`10B00-10B35`) and would have passed for the wrong
  reason. Cite the SENTENCE, never the ordinal.

## The operational cost, measured

```
$ python scripts/spec/cite.py --check 14.9.10.4 "The value '62' is placed into the I-O status"
FAIL: §14.9.10.4 exists but does NOT contain "The value '62' is placed into the I-O status"
$ python scripts/spec/cite.py --check 14.9.10.4 "The valu62' is placed into the I-O status"
OK  §14.9.10.4 15)  (General rules)
```

So the mechanism CLAUDE.md rule 1 makes non-negotiable — every citation validated with `--check` — currently
forces any code comment, golden or design paragraph citing these five rules to quote the GARBLE verbatim. That is
a live trap: the next reader "fixes" the quote, `--check` goes red, and the plausible repair is to cite a
different clause. Whatever the owner decides, that trap is what the decision is about.

## ⛔ The question

**Should the transcription stay byte-faithful to the printed defect at these five sites, or carry the recovered
reading as a marked editorial note?**

## Recommendation (per `feedback_owner_decision_protocol` — follow the surveyed model)

**Keep the normative text byte-faithful, and carry the recovered reading beside it as a marked, clearly
non-normative annotation.** How the surveyed transcriptions handle printed errata, briefly: standards bodies do
not silently repair published text — ISO issues Technical Corrigenda against the published edition; the Open
Group's Base Specifications ship the published text with separate Technical Corrigenda; W3C keeps per-Rec errata
pages; the C/C++ working drafts carry editorial-issue lists. In every case the published wording stands and the
correction is recorded out of band, attributed and dated. Silently inlining a repair would make this repository
the only source in that set whose "quotation" of ISO/IEC 1989:2023 is not what ISO/IEC 1989:2023 says.

The house convention for exactly this already exists and is heavily used: **235 `> **Figure notes (…)**`
blockquotes** already sit beside general formats in `specs/ISO_COBOL.md`, adding transcription-side observations
(underlining, delimiter scope) without touching the figure. A `> **Transcription note**` blockquote after each of
the five rules, giving the recovered reading and this note's id, is the same mechanism.

⚠ **Two things must be measured before that option is adopted, and neither is measured here.** (a) whether
`scripts/spec/extract_rule_catalog.py` tolerates a blockquote adjacent to a numbered general rule — it has no
blockquote handling at all, so its behaviour there is unknown and could move rule text into or out of the
catalog, which is the traceability inventory's own input; (b) whether any landed citation already quotes one of
the five garbled strings (a `grep` of `src/`, `docs/`, `tests/` and `kb/` for `valu62`, `set t37`, `o05'`,
`set t05`, `set t06` before the change, so `audit_code_citations.py --check` cannot go red after it).

Separately and regardless of the answer: these are defects in a published International Standard, and the
project's own interest is served by reporting them to the maintenance body (WG4 / INCITS J4) so a future
corrigendum fixes them at the source rather than five annotations tracking them forever.

## Not a dispatch for an implementer

Nothing here is implementable until the owner answers. If the answer is "stay faithful", this note closes as a
`landed` decision and its value is the recorded population of five plus the recovered readings, so the next
reader of §14.9.10.4 GR15 does not spend an hour on it. If the answer is "annotate", the two measurements above
are step 1 and the five annotations are step 2, in one change set.
