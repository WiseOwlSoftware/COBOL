# PB499

## Mechanism — value-clause-p3
The whole INITIALIZE / ALLOCATE lane is blind to the Format 2 (table) VALUE carrier. `InitializeBinder.InitializeSender` (InitializeBinder.cs:213) takes a `string? rawValue` and its only caller passes `item.RawValue` — the format-1 carrier. `DataItem.TableValues`, the format-2 carrier, is a DIFFERENT and mutually exclusive property, and nothing on this lane reads it; `ExpandInitialize` (:194-199) then hands every occurrence of an OCCURS child the SAME sender, so even the shape of a per-occurrence sender is absent. Consequence: a format-2 VALUE takes effect ONLY through the record-struct field initializer (ValueInitializer.FieldInit), i.e. only at initial state — which is precisely the moment §13.18.63.4 GR2/GR3/GR4a/GR4b say the VALUE must NOT take effect for a file-section, linkage-section, external or based item. For those four populations the table VALUE therefore never takes effect at all, and in working-storage it cannot be restored by INITIALIZE.

### Expected, from the standard
§13.18.63.4 GR11 — "General rules 1, 2, 3, 4, 5, 6, 7, 8, and 10 above apply" — imports GR3 ("In the linkage section, VALUE clauses take effect only during the execution of an explicit or implicit INITIALIZE statement") and GR4 ("a) for external items, during the execution of an INITIALIZE statement; b) for based items and their subordinate items, during the execution of an ALLOCATE or an explicit or implicit INITIALIZE statement") into format 2. §14.9.20.4 GR5c1c names the qualifying condition exactly — "A table format VALUE clause is specified in the data description entry of the elementary item and that VALUE clause specifies a value for the particular occurrence of the elementary data item" — and GR6a3 supplies the sender: "If the data item is a table element, the literal in the VALUE clause that corresponds to the occurrence being initialized determines the sending-operand." So (a) must print SUB-AFTER=[AABB..] (occurrence 3 undefined), (b) AFTER =[AABB  ], (c) ALLOC=[AABB  ], (d) TOVAL=[AABB..].

## Mechanism — value-clause-p4
INITIALIZE ... ALL TO VALUE never nulls a class-pointer or class-object item, because the VALUE-phrase qualification test demands a VALUE clause the item is forbidden to have. InitializeBinder.InitializeSender qualifies a receiver under the VALUE phrase with `spec.ToValue && (categories match) && rawValue is { } raw`; 14.9.20.4 GR5c1 has TWO arms -- (a) 'Either the category of the elementary data item is data-pointer, message-tag, object-reference, or program-pointer, or' (b) 'A data-item format VALUE clause is specified' -- and only arm (b) is written. Since 13.18.63.3 SR9 forbids a VALUE clause on those usages, rawValue is ALWAYS null for exactly the categories arm (a) exists to serve, so arm (a) can never fire. The pointer branch at InitializeBinder.cs:158-162 then uses InitializeSender's non-null result as its own qualification signal, sees null, and emits no InitializeSetNull action at all. 13.18.63.4 GR4's closing paragraph states the requirement positively for every occasion on which VALUE clauses take effect, and 14.9.20.4 GR6a1 fixes the sending operand as the predefined address NULL. The bare `INITIALIZE P.` and `INITIALIZE P ALL TO VALUE THEN TO DEFAULT.` forms both reach the ToDefault fallback and DO null the pointer, which isolates the defect to the single missing arm.

### Expected, from the standard
13.18.63.4 GR4 closing paragraph -- 'When VALUE clauses take effect, data items with a VALUE clause are initialized to the specified value and data items of class message-tag, class object, and class pointer are initialized to null' -- with GR4c listing 'during the execution of an INITIALIZE statement' as one of those occasions, and 14.9.20.4 GR5c1a + GR6a1 ('the sending-operand is the predefined address NULL'). ### The design question, stated precisely — the lane's occurrence context is a RUNTIME loop variable

"The INITIALIZE lane has no occurrence context to key it with" is true, and the reason is structural and
worth writing down, because it decides the fix shape:

```csharp
// InitializeBinder.ExpandInitialize, :256-266 — the fixed-OCCURS arm
if (child.IsTable)
{
    string v = $"__ini{_initializeLoopVar++}";
    var body = new List<InitializeAction>();
    ExpandInitialize(childCur.Indexed(v), spec, body, identifier1Item);
    if (body.Count > 0 && TableCount(child, identifier1Item, childCur.StoragePath) is { } count)
        actions.Add(new InitializeLoop(v, count, body));
    …
```

A table expands to **ONE `InitializeLoop` over ONE shared `body`** keyed on a GENERATED runtime variable.
Every occurrence therefore receives the identical `InitializeAction` list — which is precisely why the
format-1 carrier works here and the format-2 carrier cannot: a format-2 VALUE is per-occurrence by
construction. The dynamic-capacity arm (`:238-254`) has the same shape over `AllCount.Capacity`.

So every occurrence→literal association is known at bind time, and **train 26 already computed it, once, on the

lane would be that plan's next reader, and it needs to re-derive nothing.

### Two shapes, and why one of them is wrong

* **Unroll the loop when a format-2 VALUE is present** — emit one `InitializeStore` per occurrence with its
  own literal. Correct for a fixed OCCURS, but it does not compose: `TableCount` may be a RUNTIME count
  (§14.9.20.4 GR8a current / GR8b maximum, and GR10's dynamic capacity), and there is no unrolling of a
  count you do not have. It also emits O(occurrences) actions for an `OCCURS 100000`.
* **Keep the loop and make the SENDER a function of the loop variable** — an indexed lookup (a materialized
  constant array, or a switch over the map's keys with the map's *absent* occurrences falling to the element
  default, which `ResolveTableValueMap`'s comment is explicit is NOT a spec-guaranteed space/zero). This
  composes with GR8 and GR10 unchanged, and it is the shape the rest of the lane is already written in.

The second is the one to build; unrolling is at most a later size optimization for a small fixed table.

### The structural obstacle is GONE — and that changes the size of this item

When this section was first written (against `094739b3`) the map lived in `CodeGen/DataDivision/` while
`InitializeBinder` lives in `Binding/Procedure/`, and the recommendation here was to lift it to the model side
so the binder would not have to reach downward into CodeGen. **Train 26 did exactly that**: the plan is now
`Binding/Model/TableValuePlan.cs`, resolved in `DataBinder`, read through `DataItem.ValueAt`. The layering
objection no longer exists.

What remains is therefore ONE thing, not two: **give `InitializeSender` the DataItem and the occurrence instead
of a pre-extracted `string? rawValue`, and let it call `ValueAt`.** The note's own FIX SHAPE paragraph asked for
that, and its companion — *"a drift test should assert that every DataItem VALUE carrier reachable by the
emitter is also reachable by INITIALIZE"* — is now cheap to write, because there is one carrier accessor
(`ValueAt`) to assert against rather than a pair of mutually exclusive properties.
