# PB499

## Mechanism — value-clause-p3
The whole INITIALIZE / ALLOCATE lane is blind to the Format 2 (table) VALUE carrier. `InitializeBinder.InitializeSender` (InitializeBinder.cs:213) takes a `string? rawValue` and its only caller passes `item.RawValue` — the format-1 carrier. `DataItem.TableValues`, the format-2 carrier, is a DIFFERENT and mutually exclusive property, and nothing on this lane reads it; `ExpandInitialize` (:194-199) then hands every occurrence of an OCCURS child the SAME sender, so even the shape of a per-occurrence sender is absent. Consequence: a format-2 VALUE takes effect ONLY through the record-struct field initializer (ValueInitializer.FieldInit), i.e. only at initial state — which is precisely the moment §13.18.63.4 GR2/GR3/GR4a/GR4b say the VALUE must NOT take effect for a file-section, linkage-section, external or based item. For those four populations the table VALUE therefore never takes effect at all, and in working-storage it cannot be restored by INITIALIZE.

### Expected, from the standard
§13.18.63.4 GR11 — "General rules 1, 2, 3, 4, 5, 6, 7, 8, and 10 above apply" — imports GR3 ("In the linkage section, VALUE clauses take effect only during the execution of an explicit or implicit INITIALIZE statement") and GR4 ("a) for external items, during the execution of an INITIALIZE statement; b) for based items and their subordinate items, during the execution of an ALLOCATE or an explicit or implicit INITIALIZE statement") into format 2. §14.9.20.4 GR5c1c names the qualifying condition exactly — "A table format VALUE clause is specified in the data description entry of the elementary item and that VALUE clause specifies a value for the particular occurrence of the elementary data item" — and GR6a3 supplies the sender: "If the data item is a table element, the literal in the VALUE clause that corresponds to the occurrence being initialized determines the sending-operand." So (a) must print SUB-AFTER=[AABB..] (occurrence 3 undefined), (b) AFTER =[AABB  ], (c) ALLOC=[AABB  ], (d) TOVAL=[AABB..].

### Observed
Measured on the pinned compiler, not deduced. The four failing programs and the three format-1 controls were run in the same session against the same binary; the controls prove the INITIALIZE-TO-VALUE and ALLOCATE-INITIALIZED paths themselves work in those sections and that only the format-2 carrier is invisible. Verdict on GR-13.18.63.4-11 is DIVERGES. FIX SHAPE (the structural one, not the smallest diff): `InitializeSender` should take the DataItem and the occurrence index rather than a pre-extracted `string? rawValue`, and resolve the literal through the SAME `ValueInitializer.ResolveTableValueMap` the record-struct lane uses — the map is already `static` and takes (item, fillMax), so one call site change makes GR12-GR15 automatic on this lane instead of re-deriving them. A drift test should assert that every DataItem VALUE carrier reachable by the emitter is also reachable by INITIALIZE, so a third carrier cannot repeat this.

## Mechanism — value-clause-p4
INITIALIZE ... ALL TO VALUE never nulls a class-pointer or class-object item, because the VALUE-phrase qualification test demands a VALUE clause the item is forbidden to have. InitializeBinder.InitializeSender qualifies a receiver under the VALUE phrase with `spec.ToValue && (categories match) && rawValue is { } raw`; 14.9.20.4 GR5c1 has TWO arms -- (a) 'Either the category of the elementary data item is data-pointer, message-tag, object-reference, or program-pointer, or' (b) 'A data-item format VALUE clause is specified' -- and only arm (b) is written. Since 13.18.63.3 SR9 forbids a VALUE clause on those usages, rawValue is ALWAYS null for exactly the categories arm (a) exists to serve, so arm (a) can never fire. The pointer branch at InitializeBinder.cs:158-162 then uses InitializeSender's non-null result as its own qualification signal, sees null, and emits no InitializeSetNull action at all. 13.18.63.4 GR4's closing paragraph states the requirement positively for every occasion on which VALUE clauses take effect, and 14.9.20.4 GR6a1 fixes the sending operand as the predefined address NULL. The bare `INITIALIZE P.` and `INITIALIZE P ALL TO VALUE THEN TO DEFAULT.` forms both reach the ToDefault fallback and DO null the pointer, which isolates the defect to the single missing arm.

### Expected, from the standard
13.18.63.4 GR4 closing paragraph -- 'When VALUE clauses take effect, data items with a VALUE clause are initialized to the specified value and data items of class message-tag, class object, and class pointer are initialized to null' -- with GR4c listing 'during the execution of an INITIALIZE statement' as one of those occasions, and 14.9.20.4 GR5c1a + GR6a1 ('the sending-operand is the predefined address NULL'). P2-NULL.

### Observed

At initial state pointers and object references ARE null (probe gr4null), so the initial-state half of the same GR4 sentence is right and only the INITIALIZE half is wrong.
