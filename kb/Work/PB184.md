# PB184

Found 2026-08-30 by the PB164 Step D review wave's hand-rolled-DISPLAY-union sweep (F8), **deliberately not
changed under that sweep** — it is a §13.18.63.4 GR5 derivation with real blast radius, not predicate drift, and
the wave recorded it rather than fixing it inside a mechanical widening.

**MEASURED**, on the Step D tree:

```cobol
01 GV VALUE "40537".
   05 GB PIC 9 COMP-5 OCCURS 5.
```

every `GB(1..5)` initializes to **zero**. The group VALUE is dropped on the floor; nothing diagnoses it.

**MECHANISM.** `GroupValueSlicer.DistributableSubtree`
(`src/Cobol.Net.Compiler/CodeGen/DataDivision/GroupValueSlicer.cs:38-52`) is one of the hand-rolled
`{ Category: Numeric, IsFloat: false, Usage: Usage.Display }` unions the F8 sweep catalogued. A leaf passes the
screen only when it is string-stored **or** a NATIVE zoned-DISPLAY numeric; a BINARY / COMP-5 / PACKED /
float / INDEX leaf fails it, `DistributableSubtree` returns false for the whole group, and the member-wise
default (`new Struct { child = <child's own Init> }`) is emitted instead — each leaf taking its own VALUE or,
absent one, zero. `SliceInit` has the mirror-image screen.

**WHAT THE SPEC ASKS FOR.** §13.18.63.4 GR5 (`cite.py --check` OK): "If a VALUE clause is specified in a data
description entry of a group item, the group area is initialized without consideration for the individual
elementary or group items contained within this group." The literal's characters are deposited positionally
across the group's STORAGE, and each subordinate then simply IS whatever its own description makes of the bytes
lying under it. Since PB164 every numeric usage HAS a pinned byte form, so "the bytes lying under it" is now a
defined quantity for every leaf kind this screen rejects — which is exactly why the exclusion stopped being
defensible when the Tier-C arm fell.

⚠ **The in-code reason was stale twice over** and is corrected in the same commit as this note: it blamed "the
Tier-C byte boundary" (false since V59/PB164) and cited a paraphrase — "ISO §13.18.63" with the wording of the
MOVE rule §14.9.25.4 GR4, not the VALUE rule. The string "without consideration for the individual elementary
items" (no "or group") appears NOWHERE in the standard; both real occurrences read "elementary or group items".
That paraphrase is inherited across ~10 more sites in `src/`, `docs/` and `kb/` — the CLAUDE.md rule 1
inherited-citation shape, adjacent to [[PB182]]; sweeping them is that note's kind of work.

**WHY IT IS NOT A ONE-LINE WIDENING (and what to derive before touching it).**
1. The slicer works in CHARACTERS against `ImageWidth`; a byte-form leaf's window is `StorageWidth` BYTES.
   Distribution has to be re-expressed over the byte image (the `GroupImageCodec.ImageInitOf` recipe, which is
   THE seeder), not over the character text, or every offset after the first binary leaf is wrong.
2. `01 GV VALUE "40537". 05 GB PIC 9 COMP-5 OCCURS 5.` under the byte reading gives each 1-byte occurrence one
   CHARACTER of the literal — `'4'`, `'0'`, `'5'`, `'3'`, `'7'` as bytes 0x34/0x30/0x35/0x33/0x37, i.e. the
   values 52/48/53/51/55 — NOT the digits 4/0/5/3/7. That is what GR5 says, and it is a surprising-but-correct
   answer that needs to be derived and stated (and checked against what the other compilers do — the
   group-VALUE-over-non-DISPLAY case is exactly where [[feedback_survey_compilers_on_latitude]] applies) before
   it is pinned in a golden.
3. The same derivation governs the NATIONAL and USAGE BIT leaves the byte cell does not carry at all; those stay
   with RESIDUE-11 whichever way (1)/(2) land.

**FIX SHAPE:** move the distribution onto the byte image, keep the character-slice fast path only for the
all-display subtree it is already correct for, and pin the mixed case with a golden that reads the initialized
bytes back through a REDEFINES X view with `FUNCTION ORD` (the `stepd_mixed_usage_redefines` pattern) so the
claim is about STORAGE, never about a display rendering.

## LANDED 2026-08-31 — and the note above was WRONG about the mechanism

⛔ **THE PREMISE WAS REFUTED BEFORE A LINE WAS CHANGED.** The note asks for GR5 distribution over the BYTE image
so a `PIC 9 COMP-5` leaf takes its slice of the literal's bytes. **§13.18.63.3 SR14** (`cite.py --check` OK) says:

> "If a VALUE clause is specified at the group level, subordinate items within that group shall not be described
> with a JUSTIFIED or SYNCHRONIZED clause, and **all data items subordinate to an alphanumeric group item shall
> be explicitly or implicitly described with usage DISPLAY**."

`01 GV VALUE "40537".` carries no GROUP-USAGE clause, is not strongly typed and is not a variable-length group,
so GV **is** an alphanumeric group item — §13.18.29.4 GR3 (`cite.py --check` OK): "If a GROUP-USAGE clause is not
specified or implied for a group item that is not strongly typed and is not a variable-length group, that group
item is an alphanumeric group item"; §8.5.2.1 — "an alphanumeric group item has class and category
alphanumeric". `05 GB PIC 9 COMP-5` is not usage
DISPLAY. **The measured program is not conforming COBOL**, so there is no area for the byte distribution to exist
over, and the "surprising-but-correct" 52/48/53/51/55 answer the note derived is an answer to a question the
standard does not ask. SR16 extends SR13–SR15 to the format 2 (table) VALUE, so the same holds there.

GR5 is *already* implemented, and correct, for the entire population SR14 admits — every subordinate usage
DISPLAY, so the character image **is** the byte image and a positional character slice **is** the area deposit.
`GroupValueSlicer.DistributableSubtree`'s usage screen was not predicate drift; it was (accidentally) SR14's own
population. **What was missing was the DIAGNOSTIC on the complement.** This is the
[[feedback_validate_the_premise_not_only_the_rule]] shape: the citation was real, the quoted text was real, and
the finding was still impossible.

### What landed

1. **`DataBinder.CheckGroupValueDeclarations`** (new `DataBinder.GroupValue.cs`, wired in `BindPipeline` after
   `UsageInheritancePass` so SR14's "explicitly or **implicitly**" sees inherited usage) → **COBOLNET1702**,
   covering all three group-level VALUE restrictions, none of which existed anywhere in the compiler:
   SR14 conjunct 1 (JUSTIFIED / SYNCHRONIZED subordinate), SR14 conjunct 2 (non-DISPLAY subordinate — this
   note's symptom), SR13 sentence 2 (a subordinate carrying its own VALUE). One screen, because SR14 is a
   two-conjunct sentence and this repo's most reproducible defect is a two-arm rule with one arm written.
2. **`GroupValueSlicer.AreaTextOf`** — the GR5 area rule extracted to ONE place, ridden by both initializer
   lanes, and extended to the FIGURATIVE operand form it never handled.
3. **`GroupImageCodec.ImageInitOfOne`** — the group arm it never had.

### TWO live silent wrong answers on LEGAL source, found by the sibling sweep (neither was in this note)

- **A group VALUE is lost entirely when the group is REDEFINED.** `01 G VALUE "ABCD". 05 A PIC X(2). 05 B PIC
  X(2). 01 R REDEFINES G PIC X(4).` measured `A=[  ] B=[  ] R=[    ]`, while the byte-identical group *without*
  the alias gave `[AB][CD]`. `GroupImageCodec.ImageInitOf` is THE seeder for every character-image backing since
  the PB164 consolidation (Tier-B REDEFINES, EXTERNAL cells, BASED/ADDRESS-OF cells, OO backings) and it walked
  straight past the group's own `RawValue` into the members. §13.18.63.3 SR12 bars a VALUE in the redefin**ing**
  entry, never in the redefined one — so this is conforming source. The **seventh** [[feedback_two_arm_dispatch]]
  instance: the slicer's arm was written, the codec's was not, and only the slicer's lane was ever tested.
- **Every FIGURATIVE group VALUE is lost.** `01 GZ VALUE ZEROS. 05 Z1 PIC X(2). 05 Z2 PIC X(2).` measured four
  SPACES where SR13 ("a figurative constant that is permitted in a MOVE statement to a receiving item of that
  category") + §8.3.3.6.4 GR2 require four `'0'`. GR2 is the branch for "the length of the string **is**
  specified in the rules for the context", it names the VALUE clause, and it carries both the repeat-to-width and
  the truncate-from-the-right; the character identity is GR1's with the per-format GR4–GR8 rules. (GR3 is the
  complementary — length NOT specified — branch, and its sub-rule a is scoped to a concatenation expression;
  §13.18.63.4 GR5 makes the group area the receiving field, so the length is always specified here. This note,
  `GroupValueSlicer`, the design SSOT and the golden all carried GR3a until the review fleet caught it, and GR3a
  would have made the fill ONE character — anyone re-deriving the golden from it computes the wrong answer.)
  The area rule handled quoted and `ALL "lit"` operands and
  dropped figurative WORDS to the member-wise default, where each member took its own category default — which
  is why `VALUE SPACES` looked right and hid it.

### Blast radius, measured before landing

A static scan of `tests/conformance`, `tests/characterization`, `tests/differential`, `tests/version-matrix`,
`tests/nist/programs` (478 CCVS programs) and `tests/nist/copylib` found **ZERO** SR13/SR14 candidates — the 18
apparent SR13 hits were data-names containing the word `VALUE` (`KEY-VALUES`, `RECKEY-VALUE`). The scanner was
proved able to fire on known-positive input before its silence was trusted.

## ⛔ REVIEW-FLEET LANDING 2026-08-31 — the screen missed a whole population, and the population was TYPE

The first landing walked `DataBinder.ConformanceForest`. That forest's final filter is
`StrongTypeModel.TypeAnchor(item) is null`, and `ExpandType` sets `TypeName` on the **subject** of the TYPE
clause — so a reference site AND its entire clone subtree fell out of the screen.

**MEASURED (probe, both legs):**

| program | first landing | now |
|---|---|---|
| `01 T IS TYPEDEF. 05 A PIC 9(4) COMP. 05 B PIC X(2). 01 R TYPE T VALUE "ABCD".` | compiles CLEAN, `A=0000`, `B=spaces` | COBOLNET1702 at R's line |
| the byte-identical inline spelling `01 R VALUE "ABCD". 05 A PIC 9(4) COMP. 05 B PIC X(2).` | COBOLNET1702 | COBOLNET1702 |

The violation is **COMPOSED**: R's entry carries the VALUE and no usage, T's entries carry the usage and no
VALUE, and neither carries it alone. §13.18.57.4 GR3 (`--check` OK) makes the reference-site VALUE meaningful —
"the content of the literal associated with that VALUE clause is used for the initial value associated with the
subject of the entry" — and its NOTE sends the reader to the VALUE clause's own syntax rules for exactly this
composition. This is PB184's ORIGINAL symptom (a group VALUE silently dropped on a non-conforming program)
reproduced inside the fix for it.

**THE ROOT FIX IS A SECOND FOREST, not a weakened one.** `ConformanceForest` keeps its contract — the
WRITTEN-ENTRY set the per-entry data-attribute gates fire over once each, clones excluded because the template
was gated once. `DataBinder.CompositionForest` adds the clone subtrees back, and a pass now picks **by what its
rule is about**: a per-entry attribute gate takes the first, a rule about the COMPOSED entry takes the second.
Both are one `.Where` off a shared `DeclaredForest` spine, and each carries the other's name in its doc comment.

**Provenance keeps the verdict count honest.** New `DataItem.ValueIsCopied` marks a VALUE an entry only ASSUMED
(§13.18.57.4 GR1 / §13.18.49 GR1 copy it down), so the screen answers **once per WRITTEN VALUE clause**. This
also fixed a duplicate the fleet did not find: `01 A VALUE "ABCD". 05 X PIC 9(4) COMP. 01 B SAME AS A.` reported
COBOLNET1702 **twice**, both anchored at X's one declaration — B's copy of A's VALUE re-screening A's own
subtree. (A SAME AS entry can never carry its own VALUE: §13.16.3 SR12, enforced as COBOLNET1555 — verified by
probe, so no separate note is owed.) The anchor also moved: a clone subordinate's `DeclaredAt` points into the
TYPEDEF, which is legal on its own, so a composed violation is reported at the reference site instead.

**SR1 pulled forward out of [[PB206]] — because it was load-bearing for a rule already shipped.** §13.18.29.4 GR3
makes a group alphanumeric only when it has no GROUP-USAGE clause **and** is not strongly typed **and** is not a
variable-length group. The screen wrote only the first conjunct, so with SR1 unenforced both of SR1's own shapes
answered SR14's usage arm. Measured: `01 ST IS TYPEDEF STRONG VALUE "ABCD". 05 SY PIC 9(4) COMP.` and a
dynamic-capacity group each drew COBOLNET1702 naming SR14 — the wrong rule, while their real violation went
unreported. Now COBOLNET1703 (`group-value-subject-shape`), reported at the subject, and the subtree walk is
skipped because the entry itself has to change. ⚠ `OCCURS … DEPENDING ON` is NOT a variable-length group —
§8.5.1.12.1 names dynamic-**length** elementary items and dynamic-**capacity** tables only — measured on both
shapes before the predicate was written.

**SR13 sentence 2's own duplication, fixed.** `01 A VALUE "XX". 05 B VALUE "YY". 10 C PIC 9 COMP.` reported C
once per VALUE-carrying ancestor. A subject subordinate to another subject is now skipped: SR13 sentence 2
already rejects that shape once, at the outer subject, whose walk reaches the whole subtree.

**Citations repaired (all `cite.py --check`ed).** `§13.18.26.4 GR3` does not exist — §13.18.26 is the FULL clause
and has no `.4`; the rule is **§13.18.29.4 GR3**, and §8.5.2's quoted text is in **§8.5.2.1**. The figurative
area rule is **§8.3.3.6.4 GR2**, not GR3a (GR3a is the concatenation-expression rule and gives length ONE). Both
had propagated into code, this note, the design SSOT and a fixture — the [[feedback_spec_is_the_oracle]]
inheritance failure mode, caught by the fleet.

**Diagnostic text.** `UsageWord`'s fallback was `usage.ToString().ToUpperInvariant()`, rendering `PROGRAMPOINTER`,
`FLOATBINARY32`, `BINARYCHAR`, `OBJECTREFERENCE` — words no COBOL program contains. It now DERIVES the
§13.18.60.2 keyword by hyphenating the enum name (covering 18 of 24 members, so a new usage is automatic) with
five explicit spellings, guarded by `UsageWordDriftTests`, which asserts every member renders as reserved COBOL
words. It failed on its first run — `COMPUTATIONAL-1/-2/-5` are not §13.18.60.2 words; FLOAT-SHORT and FLOAT-LONG
are.

**Pins added:** `negative/pb184-group-value-type-reference` (the composed shape), `negative/pb184-group-value-
strong-subject` + `negative/pb184-group-value-variable-length-subject` (SR1's two arms), `negative/pb207-bit-
group-level-value` (the crash, refused by name), and four new legs in `2023/pb184_group_value_area`: `S5`/`C7`/
`C8` close the operand-form × lane matrix (`ALL <figurative-word>` was pinned by neither lane, `ALL "literal"`
only by the slicer), and `TV` is the POSITIVE control — an all-DISPLAY template composed at a reference site
carrying a VALUE is LEGAL, so GR5 must deposit across the cloned members and the widened screen must stay silent.
Proved able to fail: reverting `CompositionForest()` to `ConformanceForest()` reds the type-reference and
strong-subject fixtures ("must be REJECTED at --std 2002"), and the drift test reds on the wrong usage spellings.
