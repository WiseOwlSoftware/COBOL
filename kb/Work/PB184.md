# PB184

Found 2026-08-30 by the PB164 Step D review wave's hand-rolled-DISPLAY-union sweep (F8), **deliberately not
changed under that sweep** — it is a §13.18.63.4 GR5 derivation with real blast radius, not predicate drift, and
the wave recorded it rather than fixing it inside a mechanical widening.

**MEASURED**, on the Step D tree:

```cobol
01 GV VALUE "40537".
   05 GB PIC 9 COMP-5 OCCURS 5.
```

every `GB(1..5)` initializes to **zero**. The group VALUE is dropped on the floor; nothing diagnoses it.

**MECHANISM.** `GroupValueSlicer.DistributableSubtree`
(`src/Cobol.Net.Compiler/CodeGen/DataDivision/GroupValueSlicer.cs:38-52`) is one of the hand-rolled
`{ Category: Numeric, IsFloat: false, Usage: Usage.Display }` unions the F8 sweep catalogued. A leaf passes the
screen only when it is string-stored **or** a NATIVE zoned-DISPLAY numeric; a BINARY / COMP-5 / PACKED /
float / INDEX leaf fails it, `DistributableSubtree` returns false for the whole group, and the member-wise
default (`new Struct { child = <child's own Init> }`) is emitted instead — each leaf taking its own VALUE or,
absent one, zero. `SliceInit` has the mirror-image screen.

**WHAT THE SPEC ASKS FOR.** §13.18.63.4 GR5 (`cite.py --check` OK): "If a VALUE clause is specified in a data
description entry of a group item, the group area is initialized without consideration for the individual
elementary or group items contained within this group." The literal's characters are deposited positionally
across the group's STORAGE, and each subordinate then simply IS whatever its own description makes of the bytes
lying under it. Since PB164 every numeric usage HAS a pinned byte form, so "the bytes lying under it" is now a
defined quantity for every leaf kind this screen rejects — which is exactly why the exclusion stopped being
defensible when the Tier-C arm fell.

⚠ **The in-code reason was stale twice over** and is corrected in the same commit as this note: it blamed "the
Tier-C byte boundary" (false since V59/PB164) and cited a paraphrase — "ISO §13.18.63" with the wording of the
MOVE rule §14.9.25.4 GR4, not the VALUE rule. The string "without consideration for the individual elementary
items" (no "or group") appears NOWHERE in the standard; both real occurrences read "elementary or group items".
That paraphrase is inherited across ~10 more sites in `src/`, `docs/` and `kb/` — the CLAUDE.md rule 1
inherited-citation shape, adjacent to [[PB182]]; sweeping them is that note's kind of work.

**WHY IT IS NOT A ONE-LINE WIDENING (and what to derive before touching it).**
1. The slicer works in CHARACTERS against `ImageWidth`; a byte-form leaf's window is `StorageWidth` BYTES.
   Distribution has to be re-expressed over the byte image (the `GroupImageCodec.ImageInitOf` recipe, which is
   THE seeder), not over the character text, or every offset after the first binary leaf is wrong.
2. `01 GV VALUE "40537". 05 GB PIC 9 COMP-5 OCCURS 5.` under the byte reading gives each 1-byte occurrence one
   CHARACTER of the literal — `'4'`, `'0'`, `'5'`, `'3'`, `'7'` as bytes 0x34/0x30/0x35/0x33/0x37, i.e. the
   values 52/48/53/51/55 — NOT the digits 4/0/5/3/7. That is what GR5 says, and it is a surprising-but-correct
   answer that needs to be derived and stated (and checked against what the other compilers do — the
   group-VALUE-over-non-DISPLAY case is exactly where [[feedback_survey_compilers_on_latitude]] applies) before
   it is pinned in a golden.
3. The same derivation governs the NATIONAL and USAGE BIT leaves the byte cell does not carry at all; those stay
   with RESIDUE-11 whichever way (1)/(2) land.

**FIX SHAPE:** move the distribution onto the byte image, keep the character-slice fast path only for the
all-display subtree it is already correct for, and pin the mixed case with a golden that reads the initialized
bytes back through a REDEFINES X view with `FUNCTION ORD` (the `stepd_mixed_usage_redefines` pattern) so the
claim is about STORAGE, never about a display rendering.
