# PB690 — OPEN — the file's coded character set was never chosen

Found 2026-09-05 by the `PB329` implementer (report §"New defects" N4), which deliberately left it out of the
line-sequential determination: the loss is a property of the FILE's coded character set and hits RECORD sequential
identically, where GR23 does not reach, so answering it inside item 115 would have fixed one arm of a two-arm
problem.

## The facts

The alphanumeric repertoire is UTF-16 (project decision; `charset_utf16`), but
`src/Cobol.Net.Runtime/IO/SequentialConnector.cs#OpenCore` constructs its four readers/writers with
`Encoding.Latin1`, and `Rewrite` uses `Encoding.Latin1.GetBytes`; `RecordFraming` frames the same bytes. Latin-1's
encoder maps every code point above U+00FF to `?` (0x3F). A record area holding `€` (U+20AC) is written as `?` and
read back as `?`: no status, no diagnostic, wrong data on the medium and in the program.

## The rule to derive from

§8.1.2 (`cite.py --check 8.1.2 "coded character set"` → OK) — the coded character sets an implementation supports
and the mapping between the alphanumeric repertoire and a file's coded character set are implementor-defined
(Annex A.1 items 31 and 34); the CODE-SET clause §13.18.13 (`--check 13.18.13 "CODE-SET"` → OK) is the program's
way of naming a file's coded character set through an alphabet-name. So the determination to make first: what coded
character set a sequential file WITHOUT a CODE-SET clause uses (UTF-8 is the only choice that loses nothing and
interoperates; Latin-1 is what the code does today), and what happens to a character the chosen set cannot
represent (a status in the '7x' record-content family, or the substitution character — never silence). The
determination goes in CONFORMANCE.md as DOC-A.1-31/-34 rows; the CODE-SET clause's own state (declined? staged?) is
measured while there.

## Fix

One encoding decision per connector, derived from CODE-SET or the determination's default, applied to reader,
writer, `Rewrite` and `RecordFraming` alike (one place — the connector's open, where PB673 now passes the
statement's operands); an unrepresentable character reported, not substituted; goldens on record and line
sequential with a supplementary-plane character round-tripping, and a negative-content case. The keyed
organizations' stores (`RecordFraming`) are the sibling to sweep. Fixed-width record files change their byte
layout under UTF-8 (a record's byte length is no longer its character length) — measure what PB327's byte-width
layout assumes before choosing.

## BLOCKED ON THE OWNER (2026-09-05) — the default coded character set is a product decision

The fix requires choosing what coded character set a sequential file WITHOUT a CODE-SET clause uses, and that
changes the bytes of every data file the compiler writes and the layout assumptions of every fixed-width file it
reads. Today the code is Latin-1 (lossy above U+00FF); the surveyed model implementation (GnuCOBOL) is
byte-transparent — it neither encodes nor decodes; a UTF-8 default loses nothing and interoperates but makes a
record's byte length differ from its character length, which PB327's byte-width layout must then account for.
**⛔ Bare question for the owner:** for a sequential file with no CODE-SET clause, what is the file's coded character
set — UTF-8 (lossless, variable-width bytes per character), Latin-1 with a '7x' status for an unrepresentable
character (fixed one byte per character, refuses rather than corrupts), or the program's own alphanumeric
repertoire written as UTF-16 (fixed two bytes, no interchange)? `blocked_by` is empty because the blocker is the owner.
