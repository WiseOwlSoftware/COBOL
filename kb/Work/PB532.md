# PB532

## Mechanism — picture-clause-p2
Nothing in the PICTURE pipeline ever measures the LENGTH of character-string-1. PictureAnalyzer.Analyze goes from the trailing-';' strip and the empty guard (PictureAnalyzer.cs:52-64) straight into ExpandRepeats, and a grep of src/ for the constant 63 or for 'maximum number of characters' returns no hit on the PICTURE path (the only 63s in the tree are the 8.3.2.1 COBOL-word ceiling, COBOLNET1567). SR4's cap therefore does not exist at any edition. The omission is also a doc/code divergence: docs/COBOLNET_DATA_MODEL_DESIGN.md D21 lists 'SR4 (63 characters)' among the load-bearing spec anchors for the PICTURE model, so the design doc asserts a rule the code has never had.

### Expected, from the standard
ISO/IEC 1989:2023 13.18.40.3 SR4 (cite.py --check 13.18.40.3 OK): 'The maximum number of characters allowed in character-string-1 is 63.' The count is over the string AS WRITTEN, not the expanded symbol run -- SR6's second sentence ('the length of the integer, not the length of the constant-name, is counted toward the maximum number of characters in character-string-1') fixes that reading, and the expanded reading would absurdly outlaw `PIC X(30000)`. So 64 written X's shall be rejected with a named diagnostic while `PIC X(30000)` stays legal, and a constant-name repetition shall be counted by its substituted integer's digit length.

```
$ python scripts/spec/cite.py --check 13.18.40.3 "s shall be rejected with a named diagnostic while `PIC X(30000)` stays legal, and a constant-name repetition shall be counted by its substit..."
  FAIL: §13.18.40.3 exists but does NOT contain 's shall be rejected with a named diagnostic while `PIC X(30000)` stays legal, and a constant-name repetition shall be counted by its substituted integer'
$ python scripts/spec/cite.py --check 13.18.40.3 "the length of the integer, not the length of the constant-name, is counted toward the maximum number of characters in character-string-1"
  OK  §13.18.40.3 6)  (Syntax rules)
```

### Observed
Accepted at every edition. The measurement point already exists and is in the right place: DataBinder.Constants.ExpandPicConstants rewrites `(constant-name)` to `(integer)` in the SOURCE string before PictureAnalyzer sees it, which is exactly the form SR6's second sentence says to count -- so the cap is a single length test on the string handed to Analyze, taken after the constant substitution and before ExpandRepeats. The per-edition value cannot be derived from this spec: Annex E carries no picture-length item (a grep of the annex for 'picture' returns only E.2 item 27, VALUE clause literal categories, and E.3.3 item 19, the EDITING phrase), so the 1985/2002/2014 numbers need the earlier standards or an owner decision; the row diverges at all four editions either way, since no cap of any size is enforced.

### Repro
Pinned compiler. `01 W1 PIC ` followed by 64 literal X characters and a period compiles clean, rc=0, at --std 85, 2002, 2014 and 2023 (probes .../probe/pic-p2/{sr4a,e485,e42002,e42014,e42023}); the 63-character control also compiles (sr4b), so no boundary is being applied anywhere.

### Code site
src/Cobol.Net.Compiler/Binding/PictureAnalyzer.cs:52-64 (Analyze's prologue -- where the check belongs), src/Cobol.Net.Compiler/Binding/DataBinder.Constants.cs:337-363 (ExpandPicConstants -- the substitution that makes the SR6 counting rule mechanical), docs/COBOLNET_DATA_MODEL_DESIGN.md:447 (the D21 anchor list that claims SR4)
