# PB3664 — a fixed editing sign reads the untruncated sending sign

✅ **APPROVED BY THE OWNER (2026-10-24).** The owner (2026-10-24 ~18:00 PDT, attended operator session 0a5c7c77), after the operator's explanation of the spec text and GnuCOBOL's behavior for PB3664-PB3666: "Approve all three for fix, and make DISPLAY and the boolean operators agree, and record the choice in docs/CONFORMANCE.md".

**Sites:** `src/Cobol.Net.Runtime/Values/Numeric/CobolEdit.cs` (`Render`: `negative = value < 0` at about line 202 is
computed before the truncation at about line 238; line 192 passes `value < 0` to `Materialize`).

## The rule (checked with `cite.py --check`)

- §13.18.40.5 5): "Table 8, Results of fixed insertion editing, shows the character(s) produced by an editing sign
  control symbol, depending on the value of the data item." In Table 8, `+` gives `+` and `-` gives a space in the
  "Positive or zero value" column. CR and DB give spaces there.
- §13.18.40.5 6) b): "The result depends upon the value of the data to be stored. If the value is not zero, the result
  is the same as if th…" (the floating and zero-suppression rule). The value of the edited data item is the value AFTER
  the move's alignment and truncation (§14.9.25.4 6) d)).

**Derived expectation** (edition 2014, the same in 2002 and 2023): `MOVE S TO E` with `S PIC S9V999 VALUE -0.001` stores
the value zero in every receiver below, so:

| Receiver | Expected | Fresh judge (300fd78bd) |
|---|---|---|
| `PIC -9.99` | ` 0.00` | `-0.00` |
| `PIC +9.99` | `+0.00` | `-0.00` |
| `PIC 9.99CR` | `0.00  ` | `0.00CR` |

The same value reaches `-9.99` as ` 0.00` through `MOVE S TO N` (`PIC S9V99`) followed by `MOVE N TO E1`, and through
`COMPUTE E1 = S`. So the program prints two different results for one value depending on the path.

## Repro

`fz05181` (MOVE -0.000092 TO PIC -Z(7)9.99 prints `-       0.00`). Reduced (the operator re-ran it at 300fd78bd):

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. NEGZ.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 S PIC S9V999 VALUE -0.001.
01 E1 PIC -9.99.
01 E2 PIC +9.99.
01 E3 PIC 9.99CR.
01 N PIC S9V99.
PROCEDURE DIVISION.
MOVE S TO E1 E2 E3
DISPLAY "[" E1 "][" E2 "][" E3 "]"
MOVE S TO N
MOVE N TO E1
DISPLAY "[" E1 "]"
COMPUTE E1 = S
DISPLAY "[" E1 "]"
STOP RUN.
```

It prints `[-0.00][-0.00][0.00CR]`, `[ 0.00]`, `[ 0.00]`. It should print `[ 0.00][+0.00][0.00  ]` and then ` 0.00`
twice.

## For the implementer (once approved)

The four editing paths inside one `CobolEdit.Format` call disagree. BLANK WHEN ZERO, Z suppression and floating `-`
read the truncated value (zero), while the fixed `-`, `+`, CR and DB read the sign before truncation. Compute the sign
once, from the value the receiver holds, and pass that one sign to every path. Then sweep the other places that compute
an edited sign (the de-editing MOVE, the national-edited arm). Related open question, not decided here: `MOVE -100 TO
PIC S9(2)` prints `+00` on both compilers, and §14.9.25.4 6) d) 2. a. says "the sign of the numeric value shall be
represented". The typed-native carrier has no negative zero (PB1128's background). Adjudicate it beside this fix.

## GnuCOBOL 3.2 (read in the pinned 3.2 source, 2026-10-24)

It prints `[ 0.00][+0.00][0.00  ]`, the spec-derived result. `libcob/move.c` `cob_move_display_to_edited` sets `is_zero` from the digits that land in the edited picture, and every place it writes `-`, CR or DB is guarded by `neg && !is_zero` (its comment: "Check negative and not zero"). The adjacent `MOVE -100 TO PIC S9(2)` question stays open: both compilers store `+00`.

## Landed

Re-probed on the implementer's build at 0ac850004: `[-0.00][-0.00][0.00CR]` reproduced, plus `[-       0.00]` for
`-Z(7)9.99` and `[-00]` for `MOVE -100 TO PIC -99`. `CobolEdit.Render` now decides `negative` ONCE, after the alignment
and truncation, from the digit string the receiver holds (`value < 0` and a nonzero digit), and returns it so `Format`
hands the same sign to `Materialize`; every path (the fixed `+ - CR DB`, the floating `+ -`, the FOR-form character-1,
the wide literals) reads it. Sibling swept: `CobolLocaleEdit.Format` (format 2, GR18 `+`) had the same pre-truncation
sign and now reads `!storesZero`; the floating-point numeric-edited arm (`CobolEdit.Float.cs`) cannot truncate a nonzero
significand to zero and already emits a positive zero image on underflow. The `MOVE -100 TO PIC S9(2)` question: the
numeric receiver stores `+00` (the carrier has no negative zero), the edited receiver now agrees with it (a zero value is
positive), and the determination is in `docs/CONFORMANCE.md` section 3. Witnesses:
`conformance-suite/cases/13.18.40.5-Editing-rules/pb3664_edited_sign_stored_value` (one test for all four editions,
the behaviour does not differ by edition) and `CobolEditStoredSignTests`.
