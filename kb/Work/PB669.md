# PB669 — LANDED — locks are set by opt-in and must be seen by everyone

Found 2026-09-05 by the `PB321` implementer (report §"New defects" A), measured AFTER its landing on its worktree
(`<a9d94900 scratch>/PB321/probe/p4.cob`). Deliberately not taken there: record locking is a different mechanism
from OPEN arbitration and sits on the runtime's hottest path.

## Repro (`--std 2002`+; both connectors on one physical file)

```cobol
       SELECT F-A … ORGANIZATION RELATIVE ACCESS RANDOM SHARING WITH ALL OTHER LOCK MODE IS MANUAL.
       SELECT F-B … ORGANIZATION RELATIVE ACCESS RANDOM.          *> no SHARING, no LOCK MODE
           OPEN I-O F-A   OPEN I-O F-B                            *> both 00 — Table 19 row ALL OTHER / I-O × column all other / extend I-O output
           MOVE 1 TO K-A  READ F-A WITH LOCK                      *> 00, record 1 locked by F-A
           MOVE 1 TO K-B  READ F-B                                *> P4-READB=00 REC=ALPHA   ⛔ expected 51
```

## The rule

§9.1.16: "While locked by a given file connector, a record is not accessible to another file connector in the same
or a different run unit, except by the execution of a READ statement with the IGNORING LOCK phrase" (`OK §9.1.16`).
§12.4.5.9.4 GR1 a): "If there is a SHARING clause in that file control entry, no record locks are set by the
execution of I-O statements through the associated file connector" (`OK §12.4.5.9.4 1) a)`) — a rule about
SETTING locks. Nothing in §12.4.5.9.4 exempts a connector from SEEING locks others hold; the asymmetry is the
standard's, and `FileRegistry.LocksEffective`'s doc comment states it correctly ("Conflict CHECKS against locks
OTHER connectors hold are never disabled") while the code two levels up contradicts it.

## The mechanism

`src/Cobol.Net.Compiler/CodeGen/Verbs/SequentialIoEmitter.cs#LockGoverned` — a plain connector's READ is emitted
without the lock check at all; `src/Cobol.Net.Runtime/IO/FileRegistry.cs#ReadLockGovern` and `#ReadShared` — both
return early on `!_connectorShares.TryGetValue(name, …)`, i.e. a connector that never opted in never consults
the physical file's lock table. The same opt-in-overlay shape PB321 removed from OPEN: the rule is written over the
PHYSICAL FILE (§9.1.16 "another file connector in the same or a different run unit"), the code keyed it on the
connector's own clause.

## Landed 2026-09-22 (wave 44 C)

Re-probed and it REPRODUCED — and WORSE than the note recorded. On the repro
(`<w44c scratch>/p669.cob`, `--std 2002`) the plain connector answered `READB=00 ALPHA` as written, and also
`REWB=00` and `DELB=00`: it REWROTE and then actually DELETED a record another connector held locked, after which
the MANUAL connector's own re-read of record 1 answered `23`. Three conflict rules, not one.

**Half the note's mechanism was already gone.** `SequentialIoEmitter.LockGoverned` no longer exists: kb/Work
PB683 removed the compile-time governance predicate and every emitter now renders the governed entry
unconditionally. The surviving half was the runtime's, and it was the whole defect — each governed body opened
with `if (!_connectorShares.TryGetValue(name, out var meta)) return <ungoverned body>;`, so a connector that
never opted in never consulted the physical file's lock table at all.

**Fix.** `FileRegistry.ShareOf` is the ONE reader of the opt-in map and a miss yields `ImplementorDefaultShare`,
the §12.4.5.9.4 GR1 b) 2. posture (`FileLockMode.None` — the *"specify that the default is no record locking"*
option the rule itself offers); the governed body then runs unchanged. Acquisition stays gated on
`LocksEffective`, so a clause-less connector still sets no lock even from an explicit LOCK phrase; the conflict
CHECK is gated on nothing. Two questions, two gates, one body — where one gate had answered both. All five
governed entries were fixed, not one (`ReadShared`, `ReadKeyedShared`, `WriteShared`, `RewriteShared`,
`DeleteShared`); WRITE has no conflict rule to state but its early return was the same shape.

⚠ **DETERMINATION.** §14.9.30.4 GR9, §14.9.35.4 GR11 and §14.9.10.4 GR6 each open *"If record locking is
enabled for the … file connector"*, and §14.9.30.4 GR7 sends that question to §12.4.5.9. Read as a property of
the ENVIRONMENT — the processor supports record locking (§12.4.5.9.4 GR2) and the physical file is not open in
the sharing-with-no-other mode (GR3). REJECTED: "this connector's own clause causes it to acquire locks", which
would make §9.1.16's unqualified sentence false for any program that simply omits LOCK MODE — record locking
unenforceable against exactly the programs it exists to constrain — and would give GR1 a)'s narrow *"no record
locks are **set**"* a scope its words do not have. Recorded in `COBOLNET_FILES_DESIGN.md` **D20** and in
`FileRegistry.LocksEffective`'s doc comment, which had stated the conclusion correctly while the code two levels
up contradicted it.

**Performance.** Governance is now unconditional, so the common case pays a `Count` test and nothing more:
`RecordLocksGovern(meta, st, name)` — *some connector holds a lock on this physical file, or this one may
acquire one* — is asked before any record IDENTITY is computed, keeping `MutationTargetRecordId` (a key or RRN
string per statement on the keyed organizations) off the plain REWRITE/DELETE path and `LastReadRecordId` off
the plain READ tail; `ReleasePriorRecordLocks` returns on an empty table before its LINQ walk. When the gate is
false every governed action below it is provably a no-op.

**Goldens.** `2002/pb669_lock_visibility_plain_connector` (the repro, the IGNORING LOCK exemption, REWRITE and
DELETE through the plain connector, an unlocked record of the same file, and the REVERSE direction proving the
plain connector sets nothing); `CobolFileLockTests.PlainConnector_SeesAnothersRecordLock_ButSetsNone_9_1_16` is
the cross-connector matrix with three controls. The negative below the introducing edition is the existing
`negative/sharing_below_2002`.

⚠ **THE LINUX LEG IS THE VERDICT.** File-lock and ACL semantics differ between hosts and the local battery runs
only on Windows (kb/Work PB796). These results are Windows-only; CI's Linux leg on the lander's push is the real
one.

## Fix shape (as written 2026-09-05)

Split the two questions the way PB321 split them for OPEN: "does this connector SET locks" stays keyed on
`_connectorShares` (§12.4.5.9.4 GR1), and "is this record LOCKED by another connector" becomes a lookup on the
physical file's `RecordLocks` for EVERY READ / REWRITE / DELETE through any connector (the `'51'` and `'52'`
statuses of §9.1.13.6, and the READ IGNORING LOCK exemption), with the emitter routing every keyed and sequential
read through one `ReadLockGovern` whose fast path is a `RecordLocks.Count == 0` test so an unshared file costs one
dictionary probe. Goldens at 2002/2014/2023: the repro (expect `51`), the IGNORING LOCK exemption (`00`), REWRITE
through the plain connector against a locked record, and the reverse (a plain connector never sets a lock — the
MANUAL connector reads it freely); `CobolFileLockTests` gains the cross-connector matrix. Measure the hot-path cost
before and after on the sequential corpus leg (PB321's residual `_physical.For` cost is the baseline).
