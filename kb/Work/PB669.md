# PB669 — OPEN — locks are set by opt-in and must be seen by everyone

Found 2026-09-05 by the `PB321` implementer (report §"New defects" A), measured AFTER its landing on its worktree
(`<a9d94900 scratch>/PB321/probe/p4.cob`). Deliberately not taken there: record locking is a different mechanism
from OPEN arbitration and sits on the runtime's hottest path.

## Repro (`--std 2002`+; both connectors on one physical file)

```cobol
       SELECT F-A … ORGANIZATION RELATIVE ACCESS RANDOM SHARING WITH ALL OTHER LOCK MODE IS MANUAL.
       SELECT F-B … ORGANIZATION RELATIVE ACCESS RANDOM.          *> no SHARING, no LOCK MODE
           OPEN I-O F-A   OPEN I-O F-B                            *> both 00 — Table 19 row ALL OTHER / I-O × column all other / extend I-O output
           MOVE 1 TO K-A  READ F-A WITH LOCK                      *> 00, record 1 locked by F-A
           MOVE 1 TO K-B  READ F-B                                *> P4-READB=00 REC=ALPHA   ⛔ expected 51
```

## The rule

§9.1.16: "While locked by a given file connector, a record is not accessible to another file connector in the same
or a different run unit, except by the execution of a READ statement with the IGNORING LOCK phrase" (`OK §9.1.16`).
§12.4.5.9.4 GR1 a): "If there is a SHARING clause in that file control entry, no record locks are set by the
execution of I-O statements through the associated file connector" (`OK §12.4.5.9.4 1) a)`) — a rule about
SETTING locks. Nothing in §12.4.5.9.4 exempts a connector from SEEING locks others hold; the asymmetry is the
standard's, and `FileRegistry.LocksEffective`'s doc comment states it correctly ("Conflict CHECKS against locks
OTHER connectors hold are never disabled") while the code two levels up contradicts it.

## The mechanism

`src/Cobol.Net.Compiler/CodeGen/Verbs/SequentialIoEmitter.cs#LockGoverned` — a plain connector's READ is emitted
without the lock check at all; `src/Cobol.Net.Runtime/IO/FileRegistry.cs#ReadLockGovern` and `#ReadShared` — both
return early on `!_connectorShares.TryGetValue(name, …)`, i.e. a connector that never opted in never consults
the physical file's lock table. The same opt-in-overlay shape PB321 removed from OPEN: the rule is written over the
PHYSICAL FILE (§9.1.16 "another file connector in the same or a different run unit"), the code keyed it on the
connector's own clause.

## Fix shape

Split the two questions the way PB321 split them for OPEN: "does this connector SET locks" stays keyed on
`_connectorShares` (§12.4.5.9.4 GR1), and "is this record LOCKED by another connector" becomes a lookup on the
physical file's `RecordLocks` for EVERY READ / REWRITE / DELETE through any connector (the `'51'` and `'52'`
statuses of §9.1.13.6, and the READ IGNORING LOCK exemption), with the emitter routing every keyed and sequential
read through one `ReadLockGovern` whose fast path is a `RecordLocks.Count == 0` test so an unshared file costs one
dictionary probe. Goldens at 2002/2014/2023: the repro (expect `51`), the IGNORING LOCK exemption (`00`), REWRITE
through the plain connector against a locked record, and the reverse (a plain connector never sets a lock — the
MANUAL connector reads it freely); `CobolFileLockTests` gains the cross-connector matrix. Measure the hot-path cost
before and after on the sequential corpus leg (PB321's residual `_physical.For` cost is the baseline).
