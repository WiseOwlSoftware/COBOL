# PB3456 — the external-repository slices hold every campaign, not only the restructuring program

> ⚙ **flags:** process-only

Source: the wave 1132 unit (2026-10-20, `plan_wave.py --from-budget --borrow-days 6 --cluster PB3353`), whose plan
held PB1278, PB3337, PB3338 and PB3340 with "file-set collision with in-flight work the open external-repository
slices [RUNNING] (docs/CONFORMANCE.md): it waits until that work finishes (then continues it) or is decided".

**Sites:** `scripts/orchestrator/plan_wave.py` (`main`, the slice half of the file-set partition: `slices = …`,
`if a.cluster and slices:`; `classify_inflight`'s default state `RUNNING`), `scripts/orchestrator/test_plan_wave.py`.

**Mechanism.** R69 §2 (owner, 2026-10-07) reserves the open slices' DESIGN-external-repository §12 file set from the
RESTRUCTURING waves, R2 and every R3 wave (the Delete program PB2119 included): "a collision defers the wave, never the
train". `work.r3_program_problems` applies it to the R3 program (cluster PB2119) only, and plan_wave.py's own comment
says the same: "the slices gate the R3 campaign only (PB2118 Draft 7, R69 section 2): the fix lane is never held for
them". The code that follows reads `if a.cluster and slices:`, so it reserves the set from EVERY campaign. PB3353 is a
fix campaign (SORT and file I/O defects), and the set holds `docs/CONFORMANCE.md`, the file that CLAUDE.md rule 1 sends
every implementor-latitude choice to. So every PB3353 note that writes a conformance row waits for slices
PB2100, PB2101, PB2103 and PB2104. Those notes are open, but nobody is working them: no worktree, branch or dispatch
holds them, and the Mythos lane shut down on 2026-10-19. With no branch, `classify_inflight` gives the owner its default
state, so the plan prints `[RUNNING]` for work that is not running.

**Measured 2026-10-20 on main ed4477ef2.** `work.slice_file_set()` holds 99 files: 97 under `src/` or `tests/`, plus
`Directory.Build.props` and `docs/CONFORMANCE.md`. The real plan (wave 1132) held all four notes on
`docs/CONFORMANCE.md`. The same `--dry-run` with `work.EXTERNAL_SLICE_TITLE` set to a pattern that matches nothing
(the in-memory experiment, log `E:\COBOL-coord\scratch\pb3456-dryrun-noslices.log`, which reserves and writes nothing)
plans PB1278 (primary `src/Cobol.Net.Compiler/Binding/DataBinder.cs`, 5 rows). PB3337 and PB3338 then wait only on
wave 1132's group C (`docs/rearchitecture/DESIGN-runtime-library.md`), and PB3340 waits only on group A
(`SequentialConnector.cs`). That is real in-flight work, and it ends with that wave. With the slice hold in place, the
owner's tier-2 chain (decision 2026-10-19 18:58, "Option A") cannot be planned at all while any of the four slices is
open.

**Fix direction (for the implementer to confirm against R69 §2 and DESIGN-architecture-review §8.7).** Reserve the
slice set from the restructuring program only (the clusters R69 §2 names: R2 and the R3 waves, PB2119 included), the
same rule `r3_program_problems` already applies. Write the rule once, so the planner and the register check read one
predicate, and add a test of both arms to `test_plan_wave.py`: a fix campaign whose note declares `docs/CONFORMANCE.md`
is planned while a slice is open, and an R3 note declaring the same file waits. While no slice is in flight, the held
row should say OPEN (RESERVED), not RUNNING. If the owner wants the slices to hold a fix campaign too, that is an owner
decision recorded in R69, and the comment changes to match.
