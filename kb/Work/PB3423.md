# PB3423 — the campaign planner has no tier input

Found by the wave-1128 implementer lead (w1128a), 2026-10-19. The `plan_wave.py --cluster PB3353 --dry-run` plan ranks cluster defects outside the owner's tier 1 (PB3390, PB3391, the Opus grammar groups) ahead of the tier-1 notes PB3350, PB3372 and PB3382.

**Register search before filing (R1).** `kb/Work` grepped for planner ranking and tier order: PB3420 (the plan) records the limit in its "How the register enforces the order" section ("the tier-1 ids are not planned first by tier") but is a decision note that fixes nothing, and no other note owns it. So this note owns the fix.

**The mechanism.** `scripts/orchestrator/plan_wave.py` takes no tier input. `plan` ranks the campaign's clusters at `ranked.sort(key=lambda ci: (ci[0].get("depth", 0), -rows(ci[1]), -ci[0].get("harm", 0)))` (line 1064 on 2026-10-19): the place in the `blocked_by` topology, then the inventory rows claimed, then harm. Tier is not a note field, `steer.ps1` names a unit type and never a set of notes, and `-Cluster` names a campaign, not a tier (PB3420). A tier is therefore a register state only where a hold can express it (tier 2 by `status: owner`, tier 3 by `blocked_by: [PB3420]`); tier 1 has no hold, and its notes rank by rows and harm among every other READY member of the cluster.

**Harm.** No user's program is affected. A wave's budget can be spent on lower-tier groups while the owner's first-ordered correctness defects wait for a later wave.

**Fix (one place).** Give the cluster order one tier key, read by `plan` before `rows`: either a register field on the note (a `tier:` frontmatter value validated by `work.py check` and read by `work.cluster_order`, so the planner and `work.py next --cluster` agree), or the plan note's ordered list parsed once. Prefer the field: it is data the next campaign sets without touching the planner. Pair it with a drift test that a lower-tier group never plans ahead of a READY higher-tier one, and update PB3420's mechanism section to name the field in the same change.

**Landed (operator, 2026-10-19; the owner chose "Start now, fix PB3423 alongside" at the restart).** The tier is a register field, SCOPED to a campaign: `tier: ["PB3353:1"]`, a list of `CAMPAIGN:N` entries, because a note belongs to several campaigns (PB1278 to three: PB1276, PB2911, PB3353) and the owner's order for one says nothing about another. One reader, `work.tier_entries` / `work.tier_of`; `work.py check` (`topology_problems`) refuses an entry that is not `CAMPAIGN:N`, names a campaign twice, or names one the note's `cluster:` does not.
- `work.cluster_order` gives each row its EFFECTIVE tier (the lowest of its own and of every open member it blocks, so a tier-1 note's blocker is tier 1 too) and sorts by tier, then depth, then id; together still a `blocked_by` order, which `plan_wave.campaign_clusters` relies on. `work.py next --cluster` prints the tier column.
- `plan_wave.campaign_clusters` gives a cluster its lowest note's tier, and `plan_wave.lift_tiers` lowers a blocker's cluster to the tier of every cluster waiting on it, so `plan` (which letters a dependent only after its blockers' groups) can rank the tier first. The rank is (tier, depth, rows, harm); a fix-lane cluster has no tier and depth 0, so the fix lane's rank, and its pre-campaign golden, are unchanged.
- The ten tier-1 notes of PB3420 carry `tier: ["PB3353:1"]`; PB3420's order and mechanism sections name the field.
- Tests (`scripts/orchestrator/test_plan_wave.py` section 9b and section 10, 256/256): the order and the effective tier, the scoping (the same notes rank by another campaign's tiers), `lift_tiers` transitively, the lettered plan, and the drift test: under a group cap no untiered group is chosen while a READY tier-1 group waits, however much harm the untiered one carries. Reverting the rank key to (depth, rows, harm) fails exactly the two plan checks, reproducing this defect (the untiered harm-8 groups took the cap).
- Measured on the real register (`plan_wave.py --cluster PB3353 --dry-run` from the branch, after wave 1129 was planned by the old rank): the next wave plans PB2512, PB3350, PB3372, PB3382, PB3383, PB3385 (six tier-1 notes) before the untiered PB3263 and PB3369; PB1278 still waits on the external-repository slices' file set (docs/CONFORMANCE.md), a hold the tier does not override.
