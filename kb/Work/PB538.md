# PB538

## Mechanism — synchronized-clause
sync-left-right-phrase-discarded - the SYNCHRONIZED clause's LEFT/RIGHT selection is parsed and thrown away, and the determination that makes throwing it away conforming is never written down. `syncClause : (SYNCHRONIZED | SYNC) (LEFT | RIGHT)?` parses all three shapes, but the binder's whole treatment is `else if (clause.Context.syncClause() is not null) synchronized = true;` - `syncClause()` has exactly ONE call site in the compiler, the LEFT/RIGHT token is never read, and DataItem carries a single `bool Synchronized`, so the model cannot represent which of the three the program wrote. That is behaviourally correct ONLY under a one-byte natural boundary, and nothing states one: docs/CONFORMANCE.md DOC-A.1-195 says 'no physical alignment' and 'no implicit FILLER' - statements about PADDING - and is written against GR9/GR8/GR10 and 8.5.1.6.3, never against GR3/GR4/GR5, while the REQUIRED Annex A.1 item 197 determination ('positioning when neither RIGHT nor LEFT is specified') has no DOC-A.1-197 row in CONFORMANCE.md at all (47 DOC- rows; 195 present, 196 and 197 absent, though both are in docs/rearchitecture/spec-rule-catalog.json). Two rules therefore pass on an unstated premise, and the one bit a future alignment implementation would need has already been discarded at the clause site. The fix has two halves and both are cheap: record the selection (a `SyncAlignment { None, Left, Right }` on DataItem, set from the syncClause token, the way OwnSign records the SIGN selection) so the distinction survives; and add the DOC-A.1-197 row stating the natural boundary WiseOwl COBOL recognises for SYNCHRONIZED - one byte - which is what makes GR2, GR3, GR4 and GR5 simultaneously true.

### Expected, from the standard
13.18.55.4 GR4 - 'SYNCHRONIZED LEFT specifies that the elementary item is to be positioned such that it will begin at the left byte of the natural boundary in which the elementary item is placed.' GR5 - 'SYNCHRONIZED RIGHT specifies that the elementary item is to be positioned such that it will terminate on the right byte of the natural boundary in which the elementary item is placed.' GR3 leaves the bare form's positioning to the implementor; 8.5.1.6.4 makes natural boundaries a machine property and says 'The way in which data is stored is determined by the runtime module, and need not respect these natural boundaries' and 'Each implementor who provides for special types of alignment shall specify the precise interpretations that are to be made'; Annex A.1 item 197 - 'SYNCHRONIZED clause (positioning when neither RIGHT nor LEFT is specified). This item is required. This item shall be documented in the implementor's user documentation.' So all three forms may collapse to one behaviour, but ONLY if the implementor's natural boundary is one byte, and THAT determination is the thing the standard requires to be written down.
