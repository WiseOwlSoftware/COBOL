# PB792 — OPEN — the migration mode restores a spelling no edition ever had

Filed 2026-09-06 14:19 PDT by the registrar, from the finding landing train 19's lander appended to
[[PB732]] when it DROPPED that cluster at the gate. **Two of the premises this note was filed under do not
survive re-derivation on main at `07cbb2ad`, and both changed the fix.** They are the first two sections.

## The measurement that is not in dispute

Train 19's lander, quoted verbatim in `kb/Work/PB732.md:139-153`:

```
CobolNet.Tests.Conformance.VersionMatrixTests_P9 /_P10/_P11
  .Cobol85Program_StillCompilesAtLaterEdition(testName: "RW104A", edition: 2002 / 2014 / 2023) [FAIL]
  tests/nist/programs/RW104A.cob(245,31): error COBOLNET1639: RD 'RW-FS4-REPORT-1' entry 'FILLER':
  the VALUE operand 'COLUMN' is not a literal — every format of the VALUE clause writes literal-n
  (ISO §13.18.63.2) …
```

The source, `tests/nist/programs/RW104A.cob:245` (card `024500`):

```cobol
       03  VALUE "DETAIL LINE "  COLUMN 20    PIC X(12).
```

It is legal. §13.15.3 SR2 (`--check` OK): *"If the entry-name clause is specified, the data-name format or filler
format shall be specified. The entry-name clause shall immediately follow the level-number. **All other clauses
may be written in any order.**"* So a report group description entry may write `VALUE IS literal-1` and then the
COLUMN clause, and COBOLNET1639 naming `COLUMN` proves the token was parsed INSIDE `valueClause`.

## ⛔ Premise correction 1 — the swallow is `--permissive`-ONLY, and that is the whole mechanism

The brief this note was filed from says the operand list absorbs the keyword, full stop. **It does not, in a
strict compile, at any edition.** Three measurements on main:

1. `src/Cobol.Net.Frontend/Grammar/Core/CobolWords.g4:29` — the only route by which `COLUMN` can become a
   `valueClauseOperand` (`valueClauseOperand → unaryExpression → primaryExpression → dataReference → cobolWord`,
   `CobolExpressions.g4:31`, `:251`, `:260`, `CobolParserCore.g4:547`) is:

   ```antlr
   | {userWordHere("COLUMN")}? COLUMN
   ```

2. `tests/version-matrix/reserved-words.json:616-624` — `COLUMN` is `r85: true, r2002: true, r2014: true,
   r2023: true`, provenance *"continuous since 1985"*.

3. `src/Cobol.Net.Frontend/Parsing/CobolParserCoreBase.cs:298` —

   ```csharp
   protected bool userWordHere(string keyword) => Edition.Permissive || !reservedHere(keyword);
   ```

   `reservedHere` (`:279`) is `ReservedWords.Find(w)?.IsReservedAt(Edition.Year)`. For `COLUMN` that is TRUE at
   85, 2002, 2014 and 2023 — so in a STRICT compile `userWordHere("COLUMN")` is false at every edition, the
   `cobolWord` alternative is unavailable, `valueClauseOperand` cannot start on `COLUMN`, the `valueItem` loop at
   `CobolData.g4:642` terminates, and `reportGroupClause*` (`CobolReportWriter.g4:82`) matches
   `reportColumnClause` (`:141-143`) exactly as the source intends.

The failing test leg confirms it from the other side. `Cobol85Program_StillCompilesAtLaterEdition`
(`tests/Cobol.Net.Tests.Conformance/VersionMatrixTests.cs:294-300`) runs the PERMISSIVE compile FIRST and asserts
on it:

```csharp
var (permOk, permDiag) = EditionHarness.CompileNist(testName, edition, permissive: true, checkOnly: true);
Assert.True(permOk, $"[INV-1 continuity] …");
```

and the independent corroboration for the strict arm is that **RW104A is corpus-GREEN** (`tests/nist/corpus.tsv:241`
`RW104A  RW  green`), while the NIST golden run defaults to `--std 85` and NOT permissive
(`tests/Cobol.Net.Tests.Conformance/NistDifferentialTests.cs:65-68` — `COBOLNET_NIST_STD` default 85,
`COBOLNET_NIST_PERMISSIVE` off unless `=1`). A byte-identical CCVS report at `--std 85` strict is only possible
if the COLUMN clause on card 024500 was honoured.

## ⛔ Premise correction 2 — the report-group VALUE does NOT take exactly one literal

The brief offers as an alternative fix *"the report-group VALUE takes exactly one literal, per the printed
format (§13.18.63.2 — a report group entry's VALUE has ONE literal)"*. **RENDERED from the printed page**
(`python scripts/render-spec-page.py 546` → PDF p546, printed folio **516**):

```
Format 4 (report-section):

   ⎧ VALUE  IS  ⎫
   ⎨            ⎬   { literal-1 } …
   ⎩ VALUES ARE ⎭
```

`{ literal-1 } …` — §5.2.7 (`--check` OK) makes the ellipsis repeat the braced group, so Format 4 is **one or
more** literals. (`cite.py --check 13.18.63.2 "Format 4 (report-section)"` → OK; the transcription's figure note
says the same: *"The single-line `{ literal-1 }` pair is the delimiter to which the ellipsis applies — one or
more literals."*) Format 1 is the one-literal format, and it is the DATA-ITEM format, not this one. Narrowing
`valueClause` in the report section would reject conforming multi-literal source — the exact CLAUDE.md rule 4
outcome this note exists to prevent. **Do not take that fix.**

## The root cause

`userWordHere`'s own doc comment (`CobolParserCoreBase.cs:282-297`) states the contract the bypass is for:

> `--permissive` "accepts constructs the targeted edition removed, warning instead of rejecting", **and a word the
> edition added to §8.9 is precisely such a removal** — the funnel computes `ConstructAvailability.Removed` for it
> and `EditionSeverityPolicy` downgrades the COBOLNET0901 to a warning. … So the gate is STRICT-ONLY, and under
> `--permissive` the pre-reservation reading (the word is an ordinary user word, operand lists absorb it) is
> restored ON PURPOSE — that IS the pre-removal semantics the mode promises.

That reasoning is exactly right **for a word some edition ADDED to §8.9** — `COLUMNS` (r85 false, r2002 true),
`CONSTANT`, `PROPERTY`, and the rest of the 2002/2014/2023 additions. It does not reach `COLUMN`, which §8.9 has
reserved at every edition this compiler targets. There is no COBOL edition in which `COLUMN` was a user-defined
word, so migration mode has **no pre-removal semantics to restore** — and §8.3.2.1 rule 1 (`--check` OK:
*"Reserved words shall not be used as user-defined words or system-names"*) held at 85 just as it holds at 2023.
The predicate is written as a blanket `Edition.Permissive ||` over the whole gated set, so it grants the migration
exemption to words that were never removed from anything.

⛔ **The consequence is not scoped to the VALUE clause or to the report section.** Every greedy operand list in
the grammar — every `X (COMMA? X)*`, every `X+` whose element bottoms out at `cobolWord` — absorbs every
always-reserved word under `--permissive`. RW104A is the instance a golden happened to catch.

## What the compiler does with the swallowed operands today

`valueItem` (`CobolData.g4:683-686`) is `valueClauseOperand ( … valueClauseOperand)*`, so all THREE operands
(`"DETAIL LINE "`, `COLUMN`, `20`) land in ONE `valueItem`. `DataBinder.ExtractValue`
(`src/Cobol.Net.Compiler/Binding/DataBinder.cs:3458-3476`) takes `value.valueItem().FirstOrDefault()`, finds none
of its concatenation / figurative / symbolic / constant-name arms matching, and falls to the last line:

```csharp
return item.GetText() is { } raw ? NormalizeIfNumericLiteral(raw) : null;   // :3475
```

`GetText()` over that `valueItem` GLUES the operand tokens — `"DETAIL LINE "COLUMN20` — and hands that to the
report-writer sink at `src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs:518`. The entry's clause list carries
no `reportColumnClause` node at all, so the §13.18.14 COLUMN NUMBER 20 the user wrote is simply gone.

Flags, and what each is measured on:

- **`silent`** — MEASURED. Battery #61 (`61d13d3e`) was all-green on main, i.e. this permissive leg PASSES today;
  the mis-parse is accepted with no error. ⚠ Whether a downgraded COBOLNET0901 *warning* naming `COLUMN` is
  emitted alongside is NOT measured (it depends on `VersionConformancePass.VisitCobolWord`'s position filter,
  `:2072` — see [[PB764]]); a warning would still not describe the damage, but the note should not claim total
  silence it has not measured.
- **`wrong_answer`** — DERIVED from the parse shape above, not run: a report field with its COLUMN clause dropped
  and a glued VALUE string cannot print where the source says. ⚠ **The probe, and it is a documented one-liner:**
  `COBOLNET_NIST_STD=2023 COBOLNET_NIST_PERMISSIVE=1` re-targets the whole golden run (the lever
  `NistDifferentialTests.cs:60-64` exists for exactly this), so running RW104A under it and diffing against
  `tests/nist/valid/RW104A.txt` settles the runtime consequence in one command. Run it before fixing.
- `rejects_legal_source` is FALSE on main **today** and becomes TRUE the moment any VALUE-operand screen lands —
  which is the whole of [[PB732]]'s drop. That is recorded in prose rather than in the flag because the flags
  describe the compiler that exists.

## Fix shape

The reservation gate's permissive bypass must key on the word's reservation HISTORY, not on a blanket flag:
`--permissive` restores a word to `cobolWord` only where the word is reserved at the COMPILE edition and NOT
reserved at some earlier edition this compiler targets — i.e. exactly where `ConstructAvailability.Removed` is
what the doc comment says it is. `reserved-words.json` already carries every fact the predicate needs (`r85`,
`r2002`, `r2014`, `r2023` per word), so this is a change to `userWordHere` plus a query on `ReservedWordSet`, not
a new table and emphatically not a per-word list (CLAUDE.md rule 5, and [[PB764]] is the note about what happens
when a structural rule is written as a list of sites).

Pair it with a DRIFT TEST that is the complement of the existing edition-gate sweep: for every word whose
reservation row is true at all four editions, a program using it as a user-defined word is refused under
`--permissive` as well as strict. That set is derivable from `reserved-words.json`, so the test needs no
maintenance and the next always-reserved word is covered by construction.

⚠ **Edition-gate sweep required** (`feedback_edition_gate_sweep`): tightening `userWordHere` changes what parses
under `--permissive` at all four editions, and `Cobol85Program_StillCompilesAtLaterEdition` runs the permissive
leg over the WHOLE corpus witness set. The gate filter for this fix must carry `~VersionMatrix` and `~Nist` —
their absence is precisely why train 19 discovered the problem at the landing gate instead of in the cluster
(`kb/Work/PB732.md:166-174`).
