# PB5483 - a root fix lands first, and one cause is re-run once

**Sites:** `scripts/orchestrator/enqueue.py` (`fix_first_cause`, `jump_to_front`, `queue`, `land`, `--fix-first`),
`scripts/orchestrator/landing_measure.py` (`fix_first`, `HOLD_FOR_FIX`, `red_cause`, `requeued_unfixed`, the figures),
`scripts/orchestrator/land_lane.py` (`bounce_step`, `classify_bounce`, `WatchEffects.held_causes`);
`docs/rearchitecture/DESIGN-test-build-ci.md` section 3.17.2 steps 3 and 4.

## The owner's instruction

The owner, 2026-11-13: "we rerun things far too many times, often in CI, rather than chase down and fix the ultimate
issue. Then we should immediately get the issue fix in the build rather than waiting for all preceeding jobs to encounter
the same problem."

## The gap

`enqueue.py queue` handed every pull request to the merge queue with `gh pr merge --auto`, which joins the BACK. When main
or the pipeline carries a red (a flake, a CI-only fault), the branch that removes it waited behind every queued pull
request, and each of those could meet the same red first. Nothing in the landing could say "this one first". Separately,
the landing lane re-queued an INFRA or RUNNER red once PER LANDING, so one flake was re-run once on every pull request
it hit: PR #1607 met the main-carried flake of kb/Work PB5478 twice (runs 43550577247 and 43553292493), the first
re-queued, the second recorded as `finisher` because `RED_ACTS` had no word for "held for the fix".

## What is decided

1. **`enqueue.py land <branch> --fix-first "<cause>"`** (and `queue --fix-first`). The cause is REQUIRED and must name
   the red it removes: a kb/Work note id the worktree carries and/or a failed run id (`run 43550577247`, or the
   actions/runs URL). An unstated cause, or a note the worktree does not carry, is exit 2 REFUSED before the land lock,
   the merge or the stamp: jumping is for a fix main is waiting on, not for impatience. Every other guard is unchanged
   (queue ACTIVE, review stamp, GREEN gate record, DEVLOG stamp and the landing checks).
2. **The jump.** After the push, the passes and the pull request, `jump_to_front` reads the pull request's merge-queue
   entry; an entry already queued is DEQUEUED first (an enqueue of a queued pull request does not move it), unless it
   is already first at the pushed head; then GraphQL `enqueuePullRequest(jump: true, expectedHeadOid: <pushed head>)`,
   so a head that moved is GitHub's refusal. The answer must say `jump: true`.
3. **A refused jump is never a lost landing.** The pull request is queued with `gh pr merge --auto` exactly as any
   landing, the exit is 17 (`ENQUEUED, NOT JUMPED`), and the record says it did not jump. The likely refusal is a fresh
   head whose pull-request check (`ci-gate` on `pull_request`, the cheap jobs) has not passed yet; the re-run of the same
   command dequeues and jumps.
4. **The record.** Each attempt is one entry of the landing record's `fix_first` list (cause, notes, runs, jumped,
   detail, at). `landing_measure.py summary` prints the jumps and the landings that hit the named runs first (every other
   pull request whose `reds` hold one of them).
5. **No hold of other landings while a fix-first is queued.** A landing queued after the jump joins behind it, and its
   merge group is built on every entry ahead, the fix included, so it already carries the fix; a hold would only add the
   fix's whole CI wall to every landing behind it. The cost of a jump is GitHub rebuilding the groups that were already
   building behind the new front entry (up to `max_entries_to_build`, 5): their partial runs are wasted and
   `cancel_superseded.py` cancels them. That is the price of not letting each of them meet the same red.
6. **One re-run per CAUSE.** A cause's key is a red test case (the failing test is the same on every pull request it
   hits; `landing_measure.red_cause`). The lane's red records now carry their `cases`. A PIPELINE_CLASSES red whose red
   case was already re-queued once, on any pull request, while no merged fix-first landing names one of that cause's
   failed runs (`landing_measure.requeued_unfixed`), is HELD: not re-queued, recorded with the new act `hold-for-fix`,
   its watch ended BOUNCED with HELD on its line, and the operator alerted. `summary` counts re-queues and holds per
   cause by the same one key (`red_causes`), so "this cause was re-run N times before its fix landed" is one number. An
   INFRA red has no red case and so no key: it is re-queued once per landing as before.
7. **No hold outlives its cause's fix** (branch review round 1, R1-1 and R1-2). The open causes are read in time order
   (`landing_measure.open_causes`): a release covers only the reds before it, and a later red of the same test is a new
   cause. A hold is released by (a) a merged fix-first landing naming a failed run of the cause, (b) the kb/Work note the
   hold names reading `landed` or `retired` on origin/main (the lane names the open note whose text names the failing
   test when it first holds, `land_lane.cause_note`, and asks for one when none does; `open_causes_now` records the
   release), or (c) the operator: `land_lane.py release-hold <case> --reason "<the fix>"`. A hold older than 12 hours
   (`HOLD_ALARM_H`) is alerted again once per window. Exit 17 is a DONE landing to the lane (it is queued), alerted once.

## Not verified, and what the first real use must check

The self-tests fake the gh layer (`queue_gh`: a merge queue whose enqueue joins the front only when the request carries
`jump` true and refuses a wrong `expectedHeadOid`). No real pull request was queued with `jump` in this change. The first
real `--fix-first` landing must check: (a) GitHub accepts the mutation as built (the variable types `Boolean!` and
`GitObjectID!`); (b) whether it refuses a pull request whose required `pull_request` check is still pending (then the
exit-17 path is the normal first answer and the re-run jumps), or accepts it; (c) that the entry reads `jump: true` and
position 1 in `gh api graphql` afterwards; (d) what `dequeuePullRequest` does to the group already building.

A queue-watch `requeue` of a stalled fix-first pull request re-queues it at the back (`enqueue.requeue` uses `--auto`);
the operator re-runs `land --fix-first`. A queued pull request dequeued for a jump that GitHub then refuses goes back at
the back and loses its place (review R1-3; exit 17, or 9 when the fallback `--auto` is refused too). `cause_note` finds a
note by the failing test's method name on origin/main; a hold whose test no open note names is released only by (a) or
(c), and its alarm says to file one.
