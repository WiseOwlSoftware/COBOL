## Mechanism
Lead from the refuter of GR-14.6.11-2 (execution batch): an indexed file with CODE-SET IS EBCDIC, a WRITE of a record holding U+20AC answers FILE STATUS 00; the conversion runs only at persist time in IndexedConnector.CloseCore, where CodeSetConversion.ToMedium throws. ## Landed (wave 65 D, 2026-09-27) — one membership screen at the output statement, shared with PB1542

Re-probed on the w65d build (`scratchpad/w65d/probe/ix.cob`, EBCDIC indexed, WRITE "K€01DATA"): BEFORE `IX-EURO=00` then
`Unhandled exception. System.InvalidOperationException … at IndexedConnector.CloseCore()`; AFTER `IX-EURO=91`, no exception.

**The root was not the deferral but a missing question.** The WRITE and REWRITE of every organization already asked ONE
screen, `FileConnector.RecordHasCharacterWithoutByteImage` ('91', owner decision R47), but it answered `false` for any file
with a CODE-SET (`CodeSet is null && …`), so a converting file had no screen at all and the conversion's own throw was the
only check — reached at CLOSE for the keyed stores, at the WRITE for sequential. The screen now asks the file's coded
character set whichever it is: `CodeSetConversion.HasCharacterWithoutImage` (GR6 b membership, `Represents`) with a CODE-SET,
`FileCharacterSet` without. Every WRITE/REWRITE arm of every organization already calls it, so the fix is ONE line of dispatch
plus the membership predicate — no arm was edited. ⚠ DETERMINATION (the note asked to "convert at the WRITE"): the
REPRESENTABILITY question is the output statement's (GR1 "during output operations"; the status is the statement's), while
the ENCODING stays at the one physical boundary the design fixes (`CodeSetConversion` type remarks) — converting into the
in-memory store would put key values and comparisons in the medium code set. After the screen the encoding is total, so the
persist cannot fail on a program-supplied record; its throw remains a guard for a path that skipped the screen (an invariant
violation, pinned by `CodeSetConversionTests.ToMedium_OfACharacterAboveTheChannel_IsAnInvariantViolation`).
Status: '91' (§9.1.13.11 item 1; DOC-A.1-110) — the SAME condition R47 names for a file with no CODE-SET ("a record
character with no image in the file's coded character set"), so the same status and the same EC-I-O-IMP correspondence.
EC-DATA-CONVERSION (§14.6.13.1.6 Table 12, NF, `cite.py` OK) was considered and rejected: everywhere the standard sets it, an
implementor-defined substitution character is supplied and the operation completes, which is exactly what R47 forbids for
this condition. Sweep: RELATIVE and SEQUENTIAL (record, print-control, REWRITE in place) ask the same predicate; LINE
SEQUENTIAL asks it through `LineSequentialCharacterSet` ('71'/'09' — PB1542). Goldens and the rest: see PB1542.
