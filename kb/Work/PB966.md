## Reproduced

`scratchpad/reg10/pcorr.cob`:

```cobol
       01 SRC.
          05 S1 PIC X(3) VALUE "ABC".
          05 S2 PIC X(3) VALUE "DEF".
       66 SALIAS RENAMES S1 THROUGH S2.
       01 DST.
          05 S1 PIC X(3).
          05 S2 PIC X(3).
           MOVE CORRESPONDING SALIAS TO DST
```

```
pcorr.cob(13,12): error COBOLNET1757: MOVE CORRESPONDING operand 'SALIAS' is described with level-number 66, so it
is not a group data item — the operands shall be group data items (ISO §14.9.25.3 SR12)
```

## Rules (each `cite.py --check`ed)

- `--check 14.9.25.3 "Identifier-3 and identifier-4 shall specify group data items and shall not be reference-modified."` → `OK §14.9.25.3 12)`
- `--check 13.18.45.4 "When the THROUGH phrase is specified, data-name-1 defines an alphanumeric group item that includes all elementary items"` → `OK §13.18.45.4 2)`
- `--check 14.7.6 "have the same data-name and the same qualifiers, if any, up to, but not including, D1 and D2"` → `OK §14.7.6 1)`

SR12 is satisfied: SALIAS IS an alphanumeric group item. §14.7.6's opening sentence also admits it ("D1 and D2 are
identifiers that refer to alphanumeric group items, …"). Nothing excludes level 66. §14.7.6 4) excludes a
corresponding item that CONTAINS a RENAMES clause, which is not the same thing as D1 being one.

## The determination the fixer must record (§14.7.6 1) over an alias)

The items "in D1" are the elementary items GR2 says the alias "includes", but their qualifier chains run through the
REDEFINED record (`S1 OF SRC`), not through SALIAS. That leaves "the same qualifiers … up to, but not including, D1"
undefined for them. The proposed reading, which follows GR2's own wording: an alias includes ELEMENTARY items only
(no intermediate groups), so each included item's qualifier list relative to D1 is EMPTY, and it corresponds by
data-name alone. An included item whose name is not unique within the alias falls to §14.7.6 6). Survey the model
implementations (IBM Enterprise COBOL, Micro Focus, GnuCOBOL) per the owner's protocol. Record the result in
CONFORMANCE.md §7 if the survey agrees, or as a `kind: decision` note if it splits.

## Sibling sweep

The same COBOLNET1757 screen guards ADD/SUBTRACT CORRESPONDING (§14.9.2 / §14.9.44 share §14.7.6). Check whether any
other statement's "shall be a group data item" test keys on the level-number rather than on the item being a group:
INITIALIZE, a group relation condition, a group MOVE sender, and the CALL argument screen that PB965 depends on.
**One predicate, "is this identifier a group item", used by every screen.** PB392 made CORRESPONDING's SR6 key on
group KINDS. Extend that predicate so it knows about THROUGH aliases, and do not add a second test beside it.
