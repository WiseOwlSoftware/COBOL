# PB3564 — implicit filler bits after a USAGE BIT item have no storage

## Scenario

Fuzz programs fz01323 and fz03422 (`OUTPUT_DIFFERS:13.18.1`). fz03422 is the witness: an ALIGNED bit table inside an
alphanumeric group displays as NUL NUL after `MOVE B"1"`. The first program, fz01323, is GnuCOBOL 3.2 printing one character
of a `PIC 1(4)` bit item (GnuCOBOL has no BIT support, the 10-22 `THEY_REJECT` row), so it does not witness the defect.

### Reduced repro (the B2 adjudicator's probe, verbatim: `adj\B2\probes\bit2\bit2.cob`)

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. BIT2.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 G1.
   05 G1-B PIC 1 USAGE BIT.
   05 G1-X PIC X.
01 G2.
   05 G2-B PIC 1(8) USAGE BIT.
   05 G2-X PIC X.
PROCEDURE DIVISION.
   MOVE "AB" TO G1
   DISPLAY "G1 [" G1 "] X [" G1-X "] B [" G1-B "]"
   MOVE "AB" TO G2
   DISPLAY "G2 [" G2 "] X [" G2-X "] B [" G2-B "]"
   STOP RUN.
```

## Expected (spec)

Each citation was re-run through `python scripts/spec/cite.py --check` from the worktree on 2026-10-23 (all OK).

- §8.5.1.6.3 "Alignment of data items of usage bit" (OK): "Following a bit data item within an alphanumeric group item … as
  needed to advance alignment to a required natural boundary for the next item within that group. The filler bit positions are
  implicitly described as a filler elementary bit data item" (the checked sentence, continuing past that point). The filler bits
  are data of the group, so they are part of its byte image.
- §14.9.25.4 4) (OK): the group move is "treated exactly as if it were an alphanumeric to alphanumeric elementary move, except
  that there is no conversion of data from one form of internal representation to another", so the group's byte image
  round-trips: `MOVE "AB" TO G1` then `DISPLAY G1` shows `AB`.

## Actual (judge e7cf38ce4)

Reduced: `MOVE "AB" TO G1`, `DISPLAY G1` prints `[<NUL>B]` where `[AB]` is required. With an 8-bit item and no filler (`G2`) the bytes
round-trip. The B2 adjudicator's reading: a group MOVE writes the filler bits, and the next read re-packs the member carriers and
gives zeros for the filler, so what the move put there is lost.

## Mechanism and code site

`src/Cobol.Net.Compiler/CodeGen/DataDivision/GroupImageCodec.cs:1153-1159` (the `AsImageOf` BitRun arm packs the member carriers
and fills the filler with zeros) and `:1019-1034` (`BitAreaOf` composes the filler as literal zeros). The filler bits have no
storage, so whatever a group move puts there is lost. `docs/CONFORMANCE.md` line 1303 says "trailing filler bits zero"; that is
right for the initial image and not after a group store, so the fix changes that sentence in the same change set.

## Witnesses

fz03422 (an aligned bit table in an alphanumeric group); fz01323 is not a witness.

## Sibling sweep and golden to require

- Every group-image route that composes a bit run: the group MOVE, a group sent through CALL BY CONTENT/REFERENCE, group
  comparison, INITIALIZE of the group, a READ/WRITE of a record holding bit items. The implicit filler of every §8.5.1.6.3 case
  (after a bit item, at the end of a record, ALIGNED, SYNCHRONIZED) is covered.
- Related landed notes: PB161, PB584.
- Golden: the repro as a conformance case with the derived output (`[AB]`), plus an ALIGNED table leg (fz03422's shape).

## Orchestrator decision

§8.5.1.6.3 (implicit filler bits are a filler elementary bit data item of the group) and GR4 of §14.9.25.4: the group's byte image must round-trip; a group move writes the filler bits and the next read must give them back.
