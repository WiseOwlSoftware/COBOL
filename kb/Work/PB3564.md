# PB3564 — implicit filler bits after a USAGE BIT item have no storage

## Scenario

Fuzz programs fz01323 and fz03422 (`OUTPUT_DIFFERS:13.18.1`). fz03422 is the witness: an ALIGNED bit table inside an
alphanumeric group displays as NUL NUL after `MOVE B"1"`. The first program, fz01323, is GnuCOBOL 3.2 printing one character
of a `PIC 1(4)` bit item (GnuCOBOL has no BIT support, the 10-22 `THEY_REJECT` row), so it does not witness the defect.

### Reduced repro (the B2 adjudicator's probe, verbatim: `adj\B2\probes\bit2\bit2.cob`)

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. BIT2.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 G1.
   05 G1-B PIC 1 USAGE BIT.
   05 G1-X PIC X.
01 G2.
   05 G2-B PIC 1(8) USAGE BIT.
   05 G2-X PIC X.
PROCEDURE DIVISION.
   MOVE "AB" TO G1
   DISPLAY "G1 [" G1 "] X [" G1-X "] B [" G1-B "]"
   MOVE "AB" TO G2
   DISPLAY "G2 [" G2 "] X [" G2-X "] B [" G2-B "]"
   STOP RUN.
```

## Expected (spec)

Each citation was re-run through `python scripts/spec/cite.py --check` from the worktree on 2026-10-23 (all OK).

- §8.5.1.6.3 "Alignment of data items of usage bit" (OK): "Following a bit data item within an alphanumeric group item … as
  needed to advance alignment to a required natural boundary for the next item within that group. The filler bit positions are
  implicitly described as a filler elementary bit data item" (the checked sentence, continuing past that point). The filler bits
  are data of the group, so they are part of its byte image.
- §14.9.25.4 4) (OK): the group move is "treated exactly as if it were an alphanumeric to alphanumeric elementary move, except
  that there is no conversion of data from one form of internal representation to another", so the group's byte image
  round-trips: `MOVE "AB" TO G1` then `DISPLAY G1` shows `AB`.

## Actual (judge e7cf38ce4)

Reduced: `MOVE "AB" TO G1`, `DISPLAY G1` prints `[<NUL>B]` where `[AB]` is required. With an 8-bit item and no filler (`G2`) the bytes
round-trip. The B2 adjudicator's reading: a group MOVE writes the filler bits, and the next read re-packs the member carriers and
gives zeros for the filler, so what the move put there is lost.

## Mechanism and code site

`src/Cobol.Net.Compiler/CodeGen/DataDivision/GroupImageCodec.cs:1153-1159` (the `AsImageOf` BitRun arm packs the member carriers
and fills the filler with zeros) and `:1019-1034` (`BitAreaOf` composes the filler as literal zeros). The filler bits have no
storage, so whatever a group move puts there is lost. `docs/CONFORMANCE.md` line 1303 says "trailing filler bits zero"; that is
right for the initial image and not after a group store, so the fix changes that sentence in the same change set.

## Witnesses

fz03422 (an aligned bit table in an alphanumeric group); fz01323 is not a witness.

## Sibling sweep and golden to require

- Every group-image route that composes a bit run: the group MOVE, a group sent through CALL BY CONTENT/REFERENCE, group
  comparison, INITIALIZE of the group, a READ/WRITE of a record holding bit items. The implicit filler of every §8.5.1.6.3 case
  (after a bit item, at the end of a record, ALIGNED, SYNCHRONIZED) is covered.
- Related landed notes: PB161, PB584.
- Golden: the repro as a conformance case with the derived output (`[AB]`), plus an ALIGNED table leg (fz03422's shape).

## Orchestrator decision

§8.5.1.6.3 (implicit filler bits are a filler elementary bit data item of the group) and GR4 of §14.9.25.4: the group's byte image must round-trip; a group move writes the filler bits and the next read must give them back.

## Landed (2026-10-23, w1157 group I)

**Re-probe.** The note reproduced on a fresh build (`MOVE "AB" TO G1` printed `[<NUL>B]`, G2 round-tripped), and the damage was wider than the one run tail: the same loss hit the bits between the occurrences of an ALIGNED table (`T PIC 1(3) ALIGNED OCCURS 2` lost its pad and tail, the fz03422 shape), the bits between the runs of a GROUP-USAGE BIT group (`MOVE B"1111111111" TO BG` over `BA PIC 1(2). BB PIC 1(2) ALIGNED` read `1100000011`), and a group VALUE (`BV VALUE B"1111111111"` read the same).

**Root.** The implicit filler of 8.5.1.6.3 ("implicitly described as a filler elementary bit data item") had no storage on the record-struct lane: every composer wrote literal zeros for it (`BitAreaOf`, `CobolBits.Pack`'s trailing pad, `CobolBits.Strided`'s pad) and every distributor dropped it (`FromBits`, the run unpack, `EmitRunMemberFromBits`). The REDEFINES / EXTERNAL / BASED / LINKAGE lanes hold the bits in a shared string and never lost them, so the same group read differently with and without an alias.

**Fix shape.** One list, `BitLayout.FillersOf(owner)` (a `RunTail` after each run, a `TablePad` between the occurrences of a strided table), names every filler a group's struct stores; `PhysicalModel` declares each as a hidden string field (`Physical.FillerBits`, emitter-fixed name `__bf<k>`); `GroupImageCodec` composes them (`PackedRunOf` / `AsImageOf`, `BitAreaOf`, `BitCarrierOf` with `CobolBits.Strided(..., pads)`) and distributes them (`EmitMemberFromImage`, `FromBits`, `EmitRunMemberFromBits` with `CobolBits.StridePads`); `GroupValueSlicer.SliceBitInit` initializes them from a group VALUE area. A bit group's byte face is now its bit face packed (`AsImage` = `Pack(AsBits())`, `FromImage` = `FromBits(Unpack())`), one composition behind both faces (it also removes the run-image / bit-face disagreement for a group that begins mid-byte, PB3158). `RecordStructEmitter.EmitLeafMethods` skips the filler fields: the leaf vector is the neutral carrier of the cell-backed twin, which has none.

**Tests.** Goldens `14.9.25-MOVE/pb3564_group_move_keeps_bit_filler`, `13.18.1-ALIGNED/pb3564_aligned_filler_keeps_group_bits`, `13.18.60-USAGE/pb3564_bit_record_filler_file_io` (sequential and relative READ / WRITE / REWRITE / INTO / FROM round-trips with AT END 10, INVALID KEY 23 and OPEN status 35) and the negative `14.9.25-MOVE/pb3564-group-move-keeps-bit-filler-below-2002` (COBOLNET0900). `BitRunImageDriftTests.AliasedGroup_HoldsTheFillerAGroupMoveWrote` (eight shapes, struct lane = alias lane = the round trip); `AlignedBitTableExtentDriftTests.Strided_TakesItsPaddingFromTheStoredFiller_AndStridePadsReadsItBack`.

**Not stored (registered as leads, reads zero as before).** A run holding an OCCURS DEPENDING table (its tail moves with the count), the padding of an element of a dynamic-capacity bit table, the filler of a strongly-typed leaf-vector-carried group; INITIALIZE ... WITH FILLER resets the stored filler in the record-struct lane (review round 1) and the filler of a group a REDEFINES class, an EXTERNAL or BASED record or a LINKAGE area holds as shared bytes (review round 2); a REPLACING BOOLEAN sender over the bits between the occurrences of an ALIGNED table in the record-struct lane is refused at run time by name; the tail of a run in a record-struct group that holds the canonical of a Tier-B class is not stored.

## Review round 1 (2026-10-23)

R1-1 (blocking, fixed): a one-occurrence strided bit table crashed the compiler; `BitLayout.HasTablePad` is the one predicate of the TablePad entry. R1-4 (blocking, fixed): INITIALIZE ... WITH FILLER now resets the stored filler (`BitFiller.Item`, `InitializeBinder.ExpandImplicitFillers`). Residual leads: the Tier-B (REDEFINES / EXTERNAL / BASED / LINKAGE) lanes hold the filler as shared bytes with no item, so WITH FILLER does not reach it there; a REPLACING BOOLEAN sender over an ALIGNED table pad is refused by name.

## Review round 2 (2026-10-23)

R2-1 (blocking, fixed): in an EXTERNAL / BASED record or a REDEFINES area `INITIALIZE ... WITH FILLER` aborted at run time for an ALIGNED bit table (the pad was listed, the class-less filler item had no cursor) and silently left the run tail. `BitLayout.FillersOf` now lists only the positions that have a field (the subject a Tier-B class stores has none, tail and pad alike) and `BitLayout.WindowFillersOf` names each gap of a class-stored group as `BitFiller.GapItem`, an elementary bit item at its `ClassBitOffset`, which `InitializeBinder.ExpandImplicitFillers` receives through the class `ViewCursor` (ZEROES, or the REPLACING BOOLEAN sender to each gap as its own item). Golden `14.9.20-INITIALIZE/pb3564_initialize_with_filler_in_shared_storage` (EXTERNAL, BASED, REDEFINES; the REPLACING arm against an explicit PIC 1(3) / FILLER PIC 1(5) control). R2-3 (lead, fixed): the design, CONFORMANCE and note text now say this. R2-2 (lead) stays: a REPLACING BOOLEAN sender over the record-struct lane pad (one stored string of every gap) is refused by name. Open lead: the tail of a run in a record-struct group that holds the canonical of a Tier-B class is not stored.
