# PB636 — LANDED — a total argument in a partial function's landing

Found 2026-09-05 by the `PB254` implementer (report §"New defects" (B)), whose sweep classified every `IntArg(`
site against its argument rule and found RANDOM's seed TOTAL by the same derivation that moved the two TEST-
validators; not fixed there because the arm sits inside `RenderFloat`, PB253's live subject that day.

## Repro (`<a9d94900 scratch>/PB254/probe6.cob`, `--std 2023`)

```cobol
       >>TURN EC-ARGUMENT-FUNCTION CHECKING ON
       01 BIG PIC 9(19) VALUE 9999999999999999999.
       ...
           COMPUTE R = FUNCTION RANDOM(BIG)
```

```
abnormal run-unit termination: EC-ARGUMENT-FUNCTION (fatal): the intrinsic integer argument 9999999999999999999
is outside the range the function can represent (ISO §15.3)
```

With checking off, the `IntegerArg` landing substitutes 0 for the ARGUMENT (PB254 measured that substitution), so
the program runs the seed-0 sequence without a word.

## The rule

§15.75.3 r2: "it shall be zero or a positive integer" (`OK §15.75.3 2)`) — a SIGN constraint, nothing about
magnitude. §15.75.4 r1: "The returned value is greater than or equal to zero and less than one" (`OK §15.75.4 1)`).
§15.75.4 r3: "This subset shall include the values from 0 through at least 32767" (`OK §15.75.4 3)`) — the subset of
seeds that yield DISTINCT sequences has a floor; a seed outside it is still a legal argument with a defined
(possibly non-distinct) sequence. §15.3 r14 keys EC-ARGUMENT-FUNCTION on "an incorrect value … according to the
rules specified in the function definition", and no rule here makes a large seed incorrect. So a conforming program
may pass any non-negative integer and must get a value in [0, 1), never an abort.

## The mechanism

`src/Cobol.Net.Compiler/CodeGen/Emit/IntrinsicRenderer.cs`, the `"Random" => RuntimeApi.Intrinsic(method,
IntArg(ic, 0))` arm (after PB253 it lives in `FloatBody`), landing through `AsInt` — the PARTIAL-function
narrowing — into `src/Cobol.Net.Runtime/Intrinsics/CobolIntrinsics.Float.cs#Random(long seed)` (`:117`).
PB254's `IntrinsicCarrierAgreementDriftTests` derives the intake width from the runtime body's declared carrier, so
today the pairing is CONSISTENT (a `long` body, a narrow intake) and the guard cannot see that the body's carrier is
the wrong one.

## Fix shape

`Random(Int128 seed)` with a documented deterministic reduction of the seed to the generator's state (the
implementor-defined part §15.75.4 r3 leaves open — say which reduction, in the code and in `docs/CONFORMANCE.md`'s
A.1 row for RANDOM), and the arm takes `IntArgWide`; at that point PB254's guard holds the pairing. Goldens at 2002+:
a 19-digit and a 31-digit seed under armed EC-ARGUMENT-FUNCTION checking each return a value in [0, 1) and the same
value on a second seeded call with the same argument (§15.75.3's restart rule), plus the seed-0 and seed-32767
controls; the sequence-distinctness floor of r3 is pinned separately over the subset. Sweep: every other `IntArg(`
site classified BOUNDED in PB254's table stays as it is; ANNUITY's argument-2 is [[PB637]].

## Landed 2026-09-21 (wave 43C)

Reproduced first on the implementer's own build, exactly as the note describes: `abnormal run-unit termination:
EC-ARGUMENT-FUNCTION (fatal): the intrinsic integer argument 9999999999999999999 is outside the range the
function can represent (ISO §15.3)`. After: `R=0634630`.

THE FIX is the CARRIER, not the arm. PB254 established that the runtime body's declared parameter type IS the
totality claim and that `IntrinsicCarrierAgreementDriftTests` re-derives the arm↔body pairing from the shipped
signatures, so `CobolIntrinsics.Random(long)` became `Random(Int128)` — which made the narrow arm RED until
`FloatBody`'s seeded arm took `IntArgWide`. The reduction to the generator's state is unchanged and already
documented (CONFORMANCE.md DOC-A.1-145): the low 31 bits, `seed AND 0x7FFFFFFF`, the identity on 0..2³¹−1, so
§15.75.4 r3's required 0..32 767 floor stays injective with a wide margin. The row now also states the DOMAIN
(every non-negative integer) rather than only the alias.

WHICH ARM: the SEEDED arm of RANDOM's two-arm `FloatBody` dispatch. The no-argument arm (§15.75.3 r5) renders no
integer and is untouched; the §15.75.3 r2 SIGN rule — the one rule that does make a seed incorrect — still
raises, now pinned at every width by `ANegativeSeed_StillRaises_AtEveryWidth`, which is the complement half a
widening like this is most likely to lose.

Golden: `conformance:2002/pb636_random_total_seed` — armed with `>>TURN EC-ARGUMENT-FUNCTION CHECKING ON` and a
negative-seed ARMED control, then 19-digit / 31-digit / arithmetic-expression seeds against r1's range and r2's
repeat, plus r3's floor. No pseudo-random value is printed: r3 leaves the sequences implementor-defined, so every
expected line is a rule. It sits at 2002 because the WITNESS is not writable below it (§8.3.3.3.2's 19–31-digit
items, and >>TURN); the rule and the behaviour do not differ by edition, which is why there is no per-edition
copy and no `reject-at:` negative — RANDOM is a COBOL-85 function, so there is no edition below its own.
