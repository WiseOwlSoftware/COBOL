## Finding — `expressions` (under-rejects; rows `SR-8.8.2-5`)

**Mechanism.** The boolean shift count is bound as an unrestricted arithmetic expression, so rule 5's integer-operand constraint is never checked

**Repro.** --std 2023: 01 A PIC 1(4) VALUE B"1100". 01 NV PIC 9V9 VALUE 1.5. 01 N PIC 9 VALUE 2. 01 R PIC 1(4). COMPUTE R = A B-SHIFT-L 1.5. / COMPUTE R = A B-SHIFT-L NV. / COMPUTE R = A B-SHIFT-L 1 + 1. / COMPUTE R = A B-SHIFT-L FUNCTION SQRT(4). / COMPUTE R = A B-SHIFT-L N * 1. (out/probe/expressions/N03 N04 N05 N11 N20)

**Expected from the spec.** §8.8.2 rule 5: 'The second operand shall be an integer operand'; §5.5 2) makes that an integer literal, an integer intrinsic function, or a fixed-point data item with no digit positions right of the radix point; §8.4.3.2.3 SR11 bars a numeric function even if it yields an integer; Table 4 allows only an identifier or literal after a shift operator (never an arithmetic operator). Each statement above shall be rejected at compile time.

**Observed / reasoning.** All five compile clean and run (R=1000, 1000, 0000, 0000, 0000 - the count silently truncated or evaluated). ConditionBinder.BindBoolShiftSuffix: `return new BoundBoolShift(operand, kind, host.Expr.BindExpr(suf.arithmeticExpression()));` - no integer/operand-shape screen; the grammar's booleanShiftSuffix parses a full arithmeticExpression by the 'permissive-superset' doctrine, which assumes the binder narrows it, and it does not. The compile-time evaluator's twin rejects a fractional count (CompileTimeBooleanCceTests.Boolean_FractionalShiftCount_Rejected), so the rule is enforced on one arm only.

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#BindBoolShiftSuffix (line 60-70); src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4#booleanShiftSuffix

### `SR-8.8.2-2` — PARTIAL (adjudicator + refuter record, verbatim)

Rule 2 (cite.py --check 8.8.2 "A boolean expression where the preceding operator is a boolean shift operator shall end with one of the following" -> OK §8.8.2 2)). The tiers end every booleanXorTerm/booleanAndTerm with a booleanFactor or shift suffix; a trailing operator cannot complete. PROBES: `A B-AND.` -> COBOL0001 (N13), `(A B-AND)` -> COBOL0001 (T01), `A B-SHIFT-L 1 B-SHIFT-L.` -> COBOL0001 (N19), `(A B-SHIFT-L) B-AND B` -> COBOL0001 (T03), shift followed by a boolean literal B"1" -> COBOL0001 (N17). The shift count admitting a full arithmetic expression (e.g. `1 + 1`) is the rule-5 integer-operand defect, not an ending-symbol defect. No spec-derived negative test -> test-ref empty. || REFUTED: PARTIAL — booleanShiftSuffix takes a full arithmeticExpression, so `A B-SHIFT-L 1 + 1` compiles clean and runs. That expression's final operator is '+', not a boolean shift operator, so rule 2's 'Otherwise' branch applies: the expression shall end with ')', a boolean identifier or a boolean literal, and it ends with the integer literal 1. Rule 2 is therefore violated and nothing diagnoses it. The adjudicator filed this under rule 5 only, but it is equally a rule-2 escape; the grammar comment calls the arithmeticExpression 'permissive-superset' with no bind-time screen behind it for this shape. The trailing-operator halves hold (A B-AND., A B-SHIFT-L. rejected).

## What the fixer owes

Narrow booleanShiftSuffix to an integer operand (integer literal / integer data item / integer function) per SR5 — the grammar, not a screen — so SR2's 'shall end with' falls out; negative goldens for `1 + 1` and `1.5`.
