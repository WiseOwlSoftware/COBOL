# PB5912 ruling

The note asks two things, ruled separately below.

## Part 1: separately compiled describers, option (a) or (b)

Rule:
- `OK  §1985:I.1.6  (1.6 DEFINITION OF A CONFORMING SOURCE PROGRAM)  the text is in the clause`: "The results of violating the formats or rules of Standard COBOL are undefined unless otherwise specified in this standard"
- The rules in question are constraints on the run unit with no stated consequence. Each was checked:
  `OK  §1985:VII.3.6.3 GR4` ("all LABEL RECORDS clauses in the run unit"), `OK  §1985:VII.3.8.4 GR2` ("all file description
  entries in the run unit which are associated with that file connector must specify the same values"), `OK  §1985:VII.3.7.4
  GR11a`, `OK  §1985:VII.3.7.4 GR11c`, `OK  §1985:VII.3.9.4 GR2` ("The implementor will specify the consistency rules"),
  `OK  §1985:X.4.5.4 GR4`.

Evidence: code read. `ExternalFileConnectorRules.Check` and `CheckFileDescriptions`
(`src/WiseOwl.Cobol.Compiler/Binding/ExternalFileConnectorRules.cs`) compare the describers within one compilation group.
`ExternalTable.Describe` (`src/WiseOwl.Cobol.Runtime/Control/ExternalTable.cs`) compares describers registered at activation
only when `gate != ExternalChecks.None`. The gate is `ActivatorExternalMask & selfMask`, folded from `EC-EXTERNAL-*` enablement
(`CheckingFold.ExternalMaskAt`). At 85 nothing enables an EC, so the gate is always zero. I did not probe two separately
compiled programs; the zero gate at 85 follows from the code path read above.

Reasoning: The 1985 text does not say what happens when two programs of one run unit describe an external file connector
differently. These general rules say what the run unit "must have", and none of them states a consequence. §1985:I.1.6 covers
that case: the result is undefined. No 1985 rule requires an implementation to detect the violation, at compile time or at run
time. That reading agrees with the 2026-11-15 adjudication of the row `1985-GR-VII.3.7.4-11` (kb/Work
PB5683/2026-11-15-rulings-code-reads-batch-6.md, item 8): "GR11 binds the run unit; 1985 requires no detection of a
violation." Checking within a compilation group is therefore a quality choice the compiler made (PB5300, PB5638), not a duty.
Since the result is undefined, the text leaves no implementor-defined behavior for CLAUDE.md rule 1's precedence to settle.

Choose (a). Option (b) would add an 85-only activation check that bypasses EC enablement. It would need its own outcome for a
mismatch, and the 1985 text gives no outcome for it to implement. At 2023 the same cross-element check runs only when the user
enables EC-EXTERNAL-FILE-MISMATCH, so (b) would make 85 the one edition that checks by default. That adds a second gating rule
to the descriptor path and buys nothing the text asks for. Option (a) states the facts: the 1985 FD and file control
agreement rules are checked at compile time across the programs of one compilation group. A run unit whose separately
compiled describers disagree has undefined results (§1985:I.1.6), and WiseOwl COBOL does not detect it at 85. The entry goes
in `docs/conformance/` (one file, for example `3/D-EXTERNAL-FD-85.md`), naming the rows of `FileDescriptionIdentity` and the
file control rows of `FileEntryIdentity`. Those are compared at activation under the same zero gate, so the limit covers both.
This is Claude's to decide under the delegation; it needs no owner decision.

Unprobed and named, not ruled: what the run time does when two separately compiled programs at 85 describe one EXTERNAL
record or file with different record lengths (§1985:X.4.5.4 GR2, §1985:VII.3.8.4 GR2). The result is undefined, but a crash
from an out-of-range storage access would still be worth a probe before the limit is written down as harmless.

## Part 2: the side question, a LINAGE data-name of an EXTERNAL file that names no external data item, at 85

Rule: `OK  §1985:VII.3.7.4 GR11c  (║3.7.4 General Rules║)  the text is in GR11c`: "The same corresponding external data items referenced by data-name-1"
Siblings, each checked: `OK  §1985:VII.2.7.4 GR6` ("If data-name-1 is specified, it must reference an external data item"),
`OK  §1985:VIII.2.4.4 GR8` ("data-name-1 must reference an external data item").

Evidence (each `--std 85`, runs under `E:/COBOL-coord/scratch/rulings-1985-open/s3/runs/`):
- `s3/lin1b.cob` (`lin1b-001`): one program, `FD PFILE IS EXTERNAL LINAGE IS LN LINES` with LN a non-external WORKING-STORAGE item.
  Exit 0, `DONE`. Expected: COBOL1624.
- `s3/lin2b.cob` (`lin2b-001`): two programs in one source, each describing the external PFILE, one with LINAGE IS LN and the
  other with LINAGE IS LM, both non-external. Exit 0, `DONE`, no diagnostic. Expected: COBOL1624 at each data-name.
  The same source at `--std 2023` (`lin2b-002`) is refused: `error COBOL1624: external file 'PFILE': the LINAGE data item 'LN'
  shall be an external data item (ISO §2023:14.8.4.2; Annex E.2 item 9)`, and again for LM.
- `s3/pad1b.cob` (`pad1b-001`), the sibling: `PADDING CHARACTER IS PC` with PC non-external on an external file. Exit 65,
  `error COBOL1624: external file 'PFILE': the PADDING CHARACTER data item 'PC' shall be an external data item (ISO §1985:VII.2.7.4 GR6)`.

Mechanism: `src/WiseOwl.Cobol.Compiler/Binding/ExternalFileConnectorRules.cs#Check`. The LINAGE externality screen is
`if (is2023 && f.Linage is { } lin) ... NotExternal(..., "LINAGE", ..., newIn2023, "ISO §2023:14.8.4.2; Annex E.2 item 9")`, so
it is gated to 2023 on the premise that the requirement is new in 2023. At 85,
`src/WiseOwl.Cobol.Compiler/Binding/FileDescriptionIdentity.cs#LinageValue` gives such an operand the value `Undecided` ("~"),
and `OperandsAgree` treats `Undecided` as agreeing with anything. So nothing at 85 checks the operand, either for being
external or for agreeing with the other describer. lin2b's two describers, paging one external file by two different private
counters, compile clean.

Reasoning: GR11c requires the data-names of every file description entry for the connector to reference "external data
items", the same corresponding ones in each entry. A data-name naming a non-external item cannot be one of those items, with
one describer or with several. For LINAGE, then, the requirement is not new in 2023: 85 states it at level 2, so the premise of
the `is2023` gate is wrong for 85. As Part 1 says, the 1985 text alone requires no detection. The compiler, however, already
enforces at 85 every other part of this rule family that it can see: PADDING CHARACTER's external item (GR6), RELATIVE KEY's
(GR8), GR11a, GR11b, and GR11c for two different external items (PB5638). This one gap is a hole in that mechanism, one arm of
the same dispatch left behind an edition gate whose premise does not hold at 85. That is a defect by CLAUDE.md rule 4 (every
bug is a pattern), with the harm under_rejects: a program that violates GR11c compiles without a word, and in lin2b two
programs share one connector's page and LINAGE-COUNTER while sizing the page by different items. It is not a wrong answer,
because the result of a violating run unit is undefined. Severity: minor. No NIST program combines EXTERNAL with a LINAGE
data-name (searched in `tests/nist/extracted/newcob.val`), so the fix refuses no NIST source.

Fix shape: in `ExternalFileConnectorRules.Check`, make the LINAGE operand screen depend on the edition's own text instead of
`is2023`. At 85 it runs with `EditionSeverity.Error` and cites `§1985:VII.3.7.4 GR11c`, built with `edition.Edition.Cite(...)`
the way the RELATIVE KEY arm is. At 2023 it keeps its current citation and the Removed policy. 2002 is to be judged on the
2002 text (not ruled here). After this, `FileDescriptionIdentity`'s `Undecided` for a non-external data-name is never reached
at 85 without a COBOL1624 beside it.
Goldens at `--std 85`, beside the PB5638 witnesses in `conformance-suite/cases/VII.3.7@1985-LINAGE-CLAUSE/`:
(1) a lone describer with a non-external LINAGE data-name (lin1b's shape), refused with COBOL1624 citing §1985:VII.3.7.4 GR11c;
(2) two describers with different non-external data-names (lin2b's shape), refused at each. The existing
`pb5638-external-linage-agree` remains the accepted case. File the side question as a defect note of its own, since PB5912 is
a decision.
