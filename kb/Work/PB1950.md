# PB1950 — goldens that only compile under the harness's reference format

Filed by the train-1011 lander from wave 1011 group B2's report (`w1011b2-PB1087-report.md`, "New defects" item 2:
"compile red under cobol.exe run from their directory but are green in the harness … suspect CLI format
auto-detection"). The implementer saw the same on the predecessor's binary, so this train did not cause it.

## Re-probe (lander, train-1011 build)

`cd tests/conformance/2002 && cobol typedef_same_as.cob` (and with `--std=2002`) →
`typedef_same_as.cob(40,5): error COBOLNET1639: 'CUST-NAME OF INNER-RE' does not uniquely identify a data item`.
Line 40 is 73 characters long (`DISPLAY "N=[" CUST-ID OF INNER-REC "][" CUST-NAME OF INNER-REC`), so under the
CLI's default `--source-format fixed` (ISO §7.3 reference format) its last character falls in the
program-identification area and `INNER-REC` loses its `C`. The harness compiles the file green, so it does not
compile it in fixed form (or does not truncate at column 72). `pb646_national_form_numeric.cob` gives COBOL0001
the same way; not yet analysed.

## Why it matters

Silent in both directions: the golden does not mean, in the CLI's default format, what the harness checks, and a
harness that does not apply column 72 would also miss a real compiler defect in fixed-form truncation. Decide which
format the conformance harness is meant to compile in (the CLI default is fixed), make it say so, and fix every
golden that relies on the other one; add a drift test that a corpus program's lines fit the format it is compiled
in.

## Code sites

The harness's compile options in `tests/Cobol.Net.Tests.Conformance` (the reference-format argument it passes);
`tests/conformance/2002/typedef_same_as.cob` line 40; `tests/conformance/*/pb646_national_form_numeric.cob`.
