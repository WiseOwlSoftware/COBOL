# PB2806 — the fix-lane planner re-planned another session's recorded wave

**Found by:** the loop's wave unit of 2026-10-08 16:24 PDT, reading `plan_wave.py --from-budget`'s table against the
dispatch ledger (`E:\COBOL-coord\inflight-groups.json`). The Mythos session had named both hazards in its 15:07
question to the operator (mailbox `20261008-150740-mythos-question-…`): "(1) the fix-lane planner ignores the dispatch
ledger … (2) next_wave() does not read the ledger".

## What happened

At 15:07 PDT the Mythos session planned wave 1045 (8 groups: PB1941 +4, PB2097, PB2497, PB2689 +1, PB2074 +2,
PB2553 +1, PB2697 +1, PB1951 +1), recorded it in the dispatch ledger and did not launch it, waiting for the
operator's GO, CHANGE or DECLINE. At 16:24 the loop's wave unit ran `plan_wave.py --from-budget --borrow-days 3` and
got wave 1044 with the same notes in seven of its eight groups (A = 1045 A, B ⊃ PB2097, C = 1045 C, F = 1045 E,
G = 1045 F, H = 1045 G, and D on 1045 D's `IndexedConnector.cs`). Launching it would have dispatched the same work
twice on two accounts the moment the operator said GO. The unit released wave 1044 (`--release 1044`), launched
nothing, and fixed the planner (this note).

## Root cause

`plan_wave.main()` built `busy = inflight_file_sets(...)` (whose source 3 is the dispatch ledger) only inside
`if a.cluster:`, so the fix lane's plan read neither the ledger nor any other session's dispatch. Inside the loop the
gap never showed: a wave unit waits for its Workflow to return, so every dispatched note has a report before the next
wave unit plans, and step 1 (awaiting landing) or step 2 (finishers) governs it. A second planner (the Mythos session,
or any attended hand dispatch) breaks that serialization. `next_wave()` had the same blind spot: it counted reports
and DEVLOG lines, so with 1044 landed the loop would number its next wave 1045 and overwrite Mythos's
`wf-args-w1045.json` and `msg-w1045-*.txt`.

## Fix (both lanes, one rule)

- `held_by_dispatch(coord_dir, reports, terminal)`: every open note a ledger group names (hand entries within
  `HAND_TTL_SECONDS`) unless a report written at or after the group's `at` names one of its notes. Such a report
  answers the dispatch and steps 1 and 2 govern from then on, so a SPLIT wave's finisher is still planned.
- `plan(..., held=)`: a held note is taken and waits, naming its dispatch and the `--release` remedy; a stale entry
  (a dispatch that died with no report) is therefore visible in the plan's `waiting` line instead of silently
  re-planned.
- `next_wave(repo, reports, coord_dir)`: the ledger's numeric waves count as taken.
- `test_plan_wave.py` 6c (held: unanswered only, terminal never, expired hand entry never; plan() leaves a held note
  out and keeps its cluster's other notes) and the PB2562 block (a dispatched wave with no report holds its number);
  check 8's fix-lane golden is unchanged (119/119).
- `DESIGN-orchestrator-loop.md` section 9 step 1 and the `--wave` default.

Verified live: the fixed planner's dry run against the real ledger lists every wave-1045 note as `held by dispatch
w1045<letter>` and plans eight other groups (PB2692, PB2761, PB2101, PB1928, PB2588, PB2739, PB1688, PB2463 leads).

## Not done here

A note-level hold does not stop a FILE-level overlap with another session's dispatch (the dry run's PB2101 group is
on `ProgramTable.cs`, which wave 1045 B holds for PB2097). The landing check still stops the later of the two
landings; whether the fix lane should apply the file-set partition against other sessions' dispatches is kb/Work
PB2807.
