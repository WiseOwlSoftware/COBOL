# PB2614 — a read-only Workflow is recorded as in-flight write work

Filed by the train 1039b lander, 2026-10-08, from the orchestrator's pre-dispatch landing check of that train.

## What happened

The R2 architecture-review Workflow started 2026-10-08 00:32:42 PDT (cobol-reviewer agents, all READ-ONLY by hook;
inputs under `E:\COBOL-coord\scratch\r2-8be230068\`). `scripts/hooks/dispatch_guard.py` admitted it and recorded it
in the dispatch ledger, so it sat in `E:\COBOL-coord\inflight-groups.json` as a `hand` group of 66 notes (PB160,
PB175, PB372, ...) and 800 files. `scripts/orchestrator/landing_check.py` treats every ledger group as in-flight WRITE
work, so it STOPS any fix-lane train whose earliest dispatch is later than 00:32:42 and whose `src/` or `scripts/`
files meet that set: `landing_check.py --rev w1039y-goto-conditional` and `--rev w1039x-battery89` each stopped on it
alone. A review fleet writes nothing in any working tree, so it can never conflict with a landing.

The operator released the finished hand entries from `inflight-groups.json` by hand, the R2 review's record among
them (the lander found it gone at 02:46 PDT; the file was last written 02:35), so trains landing now are not stopped
by it. That removal is a manual workaround; this note is
the structural fix, and the next read-only Workflow will be recorded the same way until it lands.

## Mechanism

`scripts/hooks/dispatch_guard.py#record_hand_dispatch` returns early only for an `Agent` call whose `subagent_type`
is in `READ_ONLY_ROLES` (`dispatch_guard.py:55`). The Workflow arm (`record_hand_dispatch(args, "", "Workflow")`,
`dispatch_guard.py:165`) passes no role at all, so every Workflow is recorded, whatever its agents can do, with every
`PB` id its JSON input (script, args, the files they name) mentions. Nothing ends a hand group when its run ends, so
a recorded Workflow stays "in flight" until someone removes it.

## Fix shape

- Record a Workflow only when one of its agents' roles can WRITE: read the `agentType`s its script (or its args'
  groups) dispatches and skip the recording when every one is in `READ_ONLY_ROLES` (the guard already knows the set
  for Agent calls; one set, both arms).
- Expire a hand group when its run ends (its Workflow's completion, or a TTL for a hand Agent dispatch), so the
  ledger never holds a finished run.
- Self-test arms in `scripts/hooks/test_dispatch_guard.py`: a Workflow whose agents are all `cobol-reviewer` is not
  recorded; one with a `cobol-implementer` is; a finished hand group no longer binds a branch in
  `landing_check.py --self-test`.

## Sibling arm: a lander's Agent dispatch (train 1039b push-main, 2026-10-08 04:50 PDT)

The same recording also captures every `cobol-lander` Agent call. `cobol-lander` is not in `READ_ONLY_ROLES`, so
`record_hand_dispatch(args, role)` reads the PB ids of every file its prompt names (the lander-train brief, the resume
brief, STATUS.md, the train manifest). It recorded `cobol-lander: Land train 1039b` (02:27) as a hand group of 86 notes
and 873 files, and each resume lander (02:59, 03:25) as 14 notes and 443 files. A lander carries no work of its own:
its members are in the ledger and the train manifest, and its own worktree's diff is source 1 of
`plan_wave.inflight_file_sets`. Its entry therefore only misattributes notes, and `landing_check.py` bound three LATER
hand-dispatched branches (`w1040w-gn1-close`, `w1040u-recursion-depth`, `w1040s-a1-116-118`) to it, dated them 02:27
and stopped the train that the lander was landing (PB2609's 04:50 recurrence). Fix shape, added to the one above: a
`cobol-lander` dispatch is never recorded (one set of roles whose dispatch carries no recordable work of its own,
shared by the Agent and Workflow arms), with a `test_dispatch_guard.py` arm for a lander prompt that names a manifest.
