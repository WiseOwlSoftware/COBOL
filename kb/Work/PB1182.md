# PB1182 — LANDED (wave 1011 A, 2026-10-04)

## Landing

`StringUnstringBinder.cs#Sr8Offence` (STRING SR8) and `#UnstringReceiverAllowed` + the receiver branch in `#BindUnstring` (SR4) own these screens; `PicInfo.cs#HasPScaling` / `TrailingPScaling` / `LeadingPScaling` is the ONE reader of "this picture has P" (REUSE; `OperandText.PExpand` reads it too) — a `V` alone has a non-zero Scale and no P. Trap: the receiver screen was guarded by `!target.Item.IsGroup`, so a group-shaped refusal (bit group, strongly-typed group) can only be added in the guard, and `StrUnstrSender` is shared by four positions, so a constant-name refusal belongs in `BindUnstring` (identifier-1 only), not in the funnel.

Re-probed first on the wave-1011 Debug build: `STRING N1 …` over `PIC 9V9`, a `PIC 99P` sender, `UNSTRING … INTO` a `PIC 99P` / `PIC PP99` receiver, a GROUP-USAGE BIT group receiver and a `CONSTANT AS` sender all compiled clean and ran. All three arms are fixed at their root in `StringUnstringBinder`:
- **STRING SR8** — `Sr8Offence` (an elementary numeric identifier-1 / identifier-2 must be an integer without P), asked at the sender and the delimiter; the P positions are read from the new `PicInfo.TrailingPScaling` / `LeadingPScaling` / `HasPScaling`, which `OperandText.PExpand` (the sending image of a P-scaled item) now reads too — one definition of "this picture has P".
- **UNSTRING SR4** — `UnstringReceiverAllowed` carries `HasPScaling: false` (a V alone is no P, so `PIC 9V9` stays legal), and the receiver screen no longer exempts every group: a BIT group and — found in the same sweep, the receiver-side twin of the sender and delimiter screens PB244 added — a STRONGLY-TYPED group (category its type-name, §8.5.2.1) are refused (COBOLNET1626).
- **UNSTRING identifier-1 as a constant-name** — `BindUnstring` refuses it (COBOLNET1651) because the format specifies identifier-1, not a literal (§13.10.3 SR2), while `StrUnstrSender` keeps substituting the literal at STRING's sender and both delimiters.
Also found and fixed in the same file (I9): `GetText()` in every STRING/UNSTRING diagnostic replaced by `DataBinder.WrittenText` (kb/Work PB1313's class; `ALL ALL ","` no longer prints as `ALLALL","`), and a misattached XML summary. Witnesses: `StringUnstringOperandScreenTests`, negative `pb1182-string-non-integer-sender`, positive goldens `85/pb1181_string_unstring_screen_controls` and `2002/pb1182_constant_name_literal_positions`.

## Finding — `string-statement` (under-rejects; rows `SR-14.9.43.3-8`)

**Mechanism.** M4 - SR8's integer/no-P requirement on numeric identifier-1/identifier-2 is unenforced (only SR7's identifier-4 is checked with StrUnstrIsInteger)

**Repro.** 01 N1 PIC 9V9 VALUE 1.2. 01 OUT1 PIC X(10) VALUE SPACES.  STRING N1 DELIMITED BY SIZE INTO OUT1  (probe sr8a.cob, which prints [12        ]); also sr8b.cob: a `PIC 99P` sender and `STRING "AB05CD" DELIMITED BY D1` with D1 PIC 9V9. All compile without errors at --std 2023.

**Expected from the spec.** §14.9.43.3 SR8: "Where identifier-1 or identifier-2 is an elementary numeric data item, it shall be described as an integer without the symbol 'P' in its picture character-string." The expected result is a compile-time rejection (the COBOLNET1651 STRING/UNSTRING operand-rule family) for a 9V9 or 99P identifier-1 or identifier-2.

**Observed / reasoning.** All three programs compile without errors and run. The sender screens in BindString are Sr1Offence (usage and numeric-literal), SR2, and the all-national class mix. None of them reads PicInfo.Scale, although StrUnstrIsInteger (Category Numeric, not float, Scale 0) already expresses exactly this predicate for SR7. The header of the positive-control golden conformance:85/pb664_string_operand_screen quotes SR8 ("admitted by SR1 and constrained by SR8, never refused"), but no negative exists and the constraint was never implemented.

## Finding — `unstring-statement-p1` (under-rejects; rows `SR-14.9.48.3-4`)

**Mechanism.** UnstringReceiverAllowed tests only category/usage, never the P-scaling half of SR4, and BindUnstring exempts EVERY group from the screen — so a P-scaled numeric receiver and a GROUP-USAGE BIT (boolean) group are admitted as UNSTRING INTO targets

**Repro.** 01 S PIC X(8) VALUE "12,34". 01 N PIC 99P. 01 M PIC 9(4).  UNSTRING S DELIMITED BY "," INTO N M.  -> compiles and runs N=[01] M=[0034] at --std 85/2002/2014/2023 (also PIC PP99 -> N=[00]). And: 01 G GROUP-USAGE BIT. 05 G1 PIC 1(2).  UNSTRING S DELIMITED BY "," INTO G M. -> compiles and runs at --std 2002/2014/2023.

**Expected from the spec.** Compile-time rejection for both: §14.9.48.3 4) "Numeric items shall not be specified with the symbol 'P' in their picture character-string", and the first sentence admits only usage display (alphabetic/alphanumeric/numeric) or usage national (national/numeric); a bit group's "class and category are boolean" (§13.18.29.4 1) a)).

**Observed / reasoning.** UnstringReceiverAllowed's numeric arm is `{ Category: Numeric, IsFloat: false, Usage: Display or National }` with no Scale / P test (StrUnstrIsInteger's `Scale: 0` shows the encoding is available); the call site is guarded by `!target.Item.IsGroup`, so a bit group never reaches the screen — Sr2OffendingCategory already knows the bit-group case (`GroupUsage.Bit`) for identifier-5, the receiver arm does not (two-arm shape). All COMP/packed/float/edited/boolean elementary receivers are correctly rejected (COBOLNET1626).

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/StringUnstringBinder.cs#UnstringReceiverAllowed; src/Cobol.Net.Compiler/Binding/Procedure/Verbs/StringUnstringBinder.cs#BindUnstring (INTO loop group exemption)

## Refuter evidence — row `SR-14.9.48.3-8` (PARTIAL)

PARTIAL — SR8 designates the DATA ITEM referenced by identifier-1 as the sending operand; the format writes identifier-1 (no literal). A constant-name is not a data item and, per §13.10.3 SR2 (cite.py OK), may be used only where a format specifies a LITERAL, so it is not admissible as identifier-1. The pinned compiler accepts `UNSTRING K ...` with `01 K CONSTANT AS "XY,ZW"` at --std 2002/2014/2023 and runs it (A=[XY  ] B=[ZW  ]) - the literal-equivalent slips through the very funnel the adjudicator cited as refusing literals (ufmtlitsnd). Verified halves: function-identifier sender (da4 golden, u8func), ref-mod sender (r8refmod A=[CD] B=[EF]), subscripted sender (r8sub), sender unchanged after the statement (r8unch), condition-name sender rejected (r8cond, though with a misleading COBOLNET1639 'not defined' message). The receiving side already refuses constant-names (COBOLNET1548), so this is the two-arm shape: StrUnstrSender/ScreenedField screens index-names but not constant-names. The test-ref da4_function_sending_operand pins only the function-identifier arm.

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/StringUnstringBinder.cs#BindUnstring; src/Cobol.Net.Compiler/Binding/Procedure/Verbs/StringUnstringBinder.cs#StrUnstrSender; src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4#strUnstrSender
