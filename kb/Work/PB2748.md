**Rule it breaks:** ISO 14.9.27.4 GR25 ('If the execution of the OPEN statement is unsuccessful, the file is not affected') and 9.1.15 (the sharing mode applies 'throughout the duration of this OPEN', i.e. the SUCCESSFUL one that is still in force); 14.9.51.4 GR12 (a successful WRITE releases its record to the operating environment). The registry's own PB321 comment (FileRegistry.cs:1065-1068) states the rule for st.Open - gate on the status, because a '41' re-OPEN must not re-register the connector under the failed request's mode and sharing - but the three connector writes above c.Open(mode) were never put behind it.

**Scenario:** SELECT F ASSIGN TO "log.dat" (no SHARING clause). OPEN EXTEND F SHARING WITH ALL OTHER: HostSharing = AllOther, the writer's handle admits other writers, and SequentialConnector.ReleaseRecord flushes every WRITE because FileLockPosture.AdmitsAnotherWriter(HostShare) is true, so a second run unit appending to log.dat sees whole records. The program then executes a plain OPEN EXTEND F (a logic error the program detects through FILE STATUS '41' and continues). SharedOpenAttempt computes sharing = null clause ?? ImplementorDefaultSharing(Extend) = NoOther, finds no conflicting connector of THIS run unit in st.Open (the other appender is another process), then runs c.AssociatePhysical(...) and c.HostSharing = NoOther, and only then c.Open(mode) answers '41'. F stays open on its AllOther handle but HostShare now reads NoOther, so ReleaseRecord stops flushing: every later WRITE sits in the StreamWriter buffer, the other run unit no longer sees released records (GR12), and a buffer flush can land mid-record between the other process's appends - the split-record failure kb/Work PB753 fixed, re-armed by an unsuccessful statement. The same path flips SequentialConnector.ReversedRequested (FileRegistry.cs:1024) and, through OpenShared's RegisterSharing, can turn _locksRecords on for a connector whose release-ordinal base was never seeded by its OpenCore.
