# PB3426 — the tier-2 design memos: the sequential transaction journal (2.2.2) and the sequential frame index (2.2.3)

Both sections are in `docs/rearchitecture/DESIGN-runtime-library.md`, between 2.2.1 (the keyed store engine) and 2.3, and
each is the design its implementer follows (CLAUDE.md rule 2): PB3340 implements 2.2.2 after PB3337 and PB3338, PB3350
implements 2.2.3 in the campaign wave that plans it. Every citation was checked with `cite.py --check` (26 of 26 OK).

## 2.2.2 — a SEQUENTIAL file under APPLY COMMIT (PB3340)

- **Derived from the whole list of a sequential file's changes** (an append, an in-place same-size REWRITE, an OPEN OUTPUT's
  truncation, a DELETE FILE), the state at the last COMMIT is three things: the COMMITTED LENGTH L (a rollback truncates to
  it, undoing every append of any framing), the BEFORE-IMAGES of the rewritten ordinals (the first image only), and ONE
  BEFORE FILE for an OPEN OUTPUT or DELETE FILE (renamed aside, O(1); restored by rename when F is absent and by copy when a
  handle holds F). A rollback restores the before file, re-applies the images, truncates to L — idempotent in every order.
- **The transaction holds the END of the file** (§9.1.16's "circumstances other than a locked logical record"): a sequential
  record's identity is its ordinal, so the only rollback that keeps every other connector's identities true is a truncation,
  and a truncation is an undo only while no other connector's record lies past L — another connector's WRITE answers '51'
  (RETRY applies, §14.9.51.4 GR16) while the transaction lives. The rewritten ordinals are held too; READ locks stay region
  locks (2.2.1.10's split); the lock test reads the journal and probes the owner's liveness byte AT the test (R4-1).
- **The journal is a transient file in the file's `.wolk-*` lock directory** (`txn-<id>.journal`, `txn-<id>.before`): the
  format is headerless by design (2.2's interchange property), memory-only undo cannot roll back a killed run unit
  (§9.1.18.5, PB3330's bar), and the lock directory is the one place beside a file this runtime already owns with measured
  race rules. Four write-ahead rules (R1 header before the first change, R2 image before the overwrite, R3 an append needs
  no entry, R4 the liveness byte for the transaction's life), each with a drift test. ONE kept handle under commit control
  carries the §9.1.15 file lock past CLOSE (§14.9.6.4 GR9) and the liveness byte (`SHARING WITH NO OTHER` admits no second
  handle of the process; a byte cannot move between handles without a gap); a covered connector with no SHARING clause is
  `NO OTHER` for every open mode (a determination).
- **COMMIT** = F synced, the journal's decision byte `C` written and synced (the one durable write), the retirement;
  2.2.1.10's three regions, reversal and UNACKNOWLEDGED mark apply unchanged, as does its "what the program is told".
  **ROLLBACK** = the idempotent sequence under `StoreMutexByte` (the sequential organization's first use of the mutex, for
  the rollback and the entry step only). **The dead-owner step** at every writable OPEN (one directory probe, the price of
  §9.1.18.5 for a file not under APPLY COMMIT) and per changing statement under `ALL OTHER` only.
- **LINE SEQUENTIAL and the print stream are COVERED** by the same byte-ranged journal (the explicit decision PB3340 asked
  for; `docs/CONFORMANCE.md`'s commit row states it when PB3340 lands).
- **The simulator from round one** (owner 2026-10-17): `HostFile`'s roles become the run unit's `IHostMedium` (production:
  today's static roles; test: a medium that logs, refuses, dies and loses unsynced writes), and 2.2.2.12 is the table of
  crash points and interleavings a test executes, each with its expected state.
- **One owner decision is open, asked in PB3340:** kb/Work PB802 (2026-09-07, "no sidecar of any type") refused the
  fixed-file-attribute catalog; the journal is a different thing (transient, consumed by the next entry, describing no
  attribute of F, F byte-identical to an uncommitted-free file), but the words cover it until the owner says otherwise.
  2.2.2.11 states the memory-only alternative and exactly what it loses (a killed run unit's uncommitted sequential changes
  stay in the file for ever; other run units cannot see a dead owner's holdings), so the owner decides with it in view.

## 2.2.3 — the sequential frame index (PB3350)

- ONE walk (`ReadStreamFrame` over `StreamMedium`), two products: `CountFrames` returns a count and stores nothing
  (`CountRecords`' VARYING arm, the OPEN EXTEND base, the REVERSED count); `FrameIndex` holds one checkpoint per S = 4096
  frames plus a window of at most S exact starts for the span being read backward — memory O(records / S + S) (under 2 MB
  per billion records), a single backward READ at most S head reads, a whole-file backward pass O(records) head reads (the
  same order as today's one walk). Built for free by the forward walk (`NextFrame` passes every start) and by one counting
  walk for a target beyond the walked region (OPEN REVERSED pays one pass instead of two). `SeekToRecord` stays the one
  reposition (PB352). Rejected: a trailing length word (a format change every reader of the stream framing inherits),
  walking from 0 per step (a quadratic backward pass), the lazy whole index (today's defect).
- Witnesses: a structural drift test (no per-frame storage in the count, the index bounded as stated, over a 2^20-frame
  file) and the existing GR21 and REVERSED goldens byte-identical.
