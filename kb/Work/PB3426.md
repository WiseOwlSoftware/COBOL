## 2.2.2 — a SEQUENTIAL file under APPLY COMMIT (PB3340)

Corrected on 2026-10-19 after the branch review's two rounds (below); the text as it stands is the one the model holds.

- **Derived from the whole list of a sequential file's changes** (an append, an in-place same-size REWRITE, an OPEN OUTPUT's
  truncation, a DELETE FILE, and a CREATION — §14.9.27.4 GR18 for OPEN OUTPUT of an absent file, GR17 for OPEN EXTEND or I-O
  of an absent OPTIONAL file) and from the ORDER they run in: a transaction has two phases. BASE: the committed file with
  appends past L and in-place rewrites below it, undone by the first images and a truncation to L. REPLACED: after the first
  OPEN OUTPUT of an existing file or DELETE FILE (the capture: F COPIED whole to the before file), or from the start when the
  file was absent (no before file), every byte is the transaction's own, NOTHING later is journaled, and the rollback
  restores the before file (then the base phase's images and the truncation) or REMOVES the file. **L is read at the
  transaction's FIRST APPEND, never at its begin** (round 2's R2-1): at an append no other transaction lives, so the length
  then is the committed one; at the begin it may count another transaction's uncommitted appends, present or in flight. A
  transaction that never appended has no L and truncates nothing.
- **The transaction holds the END of the file** (§9.1.16's "circumstances other than a locked logical record"): a sequential
  record's identity is its ordinal, so the only rollback that keeps every other connector's identities true is a truncation,
  and every live transaction's rollback truncates to its own L — so every live transaction holds the END (another
  connector's WRITE answers '51', RETRY applies, §14.9.51.4 GR16), the rewritten ordinals, and the whole file once REPLACED
  ('61' to every other writable OPEN). READ locks stay region locks (2.2.1.10's split); the lock test reads the holdings
  from the live transaction's RECORD and probes its HOLDER at the test (R4-1).
- **Three transient files per transaction in the file's `.wolk-*` lock directory:** `txn-<id>.live`, the HOLDER — a
  `SidecarLockFiles` holder on every host, its exclusive advisory lock the liveness (a byte of F's region cannot be it: F
  may be removed by a DELETE FILE or not yet exist); `txn-<id>.journal`, the RECORD — header (START `P` or `A`), records
  `L` (the length at the first append), `R` (image), `K` (capture), `D` (decision `C`, `O`, `R`), each CRC-32, a torn tail
  ending the records; and
  `txn-<id>.before`. The ENTRY MUTEX (`EntryMutexByte`, a new byte of 2.2.1.8's map, through `SidecarRegionLocks` on every
  host, which needs no handle on F) guards every writable OPEN, DELETE FILE, first change, capture and rollback. ONE kept
  handle under commit control carries the §9.1.15 file lock past CLOSE (§14.9.6.4 GR9) and is the data handle (the capture
  is a COPY: a handle follows a renamed file, and Windows refuses the rename); a DELETE FILE closes it, a creation opens it.
  Five write-ahead rules: R1 header synced (and the directory) before the first change; R2 image before overwrite, base
  phase only, of records that are not the transaction's own appends; R3 the `L` record synced before the FIRST append and
  nothing for any later one; R4 the capture's order (before file, sync, directory, `K`, sync, then truncate or remove); R5 a
  refused sync of a handed-over record is fatal (item 8's ROLLBACK; nothing more changes).
- **COMMIT** = F synced, F's directory synced (a created or removed name), `D C` appended and synced (the one durable write),
  the retirement; 2.2.1.10's three regions, reversal and UNACKNOWLEDGED mark apply unchanged. **ROLLBACK** = the idempotent
  settle under the entry mutex (restore the before file; images; truncate to L when the journal has an `L` record, and F is
  never shorter than it — or remove the file; `D R` synced; retire),
  run by the owner or by the next entry; a refused one is OWED and retried. **The entry step** at every writable OPEN and
  DELETE FILE (one directory listing, the price of §9.1.18.5 for a file not under APPLY COMMIT) and per changing statement
  under `ALL OTHER` only. A writer whose file a rollback removed creates it again at its next WRITE (GR3 restores the file
  and its locks and leaves the open mode to the implementor).
- **LINE SEQUENTIAL and the print stream are COVERED** by the same journal (the explicit decision PB3340 asked for).
- **The model from round one** (owner 2026-10-17): `scripts/models/sequential_journal_model.py`, a self-test every gate and
  CI run, executes the protocol over a medium that refuses, kills or loses power at every operation, with a second run unit
  at every interleaving point of the first (before every medium operation and before every statement: round 3's R3-1), and
  asserts I1–I4 (the state at the last COMMIT or the committed one, never a third; nothing of another run unit undone; no
  litter; no capture under another's handle): 332,783 runs at depth 4 in about twenty seconds, 684,234 at depth 5 by hand; and
  it proves its own watchdog in the same run (round 2's R2-2, round 3's R3-1): six named mutations of the protocol — each
  review finding put back, and R1's, R3's and R4's order broken — each required RED on the rows it names as its witnesses.
  The `IHostMedium` seam (2.2.2.12) re-runs its rows over bytes in PB3340's C# simulator.
- **The owner decision PB3340 asked is made (2026-10-19 15:45 PDT, "option a approved"):** the journal is transient files in the
  file's `.wolk-*` lock directory; kb/Work PB802's "no sidecar of any type" (2026-09-07) refused a persistent catalog consulted
  at every OPEN and does not cover it (PB802 carries the clarification). The owner was shown four shapes with their losses
  (the journal; memory-only undo; a journal elsewhere; a header inside the file) and 2.2.2.11 keeps the three rejected ones so
  they are not re-asked. PB3340 is `open`, blocked by PB3338 in the tier-2 chain, whose scope the owner decided at 18:58 PDT (PB3337:
  "Option A", the whole module).

## 2.2.3 — the sequential frame index (PB3350)

- ONE walk (`ReadStreamFrame` over `StreamMedium`), two products: `CountFrames` returns a count and stores nothing
  (`CountRecords`' VARYING arm, the OPEN EXTEND base, the REVERSED count); `FrameIndex` holds one checkpoint per S = 4096
  frames plus a window of at most S exact starts for the span being read backward — memory O(records / S + S) (under 2 MB
  per billion records), a single backward READ at most S head reads, a whole-file backward pass O(records) head reads (the
  same order as today's one walk). Built for free by the forward walk (`NextFrame` passes every start) and by one counting
  walk for a target beyond the walked region (OPEN REVERSED pays one pass instead of two). `SeekToRecord` stays the one
  reposition (PB352). Rejected: a trailing length word (a format change every reader of the stream framing inherits),
  walking from 0 per step (a quadratic backward pass), the lazy whole index (today's defect).
- Witnesses: a structural drift test (no per-frame storage in the count, the index bounded as stated, over a 2^20-frame
  file) and the existing GR21 and REVERSED goldens byte-identical.

## Review round 1 (2026-10-19 11:48–13:30 PDT) — FINDINGS 2 at 6ed0fdc3a, both answered by the correction

The enqueue unit's reviewer found two compositions the first text got wrong, both in the class the owner's rule of
2026-10-17 exists for (a crash design checked by prose). **R1-1 (HIGH):** 2.2.2.7 re-applied every journal entry after
restoring the before file, and R2 journaled a REWRITE made AFTER a capture, so an OPEN OUTPUT, three WRITEs, a CLOSE, an
OPEN I-O, a READ and a REWRITE rolled back to the committed file with the replaced file's first record written over it; the
reverse order (an append, then a capture) had no header field to name the capture. **R1-2 (MEDIUM):** "exactly four ways"
omitted CREATION (§14.9.27.4 GR17, GR18), so an OPTIONAL file absent at the last COMMIT, created by OPEN EXTEND, written and
rolled back was left as an EMPTY file ('00' on OPEN INPUT) where the standard restores "no file" ('05', or '35').

**What was done, and why it is more than two patches.** The composition was re-derived from the ORDER of the changes (the
two phases), the capture became a record of the journal rather than a header field, and creation became the START `A` whose
rollback removes the file. Re-deriving exposed three more defects of the same class the review did not reach: (1) the
capture was a RENAME with the kept handle on F — a handle follows a renamed file, so the file lock would have moved to the
before file and Windows refuses the rename outright; it is a COPY now; (2) the liveness byte and the mutex lived on F's
REGION, which does not exist after a DELETE FILE or before a creation — the liveness is now the holder file and the mutex a
`SidecarRegionLocks` byte, both in the lock directory; (3) the model's first run found a refused sync of a handed-over `K`
record deleting the before file the cached record still named — R5 now makes that refusal fatal. The model also fixed the
rollback's ownership (`D R` synced before the retirement, so a journal a power loss resurrects after its before file is gone
is retired, not restored), and settled the connector's state after a rollback removed its file (its next WRITE creates it).

**The model is the answer to the owner's rule:** `scripts/models/sequential_journal_model.py`, a `--self-test` the gate
and CI discover (`self_tests.py`), GREEN over 195,400 runs at depth 4 (12 named rows, every program of up to four
statements, every fault at every operation, every power-loss prefix, a second run unit at every operation boundary) and
over 2.3 million at depth 6 by hand; RED when R1-1 or R1-2 is put back, or R1's or R4's order is broken (the four
mutations were run by hand; the detection, not the mutations, is what the gate keeps). The review should re-read only the
diff since 6ed0fdc3a.

## Review round 2 (2026-10-19 14:29–15:10 PDT) — FINDINGS 1 at ff898ceb7: R2-1 answered, the lead R2-2 taken

**R2-1 (MEDIUM, 2.2.2.7 step 2):** the rollback's `SetLength(L)` was unconditional while 2.2.2.3 let a second covered
transaction B begin (by a REWRITE of a record A did not touch) while A held uncommitted appends, so B's L — read at B's begin
— counted them; A rolling back first left F shorter than B's L, and B's rollback EXTENDED F with zero bytes (a garbage
record, NULs, a misframed VARYING word), a third state I1 forbids. The model hid it twice: its truncation was shrink-only,
and no covered B kept a REWRITE open across A's ROLLBACK and then rolled back. **What was done, and why it is not the
reviewer's `min(L, length)`:** the model's new interleavings (a covered B left open across the rest of A's program, then
committed, rolled back, killed, or appending first) found the TWIN of R2-1 the clamp would not have fixed — B begun between
A's begin (under the entry mutex) and A's first write (outside it) read an L BELOW A's in-flight append, and B's rollback cut
A's record, committed or not. Both have one cause, L read at the begin, and one fix: **L is read at the transaction's FIRST
APPEND**, under the lock test that found no other live transaction (each holds END), so it is the committed length and
nothing of anyone else's lies at or past it; it is journaled as the `L` record (R3), the header carries START only, a
transaction that never appended has no L and truncates nothing, and F is never shorter than an L — only an appending
transaction's rollback truncates, to its own L, and two never append at once — which the model asserts at every rollback
instead of clamping. The oracle also learned to carry an unacknowledged COMMIT's candidate state through a later run unit's
commit (the new interleavings reached it; a model defect, not a protocol one). Row "R2-1 a transaction begun beside
another's append" names it. **R2-2 (LOW, lead, taken):** `--self-test` now runs each named mutation (`R1-1`, `R1-2`, `R1`,
`R3`, `R4`, `R2-1`) and requires RED from every one, so a weakened oracle or fault injector fails the gate; `--mutations`
and `--mutation <name>` run it by hand. 276,317 runs GREEN at depth 4 (18.6 s, the mutation arm included), 630,990 at
depth 5 (34.6 s). The review should re-read only the diff since ff898ceb7.

## Review round 3 (2026-10-19 17:53–18:05 PDT) — FINDINGS 1 at 32ad1409c: R3-1 answered

**R3-1 (MEDIUM, test-coverage, the model):** the row added for R2-1 could not reach the interleaving it was named for, and the
mutation `R2-1` was GREEN on it. The second run unit ran only before a MEDIUM operation of the first, and the entry mutex is
taken by a host step, so before a ROLLBACK, a writable OPEN, a DELETE FILE or a COMMIT that follows a data operation it was
never offered the point: a CLOSE under commit control has no medium operation and the ROLLBACK's first is under the mutex, so
every point from the append to the rollback was BLOCKED except the in-flight one. The mutation arm passed only because other
rows reached the in-flight twin, and the rollback's assertion "F has fewer records than L" was reached by no gate run.
**Answered:** the second run unit runs at every INTERLEAVING POINT of the first — before every medium operation AND before every
statement (its implicit COMMIT and item 8's ROLLBACK included), so a mutex-taking statement right after a data operation is
reachable; the R2-1 row became its two arms, "undone" (the first's ROLLBACK: an L read at a begin between the append and the
ROLLBACK is 3, and the second's rollback would EXTEND F) and "committed" (the in-flight begin: that L is 2 and would CUT X1);
and each mutation names the rows that must catch it, its witnesses, the proof requiring each witness RED under its mutation
on its own (a drift check refuses a witness name not in the rows). Under `--mutation R2-1` the "undone" row is RED with the
extension violation itself: "F has 2 records, fewer than journal 1's L 3: SetLength would extend it with zero bytes". **Found
beside it, same class, same change:** under `--mutation R1-2` the model CRASHED (`FileNotFoundError`) on "create, DELETE
FILE, re-create, COMMIT" with a death at operation 4 — a START P journal over an absent file — hidden by the proof's
fail-fast; the rollback now raises the I1 violation "journal t says F existed at its begin (START P) but F is absent", a
state the protocol never reaches (the depth-5 sweep stays GREEN). 332,783 runs GREEN at depth 4 (17.3 s, the mutation arm
included: eight witness pairs), 684,234 at depth 5 (29.0 s). The review should re-read only the diff since 32ad1409c.
