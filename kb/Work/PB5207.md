# PB5207 - the build process, redesigned top-down

**Sites:** `scripts/gate.py`, `scripts/build-local.ps1`, `scripts/inert_lane.py`, `scripts/self_tests.py`, `scripts/orchestrator/enqueue.py`, `scripts/hooks/forbidden_commands.py`, `.github/workflows/build-and-test.yml`, `docs/rearchitecture/DESIGN-test-build-ci.md`

**Why (owner, 2026-11-10).** "This is precisely what the Unix make and Windows MSBuild utilities are for. They rerun only
what is required due to changes." "It's stupid that every time we go to fix a process bug, we find more process problems.
Clearly it was designed or implemented very poorly." "I've asked for the redesign of the build process many times. Each
time, I get this piecemeal change." "We've spent days on process and little time on compiler."

## The diagnosis

The pipeline was never designed as a build. It is a sequence of whole-tree steps to which each incident added a rule that
REFUSES: a lane table, a reuse rule, a compose rule, a slot queue, a stamp, a check, a hook. Three consequences:

1. **Evidence is per run and per tree, not per step and per input.** So unrelated changes invalidate everything, and each
   exception (inert lane, tooling lane, REUSED, COMPOSED) is another hand-written predicate with its own defects (PB5099,
   PB5205). The script self-tests already have the right model (a PASS keyed by the content of every file the run opened,
   shared by all worktrees); nothing else does.
2. **Steps observe live state instead of declared inputs.** Self-tests read the developer's quota meter (PB5155) and the
   live work register (a note edit re-runs orchestrator tests); Unit reads the whole tree's file names. A step whose inputs
   are "whatever it happened to read" can be neither skipped nor trusted.
3. **Rules are enforced by refusal after the fact.** An agent learns a rule by tripping it; the landing discovers a
   missing artifact at its ninth step. Each guard is small; together they are most of what an agent does in a day.

## The design

**One model: a graph of targets.** A target is a named step with (a) DECLARED INPUTS, a set of path patterns plus the
toolchain and platform, (b) a command, (c) a result. Its KEY is a digest of the git blob ids of its inputs. A result is
stored once, by target and key, in one store in the git common directory, so every worktree shares it. A target is up to
date exactly when the store holds a pass at its key. Nothing else decides whether something runs: there is no lane, no
reuse rule, no compose rule, no "same tree" test. A documentation change is "inert" because no test target lists `kb/` or
`DEVLOG/` among its inputs, not because a table says so.

**The targets.**
- `build`: `dotnet build` (MSBuild is already incremental; the engine only records that it ran for this key).
- Test targets, one per input set, not one per assembly: `unit` (compiler unit tests: `src/`, the test sources),
  `conformance` (the suite, `tests/nist`, `tests/differential`, `src/`), `characterization`, and `repo-drift` (the tests
  that bind documents, scripts, CI files and the tracked tree to each other, split out of Unit, each group with its own
  inputs). Within a target a red re-runs only its failed cases (PB5099's rule, kept).
- One target per audit, with its own inputs.
- One target per script self-test. Inputs are the script, what it imports and its test data. A self-test runs against a
  fixture, never the live repository, the live register or a live account, so a note edit cannot make it stale.
- `review`: keyed by the branch's own patch, so merging main does not invalidate a review and any content change does.

**Declared inputs are verified, not trusted.** A target that reads a path outside its declaration is a defect the engine
reports: Python targets by the open-tracing the self-test runner already has, .NET targets by the file-access watch the
Linux shards already run. The declaration can be generated from one traced run and then pinned.

**One command.** `python scripts/build.py check` brings every target up to date for the working tree and prints one
verdict line; `why <target>` prints which input changed; `land <branch>` merges main, runs `check` (after a merge that
touched no input of a target, that target is already up to date), and queues the pull request. The verdict is the
command's own exit status and last line, so nothing after it can mask it.

**The landing needs no hand-made artifact.** A branch may land when every target, `review` included, is up to date at its
merged tree. The report file, the stamp line, the STATUS file and the per-lane exemptions go; the DEVLOG entry is the one
thing a person writes, and `land` says so at its first step, not its ninth.

**CI is the same graph on other platforms.** The merge group runs the same targets on Linux and in Release, with the
same keys, and restores the store from its cache, so it too runs only what is stale there. Whether CI may also accept a
Windows Debug pass recorded on the owner's host is a separate decision, taken with numbers once the store exists.

**Time bounds are declared per target.** A self-test declares its expected seconds; the engine stops it at a small
multiple and reports a timeout as a red of that target alone. No 3,600 s detector, no hung gate.

**Guards.** A guard that parses shell text to refuse it is replaced by a design in which the harm cannot happen: the
verdict-masking guard by the one command above; the worktree-isolation guard by the harness's own permission rules; the
heredoc guard by first measuring whether the mangling it prevents still occurs, then deleting it or fixing its cause.
What remains (never `git stash`, never push to main) is a short deny-list matched on the command name.

**The nightly** is the graph's slow targets on a schedule; a red one is shown by the session probe as the first line.

## Why not MSBuild or make themselves

They decide staleness by file timestamps inside one working copy and expect each step to produce a file. This repository
works in dozens of worktrees and in CI, where timestamps mean nothing and the result of most steps is a verdict. The
model the owner named is right; the mechanism has to be content digests in a shared store (what Bazel does and what
`self_tests.py` already does on a small scale). MSBuild stays where it is already right: compiling.

## What is deleted when this lands

`inert_lane.py`'s lane tables and CODE_READS list; the gate's REUSED, COMPOSED and carry rules, its run-record schema and
the growth ledger; the slot queue's priority classes (a shared store makes most gates short); the landing's stamp, report
and catch-up checks and most of its exit codes; `status_guard.py`; the shell-parsing halves of `forbidden_commands.py`
and the isolation guard; and the self-tests of all of those. The target is a pipeline a tenth the size, whose design
document is a few pages.

## Order of work (each stage lands on its own, fast-tracked, and deletes what it replaces)

1. **The store and per-target keys for the three test assemblies with declared inputs** (PB5205 is its first half). This
   alone makes a records-only change re-run Unit and not Conformance.
2. **Split `repo-drift` out of Unit**, so a compiler change does not wait for repository tests and a document change does
   not re-run 40,000 compiler tests.
3. **Self-tests as isolated targets with declared seconds**: fixtures instead of live state, per-target timeouts.
4. **`build.py check / why / land`**, replacing `build-local.ps1`, `gate.py`'s orchestration and `enqueue.py land`.
5. **Guards**: measure, then delete or replace.
6. **CI and nightly on the same graph.**

Each stage states its measured before and after in its DEVLOG entry: gate seconds per landed pull request, targets run
per gate, refusals per agent.

## Open questions this note does not decide

- Whether CI may trust a pass recorded on the owner's host (see above).
- How finely `unit` and `conformance` split (per namespace or per corpus directory) beyond the first split; decided from
  the store's own timings after stage 1.
