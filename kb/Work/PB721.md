# PB721 — OPEN — the zero minimum is legal; the missing SCREEN and the false conformance row are the defects

Reported 2026-09-06 by the `PB339` fix-lane implementer (report `…\a9d94900…\scratchpad\reports\PB339-report.md`,
"New defects found" item 1) as **"`RECORD IS VARYING IN SIZE FROM 0` is accepted at every edition, including
COBOL-85 … whether a zero MINIMUM record size is legal below 2023 is an edition question nothing in the compiler
asks."**

**The premise was validated before the diagnosis** (`feedback_validate_the_premise_not_only_the_rule`), and it does
not hold as filed. A zero minimum is **explicitly legal COBOL**, in the only editions this repository's spec can
speak for, and there is no edition gate to write. Two real defects sit underneath the report, and neither is
edition-shaped.

## Re-measured here, not inherited

Probe `…\49b17747…\scratchpad\pb721\pb721zl.cob` (the PB339 program, PROGRAM-ID and ASSIGN renamed per
`unique_programid_per_test`), run against **main's own** built compiler
(`src/Cobol.Net.Cli/bin/Debug/net10.0/cobol.exe`, no rebuild — main is `0db46983`, and `BoundCurrentRecord` is
absent from `src/`, so PB339's fix has **not** landed and this is the pre-PB339 tree):

|---|---|---|
| 85 | `W=00` / `R=00 LEN=0000` / `Z=[          ]` | none |
| 2002 | identical | none |

| 2023 | identical | none |

`pb721rl.cob` repeats it with `ORGANIZATION IS RELATIVE` — `W=00` / `R=00 LEN=0000` at `--std 85` and `--std 2023`,
also with no diagnostic. **Both arms of Annex A.3 item 43 round-trip a zero-length record.** That measurement is
what decides this note, and it is why the relative arm was probed rather than assumed.

## What the standard prints — and the citation the report inherited answered a different question

⛔ `feedback_a_real_clause_can_answer_a_different_question`. The report's cite line was
`--check 13.18.43.4 "Integer-2 specifies the minimum number of bytes to be contained in any record of the file"`
→ **OK §13.18.43.4 7)**, glossed as *"GR7 — no lower bound stated"*. That gloss is true of GR7 and false of the
clause: GR7 is a GENERAL rule saying what integer-2 *means*. The lower bound is a **SYNTAX** rule, one subclause
up, and the report never consulted it:

- `cite.py --check 13.18.43.3 "Integer-2 shall be greater than or equal to zero"` → **OK §13.18.43.3 7)**.

So `FROM 0` is not merely un-prohibited; **SR7 names zero and permits it by name.** Three independent
corroborations that the standard means a real zero-length record and not a degenerate one:

- `--check 8.5.4 "A logical record that has been specified using the variable-length or the fixed-or-variable-length
  format of the RECORD clause in which the number of characters positions is zero"` → **OK §8.5.4 5)** — it is one
  of the nine enumerated shapes of a zero-length item, alongside the zero-length literal and the zero-occurrence
  ODO group.
- `--check 13.18.43.4 "If the number of bytes determined as above is zero, the record is a zero-length item"` →
  **OK §13.18.43.4 16)** — GR16's closing sentence contemplates the count reaching zero on a READ/RETURN INTO.
- `--check A.3 "The capabilities of specifying a zero-length record for relative and sequential files, and of
  reading and writing such records, are dependent on the capabilities of the processor"` → **OK §A.3 43)** — the
  standard treats it as a **capability**, so both providing it and declining it are conforming. Declining it is
  not free: see §4.2.6 below.

## The edition question, answered as far as the spec can answer it

- **2023** — legal by SR7, quoted above.
- **2014** — legal. Annex E is the **complete** 2014→2023 delta (`docs/VERSION_CHANGE_REFERENCE.md`'s own scope
  statement: *"The 2023 spec documents the 2014→2023 delta completely (Annex E …)"*), and it carries **no** entry
  for a zero minimum record size or for zero-length records generally. Its only zero-length entry is E.2 item 23,
  reference modification. What Annex E *does* carry for this clause family is
  `--check E.3.3 "Setting of I-O status '05', '37', '39', '41', and '62'"` → **OK §E.3.3 35)**, which is DELETE
  FILE, not the RECORD clause. So SR7 is not a 2023 introduction and no `>=2023` gate is derivable.
- **2002 and 85** — `specs/ISO_COBOL.md` **cannot answer**, and that is a documented hole, not an oversight:
  `docs/VERSION_CHANGE_REFERENCE.md` states *"There is no 85→2002 row set here at all — when gating an 85↔2002
  difference, derive it from the 2002 standard, not from this file."* An edition gate written below 2014 would
  therefore be **invented rather than derived**, and `feedback_edition_gate_sweep` says what that costs: a gate
  that leaked upward would reject source SR7 explicitly permits.

**Determination: no edition gate.** `under_rejects` on this note is set by the SR5 measurement below, not by the
zero minimum. The owner-decision protocol's usual fallback — survey the model implementations
(`feedback_survey_compilers_on_latitude`) — has nothing to survey either: `VARYING IN SIZE FROM 0` occurs **zero**
times in the committed corpora (`grep -rn "VARYING IN SIZE FROM 0" tests/` over `*.cob`/`*.cbl`/`*.at`). Recorded
here so the 85/2002 half is not re-derived from scratch by the next reader.

## Defect 1 — the compiler provides a capability its own §4.2.6 conformance record declines

`docs/CONFORMANCE.md` §2, the Annex A.3 disposition table, row 43, verbatim:

```
| 43 | Zero-length record for relative/sequential files | 13.18.43.3 SR7/SR8 | Not claimed | Minimum record length is 1 |
```

The note **"Minimum record length is 1"** is false as measured, on both organizations, at all four editions. And a
declined A.3 element is not allowed to be silent:

- `--check 4.2.6 "An implementation shall provide a warning mechanism at compile time to indicate use of
  syntactically-detectable processor-dependent language elements not supported by that implementation"` → **OK
  §4.2.6**.

`docs/CONFORMANCE.md`'s own status banner spells the house mechanism for exactly this: *"an Annex A.3
**processor-dependent** facility is accepted with a named WARNING (the **COBOLNET1578–1580 band**, §4.2.6 third
paragraph)"*. `integer-2 = 0` is as syntactically detectable as an element gets — it is a literal in the clause the
binder already parses — and **no** diagnostic of any severity is produced. So the shipped compiler and the shipped
conformance statement contradict each other, in the document whose entire job is to discharge §4.2.6 —
`--check 4.2.16 "An implementation shall satisfy the user documentation requirements specified in 4.2.3, 4.2.4,
4.2.5, 4.2.6, 4.2.10, 4.2.12, and 4.2.13 by specification in at least one form of documentation"` → **OK
§4.2.16**, and `docs/CONFORMANCE.md` is that form.

## Defect 2 — `BindRecordClause` screens none of §13.18.43.3's integer rules, and that one IS an under-rejection

`src/Cobol.Net.Compiler/Binding/DataBinder.cs:1285-1301`, the whole method:

```csharp
private static void BindRecordClause(Core.RecordClauseContext rc, FileModel file)
{
    if (rc.VARYING() is null && rc.TO() is null) { … file.RecordContains = n0; return; }
    var lits = rc.integerLiteral();
    int? lo = lits.Length > 0 ? int.Parse(lits[0].GetText()) : null;
    int? hi = lits.Length > 1 ? int.Parse(lits[1].GetText()) : null;
    if (rc.TO() is not null && lits.Length == 1) { hi = lo; lo = null; }
    string? dep = …;
    file.Varying = new VaryingRecordInfo(lo, hi, dep);
}
```

It parses and stores. There is no range check, no cross-check against the record descriptions, and no other site
takes one. `grep -rn "13\.18\.43" src/ --include=*.cs` returns **86** hits, and exactly two of them are
ENFORCEMENT rather than a comment citing the clause from a consumer:

- §13.18.43.3 **SR1** — a record-description-less FD shall carry a RECORD clause (`DataBinder.cs:1249` +
  `DiagnosticCatalog.cs:2219-2227`), which is why `SR-13.18.43.3-1` is the one row of this subclause already
  CONFORMS.
- §13.18.43.4 **GR14 a)** — `--check 13.18.43.4 "If a REWRITE or WRITE statement is being executed, the
  EC-I-O-LOGIC-ERROR exception condition is set to exist, and the execution of the REWRITE or WRITE statement is
  unsuccessful"` → **OK §13.18.43.4 14)** — the runtime `'44'` in all three connectors
  (`SequentialConnector.cs:423`, `RelativeConnector.cs:280`/`:294`, `IndexedConnector.cs:409`).

GR14 a) is a GENERAL rule about what happens at execution; it is not a substitute for the syntax rules, and the
probe below shows why. **Six SYNTAX rules have no enforcement site anywhere in the compiler:**

| rule | text (`--check`ed) | |
|---|---|---|
| SR3 | *No record description entry for the file may specify a number of bytes greater than integer-1* | **OK §13.18.43.3 3)**, Format 1 |
| SR4 | *Record descriptions for the file shall describe neither records that contain a lesser number of bytes than that specified by integer-2 nor records that contain a greater number of bytes than that specified by integer-3* | **OK §13.18.43.3 4)** |
| SR5 | *Integer-3 shall be greater than integer-2* | **OK §13.18.43.3 5)** |
| SR7 | *Integer-2 shall be greater than or equal to zero* | **OK §13.18.43.3 7)** |
| SR8 | *Integer-4 shall be greater than or equal to zero* | **OK §13.18.43.3 8)**, Format 3 |
| SR9 | *Integer-5 shall be greater than integer-4* | **OK §13.18.43.3 9)**, Format 3 |

**Measured** (`…\scratchpad\pb721\pb721sr.cob`, the same program with `FROM 20 TO 5` — an SR5 violation):

```
--std 2023   W=44   ATEND   R=10 LEN=0009   Z=[..........]
```

It compiles clean, and the ill-formed clause surfaces only as GR14 a)'s runtime `'44'` on the WRITE — the
CONSEQUENCE caught at execution, never the clause diagnosed at compile time. That is the under-rejection:
source the standard forbids by a syntax rule is accepted, and the user learns about it from a file status at run
time instead of a diagnostic at compile time. **This is why `under_rejects: true`** — the zero minimum is legal and
contributes no harm flag of its own.

## Why it matters

Defect 1 is small in code and load-bearing in kind: `docs/CONFORMANCE.md` is the §4.2.16 conformance record, and a
row that says "Not claimed — Minimum record length is 1" over a capability the compiler demonstrably provides makes
the record itself wrong, which is the one document whose wrongness a user cannot detect by testing. Defect 2 is a
whole syntax subclause with no enforcement site, in a clause every variable-length file goes through.

## The fix shape

**One screen, six rules, at `BindRecordClause` — and the records are already there.** `BindFileSection` runs
`file.Records.AddRange(records)` at `DataBinder.cs:1117`, *before* the clause loop at `:1120` calls
`BindRecordClause`, and `FileModel` already computes both quantities SR3/SR4/SR9 need — `MinRecordSize` is GR8a's
minimum-occurrence sum (`FileModel.cs:233`) and `RecordWidth` the GR8b physical maximum. So the screen is a
structure over §13.18.43.3, evaluated in one place, not six special cases — `feedback_model_the_rule_shape_not_one_case`
and CLAUDE.md rule 5: the shape that makes Format 1's SR3 and Format 3's SR8/SR9 automatic, not the one that makes
SR5 small. These are **syntax rules, not edition gates**: they hold in every edition, so the screen is
unconditional and there is no `--std` sweep (`feedback_edition_gate_sweep` does not apply).

**And row 43 has to stop being false.** Two admissible resolutions; the evidence points at the first:

1. **Claim it.** The capability works on both organizations at every edition (measured above). Flip
   `docs/CONFORMANCE.md` A.3 row 43 to **Claimed**, delete the "Minimum record length is 1" note, and pin it with a
   golden that writes and reads back a zero-length record on a sequential file *and* a relative one — A.3 item 43
   names both, so a sequential-only golden would claim more than it proves. CLAUDE.md rule 3 points here: declining
   what is implemented is deferral by another name.
2. **Decline it for real.** Keep the row and emit a named COBOLNET1578–1580-band **warning** on `integer-2 = 0` /
   `integer-4 = 0`, per §4.2.6 and the CONFORMANCE.md banner. ⛔ Not an error: SR7 makes the source legal, so
   refusing it would reject legal COBOL. A new diagnostic id is needed — take it from
   `pwsh scripts/session-probe.ps1`'s next-free code, never a guessed number.

**Rows claimed:** `SR-13.18.43.3-3/-4/-5/-7/-8/-9` — all six are GAP today and all six are closed by the one
screen; they are claimed together because a note that claimed only SR7 would leave five rules whose enforcement
site had already been written. SR1 is already CONFORMS; SR2 (BYTES/CHARACTERS synonymous) and SR6 (data-name-1's
elementary-unsigned-integer shape, partly served at `DataBinder.cs:1415`) are not integer-range rules and stay out.

## Sweep

- **The other two formats.** Format 1's SR3 and Format 3's SR8/SR9 are the same rule shape over `integer-1` and
  `integer-4`/`integer-5`; the Format-1 arm of `BindRecordClause` returns after storing `RecordContains` and checks
  nothing either. All three formats, one screen.
- **The A.3 disposition table is a testable claim, and this row was never tested.** Row 43 is not alone in kind:
  every "Not claimed" row in `docs/CONFORMANCE.md` §2 asserts that the compiler does *not* provide something, and
  nothing mechanical contradicts such a row when the compiler quietly does. Row 40 (`RECORD KEY … SOURCE`) already
  carries an explicit debt marker for the mirror problem — declined *and* not observable. A drift check that
  compiles one probe per syntactically-detectable "Not claimed" A.3 row and asserts the named warning fires belongs
  beside `audit_annex_a1.py`, which already treats the A.1 determinations as checkable. This is
  `feedback_a_dead_lookup_is_also_unverified` at the document level: a disposition nothing exercises has never been
  contradicted.
- **Not a sibling, checked and excluded.** `VaryMin` already defaults an *unstated* minimum to the smallest
  described record (GR9), which is a different rule from an explicit `FROM 0` and is correct as written.
