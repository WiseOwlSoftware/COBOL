# PB3563 — a MOVE into a RENAMES THROUGH alias converts the numeric leaf it spans

## Scenario

Fuzz programs fz03077, fz03775, fz04473, fz04474 (`OUTPUT_DIFFERS:13.18.45`). `66 R-AC RENAMES R-A THROUGH R-C` over
`X(2) 9(3) X(2)`, with the `9(3)` leaf also displayed by its own name: a MOVE to the alias converts the slice that lands on
the numeric leaf (`XXX` becomes `000`). GnuCOBOL 3.2 prints the unconverted `[XXXXXXX]`.

### Reduced repro (the B2 adjudicator's probe, verbatim: `adj\B2\probes\ren2\ren2.cob`)

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. REN2.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 R.
   05 R-A PIC X(2) VALUE "AB".
   05 R-B PIC 9(3) VALUE 123.
   05 R-C PIC X(2) VALUE "CD".
66 R-AC RENAMES R-A THROUGH R-C.
PROCEDURE DIVISION.
   MOVE "XXXXXXX" TO R-AC
   DISPLAY "REN-AC [" R-AC "]"
   DISPLAY "B [" R-B "]"
   DISPLAY "REN-AC [" R-AC "]"
   STOP RUN.
```

## Expected (spec)

Each citation was re-run through `python scripts/spec/cite.py --check` from the worktree on 2026-10-23 (all OK).

- §13.18.45.4 2) (OK): "When the THROUGH phrase is specified, data-name-1 defines an alphanumeric group item that includes
  all elementary items starting with data-name-2 …" (the checked item continues past that point).
- §14.9.25.4 4) (OK): a move that is not an elementary move "is treated exactly as if it were an alphanumeric to
  alphanumeric elementary move, except that there is no conversion of data from one form of internal representation to
  another".

So the move fills the seven-character area with `XXXXXXX` and `DISPLAY R-AC` shows `[XXXXXXX]`.

## Actual (judge e7cf38ce4)

`REN-AC [XX000XX]` (the digits slice `XXX` is converted to `000`; the verdict line also records a second shape that converts to
`006`). GnuCOBOL 3.2 prints `[XXXXXXX]`. The probes `ren1` (the spanned leaf never referenced by its own name) and `grp1`
(a plain 01 group of the same shape) are correct, so only a 66 THROUGH alias whose numeric leaf is also referenced by name is
wrong.

## Mechanism and code site

`src/Cobol.Net.Compiler/Binding/Passes/UsageCollectionPass.cs:404-407`: `P()` adds a place to `WholeGroupReferenced` only when
its item is `IsGroup`. A 66 THROUGH alias fails that structural test (PB907 lineage), so the numeric-DISPLAY leaves it spans
never join `WholeGroupReferenced` and keep a native value carrier. `src/Cobol.Net.Compiler/CodeGen/Roslyn/PlaceRenderer.cs:466-482`
(`WriteRenames`) then stores each slice through `NumericImagePlace`, which converts it.

## Witnesses

fz03077, fz03775, fz04473, fz04474.

## Sibling sweep and golden to require

- Every consumer of structural `IsGroup` where a RENAMES alias (a 66 with THROUGH, and a single-item 66 over a group) must
  answer as the group it is: the usage-collection pass, the group-image users, the place renderer. A single-item RENAMES of a
  numeric leaf is an elementary alias and must stay one.
- Golden: the repro as a conformance case with the derived output; a leg where the spanned leaf is never referenced by name
  (`ren1`) and a plain-group control (`grp1`); a drift test that every alias kind answers the group question through one
  predicate.

## Orchestrator decision

§13.18.45.4 2) makes the alias an alphanumeric group; the plain 01 group of the same shape is correct (`probes\grp1`), so the defect is the 66 alias failing structural `IsGroup` in `UsageCollectionPass` (PB907 lineage).

## Landed (wave 1157 group H)

**Re-probe (own build, origin/main 07bfc3606).** Reproduced, and wider than filed: the `ren1` shape (the spanned numeric
leaf never named by the program) is wrong too, `XX000XX`, so the leaf's being referenced by its own name was never the
condition. The condition is that the numeric DISPLAY leaf keeps a native value carrier.

**Root.** `UsageCollectionPass.P` and `.Channel` asked the STRUCTURAL `DataItem.IsGroup`, which is false for a level-66
alias (no children, PB907 lineage), while §13.18.45.4 GR2 makes a THROUGH alias an alphanumeric group item and
§14.9.25.4 GR4 makes a move involving a group an alphanumeric move with no conversion (both re-run through
`cite.py --check`: OK, §13.18.45.4 2) and §14.9.25.4 4)). `MoveClassifier.IsGroupPlace` already answered `RenamesPlace => true`;
the pass was the second reader that did not.

**Fix.** `UsageCollectionPass.Visitor.AliasImage`: a `RenamesPlace` operand adds each spanned elementary item
(`RenamesPlace.Leaves`) to `CharacterChannelItems`, which `StorageFormPass` promotes through the one `IsImagePromotable`
test; `P` and `Channel` both route a `RenamesPlace` there. The bind-time `NumericImagePlace` wrap around a leaf that is promoted
afterwards renders as the identity (`CobolNum.FormatImage(string)` / `StoreImage(string, ..., string)`), so no resolver change.
A no-THROUGH alias forwards to the renamed item's own place and stays elementary.

**Sibling sweep.** Every operand position the pass visits goes through `P`/`Channel`, so MOVE source and target, DISPLAY,
INSPECT, STRING, UNSTRING, ACCEPT and a comparison are all covered (unit test, 7 + 4 positions); INITIALIZE refuses a
RENAMES operand (§14.9.20.3 SR5, COBOL0835). A reference-modified alias slice already stored correctly (probe `rm.cob`). The
other consumers of the group answer, `MoveClassifier.IsGroupPlace`, `PlaceRenderer.GroupImage`, `StorageOverlap`,
`CorrespondingBinder` and `StatementValidation`, already carry a `RenamesPlace` arm.

**Witnesses.** Golden `conformance-suite/cases/13.18.45-RENAMES/pb3563_renames_thru_numeric_leaf_characters` (9 legs, derived
from the two rules; accept 85, RENAMES has no edition below it so no negative), unit
`RenamesAliasImageTests` (positions, span bound, no-THROUGH control, unreferenced-alias cost control).
