# PB525

## Mechanism — linage-clause
linage-footing-zero-is-the-absent-sentinel

### Expected, from the standard
The FOOTING phrase IS specified, so GR6b's value rule 2 applies to the value read at the completion of the OPEN OUTPUT: 'The footing start shall be greater than zero and not greater than the page size.' Zero does not conform, so 'the EC-I-O-LINAGE exception condition is set to exist' and the program shall not proceed to write a normal page. GR1's 'If the FOOTING phrase is not specified, no end-of-page condition independent of the page overflow condition exists' is the rule for an ABSENT phrase and cannot be reached here, because the phrase is present.

```
$ python scripts/spec/cite.py --check 13.18.34.4 "If the FOOTING phrase is not specified, no end-of-page condition independent of the page overflow condition exists"
  OK  §13.18.34.4 1)  (General rules)
```

### Observed
The program compiles, runs to completion and prints `NO-EOP` then `LC=005`: the write into what would be the footing area of a 5-line page raises no end-of-page and no exception condition, and the file closes normally. The mechanism is a sentinel collision. ONE integer slot carries two different facts - 'the footing start' and 'there is no FOOTING phrase' - and 0 is the encoding of the second, so the first can never be validated: LinageOpExpr returns the literal "0" for a null operand (SequentialIoEmitter.cs:146) and EvaluateLinage's guard is written `footing < 0` precisely so that this 0 survives. A specified FOOTING whose data item happens to hold 0 is therefore indistinguishable from no FOOTING at all, and the compiler silently picks the interpretation the standard does not allow. It is silent in both directions: no diagnostic, no exception, and the END-OF-PAGE branch the program was written around simply never fires. THE FIX IS THE SHAPE, NOT THE GUARD: make the absent phrase absent in the model rather than zero - the evaluator tuple should carry a nullable footing (or the connector should keep a separate `_hasFooting` set from FileModel.Linage.Footing != null, which the binder already knows and throws away at codegen). Then EvaluateLinage can enforce `0 < footing <= body` whenever the phrase is present, which is what GR3 and GR6 both ask for, and the `_footing > 0` guard at :176 becomes a test of presence rather than a test of value. Sweep the sibling: the same evaluator tuple encodes an absent LINES AT TOP / LINES AT BOTTOM as 0, which is harmless only because GR1 says those values ARE zero when absent - so the collision is real for FOOTING alone, and that asymmetry is exactly what a single untyped 4-tuple of ints hides.
