# PB3699 — plan_wave --drain plans no finisher for a SPLIT group whose wave a fleet stop interrupted

**Sites:** `scripts/orchestrator/plan_wave.py` (`plan`, `branch_lead_notes`), `scripts/orchestrator/test_plan_wave.py`, `docs/rearchitecture/DESIGN-orchestrator-loop.md`.

The operator's STOP at 16:39 PDT split wave 20261031; groups A (`d92-1`, CHECK), C (`d92-3`, UNLANDED) and D (`d92-4`, UNLANDED) wrote SPLIT reports (`w20261031a-PB3446`, `w20261031c-PB3509`, `w20261031d-PB3639`) and checkpointed. The loop's next campaign wave (20261104) planned F's successor but no finisher for A, C or D, and `plan_wave.py --drain --dry-run` ("finishers of started work only") listed them only as judgment rows. The operator dispatched their finishers by hand (wave 20261106). A SPLIT report with a checkpointed branch and open notes is started work: the drain, and every plan, must give it a finisher. ## Landed (2026-10-25, fix-lane wave 20261107 group C)

**Re-probe (this build, a fixture of the note's shape).** Two reports with open `process_only` leads outside every
cluster, both on unlanded branches: a FINDINGS-stamped DONE report and a SPLIT one. `plan(...)`, normal and `drain=True`,
planned a finisher for the FINDINGS lead (PB3150's arm) and none for the SPLIT lead, whose branch printed as
`UNLANDED branches naming no open note or FINDINGS lead (judgment)`: the note's symptom, in the fix lane's population.

**Root.** `plan`'s `leads` (the notes the planner decides) were the fix lane's clusters plus the lead of a FINDINGS-stamped
report. A started group's notes are `process_only` campaign notes, which the fix lane's clusters skip, so a SPLIT,
NOT STARTED or gate-ended report on a checkpointed branch had no lead. **Fix.** `leads` also holds every note such a
report answers (`Report.notes`: its lead, its dispatch group's, what its branch closes) that is in the register, not
terminal on main and held by no cluster, when the report's branch is not on main or gone (a landed branch started
nothing a finisher could continue); and `branch_lead_notes` reads an unfinished report's lead from its own branch too
(an owner task files its note there). The existing arms decide those notes unchanged (newest report, dispatch hold,
carrier, replay, owned, locked, drain). **Sweep.** The other readers of `open_ids` in `plan` (`note_file`, `note_claim`,
`not_started`) concern clusters only; `prune_worktrees.lifecycle` already shows such a SPLIT branch as a DECISION row
naming the finisher, so the survey and the planner now agree. Real register, before and after: the dry-run plans of this
tree differ only in a worktree created meanwhile (no stale SPLIT report on an unlanded branch names an open unseen
note today).

**Tests.** `test_plan_wave.py` section 6b'''': SPLIT on CHECK and on UNLANDED, NOT STARTED, a landed note (none), a
landed branch (none), a lead only its branch has; normal and drain.
