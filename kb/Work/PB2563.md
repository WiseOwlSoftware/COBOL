# PB2563 — LANDED — the orchestrator's self-tests run in no gate

Found by wave 1037 group P (PB2537): its pr-test-analyzer review noted that `next_unit.py`'s new land deferral was
tested only in `test_orchestrate.ps1` section 8c, which no gate runs. The same holds for `coord.locked`, which PB2537
moved out of `alloc.py`: its stale-lock arm is tested only by `test_alloc.py`.

## Harm

A regression in the loop's unit choice, the allocator, the planner, the budget or the mailbox passes every gate and
CI. The checks were run by hand this session: test_orchestrate 144/144, test_alloc 23/23, test_plan_wave 111/111. A
hand run is not a gate.

## Shape (rule 5: the next self-test is covered automatically)

One gate leg or audit runs them all, and finds them by DISCOVERY, never from a list: every
`scripts/orchestrator/test_*.{py,ps1}` and every module there that accepts `--self-test`. The local gate runs it (an
entry in `run_gate_legs.py`, or one Unit drift test that enumerates and runs them), and CI runs the same entry point,
so a CI step cannot be missing locally (PB1957). A drift test fails when a self-test exists that the runner did not
run.

Constraints for the implementer:
- `test_orchestrate.ps1` takes more than 10 minutes, longer than `PythonInstrument`'s 120 s limit. It needs its own leg
  or a faster fake.
- It needs PowerShell 7. `test_autostart.ps1` touches Task Scheduler shapes. Both are Windows-only, so the Linux side
  must say so explicitly; it must not skip them silently.
- `test_plan_wave.py` imports `check_practices.py`, which needs the `tools/claude-skills` submodule; a fresh worktree
  lacks it, so the runner fetches the submodule, as CI's fleet-practices step does.
- Once the runner covers them, remove the per-script Unit tests (LandingLeaseDriftTests, TrainMeasureDriftTests) and
  CI's separate landing_check step, unless they assert arms by name, which the runner should then do instead
  (CLAUDE.md rule 4: one mechanism).

Code sites: `scripts/run_gate_legs.py#AUDITS` (line 103), `.github/workflows/build-and-test.yml` audits job
(line 294), `docs/rearchitecture/DESIGN-orchestrator-loop.md` section 12.

## Landed (wave 1037 R, branch `selftests-gate`, 2026-10-08)

- **One discovering runner, `scripts/self_tests.py`.** A tracked file under `scripts/` is a self-test when its code
  handles `--self-test` (read from the Python syntax tree, or a shell `--self-test)` arm), or when it is named
  `test_*.py`/`test_*.ps1`. It found 57 (the fourteen of the table above, `filter_population.py`, the hook, spec, arch
  and gate tools, and the runner itself). Each runs in parallel with a private `COBOL_COORD_DIR`, without git's
  repository-selection variables, and with a private `GIT_CONFIG_GLOBAL` holding only an identity, so a self-test that
  commits behaves the same on a developer's machine and on a CI runner. On Windows `bash` is Git for Windows' own,
  found from `git --exec-path`, never System32's WSL launcher. Header markers: `# SELF-TEST-PLATFORM: windows — <why>`
  (reported NOT RUN elsewhere, with the reason, in the verdict) and `# SELF-TEST-NEEDS: build — <what>` (run only by
  `--built`, after a build).
- **Every entry point runs it, and none names a self-test by hand:** the gate driver's `SELF-TESTS` audit (the audits
  now run concurrently, still before the slot, PB2523/PB2524) and its post-build half beside the legs; the Linux gate's
  `selftests` leg (replacing its hand-listed `hooks` leg) and `selftests-built` after the unit and conformance builds;
  CI's `audits` job (replacing the hook, cite, ledger_plan, landing_check and dispatch_guard steps), `greenfield-unit`
  (`--built`) and `windows-build-test` (the Windows-only ones). `landing_check.py --self-test` is no longer CI-only.
- **`test_orchestrate.ps1` split** into eleven `test_orchestrate_*.ps1` parts over one harness
  (`testdata/orchestrate_test_lib.ps1`), 144/144 checks kept, so it runs in parallel inside the runner.
- **`SelfTestDiscoveryDriftTests`** (Unit): a broader text net finds no self-test the runner misses; every entry point
  above runs the runner and names no self-test itself; the runner's arms by name, a planted failing self-test turning
  it RED among them.
- **Probes.** A planted `scripts/orchestrator/test_planted_red.py` (exit 1) turned `self_tests.py` RED, exit 1, "1 of
  57 failed", which the driver's audit arm carries to a RED gate before the slot. A hand-named `landing_check.py
  --self-test` planted in the workflow turned the entry-point fact RED.
- **First Linux run** (a WSL clone, as the Linux gate runs): two self-tests had never run on Linux and were RED there.
  `fleet_active_build.py`'s "a bare drive `/e` maps to the drive root" arm sat outside its `os.name == "nt"` guard
  (now an arm per platform), and `test_autostart.ps1` installs a Windows Startup entry (now marked windows-only).
  After the fix: 44 ran GREEN in 5 s, 12 Windows-only reported NOT RUN with their reasons.
- **Measured gate cost (Windows, a loaded host):** the old serial audit phase took 42.5 s (CITATIONS 25.5 s). The
  runner takes 80–85 s for 56 self-tests, set by the eleven `test_orchestrate_*` parts running in parallel (67–80 s
  each under load, 33–65 s on a quieter host); the audits run concurrently with it, so the pre-slot phase grows by
  about 40 s. `filter_population.py --self-test` (42 s) runs beside the legs, off the critical path.
- **Kept on purpose.** The per-script Unit tests that pin arms BY NAME (GateSlotDriftTests, LandingLeaseDriftTests,
  TrainMeasureDriftTests, CitationAuditSelfTestDriftTests and the like) stay: the runner proves a self-test passes,
  and those tests prove its named arms still exist, which the runner cannot know. `guard-fast.sh` still runs the
  guard's own instruments (`guard-population.sh --self-test`, `guard-nist-audit.sh --self-test`,
  `guard-verify.sh --witnesses`) before each guard run, as its preflight; the runner runs the first two in every gate
  too.
