# PB596 — LANDED (discharged: fixed by PB388) — the citation a user reads names the wrong statement

Reported by the golden-lane round-3 `misc-p1` writer while deriving the `SR-14.9.14.3-3` negatives, and
independently reconstructed from the compiler source by the round-3 refuter ("`EcNameResolution.cs:51` emits
`{where}: exception-name '{Name}' is a level-{n} name…` with `where = "EXIT PROGRAM RAISING"`"). **Re-read on
this tree by the lander.**

## The mechanism

`src/WiseOwl.Cobol.Compiler/Binding/EcNameResolution.cs:52`

```csharp
+ "name; only a LEVEL-3 exception-name may be raised (ISO §14.9.29.3 SR1)");
```

One resolver serves every raising context — `RAISE`, `GOBACK … RAISING`, `EXIT PROGRAM … RAISING`,
`PROCEDURE DIVISION … RAISING` — and the message hard-codes §14.9.29.3 SR1, which is **RAISE's** syntax rule. A
user who wrote an `EXIT` statement is handed the rule for a statement they did not write. §14.9.14.3 SR3 states
the identical obligation for EXIT (*"Exception-name-1 shall be a level-3 exception-name as specified in the rules
for exception conditions"*, `cite.py --check 14.9.14.3` → OK 3\)), and §14.9.18.3 states it for GOBACK; the
resolver already knows which verb it is serving — it threads that verb into `{where}` and prints it — so the
clause is derivable at the same point the message is built.

The same shape sits in `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/EcBinder.cs:204`, whose EC-USER /
PD-header message likewise names one verb's rule for all of them.

## The fix shape already exists in this tree

`src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:205` does it correctly:

```csharp
$"{what} (ISO §14.9.42.3 {stopRule} for STOP RUN; §14.9.18.3 {gobackRule} for GOBACK)");
```

— the clause AND the rule number travel with the context. ⛔ Do not fix this by editing the one string:
`{where}` is already a per-verb value, so the clause belongs beside it in whatever carries the verb (a
`(verb, clause, rule)` triple resolved once), which makes the next raising context automatic instead of a fourth
literal. Pair it with a drift test asserting that each raising context's diagnostic names its OWN clause — that
is what keeps "automatic" true.

## Why no gate caught it

Neither citation audit looks at diagnostic MESSAGE text against the construct that triggered it:
`audit_code_citations.py --check` and `audit_doc_citations.py --check` are both at **0 findings** on this tree
while this string ships. The message is a user-facing conformance claim and deserves the same treatment as a code
comment.

## Resolution (wave 20261770, group D)

**Re-probe on a fresh Debug build: the mechanism no longer reproduces.** `EcRaiseSite` (PB388) already carries
`(Verb, Clause, Level3Rule, ObjectRule, LastRule, GlobalDeclarativeRule)` as one value per statement, and
`EcNameResolution.TryResolve` prints `site.Cite(site.Level3Rule)`; `EcBinder.EcBindRaising` prints the EC-USER leg with the
same site. Probes (cobol.exe, COBOL-2023):

- `EXIT PROGRAM RAISING EXCEPTION EC-BOUND` -> `COBOL0710 … only a LEVEL-3 exception-name may be raised (ISO §14.9.14.3 SR3)`
- `GOBACK RAISING EXCEPTION EC-BOUND` -> `… (ISO §14.9.18.3 SR2)`
- `RAISE EXCEPTION EC-BOUND` -> `… (ISO §14.9.29.3 SR1)`
- `EXIT PROGRAM RAISING EC-USER-L1NOPD` (not in the PD header) -> `COBOL0717 … (ISO §14.9.14.3 SR3 — otherwise EC-RAISING-NOT-SPECIFIED, Table 13)`

The note's two sub-requests were also met before this wave: the two `diagnostics.json` `expect` strings
(`l1-exit-raising-level2-name`, `l1-exit-raising-ecuser-not-in-pd`) already pin the corrected clause, and
`EcRaiseSiteDriftTests` re-derives every ordinal from `spec-rule-catalog.json`. What was still missing was the END-TO-END pin
the note asked for ("each raising context's diagnostic names its OWN clause"):
`ExceptionConditionConformanceTests.RaisingContext_DiagnosticCitesItsOwnClause` now asserts it for RAISE, GOBACK and
EXIT PROGRAM (COBOL0710) and for GOBACK and EXIT PROGRAM (COBOL0717). The other `TryResolve` callers (USE, the PERFORM WHEN
list, the declined-facility binder) pass no `level3` site and emit no level-3 diagnostic, so no fourth literal exists.
