# PB348 — a bound node built after binding is never checked by a bind pass

**Rows:** `SR-14.9.32.3-2`, `SR-14.9.32.3-3`, `SR-14.9.32.3-4`, `GR-14.9.32.4-4`, `GR-14.9.34.4-5`. Three
subjects and the batch-1 refuter found this from four directions; the refuter's evidence is the sharpest and is
given first.

## The A/B probe that settles it

§14.9.32.4 GR4 makes `RELEASE record-name-1 FROM x` **exactly** `MOVE x TO record-name-1` followed by the same
RELEASE without FROM (`--check 14.9.32.4 "The result of the execution of a RELEASE statement with the FROM phrase
is equivalent to the execution of the following statements in the order specified"` → **OK**). It is not.

Identical programs per GR4, `SD SRTF / 01 SRT-NUM PIC 9(3)`, `SORT ... GIVING` (no RETURN, so the RETURN emitter
is out of the picture):

* `out-b1/probe/ref-gr4a/c.cob` — `MOVE QUOTE TO SRT-NUM. RELEASE SRT-NUM.` at `--std 2014` **runs**: emits
  `SRT_NUM = new string(<the quote character>, 3)` then `CobolSort.Release(...)`, prints an `AFTER-MOVE=[...]`
  line holding three quote characters, then `SORT-DONE`, exit 0.
* `out-b1/probe/ref-gr4a/d.cob` — `RELEASE SRT-NUM FROM QUOTE.` at `--std 2014` **aborts**: emits
  `NotImplemented.Run("MOVE of an alphanumeric figurative constant into the numeric item 'SRT-NUM' without
  image-backed storage")` and dies with an unhandled `NotImplementedCobolFeatureException` BEFORE the release, so
  the record never reaches the initial phase and the SORT never completes.

Same source, same SD, opposite result. **Second, independent leg (edition):** at `--std 2023` the explicit MOVE
is REMOVED and errors COBOLNET0902 (exit 70), while the `RELEASE ... FROM QUOTE` form compiles with no diagnostic
at all (exit 0) — *according to the rules specified for the MOVE statement* is not applied at any edition.
**Third leg (hard compile failure):** with an OUTPUT PROCEDURE instead of GIVING (`ref-gr4a/b.cob`) the same
divergence makes the whole program uncompilable, `error CS0029: Cannot implicitly convert type 'string' to
'long'` in the generated C#.

## Why it is not only a diagnostics gap

`MoveBinder.Bind` does more than diagnose: it collects **codegen-relevant storage facts** —
`ctx.Data.MarkImageForced(t.Item)` for an alphanumeric-figurative sender into an elementary numeric-DISPLAY
receiver, and `MarkRefModStoreImage` — the facts `StorageFormPass` consumes. A `BoundMove` that never passes
through the binder is missing from that pass's input, which is why the failure is a *NotImplemented* and a raw
Roslyn type error rather than a wrong value.

## The three RELEASE syntax rules, all with the same cause

> SR2: If identifier-1 is a function-identifier, it shall reference an alphanumeric or national function.
> SR3: Identifier-1 or literal-1 shall be valid as a sending operand in a MOVE statement specifying record-name-1
> as the receiving operand.
> SR4: Literal-1 shall not be a zero-length literal.

All three `--check 14.9.32.3` → **OK**. None fires. The DECISIVE paired probe: `out-b1/probe/sr3ctl/sr3ctl.cob`
writes `01 SRT-REC PIC A(8). 01 WS-NUM PIC 9(3) VALUE 123.` and `MOVE WS-NUM TO SRT-REC.` →
`error COBOLNET0819: ... a numeric or numeric-edited sending operand does not move to an alphabetic receiver
(ISO 14.9.25.3 SR10, Table 16)`; `out-b1/probe/sr3move/sr3move.cob` writes the IDENTICAL move as
`RELEASE SRT-REC FROM WS-NUM.` → compiles clean, prints `R=[123     ]`. SR2:
`RELEASE SRT-REC FROM FUNCTION LENGTH(WS-A).` → clean at 85/2002/2023, prints `R=[8       ]`. SR4:
`RELEASE SRT-REC FROM "".` → clean at 2002/2014/2023, and the control `out-b1/probe/zlctl/zlctl.cob` proves `""`
IS modelled as a zero-length literal (`STOP RUN WITH ERROR STATUS ""` → COBOLNET1704). **SR4 is a missing
APPLICATION, not a missing capability:** the compiler owns a zero-length-literal predicate and applies it in at
least four other places (`ControlFlowBinder.cs:139-141`, `IntrinsicBinder.cs:1751`, `DataBinder.Switches.cs:692`,
`CallBinder.cs:418`).

## And the RETURN twin, §14.9.34.4 GR5 b)

> The current record is moved from the record area to the area specified by identifier-1 according to the rules
> for the MOVE statement without the CORRESPONDING phrase.

`--check 14.9.34.4 "according to the rules for the MOVE statement without the CORRESPONDING phrase"` → **OK**.
`out-b1/probe/p7/p7.cob` (`RETURN SF INTO WS-RECV` where WS-RECV is `TYPE TA`, TA `TYPEDEF STRONG`, the SD record
area an ordinary group) compiles and runs silently; the control `p8.cob` shows the identical MOVE written
explicitly is rejected COBOLNET1533; the sibling `p9.cob` (`READ DF INTO WS-RECV`) also compiles and runs
silently. **GR5's other five obligations DO hold and were verified**: the move is inside the success arm, the
record is available in both places, the `RECORD IS VARYING` size matches §13.18.43 GR16 a) (probe `p11`: LEN=06 →
`INTO=[2BB         ]`), and item identification happens after the read (probe `p10`).

## The sweep, and it is wide

`new BoundMove(...)` at EMIT time occurs at `SequentialIoEmitter.cs:270` (WRITE FROM), `:394` (REWRITE FROM),
`:375` (READ INTO), `KeyedIoEmitter.cs:177` (keyed WRITE FROM), `:220` (keyed REWRITE FROM), `:161` (keyed READ
INTO), `SortEmitter.cs:142` (RELEASE FROM) and `:173` (RETURN INTO), plus `CallEmitter.cs:505` and
`CorrespondingEmitter.cs:27`. `WriteSource` (`SequentialIoBinder.cs:188-192`) is the SHARED binder for the WRITE /
REWRITE / RELEASE FROM phrases — its own doc comment says so — and is a three-way hand-off with **no inspection
at all**; each of those phrases carries its own *shall be valid as a sending operand in a MOVE* syntax rule.

## The fix shape

Fixing one call site would be the smallest diff and the wrong shape. **Bind the implicit MOVE where the explicit
one is bound** — as a bound sub-statement of `BoundRelease` / `BoundReturn` / `BoundRead` / `BoundWrite` /
`BoundRewrite` — so every present and future `... FROM` / `... INTO` phrase inherits the MOVE syntax rules and the
storage-fact collection instead of re-deriving them, with a drift test asserting **no `new BoundMove` survives in
`CodeGen`**. That bound sub-statement is also where **PB339**'s explicit sender LENGTH belongs, and **PB337**'s
receiver-admissibility validator runs beside it.

`kb/Work/PB10` (landed) covers only the ADMISSION of a function-identifier in these positions — the positive
half, pinned by `conformance:2023/pb10_function_identifier_sending` — and explicitly not the class restriction
SR2 imposes.

**Code sites:** `SequentialIoBinder.cs#WriteSource` · `SortEmitter.cs#EmitRelease` (line 142), `#EmitReturn`
(line 174) · `SequentialIoEmitter.cs#EmitRead` · `SortBinder.cs#BindRelease` · contrast `MoveBinder.cs#BindMove`
(the bind-time screens at lines 49-59).

## Landed — 2026-09-06

**The rule now lives where a MOVE's rules live.** `MoveBinder.BindMoveOf(source, targets, implicitOf)` is THE one
application of the MOVE statement's own rules to a sender/receiver pair — the explicit MOVE statement and every
implicit phrase move alike. `BindFromPhrase` binds `… FROM` (RELEASE §14.9.32, WRITE §14.9.51, REWRITE §14.9.35 —
sequential and keyed), `BindIntoPhrase` binds `… INTO` (the sequential READ, the keyed READ, the sort RETURN), and
both end in `BindMoveOf`, so the three screens (`MoveFigurativeEditionGates`, `MoveCategoryLegality`,
`MarkRefModStoreImage`) and the fourth (`StatementValidation.CheckStrongMove`) reach the phrases by CONSTRUCTION
rather than by an edit. The bound node carries the move: `BoundWrite.FromMove`, `BoundRewrite.FromMove`,
`BoundRead.IntoMove`, `BoundKeyedWrite.FromMove`, `BoundKeyedRewrite.FromMove`, `BoundKeyedRead.IntoMove`,
`BoundRelease.FromMove`, `BoundReturn.IntoMove` — eight nodes, one shape.

**`BoundMove.ImplicitOf` names the phrase**, so every screen reports the statement the programmer WROTE:
`the implicit MOVE of RELEASE … FROM to SRT-REC (ISO §14.9.32.4 GR4 a); §14.9.32.3 SR3)`. `ImplicitMovePhrase`
owns both renderings — `WhereOf` where the message names the receiver, `Via` where it already does — so there is
one spelling of "the programmer did not write MOVE" and it is on the type.

**The per-verb rules are a ROW, not a flag, and that was load-bearing.** §14.9.32.3 SR2 (RELEASE) and §14.9.51.3
SR4 (WRITE) admit *"an alphanumeric or national function"*; §14.9.35.3 SR9 (REWRITE, the FILE phrase not
specified) admits *"an alphanumeric, boolean, or national function"*; and only RELEASE (§14.9.32.3 SR4) forbids a
zero-length literal-1. A scalar "must be alphanumeric" column would have REJECTED LEGAL SOURCE on the REWRITE arm.
The FILE-phrase readings (§14.9.51.3 SR10, §14.9.35.3 SR8) are unreachable — the FILE arm is Annex A.4.13 item 2,
declined COBOLNET1706 earlier. The function's class is read off the BOUND operand through the SAME Table-16
sender position the category screen uses (`MoveBinder.SenderPosition`, extracted from an inline switch for this
reason): a folded `FUNCTION LENGTH` reaches the binder as a plain numeric literal, which is how it would have
been read as "unknown" and waved through by a second reading of the same question.

**`SortBinder` no longer takes a `SequentialIoBinder`.** That constructor edge existed only for `WriteSource`,
the three-way operand hand-off that applied none of the three verbs' rules; it is gone, and the sort verbs and
the sequential I-O verbs are independent collaborators again.

**Diagnostics.** COBOLNET1914 `from-phrase-function-class` (one descriptor, per-verb admitted set, the site names
the verb and the category it saw) and COBOLNET1915 `from-phrase-zero-length-literal`. `docs/DIAGNOSTICS.md`
regenerated from the catalog. COBOLNET1916 was reserved and not needed.

**Drift.** `ImplicitMoveConstructionDriftTests` asserts (a) none of the three phrase emitters constructs a
`BoundMove`, and (b) every remaining construction anywhere in `CodeGen` is one of the three NAMED non-phrase
implicit moves — MOVE CORRESPONDING's per-pair moves, INITIALIZE's §14.9.20.4 GR4 stores, GOBACK RETURNING's
§14.9.18.4 GR2 move — so a new emitter-built move fails at the shape rather than in a program nobody has written
yet. It was proved to fail by construction before it was trusted: injecting `new BoundMove` into
`SortEmitter.cs` turned both assertions red by name. `IntoSenderDriftTests` moved with the builder — the owner is
now `MoveBinder#BindIntoPhrase` and the three arms are the three BINDERS.

**Goldens.** Six positive legs and nine negative fixtures, each deriving its expected value from the rule text in
its own header: `{85,2002,2014,2023}/pb348_from_into_move_rules` (PROGRAM-IDs `PB348P1`…`P4` — all five phrases
written beside the explicit statement pair each is equivalent to), `{2002,2014}/pb348_release_from_figurative_image`
(`PB348Q2`, `PB348Q3` — the abort repro, running), and in `negative/`
`pb348-release-from-integer-function`, `-write-from-integer-function`, `-rewrite-from-integer-function`,
`-release-from-zero-length-literal`, `-release-from-invalid-move-sender`, `-write-from-invalid-move-sender`,
`-return-into-strong-group`, `-read-into-strong-group`, `-release-from-quote-numeric-removed-2023`. The three
verbs get separate fixtures because they reached ONE inspection-free binder from different call sites, and the
READ and RETURN INTO fixtures are a pair for the same reason. An edition is omitted from a `reject-at` header only
where a DIFFERENT rule refuses the program first (a literal FROM operand is COBOLNET0871 at 85; TYPEDEF STRONG is
a 2002 introduction).

**Rows.** `SR-14.9.32.3-2`, `SR-14.9.32.3-3`, `SR-14.9.32.3-4` NOT-IMPLEMENTED → CONFORMS; `GR-14.9.32.4-4`
DIVERGES → CONFORMS; `GR-14.9.34.4-5` PARTIAL → CONFORMS. GAP 2780 → 2775. The same batch renames the
`code-location` of `GR-13.18.43.4-16` and `GR-14.9.30.4-4` (kb/Work PB339's rows), which named
`SequentialIoEmitter#IntoSender` — a symbol this change removed; the rule, verdict and evidence are unchanged,
only the address is.

**What did NOT hold from the original note.** The note lists `CallEmitter.cs:505` and `CorrespondingEmitter.cs:27`
among the emitter-built `new BoundMove` sites. Neither is a `… FROM` / `… INTO` phrase: they are GOBACK
RETURNING's §14.9.18.4 GR2 move and MOVE CORRESPONDING's per-pair moves of §14.9.25.4, each a different rule with
a different sender. They are deliberately left emitter-built and are NAMED in the drift test's
`EmitterBuiltMoves` table (with INITIALIZE's §14.9.20.4 GR4 stores, which the note did not list) so that their
number can only go down. Whether either should also be bound is a separate question and not this note's.
