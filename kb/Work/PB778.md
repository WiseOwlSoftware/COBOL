# PB778 — OPEN — one grammar line, two operand kinds, and the compiler has both wrong

Filed 2026-09-06 by the registrar from the PB732 implementer's report (§"New defects" (b)). The report's repro was
measured on PB732's worktree; **the mechanism below was re-derived on main at `9fad13e5` from the grammar and the
printed general format, and one of the report's conclusions does not survive that re-derivation** (see the premise
correction). Nothing here is inherited: every clause number was re-run through `scripts/spec/cite.py --check`.

## The grammar, quoted from main

`src/Cobol.Net.Frontend/Grammar/Core/CobolData.g4:450-457`:

```antlr
editingPhrase
    : EDITING literal ( IS? literal | FOR editingForPhrase )
    ;

editingForPhrase
    : NEGATIVE IS? literal ( POSITIVE IS? literal )?
    | POSITIVE IS? literal ( NEGATIVE IS? literal )?
    ;
```

`literal` is the NARROW rule — `src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4:494-497`:

```antlr
literal
    : numericLiteral
    | nonNumericLiteral
    ;
```

It has no word-shaped alternative at all. A bare user word can only reach a VALUE-style operand through
`valueClauseOperand` (`CobolExpressions.g4:31-34`, `unaryExpression | nonNumericLiteral`), whose
`unaryExpression → primaryExpression` arm admits a `dataReference`. So `EDITING "X" IS KC` cannot parse, and the
rejection is structural rather than a missing binder check — which is why the report's measured diagnostics are the
parser's, not the binder's:

```
01 KC CONSTANT AS "CR".
01 E1 PIC 9(3) EDITING "X" IS KC.
--std 2023 → COBOL0001: no viable alternative at input 'KC'
             COBOL0309: unexpected 'KC'. A literal value is expected here, not a data-name
```

(that pair measured by the PB732 implementer on his worktree; the grammar lines above are main's, and PB732's
`src/` diff does not touch `editingPhrase`).

The printed §13.18.40.2 Format 1 figure reads
`… EDITING character-1 { IS literal-1 | FOR { NEGATIVE IS literal-2 │ POSITIVE IS literal-3 } } …`, and its figure
note in `specs/ISO_COBOL.md` (the block immediately under the diagram) states that `IS`, `character-string-1`,
`character-1` **and the literals** are not underlined. So the standard names **three literal positions** in this
clause, §13.18.40.3 SR9 types them, and §13.10.3 SR2 therefore puts a constant-name in each. `EDITING "X" IS KC`
is conforming source at COBOL-2023 and this compiler refuses it. CLAUDE.md rule 4's forbidden outcome.

## ⛔ Premise correction — the fix is NOT "widen every `literal` on that line", and [[PB568]] is why

The brief this note was filed from proposes *"the same `valueClauseOperand`-style widening through the
`RawValueOperandText` chokepoint PB732 built"* applied to the EDITING clause. **Applied to all four operands that
would be wrong, and it would deepen an existing, already-filed defect.** The general format writes the FIRST
operand as `character-1`, bare — not as a literal:

- §13.18.40.3 SR8 (`--check` OK): *"Character-1 shall be any basic letter in the COBOL character set except those
  specified in a CURRENCY-SIGN clause or a basic letter character A, B, C, D, E, N, P, R, S, V, X, Z …"*
- §13.18.40.4 GR14 (`--check` OK, quoted above): character-1 is *a character position in character-string-1* — a
  PICTURE SYMBOL, not an operand carrying a value.
- §13.10.3 SR2's admission is textually scoped to *"anywhere that a format specifies **a literal**"*. The format
  does not specify a literal there, so SR2 does not reach character-1 and a `valueClauseOperand` in that slot
  would admit a spelling the standard does not define.

[[PB568]] (OPEN, MAJOR, `rejects_legal_source`) already owns character-1: it measured that the conforming BARE
spelling `PIC 99T99 EDITING T IS ":"` is a parse error and only the compiler's invented quoted spelling reaches
`PictureAnalyzer.ValidateEditing`, which is why `SR-13.18.40.3-10` and `-11` are PARTIAL. **The two notes rewrite
the same three grammar lines in opposite directions and must land in ONE change set** — character-1 narrows to a
bare picture-symbol word, literal-1/-2/-3 widen to admit a constant-name, a symbolic-character and a figurative
constant. Landing either alone re-writes the line the other one needs and is `feedback_two_arm_dispatch` a
seventh time.

## Fix shape

1. `editingPhrase` becomes `EDITING editingChar1 ( IS? editingLiteral | FOR editingForPhrase )` with
   `editingForPhrase`'s four positions on `editingLiteral` too — a NAMED rule per operand kind, so the binder can
   name the node it screens instead of counting `literal()` children, and so the two operand kinds can never
   again be widened or narrowed together by accident.
2. `editingLiteral` is `valueClauseOperand`'s admission set (constant-name · symbolic-character · figurative ·
   concatenation), resolved through the ONE chokepoint PB732 builds — `DataBinder.RawValueOperandText`
   (`src/Cobol.Net.Compiler/Binding/DataBinder.cs:3541`), whose doc comment already states the §13.10.3 SR2 /
   §13.10.4 GR1 substitution rule for exactly this case. ⚠ Do NOT copy the substitution logic into
   `DataBinder.DecodeEditLiteral` (`:3164`) — that is the second copy `feedback_one_rule_one_place` forbids, and
   `SR-13.18.40.3-9`'s PARTIAL verdict already records that `DecodeEditLiteral` **erases the literal's CLASS**
   before `PictureAnalyzer` can screen it. The substituted literal must arrive carrying its class or SR9 stays
   unenforceable on the new spelling as well.
3. `editingChar1` is PB568's shape, not this note's; land it in the same commit.

## Sweep — the narrow-`literal` class is wider than this clause

`literal` positions with no word-shaped sibling are the general shape of this defect. Measured on main
(`E:\Temp\claude\E--CobolSharp\49b17747-ce58-4386-8c49-ecb2ce644f8d\scratchpad\narrowlit.py`: every `.g4` line
matching a bare `literal` token with no `dataReference` / `identifier` / `arithmeticExpression` / `cobolWord` /
`unaryExpression` / `functionCall` / `valueClauseOperand` on the same line, comments stripped): **29 lines across
7 grammar files.** ⚠ That number is an UPPER BOUND and must not be quoted as a defect count — the heuristic is
LINE-scoped, so a `: literal` alternative whose sibling alternative sits on the next line is over-counted. What is
verified here is only the six positions in `CobolData.g4:451/455/456` plus literal-4 at `:665`. The rest is the
fixer's rule-level sweep, and the drift test that keeps it closed belongs with the fix: **a `.g4` operand written
as bare `literal` where the printed general format names a literal is a defect by construction**, and a generated
check can say so.
