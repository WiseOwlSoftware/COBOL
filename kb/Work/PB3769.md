# PB3769 — superseded merge-group runs are never cancelled

**Sites:** `.github/workflows/build-and-test.yml` (the new `supersede` job; `ci-gate`'s `needs`; the `concurrency` comment), `scripts/orchestrator/cancel_superseded.py` (`decide`, `unfinished_runs`, `sweep`, `main`, its `--self-test`), `scripts/orchestrator/queue_facts.py` (`LIVE_QUERY`, `live_heads`, its `--self-test`), `tests/Cobol.Net.Tests.Unit/LandingPipelineDriftTests.cs` (`TheMergeGroupRun_CancelsTheRunsTheQueueSuperseded_AndNothingElse`), `docs/rearchitecture/DESIGN-test-build-ci.md` §3.17.2 step 4, §3.17.6, §3.17.8.

## What happened (2026-10-25)

After #591 was ejected from the merge queue at 20:18Z, GitHub rebuilt every group behind it: each entry got a new
merge-group commit and a new workflow run. The runs of the old commits (40228927401, 40228888256, and later
40230142896, 40230142122, 40230639741) kept running, holding runners under the repository's concurrent-job limit beside
the new groups' runs, until the session cancelled them by hand with a one-off script.

## The defect

Nothing cancelled a run whose merge-group commit no queue entry heads any more. The workflow's `concurrency` group could
not: each merge group's ref is unique (`gh-readonly-queue/main/pr-<n>-<base sha>`), so a run never shares a group with
the run that replaced it, and `cancel-in-progress` was (correctly) only for `pull_request`.

## Landed (wave 20261502, group A)

Every merge-group run now starts with the `supersede` job (no `needs`, `if: github.event_name == 'merge_group'`), the
one job granted `actions: write` (plus `contents: read` for its sparse checkout of `scripts/orchestrator` and
`pull-requests: read` for the queue's entries). It runs `scripts/orchestrator/cancel_superseded.py` with the run's id
and head commit, which lists the unfinished merge-group runs (every status but completed) FIRST, then reads the head
commit of every current queue entry through `queue_facts.live_heads` (the one reader of the queue's facts; the order
matters, since a run created after the read would otherwise look superseded), and cancels each run of the queue on
main whose head commit heads no entry. It never cancels its own run or a live entry's, and ignores completed runs,
other events and other branches' queues. FAIL-SAFE: it cancels nothing when the queue cannot be read whole (a failed
or malformed read, no queue, a second page of entries), reads empty, or does not hold the run's own head commit; each
is a warning annotation. Every outcome exits 0 and the step is `continue-on-error`, so housekeeping never decides a
verdict. The replacement groups' runs are created at the moment of supersession, so they sweep the runs they replaced.

Probe on the live repository (dry run, 2026-10-25, own run 40231561214): 6 unfinished merge-group runs, 5 live
entries; the five live entries' runs KEEP, run 40230639741 (pr-596, still `queued`, its commit in no entry) CANCEL.

CI-invariant (PB1957): the job acts only on GitHub's queue, so no local leg can run it; it cannot turn CI red
(`continue-on-error`), and its decision is tested locally by its self-test, which every gate and CI's `audits` job
run through `scripts/self_tests.py`. `LandingPipelineDriftTests` holds the job's wiring and both scripts' arms.
