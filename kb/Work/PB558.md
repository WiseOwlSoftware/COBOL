# PB558

## Mechanism — value-clause-p2
LEVEL-88 ENTRIES ARE INVISIBLE TO THE REPORT-SECTION BINDER. src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs never inspects a level-number for 88 (the token does not occur in the file); its report-entry walk at :333-445 dispatches on pictureClause / usageClause / signClause / justifiedClause / blankWhenZeroClause / occursClause / valueClause and simply drops an 88 entry. The condition-name registry (DataBinder.cs:2105 BindCondition) is reached only from the data-description path, so a condition-name written in the report section is neither rejected (SR30) nor registered -- and a later reference to it binds to nothing and is staged loud at RUN time.

### Expected, from the standard
SR30 (13.18.63.3): "Condition-name and content-validation formats shall not be specified in the report section." (cite --check OK) A level-88 VALUE clause inside a report group description is nonconforming source and shall draw a compile-time diagnostic naming SR30.

```
$ python scripts/spec/cite.py --check 13.18.63.3 "Condition-name and content-validation formats shall not be specified in the report section"
  OK  §13.18.63.3 30)  (Syntax rules)
```

### Observed
MEASURED at --std 2023. Silence is the wrong answer twice over: the syntax-rule violation goes unreported, and because the entry is dropped rather than bound, a program that goes on to reference the condition-name compiles and then aborts at run time with a not-implemented exception -- the loud stage firing for source that should never have reached it. The content-validation half of the same sentence is already satisfied by the declined-facility pass (COBOLNET1708), which fires in the report section as it does elsewhere, so only the condition-name half is open. The --std 85 repro was blocked by an unrelated COBOLNET0900 gate on the `COL n` spelling; the report-entry walk carries no version predicate on this path, so the divergence is edition-invariant by construction.

## Landed 2026-09-20 — wave 41 (E) — NO-REPRO: the mechanism is gone, and the rule is enforced by two others

⛔ THE NOTE'S DEFECT DOES NOT REPRODUCE. Re-probed on this worktree's own `dotnet build CobolSharp.sln -c Debug`,
in BOTH placements (a level-88 under a printable `COL n` entry, and a level-88 directly under the level-01 report
group) and at `--std 85` as well as `--std 2023`:

```
pb558_a.cob(17,17): error COBOLNET1746: level-number 88 on 'C': report group description entries that are
  subordinate to an RD entry shall have level-numbers with the values 1 through 49 (ISO §13.18.33.3 SR4)
```

The entry is REJECTED, so the note's second measurement — a procedure-division reference to the dropped
condition-name compiling and then aborting at RUN time with a `NotImplementedCobolFeatureException` — cannot
occur either. The landing is **PB485, `f37da577b`, 2026-09-05, "the level-number had no domain, on either of its
two axes"**: `LevelNumberPass` now screens the level-number on both the section axis and the format axis over the
whole parse tree, before any binding.

WHY SR30 NEEDS NO SCREEN OF ITS OWN, stated so the absence does not read as an omission: both formats SR30 names
are level-88 formats (§13.18.63.3 SR33 — "Formats 3 and 5 may be specified only when the level-number of the
subject of the entry is 88"), and §13.18.33.3 SR4 bounds this section's level-numbers to 1 through 49. The
conjunction is exact. A third screen was written during this work — `DataBinder.Reports.BindReportEntries` grew a
level-88 arm reporting SR30 by name — and was DELETED, because it reported the same source line twice; its
diagnostic code was returned unused. The derivation now lives as a comment at that walk, so the next reader does
not re-add it.

The CONTENT-VALIDATION half of SR30's one sentence is answered separately, by the declined A.4.14 facility
(COBOLNET1708), in the report section exactly as elsewhere — measured by the note itself and unchanged.
