# PB3909 — function-reference-modification-refused: FUNCTION EXCEPTION-STATUS (1:3): reference modification of a no-argument function gives 'syntax error, unexpected :'

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S6) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\function-reference-modification-refused.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\function-reference-modification-refused\`.

## Summary

GnuCOBOL 3.2 refuses a reference modifier written directly after a standard intrinsic function that takes no
arguments, for the functions its scanner returns as the generic intrinsic-function token: EXCEPTION-FILE,
EXCEPTION-LOCATION, EXCEPTION-STATEMENT and EXCEPTION-STATUS. The parser takes the left parenthesis as the start of an
argument list and stops at the colon (`syntax error, unexpected :`). The standard treats that parenthesis as an argument
list only when the function permits arguments; these four permit none in the 2014 edition, so `(1:3)` is a reference
modifier. CURRENT-DATE and WHEN-COMPILED, which have their own tokens, accept the same form. Class: rejects legal ISO
source. Behind the parse error sits a second refusal (`cannot have reference modification`), recorded as the split
`function-reference-modification-refused--refmod-flag-off`; both must be fixed for the program to compile.

## Minimal test case

Free reference format (`-fformat=free`), 5 lines, written for this record (reduced from our fuzz witness fz02364,
night 3: `PERFORM UNTIL FUNCTION EXCEPTION-LOCATION(1:1) NOT = " "`, where cobc's only error is this one).

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. FREFMOD.
PROCEDURE DIVISION.
DISPLAY "[" FUNCTION EXCEPTION-STATUS (1:3) "]"
STOP RUN.
```

File: `E:\COBOL-coord\scratch\op\pb3838\records\function-reference-modification-refused.cob`. The same program with
EXCEPTION-LOCATION, EXCEPTION-STATEMENT or EXCEPTION-FILE and `(1:1)` (`E:\COBOL-coord\scratch\op\pb3838\work\s6\frm\r-*.cob`)
draws the same error; with CURRENT-DATE or WHEN-COMPILED it compiles; with RANDOM (numeric, and it permits an
argument) it is refused, correctly.

## Observed result

All three commands, exit code 1:

```
frefmod.cob:4: error: syntax error, unexpected :
```

With an empty argument list written first (`FUNCTION EXCEPTION-STATUS () (1:2)`, `work\s6\frm\paren.cob`) the parse
succeeds and the next check refuses it: `error: FUNCTION 'EXCEPTION-STATUS' cannot have reference modification`.

## Expected result (per ISO)

The program is legal and prints `[   ]` (no exception has been raised, so EXCEPTION-STATUS returns spaces).

- §8.4.3.1.2 Format 3 (checked): an identifier may be "identifier-1 reference-modifier-1", and identifier-1 may be a
  function-identifier (Format 1).
- §8.4.3.3.3 2) (checked): "If identifier-1 is a function-identifier, it shall reference an alphanumeric, boolean, or
  national function." §15.33.1 (checked): "The type of the function is alphanumeric." (EXCEPTION-STATEMENT §15.32.1,
  checked, the same; EXCEPTION-LOCATION §15.30.1, checked, the same.)
- §8.4.3.2.3 6) (checked): "If a function's definition permits arguments and a left parenthesis immediately follows
  function-prototype-name-1 or intrinsic-function-name-1, the left parenthesis is always treated as the left parenthesis
  of that function's arguments." EXCEPTION-STATUS's general format (§15.33.2) is `FUNCTION EXCEPTION-STATUS` with no
  arguments, so the rule does not apply and `(1:3)` is a reference modifier.
- §15.33.3 1): "If the last exception status indicates no exception, alphanumeric spaces are returned."

Edition: 2014. The 2009 committee draft that became ISO/IEC 1989:2014 (CD 1.2) has the same function-identifier
syntax rule 6, the same reference-modification syntax rule 2 (8.4.2.3.2 there), and EXCEPTION-STATUS, -STATEMENT,
-LOCATION and -FILE with no arguments (15.25 to 15.30). EXCEPTION-FILE gained an optional argument only in 2023 (§E.3.3
25), checked), so under a 2023 dialect `FUNCTION EXCEPTION-FILE (1:1)` is an argument list and is rightly refused;
under -std=cobol2014 it is a reference modifier.

Edition as recorded by the adjudicator: 2014 (functions from 2002). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Our compiler (WiseOwl)

WiseOwl COBOL (built from main 6ed90bd1c), `cobol frefmod.cob --std 2014 --source-format free -o frefmod.dll`, then
`dotnet frefmod.dll`: compile exit 0, run exit 0, output `[   ]`. EXCEPTION-LOCATION and EXCEPTION-STATEMENT with
`(1:1)`: `[ ]`. WiseOwl refuses RANDOM `(1:1)` (COBOL1543, citing 8.4.3.2.3 SR6).

Lead on our side (not a GnuCOBOL matter): at `--std 2014` WiseOwl also refuses `FUNCTION EXCEPTION-FILE (1:1)` with
COBOL1543 ("the '(' after the name of a function that takes arguments is ALWAYS its argument list"), applying the
2023 optional argument (§E.3.3 25)) to the 2014 edition; `docs/VERSION_CHANGE_REFERENCE.md` row 68 marks that edition
gate `new-feature-gate <!-- todo -->`. Program: `E:\COBOL-coord\scratch\op\pb3838\work\s6\frm\r-EXCEPTION-FILE.cob`.

The night-3 hang of the witness on WiseOwl is the program's own loop (inside ON SIZE ERROR no exception status is set,
so EXCEPTION-LOCATION stays a space and `PERFORM UNTIL ... NOT = " "` never ends), not a compiler fault.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/parser.y`, rule `function`, alternative `FUNCTION_NAME func_args func_refmod`: for every function the scanner
  returns as the generic `FUNCTION_NAME` token, the first parenthesised group is parsed by `func_args` as an argument
  list (`TOK_OPEN_PAREN exp_list TOK_CLOSE_PAREN`), whether or not the function permits arguments, so `(1:3)` fails at
  the colon. The no-argument functions with their own tokens (`func_no_parm`: `CURRENT_DATE_FUNC`, `WHEN_COMPILED_FUNC`)
  go straight to `func_refmod` and work. Giving the no-argument exception functions that path (or deciding in the
  scanner by the `function_list` argument counts, which are 0 and 0 for all four) is the fix.
- `cobc/reserved.c`, `function_list`: the four entries carry argument counts 0/0 and the reference-modification flag
  0; see the split record for the flag.

`func_args` for functions with no arguments. Once that parses, `cb_build_intrinsic` refuses the reference modification
too (`cannot have reference modification`, from the function_list flag); that needs the companion fix.
