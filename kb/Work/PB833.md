# PB833 — the one §9.1.15 rule a `flock` cannot say, and the mechanism that can

## What the standard requires

```

  OK  §9.1.15 2)  (Sharing mode)
      "The sharing with read only mode restricts concurrent access to a physical file through file connectors
       other than this one, to input mode. …"
python scripts/spec/cite.py --check 9.1.15 "The successful opening of a file establishes a file lock for the applicable sharing rules"
  OK  §9.1.15 3)  (Sharing mode)
python scripts/spec/cite.py --check 9.1.15 "Multiple paths of access may exist in the same runtime element"
  OK  §9.1.15 3)  — "… or runtime elements in different run units."
```

Rule 2's audience is *file connectors*, and §9.1.15 says in so many words that those may live in **different run
units** — so "restricts concurrent access … to input mode" binds another run unit, not only another connector of
this one. Table 19 answers the in-run-unit half and conforms for every organization; the file lock is the other
half.

## The measured mechanism

`tests/_shared/HostCapability.Sharing` establishes real handles on a real file and reports what the host did
([[PB795]] built it, and `FileLockPostureDriftTests.TheHostsShareModeSemanticsAreTheDocumentedOnes` asserts the
measurement rather than a platform literal). Measured 2026-09-06 and unchanged:

```
Linux (WSL, uid 1000)   FileShare.Read admits an outside reader=True, refuses an outside writer=False
Windows                 FileShare.Read admits an outside reader=True, refuses an outside writer=True
```

.NET implements `FileShare` on Unix with an advisory `flock`, which has exactly two states: `FileShare.None`
takes `LOCK_EX` and **every other value takes `LOCK_SH`**. `LOCK_SH` is compatible with `LOCK_SH`, so a
connector holding `FileLockPosture.OfSharingMode(FileSharing.ReadOnly)` = `FileShare.Read` cannot refuse another
run unit's writer. The undetermined implementor default shares that posture ([[PB322]]), so the rule is missing
for the clause-less case too — which is most programs.

**The harm is the same shape [[PB771]] just removed for the keyed organizations, one platform along:** a second
run unit's `OPEN EXTEND` or `OPEN I-O` succeeds with '00' where §9.1.15 2) makes it unsuccessful, both run units
write, and for a keyed file the later CLOSE rewrites the store whole.

## ⛔ Why this is a DEFECT and not the determination it is currently written as

`docs/rearchitecture/DESIGN-runtime-library.md` records it as an operating-environment determination: *"on a host
whose sharing is advisory and binary, §9.1.15's file lock degrades rule 2 toward rule 3"*. The **binary** half is
a fact about `flock`; the **"advisory and therefore unavoidable"** half is not, and that is the premise to
correct:

- Advisory is ENOUGH here. §9.1.15 3) binds *"other RUN UNITS"*, and every COBOL.NET run unit reaches the file
  through this runtime, so every one of them takes whatever lock the runtime takes. A non-COBOL process is not a
  run unit and the standard asks nothing about it.
- `fcntl` region locks (`F_SETLK` with `F_RDLCK` / `F_WRLCK`) are advisory in exactly that same way and are
  **per-access**, which is the property `flock` lacks. The three rules map onto them directly: NO OTHER ⇒ a write
  lock (refuses a foreign read lock AND a foreign write lock — rule 1's *"exclusive access"*); READ ONLY and the
  undetermined default ⇒ a READ lock (compatible with another read lock, incompatible with a write lock — rule
  2's *"restricts … to input mode"* exactly); ALL OTHER ⇒ none (rule 3's *"allows concurrent access"*).
- So the sentence *"neither `flock` state expresses rule 2"* is true and the conclusion drawn from it — that the
  rule is unexpressible — does not follow. ⚠ **This paragraph is a DERIVATION and not a measurement**; the design
  work owes a probe under WSL that establishes the three-way compatibility above before any code is written,
  exactly as [[PB795]] insists (`feedback_reachability_is_measured_not_deduced`).

## The fix shape

The posture is already derived in ONE place (`FileLockPosture`, applied by `FileRegistry.SyncHostPostures`) and
every organization now holds a handle to carry it ([[PB771]]), so the structure this needs already exists: what
is missing is a second EXPRESSION of the same derived posture for hosts whose `FileShare` cannot carry it —
taken on the connector's own handle, rebuilt by `Reposture` alongside it, and released with it. ⛔ It must be
decided in `DESIGN-runtime-library.md` first (CLAUDE.md rule 2), and the platform capability must stay MEASURED
rather than switched on an `OSPlatform` literal, which is [[PB795]]'s whole subject.

⚠ **Do not widen the posture to `FileShare.None` to compensate.** That refuses the reader rule 2 explicitly
admits, trading an under-refusal for an over-refusal of access the standard grants; the design doc is right about
that and it stays.

**Survey before choosing** (`feedback_survey_compilers_on_latitude`): GnuCOBOL is the differential oracle here and
is GPL — read its BEHAVIOUR, never its sources.

## The row

`GR-9.1.15-2` is **PARTIAL** and this note is why. Its two siblings `GR-9.1.15-1` and `GR-9.1.15-3` are CONFORMS:
rule 1 is `LOCK_EX`, the one thing a binary advisory lock CAN say, and rule 3 is permissive, so neither depends
on the missing expression. Closing this row closes §9.1.15 whole.
