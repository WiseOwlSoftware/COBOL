# PB5794 - the KEY of READ and START on an indexed file is matched to a record key by offset and width only, so an item of another class at the key's position is accepted (every edition)

**What is wrong.** A `PIC 9(4)` item at the character positions of the `X(4)` record key, in a second record description of the file, is accepted as the KEY of `READ ... KEY IS` and of `START ... KEY IS`, and the program runs (`FS=00`, the record is read by the prime key), at `--std 85` and at `--std 2023`. The match compares offset and width only. The control with a shorter numeric item (`PIC 9(3)`, k3) is refused (`COBOL0862`), because that item reaches the class, category and usage test; the positional arm returns on equal width before that test is asked. 2023 is wrong the same way (cause b): the 2023 rows `SR-14.9.30.3-11` and `SR-14.9.41.3-6` are re-recorded non-conforming by a registrar.

**Why no reading admits the numeric twin.** For START, `§1985:IX.4.7.3 SR4` admits an item that is the one specified in a RECORD KEY or ALTERNATE RECORD KEY clause, or any data item of category alphanumeric at a record key's leftmost position; a numeric item is neither. For READ, `§1985:IX.4.5.3 SR2` requires the name of "a data item specified as a record key"; on the strict reading only the RECORD or ALTERNATE KEY data-name qualifies, and on the implicit-key reading (`§1985:IX.2.7.4 GR3`) the implicit key is the character positions of an alphanumeric data-name-1, which a numeric item with its own description cannot name (`§1985:IX.2.7.3 SR2` makes every key alphanumeric). At 2023, `§2023:14.9.30.3 SR11` says data-name-1 "shall be specified in the RECORD KEY clause or an ALTERNATE RECORD KEY clause", and `§2023:14.9.41.3 SR6b` requires the key's class, category and usage.

**Lead, not ruled (nobody has ruled it).** `k4.cob`: an ALPHANUMERIC item of the same width (`R2-ALP PIC X(4)` at the key's positions) is accepted as the KEY of READ at `--std 85` and `--std 2023`. `§1985:IX.4.5.3 SR2` ("specified as a record key") and `§2023:14.9.30.3 SR11` ("specified in the RECORD KEY clause") read strictly refuse it; the implicit-key reading (`§1985:IX.2.7.4 GR3`; the 2023 rule `12.4.5.12.4 GR4` the checker names) that kb/Work PB354 chose admits it. The checker left it as an open reading; it is not the contradiction of the two rows.
