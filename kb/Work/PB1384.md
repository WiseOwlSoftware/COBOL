# PB1384 — LANDED (wave 1004 B)

Depends on PB1355 (the strict/non-strict split is what turns the truncated COPY into a comment).

## The rule (every citation re-run by the registrar)

> within a source text manipulation statement …

`python scripts/spec/cite.py --check 7.3.3 "within a source text manipulation statement"` → `OK  §7.3.3 8) b)  (Syntax rules)`

## Finding — compiler-directives (silent)

directive-inside-text-manipulation-statement: the merged CC+COPY driver (ConditionalCompilationProcessor.Render) flushes the pending COPY block at every '>>' line on the stated premise 'a COPY can never span a directive line', but nothing diagnoses the violation. A COPY statement split by a directive is then resolved from a truncated block: no text-name is read, the non-strict Frontend path (CopyProcessor strict:false) turns the not-found result into a comment with no diagnostic, and the COPY's remaining words ('cb3.') are left for the parser, where they read as a paragraph-name. A directive inside a REPLACE statement is likewise accepted.

**Rows:** SR-7.3.3-8

**Repro:**

```
Copybook cb3.cpy: '           DISPLAY "CB3 AA".' Program: PROCEDURE DIVISION. '           COPY' / '       >>DEFINE VV AS 1' / '               cb3.' / '           STOP RUN.' (E:\Temp\claude\E--CobolSharp\a700c052-f9e4-4942-84ff-a13c7505d6ec\scratchpad\adj-d2\out\probe\cd\W4C.cob; W4.cob uses >>TURN, W4D names a nonexistent copybook, W2.cob puts a >>DEFINE inside 'REPLACE ==AA== BY' ... '==BB==.').
```

**Expected from the spec:** §7.3.3 SR8: a compiler directive may be specified anywhere 'except ... b) within a source text manipulation statement' (cite.py --check 7.3.3 OK). W4C, W4, W4D and W2 must each be rejected with a diagnostic naming the directive inside the COPY/REPLACE statement.

**Observed:** W4C and W4 compile clean, run, and print NOTHING - the copybook is silently not incorporated; W4D (copybook does not exist) is equally silent and prints 'W4D'; W2 compiles clean. W1 and W3 are rejected only incidentally (COBOL0001 / COBOLNET1641). Aggravating sibling, separately worth a note: a plain 'COPY nosuch.' with a nonexistent copybook compiles and runs with NO diagnostic in the default (non-NIST) mode (W4E prints 'W4E'), because Frontend.Preprocess constructs CopyProcessor with strict:false - §7.2.3.4 GR1 'Text-name-1 or literal-1 identifies the library text to be processed by the COPY statement.'

**Code site:** src/Cobol.Net.Frontend/Preprocessor/ConditionalCompilationProcessor.cs#Render (the Flush at a directive line); src/Cobol.Net.Frontend/Preprocessor/CopyProcessor.cs#ResolveOneCopy (NotFound fallback, reported only when _strict); src/Cobol.Net.Frontend/Pipeline/Frontend.cs#Preprocess (strict: false)

Diagnose a directive line while a COPY/REPLACE statement is open (the driver knows — it flushes there); with PB1355 the truncated COPY can no longer degrade to a comment. Negative golden: `COPY` / `>>DEFINE X AS 1` / `cb3.`.

**Rows claimed:** SR-7.3.3-8

## Landed (wave 1004 B, 2026-10-02)

Re-probed on this tree: the note's silent acceptance was already half gone (PB1355 landed: `COPY` / `>>DEFINE` / `cb3.` now
draws COBOLNET2449 "text-name-1 is missing", and a missing copybook is CBL3620), but only as an INCIDENTAL parse error
that never names the directive; a directive inside a REPLACE statement (`w2.cob`) still compiled clean.

**Fix.** COBOLNET2697 (`DiagnosticCatalog.DirectiveWithinTextManipulationStatement`, §7.3.3 SR8 b), `cite.py --check`ed).
The merged driver's `Render` ends its block at every directive line, so that is where the question is answerable: before
flushing, it asks `CopyProcessor.OpenStatementAt` whether the text since a COPY or REPLACE keyword has reached its
separator period (the statements' own `TextWordScanner` words, pseudo-text delimiters toggling so a period inside
pseudo-text ends nothing). The open statement's text is carried across directive lines, so a statement split by several is
reported at each. One walk for both statements, so COPY and REPLACE cannot disagree.

**Not changed, on purpose.** The truncated COPY still draws its own COBOLNET2449 (and, for `COPY x` / directive / `.`, a
stray-period parse error) after the new diagnostic. Holding the block unflushed would stop that cascade but shifts the
output frame the §14.9.28.4 GR14 encounter lines are keyed to; the compilation has already failed, so the first error
(which names the directive) is the one a user acts on. The `COPY nosuch.` aggravating sibling the note mentions
(non-strict not-found comment) is gone: PB1355 made it CBL3620.

**Sibling sweep (which arm).** Two ways text-manipulation statements meet a directive: COPY (expanded per block at
`Flush`) and REPLACE (applied after the whole render over text whose consumed directive lines are blank). The driver-level
check is the one place that sees both; a directive a downstream stage keeps (`>>TURN`) is covered by the same check and
is also what `ScreenOperandPair` SR10 reports INSIDE pseudo-text (a different rule: §7.2.3.3 SR10 / §7.2.4.3 SR10).

Witnesses: `conformance:negative/pb1384-directive-within-copy`, `pb1384-directive-within-replace` (the copybook
`PB1384CB.cpy` sits beside them); unit `DirectiveWithinStatementTests`. Row closed: SR-7.3.3-8 (batch `w1004b-pb1384`).

**For the next implementer.** `ConditionalCompilationProcessor.cs#Render` asks `CopyProcessor.cs#OpenStatementAt` before each `Flush()`; extend that one walk (it is the statements' own `TextWordScanner` words) rather than writing a second statement-end rule. Tests run through `ConditionalCompilationProcessor.ProcessWithCopy` because `Cobol.Net.Frontend` exposes its internals only to the stale name `CobolSharp.Tests.Unit` (the InternalsVisibleTo in its csproj), so a new test cannot call an `internal` member of the front end directly.
