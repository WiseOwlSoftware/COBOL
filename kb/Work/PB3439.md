# PB3439 — the Linux landing red is not a "previous red" for the next plan

Filed 2026-10-19 by the enqueue clerk from `E:\COBOL-coord\scratch\reports\w1129g-PB2500-report.md`, "New defects found".
Register check: a grep of kb/Work by `read_previous_run` and `previous red` found PB3022 item 8 (a re-gate runs the previous
reds) and PB3247/PB3131 (what leg 1 plans from a diff); none says where the previous reds are read from. The other causes of
the same report went to PB3247 as a witness.

**Mechanism.** PB3022 item 8 makes a re-gate after a fix run the previous reds first. `scripts/gate_plan.py:221`,
`read_previous_run`, builds that set from the trx files in ONE run directory, the Windows gate's. A red found only by the
landing's Linux gate (here `EveryWordAdmittingLiteralSlot_IsWitnessedByAGolden_OrArgued`, found by the Linux unit leg) is not
in it, so the finisher's re-gate (run 20261019T192753Z-6de1c5) left the case in leg 2 although its diff edited that test file.

**Fix shape.** Read the Linux gate's reds too (its trx or its red list, from the evidence directory the gate already keeps),
through the same function, with a self-test whose only red is in the Linux directory.
