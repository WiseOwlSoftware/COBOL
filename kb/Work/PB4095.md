# PB4095 — move-all-boolean-literal-refused: -std=cobol2014: MOVE ALL B"1" TO a PIC 1 item is refused with "invalid MOVE statement"

Filed 2026-10-30 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-20261029-224533`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

Under `-std=cobol2014`, cobc 3.2 refuses `MOVE ALL B"1" TO item` with "invalid MOVE statement" when the receiving
item is a boolean item (PIC 1, with or without USAGE BIT). The figurative constant ALL boolean-literal is category
boolean and a boolean to boolean MOVE is valid, so the statement is legal. The same statement is refused with a
`PIC X(4)` receiver too, so the refusal follows the sending ALL boolean literal, not the receiver. `MOVE B"1111" TO
item` (no ALL) and `MOVE ALL "1" TO item` (an alphanumeric literal after ALL) compile. Found by the differential fuzz
run fuzz-20261029-224533 (fz05281: `MOVE ALL B"1" TO WS-GROUP-ITEM (1)`, lines 29 and 31, on PIC 1 USAGE BIT items).
The cause looks like the one PB3913 and PB3922 record (a boolean literal is held as a numeric literal); this record is
the refusal that cause produces, where those notes record wrong values.

## Minimal test case

Free-form reference format (`-free`).

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. ALLB.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 WS-D PIC 1(4) VALUE B"0000".
PROCEDURE DIVISION.
MAIN-PARA.
    MOVE ALL B"1" TO WS-D
    DISPLAY "[" WS-D "]"
    STOP RUN.
```

## Environment

- `cobc (GnuCOBOL) 3.2.0`, WSL2 Ubuntu on Windows 11.
- Compiled with `cobc -x -free -std=cobol2014 -o p prog.cob`; nothing ran, because compilation failed.
- Control: the same program with `MOVE B"1111" TO WS-D` in place of the MOVE ALL, saved as `c.cob`, compiled with
  `cobc -x -free -std=cobol2014 -o c c.cob` (exit 0) and run as `./c`.

## Observed result

```
prog.cob: in paragraph 'MAIN-PARA':
prog.cob:8: error: invalid MOVE statement
    6 | PROCEDURE DIVISION.
    7 | MAIN-PARA.
    8 >     MOVE ALL B"1" TO WS-D
    9 |     DISPLAY "[" WS-D "]"
   10 |     STOP RUN.
```

Exit code 1. The same error comes for a `PIC 1(4) USAGE BIT` receiver (after the warning `USAGE BIT is not implemented
[-Wpending]`), for a `PIC X(4)` receiver, and with `-std=default` and `-std=cobol2002`. The control program compiles
and prints `[0015]` (the PB3913 wrong value), exit code 0. `MOVE ALL "1" TO WS-D` in place of the MOVE ALL compiles and
prints `[1111]`.

## Expected result (per ISO)

- §8.3.3.6.3 2): "Literal-1 shall be an alphanumeric, boolean, or national literal". `ALL B"1"` is a legal
  figurative constant.
- §8.3.3.4.4 2): "Boolean literals are of the class and category boolean." `B"1"` is not a numeric literal.
- §13.18.40.4 8): "To define an item as boolean, character-string-1 shall contain only one or more occurrences of the
  symbol '1'", and §8.5.2.5 1) makes such an item of category boolean: "An elementary data item described as boolean
  by its PICTURE character-string." WS-D (PIC 1(4)) is a boolean item.
- §14.9.25.4 7): "The category of figurative constants when used in the MOVE statement depends on the category of the
  receiving operand"; its Table 17 makes ALL literal, where literal is boolean, of category boolean whatever the
  receiving operand.
- §14.9.25.3 10): "table 16, Validity of types of MOVE statements, specifies the validity of the move"; Table 16
  marks a boolean sending operand to a boolean receiving operand Yes (and to an alphanumeric receiving operand Yes, so
  the `PIC X(4)` variant is legal as well). The only MOVE rule that limits a figurative constant to a boolean item,
  §14.9.25.3 7), reads "Any figurative constant for which the associated character or characters are not boolean
  characters shall not be moved to a boolean data item."; the character of `ALL B"1"` is the boolean character 1, so
  the rule does not forbid it. The rule cobc applies (ALL with a numeric literal is invalid) is right for a numeric
  literal, which §8.3.3.6.3 2) does not allow after ALL, and does not apply to a boolean one.
- §8.3.3.6.4 2): the string "is repeated character by character until the size of the resultant string is greater
  than or equal to the number of character positions in the associated data item", so WS-D becomes 1111 and the
  program prints `[1111]`.
- Edition: the clause and table numbers above are those of ISO/IEC 1989:2023. The 2009 committee draft that became
  ISO/IEC 1989:2014 (CD 1.2) carries the same rules in the same words (it numbers the two MOVE tables 17 and 18), and
  boolean literals, boolean items and the ALL boolean-literal figurative constant are already in the 2001 final
  committee draft of ISO/IEC 1989:2002; `-std=cobol2014` claims 2014.

## Our compiler

WiseOwl COBOL (fresh judge `E:\tmp\fuzz-judge-20261030\cobol.exe`, `--std 2014 --source-format free`) compiles the
program with no diagnostic and prints `[1111]`, exit code 0. With a `PIC 1(4) USAGE BIT` receiver, and with a
`PIC X(4)` receiver, it also prints `[1111]`.

## Fix site

- `cobc/scanner.l`, function `scan_b` (line 1844): a boolean literal `B"..."` is returned as
  `cb_build_numeric_literal` of its binary value, under the comment at line 1930 that a boolean literal should likely
  be built instead.
- `cobc/typeck.c`, function `validate_move` (line 10749), the `CB_TAG_LITERAL` arm, class `CB_CLASS_NUMERIC`
  (line 10867): a literal with its `all` flag set goes to `invalid` (line 10872). Because of `scan_b`, `ALL B"1"`
  reaches this arm as an ALL numeric literal, whatever the receiver; that the `PIC X(4)` receiver is refused the same
  way and `MOVE ALL "1"` is accepted fits this arm. Building a boolean literal in `scan_b` (the PB3913 fix) or handling
  a boolean literal before the numeric arm would let the move through.

## Upstream state

unreported; tracker not yet searched. The 3.2 NEWS lists "more literal types added, numeric boolean etc." and the
`scan_b` comment names the missing boolean literal; neither names the MOVE ALL refusal. PB3913, the record of the same
root cause, is reported as https://sourceforge.net/p/gnucobol/feature-requests/303/; its record does not name this
refusal.

## Draft issue

**Title:** -std=cobol2014: MOVE ALL B"1" TO a PIC 1 item is refused with "invalid MOVE statement"

GnuCOBOL 3.2.0 on WSL2 Ubuntu, `cobc -x -free -std=cobol2014 -o p prog.cob`.

The program below fails to compile, exit code 1:

```
prog.cob: in paragraph 'MAIN-PARA':
prog.cob:8: error: invalid MOVE statement
    6 | PROCEDURE DIVISION.
    7 | MAIN-PARA.
    8 >     MOVE ALL B"1" TO WS-D
    9 |     DISPLAY "[" WS-D "]"
   10 |     STOP RUN.
```

Expected: the program compiles and prints `[1111]`. ISO/IEC 1989:2023 allows a boolean literal after ALL
(§8.3.3.6.3 2)), makes a PIC 1 item boolean (§13.18.40.4 8), §8.5.2.5 1)), gives the figurative constant ALL
boolean-literal the category boolean in a MOVE (§14.9.25.4 7), Table 17), and its Table 16 (§14.9.25.3 10)) allows a
boolean to boolean move; §14.9.25.3 7) forbids only a figurative constant whose characters are not boolean
characters. The committee draft that became ISO/IEC 1989:2014 has the same rules (its tables are numbered 17 and 18).
`MOVE B"1111" TO WS-D` and `MOVE ALL "1" TO WS-D` compile, so only ALL with a boolean literal is refused. The same error
comes for a `PIC 1(4) USAGE BIT` receiver, for a `PIC X(4)` receiver (boolean to alphanumeric is also valid in
Table 16), and with `-std=default` and `-std=cobol2002`.

Cause, as read in the source: `scan_b` (cobc/scanner.l) builds a boolean literal as a numeric literal, and
`validate_move` (cobc/typeck.c) treats an ALL numeric literal as invalid. This is the same root as
https://sourceforge.net/p/gnucobol/feature-requests/303/.
