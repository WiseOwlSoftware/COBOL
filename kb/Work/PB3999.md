# PB3999 — length-of-reference-modified-argument: FUNCTION LENGTH of a reference-modified item returns the length of the whole item (LENGTH (X (1:5)) gives 10 for PIC X(10))

Filed 2026-10-28 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-20261027-215606`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

`FUNCTION LENGTH (WS-CHAR (1:5))`, where WS-CHAR is `PIC X(10)`, returns 10 instead of 5. cobc folds LENGTH (and
BYTE-LENGTH) of any data-item argument to the size of the item's data description at compile time and does not look
at the reference modification, so a constant length (1:5), a variable length (1:WS-P) and an omitted length (3:) all
give 10. cobc issues no diagnostic. Class: wrong output. Fuzz night 2026-10-27/28: fz00335 (signature
OUTPUT_DIFFERS:8.8.4.10, `IF NOT WS-LEN = 5 DISPLAY "LENGTH ERROR"` after `COMPUTE WS-LEN = FUNCTION
LENGTH(WS-CHAR(1:5))`).

## Minimal test case

Free reference format (`-fformat=free`), 15 lines, written for this record.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. LENREF.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 WS-CHAR PIC X(10) VALUE SPACES.
01 WS-P    PIC 9(2) VALUE 5.
01 WS-LEN  PIC 9(2) VALUE 0.
PROCEDURE DIVISION.
    COMPUTE WS-LEN = FUNCTION LENGTH (WS-CHAR (1:5))
    DISPLAY "1 " WS-LEN
    COMPUTE WS-LEN = FUNCTION LENGTH (WS-CHAR (1:WS-P))
    DISPLAY "2 " WS-LEN
    COMPUTE WS-LEN = FUNCTION LENGTH (WS-CHAR (3:))
    DISPLAY "3 " WS-LEN
    STOP RUN.
```

File: `E:/COBOL-coord/scratch/fuzz-triage/fuzz-20261027-215606/records/length-of-reference-modified-argument.cob`.

## Observed result

Compile exit code 0, no cobc diagnostic (the only compile-time message is the C compiler's "'_FORTIFY_SOURCE'
redefined" warning, from the Ubuntu package's build flags). Run exit code 0, output:

```
1 10
2 10
3 10
```

## Expected result (per ISO)

Output `1 05`, `2 05`, `3 08`.

- §15.50.3 1) (checked): "Argument-1 shall be an alphanumeric, national, or boolean literal; a data item of any class
  or category; a based entry; or a type-name." §8.4.3.3.3 5) (checked): "Unless otherwise specified, reference
  modification is allowed anywhere an identifier referencing a data item of class alphanumeric, boolean, or national
  is permitted"; the LENGTH rules specify nothing otherwise, so the argument is legal.
- §8.4.3.3.4 5) (checked): "Reference modification creates a unique data item that is a subset of the data item
  referenced by identifier-1." Its rule c): "The evaluation of length specifies the number of bit positions or
  character positions of the data item to be used in the operation", and "If length is not specified, the unique data
  item extends from and includes the position identified by leftmost-position up to and including the rightmost
  position of the data item referenced by identifier-1" (positions 3 to 10, 8 positions).
- §15.50.4 3) (checked): "If argument-1 is other than category boolean or usage national, the returned value is an
  integer equal to the length of argument-1 in alphanumeric character positions." Argument-1 is the unique data item:
  5, 5 and 8 positions.

Edition: reference modification is a COBOL 1985 feature and the LENGTH function a 1989 intrinsic; the 2009 committee
draft for ISO/IEC 1989:2014 (CD 1.2, std.txt) carries the same rules (15.46.2 1), 15.46.3 3) and "Reference
modification creates a unique data item that is a subset of the data item referenced by identifier-1", line 6070).

## Our compiler

## Fix site

GnuCOBOL 3.2 source, read observationally: `cobc/tree.c`, `cb_build_intrinsic` (line 6990), the `case CB_INTR_LENGTH:
case CB_INTR_BYTE_LENGTH:` arm (line 7082). For an argument that satisfies `CB_REF_OR_FIELD_P`, it takes
`CB_FIELD_PTR (x)->size` and returns `cb_build_numeric_literal` of it whenever the field is not of variable size and not
ANY LENGTH; it never consults the reference's offset and length (the reference-modification part of the
`cb_reference`), so the folded literal is the size of the whole field. A reference-modified argument needs the
reference-modification length (a literal when constant, the run-time length otherwise) instead of the field size.

## Draft issue

**Title:** FUNCTION LENGTH of a reference-modified item returns the length of the whole item (LENGTH (X (1:5)) gives 10 for PIC X(10))

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1), x86_64 Linux.

Steps: `cobc -x -free -std=cobol2014 -o p lenref.cob && ./p` with

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. LENREF.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 WS-CHAR PIC X(10) VALUE SPACES.
01 WS-P    PIC 9(2) VALUE 5.
01 WS-LEN  PIC 9(2) VALUE 0.
PROCEDURE DIVISION.
    COMPUTE WS-LEN = FUNCTION LENGTH (WS-CHAR (1:5))
    DISPLAY "1 " WS-LEN
    COMPUTE WS-LEN = FUNCTION LENGTH (WS-CHAR (1:WS-P))
    DISPLAY "2 " WS-LEN
    COMPUTE WS-LEN = FUNCTION LENGTH (WS-CHAR (3:))
    DISPLAY "3 " WS-LEN
    STOP RUN.
```

Observed: `1 10`, `2 10`, `3 10` (no diagnostic from cobc, exit code 0).

Expected: `1 05`, `2 05`, `3 08`. ISO/IEC 1989:2023 8.4.3.3.4 rule 5 (the same rule in the 2014 edition's committee draft): "Reference
modification creates a unique data item that is a subset of the data item referenced by identifier-1", whose length is
the reference-modification length (or the rest of the item when the length is omitted); 15.50.4 rule 3: LENGTH returns
"the length of argument-1 in alphanumeric character positions".

Cause, as read in the source: cobc/tree.c cb_build_intrinsic, case CB_INTR_LENGTH / CB_INTR_BYTE_LENGTH, folds the
function to the field's size for any field reference without checking whether the reference is reference-modified.
