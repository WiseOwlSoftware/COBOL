# PB3467 — should DISPLAY of a scaled numeric item print the decimal point?

## ✅ THE OWNER'S ANSWER — 2026-10-21 ~22:12 PDT (attended operator session), verbatim: **"yes"**

The question answered: "Should DISPLAY of a scaled or signed numeric item follow GnuCOBOL's default (`00012.50`,
`+00012.50`), with IBM's digits-only form available behind a compile option?" So the DEFAULT conversion of
§14.9.11.4 GR1 (Annex A.1 item 56) for a numeric item is GnuCOBOL 3.2.0's default-configuration form, and today's
digit image (digits as stored, the sign overpunched per `--sign-encoding`) becomes the option's other value. The
implementation is kb/Work **PB3505**.

The evidence the owner decided on (the session's survey, 2026-10-21):

| Compiler | `9(5)V99` = 12.5 | `S9(5)V99` = +12.5 / −12.5 | Source |
|---|---|---|---|
| GnuCOBOL 3.2.0 `default`, `cobol85`, `cobol2002`, `cobol2014`, `mf` | `00012.50` | `+00012.50` / `-00012.50` | run (WSL, `cobc -x -std=…`) |
| GnuCOBOL 3.2.0 `ibm`, `mvs` | `0001250` | `0001250+` / `0001250-` | run |
| IBM Enterprise COBOL 6.4 | digits, no point (inferred from "No other categories of data require conversion") | trailing overpunch under the default `DISPSIGN(COMPAT)`; leading separate sign under `DISPSIGN(SEP)` | IBM Docs, DISPLAY statement and DISPSIGN pages |
| Micro Focus | not documented | a separate sign (GR 2 of an older mirrored Language Reference page) | unverified: the current documentation did not load |

The same probe also showed, under GnuCOBOL's default: `S9(3)V99 SIGN LEADING SEPARATE` = −1.5 prints `-001.50`,
`9(3)V99 COMP` = 1.5 prints `001.50`, and `9(3)PP` = 1200 prints `01200` (under `ibm`: `-00150`, `0000000150`, `012`).

Why the note's "the two precedents pull apart" was wrong: PB803 decided the STORAGE representation of an unseparated
sign (§13.18.52.4 GR4, A.1 item 177), a different latitude; GnuCOBOL itself stores an overpunched sign and still
DISPLAYs `+00012.50`. For THIS latitude, DOC-A.1-56 already followed GnuCOBOL (numeric literals as written, PB1643;
a signed non-DISPLAY item's leading `-`), so CLAUDE.md rule 1's precedence and the existing determination agree.

Observed: DISPLAY of `PIC 9(5)V99` holding 12.5 prints `0001250`; signed prints `000125{`. GnuCOBOL's pretty-display
prints `00012.50` and `+00012.50`.

Governing text: §14.9.11.4 GR1 leaves the representation to the implementor. PB803 settled the SIGN convention
(IBM / Micro Focus over-punch, option `--sign-encoding`). CLAUDE.md rule 1 orders latitude as ISO, then GnuCOBOL, then
IBM / Micro Focus, which would put the decimal point with GnuCOBOL; PB803 put the sign with IBM by owner decision, so
the two precedents pull apart.

Question for the owner: print the decimal point for a scaled item (GnuCOBOL), or keep the unpunctuated digit image
(IBM / Micro Focus)? Consequence: either answer is a default for every program; changing it alters every golden that
displays a scaled item, and the answer may warrant a compile option like PB803's. No code change until decided.
