# PB927 — OPEN — a file a sweep cannot see has never been swept

Source: the `PB465` report, "New defects". The one instance was FIXED there; the MECHANISM is filed here.

## The measurement (as recorded by the implementer, before their fix)

```
$ grep -rn "UpByReal" --include=*.cs tests/
Binary file tests/Cobol.Net.Tests.Unit/CobolPtrTests.cs matches
```

instead of the lines. The cause was `CobolPtr.Allocate(3, '\0', …)` written with a LITERAL NUL character
rather than the escape — the file's line 102 before that change.

## Why this is a defect and not a typo

Every sibling sweep this project runs is a `grep` over `src/` and `tests/`. A file that greps as BINARY is
invisible to all of them, silently — which is part of why that arm's tests were never re-read against the
emitter. CLAUDE.md rule 4 requires the sibling sweep; a file grep cannot read has been exempt from every
sweep ever run, and nothing reported it.

The cause is mechanical and will recur: `feedback_tool_input_unicode_escapes_decoded` — the harness decodes
`\uXXXX` in tool inputs into RAW characters, so an agent writing `'\u0000'` writes a NUL. The memory entry
already says "byte-check after scripted writes"; a memory is not a gate.

## The fix

1. A scan of `src/` and `tests/` for NUL bytes (and, while the walk is there, for a UTF-8 BOM — the
   `utf-8-sig` failure mode in `feedback_tool_writes_can_corrupt_bytes` broke CI once with every local gate
   green).
2. A **drift test** asserting the tree stays clean, so the next decoded escape is caught at the gate that
   would otherwise be blinded by it.

The test is the point. The scan finds today's instances; only the test stops tomorrow's.
