# PB3919 — alphabet-name-class-condition-not-supported: Class condition 'identifier IS alphabet-name' (ISO 2002/2014) is refused with 'syntax error, unexpected Identifier'

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S8) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\alphabet-name-class-condition-not-supported.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\alphabet-name-class-condition-not-supported\`.

## Summary

GnuCOBOL 3.2 refuses the class condition `identifier-1 IS [NOT] alphabet-name-1`, where the alphabet-name is defined
by an ALPHABET clause of the SPECIAL-NAMES paragraph. cobc accepts the ALPHABET clause and then reports
`syntax error, unexpected Identifier` at the condition, under `-std=cobol2014` and under the default dialect. The
alphabet-name class test is part of ISO/IEC 1989 since the 2002 edition and is in the 2014 edition that
`-std=cobol2014` claims. Class: feature missing.

## Minimal test case

Free reference format (`-fformat=free`), 14 lines, written for this record. File:
`E:\COBOL-coord\scratch\op\pb3838\records\alphabet-name-class-condition-not-supported.cob`. The night-4 witnesses
fz00095 and fz01504 (both `ALPHABET name IS "ABC...Z"` followed by `IF item IS name`) reduce to it; the third
witness filed under this family, fz04323, stops first on `NEAREST-TO-ZERO` and belongs to the family
nearest-to-zero-class-condition-not-supported.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. ALCC.
ENVIRONMENT DIVISION.
CONFIGURATION SECTION.
SPECIAL-NAMES.
ALPHABET ASC IS STANDARD-1.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 W PIC X(3) VALUE "AB1".
01 V PIC X VALUE X"E9".
PROCEDURE DIVISION.
IF W IS ASC DISPLAY "W IN" END-IF
IF V IS NOT ASC DISPLAY "V OUT" END-IF
STOP RUN.
```

STANDARD-1 is used so the expected result does not depend on how an implementation reads a literal alphabet: its
coded character set is ISO/IEC 646 IRV, which holds A, B and 1 and does not hold the byte X"E9".

condition `W IS ASC`; WiseOwl prints `W IN`.

## Expected result (per ISO)

The program is legal and prints `W IN` then `V OUT`.

- ISO/IEC 1989:2023 §8.8.4.4.2 (checked): the class condition's general format lists `alphabet-name-1` among its
  alternatives: `identifier-1 IS [ NOT ] { alphabet-name-1 | ALPHABETIC | ... | NUMERIC }`.
- §8.8.4.4.3 3) (checked): "If the alphabet-name-1, ALPHABETIC, ALPHABETIC-LOWER, ALPHABETIC-UPPER, BOOLEAN, or
  class-name-1 phrase is specified, identifier-1 shall reference a data-item whose usage is display or national." W and
  V are usage display. §8.8.4.4.3 2) (checked): "Alphabet-name-1 shall not reference an alphabet associated with a
  locale." ASC is not.
- §8.8.4.4.4 3) a) (checked): "If alphabet-name-1 is specified, the condition is true if the content of the data item
  referenced by identifier-1 consists entirely of characters in the coded character set identified by alphabet-name-1
  in the SPECIAL-NAMES paragraph."
- §12.3.7.4 7) c) (checked): "When the STANDARD-1 phrase is specified, the referenced coded character set shall be as
  specified in ISO/IEC 646 International Reference Version." "AB1" is entirely ISO 646 characters (true); X"E9" is not
  an ISO 646 character (false, so NOT is true).

Edition: a 2002 feature, present in 2014. The ISO/IEC 1989:2002 text lists it among the substantive changes not
affecting existing programs (item 16, "Class condition test with alphabet-name. The content of a data item can be
tested against the coded character set named as alphabet-name."); the 2009 committee draft that became ISO/IEC
1989:2014 (CD 1.2, §8.8.4.1.3) has `alphabet-name-1` in the general format and general rule 3) a) in the 2023
wording; Annex E of the 2023 standard lists no change to it.

Edition as recorded by the adjudicator: 2014 (introduced 2002). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Our compiler (WiseOwl)

WiseOwl COBOL (built from main 6ed90bd1c), `cobol alcc.cob --std 2014 --source-format free -o alcc.dll`, then

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/parser.y`, rule `condition_or_class` (line 18532): its class-condition arms are `CLASS_NAME`, `NUMERIC`,
  `ALPHABETIC`, `ALPHABETIC_LOWER`, `ALPHABETIC_UPPER` (and `OMITTED`); there is no alphabet-name arm.
- `cobc/scanner.l`, the user-word classification after `cb_build_reference` (lines 1127-1134): a word whose
  definition is a system name returns `MNEMONIC_NAME` and one that is a class-name (`CB_CLASS_NAME_P`) returns
  `CLASS_NAME`; an alphabet-name falls through to `WORD`, which `condition_or_class` cannot take.
- The class-name test the fix would parallel: the `'C'` operator pushed by `condition_or_class`, built in
  `cobc/typeck.c` `cb_build_expr` (`case 'C'` calling `build_expr_shift_class`, line 5925). An alphabet-name test
  needs the coded character set of the alphabet (`cb_alphabet_name`) as its membership set. (Corrected by the
  refuter: the record also named `cobc/tree.c` `case 'C'` at line 3022, which is `char_to_precedence_idx`, the
  PICTURE-symbol precedence table, and has nothing to do with the class test.)
