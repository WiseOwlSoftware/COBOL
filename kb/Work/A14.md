# A14 — CI wall time: the 30 minutes IS the conformance step; shard it or buy cores

Measured on run 31238417792 (all-green): in BOTH slow jobs, build is ~1.1 min and the wall time is
**conformance ~23–24 min + greenfield unit ~5 min**. No xunit.runner.json exists → xUnit defaults (parallel
across classes, threads = core count); generated programs run as subprocesses (why unique program-ids matter),
so the suite is CPU-bound and scales with cores. Standard GitHub runners are 2-core; the same suite takes
~11 min on the dev box. The Windows job runs the same greenfield suites deliberately (cross-platform net — the
BOM break was Windows-caught), so speedups must apply to BOTH, never drop one.

**Options, quality-preserving, in effort order:**
1. **Larger runners** (`runs-on: ubuntu-latest-4-cores` / windows equivalent; repo Settings → Actions →
   Runners). Zero engineering, near-linear for this suite (~23 → ~6–11 min). ⛔ NOT cost-neutral (owner
   correction 2026-08-07): standard-runner minutes run inside the FREE allocation — the baseline is $0 — while
   larger runners bill from the first minute with no free tier. This is a pay-for-speed option, full stop.
2. **Shard the conformance suite across a matrix** (3–4 shards per platform, `--filter` on class-name ranges)
   **⛔ ONLY with a population guard**: a cheap final step runs `dotnet test --list-tests`, and asserts the SUM
   of the shards' executed-test counts equals the discovered count — otherwise a hand-maintained bucket list
   silently drops a new test class (feedback_measure_the_selectors_complement /
   feedback_green_gates_arent_evidence). ~23 → ~6–8 min on free-tier runners.
3. **Move greenfield unit + characterization to their own parallel job** — takes ~5 min off each slow job's
   critical path for one YAML split; no guard needed (project-granular, nothing hand-listed).

Recommended: 3 now (trivial), 2 next (the guard is the design), 1 if the owner prefers paying over sharding.
Never cache build outputs across runs — the from-scratch build is exactly what caught the BOM break.

## LANDED (2026-08-07) — options 1 + 2; option 3 (larger runners) stays an owner-optional lever

Conformance is sharded 3 ways on BOTH platforms: `matrix` (VersionMatrixTests, 2020) · `corpus-nist`
(CorpusRunner + NistDifferential, 823) · `rest` — an EXCLUSION filter, so a new test class automatically lands
there (1419). Proven locally to partition exactly: 2020+823+1419 = 4262 = discovered. Greenfield unit +
characterization moved to their own parallel job; the Windows build job dropped its conformance step (the
sharded twin took it). The `conformance-population` guard job re-derives discovery (`--list-tests`) and asserts
each platform's shard Totals SUM to it exactly — a filter typo, class rename, or double-count is a loud
mismatch, never a silent gap. Expected wall: ~30 min → ~10-14 min per verdict.

## FOLLOW-THROUGH (2026-08-07 late) — two more measured splits; case count was a bad proxy TWICE

Run 1 of the sharded workflow (31241495896, 23.3 min wall): the `matrix` shard alone was 21 min — the
continuity method compiles each corpus program at every later edition, so its per-case cost dwarfed the
class's other 973 cases (1.5 min). Split at the METHOD (complement-shaped). Run 2 (31242438831, 21.4 min):
continuity ALONE was still ~20 min. Final split: BY EDITION via `DisplayName~NNNN` (1047 = 349 programs × 3
editions, proven 349/349/349; program names are XX###X so a year cannot collide). Six conformance shards per
platform; the population guard is unchanged and held on both runs. ⚠ The lesson for the next rebalance: shard
on MEASURED per-shard minutes from `gh run view --json jobs`, never on test counts.
