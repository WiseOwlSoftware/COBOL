# PB794 — LANDED — the one place that recognizes a directive word never looked at what follows it

Filed 2026-09-06 from battery #62's GnuCOBOL differential (`run_extensions:5006`, AGREE_REJECT →
**WE_ACCEPT_THEY_REJECT**). Every measurement below was taken on this worktree's own build of main at
`c77b4ea7`, not inherited: the probes are in
`E:\Temp\claude\E--CobolSharp\a9d94900-79fe-4a38-89f0-921976861543\scratchpad\PB794\`.

## The reproduction

`unknown.cob` and `lit.cob`, copied verbatim from `E:\Temp\gcdiff_o45zplzv\run_extensions_5006\`:

```cobol
       >>SOURCE FORMAT UNKNOWN            *> and, in lit.cob, >>SOURCE FORMAT "literal"
       IDENTIFICATION DIVISION.
       PROGRAM-ID. prog.
       PROCEDURE DIVISION.
          STOP RUN.
```

```
cobol unknown.cob --std 2023   → (clean, exit 0)
cobol lit.cob     --std 2023   → (clean, exit 0)
cobol unknown.cob --std 85     → COBOLNET0900: >>SOURCE FORMAT directive requires COBOL-2002 (targeting COBOL-85)
```

The 85 leg is the tell: the directive WORD is recognized and edition-gated, and then nothing ever asks what
followed it. At battery #61 (main `61d13d3e`, before train 20) both programs were rejected — `COBOL0001:
unexpected '>'` — because the line the reference-format stage could not match survived into the token stream.
**That was never a diagnosis of the operand; it was the absence of one showing through as a parse error**, and
[[PB725]] correctly closed the hole it came through. This note owns the residue PB725 left: the recognition point
gained an edition column and no operand column.

```
python scripts/spec/cite.py --check 7.3.24.1 "specifies whether the reference format of the source text or library text that follows is fixed form or free form"

```

⛔ **The general format is load-bearing here, so it was RENDERED, not read from the transcription**
(`python scripts/render-spec-page.py 114` → PDF page 114, printed folio 84; the PNG is in the probe directory).
The printed figure is

```
>> SOURCE  FORMAT  IS  { FIXED }        SOURCE, FIXED and FREE underlined;
                       { FREE  }        FORMAT and IS not underlined
```

so, by §5.2.2/§5.2.3, `FORMAT` and `IS` are optional words and the braces are a plain required choice: **exactly
one of FIXED or FREE shall be written.** `UNKNOWN` is a user-defined word the directive's syntax does not
specify, and `"literal"` is not a word at all — both violate §7.3.3 SR6, and neither selects a reference format,
so §7.3.24.3 GR1 has no answer for the text that follows. The transcription's figure note at §7.3.24.2 agrees
with the render exactly; it is recorded here because the *diagram* is what decides the case.

## ⛔ The half the operand sweep uncovered: nothing strips the inline comment, and it is a WRONG-FORMAT bug

§7.3.3 SR3 and SR4 say a compiler directive "may be followed only by space characters and an optional inline
comment" (`cite.py --check 7.3.3 "an optional inline comment"` → **OK, §7.3.3 3) and 4)**). Measured
(`probe2.py`, `probe3.py`, `probe4.py`), at `--std 2023`:

```
>>PROPAGATE ON *> on              → COBOLNET0883 (rejected — legal source)
>>LEAP-SECOND ON *> on            → COBOLNET1650 (rejected — legal source)
>>REF-MOD-ZERO-LENGTH ON *> on    → COBOLNET1576 (rejected — legal source)
>>FLAG-14 ALL ON *> flag          → COBOLNET1622 (rejected — legal source)
>>COBOL-WORDS RESERVE "ZQX" *> c  → COBOLNET1623 (rejected — legal source)
>>SOURCE FORMAT FIXED *> switch   → NOT RECOGNIZED AT ALL
```

The last one is the worst of the set and is not a diagnostic bug. `sw_comment.cob` — a free-form program that
switches to fixed form before six sequence-numbered lines — is rejected with `COBOL0001: no viable alternative
at input '000100'` while the identical program without the trailing comment compiles clean. The directive is
legal, the compiler does not see it, the following segment is read in the WRONG REFERENCE FORMAT, and the error
lands on a line the user did not write wrong. The cause is one end-anchored regex,
`ReferenceFormatProcessor.SourceFormatDirective` (`src/Cobol.Net.Frontend/Preprocessor/ReferenceFormatProcessor.cs:81`),
which tolerates a trailing `.` and nothing else.

## The mechanism, quoted from main

`src/Cobol.Net.Frontend/Preprocessor/ConditionalCompilationProcessor.cs:200-292` — the ONE point at which a
`>>WORD` is recognized:

```csharp
if (emitting && _bag is not null)
    CompilerDirectiveCatalog.Check(keyword, _edition, new BagSink(_bag, _diag.At.ToLocation()));   // :202  the EDITION arm
…
    // A recognized ISO §7.3 directive with no downstream stage: CONSUME it …
    else emit = CompilerDirectiveCatalog.IsDirective(keyword) ? "" : line;                          // :292  no operand arm
```

`rest` — everything after the directive word — is carried to the conditional-compilation arms (`>>IF`,
`>>DEFINE`, `>>EVALUATE`) and DROPPED on every other arm. The catalog row it consults
(`src/Cobol.Net.Editions/CompilerDirectiveCatalog.cs`, from `constructs.json`'s `directiveWords`) carries the
introducing edition and nothing about the operand, so there is no column for the check to live in and no place
for the omission to be noticed. Five stages then repeat the same four lines to find their own directive
(`PropagateDirectiveProcessor.cs:44-49`, `LeapSecondDirectiveProcessor.cs:43-48`,
`RefModZeroLengthDirectiveProcessor.cs:46-49`, `CobolWordsDirectiveProcessor.cs:46-53`,
`TurnDirectiveProcessor.cs:42-45`, plus `FlagDirectiveProcessor.cs:36-44` in its own spelling) — six copies of
"strip `>>`, match my word, take the rest as the operand", and not one of them knows about `*>`.

## The fix shape — the operand becomes a COLUMN of the same row, and the line parse becomes ONE parse

⛔ Not "add an `if` to the SOURCE FORMAT stage", and not one new code per directive (CLAUDE.md rule 5 — prefer
the shape that makes the next directive automatic):

1. **ONE line parse.** §7.3.2 gives one general format for every directive and §7.3.3 SR5 makes the space after
   the indicator optional; SR3/SR4 admit a trailing inline comment. That is one function — indicator, directive
   word, operand text with the comment removed — and it belongs beside the catalog, with every stage calling it
   instead of slicing `trimmed[2..]` again.
2. **ONE operand column.** `constructs.json` gains `directiveOperand` next to `directiveWords`: the closed word
   set (`choice`), the optional words that may surround it, whether the choice may be omitted (which is the
   PRINTED UNDERLINING's question — FIXED/FREE are underlined, so SOURCE FORMAT's choice is required, while
   §7.3.18.2's un-underlined `ON` makes LISTING's omissible), whether a catalogued directive-name is admissible
   (PUSH/POP, with §7.3.22.3 SR1's exclusions), and, for an operand the standard itself does not check
   syntactically (§7.3.19.3 SR2's comment-text-1), that fact plus its citation. A row that names a stage owner
   instead is the other half of a TOTAL partition, so a new directive cannot be silently unchecked.
3. **ONE producer.** The malformed-operand diagnostic is one descriptor for the whole family, emitted where the
   word is recognized — which lets the three bespoke operand codes go (COBOLNET0883 and COBOLNET1576 retire;
   COBOLNET1650 keeps only its §7.3.17.3 SR1 placement half) exactly as PB725 retired COBOLNET0875.
4. **A drift test derived from the catalog**, not a list: every catalogued row with a closed operand set is
   DRIVEN through the real stage with a malformed operand and must produce the diagnostic — the property that
   keeps "automatic" true when the next directive lands.

`>>SOURCE FORMAT` is the one directive whose line is consumed a stage early (`ReferenceFormatProcessor` must
switch the following segment's format before conditional compilation runs), so it recognizes its own word
through the same parse and calls the same producer — same row, same descriptor, one stage earlier, which is the
arrangement PB725 already established for its edition gate.

## Landed — 2026-09-06

**The defect reproduced exactly, and the sweep made it WIDER than the flip.** The differential's two programs
were two spellings of one hole; running every `>>` word the compiler recognizes, with a malformed operand and
with a legal inline comment, found **seven directive lines accepted in silence** and **five conforming ones
rejected**, plus the one that is neither — `>>SOURCE FORMAT FIXED *> switch`, unrecognized, so the following
segment was read in the WRONG reference format and the parse error landed on a line the user wrote correctly.

**The root cause was one rule with no column to live in, and one line-shape written seven times.** §7.3.3 SR6
composes compiler-instruction "as specified in the syntax of each directive" — the operand question — and the
recognition point PB725 built had an EDITION column and nothing else, so the answer lived in six stages with six
codes (0883 · 1650 · 1576 · 1622 · 1623 · 0718) and nowhere for the seven directives the driver consumes. §7.3.3
SR3/SR4's trailing inline comment lived in none of the seven hand-rolled `trimmed[2..].TrimStart()` copies.

**The fix is two structures, both derived:**

1. **`CompilerDirectiveLine`** (`src/Cobol.Net.Editions/CompilerDirectiveLine.cs`) — THE parse of a directive
   line: the indicator with its optional following space (§7.3.3 SR5), the directive word, and the operand with
   the SR3/SR4 inline comment removed, quote-aware so the `*>` inside `>>DISPLAY "a *> b"` is data (§8.3.3.1).
   Every stage calls it; seven copies are gone, and with them the whole inline-comment defect class.
2. **`directiveOperand`**, a new `constructs.json` column beside `directiveWords`, rendered by
   `gen-constructs.ps1` into `ConstructDialectStatus.DirectiveOperand`. The partition is TOTAL and the generator
   refuses a directive row without it: `words` (a closed set from the printed general format — optional words,
   omissible-or-not, whether a catalogued directive-name or a user-defined word is admissible), `text` (content
   unchecked, and the citation says by WHOSE decision), `stage` (a named downstream stage parses it).
   `CompilerDirectiveCatalog.CheckOperand` is the ONE producer: **COBOLNET1911**.

⛔ **Omissible-or-not is read off the PRINTED UNDERLINING, not the braces** (`feedback_underlining_not_bracketing`).
Both load-bearing pages were RENDERED: folio 84 underlines FIXED and FREE, so `>>SOURCE FORMAT` alone is
malformed; folio 78 leaves LISTING's `ON` bare, so `>>LISTING` alone is CONFORMING — which is what §7.3.18.3
GR4/GR5 call "specifying or implying the ON phrase". ⚠ The transcription's §7.3.18.2 figure note argues the
missing underline is a typesetting slip and would make the choice mandatory; the underlining plus GR4/GR5 is
followed here, because the alternative rejects legal source. §7.3.17.2, §7.3.21.2 and §7.3.23.2 are the same
shape, and their notes already read it that way. **A bare `>>REF-MOD-ZERO-LENGTH` and a bare `>>PROPAGATE`
therefore stopped being errors**, which is a second false rejection this landing removes.

**PUSH/POP's `directive-name` operand is derived from the catalog itself**, minus §7.3.20.3 / §7.3.22.3 SR1's
exclusions resolved BY ROW — so `>>PUSH WHEN` is refused because WHEN is a word of the excluded EVALUATE
directive, and a directive added later joins the admissible set with no edit.

**Retired: COBOLNET0883 and COBOLNET1576** — never reallocate (the COBOLNET0875 / COBOLNET1518 precedent).
**Narrowed: COBOLNET1650**, which now owns only §7.3.17.3 SR1's placement rule, the one obligation only that
stage can see. The PROPAGATE and REF-MOD-ZERO-LENGTH stages lost their diagnostic channel entirely.

⛔ **One behaviour change beyond the defect, deliberate:** a trailing PERIOD is no longer tolerated on a
directive. SR3/SR4 admit space characters and an inline comment and nothing else; six of the seven stages already
rejected it and only `>>SOURCE FORMAT FREE.` was accepted. No in-repo corpus program writes one.

**The drift test is catalog-derived and was proven RED before the fix.** `CompilerDirectiveCatalogDriftTests`
gains four properties: the partition is total and a stage owner names a type that exists; every closed-operand
row, DRIVEN THROUGH THE REAL STAGE with a malformed spelling derived from its own row, draws COBOLNET1911 (with
the three `text` exemptions named, so growing that set is a visible edit); the complement — each row's own
conforming operand, and its omitted phrase where the format allows one — draws nothing; and the inline comment
is not part of the operand. Removing the two `CheckOperand` calls turns the witness red with all nine directives
listed, which is what makes its green mean something.

**Goldens:** `negative/pb794-source-format-unknown` and `negative/pb794-source-format-literal` (reject-at
`2002 2014 2023` — at 85 the line is COBOLNET0900 and the operand is not the question), and the positive
`2023/pb794_directive_operands`, which switches reference format twice with an inline comment on each directive,
writes the omissible phrases bare, and exercises PUSH/POP's directive-name, CALL-CONVENTION and PAGE. Its
`A=5 / B=5 / C=5` is derived from §7.3.18.3 GR1, §7.3.19.4 GR3, §7.3.22.4 GR3 and §7.3.20.4 GR1 — every
directive in it is defined to leave run-unit data alone — and measured to match.

**Rows: nine general formats closed, GAP 2761 → 2752.** `FMT-7.3.9.2` · `-17.2` · `-18.2` · `-19.2` · `-20.2` ·
`-21.2` · `-22.2` · `-23.2` · `-24.2`, all CONFORMS. `FMT-7.3.12.2` (DISPLAY) stays a GAP as this note promised:
the fix requires an operand to be present and does not implement §7.3.12.2's arithmetic/boolean/PARAMETER
operand syntax, which is recorded on the row's own `directiveOperand` citation rather than left silent.

**Residue, measured and NOT claimed:** `>>ELSE JUNK` and `>>END-IF JUNK` are still accepted — those words head no
operand in §7.3.16.2, and the conditional-compilation driver that owns their row ignores trailing text. It is
the same shape one clause over, it belongs to the `stage` arm rather than to this producer, and it is reported
as a new defect rather than folded in here.
