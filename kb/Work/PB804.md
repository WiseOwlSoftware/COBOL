# PB804 — OPEN — the golden net grades one file and throws the rest away

Filed 2026-09-09 by the registrar from the PB792 implementer's report (§"New defects", paragraph A), which was
never filed as a note. The mechanism, the code site and the harm were re-derived on main at `d497f3c7`; the
report's line reference was one line stale and is corrected below.

## The mechanism, measured on main

`tests/Cobol.Net.Tests.Conformance/NistDifferentialTests.cs:120-125` — the whole of the output discovery, and
the whole of the evidence base:

```csharp
string printFile = Path.Combine(dir, testName.ToLowerInvariant() + ".txt");
string raw = File.Exists(printFile) ? File.ReadAllText(printFile)
    : !chained && Directory.EnumerateFiles(dir, "*.txt").FirstOrDefault() is { } any ? File.ReadAllText(any)
    : stdout;
return (true, Normalize(raw), runDetail);
```

Three branches, and each of them yields **one string**. Whatever else the program wrote into `dir` is never
opened, never normalized and never compared — and the `finally` two lines below is `CutRunner.TryDelete(dir)`,
so it is not merely ungraded, it is destroyed before anything else could look at it. (The report cited
`:118-125`; on this tree the slice is `:120-125`. The `chained` guard on the fallback is PB236's and is
correct — it stops a predecessor's report or a `tf###` data file being read as this program's output — but it
narrows the fallback, never the "exactly one file" shape.)

The CCVS driver programs that write a report through a second `SELECT` are the population this misses. RW104A is
the measured instance: it writes its CCVS log to `rw104a.txt` **and** its report-writer output to
`xxxxx049.txt`, and only the first is a golden.

## What it hid, and for how long

This is not a hypothetical hole — it swallowed a **silent wrong answer** for the length of a battery cycle.
[[PB792]]: at `--std 2023 --permissive`, RW104A card 024500 —

```cobol
03 VALUE "DETAIL LINE " COLUMN 20 PIC X(12).
```

— had `COLUMN` and `20` absorbed into the VALUE clause's operand list, lost its §13.18.14 COLUMN clause, and
printed the detail field at column 1 **with no diagnostic**. `rw104a.txt` was byte-identical to
`tests/nist/valid/RW104A.txt` throughout, because the damage was entirely inside `xxxxx049.txt` — the file this
harness does not read. Battery #61 was ALL GREEN over it.

So the net's contract, as built, is *"the CCVS print file matches"*, while the sentence every session actually
reads off a green NIST leg is *"the program produced the right output"*. Those differ by every byte a CCVS
program writes anywhere else, and the difference is exactly where a report-writer defect lives.

## Repro

On a tree **before** `c21371a6` (PB792's fix), run RW104A with `COBOLNET_NIST_STD=2023
COBOLNET_NIST_PERMISSIVE=1`, keep the run directory, and diff its `xxxxx049.txt` against the one a strict
`--std 85` run produces: the field is at column 1 in one and column 20 in the other, while `rw104a.txt` is
byte-identical in both and the test reports MATCH. On main the fix has landed, so the *defect this hid* no
longer reproduces — **the hole itself does**, and is visible by inspection of the slice above plus the
`TryDelete` that follows it.

## The rule

⛔ **No ISO clause. This is a test-net completeness question, not a conformance one** — nothing in
ISO/IEC 1989:2023 says what a differential harness must compare, and a note that reached for a clause here would
be `feedback_a_real_clause_can_answer_a_different_question`. The contract that IS violated is the project's own
gate-evidence invariant (`feedback_verdict_evidence_invariant`): a verdict needs its evidence, and "the file we
happened to read matches" is not evidence for "the program is correct". `inventory_rows` is empty for the same
reason — no rule-id is defective because of this.

## Shape of a fix (the fixer decides between these; both are structures, not lists)

1. **Compare every file the run produced.** After the run, enumerate `dir`, subtract the inputs the harness
   itself placed there (the `.dat` file, the compiled artifacts), and require each remaining file to match a
   golden of the same name under `tests/nist/valid/`. A produced file with no golden is then a LOUD event —
   either a golden to capture or an unexpected artifact — rather than the current silence.
2. **A per-program output list in `tests/nist/corpus.tsv`**, so the expected set is declared with the program
   rather than discovered. Cheaper, and it makes the RW programs' second file explicit; but it is a
   hand-maintained column, which CLAUDE.md rule 5 says to prefer against where a structure will do — option 1
   makes the NEXT program with a second output automatic, option 2 needs a row edit.

Whichever shape: **the deliverable that keeps it true is a falsification.** Perturb one byte of a secondary
output (or restore the PB792 bypass behind an env var) and prove the leg goes RED before trusting its green —
`feedback_green_gates_arent_evidence`, and this gate has spent its whole life green over at least one real
defect.

## Sweep the fixer must do

- ⛔ **`scripts/guard.sh` / `scripts/guard-fast.sh` have the SAME shape.** The battery's `guard NIST: NNN MATCH`
  line is produced by the shell guard, not by this xUnit class, and it normalizes one print file per program
  too. Fixing only the xUnit leg leaves the number the owner reads unchanged — `feedback_two_arm_dispatch`, the
  most reproducible defect shape in this repo. Ask which arm you fixed.
- **Every CCVS program with more than one `SELECT` to a file it WRITES** is in the population, not only the RW
  family; derive that list from the corpus rather than assuming it is the report-writer programs.
- **The `any-*.txt` fallback becomes wrong under option 1** (it exists precisely because "which file is the
  output" was ambiguous); retire it in the same change set rather than leaving two mechanisms
  (`feedback_one_mechanism_per_job`).
