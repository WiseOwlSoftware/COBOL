# PB3925 — usage-bit-and-aligned-not-supported--aligned-clause-position: ALIGNED clause is only accepted directly after USAGE BIT: 'syntax error, unexpected ALIGNED' for USAGE BIT PIC 1(4) ALIGNED

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S8) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\usage-bit-and-aligned-not-supported--aligned-clause-position.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\usage-bit-and-aligned-not-supported--aligned-clause-position\`.

## Summary

GnuCOBOL 3.2 parses ALIGNED only as a suffix of the USAGE clause (`USAGE BIT ALIGNED`), not as the separate data
description clause the standard defines. `05 G2 USAGE BIT PIC 1(4) ALIGNED.` is refused with `syntax error, unexpected
ALIGNED` under `-std=cobol2014` and the default dialect, while `05 G2 PIC 1(4) USAGE BIT ALIGNED.` compiles. The
standard lets the clauses of a data description entry be written in any order. Class: rejects legal ISO source. The
parser comment at the site says the simplification is deliberate ("ALIGNED actually is a separate clause but at least
for now we simplify it, requesting it after USAGE BIT").

## Observed result

`algn.cob`, `-std=cobol2014`, exit code 1:

```
algn.cob:6: warning: USAGE BIT is not implemented [-Wpending]
algn.cob:7: warning: USAGE BIT is not implemented [-Wpending]
algn.cob:7: error: syntax error, unexpected ALIGNED
```

`algn-x.cob`: `algn-x.cob:7: error: syntax error, unexpected ALIGNED`, exit code 1. Default dialect (`algn.cob`, no
`-std`): the same error, exit code 1. `algn-ok.cob` compiles (two -Wpending warnings, exit 0) and prints `2`, exit 0.

## Expected result (per ISO)

The program compiles and prints `2`.

- §13.16.3 4) (checked): in a data description entry, after the entry-name, REDEFINES and TYPEDEF placement rules,
  "The remaining clauses may be written in any order." ALIGNED is one of the clauses of the data description entry's
  format 1 (§13.16.2), a separate bracket from USAGE.
- §13.18.1.3 1) (checked): "The ALIGNED clause may be specified only for a bit group item or an elementary bit data
  item." G2 is an elementary bit data item (§13.18.60.4 5), checked: "A data item described with USAGE BIT is a bit
  data item").
- §13.18.1.4 1) (checked): "An ALIGNED clause causes the subject of the entry to be aligned on the first bit of the
  first available byte boundary." With §8.5.1.6.3 (checked: filler is generated "as needed to increase the number of
  bits to fill an integral number of characters" after the last bit item of an alphanumeric group), G is G1 (bits 1-4
  of byte 1), implicit filler (bits 5-8), G2 (bits 1-4 of byte 2) and trailing filler: 2 bytes. §15.14.4 1) (checked):
  BYTE-LENGTH returns "the length of argument-1 in number of bytes".

Edition: 2014. The ALIGNED clause was introduced in 2002 (WiseOwl's `constructs.json` row `aligned-clause-2002`; ALIGNED
is a 2002 reserved word). Annex E (2014 to 2023) adds ALIGN, a different clause, to the strong-typing consistency rules;
it does not change ALIGNED.

When cobc accepts ALIGNED (`algn-ok.cob`), it prints the expected `2` only because it gives every USAGE BIT item its
own whole byte (see `usage-bit-and-aligned-not-supported--usage-bit`); the clause itself sets nothing in the parser
action.

Edition as recorded by the adjudicator: 2014 (introduced 2002). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/parser.y`, rule `usage` (line 7989): the alternative `BIT ALIGNED` (line 7999) is the only place the `ALIGNED`
  token (declared line 2485) is accepted, with the comment that ALIGNED "actually is a separate clause".
- `cobc/parser.y`, rule `data_description_clause` (line 7472): has no `aligned_clause` alternative. Adding one (with a
  repeated-clause check like the other clauses and a flag on `cb_field`), and removing the `BIT ALIGNED` alternative,
  would accept the clause in any position; `compute_size` in `cobc/field.c` would read the flag once bit storage exists.

Legal: 13.16.2 lists [ALIGNED] as its own clause, 13.16.3 4) 'The remaining clauses may be written in any order', 13.18.1.3 1), 13.18.1.4 1), 13.18.60.4 5), 8.5.1.6.3 and 15.14.4 1) all --check OK; the 2002 text (13.16.1) and the 2009 CD (13.18.1) have the clause and the any-order rule; ALIGNED is in neither A.3 nor A.4. This is a syntax error with no 'not implemented' notice, against cobc's own FR 303 aim that such sources parse, so it stays a parser defect, unlike the announced USAGE BIT runtime gap.
