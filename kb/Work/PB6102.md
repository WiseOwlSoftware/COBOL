# PB6102 - what the landing check stops, as the docs say and as the script does

**The lead's claim does not hold, and the drift is elsewhere.** The PB3199 report says `landing_check.py` does not exist because
`git ls-files | grep landing_check` finds only COBOL cases. On main ae1136f781 the same command also lists `scripts/orchestrator/landing_check.py`, and the
docs name it as `landing_check.py` (a bare file name) or `scripts/orchestrator/landing_check.py`. The script exists and `enqueue.py checks` runs it (exit 3).

**What the landing check is (the script's docstring and code).** It runs on the landing's tree and stops (`--rev`, exit 1, `enqueue.py` exit 3) for only two reasons:
(0) a path no landing carries (`coord.NEVER_WORK`, above all the harness's tracked `.claude/settings.local.json`) and (0b) a public-API baseline that lists a symbol twice
(RS0025, `public_api_baselines.baseline_stops`). A branch whose edits MEET the landing's (a member of one matches a member of the other, `inflight.hold`) is only
NAMED in a warning: "first ready lands" (owner 2026-11-02, kb/Work PB4452). It does not compare the landing with any declared or computed file set: "a file outside it is the
planner's estimate missing a caller, and git's merge is the authority on a conflict". `scripts/orchestrator/units/enqueue.md` (the `exit 3` line) states exactly this.

**The drift.** Four places still describe the pre-PB4452 check:
- The boilerplate paragraph "Its file set is computed, never listed ... the landing check (`landing_check.py`, run by `enqueue.py land`) stops a landing that changed a
  file outside it" in 163 kb/Work notes (`grep -l "stops a landing that changed a file outside it" kb/Work/*.md`; for example `kb/Work/PB3199.md:49`, `kb/Work/PB3200.md:56`).
  The sentence is false twice: the check does not compare against the computed set, and it stops nothing for a file outside it.
- `.claude/skills/architecture-review/SKILL.md:19`: "a landing whose actual edits meet an earlier in-flight branch's by member stops and re-plans".
- `.claude/skills/workstream/templates/MANDATORY-PRACTICES.md` L12 and `.claude/skills/workstream/references/landing.md:59-60`: exit 3 "is retried only once
  `landing_check.py` passes on the branch (the overlap is gone)"; the stop is now a never-carried path or a duplicate symbol, which only a new commit clears.
- `docs/rearchitecture/DESIGN-architecture-review.md` §8.7 (about line 2100): "a remaining miss must stop a landing, never land silently" and "a shared file stops it only when
  it is R3 work on either side and the two EDITS MEET"; both are the pre-FIRST-READY-LANDS rule.

## The fix (wave 20262147 group C)

Re-probed on a23ed881c2: `landing_check.py`'s docstring and `enqueue.py checks` stop only for a never-carried path (0) and a
duplicate public-API symbol (0b); a meeting only warns. All four prose sites still said otherwise, and the sweep (a grep for
`re-plans`, `leaves its declared set` and `file outside it` over the docs and scripts) found three more: `plan_wave.py`'s
docstring, `dispatch_ledger.py`'s two descriptions of `at` and plan §0's PB2108 bullet. Each now states the docstring's rule:
the skill's paragraph, MANDATORY-PRACTICES L12 and `references/landing.md` (exit 3 is a never-carried path or a duplicate
symbol, cleared only by a new commit, as `land_lane.py` and `units/enqueue.md` already said), DESIGN-architecture-review section 8.7's heading and its two
sentences, and the generator's paragraph in `file_census_notes.py` (the set is an admission estimate the landing never
compares with; git's merge judges a conflict; the landing check only names a meeting branch).

**Decision, the 164 copies (163 at filing):** the paragraph is generated boilerplate, not a finding, so an OPEN note, which
an implementer reads as its contract, gets the corrected sentence in place: 88 open notes were rewritten mechanically (one
regular expression over both spellings, `run by enqueue.py land` and the older `run by push-main.sh`, one changed line
each, so a branch editing the same note's frontmatter or appending to it merges cleanly). The 74 landed and retired notes
keep theirs: a closed note is the register's record of the item as it was worked, and rewriting it would edit history
another branch may be reading (CLAUDE.md rule 8's one-file-per-finding rule exists for that). This note quotes the old
sentence on purpose and keeps it.
