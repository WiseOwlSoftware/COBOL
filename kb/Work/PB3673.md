# PB3673 — a failed ABI-pin settle is reported as a merge CONFLICT and costs a finisher

**Sites:** `scripts/merge_drivers.py#merge` (the `abi_pin.needs_settle` / `abi_pin.settle` arm, which returned `[abi_pin.PIN_PATH]`; now `Merged`, `_refused`, `main`'s `merge` command, `EXIT_INCOMPLETE`), `scripts/orchestrator/enqueue.py#land` (its `conflicted()` closure, `EXIT_CONFLICT`; now `incomplete`, `stopped`, the `merge` collaborator, `merge_main`, `one_line`), `scripts/abi_pin.py#run_measurement` (now `Failure`, `failure`, `settle`, `bump`, `MERGE_BLOCKED`, `MERGE_FAILED`), `scripts/run_gate_legs.py#NOT_RUN_CAUSES` (the `merge-blocked` and `merge-failed` rows), `.claude/skills/workstream/templates/finisher-brief.md`, `docs/rearchitecture/DESIGN-test-build-ci.md` (3.14.3 item 1, 3.17.2 step 2), `docs/rearchitecture/DESIGN-orchestrator-loop.md` (the lane's exit table), `tests/Cobol.Net.Tests.Unit/MergeDriverDriftTests.cs`, `tests/Cobol.Net.Tests.Unit/LandingPipelineDriftTests.cs`.

## What happens

`merge_drivers.merge` merges origin/main into the branch. When the merge is clean but the runtime ABI pin needs settling
(`abi_pin.needs_settle`), it runs `abi_pin.settle`, which builds the Unit tests and runs `RuntimeAbiPinDriftTests` in
write mode (`run_measurement`). When that build or test run FAILS, for any reason, `merge` aborts the merge and returns
`[abi_pin.PIN_PATH]`, the same shape it returns for files left in conflict. The reason goes only to stderr
(`merge_drivers: the runtime ABI pin could not be settled: …`). `enqueue.py land` cannot tell the two apart: it calls
`conflicted()`, ends `EXIT_CONFLICT` (4) with `CONFLICT in src/Cobol.Net.Runtime/RuntimeAbi.pin — merge aborted, branch
unchanged`, and writes `BLOCKED: enqueue — bringing origin/main in … conflicted …: a finisher merges origin/main,
resolves and re-gates` into the branch's report. The landing lane then waits for the enqueue unit's finisher (about
100 k tokens and a re-gate, PB3610's measured cost) to resolve a conflict that does not exist.

## Witness (2026-10-24, wave 20261032 group F, PB3630)

Lane attempt `000092-20261025T012405Z-worktree-wf_6ffe8083-b46-6` ended exit 4, `CONFLICT in
src/Cobol.Net.Runtime/RuntimeAbi.pin`. Neither side had changed the pin since the merge base `e20c6887b` (`git diff`
of base, branch head `075134749` and origin/main: empty). The log
`E:\COBOL-coord\logs\land-lane-000092-20261025T012405Z-worktree-wf_6ffe8083-b46-6.log` shows the real cause: the
measuring build failed with MSB3027/MSB3021, `Cobol.Net.Compiler.SourceGen.dll` in the worktree's `bin` locked by
another process (PB3674: the unit session's own csharp-ls), followed by `FILTER POPULATION CHECK FAILED: could not
discover tests … (the project failed to build)`. The wave unit stopped the holder and re-ran `enqueue.py land` by hand
instead of dispatching a finisher.

## Fix direction

Give a settle failure its own outcome. `merge` should return a typed result that separates "files in conflict" from
"the pin could not be measured: <reason>", and `enqueue.py` should end with a distinct exit and verdict (the
measurement's reason in the verdict line and the report, not only stderr). An environmental failure of the measuring
build (a locked file, a build server) is retryable by the lane itself; only a real conflict, or a measurement that fails
the same way twice, goes to a finisher. Sweep the other callers of `merge_drivers.merge` (the finisher's `keep` path)
and of `abi_pin.settle` for the same collapse, and add a self-test in `merge_drivers.py`'s scratch-repo tests where the
`measure` stand-in fails and the merge must not be reported as a conflict.

## Operator evidence and the pattern (2026-10-24)

A second case: PB3664's landing at 18:59 PDT (`E:\COBOL-coord\logs\land-lane-000097-20261025T015915Z-worktree-wf_ae6946ad-ce4-1.log`) stopped `CONFLICT in src/Cobol.Net.Runtime/RuntimeAbi.pin` with neither side having changed the pin; the settle ran only because `abi_pin.needs_settle` matched the pin's header (PB3671, landed), and its build failed on a held DLL. **The pattern (operator, 2026-10-24).** Three notes are one mechanism: an ENVIRONMENT cause read as a failure of the WORK. PB3673: a pin settle whose build is blocked is reported as a conflict (exit 4) and sent to a finisher. PB3674: a language server holds an analyzer DLL, so a gate or settle build fails as if the branch were broken. PB2665: a meter unit that cannot reach Chrome fails as a unit and counts toward the circuit breaker, so the loop retries it until it stops itself. The gate already has the one classifier (`run_gate_legs.NOT_RUN_CAUSES`, PB3526: an environment cause is exit 2, retried once, then the operator's). The fix extends that ONE classification to `merge_drivers.merge`'s settle, `enqueue.py`'s exit mapping and the loop's unit accounting (`orchestrate.ps1`'s breaker, `next_unit.py`'s meter rule), rather than three local patches.

## Landed (wave 20261704, group D)

**Re-probe (2026-10-25, this build).** `merge_drivers.merge` still returned `[abi_pin.PIN_PATH]` for a settle that failed
(the `pin: a settle that fails aborts the merge and names the pin` arm asserted exactly that), and `enqueue.land` mapped
every non-empty answer to `conflicted()`, exit 4. The note reproduced.

**Fix shape.** One classification, extended: the gate's `run_gate_legs.NOT_RUN_CAUSES` gains two rows, `merge-blocked`
(ENVIRONMENT) and `merge-failed` (BRANCH). `abi_pin.settle` and `run_measurement` return a `Failure(cause, why)` instead
of a string: a build output another process holds (MSB3027, MSB3021, "being used by another process", "is locked by"), a
full disk or a command that cannot start is `merge-blocked`, read from the WHOLE output (the message keeps only its last 40
lines, and the lock error can be above them); a malformed pin or owned file, a tree that does not build, a red measuring
test or a measurement that wrote no pin is `merge-failed`. `merge_drivers.merge` returns a `Merged(conflicts, incomplete,
in_progress)`, three ends a caller must tell apart. The sibling collapses of the same function are fixed with it: the
refusal of the fast-forward, of the merge itself with no file in conflict, and of the merge commit were `["?"]`, a
CONFLICT in a file named `?`; they are `incomplete` with git's own words, `merge-blocked`. `enqueue.land` ends an
ENVIRONMENT cause exit 2 (`MERGE NOT COMPLETED`, no report line: the lane retries once, a second is the operator's) and
a BRANCH cause exit 5 (a `BLOCKED: enqueue — bringing origin/main in … could not be completed` line, a finisher's), at
both of its merges (step 2 and the catch-up in step 4). `merge_drivers.py merge` ends exit 3 with `NOT COMPLETED [<cause>]`;
with `--keep` a merge stopped at the pin stays in progress for the finisher's `abi_pin.py settle --stage`. The lazy
`import abi_pin` in three functions of `merge_drivers.py` is now one top-level import and `abi_pin_path()` is deleted.

**Goldens (self-tests; the gate runs every one).** `merge_drivers.py`: the settle failure is a `Failure`, not a conflict,
branch unchanged; `--keep` leaves it in progress. `abi_pin.py`: the class of each cause, the lock error above the tail, a
malformed owned file never reaches the measurement. `enqueue.py`: exit 2 with no report line, exit 5 with one line, the
tags held to NOT_RUN_CAUSES rows, the same arm at the catch-up merge. `LandingPipelineDriftTests` and
`MergeDriverDriftTests` declare the new arms.

**Not done here.** The pattern paragraph above names two more members of the family, PB3674 (landed separately) and PB2665
(the loop's meter unit and `orchestrate.ps1`'s breaker). PB2665 is its own note and was not in this group.
