# PB5763 - a MERGE OUTPUT PROCEDURE terminated by -SEQUENCE leaves its USING files open

**Sites:** `src/WiseOwl.Cobol.Runtime/IO/CobolSort.cs` (`CobolSort.Merge`, `CobolSort.MergeCore`), `docs/conformance/3/D-SMA.md` (its (b) paragraph), `conformance-suite/cases/13.18.43-RECORD/pb1036_sort_merge_statement_ec.out` (leg G). `Merge`'s summary says: "Every USING file was closed by its implicit CLOSE before this phase and no GIVING file is opened until after it, so 'all files … are closed' already holds". That holds only without an output procedure, because `§2002:14.8.23.3 GR7c` defers the USING files' implicit CLOSE until the output procedure ends. When `MergeCore` raises -SEQUENCE, the catch in `Merge` disposes of the raise, and nothing closes the USING files.

docs/conformance/3/D-SMA.md (b) says the opposite as a determination: "the USING file of a MERGE terminated by -SEQUENCE is still open afterwards (the program's own CLOSE succeeds, golden leg G)". `pb1036_sort_merge_statement_ec` pins that, with `G MAS=00` after leg C, an OUTPUT PROCEDURE MERGE, and the case is accepted at 2002. GR6 is word-identical at 2023 (`§2023:14.9.24.4 GR6`), so the determination contradicts the rule at both editions. The fix updates D-SMA (b) and pb1036's leg G together with the runtime.

**Repro** (`E:\COBOL-coord\scratch\gl2002\integrate-9\repro\merge\g2mrgs6-merge-sequence-closes.cob`, with its derived `.expected` beside it, from the writer's `lane1\out\g2002u-14-8-23-merge\repro\`): `>>TURN EC-SORT-MERGE-SEQUENCE EC-I-O CHECKING ON`. M-A holds BBB then AAA (out of order) and M-B holds CCC. A USE procedure for EC-SORT-MERGE-SEQUENCE and one for EC-I-O each display the status and end `RESUME AT NEXT STATEMENT`. Leg G is `MERGE S2 ON ASCENDING KEY S2-REC USING M-A M-B GIVING G-OUT`, then a CLOSE of each of M-A, M-B and G-OUT. Leg O is the same MERGE with `OUTPUT PROCEDURE IS OUT-C`, then a CLOSE of M-A and M-B.

**Observed** (golden-2002-9 integrator, `cobol.exe g2mrgs6-merge-sequence-closes.cob --std 2002 --run`, rc 0): leg G is correct. After `SM=EC-SORT-MERGE-SEQUENCE` and `AFTER-G`, each of the three CLOSEs gives `IO=EC-I-O-LOGIC-ERROR` and status 42. Leg O prints `SM=EC-SORT-MERGE-SEQUENCE`, `AFTER-O`, `MAS=00`, `MBS=00`: both USING files were still open.

**Expected** for leg O: `SM=EC-SORT-MERGE-SEQUENCE`, `AFTER-O`, `IO=EC-I-O-LOGIC-ERROR`, `MAS=42`, `IO=EC-I-O-LOGIC-ERROR`, `MBS=42`. These rules were each checked with `python scripts/spec/cite.py --check`, verdict OK:
- `§2002:14.8.23.3 GR6`: "all files associated with the MERGE statement are closed".
- `§2002:14.8.23.3 GR7c`: "If an output procedure is specified, this termination is not performed until after control passes the last statement in the output procedure". This is why the output-procedure path is the one that still has its USING files open when -SEQUENCE is raised.
- A CLOSE of a file connector that is not in an open mode gives I-O status 42 (§2002:9.1.12.6, the writer's citation, not re-checked here) and EC-I-O-LOGIC-ERROR, as leg G already shows.
