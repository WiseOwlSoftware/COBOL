# PB5073 - at --std 85 duplicate GLOBAL data-names and duplicate INDEXED BY index-names compile: nothing screens GLOBAL names against each other, and the index-name duplicate check runs only when a reference is resolved

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.NameUniqueness.cs` (`ScreenNameUniqueness`, `ScreenGlobalNameUniqueness`, `ScreenIndexNameUniqueness`, the fix), called from `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.cs` (`Bind`); `src/WiseOwl.Cobol.Editions/Diagnostics/DiagnosticCatalog.cs#GlobalDataNameNotUnique` (COBOL6862) and `#IndexNameNotUniqueInProgram` (COBOL6863). The note first named `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.ClausePlacement.cs` (whole: the records name it, with InheritedGlobals, as the neighbour holding only clause-placement checks and global inheritance; the fix site is not located) and the index-name duplicate check `ResolveIndexName` (COBOL1639, made at reference time).

**Mechanism.** 1985 states three name-uniqueness rules that the compiler never asks of a declaration: the same data-name must not name a GLOBAL item and another item that shares its scope (IV.4.3.8.1 and X.4.6.3 SR2, the second as the rule on two items both written GLOBAL), and an index-name must be a unique word within the program, unconditionally (VI.5.8.3 SR14). The only duplicate-index-name check fires when a reference is resolved, so an unreferenced duplicate declaration passes.

**Found by.** The 1985 `--std=85` draft triage (kb/Work PB4995 item 3): each rule below is a conformance-suite draft that did not MATCH at `--std 85`, and its adjudicator decided COMPILER-DEFECT. Harm and observed text are the records'; nothing here was re-derived.

**Inventory.** The traceability inventory carries no 1985 rows yet, so `inventory_rows` is empty; the rows this note covers are the 1985 rule ids listed below (catalog `docs/rearchitecture/spec-rule-catalog-1985.json`).

**Rules (3; every citation checked with `scripts/spec/cite.py --check`).**

- `1985-SR-IV.4.3.8.1-4` - `§1985:IV.4.3.8.1` (record harm: under-rejects, slice-02): §1985:IV.4.3.8.1 (the paragraph after item 4): "The same data-name must not be used as the name of an item possessing the global attribute and as the name of any other data item described in the program which describes that global data item." In the draft, line 5 gives DUP-NAME the global attribute (`01 DUP-NAME PIC X VALUE "A" GLOBAL.`) and line 7 uses the same data-name for another data item described in the same program (`02 DUP-NAME` of GRP). The words "Regardless of the above" open that paragraph, so qualification does not rescue the pair. The program violates an explicitly stated provision and the draft is right to expect a refusal. §1985:X.4.6.3 SR2 states the neighbouring rule: "In the same Data Division, the data description entries for any two data items for which the same data-name is specified must not include the GLOBAL clause."
- `1985-SR-X.4.6.3-2` - `§1985:X.4.6.3 SR2` (record harm: under-rejects, slice-08): §1985:X.4.6.3 SR2: "In the same Data Division, the data description entries for any two data items for which the same data-name is specified must not include the GLOBAL clause." Lines 5 and 6 both describe 01 DUP-ITEM with GLOBAL in one Working-Storage Section. The name is never referenced, so no uniqueness-of-reference rule is involved; SR2 is the only rule violated.
- `1985-SR-VI.5.8.3-14` - `§1985:VI.5.8.3 SR14` (record harm: under-rejects, slice-03): §1985:VI.5.8.3 SR14: "Index-name-1 must be a unique word within the program." The rule is unconditional: it does not wait for a reference, unlike the uniqueness-of-reference rules. A program that writes one word as the index-name of two tables violates it whether or not the word is ever referenced. The draft tests the rule through another one: its IX is an index-name and a data-name, a collision that §1985:IV.4.2.2.1.1 already forbids ("All user-defined words, except segment-numbers and level-numbers, can belong to one and only one of these disjoint sets."), and the compiler refuses it under that rule at the data-name's line (7) where the draft marks the INDEXED BY line (6); the line is the implementor's choice, and with both entries on one line the draft matches. But a draft that isolates SR14, one word naming two index-names, is ACCEPTED, so the rule itself is unenforced and the case is a compiler defect.
