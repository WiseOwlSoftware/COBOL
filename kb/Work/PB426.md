# PB426 — the 31-position cap that keeps the carrier unreachable was dropped

## The mechanism

`src/Cobol.Net.Runtime/Values/Numeric/CobolNum.cs:651-658`:

```csharp
public static Int128 FromAlphanumeric(string image)
{
    if (string.IsNullOrEmpty(image)) return 0;
    Int128 mag = 0;
    foreach (char c in image)
        if (c is >= '0' and <= '9') mag = mag * 10 + (c - '0');
    return mag;
}
```

Every character position of the sending operand is consumed. There is no 31-position cap and no guard on the
accumulator. The standard caps the SENDING operand at 31 digits — the rightmost 31 character positions for a data
item, the rightmost 31 characters for a literal — precisely so that no implementation carrier can be exceeded;
dropping the cap makes the carrier reachable. A sending operand of 39 or more digit characters wraps the SIGNED
`Int128` to a negative value, and the unsigned receiver then stores that value's magnitude.

Below the wrap the missing cap is INVISIBLE, because both readings truncate high-order digits to the receiver's
digit count — which is why the hole outlived a large test corpus. The call-site comment at
`src/Cobol.Net.Compiler/CodeGen/Emit/NumericRenderer.cs:401` cites GR6 and GR6d3 by name, so the rule was known
and only its SIZE clause was dropped.

DERIVATION: the rightmost 31 characters of A40 are "0123456789012345678901234567890", i.e. the unsigned integer
123456789012345678901234567890; §14.6.8.2 GR4 then aligns by decimal point into `PIC 9(9)`'s nine digit
positions, truncating high-order, giving 234567890. Into `PIC 9(31)` the sending value is stored as it stands.

THE MECHANISM IS IDENTIFIED EXACTLY, not inferred: the full 40-digit parse taken mod 2**128 and read as a SIGNED
Int128 is -126561577560297064841152750825838277934, whose low-order 31 digits are
7560297064841152750825838277934 and whose low-order 9 are 838277934 — both observed values, to the digit. The
35-character control is correct, which places the threshold at the Int128 carrier rather than at the receiver.

EDITIONS: the b2 adjudication measured the same wrong value at 85, 2002, 2014 and 2023 (probe dir `edsweep`);
re-run on HEAD at 2023 above. Sub-rule (b), the figurative-constant digit count, CONFORMS and was re-measured on
HEAD: `MOVE ALL "7" TO PIC 9(3)V9(2)` stores 77777, spanning the fraction positions

receiver is not one). So only the two SIZE clauses are missing.

## The code site and the shape of the repair

- `src/Cobol.Net.Runtime/Values/Numeric/CobolNum.cs:651-658` `#FromAlphanumeric` — the unguarded accumulator.
- Reached on the MOVE channel from `src/Cobol.Net.Compiler/CodeGen/Emit/NumericRenderer.cs:401` `#FieldNumCore`
  (the `{ Category: PicCategory.Alphanumeric or PicCategory.National }` arm, whose comment cites GR6/GR6d3) and
  from `src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs:339` (the alphanumeric-sender-into-numeric-edited
  arm).

**FIX IT IN `FromAlphanumeric` ITSELF** — take the rightmost 31 CHARACTER POSITIONS of the image before
accumulating. That is the structural repair rather than the local one: it closes every channel at once and makes
the carrier unreachable BY CONSTRUCTION, which is exactly what the standard's cap is for. Guarding at the two
MOVE call sites would leave the other five channels below wrapping, and a guard that throws would convert a
silent wrong answer into a crash on legal source.
⚠ The cap is on CHARACTER POSITIONS, not on digit characters: §14.6.13.2 lets a non-digit position contribute no
digit (the behaviour `FromAlphanumeric` already implements), so the rightmost-31 window must be taken over the
image and only then scanned for digits. Truncating to 31 DIGITS would give a different, wrong answer for an image
with embedded non-digits. Golden both shapes.

## The sibling sweep the fixer must do

`FromAlphanumeric` is the shared unsigned-integer decode for every alphanumeric-in-a-numeric-context read, and
each inherits the same unguarded accumulator. Only the MOVE channel is adjudicated by this note's row; the fix
must cover them all and each needs a golden at 40 characters:

- the reference-modified numeric read — `NumericRenderer.cs:330`
- the group-image numeric read — `NumericRenderer.cs:365`
- INSPECT TALLYING — `InspectEmitter.cs:121, :125, :133`
- STRING / UNSTRING — `StringEmitter.cs:211, :226`

Then sweep the SHAPE, not just this function: every other place a COBOL size limit stated in the standard was
implemented as "accumulate and hope" rather than as a cap. Grep for `Int128`/`long` accumulators fed by a loop
over a user-controlled image.
