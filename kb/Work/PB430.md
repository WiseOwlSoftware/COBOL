# PB430 — GR4's no-conversion clause is true only for a DISPLAY sender

## The mechanism

GR4 has two sentences and this compiler gets the FIRST one wrong on the sender side and the SECOND one wrong on
one of its two arms. Both are silent wrong answers on legal source, at every edition.

**(1) The sender-side classifier rejects the standard's own definition of a group.**
`src/Cobol.Net.Compiler/Binding/Bound/MoveClassifier.cs:65-72`:

```csharp
/// … and so is a RENAMES alias (the level-66 view is composed as ONE elementary
/// alphanumeric item, §13.18.45). …
public static bool IsGroupSender(BoundOperand source) =>
    source is BoundFieldOperand { Place: not (RefModPlace or RenamesPlace) } f
    && f.Place.Item.IsGroup && !f.Place.Item.IsAsIfElementary;
```

§13.18.45.4 GR2 says the opposite of the comment: with THROUGH, data-name-1 defines an alphanumeric GROUP item. A
group item is not an elementary item, so GR4's first sentence makes a MOVE from `66 R RENAMES a THRU b` a
NON-elementary move, and GR4's second sentence then forbids conversion — and with it the receiver-category
EDITING that only an elementary move performs. Excluding `RenamesPlace` classifies it as elementary and the
receiver's edit mask is applied. This is a MIS-CLASSIFICATION, not a missing feature, and the comment is the
textbook inherited-citation failure: a real clause number attached to the opposite claim.

**(2) The no-conversion clause is not implemented on the elementary-sender-into-a-group arm.**
`src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs:146` `#EmitGroupMove` renders the source with
`OperandText.AsString(source, num, deSign: false)` (:191) — the ZONED DISPLAY image — for EVERY sender. So a
COMP-3 / COMP / COMP-5 elementary item moving into a group is converted from its packed or binary representation
to display digits, and occupies the wrong number of character positions. The compiler contradicts itself: the
group-SENDER direction, `#EmitGroupToElementaryMove` (:116), deposits the pinned representation bytes for the very
same item.

## The code sites and the shape of the repair

- `src/Cobol.Net.Compiler/Binding/Bound/MoveClassifier.cs:65-72` `#IsGroupSender` — remove `RenamesPlace` from
  the exclusion and fix the comment. ⚠ Only the THROUGH form: §13.18.45.4 GR1 makes a RENAMES WITHOUT THROUGH
  take data-name-2's attributes, so the classifier must ask the alias whether it spans a range, not whether it is
  a `RenamesPlace`. A blanket removal would break the currently-correct `gr4_renames_nothru` case. `RefModPlace`
  stays excluded — §8.4.3.3.4 GR6 genuinely makes a ref-mod result elementary alphanumeric.
- `src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs:146` `#EmitGroupMove` (:191, the
  `OperandText.AsString(..., deSign: false)` render) against `:116` `#EmitGroupToElementaryMove`.

**THE REPAIR IS ONE REPRESENTATION CODEC ASKED IN BOTH DIRECTIONS** (CLAUDE.md rule 5). The compiler already owns
the answer — `EmitGroupToElementaryMove` deposits the pinned representation bytes of exactly these items — and
`EmitGroupMove` re-derives a different one. That is the two-arm-dispatch shape with one arm written (memory:
`two_arm_dispatch`): extract the item→representation-image codec and have BOTH arms call it, so an elementary
sender into a group contributes the same bytes it would contribute as part of a group, and its width in the
receiving area is its representation width. Doing it in `EmitGroupMove` alone would leave the two arms as two
answers to one question.

## The sibling sweep the fixer must do

- Every other consumer of `MoveClassifier.IsGroupSender` and of the elementary/non-elementary decision — the
  RENAMES mis-classification is in the CLASSIFIER, so anything reading `BoundMove.Kinds` inherits it.
- Every other statement whose rules say "as if it were an alphanumeric to alphanumeric move" or otherwise move a
  group without conversion: the record-level file I/O paths, SORT/MERGE keys, REDEFINES views, CALL BY REFERENCE
  group parameters, and the group-image reads in `NumericRenderer`. Each must agree with the one codec.
- Every OTHER exclusion in a classifier whose justification is a code comment citing a clause. `IsGroupSender`'s
  RENAMES comment cited §13.18.45 for the opposite of what §13.18.45.4 GR2 says; the same shape is worth grepping
  for wherever a `not (…Place)` exclusion carries a § in its doc.
- `MoveEmitter`'s DISPLAY-sender coincidence is why this survived: `conformance:2023/move_group_overpunch`
  (`01 A PIC S9(3) VALUE -123. 01 G. 05 B PIC X(3). MOVE A TO G` -> '12L') has a DISPLAY sender, so it pins only
  GR6a's non-application and cannot see the no-conversion clause at all. The fix needs goldens with COMP-3, COMP,
  COMP-5 and floating-point senders into a group, in BOTH directions.

## Landed (wave 39)

**BOTH divergences fixed, plus the receiver-side sibling the sweep found.** `python scripts/spec/cite.py --check`
was re-run on every clause below before it was used.

**(1) The elementary-vs-group decision is now ONE predicate asked of BOTH operands.**
`MoveClassifier.IsGroupPlace` no longer excludes `RenamesPlace`: §13.18.45.4 GR2 — "When the THROUGH phrase is
specified, data-name-1 defines an alphanumeric group item" — and a `RenamesPlace` exists ONLY for the THROUGH
form, because `ReferenceResolver` forwards the no-THROUGH alias to the renamed item's own place, which is GR1
("all of the data attributes of data-name-2 become the data attributes of data-name-1"). So the designation needs
no further qualification and the control arm stays elementary, measured: `NOTHRU-SEND=[ 45]` (edited) beside
`THRU-SEND=[45 ]` (not edited). The comment that cited §13.18.45 for the opposite claim is gone.

**WHICH ARM DID I FIX? BOTH.** `MoveClassifier.Kind` re-spelled the RECEIVING half of the same GR4 sentence
structurally (`target.Item.IsGroup && !target.Item.IsAsIfElementary`) and now asks `IsGroupPlace(target)`. That
was a THIRD divergence, measured on this tree before the change and not in the note as filed: `MOVE (PIC S9(3)
VALUE -123) TO (66 R RENAMES a THRU b)` stored `123` where the structurally identical GROUP receiver stores `12L`
— §14.9.25.4 GR6 a) drops the operational sign only in a valid ELEMENTARY move. `PlaceRenderer.WriteGroupImage`
gained the `RenamesPlace` arm so a group-image store into an alias distributes through the `WriteRenames` store
the `Write` switch already owned, never a second `FromImage`.

**(2) "There is no conversion of data from one form of internal representation to another" is now ONE codec asked
in BOTH directions.** `OperandText.NonElementaryMoveSender` is `AsStorageImage` for a field operand — the
per-shape storage recipes that already define each leaf's representation (zoned, radix-2, BCD, IEEE, UTF-16BE
national, packed bits) — and the operand TEXT for a literal or figurative, which has no internal representation to
preserve (GR4's first sentence names "a literal or an elementary item" as the sending side, and §8.3.3.6.4 GR2
sizes a figurative from the receiver). Both `MoveEmitter.EmitGroupMove` and `EmitGroupToElementaryMove` call it,
so the two arms of the group move cannot answer the same question differently again. Measured on
`PIC 9(4) COMP-3 VALUE 1234`: the group direction deposited `0x01 0x23 0x4F` and the elementary-sender direction
deposited `'1' '2' '3' '4'`; both now deposit `0x01 0x23 0x4F` in three character positions. The BINARY and
COMP-5 siblings take the same arm and are asserted with it.

**Rows.** `GR-14.9.25.4-4` DIVERGES → CONFORMS (batch `pb425-finisher-pb430`).

**Golden + tests.** `conformance:85/pb430_gr4_no_conversion` (COBOL-85 is the introducing edition — every rule used
is in the 1985 standard and the divergences were silent at all four editions, so there is no edition below it for
a negative; the version matrix owns the RENAMES edition rows) and
`conformance-test:Gr4ElementaryVsGroupDecisionTests` (6 cases: the THROUGH sender against its structural twin, the
no-THROUGH control, the THROUGH receiver against its twin, and the COMP-3 / COMP / COMP-5 representation theory).
Every expected value is asserted as an EQUIVALENCE the standard requires between the alias and its structural
twin, never as a rendering this implementation happens to produce.

**Residue, named rather than claimed.** §14.9.25.4 GR9's variable-length route still tests the two operands
STRUCTURALLY (`send.Item.IsGroup`), so a THROUGH alias never enters it. That is correct for the alias side — its
span is a fixed sequence of leaf widths, so it can never be the variable-length group GR9's second conjunct
requires, and it cannot supply the §8.5.1.12 component carrier the walk needs — but §14.9.25.4 GR9's antecedent is met when
the OTHER operand is variable-length, and such a pair now takes GR4 instead. Whether §14.9.25.3 SR9's
compatibility screen admits that pair at all is unmeasured; it is registered as a lead, not claimed here.
