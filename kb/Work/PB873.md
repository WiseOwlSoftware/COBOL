# PB873 — LANDED — the digit image crosses the CALL boundary unsigned

Source: the `PB640` implementer report, "New defects" item (b). `kb/Work/PB834` records this lead in its body
and explicitly does NOT claim it ("That is a SILENT WRONG ANSWER in a different mechanism and wants its own
note; it is written down here so the lead is not lost"). This is that note.

## Repro — re-run on this tree, both argument arms

`scratchpad/reg5/pd_sign.cob` (PROGRAM-IDs `REG5PD` / `REG5PDS`), `--std 2023 --run`. `REG5PDS` is a SEPARATE
source unit, not a nested one, so the call goes through the run-time ABI. The formal `01 LR PIC S9(4)V99.` is
REDEFINED by `01 LRX REDEFINES LR PIC X(6).`, which makes it image-carried; the caller's control item is a
second item of the SAME picture, likewise redefined, displayed locally:

```
LOCAL      [00123M]                      <- the correct image of -12.34 ('M' = negative 4)
FORMAL     [00123D]  NUM=00123D          <- BY CONTENT: 'D' = POSITIVE 4. The sign is gone.
FORMAL     [00123D]  NUM=00123D          <- BY REFERENCE: the same
```

Both arms. The magnitude survives; the operational sign does not, so the callee computes with `+12.34` where
the argument is `-12.34`.

**The shape that HIDES it** — worth recording, because it is how this survived: if the CALLER's argument item is
ITSELF image-carried (redefined), the image travels intact and the probe prints `FORMAL [00123M]`
(`scratchpad/reg5/pb_sign.cob`, measured). The defect is only visible when the argument is a plain numeric item
and the FORMAL is the image-carried one — `feedback_probe_the_shape_the_subject_hides`.

## The rule, quoted

```
$ python scripts/spec/cite.py --check 14.2.3 "references to data-name-1"
  OK  §14.2.3 11)  (General rules)
      11) At all times in the activated element, references to data-name-1 and to data-name-2 are resolved in accordance with their description in the linkage section.
```

The formal's linkage-section description is `PIC S9(4)V99` — SIGNED. The adapter builds the image from the
ARGUMENT's `(Digits, Scale)` and a hard-coded unsigned profile, so the one attribute GR11 makes authoritative is
the one attribute the adapter never reads.

Two arms, the same hard-coding in both — `feedback_two_arm_dispatch`, and this time BOTH arms were measured
before filing rather than one.

## Code site and the shape of the fix

`src/Cobol.Net.Runtime/Control/CallAbi.cs#Text` and `#TextValue`. `Signed` has to come from the FORMAL, which
means the `(Digits, Scale)` meta the ABI carries today is not sufficient and the argument descriptor needs the
sign (and, for the same reason, the SIGN clause's SEPARATE / LEADING attributes — an image-carried formal with
`SIGN IS LEADING SEPARATE` has a seven-character image, not six). **That is a descriptor change, not a two-line
edit** (CLAUDE.md rule 5): do it once, as one `NumProfile` derived from the formal's own `PicInfo`, rather than
adding a `signed` boolean beside the two existing fields — the next attribute (SEPARATE, then `USAGE
NATIONAL`'s two-byte image) is then automatic.

## Landed — 2026-09-22 (wave 46 group K)

Re-probed on the wave-46 worktree build before the fix: `LOCAL [00123M]` / `FORMAL [00123D] NUM=00123D` on both
arms, exactly as filed. Root cause was the ABI's DESCRIPTOR, not the two adapters: `CobolArg` carried a
`(Digits, Scale)` pair, which can spell only a digit run. It is now `CobolArg(Mode, Carrier, NumProfile? Num)`
(Digits/Scale derived). The caller emits the argument's own `PicInfo.ProfileInitializer` (a literal or computed
value a signed DISPLAY profile of its own digits); `LandForFormal` sets `Num = formal` (GR9/GR10's record IS of
the formal's description); `Text` renders the cell through `CobolNum.FormatImage` under the carried description
(sign, SIGN SEPARATE position and byte form — §14.2.3 GR8, GR9 first branch) and writes back through its inverse;
`TextValue` lands into the FORMAL's profile (GR10: "a data item of the same description as the formal
parameter"). After: `FORMAL [00123M]`, `AFTER REF 00133M`. Goldens `85/pb873_signed_argument_image_carried_formal`,
`2002/pb873_by_value_image_carried_formal`; unit `CallAbiNumericCarrierDriftTests.ASignedArgument_KeepsItsSign_OnBothImageArms`
+ `TheCarriedDescription_DecidesTheImageShape`. GR-14.2.3-11 re-verdicted CONFORMS (batch w46k-pb873).
Sibling residue NOT closed here (reported as a lead): a BINARY/PACKED image-carried FORMAL's copy-in still decodes
the character carrier as operand (DISPLAY) text, so a COMP-3 argument into a REDEFINED COMP-3 formal reads 0.
