# PB5984 ruling
Verdict: DEFECT
Harm (DEFECT only): wrong_answer
Rule:
- `OK  §1985:VII.2.6.3 GR2  (2.6.3 General Rules)  the text is in GR2` — "Sequential organization is a permanent logical file structure in which a record is identified by a predecessor-successor relationship established when the record is placed into the file."
- `OK  §1985:VII.4.7.4 GR12  (4.7.4 General Rules)  the text is in GR12` — "The successor relationship of a sequential file is established by the order of execution of WRITE statements when the file is created."
- `OK  §1985:VII.4.7.4 GR7  (4.7.4 General Rules)  the text is in GR7` — "The execution of the WRITE statement releases a logical record to the operating system."
- `OK  §1985:VII.4.7.4 GR16  (4.7.4 General Rules)  the text is in GR16` — "If the ADVANCING phrase is not used, automatic advancing will be provided by the implementor to act as if the user had specified AFTER ADVANCING 1 LINE"
- `OK  §1985:VII.2.8.4 GR1  (║2.8.4 General Rules║)  the text is in GR1` — "Any method used will not be reflected in the record area or the record size used within the program"
- Context (not a rule designator; `cite.py --find`, edition 1985): `§1985:C.3 (19)` "The BEFORE/AFTER ADVANCING phrase of the WRITE statement is dependent upon a device capable of vertical positioning or of an action based on mnemonic-name."

GnuCOBOL makes the same choice; it is an extension's organization, and its choice contradicts the 1985 rules above, so rule 1's GnuCOBOL rung cannot adopt it.

Expected from the text: three WRITE statements release three logical records (GR7) whose predecessor-successor relationship is the order of the WRITEs (GR12, VII.2.6.3 GR2). A READ of the file returns exactly ALPHA, BRAVO, CHARLIE with status 00 and RL 5, 5, 7, then AT END, whatever ADVANCING phrase each WRITE carried: the ADVANCING phrase positions the line "on a representation of a printed page" (GR16); it releases no record. The RECORD DELIMITER method is a length method that "will not be reflected in the record area or the record size" (VII.2.8.4 GR1), which a bare delimiter read back as an RL=0 record, or a form feed and carriage return read back inside the record area, both violate.

Mechanism: `src/WiseOwl.Cobol.Runtime/IO/SequentialConnector.cs#WriteAdvancingRecord` treats a RECORD DELIMITER IS LINE-SEQUENTIAL file as a text print stream (`IsRecordPrintStream` is false for `_lineSequential`, the DOC-A.1-146 (c') model built for the 2023 line sequential organization). It calls `Position` -> `Advance` -> `WriteTravel` -> `#AdvanceLines`, which writes `_lineEnd` once per advanced line (the same bytes as the record delimiter), `#Advance` writes `'\f'` for PAGE, `#WriteTravel` writes `'\r'` for an amount of 0, and `#Present` writes the record through `EmitRecord` with no delimiter of its own. The delimiter is thus both the record boundary and the unit of vertical travel, so the READ side (`ReadRecord`, which splits on the delimiter) cannot recover the records the WRITEs released. Once a file has taken one ADVANCING write (`_printControl`) or the program declares ADVANCING for it (`AdvancingDeclared`), `#WriteRecord` routes every plain WRITE through the same arm (`SupportsVerticalPositioning`), so the defect reaches plain WRITEs too.

Fix shape: the edition decides the medium form of a delimiter-framed file, behind the existing `DialectBehavior.LineSequentialFileRules` (ChangedIn 2023, the PB5903 gate that `ReadRecord`/`WriteRecord` already ask). Before 2023 the file is sequential organization with a length method, not a line sequential file, so a WRITE with ADVANCING on it must write exactly one record and one delimiter: the positioning has no representation on that medium (C.3 (19): ADVANCING is dependent on a device capable of vertical positioning; a delimited mass-storage file is not one), and no blank line, form feed or bare carriage return may reach it. The root fix is in the routing, not in the reader: `WriteAdvancingRecord` (and `SupportsVerticalPositioning`'s reroute) asks the edition's file rules once, and a pre-2023 delimiter-framed file takes the record arm (`WriteRecord`'s path, which PB5903 already made keep the record at its size, the PB5914 point) while the ADVANCING statement's other effects stay (status, LINAGE-COUNTER if a LINAGE clause is present). A reader-side skip of empty lines is not a fix: it cannot tell a positioning line from a record, and does nothing for `\f` and `\r`. The representation choice (positioning not represented on a delimited file before 2023) is implementor latitude bounded by GR12; record it as a docs/conformance determination with the GnuCOBOL contrast stated. Golden at `--std 85` beside PB5903's `cases/VII.4.4@1985-READ-STATEMENT/pb5903_line_delimited_length_conflict_85` (or a VII.4.7 WRITE case): the four write patterns above (AFTER n, BEFORE n, AFTER/BEFORE PAGE, ADVANCING 0) each read back as exactly the records written, with status 00 and their lengths; the same program at `--std 2023` with ORGANIZATION LINE SEQUENTIAL keeps today's 2023 behavior unless a 2023 adjudication says otherwise (out of this ruling's scope).

Reasoning: The 1985 edition has no line sequential organization. A file with RECORD DELIMITER IS LINE-SEQUENTIAL (implementor-name-1, VII.2.8.4 GR3) is ORGANIZATION SEQUENTIAL, whose records are exactly those the WRITE statements released, in WRITE order (VII.2.6.3 GR2, VII.4.7.4 GR7 and GR12). Nothing in VII.4.7.4 GR16 a-h lets the ADVANCING phrase add, split or merge records; it positions the presented line on a page representation. GR16's own equivalence (no phrase acts as AFTER ADVANCING 1 LINE) is a second, internal witness: the compiler writes different files for the two spellings. The probes show three wrong answers a user program sees: phantom records (a and b, with status 04), and three records merged into one with control characters in the record area (d). The harm is wrong_answer only: nothing crashes and no legal source is refused.
