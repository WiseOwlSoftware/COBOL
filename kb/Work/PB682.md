# PB682 — OPEN — the message names an operand the program never wrote

Found 2026-09-05 by the `PB347` implementer (report §"New defects" B) in its own COBOLNET1757 messages, and left
alone there deliberately: changing only the new sites would have made the corpus of messages inconsistent.

## The shape

`GetText()` on a parser rule context concatenates the tokens with no separator. Any diagnostic that quotes an
operand that way — `rn.GetText()` is the established spelling at the pre-existing `CheckReleaseRecord`,
`ResolveFile`, `CheckCorrespondingGroupOperand` and dozens more — prints a qualified or decorated reference as one
glued word. Not a conformance rule: §4.2.2 requires the indication, not a wording; this is the product bar (a user
searching their source for `OR-KEYOFOUT-REC` finds nothing).

## Fix

One shared "source text of a context" helper — the token stream's interval text (which preserves the program's own
spacing), or a re-spaced join of the tokens — and every diagnostic site that quotes an operand routed through it.
Sweep with `grep -rn "GetText()" src/Cobol.Net.Compiler --include=*.cs` and classify each hit: operand quoted in a
message (convert), or text used as an identity key (leave, and say so beside it). A unit test that binds a qualified
reference in a negative program and asserts the message contains the spaced form.
