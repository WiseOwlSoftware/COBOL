# PB25 — LANDED — LOWER-CASE/UPPER-CASE: the LOCALE arm and a figurative argument

> ⚙ **flags:** crashes · rejects-legal-source
> · **`FUNCTION LOWER-CASE(x LOCALE loc)`** — the bracketed `[LOCALE locale-name-1]` arm of §15.57.2 is REFUSED
>   rather than diagnosed as the §A.4.9 non-support it is.
> · **A FIGURATIVE CONSTANT or ALL-literal argument compiles clean and ABORTS AT RUN TIME** —
>   `IntrinsicRenderer.StrArgVisitor`'s `Visit(BoundFigurative)` / `Visit(BoundAllLiteral)` both render
>   `EmitText.LoudValue`. Wrong stage again, and NOT a duplicate of the residue's "figurative as a §15 string
>   argument" row: this is the same defect reached through a different visitor.

## ⛔ THE FIGURATIVE HALF — THE RIGHT ANSWER WAS ALREADY WRITTEN DOWN, ONE FILE AWAY

`FUNCTION LOWER-CASE(SPACE)` is **legal source**: §8.3.3.6.3 SR1 admits a figurative constant "whenever 'literal'
appears in a format or when a rule allows it", and §8.4.3.2.3 SR8 makes argument-1 "an identifier, a literal, a
boolean expression, or an arithmetic expression". Neither SR1 exception applies (the literal is not restricted to
numeric; no syntax rule prohibits it).

**And `OperandText.AsString` had implemented the correct image all along — citing the rule in its own comments.**
Its entry intercepts `BoundFigurative` PCS-aware, and its `BoundAllLiteral` arm is annotated "length-unspecified:
the literal once (GR3c)". `StrArgVisitor` sat beside it with a second, LOUD copy of the same dispatch — and its
`BoundFieldOperand` arm *already* delegated to `OperandText.AsString`. So the fix is two arms delegating the same
way, not a third implementation ([[feedback_one_rule_one_place]], [[feedback_change_the_dispatch_not_the_callers]]).

**The lengths are §8.3.3.6.4 GR3's** — the "length of the string is NOT specified in the rules for the context"
case, which is exactly a bare function argument: **(b)** a figurative other than `ALL literal-1` is ONE character;
**(c)** otherwise the length of literal-1. That is why `SPACE` is one space and `ALL "AB"` is two characters.

## ⛔ THE SWEEP FOUND A SECOND COPY OF THE MISTAKE, IN A DIFFERENT LAYER

`FUNCTION LENGTH(SPACE)` failed too, with its own message from the BINDER — and its comment asserted the rejection
was spec-correct. **Half of it was.** One match arm refused "a numeric/figurative literal" for §15.50.3 r1, which
admits "an alphanumeric, national, or boolean literal": that excludes a NUMERIC literal (correct) and says nothing
about figurative constants, while §8.3.3.6.4 GR1 makes SPACE an ALPHANUMERIC character value here — precisely what
r1 permits. **One code standing for two rules enforced neither** — §0's own PB1 lesson, found again.

**MEASURED** (golden `pb25_figurative_intrinsic_argument`, every value derived before the run):
`LOWER-CASE(SPACE)`=`" "` · `UPPER-CASE(SPACE)`=`" "` · `LOWER-CASE(QUOTE)`=`"` · `LOWER-CASE(ALL "AB")`=`ab` ·
`UPPER-CASE(ALL "ab")`=`AB` · `REVERSE(ALL "AB")`=`BA` · **`LENGTH(SPACE)`=1 vs `LENGTH(ALL "ABC")`=3** — the pair
that distinguishes GR3b from GR3c, and therefore the assertion that the RULE is implemented rather than that the
crash stopped.

## ⛔ THE LOCALE HALF — THE ENTRY'S FRAMING WAS SLIGHTLY OFF, AND THE MEASUREMENT SAYS WHERE

The FUNCTION side was **already** correct: `locale_keyword_a49` has pinned `FUNCTION LOWER-CASE(X LOCALE LOC1)` →
`COBOLNET1518` since PB37. What was broken is one level up — **the `SPECIAL-NAMES` LOCALE clause was a raw parse
error**, so a locale-name could never be DECLARED at all:

```
SPECIAL-NAMES.  LOCALE FR IS "fr_FR".
   -> COBOL0308: unexpected '"fr_FR"'. A data-name is expected here, not a literal.
```

With no `localeClause` in the grammar the entry fell into `implementorSwitchEntry`, matched as far as the bare word
`LOCALE`, re-entered as `FR IS "fr_FR"` and died on the LITERAL — **pointing at the wrong token, for a clause the
standard defines.** §A.4.9 **item 10** is "SPECIAL-NAMES paragraph: LOCALE clause and LOCALE phrases in the
ALPHABET clause (12.3.7)", so this is an optional-locale element whose non-support is conformant per §4.2.7 /
§A.4.1 **only because it is DIAGNOSED**. An unexplained rejection is not documented non-support. It now parses
(superset-parse / bind-narrow) and carries the same cited `COBOLNET1518`.

⚠ **WHY A TEXT PREDICATE AND NOT A LEXER TOKEN, recorded because the obvious move breaks something.** LOCALE *is*
reserved from 2002 (§8.9; `reserved-words.json` r2002/r2014/r2023), so tokenizing it looks right — but
`IntrinsicBinder.KeywordWordOf` detects the FUNCTION-side LOCALE phrase precisely because it arrives as an ordinary
bare-word argument. **A token would silently break the already-working diagnostic.** Two comments (in
`IntrinsicBinder` and in `locale_keyword_a49.cob`) asserted "LOCALE is not a reserved word", which is wrong by the
repo's own data; both now say *not a lexer token*, and say why.
⚠ **EDITION-GATED, and the counterpart is tested.** At COBOL-85 LOCALE is an ordinary user word, so
`SPECIAL-NAMES. LOCALE IS FOO.` is a legal implementor-switch entry there and must keep parsing —
`SpecialNamesLocaleEditionTests` pins that, plus the shape guard that a locale-name-less `LOCALE IS FOO` is not
annexed as a malformed locale clause at 2023 either.

## ▶ WHAT THIS DID NOT FIX — [[PB48]]

`FUNCTION LOWER-CASE(ZERO)` and `FUNCTION NUMVAL(ZERO)` still fail, and **not through these arms**: `ZERO` is
rewritten to an ARITHMETIC zero by the token rewriter before binding, so it arrives as a `BoundNumericLiteral` and
never reaches the figurative path at all. Different mechanism, different layer, its own note — and the fix there is
genuinely delicate, because `FUNCTION SQRT(ZERO)` needs the numeric reading the rewrite exists to give.
