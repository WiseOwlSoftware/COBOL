# PB892 — LANDED — a rule about activation, implemented only where an activation is a statement

Source: the `PB408` report, "New defects" items 1 and 2.

## The rule

```
$ python scripts/spec/cite.py --check 14.9.18.4 "an exception condition is raised in the activating runtime element if checking for that exception condition is enabled in the activating runtime element"
  OK  §14.9.18.4 1) b)  (General rules)
      b) If the RAISING phrase is specified, an exception condition is raised in the activating runtime
      element if checking for that exception condition is enabled in the activating runtime element, and
      execution continues in ...
```

The obligation is on the ACTIVATING ELEMENT and says nothing about the activation being a statement.

## Arm A — a UDF activated in expression position

`src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs:214` carries the finding in its own comment:

> *expression — so the invocation goes out WITHOUT `siteHandlesPropagation`: a callee-staged RAISING …*

`ProgramTable.ApplyPropagationDefault` therefore DISCARDS the staged condition, and the declarative never
runs. The PB408 report measured `PERFORM UNTIL FUNCTION F408M = 7` with a matching declarative and
`>>TURN EC-USER CHECKING ON`: it printed `IN-FN / AFTER-FN` and no declarative.

⛔ **This registrar's own probe did NOT reach the defect**, and the reason is recorded so nobody re-runs it
the same way: `<scratch>/reg6/probe/q20_fn_expr_ec.cob` was refused at compile time —

```
  q20_fn_expr_ec.cob(9,12): error COBOLNET0717: GOBACK RAISING EC-USER-Z: an EC-USER exception-name shall be
  specified in the RAISING phrase of the procedure division header (ISO §14.9.18.3 SR2 ...)
```

— which is CORRECT (SR2 is real and the probe omitted the header's RAISING phrase). The behavioural
reproduction needs `PROCEDURE DIVISION RETURNING R RAISING EC-USER-Z`; the fixer writes it that way. The
CODE SITE above is decisive about what is emitted, and the PB408 implementer measured it on their tree, so
the finding stands; only my re-run of it is incomplete, and saying so is the point.

## Arm B — the typed INVOKE (LEAD, not measured)

`CALL` gets an activation-boundary default (`ProgramTable.CallProgram`'s `siteHandlesPropagation: false`
→ discard); a method invocation is a direct C# call with no runtime chokepoint, so when an INVOKE site emits
no pickup the staged slot is simply left set. `OoEmitter.cs:1010` — `EmitInvokePickup(site) =>
U.Call.EmitPropagationPickup(site)` — is the pickup; there is no boundary for the case where it is absent.
Inside ONE compilation group this is unreachable (any RAISING phrase makes the group EC-active at
`BinderDriver.cs:147`, so every site emits a pickup), and the SEPARATE-COMPILATION case needs a
two-assembly OO probe neither the PB408 implementer nor this registrar built. **It pre-exists for the
exception-OBJECT slot** — `SetPropagatingObject` was always unconditional — and PB408 extended the same
shape to names.

## The remedy

A per-EVALUATION landing for an activation that is not a statement, rather than an enablement test at a
`__pc`-anchored statement position. This is a design change to the activation boundary; both arms share it,
which is why they are one note.

**The mechanism.** `UdfBinder.DrainPending` (the ONE drain of the pending pre-op list) marks every activation it
hands a carrier `IActivatingStatement.InExpression` and stamps the carrying statement's §7.3.25 profile — the
per-evaluation activations used to carry an EMPTY profile, because `EcBinder.EcWrap`'s stamp never enters a
condition; `OoBinder.OoWrapPropertyOps` marks the property accessors. `StatementBinder.BindStatement` wraps a
statement that drained any in `BoundActivationSite` (save/zero/restore counter: the LOWEST statement, GR2 a) 3.).
An `InExpression` pickup lands RESUME through `DispatchState.OperandActivationResume` (throws `RaiseResumeSignal`
for AT procedure-name and AT NEXT STATEMENT); `EcEmitter.EmitActivationSite` catches it around the statement.
`CallEmitter.FunctionActivationText` — the second activation text — is DELETED: the lambda body is `EmitCall`'s own
captured output, so EC-FUNCTION-NOT-FOUND and the pickup behave the same in both positions. ⚠ DETERMINATION: an
object-property accessor (§8.4.3.9.4 GR1/GR2 — "as though … invoked, in accordance with the rules of the INVOKE
statement") is an operand activation, so it lands at the statement it is written in; the rejected reading (treat
it as its own INVOKE statement) has no statement to resume after.

Goldens `2002/pb892_operand_activation_resume` (eight cases), `2014/pb892_inline_invocation_resume` (inline
invocation, property GET, EC-FUNCTION-NOT-FOUND in a window), negative `pb892-operand-activation-below-2002`;
`OperandActivationDriftTests` (Unit). Design: `COBOLNET_CONDITIONS_EXCEPTIONS_DESIGN.md` RAISING propagation.

## NEXT — Arm B, now MEASURED (it was a lead)

Two-assembly probe `w48s/sep/` (`P892A.cob` EC-free main, `P892B.cob` separately compiled program + class):
the EC-free main INVOKEs (universal) a separately compiled method that ends `GOBACK RAISING EXCEPTION EC-USER-BZ`;
nothing picks it up; the main then CALLs `P892B`, which is EC-active and INVOKEs a method that raises NOTHING —
and `P892B`'s EC-USER-BZ declarative RUNS (`IN-QUIET / DECL-IN-B / B-AFTER-QUIET`). Expected (§14.9.18.4 GR1 b)):
no declarative — the condition was never raised in its unchecked activator and must not surface anywhere else.
CALL has the boundary default (`ProgramTable.CallProgram` `siteHandlesPropagation: false`); an INVOKE has no
runtime chokepoint, and emitting a discard at an EC-free group's INVOKE breaks the asserted zero-scaffolding
invariant. A pre-activation fence at EC-active pickup sites does NOT suffice either: an EC-free element CALLed
from an EC-active one can leave a stale staging that its EC-active activator's pickup then takes. The design needs
the staging to name the activation that made it (a method-activation frame the runtime can see) — a change to the
activation boundary, left to a finisher. `ExceptionState.TakePropagated` (the CALL boundary default) also leaves the
exception-OBJECT slot staged, the pre-existing half the registrar recorded.

**Arm B — the staged condition names its activation.** GR1 b) raises the condition in ONE element, the one the
returning element returns to. The staged slots (`ExceptionEngine._propagated` / `_propagatedObject`) now record the
ACTIVATING activation's identity at staging (`ModuleStack.ActivatingActivation`), and `TakeRaisedPropagation` /
`TakePropagatedObject` take a staging only when the pickup runs IN that activation (`ModuleStack.CurrentActivation`).
`ModuleStack` was already the run unit's one activation record — every mechanism §15.65.4 r5 names pushes a frame
(CALL, function reference and the main in `ProgramTable`; INVOKE and inline invocation in the emitted method body) —
so each frame now carries a unique, never-reused id, and nothing is emitted anywhere (zero scaffolding holds). The
predecessor's "a pre-activation fence is insufficient" is right, and this is not a fence: the identity is the
ACTIVATOR's, so a staging left by an EC-free intermediate is invisible to the element beneath it. The CALL-only
registry discard (`siteHandlesPropagation:false` → `ProgramTable.ApplyPropagationDefault`) and
`ExceptionEngine.TakePropagated` — which also left the OBJECT slot staged — are DELETED: one rule for every
activation kind (rule 5; the design doc records it). The main program's staging is for activation −1, so GR3's
"is ignored" needs no code either.

**The crash — the other entry of the same signal.** A declarative is entered by an exception (`__RunUse` catches
`ResumeSignal`) or by a PERFORM in the nondeclarative portion (§14.9.49.3 SR4); only the first had a landing.
`BoundOutOfLinePerform.EntersDeclarative` marks the second (range declarative, `ctx.Enclosing.Declarative` null), and
`ControlFlowEmitter.EmitPerformedRange` catches `ResumeSignal` around that execution of the range: NEXT STATEMENT
completes the range (GR2 b) — the TIMES / UNTIL phrase goes on), procedure-name is GR3's GO TO through
`ResumeTransfer`. Emitted only when the unit has a RESUME (`DispatchState.UnitHasResume`).
