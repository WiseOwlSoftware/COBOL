# PB892 — OPEN — a rule about activation, implemented only where an activation is a statement

Source: the `PB408` report, "New defects" items 1 and 2.

## The rule

```
$ python scripts/spec/cite.py --check 14.9.18.4 "an exception condition is raised in the activating runtime element if checking for that exception condition is enabled in the activating runtime element"
  OK  §14.9.18.4 1) b)  (General rules)
      b) If the RAISING phrase is specified, an exception condition is raised in the activating runtime
      element if checking for that exception condition is enabled in the activating runtime element, and
      execution continues in ...
```

The obligation is on the ACTIVATING ELEMENT and says nothing about the activation being a statement.

## Arm A — a UDF activated in expression position

`src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs:214` carries the finding in its own comment:

> *expression — so the invocation goes out WITHOUT `siteHandlesPropagation`: a callee-staged RAISING …*

`ProgramTable.ApplyPropagationDefault` therefore DISCARDS the staged condition, and the declarative never
runs. The PB408 report measured `PERFORM UNTIL FUNCTION F408M = 7` with a matching declarative and
`>>TURN EC-USER CHECKING ON`: it printed `IN-FN / AFTER-FN` and no declarative.

⛔ **This registrar's own probe did NOT reach the defect**, and the reason is recorded so nobody re-runs it
the same way: `<scratch>/reg6/probe/q20_fn_expr_ec.cob` was refused at compile time —

```
  q20_fn_expr_ec.cob(9,12): error COBOLNET0717: GOBACK RAISING EC-USER-Z: an EC-USER exception-name shall be
  specified in the RAISING phrase of the procedure division header (ISO §14.9.18.3 SR2 ...)
```

— which is CORRECT (SR2 is real and the probe omitted the header's RAISING phrase). The behavioural
reproduction needs `PROCEDURE DIVISION RETURNING R RAISING EC-USER-Z`; the fixer writes it that way. The
CODE SITE above is decisive about what is emitted, and the PB408 implementer measured it on their tree, so
the finding stands; only my re-run of it is incomplete, and saying so is the point.

## Arm B — the typed INVOKE (LEAD, not measured)

`CALL` gets an activation-boundary default (`ProgramTable.CallProgram`'s `siteHandlesPropagation: false`
→ discard); a method invocation is a direct C# call with no runtime chokepoint, so when an INVOKE site emits
no pickup the staged slot is simply left set. `OoEmitter.cs:1010` — `EmitInvokePickup(site) =>
U.Call.EmitPropagationPickup(site)` — is the pickup; there is no boundary for the case where it is absent.
Inside ONE compilation group this is unreachable (any RAISING phrase makes the group EC-active at
`BinderDriver.cs:147`, so every site emits a pickup), and the SEPARATE-COMPILATION case needs a
two-assembly OO probe neither the PB408 implementer nor this registrar built. **It pre-exists for the
exception-OBJECT slot** — `SetPropagatingObject` was always unconditional — and PB408 extended the same
shape to names.

## The remedy

A per-EVALUATION landing for an activation that is not a statement, rather than an enablement test at a
`__pc`-anchored statement position. This is a design change to the activation boundary; both arms share it,
which is why they are one note.
