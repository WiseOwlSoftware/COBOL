# PB371 — the vacuously-satisfied rule, and the verdict it has earned

**Rows:** `SR-14.9.27.3-7`, `SR-14.9.30.3-5`, `SR-14.9.47.3-2`. All three are excluded from batch b1 and remain
verdict-less GAPs pending the answer.

## The bare question

**A syntax rule that constrains a CLAIMED statement (OPEN, READ, UNLOCK) but whose antecedent can only be created
by a NOT-CLAIMED module (the APPLY COMMIT clause, A.4.3) is vacuously satisfied by every compilable program. Does
it record as `CONFORMS`, witnessed by a test pinning that the antecedent is rejected — or as
`NEEDS-OWNER-DECISION` until the module's disposition changes?**

`DOCUMENTED-NON-SUPPORT` is NOT one of the options, and that is not my call — see below.

## The three rules

> §14.9.27.3 SR7: The sharing phrase shall not be specified for a file subject to an APPLY COMMIT clause.
> §14.9.30.3 SR5: If file-name-1 is subject to an APPLY COMMIT clause, none of the phrases IGNORING LOCK, WITH
> LOCK, or WITH NO LOCK shall be specified.
> §14.9.47.3 SR2: File-name-1 shall not be a file specified in an APPLY COMMIT clause.

All three `--check` → **OK** against their clauses. Measured (`probe/open-p1/apc1.cob`, `probe/sr5/apply.cob`,
`probe/unlock/p7.cob`): an I-O-CONTROL paragraph containing `APPLY COMMIT ON <file>.` is a parse error at every
edition — `ioControlClause` admits only `sameClause`, `multipleFileClause`, `rerunClause` and `genericClause`,
and `genericClause` (`IDENTIFIER (IDENTIFIER | literal)*`) cannot swallow the reserved COMMIT token. So no
accepted program can put a file in an APPLY COMMIT clause, no OPEN / READ / UNLOCK can violate the rule, and
there is nothing left to adjudicate per row.

## Why DOCUMENTED-NON-SUPPORT is already refused, and by whom

⛔ **The landed `commit-and-rollback-only` derived selector in `tests/version-matrix/inventory-schema.json` NAMES
these exact rows and deliberately EXCLUDES them**, with its reason recorded: each one's verdict field would speak
about OPEN / READ / UNLOCK, facilities A.4.7 CLAIMS, and §4.2.7 discharges non-support through user documentation
that declines commit and rollback, never UNLOCK — so *stamping them would document a claimed facility as declined
AND, since the drift test PINS every selected row, permanently block their correct adjudication.* The selector's
`$selector` prose lists fourteen such rules across LOCK MODE, SAME, sharing mode, CLOSE, DELETE, OPEN, READ,
REWRITE, UNLOCK, fatal-exception handling and DOC-A.1-28.

**One answer therefore settles all fourteen**, and it becomes either three more CONFORMS-but-untested rows plus a
witness golden apiece, or a standing NEEDS-OWNER-DECISION family that stays GAP until A.4.3 is revisited.
