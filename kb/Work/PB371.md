# PB371 — the vacuously-satisfied rule, and the verdict it has earned

> **⚖ OWNER DECISION, 2026-09-02 (AskUserQuestion): CONFORMS + A WITNESS PINNING THE REFUSAL.** The rule holds
> because its antecedent is refused with a NAMED diagnostic; each row closes on the negative golden that pins
> that refusal. **LANDED 2026-09-03** — see "How the decision was applied" at the foot of this note.

**Rows as raised:** `SR-14.9.27.3-7`, `SR-14.9.30.3-5`, `SR-14.9.47.3-2` — all three excluded from batch b1 and
verdict-less GAPs pending the answer. **Rows as landed: SEVEN**, because one answer settles the whole family and
the family is exactly the rules whose antecedent is unsatisfiable (below).

## The bare question

**A syntax rule that constrains a CLAIMED statement (OPEN, READ, UNLOCK) but whose antecedent can only be created
by a NOT-CLAIMED module (the APPLY COMMIT clause, A.4.3) is vacuously satisfied by every compilable program. Does
it record as `CONFORMS`, witnessed by a test pinning that the antecedent is rejected — or as
`NEEDS-OWNER-DECISION` until the module's disposition changes?**

`DOCUMENTED-NON-SUPPORT` is NOT one of the options, and that is not my call — see below.

## The three rules

> §14.9.27.3 SR7: The sharing phrase shall not be specified for a file subject to an APPLY COMMIT clause.
> §14.9.30.3 SR5: If file-name-1 is subject to an APPLY COMMIT clause, none of the phrases IGNORING LOCK, WITH
> LOCK, or WITH NO LOCK shall be specified.
> §14.9.47.3 SR2: File-name-1 shall not be a file specified in an APPLY COMMIT clause.

All three `--check` → **OK** against their clauses. Measured (`probe/open-p1/apc1.cob`, `probe/sr5/apply.cob`,
`probe/unlock/p7.cob`): an I-O-CONTROL paragraph containing `APPLY COMMIT ON <file>.` is a parse error at every
edition — `ioControlClause` admits only `sameClause`, `multipleFileClause`, `rerunClause` and `genericClause`,
and `genericClause` (`IDENTIFIER (IDENTIFIER | literal)*`) cannot swallow the reserved COMMIT token. So no
accepted program can put a file in an APPLY COMMIT clause, no OPEN / READ / UNLOCK can violate the rule, and
there is nothing left to adjudicate per row.

## Why DOCUMENTED-NON-SUPPORT is already refused, and by whom

⛔ **The landed `commit-and-rollback-only` derived selector in `tests/version-matrix/inventory-schema.json` NAMES
these exact rows and deliberately EXCLUDES them**, with its reason recorded: each one's verdict field would speak
about OPEN / READ / UNLOCK, facilities A.4.7 CLAIMS, and §4.2.7 discharges non-support through user documentation
that declines commit and rollback, never UNLOCK — so *stamping them would document a claimed facility as declined
AND, since the drift test PINS every selected row, permanently block their correct adjudication.* The selector's
`$selector` prose lists fourteen such rules across LOCK MODE, SAME, sharing mode, CLOSE, DELETE, OPEN, READ,
REWRITE, UNLOCK, fatal-exception handling and DOC-A.1-28.

**One answer therefore settles all fourteen**, and it becomes either three more CONFORMS-but-untested rows plus a
witness golden apiece, or a standing NEEDS-OWNER-DECISION family that stays GAP until A.4.3 is revisited.

## How the decision was applied, 2026-09-03 — and why it is SEVEN rows, not fourteen

The `commit-and-rollback-only` selector's prose names **fourteen rules** (plus `DOC-A.1-28`) that mention APPLY
COMMIT only as an antecedent. **The owner's answer reaches only the seven whose antecedent is UNSATISFIABLE** —
which is the selector's own count: *"Seven of them have no surviving content — their antecedents are simply
unsatisfiable."* The other seven state their content under the COMPLEMENT ("Except when the file is specified
in…", "is NOT subject to…"), which under the decline is the only state this implementation has, so their content
is LIVE and their verdicts are about the claimed facility. Measured on the inventory before landing:

| Rule | Antecedent | Landed |
|---|---|---|
| `SR-12.4.5.9.3-1` | LOCK MODE for a file *subject to* APPLY COMMIT | **CONFORMS** · `conformance:negative/apply-commit-lock-mode` |
| `SR-12.4.6.4.3-11` | SAME area mixing a *subject* file with a non-subject one | **CONFORMS** · `conformance:negative/apply-commit-same-area` |
| `GR-12.4.6.4.4-3` | SAME area shared between **two** files subject to commit and rollback ("another *such* file") | **CONFORMS** · `conformance:negative/apply-commit-same-area-shared` |
| `SR-14.9.27.3-7` | OPEN sharing phrase on a *subject* file | **CONFORMS** · `conformance:negative/apply-commit-open-sharing` |
| `SR-14.9.30.3-5` | READ lock phrases on a *subject* file | **CONFORMS** · `conformance:negative/apply-commit-read-lock` |
| `SR-14.9.35.3-5` | REWRITE lock phrases on a *subject* file | **CONFORMS** · `conformance:negative/apply-commit-rewrite-lock` |
| `SR-14.9.47.3-2` | UNLOCK of a *specified-in* file | **CONFORMS** · `conformance:negative/apply-commit-unlock` |

The antecedent for all seven is the same construct — the **APPLY COMMIT clause, ISO §12.4.6.3, Annex A.4.3
item 2** — and the named diagnostic that refuses it is **COBOLNET1709** (`apply-commit-clause-unsupported`),
landed by witness cluster B2 through `DeclinedFacilityPass.VisitApplyCommitClause`. ⚠ The note's own measurement
above ("an I-O-CONTROL paragraph containing `APPLY COMMIT ON <file>.` is a parse error at every edition") was
taken BEFORE that cluster landed and is now stale: the refusal is named, which is precisely what makes the
owner's answer available.

⚠ **The SAME clause needed TWO fixtures, not one, and the first draft got that wrong.** SR-12.4.6.4.3-11 and
GR-12.4.6.4.4-3 both govern the SAME clause, so one fixture looked sufficient — but their antecedents differ:
SR11 forbids mixing a commit-subject file with one that is **not** subject, while GR3 says "another **such**
file", i.e. BOTH subject. A shared fixture writing SR11's shape would have given GR3 a witness that never writes
its own antecedent, which is precisely the property these fixtures exist to supply. Caught in self-review, split
into `apply-commit-same-area` (SR11) and `apply-commit-same-area-shared` (GR3).

**Each row got its OWN fixture rather than sharing `declined-apply-commit`,** and that is the load-bearing half.
A witness that only wrote `APPLY COMMIT` alone would keep passing the day A.4.3 is claimed, leaving seven
CONFORMS verdicts standing on an antecedent that had become reachable. Each fixture writes *the rule's own
forbidden construct* — the LOCK MODE clause, the SAME area, the OPEN sharing phrase, `READ … WITH LOCK`,
`REWRITE … WITH LOCK`, `UNLOCK` — beside the APPLY COMMIT clause, so it stops failing exactly when the row needs
re-adjudicating.

**The seven rules the decision does NOT reach**, with what they carry today, so no later reader mistakes them for
unfinished PB371 work: `GR-9.1.15-3` (blank/GAP — sharing-with-all-other mode, live), `GR-14.9.6.4-9`
(PARTIAL/GAP), `GR-14.9.10.4-7` (PARTIAL/GAP), `GR-14.9.10.4-15` (CONFORMS/OK), `SR-14.9.27.3-8` (DIVERGES/GAP —
the exact COMPLEMENT of `-7`), `GR-14.9.27.4-6` (CONFORMS but no test-ref, so GAP), `GR-14.6.13.1.3-8`
(CONFORMS/OK). `DOC-A.1-28` is likewise untouched: it is the A.1 documentation item for the facility, and its
shape is the one PB280 Q1 answered by predicate (`a1-optional-not-provided`), not this one.

**Two fixture errors caught by the CLI probe, recorded because both would have "passed" the negative runner for
the wrong reason** (a rejection is a rejection, whatever the code): `OPEN INPUT F SHARING WITH ALL OTHER` is
wrong phrase order — §14.9.27.2 Format 1 puts `[ sharing-phrase ]` before the FILE LIST — and
`UNLOCK F ALL RECORDS` is not ISO at all: §14.9.47.2 is `UNLOCK file-name-1 [ RECORD | RECORDS ]` (RENDERED, PDF
p798 / folio 768; `ALL` is a GnuCOBOL extension). Both drew bare COBOL0001 rather than COBOLNET1709. The compiler
was right in both cases.
