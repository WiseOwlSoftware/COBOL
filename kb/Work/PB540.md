# PB540

## Mechanism — usage-clause-p1
usage-p1-F3-sr3-usage-picture-screen-keys-on-anyAlpha-so-a-numeric-edited-picture-escapes

### Expected, from the standard
SR3 admits BINARY / COMPUTATIONAL / PACKED-DECIMAL 'only with a picture character-string that describes a numeric item'. A numeric-EDITED picture describes a numeric-edited item, a different category of GR3's list, so `01 A PIC ZZ9 USAGE COMP.` shall be rejected -- as shall the PACKED-DECIMAL and COMP-5 spellings of the same entry.

```
$ python scripts/spec/cite.py --check 13.18.60.3 "only with a picture character-string that describes a numeric item"
  OK  §13.18.60.3 3)  (Syntax rules)
```

### Observed
All three compile clean at --std 85, 2002, 2014 and 2023 (u_sr3_numedit_comp, u_sr3_edit_packed, u_sr3_edit_comp5, e_sr3_edit_85/2002/2014/2023). The guard's predicate is `anyAlpha`, which is false for `ZZ9`; the entry then binds as category NumericEdited carrying a binary usage. The accepted item is INTERNALLY INCONSISTENT, which is why this is worth landing rather than filing as a cosmetic under-rejection: `FUNCTION BYTE-LENGTH` reports 1 for `PIC ZZ9 USAGE COMP` where the same picture without the usage reports 3 (u_sr3_numedit_measure), while the enclosing group's character image is still three characters wide (u_sr3_edit_group prints `G=[ 12xy]`, identical to the usage-less control `H=[ 12xy]`). A declared width that disagrees with the item's own image is precisely what a REDEFINES window, a record image and a CALL boundary key on, so the divergence is latent rather than harmless. The sibling shapes are all correctly rejected -- alphanumeric (`PIC X(3)`, u_sr3_x_comp/_binary/_packed and the two ca35 goldens), alphanumeric-edited (`PIC XXBXX`, u_sr3_alnedit), boolean (routed to SR5) and national (routed to SR20) -- so the fix is one term: extend the guard from `anyAlpha` to 'not category numeric', reusing the `anyEdit` flag already computed six lines above.
