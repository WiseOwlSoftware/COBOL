# PB354 — offset-plus-width is not the rule

**Rows:** `SR-14.9.41.3-4`, `SR-14.9.41.3-6`, `SR-14.9.41.3-L2.2`, `SR-14.9.41.3-L2.3`. Three mechanisms in
start-statement-p1; one screen.

## Part 1 — nothing requires the operand to be in a record of file-name-1

`out-b1/probe/sr6-ws/prb.cob` — `RECORD KEY IS IX-KEY` / `05 IX-KEY PIC X(6)` in the FD, and in WORKING-STORAGE
`01 WS-OUTSIDE. 05 WS-PART PIC X(4). 05 WS-FILLER PIC X(20).`, then `START IXF KEY IS = WS-PART END-START`.
**Compiles clean** and binds `keyIndex = -1`, i.e. the compiler treats an unrelated 01 as if it were a record of
the file.

> §14.9.41.3 SR6 b) 1.: [the operand's] leftmost character position within a record of the file corresponds to
> the leftmost character position of a prime or alternate record key that is associated with file-name-1

`RecordLayout.KeyIndexByPosition` tests `OffsetOf(operand) == OffsetOf(pk) && operand.ImageWidth <=
pk.ImageWidth`, and `OffsetOf` walks to **the operand's own topmost parent** — so offset 0 in ANY 01 collides
with offset 0 in the record. The consequence is not confined to a missing syntax check: `KeyedIoEmitter.EmitStart`
then passes `OperandText.AsString` of the WORKING-STORAGE item as the comparand, where §14.9.41.4 GR17 a)
specifies *The specified key is set up by moving the relevant parts of the record area into a temporary data
area* (`--check 14.9.41.4` → **OK**) — the emit half is **PB355**.

## Part 2 — SR4's OCCURS ban is a side effect, under a message that is false

`out-b1/probe/sr4-occ/prb.cob` — `05 IX-KEY. 10 IX-ELEM PIC X(3) OCCURS 2 TIMES.` with
`START IXF KEY IS = IX-ELEM (1) END-START`.

> §14.9.41.3 SR4: Data-name-1 or record-key-name-1 shall not be subject to any OCCURS clauses.

`--check 14.9.41.3` → **OK**. The probe IS rejected — but only because `OffsetOf` bails to null for an item under
OCCURS (`if (p.Occurs is not null) return null;`), which collapses into the SR6 message *`<name>` neither names a
record key nor begins at the leftmost character position of one with a length not greater than that key* — **a
sentence that is FALSE of `IX-ELEM(1)`**, which does begin at IX-KEY's leftmost position and is shorter than it.
The right rejection reason exists and is never named.

## Part 3 — the relative arm has no OCCURS check at all, and its upstream guard is missing too

`out-b1/probe/sr4-occ/prb.cob` also carries `SELECT RLF ... ORGANIZATION IS RELATIVE ... RELATIVE KEY IS WS-RK`
with `01 WS-RKT. 05 WS-RK PIC 9(4) OCCURS 3 TIMES.` and `START RLF KEY IS = WS-RK (2) END-START`. Neither the
START nor the file control entry is reported. `BindStart`'s relative arm tests only
`ReferenceEquals(operand.Item, file.RelativeKeyItem)`, which is TRUE for a subscripted reference to the SAME
`DataItem`, and never consults the operand's OCCURS ancestry — the indexed arm gets that incidentally from
`RecordLayout.OffsetOf`, which the relative arm does not call.

**And the upstream rule that would have made the shape unreachable is the one member of its set that is
missing.** `KeyedValidateFile` implements §12.4.5.13.3 SR2 (unsigned integer without P, COBOLNET0863) and SR3
(not defined within a record of the file), but **not SR1** — *Data-name-1 shall not be subject to any OCCURS
clauses* (`--check 12.4.5.13.3` → **OK**). A two-of-three rule set, the shape where the missing member is easiest
to miss because the others look thorough, and the two gaps cover for each other.

## Part 4 — SR6 b) 2.'s class/category/usage identity is omitted by an explicit design note

`out-b1/probe/l22-run/prb.cob` — FD record `01 IX-REC. 05 IX-KEY PIC X(6). 05 IX-DATA PIC X(10).` with
`RECORD KEY IS IX-KEY`, plus a sibling record `01 IX-REC3. 05 IX-NUM PIC 9(4) COMP-3. 05 IX-NTAIL PIC X(13).`;
write keys `1234AA` and `9999ZZ`, reopen INPUT, `MOVE 1234 TO IX-NUM`, `START IXF KEY IS = IX-NUM`, then
READ NEXT. **Compiles with no diagnostic** and runs, printing `L22-OK ST=00` then `L22-GOT=1234AA`.

> §14.9.41.3 SR6 b) 2.: It has the same class, category, and usage as that record key.

`--check 14.9.41.3` → **OK**. IX-NUM is class numeric, category numeric, usage packed-decimal; IX-KEY is class
alphanumeric, category alphanumeric, usage display. The statement must be REJECTED at bind time.

`KeyIndexByPosition`'s own doc comment records the omission as intentional — *(SR6b.2's same-class/category/usage
check is a pre-existing looseness kept as-is; the width-<= rule is SR6b.3.)* — a documented looseness never
re-derived against the rule. **Two consequences.** (1) `EmitStart` passes `OperandText.AsString(...)` of the
packed item, i.e. a decimal TEXT RENDERING, and `IndexedConnector` compares it against the stored key characters;
the probe agrees only because `1234` happens to render as the key's first four characters, and a COMP or COMP-3
operand whose rendered text differs from the stored bytes (a signed value, a scaled value, a binary usage)
compares the wrong thing and reports success. (2) SR6 b) 3.'s length test is then applied across incommensurable
bases — `ImageWidth` is 4 for this `PIC 9(4) COMP-3` item while its packed storage is 3 bytes — so **the
surviving half of the rule is unsound exactly where the missing half would have bitten.** The two L-rows have to
be fixed together.

## The fix shape

Give `KeyIndexByPosition` the file's record ROOTS (it already has the `FileModel`) and require the operand's 01
root to be among `file.Records`; give SR4 its OWN named check, applied on BOTH arms of `BindStart` through a
shared *operand subject to OCCURS* predicate, ahead of the position walk, so the two rejection reasons stop
sharing one message; add SR6 b) 2.'s identity test; and add the missing §12.4.5.13.3 SR1 check in
`KeyedValidateFile`. Part 4's emit consequence lands with **PB355**.

**Code sites:** `RecordLayout.cs#KeyIndexByPosition`, `#OffsetOf` · `KeyedIoBinder.cs#BindStart` (both arms),
`#KeyedValidateFile` · `KeyedIoEmitter.cs#EmitStart`.

## Landed — 2026-09-05

**The screen was one method answering two rules; it is now two methods, one rule each.**

- **Part 1 — "within a record of the file".** `RecordLayout` no longer measures an operand inside whatever 01
  happens to be its own root. `InRecordOfFile` requires the operand's 01 root to be among `file.Records`, and
  both key lookups go through it, so a WORKING-STORAGE 01 at offset 0 no longer collides with offset 0 in the
  record. Negative: `conformance:negative/pb354-start-operand-outside-record`.
- **The split itself.** `KeyIndexOfKeyItem` answers "this IS a record key of the file" — by reference identity,
  or by §12.4.5.12.4 GR4's *identical* byte positions in another record description entry of the same file
  (hence equal widths: GR4 promotes the key's whole span, never a prefix). `GenericKeyIndex` answers
  §14.9.41.3 SR6 b) alone. `BindStart` asks a) then b); `BindRead` asks only the first, because §14.9.30.3 SR11
  — *"Data-name-1 or record-key-name-1 shall be specified in the RECORD KEY clause or an ALTERNATE RECORD KEY
  clause associated with file-name-1"* — has no generic arm at all. That is a TIGHTENING of READ the conflation
  had hidden: the shared lookup admitted an operand shorter than the key at the same offset.
- **Part 2 — SR4 has its own name.** `RecordLayout.IsSubjectToOccurs` is the ONE predicate for the phrase
  "subject to an OCCURS clause", and `BindStart` calls it before either organization arm, so an OCCURS operand
  is rejected under SR4's own sentence instead of under SR6's, which was FALSE of the operand it was reporting.
- **Part 3 — the relative arm, and the missing member of the rule set.** The relative arm now runs the same SR4
  check (it never called `OffsetOf`, so it had no check at all), and `KeyedValidateFile` implements
  §12.4.5.13.3 SR1. **The sweep found the other two members of that set unimplemented as well** — §12.4.5.12.3
  SR1 (RECORD KEY) and §12.4.5.6.3 SR1 (ALTERNATE RECORD KEY) state the identical ban, and both are now checked
  through the same predicate. Their `data-name-2` is the SOURCE phrase's operand, which the grammar does not
  admit (`recordKeyClause : RECORD KEY? IS? dataReference`) and `docs/CONFORMANCE.md` §2 row 40 declines, so
  data-name-1 is the whole of what the rule can require here.
- **Part 4 — SR6 b) 2. is implemented and the doc comment recording its omission is gone.**
  `SameClassCategoryUsage` compares the CLASS through the one §8.5.2.1 Table-2 classifier
  (`IntrinsicArgumentRules.ClassOfItem` — never a second copy of that table), the CATEGORY from the operand's
  PICTURE or, for an ordinary group, category alphanumeric (§13.18.29.4 GR3), and the USAGE from the resolved
  PICTURE, else the entry's own clause, else DISPLAY. b) 3. is then applied on a commensurable basis by
  construction, which is what the note required of the two L-rows.

**The complement is measured, not assumed** (`feedback_measure_the_selectors_complement`):
`conformance:2002/pb354_start_generic_key_ok` walks all FIVE accepting shapes — the declared prime key, a GR4
implicit key in a second record description, a 3-character generic prime key, the declared alternate, and a
2-character generic alternate — with keys chosen so each answer is unreachable by accident.

**Rows.** `SR-14.9.41.3-4`, `-6`, `-L2.2`, `-L2.3` all CONFORMS, plus the three swept key-clause rows
`SR-12.4.5.12.3-1`, `SR-12.4.5.6.3-1`, `SR-12.4.5.13.3-1`. `SR-14.9.30.3-11` and `GR-14.9.41.4-16` were
re-recorded for the rename with their verdicts and reasons unchanged (both are PB358's).

**What did not hold on today's tree.** Part 4's probe no longer prints `L22-OK ST=00` / `L22-GOT=1234AA`: PB355's
emit half has since moved to `OperandText.AsStorageImage`, so the packed operand's BYTES are compared against
the alphanumeric key and the START now fails with '23' instead of succeeding on a coincidence. The wrong answer
became a wrong status; the missing bind-time rejection was the same either way.
