# PB4028 — a reader sees a dead APPLY COMMIT owner's uncommitted record

**Sites:** `src/WiseOwl.Cobol.Runtime/IO/KeyedConnector.cs:1158` (`HoldingsGate`: `if (!file.Writable) break;`).

**The question for the adjudicator (not decided here).** After an APPLY COMMIT writer is killed, an `OPEN INPUT` reader reads
the dead owner's uncommitted change with status `00` until some run unit makes a writable entry (which performs the
rollback). The reader used neither IGNORING LOCK nor a sharing phrase. Is that (a) the documented determination of
DESIGN-runtime-library.md 2.2.1.10 "As built" (2) and the bullet before it, citing Annex D.2.5, or (b) a wrong answer
against 9.1.18.5, which rolls those changes back at abnormal termination?

**Evidence.** Probe `E:\COBOL-coord\scratch\w20261740c\probe\committer.cbl`, killed after its second COMMIT, then `reader.cbl`
printed `REL 0007 R-SEVEN`, a record written AFTER the last COMMIT. The D.2.5 sentence the design cites continues "... when
the sharing mode ... is 'with all other' or 'with read only' and the 'ignoring lock' phrase is used"; this reader used
neither. The design's own D.2.5 reading at DESIGN-runtime-library.md 1836-1837 says the read is possible "only with IGNORING
LOCK" (the reviewer ran `cite.py --check`: the sentence does continue so). Yet the PB3330 close-out bullet
(`kb/Work/PB3330.md:347`) calls the same read "the documented determination ... not a defect", while the same branch's
report and DEVLOG entry raise it as an open lead. Those two statements disagree; the verdict settles which stands, and the
close-out bullet is corrected to match it.

**Alternatives named by the report.** Answer `51` while the dead holding stands; or roll back through a short-lived writable
handle at the reader's OPEN. No other lead shares this root cause.

**Needs.** An adjudicator reading 9.1.18.5, D.2.5 and the sharing rules, with the precedence for latitude (ISO, then
GnuCOBOL, then IBM/Micro Focus); on a wrong-answer verdict, an implementer note for the fix at the site above.
