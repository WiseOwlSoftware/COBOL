# PB3759 — two goldens cite a clause that answers a different question

**Sites:** `conformance-suite/cases/14.8.2-Formal-parameters-and-arguments/pb3686_returning_external_prototype_pointer.cob` (header line 3; on branch PR #584 until it lands), `conformance-suite/wiseowl/cases/14.2-Procedure-division-structure/pb3678_numeric_constant_by_content_moved_formal.cob` (header line 10; on branch PR #587 until it lands), `kb/Work/PB3686.md`.

Filed 2026-10-25 by the enqueue clerk. Both files exist only on the PR branches until those land; verify the paths after the landing. One mechanism: a golden's rule tags or header derivation names a clause that is real
(the quoted text is in the standard) but does not govern what the golden executes (CLAUDE.md rule 1: a real clause can answer a different question).

## 1. PB3686's golden (R1-1, low)
Line 3 tags `[SR-14.9.39.3-22, GR-14.8.2.3.2-4]`, a SET rule and a BY REFERENCE rule the case never executes, and omits `GR-14.8.3.3-2`, the catalogued rule
whose text ends with exactly the elementary "same ALIGN … USAGE clauses" paragraph the fix implements (`docs/rearchitecture/spec-rule-catalog.json` carries the id). The PB3686 report,
the note's `closes_rows_reason` and DEVLOG 2552 all say that paragraph "has no catalogued rule id", which is false. Fix: retag the golden (`GR-14.8.3.3-2`, drop the two unexecuted tags), correct the
`closes_rows_reason` in `kb/Work/PB3686.md`, and let the registrar decide whether the row `GR-14.8.3.3-2` is now witnessed (a verdict is an adjudicator's, not the clerk's). The DEVLOG entry is history and stays as stamped; the corrected statement lives in the note.

## 2. PB3678's golden (R2-1, low)
Line 10 derives the BY CONTENT conformance of its elementary `PIC X(4)` formal from §14.8.2.2 rule 2. `cite.py --check 14.8.2.2 "alphanumeric group item"` is OK, but §14.8.2.2 opens "If either the formal
parameter or the argument is an alphanumeric group item", so it governs groups only. The rule for a non-numeric elementary formal of a NESTED call is §14.8.2.3.3 rule 2 d) ("Otherwise, the conformance rules are
the same as for a MOVE statement with the argument as the sending operand and the corresponding formal parameter as the receiving operand", checked in `specs/ISO_COBOL.md` 2026-10-25). Fix: rewrite the derivation comment.
