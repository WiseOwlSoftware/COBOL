# PB2510

Filed by the w1033 clerk from the PB1664 refuter (`E:\COBOL-coord\scratch\w1033-adj\PB1664-refute.md` section 2(a)), which struck the decision's claim that the compilers agree on PAGE for report files and says
"the report page advance is an open sibling question on the same file shape. Either decide it with this fix or file it as its own note."

**Observed (probe `PB1664-refute\rptpg`, report PAGE LIMIT 5, both hosts).**
- Pinned build `pin-97006f3`: `PH\r\nDD\r\nDD\r\nDD\fPH\r\nDD\r\n` (form feed ends the page).
- GnuCOBOL 3.2.0: `PH\nDD\nDD\nDD\nPH\nDD\n\n\n\n` (no `\f`): `libcob/reportio.c` contains no `COB_WRITE_PAGE`, and `do_page_heading` pages with `COB_WRITE_BEFORE|COB_WRITE_LINES|1` blank lines ("Skip to end of page").
- `docs/CONFORMANCE.md` DOC-A.1-159 pins the form feed: "Each line is followed by CR LF (0x0D 0x0A, on every host), except that when the next line begins a new page the line is followed by a form feed (0x0C) instead".

**Spec status (cite.py --check OK per the refuter).** `§14.9.16.4 GR6`: a failed page fit test "results in a page advance"; `§13.4.5.4 GR4`: the report writer logical record structure is implementor-defined; `§A.1 159)` (report file
record structure, required and documented). So the representation of the page advance is implementor latitude and the precedence order applies: ISO silent, GnuCOBOL represents it with blank lines. The decision's rule-1 reasoning for
`PB1664` reaches this too. Owed: an adjudication that picks blank lines or the form feed (and documents it), landed with or after `PB1664` since both rewrite DOC-A.1-159. Related: `PB1664`.

Owner 2026-10-17: addressed in the SORT and file I/O campaign (kb/Work PB3353).

## Closed (analyses sweep, 2026-10-23)

Adjudicated read-only by an Opus cobol-adjudicator on main e7cf38ce4; accepted by the Mythos session.

Closed by the sweep of 2026-10-23 with a determination: the report file keeps the form feed. §14.9.16.4 GR6 (checked) makes a failed page fit 'result in a page advance', and §13.4.5.4 GR4 (checked) leaves the report writer logical record structure to the implementor, so the bytes are latitude. Measured GnuCOBOL 3.2.0 does not supply a representation to follow: with PAGE LIMIT 5 and LAST DETAIL 4 its intermediate pages are four lines written straight into the next page heading (no blank line, no page control), and only the last page is padded with empty lines at TERMINATE, so a reader of its file cannot find the page boundaries the report's PAGE-COUNTER counted. CLAUDE.md rule 1's precedence therefore does not point at blank lines: where GnuCOBOL does represent a page advance on a print stream, it writes a form feed (WRITE ... ADVANCING PAGE on a record sequential file gives \f in both compilers), which is what DOC-A.1-159 already pins. No code change. One sentence recording this reasoning (GnuCOBOL's report paging measured, and why it is not followed) belongs in DOC-A.1-159, written in the same change that fixes kb/Work PB2556's status parenthetical in that row.

Evidence: Measured 2026-10-23 (probes/pb2510, PAGE LIMIT 5, HEADING 1, FIRST DETAIL 2, LAST DETAIL 4): with 4 GENERATEs GnuCOBOL 3.2.0 writes PH DD DD DD / PH DD then three empty lines; with 8 GENERATEs PH DD DD DD / PH DD DD DD / PH DD DD then two empty lines - every intermediate page is 4 lines run straight into the next PH and only the LAST page is filled to the limit at TERMINATE, so libcob writes NO representation of the intermediate page advances. Main writes a form feed at each page advance (DD\fPH), and GnuCOBOL's own representation of a page advance on a print file is the same form feed (probes/pb2509/advrs: WRITE ... BEFORE ADVANCING PAGE gives \f in both compilers).
