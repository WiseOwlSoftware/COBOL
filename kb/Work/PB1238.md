## Measured

**file-description-entry** — The file description entry's FORMAT (1 sequential / 2 relative-or-indexed / 3 report) is never determined, so no clause-admissibility or record-admissibility check keyed on it exists: BindFileSection binds every clause against every organization. Format-1-only clauses (LINAGE, CODE-SET) pass on relative/indexed files, LINAGE and record descriptions pass on a report FD, and the LINE SEQUENTIAL ban on BLOCK CONTAINS / RECORD CONTAINS is unscreened.

- **Repro:** All compile clean and run: (1) SELECT F ASSIGN "f.txt" ORGANIZATION LINE SEQUENTIAL. + FD F BLOCK CONTAINS 2 RECORDS. (probe/fde/sr4_block) and + FD F RECORD CONTAINS 10 CHARACTERS. (sr4_record) and RECORD CONTAINS 5 TO 10 CHARACTERS (sr4_record_range); (2) ORGANIZATION RELATIVE + FD F LINAGE IS 20 LINES. (sr5_linage_rel); ORGANIZATION INDEXED + FD F CODE-SET IS AL1. (sr5_codeset_idx); (3) FD F REPORT IS RP. 01 R PIC X(10). (sr8_record); FD F LINAGE IS 20 LINES REPORT IS RP. (sr5_report_linage).
- **Expected (spec):** §13.4.5.3 SR4: with LINE SEQUENTIAL 'neither the BLOCK CONTAINS clause nor the RECORD CONTAINS clause shall be specified' (2023). §13.4.5.3 SR5/SR7 + the rendered §13.4.5.2 formats: Format 2 (relative-or-indexed) admits only EXTERNAL, GLOBAL, BLOCK CONTAINS and record-clause, so LINAGE / CODE-SET on a relative or indexed FD are syntax errors. §13.4.5.3 SR8: 'No record description entries or constant entries shall be associated with the file description entry for a report file', and Format 3 has no LINAGE clause. Each is a compile-time error at every edition where the construct exists.
- **Observed:** Grep of src/Cobol.Net.Compiler: the only LineSequential predicates are READ PREVIOUS, the emitter and the 2023 edition gate; the only IsReportFile readers are MaterializeImpliedRecord (skip synthesis), the OPEN INPUT/I-O screen and the emitter. The clause loop in BindFileSection dispatches recordClause/codeSetClause/formatClause/linageClause/reportClause/fileGlobalExternalClause with no organization or report test. The right shape (rule 5): derive the FD's format once from the SELECT organization + REPORT clause, and hold a per-format admissible-clause table checked in one place, with a drift test against §13.4.5.2 — that also covers the SR7 sibling row (LINAGE/CODE-SET on Format 2).
- **Code site:** src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindFileSection (clause loop) / #MaterializeImpliedRecord
- **Clause (adjudicator):** 13.4.5.3 SR4 / SR5 / SR7 / SR8; 13.4.5.2

**file-description-entry** — fileDescriptionClause (CobolData.g4) still carries the FILE CONTROL entry's organizationClause | accessModeClause | recordKeyClause | alternateKeyClause | fileStatusClause alternatives, and BindFileSection's clause loop has no arm for any of them — so these clauses written on an FD are parsed and silently DISCARDED (the file keeps its SELECT's organization), despite the PB829 comment that the §13.4.5.2 formats are closed.

- **Repro:** probe/fde/fmt_fd_org: SELECT F ASSIGN "o.txt". FD F ORGANIZATION IS RELATIVE ACCESS MODE IS RANDOM. 01 R PIC X(10). -> compiles clean, runs; .g.cs registers F as a sequential connector (CobolFile.Register("FDORG::F", "o.txt", 10, false, false, ...)). probe/fde/fmt_fd_status: FD F FILE STATUS IS FS. -> compiles clean; FS is never wired.
- **Expected (spec):** The rendered §13.4.5.2 Formats 1/2/3 admit none of ORGANIZATION, ACCESS MODE, RECORD KEY, ALTERNATE RECORD KEY or FILE STATUS (those are §12.4.5 file control entry clauses), and §13.4.5.3 SR5/SR7/SR8 bind each FD to exactly one of those formats — so each is a syntax error, refused like any other residue of a closed format (COBOLNET1970 or a named diagnostic).

This is an FMT-13.4.5.2 row defect as much as SR5's; no open kb/Work note owns it.
