# PB5915, landing 2026-11-21: before 2023 a line-framed REWRITE is the sequential size rule

**Re-probed** on the wave 20262120 group A build, `--std 85`, the ruling's `pb5915c.cob`: the 3-character REWRITE of the
5-character `ALPHA` record answered 00 and the file then held `XYZ  ` as record 1. Still a wrong answer (status, file and
control flow).

**Fix.** `SequentialConnector.RewriteRecord` dispatches once on the organization and the edition's frame:
`RewriteRecordSequential` for a record sequential file, `RewriteLine` (§2023:14.9.35.4 GR17 a)-d)) when
`LineSequentialFileRules` holds, and the new `RewriteFramedRecord` when `LineDelimiterOnlyFrames` holds: '44' with the file
and the record area unchanged unless the record has as many character positions as the whole line the READ took
(§1985:VII.4.5.4 GR10, §1985:VII.1.3.5), measured by the new `_lastLineCharacters` that `NextFrame` sets beside
`_lastLineBytes`, so a REWRITE after a truncating READ is '44' by GR10 itself, not by 2023's GR17 a) partial-record flag. A
record of the same character positions that takes another number of bytes on the UTF-8 medium cannot replace the line in
place and is '44' too. The line character set refusal keeps the WRITE's status (99 at 85, PB5882's mapping of '71').

**After:** `SHORTER 44`, `LONGER 44`, same size `00` and replaced, `REWRITE-TRUNC 44`; the file reads back ALPHA, BRAVO, the
replacement, DELTA.

**Witness:** `conformance:cases/VII.4.5@1985-REWRITE-STATEMENT/pb5915_line_delimited_rewrite_size_85`.
