# PB5915 ruling

- `OK  §1985:VII.1.3.5  (1.3.5 I-O Status)  the text is in the clause; it lies in GRL2.4d.2` — "I-O Status = 44. A boundary violation exists because: ... 2) An attempt is made to rewrite a record to a sequential file and the record is not the same size as the record being replaced."

Mechanism: `src/WiseOwl.Cobol.Runtime/IO/SequentialConnector.cs#RewriteRecord` dispatches on `_lineSequential` alone to `#RewriteLine`, which applies §2023:14.9.35.4 GR17 a)-d) at every edition: b) refuses only a LONGER record, and c) pads a SHORTER one with spaces to the replaced line's byte length and overwrites in place with '00'. It does not ask `LineSequentialFileRules` (the PB5903 property, `DialectBehavior.LineSequentialFileRules`, ChangedIn 2023, `src/WiseOwl.Cobol.Runtime/Control/DialectBehavior.cs`), which PB5903 put in front of the READ and WRITE arms only. Before 2023 the file is a sequential file whose line delimiter only frames the record (§1985:VII.2.8.4 GR1), so its REWRITE is the sequential REWRITE: equal size or 44.

Fix shape: make `RewriteRecord`'s organization dispatch ask the edition's file rules once: `LineSequentialFileRules` true keeps `RewriteLine` (GR17 a)-d)); false routes a line-framed file to the sequential size rule, i.e. 44 unless `len` equals the replaced record's length (the line's length less its delimiter, `_lastLineBytes` measured in characters of the record), and only then the in-place overwrite (`OverwriteInPlace`, whose length is then unchanged). The line-character-set refusal at REWRITE (today 99 at 85) stays an implementor-defined 9x before 2023 and should be stated in the same determination text the WRITE side uses (PB5903's VERSION_CHANGE_REFERENCE row 7.88 currently quotes the READ and WRITE edges only; it gains the REWRITE edge, rule 6). Goldens at `--std 85` beside `cases/VII.4.4@1985-READ-STATEMENT/pb5903_line_delimited_length_conflict_85` (or a `VII.4.5@1985-REWRITE` case): shorter REWRITE gives 44 and the file is unchanged; longer gives 44; equal size gives 00 and replaces; the truncated-read REWRITE gives 44. The same program at `--std 2023` (ORGANIZATION LINE SEQUENTIAL) keeps GR17 c)'s pad-and-succeed.

Reasoning: 1985 has no line sequential organization; RECORD DELIMITER IS LINE-SEQUENTIAL names a length method for a variable-length record of a sequential file (VII.2.8.4 GR1, GR3). The sequential REWRITE's size rule is GR10, with no exception for a delimiter method, and 1.3.5 d 2) names the status. The code's pad-and-succeed is a 2023 line sequential rule (GR17 c)) applied outside its edition: the user's program gets 00 where the standard requires 44, and its file is changed where the standard says "the updating operation does not take place". 2002 and 2014 were not read for this ruling (2002 frozen, 2014 waiting, per the note's Scope); the `LineSequentialFileRules` gate already spans them, so the fix reaches them by the same property and each needs its own text read before its golden.
