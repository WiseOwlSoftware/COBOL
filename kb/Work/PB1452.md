## Finding — `program-address-identifier` (rejects-legal-source; rows `SR-8.4.3.13.3-1`)

**Mechanism.** The program-address-identifier's 8.4.3.13.3 SR1 category screen tests the raw `Item.Pic?.Category` instead of the compiler's ONE category predicate `ItemCategory.IsAlphanumericOrNational`, so a group item (Pic null) reads as category '(none)' and a PIC A item reads as alphanumeric (the 8.4.3.12.3 SR1 function twin carries the same screen and is already reported by the function-address-identifier adjudication)

**Repro.** 01 PP USAGE PROGRAM-POINTER. 01 GRP. 05 G1 PIC X(3) VALUE "PAI". 05 G2 PIC X(3) VALUE "SUB". PROCEDURE DIVISION. SET PP TO ADDRESS OF PROGRAM GRP (with an outermost program PAISUB in the same file) -> error COBOLNET2157 "'GRP' is of category (none)". Same for a GROUP-USAGE NATIONAL group. Conversely 01 AB PIC A(6) VALUE "PAISUB". SET PP TO ADDRESS OF PROGRAM AB compiles and locates PAISUB.

**Expected from the spec.** 8.4.3.13.3 SR1 'Identifier-1 shall be of category alphanumeric or national.' with 8.5.2.1 'an alphanumeric group item has class and category alphanumeric' / 'a national group item has class and category national': GRP and NG are admissible and GRP's content PAISUB locates the program (GR1 a); PIC A is category alphabetic, outside SR1's list, and shall be rejected with COBOLNET2157.

**Observed / reasoning.** Pinned cobol.exe, out/probe/pai/ok1.cob, N8.cob, ae.cob: GRP and NG rejected as 'category (none)'; AB accepted and located (AB-FOUND). ItemCategory.Admits already answers all three correctly (group arm via IsAlphanumericGroup, alphabetic excluded, national group via its as-if PIC N); routing the screen through it is the fix. The edited-category acceptance that predicate keeps is kb/Work PB850's, not this finding's.

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SetBinder.cs#BindProgramAddressOperand (~line 961); sibling SetBinder.cs ~line 755 (ADDRESS OF FUNCTION, 8.4.3.12.3 SR1)

## Refuter evidence — row `FMT-8.4.3.13.2` (PARTIAL)

PARTIAL — The identifier-1 arm is narrower than the standard allows. The grammar writes it as `dataReference`, which does not admit the other identifier formats. §8.4.3.1.3 SR1 defines identifier recursively: where a format allows another identifier, that identifier 'may be any of the formats for an identifier'. So a function-identifier of category alphanumeric (§8.4.3.13.3 SR1 needs only the category) is legal as identifier-1, and the compiler rejects it with a parse error. The literal arm, the prototype arm, the optional OF, subscripted and reference-modified identifier-1, and the --std 85 gate all behave correctly.

**Code site.** src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4#programAddressIdentifier; src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4#addressIdentifier; src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4#setProgramAddressStatement
