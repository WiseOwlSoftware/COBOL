# PB1942 — LANDED (wave 1039 B, 2026-10-08)

## Landed

Every literal position of the SPECIAL-NAMES paragraph now admits a constant-name (§13.10.3 SR2, `cite.py --check
13.10.3 "Except in a compiler directive, constant-name-1 may be used anywhere"` → `OK §13.10.3 2)`), and its
literal-1 meets the rules of the literal it stands for (§13.10.4 GR1 → `OK §13.10.4 1)`).

- **Grammar** (`CobolSpecialNames.g4`): ONE rule, `specialNamesLiteral : literal | cobolWord`, for literal-5/-6
  (CLASS), literal-7/-8 (CURRENCY SIGN) and literal-9 (ORDER TABLE). The ALPHABET literal-phrase and the LOCALE
  clause already admitted a word (code-name, figurative synonym, external-locale-name-1) and keep their shape. The
  CLASS value list's later operands are steered by `classOperandAhead()` (`CobolParserCoreBase`): a word continues the
  list only when the unit DECLARES it a constant-name (read off the token stream: `{1|01} word CONSTANT`, not
  `CONSTANT RECORD`), so `CLASS C IS "A" CONSOLE IS MYCON` and a following switch entry keep their reading.
- **Binder** (`DataBinder.Switches.cs`): `SpecialNamesConstant` is the one constant reading of a word there (it binds
  the later constant entry on demand through `FindConstant`, kb/Work PB1231). Its readers: `CurrencyOperandOf` (SR18,
  SR26 hex refusal and SR19 read off the constant's specification as written, SR28's class from its category);
  `TryClauseTextLiteral` (SR10/SR11, ORDER TABLE literal-9 and LOCALE literal-4); `LiteralPhraseOperand` (ALPHABET
  and CLASS: an integer constant is an ORDINAL under SR14 b1 / SR17 b2, a string constant meets the class rule and
  SR11's zero-length half). `PhraseOperand.IsOrdinal` is now decided where the operand is decoded.
- **Determination** (docs/CONFORMANCE.md §7 items 181, 184): a word declared as a constant-name is that constant,
  never an ALPHABET code-name or a LOCALE external-locale-name of the same spelling.
- **Goldens**: `2002/pb1942_special_names_constant_literals` (CURRENCY both forms incl. a national literal-7, CLASS
  ranges and an ordinal constant, ALPHABET ALSO, ORDER TABLE); negative `pb1942-currency-numeric-constant` (a numeric
  constant as literal-7 → §12.3.7.3 SR18, COBOLNET0892). The note's own repro (`CURRENCY SIGN IS KC`, `KC` = "E")
  now reaches SR22, which refuses E as a currency symbol (a picture letter) — the right answer for that literal.
- **Sweep**: SYMBOLIC CHARACTERS was done by kb/Work PB1948. The other SPECIAL-NAMES operands are names, not
  literals. Outside the paragraph, two more environment/identification positions still take only a literal and
  are kb/Work PB780's population (reported as a lead, not fixed here): the REPOSITORY specifiers' `AS literal-1 …
  literal-5` (§12.3.8.2; `externalizedNamePhrase`, read by `DataBinder.Switches.cs#BindSpecifierExternalizedName`
  through `ExternalizedName.Screen`) and the identification paragraphs' AS phrases, which bind before any constant
  is declared (`LiteralEnvironment.Unscoped`).

**For the next implementer.**
- `src/Cobol.Net.Frontend/Grammar/Core/CobolSpecialNames.g4#specialNamesLiteral` — the rule a new SPECIAL-NAMES literal
  position names; a LIST of such operands needs a left-edge predicate like `classValueSet`'s, because the paragraph's
  last alternative (`unrecognizedClause`, `IDENTIFIER (IDENTIFIER | literal)*`) and the IS-less switch entry both begin
  with words, so neither a greedy nor a non-greedy loop is right.
- `src/Cobol.Net.Frontend/Parsing/CobolParserCoreBase.cs#classOperandAhead` / `ConstantEntryNames` — the token-stream
  read of the unit's constant-names; reuse it for the next list.
- `src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs#SpecialNamesConstant` (and `NamesConstant` for a word that has
  a meaning of its own) — the one reading; `CurrencyOperandOf`, `TryClauseTextLiteral` and `LiteralPhraseOperand` hold
  the constant's literal-1 to the clause's rules. Trap: a raw `"COBOLNET08xx"` string adds a semgrep finding — report
  through the clause's one local `Report`.

# PB1942 — as filed

Filed by the train-1007 lander from wave 1007 group C's report (`w1007c-PB1231-report.md`, "New defects" item 2).
Same root as [[PB780]] (SR-13.10.3-2 is a whole-language admission; each violating literal position is its own
defect, as [[PB778]] is for EDITING).

## Defect

```
       SPECIAL-NAMES.
           CURRENCY SIGN IS KC.
       ...
       01 KC CONSTANT AS "E".
```

draws COBOL0305 (parse error) at `KC`. §13.10.3 SR2: "Except in a compiler directive, constant-name-1 may be used
anywhere that a format specifies a literal of the class and category of constant-name-1" (`cite.py --check 13.10.3`
→ `OK §13.10.3 2)`), and the CURRENCY SIGN clause of the SPECIAL-NAMES paragraph (§12.3.7) writes its operand as a
literal. The fixer confirms the literal's class and category in the rendered §12.3.7 general format. Note the ordering question too: SPECIAL-NAMES precedes the DATA DIVISION, so the constant is declared
after its use — [[PB1231]]'s declare-before-bind walk covers data-division readers, not the environment division.

[[PB1231]]'s note (sweep item 5) routed these SPECIAL-NAMES positions here rather than to its ordering fix; the
same probe applies to `SYMBOLIC CHARACTERS` and `CLASS … IS` with a constant operand, which the fixer sweeps with it.

## Repro

A program with `CURRENCY SIGN IS KC.` in SPECIAL-NAMES and `01 KC CONSTANT AS "E".` in WORKING-STORAGE.

## Code site

The SPECIAL-NAMES currency clause in `src/Cobol.Net.Frontend/Grammar/Core/` (the CURRENCY SIGN rule accepts a
literal only) and its binder in the SPECIAL-NAMES binding (DataBinder.Switches.cs / the currency-sign reader).
