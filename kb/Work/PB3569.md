# PB3569 — COBOL0864's wording on a READ with KEY

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/KeyedIoBinder.cs:103` (`KeyedIoBinder.BindRead`), `src/WiseOwl.Cobol.Compiler/Binding/Validation/StatementValidation.cs` (`StatementValidation.CheckReadKeyFormat`, `StatementValidation.CheckReadRandomAccessPhrases`, `StatementValidation.WrittenSequentialReadPhrases`), `tests/WiseOwl.Cobol.Tests.Conformance/GeneralFormatViolationTests.cs` (`GeneralFormatViolationTests.AStatementOutsideItsGeneralFormat_IsRefused`, `GeneralFormatViolationTests.TheLegalSpellingAMisnamedClaimDescribed_IsAccepted`), `tests/WiseOwl.Cobol.Tests.Conformance/ReadKeyFormatTests.cs` (`ReadKeyFormatTests`)

## Scenario

fz00018 line 58: `READ FS-RND KEY IS WS-KEY-DATA INVALID KEY ... END-READ` on an indexed file with no ACCESS MODE clause. Access is
therefore sequential (§12.4.5.5.3 1) (OK): "If the ACCESS MODE clause is not specified, sequential access is assumed."). WiseOwl
treats the statement as a sequential read and reports that the KEY phrase "cannot combine with NEXT/PREVIOUS/AT END", although
none of those phrases is in the statement. The C1 verdict on the program stands: the statement is illegal anyway because
`WS-KEY-DATA` is not a record key (§14.9.30.3 11) (OK): "Data-name-1 or record-key-name-1 shall be specified in the RECORD KEY
clause or an ALTERNATE RECORD KEY clause associated with file-name-1.").

## Code site

`src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/KeyedIoBinder.cs:104`: when `kind != ReadKind.Random` the binder emits
COBOL0864 "READ … KEY on '<file>' is a Format-2 phrase and cannot combine with NEXT/PREVIOUS/AT END (ISO §14.9.30 general
formats)". For a READ whose only offence is the access mode, the message names phrases the statement does not contain.

## Two questions for the implementer

1. The wording: the message must name what the statement actually does wrong (a KEY phrase on a file read under sequential
   access), in either answer to question 2.
2. An analysis item, not decided here: does ISO bar a Format 2 READ with KEY on a file in sequential access mode? The C1
   adjudicator left it open: §14.9.30.3 SR8 and §14.9.30.4 GR19 sit under the Format 1 heading, and §12.4.5.5.3 GR2 (OK on its
   item 2) c): "For indexed files this sequence is ascending within a given key of reference …") says only that sequential access
   reads in key order. The clerk did not re-run the SR8 and GR19 numbers (no text was quoted for them). If the Format 2 rule allows
   the statement, the refusal is also a refusal of legal source, severity and flags change, and this note is edited in place.

## Golden to require

A conformance case for the corrected message on a READ ... KEY in sequential access with a valid record key (whatever question 2
decides: accepted and run, or refused with the corrected wording).

## Landed (wave 20261715 group B)

**Re-probe on a fresh build (main 270912d24 plus the PB906 branch).** The note reproduced exactly: `READ FS KEY IS FK
INVALID KEY ...` on an indexed file with no ACCESS MODE clause drew COBOL0864 "is a Format-2 phrase and cannot combine
with NEXT/PREVIOUS/AT END" for a statement that wrote none of them. The same text also covered an explicit ACCESS MODE
IS SEQUENTIAL, and it was right for the statements that did write a sequential-read phrase (`READ f NEXT KEY IS k`), so
the diagnostic was exact on one arm of `kind != ReadKind.Random` and wrong on the other. GnuCOBOL 3.2.0 (`cobc
-fsyntax-only`) accepts all of these shapes with the warning "KEY ignored with sequential READ".

**Question 2 (analysis), answered.** No syntax rule bars a Format 2 READ under sequential access: SR6 and SR8 sit under
Format 1 and nothing is printed for the reverse. The standard nevertheless gives the statement no meaning: GR19
(`cite.py --check 14.9.30.4`: "An implicit or explicit NEXT phrase or a PREVIOUS phrase results in a sequential read:
otherwise, the read is a random read and the rules for format 2 apply") makes it a random read; §14.9.30.1 (a READ under
sequential access "makes available the next logical record") and §12.4.5.5.3 GR2 (a sequential-mode file's records are
"accessed in the sequence dictated by the file organization", GR1 assuming sequential when the clause is absent) say
what a sequential-mode file's READ does; GR3 and GR4 are what admit random access. The refusal stays, as a documented
determination (docs/CONFORMANCE.md D-READ-KEY-ACCESS), not as a legal-source refusal: the alternative, GnuCOBOL's, reads
a different record than the KEY phrase asked for. So `rejects_legal_source` stays false, as filed.

**The fix.** `StatementValidation.CheckReadKeyFormat` is the one check (called from `KeyedIoBinder.BindRead` after SR10's
`CheckReadKeyOrganization`) and it has two messages: a sequential-read phrase written beside KEY (names exactly the
phrases the statement wrote, from the same list `CheckReadRandomAccessPhrases` names for SR6, now one private helper,
`WrittenSequentialReadPhrases`), or a SEQUENTIAL file with none written (names the access mode, says when it is assumed
because the clause is absent, and names no phrase). An ACCESS MODE RANDOM file is not asked: SR6 has already named the
words. No new diagnostic code (COBOL5233-COBOL5235 returned): it is the same READ-KEY refusal family, COBOL0864, and the
raw literal moved from the binder to its SR10 sibling in `StatementValidation` (one literal in, one out).

**Goldens.** `conformance-suite/cases/14.9.30-READ/pb3569-read-key-sequential-access-default`, `...-written` and
`pb3569-read-next-key` (refused at 85, 2002, 2014 and 2023, `expect` the wording), and `ReadKeyFormatTests` (the messages
at every edition, the RANDOM and DYNAMIC acceptance, the single SR6 report on `RANDOM ... NEXT KEY`).

**Sibling sweep.** The other arm of the READ binders is the sequential-organization one: `SequentialIoBinder` refuses
any KEY phrase through `CheckReadKeyOrganization` (SR10), whose message is already exact. No other diagnostic lists a
fixed set of READ phrases (`grep "NEXT/PREVIOUS"` over `src`). `READ f INVALID KEY` with no KEY phrase on a
sequential-access file is accepted today (the emitter binds the phrase dead, the CCVS leniency); it selects no record,
so it is not this defect and stays.
