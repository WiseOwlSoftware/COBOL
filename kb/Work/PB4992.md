# PB4992 - lineage slice 1: the inventory as a view

DESIGN-spec-conformance-review.md section 4 (owner 2026-11-08: "We must eliminate redundant code and data. The new
implementation should be as if we originally architected it. No minimal hacks."), the first slice of its section 10.2.

**Today.** Each 2023 store file copies the catalog's `section`, `kind`, `ordinal` and `subject`, and stores `state`, a
value `Schema.state_for` derives; `build_inventory.py` regenerates the copies and the state on every rebuild, and about
24 readers read them from the files. A first cut of this slice (branch `lineage-slices`, its WIP commit) seeded 2,253
empty 1985 files that copy nine catalog fields each: that is the redundancy this slice removes, not a pattern to extend.
Its `lineage.py` (Edition, next_errors, state_of, the audit, kept-batch) and the store's per-edition directories and
year-led ids are kept and built on.

**The slice.**
- `inventory_store.py` is the store's files only: one directory per edition (`INVENTORY_DIRS_REL`, `inventory_dir`; a
  1985 id begins with its year, so `row_name` accepts a leading digit), reading and writing adjudications, and a
  commit's files. A new module, `inventory_view.py`, is the ONE view per edition, `inventory(edition)`: the edition's
  catalog joined with its store, each rule's state computed (the newest edition by `Schema.state_for`, an older one
  through `lineage.state_of`), in spec order (a Roman section by its value); `inventory_at(rev, edition)` is the same
  view at a commit, joining that commit's catalog (history before this slice stored the copies; the view reads
  either). The store and the view are two modules because they are two jobs (owner 2026-11-08: no god scripts).
- A store file holds `rule-id`, `rule-digest` and the adjudicated fields only; a rule with no adjudication has no file.
  The 2023 files lose `section`, `kind`, `ordinal`, `subject` and `state` (a one-time migration through the store's
  writer); the 1985 store starts empty (the WIP seed is deleted).
- Every reader below reads the view and nothing else: none opens a store file or rebuilds a row from the catalog.
  `tests/_shared/TraceabilityInventory.cs` is the C# view (the catalog join; the state by the C# twin of the state
  rule), and a drift test that compared a stored state or a stored copy with the catalog tests the view's checks.
- `build_inventory.py`'s seeding has no job left: its carry across a rebuild and its digest drift check become the
  view's refusals (a store file of a rule the catalog dropped; a digest that is not the catalog's text). It is deleted
  and every caller moved, the gate's and the docs' included.
- `record_verdicts.py` writes through the store and validates with the edition's field set (`lineage.Edition`), with no
  edition branch the edition's data can carry.
