# PB3040 — a finished dispatch keeps partitioning the tree

**Found 2026-10-11 13:28 PDT (Mythos session):** `plan_wave.py --cluster PB3015 --dry-run` planned ONE group of the
campaign (PB3029) and deferred PB3022, PB3024, PB3025, PB3026, PB2987 and PB3028 with
`file-set collision with dispatched whand (PB175, PB1671, PB1688) (scripts/gate_slot.py); dispatched whand (PB175,
PB1698, PB1699) (scripts/run_gate_legs.py); … the partition defers the wave, never the train`. The holders were the
dispatch-ledger entries of the landers of trains 1045 (2026-10-08 18:09) through 1060 (2026-10-11 12:43), four review
shards, the Workflow launches of 2026-10-08 and 2026-10-10 and the w1051v/w/y/z and w1053p hand implementers — 30
`wave: hand` entries of 100–635 files each, every one of whose agents had returned and whose trains had landed. A 31st
was the Mythos session's own 12:27 skills-agent dispatch, released by hand (`plan_wave.py --release PB3022`).

## Mechanism (`scripts/orchestrator/plan_wave.py`)

1. `record_hand_dispatch` (line ~377) is called by `scripts/hooks/dispatch_guard.py --record-dispatch` for EVERY
   write-capable Agent or Workflow call it admits — landers, review shards and locators included — and records the
   agent's prompt-named notes and a file set (the lander's: every file its clusters touch, 300–600).
2. It retires an entry only when `all(terminal(i) for i in notes)`. Every lander's note list contains **PB175** (the
   standing process note, `status: open` by design), so no lander entry ever meets that rule; nothing else retires an
   entry when its agent returns (the Workflow completion, the SubagentHandback, the train's `push-main.sh` exit 0).
3. The only other exit is `HAND_TTL_SECONDS = 24 * 3600` (line 206): a finished lander holds its 300–600 files for a
   day. Under the fix lane this rarely bit (its groups' files are source files landers also hold, but the fix lane plans
   from clusters whose files the same landers already carried); under the campaign lane (`--cluster`, process notes
   whose sites ARE the orchestrator's and gate's scripts) every note collides with every lander of the last 24 h.

## Fix (root cause; one mechanism per job)

1. **A dispatch records a file set only when its role edits source**: `dispatch_guard.py` passes the role
   (`agentType`); `record_hand_dispatch` records `files` for `cobol-implementer`/finisher roles and the Workflow's
   implementer groups, and an EMPTY set (notes only, so the "same work twice" check still sees them) for `cobol-lander`,
   `cobol-reviewer`, `general-purpose` review shards, `cobol-locator`, `cobol-clerk`, `cobol-adjudicator`,
   `cobol-refuter`. A lander's clusters' files are already held by their implementers' entries (source 1 and 2 of
   `inflight_file_sets`); recording them again partitions nothing and blocks everything.
2. **An entry retires when its agent returns**: the dispatch guard (or the Agent/Workflow completion path it mediates)
   releases the entry by its label; failing that, the planner retires an entry whose label names a train that
   `train-measurements.jsonl` recorded as `pushed`, or whose label's report (`<coord>/scratch/reports/…`) exists with a
   terminal status. The terminal-notes rule drops PB175 and the other standing notes (`process_only` notes with no
   `sites`) from its test, so it can fire.
3. `HAND_TTL_SECONDS` stays as the backstop and shrinks to 6 h.
4. A self-test for each arm (a lander entry with PB175 retires on its train's pushed record; a reviewer entry records no
   files; an implementer entry keeps its files) and the one measurement: the number of hand entries and the files they
   hold, printed by `plan_wave.py --dry-run` so the next accumulation is visible.

**Code sites:** `scripts/orchestrator/plan_wave.py` (`record_hand_dispatch`, `inflight_file_sets`, `HAND_TTL_SECONDS`),
`scripts/hooks/dispatch_guard.py` (`--record-dispatch`), `scripts/orchestrator/train_measure.py` (the pushed record).
**Interim (2026-10-11):** the operator releases the 30 dead entries by hand (`plan_wave.py --release <note id>`) so the
PB3015 campaign can plan; this note is in that campaign's cluster and lands with it.
