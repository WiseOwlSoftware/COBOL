## Finding — compile-time-boolean-expressions (rejects-legal-source)

compileTimeOperand enters booleanExpression only when boolExprAhead() sees a B-operator token, so a parenthesized boolean literal with no operator — a legal §8.8.2 boolean expression — falls to the arithmetic/non-numeric alternatives and is rejected as a malformed directive expression

**Rows:** SR-7.3.7.2-1

**Repro:**

```
>>DEFINE X AS (B"101")   |   >>IF (B"1") = B"1"   |   >>EVALUATE (B"1") / >>WHEN B"1" — each at --std 2023 (probe files n1.cob, q2.cob under out/probe/ctbool)
```

**Expected from the spec:** Accepted: §8.8.2 lists 'a boolean expression enclosed in parentheses' as a boolean expression and Table 4 (§8.8.2 rule 6) permits '(' followed by a literal and a literal followed by ')'; §7.3.7.2 SR1 requires only that the operand be a boolean literal, which it is. X is defined as B"101"; the >>IF is true; the >>EVALUATE selects the WHEN B"1" branch.

**Observed:** error COBOLNET1619: >>DEFINE X: malformed compile-time expression '(B"101")' (and the same for the >>IF and >>EVALUATE forms). With a B-operator present — (B"1100") B-OR B"0001" — it evaluates correctly, which isolates the operator-lookahead discriminator as the cause.

**Code site:** src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4#compileTimeOperand (the {boolExprAhead()}? gate); src/Cobol.Net.Frontend/Parsing/CobolParserCoreBase.cs#boolExprAhead

## Finding — compile-time-boolean-expressions (under-rejects)

the boolean shift's second operand is parsed as a full arithmeticExpression (the grammar's 'permissive-superset' booleanShiftSuffix) and the compile-time evaluator never screens it back down to an integer operand, so an arithmetic expression or a parenthesized count after B-SHIFT-* is accepted

**Rows:** SR-7.3.7.2-1

**Repro:**

```
>>DEFINE X AS B"1100" B-SHIFT-L 1 + 1   |   >>DEFINE X AS B"1100" B-SHIFT-L 2 * 1   |   >>DEFINE X AS B"1100" B-SHIFT-L (1) — each at --std 2023 compiles clean (probe n5/n20/n6)
```

**Expected from the spec:** Each rejected: §8.8.2 rule 5 'The second operand shall be an integer operand', which by §5.5 2)a) is an integer literal (or a data-name/identifier — here a numeric compilation variable via §7.3.11.4 GR1), never an arithmetic expression; and Table 4 (§8.8.2 rule 6) permits only 'Identifier or literal' after B-SHIFT-L/R/LC/RC, so '(' after a shift operator is an invalid pair.

**Observed:** No diagnostic; the count is evaluated through EvaluateDirectiveArithmetic. Sweep sibling: the runtime binder ConditionBinder.BindBoolShiftSuffix binds suf.arithmeticExpression() the same way — 'COMPUTE B1 = B1 B-SHIFT-L 1 + 1' at 2023 also parses and binds without a diagnostic (probe r2.cob line 8) — so the screen belongs once, on the shared booleanShiftSuffix, not per consumer.

**Code site:** src/Cobol.Net.Frontend/Expressions/CompileTimeExpressionEvaluator.cs#BooleanShift; src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4#booleanShiftSuffix; sibling src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#BindBoolShiftSuffix

## Finding — compile-time-boolean-expressions (under-rejects)

the 2023 boolean-shift introduction gate lives only in the VersionConformancePass compilation-unit walk; the directive re-parse sites (compileTimeOperand, cceRelationOrBoolean) are exempted from it in BooleanExpressionGateSiteDriftTests on a reachability reason and the frontend directive path carries no substitute gate, so B-SHIFT-* inside a compile-time boolean expression is accepted at 2002 and 2014

**Rows:** SR-7.3.7.2-1

**Repro:**

```
>>DEFINE G AS B"1100" B-SHIFT-L 1   (probe q3.cob, --std 2002 and --std 2014)   |   >>IF B"1100" B-SHIFT-L 1 = B"1000"   (probe r3.cob, --std 2014 — prints I-OK)
```

**Expected from the spec:** Rejected below 2023 with the same edition diagnostic the runtime form gets (COBOLNET0900): the B-SHIFT-L/R/LC/RC operators were added in 2023 (§E.2 item 3), so a 2002/2014 compile-time boolean expression 'formed in accordance with 8.8.2' of that edition contains no shift operator.

**Observed:** Both compile and run clean at 2002/2014. The runtime twin 'COMPUTE B1 = B1 B-SHIFT-L 1' at --std 2014 is COBOLNET0900 'boolean shift operators ... requires COBOL-2023' (probe r1.cob). The drift test's Exempt entries for compileTimeOperand and cceRelationOrBoolean say the walk 'never reaches it' — true, but that is why a gate is MISSING there, not a spec reason for none (the edition_gate_sweep shape).

**Code site:** tests/Cobol.Net.Tests.Unit/BooleanExpressionGateSiteDriftTests.cs#Exempt; src/Cobol.Net.Frontend/Expressions/CompileTimeExpressionEvaluator.cs#BooleanShift (no edition check); src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs (gate not reachable from the directive re-parse)

## Row GR-7.3.7.3-1 — PARTIAL (adjudicator + refuter record)

Rule (cite.py --check 7.3.7.3 OK, GR1): 'The order of precedence and the rules for evaluation of compile-time boolean expressions are shown in 8.8.2, Boolean expressions.' EvaluateBoolean folds through the ONE shared BooleanExpressionResolver (same grouping the runtime binder uses, incl. §8.8.2 rule 7b context-inherited shift precedence) over BitString, whose Combine right-zero-extends the shorter operand to the larger length (rules 9/10, --check 8.8.2 'the shorter operand were extended on the right by a sufficient number of boolean zeros' OK), Not preserves length, Shift preserves the first operand's length with zero-fill/rotate (rule 8). Verified by compile-and-run probes with spec-derived expectations (E:\Temp\claude\E--CobolSharp\a700c052-f9e4-4942-84ff-a13c7505d6ec\scratchpad\adj-d2\out\probe\ctbool\p1.cob, q1.cob — all OK): B-NOT B"1100"=0011; (1100 B-AND 0101)=0100; 1100 B-OR 0101 B-AND 0011 = 1101 (B-AND before B-OR, rule 7b); 1100 B-XOR 0110 B-OR 0001 = 1011 (B-XOR before B-OR); 1100 B-SHIFT-R 1 B-OR 0001 = 0111 (unpreceded shift has B-AND precedence, --check 8.8.2 7)b) OK); B"10" B-OR B"0001"=1001 (right extension); 1100 B-SHIFT-L 1 B-SHIFT-R 2 = 0010 (left-to-right, rule 7c); a substituted boolean variable B-AND B-NOT literal; boolean relation and simple boolean condition in >>IF, and a boolean >>EVALUATE subject. Shift count ≥ length / circular periodicity / zero-length handled (unit tests Boolean_Shift, Boolean_HugeShiftCount_NoCrash). No existing test covers the full rule-7b precedence ladder (B-NOT > B-AND > B-XOR > B-OR) for compile-time expressions: CompileTimeBooleanCceTests.Boolean_BinaryAndUnary/Boolean_Shift (Annex A Table A.2 values) and Boolean_ContextInheritedShiftPrecedence cover single operations and the shift-precedence case only, and conformance:2002/directive_expressions exercises one B-OR — so test-ref is left empty (test-needed). Formation defects (parenthesized sole literal, shift-count form, edition gate) are the SR-7.3.7.2-1 row's, not evaluation. || REFUTED: PARTIAL — §8.8.2 rule 7b gives a boolean shift the precedence of the PRECEDING OPERATION, and B-NOT is an operation in that ladder (1st, negation). The shared BooleanExpressionResolver tracks prevPrec only from BINARY operators: a B-NOT is folded inside the factor and never updates prevPrec. So in `A B-AND B-NOT B B-SHIFT-R 1` the shift wrongly takes B-AND precedence and its operand becomes (A B-AND B-NOT B). The spec requires A B-AND ((B-NOT B) B-SHIFT-R 1). Probes confirm the wrong value. The precedence ladder, the right-extension, Not, Combine and Shift semantics otherwise hold (adjudicator's probes plus re-reading BitString). The defect sits in the ONE shared resolver, so the runtime COMPUTE format-2 boolean binder almost certainly carries the same bug (a sibling).

**Code location:** src/Cobol.Net.Frontend/Expressions/CompileTimeExpressionEvaluator.cs#EvaluateBoolean; src/Cobol.Net.Frontend/Expressions/BooleanExpressionResolver.cs#Resolve; src/Cobol.Net.Frontend/Expressions/BitString.cs#Combine; src/Cobol.Net.Frontend/Expressions/BitString.cs#Not; src/Cobol.Net.Frontend/Expressions/BitString.cs#Shift
