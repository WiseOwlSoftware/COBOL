# PB2556

Filed by the train 1037b lander from the wave-1037 group C report (lead 2, an UNPROBED suspicion of the PB1664 implementer).

**The claim to test.** DOC-A.1-159 (the report writer's logical record structure) states that a refused wide line sets
`'91'` in the report file's connector, "`'71'` if the file is ORGANIZATION LINE SEQUENTIAL". The PB1664 change made every
report file's line end the host newline whatever its ORGANIZATION, and `src/Cobol.Net.Runtime/IO/FileRegistry.cs#RegisterReport`
passes `lineSequential: false` for every report connector, so the line-sequential arm that answers `'71'` (§14.9.51.4 GR23) is
probably never reached for a report file.

**Probe.** `E:\COBOL-coord\scratch\w1037c\p1664\rptls.cob` with a source item holding a character above U+00FF, the report
file declared ORGANIZATION LINE SEQUENTIAL; read the FILE STATUS through a declarative or a following WRITE of the same file.

**Owed.** Whichever status the probe shows, make the code and DOC-A.1-159 agree, with the witness golden; if `'71'` is the
documented choice, the report connector must know its file is line sequential.

## Re-filed as a defect (analyses sweep, 2026-10-23)

Adjudicated read-only by an Opus cobol-adjudicator on main e7cf38ce4; accepted by the Mythos session.

Documentation defect (rule 6): docs/CONFORMANCE.md DOC-A.1-159 states that a refused wide print line sets '91' in the report file's connector, ''71'' if the file is ORGANIZATION LINE SEQUENTIAL. The code answers '91' for every report file (FileRegistry.RegisterReport passes lineSequential: false; the print arm's refusal at SequentialConnector.cs:1456-1457 returns CharacterWithoutByteImage), and FileCharacterSet.cs:18-20 documents exactly that. Because GENERATE, INITIATE and TERMINATE do not store the FILE STATUS item and run no USE procedure (the same row's PB1603 determination; measured: status 00 throughout, the refused line left blank), the connector's value is not observable, so no program behavior changes either way and the '71' arm would need a report-file line-sequential flag for a value nothing can read. Fix: rewrite DOC-A.1-159's parenthetical to '91' for every report file whatever its ORGANIZATION (matching the code and FileCharacterSet), keep the probe's observable facts as the witness (blank line, status unchanged, no USE), and add in the same edit the PB2510 sentence on why GnuCOBOL's report paging is not followed. No code change. Still listed in PB3420 tier 3; the fix is a one-row doc edit and could ride any docs landing.

Evidence: Probe 2026-10-23 (probes/pb2556/rptwide.cob, ORGANIZATION LINE SEQUENTIAL report file with FILE STATUS and a USE procedure, the second of three GENERATEs carrying U+0100 through a PIC N SOURCE, --std 2023): the line is refused and leaves a blank line ('DD A / (empty) / DD B'), FILE STATUS reads 00 after every GENERATE and after CLOSE, the USE procedure never runs - exactly DOC-A.1-159's PB1603 determination, so the connector's '91'/'71' is not observable by a program. Code: FileRegistry.cs:183-184 registers every report connector lineSequential:false, SequentialConnector.cs:1456-1457 then answers '91', and FileCharacterSet.cs:18-20 documents '91' 'for every other organization and for a report file'. DOC-A.1-159 alone says ''71'' if the file is ORGANIZATION LINE SEQUENTIAL.
