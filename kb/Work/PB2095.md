# PB2095 — a bit item has no area at the call boundary

Filed 2026-10-05 by the train-1023 lander from the w1023a implementer report (PB2087 finisher, lead 2).

**Rule.** ISO §14.2.3 GR8: "If the argument is passed by reference, the activated runtime element operates as if the
formal parameter occupies the same storage area as the argument."

**Mechanism.** `CallEmitter.AreaFact` (`src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs` ~516-527) states a
`CobolArg.Area` only for a `RedefViewPlace` over a cell whose item is NOT a bit item (`BitLayout.IsBitItem(view.ViewItem)`
excludes it): a bit item's positions are bits, not character positions of the cell. A GROUP-USAGE BIT group passed BY
REFERENCE therefore crosses through its carrier alone, and a bit-group AREA formal of the activated element gets a fresh
cell, filled at entry and stored back at return — a copy. With the same group passed twice (`CALL "S" USING G G`, or the
INVOKE equivalent) the second formal does not see a store made through the first, and the first's copy-back at return
undoes the second's stores.

**Repro.** `E:\COBOL-coord\scratch\w1023a\p\ubt.cob` (a GROUP-USAGE BIT group passed to a bit-group formal), extended to
pass the group twice to two formals: a store through LK-1 is not visible through LK-2.

**Fix direction.** Give a bit item an area the formal can be laid over: the area's offset and width in BIT positions (the
cell's bit window), and the bit-group area formal's windows addressing those positions — one area description for
character and bit storage, not a second crossing.

## Landed 2026-10-07 (wave 1033 group B, w1033b)

**Re-probed on this tree first** (`E:\COBOL-coord\scratch\w1033b\p\bg2.cob`, `CALL "BG2S" USING G G` with G a
GROUP-USAGE BIT group): `L2=1010`, `L1=0101`, `out=1111`, so each bit formal held its own copy.

**Root.** The activated side was already right: a bit-group formal is an AREA formal, laid over `CobolArgAdapt.Area`
and windowing its bits at `8 * CobolPtr.OffsetOf(area) + ClassBitOffset`. The activating side never stated the area:
`CallEmitter.AreaOf` refused every view whose item `BitLayout.IsBitItem`, so the argument crossed through its carrier
alone and the formal got a fresh cell. **Fix:** `AreaOf` states a bit item's area as its cell and the character offset
of its first bit, `BitWindow.OffsetExpr / BitLayout.BitsPerCharacter`. The division is exact because §14.9.4.3 SR6 (and
its INVOKE and function twins §14.9.23.3 SR12 and §8.4.3.2.3 SR14, all asked through
`ParameterConformance.ScreenBitAlignment`) requires a BY REFERENCE bit item to be "aligned on a byte boundary"
(`cite.py --check 14.9.4.3 "aligned on a byte boundary"` gives OK §14.9.4.3 6)). The fix is the description the note
asked for: one area for character and bit storage, no second crossing. `AreaOf` is the one site the CALL and INVOKE
lanes both ask, so both arms are fixed at once.

**Witness.** `conformance:2002/pb2095_bit_item_by_reference_area`: G G to two bit-group formals, a bit group in the
middle of a record (RX and RY untouched), a bit leaf to a REDEFINED bit formal, and an INVOKE's two method formals.
Expected values were derived from GR8 before the run, and the run matched. No negative golden: the defect was a wrong
answer on legal source, and the edition gate of GROUP-USAGE BIT below 2002 belongs to the version matrix.
