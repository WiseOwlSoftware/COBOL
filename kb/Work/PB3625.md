# PB3625 — a date-numbered wave outranks every later serial wave in the planner's report order

> ⚙ **flags:** process-only · silent

**Found 2026-10-23 ~21:35 PDT by the wave-20261027 loop unit**, reading `plan_wave.py`'s table.

## What happens

`plan_wave.py --from-budget --borrow-days 0` planned group A of wave 20261027 as a FINISH-FIRST finisher for PB3340,
PB3492 and PB3614, its pred naming `w20261024a-PB3340-report.md` (SPLIT, written 2026-10-23 15:12) and its branch
`worktree-wf_f6f89a51-99e-1` (head `c860b0a96`). But:

- `c860b0a96` is an ANCESTOR of `w1157a-pb3340-sequential-journal` (`git merge-base --is-ancestor` exits 0), and
- that branch has a NEWER report, `w1157a2-PB3340-report.md` (Status DONE, written 19:49), and fresh commits
  (`daf5443d2`, 21:09) from the Mythos lane, which owns it.

The planner treated the 15:12 SPLIT report as PB3340's newest report because `load_reports`
(`scripts/orchestrator/plan_wave.py`, the `sorted(... key=lambda r: (r.wave, mtime, name))` at its end) orders by
`Report.wave`, an `int`: 20261024 > 1157. The two lanes use different numbering (the loop's waves are date-numbered,
`20261024`; the Mythos lane's are serial, `1157`), so every date-numbered report outranks every serial one whatever
their times, and the DONE report and its carrier never get to supersede the SPLIT report.

The unit dropped group A from the args before launch (`plan_wave.py --release 20261027a`) because the operator's
handoff had already put that branch off limits; without that handoff the fleet would have spent an Opus finisher
cherry-picking work that is already on the other branch.

## Root cause and fix shape

The wave number is not a time order between lanes. The order "newest report for a note" needs one key that is a real
order across every lane: the report's write time (or the dispatch ledger's `at` for its group), with the wave number
at most a tie-break inside one lane. Sweep every reader that orders reports or compares waves (`load_reports`, the
`--wave next` "one past the highest seen" rule, `prune_worktrees.py` and the branch survey's newest-report reads) for
the same assumption, and pin it with a fixture where a serial-wave DONE report written after a date-wave SPLIT
report for the same note supersedes it. Sibling: PB3170 (a SPLIT report re-planned although another branch replays
it).
