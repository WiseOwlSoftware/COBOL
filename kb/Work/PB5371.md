# PB5371 - a night's date was a slice of its run id

**Sites:** `scripts/fuzz_history.py#night_date`, `scripts/fuzz_history.py#run_stats`, `scripts/fuzz_history.py#unrecorded_runs`,
`conformance-suite/fuzz-history.json`

## What was wrong

`night_date` returned characters 5 to 12 of the run id, formatted as a date:

    d = n["run_id"][len("fuzz-"):len("fuzz-") + 8]
    return f"{d[:4]}-{d[4:6]}-{d[6:]}"

A run id is the run directory's name. The harness names it `fuzz-<yyyymmdd>-<hhmmss>` by default (`differential_fuzz.py`,
`fuzz_night.ps1`), but `--out` and `-RunDir` take any name, and Night 10's directory was `fuzz-batch-3000-20261103`. Its
slice is `batch-30`, so the page and `FUZZ-LEDGER.md` said "The totals below run from 2026-10-20 to batc-h--30" and listed
Night 10 as started on `batc-h--30`. Ledger versions 24c8d12f80a5 and 1485221e1e53 both carried it, and both were
published to the Artifact. Nothing refused it: the function formatted whatever eight characters it found.

## The fix

A night's date is a recorded fact, not a parse of a name.

- `run_stats` writes `date` into the record: the local date of run.json's `started` on the host that records the night
  (`local_date`). run.json writes UTC, whose own date is the next day for every night that starts in the evening in
  Pacific time (eight of the ten nights), so the UTC date cannot be shown as it stands. A `started` that is no ISO time
  with a zone is refused.
- `night_date` returns the record's `date` and stops the render on a record without a valid one, naming the run.
- `unrecorded_runs`, which finds runs that have no record by the harness-given name, takes the date from that name's own
  date group (`RUN_ID`) and refuses a name whose eight digits are no calendar date. That is the one place a date still
  comes from a name, and the pattern that finds the run is the one that states it.
- The ten records of `conformance-suite/fuzz-history.json` carry `date` now. Each was computed by `local_date` on the
  host that ran the nights, and each equals the date in its run id (nights 1 to 9) or its batch name (night 10).

## Evidence (2026-11-12)

- Before: `FUZZ-LEDGER.md` on origin/main, version 1485221e1e53: `| Night 10 | batc-h--30 | claude-sonnet-5-5 | ...`.
- After: `python scripts/fuzz_history.py render` writes version 5c32a0aba63c: `| Night 10 | 2026-11-03 | ...` and
  "from 2026-10-20 to 2026-11-03". The diff of `FUZZ-LEDGER.md` is those two lines and the version stamp.
- `python scripts/test_fuzz_history.py`: GREEN. Its DATE arms were run once before the history was backfilled and the
  tracked-history arm stopped on night 1 ("carries no ISO `date`"), so it can fail.

## Sibling sweep

`RUN_ID` (`fuzz-\d{8}-\d{6}`) was the other place that assumed the default name: `unrecorded_runs` uses it to find runs
in a note's `source`. It cannot find a run that has no record and a hand-given name. That is a design gap of its own,
filed as PB5372. No other script reads a date or a time out of a run id (`git grep` over `scripts/` for `"fuzz-"`,
`fuzz-\d` and `night_date`: the two default-name writers and this file only).
