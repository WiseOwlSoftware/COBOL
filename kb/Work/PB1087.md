# PB1087 — OPEN — no SAME-clause syntax-rule validator exists: `DataBinder.BindIoControl` links Format 2 and `continue`s past Formats 1/3, silently drops an undeclared operand, a

## Rule text (every citation re-run by the registrar)
- `python scripts/spec/cite.py --check 12.4.6.4.3 "File-name-1 and file-name-2 shall be specified in the FILE-CONTROL paragraph of the source element that contains this SAME clause"` → `OK  §12.4.6.4.3 2)  (Syntax rules)`
- `python scripts/spec/cite.py --check 12.4.6.4.3 "File-name-1 and file-name-2 shall not reference an external file connector"` → `OK  §12.4.6.4.3 3)  (Syntax rules)`

### Adjudicator finding (same-clause, harm under-rejects)
- **Mechanism:** The SAME clause grammar admits a ONE-operand clause: `sameClause : SAME (RECORD|SORT|SORT_MERGE)? AREA? FOR? fileName (COMMA? fileName)*` - the trailing `*` lets file-name-2 be absent, and nothing at bind counts the operands, so `SAME [RECORD|SORT] AREA FOR F1.` compiles silently at every edition.
- **Repro:** I-O-CONTROL. SAME RECORD AREA FOR F1.  (also SAME AREA FOR F1.) with SELECT F1 / FD F1 01 F1-REC PIC X(6); `cobol p.cob --run` at --std 2023 or 85 -> exit 0, no diagnostic (probe out/probe/same-clause/fmt_single_rec, fmt_single_area).
- **Expected (spec):** Rejected at compile time: every format prints `file-name-1 { file-name-2 } …` (one or more additional file-names), and GR1/GR2 define the clause over 'two or more files referenced by file-name-1, file-name-2'.
- **Observed:** Compiles and runs; the one-file record-area group is linked with no peers. Fix shape: `fileName (COMMA? fileName)+` in CobolIO.g4, or (preferred for a named diagnostic, the project's superset-parse/bind-narrow posture) an arity check in the SAME-clause validator of finding M2.
- **Code site:** src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4#sameClause (line ~331); src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindIoControl
- **Clause (adjudicator):** ISO/IEC 1989:2023 §12.4.6.4.2 (General formats; figure notes) with §12.4.6.4.4 GR1/GR2 'two or more files'

### Adjudicator finding (same-clause, harm under-rejects)
- **Mechanism:** No SAME-clause syntax-rule validator exists. DataBinder.BindIoControl is the clause's only consumer: it links Format 2's storage and `continue`s past Formats 1 and 3, and for Format 2 silently drops any operand that is not a declared file. Its doc comment declares the SR2-SR11 legality checks 'staged with the version-conformance pass phase'; none was ever written. So name resolution (SR2), the external-connector ban (SR3), and the whole cross-clause membership calculus - report file (SR5), sort/merge file (SR6), plain file (SR7) per-format occurrence limits, the sort-file requirement (SR8), and the file-area-subset rules (SR9, SR10) - accept every violation silently.
- **Repro:** Each of these compiles and runs with exit 0 and NO diagnostic (pinned cobol.exe, --std 2023; SR2 also at 85), programs in out/probe/same-clause/<name>/: sr2_undeclared `SAME AREA FOR F1 NOPE.`; sr2_undeclared_rec `SAME RECORD AREA FOR F1 NOPE.`; sr2_dataname `SAME AREA FOR F1 WS-X.`; sr3_external `FD F1 IS EXTERNAL` + `SAME AREA FOR F1 F2.`; sr5_report_rec `SAME RECORD AREA FOR F1 R1.` (R1 an FD with REPORT IS); sr5_report_sm `SAME SORT AREA FOR S1 R1.`; sr5_report_two_fa R1 in two `SAME AREA` clauses; sr6_sort_filearea `SAME AREA FOR F1 S1.` (S1 an SD); sr6_sort_two_rec S1 in two `SAME RECORD AREA` clauses; sr7_two_filearea / sr7_two_recarea F1 in two file-area / two record-area clauses; sr8_no_sortfile `SAME SORT AREA FOR F1 F2.` (no SD); sr9_partial `SAME AREA FOR F1 F2` + `SAME RECORD AREA FOR F1 F3`; sr10_partial `SAME AREA FOR F1 F2` + `SAME SORT AREA FOR S1 F1`.
- **Expected (spec):** Every one is a syntax-rule violation and shall be rejected at compile time: SR2 (names shall be in FILE-CONTROL), SR3 (no external file connector), SR5 (report file only in one file-area clause), SR6 (sort/merge file never in a file-area clause, at most one record-area and one sort-merge-area), SR7 (plain file in at most one file-area and one record-area clause), SR8 (a sort-merge-area clause needs a sort or merge file), SR9/SR10 (a file-area clause's files, once any appear in a record-area / sort-merge-area clause, shall all appear there). The positive halves (sr5_report_ok, sr7_ok_multi_sm, sr9_ok, fmt_all_ok) must keep compiling.
- **Observed:** All accepted silently; the record-area arm additionally builds a wrong sharing group from them (an undeclared operand is dropped; a sort file in two record-area clauses is chained into both). Fix shape: ONE I-O-CONTROL SAME-clause validator that classifies each operand (resolved file? external? FD/SD/report-FD?) and each clause's format (SORT and SORT-MERGE the same format per SR1), then checks per-file per-format occurrence counts and the SR9/SR10 subset relations - a table keyed by (file kind x format) -> allowed count, so SR5/SR6/SR7 are one rule shape rather than three hand-written checks; add a unique diagnostic per SR and a negative golden per rule. Also consider MERGE §14.9.24.3 SR11 / SORT §14.9.40.3 SR10 (SAME-clause pairings), which read the same classification.
- **Code site:** src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindIoControl (lines ~1731-1811; the `continue` at ~1779 and the silent skip at ~1795)
- **Clause (adjudicator):** ISO/IEC 1989:2023 §12.4.6.4.3 SR2, SR3, SR5, SR6, SR7, SR8, SR9, SR10
