# PB33 — LANDED — the value-producing twin now uses the validator instead of a second copy

> ⚙ **flags:** under-rejects
> §15.68.3 r1's two formats are the substance of the rule and are unenforced; sub-rules b–f conform. The
> 31-digit native cap is applied by `TestNumvalC` and not by `NumvalC` — the SAME asymmetry, from the same cause
> (the validating twin was fixed, the value-producing one was not). A sibling of PB32.

## ⚙ THE SECOND HALF LANDED 2026-08-06 — and the harm was WORSE than "under-rejects"

**MEASURED, and the flags on this note were too kind.** It was filed `under_rejects` only:

| argument-1 | `NUMVAL-C` before | `TEST-NUMVAL-C` |
|---|---|---|
| `"12$34"` | **1234 — a WRONG ANSWER** | error at position 3 |
| `"$1,2X4.5"` | 0, silently | error at position 5 |
| `"1.2.3"` | 0, silently | error at position 4 |

Interior currency is neither §15.68.3 r4a format, and stripping it produced a plausible number out of malformed
input. `wrong_answer` and `silent` are now set — the note ranked itself below what it actually did.

**THE FIX IS THE VALIDATOR, NOT A SECOND COPY OF THE RULE.** `TestNumvalC` already implements both r4a formats
exactly — that IS §15.94's job — while `NumvalC` stripped the currency and grouping separators, delegated to
`Numval`, and checked nothing. `NumvalC` now calls `TestNumvalC` and raises **EC-ARGUMENT-FUNCTION** on a
non-zero verdict (§15.3 — "If the evaluation of an argument results in an incorrect value for that argument …";
with checking off the same clause leaves the result implementor-defined, which `ArgumentError`'s 0 supplies).
⭐ The digit cap already worked this way (PB33's landed half, whose comment says "the rule has ONE implementation
for both functions rather than a copy per twin") — **the same shape now covers the whole rule**
([[feedback_one_rule_one_place]]).

⚠ Both paths were verified, not assumed: with `>>TURN EC-ARGUMENT-FUNCTION CHECKING ON` the declarative is
dispatched and the run terminates (Table 13 — fatal, §14.6.13.1.3 #7); with checking off the default stands.
⚠ Conforming values are untouched — `$1,234.5` → 1234.5, `$1,234.5CR` → −1234.5, `$12.34-` → −12.34, and
`$1,23,4.5` → 1234.5 (r4a's grouping is `digit [, digit]…` with no 3-digit constraint).

**Golden** `pb33_numval_c_format_validation` — 8 assertions, each nonconforming case PAIRED with
`TEST-NUMVAL-C` so the two functions are asserted to agree rather than merely both exist.
