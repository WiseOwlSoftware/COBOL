# PB365 — three operand arms, three wrong sets, three lines of code

**Rows:** `SR-14.9.49.3-9`, `SR-14.9.49.3-16`, `SR-14.9.49.3-17`, `GR-14.9.49.4-1`, `GR-14.9.49.4-14`. Four
adjudicated mechanisms (use p1 x3, use p2 x1) at one site.

## Arm 1 — Format 2 stops at the first match where the rule requires exactly one

`<lane3 scratch>/out-b1/probe/sr9amb/amb2.cob` — one program with two report descriptions, `RD R-A` and `RD R-B`,
EACH declaring a detail group named DET-A, and a declarative `BR SECTION. USE BEFORE REPORTING DET-A.`
**Compiles at `--std 2023` with zero diagnostics**; the declarative binds to R-A's group purely because R-A is
written first, so **a GENERATE of R-B's DET-A never runs the procedure the programmer wrote for it.** The
qualified spelling is unaffected (`qual.cob`, `USE BEFORE REPORTING DET-A OF R-B.`).

> §8.4.2.1: In order to use a resource, a statement shall contain a reference that uniquely identifies that
> resource.

`--check 8.4.2.1` → **OK**. §14.9.49.3 SR9's identifier-1 is an identifier in the §5.2.4 sense, so §8.4.2.2's
qualification and uniqueness rules apply; the report-name is the available qualifier, which is why the qualified
form exists.

`DeclBindUse`'s Format-2 arm (lines ~424-437) **RETURNS INSIDE the loop**, so it stops at the first match and can
never observe a second: the loop shape encodes *find one* where the rule requires *find exactly one*. Because it
is a wrong BINDING rather than a rejection, nothing downstream notices — the SR9 duplicate check
(`_declReportGroups.Add(group)`) is keyed on the `ReportGroupModel` OBJECT, so the two same-named groups are
distinct objects and that guard stays quiet too.

## Arm 2 — Format 4's class name is validated against the compilation group, not the REPOSITORY

`out-b1/probe/fmt-f4/norep.cob` — a program with **no REPOSITORY paragraph at all** whose declarative writes
`USE AFTER EXCEPTION OBJECT CF4A.`, naming a class defined later in the same compilation unit. **Compiles with
zero diagnostics.**

> SR16: Object-class-name-1 shall be the name of a class specified in the REPOSITORY paragraph.

`--check 14.9.49.3` → **OK**. The condition is membership of the REPOSITORY of the SOURCE ELEMENT containing the
USE, not existence somewhere in the group. `DeclBindUse` resolves with `ctx.Data.OoClasses?.Find(cname)`, where
`OoClassTable` is built once per compilation group from every CLASS-ID definition — and **the miss diagnostic
COBOLNET0859 names the wrong condition out loud**: *does not name a class of the compilation group*. The compiler
DOES model REPOSITORY specifiers elsewhere (`DataBinder.cs:361-372` collects the PROPERTY / INTERFACE / CLASS
specifiers, and `IntrinsicBinder` enforces the §8.4.3.2.3 SR2 REPOSITORY condition for intrinsic-name omission),
so the data exists and only this class of reference skips it. The under-rejection is SYSTEMIC rather than local —
`DataBinder.cs:2378` screens an `OBJECT REFERENCE class-name` the same group-wide way.

## Arm 3 — interface-name-1 has no resolution path, and is rejected by the sibling rule's diagnostic

`out-b1/probe/fmt-f4/iface.cob` and `probe/gr14-f4/iface.cob` — a REPOSITORY declaring `CLASS CF4A INTERFACE
IF4A`, an `INTERFACE-ID. IF4A.` definition, a class whose OBJECT paragraph writes `IMPLEMENTS IF4A.`, and
`USE AFTER EXCEPTION OBJECT IF4A.` Observed a HARD REJECTION:
`error COBOLNET0859: ... 'IF4A' does not name a class of the compilation group (ISO 14.9.49.3 SR16; interface
entries are the interface-RAISING refinement)`. The identical program naming the CLASS compiles and runs.

> SR17: Interface-name-1 shall be the name of an interface specified in the REPOSITORY paragraph.

> §14.9.49.4 GR14 b): [the declarative is selected when] the exception object that was raised is described with
> an IMPLEMENTS clause that references interface-name-1

Both `--check` → **OK**. §14.9.49.2's Format 4 is `USE AFTER {EXCEPTION OBJECT | EO} {object-class-name-1 |
interface-name-1}` — a brace group requiring exactly one of TWO alternatives, and only the class arm was
implemented. `OoClassTable` exposes a sibling `FindInterface` — called from `OoBinder.cs:331` and
`DataBinder.cs:2378` — that this site NEVER calls, so the interface alternative has no resolution path, no
`BoundDeclarative` shape (`DeclScope` carries only `EoClassCsName`), and no selector arm. **The diagnostic it
lands on is SR16's**, so the gap reads in the build log as a user error about a class name, and it cites a real
clause answering a different question.

## The fix shape

One class-name / interface-name resolution funnel that takes the REFERRING UNIT's REPOSITORY set as its scope,
which every OO name reference calls — never a REPOSITORY test bolted onto `DeclBindUse`. For Format 2, collect
ALL candidate matches and diagnose when the count exceeds one; the same *first report wins* shape recurs in
`ReportWriterBinder.RwFindReport` and in the LINE-COUNTER / PAGE-COUNTER resolution nearby, so that is a pattern
to sweep rather than a single site.

Fixing arm 3 is the D-EO7 selector's IMPLEMENTS half, not a lookup swap: `DeclScope` needs an interface arm and
the emitted `__EcObjDispatch` needs GR14's *implements* test. And note GR14 is a **TWO-PASS** rule (*otherwise,
all of the USE statements in the source element are analyzed again and: b) ...*) while `EmitObjDispatchSelector`
emits ONE pass — so adding interface entries means RE-SHAPING the selector into pass-1 class tests followed by
pass-2 interface tests, not appending them to the same list. The other defect in that selector is **PB366**.

**Code sites:** `ProcedureTableBuilder.cs#DeclBindUse` (lines 401-437, the COBOLNET0859 site and the Format-2
`foreach`) · `OoClassTable.cs#Find`, `#FindInterface` · `EcEmitter.cs#EmitObjDispatchSelector` ·
`DataBinder.cs:361-372`, `:2378`.

## Landed 2026-09-09

All three arms are fixed, each at the ONE place its rule belongs, and each with a funnel plus a drift test so
the next case is automatic (CLAUDE.md rule 5). `GR-14.9.49.4-14` left this note's `inventory_rows`: PB365 landed
its GR14 b) half and **PB366** owns the row for the factory-arm divergence that remains.

**Arm 1 — one report-group reference funnel.** `src/Cobol.Net.Compiler/Binding/ReportGroupResolution.cs` is the
only resolver of a written report-group name. It collects EVERY candidate and reports **COBOLNET1920** when more
than one survives — §8.4.2.2.1 ("uniqueness shall be established through qualification for each user-defined
name explicitly referenced") and §8.4.2.2.3 SR1. The `foreach (report) … FirstOrDefault(name)` search is gone
from BOTH consumers, and `ReportGroupResolutionDriftTests` fails on any file that reintroduces it (fired on both
pre-fix sources, silent on both fixed ones — measured, not assumed).

The SIBLING the note predicted was real and worse than a duplicate loop: `ReportWriterBinder.BindGenerate` had
the same first-report-wins shape AND `generateStatement : GENERATE reportName` could not parse a qualifier at
all, so `GENERATE DET-A OF R-B` — legal by §14.9.16.3 SR1's second sentence, "It may be qualified by a
report-name" — was `COBOL0001: no viable alternative at input 'OF'`. Both consumers now share one grammar rule,
`reportGroupReference : cobolWord ((IN | OF) reportName)?` (§8.4.2.2.2 Format 1's file-report-qualifier; SR3
makes IN ≡ OF), and USE Format 2's operand stopped being spelled `procedureName` — it references a report GROUP.
`RwFindReport` and the LINE-COUNTER / PAGE-COUNTER resolution were checked and are NOT instances: report-NAMES
are unique in a source unit, and `CounterExpr` already implements §8.4.2.2.3 SR9/SR10 correctly.

**Arms 2 and 3 — one class-name / interface-name funnel, scoped by §8.4.6.4.**
`src/Cobol.Net.Compiler/Oo/OoNameResolution.cs` owns "The object-class-name of an object class referenced within
a source element shall be either the name of the containing object class definition or declared in the
REPOSITORY paragraph of that or a containing source element", and the same sentence for interface-names. The
scope is an ancestor walk over the parse tree — §12.3.3 SR1/SR2/SR3 leave only the outermost program, the
function definition, the class definition and the interface definition able to carry a REPOSITORY, and §12.3.4
GR1 spreads each one's entries to every contained source unit, so the walk IS the rule with nothing to plumb and
nothing to keep in sync. It is memoized per source element on `OoClassTable.RepositoryScopeFor`.

The under-rejection was systemic exactly as the note said, so the funnel serves every site with a REPOSITORY
rule, not just `DeclBindUse`: §11.3.3 SR2 and §11.6.3 SR2 (INHERITS), §11.4.3 SR1 and §11.8.3 SR1 (IMPLEMENTS —
whose enforcement `OoClassTable` had described in a comment as "staged as a documented follow-up"), §14.2.2
SR8 (the PD-header and METHOD-ID RAISING partitions, through the non-diagnosing `Lookup`), `USAGE OBJECT
REFERENCE`, INVOKE's class-name-1 receiver, SET's class-name-1 sender, and the object-property reference's
class-name qualifier. `OoNameResolutionDriftTests` pins the remaining direct `OoClassTable.Find` callers, every
one of which re-looks-up an ALREADY scope-checked declared name rather than resolving a written reference.

**Eleven corpus programs and twenty-one inline `OoSpineTests` programs were NON-CONFORMING** and are repaired,
not exempted: each referenced a class or interface from a class definition that declared no REPOSITORY, which
§11.3.3 SR2 / §11.8.3 SR1 / §8.4.6.4 forbid. The compiler had been accepting them.

**Arm 3 also needed the SELECTOR re-shaped, exactly as the note warned.** `DeclScope` / `BoundDeclarative` carry
`BoundEoOperand` — ONE discriminated value (`BoundEoClass(OoClassSymbol)` | `BoundEoInterface(OoInterfaceSymbol)`),
never two nullable fields, because §14.9.49.4 GR14 gives the two alternatives two different tests in two
different passes. `EmitObjDispatchSelector`
now emits pass a) (every object-class-name-1 entry, source order) and only then pass b) ("all of the USE
statements in the source element are analyzed again": every interface-name-1 entry). GR14 b)'s "described with
an IMPLEMENTS clause that references interface-name-1" is §11.8.4 GR2 / §11.4.4 GR2's closure, and the emitter
already renders each class with exactly that closure as its C# interface list, so `__obj is <interface>` is all
three legs. `2002/pb365_use_eo_interface_two_pass` writes the INTERFACE declarative FIRST and expects
`CLASS-CY / AFTER-1 / IFACE / AFTER-2`: an interleaved single pass produces `IFACE` for both raises.

**Goldens:** `2023/pb365_report_group_qualified`, `85/pb365_report_group_qualified_85`,

## Reconciled with PB366 on train 24's main — 2026-09-09

This branch and **PB366** reshaped the SAME Format-4 operand from the same base `d497f3c7`, in opposite
directions, and both were right about their own half. The merge (7 content conflicts, every one resolved by
keeping both facts) landed ONE shape:

- `BoundEoOperand` is an abstract record over the two alternatives, each carrying its **resolved symbol** —
  `BoundEoClass(OoClassSymbol)` for object-class-name-1 (SR16 / GR14 a)) and
  `BoundEoInterface(OoInterfaceSymbol)` for interface-name-1 (SR17 / GR14 b)). **The `BoundEoOperand.CsName`
  smell this note's report flagged — a rendered C# type name inside a bound node — is gone**: choosing the C#
  spelling, and how MANY spellings one COBOL name selects, is the emitter's job.
- `EmitObjDispatchSelector` keeps this note's TWO GR14 PASSES and, inside each pass, renders that
  alternative's OWN CENSUS of emitted C# types as one `is` or-pattern. `EmitObjDispatchPass` now takes the
  census as a `Func<BoundEoOperand, IReadOnlyList<string>?>` that returns null for an entry belonging to the
  other pass — the same null-means-skip shape the F3 `Tier` scans in the same file use — so the pass boundary
  and the per-alternative census are one decision each and the or-pattern is spelled once.
- A class entry renders PB366's `OoClassSymbol.FactoryOrInstanceCsTypes` (`__obj is X or X__FACTORY`); an
  interface entry renders the new `OoInterfaceSymbol.ImplementedCsTypes`, which MEASURES one today because a
  COBOL INTERFACE-ID emits exactly one C# interface that both emitted halves of an implementing class carry.

`tests/conformance/2002/pb366_use_exception_object_factory.cob` was **non-conforming and is repaired, not
exempted**: two of its class definitions inherit from `PBFBASE` with no REPOSITORY paragraph, which §11.3.3 SR2
forbids and this note's §8.4.6.4 funnel enforces for the first time — so on the merged tree it was rejected with
two COBOLNET0821s until it gained the four-line REPOSITORY block, exactly the repair the eleven corpus programs
above got. Both goldens then matched their `.out` byte-for-byte on the merged tree.

`Format4UseObjectSelectorDriftTests` grew the interface twin of the census fact and the reconciliation's
load-bearing fact — the class pass precedes the interface pass in the GENERATED C#, with the fixture writing the
INTERFACE declarative first — and both new detectors were FIRED (a deliberately wrong census; a deliberately
swapped pass order) before being trusted. **`GR-14.9.49.4-14` CLOSED (DIVERGES → CONFORMS)**: it carried two
measured defects, each mechanism owned one, and this is the first tree on which both cures exist together.
