# PB4532 — table-sort-collating-sequence-persists: Table SORT without COLLATING SEQUENCE reuses the alphabet of an earlier SORT's COLLATING SEQUENCE phrase

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

After a table `SORT ... COLLATING SEQUENCE IS alphabet-name` has run, a later table SORT in the same program that has
no COLLATING SEQUENCE phrase still sorts with that alphabet instead of the program collating sequence. A native
SORT run before the alphabet SORT is correct, so the alphabet persists from one SORT statement to the next.

## Minimal test case

Free reference format (`-free`).
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. SORTCS.
ENVIRONMENT DIVISION.
CONFIGURATION SECTION.
SPECIAL-NAMES.
    ALPHABET CI IS "A" ALSO "a" "B" ALSO "b".
DATA DIVISION.
WORKING-STORAGE SECTION.
01 T VALUE "bAaB".
   05 E PIC X OCCURS 4 TIMES.
PROCEDURE DIVISION.
    SORT E ON ASCENDING KEY E
    DISPLAY "NATIVE 1 " T
    SORT E ON ASCENDING KEY E COLLATING SEQUENCE IS CI
    DISPLAY "CI       " T
    SORT E ON ASCENDING KEY E
    DISPLAY "NATIVE 2 " T
    STOP RUN.
```

## Environment

cobc (GnuCOBOL) 3.2.0 on WSL2 Ubuntu (ASCII native character set). `cobc -x -free -std=cobol2014 -o p prog.cob && ./p`.

## Observed result

Exit code 0:
```
NATIVE 1 ABab
CI       AaBb
NATIVE 2 AaBb
```

## Expected result (per ISO)

§14.9.40.4 5): the collating sequence for alphanumeric keys is "determined at the beginning of the execution of the
SORT statement", a) by the COLLATING SEQUENCE phrase "if specified, in this SORT statement", otherwise b) "Second, the
collating sequences established as the program collating sequences." The third SORT has no phrase and the program
names no PROGRAM COLLATING SEQUENCE, so by §12.3.6.4 10) "the initial program collating sequences are the native
alphanumeric collating sequence and the native national collating sequence": the native (ASCII) sequence applies and
"AaBb" sorts to "ABab", as the first SORT did. (The second line's order of A/a and B/b is undefined by §14.9.40.4 4)
without DUPLICATES; it is not the subject.) The rules are in the 2014 edition. Expected output:
```
NATIVE 1 ABab
CI       AaBb
NATIVE 2 ABab
```

## Our compiler

WiseOwl COBOL (fresh judge, `--std 2014 --source-format free`) compiles it with no diagnostic and prints the expected
three lines, exit 0.

## Fix site

cobc/parser.y, `sort_merge_body` with `_sort_collating` (read in the GnuCOBOL 3.2 source): the SORT action passes the
file-static `alphanumeric_collation` (and `national_collation`) to `cb_emit_sort_init`, and only the
`coll_sequence_values` alternatives of `collating_sequence` assign it; the empty alternative of `_sort_collating`
leaves whatever the previous COLLATING SEQUENCE phrase stored. The leak is at compile time: `cobc -C` on the program
emits `cob_table_sort_init (1, 0)` for the first SORT but `cob_table_sort_init (1, s_CI)` for both the second and the
third. libcob (`cob_table_sort_init`, which falls back to `COB_MODULE_PTR->collating_sequence` for a null argument)
behaves as designed. The same variable feeds file SORT and MERGE through `cb_emit_sort_init`; those paths are not
exercised by this program.
