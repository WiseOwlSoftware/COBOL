# PB443 — the searched table is chosen by base name and declaration order

Adjudicated in lane-3 batch b2 (`search-statement` part 1, finding search-p1-F1). **All four repros re-run on
HEAD 89044aa0**, each beside its legal counterpart.

## 1. The mechanism

`SearchBinder.BindSearch` (`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SearchBinder.cs:24`) does

```csharp
string tableName = drefs[0].cobolWord()?.GetText() ?? drefs[0].GetText();
```

and `BindSearchAll` (`:83`) does the identical thing over `s.dataReference()`. The grammar's `dataReference`
is `cobolWord dataReferenceSuffix*` (`src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4:480-498`, where
`dataReferenceSuffix` is `subscriptPart | refModPart | qualification`), and `.cobolWord()` returns **only the
base word** — so the entire suffix tail is discarded unread. The name then goes through
`ctx.Symbols.TryResolve(tableName, ctx.ActiveScope, out var candidates)` and
`candidates.FirstOrDefault(i => i.IsTable)` (`:25-27` / `:84-86`), i.e. **the first table with that base name
wins**.

Three consequences with three different harms fall out of that one line:

1. **A wrong answer on legal source.** A qualified identifier-1 whose base name is ambiguous searches the wrong
   table. `FirstOrDefault` breaks the tie by declaration order, and the qualifier that would have decided it
   was thrown away.
2. A reference-modified identifier-1 (syntax rule 1) is neither honoured nor diagnosed.
3. An identifier-1 subscripted at the searched level (syntax rule 2, sentence 2) is neither honoured nor
   diagnosed — and the superordinate subscripting that syntax rule 3 *requires* can never be checked as
   present, because nothing downstream ever sees a subscript at all.

Consequence 1 is not a syntax-rule question and is not gated by any strictness setting: it is a plain wrong
answer, and it must be fixed regardless of how the owner rules on compile-time indication for 2 and 3.

## 3. Expected vs observed, re-measured on HEAD

Compiler: `src/Cobol.Net.Cli/bin/Debug/net10.0/cobol.exe` at 89044aa0, `--std 2023 --run`.

**(1) The wrong answer, and its isolation.** Two groups each containing a table named `E`; `K IN G2 (5)` holds
05; both indexes set to 1; the statement is `SEARCH E IN G2 … WHEN K IN G2 (IX2) = 05 …`:

```
$ cobol qual_ambig.cob --run           ← 01 G1 declared FIRST
exit=0   NONE                            EXPECTED: HIT 05
$ cobol qual_ambig2.cob --run          ← the SAME program with the two 01 declarations SWAPPED, nothing else
exit=0   HIT 05
$ cobol qual_of.cob --run              ← `SEARCH E OF G2`, the other qualifier spelling
exit=0   NONE                            EXPECTED: HIT 05
```

The answer depends on **declaration order**, not on the qualifier. Swapping two declarations is the whole
difference between a correct and an incorrect result, which isolates the cause to name-only resolution and
rules out anything about the WHEN condition or the scan. The SEARCH ALL form has the identical split
(`qual_ambig3.cob`).

**(2) Syntax rule 1 — the reference modifier discarded, not diagnosed:**

```
$ cobol sr1refmod.cob --run            ← SEARCH E(1:3) … WHEN K(IX) = 03 …
exit=0   HIT 03                          EXPECTED: a compile-time diagnostic
```

byte-identical to the legal `SEARCH E` (`ok.cob`).

**(3) Syntax rule 2 sentence 2 — a subscript at the searched level discarded:**

```
$ cobol sr2subscr.cob --run            ← SEARCH E(IX)
exit=0   HIT 03                          EXPECTED: a compile-time diagnostic
```

`SEARCH E(2)` (`sr2sub2.cob`) behaves the same.

**(4) Syntax rule 3 — the required superordinate subscript omitted, with the legal form beside it:**

```
$ cobol sr3_nest_bare.cob --run        ← 05 OUTER OCCURS 3 INDEXED BY OX. 10 INNER OCCURS 4 INDEXED BY IX.
exit=0   HIT 03                          the bare `SEARCH INNER` — EXPECTED: a compile-time diagnostic
$ cobol sr3_nest_ox.cob --run          ← the conforming `SEARCH INNER(OX)`
exit=0   HIT 03                          — and it gives the right answer, so the PERMISSION half conforms
```

The two produce identical output **because** the operand's subscripts are discarded either way, which is
precisely why the omission cannot be detected: there is nothing downstream that would ever notice.

## 4. The code site and the shape of the repair

* `.../Verbs/SearchBinder.cs:24` (`BindSearch`) and `:83` (`BindSearchAll`) — the base-word reduction.
* `.../Verbs/SearchBinder.cs:25-27` and `:84-86` — `TryResolve` + `FirstOrDefault(i => i.IsTable)`.
* `src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4:480-498` — `dataReference` / `dataReferenceSuffix`, the
  structure being thrown away.

**One structural change, not three screens (CLAUDE.md rule 5).** Resolve identifier-1 through the same
reference-resolution path every other operand uses (`ctx.Refs`), which is what makes the qualifier decide the
table and makes the reference modifier and the subscript list *visible* in the first place. Then two screens
become one line each on the resolved reference: reject a reference modifier, and count subscripts against the
table's superordinate nesting depth (0 at the searched level is required; exactly one per enclosing table is
required — syntax rule 3 makes the subscripted spelling legal for the superordinate levels, so a screen that
bans subscripts outright would reject legal source).

⛔ This is the two-arm shape again in its most literal form: `BindSearch` and `BindSearchAll` are two copies of
the same eight lines. Fix the resolution once and have both call it, or the next reader finds one arm repaired.

## 5. The sibling sweep the fixer must do

* **Both binders.** `BindSearch` and `BindSearchAll` duplicate the base-word reduction, the resolve, the
  `IsTable` pick and the INDEXED check. Four pairs, all needing the same repair.
* **Grep for the `.cobolWord()?.GetText() ?? …GetText()` idiom across the binders.** Any other verb that
  identifies an operand by base name has the same ambiguity bug; this is a pattern, not a SEARCH quirk.
  (`InitializeBinder.cs:96` uses the same idiom, but only as a *pre-test* for a whole dynamic table before
  falling through to `ctx.Refs.Resolve` — read each site for which role the name plays before charging it.)
* **The VARYING operand** at `:41-50` *is* resolved through `ctx.Refs`, which is the model to copy — and the
  contrast is itself the evidence that the identifier-1 path is the outlier.
* **Editions.** All four probes reproduce identically at `--std 85`, 2002, 2014 and 2023 (measured at the pin;
  the 2023 re-runs above confirm HEAD), so nothing here is edition-gated and the gate sweep must cover all
  four.

## 7. Landed — 2026-09-13

**The resolution was the fix; the three screens fall out of it.** `ReferenceResolver.ResolveTableOperand` is the
ONE resolution of a reference written where a general format prints a TABLE operand: it reads the whole written
reference through `ReferenceResolver.ReadWritten` — the ONE decomposition of a `dataReference` into its qualifier
chain, subscript group and reference-modification carriers, which `ResolveImplCore`, `ResolveForAddressOf` and
`SubscriptGroupOf` had each written out for themselves and now share — resolves the name through the SAME
§8.4.2.2 candidate-set matcher every other operand uses (`FindItem` → `ResolveQualified`/`ResolveUnqualified`),
reports COBOLNET1639 for a name that identifies no item, and hands back the item plus the two facts the rules are
about. It is deliberately not `Resolve`: SR2 says identifier-1 takes no subscript at the searched level, so there
is no `Place` to build.

The rules live in the one check catalog, `StatementValidation.ResolveSearchTable`, under a single new code
**COBOLNET2075** — one code for one operand position, the division COBOLNET1964–1966 already established for
SR7–SR13 (COBOLNET2076 and COBOLNET2077 were allocated and returned unused).

⛔ **§4's proposed screen for SR3 WAS WRONG, AND THE STANDARD'S OWN VALIDATION SUITE IS WHAT PROVED IT.** This
note asked for "exactly one [subscript] per enclosing table is required", the first implementation shipped that
lower bound, and it **rejects legal source**: the CCVS programs write the bare spelling throughout — NC233A line
516 is `SEARCH ALL GRP2-ENTRY … WHEN SEC (IDX-1, IDX-2) = "(01,01)"` over
`02 GRP-ENTRY OCCURS 10 … 03 GRP2-ENTRY OCCURS 10`, with NO subscript on identifier-1 and the outer occurrence
supplied by IDX-1 **in the WHEN** — and the bound failed SIX NIST programs outright (NC231A, NC232A, NC233A,
NC234A, NC237A, NC238A). §14.9.37.4 GR1 says it directly: "The subscript that is used to determine the occurrence
of each superordinate table to search is specified by the user IN THE WHEN PHRASES. Therefore, each appropriate
subscript shall be set to the desired value before the SEARCH statement is executed." So SR3's "the subscripting
is still required" is required THERE, at run time, and **nothing about identifier-1's written form follows from
it** — SR3 places no screen on the operand at all. What the subscript count CAN decide is SR2's second sentence,
as an UPPER bound: a table-item reference normally takes one subscript per OCCURS level (§8.4.2.3), SR2 removes
the searched level's, so MORE subscripts than identifier-1 has superordinate tables means one sits at that level.
Both spellings are legal, and the 85 golden now runs the SAME nested table both ways and asserts the SAME answer.
The mistake is on the record because it is the one this project keeps making: a rule read as a requirement on the
construct in front of it, when the general rule two clauses later says where the obligation actually lives.

**Both arms, through one helper.** `SearchBinder.Identifier1` is called by `BindSearch` and `BindSearchAll`; the
two copies of the same eight lines are gone, and with them the `BoundUnsupported` staging (PB390's invariant —
an ERROR naming the rule, never the COBOLNET1756 deferral announce) and the message that miscited SR2 as SR1 in
both arms. The nested-dynamic-capacity guard KEEPS the carrier: it is a genuine COBOL.NET increment, not a rule
the source violates.

05 · `qual_of` NONE → HIT 05 · `qual_ambig2` (the swapped declarations) HIT 05 → HIT 05 · `sr1refmod` HIT 03 →

**§5's sibling sweep, and what it found.** `qual_ambig3` (`SEARCH ALL E IN G2`) had ALSO been failing, downstream
of the same line: the Format-2 key screen resolved the WHEN's key correctly and then compared it against the
WRONG table's KEY phrase, so a legal statement drew COBOLNET1965 "not referenced in the KEY phrase". Fixed by the
same change. The `.cobolWord()?.GetText() ?? …GetText()` grep found **one more in this mechanism**, and it is a
defect in its own right — `SearchAllFormat2Rules.CheckConditionNameSide` picked a level-88 by BASE WORD with the
tie broken by declaration order (`conds.FirstOrDefault(c => IsWithin(c.Parent, table)) ?? conds[0]`), ignoring the
OF/IN qualifier the condition BINDER honours. Measured, with two same-spelled condition-names on two keys of one
table: with `ASCENDING KEY IS K1 K2` the SR11 violation in `WHEN CN OF K2 (IX)` went UNREPORTED; with
`ASCENDING KEY IS K2 K1` the same written WHEN is LEGAL and was REJECTED, naming two keys neither of which the
source names. It now resolves through `ConditionBinder.ConditionOf` — the ONE §8.4.2.2 Format-2 condition-name
resolution — which gained a one-report-per-reference guard so the screen and the later bind cannot both report an
ambiguity. Rows SR-14.9.37.3-9 and -11 are re-recorded (verdict unchanged, premise repaired). The remaining
first-word reductions in the binders are other subsystems' (PB489 landed the data-division ones; the REPORT
SECTION SUM/UPON operands are PB482's).
