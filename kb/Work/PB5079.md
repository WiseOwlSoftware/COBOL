# PB5079 - at --std 85 seven Report Writer report-group entry rules are unchecked: PAGE FOOTING first LINE relative, NEXT GROUP without LINE, SUM RESET level, SOURCE of a control name in a page group, format 2 entry with no clause or with no format 3 child, USAGE on a nonprintable format 3 entry

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/ReportSectionBinder.cs` (`ScreenReportLineClauses`, `BindNextGroupClauses`, `ResolveReports`, `ScreenReportEntryClausePresence`), `src/WiseOwl.Cobol.Compiler/Binding/ReportSectionBinder.cs` (`ScreenResetLevel`, `ScreenSourceControlData`, `SourceControlRelation`, `ScreenReportEntryFormats`), `src/WiseOwl.Cobol.Compiler/Binding/ReportModel.cs#ReportSumModel.ResetAt`, `src/WiseOwl.Cobol.Editions/Diagnostics/DiagnosticCatalog.cs` (`ReportResetLevel`, `ReportSourceControlData`).

**Landed.** Every rule re-probed on the build (all seven accepted at --std 85 before). Now, gated by `Edition.DialectLevel < 2002`: first LINE of a page footing must be absolute (`ScreenReportLineClauses`, COBOL2199); NEXT GROUP needs a LINE clause in the group (`BindNextGroupClauses`, COBOL2284); a SOURCE of a control footing, page heading, page footing or report footing group that names a control data item (page groups), a group holding one, an item below one, or a redefinition or renaming of part of one (`ScreenSourceControlData`, COBOL6825); format 2 entry with no clause (SR6), with no format 3 child (SR4 c) and USAGE on a format 3 entry that is not printable or a format 1 or 2 entry with no printable item below (SR8) (`ScreenReportEntryFormats`, COBOL2247). RESET level (`ScreenResetLevel`, COBOL6824) is asked at EVERY edition: 1985 refuses a RESET operand lower than the footing's own control, and 2002 and later refuse one that is not higher (2023:13.18.54.3 SR8, which the note found unenforced at 2023 too). The USE BEFORE REPORTING half of 1985:XIII.3.20.3 SR5 is not made (a walk of the declarative's statements; see the report's leads). Goldens: `pb5079-*`.

**Mechanism.** ReportSectionBinder screens a report group entry against the 2023 clause rules (its messages cite §2023:13.18.35.3, 13.15.3 and 13.18.37.3) at every edition and has no arm for the 1985 rules: the first LINE of a PAGE FOOTING group must be absolute; NEXT GROUP needs a LINE NUMBER clause in the group; RESET data-name-2 must not be a lower control than the footing's own; page heading and footing groups must not SOURCE or USE-reference control data-names; a format 2 entry needs an optional clause and a format 3 child; a USAGE clause on a format 3 entry requires a printable item (the screen does not gather USAGE at all).

**Found by.** The 1985 `--std=85` draft triage (kb/Work PB4995 item 3): each rule below is a conformance-suite draft that did not MATCH at `--std 85`, and its adjudicator decided COMPILER-DEFECT. Harm and observed text are the records'; nothing here was re-derived.

**Inventory.** The traceability inventory carries no 1985 rows yet, so `inventory_rows` is empty; the rows this note covers are the 1985 rule ids listed below (catalog `docs/rearchitecture/spec-rule-catalog-1985.json`).

**Rules (7; every citation checked with `scripts/spec/cite.py --check`).**

- `1985-SR-XIII.3.15.3-9` - `§1985:XIII.3.15.3 SR9` (record harm: under-rejects, slice-09): §1985:XIII.3.15.3 SR9: "The first LINE NUMBER clause specified within a PAGE FOOTING report group must be an absolute LINE NUMBER clause." The draft's page footing group has one LINE NUMBER clause, `LINE NUMBER IS PLUS 1`, a relative one; a syntax rule, so the program is refused. The draft reads the rule correctly, its marked line 21 holds the whole violating entry, and its control (LINE NUMBER IS 19, inside the page footing's subdivision 18 to 20) conforms.
- `1985-SR-XIII.3.16.3-1` - `§1985:XIII.3.16.3 SR1` (record harm: under-rejects, slice-09): §1985:XIII.3.16.3 SR1: "A report group entry must not contain a NEXT GROUP clause unless the description of that report group contains at least one LINE NUMBER clause." The draft's control footing group is `01 TYPE CONTROL FOOTING FINAL NEXT GROUP PLUS 1.` with one subordinate entry, a sum counter with no LINE NUMBER and no COLUMN NUMBER clause, so the group's description holds no LINE NUMBER clause; a syntax rule, so the program is refused. The draft reads the rule correctly, its marked line 16 holds the NEXT GROUP clause, and its control (the same group without the clause) conforms.
- `1985-SR-XIII.3.19.3-4` - `§1985:XIII.3.19.3 SR4` (record harm: under-rejects, slice-10): §1985:XIII.3.19.3 SR4: "Data-name-2 must not be a lower level control than the associated control for the report group in which the RESET phrase appears." The draft writes CONTROLS ARE FINAL WS-A WS-B, and §1985:XIII.3.7.4 GR1 orders them: "FINAL, if specified, is the highest control, data-name-1 is the major control, the next recurrence of data-name-1 is an intermediate control, etc. The last recurrence of data-name-1 is the minor control." So WS-B is a lower level control than WS-A, and `RESET ON WS-B` in the control footing for WS-A (line 20) is what the rule forbids. The draft reads the rule correctly and breaks no other rule; its control (RESET ON FINAL) compiles.
- `1985-SR-XIII.3.20.3-5` - `§1985:XIII.3.20.3 SR5` (record harm: under-rejects, slice-10): §1985:XIII.3.20.3 SR5, last sentence: "In page heading and page footing report groups, SOURCE clauses and USE statements must not reference control data-names." The draft's RD says CONTROL IS WS-KEY and its page heading group holds `SOURCE WS-KEY` (line 23): a SOURCE clause of a page heading report group that references a control data-name. The rule is printed (folio XIII-56, after the reconstructed folio XIII-55), so its words and its number are the standard's. The draft reads it correctly and breaks no other rule; its control (SOURCE WS-AMT) compiles.
- `1985-SR-XIII.3.9.3-4` - `§1985:XIII.3.9.3 SR4` (record harm: under-rejects, slice-10): §1985:XIII.3.9.3 SR4 c: "At least one format 3 entry must be immediately subordinate to a format 2 entry." Line 17, `02  LINE 2.`, has a level-number and a LINE NUMBER clause and no PICTURE clause; the PICTURE clause is printed in braces in format 3 (§1985:XIII.3.9.2), so the entry can only be a format 2 entry (`level-number [ data-name-1 ]` with the optional LINE NUMBER and USAGE clauses), and no entry is subordinate to it. The draft reads the rule correctly and breaks no other rule; its control (`02  LINE 2 COLUMN 1 PIC X(5) VALUE "WORLD".`, a format 3 entry) compiles.
- `1985-SR-XIII.3.9.3-6` - `§1985:XIII.3.9.3 SR6` (record harm: under-rejects, slice-10): §1985:XIII.3.9.3 SR6: "A format 2 entry must contain at least one optional clause." Format 2 (§1985:XIII.3.9.2) is `level-number [ data-name-1 ]` with the optional LINE NUMBER and USAGE clauses, so everything after the level-number is optional and the rule forbids the entry that writes none of it. The draft's `05  GRP.` is not shown to be that entry: the standard calls the data-name a clause (§1985:XIII.3.9.3 SR2: "Except for the data-name clause, which when present must immediately follow the level-number, the clauses may be written in any sequence."; §1985:XIII.3.12 is headed "THE DATA-NAME CLAUSE") and an optional one (§1985:XIII.3.9.3 SR7: "In a format 2 entry, data-name-1 is optional."), so `05  GRP.` contains one optional clause. The corrected draft writes the entry SR6 forbids on any reading, a bare level-number (`05.`, line 14) with a format 3 entry subordinate to it; its control gives the entry a LINE NUMBER clause. The compiler accepts the corrected draft (and the original), so the rule is not enforced.
- `1985-SR-XIII.3.9.3-8` - `§1985:XIII.3.9.3 SR8` (record harm: under-rejects, slice-10): §1985:XIII.3.9.3 SR8 a: "If the USAGE clause appears in a format 3 entry, that entry must define a printable item." Line 18, `05 TOT PIC 9(5) SUM WS-AMT USAGE DISPLAY.`, is a format 3 entry with no COLUMN NUMBER clause, and §1985:XIII.3.11.4 GR1 says "The absence of a COLUMN NUMBER clause indicates that the entry is not to be presented on a print line." So the entry defines a sum counter and no printable item, and its USAGE clause is forbidden. Table 1 of §1985:XIII.3.9.3 SR11 agrees: the row for PIC and SUM without COLUMN leaves the USAGE column blank, and "A blank indicates that the clause is not permitted." The draft reads the rule correctly and breaks no other rule; its control (the same entry without USAGE DISPLAY) compiles.

**Observed (copied from `1985-SR-XIII.3.9.3-6`).** cobol <file> --std 85 --source-format fixed --flag-extensions -o p.dll on the corrected draft: exit 0, no diagnostic (line 14, `05.`); its control (`05  LINE PLUS 1.` over `10  COLUMN 1 PIC X(5) VALUE "HELLO".`) compiles, exit 0. The corrected draft compiles at --std 2023 as well. ORIGINAL DRAFT (`05  GRP.`, marked line 14): exit 0, no diagnostic, which is right if the data-name clause is the optional clause SR6 asks for (see the basis) and a second instance of this defect if it is not. Code site: src/WiseOwl.Cobol.Compiler/Binding/ReportSectionBinder.cs, ScreenReportEntryClausePresence: no arm asks whether an entry below level 01 with no PICTURE clause carries any clause at all.
