# PB431 — an inline PERFORM's head is a LIST where the general format prints one bracket, and only the first element survives the bind

## 1. THE MECHANISM

The general format's loop-control slot is ONE pair of square brackets over three stacked alternatives — zero or
one of times-phrase / until-phrase / varying-phrase. The grammar spells it as a **repetition**:
`src/Cobol.Net.Frontend/Grammar/Core/CobolControlFlow.g4:39-41`

    performInlineHead
        : performOptions+
        | performLocationPhrase
        ;

so an inline PERFORM may carry any number of control phrases. The binder then reads exactly one of them —
`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:345`:

    var opt = p.performOptions() ?? p.performInlineHead()?.performOptions().FirstOrDefault();

`FirstOrDefault()` discards every phrase after the first. The discarded phrase does not merely lose effect at run
time — it never reaches the bound tree, so no later pass (VersionConformancePass included) can see it or complain
about it. The Format-3 path is worse: because Formats 2 and 3 were merged into ONE inline grammar alternative
(`CobolControlFlow.g4:18-36`), a `performInlineHead` may precede the WHEN phrases, and
`EcBinder.ExceptionPerform.cs:27-107` (`EcBindExceptionPerform`) never calls `BindPerformControl` at all — so on
that path EVERY control phrase is dropped and the body runs exactly once.

The out-of-line shape is NOT affected and that is what makes this a cardinality slip in one place rather than a
design decision: the THRU alternative spells `performOptions?` (singular, `:22`), and the three explicit
out-of-line alternatives (`:20-22`) each take exactly one phrase, so a second phrase there is a parse error.

## 4. THE CODE SITE AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Frontend/Grammar/Core/CobolControlFlow.g4:39-41` — `performInlineHead : performOptions+ | …`
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:345` — the `FirstOrDefault()`
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.ExceptionPerform.cs:27-107` — no `BindPerformControl`

⛔ **The repair is NOT "change `+` to `?`."** The merged Formats-2/3 alternative is the right structure (design
§1.4 — zero cross-format lookahead), and narrowing the grammar alone would turn today's silent deletion into a
bare `COBOL0001 no viable alternative`, which names no rule and tells a user nothing. The structural repair has
three parts and the third is the one that makes the NEXT case automatic:

1. **`performInlineHead : performOptions performOptions* | performLocationPhrase`** — keep the head a list at the
   PARSE level (superset posture, the project's standing choice for a format-cardinality violation), so the
   binder still SEES the extra phrases.
2. **One cardinality screen in the binder, over the list the grammar already builds**, emitting a NEW diagnostic
   naming §14.9.28.2 Format 2 when `performInlineHead.performOptions().Length > 1`, and naming Format 3 when a
   `performInlineHead` with `performOptions` coexists with any WHEN/OTHER/COMMON/FINALLY phrase.
3. **`BindPerformControl` and `EcBindExceptionPerform` shall share ONE control-phrase resolver.** Today the
   Format-3 path silently has no control phrase at all because it was written not to ask for one. That is the
   two-arm dispatch defect: one resolver already exists (`BindPerformControl` handles all THREE grammar shapes —
   its own doc-comment says so and cites the DEVLOG-514 defect it was written to close) and the Format-3 arm
   never calls it. Route Format 3 through it, and the diagnostic in (2) falls out of ONE `Length > 1` test rather
   than two.

## 5. THE SIBLING SWEEP

* **Every merged-alternative head.** `performLocationPhrase` is the head's other arm; a `WITH LOCATION` head on a
  Format-2 (no-WHEN) inline PERFORM is the mirror-image violation and must be screened by the same site
  (`ControlFlowBinder.IsFormat3` at `:322-326` already treats a LOCATION head as the Format-3 discriminator, so
  today it is classified rather than rejected — check what happens to `PERFORM WITH LOCATION … END-PERFORM` with
  no WHEN at all).
* **Every other `FirstOrDefault()` over a grammar repetition that the format prints as a bracket.** This is the
  generic shape: grep for `.FirstOrDefault()` and `[0]` in `src/Cobol.Net.Compiler/Binding/` where the operand
  comes from a `+`/`*` context. Each one is a place where a written operand can be silently deleted.
* **The Format-3 binder's other omissions.** `EcBindExceptionPerform` not calling `BindPerformControl` is one
  symptom; audit what ELSE the Format-2 path does that the Format-3 path skips (it runs `CheckCrossStatementBans`
  and `CheckSr14Sr15`, but the loop scaffold, the EXIT PERFORM machinery and the control phrase all come from the
  Format-2 side).
* **Edition gate sweep.** Adding a rejection at any `--std` breaks anything in the corpus that compiles a
  multi-phrase head today — run the NIST corpus and the conformance suite, not just the wave filter.
