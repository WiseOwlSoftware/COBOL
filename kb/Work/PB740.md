# PB740 — OPEN — the Table-19 arbiter says yes and the OS handle says no

Reported TWICE, from opposite sides, by two implementers who never saw each other's finding — which is why this
is one note and not two:

- `…\a9d94900…\scratchpad\reports\PB713-report.md`, "New defects (b)": *"two clause-less connectors that Table 19
  PERMITS to share a file are refused by the OS handle posture … **Not verified by execution** — deduced from the
  posture … **Probe it before filing a severity**."*
- `…\a9d94900…\scratchpad\reports\PB714-report.md`, "New defects (a)": the same divergence measured from the
  other direction (`SHARING WITH ALL OTHER` existing, clause-less incoming), plus the mirror in one parenthesis:
  *"a connector opened `SHARING WITH NO OTHER` currently gets `FileShare.ReadWrite`, i.e. LESS OS exclusion than

had not been run; the probe below is what sets it, and it sets it higher than "latent".

### Half 1 — the refused open, the exact shape the report asked for

`pb740p1.cob` — THREE clause-less `SELECT`s on one `ASSIGN TO "pb740p1.dat"`, `ORGANIZATION IS SEQUENTIAL`,
no `SHARING`, no `LOCK MODE`, only `FILE STATUS`: a seeding connector (OUTPUT / WRITE / CLOSE), then
`OPEN INPUT F-A`, then `OPEN EXTEND F-B`.

```
A-OPEN=00
B-OPEN=30        ← the defect
B-WRITE=48
$ od -c pb740p1.dat →  S E E D          (the appended record never reached the file)
```

The `'48'` on the WRITE is correct and downstream — `--check 9.1.13.7 "The execution of a WRITE statement is
attempted referencing a file connector that is not open in the correct open mode"` → **OK §9.1.13.7 8)**, the
connector never opened. `'30'` on the OPEN is the defect, and it is what makes the rest of the program
impossible.

### Half 2 — the mirror, measured cross-process rather than argued

The mirror is invisible from inside one run unit (the registry arbitrates before the OS ever sees the second
handle), so it was measured across processes: `drive.py` starts the compiled program, waits for its
`A-OPEN=00` line, and — **while the COBOL connector still holds the file open**, parked on a blocking `ACCEPT` —
has an external process try to append to it.

| probe | the COBOL connector | external writer, mid-open | external reader |
|---|---|---|---|
| `pb740p2.cob` | clause-less, `OPEN INPUT` | **REFUSED** — `PermissionError` | succeeded |
| `pb740p3.cob` | `SHARING WITH NO OTHER`, `OPEN INPUT` | **SUCCEEDED** — file ends `SEEDXXXX` | succeeded |

**Writing the most restrictive sharing mode the standard has is what let a foreign process modify the file.**
That is PB321 Part 2's finding surviving PB321's fix: PB321 removed the *in-run-unit* half by making Table 19

## The mechanism, at current line numbers on `89555b09`

1. `FileRegistry.Conflicts` — `src/Cobol.Net.Runtime/IO/FileRegistry.cs:831-844` — reports a conflict only where
   **every** candidate sharing mode gives *Unsuccessful open*:
   `if (Table19.Cell(incSharing, inc.Mode, exSharing, ex.Mode) == OpenSharingOutcome.NormalOpen) return false;`
   With both sides undetermined, `AllOtherExtendIO × AllOtherInput` is a *Normal open*
   (`Sharing/OpenTable19.cs:158`; `:137` is the READ-ONLY sibling), so the arbiter permits the open. **The
   Table-19 layer is behaving exactly as designed.**
2. Neither connector is a sharing participant, so neither is `SharedStreams`: it is set in exactly one place,
   `FileRegistry.RegisterSharing` (`FileRegistry.cs:711`, `if (_files.TryGetValue(name, out var c))
   c.SharedStreams = true;`), which the emitter calls only for a SELECT carrying a SHARING **or** LOCK MODE
   clause.
3. `SequentialConnector.OpenCore`'s four `SharedStreams ? … : …` ternaries then take the *unshared* arm —
   `SequentialConnector.cs:297` (INPUT, `new StreamReader(HostPath, …)`), `:305` (OUTPUT), `:317` (EXTEND,
   `new StreamWriter(HostPath, append: true, …)`), `:338` (I-O, the explicit
   `SharedStreams ? FileShare.ReadWrite : FileShare.Read`). The convenience constructors are `FileShare.Read`.
   F-A therefore holds a read handle that denies write sharing, and F-B's append handle asks for **Write**
   access; Windows refuses it.
4. The refusal surfaces as `IOException` and is mapped by `FileConnector.cs:409` —
   `catch (IOException) { s = FileStatusCode.PermanentError; }` — to `'30'`.

The posture is documented as deliberate at `FileConnector.cs:156`: *"An unshared connector keeps the default
exclusive-writer OS posture, byte-for-byte."* It is that sentence, not a bug in the arbiter, that produces the
wrong status — which is why this is filed rather than patched at the ternary.

## ⛔ The owner question — for the ledger's owner card (question 20)

> Should an unshared file connector keep the exclusive OS handle posture (protecting the file from other
> PROCESSES at the cost of refusing opens Table 19 permits inside the run unit), or route every connector's
> handle through the sharing posture so the Table-19 arbiter is the only gate?

It is genuinely owner-visible and not derivable: the standard's model has file connectors and run units in it,
and no foreign process at all, so §9.1.15 cannot settle what a COBOL handle should deny a non-COBOL writer.
Whichever way it goes, the mirror is a defect under both answers — an unshared connector must not end up
**more** protected than one that wrote `SHARING WITH NO OTHER`, which §9.1.15 1) calls exclusive access.

## The fix shape

**One posture register, not four ternaries.** The share mode belongs where the open mode is decided — the
registry already knows every connector's arbitrated posture at `SharedOpenAttempt` time — so the connector should
be handed the `FileShare` it must use rather than deriving one from a boolean at four call sites. That is also
PB713's shape (its report describes a `HostFile.OpenConnectorStream` / `OpenAuxiliary` split for exactly this
reason), so **PB740 and PB713 want the same structure and should land in that order or together**;
`feedback_one_mechanism_per_job`.

Two admissible postures, one owner decision (above):

1. **Arbiter-only.** Every connector's handle opens `FileShare.ReadWrite` and Table 19 is the sole gate. Fixes
   both halves; loses cross-process protection entirely, which is what the question asks about.
2. **Exclusive-by-default, derived from the arbitrated mode.** A connector opens the OS posture its *arbitrated*
   sharing mode implies — `NO OTHER` ⇒ `FileShare.None`, `READ ONLY` ⇒ `FileShare.Read`, `ALL OTHER` ⇒
   `FileShare.ReadWrite`, undetermined ⇒ the same universal-quantifier rule `Conflicts` already uses (the most
   permissive posture no candidate default forbids). This fixes the mirror *and* half 1, and it keeps external
   protection where the program actually asked for it.

⛔ Whatever is chosen, it is **not** a per-call-site edit: `RelativeConnector`, `IndexedConnector`/`KeyedConnector`
and `RecordFraming` all open host paths too, and a fourth organization must not be able to re-introduce the
divergence (CLAUDE.md rule 5 — the shape that makes the next case automatic, with a drift test that no host-path
open under `src/Cobol.Net.Runtime/IO` names its own `FileShare`).
