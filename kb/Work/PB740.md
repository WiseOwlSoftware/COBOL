# PB740 — one boolean answered §9.1.15 for both of its audiences, and got each of them backwards

Reported TWICE, from opposite sides, by two implementers who never saw each other's finding — which is why this
is one note and not two:

- `…\a9d94900…\scratchpad\reports\PB713-report.md`, "New defects (b)": *"two clause-less connectors that Table 19
  PERMITS to share a file are refused by the OS handle posture … **Not verified by execution** — deduced from the
  posture … **Probe it before filing a severity**."*
- `…\a9d94900…\scratchpad\reports\PB714-report.md`, "New defects (a)": the same divergence measured from the
  other direction (`SHARING WITH ALL OTHER` existing, clause-less incoming), plus the mirror in one parenthesis:
  *"a connector opened `SHARING WITH NO OTHER` currently gets `FileShare.ReadWrite`, i.e. LESS OS exclusion than
  an unshared one."*

**Both halves are now MEASURED, not deduced.** The PB713 half was filed without a severity precisely because it
had not been run; the probe below is what sets it, and it sets it higher than "latent".

### Half 1 — the refused open, the exact shape the report asked for

`pb740p1.cob` — THREE clause-less `SELECT`s on one `ASSIGN TO "pb740p1.dat"`, `ORGANIZATION IS SEQUENTIAL`,
no `SHARING`, no `LOCK MODE`, only `FILE STATUS`: a seeding connector (OUTPUT / WRITE / CLOSE), then
`OPEN INPUT F-A`, then `OPEN EXTEND F-B`.

```
A-OPEN=00
B-OPEN=30        ← the defect
B-WRITE=48
$ od -c pb740p1.dat →  S E E D          (the appended record never reached the file)
```

The `'48'` on the WRITE is correct and downstream — `--check 9.1.13.7 "The execution of a WRITE statement is
attempted referencing a file connector that is not open in the correct open mode"` → **OK §9.1.13.7 8)**, the
connector never opened. `'30'` on the OPEN is the defect, and it is what makes the rest of the program
impossible.

### Half 2 — the mirror, measured cross-process rather than argued

The mirror is invisible from inside one run unit (the registry arbitrates before the OS ever sees the second
handle), so it was measured across processes: `drive.py` starts the compiled program, waits for its
`A-OPEN=00` line, and — **while the COBOL connector still holds the file open**, parked on a blocking `ACCEPT` —
has an external process try to append to it.

| probe | the COBOL connector | external writer, mid-open | external reader |
|---|---|---|---|
| `pb740p2.cob` | clause-less, `OPEN INPUT` | **REFUSED** — `PermissionError` | succeeded |
| `pb740p3.cob` | `SHARING WITH NO OTHER`, `OPEN INPUT` | **SUCCEEDED** — file ends `SEEDXXXX` | succeeded |

**Writing the most restrictive sharing mode the standard has is what let a foreign process modify the file.**
That is PB321 Part 2's finding surviving PB321's fix: PB321 removed the *in-run-unit* half by making Table 19
arbitrate every connector, and the OS-posture half — the half only another process can observe — was left
exactly as it was.

## The mechanism, at current line numbers on `89555b09`

1. `FileRegistry.Conflicts` — `src/Cobol.Net.Runtime/IO/FileRegistry.cs:831-844` — reports a conflict only where
   **every** candidate sharing mode gives *Unsuccessful open*:
   `if (Table19.Cell(incSharing, inc.Mode, exSharing, ex.Mode) == OpenSharingOutcome.NormalOpen) return false;`
   With both sides undetermined, `AllOtherExtendIO × AllOtherInput` is a *Normal open*
   (`Sharing/OpenTable19.cs:158`; `:137` is the READ-ONLY sibling), so the arbiter permits the open. **The
   Table-19 layer is behaving exactly as designed.**
2. Neither connector is a sharing participant, so neither is `SharedStreams`: it is set in exactly one place,
   `FileRegistry.RegisterSharing` (`FileRegistry.cs:711`, `if (_files.TryGetValue(name, out var c))
   c.SharedStreams = true;`), which the emitter calls only for a SELECT carrying a SHARING **or** LOCK MODE
   clause.
3. `SequentialConnector.OpenCore`'s four `SharedStreams ? … : …` ternaries then take the *unshared* arm —
   `SequentialConnector.cs:297` (INPUT, `new StreamReader(HostPath, …)`), `:305` (OUTPUT), `:317` (EXTEND,
   `new StreamWriter(HostPath, append: true, …)`), `:338` (I-O, the explicit
   `SharedStreams ? FileShare.ReadWrite : FileShare.Read`). The convenience constructors are `FileShare.Read`.
   F-A therefore holds a read handle that denies write sharing, and F-B's append handle asks for **Write**
   access; Windows refuses it.
4. The refusal surfaces as `IOException` and is mapped by `FileConnector.cs:409` —
   `catch (IOException) { s = FileStatusCode.PermanentError; }` — to `'30'`.

The posture is documented as deliberate at `FileConnector.cs:156`: *"An unshared connector keeps the default
exclusive-writer OS posture, byte-for-byte."* It is that sentence, not a bug in the arbiter, that produces the
wrong status — which is why this is filed rather than patched at the ternary.

## ⛔ The owner question — for the ledger's owner card (question 20)

> Should an unshared file connector keep the exclusive OS handle posture (protecting the file from other
> PROCESSES at the cost of refusing opens Table 19 permits inside the run unit), or route every connector's
> handle through the sharing posture so the Table-19 arbiter is the only gate?

It is genuinely owner-visible and not derivable: the standard's model has file connectors and run units in it,
and no foreign process at all, so §9.1.15 cannot settle what a COBOL handle should deny a non-COBOL writer.
Whichever way it goes, the mirror is a defect under both answers — an unshared connector must not end up
**more** protected than one that wrote `SHARING WITH NO OTHER`, which §9.1.15 1) calls exclusive access.

## The fix shape

**One posture register, not four ternaries.** The share mode belongs where the open mode is decided — the
registry already knows every connector's arbitrated posture at `SharedOpenAttempt` time — so the connector should
be handed the `FileShare` it must use rather than deriving one from a boolean at four call sites. That is also
PB713's shape (its report describes a `HostFile.OpenConnectorStream` / `OpenAuxiliary` split for exactly this
reason), so **PB740 and PB713 want the same structure and should land in that order or together**;
`feedback_one_mechanism_per_job`.

Two admissible postures, one owner decision (above):

1. **Arbiter-only.** Every connector's handle opens `FileShare.ReadWrite` and Table 19 is the sole gate. Fixes
   both halves; loses cross-process protection entirely, which is what the question asks about.
2. **Exclusive-by-default, derived from the arbitrated mode.** A connector opens the OS posture its *arbitrated*
   sharing mode implies — `NO OTHER` ⇒ `FileShare.None`, `READ ONLY` ⇒ `FileShare.Read`, `ALL OTHER` ⇒
   `FileShare.ReadWrite`, undetermined ⇒ the same universal-quantifier rule `Conflicts` already uses (the most
   permissive posture no candidate default forbids). This fixes the mirror *and* half 1, and it keeps external
   protection where the program actually asked for it.

⛔ Whatever is chosen, it is **not** a per-call-site edit: `RelativeConnector`, `IndexedConnector`/`KeyedConnector`
and `RecordFraming` all open host paths too, and a fourth organization must not be able to re-introduce the
divergence (CLAUDE.md rule 5 — the shape that makes the next case automatic, with a drift test that no host-path
open under `src/Cobol.Net.Runtime/IO` names its own `FileShare`).

## Landed

**Both halves were re-probed on this worktree's own build before anything was changed, and both reproduced.**
`pb740p1.cob` answered `A-OPEN=00 / B-OPEN=30 / B-WRITE=48` with the appended record absent from the file, and
`drive.py pb740p3` had an external process append four bytes to a file a `SHARING WITH NO OTHER` connector held
open while `drive.py pb740p2`'s clause-less connector refused the same write.

**The root was not the ternary: it was that ONE fact was answering TWO of §9.1.15's questions.** The clause
reads on both audiences, and the standard is explicit that they are different — *"Multiple paths of access may
exist in the same runtime element, contained elements, separate runtime elements within the same run unit, or
runtime elements in different run units"* (`--check 9.1.15` → OK). For the paths INSIDE the run unit it names
the gate: *"Before access to a shared physical file is allowed through an OPEN statement, the sharing mode and
the open mode of that OPEN statement shall be allowed by all other file connectors that are currently associated
with the physical file, as described in … Table 19"* (OK §9.1.15). For the ones outside it names a different
mechanism: *"The successful opening of a file establishes a file lock for the applicable sharing rules, thereby
preventing other run units from opening that file with incompatible sharing rules"* (OK §9.1.15). A host share
mode can only be the second, because it names no requester: it cannot admit this run unit's second connector
while refusing a foreign process. `FileConnector.SharedStreams` — *"did this SELECT write a SHARING or LOCK MODE
clause?"* — was spent on both, and answered each backwards.

**The fix is a derivation with one home.** `IO/Sharing/FileLockPosture.cs`:

- `OfSharingMode` is §9.1.15's three rules read literally — `NO OTHER` ⇒ `FileShare.None` (*"specifies exclusive
  access to a physical file"*, OK §9.1.15 1)), `READ ONLY` ⇒ `FileShare.Read` (*"restricts concurrent access …
  to input mode"*, OK §9.1.15 2)), `ALL OTHER` ⇒ `FileShare.ReadWrite` (*"allows concurrent access … specifying
  input, I-O, or extend mode"*, OK §9.1.15 3)). The UNDETERMINED implementor default keeps today's
  `FileShare.Read` **byte for byte** — see the owner question below, which this note did NOT decide.
- `For` widens that base to admit the access of every connector Table 19 has already admitted on the physical
  file, and `FileRegistry.SyncHostPostures` re-derives the whole set whenever it changes: an OPEN widens, a
  CLOSE or a failed OPEN narrows back (§9.1.15, *"The file lock is removed by an explicit or implicit CLOSE
  statement executed for that file connector"*). A share mode is fixed when a handle is created, so "widen"
  means REBUILD — `FileConnector.Reposture` is virtual and `SequentialConnector` overrides it, reopening at the
  logical offset the connector already tracks because `StreamReader` buffers and `BaseStream.Position` is never
  the read position.
- `HostFile.OpenConnectorStream` takes the posture instead of deriving one, and `OpenAppendStream` became
  `OpenConnectorWriteStream(path, mode, share)` — serving `OPEN OUTPUT`'s `Create` as well, because Table 19
  admits an incoming EXTEND against a connector open in the OUTPUT mode — with PB739's shared-append choice now
  made on the POSTURE (`AdmitsAnotherWriter`) rather than on a clause. That last point is load-bearing rather
  than tidy: this change makes two clause-less connectors openable EXTEND on one file for the first time, and
  keying the repositioning stream on a clause would have handed exactly that pair two buffered writers anchored
  at one offset — PB739's silent record loss, in a new shape, opened by its own fix.

**Measured after:** `A-OPEN=00 / B-OPEN=00 / B-WRITE=00`, the file `SEEDBBBB`; the `SHARING WITH NO OTHER`
connector now refuses an external write AND an external read; the clause-less connector is unchanged in both
directions (write refused, read admitted).

**The widening does not spend the protection it was afraid of.** The host checks a new handle against EVERY
outstanding one, so the run unit's lock against the outside is the INTERSECTION of its connectors' postures: the
reader widened so its sibling appender could open is joined by an appender whose own posture still refuses an
outside writer, and the outside writer is still refused. `WideningForASiblingDoesNotAdmitAnOutsider_AndIsGivenBackAtTheClose`
measures that, and the give-back at the CLOSE.

**Guards.** `tests/Cobol.Net.Tests.Unit/FileLockPostureDriftTests.cs` — the whole (sharing mode × open mode)
square on both sides, 256 pairs opened through real connectors on a real physical file and checked against
`FileRegistry.Conflicts`' own verdict, so the host can never veto a cell again; the file lock measured from a
handle OUTSIDE the connector in all three modes with the clause-less arm as the control that PB740 changed
nothing there; the record-lock sentence of each rule (*"Record locks are ignored"* vs *"Record locks are in
effect"*); the reported pair end to end with the reader's file position indicator asserted across the rebuild;
and the two symbolic theorems (every *Normal open* cell has mutually admissible postures, and no DETERMINED mode
ever needs widening — the widening exists for the undetermined default alone). **Proved red on the pre-fix
posture rule: 38 of 266.**

**Goldens.** `tests/conformance/{2002,2023}/pb740_clauseless_share.{cob,out}` (`PB740S02` / `PB740SHR`), three
legs: the reported pair with the reader's position, the `SHARING WITH NO OTHER` '61' as the control that the
arbiter is untouched, and two clause-less appenders with neither record lost (counted and searched, because
§14.9.51.4 GR19 leaves only their ORDER undefined). Expected values derived from the spec before the run and
matched line for line at both editions.

**Rows.** `GR-9.1.15-1`, `GR-9.1.15-2`, `GR-9.1.15-3` GAP → **PARTIAL** (GAP unmoved) — the three sharing-mode
rules: the Table-19 arbitration, the file lock, and the record-lock sentence each rule ends with.
⛔ **NOT CONFORMS, and the correction is the registrar's ([[PB771]], found at the train-18 landing).** This
note's evidence for all three rows is SEQUENTIAL-ONLY. The RELATIVE and INDEXED organizations establish no
§9.1.15 file lock against other run units AT ALL: both keyed connectors reach the physical file only through
short-lived `RecordFraming.ReadStore`/`WriteStore` handles taken via `HostFile.OpenAuxiliary`
(`src/Cobol.Net.Runtime/IO/FileSupport.cs`), which is fixed at `FileShare.ReadWrite` and names no sharing mode
at all, and the CLOSE `WriteStore` is `FileMode.Create` — so another run unit's writes to the same physical
file are silently lost, with both sides reporting '00'. The IN-RUN-UNIT half of these rules (Table 19) IS
arbitrated for every organization and is what this note fixed; it is the OTHER-RUN-UNIT half, the lock itself,
that only the sequential organization carries. **[[PB771]] owns the keyed half**, and a CONFORMS here would
have been a verdict with a known hole — the `green_test_can_hold_a_gap_open` shape, one clause up.
`GR-14.9.27.4-4` was RE-DERIVED and re-recorded through the same batch (it was already CONFORMS, so the GAP did
not move, and it stays **PB321's** claim rather than this note's): its clause-less witness could not have seen
this defect, because both of that golden's legs hold the ACCESS axis fixed, and INPUT + EXTEND is the first cell
where the arbiter and the host can disagree. `GR-14.9.51.4-19` was re-recorded through a batch too, for the role
rename alone.

## ⛔ Still open, and deliberately not decided here

**Owner question 20 stands exactly as filed:** should a connector carrying §9.1.15's UNDETERMINED implementor
default (no SHARING clause, no LOCK MODE clause) hold an OS handle that protects its physical file from other
PROCESSES at all? Its posture is unchanged by this note — `FileShare.Read`, the value the .NET path constructors
gave — and answering it is now a one-line change in `FileLockPosture.OfSharingMode`.

**Filed, not fixed here:** the keyed and relative organizations establish NO §9.1.15 file lock against other run
units, because they hold no long-lived host handle at all (their store is loaded at OPEN and persisted at CLOSE
through `HostFile.OpenAuxiliary`). That is a property of the store model rather than of this derivation, it is
uniform across their sharing modes, and it therefore inverts nothing — which is why it is a separate finding and
not part of this mirror. `DESIGN-runtime-library.md` names it.
