# PB5867 - a comma or a semicolon separator between PICTURE and the character-string is refused (every edition)

**Ruling: UPHELD (b), harm rejects_legal_source.** A comma or a semicolon separator between PICTURE (or PIC, or PICTURE IS) and the character-string is refused: `PICTURE; 9(3)`, `PIC, 999`, `PICTURE IS, X(2)`. The lexer's picture mode skips only spaces before the string. Severity MINOR. Cause (b): wrong the same way at 2023 (the refuter ran both). The row `1985-SR-IV.4.2.1-2` does not close on its inherited verdict. It was one of eleven KEPT rows of 1985 read on a compiler built at main 1712645b47 (the Mythos lane's run wf_dabeb5ce-52d of the operator's workflow); the first read agreed, the slice-1985-230 refuter OVERTURNED it on a shape the first read did not try.

**Mechanism 1, ruled from the text.** `§1985:IV.4.2.1 SR2` says "the punctuation characters comma and semicolon, immediately followed by a space, are separators that may be used anywhere the separator space is used" (cite.py OK), and its one exception is a comma "used in a PICTURE character-string". The place between the word PICTURE and the character-string is a place where the separator space is used. A semicolon is never a PICTURE symbol, so the exception cannot reach `PICTURE; 9(3)`; and a comma followed by a space before the string is no part of the string (a string of the comma alone is no PICTURE), so it is the separator too. Everything else the refuter tried with comma and semicolon separators, across the divisions, is accepted. The source is unusual and legal.

**Where:** the lexer's picture mode: `src/WiseOwl.Cobol.Frontend/Grammar/Core/CobolLexer.g4#PICMODE` (the site the refuter's evidence names). The refuter's reading: the mode skips only `[ \n]+` before the string, so the string token captures the leading `,` or `;`; its trailing-separator trim fires only at the END of the string.
