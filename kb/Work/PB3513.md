# PB3513 — ACCEPT does not read the decimal form back

PB3505 made DISPLAY of a numeric item print GnuCOBOL 3.2.0's default decimal form (`00012.50`, `-00012.50`). ACCEPT of a
numeric item still decodes a digit window (DOC-A.1-1; ISO §14.9.1.4 GR1: the conversion between the device and the data
item is implementor-defined), so text produced by DISPLAY and fed to ACCEPT mis-reads. Precedence (CLAUDE.md rule 1): ISO
leaves it to the implementor, so GnuCOBOL's behavior decides.

## Repro (`s6.cob`, input `s6.in` = `00012.50`, `-00012.50`, `+005`, one per line)

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. S6.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 A PIC 9(5)V99.
       01 B PIC S9(5)V99.
       01 C PIC S9(3).
       PROCEDURE DIVISION.
           ACCEPT A
           ACCEPT B
           ACCEPT C
           DISPLAY A "|" B "|" C "|"
           STOP RUN.
```

| Compiler | Output |
|---|---|
| WiseOwl (origin/main after PB3505) | `00001.25\|+00000.12\|+000\|` |
| GnuCOBOL 3.2.0 | `00012.50\|-00012.00\|+000\|` |

Harm: wrong answer, silent. A program that DISPLAYs a numeric item and later ACCEPTs that text (pipelines, test drivers)
reads a value about ten times too small, and a negative sign is lost.

## Fix direction

One ACCEPT-side conversion that reads the decimal device form (decimal point or comma per DECIMAL-POINT IS COMMA, a
leading or trailing separate sign), selected by the same option as PB3505 (`--numeric-display`; under `digits` the digit
window stays). Reuse the PB3505 composition in `CobolNum.DeviceDecimal.cs` as the inverse; do not add a second spelling
of the form. Survey GnuCOBOL 3.2.0 ACCEPT for every numeric USAGE and SIGN form first (as PB3505 did for DISPLAY) and
record it in DOC-A.1-1. The function-result text widths (PB3514) share this latitude and are decided alongside.

**Sites:** src/Cobol.Net.Compiler/CodeGen/AcceptDisplayEmitter.cs (EmitAcceptDevice); src/Cobol.Net.Runtime/Values/Numeric/CobolNum.cs (ParseDisplay); src/Cobol.Net.Runtime/Values/Numeric/CobolNum.DeviceDecimal.cs; docs/CONFORMANCE.md (DOC-A.1-1); a new ACCEPT golden under wiseowl/cases with an options.json `digits` twin.

## Landed (wave 1157, 2026-10-23)

**Re-probe.** The note reproduced on the wave's own build: `00001.25|+00000.12|+000|` against GnuCOBOL 3.2.0's
`00012.50|-00012.00|+000|` for the note's `s6.cob`. The cause is one: ACCEPT's numeric arm read a digit window of the
item's size and decoded every digit character of it at the PICTURE's scale, the decimal point and the sign character
contributing nothing, which is the inverse of the pre-PB3505 DISPLAY and of nothing after it.

**The mechanism.** The ACCEPT arm now follows the same option as DISPLAY (`--numeric-display`): `decimal` (the default)
converts through `CobolNum.ParseDeviceDecimal` (`CobolNum.DeviceDecimal.cs`, beside the composition it inverts), reached
through `AcceptSource.DeviceNumeric`, which sizes the transfer (a character-form item its own size in leftmost
characters, a binary or packed item one whole record); `digits` keeps `ParseDisplay` over the digit window, byte for
byte. The rules are GnuCOBOL 3.2.0's, measured by running `cobc -x -std=default` over about 1,300 receiver and text pairs
(every usage, signed and unsigned, SIGN LEADING/TRAILING SEPARATE and over-punched, P scaling both ways, COMP-5 and
BINARY-DOUBLE, DECIMAL-POINT IS COMMA, over-long and invalid text); the new reader agrees with all of them except two
documented differences: a scaled COMP-5 DISPLAYs its unscaled integer in GnuCOBOL (PB3505's divergence; the value read is
the same) and a NATIONAL numeric item given a line longer than the item (GnuCOBOL keeps unrelated digits; WiseOwl COBOL
converts the leftmost characters, GR4 b). The determination, with the rules and the readback caveat (a signed item's
`-00012.50` reads `-00012.` because the window is the item's own size), is docs/CONFORMANCE.md DOC-A.1-1.

**Sweep.** The only emitter that reads the device into a numeric item is `AcceptDisplayEmitter.EmitAcceptDevice`; its other
arms (group, reference-modified, alphanumeric, national, boolean, float) are character stores or the float reader, which
already reads the decimal point. `NumParseDisplay`'s other callers (STRING into a windowed COMP, a CALL argument, the group
slicer) decode storage images, not the device, and are not the device form's. The differential fuzz harness never ACCEPTs.
`NumericDisplayFormDriftTests` now holds the new reader's reach too.

**Tests.** Five process-level tests in `AcceptDifferentialTests` (the note's repro under both option values, every usage,
invalid text, comma mode) and eight rows in `NumericDisplayDecimalTests` (the reader's table, the container wrap, P scaling,
the inverse property over DISPLAY's text). The suite cannot carry the golden the note named (conformance-suite programs run
with standard input closed), so the ACCEPT value pins live in the C# tests, which pipe stdin.

`closes_rows: []` stands: the note implements the PB3467 owner decision for ACCEPT and claims no inventory row.
