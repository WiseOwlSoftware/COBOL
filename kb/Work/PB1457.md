# PB1457 — LANDED

## The rule (every citation re-run by the registrar through `cite.py --check`)

> reference-modification is not permitted

`python scripts/spec/cite.py --check 8.4.3.3.3 "…"` → `OK  §8.4.3.3.3 5)  (Syntax rules)`

## Finding — `reference-modification` (under-rejects; rows `SR-8.4.3.3.3-5`)

**Mechanism.** SEARCH ALL Format-2 key operand (data-name-1 / data-name-2) is never screened for a reference modifier: SearchAllFormat2Rules.CheckKeySide resolves the written reference through refs.Probe(dref)?.Item (the base item) and checks KEY membership, SR8's index subscript and SR12, but not whether the reference as written carries a reference modifier, so the §8.4.3.3.3 SR5 NOTE ('where data-name-n is used in a general format ... reference-modification is not permitted') goes unenforced at the one Procedure-division data-name-n site the COBOLNET2024 screen does not reach

**Repro.** 01 TB. 05 T OCCURS 3 ASCENDING KEY TK INDEXED BY IX. 10 TK PIC X(3).  ...  SEARCH ALL T AT END DISPLAY "E" WHEN TK(IX)(1:2) = "AB" DISPLAY "X" END-SEARCH.  (pinned cobol.exe, --std 2023; out/probe/refmod-sr5/E3.cob) -> compiles clean, prints X. The same holds for an AND data-name-2 conjunct.

**Expected from the spec.** A compile-time error in every edition: §14.9.37.2 Format 2 prints `WHEN data-name-1 IS EQUAL TO ...` / `AND data-name-2 ...`; §14.9.37.3 SR8 adds only the index-name subscript; §8.4.3.3.3 SR5 restricts reference modification to identifiers and its NOTE says it is not permitted where data-name-n is written. §4.2.2 makes the indication mandatory.

**Observed / reasoning.** Compiles clean and executes a prefix-key search. Siblings measured refused: FILE STATUS, LINAGE, OCCURS DEPENDING ON, OCCURS KEY, SORT/MERGE KEY (COBOLNET2024), READ KEY (COBOLNET0864), START KEY (COBOLNET0862), RECORD KEY (PB481). SEARCH ALL is the one data-name-n operand that is screened by its own rule model (SearchAllFormat2Rules) rather than the KeyReference path that carries the NOTE screen.

**Code site.** src/Cobol.Net.Compiler/Binding/Validation/SearchAllFormat2Rules.cs#CheckKeySide (~:205-245)

## What the fixer owes

Route the SEARCH ALL key sides through the same KeyReference screen FILE STATUS / LINAGE / ODO / OCCURS KEY / SORT KEY (COBOLNET2024), READ KEY (0864), START KEY (0862) use — or have CheckKeySide call it — so the NOTE lives in one place. Negative golden E3 incl. the AND data-name-2 conjunct.

## Landed (wave 1033, group D)

Re-probed on a fresh build: `out/probe/refmod-sr5/E3.cob` compiled clean at --std 85 and 2023 (and the AND data-name-2 conjunct too). Fix: `DataBinder.ScreenReferenceModifier` is the reference-modifier arm of the one data-name-n screen (`ScreenDataNameShape`), split out because SEARCH ALL Format 2 is the one data-name-n operand that MUST carry a subscript (§14.9.37.3 SR8), so the subscript arm cannot be asked there. The NOTE's sentence is worded once (`ReportReferenceModified`) and `SearchAllFormat2Rules.CheckKeySide` asks the screen for data-name-1 and every AND data-name-2, reporting COBOLNET2024 (no new code). A reference-modified identifier-3 on the sending side is legal and stays so (`85/pb1457_search_all_sending_refmod_legal` prints FOUND=02). Goldens: `negative/pb1457-search-all-key-refmod`, `negative/pb1457-search-all-and-key-refmod`.

Sibling sweep (every procedure-division general format that prints data-name-n, scanned from the spec): ALLOCATE/FREE/SET ADDRESS OF are refused by §8.4.3.3.3 SR1 (COBOLNET1647) and §14.9.39.3 SR18 (COBOLNET0869) for a reference-modified operand, GENERATE does not parse one, SORT/MERGE/READ/START were already screened, SEND/RECEIVE are the documented-unsupported messaging facility. `SR-8.4.3.3.3-5` PARTIAL to CONFORMS (batch w1033d-pb1457). Found and NOT fixed (a different rule and binder): a condition-name written with a reference modifier (`IF CN (1:2)`, `SEARCH ALL ... WHEN CN (IX) (1:2)`) compiles clean; §8.4.4.2 prints only `condition-name-1` / `qualified-condition-name-with-subscripts-1` — reported as a lead.
