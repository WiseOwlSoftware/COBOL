# PB3448 — the register's `area:` values are not normalized

> ⚙ **flags:** process-only

Source: carried by the PB3263 report from PB3369 (landed). PB3369's prose ("The bar for the fix") records it: "the register's areas are not normalized today (`io`, `runtime/io`, `binder/sort`, `codegen/sort`, `binding/io`, `binder/file-io` and more), so an area rule needs a normalization or a drift test of its own". A defect recorded only in a landed note's prose is not owned, so it is filed here.

**Mechanism.** `area:` is free text per note. The planner's UNKNOWN fallback compares the exact strings, so one subsystem written five ways is five areas; any rule that binds by area (the I/O and SORT requirement is the first) silently misses notes whose spelling differs.

**Fix direction.** One normalization of `area:` (a controlled vocabulary or one canonical-family function used by `work.py check` and every consumer), with a drift test that every open note's area resolves to a known family. The implementer locates the code sites (`work.py`, the `plan_wave.py` area comparisons).

**Sites:** (from this note's own text, for the wave planner's file-set partition, kb/Work PB3263; the implementer corrects it)
- `scripts/spec/work.py` (the one normalization of `area:` and its `check` arm)
- `scripts/orchestrator/plan_wave.py` (`subsystems`, the UNKNOWN fallback's area key; `choose_model`'s `area_patterns`)
- `scripts/orchestrator/test_plan_wave.py` (the drift test that every open note's area resolves to a known family)
- `scripts/arch/r2_subsystems.py` (the R2 table's `area` values, which the vocabulary must cover)
