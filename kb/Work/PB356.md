# PB356 — FIRST and LAST answered exactly inverted

**Rows:** `GR-14.9.41.4-18`, `GR-14.9.41.4-19`. Found independently by start p2 and start p3; one line.

## The programs

`out-b1/probe/start-p2-a/p2a.cob` — indexed, ACCESS DYNAMIC, `RECORD KEY IX-PRIME PIC X(2)`,
`ALTERNATE RECORD KEY IX-ALT PIC X(2) WITH DUPLICATES`; three records written with deliberately opposite orders
(prime 01/alt CC, prime 02/alt BB, prime 03/alt AA). `OPEN INPUT`; `MOVE "BB" TO IX-ALT` +
`START IXF KEY IS EQUAL TO IX-ALT` (establishing the ALTERNATE as key of reference); then `START IXF LAST` (or
FIRST); then `READ IXF NEXT`. Observed **`AFTER-LAST PRIME=01 ALT=CC`** and **`AFTER-FIRST PRIME=03 ALT=AA`** —
both exactly inverted.

`out-b1/probe/first-refkey/STPRBD.cob` shows the continuation cost: after `START KXF FIRST`, the following
sequential READs give `S2-ID=03 ALT=AA` then `S3-ID=02 ALT=MM` — still walking the ALTERNATE ordering.

## The rule

> §14.9.41.4 GR18: If FIRST is specified, the file position indicator is set to the value of the primary key of
> the first existing logical record in the physical file and the key of reference is set to the primary key.

`--check 14.9.41.4 "the key of reference is set to the primary key"` → **OK**; GR19 says the same for LAST and
the last record. So START LAST must reposition on the PRIME ordering and reset the key of reference to the prime
key: the READ NEXT delivers PRIME=03 (and, in the FIRST variant, PRIME=01), and every subsequent sequential READ
walks in prime-key order.

## What the compiler does

`IndexedConnector.StartFirstLast` (lines 483-495) does `var seq = Ordered(_refKey);` — the key of reference left
over from the previous START or random READ — and **never assigns `_refKey = -1`**. Only `OpenCore` (line 121)
ever resets it.

**The method's XML doc states the intent explicitly and wrongly:** *position at the first/last record under the
CURRENT key of reference (the prime key after OPEN, §14.9.27 GR14)* — a real clause answering a different
question. §14.9.27.4 GR14 governs what OPEN sets, not what START FIRST/LAST sets, and §14.9.41.4 GR18/GR19
override it.

**The harm compounds.** The key of reference is also left as the alternate, so every subsequent sequential READ
walks the wrong ordering; and where the alternate carries SUPPRESS WHEN, `Ordered` additionally HIDES records
that GR18/GR19's primary-key view must include.

## The fix, and the sweep that bounds it

Set `_refKey = -1` before computing `seq` in `StartFirstLast` — and only there. `RelativeConnector.StartFirstLast`
has no key of reference and is correct as written. The sibling to check is every other `Ordered(_refKey)` caller:
`ReadSequential` (line 239) is correct, because the key of reference legitimately persists there (§14.9.30.4
GR30/GR31). A drift test that asserts the key of reference is the prime key after any START FIRST/LAST keeps the
next `Ordered(_refKey)` caller honest.

**Code site:** `IndexedConnector.cs#StartFirstLast` (the method had moved to lines 624-640 by the time it was
fixed — the note's 483-495 was written against an older tree).

## Landed — 2026-09-13

Re-probed first on today's tree and it reproduced verbatim: `AFTER-LAST PRIME=01 ALT=CC`,
`AFTER-FIRST PRIME=03 ALT=AA`, and the continuation `F2 PRIME=02` / `F3 PRIME=01` walking the alternate.

**The fix is the SHAPE, not the assignment.** The note proposed `_refKey = -1` before computing `seq`. That is
the right value but the wrong place to stop: §14.9.41.4 states the key-of-reference decision once per START
FORMAT and never as a default — GR16 for the KEY phrase, GR18/GR19's *"the key of reference is set to the primary
key"* for FIRST/LAST — so any epilogue that READS `_refKey` has no correct reading and the next START format
inherits the bug. `IndexedConnector` now completes every successful START through one
`StartSucceeded(int keyOfReference, KeyedRec found)` whose key of reference is a **required argument**;
`StartFirstLast` passes `PrimeKey` and searches `Ordered(PrimeKey)` (GR18/GR19 name the primary key twice — once
as the ordering, "in the physical file", once as the outcome) and no longer mentions `_refKey` at all. The
KEY-phrase `Start` passes `keyIndex` and lost its duplicate copy of the GR17 e) 1. FPI assignment. A new
`PrimeKey` constant replaces the bare `-1` at the key-of-reference sites. The wrong-question XML doc that cited
§14.9.27.4 GR14 is gone; that clause governs what OPEN establishes.

**Sweep.** The four sites that establish the key of reference are exactly the four the standard names:
`OpenCore` (§14.9.27.4 GR14, prime), `ReadRandom` (§14.9.30.4 GR30/GR31), `Start` (GR16) and now
`StartFirstLast` (GR18/GR19); `ReadSequential` correctly leaves it alone (§14.9.30.4 GR21 b)'s "Otherwise"),
and `InvalidateFilePosition` correctly leaves it alone (GR7 makes it undefined). `RelativeConnector` and
`SequentialConnector` have no key of reference, and `FileRegistry.StartFirstLast` dispatches all three
organizations, so there was no unfixed second arm.

**Tests.** `conformance:2002/pb356_start_first_last_indexed` — prime and alternate orderings deliberately
inverted (01/CC, 02/BB, 03/BB, 04/AA), every START preceded by a START KEY IS EQUAL that establishes the
ALTERNATE, so FIRST/LAST answering the inherited key is a different record every time; it also pins the four
following READ NEXTs in PRIME order at '00' (the duplicate BB pair would raise GR27's '02' under the alternate)
and GR18/GR19's empty-file '23'. `conformance:2023/pb356_start_first_last_suppressed` — the SUPPRESS WHEN half:
records the ALTERNATE path withholds (§12.4.5.6.4 GR6) that FIRST/LAST must still see. Both were run against
the pre-fix compiler and both fail loudly there. `unit:StartKeyOfReferenceDriftTests` holds the SHAPE — one
epilogue, the key of reference an argument of it — with a fabricated-failure proof that includes the half-fix
(FIRST/LAST corrected, the KEY phrase left inline).

(`constructs.json start-first-last-2002`, COBOLNET0900). Design: `docs/COBOLNET_FILES_DESIGN.md`, the START
