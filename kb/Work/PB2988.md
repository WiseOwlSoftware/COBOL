# PB2988 — a TYPEDEF's CAPACITY IN register is refused when the type is used twice

Found 2026-10-10 by the train 1055 review of clusters D and E (the review agent's aside "TYPEDEF DYNAMIC CAPACITY
IN used twice", probe e6). Not caused by any train 1055 cluster: the refusal is in `DynamicResolve`, which no
cluster touched. Filed by the lander, not fixed in the train, under the night-stop landing rule (land what is in
progress, no new work).

**Repro** (`E:\COBOL-coord\scratch\t1055\review-DE\e6.cob`, run on the train 1055 build at 094ba5484):

```cobol
       01 ST TYPEDEF.
          05 K PIC X.
          05 D PIC X OCCURS DYNAMIC CAPACITY IN DC.
       01 A TYPE ST.
       01 B TYPE ST.
       PROCEDURE DIVISION.
           MOVE "X" TO D OF A (1)
           MOVE "Y" TO D OF B (3)
           DISPLAY DC OF A " " DC OF B
```

```
e6.cob(7,11): error COBOL1523: CAPACITY IN 'DC' on 'D': data-name-3 is implicitly defined by the OCCURS DYNAMIC
  entry and shall not duplicate another data-name or CAPACITY register (ISO §13.18.38.3 SR30)
e6.cob(13,12): error COBOL2127: 'DC OF B': the written qualifiers do not name context of 'DC'. ...
```

With ONE `TYPE ST` entry the same program compiles and prints `0000000001`, and with two entries but no
`CAPACITY IN` phrase it compiles and runs, so the template itself is not counted: the second EXPANSION collides
with the first.

**Spec.** §13.18.38.3 SR30 (checked with `cite.py --check`): "Data-name-3 shall not be defined elsewhere in the
source element. If qualifiers are required for uniqueness, it shall be treated as though implicitly defined at the
same level as the entry containing the OCCURS clause." Data-name-3 is written ONCE, in the type declaration; each
TYPE entry reproduces that one definition (§8.4.2.2.1 rule 4 is what `DataItem.ClonedFrom` models), exactly as
`K` and `D` are reproduced under A and B and referenced `D OF A`, `D OF B`. The rule's second sentence is the case
this program is: the register is not unique, so it is qualified (`DC OF A`, `DC OF B`) through its implicit level.
The program is conforming; the refusal is wrong.

**Code site.** `src/WiseOwl.Cobol.Compiler/Binding/DataBinder.Odo.cs` `DynamicResolve`, the SR30 test at line 658:
`if (ByName.ContainsKey(capName) || _capacityRegisters.ContainsKey(capName))` refuses any second register of the
same name, and the `continue` skips `AddCapacityRegister`, so `DC OF B` then resolves to nothing (COBOL2127,
`ReferenceResolver.CapacityRegisterFor`). `_capacityRegisters` is already a name → LIST of tables (it holds the
inherited GLOBAL registers in nearest-element order, kb/Work PB1674), so the store supports several tables per name.

**Fix shape.** "Defined elsewhere" compares DEFINITIONS, not expansions: a register whose table is a clone of the
same written entry (follow `DataItem.ClonedFrom` to its root, as `DataBinder.QualifiedCandidates` does at
`DataBinder.cs` ~8385) as every table already listed under that name is the same definition, and is added beside
them; only a register from a different written entry (or an explicit data-name, the `ByName` arm) is the SR30
duplicate. Check that `DeclareUserWord(capName, DataName)` accepts the second announcement of the same word and
kind. Goldens: e6 as a positive (each register reads its own table's current capacity) and the existing COBOL1523
negatives unchanged. Sibling sweep: an index-name in a TYPEDEF's `OCCURS 3 INDEXED BY IX` used by two TYPE entries
already compiles and runs (`SET IX OF B TO 3` then `D OF B (IX OF B)`, probe
`E:\COBOL-coord\scratch\t1055\e6run\e6idx.cob`, prints `Y`), so the index-name path handles expansions and the
capacity register is the arm that does not; any other per-expansion "shall not be defined elsewhere" screen is
the sweep's remainder.

## Landed 2026-10-12 (w1069 B)

Re-probed on the wave's build (ddee217e3): e6 still drew COBOL1523 + COBOL2127. Root, as the note named:
`DataBinder.DynamicResolve`'s SR30 screen counted a TYPE / SAME AS COPY of the written entry as a second definition.
Fix: `DataItem.WrittenDefinition` (the `ClonedFrom` chain's end), and the screen refuses only when a table already
listed under the name is a copy of a DIFFERENT written entry (or the name is an explicit data-name); copies of one
written entry are listed side by side (`_capacityRegisters` was already a list per name).

Sibling arm found and fixed: `ReferenceResolver.CapacityRegisterFor` assumed "at most one register per spelling in
one element" and took the FIRST qualifier match, so the bare `DC` over two copies read A's register silently. It now
counts the registers the qualifiers reach in the nearest declaring element and reports §8.4.2.2.3 SR1 through the ONE
verdict `DataBinder.UniqueOrReportAmbiguous` (COBOL1639; `--permissive` warns and takes the first), as the new
fault `CapacityRefFault.Ambiguous`; `SetBinder.BindSetCapacity` takes the resolver's place for every non-None fault.
The index-name arm was already right (the note's e6idx probe).

Goldens: `tests/conformance/2014/pb2988_capacity_register_type_copies` (two TYPE copies, a SAME AS copy, two TYPE
copies under one group read through two qualifiers, SET Format 14 through a qualified register); negatives
`pb2988-capacity-register-copies-unqualified` (COBOL1639) and `pb2988-capacity-register-two-written-entries`
(COBOL1523 still holds for two written entries).

## Review R1-1 answered (wave 1073 A2)

The branch review (`E:\COBOL-coord\scratch\review-w1072-a2.jsonl`, R1-1) found the `--permissive` arm of the new
`CapacityRefFault.Ambiguous` unsound: the fault ladder ranks `Ambiguous` above `UnderATable`, and the arm handed back
the place `CapacityRegisterFor` had computed for the unique case, which is null when the register's table lies under
a table. So `01 ST TYPEDEF. 05 R OCCURS 2. 10 D … CAPACITY IN DC.` with two `TYPE ST` entries and a bare `MOVE DC`
drew COBOL1639 (a warning) and then the internal error COBOL2362 instead of COBOL2126. Fix: the register's
own judgment is ONE helper, `ReferenceResolver.CapacityRegisterPlaceOf(table)` (null means under a table), asked of
the uniquely named register in `CapacityRegisterFor` AND of the register the permissive disposition picks in
`CapacityPlaceOf`; a `CapacityRef` now carries a place only when its fault is `None`. Sibling arm, same shape: the
index-name resolver (`ResolveIndexName`) screened §13.7.3 SR4 (`ScreenLinkageIndex`) only for a unique candidate; a
permissive pick whose table lay in an unreferenceable LINKAGE record is now screened too (COBOL2746). (This
section first said that missing screen was why such a program failed Roslyn with CS0131; the wave 1074 review answer
below corrects the cause.) Regression tests:
`OccursDynamicGuardTests.Permissive_AmbiguousCapacityRegister_FirstUnderATable_Is2126` (two shapes),
`OccursDynamicGuardTests.Permissive_AmbiguousCapacityRegister_FirstLegal_ReadsIt` and
`IndexNameUniquenessTests.Permissive_AmbiguousIndexName_ScreensTheLinkageRecordItResolvesTo`.

## Review R1-1 of wave 1073 answered (wave 1074 A2)

The review of `c5324ec37` (`E:\COBOL-coord\scratch\review-w1073-a2.jsonl`, R1-1) found the CS0131 cause misdiagnosed.
`ResolveIndexName` reports a written reference once (`_indexRefsReported`), and SET asks about its operand twice
(classify, then bind). The second ask of an ambiguous reference returned `IndexRefOutcome.Failed` with no declaration,
so the SET receiver was the inert occurrence number `1` and the generated `1 = __set0;` failed Roslyn. Every
`--permissive` ambiguous SET of an index-name failed that way, including the legal shapes (working storage, or a
LINKAGE record that is the USING operand). Fix: the outcome no longer depends on whether the ask reports.
`DataBinder.UniqueOrReportAmbiguous` takes `report` and returns the same verdict either way, and `ResolveIndexName`
gates only the diagnostic on its report-once set. `CapacityPlaceOf` had the same shape (a probe or a repeated ask
of an ambiguous register returned null where the reporting ask returned the picked register's place) and gets the
same treatment. Regression tests:
`IndexNameUniquenessTests.Permissive_AmbiguousIndexName_SetResolvesToTheFirstDeclarationAtEveryAsk` (SET TO, SET UP
BY, a relation, a subscript; prints `THREE` and `A`),
`IndexNameUniquenessTests.Permissive_AmbiguousIndexName_InAReferenceableLinkageRecord_Compiles` and
`OccursDynamicGuardTests.Permissive_AmbiguousCapacityRegister_InSubscriptAndRefModPositions_ReadsTheFirst`.
