# PB2988 — a TYPEDEF's CAPACITY IN register is refused when the type is used twice

Found 2026-10-10 by the train 1055 review of clusters D and E (the review agent's aside "TYPEDEF DYNAMIC CAPACITY
IN used twice", probe e6). Not caused by any train 1055 cluster: the refusal is in `DynamicResolve`, which no
cluster touched. Filed by the lander, not fixed in the train, under the night-stop landing rule (land what is in
progress, no new work).

**Repro** (`E:\COBOL-coord\scratch\t1055\review-DE\e6.cob`, run on the train 1055 build at 094ba5484):

```cobol
       01 ST TYPEDEF.
          05 K PIC X.
          05 D PIC X OCCURS DYNAMIC CAPACITY IN DC.
       01 A TYPE ST.
       01 B TYPE ST.
       PROCEDURE DIVISION.
           MOVE "X" TO D OF A (1)
           MOVE "Y" TO D OF B (3)
           DISPLAY DC OF A " " DC OF B
```

```
e6.cob(7,11): error COBOLNET1523: CAPACITY IN 'DC' on 'D': data-name-3 is implicitly defined by the OCCURS DYNAMIC
  entry and shall not duplicate another data-name or CAPACITY register (ISO §13.18.38.3 SR30)
e6.cob(13,12): error COBOLNET2127: 'DC OF B': the written qualifiers do not name context of 'DC'. ...
```

With ONE `TYPE ST` entry the same program compiles and prints `0000000001`, and with two entries but no
`CAPACITY IN` phrase it compiles and runs, so the template itself is not counted: the second EXPANSION collides
with the first.

**Spec.** §13.18.38.3 SR30 (checked with `cite.py --check`): "Data-name-3 shall not be defined elsewhere in the
source element. If qualifiers are required for uniqueness, it shall be treated as though implicitly defined at the
same level as the entry containing the OCCURS clause." Data-name-3 is written ONCE, in the type declaration; each
TYPE entry reproduces that one definition (§8.4.2.2.1 rule 4 is what `DataItem.ClonedFrom` models), exactly as
`K` and `D` are reproduced under A and B and referenced `D OF A`, `D OF B`. The rule's second sentence is the case
this program is: the register is not unique, so it is qualified (`DC OF A`, `DC OF B`) through its implicit level.
The program is conforming; the refusal is wrong.

**Code site.** `src/Cobol.Net.Compiler/Binding/DataBinder.Odo.cs` `DynamicResolve`, the SR30 test at line 658:
`if (ByName.ContainsKey(capName) || _capacityRegisters.ContainsKey(capName))` refuses any second register of the
same name, and the `continue` skips `AddCapacityRegister`, so `DC OF B` then resolves to nothing (COBOLNET2127,
`ReferenceResolver.CapacityRegisterFor`). `_capacityRegisters` is already a name → LIST of tables (it holds the
inherited GLOBAL registers in nearest-element order, kb/Work PB1674), so the store supports several tables per name.

**Fix shape.** "Defined elsewhere" compares DEFINITIONS, not expansions: a register whose table is a clone of the
same written entry (follow `DataItem.ClonedFrom` to its root, as `DataBinder.QualifiedCandidates` does at
`DataBinder.cs` ~8385) as every table already listed under that name is the same definition, and is added beside
them; only a register from a different written entry (or an explicit data-name, the `ByName` arm) is the SR30
duplicate. Check that `DeclareUserWord(capName, DataName)` accepts the second announcement of the same word and
kind. Goldens: e6 as a positive (each register reads its own table's current capacity) and the existing COBOLNET1523
negatives unchanged. Sibling sweep: an index-name in a TYPEDEF's `OCCURS 3 INDEXED BY IX` used by two TYPE entries
already compiles and runs (`SET IX OF B TO 3` then `D OF B (IX OF B)`, probe
`E:\COBOL-coord\scratch\t1055\e6run\e6idx.cob`, prints `Y`), so the index-name path handles expansions and the
capacity register is the arm that does not; any other per-expansion "shall not be defined elsewhere" screen is
the sweep's remainder.
