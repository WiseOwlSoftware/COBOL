# PB812 — OPEN — the prohibited region is an interval where the rule names a reachable set

Filed 2026-09-09 by the registrar (second pass) from the **PB440 implementer's report** §12 —
`scratchpad/reports/PB440-report.md` — found in that landing's sibling sweep and deliberately not fixed there
(the site's element type changed to `PcRange` and its behaviour was left identical so the change set stayed one
mechanism). **Re-probed on this worktree's own build at `d3ba5795`, with the implementer's own two programs.**

## The measurement, with a positive control

```
$ cobol.exe mergeinv.cob --std 2023        -> exit 0, NO diagnostic
$ cobol.exe mergepos.cob --std 2023        -> error COBOLNET1572: MERGE 'M-FILE' is prohibited in the output
                                              procedure of another MERGE or the input or output procedure of a
                                              file SORT (ISO 14.9.24; COBOL-2023, Annex E.2 item 20)
```

(`registrar2/probe/mergeinv.cob`, `registrar2/probe/mergepos.cob`, copied from
`scratchpad/PB440/probe/`.) The two programs differ in one phrase: `INPUT PROCEDURE IS IN-B THRU IN-A` with
`IN-A` physically preceding `IN-B` (inverted) versus `INPUT PROCEDURE IS IN-SECT` (a single section). The MERGE
is the same statement in the same paragraph in both. **The positive control is what makes this evidence** — the
check does fire, and the inverted range is what hides the statement from it.

## The rule, quoted, with the `--check` line actually run

```
$ python scripts/spec/cite.py --check 14.9.40.4 "The range includes all statements that are executed as the result of a transfer of control in the range of the input procedure"
OK  §14.9.40.4 10)  (General rules)
    10) The input procedure may consist of any procedure needed to create the records that are to be made
        available to the sort mechanism by executing RELEASE statements. The range includes all statements that
        are executed …
```

The range is defined by **execution**, not by text position. A statement is in the range if control reaches it
from the range — including through a PERFORM out of the range and back, which no interval over the pc space can
express either.

## Expected vs observed

| | expected | observed |
|---|---|---|
| `mergeinv.cob` at `--std 2023` | COBOLNET1572 | exit 0, silent |
| `mergepos.cob` at `--std 2023` | COBOLNET1572 | COBOLNET1572 |

## Code site

`src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs` — `GateMergeInSortMergeProc`, Pass B:

```csharp
prohibited.Any(r => paraPc >= r.Start && paraPc <= r.End)
```

For `IN-B THRU IN-A` the pair is `(Start = pc(IN-B), End = pc(IN-A))` with `Start > End`, so the predicate is
false for every pc and the region is empty. `PcRange.IsEmpty` is **not** the fix — a genuinely empty range is
correctly excluded by the same test ([[PB440]] landed that reading with its own goldens).

## The fix shape (rule 5 — this is a re-design, not a predicate tweak)

A **reachability walk** over the pc space from `Range.Start`, bounded by `Range.End`, using the same
return-address model `__Dispatch` already carries — the set of paragraphs reachable from the range's entry — not
a numeric interval. That is the shape the rule has, and it is the shape that also answers the PERFORM-out-and-
back case the interval cannot express at all. It needs its own design paragraph in the deep-dive that owns
SORT/MERGE before it is written.

## Sibling sweep the fixer owes

Every other site that models a procedure RANGE as `Start..End` over pcs, not only this one. `feedback_scan_all_similar`:
the inverted `THRU` is legal COBOL everywhere a procedure-name range may be written (PERFORM, SORT/MERGE
INPUT/OUTPUT PROCEDURE, USE), so each such site has the same hole. [[PB440]] fixed the *empty* range in the
PERFORM family; this note is the *inverted* range, and the sweep is whether any third site reads the pair
arithmetically.

## Extended 2026-09-24 by REGISTRAR 14c (lane-3 batch d1-14c, pinned tree `68bbdb00f`)

ROLLBACK's §14.9.36.3 SR2 ("This statement shall not be specified in the input or output procedure of a MERGE or SORT statement" — `cite.py --check 14.9.36.3` → OK §14.9.36.3 2)) reads the SAME numeric-span predicate in GateMergeInSortMergeProc's BoundCommitRollback arm, so an inverted `INPUT PROCEDURE IS IN-B THRU IN-A` range escapes it exactly as the MERGE arm does (rb10_inverted.cob: only COBOLNET1579, no COBOLNET1690). The COMMIT twin SR-14.9.7.3-2 is recorded CONFORMS but reads the same predicate — the fix covers it. Secondary: the SR2 COBOLNET1690 carries no source location (the EditionDiagnostic built there gets only a textual `where`). Add a ROLLBACK-in-SORT-procedure negative (pb137-commit-in-sort-proc covers COMMIT only). ⚠ PB1139 (SORT SR3's procedure/declarative bans) must not inherit the span approximation either — one range model for all three verbs.

**Finding (`rollback-statement`, under-rejects; rows `SR-14.9.36.3-2`).** The SORT/MERGE procedure-range test in VersionConformancePass.GateMergeInSortMergeProc treats each input/output procedure as a NUMERIC SPAN over its pc pair. For an inverted range (procedure-name-1 physically after procedure-name-2) the span is empty, so the COMMIT/ROLLBACK SR2 arm misses statements written inside the procedure, just as the MERGE arm does. Open kb/Work PB812 owns this mechanism but lists only GR-14.9.40.4-10.

**Repro.** probe/rollback/rb10_inverted.cob at --std 2023: SORT SWK ... INPUT PROCEDURE IS IN-B THRU IN-A, with paragraph IN-A physically before IN-B and a ROLLBACK in both. The pinned cobol.exe reports only warning COBOLNET1579 (twice) and exits clean. Positive controls rb3_sort_output_section.cob and rb4_merge_output_thru.cob both draw COBOLNET1690.

**Expected from the spec.** §14.9.36.3 SR2: 'This statement shall not be specified in the input or output procedure of a MERGE or SORT statement.' A ROLLBACK in IN-B, which is procedure-name-1 of the input procedure, violates the rule and must draw COBOLNET1690, like every other SR2 case.

**Observed / reasoning.** No COBOLNET1690 is reported. The BoundCommitRollback arm (VersionConformancePass.cs ~214-221) uses the same `prohibited.Any(r => paraPc >= r.Start && paraPc <= r.End)` interval test as the COBOLNET1572 MERGE arm, and that test is PB812's defect. The COMMIT twin SR-14.9.7.3-2 is recorded CONFORMS in the inventory, but it reads the same predicate and so has the same hole. Secondary: the SR2 COBOLNET1690 carries no source location (it prints 'error COBOLNET1690: ...' with no file(line,col)), while the SR1 site does. The EditionDiagnostic built here gets only a textual 'where'. PB812's fix should widen its inventory_rows to SR-14.9.36.3-2 and SR-14.9.7.3-2 and add a ROLLBACK-in-SORT-procedure negative golden, because none exists (pb137-commit-in-sort-proc covers COMMIT only).
