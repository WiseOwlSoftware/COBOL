# PB2502

Filed by the w1033 clerk from the PB850 refuter (`E:\COBOL-coord\scratch\w1033-adj\PB850-refute.md` section 5, "A new lead outside PB850").
The refuter did not decide whether the RENAMES key is legal; either answer leaves a defect (a crash). If the adjudication finds the THRU form
legal, the fix is to implement it; if not, the fix is a compile-time refusal. The file states no severity; MINOR is the register default
and the operator may raise it (the harm is a run-time abort).

**Observed (pinned build `pin-97006f3`).** Naming a level-66 RENAMES item in RECORD KEY compiles clean, then aborts at run time:

    NotImplementedCobolFeatureException: ... indexed file '...::F': RECORD KEY missing or not locatable in the record image (ISO §12.4.5.12)

It happens with the THRU form and the alias form (no THRU), and with an edited item or a plain `PIC X(5)` item. Probes in
`E:\COBOL-coord\scratch\w1033-adj\PB850-refute\`: `rk_renames_thru.cob`, `rk_renames_alias.cob`, `rk_renames_plain.cob`,
`rk_renames_alias_plain.cob` (`probe-renames-control.txt`). The abort is raised from `KeyedIoEmitter.cs:65`.

**Spec (cite.py --check OK per the refuter).** `§13.18.45.4 GR2`: "When the THROUGH phrase is specified, data-name-1 defines an alphanumeric group
item", so a THRU alias meets `§12.4.5.12.3 2)` ("category alphanumeric or category national within a record description entry"). Two rules treat a
RENAMES entry as part of the record description entry: `§13.18.24.3 SR2` and `§13.18.45.3 SR2` (the entries "immediately follow the last data
description entry of the associated record description entry"). So the THRU-form key is plausibly legal source. The alias form (no THRU) is a
different data item over the same storage (compare PB602); its legality as a key is not decided in the file. Related: `PB850`.

# PB2502 — LANDED — a level-66 RENAMES item is a legal RECORD KEY, ALTERNATE RECORD KEY and SORT key

**Adjudication (spec; every citation here run through `cite.py --check`, OK).** Both forms are legal source. §13.18.45.4 GR2: the THROUGH alias "defines an
alphanumeric group item", so it meets §12.4.5.12.3 SR2's "category alphanumeric or category national within a record description entry" (the RENAMES entries belong
to the record description entry: §13.18.45.3 SR2). §13.18.45.4 GR1: the alias without THROUGH takes ALL the attributes of data-name-2 and occupies its storage area, so
it is a legal key exactly when data-name-2 is (an edited or numeric data-name-2 stays COBOLNET0863). The note's "legal, or an under-reject" fork therefore resolves to
"implement it".

**Root cause.** An alias rides `DataItem.Renames66`, not `Children`, and every position, width and kind reader walked `Children`. `RecordLayout.FirstOccurrenceOffsetOf`
found nothing (null) and `KeyedIoEmitter.KeyWindow` read the null as "not locatable" (the abort). `DataItem.ByteWidth` of a group alias was 0 (no PICTURE, no children),
and `ItemCategory.GroupKindsOf` answered None for a no-THROUGH alias of a group (its comment said the alias "is never asked here", which a key screen does).
**The sibling arm was broken too:** a SORT/MERGE key naming an alias was refused as COBOLNET1757 "subject to any OCCURS clause" (§14.9.40.3 SR6 b, f), because that
screen reads the same null as its OCCURS bail. One fix, at the readers: `FirstOccurrenceOffsetOf`, `OffsetInRecord` and the variable-length key walk (`ContiguousPlaceOf`)
forward an alias to `Renames.From`; `DataItem.ByteWidth` forwards a PICTURE-less no-THROUGH alias to its group; `GroupKindsOf` forwards to the renamed item.

**Witnesses.** `conformance:85/pb2502_renames_record_key` (prime THRU key, group-alias and elementary-alias alternate keys; WRITE, READ KEY IS, START, READ NEXT, statuses
22 and 10), `conformance:85/pb2502_renames_sort_key`, `conformance:negative/pb2502-record-key-alias-of-numeric` (the fix places an alias; it does not admit every alias).
Probed on the fix, not pinned: an alias key in the secondary 01 of a multi-record FD, and an alias key after a DYNAMIC LENGTH member (the PB1025 contiguous window).
