# PB408 — the GR1b enablement test is taken in the wrong runtime element, and GR1b3a is absent

**Row:** `GR-14.9.18.4-1`. GR1 a), b1, b2 and b3b CONFORM; the row diverges on **two independent mechanisms**,
both re-measured on this worktree's HEAD `cobol.exe` (base 89044aa0), not inherited from the pinned compiler.

## MECHANISM 1 — the enablement test is evaluated in the CALLEE

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.cs#EcBindRaising` closes the phrase at bind time with
`Enabled: ctx.EcState.Turn.Enabled(info.Name, null, line)` (`:212`) — **the callee's own §7.3.25 TURN state**,
frozen into the `BoundRaising`. `CodeGen/Verbs/CallEmitter.cs#EmitRaisingStage` (`:615`) then acts on that flag:
`if (!r.Enabled)` at `:630` either emits a comment and stages nothing (`:632`, nonfatal) or throws
`CobolFatalException` inside the callee (`:637`, fatal). On the other side, the activator's pickup
`CallEmitter.cs#EmitPropagationPickup` (`:251`) is gated on `ecState.Active` alone — a whole-COMPILATION-GROUP
flag — so the activator's own per-condition checking state is never consulted anywhere on the path.

The two elements genuinely differ inside ONE compilation group, which is what makes this reachable without
separate compilation: §7.3.25.4 GR6 enables checking "for the procedure division statements and procedure
division headers that follow in the compilation group" and GR8 disables it "for all procedure division
statements and procedure division headers that follow in the compilation group" — TURN is lexical over the
group, so a `>>TURN … ON` before the main and a `>>TURN … OFF` before the subprogram put the two elements in
different states in one file.

## MECHANISM 2 — GR1b3a's EC-RAISING-NOT-SPECIFIED substitution is absent

`GOBACK RAISING LAST EXCEPTION` binds at `EcBinder.cs:163` to
`new BoundRaising(null, IsLast: true, Fatal: false, Enabled: true)` — no PD-header RAISING list is consulted,
`Fatal` and `Enabled` are constants — and emits at `CallEmitter.cs:625-628` as a bare
`ExceptionState.SetPropagatingLast()`, whose runtime facade
(`src/Cobol.Net.Runtime/Exceptions/ExceptionState.cs:905`) re-stages the recorded name and fatality verbatim.
Nothing in that chain can see the containing source element's `PROCEDURE DIVISION … RAISING` list. The STATIC
sibling of the same rule **is** implemented for the `RAISING EXCEPTION exception-name-1` arm — `EcBinder.cs:203`
tests `ctx.EcState.PdRaising` and raises `COBOLNET0717` — so only the arm whose name is unknown until run time
was left out.

## THE SHAPE OF THE REPAIR

The fatal arm at `CallEmitter.cs:637` is the *same* misapplication that
`src/Cobol.Net.Runtime/Control/ProgramTable.cs#ApplyPropagationDefault` (`:181`) already documents as removed on
the runtime side: §14.6.13.1.3 rule 8's implementor latitude governs what may happen once a fatal condition
EXISTS, and GR1b stops it coming into existence in an unchecked activator at all. One rule, two arms, one
fixed — `feedback_two_arm_dispatch`.

⛔ **The structural repair, not a patch (CLAUDE.md rule 5): delete the callee-side `Enabled`/`Fatal` arms
entirely and decide at the ACTIVATOR.** The tree already owns exactly this latch one rule over —
§14.9.4.4 GR3e's EC-EXTERNAL handshake stores the CALL site's mask as the activated element's activator mask
(`ProgramTable.cs:258-259`, `ActivatorExternalMask`, `CallProgram(siteHandlesPropagation)` at `:191`/`:291`).
Generalising that one latch past EC-EXTERNAL — the activating element's per-condition checking mask, consulted
by the pickup — makes `BoundRaising.Enabled` unnecessary rather than merely relocated, and makes the next
activator-side rule automatic. Pair it with a drift test that a `BoundRaising` carries no bind-time enablement
decision at all.

For mechanism 2, `SetPropagatingLast` needs the containing element's PD-header RAISING set as an argument (the
binder has it in `ctx.EcState.PdRaising`), and the substitution must happen where the dynamic name is known.

## THE SIBLING SWEEP

1. **`EXIT PROGRAM RAISING`** — `CallEmitter.cs:604` calls the same `EmitRaisingStage`, and §14.9.14.4 GR3 sends
   EXIT PROGRAM under a caller into §14.9.18's general rules. Same fix, same probes.
2. **The METHOD arm** — `OoBinder.cs#OoBindMethodRaising` (`:1056`) funnels into the same `EcBindRaising`, so an
   `INVOKE` activator has the same wrong-element test.
3. **Functions** — `probe gr1fn/fnraise` shows the FUNCTION propagation path works today; re-probe it after the
   latch lands so the fix does not regress the arm that is right.
4. **Two GREEN tests must be re-baselined by the fix, not treated as constraints.**
   `tests/Cobol.Net.Tests.Conformance/ExceptionConditionConformanceTests.cs:585`
   (`GobackRaising_IntoUncheckedActivator_IsNotRaisedThere`) is green and its comment asserts separate
   compilation "is the only way this rule is reachable" — the three in-group probes above contradict that
   premise (`feedback_reachability_is_measured_not_deduced`). `:769`
   (`GobackRaisingLastException_PropagatesTheLastStatus`, ECT028) hard-codes `CAUGHT: EC-USER-Q\nAFTER-CALL` for
   exactly `gr1b3a/sub.cob`'s shape — a green test pinning the wrong answer
   (`feedback_green_test_can_hold_a_gap_open`). ECT028's fixture is additionally non-conforming source: its
   `GOBACK RAISING LAST EXCEPTION` sits in an ordinary nondeclarative paragraph, which §14.9.18.3 rule 5
   forbids (see [[PB410]]).
