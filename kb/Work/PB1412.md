## Finding — `expressions` (rejects-legal-source; rows `GR-8.8.2-8`)

**Mechanism.** The condition binder's boolean-operator discriminator omits the four shift tokens, so a shift-only boolean expression in IF / relation / EVALUATE is refused

**Repro.** --std 2023: 01 A PIC 1(4) VALUE B"1100". 01 F1 PIC 1 VALUE B"1". IF A B-SHIFT-L 1 = B"1000" DISPLAY "Y" ELSE DISPLAY "N". IF F1 B-SHIFT-L 1 DISPLAY "Y" ELSE DISPLAY "N". EVALUATE A B-SHIFT-L 1 WHEN B"1000" DISPLAY "EV-Y" WHEN OTHER DISPLAY "EV-N" END-EVALUATE. (out/probe/expressions/p1.cob lines 58/60, C1.cob)

**Expected from the spec.** §8.8.4.2.2 Format 2 (boolean relation) takes boolean-expression-1/-2, and §8.8.2 lists 'a boolean expression and an integer operand separated by a boolean shift operator' as a boolean expression; rule 8 gives A B-SHIFT-L 1 = 1000, so the relation is true -> Y. §8.8.4.3 SR1 is met (F1 is length 1); F1 B-SHIFT-L 1 = 0, so GR1 makes the condition false -> N. EVALUATE -> EV-Y.

**Observed / reasoning.** Relation: COBOLNET2362 'comparison operand was refused without a diagnostic ... internal error'. Simple condition: COBOLNET2318 'used as a condition, but it is a literal ...'. EVALUATE: COBOLNET2318 + COBOLNET1634. ConditionBinder.HasBoolOp (line 311) returns true only for B_AND/B_OR/B_XOR/B_NOT, so BindPrimaryBoolean / BindBoolOrValueOperand route a shift-only expression to UnwrapBareBool, which returns null because a shift suffix is present, and the operand is refused. The parse-side predicate boolExprAhead (CobolParserCoreBase.cs) and boolArgAhead DO list B_SHIFT_L/R/LC/RC, and VersionConformancePass keeps a separate HasShiftOp - two arms of one dispatch, one updated when shifts landed. COMPUTE Format 2 and shift MIXED with a B-op in a condition bind correctly (C1.cob line 9).

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#HasBoolOp (line 311), consumers BindPrimaryBoolean (line 278) and BindBoolOrValueOperand (line 289)

### `GR-8.8.2-9` — PARTIAL (adjudicator + refuter record, verbatim)

Rule 9 (cite.py --check 8.8.2 "the operation shall proceed as though the shorter operand were extended on the right by a sufficient number of boolean zeros" -> OK §8.8.2 9)) has four halves: usage-independence, shift result length = first item, positionwise combine, right zero-extension. CobolBool works over the D-B1 '0'/'1' substrate (usage erased), Combine takes max length with Bit() reading '0' past the end, Shift keeps v.Length; BoolResultLength's BoundBoolShift arm returns the operand's length. PROBES p1b.cob: S2(11) B-OR L4(0001) -> 1101 stored in PIC 1(6) as 110100; L4 B-XOR S2 -> 110100; USAGE BIT UB B-AND B -> 0100 and B-SHIFT-R 1 -> 0110; S2 B-SHIFT-L 1 into PIC 1(6) -> 100000 (shift result 2 positions, then the COMPUTE store pads). All four halves verified. test-ref empty: unit:CobolBoolTests covers the extension/positionwise halves (And_UnequalLengths_RightZeroExtends / Or_ShorterRightExtended) but no spec-derived test pins the shift-length or usage-independence halves. || REFUTED: PARTIAL — The shift operation is not built in the boolean RELATION context (§8.8.4.2.2 Format 2 takes boolean-expression-1/-2). ConditionBinder.HasBoolOp (line ~314) tests only B_AND/B_OR/B_XOR/B_NOT, so a relation whose boolean operand carries only a shift misses the boolean channel. It falls into ComparisonOperandOf, which refuses it without a diagnostic: COBOLNET2362 'internal error' on legal 2023 source. Also, the adjudicator's SHIFTLEN probe (S2=B"11" B-SHIFT-L 1 into PIC 1(6) -> 100000) could not tell the two readings apart: a 6-position extend-then-shift also gives 100000. My circular-shift probes do confirm the first-item length in COMPUTE. The positionwise, right-zero-extension and usage-independence halves hold, including USAGE BIT and USAGE NATIONAL operands.
