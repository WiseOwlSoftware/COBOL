# PB6068 - the cascade guard is keyed by file, not by statement

PB5496 stopped COBOL7081 firing on a RELEASE/RETURN whose SORT/MERGE statement was itself refused (its procedures' ranges are then
unknown). The guard `procedures.Refused.Contains(file)` skips every use of that file anywhere in the compilation group, not only
the uses inside the refused statement's own INPUT/OUTPUT PROCEDURE range. A second SORT of the same SD that is fine, with a
RELEASE written outside any input procedure of the file, goes unreported. Also noted in PB5496's own report: a statement refused
BEFORE its SD resolves keeps no file, so a RETURN of that name is still judged.

Fix: record the refused statement's candidate procedure ranges (the ones the refusal left unresolved) and skip only a use that
falls in them; keep judging every other use. Probe: two SORTs of one SD, the first refused (for example a bad key), a RELEASE in a
plain paragraph; expect COBOL7081 once.

**Sites:** `src/WiseOwl.Cobol.Compiler/Validation/VersionConformancePass.cs#GateReleaseReturnRange`, `SortMergeProcedures.Refused` (as changed: `SortMergeProcedures.Unresolved`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundTree.cs#RefusedSortMerge`, `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/SortBinder.cs#MarkRefusedSortMerge`.

**Landed.** A refused SORT/MERGE now keeps the ranges its INPUT/OUTPUT PROCEDURE phrases name (BoundRejected.RefusedSortMerge, resolved quietly by SortBinder.MarkRefusedSortMerge), and SortMergeProcedures.Of adds them to Inputs/Outputs like a bound statement's, so a RELEASE/RETURN in them is quiet and one elsewhere is COBOL7081. Only a phrase whose name resolves to no procedure leaves its (file, direction) unjudged (Unresolved). Witnesses: RefusedSortMergeReleaseReturnTests (4 new facts).
