# PB4381 - EmbeddedBlockReading.Read gives up on the whole source at the first EXEC that opens no block

**Sites:** `src/WiseOwl.Cobol.Frontend/Parsing/EmbeddedBlockReading.cs` (`EmbeddedBlockReading.Read`, `EmbeddedBlockReading.Scan`, new, replacing `Block`; `EmbeddedBlockReading.Message`, `EmbeddedBlockReading.Report`), `src/WiseOwl.Cobol.Frontend/Pipeline/Frontend.cs` (`Frontend.ParsesCleanly` and `Frontend.NewParser`, new, the one place the edition reaches a whole-group parser; `tests/WiseOwl.Cobol.Tests.Unit/EditionReadDriftTests.cs` (the Carrier row moved to `Frontend.NewParser`); `Frontend.LexAndParseOnce`, the `Read` call), `tests/WiseOwl.Cobol.Tests.Unit/RecoverySources.cs` (`RecoverySources.Accepts`, `RecoverySources.Check`), `conformance-suite/wiseowl/cases/4.2.10-Nonstandard-extensions/pb4381-exec-is-an-index-name.cob`, `src/WiseOwl.Cobol.Frontend/Parsing/ProgramText.cs` (`ProgramText.Holds`, now the one test `Read` asks of a block's tokens), `src/WiseOwl.Cobol.Frontend/Diagnostics/DiagnosticDescriptors.cs` (`DiagnosticDescriptors.COBOL5842`, new), `src/WiseOwl.Cobol.Editions/Diagnostics/DiagnosticCatalog.cs` (`DiagnosticCatalog.UnterminatedEmbeddedBlock`, new), `tests/WiseOwl.Cobol.Tests.Unit/EmbeddedPrecompilerBlockTests.cs`, `conformance-suite/wiseowl/cases/4.2.10-Nonstandard-extensions/pb4381-exec-sql-block-unterminated.cob`, `conformance-suite/wiseowl/diagnostics/pb4381-exec-sql-block-unterminated.json`, `conformance-suite/wiseowl/cases/4.2.10-Nonstandard-extensions/pb4384-exec-sql-semicolon-in-block.cob`, `conformance-suite/wiseowl/diagnostics/pb4384-exec-sql-semicolon-in-block.json`, `docs/CONFORMANCE.md` (section 3.2, item 4), `docs/rearchitecture/DESIGN-frontend-grammar.md` (section 3.9), `docs/manual/migrating.md`.

**Read at:** commit a4f54e0a4 (tip of `worktree-wf_ca25d124-0aa-10`, PR #971, in the merge queue). The file is not on main (4aff86e01) until that PR lands; verify the site there before editing.

`Read` makes each `EXEC ... END-EXEC` block one `EMBEDDED_BLOCK` token only when EVERY EXEC of the source opens a block. EXEC is no reserved word (ISO section 8.9 lists none), so a program may declare `01 EXEC PIC X.`, and the all-or-nothing rule is the by-design reading for that declared word. The same rule fires for a block left without its END-EXEC before a separator period, which is a plain fault in the SQL text, not a use of EXEC as a word. In both cases one EXEC returns an empty reading and every other, well-formed block of the source draws the generic `COBOL0001: cannot parse construct near 'SQL'` again, the message PB4341 removed (a syntax-fault message for a precompiler construct).

Repro: any source with one well-formed `EXEC SQL ... END-EXEC.` block and one `EXEC SQL ...` with no END-EXEC; the well-formed block draws COBOL0001. Independent of PB4382 and PB4383.

Fix direction: an EXEC that opens no block should be reported as itself (the unterminated block is its own diagnostic) while the blocks that do close stay one token each; only a source that declares EXEC as a data item (a declaration or reference where a word is legal) falls back to reading EXEC as a COBOL word. The implementer derives the discriminator from section 8.9 and 8.3.5 rule 3.

Grepped `kb/Work`: no open note names `EmbeddedBlockReading` (PB4341 and PB4286 are held by the PR #971 branch).

## Landed

`EmbeddedBlockReading.Scan` classifies each EXEC: a word and an END-EXEC before a separator period (ISO 8.3.5 rule 3) is a
closed block (COBOL5818); a USER-DEFINED word (SQL, CICS, DLI are reserved in no edition) and the period first is a CANDIDATE
for a block left unterminated (COBOL5842, taken through the text before the period, one token like any block); anything else is
a COBOL word, and one such EXEC still makes the whole source read as COBOL. The candidate is only that (review R1-1): a
declaration that takes a list of user-defined words (`INDEXED BY EXEC IDX.`, `SYMBOLIC CHARACTERS EXEC BEL ARE ...`) has the same
shape, so `Read` asks the parse when it finds a candidate and no certain word: `Frontend.ParsesCleanly` parses a copy of the
stream with every EXEC a COBOL word, and a clean parse means EXEC is the program's word.

**For the next implementer.** Never restore a lexical rule that calls a user word after EXEC an unterminated block: the shapes
are the same text and only the grammar tells them apart. The residual: a source that writes EXEC as an index-name and also holds a
genuinely unterminated block fails the clean parse, so its legal declaration is reported as a block too.
