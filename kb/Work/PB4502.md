# PB4502 — an output path with no directory crashed the compiler

**Found:** 2026-11-03. `cobol --std 85 nopara.cob -o /dev/null` from Git Bash printed `Unhandled exception:
System.ArgumentNullException: Value cannot be null. (Parameter 'path')` from `Path.GetFullPath`, called by
`MetadataRepositoryProvider..ctor` through `BinderDriver.Bind`, for every source; `-o NUL` did the same.

**Root cause.** Git Bash passes `/dev/null` to a native program as `NUL`. `Path.GetFullPath("NUL")` is the device path
`\\.\NUL`, and `Path.GetDirectoryName` of it is null, as it is for a volume root. `CompilerDriver.Compile` built the
default repository directory as `Path.GetDirectoryName(Path.GetFullPath(outputDll))!`, so the null went into the
search space's directory list and the provider's `Path.GetFullPath(directory)` threw. `ExpansionAssemblies.Write`
spelled the same default a second time, the same way.

**Fix (as landed).** `CompilerDriver.Options` states the output once, as METHODS (every public property of the record is
an input the compiled-program cache keys on and `CompileStateDriftTests` classifies, and these are derived, not options):
`OutputDll()` (the `-o` path, else the source with `.dll`), `OutputDirectory()` (null when the path names no file in a
directory) and `RepositoryDirectories()` (`--repository`, else the output directory: the ONE place that default is written,
read by the compilation and by each expansion's own compilation). The test-side `CompiledProgramCache` held a third copy of
the output-path rule (its own `OutputDll`/`OutputDirectory` helpers); its callers now read the two methods and the copy is gone. `Compile` refuses an output with no directory before the front end, with the new outcome
`OutputNotWritable`, which the CLI maps to exit status 73 (sysexits EX_CANTCREAT): "output path 'nul' names no file in a
directory (a device such as NUL, or a volume root): write the assembly to a file path (`cobol check-batch` checks sources
without writing one)". The manual's exit-status table carries the row, held by `tests/doc-facts/compiler-facts.json`.

**Witnesses.** `CompilerDriverTests.CompilerDriver_RefusesAnOutputWithNoDirectory` (a volume root on every host, `NUL`
on Windows); `CliParserTests.EveryCompileOutcome_HasItsSysexitsCode` (`OutputNotWritable` → 73).

**Sibling sweep.** Every `Path.GetDirectoryName(...)!` in `src/`:
- Compiler: `CompilerDriver.cs` and `ExpansionAssemblies.cs` (fixed, above); `AssemblyPackager.DeployRuntime`,
  `MetadataRepositoryProvider.OutputDirectory` and `RoslynBackend` (`outDir`) read the output path only after `Compile`
  has refused one with no directory, so their assumption now holds by construction.
- Runtime: `FileRegistry.cs` (`SyncDirectory`), `FileSupport.cs` (two `GetUnixFileMode` calls),
  `SequentialJournal.FileDirectoryOf`, `SidecarLockFiles.cs` (two). These take a user file's host path. A program
  with `ASSIGN TO "NUL"` (LINE SEQUENTIAL) was probed through OPEN OUTPUT, WRITE, CLOSE and OPEN EXTEND: every status
  was 00 and nothing threw. The remaining sites are the Unix-mode and sharing/journal paths, which a device path does not
  reach on that probe; none was reproduced.

**Branch review round 1 (w20261846a-review-r1).** R1-1 (medium): refusing only a directory-less path left every other
output the host refuses crashing: `-o /dev/null` on Linux threw UnauthorizedAccessException writing `/dev/null.g.cs`, and
an unwritable directory (`C:\Windows\System32\x.dll`, unelevated) the same. Fixed at one boundary: `Compile`'s write
phase (each expansion's assembly, then the backend's `.g.cs`, assembly and packaging) is one guarded block, and an
`IOException` or `UnauthorizedAccessException` from it is `OutputNotWritable` (exit 73) with the host's message:
"cannot write the output of '<path>': <message>". Any other exception still propagates. Witness:
`CompilerDriverTests.CompilerDriver_ReportsAnOutputTheFileSystemRefuses` (a directory where the `.g.cs` goes). R1-2 (low):
the manual's exit table is back in numeric order, and its 73 row names both causes.

**Branch review round 2 (w20261846a-review-r2).** R2-1 (medium): an expansion's own assembly is written by a nested `Compile`, whose catch made the refusal its own OutputNotWritable, and `ExpansionAssemblies.Write` then reported every failed nested result as BackendError (exit 70, the code for Roslyn refusing generated C#). `Written` now carries `Failure`, the nested compilation's Outcome, and the group's result takes it, so a refused expansion write is exit 73. R2-2 (low, taken in the same change): the handler dropped what the phase had gathered; it now keeps the expansions' warnings (which `WithdrawWarningsOf` had already removed from the group's report) and the files already written. The comments that claimed one handler covered every file, and the CLI's exit-code summary, are corrected.
