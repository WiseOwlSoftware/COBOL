# PB4502 — an output path with no directory crashed the compiler

**Found:** 2026-11-03. `cobol --std 85 nopara.cob -o /dev/null` from Git Bash printed `Unhandled exception:
System.ArgumentNullException: Value cannot be null. (Parameter 'path')` from `Path.GetFullPath`, called by
`MetadataRepositoryProvider..ctor` through `BinderDriver.Bind`, for every source; `-o NUL` did the same.

**Root cause.** Git Bash passes `/dev/null` to a native program as `NUL`. `Path.GetFullPath("NUL")` is the device path
`\\.\NUL`, and `Path.GetDirectoryName` of it is null, as it is for a volume root. `CompilerDriver.Compile` built the
default repository directory as `Path.GetDirectoryName(Path.GetFullPath(outputDll))!`, so the null went into the
search space's directory list and the provider's `Path.GetFullPath(directory)` threw. `ExpansionAssemblies.Write`
spelled the same default a second time, the same way.

**Fix (as landed).** `CompilerDriver.Options` states the output once: `OutputDll` (the `-o` path, else the source with
`.dll`), `OutputDirectory` (null when the path names no file in a directory) and `RepositoryDirectories` (`--repository`,
else the output directory: the ONE place that default is written, read by the compilation and by each expansion's own
compilation). `Compile` refuses an output with no directory before the front end, with the new outcome
`OutputNotWritable`, which the CLI maps to exit status 73 (sysexits EX_CANTCREAT): "output path 'nul' names no file in a
directory (a device such as NUL, or a volume root): write the assembly to a file path (`cobol check-batch` checks sources
without writing one)". The manual's exit-status table carries the row, held by `tests/doc-facts/compiler-facts.json`.

**Witnesses.** `CompilerDriverTests.CompilerDriver_RefusesAnOutputWithNoDirectory` (a volume root on every host, `NUL`
on Windows); `CliParserTests.EveryCompileOutcome_HasItsSysexitsCode` (`OutputNotWritable` → 73).

**Sibling sweep.** Every `Path.GetDirectoryName(...)!` in `src/`:
- Compiler: `CompilerDriver.cs` and `ExpansionAssemblies.cs` (fixed, above); `AssemblyPackager.DeployRuntime`,
  `MetadataRepositoryProvider.OutputDirectory` and `RoslynBackend` (`outDir`) read the output path only after `Compile`
  has refused one with no directory, so their assumption now holds by construction.
- Runtime: `FileRegistry.cs` (`SyncDirectory`), `FileSupport.cs` (two `GetUnixFileMode` calls),
  `SequentialJournal.FileDirectoryOf`, `SidecarLockFiles.cs` (two). These take a user file's host path. A program
  with `ASSIGN TO "NUL"` (LINE SEQUENTIAL) was probed through OPEN OUTPUT, WRITE, CLOSE and OPEN EXTEND: every status
  was 00 and nothing threw. The remaining sites are the Unix-mode and sharing/journal paths, which a device path does not
  reach on that probe; none was reproduced.
