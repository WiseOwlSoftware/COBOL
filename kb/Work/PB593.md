# PB593 — OPEN — a real clause answering a different question, copied into three places

Found by the golden-lane round-3 `dns-witness` writer; **re-derived by the lander with `cite.py --check` before
filing**. It is `a_real_clause_can_answer_a_different_question` and CLAUDE.md rule 1's inheritance failure mode in
one: the quoted sentence really is in §4.2.7, so `--check` returns OK, and the clause NUMBER was never re-derived
before it propagated.

## The two clauses, checked

```
python scripts/spec/cite.py --check 4.2.7 "Language elements that an implementor may, but need not, implement
    are listed in A.4, Optional language element list."
  -> OK  §4.2.7  (Optional language elements)

python scripts/spec/cite.py --check 4.2.5 "Language elements that depend on implementor definition to complete
    the specification of the syntax rules or general rules are listed in A.1, Implementor-defined language
    element list"
  -> OK  §4.2.5  (Implementor-defined language elements)
```

§4.2.7 is titled *Optional language elements* and its first sentence binds it to **A.4**. §4.2.5 is titled
*Implementor-defined language elements* and its first sentence binds it to **A.1**. The sentence everyone quoted
from 4.2.7 — *"An implementor shall identify in user documentation the optional language elements for which that
implementor claims support"* — is a duty about **A.4 items**, so it cannot be the ground on which an **A.1** row
is declined.

## The three sites that carry it

1. `tests/version-matrix/inventory-schema.json` → `verdicts.DOCUMENTED-NON-SUPPORT.meaning`: *"…§4.2.7 for an
   OPTIONAL element ('An implementor shall identify in user documentation the optional language elements for
   which that implementor claims support')…"*. This is the SOURCE the other two copied.
2. The `notes` field of inventory rows `DOC-A.1-127` and `DOC-A.1-206`
   (`tests/version-matrix/traceability-inventory.json`), both written by the `PB280` Q1 back-fill: *"…plus §4.2.7
   ('An implementor shall identify …', cite.py --check OK), which this verdict's own `meaning` already names as
   its second ground."* — the note says out loud that it inherited the clause from site 1.
3. `kb/Work/PB373.md` frontmatter `spec_refs: [..., "4.2.7"]`.

## Why the verdicts are nevertheless unaffected

A.1's own preamble already carries the licence on its own — *"Optional: The element may be provided at the
implementor's option."* and *"Documentation required: If the element is provided by the implementor, the
implementor's user documentation shall document the element or shall reference other documentation that fulfills
this requirement."* — and §4.2.5 is the conformance clause that governs the A.1 list. Both grounds hold; only the
NUMBER is wrong. So this is MINOR and no row is re-verdicted by it.

## The repair

Name **§4.2.5** (with A.1's preamble) wherever an A.1 item's DOCUMENTED-NON-SUPPORT ground is stated, and keep
§4.2.7 for the A.4 arm, which is the arm it actually governs. Site 1 is the one that matters: the schema's
`meaning` is what the next back-fill will copy. Sites 2 and 3 are then swept.

⚙ Worth a mechanical guard rather than a sweep: the `meaning` string names one clause per verdict-and-annex arm,
so a small check that an A.1-kind row's ground cites 4.2.5 and an A.4-kind row's cites 4.2.7 would make the next
occurrence impossible instead of merely fixed. `scripts/spec/audit_annex_a1.py` already reads both annexes and is
the natural home.
