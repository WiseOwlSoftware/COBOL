# PB347 — the predicate enforced is not the rule

**Rows:** `SR-14.9.32.3-1`, `FMT-14.9.32.2` — and, added when the sweep confirmed the same helper carried the
same two acceptances at the other two verbs, `SR-14.9.51.3-5` (WRITE) and `SR-14.9.35.3-1` (REWRITE).

## The programs

`<lane3 scratch>/out-b1/probe/sr1sub/sr1sub.cob` — `SD SRTF / 01 SRT-REC / 05 SR-KEY PIC X(3) / 05 SR-DATA
PIC X(5)`; the input procedure runs `MOVE "AAA" TO SR-KEY. MOVE "aaaaa" TO SR-DATA. RELEASE SR-DATA.` and then a
legitimate `RELEASE SRT-REC.`. `out-b1/probe/neg/neg.cob` line 26 is `RELEASE SRT-REC(1:3).`

Both compile with **zero diagnostics at every `--std`**. `sr1sub` runs and the output procedure returns TWO
records — `R=[BBBbbbbb]` and `R=[aaaaa   ]` — the second being SR-DATA's 5-byte image space-extended to the SD's
8-byte width: **a record the program never released, injected into the sorted result.** `neg.cob` generates
`CobolSort.Release("RELNEG01::SRTF", CobolString.RefMod(SRT_REC.AsImage(), (int)(1), (int)(3)))` (read in the
emitted `neg.g.cs`), releasing a 3-byte record.

## The rule

> §14.9.32.3 SR1: Record-name-1 shall be the name of a logical record in a sort-merge file description entry and
> it may be qualified.

`--check 14.9.32.3` → **OK**. SR-DATA is a 05 subordinate item, not a logical record, so the compilation group is
illegal and §4.2.2 (*An implementation shall provide a warning mechanism that optionally may be invoked by the
user at compile time to indicate violations of the general formats and the explicit syntax rules of standard
COBOL*, `--check` → **OK**) requires a compile-time indication.

For the reference-modified form, the general format writes **record-name-1**, not identifier-1, and §8.4.3.3.3
SR5 confines reference modification to identifier positions — its NOTE stating outright that *where data-name-n
is used in a general format or syntax rule, then reference-modification is not permitted* (`--check 8.4.3.3.3` →
**OK**).

## What the compiler does

`SortBinder.BindRelease` resolves record-name-1 with the general `ctx.Refs.Resolve` — which is RIGHT, because
SR1's qualification half depends on it and `RELEASE SRT-REC OF SRTF` works (`out-b1/probe/sr1qual`) — and then
asks `seqIo.FileOfRecord(record)`. `FileOfRecord` walks `record.Item` up to its top-level 01
(`while (root.Parent is { } p) root = p;`) and returns the file whose `Records` contain THAT ROOT. **So the
predicate actually enforced is *the reference lies somewhere inside an SD record*, not *the reference IS an SD
record*.** Two facts follow automatically: any subordinate item passes, and a reference-modified record passes
(the ref-mod rides on the `Place` and the root is unchanged).

The released width is then taken from the reference itself (`Model.RecordLayout.AreaWidth(record.Item)` at bind,
`OperandText.AsString(new BoundFieldOperand(rl.Record))` at emit), which is why a wrong operand silently produces
a wrong-WIDTH record instead of anything loud.

## Sweep

`FileOfRecord` is the shared record-name resolver for **WRITE** (`SequentialIoBinder.BindWrite:106`) and
**REWRITE** (`:169`) too, whose record-name-1 operands carry the same syntax rule — the same subordinate-item and
reference-modified acceptances should be expected there and were not probed in this lane. Probe both in the same
change set.

## The fix shape

`FileOfRecord` (or a new sibling) returns the file ONLY when the reference IS a `Records[]` entry with no
reference modification and no subscripting, so the next verb with a record-name-1 operand inherits the rule
instead of re-deriving it. The STAGING half — the rejection is a runtime loud rather than a bind error — is
**PB236**.

**Code sites:** `SortBinder.cs#BindRelease` (lines 222-241) · `SequentialIoBinder.cs#FileOfRecord`
(lines 244-257) · `CobolIO.g4#releaseStatement` (line 701).

## Landed

**All three verbs, one rule, one home.** `SequentialIoBinder.FileOfRecord` is DELETED. The `record-name-1`
operand rule now lives once, in the syntax-rule catalog, as
`StatementValidation.ResolveRecordName(record, refText, verb, rule, out file)` — `ResolveFile`'s shape: it
returns the owning `FileModel`, or false having reported COBOLNET1757. WRITE (§14.9.51.3 SR5), REWRITE
(§14.9.35.3 SR1) and RELEASE (§14.9.32.3 SR1) all call it, so a fourth verb naming a record inherits the rule
instead of re-deriving it.

**The predicate is IDENTITY, not containment.** `FileOfRecord` walked the reference's `DataItem` up to its
top-level 01 and asked whether THAT root was one of a file's records, so what it enforced was *the reference
lies somewhere inside a record*. `ResolveRecordName` asks whether the reference's own `Item` IS a
`FileModel.Records` entry. The upward walk survives as the message rather than the verdict — naming the record
the operand is subordinate to is the repair, and it is now the sentence the user reads:
`'SR-DATA' is subordinate to 'SRT-REC', which is the logical record of 'SRTF' — name that record, not one of
its items`.

**And record-name-1 is not an identifier, so it is not reference-modifiable.** A record-name is a user-defined
word (§8.3.2.2.25, `--check` OK); §5.2.4's operand table gives that operand type *"User-defined word, including
qualification and subscripting if needed"* (`--check 5.2.4` OK) and nothing further; §8.4.3.3.3 SR5 permits
reference modification only *"anywhere an identifier referencing a data item of class alphanumeric, boolean, or
national is permitted"* (`--check` OK), its NOTE spelling out the consequence (`--check` OK). The **printed**
RELEASE general format was rendered from the licensed PDF (page 734 = printed 704) rather than trusted from the
OCR, and it writes `record-name-1`, not `identifier-1` — the transcription is faithful here. The refusal is at
BIND and the grammar is UNCHANGED: `releaseStatement : RELEASE dataReference` and `recordName : dataReference`
stay general, because the subordinate-item half of the same rule cannot be decided by a grammar at all, and
both halves of one rule belong in one place.

**The sweep found the siblings the note predicted, and one more.** All three verbs shared the helper and all
three carried both acceptances — measured on this worktree's own build before the fix, `WRITE OR-DATA`,
`WRITE OUT-REC(1:3)`, `REWRITE IR-DATA` and `REWRITE IO-REC(1:3)` each compiled with **zero diagnostics** and
emitted `CobolFile.Write`/`Rewrite` with the wrong operand, hence the wrong record WIDTH. `WRITE OR-KEY OF
OUT-REC` — the QUALIFIED subordinate form — was silently accepted too. The extra finding was a staging one:
`WRITE WS-REC`, naming a WORKING-STORAGE 01, drew only the COBOLNET1756 **deferral warning**, which announces
the COMPILER's own gap, for what is the source's error (§14.9.51.3 SR1 leaves it no file to name). WRITE's and
REWRITE's `file is null || record is null` arm had CONFLATED two diagnoses; they are now split — an
unresolvable name already has COBOLNET1639 (§8.4.2.1) from the resolver and stays a deferral, a reference that
resolves but is not a logical record is refused at bind, per §4.2.2 ¶2.

**No diagnostic code was claimed.** COBOLNET1826–1827 were reserved and are NOT used: `StatementOperandRule`
(COBOLNET1757) is documented as *"the CODE is the identity of the MECHANISM (a bind-time operand refusal), the
MESSAGE carries the rule"*, and this is that mechanism. Its descriptor and `docs/DIAGNOSTICS.md` now name
WRITE, REWRITE and the reference-modification corollary.

**Edition posture.** Edition-INVARIANT. The sentence is written identically in 1985, 2002 and 2014, so there is
no gate and no `constructs.json` row; every negative golden carries `*> reject-at: 85 2002 2014 2023` and was
verified at all four.

**Goldens.** Seven negatives — `tests/conformance/negative/pb347-{release,write,rewrite}-subordinate-item`,
`pb347-{release,write,rewrite}-refmod-record`, `pb347-write-record-of-no-file` — each checked at four editions,
and two acceptance twins, `tests/conformance/2023/pb347_record_name_identity` and
`tests/conformance/85/pb347_record_name_identity_85`, which pin that the qualified `OF` form still binds at all
three verbs and that a SORT returns exactly the records RELEASE named (`N=003`, no injected record).

**Rows.** `SR-14.9.32.3-1` and `FMT-14.9.32.2` DIVERGES → CONFORMS; `SR-14.9.51.3-5` and `SR-14.9.35.3-1`, the
WRITE and REWRITE spellings of the same sentence, GAP → CONFORMS (added to `inventory_rows` — the fix
implements them completely and both halves of each are witnessed). GAP 2810 → 2806.

**Docs.** `docs/COBOLNET_FILES_DESIGN.md` gains §"The `record-name-1` operand — ONE rule for WRITE, REWRITE and
RELEASE"; `docs/COBOLNET_DESIGN.md`'s GLOBAL-FD sentence names the successor;
`docs/DIAGNOSTICS.md` regenerated.

**One thing in the note did NOT hold.** It said the STAGING half "is PB236". That is true for RELEASE, which
PB236 had already moved to bind time — but NOT for WRITE and REWRITE, whose refusal was still a
`BoundUnsupported` deferral. Moving them is part of this fix, not a separate one: leaving them would have
turned a silent acceptance into a run-time abort, which §4.2.2 ¶2 does not permit either.
