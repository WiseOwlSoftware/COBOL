# PB707 — OPEN — a conflict status that bypasses the one retry loop

Found 2026-09-05 by the `PB346` implementer (report §9) while enumerating every `RetryLoop` call site: five verbs
reach it; WRITE's shared arm and REWRITE's post-conflict preflight return '53'/'54' without entering it.

## The facts

§14.9.51.4 GR16 (`cite.py --check 14.9.51.4 "The RETRY phrase is used to control the behavior of the WRITE
statement for files opened for file sharing"` → OK 16)) scopes RETRY on WRITE to "the case where resources needed to
write a record are locked by another run unit", which cannot arise in this single-run-unit model — so `WriteShared`'s
own summary is correctly reasoned and cited, and this is not a divergence. But §9.1.13.8 (`--check 9.1.13.8
"record operation conflict"` → OK) makes '53' (run-unit lock maximum) and '54' (connector lock maximum) record
operation conflict conditions, and §14.7.9.3 GR4 engages on any such condition; `ExhaustionStatus` returns a
non-`RecordLocked` conflict unchanged under every form, so routing them through `RetryLoop` is behaviour-identical
and puts the rule in the one place it is written. **Repro:** a sharing-active connector holding fifteen record
locks executing `WRITE R WITH LOCK RETRY 3 TIMES` — '54' returned on the first preflight, `RetryLoop` never entered.

## Fix

Route `WriteShared`'s preflight and `RewriteShared`'s post-conflict preflight through `RetryLoop` (the arguments are
already there and discarded), delete the `_ = retryKind` discards, and add the '53'/'54' rows to
`RetryLoop_LandsTheConflictsOwnStatus_ByClass` so the loop is proven to pass them through unchanged. Small; pairs
with the D8 no-restatement rule PB346 wrote.

## Registrar verification 2026-09-06 — the four clauses re-derived, and why they point opposite ways

Train 14's lander re-collected this from the [[PB346]] implementer report (§9); already registered here, so
nothing new was filed (CLAUDE.md rule 8). Verified against main at `0db46983` — the code is unchanged,
`src/Cobol.Net.Runtime/IO/FileRegistry.cs:1055` still reads `_ = retryKind; _ = retryAmount;`, and `RewriteShared`
(`:1076`) still DOES pass both on to its pre-operation conflict check, so the two arms of one file disagree. That
asymmetry is the shape.

**All four clauses `--check`ed fresh rather than inherited** (rule 1 — the failure mode is inheriting, and this
note's argument stands on all four at once):

- `--check 12.4.5.9 "lock"` → **OK §12.4.5.9 (LOCK MODE clause)**. GR7 verbatim: *"The implementor shall specify
  the maximum number of record locks that may be held by a file connector; that maximum shall be at least 15. The
  implementor shall specify the maximum number of record locks that may be held by a run unit; that maximum shall
  be at least 255. **Any I-O statement that attempts to obtain a record lock that would exceed either limit is
  unsuccessful and receives an I-O status that indicates that condition.**"*
- `--check 9.1.13.8 "lock"` → **OK §9.1.13.8 1)**. The clause's own heading is **"Record operation conflict
  condition with unsuccessful completion"**, and items 3) and 4) are '53' (*"this run unit holds the maximum number
  of locks allowed by this implementation"*) and '54' (*"this file connector holds the maximum number of locks"*).
  So the two statuses `PreflightNewLock` returns ARE record operation conflict conditions **by the clause that
  defines them** — this note's premise, confirmed from the definition rather than from the first digit.
- `--check 14.7.9.3 "record operation conflict"` → **OK §14.7.9.3 4)** — *"If the I/O operation is unsuccessful on
  the first attempt because of a file sharing conflict condition or a record operation conflict condition, the
  following apply:"*. GR4 therefore engages on '53'/'54' on its face.
- `--check 14.9.51.4 "The RETRY phrase is used to control the behavior of the WRITE statement for files opened for
  file sharing"` → **OK §14.9.51.4 16)**, whose sentence continues *"…for the case where resources needed to write
  a record are locked by **another run unit**"* — which cannot arise in a single-run-unit model.

**The two readings genuinely point opposite ways, and that is why this stays a shape finding and not a
divergence:** §14.7.9.3 GR4 says route it through the retry machinery; §14.9.51.4 GR16 scopes WRITE's RETRY to a
case this process model cannot produce. `RetryLoop`'s `ExhaustionStatus` returns a non-`RecordLocked` conflict
unchanged under every form, so the routing is behaviour-identical — the fix is about which clause the code is
written under. Nothing here changes the note's severity or its `process_only` disposition.
