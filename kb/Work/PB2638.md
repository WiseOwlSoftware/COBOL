**Rule it breaks:** ISO §14.7.4.3 GR3-GR10 (the arithmetic value is rounded to the nearest value that can be represented in the resultant identifier; GR7 PROHIBITED raises EC-SIZE-TRUNCATION and leaves the receiver unchanged) and §14.7.5 no-phrase rule 4 (EC-SIZE-TRUNCATION for a result further from zero than the resultant item permits); sibling arms agree (dimensions.md dimension 2, feedback_two_arm_dispatch)

**Scenario:** 01 FE PIC +9.99E+99. COMPUTE FE ROUNDED = 2 / 3 stores +6.66E-01 where GR4 owes +6.67E-01 (the representable values of FE are 3-digit significands, so the nearest one is 6.67E-01); ROUNDED MODE IS TOWARD-GREATER, AWAY-FROM-ZERO and NEAREST-EVEN are likewise all truncation. COMPUTE FE ROUNDED MODE IS PROHIBITED = 2 / 3 ON SIZE ERROR ... NOT ON SIZE ERROR ... stores the truncated +6.66E-01 and runs NOT ON SIZE ERROR where GR7 owes the size error with FE unchanged. Cause: CobolEdit.TryFormatFloat / FormatFloatCore take no rounding mode and truncate by BigInteger.Divide; ArithmeticEmitter.StoreArith's float-edited arm drops its mode parameter (comment: ROUNDED has no fixed scale to round to) and excludes the receiver from the one r7 gate (comment: not this gate's to answer), so nobody answers it. The same arm writes EC-SIZE-OVERFLOW into the EC name on failure (ArithmeticEmitter.cs:453) while the numeric-edited, locale-edited, float and plain arms (480, 517, 547, 578) write EC-SIZE-TRUNCATION, so a USE AFTER EC-SIZE-TRUNCATION declarative or FUNCTION EXCEPTION-STATUS sees the wrong level-3 name. Truncation is correct for MOVE only (§14.6.8.4 GR2), which is the one disposition the code implements.
