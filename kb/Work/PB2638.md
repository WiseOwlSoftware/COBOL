COMPUTE FE ROUNDED MODE IS PROHIBITED = 2 / 3 ON SIZE ERROR ... NOT ON SIZE ERROR ... stores the truncated +6.66E-01 and runs NOT ON SIZE ERROR where GR7 owes the size error with FE unchanged. Cause: CobolEdit.TryFormatFloat / FormatFloatCore take no rounding mode and truncate by BigInteger.Divide; ArithmeticEmitter.StoreArith's float-edited arm drops its mode parameter (comment: ROUNDED has no fixed scale to round to) and excludes the receiver from the one r7 gate (comment: not this gate's to answer), so nobody answers it. Truncation is correct for MOVE only (§14.6.8.4 GR2), which is the one disposition the code implements.

## Landing

**Landed 2026-10-08 (wave 1042 H).** Re-probed on a fresh build, `FE PIC +9.99E+99`: `COMPUTE FE ROUNDED = 2 / 3` gave
`+6.66E-01`, `ROUNDED = C` (C = 1.235) `+1.23E+00`, AWAY-FROM-ZERO and TOWARD-GREATER `+1.23E+00` for 1.234, and
`ROUNDED MODE IS PROHIBITED = A` (A = 1.234) ran NOT ON SIZE ERROR; all as the note measured. Fix: `FormatFloatCore`
takes the landing's `CobolRounding` and rounds the dropped digits through the one `CobolNum.RoundDiv` kernel (the SIGNED
value, so TOWARD-GREATER / TOWARD-LESSER see the sign), renormalizes a carry out of the last digit (`9.996` into
`+9.99E+99` is `+1.00E+01`) and tests the exponent AFTER the carry (§14.7.5 case 3 "after … any applicable rounding
specifications"; a significand rounding past `+9.99E+9` is the size error, the same value truncated is not), and reports
PROHIBITED-with-a-nonzero-tail as `FloatStoreOutcome.Inexact` (§14.7.4.3 rule 7), which `TryFormatFloat` turns into
the size error with the receiver unchanged. `FormatFloatMove` is renamed `FormatFloatStore(…, CobolRounding mode, …)`
and `TryFormatFloat(…, out image, CobolRounding mode, …)` takes the mode: the CALLER names the landing (a MOVE passes
TRUNCATION through `RuntimeApi.EditFormatFor`; `ArithmeticEmitter.StoreArith`'s float-edited arm passes the receiver's
mode through the new `RuntimeApi.EditFormatFloat` / `EditTryFormatFloat`), no default and no forwarder. The same arm
now latches EC-SIZE-TRUNCATION, like the numeric-edited, locale-edited, float and plain arms (it wrote EC-SIZE-OVERFLOW).
The unchecked no-phrase store rounds by the mode and lands PROHIBITED truncated (DOC-A.1-70), as every unchecked
store does. The note's own scenario text `PROHIBITED = 2 / 3` already raised (DivideOrThrow), as its measurement said.
Pinned by `CobolEditFloatRoundingTests` (every mode, tie and sign, the carry, PROHIBITED, the exponent after the
carry, the `CobolDec` and `double` carriers) and the golden `2023/pb2638_float_edited_rounded_store` (14 cases, every
image derived by hand from §14.7.4.3 before the run, plus the EC-SIZE-TRUNCATION name under `>>TURN EC-SIZE CHECKING
ON`).

Sibling arms: `StoreArith` is the only arithmetic store (every ADD/SUBTRACT/MULTIPLY/DIVIDE/COMPUTE/CORRESPONDING/SET
caller goes through it), and its four receiver arms (float-edited, locale, numeric-edited, plain/float) now agree on
the mode, the PROHIBITED test and the EC name. Found in the same area and fixed (I9): a float-edited receiver's OUTERMOST
quotient was formed at the mask's working-scale hint plus 14 guard digits, truncated, so `COMPUTE FE ROUNDED = 1 / D`
(D = 3E24) into `+9.99E+99` stored `+0.00E+00` and a rounding tie could never see its tail; `NumericRenderer.Divide`
now forms it on the SDIDI by round-to-odd (`_outermost && _rcv.FloatEdited`, the form an exact wide operand's quotient
already takes), golden case 15 (`+3.33E-25`). Not fixed, a lead for the register: statements with SEVERAL receivers
build their `ReceiverContext` without `FloatEdited` (`ArithmeticEmitter.cs` EmitGiving / multi-target COMPUTE /
MULTIPLY / DIVIDE), so a float-edited receiver among them still gets the scale-hint quotient. Docs: `CONFORMANCE.md` (the float-edited disposition paragraph), `COBOLNET_DATA_MODEL_DESIGN.md` (D21
entry points and the rounding step), `ReceiverContext.cs` comments. Inventory: see PB2639's note (one batch).
