# PB406 — a defective cross-reference in the standard, and the rule it really points at is gated on the wrong element

This note is two things at once, and both are needed to explain why `GR-14.9.14.4-3` is DIVERGES. Part 1 is a
defect in the STANDARD that must not be "repaired" in `specs/ISO_COBOL.md` and must not be implemented
literally. Part 2 is a measured divergence in the compiler that only becomes visible once part 1 is resolved.

## 1. The standard's own cross-reference is defective

14.9.14.4 GR3 governs an EXIT PROGRAM executed in a program that IS under the control of a calling runtime
element, and sends the reader onward:

    python scripts/spec/cite.py --check 14.9.14.4 "If an EXIT PROGRAM statement is executed in a program that is under the control of a calling runtime element, execution proceeds as specified in 14.9.18, GOBACK statement, General rules 3 and 4"
      -> OK  §14.9.14.4 3)  (General rules)

The two rules it names are not the rules meant. In 14.9.18.4:

    python scripts/spec/cite.py --check 14.9.18.4 "If a GOBACK statement is executed in a program that is not under the control of a calling runtime element, the program operates as if executing a STOP statement"
      -> OK  §14.9.18.4 3)  (General rules)
    python scripts/spec/cite.py --check 14.9.18.4 "The execution of a GOBACK statement within a method causes the executing method to terminate"
      -> OK  §14.9.18.4 4)  (General rules)

So the third general rule is the **not**-under-control case and the fourth is the within-a-method case, and
neither can apply to a statement whose own condition is *under* the control of a calling element. Taken
literally, a called-program EXIT PROGRAM would stop the run unit, which contradicts 14.9.14.1 and contradicts
the condition split of the GOBACK rules themselves — the under-control case would be left with no rule at all.

    python scripts/spec/cite.py --check 14.9.14.1 "The EXIT PROGRAM statement marks the logical end of a called program"
      -> OK  §14.9.14.1   (General)

The rules that DO match GR3's stated condition are the first and second:

    python scripts/spec/cite.py --check 14.9.18.4 "If a GOBACK statement is executed in a program that is under the control of a calling runtime element, execution proceeds as follows"
      -> OK  §14.9.18.4 1)  (General rules)
    python scripts/spec/cite.py --check 14.9.18.4 "The execution of an GOBACK statement causes the executing program to terminate, and control to return to the calling statement"
      -> OK  §14.9.18.4 2)  (General rules)

The first opens with word-for-word the condition of 14.9.14.4 GR3; the second supplies the termination, the
header RETURNING result and the INITIAL implicit CANCEL. **This is not a transcription defect** — the b2
adjudicator verified the printed page against the canonical PDF and the standard itself prints the wrong
ordinals — so `specs/ISO_COBOL.md` must be left exactly as it is. Recorded here so the next adjudicator of
this clause does not read the literal text as authority and open a false divergence against a conforming
implementation.

Three legs of the intended reading were measured and all three hold on this tree: RAISING propagation
(`conformance-test:ExceptionConditionConformanceTests.ExitProgramRaising_InCalledProgram_Propagates`), the
header RETURNING value (probe `gr3-returning`, `R=0042`), and the INITIAL implicit CANCEL (probe
`gr3-initial-cancel`, `N=1` on both activations).

## 2. But the intended reading imports GOBACK GR1 b), and its gate is on the wrong element

    python scripts/spec/cite.py --check 14.9.18.4 "an exception condition is raised in the activating runtime element if checking for that exception condition is enabled in the activating runtime element"
      -> OK  §14.9.18.4 1) b)  (General rules)

The gate is explicit and singular: the raise happens in the ACTIVATOR, and the test is whether checking is
enabled **in the activating runtime element**. The compiler tests the other one.
`CallEmitter.EmitRaisingStage` (`src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs:615-647`) keys on
`r.Enabled` — the `>>TURN` state baked in at bind time **in the RAISING (called) program**, computed at
`EcBinder.cs:211` from `ctx.EcState.Turn.Enabled(info.Name, null, line)` — and its own doc-comment says so.
When that is off and the name is nonfatal it stages nothing at all (`CallEmitter.cs:630-636`). The activator's
enabling state, the only one GR1 b) names, is never consulted at the staging end.

The result is a legal program whose activator has checking enabled and a matching USE declarative, and whose
handler silently never runs.

**The interpretive alternative, recorded so a fix-time reader can re-adjudicate rather than inherit this.** One
could argue from 14.6.13.1.1 that the called element's own disabled state suppresses the raise at its source:

    python scripts/spec/cite.py --check 14.6.13.1.1 "if checking for an exception condition is not enabled"
      -> OK  §14.6.13.1.1   (General)

That reading is rejected here because GR1 b) is the SPECIFIC rule for this statement, it localises the raise to
the activator, and it names the activator's state as the sole test — under the compiler's reading GR1 b)'s
qualifying clause would have nothing left to do. **Even if the alternative were adopted the row could not stand
at CONFORMS**, because the enabling-locus edge was simply never measured until this batch.

## 3. Expected vs observed — RE-MEASURED ON HEAD (89044aa0)

`gr3-actvon-suboff.cob` is two source elements in one file. The ACTIVATOR opens with
`>>TURN EC-USER-Z CHECKING ON`, has a DECLARATIVES section with `USE AFTER EXCEPTION CONDITION EC-USER-Z`
displaying `CAUGHT: ` and the exception status, and calls the subprogram. The SUBPROGRAM is preceded by
`>>TURN EC-USER-Z CHECKING OFF`, has `PROCEDURE DIVISION RAISING EC-USER-Z`, and ends with
`EXIT PROGRAM RAISING EXCEPTION EC-USER-Z.`

    $ cobol.exe gr3-actvon-suboff.cob --std 2023 --run
      AFTER-CALL                                                                                  [exit 0]

    $ cobol.exe gr3-ctrl-bothon.cob --std 2023 --run      # the control: no >>TURN ... OFF before the subprogram
      CAUGHT: EC-USER-Z
      AFTER-CALL                                                                                  [exit 0]

Expected for the first program: GR1 b)'s test is the ACTIVATOR's state, which is ON, so the condition is raised
in the activator, its USE declarative runs, and the output is `CAUGHT: EC-USER-Z` then `AFTER-CALL`. Observed:
the handler never runs. The control proves the whole path works when both elements have checking on — which is
**exactly the configuration in which this gate is invisible**, and is the configuration all three of the
adjudicator's original legs used. The axis the subject held fixed had to be flipped before the defect appeared.

## 4. The code site and the shape of the repair

- `src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs:615-647` — `EmitRaisingStage`, keyed on `r.Enabled`.
- `src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs:630-636` — the not-enabled arm that stages nothing for a
  nonfatal name, and terminates loudly for a fatal one.
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.cs:210-213` — where `Enabled` is baked in from the
  RAISING element's own `>>TURN` state (the `Enabled:` argument at `:211`).
- `src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs#EmitExitProgram` (`:594-607`) — the caller, and the
  conforming implementation of parts 1 and 3 of the intended reading.

**The repair is not "read the caller's TURN state at bind time" — the caller is not known at bind time**, and
in a separately-compiled run unit it cannot be. The staging side must become unconditional for the nonfatal
case (stage the condition; the ACTIVATOR's pickup decides whether to raise it), and the enabling test must move
to the pickup, where the activator's own compiled-in `>>TURN` state already lives. That is a one-directional
move — a decision currently taken in the wrong element, relocated to the only element that can take it — and it
makes the separately-compiled case automatic instead of a second mechanism. The fatal arm's
14.6.13.1.3 #8 implementor choice is unaffected and should keep its current documented behaviour.

## 5. The sibling sweep the fixer must do

- **GOBACK RAISING shares `EmitRaisingStage`** (`CallEmitter.cs:580`), so the identical gate applies to
  `GR-14.9.18.4-1` and must be measured with the same activator-on/sub-off shape before either row moves.
- **`EcEmitRaise`** is the sibling the doc-comment names as mirroring this logic; the bare RAISE statement
  raises in its OWN element, so its use of the bind-time TURN state is probably right — confirm rather than
  assume, because "probably right" is what left this one unmeasured.
- **The `ProgramRegistry` boundary default** for an EC-free caller is the other consumer of the staged
  condition; a nonfatal condition that is now always staged must still be discarded there rather than surfacing.
- **Every other place a `>>TURN` decision crosses a program boundary** — CALL's own exception handling, the
  EC-OO object leg (which correctly has no Enabled/Fatal logic at all, `CallEmitter.cs:619-624`, because
  objects are not TURN-gated). The object leg is the shape the name leg should converge on.
- The three legs already measured green (RAISING propagation, header RETURNING, INITIAL implicit CANCEL) must
  stay green: they are the evidence that parts 1 and 3 of GR3's intended reading are implemented whole.

## 6. Rows

- **`GR-14.9.14.4-3`** (DIVERGES) — the verdict rests on the enabling-locus measurement above, given on the
  only coherent reading of a defective cross-reference. The row's `test-ref` is
  `conformance-test:ExceptionConditionConformanceTests.ExitProgramRaising_InCalledProgram_Propagates`, which
  exercises the both-enabled configuration and therefore cannot see this. What would move the row: a
  `tests/conformance/<edition>/` golden of the `gr3-actvon-suboff` shape, plus the sub-on/activator-off
  complement, so the enabling locus is asserted in both directions rather than held fixed.
- GOBACK GR1 a) (a non-COBOL activator) is implementor-defined and out of scope for this row.
