# PB5937 - every SET ... TO LOCALE leaves an entry in the run unit's slot-image table for the life of the run unit

**Sites:** `src/WiseOwl.Cobol.Runtime/Control/PointerImage.cs#AreaBase` (line 265, `s_areaBases` at line 75, `NoteIdentity` at line 270),
`src/WiseOwl.Cobol.Runtime/Control/SlotImageTable.cs#Note`, `src/WiseOwl.Cobol.Runtime/*/LocaleState.cs#Save` (line 271) and
`SavedLocalePointer` (line 335), `CobolPtr.cs` (the slot write that images every store, line 344 per the lead).

**The lead (PB5928 review round 2, R2-1, low, performance).** PB5928's fix (the weak path deleted, ruling by MEANING: an image a program can write
and read back must resolve for as long as the thing it names lives; GR26 says the SET "saved and a reference to the saved locale is placed into the
pointer data item", §2023:14.9.39.4 GR26) made every addressless data-pointer value an `Identity` that "never ends and lives as long as the run
unit that owns the table". Each `SET ... TO LOCALE` makes a NEW `SavedLocalePointer` (`LocaleState.Save`) with a NEW base (`s_areaBases` is keyed
by object), so a program that saves the locale into a storage-area pointer member in a loop retains one snapshot, one `Identity`, one table entry
and one area-base box per iteration until STOP RUN. The same holds for a fresh `ManagedPointer<T>` carrier per imaging. It is not a wrong answer
(the token on a file is the program's hold, so the retention is the price of the R1-1 fix), but it is unbounded within a run unit where `main` was
bounded. The lead quotes about 148 bytes per iteration and a 335-byte carrier.

**Still true on origin/main (0d4042678a), read this session.** `PointerImage.cs:265-270`: `s_areaBases.GetValue(area, static _ => new
StrongBox<long>(NextBase()))` then `RunUnit.Current.SlotImages.Note(b, new Identity(area))`; `Identity` (line 169) is the record whose doc says it
never ends; `LocaleState.cs:271` `Save(bool userDefault)` returns a new `SavedLocalePointer` on every call. No repro was built or measured in this
note; the next owner measures first: a COBOL program with `PERFORM 1000000 TIMES SET P TO LOCALE LC_ALL MOVE P TO REC-P END-PERFORM`, with
`GC.GetTotalMemory(true)` before and after, to confirm the per-iteration figure and that the growth is linear.

**What a fix must keep.** The PB5928 invariant (a token written to a file resolves for as long as the program can read it back, so no weak path)
and a COBOL-visible rule: the saved locale is a distinct reference each time (GR26). Candidate shapes, not decided here: an equal-content
`SavedLocalePointer` interned per run unit (the same snapshot gets the same identity and base, so a loop that saves an unchanged locale retains
one), or a bound on the table tied to the saved locale's own life (the locale it names). The choice changes what a pointer compare and
`SET LOCALE ... TO P` observe, so it is a design decision for the PB5928 owner. Measure, then record the decision as a `kind: decision` dated file
beside this note.
