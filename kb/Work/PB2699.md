# PB2699 — the loop's planner reads a main checkout that falls behind origin/main

**Found by:** the wave-1042 unit (2026-10-08 07:51 PDT), reading `plan_wave.py`'s table.

## Defect

At planning time the main checkout `E:\COBOL` was at `440b526a3` (train 1040) and `origin/main` at `7fb5cab75`
(train 1041b), 7 commits ahead. `plan_wave.py` printed `devlog_n 1937; previous train 1040` and wrote both into
`wf-args-w1042.json`, while the DEVLOG top on `origin/main` is entry 1938 and the last train was 1041b. The worktrees it
plans are cut from `origin/main` (its `base` line reads `git rev-parse origin/main`), but everything it plans FROM is
read from the checkout:

- `scripts/orchestrator/plan_wave.py` `previous_train()` and `next_wave()` open `REPO / "DEVLOG.md"`, where `REPO` is
  `coord.REPO`, the directory the script lives in (`scripts/orchestrator/coord.py:28`).
- `alloc.py peek devlog` (`devlog_top(repo)`) reads the same file.
- `work.load()` reads `REPO / "kb" / "Work"` (`scripts/spec/work.py:73`), so the open notes, their `status`,
  `blocked_by` and file sets are the checkout's.
- the fix-cluster source index is built over the checkout's `src/`.

Only `scripts/orchestrator/autostart.ps1` (lines 48-57) brings the checkout up to date, with `git pull --ff-only` when
nothing but `settings.local.json` is modified, and only once, before it starts `orchestrate.ps1`. Nothing between units
does, and every train lands from its own worktree through `push-main.sh`, so the checkout falls one train further behind
with each landing for as long as the loop runs.

## Harm

Wave 1042's two stale values are harmless: the train brief tells the lander to re-read the DEVLOG top and use top + 1,
and the previous-train label is prose. The register is the real exposure. A note landed by a train after the checkout's
commit still reads `open`, so the planner can dispatch an implementer at a fixed defect (the implementer's re-probe, I3,
discharges it after a full orientation). A note filed by such a train is invisible, so it cannot be planned, and a
`blocked_by` that train cleared still blocks. None of this is reported anywhere; the planner prints no warning when the
checkout is behind `origin/main`.

## Fix direction

Make the tree every unit reads current in one place, not in each reader. The supervisor (`orchestrate.ps1`) should
fast-forward the checkout before it starts each unit, under the same rule `autostart.ps1` uses (only when nothing but
`settings.local.json` is modified; never stash, never reset), and log the result; no unit runs at that moment, so it
cannot move a tree a unit is reading. `plan_wave.py` should then refuse to plan, or plan only with an explicit
`--allow-stale`, when `HEAD` is not `origin/main`, naming both shas. A drift test: a planner run whose `HEAD` lags a
fixture `origin/main` exits non-zero. The duplicated pull in `autostart.ps1` then moves into the supervisor's one
routine (CLAUDE.md rule 4: no second copy).
