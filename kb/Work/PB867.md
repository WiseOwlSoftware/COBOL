# PB867 — OPEN — an explicit RAISE that does nothing

Source: the `PB367` implementer report, item (a), which measured the behaviour and declined to call it a defect.

## Observed (the source report's probe, `p3-f3.cob`)

A program whose `MAIN` does `RAISE EXCEPTION EC-USER-DEMO.` with a matching `USE AFTER EC EC-USER-DEMO`
declarative and **no** `>>TURN` prints only `AFTER`: the declarative never runs and nothing is reported.

## The two texts

```
$ python scripts/spec/cite.py --check 14.6.13.1.1 "Checking is not enabled unless the TURN directive or WHEN phrase of the PERFORM statement is used to enable checking for the exception"
  OK  §14.6.13.1.1   (General)
$ python scripts/spec/cite.py --check 14.9.29.4 "RAISE"
  OK  §14.9.29.4 1)  (General rules)
      1) If exception-name-1 is specified, the associated exception condition is raised, and EXCEPTION-OBJECT is set to null. Execution continues as specified in 14.6.13, Exception condition handling.
```

Reading A (today's tree): §14.6.13.1.1 says checking for a user-defined condition is not enabled without a TURN
or a WHEN phrase, and an unchecked condition is not raised — so the RAISE is inert.

Reading B: §14.9.29.4 GR1 says the condition IS raised by the statement and that execution continues "as
specified in 14.6.13" — i.e. the RAISE is the enabling event for its own condition, and §14.6.13.1.1's sentence
governs conditions detected by the IMPLEMENTATION, not conditions a program raises explicitly.

## Why it needs deciding rather than fixing

An explicit RAISE of a condition nobody is checking silently doing nothing is a surprising outcome for a user,
and the surprise is exactly the kind that reaches a bug report as a wrong answer. But reading A is defensible
from the text and is what the tree does; changing it without the adjudication would be a behaviour change
pinned by nothing.

## Owner question

Does `RAISE EXCEPTION EC-USER-x` raise the condition when checking for it has not been enabled?

## Code site

`src/Cobol.Net.Compiler/CodeGen/EcEmitter.cs#EmitRaise` and the `>>TURN` mask.

## Sibling sweep whoever decides owes

* `RAISE identifier` (the EXCEPTION-OBJECT form) and `EXIT ... RAISING` / `GOBACK ... RAISING` ask the same
  question for the same conditions.
* The level-3 EC-USER family is where it bites; the level-1/2 conditions have implementation detection and are
  a different population.

## Research 2026-09-30 (exceptions-group research, main `4a1dda60e`) — the SPEC decides this; no owner question remains

The adjudication does not need the owner: §14.6.13.1.1 answers it in so many words, for EVERY statement's general
rules, RAISE included:

```
$ python scripts/spec/cite.py --check 14.6.13.1.1 "Therefore, when the general rules for a statement indicate that a specific exception condition exists, it is raised only if checking for that exception condition is enabled"
  OK  §14.6.13.1.1   (General)
$ python scripts/spec/cite.py --check 14.9.29.4 "For nonfatal exception conditions where there are no applicable exception processing procedures, the RAISE statement acts as a CONTINUE statement"
  OK  §14.9.29.4 1)  (General rules)
```

§14.9.29.4 GR1 ("the associated exception condition is raised") is a general rule of a statement indicating that a
condition exists — exactly the sentence's subject — so it is raised only if checking is enabled; and for the EC-USER
family §14.6.13.1.1 adds "Checking is not enabled unless the TURN directive or WHEN phrase of the PERFORM statement is
used to enable checking for the exception." **Reading A (today's tree) is the standard's.** Reading B has no text: GR1's
"Execution continues as specified in 14.6.13" sends the reader INTO the clause that holds the enablement sentence.

**The EXCEPTION-OBJECT half follows the same way.** §14.6.13.1.1 bundles the three effects of a raise into one sentence
— "the associated exception condition is raised, the last exception status is set to indicate that exception
condition, and the predefined object reference EXCEPTION-OBJECT is set to null" (OK §14.6.13.1.1) — so an un-raised
condition nulls nothing, and the registrar-14c probes (`sr2c.cob` → `EO-SET`; `gr1.cob` → the previous EXCEPTION-STATUS
kept) show the conforming behaviour. The FATAL-name-with-checking-off arm (EmitRaise's terminate) is the separate
§14.6.13.1.3 8) implementor choice, consistent with the 2026-07-28 owner rule (loud abort where the standard names no
outcome) — out of this note's question.

**Sibling sweep (from the note):** `GOBACK … RAISING` / `EXIT … RAISING` already obey the same sentence in the
ACTIVATOR (§14.9.18.4 1) b), PB408); `RAISE identifier` (an object) is never TURN-gated — §14.6.13.1.1's enablement is
about exception status indicators, and an exception object has none (§7.3.25 takes names only; design doc "RAISE
identifier-1 … NOT TURN-gated").
