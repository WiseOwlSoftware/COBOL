# PB206

Found 2026-08-31 by [[PB184]]'s sibling sweep, **deliberately not landed with it**: PB184's landing screens the
three rules that restrict a group VALUE's SUBTREE (SR13 sentence 2, SR14's two conjuncts — COBOLNET1702). These
restrict the SUBJECT and the LITERAL instead — a different axis, each with its own derivation.

✅ **SR1 LANDED 2026-08-31 with PB184's review-fleet landing (COBOLNET1703)** — pulled forward out of this note,
not because it was convenient but because the review round proved it was *load-bearing for a rule PB184 had
already shipped*. §13.18.29.4 GR3 makes a group an alphanumeric group item only when no GROUP-USAGE clause is
specified or implied **and** it "is not strongly typed and is not a variable-length group"; PB184's screen wrote
only the first conjunct, so with SR1 unenforced a strongly-typed or variable-length subject answered SR14's usage
arm. Measured then: `01 ST IS TYPEDEF STRONG VALUE "ABCD". 05 SY PIC 9(4) COMP.` and
`01 GV VALUE "ABCDE". 05 GB PIC 9(4) COMP OCCURS DYNAMIC CAPACITY IN CAP FROM 1 TO 5.` each drew COBOLNET1702
naming SR14 — the wrong rule, on source whose actual violation was unreported. Both shapes now draw COBOLNET1703
and the `alphanumeric` predicate states all three of GR3's conjuncts. Pins:
`tests/conformance/negative/pb184-group-value-{strong,variable-length}-subject.cob`.
⚠ The ODO distinction was measured, not assumed: §8.5.1.12.1 defines a variable-length group over *dynamic-length
elementary items and dynamic-capacity tables*, so an `OCCURS … DEPENDING ON` group is NOT one — it stays an
alphanumeric group item and still draws the SR14 verdict.

**MEASURED** on 8ca74a3d, each compiled CLEAN with no diagnostic:

| rule | program | observed |
|---|---|---|
| ~~SR1~~ | ~~`01 TT IS TYPEDEF STRONG. 05 T1 PIC X(2). 01 GT TYPE TT VALUE "AB".`~~ | ✅ landed — COBOLNET1703 |

| SR4 size | `01 GZ VALUE "ABCDEF". 05 O1 PIC X(2). 05 O2 PIC X(2).` | `DISPLAY GZ` → `ABCD` — silently truncated |

**THE RULES STILL OPEN.**

- **SR13 sentence 1** (FORMAT 1; SR16 extends it to format 2): "If the VALUE clause is specified at the group
  level, literal-1 shall be of the same category as the group item or shall be a figurative constant that is
  permitted in a MOVE statement to a receiving item of that category." A group VALUE never reaches
  `DataBinder.ValidateValueCategory` at all — its call site is guarded `pic is not null`, and a group has no
  PICTURE — so the whole category axis is unscreened for group subjects.
- **SR4 / SR5 / SR10 group clause**: "Alphanumeric literals in the VALUE clause of an alphanumeric group item
  shall not exceed the size of the group item" (SR4), with the national (SR5) and boolean (SR10) twins.
  ⛔ **THREE-ARM RULE** — SR4/SR5/SR10 are the same sentence written once per category, so screening only the
  alphanumeric one is the [[feedback_two_arm_dispatch]] shape with a third arm.

**WHY IT NEEDS ITS OWN DERIVATION, not a bolt-on to COBOLNET1702.** The size rule turns a currently-silent
TRUNCATION into a rejection, and unlike PB184's three rules its blast radius cannot be measured by a static
scan — a group's size is a computed fact, not a textual one. It has to be measured by landing the screen behind
a probe and running the full battery, which is a wave of its own. (The static scan DID clear the other two:
zero SR13-category candidates across `tests/conformance`, `tests/characterization`, `tests/differential`,
`tests/version-matrix`, `tests/nist/programs` and `tests/nist/copylib`.)

**FIX SHAPE.** Extend `DataBinder.CheckGroupValueDeclarations` — it is already the ONE place group-level VALUE
rules live, and SR1's landing proved the addition shape works. ⛔ The forest is **`CompositionForest`**, not
`ConformanceForest` as this note originally said: these rules are properties of the COMPOSED entry, and the
written-entry forest drops every TYPE clone subtree (that error is exactly what the review fleet found in PB184's
first landing). Add the literal test (SR13 s.1 category + the SR4/SR5/SR10 size limit against `group.ImageWidth`,
per category, all three arms), keyed off `IsGroupValueSubject` so it inherits the once-per-WRITTEN-VALUE
provenance rule for free.

## Batch-b3 extension (lane 3, §13.18.63) — 2026-09-04

The lane-3 VALUE-clause adjudication measured this note's two mechanisms on their own inventory rows, and both adjudicators routed the finding HERE rather than filing a duplicate:

- `SR-13.18.63.3-13` — the group-level VALUE literal never enters the category funnel at all: `DataBinder.ValidateValueCategory` (DataBinder.cs:1249) switches on `pic.Category` and a GROUP entry has no `PicInfo`, so the whole screen is skipped rather than failing open on one arm. The p3 adjudicator flagged the leg as ALREADY OWNED by this note ("do not re-file it") — so it is recorded here.

Both rows are recorded PARTIAL in batch b3; they close when this note's group-SIZE limit lands.

## LANDED 2026-09-04 — and the mechanism was LARGER than this note's two rules

**Both claims reproduced** on `1d949007`, on this worktree's own `cobol.exe`: `01 GN VALUE 1234. 05 N1 PIC X(2).
05 N2 PIC X(2).` compiled clean and seeded `N1=[  ] N2=[  ]` (SR13 s.1 — the literal lost ENTIRELY, not merely
accepted: §13.18.63.4 GR5's area deposit is over the operand's CHARACTERS and a numeric literal has none), and
`01 GZ VALUE "ABCDEF". 05 O1 PIC X(2). 05 O2 PIC X(2).` compiled clean and displayed `ABCD` (SR4 s.3).

**THE ROOT CAUSE WAS ONE SENTENCE, NOT ONE RULE.** The note framed this as "extend
`DataBinder.CheckGroupValueDeclarations`". Re-probing found the group subject is not the only unscreened one, and
that the group and elementary halves are the SAME sentences: SR4, SR5 and SR10 each carry the size limit TWICE —
once for an elementary item ("the size indicated by an explicit PICTURE clause") and once for a group ("the size
of the group item") — and their FIRST sentences say "the item" / "the subject of the entry", never "the elementary
item". §8.5.2.1 gives a group a class and category outright and §13.18.29.4 GR1b/GR2b give a bit / national group
an as-if PICTURE, so **SR13 sentence 1 is SR4/SR5/SR10's first sentences restated for a group subject.** Writing
the group screen separately would have been a second copy of the answer. Instead
`DataBinder.ValidateValueCategory` became THE §13.18.63.3 VALUE-operand screen for every subject the rules name,
and the group enters it with its own category picture (`GroupSubjectPic`).

### THREE MORE DEFECTS THE ONE-PLACE SHAPE EXPOSED, none of them in this note

1. **SR4 sentence 2 — the ELEMENTARY size limit — was unenforced too, and silently truncated.**
   `01 E1 PIC X(2) VALUE "ABCD".` displayed `AB`. Its national (SR5 s.2) and boolean (SR10 s.2) twins were both
   implemented: the [[feedback_two_arm_dispatch]] shape with the third arm missing. Now **COBOLNET1740**, error at
   every edition (Annex E.2 item 27's 2023 size change is scoped to NUMERIC-EDITED items — COBOLNET1570 — not to
   this). A FIGURATIVE operand is exempt BY RULE: §8.3.3.6.4 GR2 repeats it to the subject's size and truncates
   from the right, naming the VALUE clause as the context that specifies the length.
2. **The size arms REJECTED LEGAL SOURCE on a DYNAMIC LENGTH subject.** They measured against `pic.Length`, so
   `01 UN PIC N DYNAMIC LENGTH VALUE N"SEED".` drew COBOLNET0898 ("exceeds the item's 1 national positions")
   while its byte-for-byte twin `01 UD PIC X DYNAMIC LENGTH VALUE "SEED".` compiled and ran — one arm sized, one
   not. §13.18.19.3 SR1 makes such an item's PICTURE "one instance of the picture symbol 'N', or 'X'" and
   §13.18.19.4 GR1 makes that symbol determine the CLASS; it indicates no size at all (the maximum is the LIMIT
   phrase's, or implementor-defined — GR2). The screen now takes the size as an argument (`sizePositions`), null
   for a DYNAMIC LENGTH / ANY LENGTH subject.
3. **PB207's staged-loud refusal ran FIRST and answered for two populations it does not govern.** COBOLNET0899
   (the §13.18.63.4 GR5 area deposit over a bit-packed group, PB207's) used to `continue` before every syntax
   rule, so (a) SR10's own group sentence was UNREACHABLE — a bit group with an oversize boolean literal was told
   the area rule is unimplemented — and (b) a group with no GROUP-USAGE clause but a USAGE BIT subordinate, which
   is an alphanumeric group item (§13.18.29.4 GR3) whose bit leaf violates SR14's usage conjunct, got the same
   answer. The refusal now runs LAST, gated on "no error already reported for this subject": a refusal is what is
   left when the source is conforming and we cannot compile it, never the first thing said about source that is
   not. PB207's own stage is untouched — a CONFORMING bit-group VALUE still reaches it.

### What landed

- **`DataBinder.ValidateValueCategory`** — THE screen, now taking `int? sizePositions` (no default: every call
  site states it) and `bool groupSubject`. New alphanumeric SIZE arm (COBOLNET1740, SR4 s.2 + s.3); SR5/SR10 size
  arms read `sizePositions`; the SR4-sentence-1 `--permissive` leniency is withheld from a group subject and is a
  hard error citing SR13 there, because the leniency promises a store ("the literal's characters as MOVE would
  store them") that a group area cannot perform for a numeric literal.
- **`DataBinder.ValueSizePositions`** — the elementary subject's size, null for DYNAMIC LENGTH / ANY LENGTH.
  ⚠ **SUPERSEDED IN SHAPE 2026-09-05 by [[PB598]]** (this note's verdicts and diagnostics are unchanged). The
  `int? sizePositions` + `bool groupSubject` pair described here is now ONE `ValueSubject` descriptor
  (`src/Cobol.Net.Compiler/Binding/ValueSubject.cs`) and `ValueSizePositions` is gone, its body being
  `ValueSubject.ForElementary`. The reason is a defect this landing completed: the pair let the three level-88
  call sites hand the screen the CONDITIONAL VARIABLE's size, and §13.18.63.3 SR4/SR5/SR10's size sentences
  name only an elementary item and a group item — never a condition-name — so `01 XV PIC X. 88 XC VALUE "cd".`
  became COBOLNET1740, a rejection of legal source.
- **`DataBinder.GroupValue.GroupSubjectPic`** — the §8.5.2.1 category picture of a group SUBJECT. Deliberately
  NOT `DataItem.OperandPic`, which is null for an alphanumeric group because §14.9.25.4 GR4 makes a MOVE across
  one a conversion-free copy Table 16 does not describe; as a VALUE subject the group has a category outright.
- The PB207 refusal reordered, and the `DiagnosticCatalog.ValueLiteralOversize` descriptor.
