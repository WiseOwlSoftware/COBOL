# PB313 — a real implementor decision with no published answer

## The question the standard leaves open

`FUNCTION FORMATTED-DATETIME("YYYYMMDDThhmmss" 143951 18867.812479168304)` — a standard-numeric-time-form value
(§15.5.5 says *"a numeric value"*, not an integer) rendered into a format whose seconds subfield has **no**
fraction positions. And `"YYYYMMDDThhmmss.ssss"` with the same argument, where the format holds four fraction
digits and the argument carries twelve.

* `cite.py --check 15.3.3.1 "The two colon characters appear in the data associated with an extended common time
  format."` → OK — §15.3.3.1 gives the seconds subfield exactly two `s` positions.
* `cite.py --check 15.3.3.3 "The seconds subfield of the data shall contain a value that is greater than or equal
  to 00 and is less than 60 when the LEAP-SECOND directive with the OFF phrase is in effect."` → OK — it bounds
  the value.

**Neither says what becomes of precision the subfield cannot hold.** Truncation (…27, …8124) and rounding (…28,
…8125) are both admissible readings.

## What is documented today, and why it does not answer

`docs/CONFORMANCE.md` §7 item **202** documents only the MAXIMUM number of fraction digits a *format* may specify
(18, from §15.3.3.2). Item **87** documents only the CLOCK's zero-fill for `FORMATTED-CURRENT-DATE`. Neither
answers what happens to an **argument's** excess precision, which is a different axis: the argument's precision is
the caller's, not the clock's.

## What the compiler does

It **truncates**, as `EmitFormatted` renders. That is a real implementor decision a user has to be able to predict,
and A.1 does not currently list an item for it.

## What was done instead of guessing

The golden lane's first draft of `l1_fdt_returned_value_combination` asserted seven values that turned on this. The
delivered goldens **avoid the question entirely** — integer seconds for the shape legs, a four-digit argument for
the four-digit leg, and `SF` kept only where the width is two and both readings agree on `81` — so nothing that
landed depends on an undocumented choice. The documentation gap survives the correction, which is what this note is
for.

## Proposal

Add a §7 determination (or extend item 202's row with a second, clearly-separated sentence — the audit's
number/element cross-check decides which) stating that an argument's precision beyond the format's fraction
positions is **truncated, not rounded**, and pin it with a golden whose two readings differ. Until then a user
reading `docs/CONFORMANCE.md` cannot predict the answer, which is the §4.2.5 obligation this is measured against.
