# R18 — EXP / EXP10 / E ignore the standard arithmetic modes: not SDIDI-evaluated, and the returned value depends on the receiver

> R00 ledger-audit orphan (2026-08-08): F15 + F19 of `PHASE-B-15.32-15.44-findings.md`, probe-verified OPEN
> against the R10-landed tree (`5312996a`). The probe programs are reproducible from the finding text.

PROBES (2026-08-08, OPTIONS. ARITHMETIC IS STANDARD-DECIMAL):
- `FUNCTION EXP(2)` vs `FUNCTION E ** 2` → `NE` (7.3890560989306499891 vs …8975); §15.4.1 r1 makes the
  function equal its equivalent arithmetic expression, and §8.8.1.5.4 r2b + §15.27.3 r3 fully determine the
  EAE here (E*E in SDIDI, no latitude).
- `COMPUTE P09 = FUNCTION EXP10(0.5)` / `COMPUTE P17 = …` → 3.162277660 vs 3.16227766016837952 — the SAME
  reference returns different values by receiver, violating §15.4.1's same-for-all-instances rule.
ROOT (ledger): IntrinsicRenderer routes `sig.Float` to RenderFloat before any arithmetic-mode test, and the
COBOLNET0899 staging list excludes EXP/EXP10/E on the false premise that the float family has no EAE
(§15.34.4 / §15.35.4 carry one; FUNCTION E has §15.27.3 r3's exact value). The exact-family SDIDI lift landed
(FRACTION-PART/INTEGER probes are exact now — PB38's wave), so this is the FLOAT-family residue of the same
§15.4.1 rule. FIX: under a standard mode, evaluate EXP/EXP10/E through the CobolDec bodies (or stage them
loud) — an owner-visible choice per the F19 correction; binary64 Math.Pow is not SDIDI arithmetic.

## LANDED 2026-08-08

**The standard-mode arm runs BEFORE the float dispatch in `IntrinsicRenderer.RenderNum`**, and it reuses the
machinery the hand-written spellings already had — no new engine:

- `FUNCTION E` / `FUNCTION PI` fold to the exact 34-digit SDIDI constants `CobolDec.E` / `CobolDec.Pi`
  (§15.27.3 r3 / §15.73.3 r3, both cite-checked; **PI is the sweep sibling this note had not named** — same
  rule shape, one line). My first guess at PI's clause (§15.72.3) was ORD-MIN; cite.py caught it — §15.73.3.
- `EXP(x)` renders `CobolDec.Pow(CobolDec.E, x')` and `EXP10(x)` renders `CobolDec.Pow(10, x')` — the SAME
  `Pow` the spelled-out `**` uses (§8.8.1.5.4), over the SAME constants, so §15.4.1 r1's function-equals-EAE
  holds BY CONSTRUCTION. A float argument lifts via `DecOperand` → `CobolDec.FromDouble` (§8.8.1.5.1).

Probes after: `EXP(2) = E ** 2` → **EQ** (was NE with both sides wrong) · `EXP10(23)` → exactly 10^23 with
`DIFF=0` (was binary64's …991611392) · the F19 receiver pair now holds prefixes of ONE SDIDI (receiver-scale
rounding at the final transfer is §14.7's rule; §15.4.1's same-for-all-instances is about the returned value,
which is now single).

**Residual, noted not forked:** for a NON-INTEGER exponent, `CobolDec.Pow`'s approximation is binary64-seeded
(§8.8.1.5.4 r2e implementor territory shared with every hand-written `**`) — one rule in one place; refining
Pow refines both spellings at once. The golden pins the current documented approximation on the EXP10(0.5)
pair with a comment saying so.

anchors on the FIRST `switch (sig.RuntimeMethod)`) — the arm is now an if-chain with a comment, since it is
NOT an exact-family arm (DecOperand handles Real). And the guard's name class could not see digit-bearing
methods (`[A-Za-z]+` missed `Exp10` entirely — the PB21 under-count shape); widened to `[A-Za-z0-9]+`.
The RuntimeApi characterization guard forced `DecE`/`DecPi`/`DecFrom` helpers — routed.

Golden `exp_standard_decimal_eae` (2023, registered): EAE equality, 10^23 exactness, both constants truncated
