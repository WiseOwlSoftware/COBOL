# PB5836 - a finished hand-dispatched branch stays IN FLIGHT while the dispatching session lives: the worktree lock carries the SESSION's process id and the survey's live test reads it

**Sites:**
- `scripts/prune_worktrees.py#live_lock` (reads the process id in the lock's reason)
- `scripts/prune_worktrees.py#lifecycle` (returns IN FLIGHT "worktree locked by a live agent" when `live_lock` holds)

Kind: defect. `process_only: true`. No harm flag. Severity: MINOR unless the register's rule says otherwise. Area: tooling/orchestrator. Related: PB2600, PB3027, PB3608, PB5759. Measured on Monday 2026-11-16, 00:04 to 00:32 PST, by the Mythos lane.

## What happened
The follow-up implementer of kb/Work PB5759 returned DONE at about 00:04 on branch
`worktree-agent-a1369f767c02c7fc0`, gate GREEN at f3412a8c3d. The loop mailed `STALL w20262055a (PB5759): no progress
for 26 min on its branch review` at 00:31. No reviewer had started, because the survey did not offer the branch:
`python scripts/prune_worktrees.py` printed
`IN FLIGHT worktree-agent-a1369f767c02c7fc0 [worktree] — worktree locked by a live agent (claude agent agent-a1369f767c02c7fc0 (pid 14380))`.

`git worktree list --porcelain` showed the lock `locked claude agent agent-a1369f767c02c7fc0 (pid 14380)`. Process
14380 is the attended session itself (`claude.exe`, started 2026-11-15 17:39), not the agent: the harness writes the
SESSION's process id into the lock of every worktree it creates for an agent. The agent the lock names had finished
hours before; a second agent had since worked in the same worktree and finished too. Five worktrees of the session
carried such a lock at 00:32, two of them (the clerks of notes batches 8 and 9) for agents that had finished and
landed.

After `git worktree unlock E:/COBOL/.claude/worktrees/agent-a1369f767c02c7fc0` the survey printed
`WAITING FOR REVIEW worktree-agent-a1369f767c02c7fc0 [worktree] — w20262055a-PB5759-report.md: Status DONE, no review stamp`.

## The mechanism
`scripts/prune_worktrees.py`: the lifecycle rule returns IN FLIGHT when `live(row.lock)` holds, and `live` reads the
process id in the lock's reason. For a worktree the Agent tool made, that id is the dispatching session's, so the
test answers "is the session alive", not "is the agent alive". A finished branch whose lock the harness did not
release is hidden from the review lane and the landing lane until the session ends, and the only signal is the
STALL mail.

Not every finished agent leaves its lock: the worktrees of the kb/Work PB5754 and PB5822 implementers had none after
they returned. Which agents keep theirs (one that ended while a background task of its own still ran, or one whose
worktree a second agent then used) was not determined.

## What a fix must decide (not decided here)
- What the survey may trust as "an agent is working here": the lock alone is not it. A branch whose report says
  DONE at the branch's tip is finished whatever the lock says, and the survey already reads the report.
- Whether a dispatching session should release the lock itself when an agent returns DONE.
