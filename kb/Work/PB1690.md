## Landed (wave 1001 C, 2026-10-01)

COBOLNET2691 (`DiagnosticCatalog.DirectiveAfterProgramText`, §7.3.3 SR2 — `cite.py --check` OK). The recognizer is the ONE
literal-aware scan of the §6.5 pass (`ScanProgramText`, stop kind `Directive`): a `>>` outside a literal and a comment,
preceded by program text on its line and followed by a word the directive catalog knows
(`CompilerDirectiveLine.TryParse` + `CompilerDirectiveCatalog.IsDirective` — the SAME recognition every directive stage
uses, no second slice). The directive text and the rest of the line are cut, so the parser adds no nameless COBOL0001;
the corpus negative `pb1361-directive-after-program-text` now expects COBOLNET2691. A `>>` inside a literal or a comment,
or not followed by a directive word, is not a directive. Witnesses: `conformance:negative/pb1361-directive-after-program-text`,
`conformance:negative/pb1690-directive-after-program-text-fixed`,
`unit:ReferenceFormatLogicalConversionTests.DirectiveAfterProgramText_IsDiagnosedByName`. Not done (PB1360's): a
continuation line whose latest logical line is a directive line.


# PB1690 — LANDED

Filed by the train-70 lander from wave 70 group B's report (implementer of PB1361; `w70b-PB1362-report.md`, lead 3).

## Finding

**Repro.** `E:\Temp\claude\E--COBOL\73cac64c-391d-42c0-bcdf-c880e3e10305\scratchpad\w70b\probe\d1.cob`: a line with
program text before `>>SOURCE FORMAT …` is refused as `COBOL0001` (an unexpected `>`), which names neither the
directive nor the rule. The corpus negative `tests/conformance/negative/pb1361-directive-after-program-text` pins
exactly that generic COBOL0001.

**Rule** (`cite.py --check` OK). §7.3.3 2): "A compiler directive shall be preceded only by zero, one, or more space
characters."

**Code site.** `src/Cobol.Net.Frontend/Preprocessor/ReferenceFormatProcessor.cs#FormatSegments` /
`#DirectiveText`: a line whose program-text area holds `>>` after non-space text is not a directive line, so it stays
program text; nothing names the violation. The fix recognizes the shape (a `>>` directive word after program text)
and raises a catalogued diagnostic citing §7.3.3 2), then updates the negative's `.err`.

## Revisit before implementing (directives-cluster batch, DEVLOG 1810)
Not taken (needs a new diagnostic code and a change to `ReferenceFormatProcessor.FormatSegments`/`DirectiveText`, then the .err of
`negative/pb1361-directive-after-program-text` from COBOL0001 to the new code). Free-form detection must not misfire on a literal or
inline comment containing `>>`; drive the recognizer from `CompilerDirectiveLine` rather than a second slice.
