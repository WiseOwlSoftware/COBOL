# PB4499 — GnuCOBOL accepts CALL ... USING OMITTED without a program prototype under the ISO dialects

## Summary

ISO/IEC 1989:2023 §14.9.4.2 Format 1 (Program), rendered from the printed page (PDF p618), gives USING only
`[BY REFERENCE] {identifier-2} ...` or `BY CONTENT {identifier-2} ...`; OMITTED exists only in Format 2
(program-prototype), which `AS` or a program-prototype-name selects. ISO/IEC 1989:2002 §14.8.4.1 is the same (OMITTED
only in Format 3, program-prototype), and COBOL-85's CALL has no OMITTED phrase (OMITTED is a COBOL-85 reserved word, for LABEL RECORDS ARE OMITTED). cobc 3.2 accepts the Format 1 spelling with no
diagnostic, even with `-Wall`, under `-std=cobol85`, `-std=cobol2002` and `-std=cobol2014`.

## Minimal test case

Written for this note (not taken from the GnuCOBOL testsuite):

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. OMITCALL.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 A PIC X VALUE "A".
       PROCEDURE DIVISION.
       MAIN-PARA.
           CALL "SUBPROG" USING A OMITTED
           STOP RUN.
```

`cobc -fsyntax-only -Wall -std=cobol2014 omit.cob` (also `cobol2002`, `cobol85`).

## Environment

GnuCOBOL 3.2.0 (`cobc (GnuCOBOL) 3.2.0`), Ubuntu under WSL2 on Windows 11, 2026-11-03.

## Observed result

No output, exit 0, under each of the three dialects.

## Expected result (per ISO)

A diagnostic: OMITTED is not part of Format 1's USING phrase (§14.9.4.2, `cite.py --check 14.9.4.2 "Format 2
(program-prototype)"`: OK), so the statement does not conform. Under `-std=cobol85` the CALL statement has no OMITTED phrase (vendor evidence in the upstream state; OMITTED itself is a COBOL-85 reserved word).
The default dialect may keep it as an extension.

## Our compiler (WiseOwl)

COBOL0899 at every edition: "CALL USING OMITTED: the OMITTED phrase belongs to the program-prototype CALL (ISO §14.9.4.2
Format 2) ...". `--permissive` makes it a warning (kb/Work PB4012). The refusal is `CallBinder.Format2OnlySpellingOf`.

## Fix site (GnuCOBOL 3.2 source, read observationally)

`cobc/parser.y`, rule `call_param`, alternative `_call_type OMITTED`: it checks only that the mode is BY REFERENCE and
never asks whether the CALL names a prototype or whether the dialect supports the phrase. A `cb_verify` against a new
dialect option (unconformable in cobol85/2002/2014, ok in the default) when the CALL has no prototype would close it.

## Draft issue

**Title:** -std=cobol2014, cobol2002 and cobol85 accept CALL ... USING OMITTED in a CALL with no program prototype

As posted (owner-reviewed, 2026-11-03):

Under `-std=cobol2014`, `-std=cobol2002` and `-std=cobol85`, cobc compiles `CALL "SUBPROG" USING A OMITTED` without any diagnostic, even with `-Wall`. The standard allows OMITTED only in the program-prototype form of CALL, the one selected by `AS` or by a program-prototype-name, so these dialects do not report a use of OMITTED that the standard does not allow. We understand from [#562](https://sourceforge.net/p/gnucobol/bugs/562/) that OMITTED in a plain CALL is supported on purpose for COBOL-to-COBOL calls. This report does not ask to change the default dialect, only for a dialect-controlled diagnostic under the ISO dialects.

## To reproduce

`omit.cob` (attached):

~~~~
       IDENTIFICATION DIVISION.
       PROGRAM-ID. OMITCALL.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 A PIC X VALUE "A".
       PROCEDURE DIVISION.
       MAIN-PARA.
           CALL "SUBPROG" USING A OMITTED
           STOP RUN.
~~~~

    cobc -fsyntax-only -Wall -std=cobol2014 omit.cob

and the same with `-std=cobol2002` and `-std=cobol85`.

## What happens

3.2.0 and 3.3-dev r5751 print nothing and exit 0 under each of the three dialects.

## What should happen

Under `-std=cobol2014`, `-std=cobol2002` and `-std=cobol85`, an error, or a warning controlled by a dialect support option, at the OMITTED. The default dialect keeps accepting it.

The standard's general formats (the ISO text is a format diagram, so it is described here rather than quoted):

- ISO/IEC 1989:2023 §14.9.4.2, Format 1 (Program): the USING phrase lists `[ BY REFERENCE ] { identifier-2 } ...` and `BY CONTENT { identifier-2 } ...`, with no OMITTED. OMITTED appears only in Format 2 (program-prototype), which begins `CALL [ { identifier-1 | literal-1 } AS ] { NESTED | program-prototype-name-1 }`.
- ISO/IEC 1989:2002 §14.8.4.1 is the same: OMITTED appears only in Format 3 (program-prototype).
- For COBOL-85 we do not have the 1985 text. IBM's Enterprise COBOL reference, whose baseline is ISO 1989:1985 and its amendments ([Industry specifications](https://www.ibm.com/docs/en/SS6SG3_6.2.0/lr/ref/rlind.html)), lists OMITTED in the CALL statement among its [IBM extensions](https://www.ibm.com/docs/en/SS6SG3_6.2.0/lr/ref/rlext.html), and HP's COBOL documents it as an [HP extension](https://www.zx.net.nz/mirror/h71000.www7.hp.com/doc/82final/6297/6297pro_090.html), so `-std=cobol85` should report it too.

## Where the fix belongs

In `cobc/parser.y`, the `_call_type OMITTED` alternative of `call_param` checks only that the argument is passed BY REFERENCE. It does not look at whether the CALL names a prototype or at the dialect. A new support option in `cobc/config.def` (unconformable in `cobol85.conf`, `cobol2002.conf` and `cobol2014.conf`, ok in `default.conf`), checked there when the CALL has no prototype, would cover it. Which dialects should allow it is the maintainers' choice, so there is no patch.
