# PB879 — LANDED — an edition rule that only one statement shape can reach

Source: the `PB416` report, "New defects" item 3. Same repro program as `PB880`; **two different
mechanisms, and both are live** — PB879 is why the program is not refused at compile time, PB880 is why it
dies the way it does once it runs.

## The measurement

`<scratch>/reg6/probe/p03_init_space_num.cob` (PROGRAM-ID `R6P03`) and its explicit twin
`p03b_move_space_num.cob` (`R6P03B`), both `--std 2023 --run` on this tree:

```
## p03_init_space_num.cob   INITIALIZE G REPLACING NUMERIC DATA BY SPACE
Unhandled exception. CobolNet.Runtime.NotImplementedCobolFeatureException: ... MOVE of an alphanumeric
figurative constant into the numeric item 'N' without image-backed storage ... §14.9.25.3 SR5 / Annex E.2 item 1
rc=127

## p03b_move_space_num.cob  MOVE SPACE TO N
  error COBOLNET0902: MOVE of an alphanumeric figurative constant (SPACE/HIGH-VALUE/LOW-VALUE/non-digit ALL)
  to a numeric or numeric-edited item was removed in COBOL-2023 (targeting COBOL-2023) — MOVE SPACE TO N
  (Annex E.2 item 1 bullet 1; §14.9.25.3 SR5; VCR row 1 ...)

```

**The run-time message names SR5 and Annex E.2 — the compiler knows the rule and knows which statement
violated it, and issues it as a Tier-C abort instead of the diagnostic the same rule produces one file away.**

## The rule

```
$ python scripts/spec/cite.py --check 14.9.20.3 "a MOVE statement with identifier-2 or literal-1 as the sending item and an item of the specified category as the receiving operand shall be valid"
  OK  §14.9.20.3 4)  (Syntax rules)
$ python scripts/spec/cite.py --check 14.9.20.4 "MOVE sending-operand TO receiving-operand"
  OK  §14.9.20.4 4)  (General rules)
```

SR4 requires the implied MOVE to be VALID and GR4 spells the implied statement out as
`MOVE sending-operand TO receiving-operand`, so the two forms are the same statement and shall answer the
same way at the same edition.

## The code site

`src/Cobol.Net.Compiler/Conformance/VersionConformancePass.cs#GateMove` — it matches on a bound `BoundMove`
node. `InitializeBinder` never builds one (see PB880: the node is built in the EMITTER, after every pass has
run), so the three edition rows — permitted through 2014, REMOVED at 2023 except the digit-only-ALL case,
QUOTE on its own dual row — are unreachable from INITIALIZE at every `--std`.

## ⛔ The remedy is NOT to move the rule into MoveTable16

`MoveTable16.DataItemRefusal`'s own doc comment states the reason, and it is correct: Table 16 is
edition-blind by design, and a figurative constant is not a data item, so no operand `DataItemRefusal` can be
given could reach SR5. The repair is a **`BoundInitialize` arm in the version pass** — for each
`InitializeStore` whose source is an alphanumeric figurative constant and whose place is numeric or
numeric-edited, ask the same three edition rows `GateMove` asks. This is a VERSION-CONFORMANCE change, which
is why it is a note of its own and not part of PB878.

## The sibling sweep

`VersionConformancePass` gates on bound NODE KINDS throughout. **Every rule it hangs on a node kind that a
DESUGAR can produce without building that node is the same defect.** The fixer enumerates the pass's node
matches and, for each, asks which implicit-statement desugars reach the same rule: INITIALIZE's implied MOVE
and implied SET (§14.9.20.4 GR4/GR6), MOVE CORRESPONDING's per-pair moves (§14.7.6), GOBACK RETURNING's
implied move, the report-writer SOURCE/SUM stores. A drift test that fails when a new `Bound*` desugar is
added without a version-pass arm is the shape that makes the next one automatic.

## Landed 2026-09-22 — wave 45 (B)

Re-probed on the worktree build: `INITIALIZE G REPLACING NUMERIC DATA BY SPACE` compiled clean at `--std 2023`.

**The fix is the arm the note named, with the rows in ONE place.** SR5's three edition rows moved out of
`GateMove` into `VersionConformancePass.GateSr5`; `GateMove` asks it per receiver and the new `GateInitialize`
asks it per REPLACING category over `BoundInitialize.Replacing` (the written phrase now rides the node). Asked of the
PHRASE, per §14.9.20.3 SR4's "an item of the specified category", not per receiver. ⚠ DETERMINATION: the
digit-only-ALL exception is applied to category NUMERIC as if its item were an integer (never rejects a program
whose actual receivers are integers); NUMERIC-EDITED takes the removal row.

After: 2023 strict → COBOLNET0902 "INITIALIZE REPLACING NUMERIC … BY SPACE (the MOVE ISO §14.9.20.3 SR4 requires to
be valid)"; 2023 `--permissive` → warning + `N=[   ]`; 2014 → `N=[   ]`.

Sibling sweep of the pass's node matches: the SET gates (Format 8/9, SET SIZE, pointer UP/DOWN) are not reachable
from INITIALIZE's implied SET without the operand's own DATA-attribute gate firing first (the pointer categories
are edition-gated at their declaration), and the CORRESPONDING / GOBACK moves are now bound child statements the
`StatementChildren` walk reaches (their senders are data items, which SR5 never reaches).

Golden: `negative/pb879-initialize-replacing-space-numeric-2023` (reject-at 2023 · COBOLNET0902); the positive twin
is PB880's `85/pb880_initialize_replacing_figurative_numeric`.
