# PB1512 — OPEN

## The rule (every citation re-run through `cite.py --check`)

> 1) I-O status = 30. A permanent error exists and no further information is available concerning the input-output operation.

`OK  §9.1.13.6 1)  (Permanent error condition with unsuccessful completion)`


## Finding — `i-o-status-p1` (crashes; rows `GR-9.1.13.6-1`)

**Mechanism.** Host I/O failures inside the sequential READ/WRITE bodies are never mapped to an I-O status: SequentialConnector.Read/Write (and the StreamReader/StreamWriter they drive) have no catch, and neither FileRegistry nor CobolFile wraps the verb, so a System.IO.IOException escapes the generated statement and kills the run unit. The OPEN (FileConnector.Open), CLOSE (FileConnector.Close, PB140), DELETE FILE (ForDeleteFileFailure) arms all map to '30'/'37'/'61' - the READ/WRITE arms of the same dispatch were never fixed.

**Repro.** out/probe/iostat-30/p30.cob: SELECT F ASSIGN TO "p30.dat" ORGANIZATION SEQUENTIAL FILE STATUS ST; FD F 01 FR PIC X(4). OPEN INPUT F (-> 00), ACCEPT W (pause), meanwhile another process opens p30.dat (FileAccess.Read, FileShare.ReadWrite) and calls FileStream.Lock(0,12); then READ F AT END CONTINUE END-READ; DISPLAY ST. Observed: 'Unhandled exception. System.IO.IOException: The process cannot access the file because another process has locked a portion of the file' at System.IO.RandomAccess.ReadAtOffset, process exit -532462766, nothing displayed.

**Expected from the spec.** §9.1.13.6 1): the READ is unsuccessful with I-O status '30' ('A permanent error exists and no further information is available'), set before any exception processing (§9.1.13.1); the FILE STATUS item receives '30', applicable USE procedures run, and then the implementor's documented fatal-status action (A.1 item 103) applies - never an unhandled .NET exception.

**Observed / reasoning.** MEASURED for READ with the pinned compiler. WRITE: by reading - SequentialConnector.Write buffers through StreamWriter and ReleaseRecord calls _writer.Flush() with no catch, so a device-full or locked-region failure during WRITE takes the same path (not measured). Keyed organizations persist at OPEN/CLOSE, which are mapped.

**Code site.** src/Cobol.Net.Runtime/IO/SequentialConnector.cs#Read; src/Cobol.Net.Runtime/IO/SequentialConnector.cs#Write; src/Cobol.Net.Runtime/IO/SequentialConnector.cs#ReleaseRecord; contrast src/Cobol.Net.Runtime/IO/FileConnector.cs#Open (catch IOException -> '30') and #Close

## What the fixer owes

Wrap every connector verb (READ, WRITE, REWRITE, DELETE, START on every organization — sweep, this is the two-arm shape) at ONE dispatch seam so a host IOException becomes '30' (or the more specific status a documented determination assigns — PB1192's medium-exhaustion → '34' boundary is the WRITE sibling) and the §9.1.13 exception path (EC-I-O-PERMANENT-ERROR, USE/WHEN, implicit fatal) runs instead of a .NET crash. Golden: p30 (a file truncated by another process between OPEN and READ); a unit test injecting an IOException through a fake stream for WRITE.
