# PB5939 - the SessionStart hook runs its reads concurrently, and the slow ones are fast

**What was wrong.** `scripts/hooks/session_start.py` ran `scripts/session-probe.ps1` (pwsh) and then the tooling check, and the
probe ran about twenty independent reads one after another: the sum was about 57 s of component time (measured alone, from
`E:/COBOL`): `prune_worktrees.py --brief` 26 s, `ruleset.py check` 9.4 s, `work.py check` 6.1 s, `tooling_check` 4.3 s,
`fuzz_history.py status` 3.8 s, the rest under 2 s each.

**The root causes, and what each became.**
1. *Sequential reads.* The probe is now `scripts/session_probe.py`: one function per section, `run()` starts them all at once and
   prints the lines in `SECTIONS` order, so the wall time is the slowest section. A section that raises or hangs prints its
   own UNREAD line (each command has a 120 s guard) and costs the others nothing. The hook runs the probe's sections and
   `tooling_check` on one pool. `session-probe.ps1` is deleted and every caller and doc names the new file.
2. *The branch survey* (`prune_worktrees.py`). Per row it ran `git status` (about 1 s each at 80 worktrees on a 48,000-file
   tree) one by one with the coverage reads, and the review-coverage loop (`review_holds`: a `git merge-tree` and a
   `git diff-tree` per branch) ran serially in the main thread for every branch with a review stamp, landed ones included:
   18 s of a 32 s run. Now: every worktree's `git status`, the `git grep` of main's names and the pull-request read start
   at once on one pool of `SURVEY_WORKERS`; the coverage reads run on the pool and only for rows the lifecycle reads them
   for (a LANDED row returns before `stamp_held`, so its `review_holds` stays False); the origin fetch and the landing
   order's register read run beside the survey. No verdict changes: `--brief` is byte-identical on one tree (DEVLOG entry).
3. *`ruleset.py check`*: six `gh` calls in a row. The four after the repository name (ruleset, settings, classic
   protection, queue depth) now go out together, and their answers are taken in the old order, so the first problem
   reported and the SKIPPED rule are unchanged.
4. *`work.py check`*: the sites rule read each note's site block (a `git ls-files` per glob, a parse of each named source
   file) one note at a time; the notes are read side by side now. Its output is the same list in the same order.
5. *`fuzz_history.py status`* re-extracted origin/main (4 s) to judge a main that had not moved. The verdict is a pure function
   of the object ids of what the extract holds and the interpreter, so it is kept in the clone's git directory under that key.

**Not done, and why.** The probe still runs `work.py next` and `work.py check` as two processes (two register loads, about
1.4 s each): `check` is the full lint, `next` only ranks, and joining them would put the lint inside every `next`.
The per-worktree `git status` is a floor (the untracked scan is two thirds of it; `-uno` would change the dirty count and
so verdicts).

**Sites:**
- `scripts/session_probe.py` (`SECTIONS`, `run`, `guarded`, `self_test`) (whole: the replacement of `session-probe.ps1`)
- `scripts/hooks/session_start.py` (`main`, `probe`)
- `scripts/prune_worktrees.py` (`survey`, `live_survey`, `main`)
- `scripts/orchestrator/ruleset.py` (`check`)
- `scripts/spec/work.py` (`sites_problems`)
- `scripts/fuzz_history.py` (`main_verdict`, `main_state`, `extract_verdict`)
- `scripts/test_fuzz_history.py` (`main`)
