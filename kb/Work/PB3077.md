# PB3077 — the planner takes the reviewer's label for the branch

## Found (2026-10-11 18:05 PDT, Mythos session, planning wave 1064)
Planning the review finishers of wave 1062's four reviewed branches (operator GO 17:39) through `plan_wave.py`'s own
parsers, `parse_report` returned branch `worktree-wf_aba5c7ac-b61-1-r1` for `w1062a-PB2987-report.md` and
`worktree-wf_aba5c7ac-b61-7-r1` for `w1062a2-PB3023-report.md`; `git_branch_classifier` called both ABSENT, and the
rendered `FINISH-FIRST` instruction told each finisher to `git merge` a branch that does not exist. The reports'
`Branch:` lines say `worktree-wf_aba5c7ac-b61-1` and `worktree-wf_aba5c7ac-b61-7` (both UNLANDED). The two reports
whose header is the template form (`**branch:** `x`` on the Status line, the stamp below it) parsed right, which is why
the earlier planner self-test and wave 1062's own planning saw nothing.

## Mechanism (`scripts/orchestrator/plan_wave.py`)
`parse_report` took the header (up to the first `## `) as one text and read `BRANCH.search(text)`: the FIRST
`worktree-[A-Za-z0-9_.-]+` word. `review_findings.py stamp` (kb/Work PB3027, on main since train 1063) writes the review
one line under the Status line, which in an O11 header (`Status:` · `Worktree:` · `Branch:` · `HEAD:` · `Base:`) is
ABOVE the Branch field, and the reviewer's label is `land-review-<branch>-r<k>` — the branch name with a suffix. The
label therefore won. The same text fed `WORKTREE` and `HEAD`, which the stamp happens not to match (its sha follows the
label, not the word `head`; its findings path has no `\worktrees\`).

## Harm
A DONE report whose stamp says FINDINGS, with its branch read as ABSENT (a LANDED class), satisfies neither the finisher
arm (`cls not in LANDED_CLASSES and … FINDINGS`) nor the awaiting-landing arm: its open notes are not `taken`, so the
fix lane and the campaign lane would plan them again as fresh cluster groups — the same work twice, in a worktree that
does not merge the reviewed branch — while the reviewed branch sits in `prune_worktrees.py`'s DECISION rows with nobody
planned to finish it. `prune_worktrees.py` is not affected: `newest_report` reads the header's branch FIELD with its own
`BRANCH_FIELD` rule, which is why `session-probe` still listed the five branches under their reports. In wave 1064 the
collisions of kb/Work PB3040 masked it (the campaign planner never reached these notes); the hand-planned dispatch found
it because it rendered the finisher text.

## Fix (branch `plan-report-branch-PB3077`, cut from main 01f392184)
- `parse_report` reads the branch from the header's own FIELD first — `BRANCH_FIELD`, matched at a FIELD POSITION only:
  the start of a header line (`Branch: x`) or right after the template's ` · ` separator (`· **branch:** `x``) — and
  falls back to the first `worktree-…` word only on the header WITHOUT its review stamp lines (`REVIEW_LINE`);
  worktree and head are read from the unstamped header too, so no later shape of the stamp can feed them either.
  The first cut of this rule (03eea91cd) was unanchored, and the branch review's round 1 (R1-1) showed that real report
  prose says "this branch: every file …" (w1043x-PB2806 line 27, w1055z-PB2426): with no field, or with that prose
  above the field, it took `every` — the same ABSENT harm. Anchored, with an arm for each case.
- `test_plan_wave.py` arms: an O11 header with the stamp above the Branch field gives the field's branch, worktree and
  head; a template header with the stamp below its `**branch:**` field gives the field; a header with no field gives
  the first branch word outside the stamp; the stamp still parses beside the field; mid-prose `branch:` is not a
  field, with no field present and above the field alike.
- `review_findings.py` reuses `plan_wave.REVIEW_LINE` (one definition of "a review stamp line").
- Sweep: the readers of a report header are `plan_wave.parse_report`, `prune_worktrees.newest_report` (field-first
  already; its wider `\bbranch\b` rule is for membership, not identity, and stays) and `review_findings.stamp` (writes
  under Status, reads back through `parse_report`). No other script parses a branch out of a report.

## Why the stamp stays where it is
Moving the stamp below `Base:` would fix only reports stamped from then on and would put the review verdict out of the
header's first lines that `plan_wave.parse_report` and the operator read; the reader is the one place to make the
header's meaning explicit (the FIELD names the branch), and the arms above hold it.
