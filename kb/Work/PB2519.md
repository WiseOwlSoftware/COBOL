# PB2519

Filed from the PB1934 refuter (`E:\COBOL-coord\scratch\w1033-adj\PB1934-refute.md` section 4 and corrected decision item 3: "a Format 2 or Format 3 RECORD clause on a report FD bounds nothing"). The file names no harm flag; `wrong_answer: true` and `silent: true` reflect the observed over-long line with no EC.

**Observed (pinned build `pin-97006f3`; `E:\COBOL-coord\scratch\w1033-adj\PB1934-refute\pin\`).** `pv` (`RECORD IS VARYING IN SIZE FROM 1 TO 20`, CODE "A") and `p3` (`RECORD CONTAINS 1 TO 20`) both write the 25-character `A0123456789    ABCDEFGHIJ` with no EC. The record exceeds integer-3 / integer-5, while Format 1 (`RECORD CONTAINS 20`) cuts the line at the record.

**Expected from the spec (cite.py --check OK per the refuter).** `§13.18.43.4 GR7`: "Integer-3 specifies the maximum number of bytes in any record of the file"; `GR18`: integer-4 and integer-5 are the minimum and maximum record sizes; `§13.4.5.2` Format 3 carries `[ record-clause ]`; `§13.18.12.4 GR2`: the code characters are included in the logical record size. What becomes of columns past the maximum is `§A.1 159)` latitude (see `PB1934`), but the bound must be applied for every RECORD format, not only Format 1.

**Site (two-arm).** `src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs#ResolveReports` (about :4279): `model.LineWidth = model.File?.RecordContains is { } record ? Math.Max(1, record - (model.Code?.Length ?? 0)) : widest;` reads only the Format-1 `RecordContains`. The line width should come from the file's maximum record size for every format through the one rule. Related: `PB1934`.

## Landed (wave 1037 G, with PB1934) — one reading of the RECORD clause's upper operand

Re-probed before the fix: `pv` (RECORD IS VARYING IN SIZE FROM 1 TO 20, CODE "A") and `p3` (RECORD CONTAINS 1 TO 20, CODE "A") wrote the 25-character `A0123456789    ABCDEFGHIJ` with no cut; the Format 1 control cut at 20.
Root cause (the two-arm shape the note named): `DataBinder.Reports.cs#ResolveReports` read `File.RecordContains`, which only the Format 1 binder sets. It now reads `FileModel.RecordClause?.Upper`, the existing projection of all three formats (integer-1, integer-3, integer-5; §13.18.43.4 GR6, GR7, GR18). The other reader of the RECORD clause's maximum size (§14.9.30.4 GR6: "the maximum size established by the RECORD clause"), `DataBinder.cs` (the record-less FD's implied record, §14.9.30.4 GR6, ~2103), spelled the same thing `Varying?.Max ?? RecordContains`; it reads `RecordClause?.Upper` now too, so the rule exists in one place. A Format 2 clause with no TO phrase establishes no maximum (GR10 refers to record descriptions a report file does not have), so the width stays the widest item, as for an absent clause.
Both now write `A0123456789    ABCDE` (CODE plus 19 columns = 20 bytes).
Goldens (`tests/conformance/2002/`): `pb2519_record_varying_bounds_line`, `pb2519_record_contains_range_bounds_line`.
