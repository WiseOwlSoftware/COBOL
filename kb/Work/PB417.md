# PB417 — a rule about how many operands, checked by comparing parse text

Adjudicated in lane-3 batch b2 (`initialize-statement` part 1). All four probes **re-measured on HEAD
89044aa0**, including the positive control that proves the diagnostic is live.

## 1. The mechanism

`EcBinder.CheckCrossStatementBans`
(`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.ExceptionPerform.cs:273-279`) collects

```csharp
var names = ini.dataReferenceList().dataReference().Select(d => d.GetText().ToUpperInvariant()).ToList();
foreach (var dup in names.GroupBy(n => n).Where(g => g.Count() > 1))
    ctx.Edition.Error("COBOLNET1614", …);
```

and reports only when one **raw parse string** appears twice. Two independent things are wrong with that.

**First, the reading.** Every sibling rule in this family forbids a *multi-operand statement* in an
exception-checking PERFORM, and the general rule that motivates all of them gives INITIALIZE exactly the
multi-implicit-statement expansion — including the resumption point — that they exist for. On that reading
`INITIALIZE G H` in imperative-statement-1 is illegal and is accepted today.

**Second, and true under either reading, the KEY is wrong.** `GetText()` compares source spelling, so the same
data item written two ways escapes the test entirely: `INITIALIZE E(1) E(2)` and `INITIALIZE N OF G N IN G`
both pass. The rule needs the **resolved reference**, not the parse text.

The scoping and the diagnostic wiring are right — only the predicate is wrong, which is what makes this a
narrow, high-confidence fix.

"imperative-statement-1 in an exception-checking"), but the clause number was right:

```

OK  §14.9.10.3 4)  (Syntax rules)

$ python scripts/spec/cite.py --check 14.9.21.3 "An INITIATE statement that specifies more than one report-name-1 shall not be specified in an exception checking PERFORM statement"
OK  §14.9.21.3 3)  (Syntax rules)

$ python scripts/spec/cite.py --check 14.9.46.3 "A TERMINATE statement that specifies more than one report-name shall not be specified in an exception checking PERFORM statement"
OK  §14.9.46.3 3)  (Syntax rules)

$ python scripts/spec/cite.py --check 14.9.50.3 "A VALIDATE statement that specifies more than one identifier shall not be specified in an exception-checking PERFORM statement"
OK  §14.9.50.3 6)  (Syntax rules)

$ python scripts/spec/cite.py --check 14.9.27.3 "An OPEN statement that specifies file-name-1 more than once shall not be specified in imperative-statement-1 of an exception-checking PERFORM statement"

```

Note the family splits into two spellings: four rules say **"more than one"** operand outright; the OPEN rule
says **"more than once"**, and the INITIALIZE rule says **"only once"**. The OPEN and INITIALIZE spellings are
the ones the compiler implemented literally, and they are also the two the compiler keys on parse text. Whether
"specified only once" means one operand or no repeats is a genuine reading question — but it does not need
answering to act, because the text-key hole exists under **both** readings.

## 3. Expected vs observed, re-measured on HEAD

Compiler at 89044aa0, `--std 2023`, all four programs the same shape
(`PERFORM … INITIALIZE … WHEN EC-ALL CONTINUE END-PERFORM`):

```

exit=0   OK                             expected (family reading): rejected
$ cobol sr2_subscripted.cob --run     ← INITIALIZE E(1) E(2)

$ cobol sr2_qualified.cob --run       ← INITIALIZE N OF G N IN G
exit=0   OK                             expected (BOTH readings): rejected — one data item, two spellings
POSITIVE CONTROL, proving the check is live and correctly region-scoped:
$ cobol sr2_two_same.cob              ← INITIALIZE G G
exit=70  COBOLNET1614: identifier 'G' is specified more than once in an INITIALIZE in imperative-statement-1
         of an exception-checking PERFORM (ISO §14.9.20.3 SR2)
```

⚠ `INITIALIZE E(1) E(2)` deserves care: under the narrow reading, `E(1)` and `E(2)` are two **different**
occurrences, so a defensible reading says they are two references to the same *data-name* — which is what the
rule names ("identifier-1"). Under the family reading they are two identifier-1 operands and are barred
outright. Either way the current text key is not the rule's key; the qualified probe
(`N OF G` / `N IN G` — indisputably one data item, two spellings) is the unambiguous witness and is the one to
build the golden on.

## 4. The code site and the shape of the repair

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.ExceptionPerform.cs:273-279` (COBOLNET1614) and
`:283-289` (COBOLNET1616, the OPEN twin) — two copies of the same `GetText()`-grouped duplicate test.

The repair is one shared helper over **resolved** references, not two edited predicates: this method already
carries seven cross-statement bans for the same PERFORM region, five of which are plain
"more than one operand" counts (DELETE FILE, INITIATE, MERGE, TERMINATE, VALIDATE) and two of which are
"the same operand twice" (INITIALIZE, OPEN). Express the region-A ban as *(statement kind → operand-list
accessor → predicate)* rows and both spellings become table entries; then a new statement in this family is a
row rather than a copied block, and the resolved-reference key is written once. If the owner settles the
reading question toward the family, the INITIALIZE and OPEN rows simply switch predicate.

**Owner decision, not mine:** whether "specified only once" bars a second *distinct* operand. This note takes
no position and stays open either way — the text-key half is a defect under both readings, and the row's
verdict is PARTIAL either way.

## 5. The sibling sweep the fixer must do

* **COBOLNET1616, ten lines below**, implements the OPEN rule with the identical `GetText()` mechanism and
  inherits exactly the same hole. It is a different clause's row, so it needs its own verdict update — but it
  must be fixed in the same change or the note's "one rule, one place" repair is only half done.
* The other five bans in the same method key on statement presence, not on operand identity, so they are not
  affected — confirm by reading, not by assumption.
* Editions: the exception-checking (format 3) PERFORM depends on exception-names and RESUME, neither of which
  exists in COBOL-85, so the rule is vacuous at 85 and the gate sweep is 2002/2014/2023 only.
