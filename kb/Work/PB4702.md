# PB4702 — TruncatedQuotient past the 256-bit form: a wrong remainder though the quotient fits

**Sites:** `src/WiseOwl.Cobol.Runtime/Values/Numeric/CobolExact.cs:155` (`CobolExact.TruncatedQuotient`)

Reported by the branch review, not probed. R1-3, copied: when the dividend alignment leaves the 256-bit form, `TruncatedQuotient`
falls to the operands' 34-digit images, and the back-multiply overflows there too, so a quotient that FITS identifier-3 with no size
error still gets a wrong remainder. Not introduced by the PB4640 diff (the base build prints the same value) and within the
past-77-digits determination of DOC-A.1-123, though the dividend itself has only 75 digits. The review cited `CobolExact.cs:164`.

**Landed (wave 20261872, group A).** Re-probed on the build (`E:/COBOL-coord/scratch/w20261872a/pd/rem3.cob`): `DIVIDE FUNCTION ABS (A*A*A*K + 7) BY FUNCTION ABS (A*A*A) GIVING Q REMAINDER R2` with `Q`, `R2` `PIC 9(3)V9(28)` (A = 10^18 - 1, K = 999; the dividend aligned to 28 places is 85 digits) stored R2 = 0 on the main build and 7 on this one (999 x A^3 + 7 less 999 x A^3); Q is 999.0000000000000000000000000000 in both. Cause as the note says: `CobolExact.TruncatedQuotient` fell to the operands' 34-digit images when the dividend's alignment left the 256-bit form. Fix: that fallback is `CobolBig.DivTruncated`, the exact truncated quotient (PB4592's third form), so the subsidiary quotient and the nested quotient (`DivTruncated`) keep every digit at any size.

**Golden:** `conformance-suite/cases/14.9.12-DIVIDE/pb4702_remainder_dividend_past_the_wide_form` (2002, 2014, 2023), refused at 85 by `wiseowl/diagnostics/pb4702_remainder_dividend_past_the_wide_form_85.json`; unit `CobolBigExactFormTests.ArithmeticPastTheWideForm_IsExact` (the truncated quotient of 10^75 / 3 at 10 places).
