# PB3598 - the implicit bit filler has no storage in the ODO, dynamic-capacity and leaf-vector shapes

PB3564 gave the implicit filler after a USAGE BIT item a stored hidden field in the common shapes (`MOVE "AB" TO G1` then `DISPLAY G1`
now keeps `AB`). Its note registers three shapes as "not stored, reads zero as before" in prose only; this note makes them trackable
(PB3564 holds the prose, not a work item). Same defect: 8.5.1.6.3 makes the filler bits data, and a group MOVE (14.9.25.4) must carry
them.

1. A run holding an OCCURS DEPENDING bit table stores no tail, because the tail moves with the count (`BitLayout.HasFixedTail`;
   `GroupImageCodec.OdoPrefixImage` and the `FromVarImage` reader).
2. The elements of a dynamic-capacity bit table keep no padding (`GroupImageCodec.DynElementImage`).
3. A strongly-typed group carried as a leaf vector drops the filler (`RecordStructEmitter.EmitLeafMethods`).

## Fix shape (for the implementer)

State the filler per shape once: for ODO the tail is a function of the current count and travels with the prefix image; a dynamic
element image includes its pad; a leaf vector carries the filler positions `BitLayout.FillersOf` names. Reuse `FillerPositions` as the
single enumeration. Goldens per shape (MOVE of an alphanumeric to the group, then DISPLAY and a byte read), 2002/2014/2023. Run each
citation through `cite.py --check` first.

**Sites:** src/WiseOwl.Cobol.Compiler/Binding/Model/BitLayout.cs, src/WiseOwl.Cobol.Compiler/CodeGen/DataDivision/GroupImageCodec.cs, src/WiseOwl.Cobol.Compiler/CodeGen/DataDivision/RecordStructEmitter.cs

Lines: `GroupImageCodec.cs:400` (`OdoPrefixImage`), `:466` (`DynElementImage`), `RecordStructEmitter.cs:207` (`EmitLeafMethods`) on
main; `BitLayout.cs:342` (`HasFixedTail`) on PB3564's branch `worktree-wf_37d4041f-6f7-47` (87a2182c2; it replaced `StoresTail` there).

## Progress (2026-10-24, w20261024 group B) - shape 3 and the stored half of shape 1 landed; shape 2 and an owner question stay open

**Re-probe.** All three reproduced on a fresh build. Shape 1 (`N PIC 9`, `B PIC 1(2)`, `T PIC 1(3) OCCURS 1 TO 4 DEPENDING ON N`; `MOVE "3~~" TO G` then the third character): 125 where the rule requires 127, the two filler positions past the maximum extent were stored nowhere. Shape 3 (a strongly-typed group with a POINTER leaf, `INITIALIZE V1 WITH FILLER REPLACING BOOLEAN DATA BY B"1"`, `MOVE V1 TO V2`, DISPLAY): V1 `0xC0`, V2 `0x80`.

**Shape 3 (landed).** The leaf vector now carries the fillers after the members: `RecordStructEmitter.EmitLeafMethods` appends one string per `BitLayout.FillersOf` entry (its `__bf` field), `PlaceRenderer.CellLeaves` / `CellLeavesStore` append and store one per `BitLayout.WindowFillersOf` entry (a table's pad as every gap back to back), the two enumerating the same `FillerPositions` in the same order. Witness `LeafVectorFillerTests` (a unit test: the only portable reading of the filler of a pointer-bearing group is DISPLAY, whose pointer positions are implementor-defined, and a strong-group comparison, 8.8.4.2.12, was measured not to look at the filler). A struct-to-struct MOVE, a nested-program CALL (storage-area formals, both directions), a dynamic-capacity table of group elements (also under INITIALIZE ... WITH FILLER) and a nested group were probed.

**Shape 1 (the stored part landed).** A run holding an OCCURS DEPENDING table now has a stored tail field for the positions past its MAXIMUM extent (`BitLayout.FillerPositions` no longer skips the run: the tail is measured at the maximum count; `HasFixedTail` is deleted), which the run's packed image already had room for and no occurrence owns. Golden `14.9.25-MOVE/pb3598_odo_bit_run_tail_travels_with_the_group` (leg C3 reads 125 before and 127 after) and its negative. The rest of the shape is NOT a missing store but a conflict the note did not see: at a count below the maximum the filler that ends the current extent's last character lies in the first unused occurrence's storage, so the same bits are both filler (8.5.1.6.3, data of the group, moved as characters by 14.9.25.4 GR4) and an occurrence 13.18.38.4 GR8 a) leaves unused. The compiler's two receiving stores answer differently: an ordinary ODO group's (`PlaceRenderer.ReceiveInto`) splices a prefix of CHARACTERS, so the sender's filler wins; a variable-length group's (`OdoTail.KeepUnused`, the CALL carrier and the cell-backed group) splices at the BIT of the first unused occurrence, so the unused occurrence wins, which `_unassigned/pb3030_bit_odo_run_continuation` and `_unassigned/pb3030_bit_odo_variable_group` pin (`M ab 0 10111111`: "keeps the rest"). Making the second splice at the character turns both goldens (`10100001`, `10000011`) and overturns a recorded determination, so it was tried, measured and reverted: it needs an owner decision, or the heavier design in which the filler has storage of its own (a count-dependent tail field beside the occurrences, so both readings hold).

**Still open (shape 2, the owner question of shape 1, and one residue).**
1. The elements of a dynamic-capacity bit table keep no padding (`GroupImageCodec.DynElementImage` packs `Length` positions into `ceil(Length/8)` characters, the pad bits are zero and dropped on the way back). A fix needs the element's pad stored beside it: the element carrier is the boolean string every operation reads, so the pad cannot ride in it, and a parallel pad column would have to follow every capacity change of `CobolDynTable` (SET capacity, ALLOCATE, recreation, `CreatedAs`). The pad can only become non-zero through a READ of a variable-length record that holds such a table (a VLG moves only to a compatible group), so the harm is narrow. Too large to fold into this slice; no code written.
2. The owner question of shape 1 above: for a count below the maximum, do the bits that end the current extent's last character belong to the sender's filler (character splice, today's ordinary-group answer) or to the first unused occurrence (bit splice, today's variable-length-group answer, pinned by two goldens)? Whichever is chosen, the other lane and its golden change with it; the design that keeps both readings is a count-dependent tail field beside the occurrences.
3. INITIALIZE ... WITH FILLER over a run holding an OCCURS DEPENDING table resets the stored positions past the maximum extent, not the in-range filler that ends the current extent's last character (it lies in the first unused occurrence's bits, at a window whose offset moves with the count).

## Landed (2026-10-24, w20261032 group D)

**Re-probe (own build, base e20c6887b).** Shape 3 and the stored half of shape 1 still hold (golden `pb3598_odo_bit_run_tail_travels_with_the_group`, unit `LeafVectorFillerTests`). Shape 1 in a VARIABLE-LENGTH group did not: `S` and `R` each `DS PIC X DYNAMIC LENGTH`, `B PIC 1(2)`, `T PIC 1(3) OCCURS 1 TO 4 DEPENDING ON N`, the sender at count 3 with the filler past the maximum extent set to 10: `MOVE S TO R` left the receiver's filler 00 (second character 0x60 where 0x62 is required). Root: `OdoTail.KeepUnused` kept the receiver's bits from the first unused occurrence to the END of the member, so the stored tail was dropped at every count below the maximum (a cell-backed receiver, `StorageCell.StoreVarGroupAt`, and the CALL carrier share the method).

**The two questions the earlier landing left to the owner are answered by the standard, so no owner decision remains.** (a) The bits that end the current extent's last character at a count below the maximum are not filler: §8.5.1.6.3 generates the filler after "the last data item in a record", the table at its MAXIMUM, so they are the first unused occurrence's bits, whose content "is undefined" (§13.18.38.4 7)) and which §13.18.38.4 8) a) leaves out of the operation. The two receiving stores differ there only where the standard leaves the content undefined, which is implementor latitude: a group with no dynamic-length item or dynamic-capacity table is a fixed-length group (§8.5.1.12.1), so its move is §14.9.25.4 GR4's alphanumeric move of whole characters (the sender's bits), and a variable-length group moves by GR9 a) ("each character position that is not occupied by a corresponding table") — an OCCURS DEPENDING table is NOT a corresponding table (§8.5.1.12.2: "Two tables correspond if at least one of them is a dynamic-capacity table"), so GR9 a) moves every character position exactly as GR4 does, and the variable-length store keeping the unused occurrences' bits (the choice since PB3030, exercised by `pb3030_bit_odo_run_continuation`) is a latitude choice, not a rule path (branch review R1-1 corrected the first landing's reading, which had called it §14.6.9.2's table move). Both conform; no recorded determination changes. (b) INITIALIZE ... WITH FILLER therefore has no in-range filler to reset: the filler is the stored positions past the maximum extent, and a depending item inside the group makes the group a receiver at its maximum length (GR8 b)).

**Fix (shape 1, variable-length lane).** `OdoTail.KeepUnused` keeps the receiver's bits only from the first unused occurrence to the end of the table at its maximum extent (`CobolTable.TrimmedExtent`) or of the receiver's current characters, whichever ends first; the filler past the maximum that lies in the characters the receiver uses is the SENDER's (as a count at the maximum moves it), and the characters past the current extent are the receiver's own, whole. Golden `14.9.25-MOVE/pb3598_odo_bit_run_tail_variable_group` (legs V1 and V4, a working-storage and a cell-backed receiver, read 0x60 before and 0x62 after; V2 and V3 are the controls that kept passing) and its negative below 2014.

**Shape 2 (dynamic-capacity bit table element padding): DETERMINED, not stored.** The pad is out-of-line allocation slack and the rounding of the element's byte length, not a filler item: §8.5.1.9.1 3) makes dynamic-table storage non-contiguous and implementor-allocated (no "next item within that group" for §8.5.1.6.3 to align), §15.14.4 4) rounds a bit item's length up with no filler (§8.5.1.6.3's NOTE: none at a level 77 or 01 elementary item), and §14.6.9.2 moves a dynamic-capacity table element by element by the MOVE rules, so no operation carries the bits; INITIALIZE ... WITH FILLER, the one statement naming the implicit filler items, leaves them at zero (`DynamicBitElementPadTests`). Recorded in `docs/CONFORMANCE.md` USAGE BIT as a determination the owner may overturn; a stored pad would need a parallel pad column in `CobolDynTable` across every capacity change, EXTERNAL cell tables and BASED storage, for bits no statement can observe.

**Sites changed:** `src/WiseOwl.Cobol.Runtime/Values/OdoTail.cs`, `src/WiseOwl.Cobol.Compiler/Binding/Model/BitLayout.cs` (comment), docs `CONFORMANCE.md` and `DATA_MODEL_DESIGN.md`. Sibling sweep: the three consumers of `KeepUnused` (`GroupImageCodec` `OdoMemberTail.KeepUnusedOccurrences`, `StorageCell.StoreVarGroupAt`, the cell-backed variable-length store) read the one method; the ordinary group's `PlaceRenderer.ReceiveInto` is GR4's whole-character splice by design; `BitsWrite` (a GROUP-USAGE BIT group, exact bits) was not touched.

**Found while probing, not this group's (registered as PB3666, branch review R1-2).** A corresponding-table MOVE of an alphanumeric dynamic-capacity element into a USAGE BIT element stores the raw characters in the boolean carrier (`G2 TO G1`, T2 PIC X OCCURS DYNAMIC to T1 PIC 1(3) USAGE BIT OCCURS DYNAMIC: `DISPLAY T1 (1)` prints `Z00` for X"5A"). It is the elementary alphanumeric-to-boolean MOVE that PB3666 already carries (Table 16 admits it; the owner approved the fix 2026-10-24), reached through the element MOVE `MoveBinder.ElementMovesOf` binds with `BindMoveOf`, so the PB3666 fix at `MoveEmitter.CharacterStore` covers it; its sweep list now names the table-element path.
