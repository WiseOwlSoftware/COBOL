# PB3678 — node shape decides whether a parenthesized function is an expression or a function value

**Sites:** `src/Cobol.Net.Compiler/Binding/Bound/BoundTree.cs` (`BoundComputedOperand.IsNumericFunctionValue`),
`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/CallBinder.cs` (`CallBinder.ExpressionOperand`, the last arm),
`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs` (`ConditionBinder.CompoundOperand`, now internal),
`tests/Cobol.Net.Tests.Unit/GroupMoveSenderChannelDriftTests.cs` (`ParenthesizedFunction_IsAnExpression_TheTreeShapeIsNeverAsked`).

Filed 2026-10-24 by the enqueue unit's clerk from the PB3613 reviewer's R2-1 LEAD (low, not blocking at round 2),
branch `worktree-wf_6ffe8083-b46-11` (PR #535, open; PB3613 is held by it), report
`E:\COBOL-coord\scratch\reports\w20261032e-PB3613-report.md`. Not re-probed.

## What happens

`IsNumericFunctionValue` answers true for any numeric `BoundIntrinsicCall` and reads the `FunctionValue` flag only for
the other tree shapes. A parenthesized function is an arithmetic expression (`FunctionValue` false). When its intrinsic
lowers to a `BoundIntrinsicCall` the parenthesized form is accepted as a MOVE sender; when it lowers to a `BoundBinary`
it is refused. The node-shape dependence is what PB3613's R1-1 was about.

Measured by the reviewer: `E:/tmp/r3613r2/q2.cob`, `q3.cob`. `MOVE (FUNCTION MIN(N 3)) TO G` stores 15;
`MOVE (FUNCTION LENGTH(VG)) TO G` is refused COBOLNET1688.

## Fix shape

State the expression-versus-function-value fact once at bind time and read only that fact in `IsNumericFunctionValue`,
so the answer does not depend on how the intrinsic lowers. Which of the two outcomes ISO requires for a parenthesized
function as a group-move sender is a spec question the clerk did not judge.

## Landed

Re-probed on a fresh build (`E:/COBOL-coord/scratch/mythos/w20261500g/p1.cob`): `CALL ... AS NESTED USING BY CONTENT (FUNCTION MIN(N 3))` into a
plain-group formal compiled and stored 15, `(FUNCTION LENGTH(VG))` was refused COBOLNET1688, and `(N)` / `(+ N)` compiled too. (The note's
`MOVE (...)` does not parse: a MOVE sender is an identifier or a literal, so the lanes are CALL AS NESTED, Format-1 CALL and INVOKE. Format-1 CALL
refuses a parenthesized argument at bind, COBOLNET0899, and INVOKE already refused all three.)

Spec (the question the clerk left open): a parenthesized function is an arithmetic expression, not an argument that "consists merely of a single
identifier or literal" (§14.9.4.4 GR8, `cite.py --check` OK), and an arithmetic expression is no MOVE sender, so §14.8.2.2 rule 2 refuses it opposite
a group formal; docs/CONFORMANCE.md D-B4 already said only an arithmetic expression is refused. One outcome for every tree: REFUSED. The note's
`rejects_legal_source` premise was wrong (the parenthesized LENGTH refusal was right; the MIN acceptance was the under-rejection).

Fix: `IsNumericFunctionValue` reads only the binder's statement (`FunctionValue`, plus the call's result category), never the tree's shape. The
sibling arm was the same defect one level up: `CallBinder.ExpressionOperand`'s last arm mapped a bound `(C)` back to the item through
`IntrinsicBinder.OperandOf`; it now wraps the expression as the computed operand it is (`ConditionBinder.CompoundOperand`, PB1935's rule for
comparisons, shared). Goldens: `14.2-Procedure-division-structure/pb3678_parenthesized_{function,length,item}_group_formal_refused`,
`pb3678_parenthesized_function_numeric_formal` (+ `_below_2002`); drift pin `GroupMoveSenderChannelDriftTests`.

Left open (a different mechanism, reported as a lead): a parenthesized numeric LITERAL `(3)` / `(-3)` is still taken for the literal, because
`Gr8ArgumentLiteral.NumericText` recovers a literal from a computed operand for the BY VALUE `-1.234E-5` spelling and cannot tell a parenthesized one.
