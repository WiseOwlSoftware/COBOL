# PB5792 - 1985-GR-X.2.3.3-3: the rule says a contained program's object code is inseparable from its container's, which is a property of object code that no program can observe; the row has no witness and takes no verdict until a derivation or a decision closes it

**Decision (registered 2026-11-15 from the adjudication of the twenty rows and the refuter's second pass).** `1985-GR-X.2.3.3-3` gets NO case and NO record. The rule's subject is the implementation's object code, and no program can fail on it. The existing CALL case of a contained program must not be recorded as its witness.

**The text (each citation checked again with `python scripts/spec/cite.py --check`, verdict OK).**
- `§1985:X.2.3.3 GR3`: "The object code, resulting from compiling a source program contained within another program, is considered in these specifications to be inseparable from the object code resulting from compiling the containing program"
  `OK  §1985:X.2.3.3 GR3  (║2.3.3 General Rules║)  the text is in GR3`
- `§1985:II.6.4.1.2 SR4`: "A calling program may call a program which neither possesses the common attribute nor is separately compiled if, and only if, that program is directly contained within the calling program"
  `OK  §1985:II.6.4.1.2 SR4  (6.4.1.2 Scope of the CALL Statement)  the text is in SR4`

**Why no program witnesses it.** The adjudicator found no program that can fail on "inseparable" object code, and the refuter, trying to write one, found the same: every observable consequence (calling a contained program from its container, from a separately compiled program, CANCEL of the container) is governed by its own rule (`§1985:II.6.4.1.2 SR4`, `§1985:X.2.3.3 GR2`, the CALL and CANCEL rules), and a compiler that emitted a separately loadable but still reachable contained program passes them all. A case in which OUTERP CALLs the contained INNERP passes whether or not the object code is inseparable.

**Why the row takes no derivation as it stands.** The derivation schema bars the "definitional" arm for a rule whose subject is the implementation or the implementor (DESIGN-spec-conformance-review.md section 1.1: "A rule whose subject is the implementation or the implementor is never this arm"). An argued derivation (`unpopulatable-antecedent` or `indistinguishable-consequent`) would need its own refuter pass. The compiler's behavior is not in question: one assembly, the contained program a nested class (`src/WiseOwl.Cobol.Compiler/CodeGen/ProgramEmitter.cs#EmitProgramClass`), so the rule holds in substance.

**What closes the row.** Either an argued derivation ("no program can observe the property") with a refuter pass under section 1.1, or an owner-visible decision that the conformance register states the rule as not observable. The 2023 counterpart restates the rule for executable code and has no catalog row until PB5451: `§2023:10.4`: "The executable code resulting from compilation of a contained source unit is considered inseparable from the executable code resulting from compilation of the containing source unit."
  `OK  §2023:10.4  (Contained source units)  the text is in the clause`
