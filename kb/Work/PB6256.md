**Rule it breaks:** §2023:8.8.4.2.4 compares numeric operands by algebraic value, and §2023:8.3.3.6.4 GR4 makes ZERO the numeric value 0 in a numeric context, so IF X = ZERO and IF X = 0 are one comparison; the file own one-comparison-rule doctrine (RelationCategories/ForComparison comments, kb/Work PB741 two-arm shape) forbids a second spelling

**Scenario:** RenderRelational routes every figurative operand to RenderFigurativeRelational (ConditionRenderer.cs:343). With ZERO opposite a numeric anchor it takes the tail at :617-621: FigOrNum calls num.AsNum WITHOUT keepWide, then Align(l, s) on both sides. Align (NumericRenderer.cs:1549-1568) lands a Dec through DecToUnscaledIntermediate, which RAISES EC-SIZE-OVERFLOW past the Int128 carrier, and a U value through DeU/NumWiden, loud at 2^127 and above. So IF A * B = ZERO over PIC 9(30) items each holding 1E29 (product 1E58, which PB1900 compares exactly) raises a fatal size error at 2002+, while IF A * B = 0 answers FALSE through CompareWide/CobolDec.Compare (:502-525); an unsigned 16-byte COMP-5 holding 2^127 or more is loud against ZERO but compares by value against 0 through NumCompareU (:530). The float arm at :618 also skips the PB5835 NativeArithmeticComparison gate and the STANDARD-DECIMAL lift that :517 applies. Same COBOL meaning, a different answer or an abend, depending on whether the program wrote ZERO or 0.

**Measured how:** R2 batch finding `codegen-2--code--f1#1` (pair codegen-2--code), read in the pinned tree at 9e65164eb3a9; skeptics rule upheld, scenario upheld, site upheld.

**Spec:** §2023:8.8.4.2.4 "a comparison is made with respect to the algebraic value of the operands" (`cite.py --check` passed at collection); §2023:8.3.3.6.4 "The zero format represents the numeric value" (`cite.py --check` passed at collection); §2023:8.8.4.2.4 "For operands whose class is numeric, a comparison is made with respect to the algebraic value of the operands regardless of the manner in which their usage is described" (`cite.py --check` passed at collection); §2023:15.67.4 "The returned value is the numeric value represented by argument-1" (`cite.py --check` passed at collection)

**Target:** One numeric comparison: when ZERO stands opposite a numeric anchor, RenderFigurativeRelational hands the pair to RenderNumericRelational with ZERO rendered as the numeric literal 0 (the GR4 reading), and FigOrNum with its private Align/Real tail is deleted, so every numeric relation shares the wide, Dec, U and native-arithmetic arms

**Design reference:** DESIGN-architecture-review §8.

**Also found as** (the same mechanism, merged before filing; every provenance kept):

**Landed (PB6256):** `RenderFigurativeRelational`'s numeric tail and `FigOrNum` are deleted; ZERO opposite a numeric anchor now takes `RenderNumericRelational` (NumericRenderer reads ZERO as the unscaled integer 0). The re-probe also found the unsigned-wide arm emitting an ambiguous `CobolNum.CompareU` call for any bare-literal operand (`IF U = 0` as well as `IF U = ZERO`, CS0121), fixed in the same arm by typing the signed side `(Int128)`.
