# PB3419 — the LaneTick comment names STOP-UNIT as a landing hold

A lead from the branch review of `notes-pb3381-leads-pb3380-landed-20261018` (R1-1; findings file
`E:\COBOL-coord\scratch\review-notes-pb3381-leads-pb3380-landed-20261018.jsonl`; report
`E:\COBOL-coord\scratch\reports\w1127w-PB3402-report.md`). Severity low, a stale comment.

**Applies once PB3402 is on main.** That branch carries the PB3402 fix (owner 2026-10-18 ~23:58, "Stop the soft cap from
holding landings"): `land_lane.py` `stop_reason` reads `scratch\STOP-loop` in place of `STOP-UNIT`. It is not on main at
0eba56a75, so this note must not be fixed before it lands: the corrected comment would describe behaviour main lacks.

**Code site** (re-read on origin/main 0eba56a75): `scripts/orchestrator/orchestrate.ps1:194`, the comment block above
`$script:LaneTick`: "The tick itself starts nothing once STOP-UNIT, STOP or the owner's global stop exists".

cap's pair and the owner's global STOP) and HALT do. An operator who creates STOP-UNIT by hand to pause landings, trusting
this comment, sees them go on.

**Fix.** After PB3402 lands, reword the comment to name the stop files `land_lane.py` `stop_reason` actually reads, and
sweep the other prose that says STOP-UNIT holds the lane (`git grep -n "STOP-UNIT" -- scripts docs`).
