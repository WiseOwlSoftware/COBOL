# PB5464 - a test case that reddens two landings is surfaced by nothing

**Sites:** `scripts/orchestrator/land_lane.py:816` (`classify_red`), `scripts/orchestrator/land_lane.py:1030` (the
`landing_measure.record_red` call), `scripts/orchestrator/landing_measure.py:259` (`record_red`),
`scripts/orchestrator/landing_measure.py:428` (`summarize`, the "merge-queue reds by class" row), `scripts/session-probe.ps1`.

**What the code does (read at f9d3265063).** The landing lane classifies each merge-queue red (`classify_red`) and
records it once per run with `record_red`: `{run, class, why, act, ok, at}`. The red test cases are not a field: they
appear only inside the `why` sentence, cut to 240 characters and to the first `NAMED` cases ("every red case (1:
WiseOwl.Cobol.Tests.Unit.GrammarDiagramGeneratorDriftTests.Generator_RunsClean) ran GREEN in the branch's gate ..."). A
`RUNNER` (and `INFRA`) red is re-queued once with no agent and filed as the `infrastructure` bounce cause. The only view,
`landing_measure.py summary`, prints the reds' counts by class ("merge-queue reds by class (PB4271)"). No view groups the
reds by test case, and `scripts/session-probe.ps1` reads none of this record (no line names `landing_measure` or `reds`).

**The red that showed it.** `GrammarDiagramGeneratorDriftTests.Generator_RunsClean` reddened #1580 (run 43327928785,
2026-11-12 15:38 PST) and #1590 (run 43412496532, 2026-11-13 03:30 PST), both RUNNER, both re-queued (kb/Work PB5463).
The record of #1590 says "the same case bounced #1580", but that clause is not what `classify_red` writes: a session
added it by hand. Earlier, `MessagingPeerTests.ANotifySocketThatRefusesIsAStartFailureAndEveryStatementIsImpWithTheReason`
reddened #1260 twice in fifteen minutes (2026-11-06 19:03 and 19:18) and `NistDifferentialTests_P1.NistProgram_MatchesGolden(NC201A)`
reddened #1463 twice (2026-11-10 06:31 and 06:46), each RUNNER. Nothing printed any of the three repeats.

**Harm.** CLAUDE.md, Testing: "a flake is a kb/Work defect fixed at its root, never retried inside the run". The lane's
re-queue is right for one red. A second red of the same case is a flake with a rate, and the record that holds that
rate is read by nobody: the flake is found only when a session happens to read two runs' logs.

**Shape (the fixer decides).** Record the red cases as a field of each red (`cases: [...]`, every case, not the first
`NAMED`), validated by `validate`; one function in `landing_measure` that returns every case red in two or more runs
within a window, with the runs and pull requests; a `summary` row and a session-probe line that print it (the probe is
where the owner and every session read state); a self-test case with two runs of one case. Optionally, the lane wakes a
filer or refuses the second re-queue of the same case. Too large for the PB5463 branch: a schema field, its validation,
two views and a probe line across three files in the tooling lane, where PB5463's change is one test file.
