# PB3492 — DELETE FILE after a CLOSE under commit control is refused '62' by the connector's own kept handle

From the PB3483 implementer report (`E:/COBOL-coord/scratch/reports/w1140d-PB3483-report.md`, `## New defects` 1). Wrong answer: DELETE FILE on a file whose connector was CLOSEd under commit control answers '62'.

**Mechanism.** In the `FileRegistry.cs` DELETE FILE retry loop, the `HostFile.IsHeldByAnother(c.HostPath)` arm (about line 865) sees the connector's own kept handle as another's: on Windows through the share mode, on Unix through the `flock` LOCK_EX probe against the kept LOCK_SH. It shares its root with `FileConnector.HeldByAnotherHandle`.

**OWNER DECISION NEEDED.** What DELETE FILE does to a standing transaction (the kept locks and handle a CLOSE under commit control leaves until COMMIT or ROLLBACK, §14.9.7.4 GR4) must be decided before this can be fixed: refuse, roll back and delete, or delete and keep the transaction. Spec leads: §14.9.10.4 and §14.9.36.4 GR3 (cite-check before use). The register cannot mark this blocked (no open note carries the decision), so the fix waits on that decision by this paragraph: it is to be put to the owner as a bare question with the options laid out.

**Sites:**
- `src/Cobol.Net.Runtime/IO/FileRegistry.cs`

## Re-probed and SETTLED (wave 1157, group A, 2026-10-23)

**No owner decision is needed: the standard answers it.** The NOTE under §14.9.10.4 GR15 (`cite.py --check 14.9.10.4 "Such
files can still be deleted"` → OK, rule 15): *"For file connectors subject to APPLY COMMIT clauses, while those APPLY COMMIT
clauses remain active, then file and record locking persists. Such files can still be deleted, however if they are, then in
the event of a rollback they will be restored to the state they were in at the last commit or, if none, the start of the run
unit."* GR15's conflict is a file *"locked by another file connector"*, and the connector's own kept handle is not another's.
So the DELETE FILE proceeds and the transaction stands: ROLLBACK restores the file, COMMIT keeps it deleted. The design is
`docs/rearchitecture/DESIGN-runtime-library.md` 2.2.2.14: the keyed organizations' two capture verbs ride kb/Work PB3340's
journal (the before file copied through the kept handle, the `K` record, then the removal), so this note is implemented with
or right after PB3340's journal.

**A sibling with the same root, found by the re-probe:** an OPEN OUTPUT of an EXISTING keyed file under commit control is not
undone by a ROLLBACK either. `KeyedConnector.Recreate` ends the kept transaction when the creation lands (2.2.1.10, kb/Work
PB3493), so nothing is left to roll back. Both verbs replace the whole physical file and need the capture.

Probe (07bfc3606, this branch's build): the program below prints

```
SECOND OPEN OUTPUT FS=00
RECORD 1 ABSENT FS=23
RECORD 2 ABSENT FS=23
DELETE AFTER CLOSE FS=62
```

Expected from §14.9.36.4 GR3 and the GR15 NOTE: `RECORD 1=AAAA` (the state at the COMMIT), `RECORD 2 ABSENT`, and the DELETE
FILE `00`.
