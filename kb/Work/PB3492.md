# PB3492 — DELETE FILE after a CLOSE under commit control is refused '62' by the connector's own kept handle

From the PB3483 implementer report (`E:/COBOL-coord/scratch/reports/w1140d-PB3483-report.md`, `## New defects` 1). Wrong answer: DELETE FILE on a file whose connector was CLOSEd under commit control answers '62'.

**Mechanism.** In the `FileRegistry.cs` DELETE FILE retry loop, the `HostFile.IsHeldByAnother(c.HostPath)` arm (about line 865) sees the connector's own kept handle as another's: on Windows through the share mode, on Unix through the `flock` LOCK_EX probe against the kept LOCK_SH. It shares its root with `FileConnector.HeldByAnotherHandle`.

**OWNER DECISION NEEDED.** What DELETE FILE does to a standing transaction (the kept locks and handle a CLOSE under commit control leaves until COMMIT or ROLLBACK, §14.9.7.4 GR4) must be decided before this can be fixed: refuse, roll back and delete, or delete and keep the transaction. Spec leads: §14.9.10.4 and §14.9.36.4 GR3 (cite-check before use). The register cannot mark this blocked (no open note carries the decision), so the fix waits on that decision by this paragraph: it is to be put to the owner as a bare question with the options laid out.

**Sites:**
- `src/Cobol.Net.Runtime/IO/FileRegistry.cs`

## Re-probed and SETTLED (wave 1157, group A, 2026-10-23)

**No owner decision is needed: the standard answers it.** The NOTE under §14.9.10.4 GR15 (`cite.py --check 14.9.10.4 "Such
files can still be deleted"` → OK, rule 15): *"For file connectors subject to APPLY COMMIT clauses, while those APPLY COMMIT
clauses remain active, then file and record locking persists. Such files can still be deleted, however if they are, then in
the event of a rollback they will be restored to the state they were in at the last commit or, if none, the start of the run
unit."* GR15's conflict is a file *"locked by another file connector"*, and the connector's own kept handle is not another's.
So the DELETE FILE proceeds and the transaction stands: ROLLBACK restores the file, COMMIT keeps it deleted. The design is
`docs/rearchitecture/DESIGN-runtime-library.md` 2.2.2.14: the keyed organizations' two capture verbs ride kb/Work PB3340's
journal (the before file copied through the kept handle, the `K` record, then the removal), so this note is implemented with
or right after PB3340's journal.

**A sibling with the same root, found by the re-probe:** an OPEN OUTPUT of an EXISTING keyed file under commit control is not
undone by a ROLLBACK either. `KeyedConnector.Recreate` ends the kept transaction when the creation lands (2.2.1.10, kb/Work
PB3493), so nothing is left to roll back. Both verbs replace the whole physical file and need the capture.

(R4), `Commit` and `Rollback` over `IHostMedium`, the entry step and the settle, all witnessed over the fault-injecting medium.
What remains is design 2.2.2.14's keyed half, and this note now claims the three inventory rows it holds PARTIAL
(GR-9.1.18.4-p1, GR-9.1.18.5-p1, GR-14.9.36.4-3):

1. `FileRegistry.DeleteFile` for a `KeyedConnector { CommitControlled: true }`: the shape of
   `FileRegistry.DeleteCoveredSequential` (the entry mutex, the holdings and GR15 tests with the kept handle given back, the
   journal begun START `P`, `Capture(DeleteFile)` through a copy handle, the kept handle closed, the removal and its directory
   sync) - the '62' this note reported disappears with it.
2. `KeyedConnector.Recreate` (an OPEN OUTPUT over a kept state): capture before the creation instead of ending the kept
   transaction (`ReleaseKept`), the captured transaction going with the before file.
3. The ROLLBACK of a captured keyed file: `SequentialJournal.Rollback`'s step (1) restores the before file; then the restored
   store is adopted again from the file (its pages changed under the run unit's cache) and the run unit's own transaction in
   it is rolled back (its TRANSACTIONS tree names it) BEFORE the journal's `D R` - the journal's rollback sequence needs a hook
   for that between its restore and its decision. The entry step's settle of a dead owner's keyed capture runs before
   2.2.1.10's dead-owner step reads the restored store.
4. Witnesses: the probe above as a golden (`RECORD 1=AAAA`, `RECORD 2 ABSENT`, `DELETE AFTER CLOSE FS=00`), the keyed rows
   through `FaultHostMedium` (`SequentialCommitControlTests` is the pattern), 2.2.1.16's OPEN OUTPUT rows and a DELETE FILE row
   amended; then the three rows re-verdicted CONFORMS.

## Landed (wave 20261028 group A, 2026-10-24)

Re-probed on this branch's base (9f815f941): the probe above printed `RECORD 1 ABSENT FS=23` and `DELETE AFTER CLOSE FS=62`, and
a sibling with the same root reproduced: an OPEN OUTPUT that CREATES a keyed file under commit control, then ROLLBACK, left the
file in place (`OPEN INPUT` of it as OPTIONAL answered `00` where §14.9.36.4 GR3's state at the start of the run unit had no
file, `05`). After the fix the probe prints `RECORD 1=AAAA`, `RECORD 2 ABSENT FS=23`, `DELETE AFTER CLOSE FS=00`, and the
creation probe `05`.

The fix is DESIGN-runtime-library.md 2.2.2.14 as built (the design paragraph now describes it):

- `FileConnector` carries `CommitControlled`, the run unit's journals (`Transactions`) and the ENTRY STEP for every organization
  (`EnterPhysicalFile`, hoisted from `SequentialConnector`; `KeyedConnector`'s own flag deleted), so a keyed writable OPEN settles
  a dead run unit's capture before the store's dead-owner step reads the file.
- `KeyedConnector.JournalCapture` copies an EXISTING file through the OPEN OUTPUT's own handle into the journal's before file (R4)
  before the creation; `JournalCreation` begins START `A` before the handle creates an absent file; `AbandonOpen` WITHDRAWS a
  journal the OPEN began when the file was not affected (GR25: the kept transaction stands, kb/Work PB3493's refused-creation test
  unchanged); a covered re-OPEN takes a read-write handle while a replaced journal stands.
- `FileRegistry.DeleteCovered` (both organizations; was `DeleteCoveredSequential`): the kept handle is given back for the GR15 probe
  and the removal, and the Table 19 column lock with it (`GiveBackForRemoval`) — the Windows column holder is a handle on the file,
  which refused the removal and was the '62' of the probe; the same defect for a sequential connector under `SHARING WITH READ ONLY`
  or `ALL OTHER` is fixed by the same change. An uncovered DELETE FILE now runs the entry step too (`JournalHoldsAgainstDelete`).
  Branch review R1-1: what the DELETE FILE gives back is TAKEN BACK by every attempt and step that does not remove the file
  (`GiveBackForRemoval` returns a `RemovalGiveBack`; `RunUnitFileLock.Suspend`/`Resume`), so an unsuccessful DELETE FILE leaves the
  file and the transaction (its liveness byte) as the CLOSE left them; the keyed transaction ends with the removal itself.
- `FileRegistry.CommitKeyed` promotes the keyed transaction in the file as it stands (a store left with no writable file is
  refused, never forgotten: review R1-1), then decides the journal; `RollbackKeyed` restores the before file and, before `D R`,
  every store of the run unit adopts the restored file and runs the dead-owner step (`KeyedStore.AdoptRestored`), which rolls
  back the captured transaction. The keyed transaction and the journal are one `TransactionHolder`. A creation's ROLLBACK removes
  the file under a connector still OPEN too (review R1-2, GR3): the connector stays open on no file
  (`KeyedConnector.LeaveTheRemovedFile`) and its next WRITE creates the file again (`WriteCreatingTheFileAgain`); the sequential
  twin's Table 19 column now leaves the file at that removal as well (it refused the ROLLBACK '30' under ALL OTHER on Windows).
