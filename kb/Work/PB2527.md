# PB2527 — three serial corpus partitions set the Conformance wall

## Measured (w1033 gate performance diagnosis, section 2, `conf-timeline.txt`, `simulate.py`)

The Conformance leg is 32-wide for about 160 s (workstation GC; about 90 s with Server GC), then spends **95-220 s at 1-4
threads**: `CorpusRunnerTests` is split into only 3 partitions of about 1,546 cases each and xunit v2 runs one class as
one serial collection, so each partition's 246-282 s is the wall. The next poles are `OptionalWordSubsetDriftTests`
(23 rows in one class, 131-152 s span, one row 59 s), `IntrinsicFunctionDifferentialTests` (~100 s) and
`UsageInheritanceDriftTests` (~105 s). `simulate.py` replays measured per-test durations onto 32 workers and reproduces
the real makespans (247 s modeled vs 255 s measured). With Server-GC durations: corpus 3 to 24 partitions 212 s in name
order, **162 s longest first**; plus `OptionalWordSubsetDriftTests` split 8 ways, **118 s** longest first (the floor,
sum/32, is 117 s).

## Mechanism

`tests/Cobol.Net.Tests.Conformance/CorpusRunnerTests.cs` declares three partition classes (`CorpusRunnerTests_P0..P2`);
`OptionalWordSubsetDriftTests` is one class; collections start in the order xunit enumerates them, so a long partition
that starts late finishes late.

## Shape

The existing `TestPartitioning` mechanism with 24 corpus partitions and an 8-way split of `OptionalWordSubsetDriftTests`;
the partition classes ordered so the longest collections start first. The partition count and the order are asserted by
a drift test, and the population union stays EXACTLY the discovered population per platform (`test_population.py`, CI's
shard assertion, `TestPartitionAudit`).
