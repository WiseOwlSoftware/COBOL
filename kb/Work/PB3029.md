# PB3029 — LF is the one line ending; the working tree stops lying about the commit

**Owner, 2026-10-11 ~12:35 PDT, verbatim:** "We should probably standardize on a single line-ending format. CRLF vs
others keeps biting us." Format chosen (a routine call, stated so the owner can overrule it): **LF** — CI's Linux jobs,
WSL, bash and the Workflow tool already require it; `.gitattributes` already forces it for `*.sh` and the workflow `.js`
files after each bit (CRLF'd scripts refused as "control characters", `set -u\r` failures in every fresh worktree,
kb/Work PB1732, wave 72 G); the DEVLOG's CRLF exception needed a byte-splicing insert script (`prepend-devlog.py`) and
a mangled-backslash hook; the forbidden-commands hook blocks heredocs for the same family of reasons.

**Measured 2026-10-11 (`git ls-files --eol`, this worktree):** index `lf` / working tree `crlf`: **15,234** files; `lf`/`lf`
189 (the `.sh`/`.js` under `eol=lf`); `-text` 22 (binaries and DEVLOG.md); index `crlf` 2; `mixed` 2; `core.autocrlf=true`
from the system gitconfig. So the object database is ALREADY LF; what differs is what each OS reads from the same
commit — the exact shape of "keeps biting us": a Windows gate and a Linux gate test different bytes (goldens `.out`/`.err`
2,401 + 1,851 files, `.cob` fixtures 5,466, `.md` 2,611, `.cs` 1,374, `.py` 202, `.ps1` 43).

**Design:** `DESIGN-test-build-ci.md` §3.17.4 (conflict-free landing files) names this note; it is a precondition of
the DEVLOG migration (PB3025 writes LF) and of generated views (PB3026).

## What changes
1. `.gitattributes`: `* text=auto eol=lf` as the first rule (the per-pattern `eol=lf` lines become redundant and go; the
   binary patterns stay `-text`/`binary`); `DEVLOG.md -text` goes with PB3025's migration (the per-entry files are LF).
   Anything that MUST be CRLF is named explicitly with its reason (today: nothing is known; `.bat`/`.cmd` would be).
2. One normalization landing: `git add --renormalize .` (the 2 `crlf` and 2 `mixed` blobs change; nothing else does in
   the index), plus `git config merge.renormalize true` written into the repo's documented setup (`scripts/setup-*.ps1`,
   CONTRIBUTING) so every open branch rebases across it without line-ending conflicts; every worktree's files flip to LF
   at its next checkout (`git checkout -- .` after fetching) — the landing's DEVLOG entry tells the in-flight agents.
3. Tools write LF: the Write/Edit tools and every script that writes a tracked text file (`python` `write_text`,
   PowerShell `Set-Content`, `prepend-devlog.py` until PB3025 deletes it, the generators) use `newline=chr(10)` / `-NoNewline`
   + explicit LF; a drift check (`LineEndingDriftTests` or a script self-test run by every gate and by CI's audits) fails
   when any tracked text file in the index or the working tree contains a CR. The pre-commit path is `git diff --check`
   plus that check in `enqueue.py` (PB3023).
4. Windows legs must stay green after the flip: a test that compares a golden byte-wise with program output produced
   with `Environment.NewLine`, or a fixture reader that assumes CRLF, is a defect to fix in the same landing (sweep:
   `grep -rn "Environment.NewLine\|\\r\\n" tests src --include=*.cs` triage; CI's Windows runner checks out with the same
   attributes, so CI and the box agree again). PB1957 gains the row "line endings: (a) made identical".
5. Hooks and skills that exist only because of CRLF (`forbidden_commands.py`'s heredoc-backslash arm is about shell
   mangling, not CRLF — it stays; the `devlog_line_endings` memory and `tool_writes_can_corrupt_bytes` are updated in the
   memory, outside the repo) are reviewed; `reference_devlog_is_crlf` becomes false when PB3025 lands.

**Not blocked.** Lands early in the campaign (before PB3025's migration, so the migration writes LF once).
**Code sites:** `.gitattributes`, `scripts/prepend-devlog.py`, `scripts/spec/*.py` writers, `scripts/orchestrator/*.py` writers,
`scripts/*.ps1` writers, `tests/Cobol.Net.Tests.Unit/*DriftTests.cs` (new `LineEndingDriftTests`), `CONTRIBUTING.md`, `docs/rearchitecture/DESIGN-test-build-ci.md` §3.17.4.
