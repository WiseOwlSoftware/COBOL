# PB3881 — exception-file-n-not-implemented-at-run-time: FUNCTION EXCEPTION-FILE-N compiles under -std=cobol2014 but the run aborts: 'attempt to use non-implemented function'

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S2) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\exception-file-n-not-implemented-at-run-time.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\exception-file-n-not-implemented-at-run-time\`.

## Summary

GnuCOBOL 3.2 under `-std=cobol2014` compiles a reference to the standard intrinsic function EXCEPTION-FILE-N with no
diagnostic, and the run ends at the call with `libcob: error: attempt to use non-implemented function`, exit code 1.
The default dialect refuses the same source at compile time (`FUNCTION 'EXCEPTION-FILE-N' is not implemented`): the
`-std=cobol2014` (and `-std=cobol2002`) word list re-activates a function that cobc's own table marks as not
implemented. Verdict: GNUCOBOL-DEFECT. Class: compiles but is not implemented at run time. Edition: 2014.

## Expected result (per ISO)

The program is legal and its run displays `[00]` (two national zeros) and then `END`.

- §15.29.1 (checked): "The EXCEPTION-FILE-N function with no argument specified returns a national character string
  that is the I-O status value and file-name of the file connector, if any, associated with the last exception status".
- §15.29.4 1) a) (checked): "If the last exception status is not an EC-I-O exception condition, the returned value is
  two national zeros." The program raises no exception condition before the call.
- §4.2.2 (checked): the implementation shall provide the functionality of every required element; EXCEPTION-FILE-N is
  not listed in A.3 or A.4.

GnuCOBOL's own alphanumeric twin, FUNCTION EXCEPTION-FILE, returns `00` in the same position under the same flags
(work\exception-location-n-not-implemented-at-run-time\elx.cob, output `[00]`, exit 0), which is the value this function owes in national characters.

Edition: The no-argument form used here is the 2014 form. §E.3.3 26) (checked): "FUNCTION
EXCEPTION-FILE-N. An optional argument has been added to this function ... while leaving the original feature unchanged
when no argument is supplied." The function therefore existed in 2014 without an argument; only the argument is new in
2023.

Citations inherited from the night records: The slice's §15.29.4 1) a) checks and is used. Its second citation, §14.6.13.1.1, concerned the witnesses' file-status 35 OPEN and is not needed for this program, which has no file. The slice's needs_judgment (one witness record names both EXCEPTION-LOCATION-N and EXCEPTION-FILE-N) is resolved by reducing each function to its own program; EXCEPTION-LOCATION-N has its own record.

Edition as recorded by the adjudicator: 2014. `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Fix site (GnuCOBOL 3.2 source, read observationally)

In `gnucobol-3.2` (read observationally; identifiers only):

The function is declared in the compiler's intrinsic table as known but not implemented, and libcob carries only a
stub, but the `-std=cobol2014` word list re-activates it, so the compile-time refusal that cobc has for such functions
never fires:

- `cobc/reserved.c`, `function_list[]`, the `EXCEPTION-FILE-N` entry (line 3407): its `active` member is `CB_FEATURE_NOT_IMPLEMENTED`.
- `cobc/tree.c`, `cb_build_intrinsic` (line 7030): a function whose entry is `CB_FEATURE_NOT_IMPLEMENTED` is refused with
  `FUNCTION '%s' is not implemented`. This is the diagnostic the default dialect prints.
- `config/cobol2014.words`: line 535 `not-intrinsic-function: DIALECT-ALL`, then line 555 `intrinsic-function: EXCEPTION-FILE-N`
  (`config/cobol2002.words` has the same pair, line 534 and line 553).
- `cobc/reserved.c`, `change_intrinsic` / `set_intrinsic_mode` (line 4979): the DIALECT-ALL deactivation moves the
  entry from `CB_FEATURE_NOT_IMPLEMENTED` to `CB_FEATURE_DISABLED`; the later activation then moves it from
  `CB_FEATURE_DISABLED` to `CB_FEATURE_ACTIVE`. The function's own FIXME comment (line 4981) names this
  not-implemented, disabled, active sequence as unhandled. After it, `cobc -std=cobol2014 --list-intrinsics` reports
  the function as implemented ("Yes") and `cb_build_intrinsic` accepts it.
- `libcob/intrinsic.c`, `cob_intr_exception_file_n` (line 7112): calls `error_not_implemented` (line 3135), which sets
  `EC-IMP-FEATURE-MISSING` and calls `cob_fatal_error (COB_FERROR_FUNCTION)`; `libcob/common.c`, `cob_fatal_error`
  (line 9109) prints `attempt to use non-implemented function` and ends the run with exit code 1.

Two fixes are possible, and they are independent: (a) make `set_intrinsic_mode` keep `CB_FEATURE_NOT_IMPLEMENTED`
through a DISABLED-then-ACTIVE sequence, so that every dialect refuses the function at compile time, as the default
dialect already does; (b) implement `cob_intr_exception_file_n`. The alphanumeric twin `cob_intr_exception_file` (line 4164) is implemented and returns `00` for the same program state (probe below); the national function is that value as national characters.

The same mechanism covers all six functions of this group (BOOLEAN-OF-INTEGER, CHAR-NATIONAL, EXCEPTION-FILE-N,
EXCEPTION-LOCATION-N, INTEGER-OF-BOOLEAN, STANDARD-COMPARE; records in this directory), so fix (a) is one change
for all of them and one upstream ticket can carry all six repros.

## Draft issue

**Title:** FUNCTION EXCEPTION-FILE-N compiles under -std=cobol2014 but the run aborts: 'attempt to use non-implemented function'

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1), Linux x86_64.

Steps:

    cobc -std=cobol2014 -fformat=free -x -o efn efn.cob
    ./efn

with efn.cob:

```
IDENTIFICATION DIVISION.
PROGRAM-ID. EFN.
PROCEDURE DIVISION.
    DISPLAY "[" FUNCTION EXCEPTION-FILE-N "]"
    DISPLAY "END"
    STOP RUN.
```

Observed: the compile succeeds with no diagnostic (also with -fsyntax-only -Wall). The run prints nothing from the
DISPLAY statement and ends with exit code 1:

    libcob: error: attempt to use non-implemented function

Without -std (default dialect), the same source is refused at compile time:
`efn.cob:4: error: FUNCTION 'EXCEPTION-FILE-N' is not implemented`. `cobc -std=cobol2014 --list-intrinsics` lists EXCEPTION-FILE-N as
implemented ("Yes"); plain `cobc --list-intrinsics` lists it as "No".

Expected: the program is valid COBOL 2014 (FUNCTION EXCEPTION-FILE-N with no argument, ISO/IEC 1989
15.29). No exception condition has been raised, so per 15.29.4 rule 1a the result is two national zeros; the run should
display `[00]` and then `END`. (GnuCOBOL's FUNCTION EXCEPTION-FILE returns "00" in the same place.)

Cause, as far as we can see: config/cobol2014.words (and cobol2002.words) first deactivates all functions with
`not-intrinsic-function: DIALECT-ALL` and then activates EXCEPTION-FILE-N; set_intrinsic_mode in cobc/reserved.c turns the
not-implemented entry into disabled and then into active (its FIXME notes this), so cb_build_intrinsic's
"is not implemented" check is bypassed and the call is generated against the libcob stub cob_intr_exception_file_n, which calls
error_not_implemented. Either keeping the not-implemented state through that sequence (compile-time refusal in every
dialect) or implementing the function would remove the run-time abort. The same applies to BOOLEAN-OF-INTEGER,
CHAR-NATIONAL, EXCEPTION-FILE-N, EXCEPTION-LOCATION-N, INTEGER-OF-BOOLEAN and STANDARD-COMPARE.
