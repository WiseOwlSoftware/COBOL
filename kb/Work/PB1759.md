# PB1759 — HIGH-VALUE U+FFFF and the storage-byte law (owner R51 / R52)

Design: `docs/COBOLNET_FILES_DESIGN.md` D29 (as corrected). Absorbed kb/Work PB1093 (its rows GR-12.3.7.4-8, GR-12.3.7.4-10, GR-12.4.5.7.4-1, GR-8.3.3.6.4-6 closed with this work). What was built is in "Landing" below; the two sections between here and "Step 0" are the ORIGINAL PLAN, kept as the record of what was proposed and why it changed.

## Original plan — SUPERSEDED by Step 0 and Landing below (the per-leaf `AsMedium`/`FromMedium` was not built)

1. **Split the codec's two images.** `GroupImageCodec` emits `AsImage()` / `FromImage()` for two jobs: the IN-MEMORY
   group image (group MOVE, group comparison, DISPLAY, CALL windows — text semantics, must stay lossless) and the FILE
   image. Add `AsMedium()` / `FromMedium()` per record struct: per-leaf kinds — alphanumeric / edited (and groups of
   them): U+FFFF <-> byte 0xFF; numeric byte forms unchanged; national UTF-16BE pairs unchanged; anything else above
   U+00FF stays R47's refusal. File emitters (WRITE, REWRITE, READ, RELEASE/RETURN, START, DELETE key images) use the
   medium image; nothing else does.
2. **Change the HIGH-VALUE answer** at every site R52 lists (`CollatingModel.Extremes` and `.HighValue`,
   `DataBinder.NativeHighValue`, `FigurativeConstants` 'H', `AlphanumericCollation` defaults, the file collating
   FINGERPRINT in `FixedFileAttributes`, `InitialStateBackground`, `ValueInitializer`, `LiteralEnvironment`) — ONE
   member every site reads.
3. **Goldens:** a record file round trip of `MOVE HIGH-VALUES TO REC` / WRITE / READ / `IF REC = HIGH-VALUES`; a
   REDEFINES numeric view over the same bytes (0xFF read as a number); the ALPHABET-with-HIGH-VALUE case PB1093
   measured (`ALPHABET AL IS HIGH-VALUE "B" "A"` — X"FF" must no longer sort first, U+0100 must compare below
   HIGH-VALUE); `ORD(HIGH-VALUE)` = 65536.
4. **Docs in the same change:** DOC-A.1-31 (the accepted `ÿ` cost), DOC-A.1-183/-188, D29, COBOLNET_DESIGN §14.9 /
   §18 #14 ("flagged divergence" paragraphs), PHASE4_RECONCILIATION.

## Original "revisit before starting" list — ANSWERED by Step 0 below

- Enumerate every consumer of the in-memory image versus the file image (47 files reference AsImage/FromImage) and
  classify each — the split is only safe if no memory-image consumer reaches a connector and vice versa.
- Indexed / relative KEY images and the sort store compare record images: HIGH-VALUE keys must compare as the
  collation says on BOTH sides of the medium (in memory U+FFFF, on disk 0xFF).
- Line sequential files: HIGH-VALUE in a text line stays refused ('71', item 115) — confirm with PB1760.

## Step 0 — measured 2026-09-29 23:17 PDT on ff6b486a0 (implementer, before any code change)

**The consumer classification.** 47 `src` files mention `AsImage`/`FromImage`, but most are binder/model files naming
the image-capability PREDICATES (`StoreAsImage`, `IsImageCapable`, `ElementTransferImageCapable`). The emitted calls
reach the codec through exactly two renderers, and every statement goes through them:

| renderer (the one entry) | in-memory consumers | file-image consumers |
|---|---|---|
| `PlaceRenderer` `Read(group).AsImage()` / `GroupTarget.FromImage` / `WriteFullGroupImage` | MOVE (`MoveEmitter`, `ReceivingStore`), comparisons (`ConditionRenderer`), DISPLAY/ACCEPT, CALL/INVOKE windows (`CallEmitter`, `OoEmitter`, `ProgramEmitter` parameters), SET, INITIALIZE, INSPECT/STRING/UNSTRING, arithmetic sending images (`NumericRenderer`), FILE STATUS group store | READ into the record area (`SequentialIoEmitter.EmitImageInto`, `KeyedIoEmitter`) |
| `OperandText` `FieldImage` / `SendingGroupImage` / `RecordAreaImage` | every sending operand above, `ASSIGN USING` names | WRITE / REWRITE / RELEASE record images, keyed START/DELETE key images (`KeyedIoEmitter`), SORT keys (`SortEmitter` — compared in memory, never on a medium) |

**Straddlers — the split D29 proposed is not clean at the codec.** `WriteFullGroupImage` is the ONE full-image store
for both a READ and a FILE STATUS group; `RecordAreaImage` / `FieldImage` serve WRITE and in-memory sending operands
alike; the SORT work store and RELEASE/RETURN keep images IN MEMORY (`CobolSort` has no medium; only USING/GIVING
files cross one). And D29's per-leaf `AsMedium`/`FromMedium` cannot reach the record areas that have NO leaves: a
multi-01 FD's shared area and every Tier-B REDEFINES backing are STRING backings (`RedefViewPlace`), and an
elementary record area has no struct.

**The facts that decide the design.**
1. The medium boundary in the runtime is TWO code sites: `FileConnector.ToMedium`/`FromMedium` (the sequential and
   line sequential streams — `StreamWriter(FileCharacterSet.Medium)` / `StreamReader(Latin1)`) and
   `RecordFraming.WriteStore`/`ReadStore` (the relative and indexed stores). Keyed stores hold records IN MEMORY as
   native strings, so keys compare in memory (U+FFFF highest) and only persist/load crosses bytes.
2. Every in-memory byte-form DECODER already truncates a character to its low byte (`CobolNum.Image`
   `ParseBinaryImage` / `ImageFloatBits` / packed: `(byte)image[i]`; `CobolBits.NatReadWindow`: `& 0xFF`), so a
   U+FFFF at a numeric position reads as the byte 0xFF today — a numeric view needs no per-leaf decode.
3. Every in-memory byte-form ENCODER writes a byte b as the character U+00bb (`BinaryBytes`, `FormatIeeeBits`,
   `PointerImage`, `CobolBits.Pack`/`PutNat`).
4. Probe `scratchpad/hv/p1.cob` (a record `05 A PIC X(3). 05 B PIC S9(4) COMP.`): `MOVE HIGH-VALUES TO REC` then
   `IF REC = HIGH-VALUES` prints `REC-EQ-HV` today ONLY because HIGH-VALUE is U+00FF — the struct re-images B's
   bytes FF FF as U+00FF U+00FF. With HIGH-VALUE = U+FFFF and fact 3 unchanged (D29 as written), the same program
   prints `REC-NE-HV`: a wrong answer on the most common HIGH-VALUES idiom, because merely storing the group
   through a binary leaf CHANGED its content (§14.9.25.4 GR4 moves a group "without conversion of data from one form of
   internal representation to another"; nothing alters the characters afterwards).

**Design correction (D29 amended in the landing change set; owner addendum 2026-09-29 permits it).** The collision
is not between text and binary — it is between two CHARACTERS (U+00FF and U+FFFF) and one BYTE (0xFF). So the rule
is one law about bytes and characters, written ONCE in the runtime (`StorageByte`), and applied wherever a byte
becomes a character or back: **byte 0xFF is the character U+FFFF (HIGH-VALUE); every other byte b is U+00bb; a
character's byte is its low byte, so U+00FF and U+FFFF share 0xFF.** Encoders (binary, IEEE, pointer, bit, national
pair) write through it; decoders already truncate. At the file medium the SAME law is the channel mapping
(`FileCharacterSet`): U+FFFF -> 0xFF on output, 0xFF -> U+FFFF on input, any other character above U+00FF still
refused (R47's '91'/'71'). Because a byte-form leaf's image now holds U+FFFF for 0xFF, the medium mapping needs no
leaf kinds at all: the record struct, a Tier-B backing, a multi-01 FD area and an elementary record all cross the
medium through the one channel, and a REDEFINES numeric view reads the byte back through the decoders' truncation.
No second generated image (`AsMedium`/`FromMedium`) exists. **Accepted cost, generalized (DOC-A.1-31):** a real
`ÿ` (U+00FF) that passes through a BYTE — the record medium OR a byte-form (binary, float, pointer, bit) storage
position — returns as HIGH-VALUE; in an alphanumeric leaf in memory it stays U+00FF, and `X"FF"` stays U+00FF.

## Landing (2026-09-29)

**What landed** — the corrected design of step 0, not the proposed per-leaf `AsMedium`/`FromMedium`:
- ONE storage-byte law, `src/Cobol.Net.Runtime/Values/Text/StorageByte.cs` (`StorageByte.ToChar/ToByte/HasByte`) and
  ONE native extreme pair, `NativeCollatingSequence.HighValue/LowValue` (same file). Every byte-form encoder writes
  through it (`CobolNum.Image` binary/IEEE/packed, `PointerImage.Render`, `CobolBits` bit blit and national pairs) and
  every decoder reads through it; `CobolIntrinsics.RawBytes` (item 209's byte reduction) gives U+FFFF the byte 0xFF.
- The fixed-record medium: `FileCharacterSet.ToChannel/FromChannel` (U+FFFF <-> 0xFF), called by the two medium
  sites `FileConnector.ToMedium/FromMedium` and `RecordFraming.WriteStore/ReadStore`; `HasCharacterWithoutByteImage`
  admits U+FFFF. A CODE-SET medium writes HIGH-VALUE as its highest code unit (`CodeSetConversion.HighUnit`, R51
  item 4).
- HIGH-VALUE U+FFFF at every R52 site: `CollatingTable.Extremes` (whole repertoire, `national` parameter deleted from
  `Build`), `AlphabetDef/NationalAlphabetDef.HighValue`, `AlphabetFigurative` (its `national` parameter deleted with
  `DataBinder.NativeHighValue`), `LiteralEnvironment` (carries only "inside SPECIAL-NAMES"), `FigurativeConstants.FillChar`
  (and `Fill`, now one rendering of `FillChar` — the byte-identity second switch deleted), the runtime collation
  defaults, `FixedFileAttributes.Fingerprint` (all 65,536 weights). `InitialStateBackground` / `ValueInitializer`
  needed no change — they read `FillChar`.

**Goldens**: `85/pb1759_high_value_record_round_trip_85` (sequential, relative with a REDEFINES numeric view, indexed
HIGH-VALUES key order and random read; `IF REC = HIGH-VALUES` after a group MOVE over a COMP field),
`2023/pb1759_high_value_is_the_highest_native_character` (ORD 65536, wide character below, national, `X"FF"` is not
HIGH-VALUE, COMP-5 group, CLASS IS HIGH-VALUE, the accepted `ÿ` cost), `2023/pb1093_alphabet_high_value_tail`.
Re-derived: `2023/stepd_based_comp_leaf`, `2023/stepd_mixed_usage_redefines` (a byte 0xFF viewed as a character is
ORD 65536), `2023/pb152_options_initialize_arm_agreement` (IMG=65536). `da1_alphabet_hex_thru` and
`pb297_figurative_sizing_categories` did NOT move (measured: neither pins the alphanumeric HIGH-VALUE's code).
Unit: `FileBoundaryTests.StorageByteLaw_HighValueIsTheByteFF_OnTheChannelToo`,
`CodeSetConversionTests.HighValue_IsTheCodeSetsHighestUnit`, the byte-image tests re-expressed through the law.

**For the next implementer:** `StorageByte` is the only place a byte becomes a character — never write `(char)b` for
a storage byte or `(byte)c` for a storage character; `FileCharacterSet.ToChannel/FromChannel` is the only medium
mapping for a fixed-record file (a new medium site calls it, never re-implements it).
