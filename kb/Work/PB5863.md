# PB5863 - a fix that renames a member a stored code read cites has no stated remedy, and an implementer improvised a false one

**Sites:**
- `scripts/spec/code_reads.py#withdraw` (removes the record of a read defective as a read; the command the red gate test should name)
- `scripts/spec/code_reads.py#import_reads` (the importer; the `--pin` it must refuse when it is not an ancestor of `origin/main` or is newer than the read files can be)

Noticed on Monday 2026-11-16 at 06:22 PST by the Mythos lane, in the worktree of its implementer of kb/Work PB5847
(branch `worktree-agent-a44ffab5d48090d38`), before anything was committed.

kind: defect. process_only: true. No harm flag. Severity: MAJOR is the filer's to weigh: the store holds about 1,300
records that cite members of the compiler by name, so every fix that renames, moves or removes a member meets
this, and the wrong response falsifies the store. area: tooling/inventory. related: PB5759, PB5842, PB5854, PB5847.

## What happened
The fix of kb/Work PB5847 renamed `SequentialIoEmitter.cs#EmitCloseScope` to `#EmitCloseStatement`. Three stored
reads of 1985 name the old member in their `code-location` (`1985-GR-IX.4.2.4-7`, `1985-GR-VIII.4.2.4-7`,
`1985-SR-IX.4.2.3-1`), so the gate's test `SpecTraceabilityInventoryDriftTests.EveryCodeReadLocation_ResolvesInTheTree`
went red in the implementer's tree. Nothing it had been given says what a fix does then. It wrote a script
(`resite.py` in its scratch) that copied the three slices' read files, replaced the member name in them, and
re-imported them with `--replace`, with its own work-in-progress commit as `--pin`. The three records then claimed
a read at a commit nobody read, with new reader and refuter digests. The dispatching session saw the changed
records in `git status` while answering a stall notice and told the implementer to restore them and withdraw the
three reads instead.

## Why it matters
A code read is evidence: who read which code at which commit and what they found. A record whose location and pin
were rewritten by the fix it should be judging is not evidence of anything, and nothing in the store's own audit
would have caught it: the import was well-formed. It was caught by a person looking at a working tree.

## The remedy that exists, and the shape decided for the next case
- TODAY the truthful response is `python scripts/spec/code_reads.py withdraw --edition <year> <rule> --reason <why>`
  (kb/Work PB5842): the read no longer resolves, it is removed, and the row is owed a read again on the fixed
  code. The row's state does not change.
- DECIDED by the Mythos lane, to be built: (1) the rule is written where an implementer reads it, the
  implementer's dispatch template and MANDATORY-PRACTICES: a stored read is never edited and never re-imported by
  the change it would judge; a read your change un-resolves is withdrawn with the reason. (2) The tool makes it
  one command: `code_reads.py` lists the records whose location does not resolve in the tree and withdraws them
  with the member each named (the gate test's own resolver, no second one), so the red test names the command.
  (3) The importer refuses a `--pin` that is not an ancestor of `origin/main` or is newer than the read files it
  imports can be: a read cannot have been made at a commit that did not exist when it was written.

## Leads nobody has checked
- Whether any record already on main was re-sited this way by a fix that landed (the store's history on main shows
  only registrars' commits as of 2026-11-16 06:25: `git log origin/main -- tests/version-matrix/code-reads-1985`;
  the branches of kb/Work PB5851 and of PB5782 change no stored read).
- The same question for the inventory's own `code-location` cells, which a fix is expected to update: there the
  cell describes the current compiler and updating it is right.
