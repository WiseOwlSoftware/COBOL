# PB329 — statuses 39 and 09, unreachable by construction

**Rows:** `GR-14.9.30.4-16` (Part 2) and, since 2026-09-05, `GR-14.9.30.4-1` — the ALL-FORMATS roll-up rule "the
I-O status … is updated as indicated in 9.1.13". That row was PARTIAL on two value defects; [[PB336]] landed the
other one (the absent-OPTIONAL `'10'`/`'46'` guard order) and handed the row here, because Part 2 was then the
ONLY reason it was still PARTIAL. The landing also claims `DOC-A.1-115`, the Annex A.1 determination the rule
delegates to — a determination and the rule that consumes it close together or not at all.

## Landed — 2026-09-05

**Part 1 ('39') was ALREADY CLOSED when this landing began** and is re-confirmed by measurement, not by reading
the note: `FileStatusCode.FixedAttributeConflict` exists, `FileConnector.Open` compares against the persisted
`FixedFileAttributes` sidecar under §14.9.27.4 GR10, and `DOC-A.1-129` documents the validated set. Row
`GR-14.9.27.4-10` belongs to [[PB193]], which carries the forensics. Part 1's paragraphs below are the pre-fix
finding, kept for the record.

**Part 2 ('09') is what this landing did, and the mechanism turned out to be three arms, not one.**

- **The determination first.** §14.9.30.4 GR16, §14.9.51.4 GR23, §14.9.35.4 GR17 d) and §9.1.13.10 item 1 all
  delegate to "the implementor-defined character set for a line sequential file", and Annex A.1 item 115 makes
  it a REQUIRED, documented determination — which nothing in the tree had made. It is now
  `docs/CONFORMANCE.md` **`DOC-A.1-115`**: *every character whose code point is U+0020 (SPACE) or above is a
  member; the C0 controls U+0000–U+001F below it — the two line delimiters CR and LF and the tab HT among
  them — are not; DEL and the whole Latin-1 supplement are.* Four-step derivation in the row: the delimiters
  are forced out by §9.1.7.2's definition of a line sequential record's extent; a set of "everything but the
  delimiters" would make GR16's `'09'` unreachable by construction, and a required determination that makes
  its own rule vacuous is not a determination; the remaining C0 controls are the stream/device repertoire, not
  text; and ⚖ GnuCOBOL — surveyed, not assumed — defaults `COB_LS_VALIDATE` to true "per COBOL 2022" and
  validates read (`09`) and written (`71`) data against the same below-SPACE boundary.
- **One set, one predicate, five call sites.** `LineSequentialCharacterSet` is the set's one executable copy;
  `SequentialConnector.RecordAreaOutsideLineCharacterSet` is the one call shape. It is consulted by `Read`
  (→ `'09'`), by BOTH write entry points — `Write`, `WriteAdvancing` (→ `'71'`); a third,
  `WriteBeforeAndAfter`, existed until kb/Work PB712 deleted it (§14.9.51.2 prints ONE ADVANCING operand) —
  and by `Rewrite`, whose private `IndexOf('\n') || IndexOf('\r')` test it REPLACES. The note's premise that
  "the unswept twin is one method away" was half right: REWRITE was implemented, but **the WRITE arm
  (§14.9.51.4 GR23) did not exist either**, so the pair was really a triple with one arm present.
- **The record area's CHARACTERS, not its bytes.** §14.9.30.4 GR15 splits a record area into alphanumeric and
  national, and the connector channel carries one char per BYTE, so a national area is tested two bytes at a
  time as UTF-16BE (D-N1) exactly as `FitRecord`/`TrimRecordEnd` pad and trim it. A byte-wise test would have
  read `N"CD"`'s `00 43 00 44` as two control characters and refused every national line sequential record —
  it would have broken the standing golden `2002/pb327_national_line_sequential_fill`.
- **`'09'` wins over `'06'`.** GR16 is stated after GR15 and its only condition is "the execution of the READ
  statement is successful", so it also lands on a truncated over-length read; `ReadSucceeded`'s arbitration
  follows that order.

**Measured on the built `cobol.exe`, before → after** (probe: a record sequential print write seeds a line
holding `0x00`, then the same host path is read LINE SEQUENTIAL, then a line sequential WRITE is attempted):

```
BEFORE   PRINTWRITE=00   LSREAD=00   ORD3=1   LSWRITE=00   (and pb329probw.dat held the NUL)
AFTER    PRINTWRITE=00   LSREAD=09   ORD3=1   LSWRITE=71   (and pb329probw.dat is 0 bytes)
```

Goldens `2002/pb329_line_sequential_charset`, `2014/…_2014`, `2023/…_2023` walk `'09'` (READ, record still
delivered), `'71'` (WRITE), `'71'` (REWRITE), §9.1.13.10 item 1's unchanged medium (the file is re-read and
holds only the records the successful writes released) and the set's boundary (`0x7F` → ordinal 128 and `0xFF`
→ ordinal 256 are members) at every edition the LINE SEQUENTIAL organization exists in.

## Part 1 — status '39', the fixed file attribute conflict — ✅ LANDED under [[PB193]]

`FixedFileAttributes` (the persisted §9.1.6 catalog) + `FileConnector.Open`'s §14.9.27.4 GR10 comparison
produce '39' now; `FileStatusCode.FixedAttributeConflict` exists; row `GR-14.9.27.4-10` is OK and its
Annex A.1 item 129 determination is documented at `docs/CONFORMANCE.md` `DOC-A.1-129`. The row moved to
PB193, which carries the forensics. **The paragraphs below are the pre-fix finding, kept for the record.**

> §14.9.27.4 GR10: ... the attributes of the file connector as specified in the file control paragraph and the
> file description entry are compared with the fixed file attributes of the file. If the attributes don't match,
> a file attribute conflict condition occurs, the execution of the OPEN statement is unsuccessful, and the I-O
> status associated with file-name-1 is set to '39'. The implementor defines which of the fixed-file attributes
> are validated ...

`--check 14.9.27.4 "the attributes of the file connector as specified in the file control paragraph and the file
description entry are compared with the fixed file attributes of the file"` → **OK**. Annex A.1 item 129 makes
the validated set a required, documented implementor determination.

**Probe** (`<lane3 scratch>/out-b1/probe/attr39`): `ATTRW01.cob` writes `attr39.dat` as `ORGANIZATION IS
RELATIVE` with 10-byte records; `ATTRR01.cob` then SELECTs the SAME host path as `ORGANIZATION IS SEQUENTIAL`
with a 20-byte record and opens it INPUT. **`FileStatus.cs` has no '39' constant at all** (the codes present are
00/02/04/05/06/10/14/21/22/23/24/30/34/35/37/38/41/42/43/44/46/47/48/49/51/52/53/54/61/62/71) and no connector
`OpenCore` reads a persisted physical-attribute catalog. The §9.1.6 fixed attributes (organization, key
geometry, code set, min/max record size, record type, key collating sequence, record delimiter) are simply not
carried by the host-file model, so **the validated set is empty and '39' is unreachable**.

## Part 2 — status '09', the line-sequential character set — ✅ LANDED 2026-09-05 (above)

> §14.9.30.4 GR16: If the execution of the READ statement is successful but the record area contains one or more
> characters not in the implementor-defined character set for a line sequential file, the I-O status in the read
> file connector is set to '09'.

`--check 14.9.30.4 "the record area contains one or more characters not in the implementor-defined character set
for a line sequential file"` → **OK**; §9.1.13.2 item 7 says the same from the status side.

**Pre-fix probe** (`<lane3 scratch>/out-b1/probe/ls09/`): `mk.py` writes `ls09.dat` as `AB` + 0x00 0x1A 0x0B +
`CD` + CRLF; `LS09.cob` SELECTs it LINE SEQUENTIAL with `PIC X(7)` and displays the FILE STATUS after one READ.
Observed `LS09 STATUS=00`. `"09"` appeared nowhere in `src` (one unrelated `LocaleFacts` comment),
`FileStatusCode` had no '09' member, and `SequentialConnector.Read`'s line-sequential arm inspected only the
record LENGTH (the '06' truncation), never its characters.

**The unswept twin was one method away — and was itself only two thirds of the rule.**
`SequentialConnector.Rewrite` returned `FileStatusCode.LineRecordInvalidChar` '71' when the new record carried
CR or LF, citing §14.9.35.4 GR17 d), so the implementation already asserted a line character set on REWRITE
traffic; the landing found that §14.9.51.4 GR23's WRITE arm was absent as well.
