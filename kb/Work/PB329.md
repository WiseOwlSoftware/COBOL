# PB329 — statuses 39 and 09, unreachable by construction

**Rows:** `GR-14.9.27.4-10`, `GR-14.9.30.4-16`.

## Part 1 — status '39', the fixed file attribute conflict

> §14.9.27.4 GR10: ... the attributes of the file connector as specified in the file control paragraph and the
> file description entry are compared with the fixed file attributes of the file. If the attributes don't match,
> a file attribute conflict condition occurs, the execution of the OPEN statement is unsuccessful, and the I-O
> status associated with file-name-1 is set to '39'. The implementor defines which of the fixed-file attributes
> are validated ...

`--check 14.9.27.4 "the attributes of the file connector as specified in the file control paragraph and the file
description entry are compared with the fixed file attributes of the file"` → **OK**. Annex A.1 item 129 makes
the validated set a required, documented implementor determination.

**Probe** (`<lane3 scratch>/out-b1/probe/attr39`): `ATTRW01.cob` writes `attr39.dat` as `ORGANIZATION IS
RELATIVE` with 10-byte records; `ATTRR01.cob` then SELECTs the SAME host path as `ORGANIZATION IS SEQUENTIAL`
with a 20-byte record and opens it INPUT. **`FileStatus.cs` has no '39' constant at all** (the codes present are
00/02/04/05/06/10/14/21/22/23/24/30/34/35/37/38/41/42/43/44/46/47/48/49/51/52/53/54/61/62/71) and no connector
`OpenCore` reads a persisted physical-attribute catalog. The §9.1.6 fixed attributes (organization, key
geometry, code set, min/max record size, record type, key collating sequence, record delimiter) are simply not
carried by the host-file model, so **the validated set is empty and '39' is unreachable**.

## Part 2 — status '09', the line-sequential character set

> §14.9.30.4 GR16: If the execution of the READ statement is successful but the record area contains one or more
> characters not in the implementor-defined character set for a line sequential file, the I-O status in the read
> file connector is set to '09'.

`--check 14.9.30.4 "the record area contains one or more characters not in the implementor-defined character set
for a line sequential file"` → **OK**; §9.1.13.2 item 7 says the same from the status side.

**Probe** (`<lane3 scratch>/out-b1/probe/ls09/`): `mk.py` writes `ls09.dat` as `AB` + 0x00 0x1A 0x0B + `CD` +
CRLF; `LS09.cob` SELECTs it LINE SEQUENTIAL with `PIC X(7)` and displays the FILE STATUS after one READ.
Observed `LS09 STATUS=00`. `"09"` appears nowhere in `src` (one unrelated `LocaleFacts` comment), `FileStatusCode`
has no '09' member, and `SequentialConnector.Read`'s line-sequential arm inspects only the record LENGTH (the
'06' truncation), never its characters.

**The unswept twin is one method away.** `SequentialConnector.Rewrite` returns `FileStatusCode.LineRecordInvalidChar`
'71' when the new record carries CR or LF, citing §14.9.35.4 GR17 d) — so the implementation already asserts a
line character set on WRITE-side traffic and never checks the READ side.

## Both parts need a determination first

Neither status can be produced until the implementor answers the question the rule delegates: WHICH fixed
attributes are validated (A.1 item 129), and WHICH repertoire is the line-sequential character set.
`docs/CONFORMANCE.md` §3 pins determinations for '04', '07', '37' and '39'-less codes and none for either.
**PB322** owns the determination-documentation mechanism; the two must land together, and the '09' predicate
must then be shared by the READ and REWRITE directions so the two sides can never disagree about what a
line-sequential character is.

**Code sites:** `SequentialConnector.cs#Read`, `#Rewrite` · `src/Cobol.Net.Runtime/IO/FileStatus.cs` ·
`SequentialConnector.cs#OpenCore`, `RelativeConnector.cs#OpenCore`, `IndexedConnector.cs#OpenCore` ·
`docs/CONFORMANCE.md`.
