# PB5210 - CLOSE WITH LOCK locks the file-name, not the physical file: an OPEN of the same physical file through another file-name succeeds with status 00 where 1985 gives 38, and OPEN OUTPUT through it recreates the locked file

**Sites:**

- `src/WiseOwl.Cobol.Runtime/IO/FileRegistry.cs` (`_locked`, `CloseWithLock`, `SharedOpenAttempt`)

**Mechanism.** 1985 status 38 is for "an OPEN statement is attempted on a file previously closed with lock" (§1985:IX.1.3.4), and the 1985 conventions make "file" the physical file: "The terms file referenced by file-name and file mean the physical file regardless of the file-name used in the COBOL program" (§1985:II.2). `FileRegistry.CloseWithLock` adds the connector's NAME to `_locked`, and `SharedOpenAttempt` answers 38 only when the name being opened is in that set. A second SELECT whose ASSIGN names the same physical file has another name, so its OPEN succeeds, reads the locked file's records, and OPEN OUTPUT through it empties the file. The runtime treats the two connectors as one physical file in every other respect (a record written through one is read through the other), so only the lock is kept per connector. The sequential, relative and indexed modules share the registry, so all three organizations take the same path (probed: sequential and indexed).

**Found by.** The 1985 refuter pass (2026-11-10; records `E:/COBOL-coord/scratch/refute-85/out/r05.json`, probes `probes-r05/r3_lock.cob`, `r2.cob`): a refuter attacked the CONFORMS verdict of the row below, OVERTURNED it, and the repros were rerun on current main for this note.

**Inventory.** `work.py check` refuses a 1985 rule id in `inventory_rows` (kb/Work PB5094, open), so `inventory_rows` is empty and the rows this note claims are the rule ids below.

**Rules (1 claimed, 2 siblings; every citation checked with `scripts/spec/cite.py --check`).**

- `1985-GR-IX.1.3.4-L2.4` - `§1985:IX.1.3.4` (refuter: OVERTURNED, harm: wrong-answer). Item d: "I-O Status = 38. A permanent error exists because an OPEN statement is attempted on a file previously closed with lock." §1985:IX.4.2.4: "The file is locked and cannot be opened again during this execution of this run unit." §1985:II.2: "The terms file referenced by file-name and file mean the physical file regardless of the file-name used in the COBOL program".
- Siblings by construction, the same item d in the other two modules: `1985-GR-VIII.1.3.4-L2.4` (relative) and `1985-GR-VII.1.3.5-L2.3` (sequential; the sequential repro below shows it). They close with this note when their rows are recorded.

**Observed (current main, the build at 3d12682fd2, rerun 2026-11-10).** exit 0: `WRITE 00`, `CLOSE F1 WITH LOCK 00`, `OPEN INPUT F1 (38) 38`, `OPEN INPUT F2 (38 per II.2) 00`, `READ F2 00 AAAA`, `OPEN OUTPUT F2 (38) 00`. The sequential twin (two SELECTs of `LS.DAT`): `CLOSE F1 WITH LOCK 00`, `OPEN INPUT F1 38`, `OPEN INPUT F2 00`, `READ F2 00 AAAA`, `OPEN OUTPUT F2 00`. (At `--std 2023` the program is refused: CLOSE WITH LOCK was removed, COBOL0902.)

**Expected (from the 1985 text).** `OPEN INPUT F2` and `OPEN OUTPUT F2` are each unsuccessful with status 38, the READ finds the file not open, and the file keeps its record: F2 names the physical file F1 closed with lock (§1985:II.2, §1985:IX.1.3.4 item d, §1985:IX.4.2.4).

**Fix direction (root cause, CLAUDE.md rule 4).** Record the lock against the physical file the registry already resolves for sharing (the same identity `SharedOpenAttempt` uses to arbitrate two connectors of one file), not the connector name: `CloseWithLock` marks the physical file, and every OPEN of any connector onto it answers 38 for the rest of the run unit. One table keyed by physical identity, so a new organization or a new connector inherits the rule; a test opens the locked file through a second SELECT in each organization.
