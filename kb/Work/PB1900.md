# PB1900 — LANDED

## Landed (wave 1039, group G)

**Reproduced on the base build** (`COMPUTE R = A * B - C * D`, all `PIC 9(21)`, A = B = 10^20+1, C = 10^20, D = 10^20+2, R `PIC 9(9)`):
`R=010000000`; the exact answer is 1. Siblings measured on the same build, each wrong the same way: `IF A * B - C * D = 1` took the FALSE
branch, `EVALUATE` the OTHER branch, `FUNCTION ABS(A * B - C * D)` answered 10000000, `COMPUTE R = A*B*C - C*D*A + 5` stored 0, and
`COMPUTE … = (A * B - C * D) / 3` into `PIC S9(5)V99` stored 33333.33.

**Root cause.** `NumericRenderer.Multiply` formed a nested product whose operands' digit bounds exceed 38 on the SDIDI
(`CobolDec.MulToOdd`, 34 significant digits), and every operation above it continued on the SDIDI, so the cancellation of two nearly
equal products left only the rounding error of each.

**Fix (the shape that makes the NEXT case automatic).** A new runtime type `CobolWide` (`src/Cobol.Net.Runtime/Values/Numeric/CobolWide.cs`) is an exact
signed 256-bit integer at a compile-time scale. `NumX.Wide` carries it; the renderer's digit-bound analysis (`NumX.Digits`) selects it for a
nested product and for the sums, differences and negations above it whenever the exact value provably fits `CobolWide.MaxDigits` (77) digits;
beyond that, or beside an operand of unknown bound, the SDIDI round-to-odd form stands (the limit of the determination). It NEVER leaves
`NumericRenderer` unsettled: every public entry (`Render`, `AsNum`, `Fold`, `Combine`) calls `Settle`, which rounds ONCE at the receiver's own scale
and mode at the final transfer (`CobolWide.ToUnscaled` over the `CobolDec.TransferWide` kernel that `MulAtScale` now shares — one transfer rule)
and otherwise lowers to the SDIDI by round-to-odd. Two consumers take it exact through `keepWide` and settle it themselves: a several-receiver COMPUTE's
one initial evaluation (snapshotted as a `CobolWide`, settled per receiver) and a relation (`CobolWide.Compare`, exact: two products that differ below the 34th digit
are no longer equal). `ExactWideSettlementDriftTests` closes that list. Quotients stay on round-to-odd (`CobolDec.DivToOdd`): GnuCOBOL's own divide is inexact.
DOC-A.1-123 and `COBOLNET_NUMERIC_DESIGN.md` D26 are rewritten to state the determination and its limits.

**Sibling sweep.** Every other place that forms a native product past the carrier: `NumericRenderer.Multiply` (this) is the only producer of `MulToOdd`;
`MulAtScale` (the outermost product) was already exact and now shares the transfer kernel; `IntrinsicRenderer`'s SUM / RANGE / MEAN / MEDIAN / MIDRANGE SDIDI body
(DOC-A.1-92) is the §15.4.1 implementor-defined approximation the 2026-09-30 adjudication already licensed and is unchanged; the DIVIDE alignment
(`QuotientAtScale`) was already exact. The float receiver keeps its binary64 evaluation (D16): `COMPUTE F1 = A * B - C * D` into COMP-2 is 0 by IEEE.

**Pinned by** `conformance:2002/pb1900_nested_product_cancellation`, `conformance:2014/pb1900_nested_product_rounded_modes`, `unit:CobolWideTests`,
`unit:ExactWideSettlementDriftTests`.

## Landing

- `src/Cobol.Net.Runtime/Values/Numeric/CobolWide.cs#CobolWide` — the exact 256-bit lane (`Mul`/`Up`/`Add`/`Sub`/`Negate`/`Compare`/`ToUnscaled`/`ToDec`); REUSE it for any new exact native intermediate. Trap: `UInt128` carries are easy to get wrong — every constructive op checks its own overflow and raises EC-SIZE-OVERFLOW.
- `src/Cobol.Net.Runtime/Values/Numeric/CobolDec.cs#TransferWide` — the ONE final-transfer kernel (round once, two statement dispositions); `MulAtScale` and `CobolWide.ToUnscaled` both call it. `FromWideToOdd` is the one round-to-odd reduction.
- `src/Cobol.Net.Compiler/CodeGen/Emit/NumericRenderer.cs#Settle` — the only way a `NumX.Wide` leaves the renderer; `Render`/`AsNum`/`Fold`/`Combine` call it, `keepWide` opts out (ArithmeticEmitter multi-receiver COMPUTE and ConditionRenderer relation only, pinned by `ExactWideSettlementDriftTests`). Producers: `Multiply` (nested product) and `CombineAdditive`/`Negate`; everything else lowers through `LowerWide`/`DecOperand`. Trap: `RuntimeApiGuardTests` counts bare `Cobol*.` text in the renderer — route constants through `RuntimeApi`.
- `src/Cobol.Net.Compiler/CodeGen/Emit/EmitCore.cs#NumX` — `Wide` is deliberately NOT a `NumXCarrier`; `Carrier` throws on it.
- Open siblings found, not fixed: a subscript EXPRESSION is a typed `Position` tree rendered in plain `long` (`PositionRenderer.Render`), so 21-digit operands wrap; `A ** 2` over a FRACTIONAL base is a binary64 approximation (`NumericRenderer.Power`, `integerOperands` requires scale 0).

## Original note

Found by the 2026-09-30 read-only adjudication of the numeric cluster's documented limits (checked citations; see the session scratchpad report `w0930-limits-adjudication.md`, item 3). It is NOT an ISO divergence:
8.8.1.3 "Native arithmetic is an implementor-defined method of evaluating an arithmetic expression", 14.7.7 4) a) "Otherwise, an implementor-defined intermediate data item is used", Annex A.1 item 123
(documented in DOC-A.1-123); under STANDARD-DECIMAL 8.8.1.5.2 REQUIRES decimal128 results, so 34 digits is correct there. It IS a departure from CLAUDE.md rule 1, which makes the implementor latitude follow GnuCOBOL
(`cob_decimal_mul` is `mpz_mul`, exact: libcob/numeric.c:2232-2237; DOC-A.1-123 itself says so).

**Wrong answer, plain ISO code.** All operands `PIC 9(21)` (within the 13.18.40.3 SR14 limit of 31 digits), A = B = 10^20+1, C = 10^20, D = 10^20+2, R `PIC 9(9)`:
`COMPUTE R = A * B - C * D`. The exact result is 1. The 41-digit `A * B` goes through `MulToOdd` (`NumericRenderer.cs` ~L745) and becomes 10^40 + 2*10^20 + 10^7, so R stores **10000000**. The adjudicator derived this from
the code and DOC-A.1-123 and did not run it: **probe it first.** Only cancellation exposes the loss; the original COMP-5 repro in the train review uses a non-ISO usage.

**Fix design.** In NATIVE mode carry a nested product that exceeds the Int128 bound as an EXACT scaled wide integer (the 256-bit product `CobolDec.MulAtScale` already forms) and do the additions and subtractions on that
exact form; round ONCE, at the final transfer to the receiver. Reserve the 34-digit SDIDI for STANDARD-DECIMAL, where 8.8.1.5.2 requires it. Then rewrite the DOC-A.1-123 sentence that names the 34-digit nested intermediate as the
determination. Quotients may stay on round-to-odd: GnuCOBOL's own divide is inexact too (`shift_decimal` then a truncating `mpz_tdiv_q`, numeric.c:2259-2261), so the precedence does not demand exactness there.
Sibling sweep: every other native place that rounds an intermediate to 34 digits (SUM / RANGE / MEAN / MEDIAN / MIDRANGE, DOC-A.1-92, whose rounding the same adjudication found licensed as an approximation under 15.4.1).

**Train 1039b review (lander).** A FLOATING-POINT numeric-edited resultant's scale is only the mask's hint (14.6.8.4: the value normalizes into the mask), yet `Settle`, the `MulAtScale` arm and the outermost `Divide` rounded at it: `COMPUTE FE = A * A` (A = 10**20) into `-9.9(5)E+99` stored 0.00000E+00. `ReceiverContext.RoundsAtItsScale` is now the one predicate (with `FloatLanding` and the MAX/MIN selection); golden `2023/pb1900_float_edited_resultant_scale`.
