## Finding — `cobol-character-repertoire` (rejects-legal-source; rows `GR-8.1.3.2-4`, `GR-8.1.3.2-3`)

**Mechanism.** The lexer's word-character class NAME_BODY/NAME_TAIL is ASCII-only ([a-z0-9_-]), so no Annex B extended letter can appear in any COBOL word although docs/CONFORMANCE.md A.4.6 claims the Extended letters module; the case-folding (b) and combining-character length (c) legs are therefore unreachable

**Repro.** IDENTIFICATION DIVISION. PROGRAM-ID. REXT. DATA DIVISION. WORKING-STORAGE SECTION. 01 CAFÉ PIC X(3) VALUE "abc". PROCEDURE DIVISION. DISPLAY café. STOP RUN.  (UTF-8 source, fixed form; pinned cobol.exe --std 2023 --run)

**Expected from the spec.** Compiles and DISPLAYs 'abc': U+00C9/U+00E9 are Annex B characters present in the UTF-16 compile-time coded character set, hence extended letters (8.1.3.2 GR4 a), legal COBOL-word characters (8.3.2.1), and the uppercase form folds to the lowercase one per Annex C (GR4 b), so CAFÉ and café are the same data-name. A combining character in a word counts as its own character toward the 63-character limit (GR4 c).

**Observed / reasoning.** error COBOL0001: cannot parse construct near 'É' and COBOL0307: unexpected 'é'; likewise 01 ÄRGER -> COBOL0307 unexpected 'Ä'. CobolLexer.g4 NAME_BODY/NAME_TAIL admit only [a-z0-9_-]. CONFORMANCE.md A.4.6 = Claimed, section 2 row 38 = Claimed. When fixed: the binder's 63 StringComparer.OrdinalIgnoreCase sites are invariant upper-casing, not Annex C lower-folding -- they diverge on extended letters (U+0130, U+212A ...), so the fix needs ONE Annex C folding function the name tables share (rule 5: shape that makes the next case automatic), plus the 2014->2023 Annex B deltas (E.2 item 4: U+037A deleted, U+30FB not first/last) gated per edition, and the 8.3.2.1 63-character count by code point with combining marks counted separately.

**Code site.** src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4#NAME_BODY (line ~921) / NAME_TAIL (line ~920); src/Cobol.Net.Compiler/Binding (OrdinalIgnoreCase name comparison)

## Finding — `cobol-words` (rejects-legal-source; rows `GR-8.3.2.2-L2.2`, `SR-8.3.2.2-3`)

**Mechanism.** The lexer's COBOL-word rule admits only basic letters: NAME_BODY is built from [a-z] (case-insensitive), digits, hyphen and underscore, so ANY extended letter in a user-defined word is a lexical error — while docs/CONFORMANCE.md claims Annex A.4.6 'Extended letters' as Claimed (on the strength of the national-literal repertoire, which is a different facility)

**Repro.** out/probe/ext2/umd.cob (UTF-8 with BOM): `01 Xé PIC X(3) VALUE "ABC".` + `DISPLAY Xé` -> `cobol umd.cob --std 2002|2023` -> COBOL0001 cannot parse construct near 'é'; umsub.cob `PROGRAM-ID. PRÜFSUB.` -> COBOL0307 unexpected 'Ü'.

**Expected from the spec.** With A.4.6 claimed, é and Ü are extended letters (Annex B) and the programs compile; Xé displays ABC, and case folding per §8.1.3.2 4) b) makes XÉ the same word. If the owner instead declines A.4.6, CONFORMANCE.md must say Not claimed and the §8.3.2.2 externalized-extended-letter determination (PB661 item a) follows from that.

**Observed / reasoning.** Lexer error at the first extended letter at 2002 and 2023. The claim row cites only 'National (UTF-16) repertoire' — national LITERALS — which does not answer §8.1.3's user-defined-word use. Either the lexer (NAME_BODY / NAME_TAIL and the word-length measure of §8.1.3.2 4) c)) must admit the Annex B set, or the claim is false; this is an owner-visible conformance claim contradiction.

**Code site.** src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4#NAME_BODY; docs/CONFORMANCE.md A.4.6 and §2 row 38
