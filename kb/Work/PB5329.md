# PB5329 - requeue's guard cannot tell a run GitHub will never finish from a run in flight

**Sites:** `scripts/orchestrator/enqueue.py#requeue` (line 406, the guard), `scripts/orchestrator/land_lane.py#watch_step` (lines 911 to 999, the step that calls `enqueue.requeue`), the `enqueue.py` self-test.

## What the code says today

Read in the worktree at origin/main 6f80ff6692: `requeue` lists the runs of the head commit
(`gh run list --commit <head> --json databaseId,status`) and refuses, touching nothing, while any run's status is not
`completed`. Its docstring gives the reason: a close and reopen starts a new run that cancels the one in flight
(`cancel-in-progress` in build-and-test.yml), whose `ci-gate` then fails (kb/Work PB4052). `status` is the only fact it reads.

## What happened

Read by the controller on 2026-11-11:

- Pull-request check runs 43097245139 (PR #1514, branch notes-after-reboot, created 20:38:22Z) and 43098272601 (PR #1515,
  branch notes-prune-double-delete, created 20:49:17Z) were created during the GitHub Actions outage. Both still read
  `queued` at 21:22Z, 14 minutes after the Actions component read operational (21:08Z, githubstatus.com), while
  pull-request runs created after 21:05Z completed in minutes.
- `gh run cancel <id>` answered "Cannot cancel a workflow run that is completed". `gh run rerun <id>` answered "cannot be
  rerun; This workflow is already running". The API kept reading `queued`.
- Cleared by hand at 21:23Z: `gh pr close`, `gh pr reopen` and `gh pr merge --auto` on each pull request. New runs
  43102592141 and 43102602998 started at once.

## The defect

The zombie run stays `queued` on the same head commit after the reopen. So `requeue`'s guard would refuse that pull request
on every later tick, and the landing lane's queue watch (`land_lane.py`) could never clear it: the only remedy that worked
is the one the guard forbids. The guard cannot tell a run GitHub will never finish from a run in flight.

## Fix

The guard needs a second fact besides `status` before it calls a run live. Examples: the run has a job that is queued or in
progress on a runner, or the run's age is within a bound taken from the workflow's own time limits. The implementer chooses
after reading what the API reports for such a run (the jobs of a zombie, its timestamps), and the self-test gains the
zombie case: a run `queued` with no job on a runner and older than the bound does not stop the requeue, and a run in
flight still does.
