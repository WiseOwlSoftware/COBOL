# PB3107 — the landing oracle serializes input-changing landings

> ⚙ **flags:** process-only

Source: enqueue unit 2026-10-12 15:17 PDT.

`scripts/orchestrator/landing_oracle.py` RULE 1 (a tree carries exactly ONE recorded baseline) and RULE 3 (no path under its
`inputs` changed after the baseline's commit) mean a branch that changes an oracle input must re-record its baseline AFTER
every earlier input-changing branch has merged on main: two branches that each recorded on the same main merge into a tree
with two manifests (RULE 1) or a baseline behind the other's inputs (RULE 3). Each re-record today costs a `cobol-finisher`
(`compare_oracle.py`, `capture_oracle.py --record`, commit; finisher-brief ORACLE stop), then a branch review round for the
manifest commit (enqueue.py refuses it as UNREVIEWED, exit 11: only main's commits, clean merges and DEVLOG-only commits pass
after a CLEAN stamp), then a new landing with both gates, then the merge group's CI.

**Measured 2026-10-12.** Of wave 1069's Review-CLEAN branches, six change oracle inputs (worktree-wf_d63f7207-db5-4, -11, -17,
-18, -22, -30). Only db5-18 carried its own baseline (69e756b0880b, PR 15). db5-4 and db5-11 stopped on exit 7 after both
gates had run GREEN (wasted gates). db5-4's finisher measured `=== ARCH-ORACLE: IDENTICAL — 7780 cases (baseline 60d47c6d52a9,
new b5237d034c28) ===` (the stop was purely mechanical; `E:\COBOL-coord\scratch\finisher-db5-4-compare.log`), and its fresh
baseline went stale the moment PR 15 entered the queue. The five remaining input-changing branches must land strictly one at a
time, each finisher, review, land, merge group before the next may record: about five serial cycles of roughly 50 minutes.
`enqueue.py land` also runs the oracle check AFTER the gates, so a branch it will refuse spends both gates first
(`landing_oracle.py --rev <branch>` answers in seconds before any gate).

**Code sites.** `scripts/orchestrator/landing_oracle.py` (RULE 1-3, RECORD text); `scripts/orchestrator/enqueue.py` (the
checks step, exit 7; the exit-11 review exemption); `scripts/arch/capture_oracle.py`; `scripts/arch/compare_oracle.py`;
`.claude/skills/workstream/templates/finisher-brief.md` (ORACLE stop).

**Fix shape (for the implementer to confirm).** Check the oracle before the gates. When `compare_oracle.py` on the merged head
is IDENTICAL (or differs only in cases the branch's own DEVLOG entry already explains), `enqueue.py` records the baseline on
the merged head itself as a mechanical commit the review exemption admits, like the DEVLOG stamp; stop for a finisher only on
a NEW difference.

## Landed (wave 1071 group X, with PB3123)

**Re-probe (base 3b1261dfe).** `gh run view 38358556637 --log-failed` (PR 29's merge group, a PR that changed no
oracle input) shows `ArchOracleDriftTests.TheRecordedBaseline_IsOneWellFormedManifest` failing with
`Assert.Single() Failure: The collection contained 2 items`: the stacked tree held the baselines of the two pull
requests queued ahead of it.

**The decision (DESIGN-test-build-ci.md §3.17.2 step 4, DESIGN-orchestrator-loop.md §4.7).** The note's candidate,
recording the baseline on the merged head at enqueue, was REJECTED: a merge group is built on every group queued
ahead of it, so two pull requests each recording on its own merged head still stack two records (or one behind the
other's inputs) in the tree the queue tests. No committed record of one tree can describe a tree only the queue
builds. A capture is a pure function of its commit (DESIGN-architecture-review.md §4.1), so the committed manifest
was only a cache: the oracle now commits nothing. `scripts/arch/compare_oracle.py [--base REV]` captures the change's
own base commit (default: the merge base of HEAD and origin/main) with THAT commit's `capture_oracle.py` in a
detached worktree, keeps it under `TestResults/arch-oracle/<commit12>/`, and compares the current tree's capture case
by case. Deleted with the cache: `capture_oracle.py --record`, the manifest's `inputs` (the MSBuild-closure walk and
the row sources' `DataRoots`/`DataInputs`, which existed only for the landing check), the landing oracle script and
enqueue.py's exit 7, the finisher's ORACLE stop, the golden lane's re-record step, and
`ArchOracleDriftTests.TheRecordedBaseline_IsOneWellFormedManifest` / `EveryRowSource_DeclaresTheDataItReads`.
`LandingPipelineDriftTests` retires the landing oracle with the direct-push scripts (no current-state file names it)
and adds `NoTrackedRecord_DescribesOneBranchsTree` (no committed arch-oracle baseline, no `--record`): red on the base
tree, where `docs/rearchitecture/evidence/arch-oracle/16b7de18c926.manifest.json` was tracked.

**Sibling sweep** (every check whose verdict could depend on what is queued): the DEVLOG number (PB3123, same
landing); the witness-loss audit and the `changes` job read base..head, and a group's `base_sha` is the group ahead's
head, so the range is the pull request's own (the workflow comment that said otherwise is corrected);
`landing_check.py` reads in-flight branches by design and only locally; the hand-maintained conformance manifests'
merge conflicts are PB3116's (a git conflict, not a check).
