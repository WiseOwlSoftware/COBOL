# PB3275 — a pull request state read against a head it was not observed at (ENQUEUED and BOUNCED arms)

Source: coordinator steer to the enqueue clerk, 2026-10-16 (no report file).

**Mechanism.** `scripts/prune_worktrees.py` `pull_requests()` (lines ~555-586; line 581) treats a PR as `queued` when `isInMergeQueue OR autoMergeRequest`. A pull request whose auto-merge is on but which CONFLICTS with main (GitHub `mergeable: CONFLICTING`, `mergeStateStatus: DIRTY`) never joins the merge queue, so it is never BOUNCED (no `RemovedFromMergeQueueEvent`), and the survey reads it ENQUEUED forever. `land_lane.py status` shows it DONE/ENQUEUED and no finisher is ever dispatched.

**Evidence.** PR #107 (branch `worktree-wf_00451f9d-3d9-14`), opened 2026-10-16T14:51:35Z by enqueue.py with auto-merge, never entered the queue (its timeline holds commits and an AutoMergeEnabledEvent only; no merge-group run). It was still OPEN at about 15:45Z while #108-#113 merged or queued. `git merge-tree` shows conflicts in `tests/conformance/2002/manifest.json` and `tests/conformance/negative/manifest.json` (the PB3116 hotspot).

**Fix shape (the coordinator's).** Add `mergeable mergeStateStatus` to `PR_QUERY` and classify an open PR that is not in the queue and reads CONFLICTING as a stop (a BOUNCED-like state, "conflicts with main; never entered the queue") that the enqueue unit's step 4 finisher takes, with a self-test case. Related: PB3023 (enqueue.py), PB3103, PB3125 (survey lifecycle states).

**Second half (coordinator addendum).** `scripts/prune_worktrees.py:438` returns ENQUEUED whenever `pr.queued` (auto-merge on), WITHOUT comparing the PR head with the branch tip (the BOUNCED arm at :440 does compare `row.tip == pr.head`). So when a finisher commits a new tip on a branch whose PR is stuck CONFLICTING with auto-merge on, the survey still reads ENQUEUED: the new tip never shows WAITING FOR REVIEW or WAITING TO LAND and the landing lane never lands it. Witness: `worktree-wf_00451f9d-3d9-14`, finisher merge commit d35c76494 (2026-10-16) vs PR #107 head bcaa82b8e. Fix shape: an ENQUEUED read requires the PR head to be the branch tip (or the tip's mechanical successor), and an open PR that is CONFLICTING and not in the queue is a stop the enqueue unit's finisher takes; both with self-test cases beside the existing ones at `prune_worktrees.py` ~1165-1196.

## Variant 2: a failed PR check (enqueue unit, verified about 11:05 PDT 2026-10-17)

A pull request whose OWN required check fails never enters the merge queue either, and `prune_worktrees.py:581`
(`queued = isInMergeQueue or autoMergeRequest`) reads it ENQUEUED the same way.

Evidence: PR #175 (branch `notes-pb3319-s0b-edition-leads-20261017`, head 6822e4418) has had auto-merge enabled since
2026-10-17T04:46:04Z, `mergeStateStatus` BLOCKED, `isInMergeQueue: false` and no merge-queue entry. Its pull_request run
39003798946 failed in the `audits` job, so `ci-gate` reads FAILURE. The cause was the work register: PB3319, PB3321 and
PB3322 carried `blocked: true` although their `blocked_by` PB3173 had landed. The survey showed it ENQUEUED ("is in the merge
queue") for over 6 hours. No REMOVED_FROM_MERGE_QUEUE event exists, so it could never read BOUNCED.

Fix shape: the same query change as above also asks for the head commit's check state (`statusCheckRollup`), and an open PR
with auto-merge on, not in the queue and with a FAILURE rollup is a stop the enqueue unit's finisher takes, with a self-test
case. The one rule for all variants: ENQUEUED requires `isInMergeQueue`, never auto-merge alone.

## Variant 3: the BOUNCED arm compares the branch tip with the pull request's CURRENT head (enqueue unit, verified 2026-10-18 22:45-22:50 PDT)

`scripts/prune_worktrees.py#lifecycle` (main 49e1c6b79, line 454) reads `if pr.bounced and (not row.tip or row.tip == pr.head): return 'BOUNCED'`. `pr.head` is the pull request's CURRENT `headRefOid`, which GitHub moves whenever the branch is pushed, not the head the queue removed. CLAUDE.md rule 7 has every checkpoint pushed, so a finisher (or any session) that pushes its fixed tip to a bounced PR's branch makes `row.tip == pr.head` true again and the branch reads BOUNCED forever: never WAITING FOR REVIEW, never WAITING TO LAND, and the landing lane never lands it. `land_lane.py rearm` cannot help: `lifecycle` returns BOUNCED before the lane/re-arm arm (lines 431-433) is reached. The enqueue unit's step 4 dispatches ONE finisher for every BOUNCED row, so each later enqueue unit would dispatch a pointless finisher for an already-fixed branch.

Witness: `worktree-wf_14a1e62b-326-31`, PR #268. The queue removed it at 2026-10-19T03:26:03Z (`failed_checks`); the last PR commit before the removal was 5dac40c9a. Then cc441f527 (the bounce finisher), 891f8604e (a main merge) and c1421bf44 (notes) were pushed (PR timeline `PullRequestCommit` items after the `RemovedFromMergeQueueEvent`). The branch was reviewed CLEAN at c1421bf44 (findings file `E:\COBOL-coord\scratch\w1118\review-w1118-a6.jsonl`), and `E:\COBOL-coord\land-lane\survey.json` at 22:46 still read `state: BOUNCED, tip: c1421bf44...`. `RemovedFromMergeQueueEvent.beforeCommit` is the merge-group commit (ea372924c here), NOT the PR head, so it cannot be compared with the tip.

Fix shape: a PR is BOUNCED only while the branch tip is the PR head AT the removal (the last `PullRequestCommit` before the newest `RemovedFromMergeQueueEvent`, read in the same GraphQL query `pull_requests` already makes); a tip pushed after the removal reads by its report (WAITING FOR REVIEW / WAITING TO LAND) like an unpushed finisher tip. Self-test arm beside the existing `fnd-fix` case (around line 1498): a removed PR whose headRefOid IS the tip but whose timeline has a commit after the removal reads WAITING TO LAND when reviewed CLEAN.

The ENQUEUED arm and the BOUNCED arm are one mechanism: a pull-request state read against a head it was not observed at. Severity stays MAJOR: it holds finished work, which the owner forbade 2026-10-18 12:10 (kb/Work PB3381).

**Sites:** `scripts/orchestrator/queue_facts.py` (the GraphQL read, `PullRequest.pushed_since_removal`, `PullRequest.bounced`, `pushed_since_removal()`, the listing label and the self-test), `scripts/prune_worktrees.py` (`lifecycle`'s NOT QUEUED arm, the module doc and the self-test).

## Landed (wave 20261030, group D)

Re-probe on this build: variant 1's first half and variant 2 were already fixed by PB3527 (ENQUEUED requires `in_queue`; a
conflicting or red pull request reads BOUNCED at its head), with self-test cases. Two arms of the one mechanism remained:
variant 3 (a pull request bounced, then its fixed tip pushed, read BOUNCED for ever: `headRefOid` is the current head)
and variant 1's second half (a finisher's tip past the head of a CONFLICTING or red auto-merge pull request read NOT QUEUED
for ever). Fixed at the root: `queue_facts` reads whether a commit followed the newest queue removal
(`pushed_since_removal`, the one reader of the timeline window) and `PullRequest.bounced` is empty once it did, so the survey,
the landing lane's watch and the listing agree; `lifecycle` hands a tip past an unqueueable head to its report. Self-test cases
sit beside the existing ones in `queue_facts.py` and `prune_worktrees.py`; the new BOUNCED case was mutation-checked.
