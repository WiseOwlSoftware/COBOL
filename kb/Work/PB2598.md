# PB2598 — a seeded account re-asks a review its skill set already had

Owner, 2026-10-08 00:13 PDT: "Why have you started repeatedly asking me questions when you haven't needed to do so all
day?" The 2026-10-07 23:47 session start of the operator (account 2, `CLAUDE_CONFIG_DIR=C:\Users\brent\.claude-acct2`)
printed `ASK-OWNER /skill-doctor — owner-only interactive command, due (weekly)`, and MANDATORY-PRACTICES O6 makes every
ASK-OWNER line a question, so the operator asked the owner, who was going to bed.

**Model:** Opus (tooling with self-tests). Dispatched with PB2599 as one group (wave 1038 U: the session and hook checks).

## Defect

`scripts/hooks/tooling_check.py:33` reads `SKILL_DOCTOR_STAMP = account.config_dir() / 'cobolsharp-skill-doctor.stamp'`
(weekly, `SKILL_DOCTOR_DAYS = 7`). PB2479's sweep made the stamp per ACCOUNT. Account 1's stamp
(`C:\Users\brent\.claude`) is dated 2026-10-02 19:17. Account 2's config dir was seeded on 2026-10-07 from account 1's
`skills`, `plugins` and `settings.json` (`scripts/account-profile.ps1`, `model_rules.json` `accounts.seed`) and carries
no stamp, so its first session start reported the weekly review as due although the skill set it runs had been
reviewed five days earlier. The seeder has no stamp handling (`grep -i stamp scripts/account-profile.ps1` finds only a
timestamp comment).

## The question the check must answer

What does `/skill-doctor` review? Its documentation (https://code.claude.com/docs/en/skills): "Run `/skill-doctor` to
see what each of your skills costs and how often it gets used, so you can decide which ones to turn off"; it "flags
skills in the listing that have never been invoked". The ACTION it drives is pruning the skill SET (turning skills and
plugins off), and the docs say usage "is recorded on the machine of each person who installed the plugin"
(https://code.claude.com/docs/en/plugins/measure), not per config dir. So the weekly review covers the skill set: the
user skills in `<config dir>/skills` and the plugins `<config dir>/settings.json` enables (the project's own
`.claude/skills` are the same for every account). An account whose whole skill set was reviewed within the week, under
any account's stamp, needs no new review.

## Landed (branch w1038u-session-checks, wave 1038 group U)

- The rule lives in ONE place, `scripts/orchestrator/account.py`: `skill_set(acct)` (the user skills in
  `<config dir>/skills` plus the plugins its `settings.json` enables) and `skill_review(acct, rules)`, the newest stamp
  younger than `SKILL_REVIEW_DAYS` (7) among EVERY account in the table whose skill set contains `acct`'s. The stamp's
  name and the window moved there too; `account.py --skill-review` prints the answer.
- `tooling_check.py` reads no stamp of its own any more: the `/skill-doctor` line asks `account.skill_review` and says
  whose review covers the account (`reviewed 5 day(s) ago under account1, whose skill set contains this account's`);
  when it is due, the ASK-OWNER line names the running account's stamp to touch. The account is resolved once, so an
  unknown config dir asks only on the `Claude account` line.
- The seeder (`account-profile.ps1`) is unchanged on purpose: copying the source's stamp would be a second mechanism and
  would claim a review for skills the account may add later; the containment test answers the question directly.
- Test, over temporary config dirs (`account.py --self-test`, 24/24, Windows and WSL): no stamp -> due; a seeded copy of
  a set reviewed 5 days ago under its source -> covered by the source; the newest covering review wins; a skill or an
  enabled plugin outside the reviewed set -> due; a subset -> covered; 7 days old -> due. Mutation: restricting the
  candidates to the account's own stamp (the old rule) fails the two inheritance cases. The self-test runs in every gate,
  CI and the Linux gate through `scripts/self_tests.py` discovery (kb/Work PB2563; train 1039b dropped the branch's
  hand-list entries); before this it ran nowhere.
- MANDATORY-PRACTICES O6 names the stamp the ASK-OWNER line prints instead of `~/.claude/...`.
