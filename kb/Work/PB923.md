# PB923 — LANDED — the parse node an operand lands in is not its meaning

Source: the `PB428` report, "New defects". Re-measured here.

## The measurement

`<scratch>/reg7/probe/v6_invoke_fn.cob`, `--std 2023` — an alphanumeric function for an alphanumeric
formal (`01 P1 PIC X(8).`):

```cobol
           INVOKE O "M" USING BY CONTENT FUNCTION TRIM(X)
```

```
v6_invoke_fn.cob(12,12): error COBOLNET0828: INVOKE "M": BY CONTENT arithmetic-expression argument
'FUNCTIONTRIM(X)' for formal 'P1': §14.8.2.3.3 rule 2a transfers an expression by the COMPUTE rules, which
requires a category-numeric formal parameter
```

**The control**, `v7_invoke_plain.cob` — the same INVOKE with `BY CONTENT X` — binds cleanly and reaches
run time (it then dies EC-OO-NULL, correctly, because the probe never instantiates the receiver; the BIND
is what is being measured).

⚠ Two spellings that do NOT reach this defect, recorded so nobody repeats them.
`INVOKE O "M" USING FUNCTION TRIM(X)` (no BY CONTENT) draws `COBOL0001: unexpected 'FUNCTION'` — the bare
`invokeArgument` arms are `dataReference | literal` only, which is a SECOND, grammar-level hole worth its
own measurement. And a method header written `PROCEDURE DIVISION USING BY CONTENT P1.` does not parse at
all (`COBOL0001: cannot parse construct near 'CONTENT'`) — BY CONTENT is an INVOKE phrase, not a header
phrase; the PB428 report's repro carries that spelling and a probe built from it verbatim never reaches
the binder.

## The rule

```
$ python scripts/spec/cite.py --check 8.4.3.1.2 "function-identifier"
OK  §8.4.3.1.2   (General format)
    Format 1 (function-identifier):
```

§8.4.3.1.2 Format 1 makes a function-identifier one of the printed forms of **identifier**. Therefore:

```
$ python scripts/spec/cite.py --check 14.8.2.3.3 "MOVE"
OK  §14.8.2.3.3 2) d)  (Elementary items passed by content or by value)
    d) Otherwise, the conformance rules are the same as for a MOVE statement with the argument as the
       sending operand and the corresponding formal parameter as the receiving operand.
```

rule 2 d)'s MOVE lane governs — an alphanumeric sender into an alphanumeric receiver, which is legal — and
rule 2 a)'s COMPUTE lane, the one the diagnostic cites, is for an ARITHMETIC EXPRESSION argument. The
general permission is §15.2:

```
$ python scripts/spec/cite.py --check 15.2 "anywhere a sending data item of that class and category may be specified"
OK  §15.2   (Types of functions)
    The type of a function is determined by the class and category of the unique data item that results
    from the evaluation of that function, and the function so described may be used anywhere a sending
    data item of that class and category may be specified.
```

## The code site

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/OoBinder.cs#OoBindInvocationArg`, the
`arithCtx … explicitContent` arm. The grammar deliberately routes BY CONTENT through
`arithmeticExpression` — `CobolOO.g4#invokeArgument` says so in as many words, and says why: an alternation
listing `dataReference` beside `arithmeticExpression` silently destroys the identifier path, so **the
identifier case is recovered IN THE BINDER** from a sole-dataReference expression. That recovery exists
and covers exactly one shape. A function-identifier is a second shape it does not cover.

## The fix shape the report names, and it is right

A fifth member of the `ConditionBinder.SolePrimary` family — `SoleFunctionCall` already exists at
`ConditionBinder.cs:180` — routed to the identifier branch with a §15.4 result temp. The grammar comment
already names that family as the mechanism, so this is completing a design rather than inventing one.

⛔ **And the sweep is the real work.** "The parse node an operand lands in is not its meaning" is a
property of every slot the grammar routes through `arithmeticExpression` for prediction reasons: CALL's
BY CONTENT / BY VALUE, the INVOKE arms above, SEARCH's WHEN, and the partial-expression positions. Each
should be measured with a function-identifier argument, and the recovery should be ONE shared reduction
the arms call rather than a per-arm `is SoleDataReference` test. `feedback_one_rule_one_place`.

## Rows

None claimed. `SR-14.8.2.3.3-*` has no row for rule 2's lettered items in the inventory's shape (the
clause's rules are lettered prose — the exact case `cite.py`'s own docstring warns about), so the fix's
evidence is a golden, not a re-verdict.

## Landed — wave 49 (AD), branch worktree-wf_ca96470f-e1c-4

Re-measured on the worktree's own build at `b10cfa307`: `v6_invoke_fn.cob` still drew COBOLNET0828 ("rule 2a …
requires a category-numeric formal"); a run-able twin with an instantiated receiver (`LOWER-CASE`, `UPPER-CASE`,
`REVERSE` into a PIC X(8) formal) drew it three times. After: the three values cross by the MOVE rules
(`[  hi    ]`, `[  HI    ]`, `[    IH  ]`) and `MAX(N 12)` into a PIC 9(4) formal still takes the COMPUTE lane
(`[0012]`).

**The fix completes the recovery family the grammar comment names.** In `OoBinder.OoBindInvocationArg`, a sole
function-identifier (`ConditionBinder.SoleFunctionCall`) is recovered as §14.9.23.2's identifier-5 when the
FORMAL is not numeric — §14.8.2.3.3 rule 2 picks its lane by the formal, and for a numeric formal rule 2 a)'s
COMPUTE lane already IS the expression arm — and it crosses over the §15.4 temporary that the ONE sending-value
materializer (`SendingValueTemp.Materialize`, the MOVE/EVALUATE intermediate) provides, BY CONTENT for the same
SR9 reason as the inline-invocation temporary beside it. The same slot now shares one identifier path for the
three identifier formats (data reference, inline invocation, function-identifier).
A function the binder FOLDS to a constant (`FUNCTION LENGTH` of a fixed-length item) crosses through the literal
arms instead, so `BY CONTENT FUNCTION LENGTH(X)` into a PIC X(4) formal gives `[8   ]`, as `MOVE FUNCTION
LENGTH(X) TO R` does.

⚠ **Residue, deliberately not closed here:** a NUMERIC-typed, non-folded function into a non-numeric formal
(`BY CONTENT FUNCTION INTEGER(N)` into PIC X(4)) is still refused (COBOLNET0828, rule 2 a) wording). Rule 2 d)
admits an INTEGER function by Table 16, and `MOVE FUNCTION INTEGER(N) TO R` gives `[3   ]`; routing it over the
§15.4 temporary (`SendingValueTemp.FunctionValuePic`, 30 digits) was measured to cross as `[0000]` — the
temporary's representation is not the one MOVE moves from. Reported as a lead (the representation of a numeric
function value used as a character sender has two answers in the compiler).

**The sweep.** CALL is NOT a sibling: §14.9.4.3 SR3 — "Identifier-2 shall reference an address-identifier or a
data item defined in the file, working-storage, local-storage, or linkage section" — excludes a function-identifier
from CALL's identifier-2, so `CALL … BY CONTENT FUNCTION TRIM(X)` stays refused (its message cites Format 2 rather
than SR3 — reported as a lead). INVOKE's identifier-5 carries no such restriction (§14.9.23.3 SR21 only makes it
sending). The condition positions (SEARCH WHEN, relation comparands) already recover a sole function through
`ConditionBinder.SoleFunctionCall` (PB172).

Goldens: `2002/pb923_invoke_content_function_identifier` and
`negative/pb923-invoke-content-alnum-function-numeric-formal` (COBOLNET0844 — rule 2 a)'s COMPUTE sender shall
be numeric).
