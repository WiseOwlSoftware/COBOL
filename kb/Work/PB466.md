# PB466 — the procedure table throws away the fact that a name is ambiguous, then resolves it anyway

## Landed

**Re-probed first, on a fresh build of base `01062f29`, and it still reproduced exactly as written** — `GO TO
DUP-P` printed `ONE`, `PERFORM DUP-P` printed `ONE` / `BACK`, both with no diagnostic; and both legal controls
(rule 6 in-section, explicit `IN S-TWO`) were correct. Two further shapes the note predicted but had not
measured were probed here and were broken the same way: a paragraph-name duplicated WITHIN one section
(§8.4.2.2.3 SR7) compiled clean and ran the first copy, and a duplicated SECTION-name compiled clean and
performed the first section.

**THE REPAIR IS THE STRUCTURAL ONE THE NOTE ASKED FOR, AND ONE STEP FURTHER.**
`src/Cobol.Net.Compiler/Binding/Procedure/ProcedureNameMap.cs` is a new type whose whole job is that a
procedure-name scope REMEMBERS a repeated spelling — `Declare` keeps it, `IsDuplicated`/`CountOf`/`Definitions`
answer the §8.4.2.2.1 question at the reference. All FIVE `TryAdd` registrations are gone
(`ProcedureTableBuilder.AddParagraph` ×3, the two section maps, plus `StatementBinder.cs:282`'s method-scope
section map). The first definition still lives in the same single-probe dictionary and the duplicate list is
allocated only when a program actually collides, so the hot path is unchanged.

**The two scopes were two copies of the resolution algorithm, and the method copy had inherited the identical
hole one level down.** They are now ONE body, `ResolveProcedureWord`, that selects its maps — which is also what
made the third private copy visible: `FinalizeDebug`'s USE FOR DEBUGGING `ON procedure-name` subject reached
`_paraIndex`/`_sections` directly and now resolves through the same method, ambiguity diagnostic included.

**Two codes, because the two rules have different repairs.** `COBOLNET2121` (§8.4.2.2.1 rule 1 + §8.4.2.2.3
SR1) names every candidate with its section and source line and says "qualify or rename"; `COBOLNET2122`
(§8.4.2.2.3 SR7) says "rename", because §8.4.2.2.2 format 4 gives a paragraph-name only its section-name as a
qualifier and both declarations carry it — telling that user to qualify would be telling them to write
something the standard has no format for. Both are reported at the REFERENCE, never at the declaration, because
both rules are conditioned on "explicitly referenced": an unreferenced duplicate is conforming and compiles,
which the positive golden measures.

**The candidate count sums paragraphs AND sections** (§14.4.1 — "A procedure-name is a word used to refer to a
paragraph or section"), which is how the duplicated-section-name arm the note did not list gets covered.

**The full caller sweep the note demanded is covered by construction** — every site in the note's table goes
through `ResolveProcedureOperand`, so the fix is at the one step, and each verb has its own witness: GO TO,
PERFORM and PERFORM…THRU (`negative/pb466-ambiguous-procedure-name`, the THRU written with an unambiguous first
operand so the RANGE END is what is measured), ALTER at 85 (`negative/pb466-ambiguous-alter-85`), RESUME AT at
2002+ (`negative/pb466-ambiguous-resume-at`), SORT INPUT/OUTPUT PROCEDURE (`negative/pb466-ambiguous-sort-procedure`),
the section-name arm (`negative/pb466-ambiguous-section-name`) and SR7
(`negative/pb466-paragraph-name-duplicated-in-section`). The legal side is
`tests/conformance/85/pb466_procedure_name_uniqueness.cob` (PROGRAM-ID `PB466UNIQ85`): format-4 qualification,
rule 6 measured as two IDENTICAL unqualified sentences printing different lines, and an unreferenced duplicate
compiling clean. `ProcedureNameUniquenessDriftTests` pins the shape (no scope may register with `TryAdd` or an
overwriting indexer — with a fact that fails the scanner on the pre-fix lines) and the behaviour at all four
editions.

**Rows.** `inventory_rows` is no longer empty: `SR-8.4.2.2.1-6` (rule 6) and `SR-8.4.2.2.3-7` (SR7) are entirely
about paragraph-names, are now implemented and witnessed both ways, and are recorded CONFORMS (batch
`pb466-procedure-name-uniqueness`; GAP 2422 → 2420). ⛔ **DELIBERATELY NOT CLOSED:** `SR-8.4.2.2.3-1` and
`SR-8.4.2.2.1-1` state the uniqueness requirement over EVERY user-defined name class, and only the

## THE MECHANISM

`src/Cobol.Net.Compiler/Binding/Procedure/ProcedureTableBuilder.cs#AddParagraph` (`:43-58`) registers every
paragraph into three maps. The global one is line `:52`:

```csharp
_paraIndex.TryAdd(name, _paras.Count); // first definition wins for the global fallback
```

`TryAdd` **silently discards the second and every later definition of a duplicated name**. The table therefore
does not merely fail to diagnose ambiguity — after `AddParagraph` runs it has no way to *represent* it: the
multiplicity is gone by the time anything could ask.

`#ResolveProcedure` (`:174-197`) then walks explicit qualifier → in-section → global → section-name:

```csharp
if (qualifier is not null) …                                                     // :191 — correct
if (ctx.CurrentSection is { } cur && cur.Paras.TryGetValue(head, out int local)) // :194 — correct (rule 6)
    return (local, local);
if (_paraIndex.TryGetValue(head, out int pc)) return (pc, pc);                   // :195 — THE ESCAPE
```

The first two arms implement §8.4.2.2.1 rules 6 and the qualified case exactly. The third is a fall-through that
answers "some paragraph with this spelling" when the standard's answer is "this reference is not unique and
requires qualification".

## THE RULE, QUOTED, WITH ITS `--check` LINES

- `--check 8.4.2.2.1 "uniqueness shall be established through qualification"` → `OK §8.4.2.2.1 (General)`.
  The lead paragraph: "Identical user-defined names may be specified in a source unit; however, uniqueness shall
  be established through qualification for each user-defined name explicitly referenced, except as specified in
  rules 2 through 6."
- `--check 8.4.2.2.1 "Qualification of a user-defined name is required unless one of the following is true"` →
  `OK §8.4.2.2.1 (General)` — the sentence that governs the numbered list.
- `--check 8.4.2.2.1 "No other name has the identical spelling"` → `OK §8.4.2.2.1 1)`. Rule 1 is the only
  excuse that could apply to a duplicated spelling, and it is false by construction here.
- `--check 8.4.2.2.1 "The name is a paragraph-name and the section containing the reference also contains the named paragraph"`
  → `OK §8.4.2.2.1 6)`. Rule 6 is the paragraph-specific excuse — and it is *conditioned on the referencing
  section containing the paragraph*, which is precisely what is false when the two definitions live in two
  OTHER sections.
- `--check 4.2.2 "syntax"` → `OK §4.2.2 (Acceptance of standard language elements)` — the source is
  non-conforming and owes a compile-time indication.

Rules 2-5 concern REDEFINES, VARYING, type declarations and data-names subordinate to a common group; none
reaches a paragraph-name.

## EXPECTED vs OBSERVED — measured on HEAD

`scratchpad/probe-g3-goback-goto/refute-go-to/g3-ambiguous-dup.cob`:

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. RFG3AMBG.
       PROCEDURE DIVISION.
       S-THREE SECTION.
       P3A.
           DISPLAY "START".
           GO TO DUP-P.
       S-ONE SECTION.
       DUP-P.
           DISPLAY "ONE".
           STOP RUN.
       S-TWO SECTION.
       DUP-P.
           DISPLAY "TWO".
           STOP RUN.
```

`DUP-P` is defined in `S-ONE` and in `S-TWO`; the reference is in `S-THREE`, which contains neither, so rule 6
does not excuse it and rule 1 is false. **Expected:** rejected at compile time — the reference is not unique.

```
$ cobol.exe scratchpad/probe-g3-goback-goto/refute-go-to/g3-ambiguous-dup.cob --std 2023 --run
START
ONE
```

Compiles with **no diagnostic** and transfers to `S-ONE`'s copy — the first definition in source order.
Identical at `--std 85`. The choice is invisible: adding a third `DUP-P` above `S-ONE`, or reordering the
sections, silently changes which statements a legal-looking program executes.

**The escape is NOT GO TO's.** `scratchpad/probe-g3-goback-goto/amb/perfamb.cob` is the same shape with
`PERFORM DUP-P.` in `S-THREE`: `cobol.exe … --std 2023 --run` prints `START` / `ONE` / `BACK` — same silent
first-definition pick, same absence of a diagnostic.

**Both legal paths are correct and must stay correct** (these are the controls the repair must not break):
`amb/insection.cob` — `GO TO DUP-P.` written in `S-ONE`, which also contains `DUP-P`, is excused by rule 6 and
prints `ONE-LOCAL`. `go-to/p17-qualified.cob` — `GO TO DUP-P IN S-TWO` reaches `S-TWO`'s copy and prints
`S-TWO-DUP`. **No legal program is mis-resolved**, which is why this note is recorded as an under-rejection
rather than a wrong answer (see the flags note below).

## THE SHAPE OF THE REPAIR

**The correct behaviour is a DIAGNOSTIC, not a different silent choice.** §8.4.2.2.1 does not offer a
tie-breaking rule for procedure-names — it says qualification is required — so "resolve to the nearest
preceding definition", "resolve to the last", or any other disambiguation would be a second wrong answer with a
different flavour. The compiler must say the reference is ambiguous and name the candidate sections.

⛔ Not a check bolted onto `ResolveProcedure`'s fall-through (CLAUDE.md rule 5). The information needed to
answer the question is **destroyed at registration time** by `TryAdd`, so a test at the resolve site would have
nothing to test. The structural repair is to make the global map carry multiplicity —
`Dictionary<string, List<int>>`, or a first-pc plus a duplicate-spelling set — so that `:195` can distinguish
"exactly one definition" (resolve) from "more than one" (diagnose), and so that the table can *state* what it
knows rather than having silently forgotten it. Pair it with a drift test asserting that no name map in the
procedure table uses `TryAdd` to swallow a redefinition.

The diagnostic pattern to copy already exists one subsystem over, on the DATA side, for the identical rule
shape: `src/Cobol.Net.Compiler/Binding/DataBinder.cs:1852-1859` raises an error when a qualified reference does
not resolve to exactly one entry, citing §8.4.3.2. The procedure side needs the same "exactly one candidate"
shape citing §8.4.2.2.1. `feedback_two_arm_dispatch` in its data/procedure form: one rule about unique
reference, written for data names and never for procedure names.

## THE SIBLING SWEEP the fixer must do

Every caller of `ProcedureTableBuilder.ResolveProcedure` reaches the same fall-through, so the ambiguity escape
belongs to none of them individually:

| site | statement |
|---|---|
| `Verbs/ControlFlowBinder.cs:228`, `:234` | GO TO Format 2 targets, GO TO Format 1 |
| `Verbs/ControlFlowBinder.cs:303`, `:308` | PERFORM procedure-name-1, PERFORM … THRU procedure-name-2 |
| `Verbs/EcBinder.cs:135` | RESUME AT procedure-name |
| `Verbs/SetAlterBinder.cs:52`, `:125`, `:130` | the ALTER pre-scan and ALTER's two operands (85) |
| `Verbs/SortBinder.cs:428`, `:432` | SORT/MERGE INPUT and OUTPUT PROCEDURE, and their THRU ends |
| `ProcedureTableBuilder.cs:365-366` | `SortMergeProcedureRanges`, the range computation |

Two of these are worse than GO TO's case and should be probed explicitly: a **PERFORM … THRU** whose two
operands resolve ambiguously produces a *range*, so an arbitrary pick can silently execute an arbitrary span of
the program; and the `SortMergeProcedureRanges` walk swallows a failed resolve with a bare `return`, so it has
no diagnostic path at all today.

Also to check in the same pass: the method-confined arms at `:181-190` use `TryGetValue` over the method's own
maps, which are populated by the same `TryAdd` at `:50` — the method scope has the identical hole, one level
down (§11.7).

Goldens: a negative fixture per verb in the table above, plus positive goldens for the two legal paths measured
here (rule 6 in-section, and explicit qualification), so a later "make resolution more forgiving" edit fails.

## A note on the harm flags

Set from measurement, and deliberately NOT `wrong_answer: true`. Every program that reaches the escape is
**non-conforming** — §8.4.2.2.1 requires qualification — so the standard defines no correct target for the
reference, and claiming the compiler computes a *wrong* one would over-claim. What is measured is that illegal
source compiles clean (`under_rejects`) and is then given a specific, source-order-dependent, invisible
resolution (`silent`). Severity is MAJOR rather than MINOR because that silent choice determines which
statements run: a duplicated paragraph-name across sections is ordinary in real COBOL — rule 6 exists because
it is ordinary — so this is the shape where a rename produces a program that runs and does the wrong thing with
no diagnostic anywhere. Re-grade it if the register prefers to score the user-visible effect rather than the
conformance status of the source.
