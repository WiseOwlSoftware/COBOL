# PB3414 — the READ ONLY keyed writer's store mutex has no behavioural witness

Filed by the operator from the Mythos lane's review of `worktree-wf_14a1e62b-326-19` (PB3335), round 5, lead R5-L1
(the reviewer graded it MEDIUM, inventory witness; `E:\COBOL-coord\scratch\reports\w1118a5-PB3335-report.md`). PB3335 landed with PB3336 in
PR #268 (main 0eba56a75, 2026-10-18 23:19).

**The site (on main at 0eba56a75).** `src/WiseOwl.Cobol.Runtime/IO/KeyedConnector.cs` line 150, in `TakeFileLock`:
`_coherent = FileLockPosture.AdmitsAnotherRunUnit(HostShare)`. The traceability row GR-14.9.51.4-12 names this member.
The rule: every sharing mode but NO OTHER admits another run unit's connector (§9.1.15 1)), so a keyed writer under
`SHARING WITH READ ONLY` must run each statement under the store mutex. Otherwise an INPUT reader in another run unit,
which §9.1.15 2) admits beside it, can follow a tree whose page a later statement reuses from the ledger's released pages
(DESIGN-runtime-library.md §2.2.1.7).

**The gap (the finisher's measurement, as the reviewer recorded it).** Change line 150 to `AdmitsAnotherWriter`.
`AKeyedReadOnlyWriter_IsReadByAnotherRunUnit_AtTheWrite` (both organizations) stays green, and so do all 48
`KeyedStoreReloadFailureDriftTests` cases. Only
`StoreCoherenceTests.The_keyed_store_asks_about_any_run_unit_and_the_sequential_release_about_any_other_connector`
(StoreCoherenceTests.cs:644) catches it, and it does so by source text: `KeyedConnector.cs` must call
`AdmitsAnotherRunUnit` and must not call `AdmitsAnotherWriter`. That case is not in the row's test-ref. The
`Two_run_units_*` cases cover ALL OTHER only.

**The fix (MANDATORY-PRACTICES I11 applies: the abnormal path is the point).**
1. Add the StoreCoherenceTests case to GR-14.9.51.4-12's test-ref through a `record_verdicts.py` batch.
2. A behavioural page-write ordering witness at the `KeyedStore.MediumObserver` seam. Hold run unit A's READ ONLY
   statement after its first tree-page write and before page 2, then show that run unit B's INPUT statement waits on the
   mutex and reads the tree as it stood before A's statement, or after it, never between. The witness must go red under
   the line-150 mutation. Add it to the row's test-ref.

**Landed (wave 1132 E).** The re-probe on a fresh build reproduced the gap exactly: with line 150 weakened to
`AdmitsAnotherWriter` the READ ONLY cases of the new witness go red and the existing behavioural cases stay green. The code is
unchanged. `ReadOnlyKeyedWriterStoreMutexTests` is the behavioural witness (both organizations, `SHARING WITH READ ONLY` and
`ALL OTHER`, the machine's region host and the lock-file host). At every page write and sync of a WRITE, REWRITE and DELETE (the
tree pages 6 and 7, then page 2, each observed before it is made) a second read-access handle asks the region host whether
the store mutex byte is held by another handle, and it is. A host refusal of each page write of a WRITE in turn answers '30',
leaves the mutex free on the host at the answer, lets the other run unit's INPUT reader read the tree as it stood (record 3
absent, '23'), replays the permanent error to the next statement without touching the file, and the CLOSE answers '00'.
The witness is a deterministic seam probe, not a thread race: a reader started inside the writer's statement and left to race
would pass under the weakening most of the time, so "the reader waits" is asserted as the mutex held at the moment of each
write, which is the only thing that makes it wait. Both new cases and the source-text case
`StoreCoherenceTests.The_keyed_store_asks_about_any_run_unit_and_the_sequential_release_about_any_other_connector` are in
GR-14.9.51.4-12's test-ref (record_verdicts batch `pb3414-keyed-read-only-writer-mutex-witness`; GAP 66 to 66).
PB3415 (the stale comments in `StoreCoherenceTests.cs` and `FileLockPosture.cs`) is another group's and was not touched.
