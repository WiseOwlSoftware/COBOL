# PB1197 — OPEN

## The rule (every citation re-run by the registrar through `cite.py --check`)

> RAISE { EXCEPTION exception-name-1 | identifier-1 }

`python scripts/spec/cite.py --check 14.9.29.2 "…"` → `OK  §14.9.29.2   (General format)`

## Refuter evidence — row `FMT-14.9.29.2` (PARTIAL)

PARTIAL — identifier-1 in the general format is ANY identifier (§8.4.3.1.2 Formats 1-9) that is an object reference, but the grammar narrows it to objectReference (dataReference|NULL|SELF|SUPER). Two legal identifier-1 shapes are rejected at the parse. The first is the inline method invocation (§8.4.3.1.2 Format 4). §8.4.3.4.3 SR1 bars it only as a receiving operand, and RAISE SR3 makes identifier-1 a sending operand. The second is the object-view (Format 5, §8.4.3.5.3 SR2, receiving-only ban). The compiler's own inlineMethodInvocation rule exists and parses in SET ... TO, so this is RAISE-specific for the inline invocation. The EXCEPTION alternative and plain data-name object references do conform.

**Code site.** src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4#raiseStatement; src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.cs#BindRaise; src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs#RAISE (raise-statement-2002, COBOLNET0876)

## What the fixer owes

CobolParserCore.g4#raiseStatement: admit the sending-identifier forms (inline invocation, object-view) and screen object-reference-ness in EcBinder.BindRaise (SR2 keeps its targeted diagnostic for NULL/SUPER/SELF). Sweep the other statements whose format writes identifier-n for an object-reference SENDER and whose grammar uses objectReference. Positive golden at 2002.
