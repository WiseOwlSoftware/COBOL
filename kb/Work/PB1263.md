## Landed (wave 1015 Y)

**Fix.** `DataBinder.OccursKeyResolve` (`DataBinder.Odo.cs`) now asks `OccursKeyItemFault` of every KEY data-name-2 that resolved within the table (SR3, COBOLNET2353, stays where it was). The new check applies §13.18.38.3's four constraints on what a key may be, and each one draws the new **COBOLNET2787** `occurs-key-item-not-admitted`:
- **SR4:** a group strictly between the table and the key that contains an OCCURS clause and is one of the rule's own four group kinds (asked through `ItemCategory.GroupKindsOf`).
- **SR6:** a key other than the subject whose own entry is a table (`IsTable`: fixed, occurs-depending or dynamic).
- **SR8:** a key of class boolean, message-tag, object or pointer. This uses the new `ItemCategory.IsBooleanMessageTagObjectOrPointer`: boolean comes from the operand PICTURE (so a bit group counts), and the other three come from the SR14 usage population, which is exactly those three classes.
- **SR9:** a variable-length group (`GroupKinds.VariableLength`, §8.5.1.12.1).

A refused key is recorded as unresolved, so SEARCH ALL and the table SORT never order on it.

**Sibling sweep.** The same check runs for Formats 1, 2 and 4, because `OccursKeyResolve` walks every table that has keys, the dynamic ones included. The sweep also covered the KEY phrase of the table SORT statement, which is a statement operand with its own rule set. That phrase is not this rule, and it reads `ResolvedKeys` (so a refused key never reaches it).

**Witnesses.** The positive is `conformance:85/pb1263_occurs_key_items_admitted`: a group key, a key beside a sibling table, and the subject as its own key, each answering SEARCH ALL. The four negatives are `conformance:negative/pb1263-occurs-key-under-nested-table`, `-is-table`, `-boolean` (2002+) and `-variable-length-group` (2014+). Rows SR-13.18.38.3-4/6/8/9 were re-verdicted CONFORMS (batch `w1015y-pb1263`), which moved the GAP from 336 to 332.
