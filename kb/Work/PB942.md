# PB942 — OPEN — one clause, one violation, two messages

Source: the **PB587 (data-description screens) implementer report**, "New defects" item 1, which states the
defect is **PRE-EXISTING** — *"my SR6 screen inherits the shape rather than creating it"* — and that it shares a
code site with the report's second lead.

## Observed, MEASURED on this tree (`e_thru_twice.cob`, `--std 2023`)

```
       01 N PIC N(3).
          88 NR VALUE "AAA" THRU "CCC".
```

```
  …e_thru_twice.cob(6,11): error COBOLNET0898: condition-name 'NR': the VALUE of a national data item shall be
    a national literal (N"…") or a figurative constant (ISO §13.18.63 SR5)
  …e_thru_twice.cob(6,11): error COBOLNET0898: condition-name 'NR': the VALUE of a national data item shall be
    a national literal (N"…") or a figurative constant (ISO §13.18.63 SR5)
```

Two identical messages, same code, **same line and same column** — not two findings at two positions. The PB587
report measures the second spelling too: `01 X PIC ZZ9.99. 88 XR VALUE 1 THRU 9.` at `--std 85` gives two
identical COBOLNET0900.

## Expected, from the standard

```
$ python scripts/spec/cite.py --check 13.18.63.3 "The words THROUGH and THRU are equivalent"
  OK  §13.18.63.3 28)  (Syntax rules)
      28) The words THROUGH and THRU are equivalent.
```

§13.18.63.2 Format 3 writes the range as `literal-2 { THROUGH | THRU } literal-3` — **one value specification**,
which §14.7.8 evaluates as a range and which §13.18.63.3's own rules address as a unit (SR26 is about the pair,
SR27 about literal-4 against "any occurrence of literal-2"). One clause, one violation, one message.

## The code site

`src/Cobol.Net.Compiler/Binding/DataBinder.cs` — `BindCondition`'s range arm, which calls `ValidateValueCategory`
**once per endpoint** and lets each call report. The two-endpoint call is correct (each endpoint genuinely has to
be screened); what is wrong is that the REPORTING is per call rather than per clause.

The minimal shape is not "suppress the second message" — that is the workaround, and it goes wrong the moment the
two endpoints violate DIFFERENT rules (`88 R VALUE 1 THRU N"C".`, where one endpoint is the wrong class and the
other the wrong category). The shape that makes the next case automatic is to screen both endpoints, collect the
findings, and report **the clause's** finding once, naming the offending endpoint(s) — which is also the only
form that can say `literal-2` versus `literal-3` in the message, as the standard's own rules do.

## Why this is filed as its own mechanism and not folded into `PB586`

`PB586` (open) is *"§13.18.63.3 SR2's RANGE half never reaches a level-88 (Format 3) literal"* — a rule that is
**not asked at all**. This note is about a rule that IS asked, correctly, and then reported twice. Different
defect, same method, same sitting: `cluster:` hands them to one implementer, and an implementer who lands PB586
without this one will double-report SR2's new diagnostic too, because it will be added at the same per-endpoint
call site.

## The sibling sweep the fixer owes

Every screen reached from a REPEATED operand list in a general format, not only this one. Ask at each: does the
message count match the number of CLAUSES the programmer wrote, or the number of OPERANDS the binder walked?
Named starting points: the multi-operand VALUE (§13.18.63.3 SR35, which `PB921` gates per literal), `88 … VALUE
a, b, c THRU d`, the OCCURS `ASCENDING KEY` list, and the SET Format-3 condition-name list train 43 widened
(`PB450`). Add every one that double-reports to this note before closing.
