# PB639 — LANDED — the same wrap, one statement class over

Found 2026-09-05 by the `PB288` implementer (report §"Two new defects" (1)), which fixed the CALL crossing by
routing it through `CobolNum.RescaleStoreCap` — the primitive DOC-A.1-70 names — and then measured that the inline
COMPUTE the standard says the crossing IS does not use it either. Deliberately not taken there: a different
emitter, a real blast radius (every arithmetic statement's no-phrase store), its own implementer.

## Repro (`--std 2023`, no `ON SIZE ERROR`, no `>>TURN EC-SIZE CHECKING ON`)

```cobol
       01 WC PIC S9(9)V9(9).
       ...
           COMPUTE WC = 1000000000000000000000000000000
           DISPLAY WC                        *> -123822295.304634368 (observed)   0.000000000 (DOC-A.1-70)
```

The observed value is the two's-complement wrap of 10³⁰ × 10⁹ inside the Int128 carrier — the same number the
CALL crossing produced BY VALUE before PB288.

## The rule

§14.7.5 r3: "if, after radix point alignment and any applicable rounding specifications, the result of an
arithmetic statement is further from zero than permitted for the associated resultant data item" (`OK §14.7.5
3)`) — the size error condition exists; with no SIZE ERROR phrase and checking off, what the receiver holds is the
implementor's documented determination, and `docs/CONFORMANCE.md` DOC-A.1-70 documents it as the result's
LOW-ORDER digits (the `RescaleStoreCap` disposition), never a wrapped carrier. The doc and the code disagree today,
which is the shape [[a_dead_lookup_is_also_unverified]] warns about in a determination's clothing: a documented
answer nothing re-measured.

## The mechanism

`src/Cobol.Net.Compiler/CodeGen/Verbs/ArithmeticEmitter.cs`: the two landings at `:372` and `:405` render
`RuntimeApi.NumRescale(value.Expr, scale, receiverScale, mode, checkedPath)` — `CobolNum.Rescale`, the plain
rescale that the file's own comment at `:391` calls "silent truncation — the DEVLOG-610-audited PROHIBITED leak".
The CHECKED path (`checkedPath`, the SIZE ERROR / EC-SIZE arm) raises correctly; the UNCHECKED path is where the
determination applies and where the wrap lives. PB288 landed the correct primitive for the ABI
(`CobolArgAdapt.Land` = `RescaleStoreCap` + `CobolNum.Store` capacity conformance); the inline path never adopted
it.

## Fix shape

One store primitive for a numeric result with no phrase and checking off — DOC-A.1-70's — used by BOTH the inline
arithmetic landing and the CALL crossing (PB288's `Land`), so the determination is written once: replace the
unchecked `NumRescale` at both `ArithmeticEmitter` sites with the `RescaleStoreCap` + capacity-conformance pair (or
a `RuntimeApi.NumStoreCap` that wraps them), keep the checked path as it is, and sweep every other
`RuntimeApi.NumRescale` render in the emitters (MOVE's numeric landing, the intrinsic landing, the SET arithmetic
forms) against the same question: is this an unchecked store into a receiver whose capacity the value can exceed?
Goldens at 2002/2014/2023: the repro above (0.000000000), a 19-digit case (the `CreateTruncating` boundary PB288
found), the ON SIZE ERROR twin (receiver unchanged, §14.7.5 r1) and the CHECKING ON twin (EC-SIZE-TRUNCATION),
plus a drift test that no emitter renders `NumRescale` on an unchecked numeric-receiver store — derived by scanning
the emitters, the way `CarrierLandingFormTests` scans `IntrinsicRenderer`. Update DOC-A.1-70's test-refs to the new
goldens; the row's determination text stands.

## Landed — 2026-09-05

Reproduced first on a fresh build (`C1=12382229530463436Q` = −123822295.304634368), then the note's own mechanism
statement was found to be **half right and half wrong**, and the mechanism itself **bigger in both directions**.

**Where the note was wrong.** `ArithmeticEmitter.cs:372` and `:405` are the LOCALE-edited and numeric-EDITED arms;
the repro's receiver is plain `PIC S9(9)V9(9)`, whose store never touches them. The plain numeric landing wraps
inside `CobolNum.Store` itself — the very function `CONFORMANCE.md` DOC-A.1-70 names as "the classic high-order
truncation". The note's "the CHECKED path raises correctly" is also wrong, and that was the worse defect: the
capacity check ran on the WRAPPED alignment, so a wrap that landed back inside the picture read as fitting.
`COMPUTE WC = 340282366920938463463374607432 ON SIZE ERROR` — a legal 30-digit literal (§8.3.3.3.2) that is
ceil(2^128 / 10^9) — ran **NOT ON SIZE ERROR** and stored +0.231788544 where §14.7.5 storing rule 2 requires the
receiver unchanged; the same statement under `>>TURN EC-SIZE CHECKING ON` raised **nothing at all**.

**The rule, all citations mechanically checked.** §14.7.5 case 3 (`OK §14.7.5 3)`) is a fact about the ALGEBRAIC
result "after radix point alignment", never about a wrapped carrier. No-phrase rule 4 (`OK §14.7.5 4)`) sets
EC-SIZE-TRUNCATION; §14.6.13.1.3 item 8 (`OK §14.6.13.1.3 8)`) hands the checking-off disposition to the
implementor, and DOC-A.1-70 documents it as the result's LOW-ORDER digits. The MOVE twin is §14.6.8.2 r4
(`OK §14.6.8.2 4)`) — "the data is aligned by decimal point and is transferred to the receiving digits with zero
fill or truncation on either end". With the phrase, storing rule 2 (`OK §14.7.5 2)`) leaves the receiver unchanged.

**The fix — one predicate, and one split the note did not ask for.** `CobolNum.WideningFits(value, up)` is now the
ONE test of "can the carrier form this alignment", asked BEFORE the multiply by `RescaleEscape` (throws the case-5
EC-SIZE-OVERFLOW), `RescaleChecked` (throws the case-3 EC-SIZE-TRUNCATION — it previously only tested PROHIBITED),
`TryStore` and `CobolEdit.TryFormat` (both return false). It is MinValue-safe by construction. The UNCHECKED store
then **splits on the receiver's capacity discipline**, because "the low-order digits" means two different things: a
DISPLAY/COMP/PACKED receiver takes the DECIMAL low-order digits (`RescaleStoreCap` — the ≤38-digit cap applied
before the multiply, exact because 10^D divides 10^38), while a BinaryCapacity receiver takes the CONTAINER's
two's-complement residue, where the carrier's own wrap modulo 2^128 is already exact and must NOT be capped.
`StoreU` has had that split since R10; `Store` was the unfixed arm — [[two_arm_dispatch]] again. `CobolEdit.Format`
took `RescaleStoreCap` for the same reason, and the emitter's receiver-bound alignment got its own spelling,
`RuntimeApi.NumRescaleStore(…, bool checkedPath)`, with NO default; `RuntimeApi.NumRescale` is now only the
value-semantics narrowing helper the three integer sites use.

**Goldens.** `pb639_store_landing_low_order_digits` at 2002 / 2014 / 2023 — eight rows, every expected value
derived in the file's own header. Six are red on the pre-fix compiler and the two that are not are the deliberate
pins (the COMP-5 residue that must not change, and the in-capacity control). `CarrierLandingFormTests` gained the
native carrier's three landings, the wrap-into-capacity fact, the `WideningFits` boundary, the edited twin and two
source-scanning drift guards; `SizeErrorDispositionTests` gained the no-phrase CHECKING-ON disposition (which
terminates naming EC-SIZE-TRUNCATION) and its checking-off twin.

**Inventory.** `GR-14.7.5-L3.4` (no-phrase rule 4 over the RESULT) GAP → CONFORMS, GAP 2864 → 2863;
`GR-14.7.5-3` kept CONFORMS with its evidence refreshed — it had been closed on capacity checks that ran on a
wrapped value.

**Docs.** DOC-A.1-70 now says what "low-order digits" means per capacity discipline and carries the new test-refs;
DOC-A.1-179 gained item (4), the receiver-bound alignment under checking; `COBOLNET_NUMERIC_DESIGN.md` gained the
native lane's third landing form and the capacity-discipline split, next to PB77's two-form rule.
