# PB1400 — LANDED (wave 1095, group J)

## Landing

**Re-probed** on the w1095j build (`E:\COBOL-coord\scratch\w1095\w1095j\probe\p1.cob`, `p2.cob`): `COMPUTE N = GB + 1`
on a `GROUP-USAGE BIT` group drew `group item 'GB' (class alphanumeric, ISO §8.5)`, and the same for its subordinate
group GBS, the `GROUP-USAGE NATIONAL` group GN and its subordinate GNS, and a strongly-typed group SG (whose §8.5.2.1
class is its type-name). The same arm family said `class alphanumeric` for every reference-modified operand
(`NN(1:1)` of a `PIC N(2)` item is class national, §8.4.3.3.4 GR6), and a sibling mechanism spelled a class from the
enum name: a numeric-edited subscript read `item 'NE' of class numericediteddeediting`, and CALL / CANCEL targets, BY
VALUE arguments (CALL, INVOKE, a user-defined function) and a report CODE operand did the same.

**Fix.** `IntrinsicArgumentRules.ClassNameOf(Place)` spells the §8.5.2.1 class of a place through `ClassOfPlace` and
`Name` (the one Table-2 spelling); only a strongly-typed group differs, naming its type-name (§8.5.2.1: "Both the
class and the category of a strongly-typed group item are the type-name specified in the TYPE clause"), where
`ClassOfItem` keeps §15.3 2)'s argument-position alphanumeric. `ExpressionBinder.NonNumericOperandKind`'s ref-mod,
group and trailing arms ask it; every `CobolClass` rendered with `ToString().ToLowerInvariant()` now goes through
`IntrinsicArgumentRules.Name` (ReferenceResolver, DataBinder.Reports, CallBinder ×3, OoBinder, UdfBinder,
EvaluateBinder ×3, AllOrNothingClass ×2, ExpressionBinder ×2). `ClassSpellingDriftTests` (Unit, tree sweep) pins it.
The refusals themselves were already right and are unchanged.

**Witnesses.** `conformance:2002/pb1400_group_usage_operand_class` (bit group and its subordinate group as boolean
operands; national group and its subordinate group as national operands), `negative/pb1400-group-usage-arithmetic-operand`
(COBOL0844 at 2002/2014/2023), and `ArithmeticOperandClassTests.TheRefusal_NamesTheSection8521ClassOfTheOperand`
(the text, per edition). Rows GR-8.5.2.5-3 and GR-8.5.2.10-3 PARTIAL → CONFORMS (GAP 83 → 81).

**Review round 1 (finding R1-1, w1095j review finisher).** The class doc of `ArithmeticOperandClassTests` still stated
the refuted rule ("A group item (class alphanumeric, §8.5) … NOT permissible"), and the sweep found it in eleven more
places: the `ExpressionBinder` class doc, `CorrespondingBinder` (CORRESPONDING rule 3), `IntrinsicBinder` (MAX/MIN
string arm, which admits national and boolean groups), `OperandText` (group comparison; §8.8.4.2.1 treats only an
ALPHANUMERIC group as elementary alphanumeric), `TierCRejectionTests`, the fixtures `da6-group-numeric-operand`,
`l1_display_admitted_classes`, `pb59_operand_category_total` (×2), and — wrong in a different way — the COBOL1796
message text, `DataBinder.UsageDeclaration` and `pb231-external-pointer-item`, which called a strongly-typed EXTERNAL
group "class alphanumeric" where §8.5.2.1 makes its class its type-name. All corrected; the SR4 verdict they explain
is unchanged (the group is still not class pointer). `ClassSpellingDriftTests.NoSourceOrCorpusComment_SaysEveryGroupIsClassAlphanumeric`
now scans every C# source and corpus program for the universal claim.

**Review round 2 (findings R2-1, R2-2, w1095j review finisher).** R2-1: round 1's `OperandText` rewrite said an
alphanumeric group is "the only kind that holds" BINARY/PACKED leaves; a strongly-typed group can hold them too (its
class is its type-name, §8.5.2.1). The comment now says so, and why it never reaches the image as a compare operand
(§8.8.4.2.3 SR1 admits only a same-type pair, which §8.8.4.2.12 compares element by element). R2-2: the drift pattern
missed a second shape, the class INFERRED from groupness ("is a group item and so of class alphanumeric"), in
`l1-initialize-replacing-category-repeat` and `l1_test_numval_f_class_screen`. The pattern gained that shape and now
reads whole files with comment continuations joined, so a claim a line break splits is caught; it found four more
sites (`IntrinsicResultType.OperandCategory`'s doc, `SortEmitter`'s group-key arm, `TierCRejectionTests`,
`da5_table_sort_group_key`), all corrected. On the base tree it reports 19 sites, the pb59 split line among them.
`TheUniversalClaimPattern_CatchesTheFormsItWasWrittenIn` pins the forms caught and the true statements that pass.

## Measured (rows this note claims beyond the findings above)

### `GR-8.5.2.5-3` — PARTIAL (adjudicator + refuter record, verbatim)

Rule: '3) A group item explicitly or implicitly described with a GROUP-USAGE clause with the BIT phrase.' (cite.py OK). Both halves verified: explicit (GB) and IMPLICIT (subordinate group GBS inside a GROUP-USAGE BIT group) -- probe p2.cob: LENGTH(GBS)=6 boolean positions (§15.50.4 r1), MOVE B"110011" TO GBS -> GB1=1100 GB2=11. pb522 golden derives the boolean-position LENGTH of explicit and nested bit groups from §8.5.2.5 item 3 + §15.50.4. || REFUTED: PARTIAL — The LENGTH, MOVE and COMPUTE-boolean paths treat a GROUP-USAGE BIT group as boolean. GBS B-OR B"101010" works, and MOVE GB TO a PIC 1(4) item gives 1011. But a second site restates group class without the GROUP-USAGE branch: ExpressionBinder.NonNumericOperandKind has the arm '_ when p.Item.IsGroup => class alphanumeric, ISO 8.5'. So COMPUTE N = GB + 1 on a bit group is rejected with a diagnostic that tells the user the bit group is 'class alphanumeric'. §8.5.2.1 and §8.5.2.5 item 3 make it class and category boolean. This is one rule in two places, and one of them is wrong for this rule's subject. The rejection itself is correct. Fix: derive that text from ItemCategory.GroupKindsOf / ClassOfItem.

### `GR-8.5.2.10-3` — PARTIAL (adjudicator + refuter record, verbatim)

Rule: '3) A group item explicitly or implicitly described with a GROUP-USAGE clause with the NATIONAL phrase.' (cite.py OK). Both halves probed (p2.cob): subordinate group GS inside '01 GN GROUP-USAGE NATIONAL' -> LENGTH 3 national positions, BYTE-LENGTH 6, and MOVE "XYZ" TO GS converts to national as an elementary PIC N(3) (§13.18.29.4 GR2 b) -> GN1=XY GN2=Z. pb522 derives explicit + nested national group LENGTH; negative/pb59-display-of-group pins the complement (a plain group is not national). || REFUTED: PARTIAL — MOVE, LENGTH and the SR10 screen treat a GROUP-USAGE NATIONAL group as national. MOVE 'PQ' TO GN converts, and MOVE GS TO X2 is rejected as a national sender. The same second site as the bit group, ExpressionBinder.NonNumericOperandKind's IsGroup arm, gets it wrong: COMPUTE N = GB + 1 on a national group is diagnosed as 'group item GB (class alphanumeric, ISO 8.5)', but §8.5.2.10 item 3 / §8.5.2.1 make it class national. Two sites derive group class, and one lacks the GROUP-USAGE branch. There is also a group-MOVE lead, recorded under GR-8.5.2.3-3: a national group moved into an alphanumeric group is converted instead of being copied without conversion (§14.9.25.4 GR5).

Derive the diagnostic's class text from ItemCategory.GroupKindsOf / ClassOfItem (the one derivation LENGTH/MOVE already use) and delete the private IsGroup arm. The refusal itself is correct; this is the one-rule-two-places shape.
