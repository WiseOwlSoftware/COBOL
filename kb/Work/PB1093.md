# PB1093 — OPEN — the collating model answers 'the highest alphanumeric character' over the LATIN-1 block although the native alphanumeric set is the 65,536 UTF-16 code units: `C

## Rule text (every citation re-run by the registrar)
- `python scripts/spec/cite.py --check 12.3.7.4 "the figurative constants HIGH-VALUE and LOW-VALUE are associated with those characters having the highest and lowest positions"` → `OK  §12.3.7.4 10)  (General rules)`
- `python scripts/spec/cite.py --check 12.4.5.7.4 "Each collating sequence is a fixed file attribute"` → `OK  §12.4.5.7.4 1)  (General rules)`

### Adjudicator finding (special-names-paragraph-p3, harm wrong-answer)
- **Mechanism:** The alphanumeric HIGH-VALUE is pinned to the Latin-1 block (U+00FF) while the native alphanumeric character set - and every other part of the collating model - is the 65,536 UTF-16 code units: CollatingTable.Extremes starts GR8's walk at (char)0xFF for the alphanumeric arm (0xFFFF for national), and AlphabetFigurative maps a HIGH-VALUE written in SPECIAL-NAMES to U+00FF (U+FFFF for national). One rule ('the highest character of the sequence') answered over two different repertoires.
- **Repro:** probe/snp3/g10a.cob, --std 2023: OBJECT-COMPUTER. X PROGRAM COLLATING SEQUENCE IS AL. SPECIAL-NAMES. ALPHABET AL IS HIGH-VALUE "B" "A". 01 X PIC X. 01 Y PIC X. MOVE X"FF" TO X. IF X < "A" ... (prints FF-LT-A; ORD(X"FF") = 1). MOVE HIGH-VALUE TO Y. IF Y = X"FF" ... (HV-NOT-FF: Y is U+00FE). MOVE FUNCTION CHAR(257) TO X. IF X > Y ... (prints U0100-GT-HV).
- **Expected (spec):** Under the implementor's own GR6 definition (65,536 native characters in code-unit order; measured ORD(CHAR(65536)) = 65536): GR10 makes the SPECIAL-NAMES HIGH-VALUE the highest native alphanumeric character, U+FFFF, so ALPHABET AL puts U+FFFF at position 1, U+00FF stays in the GR7 k3 tail above 'A' (X"FF" < "A" FALSE; ORD(X"FF") is its k3 tail position, not 1). GR8 makes the runtime HIGH-VALUE the character at the highest position of AL, the last native code unit left unspecified: U+FFFF (U+FFFE if U+FFFF were specified). No character compares greater than HIGH-VALUE, so 'U0100-GT-HV' must not print.
- **Observed:** Measured with the pinned cobol.exe: FF-LT-A, HV-NOT-FF, LV-IS-FF, U0100-GT-HV, ORDFF=1. The national arm is correct on both rules (Extremes starts at 0xFFFF; alphabet_national golden). The same pin governs the EBCDIC code-name (its 256 specified positions make Extremes fall through to GR8's tie rule inside the Latin-1 block although U+0100..U+FFFF sit above them by the implementor's adopted k3 tail) and the native (no-PCS) HIGH-VALUE (ORD(HIGH-VALUE) = 256 of 65,536 - §8.3.3.6.4 GR6, outside this part; sweep it). docs/COBOLNET_DESIGN.md §14.9 / §18 #14 and PHASE4_RECONCILIATION call it a 'flagged divergence' kept for byte stability; no register note and no owner decision own it. The fix is one repertoire answer: either the native alphanumeric set really is 65,536 wide (then HIGH-VALUE is U+FFFF in both Extremes and AlphabetFigurative, and the single-octet HIGH-VALUE image at the Latin-1 file boundary becomes a codec question), or it is 256 wide (then the SR14 b1 ordinal bound, the k3 tail, CHAR/ORD and CodedCharacterSet.OrdinalCount are all wrong) - a design decision the fix must make and document, not a per-site patch.
- **Code site:** src/Cobol.Net.Compiler/Binding/CollatingModel.cs#CollatingTable.Extremes (char high = national ? (char)0xFFFF : (char)0xFF); src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs#AlphabetFigurative ("HIGH-VALUE" => national ? "\uFFFF" : "\u00FF")
- **Clause (adjudicator):** ISO/IEC 1989:2023 §12.3.7.4 GR8 and GR10 (cite.py --check 12.3.7.4 "the figurative constants HIGH-VALUE and LOW-VALUE are associated with those characters having the highest and lowest positions" -> OK; --check 12.3.7.4 "If more than one character has the highest position in the program collating sequence, the last character specified is associated with the figurative constant HIGH-VALUE" -> OK); GR6 for the repertoire

Sweep: the native no-PCS HIGH-VALUE (ORD(HIGH-VALUE) = 256 of 65,536 — §8.3.3.6.4), the EBCDIC code-name path, and the design-doc 'flagged divergence' paragraphs (COBOLNET_DESIGN §14.9 / §18 #14, PHASE4_RECONCILIATION) — no register note or owner decision ever owned that divergence.
