# PB330 — which OPEN is banned inside imperative-statement-1

**Rows:** `SR-14.9.27.3-3`. Verdict PARTIAL, as the batch-1 refuter set it. **This is a reading question for the
fixer to settle from the standard, not an owner question** — both readings are stated below with their evidence
so the fixer settles it once rather than re-deriving it.

## The rule

> §14.9.27.3 SR3: An OPEN statement that specifies file-name-1 more than once shall not be specified in
> imperative-statement-1 of an exception-checking PERFORM statement.

`--check 14.9.27.3 "An OPEN statement that specifies file-name-1 more than once shall not be specified in
imperative-statement-1"` → **OK**.

## What the compiler implements — reading A, and it implements it well

`EcBinder.ExceptionPerform.cs#CheckCrossStatementBans` reads *specifies file-name-1 more than once* as **the
same file-name appearing twice**. It walks region A = `p.statementBlock()` (the grammar puts the WHEN / OTHER /
COMMON / FINALLY bodies in their own contexts, so region A really is imperative-statement-1), FLATTENS the whole
statement — `op.openClause().SelectMany(oc => oc.openFileSpec())` — before grouping, so a repeat is caught
across mode groups as well as inside one, and case-folds with `ToUpperInvariant`.

Thirteen probes confirm it: rejected COBOLNET1616 for the cross-group form (`OPEN OUTPUT F1 INPUT F1`), a
case-different spelling, the OPEN nested in `IF`/`END-IF` and in `EVALUATE`, one instance carrying `WITH NO
REWIND`, three occurrences over three groups, the `[WITH] LOCATION` head form, and a nested Format-3 PERFORM's
own imperative-statement-1; correctly SILENT for two different files, a duplicate in a WHEN body, in WHEN OTHER,
in FINALLY, and in a Format-2 inline PERFORM. Editions: 2023 only — Annex E item 19 introduces inline exception
processing and `--std 2014` adds COBOLNET0900, so below 2023 there is no construct for the rule to govern.

## Reading B — the multi-operand form — and the three pieces of evidence for it

**a) Family.** Every sibling imperative-statement-1 ban forbids the MULTI-OPERAND form, not a duplicate:
CLOSE *specifies more than one file-name* (§14.9.6.3 r3), DELETE FILE *more than one file-name* (§14.9.10.3 r4),
VALIDATE *more than one identifier* (§14.9.50.3 r6), INITIALIZE *Identifier-1 shall be specified only once*
(§14.9.20.3 r2), MERGE and SORT banned outright. On reading A, OPEN is the sole outlier: it would ban a thing
that is already erroneous everywhere while PERMITTING exactly the multi-operand form its four siblings forbid.

**b) Phrasing.** When this standard means *no duplicates* it anchors the sentence — *The same category shall not
be repeated* (§14.9.20.3 r6, the same clause as r2), *A given class name*, *A particular user-defined word*,
*Any particular screen-attribute*. Eight of the nine unambiguous duplicate rules carry such an anchor;
§14.9.27.3 r3 carries none.

**c) Purpose.** §14.9.27.4 GR25 c) transfers control to the WHEN phrase on an unsuccessful OPEN in
imperative-statement-1, so the file-names after the failing one never open; GR20 defines resumption for that
partial execution only on the declarative path. The ban therefore exists to keep a multi-operand OPEN out of a
context whose control transfer would leave it half-executed — which is precisely the multi-operand form.

## The observable difference, and why the row is not CONFORMS

`OPEN OUTPUT F1 F2 F3` inside imperative-statement-1 compiles clean today, while `CLOSE F1 F2` in the same
position is rejected. Under reading B the OPEN must be rejected too. The predicted sibling is `INITIALIZE N M`,
whose §14.9.20.3 r2 has the same shape — probe it in the same change set.

If the fixer finds the standard genuinely ambiguous after weighing a-c, the disposition is a `status: owner`
decision note, not a silent choice; nothing here suggests it is.
