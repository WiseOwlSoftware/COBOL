# PB214

Found and CLOSED by the PB169–PB172 burn-down cluster's sibling sweep (2026-08-31); registered per CLAUDE.md
rule 8.

MEASURED on 9a89fbd1: `01 X PIC X(2) VALUE "ab".` / `EVALUATE X WHEN X"6162" … END-EVALUATE` compiled clean
and then died with

    Unhandled exception. CobolNet.Runtime.NotImplementedCobolFeatureException: … EVALUATE operand

— the wrong-stage family, on source the standard admits: §8.3.3.2 Format 2 IS the hexadecimal FORMAT of the
alphanumeric literal and §8.3.3.2.1 makes every format of it "of the class and category alphanumeric"
(`cite.py --check` → OK), so it belongs wherever an alphanumeric literal belongs.

⛔ THIS IS DA3's DEFECT IN THE ONE COPY DA3's EXTRACTION MISSED. `ExpressionBinder.NonNumericLiteralOperand`
carries a remark naming the THREE hand-maintained copies it collapsed for exactly this reason — "a
hexadecimal-alphanumeric literal was simply MISSING from one copy, so `IF G = X"6162"` staged loud at run
time while the same literal worked in a MOVE". `EvaluateBinder.BindValueOperand` was a fourth, listing
concatenation / figurative / STRINGLIT / NATLIT / BOOLLIT and no HEXLIT. Three copies guarantee the next
literal form is wired into two of them; four guarantee it is wired into three.

CLOSED BY: replacing the five hand-arms with the single `host.Expr.NonNumericLiteralOperand(...)` call — the
ONE mapping — so the next literal form is a one-line change in one place. Pinned by the
`HEX=HIT` line of `tests/conformance/2023/pb172_sole_function_operand`.
