**Scenario:** The same seven-line shape `if (on) { if (C) on; if (not) else not; } else if (not) if (!C) not;` is written in StringEmitter.EmitOverflow (StringEmitter.cs:320-333), ArithmeticEmitter.EmitArith (ArithmeticEmitter.cs:376-383), SequentialIoEmitter.EmitInvalid (SequentialIoEmitter.cs:562-572, with a notGate parameter) and KeyedIoEmitter.EmitDeleteFile (KeyedIoEmitter.cs:391-399, without one); CallEmitter composes its NOT guard a third way (CallEmitter.cs:135-138 and EmitNotOnException 146-153) and the READ arms a fourth (SequentialIoEmitter.EmitNotPhrase 152-156, called at 649, 792, 799 and KeyedIoEmitter 230-231). PB1120 had to find and gate the I-O copies one by one, PB606 the CALL one, and the DELETE FILE copy was missed: MEASURED, a DELETE FILE of an absent OPTIONAL file under an EC-I-O-WARNING declarative prints both the declarative's line and the NOT ON EXCEPTION line (codegen-5--duplication--f2#2). The next statement that gains a NOT phrase gate (an XML/JSON statement's NOT ON EXCEPTION, or an EC-SIZE declarative interplay) has to be found in each copy again
