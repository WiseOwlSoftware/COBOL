**Landing (2026-11-11, wave 20262000, group C).** Re-probed on a Debug build first: with the keyed store's refused CLOSE promotion (the host-refusal medium of `KeyedClosePermanentErrorWitnessTests`) the registry answered `OpenModeOf("W") == 3` (I-O) after the CLOSE answered '30' (expected -1), and a compiled program with `USE AFTER STANDARD EXCEPTION PROCEDURE ON I-O` ran its declarative twice, for the CLOSE and again for the READ ('47') that followed on the closed file (trace `USE 30, CLOSE 30, USE 47, READ 47`).

**Fix shape.** The CLOSE's USE scoping takes its own statement mode, the OPEN scope's twin: `FileConnector.Close` clears `ModeKnown` whatever the outcome (the two organization `CloseCore` bodies no longer do), and `CobolFile.BeginClose` / `EndModeScope` bracket every CLOSE statement, its status store and its USE hook (`SequentialIoEmitter.EmitCloseScope`, the SORT/MERGE implicit closes too), so the CLOSE's own procedure still finds the mode the file was open in, and no later statement does. `_beingOpened` became `_statementMode`, shared by both statements, and `EndOpen` became `EndModeScope` (every caller changed, nothing kept).

**Witnesses.** `ClosedFileOpenModeViewTests` (registry level, relative and indexed: no mode after a failed CLOSE, the I-O mode inside `BeginClose`, none at `EndModeScope`, none for a CLOSE of a file never opened) and `KeyedClosePermanentErrorWitnessTests.A_mode_scoped_use_procedure_runs_for_the_close_that_answers_30_and_not_for_the_read_after_it` (compiled program, trace `USE 30, CLOSE 30, READ 47`). Each is red with the `ModeKnown = false` line of `FileConnector.Close` removed.
