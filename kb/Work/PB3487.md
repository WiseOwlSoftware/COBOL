## What happens

`next_unit.py`'s campaign rule (DESIGN-orchestrator-loop §9.1, the paragraph after rule 7) picks `campaign` when a
lead's cluster has a READY note by `work.py`'s `cluster_order`, i.e. by the register alone. The planner
(`plan_wave.plan`) then removes every candidate whose file set collides with in-flight work, or whose branch is
already awaiting landing. When it removes all of them the campaign unit plans 0 groups and hands off; the fix lane
is empty too, so the next `wave` unit also plans nothing; then the campaign rule fires again on the same three
"ready" notes. Nothing in the choice reads the planner's answer, and no backoff follows an empty unit.

Observed in run `orchestrate-20261020-102214` while PR #351 (PB3337's first slice) sat in the merge queue:

| start | unit | length | planned |
|---|---|---|---|
| 20:39:09 | campaign PB3353 ("3 ready note(s): PB1278, PB3337, PB3460") | 115 s | 0 groups |
| 20:41:05 | enqueue | 143 s | — |
| 20:43:29 | wave (fix lane) | 109 s | 0 groups ("the fix lane is empty until #351 lands") |
| 20:45:18 | campaign PB3353 (same three notes) | 87 s | 0 groups |
| 20:46:47 | wave | … | … |

`plan_wave.py --cluster PB3353 --dry-run` at 20:50 shows why: PB3337 "awaiting landing (excluded; an `enqueue`
unit first): worktree-wf_316f7d48-4e6-7"; PB3338, PB3340, PB3460 and PB1278 "file-set collision with in-flight work"
(worktree-wf_316f7d48-4e6-1/-4 IN FLIGHT, worktree-wf_5b092cc6-8b9-1 DECISION). Each unit costs about 0.04 % of the
weekly quota (budget lines 70.00 → 70.16 % over the four) with the week already projected to run out before its
reset; a merge-queue run of 30–60 min repeats the cycle 15–30 times.

## What the fix needs (the shape, not the patch)

- ONE reading of "the campaign can plan something": the campaign rule asks the planner's partition (a dry
  `plan_wave.plan` over the cluster, or the same predicate it applies), never `cluster_order`'s register-only
  readiness. A lead whose ready notes are all held is `waiting` (the state `next_unit` already reports), not `ready`.
- The same for the fix lane's `wave` choice: when the last `wave` unit planned 0 groups and nothing it reads has
  changed since (main's head, the worktree set, the dispatch ledger, the register), choosing it again is the churn.
- When every lane is held only by work in flight, the supervisor waits for a change (a landing on main, a unit
  handoff, a worktree's new commit, the land lane's next survey) instead of starting a unit; `meter` and `enqueue`
  keep their own triggers.
- A drift test in `test_orchestrate_campaign.ps1`: a cluster with ready notes whose planner answer is 0 groups
  chooses no campaign unit; the moment the hold lifts (the fake landing merges), it chooses one.
