## Code sites

- `src/Cobol.Net.Runtime/Control/ProgramTable.cs:61` and `:78` — the program table is keyed by
  `ExternalizedNames.Comparer`, the 2023 mapping, at every edition.
- `src/Cobol.Net.Runtime/Control/CobolObject.cs:60` — `NormalizeMethodName` folds by `CobolNames.Fold`, the 2023 mapping.

## Mechanism

PB2840 writes a LITERAL that names a program or method in the edition's Annex C spelling at compile time
(`ExternalizedNames.FormWritten`, `CobolNames.EditionSpelling`), because the lexer wrote the PROGRAM-ID / METHOD-ID
word it names that way. A name held in a DATA ITEM is run-time data and reaches the run time with no edition, so it
maps by the 2023 table: below 2023 (Annex E.2 item 14 deleted the final-sigma pair only at 2023) `CALL WS-NAME` with
`WS-NAME` holding "Z<final sigma>" finds no `PROGRAM-ID. Z<sigma>` and raises EC-PROGRAM-NOT-FOUND, where the same
name written as a literal is found. DOC-A.1-68 documents the current behaviour. The root is shared with PB2840: the
fix needs a run-unit edition fact the run time can read (the compiled program's edition), then the dynamic lookups
apply `EditionSpelling` to the value as the literal path does.

## Repro

At `--std 2014`: `PROGRAM-ID. Z<sigma>` as a called program; the caller `MOVE "Z<final sigma>" TO WS-NAME` and
`CALL WS-NAME`: EC-PROGRAM-NOT-FOUND; `CALL "Z<final sigma>"` reaches it.

## Landed

Re-probed on a fresh build: `CALL WS-NAME` / `CANCEL WS-NAME` / `SET PP TO ENTRY WS-NAME` / `INVOKE U WS-METHOD` (universal) /
`ADDRESS OF PROGRAM WS-NAME` / `ADDRESS OF FUNCTION WS-NAME` holding final sigma all missed the sigma word at `--std 2002` and
`2014` (EC-OO-METHOD for the method, EC-PROGRAM-NOT-FOUND / NULL pointer for the programs).

Root: the run time maps every name by the 2023 Annex C table and has no edition, so the edition spelling PB2840 gives a
LITERAL (at bind time) never reached a name held in a data item. Fix, at the one place the rule belongs: the compiled
program passes its own edition. `ExternalizedNames.FormWritten` became `ExternalizedNames.FormInEdition` (every caller changed,
no alias; it forms a name from a literal's content or a data item's value alike), `CobolNames.HasEditionSpelling` is the one
question "does this edition's Annex C differ from the 2023 table" (the lexer's `EditionSpelling` asks it too), and
`RuntimeApi.ExternalizedNameInEdition` wraps every emitted data-item name read below 2023 (CallEmitter CALL and CANCEL,
PtrEmitter `NameImage` for ENTRY / ADDRESS OF PROGRAM / ADDRESS OF FUNCTION, OoEmitter universal INVOKE); at 2023 the
expression is emitted unchanged. `ExternalizedNameFormationDriftTests.EveryDataItemNameRead_GoesThroughTheEditionSpellingFunnel`
keeps a new dynamic-name verb or arm from bypassing it. Witnesses: `conformance:2002/pb2991_data_item_names_edition_spelled`,
`conformance:2014/pb2991_function_address_data_item_edition_spelled`, `conformance:2023/pb2991_data_item_names_two_words_at_2023`
(the 2023 side: final sigma and sigma stay two words). Documented in DOC-A.1-68 and DESIGN-frontend-grammar.
Limit, unchanged: a run unit whose programs are compiled at different editions still compares by each caller's edition.
