## The defect

Every morning's triage of a differential-fuzz night (seven nights, 2026-10-21 to 2026-10-27) ran from tooling that exists
only in that session's TEMP scratchpad: night 6's is `residue.py`, `slice.py`, `render.py`, `collect.py`, `verify.py`,
`retarget.py`, `save_reports.py`, `reports_from_journal.py`, `cites.sh`, `briefs/common.md` + `briefs/slice-template.md`
(+ per-slice briefs) and `wf.js` (a Workflow that runs the read-only adjudicators four wide). Each night copied the
previous night's set and retargeted it by hand (`retarget.py` exists only to rewrite the hard-coded run directory, judge
path and scratchpad paths), so a lesson written into one night's `common.md` survives only if the next session finds it,
and a scratchpad's end loses the tooling (PB3838's tier 2 had to rescue nights 3 to 5's verdict files from three dead
sessions' scratchpads).

And the triage's GNUCOBOL-SIDE verdicts file nothing: the brief says "You FIX NOTHING and FILE NOTHING", so every
GnuCOBOL defect a night finds stays in prose until a campaign like PB3838's tiers 2-4 harvests, adjudicates, refutes
and files it by hand (seven nights; 65 notes, PB3873-PB3937).

## The fix (PB3838 "The plan" item 5; rule 5: the shape that makes the next night automatic)

1. **A design first** (CLAUDE.md rule 2): no design doc covers the differential fuzz harness today (`git grep
   differential_fuzz -- docs` outside the evidence folder is empty). Write its canonical section (a new
   `docs/rearchitecture/DESIGN-differential-fuzz.md`, registered in `docs/DOC_INDEX.md` and `docs/DESIGN.md` §0.5): the
   night (launcher, harness, judge), the morning's triage (residue, slicing, the adjudicators, collection, the report),
   and the filing of GNUCOBOL-SIDE verdicts.
2. **ONE tool in the tree** taking the run directory and the judge as ARGUMENTS (no per-night retarget, no hard-coded
   paths, no TEMP path in any output): the night-6 scripts' jobs as its subcommands, the briefs as templates it renders
   (`common.md`'s lessons kept verbatim where they still hold: the fifth night's "look for the more specific rule and
   refute the compiler's own argument", the per-program output directory, never `--run`, cite.py for every clause), and
   the triage Workflow script in `.claude/workflows/` (where the tree keeps Workflow scripts). The Python tool carries
   a `--self-test` that `scripts/self_tests.py` discovers (discovery covers `.py` and `.sh` scripts and `test_*.py` /
   `test_*.ps1`, never a `.js` Workflow), so the Workflow script stays thin: every decision it makes is the tool's,
   tested there.
3. **GNUCOBOL-SIDE files an `upstream` note, after an independent refuter**: every GNUCOBOL-SIDE verdict the triage's
   adjudicator returns goes to an independent `cobol-refuter` before anything is written (PB3838's plan item 3: "Every
   'GnuCOBOL is wrong' verdict goes to an independent refuter before it is filed, because it is meant for publication";
   tier 3 measured why: 12 RECLASSIFY and 1 OVERTURNED of 113, and `work.py check` checks only the structure). The
   Workflow runs the refute phase; only a verdict the refuter UPHOLDS, or RECLASSIFIES to another GnuCOBOL-side class,
   is filed, with the refuter's correction applied in every section. It is written as an `upstream` kb/Work note that
   passes `work.py check` (PB3838's eight-item bar, the kind PB3838 tier 1 landed): the minimal repro copied OUT of the
   git-ignored run directory into the note, the cobc command and output, the ISO clause checked with cite.py, the
   GnuCOBOL site, `upstream_status: unreported`. An overturned verdict, or one that cannot meet the bar, stays in the
   triage report, never filed half (PB3838 standing requirement 1). A family an existing upstream note already records
   is added to that note as a witness, never filed twice (the harvest's dedupe, kb/Work PB3873-PB3937 are the existing
   ones). No GnuCOBOL source, testsuite text or expected output beyond identifiers (GPL, standing requirement 3).
4. **Tonight's triage uses it**: the next fuzz night's morning runs from the tree, and its evidence record names the
   tool's commands.

Owner standing decision (2026-10-24 ~17:00, quoted in every night's brief): "Do not begin fixing any fuzz identified
issues without my explicit approval". Filing an `upstream` note is recording, not fixing; the tool still fixes nothing.

## Landed

`scripts/fuzz_triage.py` is the one tool (`prepare`, `collect`, `cites`, `verify`, `refute-plan`, `file`, `render`), with
`.claude/workflows/fuzz-triage.js` as its thin Workflow and `scripts/fuzz_triage_briefs/` as the briefs' templates;
`docs/rearchitecture/DESIGN-differential-fuzz.md` is the design (§3 the morning, §4 adjudication and refutation, §5 the
filing). Re-probed on the sixth night's run directory: `prepare` produces the same twelve slices (A1, B1-B4, C1-C4, D1-D2,
N1) with the row counts of the hand-run triage. A GNUCOBOL-SIDE verdict is filed only after the independent refuter, to the
register's own `upstream_problems` bar, with the minimal program copied into the note and every quoted citation checked by
`cite.py`; a family an existing note records gains the run's program ids as witnesses.

The self-test is `scripts/test_fuzz_triage.py`, discovered by its name (the repository's convention for a stand-alone
self-test); the tool itself takes no `--self-test` flag, since a flag that only forwarded to that file would be run twice by
`scripts/self_tests.py`.

Tonight's use (plan item 4) is the operator's: the morning triage runs the commands in the design's section 3.1 and 4.2,
and its evidence record names them.

Branch review round 1 (four blocking findings, all fixed at the root). The triage directory defaults to
`<coord>/scratch/fuzz-triage/<run id>` and any directory inside a git checkout is refused (`coord.scratch_problem`), because
the read-only adjudicators' hook refuses every Write inside a git tree and a run directory is inside one. The refutation
line carries `citations`, which `file` checks and `spec_refs` come from, and the corrected copy's `§` clauses must equal
them. Several witnesses of one note in one run append to one bullet. The tool reads fences, sections and the Draft title
through `work.py` (`fenced_block_texts`, `section_named`, `draft_title`), and `verify` exits 1 when a repro is missing or
its compile times out.
