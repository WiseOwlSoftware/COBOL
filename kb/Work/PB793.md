## ⛔ The bare question

**Should COBOL.NET accept `ASCII` and `EBCDIC` as ALPHABET `code-name-1`?**

## The default, if the owner does not say otherwise

**Yes — accept both**, per the standing protocol. `feedback_owner_decision_protocol` (2026-08-30): follow the
surveyed model implementations; ask only on significant considerations. `follow_gnucobol_on_split_latitude`
(owner decision): where the standard leaves a point implementor-defined and the vendors split, follow GnuCOBOL —
its LATITUDE, never its non-ISO extensions. The PB770 implementer's survey: **GnuCOBOL, Micro Focus and IBM all
accept `ASCII` and/or `EBCDIC` as code-name-1**; GnuCOBOL treats `ASCII` as the native set and `EBCDIC` as its
translation table. This note is filed rather than defaulted because the cost is not a clause — it is a coded
character set, its collating sequence, its correspondence with the native set, and two conditionally-required
Annex A.1 documentation items. That is the "significant consideration" the protocol reserves for the owner.

## Why it is latitude and not conformance — mechanically checked

```
python scripts/spec/cite.py --check 12.3.7.3 "The implementor shall specify the names supported for code-name-1 and code-name-2 in the ALPHABET clause, if any"
  OK  §12.3.7.3 15)  (Syntax rules)
      15) The implementor shall specify the names supported for code-name-1 and code-name-2 in the ALPHABET
          clause, if any.
python scripts/spec/cite.py --check 12.3.7.4 "The ALPHABET clause provides a means of relating a name to a specified coded character set"
  OK  §12.3.7.4 7)   (General rules)
```

"**if any**" is the licence for an empty set, and Annex A.1's own preamble makes the item OPTIONAL ("The element
may be provided at the implementor's option"). So **today's refusal is conforming** — that is why every harm flag
on this note is false and `process_only` is true. Nothing a user writes is answered wrongly; a spelling other
compilers accept is refused, by documented design.

## What main does today (PB770, landed)

`src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs:941-951`, `AlphabetCodeNameRefused` — *"⛔ THE ONE
§12.3.7.3 SR15 check, for code-name-1 (alphanumeric) and code-name-2 (national) alike … This implementation
supports NONE"*:

```
ALPHABET A-ASC IS ASCII
→ COBOLNET1907: ALPHABET A-ASC IS ASCII: not a supported code-name — this implementation defines no
  code-name-1 names (ISO §12.3.7.3 SR15; the alphanumeric coded character sets are NATIVE, STANDARD-1,
  and STANDARD-2)
```

The check is deliberately narrow: it fires only on a definition that is ONE bare word, which is the only shape
code-name-1/-2 has in the general format (`specs/ISO_COBOL.md` §12.3.7.2, "where alphabet-name-clause is" —
`code-name-1` / `code-name-2` stacked with NATIVE / STANDARD-1 / STANDARD-2 / UCS-4 / UTF-8 / UTF-16 / LOCALE /
`{ literal-phrase } …`). Before PB770 an unrecognized code-name was silently reinterpreted as the CHARACTERS OF
ITS OWN SPELLING — `ALPHABET A-ASC IS ASCII` built an alphabet whose first four positions were A, S, C, I — so
the empty set replaced a wrong answer with a diagnostic. **Whatever is decided here, that reinterpretation does
not come back.**

## The documentation state, and what "yes" would add

`docs/CONFORMANCE.md:1121`, **DOC-A.1-184** (*"the names supported for code-name-1 and code-name-2"*, §12.3.7.3
SR15, **optional** + documented-if-provided) currently reads **"Not provided. The set of supported code-names is
EMPTY, in both classes."** Its own text records the two items that wake up the moment a code-name exists:

- **DOC-A.1-183** — *"SPECIAL-NAMES paragraph, ALPHABET clause, code-name-1 (alphanumeric coded character set and
  collating sequence; ordinal number of characters; correspondence with native alphanumeric character set)"*,
  **conditionally required** *"because it is conditioned upon the existence of a code-name"*.
- **DOC-A.1-185** — the code-name-2 / national twin, same requirement class.

Both are VACUOUS today and are recorded as such. (Row texts read from
`docs/rearchitecture/spec-rule-catalog.json:40110` and `:40132`.)

## What implementing "yes" actually costs

1. A **code-name table** — the structure SR15's answer belongs in, not a pair of hand-written `if` arms
   (CLAUDE.md rule 5). `AlphabetCodeNameRefused` becomes a LOOKUP with a refusal on miss, so the next supported
   code-name is a row, and the empty-set case stays exactly today's diagnostic.
2. For `ASCII`: the coded character set, its ordinals and its correspondence with the native set — which on this
   compiler's UTF-16 substrate (`charset_utf16`; implementor item 188 / D-N1) is the identity over the first 128
   positions, so DOC-A.1-183 is short but must be written.
3. For `EBCDIC`: a real coded character set AND its collating sequence AND its native correspondence. ⚠ Which
   EBCDIC — there are many code pages — is itself an implementor choice this note does not pre-empt; GnuCOBOL
   ships one translation table, and `survey_compilers_on_latitude` says to survey before choosing.
   ⛔ **GPL: GnuCOBOL's table may not be copied** (`feedback_gnucobol_differential`); the latitude may be
   followed, the source may not.
4. DOC-A.1-183 and DOC-A.1-185 flip from vacuous to REQUIRED and need `docs/CONFORMANCE.md` rows with witnesses,
   and DOC-A.1-184 is rewritten from "Not provided" to the supported set.
5. `CONFORMANCE.md` §7 / Annex A.1 sweep, plus a positive golden per code-name per class.

## Landed — 2026-09-06

The feature is on the tree, implemented from the standard rather than from the refusal it replaces.

**The mechanism is a TABLE, and that was the point** (CLAUDE.md rule 5). `src/Cobol.Net.Compiler/Binding/`
`ImplementorCodeNames.cs` holds one `ImplementorCodeName` row per supported name, carrying everything
§12.3.7.4 GR7 i/j obliges the implementor to specify for it — the coded character set's ordinal count, the
collating positions, and the correspondence with the native set. `DataBinder.AlphabetCodeNameRefused` became
`DataBinder.AlphabetCodeName`, a LOOKUP keyed by (spelling, class) with the refusal on miss, called from BOTH
arms; the COBOLNET1907 message names the supported set FROM the table, so it cannot go stale. **The next
supported code-name is a row and no code path at all.**

**The determinations** (published in full at `docs/CONFORMANCE.md` §7 DOC-A.1-183, and summarised in
DOC-A.1-184):

- **`ASCII`** = ISO/IEC 646 International Reference Version. 128 ordinals; ordinal *n* = native character
  U+(*n*−1); the correspondence with the native set is the IDENTITY (the first 128 positions of this native
  set ARE ISO/IEC 646 IRV — item 188 / D-N1); the collating sequence is the native order. That is the SAME
  answer §12.3.7.4 GR7 c gives the `STANDARD-1` keyword, and deliberately so: "ASCII" names a 7-bit code, not
  a 256-character one, and inventing an "extended ASCII" reading would name a set no standard defines. So
  `ASCII` is a supported SPELLING of a set the standard also names, provided because programs written for other
  compilers spell it that way. No runtime carrier is emitted for it.
- **`EBCDIC`** = **IBM CCSID 37** (code page 037, EBCDIC US/Canada). 256 ordinals; ordinal *n* is the native
  character that page assigns to code unit *n*−1; the collating position of a native character IS its code unit
  in that page; the correspondence is the page. ⛔ The whole table is DERIVED at bind time from .NET's own
  `Encoding.GetEncoding(37)` — nothing is transcribed, so there is no 256-entry literal to mistype or to drift
  — and no NuGet dependency was needed: .NET 10 carries `CodePagesEncodingProvider` in-box (a `PackageReference`
  was added first and NU1510 rejected it as redundant, which is the evidence).
- **Why CCSID 37**, surveyed rather than assumed ([[survey_compilers_on_latitude]]): it is the canonical
  registered COMPLETE single-byte EBCDIC page — a bijection of all 256 code units onto exactly the 256 native
  characters U+0000–U+00FF, round-tripping byte-exactly (measured) — and the z/OS default, i.e. the one the
  compiler whose users write `ALPHABET … IS EBCDIC` means. GnuCOBOL's own `-febcdic-table=default` is a
  historical restricted table corresponding to no registered CCSID; its named alternates (`ebcdic500_ascii7bit`,
  `ebcdic500_ascii8bit`, `ebcdic500_latin1`) are CCSID 500 variants. Following its latitude — which NAMES are
  accepted — does not mean adopting a table that is both GPL and unregistered. CCSID 500 differs from 37 in
  five punctuation positions and is the obvious second row.
- **Characters outside the page.** The native alphanumeric set is the 65,536 UTF-16 code units (D-N1) and
  CCSID 37 spells 256 of them. As a COLLATING SEQUENCE the other 65,280 take §12.3.7.4 GR7 k3's tail position
  ("*a position … greater than that of the highest character specified … The relative order within the set of
  these unspecified characters is unchanged from the native collating sequence*"), which this implementation
  adopts as its GR7 i specification — so GR7 i's obligation to give EVERY character a position is discharged by
  the standard's own rule, and by the SAME sparse `CollatingTable` the literal phrase builds. As a CODED
  CHARACTER SET they are simply not members: no ordinal, no medium representation.

**§12.3.7.4 Table 6 gives code-name-1 a Y in BOTH columns, so both halves are live.** The COLLATING half rides
the existing `CollatingTable` → `AlphanumericCollation` path with no new runtime type (PROGRAM COLLATING
SEQUENCE, the SORT/MERGE COLLATING SEQUENCE phrase, §8.8.4.2.7 relations, CHAR/ORD, the figurative extremes).
The CODED-SET half rides `CodedCharacterSet`, whose `OrdinalCount` now reads the row (128 / 256 instead of the
default 65,536), so `SYMBOLIC CHARACTERS … IN` and `CLASS … IN` resolve ordinals in the named set and bound
them by its real size.

**Two structural corrections came with it, both CLAUDE.md rule 5 rather than rule 3:**

1. `CollatingTable.Build` — the array shaping AND the §12.3.7.4 GR8/GR9 extremes, previously
   `DataBinder.Switches.AlphabetExtremes`, are now ONE method on the model, called by the literal-phrase arm and
   the code-name arm alike. Neither re-derives HIGH-VALUE or LOW-VALUE.
2. `CodedCharacterSet.Medium` (`CodeSetMedium` `Identity` / `Translated` / `NotProvided`) — the CODE-SET
   binder's A.3 item 27 refusal used to be the literal test `set.Table is not null || set.Phrase is "UTF-8" or
   "UCS-4"` in `BindCodeSetClause`, which would have refused every code-name set the moment one gained a table.
   The question is a property OF THE SET and is now answered there, once.

**§13.18.13 CODE-SET now converts, which it never has.** §13.18.13.4 GR6 a/b — "*each coded character from the
storage medium is replaced with its associated native coded character*" / the reverse — is realized by
`CobolNet.Runtime.IO.CodeSetConversion`, a 256-entry permutation the COMPILER computes from the alphabet and
emits as a `char[]` literal (so the runtime holds no code page and knows no alphabet name, exactly as it holds no
locale table for a collating sequence). The boundary is the ONE physical transfer point of each organization and
nowhere else — `SequentialConnector.NextFrame` reading, its new `EmitRecord`/`EmitRecordLine` twins and
`OverwriteInPlace` writing, and `RecordFraming`'s store payload for RELATIVE and INDEXED — so a record area, a
key value, a comparison and a lock identity are always in the NATIVE character set, which is what every other
rule is written about. The §9.1.7.2 framing this processor adds AROUND a record (the length prefix, the line
delimiter) is not data of the record and stays native; that determination is published in `CONFORMANCE.md` §2
row 27.

⚠ **One consequence had to be re-decided, not merely re-worded.** `CONFORMANCE.md` DOC-A.1-129 justified
leaving the code set out of the validated fixed-file-attribute set by saying the value was a CONSTANT ("no second
value to take"), because every non-identity alphabet was refused. That is now false. It stays out, but as a
DETERMINATION under §14.9.27.4 GR10's explicit latitude, for two reasons: the attribute catalog is written when
THIS processor creates a file, and the purpose of a CODE-SET clause is to read a file some OTHER system wrote,
which carries no catalog — so the check would fire exactly where it is not needed; and reading a converted file
through a description with NO CODE-SET clause is §13.18.13.4 GR7's own default and the raw-medium idiom a dump or
transcode utility is written in, so a '39' there would reject legal source. `FixedFileAttributes.Conflicts`'
comment carries the same text.

**Goldens** (all values derived from the two determinations and checked against them, never from the compiler):
`conformance:2023/pb793_code_name_alphabets` (the coded set through `SYMBOLIC … IN`, the sequence through
FUNCTION CHAR/ORD and two relations, and the SORT COLLATING SEQUENCE phrase in a sibling unit that inherits no
PCS — with a native leg beside it so neither can pass for the other's reason);
`conformance:2023/pb793_code_set_ebcdic` (the round trip AND the medium itself, read through a second file
description carrying no CODE-SET clause — without that leg a compiler converting on NEITHER side would pass);
`conformance:85/pb793_code_name_alphabets_85` (the same clause at the earliest edition it exists in, ASCII and
EBCDIC side by side so the identity arm is evidence about the translated one). The negative
`conformance:negative/pb770-alphabet-unsupported-code-name` was REWORKED rather than deleted: it named `ASCII`,
which is now legal, and now names `FIELDATA` — a real historical coded character set another vendor might
support and this one does not.

**The two measured differential rows return to `AGREE_ACCEPT`**: `configuration:885` ("cobc configuration:
ebcdic-table", `ALPHABET an-ebcdic IS EBCDIC` under a PROGRAM COLLATING SEQUENCE) and `run_misc:5406`
("SYMBOLIC clause", which declares both names and asserts that ordinal 241 in EBCDIC and ordinal 49 in ASCII are
both the character `0` — reproduced exactly by this implementation before any golden was written). The lander
re-baselines `tests/external/gnucobol-verdict-baseline.tsv` by hand.

**Codes:** COBOLNET1907 reused, its catalog text rewritten to describe a table rather than an empty set. The
