# R03 — LANDED — the hexadecimal literal formats, all three of them

> ⚙ Migrated from the fix queue's RESIDUE block, which never itemised these — so no work list could see them.

## ⛔ MEASURED — a SILENT WRONG ANSWER, not the parse error the title suggested

`NX` lexed as an IDENTIFIER and `"0041"` as a separate string, so in an argument list one literal became TWO
operands. Usually that surfaced as an arity complaint. **With a data item actually named `NX` in scope, nothing
complained at all:**

```cobol
01 NX PIC X(4) VALUE "ZZZZ".
MOVE FUNCTION MAX(NX"0041") TO R.     *> gave ZZZZ, silently
```

That is `MAX(NX, "0041")` — an unrelated item compared against a string. The lexer's own comment had recorded
the gap in as many words: *"NX"…" (hex national) is deferred"* and *"BX"…" (hex boolean) is deferred"* — **two
arms, and the note named one** ([[feedback_two_arm_dispatch]]).

## ⭐ FORMAT 2 IS THE SAME TOKEN, BECAUSE IT IS THE SAME LITERAL KIND

§8.3.3.5.2 and §8.3.3.4.2 each print TWO general formats, and their ALL-FORMATS general rules put both in ONE
class and category (§8.3.3.5.4 GR2, §8.3.3.4.4 GR2). So Format 2 folds into `NATLIT` / `BOOLLIT` rather than
becoming new tokens — which is what the standard says AND what made the change tractable: **32 call sites
already route NATLIT→national and BOOLLIT→boolean, and every one stays correct untouched**, including the
COBOL-2002 introduction gate (verified at `--std 85` with NO national/boolean PICTURE in the program, so it is
the LITERAL's gate being proven, not the item's).

⚠ **THE ALTERNATIVE IS A MISTAKE ALREADY IN THIS FILE.** `HEXLIT` is its own token even though §8.3.3.2 makes a
hexadecimal literal *"one FORM of an alphanumeric literal, not a separate kind of thing"* — `CobolLiteral`'s own
words — and that split is why its decoding had to be added at FOUR call sites, the fourth being a silent
VALUE-clause miscompile. A `NATHEXLIT` token would have bought the same bill twice.

## ⛔ THE SWEEP FOUND TWO MORE, AND ONE OF THEM PREDATES THIS ITEM ENTIRELY

**① The grouping rule was enforced NOWHERE, in any of the three formats.** The decoders answer `""` for a
malformed digit count and every caller took that as the value:

```
FUNCTION LENGTH(X"414")   → 1, silently     (pre-existing since X"…" was introduced)
FUNCTION LENGTH(NX"041")  → 1, silently     (inherited the moment the token started matching)
```

The three clauses do **not** state the same rule, and writing one check for all three would have been wrong:

| form | clause | groups |
|---|---|---|
| `X"…"` | §8.3.3.2.3 **r6** | 2 digits (one byte per alphanumeric character) |
| `NX"…"` | §8.3.3.5.3 **r5** | 4 digits (D-N1: one UTF-16 unit per national position) |
| `BX"…"` | §8.3.3.4.3 **r3** | **none** — §8.3.3.4.4 GR5 maps each digit independently to four boolean characters |

`COBOLNET1635` now reports it, per format, citing that format's own rule. **BX is deliberately unscreened**, and
the golden pins `BX"5"` and `BX"5AB"` as legal so a later "symmetry" fix cannot reject them.

⚠ **THE CHECK IS AT BIND, NOT IN THE LEXER, AND THAT IS THE LOAD-BEARING DECISION.** A lexer rule refusing an odd
digit count would not reject the program — the token would simply fail to match, `X"414"` would split into an
IDENTIFIER and a STRINGLIT, and the literal would be back in the silent-degradation hole this item exists to
close. **The token must match so that something is left to diagnose.**

**② `X""` was refused outright.** §8.3.3.2.3 NOTE 2 — "Hexadecimal-alphanumeric literals can be of zero length" —
and the lexer's `[0-9a-f]+` said otherwise, so `X""` split exactly as NX/BX did. Now `*`, matching the NOTEs in
all three clauses. `FUNCTION LENGTH(X"")` answers 1, identical to `FUNCTION LENGTH("")` — consistent with the
existing zero-length-literal behaviour rather than inventing a new answer for it.
