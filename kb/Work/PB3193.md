# PB3193 — EnsureUtf8 changes the host process's console streams

Source: `w1080f-PB3163-report.md` "## New defects / leads" (filed by the clerk, 2026-10-15).

**The lead.** `StandardStreams.EnsureUtf8` (`src/WiseOwl.Cobol.Runtime/IO/StandardStreams.cs:58-76`, called from `ProgramTable.RunOnThisThread` on every `RunMain` / `RunModule`) replaces `Console.Out`, `Console.Error` and `Console.OutputEncoding` in the HOST process. It is the same family as PB3163 (a run unit mutating state of the process that embeds it), but a different mechanism: PB3163 was the exit code; this is the display device's encoding.

**Why it is not simply fixed.** A documented PB59/PB899 decision made UTF-8 output on the display device a deliberate behavior, so this needs a design call on the embedding boundary: which side owns the console encoding when a run unit is embedded (an option is to write through a run-unit-owned stream and touch the process console only at the process-entry boundary, the way PB3163 now delivers the exit code once at `ProgramTable.RunModule`). The report says it shares no root with PB3163; do not widen that landing. An implementer designs it from the PB59 and PB899 notes before changing anything, and a host-embedding test pins the result (a host that set its own `Console.Out` before running a unit still has it afterwards).

## Landed (wave 1098, group B)

**Re-probe** on a fresh Debug build: a host (Roslyn-compiled C#, its own process) that set `Console.OutputEncoding =
Encoding.Latin1` (28591) and installed its own `Console.Out` / `Console.Error` writers read code page 65001 after one
`ProgramRegistry.RunMain`, because `ProgramTable.RunOnThisThread` called `StandardStreams.EnsureUtf8` on every run.

**The design call** (from PB59, PB899 and PB3163; recorded in `docs/rearchitecture/DESIGN-runtime-library.md` beside the
generated `Main`'s entry, and in CONFORMANCE.md DOC-A.1-59 and DOC-A.1-167): the process console belongs to the PROCESS,
and only an entry that IS the process configures it, the `cobol` CLI's `Main` and `ProgramTable.RunModule` (the
generated `Main`; DOC-A.1-167: "A standalone `cobol` executable IS its own host"). Under a host, the standard display
device is the host's `Console.Out` / `Console.Error` as the host configured them. A run-unit-owned stream was
considered and not adopted: it would either bypass a host's `Console.SetOut` redirection (a writer over the raw handle)
or be the host's writer anyway (read through `Console.Out`), a seam with no behaviour of its own. Per-run-unit display
streams for concurrent run units are a question for the host surface (PB2099), not for this defect.

**Fix:** the `EnsureUtf8` call moved from `RunOnThisThread` to `RunModule`, before the run-unit thread starts; `RunMain`,
`RunUnit.Run` and CALL leave the console alone. **Sibling arm found in the same function (I9):** the device-boundary
rule covered output only. On Windows a REDIRECTED standard input was decoded in the console's OEM code page, so the
bytes C3 A9 5A piped into `ACCEPT X` gave `FUNCTION ORD` values 9501 8977 (U+251C U+2310, cp437) instead of 234 91.
`EnsureUtf8` now gives a redirected standard input a UTF-8 reader (no BOM detection, the shape of Console's own),
documented in DOC-A.1-1; the harness (`ProcessObserver`) encodes what it pipes as UTF-8 to match.

**Witnesses:** `RunUnitHostConsoleTests` (Conformance: the host's encoding and both writers survive, and each DISPLAY
reaches the host's writer intact), `AcceptDifferentialTests.Device_RedirectedInput_DecodesAsUtf8`, and the sweep
`ProcessStateOwnerDriftTests` (Unit), which holds every process-owned write (the exit code, `Environment.Exit`, the
console setters, the `EnsureUtf8` calls) to its process entry. All three went red against a mutation that restored the
old call site and disabled the input arm.
