# PB229

**Rows:** `GR-14.9.2.4-5`

ADD CORRESPONDING's §14.7.6 pair selection lost its only rule-4/rule-5 evidence to a legacy bake, its FILLER-subtree exclusion is justified by the oracle rather than the spec, and one `try` wraps every implied statement so an evaluation-time size error can abort the rest.

Row: GR-14.9.2.4-5 (ADD CORRESPONDING's second sentence — 'the results are the same as if the user had referred to each pair … in separate ADD statements' — carrying §14.7.6's six pair-selection rules).

WHAT IS RIGHT, and re-derived rather than assumed. §14.7.6's six rules were re-read in full at specs/ISO_COBOL.md:21821-21841. Rule 1 (same data-name and same qualifiers up to but not including D1/D2, FILLER excluded): CorrEligible rejects a nameless entry and the matcher descends ONLY into name-matched group×group pairs (:117-124), so a pair's relative qualification path is identical to D1/D2 by construction. Rule 2 is MOVE-only and is correctly routed to the `verb is CorrVerb.Move` arm (:125-130), so it does not apply to ADD. Rule 3 ('In an ADD or SUBTRACT statement, both of the data items are numeric data items') is the `else if (s.Pic?.Category is not PicCategory.Numeric || d.Pic?.Category is not PicCategory.Numeric) continue;` at :134-135 — a SILENT non-correspondence, not an error, which is what 'a pair of data items correspond if' requires; pinned by CorrespondingDifferentialTests.AddCorresponding_Rule3_NonNumericNamesakeIsNotAPair (a PIC 9 / PIC X namesake leaves the target untouched while the numeric namesake still adds). Rule 6 is applied SYMMETRICALLY (srcCount at :105-112 as well as cands.Count at :114), stricter than the legacy matcher and exactly what 'unique after application of the implied qualifiers' says. The second sentence's other obligations hold: pairs are emitted in D1 declaration order (the `foreach (var s in src.Children)` walk = §14.7.6's 'in the order in which the elements in the group data item immediately following CORRESPONDING are specified'), the one statement rounded-phrase reaches every pair (conformance:2014/corresponding_rounded_mode), the group anchors are hoisted so item identification happens once at statement start (CorrAccess.Hoist), a zero-pair group pair is a legal empty implied set (:78-80), and §14.7.6's statement-level SIZE ERROR aggregation on top of 'separate statements' is pinned by AddCorresponding_SizeError_AggregatedAcrossPairs (one 'SE' dispatch, the erring receiver unchanged at 5, the later pair still stored at 30, the NOT phrase ignored).

RESIDUE 1 — RULES 4 AND 5 HAVE NO QUALIFYING EVIDENCE (process_only). The closing test for both was conformance-test:CorrespondingDifferentialTests.AddCorresponding_TableShape_OccursChildExcluded (CorrespondingDifferentialTests.cs:235-236), which is `AssertSameAsLegacy(...)` → DifferentialGolden.Assert, whose default mode (COBOLNET_DIFF_MODE unset → 'golden', DifferentialGolden.cs:29-31) asserts only that COBOL.NET still equals a committed .out BAKED FROM A LIVE LEGACY RUN (bake mode, :51-62). That is a characterization net against the frozen oracle, non-qualifying under ground rule 3, and it was removed from the row's test-ref. With it gone, rule 4's OCCURS/REDEFINES/RENAMES/index leg and rule 5's 'nothing subordinate to an ineligible intermediate group' leg have NO spec-derived test on ADD at all — although the code for both is present and looks right (CorrEligible tests IsTable, RedefinesTargetName, Renames and Usage.Index, with the class-object/pointer/message-tag legs unmodelled but unreachable for ADD because rule 3 already requires category numeric on both sides; and the recursion filters with CorrEligible BEFORE descending, so an ineligible group's whole subtree is never visited).

RESIDUE 2 — THE FILLER SUBTREE RULE IS ORACLE-JUSTIFIED (silent). CorrEligible's FILLER leg excludes a nameless entry AND, by `continue`-ing before the descent, its ENTIRE SUBTREE. The code's own doc-comment (:152-158) justifies that with 'the legacy/NIST-proven reading' — the oracle, not a derivation — while its stated premise ('a FILLER level contributes no qualifier') is precisely the argument that an item UNDER a FILLER group DOES satisfy rule 1's 'the same data-name and the same qualifiers, if any, up to, but not including, D1 and D2' relative to a same-named item declared directly under D2. If the premise is right the subtree should be VISITED, not skipped, and the current behaviour is a silent non-correspondence — pairs that should add simply do not, with no diagnostic.

RESIDUE 3 — ONE `try` WRAPS EVERY IMPLIED STATEMENT. CorrespondingEmitter.Emit runs all pairs inside the single try at ArithmeticEmitter.EmitArith:245, so a CobolSizeError raised during a pair's EVALUATION (CobolNum.Widen off an unsigned-wide operand) would ABORT the remaining implied statements, which §14.7.6 forbids ('after all of the implied statements are completed'). Reachability is unmeasured — the per-pair composite cap makes it unlikely — but the shape is there, and reachability is measured, not deduced.

ALSO UNTESTED: §14.7.6's no-phrase aggregation ('the level-3 EC-SIZE exception condition for the LAST of the implied statements that raised a size error condition is set to exist after all of the implied statements are completed') IS implemented — EmitArith:236-247 latches `__sizeEcN` by ASSIGNMENT per failing store, so last-wins, and EcEmitter.EmitSizeHandling runs after the pair loop — but has no test whatsoever.

WHAT WOULD CLOSE IT: an AssertOutput (not AssertSameAsLegacy) golden for the OCCURS/REDEFINES exclusion on ADD CORR; a no-SIZE-ERROR-phrase `>>TURN EC-SIZE` golden proving the LAST erring pair's condition is the one set; a spec derivation for the FILLER-group subtree with a golden either way; and per-pair isolation of the evaluation-time raise (or a derivation showing it cannot escape).

SPEC REFS as carried by the row: §14.9.2.4 GR5; §14.7.6 rules 1-6, its ordering sentence, its SIZE ERROR aggregation and its last paragraph (spec lines 21816, 21821-21841); §14.7.4.
