# PB3485 — HOLDINGS keys compare as bytes

From the implementer report of PB3337 (`E:\COBOL-coord\scratch\reports\w1137a-PB3337-report.md`, `## New defects` 4, carried). PB3337 has landed (PR #351, main 2353545b2), so this note is ready.

**Mechanism.** The HOLDINGS table (the locks a transaction keeps in the file) compares keys as bytes in `TransactionKeys.Record` (`src/Cobol.Net.Runtime/IO/Store/Transactions.cs`). The report gives no failing scenario. The implementer must first establish, against the spec and the index's own key comparison, whether a key the file treats as equal can have a different byte image (collating sequence, national or padded keys). If it can, compare through the index's comparer and sweep the sibling key comparisons for the same fault; if it cannot, record why and close the note.

## Landed (2026-10-21, wave 1140 group H)

**The re-probe says it can.** An INDEXED file whose collating sequence makes two key images one key (`ALPHABET … ALSO`: "A"
shares its position with "a") has records whose identity no byte compare decides (§12.4.5.12.4 GR1: key equality *"is based
on the collating sequence used for the file according to the rules for a relation condition"*; §14.9.51.4 GR35 for a unique
alternate key's value). Probe: seed "abcd"; run unit A under commit control DELETEs by the image "abcd"; run unit B WRITEs
"ABCD" and got **'00'** where the holding makes it '51' (§9.1.16, DOC-A.1-152). Three faults shared the root, "a key is its
bytes":

1. **The UNDO and HOLDINGS trees were ordered by the bytes.** A holding taken under one image was invisible under another, and
   a transaction's second change of a record under another image kept a second before-image (the first change's after-image)
   for the ROLLBACK to restore. Fixed at the root: `HoldingsKeyOrder` (Transactions.cs) orders a record holding through the
   prime tree's order and a value holding through its alternate key's, handed to the page layer by the connector at OPEN
   (`PagedFile.HoldingsOrder`: the page layer retires a transaction with no connector in reach). `PagedFile.Open/Create` take it;
   20 test callers changed (no default).
2. **A record's identity was the statement's image of its key, not the tree's.** REWRITE and DELETE took the caller's
   spelling for the UNDO key, so a ROLLBACK re-inserted the record under it (a changed key image in the prime tree).
   `IndexedStore.Get` now returns the stored key (`BTree.TryGet(key, out storedKey, out value)`), which REWRITE, DELETE and the
   random READ use.
3. **The §9.1.16 record lock was the statement's image, too** (`IndexedConnector.MutationTargetRecordIdCore`, `FindRandom`'s
   prime arm): a READ WITH LOCK by "abcd" did not conflict with a REWRITE by "ABCD" in another run unit. The sibling sweep
   found it; both now name the record by the stored image, which is also what the sequential READ and the alternate-key paths
   already used.

Witnesses: `tests/Cobol.Net.Tests.Unit/Store/HoldingsKeyOrderTests.cs` (11; 9 fail with the fix removed): the lock test of
a DELETE, a REWRITE and a freed unique value by every image; two changes under two images restore the first image; the record
lock; a dead owner rolled back by the next writer and by the next OPEN; a COMMIT refused at every read, write and sync under
variant images (its reversal included); the order itself. Left alone: a key number the order table has none for (the
`COBOLNET_KEYCHECK` opt-out) compares as bytes; documented in 2.2.1.10 As built (4).
