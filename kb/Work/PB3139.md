# PB3139 — a strong variable-length group with a pointer or object-reference leaf has no activation crossing form

> Re-verdicted 2026-10-16 (w1105 group H, PB3273): the shape is REACHABLE and REFUSED. See "Measured" below.

Source: wave 1072 F report (`w1072f-PB3129-report.md`, "New defects" item 2, "carried from the implementer, still
unprobed"). Filed by the enqueue unit's clerk on 2026-10-14. The clerk could not decide reachability (it is compiler
judgment), so the question is recorded as written.

**Code site.** `src/Cobol.Net.Compiler/Oo/OoConformance.cs:625-628`, in `DescriptionMismatch` (the §14.8.2.3.2
comparator, group arm):

```
if (OoClassTable.LeafCarried(formal) && OoClassTable.LeafCarried(arg)) return null;
if (arg.IsGroup && !arg.BoundaryImageCapable) return TierCIsland.Reason(arg, "argument group");
if (!formal.BoundaryImageCapable) return TierCIsland.Reason(formal, "formal group");
```

The comment above it (PB1116) says two STRONG groups of the same type are decided by the strongly-typed sentence and
cross as a leaf vector (`OoClassTable.LeafCarried`). PB204 lets a compatible variable-length group cross through its
current-extent codec. What nobody probed is a group that is BOTH strong and variable-length and holds a pointer /
object-reference leaf: whether `LeafCarried` is true for it (so the arm is never reached), and if it is not, whether
the Tier-C refusal (`TierCIsland.Reason`, `Binding/Model/TierCIsland.cs:50-55`) is the right answer or a refusal of
legal source.

**The original question (answered below).** Is the arm reached for a group that is BOTH strong and variable-length and
holds a pointer leaf, and does it answer correctly? Related: PB3129 (landed; the non-strong sibling), PB1116, PB965, and
PB3273 (the host entry withheld for the shape).

## Measured (2026-10-16, w1105 group H, on a fresh Debug build of main 2b5a81145; repros in `E:/COBOL-coord/scratch/w1105h/`)

The question is answered: the arm is REACHED, and it refuses legal source. `LeafCarried` is false for the shape
(`OoClassTable.LeafCarried` excludes `VariableLengthCompatibility.IsVariableLength`, "a variable-length strong group
keeps the section 8.5.1.12 carrier"), and that carrier is not available either, because `DataItem.CurrentExtentImageCapable`
is false for any group with a reference leaf (a pointer is no member of `CurrentExtentComposes`'s law). The shape has no
crossing form in ANY lane:

- `MIX2.cob` (strong type `TG` = `PIC X DYNAMIC LENGTH LIMIT IS 10`, `USAGE POINTER`, `PIC 9(2)`; a prototype `MIXSUB`
  with `USING LK-G TYPE TG`; `CALL MIXSUB USING WS-G`) is refused: `error COBOL1688: CALL ... program-prototype 'MIXSUB'
  argument 1 ('WS-G') does not conform to formal parameter 'LK-G': argument group 'WS-G' with a pointer/object-class leaf
  (no character image) - the Tier-C byte island (no whole-group character image), deferred`.
- `MIX4.cob` / `BOTH.cob` (the activated program alone, `PROCEDURE DIVISION USING LK-G`) compile, and the formal's
  copy-in is `NotImplemented.Value<string>("variable-length group image of 'L-B' with a pointer/object-class leaf ...")`
  (line 136 of the generated `BOTH.g.cs`), so any activation of it reaches the loud.
- `MIX3.cob` (one program, `MOVE WS-G TO WS-H` after `SET TP OF WS-G TO ADDRESS OF WS-X`) compiles and prints
  `[hello] 05 DATA` for the field accesses (the cell holds the dynamic slot and the managed slot together, so STORAGE
  works), then the group MOVE aborts with `NotImplementedCobolFeatureException: the sending operand of a variable-length
  group MOVE, 'WS-G', is a variable-length group whose current extent this implementation cannot compose ... CONFORMANCE.md
  A.1 item 57`.

**Expected, from the standard** (each `cite.py --check` OK): section 14.8.2.2 rule 2) "If either the formal parameter or the
corresponding argument is a strongly-typed group item, both shall be of the same type", so two groups of the one type
correspond whatever they hold; section 13.18.60.3 SR14 admits a POINTER leaf "subordinate to a type declaration that includes
the STRONG phrase", and nothing in section 8.5.1.12.1 ("a group item whose data description has at least one dynamic-length
elementary item or dynamic-capacity table as a subordinate item") bars a strong group from being variable-length. The
declaration is legal, so the CALL (through a prototype: section 14.9.4.3 SR10 admits no other form for a strong group) is
legal, and COBOL1688 rejects legal source.

**Where the form belongs.** The storage already holds both (the cell has managed slots and dynamic slots); the missing
piece is a crossing form. `CallEmitter.AreaOf` already states a variable-length group's cell area (`VarGroupWindow`,
PB2094), so a strong group of the one type can cross BY REFERENCE as its area alone, as a leaf-carried fixed strong group does
(PB1116/PB2087); BY CONTENT needs the detached cell copy (`CobolArgAdapt.ContentRecord`) to copy the dynamic slots too; and
the capability gate (`CurrentExtentImageCapable` / `LeafCarried` / `ActivationDescriptions.Of`) is the single place that
must say the shape crosses. The consumers that compare or move the group whole (MOVE, relation, DISPLAY, LENGTH) need their
own determination of what a reference member contributes to a carrier (the placeholder image of DOC-A.1-214, with or
without the reference). That is a redesign beyond a host-surface slice, so it is registered here, with the host entry
(PB3273) waiting on it.

## Progress (2026-10-16, w1106c — the COBOL boundary and the MOVE; the host entry remains)

Re-probed on a fresh Debug build of main 0b8557338: `MIX2.cob` drew COBOL1688 on the CALL and ALSO COBOL1513 (the
prototype against its own definition, the same missing crossing form seen by the signature comparator); `MIX3.cob`'s
group MOVE aborted with the GR9 loud; `BOTH.cob`'s formal staged the Tier-C loud at its copy-out. A fixed-length twin
(`PIC X(10)` for the dynamic item) crossed correctly, so the variable-length exclusion was the whole cause.

**Fix (one capability, every consumer).** `OoClassTable.LeafCarried` no longer excludes a variable-length strong group:
one whose current extent composes keeps its §8.5.1.12 carrier (`BoundaryImageCapable` excludes it), one with a reference
leaf has no other form, so it crosses as the leaf vector / the cell area like a fixed one (§14.8.2.2 rule 2). The
consumers that the gate now admits were completed:
- the cell AREA carries the components: `StorageCell.CopyArea` / `StoreArea` take the area's `DynBase` and component
  count (a dynamic-length item's content; a dynamic-capacity table as a detached copy, `CobolDynTable.CopyOf`, its
  element cells copied whole with their slots), so `CobolArgAdapt.ContentRecord` (BY CONTENT; it now keeps the area's
  `Shape`, so the formal is laid over it) and `StoreReturnArea` (RETURNING) keep them;
- the BY CONTENT carrier of a slot-riding group is a read-only view (`RuntimeApi.ReadOnlyTextView`) — the eager
  image snapshot was the loud;
- the leaf vector carries a dynamic-capacity table as its current occurrences: `RecordStructEmitter.EmitLeafMethods`
  emits an instance `WithLeaves` (replacing the static `OfLeaves`) that recreates the receiver's own table
  (`CobolDynTable.Recreated`, §14.6.9.2), and `PlaceRenderer.CellLeaves` / `CellLeavesStore` read a cell table's
  occurrences up to its capacity and recreate the receiving one (`ViewCursor.AtElementCell`);
- `MoveEmitter.EmitGroupMove` asks the leaf vector BEFORE GR9's composer (two groups of one type are GR9 a)'s equal-length
  groups whose every position, item and table corresponds).
Goldens: `conformance-suite/cases/14.8.2.2-Group-items/pb3139_strong_vlg_pointer_call` (CALL BY REFERENCE / BY CONTENT / RETURNING, a
function result, MOVE cell<->struct; pointers in a table element), `pb3139_strong_vlg_objref_invoke` (INVOKE, object
references in a table element), negative `conformance-suite/cases/13.18.19-DYNAMIC-LENGTH/pb3139-strong-vlg-pointer-at-2002`. The shipped runtime surface changed
(CopyArea / StoreArea / ContentRecord / StoreReturnArea): the runtime major rises (10 on main a0a2ff24f, which PB3339 had already taken to 9), `RuntimeAbiPinDriftTests` re-pinned.

**Remaining (the NEXT step of this note): the .NET host entry (PB3273's restriction).** `PublishedRecordEmitter.Renders`
still withholds an entry for a group holding both a component and a reference: the COBOL boundary now carries it as its
cell area with components, but the published record composes no such area (its slot form `__Area` has no component, its
variable-length form `CobolVarGroup` no slot), so an entry's argument would reach the formal's non-aliased copy-in loud.
Lifting it = `__Area` composing the components beside the slots (and `__TryGet` reading them back, a dynamic table's
element records included), `HostEntryEmitter` passing that area with the group's `Shape`, then lifting `Renders` and
turning `HostEntryShapeDriftTests.AGroupHoldingAComponentAndAReference_PublishesNoEntry_WhileTheBoundaryHasNoFormForIt`
into the positive pin. Out of scope here as well, and unchanged: DISPLAY / relation / LENGTH of the whole group (the
DOC-A.1-214 placeholder-image determination the body above names).

## Progress (2026-10-17, w1111b — carried onto main 4016a67cb; the host entry still remains)

routed through `PIC Z` / `PIC X` holders for the portability lint. All three re-probed and gated green (leg 1).

**Design constraint found for the host-entry step (read before starting it).** The callee's area formal is laid over the
host's area only when the area states a `Shape` its atoms `LaysOver` (`CobolArgAdapt.Area`), so `HostEntryEmitter.ArgOver`
must pass `RuntimeApi.ArgArea(cell, "0", "0", <atoms>)` with the group's `VariableLengthCompatibility.GroupAtoms` through
the module's one `GroupAtomTable` (`ProgramEmitter._atoms`, emitted after the host entries, so the emitter needs it as a
constructor argument). The area's dynamic-capacity tables are then the HOST's `CobolDynTable<StorageCell>` objects, whose
seed is what a later statement of the activated program creates occurrences from: the description's own seed
(`DataEmitter.AreaFormalShape`'s fresh-cell factory, `GroupImageCodec.CellDynSeeds`, the INITIALIZED recipe of
§8.5.1.9.5) is emitted in the PROGRAM class and names that class's private `NumProfile` fields (`_P_<uid>`), so the host
class cannot reuse its text. Either the program class exposes the formal's fresh-cell factory (an internal static the host
entry calls), or the host composes its tables through a seed of its own and the INITIALIZED phrase's created elements are
decided there; pick against DESIGN-external-repository §4.3 and record the choice in the design doc.
