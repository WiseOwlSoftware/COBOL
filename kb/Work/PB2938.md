# PB2938 — the ref-mod detail names the int clamp, not the operand's value

**Found:** wave 1053 group G (PB2695), report `E:\COBOL-coord\scratch\reports\w1053g-PB2695-report.md`, "New defects"
1, and the sibling sweep in PB2695's Landed section; filed by the train 1053 lander.

**The defect.** A reference modifier's leftmost position or length whose value exceeds an `int` (`01 A PIC 9(21) VALUE
100000000000000000001.`, `>>TURN EC-BOUND-REF-MOD CHECKING ON`, `MOVE X(A:1) TO Y`) raises EC-BOUND-REF-MOD correctly,
but its detail names `reference modification (2147483647:1)`: the `int`-saturated value, never the operand the program
holds. The value stays out of range (the clamp preserves §8.4.3.3.4 rule 5's outcome); only the message is wrong.

**Mechanism.** The same narrowing PB2695 removed from the subscript chain, on a different consumer chain: the operand
reaches the runtime through `RuntimeApi.HostInt32` (`src/Cobol.Net.Compiler/CodeGen/Roslyn/RuntimeApi.cs` about line
1067; `StrRefModStartOffset` about line 1049), and `CobolString.RefMod` / `SpliceInto` / `RefModStartOffset` format the
clamped `int` into the detail (`src/Cobol.Net.Runtime/Values/Text/CobolString.cs` lines 179, 198 and 230). The ref-mod
API is `int`-typed with many callers, which is why PB2695 left it out.

**What closes it.** The PB2695 shape: a position carrier that holds the clamp the accessor uses and the exact value text
built only at the saturation extremes (`Values/Tables/Occurrence.cs` is the subscript twin), threaded through the
ref-mod accessors so overload resolution picks it and no emission site passes display text; a golden with a 21-digit
start and length under EC-BOUND-REF-MOD.

**Rule:** §8.4.3.3.4 5) (the reference-modification range check); the detail text is the implementor's, and it must
name the value the program holds.
