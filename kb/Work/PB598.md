# PB598 — LANDED — a size rule for an item, applied to a condition-name

Found 2026-09-05 attributing battery #45's GnuCOBOL differential flips (`scratchpad/battery-45/flips/ATTRIBUTION.md`,
23 citations `cite.py --check`ed, all OK); re-derived on the battery worktree at `b3aad3fc` for this note.

## Repro (`--std 2023`; identical at 85/2002/2014)

```cobol
       01 XV PIC X.
          88 XC VALUE "cd".              *> COBOLNET1740  — NEW at b3aad3fc (PB206), accepted at 89044aa0
       01 NV PIC N(2).
          88 NC VALUE N"ABC".            *> COBOLNET0898 (SR5) — already wrong at 89044aa0
       01 BV PIC 1(2) USAGE BIT.
          88 BC VALUE B"101".            *> COBOLNET0898 (SR10) — already wrong at 89044aa0
```

Measured on the pre-train-2 build: the alphanumeric case compiles and behaves exactly as the standard requires
(`FALSE` / `XV=[c]` / `FALSE` — the condition is never true, `SET XC TO TRUE` truncates to the right). PB206 did
not create the defect; it completed it, which is why only the alphanumeric arm surfaces as a differential flip
(the corpus has no oversize national or boolean level-88 literal — measured: 0 of 1,611 members).

## The rule

SR4 sentence 2 constrains only "the VALUE clause of **an elementary item**" against "the size indicated by **an
explicit** PICTURE clause" (`OK §13.18.63.3 4)`); SR5 s.2 and SR10 s.2 are the same sentence for national and
boolean (`OK §13.18.63.3 5)`, `OK §13.18.63.3 10)`). A Format-3 entry is `88 condition-name-1 value-clause .`
(`OK §13.16.2`) — no PICTURE clause is writable in it — and its subject is a condition-name (`OK §13.16.4 3)`,
`OK §8.5.1.3.2 3)`), not a data item (§3.169) and not an elementary item (§8.5.1.3.1). SR33 ("Formats 3 and 5
may be specified only when the level-number of the subject of the entry is 88", `OK §13.18.63.3 33)`) confirms
the subject of a Format-3 VALUE clause is the level-88 entry's own. §13.18.63.4 GR19 gives a condition-name its
conditional variable's characteristics only **implicitly** (`OK §13.18.63.4 19)`), which is what "explicit"
excludes.

⚠ **CORRECTED ON LANDING.** This note said "SR24's import of SR10 into Format 3 carries its first sentence
only". It does not, and the correction matters because it is the difference between an argument about the
IMPORT and an argument about the SENTENCE. §13.18.63.3's syntax rules are printed in LABELLED BLOCKS —
`ALL FORMATS` SR1–SR9, `FORMAT 1` SR10–SR15, `FORMAT 2` SR16–SR23, `FORMAT 3` SR24–SR33,
`FORMAT 4` SR34–SR35, `FORMAT 5` SR36–SR39 — so SR4 and SR5 govern a Format-3 entry **directly**
(they are ALL FORMATS rules), while SR10 sits in the FORMAT 1 block and reaches Format 3 only through SR24,
"Syntax rules 10 and 17 above apply" (`OK §13.18.63.3 24)`), which imports the rule **whole** — both
sentences. The import is therefore not what stops the size sentence; the sentence's own antecedent is, and that
antecedent is the same in all three rules. The conclusion is unchanged and the argument is now ONE argument for
every arm.

No other rule bounds the size:
the condition compares by relation-condition rules (`OK §8.8.4.5.3 2)`) and `SET … TO TRUE` transfers with
truncation to the right (`OK §14.9.39.4 6)` → `OK §13.18.63.4 7)` → `OK §14.6.8.5`).

**Relation to `PB586`** (SR2's representability half not reaching level 88): compatible, and textual. SR2 is
written against "the subject of the entry" and bounds by "**the** PICTURE clause or **the** USAGE clause" for a
NUMERIC subject; SR4/SR5/SR10's size sentences are written against "an elementary item" with "an explicit
PICTURE clause". Both touch the same three call sites — land them together or in a stated order.

## Code site (`src/Cobol.Net.Compiler/Binding/DataBinder.cs`, line numbers at `b3aad3fc`)

The three level-88 call sites pass a non-null `sizePositions` computed from the CONDITIONAL VARIABLE's picture —
`:2286` `int? rangeSize = ValueSizePositions(rp, parent.IsDynamicLength, parent.IsAnyLength);` feeding `:2287`/
`:2288` (THROUGH low/high) and `:2303`–`:2304` (single-literal leg). Those light the three size arms inside
`ValidateValueCategory` (`:1363`): `:1435`–`:1438` (SR5, COBOLNET0898), `:1449`–`:1452` (SR10, COBOLNET0898),
`:1520`–`:1526` (SR4, COBOLNET1740 — PB206's third arm). **The fix is at the call sites, not in the arms:** a
Format-3 subject indicates no size, so all three level-88 calls pass no size, exactly as `ValueSizePositions`
already returns null for DYNAMIC LENGTH / ANY LENGTH. Make it structural rather than three literal nulls: reach
the screen through a single "subject kind" descriptor (elementary entry / group / condition-name) so a fourth
subject kind cannot acquire a size by accident — the XML doc at `:1339`–`:1362` already enumerates the three
kinds in prose, and that prose is what must become a type. `ScreenValueLiteral` (`:1284`) and the group site
(`DataBinder.GroupValue.cs:126`) keep their sizes.

## Goldens

(1) POSITIVE, all four editions — an oversize level-88 alphanumeric literal compiles, the condition is FALSE and
`SET … TO TRUE` truncates: expected `FALSE / XV=[c] / FALSE`. (2) POSITIVE, 2002+ — the national and boolean
twins. (3) A THROUGH-range positive (`88 R VALUE "aa" THRU "zz"` on `PIC X`) — the range leg is a separate call
site. (4) The existing negatives `pb206-value-oversize-elementary` (PB206N3) and `pb206-group-value-oversize`
(PB206N2) must stay red — that pair is the drift proof that the withheld size is scoped to level 88 only.
Rebaseline `syn_misc:388` stays `AGREE_ACCEPT` and the differential returns to zero flips on this row.

## Landed 2026-09-05

**The fix is a TYPE, not three nulls.** `ValidateValueCategory` took an `int? sizePositions` plus a
`bool groupSubject`; those are not two facts but one — WHICH SUBJECT §13.18.63.3 is addressing — spelled twice,
and a caller was free to compose a pair the standard does not have. It did. They are now one `ValueSubject`
(`src/Cobol.Net.Compiler/Binding/ValueSubject.cs`), a `readonly record struct` carrying a `ValueSubjectKind` and
the size, constructible ONLY by `ForElementary(pic, isDynamicLength, isAnyLength)`, `ForGroup(sizePositions)` and
`ForConditionName()` — each of which states its size rule with its citation on the factory itself.
`ValueSizePositions` is gone: its DYNAMIC LENGTH / ANY LENGTH derivation is now `ForElementary`'s body, so "what
size does this subject indicate" is answered once per kind and never at a call site. A fourth subject kind has to
add a factory and write its rule down; it cannot inherit a size by accident.

All five call sites now name their subject: `BindCondition`'s THROUGH-range pair and its singleton leg →
`ForConditionName()`; the format-1 item VALUE (`BindEntry`) and the format-2 per-occurrence literals
(`ValidateTableValues`) → `ForElementary`; the group-level VALUE (`DataBinder.GroupValue`) → `ForGroup`.

**Measured on this worktree.** Before: all three arms rejected (`COBOLNET1740` alphanumeric, `COBOLNET0898`
national and boolean). After, at `--std` 2002 / 2014 / 2023: `FALSE` / `XV=[c]` / `FALSE`, exactly the
derivation. At `--std 85` the same source is rejected for the national/boolean CATEGORY gate (`COBOLNET0900`)
and for nothing else — the alphanumeric arm runs. GnuCOBOL differential `syn_misc:388` compiles clean (exit 0)
→ **`AGREE_ACCEPT` restored**, matching the baseline row, which was not touched.

### Not taken here

[[PB586]] (SR2's REPRESENTABILITY half never reaching a level-88 literal) was left, and deliberately. It does not
fall out of the subject descriptor: SR2's two halves live in two methods — `ValidateValueCategory` (class) and
`ValidateNumericValue` (range/sign) — and the level-88 sites call only the first. Closing it means routing those
sites through `ScreenValueLiteral`, a second mechanism with its own §14.7.8 range interaction.
⚠ **A warning for whoever takes it:** GnuCOBOL accepts `01 x PIC 9. 88 never-true VALUE 99.` with a warning, and
that is the FIRST check inside the very case this note flipped back (`syn_misc:388`, `prog.cob:8`). Landing PB586
as a hard error flips that row to `WE_REJECT_THEY_ACCEPT` again. Its disposition has to be settled against SR2's
"shall" — which admits only a diagnostic — and the row rebaselined in the same change set, not discovered by the
next battery.

[[PB575]] (SR24's group-parent leg — `parent.Pic` is null for a bit or national GROUP conditional variable, so the
whole funnel is skipped) is untouched and still open: the same three call sites from a third direction.
