# PB1746 — the counter registers' width under GnuCOBOL

## The question

§8.4.3.15.4 GR1 (`cite.py --check 8.4.3.15.4 "temporary"` → OK §8.4.3.15.4 1)): "PAGE-COUNTER and LINE-COUNTER
reference temporary unsigned integer data items of class and category numeric, which are maintained for each report."
The standard gives no size and no usage. kb/Work R26 set the capacity (LINAGE-COUNTER: the page size's digits;
PAGE-/LINE-COUNTER: PIC 9(18)), and wave 73 group C (PB1153, PB1199, PB1318) made the implicit description
`PIC 9(d) USAGE DISPLAY` in every consumer, recorded in `docs/CONFORMANCE.md` beside R26's capacity.

Consequences the owner may not want: `DISPLAY PAGE-COUNTER` prints 18 digits (`000000000000000001`), and
`MOVE LINE-COUNTER TO` a PIC X(4) item stores the leftmost four digits, `0000`.

## What to do

With a local `cobc`, compile a report file with PAGE-COUNTER and LINE-COUNTER referenced in DISPLAY, MOVE to a
PIC X(4), STRING and FUNCTION LENGTH, and record GnuCOBOL's width for each. Where GnuCOBOL's width differs from 18,
the owner decides whether R26's capacity follows it (CLAUDE.md rule 1: the spec is silent, so GnuCOBOL decides the
latitude). Record the result in `docs/CONFORMANCE.md`'s counter-register entry.

## Re-filed as a defect (analyses sweep, 2026-10-23)

Adjudicated read-only by an Opus cobol-adjudicator on main e7cf38ce4; accepted by the Mythos session.

§8.4.3.15.4 1) gives the registers no size and no usage, so CLAUDE.md rule 1's latitude order makes GnuCOBOL decide, and GnuCOBOL answers: an unsigned 32-bit binary integer (USAGE UNSIGNED-INT, a 10-digit image), not a 18-digit DISPLAY item. The current PIC 9(18) USAGE DISPLAY shape (R26's capacity, made the implicit description by PB1153/PB1199/PB1318 and documented in docs/CONFORMANCE.md §3 'The counter registers' declared capacity') was an implementor choice made without the survey, so it differs from the rule-1 answer in width (DISPLAY PAGE-COUNTER: 18 digits vs 10), in capacity (HIGHEST-ALGEBRAIC 999,999,999,999,999,999 vs the unsigned 32-bit maximum, to be measured with cobc) and in usage (STRING accepts the register here; GnuCOBOL refuses it under §14.9.43.3 SR1). Fix: re-derive the registers' implicit description from GnuCOBOL (one statement in AlgebraicRanges.OfCounterRegister and the counter-register description every consumer reads), rewrite the CONFORMANCE §3 entry with the survey, update the goldens that pin 18 digits (algebraic_counter_registers and wave 73 C's), and add a negative for STRING of a register. MOVE LINE-COUNTER TO a PIC X(4) item stays 0000 in both. If the owner prefers to keep the 18-digit DISPLAY shape against rule 1, that is the one question to ask instead.

Evidence: Survey done with the WSL cobc 3.2.0 (probe pb1746/g.cob) and the pinned source: GnuCOBOL declares both registers CB_USAGE_UNSIGNED_INT (cobc/tree.c:4290-4311), DISPLAY PAGE-COUNTER/LINE-COUNTER prints 10 digits ([0000000001]), MOVE to PIC X(4) stores 0000, STRING refuses the register ('must be USAGE DISPLAY or NATIONAL'), FUNCTION LENGTH(PAGE-COUNTER) is a syntax error. Ours (main): 18 digits ([000000000000000001]), X(4) 0000, STRING accepted ([000000000000000001]), LENGTH 18.

Rule: §8.4.3.15.4 1) (checked); latitude per CLAUDE.md rule 1 (GnuCOBOL 3.2 cobc/tree.c)

# Landed 2026-10-23 (wave 20261027, group F)

Re-probed on the fix lane's build (main 15ac00571): `DISPLAY PAGE-COUNTER` printed `000000000000000001`, `STRING`
accepted the register, `FUNCTION LENGTH` answered 18, `UNSTRING PAGE-COUNTER` compiled and split the image - all as
the adjudication measured. The WSL cobc 3.2.0 survey was re-run (probes under the wave scratch `pb1746/`) and the
pinned source read: `build_report` (cobc/tree.c) declares `CB_USAGE_UNSIGNED_INT` for LINE-COUNTER and PAGE-COUNTER
(and for LINAGE-COUNTER, which GR1 sizes by the page size's digits, so the standard decides that one and it stays
`PIC 9(d) USAGE DISPLAY`).

Fix: the report counters' implicit description is now ONE statement, `PicInfo.ReportCounterItem` = the unsigned
`BinaryLong` shape (capacity 4,294,967,295, 10-digit image, 4 bytes); `AlgebraicRanges.DescribeCounter` builds
every consumer's answer from it (the algebraic extremes, the image width, the LENGTH / BYTE-LENGTH bytes and the
usage predicate), replacing the second hand-written copy (`ReportCounterCapacity` 999999999999999999) that sat beside
the receiving profile's 18 digits. The usage predicate drives three screens: STRING's SR1 (a register sender,
COBOL1626), the 8.8.4.2.5 relation (COBOL2532) and - found on the way - UNSTRING's SR2 category screen, which
had no arm for a register at all (all three registers, COBOL1651). The runtime carriers
(`CobolReport.LineCounter` / `PageCounter`) reduce every assignment modulo `CounterModulus` (2^32), pinned to the
compiler's description by `ReportCounterDescriptionDriftTests`. docs/CONFORMANCE.md section 3 carries the survey and
the determination. Goldens: `wiseowl:cases/8.4.3.15-Report-counters/pb1746_*` (description, page-advance wrap) and
five `pb1746-*` refusals; the PB1153 / R26 goldens were updated to the 10-digit, 4-byte description.

## Landing

- `src/WiseOwl.Cobol.Compiler/Binding/AlgebraicRange.cs#AlgebraicRanges.DescribeCounter` - the one reader of a register's description (extremes, digits, bytes, usage); REUSE `CounterRegisterDigits` / `CounterRegisterByteLength` / `CounterRegisterIsUsageDisplay`, never a second capacity string. Trap: LINAGE-COUNTER is a DISPLAY `PIC 9(d)` by §8.4.3.14.4 GR1 while LINE-/PAGE-COUNTER are the 32-bit binary item, so any "is it display" question must ask the usage predicate, not `IsCounterRegister`.
- `src/WiseOwl.Cobol.Compiler/Binding/Model/PicInfo.cs#PicInfo.ReportCounterItem` - the ONE statement of the report counters' description (`BinaryItem(Usage.BinaryLong, signed: false)`); the PAGE-COUNTER receiving place reads it too. Changing the width means changing `CobolReport.CounterModulus` with it (`ReportCounterDescriptionDriftTests`).
- `src/WiseOwl.Cobol.Runtime/IO/ReportWriter.cs#CobolReport.CounterModulus` - the runtime's twin; the `LineCounter` / `PageCounter` setters mask to it, so the engine's `+= ` and `+ 1` arithmetic wraps like cobc's.
- `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/StringUnstringBinder.cs#Sr1Offence` / `UnstringSenderCategory` - the register arms; a register reaches these as a `BoundComputedOperand`, never a field operand, so a new operand-screen needs its own register arm (INSPECT does not: PAGE-COUNTER is a Place there; LINE-/LINAGE-COUNTER INSPECT is the PB1056 deferral census, COBOL1756).
- `src/WiseOwl.Cobol.Compiler/Binding/RelationComparability.cs#IsNumericIntegerOperand` - the register arm asks the usage predicate.
