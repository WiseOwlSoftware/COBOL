**Mechanism.** §1985:VIII.4.5.4 GR16 measures the record read against the record DESCRIPTIONS: "If the number of character positions in the record that is read is less than the minimum size specified by the record description entries for file-name-1, the portion of the record area which is to the right of the last valid character read is undefined", and if it is greater than the maximum the record is truncated; in both cases "the READ statement is successful and an I-O status is set indicating a record length conflict has occurred". The code read held that the OPEN's fixed-attribute check (status 39 when the store's record bounds differ from the RECORD clause, `FixedAttributeConflict`) keeps every record inside the bounds, so GR16 can never arise. The refuter showed that the RECORD clause bounds and the record-description bounds are different numbers: §1985:VII.3.8.3 SR2 lets the descriptions lie anywhere inside FROM integer-2 TO integer-3, and a WRITE with a DEPENDING ON value inside integer-2..integer-3 succeeds. So one program, with no attribute conflict, writes records shorter and longer than its only record description, and the relative READ reports 00 for both.

**Reading to settle in the fix.** §1985:VIII.1.3.4 defines status 04 as "A READ statement is successfully executed but the length of the record being processed does not conform to the fixed file attributes for that file", in terms of the fixed file attributes, while GR16 states the condition in terms of the record description entries. The refuter took GR16 as the controlling text for the READ (rule 1); the fix records the reading in `docs/CONFORMANCE.md` beside DOC-A.1-129 and applies it to the sequential and indexed READ, whose modules print the same rule.
