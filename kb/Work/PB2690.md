# PB2690 — LANDED: the pair conversion at the activation boundary, the related arm, and the INITIALIZED defaults of boundary-created occurrences (the last in wave 1072 C, below)

## What was found (w1042 C, PB2496, landed in train 1042)
PB2496 moved MOVE and the relation condition onto ONE pair conversion, `CobolVarGroup.Reshape`/`Compare` over the
two operands' `GroupAtom` shapes, which recurse per element into a nested dynamic table of variable-length elements.
The activation boundary did not move with them:

1. **LOUD on legal source.** At CALL (`CallAbi.Text`, `TextValue`, `VarGroup`, `VarGroupValue`, `StoreReturn*`) and at
   INVOKE (`OoEmitter.FixedArgumentSpans`, `VarPlaceSpans`) a fixed-length group facing a variable-length group is
   still paired by flat `CorrespondingSpans`, which carry no element layout. A fixed group opposite a dynamic-capacity
   table of variable-length elements therefore reaches the named refusal in the span adapters (`ToFixedImage`,
   `OverlayFixedImage`, `ElementCarriersAt` refuse a nested component by name), where §14.2.3 GR8/GR9 and
   §8.5.1.12.1 make the pair legal when the groups are compatible.
2. **PERF.** The atom arrays for `Compare` and `Reshape` are emitted inline (`RuntimeApi.GroupAtomsNew`, used by
   `RuntimeApi.cs` lines ~1886 and ~1911, and by `CallEmitter.BoundaryAtoms` / `ProgramEmitter.GroupFormalAtoms`),
   so every execution of a variable-length MOVE, comparison or CALL allocates them; `Compare` also re-walks the
   correspondence on every call.

## Fix shape (one mechanism)
Move `CallAbi` and `OoEmitter` to `Reshape` with `(image, [])` for the fixed side and the argument/formal atoms, as
MOVE does since PB2496, and delete `FromFixedImage`, `ToFixedImage`, `OverlayFixedImage` and `CorrespondingSpans`
(rule 4: no adapter left behind). Emit each distinct atom array ONCE as a `static readonly GroupAtom[]` field of the
program class and reference it, and let the runtime cache the correspondence walk per atom-array pair.

## Repro
Variant of `tests/conformance/2014/pb2496_vlg_dynamic_element_tables_call.cob` whose actual argument is a FIXED group
of the formal's element layout (a fixed OCCURS table of fixed elements) passed BY REFERENCE to a formal that is a
dynamic table of variable-length elements: aborts with the named NotImplemented in the span adapter.

## Sites
`src/Cobol.Net.Runtime/Control/CallAbi.cs#VarGroup` (line ~1124), `#VarGroupValue` (~1181), `#StoreReturn` (~1515);
`src/Cobol.Net.Compiler/CodeGen/Verbs/OoEmitter.cs#FixedArgumentSpans`/`#VarPlaceSpans`;
`src/Cobol.Net.Compiler/CodeGen/Roslyn/RuntimeApi.cs#GroupAtomsNew`.

## The related arm (ADJUDICATED and LANDED in wave 1069 C; this section is the record of the question)

Re-probed 2026-10-10 on this build: `E:\COBOL-coord\scratch\w1045f\p\b6.cob` (`--std 2014`) prints
`IN=[xa dd]` and `G1=[xpzz] C1=0000000001`: the callee's store to occurrence 2 of its FIXED table T OCCURS 2 is lost because
the caller's dynamic table has capacity 1. The determination in code today (`CobolVarGroup.Overlay`, recorded as a
DETERMINATION) is that a formal's fixed table cannot change the argument table's capacity; 8.5.1.12.3 sentence 3 ("the
dynamic-capacity table is considered to be the same length as the corresponding table") could be read the other way. The
standard does not decide it (8.5.1.12.3 and 14.2.3 GR8 both bear on it), so it is an implementor determination: CLAUDE.md
rule 1's precedence (ISO, then GnuCOBOL, then IBM / Micro Focus) has to be applied to a construct whose external behavior
nobody has measured here, and the choice then recorded in `docs/CONFORMANCE.md`. Whoever takes this note adjudicates first,
then changes `Overlay`'s fixed-table arm and its twin `OverlayImage`/`OverlaidImage` together.

## Landed (wave 1069 C, 2026-10-12): the related arm, and the performance residue

**The adjudication.** Re-probed on a fresh build: `E:\COBOL-coord\scratch\w1045f\p\b6.cob` and `c6.cob` (`--std 2014`) still
printed `G1=[xpzz] C1=0000000001` (the callee's store to occurrence 2 of its FIXED `T OCCURS 2` was lost). The standard
decides it, and the earlier "implementor determination" (`Overlay`: a formal's fixed table "has no capacity to state") was
a paraphrase the text does not support. Section 14.2.3 GR8 (cite.py OK): the BY REFERENCE formal "operates as if the formal
parameter occupies the same storage area as the argument". A store through the formal's occurrence N is then a receiving
reference to the argument's dynamic-capacity table, and section 8.5.1.9.3 (cite.py OK) covers it outright: "When a data
item in a dynamic-capacity table is referenced as a receiving item and the value of the subscript exceeds the current
capacity of the table, a new element is automatically created and the capacity of the table is increased to the value given
by the subscript." Section 8.5.1.12.3 sentence 3 ("the dynamic-capacity table is considered to be the same length as the
corresponding table") makes the pair legal; it speaks "for purposes of determining compatibility", so it neither grows the
table on a mere call nor forbids growth on a store. Precedence (CLAUDE.md rule 1): the ISO text controls the arm that
matters, so no GnuCOBOL or vendor measurement was taken or claimed. The one latitude is HOW a store is recognised: the
boundary hands a copy and sees only the finished view, so a store is recognised by its effect (an image that is not the
space fill the view showed for an occurrence the argument lacks); a callee that only reads past the capacity creates
nothing; a callee that stores spaces there cannot be told from one that did not. Recorded as D-VGB in
`docs/CONFORMANCE.md` section 3 and in `docs/COBOLNET_INTERPROGRAM_DESIGN.md`.

**The fix** (one place): `CobolVarGroup.Overlay`'s fixed-table arm goes through `OverlaidTable` (scalar elements) and
`GrownCount` (the nested arm, `OverlaidOccurrences` with `resize: false`), so `OverlayImage` (a fixed GROUP formal over a
variable-length argument), a variable-length formal with a fixed table, and the INVOKE lanes (typed `RuntimeApi.VarGroupOverlay*`
and the universal `CobolInvokeArg`) all grow the table alike, at the element level and one level down. The reverse arm
(`OverlaidImage`: a variable-length formal over a FIXED argument) cannot grow, as before. Goldens:
`2014/pb2690_fixed_table_formal_grows_dynamic_argument_call` (scalar elements; a read-only callee, BY CONTENT, a fixed GROUP
formal, a dynamic-length-only store), `_vlg_element_table_call` (elements holding an inner table),
`_dynamic_argument_invoke` (typed; the universal lane was probed by hand), negative
`pb2690-fixed-table-formal-grows-dynamic-argument-below-2014`, unit `BoundaryGroupCorrespondenceTests` (the stores, the
nested inner occurrence, and the two tests that had pinned the old "no growth" reading). `2014/pb965_vlg_into_fixed_invoke`
pinned the old reading in its OUTPUT (`VCAP=2` after a method stored `LT(3)`): re-derived, now `[mno]` and `VCAP=3`.

**The performance residue.** `GroupCompatibility.FixedRun` returns ONE array per width (`s_fixedRuns`, registered in
`RunUnitStateDriftTests.ProcessLifetimeCollections`), so the call sites that built it per call (`CallAbi` StoreReturn,
`FixedShapeOf`, `VariableToFixedPair`; `ActivationRelations.AtomsOf`; `CobolVarGroup.ElementShape`) hit the pair-plan and
geometry caches. Test `TheOneRunShapeOfAWidth_IsOneArray_SoTheBoundarysCachesHitOnEveryCall`.

**Sibling sweep.** The other arms of the dispatch: MOVE and RETURNING recreate the receiving table through `Reshape` at the
sender's capacity (section 14.6.9.2) and never lost a store; `OverlaidImage` (fixed argument) cannot grow; both INVOKE lanes
call the same `Overlay`. No other writer drops a store past a dynamic table's capacity.

## The record of the last half (wave 1069 C branch review round 1, finding R1-1): INITIALIZED defaults of the occurrences a boundary store creates

The landed growth (`CobolVarGroup.OverlaidTable` / `GrownCount`) creates the occurrences the callee stored into, but every
item of a created occurrence that the callee did not store comes back SPACE FILLED, and so does every intermediate
occurrence. Section 8.5.1.9.5 (cite.py OK) says that for a dynamic-capacity table with the INITIALIZED phrase, "any elementary
items not referenced as receiving operands in a statement that creates new elements in that table are first initialized as
though they had been the subject of a statement of the form INITIALIZE ... WITH FILLER ALL TO VALUE THEN TO DEFAULT".
Repro (`--std 2014`, the reviewer's probe, built at 543e79ed1): caller `01 GA. 05 AX PIC X VALUE "x". 05 ATB OCCURS DYNAMIC
CAPACITY IN CA FROM 1 INITIALIZED. 10 AE PIC X VALUE "a". 10 AF PIC X VALUE "b".` calls `RVB3 AS NESTED USING GA`, whose
LINKAGE formal has `05 TF OCCURS 3. 10 FE PIC X. 10 FF PIC X.` and does `MOVE "r" TO FE (3)`. The caller prints
`[ab|  |r ] 3`; the same store made directly in the caller prints `[ab|ab|rb] 3`, which 14.2.3 GR8 + 8.5.1.9.3 + 8.5.1.9.5
require. Without INITIALIZED the content of the unreferenced locations is "undefined", so only INITIALIZED tables are wrong.

Why it was not fixed in the review round (I9: a redesign beyond the slice). `Overlay` is a pure function of two carriers and
two atom arrays; neither knows the table's INITIALIZED default element, which exists only as a C# seed expression on the
`CobolDynTable` (`_createdAt`) and is never a bind-time constant (`ValueInitializer` emits expressions). The default has to
travel on the ARGUMENT carrier, so every builder of a dynamic-table component must supply it: the emitted
`AsVarImage` composer (`GroupImageCodec.EmitVarImageMethods`, `DynTable` and `DynGroupTable` parts), the cell reader
(`StorageCell.VarGroupAt` / `ElementCarriersAt`), and the carrier's own rebuilds (`Slice`, `Concat`, `SplitTail`/`JoinTail`,
`Overlay`, `Reshape`), plus a new `CobolDynTable` accessor for the created element's image (and carrier, for the nested arm).
`Overlay` then merges item by item with the same effect test as D-VGB (an item whose image is all spaces was not stored;
item boundaries are the arm atom's `Element` Fixed atoms, a scalar element is one item). Two builders and six rebuilds is
the two-arm shape this repository's drift tests exist for, so it wants its own drift test and a design-doc paragraph in
`docs/COBOLNET_INTERPROGRAM_DESIGN.md`. The nested arm also needs the created element's inner components (a dynamic table
opens at its FROM minimum; a dynamic-length item at its default). Witness once fixed: a golden with the probe above
(CALL and INVOKE) expecting `[ab|ab|rb] 3`.

## Landed (wave 1072 C, 2026-10-13): the occurrences a boundary store creates take the table's creation seed

**Re-probed** on a fresh build of 2da05a28a: `E:\COBOL-coord\scratch\w1069c\r3.cob` (`--std 2014`) printed
`CALL=[ab|  |r ] 3` / `DIRECT=[ab|ab|rb] 3`, as the reviewer measured. After the fix both lines read `[ab|ab|rb] 3`.

**The rule.** 8.5.1.9.5 (cite.py OK): with INITIALIZED, "any elementary items not referenced as receiving operands in a
statement that creates new elements in that table are first initialized as though they had been the subject of a
statement of the form INITIALIZE ... WITH FILLER ALL TO VALUE THEN TO DEFAULT"; its NOTE (cite.py OK) allows not
allocating them "provided that at runtime the implementation of the program is functionally identical to one where the
intermediate occurrences are physically allocated and, if specified, initialized". 14.2.3 GR8 (OK) makes the BY
REFERENCE formal occupy the argument's storage; 14.2.3 GR9 (OK) makes a BY CONTENT record one that does "not occupy the
same storage area as the argument", so it keeps the MOVE's space fill (14.6.9.2 2), OK).

**The fix shape: the creation travels on the ARGUMENT's carrier, and only a BY REFERENCE crossing's.** The note's analysis
held (the default exists only as the `CobolDynTable` creation seed), but the design came out simpler than its
"item-by-item merge" sketch, and more exact. `CobolVarGroup.Created` (one entry per component) holds each
dynamic-capacity table's element creation (`CobolDynTable.CreatedAs`, the seed `RefReceiving` grows with, per occurrence
number, so a Format 2 VALUE's keyed seed is honoured); the builders state it only for storage (`AsVarImage(__byReference:
true)`, `StorageCell.VarGroupAt(byReference: true)`, through `PlaceRenderer.VarGroupBoundaryImage(..., byReference: true)` from
`CallEmitter.RefCarrier`, the typed INVOKE's write-back read and copy-out, and the universal box). `Reshape` then SHOWS a
fixed table's occurrences past a storage table's capacity as created (the NOTE's "physically allocated and initialized"),
and `Overlay` keeps the highest occurrence whose image differs from that, building a created one as the created element
with the formal's stores over it (`OverlaidTable`, `GrownCount`, `OverlaidOccurrences`). No item boundaries are needed,
and the merge sketch's blind spot (a stored SPACE read back as the default) cannot occur: every item the callee did not
store already holds the default in the view it stored over. The one residue is the effect test's own: a callee that
stores into an occurrence exactly the image the table creates leaves the CAPACITY as it was (the content is the same).
D-VGB (docs/CONFORMANCE.md section 3) and docs/COBOLNET_INTERPROGRAM_DESIGN.md say so.

**Which arm.** Both builders (record struct and cell), both conversions (the view and the write-back), both element arms
(fixed-length elements and variable-length ones, whose created element carries its own inner creations), and every
boundary lane: CALL BY REFERENCE (fixed and variable-length formals), the typed INVOKE (`a.WriteBack`), the universal
INVOKE (always BY REFERENCE, 14.9.23.3 SR6) and, as the counter-arm, BY CONTENT on CALL and INVOKE (a value: spaces).

**Witnesses.** Goldens `2014/pb2690_initialized_created_occurrences_call` (GA the probe, DA the direct store, GB a read-only
callee, GC SPACES stored, GD a variable-length formal, GE BY CONTENT, GN a table of variable-length elements with an
INITIALIZED inner table) and `_invoke` (typed, universal, BY CONTENT, nested); negative
`pb2690-initialized-created-occurrences-below-2014` (COBOLNET0900); unit `BoundaryGroupCorrespondenceTests`
(`AStorageTable_ShowsAndCreatesTheOccurrencesPastItsCapacity_AsTheTableCreatesThem`,
`AStorageTableOfVariableLengthElements_CreatesEachElementFromItsCreation`,
`ATablesCreation_IsTheSeedItsReceivingReferenceGrowsWith_ByOccurrence`).
