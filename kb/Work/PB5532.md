# PB5532 - the CLI project sets no PackAsTool or PackageId although its own comment and CLAUDE.md say the WiseOwl.COBOL tool package is what it packs: it packs as `cobol`

**Sites:** `src/WiseOwl.Cobol.Cli/WiseOwl.Cobol.Cli.csproj` (whole project file: `PackAsTool`, `PackageId`, `ToolCommandName`; XML, no member check)

**Mechanism.** The comment at line 25 of `WiseOwl.Cobol.Cli.csproj` says the publish output "is what the WiseOwl.COBOL tool package packs (PackAsTool publishes, then packs that)", and CLAUDE.md names the NuGet package `WiseOwl.COBOL` with the exe `cobol`. `grep -rn "PackAsTool\|<PackageId" --include=*.csproj --include=*.props --include=*.targets` over the tree finds neither property set anywhere (kb/Work PB1613 mentions PackAsTool in prose, as the design). With no `PackageId` the SDK names the package after the assembly, `cobol`, so `dotnet pack` of the CLI does not produce the package the documents name. The report marked this "carried" with its own root.

**Owner scope.** Publishing the product (a NuGet id on nuget.org) stays the owner's; this note covers making the project agree with its documented name, not publishing.

**Fix direction.** Set `PackAsTool`, `ToolCommandName=cobol` and `PackageId=WiseOwl.COBOL` in the CLI project, with a pack self-test that reads the produced `.nupkg` id (the same test can prove PB5518's conformance statement), or correct CLAUDE.md and the comment if the package is meant to be named otherwise.
