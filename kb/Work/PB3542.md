# PB3542 — the order and the conditions of item 8's ROLLBACK

## Lead

Item 8's ROLLBACK (§14.6.13.1.3 item 8: "if there is a fatal exception condition for a file subject to an active APPLY
COMMIT clause, then a ROLLBACK statement is executed unconditionally") is emitted after the I-O hook, so a USE procedure
that ends in RESUME AT procedure-name skips it. The adjudication found the emission also wrong in two other ways (below).

Code sites: `src/Cobol.Net.Compiler/CodeGen/Verbs/SequentialIoEmitter.cs#EmitUseHook`,
`TransactionControl.RollbackOnFatal`, `src/Cobol.Net.Compiler/CodeGen/Verbs/SortEmitter.cs:615` `EmitTransferUse`.

## The standard decides (no owner question); each quote re-run through `cite.py --check`, OK

§14.6.13.1.3 says that when a fatal exception condition exists, "one of the following occurs in the order specified".

- With checking ENABLED (items 4 and 5) there is NO item-8 ROLLBACK. Item 8 opens "If checking for the exception condition
  is not enabled". Item 5: "If checking for the exception condition is enabled and there is an applicable USE statement
  in the source unit … the associated declarative is executed. If execution of the declarative completes normally the
  execution of the run unit is terminated abnormally as specified in 14.6.12". A RESUME continues per item 5 NOTE 2; a
  normal completion ends the run unit under §14.6.12, whose rollback restores files only ("If commit and rollback is in
  effect, a rollback is executed. This rollback differs from user specified rollbacks in that only files and not any of the
  data items specified or implied in APPLY COMMIT clauses are restored").
- With checking NOT enabled, item 3 sends the fatal EC-I-O condition to the rules of §9.1.13 (I-O status; §9.1.13.1 puts the
  implementor's action after the execution of any applicable exception processing statement), and item 8 then runs a full
  ROLLBACK "unconditionally". So the ROLLBACK runs after the declarative and before any RESUME transfers control. RESUME is
  legal in a file declarative (§14.9.33.3 SR1: "The RESUME statement may be specified only in a declarative or in an
  imperative statement in a WHEN phrase of an exception-checking PERFORM statement.").
- Under SORT or MERGE, item 2 ("If the executed statement is a MERGE or SORT statement, then the rules for those statements
  apply.") applies and item 8 is never reached. §14.9.36.4 GR2 makes a ROLLBACK attempted under SORT/MERGE control raise
  EC-FLOW-ROLLBACK ("If this statement is attempted to be executed under the control of a recursive runtime element or a
  file SORT or MERGE statement, then the exception condition EC-FLOW-ROLLBACK is set to exist.").

## Corrections to the earlier text of this note

- The first draft's Reading 1 wrongly said "no stated ROLLBACK" on the run-unit-termination path: §14.6.12 states one, and
  it restores files only.
- Only RESUME AT procedure-name skips the ROLLBACK: `DispatchResult.IsTransfer` is `result >= 0` and `ResumeNext` is -2, so
  RESUME AT NEXT STATEMENT falls through to `RollbackOnFatal`.
- The RESUME NOTE is item 5's NOTE 2 (not item 4's identical NOTE 1).

## Fix shape

Emit the ROLLBACK only when the condition is not enabled (`EmitUseHook` already builds that `notEnabled` test), place it
before `ResumeTransfer`, and leave it out of the SORT/MERGE transfer hooks (`verbDisposes`). The two other wrong
behaviours are filed as PB3543 (`RollbackOnFatal` never asks whether checking is enabled) and PB3544 (`EmitTransferUse`
rolls back under SORT control and bypasses `FlowForbidden`); this note covers the ordering relative to RESUME AT and the
emission site.

**Sites:**
- `src/Cobol.Net.Compiler/CodeGen/Verbs/SequentialIoEmitter.cs (EmitUseHook)`
- `src/Cobol.Net.Runtime/IO/TransactionControl.cs (RollbackOnFatal)`
- `src/Cobol.Net.Compiler/CodeGen/Verbs/SortEmitter.cs:615 (EmitTransferUse)`

## Landed (wave 1156 A)

§14.6.13.1.3 item 8's ROLLBACK is now ONE rule, written once in `SequentialIoEmitter`: `Item8Applies` (where it can apply: never on a SORT/MERGE implicit transfer, item 2; never where the statement's ON EXCEPTION phrase processes the condition, item 1 and §14.9.10.4 GR20 c); never on a success arm; an explicit statement only for a file that `FileModel.IsCommitControlled`), `EmitItem8Question` (asked AT THE RAISE, before any declarative: `CobolFile.RollbackDueOnFatal(name, checkingEnabled)`, the emitter passing the raised condition's bit in the statement's checking mask) and `EmitItem8Rollback` (run after the declarative and BEFORE a RESUME transfers control or DOC-A.1-103 ends the run unit). Every hook arm (the `__IoCheckEc` arm, the EC-model `__IoCheck` arm, the plain arm, the no-declaratives arm) and the foreign-file arm of a refused COMMIT/ROLLBACK (`EmitForeignFileIoCheck`) consume it; `TransactionEmitter` no longer writes the call. `TransactionControl.RollbackOnFatal()` executes the ROLLBACK statement's general rules (`Execute`, shared with `Rollback`), so GR1 and GR2 hold for it, and every input-output statement on a file under commit control declares EC-FLOW-ROLLBACK (`EcBinder.NodeKindRaises`). `Item8RollbackSiteDriftTests` pins the one site.

Re-probed first on the worktree's build: a USE procedure ending in RESUME AT P2 with checking off left WS-COUNT at 0002 and record 2 in the file (no ROLLBACK). Fixed: 0001, '00', record 2 absent (`conformance:cases/14.6.13.1.3-Fatal-exception-conditions/pb3542_item8_before_resume_at_procedure`). Two sibling arms found on the way and fixed in the same rule: a declarative that CLOSEs the file replaced the fatal status before the old post-hook question was asked, so nothing was rolled back (`pb3542_item8_asked_at_the_raise`); and a DELETE FILE whose ON EXCEPTION phrase processed '41' still rolled back, which item 1 forbids (`pb3542_item8_not_after_an_on_exception_phrase`). The foreign-file arm exposed that `TransactionControl.HasStatusItem` STORED the refusal's status as it answered, which would put '30' back over the FILE STATUS item item 8 had just restored; it is now a question over what the refusal recorded.

For the next implementer (code sites):
- `src/Cobol.Net.Compiler/CodeGen/Verbs/SequentialIoEmitter.cs#Item8Applies` (with `EmitItem8Question`, `EmitItem8Rollback`): the one item 8 rule; a new hook arm calls the question BEFORE its dispatch call and the ROLLBACK AFTER it, before `dispatch.ResumeTransfer`. `CheckingEnabled` is the `__en` test the generated `__IoCheckEc` computes.
- `src/Cobol.Net.Runtime/IO/TransactionControl.cs#Execute`: the ROLLBACK statement's GR1/GR2/GR3 body, shared by `Rollback` (tells a refusal) and `RollbackOnFatal` (does not). Trap: `HasStatusItem` must stay side-effect free; it is asked after item 8 has restored the FILE STATUS items.
- `src/Cobol.Net.Compiler/Binding/Model/FileModel.cs#IsCommitControlled`: the keyed-file-of-a-clause fact; never re-spell `SubjectToApplyCommit && !IsSequential`.
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.RaiseDeclarations.cs#NodeKindRaises`: EC-FLOW-ROLLBACK on every I-O statement over a commit-controlled file; without it the runtime's checking flag is off at the READ and GR2 raises nothing.
