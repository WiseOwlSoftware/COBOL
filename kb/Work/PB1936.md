# PB1936 — VERDICT 2026-10-03 (the VALUE reading; the refusal is wrong, fix is PB1946)

**Verdict.** Rule 2 d) asks the MOVE question of the argument's value, so an arithmetic expression is a numeric sender
and the pair is judged by Table 16 exactly as a numeric literal is. The refusal PB1113 landed is too strict.

**Why (every citation run through `cite.py --check`).**
1. §14.8.2.3.3 rule 2 a) applies COMPUTE rules "with the argument as the sending operand" (OK 2) a)), and a COMPUTE's
   sender is an arithmetic expression. The clause therefore uses "sending operand" for the ARGUMENT, including an
   expression, not in MOVE's own syntactic sense; rule 2 d) uses the identical phrase (OK 2) d)).
2. §14.9.4.3 SR17: "Identifier-4 and any identifier specified in arithmetic-expression-1 or boolean-expression-1 is a
   sending operand" (OK 17), and the CALL syntax admits the expression BY CONTENT, so the standard intends the pair to be
   expressible; a formal category with no admitted expression would make that syntax unusable for every non-numeric formal.
3. No clause found restricts the formal's category for an expression argument (CALL SRs read in full for
   "arithmetic-expression").
4. Consistency: a numeric literal into the same formal is admitted through the MOVE rules (PB1113's own landed arm), and the
   expression has the same category (numeric).

**Not used:** GnuCOBOL, because the spec decides this (rule 1); it was not consulted.

**Correction.** An earlier statement in this session that "refusing is the literal reading and is correct" was wrong: it
read MOVE's format (identifier-1 or literal-1) into a rule that says "the argument as the sending operand". The wave 1007
group B brief repeated it; no code depended on it.

The defect is `kb/Work/PB1946`; this adjudication is closed.

## Question

§14.8.2.3.3 rule 2 a): "If the formal parameter is numeric, the conformance rules are the same as for a COMPUTE
statement with the argument as the sending operand" (`cite.py --check` → `OK §14.8.2.3.3 2) a)`), and rule 2 d)
says that otherwise "the conformance rules are the same as for a MOVE statement with the argument as the sending
operand" (→ `OK §14.8.2.3.3 2) d)`). An arithmetic expression is not a MOVE sending operand (§14.9.25.2: identifier-1 or literal-1), so
PB1113 refuses `CALL ... USING BY CONTENT A + 1` into a `PIC ZZ9.99` (or `PIC X(4)`, `PIC N(4)`) formal. The
other reading treats the expression's VALUE as the sender: a numeric noninteger value into a numeric-edited
receiver is Table 16 "Yes", so the call would be legal and the value edited.

**Verdict needed.** Which reading §14.8.2.3.3 rule 2 d) requires (spec first; GnuCOBOL's behavior only if the
spec leaves latitude, CLAUDE.md rule 1). If the value reading wins: admit the pair, store through the receiving
category's MOVE store (the numeric-literal arm already does: `MoveEmitter.ConvertSource`), add a golden and keep
the alphanumeric/national noninteger rows refused by Table 16.

**Site.** `src/Cobol.Net.Compiler/Oo/OoConformance.cs#ContentValueMismatch`, the `sender.IsExpression` arm (both the
CALL lane through `ParameterConformance.ContentConformanceReason` and the INVOKE lane through `OoBinder` ask it).
`ContentValue.Arithmetic` already carries the noninteger Table 16 row.
