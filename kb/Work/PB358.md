# PB358 — a declared non-support with no witness

**Rows:** `SR-14.9.41.3-7`, `GR-14.9.41.4-15`, `GR-14.9.41.4-16`, `SR-14.9.30.3-11`, `SR-14.9.30.3-12`.
(`GR-14.9.41.4-13` and `-17` are held at PARTIAL by other causes and are owned by **PB357** and **PB355**.)

## Landed — 2026-09-09

**Both arms re-probed on a freshly built `cobol.exe` before anything was written**, and both reproduced. The note
had probed only the prime key; the ALTERNATE arm was *worse*, drawing **two** generic errors — one at `SOURCE`
and a second at the `WITH` of a `DUPLICATES` phrase the parser had already lost its place before reaching:

```
prime.cob(9,43): error COBOL0312: unexpected 'SOURCE'. Unexpected token in FILE-CONTROL paragraph.
                 Check SELECT/ASSIGN TO syntax. A period may be missing at the end of the previous sentence.
alt.cob(11,20):  error COBOL0312: unexpected 'SOURCE'. …
alt.cob(11,40):  error COBOL0312: unexpected 'WITH'. …
```

**The general formats were RENDERED, not read off the OCR** (`scripts/render-spec-page.py 350 359`): printed page
359 / folio 329 for §12.4.5.12.2 and page 350 / folio 320 for §12.4.5.6.2. The transcription is faithful —
`RECORD`, `ALTERNATE` and `SOURCE` carry underline rules; `KEY` and **both** occurrences of `IS` do not; the
ellipsis sits on the inner `{ data-name-2 }` brace pair.

**The disposition is a NAMED REFUSAL, `COBOLNET1954`, at every edition on BOTH clauses.**

- **One shared grammar rule** — `CobolIO.g4#recordKeySourcePhrase` (`recordKeyName SOURCE IS? dataReference+`),
  used by `recordKeyClause` *and* `alternateKeyClause` — so the binder can SEE the arm and refuse it by name.
  Exactly the shape `WRITE … FILE file-name-1` already has for Annex A.4.13 item 2.
- **One diagnostic for both clauses**, because A.3 item 40 names them in ONE sentence and the two general formats
  print the SAME brace group. A second code would put one rule in two places and invite the two-arm defect the
  original finding already committed (it named only the prime key).
- **`EditionSeverity.Error`, `Annex: DeclinedAnnex.A3`**, refused through the one `EditionContext.Declined` seam.

## ⛔ The doctrine correction this landing forced

The declined-element band asserted, in `DiagnosticCatalog`'s header **and** in `EditionContext.Declined`'s
summary, that *"an Annex A.3 processor-dependent facility is accepted-and-warned under §4.2.6, while an Annex A.4
optional module that is Not claimed is refused."* That was a **coincidence in the rows that existed** written down
as if it were the rule — every refusal happened to be A.4. COBOLNET1954 refutes it: an **A.3** element that must be
REFUSED, because §12.4.5.12.4 GR2 / §12.4.5.6.4 GR2 make the form *"a record key consisting of the concatenation
of all occurrences of data-name-2 in the order specified"* and record-key-name-1 (§8.3.2.2.24, scoped by
§8.4.6.2.4) names no data item — an inert compile would leave the file with **no prime key**, a wrong answer
rather than an absent facility. §4.2.6 ¶3's closing sentence is the licence, and it is the sentence the earlier
analysis never reached: *"The implementor is not required to produce executable code when unsupported
processor-dependent language elements are used."* (`cite.py --check 4.2.6` → OK.)

**The band splits on whether an inert reading exists, not on which annex lists the element.** Both comments now
say so, and name COBOLNET1954 as the row that proves it. The annex still decides the POSTURE CLAUSE the message
cites (`DiagnosticDescriptor.Annex` → `PostureClause`); it does not decide the severity.

## ⛔ A measured cascade, fixed at the rule rather than at the site

The first build of the surface emitted COBOLNET1954 **and** §12.4.5.1 Format 1's *"indexed file 'IXF' has no
RECORD KEY clause"* — a **false** sentence (the program plainly wrote the clause) pointing at a different repair.
`FileControlKeyRules`' requiredness row inferred absence from a null data-name, which was safe only while every
RECORD KEY clause that parsed also bound one. That rule's subject is the clause's **PRESENCE**, so it now reads
`FileKeyOperand.Written`, fed by `FileModel.RecordKeyClauseWritten`. Any future declined clause form is covered
without touching the row. `FileControlKeyRuleSpecTests` asserts the *absence* of the second diagnostic — a
"there is at least one error" check passes either way.

`conformance:85/pb358_start_no_key_phrase` closes the test-needed half of `GR-14.9.41.4-15`, which had none: the

KEY phrase passes an equality probe unchanged, so L2 puts the prime key strictly BETWEEN two records, where the

walk would answer differently. The run matched the spec-derived `.out` line for line on its first execution.

## The rules that name the operand

§12.4.5.12.2's general format is `RECORD KEY IS { data-name-1 | record-key-name-1 SOURCE IS { data-name-2 } … }`
(`cite.py --check 12.4.5.12.2 "record-key-name-1 <u>SOURCE</u> IS"` → **OK**), with the identical alternative in
§12.4.5.6.2 for ALTERNATE RECORD KEY (**OK**).

> §14.9.41.3 SR7: Record-key-name-1 shall be specified with the SOURCE phrase in the RECORD KEY clause or in the
> ALTERNATE RECORD KEY clause in the file control entry for file-name-1

`--check 14.9.41.3` → **OK**. Four of START's general rules name record-key-name-1 as a first-class operand
alternative: GR13 (its class decides whether the count is alphanumeric or national character positions), GR15
(the prime key may be spelled as one), GR16 (it becomes the key of reference) and GR17 b) (its length sizes the
temporary area).

## The disposition, and why it is conforming

`docs/CONFORMANCE.md` §A.3 item 40 declares the `record-key-name SOURCE IS` key form **Not claimed**, and Annex
A.3 item 40 makes the capability processor-dependent, with §4.2.6 requiring the absence to be specified in user
documentation. **So refusing the source is CONFORMING and this was not a new owner decision** —
[[PB293]] recorded on 2026-09-05 that the posture is settled and the owner question withdrawn under the
owner-decision protocol. **What was defective is that the refusal was unwitnessed**, and that is what landed.

## How the five rows were adjudicated

The discriminator is the owner's own, set on `SR-12.4.5.9.3-1` ([[PB371]], 2026-09-02): **the verdict follows the
RULE'S OWN SUBJECT.**

- `SR-14.9.41.3-7` → **DOCUMENTED-NON-SUPPORT**. Its subject IS the declined element: it says nothing about START
  except where record-key-name-1 must be declared. PB697's adjudication put §4.2.6 ¶3's obligation on this row,
  and this landing discharges it.
- `GR-14.9.41.4-15`, `GR-14.9.41.4-16`, `SR-14.9.30.3-11`, `SR-14.9.30.3-12` → **CONFORMS**. Each rule's subject
  is a CLAIMED facility (START's omitted-KEY behaviour, the key of reference, READ's KEY-phrase operand and its
  qualification); record-key-name-1 appears only as one of two operand spellings, and that spelling is now
  refused BY NAME and witnessed. PARTIAL would say the implementation is incomplete, which after this landing it
  is not — the operand class is unwritable **by decision**, and the decision is diagnosed.

GAP 2643 → **2638**.

## What providing the feature would cost — recorded, NOT proposed

[[PB293]] itemizes it and this landing re-measured it against today's tree: a record key would become a **LIST of
byte windows** end-to-end — `FileModel`'s key model, `KeyedIoEmitter.EmitRegistration`,
`RuntimeApi.FileRegisterIndexed`/`FileAddAlternateKey`, `IndexedConnector`'s single `(Off, Len)` slice and
`KeyOf`, `RecordLayout.KeyIndexOfKeyItem` (which matches by STORAGE POSITION and cannot express a concatenation),
plus `FixedFileAttributes.KeyDescriptor` and therefore **the framed store's on-disk header** — a second
owner-visible break of `docs/COBOLNET_FILES_DESIGN.md` D10's format, three days after the first — plus the
§12.4.5.7 Format-2 per-key COLLATING SEQUENCE seam. The standard makes the element optional; this implementation
declines it and now says so.
