# PB3311 — the planner re-plans a FINDINGS finisher that is already running

Filed 2026-10-16 by the wave 1105 unit (loop, account 2).

## Harm

Two agents answer the same review finding on the same branch. The second one merges the branch's tip, re-does the
first one's fix, and leaves two competing branches for one note. That costs a finisher's tokens and a reviewer's, and
then someone has to decide which branch to keep (an O10 DECISION row). Nothing reports it: the plan table reads as a
normal FINISH-FIRST group.

## What happened (wave 1105, 2026-10-16 17:12 PDT)

`plan_wave.py --from-budget --borrow-days 0` planned group A, `FINISH-FIRST` for PB3198: "the branch review of w1101a
(PB3198) found 1 finding(s) at head ff8f1c01b". At that moment an account-1 session (2d531566) was answering that
same finding in the branch's own worktree `E:\COBOL\.claude\worktrees\wf_7bb8ec7e-39f-11`:

- the branch tip had moved past the reviewed head: `2e75f63e9` (17:02, "WIP checkpoint: PB3198 review R3-1 ...") and
  `44212fd75` (17:03, origin/main merged in);
- a `build-local.ps1` gate was running in that worktree (bash pid 535365, started 17:04:33);
- the dispatch ledger held `w1101 AR1` (PB3198).

The unit dropped group A from the Workflow args (the plan's other seven groups launched) and released `1105a`.

## Mechanism

Two independent holes, both in `scripts/orchestrator/plan_wave.py`:

1. **A finisher group's own branch is exempt from the RUNNING test.** `plan()` makes a group whose files meet RUNNING
   work wait, but "the group's own work never collides: a branch its pred already continues (`Group.continues`)". The
   FINISH-FIRST pred continues exactly the branch that is being worked, so the live work is classed as the group's own
   and the group is planned. (PB3198's note names no `src/` file, so its file set was empty as well and no other
   collision could catch it.) The `findings()` arm asks only `cls not in LANDED_CLASSES and r.finished and
   r.review.verdict == "FINDINGS"`; it never asks whether the branch is IN FLIGHT (prune_worktrees' state: a locked
   worktree, a dispatch still in flight, or a touch inside `--min-age`) or whether its tip is still the reviewed head.
2. **A reviewer's stamp answers the dispatch.** `held_by_dispatch()` releases a ledger group's hold when "a report
   written at or after the group's `at` names one of the group's notes", by the report file's mtime. The branch
   reviewer writes its `Review:` stamp INTO the report, so every review (r3 here: the report was rewritten at 16:45) bumps the mtime past the
   finisher dispatch's `at` (AR1, 15:54) whether or not that dispatch has returned. The hold test reads a file time
   that a second writer moves.

## Fix shape

- The FINDINGS arm waits, with the reason named in the plan's `waiting` list, when the report's branch is IN FLIGHT by
  its OWN lifecycle in the branch survey (`prune_worktrees.owned`: a live agent's lock, a dispatch still out, or a
  touch inside `--min-age`, which is how a resumed branch whose tip moved past the reviewed head reads; never IN FLIGHT
  only because `contained()` found a carrier that merged it). Then "someone is already finishing it" becomes a planner
  state, not a judgment the wave unit has to make by reading `ps`.
- ONE predicate says "a dispatch returned" (`plan_wave.answers`): the report is the group's OWN (its slug,
  `w<wave><letter>`) and was written at or after the group's `at`. `held_by_dispatch` and `inflight_file_sets` both
  call it. This is the replacement kb/Work PB3152 prescribes for the answered test (its section "a second predicate for
  a dispatch returned"): a report's dispatch is its slug, which names the ledger group, which holds the notes it was
  dispatched with. One fix, not two: PB3311 does not key the answered rule on a header sentence, and PB3152's
  remaining parts (`newest` and `attempts` read `Report.ids`) stay PB3152's.
- Self-tests in `scripts/orchestrator/test_plan_wave.py` cover both holes.

## Sweep

Swept 2026-10-16 (wave 1106): `prune_worktrees.py` reads a report's mtime only as its age (`age_minutes`, the 24-hour
"never landed" staleness of a DECISION row; a reviewer's stamp resetting it is a real touch, not a verdict);
`land_lane.py` and `next_unit.py` read neither a report's mtime nor `Group.continues`. `Group.continues` has one reader
(plan's collision exemption), and the FINDINGS arm now asks the survey directly.

Siblings: kb/Work PB3152 (open) shares the answered predicate (fixed here) and owns the `Report.ids`
mention-as-ownership readers (`newest`, `attempts`). kb/Work PB2974 (open) is the same family through another arm: a
SPLIT report's branch is held only for the notes its finisher's ledger group names. The survey's state alone cannot
cure that arm (a just-returned SPLIT branch is IN FLIGHT for `--min-age`), see Landed.

## Landed (wave 1106 B, the review finisher of w1105z)

Re-probe on this build: `plan_wave.py --budget-points 3 --dry-run` printed, for PB3174 (a FINDINGS report whose branch
`worktree-wf_01e2943e-c55-6` the survey reads IN FLIGHT), `waiting: PB3174: its review findings are being answered:
branch ... is IN FLIGHT ...` and planned no finisher.

- Hole 1: `plan()` takes `owned` (`prune_worktrees.owned` over the survey rows, see the w1106b review below) and a
  FINDINGS report whose branch is owned goes to `waiting`, in the fix lane and under `--drain`, for an open note and
  an unseen lead alike. The SPLIT and unlanded arms are untouched: a just-returned SPLIT branch reads IN FLIGHT for
  `--min-age` after its last touch, so the same rule there would stall every SPLIT finisher for three hours; PB2974
  owns that arm (it needs the lock and the ledger, not the clock).
- Hole 2: `answers()` replaces both the mtime-and-mention test of `held_by_dispatch` and the bare slug test of
  `inflight_file_sets`. A reviewer's stamp on a different dispatch's report, a header that mentions the note and an
  earlier dispatch's report of a reused slug answer nothing. Residual: an earlier report of a reused slug restamped
  after the new dispatch still answers it (the cure is one wave number per planner, PB3152's witness).
- Review finding R1-1 (this note duplicated PB3152's prescription for the answered test): resolved by implementing
  the predicate once, in PB3152's shape, and saying so in both notes.
- Branch review of w1106b, R1-1 (answered by wave 1109 B): the first hole-1 fix read the survey's bare state, and
  `prune_worktrees.contained()` also writes IN FLIGHT on a FINDINGS-stamped DECISION branch that a carrier merely
  contains (an O2 same-file successor of ANOTHER note, WAITING TO LAND, ENQUEUED or STOPPED). That reversed PB3150's
  R1-2 rule (a carried FINDINGS branch still gets its finisher, its pred naming the carrier), and once the carrier
  landed no arm would ever plan the finisher: the finding would reach main unanswered. Fixed at the survey:
  `Row.carrier` records what `contained()` found, `prune_worktrees.owned(rows)` is the one "live owner of its own" set
  (IN FLIGHT and no carrier), and `plan()` takes it as `owned` instead of `states`. Witnesses: `test_plan_wave.py`
  runs `contained()` and `owned()` on the reviewer's scenario into `plan()` (carried PB79 gets its finisher naming
  the carrier; the carrier's own note waits only while the carrier is owned); the prune_worktrees self-test checks
  each carrier and the exact owned set on a real repository. Both go red when `owned()` reads the bare state.
