# PB4088 — a changed constructs.json row, or the binder its probe reaches, does not pull the row's own cells into leg 1

**Site:** the build-local impact-map planner, `scripts/run_gate_legs.py` (`plan`) with `scripts/spec/impacted_tests.py`, whose reach
rule for a changed file under `tests/version-matrix/` is `reach.direct_names.add("VersionMatrix")`.

**What happened.** PR #795 (PB2024, branch `worktree-wf_66e93b32-365-8`) changed the `async-messaging-2023` row of
`tests/version-matrix/constructs.json` and the 2023 binder screen that row exercises. Yet
`VersionMatrixTests_P7.Construct_MatchesEditionExpectation(async-messaging-2023, 2023)`, and the 85 and 2014 expectation cells of
the same row, sat in leg 2 of run 000002 (the reviewed head) and of run 000001 (this head). Under batched gating leg 1 is the only
local run (PB2515), so the cells that exercise the change first ran in CI's merge group: the CI invariant's gap.

**Expected.** A changed constructs.json row, or a changed binder a row's probe reaches, pulls EVERY cell of that row (all
editions) into leg 1.

**Not the same as** PB3144 (a changed emitted-C# snapshot file), PB3963 (three NIST programs) or PB2696 (goldens for two changed
runtime files): each is a different data file or reach. This one is the version-matrix row.

**Direction (not a fix).** Let the planner read which rows of constructs.json a diff touches and select that row's cells, with a
drift test that every row's cells are reachable from a change to the row.
