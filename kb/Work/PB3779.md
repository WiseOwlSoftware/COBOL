# PB3779 — the memory index rides every agent turn; keep the anchors, move the dated lines out

**Sites:** `C:\Users\brent\.claude\projects\E--COBOL\memory\MEMORY.md` (the index; outside the repository), `C:\Users\brent\.claude\projects\E--COBOL\memory\project_history_index.md` (the file the dated lines move to), `scripts/session-probe.ps1` (prints the index size), `scripts/orchestrator/account.py` (`MEMORY_INDEX_CAP_CHARS`, `MemoryIndex`, `memory_index`, `_memory_index_cases`, `main`), `.claude/skills/session-start/SKILL.md` (the `memory index` bullet), `docs/rearchitecture/DESIGN-orchestrator-loop.md` (section 2.1), `docs/DOC_INDEX.md` (the orchestrator row)

## Measured

An implementer's first request carries MEMORY.md at 20,544 chars (today 19,471 chars, 69 lines), about 4.9K tokens of
the 55K-token baseline, in every one of the 11.8K agent turns a day and the 2.5K main-thread turns. The index's
"Project" section is 12 lines of dated 10-24/10-25 decisions and resume pointers, and the feedback sections repeat
dated entries (10-17, 10-22, 10-23, 10-24) whose one-line summaries are the memory files' own first lines; the four
anchors and the reference lines are the standing part. A subagent reads none of it (0 of 105 agents opened a memory
file; the agent's whole task is its dispatch file).

Saving: trimming to the anchors, the standing ways of working and one `history-index` pointer (about 6K chars) is
about 3.4K tokens a turn: **about $75 a week** (agents $63, main threads $14).

## Fix

The index holds one line per standing topic and the four anchors; every dated decision, resume note and lane handoff
is ONE line in `project_history_index.md` (which already indexes the superseded resume notes) and reached from the
index by its one pointer. The cap: the index stays under about 6K chars; `session-probe.ps1` prints `memory index:
<chars>` beside the other mechanical facts and flags it over the cap, so the drift is seen at every session start
rather than measured once. The memory files themselves are untouched; nothing the owner wrote is lost, it moves one
hop away.

## Acceptance

MEMORY.md under 6K chars with the four anchors and the standing lines intact; `project_history_index.md` carries every
line removed; the probe prints the size; a dispatched agent's `api-request-shape` shows the memory block at the new
size.

## Landed

2026-10-26 (wave 20261709, group B). MEMORY.md went from 17,394 chars and 72 lines (19.5K on 10-25; the operator kept
adding) to 5,053 chars and 20 lines: the four anchors, the two START HERE lines `scripts/start-session.ps1` reads, one
`history-index` pointer and 55 standing-rule links on seven lines. `project_history_index.md` now carries the old index
line for line, so every one of its 210 topic links is still reachable from one of the two files; it says so in its
description, and the memory files themselves are untouched. The pre-change copies of both files are in
`E:\COBOL-coord\scratch\op\w-pb3776\w20261709b\` (`MEMORY.md.before`, `project_history_index.md.before`).

The cap is now seen, not measured once: `account.py --memory-index` (`MEMORY_INDEX_CAP_CHARS` = 6000; the path comes
from the account's config dir and the MAIN checkout's repo key, where a linked worktree's sessions keep their memory)
prints `memory index: <chars> chars, <lines> lines (cap 6000)` and exits 1 over it. `session-probe.ps1` prints that
line beside the mailbox line, with a warning prefix when over, and the session-start skill names the remedy. The
account self-test pins the cap boundary, the worktree-to-main-checkout key, an absent file and a non-UTF-8 file. The
header of MEMORY.md states the rule for whoever writes the next entry: a dated decision goes to the history index, and
a superseded START HERE line moves there.

The acceptance's last item, a dispatched agent's `api-request-shape` showing the memory block at the new size, can be
read only from the first agent dispatched after this landing; it is not measured here.
