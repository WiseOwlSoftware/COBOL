# PB853 — LANDED 2026-09-22 — a rule with no screen, and an invented operand that now crashes

Source: the `PB506` implementer report, item (C). ⚠ Its observation has MOVED: PB506's landing routed the
fabricated figurative `SPACE` through the VALUE recipe instead of `ConvertSource`, and the re-measurement below
shows the consequence.

## The rule, quoted

```
$ python scripts/spec/cite.py --check 13.15.3 "Every elementary entry with a COLUMN clause shall also contain either a SOURCE, VALUE or SUM clause."
  OK  §13.15.3 10)  (Syntax rules)
```

## Code site and the shape of the fix

`src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs`, the `else` of the source selection —
`: [new FieldValueSource("SPACE")];   // no VALUE/SOURCE/SUM => spaces (ISO §13.15 - empty item)`. That fallback
is the compiler INVENTING an operand for a shape SR10 forbids. The fix is to DIAGNOSE the entry (COBOLNET2014 is
allocated to this rule and unused) and DELETE the fabrication; the crash then becomes unreachable for the right
reason rather than being caught.

## Sibling sweep the fixer owes

* Every other fabricated operand in `DataBinder.Reports.cs` (grep `FieldValueSource("` for constructed
  literals) — each is the same shape: a compiler-invented sender standing in for a rule it did not enforce.
* §13.15.3's neighbouring syntax rules (SR8, SR9, SR11) — whichever have no site are the same pass's work.
* The `figurative 'S' in a numeric context` staging in the numeric renderer is reachable from this fallback
  ONLY; if another caller can reach it, that is a second note.


## The CONVERSE arm, measured 2026-09-13 by REGISTRAR #5 — and it settles the PB504 lead by derivation

The `PB504` implementer report raised, at LOW confidence and asking for adjudication, that a report-group
printable item with a COLUMN clause and NO PICTURE is REJECTED, and that the `FieldValueSource("SPACE")`
fallback this note is about is therefore DEAD for that shape. Both halves re-measured here; the adjudication is
answered from §13.15.3 SR10 itself — the rule this note already owns.

### Measured

`scratchpad/reg5/p6_rpt.cob` (PROGRAM-ID `REG5P6`), `--std 2023`, an RD whose detail group is

```cobol
01 DET TYPE DE LINE PLUS 1.
    03 COLUMN 1.
    03 COLUMN 6 PIC X(3) VALUE "END".
```

```
p6_rpt.cob(17,12): error COBOLNET0899: RD 'R-ONE': printable item at COLUMN 1 has no PICTURE clause
                   (ISO 13.16 - an elementary printable item requires one)
```

### The derivation — `03 COLUMN 1.` is NOT legal source, so this is not a rejects-legal-source defect

```
$ python scripts/spec/cite.py --check 13.15.3 "Every elementary entry with a COLUMN clause shall also contain either a SOURCE, VALUE or SUM clause."
  OK  §13.15.3 10)  (Syntax rules)
```

An entry with a COLUMN clause and no PICTURE also has no SOURCE, VALUE or SUM, so SR10 forbids it. The REFUSAL
is right; what is wrong is that it is issued under **§13.16** (a PICTURE-presence rule) rather than under the
rule that actually decides it, and that it is a `COBOLNET0899` *recognized-but-not-implemented* staging rather
than a syntax-rule error. So the compiler enforces SR10 by accident, on the PICTURE-less half only, under the
wrong citation — while the PICTURE-bearing half (this note's `03 COLUMN 1 PIC 999.`) sails through.

**That makes the two halves ONE screen, not two.** The fix this note already calls for — diagnose the entry
under SR10 with COBOLNET2014 and delete the fabrication — must key on the ABSENCE OF SOURCE/VALUE/SUM, not on
the absence of a PICTURE, at which point:

* `03 COLUMN 1.` is refused under SR10 instead of under §13.16, and
* `03 COLUMN 1 PIC 999.` is refused at all, which it is not today, and
* the `pic is null` arm in `DataBinder.Reports.cs` stops being the thing that decides an SR10 question.

### The fallback is dead for that shape, confirmed

`DataBinder.Reports.cs` evaluates the `pic is null` refusal BEFORE the source selection, so
`new FieldValueSource("SPACE")` is unreachable for a PICTURE-less entry and reachable ONLY for the
PICTURE-bearing one. Deleting the fabrication therefore removes dead code and a wrong answer in one edit —
but a fixer who deletes it without adding the SR10 screen turns today's silent fabrication into a NullReference,
so the two must land together.

### One more consequence for the row

`SR-13.15.3-10` cannot be closed on a witness that only exercises the PICTURE-less shape: that shape is refused
by a different rule's site and would certify a screen that does not exist. The row needs BOTH goldens — a
PICTURE-less entry and a PICTURE-bearing entry, each expecting the SR10 diagnostic.
