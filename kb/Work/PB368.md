# PB368 — the right consequence without the condition

**Rows:** `GR-14.9.49.4-2`.

## The program

`<lane3 scratch>/out-b1/probe/gr2-flow-use/p1.cob` — `>>TURN EC-FLOW-USE CHECKING ON`; `SELECT F1` on an absent
file;
`DECLARATIVES D1 SECTION. USE AFTER STANDARD ERROR PROCEDURE ON F1. / D1-P. DISPLAY "D1-ENTER". OPEN INPUT F1.
DISPLAY "D1-EXIT FS=" FS1.` and `DFU SECTION. USE AFTER EC EC-FLOW-USE. / DFU-P. DISPLAY "FLOW-USE-HANDLER".
RESUME AT NEXT STATEMENT. END DECLARATIVES`; MAIN does `OPEN INPUT F1` then `DISPLAY "AFTER"`.

Observed: `D1-ENTER` / `D1-EXIT FS=35` / `AFTER` — **the condition does not exist at all.**

## The rule

> §14.9.49.4 GR2: [if the execution of a USE procedure would be caused while that procedure had previously been
> activated and had not yet returned control] the EC-FLOW-USE exception condition is set to exist

`--check 14.9.49.4 "the EC-FLOW-USE exception condition is set to exist"` → **OK**. The inner OPEN fails on the
same file, so EC-FLOW-USE is set; checking is enabled and a level-3 Format-3 declarative names it, so the GR3 e)
tier selects DFU: `D1-ENTER` / `FLOW-USE-HANDLER` / `D1-EXIT FS=35` / `AFTER`. With no such declarative
EC-FLOW-USE is Fatal (Table 13) and the run unit terminates abnormally.

## What the compiler does

`DispatchEmitter.EmitRunUseBody` (line 284) emits `if (__useActive[__id]) return -1;` and returns quietly. A
tree-wide grep for EC-FLOW-USE finds it ONLY as a catalog row (`ExceptionCatalog.cs`, `L3("EC-FLOW-USE",
EcFatality.Fatal)`) and in the frozen legacy comment `src/CobolSharp.Runtime/FileRuntime.cs:26`.

**The guard is the right consequence, but the rule's sole normative content is the RAISE** — and without it a
program cannot detect its own declarative recursion, and the Table 13 fatal default never fires.

## The fix shape

The fix belongs at the ONE place that knows the guard fired: `EmitRunUseBody`'s early return. That is also the
seam the `>>PROPAGATE` / EC-FLOW-GLOBAL-EXIT / EC-FLOW-GOBACK residue needs — §14.6.13.1.3 item 6 must EXCLUDE
those names from propagation, which is impossible while none of the three conditions exists.

**PB349** owns the drift test this belongs under: every turnable name in `ExceptionCatalog` has a raise site.
This is the third of five such names found inert in one batch (with **PB326**'s two).

**Code sites:** `DispatchEmitter.cs#EmitRunUseBody` (line 284), `#EmitUseMachinery` (line 218, where the guards
are allocated) · `OoEmitter.cs:589` · `ExceptionCatalog.cs`.

## LANDED 2026-09-13 — the guard IS the raise site, and every selection path inherits it

**Re-measured first, on this worktree’s own build (main `d80cb676`).** The note’s repro was rebuilt as
`<scratch>/PB368/probe/p1.cob` and reproduced EXACTLY as recorded: `D1-ENTER / D1-EXIT FS=35 / AFTER`. The
generated C# showed why — `__RunUse` opened with `if (__useActive[__id]) return -1;` and the inner `OPEN`
carried no statement guard at all, because `>>TURN EC-FLOW-USE CHECKING ON` reached no `Enabled` set: the name
was in no `EcBinder.EcWrap` query, so nothing was ever wrapped, no ambient flag existed, and no raise site
existed to read one. The condition did not exist in three places at once.

**The fix, at the one place the rule belongs.** EC-FLOW-USE is now an ordinary ambient fatal condition, the
five declarations `CheckingFlags` documents and nothing else: the `FlowUse` field, `ExceptionEngine
.FlowUseChecking`, the one-line `FlowUseError => FatalIfEnabled(FlowUseChecking, "EC-FLOW-USE", detail)` (plus
its static shim), the `("EC-FLOW-USE", "FlowUseChecking")` row in `EcEmitter.FatalAmbientGates`, and the
`EcBinder.EcWrap` ambient arm. The RAISE is in `DispatchEmitter.EmitRunUseBody` — the single body every
selection path reaches an active USE procedure through — immediately before the decline it already performed.

**Why AMBIENT and not a node-kind query.** GR2’s subject is *a statement* that raises a condition selecting an
active USE procedure, and that is every statement able to reach a declarative at all: an I-O verb under the
GR3 a)/b) tiers, an RWCS verb under GR8, a RAISE, a CALL, or any statement whose INLINE raise site (subscript,
ref-mod, pointer, size error) reaches the GR3 c)–g) tiers. The precise-node alternative is a hand-maintained
list of node kinds — the exact shape that produced PB230 — and it fails the very repro here, whose inner
`OPEN` has an EMPTY enabled set (only EC-FLOW-USE is turned on). The SYNTACTIC alternative, “a statement
lexically inside DECLARATIVES”, is wrong outright: a declarative may PERFORM a paragraph anywhere in the
procedure division, and GR2 says *during the EXECUTION of* a USE procedure. This is the EC-BOUND-REF-MOD
precedent, and its documented cost — a guard around a statement that invokes no declarative — is a no-op.

**The arm the raise must NOT reach.** The exception-checking PERFORM’s imp-2/3/4 handlers are appended pc
ranges run by the SAME `__RunUse` over the SAME `__useActive` array, and they are not USE procedures —
§14.9.28.4 GR17 selects them, not §14.9.49.4 GR3 — so the emitted guard raises only below
`DispatchState.DeclCount` (`if (__id < 2) ExceptionState.FlowUseError(…)`), and an OO method-local `__RunUse`,
which is all handlers with DeclCount 0, emits the bare guard byte-identically.
