## Analysis 2026-09-29 (batch 8, not taken)

Not a one-site fix: raw lines are indexed in many places before the fixed-form slicer (`ReferenceFormatProcessor.cs` directive detection at ~271/281/418/442-448, `LogicalConversion.cs` ~110/363), and a TAB inside an alphanumeric literal would change its value if expanded at the top. ## Task brief (research 2026-09-30)

**Premise check.** Right, and re-measured on 4a1dda60e: `<TAB><TAB>DISPLAY "TAB-OK".` in fixed form → COBOLNET2616
("column 7 holds 'L'") + COBOL0001 at `--std 85` and `2023`; a TAB inside a literal is kept as U+0009
(`DISPLAY "[A<TAB>B]"` prints a raw tab). **The tab WIDTH is no longer an open question**: DOC-A.1-157
(docs/CONFORMANCE.md) already determines "a horizontal tab (U+0009) … advances to the next tab stop — positions 1, 9,
17, 25, … (a tab width of 8, GnuCOBOL's default `tab-width`; rule 1 precedence) — so it occupies one to eight
positions", and GnuCOBOL 3.2 confirms the rule exactly (`cobc/pplex.l` `ppinput`: `buff[n++] = ' '; while (n %
cb_tab_width != 0) buff[n++] = ' ';`, `tab-width: 8` in every `config/*.conf`, configurable 1–12 — not needed here).

**⚖ OWNER DECISION — a TAB inside an alphanumeric / national literal.** ISO: §6.1 1) c) leaves "the meaning of lines
and character positions" to the implementor (`cite.py --check 6.1` OK), while §6.1 2) b) says "all characters of the
computer's coded character set shall be retained in alphanumeric and national literals" (`OK §6.1 b)`).
- **A (recommended) — expand everywhere, literals included.** GnuCOBOL's reader expands before any scanning, so its
  literal holds spaces; DOC-A.1-157's "occupies one to eight positions" already reads this way, making the TAB an
  input-medium positioning control rather than a character of the literal. `"[A<TAB>B]"` written with the `"` at
  column 25 becomes `[A` + 5 spaces + `B]` (the TAB at column 28 advances to 33). A program that wants the character
  writes `X"09"`. One stage, no literal awareness before the format is known (PB1800).
- **B — keep U+0009 as one position inside a literal.** Honors a literal reading of §6.1 2) b), but the line-entry
  stage would need literal state, which depends on the reference format and on continuation — the expansion could no
  longer happen at line entry, and the column after the literal would disagree with DOC-A.1-157.
- **C — diagnose a TAB inside a literal** (the user writes `X"09"`). Strictest; no precedent in GnuCOBOL/IBM/MF.

**Implementation** (after the decision) = PB1800's `PhysicalLines` reader, same slot as PB1803. Update DOC-A.1-157
(drop the ⚠ PB1586 edge; state the literal answer) and DOC-A.1-23 ("the horizontal tab … treated as white space" →
no TAB reaches the text-word stage). With no TAB surviving line entry, `TextWord.cs#IsSeparatorSpace`'s `'\t'`, the
lexer `WS` tab and `FloatingComment`'s `' ' or '\t'` become dead — delete them under PB1800's drift test (a).
