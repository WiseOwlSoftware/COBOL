# PB3613 — a numeric FUNCTION value sent to a group keeps its sign and decimal point

**Sites:** `src/Cobol.Net.Compiler/CodeGen/Emit/OperandText.cs` (`NonElementaryMoveSender`, the last arm: `AsString(op, num, deSign:false)` on a numeric `BoundComputedOperand`).

## Found

Source: `w20261024c-PB3570-report.md`, new defect (unchanged from the reviewed report). PB3570 decided that a numeric
literal sent to a group stores its digits only (no sign, no decimal point). The function-value sender was not brought
along.

Repro (the reporter's file): `E:\COBOL-coord\scratch\w20261024c\fn.cob`.

- `MOVE FUNCTION MIN(N 3) TO G` with N = -15 stores `-15` in the group.
- `MOVE FUNCTION MIN(M 3) TO G` with M = -1.5 stores `-1.5`.
- A numeric literal sent to the same group stores digits only (the PB3570 rule).

## The fix

Decide the function sender with the PB3570 decision (the documented latitude of 14.9.25.4), then add the arm to
`OperandText.NonElementaryMoveSender` so a numeric computed operand is sent through the same codec as the literal.
Sibling sweep: every caller of `NonElementaryMoveSender` (see PB3562, which already lists them and handled the boolean
and national function senders) with a numeric function sender, including CALL BY CONTENT to a group formal.

## Landed (2026-10-24, wave 20261032 group E) - a numeric function value sends its digits through every channel

**Re-probe (own build, Debug).** The reporter's file stored `-15` (FN1) and `-1.5` (FN2) as filed; a numeric function folded to a literal
(`FUNCTION MIN(-15 3)`) kept `-15` too (PB3570 had exempted it on purpose). Two sibling lanes were worse than the note said:
`CALL ... AS NESTED USING BY CONTENT FUNCTION MIN(N 3)` into a plain-group formal was REFUSED (COBOL1688, "an arithmetic
expression has no character image": `ActivationDescriptions.OfValue` lumped a numeric function with an arithmetic expression, but a
function-identifier is a MOVE sender, so ISO 14.8.2.2 rule 2 admits it), a Format-1 CALL crossed the value cell's 38-digit zoned image
(`000000`), and an INVOKE crossed the SendingValueTemp's own signed text (`-15`, `-1.500`).

**Determination.** Like a literal, a numeric or integer function's value states no representation (15.2 4)-5): "an operational sign", no
usage; 15.4.1 leaves "the characteristics and representation of the returned value" to the implementor under native arithmetic), so
PB3570's owner determination (digits only, GnuCOBOL's literal data) is the one for the value. GnuCOBOL itself sends the function's internal
field (`1u` for MIN of an S99, a 4-byte binary for INTEGER, `15` for ABS, measured with cobc 3.2.0), which is no rule, so the value follows
the literal. docs/CONFORMANCE.md D-B4 records it.

**Fix.** One digits rule, `CobolNum.GroupDigits` (runtime; the compiler calls it on a literal's canonical text, the emitted code on a
function value's text), replaces `OperandText.LiteralDigits`. `NonElementaryMoveSender` has the literal arm for EVERY numeric literal (the
`FunctionValue: false` exemption is gone) and an arm for a numeric computed operand (`RuntimeApi.NumGroupDigits(AsString)`), which MOVE
and the INVOKE group arm read. The CALL lane: `ActivationDescriptions.OfValue` describes a numeric function as a MOVE sender
(`ActivationShape.Literal`; the arithmetic expression keeps `Expression`), `CallEmitter` sends a numeric function into a known plain-group
formal through the one sender, and `CobolArgAdapt.WithValueSending` states the digits as the argument's `StorageImage` for a formal it
cannot see. INVOKE: `OoBinder` leaves a numeric function on the expression arm for a plain-group formal and `OoEmitter`'s group arm sends it.

**Goldens.** `14.9.25-MOVE/pb3613_numeric_function_group_move` and `..._comma` (2002 on), `14.2-Procedure-division-structure/pb3613_numeric_function_group_formal`
(CALL AS NESTED, Format-1 CALL, INVOKE) and its negative `..._below_2002`. Drift pin: `GroupMoveSenderChannelDriftTests`.

**Review round 1 (finisher).** The branch review found one blocking sibling: FUNCTION LENGTH (and BYTE-LENGTH) of a variable-length group is
lowered by `IntrinsicBinder.VariableLengthGroupSum` to a `BoundBinary`, which `ActivationDescriptions.OfValue` still described as an arithmetic
expression, so `CALL ... AS NESTED USING BY CONTENT FUNCTION LENGTH(VG)` into a plain-group formal was refused (COBOL1688) while the MOVE and
the Format-1 CALL worked. Root cause: a function value and an arithmetic expression can be the same tree, and nothing said which. Fix:
`BoundComputedOperand.FunctionValue` / `IsNumericFunctionValue`, stated once by `IntrinsicBinder.OperandOf(expr, functionValue)` (the parameter is
required, so a new position decides), read by the activation description, the CALL arm, the INVOKE binder guard and emitter (`BoundInvokeArg.ContentFunctionValue`)
and the sending codec; the plain-group test is `DataItem.IsPlainGroup` in every site (`CallEmitter.IsPlainGroupFormal` deleted). Golden:
`pb3613_numeric_function_group_formal` gained the LENGTH(VG) case on all three lanes, and `pb3613_arithmetic_expression_group_formal_refused`
pins that a real arithmetic expression stays refused (COBOL1688).
Open lead (not fixed here): a numeric function evaluated on the STANDARD-DECIMAL lane (a COMP-2 argument, `FUNCTION MIN(F 3)`, F = 0.0001) is cut to the
receiver-less 6 fraction digits by a Format-1 CALL (CallEmitter's `BoundComputedOperand` expression arm, `num.Render(expr.Expr, rcv)` with `rcv = None`), so
`CALL "W" USING BY CONTENT FUNCTION MIN(F 3)` sends `0000100` where the same call AS NESTED and `MOVE` send `000010000000000000000479`.
