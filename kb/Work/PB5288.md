# PB5288 - a SEND whose destination table names one destination in two occurrences merges segment and message control across them: Dialogue.Release keys the pending message by destination name and is called once per occurrence

**Sites:**

- `src/WiseOwl.Cobol.Runtime/Communication/MessageControlSession.cs` (`Release`, `SendToDestinations`)

**Mechanism.** §1985:XIV.3.6.4 GR10 makes ESI, EMI and EGI close the segment, message and group, the MCS maintaining "segment, message, or group control". Nothing in §1985:XIV.2.2.4 forbids two destination-table occurrences naming one destination. `Release` keys the pending message by destination name and `SendToDestinations` calls it once per occurrence, so the second occurrence's ESI closes a second segment of the same message: AA ESI then BB EMI to LOOP twice gives one message [AA, AA, BB] and a second [BB], which no reading of the rules produces.

**Inventory.** `work.py check` refuses a 1985 rule id in `inventory_rows` (kb/Work PB5094, open), so `inventory_rows` is empty and the rows this note claims are the rule ids below. None of them is recorded: the non-conforming verdicts wait in `E:/COBOL-coord/scratch/coderead-85/p2-for-register.json`.

**Rules (1 claimed; every citation checked with `scripts/spec/cite.py --check`).**

- `1985-GR-XIV.3.6.4-10` - `§1985:XIV.3.6.4 GR10` (refuter: OVERTURNED to PARTIAL, harm: wrong-answer): "the message segment is complete"

**Repro.** `E:/COBOL-coord/scratch/coderead-85/out-pipe/refute-slice-63/r4/r4.cob` with its mcs.json: OUT-CNT 2, OUT-DEST (1) and (2) both LOOP (delivered to HOLD); `SEND FROM "AA" WITH ESI`, `SEND FROM "BB" WITH EMI`, then RECEIVE SEGMENT until no data; `cobol.exe --std 85 --source-format fixed --run r4.cob`.

**Observed (a build of origin/main f2cf36fd15, rerun 2026-11-11; main has since changed only `IndexedConnector.cs` under `src/`, which none of these repros reaches).** `AFTER-ESI 00 000000`, `AFTER-EMI 00 000002`, `SEGMENT 0002 1 [AA...]`, `SEGMENT 0002 1 [AA...]`, `SEGMENT 0002 2 [BB...]`, `SEGMENT 0002 2 [BB...]`.

**Expected (from the 1985 text).** Either one message [AA, BB] (one per distinct destination) or two messages [AA, BB] (one per occurrence); never [AA, AA, BB] and [BB]. The fix chooses and documents one.

**Fix direction (root cause, CLAUDE.md rule 4).** Key the pending message per occurrence, or release once per distinct destination, and record the choice in docs/CONFORMANCE.md; test this program.
