## Repro

`E:\COBOL-coord\scratch\w1037a\p\pg.cob`: a `PIC 9(4)` holding 1234 passed BY CONTENT to a program whose details
§12.3.8.4 GR10 c) takes from the external repository, into a `PIC 9(3)` formal, arrives as `123`; §14.2.3 rule 9
("if the formal parameter is numeric, a COMPUTE statement without the ROUNDED phrase") gives `234`. The literal 12
arrives as `12 ` (expected `012`), ZERO as `0  `. A CALL by data-name to a program the activating element has a
program-specifier for behaves the same.

## Code sites

- `src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs#LandedForFormal` — needs `a.Formal`, which is null on these lanes.
- `src/Cobol.Net.Runtime/Control/CallAbi.cs#CobolArgAdapt` — the callee adapters adopt the image unconverted.

## Notes

Adjacent to PB289 (expression landing scale), not the same root: here the conversion is missing entirely because
the formal is known only at run time. The fix is a run-time landing driven by the registered formal description
(`BoundaryItem.Description`, which PB165 now carries) rather than a compile-time one.

## Landed (wave 1039 group C, 2026-10-08)

Re-probed on the w1039c build: `pg.cob` printed `N3 GOT 123` (case 7), `12 ` (11), `0  ` (12) and `123` (14). Root
cause: the activating element lands §14.2.3 GR9's second regime and GR10 only when it knows the formal at compile time
(`CallEmitter.LandedForFormal`, `BoundCallArg.Formal`), and the activated unit registered no description it could be
landed through unless it checked EC-PROGRAM-ARG-MISMATCH. `OK §14.2.3 9)` "if the formal parameter is numeric, a
COMPUTE statement without the ROUNDED phrase"; `OK §14.2.3 9)` "a program for which there is a program-specifier in the
REPOSITORY paragraph of the activating runtime element"; `OK §12.3.8.4 10) c)` "the details are taken from the external
repository".

Fix: every unit registers each NUMERIC formal's profile and CLR carrier (`BoundaryItem.Landing`, a stateless
`CarrierLanding<T>.Instance`, `T` the formal's `PicInfo.ClrType`, chosen by the one `CallEmitter.NumericLandingPic` the
compile-time landing also asks), whatever its checking state; a site with no signature that passes an argument BY
CONTENT or BY VALUE states its program-specifiers (the empty array when it writes none) and its EC-SIZE-TRUNCATION state
(`siteSizeTruncationChecking:`); and `ProgramTable.CallProgram` lands each BY VALUE argument, and each BY CONTENT one
whose program the element has a specifier for, through `BoundaryItem.Land` → `CobolArgAdapt.LandForFormal<T>` (the
compile-time lane's landing) after the conformance checks and before the transfer. After: `234`, `012`, `000`, `234`.
Sibling arms: the program-pointer CALL forwards both facts (`CallPointer`); a function activation always holds its
signature; a universal INVOKE admits no BY CONTENT or BY VALUE (§14.9.23.3 SR6, COBOLNET0866). The BY VALUE crossing to a
GR10 c) prototype now raises EC-SIZE-TRUNCATION in the activating element under checking (it landed callee-side,
unchecked: `12345` arrived as `2345`). Golden `2002/pb2549_runtime_located_call_landing`; unit
`BoundaryItemLandingTests`.

For the next implementer: `src/Cobol.Net.Runtime/Control/ProgramTable.cs#LandArguments` owns the run-time lane (after
the GR3 d) checks, before the transfer); `src/Cobol.Net.Runtime/Control/CallAbi.cs#BoundaryItem.Land` and
`#CarrierLanding` — reuse them, never a second landing; `src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs#NumericLandingPic`
is the one "formal is numeric" test for both lanes, `#LandsAtRunTime` decides when a site states `programSpecifiers:`
(the EMPTY array means "no specifiers but land BY VALUE"; null means nothing to land) and `siteSizeTruncationChecking:`;
`src/Cobol.Net.Compiler/CodeGen/ProgramEmitter.cs#EmitEntryWrapper` now registers `formals:` for every unit with a
numeric formal. Trap: Format 1 CALL admits no BY VALUE (COBOLNET0899), so a BY VALUE run-time-lane golden needs a
GR10 c) prototype.
