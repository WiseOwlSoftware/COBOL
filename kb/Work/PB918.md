# PB918 — OPEN — a recovery that invents a second error

Source: the `PB554` report, "New defects" item 1. **The report's own repro does not show the cascade** —
corrected here.

## The measurement

`<scratch>/reg7/probe/s_sameas_sr12.cob`, `--std 2023`:

```cobol
       01 Z PIC S9(5).
       01 A SAME AS Z ALIGNED.
```

```
s_sameas_sr12.cob(6,8): error COBOLNET1555: … the SAME AS clause shall not be specified in the same data
description entry with any clauses except CONSTANT RECORD, entry-name, EXTERNAL, GLOBAL, level-number, and
OCCURS (ISO §13.16.3 SR12); this entry also specifies ALIGNED
s_sameas_sr12.cob(6,8): error COBOLNET1942: … the ALIGNED clause may be specified only for a bit group item
or an elementary bit data item (ISO §13.18.1.3 SR1) — this entry is an alphanumeric group item …
s_sameas_sr12.cob(6,8): error COBOLNET0881: data item 'A': a PICTURE clause shall be specified for an
elementary item (ISO §13.16.3 SR8) …
```

Three diagnostics for one mistake, and the third is about a clause the user did not omit: they wrote
`SAME AS Z`, which IS the description. COBOLNET1942 is a second artefact of the same recovery — once the
SAME AS reference is cleared, the entry is re-classified as an alphanumeric group and ALIGNED is judged
against that invented shape.

⚠ **The report's TYPE spelling does not reproduce.** `01 A1 TYPE T PIC 9(5).`
(`<scratch>/reg7/probe/s_type_sr14.cob`) draws COBOLNET2150 **alone** — the entry's own PICTURE satisfies
SR8, so nothing cascades. The TYPE arm needs a spelling with no PICTURE:
`<scratch>/reg7/probe/s2_type_sr14_nopic.cob`, `01 A1 TYPE T JUSTIFIED RIGHT.` →

```
s2_type_sr14_nopic.cob(6,8): error COBOLNET2150: … (ISO §13.16.3 SR14); this entry also specifies JUSTIFIED
s2_type_sr14_nopic.cob(6,8): error COBOLNET0881: data item 'A1': a PICTURE clause shall be specified for an
elementary item (ISO §13.16.3 SR8) …
```

Both arms therefore reproduce, and they reproduce for the SAME reason, which is the point of one note.

## The rules

```
$ python scripts/spec/cite.py --find "The SAME AS clause shall not be specified in the same data description entry"
§13.16.3 12)  (Syntax rules)
$ python scripts/spec/cite.py --find "The TYPE clause shall not be specified in the same data description entry"
§13.16.3 14)  (Syntax rules)
```

and SR8, quoted in full because COBOLNET0881's own wording is a PARAPHRASE of its second sentence and the
first sentence is what makes the paraphrase legitimate:

> 8) The PICTURE clause shall not be specified for the subject of a RENAMES clause or for an item whose
> usage is binary-char, … **For any other entry describing an elementary item, a PICTURE clause shall be
> specified except as indicated in Syntax rule 9.**

Neither SR12 nor SR14 states a recovery. The "IsBased discipline" — report and clear — is this project's
convention, not the standard's, and the convention is what produces the cascade.

## The code sites

* `src/Cobol.Net.Compiler/Binding/DataBinder.cs` — the SR14 guard's `typeRefName = null`.
* the SR12 guard's SAME AS twin in the same file.
* `src/Cobol.Net.Compiler/Binding/DataBinder.PictureRequired.cs:101` — where the cleared entry meets SR8.

## The decision the fix has to make (and it is a DESIGN decision, not a diagnostic tweak)

Should a cleared composition reference KEEP the referenced description for layout and screening purposes,
and only refuse the ENTRY? That answer is the same for SAME AS, TYPE and any future composition clause, so
it belongs in one place — the recovery policy — and not in two guards. Suppressing COBOLNET0881 downstream
would be the workaround CLAUDE.md rule 4 forbids: the item really has no description, and the next screen
that asks will produce the next artefact (COBOLNET1942 already does).
