# PB3024 — the merge queue lands; CI's merge-group run is the one whole-population gate

**Owner decision 2026-10-11 ~11:33 PDT (kb/Work PB3015 Q1b): "GitHub merge queue (Recommended)"** — one pull request
per landing enters the queue on `main`; GitHub tests the queued pull requests together per merge group and advances
main in order; the landing lease, `push-main.sh`'s CI wait and the `ci/**` branches go. Facts: the repository is PUBLIC
(standard runners free; 20 concurrent jobs); `main` has classic protection today (`ci-gate` required, admins enforced,
no ruleset: `gh api repos/BrentRector/COBOL/rulesets` → `[]`), and a merge queue needs a ruleset.

**Design:** `DESIGN-test-build-ci.md` §3.17.2 (steps 4–5), DESIGN §3.17.6.

**FAST TRACK (owner 2026-10-11 ~12:58 PDT, asked "Why are we still using push-main? I thought we queued PRs to github
and it did the CIs merges to main?", answered "Fast track now (Recommended)"):** this note is NO LONGER blocked by
PB3023. Its GitHub half and the hand form of the enqueue step land TODAY as **phase 1**, through `push-main.sh` one last
time; the scripted `enqueue.py` (PB3023), the per-entry DEVLOG (PB3025) and the rest follow as **phase 2**.
**NEEDS-OPUS:** the cutover of the live landing path (the workflow, the ruleset, every lander brief and unit text, the
retirement of push-main and the lease) needs judgment, not a mechanical edit.

### Phase 1 — today (this note's landing)
1. `.github/workflows/build-and-test.yml`: `on: merge_group:`; the `changes` job runs the full matrix for `merge_group`
   and `workflow_dispatch`, the CHEAP jobs only for `pull_request` (audits, work-register and DEVLOG-entry checks — so a
   lander's PR does not spend 20 runners before its merge group does), and for `push` to `main` the already-verified
   short-circuit (the merge-queue commit IS the commit that reaches main, so its `ci-gate` success is already recorded;
   verify this on the first queued landing and fix the short-circuit if the sha differs); `push.branches` loses `ci/**`.
2. `scripts/orchestrator/ruleset-main.json` (the ruleset as data: require a pull request with 0 approvals; merge queue,
   method merge commit, min 1 / max 5, timeout 60 min; required status check `ci-gate` on the merge group; bypass list
   empty) and `scripts/orchestrator/ruleset.py apply|check|--self-test` (`apply` = `gh api` from the JSON and delete the
   classic protection — run ONLY by the owner's explicit go; `check` = live vs committed, the drift test's engine,
   offline → SKIPPED never GREEN).
3. The lander opens and queues a pull request instead of pushing: lander-train-brief steps 6–7 become — run
   `landing_devlog.py` and `landing_check.py` in the worktree (they leave `push-main.sh`), `gh pr create --title "<train
   subject>" --body-file <forensic message>`, `gh pr merge --auto --merge`, record the PR number in the report and in
   `train_measure.py record --pr <n>` (the merge time is read later from `gh pr view --json mergedAt` by the next land
   unit), and END — no CI wait, no lease. `units/land.md`, `lander-brief.md`, `golden-lander-brief.md`,
   `wf_rolling_wave.js`'s train prompt, MANDATORY-PRACTICES L3 (the lease) and L13 (the push refusal), `dispatch_guard.py`,
   `prune_worktrees.py` (LANDED by ancestry still works; it learns ENQUEUED from `gh pr view`, offline-safe) say the
   same. `push-main.sh`, `landing_lease.py` and their drift tests are deleted (rule 4); `session-probe.ps1`'s `gate :` line
   reads `ruleset.py check` and the queue depth.
4. The doc sweep for the words "push-main" and "landing lease": CLAUDE.md (Testing; rule 7's "push every checkpoint" is
   about branches and stays), plan §0 "Gates" and §9, the `gate`, `land-a-fix`, `workstream`, `session-start` and `kb-sync`
   skills, `docs/DOC_INDEX.md`, `CONTRIBUTING.md`, PB1957's invariant text, the `devlog` memory lines are the attended
   session's.
5. `LandingPipelineDriftTests` phase-1 arms: `merge_group` present, no `ci/**`, no reference to `push-main.sh` or
   `landing_lease.py` in the tree, the committed ruleset equals the live one (SKIPPED offline).
6. **The switch:** this landing goes through `push-main.sh` (the last one). The moment it is on main the attended session
   asks the owner, one bare question, to run `python scripts/orchestrator/ruleset.py apply` (or to approve the agent
   running it); from that instant main accepts only queued pull requests, and the loop's next land unit opens PRs.

### Phase 2 — with PB3023 and PB3025
The scripted `enqueue.py` replaces the lander's hand steps; the DEVLOG-entry check becomes `devlog.py check` in CI's
audits on `pull_request` and `merge_group`; `landing_check.py` runs in CI's audits too; the lander role retires.

## What changes (the full design; phase 1 above is its first slice)
1. **Ruleset on `main`** (created with `gh api` from a committed JSON, `scripts/orchestrator/ruleset-main.json`, so the
   setting is in the tree and a drift test can compare the live ruleset against it): require a pull request (0
   approvals; the review is the wave's reviewer step, PB3027); require the merge queue — merge method **merge commit**
   (the branch's commits stay ancestors of main, so `prune_worktrees.py`'s landed test, `carried()` and `git cherry`
   keep working offline; `git log --first-parent main` reads one merge commit per landing whose message is the PR body;
   squash rejected on the operator's review 2026-10-11 12:16), minimum group size 1, maximum 5, check-response timeout
   60 min; required status check `ci-gate` evaluated on the merge group; bypass list empty (enforced for administrators,
   as today). The classic protection is deleted in the same change.
   **Cutover (operator review item 4, reshaped by the owner's fast track ~12:58):** this note's phase 1 (above) is the
   last landing through `push-main.sh`, ahead of PB3023; applying the ruleset is an owner-attended step — the attended
   session asks the owner for an explicit go at that moment (one bare question), because from that instant main
   accepts only queued pull requests.
2. **`.github/workflows/build-and-test.yml`:** `on: merge_group:` added; `push.branches: [main]` (no `ci/**`); the
   `changes` job runs the matrix for `merge_group` and `workflow_dispatch`, and for `push` to main only when the
   merged sha has no `ci-gate` success recorded (the merge group tested that tree — the existing already-verified
   short-circuit covers it); on `pull_request` the matrix is skipped and the cheap jobs run (`audits`, the DEVLOG entry
   check PB3025, the work-register check). `ci-gate`'s `needs:` and its wired-jobs drift check are unchanged. The
   `concurrency` group cancels superseded `pull_request` runs only, as today; a `merge_group` run is never cancelled.
3. **Retired (rule 4):** `scripts/push-main.sh`, `scripts/orchestrator/landing_lease.py` and its drift tests, the
   `landing-lease.jsonl` log, MANDATORY-PRACTICES L3 and L13 (there is no push to refuse), `landing_devlog.py` as a
   push-main step (it is `devlog.py check`, PB3025, run by `enqueue.py` and by CI), `landing_check.py`'s push-main
   call site (run by `enqueue.py` and by CI's audits on the merge group). `session-probe.ps1`'s `gate :` line reads the
   ruleset and the queue depth instead of "land with push-main.sh".
4. **The CI invariant restated** (CLAUDE.md Testing, MANDATORY-PRACTICES): a PR bounced by the queue is a defect fixed on
   its branch before re-enqueue; main never carries a red because nothing reaches it except a tested merge group.
5. `LandingPipelineDriftTests` (DESIGN-test-build-ci §3.17.8): `merge_group` present, no `ci/**`, no reference to `push-main.sh` or
   `landing_lease.py` in the tree, the live ruleset equals the committed JSON (skipped without network, never green
   without the comparison).
