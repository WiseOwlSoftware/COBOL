## Found at the first apply (2026-10-11 16:27 PDT, Mythos session, on the owner's go)

GitHub refused the committed repository settings: `merge_commit_title=MERGE_MESSAGE` with
`merge_commit_message=PR_BODY` is not a pair it accepts (HTTP 422 `invalid_merge_commit_setting_combo`; the pairs are
PR_TITLE+PR_BODY, PR_TITLE+BLANK, MERGE_MESSAGE+PR_TITLE). `ruleset.py apply` stopped at that first call: no ruleset
was created, the classic protection stood, `check` stayed ABSENT and the land unit of the moment kept push-main. The
self-test could not see it: its fake gh accepts anything. Fixed in branch `ruleset-settings-PB3024` (cut from main
b7f3eedba, the train that landed phase 1): the committed pair is MERGE_MESSAGE + PR_TITLE — the title stays
MERGE_MESSAGE for `train_heads` (above) — `ruleset.py` refuses any pair outside GitHub's three before it calls GitHub
(`VALID_MERGE_COMMIT_PAIRS`, `merge_commit_pair_problem`, two new arms), and DESIGN-test-build-ci section 3.17.6 no
longer promises the forensic message on the merge commit: the record is the branch's own commits beneath the merge
and the PR body. The apply is re-run on the same go once this is on main.
