# PB3024 — the merge queue lands; CI's merge-group run is the one whole-population gate

**Owner decision 2026-10-11 ~11:33 PDT (kb/Work PB3015 Q1b): "GitHub merge queue (Recommended)"** — one pull request
per landing enters the queue on `main`; GitHub tests the queued pull requests together per merge group and advances
main in order; the landing lease, `push-main.sh`'s CI wait and the `ci/**` branches go. Facts: the repository is PUBLIC
(standard runners free; 20 concurrent jobs); `main` has classic protection today (`ci-gate` required, admins enforced,
no ruleset: `gh api repos/BrentRector/COBOL/rulesets` → `[]`), and a merge queue needs a ruleset.

**Design:** `DESIGN-test-build-ci.md` §3.17.2 (steps 4–5), DESIGN §3.17.6.

**FAST TRACK (owner 2026-10-11 ~12:58 PDT, asked "Why are we still using push-main? I thought we queued PRs to github
and it did the CIs merges to main?", answered "Fast track now (Recommended)"):** this note is NO LONGER blocked by
PB3023. Its GitHub half and the hand form of the enqueue step land TODAY as **phase 1**, through `push-main.sh` one last
time; the scripted `enqueue.py` (PB3023), the per-entry DEVLOG (PB3025) and the rest follow as **phase 2**.
**NEEDS-OPUS:** the cutover of the live landing path (the workflow, the ruleset, every lander brief and unit text, the
retirement of push-main and the lease) needs judgment, not a mechanical edit.
