# PB4707 — BindBareOperandStandalone does not judge as BindCondition does

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs:697` (`ConditionBinder.BindBareOperandStandalone`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs:718` (`ConditionBinder.BindBareOperandStandalone`, `ConditionBinder.BindSoleOperandCondition`)

Reported by the branch review, not probed. Copied from the PB4627 report (wave 20261868 g):

R1-1: `BindBareOperandStandalone` asks `ins.Active` before `ins.BooleanRelation`, in the opposite order to `BindSoleOperandCondition`, so a bare operand after a stated boolean relation is not judged as `BindCondition` judges it (the doc comment and the report claim it is): the address arm (line 697) never asks `BooleanRelation`, and the value/class-name arms (lines 710, 714) miss the boolean-expression relation, which `BindPrimaryBoolean` records with `BooleanRelation` true and no Subject.

R1-2: the walk's default arm ends the insertion for a boolean operand but never asks the section 8.8.4.3.3 SR1 length-1 screen (`AsCondition` / `BindSimpleBooleanCondition`), although the new doc comment says the walk judges the written condition as `BindCondition` does and that the analysis has already bound the operand; `AnalyzeBareOperand` binds it unwrapped and the screen lives only in the wrapper.

**Sites (landed):** `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#BindBareOperandStandalone`, `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#BareObjectRoleOf`, `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#BindSoleOperandCondition`, `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#BindComparison` (the bare address-identifier arm), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#BindAbbreviatedRelation`, `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#RefuseAbbreviationAfterBooleanRelation`, `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#BindPartialOperandsStandalone`; `docs/CONDITIONS_EXCEPTIONS_DESIGN.md` D5a.

## Landing

- Re-probe on the branch build (before the fix), both leads reproduced. R1-1: `EVALUATE TRUE WHEN > 1 AND B1 B-AND B2 = B"0" AND 5` drew COBOL1634 + COBOL2318 where the same condition in an IF draws COBOL2723; `WHEN > 1 AND B1 = B2 AND ADDRESS OF A` drew COBOL1634 alone where an IF draws COBOL2723. R1-2: `WHEN > 1 AND BW` (a PIC 1(2) item) drew COBOL1634 alone where an IF draws COBOL1511.
- Siblings of the one cause, found in the same file and fixed with it: (1) `BindComparison`'s bare address-identifier arm decided on "is a subject carried?" alone, so in an IF `B1 B-AND B2 = B"0" AND ADDRESS OF A` drew COBOL2318 ("used as a condition") instead of COBOL2723; (2) a refused abbreviation (after a boolean relation, or with no subject to insert) returned before it bound its object, so `IF B1 = B2 OR UNDEFX` and `IF N = 1 AND (N = 1) AND < UNDEFX` hid COBOL1639 behind COBOL2723 / COBOL2552 (the IF counterpart of PB4446).
- Fix shape: `BareObjectRoleOf` is the ONE decision (boolean relation, then insertion, then neither), asked by `BindSoleOperandCondition`, `BindComparison`'s address arm and the walk's address and value arms; the walk's boolean arm is `AsCondition`, the wrapper that carries the SR1 length-1 screen; `RefuseAbbreviationAfterBooleanRelation` takes the binder of the object and `BindAbbreviatedRelation` binds the object before COBOL2552.
- Pinned by `EvaluateObjectOperandFaultTests` (15 walk rows, 8 IF rows) and the refusal goldens `pb4707-evaluate-refused-pair-value-after-boolean-expression-relation`, `pb4707-evaluate-refused-pair-address-after-boolean-relation`, `pb4707-evaluate-refused-pair-simple-boolean-condition-length`, `pb4707-address-after-boolean-expression-relation` and `pb4707-abbrev-after-boolean-relation-object-fault`.
