# PB891 — OPEN — a flag with no stack, in a language with nesting

Source: the `PB368` report, "New defects" — filed there as the single lead of that change set.

## The mechanism, read from the emitter

`src/Cobol.Net.Compiler/CodeGen/EcEmitter.cs`:

```
:150   foreach (var g in gates) w.Line($"ExceptionState.{g.Flag} = true;");
:162   w.Line("finally { " + string.Join(" ", gates.Select(g => $"ExceptionState.{g.Flag} = false;")) + " }");

:253   foreach (var g in gates.Where(g => g.Flag is not null)) w.Line($"ExceptionState.{g.Flag} = true;");
:271-2 var reset = gates...Select(g => $"ExceptionState.{g.Flag} = false;")...
       if (reset.Count > 0) w.Line("finally { " + string.Join(" ", reset) + " }");
```

`= false` is not "restore what it was"; it is "assume it was off". Two failures follow, in opposite
directions:

* **an enclosing statement loses its enable.** When a guarded statement's execution runs OTHER statements in
  the same runtime element — a declarative invoked from its `__IoCheck`, an F3 handler range, a debugging
  declarative — the inner gate's `finally` sets the flag `false`, so a LATER raise site of the OUTER
  statement reads "checking off" and the condition is not raised.
* **an unguarded inner statement inherits `true`** and can raise a condition that is not enabled at THAT
  statement.

```
$ python scripts/spec/cite.py --check 14.6.13.1.1 "if checking for an exception condition is not enabled, the exception condition will not be raised"
  OK  §14.6.13.1.1   (General)
```

Enablement is a property of the SOURCE TEXT at the raising statement, so both directions are wrong answers.

## ⛔ The correct shape is seventeen lines away in the same file

```
:637   w.Line("var __ck = ExceptionState.PushAllCheckingOff();   // GR14 implicit PUSH ALL + TURN OFF ALL");
:644   w.Line("finally { ExceptionState.PopAllChecking(__ck); }   // GR14 implicit POP ALL");
```

§14.9.28.4 GR14's implicit PUSH/POP already has a saved-state discipline in `CheckingFlags`. The repair is a
**saved local per gate**, the same shape, applied to `EmitArgOrPlain` and `EmitGatesOrInner`.

## ⛔ What the fixer must expect — this changes generated text for EVERY EC golden

There are ~30 ambient conditions and every one of them goes through these two methods. The diff is wide and
shallow: it is a mechanism, not an EC-FLOW-USE special case, and shrinking it to one condition would leave
the other twenty-nine with the same bug and a test that says otherwise.

## Repro shape (NOT yet measured end to end)

A declarative whose body lies in a `>>TURN … CHECKING OFF` region, invoked from a statement in a CHECKING ON
region; then a second raise site of that outer statement. **This note is filed from the emitted-text
mechanism, which is decisive about what is generated; the behavioural golden is the fixer's first step**, and
it should be written BEFORE the fix so it fails once (memory `green_gates_arent_evidence`).

## Relation to PB841

`kb/Work/PB841` is the same family and a different boundary — the flags leaking across a CALL, because
`ProgramTable.CallProgram` saves the external mask and the PERFORM depth and not `ExceptionEngine._checking`.
PB841 is the CALL boundary, PB891 is the STATEMENT boundary. One implementer takes both: the answer in both
cases is that the ambient checking state is a SAVED-AND-RESTORED stack rather than a flag anyone may clear.
