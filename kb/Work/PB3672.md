# PB3672 — an environment failure in the pin settle reads as a conflict; the session's language server locks agents' DLLs

**Sites:** `scripts/merge_drivers.py` (`merge`: the settle-error return), `scripts/orchestrator/enqueue.py` (the exit 4
path), `scripts/orchestrator/land_lane.py` (its classification of the stop), `scripts/run_gate_legs.py` (`NOT_RUN_CAUSES`, the one
classification of environment causes, PB3526).

## The case (2026-10-24 18:59 PDT)

The landing lane started `enqueue.py land` on PB3664's branch. After the clean merge of main, `abi_pin.settle` built
the solution in the worktree (always, until PB3671). MSBuild could not copy `WiseOwl.Cobol.Compiler.SourceGen.dll` over
the one in `bin`: "The file is locked by: CSharpLanguageServer (62616)". That was the attended operator session's
`csharp-ls.exe`. `merge_drivers.merge` returns the pin's path as if it were in conflict, so `enqueue.py` ended exit 4
CONFLICT and the lane marked the branch STOPPED for a finisher. Nothing conflicted. The operator stopped the language
server and re-armed the branch (`land_lane.py rearm`).

## Two defects

1. **A settle failure is not a conflict.** `merge` gives the same answer for a real conflict and for a settle that could
   not build or measure. It should return the settle's reason, and `enqueue.py` should classify it once through
   `run_gate_legs.NOT_RUN_CAUSES`. An environment cause (a locked file, no SDK) is exit 2, retried once and then handed
   to the operator. A branch cause (the merged tree does not build, the measurement is red) blocks like a red gate,
   exit 5, a finisher's. Neither is exit 4.
2. **The dispatching session's language server holds agent worktrees' DLLs.** Workflow agents are subagents of the
   session that launched them, so their C# edits go through that session's `csharp-ls`. It loads the agent's worktree
   (the session reported diagnostics from `wf_ae6946ad-ce4-1` and `wf_17b59ed2-4ae-1`) and keeps analyzer assemblies
   open, so any later build that must overwrite `WiseOwl.Cobol.Compiler.SourceGen.dll` fails with MSB3027. PB3339 recorded the
   same lock as a "trap" (rename the held file) and nothing fixed it. The fix direction: keep the operator session's
   language server out of agent worktrees, by its workspace configuration or by worktrees outside the main checkout's
   tree, or have the gate and the settle build detect a held analyzer DLL and name the holder as an environment cause.
   Measure it: count the MSB3027 lock failures in gate and landing logs over a day, before and after.

## Retired (2026-10-24)

The loop's units filed the same two defects as PB3673 and PB3674 within the hour, one note per mechanism, which is the register's rule. This note's evidence (PB3664's 18:59 landing, `land-lane-000097`, and the attended session's csharp-ls holding `WiseOwl.Cobol.Compiler.SourceGen.dll` in a worktree of an agent it dispatched) is copied into them. **The pattern (operator, 2026-10-24).** Three notes are one mechanism: an ENVIRONMENT cause read as a failure of the WORK. PB3673: a pin settle whose build is blocked is reported as a conflict (exit 4) and sent to a finisher. PB3674: a language server holds an analyzer DLL, so a gate or settle build fails as if the branch were broken. PB2665: a meter unit that cannot reach Chrome fails as a unit and counts toward the circuit breaker, so the loop retries it until it stops itself. The gate already has the one classifier (`run_gate_legs.NOT_RUN_CAUSES`, PB3526: an environment cause is exit 2, retried once, then the operator's). The fix extends that ONE classification to `merge_drivers.merge`'s settle, `enqueue.py`'s exit mapping and the loop's unit accounting (`orchestrate.ps1`'s breaker, `next_unit.py`'s meter rule), rather than three local patches.
