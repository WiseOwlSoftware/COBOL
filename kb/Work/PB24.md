# PB24 — FUNCTION LENGTH is wrong or absent on four shapes

⚙ **ALL FOUR CLAIMS RE-MEASURED 2026-08-04 BEFORE ANY CODE CHANGED. Three held, one did not.**

## ✅ LANDED — a reference-modified argument (was: compiles clean, throws at run time)

`FUNCTION LENGTH(WS-NAME(1:5))` is conforming source — §15.50.3 r1 admits "a data item of any class or category"
and §8.4.3.3.3 makes a reference-modified item one (both `cite.py --check`ed). It bound to a `BoundExprError`,
which renders as a NotImplemented guard: **compiled clean, threw at run time, exit 127.** The PB7/DA7 wrong-stage
family — except there was no verdict to deliver at all, because the source is legal and the answer computable.

**The fix added no machinery, and that is the interesting part.** `IntrinsicRenderer`'s `Length` arm renders its
argument through the ONE string channel, and a reference-modified place renders as the **substring** — so the
runtime length over that image already IS §15.50.4's character-position count. Changing the arm from
`BoundExprError` to the runtime `BoundIntrinsicCall` was the whole change, and all three ref-mod forms fell out
together: literal `(1:5)` → 5, runtime `(I:L)` → 6, omitted-length `(15:)` → 6, and `(20:1)` → 1.
Golden: `2023/pb24_length_refmod_argument`.

## ✅ LANDED — a variable-length group (was: silently wrong)

**Was:** a group of `PIC X(4)` plus a `PIC X DYNAMIC LENGTH` child holding `"XYZ"` returned **4**; §15.50.4 r7
requires **7**. No diagnostic.

**Root cause:** `BindLengthFold` had arms for ref-mod, ODO, ANY LENGTH, national dynamic-length and
dynamic-length *elementary* items — and **no arm for a GROUP with a dynamic descendant**, so it fell to the fixed
fold, where `DataItem.ImageWidth` contributes 0 for such a child (§8.5.1.10). A missing arm in a dispatch, in its
silent form.

**Fix:** r7 is built from the compile-time-known structure — `ImageWidth` already *is* r7(a) (it sums the fixed
subordinates and zeroes the dynamic ones), so the arm adds r7(b): one runtime `FUNCTION LENGTH` per dynamic-length
leaf, found by a **recursive** walk because r7 says "all subordinate", not "all immediate children".
⚠ The cheap fix was tried and does not work: routing the group through the runtime string channel fails, because
the whole-group image of such a group is itself staged loud (the Tier-C byte island).
⚠ **r7(c) — a subordinate dynamic-capacity table — is staged LOUD, not summed wrong.** `ImageWidth` counts such a
table as ONE occurrence, so folding it would return a plausible number wrong by (capacity − 1) elements.
Golden: `2023/pb24_length_variable_length_group` — fixed group unchanged · one dynamic · TWO dynamic · a dynamic
leaf NESTED in a subordinate group · and a **regrow at run time** (4+12 = 16), which is what proves the value
tracks content rather than being a new constant.

## ✅ LANDED — the PHYSICAL keyword (was: rejected legal source)

`FUNCTION LENGTH(WS-G PHYSICAL)` → `COBOLNET1504: takes 1 argument(s); 2 given`. §15.50.2's format is
`FUNCTION LENGTH ( argument-1 [ PHYSICAL ] )` — a KEYWORD, counted as an operand.

**No grammar change was needed.** It is consumed exactly as `ANYCASE` is for the NUMVAL-C family, because a bare
word already parses as an argument context (`BindLengthFamily`).

⚖ **What it RETURNS is an implementor determination, and r8's closing sentence makes it small:** *"If argument-1
is physically located where it is defined, LENGTH returns the same value that would be returned had the PHYSICAL
argument not been specified."* COBOL.NET determines that a variable-length group IS physically located where
defined — no addressable out-of-line pointer is observable by a program — so PHYSICAL is semantically
transparent. Recorded in `docs/CONFORMANCE.md` §4.2.16.
Goldens: `2023/pb24_length_physical_keyword` (each PHYSICAL form asserted equal to its plain form) and
`negative/pb24-length-two-operands` (a genuine second operand must still be rejected — consuming a keyword must
not degrade into accepting anything).

## ⛔ OPEN — §15.50.4 r9, the rounding step: MEASURED AND VIOLATED

**It is reachable, and the legality question is settled.** A group mixing an alphanumeric and a bit item is an
**alphanumeric group item** — §3's definition is "group item *except for* a bit group item, a national group
item, a strongly-typed group item, or a variable-length group item" — so §15.50.4 r3 applies (the value is in
alphanumeric character positions) and r9 rounds it up.

**MEASURED:** `05 M1 PIC X(3).` + `05 M2 PIC 1(5) USAGE BIT.` returns **8**. Required: 3 characters (24 bits) plus
5 bits = 29 bits = **3.625** alphanumeric positions → r9 → **4**. The implementation counts each bit as a whole
character position. **Silent wrong answer.**

**Fix shape:** group length must be computed in BITS and converted to character positions with a ceiling, rather
than summing per-child character widths. That is a change to how `ImageWidth` composes a mixed group, not another
arm on `BindLengthFold` — which is why it is its own change and not bundled here.

## ⛔ AND ONE CLAIM DID NOT SURVIVE

The original entry said the variable-length group case covered **OCCURS DEPENDING** and was "silent". It is not:
an ODO group raises `NotImplementedCobolFeatureException` naming §15.50.4 r7 — **loud, at run time**. The silent
wrong answer is specific to a **dynamic-length** child (§8.5.1.12), which is what the entry's own citation said
and its prose contradicted. Corrected here rather than carried forward.
