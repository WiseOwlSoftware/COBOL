# PB449 — the SET format is selected from the FIRST receiving operand alone

Lane-3 adjudication batch b2, group g7-set-a. **Every repro below was re-run on HEAD `89044aa0`** (the
adjudication ran on the pinned `5fe593a0`); all still reproduce.

## 1. THE MECHANISM

`SET` has seventeen printed general formats and several of them share one token shape. The binder therefore
*sniffs* the format from an operand's category — and it sniffs **`drefs[0]` and nothing else**.

`PtrBinder.TryBindSetUpDown` (`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/PtrBinder.cs:257-282`) decides
whether a `SET … UP/DOWN BY` statement is Format 10 (data-pointer arithmetic) or Format 2 (index arithmetic):

    if (host.Expr.IndexFieldOf(drefs[0]) is not null) return null;                       // :263
    if (ctx.Refs.Probe(drefs[0]) is not { } sniff
        || sniff.Item.Pic?.Category is not PicCategory.Pointer) return null;             // :264-265

If that one operand is not a data-pointer the method returns `null` and the **whole statement** — including any
data-pointer operands written later in the list — falls through to `SetBinder.BindSetUpDown`
(`SetBinder.cs:366-379`), whose `SetTargetOf` (`SetBinder.cs:444-447`) accepts anything `ResolveReceiving` can
resolve. When the pointer *is* written first, the SR23 screen at `PtrBinder.cs:274-279` runs over
`drefs.Skip(1)` and produces a correct, self-citing `COBOLNET0869`. Same rule, same two operands, two verdicts —
decided by source order, which is not a rule variable anywhere in §14.9.39.

The TO direction has the identical shape at `SetBinder.cs:337-353`: the re-route reads `tds[0]` **or** the
sender (`t0`/`s0` at :340-341), so a Format-9 statement whose *first* receiver and sender are both numeric while
a *later* receiver is a program-pointer escapes routing entirely and SR21 is never asked.

**This is the shape the file's own comment says was fixed one level down.** `PtrBinder.cs:269-271` records
[[PB221]] verbatim: "Committing the probe's Place made `SET P(XE) Q(XE) UP BY 4` diagnose COBOLNET0844 for Q and
not for P: one statement, one rule, two verdicts, decided by which operand the format sniff happened to read."
That landing made the first operand share the others' **resolution**. It did not make the format **selection**
consider more than the first operand, and the same sentence still describes what is left.

There is also **no residual arm**: nothing says "no printed format admits this statement". A receiving list that
matches no format is simply executed as Format 1/2 arithmetic.

      N=[0005]                                        ← no format admits this; it is executed

And the SR21 leg the refuter found, re-measured here on HEAD (`probe-g7-set-a/p449/z1_pp_late_recv.cob`,
`01 PP1 USAGE PROGRAM-POINTER. 01 WS-N PIC 9(4). 01 WS-M PIC 9(4).` + `SET WS-N PP1 TO WS-M`):

    (compiles with ZERO diagnostics)
    Unhandled exception. … arithmetic into a non-fixed-point target 'PP1'

Both operands are identifiers, so Format 9 matches syntactically, and Format 9 is the **only** format whose
receiving operand may be a program-pointer. SR21 is violated twice over and never asked, because neither `t0`
nor `s0` is a program-pointer.

**Expected:** each of these statements shall be diagnosed, and diagnosed *identically whichever operand is
written first*. `g2_num_upby` shall be rejected rather than executed.

## 4. THE CODE SITE AND THE SHAPE OF THE REPAIR

| arm | file:line | what it reads |
|---|---|---|
| UP/DOWN BY format sniff | `PtrBinder.cs:263-265` | `drefs[0]` only |
| the SR23 screen it gates | `PtrBinder.cs:274-279` | `drefs.Skip(1)` |
| TO-direction re-routes (F4 / F9 / F5) | `SetBinder.cs:340-352` | `tds[0]` and the sender only |
| permissive fall-through | `SetBinder.cs:354-360`, `:373-378` → `SetTargetOf` `:444-447` | anything resolvable |

⛔ **The repair is not a second screen; it is to move the selection off `[0]`** (CLAUDE.md rule 5). Format
selection shall be computed from the **whole receiving list plus the sender** — classify every operand once,
then pick the single format whose printed receiving brace admits *all* of them — and there shall be a terminal
arm that reports "no SET format admits this receiving list" rather than falling into Format 1/2. A scalar
`category-of-operand-0` is standing in for what §14.9.39.2 makes a **set-valued** question, which is exactly
`model_the_rule_shape_not_one_case`. Pair it with a drift test that compiles each mixed list **in both orders**
and asserts the two diagnostics are the same.

## 5. THE SIBLING SWEEP THE FIXER MUST DO

* `SetBinder.cs:340-352` — all three TO re-routes (Pointer / ProgramPointer / ObjectReference) ride the same
  `t0 || s0` sniff. Fixing only the UP/DOWN arm repeats [[PB221]]'s mistake one level up.
* `SetBinder.cs:59-70` (`setObjectReferenceStatement` dispatch) — `sorCat` is `Probe(sor.dataReference(0))`,
  the same first-operand sniff for the NULL/SELF/SUPER sender route.
* `DynTryBindSetCapacity` (`SetBinder.cs:387-405`) already reads `targets[0]` but *does* screen `Count > 1`
  (COBOLNET1524) — it is the one arm with a residual check, and it is the model.
* `DynTrySetSize` (Format 16 bare form) — same peek idiom, unchecked list.
* The Format-9 data-pointer near-miss: `SET PP1 TO DP1` is refused by the **data-pointer** arm, blaming an
  operand that conforms to SR21, and its message names a format ordinal that is condition-setting in 2023, not
  pointer assignment. That wrong-ordinal sweep is **[[PB388]]**'s (`SetBinder.cs:194/:204/:217`,
  `BoundTree.cs:744`) — do not re-tabulate it here; land it in the same change set.
