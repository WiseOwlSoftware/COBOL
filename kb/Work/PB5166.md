# PB5166 - at --std 85 an unqualified LINAGE-COUNTER in a contained program with one LINAGE file of its own is refused (COBOL5997) when a containing program has a GLOBAL LINAGE file: LinageFileOf counts the 2023 visible files, not the program's own file description entries

**Sites:**

- `src/WiseOwl.Cobol.Compiler/Binding/CounterResolver.cs` (`LinageFileOf`)
- `src/WiseOwl.Cobol.Compiler/Binding/DataBindState.cs` (`VisibleFiles`)

**Mechanism.** §1985:IV.4.3.8.1 SRL2.8 requires LINAGE-COUNTER to be qualified only if more than one file description entry with a LINAGE clause is specified in the source program. `CounterResolver.LinageFileOf` resolves an unqualified reference only when exactly one LINAGE file is in `VisibleFiles`, the program's own files plus every containing program's GLOBAL files, which is the 2023 count. A contained program with one LINAGE file of its own under a container whose LINAGE file is GLOBAL is refused at --std 85, a legal program rejected.

- `1985-SR-IV.4.3.8.1-L2.8` - `§1985:IV.4.3.8.1 SRL2.8` (record verdict: PARTIAL, harm: rejects-legal-source). Checked: §1985:IV.4.3.8.1 SRL2.8: "LINAGE-COUNTER must be qualified each time it is referenced if more than one file description entry containing a LINAGE clause has been specified in the source program.". Code sites read: src/WiseOwl.Cobol.Compiler/Binding/CounterResolver.cs#LinageFileOf; src/WiseOwl.Cobol.Compiler/Binding/DataBindState.cs#VisibleFiles. Code read: §1985:IV.4.3.8.1 SRL2.8: "LINAGE-COUNTER must be qualified each time it is referenced if more than one file description entry containing a LINAGE clause has been specified in the source program." LinageFileOf is the one resolver of the register: a qualified reference takes the named file if its file description entry has a LINAGE clause (COBOL0863 otherwise), and an unqualified one resolves only when exactly one file with a LINAGE clause is in VisibleFiles, else COBOL5997. It has no edition arm, and VisibleFiles is the program's own files plus every containing program's GLOBAL files, which is the count of §2023:8.4.2.2.3 SR8 ("may be referenced within the source element in which the reference to LINAGE-COUNTER occurs"), not the 1985 one. For a program that contains no other and is contained in none the two counts are the same and the rule is met; probed at --std 85: two LINAGE files refuse each unqualified reference (DISPLAY, IF) and accept OF and IN with either file-name in DISPLAY, MOVE, ADD and a relation; one LINAGE file beside a file without LINAGE needs no qualifier; a qualifier naming a file without LINAGE is refused. The counts differ in a contained program that specifies one LINAGE file of its own under a containing program whose LINAGE file is GLOBAL: one file description entry with a LINAGE clause "has been specified in the source program" that holds the reference, so 1985 requires no qualifier, and the reference is to that program's own register (§1985:X.1.3.8: a program's reference is "to the object which that program describes rather than to the object, possessing the same name, described in another program"; §1985:X.1.3.8.2 uses "declared in a source program" for a program's own declarations, apart from those of a program it contains), while the compiler refuses it with COBOL5997 because the containing program's register is a global name (§1985:X.4.2.4 GR1) and so a second visible file. This reads "the source program" as the program that holds the reference; GnuCOBOL 3.2 at -std=cobol85 counts the same way and accepts the program (a regression net, not authority). Under the other reading, in which a contained program's file description entries count for the program that contains it, the compiler departs the other way: a containing program with one LINAGE file and a contained program with another, neither GLOBAL, compiles with an unqualified reference in each (probed). The witness is one program with two LINAGE files and DISPLAY LINAGE-COUNTER, refused with COBOL5997. No kb/Work note owns the fix.

**Repro (`1985-SR-IV.4.3.8.1-L2.8`).** `cobol.exe <file> --std 85 --source-format fixed --run`

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. LCOUT.
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
           SELECT PFILE1 ASSIGN TO "LCOUT1.DAT".
       DATA DIVISION.
       FILE SECTION.
       FD  PFILE1 IS GLOBAL LINAGE IS 20 LINES.
       01  P1-REC PIC X(20).
       PROCEDURE DIVISION.
       MAIN-PARA.
           CALL "LCIN".
           STOP RUN.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. LCIN.
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
           SELECT PFILE2 ASSIGN TO "LCOUT2.DAT".
       DATA DIVISION.
       FILE SECTION.
       FD  PFILE2 LINAGE IS 30 LINES.
       01  P2-REC PIC X(20).
       PROCEDURE DIVISION.
       IN-PARA.
           OPEN OUTPUT PFILE2.
           DISPLAY LINAGE-COUNTER.
           CLOSE PFILE2.
           EXIT PROGRAM.
       END PROGRAM LCIN.
       END PROGRAM LCOUT.
```

**Expected (from the 1985 text, the record's).** The program compiles and displays 01, the LINAGE-COUNTER of PFILE2 after OPEN OUTPUT. §1985:IV.4.3.8.1 SRL2.8 requires the qualifier only "if more than one file description entry containing a LINAGE clause has been specified in the source program", and LCIN specifies one. §1985:IV.4.3.8: "These conventions ensure that the resource identified is that described in the program containing the reference." §1985:VII.3.7.4 GR9: "Since more than one LINAGE-COUNTER may exist in a program, the user must qualify LINAGE-COUNTER by file-name when necessary."

**Observed (the record's).** exit 65: repro.cob(28,20): error COBOL5997: unqualified LINAGE-COUNTER with more than one LINAGE file: qualify by file-name (ISO §2023:8.4.3.14 SR3 / §2023:8.4.2.2 Qualification). With DISPLAY LINAGE-COUNTER OF PFILE2 the program compiles and displays 01.

**Fix direction (root cause, CLAUDE.md rule 4).** Count by the edition: before 2014 the program's own file description entries, at 2014 and later the visible ones, decided inside LinageFileOf through the edition context so the rule has one home.
