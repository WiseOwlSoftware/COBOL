# PB527

## Mechanism — picture-clause-p1
A data description entry that carries BOTH a PICTURE clause and subordinate entries has no representation in the bound data model, so nothing can diagnose it. DataItem.IsElementary is defined as `Pic is not null` and IsGroup as `Pic is null && Children.Count > 0` (Model/DataItem.cs:347,350): the moment a PICTURE is present the entry is ELEMENTARY by definition and its Children collection is simply never consulted by codegen. DataBinder's single Analyze call site for a data description entry (DataBinder.cs:2591-2597) passes the picture text, the usage, the SIGN clause and the BLANK WHEN ZERO flag but not the entry's level or its subordinates, and PictureAnalyzer has no parameter through which it could see them - so ISO 13.18.40.3 SR1 has no enforcement site anywhere and no diagnostic in the catalog names it. The fix is not a guard inside PictureAnalyzer (which cannot see the tree) but a bind-time structural check at the entry level, beside the other 13.16.3 co-clause checks, plus a data-model invariant so the illegal shape can never reach codegen again.

### Expected, from the standard
ISO/IEC 1989:2023 13.18.40.3 syntax rule 1: "The PICTURE clause may be specified only at the elementary level." An entry that has subordinate entries is not elementary, so the PICTURE clause on it is illegal source and shall be rejected with a named diagnostic that cites 13.18.40.3 SR1. No edition relaxes this (the rule is 85-era; measured identically at all four).

```
$ python scripts/spec/cite.py --check 13.18.40.3 "The PICTURE clause may be specified only at the elementary level"
  OK  §13.18.40.3   (Syntax rules)
```

### Observed
Accepted silently at every edition. Two distinct harms follow. The mild one is data loss: the subordinate entries are dropped from the emitted record struct and the group behaves as a plain elementary item of the PICTURE's width. The severe one is that the compiler CRASHES OUT THROUGH ROSLYN the instant the user references one of those subordinates - the reference binds (the symbol table still holds the child), codegen emits a member access against the parent's `string` storage, and the user is shown a C# compiler error and a path to a generated file, not a COBOL diagnostic. That is the classic loud-guard hole: an illegal shape that the model cannot represent is smuggled past bind and surfaces as an internal failure.

## Landed (2026-09-20, wave 42 group E) — COBOLNET2191

**Re-probed first.** On a `dotnet build CobolSharp.sln -c Debug` of the implementer's own worktree (cut from
main `545577479`), the note reproduced exactly as written: `01 G PIC X(3). 05 A PIC X.` compiled clean at
`--std 2023` and printed `G=[QRS] L=3` with A gone, and adding `DISPLAY A` failed in the BACKEND with
`error CS1061: 'string' does not contain a definition for 'A'` and a path to the generated `.g.cs`.

**The rule, re-derived (CLAUDE.md rule 1 — the note's citation was re-run, and a second one was needed).**

```
python scripts/spec/cite.py --check 13.18.40.3 "The PICTURE clause may be specified only at the elementary level"
  OK  §13.18.40.3   (Syntax rules)  1.
python scripts/spec/cite.py --check 8.5.1.3.1 "those not further subdivided, are called elementary items"
  OK  §8.5.1.3.1   (General)
```

SR1 is one sentence and it does not define "elementary level"; §8.5.1.3.1 does — "The most basic subdivisions of
a record, that is, those not further subdivided, are called elementary items". So the test is the SUBORDINATE
COUNT, and both citations belong in the message. ALL FORMATS, 85-era, identical at all four editions (measured).

**Where it landed, and why there.** `DataBinder.PictureRequired.cs` already held §13.16.3 SR8's closing guard —
*elementary ⇒ has a PICTURE*. SR1 is its exact converse — *has a PICTURE ⇒ elementary* — and the two need the
same undecidable-at-entry-bind fact (does this entry have subordinates). They are now one pass over the finished
forest, `CheckPictureRequired` → `CheckPictureAtElementaryLevel`, sharing `HasNoSubordinates`, with the same
two-forest discipline (report over `ConformanceForest` so a defective TYPEDEF template is named once; repair
over `CompositionForest` so a clone `ExpandTypes` already made is repaired too). The note proposed "beside the
other §13.16.3 co-clause checks" at bind; that placement cannot work — `BindEntry` runs before the subordinate
entries are parsed — and the SR8 guard is the site that already solved exactly that problem.

**The data-model invariant the note asked for.** The recovery CLEARS THE PICTURE, not the children: the entry
becomes the group its hierarchy declares, so the forest stays consistent and no data-name the procedure division
may reference is deleted (which would turn one reported defect into a cascade of invented ones). That makes
`IsGroup` XOR `IsElementary` TOTAL, and `PicturePlacementInvariantDriftTests` (Unit) asserts it — over thirteen
legal data-division shapes (nesting, tables, REDEFINES, RENAMES, condition-names, FILLER, a picture-less usage,
a group USAGE, TYPE, SAME AS, SR9's VALUE-implied picture) and over three illegal ones. ⛔ It was PROVED to fail:
with the one recovery line removed it went 3 red of 16 (`feedback_green_gates_arent_evidence`).

**Sibling sweep (CLAUDE.md rule 4).** The sibling shapes of "an entry the model cannot classify" were checked:
the NEITHER arm (no PICTURE, no subordinates) is SR8's, already guarded; a PICTURE beside TYPE or SAME AS is
already refused by §13.16.3 SR12/SR14, so no unexpanded reference can reach this guard; levels 66 and 88 are not
Format-1 entries and are excluded by level in both directions. The drift test's totality assertion is what
catches the next clause that can produce an unclassifiable entry.

**Goldens.** `tests/conformance/negative/pb527-picture-on-a-group` (reject at all four — SR1 is
edition-independent) and the over-rejection guard `tests/conformance/85/pb527_picture_placement` at the rule's
introducing edition, which pins the populations the screen must leave alone.
