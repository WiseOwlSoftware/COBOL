# PB527

## Mechanism — picture-clause-p1
A data description entry that carries BOTH a PICTURE clause and subordinate entries has no representation in the bound data model, so nothing can diagnose it. DataItem.IsElementary is defined as `Pic is not null` and IsGroup as `Pic is null && Children.Count > 0` (Model/DataItem.cs:347,350): the moment a PICTURE is present the entry is ELEMENTARY by definition and its Children collection is simply never consulted by codegen. DataBinder's single Analyze call site for a data description entry (DataBinder.cs:2591-2597) passes the picture text, the usage, the SIGN clause and the BLANK WHEN ZERO flag but not the entry's level or its subordinates, and PictureAnalyzer has no parameter through which it could see them - so ISO 13.18.40.3 SR1 has no enforcement site anywhere and no diagnostic in the catalog names it. The fix is not a guard inside PictureAnalyzer (which cannot see the tree) but a bind-time structural check at the entry level, beside the other 13.16.3 co-clause checks, plus a data-model invariant so the illegal shape can never reach codegen again.

### Expected, from the standard
ISO/IEC 1989:2023 13.18.40.3 syntax rule 1: "The PICTURE clause may be specified only at the elementary level." An entry that has subordinate entries is not elementary, so the PICTURE clause on it is illegal source and shall be rejected with a named diagnostic that cites 13.18.40.3 SR1. No edition relaxes this (the rule is 85-era; measured identically at all four).

```
$ python scripts/spec/cite.py --check 13.18.40.3 "The PICTURE clause may be specified only at the elementary level"
  OK  §13.18.40.3   (Syntax rules)
```

### Observed
Accepted silently at every edition. Two distinct harms follow. The mild one is data loss: the subordinate entries are dropped from the emitted record struct and the group behaves as a plain elementary item of the PICTURE's width. The severe one is that the compiler CRASHES OUT THROUGH ROSLYN the instant the user references one of those subordinates - the reference binds (the symbol table still holds the child), codegen emits a member access against the parent's `string` storage, and the user is shown a C# compiler error and a path to a generated file, not a COBOL diagnostic. That is the classic loud-guard hole: an illegal shape that the model cannot represent is smuggled past bind and surfaces as an internal failure.
