# PB144 — the phrase-placement leniency family, and the indexed DELETE nobody ran

**Landed.** Nine inventory rows flipped to CONFORMS: `SR-14.9.10.3-1`/`-2`, `SR-14.9.35.3-2`, `SR-14.9.30.3-6`,
`GR-14.9.10.4-1`/`-3`/`-8`/`-9`/`-11`. Design: `docs/COBOLNET_FILES_DESIGN.md` **D9**. New diagnostic:
`COBOLNET1720`.

## (A) The leniencies got their strict arm

Three syntax rules — §14.9.10.3 SR2 (DELETE's INVALID KEY in sequential access), §14.9.35.3 SR2 (REWRITE's, two
arms), §14.9.30.3 SR6 (READ's ADVANCING/AT END/NEXT/NOT AT END/PREVIOUS under ACCESS RANDOM) — were each bound
unconditionally with a "tolerated in the default (CCVS-lenient) mode" comment and **no strict arm**. Probed at
`--std 2023` strict: all of them compiled clean with **no diagnostic at all**. That is `under_rejects` — the
compiler silently accepting source the standard says "shall not be specified".

⚠ **The two-arm defect, again, inside the rule itself.** §14.9.35.3 SR2 forbids the phrase for "a file with
**sequential organization** *or* a file with relative organization and sequential access mode". Only the second
arm was ever commented. The first goes through `SequentialIoBinder.BindRewrite`, which **never read
`rewriteInvalidKeyPhrase()` at all** — parsed and dropped on the floor, worse than the keyed twin that at least
bound it as dead. Both arms are screened now and both have a negative fixture.

All four sites route through `StatementValidation.ScreenForbiddenPhrase` → **`EditionContext.Removed`**, the ONE
policy seam (⚠ PB144's original note said that seam "is unused" — stale; it had call sites already). Error under
strict, warning with an **unchanged bind** under `--permissive`, which is what keeps the CCVS-85 corpus compiling.
One reusable code for all three rules, on the `COBOLNET1694` precedent. §14.9.10.3 **SR1** stays a hard
`COBOLNET0865` at every edition — it is not a leniency — but it had **no negative fixture** either (the code
occurred exactly once in the repo, at its own emit site), so it got one.

**The edition-gate sweep was run, and it was the real risk.** 315 `REWRITE … INVALID KEY` and 28
`DELETE … INVALID KEY` sites exist in the NIST programs, and NIST runs **strict** by default. All 459 compiled at
`--std 85`: the **same 17 pre-existing failures** (`CM*` COMMUNICATION SECTION, `DB*` `COBOLNET1571` — each read
individually, none mine) and **zero** new ones. Every one of those 343 sites is on an organization/access mode
where the phrase is legal, which is exactly what the screens test. The harness was proved able to report
`COBOLNET1720` as a failure before that zero was believed.

## (B) The indexed DELETE RECORD path that had never executed

**Measured first:** 37 fixtures mention INDEXED and **not one** issued a DELETE against one; both DELETE unit
tests build RELATIVE connectors. So `IndexedConnector.Delete` — and `KeyedIoEmitter`'s key-slice emission — had
never run in the suite. `2002/pb144_indexed_delete_record` now exercises eight legs, every expected value derived
from its rule *before* the fixture was executed:

| leg | rule | result |
|---|---|---|
| `IX49` | GR1 — open mode shall be I-O | `49` |
| `IXDEL00` | GR3 — remove the record identified by the prime key | `00` |
| `IXGONE` | GR5 — the removed record can no longer be accessed | `23` |
| `IXIK23` / `IXIKFIRED` | GR3 + GR11 — absent key ⇒ invalid key condition, imperative runs | `23`, `YES` |
| `IXNIK` | GR11 — a successful delete takes NOT INVALID KEY | `NOT-INVALID` |
| `IXAREABEF`/`IXAREAAFT`/`IXGR8` | GR8 — the record area is unaffected | identical |
| `IXNEXTST` / `IXNEXT` | GR9 — the FPI is unaffected | `00`, `K03` |
| `IX43` | GR2 — sequential access needs a prior successful READ | `43` |

All eight passed on the first run. The analysis warned that "a first-run green on previously-unexecuted legs
deserves suspicion, not celebration", and GR8/GR9 in particular hold *by omission* — so **GR9 was
mutation-proved**: with `Delete` mutated to set `_fpiValid = false`, `IXNEXTST` flips `00`→`46` and `IXNEXT`
flips `K03`→`K02`. The mutant was reverted and the file verified byte-identical. GR8 holds by construction (the
record area is the generated record struct; the runtime connector cannot reach it), and the fixture prints both
captured images so a divergence shows as a value change rather than hiding behind a boolean.

## What this note does NOT cover

**PB144-B — the split prime/alternate key (`RECORD KEY … SOURCE IS`) — is deliberately excluded and is now
tracked as its own note, [[PB293]], so marking this one landed does not lose it.** Its premise inverts on the
spec: §A.3 item 40 makes the SOURCE phrase **processor-dependent**, so a
conforming implementation need not provide it, and `docs/CONFORMANCE.md` row 40 already records it as *Not
claimed*. What is defective is the **shape of the refusal** (`SOURCE` is a hard lexer token outside `cobolWord`,
so the construct dies as a raw ANTLR syntax error naming a token rather than naming the determination, where the
tree's own CODE-SET precedent at `DataBinder.cs` under `COBOLNET1672` shows the required form). *Providing* the
feature is **not** proposed and opens no owner question — [[PB293]] records why (the standard grants the
standing-pat position, row 40 already claims it, and nothing in the conformance claim turns on it); the named
refusal is the whole debt. Not started here.
