# PB439 — asking the node's C# type where the rule asks a COBOL question

## 1. THE MECHANISM

`ControlFlowEmitter.InitVaryingTarget` emits the GR3 check only when the FROM operand's BOUND NODE has one
particular C# type — `src/Cobol.Net.Compiler/CodeGen/Verbs/ControlFlowEmitter.cs:348-360`:

    private void InitVaryingTarget(PerformVarying v, VaryingLevel lv)
    {
        if (v.CheckIndexRange && lv.Var is SetIndexTarget ix && lv.From is BoundNumRef)
        {
            string tmp = $"__pv{ctx.Names.NextVary()}";
            ctx.Writer.Line($"long {tmp} = (long)({NumericRenderer.Align(num.RenderOperandLike(lv.From), 0)});");
            ctx.Writer.Line($"ExceptionState.PerformVaryingIndexError({tmp}, …);");
            ctx.Writer.Line($"{ix.IndexField} = {tmp};");
            return;
        }
        set.StoreSetTarget(lv.Var, num.RenderOperandLike(lv.From));   // no check at all
    }

A data REFERENCE — plain, qualified, subscripted or reference-modified — binds to `BoundNumRef`, so those are
covered. A FUNCTION-IDENTIFIER binds to an intrinsic-call node and silently takes the plain `StoreSetTarget`
path. The gate is a bound-node SHAPE test where the rule says "an identifier", and a function-identifier is one
of the identifier general formats. The operand is produced by
`ControlFlowBinder.BindVaryingLevel:392-406` via `ExpressionBinder.BindIndexWindowExpr`.

The two other producers for this slot are correctly out of GR3 scope by the rule's own words — `BoundNumLiteral`
(a literal FROM) and `BoundIndexRef` (an index-name FROM) — so a function-identifier is **the one legal
identifier shape that falls through**. The doc-comment above the method names those two exclusions explicitly
and does not mention the function case, which is how it stayed unnoticed.

## 2. THE RULE, QUOTED, WITH ITS `--check` LINES

    python scripts/spec/cite.py --check 14.9.28.4 "If an index-name is specified in the VARYING or AFTER phrase, and an identifier is specified in the associated FROM phrase"
    OK  §14.9.28.4 3)  (General rules)

    python scripts/spec/cite.py --check 14.9.28.4 "the EC-RANGE-PERFORM-VARYING exception condition is set to exist"
    OK  §14.9.28.4 3)  (General rules)

⚠ Both fragments quote enough antecedent to land on GR3 and nowhere else — GR12, its nearest neighbour that also
speaks about the FROM phrase, names the initialization VALUE and says nothing about positivity or about an
exception condition. The full rule: with an index-name in the VARYING or AFTER phrase and an identifier in the
associated FROM phrase, at the time the data item referenced by the identifier is used to initialize the index,
the data item shall have a positive value; if it does not, EC-RANGE-PERFORM-VARYING is set to exist. That EC is
FATAL (Table 13).

That a function-identifier IS an identifier in that slot:

    python scripts/spec/cite.py --check 8.4.3.2.4 "A function-identifier references a temporary data item whose value"
    OK  §8.4.3.2.4 1)  (General rules)

    python scripts/spec/cite.py --check 8.4.3.1.1 "An identifier is a sequence of character-strings and separators used to reference a data item uniquely"
    OK  §8.4.3.1.1   (General)

— the same reasoning the project used to land kb/Work PB86 for the `PERFORM … TIMES` count. And the source is
LEGAL under the syntax rules: §14.9.28.3 SR4 a) requires the FROM identifier to reference an integer data item,
which an integer-type function meets.

    python scripts/spec/cite.py --check 14.9.28.3 "If an index-name is specified in the VARYING or AFTER phrase, then"
    OK  §14.9.28.3 4)  (Syntax rules)

## 3. EXPECTED vs OBSERVED — RE-RUN ON HEAD (89044aa0)

Still reproduces. HEAD `cobol.exe`, `--std 2023`.

          >>TURN EC-RANGE-PERFORM-VARYING CHECKING ON
           01 WS-T.  05 WS-E PIC 9 OCCURS 5 TIMES INDEXED BY IX.
           01 WS-Z PIC S9 VALUE 0.
           … a USE AFTER EXCEPTION CONDITION EC-RANGE-PERFORM-VARYING declarative that DISPLAYs "CAUGHT=…"
             and RESUMEs …
           PERFORM VARYING IX FROM FUNCTION INTEGER(WS-Z) BY 1 UNTIL IX > 3  CONTINUE  END-PERFORM

    $ cobol.exe .../gr3_function_from.cob --std 2023 --run
    exit 0
    P-FN
    P-FN-AFTER

**No CAUGHT line** — the declarative never ran, so the fatal EC was never set to exist. And the index really was
initialized to 0:

    $ cobol.exe .../gr3_fn_count.cob --std 2023 --run
    exit 0
    N=0004
      the same loop with a counted body executes FOUR times (IX = 0, 1, 2, 3).

**The identical program with a SUBSCRIPTED identifier FROM — which binds to `BoundNumRef` — is correct**, and it
is the contrast that isolates the mechanism:

    $ cobol.exe .../gr3_subscripted_from.cob --std 2023 --run
    exit 0
    P-SUB
    CAUGHT=EC-RANGE-PERFORM-VARYING
    P-SUB-AFTER

**Expected** for the function case: the temporary data item the function-identifier references holds 0, which is
not positive, so EC-RANGE-PERFORM-VARYING shall be set to exist, and with checking enabled by the `>>TURN`
directive the USE declarative shall be given control.

**The harm is a MISSING FATAL EXCEPTION, not a missing diagnostic** — GR3 is a general rule, so this is a
run-time behaviour divergence on legal source, which is why `wrong_answer` is flagged rather than
`under_rejects`. The consequence does not stop at the absent declarative: the index is then used to subscript
the table, so a program that would have terminated (or been resumed by a USE declarative) instead reads or writes
at occurrence 0 or below.

I re-ran the three programs above at 2023 on HEAD. The rest of GR3 was measured by the adjudicator and I did not
re-run it: 2002 and 2014 raise identically; at 85 the `>>TURN` directive is itself rejected (`COBOLNET0875`) so
no checking can be enabled, which is correct — the EC machinery is 2002+.

## 4. THE CODE SITE AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Compiler/CodeGen/Verbs/ControlFlowEmitter.cs:348-360` — `InitVaryingTarget`, the
  `lv.From is BoundNumRef` gate
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:392-406` — `BindVaryingLevel`, which
  produces the operand through `ExpressionBinder.BindIndexWindowExpr`
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:382` — the bind-time
  `checkIndexRange` capture
* `src/Cobol.Net.Runtime/Exceptions/ExceptionState.cs#PerformVaryingIndexError` — the runtime `value <= 0` test
* `src/Cobol.Net.Compiler/CodeGen/EcEmitter.cs:151` — the EC-name → `PerformVaryingChecking` ambient-gate row

⛔ **Do not add a second `is` arm.** `lv.From is BoundNumRef || lv.From is BoundIntrinsicCall` closes this case
and leaves the next identifier shape open, which is exactly the failure mode already on display. Follow rule 5:
**stop asking the node's C# type and ask the rule's question** — "is the FROM operand an IDENTIFIER (as opposed
to a literal or an index-name)?" — a property the BINDER knows and the emitter is currently re-deriving badly.
Carry it on `VaryingLevel` as an operand-KIND (literal | index-name | identifier), set once where the operand is
bound, and the emitter's guard becomes `lv.FromKind is Identifier`. That makes the NEXT identifier shape
automatic, and it is the only version that can be covered by a drift test asserting the kind for each operand
shape.

## 5. THE SIBLING SWEEP

* ⛔ **Every other guard keyed on `is BoundNumRef` (or any bound-node type test) where the spec says
  "identifier".** This is the pattern, not the instance. Grep `src/Cobol.Net.Compiler/CodeGen/` for `is Bound…`
  in a condition that decides whether a SPEC-mandated check is emitted; each is a place where one legal operand
  shape escapes.
* **The BY/augment sites are correctly out of GR3 scope** (the rule governs FROM initialization only), but the
  same operand-kind question is asked there by **PB432**'s SR4/SR5 screens — one kind field serves both.
* **Every EC whose enablement is captured at BIND time and whose raise site is emitted conditionally.** GR3's
  `checkIndexRange` capture is the F10/V3 template; if a guard can be skipped by an operand's node shape here, it
  can elsewhere.
* **The out-of-line spelling.** `PERFORM p VARYING IX FROM FUNCTION …` takes the same `BindVaryingLevel` and the
  same `InitVaryingTarget`, so it inherits the hole; confirm it in the same commit.
* **Note the adjacent OPEN note PB215** asks a DIFFERENT question about the same FROM slot (an index DATA item
  admitted where §13.18.60.3 SR10 does not name the context) and does not cover this. Do not merge them, but a
  fixer touching `BindVaryingLevel`'s operand handling should read both.

## 6. ROWS

* `GR-14.9.28.4-3` — PARTIAL. The rule is implemented END-TO-END and correctly NARROW: an index-name VARYING
  FROM a data item holding 0 or -1 raises the fatal EC and is caught by a USE declarative; a positive item does
  not; a LITERAL FROM and a DATA-ITEM induction variable are correctly out of scope; an AFTER-level index-name is
  checked; a SUBSCRIPTED identifier FROM is checked (measured above); and the AFTER level's RE-INITIALIZATION on
  a later outer augment is checked, so the rule's "at the time … is used to initialize" covers EVERY
  initialization, not only the first. The GAP is the function-identifier FROM operand, measured above.
