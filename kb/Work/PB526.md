# PB526

## Mechanism — linage-clause
linage-ec-is-a-clr-throw

### Expected, from the standard
'If the value does not conform to these two rules, the EC-I-O-LINAGE exception condition is set to exist. If execution continues after processing of this exception condition, it continues with the statement following the WRITE statement; the LINAGE-COUNTER is set to 0 and remains at that value until the file is closed; and all subsequent WRITE statements referencing the file cause the EC-I-O-LINAGE exception condition to continue to exist until the file is closed.' For p18_use.cob that means: the WRITE sets EC-I-O-LINAGE, the USE AFTER STANDARD ERROR declarative for LPF is entered, and on its return execution resumes at the DISPLAY following the WRITE with LINAGE-COUNTER holding 0 and holding it until CLOSE, every later WRITE re-raising.

### Observed
Every one of the six programs ends in an unhandled .NET System.InvalidOperationException and a process kill - at OPEN for the first four, inside AdvanceLinageCounter for the last two. p18_use.cob is the decisive one: the declarative NEVER FIRES (no `USE-FIRED` line is printed), nothing after the WRITE executes, and FILE STATUS is never set - so the single path on which the standard's 'if execution continues' branch is reachable is closed, and with it the entire second half of GR6. LINAGE-COUNTER is never set to 0; there are no 'subsequent WRITE statements' to keep raising. The connector's own comment (:123-125) is candid that this is debt - 'the EC subsystem is a later slice, so the seam fails LOUD (COBOLNET_DESIGN 1.4), never a silent bad page model' - and the loud-over-silent choice was the right one for the seam; what makes it a defect rather than a staged gap is that the EC subsystem now EXISTS (ExceptionCatalog.cs:118 carries EC-I-O-LINAGE with its fatality) and this one raiser was never rewired to it, so a GREEN tree hides an unreachable rule. Note the asymmetry the throw also creates: at OPEN OUTPUT a fatal EC with no handler does terminate the run unit, so the OBSERVABLE outcome there is defensible by accident; at a WRITE it is not, because GR6 spells out a resumable continuation. Fix: route EvaluateLinage's two value rules through the EC subsystem, add the file-connector latch (LINAGE-COUNTER pinned at 0 until CLOSE, every later WRITE re-raising) that GR6 requires, and pin it with a golden that has a USE AFTER STANDARD ERROR declarative and asserts BOTH the declarative firing and the statement after the WRITE running.

## Landed — 2026-09-13

**The exception condition is an exception condition.** `SequentialConnector.EvaluateLinage` no longer throws
`System.InvalidOperationException`; it returns whether the operand values conform to §13.18.34.4 GR6 b)'s two
value rules, and a violation reports an unsuccessful I-O status **'90'** together with the exception-name GR6 b) 2
NAMES (`FileConnector.SetIoCondition`). The RAISE goes through the ONE EC-I-O channel every other I-O condition
already uses — the emitted `__IoCheckEc` hook after the verb — which owns the USE format-1 and format-3 tiers, the
exception-checking PERFORM frames and the fatal default. No new raise channel was created.

**Why a status, and why '90'.** EC-I-O-LINAGE is Fatal (Table 13) and §14.6.13.1.3 3) routes a fatal EC-I-O
condition through §9.1.13's rules, which are rules about the I-O status; without one the whole §9.1.12 /
§14.9.49.4 GR6 path is closed to a program that writes no `>>TURN`, which at `--std 85` is every program.
§9.1.13.2–§9.1.13.10 enumerate every other class's values and none of them is this condition, so §9.1.13.11's
implementor-defined `9x` is the slot — and '9' is a fatal first digit under this implementation's own
determination, matching Table 13. The determination is `docs/CONFORMANCE.md` §7 **DOC-A.1-110** (newly claimed,
`audit_annex_a1.py --check` ok). ⚖ The surveyed GnuCOBOL value '57' is NOT followed: it is in a nonfatal class and
its first digit raises EC-I-O-RECORD-OPERATION under §9.1.13.1 — the wrong condition, in the wrong fatality.

**The name travels beside the status.** §9.1.13.1's status→EC correspondence has no entry for EC-I-O-LINAGE and
reads a '9x' as EC-I-O-IMP; §14.6.13.1.1's *"Unless otherwise specified, if more than one exception is detected
during the execution of a statement, the one that is set to exist is undefined"* is the licence for the specific
rule to win. `FileConnector.IoConditionName` carries the named condition (cleared by the ONE `Status` setter, so
it cannot outlive its operation), `FileRegistry.IoConditionName` is the one place the named condition and the
correspondence are combined, and the generated hook reads it instead of calling `IoEcOfStatus` itself.
`ExceptionCatalog.IoMaskNames` gained EC-I-O-LINAGE (append-only) so `>>TURN EC-I-O-LINAGE CHECKING ON` reaches a
statement's mask.

**All three consequences of GR6 b) 2's closing sentence are realized.** Execution continues with the statement
following the WRITE; LINAGE-COUNTER is set to 0 and remains there until the file is closed; and every subsequent
WRITE re-reports the condition (`_linagePageBroken`, a bit SEPARATE from `HasLogicalPage` — read off the zeroed
page model, every later write would take the no-LINAGE print-stream arm and succeed). The connector stays OPEN at
an OPEN-time violation, because "until the file is closed" and "all subsequent WRITE statements referencing the
file" both presuppose it; `EndLinagePage` clears the latch at CLOSE.

**Folded in: PB525.** The same evaluator, the same rule. GR6 b) 2's lower bound could not be enforced while 0
encoded "the FOOTING phrase is absent", so the two are one mechanism and were fixed together — see PB525's own
Landed paragraph.

**Swept.** `grep -rn "throw new InvalidOperationException" src/Cobol.Net.Runtime/ | grep -i "EC-"` now returns
nothing: this was the only raw CLR throw in the runtime naming an exception condition. Both WRITE entry points
carry the latch (a plain WRITE on a LINE SEQUENTIAL LINAGE file does not route through `WriteAdvancing` — the
two-arm shape that bit PB523), measured on a LINE SEQUENTIAL probe. A sibling defect found and fixed with it:
`SequentialIoEmitter.EmitWrite` ran the AT / NOT AT END-OF-PAGE branches unguarded by the write's success, against
§14.9.51.4 GR27 ("the WRITE statement is successful") and GR28 ("during the successful execution"), so the NOT arm
fired on every unsuccessful write of a LINAGE file ('48', '71', and now '90').
