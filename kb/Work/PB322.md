## Why one note

Each entry is an element the standard makes the IMPLEMENTOR's to decide and **required** to document, where
COBOL.NET has a de-facto behaviour, no §7 determination, and — in three cases — a written claim that contradicts
the code. That is one mechanism: a rule delegating to the implementor is discharged by writing the answer down
ONCE and implementing it, and none of these was.

## The determinations

**A. File sharing — the default mode when unspecified.** Annex A.1 item 77 and item 131 both make it required
and documented, citing §9.1.3, §9.1.15 and §14.9.27.4 GR23. Nothing appears in `docs/CONFORMANCE.md` outside the
A.4.7 *Claimed* row. The one place a default IS written down states a choice the code does not implement:
`docs/PHASE4_RECONCILIATION.md:1523` records *our documented choice = default sharing NO OTHER (exclusive,
record locks ignored per GR3)*, while `FileSupport.cs`'s own summary says the opposite (*the implementor default
... is outside the sharing subsystem entirely*). Observable: two plain connectors on one physical file both open
'00', and an OPEN OUTPUT over an open connector reports '30' — an OS sharing violation leaking into the I-O
status — where the PHASE4 choice makes both '61'. **PB321's fix cannot be written until this is settled.**

⛔ **`GR-14.9.27.4-23` is THIS note's row as of 2026-09-05** (it moved here from PB316). GR23 has three
sentences and PB316 landed the first two — the SHARING phrase now overrides only the file control entry of the
file-names in ITS OWN repeated group, and a group carrying no phrase keeps the file control entry's sharing
instead of a sibling group's override. The THIRD sentence is determination A above and is all that keeps the
row defective: no sharing mode is *established* for a connector with neither clause nor phrase — it is left
outside the sharing subsystem rather than placed in one of §9.1.15's three modes — so `OPEN INPUT` then
`OPEN OUTPUT` on one physical file answers '30' where every one of the three modes gives Table 19's '61'
(re-probed 2026-09-05). ⚠ Landing A must re-derive the first two lines of
`tests/conformance/2002/pb316_open_group_scope.out`: its retry-scope halves observe a connector with no
SHARING clause, so establishing a real default changes what that connector arbitrates against. The GR20
EQUALITY the golden asserts survives either way; the literal statuses do not.

**B. Which devices allow concurrent access** — A.1 items 52 and 76, the predicate §14.9.27.4 GR21's
*shareable* rests on. Absent.

**C. Deadlock detection and the retry parameters.** §9.1.13.8 item 2 (*the implementor shall specify under what
conditions a deadlock is detected*) plus §14.7.9.3 GR1/GR2 (the retry interval; m, n, the maximum meaningful
timeout; the retry-frequency technique). `OPEN ... RETRY FOREVER` / `FOR n SECONDS` answers '52', which
§9.1.13.8 item 2 licenses only against a SPECIFIED deadlock condition — and which re-routes the raised exception
from EC-I-O-FILE-SHARING to EC-I-O-RECORD-OPERATION under §9.1.13.1's first-digit map. Absent. (The
zero/negative arm of the same machinery is a behavioural defect: **PB346**.)

**D. OPEN OUTPUT and physical page boundaries** — A.1 item 130. §14.9.27.4 GR18's second half says *the
positioning of the output medium with respect to physical page boundaries is implementor-defined* (`--check
14.9.27.4` → **OK**). A behaviour exists (a LINAGE file gets `EvaluateLinage()` + `LinageCounter = 1` at OPEN
OUTPUT completion per §13.18.34 GR6b1/GR7d; a non-LINAGE file starts at stream offset 0) and is nowhere
DEFINED. GR18's first half — the file is created and contains no records — is verified and conformant.

**E. The action after a USE procedure when the I-O status is a fatal EC-I-O condition** — A.1 item 218, and this
one is worse than undocumented: **it is two different behaviours selected by a directive the rule does not
mention.** §14.9.49.4 GR7 c) and GR12 c) both key on the I-O STATUS VALUE — *the implementor determines what
action is taken as described in 9.1.13* (`--check 14.9.49.4` → **OK**) — not on whether checking is enabled.
Measured on the same status '35' and the same declarative shape: with no `>>TURN`, execution continues and
`AFTER-OPEN FS=35` prints (`probe/gr7-handler-end/p2.cob`); with `>>TURN EC-I-O CHECKING ON`, the run unit
terminates abnormally (`probe/gr3-gr5-tiers/p1.cob`). The two branches live in different generated hooks —
`EcEmitter.cs#EmitIoCheckEc` ends with `if (__en && ExceptionCatalog.IsFatalIoStatus(__st)) throw new
CobolFatalException(...)`, while the plain `__IoCheck` (`DispatchEmitter.cs#EmitUseMachinery`) has no fatal arm
at all. `docs/CONFORMANCE.md` carries no A.1 item 218 row.

**F. The implied RECORD clause of a sort-merge description entry.** With no RECORD clause the implicit clause is
implementor-defined (§13.18.43.4 GR5), and if format 1 is implied the size is *the record size of the largest
record description entry in this file description entry* (`--check 13.18.43.4` → **OK**) — the fixed-length sort
file §14.9.40 GR7 presupposes. `SortBinder.BindRelease` instead releases at record-name-1's OWN description size
(`SortBinder.cs:238-240` + `BoundSort.cs:71`), so an SD with `01 SRT-SHORT PIC X(4)` and `01 SRT-LONG PIC X(10)`
and no RECORD clause holds a 4-byte and a 10-byte record for ONE SD, and `SORT ... GIVING` writes a 4-character
record into a `PIC X(10)` FD record (`probe/ref-gr6/w.cob`). That MAY be legitimate latitude — GR5 also lets the
implementor imply format 2, under which 4 bytes is in range and §14.9.32.4 GR6 is vacuous — but the choice is
nowhere DECLARED, and the two comments defending it cite §14.9.40 GR7, a rule about file-name-2 (the USING
file), not about a RELEASE in an input procedure. That mis-citation is **PB320** item 6.

Row `GR-14.9.32.4-6` (Annex A.2 item 45: the bytes a RELEASE sends past the end of record-name-1 are undefined) is
the SD twin of PB1907 D-WRT1 (WRITE/REWRITE send the record area's content past record-name-1, ISO length). The one
predicate `FileModel.TransfersPastRecord` and the image helper `SequentialIoEmitter.SentRecordImage` are reusable,
but `SortBinder.BindRelease` releases at record-name-1's OWN size, and what size a multi-01 SD with no RECORD
clause releases is determination **F** above (A.1 item 147, the implied RECORD clause of a sort-merge file). Decide F
first, then apply D-WRT1's rule. Code site: `src/Cobol.Net.Compiler/CodeGen/Verbs/SortEmitter.cs` `EmitRelease`
(~line 534). Repro: an SD with 01s of 4 and 10 bytes and no RECORD clause; fill the long record, RELEASE the short
one, RETURN it and display the 10 bytes.
