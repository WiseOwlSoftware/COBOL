# PB4046 — the adopt self-test's restart scenario fails intermittently in CI, and says nothing about why

**Sites:** `scripts/orchestrator/test_orchestrate_adopt.ps1` (scenario 4, `Run-Orch 'adoptrestart'`),
`scripts/orchestrator/adopt_main.py#_decide`, `scripts/orchestrator/orchestrate.ps1` (the adoption and restart path)

**What happened.** The merge-group run 40918334805 of PR #755 (fuzz night 8 notes: kb/Work, FUZZ-LEDGER.md,
docs/fuzz-ledger, conformance-suite/fuzz-history.json, a DEVLOG file; no script changed) failed `Windows script
self-tests` on this one test:

```
FAIL: restart: the supervisor says it restarts: got 'False', want 'True'
FAIL: restart: the adopted checkout supervisor ran: got 'False', want 'True'
FAIL: restart: it was handed the arguments: got 'False', want 'True'
FAIL: restart: and the counters: got 'False', want 'True'
FAIL: restart: the operator steer stays on disk for the successor: got 'False', want 'True'
FAIL: restart: no unit ran in the predecessor: got '1', want '0'
FAIL: restart: the checkout is origin/main: got '07a2da5…', want '720a173…'
orchestrate self-test (adopt): 14/21 checks OK
```

Scenarios 1 to 3 passed in the same run. In scenario 4 the checkout stayed on the old commit and the unit ran, so
`_decide` returned `KEPT`. Its `kept` reasons are: fetch failed, the ref is missing, ahead, diverged, the wrong branch, a
dirty tree, or CI not `success` under the fake gh. The test drops `$r.out`, so the reason is lost. The same file passed
21/21 locally on 2026-10-29, and in merge-group run 40910800033 (PR #754) an hour earlier.

**Why it matters.** It breaks THE CI INVARIANT: CI failed where the local gate (which reused this self-test's recorded
PASS, PB2914) saw nothing. A notes-only landing bounced on it.

**Fix.** First make the failure say why: on any failed check, print the run's adoption line (`adopt main: …`) and the
tail of `$r.out`. Then find the race. Candidates are a tracked file the scenario-3 run leaves modified, which would be
"dirty" in scenario 4, and the fake gh's answer when `FAKE_GH_JSON` is switched between runs. Fix that at its root,
and run the test repeatedly on a Windows runner to show it holds.

## Second witness (2026-10-29 18:5x PDT): PR #791, merge-group run 40987962746

`worktree-wf_484eb705-564-32` (#791) left the queue on the same test, Windows script self-tests. This time scenario 3 failed
as well, `red: kept, with the reason: got 'False', want 'True'`, with the seven restart checks of scenario 4 (13/21). So
`_decide` KEPT for a reason other than "not stable yet" in scenario 3, and again in scenario 4, the checkout staying at
60a9e7992 while origin/main was 8772436fc. Reported by the Mythos lane (mailbox 19:07).

## Ruled out (operator, 2026-10-29)

- **Automatic maintenance racing the fetch** (the Mythos lane's candidate): `self_tests.py` runs every self-test with
  `GIT_CONFIG_GLOBAL` naming a private config that holds `NO_AUTO_MAINTENANCE` (`self_tests.py` lines 302 and 564), and
  orchestrate.ps1, adopt_main.py and their git inherit it. In CI no git process of this test starts maintenance. A hand run
  outside the runner does, which is PB4083's, not this flake's.
- **The impact-map recorder in the checkout**: `impact_lane.request` returns "no recorder in this checkout" at once for the
  scratch repository, which has no recorder script, so no worker runs beside the next scenario.
- **A git warning read as a modified file**: `adopt_main._git` adds stderr to the output only when git FAILS, so a warning
  from `git status --porcelain` (a CRLF note under the runner's `core.autocrlf`) cannot reach `tracked_changes`.
- **Not reproduced locally**: six runs in a row on this host, 21/21 each.

What is left: a tracked file really modified in the checkout (the candidate above), a FAILED git command there (`fetch`
or `status`), or a branch or ancestry reading. A failed `status` reads as "N tracked file(s) are modified", since
`tracked_changes` returns git's message as its one entry, so even that reason line has to be read in full. And a path
that prints NO `adopt main:` line at all (review R1-1): the supervisor's `main not adopted (...)`, when adopt_main.py fails
as a process OR WRITES ANYTHING TO STDERR. Both witnesses fit it (scenario 3's expected line missing, scenario 4's checkout
not moved), and it is the defect below.

## Step 1 landed: the failure says why

`testdata/orchestrate_test_lib.ps1` keeps each run's output (`$script:lastRun`), and a failed `Check` quotes the lines of it
that match the part's `$script:Evidence`. `test_orchestrate_adopt.ps1` names `adopt main:|main not adopted|wrote to
stderr`, so the next failure prints the supervisor's own outcome and reason, for example `[run 'adoptwarn': ... main not
adopted (the loop continues on the checkout as it is): Conversion from JSON failed ...]`.

## A defect found on the way, fixed: the supervisor parsed a tool's stderr as its JSON answer

`orchestrate.ps1#Invoke-Py` ran `& $Python @ArgList 2>&1` and returned stdout and stderr TOGETHER, which its callers parse
as JSON (adopt_main.py's answer, budget.py's, next_unit.py's). One line on stderr from a tool that SUCCEEDED (a Python
warning, a child's diagnostic) made the answer unreadable. For the adoption that means "main not adopted", the unit runs
on the old checkout, and the loop goes on. The startup's `account.py` and `work.py next` reads did the same by hand. Now
`Invoke-Py` splits the streams: stdout is the answer, and stderr is said ("python X wrote to stderr (said, not parsed):
...") and never parsed. A failing tool throws with both streams. The two startup reads go through it. Test: adopt scenario 5 plants a stderr line from
adopt_main.py through `testdata/fake-python.ps1` (`FAKE_PYTHON_STDERR`). The adoption still happens and the line is said:
24/24. On main's supervisor the same scenario fails with "main not adopted ... Conversion from JSON failed" (22/24).
Siblings outside the supervisor (`start-session.ps1`, `account-profile.ps1`, `autostart.ps1`) are PB4084.

Whether a stray stderr line was what failed CI's two runs is not proven: nothing in them was printed. This note stays open
until a failure's evidence line names the cause, or until enough merge-group runs pass to retire it with that count.
