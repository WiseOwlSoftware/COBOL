# PB4046 — the adopt self-test's restart scenario fails intermittently in CI, and says nothing about why

**Sites:** `scripts/orchestrator/test_orchestrate_adopt.ps1` (scenario 4, `Run-Orch 'adoptrestart'`),
`scripts/orchestrator/adopt_main.py#_decide`, `scripts/orchestrator/orchestrate.ps1` (the adoption and restart path;
`Step-Lane`, `Invoke-AdoptMain`), `scripts/orchestrator/land_lane.py#survey_rows`

**What happened.** The merge-group run 40918334805 of PR #755 (fuzz night 8 notes: kb/Work, FUZZ-LEDGER.md,
docs/fuzz-ledger, conformance-suite/fuzz-history.json, a DEVLOG file; no script changed) failed `Windows script
self-tests` on this one test:

```
FAIL: restart: the supervisor says it restarts: got 'False', want 'True'
FAIL: restart: the adopted checkout supervisor ran: got 'False', want 'True'
FAIL: restart: it was handed the arguments: got 'False', want 'True'
FAIL: restart: and the counters: got 'False', want 'True'
FAIL: restart: the operator steer stays on disk for the successor: got 'False', want 'True'
FAIL: restart: no unit ran in the predecessor: got '1', want '0'
FAIL: restart: the checkout is origin/main: got '07a2da5…', want '720a173…'
orchestrate self-test (adopt): 14/21 checks OK
```

Scenarios 1 to 3 passed in the same run. In scenario 4 the checkout stayed on the old commit and the unit ran, so
`_decide` returned `KEPT`. Its `kept` reasons are: fetch failed, the ref is missing, ahead, diverged, the wrong branch, a
dirty tree, or CI not `success` under the fake gh. The test drops `$r.out`, so the reason is lost. The same file passed
21/21 locally on 2026-10-29, and in merge-group run 40910800033 (PR #754) an hour earlier.

**Why it matters.** It breaks THE CI INVARIANT: CI failed where the local gate (which reused this self-test's recorded
PASS, PB2914) saw nothing. A notes-only landing bounced on it.

**Fix.** First make the failure say why: on any failed check, print the run's adoption line (`adopt main: …`) and the
tail of `$r.out`. Then find the race. Candidates are a tracked file the scenario-3 run leaves modified, which would be
"dirty" in scenario 4, and the fake gh's answer when `FAKE_GH_JSON` is switched between runs. Fix that at its root,
and run the test repeatedly on a Windows runner to show it holds.

## Ruled out (operator, 2026-10-29)

- **Automatic maintenance racing the fetch** (the Mythos lane's candidate): `self_tests.py` runs every self-test with
  `GIT_CONFIG_GLOBAL` naming a private config that holds `NO_AUTO_MAINTENANCE` (`self_tests.py` lines 302 and 564), and
  orchestrate.ps1, adopt_main.py and their git inherit it. In CI no git process of this test starts maintenance. A hand run
  outside the runner does, which is PB4083's, not this flake's.
- **The impact-map recorder in the checkout**: `impact_lane.request` returns "no recorder in this checkout" at once for the
  scratch repository, which has no recorder script, so no worker runs beside the next scenario.
- **A git warning read as a modified file**: `adopt_main._git` adds stderr to the output only when git FAILS, so a warning
  from `git status --porcelain` (a CRLF note under the runner's `core.autocrlf`) cannot reach `tracked_changes`.
- **Not reproduced locally**: six runs in a row on this host, 21/21 each.

What is left: a tracked file really modified in the checkout (the candidate above), a FAILED git command there (`fetch`
or `status`), or a branch or ancestry reading. A failed `status` reads as "N tracked file(s) are modified", since
`tracked_changes` returns git's message as its one entry, so even that reason line has to be read in full. And a path
that prints NO `adopt main:` line at all (review R1-1): the supervisor's `main not adopted (...)`, when adopt_main.py fails
as a process OR (until the fix below) wrote anything to stderr. The stderr arm cannot explain the witnesses' scenario 4:
adopt_main.py fast-forwards the checkout before it answers, so on that arm the checkout MOVES and only the supervisor's
answer and restart are lost (review R2-1), while both witnesses kept the old commit. A process failure of adopt_main.py
(non-zero exit) would fit both scenarios, and the evidence line now names it.

## Step 1 landed: the failure says why

`testdata/orchestrate_test_lib.ps1` keeps each run's output (`$script:lastRun`), and a failed `Check` quotes the lines of it
that match the part's `$script:Evidence`. `test_orchestrate_adopt.ps1` names `adopt main:|main not adopted|wrote to
stderr`, so the next failure prints the supervisor's own outcome and reason, for example `[run 'adoptrestart': ... adopt
main: kept ...: <the reason>]`, or `[run 'adoptrestart': ... main not adopted (the loop continues on the checkout as it
is): python ... failed (N): <adopt_main.py's own output>]` when the tool itself failed. (A successful adopt_main.py whose
answer cannot be read says `adopt main: adopt_main.py's answer is unreadable (...)`, review R3-1.)

## A defect found on the way, fixed: the supervisor parsed a tool's stderr as its JSON answer

`orchestrate.ps1#Invoke-Py` ran `& $Python @ArgList 2>&1` and returned stdout and stderr TOGETHER, which its callers parse
as JSON (adopt_main.py's answer, budget.py's, next_unit.py's). One line on stderr from a tool that SUCCEEDED (a Python
warning, a child's diagnostic) made the answer unreadable. adopt_main.py had already fast-forwarded the checkout, so for
the adoption that meant a false "main not adopted" and NO RESTART when the landing changed the supervisor's own script:
the loop ran its next unit on the old supervisor code. The startup's `account.py` and `work.py next` reads did the same by
hand. Now `Invoke-Py` splits the streams: stdout is the answer, and stderr is said ("python X wrote to stderr (said, not
parsed): ...") and never parsed. A failing tool throws with both streams. The two startup reads go through it.
`Invoke-AdoptMain` says an unreadable answer from a successful adopt_main.py as such ("the checkout may have moved"),
never as "main not adopted" (review R2-4). Test: adopt scenario 5 lands a change to the supervisor's own script and plants
a stderr line from adopt_main.py through `testdata/fake-python.ps1` (`FAKE_PYTHON_STDERR`): the line is said and the
supervisor still restarts from the adopted checkout. On main's supervisor the restart checks fail (review R2-2).
Siblings outside the supervisor (`start-session.ps1`, `account-profile.ps1`, `autostart.ps1`, `session-probe.ps1`) are PB4084.

This fix is not CI's flake: in both witnesses scenario 4's checkout stayed on the old commit, which this path does not do.
The race below is.

## Root cause found (2026-10-30, the finisher of PR #791's bounce)

Source: the PB3797 finisher's report (PR #791 removed from the merge queue, failed_checks, 2026-10-30T02:03:15Z; merge-group run
40987962746, `Windows script self-tests`: `test_orchestrate_adopt.ps1: RED`, 13/21, case 3 "red: kept, with the reason" and every
case-4 restart check). The red is already on main, nondeterministic, and not that branch's: it passed 21/21 on the branch and on
origin/main eced2608b locally, and the re-queued PR's merge-group run 40990733301 ran it GREEN in 43.1 s.

**The race.** `orchestrate.ps1`'s main loop calls `Step-Lane` (about line 727), which starts `land_lane.py tick --repo <checkout>`
IN THE BACKGROUND, and at once calls `Invoke-AdoptMain` (about line 733). `land_lane.survey_rows` (about line 559) runs
`git fetch -q origin` and `adopt_main._decide` (about line 182) runs `git fetch --quiet origin main`, in the same checkout, so
they race on `refs/remotes/origin/main`. The loser fails with `error: cannot lock ref 'refs/remotes/origin/main': is at X but
expected Y`. Adopt then says `kept ... origin/main could not be fetched` (no adoption, no restart, the unit runs on the stale
checkout), or the lane says `land lane: no survey, nothing launched`.

**Reproduced.** With a `gh` that fails at once on PATH (CI's step has no GH_TOKEN, so its gh fails fast), concurrent runs gave
CI's exact 13/21 pattern on the branch and a 17/21 failure (case 2 losing the same race) on origin/main.

**Why it is green locally.** An authenticated gh makes `queue_facts.read` (two real GitHub calls) delay the lane's fetch by 1-3 s,
so adopt wins by a wide margin and the local gate passes. The self-test is not hermetic: it reaches the real GitHub. That is the
CI invariant's gap.

**Fix shape (the finisher's).** One owner per fetch of the loop checkout: the supervisor adopts BEFORE `Step-Lane` and waits on
(`Complete-LaneTick`) any tick still running from a previous period, or both fetches take one coord lock. For the CI-invariant half,
make the self-test hermetic: hand `land_lane.py tick` the test's fake gh (a `--gh` seam like adopt_main's, passed from `-GhExe`), or
put a fake on PATH in `testdata/orchestrate_test_lib.ps1` `Run-Orch`, so local and CI time the race alike. Then a test that holds
the lane's fetch open while adopt runs.

**In production** a lost race skips one adoption (a landed supervisor fix waits a unit) or one lane tick (a landing waits a period).

## Fixed (operator, 2026-10-29, at the owner's request: "fix PB4046 too")

Two changes, each removing one half of the race. A third makes the self-test see what CI sees.
- **No shared ref to race on.** `adopt_main.py#_decide` fetches origin's main into `FETCH_REF`, `refs/adopt-main/main`, a ref
  only it writes: `git fetch --quiet --no-tags --refmap= --no-write-fetch-head origin +refs/heads/main:refs/adopt-main/main`.
  `--refmap=` turns off git's opportunistic update of `refs/remotes/origin/main`, and `--no-write-fetch-head` leaves the
  checkout's FETCH_HEAD alone. So no fetch elsewhere in the repository, whether a landing, a finisher, another session or
  the lane's survey, can fail the adoption's fetch. Every worktree shares `refs/remotes/origin/main`, so the race was never
  only the supervisor's own.
- **Adopt before the tick, never beside one.** `orchestrate.ps1`'s loop runs `Invoke-AdoptMain` BEFORE `Step-Lane`. The new
  `Wait-LaneTick` waits up to 120 s for a tick still running from the unit; one that outlasts it defers the adoption to the
  next iteration (`adopt main: deferred: ...`). This also keeps the tick's survey (`git status` in each worktree) off the
  checkout while it fast-forwards.
- **Hermetic self-tests.** `testdata/orchestrate_test_lib.ps1#Run-Orch` puts a `gh` that fails at once first on every
  supervisor run's PATH, as on CI. A case that needs GitHub's answers passes its own fake (`-GhExe`).
- Tests, with no timing in their verdicts:
  - `test_adopt_main.py` section 10 lands a commit and then holds `refs/remotes/origin/main.lock`, what a concurrent fetch
    holds. The adoption must still go through and write neither that ref nor FETCH_HEAD. On main's adopt_main it fails with
    CI's own message: `origin/main could not be fetched (error: cannot lock ref 'refs/remotes/origin/main' ...)`.
  - `test_orchestrate_adopt.ps1` scenario 6 runs a four-second fake tick (`FAKE_PYTHON_TICK_SECONDS`) and requires that no
    adoption interval overlap a tick's. `testdata/fake-python.ps1` writes both intervals to `fake-python-timeline.txt`,
    and a tick the run outlives counts as open-ended. It passes 29/29 here and 28/29 on main's supervisor.
  - All 15 `test_orchestrate_*.ps1` parts pass.
- Docs: `DESIGN-orchestrator-loop.md` §4.10 and adopt_main.py's module docstring say both rules.
- The lane's survey still fetches into the shared ref, which it needs: LANDED is read against `origin/main`. A collision there
  with a fetch in another worktree costs one tick period, and the lane says so ("no survey, nothing launched"), as before;
  the supervisor no longer causes one.
