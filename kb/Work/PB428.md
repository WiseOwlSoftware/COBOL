# PB428 — the sending-operand designation is right; one of the shapes it designates cannot be written

## The mechanism

SR3 designates literal-1 and the data item referenced by identifier-1 as MOVE's sending operands, so the row's
surface is EVERY literal-1 and EVERY identifier-1 the language admits in that position. §8.4.3.1.2 gives
identifier ELEVEN general formats. Ten of them are accounted for: Formats 5, 6, 8 and 9 (object-view,
predefined-object, predefined-address, address-identifier) are class object or pointer and are excluded by
§14.9.25.3 SR1; Formats 1, 2, 3, 10 and 11 (function-identifier, qualified-data-name-with-subscripts,
reference-modification, qualified LINAGE-COUNTER, qualified report counter) are all reachable through the
grammar's `dataReference` / `functionCall` arms of `moveSendingOperand` and were measured working. **Format 4,
inline-method-invocation, cannot be written at all.**

Reading the tree on HEAD makes the mechanism sharper than "it is a statement rule, not an operand rule". §8.4.3.4.2
prints the construct as `{object-class-name-1 | identifier-1} :: literal-1 [ ( arguments ) ]`, with `::` and the
parentheses as required punctuation. **`::` HAS NO LEXER TOKEN.** The only occurrence of the sequence anywhere in
`src/Cobol.Net.Frontend/Grammar/` is a passing mention in a lexer comment
(`Core/CobolLexer.g4:903`). And the rule that carries the construct's NAME —
`src/Cobol.Net.Frontend/Grammar/Core/CobolOO.g4:194` —

```antlr
inlineMethodInvocationStatement
    : dataReference LPAREN argumentList? RPAREN
    ;
```

has no `::` and no method literal; it is a different shape wearing the name, dispatched at
`CobolParserCore.g4:701` under `{is2023()}?` as a STATEMENT alternative only. So the position argument understates
it: the construct is absent from the accepted language in EVERY position, and there is nothing to lift into
`moveSendingOperand`. A `ConstructRegistry` row `inline-method-invocation-2023` and a `FlagConformancePass`
visitor (`src/Cobol.Net.Compiler/Validation/FlagConformancePass.cs:214`) already exist for the misnamed shape.

An inline method invocation is unambiguously a legal identifier-1 for MOVE: §8.4.3.4.3 SR1 restricts it only from
the RECEIVING side, and §8.4.3.4.4 GR1 gives it the class and category of the invoked method's RETURNING item, so
a method returning an alphanumeric item is not touched by SR1's class prohibition either. §8.4.3.4.2's general
format (rendered above from `specs/ISO_COBOL.md`) is the shape that must parse.

This is not someone else's optional module: `docs/CONFORMANCE.md:861` records for A.4.10 that "the OO CORE is
mandatory surface, claimed separately", with only the three A.4.10 OPTIONAL items unclaimed (CLASS-ID multiple
inheritance, parametric polymorphism — and item 2 IS supported).

## The code sites and the shape of the repair

- `src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4` — no `::` token (only the comment at :903).
- `src/Cobol.Net.Frontend/Grammar/Core/CobolOO.g4:194` — `inlineMethodInvocationStatement`, the misnamed rule.
- `src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4:701` — its statement-only dispatch under `{is2023()}?`;
  `:1010-1014` — `moveSendingOperand`, the three arms that would need the fourth.
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/MoveBinder.cs:37-42` — where the fourth arm would bind;
  `src/Cobol.Net.Compiler/Binding/Bound/BoundTree.cs#BoundMove` — the Source every downstream sender-side rule
  reads.

**MODEL IT AS AN IDENTIFIER, NOT AS A MOVE ARM** (CLAUDE.md rule 5). §8.4.3.1.2 makes inline method invocation one
of eleven IDENTIFIER formats, so the repair is: add the `::` token; write
`inlineMethodInvocation : (className | dataReference) COLONCOLON literal (LPAREN argumentList? RPAREN)?` per
§8.4.3.4.2; make it an ALTERNATIVE OF THE IDENTIFIER/OPERAND rule rather than of `statement`, so every statement
that admits identifier-1 gets it at once; and let the existing `inlineMethodInvocationStatement` become a
statement wrapper around it (or be deleted, if the standard has no such statement — check §14.9 before keeping
it). Grammar changes are pre-authorized. A per-verb arm bolted onto `moveSendingOperand` would leave the same
hole in DISPLAY, the arithmetic verbs, the relation conditions and every other identifier context — which is
precisely the shape this note is about.
⚠ Binding it needs §8.4.3.4.4 GR1's temp-identifier semantics (the invocation's class and category come from the
method's RETURNING parameter) and §8.4.3.4.3 SR1's receiving-side prohibition, which must then hold by a CHECK
rather than by the construct's absence.

## The sibling sweep the fixer must do

- Every statement and condition whose operands are "identifier-N", i.e. every one of the eleven §8.4.3.1.2
  formats in every operand position. The audit worth running once is mechanical: for each of the eleven formats,
  a probe in a sending position and (where legal) a receiving position of MOVE, DISPLAY, the arithmetic verbs,
  IF, EVALUATE, STRING/UNSTRING, INSPECT and CALL USING. Format 4 is the one measured missing here; the sweep is
  what shows whether it is the only one.
- ⚠ The b2 refuter reached the same conclusion by a different route ("the grammar carries
  `inlineMethodInvocationStatement` … as a STATEMENT only") and supported it by pointing at the grammar's Wave-H
  comment ten lines away as calling this "a live non-conformance". **That comment is about a different thing** —
  it governs the MCS RECEIVE/SEND, VALIDATE, COMMIT and ROLLBACK facility arms below it, not inline method
  invocation. The conclusion stands on the spec and on the measurement above; the comment is not evidence for it,
  and the sweep should not go looking for other Wave-H arms on the strength of that sentence.


## Landed — 2026-09-19 (wave 39)

RE-PROBED FIRST on this worktree's own build: the note's repro still held verbatim (`MOVE OBJ :: "ADDTO" (AMT)
TO R` → four raw `COBOL0001`/`COBOL0307` errors naming a colon, no named diagnostic anywhere), and the two
mechanism claims held too — `::` had no lexer rule, and `inlineMethodInvocationStatement` matched
`dataReference ( argumentList )` as a STATEMENT.

**The general format was RENDERED, not read from the transcription** (`scripts/render-spec-page.py 163`, printed
folio 133). The PDF confirms the §8.4.3.4.2 figure exactly as `specs/ISO_COBOL.md` carries it: `::` and the
parentheses are required punctuation, `OMITTED` is the only underlined word, the OUTER bracket makes the whole
parenthesised argument list optional, and the `…` repeats the brace group INSIDE the single pair.

**The fix, at the three places the rule belongs.**

1. **Lexer** — `COLONCOLON : '::' ;` (§8.7.4 "The invocation operator is the two contiguous COBOL characters
   '::'"; §8.3.5 rule 7 "The COBOL character colon, EXCEPT AS PART OF THE INVOCATION OPERATOR, is a separator"
   is what makes the two characters one lexical unit). §8.7.4's separator-space sentence is not enforced at the
   token level, the same posture `AMPERSAND` already takes for §8.7.3's identical sentence.
2. **Grammar** — `inlineMethodInvocation : objectReference inlineInvocationSegment+ refModPart*` with
   `inlineInvocationSegment : COLONCOLON literal (LPAREN argumentList? RPAREN)?`, in `Core/CobolOO.g4`. The
   receiver is INVOKE's OWN `objectReference` rule, so SELF/SUPER and a class-name arrive for free and NULL
   arrives too and is rejected by name (the P3 superset parse). The segment REPEATS because §8.4.3.1.3 SR1
   defines identifier recursively. `refModPart*` is §8.4.3.1.4 GR1 g). `argument` was rewritten to the printed
   five forms — OMITTED and boolean-expression-1 had no surface at all. The misnamed
   `inlineMethodInvocationStatement` and its statement dispatch are DELETED: §14.9's roster has no such
   statement, and §8.4.3.4 sits in §8.4.3 *Identifiers*.
3. **Binder** — ONE activation mechanism. `InvocationSite` / `InvocationArg` (`OoBinder.InlineInvocation.cs`)
   abstract what the §14.9.23 binder reads off a statement, so `OoBindByReceiver`, `OoBindInstanceInvoke`,
   `OoBindClassInvoke`, `OoBindResolvedInvoke` and `OoBindInvocationArg` are shared verbatim between the two
   syntaxes — which is what §8.4.3.4.4 GR1 requires, since it DEFINES the inline form as one of four INVOKE
   statements and §8.4.3.4.3 SR3 requires that INVOKE to be valid under §14.9.23. The inline binder adds exactly
   two things: `OoCreateInvocationTemp` (GR1 b)'s clone of the method's own RETURNING item — an IDENTITY
   crossing, so §14.8.3.3 has nothing to check) and registration on `DataBinder.PendingPreOps`, the ONE
   statement-scoped pre-op list the user-function activation already uses. The expression is a `BoundNumRef`
   over the temp, the same carrier a UDF result takes.

**THE POSITION ARGUMENT WAS ANSWERED STRUCTURALLY, NOT PER-VERB.** The note called for an alternative of "the
identifier/operand rule". This grammar has no single identifier rule and CANNOT get one before PHASE 15 CUT 2:
`ArithmeticSendingOperandDriftTests` records that the frozen legacy compiler reads `.dataReference()` /
`.literal()` / `.functionCall()` off these contexts BY NAME, so collapsing or aliasing them breaks its build —
which is exactly why identifier Format 1 (`functionCall`) is ALREADY written per-site. Putting Format 4 inside
`dataReference` would have been a SECOND mechanism for "an identifier format that is not a data-name
reference", and would have made every existing `dataReference` consumer silently treat `O :: "M"` as `O`. So
Format 4 went where Format 1 goes — twenty operand rules — and the pairing was made MECHANICAL instead of
hand-maintained: `InlineMethodInvocationOperandDriftTests` asserts over the .g4 text that every rule admitting
`functionCall` admits `inlineMethodInvocation`, that no RECEIVING rule admits either, and that the rule still
matches the printed general format. §8.4.3.4.3 SR1 therefore holds STRUCTURALLY, exactly as §8.4.3.2.3 SR1
does for a function-identifier — a correction to the note's "must then hold by a CHECK", made for the reason
above rather than for convenience.

**A sibling found by the sweep and fixed here**: an inline invocation used as a METHOD ARGUMENT parsed into
`arithmeticExpression` and was bound as an expression, so §14.8.2.3.3 rule 2a's COMPUTE lane refused an
alphanumeric-returning invocation into a `PIC X` formal — legal source, rejected. It is recovered as an
IDENTIFIER through `ConditionBinder.SoleInlineInvocation`, the fourth member of the existing sole-operand
family. It stays BY CONTENT, and that is GR6 a)2 rather than convenience: GR1 c)'s temporary is not "a data
item defined in the file, working-storage, local-storage, or linkage section", so §14.9.23.3 SR9 is not met.

**Edition**: 2002, on RECOGNITION. The registry row `inline-method-invocation-2023` is REPLACED by
`inline-method-invocation-2002`; the old row's own recorded reason for staying `pending` was that
`identifier(args)` "has NO distinctive token", which was true of the shape it described and false of the real
construct. The edge is DERIVED, not quoted (the repo holds no 2002 or 2014 text): §A.4.10 lists exactly three
OPTIONAL object-orientation elements and inline invocation is not among them; Annex E itemizes the 2014→2023
delta and does not list it; §8.4.3.4.4 GR1 defines it as the equivalent INVOKE statement, itself a 2002
introduction. Plan §Step 0-W item (1) predicted the same edge independently.

**Diagnostics**: COBOLNET2138 (§8.4.3.4.3 SR2 — NULL or universal receiver), COBOLNET2139 (§8.4.3.4.4 GR1 b) /
§14.8.3.1 — the method declares no RETURNING item), COBOLNET2140 (§8.4.3.4.3 SR4 — ANY LENGTH / ACTIVE-CLASS
RETURNING). The SR4 golden takes the ACTIVE-CLASS arm deliberately: an ANY LENGTH RETURNING item is staged loud
at COBOLNET0899 before any invocation binds, so an ANY LENGTH fixture would pin the STAGE and leave SR4's own
arm unverified.
