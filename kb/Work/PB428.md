# PB428 — the sending-operand designation is right; one of the shapes it designates cannot be written

## The mechanism

SR3 designates literal-1 and the data item referenced by identifier-1 as MOVE's sending operands, so the row's
surface is EVERY literal-1 and EVERY identifier-1 the language admits in that position. §8.4.3.1.2 gives
identifier ELEVEN general formats. Ten of them are accounted for: Formats 5, 6, 8 and 9 (object-view,
predefined-object, predefined-address, address-identifier) are class object or pointer and are excluded by
§14.9.25.3 SR1; Formats 1, 2, 3, 10 and 11 (function-identifier, qualified-data-name-with-subscripts,
reference-modification, qualified LINAGE-COUNTER, qualified report counter) are all reachable through the
grammar's `dataReference` / `functionCall` arms of `moveSendingOperand` and were measured working. **Format 4,
inline-method-invocation, cannot be written at all.**

Reading the tree on HEAD makes the mechanism sharper than "it is a statement rule, not an operand rule". §8.4.3.4.2
prints the construct as `{object-class-name-1 | identifier-1} :: literal-1 [ ( arguments ) ]`, with `::` and the
parentheses as required punctuation. **`::` HAS NO LEXER TOKEN.** The only occurrence of the sequence anywhere in
`src/Cobol.Net.Frontend/Grammar/` is a passing mention in a lexer comment
(`Core/CobolLexer.g4:903`). And the rule that carries the construct's NAME —
`src/Cobol.Net.Frontend/Grammar/Core/CobolOO.g4:194` —

```antlr
inlineMethodInvocationStatement
    : dataReference LPAREN argumentList? RPAREN
    ;
```

has no `::` and no method literal; it is a different shape wearing the name, dispatched at
`CobolParserCore.g4:701` under `{is2023()}?` as a STATEMENT alternative only. So the position argument understates
it: the construct is absent from the accepted language in EVERY position, and there is nothing to lift into
`moveSendingOperand`. A `ConstructRegistry` row `inline-method-invocation-2023` and a `FlagConformancePass`
visitor (`src/Cobol.Net.Compiler/Validation/FlagConformancePass.cs:214`) already exist for the misnamed shape.

           specification of the method identified by literal-1 and either identifier-1 or object-class-name-1;

An inline method invocation is unambiguously a legal identifier-1 for MOVE: §8.4.3.4.3 SR1 restricts it only from
the RECEIVING side, and §8.4.3.4.4 GR1 gives it the class and category of the invoked method's RETURNING item, so
a method returning an alphanumeric item is not touched by SR1's class prohibition either. §8.4.3.4.2's general
format (rendered above from `specs/ISO_COBOL.md`) is the shape that must parse.

This is not someone else's optional module: `docs/CONFORMANCE.md:861` records for A.4.10 that "the OO CORE is
mandatory surface, claimed separately", with only the three A.4.10 OPTIONAL items unclaimed (CLASS-ID multiple
inheritance, parametric polymorphism — and item 2 IS supported).

EXPECTED: accepted, the method invoked, its RETURNING item moved to W. OBSERVED: three raw ANTLR errors naming a
colon — not a named diagnostic, not a staged loud, and no mention of methods or of the edition. The lexer stops
at the first `:` because `::` is not a token, which is why the message is about punctuation rather than about a
construct.

## The code sites and the shape of the repair

- `src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4` — no `::` token (only the comment at :903).
- `src/Cobol.Net.Frontend/Grammar/Core/CobolOO.g4:194` — `inlineMethodInvocationStatement`, the misnamed rule.
- `src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4:701` — its statement-only dispatch under `{is2023()}?`;
  `:1010-1014` — `moveSendingOperand`, the three arms that would need the fourth.
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/MoveBinder.cs:37-42` — where the fourth arm would bind;
  `src/Cobol.Net.Compiler/Binding/Bound/BoundTree.cs#BoundMove` — the Source every downstream sender-side rule
  reads.

**MODEL IT AS AN IDENTIFIER, NOT AS A MOVE ARM** (CLAUDE.md rule 5). §8.4.3.1.2 makes inline method invocation one
of eleven IDENTIFIER formats, so the repair is: add the `::` token; write
`inlineMethodInvocation : (className | dataReference) COLONCOLON literal (LPAREN argumentList? RPAREN)?` per
§8.4.3.4.2; make it an ALTERNATIVE OF THE IDENTIFIER/OPERAND rule rather than of `statement`, so every statement
that admits identifier-1 gets it at once; and let the existing `inlineMethodInvocationStatement` become a
statement wrapper around it (or be deleted, if the standard has no such statement — check §14.9 before keeping
it). Grammar changes are pre-authorized. A per-verb arm bolted onto `moveSendingOperand` would leave the same
hole in DISPLAY, the arithmetic verbs, the relation conditions and every other identifier context — which is
precisely the shape this note is about.
⚠ Binding it needs §8.4.3.4.4 GR1's temp-identifier semantics (the invocation's class and category come from the
method's RETURNING parameter) and §8.4.3.4.3 SR1's receiving-side prohibition, which must then hold by a CHECK
rather than by the construct's absence.

## The sibling sweep the fixer must do

- Every statement and condition whose operands are "identifier-N", i.e. every one of the eleven §8.4.3.1.2
  formats in every operand position. The audit worth running once is mechanical: for each of the eleven formats,
  a probe in a sending position and (where legal) a receiving position of MOVE, DISPLAY, the arithmetic verbs,
  IF, EVALUATE, STRING/UNSTRING, INSPECT and CALL USING. Format 4 is the one measured missing here; the sweep is
  what shows whether it is the only one.
- ⚠ The b2 refuter reached the same conclusion by a different route ("the grammar carries
  `inlineMethodInvocationStatement` … as a STATEMENT only") and supported it by pointing at the grammar's Wave-H
  comment ten lines away as calling this "a live non-conformance". **That comment is about a different thing** —
  it governs the MCS RECEIVE/SEND, VALIDATE, COMMIT and ROLLBACK facility arms below it, not inline method
  invocation. The conclusion stands on the spec and on the measurement above; the comment is not evidence for it,
  and the sweep should not go looking for other Wave-H arms on the strength of that sentence.
