# PB263 — the CALL argument lane has its own literal rendering, and it cannot carry a float literal

Found by the SIBLING SWEEP of owner decision D-B (the arithmetic wave, 2026-08-31), which asked where else a
floating-point literal is rendered. **Pre-existing at HEAD `6cd228b6` — D-B neither caused nor fixed it.**

## Measured, 2026-08-31, at HEAD and again after D-B (identical both times)

```cobol
CALL "P5T" AS NESTED USING BY CONTENT 1.5E+3 BY REFERENCE R2
```

```
error: backend compilation failed (generated C# at pdb5.g.cs):
  (43,144): error CS1503: Argument 1: cannot convert from 'double' to 'long'
```

and with a wider literal, the Int128 carrier arm:

```cobol
CALL "P4T" AS NESTED USING BY CONTENT 1.2345678901234567890123E+3 BY REFERENCE R2
```

```
  (47,146): error CS1503: Argument 1: cannot convert from 'double' to 'System.Int128'
```

**BOTH carrier arms fail, so the defect is universal**: any floating-point literal, of any width, passed
BY CONTENT to a CALL. There is no workaround short of introducing a data item.

## The site and the root cause

`src/Cobol.Net.Compiler/CodeGen/Verbs/CallEmitter.cs`, the `case BoundNumericLiteral n:` arm of the argument
builder:

```csharp
var lit = UnscaledLit(n.Text);
int digits = n.Text.Count(char.IsAsciiDigit);
string cellT = lit.U ? "UInt128" : digits > 18 ? "Int128" : "long";
return $"new CobolArg({...}, ManagedPointer<{cellT}>.Cell({lit.Expr}), {digits}, {lit.Scale})";
```

`EmitText.UnscaledLit` returns `new NumX(t, 0, Real: true)` — the literal's own text as a C# `double` literal —
for any E-form literal, so `lit.Expr` is `1.5E+3` and the cell type is chosen from a DIGIT COUNT that also
miscounts (the exponent's digits are counted as significand digits: `"1.5E+3"` yields 3).

⛔ **The root cause is not the cast — it is that the CALL argument lane carries a SECOND literal rendering.**
`NumericRenderer.LiteralNum` is THE literal → `NumX` mapping (since D-B, one rendering for every position and
every arithmetic mode); this arm reaches past it to the raw `UnscaledLit` helper and then re-derives a carrier
and a scale of its own. That is [[feedback_one_rule_one_place]] in its usual shape, and it is why D-B's own
statement — "the literal is its exact §8.3.3.3.3 rule-5 value everywhere" — has an exception here.

## Fix shape (NOT implemented in the arithmetic wave — a different subsystem, §14.9.4 argument conformance)

Give `CallEmitter` ONE numeric-argument funnel used by BOTH the `BoundNumericLiteral` arm and the
`BoundComputedOperand` arm (which has its own, differently-broken, defect — [[PB264]]): render the operand
through `NumericRenderer`, land it once, and choose the carrier from the resulting `NumX` (`U` → `UInt128`,
`Dec`/wide → `Int128`, else `long`) rather than from a digit count taken off the source text. Two arms, one
rule — and the drift test that belongs with it is the one asking whether any emitter still calls
`EmitText.UnscaledLit` on operand text instead of going through the renderer (`OoEmitter.cs:838`, the INVOKE
argument path, is the third such site and has not been measured yet).

Goldens owed: a positive 2023 case passing a float literal BY CONTENT and BY VALUE and displaying what the
callee received, plus the wide fixed-point literal of [[PB264]] in the same program so the two arms are pinned
side by side.
