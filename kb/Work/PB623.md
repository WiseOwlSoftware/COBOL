# PB623 — LANDED — the value that fits gets the inexact landing

Found 2026-09-05 by the `PB253` implementer (report §"New defects" (1)), which fixed the STANDARD-mode container
ordering and measured that the NATIVE channels split the same way for a different reason; verified UNCHANGED by
PB253's landing (the native path is untouched there). Re-derived on its worktree at `f94507d9`.

## Repro (`--std 2014`, NO OPTIONS paragraph — native arithmetic)

```cobol
       01 NEAR-PI PIC S9V9(30) VALUE 1.570796326794896619231321691639.
       01 R       PIC S9(28)V9(2).
       ...
           MOVE FUNCTION TAN(NEAR-PI) TO R
           DISPLAY "MV " R                     *> 16331239353195368.96
           COMPUTE R = FUNCTION TAN(NEAR-PI)
           DISPLAY "CP " R                     *> 16331239353195369.92
```

The returned binary64 is exactly 16331239353195370 (shortest round-trip `1.633123935319537E+16`; ULP 2 at that
magnitude, so an exactly representable even integer — confirmed by the STANDARD-DECIMAL run, whose identity
conversion yields 16331239353195370.00). The exact value at scale 2 is 16331239353195370.00, so BOTH native channels
are wrong: the MOVE by 1.04, the COMPUTE by 0.08. `FUNCTION RANDOM(7)` shows the same split at ordinary magnitudes:
0.3832204692918902784 (MOVE) against 0.38322046929189024 (COMPUTE).

## The rule

§15.4: "The evaluation of a function produces a returned value in a temporary elementary data item" (`OK §15.4`) —
ONE value. §15.4.1: "the returned value is the same for all instances of a given function within a single execution
of the runtime element so long as the value and order of the arguments, the collating sequence, and the locale are
unchanged" (`OK §15.4.1`) — two stores of one returned value cannot differ. §15.4.1's native latitude is over "the
characteristics and representation of the returned value", not over two different transfers of one representation
into one receiver. The MOVE transfer itself is §14.6.8.2 r4: "the data is aligned by decimal point and is
transferred to the receiving digits with zero fill or truncation on either end" — truncation of the VALUE, not of a
rounded surrogate for it.

## The mechanism

`src/Cobol.Net.Runtime/Values/Numeric/CobolFloat.cs` — `ToScaled` (`:148`) and `ToScaledUnchecked` (`:168`) both
compute `double scaled = v * Pow10.AsDouble(scale)` BEFORE rounding; once `|v| × 10^scale` exceeds 2⁵³ the product
is itself rounded, and the two entry points then round it differently. The exact path already exists in the same
file: `LowOrderDigits` (`:188`) expands the binary64 exactly over `BigInteger` — and it is reached ONLY when the
product falls outside the Int128 carrier. The arms are inverted: the value that FITS gets the inexact landing, the
value that does not gets the exact one. `LowOrderDigits`'s own doc comment already says it is "Correct for EVERY
finite double, so a determination that lands the exact expansion inside the carrier as well needs only the caller's
carrier test removed".

## Fix shape

One landing for a binary64 into a scaled Int128, exact for every finite double: route both entry points through the
exact expansion, with a hot-path guard that keeps the native multiply ONLY where it is provably exact (`|v| × 10^scale
< 2⁵³` and `scale` within the exactly-representable powers of ten) — a guard stated as a predicate with its bound,
not a magnitude guess. The two entry points then differ only in the sentinel check `ToScaled` performs, which is
their documented difference. Goldens under native at 2002/2014/2023: the TAN and RANDOM programs above asserting
MOVE = COMPUTE = the exact expansion (PB253's standard-mode goldens are the model; their invariant legs transfer
unchanged to native), plus a drift test that `ToScaled` and `ToScaledUnchecked` agree with `LowOrderDigits` over a
sweep of magnitudes straddling 2⁵³ and the carrier bound. Sweep the other consumers of `ToScaled*` (the MOVE
sender path, the float-receiver relation path) for the same split before closing.

**The mechanism was three copies of one wrong sentence, not one.** `CobolFloat.ToScaled`, `ToScaledUnchecked` and
`CobolIntrinsics.FromDouble` each formed `v * Pow10.AsDouble(scale)` in binary64 and rounded THAT. Two consequences
the note named — past 2^53 the product is a rounded surrogate, and the two channels land at different scales (the
MOVE at the receiver's, the arithmetic channel at a working scale it then rescales from), so one returned value
became two receiver contents. A third the note did not name: `Pow10.AsDouble(-2)` falls out of the table into a
loop that runs zero times and returns **1**, so a trailing-P receiver (`PIC 9(9)PP`, scale −2) landed a value 10^2
too large and the store then truncated it to zeros. A fourth sibling, same sentence: `InexactAtScale` asked the
ROUNDED MODE PROHIBITED question of the same product — `0.1 * 10.0` is exactly 1.0 in binary64, so a value with 55
fraction digits was reported representable in one, a gate saying "exact" over a landing that then truncates 54
digits away.

**The fix is one landing, `CobolFloat.TryExactScaled(v, scale, mode, out landed)`.** A finite double is ±man·2^exp
exactly (`Decompose`, trailing zero bits shifted into the exponent so man is odd), so
v·10^scale = ±man·5^scale·2^(exp+scale): ONE `Int128` multiply by `Pow10.FiveAsWide(scale)` — 10^n's odd cofactor,
a new table replacing the deleted `double` view — and one shift when exp+scale ≥ 0, else one `CobolNum.RoundDiv`.
The fast path's bound is a proof, not a magnitude guess: man < 2^53 and 5^31 < 2^72 put the product below
2^125 < 2^127 for every scale ≤ 31, which covers every PICTURE fraction (§13.18.40.3 rule 14 — "the number of digit
positions described by character-string-1 shall range from 1 through 31", cite.py-verified). A wider scale, a
negative one, or a magnitude past the carrier takes the same expansion over `BigInteger` (`ExactRatio` →
`ExactScaled`), and `LowOrderDigits` is now that same function taken modulo 10^38 — so "past the carrier" changes
only WHICH digits survive, never WHAT the value is. `ToScaled` (saturate) and `ToScaledUnchecked` (low-order
digits) keep their PB77 forms and differ ONLY there; `CobolIntrinsics.FromDouble` calls the same landing with its
own working-scale mode. `RoundScaled` and `NearestTowardZero` are deleted — `RoundDiv` is the one rounding kernel —
and `Pow10.AsDouble` with them, since it had no other caller.

**Spec basis, re-derived and mechanically checked, not inherited.** §14.6.8.2 rule 1 — "If the sending operand is
an intermediate data item or a data item described with a standard floating-point usage, the value is treated as if
it had been converted to a fixed-point value" (`OK §14.6.8.2 1)`) — is the rule with NO latitude, and it is what
the FLOAT-BINARY-64 and returned-value cases run on; rule 4 then truncates ("aligned by decimal point and is
transferred to the receiving digits with zero fill or truncation on either end", `OK §14.6.8.2 4)`). Rule 2 —
"the implementor defines the manner in which the value is converted to a fixed-point value" (`OK §14.6.8.2 2)`) —
is the FLOAT-SHORT/-LONG/-EXTENDED latitude, and it takes the SAME conversion here because `COMPUTE r = c2` lands
through a rule-1 intermediate, so any other manner would re-split MOVE from COMPUTE. §15.4.1's "the returned value
is the same for all instances of a given function within a single execution of the runtime element so long as the
value and order of the arguments, the collating sequence, and the locale are unchanged" (`OK §15.4.1`) is what the
split violated. The PROHIBITED gate is §14.7.4.3 item 7 (`OK §14.7.4.3 7)`), **not §14.7.5 r7** — the tree carried
that inherited clause number at four sites (`CobolFloat` ×2, `ArithmeticEmitter`, `RuntimeApi`) and all four are
corrected; §14.7.5 is the SIZE ERROR phrase, §14.7.4.3 the ROUNDED phrase's per-mode general rules. The design doc
had it right all along, which is how the drift was visible.

**It answered [[PB90]]**, which asked whether the in-carrier manner should be the exact expansion, the shortest
round-trip decimal, or the rounded product, and reserved the choice for a GnuCOBOL survey. No `cobc` exists in this
environment (PB90 said so too), and the survey is no longer decisive: rule 1 has no latitude for a standard-float
sender, and applying anything else under rule 2 would put `MOVE c2 TO r` and `COMPUTE r = c2` back into
disagreement. PB90 is closed by that derivation and the CONFORMANCE.md §3 bullet now states the manner.

**Owner-visible consequence, surfaced rather than buried:** `MOVE <COMP-2 8.2> TO PIC 9V9` now stores **8.1**, not
8.2 — the double nearest 8.2 is 8.199999999999999289457264239899814128875732421875 and the transfer truncates. Both
channels agree, `ROUNDED` still gives 8.2, and that is what rule 1 + rule 4 say; PB90 called this option (a)
"user-hostile" and it is, but the alternative is a value that no reading of "the value" supports.
