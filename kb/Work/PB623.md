# PB623 — OPEN — the value that fits gets the inexact landing

Found 2026-09-05 by the `PB253` implementer (report §"New defects" (1)), which fixed the STANDARD-mode container
ordering and measured that the NATIVE channels split the same way for a different reason; verified UNCHANGED by
PB253's landing (the native path is untouched there). Re-derived on its worktree at `f94507d9`.

## Repro (`--std 2014`, NO OPTIONS paragraph — native arithmetic)

```cobol
       01 NEAR-PI PIC S9V9(30) VALUE 1.570796326794896619231321691639.
       01 R       PIC S9(28)V9(2).
       ...
           MOVE FUNCTION TAN(NEAR-PI) TO R
           DISPLAY "MV " R                     *> 16331239353195368.96
           COMPUTE R = FUNCTION TAN(NEAR-PI)
           DISPLAY "CP " R                     *> 16331239353195369.92
```

The returned binary64 is exactly 16331239353195370 (shortest round-trip `1.633123935319537E+16`; ULP 2 at that
magnitude, so an exactly representable even integer — confirmed by the STANDARD-DECIMAL run, whose identity
conversion yields 16331239353195370.00). The exact value at scale 2 is 16331239353195370.00, so BOTH native channels
are wrong: the MOVE by 1.04, the COMPUTE by 0.08. `FUNCTION RANDOM(7)` shows the same split at ordinary magnitudes:
0.3832204692918902784 (MOVE) against 0.38322046929189024 (COMPUTE).

## The rule

§15.4: "The evaluation of a function produces a returned value in a temporary elementary data item" (`OK §15.4`) —
ONE value. §15.4.1: "the returned value is the same for all instances of a given function within a single execution
of the runtime element so long as the value and order of the arguments, the collating sequence, and the locale are
unchanged" (`OK §15.4.1`) — two stores of one returned value cannot differ. §15.4.1's native latitude is over "the
characteristics and representation of the returned value", not over two different transfers of one representation
into one receiver. The MOVE transfer itself is §14.6.8.2 r4: "the data is aligned by decimal point and is
transferred to the receiving digits with zero fill or truncation on either end" — truncation of the VALUE, not of a
rounded surrogate for it.

## The mechanism

`src/Cobol.Net.Runtime/Values/Numeric/CobolFloat.cs` — `ToScaled` (`:148`) and `ToScaledUnchecked` (`:168`) both
compute `double scaled = v * Pow10.AsDouble(scale)` BEFORE rounding; once `|v| × 10^scale` exceeds 2⁵³ the product
is itself rounded, and the two entry points then round it differently. The exact path already exists in the same
file: `LowOrderDigits` (`:188`) expands the binary64 exactly over `BigInteger` — and it is reached ONLY when the
product falls outside the Int128 carrier. The arms are inverted: the value that FITS gets the inexact landing, the
value that does not gets the exact one. `LowOrderDigits`'s own doc comment already says it is "Correct for EVERY
finite double, so a determination that lands the exact expansion inside the carrier as well needs only the caller's
carrier test removed".

## Fix shape

One landing for a binary64 into a scaled Int128, exact for every finite double: route both entry points through the
exact expansion, with a hot-path guard that keeps the native multiply ONLY where it is provably exact (`|v| × 10^scale
< 2⁵³` and `scale` within the exactly-representable powers of ten) — a guard stated as a predicate with its bound,
not a magnitude guess. The two entry points then differ only in the sentinel check `ToScaled` performs, which is
their documented difference. Goldens under native at 2002/2014/2023: the TAN and RANDOM programs above asserting
MOVE = COMPUTE = the exact expansion (PB253's standard-mode goldens are the model; their invariant legs transfer
unchanged to native), plus a drift test that `ToScaled` and `ToScaledUnchecked` agree with `LowOrderDigits` over a
sweep of magnitudes straddling 2⁵³ and the carrier bound. Sweep the other consumers of `ToScaled*` (the MOVE
sender path, the float-receiver relation path) for the same split before closing.
