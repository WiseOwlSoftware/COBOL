# PB756 — OPEN — an undocumented `?` on an UNDERLINED word, beside a documented one on a plain word

Found 2026-09-06 in the PB695 family-3 implementer's report (NEW DEFECT B). Verified independently on main at
`0a24276f`. Sibling of [[PB755]] — same shape, same file, same measurement method, same missing audit.

## What the standard prints — rendered and MEASURED

`python scripts/spec/clause_page.py 12.4.5.6.2` → **PDF page 350, printed folio 320**;
`python scripts/render-spec-page.py 350`. The ALTERNATE RECORD KEY clause's general format:

```
                        ╭ data-name-1                             ╮
ALTERNATE RECORD KEY IS ┤                                         ├
                        ╰ record-key-name-1 SOURCE IS { data-name-2 } … ╯
[ WITH DUPLICATES ] [ SUPPRESS WHEN literal-1 ]
```

Underlines re-measured off the raw vector rectangles as second reader (`--band` dump, no threshold applied):

| word | box (x) | rule under it | cover |
|---|---|---|---|
| `ALTERNATE` | 70.08–128.01 | 71.39–126.94 @ gap 0.98 | **95.9%** |
| **`RECORD`** | **131.86–171.34** | **133.25–170.36 @ gap 0.98** | **94.0% — UNDERLINED** |
| `KEY` | 174.45–193.41 | neither rule overlaps the box | **0.0% — PLAIN** |
| `IS` | 195.74–204.51 | neither rule overlaps the box | **0.0% — PLAIN** |

`python scripts/spec/figure_extract.py 350` agrees independently — *"underlined (REQUIRED per 5.2.2), 5 distinct:
ALTERNATE, DUPLICATES, RECORD, SOURCE, SUPPRESS"* — and so does the transcription's figure note, which
`cite.py --check 12.4.5.6.2 "ALTERNATE RECORD KEY"` returns verbatim: *"`ALTERNATE`, `RECORD`, `SOURCE`,
`DUPLICATES`, and `SUPPRESS` are underlined in the printed standard (required words); `KEY`, `IS`, `WITH`, and
`WHEN` are …"*. Three readings, one answer: **RECORD required, KEY and IS optional.**

- `--check 5.2.2 "They are shown in uppercase and underlined in general formats"` → **OK §5.2.2 (Keywords)**.
- `--check 8.3.2.4.3 "uppercase words that are not underlined are called optional words"` → **OK §8.3.2.4.3**
  — the rule that licenses `KEY?` and `IS?`, and only those.

## What the grammar spells

`src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4:192-196` on main, verbatim — and note it carries **no comment of
its own**:

```
alternateKeyClause
    : ALTERNATE RECORD? KEY? IS? dataReference
      (WITH? DUPLICATES)?
      alternateKeySuppressWhen?
    ;
```

## The asymmetry that makes this more than one `?`

Four lines above it, `recordKeyClause:188-190` carries a long comment (`:178-187`) that documents ITS relaxation
as a deliberate, named, gated dialect leniency:

```
// Leniency L3 (see docs/dialect-strictness.md): ISO §12.4.5.12 requires `RECORD KEY IS data-name`
// (⚠ KEY is NOT required — see below), and the CCVS suite writes `RECORD data-name` without KEY (e.g.
// IX103A `RECORD IX-FS1-KEY`). The grammar parses the permissive superset `RECORD KEY? IS?
// dataReference`; the no-KEY form is accepted in DialectMode.Default and diagnosed under named-strict
// modes by the inline check in SemanticBuilder.VisitFileControlClauseGroup (CBL3615/3616).
```

Three things are true of that comment and all three matter here:

1. **It is about `KEY`, a word the page prints PLAIN** — so L3 is not a leniency at all under §8.3.2.4.3; the
   no-KEY form is conforming source. Nothing in L3 licenses dropping `RECORD`, which the page underlines. The
   `alternateKeyClause` `RECORD?` therefore has NO documentation anywhere, deliberate or otherwise.
2. **`docs/dialect-strictness.md` does not exist.** `find . -name "dialect-strictness*" -not -path "./.claude/*"`
   → nothing. The only copies are inside worktree checkouts. The comment points at a doc the tree does not have.
3. **CBL3615/3616 never fire in this compiler.** `grep -rn "CBL3615\|CBL3616" --include=*.cs src/` returns four
   hits: the two DESCRIPTORS in `src/Cobol.Net.Frontend/Diagnostics/DiagnosticDescriptors.cs:669-672`, and the
   two REPORT sites in `src/CobolSharp.Compiler/Semantics/SemanticBuilder.cs:897-899` — the LEGACY engine, which
   is an opt-in differential oracle slated for deletion at P15. So the named-strict gate the comment promises
   does not exist on the greenfield path for the KEY word either. This is
   `feedback_a_dead_lookup_is_also_unverified`: a descriptor nothing reads has never been contradicted.

## Why it matters

§4.2.10 3) (`--check 4.2.10 "An implementation that introduces additional reserved words as nonstandard
extensions conforms"` → **OK §4.2.10 3) (Nonstandard extensions)**) admits nonstandard latitude only against a
documentation obligation — *"Documentation associated with an implementation shall identify nonstandard
extensions for which support is claimed"* (`--check 4.2.10 "Documentation associated with an implementation
shall identify nonstandard extensions for which support is claimed and shall specify any reserved words added
for nonstandard extensions"` → **OK §4.2.10 3)**). This acceptance is claimed nowhere, gated nowhere and
diagnosed nowhere, so it is not an extension — it is a private dialect. A program written `ALTERNATE KEY IS K`
compiles here and is a syntax error under every other implementation.

## The decision this note asks for, and the fix shape

**This is a defect, not a leniency, unless the owner says otherwise** — no CCVS card is known to write it (the
L3 comment's CCVS evidence, `IX103A RECORD IX-FS1-KEY`, is about the PRIME key clause and about KEY, not about
ALTERNATE's RECORD). Absent a named source demanding it:

```
alternateKeyClause
    : ALTERNATE RECORD KEY? IS? dataReference
      (WITH? DUPLICATES)?
      alternateKeySuppressWhen?
    ;
```

with a negative golden pinning `ALTERNATE KEY IS K` as a syntax error and positives for the printed spellings
(`ALTERNATE RECORD KEY IS K`, `ALTERNATE RECORD K`, `ALTERNATE RECORD KEY K`) so the tightening is proved not to
have eaten one. If the owner instead wants the form kept as a dialect leniency, then it needs what L3 only
claims to have: a descriptor, a `DialectMode` gate on the greenfield path, and a row in a doc that exists.

Either way the L3 comment itself is wrong on main and should be repaired in the same change set — it names a
doc that is absent and a strictness check that lives only in the engine being deleted.
