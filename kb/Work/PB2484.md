# PB2484 — OPEN

Filed 2026-10-07 by the train-1035 lander from the wave-1033 group A implementer report (`w1033a-PB833-report.md`,
new lead 1). PB833 landed in that train with the cross-run-unit file lock on Windows (mandatory share modes plus the
OUTPUT host probe) and on Linux (open-file-description region locks); macOS was left without one and documented as
such in `docs/CONFORMANCE.md` DOC-A.1-75.

**Shape.** `src/Cobol.Net.Runtime/IO/Sharing/OfdRegionLocks.cs#AbiMatches` admits only Linux on x86-64/arm64, so
`OfdRegionLocks.Open` returns null on Darwin and `RunUnitFileLock.Take` answers `Unavailable`; the connector then has
only the file lock its `FileShare` gives, which .NET maps onto one advisory `flock` `LOCK_SH` for every posture but
NO OTHER. §9.1.15 2) — "The sharing with read only mode restricts concurrent access to a physical file through file
connectors other than this one, to input mode" — therefore binds another connector of the same run unit (the
`FileRegistry` Table 19 arbiter) but not another run unit.

**Repro.** `RunUnitFileLockDriftTests.ASecondRunUnitsOpenIsArbitratedByTable19` on a macOS host: the rows where a
READ ONLY or ALL OTHER holder must refuse a writer go red. No CI leg runs macOS, so this is untested here.

**Fix direction.** Darwin's classic `fcntl` locks are owned by the process and dropped when any descriptor of the file
closes (the reason Linux uses OFD locks), and its OFD commands are not public. Candidates: a per-file lock-helper
descriptor kept open for the run unit's life with process-owned `F_SETLK` locks plus in-process reference counting, or
`flock` on a per-column sidecar lock file. Either must keep the Table 19 lookup the one answer (`Table19.Cell`), as
`RunUnitFileLock` does.
