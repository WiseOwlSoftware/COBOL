# PB50 — LANDED — the ZERO the standard names as an arithmetic operand can now be written in a subscript

> ⚙ **FOUND BY [[PB48]]'s PROBE MATRIX, AND MEASURED ON THE PRE-PB48 TREE — pre-existing, not a regression.**

## MEASURED (2026-08-05, reproduced unchanged 2026-08-07)

```
MOVE E(1)        TO T   ✅            MOVE FUNCTION UPPER-CASE("abcdef") (2:3)        TO T  ✅
MOVE E(IX + 0)   TO T   ✅            MOVE FUNCTION UPPER-CASE("abcdef") (ZERO + 2:3) TO T  ⛔ run-time abort
MOVE E(ZERO + 1) TO T   ⛔ run-time abort
```

§8.8.1.1: "An arithmetic expression may be an identifier referencing a numeric data item, a numeric literal,
**the figurative constant ZERO** (ZEROS, ZEROES), …" (`--check`ed). §8.4.2.3.2 makes a subscript an arithmetic
expression, §8.4.3.3.3 SR4 both reference-modification positions. **Legal source, aborting at run time.**

## ⛔ THE ENTRY NAMED A CAUSE THE CODE NO LONGER HAD — and there were TWO real ones

This note's own headline read *"`ReferenceResolver.RenderSegment` is a hand-maintained token-type switch with no
arm for it"*. **That was already false when it was written**: [[PB42]] had widened the switch's `default:` to
route EVERY unrenderable token to the D18 materializer, so no arm was missing. The standing §0 caution — a queue
entry's root cause is a CLAIM, not a fact — for the third time this session.

**CAUSE 1 — the `SUB_IDENTIFIER` arm returned `null` instead of routing to D18.** SUBSCRIPT lexer mode has no
`ZERO` token (`SUB_IDENTIFIER : NAME_BODY`), so the figurative arrives as an ordinary identifier, resolves to no
data item, and that early return was **the one place in the renderer that decided a segment was unrenderable
without asking D18** — contradicting the rule stated ten lines below it in the same function.

**CAUSE 2 — `SubscriptExpressionFragment`, the D18 re-parse itself, did not apply `ZeroTokenRewriter`.** So even
once routed there, the bare `ZERO` could not match `arithmeticExpression`. This note's own "▶ WHAT TO CHECK
FIRST" predicted it exactly ("it does not today … that may be the real reason the route was not taken") — the
prediction was right and the headline was wrong, in the same note.

**Both had to go for either symptom to work.** Fixing one alone changes nothing observable, which is why a
partial fix would have read as "no progress" rather than "half done".

## ⭐ THE SWEEP FOUND A WRONG ANSWER — [[PB54]]

Cause 2 is not local to subscripts. THREE fragment re-parsers hand-assembled the same five steps and **exactly
one applied the rewriter**. The other missing one is `FunctionArgFragment`, where the consequence is worse than
an abort: `MIN(ZERO + 5, 2)` returned **0** while `FUNCTION MIN(ZERO + 5, 2)` returned 2 — silently, for a
spelling §8.4.3.2 SR2 makes the same reference. All three now share `FragmentParse`, where the ZERO decision is
an explicit argument rather than an omission.

## ⚠ RESIDUE OBSERVED, NOT FIXED — an undefined subscript name is a RUN-TIME abort

`E(NOSUCHNAME + 1)` compiles clean and aborts at run time — before this change and after it (verified in both
directions; only the message improved, from the whole reference text to the offending NAME). That is the
wrong-stage family, not this defect: the posture is unchanged, so nothing here made it worse, and a compile-time
"unresolved data-name in a subscript" diagnostic is its own piece of work.

## ▶ PINNED

`pb50_figurative_zero_position_expressions` — 7 assertions: the two controls that always worked, `ZERO`/`ZEROS`
in a subscript, and the figurative in BOTH ref-mod positions (the two symptoms arrive by different routes with
different token types, so neither stands in for the other).
