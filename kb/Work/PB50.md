# PB50 — OPEN — the ZERO the standard names as an arithmetic operand cannot be written in a subscript

> ⚙ **FOUND BY [[PB48]]'s PROBE MATRIX, AND MEASURED ON THE PRE-PB48 TREE — pre-existing, not a regression.**

## MEASURED (2026-08-05)

```
01 TB.  05 E PIC X(4) OCCURS 3 TIMES.
MOVE E(1)        TO T   ✅ "aaaa"
MOVE E(IX + 0)   TO T   ✅ "aaaa"
MOVE E(ZERO + 1) TO T   ⛔ run time: "reference 'E(ZERO + 1)'"

MOVE FUNCTION UPPER-CASE("abcdef") (2:3)        TO T  ✅ "BCD"
MOVE FUNCTION UPPER-CASE("abcdef") (1 + 1:3)    TO T  ✅ "BCD"
MOVE FUNCTION UPPER-CASE("abcdef") (IX + 1:3)   TO T  ✅ "BCD"
MOVE FUNCTION UPPER-CASE("abcdef") (ZERO + 2:3) TO T  ⛔ run time:
                                    "reference modification of FUNCTION UPPER-CASE"
```

The discriminator is the figurative constant and nothing else — literals work, data-name arithmetic works.

## THE SPEC

§8.8.1.1: "An arithmetic expression may be an identifier referencing a numeric data item, a numeric literal,
**the figurative constant ZERO** (ZEROS, ZEROES), …" (`--check`ed). §8.4.2.3.2 makes a subscript an arithmetic
expression and §8.4.3.3.3 SR4 makes both reference-modification positions arithmetic expressions. So both shapes
above are LEGAL SOURCE.

## THE MECHANISM — ONE cause, two symptoms

`ReferenceResolver.RenderSegment` (`ReferenceResolver.cs:809`) renders a subscript/ref-mod segment by walking a
token list through a `switch (t.Type)` with a hand-written arm per token type. **There is no `ZERO` arm and no
`ZERO_ARITH` arm**, so the segment renders as null; `ReadRefMod` then returns null and `IntrinsicBinder.cs:147`
turns that into a `BoundExprError`, i.e. a run-time loud. The subscript symptom reaches the same switch through
`InterpretSubscripts`.

⛔ **THIS IS [[PB42]]'s RULE, RESTATED BY A THIRD CASE.** Plan §0 records the standing answer: "**THE D18 ROUTE IS
NOW THE STANDING ANSWER for any subscript / ref-mod segment the token renderer cannot render** … The gate is
'can the renderer render it', NOT a token list — PB42 is what the list version cost." Here the token LIST *is*
the renderer, so the same failure recurs one layer down. Adding a `ZERO_ARITH` arm would be the small diff and
the wrong one; the question to settle is why this segment does not take the D18 route the way a function-bearing
or compound-scaled segment already does.

## ▶ WHAT TO CHECK FIRST

⚠ The two symptoms arrive with DIFFERENT tokens, and a fix that handles one may miss the other. In
`E(ZERO + 1)` the group is a SUBSCRIPT-mode capture, so the ZERO is never rewritten (it is preceded by
`SUB_LPAREN`) and arrives as `ZERO`; in the DEFAULT-mode ref-mod it is preceded by `LPAREN` and arrives as
`ZERO_ARITH`. **Two token types, one missing arm each** ([[feedback_two_arm_dispatch]]).
⚠ Check `SubscriptExpressionFragment` — the D18 re-parse — for whether it runs `ZeroTokenRewriter` at all. It
does not today, so even the D18 route would see a bare `ZERO` that `arithmeticExpression` cannot match. That may
be the real reason the route was not taken, and it is a second place the figurative is invisible.
⚠ Bare `E(ZERO)` is a separate question from `E(ZERO + 1)`: subscript value 0 violates §8.4.2.3.4, so it is
illegal — but it must be diagnosed, not aborted at run time.
