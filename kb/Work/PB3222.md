**Rule it breaks:** One rule, one place (DESIGN-architecture-review §5.2): the §8.5.2.1 Table 2 class of a data item is answered by IntrinsicArgumentRules.ClassOfItem, whose Usage.Index arm exists because PicInfo.IndexItem carries storage category Numeric; §14.2.2 SR2 admits only class numeric, message-tag, object or pointer.

**Scenario:** ByValueClass (ProcedureHeaderScreen.cs:79-86) tests item.Pic?.Category is Numeric or the pointer/object categories. An index data item carries category Numeric for its storage model, so it passes. Measured with the built cobol (src/Cobol.Net.Cli/bin/Debug/net10.0; ProcedureHeaderScreen.cs identical on main): `LINKAGE SECTION. 01 IX USAGE INDEX. 01 NX PIC X(4). PROCEDURE DIVISION USING BY VALUE IX NX.` reports COBOLNET1553 for NX only; IX, class index per Table 2, binds as a BY VALUE formal (under-rejects). It is the sibling kb/Work PB1418 fixed for the argument side (UdfArgIsValueClass tested Pic.Category == Numeric without excluding Usage.Index) and PB132 fixed for CALL (ParameterConformance.ValueArgumentClass): the header formal side, shared by DataBinder.Linkage.cs:461 and DataBinder.Oo.cs:379, kept its own copy. It also reads the storage Category, not AnalyzedCategory, so a recovery profile is re-diagnosed rather than failing open as ClassOfItem does.
