# PB345 — a legal FD that produces no file connector

**Rows:** `GR-14.9.30.4-6`, `GR-14.9.47.4-2`, `GR-14.9.47.4-3`. Read p4 and unlock found the two arms
independently; it is one mechanism with a fixed arm, a half-fixed arm and an unfixed arm.

## The programs

**Sequential** (`out-b1/probe/gr6norec/gr6norec.cob`): two SELECTs on `gr6.dat` — FOUT with `FD FOUT.` /
`01 OREC PIC X(20).`, and FIN with `FD FIN RECORD CONTAINS 20 CHARACTERS.` and **no record description entry**.
Write one 20-character record through FOUT, CLOSE, then `OPEN INPUT FIN` and `READ FIN INTO BUF`.

**Keyed** (`out-b1/probe/unlock/pa.cob`): `SELECT R1 ... ORGANIZATION IS RELATIVE ACCESS MODE IS RANDOM RELATIVE
KEY IS RK FILE STATUS IS RS.` / `FD R1 RECORD CONTAINS 5 CHARACTERS.` with no record description entry /
`MOVE "ZZ" TO RS. UNLOCK R1. DISPLAY ...`. Siblings measured on the same shape: `a1.cob` (`OPEN I-O R1`),
`a2.cob` (`CLOSE R1`), `a3.cob` (`READ R1 INVALID KEY ...`) and `p9.cob` (the INDEXED twin) all abort
identically.

Both abort: `System.InvalidOperationException: file connector '<unit>::<name>' was never registered — a compiler
defect, not a program error (kb/Work PB140)`, exit 82.

## The rules

> §13.4.5.3 SR3 (FORMATS 1 AND 2): When no record description entries are specified: [a RECORD clause shall be
> specified; WRITE/REWRITE use FILE ... FROM and READ uses INTO]

> §13.4.5.3 SR7: Format 2 is the file description entry for a relative file or an indexed file. For an indexed
> file, one or more record description entries shall be associated with the file description entry.

Both `--check 13.4.5.3` → **OK**. SR3 EXPRESSLY contemplates the shape, and SR7 confines the *one or more*
requirement to INDEXED files, so the RELATIVE case is legal. §13.4.2's general format says the same structurally
and was RENDERED from the canonical PDF (printed p.341 = PDF p.371): the record-description group after
`file-description-entry` is in SQUARE BRACKETS (optional, §5.2.6.2) while the sort-merge arm's is in BRACES
(required, §5.2.6.3, restated as §13.4.6.3 SR2).

> §14.9.30.4 GR6: The execution of a READ statement with the INTO phrase when there are no record description
> entries subordinate to the file description entry proceeds as though there were one record description entry
> describing an alphanumeric group item of the maximum size established by the RECORD clause.

`--check 14.9.30.4` → **OK**. So the sequential program's OPEN succeeds and the READ delivers the 20 characters.
For the keyed program, §14.9.47.4 GR2 + GR3 apply: the connector is not in an open mode, so the UNLOCK updates
the I-O status to '42' per §9.1.13.7 item 2, and `RS` displays as `42`.

## What the compiler does

**Keyed arm — no registration at all.** `KeyedIoEmitter.cs:43`:
`if (file.Records.Count == 0) return;   // a SELECT with no FD - never opened with data (sequential convention)`.
The comment states a premise the standard refutes twice over: an FD with no record description entries is not *a
SELECT with no FD*, and it is legal for Format 2.

**Sequential arm — registered only for report files.** `SequentialIoEmitter.EmitFileRegistration` (lines 77-91)
reaches `if (file.Records.Count == 0)` and then registers only when `file.ReportNames.Count > 0`, with a comment
saying exactly why (*A REPORT FILE legally has no record description (ISO §9.1.22 / §13.18.46) - it MUST still
register, or its OPEN falls through to the keyed registries*). One arm was fixed; the keyed arm was not, and the
sequential arm was fixed for one reason among several.

**A second, independent half on the sequential arm.** `FileModel.AreaRecord` (`FileModel.cs:215`) returns null
when `Records.Count == 0`, and `SequentialIoEmitter.EmitRead` guards BOTH the record-area store
(`if (area is not null) EmitImageInto(...)`) and the implicit INTO move (`if (rd.Into is { } into && area is not
null)`) on it — so repairing registration ALONE would turn the crash into a SILENT no-op, with the READ reporting
'00' and identifier-1 left unchanged.

## The fix shape

**Synthesize the implied record description at BIND time** — an alphanumeric group of the RECORD clause's maximum
size — so `FileModel.AreaRecord` is never null for a non-report FD. Registration, the record-area store and the
INTO move then all fall out automatically instead of each needing its own null arm, and both organizations get
it from one place. The INDEXED variant, which §13.4.5.3 SR7 makes ILLEGAL source, needs the missing compile-time
SR7 screen rather than a runtime abort.

`kb/Work/PB140` is `status: landed` and its body does not cover this: it installed the `Require` chokepoint that
is now firing, which is what surfaced the gap. The UNLOCK entry that is still NOT on that chokepoint — and would
keep the next such bug invisible — is **PB360**.

**Code sites:** `KeyedIoEmitter.cs#EmitRegistration` (line 43) · `SequentialIoEmitter.cs#EmitFileRegistration`
(lines 77-91), `#EmitRead` (lines 357, 367, 374) · `FileModel.cs#AreaRecord` (line 215).

## Landed

**Landed 2026-09-05.** Every shape in this note re-reproduced on the landing tree before anything changed
(`file connector 'GR6NOREC::FIN' / 'PA::R1' / 'IXNOREC::I1' / 'NORECCL::F1' was never registered`), and the fix is
the note's own fix shape, taken whole: **`DataBinder.MaterializeImpliedRecord` materializes §14.9.30.4 GR6's
implied record description at BIND time** — an unnamed level-01 GROUP over one FILLER `PIC X(n)` — as the last act
of binding each file description entry, so `FileModel.AreaRecord` is non-null for every FD that can be opened with
data and registration, the record-area store and the implicit INTO move all fall out of the ordinary path. It is a
GROUP and not an elementary `PIC X(n)` because the difference is observable and GR6 chose: §14.9.25.4 GR4's second
paragraph makes a group sender's MOVE an alphanumeric-to-alphanumeric elementary move, so `READ … INTO` a `PIC 9(5)`
receiver takes the leftmost five bytes, where an elementary alphanumeric sender would instead be an
alphanumeric-to-numeric elementary move of all twenty. The 2023 golden's `R2=00 [12345]` line is what pins the word.

**The record-less arm is now decided ONCE, above the organization split.** It had been asked twice and answered
differently — `SequentialIoEmitter.EmitFileRegistration` registered only a REPORT file and `KeyedIoEmitter`'s
`if (file.Records.Count == 0) return;   // a SELECT with no FD` returned outright — which is why neither
organization produced a connector. The keyed early return is DELETED and the decision moved to
`EmitFileRegistration`'s single loop, above `if (!file.IsSequential)`, where exactly two shapes can now reach it: a
REPORT file (§13.4.5.3 SR8) and a SELECT with no FD at all (§13.4.5.4 GR1, already diagnosed). Both registration
ARMS — `DispatchEmitter.__Activate` and `OoEmitter.EmitFileMembers` — call that one method, so both are fixed by
the one change.

**Two screens, because two rules withdraw §13.4.5.3 SR3's permission and one bounds it.**
`COBOLNET1836` (`record-less-fd-no-record-size`) enforces §13.4.5.3 SR3 a) / §13.18.43.3 SR1, read as GR6 makes it
load-bearing: the RECORD clause must establish a MAXIMUM, so a bare `RECORD IS VARYING` with no `TO` is rejected too
(§13.18.43.4 GR10 refers that case to the largest record DESCRIBED, and none is). `COBOLNET1837`
(`file-description-record-required`) enforces §13.4.5.3 SR7 (INDEXED) and §13.4.6.3 SR2 (sort-merge) — one code,
because they are the same requirement, and the message names the arm.

**A sibling the note had not named: the record-less SD.** §13.4.6.3 SR2 has always forbidden it, and the only
diagnostic it drew was the compiler's OWN deferral warning — COBOLNET1756, *"SORT 'S1' without an SD record — not
implemented"* — followed by a run-unit abort: the compiler announcing a gap of its own for the source's error.
`SortBinder.RecordLessSd` now binds SORT, MERGE and RETURN on such a file to a no-op so the entry's COBOLNET1837 is
the only diagnosis.

**Goldens.** `conformance:2023/pb345_record_less_fd_area` (PB345RA) exercises both organizations in one program —
the sequential GR6 READ INTO into an alphanumeric and into a numeric receiver, the AT END, and the relative
connector's UNLOCK closed (42), READ closed (47), OPEN OUTPUT / CLOSE (00), UNLOCK open (00) and RANDOM READ of a
missing record (23), every value derived in the source's header from §9.1.13.2/.4/.5/.7 — with the COBOL-85 twin
`conformance:85/pb345_record_less_fd_area` (PB345R85, the UNLOCK legs dropped as a 2002 introduction) holding the
rule edition-invariant. Four negatives, each rejecting at all four editions with exactly its own code and nothing
else: `pb345-fd-no-record-clause` and `pb345-fd-varying-no-maximum` (COBOLNET1836), `pb345-indexed-no-record` and
`pb345-sd-no-record` (COBOLNET1837).

**Rows.** `GR-14.9.30.4-6` NOT-IMPLEMENTED → CONFORMS; `GR-14.9.47.4-2` and `GR-14.9.47.4-3` PARTIAL → CONFORMS;
and three rows this fix implements that the note had not claimed — `SR-13.4.5.3-7`, `SR-13.4.6.3-2` and
`SR-13.18.43.3-1`, all GAP → CONFORMS. GAP 2802 → 2796. **`SR-13.4.5.3-3` is deliberately NOT claimed:** this fix
implements its sub-rule a), but sub-rules b) (`WRITE`/`REWRITE` on such a file shall use the `FILE … FROM` phrases)
and c) (`READ` shall use `INTO`) are still unscreened, and b)'s required form is an A.4.13 optional element this
compiler declines. `PB360` stays OPEN and keeps its claim on the two UNLOCK rows: `FileRegistry.Unlock`'s
missing-connector arm is still the pre-PB140 `TryGetValue`-and-return; a legal FD no longer reaches it, which is
exactly why it is now invisible.

**The note's own account held on today's tree in every particular except one**: `MOVE "ZZ" TO RS. UNLOCK R1.`
reproduces only WITH the periods it prints. Written period-less, the UNLOCK statement is swallowed as a further
`MOVE` receiver, because `UNLOCK` sits in the generated `cobolWord` name-slot rule with **no**
`{!reservedHere("UNLOCK")}?` predicate — `tests/version-matrix/cobol-words.json` gives it `nameSlot: true` and no
`reservationGated` flag, unlike COMMIT, CRT, CURSOR, PADDING and ROLLBACK. That is a separate mechanism and is
reported for a note of its own.
