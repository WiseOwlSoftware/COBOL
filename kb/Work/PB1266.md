### Finding occurs-clause-p1 — §13.18.38.3 SR7; §13.18.38.2 (wrong-answer; rows SR-13.18.38.3-7, FMT-13.18.38.2)

**Mechanism.** Two OCCURS-related diagnostics state false facts while correctly failing the compile: an index-name in ADD / CALL USING draws COBOLNET1639 "'IX' is not defined", and a KEY phrase written after INDEXED BY draws COBOL0100 'ASCENDING/DESCENDING KEY clause in OCCURS is not yet supported. Table created without sort key.'

**Repro.** `05 T PIC X OCCURS 3 INDEXED BY IX.` + `ADD 1 TO IX` (out13/probe/occurs-p1/sr7_add.cob) or `CALL "NOSUCH" USING IX` (sr7_call.cob); `05 T PIC 9 OCCURS 3 INDEXED BY IX ASCENDING KEY T.` (fmt_indexed_before_key.cob)

**Expected, from the standard.** The rejections are correct: SR7 admits an index-name only in the five contexts, and §13.18.38.2 puts KEY before INDEXED BY. The message should name the rule broken, as COBOLNET1637 does for DISPLAY/MOVE/COMPUTE/ref-mod.

**Observed.** 1639 claims no declaration gives IX, when INDEXED BY declared it. SetBinder.cs:391 calls this exact message 'false about a name INDEXED BY declared, and it sends the reader hunting a typo', fixed for SET but not for ADD/CALL. COBOL0100 claims the KEY clause is unsupported and that a table was created, which is false on both counts.

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs (ADD/CALL receiving resolution of an index-name); the parser error strategy's OCCURS KEY message
