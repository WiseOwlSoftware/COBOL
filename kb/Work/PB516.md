# PB516

## Mechanism — data-description-entry-p1
The BASED clause's SECTION placement is never asked. BindEntry holds the level test but has no EntrySection; BindEntries holds the section and uses it only for CONSTANT RECORD (13.18.15.3 SR1). So a BASED record under an FD compiles clean.

### Expected, from the standard
13.16.3 SR16 first sentence: 'The BASED clause may be specified only in data description entries in the linkage section, in the working-storage section, and in the local-storage section.' A level-01 BASED entry under a file description entry shall be rejected with a named diagnostic. (The second sentence -- level 1 or 77 -- IS enforced, COBOLNET0881, golden conformance:negative/based-level-05.)

```
$ python scripts/spec/cite.py --check 13.16.3 "The BASED clause may be specified only in data description entries in the linkage section, in the working-storage section, and in the local-..."
  OK  §13.16.3 16)  (Syntax rules)
```

### Observed
Accepted. The three legal sections were probed positive (working-storage sr16_based_ws_ok, local-storage q_based_ls, linkage q_based_lnk), so only the negative is missing. The consequence is a record area the file subsystem allocates and READ/WRITE fill, simultaneously described as an unallocated template whose implicit data-address pointer is NULL until SET ADDRESS / ALLOCATE (13.18.5 / 8.6.5) -- two storage models on one record. The binder's own comment at the 0881 site concedes the gap ('the file-subsystem sweep is a named residue'). BindEntries already passes EntrySection to exactly this purpose for CONSTANT RECORD; the fix is one section screen serving both clauses rather than a second bespoke check.
