## Measured (adjudicator / refuter evidence, verbatim)
### [multiply-statement] F1 non-receiver guard omits inlineMethodInvocation: the arithmetic Format-1 'receivers only' screen enumerates literal and functionCall but not the PB428 inlineMethodInvocation arm, so an inline method invocation written as a Format-1 receiver is silently DROPPED (MULTIPLY/ADD/SUBTRACT compile clean) or crashes the compiler (DIVIDE)
- **Rows:** FMT-14.9.26.2 — harm `silent`
- **Repro:** 01 A PIC S9(3)V9 VALUE 2.5. 01 B PIC S9(3)V9 VALUE 3.3. 01 OB USAGE OBJECT REFERENCE. PROCEDURE DIVISION. MULTIPLY A BY B OB::"GETX". DISPLAY B. -> compiles with no diagnostic and prints 008B (+8.2); MULTIPLY A BY OB::"GETX". compiles clean as a no-op (zero receivers). Sibling sweep (same pinned cobol.exe): ADD A TO OB::"GETX". and SUBTRACT A FROM OB::"GETX". compile clean; DIVIDE A INTO OB::"GETX". crashes the compiler with System.InvalidOperationException: Sequence contains no elements. (Multi-operand ADD/SUBTRACT/DIVIDE forms parse-reject at '::'.) Probes under out/probe/multiply (O1.cob, S1.cob, S2.cob).
- **Expected (spec):** Compile-time rejection. In Format 1 identifier-2 is the receiving item (14.9.26.4 GR1: the product 'is stored as the new value of the data item referenced by identifier-2'), and 8.4.3.4.3 SR1: 'Inline method invocation shall not be specified as a receiving operand.' The same holds for ADD TO / SUBTRACT FROM / DIVIDE INTO Format 1 receivers.
- **Observed:** multiplyByOperand (and the ADD/SUBTRACT/DIVIDE Format-1 operand rules) admit inlineMethodInvocation because they double as the Format-2 SENDING operand (PB134/PB428). PB428's landing claimed SR1 holds STRUCTURALLY because 'no RECEIVING rule admits either', but these rules are mixed sending/receiving and the binder's per-format narrowing is the only guard: BindMultiply rejects `op.receivingOperand()?.literal() is not null || op.functionCall() is not null` only, and Format1Receivers(..., nonReceiverOperand) is passed `literal() || functionCall()` for ADD/SUBTRACT/DIVIDE. The invocation then falls out of ExpressionBinder.Receivers (which reads only receivingOperand().dataReference()) without a diagnostic - and DIVIDE's zero-receiver path still crashes (the targets.Max on empty the PB134 comment says was fixed). Two-arm dispatch: the functionCall arm was fixed, the inlineMethodInvocation twin was not. Fix shape: one 'is this operand a receiver' predicate over the mixed operand contexts (receivingOperand().dataReference() present) used by all four verbs, with a drift test pairing it to InlineMethodInvocationOperandDriftTests.
- **Code site:** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ArithmeticBinder.cs#BindMultiply (the foreach over byOps); src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ArithmeticBinder.cs#Format1Receivers and its ADD/SUBTRACT/DIVIDE call sites; src/Cobol.Net.Compiler/Binding/Procedure/ExpressionBinder.cs#Receivers(IEnumerable<MultiplyByOperandContext>)
