# PB3291 — `plan_wave.py` takes a wave number that is already taken

**Found by:** the operator's info 20261016-140612 to the Mythos lane ("Wave number 1098 is used twice ... please stop
passing --wave; file the guard"), under the operator's task 20261015-123901. Corrected by the branch review
(enqueue-review-notes-plan-wave-guard-20261016-r1, R1-1 to R1-3) against the files on disk.

**Harm (process only).** Two waves that share a number share every record keyed on it: the dispatch ledger's
(wave, letter) key and the report slug `w<wave><letter>`. On 2026-10-16 that cost one in-flight group its dispatch hold
and its declared file set for 50 minutes, and hid three other groups' declared file sets while they ran (Repro 1). No
user program is affected: `wrong_answer`, `crashes` and `rejects_legal_source` are all false.

**Mechanism.** `scripts/orchestrator/plan_wave.py` takes `--wave <number>` (argparse, line 1196: "the wave number, or
next (default): one past the highest seen") and uses an explicit number as given (line 1323: `wave =
str(next_wave(REPO, reports, cdir)) if a.wave == "next" else str(a.wave)`). Nothing checks whether that number is taken.
The default form has a hole of its own. `next_wave()` (lines 1162-1173) collects the wave numbers of the reports, of the
dispatch ledger (`E:\COBOL-coord\inflight-groups.json`, read through `ledger_groups`) and of the newest DEVLOG lines,
and returns their maximum plus one. It reads no scratch directory and has no is-taken test, so it cannot see a wave
whose ledger entries were released and which wrote no report (Repro 2).

**Repro 1, 2026-10-16: an explicit `--wave` reused a taken number.** The orchestrator loop's wave unit planned wave 1098
at 12:12 with `--scratch` at the scratch ROOT: `E:\COBOL-coord\scratch\groups.json`, `msg-w1098-a.txt` to `c.txt` and
`wf-args-w1098.json` (stop file `STOP-loop`), groups A PB2099, B PB3193 and C PB3268. Its reports are
`w1098b-PB3193-report.md` (12:44), `w1098a-PB2099-report.md` (12:53) and `w1098c-PB3268-report.md` (13:59). The
attended Mythos session's planner (`E:\COBOL-coord\scratch\tools-mythos\plan_w1098.py`) passed `--wave 1098 --scratch
E:/COBOL-coord/scratch/w1098` and rendered eight groups at 13:09 (A PB3196 to H PB3207, in `w1098\groups.json`,
`msg-w1098-a.txt` to `h.txt` and `wf-args-w1098.json`, stop file `w1098\STOP-w1098`). At 13:09 the reports already held
w1098a and w1098b and the ledger held the loop's 1098C, so a test of the reports or the ledger would have refused 1098.
What the collision did:
- `record_dispatch` (line 480) upserts on (wave, letter), so recording the Mythos 1098A to H replaced the loop's 1098A
  to C entries. The loop's A and B had already reported; its C had not, so from 13:09 until its report at 13:59 PB3268
  had no dispatch hold (`held_by_dispatch`) and no declared file set (`inflight_file_sets`, source 3).
- `inflight_file_sets` counts a ledger group as answered when any report carries its slug (line 469: `answered =
  {r.slug.lower() for r in reports}`). The loop's `w1098a` and `w1098b` reports therefore answered the Mythos 1098A and
  1098B groups from the moment they were recorded, and the loop's `w1098c` report answered the Mythos 1098C from 13:59.
  Their declared file sets left source 3 while they ran (the Mythos reports are `w1098a-PB3196-report.md` at 13:31 and
  `w1098b-PB3197-report.md` at 14:16; its C was still running at the 14:45 session close).
- The reports directory holds two names each for A and B (`w1098a-PB2099` and `w1098a-PB3196`, `w1098b-PB3193` and
  `w1098b-PB3197`), told apart only by the lead id, and a `plan_wave.py --release 1098A` selector names a number and
  letter that both waves used.

What it did NOT do: the two waves wrote different scratch directories, so no spec, groups file or workflow-arguments file
was overwritten (the root files still hold the loop's three groups, mtime 12:12). They share only the global `STOP` that
every wave shares. The review records do not mix branches: the root's `review-w1098-a.jsonl` to `c` hold only the loop's
`worktree-wf_d588a65b-0ab-*` branches, and `w1098\review-w1098-a.jsonl` and `b` only the Mythos
`worktree-wf_e3902303-54c-*` ones.

**Repro 2, 2026-10-16 ~15:05: the default form returned a taken number.** Wave 1100 (Mythos, the GAP campaign PB2911)
was rendered at 14:30 into `E:\COBOL-coord\scratch\w1100` (groups B PB780, F PB242, and G to J). Its agents were killed
before any of them wrote a report, and its ledger entries were released (`plan_wave.py --release 1100B`, `1100F`, and G
to J). With no report and no ledger entry of wave 1100 left, `next_wave()` returned 1100, although `scratch\w1100` still
holds the wave's specs and the B and F groups' batch directories. The session stepped past it by hand: the `while` loop
after `pw.next_wave(...)` in `E:\COBOL-coord\scratch\tools-mythos\plan_resume_20261016.py` (mtime 15:07) skips every
number whose `scratch\w<N>` exists. The default form therefore has the same hole as the explicit form, which is why the
fix is one predicate that both forms call.

**Fix shape (one rule, one place, with a drift test in `scripts/orchestrator/test_plan_wave.py`).** ONE predicate,
`wave_taken(n)`, is true when any of these holds wave n: the reports directory (any `w<n><letter>-*-report.md`), the
dispatch ledger (any entry of wave n), the newest DEVLOG lines (a wave or train label n, the test `next_wave` applies
today), or the scratch directory (`w<n>`, or `wf-args-w<n>.json` at its root: the loop's wave unit plans with
`--scratch` at the scratch root, so its waves leave only the latter, and the loop's wave 1098 has no directory of its
own). BOTH forms call it. `next_wave()` starts one past the highest number seen and steps past every taken number; an
explicit `--wave N` is REFUSED (exit non-zero, naming the holder) when `wave_taken(N)`. The drift test pins that the two
forms share the predicate: a number held by each holder alone (a report, a ledger entry, a DEVLOG label, a scratch
directory, a root `wf-args` file) is both skipped by `next_wave()` and refused by `--wave`. A session that wants a
number asks `next_wave()`; nothing passes `--wave` except a test. With the fix in place, the hand loop in
`plan_resume_20261016.py` is no longer needed.
