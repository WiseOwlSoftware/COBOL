# PB3291 — `plan_wave.py --wave N` does not refuse a wave number that is already taken

**Found by:** the operator's info 20261016-140612 to the Mythos lane ("Wave number 1098 is used twice ... please stop
passing --wave; file the guard"), under the operator's task 20261015-123901.

**Harm (process only):** a report or a review stamp can be read for the wrong branch, and one wave's STOP file stops the
other wave. No user program is affected: `wrong_answer`, `crashes` and `rejects_legal_source` are all false.

**Mechanism.** `scripts/orchestrator/plan_wave.py` takes `--wave <number>` (argparse, line 1196: "the wave number, or
next (default): one past the highest seen") and uses the number as given (line 1323: `wave = str(next_wave(REPO,
reports, cdir)) if a.wave == "next" else str(a.wave)`). It never checks whether the reports directory, the dispatch
ledger (`E:\COBOL-coord\inflight-groups.json`) or the scratch directory already hold that wave. `next_wave()` skips
every taken number; the explicit form does not apply the same test.

**Repro, 2026-10-16.** The orchestrator loop's wave unit planned wave 1098 at 12:10 (groups A PB2099, B PB3193,
C PB3268; reports `w1098a-PB2099-report.md` 12:53, `w1098b-PB3193-report.md` 12:44, `w1098c-PB3268-report.md` 13:59).
The attended Mythos session's planning script passed `--wave 1098` explicitly at 13:00 and again at 13:09
(`E:\COBOL-coord\scratch\tools-mythos\plan_w1098.py`); `next_wave()` would have returned 1099 then. Consequences:
- its `make_dispatch_specs.py` run at 13:09 overwrote the shared `E:\COBOL-coord\scratch\w1098\groups.json`,
  `wf-args-w1098.json` and `msg-w1098-a.txt` to `c.txt` (the loop's implementers had read theirs at 12:10, so no spec was
  followed wrongly);
- its ledger entries 1098A-H replaced the loop's 1098a-c;
- both waves share `scratch\w1098\STOP-w1098`;
- the records `review-w1098-a.jsonl` to `c` now mix two branches per letter, and `review_findings.py stamp` takes the
  newest verdict;
- `plan_wave.py --release 1098A` hits both waves.

**Fix shape (one rule, one place, with a drift test in `scripts/orchestrator/test_plan_wave.py`).** `plan_wave.py`
REFUSES an explicit `--wave N` (exit non-zero, naming the holder) when the reports directory holds any
`w<N><letter>-*-report.md`, the ledger holds any entry of wave N, or `<coord>\scratch\w<N>` exists with a
`groups.json`. `next_wave()` already skips those, so the explicit form applies the same test through the same
function. A session that wants a number asks `next_wave()`; nothing passes `--wave` except a test.
