# PB456 — Format 5's re-route declines silently, and nothing else screens the statement

Lane-3 adjudication batch b2, group g7-set-a. **Re-run on HEAD `89044aa0`**; still reproduces.

## 1. THE MECHANISM

Format 5 is not chosen by syntax — `SET a TO b` is also Format 1's shape — so `BindSetTo` re-routes
**semantically**. Its precondition (`SetBinder.cs:337-338`) is:

    if (tv.dataReference() is { Length: > 0 } tds
        && OoBinder.OoExtractBareReference(tv.arithmeticExpression()) is { } senderDref)

`OoExtractBareReference` (`OoBinder.cs:981-998`) returns non-null only when the arithmetic expression is
**exactly one bare `dataReference` spanning the whole expression text**. A numeric literal is not; `N + 1` is
not; `FUNCTION …` is not. The test fails, the re-route never fires, and the statement stays on the Format-1
path — **with an object-reference item as its receiver**.

At that point **no SET operand rule applies to it at all**:

* SR8 and SR9 are not consulted, because Format 5 was not selected;
* SR1 is not consulted either, because `SetTargetOf` (`SetBinder.cs:444-447`) applies no class screen — that
  missing receiver screen is [[PB212]].

The statement binds, and the emitter meets an object reference in an arithmetic store. This is the same root as
[[PB449]]: **one screen that saw the receiver and the sender together would decide the format AND the rule**,
instead of a probe-based re-route that silently declines and leaves nothing behind it.

The two-format argument is what makes this a defect rather than a preference. `SET U TO 5` with
`01 U USAGE OBJECT REFERENCE`:

* is **not** a legal Format 5 — a numeric literal is not identifier-4 (SR9);
* is **not** a legal Format 1 either — SR1 requires identifier-1 to be class index or an integer data item, and
  a universal object reference is neither.

§14.9.39.2's Format 1 sending brace does admit `arithmetic-expression-1`, so the *shape* parses; no format's
**receiving** brace admits an object reference under an arithmetic sender. So the program shall be refused under
one of those two rules — never compiled.

on every statement that reaches it. `sr9_nonobject_sender` is the sharpest pair-mate — a bare `WX` reference
*does* satisfy `OoExtractBareReference`, so the re-route fires and SR9 refuses it correctly; change `WX` to `5`
and the same illegal statement compiles clean.

## 4. THE CODE SITES AND THE SHAPE OF THE REPAIR

| arm | file:line |
|---|---|
| the re-route precondition | `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SetBinder.cs:337-338` |
| the three category re-routes it gates | `SetBinder.cs:340-352` (`t0`/`s0`) |
| the "exactly one bare reference" test | `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/OoBinder.cs:981-998` `OoExtractBareReference` |
| the permissive fall-through | `SetBinder.cs:354-360` → `SetTargetOf` `:444-447` |

⛔ **The repair is to make declining IMPOSSIBLE, not to add a fourth sender shape** (CLAUDE.md rule 5).
`OoExtractBareReference` is doing double duty: it answers "can I get a `dataReference` out of this expression?"
*and* is being read as "is this a Format-5 statement?". Those are different questions, and the second one is
answered by the **receiver's category**, which is available regardless of the sender's shape.

The shape: classify the receiving list (and the sender when it is extractable) **once**, select the format from
that classification, and give the selection a **terminal arm** — if the receivers are object references and the
sender is not a legal identifier-4 / object-class-name-1 / NULL / SELF, that is an SR9 diagnostic, not a
fall-through. The same terminal arm is what [[PB449]] asks for on the UP/DOWN and pointer routes, and what
[[PB212]] asks for on Format 1's receiver: **one selection point, one residual rejection**, rather than three
peeks that each quietly return `null`.

A drift test belongs with it: for each receiver category, compile a statement with every sender shape the
grammar admits (bare reference · literal · expression · function · NULL · SELF · SUPER · class-name) and assert
that **no combination compiles silently**.

* [[PB451]] owns everything the re-route protects *after* it fires (SR8-SR14); these screens are only as good as
  the selection that reaches them.

## LANDED — 2026-09-19 (wave 39, group SET-FORMATS; one selection point with [[PB449]])

**Declining is now impossible, which is what the note asked for.** `OoExtractBareReference` no longer answers
"is this a Format-5 statement?" — it answers only "can I get a `dataReference` out of this expression?", which
is the question it was written for. Format 5 is selected from the RECEIVER's category by
`SetFormatSelection`, whatever the sender looks like, so the re-route has no null arm to take:
`SetBinder.BindSetTo` routes to `OoBindSetObjectRef` with `senderRef` null for a literal, an expression or a
function sender, and that binder's former `return new BoundUnsupported("SET object-reference sender shape")`
— unreachable precisely because the caller declined for exactly that shape — is now SR9, naming the operand as
written. The same arm was added to the data-pointer (SR17), program-pointer (SR21) and function-pointer (SR20)
binders, which had the identical dead `BoundUnsupported`.

**Measured on this worktree's own build, `--std 2023`, `01 U USAGE OBJECT REFERENCE`:**

    sr9_literal_sender.cob  SET U TO 5      -> COBOLNET0867 ... identifier-4 shall be an object reference (SR9)
    sr9_expr_sender.cob     SET U TO N + 1  -> COBOLNET0867, same rule
    sr9_nonobject_sender    SET U TO WX     -> COBOLNET0867 (the control; unchanged, and its message now NAMES
                                               the receivers instead of the U+2026 the renderer ate — [[PB388]])

Both of the first two used to compile with ZERO diagnostics and abort at run time.

**The sibling sweep:** `DynTrySetSize` and `DynTryBindSetCapacity` were the same peek-and-decline idiom on the
receiver side; both are now ordinary binds entered only after selection, with no null return into a permissive
fall-through. The `setObjectReferenceStatement` first-operand sniff went with them.

**Rows:** `SR-14.9.39.3-8` and `SR-14.9.39.3-9` are `CONFORMS`.
**Still open, and deliberately NOT moved by this change:** [[PB212]], the Format-1 receiver CLASS screen (SR1).
The selector routes a non-carrier receiver to Format 1's BRACE, which is what the printed format says; SR1 is a
category rule over that brace and is PB212's own item. Putting it in the selector would have made a missing
screen look like a missing FORMAT.

## WAVE-41 FINISHER — the two arms the wave-39 gate never selected

Train 40 dropped this cluster whole on two `OoSpineTests` reds (no filter term of the cluster's gate selected
that class). Both are the SAME mechanism one level down — a rule about an OBJECT reference reached through a
path that had no object in it — and both are fixed at their root, not at the test:

1. **`SET N4 TO U.` drew the ARITHMETIC screen (COBOLNET0844) where §14.9.39.3 SR8 was owed.** Format 1's
   receiving brace is `{ index-name-1 | identifier-1 } …` and `identifier-1` admits ANY identifier, so a
   receiving list of one `PIC 9(4)` item selects Format 1 and the sender was never asked. But Format 1's own
   SENDING brace cannot hold that sender: §8.8.1.1 admits only numeric operands in `arithmetic-expression-1`,
   and SR2 makes `identifier-2` "a data item of class index". An item of class object — or of category
   data-pointer, program-pointer, function-pointer — is admissible in NO Format-1 sending position, and each is
   named by exactly ONE other format's sending brace (5, 7, 9, 8). `SetFormatSelection.SelectForTo` is that arm:
   the receiving list still decides, except against Format 1's catch-all, where the sender identifies the format
   and that format's own receiving rule refuses the receiver BY NAME. It is a table COLUMN (`Row.SendsOnly`),
   not an arm for class object, so the pointer siblings — which drew the same COBOLNET0844 — are fixed with it,
   and `SetFormatSelectionDriftTests` pins that no kind Format 1 CAN send ever appears in that column.
2. **The Format-5 receiver screen was ONE arm doing TWO rules.** `Resolve(t) is not { } tp || tp.Item.Pic is
   not { Category: ObjectReference }` stacked SR8 on top of the resolver's own COBOLNET1639 for an undefined
   name, and — once (1) routed index-names here — answered a FALSE "'IX' is not defined" about a name
   `INDEXED BY` declares and §13.18.38.3 SR7 permits in a SET statement. It is now three arms: unresolvable →
   the resolver's rule alone; not of class object → SR8 alone; otherwise → resolve and bind.

**Goldens:** `conformance:negative/pb456-set-object-sender-numeric-receiver` (SR8 through the sender),
`pb456-set-pointer-sender-numeric-receiver` + `pb456-set-pointer-sender-not-a-pointer` (SR17's two sentences,
one witness each), `pb456-set-exception-object-receiver` (§8.4.3.6.3 SR1), and the positive
`conformance:2002/pb456_set_sender_selected_formats` — the complement, where the receiving list already decides
and the legal statements must still run.

**Rows:** `SR-14.9.39.3-17` joins `-8` and `-9` at `CONFORMS`.
