# PB456 — Format 5's re-route declines silently, and nothing else screens the statement

Lane-3 adjudication batch b2, group g7-set-a. **Re-run on HEAD `89044aa0`**; still reproduces.

## 1. THE MECHANISM

Format 5 is not chosen by syntax — `SET a TO b` is also Format 1's shape — so `BindSetTo` re-routes
**semantically**. Its precondition (`SetBinder.cs:337-338`) is:

    if (tv.dataReference() is { Length: > 0 } tds
        && OoBinder.OoExtractBareReference(tv.arithmeticExpression()) is { } senderDref)

`OoExtractBareReference` (`OoBinder.cs:981-998`) returns non-null only when the arithmetic expression is
**exactly one bare `dataReference` spanning the whole expression text**. A numeric literal is not; `N + 1` is
not; `FUNCTION …` is not. The test fails, the re-route never fires, and the statement stays on the Format-1
path — **with an object-reference item as its receiver**.

At that point **no SET operand rule applies to it at all**:

* SR8 and SR9 are not consulted, because Format 5 was not selected;
* SR1 is not consulted either, because `SetTargetOf` (`SetBinder.cs:444-447`) applies no class screen — that
  missing receiver screen is [[PB212]].

The statement binds, and the emitter meets an object reference in an arithmetic store. This is the same root as
[[PB449]]: **one screen that saw the receiver and the sender together would decide the format AND the rule**,
instead of a probe-based re-route that silently declines and leaves nothing behind it.

    OK  §14.9.39.3 1)  (Syntax rules)

The two-format argument is what makes this a defect rather than a preference. `SET U TO 5` with
`01 U USAGE OBJECT REFERENCE`:

* is **not** a legal Format 5 — a numeric literal is not identifier-4 (SR9);
* is **not** a legal Format 1 either — SR1 requires identifier-1 to be class index or an integer data item, and
  a universal object reference is neither.

§14.9.39.2's Format 1 sending brace does admit `arithmetic-expression-1`, so the *shape* parses; no format's
**receiving** brace admits an object reference under an arithmetic sender. So the program shall be refused under
one of those two rules — never compiled.

The control set is the evidence that this is a **selection** defect, not a screening one: every screen works,
on every statement that reaches it. `sr9_nonobject_sender` is the sharpest pair-mate — a bare `WX` reference
*does* satisfy `OoExtractBareReference`, so the re-route fires and SR9 refuses it correctly; change `WX` to `5`
and the same illegal statement compiles clean.

## 4. THE CODE SITES AND THE SHAPE OF THE REPAIR

| arm | file:line |
|---|---|
| the re-route precondition | `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SetBinder.cs:337-338` |
| the three category re-routes it gates | `SetBinder.cs:340-352` (`t0`/`s0`) |
| the "exactly one bare reference" test | `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/OoBinder.cs:981-998` `OoExtractBareReference` |
| the permissive fall-through | `SetBinder.cs:354-360` → `SetTargetOf` `:444-447` |

⛔ **The repair is to make declining IMPOSSIBLE, not to add a fourth sender shape** (CLAUDE.md rule 5).
`OoExtractBareReference` is doing double duty: it answers "can I get a `dataReference` out of this expression?"
*and* is being read as "is this a Format-5 statement?". Those are different questions, and the second one is
answered by the **receiver's category**, which is available regardless of the sender's shape.

The shape: classify the receiving list (and the sender when it is extractable) **once**, select the format from
that classification, and give the selection a **terminal arm** — if the receivers are object references and the
sender is not a legal identifier-4 / object-class-name-1 / NULL / SELF, that is an SR9 diagnostic, not a
fall-through. The same terminal arm is what [[PB449]] asks for on the UP/DOWN and pointer routes, and what
[[PB212]] asks for on Format 1's receiver: **one selection point, one residual rejection**, rather than three
peeks that each quietly return `null`.

A drift test belongs with it: for each receiver category, compile a statement with every sender shape the
grammar admits (bare reference · literal · expression · function · NULL · SELF · SUPER · class-name) and assert
that **no combination compiles silently**.

## 5. THE SIBLING SWEEP THE FIXER MUST DO

* `DynTrySetSize` and `DynTryBindSetCapacity` (`SetBinder.cs:387-405`, and the Format-16 bare form) are the same
  peek-and-decline idiom on the *receiver* side; each returns `null` into the same permissive fall-through.
* `SetBinder.cs:59-70`, the `setObjectReferenceStatement` dispatch, probes `sor.dataReference(0)` — the
  NULL/SELF/SUPER sender route reaches Format 5 by a *different* path with the same first-operand sniff
  ([[PB449]] §5).
* [[PB212]] (open) is the missing Format-1 receiver class screen; it is the second half of every program in §3 —
  once the re-route declines, SR1 is the only rule left and it is not enforced. The two should land together, or
  the fall-through simply moves.
* [[PB451]] owns everything the re-route protects *after* it fires (SR8-SR14); these screens are only as good as
  the selection that reaches them.
