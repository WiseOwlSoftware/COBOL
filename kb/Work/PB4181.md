# PB4181 — is the gate cap of 3 still the throughput optimum?

**Sites:**
- `scripts/gate_slot.py#DEFAULT_SLOTS` (the owner's "Cap 3 permanently", 2026-10-10, kb/Work PB2514)
- `docs/rearchitecture/DESIGN-test-build-ci.md` (the gate-slot section; section 3.14.6, the PB1720 measurement)

**Why the cap is 3.** The comment on `DEFAULT_SLOTS` records the measurement it was decided against (2026-09-29, PB1720):
the lander's whole-Conformance leg slowed 1.24x to 1.30x with one implementer gate beside it and about 1.56x with two or
three; at cap 1 implementer gates waited 62 % of their wall time. The owner chose throughput. The measurement predates
server GC for test hosts (PB2526, 2026-10-07), and it measured one gate's SLOWDOWN, not the host's throughput.

**The new evidence.** The PB4150 experiment's driver log (E:/COBOL-coord/scratch/mythos/w-g4/w20261775a, arm B run 6):
wall 240.5 s, CPU 705.0 s on 32 processors, so one Conformance leg averaged about 2.9 busy cores; peak working set
1,897 MB. Three gates at once may leave most of the host idle (averages hide build bursts and memory peaks).

**The measurement (start only after PB4150 returns; the owner keeps the cap at 3 until then so its timings are not
skewed).** On the shared host, run a fixed batch of real leg-1 gates (built, cold and warm) at caps 3, 4, 5, 6 and 8;
record gates completed per hour, each gate's wall, CPU utilisation, memory peak and GC pause share; at least two
batches per cap, alternated. The metric is throughput and the landing gate's latency (landing tickets are served
first, PB3103), not one gate's slowdown.

**Done when.** The numbers are in this note and in the design doc's gate-slot section, and the owner has decided: keep 3,
a new fixed cap, or load-based admission (admit a gate while CPU and free memory have headroom, still FIFO with
landing first). A changed cap updates `DEFAULT_SLOTS`, its comment and its self-test in one change.

## Measured: the proxy series (2026-10-31, the reserved window, after PB4195)

The real-gate batches above need the fleet's gates, so the reserved window measured a proxy first: N copies of the
Conformance assembly (PB4195's arm A, cache off, server GC) started together inside the one slot, nothing else running,
N = 1, 2, 3, 4, 6, 8, two repetitions (`E:/COBOL-coord/scratch/w-m1/capseries.sh`, results in `cap/rep<R>-n<N>/runs.txt`).
Runs per hour = N x 3600 / the batch's wall:

| N | 1 | 2 | 3 | 4 | 6 | 8 |
|---|---|---|---|---|---|---|
| batch wall, rep 1 / rep 2 (s) | 125 / 123 | 213 / 217 | 308 / 298 | 421 / 389 | 618 / 594 | 841 / 824 |
| runs per hour (mean) | 29.0 | 33.5 | 35.7 | 35.6 | 35.7 | 34.6 |
| one run's wall against N = 1 | 1.00x | 1.73x | 2.40x | 3.25x | 4.86x | 6.63x |

- **Throughput saturates at N = 3**: 23 % more than one leg, and nothing more at 4, 6 or 8. One quiet Conformance leg
  already keeps most of the host busy; this note's premise (about 3 busy cores) counted the test host's own CPU only,
  not the compiled programs it runs as child processes.
- **N = 8 turns runs red without a regression**: two runs of rep 1 and all eight of rep 2 failed on HARNESS
  NON-OBSERVATION only (`OBSQ3A` under `NistProgram_MatchesGolden(OBSQ4A)`, `OBSQ5A`,
  `pb3350_open_reversed_varying_span_85`: a program with 8-9 s of its own CPU not finished in two 120 s attempts at
  77-87 % host load), never a value mismatch. The harness reported it as designed; it marks the load past which more
  gates cost correctness signals as well as time.
- **What the proxy does not cover**: builds (bursty, memory-heavy) and leg-1 gates, which run a slice of the
  population rather than a whole leg, so a leg-1 gate leaves more of the host idle than this proxy's legs did.

**Reading for the owner's decision**: on this host a fourth slot adds no throughput for whole legs and about 35 % more
wall to each; the evidence supports keeping 3. Load-based admission would only help gates far smaller than a leg.
Recorded in DESIGN-test-build-ci.md section 3.14.6. Open until the owner decides (keep 3, another cap, or the real-gate
batches).
