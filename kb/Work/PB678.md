# PB678 — LANDED — a comparator that was only ever guarded by a refusal

Found 2026-09-05 by the `PB327` implementer (report §"New defects" A), which removed the FD/SD record gate that had
refused every national leaf in a file record — and with it the only thing standing between a national SORT key and a
comparator written for alphanumeric weights. The implementer did not take it: the collation comparator is a
different mechanism from the record codec.

## The rule

§14.9.40.4 GR5 (`cite.py --check 14.9.40.4 "national"` → `OK 5)`): *"The alphanumeric collating sequence that
applies to the comparison of key data items of class alphabetic and class alphanumeric, and the national collating
sequence that applies to the comparison of key data items of class national, are each separately determined at the
beginning of the execution of the SORT statement in the following order of precedence:"* — TWO sequences, chosen by
the KEY's class. §14.9.24.4 GR5 says the same for MERGE, word for word (`--check` OK).

The PRECEDENCE sub-items, re-derived rather than inherited:

- **GR5a** — *"First, the collating sequence established by the COLLATING SEQUENCE phrase, if specified, in this
  SORT statement. The collating sequence associated with alphabet-name-1 applies to key data items of class
  alphabetic and alphanumeric; the collating sequence associated with alphabet-name-2 applies to key data items of
  class national."* (`cite.py --check 14.9.40.4 "the collating sequence associated with alphabet-name-2 applies to
  key data items of class national"` → `OK 5) a)`)
- **GR5b** — *"Second, the collating sequences established as the program collating sequences."*
  (`--check 14.9.40.4 "Second, the collating sequences established as the program collating sequences"` →
  `OK 5) b)`)

⛔ **`SortBinder`'s comment cited GR5b for the class rule and that was the WRONG sub-item.** GR5b is only the
precedence step that falls back to the program collating sequences; nothing in it maps a CLASS to a sequence. The
class mapping is the GR5 lead-in sentence and, for the statement phrase, GR5a. The note it was inherited from said
"GR5b" too. The comment is gone with the loud stage it justified.

The comparison each class then performs is GR8 (Format 1) / GR19 (Format 2) deferring to the relation-condition
rules: §8.8.4.2.7 alphanumeric, §8.8.4.2.9 national (*"Comparison is made with respect to the collating sequence of
characters specified for the current national program collating sequence. The length of an operand is the number of
national character positions in the operand"*), §8.8.4.2.8 boolean (*"a comparison of their boolean value,
regardless of their usage"* — never collated), §8.8.4.2.4 numeric (algebraic — never collated).

## The mechanism, as MEASURED on 2026-09-05

The note claimed one defect; the probe found the site carried **two**, and a **third** of the same shape one class
over. Probe `SORT` on an SD whose key is `PIC N(1)`, records released C, A, B, `COLLATING SEQUENCE IS REV-AN`
(`ALPHABET REV-AN IS "CBA"`):

    OUT=CCC   OUT=AAA   OUT=BBB          ← the RELEASE order: every key compared EQUAL

1. **The key WINDOW was in carrier positions over a BYTE image.** `SortBinder.SortAddFileKeys` set
   `len = item.ImageWidth` while `RecordLayout.OffsetInRecord` walks the PHYSICAL (byte) layout PB327 put the
   record on. `ByteWidth == ImageWidth` for every leaf kind but NATIONAL, which is two bytes per position
   (§13.18.60.4 GR8; D-N1) — so a national key's window covered only its first half, and for Latin national
   characters that half is the shared high byte U+0000. Three distinct keys compared equal and the stable sort
   returned the release order.
2. **What it compared was weighed by the ALPHANUMERIC sequence** — the note's finding. Control probe with the same
   program and a `PIC X` key answered `CCC BBB AAA`, so the alphanumeric channel was live and correct; the national
   key simply had no arm of its own.
3. **A BOOLEAN key took the alphanumeric weights too.** GR5 names a sequence for class alphabetic/alphanumeric and
   for class national and for no other class; §8.8.4.2.8 compares boolean operands by VALUE "regardless of their
   usage". A table sort on a `PIC 1(8) USAGE BIT` key under `ALPHABET REV-AN IS "10"` answered `CCC BBB AAA` where
   boolean value order is `AAA BBB CCC` — the alphabet reordered the carrier's `'0'`/`'1'` and inverted every bit
   position. Same dispatch, one class over.

The Format-2 TABLE sort staged loud at `SortBinder.cs:176` (`COBOLNET0899`), with a comment saying "file-sort
national keys are separately blocked by the D-N2 FD/SD record gate" — the gate PB327 removed. A national GROUP key
was not covered by that stage at all (it has no `Pic`), so it fell through to the `AsImage()` arm and compared its
2m UTF-16BE bytes under the alphanumeric weights, which is kb/Work PB327's own defect shape one channel over.

## Landed

2026-09-05. **ONE comparator selected by the key's CLASS, for both formats and both verbs.**

- `CollatingModel.cs` gains the ONE classification: `CollatingClass` (Alphanumeric · National · Boolean · Numeric)
  with `CollatingSelection.Of`, and `SortCollation` — the GR5 sequence PAIR. Nothing re-decides which class an
  operand is; `ConditionRenderer`'s two inline copies of the same ternary now route through
  `EmitContext.CollateArgFor`, which is the same classifier.
- `SortBindCollating` returns the pair, resolving each half by GR5a then GR5b independently, and CARRIES the
  national half (it used to resolve alphabet-name-2, validate it, and throw it away — "no reachable program
  observes the sequence", which stopped being true when PB327 landed).
- `BoundSortMergeKey` carries `CollatingClass` in place of `bool Numeric`; `SortAddFileKeys` reads
  `DataItem.OperandPic` (the ONE operand-category reader, D20) so a national or bit GROUP key is the elementary
  operand §13.18.29.4 GR2b/GR1b makes it, and takes the key's `ByteWidth` for the window.
- `CobolSort.Key` carries `KeyClass`; `KeyColumns` holds a per-key sequence (`SequenceFor`) instead of one
  per-statement sequence, and a national key's column DECODES its UTF-16BE byte pairs through
  `CobolBits.NatReadWindow` before comparing, because §8.8.4.2.9 compares national POSITIONS. `Init`/`Sort`/`Merge`
  take both sequences, and the §14.6.6 r5 snapshot is now keyed on a `Snapshotted` flag rather than on "the stored
  sequence is non-null" — the native order is a real snapshot value.
- `SortEmitter.TableCompare` dispatches on the class: `AsNat()` for a national group, `AsBits()` + the
  §8.8.4.2.8 boolean-zero pad for a bit group, the boolean pad with NO sequence for a boolean leaf, and the
  national carrier for a national leaf. The `SortBinder.cs:176` loud stage is deleted.

Goldens: `tests/conformance/2023/pb678_sort_national_key_collating` (GR5a — seven legs, three DIFFERENT orders so
no leg can pass for another leg's reason, plus MERGE's own leg for §14.9.24.4 GR5),
`tests/conformance/2002/pb678_table_sort_key_class` (GR5b, the statement-overrides-program case, the boolean key,
and a national GROUP key agreeing with the elementary one — placed at 2002, the lowest edition the rule applies to,
where its output is byte-identical to 2014/2023), `tests/conformance/negative/pb678-sort-collating-for-forms-at-85`
(COBOLNET0872 — the gate that became load-bearing when the phrase started being carried).

Inventory: `GR-14.9.40.4-5` and `GR-14.9.24.4-5` CONFORMS (GAP 2802 → 2800).
