# PB453 — the absent SET formats fail through the parser instead of through a named refusal

Lane-3 adjudication batch b2, group g7-set-a. **Every repro below was re-run on HEAD `89044aa0`**; all still
reproduce.

⚠ **Scope correction, recorded because it is the reason this note is smaller than its adjudication.** The b2
adjudication grouped Format 6 (`SET … ATTRIBUTE`) into this mechanism. **That half no longer reproduces**: the
landing `60bf02d7` ("A.4.2 screen handling: refused by name, 163 rows …") gave it a named refusal, measured on
HEAD below. Rows `SR-14.9.39.3-15`, `SR-14.9.39.3-16` and `GR-14.9.39.4-11` are closed
(DOCUMENTED-NON-SUPPORT) and are **not** claimed here. Format 6 now appears in this note only as the **model the
two remaining halves should be repaired into**.

## 1. THE MECHANISM

Two SET formats have no surface, for two different reasons, and **both fail the same way: a bare ANTLR
cascade**.

* **Format 15 (numeric-content)** is mandatory base language and simply absent — see [[PB452]], which owns the
  feature gap and its general rules. This note owns its two **syntax** rows, because what SR31 and SR32 record
  is not "the screen is wrong" but "the statement dies in the parser before any screen exists".
* **Format 17 (message-tag)** is absent one level below the statement: `USAGE MESSAGE-TAG` is not a usage the
  data binder knows — `PicCategory` has no `MessageTag` member and the tree says so itself at
  `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/IntrinsicBinder.cs:1340` and
  `src/Cobol.Net.Compiler/Binding/IntrinsicArgumentRules.cs:64`. No Format-17 operand can be declared, so the
  statement is never reached.

⛔ **The Format-17 half is not a missing feature — it is a declined facility given the wrong diagnostic, and the
SAME facility's other half already has the right one.** The asynchronous messaging facility is Annex A.3 item 4
(processor-dependent), `docs/CONFORMANCE.md` §4 item 1 declines it, and §4.2.6 ¶3 makes the compile-time warning
mechanism **mandatory** for exactly this case. The statements half honours that; the data-item half does not:

    SEND TO WS-DEST FROM WS-MSG      → warning COBOLNET1578 (named, cites §4.2.6, Annex A.3 item 4, and
                                       docs/CONFORMANCE.md §4) — the program compiles and runs
    01 MT USAGE MESSAGE-TAG.         → error COBOL0001: no viable alternative at input 'MESSAGE-TAG'

One facility, one disposition, two postures — the two-arm shape, with the second arm never written. And because
`MESSAGE-TAG` is a **reserved word**, the user cannot spell it as a user-defined word either: there is no
workaround and no signal, only a token name.

`docs/CONFORMANCE.md` records the gap in its own words at §4 item 1 ("MESSAGE-TAG data items … the statements
are accepted-inert with COBOLNET1578") — the enumeration covers `SEND`/`RECEIVE` and lists MESSAGE-TAG data
items as part of the surface, but no recognize-and-warn arm was ever written for the data-division half. The
same doc records at §1 that **COBOLNET1578 is still unasserted** by
`DocumentedNonSupportWitnessTests`, so it could lose its diagnostic without a gate going red.

The A.3 disposition was verified against the annex, not inherited: A.3 item 4 reads "The asynchronous messaging
facility is dependent on the capability of a processor to allow run units to communicate with each other"
(measured at spec line 34861+; `MESSAGE-TAG` itself appears nowhere in A.3 or A.4, so the *word* is base
language and it is the **facility** that is processor-dependent). Format 15, by contrast, appears in **neither**
annex — A.4's whole SET inventory is three items (formats 6, 14, 11/12) — so it is not declinable at all.

⛔ **AN OWNER DECISION IS OWED BEFORE ANYONE IMPLEMENTS FORMAT 17, and it is a defect in the standard, not in
this compiler.** The printed general format (rendered PDF page 762, not taken from the transcription) is
`SET data-name-4 TO { data-name-5 | NULL }`, making **data-name-4 the receiver**. GR40 moves the content of
data-name-4 *into* data-name-5, and GR41 sets the content of **data-name-5** to the null value — making the
`TO` operand the receiver. SR35 constrains only the class and does not settle it. The two readings disagree
about which operand is written to; do not guess.

⛔ **The repair is a SURFACE, not a suppression** (CLAUDE.md rule 4). Both the screen decline and the MCS
statement decline work the same way and it is the shape to reuse: give the declined construct a **grammar
alternative that exists only so it can be refused by name**, then refuse it in the binder with a diagnostic that
identifies the *facility*. The Format-6 comment at `CobolParserCore.g4:1179` says so explicitly. Concretely:

1. `usageKeyword` gains a `MESSAGE-TAG` alternative and `PicCategory`/`Usage` gain the member, refused at the
   data description entry with the MCS facility diagnostic — **not** silently classified, so nothing downstream
   can mistake it for implemented.
2. `setStatement` gains the Format-17 alternative behind the same refusal, so `SET MT-A TO MT-B` names the
   facility rather than the token.
3. `DocumentedNonSupportWitnessTests` gains the assertion COBOLNET1578 does not have. A warning nothing asserts
   is a warning that can silently stop firing — `docs/CONFORMANCE.md` §1 already says so about this exact code.
4. Format 15 is a **feature**, not a decline: its surface lands with [[PB452]]. Until it does, its refusal has
   no named band to fall into either, which is why SR31/SR32 sit here.

## 5. THE SIBLING SWEEP THE FIXER MUST DO

* **Derive the declined surface from the annex, not from a hand-written enumeration.** `docs/CONFORMANCE.md`
  §4's prose lists families; A.3 and A.4 list items. Format 6 was missing from the doc's own enumeration until
  `60bf02d7`, and the MESSAGE-TAG data item is missing from the mechanism today for the same reason. A.4.2
  alone has 27 items. A generated cross-check of *annex item → refusing diagnostic* is the durable form, and it
  is the kind of structure CLAUDE.md rule 8 explicitly permits (mechanically derived, never hand-maintained).
* The EC-MCS-\* exception-names are still **accepted** against a facility with no setting sites
  (`docs/CONFORMANCE.md` §4 item 1's own ⚠). Same facility, third arm.
* [[PB260]] / [[PB261]] were opened for exactly this posture gap on the screen and COMMIT declines; this is the
  MCS instance of the same pattern and should land in their shape.
* `constructs.json` needs a `MESSAGE-TAG` usage row when the surface lands, with the 2023 introduction edition,
  or the usage-inventory drift test stays blind to it.
