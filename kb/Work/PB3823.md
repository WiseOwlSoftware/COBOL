# PB3823 — an idempotence claim a second call can break

**Sites:** `scripts/standard_streams.py#ensure_utf8` (the loop over `_STREAMS` calls `reconfigure(encoding=..., errors=...)` on
stdin, stdout and stderr; docstring: "Safe to call any number of times").

## Measured

The docstring on origin/main 33e3dcf21 still promises it. The reviewer's scenario: once a stream has been read (stdin) or
written past its first buffer, `TextIOWrapper.reconfigure` refuses to change the encoding and raises
`io.UnsupportedOperation`, so a second call (a script that imports a module whose `__main__` hook ran, or a helper that calls
`ensure_utf8` again) crashes instead of doing nothing. Reproduce first: `python -c "import sys; sys.stdin.readline();
from standard_streams import ensure_utf8; ensure_utf8(); ensure_utf8()" < somefile` with `scripts/` on the path; if it does
not raise on the supported Python, correct this note and the docstring claim stands.

## Acceptance

- `ensure_utf8` leaves a stream that is already UTF-8 with the right errors handler untouched (compare `stream.encoding` and
  `stream.errors` first), so the second call is a no-op by construction; a `--self-test` arm calls it twice after a read.
- If the reproduction shows no failure, the note closes with that measurement instead of a code change.

## Landing (wave 20261737, group C)

**Re-probe (Python 3.14.7, Windows, this tree before the fix).** `sys.stdin.readline()` then `ensure_utf8()` with stdin a
file: `io.UnsupportedOperation: It is not possible to set the encoding or newline of stream after the first read`, raised
at `reconfigure(encoding="utf-8", errors=errors, **buffering)` (stdin is cp1252 on this host, so even the FIRST call
after a read raised). stdout after a write is not refused: only stdin is, and only for a stream not already UTF-8.

**The fix.** `ensure_utf8` compares each stream with the target first (`_is_utf8(stream)` through `codecs.lookup`, plus
`stream.errors`, plus `line_buffering` when asked) and calls `reconfigure` with only the settings that differ, so a stream
already in the state (UTF-8 mode, an earlier call) is not touched and the second call is a no-op by construction. A
stream that is NOT yet UTF-8 and has been read still raises: the bytes read were decoded wrongly, and swallowing the error
would be a silent failure. The docstring says so. Arms in `standard_streams.py --self-test` (a real child process, stdin
piped): call, read, two more calls under cp1252; read then two calls under UTF-8 mode; read in cp1252 then the first call
is refused.

**Sites:** `scripts/standard_streams.py` (`ensure_utf8`, `_is_utf8`, `self_test`).
