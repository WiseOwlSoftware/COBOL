Filed 2026-09-26 by the **train-61 lander** from the w61d implementer report (PB1192/PB690/PB1098).

## Observation
Since w61d (R47), `ReportWriter` (`src/Cobol.Net.Runtime/IO/ReportWriter.cs`) advances its device line only on a
successful `WriteAdvancing`, and a refused line appears in the file as a blank line
(golden `conformance-suite/cases/A.1-Implementor-defined-language-element-list/pb690_report_line_byte_image_85`). The WriteAdvancing status is otherwise unread, so
the refusal never reaches the program.

## To decide
Not a spec breach as filed: GENERATE is not among the statements §9.1.13.1 gives an I-O status. The question is
whether a refused report line should raise an exception condition (EC-I-O-IMP under checking, or another EC-I-O
condition) so a program can observe it — survey GnuCOBOL / IBM / Micro Focus per CLAUDE.md rule 1, record the
determination in `docs/CONFORMANCE.md`, and implement or close.

Owner 2026-10-17: addressed in the SORT and file I/O campaign (kb/Work PB3353).

## Landed (wave 1126 group D) - the determination

**Re-probe on this build** (the PB690 report with a FILE STATUS item and a USE AFTER EXCEPTION procedure on the report
file): the U+20AC line is refused and leaves its blank line; FILE STATUS reads `00` after OPEN, each GENERATE, TERMINATE
and CLOSE, the USE procedure never runs, and the run reaches STOP RUN.

**The question.** Should the refusal raise an exception condition so a program can observe it?
- **The standard.** `cite.py --check 9.1.13.1 "The value of the I-O status is set during the execution of a CLOSE, DELETE,
  OPEN, READ, REWRITE, START, UNLOCK or WRITE statement"` is OK. GENERATE, INITIATE and TERMINATE are not listed, and no
  rule of 14.9.16.4, 14.9.21.4 or 14.9.46.4 writes the line "as if a WRITE statement" (`cite.py --check 14.9.24.4 "Each
  record is written as if a WRITE statement without any optional phrases had been executed"` is OK, 14.9.24.4 GR12, and
  is MERGE's and, at 14.9.40.4 GR15 b) (`cite.py --check 14.9.40.4 "Each record is written as if a WRITE statement"`
  is OK), SORT GIVING's: those two verbs write an implicit WRITE and carry its I-O status; a report line has no such rule). GENERATE sets no I-O status, so 9.1.13.1 raises no EC-I-O condition from it. The action after a
  fatal status is the implementor's (9.1.13.1: "The implementor may either continue or terminate the execution of the
  run unit").
- **GnuCOBOL 3.2.0** (WSL, measured 2026-10-18): a plain LINE SEQUENTIAL WRITE to `/dev/full` answers FILE STATUS `34`
  at the 68th record; the same medium as a REPORT file's ASSIGN, 300 GENERATEs of 60 columns, leaves FILE STATUS `00`
  after the loop, after TERMINATE and after CLOSE, and the USE AFTER EXCEPTION procedure never runs. (IBM Enterprise COBOL
  has no Report Writer; Micro Focus was not measured.) CLAUDE.md rule 1 takes GnuCOBOL's answer: not observable. This is
  the determination PB1956 recorded for the closed-file arm.
- **Decision recorded.** docs/CONFORMANCE.md DOC-A.1-159 now says so (no FILE STATUS store, no EC-I-O condition, no USE
  procedure; INITIATE and TERMINATE likewise; `34` as well as `91`/`71`). A later owner decision to make the refusal
  observable would be a new `kind: decision` against DOC-A.1-159 and DOC-A.1-103.

**Witnesses added** (the abnormal paths, MANDATORY-PRACTICES I11):
`tests/Cobol.Net.Tests.Conformance/ReportLineRefusalConformanceTests.cs` has `RefusedReportLine_IsNotAnIoStatementException`
(SEQUENTIAL `91` and LINE SEQUENTIAL `71`, FILE STATUS and USE on the report file, every report statement, the medium's
blank line) and `RefusedReportLine_RaisesNoEcIo_WhenCheckingIsEnabled` (review round 1: `>>TURN EC-I-O CHECKING ON`, nine organization x FILE STATUS x declarative combinations, a TERMINATE-flushed refusal) and `ReportLine_RefusedByAFullMedium_IsNotAnIoStatementException` (`34` through `/dev/full` on Linux). Before
this the determination had one golden with neither a FILE STATUS item nor a USE procedure, and no `34` case.
