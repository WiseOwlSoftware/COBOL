# PB3651 — prune_worktrees.replays breaks a replayed-count tie by branch size, while its comment, docstring, plan_wave item 10 and DESIGN-orchestrator-loop item 9 say the later report wins

**Sites:** `scripts/prune_worktrees.py` (`replays`, ~line 345), `scripts/orchestrator/plan_wave.py`, `docs/rearchitecture/DESIGN-orchestrator-loop.md`.

## What happens

When two uncarried branches replay the same number of commits of a carried branch, `replays` breaks the tie with key(c) = (distinct patches held, rank, name). The LARGER uncarried branch therefore wins before the later report is consulted. The inline comment, the `Replay` docstring, plan_wave item 10 and DESIGN-orchestrator-loop item 9 all say the tie goes to the later report.

## Fix direction

Decide which rule is intended (the docs were written for the later report) and make the key and the four statements agree; pin it with a `test_plan_wave.py` case where a larger uncarried branch ties a later one. Ownership of the carrier choice stays in `replays` (one rule, one place).

## Source

Report `w20261030c2-PB3170-report.md` (PB3170, PR #509), lead R2-1 (info).

## Landed (2026-10-24, fix-lane wave 20261031 group D)

**Intended rule.** Four statements (the `Replay` docstring, the inline comment, plan_wave item 10 and
DESIGN-orchestrator-loop item 9) say the carrier is the branch that replays the most of the carried branch's commits,
and on a tie the LATER report. Only the code differed, so the code was fixed.

**Re-probe.** `prune_worktrees.replays` chose `max(by, key=(replayed count, key(branch)))` with
`key(b) = (distinct patches held, rank, name)`, so of two carriers replaying the same number of commits the one holding
more patches won, whatever its report's age. Scratch repository: x holds four commits; lg (earlier report) cherry-picks
them and adds three of its own, mid (later report) cherry-picks them and adds one. Before the fix x's carrier was `lg`.

**Fix (`scripts/prune_worktrees.py`).** The tie key is `(replayed count, rank, name)`: the carrier choice is the same one
line, now ordered as documented. No other reader orders carriers (`plan_wave.branch_replays` passes the reports' order as
`rank` and reads `Replay.carrier`; `by` is only presented, in name order). Test: `test_plan_wave.py` PB3651 block (red with
the old key: `got ('lg', ...) want ('mid', ...)`), including the reversed reports' order, where the larger branch is the
later report and carries x.
