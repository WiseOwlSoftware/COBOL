# PB515

## Mechanism — data-description-entry-p1
There is no VALUE-by-CLASS screen at the data description entry. What exists is one usage-keyed branch that rejects VALUE on PROGRAM-POINTER / FUNCTION-POINTER citing a different rule (13.18.63 SR9); classes index and object, and the data-pointer leg of class pointer, are unscreened. Two of the three then reach Roslyn and fail as raw CS0029 against generated C#, and the third is accepted and honoured.

### Expected, from the standard
13.16.3 SR10: 'The VALUE clause shall not be specified for data items of class index, message-tag, object, or pointer.' All three repros shall be rejected with a named diagnostic. (There is no VALUE NULL form for these items: 8.4.3.7 / 8.4.3.10 make NULL a predefined reference/address used by SET and relation conditions, never a VALUE-clause literal.)

```
$ python scripts/spec/cite.py --check 13.16.3 "The VALUE clause shall not be specified for data items of class index, message-tag, object, or pointer"
  OK  §13.16.3 10)  (Syntax rules)
```

### Observed
`77 I USAGE INDEX VALUE 7.` compiles clean at --std 2023 and --std 85 and the value is LIVE: `SET N TO I` yields 007, so illegal source silently acquires a defined initial occurrence number. `USAGE POINTER VALUE NULL` (and VALUE ZERO) and `USAGE OBJECT REFERENCE VALUE NULL` reach the backend and die as `error CS0029: Cannot implicitly convert type 'string' to 'CobolNet.Runtime.ManagedPointer'` / `...CobolObject` -- loud, but unnamed and pointing at the generated .g.cs, which is the loud-failure violation the design forbids. The message-tag leg is vacuous today: USAGE MESSAGE-TAG has no grammar at all (`no viable alternative at input 'MESSAGE-TAG'`). The entry already resolves Usage and PicInfo before the VALUE is validated, so ONE class-keyed screen beside the existing 13.18.63 SR9 branch covers all four classes and removes both CS-leak paths.
