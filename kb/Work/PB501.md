# PB501

## Mechanism — data-description-entry-p3
A level-88 data description entry is never checked against its own general format. BindCondition (DataBinder.cs ~L2105) walks whatever clauses the entry happens to carry and appends each VALUE operand to Condition88.Values; nothing asserts that a value-clause was present at all. Format 3 (`88 condition-name-1 value-clause .`) and Format 4 (`88 [ condition-name-2 ] value-clause .`) both make the value-clause mandatory -- it is unbracketed in both figures. With an empty Values list ConditionRenderer.RenderCondition88 evaluates `"(" + string.Join(" || ", tests) + ")"` over an empty sequence and emits the two-character C# fragment `()`, so the generated source contains `if (())` and the Roslyn backend fails. The user sees a C# compiler error against a generated file, not a COBOL diagnostic.

### Expected, from the standard
13.16.2 Format 3 is `88 condition-name-1 value-clause .` and Format 4 is `88 [ condition-name-2 ] value-clause .`; the value-clause is unbracketed in both, so it is required. 13.16.3 SR24 (--check text present at 13.16.3): 'Format 3 or 4 is used for each condition-name.' `88 NOVAL.` matches neither, so it is illegal source at every edition and shall be rejected with a COBOL diagnostic naming the missing value-clause. 13.16.4 GR3 (--check OK) states what a Format-3 entry carries -- 'the name of the condition AND the value, values, or range of values associated with the condition-name' -- and a condition-name bound with an empty value set has no such association at all. Whatever the diagnosis, a well-formed compiler must never hand the user a generated-C# syntax error.

```
$ python scripts/spec/cite.py --check 13.16.4 "the name of the condition AND the value, values, or range of values associated with the condition-name"
  OK  §13.16.4 3)  (General rules)
```

### Observed
Read: BindCondition has no post-loop guard on cond.Values.Count and unconditionally does `parent.Own88s.Add(cond)`; RenderCondition88's final line is `return "(" + string.Join(" || ", tests) + ")";` where tests is `c.Condition.Values.Select(...)`. Measured: the generated file's `if (())` and the CS1525. The grammar cannot catch this on its own -- `dataDescriptionEntry : levelNumber dataName? dataDescriptionBody DOT` is ONE rule for every level number, with no per-format shape, so every level-88 format rule has to be enforced at bind. That single shared production is the reason this and finding F3 are the same absence.

## Mechanism — data-description-entry-p3
The same missing format screen, other arm. BindCondition's first statement is `if (entry.dataName()?.GetText() is not { } name) return;` -- a level-88 entry with no name is discarded with no diagnostic and no Own88s entry. Because dataDescriptionEntry makes dataName optional for every level, `88 VALUE 1.` parses (VALUE is taken as the start of the value-clause, not as a data-name) and then evaporates. The program compiles clean and the user's intent -- whatever it was -- is gone.

### Expected, from the standard
13.16.2 Format 3 requires condition-name-1 (it is not bracketed). Format 4 does permit `88 [ condition-name-2 ] value-clause .`, but its value-clause is 13.18.63 Format 5 (content-validation-entry), whose figure ends in a REQUIRED `{ INVALID | VALID }` choice -- the figure note in the transcription says so explicitly ('{ INVALID / VALID } is a required choice'). `88 VALUE 1.` supplies no VALID/INVALID phrase, so it is not a legal Format 4 entry either. 13.16.3 SR24 leaves no third possibility: 'Format 3 or 4 is used for each condition-name.' The entry is therefore illegal at every edition and shall draw a diagnostic; 13.16.4 GR3 is the rule it fails, since a Format-3 entry 'contains the NAME of the condition' and this one contains none.

```
$ python scripts/spec/cite.py --check 13.16.4 "Format 3 or 4 is used for each condition-name"
  FAIL: §13.16.4 exists but does NOT contain 'Format 3 or 4 is used for each condition-name'
$ python scripts/spec/cite.py --check 13.16.3 "Format 3 or 4 is used for each condition-name"
  OK  §13.16.3 24)  (Syntax rules)
```

### Observed
Read: the early `return` in BindCondition; the optional `dataName?` in the shared dataDescriptionEntry production; the `(IS | ARE)?` superset in valueClause that lets a Format-5 tail share the Format-3 arm. Measured: clean compile, exit 0, a .dll on disk. Reachability of the silent drop is measured, not deduced -- the entry produced no COBOLNET0901 either, so no other screen catches it. Same root as finding F2 and best fixed in the same bind-time screen: one adjudication of a level-88 entry against Formats 3 and 4, reporting which constituent is missing.
