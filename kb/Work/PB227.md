# PB227

**Rows:** `GR-14.9.1.4-11`

ACCEPT … FROM TIME's eight-digit conceptual image is produced by a code path no test reaches — every TIME golden takes the numeric arm that never evaluates `sendImage`.

Row: GR-14.9.1.4-11 ('TIME … elapsed time since midnight on a 24-hour clock … EIGHT digits', positions 1-2 hours 00-23, 3-4 minutes 00-59, 5-6 seconds, 7-8 hundredths 00-99).

WHAT IS CORRECT BY DERIVATION. AcceptSource.Time() returns `n.Hour * 1000000L + n.Minute * 10000L + n.Second * 100L + n.Millisecond / 10`, rendered at width 8 — the exact positional layout; DateTime.Hour is 0..23 (the 24-hour clock), Minute/Second 0..59, Millisecond/10 is 0..99 for the hundredths, and 'hundredths of a second' requires TRUNCATION, which integer division gives (679 ms → 67, not 68). The 'system does not have the facility … value zero is returned' clause is inapplicable (the facility exists). The LEAP-SECOND leg is answered and documented rather than accidental: positions 5-6 are 00-59 on the OFF branch (DateTime.Second never exceeds 59), and on the ON branch nn is implementor-defined — docs/CONFORMANCE.md's Annex A.1 item 112 row makes that determination explicitly and negatively ('NO — never … The REPORTED side stays this negative determination on both directive branches') and item 111 cross-references §14.9.1 GR11 to it, so the fact that AcceptSource.Time never reads DataBinder.LeapSecond (unlike IntrinsicRenderer.LeapSecondFlag, which every §15.3 date/time function receives) is a documented choice, not a gap.

THE GAP, and it is wider than 'positions 1-4 unpinned'. The one TIME test — conformance-test:AcceptDifferentialTests.Time_SmallNumericReceiver_KeepsLowOrderDigits — pins clock 14:30:45.67 into PIC 9(4) = '4567', i.e. seconds 45 and hundredths 67. A PIC 9(4) receiver takes EmitAcceptTemporal's NUMERIC arm (`NumStore(call, "0", profile)` + Narrow) and never evaluates `sendImage`, so `CobolNum.FormatUnsignedDisplayU(AcceptSource.Time(), 8)` — the width-8 conceptual rendering GR11 actually specifies — is exercised by NO test at all for TIME. The *1000000 and *10000 weights, the hour zero-pad and the eight-digit width are all unobserved. That path was hand-checked once on this row for a leading-zero hour (09:05:03.07 → 9*1000000 + 5*10000 + 3*100 + 7 = 9050307, rendered '09050307' — correct), and a hand-check is not a gate.

WHAT WOULD CLOSE IT: a golden with a PIC 9(8) receiver under a pinned clock, plus the 00:00:00.00 and 23:59:59.99 endpoints for the 00-23 and 00-99 ranges, and one leading-zero hour so the zero-pad is pinned.

SPEC REFS as carried by the row: §14.9.1.4 GR11; §15.3 (the date/time function family, for the leap-second contrast); docs/CONFORMANCE.md Annex A.1 items 111 and 112.

## Mechanism

src/Cobol.Net.Runtime/IO/AcceptSource.cs#Time (`n.Hour * 1000000L + n.Minute * 10000L + n.Second * 100L + n.Millisecond / 10`), whose GR11 image is `CobolNum.FormatUnsignedDisplayU(AcceptSource.Time(), 8)` — but src/Cobol.Net.Compiler/CodeGen/Verbs/AcceptDisplayEmitter.cs#EmitAcceptTemporal's numeric arm (`NumStore(call, "0", profile)` + Narrow) never evaluates `sendImage`, and the only TIME test takes that arm
