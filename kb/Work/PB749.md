# PB749 — OPEN — four "as if" statements, one status store, and it is the wrong one

Found 2026-09-06 in the PB714 implementer's report (NEW DEFECT d), which named it and deliberately did not take it
because the fix puts a store inside a per-record loop. Verified against main (`89555b09`).

## The mechanism, measured

`src/Cobol.Net.Compiler/CodeGen/Verbs/SortEmitter.cs` — `EmitInputFile` (`:91-124`) and `EmitGivingFile`
(`:130-148`):

| `:99` | | | `EmitUseHook(input)` |
| `:109-118` | `while (FileReadSharedOk(…))` → `SortRelease` — the implicit READ, N times | **no** | none |
| `:119` | `FileClose` — implicit CLOSE (GR12 c) | | |

| `:138-144` | `while (SortReturn(…))` → `FileWriteShared` — the implicit WRITE, N times | **no** | none |

| `:146` | | **yes** | |
| `:147` | | | `EmitUseHook(output)` |

**N+2 implicit input-output statements per file, one store, and it is the CLOSE's.**

The posture is written down as intent in the method's own doc comment, `:88-89`:

> *"The file's FILE STATUS item observes the final (CLOSE) status, the only value visible after the statement."*

⛔ That sentence is the defect stated as a design. "The only value visible **after** the statement" is true only
if nothing of the program's runs **during** it — and GR12 a) / GR15 a) each name *"an applicable USE procedure"*
explicitly, so the standard provides for exactly that.

## The contract it breaks is documented on the helper it calls

`src/Cobol.Net.Compiler/CodeGen/Verbs/SequentialIoEmitter.cs:26-29`, the doc comment on `EmitUseHook`:

> *"The declarative hook **after a verb's FILE STATUS store** (GR6 — after the standard status routine, BEFORE the
> statement's phrase branches)."*

Both `SortEmitter` OPEN sites emit the hook with no store before it.

## Sweep — and it is exact

Every `EmitUseHook` call site under `src/Cobol.Net.Compiler/CodeGen/`, checked for a preceding
`EmitStoreFileStatus` (mechanical scan, then the two apparent misses read by hand — `SequentialIoEmitter.cs:436`
stores at `:432` and `KeyedIoEmitter.cs:328` stores at `:322`, both merely further than four lines away because
of intervening comments):

**16 call sites. 14 store first. The 2 that do not are `SortEmitter.cs:99` and `SortEmitter.cs:137`** — the two
implicit OPENs, one on each transfer. Every explicit verb in the compiler holds the contract; the "as if"
statements are the only ones that do not, which is precisely `feedback_two_arm_dispatch` in its emitter form:
the implicit arm of the I/O statement dispatch was never given the store the explicit arm has.

## The rules — every citation re-derived on main, none inherited

- `--check 14.9.40.4 "as if a READ statement with the NEXT phrase"` → **OK §14.9.40.4 12) b)** — SORT USING:
  *"Each record is obtained as if a READ statement with the NEXT phrase, the IGNORING LOCK phrase, and the AT END
  phrase had been executed."*
- `--check 14.9.40.4 "as if a WRITE statement without any optional phrases had been executed"` → **OK
  §14.9.40.4 15) b)** — SORT GIVING.
- `--check 14.9.24.4 "as if a READ statement"` → **OK §14.9.24.4 7) b)** — MERGE USING, same sentence.
- `--check 14.9.24.4 "as if a WRITE statement"` → **OK §14.9.24.4 12) b)** — MERGE GIVING, same sentence.
- `--check 9.1.13.1 "The value of the I-O status is set during the execution"` → **OK §9.1.13.1**: *"The value of
  the I-O status is set during the execution of a CLOSE, DELETE, OPEN, READ, REWRITE, START, UNLOCK or WRITE
  statement and prior to the execution of any imperative statement associated with that input-output statement or
  **prior to the execution of any applicable exception processing statements**."*
- `--check 12.4.5.8.4 "I-O status"` → **OK §12.4.5.8.4 1)**: *"If the FILE STATUS clause is specified, the data
  item referenced by data-name-1 is updated to contain the value of the I-O status for the file connector
  referenced by the subject of the entry…"*

The chain closes without a gap: a transfer record is obtained *as if a READ statement had been executed*, so it
IS a READ for §9.1.13.1's purposes; §9.1.13.1 requires the status to be set during it and **before** any
exception processing statement; §12.4.5.8.4 GR1 requires the program's FILE STATUS item to carry it. A USE
declarative entered from inside the transfer therefore reads a value the standard says it should not see — and
after the loop, the item ends up holding the CLOSE's status regardless of what any of the N reads did.

## ⛔ A citation defect at the same site, found while re-deriving the above

`SortEmitter.cs:140`'s inline comment reads **"(GR15 b) / MERGE GR13 b)"**. MERGE's GIVING transfer is
**§14.9.24.4 GR12** a)/b)/c); **GR13** is the unrelated fixed-length space-fill rule (*"If the file referenced by
file-name-4 contains only fixed-length records, any record … containing fewer character positions than that
fixed-length is space filled on the right"*). The method's OWN doc comment eight lines up (`:130-133`) already
says *"SORT GR15 / MERGE GR12"* — so two comments in one method disagree and the inline one is wrong. This is
CLAUDE.md rule 1's inheritance failure mode exactly: the quoted text is genuine, the clause NUMBER was never
re-derived. Correct it in the same change set.

## Why the fix is a design-doc decision, not an implementer's

A per-record store is a store in the hot path of every `SORT … USING` and `MERGE … GIVING`. The doc must choose
the SHAPE, and the emitter already knows all three predicates at COMPILE time, so this is a structural question
and not a cost question (`feedback_design_structural_singular_first`):

1. **Unconditional** — emit `EmitStoreFileStatus` inside both loops.
2. **Only when the file has a FILE STATUS clause** — `EmitStoreFileStatus` already returns immediately when
   `file.FileStatusName is null` (`SequentialIoEmitter.cs:630`), so the emitter can simply not emit the call at
   all for such a file and the loop is byte-identical to today's.
3. **Only when a declarative or EC checking can observe it** — `dispatch.UseDecls`, or `ec.IoMaskFor(file) != 0`;
   the same predicates `EmitUseHook` itself switches on (`SequentialIoEmitter.cs:36`, `:51`).

⚠ 2 and 3 together emit nothing extra for the overwhelmingly common file with neither a FILE STATUS clause nor a
declarative — which is why the answer is a shape and not a benchmark. ⛔ Whichever is chosen, the same predicate
must govern the store and the hook, or the two go out of step the next time one of them is edited.

**Which doc.** `docs/COBOLNET_FILES_DESIGN.md` is the only file/sort design doc in `docs/` (there is no
`DESIGN-sort-merge.md` under `docs/rearchitecture/`), so the decision belongs there, cross-checked against
`docs/COBOLNET_DESIGN.md` §0.5's deep-dive list. It should state the rule for **all four** implicit statements —
OPEN, READ, WRITE, CLOSE — as one contract, not for the loop alone.

## Also in scope, and it needs no loop at all

The **implicit OPEN's** store is missing on both methods and costs two lines outside any loop (`:98/:99` and
`:136/:137`). It is the half that makes `EmitUseHook`'s documented contract false today, and it can land with the
design decision or ahead of it.

## Repro

A USING file whose implicit READ completes unsuccessfully other than at end (e.g. a record-identification
failure), with a `USE AFTER STANDARD ERROR PROCEDURE` declarative on that file that DISPLAYs its FILE STATUS item:
the declarative shows the value left by the last statement that stored one — the implicit OPEN's predecessor
during the loop, and the CLOSE's afterwards — never the READ's. The mirror case on GIVING is an implicit WRITE
that fills the medium ('34').
