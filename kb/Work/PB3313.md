# PB3313 — the lock directory vanishes under its creation and a waiting hold answers Unavailable

> ⚙ **flags:** wrong-answer · silent

**Found by** the w1095i (PB1099) landing: `enqueue.py land` stopped exit 5 on `a9bc4326387b` with the Linux gate's one red,
`RegionLocksDriftTests.TwoWaitingHoldsBothGetTheByteInTurn(kind: LockFiles)`, `Expected [Ok, Ok] Actual [Unavailable, Ok]`
(33,918 of 33,919 unit cases passed). It is the Linux arm of the symptom kb/Work PB3109 fixed for Windows, with a different
mechanism.

**Attribution (measured, WSL, 32 cores).** The branch's diff touches nothing under `src/Cobol.Net.Runtime/IO/Sharing/` nor
`HostFile`'s lock-file questions. The one theory, run 160 times at 24 `dotnet test` processes at once: 2 LockFiles failures at the
branch head `a9bc43263`, 4 at origin/main `2ece4453f`. Main's defect, not the branch's.

**Root cause (measured).** A scratch harness of the test's own shape (two endpoints, barrier, waiting exclusive holds on
`HostRegionLocks.StoreMutexByte`), recording every first-chance exception of the thread whose hold answered non-Ok, 8 processes x
3,000 rounds beside 24 CPU burners: 14 of 24,000 rounds non-Ok, and all 14 ended on `IOException HResult=17 ("already exists") at
System.IO.Directory.CreateDirectory`, right after `FileNotFoundException at File.GetUnixFileMode`. The sequence:
`SidecarLockFiles.Publish` (`src/Cobol.Net.Runtime/IO/Sharing/SidecarLockFiles.cs:98`) calls `HostFile.CreateLockDirectory`
(`src/Cobol.Net.Runtime/IO/FileSupport.cs`) OUTSIDE its retry `try`; the probe finds no directory, a sibling's publication makes it,
.NET's `mkdir` answers `EEXIST`, the sibling's CLOSE (`LockFileHolder.Dispose` -> `RetireDirectory` -> `rmdir`) removes it, and
.NET's own existence check then finds nothing and throws the `EEXIST`. It escapes to `SidecarRegionLocks.Hold`'s
`catch (IOException)` -> `Unavailable`, whatever `wait` says. Windows' .NET treats the same race (`ERROR_ALREADY_EXISTS`, then
gone) as success, and the publication that follows retries on `DirectoryNotFoundException`.

**Harm.** `KeyedConnector.HoldStoreMutex` maps any non-Ok to "no mutex", so the statement runs unprotected (the PB2936 lost-update
shape); `SidecarColumnLockHost.Establish` reads the same escaping `IOException` as `Unavailable`, an OPEN granted with no file
lock. The lock-file hosts run off Windows and off OFD-Linux (macOS above all), so a shipped program meets it there; the gate meets it
in `RegionLocksDriftTests`, which holds the lock-file host to the contract on every machine, and it could bounce any landing.

**Fix.** `HostFile.CreateLockDirectory` reads `EEXIST` with no FILE at the name as that race and returns
(`HostFile.IsClosingSiblingRace`), as .NET answers it on Windows (which fails an existing name only when a file is there); with
nothing left at the name `Publish`'s `OpenLockHolder` then meets the missing directory and publishes again (its bounded retry,
"each retry is a different race lost"). Any other failure still throws. The same harness with the fix: no `EEXIST` in 248,000 rounds
(24,000 + 48,000 + 48,000 + 128,000), and one non-Ok hold by a different, rarer mechanism, PB3314 (open). No test can freeze .NET between `mkdir` and its check without a native seam
(the lock-file host makes no native call), so the witness stays the repetition one. The design rule is in
`docs/rearchitecture/DESIGN-runtime-library.md` beside PB3109's.

**Sibling sweep.** Every other step of `Publish` and `Look` already classifies a vanished directory or file as a lost race
(`DirectoryNotFoundException`, `FileNotFoundException`, `LockFileState.Gone`); `CreateLockDirectory` is the only caller of
`Directory.CreateDirectory` in the runtime (`grep`), and its Windows arm needs nothing (.NET's own check). Its `SetUnixFileMode`
already swallows a directory gone again.

**Branch review R3-1 (w1106a).** The first fix swallowed `EEXIST` only when NOTHING was at the name (`!Path.Exists`), so the
race's other arm still threw: the sibling's CLOSE removes the directory, .NET's check finds nothing and builds the `EEXIST`, and the
sibling's NEXT publication makes the directory again before the filter looks, so `Path.Exists` is true and the exception escapes
`Publish` into `Hold`'s `catch (IOException)` (`Unavailable`; `HoldStoreMutex` runs the statement unprotected). The two-endpoint
witness cannot reach it (after its release the other endpoint waits at the barrier). The decision is now
`HostFile.IsClosingSiblingRace`: `EEXIST` with the name empty or a directory is the race (the directory-again arm returns, the
directory being another holder's, as at the method's first probe); a file at the name, a name the host will not describe, or any
other errno keeps the failure. `RegionLocksDriftTests.ALockDirectoryEexist_IsTheClosingSiblingRace_UnlessAFileHoldsTheName` asks
the decision of all four states directly; its `directory` row is red under the first fix.

Related: PB3109 (landed; the Windows arm, delete-pending), PB2917, PB2936, PB1957 (CI invariant: the local gate RAN the witness,
which is a repetition race).
