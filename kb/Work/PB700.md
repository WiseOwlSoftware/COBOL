# PB700 — OPEN — a known residue, named

Found 2026-09-05 by the `PB352`/`PB354` implementer (report §"New defects" c), while adding the sort-file screen START
had been missing: UNLOCK is the one verb that keeps its own copy. Both arms reject, so no program is miscompiled;
the cost is the usual one — two spellings of one rule, and the next sweep re-finding it.

## The facts

`cite.py --check 14.9.47.3 "sort"` → OK 1): UNLOCK's clause states the sort-file ban in its own words, which is
why the inline screen cites a different § and emits a different code from `ScreenSortMergeFile`'s. PB140's doc
comment on `ScreenSortMergeFile` already calls the old posture "a patchwork … a bind error at UNLOCK" — a deliberate
residue.

## Fix

Route `BindUnlock` through `ScreenSortMergeFile` with the verb name, and let the screen carry BOTH citations where
a verb's own clause restates the rule (a `verbClause` argument, so the message can name §14.9.47.3 SR1 for UNLOCK
and §13.4.6.3 for the rest) — one implementation, one code, the negative golden for UNLOCK on an SD re-trued to
COBOLNET1692 if the code changes (check whether any golden pins COBOLNET1512 first). Small; pairs naturally with
PB699's move of the entry rules.

## Registrar verification 2026-09-06 — PB700 is also a doc-vs-code divergence, and the descriptor quotes text the standard does not have

The PB699 implementer took PB699 and reported PB700 **not started**, with the reason (the two do not share a
site: PB699 is `DataBinder.ResolveFiles` -> `FileControlKeyRules`, PB700 is the UNLOCK verb binder). `status:`
is untouched here and stays `open`. What follows is that report's two hand-off facts, verified against main
(`89555b09`) — plus a third the verification turned up, which is worse than either.

### 1. The site, confirmed line for line

`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/FileLockBinder.cs:36-38`, inside `BindUnlock` (`:27`):

```csharp
if (file.IsSortMerge)
    ctx.Edition.Error("COBOLNET1512", $"UNLOCK may not name the sort/merge file '{name}' "
        + "(ISO §14.9.47 SR1)");
```

A **raw string code**, not a `DiagnosticCatalog` descriptor — where every other I-O verb calls
`ctx.Validation.ScreenSortMergeFile(file, verb)` ->
`DiagnosticCatalog.SortMergeFileInIoStatement`. The rule it cites is real:
`cite.py --check 14.9.47.3 "sort"` -> **OK §14.9.47.3 1)** *"File-name-1 shall not refer to a sort file or a
merge file."*

⚠ **And the raw code is reused inside the same file for an unrelated rule.** `FileLockBinder.cs:93` emits
`"COBOLNET1512"` again for the AUTOMATIC lock-phrase ban (§14.9.30 SR4 / §14.9.51 SR22 / §14.9.35 SR4). So
COBOLNET1512 currently spans two rules with nothing in common but this file — which is the reason a raw literal
is not a descriptor, made concrete. Routing the sort-file arm to COBOLNET1692 also un-conflates the code.

### 2. COBOLNET1692's descriptor already documents the fix as done

`src/Cobol.Net.Editions/Diagnostics/DiagnosticCatalog.cs:462-469`, `SortMergeFileInIoStatement`. The claim is at
**`:466`**, verbatim:

```
+ "FILE, OPEN, READ, REWRITE, START, UNLOCK and WRITE all reject it at compile time. The old posture "
```

reading in full, `:464-468`:

> *"An input-output statement names a sort-merge (SD) file. “A sort-merge file is referenced only by a SORT,
> MERGE, RELEASE, or RETURN statement” (and a SORT/MERGE USING/GIVING) — CLOSE, DELETE, DELETE FILE, OPEN, READ,
> REWRITE, START, **UNLOCK** and WRITE all reject it at compile time. …"*

`docs/DIAGNOSTICS.md:194` is generated from it and carries the same sentence. So the normative user documentation
says UNLOCK rejects an SD **through COBOLNET1692**, and the code emits COBOLNET1512 from a raw literal instead —
CLAUDE.md rule 6, in the same change set as the fix.

### 3. ⛔ NEW — the descriptor's QUOTED sentence is not in the standard, at that clause or anywhere

The quotation marks in `:464-465` assert verbatim spec text. It is not:

- `cite.py --check 13.4.6.3 "A sort-merge file is referenced only by a SORT, MERGE, RELEASE, or RETURN statement"`
  -> **FAIL: §13.4.6.3 exists but does NOT contain it**
- `cite.py --find "A sort-merge file is referenced only by"` -> **NO CLAUSE contains it**
- `cite.py --find "referenced only by a SORT"` -> **NO CLAUSE contains it**
- `grep -n "SORT, MERGE, RELEASE\|RELEASE, or RETURN"` over `specs/ISO_COBOL.md` -> **0 hits**

§13.4.6.3's four syntax rules are, in full: 1) *"File-name-1 shall be specified in a file control entry."*
2) *"One or more record description entries shall be associated with the sort-merge file description entry."*
3) *"File-name-1 shall not be specified in an input-output statement."* 4) the record-description-entry rule
(FROM / INTO). **SR3 is the genuine text and it says the same thing in different words** — which is exactly how
this survives: the cited clause is real and answers the right question, so `--check` on the SECTION passes and
only a check on the SENTENCE fails
(`feedback_a_real_clause_can_answer_a_different_question`; CLAUDE.md rule 1's inheritance shape).

The shared screen's own message paraphrases correctly and without quote marks
(`src/Cobol.Net.Compiler/Binding/Validation/StatementValidation.cs:399-400`:
*"an SD file-name may appear only in SORT/MERGE/RELEASE/RETURN (ISO §13.4.6.3 SR3/SR4)"*). The descriptor is the
only place that presents it as a quotation, and `docs/DIAGNOSTICS.md` republishes it. **Replace the quoted
sentence with §13.4.6.3 SR3's actual words in the same change set** — and sweep `DiagnosticCatalog.cs` for other
descriptors whose quoted text has never been `--check`ed at the sentence level.

### 4. The golden question this note asks, answered

*"check whether any golden pins COBOLNET1512 first"* — **no golden pins the CODE.** The only two files under
`tests/conformance/` naming COBOLNET1512 are `2002/pb319_sr8_antecedent.cob:19` and
`2023/l1_read_lock_mode_governs.cob:30`, and both hits are **comment lines** describing a historical posture, not
expectations.

⚠ **But `tests/conformance/negative/unlock-sort-file.err` still has to be re-trued**, on the message rather than
the code. It pins:

```
UNLOCK may not name the sort/merge file
```

and `ScreenSortMergeFile` writes `"{verb} may not name the sort-merge file '{name}' — …"` — **`sort/merge`
becomes `sort-merge`**, so the substring no longer matches. One character, and it is the kind that turns a
correct fix into a red gate if it is not in the same commit.
