# PB1026 — LANDED

## The rule
`OK  §13.18.22.4 4)` — "If the EXTERNAL clause is specified in a file description entry: a) the file connector associated
with this file description entry is an external file connector; and" (b) the record area is shared by every program
that describes the file EXTERNAL.

## What the fixer owes
The run-unit's EXTERNAL cell must carry the whole shared area PB981 defines (character half AND the out-of-line
members), so every program describing the file sees the same record; goldens with two separately-compiled programs.

## Landed (2026-09-23, wave 57 finisher C)
Re-probed on the finisher's build: `w57c/e1.cob` (an EXTERNAL FD with a dynamic-length record) → COBOLNET0899, as
filed. The sweep found a SIBLING with the same root that was a silent wrong answer, not a loud one: a
WORKING-STORAGE `01 G EXTERNAL. 05 A PIC X(3). 05 D PIC X DYNAMIC LENGTH.` compiled, and `D` was a ZERO-WIDTH
byte window of the run-unit cell — `DISPLAY G` printed only `A` (and an ADDRESS-OF-taken variable-length group,
the same cell-backed shape, shifted every member after `D` by its one-character seed).

**Root.** The cell-backed storage shape (`ForceStringCanonical` — EXTERNAL, ADDRESS OF, BASED) carried only
the CHARACTER half of an area. `StorageCell` already had a second half, its managed slots (PB231 — pointers);
a dynamic-length item now rides it too: `OK §8.5.1.10.3` "may be located elsewhere in the computer's memory".
`DataItem.ClassDynOrdinal` numbers the class's dynamic-length leaves (one writer, the forcer); `Place.DynSlotWindow`
reads/writes `StorageCell.DynAt/SetDynAt`; `Place.VarGroupWindow` makes a group over such leaves read and write as
its CONTIGUOUS image (`OK §8.5.1.11.2`; `StorageCell.ContiguousAt/StoreContiguousAt`, the D-FRA take step) and cross
a variable-length MOVE / boundary as its `CobolVarGroup` carrier; both derive from `Place.CellWindowCoding`, which
`ProgramEmitter.PrefixPlace` re-anchors with one expression. The four `PlaceRenderer` variable-length dispatchers,
DISPLAY, `CallPlaceIsVarGroup` and the FUNCTION LENGTH sum each gained the cell arm. A dynamic-length leaf seeds
zero bytes (`OK §8.5.1.12.3` "all dynamic-length elementary items are considered to be of zero length") and its
VALUE seeds its slot (`GroupImageCodec.CellDynSeeds` → `StorageCell.SeedDyn`; `OK §8.6.4` "If no VALUE clause is
specified, the length of that item in its initial state is zero"). Refused by name: a dynamic-length item inside
a table element and a dynamic-capacity table (`VariableLengthCellResidueOf`) — the struct composer's own exclusions.

**EXTERNAL FD.** `OK §13.18.22.4 4)` b) "the data contained in all record description entries subordinate to that
file description entry is external": the character half is one cell `FD::<name>` (via `FileModel.CharacterAnchor`),
and each out-of-line record its own cell `FD::<name>#<k>` (k = ordinal among the file's out-of-line records) — GR5
externalizes the FILE name only. A pointer-class record rides its cell's managed slot (`OK §13.18.22.3 4)` restricts
the clause "specified for a data item"; here it is specified for the file — CONFORMANCE.md §3 D-FRA).

Golden `2014/pb1026_external_out_of_line_records` (three separately compiled programs, different record names);
negative `pb1026-external-dynamic-record-at-2002`. Row GR-13.18.22.4-4 → CONFORMS (batch `pb1026-external-area`).
