# PB663 — LANDED — a formal with no arm for its class

Found 2026-09-05 by the `PB231` pointer-third implementer (report §"New defects" (1)), reproduced on the pristine
main-tree compiler, so pre-existing and independent of the byte-window work.

## Repro (`--std 2002`+; `<a9d94900 scratch>/PB231-pointer/probe9.cob`)

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. PROBEP9.
       DATA DIVISION.
       LINKAGE SECTION.
       01 L-P USAGE POINTER.
       PROCEDURE DIVISION USING L-P.
       SUBMAIN.
           IF L-P = NULL DISPLAY "SUB NULL" ELSE DISPLAY "SUB SET" END-IF
           GOBACK.
```

```
error CS1503: cannot convert from 'string' to 'CobolNet.Runtime.ManagedPointer?'
```

Generated: `private ManagedPointer<string> __lnkp0 = ManagedPointer<string>.Cell(new string(' ', 1));` and then
`ManagedPointer.SameTarget(__lnkp0.Value, null)` — a string-cell carrier where the value is a pointer.

## The rule

§13.18.60.4 GR23: "Each implementor defines the precise effect of the USAGE POINTER clause upon alignment, size,
representation, and range of values of the data item in the storage of the computer." (`OK §13.18.60.4 23)`) —
this implementation's representation of a data-pointer is the pointer carrier (`CobolPtr`, per the DATA_MODEL
design); §14.2.3 GR8 makes a BY REFERENCE formal the same storage as the caller's argument, so the formal must be
carried by the class's own carrier, exactly as a numeric formal is.

## The mechanism

`src/Cobol.Net.Compiler/CodeGen/ProgramEmitter.cs:234` (the formal-carrier loop): `isNum ? … :
ManagedPointer<string>.Cell(new string(' ', Math.Max(1, f.Item.ImageWidth)))` — two arms, numeric and
"everything else as a string cell". A pointer, program-pointer or object-reference formal falls into the string
arm; the binder then emits pointer operations against it.

## Fix shape

The formal-carrier loop dispatches on the item's CLASS through the same classification `PB231`'s
`SlotWindow.CarriedBySlot` now defines (the one population test for pointer/object-class items): a pointer-class
formal gets the pointer carrier (`ManagedPointer<CobolPtr>`-shaped, matching how a BY REFERENCE pointer argument is
passed at the call site — read `CallAbi`/`CobolArgAdapt` for the argument side first, since the carrier must agree
at both ends), an object-reference formal its reference carrier. Goldens at 2002/2014/2023: a subprogram with a
`USAGE POINTER` formal tested for NULL and dereferenced (called BY REFERENCE with a NULL pointer and with a real
address), a `PROGRAM-POINTER` formal, and an `OBJECT REFERENCE` formal; a drift test over `LinkageCarrierTests`
(or the nearest existing class) that every `PicCategory` a LINKAGE item can have maps to a carrier arm — derived
from the category enum, so a new class is a red test rather than a string cell.

## Landed 2026-09-22 (wave 44D)

RE-PROBED FIRST on the implementer's own build of `2f6b38c61`, and it still reproduced exactly as written:
`error CS1503: Argument 1: cannot convert from 'string' to 'CobolNet.Runtime.ManagedPointer?'`, with the
generated `private ManagedPointer<string> __lnkp0 = ManagedPointer<string>.Cell(new string(' ', 1));` and
`__lnkp0 = CobolArgAdapt.Text(__args, 0, 1);`. One correction to the note's repro path: a FORMAT 1 CALL cannot
reach this callee at all — §14.9.4.3 SR10 ("If the BY REFERENCE phrase is specified or implied for an
identifier-2, that identifier shall be neither a strongly-typed group item nor a data item of class object or
pointer") is enforced as COBOLNET1679, so the crossing is reachable only through a Format-2 activation
(`AS NESTED`, a prototype) or a separately compiled activator. That is why the hole survived the entire pointer
increment: nothing in the corpus could call such a program.

THE FIX IS A CLASSIFICATION, NOT AN ARM. The activating side already emitted the right carrier
(`ManagedPointer<ManagedPointer>.OverField(…)` — measured), because `RefCarrier`'s fall-through arm is the item's
own `ElementType`. The activated side asked a different question: `bool isNum`, numeric on one side and "a
space-filled `ManagedPointer<string>`" on the other. Two formulations of one rule, and the callee's had TWO arms
where the model has FOUR. Both sides now read ONE classification — `CallCrossing` { Native · Text · VarGroup ·
Managed } via `CallEmitter.CrossingOf(Place)` and `ProgramEmitter.FormalCrossing(LinkageFormal, Place?)` — and
`ProgramEmitter.FormalAdopt` is the ONE adoption expression, replacing the two copies of the dispatch that the
resident and round-trip loops each spelled out (both were missing the managed arm: the two-arm shape with the
arms one method apart).

WHICH ARM DID I FIX? Both callee arms and both caller arms. (1) The CARRIER-RESIDENT arm — where a pointer formal
actually lives, since residency demands a childless elementary non-float item and a pointer is one. (2) The
ROUND-TRIP arm, where a managed item classified NATIVE and asked `CobolArgAdapt.Num<ManagedPointer>` for a
carrier whose `struct, INumberBase<T>` constraint it cannot satisfy — unreachable on conforming source
(§13.18.44.3 SR12/SR14 bar a REDEFINES of class pointer) but wrong, and now correct. (3) The BY REFERENCE and
(4) the BY VALUE legs: §14.2.3 GR10 names "a SET statement" as the filling for a formal of class object or
pointer, which is exactly `CobolArgAdapt.SlotValue`'s detached reference copy, so COBOLNET0899
(`by-value-formal-carrier`) no longer refuses them — it now covers only a FLOATING-POINT usage and a METHOD's
BY VALUE formal on the INVOKE channel. The caller's `RefCarrier` and BY CONTENT snapshot were re-expressed over
the same switch (byte-identical output, one rule); `CallNumCarrier` became `CallCellCarrier`, because it always
answered "the item's own carrier" for the managed lane too and the name said otherwise.

`CobolArgAdapt.Slot<T>` / `SlotValue<T>` admit only the same `T` and degrade to the loud omitted carrier
otherwise, which is the whole of the adaptation: §14.8.2.3.2 ("If either the argument or the formal parameter is
of class pointer, the corresponding formal parameter or argument shall be of class pointer and the corresponding
items shall be of the same category", plus its object-reference rules 1–3) leaves no conversion to invent.
`Omitted<T>` gained the data-pointer's benign empty value, `ManagedPointer.Null` (§8.4.3.10.4 GR1) — `default`
would have turned GR12's documented leniency into an NRE.

("the callee-side formal carrier for those categories is emitted as the STRING carrier" / "the class-object /
class-pointer SET leg, which is loud-staged at bind with COBOLNET0899"). Both are CONFORMS

removed.
