# PB3782 — the LSP rule is dead as dispatched

**Sites:** `.claude/skills/workstream/templates/dispatch-spec-implementer.md` (the C# NAVIGATION and LSP DIAGNOSTICS paragraphs), `.claude/skills/workstream/check_practices.py#BRIEFS` (the `LSP DIAGNOSTICS` pattern), `.claude/skills/workstream/templates/MANDATORY-PRACTICES.md` (P13), `.claude/agents/cobol-implementer.md`, `.claude/agents/cobol-reviewer.md`

## Measured

Every role's first request lists `LSP` among the deferred tools (name only; the schema loads through `ToolSearch`).
The spec's two P13 paragraphs tell the implementer to use the LSP tool before grepping and to act on its diagnostics
before each commit; neither says to load it. Over 105 agents the tool was never loaded (4 ToolSearch calls in all:
TaskStop, Monitor, WebSearch, WebFetch) and never called; implementers navigated with Bash grep (2,343 Bash calls to
11 Grep). `check_practices.py` passes the spec because the text `LSP DIAGNOSTICS` is present. The owner's instruction
of 2026-10-01 (hints left unfixed pile up for the branch review) is in no effect, and the paragraphs cost about 250
tokens of every spec for nothing.

## Fix

Make the rule followable and measure it, or retire it with its checker pattern (O1), never leave it enforced as text:
the spec's paragraph opens with the load (`ToolSearch select:LSP`, once, before the first C# edit) and the diagnostics
step names the call; the reviewer's branch form checks the diagnostics the same way. If the next two waves show the
tool loaded and used by most implementers, P13 stands; if the LSP (csharp-ls) proves unavailable in a worktree
(`tooling_check.py` already probes it in the session), P13's diagnostics half becomes a build-time analyzer step the
gate runs (the analyzers' warnings-as-errors) and the navigation half is dropped, its pattern removed from
`check_practices.py` in the same change.

Guard: `check_practices.py` requires the load line beside the `LSP DIAGNOSTICS` pattern; the measurement
(`measure_costs.py` or the next skills-opt run) reports LSP calls per implementer as a line, so a dead rule is seen.

## Acceptance

A rendered spec carries the load line; in the next wave the share of implementers that called the LSP tool is
reported in the wave's summary; P13 either shows use or is retired with its checker pattern and the owner told why.
