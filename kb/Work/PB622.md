# PB622 — LANDED (closed by the analyses sweep) — one probe decides whether this is a defect

Found 2026-09-05 by the `PB252` implementer (report §"New defects" (B)), which closed the exact-carrier VALUE
functions against wrapping and, by construction, left the RESCALE class outside its reflection-closed set — the
exemption prose in `ExactCarrierBoundaryDriftTests` says so rather than pretending coverage. Not constructed as a
repro; filed as the measurement it needs ([[reachability_is_measured_not_deduced]]).

## The site

`src/Cobol.Net.Runtime/Intrinsics/CobolIntrinsics.Exact.cs` (`:64`–`:73` on PB252's tree): `Floor(Int128 v, int
scale)` is `if (scale <= 0) return v * Pow10.AsWide(-scale);` and `Truncate` has the same shape. A `PIC 9(n)P(m)`
item gives a negative scale (§13.18.40.4's `P` semantics), and `v × 10^m` is unchecked, so for large m the product
can pass `Int128.MaxValue` and wrap — the same shape PB252 just removed from SUM/RANGE/MEAN, one class over. §14.7.5
r5 (`OK §14.7.5 5)`) is the clause that makes an escape the conforming answer if the range is exceeded.

## The probe

Whether the emitter can hand `Floor`/`Truncate` a negative scale at all: does `Arg(ic, 0)` (PB251's `INTAKE(LANDED)`
seam) normalise a `P`-scaled operand to scale ≥ 0 before the call, or does the raw negative scale reach the runtime?
Build a `PIC 9(1)P(37)` operand (value 9 × 10³⁷, in range for the item) and call `FUNCTION INTEGER-PART` /
`INTEGER` / `FRACTION-PART` on it under native arithmetic; the product 9 × 10³⁷ × 10³⁷ is well past the carrier.

## Outcomes

- Reachable → convert to `kind: defect` (wrong_answer, silent), and the fix is PB252's shape: route the multiply
  through `ExactMul` with the function name, and extend `ExactCarrierBoundaryDriftTests`' closed set to the
  `(Int128, int)` rescale signature with its own boundary pin.
- Unreachable because the intake normalises the scale → record where that normalisation lives, add the assertion
  that pins it (a drift test that `Floor`/`Truncate` are never called with a negative scale), and close.

## Closed (analyses sweep, 2026-10-23)

Adjudicated read-only by an Opus cobol-adjudicator on main e7cf38ce4; accepted by the Mythos session.

Closed 2026-10-23 (open-analyses sweep S4). The rescale arm is guarded: 2c8889d36 (PB2698) changed Floor and Truncate at scale <= 0 to ExactMul(v, Pow10.AsWide(-scale), name), so any carrier overflow is the §14.7.5 size error, never a wrap. The overflow is also unreachable from source: §13.18.40.3 SR14 limits a numeric item to 31 digit positions counting P (COBOLNET0801 refuses 9P(37)), so the rescaled value is below 10^31. Probe probes/pb622/p622b.cob on e7cf38ce4: INTEGER, INTEGER-PART and FRACTION-PART of S9P(30) holding -9E30 return the exact values. No further work.

Evidence: Commit 2c8889d36 (PB2698, 2026-10-10) routed Floor/Truncate's negative-scale multiply through ExactMul (CobolIntrinsics.Exact.cs:76,83), so the product escapes loud; and §13.18.40.3 SR14 caps a numeric item at 31 digit positions including P, so v*10^m < 10^31 never nears Int128. Probe probes/pb622/p622b.cob: INTEGER/INTEGER-PART/FRACTION-PART of S9P(30) = -9E30 print -9000000000000000000000000000000 / same / 0.
