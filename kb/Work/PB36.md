# PB36 — LANDED — MODULE-NAME's r5 names four activation mechanisms and INVOKE is not among the implemented ones

> ⚙ **flags:** wrong-answer
> §15.65.4 r5. The refuter found the blast radius LARGER than the adjudicator measured, and refuted the
> adjudicator's load-bearing claim that "the STACK arm is already right".

## ⛔ THE RULE, AND THE JUSTIFICATION THAT DID NOT GOVERN

**§15.65.4 r5** names the mechanisms outright: *"the returned value is the name of the runtime element that
activated the currently running runtime element. This may be by a CALL statement, **an INVOKE statement**, a
function reference, or an inline invocation."*

`ModuleStack`'s own class comment said the omission was *"conformant, not residue: §15.65.4 r3/r4 make the
returned form for method-id elements implementor-defined"*. **Both cited rules are real and neither governs.**
r3 is about a runtime element that is **not a COBOL runtime element** — a COBOL method is one. r4 is about the
**FORM** of the name and *"may return the name as specified in the program-id, function-id, or method-id
paragraph"* — it lists **method-id**, which presumes the element is on the stack. Latitude over which name string,
never over whether the frame exists. (Third time this session a design comment cited a true clause that answers a
different question — see [[PB43]] and [[PB24]].)

## 📐 MEASURED BEFORE (at `31e96dbe`) — inside a method

| keyword | got | required |
|---|---|---|
| `CURRENT` | `PB36INVK` — the CALLER | the running element's compilation unit (r7) |
| `ACTIVATING` | `[ ]` — a single space | `PB36INVK` (r5) |
| `STACK` | `PB36INVK; ` — no method at all | the method's unit, then the chain (r9) |

⛔ The ACTIVATING answer was the worst of the three: **r5 reserves a single space for a MAIN PROGRAM**, so the
method was claiming to be one — indistinguishable from the legitimate case.

## ✅ FIXED — one push, in the method body

The frame is pushed INSIDE the emitted method (`OoEmitter.EmitMethod`) in a `try`/`finally`, **not at the INVOKE
site**: a method is reached by a typed direct call, by the universal `__CobolInvoke` switch, and by an inline
invocation, so a per-site push would be the two-arm dispatch this compiler keeps re-learning
([[feedback_two_arm_dispatch]]). The frame is `(method name, declaring class as the unit's outermost, not
nested)`, which makes r7/r5/r9 all fall out. The `finally` matters: a leaked frame makes every later MODULE-NAME
read one element too deep, and a method exits by RETURNING, by GOBACK unwinding as `MethodReturn`, or by an
exception reaching the invoker.

**MEASURED AFTER:** `I-CUR=[CPB36MN]` · `I-ACT=[PB36MODNAME]` · `I-STACK=[CPB36MN;PB36MODNAME; ]` · the frame
pops (`AFTER-STACK=[PB36MODNAME; ]`). CALL and function-reference paths are byte-identical — pinned in the same
golden as regressions. Golden: `tests/conformance/2023/pb36_module_name_invoke_activation`.

## ✅ THE SECOND HALF — r9 STACK GRANULARITY, SETTLED BY OWNER DECISION 2026-08-05

The entry recorded that a refuter *"refuted the adjudicator's load-bearing claim that the STACK arm is already
right"*. It was right, and the fix above produced the measurement that proved it — STACK contradicting ACTIVATING
for method-to-method activation.

⛔ **BUT THE DECISIVE CASE TURNED OUT TO HAVE NO OO IN IT AT ALL.** Probing further found the collapse losing
**RECURSION DEPTH** on a plain `RECURSIVE` CALL chain:

```
PB36REC → PB36R2 → PB36R2 → PB36R2        three activations
REC-STACK = [PB36R2;PB36REC; ]            one entry            <- before
REC-ACT   = [PB36R2]                      correct
```

So the defect was never about methods; the method case was the second symptom. The blast radius was larger than
either the adjudicator OR the refuter had measured.

**The ruling: STACK lists RUNTIME ELEMENTS (r9 read literally), not compilation units.** entry 1 = CURRENT (r7);
every entry after it = what ACTIVATING returns within the previous (r5); penultimate = TOP-LEVEL (r10); last = a
single space. The collapse is gone.

| case | before | after |
|---|---|---|
| recursion ×3 | `PB36R2;PB36REC; ` | **`PB36R2;PB36R2;PB36R2;PB36REC; `** |
| method → method | `CPB36MN;PB36MODNAME; ` | **`CPB36MN;SHOW;PB36MODNAME; `** (agrees with ACTIVATING) |
| CALL to a separate program | `SUB;MAIN; ` | unchanged |
| nested (contained) program | `MAIN; ` | **`MAIN;MAIN; `** — the documented cost |

⚖ **The nested repeat is r9's own composition, not a defect**: the first entry is outermost-granularity and the
chain is element-granularity, so for a contained program they coincide. §15.65.1's looser "a list of all the module
names" wording was the alternative and **cannot represent recursion at all**. Documented under §4.2.16 in
`docs/CONFORMANCE.md` row 213.

## ⚙ THE MECHANISM WAS CHALLENGED AND MEASURED, NOT ASSUMED

Owner question: why a custom module stack when .NET already has one? Three reasons `StackTrace` is not a drop-in —
JIT **inlining elides frames** (a correctness hole for a function a program can branch on; suppressing it needs
`NoInlining` everywhere), CLR frames are **not** COBOL runtime elements (0..n CLR frames per COBOL element,
depending on typed vs universal vs inline invocation), and the frame carries COBOL facts the CLR has no notion of
(the unit's outermost id for r7, contained-ness for r8, main-ness for r5).

**Then it was measured** (5 M activations, emitted code at `OptimizationLevel.Release`, median of 5):

| build | median | per activation |
|---|---|---|
| no push | 334 ms | — |
| push/pop, two ambient reads | 393 ms | **+11.8 ns** |
| push/pop, stack cached to ONE ambient read | 372 ms | **+7.6 ns** |

⭐ **The cost was the ambient lookup, not the bookkeeping.** `RunUnit.Current` is an `AsyncLocal`, and Push/Pop
each resolved it — so every activation paid it twice. `CobolModule.Stack` resolves once and the emitted method
holds it across the pair; the golden is byte-identical and 36% of the cost is gone.

⚠ **AND A PROPOSAL OF MINE WAS RETRACTED ON INSPECTION.** I suggested eliding the push when a compilation unit
contains no `MODULE-NAME` reference. **Unsound under separate compilation**: a method that elides its push is
still on the stack when a separately-compiled program it CALLs asks ACTIVATING, and that program would get the
wrong activator. It is the same reason the CALL-side push lives in the runtime rather than in emitted code.

## ⚠ A GREEN TEST HELD THE OLD DECISION, AND MY WAVE-LOCAL FILTER MISSED IT

`IntrinsicFunctionDifferentialTests.ModuleName_StackFromNestedProgram_2023` asserted `K=OUTERM;` and its comment
stated the rejected reading as fact — *"STACK collapses same-unit frames to ONE runtime element (OUTERM), not the
OUTERM;OUTERM duplicate a per-CALL-frame walk gives."* Updated to `K=OUTERM;OUTERM;` with the reasoning and the
§4.2.16 pointer. See [[feedback_green_test_can_hold_a_gap_open]].

⚠ **The wave-local gate did not select it.** I filtered on `~Corpus` (440/440 green) because that is where the new
goldens live; the change was to MODULE-NAME semantics, whose tests are named for it. `~Corpus|~ModuleName` gives
447/447 in the same time. The comprehensive battery caught it — the tiering worked — but the filter should come
from what the CHANGE touches, not from where the new goldens sit.
