# PB96 — LANDED — `66 AC RENAMES A THRU C.` yielded "ababcd" (LENGTH 6) where the record area is "abcd" (4)

> ⚙ **flags:** wrong-answer, silent · found 2026-08-18 writing [[PB93]]'s legal-shape test · **landed 2026-08-18** (DEVLOG 1320).

**Measured** (`scratchpad/pb93/rn.cob`, `--std 2023`):
```
       01 REC.
          05 A PIC X(2) VALUE "ab".
          05 B REDEFINES A PIC X(2).
          05 C PIC X(2) VALUE "cd".
       66 AC RENAMES A THRU C.
           DISPLAY "[" AC "] LEN=" FUNCTION LENGTH(AC).      ->  [ababcd] LEN=6
```
The record's storage is A(2) + C(2) = 4 characters; B overlays A (§13.18.44 — a redefinition adds no storage).

**Spec:** §13.18.45.4 GR1/GR2 — data-name-1 (the alias) is the storage area beginning at data-name-2 and ending at
data-name-3 within the record; §13.18.44.4 — the redefining entry describes the SAME area. The alias's content
is the record's characters from A's first to C's last: "abcd".

**Mechanism:** `DataBinder.ResolveRedefines`'s RENAMES loop composes `info.SpanLeaves` by walking the record's leaves
in declaration order between FROM and THRU and summing `ImageWidth × Occurs` — a redefining leaf (`B`, whose
`RedefinesTargetName` is set) is a VIEW over A's storage, yet it is added to the span as if it occupied its own
characters, and the alias's `Pic.Length` and image both count it. The same walk feeds `SpanLeaves` to the
RENAMES place's read/write, so the alias reads A twice.

**Fix shape:** the span is a STORAGE window, not a leaf list — compose it from the record's NON-redefining leaves
only (`RedefinesTargetName is null`, the same filter `DataItem.ImageWidth` / `RecordLayout` / `BitLayout` already
apply), or better from the record's character offsets: FROM's start offset to THRU's end offset over
`RecordLayout`, so a THRU that ends inside a redefinition (`RENAMES A THRU B`) is the storage window B overlays.
Sweep: `FUNCTION LENGTH` of the alias, the alias as a MOVE/compare operand, a RENAMES range with an OCCURS'd leaf
(SR3 forbids subject items with OCCURS, but a subordinate table inside a group operand?), and the RENAMES place's
write (`WriteRenames`) which distributes back over `SpanLeaves`. Golden: the four-shape probe above (THRU C,
THRU B, FROM B, a THRU inside a nested group).

## As built (DEVLOG 1320)

`RenamesInfo.Span` is a list of `RenamesSpanPart(Leaf, Occurrence, Start, Length)` that TILES the storage window
`[Offset(FROM), Offset(THRU) + Width(THRU) − 1]` — `Offset` is the ONE recursive storage function (a redefiner sits
at its target's offset; a redefining sibling adds no width). The tiling is greedy over EVERY leaf of the record,
REDEFINES views included (a view reads the storage it overlays exactly as the redefined entry does — NC252A's
`RDF8-5 THRU RDF8-6` lies inside a double redefinition of an OCCURS 36 table and only those two views tile it): at
each position the longest whole leaf / whole table cell that starts there and fits, else a partial slice of the most
specific cell containing the position; the cursor advances by what was covered, so no storage is ever counted
twice. A whole part expands every occurrence; an occurrence part is the cell's place, a partial one its ref-mod
view (`RefModPlace(cell, start, length)`); `RenamesPlace` carries each part's width so `WriteRenames` distributes
a store by the parts. `ren.Pic.Length` is the window's width; a window the leaves cannot tile is COBOLNET1655.
The shorter-redefinition-as-data-name-3 case (`RENAMES A THRU B`, B redefining A's first two characters → the
alias is those two characters, tiled by the view B) is a CONFORMANCE.md §4 determination — the
leftmost-to-rightmost reading GnuCOBOL and IBM apply. Golden `2023/pb96_renames_span_over_redefines` (A THRU C,
A THRU B, B THRU C, C THRU G1, B THRU G — reads, LENGTHs, a store through BG distributing to A/C/G1/G2, a store
through AB); NC252A pins the table-inside-redefinition shape. Inventory GR-13.18.45.4-1/2 → CONFORMS.
