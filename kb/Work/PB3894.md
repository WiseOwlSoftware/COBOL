# PB3894 — move-alphanumeric-to-national-copies-bytes: MOVE alphanumeric to PIC N copies the bytes unconverted (MOVE "CD" TO PIC N(2) is not equal to N"CD")

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S4) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\move-alphanumeric-to-national-copies-bytes.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\move-alphanumeric-to-national-copies-bytes\`.

## Summary

Under `-std=cobol2014`, `MOVE "CD" TO NAT` (NAT `PIC N(2)`) stores the bytes `43 44 20 20`: the alphanumeric bytes are
copied unconverted into the four-byte national item and the rest is filled with alphanumeric spaces. A national
literal N"CD" in the same program is stored as `00 43 00 44` (UTF-16, big-endian). The moved item therefore compares
unequal to N"CD". The same happens when the sender is an alphanumeric data item. Class: wrong output.

## Minimal test case

Free reference format (`-fformat=free`), 9 lines, written for this record (reduced from WiseOwl fuzz programs fz01484
and fz03579, night 3).

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. MVNAT.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 NAT PIC N(2).
PROCEDURE DIVISION.
MOVE "CD" TO NAT
IF NAT = N"CD" DISPLAY "EQUAL" ELSE DISPLAY "NOT EQUAL" END-IF
STOP RUN.
```

File: `E:\COBOL-coord\scratch\op\pb3838\records\move-alphanumeric-to-national-copies-bytes.cob`.

Supporting probe (not minimal; `E:\COBOL-coord\scratch\op\pb3838\work\move-alphanumeric-to-national-copies-bytes\probe.cob`):
the national item is redefined by a `PIC X(4)` item and each byte's `FUNCTION ORD` is displayed after the MOVE and for a
VALUE N"CD" item. GnuCOBOL prints ordinals 68 69 33 33 after the MOVE (bytes 43 44 20 20) and 1 68 1 69 for the VALUE
(bytes 00 43 00 44). A second probe (`probe2.cob`, same folder) moves an alphanumeric data item `PIC X(2) VALUE "CD"`
and gets the same result (`item: not equal`).

## Environment

- `cobc (GnuCOBOL) 3.2.0`, Ubuntu package `gnucobol3 3.2-4build1`, WSL2 (Linux 6.18.54.1-microsoft-standard-WSL2 x86_64).
- Commands:
  ```
  cobc -std=cobol2014 -fformat=free -x mvnat.cob

  ```

## Observed result

Compile exit code 0, with `handling of USAGE NATIONAL is unfinished` (line 5) and `handling of national literal is
unfinished` (line 8) `-Wunfinished` warnings. Run exit code 0, output:

```
NOT EQUAL
```

The generated C (`cobc -C`) for line 7 is a call to `cob_move` with the literal and the national field.

## Expected result (per ISO)

Output `EQUAL`.

- ISO/IEC 1989:2023 §14.9.25.3 10) (checked): "table 16, Validity of types of MOVE statements, specifies the validity
  of the move." Table 16 marks an alphanumeric sender to a national receiver as valid.
- §14.9.25.4 6) (checked): "Any necessary conversion from alphanumeric character to national character representation
  shall be performed, before any alignment, in accordance with a correspondence defined by the implementor." The
  correspondence is the implementor's, but GnuCOBOL's own national literal N"CD" shows that its national C is
  `00 43` and D is `00 44`; the MOVE stores `43 44`, which is no national character representation of "CD".
- §14.6.8.5 (checked): "The data in the sending operand is transferred, after any necessary conversion, to the
  receiving character positions and aligned at the leftmost character position in the data item with space fill or
  truncation to the right, as required." The receiver has two national character positions; "CD" fills both, so no
  fill is due. GnuCOBOL instead puts two bytes in the first character position and fills the second with two
  alphanumeric space bytes.
- §8.8.4.2.9 (checked): national operands compare "with respect to the collating sequence of characters specified for
  the current national program collating sequence", and §8.8.4.2.10 1) (checked): "The operands are determined to be
  equal if all pairs of corresponding national characters are equal." After a correct MOVE both operands hold the
  national characters C and D, so the condition is true.

Edition: national data and the alphanumeric-to-national MOVE are 2002 features, present in the 2014 edition; Annex E of
the 2023 standard lists no change to this conversion.

Edition as recorded by the adjudicator: 2014 (national data and the alphanumeric-to-national MOVE are 2002; no 2023 Annex E change). `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Class

GNUCOBOL-DEFECT: wrong output (the stored value, and every comparison or function result that reads it).

## Our compiler (WiseOwl)

WiseOwl COBOL (built from main 6ed90bd1c), `cobol mvnat.cob --std 2014 --source-format free -o mvnat.dll`, then
`dotnet mvnat.dll`: compile exit 0, run exit 0, output `EQUAL`. On the byte probe WiseOwl shows 1 68 1 69 for both
the moved item and the VALUE item (its national representation is UTF-16 big-endian, the same as GnuCOBOL's literal).

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `libcob/move.c`, function `cob_move` (line 1446 in the 3.2 tree): the dispatch on the source type has no case for a
  national destination; an alphanumeric source falls to the `default` arm of the destination switch (around line 1863)
  and calls `cob_move_alphanum_to_alphanum`, a byte copy with alphanumeric space padding. A national destination needs
  a conversion routine (each alphanumeric character to its national code unit, national-space fill, then the alignment
  of the JUSTIFIED clause).
- `cobc/typeck.c`, `cb_build_move_literal` (line 12016) and `cb_build_move_field` (line 12294): the compile-time move
  builders; for this program they emit the `cob_move` call, and a fix that inlines literal moves would also have to
  convert there.

## Draft issue

**Title:** MOVE alphanumeric to PIC N copies the bytes unconverted (MOVE "CD" TO PIC N(2) is not equal to N"CD")

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1), x86_64 Linux.

Steps: `cobc -std=cobol2014 -fformat=free -x mvnat.cob && ./mvnat` with

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. MVNAT.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 NAT PIC N(2).
PROCEDURE DIVISION.
MOVE "CD" TO NAT
IF NAT = N"CD" DISPLAY "EQUAL" ELSE DISPLAY "NOT EQUAL" END-IF
STOP RUN.
```

Observed: `NOT EQUAL`. Viewing NAT through a `PIC X(4)` REDEFINES shows the bytes `43 44 20 20`, while a
`VALUE N"CD"` item holds `00 43 00 44`. Moving an alphanumeric data item instead of the literal gives the same result.

Expected: `EQUAL`. ISO/IEC 1989:2014 (2023 §14.9.25.4 rule 6): "Any necessary conversion from alphanumeric character to
national character representation shall be performed, before any alignment, in accordance with a correspondence
defined by the implementor." The move is valid (2023 §14.9.25.3 rule 10, Table 16: alphanumeric to national), and the
converted characters are then aligned in the receiver's character positions (2023 §14.6.8.5).

Cause: `cob_move` in libcob/move.c has no national destination case, so the move goes to
`cob_move_alphanum_to_alphanum`.
