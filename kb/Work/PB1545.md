**Re-probed** (base `1916f7a1c`, this worktree's Debug build): `hx85.cob` (`01 A PIC XX VALUE X"4142"` +
`DISPLAY X"4344"`) printed `AB` / `CD`, exit 0, at 85, 2002, 2014 and 2023 — confirmed. AFTER: at 85
`hx85.cob(5,19): error COBOLNET0900: the hexadecimal alphanumeric literal X"..." requires COBOL-2002` (and at (8,13));
2002 and later unchanged.

**Rule.** `cite.py --check 8.3.3.2.2 "Format 2 (hexadecimal-alphanumeric)"` → OK §8.3.3.2.2. ⚠ DETERMINATION (VCR row
7.29): the format is a COBOL-2002 introduction. Evidence: IBM's reproduction of the 2002/2014 substantive-changes list
carries "Hexadecimal literals. The ability was added to specify alphanumeric, boolean, and national literals using
hexadecimal (radix 16) notation" — one item for the three forms, whose national and boolean members GnuCOBOL 3.2's
dialect files put at 2002; no NIST CCVS-85 program (459) writes one. GnuCOBOL accepts `X"…"` at `-std=cobol85`
(it has no dialect option for it: silence). Rejected reading: "COBOL-85 had X literals" (IBM's long-standing extension).

**Fix.** constructs.json `hex-alphanumeric-literal-2002`; the gate is on the TOKEN, `LiteralScreenPass.GateFormat`,
position-blind, because the national/boolean literal gates in `VersionConformancePass.VisitNonNumericLiteral` are
statement-scoped and lean on the data-category gate for VALUE clauses, which an alphanumeric item does not have.
Sweep: 32 goldens of the 85 corpus read report files byte by byte through `X"0A"`/`X"0D"`/`X"0C"`; they now declare
`SYMBOLIC CHARACTERS SYM-X0A … ARE 11 …` (§12.3.7, COBOL-85) — output unchanged. `85/pb1181_…`'s hexadecimal
UNSTRING delimiter control moved to the new 2002 golden.

# PB1545 — the original finding

## Finding

`X"4142"` in a VALUE clause and in a DISPLAY compiles and runs identically at `--std 85` and `--std 2002` (scratch `hx85.cob` →
`AB` / `CD` at both). `tests/version-matrix/constructs.json` has no row for the hexadecimal alphanumeric literal, and
`VersionConformancePass` gates only NATLIT/BOOLLIT (recorded as an open question in
`docs/rearchitecture/pb59-mechanism-map-2026-08-09.md`: "If §8.3.3.2 does introduce the hexadecimal-alphanumeric literal at a
specific edition, that is a separate finding about the EXISTING token") — it was never filed. ISO/IEC 1989:1985 defines no
hexadecimal literal (it arrived with ISO/IEC 1989:2002, where `NX"…"` is also gated today), so a program using `X"…"` at
`--std 85` is using a later edition's construct without the COBOLNET0900 every other such construct draws.

⚠ **Confirm before fixing** — `docs/VERSION_CHANGE_REFERENCE.md` covers only 2002→2023, so the 1985 status is not yet written down
anywhere in the repo. If it holds: add the constructs.json row (`introducedIn: 2002`), gate the HEXLIT token at the same site as
NATLIT, and run the edition-gate test sweep (`new-construct` skill) — every golden under `tests/conformance/85/` using `X"` must be
moved or re-derived.
