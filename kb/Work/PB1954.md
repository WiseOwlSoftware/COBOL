# PB1954 — LANDED (adjudicated a defect 2026-10-07; fixed in wave 1037)

Filed by the train-1013 lander from wave 1013 group P's report (`w1013p-PB1246-report.md`, "New defects", item 1).

## Observation

PB1246 (landed in train 1013) made `DataBinder.BindEntries` refuse unequal sibling levels in a DATA record
(`01 G. 05 A. 03 B.` → COBOLNET2771, §8.5.1.3.2: "All items that are immediately subordinate to a given group item
shall be described using numerically equal level-numbers greater than the level-number used to describe that group
item"; `cite.py --check 8.5.1.3.2` OK). The REPORT GROUP chain is bound by a different loop and was not
swept: a report group whose members are `05 COLUMN 1 …` then `04 COLUMN 3 …` under one `03` group compiles clean.

- Repro: `E:\Temp\claude\E--COBOL\e8598e10-eb23-44b5-98e0-e0f07cc381fb\scratchpad\w1013p\p\rpt_lvl.cob`.
- Code site: `src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs` — the report-entry chain loop in front of
  `BindReportEntry` (around line 2392 on the train-1013 tree; the implementer measured ~2745 on its own tree).

## Question to adjudicate

Does §8.5.1.3.2 (level-numbers in a record description) govern a report group description entry, whose hierarchy
§13.18.33.4 GR1 also states? If it does, the fix reuses PB1246's position rule (one rule, one place:
`LevelNumberHierarchy`) in the report chain loop with COBOLNET2771; if it does not, record the reading in
`docs/CONFORMANCE.md` and close.

**Outcome: DEFECT CONFIRMED. Under-rejects, silent.** `§8.5.1.3.2`'s equal-sibling rule governs report group description entries; the pinned build accepts unequal sibling levels in a report group at every edition while it refuses the same shape in a data record (COBOLNET2771). `kind` flips to `defect`; `under_rejects: true`, `silent: true`, `wrong_answer: false` (the run follows §8.5.1.3.2's first sentence: Y attaches to G).

**Spec (cite.py --check OK; the refuter re-ran the decision's nine and added eight).** `§8.5.1.3.2`: "All items that are immediately subordinate to a given group item shall be described using numerically equal level-numbers greater than the level-number used to describe that group item" and "A group includes all group and elementary items following it until a level-number less than or equal to the level-number of that group is encountered".
`§13.18.33.1` ("Level numbers 1 through 49 indicate the position of a data item or screen item within the hierarchical structure described by a data description entry, a report group description entry, or a screen description entry") is the one level-number clause shared by data, report and screen entries; `§13.18.33.4 GR1`; `§13.15.4 GR1`, `§13.8.5`, `§13.15.3 SR3, SR8`; `§13.18.35.3 SR4`. The strongest counter-reading (§8.5.1.3 is framed around records; `§13.15.4 GR2` imports only four clauses) fails: GR2 imports clause rules, not the level hierarchy;
the report section's own rules (SR8, SR9, `§13.15.4 GR1/GR3`) speak of "subordinate", "group", "elementary" and clause 3 defines none of them (only §8.5.1.3.2 does); the rule says "shall", so no latitude (GnuCOBOL 3.2.0 refuses every report probe like the working-storage one: "no previous data item of level NN"). The three exemptions of §8.5.1.3.2 (66, 77, 88) cannot appear in a report group.

**Observed (85/2002/2014/2023).** `rptlvl` (`03 G.` `05 COLUMN 1 ..` `04 COLUMN 3 ..`): compiles clean, prints `A B`; `rptlvl2` (`01 D TYPE DE.` `05 LINE PLUS 1.` `03 LINE PLUS 1.`): clean, `A` / `B`; control `wsctl` (same shape in WORKING-STORAGE): COBOLNET2771 exit 70. Refuter: `rptlvl3` (three deep) clean; `rptocc` (inside `05 G OCCURS 2 STEP 4`) clean at 2002+ (85: COBOLNET0900 for report OCCURS only); `rptsr9` is caught by SR9 (COBOLNET2247) for another reason; control `rptok` (`01 D1. 03 LINE. 05 COL.` then `01 D2. 07 LINE. 09 COL.`) must stay green.
