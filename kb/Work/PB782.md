# PB782 — OPEN — the product's own front door is untested

Filed 2026-09-06 by the registrar from the PB750 finisher's report (§"New defect", "Second, smaller finding").
The report gave the shape and no repro; **every fact below was re-derived on main at `9fad13e5`, and the report's
statement of the contract is wrong in a way that makes the defect worse** — see the premise correction.

## Measured on main

**1. The only exit-code test drives the legacy exe.** `tests/CobolSharp.Tests.Unit/CliExitCodeTests.cs:22`:

```csharp
string p = TestRepo.Src("CobolSharp.CLI", "bin", cfg, "net10.0", "cobolsharp.dll");
```

Its two facts (`:46`, `:71`) assert `exit == 0` for a valid program and `exit == 1` for `--bogus-flag`
("a normal diagnosed failure, not 70 (the catch must not intercept it)").

**2. Nothing anywhere drives the greenfield one.**

```
grep -rn "Cobol.Net.Cli\|cobol\.dll" --include=*.cs tests/     →  (no output)
```

Zero hits across every test project. The `ExitCode` symbol appears in 16 test files; the two that look like
coverage are not:

- `tests/Cobol.Net.Tests.Conformance/StopGobackExitCodeTests.cs` asserts the exit code of the **compiled user
  program** (`prog.dll`, §14.9.42 STOP / §14.9.18 GOBACK status wiring), not of the compiler.
- `tests/Cobol.Net.Tests.Conformance/CompilerUnderTest.cs:128` compiles **in process** through
  `CompilerDriver.Compile`; `CutRunner.RunExit(:75)` then launches the produced `prog.dll`. The `cobol` host is
  never started, so its argument parsing, its `catch`, and its exit mapping are all unexercised.

**3. ⛔ Premise correction — the two CLIs do not share a contract, so the legacy test is not even a
description of the right one.** The report calls it "the CLI exit-code contract (0 = success, 1 = diagnosed
failure, 70 = internal error, never a raw CLR crash)". That is the LEGACY contract. `src/Cobol.Net.Cli/Program.cs`
on main:

```
:130  return 66;                              // RunCheckBatch — manifest not found
:147  return 0;                               // RunCheckBatch — "always exits 0", per its own doc comment,
                                              //   even when entries FAIL (the caller aggregates the PASS/FAIL lines)
:170  return result.Status switch { SourceNotFound => 66, FrontendError => 65, BackendError => 70, _ => 70 }
:179  return options.Run ? Run(result.OutputDll) : 0;
:188  return proc.ExitCode;                   // --run forwards the compiled program's code
:23   Main => BuildParser().Command.Parse(args).Invoke();   // System.CommandLine owns the bad-argument code
```

So the shipped contract is **0 · 65 · 66 · 70 · a forwarded child code · a deliberate always-0 batch mode**, with
the bad-argument code owned by `System.CommandLine` and asserted nowhere. A greenfield twin written by copying
`CliExitCodeTests` would assert `1` for a bad flag and `65`-shaped failures as `1`, i.e. it would encode the other
compiler's contract as this one's. **That is the reason this note is filed at MAJOR and not as a coverage
nice-to-have**: the two contracts diverge silently, and the `--run` and `--check-batch` arms mean a caller
scripting `cobol` cannot distinguish "compile failed" from "the program I ran returned 65" without a documented,
tested mapping.

**4. The stand-in test is on P15's deletion list.** `docs/COBOLNET_REARCHITECTURE_PLAN.md:3108`:
*"**OUT of scope (P15):** deleting the legacy byte engine / `tests/CobolSharp.Tests.*` / the legacy `guard*.sh`
scripts … P14 *builds and proves* the replacement; P15 *removes* the original."* When that happens the repo loses
its only end-to-end CLI exit-code assertion and gains nothing, silently.

**5. And it is not evidence today either — it opts out.** `CliExitCodeTests.cs:49` and `:74`:

```csharp
string? cli = FindCliDll();
if (cli == null) return; // CLI not built in this run — skip
```

A `Fact` that returns instead of skipping is reported as **PASSED** by vstest. On any run where
`src/CobolSharp.CLI/bin/<cfg>/net10.0/cobolsharp.dll` is absent, both facts are green having measured nothing —
`feedback_green_gates_arent_evidence` and `feedback_verdict_evidence_invariant` (a run must assert its
population). Whatever replaces this must FAIL, not pass, when the exe it is about was not built.

## Fix shape

1. **One new fact class in `tests/Cobol.Net.Tests.Conformance`** (the assembly that already owns end-to-end
   process observation) driving `src/Cobol.Net.Cli/bin/<cfg>/net10.0/cobol.dll` through the shared
   `CobolNet.Tests.Shared.ProcessObserver` — ⛔ **not a private `ProcessStartInfo` launcher**; the register
   already carries a note about unbounded private launchers in this very file, and a second one is how the first
   was allowed to stand.
2. **Assert the contract that exists, derived from `Program.cs` and written down beside it**: 0 for a clean
   compile; 66 for a missing source; 65 for a source with a diagnostic; 70 for a backend failure; the forwarded
   child code under `--run`; 0 from `--check-batch` with a FAIL line on stdout. Where the derived answer looks
   wrong (a `--check-batch` whose manifest is missing returns 66 while one whose entries all FAIL returns 0 is a
   real question), that is a defect to file, not a value to enshrine — read the contract out of the code, decide
   it, then pin it.
3. **The exe must be a build input of the test, not a discovered artifact.** No `if (path == null) return;`. If
   the CLI is not built the fact fails with a message naming the missing path, so the population is asserted.
4. **Pin the `System.CommandLine`-owned codes in the same class**, because they are the ones no COBOL.NET source
   line decides: an unknown flag; `--std 1999`, whose validator calls `result.AddError` at `Program.cs:54`; and
   `--help` (plus `--version` if the default directive is enabled — ⚠ neither is declared in `BuildParser`, so
   check whether they exist before asserting them). These are the first invocations a packaging script makes and
   the ones a library upgrade can change under the product without a single source edit.

## Append — 2026-09-09 — re-found from the outside, and the shape has a name now ([[PB795]])

**Why THIS note and not [[PB768]]**, since both name `CliExitCodeTests.cs`: PB768 owns the *launcher* — the

**What the outside view adds.** [[PB795]] landed the answer to the objection this note's item 3 leaves open —
*"how do you skip honestly?"* — and the answer is measured rather than argued: in this pin (xunit 2.9.2 /
xunit.runner.visualstudio 2.8.2) `Assert.Skip`'s `DynamicSkipToken` marker exists only inside
`xunit.assert.dll`, no runner translates it, and a dynamic skip would be reported as a FAILURE. So there is no
honest skip available without a package addition or an xUnit v3 upgrade, and **the correct landing is the one
PB795 took thirteen times over: an unestablished precondition is RED per test, carrying the measured reason.**
That removes the last reason to leave `:49` and `:74` as returns.
