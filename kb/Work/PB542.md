# PB542

## Mechanism — usage-clause-p1
usage-p1-F5-move-operand-class-screen-covers-class-index-only-so-a-class-pointer-move-reaches-the-backend

### Expected, from the standard
`MOVE P TO N` and `MOVE P TO X` with `01 P USAGE POINTER.` are nonconforming twice over -- SR9's list of contexts that may reference a data-pointer has no MOVE, and §14.9.25.3 SR1 excludes class pointer from both MOVE operand positions -- so each shall draw a named compile-time diagnostic. The same holds for `01 PP USAGE PROGRAM-POINTER.` under SR8.

```
(the finding quotes no rule sentence verbatim, so there is nothing to --check; the implementer MUST quote §13.18.60.3 and re-run `cite.py --check` before writing a code comment)
```

### Observed
Neither reaches a binder screen. With a NUMERIC receiver the program dies in the BACKEND with a raw Roslyn error the user cannot act on: `MOVE P TO N` gives `error CS1503: Argument 1: cannot convert from 'CobolNet.Runtime.ManagedPointer' to 'System.Int128'` (u_sr9_move at 2023, u_sr9_move_2002 at 2002) and `MOVE PP TO N` the same with ProgramPointer (u_sr8_move). WITH AN ALPHANUMERIC RECEIVER IT IS WORSE -- it compiles, runs, and stores a WRONG VALUE: `01 P USAGE POINTER. 01 X PIC X(8) VALUE 'zzzzzzzz'.` then `SET P TO NULL`, `MOVE P TO X`, `DISPLAY 'X=[' X ']'` prints `X=[CobolNet]`, the first eight characters of the .NET type name "CobolNet.Runtime.ManagedPointer" (u_sr9_move_grp2). A managed object's ToString() has leaked into a COBOL data item. MECHANISM: MoveBinder screens exactly one of the four classes §14.9.25.3 SR1 excludes, so the pointer/object arms fall through to the emitter's generic conversion path, which for an alphanumeric target is a string conversion. THE SWEEP is the other three excluded classes at the same site (message-tag has no model yet; class object should be probed) and every other verb whose syntax rule closes a class list the same way -- DISPLAY (§14.9.11.3 SR1) already has its arm, INITIALIZE (§14.9.20.3 SR1) does not (see finding 6).
