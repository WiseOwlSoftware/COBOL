# PB2700 — LANDED

## Repro — measured
`E:\COBOL-coord\scratch\w1041p\probes\opn35.cob`: `SELECT M1 ASSIGN TO "nof1.dat"` (absent, not OPTIONAL, no FILE
STATUS clause, no USE procedure), `SORT SW … USING M1 OUTPUT PROCEDURE OP`, then an explicit `OPEN INPUT M1`. Prints

```
BEFORE SORT
AFTER SORT
abnormal run-unit termination: EC-I-O-PERMANENT-ERROR (fatal): I-O status 35 on M1 (OPEN); …
```

The SORT's implicit OPEN fails with the same `35`, nothing covers it, and the program carries on silently past the
SORT with its output procedure never run; only the LATER explicit OPEN of the same file ends the run unit.
`mg10.cob` (MERGE, `m1.dat`/`m2.dat` absent) prints nothing and exits 0 — but its FIRST USING file M1 carries a FILE
STATUS clause, so its first failure IS covered; the uncovered MERGE case needs a USING file with no FILE STATUS.

## The rules
- §9.1.13.1: a fatal I-O status — "the implementor determines what action is taken … The implementor may either
  continue or terminate the execution of the run unit. If the implementor chooses to continue execution of the run
  unit, control is transferred to the end of the statement that produced the fatal exception condition unless the
  rules for that statement define other behavior." DOC-A.1-103 decides it: continue only when the program is equipped
  to see the failure (a FILE STATUS clause, or a USE procedure applied), otherwise terminate the run unit.
- §14.9.40.4 GR12 a) / §14.9.24.4 GR7 a): the USING file's initiation is performed "as if an OPEN statement with the
  INPUT phrase … had been executed"; both rules speak only of a NONFATAL status of that OPEN.
- §14.6.13.1.3 2) "If the executed statement is a MERGE or SORT statement, then the rules for those statements apply"
  — which is where the DOC-A.1-103 carve-out ("a SORT or MERGE implicit transfer follows the verb's own rule
  instead") came from.

## Code site
`src/Cobol.Net.Compiler/CodeGen/Verbs/SequentialIoEmitter.cs#EmitUseHook` — `EmitUncoveredFatalTermination` returns
early on `verbDisposes`, the flag every SORT/MERGE as-if statement passes (`SortEmitter.EmitTransferUse`), so
`CobolFile.TerminateOnUncoveredFatalStatus` (`src/Cobol.Net.Runtime/IO/CobolFile.cs`) is never asked for an implicit
transfer; `SortEmitter.EmitDisposition` (PB993's table) then only jumps to the statement's end label. A two-arm
dispatch: the plain OPEN's arm asks the question, the implicit OPEN's arm never does.

## What the fixer owes
One disposition rule for every as-if statement of the implicit transfers that asks the plain statement's
uncovered-fatal question (sweep SORT and MERGE, USING and GIVING, OPEN/READ/WRITE/CLOSE); goldens for SORT and MERGE
with a missing USING file and nothing covering it (terminates with the fatal message) and with a FILE STATUS clause or
a USE procedure (continues; the program sees `35`); DOC-A.1-103's determination corrected in `docs/CONFORMANCE.md`.

## Landing (w1041r, branch `w1041r-sort-implicit-open`)
Re-probed on the worktree's build of `7fb5cab75`: `opn35.cob` printed `BEFORE SORT` / `AFTER SORT` and ended at the
later explicit OPEN. After: `BEFORE SORT` then `abnormal run-unit termination: EC-I-O-PERMANENT-ERROR (fatal): I-O
status 35 on M1 (SORT USING implicit OPEN); the file has no FILE STATUS clause and no USE procedure applies`. `mg10.cob`
is unchanged (prints nothing, exit 0) and correctly so: its first USING file has a FILE STATUS clause, the covered arm.

**The rule's reading (⚠ DETERMINATION, recorded in DOC-A.1-103).** Each as-if statement is performed "as if" the
statement "had been executed", so §9.1.13.1's implementor action — DOC-A.1-103 — applies to it as to the explicit one;
the verb's rules ("the SORT is terminated", MERGE's bypass/continue cells) are what the CONTINUED run unit does with
the statement. The one rule that continues past an uncovered status is the GIVING write's boundary paragraph. Checking
enabled for the condition keeps PB993's §14.6.13.1.3 2) reading (statement terminated, run unit continues). GnuCOBOL
3.2 (measured under WSL) continues after a SORT/MERGE with a missing USING file — its sort runtime bypasses the error
handler its explicit statements use; the determination follows its stated rule rather than that omission.

**Fix.** `SequentialIoEmitter.EmitUseHook` no longer suppresses the uncovered-fatal question on `verbDisposes`: it
returns it as `UseHookResult.Uncovered` (an `UncoveredFatal`), adding the "condition not enabled" mask test the
`__verbRule` arm needs, and `SortEmitter.EmitDisposition` renders it first through the one
`SequentialIoEmitter.EmitUncoveredFatalTermination`, for all six as-if statements of both verbs (USING and GIVING;
OPEN, READ, WRITE, CLOSE) after the WRITE-boundary test. `SortTransferRuleDriftTests` pins one renderer and one
disposition call site.

Code sites for the next implementer: `SequentialIoEmitter.cs#EmitUseHook` (the `Uncovered` local function decides
emit-now vs return) and `#EmitUncoveredFatalTermination` (the ONE renderer — reuse it); `SortEmitter.cs#EmitDisposition`
(uncovered question, then `RuleFor`'s cell) and `#EmitTransferUse` (returns `TransferHook(Used, Uncovered)`). Trap: the
`__IoCheckEc` hook's `NoHandler` does NOT imply "checking not enabled" under `__verbRule`.
