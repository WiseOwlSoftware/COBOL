# PB664 — LANDED — the arm of a screen the other statements have

Found 2026-09-05 by the `PB231` pointer-third implementer (report §"New defects" (2)), reproduced on the pristine
main-tree compiler; pre-existing.

## Repro (`--std 2002`+; `<a9d94900 scratch>/PB231-pointer/probe13.cob`)

```cobol
       01 P   USAGE POINTER.
       01 A66 PIC X(4).
           MOVE P TO A66
           DISPLAY A66                 *> the first four characters of a .NET type name
```

Emitted: `A66 = CobolString.Store(P.ToString(), 4);`.

## The rule

§14.6.8 (the MOVE statement's rules) defines the transfer by the sending and receiving CATEGORIES in Table 16, and
Table 16 has no row for a class-pointer sender (`cite.py --find "Table 16"` and read the row list before acting);
§13.18.60.4 GR22/GR23 put an object reference in class object and a data-pointer in class pointer. A MOVE with an
undefined meaning is nonconforming source and must be rejected at bind, exactly as its siblings are: DISPLAY of a
pointer is refused under §14.9.11.3 SR1 "Identifier-1 shall not reference …" (`OK §14.9.11.3 1)`, COBOLNET1694) and
INSPECT under §14.9.22.3 SR1 (COBOLNET1626).

## The mechanism

`src/Cobol.Net.Compiler/CodeGen/Emit/OperandText.cs`, the sending-image switch's fall-through
`_ => $"{PlaceRenderer.Read(p)}.ToString()"` — reached only by the pointer/object categories, and it should be
unreachable behind a bind-time screen that `MoveClassifier` / `MoveEmitter` do not have. [[two_arm_dispatch]]:
DISPLAY and INSPECT got the screen, MOVE did not.

## Fix shape

One category-admissibility table for a MOVE sender, derived from Table 16's row list (the same source PB305's
`TableTwoClass` projection reads), consulted at bind in `MoveClassifier` with one descriptor (next free code) naming
§14.6.8's table; delete the `.ToString()` fall-through so a pointer reaching the renderer is a loud bind-phase
invariant failure, never text. Sweep the other receiving/sending statements for the same missing arm (STRING,
UNSTRING, the EVALUATE subject, a relation condition's operand — measure each with a pointer operand). Negatives at
2002/2014/2023 for MOVE pointer → alphanumeric, MOVE object-reference → alphanumeric, MOVE program-pointer →
numeric; positive control: `SET` between pointers, the only conforming transfer.

## LANDED — 2026-09-22, wave 44 (group MOVE AND OPERAND RENDERING)

⛔ **The note's OWN repro no longer reproduced, and the note was still right.** `MOVE P TO A66` is refused
COBOLNET0809 — `MoveTable16.SenderClassRefusal` over the ONE §8.5.2.1 Table-2 reader, landed at `4f1c8cacb`
(PB392 + PB423). What had NOT been done was the note's own "sweep the other receiving/sending statements for
the same missing arm", and every statement it named was measured on a fresh build at `2f6b38c61`:

```
--std 2023
STRING P DELIMITED BY SIZE INTO A66   A66=[CobolNet.Runtime.CellPointer        ]   WRONG ANSWER
STRING CMP / PKD / IDX ... INTO A66   accepted; the INDEX sender produced nothing at all
STRING SRC DELIMITED BY P INTO A66    accepted; the delimiter is a type name, so nothing ever matches
STRING 12 ... / ... DELIMITED BY 5    accepted; SR1's literal half was enforced nowhere
STRING <PIC N(2)> ... INTO <PIC X(8)> accepted; SR1's national-consistency sentence was enforced nowhere
UNSTRING P DELIMITED BY " " INTO B66  B66=[Cobo]                                   WRONG ANSWER
UNSTRING A66 DELIMITED BY P INTO B66  B66=[AB C] — no delimiter found
DISPLAY P / INSPECT P / IF P = A66 / EVALUATE P   already screened (1694 / 1626 / 0869)
```

So the arm that was missing was not MOVE's: it was STRING's and UNSTRING's SENDING positions, and the two
shapes of the omission are different and both instructive.

* **STRING** had SR1 at identifier-3 and nowhere else — one sentence, three identifier positions and two
  literal positions, enforced at one. It is now ONE predicate (`Sr1Offence`) asked at identifier-1,
  identifier-2 and identifier-3 through ONE report site (`Sr1Reject`, COBOLNET1626), plus SR1's SECOND
  sentence (`Sr1MixesNational`, the class read from `IntrinsicArgumentRules.ClassOf`). A GROUP stays exempt
  (usage is an elementary property; §14.9.43.4 GR3 a) carries a group), a reference-modified operand answers
  with identifier-1's own usage (§8.4.3.3.4 GR6), and a FUNCTION-IDENTIFIER is deliberately not screened:
  SR1's antecedent is a DESCRIPTION and a function result has no data description entry.
* **UNSTRING** had SR2 at every position the rule names — as a BLACKLIST of the categories it refuses. The
  four PICTURE categories the model gained after it was written (data-pointer, program-pointer,
  function-pointer, object reference) therefore passed as if admitted. It is now the rule's own shape, a
  WHITELIST, so the NEXT category is refused by construction (`feedback_model_the_rule_shape_not_one_case`).
* **`OperandText.FieldAsString`'s `_ => Read(p).ToString()` fall-through is DELETED**, as the note asked.
  An operand of those four categories reaching the sending-image renderer is now a loud invariant failure
  naming the missing syntax-rule screen — never text. It was reachable from exactly the statements above.

**Goldens.** `tests/conformance/85/pb664_string_operand_screen.cob` is the POSITIVE control the rule needs,
because the failure mode of a rejection is over-reach: five legs of admitted spellings, including a USAGE
BINARY `WITH POINTER` item that WITNESSES SR1's identifier-4 exemption, a usage-display numeric sender, a
group sender and a numeric-edited sender. Negatives: `pb664-string-sender-usage` and
`pb664-string-numeric-literal` (every edition), `pb664-string-sender-pointer`,
`pb664-unstring-sender-pointer` and `pb664-string-national-mix` (2002+, where the shapes exist).


## AMENDED after the shared-seam gate — the screen caught a golden asserting a rule over ILLEGAL source

Enforcing SR1 at the sending position turned `conformance:2023/ec_data_not_finite` red, and the golden was
the thing that was wrong: it carried `STRING WS-INF DELIMITED BY SIZE INTO WS-TXT` over a `USAGE COMP-2`
item. SR1 refuses that (`usage display or national`) and SR8 refuses it again ("Where identifier-1 or
identifier-2 is an elementary numeric data item, it shall be described as an integer"), so the leg was green
only while SR1 was unenforced. Its twin is refused too — `MOVE WS-INF TO WS-TXT` is COBOLNET0819 under
§14.9.25.3 SR10 / Table 16 — so neither of the two chokepoints the file's header listed beside DISPLAY is
reachable from conforming source with a float. The leg is REMOVED and the header now records why; the
DISPLAY leg reaches the same string-image read from source the standard admits, and the three remaining
raises still pin §14.6.13.1.3 GR5's declarative dispatch (the only row that cites the file).

`SR-14.9.43.3-1` is therefore **CONFORMS** and is this note's `closes_rows` entry: both directions of the
rule are witnessed — five negatives for the refusals and five admitted spellings in the 85 positive,
including identifier-4 as a USAGE BINARY item so the exemption is measured rather than assumed. The one
admitted shape with no positive witness is the ALL-NATIONAL STRING below, and it is a different clause's
implementation, not this rule's screen.

**NOT closed, and it is a rejection of legal source**: `STRING <all national operands> INTO <PIC N item>` —
which SR1 ADMITS — dies at run time in `NotImplementedCobolFeatureException: STRING INTO receiver 'NOUT'
(usage display required, ISO §14.9.43.3 SR1)`. The message mis-cites this rule to refuse what it permits.
Pre-existing, in the STRING emitter's staged national transfer, and registered as a lead in the wave-44
report; it is why SR-14.9.43.3-1 is PARTIAL rather than CONFORMS.
