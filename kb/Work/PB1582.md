# PB1582

Found 2026-09-25 by the w59j (PB1548) implementer. Repro: `CLASS-ID. X. FACTORY. METHOD-ID. NEW.` → COBOLNET0836.
Site `src/Cobol.Net.Compiler/Oo/OoClassTable.cs:411`. Depends on PB1548's standard class BASE (w59j branch
`worktree-agent-aeb91cab65cad6f99` @da3803b0c, not yet landed) — fix on top of it: without BASE, NEW is an ordinary
name; with BASE, NEW must carry OVERRIDE (and must conform to §16.2's New signature); cite.py --check both rules.

## Task brief (research 2026-09-30)

**Re-measured on `4a1dda60e` (PB1548's BASE has landed): reproduces** — a factory `METHOD-ID. NEW.` in a class that does
not inherit BASE, and `METHOD-ID. NEW OVERRIDE.` in a BASE subclass, both → COBOLNET0836 ("overriding New is a
deferred v1 restriction").

- **Spec (cite-checked):** §11.7.3 SR3 "If the OVERRIDE phrase is specified, there shall be a method with the same method
  resolution signature" (OK 3)); §16.2 declares BASE's factory `Method-id. New.` (OK §16.2) without FINAL; §11.7.3 SR4 a)
  (a class method with an inherited name and no OVERRIDE is refused — so `METHOD-ID. NEW.` WITHOUT OVERRIDE in a BASE
  subclass is still an error, by SR4 a), not by 0836).
- **Change:** delete COBOLNET0836 (`OoClassTable.cs` ~411) and its catalog row; outside BASE's hierarchy NEW is an
  ordinary factory method (INVOKE C "NEW" resolves to it); inside it, `NEW OVERRIDE` overrides BASE's New — the D4
  "generated constructor" realization must dispatch `INVOKE C "NEW"` to the override (virtual `__New` on the factory
  singleton, OO design D4/D7) and `INVOKE SUPER "NEW"` inside it to BASE's creation. Conformance of the override to
  §16.2's New signature (RETURNING an ACTIVE-CLASS reference) through `MethodConformanceMismatches`. Update OO design D4.
- **Goldens (2002):** no-BASE class with factory NEW → `MY-NEW` (and its RETURNING delivered); BASE subclass `NEW
  OVERRIDE` calling `INVOKE SUPER "NEW" RETURNING R` → `MY-NEW` then a usable instance; negatives: `NEW` without OVERRIDE
  in a BASE subclass (SR4 a)), `NEW OVERRIDE` with a USING formal (§9.3.8.2.3 rule 1 vs New).
- **Size:** half slot; touches the D4 creation path — review carefully.

## Landed 2026-10-04 (wave-1015 implementer Z)

**Re-probed: reproduced** (both shapes → COBOLNET0836). Now a root class's factory NEW runs as an ordinary method
(`MY-NEW`, `R=123`), and a BASE subclass's `NEW OVERRIDE` runs for `INVOKE C "NEW"` and creates through
`INVOKE SUPER "NEW"`; a subclass inheriting the override gets an object of its OWN class (BASE's New creates through
the virtual `__Create`).

**For the next implementer.**
- `src/Cobol.Net.Compiler/Oo/OoClassTable.cs#Build` (factory arm) — no NEW special case; `ResolveOverrides` marks
  `NEW OVERRIDE` against BASE's New by roster key (adopting CsName `__New`) and refuses `NEW` without OVERRIDE (0837).
- `src/Cobol.Net.Runtime/Control/BASE.cs#BASE__FACTORY.__New` — now `public virtual CobolObject? __New()`; the result
  type is the universal one so a COBOL override (ACTIVE-CLASS returning → universal crossing) overrides it, C#
  covariance narrowing it to the class type.
- `src/Cobol.Net.Compiler/Binding/Bound/BoundOo.cs#InvokeForm.NewSuper` + `OoEmitter.EmitNew` — SUPER "NEW" renders
  `base.__New()` (non-virtual); SELF "NEW" stays `this.__New()` (virtual). Trap: before this, SELF and SUPER shared
  NewSelf → `this.__New()`, which inside an override would recurse.
- The override's signature against §16.2's New is `OoConformance.ValidateOverrideSignatures` (0829), unchanged.
