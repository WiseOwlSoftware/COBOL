# PB1932 — LANDED

## Landed (wave 1014, group U) — a property GET is evaluated in its argument's place

**Repro written and run** on base `59ef8b01b` (an EXTERNAL counter the GET increments): `FUNCTION SUM(CNT, P OF A)`
→ 2, `SUM(CNT, MAX(P OF A, 0))` → 2; expected 1 and 1 (`cite.py --check 8.4.3.2.4 "from left to right"` → OK 2);
`cite.py --check 8.4.3.9.4 "determined as though the associated get property method were invoked"` → OK 1)).
**Root cause:** a property GET was drained only by the statement-level `OoWrapPropertyOps`, the OUTER sequence, so it
ran ahead of every pre-op and every argument of the statement. **Fix (one place, `ArgumentOrder.Record`):** a function
argument's property references are always SENDING (an intrinsic argument; a user-function identifier argument is BY
REFERENCE "other than an object property", §8.4.3.2.4 GR5 a)), so their GETs move from the property list onto the
pending pre-op list at the argument's position (`OoBinder.OoDrainPropertyGets`, injected into `ArgumentOrder`); the
argument then counts as one that registered pre-ops, and the window freezes every earlier argument before it. One
chokepoint (`IntrinsicBinder.BindArgOperand`) serves the intrinsic and the user-defined activation. **Golden:**
`conformance:2002/pb1932_property_argument_order` — five derived lines (intrinsic, nested intrinsic, property first,
user function with an expression argument, and a BY REFERENCE identifier argument whose value is read at the transfer
of control, GR6 a)). **Sweep:** the per-evaluation windows (PERFORM UNTIL, a non-first OR operand) take the same
path — probed: `PERFORM UNTIL FUNCTION SUM(CNT, P OF A) > 6` runs 3 times with CNT=4, `IF W = 9 OR FUNCTION SUM(CNT,
P OF A) = 1` is true.

Filed by the train-1005 lander from wave 1005 group C's report (`w1005c-PB1423-report.md`, lead 4). No repro yet.

## The defect

§8.4.3.2.4 GR2: a function's arguments "are evaluated individually in the order specified in the list of arguments,
from left to right" (`cite.py --check 8.4.3.2.4 "from left to right"` → `OK §8.4.3.2.4 2)`). PB1423 made the
user-function and intrinsic arguments obey it through `ArgumentOrder`. An object property used as a sending item is
temp-1, "determined as though the associated get property method were invoked" (§8.4.3.9.4 GR1), but its GET is
drained by the OUTER property-op wrap (`OoPendingPropertyOps`, `OoBinder.OoWrapPropertyOps`) ahead of every pre-op of
the statement. So in `FUNCTION F(A, P OF OBJ)` a GET that changes A is seen by the first argument, which is evaluated
before the property under GR2.

**Repro to write.** A class whose property GET adds 1 to a working-storage item that the same statement also passes as
an earlier argument of a user function; expected: the earlier argument reads the value before the GET.

**Sites.** `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/UdfBinder.cs#UdfWrapCalls`,
`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/OoBinder.cs#OoWrapPropertyOps`,
`src/Cobol.Net.Compiler/Binding/Procedure/ArgumentOrder.cs` (the window a property GET should register in).
