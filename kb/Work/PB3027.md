# PB3027 — review the branch when it is DONE, not the train when it is leaving

**From the owner's Q3 decision (kb/Work PB3015, 2026-10-11): one pull request per finished branch** — the loop reviews
it, rebases it, runs the targeted local gate and enqueues it. The lander's "review the train before it leaves" (owner
2026-09-25, lander-train-brief step 5b) had its review shards inside the lander's critical path: in land unit 6 of
2026-10-10 four review shards ran between gate 1 and the resumer's gate 2; across the land units the shards were 23 % of
the subagent tokens (PB3015's evidence, table 6), and every finding fixed in-train re-gated every cluster.

**Design:** `DESIGN-test-build-ci.md` §3.17.2 step 2, DESIGN §3.17.5.
**NEEDS-OPUS:** a change to the rolling-wave workflow script, which every fleet runs through, needs judgment.

## What changes
1. `wf_rolling_wave.js`: when an implementer returns DONE, the wave dispatches ONE `cobol-reviewer` (read-only, Opus,
   turn cap 160) on that branch: the `review` skill's full-code pass over `git diff origin/main...HEAD`, then the drift
   rules each changed file is governed by (`python scripts/spec/drift_rules.py <changed files>`), fixed time limits in
   tests, citations (`cite.py --check`), the four owner dimensions where the diff warrants. It appends one JSON line per
   finding to `<scratch>/review-w<wave>-<letter>.jsonl` and returns `CLEAN` or `FINDINGS n` (payload capped, PB1912).
2. `FINDINGS` → the same workflow dispatches the branch's implementer again (SendMessage within a step of finishing,
   else a fresh finisher from the checkpoint) with the findings file; the branch is DONE only when a re-review is `CLEAN`
   or every finding is answered in the report (`no_change_needed` with the reason). The report's O11 header gains
   `Review: CLEAN <reviewer agent> <sha>`; `enqueue.py` (PB3023) refuses a branch without it.
3. The attended session's own branches get the same step by hand (one reviewer dispatch) before `enqueue.py`.
4. Retired: lander-train-brief step 5b and MANDATORY-PRACTICES' "review the train" line (with PB3023); the `review` skill
   gains the branch form (one branch, one reviewer, the findings file).
5. Measured: findings per branch, re-review rate, reviewer minutes, against the 2026-10-10 evidence (review shards 26–45
   min each inside a 53-min gate).

**Not blocked.** Can land before the queue; immediately removes review from the lander's path.
**Code sites:** `.claude/skills/workstream/templates/wf_rolling_wave.js`, `.claude/skills/review/SKILL.md`,
`.claude/agents/cobol-reviewer.md`, `.claude/skills/workstream/templates/{MANDATORY-PRACTICES.md,dispatch-spec-implementer.md}`,
`scripts/orchestrator/plan_wave.py` (the report header's `Review:` line in `REPORT_NAME`'s checks).

## Landing (wave 1062 group E, 2026-10-11)

Items 1–5 are built; item 2's "enqueue.py refuses a branch without it" lands as the branch LIFECYCLE, which is what
both today's land unit and PB3023's `enqueue.py` read (`prune_worktrees.py`: WAITING TO LAND only under a CLEAN stamp).

- **The record and the stamp:** `scripts/orchestrator/review_findings.py` (`start` / `finding` / `verdict` / `stamp` /
  `show` / `summary`, self-test). One JSON line per decision; the tool numbers findings `R<round>-<n>`, refuses a
  finding without its scenario, computes the verdict from the file (a malformed line is an error, never skipped), and
  stamps `**Review:** CLEAN <reviewer> <head>` or `FINDINGS <n> <reviewer> <head> <file>` under the report's Status line,
  reading it back through `plan_wave.parse_review` — the ONE reader (`plan_wave.REVIEW`, `Review.covers(tip)`).
- **The wave:** `wf_rolling_wave.js` `reviewed()` runs in the group's slot when a result is DONE (or DISCHARGED with
  commits): one `cobol-reviewer` (opus, ceiling `reviewer_ceiling_min` 90), then on FINDINGS a REVIEW FINISHER (a fresh
  `cobol-implementer` that merges the branch: a workflow cannot SendMessage an agent that has returned, so "SendMessage
  within a step" is not available there), at most `review_fix_rounds` (2). `landable()` = finished AND `review ===
  'CLEAN'`; a same-file predecessor is reviewed through its successor, or alone when it falls back; a SPLIT result is no
  longer landed by the wave (it is the planner's finisher, as in a land unit). The result carries `reviews` (item 5).
- **The lifecycle:** `prune_worktrees.py` gains WAITING FOR REVIEW (DONE without a CLEAN stamp at the tip; a stamp at an
  older head is unreviewed work); a FINDINGS stamp is a DECISION whose finisher `plan_wave.py` plans (`finisher_pred`'s
  review arm names the findings file and the answer-by-id rule); and `contained()`: a branch with no report whose tip is
  inside a waiting or in-flight fix-lane branch (a review finisher's merged predecessor, a same-file predecessor) is IN
  FLIGHT, landing through it.
- **The role and the rules:** `cobol-reviewer.md` has the branch form and the R2 form; the turn cap stays 120 (one role,
  one cap; the note's 160 was the generic read-only cap of P5, and one branch's diff fits 120). `review/SKILL.md` "The
  branch form"; MANDATORY-PRACTICES I10 (new), L9 (now: the lander does not review), O10/O11 (the new state);
  lander-train-brief step 5b deleted and step 2 checks the stamp; `cobol-lander.md`; `units/land.md` step 2 (the land
  unit dispatches the reviewer for any WAITING FOR REVIEW row: item 3's hand step, made automatic);
  `dispatch-spec-implementer.md`, the report template (`## Review findings`), workstream SKILL.md and
  references/landing.md; `check_practices.py` pins the reviewer, the tool and the CLEAN gate in the wave, I10 in the
