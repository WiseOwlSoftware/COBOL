# PB297

Found 2026-09-02 while writing a kb/Work PB152 golden — the golden needed to assert that two carrier bytes
were NUL, wrote the natural comparison, and got the wrong answer from a construct that has nothing to do with
PB152. Reproduced with NO OPTIONS paragraph and no PB152 code in the path.

## Repro (measured, complete program)

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. PB297REPRO.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 X PIC X(2) VALUE LOW-VALUES.
       01 S PIC X(2) VALUE SPACES.
       01 H PIC X(2) VALUE HIGH-VALUES.
       01 W-N PIC 9.
       PROCEDURE DIVISION.
       MAIN.
           MOVE 0 TO W-N
           IF X    = LOW-VALUES  MOVE 1 TO W-N END-IF
           DISPLAY "whole-vs-LOW    =" W-N          *> 1  correct
           MOVE 0 TO W-N
           IF X(1:2) = LOW-VALUES MOVE 1 TO W-N END-IF
           DISPLAY "len2-vs-LOW     =" W-N          *> 1  correct   (len == item width)
           MOVE 0 TO W-N
           IF X(1:1) = LOW-VALUE  MOVE 1 TO W-N END-IF
           DISPLAY "len1-vs-LOW     =" W-N          *> 0  ⛔ WRONG
           MOVE 0 TO W-N
           IF H(1:1) = HIGH-VALUE MOVE 1 TO W-N END-IF
           DISPLAY "len1-vs-HIGH    =" W-N          *> 0  ⛔ WRONG
           MOVE 0 TO W-N
           IF S(1:1) = SPACE      MOVE 1 TO W-N END-IF
           DISPLAY "len1-vs-SPACE   =" W-N          *> 1  correct — and this is why it went unnoticed
           STOP RUN.
```

The same shape over a Tier-B REDEFINES window, again with no OPTIONS clause, shows the byte content is not in
doubt — only the comparison is:

```cobol
       01 G.
          05 GA PIC X(3) VALUE "abc".
          05 GC PIC 9(4) COMP VALUE 0.
       01 R REDEFINES G PIC X(5).
...
           IF R(1:3) = "abc"      →  1   the window read is sound
           MOVE FUNCTION ORD(R(4:1)) TO W-O  →  00001   the byte IS the low value (§15.70.1: "The lowest
                                                        ordinal position is 1")
           IF R(4:2) = LOW-VALUES →  0   ⛔ WRONG
           IF R(4:2) = X"0000"    →  1   the SAME bytes against a hexadecimal literal compare EQUAL
```

## Why it matters

This is a WRONG ANSWER with no diagnostic, on an idiom that is everywhere in real COBOL — testing a byte of a
buffer for the low value is how programs check for binary terminators, unset flag bytes and end-of-data
sentinels. It reports "not low-value" for storage that IS low-value, so the program silently takes the wrong
branch. `X"00"` and `ORD` both give the right answer, which means the bug is invisible to anyone who happens to
write those instead.

## Hypothesis for the mechanism — a lead, NOT a conclusion, to be measured before it is trusted

Every observation is explained by the figurative operand being materialized at the width of the BASE data item
rather than at the width of the reference-modified operand, followed by §8.8.4.1.1's shorter-operand padding
with SPACES:

| case | figurative filled to | other operand | comparison |
| --- | --- | --- | --- |
| `X(1:1) = LOW-VALUE`, X is `PIC X(2)` | 2 NULs (base width) | 1 NUL | `"\0\0"` vs `"\0 "` → unequal ⛔ |
| `X(1:2) = LOW-VALUES`, X is `PIC X(2)` | 2 NULs | 2 NULs | equal ✓ (widths coincide) |
| `S(1:1) = SPACE`, S is `PIC X(2)` | 2 spaces | 1 space | pad is also a space → equal ✓ (bug hidden) |
| `R(4:2) = LOW-VALUES`, R is `PIC X(5)` | 5 NULs | 2 NULs | unequal ⛔ |

§8.3.3.6.4 GR2 sizes a figurative constant to the associated data item, and §8.4.3.3.4 GR5 makes a
reference-modified operand "a unique data item" whose length is the ref-mod length — so the associated item for
sizing purposes should be the REF-MOD, not its base. That is the rule the fix has to be derived against; the
table above is a prediction to confirm at the code, not a diagnosis.

⛔ **The SPACE row is the reason this is registered as its own note rather than assumed narrow.** Whatever the
mechanism turns out to be, any test written with SPACE passes under it, so the existing corpus's silence about
this is not evidence. Whoever takes it should sweep every figurative × ref-mod combination rather than fixing
the two spellings named here — the two-arm shape ([[two_arm_dispatch]]) is exactly what a hand-picked pair of
repros produces.

## Not fixed here

Out of the cluster-F fix lane's scope (PB183 / PB152). PB152's Tier-B golden was written with `FUNCTION ORD`
instead of the comparison, and says why in its header, so no golden rests on the defective construct.
