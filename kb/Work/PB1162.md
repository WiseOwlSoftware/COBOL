`python scripts/spec/cite.py --check 14.7.9.2 "…"` → `OK  §14.7.9.2   (General format)`

## Finding — `retry-phrase` (rejects-legal-source; rows `FMT-14.7.9.2`)

**Mechanism.** Lexer subscript trigger is edition-blind: a '(' after a word that is reserved at the target edition (RETRY, B-AND, B-SHIFT-L, ...) is lexed as a subscript opener because the word is a legal user word at SOME edition

**Repro.** SELECT F ASSIGN "x.dat" ORGANIZATION RELATIVE ACCESS DYNAMIC RELATIVE KEY K LOCK MODE MANUAL. 01 N PIC S9V9 VALUE 1.5. PROCEDURE DIVISION. READ F RETRY (N) TIMES.  (also WRITE R RETRY (N + 1) TIMES / OPEN INPUT RETRY (N) TIMES F / DELETE FILE F RETRY (N) TIMES; sibling: COMPUTE C = A B-AND (B B-OR A). and COMPUTE C = A B-SHIFT-L (N). with USAGE BIT items) — cobol --std 2023

**Expected from the spec.** Compiles: §14.7.9.2 takes arithmetic-expression-1/-2, and §8.8.1.1 'An arithmetic expression may be ... an arithmetic expression enclosed in parentheses' (cite.py --check 8.8.1.1 OK); §8.8.2 Table (cite.py --check 8.8.2 "B-AND, B-OR, B-XOR" OK) permits '(' after a boolean operator.

**Observed / reasoning.** COBOL0001 'cannot parse construct near N' at 2002/2014/2023 for every RETRY site; `RETRY FOR (N) SECONDS` and `RETRY 1 + (N) TIMES` compile, isolating the '(' immediately after RETRY. `A B-AND B` compiles, `A B-AND (B B-OR A)` does not. Cause: CobolLexer.g4 OnDefaultLParen pushes SUBSCRIPT when PreviousTokenCouldBeDataName(), and the generated `_dataNameTokens` (CobolLexerWordSet.g.cs, from cobol-words.json subscriptTrigger rows) contains RETRY, B_AND, B_OR, B_XOR, B_SHIFT_L..., EXCLUSIVE_OR etc. with no edition test — at an edition where §8.9 reserves the word it can never be a data-name. Root fix: make the trigger consult the edition's reservation (the same derived set ReservationGateRewriter/IsReservationGated uses) rather than token type alone, and sweep every word in _dataNameTokens that a general format follows with an expression.

**Code site.** src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4#OnDefaultLParen / PreviousTokenCouldBeDataName; src/Cobol.Net.Frontend/Parsing/CobolLexerWordSet.g.cs#_dataNameTokens

## What the fixer owes

Make CobolLexer.g4 OnDefaultLParen / PreviousTokenCouldBeDataName consult the edition's reservation (the same derived set ReservationGateRewriter / IsReservationGated uses) rather than token type alone; then sweep EVERY word in the generated `_dataNameTokens` (CobolLexerWordSet.g.cs, from cobol-words.json subscriptTrigger rows) that a general format follows with an expression or a parenthesised operand. Drift test: no word reserved at edition E is a subscript trigger at E.

### Finding — `complex-combined-conditions` (rejects-legal-source; rows `FMT-8.8.4.11.2`)

**Mechanism.** The lexer's subscript-trigger decision (CobolLexer.g4 OnDefaultLParen -> PreviousTokenCouldBeDataName over the generated _dataNameTokens set) is edition-blind: XOR and EXCLUSIVE-OR carry subscriptTrigger=true because they are user-defined words below 2023, so at COBOL-2023 - where they are reserved and can only be the logical operator - a '(' following them is lexed in SUBSCRIPT mode and a parenthesized condition-2 cannot parse.

**Repro.** 01 A PIC 9 VALUE 1. 01 B PIC 9 VALUE 2. 01 C PIC 9 VALUE 3. PROCEDURE DIVISION. IF A = 1 XOR (B = 9) DISPLAY "T" ELSE DISPLAY "F" END-IF. IF A = 1 EXCLUSIVE-OR (B = 9 OR C = 3) DISPLAY "T" ELSE DISPLAY "F" END-IF. -- compile with the pinned cobol.exe --std 2023 (probe/ccc/p.cob, g6.cob).

**Expected from the spec.** Compiles and prints T then F. §8.8.4.11.2 general format admits condition-2 after XOR/EXCLUSIVE-OR, and §8.8.4.11.3 Table 5 says an 'EXCLUSIVE-OR or XOR, OR or AND' element, when not last, 'may be immediately followed by only: simple-condition, NOT, (' - the '(' is expressly permitted.

**Observed / reasoning.** error COBOL0001: cannot parse construct near 'B' at every spelling ((A = 1) XOR (B = 9), XOR (B = 9 OR C = 3), EXCLUSIVE-OR (B = 9), paren on the next line). The same conditions with OR or AND in place of XOR compile and run correctly, and XOR NOT (B = 9) compiles, isolating the '(' immediately after the operator token. Sibling (same mechanism, §8.8.2): COMPUTE BR = BA B-AND (BC B-OR BD) at 2023 fails with COBOL0001 near 'BC' (probe g7.cob; expected B"1000"). The fix belongs at the trigger set's edition dimension (a word reserved at the target edition is never a data-name), not a per-word exclusion.

**Code site.** src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4#OnDefaultLParen; src/Cobol.Net.Frontend/Parsing/CobolLexerWordSet.g.cs#_dataNameTokens (generated from tests/version-matrix/cobol-words.json subscriptTrigger rows by scripts/gen-cobol-words.ps1)

### Finding — `expressions` (rejects-legal-source; rows `SR-8.8.2-6`, `GR-8.8.2-7`)

**Mechanism.** A '(' after a boolean operator is lexed as a SUBSCRIPT paren, so a parenthesized non-leading boolean operand cannot be written

**Repro.** 01 A PIC 1(4) VALUE B"1100". 01 B PIC 1(4) VALUE B"0101". 01 C PIC 1(4) VALUE B"0011". 01 R PIC 1(4). ... COMPUTE R = A B-AND (B B-OR C). DISPLAY R.  (also B-NOT (A B-AND B), A B-XOR (B), IF A B-AND (B B-OR C) = B"0100"); pinned cobol.exe --std 2002/2014/2023 -> COBOL0001 'cannot parse construct near 'B''. Probe files out/probe/expressions/PA.cob PB.cob PB2.cob PD.cob T13-T16.cob.

**Expected from the spec.** §8.8.2 rule 6 Table 4 marks (B-AND/B-OR/B-XOR, '(') and (B-NOT, '(') as permissible pairs, and the clause's operand list includes 'a boolean expression enclosed in parentheses'; rule 7a evaluates it first. COMPUTE R = A B-AND (B B-OR C) = 1100 B-AND 0111 = 0100; B-NOT (A B-AND B) = B-NOT 0100 = 1011; A B-XOR (B) = 1001.

**Observed / reasoning.** COBOL0001 at the token following '('. CobolLexer.g4 OnDefaultLParen: `if (!_primeDirectiveExpr && PreviousTokenCouldBeDataName() && !PreviousIsFunctionName() && !IsReportSumClauseKeyword()) { PushMode(SUBSCRIPT); ... }` - B_AND/B_OR/B_XOR/B_NOT are in the data-name token set (context-sensitive user words below 2002), so the grouping '(' becomes SUB_LPAREN and booleanFactor's LPAREN alternative never sees it. The lexer comment itself records the hazard ('`A B-AND (...)` would mis-lex the group in SUBSCRIPT mode') but exempts only the directive-expression region; the same exemption is missing for procedure-division boolean expressions, and boolExprAhead's IsBoolOperandStart(LPAREN) also never sees SUB_LPAREN after B-NOT. A leading group `(A B-AND B) B-OR C` works because '(' then follows '=' / COMPUTE, not a word.

**Code site.** src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4#OnDefaultLParen (line ~128) with #PreviousTokenCouldBeDataName (line 37); src/Cobol.Net.Frontend/Parsing/CobolParserCoreBase.cs#IsBoolOperandStart

#### `SR-8.8.2-1` — PARTIAL (adjudicator + refuter record, verbatim)

Rule 1 (cite.py --check 8.8.2 "the unary operator B-NOT" -> OK §8.8.2 1)). booleanFactor admits only B_NOT / LPAREN / valueOperand as a first symbol; BindBoolOperandValue accepts a category-boolean item/ref-mod/boolean function, a boolean literal (incl. folded concatenation), figurative ZERO and ALL B"...", and reports COBOLNET1511 for any other operand. PROBES: leading '(' (T07 (B-NOT A) B-AND B=0001), leading B-NOT (p1b), boolean literal and item accepted; leading B-AND rejected (N12, COBOLNET0901 - rejection correct though the message names the reserved-word rule); non-boolean identifier -> 1511 (BooleanOperatorTests.NonBooleanOperand_InBooleanExpression_Rejected1511 covers only that half). ZERO / ALL literal as a leading operand is accepted (p1b ZERO-OR=1100) - consistent with the clause's own operand list and rule 4/5, which presuppose a figurative first operand. test-ref empty: no spec-derived test covers the leading-symbol set as a whole. || REFUTED: PARTIAL — Rule 1 binds EVERY boolean expression, including the nested ones the recursive definition builds (the operand of B-NOT and each operand of a binary operator is itself a boolean expression). The '(' start is honored only at the outermost position. A nested boolean expression that begins with '(' is rejected with COBOL0001 on legal source: after B-NOT, and after B-AND/B-OR. Only the identifier, literal and B-NOT starts work in nested position. The root cause is shared with the Table 4 finding the adjudicator named, but the rule-1 half that admits '(' is realized only at the top level, so CONFORMS overstates it. The enforcement half is sound: a numeric-literal start gets 1511 and a leading B-AND is rejected.

#### `SR-8.8.2-3` — PARTIAL (adjudicator + refuter record, verbatim)

Rule 3 (cite.py --check 8.8.2 "There shall be a one-to-one correspondence between left and right parentheses" -> OK §8.8.2 3)). booleanFactor's LPAREN booleanExpression RPAREN makes balance structural. PROBES: `(A B-AND B.` -> COBOL0001 missing token (N09); `A B-AND B)` -> COBOL0307 (N15); `( ) B-AND A` -> COBOL0001 (N26); nested `((A B-OR B)) B-AND C` = 0001 accepted. Balanced parentheses in a NON-leading position are wrongly rejected, but by the lexer's subscript capture (the Table 4 finding), not by this rule's enforcement. No spec-derived negative test -> test-ref empty. || REFUTED: PARTIAL — Unbalanced parentheses are rejected, but every correctly paired pair of parentheses outside the expression's leading position is rejected too. The parenthesization facility that rule 3 constrains (and that rule 7a evaluates) works only at the start of an expression. `A B-AND ( B )` has a perfect one-to-one correspondence and still gets COBOL0001. The adjudicator acknowledged this and attributed it to the Table 4 finding, but a verdict on the parentheses rule cannot be CONFORMS while balanced parentheses are refused in most positions. Only the rejection half is verified.
