# PB393 — the variable-length group is a hole with four rims, and each rim is a different loud abort

## THE MECHANISM

A **variable-length group** (§8.5.1.12.1: a group with a dynamic-length elementary item or a dynamic-capacity
table subordinate to it) and its ODO cousin have **no data path** through MOVE, INITIALIZE or CORRESPONDING.
Four separate gates produce four differently-worded run-time aborts on source the standard requires to execute:

1. **`MoveEmitter`, the Tier-C image guard.** `DataItem.IsImageCapable` (`DataItem.cs:400-419`) is hard-wired
   false for a dynamic-length item or a group containing one, and `MoveEmitter.cs:119/:172` turn that into
   `LoudStmt(TierCIsland.Reason(...))`. Nothing anywhere computes §8.5.1.12.2 positional correspondence, drives
   §14.6.9.2 "Moving a table" for a corresponding table pair, or performs GR9b's space-fill recursion.
2. **`InitializeBinder.BindInitializeTarget`, a closed switch over PLACE SHAPES** (`:126-128`):
   `MemberPlace → …, RedefViewPlace → …, _ => null`. An occurs-depending group resolves to `OdoGroupPlace`,
   which is a **`PlaceDecorator` WRAPPING the MemberPlace** (`Place.cs:141`), so it matches neither arm, the
   cursor is null and the binder emits `InitializeErrorAction`. **Any future decorated identifier-1 lands in the
   same `_ => null`** — that is the reusable half of the defect.
3. **`InitializeBinder.ExpandInitialize`'s child walk** (`:181`) has an explicit `if (child.IsDynamicTable)` arm
   that stages COBOLNET1527 loud. That staging predates GR10 being read: **GR10 does not defer this case, it
   SPECIFIES it** — and the machinery the fix needs already exists twenty lines above, where identifier-1 IS the
   table (`InitializeDynLoop` over 1..Capacity).
4. **`CorrespondingBinder.CorrAccess.Create`'s two-arm Place switch** — MemberPlace or RedefViewPlace, else null
   — so a variable-length group operand, a kind §14.9.44.3 SR6 explicitly ADMITS, aborts the program (shared by
   all three CORRESPONDING verbs; the SR6 kind-set half of that is `kb/Work/PB392`).

And the screen that should have caught the ILLEGAL cases is absent: §14.9.25.3 SR9's compatibility test is
implemented nowhere. §8.5.1.12's concept IS modelled — `ReferenceResolver.HasVariableLengthSubordinate` backs
the REDEFINES / VALUE / GROUP-USAGE screens — but nothing consults it from `MoveBinder` or `StatementValidation`.
So **an incompatible program compiles clean (SR9's own failure) and a compatible one compiles clean and then
aborts (GR9's failure)** — one hole, both rims.

**One shape works, by accident, and that is the trap.** When the two groups' flattened leaf layouts are
IDENTICAL, `MoveEmitter.AlignedLeafPairs` fires a memberwise leaf copy that never consults GR9 — measured below.
That is exactly the shape a first test would cover, which is why the hole reads as narrower than it is.

**This is NOT documented non-support**: `docs/CONFORMANCE.md` row 57 covers only DISPLAY of a variable-length

Every abort is preceded by a passing control in the same executable, so no leg can be blamed on the harness.
Two details the fixer needs:

* **The GR8 leg is a MoveKind routing hole, not GR9's business.** The whole dynamic-length store lives in
  `MoveEmitter.ConvertSource` (`if (target.IsDynamicLength) return RuntimeApi.DynStore(...)`), which **only
  `MoveKind.Convert` reaches**; a GROUP sender routes to `MoveKind.GroupToElementary`, whose renderer never
  consults `IsDynamicLength` and asks `IsImageCapable` first. `WS-D` is a bare dynamic-length ELEMENTARY item —
  not a group — so neither GR9 nor SR9 can apply; §8.5.1.10.4 fixes the answer outright.
  **The message also misattributes the cause**: it says `WS-D` has "a dynamic-length / dynamic-capacity MEMBER"
  when `WS-D` has no members and IS the dynamic-length item.
* **A second-order trap once the place reaches the walk**: `ExpandInitialize` bounds a fixed OCCURS child with
  `child.Occurs`, which `DataItem` documents as *the MAXIMUM* for an occurs-depending table. That is right for
  §13.18.38.4 GR8b (depending object INSIDE the group, receiving operand → maximum length) and **wrong** for
  GR8a (object outside → the current count), so a naive fix that merely unwraps the decorator would
  over-initialize. `OdoGroupPlace` already carries `Depending`, `MinOccurs`, `MaxOccurs` and `DependingInside` —
  exactly the loop bound's inputs.

## THE CODE SITES, AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs:119, :172` (the Tier-C guards) and `#AlignedLeafPairs`
  (the accidental narrow success); `src/Cobol.Net.Compiler/Binding/Model/DataItem.cs:400-419` (`IsImageCapable`);
  `src/Cobol.Net.Compiler/Binding/Model/TierCIsland.cs#Reason` (the misattributing message).
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs:126-128` (the place switch),
  `:181-187` (the COBOLNET1527 arm), `:194-200` (the `child.Occurs` bound);
  `src/Cobol.Net.Compiler/CodeGen/Verbs/InitializeEmitter.cs` (`InitializeErrorAction → LoudStmt`).
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/CorrespondingBinder.cs:228-239` (`CorrAccess.Create`) reached
  from `:70-77`; `src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:211`.
* `src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs#HasVariableLengthSubordinate` — the predicate SR9's home
  should be built on, alongside `MoveBinder.Bind`'s `CheckStrongMove`.

**Repair (CLAUDE.md rule 5 — this needs a STRUCTURE, not a widened predicate):**

1. **One §8.5.1.12 module**: `VariableLengthCompatibility` — positional correspondence (§8.5.1.12.2) and
   matching (§8.5.1.12.3) over two groups, computing relative byte positions with dynamic-length items counted
   as zero length. It answers SR9 at bind time AND yields the member pairing GR9 needs at emit time.
   `kb/Work/PB204` records that no such predicate exists anywhere; building it once serves SR9, GR9, the
   CALL/INVOKE boundary and group comparison instead of three separate answers.
2. **A GR9 emitter** over that pairing: table pairs through §14.6.9.2, the excess part through GR9b's three-step
   recursion, the common part as GR9a.
3. **Make the INITIALIZE place switch decorator-aware** — unwrap `PlaceDecorator` (or give `Place` a
   `Base`/`Cursor` accessor) so an ODO group reaches the walk, and give the child walk an ODO-bounded loop
   (using `OdoGroupPlace`'s own `Depending`/`DependingInside`, per §13.18.38.4 GR8a vs GR8b) and a
   capacity-bounded loop for a dynamic child (GR10), replacing the COBOLNET1527 stage.
4. **Widen `CorrAccess.Create`** to anchor a variable-length group operand — the same decorator question as (3),
   so answer it once.
5. **Drift test**: assert that no `IsImageCapable`/`_ => null` fallback is reachable from any operand shape the
   general formats admit — the current design lets a new decorated place kind silently rejoin the hole.

## THE SIBLING SWEEP THE FIXER MUST DO

* Every `_ => null` / `_ => false` over a Place kind (`grep -rn "_ => null" src/Cobol.Net.Compiler/Binding/`) —
  `InitializeBinder` has three, `CorrespondingBinder` one.
* Every `IsImageCapable` caller — the Tier-C island reaches WRITE/RELEASE, comparison and DISPLAY as well
  (PB244 owns the DISPLAY rim, PB204 the CALL/INVOKE rim; neither reaches MOVE/INITIALIZE/CORRESPONDING).
* Every MoveKind that bypasses `ConvertSource` — three of the five do, and `ConvertSource` is the ONLY place in
  CodeGen that tests `IsDynamicLength`.
* **A GREEN GOLDEN READS AS COVERAGE FOR GR10 AND IS NOT**: `conformance:2014/dyn_initialize` cites
  "ISO §14.9.20 GR10" but initializes the dynamic TABLE (`INITIALIZE WS-ROW`), a path special-cased in
  `BindInitializeTarget` before the child walk is reached. It does not exercise a group CONTAINING one
  (`feedback_green_test_can_hold_a_gap_open`).

## Rows

* **`GR-14.9.20.4-8`** (INITIALIZE of a group with a variable-occurrence item) and **`GR-14.9.20.4-10`**
  (INITIALIZE of a group containing a dynamic-capacity table) — two arms of the same binder, two different
  aborts, both re-measured on HEAD.
* **`GR-14.9.25.4-8`** (PARTIAL) — the dynamic-length ELEMENTARY channel is genuinely implemented and pinned by
  three spec-derived 2014 goldens (`dynamic_length_item`, `dynamic_length_figurative`, `dynamic_length_limit`);
  what fails is the receiving shape reached from a GROUP sender, which bypasses `ConvertSource` entirely.
* **`GR-14.9.25.4-9`** with **`L3.1` / `L3.2` / `L3.3`** — GR9 and its three-step space-fill recursion; no code
  computes correspondence, moves a table pair, or space-fills an excess part. Four shapes measured, one
  accidental success.
* **`SR-14.9.25.3-9`** (NOT-IMPLEMENTED) — the compatibility screen is absent, so an INCOMPATIBLE program
  compiles clean; the deferral is owner-documented as a design island (`COBOLNET_DESIGN §4.2`), which explains
  the run-time abort but does not make the clean compile of illegal source correct. **SR9's screen and GR9's
  transfer belong in ONE change set** — screening on top of the island would only move the refusal earlier for
  programs that still cannot execute.
* **`GR-14.9.44.4-5`** — the SUBTRACT CORRESPONDING arm: `SRC`/`DST` are variable-length groups, §14.7.6 rule 4
  excludes the OCCURS item, leaving exactly one pair `P`, and GR5 should store 10−3; instead the program aborts
  at `CorrAccess.Create`. The fixed-OCCURS control prints `P=000G`, isolating the trigger to the ODO group.
