# PB5552 - the shard weights went stale as the population grew, and only the spread could say so

**Sites:** `tests/_shared/test-weights.json` (regenerated); `scripts/shard_weights.py` (`Shard.seconds`, `shard_walls`,
`Weights`, `read_weights`, `Unweighted`, `unweighted`, `spreads`, `verdict`, `UNWEIGHTED_LIMIT`, the self-test);
`docs/rearchitecture/DESIGN-test-build-ci.md` (the weighted-shards paragraph, the `shard-spread` row);
`docs/DOC_INDEX.md` (`scripts/shard_weights.py` row); `.github/workflows/nightly.yml` (`shard-spread` comment).

**The symptom.** The nightly of 2026-11-14 went red on `shard-spread`: 1.54x OVER, run 43603799163, Linux shard 2 at
445 s against a mean of 288 s. `report --from-dir` over the same eight runs, downloaded (43610738211, 43609417082,
43607149472, 43603799163, 43602800739, 43602766964, 43601542838, 43601103784), reproduces the line exactly.

**The measurement.** Every Linux trx of the eight runs was read per class (`class_seconds`, the reader `generate` uses).
A Python port of `TestWeights.Deal` over the committed weights (2026-11-04, PB5230's rename of 2026-11-10) reproduces
every run's actual assignment (0 classes disagree in any run). Of the 1,162 classes the shards ran, 112 are not in the
file; they are dealt blind at `default_seconds` (0.1 s) after every named class, in ordinal order. They cost 179 to
214 s a run on Linux (3.6 to 4.2 % of the summed class seconds), and 135 to 156 s of it landed on shard 2 in every
run: `CommunicationCcvsTests` (Conformance, 92 s on Linux, 94 to 118 s on Windows) and `ParseRecoveryCascadeTests`
(28 to 35 s). In run 43603799163 shard 2's heaviest classes were `NistDifferentialTests_P0` 135 s,
`BothRunnersVerdictDriftTests_P7` 92 s, `CommunicationCcvsTests` 92 s (unweighted) and `BothRunnersVerdictDriftTests_P1`
91 s. The deal's spread in summed class seconds over the old weights is 1.13x to 1.40x on Linux and 1.16x to 1.47x on
Windows; the wall spread of the same deal is 1.10x to 1.54x, so runner noise sits on top of it.

**The cause: both stale-weight mechanisms, the unknown classes the larger single one.** Filling in only the 113 classes
the old file lacked (their new weights, every other weight left alone) brings the worst simulated Linux spread from
1.40x to 1.24x and Windows' from 1.47x to 1.28x; the full regeneration brings them to 1.14x and 1.11x, so the drift of
named classes' costs is the rest. No single named class outgrew its weight by itself.

**The remedy, applied.** `python scripts/shard_weights.py generate` (its own step: the newest three successful
merge-group runs, 43647068789, 43647404325, 43649429257, all after the eight measured): 1,163 classes, default 0.2 s;
its own deal is within 0.1 % of the mean on 5 and 7 shards. The 29 classes the old file named and no run ran (PB4405's
leftovers among them) are gone. The deal of the regenerated weights over the eight runs' measured class seconds
(out of sample: the weights were read from later runs), summed class seconds per shard:

The wall spread of the regenerated deal can only be read from merge-group runs after this lands.

**The mechanism (rule 5): the report measures the blindness, not only its effect.** A weights file that silently goes
stale until the spread crosses 1.5x is the pattern: the spread is shared runners' wall clock (one deal read 1.10x to
1.54x over eight runs), so it crosses late and by chance. The report now reads every shard's class seconds with
`class_seconds` (the one trx class reader, also now the source of a shard's assemblies; `trx_assemblies` is deleted) and
reports, beside the spread, the worst UNWEIGHTED work of the measured (run, OS): the seconds of the classes the weights
file does not name over the mean shard's class seconds, naming the heaviest such class. Above `UNWEIGHTED_LIMIT` (0.10,
the most that blindness can add to one shard, as a share of a shard) the line says STALE and names the remedy, exit 1.
Over the eight runs the old file reads 0.18 to 0.25 (STALE); the regenerated one 0.00. It reddens early: run
42385835322 (2026-11-07, three days after the 2026-11-04 regeneration), read against the file in force that day, measured
0.17 on Linux and 0.32 on Windows at spreads of 1.32x and 1.14x, a week before the spread went red.

**Not chosen, and why.** A scheduled job that regenerates and commits the file: the weights file is read by every test
host, so its change is a code-lane landing, which needs a local gate's GREEN record at the tip (`enqueue.py land`); a
workflow cannot produce one. STALE makes the regeneration a named, early, one-command task instead.

**Proof.** `python scripts/shard_weights.py --self-test`: ok. Its STALE arms plant two even shards (1.00x) with 20 s of
180 s in a class the weights do not name (0.22, STALE, exit 1, the class and remedy named), the same shards over weights
that name it (0.00, exit 0), the share exactly at the limit (not STALE), and the worst (run, OS) of a window named.
Mutations, each run from beside the real scripts: dropping `or stale` from the exit fails two arms; counting every class
as weighed fails the same two.
