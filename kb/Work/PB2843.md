# PB2843 — LANDED — a declared-name path collision across modules

Found by the train 1047 lander's review (step 5b) and filed by it, 2026-10-08 20:54 PDT. Reviewer finding on cluster 45B (PB2097), CONFIRMED by code trace, pre-existing since PB303 (the staged
registration's "never a second node" claim does not hold for it).

## Mechanism
`src/Cobol.Net.Runtime/Control/ProgramTable.cs:179-190` refuses a duplicate by `CallName` (the externalized name)
only; the commit at ~line 194 writes `_byPath[n.Path]`, and `Path` is built from the DECLARED name
(`BoundUnit.cs:60`), not the externalized one.

## Scenario
Module A: `PROGRAM-ID. WORKER.` with a nested `HELPER`. Module B (`X.dll`): `PROGRAM-ID. WORKER AS "X".`, legal by
§8.3.2.2 2) (its externalized name is "X"). When A's WORKER does `CALL "X"`, B passes the duplicate check and replaces
A's `_byPath["WORKER"]`; A's later `CALL "HELPER"` takes B's node as the caller (~line 749), the containment rule
misses, and the CALL answers EC-PROGRAM-NOT-FOUND. `ParentInstance` and `CancelNode` follow the wrong node too.

## Fix shape
Root the path at the externalized name (unique once the duplicate check passes), or refuse a `Path` collision in the
staged check; a host test with two modules.

## Landed (wave 1051 B, 2026-10-10)
Re-probed on the wave's own build: `E:/COBOL-coord/scratch/w1051b/p2843/` (WORKER.dll containing HELPER; X.dll with
`PROGRAM-ID. WORKER AS "X"`) printed `HELPER NOT FOUND` after `CALL "X"`; after the fix it prints `A HELPER RAN`.
**Root:** the run-unit key (the path) is now formed in ONE place, `ProgramTable.OutermostPath` (an outermost unit's
EXTERNALIZED name, which §8.3.2.2 2) makes unique in a run unit and `RegisterModule` already refuses twice; escaped,
so an AS literal holding `/` never meets a containee's path) and `ProgramTable.ContainedPath`; `BoundUnit.Path` calls
them. The staged registration and the commit now refuse a repeated path LOUDLY (`InvalidOperationException`) instead
of replacing a node. The same key also names the unit's internal file connectors (`<path>::<file>`) and its EXTERNAL
describer identity, which collided across the same two modules (the §14.8.4 conformance check skipped one describer
as "self"); both are fixed by the one key. **Sibling arm:** a CALL or CANCEL written in a METHOD passed its CLASS name
as the calling path, which named any program whose path is spelled like it and exposed that program's containees to
the method against §8.4.6.3 1); it now passes `CallUnitState.NoProgramPath` (empty, a path no unit has; null is the
host boundary of DESIGN-external-repository §4.1). Tests: `ModuleRegistrationHostTests.ASiblingModuleDeclaringTheSameProgramNameAsAnotherName_LeavesTheFirstModulesContaineesCallable`
(two compiled modules), `ModuleRegistrationTests.ThePath_IsInjective_EvenForAnExternalizedNameHoldingTheSeparator`,
`ModuleRegistrationTests.ARepeatedPath_IsRefusedLoudly_NeverReplacingANode`. Design: DESIGN-external-repository §11.2.
