# PB566

## Mechanism
the BLANK WHEN ZERO guard tests the UNSCALED sending value 37 lines before the mask rescale, so a MOVE that STORES zero does not blank while the arithmetic arms do

### The refutation this note is written from
Row `GR-13.18.8.4-1` was adjudicated CONFORMS and OVERTURNED to `PARTIAL` by the refuter. Its reasoning, verbatim:

> The adjudicator measured only stores whose SENDING value is already zero (MOVE 0 / MOVE ZERO / an identifier holding zero) - the one axis GR1 holds fixed. Flipping it breaks the row: for a NONZERO sending value that STORES as zero, the MOVE arm does not blank while the arithmetic arm does, on identical items. GR1 obliges blanking 'when the item is a receiving operand and the value being stored is zero'; a PIC 9(3) item cannot hold 0.4, so the value stored is zero (the same truncated value the edit pipeline itself uses - proof: PIC ZZZ9 BLANK WHEN ZERO receiving 0.4 renders ' 0', i.e. Z-suppression ran on the TRUNCATED 0 in the same Format() call whose BWZ guard tested the UNTRUNCATED 0.4). Mechanism: src/Cobol.Net.Runtime/Values/Numeric/CobolEdit.cs:79 tests `blankWhenZero && value == 0` on the raw (value, valueScale) pair, 37 lines BEFORE the mask rescale at :116 (`CobolNum.Rescale(value, valueScale, fracDigits, Truncation)`); the arithmetic emitters happen to hand it a value already at the resultant's scale, so COMPUTE/GIVING blank correctly and MOVE does not. Two-arm defect (feedback_two_arm_dispatch), and the refutation is robust to the interpretive question: under the opposite reading of 'the value being stored' (the SENDING value) the MOVE arm would be right and COMPUTE/ADD GIVING/DIVIDE GIVING wrong - so the row cannot be CONFORMS under either reading. Sibling not yet probed but visibly identical by reading: src/Cobol.Net.Runtime/Values/Numeric/CobolLocaleEdit.cs:87 `if (blankWhenZero && unscaled == 0)` also precedes its rescale, and its DeEdit at :237 shares the shape. PARTIAL rather than DIVERGES per the brief's 'two halves, one verified' rubric and for consistency with this file's GR-13.18.8.4-3 row, but the open half is a SILENT WRONG ANSWER on legal COBOL through the commonest verb in the language, not merely an unprobed edge. Identical at --std 85/2002/2014/2023. test-ref is empty, so nothing was over-claimed there; the row still cannot close.
