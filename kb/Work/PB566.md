# PB566

## Mechanism
the BLANK WHEN ZERO guard tests the UNSCALED sending value 37 lines before the mask rescale, so a MOVE that STORES zero does not blank while the arithmetic arms do

### The refutation this note is written from
Row `GR-13.18.8.4-1` was adjudicated CONFORMS and OVERTURNED to `PARTIAL` by the refuter. Its reasoning, verbatim:

> The adjudicator measured only stores whose SENDING value is already zero (MOVE 0 / MOVE ZERO / an identifier holding zero) - the one axis GR1 holds fixed. Flipping it breaks the row: for a NONZERO sending value that STORES as zero, the MOVE arm does not blank while the arithmetic arm does, on identical items. GR1 obliges blanking 'when the item is a receiving operand and the value being stored is zero'; a PIC 9(3) item cannot hold 0.4, so the value stored is zero (the same truncated value the edit pipeline itself uses - proof: PIC ZZZ9 BLANK WHEN ZERO receiving 0.4 renders ' 0', i.e. Z-suppression ran on the TRUNCATED 0 in the same Format() call whose BWZ guard tested the UNTRUNCATED 0.4). Mechanism: src/Cobol.Net.Runtime/Values/Numeric/CobolEdit.cs:79 tests `blankWhenZero && value == 0` on the raw (value, valueScale) pair, 37 lines BEFORE the mask rescale at :116 (`CobolNum.Rescale(value, valueScale, fracDigits, Truncation)`); the arithmetic emitters happen to hand it a value already at the resultant's scale, so COMPUTE/GIVING blank correctly and MOVE does not. Two-arm defect (feedback_two_arm_dispatch), and the refutation is robust to the interpretive question: under the opposite reading of 'the value being stored' (the SENDING value) the MOVE arm would be right and COMPUTE/ADD GIVING/DIVIDE GIVING wrong - so the row cannot be CONFORMS under either reading. Sibling not yet probed but visibly identical by reading: src/Cobol.Net.Runtime/Values/Numeric/CobolLocaleEdit.cs:87 `if (blankWhenZero && unscaled == 0)` also precedes its rescale, and its DeEdit at :237 shares the shape. PARTIAL rather than DIVERGES per the brief's 'two halves, one verified' rubric and for consistency with this file's GR-13.18.8.4-3 row, but the open half is a SILENT WRONG ANSWER on legal COBOL through the commonest verb in the language, not merely an unprobed edge. Identical at --std 85/2002/2014/2023. test-ref is empty, so nothing was over-claimed there; the row still cannot close.

## Landed 2026-09-20 (wave 41 finisher)

The guard is now AFTER the store rescale in `CobolEdit.Render`, testing the stored digit string, and the
pre-rescale test on the raw `(value, valueScale)` pair is deleted — there is one test, not two. The
determination: §13.18.8.4 GR1's "the value being stored" is the value the item ends up HOLDING, because
§14.9.25.4 GR6 d) closes "Alignment of the numeric value by decimal point, any necessary zero filling, any
truncation of digits, and transfer of the algebraic data into the receiving data item, take place as defined in
14.6.8" and §14.6.8.2 r4 transfers "with zero fill or truncation on either end as required" (§13.18.8.1 in one
line: the clause "causes the blanking of an item when a value of zero is being stored in it"). Every citation
re-run through `cite.py --check`. That covers LOW-order truncation (`MOVE 0.4 TO PIC 9(3)`) and HIGH-order
truncation (`MOVE 100 TO PIC 99`) alike, and it is the same value the neighbouring rule-7 b) all-suppressed test
already read — the file used to disagree with itself two branches apart.

Siblings swept (CLAUDE.md rule 4):

- `CobolLocaleEdit.Format` — r14's decimal-point alignment is hoisted above the two zero short-circuits, so r10
  (BLANK WHEN ZERO) and r15 b) (all-Z) both ask what is BEING STORED. The alignment reads the PICTURE only, so
  r10 still decides before any locale is consulted and an unavailable locale still stores blanks for a zero.
- `CobolEdit.Float` — both arms already tested the stored value (normalization leaves the significand's leading
  digit nonzero, so its truncation cannot produce a zero; §14.9.25.4 GR6 d) 4 b makes an underflow zero). The
  rules are now cited at both.
- `StrongTypeModel.cs:185` — the stale `§13.18.7` (the BLANK clause) corrected to `§13.18.8`; repo swept for
  siblings, none.

Golden: `tests/conformance/85/pb566_blank_when_zero_stored_value.cob` (+ `.out`, 85 manifest) — both truncation
ends, MOVE vs COMPUTE vs MULTIPLY GIVING on the same items, a floating-currency mask, VALUE 0, INITIALIZE and
the GR3 de-edit back, each expectation derived from the rule and not from the compiler. The SR22 rejecting side
(`'S'`/`'*'` with the clause) is already pinned by `tests/conformance/negative/pb528-picture-composition.cob`
items PB09/PB10, so no second negative was forked.

Row `GR-13.18.8.4-1`: PARTIAL → CONFORMS (batch `pb566-gr1.json`; with PB509's row the inventory GAP moved 2366 → 2364).
