# PB175

Found 2026-08-30 by the PB168 pre-landing review's mechanical step: `python scripts/semgrep/verify.py`
FAILs on the CLEAN tree at `e71c031d` — `cobolnet-no-biginteger` 4 → 34 (+30), 
`cobolnet-raw-diagnostic-code-literal` 423 → 472 (+49), `cobolnet-no-decimal` 3 → 2 (a DOWN, also
unbaselined). Verified by stash/verify/pop that the PB168 working-tree diff contributes ZERO of these —
the drift landed with earlier batches.

Two halves:

1. **Adjudicate the drift.** For each rule, diff the current findings against the baseline set and
   disposition each new site: a genuine violation gets fixed (the banned-numeric rules exist because
   `COBOLNET_DESIGN.md` §1.2 bans those types outside their sanctioned homes); a sanctioned use gets an
   explicit recorded decision, and only then a re-baseline. +30 BigInteger sites is the suspicious one —
   the sanctioned arbitrary-precision home is CobolDec's SDIDI internals; 30 new sites suggests a
   mechanism leaked outward. The raw-diagnostic-literal count (+49) is likelier benign accretion
   (`ctx.Edition.Error("COBOLNETnnnn", …)` call sites the descriptor migration has not reached), but each
   still needs the look. The DOWN on no-decimal must also be re-baselined — a baseline that overstates
   violations hides the next UP.

2. **Give the check a gate seat.** The drift was invisible because verify.py runs in NO gate — not
   build-local, not battery.sh (green_gates_arent_evidence: a check nobody runs cannot go red). Add it as
   a battery leg (it is seconds, no build dependency) so baseline drift fails the comprehensive gate the
   batch it lands, with the usual verdict-line read.

**The disposition is `recorded decision`, not `fix`, and the ground is that neither site introduces a CODE.**
Both are additional call sites of a band this note already names as the remaining 439's shape — a code with no
`DiagnosticCatalog` descriptor, emitted only from bare literals:

PB236 reused them deliberately (its report names 1639/0862/0898 as reuse), which is the RIGHT call under

So the harm this rule guards — a code with no descriptor, no `docs/DIAGNOSTICS.md` row, no drift test, and

**What is NOT being claimed.** This does not convert the bands, and the conversion is still owed and still

## 2026-09-05 — landing train 7: `cobolnet-no-biginteger` 36 → 46, adjudicated as the SAME sanctioned mechanism

`verify.py` on the merged train-7 tree: `bound-node-carries-rendered-text` 3 → 3, `no-decimal` 2 → 2,
`raw-diagnostic-code-literal` 441 → 441 — and **`cobolnet-no-biginteger` 36 → 46**. The whole +10 is in ONE
file, `src/Cobol.Net.Runtime/Values/Numeric/CobolFloat.cs` (7 occurrences on `9be09f0f`, 17 after), and it is
PB623's. Measured per file: `PicInfo.cs` 1, `CobolIntrinsics.Text.cs` 1, `CobolDec.cs` 8, `CobolEdit.Float.cs`
16, `CobolNum.cs` 3 — every one of those unchanged by the train.

**The disposition is `recorded decision`, not `fix`, and the ground is that the rule's own escape clause is
met at every new site.** The rule reads: "`BigInteger` is banned in the runtime value model. 19-38 digit
fixed-point uses Int128. If a value genuinely exceeds Int128, that is a spec question (§8.8.1 arithmetic
bounds) to answer with a citation, not a wider type." `CobolFloat` already carried SEVEN accepted occurrences
inside the 36 — PB77's (2026-08-18) past-the-carrier exact expansion, `man × 5^scale` then a shift or a
`RoundDiv`, which is reached ONLY when the exact value does not fit the `Int128` carrier. PB623 did not add a
new use of the type: it made that same expansion the ONE landing (`ExactRatio` / `ExactScaled` /
`TryExactScaled`), so the existing mechanism now serves the four entry points that previously each held their
own `v * Pow10.AsDouble(scale)` binary64 multiply. The fast path is still pure `Int128` and is proved to cover
every PICTURE fraction (man < 2^53 and 5^31 < 2^72 put the product below 2^125, §13.18.40.3 rule 14);
`BigInteger` is reached only past the carrier, past scale 31, or on a negative scale — exactly the "value that
genuinely exceeds Int128" the rule exempts, with §14.6.8.2 rules 1 and 4 and CONFORMANCE.md DOC-A.1-70 as the
citation. The alternative would be to keep a binary64 multiply that §14.6.8.2 rule 1 forbids.

**What is NOT being claimed.** This does not widen the value model: no field, no carrier and no public
signature changed type — every `BigInteger` here is a local in a conversion helper, and `TryExactScaled`
still returns `Int128`. Half 1 of this note (adjudicating the pre-existing 36 and the 439-shaped literals)
is untouched and still owed.

Re-baselined with `python scripts/semgrep/verify.py --update-baseline` on the merged train tree, so
`cobolnet-no-biginteger` now records **46** and an `UP` again means a real increase.
