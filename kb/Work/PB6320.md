# PB6320 — the running account is the config dir's name, never the login's

**Sites:** `scripts/orchestrator/account.py` (`config_dir`, `current`, `Account.uuid`), `scripts/orchestrator/budget.py` (`live_reading`)

**What happened (2026-11-27).** The default config dir `~/.claude` was signed into account 2 (the owner's choice while account 1 is offline). `account.py` maps a config dir to a row of `model_rules.json` `accounts.list` by directory alone, and the row whose `config_dir` is null is `~/.claude`, which is account 1. So the session ran as account 2 and every tool that asks "which account am I" answered `account1`:

- `budget.py` stamped account 2's status-line readings (`<config dir>/rate-limits.json`) as account1's and used account1's weekly reset (Sunday 10:00 UTC) instead of account 2's (Saturday 17:00 UTC), so the week boundary and the remainder it printed were wrong;
- the loop mailed "ledger publish owed (account1)" for an artifact this login cannot open.

Telemetry was right throughout, because it is keyed by `user.account_uuid`, the one fact that names the login.

**Where the code is.** `scripts/orchestrator/account.py:138-141` (`config_dir`) returns `CLAUDE_CONFIG_DIR` or `~/.claude`; `account.py:206-216` (`current`) returns the table row whose directory equals it and consults nothing else; `account.py:96-114` (`global_config`, `_oauth`, `uuid`) already reads the signed-in `oauthAccount.accountUuid` from the config dir's `.claude.json`, but only telemetry filters (`budget.py:100`, `account_events`) and `as_json` use it. `budget.py:188` (`live_reading`) then reads the row's config dir and `budget.py:218` (`current`) takes the row's weekly reset. The module header (`account.py:15-18`) states the rule as "the config dir names the account"; it holds only while each config dir stays signed into its own account.

**Fix direction.** Resolve the account from the signed-in login's account uuid, or at least verify it: the row records the account uuid it expects (or `current` reads the config dir's `.claude.json` `oauthAccount.accountUuid` and finds the row by it), and when the config dir's row and the login's uuid disagree `current` fails loudly, naming both, never labelling the login with the row's name (the standing rule that an unresolvable input fails loudly and takes no default). Add a self-test case to `account.py --self-test` for a config dir whose `.claude.json` names the other account's uuid, and a case for a row with no recorded uuid. The loop's mail and the ledger publish read the same resolved account.
