# PB6161 — LANDED — at COBOL-85 the second OPEN of an open physical file answers 41

## Owner decision (2026-11-24)

The owner, asked whether at `--std 85` a second OPEN of a physical file already open through another SELECT answers status 41,
answered verbatim: **"Yes, return 41"**. This replaces PB670's option (i) (2026-10-23, "permit the second open as 1985's silence
allows") at COBOL-85 only. The same day the owner added that each edition's own text decides it, so 2002, 2014 and 2023 were
derived again from their own text below and not assumed to keep the existing behaviour.

## The defect

PB670 asked on the premise that 1985 is silent. It is not (PB6130 lead L1, upheld by its refuter):
- §1985:II.2: "The terms 'file referenced by file-name' and 'file' mean the physical file regardless of the file-name used in the
  COBOL program".
- §1985:VII.4.3.4 GR5: "each subsequent OPEN statement execution for that same file must be preceded by the execution of a CLOSE
  statement".
- §1985:VII.1.3.5, I-O status 41: "An OPEN statement is attempted for a file in the open mode".
- Whether two ASSIGN literals name one file is the implementor's (§1985:VII.2.3.3 SR3). WiseOwl maps them to one physical file
  when they reach one host path.

Repro (before this change): golden `pb670_cobol85_no_sharing_facility` expected 00 for legs B-IN, C-IO, C-EXT, B-IO and C-OUT.
Code site: `src/WiseOwl.Cobol.Runtime/IO/FileRegistry.cs#SharedOpenAttempt` skipped every check at 85.

The 2002 status 41 rule was read on the rendered PDF page (2002 PDF page 175, printed page 153): "An OPEN statement is attempted
for a file connector in an open mode". The 2002, 2014 and 2023 behaviour already matched its text; only 1985 changed. Every
citation passed `cite.py --check`.

## Fix

- `FileRegistry.SharedOpenAttempt`: one loop over the connectors open on the physical file answers 41 at 85 and Table 19's 61 from
  2002.
- Deleted, because they existed only to admit an 85 sibling: `FileRegistry`'s release-before-sibling loop,
  `FileConnector.ReleaseBufferedRecords` and `SequentialConnector`'s override with its deferred release fault, the open-sibling arm
  of `FileConnector.OtherConnectorsMayShare`, `StoreTable.AttachCreated`'s `arbitrated` parameter (PB754's guard is loud at every
  edition again) and the OUTPUT arm's truncation `NoteRelease` in `SequentialConnector.OpenCore`.
- Witnesses: `wiseowl/cases/14.9.27-OPEN-STATEMENT/pb6161_second_select_opens_an_open_file_85` (85) and
  `pb6161_second_select_opens_an_open_file` (2002, 2014, 2023), expected values derived from the text above; the old
  `pb670_cobol85_no_sharing_facility` is replaced by the 85 twin. `SharingFacilityEditionTests` covers every organization and every
  pair of modes at each edition, a third connector, the refused connector's CLOSE (42, the holder unaffected) and the buffered
  85 writer.
- Docs: `docs/conformance/3/D-85-OPEN-OF-AN-OPEN-FILE.md` (the per-edition derivation), DOC-A.1-77 and -131,
  `docs/rearchitecture/DESIGN-runtime-library.md`, `docs/VERSION_CHANGE_REFERENCE.md` row 7.39, `DialectBehavior.FileSharingFacility`.
- 1985 code reads 1985-GR-VII.4.7.4-7 and -12 named the deleted member; they were re-read on this branch by a reader and a
  refuter and imported with `code_reads.py import --replace`.

## Sweep

The refusal is one loop in the one OPEN dispatch (`OpenArbitrated` → `SharedOpenAttempt`), which every OPEN reaches, sequential,
relative and indexed, so a third SELECT, every open mode and OPEN after CLOSE are covered by the same site (unit tests). SORT and
MERGE USING/GIVING files open through the same registry. A connector's own re-OPEN still answers 41 first through
`RefusedAsAlreadyOpen` at every edition.
