# PB5188 - at --std 85 an index data item is admitted as an intrinsic function argument, a SORT or MERGE key and a report SOURCE: the operand rules take the 2023 contexts with no edition arm

**Sites:**

- `src/WiseOwl.Cobol.Compiler/Binding/Procedure/ExpressionBinder.cs` (`Rules`; landed: `IndexDataItemAdmittedAt`, `OperandRef`)
- `src/WiseOwl.Cobol.Compiler/Binding/IntrinsicResultType.cs` (`UniformArgumentType`)
- `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/SortKeyAdmission.cs` (`Violation`)
- `src/WiseOwl.Cobol.Compiler/Binding/ReportSectionBinder.cs` (`BindSourceOperand`)
- `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ReportWriterBinder.cs` (landed: `ScreenSourceIdentifier`, where the SOURCE identifier-1 is resolved and screened)
- `src/WiseOwl.Cobol.Editions/Diagnostics/DiagnosticCatalog.cs` (landed: `IndexDataItemContext`, COBOL6979)

**Mechanism.** §1985:VI.5.14.3 SR5 lets an index data item be referenced only in SEARCH or SET, a relation condition and the USING phrases of the Procedure Division header and CALL. The arithmetic, subscript, reference-modifier, PERFORM VARYING and MOVE contexts refuse it at 85. Three contexts do not: `OperandContextRules.Rules` admits it as an intrinsic function argument (the 2023 answer) and `UniformArgumentType` types MAX, MIN, ORD-MAX and ORD-MIN over it, so FUNCTION LENGTH (IX) and MAX (IX IY) compile; `SortKeyAdmission.Violation` admits it as a SORT or MERGE key; `ReportSectionBinder.BindSourceOperand` admits it as a SOURCE.

**Found by.** The 1985 code read (2026-11-10; its records are `E:/COBOL-coord/scratch/coderead-85/for-register.json`): each rule below was read against the code sites it names and probed at `--std 85`, and found non-conforming. Verdict, harm, evidence, repro and observed text are the records'; the rows' verdicts are recorded on another branch.

**Inventory.** `work.py check` refuses a 1985 rule id in `inventory_rows` (kb/Work PB5094, open), so `inventory_rows` is empty and the rows this note claims are the rule ids of the list below.

Implemented at 85 for every arithmetic and statement operand the compiler screens by class: OperandContextRules.Rules admits a class-index data item in the SET window and refuses it in an arithmetic expression, a subscript, a reference modifier and PERFORM VARYING (COBOL0844, worded by NonNumericOperandKind), Sr1ClassRefusal refuses it in MOVE and in the implicit moves of READ INTO, WRITE FROM, RELEASE FROM, RETURN INTO and INITIALIZE REPLACING (COBOL0809), and each statement's own operand screen refuses it elsewhere. Probed at --std 85: accepted in SET IX TO XI, SET XI TO IX, SET IY TO IX, SEARCH VARYING IX, IF IX = IY, IF IX = XI and CALL USING IX; refused in MOVE (both sides), ADD, SUBTRACT, MULTIPLY, DIVIDE and its REMAINDER, COMPUTE (both sides), DISPLAY, ACCEPT, ACCEPT FROM DAY, a subscript, both reference-modifier positions, PERFORM TIMES and VARYING (varied item, FROM, BY), the class and sign conditions, GO TO DEPENDING, INITIALIZE, every INSPECT, STRING and UNSTRING operand, EVALUATE subject and object, CALL and CANCEL targets, FILE STATUS, RELATIVE KEY, LINAGE, RECORD VARYING DEPENDING, OCCURS DEPENDING, WRITE ADVANCING, and the report CONTROL and SUM clauses. Not implemented, three contexts the 1985 list does not name: (1) an intrinsic function argument: Rules gives FunctionArgument the 2023 answer (IndexDataItemAdmitted true, "SR10: an intrinsic function argument") with no edition arm, and UniformArgumentType types MAX, MIN, ORD-MAX and ORD-MIN over index arguments, so FUNCTION LENGTH (IX), ORD-MAX (IX IY), ORD-MIN (IX IY), MAX (IX IY) and MIN (IX IY) compile at 85; §1989:A.2.2 gives the argument types as numeric, alphabetic, alphanumeric and integer only, and §1985:IV.4.3.3 knows three classes ("alphabetic, numeric, and alphanumeric"), so no function rule of the 1989 module admits the item either. (2) a SORT or MERGE key: SortKeyAdmission.Violation has no index arm, so SORT S1 ASCENDING KEY SK and MERGE S1 ASCENDING KEY SK with 05 SK USAGE INDEX compile (at 2023 too). (3) the report SOURCE clause: BindSourceOperand admits SOURCE IS IX (the CONTROL clause on the same item is refused, COBOL1700). The witness is MOVE IX TO N, refused with COBOL0809.

**Repro (`1985-SR-VI.5.14.3-5`).** `cobol.exe <file> --std 85 --source-format fixed --run`

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. IDXFN.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  TBL.
           05  ELT PIC X OCCURS 5 TIMES INDEXED BY XI.
       01  IX USAGE IS INDEX.
       01  IY USAGE IS INDEX.
       01  N PIC 99 VALUE 0.
       PROCEDURE DIVISION.
       P1.
           SET XI TO 3.
           SET IX TO XI.
           SET XI TO 2.
           SET IY TO XI.
           COMPUTE N = FUNCTION ORD-MAX (IX IY).
           DISPLAY N.
           COMPUTE N = FUNCTION LENGTH (IX).
           DISPLAY N.
           STOP RUN.
```

**Expected (from the 1985 text, the record's).** A diagnostic at each function reference (lines 16 and 18) and no object program: §1985:VI.5.14.3 SR5 "An index data item can be referenced explicitly only in a SEARCH or SET statement, a relation condition, the USING phrase of a Procedure Division header, or the USING phrase of a CALL statement." A function argument is none of the five (the 2023 rule, §2023:13.18.60.3 SR10, adds "an intrinsic function argument"), and §1989:A.2.2 lists the types of argument as numeric, alphabetic, alphanumeric and integer.

**Observed (the record's).** exit 0, no diagnostic (none with --flag-extensions either); the program runs and displays 01 and 08. Siblings at --std 85, each exit 0 with no diagnostic: FUNCTION ORD-MIN (IX IY), SET XI TO FUNCTION MAX (IX IY), IF FUNCTION MIN (IX IY) = IY; SORT S1 ASCENDING KEY SK USING F1 GIVING F3 and MERGE S1 ASCENDING KEY SK USING F1 F2 GIVING F3 where 05 SK USAGE INDEX is in the SD record; 10 COLUMN 1 PIC 9(4) SOURCE IS IX in a report DETAIL group.

**Fix direction (root cause, CLAUDE.md rule 4).** Make IndexDataItemAdmitted in the one operand-context table a function of the edition, so the 1985 list is one arm of the table every context reads, and route the SORT key and SOURCE contexts through that table instead of their own screens.
