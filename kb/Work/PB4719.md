# PB4719 — MCS NameOf misses the colon

**Sites:** `src/WiseOwl.Cobol.Runtime/Communication/MessageStoreState.cs:190` (`MessageStoreState.NameOf`, with its screen members `NotInAFileName`, `ReservedDeviceNames` and `DeviceStem`); `tests/WiseOwl.Cobol.Tests.Unit/MessageControlTests.cs` (`UnusableDefinitionFile_IsStatus91_OnEveryStatement`, `NameResemblingAReservedOne_IsDefined`); `docs/rearchitecture/DESIGN-communication-facility.md` section 6

The file exists only on open PR #1161 (branch `worktree-wf_d99db659-fdf-22`); the line is read from that worktree. Reported by the branch review, not probed. R2-1, copied: the finisher's new `NameOf` screen refuses a symbolic name holding a slash or a backslash because a device file is built from the name, and misses the colon on Windows, so a name can still leave the MCS directory or land in a file's alternate stream, with status 00. The design section 6 and the `NameOf` summary say a name that would address a directory is refused.

**Landed (wave 20261872 C).** Re-probed with the new theory cases against the old screen at main 7ccb2822b: 34 failed, each a definition accepted (status 00) for `C:EVIL`, `a<b`, `a|b`, `a?b`, `a*b`, a quote, a control character, or a device name (`CON`, `NUL.x`, `COM1`, `LPT0`, `CONIN$`). The device file is `<name>.out` (`MessageStore.Commit`), so on Windows `C:EVIL` is a drive-relative path, `A:B` an alternate stream and `NUL.out` the NUL device. `MessageStoreState.NameOf` now refuses every character in the union of `Path.GetInvalidFileNameChars` and the Windows set (the colon included) and a name whose stem before the first dot, without trailing spaces, is a Windows device name, the same on Linux. The mcs-state.json readers look names up in the definitions' dictionaries and build no path, so `NameOf` is the one screen (sweep: `Path.Combine` in `Runtime/Communication` takes only `DefinitionFile`, `LockFile`, `StateFile` and `device + ".out"`).
