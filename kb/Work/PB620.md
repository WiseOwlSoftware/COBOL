# PB620 — LANDED — one function still on the landing intake

Found 2026-09-05 by the `PB251` implementer (report §"NEW DEFECT"), whose `INTAKE(<class>)` contract on every
`IntrinsicRenderer` argument seam is what made this class findable: every remaining `Arg(...)` call in the exact
switch is a candidate, and of `SignOf`, `Floor`, `Truncate`, `FractionPart`, `Mod`, `Rem` and COMBINED-DATETIME, only
the last has no `RenderDec` arm. Re-derived on the PB251 worktree (`4e45fa8e`); the code site re-located on main.

## Repro (`--std 2023`, `OPTIONS. ARITHMETIC IS STANDARD-DECIMAL.`, `01 WS-S PIC 9(5)V9(8) VALUE 3661.12345678.`)

```cobol
           DISPLAY "LIT=" FUNCTION COMBINED-DATETIME(1, WS-S)        *> 1.0366112345678   (correct)
           DISPLAY "EXP=" FUNCTION COMBINED-DATETIME(1, WS-S + 0)    *> 1.03661123456     (two digits lost)
           COMPUTE WS-E = 1 + (WS-S + 0) / 100000                    *> 1.0366112345678   (the EAE, spelled out)
```

Source: `<a9d94900 scratch>/PB251/p5.cob`.

## The rule

§15.4.1 r1, under a standard arithmetic mode: "the returned value shall equal the value of the equivalent arithmetic
expression" (`OK §15.4.1 1)`), and its NOTE 2 states the consequence outright — `function-identifier =
equivalent-arithmetic-expression` evaluates TRUE. §15.17.4 r1 gives COMBINED-DATETIME's EAE, "The equivalent
arithmetic expression is as follows:" `argument-1 + (argument-2 / 100000)` (`OK §15.17.4 1)`). The argument's own
rule, §15.17.3 r2, requires only the "standard numeric time form" (`OK §15.17.3 2)`) and places no fraction-digit
limit on it. The three lines above must agree; they do not.

## The mechanism

`src/Cobol.Net.Compiler/CodeGen/Emit/IntrinsicRenderer.cs`, the exact switch's `case "CombinedDatetime":` (main
`:315`): argument-2 is consumed as `NumX t = Arg(ic, 1)` — `INTAKE(LANDED)` after PB251, i.e. `NumericRenderer.Landed`
at `rcv.WorkingScale(ReceiverContext.SdidiLandingScaleFloor)` = `max(receiver scale, 6)`, which is 6 in a
receiver-less context. `RenderDec` has no `"CombinedDatetime"` arm, so the standard-mode call falls through to the
exact switch and the SDIDI argument is truncated on intake. A literal or a data item argument never reaches the
landing (they are read exact); only an arithmetic-expression argument does, which is why the note's first line is
right and its second is wrong.

## Fix shape

Give COMBINED-DATETIME a `RenderDec` arm — or consume argument-2 through `DecArg` — exactly as PB56 did for the other
EAE functions; the residue is "one function still on the landing intake", one function over. The intake contract
already names the seam: the `Arg` call at `:315` changes class from LANDED to EXACT/LIFTED and the drift test
(`IntrinsicArgumentIntakeContractDriftTests`) holds the vocabulary. Golden: a STANDARD-DECIMAL program with the three
lines above (literal argument, expression argument, spelled-out EAE) asserting all three equal, plus the NATIVE twin
asserting the same three agree with each other (§15.4.1's native latitude is over representation, and the function
has an EAE, so r1 binds under native too); a drift assertion that every EAE function in `IntrinsicCatalog` has a
`RenderDec` arm.

## Landed 2026-09-21 (wave 43C)

Reproduced first on the implementer's own build, exactly as the note describes (`--std 2023`, `OPTIONS.
ARITHMETIC IS STANDARD-DECIMAL.`): `LIT=1.0366112345678` against `EXP=1.03661123456`, and the §15.4.1 NOTE 2
relation condition `FUNCTION COMBINED-DATETIME(1, WS-S + 0) = 1 + ((WS-S + 0) / 100000)` evaluating FALSE.

THE FIX went to the rule's own place rather than to this arm. `IntrinsicRenderer.RenderDec` gained a
`"CombinedDatetime"` arm over a new `CobolDate.CombinedDatetimeDec(mode, integerDate, seconds, leapSecond)` —
§15.17.4 r1's equivalent arithmetic expression written out on the SDIDI, `argument-1 + (argument-2 / 100000)`,
where the division by a power of ten is exact at every argument scale — so a Dec- or float-carried argument-2
is claimed BEFORE the exact switch under either arithmetic mode. The exact arm's intake changed from `Arg`
(INTAKE(LANDED)) to `RawArg` (INTAKE(EXACT)), so no landing stands in front of argument-2 on any carrier. Both
carriers ask ONE §15.17.3 screen (`CobolDate.CombinedDatetimeOutOfRange`), and `SecondsOutOfStandardForm`'s
(unscaled, scale) overload now forwards to a `CobolDec` one — one comparison, one message, no drift (the PB32
lesson), and the bound is no longer scaled UP into the carrier (the old `86400 * 10^secScale` wrapped past
secScale 33).

⚠ ONE CLAIM IN THIS NOTE DID NOT SURVIVE. "§15.4.1's native latitude is over representation, and the function
has an EAE, so r1 binds under native too" is wrong: §15.4.1 r1 is stated "When standard-decimal arithmetic or
standard-binary arithmetic is in effect", and the native paragraph grants "an implementor-defined approximation
of the value of that expression". The native lane agrees anyway — measured identical, all three lines — but
because COBOL.NET's approximation of an EAE IS the exact/SDIDI evaluation, which is a DETERMINATION and not r1.
The prescribed NATIVE twin golden was therefore measured (identical output) and NOT added to the corpus: under
native a Dec-carried argument-2 is not reachable from source, so the twin would pin the same exact arm leg A
already pins. The structural claim is held by the drift test instead.

THE SHAPE, so the next one is automatic: `ExactCarrierBoundaryDriftTests` invariant 3 —
`EveryArmThatCanTakeADecArgument_HasADecBody` — reads both switches out of the renderer and fails when an
exact-switch arm that consumes a FRACTION-BEARING intake (`Arg`/`RawArg`/`AlignedArgs`/`RawArgPairs`, never the
scale-0 `IntArg`) has no `RenderDec` label. It catches this defect on its own first input and clears FACTORIAL,
whose integer argument needs no Dec body.

Goldens: `conformance:2014/pb620_combined_datetime_eae` (both carriers into one receiver, NOTE 2's relation
condition, §15.4.1's same-value rule across two argument shapes, and the §15.17.3 r2 screen asked of each
carrier under armed EC-ARGUMENT-FUNCTION checking) and `conformance:negative/pb620-combined-datetime-below-2014`
(COBOLNET1502, the edition half).

## The THIRD carrier (same landing, found by the group's own sibling sweep)

COMBINED-DATETIME has three carriers, not two, and the binary64 one had NO argument rule at all. Measured on a
pre-fix build of this worktree, in ONE program under ONE armed `>>TURN EC-ARGUMENT-FUNCTION CHECKING ON`
directive (`scratchpad/w43c/p620f.cob`):

```
FLOAT=00000018639999999999      FUNCTION COMBINED-DATETIME(1, F)   F USAGE COMP-2 VALUE 86400
abnormal run-unit termination: EC-ARGUMENT-FUNCTION (fatal): COMBINED-DATETIME argument-2 is not in standard
numeric time form: the value shall be >= 0 and < 86,400 (ISO §7.3.17.4 GR5, LEAP-SECOND OFF)
                                FUNCTION COMBINED-DATETIME(1, G)   G PIC 9(5)V9(8) VALUE 86400
```

One VALUE, two answers, decided by the item's USAGE. §15.17.3 r2 is a rule about argument-2's VALUE -- "Argument-2
shall be in standard numeric time form" (`OK §15.17.3 2)`), and §15.5.5 defines that form by MAGNITUDE alone -- so
the USAGE of the item holding it cannot decide whether §15.3's "incorrect value for that argument"
(`OK §15.3 14)`) applies. `CobolIntrinsics.CombinedDatetimeReal` now asks the SAME screen as its two exact-carrier
twins, through `CobolDate.CombinedDatetimeOutOfRangeReal` -> the one `CombinedDatetimeOutOfRange` comparison; it
takes the compilation group's LEAP-SECOND state like they do (§7.3.17.4 GR4/GR5 is what sets the bound, so a screen
blind to the directive would admit 86 400.5 on one carrier and refuse it on another); and a non-finite operand is
screened at the same site, because neither §15.5.2's integer date form nor §15.5.5's standard numeric time form is
a range containing an infinity or a NaN.

WHICH ARM: the third one. The first pass fixed the exact arm and added the Dec arm; this is the arm neither
touched. Held by `IntrinsicCarrierAgreementDriftTests.CombinedDatetime_ScreensItsArguments_FromEveryCarrier`,
which asserts ONE message from all three carriers for each of r1 and r2, and then asserts that one step INSIDE
the bound every carrier still answers §15.17.4 r1's expression -- a guard that raised early would be as wrong as
one that never raised. Golden: `conformance:2014/pb620_combined_datetime_carriers` (PB620CAR, 2014+, native
arithmetic -- the only mode in which the binary64 body is reachable, since the SDIDI claims every float argument
under a standard mode). No binary64 VALUE is printed: §15.4.1's last paragraph grants native arithmetic "an
implementor-defined approximation of the value of that expression" (`OK §15.4.1`) and 1/100000 is not a binary
fraction, so the float legs assert only rule-derived facts.

Inventory: batch `w43c-combined-datetime-third-carrier` (AR-15.17.3-1, AR-15.17.3-2) -- evidence only, GAP
2310 -> 2310.
