# PB3567 — a positive signed literal VALUE on an unsigned item is accepted

## Scenario

Fuzz program fz04158 (`THEY_REJECT:8.8.4.2.4`; GnuCOBOL: "data item not signed", line 14, `PIC 9(4) VALUE +0`). fz00665 and
fz02760 in the same signature are the COMP-1 / COMP-3 extension that GnuCOBOL does not know (GNUCOBOL-SIDE), not this defect.
WiseOwl enforces the rule only for a negative literal (COBOL1625). GnuCOBOL's own test `syn_value.at` ("Signed numeric
literal") expects both `+1` and `-1` on `PIC 9` refused (the adjudicator's report).

### Reduced repro (the D1 adjudicator's probe, verbatim: `adj\D1\probes\sgn\sgn5.cob`)

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. SGN5.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 U0 PIC 9(4) VALUE +5.
PROCEDURE DIVISION.
MAIN-PARA.
    DISPLAY "U0 [" U0 "]"
    STOP RUN.
```

## Expected (spec)

Each citation was re-run through `python scripts/spec/cite.py --check` from the worktree on 2026-10-23 (all OK).

- §13.18.63.3 3) (OK): "If a signed numeric literal is specified, the subject of the entry shall be either a signed numeric
  data item or a numeric-edited data item with a representation of a sign."
- §8.3.3.3.2 2) (OK): "A literal shall not contain more than one sign character. If a sign is used, it shall appear as the
  leftmost character of the literal. If the literal is unsigned, the literal is nonnegative." A literal written with `+` carries
  a sign, so it is a signed literal.

Expected: refused at every edition, like the negative literal (COBOL1625).

## Actual (judge e7cf38ce4)

Compiles at 2014 and at 2023 and prints `U0 [0005]`.

## Mechanism and code site

`src/Cobol.Net.Compiler/Binding/DataBinder.cs:3331` (`ValidateNumericValue`): `if (neg && !signBearing)` applies SR3 only to
negative literals. The fix that added it (CA34, recorded in kb/Work PB3) skipped '+' as "the harmless idiom". That was an
implementer's latitude call, not an owner decision, and `docs/CONFORMANCE.md` does not record it.

## Witnesses

fz04158 (fz00665 and fz02760 are not witnesses).

## Sibling sweep and golden to require

Sweep the same check wherever a literal's sign is tested against an unsigned subject: VALUE in condition-names, INITIALIZE
REPLACING literals. A MOVE of a signed literal to an unsigned item is a conversion and is NOT this rule. Golden: `VALUE +5`,
`VALUE +0` and `VALUE -5` on an unsigned item (refused at every edition), the same on a signed item and on a numeric-edited
item with a sign representation (accepted).

## Orchestrator decision

§13.18.63.3 3): "If a signed numeric literal is specified, the subject of the entry shall be either a signed numeric data item or a numeric-edited data item with a representation of a sign"; a literal written with `+` is signed (§8.3.3.3.2 2): "If a sign is used, it shall appear as the leftmost character of the literal. If the literal is unsigned, the literal is nonnegative."). CA34 (kb/Work PB3) scoped COBOL1625 to negative literals as "the harmless idiom"; that was an implementer's latitude call, not an owner decision, and the rule has no sign-value carve-out. Sweep: the same check wherever a literal's sign is tested against an unsigned subject (VALUE in condition-names, INITIALIZE REPLACING literals, MOVE of a signed literal to an unsigned item is a conversion and is NOT this rule).

## Landed (w1157 group D, 2026-10-23) — a signed literal is signed whichever sign it carries

**Re-probe (the worktree's own build, before the fix).** The note reproduced: `PIC 9(4) VALUE +5` compiled at every edition
and printed `0005`; `VALUE -5` was already COBOL1625.

**Root.** `DataBinder.ValidateNumericValue` read the literal's sign into `neg = t[0] == '-'` and tested `neg && !signBearing`,
scoping SR3 to negative literals (the CA34 fix, kb/Work PB3, recorded '+' as "the harmless idiom"). It now tests
`signedLiteral = t[0] is '-' or '+'`. §13.18.63.3 3) speaks of "a signed numeric literal" and §8.3.3.3.2 2) makes a literal
that uses a sign a signed one ("If the literal is unsigned, the literal is nonnegative" is the only other kind); the rule
has no sign-value carve-out, and the CA34 reading was an implementer's latitude call, not an owner decision. Both citations
were run through `cite.py --check`. The diagnostic text (COBOL1625) and the catalog entry now say "signed", not
"negative", and name the literal.

**Sibling sweep.** One funnel (`ScreenValueLiteral`) asks SR3 for every VALUE format (item, table, level-88, report; the
group arm is excepted because a group is never numeric), and `ValidateNumericValue` is its one reader, so there is no second
arm: `88 U0-A VALUE +5` over an unsigned conditional variable is refused like `-5` (probed at 2002, 2014 and 2023). INITIALIZE
... REPLACING and a MOVE of a signed literal are conversions (§14.9.20.4 4) is "as though a series of implicit MOVE or SET
statements") and are not this rule. The population scans found no program in the suite, the NIST corpus or the tests that
writes `+` on an unsigned VALUE.

**Goldens.** `13.18.63-VALUE/pb3567-value-plus-literal-unsigned-subject` (`VALUE +5`, `VALUE +0` on PIC 9(4), refused at
all four editions), `pb3567_value_signed_literal_signed_subject` (S9(4) VALUE +5 / -5 / +0 accepted at every edition,
read back through comparisons), `pb3567_value_signed_literal_numeric_edited_2023` (sign-bearing numeric-edited items take
both signs; images from §13.18.40.5 Table 8). The `ca34_value_negative_unsigned` diagnostics expectation text moved with the
message. Inventory: SR-13.18.63.3-3 re-verdicted CONFORMS (statement restated, three witnesses added); no row closed.

**Review round 1 (R1-1): the floating-point arm.** `NumericLiteral.ExpandFloatingPoint` (which rewrites a floating-point
VALUE literal to its exact fixed-point value before the screen, §8.3.3.3.3 GR5) dropped a leading `+`, so
`PIC 9(4)V9 VALUE +1.5E+0`, `VALUE +0.0E+0` and `88 ... VALUE +1.0E+1` passed SR3 while `VALUE +1.5` was refused;
§8.3.3.3.3 2) makes a literal with a signed significand a signed literal. The expansion now keeps the written sign. Goldens
`pb3567-value-plus-float-literal-unsigned-subject` (refused at 2002, 2014, 2023) and
`pb3567_value_signed_float_literal_signed_subject` (accepted, exact values).
