# PB3567 — a positive signed literal VALUE on an unsigned item is accepted

## Scenario

Fuzz program fz04158 (`THEY_REJECT:8.8.4.2.4`; GnuCOBOL: "data item not signed", line 14, `PIC 9(4) VALUE +0`). fz00665 and
fz02760 in the same signature are the COMP-1 / COMP-3 extension that GnuCOBOL does not know (GNUCOBOL-SIDE), not this defect.
WiseOwl enforces the rule only for a negative literal (COBOLNET1625). GnuCOBOL's own test `syn_value.at` ("Signed numeric
literal") expects both `+1` and `-1` on `PIC 9` refused (the adjudicator's report).

### Reduced repro (the D1 adjudicator's probe, verbatim: `adj\D1\probes\sgn\sgn5.cob`)

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. SGN5.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 U0 PIC 9(4) VALUE +5.
PROCEDURE DIVISION.
MAIN-PARA.
    DISPLAY "U0 [" U0 "]"
    STOP RUN.
```

## Expected (spec)

Each citation was re-run through `python scripts/spec/cite.py --check` from the worktree on 2026-10-23 (all OK).

- §13.18.63.3 3) (OK): "If a signed numeric literal is specified, the subject of the entry shall be either a signed numeric
  data item or a numeric-edited data item with a representation of a sign."
- §8.3.3.3.2 2) (OK): "A literal shall not contain more than one sign character. If a sign is used, it shall appear as the
  leftmost character of the literal. If the literal is unsigned, the literal is nonnegative." A literal written with `+` carries
  a sign, so it is a signed literal.

Expected: refused at every edition, like the negative literal (COBOLNET1625).

## Actual (judge e7cf38ce4)

Compiles at 2014 and at 2023 and prints `U0 [0005]`.

## Mechanism and code site

`src/Cobol.Net.Compiler/Binding/DataBinder.cs:3331` (`ValidateNumericValue`): `if (neg && !signBearing)` applies SR3 only to
negative literals. The fix that added it (CA34, recorded in kb/Work PB3) skipped '+' as "the harmless idiom". That was an
implementer's latitude call, not an owner decision, and `docs/CONFORMANCE.md` does not record it.

## Witnesses

fz04158 (fz00665 and fz02760 are not witnesses).

## Sibling sweep and golden to require

Sweep the same check wherever a literal's sign is tested against an unsigned subject: VALUE in condition-names, INITIALIZE
REPLACING literals. A MOVE of a signed literal to an unsigned item is a conversion and is NOT this rule. Golden: `VALUE +5`,
`VALUE +0` and `VALUE -5` on an unsigned item (refused at every edition), the same on a signed item and on a numeric-edited
item with a sign representation (accepted).

## Orchestrator decision

§13.18.63.3 3): "If a signed numeric literal is specified, the subject of the entry shall be either a signed numeric data item or a numeric-edited data item with a representation of a sign"; a literal written with `+` is signed (§8.3.3.3.2 2): "If a sign is used, it shall appear as the leftmost character of the literal. If the literal is unsigned, the literal is nonnegative."). CA34 (kb/Work PB3) scoped COBOLNET1625 to negative literals as "the harmless idiom"; that was an implementer's latitude call, not an owner decision, and the rule has no sign-value carve-out. Sweep: the same check wherever a literal's sign is tested against an unsigned subject (VALUE in condition-names, INITIALIZE REPLACING literals, MOVE of a signed literal to an unsigned item is a conversion and is NOT this rule).
