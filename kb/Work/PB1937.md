# PB1937 — OPEN (unprobed)

Filed by the train-1006 lander from wave 1006 group D's report (`w1006d-PB1144-report.md`, "New defects", item 1).
Same mechanism family as PB1118 (landed in train 1006).

## Suspected defect

§14.2.3 GR8 makes a BY REFERENCE formal occupy "the same storage area as the argument", and §14.6.13.2 rule 5
raises EC-DATA-INCOMPATIBLE when a dynamic-length item's content does not agree with the reading description's
DYNAMIC LENGTH clause. The variable-length-group copy-in at the activation boundary stores each dynamic-length member
through `CobolDynString.Store(value, dynMax[k])`, which TRUNCATES to the formal's maximum. If the argument's member is
longer than the formal's LIMIT, the callee sees a shortened value with no condition, and the copy-back on return
writes the shortened value over the caller's: silent data loss.

**Not probed.** It needs a Format-2 CALL or INVOKE whose argument is a variable-length group with a dynamic-length
member whose LIMIT exceeds the formal's. Probe first (I3); if it reproduces, the read should take the content whole
and raise through `CobolDynString.Agree` as PB1118's foreign-storage reads do, never truncate on the way in.

**Sites.** `src/Cobol.Net.Runtime/Control/StorageCell.cs:122` (`SetDynAt(..., CobolDynString.Store(v.Dyn(k), dynMax[k]))`)
and the `GroupImageCodec` `FromVarImage` dynamic-member store.

## Landed 2026-10-04 (wave 1013 group N, w1013n)

**Re-probed first** (`w1013n/p/t1937.cob`, caller `D LIMIT 10` holding 8 characters, formal `D LIMIT 3`, Format-2 CALL):
the callee displayed `SUB[HabcF]` and the caller afterwards `[HabcF]` with `LENGTH(D)` = 3 — the shortened value was
written back over the caller's. Reproduced as filed.

**Fix (one rule, three sites).** §14.2.3 GR8 (`cite.py --check` OK) makes the formal occupy the argument's storage, so the
BOUNDARY copy-in into a LINKAGE formal keeps a dynamic-length member's whole content; only a store through the
RECEIVING description (a MOVE into the group, the copy-back into the caller's own item) truncates to its LIMIT
(§8.5.1.10.4).
- `GroupImageCodec.EmitVarImageMethods`: `FromVarImage(CobolVarGroup __v, bool __storage = false)`; the DynLeaf arm is
  `__storage ? __v.Dyn(k) : CobolDynString.Store(__v.Dyn(k), max)`, forwarded into nested groups and fixed-OCCURS elements.
- `PlaceRenderer.WriteVarGroupImage(..., formalStorage)`; the two LINKAGE formal copy-in sites pass `true`
  (`ProgramEmitter` formal copy-in, `OoEmitter` method-formal copy-in).
- The read side of rule 5 (`CobolDynString.Agree`, PB1118) now covers a WHOLE-GROUP read of a LINKAGE group too:
  `CurrentImage` agrees every LINKAGE dynamic-length member; `AsVarImage` takes `__agree` and a STATEMENT's read passes
  it, while the boundary's own copy-out passes nothing (a callee that never referenced the member must not raise at return).
- `StorageCell.cs:122` (`StoreVarGroupAt`, a CELL's dynamic slot) is deliberately unchanged: the slot belongs to the cell
  class's own description, shared by every description of the cell, so storing through it truncates to that LIMIT.
- **Witnesses:** `conformance:2014/pb1937_vlg_formal_limit_keeps_argument_storage` (checked callee raises and RESUMEs,
  caller intact; unchecked callee reads the whole; an agreeing 2-character content raises nothing) and negative
  `pb1937-vlg-formal-limit-at-2002`.
- **closes_rows:** none — the note owned no inventory row; the rule rows of §14.2.3 GR8 and §14.6.13.2 rule 5 were closed
  by earlier landings (PB1118), and this fix adds the variable-length-group arm of both.
