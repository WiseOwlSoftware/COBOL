**Rule it breaks:** one mechanism per job (DESIGN-architecture-review §5.2; CLAUDE.md rule 4): the value of a literal is decided once, by CobolLiteral.Decode (src/Cobol.Net.Frontend/Common/CobolLiteral.cs:148, used by ExpressionBinder, ConcatFolder and SetBinder), which keeps the §8.3.3.2.4 GR1 rule that only the delimiting separators are removed and decodes the hexadecimal forms; StripLiteral re-decides it by deleting every quote and apostrophe in the token, and is the only such hand decoder in Cobol.Net.Compiler (swept: no other quote-strip or [1..^1] slice)

**Scenario:** Verified on the pin's Debug build (cobol.exe at 8be230068): a program with SELECT F1 ... FILE STATUS IS WS-FS, 01 WS-FS PIC XX with 88 FS-HEX04 VALUE X"3034", and under >>FLAG-14 I-O-STATUS-04 the statements IF WS-FS = "0'4" and IF FS-HEX04. The compiler warns COBOLNET1621 'a reference to a FILE STATUS item that tests for 04' at the first (the literal's value is the three characters 0'4, which StripLiteral turns into 04) and says nothing at the second (X"3034" has the value 04, which StripLiteral turns into X3034). The same decoder feeds the 88-set build in Run and the VALUE-EDITING scan (LiteralHasNoEditingSymbols), so an embedded doubled quote is misread there too

**Landed.** FlagConformancePass.StripLiteral is deleted. The relation operand (OperandLiteral), the level-88 VALUE reading (FileStatusConditionName) and the VALUE-EDITING scan (LiteralHasNoEditingSymbols) read the literal's value through CobolLiteral.Decode, the one literal decoder: the delimiters are no part of the value (section 8.3.3.2.4 GR1), a doubled one is one character (sections 8.3.3.2.3 SR3 and 8.3.3.5.3 SR3), and X"3034" is the characters 04 (section 8.3.3.2.4 GR4). Re-probe on the pin: IF WS-FS = "0'4" was flagged and IF FS-HEX04 (88 VALUE X"3034") and IF WS-FS = X"3034" were not; now only the last two are. The hexadecimal literal is the HEXLIT token, which the old reader never saw in a relation; CharacterLiteralText names the three tokens (STRINGLIT, NATLIT, HEXLIT) once for both readers. VALUE-EDITING now scans a hexadecimal VALUE by its value (X"3132" is flagged, X"312E" is not). Witnesses: FlagPopulationTests IoStatus_FlagsEveryConditionThatTestsTheFileStatusItem (the PB3234 rows) and ValueEditing_AHexadecimalLiteralIsScannedByItsValue.
