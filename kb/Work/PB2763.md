**Rule it breaks:** Work fixed for the run is done once, not per call (design §4 item 5 and §5.4; dimensions.md 3, the performance dimension). The trim rule has a span form whose stated purpose is that 'a fixed-width (space-padded) operand costs no substring per comparison' (LocaleCollation.TrimForLocale doc), and STANDARD-COMPARE does not use it

**Scenario:** orderingTable is the DECODED literal-9 of an ORDER TABLE clause (CobolIntrinsics.StandardCompare doc), so it is a compile-time constant. Every call still runs CollationEngine.TryGetOrderingTable, which does the following. IsDefaultOrderingTableName runs Canon on the argument AND on the constant DefaultOrderingTableName: a Split array, its parts, a Join and an upper-case pass for each, so at least 6 objects come from the constant alone, which never changes. IsKnownLocale then runs CldrLocaleTag.Parse twice (directly, then again inside LoadExact via CldrLocaleTag.FileName; about 8 objects each by my reading). TableForLocale then does the ResolveLocale dictionary lookup. For the default table at levels 1-3, CollationEngine.StandardAtLevel goes through Cached, which allocates new CollationOptions(strength, Shifted) on every call. Finally, LocaleCollation.TrimForLocale(string) allocates a substring for every operand with trailing spaces, which is the normal shape of a PIC X(n) argument. A program that calls STANDARD-COMPARE once per record over a 1,000,000-record file under ORDER TABLE 'es' therefore performs 2,000,000 tag parses and more than 20,000,000 allocations whose results are identical on every call
