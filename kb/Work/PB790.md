# PB790 — OPEN — a bracket the grammar read as two brackets

Filed 2026-09-06 14:19 PDT by the registrar from the PB770 implementer's report (§"New defects found",
paragraph A). PB770 LANDED in train 19; this is pre-existing on both arms and PB770 did not change it.

⛔ **The report filed this claim as UNMEASURED** — *"§12.3.7.2's general format brackets `{THROUGH|THRU}
literal-2` and `{ALSO literal-3}…` as ALTERNATIVES within one literal-phrase entry — **but that claim is not yet
measured**; … `scripts/render-spec-page.py 321` … is what settles whether the brackets are exclusive before
anything is rejected"*. **The registrar rendered it. The claim holds.** The evidence is below, and the note is
filed on the rendering rather than on the transcription.

## The printed figure, RENDERED (not read off the OCR)

`python scripts/render-spec-page.py 321` → PDF page 321, printed folio **291**, section "where literal-phrase
is:". The figure is:

```
              ⎡  ⎧ THROUGH ⎫             ⎤
              ⎢  ⎨         ⎬  literal-2  ⎥
  literal-1   ⎢  ⎩ THRU    ⎭             ⎥
              ⎢                          ⎥
              ⎣  { ALSO literal-3 } …    ⎦
```

Two alternatives **stacked inside ONE pair of square brackets**, with **no choice-indicator bars** anywhere in
the figure. §5.2.6.2 (`--check` OK): *"Brackets, [ ], enclosing a portion of a general format indicate that the
syntax element contained within the brackets **or one of the alternatives contained within the brackets** may be
explicitly specified or that portion of the general format may be omitted."* Choice indicators are the ONLY
notation that would license both (§5.2.6.4 — *"When enclosed by brackets, zero or more of the alternatives
contained within the choice indicators shall be specified"*), and the printed page has none. So a literal-phrase
entry carries a THROUGH range, **or** one or more ALSO phrases, **or** neither — never both.

The transcription's own figure note at `specs/ISO_COBOL.md` (under the literal-phrase `<pre>` in §12.3.7.2) says
the same thing — *"The outer bracket is optional and holds two mutually exclusive alternatives"* — and is
CONFIRMED correct by the render. Recorded because `feedback_spec_diagrams_render_pdf` makes the transcription's
diagram claims a hypothesis until the page is rendered, and this one now is not.

The syntax rules corroborate rather than decide: §12.3.7.3 SR14 b)3 / c)3 (`--check` OK) reads *"Each alphanumeric
literal, when a THROUGH **or** ALSO phrase is specified, shall be one character in length"* — one rule stated once
over both phrases, which is how the standard writes a rule about a single-slot alternative.

## The grammar, quoted from main at `07cbb2ad`

`src/Cobol.Net.Frontend/Grammar/Core/CobolSpecialNames.g4:194-197`:

```antlr
alphabetEntry
    : (cobolWord | literal) ((THRU | THROUGH) (cobolWord | literal))?
      (ALSO (cobolWord | literal))*
    ;
```

Two INDEPENDENT optionals. `"A" THRU "C" ALSO "D"` matches, and there is no predicate, no bind check and no test
anywhere that refuses it (`grep -rn "ALSO" src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs` — the only
consumers are the two branches quoted next).

## Where the operands are dropped

`src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs`, `AlphabetLiteralPhrase` (`:980`), the per-entry loop at
`:1004-1046`:

```csharp
var operands = AlphabetOperands(name, entry, national);            // :1006  ALL of them, source order
if (operands.Count == 0) continue;
bool thru = entry.THRU() is not null || entry.THROUGH() is not null;
if (thru || entry.ALSO().Length > 0) { …SR14 b3/c3 length check over EVERY operand… }   // :1009-1025
if (thru)
{
    if (operands.Count < 2) continue;
    int a = operands[0][0], b = operands[1][0], step = a <= b ? 1 : -1;
    for (int c = a; ; c += step) { Assign((char)c, advance: true); if (c == b) break; }
    continue;                                                       // :1032  ⛔ operands[2..] never read
}
if (entry.ALSO().Length > 0) { … }                                  // :1034  unreachable for this entry
```

`AlphabetOperands` (`:1168`) walks `entry.ChildCount` in source order, so for `"A" THRU "C" ALSO "D"` it returns
`["A","C","D"]` — the ALSO operand IS decoded, IS length-checked by the SR14 b3 arm at `:1015`, and is then
discarded by the `continue` at `:1032`. It never reaches `Assign`, so it takes no ordinal position.

## What the user's program gets

The declaration is illegal source that compiles, and the collating sequence it builds is one no legal reading of
the clause produces. §12.3.7.4 GR7 k3 puts every UNSPECIFIED character above the highest specified one, so `'D'`
sorts ABOVE `'A'..'C'` — where the ALSO operand the user wrote asks (GR7 k6) for `'D'` to share literal-1's
position with `'A'`. Every downstream reader of the alphabet inherits that: PROGRAM COLLATING SEQUENCE, SORT/MERGE
key order, `STANDARD-COMPARE`, and the HIGH-VALUE/LOW-VALUE extremes computed by `AlphabetExtremes` (`:1060`).

Flags: `under_rejects` (illegal source accepted at every `--std` and both strictness axes) + `silent` (no
diagnostic of any kind). `wrong_answer` is deliberately FALSE: the source is not conforming, so the standard
defines no correct answer to be wrong about — the harm is the silent acceptance and the sequence it fabricates,
which is what the prose above says instead of a flag that would overstate it.

⚠ **Not measured, and it should be by whoever fixes this:** the exact ordinal `'D'` ends up with, and the
`AlphabetExtremes` HIGH/LOW consequence. The registrar did not build (per the coordinator's instruction). The
probe is a three-line program — `ALPHABET ALF IS "A" THRU "C" ALSO "D".` + `PROGRAM COLLATING SEQUENCE IS ALF` +
`IF "D" < "A" DISPLAY "BELOW" ELSE DISPLAY "ABOVE"` — compiled at `--std 2023` and at `--std 85`.

## Fix shape

The grammar rule is the defect, not the binder: `alphabetEntry` must offer the two phrases as ONE alternation, so
the binder's `if (thru) … continue` can no longer be silently reached with ALSO operands behind it.

```antlr
alphabetEntry
    : (cobolWord | literal)
      ( (THRU | THROUGH) (cobolWord | literal)
      | (ALSO (cobolWord | literal))+
      )?
    ;
```

That makes the co-occurrence a PARSE-time refusal rather than a bind-time check nobody wrote, and it deletes the
`operands[2..]` reachability question instead of answering it. ⚠ Pair it with a NEGATIVE fixture per arm
(alphanumeric and `FOR NATIONAL` — `feedback_two_arm_dispatch`; PB770 is the fifth instance in this very clause)
and check the diagnostic the new shape produces is not a bare COBOL0001: `CobolParserCoreBase.ReservedUserWordViolation`
(`src/Cobol.Net.Frontend/Parsing/CobolParserCoreBase.cs:311`) is this frontend's precedent for a grammar-level
refusal that still names its cause instead of degrading to "no viable alternative".

⛔ Do NOT "fix" this by making the binder merge the two phrases. §12.3.7.4 GR7 k5 (THROUGH — a native run over
ascending positions) and k6 (ALSO — one shared position) place operands by incompatible rules; there is no
defined meaning for a merged entry, which is precisely why the printed format excludes it.

## Sweep — where else two stacked bracket alternatives became two optionals

The shape is "a printed bracket holding stacked alternatives, transcribed into the `.g4` as independent `?`/`*`
suffixes". ⚠ **Not swept here** — this note measures one instance. The nearest sibling by construction is the
CLASS clause's own `{ literal-5 [ {THROUGH|THRU} literal-6 ] }` group (same paragraph, §12.3.7.2, and its figure
note records "No choice indicators appear in this figure"), which has no ALSO to conflict with; the general sweep
belongs with the fix and wants the printed page per candidate, not the OCR.
