# PB3760 — `(3)` is a computed operand, yet it crosses as the literal 3

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundCall.cs#Gr8ArgumentLiteral` (deleted; `BoundCallArg` states the invariant), `src/WiseOwl.Cobol.Compiler/Oo/ActivationDescriptions.cs#OfValue`, `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/CallEmitter.cs#ArgCarrierText`, `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/CallBinder.cs#BindCall` (the BY VALUE arm's sole-literal arm; the keyword-less arithmetic-expression arm's GR9 mode) and `#Gr9NonIdentifierMode` (was `Gr9BareLiteralMode`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/IntrinsicBinder.cs#BindArgOperand` (the `activationArgument` leg, was `nullAdmitting`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/UdfBinder.cs#UdfActivate`, `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#ReduceArgument` (doc), `tests/WiseOwl.Cobol.Tests.Unit/GroupMoveSenderChannelDriftTests.cs#WrittenLiteral_IsTheOperandKind_NoReaderRecoversOneFromAnExpression`, `tests/WiseOwl.Cobol.Tests.Unit/PredefinedNullContextDriftTests.cs#BoundPredefinedNull_HasOneProducer_AndEveryCallerIsAnSr1Context`.

Filed 2026-10-25 by the enqueue clerk. A parenthesized numeric LITERAL `(3)` or `(-3)` BY CONTENT into a GROUP formal is still accepted and stores 3. The report cites §14.9.4.4 GR8 and §14.8.2.2 rule 2 (an adjudicator confirms with `cite.py --check` before the fix): they conform a group formal
only against an argument that is itself an alphanumeric group item or a literal; a parenthesized numeric literal is an arithmetic expression (PB3678's ruling: only an operator, a sign or enclosing parentheses make an expression), so the
call is not conforming and should be refused. It is under-rejection: the source is accepted and silently stores the value.

## Mechanism
`Gr8ArgumentLiteral.NumericText` (`BoundCall.cs` about line 31) recovers a literal's text from a `BoundComputedOperand`, so that `BY VALUE -1.234E-5` (which arrives as `BoundNegate(BoundNumLiteral)`) reads as a literal. It
cannot tell that spelling from a parenthesized `(3)`. Its readers: `ActivationDescriptions.OfValue` (line 33: `BoundComputedOperand ce when Gr8ArgumentLiteral.NumericText(ce.Expr) is { } text`) and `CallEmitter`'s numeric-literal funnel (the `case BoundComputedOperand ce when Gr8ArgumentLiteral.NumericText(ce.Expr)` arm, about line 1017 of `ArgCarrierText`).
Both read the recovery as "this is a written literal".

## Fix direction
Carry a bind-time statement of whether the operand was a written literal (a sign alone is part of the literal; an enclosing parenthesis is not) to those readers, rather than re-deriving it from the expression shape downstream (one reduction, PB165).
Golden: `CALL ... USING BY CONTENT (3)` into a group formal refused, in every edition, with `BY CONTENT 3` and `BY VALUE -1.234E-5` still accepted. Repro: `E:/COBOL-coord/scratch/mythos/w20261500g/p2.cob` lines 21-22.

## Landing

Re-probed on a fresh build (`E:/COBOL-coord/scratch/w20261720e/p2.cob`, the repro): `BY CONTENT -3`, `(-3)`, `(3)` and `3` into the
plain-group formal all compiled, and stored `3`, `L` (the overpunched -3: the recovered literal crossed as a numeric cell, not
through the group arm), `3` and `3`; only `(N + 1)` was refused. Siblings measured the same way: INVOKE `BY CONTENT (3)` and a bare
`(3)` into a group formal passed bind and then crashed the code generator (`InvalidOperationException: an INVOKE argument into a group
formal is neither an identifier, a literal nor a numeric function`, `OoEmitter.EmitInstanceInvoke`), `FUNCTION F((3))` into a group
formal stored 3, and - found on the way - a keyword-less `(7)` against a BY VALUE formal was refused COBOL1687 (it was hard-coded
BY CONTENT, where §14.9.4.4 GR9 b) assumes BY VALUE: `cite.py --check` OK).

Spec (each `cite.py --check` OK): §14.9.4.4 8) and §14.9.23.4 4) regard only an argument that "consists merely of a single identifier
or literal" as one; §8.8.1.1 makes "an arithmetic expression enclosed in parentheses" an arithmetic expression; §8.3.3.3.2 2) puts a
leading sign inside the literal; §14.8.2.2 2) asks a MOVE question of a BY CONTENT argument opposite a group formal, and an arithmetic
expression is no MOVE sender; §8.4.3.2.4 5) b) passes a function argument that "is a literal, an arithmetic expression" BY CONTENT.

Fix: the bound operand's KIND is GR8's answer, stated once by the binder. `Gr8ArgumentLiteral` is deleted with both readers' arms
(`ActivationDescriptions.OfValue`, `CallEmitter.ArgCarrierText`); the one producer that needed it, the CALL BY VALUE arm, binds the
parse tree's sole numeric literal (`ReduceArgument`'s `SoleNumericLiteral`, sign included) as a `BoundNumericLiteral` like the BY
CONTENT and keyword-less arms; the function-prototype activation argument (`IntrinsicBinder.BindArgOperand`, flag renamed
`activationArgument`, which also carries the SR1 a) NULL admission) binds a sole written literal as the literal and a parenthesized or
compound argument through `ConditionBinder.CompoundOperand` (PB3678's CALL door), never back through `OperandOf`. The keyword-less
expression takes `Gr9NonIdentifierMode` and SR22's class screen. INVOKE needed no binder change: it already bound a sole literal as the
literal, and its conformance read the deleted recovery. Goldens: `cases/14.9.4-CALL/pb3760_parenthesized_literal_group_formal_refused`,
`cases/14.9.23-INVOKE/pb3760_invoke_parenthesized_literal_group_formal_refused`,
`cases/8.4.3.2-Function-identifier/pb3760_function_parenthesized_literal_group_formal_refused`,
`cases/14.9.4-CALL/pb3760_literal_and_expression_arguments` (+ `_below_2002`); drift pin
`GroupMoveSenderChannelDriftTests.WrittenLiteral_IsTheOperandKind_NoReaderRecoversOneFromAnExpression`; docs/CONFORMANCE.md D-B4 and
docs/INTERPROGRAM_DESIGN.md (Format 2's argument classification) updated.

For the next implementer:
- `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundCall.cs#BoundCallArg` - a written numeric literal is a `BoundNumericLiteral` in every lane and mode; a `BoundComputedOperand` is an expression or a function value. Never recover a literal from `ce.Expr` (`(3)` binds to the same `BoundNumLiteral` as `3`); the drift pin refuses the shape.
- `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/IntrinsicBinder.cs#BindArgOperand` - the `activationArgument` leg is the UDF lane only; the intrinsic lane still maps a parenthesized argument through `OperandOf` (an intrinsic's own §15 argument rules decide it, not GR8).
- Trap: `SoleOperand.Primary` returns a PARENTHESIZED primary (it stops at the `primaryExpression` tier), so "is this a sole unparenthesized primary" is `Primary(ax) is { } p && p.LPAREN() is null`.
