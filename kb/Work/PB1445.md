# PB1445 — LANDED

## The rule (every citation re-run by the registrar through `cite.py --check`)

> A literal shall not contain more than one sign character. If a sign is used, it shall appear as the leftmost character of the literal

`python scripts/spec/cite.py --check 8.3.3.3.2 "…"` → `OK  §8.3.3.3.2 2)  (Fixed-point numeric literals)`

## Finding — `numeric-literals` (crashes; rows `SR-8.3.3.3.2-2`)

**Mechanism.** DataBinder.IsLiteralValueOperand strips every unary sign off a VALUE operand with no count or adjacency check, so a VALUE literal with two signs or a sign separated from its digits is taken as literal-1 -- and `VALUE --5` reaches the C# backend and crashes it

**Repro.** 01 B PIC S9 VALUE --5.   (--std 2023; DISPLAY B) -> 'error: backend compilation failed ... error CS1059: The operand of an increment or decrement operator must be a variable, property or indexer'. Also accepted silently: VALUE +-5 (stores -5), VALUE -+5, VALUE ++5 (+5), VALUE - 5 (-5), VALUE -<newline>5 (-5), and 88 C1 VALUE - 5 (C1 true for B = -5). Probes: out/probe/numlit/u1,u2,u3,u5,u6,t4,u9.cob.

**Expected from the spec.** Each is refused with a diagnostic. §13.18.63.2 Format 1 is `VALUE IS literal-1` (Format 3 likewise literal-2/-3); §8.3.3.3.2 2) -- "A literal shall not contain more than one sign character. If a sign is used, it shall appear as the leftmost character of the literal" -- and the literal is "a character-string" (§8.3.3.3.2 lead), a space being a separator (§8.3.5 1)). So `--5`, `+-5`, `- 5` are not literals, and the VALUE clause admits no arithmetic expression (compile-time arithmetic expressions are permitted only in DEFINE/EVALUATE directives, constant conditional expressions and constant entries, §7.3.6).

**Observed / reasoning.** DataBinder.cs:5203-5206: `var u = op.unaryExpression(); while (u?.unaryExpression() is { } signed) u = signed; var p = u?.primaryExpression(); if (p?.numericLiteral() is not null ...) return true;` -- the loop descends through any number of addOp tiers and never consults ArithmeticFormationRules.SignIsPartOfLiteral (the project's one §8.3.3.3.2 rule-2 contiguity test, used by SoleOperand.NumericLiteral for EVALUATE/DEFINE/CONSTANT). The correct shape already exists: SoleOperand.NumericLiteral returns the literal text only when the operand is ONE sign adjacent to a bare numeric literal. The --5 text then flows verbatim into the emitted C# initializer, where `--5` is a decrement operator.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.cs#DataBinder.IsLiteralValueOperand (lines 5193-5216); valueClauseOperand : unaryExpression in src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4:55

## Finding — `numeric-literals` (under-rejects; rows `SR-8.3.3.3.2-2`)

**Mechanism.** The procedure-division `literal` slot reads a numeric literal as `(PLUS | MINUS)? numericLiteralCore` with the sign a separate default-mode token and no adjacency screen, so `MOVE - 5`, `ADD - 5`, `DISPLAY - 5` treat a separated sign-and-number as the literal -5

**Repro.** PROCEDURE DIVISION. MOVE - 5 TO A (A PIC S9(5)V99) -> accepted, A = -5.00; ADD - 5 TO A -> accepted, adds -5; DISPLAY - 5 -> accepted, prints -5; MOVE - .5 TO A -> accepted, A = -0.50. Same at --std 85/2002/2014/2023. Probes: out/probe/numlit/s2,s8,u4,s10.cob.

**Expected from the spec.** Refused. MOVE's sending operand, ADD's operands and DISPLAY's operands are identifier or literal; `- 5` is neither -- §8.3.3.3.2 2) puts a sign INSIDE the literal only as its leftmost character of one character-string, and §8.3.5 1) makes the space a separator. (A relation operand such as `IF A = - 5` is an arithmetic expression and remains legal; that probe s7 is correctly accepted.)

**Observed / reasoning.** CobolExpressions.g4:701 `signedNumericLiteral : (PLUS | MINUS)? numericLiteralCore` -- the fused SIGNED_INTEGERLIT/SIGNED_DECIMALLIT tokens exist only in the FUNCTION-argument and subscript lexer regions, so in DEFAULT mode `-5` and `- 5` (and `-`<newline>`5`) give the same MINUS INTEGERLIT pair, and consumers read ctx.GetText(), which drops the whitespace. The only adjacency screen for this grammar shape is SignedIntegerLiteral.Screen (COBOLNET2155), wired to the VALUE Format 2 subscript slot alone; its own doc comment names exactly this superset-parse hazard. Fix shape: one bind-time (or parse-listener) screen on every signedNumericLiteral with a PLUS/MINUS child, reusing the StopIndex+1 == StartIndex test, so the next literal slot is covered automatically.

**Code site.** src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4#signedNumericLiteral (line 701); src/Cobol.Net.Compiler/Binding/SignedIntegerLiteral.cs#SignedIntegerLiteral.Screen (the lone screened slot)

## What the fixer owes

ONE screen on every signedNumericLiteral with a PLUS/MINUS child (and on IsLiteralValueOperand, which must accept exactly one sign token adjacent to a bare numeric literal — reuse SoleOperand.NumericLiteral), using SignedIntegerLiteral.Screen's StopIndex+1 == StartIndex test, so the next literal slot is covered automatically; SignedIntegerLiteral.Screen (COBOLNET2155, today VALUE Format 2 only) should become that one screen. Keep `IF A = - 5` legal (an arithmetic expression). Negative goldens: VALUE --5 / +-5 / - 5, 88 VALUE - 5, MOVE - 5, DISPLAY - 5, MOVE - .5.

## Landing (wave 70, group U2 — reuses COBOLNET2155)

§8.3.3.3.2 rule 2 now has ONE contiguity test, `ArithmeticFormationRules.SignAbuts` (the sign's stream StopIndex + 1
== the literal's StartIndex, same line), asked from three places that each needed it:
- `LiteralScreenPass` (the one place a literal's own syntax rules are asked) screens EVERY `signedNumericLiteral` and
  `signedIntegerLiteral` node carrying a sign — the procedure `literal` slots (`MOVE - 5`, `ADD - 5`, `DISPLAY - 5`,
  `MOVE - .5`) and the VALUE Format 2 subscripts alike → COBOLNET2155. `SignedIntegerLiteral.Screen` became the
  pure reader `SignedIntegerLiteral.Read` (the pass reports; the reader returns the unsigned digits on a violation).
- `DataBinder.IsLiteralValueOperand` accepts a signed VALUE operand only when `SoleOperand.NumericLiteral` (new
  `UnaryExpressionContext` overload) calls it ONE literal; `ReportNonLiteralValueOperand` names the broken sentence
  through `ArithmeticFormationRules.SignedLiteralViolation` ("more than one sign character" / "sign separated") →
  COBOLNET2155. `VALUE --5` no longer reaches the backend (was CS1059, exit 70).
`IF A = - 5` and `COMPUTE A = - 5 * 2` stay legal: an expression operand's `- 5` is the unary alternative the parser
takes first, never a signed `signedNumericLiteral`. Goldens: `85/pb1445_signed_literal_forms`; negatives
`pb1445-value-double-sign`, `pb1445-condition-value-separated-sign`, `pb1445-move-separated-sign`. Row SR-8.3.3.3.2-2 →
CONFORMS (batch `w70u2-PB1445`, GAP 882 → 881).

For the next implementer:
- `src/Cobol.Net.Frontend/Expressions/ArithmeticFormationRules.cs#SignAbuts` — the ONLY rule-2 contiguity test; never
  compare `GetText()` (it strips the space). `#SignedLiteralViolation` names which sentence a signs-plus-literal operand
  breaks; `#SignRuleQuote` is the rule text every message quotes.
- `src/Cobol.Net.Compiler/Validation/LiteralScreenPass.cs#SignedSlot` — a new grammar rule that parses a sign as a
  separate token in front of a numeric literal gets a case here and is screened in every slot.
- Trap: the unsigned `ZERO_ARITH` figurative is still a VALUE literal; a SIGNED figurative (`VALUE -ZERO`) is not.
