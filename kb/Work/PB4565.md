# PB4565 — relative-delete-of-missing-record-succeeds: DELETE of an already-deleted relative record returns status 00 instead of 23 (invalid key)

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

A relative file is in dynamic (or random) access, and a DELETE names a relative key whose record has already been
deleted. The DELETE succeeds with status 00 and takes the NOT INVALID KEY phrase. ISO requires the invalid key
condition (status 23). A DELETE of a slot inside the file that was never written (relative key 1 here) also
returns 00.

## Minimal test case

Free reference format (`-free`).
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. DELTWICE.
ENVIRONMENT DIVISION.
INPUT-OUTPUT SECTION.
FILE-CONTROL.
    SELECT F ASSIGN TO "deltwice.dat"
        ORGANIZATION IS RELATIVE
        ACCESS MODE IS DYNAMIC
        RELATIVE KEY IS RK
        FILE STATUS IS FS.
DATA DIVISION.
FILE SECTION.
FD F.
01 REC PIC X(4).
WORKING-STORAGE SECTION.
01 RK PIC 9(2) VALUE 0.
01 FS PIC XX VALUE SPACES.
PROCEDURE DIVISION.
    OPEN OUTPUT F
    MOVE 3 TO RK
    MOVE "R003" TO REC
    WRITE REC
    CLOSE F
    OPEN I-O F
    MOVE 3 TO RK
    DELETE F RECORD
        INVALID KEY DISPLAY "FIRST DELETE INVALID " FS
        NOT INVALID KEY DISPLAY "FIRST DELETE OK " FS
    END-DELETE
    DELETE F RECORD
        INVALID KEY DISPLAY "SECOND DELETE INVALID " FS
        NOT INVALID KEY DISPLAY "SECOND DELETE OK " FS
    END-DELETE
    READ F
        INVALID KEY DISPLAY "READ 3 INVALID " FS
        NOT INVALID KEY DISPLAY "READ 3 FOUND " REC
    END-READ
    CLOSE F
    STOP RUN.
```

## Environment

cobc (GnuCOBOL) 3.2.0 on WSL2 Ubuntu (Windows 11 host). Compiled with `cobc -x -free -std=cobol2014 -o p prog.cob`
(prog.cob holds the program above) and run as `timeout 10 ./p` from the program's directory; the program creates its
own data file. cobc's compile step prints a C-compiler warning from the host's CFLAGS (`'_FORTIFY_SOURCE' redefined`),
which has no bearing on the result.

## Observed result

Exit code 0. Output:
```
FIRST DELETE OK 00
SECOND DELETE OK 00
READ 3 INVALID 23
```

## Expected result (per ISO)

§2023:14.9.10.4 rule 4: "If the file is relative and the access mode is random or dynamic, the mass storage control system
logically removes from the physical file that record identified by the content of the relative key data item associated
with file-name-1. If the physical file does not contain the record specified by the key, the invalid key condition
exists". §2023:9.1.13.5 rule 3) a) sets I-O status 23 when "an attempt is made to randomly access a record that does not
exist in the physical file".

Edition: the rule holds in COBOL 2014. The 2009 committee draft (CD 1.2) carries it in the same words, and Annex E of
2023 lists no change. The first DELETE removes record 3, and the READ that follows confirms with status 23 that the
physical file no longer contains it. The second DELETE therefore meets the invalid key condition. Expected output:
```
FIRST DELETE OK 00
SECOND DELETE INVALID 23
READ 3 INVALID 23
```

## Our compiler

WiseOwl COBOL (`--std 2014 --source-format free`) compiles the program with no diagnostic (no COBOL#### code), prints
the three expected lines and exits with code 0.

## Fix site

libcob/fileio.c, `relative_delete`. It reads the slot's record-size word and returns COB_STATUS_23_KEY_NOT_EXISTS only
when that read fails, that is, when the slot lies past the end of the file. Unlike `relative_read`, it never tests the
size word for 0, the marker of a deleted slot. An already-deleted slot is therefore written with 0 again and
COB_STATUS_00_SUCCESS is returned.
