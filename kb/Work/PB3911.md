# PB3911 — rewrite-record-from-not-supported: REWRITE record-name RECORD FROM ...: optional word RECORD gives 'syntax error, unexpected RECORD'

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S6) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\rewrite-record-from-not-supported.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\rewrite-record-from-not-supported\`.

## Summary

GnuCOBOL 3.2 refuses the optional word RECORD after the record-name (or file-name) of a REWRITE statement:
`REWRITE R RECORD FROM W` and `REWRITE R RECORD` both draw `syntax error, unexpected RECORD`. The general format of
REWRITE in the 2014 edition (and in 2023) is `REWRITE {record-name-1 | FILE file-name-1} RECORD [FROM ...]` with RECORD
not underlined, that is an optional word. Without the word the same statements compile and run. Class: rejects legal
ISO source.

```

```

`rwnorec.cob` and `rwfile.cob`: compile exit 0, run exit 0, output `NEW`.

## Expected result (per ISO)

The program is legal and prints `NEW`.

- §14.9.35.2 (checked, and rendered from the printed page, 2023 PDF page 740): the general format is
  `REWRITE { record-name-1 | FILE file-name-1 } RECORD [ FROM { identifier-1 | literal-1 } ] ...`; the figure note
  records that "`RECORD`, `WITH`, and `KEY` are **not** underlined".
- §5.2.3 (checked): "Optional words are reserved words or context-sensitive words. They are shown in uppercase and not
  underlined in general formats."
- §14.9.35.3 1) (checked): "Record-name-1 is the name of a logical record in the file section of the data division and
  may be qualified." §14.9.35.3 6) (checked): "If record-name-1 is specified, identifier-1 or literal-1 shall be valid
  as a sending operand in a MOVE statement specifying record-name-1 as the receiving operand." W (PIC X(3)) to R
  (PIC X(3)) is a valid MOVE.

Edition: 2014. The 2009 committee draft that became ISO/IEC 1989:2014 (CD 1.2, 14.9.33.1, rendered from its PDF, draft
page 544) prints the same format with RECORD not underlined. Annex E of the 2023 standard lists no change to REWRITE's
format (its only REWRITE item, §E.3.3 41), is a clarification about identifier-1).

Edition as recorded by the adjudicator: 2014. `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Class

GNUCOBOL-DEFECT: rejects legal ISO source (edition 2014).

## Our compiler (WiseOwl)

WiseOwl COBOL (built from main 6ed90bd1c), `cobol rwrec.cob --std 2014 --source-format free -o rwrec.dll`, then
`dotnet rwrec.dll`: compile exit 0, run exit 0, output `NEW`. `rwreconly` and `rwnorec`: `NEW`. WiseOwl refuses
`REWRITE FILE F` (COBOL1706) because it claims no support for the optional element Annex A.4.13 (the FILE phrase);
that is its documented choice, not part of this record. On the night witness fz00553 WiseOwl's run stops at OPEN I-O
of the absent indexed file (status 35, no FILE STATUS or declarative), which §9.1.13.1 leaves to the implementor.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `cobc/parser.y`, rule `rewrite_body`: `file_or_record_name from_option _retry_phrase _with_lock
  _invalid_key_phrases` has no optional `RECORD` between `file_or_record_name` and `from_option`. The grammar already
  has an optional-RECORD nonterminal (`_record`), which fits there.
