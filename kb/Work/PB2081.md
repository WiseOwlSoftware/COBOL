# PB2081 — context cap fired on a subagent's context

**What happened.** On 2026-10-05 three consecutive `land` units for train 1021 each ended `split` with "context N > 150000: winding the unit
down". The owner's question was why one unit keeps hitting limits and never finishes.

**Measured** (`E:\COBOL-coord\logs\*-land.jsonl`, `parent_tool_use_id` split): unit-own peak context 87,208 / 123,167 / 122,028 tokens
(all under the cap); subagent peak context 224,546 / 228,741 / 161,945 (the cobol-lander, 673 / 565 / 111 events). `orchestrate.ps1` set
`$stats.context` from EVERY `assistant` event, so the cap saw whichever message came last, usually the lander's. Each wind-down created
`scratch\STOP`, so the lander (maxTurns 220, its own bound) checkpointed and returned SPLIT mid-train, and the next unit re-read the checkpoint, status
file, manifest and reports before doing any new work: pure rework.

**Fix (landed with this note's change set).** `orchestrate.ps1` counts only events without `parent_tool_use_id` toward `context`/`peak_context`;
subagent events feed `peak_subagent_context` (logged). `test_orchestrate.ps1` check 7b (fake mode `bigsubagent`) pins it; DESIGN-orchestrator-loop.md
section 3 states the rule.

**Sibling sweep.** The same stream also feeds `Write-Checkpoint`/`checkpoint.py` counters (`calls`, `input`, `output` still count all messages, which is
right for cost); nothing else reads `context`. Open question for a follow-up: whether the lander subagent itself should be bounded by tokens as well
as turns (it reaches 225k); that is a lander-brief design question, not a supervisor one.
