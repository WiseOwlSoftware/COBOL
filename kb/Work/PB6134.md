# PB6134 - a requestor's SEND hung past the observation budget under gate load

**Sites:** `tests/WiseOwl.Cobol.Tests.Conformance/MessagingProcessTests.cs` (`AMessageLongerThanIdentifier1_IsTakenAndEcMcsMessageLength_AndTheServerCanStillAnswerIt`, line 223), `src/WiseOwl.Cobol.Runtime/Messaging/MessagingProtocol.cs` (`Scan`, `OnEnumerated`, `OnConnected`, `Quiesce`, `AfterLinkLoss`), `src/WiseOwl.Cobol.Runtime/Messaging/MessagingPeer.cs` (`Run`, `Pump`), `src/WiseOwl.Cobol.Runtime/Messaging/SocketTransport.cs` (`Connect`, `AcceptServerAsync`)

**Observation.** The full gate of worktree-wf_3da4b722-0ee-19 at 8ec00439f3 (run `TestResults/build-local/000006-20261123T170505Z`, Conformance 29,233 ran, 1 failed) failed this one case after 3 m 22 s:
`HarnessNonObservationException: no stdout line from 'dotnet "...\pb4744p-993427590137\PB4744C4.dll"' within 120000 ms`. The server
(`PB4744S4`, `WISEOWL_COBOL_MCS_SERVER=SRV`, EC-MCS-MESSAGE-LENGTH checking on) had printed `READY`; the requestor never printed `SENT`, the line
it DISPLAYs right after its SEND, whether the SEND succeeds or takes its ON EXCEPTION phrase. So the requestor's SEND did not complete in
120 s. Every failure path of the protocol ends the SEND (`OnActionFailed` -> `FinishSend` EC-MCS-IMP; no link and no start definition ->
EC-MCS-NO-SERVER), so a SEND that never returns is one that holds a live link to the server in `SendPhase.Waiting` while the server's
RECEIVE never takes the offer, or a requestor process that never reached the statement.

**Not reproduced.** On the same build: the class alone twice (25/25, 13 s and 8 s), and 8 concurrent runs of the class (200/200, 26-30 s
each). No other gate record under `.claude/worktrees/*/TestResults/build-local/` holds a failure of `MessagingProcessTests`. The branch
whose gate saw it changes only PICTURE analysis and the default currency sign (kb/Work PB5712, PB5614) and reaches no messaging code; main's
merged changes at that head (PB5715, PB6107) reach EXIT PROGRAM / GOBACK and two 2002 exception names.

**Ruled out by reading.** `MessagingPeer.Run`'s wait resets the wake before it pumps (`_wake.Reset()` then `Pump`, then `Wait`), so an
event queued during the pump sets it again: not a lost wakeup in the requestor's loop.

**Next.** Capture both processes' state when it recurs: the test reads only the requestor at the failing step, so the server's stdout
after `READY` and both processes' stderr are lost. A LiveProcess non-observation should report every live process's stderr and any unread
stdout of the test's other processes (the diagnosis needs to know whether the server reached `SRV EXC`), and the server-side accept loop
(`SocketTransport.AcceptServerAsync`, `AcceptRetryDelay`) and the server's handling of a Hello that arrives before its RECEIVE starts are
the first code to read against a captured trace.
