# PB188

Registered from the PB164 Step D review fleet's out-of-wave disposition (finding R-c). Reachable since the V59 /
PB164 wave-1 predicate widening, which is when a leaf could first be BOTH byte-form and `StoreAsImage`.

**THE ARM.** `src/Cobol.Net.Compiler/CodeGen/DataDivision/ValueInitializer.cs`, the CCVS-leniency branch:

```csharp
if (effRaw is { } q && q.StartsWith('"') && pic.Category is PicCategory.Numeric && !pic.IsFloat)
    return item.StoreAsImage
        ? RuntimeApi.StrStore(EmitText.CsLiteral(CobolLiteral.Decode(q)), $"{pic.Length}")
        : CarrierInit(EmitText.UnscaledAtScale(CobolLiteral.Decode(q), pic.Scale), pic);
```

The leniency itself is a deliberate, documented posture: §13.18.63.3 SR2 wants a numeric literal for a numeric
item, the 1985 CCVS corpus writes `PIC 999 VALUE "000"` (NC107A's `DATA-P`), and the compiler accepts the
character form rather than rejecting the corpus. That is not what this note is about.

**THE DEFECT IS THE WIDTH.** The `StoreAsImage` arm pads/truncates to `pic.Length` — the PICTURE's DIGIT COUNT.
For a zoned DISPLAY item digits and bytes are the same number, which is why the arm was correct when it was
written and why nothing caught it since. For a byte-form leaf they are NOT: `PIC 9(4) COMP` is 4 digits and
**2 bytes** (item 205's width ladder), `PIC 9(18) COMP-5` is 18 digits and 8 bytes, `PIC S9(3) COMP-3` is 3
digits and 2 bytes. So the seed writes a window of the wrong LENGTH into a shared-storage image whose member
offsets are computed from `StorageWidth`, and every member after it in the group image is displaced — a silent
wrong answer in the initial value of an entire record, reached without the program doing anything but declaring
a VALUE the compiler chose to accept.

**WHY IT SURVIVED.** The one seeder every other backing site uses is `GroupImageCodec.ImageInitOf` (the F4
consolidation in this same landing deleted two other copies and made it THE seeder); this arm predates that
consolidation and hand-spells its own store. It is the same "one rule in two places" shape as the rest of the
Step D sweep — and, like [[PB186]], it is a lane whose SIGNED/UNSIGNED and DIGIT/BYTE axes were simply never
re-derived when the predicate widened underneath it.

**FIX SHAPE.** Route the arm through `GroupImageCodec.ImageInitOf` / the item's own byte-form encoder so the
width comes from `StorageWidth` by construction rather than from a second literal; then decide, and state, what
the leniency MEANS for a byte-form leaf — the honest reading is that `VALUE "0012"` on a `PIC 9(4) COMP` item is
the numeric value 12 encoded as its two big-endian bytes (the leniency's whole point is to read the characters
AS the numeric literal the SR wanted), not four characters deposited raw. Pin it byte-level: a golden that reads
the initialized group back through a REDEFINES `X` view with `FUNCTION ORD`, plus the following-member offset,
so the displacement half can never come back.

## LANDED 2026-08-31 — the width was real, and (per the correction below) so was a live behavior change

**THE WIDTH DEFECT IS REAL AND IS FIXED.** A `StoreAsImage` numeric leaf's storage is a
`CharImage(item.ImageWidth)` window (`StorageFormPass.Classify`), and both seeders hand-spelled a `pic.Length`
store. Fixed by routing BOTH through the one encoder, `RuntimeApi.NumFormatImage` with the item's own profile,
so the width comes from the pinned byte form BY CONSTRUCTION:

- `ValueInitializer.InitializerFor` — the CCVS-leniency arm this note names.
- `GroupImageCodec.ImageInitOfOne` — **its twin, which this note does not name.** The identical
  `StrStore(chars, pic.Length)` sat there too, and the fix collapses it into the numeric arm directly below it
  (the leniency's meaning — read the characters AS the numeric literal SR2 asked for — is the SAME encode, so
  the two arms become one). Eighth [[feedback_two_arm_dispatch]] instance.

⚠ **THE REACHABILITY CLAIM IS REFUTED — MEASURED, NOT ARGUED.** Both arms were replaced with undefined C#
identifiers (so any compile reaching one fails with CS0103) and the **full Conformance suite passed 5143/5143**.
The marker mechanism was then proved to fail loudly by planting the same identifier in an arm the new
`pb184_group_value_area` golden provably reaches — `error CS0103: The name '__PB184_MARKER_PROOF__' does not
exist in the current context` — so the green is evidence, not silence ([[feedback_green_gates_arent_evidence]]).

The mechanism above is upstream of the **FORMAT 1** input: `DataBinder.ValidateValueCategory` (the PB94 SR2
screen) meets a quoted literal on a numeric subject FIRST and either **errors** (strict — emit never runs) or
**rewrites the raw text to the number** (`--permissive`, `return Edition.Permissive ? content.Trim() : raw`), so
`item.RawValue` no longer starts with `"` by the time either seeder sees it. Measured:
`05 B PIC 9(4) COMP VALUE "0012"` inside a REDEFINES-aliased group seeds bytes `00 0C` — correct — under
`--permissive` at both 2023 and 85, and is rejected at strict.

## ⛔ CORRECTION 2026-08-31 (the review fleet) — "the arms are dead, no program's answer changes" IS WRONG

`ValueInitializer.InitializerFor` reads `effRaw = rawOverride ?? item.RawValue`, and the paragraph above reasons
only about `item.RawValue`. The OTHER input, `rawOverride`, is fed per occurrence by `TableValueInit` from
`DataBinder.BuildTableValueSpecs` — **raw literal text, quotes intact**, on a path that never calls
`ValidateValueCategory` (its only call sites are the format-1 `RawValue` arm and the level-88 arms). So the
FORMAT 2 (table) VALUE reaches the arm unscreened and the arm is **LIVE**.

The 5143/5143 instrumented green was honest about what it measured — the CORPUS contains no such program — and
dishonest only in what was concluded from it. [[feedback_reachability_is_measured_not_deduced]], on the closing
sentence of the argument rather than its premise.

**MEASURED, before and after, on the same source:**

```cobol
01 GL.
   05 LA PIC X(2) VALUE "AA".
   05 LB PIC S9(3) SIGN IS LEADING SEPARATE OCCURS 2 VALUE "012" FROM (1) TO (2).
   05 LC PIC X(2) VALUE "CC".
... DISPLAY GL      *> the whole-group operand promotes LB to StoreAsImage
```

| | `8ca74a3d` | with the fix | §13.18.63.4 GR5/GR7 + §13.18.52.4 GR6a/GR6b |
|---|---|---|---|
| `DISPLAY GL` | `AA012012CC` (10) | `AA+012+012CC` (12) | `AA+012+012CC` |
| `DISPLAY LB(1)` | `012` | `+012` | `+012` |

`PIC S9(3) SIGN IS LEADING SEPARATE` is the visible case precisely because it is a **zoned DISPLAY** leaf whose
`pic.Length` (3 digits) differs from its `ImageWidth` (4 positions — §13.18.52.4 GR6a: the sign "character
position is not a digit position"). The old `StrStore(chars, pic.Length)` seeded 3 characters into a 4-wide
window and displaced every following member of the group image. The population is `AddNumericDisplayLeaves`'
promoted set (`StorageFormPass.cs`), i.e. numeric **USAGE DISPLAY** leaves — a quoted-literal COMP leaf goes down
[[PB208]]'s road instead (its table VALUE is dropped entirely, so it never reaches this arm).

**Pin, added by the correction:** `tests/conformance/2023/pb188_table_value_image_width.{cob,out}` — the LEADING
and TRAILING SEPARATE twins, so a four-wide window cannot be mistaken for a three-wide one plus a stray sign.
Every expected value was derived from GR12/GR13 + GR6a/GR6b and written down before the confirming run; all four
lines differ from `8ca74a3d`. ⚠ The fixture's program is NOT conforming (SR2 is an ALL FORMATS rule and the
format-2 screen does not exist — [[PB208]] half 1); its header says so, and when PB208 lands it moves behind
`--permissive`.

**Model pin (kept).** `ImageWidthIsStorageWidthTests.ByteFormLeaf_ImageWidthIsNotThePictureLength` +
`SignSeparateDisplayLeaf_ImageWidthIsNotThePictureLength` assert that `Pic.Length` is a DIFFERENT number from
`ImageWidth` for exactly the leaves V59/PB164 admitted to the image — including `PIC S999 SIGN SEPARATE`, a
**zoned DISPLAY** item whose 3 digits occupy 4 positions, which shows the axis was never only about COMP.
Proved able to fail: inverting the assertion reds 5/5 rows.

**Sibling sweep.** Every other `pic.Length` width read in `CodeGen/DataDivision` is a category where
`ImageWidth == pic.Length` by construction (alphanumeric / numeric-edited / national in the D-N1 character model;
a USAGE BIT leaf's `StrStoreBoolean(…, pic.Length)` is the unpacked carrier that `BitsPack` then packs to
`ceil(n/8)`). No further instances.
