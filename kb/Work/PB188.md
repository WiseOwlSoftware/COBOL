# PB188

Registered from the PB164 Step D review fleet's out-of-wave disposition (finding R-c). Reachable since the V59 /
PB164 wave-1 predicate widening, which is when a leaf could first be BOTH byte-form and `StoreAsImage`.

**THE ARM.** `src/Cobol.Net.Compiler/CodeGen/DataDivision/ValueInitializer.cs`, the CCVS-leniency branch:

```csharp
if (effRaw is { } q && q.StartsWith('"') && pic.Category is PicCategory.Numeric && !pic.IsFloat)
    return item.StoreAsImage
        ? RuntimeApi.StrStore(EmitText.CsLiteral(CobolLiteral.Decode(q)), $"{pic.Length}")
        : CarrierInit(EmitText.UnscaledAtScale(CobolLiteral.Decode(q), pic.Scale), pic);
```

The leniency itself is a deliberate, documented posture: §13.18.63.3 SR2 wants a numeric literal for a numeric
item, the 1985 CCVS corpus writes `PIC 999 VALUE "000"` (NC107A's `DATA-P`), and the compiler accepts the
character form rather than rejecting the corpus. That is not what this note is about.

**THE DEFECT IS THE WIDTH.** The `StoreAsImage` arm pads/truncates to `pic.Length` — the PICTURE's DIGIT COUNT.
For a zoned DISPLAY item digits and bytes are the same number, which is why the arm was correct when it was
written and why nothing caught it since. For a byte-form leaf they are NOT: `PIC 9(4) COMP` is 4 digits and
**2 bytes** (item 205's width ladder), `PIC 9(18) COMP-5` is 18 digits and 8 bytes, `PIC S9(3) COMP-3` is 3
digits and 2 bytes. So the seed writes a window of the wrong LENGTH into a shared-storage image whose member
offsets are computed from `StorageWidth`, and every member after it in the group image is displaced — a silent
wrong answer in the initial value of an entire record, reached without the program doing anything but declaring
a VALUE the compiler chose to accept.

**WHY IT SURVIVED.** The one seeder every other backing site uses is `GroupImageCodec.ImageInitOf` (the F4
consolidation in this same landing deleted two other copies and made it THE seeder); this arm predates that
consolidation and hand-spells its own store. It is the same "one rule in two places" shape as the rest of the
Step D sweep — and, like [[PB186]], it is a lane whose SIGNED/UNSIGNED and DIGIT/BYTE axes were simply never
re-derived when the predicate widened underneath it.

**FIX SHAPE.** Route the arm through `GroupImageCodec.ImageInitOf` / the item's own byte-form encoder so the
width comes from `StorageWidth` by construction rather than from a second literal; then decide, and state, what
the leniency MEANS for a byte-form leaf — the honest reading is that `VALUE "0012"` on a `PIC 9(4) COMP` item is
the numeric value 12 encoded as its two big-endian bytes (the leniency's whole point is to read the characters
AS the numeric literal the SR wanted), not four characters deposited raw. Pin it byte-level: a golden that reads
the initialized group back through a REDEFINES `X` view with `FUNCTION ORD`, plus the following-member offset,
so the displacement half can never come back.
