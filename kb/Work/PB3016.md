# PB3016 — the rolling wave's landing policy is an argument to remember, not a rule it reads

**Found 2026-10-11 10:36 PDT (Mythos session, wave 1059):** the operator's GO for wave 1059 said "implementers only, NO
lander" (MANDATORY-PRACTICES O11, kb/Work PB2602: while the loop runs, its land unit is the one landing queue). The
Mythos session launched `wf_rolling_wave.js` with the planner's recorded args (`train_size 5`, `min_final_train 3`),
noticed the script would dispatch a `cobol-lander` once five branches were DONE, stopped the run within two minutes
(`wf_a8f62efa-167`, six empty worktrees removed) and relaunched with `train_size 99`, `min_final_train 99`
(`wf_ba3ffb9d-2e5`) — the same stand-in wave 1045 used on 2026-10-08. The operator named the root cause the same hour:
"train_size 99 stands in for a rule the workflow lacks. The rolling wave should read coord.py loop-state and start NO
lander while the loop runs (O11), with no argument to remember."

**Mechanism.** `wf_rolling_wave.js` lines 23–24: `TRAIN = args.train_size || 5`, `MIN_FINAL = args.min_final_train || 3`;
`onResult` lands when `buffer.length >= TRAIN`, and the tail lands a remainder `>= MIN_FINAL`. Nothing in the script
or in `plan_wave.py`'s `wf-args-w<wave>.json` says whether THIS wave may land at all. The loop's wave unit and an
attended session run the same planner and the same script; only the caller's memory of O11 separates them. A forgotten
argument is PB2602's defect again: two landing mechanisms racing for main, each train rebased and re-gated when the
other lands.

**Fix direction (root cause, no workaround).**
1. The planner decides the landing policy and records it: `plan_wave.py` writes `land: true|false` into
   `wf-args-w<wave>.json` — `true` only when the caller IS the loop's wave unit (orchestrate.ps1 marks its units; the
   attended session is never one), `false` otherwise while `coord.py loop-state` is `running`; with the loop stopped an
   attended wave may land (O11's exception, one lander).
2. `wf_rolling_wave.js` honours `args.land === false`: it never calls `land()`, logs each DONE branch as WAITING TO LAND
   for the loop's land unit, and `train_size`/`min_final_train` keep their meaning only when landing is allowed.
3. `dispatch_guard.py` refuses a `wf_rolling_wave.js` launch whose args allow landing while the loop runs and the
   caller is not the loop (the guard already refuses a lander dispatch without `LOOP STATE:`).
4. A self-test for `plan_wave.py` (loop running + attended caller → `land: false`) and a drift test over the script's
   args contract, so the next case is automatic.

Under PB3015's proposal P2 (a merge queue is the landing) the lander role itself changes; this note stands whatever
that decision, because the policy question — may THIS wave land — remains and must be computed, never remembered.

**Decided 2026-10-11 ~11:40 PDT (owner, PB3015 Q3: one pull request per finished branch):** the question is removed
with the mechanism. `wf_rolling_wave.js` loses `land()`, `train_size` and `min_final_train` under PB3023: a wave
produces DONE branches and the loop's `enqueue` unit (or the attended session's `enqueue.py` run) lands them. This note
closes with PB3023; until then the stand-in `train_size 99` is the only way an attended wave honours O11, and every such
launch names this note.

**Code sites:** `.claude/skills/workstream/templates/wf_rolling_wave.js:23-24,160-176`,
`scripts/orchestrator/plan_wave.py` (the `wf-args` writer), `scripts/hooks/dispatch_guard.py`.

## Landed (by removal, with PB3023, wave 1062 group A2, 2026-10-11)

`wf_rolling_wave.js` starts no lander: `land()`, `trains`, `train_size`, `min_final_train`, `previous_train` and the
lead-id blocks are deleted, `plan_wave.py` no longer writes them into the args, and a wave returns its branches
reviewed CLEAN as `ready` for the loop's `enqueue` unit (`enqueue.py land`, kb/Work PB3023). There is no argument left
to remember: an attended wave and a loop wave behave the same, and the one landing path is the script.
