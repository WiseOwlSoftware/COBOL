# PB1542 — OPEN

## The rule

> 6) For each data item to be converted: … b) On output, each native coded character in the record is replaced for the storage medium with its associated coded character as defined in the alphabet being used.

`cite.py --check 13.18.13.4 "On output, each native coded character in the record is replaced for the storage medium with its associated coded character as defined in the alphabet being used"` → OK §13.18.13.4 6) b).
A character with NO associated coded character cannot be replaced, so neither writing its native code unit nor crashing is the
rule; Table 12 names the condition — EC-DATA-CONVERSION, "Conversion failed because of incomplete character correspondence".

## Repro (`/tmp/adj/doc/doc-w1-s6/refute-probe/p187/cs.cob`, `as.cob`, `eb.cob`; re-probed, `--std 2023`)

`ALPHABET S2 IS STANDARD-2` (or `ASCII`), `FD F CODE-SET IS S2`, `01 R PIC X(3)`: WRITE "AB~" then "AéB" → both status 00, the file
holds `41 42 7E 41 E9 42` (X'E9' is not an ISO/IEC 646 IRV character). With `ALPHABET S2 IS EBCDIC` and "A€B": `Unhandled exception.
System.InvalidOperationException: the record contains U+20AC, which the file's CODE-SET coded character set does not represent
(ISO §13.18.13.4 GR6 b)` from `CodeSetConversion.ToMedium` — the run unit dies with a .NET stack trace.

## Code site and fix

`src/Cobol.Net.Runtime/IO/CodeSetConversion.cs#ToMedium`: the identity-correspondence arm (STANDARD-1/-2/ASCII) never checks the
128-character repertoire, and the single-byte-page arm throws. One screen for both arms, surfacing as an unsuccessful WRITE /
REWRITE with an I-O status and EC-DATA-CONVERSION (decide the status with PB690's sibling, the Latin-1 '?' corruption), and the
same on the input side (`GR6 a)`). The §7 row DOC-A.1-187 names this defect and is recorded PARTIAL on it.
