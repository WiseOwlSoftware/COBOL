# PB6357 — trains, and one group per source file, in the tooling

**Sites:** `.claude/skills/workstream/make_dispatch_specs.py` (the implementer spec template), `scripts/orchestrator/plan_wave.py` (grouping), `scripts/orchestrator/enqueue.py` (landing), `scripts/orchestrator/review_lane.py`, `scripts/orchestrator/landing_check.py`

## What happened (2026-11-27, the evidence)

The night of 2026-11-27 dispatched ~16 single-mechanism implementer groups by hand (waves 20262173,
20262175-20262181). Every one ran its own whole-population gate (~12 min, ~29.5 k Conformance + ~43 k Unit
cases), and each takes its own review, merge-queue CI run, DEVLOG entry and ledger republish (each of which
also wakes the operator session). Two were outright duplicates of the loop's own wave 20262174 (PB3259 and
PB6232). Several touched the same source files on separate branches (EvaluateSubjectBinder: PB6232 and
PB6329; ConditionRenderer: PB6256 and PB6265), so the second waited for the first to land and re-gated.

## Decision

1. **Trains.** An implementer does NOT run the whole-population gate. It runs the targeted set (its own
   goldens and the unit tests of the projects it touched, plus the cheap audits) and reports READY.
   A train collects up to ~12 READY, file-disjoint branches: merge them into one train branch, ONE gate,
   ONE review pass (per-branch reviewers may run in parallel on their diffs, but nothing gates per branch),
   ONE `enqueue.py land`, ONE DEVLOG entry, ONE ledger publish. A branch ready after a train's gate started
   waits for the next train. A red train is bisected by halves; the red branch drops to the next train.
2. **One group per source file.** When a wave is planned, every open note whose sites name a common
   source file is ONE group (union of notes over shared site files, capped by size; an oversize union
   splits by member, never by file). A file is never in two in-flight groups; a hand dispatch beside
   the loop is refused if its notes or files are already in flight (`inflight-groups.json`).
3. **Enforced, not remembered.** Drift tests: the implementer spec template carries no whole-population
   gate step; `enqueue.py land` refuses a single-branch landing while other READY branches wait (unless
   the owner exempts it); `make_dispatch_specs.py` refuses a group whose notes or files are in flight.

**Why:** the gate, review, merge queue and publish are per-landing costs that do not scale with the size
of the fix; the owner has asked four times. One group per file also removes the land-then-rebase-then-regate
chain between branches that touch the same file.

**Cost of the change:** one tooling group (the five sites above). Until it lands, hand dispatches follow
the rule by hand: group by file, no implementer gate, one train gate.
