# PB2819 — three quiet arms of the mailbox's process-table reads

Found by the train 1045 lander's review of PB2814's fix (2026-10-08 18:20 PDT). The fix itself landed; these two arms
of it give a misleading answer where they should say they cannot tell.

## 1. A missing operator-session.json makes every session the Mythos lane

`scripts/orchestrator/mailbox.py#lane`: `op = session(cdir, None, None, None).get("config_dir")`, then
`"operator" if op and account.same_dir(...) else "mythos"`. With `operator-session.json` absent (a fresh coordination
directory) or unreadable (`session` returns `{}`), `op` is None and the operator session is told
`mailbox (mythos): 0 open in to-mythos` and asked to arm `watch --inbox mythos`. Expected: a line that says the lane is
unknown and names `mailbox.py session` as the command that records it.

## 2. An unreadable process table is reported as "not in a Claude Code session"

`scripts/orchestrator/mailbox.py#status`: when `coord.process_table()` returns `[]` (its documented answer when the
CIM query fails or times out), `session_root` finds nothing and `status` returns
`watcher state unknown (not running under a Claude Code session)` with `armed = True`, so the stop line never prints.
Expected: "process table unreadable" as its own wording, and the caller (session-probe) treating it as unarmed or as a
warning, not as all-clear.

## 3. The auto watch prunes delivered records against an unreadable process table, and treats any process as a live session

Found by the round-4 review of PB3387 (report `E:\COBOL-coord\scratch\reports\w1126x-PB3387-report.md`, `R4-1 LEAD`,
low); the code landed with PR #274. `scripts/orchestrator/mailbox.py` (`watch`, about line 249): with `root == "auto"`
the watcher reads `table = coord.process_table()` and calls `prune_delivered(cdir, {p["pid"] for p in table})`, so
`live` is every pid in the table. Two quiet readings follow:

- `coord.process_table()` answers `[]` when the table cannot be read (the failure value arm 2 above names). An empty
  `live` set reads as every session having ended, so the prune DELETES the delivered records of sessions that are alive,
  and each of them is delivered its already-seen messages again.
- Liveness is "any process holds the pid", not "a Claude Code process holds it". A dead session's record survives a pid
  reuse, and a later process with that pid inherits the record (the docstring says the pruning exists to prevent
  exactly that).

Same mechanism as arm 2: an unreadable process table read as a definite answer.

## Fix shape

`lane` returns a distinct unknown value when no operator config dir is recorded, and `status` prints it; `status`
tells an empty table apart from a table with no Claude ancestor. Self-test arms for both, beside PB2814's. For arm 3:
an empty table prunes nothing, and liveness checks that the process holding the pid is a Claude Code session (the test
`session_root` already applies), not merely that some process holds the pid; self-test arms for an empty table (no
record deleted) and a reused pid held by a non-Claude process (the record is pruned).
