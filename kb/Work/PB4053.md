# PB4053 — the planner partitions a keyed-table file by row key, not by file

**Sites:** `scripts/orchestrator/plan_wave.py` (`plan_partition`, the file-set partition and the chain links), `scripts/orchestrator/inflight.py` (`Claim.of`, `collision`), `.claude/skills/workstream/check_practices.py` (`group_claim`), `scripts/merge_drivers.py` (`DRIVERS`, `pattern_matches`: the keyed-table driver's file patterns, the one list both read)

**Measured (2026-10-29).** `plan_wave.py --cluster PB2911 --from-budget --dry-run` puts the GAP campaign's Annex A.1
documentation notes in ONE chain, because each declares a site in `docs/CONFORMANCE.md`: PB438, then PB464, then PB1092 and
PB1397, then PB1369. Under `wave.links_per_chain` 1 (PB3638) that is four waves, hours apiece, for notes that each add their
own rows to the §7 register. The owner asked for a way around `docs/CONFORMANCE.md` as a single point of sync.

**What PB3738 fixes and what it leaves.** PB3738 (DESIGN-orchestrator-loop.md §16.8) cuts the prose determinations into
one file each, so notes that write different determinations stop colliding by file. The §7 and §8 register tables stay
tables (the owner's decision of 2026-10-25), merged by the keyed-table driver keyed on each row's first cell, so two
branches that add different rows merge cleanly. The planner still collides them, though, because it partitions by file
path (or a declared member), and every A.1 note adds a row to the same §7 table file.

**Fix.** Partition a keyed-table file by row key. A site that names a row (`docs/conformance/7-a1-register.md#DOC-A.1-116`)
claims that row, two groups adding different rows do not collide, and a site that names the whole file still claims the
whole file. Read the keyed-table patterns from `merge_drivers.DRIVERS`, so the planner and the driver share one list; a
table the driver does not merge stays file-partitioned. The landing side needs nothing new: `enqueue.py` already holds a
second pull request on a driver-merged file until the first merges (EXIT_DRIVER_FILE_QUEUED, because GitHub's merge
queue runs no merge driver), so the parallel branches land one after another, minutes apart rather than a wave apart.
Pair it with a drift test: every keyed-table pattern in `merge_drivers.DRIVERS` is one the planner partitions by row.

**Acceptance.** With PB3738 landed, a dry-run plan of the A.1 notes (PB464, PB1092, PB1397, PB1369, PB2556, PB1253)
places them as parallel groups in one wave, each claiming its own row keys and determination files. Two notes that touch
the SAME row still chain.
