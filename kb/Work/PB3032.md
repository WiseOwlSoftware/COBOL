# PB3032 — a load-sensitive orchestrator self-test

Filed 2026-10-11 by the train 1060 lander from the wave 1059 group A implementer's lead (new defect 1 of
`E:\COBOL-coord\scratch\reports\w1059a-PB2982-report.md`). Not re-probed by the lander.

**Observed.** The implementer's first gate (`TestResults/build-local/20261011T181903Z-42c6f6` in worktree
`wf_ba3ffb9d-2e5-1`) was RED in its SELF-TESTS audit, NO LEG RAN: `test_orchestrate_stop.ps1` reported
`stale lock taken over: got '0', want '1'` (`Run-Orch 'stale'` ran 0 units). Alone it passes 29/29, and the re-gate
passed. This is a wrong RESULT under load, not the hang guard PB2914 repaired (a timeout is `SELF-TESTS HANG`).

**Code site.** `scripts/orchestrator/test_orchestrate_stop.ps1:40-42` (the 'stale' case) and
`scripts/orchestrator/testdata/orchestrate_test_lib.ps1:27` (`Run-Orch`). `Check` drops `$r.out` on failure, so the
first step is to print it, then find which timing the stale-lock takeover depends on (owner 2026-10-10: a red that
passes alone is a defect to root-cause, never a flake to re-gate past).

**Root cause (train 1061 lander, 2026-10-11, measured; `E:\COBOL-coord\scratch\t1061\lander-report.md`).** It is not
timing. The 'stale' case fakes a dead holder with `pid = 999999` (`test_orchestrate_stop.ps1:41`), but Windows ignores
the low two bits of a process id, so `Get-Process -Id 999999` answers for PID 999996. PIDs on this host reach about
1,012,220, so 999996 is often a LIVE process while a gate spawns its self-tests; `Take-Lock`
(`orchestrate.ps1:121`) then correctly sees a live holder and refuses, and the test reports 0 units. Measured twice:
the lander's `Get-Process -Id ($PID+3)` returned its own pwsh, and the land unit's re-probe
(`Get-Process -Id ($PID + 3)` from pwsh 1001528) returned a process. The train 1061 gate's run 2 failed this way;
its run 3 reused the self-test's recorded PASS (PB2914), so it did not re-run.

**Fix shape.** The test needs a PID that cannot be live: pick it at setup (a value whose four aliases
`Get-Process` all refuse) rather than a constant. The production sites share the weakness for a REAL stale lock (a
dead holder's PID reused by, or aliasing to, a live process keeps the lock forever): `orchestrate.ps1:121`
(`Take-Lock`), `stop.ps1:36` (`Get-Running`, so `-Status` reports a dead loop as running) and `detached.py#pid_alive`
(`OpenProcess`; kb/Work PB4008 made it THE one liveness probe). One liveness helper that also compares the process's
start time with the lock's `started_at` closes all of them; rule 4 says sweep and fix them together. PB4008 adds a
second reason for the two PowerShell sites: `Get-Process -Id` reads a process LISTING, which can still name an exited
process whose object another handle keeps; the exit state (`HasExited`, or `detached.pid_alive`) is the question.

wf_14a80b82-683-1, readjudicate-pb5062 and one more; self-test scratch dirs `self-tests-tvz3iyhb`, `-0bnnz0xe`, `-j1fjk_xm`

(`one`, `crash`, `wakes`, `stopnow`, `ledgerowed`, `steerwins`, `acct1`, `tasksdir`, `lanezero`, `stale`, `adoptff`,
