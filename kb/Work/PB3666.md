# PB3666 — alphanumeric text moved to a bit item keeps its characters

✅ **APPROVED BY THE OWNER (2026-10-24).** The owner (2026-10-24 ~18:00 PDT, attended operator session 0a5c7c77), after the operator's explanation of the spec text and GnuCOBOL's behavior for PB3664-PB3666: "Approve all three for fix, and make DISPLAY and the boolean operators agree, and record the choice in docs/CONFORMANCE.md".

**Sites:** `src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs` (`CharacterStore`, its Boolean arm at about line 771)
calling `RuntimeApi.StrStoreBoolean` (`src/Cobol.Net.Compiler/CodeGen/Roslyn/RuntimeApi.cs` at about line 1014), which is
`CobolString.Store` with pad '0' and no character-to-bit conversion.

## What happens (adjudicator D2's probes, fresh judge 300fd78bd)

After `MOVE "AB"` from a `PIC X(2)` item to a `USAGE BIT PIC 1(5)` item, DISPLAY shows `AB000` (or `000AB` with
JUSTIFIED). The same item then gives `11111` under B-NOT, so the boolean operators read it as `00000`. Probes:
`fuzz4\adj\D2\probes\bitgrp\bitgrp.cob` and `bitmv\bitmv.cob` in session 0a5c7c77's scratch.

## The rules (checked by the adjudicator)

- Table 16 (§14.9.25.3) allows an alphanumeric sending operand with a boolean receiver.
- §13.18.60.4 5): "bits shall be used to represent a boolean data item".
- §14.6.8.6: the data goes into the boolean positions "after any necessary conversion".

No rule found so far says how a character that is not '0' or '1' converts to a bit, so the adjudicator gave no
WISEOWL-DEFECT verdict. The content may be undefined (§14.6.13.2 1)). Even so, an item whose image is not boolean, and
whose DISPLAY and boolean operators disagree, is a state no conversion produces.

## The question

Is the result undefined (then document the choice, at least as consistent behavior between DISPLAY and the operators),
or does the standard define the conversion (then implement it)? Search the register and the PB3562 and PB3564 designs
first: those notes fixed the boolean sender and the implicit filler bits, not this receiver arm.

## Decided (2026-10-24)

With the determination below in force, the item's DISPLAY prints characters that are not its boolean value, so the defect is a wrong answer (`wrong_answer: true`). The owner: "make DISPLAY and the boolean operators agree, and record the choice in docs/CONFORMANCE.md". ISO defines no conversion for a character other than '0' or '1' (§14.6.8.6 "after any necessary conversion"; §3.21 a boolean character is the value zero or one), and later references to non-boolean content are undefined with EC-DATA-INCOMPATIBLE (§14.6.13.2 1)). The choice the operator proposed and the owner approved is the rule the boolean operators already apply: the MOVE converts each transferred character, '1' to boolean 1 and every other character to boolean 0, then zero-fills or truncates to the right as §14.6.8.6 requires (JUSTIFIED per §13.18.32). It holds for a USAGE BIT receiver and a USAGE DISPLAY (`PIC 1`) receiver alike, and for every path that stores into a boolean item from an alphanumeric or national sender (MOVE, a group-to-elementary path, VALUE if one admits it, INITIALIZE REPLACING): sweep them. Record the determination in `docs/CONFORMANCE.md` as an implementor choice for content the standard leaves undefined, with the GnuCOBOL survey below. Goldens: "AB", "1A0B1" and "101" into PIC 1(5) under both usages, with JUSTIFIED, and B-NOT / B-AND on the results.

## GnuCOBOL 3.2 (probed 2026-10-24)

No usable precedent. It warns "USAGE BIT is not implemented [-Wpending]" and stores a USAGE BIT PIC 1(5) item in one byte ("01" gives `0`, "AB" gives `A`), and refuses JUSTIFIED on a boolean item. Its USAGE DISPLAY `PIC 1(5)` moves text as a number: "101" lands right-aligned as `00101`, against §14.6.8.6's zero fill to the right (WiseOwl's `10100` is right), and any non-boolean text gives `00000`. IBM Enterprise COBOL has no boolean category; Micro Focus was not checked.

## Sibling path found by PB3598 (2026-10-24, review finisher)

The same store is reached by a variable-length group MOVE between corresponding dynamic-capacity tables whose element categories differ (`MoveBinder.ElementMovesOf` binds the elementary MOVE of the two element places with `BindMoveOf`, so it takes `CharacterStore` like any MOVE). Repro: `E:\COBOL-coord\scratch\w20261032d20\s3b.cob` (T2 PIC X OCCURS DYNAMIC to T1 PIC 1(3) USAGE BIT OCCURS DYNAMIC, `MOVE G2 TO G1`, `DISPLAY T1 (1)` prints `Z00`). The fix must be checked there too, and its golden should carry a group-MOVE leg.

## Landing (2026-10-24, wave 20261105 group A)

Re-probed on a fresh build: `MOVE "AB"` into `PIC 1(5)` showed `AB000` (DISPLAY and USAGE BIT alike, `000AB` JUSTIFIED) while `B-NOT` gave `11111`. The same stale characters came from a national sender, a reference-modified receiver (`BR(1:3)` gave `AB100`), STRING INTO a DISPLAY boolean item, a group sender into a DISPLAY boolean item (which also space-filled the short tail) and the element MOVE of a dynamic-table group MOVE.

Fix at the root: `CobolBool.FromCharacters` converts each character (`1` to boolean one, every other character to zero) and `CobolBool.Store` converts, then fits with boolean zeros (JUSTIFIED per 13.18.32). `RuntimeApi.StrStoreBoolean` emits `CobolBool.Store` for every store into a boolean item (MOVE, COMPUTE, VALUE, group bit extents); `PlaceRenderer.Write` converts a boolean slice; `StringEmitter.WriteImage` a STRING image; `ReceivingStore.Characters` a GR4 group move into a USAGE DISPLAY boolean item (zero fill, no longer space fill); `AcceptSource.DeviceBoolean` reuses the same rule. A group sender into a USAGE BIT item keeps GR4's bytes (no conversion; every bit pattern is a valid boolean).

Determination D-B5 in docs/CONFORMANCE.md section 3. Goldens: `wiseowl/cases/14.9.25-MOVE/pb3666_boolean_receiver_converts_characters` (+ `_below_2002`) and `pb3666_dynamic_table_group_move` (+ `_below_2014`). Unit: `CobolBoolTests.Store_ConvertsEachCharacterThenFits`. Drift pin: `ReceivingStoreDriftTests.EveryStoreIntoABooleanItem_ConvertsItsCharacters`.

For the next implementer, one line per file:
- `src/Cobol.Net.Runtime/Values/Text/CobolBool.cs#FromCharacters` / `#Store` - the entry points that own the conversion and the boolean-zero fit; REUSE them, never spell `CobolString.Store(..., pad: '0')`. The trap: a store into a boolean item that fits by another rule (a slice splice, a STRING image) still needs `FromCharacters`.
- `src/Cobol.Net.Compiler/CodeGen/Roslyn/RuntimeApi.cs#StrStoreBoolean` / `#BoolFromCharacters` - the only emitters of those two calls. The trap: `RuntimeApiGuardTests` counts a bare `Cobol*.` access in a trailing `//` comment of a CodeGen file, so do not name `CobolBool.Store` in one.
- `src/Cobol.Net.Compiler/CodeGen/Verbs/ReceivingStore.cs#Characters` - the new boolean arm (USAGE DISPLAY only) gives a GR4 group move zero fill and conversion; a USAGE BIT receiver's area is bytes and stays `StrStoreAligned`.
- `src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs#CharacterStore` - the Boolean arm delegates to `StrStoreBoolean`; `PlaceRenderer#Write` (RefModPlace arm) and `StringEmitter#WriteImage` convert through `BoolFromCharacters`.
- `src/Cobol.Net.Runtime/RuntimeAbi.pin` - a change to the emitted landing of a boundary formal moves `boundary-hash`; `abi_pin.py repin` is right when the call layout is unchanged.
