# PB836 — LANDED — an implicit redefinition is not a REDEFINES clause

Source: the `PB337` implementer report, "New defects found" item 1.

## Repro — re-run on this tree

`scratchpad/reg4/probe/p02_fd_multi01_strong.cob` (PROGRAM-ID `R4P02`), `--std 2023`:

```cobol
       FD F.
       01 F-REC-BIG TYPE T1.
       01 F-REC-2 PIC X(4).
       ...
       01 T1 IS TYPEDEF STRONG.
          05 A PIC X(4).
```

```
(12,8): error COBOLNET1697: 'F-REC-BIG' is redefined (data-name-2) but is a strongly-typed group item (ISO §13.18.44.3 SR14)
(12,8): error COBOLNET1532: 'F-REC-2' REDEFINES strongly-typed item 'F-REC-BIG': a strongly-typed item shall not be redefined in whole or in part (ISO §13.18.57.3 SR4)
```

The source contains no REDEFINES clause.

## The rules, quoted

```
$ python scripts/spec/cite.py --check 13.18.33.4 "Multiple level 1 entries subordinate to a FD or SD entry represent implicit redefinitions of the same area"
  OK  §13.18.33.4 3)  (General rules)
      3) Multiple level 1 entries subordinate to a FD or SD entry represent implicit redefinitions of the same area.
```

That is the rule the source is using, and it is a GENERAL rule about the record area, not a permission to write
a REDEFINES clause. The two rules the compiler applies are rules about the **clause**:

```
$ python scripts/spec/cite.py --check 13.18.44.3 "strongly-typed"
  OK  §13.18.44.3 12)  (Syntax rules)
      12) The REDEFINES clause shall not be specified for a data item of class object, message-tag, or pointer or a strongly-typed group item.
$ python scripts/spec/cite.py --check 13.18.57.3 "If type-name-1 is described with the STRONG phrase, the subject of the entry shall not be implicitly or explicitly redefined in whole or in part"
  OK  §13.18.57.3 4)  (Syntax rules)
```

⚠ Note for the fixer: §13.18.57.3 SR4 says "implicitly **or** explicitly redefined", so the STRONG rule DOES
reach an implicit redefinition and COBOLNET1532 may well be the right answer for this shape; §13.18.44.3 SR14
(data-name-2 shall not be a strongly-typed group item) is a rule about the clause's OPERAND and is not. The
defect is therefore not "both diagnostics are wrong" but "the binder cannot tell the two constructs apart":
it sets `RedefinesTarget` on an entry that has no REDEFINES clause, after which every rule keyed on that field
fires on the implicit case too. The right shape is a separate `ImplicitRecordAreaSharing` fact (or a flag on the
existing one) so that each rule can say which construct it screens — and `§13.18.44.3` SR14's message must stop
naming source the program did not write ("'F-REC-BIG' is redefined (data-name-2)").

## Code site

`src/Cobol.Net.Compiler/Binding/DataBinder.cs` ~1266 — `sdRecords[i].RedefinesTarget ??= sdRecords[0];` and its
FD twin. The SR4/SR14 screens then read that synthesized field.

## Harm

`rejects_legal_source`: a file description entry with one strongly-typed record description and any second
record description is refused, and §13.18.33.4 GR3 is what makes that source legal. The wrong citation is a
second harm: a reader sent to §13.18.44.3 SR14 finds a rule about a clause the program does not contain.

## Sibling sweep the fixer owes

* Every reader of `DataItem.RedefinesTarget` (grep) — each must state whether it screens the CLAUSE or the AREA.
* The SD twin, and the report-description case §13.18.33.4 GR3's second sentence expressly excludes
  ("Multiple level 1 entries subordinate to a report description entry do not represent implicit redefinitions").
* `docs/COBOLNET_FILES_DESIGN.md`'s record-area determination, which states the sharing rule in prose.

## Landed (wave 47 group P)

Re-probed on the worktree's own build before the fix (the registrar's `p02` probe was not on disk; rebuilt as
`w47p/r836a..g`): strong record FIRST → COBOLNET1697 (§13.18.44.3 SR14, "'F-REC-BIG' is redefined
(data-name-2)") + COBOLNET1532; strong record SECOND → COBOLNET1697 (SR12) ALONE, no SR4 at all; a level-1
`USAGE POINTER` record beside another record → COBOLNET1697 (SR12); a `DYNAMIC LENGTH` record → COBOLNET1698 (SR17).

**The fix is the separate fact the note asked for.** `DataItem.RedefinesKind` (`RedefinitionKind`: `Clause` ·
`ImplicitFileRecord` · `SameRecordArea`, in `RedefinesModel.cs`) is written only together with `RedefinesTarget`
through `DataItem.SetRedefinition` — `RedefinesTarget`'s setter is now private, so the two facts cannot disagree.
Every reader was classified (the sibling sweep the note owed): the offset / bit-offset / anchor / `RecordLayout`
readers are AREA readers and read the target for both kinds; the per-entry §13.18.44.3 SR5/SR12/SR14/SR17 screens,
the 1525 dynamic-subject arm and the SR5/SR12-14/SR17 tier verdicts are CLAUSE readers and read `Clause` only; the
`ResolveRedefines` screens (SR7/SR8/SR16) were already clause-only by construction (they iterate
`RedefinesTargetName`). The SD twin and the record-area SAME arm take the same path; a report description never
calls `SetRedefinition` (§13.18.33.4 GR3's second sentence).

**What DOES reach the implicit case** is §13.18.57.3 SR4 ("implicitly or explicitly redefined"), exactly as the
note's ⚠ said: `CheckStrongTypeDeclarations` gains an implicit arm, SYMMETRIC (both sides of each pair — the
strong-second order previously got no SR4 at all), one COBOLNET1532 per strong item, citing §13.18.33.4 GR3 or
§12.4.6.4.4 GR2. A record shape the shared backing cannot carry (pointer, dynamic-length, variable-length group,
dynamic-capacity table) is legal source the storage model does not yet share: staged loud as COBOLNET0899
`implicit-record-area-shape` (`DiagnosticCatalog.ImplicitRecordAreaShape`) — debt reported as debt, not a
borrowed REDEFINES rule; the residue is a lead for the registrar. ComputeTier's reject text now names "the
shared record area" rather than a REDEFINES the source does not contain.
