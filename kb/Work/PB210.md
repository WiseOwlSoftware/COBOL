# PB210

Found by the PB169–PB172 burn-down cluster's exhaustive §8.8.1.1 funnel-entry sweep (2026-08-31), which
classified every entry into the numeric funnel as screened / unscreened / wrongly-screened. This is an entry
that **never enters the funnel and has no screen of its own either**.

`ControlFlowBinder.BindGoToDepending` binds identifier-1 with `host.Expr.FieldOperand(sel)` — the raw
operand mapping, which deliberately applies no class rule because its r7-legal consumers share it — and then
applies nothing. ISO §14.9.17.3 syntax rule 1 (`cite.py --check 14.9.17.3 "Identifier-1 shall reference a
numeric elementary data item that is an integer"` → OK) closes the operand to a numeric elementary INTEGER
item, which is narrower even than §8.8.1.1: a group, an alphanumeric item, a scaled numeric item and an index
data item are all excluded.

WHAT WOULD CLOSE IT: the position's own screen at `BindGoToDepending`, asked through the ONE §8.5.2.1 Table-2
classifier (`IntrinsicArgumentRules.IsArithmeticOperandClass`) plus the integer test
(`IntrinsicResultType.IsIntegerOperand`) — the `CountOperand` pattern PERFORM … TIMES already follows for its
own §14.9.28.3 SR2 — a negative fixture per excluded shape, and a positive golden holding the legal integer
form. It belongs in the funnel entry-point table (`DESIGN-binder-bound-tree.md` §3.6) as a row governed by its
own SR, not by §8.8.1.1.

NOT FIXED BY THE CLUSTER B LANDING, deliberately: it is a distinct statement rule with its own clause, and
CLAUDE.md rule 8 wants it registered before it is narrated, not folded into another item's diff.

## 2026-09-04 — lane-3 adjudication batch b2 re-measured this row; it stays PB210's

**Row claimed: `SR-14.9.17.3-1`.** The b2 GO TO adjudication re-derived the rule and probed it; everything below
was then **re-measured on this worktree's HEAD `cobol.exe` (base 89044aa0)**, not on the pinned adjudication
compiler. Nothing has been fixed since; the row is still open and still PB210's — no second note was opened.

`--check 14.9.17.3 "Identifier-1 shall reference a numeric elementary data item that is an integer"` →
`OK §14.9.17.3 1)`.

**SR1 has TWO halves and PB210's title names only the first.** "a numeric elementary data item" AND "that is an
integer" are one screen, not two bugs, but the second half has the sharper consequence:

- **Class half** (`probe/go-to/p3-alpha-selector.cob`, `01 SEL-X PIC X(2) VALUE "AB".` then
  `GO TO PARA-A PARA-B DEPENDING ON SEL-X.`) — `cobol.exe p3-alpha-selector.cob --std 2023 --run` compiles clean
  under the default STRICT dialect and prints `START` then `FELL-THROUGH`. Same at `--std 85`.
- **Integer half** (`probe/go-to/p12-noninteger.cob`, `01 W-F PIC 9V9 VALUE 2.7.` then the same GO TO) — compiles
  clean and prints `START` then `B-TAKEN`. `ControlFlowEmitter.cs:39`'s `(int)(…)` truncation turned 2.7 into 2
  and **selected procedure-name-2**: an illegal program is not merely accepted, it is handed a specific transfer
  the standard never defines for it.

Two things for whoever lands PB210:

1. The screen must cover BOTH halves. A class-only screen written to this note's title would leave `PIC 9V9`
   accepted, and that is the half that produces a definite wrong branch.
2. **The code comment at `ControlFlowEmitter.cs:38` attributes the selector's integer requirement to §14.9.20.3,
   which is the INITIALIZE statement's syntax rules — not GO TO's.** The rule is §14.9.17.3 rule 1. Re-point the
   comment in the same change (CLAUDE.md rule 1: a clause number inherited and never re-derived).

⚠ Fixture placement warning: `GO TO … DEPENDING` inside an inline PERFORM does not transfer at all on this tree
(`ControlFlowEmitter.cs:47`, the same defect as [[PB413]]), so a positive fixture for the legal integer form
must NOT be written inside an inline PERFORM or it will fail for an unrelated reason.

## Landed 2026-09-22 (wave 52, one operand-class screen for PB210 + PB211 + PB212)

Re-probed on the implementer's own build before the fix (every note's shape reproduced). The three notes are ONE absence -- a class-closed identifier position bound with a bare `FieldOperand` / `Refs.Resolve` and nothing asked -- so the fix is ONE mechanism: `src/Cobol.Net.Compiler/Binding/Procedure/OperandClassScreen.cs`. A class-closed position is a ROW of `OperandPositions` (statement, operand, rule, the rule's words, the admitted `OperandClasses`, the diagnostic) and its binder makes one call; `OperandClassScreen.ClassesOf` reads the ONE Table-2 classifier (`IntrinsicArgumentRules.ClassOfItem`) and the ONE integer primitive (`PicInfo.IsIntegerDescription`). `OperandClassScreenDriftTests` runs every row against seven class shapes end to end, with the shapes' classes written from the standard independently of the classifier. The sibling sweep added the PERFORM VARYING induction variable (§14.9.28.3 SR2 / SR5 a)) as a fourth row. Goldens: `85/pb212_operand_class_screens` (all legal shapes, every edition) and the negatives named below. DESIGN-binder-bound-tree.md §3.6/§3.8 updated.

**This note:** GO TO … DEPENDING ON identifier-1 is `OperandPositions.GoToDependingSelector`; BOTH halves of SR1 (numeric elementary AND integer) refuse with COBOLNET2324 in both lanes -- alphanumeric, numeric-edited, group, index, floating-point and scaled selectors (the `PIC 9V9` = 2.7 selector that silently took procedure-name-2 is `negative/pb210-go-to-depending-noninteger`). The `ControlFlowEmitter` comment citing §14.9.20 had already been re-pointed to §14.9.17.3 SR1 by an earlier landing.
