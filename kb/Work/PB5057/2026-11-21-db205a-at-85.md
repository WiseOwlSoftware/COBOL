## 2026-11-21 — the second question answered: DB205A at `--std 85 --nist` is an operator test, not a 1985 hang

Probed on this tree (26e6da8f73, Debug CLI): `cobol --std 85 --nist DB205A DB205A.cob` compiles (exit 0, COBOL0903
obsolete-element warnings only). Two runs, each in a new directory outside the tree, stdin closed, `WISEOWL_COBOL_MCS` = the
run directory (what `CutRunner.RunExit` sets):

1. **Without `tests/nist/data/mcs.json` in the run directory** (the MCS knows no queue): the run is killed at its 120 s
   budget, busy on one core (`dotnet-stack`: `_PRG_DB205A.__Dispatch`, 2.95 s CPU in 3 s). The loop is the program's own
   drain of its input queue, RECEIVE-TEST-1: `RECEIVE CM-INQUE MESSAGE INTO WORK-AREA NO DATA GO TO RECEIVE-TEST-1-CONT.`
   then `GO TO RECEIVE-TEST-1-INIT.` The queue `CCVSQ1` (X-card XXXXX030) is unknown to the MCS, and §1985:XIV.3.5.4 GR5c
   ("the appropriate status key code is stored and control is then transferred as if data had been made available",
   `cite.py --check` OK) sends control past the NO DATA phrase on every RECEIVE, so the drain never ends. That is the
   standard's behaviour, and it is the 5-hour busy loop this note records: the run that leaked was a DB205A run without
   the MCS definitions.
2. **With `mcs.json`** (as `CommunicationCcvsTests.Run` stages it): the drain receives the queue's two messages
   (an instrumented copy DISPLAYs the CD after each RECEIVE: text lengths 0030 and 0024, status 00), takes NO DATA and

   --check` OK).

CM104M and CM202M, which `CommunicationCcvsTests` compiles only. Neither run is a defect of the 1985 debug module or the
communication facility: the compile is clean and both stops are the 1985 rules. `tests/nist/corpus.tsv` already keeps it
