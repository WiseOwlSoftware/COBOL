# PB3889 — date-to-yyyymmdd-zero-year-check--argument-1-range: DATE-TO-YYYYMMDD and DAY-TO-YYYYDDD do not flag argument-1 of 0, -1..-9999, or >= 1000000 (>= 100000)

Campaign PB3838, tier 4: filed 2026-10-27 from the tier 2 harvest and the tier 3 adjudication (slice S3) and refutation (UPHELD). Upstream status `unreported`: the tracker has not been searched (tier 6, owner-gated). Evidence, outside git on one machine: `E:\COBOL-coord\scratch\op\pb3838\records\date-to-yyyymmdd-zero-year-check--argument-1-range.md` and `.cob`, the refuter's reruns under `E:\COBOL-coord\scratch\op\pb3838\refute\date-to-yyyymmdd-zero-year-check--argument-1-range\`.

## Summary

ISO requires argument-1 of DATE-TO-YYYYMMDD to be a positive integer less than 1000000 (DAY-TO-YYYYDDD: less than
100000); any other value sets the EC-ARGUMENT-FUNCTION exception condition. GnuCOBOL 3.2 splits argument-1 into a
two-digit year and the rest first, and tests the year it derived (`year < 0 || year > 999999`). So 0 passes (year 0),
-1 through -9999 pass (the C division truncates toward zero, year 0), and 1000000 passes (year 100); the upper bound can
never be exceeded. Only values of -10000 or less are detected. In the program below GnuCOBOL detects -10000
(EXCEPTION-STATUS = EC-ARGUMENT-FUNCTION, result 0) but not 0 (EXCEPTION-STATUS spaces, result 20000000), although
both violate the same rule.

The returned value itself is not the defect: when checking for EC-ARGUMENT-FUNCTION is not enabled, ISO lets the
implementor define the result of the function reference (15.3), so 20000000 alone is latitude. The defect is the
missed detection: with checking enabled, ISO raises EC-ARGUMENT-FUNCTION for 0. (In 3.2 the enabled check has no
run-time effect at all; that is the separate record `date-to-yyyymmdd-zero-year-check--checking-not-honored`.)

## Minimal test case

Fixed reference format (cobc's default; the directive starts in column 8), 9 lines,
`records/date-to-yyyymmdd-zero-year-check--argument-1-range.cob`:

```cobol
       >>TURN EC-ARGUMENT-FUNCTION CHECKING ON
       IDENTIFICATION DIVISION.
       PROGRAM-ID. DTARG1.
       PROCEDURE DIVISION.
           DISPLAY FUNCTION DATE-TO-YYYYMMDD (0 10 2026)
           DISPLAY "[" FUNCTION EXCEPTION-STATUS "]"
           DISPLAY FUNCTION DATE-TO-YYYYMMDD (-10000 10 2026)
           DISPLAY "[" FUNCTION EXCEPTION-STATUS "]"
           STOP RUN.
```

## Expected result (per ISO)

ISO/IEC 1989:2023, all checked:

- 15.23.3 rule 1: "Argument-1 shall be a positive integer less than 1000000." 15.25.3 rule 1 (DAY-TO-YYYYDDD):
  "Argument-1 shall be a positive integer less than 100000."
- 15.3 (the paragraph after the list of argument types): "If the evaluation of an argument results in an incorrect
  value for that argument ... the EC-ARGUMENT-FUNCTION exception condition is set to exist." and "If the
  EC-ARGUMENT-FUNCTION exception condition is set to exist and checking for EC-ARGUMENT-FUNCTION is not enabled, the
  implementor defines the result of the function reference."
- 7.3.25.4 rule 6: with `>>TURN ... CHECKING ON`, "checking for the exception condition associated with exception-name-1
  is enabled for the procedure division statements ... that follow".
- 14.6.13.1.6, Table 13: `EC-ARGUMENT-FUNCTION | Fatal | Function argument error`; 14.6.13.1.3 rule 7: "If checking
  for the exception condition is enabled, execution of the run unit is terminated abnormally".

Every argument-1 above (0, -1, -10000, 1000000; 0 and 100000 for DAY-TO-YYYYDDD) violates rule 1, so each call sets
EC-ARGUMENT-FUNCTION to exist. With checking enabled, the first call of `dtarg1` raises it and ends the run unit
abnormally; no line is displayed. The ISO-required detection is the same for 0 and for -10000; GnuCOBOL's differs.

Edition: the 2009 committee draft that led to ISO/IEC 1989:2014 (CD 1.2, its 15.20 and the DAY-TO-YYYYDDD clause)
carries both argument-1 rules in the same words, and Annex E of 2023 lists no change. The requirement holds for
`-std=cobol2014`.

Edition as recorded by the adjudicator: 2014. `upstream_edition: 2014` is the edition `-std=cobol2014` claims; the cited clauses were validated with `scripts/spec/cite.py --check` by the adjudicator and again by the refuter.

## Class

Wrong output (an argument the standard declares incorrect is not detected; EC-ARGUMENT-FUNCTION is not set). Without
checking enabled the returned value is implementor-defined (15.3), so the record rests on the detection, not on the
value 20000000.

## Our compiler (WiseOwl)

`cobol dtarg1.cob --std 2014 --run` (WiseOwl, built from main 6ed90bd1c): `abnormal run-unit termination:
EC-ARGUMENT-FUNCTION (fatal): DATE-TO-YYYYMMDD argument-1 0 is not a positive integer less than 1000000 (§15.23.3 r1)`,
exit 1; nothing else displayed. The four variants each end the same way naming their argument. It matches the ISO
expectation.

## Fix site (GnuCOBOL 3.2 source, read observationally)

- `libcob/intrinsic.c`, function `cob_intr_date_to_yyyymmdd`: argument-1 is divided by 10000 into `year` (remainder
  `mmdd`) before the test `year < 0 || year > 999999`; the comment above says "The unusual year checks are as specified
  in the standard". The test belongs on the undivided argument-1 value: less than 1 or not less than 1000000.
- `libcob/intrinsic.c`, function `cob_intr_day_to_yyyyddd`: the same pattern, dividing by 1000 before the same test;
  the bound for this function is 100000.
- The sibling `cob_intr_year_to_yyyy` in the same file was not examined for this record.

## Draft issue

**Title:** DATE-TO-YYYYMMDD and DAY-TO-YYYYDDD do not flag argument-1 of 0, -1..-9999, or >= 1000000 (>= 100000)

**Body:**

Environment: GnuCOBOL 3.2.0 (Ubuntu gnucobol3 3.2-4build1), `cobc -std=cobol2014 -x`.

Program (fixed format):

```cobol
       >>TURN EC-ARGUMENT-FUNCTION CHECKING ON
       IDENTIFICATION DIVISION.
       PROGRAM-ID. DTARG1.
       PROCEDURE DIVISION.
           DISPLAY FUNCTION DATE-TO-YYYYMMDD (0 10 2026)
           DISPLAY "[" FUNCTION EXCEPTION-STATUS "]"
           DISPLAY FUNCTION DATE-TO-YYYYMMDD (-10000 10 2026)
           DISPLAY "[" FUNCTION EXCEPTION-STATUS "]"
           STOP RUN.
```

Steps: `cobc -std=cobol2014 -x dtarg1.cob && ./dtarg1`

Observed: argument-1 = 0 returns 20000000 and sets no exception (EXCEPTION-STATUS is spaces); argument-1 = -10000
returns 0 and sets EC-ARGUMENT-FUNCTION. Also undetected: DATE-TO-YYYYMMDD (-1 10 2026) -> 19999999,
(1000000 10 2026) -> 20000000; DAY-TO-YYYYDDD (0 10 2026) and (100000 10 2026) -> 2000000.

Expected: EC-ARGUMENT-FUNCTION for every one of these. ISO/IEC 1989:2014 (and 2023): DATE-TO-YYYYMMDD argument rule 1,
"Argument-1 shall be a positive integer less than 1000000"; DAY-TO-YYYYDDD argument rule 1, "... less than 100000";
15.3: an incorrect argument value sets EC-ARGUMENT-FUNCTION to exist. (With checking enabled, as here, the condition is
fatal and the run unit ends at the first call; that part is a separate report.)

Cause: `cob_intr_date_to_yyyymmdd` and `cob_intr_day_to_yyyyddd` (libcob/intrinsic.c) test the year derived from
argument-1 after dividing it by 10000 (1000), so the range test can never see the values above. Testing argument-1
itself (1 <= argument-1 < 1000000, resp. < 100000) fixes both.
