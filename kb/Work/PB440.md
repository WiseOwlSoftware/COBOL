# PB440 — one range the standard explicitly allows to be EMPTY, and both arms of the compiler get it wrong

## 1. THE MECHANISM

A section with **zero paragraphs** is legal COBOL, and it makes GR4's specified set of statements empty. The
compiler has two arms for that case and neither implements the rule.

**Arm A — the whole statement, control phrase included, is silently DELETED.**
`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:313-314`:

    else if (start > end)
        return new BoundNop();   // PERFORM of an EMPTY section runs nothing (no first statement, ISO §14.9.28)

`BindPerformControl` is never called on that path, so the times/until/varying phrase never reaches the bound
tree: no initialization, no condition test, no augment, no loop. The comment's premise is right (an empty
procedure-name-1 has no first statement) and its conclusion is wrong — GR13 a) sets the induction variables
BEFORE any transfer, and GR5's exception clause names GR9/GR10/GR11 as the only reasons a transfer does not
happen, not "the set is empty". The pc range comes out empty because `SectionInfo.EndPc` is initialized to
`startPc - 1` (`src/Cobol.Net.Compiler/Binding/Procedure/SectionInfo.cs`) and
`ProcedureTableBuilder.AddAnonymousParagraph:66-68` returns early on zero sentences, so a zero-paragraph section
gets `StartPc = _paras.Count`, `EndPc = StartPc - 1`.

**Arm B — with THRU written, the `BoundNop` arm is SKIPPED and the dispatcher runs off the end of the range.**
The THRU branch at `ControlFlowBinder.cs:306-312` sets `end = thru.End` unconditionally and returns before
reaching `:313`. So `EmitOutOfLinePerform:211-228` emits `__Dispatch(start, start-1)`, and in
`src/Cobol.Net.Compiler/CodeGen/DispatchEmitter.cs:158-176` the loop is

    int __pc = __startPc;
    while ((uint)__pc < (uint)__N)
    {
        bool __atExit = __pc == __exitPc;   // captured before the body overwrites __pc
        switch (__pc) { … }
        if (__atExit && __pc == __exitPc + 1) return __pc;   // a named THRU exit paragraph fell off its end
    }

With `__exitPc == __startPc - 1`, `__atExit` is **never** true, so the return test can never fire and the loop
runs from `start` to the end of the pc space — executing the statements of every FOLLOWING section, once per
iteration of whatever control phrase was written.

⛔ **Both arms are reachable from legal source and neither case is "undefined".** GR4 DEFINES the specified set,
and an empty set is a set. The ten rows below are ONE root cause; they are listed separately because each row's
own words are directly contradicted by a measured result, and closing GR4's range resolution closes all ten.

## 4. THE CODE SITE AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ControlFlowBinder.cs:305-316` — the range resolution;
  `:311` the THRU branch (arm B's entry), `:313-314` the `BoundNop` (arm A)
* `src/Cobol.Net.Compiler/Binding/Procedure/SectionInfo.cs` — `EndPc` defaults to `startPc - 1`
* `src/Cobol.Net.Compiler/Binding/Procedure/ProcedureTableBuilder.cs:66-68` (`AddAnonymousParagraph` returns
  early on zero sentences), `:150-157` (the section's `StartPc`/`EndPc`)
* `src/Cobol.Net.Compiler/CodeGen/DispatchEmitter.cs:158-176` — the `__atExit && __pc == __exitPc + 1` return
  test that cannot fire on an inverted-by-one range
* `src/Cobol.Net.Compiler/CodeGen/Verbs/ControlFlowEmitter.cs:211-228` (`EmitOutOfLinePerform`), `:249-282`
  (`EmitPerformLoop` — ONE loop scaffold shared by both shapes, which is what makes GR4's "function identically"
  half structural everywhere EXCEPT here)

⛔ **The repair is NOT `if (start > end) end = start - 1;` nor a guard bolted onto the THRU branch.** The root
cause is that **an empty range is represented as an INVERTED pc pair, and every consumer has to notice**. `(3, 2)`
is indistinguishable from a malformed range, the dispatcher's return test is arithmetic on `exitPc + 1`, and the
binder's only defence is a comparison it applies in one of its two branches. Follow rule 5:

1. **Make emptiness a FIRST-CLASS property of the resolved range, not an arithmetic accident.** `ResolveProcedure`
   (and `SectionInfo`) shall say "this procedure has no statements" rather than encoding it as `End < Start`.
   Then `BindPerform` composes a range that is EMPTY-but-well-formed, and the two branches at `:311` and `:313`
   collapse into one.
2. **`BoundOutOfLinePerform` shall carry the control phrase in EVERY case.** The loop scaffold, the induction
   bookkeeping, the condition tests and the return are the PERFORM's semantics; the range is only what the body
   does. Today the empty case throws the semantics away with the body. `EmitPerformLoop` already emits an
   out-of-line body as a plain call, so an empty body is `;` — the scaffold around it is unchanged, and GR4's
   "function identically" becomes structurally true instead of true-except-here.
3. **The dispatcher must not be asked to run an empty range at all** — with (1) and (2), the emitted body for an
   empty range is nothing, so `__Dispatch` is never called with an inverted pair and arm B disappears rather
   than being guarded. If a guard is nevertheless wanted, put it as an ASSERT in `DispatchEmitter` (`exitPc >=
   startPc`) so a future inverted pair fails loudly instead of running the rest of the program.

⚠ **A fix that closes arm A and not arm B, or vice versa, is the recurring two-arm defect.** They are the same
root cause reached through two branches of one `if`/`else if`, and each has its own measured refutation above.

## 5. THE SIBLING SWEEP

* **Every other consumer of a resolved procedure RANGE.** `GO TO section`, `ALTER`, SORT/MERGE `INPUT
  PROCEDURE`/`OUTPUT PROCEDURE`, `USE FOR DEBUGGING` subjects, `RESUME AT procedure-name` and the F3 handler
  pc-ranges all take `(Start, End)` pairs from the same table. Each must be asked what it does with an empty
  section — `GO TO` an empty section and a SORT `INPUT PROCEDURE` naming one are the two most likely to have the
  identical defect.
* **Every other `start > end` / `End < Start` test in the binder and emitter.** Grep for the comparison; each
  occurrence is a place where the inverted-pair encoding is being decoded by hand.
* **The empty PARAGRAPH path**, which is correct today (it has its own pc), must STAY correct after the
  representation changes — it is the regression risk of step (1).
* **`PERFORM p THRU p` where p is a non-empty section**, and the INVERTED range (procedure-name-2 physically
  preceding procedure-name-1, NC102A PFM-TEST-F1-10) both ride the same `__atExit` return test; re-measure both
  after touching `DispatchEmitter`.
* ⛔ **The section/THRU/inverted-range tests in `SectionDifferentialTests` are all `AssertSameAsLegacy`** — they
  pin the legacy oracle and cannot close any of these ten rows, nor detect a regression against the spec. The
  fix must ship SPEC-DERIVED goldens, at minimum: the empty-section out-of-line VARYING beside its inline twin
  (the pair above), and the empty THRU range.
* **`ControlFlowDifferentialTests.Perform_Thru_Times_RunsRangeNTimes`** is spec-computed and is the one test in
  the area that closes its row on its own — but it pins the count on a two-paragraph range and cannot see this.

All ten rest on the two measured arms above; each line says what its own row's words assert and where the
measurement contradicts them.

* `GR-14.9.28.4-4` — DIVERGES. Both halves wrong on an empty section: "function identically" is measurably false

* `GR-14.9.28.4-5` — PARTIAL. The mainline transfer and BOTH return-mechanism arms are right on a non-empty

* `GR-14.9.28.4-L2.4` — PARTIAL (13 c) 4). The leftward walk, increment-then-reset and the termination clause

## 7. LANDED — 2026-09-09 (base 39479e19)

Both arms are closed at the root, and the fix is the restructuring the note asked for rather than a guard.

**The root cause, restated after implementation.** The note said an empty range is "an INVERTED pc pair and
every consumer has to notice". Implementation showed the sharper form: **emptiness is not derivable from the
pair AT ALL.** A legal INVERTED THRU range (GR6, NIST NC102A PFM-TEST-F1-10) also has `End < Start`, and when
procedure-name-2 is ADJACENTLY before procedure-name-1 it produces the IDENTICAL pair `(s, s-1)` as a
zero-paragraph section. One must execute nothing; the other must execute from `s` until control reaches
`s-1`. So `if (start > end)` was not merely applied in one of two branches — it was an ambiguous test
wherever it appeared. The bit is now CARRIED.

* `src/Cobol.Net.Compiler/Binding/Model/PcRange.cs` (new) — `Start` / `End` / `IsEmpty`, with `At`, `Of`,
  `EmptyAt`, the GR4/GR5b composition `Through`, and `IsParagraph` (ALTER's "procedure-name-1 shall be a
  paragraph"). The canonical empty pair stays `(s, s-1)` because that is exactly what makes `Through` come out
  right with no special case; `Through` marks the composition empty only when BOTH endpoints are empty and
  nothing lies between them.
* `SectionInfo` carries the `PcRange` and closes it through `CloseAt`, which is the ONE place a zero-paragraph
  section is decided. `ResolveProcedure` returns `PcRange?`.
* `BindPerform` has ONE path: resolve, compose THRU, `new BoundOutOfLinePerform(range, BindPerformControl(p),
  line)`. The `BoundNop` arm is gone; the control phrase is bound in every case.
* `EmitOutOfLinePerform` emits the loop scaffold for EVERY range and supplies an EMPTY body action when the
  range is empty, so GR4's "function identically" is structural: the emitted C# is the inline emission minus
  the body.
* `DispatchState.DispatchCall` is the ONE place a range becomes `__Dispatch(a, b)` and THROWS on an empty one,
  so arm B disappears rather than being guarded.

**The sibling sweep found and closed a second wrong-answer defect.** `SortEmitter`'s three `Start <= End`
guards were the same ambiguous decode: a legal INVERTED `INPUT PROCEDURE IS p THRU q` was silently DROPPED,
releasing no records at all (measured: `SORT ... INPUT PROCEDURE IS IN-B THRU IN-A` printed `DONE` and nothing
else; it now returns `OUT=A OUT=B OUT=C`). `SetAlterBinder`'s two `Start == End` tests became `IsParagraph`.
The remaining consumers were measured and are correct unchanged: `GO TO` an empty section transfers to `Start`,
which is where execution continues past it (a plain transfer, correct for free, incl. a trailing empty
section); `ALTER` excludes it; an empty SORT INPUT PROCEDURE releases nothing; a DECLARATIVE section is never
empty (`DeclCollectSection` materializes a zero-sentence paragraph). The empty PARAGRAPH path — the
regression risk of step (1) — still runs nothing and returns without falling into the following paragraph.

**Measured, at the same `--std 2023` probes the note recorded.** `empvar_before` A=0004 B=0001 (was A=0077
B=0088, byte-identical to the inline twin now); `empthru` A=0004 B=0001 with no TAIL lines (was nine);
`empthru_basic` BASIC N=0000 / TIMES N=0000 (was 1 / 3).

**Goldens (spec-derived, expected values computed from the rules, not from a run).**
`tests/conformance/{85,2002,2014,2023}/pb440_perform_empty_range` (the out-of-line/inline twin pair, the empty
THRU basic and TIMES forms, the plain form, GR10's zero-trip), `2023/pb440_perform_range_composition` (GR4/GR5/
GR6 composition incl. the inverted range and the empty PARAGRAPH), `2023/pb440_perform_test_after_empty`
(GR13 c) 1-4, three shapes in one program), `2023/pb440_sort_procedure_range` (the inverted and empty SORT
INPUT PROCEDURE). Drift: `ProcedureRangeEmptinessDriftTests` — the `(s, s-1)` collision, the eight `Through`
compositions, `DispatchCall`'s refusal, and two SOURCE scans (no second dispatch-call construction site; no
`.Start`-vs-`.End` comparison anywhere in the compiler), both with positive controls and both proved to fail.

Design: control-flow deep-dive **D5a** + the zero-paragraph edge case; `COBOLNET_DESIGN.md` §5.2 row and §5.4.
All ten rows re-verdicted CONFORMS (batch `pb440-perform-empty-procedure-range`, GAP 2733 → 2723).

⛔ **What did NOT hold from the note.** §4's step 1 said `ResolveProcedure` should "say 'this procedure has
no statements' rather than encoding it as `End < Start`". The encoding is KEPT — it is what makes the THRU
composition correct — and the fix is that the ENCODING NO LONGER CARRIES THE MEANING: `IsEmpty` does. Step 3's
optional assert was made mandatory and moved to EMIT time (an assert inside the generated `__Dispatch` would
cost a branch in every user program and fail at run time).
