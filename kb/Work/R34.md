# R34 — COPY REPLACING does not reach text included by a NESTED COPY: the §7.2 recursive replacement never materializes the replaced name

> Found by the R21+R22+R30 battery's differential leg (2026-08-08): flips `syn_copy:630` ("COPY:
> recursive replacement") and `listings:996` (same construct in the listings family), AGREE_ACCEPT →
> WE_REJECT_THEY_ACCEPT carrying COBOLNET1639 "'COPY-VAR' is not defined".

THE CASE: `copy-1.inc` contains only `COPY "copy-2.inc".`; `copy-2.inc` declares `01 TEST-VAR PIC X(2)`.
The program writes `COPY "copy-1.inc" REPLACING ==TEST-VAR== BY ==COPY-VAR==.` and references COPY-VAR.

⛔ **THIS NOTE'S ORIGINAL PREMISE WAS WRONG, and the citation the note itself demanded flipped it**
([[validate_the_premise_not_only_the_rule]]). It asserted "ISO §7.2.3: the REPLACING phrase operates on
the library text … including text a nested COPY brings in — so TEST-VAR must arrive as COPY-VAR". The
actual rule is the OPPOSITE: **§7.2.3.4 GR10 — "If the REPLACING phrase is specified, the library text
shall not contain a COPY statement"** — and GR12 permits nesting (at least 5 levels) only WITHOUT
replacing. GnuCOBOL's "COPY: recursive replacement" testcase exercises a GnuCOBOL EXTENSION over
ISO-illegal source. The premise had been read off the oracle's behavior, not the standard.

THE REAL DEFECT (measured): the preprocessor recursed into the nested copybook OUTSIDE the replacement
scope — the illegal combination expanded to arbitrary partial text (TEST-VAR arrived unreplaced) and the
failure surfaced as a misleading downstream COBOLNET1639 on COPY-VAR. The verdict (reject) was right by
accident; the REASON was wrong, and `rejects_legal_source` is corrected to false.

## LANDED 2026-08-08

**COBOLNET1640** (`copy-replacing-nested-copy`): `CopyProcessor.ResolveOneCopy` detects a COPY statement
in the normalized library text when replacements are present — using the SAME `FindCopyKeyword` the
expander splices by, so the report and the recursion can never disagree — and reports at the outer
COPY's line, citing GR10 verbatim. Expansion continues after the report (the diagnostic is the verdict;
the splice keeps the downstream parse coherent). Measured before/after: the GR10 shape draws 1640 at the
COPY line (was: 1639 on a downstream name); plain nested ×2, nested ×5 (GR12's floor) and flat
REPLACING all stay clean and correct. The GnuCOBOL replacement-reaches-nested-text semantics remain a
vendor-dialect-axis candidate, adjudicated separately if ever wanted.
