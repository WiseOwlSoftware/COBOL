# PB399 — four EVALUATE syntax rules with no screen, and an index guard standing in for one of them

## 1. The mechanism

Four of EVALUATE's syntax rules are **syntax** rules — a violation shall be a compile-time diagnostic — and
none of the four has a screen. Two distinct absences produce them.

**(a) SR2, the operand-count rule, is stood in for by a bounds guard inside the binding loop.**
`EvaluateBinder.Bind` walks the WHEN groups with `for (int i = 0; i < groups.Length; i++)`
(`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs:45`) and, at `:48`, returns
`new BoundUnsupported("EVALUATE: more WHEN objects than subjects (ISO §14.9.13 SR)")` when `i` runs past the
subject array. That is a defensive index guard wearing a rule's clothes, and the two directions fail
differently *because* of it:

- **MORE objects than subjects** — the guard fires, but into the BOUND TREE, so the "diagnostic" arrives as an
  unhandled `NotImplementedCobolFeatureException` at RUN TIME, and only if that WHEN is actually reached. It is
  coverage-shaped in exactly the way PB47 described for the Table-15 screen before that screen moved to compile
  time.
- **FEWER objects than subjects** — there is no check anywhere. The loop terminates at `groups.Length`, the
  surplus SUBJECTS are never paired with anything, and the WHEN phrase matches on the strict subset of pairs
  that happened to be written. This half is the more insidious: illegal source silently produces a program that
  takes a branch on a subset of its own selection subjects, with no diagnostic at any stage and no run-time
  signal. That is the one-arm-of-two shape (PB45, PB47) again.

**(b) The range-expression operands are handed straight to `BindValueOperand` with no admissibility screen of
any kind**, so SR4, SR9 and SR7 a) all fail on one absence. `EvaluateBinder.cs:218-219` binds
`range.valueOperand(0)` and `range.valueOperand(1)` and goes directly to `left >= lo && left <= hi`; nothing
between the parse and the emit asks what class the operands are, whether the two classes match, or whether
either is a variable-length group. The Table-15 screen cannot catch these **and is not the right place to
try**: `ObjectOperandKind` (`EvaluateBinder.cs:118`) classifies a `valueRange` as one
`EvaluateObjectOperand.RangeExpression` row and never looks inside it, which is correct — Table 15 is about the
subject/object PAIRING, not about a range's internals.

The pointer case is the sharpest. SR4 excludes class pointer outright, and independently 8.8.4.2.16 defines
only equality for pointer operands, so the `>=` / `<=` pair the lowering emits is not a comparison the standard
defines at all: the compiler invents an ordering on raw addresses, which is meaningless and platform-dependent.

    $ cobol.exe p10-sr4-class.cob --run        # PIC X(3) subject, `WHEN "A" THRU 5` — alphanumeric x numeric
      OTHER                                                                                       [exit 0]

    $ cobol.exe p22-ptr-range.cob --run        # three USAGE POINTER items, `EVALUATE WS-P WHEN WS-Q THRU WS-R`
      PTR-OTHER                                                                                   [exit 0]

    $ cobol.exe p12-vlg.cob --run              # two groups each holding OCCURS 1 TO 5 DEPENDING ON, as the range ends
      VLG-RANGE                                                                                   [exit 0]

Expected in every case: **rejected at compile time** with a syntax diagnostic, and no executable produced.
p13/p02 violate SR2 (the positional correspondence SR7's stem requires is undefined when the counts differ);
p10 and p22 violate SR4 (different classes; class pointer excluded), p22 additionally SR7 a) via 8.8.4.2.16;
p12 violates SR9. Observed: p13 compiles clean and dies only when the WHEN is reached; the other four compile
clean, emit no diagnostic at any stage, and run to completion. **The branch taken is not the point** — the
point is that four syntax rules produced no diagnostic. Beyond the missing diagnostic: p22's emitted code
orders raw addresses, and p12's range bounds are read at whatever length the ODO counter holds at the moment
the WHEN is considered, so the same source can compare different numbers of characters on different runs.

## 4. The code site and the shape of the repair

- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs:45-48` — the `if (i >= subjects.Length)`
  guard, and the absence of any `groups.Length < subjects.Length` test anywhere in `Bind`.
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs:215-231` — the `item.valueRange()` arm.
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs:86-95` — `ScreenPairing`, the existing
  compile-time screen and the natural neighbour for the count check.
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#CheckedRelational` — emits `>=` / `<=`
  with no 8.8.4.2 admissibility question for the range case.

**SR2:** one count comparison beside `ScreenPairing`, reported once through `ctx.Edition.Error` (a new
`DiagnosticCatalog` entry), covering BOTH directions and naming the two counts. The guard at `:48` then
becomes an assertion that can no longer fire — delete it or turn it into a `Debug.Assert`; leaving a live
`BoundUnsupported` behind a compile-time check is how the run-time arm survives a "fix".

**SR4 / SR9 / SR7 a):** ONE screen over the range PAIR — class equality, the four excluded classes, the
variable-length-group test, and the 8.8.4.2 admissibility question — called once from the `valueRange` arm.
Not three `if` statements, and structured so the **VALUE clause's THROUGH phrase can call the same screen**,
because 14.7.8 says the two share this specification. Where PB398 threads an alphabet through `valueRange`,
this screen is the natural place to ask whether that alphabet's kind matches the operand class (SR3), so the
two fixes should land against the same helper rather than against two.

## 5. The sibling sweep the fixer must do

- **`valueClauseRange` / the VALUE clause THROUGH phrase** — SR4's and SR9's VALUE-clause analogues live in
  13.18.61; if the screen is written only for EVALUATE, the same illegal range is still accepted in a VALUE.
- **Every other operand-count rule of the ALSO family** — the SEARCH ALL WHEN list and the `PERFORM VARYING …
  AFTER` chain both pair positionally; ask whether their guards are index guards too.
- **Every `BoundUnsupported` that names an ISO SR** — grep `BoundUnsupported(".*ISO` in the binders. A
  `BoundUnsupported` naming a *syntax* rule is by construction a rule reported at the wrong stage; each hit is
  either this same defect or wants the same treatment.
- **`CheckedRelational` callers** — if the 8.8.4.2 admissibility question is added inside `CheckedRelational`
  rather than in the range screen, it fires for plain relation conditions too, which is probably right but is a
  behaviour change across the whole condition spine; measure it before choosing where the question goes.
- Edition sweep: p13 and p02 were **re-measured on HEAD at `--std 85` and behave identically** (the same
  run-time exception and the same silent `MATCHED-ONE-OBJECT`), so the new diagnostic must be raised at every
  edition, not gated.
