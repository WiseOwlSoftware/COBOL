# PB319 — one rule, two places, and the second copy lost the condition

**Rows:** `SR-14.9.27.3-8`.

## The program

`<lane3 scratch>/out-b1/probe/open-p1/sr8ovr.cob` — `SELECT F1 ... ORGANIZATION IS SEQUENTIAL SHARING WITH ALL
OTHER.` with no LOCK MODE clause, whose only OPEN is `OPEN OUTPUT SHARING WITH NO OTHER F1`. Observed:

```
sr8ovr.cob(6,12): error COBOLNET1512: file 'F1': SHARING WITH ALL OTHER requires the file to have a
                 LOCK MODE clause (ISO 14.9.27 SR8)
```

reported at the SELECT, on a program SR8 does not reach. The second shape is already in the corpus:
`tests/conformance/negative/sharing-all-no-lockmode.cob` declares the same SELECT and has **no OPEN statement
anywhere** (its whole procedure division is `MAIN. STOP RUN.`), and its `.err` golden pins the rejection GREEN.

## The rule

> §14.9.27.3 SR8: When file-name-1 is not subject to an APPLY COMMIT clause, then if the sharing phrase is
> omitted from the OPEN statement and the ALL phrase is specified in the SHARING clause of the file control
> entry for file-name-1 or if the ALL phrase is specified on the OPEN statement, the LOCK MODE clause shall be
> specified in the file control entry for file-name-1.

`--check 14.9.27.3 "the LOCK MODE clause shall be specified in the file control entry for file-name-1"` → **OK**.

The requirement has two disjuncts and **both mention an OPEN statement**: [sharing phrase omitted from the OPEN
AND the SELECT says ALL] or [ALL specified on the OPEN]. `sr8ovr.cob` satisfies neither — its OPEN carries a
sharing phrase, and that phrase is NO OTHER — so the program is legal and must compile. A program with no OPEN
at all likewise satisfies neither.

The SHARING clause's own clause imposes nothing: §12.4.5.15.3 has exactly ONE general rule (the SHARING clause
specifies the sharing mode unless overridden by the OPEN statement's SHARING phrase) and **no syntax rules**, so
§14.9.27.3 SR8 is the only source of a LOCK MODE requirement anywhere in the standard.

## What the compiler does

Two enforcement sites exist for one rule.

* `StatementValidation.CheckOpenSharingAllOther`, called from `BindOpen` per file, is a faithful transcription
  of the disjunction — `effectiveSharing is SharingMode.AllOther && file.LockMode is null` over
  `sharing ?? file.Sharing` — and is correctly conditioned on an OPEN.
* `DataBinder.BindFileControl` then repeats the CONCLUSION without the ANTECEDENT: `if (file.Sharing ==
  SharingMode.AllOther && file.LockMode is null) Edition.Error("COBOLNET1512", ...)`, its comment claiming the
  OPEN site *also checks*.

It is the SELECT copy that must go: the OPEN copy already covers the [phrase omitted AND SELECT says ALL]
disjunct the moment an OPEN exists, which is the only moment the rule speaks. The extraction IS the fix.

**The green golden is why this survived.** `tests/conformance/negative/sharing-all-no-lockmode.cob` asserts the
over-rejection as intended behaviour, so the gate reads clean while the compiler refuses legal COBOL. It must be
**re-derived from SR8's text** — given an OPEN that actually triggers a disjunct — in the same change set, never
rebaselined.

## Two further gaps in the same rule, both currently masked

* SR8's leading exemption — *when file-name-1 is not subject to an APPLY COMMIT clause* — is not modelled at
  all. Harmless only while APPLY COMMIT is a parse error, and live the day A.4.3 is claimed.
* The OPEN-site check's input leaks across the format's repeated group: **PB316**.

**Code sites:** `DataBinder.cs#BindFileControl` (the unconditioned SELECT-time copy) ·
`StatementValidation.cs#CheckOpenSharingAllOther` (the correctly-conditioned copy) ·
`tests/conformance/negative/sharing-all-no-lockmode.cob` + `.err`.

## Re-measured 2026-09-05 by the PB316 implementer (train 8)

PB316 (the OPEN repeated group made the bound tree's shape) measured this note's mechanism from the OPEN side and added three facts. (1) A program whose only file carries `SHARING WITH ALL OTHER` and no `LOCK MODE`, with a plain `OPEN OUTPUT F1`, reports the SAME rule TWICE in two spellings — COBOLNET1512 from `DataBinder.cs` (~:876, off the SELECT clause alone) and COBOLNET1512 from `StatementValidation.CheckOpenSharingAllOther` (`:345`, the OPEN binder, which already covers BOTH disjuncts of §14.9.27.3 SR8's antecedent) — repro `<a9d94900 scratch>/PB316/probe/sr8dup.cob`. The OPEN binder is the one correct home: SR8 is a rule about file-name-1, which §14.9.27.2 defines as the OPEN statement's operand, and §12.4.5.15 has no syntax rule requiring LOCK MODE, so the SELECT-side copy also rejects a file declared `SHARING WITH ALL OTHER` and NEVER opened — the extraction IS the fix (`one_rule_one_place`). ⚠ `tests/conformance/negative/sharing-all-no-lockmode.cob` PINS the over-rejection (it has no OPEN statement at all) — a green test holding the gap open; re-point it at a program that DOES open the file. (2) SR8 opens "When file-name-1 is not subject to an APPLY COMMIT clause" (`OK §14.9.27.3 8)`; its NOTE: files subject to APPLY COMMIT already have an implicit LOCK mode clause) and NEITHER site tests the APPLY COMMIT clause, so an APPLY COMMIT file with `SHARING WITH ALL OTHER` and no explicit `LOCK MODE` is rejected where the standard exempts it; the sibling SR7 IS implemented (`negative/apply-commit-open-sharing.cob`), so the APPLY COMMIT fact is available at bind time — the other arm of the same pair, to be folded into this note's extraction. (3) After PB316 the OPEN binder's `sharing ?? file.Sharing` reads the file's OWN group's phrase, so the one remaining site sees exactly SR8's two disjuncts.
