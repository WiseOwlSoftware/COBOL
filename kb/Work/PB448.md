# PB448 — two nesting defects in the SEARCH general rules, one of which makes a wrong citation pass

Adjudicated in lane-3 batch b2 (`search-statement` part 2). **Both instances re-verified on HEAD 89044aa0**
against the spec submodule as it stands there.

⚠ **Reporting form.** This note deliberately does **not** place a spec quotation next to the clause address it
belongs to. That is the whole subject of the note — the address `cite.py` returns for these two items is not
the address the standard gives them — and writing the true pairing would be indistinguishable, to the citation
audits, from a misfiling. Every quotation below appears only inside a `cite.py --check` command line, where no
`§` stands beside it.

## 1. The mechanism

**Instance 1 — an item that lost its indent, and now answers to its sibling's address.**
In `specs/ISO_COBOL.md` the first two sub-items of the SEARCH clause's first general rule, step b, are written
at line 27029 and line 27031 as `   1\.` and `   2\.` — three spaces of indent, escaped period, correctly
nested under `   b)` at line 27027. The third is written at **line 27034** as `3.`: **no indent, no escape**,
and preceded by a **double blank line** (lines 27032-27033). Markdown therefore renders it as a fresh
top-level ordered list rather than as the third alternative of step b, and the citation resolver — which
tracks the last indented marker it saw — attributes it to `2.`.

The consequence is exactly backwards from what the citation discipline exists for: a comment, golden or design
doc that **correctly** names the item's real number would **fail** `--check`, while one that names its sibling
**passes** while pointing at a different rule. Two distinct rules resolve to one address and neither the
caller nor `--check` can tell.

The damage is already downstream. The rule catalog could not derive a general-rule number for the item and
gave it the synthetic id **`GR-14.9.37.4-L2.3`** (confirmed present in `docs/rearchitecture/spec-rule-catalog.json`
on HEAD), so the traceability inventory carries a row whose name no code comment can ever match.

**Instance 2 — four items flattened to one level, eight rules later.** In the same clause's sixth general
rule, the two complementary cases a) and b) are siblings, with a)'s alternatives 1. and 2. nested under a).
The transcription writes **all four at the same three-space indent** (`specs/ISO_COBOL.md:27071` a),
`:27073` 1., `:27075` 2., `:27079` b)), so the nesting tracker attributes b) to the preceding numbered item
and the resolver returns an address that **does not exist in the standard**. That instance is the less
dangerous of the two — a correct citation fails loudly rather than resolving to a different real rule — but it
is the same cause and wants the same repair.

## 2. The repro, on HEAD

```
$ python scripts/spec/cite.py --check 14.9.37.4 "neither exception condition was raised because the checking for those exception conditions was not enabled, control is transferred to the end of the SEARCH statement"
OK  §14.9.37.4 1) b) 2.  (General rules)
    3. If the AT END phrase is not specified and neither exception condition was raised because the checking
       for those exception conditions was not enabled, control is transferred to the end of the SEARCH statement.

$ python scripts/spec/cite.py --check 14.9.37.4 "an applicable exception processing statement associated with that exception condition exists, control is transferred according to the rules for that statement"
OK  §14.9.37.4 1) b) 2.  (General rules)
    2\. If the AT END phrase is not specified and either the EC-RANGE-SEARCH-INDEX or EC-RANGE-SEARCH-NO-MATCH …
```

Two different rules, one reported address — and the first command's own excerpt begins `3.`, i.e. the tool
prints the right text under the wrong label, in one line of output.

```
$ python scripts/spec/cite.py --check 14.9.37.4 "If no such setting of the search index exists, the final setting of the search index is undefined"
OK  §14.9.37.4 6) 2. b)  (General rules)
```

`6) 2. b)` is not an address the standard has.

The source, on HEAD:

```
$ sed -n '27027,27034p' specs/ISO_COBOL.md

(blank)
   1\. If the AT END phrase is specified, …
(blank)

(blank)
```

## 3. Measured against the printed standard, not inferred

The item's level was established from **PDF text-block geometry**, not from reading an image. On PDF page 753
the `3.` marker sits at x=115.05 with its text at x=132.56; the `1.` and `2.` markers on page 752 sit at
x=98.50 with text at x=116.01. Page 753's whole indent ladder is offset **+17.5pt** from page 752's because
752 is a verso and 753 a recto — 752's general-rule column is x=63.49 and 753's is x=80.03, and 752's page
number prints left at x=63.49 while 753's prints right at x=416.95. So x=115.05 on the recto is the **same
logical column** as x=98.50 on the verso: the item is at the sibling level, and its content completes the
three-way enumeration the rule needs (AT END specified; AT END absent with an EC raised and a handler; AT END
absent with no EC raised because checking was off).

For instance 2, on PDF page 754, a) is at x=81.01 and b) is at x=81.01 — the same column — while 1. and 2. sit
at x=98.51.

## 4. The repair

* `specs/ISO_COBOL.md:27034` — restore the three-space indent and the escaped `3\.`; delete the stray extra
  blank line at `:27032-27033`.
* `specs/ISO_COBOL.md:27071` / `:27073` / `:27075` / `:27079` — restore b)'s indent to match a)'s and push
  1./2. one level deeper.
* Re-derive the rule catalog afterwards, so the first item gets its real id in place of the synthetic
  `GR-14.9.37.4-L2.3`, and re-check any inventory row or note that references that id.

Both instances should be fixed in **one pass over this clause's list structure**, because a partial repair
leaves the catalog half-renumbered.

## 5. The sibling sweep the fixer must do

* ⛔ **`kb/Work/PB385.md` (open) owns the general form of this defect** — 105 continuation sub-items
  transcribed at column 0, scanned mechanically. Its scan pattern looks for a column-0 `x)` item continuing an
  indented run; **this note's instance 1 is a column-0 `x.` numbered item, and instance 2 is a
  same-indent flattening with no column-0 marker at all**, so neither is in PB385's 105. Whoever repairs
  either should widen PB385's scan to cover both shapes before declaring the family closed — the two notes are
  the same mechanism found by two different probes, and PB385 is the one with the corpus-wide sweep.
* **Re-run the widened scan over every clause whose rules carry a two-level enumeration**, not just this one;
  the SEARCH clause has two instances eight rules apart, which is evidence of a systematic pipeline behaviour
  rather than two typos.
* **Every row in the traceability inventory whose id carries an `L<n>.<m>` synthetic form** deserves a look:
  the synthetic id is the catalog's signal that it could not derive a real number, and at least some of those
  are this defect rather than a genuinely unnumbered item.

## 6. Rows

This note claims **no** inventory rows. It is a transcription and tooling defect, not a compiler behaviour: it
changes nothing a user's program does, which is why `process_only` is true. Its harm is that it makes the one
mechanical guard CLAUDE.md rule 1 relies on — a `--check` that proves a citation's clause number — return a
confident wrong answer for two rules in this clause.
