# PB246

**Rows:** `AR-15.84.3-2`, `RV-15.84.4-4`

FUNCTION SQRT's NATIVE lane is a bare Math.Sqrt with no domain guard and no absolute value, where LOG and LOG10 four lines away carry both at the body.

ROWS: AR-15.84.3-2 (§15.84.3 r2 — 'The value of argument-1 shall be zero or positive') and RV-15.84.4-4 (§15.84.4 r4 — 'the returned value is the ABSOLUTE VALUE of the approximation of the square root of argument-1').

SCOPE FIRST, because HEAD has moved: PB116 landed `SqrtDec` (`CobolIntrinsics.Dec.cs:184-189`) with an explicit `if (v.Sig < 0) return CobolDec.From(ArgumentError("SQRT argument-1 shall be zero or positive (ISO §15.84.3 rule 2)"), 0)`, and `CobolDec.Sqrt` (:372-374) returns `new CobolDec(0, 0)` — a POSITIVE zero — for `Sig <= 0`. So AR-15.84.3-2's own concrete witness (an SDIDI −1E−330 under ARITHMETIC IS STANDARD-DECIMAL) is CLOSED. What survives is the NATIVE lane, and it survives whole.

HALF ONE — NO DOMAIN GUARD (AR-15.84.3-2). `CobolIntrinsics.Float.cs:28` is a bare `Math.Sqrt(x)` and the whole family's detection is the NaN artifact. That is sound only while the double the body receives has the same SIGN as argument-1. `IntrinsicRenderer.Dbl → NumericRenderer.Real` (:697) converts an SDIDI operand as `(expr).ToDouble()` and `CobolDec.cs:310` is `(double)Sig * Math.Pow(10, Exp)`; for `Exp <= -324` the power underflows to +0.0, so a NEGATIVE value becomes −0.0 (verified at the IEEE level: (−1.0)*pow(10,−400) = −0.0, signbit −1), and `Math.Sqrt(-0.0) = -0.0`, not NaN. Nothing downstream recovers it: `RealResult` and `FromDouble` screen `double.IsNaN` ONLY. The sibling in the same file is the proof this is a miss and not a design — :32-33 give LOG and LOG10 an EXPLICIT `x <= 0` guard citing their own clauses at the body — and SQRT's in-code comment misnames the clause it claims to honour ('argument ≥ 0 (rule 1)'; r1 is the CLASS rule, r2 is the value rule).

HALF TWO — 'ABSOLUTE VALUE' IS NOT IMPLEMENTED, MERELY UNREACHABLE-BY-ARGUMENT (RV-15.84.4-4). The rule does not say 'made non-negative when negative'; it says the returned value IS the absolute value, and IEEE abs clears the sign bit: |−0.0| = +0.0 while `sqrt(-0.0) = -0.0`. IEC 60559 mandates `sqrt(−0) = −0` EXACTLY so that sqrt is not the absolute value there — −0.0 is the unique input on which r4's phrase does work, and it is the input the code gets wrong. −0.0 is a LEGAL argument-1: §15.84.3 r2 admits zero, and a COMP-1/COMP-2 item reaches −0.0 by ordinary native underflow (a product of a negative and a positive tiny float). `grep Abs src/Cobol.Net.Runtime/Intrinsics/CobolIntrinsics.Float.cs` returns NOTHING — there is no Math.Abs in the body or in any of the four RenderFloat arms.

OBSERVABILITY: the receiver-less/float arm (`IntrinsicRenderer.cs:424 RealResult(call)`) keeps the value unquantized and the text channel renders it through `CobolFloat.cs:25 Display(double v) => v.ToString(InvariantCulture)`, which on .NET Core 3.0+ is IEEE-faithful and therefore renders a negative zero WITH its sign — so `DISPLAY FUNCTION SQRT(<a COMP-2 holding -0.0>)` is the candidate wrong output, and a COMP-2 receiver stores the signed zero bit-for-bit. The refuter reported this as an unverified edge rather than DIVERGES because it was read-only and could not RUN it; the probe is the first thing this note owes.

FIX SHAPE, one line, beside LOG's: `x < 0 -> ArgumentError("§15.84.3 r2")` in the body — which also closes the −0.0 domain case by construction — plus `Math.Abs` on the result for r4, and a golden pinning SQRT over a negative-zero float operand in the receiver-less, float-receiver and fixed-receiver contexts.

WHAT IS CONFORMING AND MUST NOT BE 'FIXED': `Math.Sqrt` is IEC 60559 correctly-rounded, so the APPROXIMATION half of r4 is right; SQRT's catalog row carries `Codomain.None` and that is CORRECT — §15.84.4 states no bound, so the `FromDoubleBounded` clamp (RANDOM's [0,1), ASIN/ACOS/ATAN's π bounds) must not apply.

VERIFIED LIVE AT HEAD (read-only): `CobolIntrinsics.Float.cs:28` unchanged and still carries the comment 'negative → NaN → 0'; no `Abs` in the file.

## Mechanism

src/Cobol.Net.Runtime/Intrinsics/CobolIntrinsics.Float.cs:28 `public static double Sqrt(double x) => Math.Sqrt(x);` — no `x < 0` arm and no `Math.Abs` anywhere on the path (`grep Abs` over the file returns nothing), against :32-33 where Log/Log10 name §15.55.3 r2 / §15.56.3 r2 at the body; the only detection is the NaN artifact screened by CobolIntrinsics.cs#RealResult and #FromDouble, both testing `double.IsNaN` alone

## Lineage

PB13/PB5 (landed) moved the raise site out from under the unquantized render and set the quantizer cap; PB116 (landed) gave SQRT its 34-digit SDIDI arm and, with it, a §15.84.3 r2 value guard on the DEC lane only. The native float body was never swept.
