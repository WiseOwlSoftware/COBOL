# PB3538 — chained division overflows the intermediate carrier

## Scenario

Found by the slice-N adjudicator (Opus) 2026-10-22, re-run and the code site read by the Mythos session on the frozen
judge `E:\tmp\fuzz-judge-20261022\cobol.exe` (main af5e24cfa's compiler: PB3510/3511/3512/3517 fixed). Related: PB1511
(the 14 guard digits' documentation).

## Expected (spec)

- §14.7.4.3 GR2 (OK): "If the ROUNDED phrase is not specified, execution is as if ROUNDED MODE IS TRUNCATION had been

- §14.7.5 item 5) (OK): a size error arises "if native arithmetic is in effect and the implementor defines that the range of

## Mechanism (read in `src/WiseOwl.Cobol.Compiler/CodeGen/Emit/NumericRenderer.cs` about lines 950 to 962, `Divide`, the nested arm)

```
int baseScale = Math.Max(_rcv.Scale, Math.Max(a.Scale, b.Scale));
int maxExp = 20;
int guard = Math.Min(DivGuardDigits, maxExp - (b.Scale + baseScale - a.Scale));
ds = baseScale + Math.Max(0, guard);
```

A nested quotient's scale is `max(receiver, a, b) + 14 guard digits`, and `a.Scale` for the next division IS the previous
quotient's scale, so the scale compounds: 14, 28, 42. The `maxExp` clamp limits only the guard digits added at this step,
never the accumulated scale; at scale 42 any quotient of magnitude 1 or more exceeds Int128 (about 1.7e38). The product arm
compounds the same way (two scale-14 quotients multiply to scale 28, three to 42).

## Root-cause shape to require (CLAUDE.md rules 4 and 5; the owner's bar 2026-10-22 11:05: no hack, the architecturally correct design for a decade-long supported compiler)

The intermediate-result engine needs ONE rule for the precision of a nested intermediate that does not depend on the depth
of the expression: a bounded intermediate scale (the documented native-arithmetic intermediate: 34 significant digits,
DOC-A.1-123) that every arm (quotient, product, sum, difference, exponentiation, function result) renormalizes to before
the next operation, with truncation at that step documented as the implementor's intermediate rule (§14.7 NOTE and the
DOC-A.1-123 text updated together), so that depth never changes the result's correctness and a size error occurs only when
the VALUE leaves the documented range. A guard that caps the depth, or a per-arm clamp of the accumulated scale, is a
workaround. Sweep: every arm of NumericRenderer that derives its scale from an operand's scale; nested exponentiation;
function results used as operands; `ARITHMETIC IS STANDARD-DECIMAL` (does the same compounding exist in the
standard-decimal lane, where §8.8.1.5 fixes the intermediate?); the `--permissive` lane.

## Goldens to require

The repro (both COMPUTEs, with and without ON SIZE ERROR) and the product sibling, at every accepted edition, expected
values derived from §8.8.1.2 and §14.7.4.3; a depth-10 chain (8 / 2 ten times, and 1 / 3 ten times to a receiver of scale
4) that must give the truncated left-to-right value; the same chains under `ARITHMETIC IS STANDARD-DECIMAL`; a drift test
that no NumericRenderer arm's intermediate scale depends on an operand intermediate's scale beyond the bounded rule.

## Landed (wave 1153 group A, 2026-10-22)

Re-probed on the branch's own build first: `div2` printed `THREE 0001`, `SIZE ERROR`, `FOUR-CHECKED 0001` and ended with
EC-SIZE-OVERFLOW (rc 1); `div3` printed `P2 0016` and ended with EC-SIZE-OVERFLOW. Both now print the spec-derived values
(`THREE 0001`, `FOUR-CHECKED 0000`, `FOUR 0000`; `P3 0064`).

**The fix (numeric design D2, `NumericRenderer.Divide`).** A nested quotient's working scale is
`max(receiver scale, operands' precision) + 14`, where the precision is `NumX.FractionPrecision`: the fraction digits a
value's operands carry. A quotient's guard digits are NOT part of it, and sums, products, negations and wide powers carry
it the way they carry the scale. So the guard is added once, whatever the depth. The quotient's lane comes from its digit
bound (the dividend's integer digits, plus the divisor's fraction digits, plus the working scale), as a product's does
(PB1143). Within 38 digits it is the truncating Int128 quotient. Past that it goes to the SDIDI by round-to-odd. The old
maxExp clamp is gone, because the bound proves the dividend alignment fits.

**The sibling arm (`Multiply`).** An operand with no digit bound of its own (a function value, a windowed view) is bounded
by its `Int128` carrier (`PicInfo.CarrierDigitBound`, 39 digits). Its product therefore takes the exact wide, `MulAtScale`
or SDIDI arms. It no longer takes `CobolNum.MulChecked` at the summed scale, which ended
`FUNCTION MEAN (F G) * FUNCTION MEAN (F G) * FUNCTION MEAN (F G)` (5.36, scale 54) with EC-SIZE-OVERFLOW. `MulChecked` is
deleted, which changed the shipped runtime surface: runtime major 13, ABI pin re-pinned. DIVIDE ... REMAINDER's capped
subsidiary quotient carries its digit bound, and its back-multiply stays exact into the subtraction (`Combine` with
`keepWide`).

**Design measured and rejected.** Putting every nested quotient on the SDIDI (34 digits, round-to-odd) is bounded too.
On the whole Conformance assembly it turned one case of 18,125 red: pb60's native `2 / 7 * 7` became 2.000000, where
GnuCOBOL's truncating divide and exact multiply give 1.999999. It would also move every nested division onto software
decimal128.

**STANDARD-DECIMAL.** It never had the defect: `CombineCore` routes every operation to the SDIDI before the native
`Divide`. The `pb3538_chained_division_standard_decimal` golden pins it.

**Witnesses.** `conformance-suite/cases/8.8.1.2-Native-standard-binary-and-standard-decimal/pb3538_chained_division_native`
(85 to 2023), `pb3538_chained_division_standard_decimal` (2014, 2023) and `pb3538_unbounded_operand_products` (2002 to
2023). `NestedQuotientPrecisionDriftTests` compiles each quotient-crossing shape at depth 2 and depth 16 and requires the
same division-kernel scales. Run against the base tree it was red, with scales growing to 228. CONFORMANCE.md
DOC-A.1-123 and DOC-A.1-179 are corrected.

**A golden re-derived.** `14.9.12-DIVIDE/l1_divide_remainder_backmultiply_size_error` had pinned the checked
multiply's size error (`OVF=SIZEERR`) for a DIVIDE ... REMAINDER back-multiply of value about 10**12 whose UNSCALED
form is about 10**40. The value is inside the range, so §14.7.5 case 5 raises nothing. Re-derived:
`OVF=NONE BQ=999999999999.98999999900000 BR=000000000000.000000000` (BR = 1.0000001E-16, truncated). The inventory rows
GR-14.7.5-5 and GR-14.9.12.4-7 are restated through batches. `14.7.5-SIZE-ERROR-phrase-and-size-error/pb91_native_overflow_outside_arithmetic` made its native overflows from
products of two `FUNCTION ABS(A)` values (A = 10**20 - 1). Under the new rule that product is exact, so its overflow
legs now add 1 to HIGHEST-ALGEBRAIC of a `PIC S9(19) COMP-5` item (2**127 - 1), a sum no Int128 intermediate holds.
The expected statuses are unchanged, and a new R8 leg pins the ABS product as TRUE.

**For the next implementer.**

  when the operand may be an intermediate. `DivideAt` is the one spelling of the scaled kernel call.
- `src/WiseOwl.Cobol.Compiler/CodeGen/Emit/NumericRenderer.cs#Multiply` / `#DigitBound` / `#Carried`: an unknown digit bound
  is `PicInfo.CarrierDigitBound`. Every exact arm that builds a NumX from operands passes
  `Precision: Carried(a, b, <rule>)`, as `CombineAdditive`, `Multiply`, `Negate` and the wide `Power` arm do.
- `src/WiseOwl.Cobol.Compiler/CodeGen/Emit/EmitCore.cs#NumX.FractionPrecision`: a null `Precision` means "it is the Scale" for an exact value, and "known only at run time" for a Dec (`NumX.RuntimePrecision`; `FractionPrecision` throws on it).
  A new producer that drops it is safe only when no quotient can be its operand.
- `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/ArithmeticEmitter.cs#EmitDivideRemainder`: the back-multiply is
