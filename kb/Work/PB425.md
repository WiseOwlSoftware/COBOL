# PB425 — the exclusion is implemented, the rule is not

## The mechanism

§14.9.25.4 GR2 makes an alphanumeric or national zero-length literal BEHAVE AS the figurative constant SPACE, and
GR3 makes a boolean one behave as figurative ZERO — in both cases unless the receiving operand is a
dynamic-length elementary item. The compiler implements only the EXCLUSION.
`src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs:285-286`:

```csharp
if (target.IsDynamicLength)
    return RuntimeApi.DynStore(OperandText.AsString(source, num, deSign: true), target.DynLengthLimit.ToString());
```

whose comment names GR2 and correctly keeps `""` at length zero. For every OTHER receiver the zero-length literal
simply flows on as an empty string and is padded by the receiver's own alignment rule. That COINCIDES with the
required answer for most receivers — which is exactly why it survived a large corpus — and stops coinciding
wherever the substituted figurative's own value is not a space: a NUMERIC receiver for GR2, and an ALPHANUMERIC
receiver for GR3. Both feed the same missing rewrite, so one fix closes both, and GR1's zero-length-item clause
routes a zero-length DYNAMIC LENGTH SENDER into the same hole.

Table 17 (under GR7) gives SPACE/ZERO against an Alphanumeric receiving operand the category ALPHANUMERIC, and
§8.3.3.6.4 GR1 gives ZERO's alphanumeric character value as '0'. That is what makes GR3's divergence measurable:
figurative ZERO into `PIC X(3)` is "000", not spaces.

⚠ §14.9.25.3 SR5 does NOT reach any of these, and the distinction is load-bearing for the fix (below). SR5's
prohibition names "an alphanumeric figurative constant (SPACE, QUOTE, HIGH-VALUE, LOW-VALUE, ALL "literal", or
ALL symbolic-character)" — a closed list of things WRITTEN IN THE SOURCE. A zero-length literal is a literal, and
syntax rules are decided on what is written; GR2 is a GENERAL rule about the value moved. Same for SR7 and a
boolean receiver.

## The code site and the shape of the repair

- `src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs#ConvertSource` (:273; the `target.IsDynamicLength` arm at
  :285-286 implements the exclusion and names GR2; NO arm implements the substitution).
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/MoveBinder.cs#Bind` (:31-59) — no rewrite of a zero-length
  literal-1 to a `BoundFigurative`.

**DO IT IN THE BINDER, PER RECEIVER, AS A VALUE REWRITE** — rewrite a zero-length `BoundStringLiteral` / national
literal to `BoundFigurative{Kind:'S'}` and a zero-length boolean literal to `BoundFigurative{Kind:'Z'}` when the
receiver is not dynamic-length, so the existing figurative machinery (`MoveClassifier`'s
FigurativeToNumericImage arm, `FigurativeConstants.Fill`'s category dispatch, Table 17) is reached automatically
instead of being bypassed. Doing it in the EMITTER would leave the category dispatch blind to the substituted
figurative.

⛔ **BUT THE REWRITE MUST NOT BE VISIBLE TO THE SYNTAX-RULE GATES, and the b2 finding's proposed repair got this
backwards.** The finding argued for a binder rewrite specifically so "the §14.9.25.3 SR5/SR7 gates are reached
automatically". They must NOT be: SR5 and SR7 are SYNTAX rules over a closed list of figurative constants written
in the source, and a zero-length literal is not one of them. If the rewrite feeds the SR5 gate, then at 2023
strict `MOVE "" TO PIC 9(3)` — which the standard permits — becomes COBOLNET0902, and the fix turns a wrong
answer into a false rejection, the one outcome CLAUDE.md rule 4 forbids outright. Rewrite AFTER the syntax
screens (or mark the rewritten operand as substitution-derived and have the gates skip it), and pin BOTH
directions with goldens: the value is the figurative's, the diagnostics are the literal's.

## The determination the fixer owes

`MOVE "" TO <a boolean receiver>` has no answer in the standard as written, and it should be recorded as a
determination rather than guessed at. GR2 substitutes figurative SPACE; Table 17's SPACE row DOES list a Boolean
receiving operand and gives the category Boolean; but §8.3.3.6.4 Format 2 GR5 gives the space format only "one or
more of the character space in the computer's runtime coded character set" and names no boolean value, while SR7
(which would have barred it) does not reach a literal. HEAD currently stores boolean zeros
(`gr2_zl_boolean.cob --std 2023` -> `B-ZL=[0000]`), which is the same answer GR3 gives the boolean literal — a
defensible reading, but an undeclared one. Survey the other compilers before choosing (memory:
`survey_compilers_on_latitude`) and write the determination down.

## The sibling sweep the fixer must do

- Every OTHER statement whose general rules substitute a figurative constant for a written operand. The failure
  shape is "the EXCLUSION clause was implemented because it changed behaviour; the SUBSTITUTION was not because
  it usually did not." Grep the spec for "is treated as if it were the figurative constant" and check each hit.
- Every zero-length-literal consumer: STRING, UNSTRING, INSPECT, the relation conditions, and VALUE. GR1's
  zero-length-ITEM clause makes a zero-length dynamic-length item enter the same path, so anything reading a
  dynamic-length sender is in scope.
- The national leg of GR2 (`N""` into a numeric or boolean receiver) was not probed; it rides the same rewrite.

## Rows

- `GR-14.9.25.4-2` (DIVERGES) — the dynamic-length EXCLUSION conforms and is pinned; the substitution is written
  nowhere, measured divergent at a numeric receiver and reachable a second way through GR1.
- `GR-14.9.25.4-3` (DIVERGES) — same missing mechanism, measured divergent at an alphanumeric receiver. GR3's own

  LENGTH item's PICTURE to one N or one X, so no boolean dynamic-length item exists to exercise it — recorded so
  the exclusion is not later mistaken for untested coverage. No spec-derived test references either rule.

## Landed — 2026-09-13

GR2 and GR3 are implemented as the standard writes them, at ONE seam, with the exclusion beside them; GR1's
zero-length-ITEM clause is implemented as the runtime half of the same rule. All three legs above were re-probed
on this worktree's own build before any change and all three reproduced; all three now conform.

**The one home.** `MoveClassifier.Sender(source, target)` — a zero-length `BoundStringLiteral` becomes
`BoundFigurative 'S'` (GR2, an alphanumeric or national literal) or `'Z'` (GR3, a boolean one) unless the
RECEIVING operand is a dynamic-length elementary item. `BoundStringLiteral` is the one node for all three literal
categories, so GR2 and GR3 are one two-armed answer keyed on the literal's own category, not two screens. It is
computed PER RECEIVER because the exclusion is per receiver: `MoveClassifier.Classify` now returns
`IReadOnlyList<MoveStore>` — `MoveStore(BoundOperand Sender, MoveKind Kind, MoveSenderOrigin Origin)`, the
third field naming WHICH rule put the sender there so an unstorable fill's loud blames the right one — and
`BoundMove.Kinds` became
`BoundMove.Stores`, so `MOVE "" TO D-DYN, R-NUM` empties the dynamic-length item AND space-fills the numeric one
from one statement. `MoveEmitter.Emit` reads the sender and the kind off the same store; `EmitFigurativeToNumericImage`
became the string-returning `FigurativeToNumericImageStore`, and a new `ElementaryStore` renders either arm.

**Which arms inherit it, and why they cannot not.** Every implicit MOVE constructs a `BoundMove`, so the
substitution reaches all of them by construction rather than by an edit: the `WRITE`/`REWRITE`/`RELEASE … FROM`
and `READ`/`RETURN … INTO` phrases through `MoveBinder.BindMoveOf`, `MOVE CORRESPONDING`'s per-pair moves,
GOBACK RETURNING's §13.18.18.4 GR6 move, and INITIALIZE's §14.9.20.4 GR4 per-target implicit MOVE through
`InitializeEmitter`'s own construction — measured: `INITIALIZE g REPLACING ALPHANUMERIC DATA BY B""` now stores
`000`, and `InitializeBinder`'s target model was not touched (PB419 is in flight there).

**The storage fact moved to the node.** `MoveFigurativeEditionGates` was renamed `MoveOperandClassChecks` and now
holds only the §14.9.25.3 SR1 class check; its `StoreAsImage` marking became `MarkFillImageStorage(move)`, run
AFTER construction and keyed on the node's own `MoveKind`. It had been a hand-copy of `MoveClassifier`'s
figurative-into-numeric test, and the copy could not see the substitution — so `MOVE "" TO PIC 9(3)` would have
rendered a space image into an item with no image backing.

**GR1's zero-length-ITEM route.** `MoveClassifier.ZeroLengthItemRoute` decides when a RUNTIME length test is
needed and over which sending place; `MoveEmitter` emits `if (<sender>.Length == 0) { <GR2 store> } else { <the
ordinary store> }`. The RECEIVER filter is a proof, not a shortcut: for every category other than numeric and
numeric-edited an empty sender and the substituted figurative deposit the same characters (§14.6.8.3–§14.6.8.6 pad
with the same fill the figurative supplies), so no test is emitted there. The SENDER filter is total because
everything else is normalized into it — `MoveBinder` now freezes a reference-modified or function-identifier
sender into `SendingValueTemp`'s dynamic-length carrier (`MoveClassifier.NeedsLengthFreeze`), which GR1's own
"evaluated only once" sentence requires anyway, so the length is read off a field and never by re-running the
expression. Measured: `MOVE FUNCTION TRIM(<all spaces>) TO PIC 9(3)` now stores the SPACE fill and
`FUNCTION TRIM("  12")` still stores 012.

**⛔ The diagnostics stayed the literal's** — the half that makes this a fix rather than a different defect. The
b2 finding had it backwards: it argued for the binder rewrite so "the §14.9.25.3 SR5/SR7 gates are reached
automatically". They must NOT be. SR5/SR6/SR7 name a CLOSED LIST of figurative constants written in the source and
a zero-length literal is not one, so the screens read `BoundMove.Source` (the written operand) and the stores read
`BoundMove.Stores`. `MOVE "" TO PIC 9(3)` still compiles at 2023 STRICT where `MOVE SPACE TO` the same item is
COBOLNET0902, and `MOVE B"" TO PIC 9(3)` is still COBOLNET0819 on Table 16's Boolean row. Both directions are
pinned, and `ZeroLengthSubstitutionDriftTests` fails on the pre-fix tree (proved by re-running its predicates
against `f8fa6452`: 6 `m.Source` reads in `MoveEmitter`) and on a mutated `GateMove` that reads `Stores`.

**The determination the note asked for, written down.** `MOVE "" TO <a boolean receiver>` has no answer in the
standard: GR2 substitutes SPACE, Table 17 gives SPACE against a Boolean receiving operand the category BOOLEAN,
and §8.3.3.6.4 GR5 names no boolean space while §8.3.3.4.3 SR2 admits only '0' and '1' in a boolean item.
**DETERMINATION D-B2** (docs/CONFORMANCE.md §3): the boolean character '0' — the only boolean character the
standard attaches to a fill (§14.6.8.6 "with zero fill or truncation to the right"; §8.3.3.6.4 GR4 "one or more of
the boolean character '0'"), and the same answer GR3 gives, so the two GR arms agree. It is HEAD's existing
observable answer, so nothing regressed; what changed is that it is now a rule rather than a coincidence of the
receiver's pad. Written once, in `FigurativeConstants.FillChar`/`Fill`. (The label is D-B2 because D-B1 is the
long-standing boolean-representation determination in `COBOLNET_DATA_MODEL_DESIGN.md`.)

**The sibling sweep, pasted.** `grep -n "treated as if it were the figurative constant" specs/ISO_COBOL.md`
returns EXACTLY two hits — §14.9.25.4 GR2 and GR3 — so the "some other statement substitutes a figurative and
only its exclusion was implemented" family has no second member. `cite.py --find "rules for the MOVE statement"`
returns the twelve clauses that defer to MOVE: the FROM/INTO phrases and INITIALIZE inherit the substitution
through `BoundMove` (above); ACCEPT (§14.9.1.4 GR6) and the DESTINATION clause (§13.18.18.4 GR6) have no
literal-1 in the sending position; §13.18.63 (VALUE) does NOT defer to the MOVE rules, so GR2/GR3 do not reach a
VALUE clause. The remaining zero-length-literal clauses (STRING, UNSTRING, INSPECT, the §15 arguments, RELEASE
… FROM) all PROHIBIT one rather than substituting for it, which is a different mechanism and already enforced.

**Residue, named rather than claimed.** The GROUP-shaped zero-length items of §8.5.4 items 2, 5 and 7 (a group
whose only member is a zero-length item; a zero-length variable-length record; a variable-length group of empty
dynamic tables) do NOT take GR1's route: they send through §14.9.25.4 GR4's group move, whose KIND GR1 would
itself change, and `SendingValueTemp`'s non-materialization of a variable-length group is the same boundary,
already recorded on row GR-14.9.25.4-1.

**Rows.** `GR-14.9.25.4-2` and `GR-14.9.25.4-3` re-verdicted DIVERGES → CONFORMS (batch
`pb425-zero-length-literal-move`, GAP 2468 → 2466). `SR-14.9.25.3-1` and `SR-14.9.25.3-5` had their
`code-location` repaired for the `MoveFigurativeEditionGates` rename; their verdicts are unchanged.

**Tests + goldens.** `conformance:2002/pb425_zero_length_literal_move` (the whole GR2/GR3 receiver matrix at the
introducing edition, plus the GR2 equivalence with `MOVE SPACE`), `conformance:2014/pb425_zero_length_item_move`
(the exclusion, per receiver, and both GR1 routes — 2014 only because its probes need a DYNAMIC LENGTH item, not
because the rule differs by edition), `conformance:negative/pb425-boolean-zero-length-to-numeric` (Table 16 on the
WRITTEN literal, reject-at 2002 2014 2023), `ZeroLengthLiteralMoveTests` (11 cases) and
`ZeroLengthSubstitutionDriftTests` (3).

## Landed — the FINISHER (wave 39)

The landing above left ONE thing wrong, and it was the freeze, not the substitution. `NeedsLengthFreeze` decided
by the sending operand's SHAPE alone — a reference-modified place or an intrinsic call — where GR1's own sentence
is conditional ("If identifier-1 IS a zero-length item") and §8.5.4's enumeration makes both of those shapes
conditional in turn:

- **§8.5.4 item 9** admits a reference-modified data item "when that has been permitted by use of the compiler
  directive REF-MOD-ZERO-LENGTH". The trailing qualifier IS the rule: outside such a region §7.3.23.3 GR1 raises
  EC-BOUND-REF-MOD where item 9 would otherwise produce a zero-length item, so GR1's antecedent can never hold.
- **§8.5.4 item 6** admits "an intrinsic function that returns a zero-length value". A NUMERIC returned value
  never is one — §15.4 puts it in "a temporary elementary data item" of the implementor's numeric description
  (§15.4.1), which has at least one digit position.

Freezing on the shape alone was a WRONG ANSWER, not a wasted temp: a numeric function sender was hoisted into
`SendingValueTemp.FunctionValuePic` (21 integer + 9 fraction digits), which is narrower than a STANDARD-DECIMAL or
floating-point result, so the hoist re-rounded a value that can never be zero-length. `MOVE FUNCTION E` into a
31-digit item stored `2718281828000000000000000000000` for `2718281828459045235360287471352`. Eight corpus cases
were measured RED before and GREEN after: `pb65_dec_move_channel`, `pb60_numvalf_native_channels`,
`pb60_numval_standard_decimal`, `pb251_numval_native_value_fixed`, `pb253_prose_float_standard_container`,
`pb253_prose_float_sdidi_container` (2014 and 2023) and `l1_numval_family_cap_discriminators`.

`MoveClassifier.CanBeZeroLengthItem` is the one home of §8.5.4's question for the two shapes whose length is not a
stable field read; the other items need no intermediate (a DYNAMIC LENGTH or ANY LENGTH item carries its own
length field, which `ZeroLengthItemRoute` reads directly, and the group-shaped ones send through GR4).

**Citation repair, in the same change set (CLAUDE.md rule 1).** The landing's own comments, tests, golden and note
cited §8.5.1.10 for the zero-length-item ENUMERATION. §8.5.1.10 is *Dynamic-length elementary items* and
`cite.py --check 8.5.1.10 "zero-length item"` FAILS; the enumeration whose item numbers 2/3/4/5/6/7/9 were being
quoted is §8.5.4. Ten citations repaired (five in `MoveClassifier.cs`, two in `ZeroLengthLiteralMoveTests`, two in
the 2014 golden, one here). This is the inherited-clause failure CLAUDE.md rule 1 names, caught on re-derivation.

**Golden + tests.** `conformance:2023/pb425_zero_length_sender_shapes` (both §8.5.4 arms; 2023 because
REF-MOD-ZERO-LENGTH is a COBOL-2023 directive and is what makes item 9 reachable — its below-2023 rejection is the
version matrix's own `ref-mod-zero-length-2023` construct row, COBOLNET0900), plus
`ZeroLengthLiteralMoveTests.Gr1_NumericFunctionSender_IsNotAZeroLengthItem_AndIsNeverReDescribed` and
`.Gr1_ReferenceModifiedSender_IsAZeroLengthItemOnlyWhereTheDirectivePermitsIt`. The golden was PROVEN to fail
pre-fix (`FN-NUM=[0123456789000000]` against `[0123456789012345]`).
