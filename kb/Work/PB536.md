# PB536

## Mechanism — sign-clause
sign-codeset-check-precedes-inheritance

### Expected, from the standard
§13.18.52.3 SR3: 'If the CODE-SET clause is specified in a file description entry, any signed numeric data description entries associated with that file description entry shall be described with the SIGN IS SEPARATE clause.' §13.18.13.3 SR3 a says the same from the CODE-SET side. §13.18.52.4 GR1 fixes what 'described with' means for a subordinate item: 'The SIGN clause specifies the position and the mode of representation of the operational sign for the numeric item to which it applies, OR FOR EACH NUMERIC ITEM SUBORDINATE TO THE GROUP TO WHICH IT APPLIES.' A signed numeric item under a group carrying SIGN IS ... SEPARATE therefore IS described with the clause, and the record description is LEGAL: the program shall compile.

```
$ python scripts/spec/cite.py --check 13.18.52.3 "The SIGN clause specifies the position and the mode of representation of the operational sign for the numeric item to which it applies, OR F..."
  FAIL: §13.18.52.3 exists but does NOT contain 'The SIGN clause specifies the position and the mode of representation of the operational sign for the numeric item to which it applies, OR FOR EACH NUMERIC ITEM SUBORDINATE TO THE GROUP TO WHICH IT APPLIES'
$ python scripts/spec/cite.py --check 13.18.52.4 "The SIGN clause specifies the position and the mode of representation of the operational sign for the numeric item to which it applies, OR F..."
  OK  §13.18.52.4 1)  (General rules)
```

### Observed
It is rejected. The record is refused with COBOLNET1672 'CODE-SET: the signed numeric record item N shall be described with the SIGN IS SEPARATE clause (ISO §13.18.13.3 SR3 a)'. MECHANISM, confirmed by reading both call sites: BindCodeSetClause is invoked from BindFileSection while the entries are still being bound (DataBinder.cs:1011), and its CheckItem reads the leaf's `pic.SignKind`; but a GROUP-level SIGN clause reaches that leaf only in the post-build InheritSignClauses pass, which the declared pipeline runs much later (BindPipeline.cs:46). At check time the leaf still carries the entry-bind default SignKind = TrailingOverpunch, so `!sp.SignKind.Contains("Separate")` is true and the diagnostic fires. The compiler's own storage model disagrees with its own diagnostic: strip the CODE-SET clause from the identical record and the same group SIGN gives N a separate sign character -- the file written is `-0012ZZ`, 7 bytes, FUNCTION BYTE-LENGTH(N) = 5 (probe sg_fd_groupsign). This is the general shape of the defect, not one clause: any entry-bind-time screen that reads an EFFECTIVE description fact settled by a later pass will disagree with the shape the compiler actually emits, so the sweep is over every read of PicInfo.SignKind / Usage / GroupUsage made from inside BindEntries/BindFileSection rather than from a declared pass.
