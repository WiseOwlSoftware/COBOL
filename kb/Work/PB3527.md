# PB3527 — nothing verifies that a landed pull request entered the merge queue

## Owner question (2026-10-22 ~12:45 PDT, verbatim)

"Why did it get stuck? That is a process problem"

## What happened (facts as recorded)

- PR #385 (`worktree-wf_8c44feac-62f-11`, PB3512): auto-merge enabled 18:44:50Z.
- Run 39834070835 completed success 18:46:47Z.
- Job `ci-gate` (id 120018552758, ubuntu-26.04): status completed, conclusion success, started 18:46:44Z, completed
  18:46:46Z, three steps all success.
- The check-run for the head commit fb899d188e35 showed status `in_progress`, conclusion null, until the Mythos session ran
  `gh run rerun 39834070835` at about 19:35Z, which created check-run 120043423624.
- The merge queue (`gh api graphql mergeQueue(branch:"main") entries`) was empty the whole time. The PR state was BLOCKED.
- Three other PRs enqueued the same hour (#388, #389, #390) merged normally.

The landing ends at `=== ENQUEUE: ENQUEUED ===`. Nothing after that checks that the pull request actually entered the
merge queue, so a required check-run that never resolves holds the landing for as long as nobody looks (50 minutes here).

Code sites: `scripts/orchestrator/enqueue.py`, `scripts/orchestrator/land_lane.py`, `scripts/orchestrator/landing_measure.py`.
Related: PB3023 (the one landing script), PB3103, PB3379.

## Fix shape (for the implementer)

After `=== ENQUEUE: ENQUEUED ===` the landing lane watches the pull request:

1. Within N minutes of its PR-level run completing, the PR must be in the merge queue (or merged).
2. If not, read the head commit's check-runs. A required check-run still `in_progress` whose job is `completed` is a
   propagation fault: run `gh run rerun <run>` once, recorded by `landing_measure.py` as a bounce cause "stuck check-run".
3. A second occurrence on the same PR alerts the operator (mailbox) instead of looping.
4. `prune_worktrees.py --brief` shows the ENQUEUED-but-not-queued state as its own row.

## Golden / drift

A self-test with a stubbed `gh` covers the three states: queued, merged, stuck.

## Landed (wave 1150 group A, 2026-10-22)

Re-probed on the branch first: a pull request with auto-merge on and NOT in the merge queue (PR #385's shape: state
BLOCKED, `ci-gate` in progress) read ENQUEUED in `prune_worktrees.py` with the evidence "is in the merge queue", because
`PullRequest.queued` counted auto-merge as queued; and `enqueue.py` read build-local's
`NOT RUN — another gate holds this worktree's gate lock` as not GREEN, exit 5 GATE RED (PB3511's branch, 12:30; the
`BLOCKED:` line is in `w1147b-PB3511-report.md`). Two mechanisms, one family (one reader per fact):

1. **The queue watch.** `scripts/orchestrator/queue_facts.py` is now THE one reader of GitHub's facts (moved out of
   `prune_worktrees.py`, every caller changed): one GraphQL query for the merge queue's own entries
   (`mergeQueue(branch: "main")`) and every open pull request into main (`isInMergeQueue`, `mergeStateStatus`,
   `autoMergeRequest.enabledAt`, the newest removal event, the head commit's check-runs), plus the jobs API only for a
   REQUIRED context's unresolved check-run (`ruleset.required_contexts`): a check-run in progress whose job completed is
   `stuck`. `land_lane.py tick` watches every exit-0 attempt's pull request (`watch_step`, pure; `watch_queue`) until
   the queue holds it: past `QUEUE_GRACE_MIN` (10) after its required checks' work ended, read 1 re-runs the stuck
   check's workflow run, read 2 closes, reopens and re-queues it (`enqueue.rerun_check`, `enqueue.requeue`: enqueue.py
   stays the only file that queues), read 3 sends the operator a mailbox `question` and stops. Each read is recorded on
   the attempt and as a `stall` in `landing_measure.py` (cause `stuck-check-run`, `not-queued` or `closed`, with its
   read number: a stall, not a bounce, since `bounces` counts failed merge-group runs and `complete` re-reads them).
   The survey gains NOT QUEUED (`prune_worktrees.py --brief` lists it with how long it has waited, GitHub's facts and
   the watch), and a required check that failed before the queue reads BOUNCED (the finisher's), never ENQUEUED.
2. **A held gate lock is BUSY.** The gate driver's verdict for a held lock is `BUSY` (exit 3), and
   `run_gate_legs.read_verdict` is the one reader of a verdict line (GREEN, BUSY or RED); `enqueue.py land` ends a BUSY
   gate `GATE BUSY`, exit 12, with no report line, and the lane retries it at the same head once the worktree's gate
   lock is free (`land_lane.wait_free`), never sending it to a finisher.
