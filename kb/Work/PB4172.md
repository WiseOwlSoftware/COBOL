# PB4172 — A sole figurative ZERO is refused (COBOL0001) wherever the only operand is an arithmetic expression: SET ...

**Sites (as landed, kb/Work PB4120):** `src/WiseOwl.Cobol.Frontend/Parsing/ZeroSignReading.cs` (`Revise`, `Try`), `src/WiseOwl.Cobol.Frontend/Parsing/AdmittedKinds.cs` (`Refusal`). **Sites (as filed):** `src/WiseOwl.Cobol.Frontend/Grammar/CobolParserCore.g4` (`setToValueStatement`, `setSizeStatement`, the SET UP/DOWN BY rule, `allocateStatement`; `primaryExpression` has no figurative arm), `src/WiseOwl.Cobol.Frontend/Grammar/Core/CobolControlFlow.g4` (CONTINUE AFTER), `src/WiseOwl.Cobol.Frontend/Parsing/ZeroTokenRewriter.cs#AZeroWrittenAtIsArithmetic` (ZERO becomes the arithmetic token only by adjacency to an arithmetic operator, the ref-mod colon, or a paren pair around it alone).

The lead's text (PB3428 report, 'New defects' item 1): §8.8.1.1 admits "the figurative constant ZERO (ZEROS, ZEROES)" as an arithmetic expression (with §14.9.39.2 Format 1 arithmetic-expression-1; both checked OK in the report), yet `SET IX TO ZERO.`, `SET IX UP BY ZERO.`, `SET IX DOWN BY ZERO.`, `SET W-N TO ZERO.`, `ALLOCATE ZERO CHARACTERS RETURNING P.`, `CONTINUE AFTER ZERO SECONDS.` draw COBOL0001 at 85 and 2023. `COMPUTE W-N = ZERO` compiles (COMPUTE's boolean arm, PB51). "Cause: `ZeroTokenRewriter` makes ZERO_ARITH only by adjacency, and `primaryExpression` has no figurative arm, so every `arithmeticExpression`-only operand position refuses it."

**Overlap check:** PB51 (landed) fixed COMPUTE alone ("the ONE verb"); no open note holds the other positions (a grep of `kb/Work` for `ZeroTokenRewriter` finds only landed notes). PB3861's `## Landing` documents the related wording fix (COBOL5506 names ZERO only where a ZERO written there parses).

**Unprobed siblings the lead names** (same grammar, not yet probed): RETRY, START ... LENGTH, report SUM / VARYING, B-SHIFT.

**Fix the lead proposes:** make the arithmetic-expression-only positions take a sole ZERO (the root is the missing figurative arm / the adjacency-only rewriter, not each verb). When fixed, COBOL5506 names ZERO at those positions automatically (the parse will take it), so re-pin the `WrittenKindRefusalTests` rows and the `pb3861-*` goldens that currently say "only a numeric literal is expected" at SET positions.

**Probe:** `E:/COBOL-coord/scratch/w20261769c/fin/probe.py`.

**Source:** `E:/COBOL-coord/scratch/reports/w20261769c-PB3428-report.md`, 'New defects' item 1. The report says it shares no root with the implementer's lead 2 (PB4173).

## Landed with PB4120 (wave 20261780 C, 2026-10-30)

One root with PB4120's R1-2: the arithmetic-expression-only slots refused a bare figurative ZERO because the rewriter decides by
adjacency alone. Fixed there, by the parse (ZeroSignReading puts a refused figurative ZERO on trial as ZERO_ARITH), not by a
figurative arm in `primaryExpression` (exponential prediction, the rewriter's reason to exist) or per verb. Every position this
note lists compiles (`ZeroSignReadingTests.ABareZeroInAnArithmeticExpressionOnlySlot_Compiles`), and the re-pin it asked for is
done: `WrittenKindRefusalTests`' SET rows and `pb3861-set-index-to-alphanumeric-literal` now name ZERO. Its unprobed siblings:
RETRY, START ... LENGTH and B-SHIFT compile with a bare ZERO; the report SUM / VARYING slots are the same arithmeticExpression
rule. See PB4120's landing for the probes and witnesses.
