# PB2553

Filed by the train 1037b lander from the wave-1037 group G report (lead 1; PB1943 + PB2520 landed in that train).

**What a user sees.** PB1943 made a sum counter a signed USAGE DISPLAY item (`PicInfo.SumCounterItem`; the representation
is the implementor's, recorded in `docs/CONFORMANCE.md` A.4.11) and admitted reference modification of it. The counter is
ENGINE STATE (`ReportSumCounterPlace`, `Place.OwnsStorageCell == false`), not a declared storage cell, so a reference-modified
store is a decode-modify-encode of the engine's integer through the numeric-image wrap. A store of a NON-DIGIT character —
`MOVE HIGH-VALUE TO CF-T (1:1)` — has nowhere to live: the image is decoded back to a number and the non-digit becomes zero,
silently. For a declared numeric DISPLAY item the same store keeps the invalid byte, and the next numeric use of the item
can raise EC-DATA-INCOMPATIBLE when checking is enabled.

**Repro.** `E:\COBOL-coord\scratch\w1037g\p\ctr.cob` at `--std 2014`.

**Code site.** `src/Cobol.Net.Compiler/CodeGen/Roslyn/PlaceRenderer.cs`, the `NumericImagePlace` write arm (`NumStoreImage`)
over a `ReportSumCounterPlace`.

**Owed.** Either raise EC-DATA-INCOMPATIBLE at the store when the decoded image is not a valid numeric image (the cleaner
answer: the content cannot be represented), or record the loss as a documented determination in A.4.11 with its witness.
The wave-1037 implementer documented it as latitude in A.4.11; that sentence is the current state, not a decision.

## Landed 2026-10-08 (w1045f)

**Re-probed first, on this worktree's build (base 685b44315).** `E:\COBOL-coord\scratch\w1045f\p\ctr.cob` (the note's
`w1037g\p\ctr.cob`) at `--std 2014`: the run ABORTED at `MOVE SPACE TO CF-T` (NotImplementedCobolFeatureException: "MOVE of
an alphanumeric figurative constant … into the numeric item 'CF-T' without image-backed storage") before reaching the
note's `MOVE HIGH-VALUE TO CF-T (1:1)` — a crash sibling of the same root the note did not record. The new golden's
program on the base build: `MOVE "X" TO CF-T (2:1)` then `CF-T (1:4)` read `013D` and `CF-T IS NUMERIC` was true.

**Rule, and the note's suggested fix rejected.** §8.4.3.3.4 GR5: the modified item "is a subset of the data item referenced
by identifier-1", so the stored character IS in the counter; §14.6.13.2 rule 2 sets EC-DATA-INCOMPATIBLE when such content
"is referenced during the execution of a statement", never at the store. Raising the EC at the store (the note's "cleaner
answer") would raise it where the standard does not; documenting the loss would keep a wrong answer. The counter needs a
character cell.

**Fix shape.** The register is IMAGE-CARRIED by determination: `StorageFormPass.Compute` gives every sum family's
register `StorageForm.CharImage(Numeric)`, so `StoreAsImage` is true and every consumer reads and writes it as any
image-carried numeric item (checked decode, the class condition's image test, a figurative fill's plain store, a ref-mod
splice). `PlaceRenderer` renders the place as `CobolReport.SumImage` / `SetSumImage` (`RuntimeApi.ReportSumImage` /
`ReportSumStoreImage`, the old `ReportSumRead` / `ReportSumWrite` and `SumValue` / `SetSumValue` deleted). The engine keeps
its `Int128` accumulation and holds the characters in `SumEntry.Image` while they are not a numeric image; `SumEntry.Add`
reads that content through `CobolNum.ParseImageSending`, so a GENERATE's GR3 addition raises rule 2 too; `Reset` and any
numeric store clear it.

**Sibling sweep.** The other engine-state places (`PlaceStorageCellDriftTests.Views`): PAGE-COUNTER is USAGE BINARY
(`PicInfo.ReportCounterItem`) and takes the general BINARY-receiver figurative-fill loud (`MoveEmitter.FigurativeToNumericImageStore`,
a documented narrow guard, not this mechanism); a CAPACITY register refuses every receiving use but SET (COBOLNET1523);
DEBUG-ITEM and EXCEPTION-OBJECT are not numeric DISPLAY items.

**For the next implementer.**
- `src/Cobol.Net.Compiler/Binding/Passes/StorageFormPass.cs#Compute` — where the counter register's carriage is decided;
  every consumer follows `DataItem.StoreAsImage`, so never special-case the counter in a verb.
- `src/Cobol.Net.Runtime/IO/ReportWriter.cs#SumEntry` (`Image`, `Current`, `ImageOf`, `Store`) — the counter's character
  cell; `SumImage` / `SetSumImage` are its procedure-division face.
- `src/Cobol.Net.Compiler/CodeGen/Roslyn/PlaceRenderer.cs` (`ReportSumCounterPlace` arms) → `RuntimeApi.ReportSumImage` /
  `ReportSumStoreImage`, the profile is `RegisterItem.ProfileName`.
- Trap: a stored item's image ALREADY carried invalid content correctly (`num1.cob`); the counter was the one numeric
  DISPLAY item whose carriage no pass decided, because it is off `Roots`.

**Goldens.** `tests/conformance/85/pb2553_sum_counter_character_cell` (PB2553A, 85 and up: ref-mod store kept, class test,
figurative fill, a numeric store revalidates); `tests/conformance/2002/pb2553_sum_counter_incompatible` (PB2553B: rule 2's
raise on ADD and on the GENERATE addition, the class condition exempt). No negative: the rule has no edition below 85.
