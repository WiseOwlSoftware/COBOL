# PB2553

Filed by the train 1037b lander from the wave-1037 group G report (lead 1; PB1943 + PB2520 landed in that train).

**What a user sees.** PB1943 made a sum counter a signed USAGE DISPLAY item (`PicInfo.SumCounterItem`; the representation
is the implementor's, recorded in `docs/CONFORMANCE.md` A.4.11) and admitted reference modification of it. The counter is
ENGINE STATE (`ReportSumCounterPlace`, `Place.OwnsStorageCell == false`), not a declared storage cell, so a reference-modified
store is a decode-modify-encode of the engine's integer through the numeric-image wrap. A store of a NON-DIGIT character —
`MOVE HIGH-VALUE TO CF-T (1:1)` — has nowhere to live: the image is decoded back to a number and the non-digit becomes zero,
silently. For a declared numeric DISPLAY item the same store keeps the invalid byte, and the next numeric use of the item
can raise EC-DATA-INCOMPATIBLE when checking is enabled.

**Repro.** `E:\COBOL-coord\scratch\w1037g\p\ctr.cob` at `--std 2014`.

**Code site.** `src/Cobol.Net.Compiler/CodeGen/Roslyn/PlaceRenderer.cs`, the `NumericImagePlace` write arm (`NumStoreImage`)
over a `ReportSumCounterPlace`.

**Owed.** Either raise EC-DATA-INCOMPATIBLE at the store when the decoded image is not a valid numeric image (the cleaner
answer: the content cannot be represented), or record the loss as a documented determination in A.4.11 with its witness.
The wave-1037 implementer documented it as latitude in A.4.11; that sentence is the current state, not a decision.
