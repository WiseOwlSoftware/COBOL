# PB3192 — method-scoped TYPEDEF and method-constant LENGTH OF resolve against the object

Source: `w1080e-PB3164-report.md` "## New defects", items 1 and 2 (filed by the clerk, 2026-10-15). The report says they share a root, and PB3164's own body (landed) lists both as untouched siblings of its constant-scope fix. One note, because the root is one rule: a method's declarations must be answered from the method first, and the class-wide tables are read while the method binds. The two sites differ, so the fix must cover both.

**1. A method's TYPEDEF is not method-scoped** (rejects_legal_source, wrong_answer). In `E:\COBOL-coord\scratch\w1080e\p16.cob`, an object `TT TYPEDEF PIC X(2)` plus a method `TT TYPEDEF PIC X(4)` gives a false COBOL1529, and `X TYPE TT` takes 2 positions. A sibling method also sees the type-name. Rule: §8.4.6.2.2 / §8.4.6.2.1, §11.7.4 GR5 (finisher's citations; run `cite.py --check` on each before using it). Site: `DataBinder.cs#RegisterTypeDecl` (`TypeDecls`, one per binder) and the `TryFindTypeDecl` readers, which are post-build (`ExpandTypes`: the owner comes from `ScopeOf(root)`).

**2. A method constant's LENGTH OF resolves against the object** (wrong_answer, silent). In `w1080e\p17.cob`, method `C AS LENGTH OF W` with method `W PIC X(5)` after it and object `W PIC X(3)` prints `A 3` where `A 5` is expected. In `p18.cob` (W before C) it gives a false "not defined". Site: `DataBinder.Constants.cs#LengthOperandItem` calling `ReferenceResolver.FindItem`: method items sit in the class-wide `ByName` during the method's data bind, and `ActiveScope` is null.

**Fix direction** (not designed here). PB3164 introduced `ConstantScopeOf`, the method-first scope for constants (§11.7.4 GR5); route the type-name lookup and the `LENGTH OF` operand lookup through the same one answer instead of a second method-scope mechanism (rules 4 and 5). Goldens: the three repros above, plus a sibling method that must not see the first method's type-name. Sweep other class-wide tables read during a method's data bind (`ByName` readers) for the same shape.

## Wave 1111 group D: re-probed, NOT fixed (handed to a finisher, mechanism boundary)

Re-probed on the Debug build at 4016a67cb: both repros reproduce (E:/COBOL-coord/scratch/w1111d/p/p16.cob: COBOL1529 "duplicate type-name 'TT'" and COBOL1740; p17.cob: prints `A 3 / B 3`, expected `A 5 / B 3`; p18.cob: COBOL1547 "the data-name is not defined"). The group's other four notes landed first; this one is the OO method-scope restructuring and was split off rather than half-done.

**Root, measured.** A method's data entries bind into the class's ONE forest and register their NAMES class-wide (`DataBinder.RegisterName` -> `ByName`, `DataBinder.cs` ~4793 conditions -> `Conditions`, `RegisterTypeDecl` -> `TypeDecls`); `OoScopeSubtree` moves the item and condition names into `OoMethodDataScope` only AFTER the whole method has bound (`DataBinder.Oo.cs:419-424`). While the method binds, `ActiveScope` is `new(ActiveMethodScope)` and `ActiveMethodScope` is null, so every resolver (`ReferenceResolver.FindItem` in `LengthOperandItem`) answers from the class-wide tables: the object's `W` before the method's `W` has bound (p17), an ambiguity once both are bound (p18). TYPEDEF templates never move at all (`TypeDecls` is one dictionary per binder; `TryFindTypeDecl(name)` takes no scope).

**A third symptom of the same root (found this wave, p/q1.cob in the same directory).** A method `01 X TYPE TT` (TT a group TYPEDEF with `05 M`) registers the clone's `M` class-wide in `ExpandTypes` (`CloneItem` -> `RegisterName`, `CloneConditionOnto`), AFTER `OoScopeSubtree` ran, so a SIBLING method's `DISPLAY M` resolves to it with no diagnostic and the backend fails with CS0103 ("The name 'X' does not exist in the current context").

**Design (rule 5: the shape that makes the next case automatic).** (1) Method names register into the METHOD's scope AT BIND: `RegisterName`, the condition registrations and `RegisterTypeDecl` write to `_bindingMethodScope`'s tables when it is set, and to `OoRootOwner[root]`'s scope for a post-build clone (`ExpandTypes`); `OoScopeSubtree`'s name moving is then deleted. (2) `ActiveScope` becomes `new(ActiveMethodScope ?? _bindingMethodScope)`. (3) `OoMethodDataScope.Declares` also asks `Constants.OtherWords`, the method's words DECLARED before any entry binds (`DeclareDataEntries`), so a later-declared method word hides the object's during the bind (p17); `IsDescribedLater` then drives the existing wait/bind-ahead machinery (`BindLaterRecords`). (4) `OoMethodDataScope.TypeDecls` plus one `TryFindTypeDecl(name, Scope, out)` (callers pass `ScopeOf(item.Root)`; register each method template in `OoRootOwner` so a template member's root finds its owner) and one `AllTypeDecls()` for the ~10 enumerations of `TypeDecls.Values` (`DescriptionCompletion.cs:77`, `DataBinder.cs` ExpandTypes, ClauseResolutionForest, TemplateItems, DeclaredForest, WithLapsedType*, LapsedTypeMembers, IndexLapsedTypeMembers); the rule-4 "lapsed member" machinery must be scoped by `Scope` too. `TemplateClauseResolutionDriftTests` and `GlobalNameClassDriftTests` govern these files. (5) Goldens: p16 (accepted: `A ABCD`, `B AB`), p17 (`A 5`, `B 3`), p18 (`A 5`, `B 3`), q1 sibling (refused: M undefined in the sibling), all at 2002+. Do NOT start from `ConstantScopeOf`: it is the constant-only half of the same rule and goes away into the method scope's tables.

## Landed (wave 1112 group A)

Re-probed on the wave-1112 build: p16, p17, p18 and q1 reproduce exactly as recorded above; a new sibling probe
(`E:/COBOL-coord/scratch/w1112a/p/s1.cob`, a method's `01 B SAME AS A` beside an object `A`) printed `A AB` for `A ABCDE`:
`ExpandSameAs` resolved data-name-1 in program scope. The design above was implemented, with one change of shape: the
owner of a name is the owner of its item's ROOT (`DataBinder.NameScopeOf` = `ScopeOf(item.Root).Method`), recorded in
`OoRootOwner` when a method's entry opens the record or type declaration (`BindEntries`' `AttachToHierarchy`, from
`_bindingMethod`), rather than "`_bindingMethodScope` when set": an object item composed ahead DURING a method's bind (a
method constant measuring an object TYPE subject) must register its copies in the object's maps, so the registering scope is
the item's, never the one being bound.

- `RegisterName`, `RegisterIndexes`, the new `RegisterCondition` (the bound entry's and `CloneConditionOnto`'s one insert)
  and `RegisterTypeDecl` ask the owning element; `OoScopeSubtree` is deleted.
- `CurrentMethodScope` (`ActiveMethodScope ?? _bindingMethodScope`) is the one "which method is this reference in" answer
  read by `ActiveScope`, `ActiveMethodDeclares` and `MethodConstants`; `ConstantScopeOf` asks `ActiveMethodDeclares` alone.
- `OoMethodDataScope.TypeDecls`; `TryFindTypeDecl(name, scope, out)`; `AllTypeDecls()` for the whole-forest walks
  (`ExpandTypes`, `ComposeAhead`, `ClauseResolutionForest`, `TemplateItems`, `DeclaredForest`); `TypeDeclsOf(scope)` for
  the own-table check in `ExpandTemplate`; the rule-4 lapsed arms take the method whose tier answered.
- `OoMethodDataScope.Declares` asks `TypeDecls` and `Constants.OtherWords`; `DeclareDataEntries` keeps a type declaration's
  members out of `OtherWords` (§13.18.58.4 GR1), so an unreferenced method template's `M` does not hide the object's `M`.
- `ExpandSameAs` resolves in `ScopeOf(item.Root)`; `IntrinsicBinder.TypeNameArgument` resolves in `ctx.ActiveScope`.

Goldens (`conformance-suite/cases/11.7-METHOD-ID/`): `pb3192_method_typedef_scope`, `pb3192_method_constant_length_scope`
(accepted 2002+), `pb3192-method-type-copy-member-in-sibling` (COBOL1639) and `pb3192-method-type-name-in-sibling`
(COBOL1530), refused 2002, 2014, 2023. Drift test `MethodNameRegistrationDriftTests`; `GlobalNameClassDriftTests`
extended. No inventory row claimed or closed (GR-11.7.4-5 was already OK).

For the next implementer:
- `src/Cobol.Net.Compiler/Binding/DataBinder.Oo.cs#NameScopeOf` — the one "whose name index" answer (owner of the item's ROOT); REUSE it for any new name index a data entry declares, and add the index to `OoMethodDataScope.Declares` (GlobalNameClassDriftTests finds it by reflection).
- `src/Cobol.Net.Compiler/Binding/DataBinder.Oo.cs#CurrentMethodScope` — "which method is this reference in" for statement AND data-division references; trap: `_bindingMethodScope` alone is wrong for an object item composed ahead during a method's bind (its copies belong to the object).
- `src/Cobol.Net.Compiler/Binding/DataBinder.cs#TryFindTypeDecl(name, scope, out)` / `AllTypeDecls` — pass `ScopeOf(entry.Root)` from a post-build pass, `ActiveScope` from a statement; walk `AllTypeDecls()` (never `TypeDecls.Values`) in a whole-forest pass.
- `src/Cobol.Net.Compiler/Binding/DataBinder.Constants.cs#DeclareDataEntries` — `OtherWords` excludes a type declaration's members (13.18.58.4 GR1).
- `src/Cobol.Net.Compiler/Binding/Model/SymbolTable.cs` — the method tier applies the rule-4 lapsed arms with the method's own type declarations (`WithLapsedType*(…, m)`).
