# PB3722 — the PROGRESS line reads the whole dispatch ledger

**Sites:** `scripts/orchestrator/progress.py` (`progress`: the loop over `plan_wave.ledger_groups`), `scripts/orchestrator/plan_wave.py` (`ledger_groups`, `answers`, the retirement rule PB2795 gave every other reader), `scripts/orchestrator/orchestrate.ps1` (the PROGRESS and STALL calls).

## What happens

At 10:23:50 on 2026-10-25 the campaign unit's first PROGRESS line read "groups running 8, DONE reviewed CLEAN 6 … oldest waiting: w20261031g (PB3636) 1068 min on running" and posted a STALL to the operator's mailbox. Wave 20261107 had dispatched 7 groups ten minutes earlier and none had returned. The eighth "running" group, w20261031g, was killed by the operator's 2026-10-24 16:39 STOP before its first commit: it left no report and no commit (`git log --all --grep PB3636` finds only the note's filing), and the branch survey pruned its empty branch as LANDED. The six "CLEAN" groups are ledger entries from waves 1082 to 1138 (1082C PB3160, 1101Z PB3291, 1113A PB3353, 1128A PB3420, 1134A PB3463, 1138y PB3487), weeks old, kept because their notes are still open. The operator released w20261031g by hand (`plan_wave.py --release 20261031g`).

`progress.progress` walks every ledger entry. An entry no report answers counts RUNNING and, past 60 minutes, a STALL; an entry a report answers counts by that report's verdict, however old. PB2795 retired a report-answered group for every other reader (the planner, the landing check, the survey); progress.py, added by PB3638, is a new reader that does not follow that rule. The owner's progress report (PB3638: "report progress every event") therefore misstates the unit's work in both directions.

## Fix direction

One rule for every reader: progress counts the groups the CURRENT wave or unit dispatched (the ledger's `at` after the unit's start, or the wave the unit launched) plus any older group still unlanded and not retired by PB2795's rule, and a DONE group counts CLEAN-awaiting-landing only while its branch is not on main. A group whose agent died without a report (a STOP before its first commit) is the PB3040 retention face: the wave's STOP wind-down must write a SPLIT report or release the entry, so it is answered or gone. Self-tests: a killed group with no report and no branch reads neither RUNNING nor STALL once its unit ends; a weeks-old answered group is not counted; the unit's own groups are.
