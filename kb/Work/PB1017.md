# PB1017 — LANDED

## Landed (2026-09-22, wave 54 group H)
Re-probed on the implementer's own build: PB974 had already widened the old check to every kind's AS literal, so the
AS half no longer reproduced; what DID reproduce was everything else the rule compares. SR1 was keyed on (kind, name)
and compared only the externalized name, so a repeated class-specifier with a different EXPANDS USING list, a name
specified as a CLASS and as an INTERFACE, and `FUNCTION F INTRINSIC` beside `FUNCTION F` were all accepted — and the
externalized-name comparison made `CLASS X` beside `CLASS x` (one user-defined word, §8.3.2) a false difference.

**Fix.** ONE check, `DataBinder.CheckRepositorySpecification`, keyed on the NAME (case-folded) across every kind the
rule lists, comparing a `RepositorySpecification` record — kind, AS literal (null when absent), canonical EXPANDS text —
by record equality; the intrinsic-function-name-1 list of `FUNCTION … INTRINSIC` now reaches it. COBOLNET1761, the
code the rule already reported under. Docs: INTERPROGRAM §D2 step 1, OO §AS-phrase paragraph, CONFORMANCE DOC-A.1-163.

**Goldens.** `conformance:2002/pb1017_repository_identical_repeats` (identical repeats in two case spellings, an
EXPANDS twice, an intrinsic twice — compiles and runs); `conformance:negative/pb1017-repository-specification-not-identical`
(the three different-repeat shapes, COBOLNET1761). The EXPANDS shape also draws the pre-existing COBOLNET2240 (§9.3.12).

## The rule
`OK  §12.3.8.3 1)` — "If any object-class-name-1, interface-name-2, program-prototype-name-1, function-prototype-name-1,
intrinsic-function-name-1 or property-name-1 is specified more than once in the REPOSITORY paragraph, all the
specifications for that name shall be identical."

## What the fixer owes
One repeated-specifier comparison over every specifier kind, comparing the whole specification (AS literal, EXPANDS
class and its USING list, FUNCTION … INTRINSIC), in place of the PROGRAM-only check. Negative goldens per kind.
