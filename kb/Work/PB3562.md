# PB3562 — a boolean function sender in a group MOVE copies its text carrier

## Scenario

`01 G USAGE BIT. 05 GB OCCURS 8 TIMES PIC 1.` is an ALPHANUMERIC group: a group-level USAGE applies only to the elementary
items under it. `MOVE FUNCTION BOOLEAN-OF-INTEGER(255 8) TO G` is a group move, and a group move copies the sender's
representation with no conversion. WiseOwl copies the function value's '0'/'1' TEXT instead, so the first character '1'
(0x31) lands as the bits 00110001. Found by the B1 adjudicator (fz01430, fz02128, fz04225) and, from the GnuCOBOL side
(GnuCOBOL 3.2 cannot run the function), by the D1 adjudicator on the same programs.

- §14.9.25.4 4) (OK): a move that is not an elementary move "is treated exactly as if it were an alphanumeric to

## Actual (judge e7cf38ce4)

B1 probe: `ITEM-TO-GROUP [11111111]`, `FUNC-TO-GROUP [00110001]`, `FUNC-TO-BITGRP [10100101]`. D1 probe: `ITEM [0000|0001]`,
`FUNC [0011|0000]` (the byte stored is 0x30, the character '0').

What the probes rule out: the same move from a `PIC 1(8) USAGE BIT` item holding the same value is right; the function moved
into a `GROUP-USAGE BIT` group is right; a NATIONAL function moved into an alphanumeric group is right (`adj\B1\probes\natgrp`).
Only a boolean function sender into an alphanumeric group move is wrong.

## Mechanism and code site

`src/Cobol.Net.Compiler/CodeGen/Emit/OperandText.cs:276` (the `_ => AsString` arm of `NonElementaryMoveSender`), reached from
`src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs:441` (`EmitGroupMove`). `NonElementaryMoveSender` sends a
`BoundFieldOperand`'s storage image, but every other operand (a function) as `AsString`, the boolean carrier's '0'/'1' text.
For a usage-bit value that text is a representation conversion, which GR4 forbids.

## Witnesses

fz01430, fz02128, fz04225 (group receivers; fz02127 and fz03526 move into elementary items and are right). Slice B1
(`OUTPUT_DIFFERS:15.13`, 5 programs) and slice D1 (`THEY_FAIL_RUN:15.13`, 5 programs) are the same set.

- A boolean LITERAL sent to the same group takes the same arm (`B"00000001"` also stores 0x30, per the D1 adjudicator); §8.3.3.4

- Golden: the B1 probe as a conformance case with the derived output, plus a CALL BY CONTENT leg to a group formal and a
  boolean-literal leg; a drift test that no group-move sender channel converts a usage-bit operand to text.

## Orchestrator decision

GR4 of §14.9.25.4 makes a move to a group an alphanumeric-to-alphanumeric move with NO conversion of internal representation; an elementary bit SENDER already copies its bit image (ITEM-TO-GROUP [11111111]), so the function sender must too. Sibling sweep for the implementer: every caller of `OperandText.NonElementaryMoveSender` (MoveEmitter.cs:307/327/358/441/639, CallEmitter.cs:450 CALL BY CONTENT to a group formal) with a boolean AND a national function sender (the national arm was probed correct, `adj\B1\probes\natgrp`).

## Landed — the temporary was the function's DISPLAY twin, and four sibling lanes shared the text carrier

**Re-probe (own build, Debug).** The B1 probe printed `FUNC-TO-GROUP [00110001]` and the D1 probe `FUNC [0011|0000]`, as filed.
The note's mechanism line was one step short: `NonElementaryMoveSender` never saw the function. `MoveBinder` freezes a
character-category function sender into `SendingValueTemp`'s run-time-length carrier (§14.9.25.4 GR1, `NeedsLengthFreeze`),
and that carrier's usage came from `CharacterUsage`, which answered NATIONAL for a national function and DISPLAY for
everything else, a boolean function included. So the sender reaching the group move was a boolean item of usage DISPLAY,
whose storage image is its '0'/'1' text. (A national function was right for that reason: its carrier is usage national.)

**Fix, one rule in each place it lives.**
1. `SendingValueTemp.CharacterUsage`: a boolean function's returned value is "a boolean item of usage bit" (§15.13.4 1),
   §15.2 2)), so its temporary is usage BIT. `OperandText.ElementaryCharacterImage` packs a run-time-length usage-bit
   carrier with `BitsPackAll` (a function result's or a reference-modified slice's intermediate has no PICTURE length).
2. `OperandText.NonElementaryMoveSender`: a literal or function VALUE whose usage is national or bit (read through the one
   reader, `IntrinsicArgumentRules.StaticUsageOf`; the shapes that reach the sender un-materialized: every literal, and a
   function whose temporary the binder did not make) sends its representation: `NatBytes` for usage national,
   `BitsPackAll` for usage bit. The national literal arm is a second defect of the same arm: `MOVE N"EF" TO G` deposited
   the alphanumeric bytes 'E' 'F'.
3. The CALL / INVOKE boundary into a KNOWN plain-group formal (`CallEmitter.IsPlainGroupFormal`: a Format-2 CALL, a CALL AS
   NESTED, a user-defined function, an INVOKE method) reads the same codec: a USAGE BIT / USAGE NATIONAL argument
   (`OperandText.CarrierDiffersFromStorage`, also a bit or national group), a national literal and a boolean or national
   function value cross as their storage image, not their operand text. Measured before: `CALL .. AS NESTED USING BY
   CONTENT E8` (PIC 1(8) USAGE BIT, B"10100101") into an alphanumeric group of eight bit items arrived as 00110001, and
   INVOKE the same.

**Determination D-B3 (docs/CONFORMANCE.md):** a boolean LITERAL has no stated usage (§8.3.3.4.4 GR3 gives its value only) but
is written as characters of the coded character set (§8.3.3.4.3 SR2), so it stays usage DISPLAY, which `StaticUsageOf`
already answered every argument screen: `MOVE B"01100110" TO G` deposits the eight characters, while a boolean function
value deposits one packed byte. (Packing the literal was the first reading and was dropped: it made one literal two usages.)

**Goldens:** `cases/14.9.25-MOVE/pb3562_group_move_function_values` (+ `pb3562_group_move_function_below_2002`, refused at 85
with COBOLNET1502), `cases/14.2-Procedure-division-structure/pb3562_content_group_formal_usage_values`,
`wiseowl/cases/14.9.25-MOVE/pb3562_boolean_literal_group_move`.

**Not landed (a lead, same root: the CALL boundary's alphabet for an elementary usage-bit / usage-national argument).** A
Format-1 CALL whose activated program the site does not see (no program-specifier, or one in the REPOSITORY that is
defined later: `LandsAtRunTime`) crosses the argument as its operand-text cell, and a plain-group formal copies that cell
as the group's characters: `CALL "SUBG" USING BY CONTENT E8` into the alphanumeric group of eight bit items still arrives
as 00110001 (GR9's first branch makes the record "of the same length as the argument", moved "without conversion", so its
storage image is what the group formal should see). The fix needs the cell to carry both alphabets (the elementary
formals read the operand text, a group formal the storage image), i.e. a change to `MoveSending` / `MoveLanding` and the
first-branch cell, which is an ABI design beyond this slice.

### For the next implementer (orient.py's LEARNED lines)
- `src/Cobol.Net.Compiler/Binding/Procedure/SendingValueTemp.cs#CharacterUsage` - the usage of a function result's temporary
  (national -> national, boolean -> BIT, else DISPLAY); the trap: a boolean function's temp was DISPLAY, so the group move
  copied its text, and the note's `NonElementaryMoveSender` line never saw the function at all (MoveBinder had frozen it).
- `src/Cobol.Net.Compiler/CodeGen/Emit/OperandText.cs#NonElementaryMoveSender` - the ONE sending codec of a non-elementary
  MOVE and of a known-group-formal crossing; its last arm is keyed on `IntrinsicArgumentRules.StaticUsageOf` (REUSE it, never
  a category test: NationalUnitDriftTests refuses PicCategory.National alone). `CarrierDiffersFromStorage(Place)` asks the
  same reader of a place; `ElementaryCharacterImage` packs a run-time-length usage-bit carrier with `BitsPackAll`.

  formal that is a group but not an as-if-elementary bit or national group; `BoundCallArg.Formal` is null for a Format-1 CALL,
  whose cell is still the operand text (the lead above). `OoEmitter` reads the same predicate for a method formal.
