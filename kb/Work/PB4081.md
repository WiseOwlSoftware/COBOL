# PB4081 — a branch that adds a `work.py check` rule meets the notes main gained since its base only at the merge-in

**Sites:** `scripts/spec/work.py` (`check`, `sites_problems`), `scripts/orchestrator/enqueue.py` (`land`)

**Witness.** Branch `worktree-wf_484eb705-564-32` (PR #791, PB3797 and PB3836) adds two `work.py check` rules: `process_only` on a note whose Sites are under `src/`, and a code file named without members. The branch was gated green on its own tree. `enqueue.py land` merged origin/main in and the gate's WORK REGISTER audit went RED (run 000003-20261030T001302Z, `=== ENQUEUE: GATE RED (Windows) on 5429a189f6fe ===`): three notes main gained after the branch's base, PB4073, PB4074 and PB4068, broke the new rules. The finisher repaired them (`e1b97d1ed`). The merge also brought in main's PB4053, whose Sites named `check_practices.py` for the member `inflight.collision`, which lives in `scripts/orchestrator/inflight.py`; it was repaired the same way.

**Not PB4053, not PB3389.** The finisher's shorthand "the PB4053 shape" names one of the offending notes, not the mechanism: PB4053 is about the wave planner colliding keyed-table files by file. PB3389 (landed) is one stored field, `blocked`, going stale against the notes ahead of a branch in the merge queue. This mechanism is general: a rule a branch adds is checked on the branch's own tree only, so every note filed on main between the branch's base and its landing is checked first at the merge-in, costing a gate round and a finisher's hand repair. A search of `kb/Work/` for an open owner found none.

**Fix direction (recorded, not decided).** A rule cannot know a note that does not exist yet, so the failure cannot move earlier; it can be made cheap. When the branch's diff changes `work.py`'s rules, the landing's merge-in runs `work.py check` once on the merged tree before the gate slot is taken and prints each offending note id with its rule, so the repair is one named edit. A rule that tightens existing notes should also be scoped the way PB3263 scoped `SITES_REQUIRED_FROM`, so a note filed after the base is not suddenly in breach.
