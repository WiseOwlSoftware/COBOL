# PB2517

Filed from the PB2071 refuter (`E:\COBOL-coord\scratch\w1033-adj\PB2071-refute.md` section 5, probe `r13u`; flags under-rejects, silent). No kb/Work note covers it (the refuter searched).

**Repro (compiles clean at 2002, 2014, 2023).**

    01 U IS TYPEDEF STRONG.
       05 G VALUE "AB".
          10 A PIC X.
          10 B PIC X.
    01 V TYPE U.

**Expected from the spec (cite.py --check OK).** V.G is a group subordinate to a TYPE-STRONG subject, hence a strongly-typed group item (`§8.5.3.1`, second arm). It carries the VALUE by `§13.18.58.4 GR3`, so `§13.18.63.3 SR1` ("The subject of the entry shall not be a strongly-typed group item or a variable-length group") is violated (informative D.8.3 5) agrees). Control `r17` (`01 W TYPE S VALUE "AB"`, the first arm) is rejected COBOLNET1703.

**Mechanism and site.** `CheckGroupValueDeclarations` skips the clone because `IsGroupValueSubject` excludes `ValueIsCopied` (`src/Cobol.Net.Compiler/Binding/DataBinder.GroupValue.cs:249-250`), and the template's G is not strongly typed (`StrongRoot` is null without a TYPE clause), so the "screened where it is declared" promise never fires. Provenance dedupe may suppress only a predicate the template could already answer, never one that becomes true only on composition (the same hazard as in PB2071's fix shape). The inventory row `SR-13.18.63.3-1` is CONFORMS and must be re-verdicted with the fix. Related: `PB2071`.

## Landed - wave 1037 group E, 2026-10-07

Re-probed on a fresh Debug build (the repro compiled clean at 2002 and 2023, the first-arm control `01 W TYPE S VALUE "AB"` drew COBOLNET1703). Root cause as filed: `CheckGroupValueDeclarations` took "the template answered for the assumed VALUE" as true of every predicate, but SR13 and SR14 are properties of the entry that WROTE the clause while SR1 is a property of what the subject IS. A TYPEDEF STRONG template's group is not a typed item (8.5.3.1: strongly typed means described with, or subordinate to an item described with, a TYPE clause naming a STRONG declaration), so SR1 is false in the template and becomes true only when a TYPE reference composes it.

Fix: `DataItem.ValueIsCopied` (a bool) became `DataItem.ValueCopiedFrom` (the entry the VALUE was copied from; written by the one `CopyEntryDescription`), because the suppression must depend on what the SOURCE already was. The screen's new `ScreenAssumedGroupValueSubject` asks SR1 of every assumed group VALUE and stays silent only when `Sr1SubjectShape(source)` is already non-null, so a chained declaration (`01 S2 TYPEDEF STRONG TYPE S`) is reported once where the strength is composed and a SAME AS of an already-reported entry draws no second verdict. The verdict is anchored at `StrongTypeModel.StrongRoot` (the entry whose TYPE clause composed the strength), not the nearest TYPE clause. Shapes covered: VALUE on a group under a strong template, VALUE on the template root, strong through an outer TYPE clause with a weak inner one.

Witnesses: negatives `pb2517-group-value-in-strong-type-reference`, `pb2517-group-value-on-strong-typedef-root`, `pb2517-group-value-in-nested-type-of-strong-record`; positive `2002/pb2517_group_value_in_weak_type_ok`. Row `SR-13.18.63.3-1` stays CONFORMS and is now true; closed by batch `w1037e-PB2517-sr-13.18.63.3-1`. Left alone: an UNREFERENCED strong template holding a group VALUE still compiles clean (the template is not a typed item), which is the same open question as PB2071's REDEFINES-in-unused-strong-typedef.
