# PB601 — RETIRED — fixed by PB392: the rule names a set, and the screen now asks the set

Found 2026-09-05 by the `PB236` implementer (its report §12 C), which landed SR6's "both operands shall be group
items" and "shall not be described with level-number 66" arms as COBOLNET1757 and measured that the group-KIND
half of the sentence is not enforced. The row moves here from PB236 so PB236 can land whole. Re-derived on this
tree for this note.

## The rule

§14.9.2.3 SR6 (quoted from `specs/ISO_COBOL.md`; `cite.py --check 14.9.2.3 "Identifier-4 and identifier-5 shall
be alphanumeric group items, national group items, variable-length groups, or strongly-typed group items and
shall not be described with level-number 66."` is the fix's first step): the operand of ADD CORRESPONDING is one
of FOUR named group kinds. §14.9.44.3 (SUBTRACT) carries the same sentence. A BIT group (`GROUP-USAGE BIT`) is a
group item §14.7.6's D1/D2 correspondence would pair, and it is not in SR6's set.

## The mechanism

`StatementValidation`'s CORRESPONDING operand screen (PB236) tests `IsGroup` on each operand, which is true for a
bit group. The case is unreachable today only because a bit group does not yet bind as a CORRESPONDING operand
(the data-model gap the same note records), so nothing observable is wrong — but the screen encodes a boolean
where the rule names a set (`feedback_model_the_rule_shape_not_one_case`), and it will admit the bit group the day
the data model does.

## Fix shape

Replace the `IsGroup` test with a group-KIND predicate over the four names SR6 lists (alphanumeric group,
national group, variable-length group, strongly-typed group), shared by ADD and SUBTRACT; a negative golden for a
`GROUP-USAGE BIT` operand once the data model binds it (until then a unit test over the predicate with a bit
group `DataItem`), and the row re-verdicted CONFORMS with both sides witnessed.

## Re-probed and retired — wave 1001 group D (w1001d)

**Re-probed first** on the w1001d Debug build of `b62408c25`: `01 SRC GROUP-USAGE BIT. 05 P PIC 1(4).` with a twin
`DST`, then `ADD CORRESPONDING SRC TO DST` and `SUBTRACT CORRESPONDING SRC FROM DST` are both REFUSED at compile time,
once per operand: `COBOLNET1757: ADD CORRESPONDING operand 'SRC' is a bit group item (ISO §13.18.29.4 GR1) — the
operands shall be alphanumeric group items, national group items, variable-length groups, or strongly-typed group
items (ISO §14.9.2.3 SR6)` (and the §14.9.44.3 SR6 twin). `ADD CORRESPONDING` over two `GROUP-USAGE NATIONAL` groups is
ADMITTED, as SR6 lists that kind. The note's premise ("unreachable today only because those categories do not yet bind
as CORRESPONDING operands") is out of date: kb/Work PB392 (`4f1c8cacb`, "a group KIND is a set") replaced the
`IsGroup` boolean with `ItemCategory.GroupKindsOf`, the group-kind predicate the "Fix shape" above asks for, shared by
ADD and SUBTRACT (`StatementValidation.CheckCorrespondingGroupOperand`), and witnessed both sides
(`conformance:negative/pb392-subtract-corresponding-bit-group`, `conformance:negative/pb236-add-corr-elementary`,
`conformance:2002/pb392_corresponding_group_kinds`, `GroupKindDriftTests`). The inventory row `SR-14.9.2.3-6` is already
CONFORMS with PB392's witnesses, so this note's claim on it was stale. Nothing to implement.
