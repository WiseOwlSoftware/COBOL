## Finding — pop-directive (under-rejects)

The PUSH/POP directive-name admissible set (CompilerDirectiveCatalog.OperandDirectiveNames) is derived from every catalog row regardless of edition, so the two directives removed at 2023 (FLAG-85, FLAG-NATIVE-ARITHMETIC) are accepted as directive-name at 2023 - the only edition where PUSH/POP exist.

**Rows:** SR-7.3.20.3-1

**Repro:**

```
--std 2023:
       >>PUSH FLAG-85
       IDENTIFICATION DIVISION.
       PROGRAM-ID. POPP3.
       PROCEDURE DIVISION.
           DISPLAY "A"
           STOP RUN.
       >>POP FLAG-85
(probe/popdir/p3.cob) -> compiles clean, prints A; COBOLNET1911's own message lists FLAG-85 and FLAG-NATIVE-ARITHMETIC as admissible.
```

**Expected from the spec:** §7.3.20.3 SR1: directive-name 'shall be the name of a compiler directive'; Annex E.2 item 21 removed FLAG-85 and FLAG-NATIVE-ARITHMETIC in 2023, so neither names a compiler directive at 2023 -> COBOLNET1911 on both lines (same for §7.3.22.3 SR1 on PUSH).

**Observed:** OperandDirectiveNames returns Words minus the ExcludedDirectives rows with no StatusAt(edition) filter; PushableRows/PushableRowOf likewise include flag-85-directive-window and flag-native-arithmetic-directive-window (DirectiveStateRegistry records them as 'NONE HELD ... no source may contain both', overlooking the operand).

**Code site:** src/Cobol.Net.Editions/CompilerDirectiveCatalog.cs#OperandDirectiveNames (and PushableRowsLazy)

## Finding — pop-directive (under-rejects)

No stage applies the NAMED directive's own placement rule to a PUSH/POP naming it: a >>POP (or >>PUSH) directive-name is screened only as a word, never for position, so a POP of LEAP-SECOND, PROPAGATE or COBOL-WORDS inside a compilation unit is accepted silently though the named directive there is rejected.

**Rows:** SR-7.3.20.3-2

**Repro:**

```
--std 2023:
       IDENTIFICATION DIVISION.
       PROGRAM-ID. POPP1.
       PROCEDURE DIVISION.
       >>PUSH LEAP-SECOND
           DISPLAY "A"
       >>POP LEAP-SECOND
           DISPLAY "B"
           STOP RUN.
(probe/popdir/p1.cob) -> clean, prints A B; the same position with >>LEAP-SECOND ON gives COBOLNET1650. Likewise >>POP PROPAGATE / >>POP COBOL-WORDS in the procedure division (p5.cob) are clean while >>COBOL-WORDS there is COBOLNET1623.
```

**Expected from the spec:** §7.3.20.3 SR2: 'the POP directive shall not be specified where directive-name must not be specified' - with §7.3.17.3 SR1 (LEAP-SECOND not within a compilation unit), §7.3.21.3 SR1 (PROPAGATE not within a compilation unit), §7.3.10.3 SR1 (COBOL-WORDS only before the first IDENTIFICATION DIVISION) -> a diagnostic on each such POP line (and each such PUSH line, §7.3.22.3 SR2).

**Observed:** DirectiveSiteProcessor records DirectiveSite(Line, Word, AllForm) with no named row; PushPopAllPlacementPass checks ALL only; the per-directive placement checks (COBOLNET1650, COBOLNET1623) live in their own stages keyed on their own directive word. Structural fix: each directive row carries its placement rule as data so a PUSH/POP naming the row inherits it.

**Code site:** src/Cobol.Net.Frontend/Preprocessor/DirectiveSiteProcessor.cs#Process; src/Cobol.Net.Compiler/Validation/PushPopAllPlacementPass.cs

## Finding — push-directive (under-rejects)

PUSH/POP directive-name operand set is derived from the edition-independent directive catalog, so directives REMOVED in 2023 (FLAG-85, FLAG-NATIVE-ARITHMETIC) remain admissible directive-names at 2023, the only edition in which PUSH/POP exist

**Rows:** SR-7.3.22.3-1

**Repro:**

```
--std 2023 (default): IDENTIFICATION DIVISION. PROGRAM-ID. A10. PROCEDURE DIVISION. >>PUSH FLAG-85 (at column 8) DISPLAY "OK". STOP RUN. -> compiles clean and prints OK; same for >>PUSH FLAG-NATIVE-ARITHMETIC. >>FLAG-85 ON in the same program draws COBOLNET0902 (removed in 2023). COBOLNET1911's own message lists FLAG-85 and FLAG-NATIVE-ARITHMETIC among the admissible names.
```

**Expected from the spec:** §7.3.22.3 SR1 restricts directive-name to 'the name of a compiler directive'; §E.2 item 21 removed FLAG-85 and FLAG-NATIVE-ARITHMETIC from the 2023 standard, so at 2023 neither word names a compiler directive and >>PUSH FLAG-85 shall be diagnosed as a malformed operand (as >>PUSH FOO is). The same holds for >>POP (§7.3.20.3 SR1, sibling).

**Observed:** CompilerDirectiveCatalog.OperandDirectiveNames returns Words (the whole catalog map keys) minus the ExcludedDirectives rows, with no edition filter; the flag-85-directive-window and flag-native-arithmetic-directive-window rows (removed 2023) are in the map. PushableRows (the PUSH ALL set, §7.3.22.4 GR2) is derived the same way and also includes them. Fix shape: derive the operand directive-name set from the rows that are LIVE in the target edition (the same edition gate the recognition point already applies), so a removed row drops out automatically; pair with a drift test that every name admitted at edition E is a directive recognized at E.

**Code site:** src/Cobol.Net.Editions/CompilerDirectiveCatalog.cs#OperandDirectiveNames (line ~155) and #PushableRows

## Finding — push-directive (under-rejects)

No stage applies the placement rule of the NAMED directive to a >>PUSH directive-name (and, by the identical SR2, to >>POP directive-name): the operand screen checks the word only

**Rows:** SR-7.3.22.3-2

**Repro:**

```
--std 2023: IDENTIFICATION DIVISION. PROGRAM-ID. B1. PROCEDURE DIVISION. >>PUSH LEAP-SECOND DISPLAY "OK". STOP RUN. -> compiles clean, prints OK. Replacing the directive line with >>LEAP-SECOND ON draws COBOLNET1650 (§7.3.17.3 SR1). >>PUSH PROPAGATE at the same place also compiles clean.
```

**Expected from the spec:** §7.3.22.3 SR2: 'If directive-name is specified, the PUSH directive shall not be specified where directive-name must not be specified.' LEAP-SECOND (§7.3.17.3 SR1) and PROPAGATE (§7.3.21.3 SR1) shall not be specified within a compilation unit, so >>PUSH LEAP-SECOND / >>PUSH PROPAGATE inside a compilation unit are syntax-rule violations; written before the first IDENTIFICATION DIVISION they are legal (and do compile clean today).

**Observed:** The placement rule lives only inside the individual directive's stage (LeapSecond's COBOLNET1650) or nowhere (PROPAGATE's §7.3.21.3 SR1 is a documented unenforced limitation in PropagateDirectiveProcessor), so a PUSH/POP naming the directive cannot inherit it. Fix shape: make each directive row's placement restriction DATA on the construct row (e.g. 'not within a compilation unit', 'not within an exception-checking PERFORM'), enforced once at the position-aware site pass (the DirectiveSiteProcessor / PushPopAllPlacementPass seam that already knows compilation-unit boundaries for SR3), and apply it both to the directive itself and to a PUSH/POP whose directive-name selects that row. That also closes PROPAGATE's own SR1 and makes a new restricted directive automatic; drift test: every row with a placement restriction draws its diagnostic both bare and via >>PUSH/>>POP <name>.

**Code site:** src/Cobol.Net.Editions/CompilerDirectiveCatalog.cs#OperandDiagnostic (word-only check); src/Cobol.Net.Frontend/Preprocessor/DirectiveSiteProcessor.cs; src/Cobol.Net.Compiler/Validation/PushPopAllPlacementPass.cs; src/Cobol.Net.Frontend/Preprocessor/PropagateDirectiveProcessor.cs (unenforced §7.3.21.3 SR1)

## What the fixer owes (and the sibling sweep)

Derive the admissible set from the catalog rows AVAILABLE at the target edition; attach each catalog row's placement rule as data and have `DirectiveSiteProcessor` / `PushPopAllPlacementPass` apply the named directive's rule to PUSH/POP naming it (PB1378 gives LEAP-SECOND/PROPAGATE their rule). Negative goldens: `>>PUSH FLAG-85`; `>>POP LEAP-SECOND` inside a unit.

**Rows claimed:** SR-7.3.20.3-1, SR-7.3.20.3-2, SR-7.3.22.3-1, SR-7.3.22.3-2
