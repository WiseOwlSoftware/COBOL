**Rule it breaks:** One rule in one place / one mechanism per job (DESIGN-architecture-review §5.2; dimensions.md 4). RecordFraming's own summary calls itself 'THE ONE on-disk record framing' and FrameBytes 'THE ONE size formula', yet only the ENCODE side is single (FrameWord, EncodeExtentTable); the DECODE side is written once per caller, plus a second char-shaped copy of the word and table decoders (CharWord, PrefixLength, ExtentCount, ExtentTableFromChars beside BinaryPrimitives and DecodeExtentTable).

**Scenario:** A RECORD VARYING record-sequential file whose last frame is torn (a run unit killed mid-WRITE, a file copied short): SequentialConnector.NextFrame reads the prefix, allocates new char[len], FillChars returns fewer characters and the short payload is DELIVERED as record N+1, while FrameStarts - which feeds ExistingRecordCount (the OPEN EXTEND released ordinal and the REVERSED record count) and the READ PREVIOUS index _varyingStarts - breaks on 'a torn tail ends the store' and says N; ReadStore says N too. A forward READ loop and a backward READ of the same file see different record populations. A length word 0xFFFFFFFF after a valid first frame: StreamFramingParses admits the OPEN (it tests only the first word), FrameStarts counts it as a zero-length frame, and NextFrame's PrefixLength returns int.MaxValue so new char[int.MaxValue] throws OutOfMemoryException. A huge extent count: DecodeExtentTable bounds it against the bytes present, FrameStarts skips 8L*count, NextFrame allocates new char[8*count] from ExtentCount's int.MaxValue/8 clamp before reading anything. Every future frame property (a new flag bit, a stream-shape version) has to be added to four decoders in two encodings with nothing forcing them to agree.

**Target:** One frame-head decoder in RecordFraming over bytes - e.g. TryReadFrameHead returning Gap | Frame(payloadLength, extents, headBytes) | Torn, with ONE torn-tail rule, ONE gap rule, and FrameBytes/ExtentTableBytes as the one size formula - called by ReadStore, FrameStarts, StreamFramingParses and by the variable RecordCodec that §8.3 extracts from SequentialConnector (R0-0011). The char-shaped decoders (CharWord, PrefixLength, ExtentCount, ExtentTableFromChars) and the char encoder WriteWord are deleted: the variable codec reads its frame head as bytes (or converts the Latin-1 head chars to a byte span once) and calls the same decoder. The torn-tail and gap answers for a stream file are decided once, the oracle differential shows any output change, and a drift test pins that every frame reader reaches the one decoder.
