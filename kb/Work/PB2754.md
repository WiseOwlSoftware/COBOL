**Scenario:** A RECORD VARYING record-sequential file whose last frame is torn (a run unit killed mid-WRITE, a file copied short): SequentialConnector.NextFrame reads the prefix, allocates new char[len], FillChars returns fewer characters and the short payload is DELIVERED as record N+1, while FrameStarts - which feeds ExistingRecordCount (the OPEN EXTEND released ordinal and the REVERSED record count) and the READ PREVIOUS index _varyingStarts - breaks on 'a torn tail ends the store' and says N; ReadStore says N too. A forward READ loop and a backward READ of the same file see different record populations. A huge extent count: DecodeExtentTable bounds it against the bytes present, FrameStarts skips 8L*count, NextFrame allocates new char[8*count] from ExtentCount's int.MaxValue/8 clamp before reading anything. Every future frame property (a new flag bit, a stream-shape version) has to be added to four decoders in two encodings with nothing forcing them to agree.

**Target:** One frame-head decoder in RecordFraming over bytes - e.g. TryReadFrameHead returning Gap | Frame(payloadLength, extents, headBytes) | Torn, with ONE torn-tail rule, ONE gap rule, and FrameBytes/ExtentTableBytes as the one size formula - called by ReadStore, FrameStarts, StreamFramingParses and by the variable RecordCodec that §8.3 extracts from SequentialConnector (R0-0011). The char-shaped decoders (CharWord, PrefixLength, ExtentCount, ExtentTableFromChars) and the char encoder WriteWord are deleted: the variable codec reads its frame head as bytes (or converts the Latin-1 head chars to a byte span once) and calls the same decoder. The torn-tail and gap answers for a stream file are decided once, the oracle differential shows any output change, and a drift test pins that every frame reader reaches the one decoder.

**Design reference:** §8.3.

**The wave's contract:** every caller changes in the same change (CLAUDE.md rule 4: no alias, shim or forwarder); the drift test that pinned the thing goes with it, or a new boundary gets one; the §4 oracle (`python scripts/arch/compare_oracle.py`) proves neutrality; a change that changes behavior is a `kind: defect` lead for the fix lane, never part of the wave (PB2119).

**Landed (wave 1092 F).** Re-probed first on the worktree's own build with a RECORD VARYING sequential READ loop
over crafted files (`E:\COBOL-coord\scratch\w1092\w1092f\probe`): a torn last frame was delivered as record 3
(`[PART] 00`), and a gap word or a huge extent-table count after two good frames ended the run unit with
`Out of memory.` — the scenario reproduced exactly.

The fix is the target: `RecordFraming.ReadFrame<TMedium>` is the ONE frame decoder (the gap rule, the torn-tail
rule, and `IFrameMedium.Holds` asked before anything is sized by a count read from the medium), and
`EncodeFrameHead` / `EncodeGap` / `EncodeExtentTable` the one encoder. Three media read through it —
`ImageMedium` (`DecodeStore`), `StreamMedium` (`FrameStarts`, `StreamFramingParses`) and the sequential
connector's `ChannelMedium` (its Latin-1 channel, a head's characters converted to bytes once) — and
`ReadStreamFrame` maps a gap in a stream-level file (which has no slots) to the end of the data. Deleted with
every caller changed: `WriteFrameHead(TextWriter)`, `WriteWord`, `ExtentTableChars`, `PrefixLength`,
`ExtentCount`, `ExtentTableFromChars`, `CharWord`, `DecodeExtentTable`, `FrameWord`. The REWRITE's in-place table
goes to the medium as `EncodeExtentTable`'s bytes (`OverwriteInPlace` takes a byte span).

**The decided answers** (an implementor framing determination, §9.1.7.2; recorded in `docs/CONFORMANCE.md`
DOC-A.1-151): a frame the data ends inside, a head this writer cannot produce (a negative table component, a
count or length past the medium), and — in a stream-level file — the gap tag END the data at that frame for the
forward READ, the record count / OPEN EXTEND ordinal, the backward-READ index and the OPEN's framing check alike.
What changed for a user: only a damaged file reads differently (the torn record is no longer delivered; the OOM is
gone); every well-formed file reads byte-for-byte as before. The compiler's output is untouched (runtime only).

**Witnesses.** `FrameDecoderDriftTests` (new): the frame word's constants and 32-bit word decode are spelled only
in `ReadFrame`/`ReadExtentTable`/`EncodeFrameHead`/`EncodeGap`; every frame reader reaches the decoder; on seven
damaged shapes the forward READ, `FrameStarts` and `StreamFramingParses` stop at the same frame; the store shape
keeps a gap as a slot. `RecordExtentsTests.TheStreamFraming_CarriesTheTable_AndTheFrameWalkSkipsIt` reads its
frames through the decoder. `SharedReadCoherenceDriftTests` admits `ChannelMedium` as part of the one walk and
checks that only `NextFrame` constructs it.
