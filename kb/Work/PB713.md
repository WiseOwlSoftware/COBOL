# PB713 — a sharing-active EXTEND connector locks the file against its own second handle

Found 2026-09-05 by the `PB683` implementer (report, "New defects found", (a)) while sweeping the sharing
predicate it deleted. Reproduced here from source, with the stack.

## The facts

- **Reproduced.** `E:\Temp\claude\E--CobolSharp\49b17747-ce58-4386-8c49-ecb2ce644f8d\scratchpad\pb713a.cob` —
  a `SELECT` with `ORGANIZATION IS LINE SEQUENTIAL`, `SHARING WITH ALL OTHER`, `LOCK MODE IS MANUAL`; write one
  record, `CLOSE`, then `OPEN EXTEND`. Built at `c34f01ad`, `--std 2023 --run`:

  ```
  SEEDED
  Unhandled exception. System.IO.IOException: The process cannot access the file '…pb713a-dat.txt' because it is
  being used by another process.
     at System.IO.File.ReadLines(String path)
     at CobolNet.Runtime.IO.SequentialConnector.SeedSharedWriteBase()
     at CobolNet.Runtime.IO.FileRegistry.SharedOpenAttempt(String name, FileOpenMode mode, …)
     …
     at CobolNet.Runtime.IO.CobolFile.OpenExtend(…)
  ```

  No I-O status, no USE declarative, no diagnostic — the process dies inside `OPEN`.
- **The order.** `src/Cobol.Net.Runtime/IO/FileRegistry.cs:812-822` (`SharedOpenAttempt`): `string status =
  c.Open(mode);` first, then, on success, `if (c is SequentialConnector f && _connectorShares.ContainsKey(name))
  f.SeedSharedWriteBase();`. The seed therefore always runs with the connector's own handle already open.
- **The two handles.** `SequentialConnector.cs:298-301` — the EXTEND writer, on a SHARING-active connector, is
  `new FileStream(HostPath, FileMode.Append, FileAccess.Write, FileShare.ReadWrite)`: it holds **Write** access
  and grants others ReadWrite. `SequentialConnector.cs:101-113` — `SeedSharedWriteBase` then probes the same
  path for its record count:
  - `:111` line-sequential: `File.ReadLines(HostPath)` → `StreamReader(string)` → `FileShare.Read`. The share
    mode a handle requests must permit the access others already hold; `Read` does not permit the outstanding
    **Write**, so `CreateFile` fails. **This is the crash.**
  - `:110` varying: `RecordFraming.ReadStore(HostPath)` → `RecordFraming.cs:67`,
    `new FileStream(path, FileMode.Open, FileAccess.Read)` — the three-argument constructor defaults to
    `FileShare.Read`. **The same bug, not merely "likely"**: it is the identical share mode by the constructor's
    documented default.
  - `:112` fixed-width: `new FileInfo(HostPath).Length` — metadata only, no handle. Safe, which is why the
    default organization never showed this.
- **What the seed is for.** §14.9.51.4 GR18 (`cite.py --check 14.9.51.4 "the first record written after the
  execution of the OPEN statement with the EXTEND phrase is the successor of the last record in the physical
  file"` → `OK §14.9.51.4 18)`) — an EXTEND append continues the existing records, so the write-ordinal base is
  the count present at OPEN. The requirement is right; the way it is measured is not.

## Why it matters

Any program that opens a shared LINE SEQUENTIAL (or varying) file `EXTEND` dies. Not a wrong status, not a
missed lock — an unhandled .NET exception out of `Main`, with a message about "another process" naming a process
that is the program itself. It is also exactly the shape a user cannot work around, since the SELECT clauses that
trigger it (`SHARING`, `LOCK MODE`) are the ones a shared-file program must write. §14.9.27.3 SR8 hides it
further: it forces a LOCK MODE clause for the `ALL` spelling, so the shapes that reach `_connectorShares` are a
narrow band that the corpus under-covers.

## The fix shape

Do not open a second handle to measure a file this connector already has open. One mechanism for all three arms
(`feedback_one_mechanism_per_job`): the seed asks the CONNECTOR for its base, and every probe handle the runtime
opens on a host path inherits the connector's own share mode — `SharedStreams ? FileShare.ReadWrite :
FileShare.Read` — through one helper, so a fourth organization cannot re-introduce it. Where the writer is
already open, prefer its own `BaseStream.Length` / a counted seek over any new handle at all. Pair it with the
probe above as a golden on all three organizations (line sequential, varying, fixed) in both `SHARING` spellings,
and with the fixed-width arm kept as the control that already passed.

## Sweep

Every place the runtime opens a second handle on a path a connector may hold —
`grep -rn "File.Read\|new FileStream(" src/Cobol.Net.Runtime/IO/*.cs`:
`RecordFraming.cs:67` (`FileAccess.Read`, default share Read — the varying arm above),
`RecordFraming.cs:46` (`FileMode.Create, FileAccess.Write`, three-argument → default `FileShare.None`, which
forbids *every* other handle and is the stricter form of the same defect),
`FixedFileAttributes.cs:234` (`File.ReadAllLines` on the sidecar — a different path, so it fails only if the
sidecar is itself held), and `FileSupport.cs:181` (already `FileShare.ReadWrite`, the shape the others should
have). The audit that makes this stay fixed is mechanical: no `FileStream`/`File.Read*` call in
`src/Cobol.Net.Runtime/IO` may omit an explicit `FileShare`.

## Landed

Landed 2026-09-06 on top of origin/main `8ff37de6` (train 14). Reproduced first, exactly as filed, on a build of
`c34f01ad` — and the varying arm was reproduced too rather than deduced: `pb713v.cob` (a `RECORD IS VARYING`
`SELECT` with `SHARING WITH ALL OTHER` / `LOCK MODE IS MANUAL`) died with the identical `IOException` through
`RecordFraming.ReadStore` → `SequentialConnector.SeedSharedWriteBase`.

**The order was the root, not the share mode.** The measurement moved OUT of the registry and INTO the connector's
own OPEN body: `SequentialConnector.OpenCore`'s EXTEND arm now calls the new private `ExistingRecordCount()`
BEFORE it opens the append writer, so at the moment the file is measured this connector holds no handle on it at
all. §14.9.51.4 GR19 licenses the earlier point — *"the added records follow the records present in the physical
file when it was opened"* — and an `OPEN EXTEND` writes nothing, so the count at the writer's creation and at the
OPEN's completion are the same number. Two further things fall out of the relocation and both were part of the
defect:

- The measurement is now inside `FileConnector.Open`'s try, so a host failure reading the file is §9.1.13.6 item
  1's '30' rather than an escaping exception. §14.9.27.4 GR1 makes an I-O status the ONLY outcome an OPEN has;
  the registry's post-open block (`FileRegistry.SharedOpenAttempt`) now touches no byte of the host at all, and
  its comment says so.
- The duplicate host probe is gone. `SeedSharedWriteBase` called `HostFile.Probe` a second time in the same OPEN,
  against the ONE-probe discipline PB323 established; `OpenCore` already has the `presence` the OPEN contract
  handed down.

**The share mode became a structure rather than a call-site decision.** `HostFile` — already documented as the one
place the runtime asks the operating environment about a physical file — gained the third question, the one that
had no home: `OpenConnectorStream(path, mode, access, sharedConnector, options)` for a connector's own long-lived
handle (the §9.1.15 posture ternary, written out at four `SequentialConnector` sites, now exists once) and
`OpenAuxiliary(path, mode, access)` for a short-lived bookkeeping handle over a path a connector of this run unit
may hold, always `FileShare.ReadWrite`. Every host-path open under `Cobol.Net.Runtime/IO` routes through one of
them, so no site can inherit a .NET constructor default again — and the defaults are wrong in both directions:
the three-argument `FileStream` is `FileShare.Read` (what refused the varying arm) and the two-argument one is
`FileShare.None` (what `RecordFraming.WriteStore` was using, the stricter form of the same defect).

**Sweep**, `grep -rn "\bFile\.[A-Za-z]*\s*(\|new FileStream(\|new StreamReader(\|new StreamWriter(" src/Cobol.Net.Runtime/IO/`
— every site, and what each was: `SequentialConnector.cs:111` `File.ReadLines` (the crash) and `:110`
`RecordFraming.ReadStore` (the sibling crash) → one `ExistingRecordCount`; `SequentialConnector.cs:279/287/299/318`
the four connector streams, each with its own hand-written share ternary → `OpenConnectorStream`;
`SequentialConnector.cs:317` the optional-file create → `OpenAuxiliary`; `RecordFraming.cs:46` implicit
`FileShare.None` and `:67` implicit `FileShare.Read` → `OpenAuxiliary`; `FixedFileAttributes.cs:234`
`File.ReadAllLines` and `:291` `File.WriteAllText` on the sidecar → `OpenAuxiliary` (not a crash, but the SILENT
form: §9.1.15 puts *"runtime elements in different run units"* on one physical file, and a sidecar being written
by one run unit refused the other's read, which is indistinguishable from "attributes not recorded" and silently
skips §14.9.27.4 GR10's '39'); `FileSupport.cs:181` `PermitsWrite` was already `FileShare.ReadWrite`, the shape
the others should have had. Metadata-only sites (`FileInfo.Length` in `ExistingRecordCount`'s fixed-width arm and
in `NoticeIfLayoutDisagrees`) take no handle and are unchanged — which is exactly why the fixed-width framing was
the one arm that never crashed.

**Guards.** `SharedExtendOpenDriftTests` is the whole matrix: three sequential framings (line sequential, fixed
record sequential, `RECORD IS VARYING`) × three §9.1.15 participation spellings (a `SHARING WITH ALL OTHER` clause
with its §14.9.27.3 SR8 companion `LOCK MODE`, a `LOCK MODE`-only entry, and the OPEN statement's own SHARING
phrase), plus the relative and indexed organizations, each opened shared-EXTEND and read back; and a second
theory asserting the §9.1.16 write ORDINAL continues (the appended record is ordinal 2, not 1) over the two
spellings that carry a `LOCK MODE` clause and therefore have a lock to observe. A static guard forbids any
host-path open under `Cobol.Net.Runtime/IO` outside `FileSupport.cs`, with the positive complement pinning both
roles to their home. All of it was proved RED on the pre-fix tree: 12 of 23 failed, exactly the line-sequential
and varying rows plus the two static guards, with fixed-width, relative and indexed green on both trees.

**Goldens** split by edition floor, because the matrix spans two: `tests/conformance/2023/pb713_shared_extend_open`
carries all eight files (ORGANIZATION IS LINE SEQUENTIAL is COBOL-2023, PB688), and
`tests/conformance/2002/pb713_shared_extend_open` carries the subset legal at the SHARING clause's own 2002 floor
— fixed and varying record sequential, relative, indexed, and the two spellings SR8 does not constrain.

**Row.** `GR-14.9.51.4-18` GAP → CONFORMS (GAP 2815 → 2814).
