# PB250

**Rows:** `FMT-15.94.2`

>>COBOL-WORDS is inert for every keyword the ANTLR lexer does not carry as a literal token — so TEST-NUMVAL-C's LOCALE/ANYCASE both reject legal source and silently eat a user-defined word.

ROW: FMT-15.94.2 (§15.94.2, the TEST-NUMVAL-C general format). The FORMAT is implemented correctly — that was re-verified from the printed page and by tracing all eight shapes, including the three untested ones — and the defect is one level down, in how the two keywords of that format interact with §7.3.10 >>COBOL-WORDS.

SPEC GROUND (each --checked on the row): ANYCASE and LOCALE are both §8.9 RESERVED words and neither is in the §8.10 context-sensitive table. §7.3.10.3 SR3 — 'The content of literal-1, literal-3, and literal-4 shall be a reserved word, a context-sensitive word, or an intrinsic function name' — makes both legal operands of the directive. §7.3.10.4 GR2: an EQUATEd literal-2 'may be used in any syntax requiring the use of the reserved word'. GR4: a SUBSTITUTEd literal-5 'shall be used in any syntax where the COBOL word that is the content of literal-4 is documented as required or optional', and literal-4 'shall no longer be a reserved word'. GR3: an UNDEFINEd literal-3 'shall no longer be reserved or restricted in any way' and its syntax 'shall not be available'. §15.94.2 IS such a syntax: it documents LOCALE and ANYCASE as its keywords.

MECHANISM, read end to end. `CobolWordsRewriter.Rewrite` installs a synonym only when `CobolKeywordTokens.TryTokenType` succeeds, and that map is built ONLY from the ANTLR lexer's literal token names. Its own summary asserts an INVARIANT — 'Every reserved word and context-sensitive word is a literal lexer token' — and the invariant is FALSE for LOCALE and ANYCASE: the generated vocabulary jumps 'LESS','LINE','LINES','LOCATION' with no LOCALE and no ANYCASE, and CobolExpressions.g4:359 says so in words. No retype happens, in either direction. `BindNumvalCFamily` then recognises the words by RAW TEXT and never consults `ctx.CobolWords`, although the same file consults it for the function name — ONE RULE, TWO PLACES.

BOTH DIRECTIONS ARE REACHABLE, because the directive is ACCEPTED: `VersionConformancePass.IsExistingWordCategory` (:138-139) passes SR3 through the `ReservedWords.Find(w)` fallback, and `tests/version-matrix/reserved-words.json` carries {"word":"LOCALE", r85:false, r2002:true, …} and the same row for ANYCASE. So the program compiles clean and the directive is SILENTLY INERT.
(1) REJECTS LEGAL SOURCE. `>>COBOL-WORDS EQUATE "LOCALE" WITH "LOCALITY"` then `FUNCTION TEST-NUMVAL-C(X LOCALITY FR)`: LOCALITY and FR bind as OPERANDS, so :1572's `operands.Count is < 1 or > 2` fires COBOLNET1504 — an ARITY error naming the very keyword the program legally renamed.
(2) SILENT WRONG ANSWER. `>>COBOL-WORDS UNDEFINE "ANYCASE"` (GR3) or `SUBSTITUTE "ANYCASE" BY "IGNORE-CASE"` (GR4) makes ANYCASE a user-defined word and withdraws the ANYCASE syntax; `FUNCTION TEST-NUMVAL-C(X ANYCASE)` — where ANYCASE is now the user's currency data item — is STILL eaten as the keyword at :1527, so the compiler turns on case-insensitive currency matching and injects the compilation-unit currency at :1619 instead of using the named item as argument-2, with NO diagnostic.

THE ASYMMETRY IS PROVABLE INSIDE ONE COMPILER: TRIM's LEADING/TRAILING (§15.96.2) ARE literal lexer tokens (`CobolExpressions.g4#fnArgPhraseWord`), so >>COBOL-WORDS IS honoured for that format's phrase words and is NOT honoured for this one. The population is therefore every phrase word carried as a bare IDENTIFIER — CobolExpressions.g4:359 lists ANYCASE, HEX, NAT, ANUM, BYTE, CURRENT, ACTIVATING, NESTED, STACK, TOP-LEVEL — and the sweep is the note's second half.

FIX SHAPE (rule 5 — the structural answer, not the smallest diff): the keyword-token map must be derived from the reserved-word table rather than from the lexer vocabulary, with a DRIFT TEST re-deriving the population so the written invariant becomes true and stays true; and the raw-text keyword comparisons in BindNumvalCFamily (and every sibling bare-word phrase site) must go through the same `ctx.CobolWords` resolution BindIntrinsicCore already uses for the function name. Goldens: a positive for an EQUATEd LOCALE/ANYCASE synonym and a negative for the UNDEFINEd spelling — nothing anywhere currently exercises >>COBOL-WORDS against any function's keyword.

ALSO RECORDED BY THIS ROW (documentation only): `IntrinsicBinder.cs:555-556` still reads 'The LOCALE phrase is the A.4.9 documented non-support (decision 3 …)', contradicting the live T6 LOCALE arm 1000 lines below and the accurate note at :506-510. And the editions for this row were corrected 85,2002,2014,2023 → 2002,2014,2023 from reserved-words.json's r85:false on BOTH keywords.

VERIFIED LIVE AT HEAD (read-only): CobolWordsRewriter.cs:35/:50 and CobolKeywordTokens.cs:42 unchanged; no ANYCASE/LOCALE lexer rule in any .g4.

## Landed

Landed 2026-09-05. Both directions of the note reproduce on a fresh build and both are fixed; the sweep found the
same rule broken in three more places, and the population turned out to be a CLASS, not two words.

**MEASURED FIRST.** Of the 552 words in ISO §8.9 ∪ §8.10, `CobolKeywordTokens` carried 447. **17 more ARE lexed
as keyword tokens yet were invisible to it** — ANTLR publishes a literal NAME only for a token defined by exactly
one literal, so a multi-spelling rule (`ZERO : 'ZERO' | 'ZEROS' | 'ZEROES'`, `PIC : 'PICTURE' | 'PIC'`, the
figurative plurals, IS/IN/OF/ALL) publishes none and `>>COBOL-WORDS UNDEFINE "ZERO"` was silently inert too.
**88 are no lexer token at all** — the note's ANYCASE and LOCALE among them, with HEX, NAT, ANUM, BYTE, CURRENT,
ACTIVATING, NESTED, STACK, TOP-LEVEL, PHYSICAL, the LC_ categories and UCS-4/UTF-8/UTF-16.

**THE FIX IS ONE RULE IN ONE PLACE, CALLED FROM BOTH MECHANISMS.** `CobolWordsMap.Resolve` is now the single
reading of §7.3.10.4 GR2/GR3/GR4 — the canonical word for an EQUATE/SUBSTITUTE synonym, `null` for an UNDEFINE'd
or SUBSTITUTE'd-away word, the word itself otherwise — and `CobolWordsMap.Is` is the single comparison built on
it. It replaced two inline copies in `IntrinsicBinder` and is now called from every by-name classifier:

- `IntrinsicBinder.KeywordWordOf` — **the funnel every §15 phrase word is read through**, so TRIM, FIND-STRING,
  SUBSTITUTE, CONVERT, MODULE-NAME, LENGTH and NUMVAL-C/TEST-NUMVAL-C are all covered by the one call, and the
  next phrase word added is covered automatically. This also closed a leak the note did not predict: for a
  TOKENIZED phrase word the de-reserve retype produces an IDENTIFIER carrying the same text, which the
  `cobolWord` branch re-read as the keyword — so `SUBSTITUTE "LEADING" BY "LEFTMOST"` ate the user's own
  `01 LEADING` inside `FUNCTION TRIM`.
- `CobolParserCoreBase.Word` — the one text comparison behind every parser predicate (LOCALE, ORDER,
  CLASSIFICATION, ATTRIBUTE, the LC_ categories, `reservedHere`, `facilityWord`). The parser now receives the map
  beside `DialectLevel`. Without this an EQUATEd LOCALE never reached the SPECIAL-NAMES clause or `SET LOCALE`.
- `SetBinder` (SET LOCALE categories, USER-DEFAULT/SYSTEM-DEFAULT), `DataBinder.Switches` (the SPECIAL-NAMES
  LOCALE clause, the ALPHABET LOCALE phrase, the UCS-4/UTF-8/UTF-16 coded-set names), `CallBinder` and
  `VersionConformancePass` (`CALL … AS NESTED` — both arms of that two-arm dispatch).

**THE TOKEN ARM WAS FIXED TOO, MECHANICALLY.** `CobolKeywordTokens` keeps the vocabulary walk as its fast path and
falls back to a **lex probe** — run the real lexer over the word and read the type it produces — so a
multi-spelling rule resolves without a hand-maintained list and the next one is automatic. The probe is cold: it
runs only for a word a directive actually names. `CobolWordsRewriter`'s de-reserve retype now matches the token
TEXT as well as its type, because one token type carries several COBOL words while SR3 names exactly one:
`UNDEFINE "ZERO"` must not free ZEROS and ZEROES with it.

**THE DIRECTIVE IS APPLIED TO A WORD EXACTLY ONCE.** A first cut applied `Resolve` at `KeywordWordOf`
unconditionally and REGRESSED `FUNCTION TRIM(X LEFTMOST)` after `SUBSTITUTE "LEADING" BY "LEFTMOST"`: the retype
had already resolved the synonym AND re-spelled it canonically, so the second resolution saw literal-4 — canonical
and de-reserved at once — and answered "not a keyword". `CobolWordsRewriter.CanonicalWordOf`/`TokenIs` own that
distinction now (a non-IDENTIFIER token has been resolved already; only an IDENTIFIER can still carry an
unresolved word), and a unit test pins it.

**A THIRD ARM THE NOTE DID NOT SEE, FOUND BY PROBING THE SWEEP.** §7.3.10.3 SR3's category test asked the LEXER
VOCABULARY whether a word is context-sensitive — which knows only the context words this compiler tokenizes — so
the perfectly legal `>>COBOL-WORDS EQUATE "HEX" WITH …` was rejected outright with COBOLNET1623, and with it
every directive naming one of the 31 §8.10 words that arrive as bare IDENTIFIERs. A **generated §8.10 table**
(`ContextSensitiveWords`, emitted from the spec section by `scripts/gen-reserved-words.ps1`, drift-tested against
that section) now answers SR3 and SR4. It needs no per-edition flags: the directive is a COBOL-2023 introduction
(`cobol-words-directive-2023`), so 2023 is the only edition at which those rules are ever asked. §8.10's own NOTE
is the confirming evidence — "Words can be added or deleted from this list for a specific compilation group by
use of the COBOL-WORDS directive."

**A LATENT GENERATOR DEFECT, TRIGGERED AND FIXED.** `gen-reserved-words.ps1` was no longer reproducible: it
emitted `namespace CobolNet.Validation` while the committed table says `CobolNet.Editions` (a re-run broke the
build), and its OCR continuation-join had not kept up with the transcription repair that bulleted and code-fenced
the continuation lines — so a re-run silently **un-reserved FLOAT-NOT-A-NUMBER-QUIET and -SIGNALING at 2023**.
Both are fixed and the script now reproduces the committed §8.9 tables byte-identically.

**DRIFT TESTS, PROVEN RED FIRST.** `CobolWordsReachDriftTests` measures the invariant `CobolKeywordTokens` used
merely to ASSERT; with the lex probe disabled it fails naming exactly the 17 words the independent measurement
found. `ContextSensitiveWordsDriftTests` ties the §8.10 table to its JSON and to the spec section.

**GOLDENS.** `2023/pb250_cobol_words_phrase_word_equate` (GR2 on a non-tokenized §15 phrase word),
`2023/pb250_cobol_words_phrase_word_undefine` (GR3 — the user's data item bound as argument-2, the note's silent
wrong answer), `2023/pb250_cobol_words_multi_spelling` (UNDEFINE "ZERO" leaves ZEROS reserved),
`negative/pb250-cobol-words-undefined-keyword-syntax-withdrawn` (GR3's withdrawn syntax). The row's own owed
shapes came with them: `2002/pb250_test_numvalc_remaining_shapes` (the three untested §15.94.2 shapes) and
`negative/pb250-test-numvalc-locale-and-argument2-are-alternatives` (the stack exclusion under this function's own
name). `FMT-15.94.2` re-verdicted PARTIAL → CONFORMS (GAP 2906 → 2905).

**THE DOCUMENTATION ERRORS THE NOTE RECORDED ARE CORRECTED**, and so is their root: `DESIGN-cobol-words-directive`
§2 asserted that a word with no keyword token type is "a pure intrinsic-function-name, or an unknown SR3
violation", which is the false premise the whole defect rests on. §2.1 now carries the measured partition and the
once-only rule; §5 carries the §8.10 correction. The stale `IntrinsicBinder` LOCALE non-support line is gone, and
so is the neighbouring claim that ANYCASE and LOCALE are §8.10 context-sensitive — they are §8.9 reserved, and the
argument-1 exclusion is POSITIONAL.

## Mechanism

src/Cobol.Net.Frontend/Parsing/CobolWordsRewriter.cs:35 and :50 install a synonym only when `CobolKeywordTokens.TryTokenType(canonical, out int kt)` succeeds (DeReservedTokenTypes at :30-37 is guarded the same way); src/Cobol.Net.Frontend/Parsing/CobolKeywordTokens.cs:42's map is built ONLY from the ANTLR lexer's literal token names (:20-37) — and src/Cobol.Net.Frontend/Grammar/Core/CobolExpressions.g4:359 states outright that ANYCASE and friends 'are plain IDENTIFIERs'; IntrinsicBinder.BindNumvalCFamily then matches raw text (KeywordWordOf :2516; `== "ANYCASE"` :1527, `== "LOCALE"` :1547) and never consults `ctx.CobolWords`, while BindIntrinsicCore :446-448 in the SAME file consults it for the FUNCTION NAME
