# PB651 — LANDED — a lane the strict verdict no longer covers

Found 2026-09-05 by the `PB635` implementer (report §"For the orchestrator" (C)). PB248 (train 5) re-derived §15.3
type 6 — "an integer data item or an always-integral arithmetic expression" — so a floating-point operand at an
integer argument position is strict-illegal (COBOLNET1627) and permissive-legal (a warning, then the bind
proceeds). PB635 measured the consequence one renderer down: the float dispatch, reasoning that a float could
only arrive in a numeric-carrier position, emitted `FindStringReal`, `OrdReal`, … for TEN functions under
`--permissive` — Roslyn CS0117 on a program the compiler had accepted. `FloatIntegerArgumentPermissiveTests` is
the home PB248 created for exactly this class ("both paths are still REACHED under --permissive"), and it held two
programs before PB635 added its four.

## The probe

For every row of `IntrinsicCatalog` with an integer-typed position, and for every non-intrinsic site whose
argument class is screened at bind (PERFORM … TIMES, the subscript/reference-modification positions, the CALL BY
VALUE carrier), compile a `--permissive` program passing a `COMP-2` (and a `FLOAT-DECIMAL-34` where the edition
admits it) at that position and assert: (a) the compile succeeds with the warning, (b) the generated C# compiles,
(c) the program runs and its result follows the documented permissive determination (PB248's screen substitutes /
truncates — read its landed section for which). Every (b) failure is a `PB635`-class crash; every (c) failure is a
wrong answer in the migration lane. Two known sites to start from are in PB635's report.

## Outcome

Each failure becomes a defect note with its repro; the probe itself becomes a drift test over the catalog (the
population derived, per [[PB650]]), run in the wave-local gate so the permissive lane cannot silently diverge from
the strict one again.

## Extended 2026-09-23 by REGISTRAR #13 (`leads-w53-w57.md`, train-57 lander report)

## Landed (wave 1084 group G, branch `worktree-wf_f560587e-74d-14`)

**The probe is a drift test.** `tests/Cobol.Net.Tests.Unit/IntrinsicIntegerPositionPermissiveDriftTests.cs` derives
every §15.3 type-6 OPERAND position from the spec-verified schemas (`IntrinsicArgumentRules.Verified`, the table the
strict screen reads; 33 positions over 23 functions today) and fails on a position with no fixture. It runs ONE
`--permissive` program that calls each over a `FLOAT-LONG` holding the integer, one holding it plus one half, and the
integer literal (the control), and asserts the compile warns COBOLNET1627, the generated C# compiles, and both float
probes answer exactly the control (docs/CONFORMANCE.md DOC-A.1-124: the integer, or the truncated integer with
EC-ARGUMENT-FUNCTION checking off).

**What it found, measured before the fix:** no backend error anywhere (PB635's fix holds), but three functions
answered differently from their integer: `MOD(7.5 3)` = 1.5 and `MOD(7 3.5)` = 0 (the scaled arm aligned the
fraction), `COMBINED-DATETIME` over a float argument-1 rode the binary64 lane and added 143951.5 as it stood (and
printed `143951.036` where the control prints `143951.03600`), and `ANNUITY(0.05 3.5)` computed 3.5 periods.

**The fix is one entry.** `IntrinsicRenderer.RawArg` is now the indexed argument entry every numeric-channel intake
and lane predicate reads (`Arg`, `Dbl`, `DecArg`, `IntArg`, and `AnyRealArgument` & co. through `Operands`): at a
verified type-6 position (`IntrinsicArgumentRules.IsIntegerPosition`) a float, SDIDI or fractional fixed-point operand
lands at scale 0 through the shared wide type-6 intake, which keeps the value or raises: a float past Int128
(±1.7e38) is EC-ARGUMENT-FUNCTION (`CobolIntrinsics.IntegerArgWideReal`). The first cut clamped such a float to the
carrier's extreme (`IntegerArgTotalReal`); the branch review (R1-2) measured `MOD(1.0E39, 7)` = 1 and
`ANNUITY(0, 1.0E39)` = 1/1.7e38 from it, silently. The clamp now lives only in `IntrinsicRenderer.IntArgWideSaturating`,
taken by the arms whose answer is the same for every integer past a bound (TEST-DATE-YYYYMMDD / TEST-DAY-YYYYDDD
argument-1, FIND-STRING argument-3 — PB254's total-argument determination), and
`IntrinsicCarrierAgreementDriftTests.OnlyAnArgumentWhoseAnswerIsConstantPastABound_Saturates` holds that set closed. An integer has no binary64-ness, so a float at a type-6 position no longer
enters the binary64 lane: `FloatLaneExempt` is deleted, and so are the unreachable binary64 bodies of the
integer-only functions (date family, TEST- validators, windowing trio, `ModReal`) — runtime major 4 → 5, the shipped
surface re-pinned. `IntrinsicRealArgDriftTests.NoRealBody_ServesAFunctionWhoseEveryPositionIsType6` keeps them gone.
`FloatIntegerArgumentPermissiveTests.Pb651FractionalFloat_AtATypeSixPosition_UnderPermissive_IsTruncatedOnEveryLane`
pins the three spec-derived values.

**The non-intrinsic sites, re-probed:** a float `PERFORM … TIMES` count is refused in both modes (COBOLNET1646,
§14.9.28.3 SR2); a float subscript and a float reference-modifier bound are legal arithmetic-expression positions and
answer the truncated integer (`E(7.5)` is the 7th occurrence); a float `CALL … BY VALUE` into a `BINARY-LONG` formal
(permissive, COBOLNET0899) delivers 7. None diverges.

**The registrar's extension (NUMVAL through the multi-receiver MOVE) is NOT fixed here** and is reported as a lead:
it is the §15.4 function-value temporary (`SendingValueTemp.FunctionValuePic`, scale 9), not the type-6 lane, and it
is wider than the note says — STRICT, `MOVE FUNCTION PI TO Q1 Q2` (PIC 9V9(15)) stores 3.141592653000000 where
`MOVE FUNCTION PI TO Q3` stores 3.141592653589793 (also SQRT, MEAN, NUMVAL into a receiver past scale 9). Its fix
needs the temporary to hold the value on the carrier the renderer chooses, which is decided in codegen while the
temporary is described at bind — a redesign beyond this slice.

**Finisher (landing Linux gate RED, 2026-10-16).** The type-6 intake must keep an SDIDI operand on the SDIDI. Landing it on `Int128` made MOD(10 ** 40, 3) and MOD(A ** 3, B) fatal EC-SIZE-OVERFLOW (`2014/pb2630_integer_family_beyond_int128`, `2023/pb69_native_power_past_the_carrier`). `RawArg` now emits `CobolIntrinsics.IntegerArgUnboundedDec`. `2023/pb56_dec_carrier_intrinsics`'s MOD line took non-integral arguments (§15.64.3 r1), so it now takes integral SDIDI values.
