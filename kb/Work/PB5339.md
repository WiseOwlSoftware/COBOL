# PB5339 - another run unit's ACCEPT MESSAGE COUNT does not include a message partly received by a different run unit: the store releases the message at its first portion, where §1985:XIV.3.1.4 GR1 counts it until the last

**Sites:**

- `src/WiseOwl.Cobol.Runtime/Communication/McsTables.cs` (`TakeQueueMessage`)
- `src/WiseOwl.Cobol.Runtime/Communication/MessageControlSession.cs` (`Receive`)
- `src/WiseOwl.Cobol.Runtime/Communication/MessageStoreState.cs` (`MessageStoreState`)
- `src/WiseOwl.Cobol.Runtime/Communication/McsStore.cs` (`DrawRunUnit`, `OwnerIsAlive`)
- `src/WiseOwl.Cobol.Runtime/Communication/McsTables.cs` (`PutPartialReceive`, `DeletePartialReceive`, `PartialReceives`)
- `src/WiseOwl.Cobol.Runtime/IO/Sharing/HostRegionLocks.cs` (`McsRunUnitLivenessByte`)

**Mechanism.** PB5285 made the run unit's own count include the remainders of a message it has partly received (`Dialogue.PartlyReceivedFrom`), but the store itself still releases the message at the first portion (kept so that a crash leaves no stale count). Another run unit reading the same queue therefore does not count it. §1985:XIV.3.1.4 GR1 counts "the number of complete messages that exist in the queue structure" (`cite.py --check "§1985:XIV.3.1.4 GR1" "the number of complete messages that exist in the queue structure"` prints OK). The lead cites it as "1985 GR1 / VI.6.24.4 GR3"; the check refuses §1985:VI.6.24.4 GR3 for that text (it is in §1985:XIV.3.1.4 GR1), so the VI.6.24.4 GR3 half of the lead is unverified.

**Fix direction (as the lead states it).** A store-level partial-message row with run-unit liveness, so a message stays counted while its receiving run unit is alive and returns to the queue (or is dropped, per STOP RUN's rule) when it is not. Shares its root with PB5285.

**Source.** PB5281's implementer; not fixed (documented limit in CONFORMANCE 3.3).
