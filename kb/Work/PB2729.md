**Rule it breaks:** ISO §8.3.3.3.3 1) — a floating-point literal is 'formed from two fixed-point numeric literals separated by the letter E'; §8.3.3.3.2 3) — in a fixed-point literal the decimal point 'may appear anywhere within the literal except as the rightmost character'. So `1.E2` (significand `1.`) is not a literal. NumericLiteral.CheckFloatingPointForm's own doc says the significand's point is 'the lexer's shape' — the lexer is the declared single owner of that half of the rule, and its body `[0-9]+ '.' [0-9]*` writes it wrong; DEC_BODY two lines away (`[0-9]+ '.' [0-9]+ | '.' [0-9]+`) writes the same fixed-point rule right, so the one rule is spelled twice and the copies disagree (feedback_one_rule_one_place). Loud failure: an illegal literal must draw a named diagnostic, never a backend crash.

**Scenario:** Measured with the built compiler (FLOAT_BODY / FLOAT_COMMA_BODY unchanged since the pin): `01 Y USAGE FLOAT-LONG VALUE 3.E2.` lexes as one FLOATLIT, passes DataBinder's §8.3.3.3.3 screen (CheckFloatingPointForm checks digit counts and the zero form only), and is emitted verbatim as C# `private double Y = 3.E2d;`, which Roslyn reads as member access on int: `error: backend compilation failed … CS1061: 'int' does not contain a definition for 'E2d'`, exit 70 — an internal failure on user source. In the procedure division `COMPUTE X = 1.E2 + 5` compiles clean and prints 00105 at --std 2023, accepting a literal no conforming implementation must accept. The FN_SIGNED_FLOATLIT / FN_SIGNED_COMMA_FLOATLIT twins share the bodies, so `MAX(-1.E2 …)` and the comma-mode `1,E2` carry the same hole.

## Landed (w1051d, 2026-10-10)

Re-probed on the worktree build (main 471d0e954): `01 Y USAGE FLOAT-LONG VALUE 3.E2.` died in the backend (CS1061,
exit 70) and `COMPUTE X = 1.E2 + 5` compiled (exit 0), both as filed.

**Mechanism and fix.** The significand IS a fixed-point literal (§8.3.3.3.3 1)), so it is now written as one:
`fragment FLOAT_BODY : DEC_BODY 'E' [-+]? INT_BODY` and `fragment FLOAT_COMMA_BODY : DEC_COMMA_BODY 'E' [-+]? INT_BODY`
(`src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4`). DEC_BODY was already the one correct spelling of §8.3.3.3.2 3);
the float bodies carried a second, wider copy. The FN_SIGNED twins reference the bodies, so the signed argument forms
inherit the fix. `3.E2` now lexes as INTEGERLIT `3` and a period with no space after it, which the one §8.3.5 rule site
(`SeparatorRule`) already names: COBOLNET2632 (rule 3); `3,E2` draws COBOLNET2631 (rule 2). So the rejection is named
by the rule the spelling breaks, and no form check downstream has to re-ask the significand's shape.
`NumericLiteral.IsFloatingPointForm` / `CheckFloatingPointForm` docs now say the point's position is the lexer's,
through DEC_BODY.

**Drift guard.** `SignedLiteralShapeDriftTests.EveryFloatBody_SignificandIsAFixedPointBody`: every `FLOAT*_BODY` is
`DEC*_BODY 'E' [-+]? INT_BODY`, so a new float shape cannot spell its own significand.

**Goldens.** `2002/pb2729_float_significand_forms` (1.0E2, .25E+1, a signed -1.5E2 argument and 25.0E-1 stay one
literal each); negatives `pb2729-float-significand-point-value`, `-compute`, `-argument` (§8.3.5 rule 3) and
`pb2729-float-significand-comma` (§8.3.5 rule 2), each at every edition.

- `src/Cobol.Net.Frontend/Parsing/SeparatorRule.cs` — names a lexically broken literal (a point or comma with no
  space after it); a lexer narrowing that leaves a DOT or COMMA token behind gets its diagnostic here for free.
- Trap: the Write tool decodes `\u` escapes in C# and the Bash hook blocks backslashes in heredocs; use

over `src/**/*.g4`, and of digit-point-digits regexes over `src/**/*.cs`).
