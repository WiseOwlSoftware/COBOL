**Rule it breaks:** ISO §8.3.3.3.3 1) — a floating-point literal is 'formed from two fixed-point numeric literals separated by the letter E'; §8.3.3.3.2 3) — in a fixed-point literal the decimal point 'may appear anywhere within the literal except as the rightmost character'. So `1.E2` (significand `1.`) is not a literal. NumericLiteral.CheckFloatingPointForm's own doc says the significand's point is 'the lexer's shape' — the lexer is the declared single owner of that half of the rule, and its body `[0-9]+ '.' [0-9]*` writes it wrong; DEC_BODY two lines away (`[0-9]+ '.' [0-9]+ | '.' [0-9]+`) writes the same fixed-point rule right, so the one rule is spelled twice and the copies disagree (feedback_one_rule_one_place). Loud failure: an illegal literal must draw a named diagnostic, never a backend crash.

**Scenario:** Measured with the built compiler (FLOAT_BODY / FLOAT_COMMA_BODY unchanged since the pin): `01 Y USAGE FLOAT-LONG VALUE 3.E2.` lexes as one FLOATLIT, passes DataBinder's §8.3.3.3.3 screen (CheckFloatingPointForm checks digit counts and the zero form only), and is emitted verbatim as C# `private double Y = 3.E2d;`, which Roslyn reads as member access on int: `error: backend compilation failed … CS1061: 'int' does not contain a definition for 'E2d'`, exit 70 — an internal failure on user source. In the procedure division `COMPUTE X = 1.E2 + 5` compiles clean and prints 00105 at --std 2023, accepting a literal no conforming implementation must accept. The FN_SIGNED_FLOATLIT / FN_SIGNED_COMMA_FLOATLIT twins share the bodies, so `MAX(-1.E2 …)` and the comma-mode `1,E2` carry the same hole.
