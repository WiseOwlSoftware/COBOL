Filed 2026-09-26 by the **train-61 lander** from the w61e implementer report (PB1196/PB1147/PB1581), lead 4.

## Observation (not probed)
PB1196 routed every arithmetic store into a binary32/binary64 resultant through `FloatResultant`
(`src/Cobol.Net.Runtime/Values/Numeric/FloatResultant.cs`). The argument-landing path for a prototype CALL / INVOKE
BY CONTENT or BY VALUE into a FLOAT formal — which the w61e report reads from §14.2.3 GR9/GR10 as a COMPUTE without
ROUNDED — goes through `CallEmitter.LandedForFormal` (fixed formals only) and the runtime `CobolArgAdapt` float arm,
neither of which calls FloatResultant.

## To decide
Probe with a prototype CALL passing a fixed-point value that is not exactly representable in binary32 into a
FLOAT-SHORT formal; compare with the COMPUTE landing of the same value (implied TRUNCATION). If they differ, this
becomes a wrong-answer defect whose fix routes the float formal arm through FloatResultant. Re-derive the §14.2.3
rule numbers with `cite.py --check` before citing them.
