# PB899 — LANDED — a diagnostic that is correct in memory and wrong on the wire

Source: the `PB391-finisher` report, "New defects" item 3, **which SUPERSEDES the first PB391 implementer's
"the MOVE diagnostic names the sending operand as `.`" lead**. That lead was a misreading:
`ImplicitMovePhrase.WhereOf` renders `MOVE … TO {receiver}` with U+2026 deliberately, because an explicit
MOVE's sender is not named. What happens to it is best-fit encoding.

## The measurement — bytes, not characters

```
$ cobol.exe p13_proto.cob --std 2023 > diag2.txt 2>&1
$ od -c diag2.txt | tail -2
0000200   d       (   I   S   O     025   8   .   9   )  \r  \n
```

`(ISO §8.9)` — U+00A7 arrives as the single byte **0x15**, which is `§` in cp437 and a control character in
UTF-8 and in every Windows ANSI code page. The PB391 finisher captured the same shape for a MOVE
diagnostic: `MOVE . TO KX … (ISO \x15 14.9.25.3 SR8)`, with U+2026 best-fitted to `.`.

## The two arms

```
src/Cobol.Net.Runtime/Control/ProgramTable.cs:126-127
    if (Console.OutputEncoding.CodePage != 65001)
        try { Console.OutputEncoding = new System.Text.UTF8Encoding(false); } catch (System.IO.IOException) { }
```

A RUN program gets UTF-8. **The CLI's diagnostic path has no `Console.OutputEncoding` setup at all** — grep
`src/Cobol.Net.Cli/` for `OutputEncoding` returns nothing but the copied runtime assembly. One rule
("COBOL.NET's output is UTF-8"), two places it could be written, one of them written
(memory `two_arm_dispatch`).

## Why no gate sees it

The corpus runner matches `.err` files on a diagnostic CODE substring (`COBOLNET0901`), which is pure ASCII,
so a mangled `§` is invisible to every golden. A redirected or piped diagnostic is what a user and a CI log
actually read.

## The fix

Set the console encoding ONCE, at the CLI entry point, for both stdout and stderr, and delete the runtime's
copy or have it call the same helper — not a second `if`. Then add a golden that asserts the BYTES of one
diagnostic containing `§`, because a code-substring match will never catch this class again.

## Landed — 2026-09-19 (wave 39, group CORPUS-FETCH-AND-GUARD)

Re-probed on this worktree's own build before any edit, and the note held exactly. A source rejected by
COBOLNET0886 (`INITIAL and RECURSIVE are mutually exclusive (ISO §11.10.3 SR5–6)`), run through `cmd /c chcp 437`
with output redirected to a file:

```
BEFORE  … 28 49 53 4f 20 15 31 31 2e 31 30 2e 33 20 53 52 35 2d 36 29    "(ISO ␕11.10.3 SR5-6)"
AFTER   … 28 49 53 4f 20 c2 a7 31 31 2e 31 30 2e 33 20 53 52 35 e2 80 93 36 29    "(ISO §11.10.3 SR5–6)"
```

U+00A7 arrived as the single byte 0x15 (cp437's `§`) and U+2013 was best-fitted to `-`; both now arrive as their
UTF-8 sequences. **The en dash is the silent half the note did not name**: a single-byte code page best-fits it
without any error at all, so the citation read plausibly while being wrong.

The rule now lives in ONE place — `src/Cobol.Net.Runtime/IO/StandardStreams.cs`, `EnsureUtf8()` — called by BOTH
arms: `Program.Main` in the CLI, before a single argument is parsed, and `ProgramTable.RunMain`, whose inline
`if (Console.OutputEncoding.CodePage != 65001)` WAS the only copy and is deleted. Idempotent (once per process,
`Interlocked`), and defensive in a way the old `if` was not: where the `Console.OutputEncoding` setter raises
(a consoleless host), it falls back to explicit UTF-8 writers over the standard handles rather than silently
giving up. Sibling sweep: `grep -rn "OutputEncoding" src/ --include=*.cs` now returns exactly that one file, and
`static.*Main|<OutputType>` over `src/` finds no third greenfield entry point (the emitted program's `Main` reaches
the rule through `ProgramRegistry.RunMain`; `src/CobolSharp.CLI` is the legacy oracle, deleted at P15).

Witness: `CliDiagnosticEncodingTests` (tests/Cobol.Net.Tests.Unit) asserts the BYTES of a `§`-bearing diagnostic
through a REDIRECTED stream — text assertions cannot see this, because the harness decodes every capture as UTF-8
and the corpus runner matches `.err` files on a pure-ASCII code substring. ⚠ It asserts its own premise too: a
child with no console inherits .NET's UTF-8 default and would pass on the broken build, so on Windows the driver
runs under a `cmd.exe` whose own console is set to cp437 (`CreateNoWindow` gives it a private console — the
developer's terminal is measurably untouched) and the fact FAILS if `chcp` did not report 437. **Proved failing
first:** with the CLI's call removed the fact reports `Failed: 1` and prints the offending `…49534F2015…` bytes.

`docs/rearchitecture/DESIGN-test-build-ci.md` §3.5 now states that the wire encoding of a diagnostic is part of
the diagnostic, and names the one helper and both callers.
