# PB2833 — LANDED — DynMaxOf was 0 for every dynamic-capacity table

Found by the w1045h implementer (PB1951, report "New defects") and Filed by the train 1047 lander, 2026-10-08 20:53 PDT.

## Mechanism
`src/Cobol.Net.Compiler/Binding/Model/Place.cs#DynMaxOf` (line ~636) reads a component's maximum from
`OccursSpec.Max`, and the binder sets `Max = 0` for every `OCCURS DYNAMIC` table
(`src/Cobol.Net.Compiler/Binding/DataBinder.Odo.cs:79`: `Min = fromCap ?? 0, Max = 0, IsDynamic = true`). The
`VarGroupWindow` built from those maxima (Place.cs:602 and :630) therefore admits zero occurrences for the table.

## Harm (latent, measured once)
Any `StoreContiguousAt` of an image into a cell-backed (EXTERNAL / BASED) group that holds such a table drops its
occurrences. The one measured reacher, the Format 2 table SORT of an EXTERNAL element, now moves that element as its
component carrier (PB1951's sibling fix, train 1047), so it no longer reaches this. The other reachers (READ INTO,
record-image stores into EXTERNAL groups, a group MOVE into one) are UNPROBED. A dynamic-capacity table has no fixed
maximum unless `TO` gives one, so the window must take the current capacity, or the `TO` bound when it exists.

## Landed (wave 1051 group E, branch worktree-wf_4151e8da-91b-5)

**Re-probe (own build).** The note's premise holds in the model: `OccursSpec.Max` is 0 for `OCCURS DYNAMIC`
(`DataBinder.Odo.cs:79`), and `VarGroupWindow.DynMaxOf` read it, so the cell group window, every element shape and the
DECLARED group's contiguous layout (`GroupImageCodec.ContiguousLayout`, the same `OccursSpec?.Max ?? 0`, a second copy
of the choice the note did not name) gave a dynamic table a maximum of zero.

**Reachers: none.** The note listed READ INTO, record-image stores and a group MOVE as unprobed. Each is refused at bind
time, so no legal statement stores a contiguous image into a variable-length group that holds a dynamic-capacity table
(probes under `E:\COBOL-coord\scratch\w1051e\d1.cob`-`d5.cob`): `MOVE <elementary> TO G` and `MOVE ALL` COBOLNET1931
(§8.5.1.12.1, a variable-length group is compatible only with a group), `READ F INTO G` COBOLNET1931 (the record has no
table where `G` has one), `STRING ... INTO G` / `UNSTRING ... INTO G` COBOLNET1651 (§14.9.43.3 SR11, §14.9.48.3 SR10),
`INSPECT G` COBOLNET1626 (§14.9.22.3 SR1 admits an "alphanumeric or national group item", and §8.5.1.12.1 says a variable-length group "is not equivalent to an alphanumeric data item"), a condition-name on `G` COBOLNET1976 (§13.16.3 SR24 h)). A record cannot hold
one either: §8.5.1.9.1 3) bars a dynamic-capacity table from the file section. The one measured reacher, the Format 2
table SORT, moves an element as its component carrier since PB1951. So the harm was latent, and the fix is the model's
truth plus a pin, not a behaviour change a program can see.

**The fix.** `OccursSpec.MaxCapacity` is the one answer to "how many occurrences can this table hold": `Max` for a fixed or
OCCURS DEPENDING table, the implementor's maximum (`CobolDynTable.MaxOccurrences`, DOC-A.1-60) for a dynamic-capacity table
(§8.5.1.9.1 2) "it may have an unlimited capacity"). `DataItem.VariableComponentMax` is the one reader of a variable-length
component's maximum (a table's capacity or a dynamic-length item's `LIMIT`); `VarGroupWindow.Of`, `ElementShapeOf` and
`GroupImageCodec.ContiguousLayout` all ask it, and `DynMaxOf` and the layout's `OccursSpec?.Max ?? 0` are deleted.
**The note's suggestion was not followed:** "the current capacity, or the `TO` bound when it exists". `TO integer-5` is
only "the expected capacity of the table" (§13.18.38.4 GR17); a SET past it sets EC-BOUND-SET and still grows the table
(§14.9.39.4 GR30), and a window is sized before any capacity is known, so neither bounds the layout.
`tests/Cobol.Net.Tests.Unit/DynamicTableMaximumTests.cs` pins the answer for a plain table, a table with FROM/TO, the cell
window (a dynamic-length item beside a table), a nested element shape, and an OCCURS DEPENDING table.

**Sibling sweep.** Every reader of `OccursSpec.Max`: `StrongGroupComparison.WalkTable` (`table.Occurs ?? Max`) never meets a
dynamic table (a strongly-typed group comparison reaching one is refused COBOLNET0899 first); `OccurrenceCounts`,
`SequentialIoEmitter:980` and the report writer's `ReportDepending` are OCCURS DEPENDING arms where `Max` is real. The
runtime's `StoreComponentAt` ignores the maximum of a table component (it recreates the table from the carrier), so no
runtime change was needed. The emitted C# for an EXTERNAL/BASED group holding a dynamic table now spells the
implementor's maximum in `dynMax` (an oracle difference for the lander to attribute by class).
