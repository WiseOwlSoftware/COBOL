# PB3367 — LANDED — a failed `git add` mid-stamp strands the branch

**Sites:** `scripts/devlog.py` (`stamp`, `run_stamp`, `_git`, `_git_write`, `GitError`, `half_stamp`, `half_stamp_paths`,
`stamp_due`, `finish_half_stamp`), `scripts/orchestrator/enqueue.py` (`land`: the dirty check and the stamp step's exits,
`_stamp`).

Reported 2026-10-18 by the coordinator (wave-1115 clerk lead 6). Register check: PB3023, PB3107, PB3123 and PB3125 are landed and cover other faults.

**Measured.** Branch `worktree-wf_968a1070-783-42` (kb/Work PB3314), attempt log `E:\COBOL-coord\logs\land-lane-worktree-wf_968a1070-783-42-20261018T073428235097Z.log`: `git add -- DEVLOG/2182-pb3314-a-lock-directory-in-the-middle-of-its-rmdir-refuses.md` returned 128 after both gates were GREEN. The same command run by hand minutes later succeeded. Likely cause: a concurrent git process holding the worktree's `index.lock`; UNMEASURED, because stderr was dropped.

**Mechanism.** `scripts/devlog.py#stamp` (about lines 383-412) writes `DEVLOG/<number>-<slug>.md` and unlinks each pending file BEFORE `_git(wt, "add", ...)` with `check=True`. When git fails, the pending file is gone, the numbered file is untracked and the allocator's number is consumed. `#run_stamp` (line 421) then refuses ("has no pending entry to stamp"), so every rerun fails. `#_git` (line 143) captures stderr and `CalledProcessError` hides it.

**Fix direction.** Stage in an order a retry can repeat (or detect and resume a half-done stamp that already holds the number), retry index.lock contention, and print git's stderr on failure. Add a test that fails the add and then reruns the stamp.

**Recurrence 2026-10-18 (branch `worktree-wf_e873df80-6b5-22`, PB1587).** Landing attempt `20261018T224407764780Z`, log `E:\COBOL-coord\logs\land-lane-worktree-wf_e873df80-6b5-22-20261018T224407764780Z.log`: both gates GREEN, then `devlog.py stamp` failed at `git add -- DEVLOG/2225-pb1587-...md` with exit 128 and no stderr in the log (the `_git` capture). The tree was left half-stamped: the pending entry unlinked, 2225 untracked, number 2225 consumed. The same `git add -n` succeeded minutes later, so the cause was transient; no `index.lock` was left behind. The enqueue unit restored the pending entry, removed the untracked file by hand and re-armed the branch.

**Sibling.** `scripts/orchestrator/enqueue.py`'s verdict line misnames the cause as "the branch needs one `DEVLOG/pending-<slug>.md`" when the branch has one and git failed.

**Recurrence 2026-10-21 (branch `worktree-wf_36fbfc86-472-25`, PB3484).** `devlog.py stamp`'s `git commit` exited 128 with its stderr swallowed (the `_git` capture); entry 2330 was left staged and was finished by hand as commit c1b8320b8.

## Landed (2026-10-25, fix-lane wave 20261107 group F, with PB3693)

Re-probed on a planted `index.lock` in a linked worktree: the old `stamp` wrote the numbered entry, unlinked the pending
file, and `git add` exited 128; the rerun said "has no pending entry to stamp" for ever, and `_git`'s capture dropped
git's stderr. Fixed at the one place the stamp writes (`scripts/devlog.py`):

- `_git(check=True)` raises `GitError` carrying git's OWN stderr (it raised `CalledProcessError`, which hides it).
- `_git_write` retries a git write that fails on `index.lock` (`GIT_LOCK_WAITS`, 0.2 s to 4 s) and only on that cause.
- `stamp` is all or nothing and COMMITS inside the transaction: the entry and the pending removals are staged while the
  pending files are still on disk, the files are unlinked only then, and any failure restores the pending bytes, resets
  the index paths and deletes the numbered file before it raises. `run_stamp` prints the error and exits 3 (`EXIT_GIT`).
- An INTERRUPTED stamp (process killed after the unlink; the entry written, the pending file gone, nothing committed) is
  `half_stamp`; `stamp_due` counts it as work, `run_stamp` completes it under the number the entry holds
  (`finish_half_stamp`), and `enqueue.land`'s dirty check sets its paths aside (`half_stamp_paths`) so the lane can land it.
- `enqueue.land` maps exit 3 to exit 2 (the lane retries it once, nothing stamped) and no longer words every stamp failure
  "the branch needs one pending entry": exit 6 now says it needs a pending entry the stamp can number.

Self-tests (`devlog.py`): a held `index.lock` rolls back (bytes, HEAD, index, status clean) and the rerun stamps; a
brief lock is waited out by one retry; an interrupted stamp is completed by the rerun. (`enqueue.py`): exit 3 is exit 2,
other failures exit 6, an interrupted stamp is no "uncommitted path" refusal and a stray edit beside it still is. The
consumed allocator number is not given back: a failed stamp leaves a gap in the numbering, which the landing rule allows
(it asks only for a number above the tree's newest).
