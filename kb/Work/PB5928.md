# PB5928 - a far pointer's token read back as a foreign address after a garbage collection

**Sites:** `src/WiseOwl.Cobol.Runtime/Control/SlotImageTable.cs` (`Note`, `Sweep`), `src/WiseOwl.Cobol.Runtime/Control/PointerImage.cs` (`FarBase`, the
entry records), `tests/WiseOwl.Cobol.Tests.Unit/SlotImageRoundTripTests.cs`.

**Symptom.** A full Unit gate (the run named in `source`) failed
`SlotImageRoundTripTests.DataPointerOf_APointerDisplacedBeyondTheWindow_ReadsBackAsItself_NeverAsAnotherArea` with
"Assert.IsType() Failure: Expected CellPointer, Actual ForeignAddress". The class passes when run alone, and the test passed in earlier full gates.

**The process-wide base state is correct.** The standard leaves a pointer's representation to the implementor (§2023:13.18.60.4 GR23: "Each implementor
defines the precise effect of the USAGE POINTER clause upon alignment, size, representation, and range of values"), and the determination (DOC-A.1-216)
counts bases per PROCESS on purpose: two run units of one process then never hand out the same token, so a token another run unit wrote is foreign
(`ATokenFromAnotherRunUnit_IsForeign_NotNull_AndRaisesOnDereference`), as a machine address is. `RunUnitStateDriftTests` records `s_nextBase` and
`s_lastTagBlock` as the two documented process stores. What a token DECODES to is the run unit's own `SlotImageTable`, which is run-unit scoped. The
test's premise "B's base is A's next" is false when another test images a pointer between A and B, but that premise only made the aliasing check
meaningful; it could not produce this failure, which is on the type of the decoded pointer.

**Root cause.** `SlotImageTable.Note` held an entry STRONGLY only when it was a `CellLife` or a `NamedAddress`, and everything else as a `WeakReference`,
meant for the identity of an addressless pointer (review R1-2). The far-pointer entry PB4925 added, `FarDisplacement`, is a record made for the table that
nothing else references, so it fell into the weak arm: the next garbage collection dropped it while its cell was alive, and `DataPointerOf` answered a
`ForeignAddress`. In the full gate a parallel test (`AnEndedCellLife_IsNotRetainedByTheRunUnitsTable` calls `GC.Collect`, and any allocation-heavy
class triggers one) collected between the image and the decode. For a program: a pointer `SET ... UP BY` 2^31 or more and written to a file reads back,
after any collection, as an address that compares unequal to the pointer it was written from and stays invalid after `SET ... DOWN BY` the same amount,
where the run unit should restore the same pointer (§2023:13.18.5.4 GR4 makes only a reference through a pointer that is "not a valid address of
storage" raise EC-BOUND-PTR; the far pointer itself is a valid value). A silent wrong answer.

**Fix (structural).** Every entry the codec makes for the table derives from `PointerImage.ImagedEntry`, which the table holds strongly and drops only
when its `Ended` says the storage life it names has ended (a `CellLife` and a `FarDisplacement` end with their cell's generation; a `NamedAddress` never
does). The weak hold is a separate method, `NoteIdentity(long, ManagedPointer)`, for the one case that is the program's own value. A new kind of entry is
therefore held strongly by its type, with no list in the table to forget it in.

**Reproduction.** `DataPointerOf_AFarPointer_ReadsBackAsItself_AfterACollection` images a far pointer in a frame of its own, collects, and decodes: before
the fix it failed with the gate's exact message ("Expected CellPointer, Actual ForeignAddress"), deterministically, alone; after it, it passes. The
original test's premise is also made deterministic: the displacement that would alias B is read from the two images instead of assumed to be 2^32.

**Sibling sweep.** `new WeakReference` occurs once in `src/` (the identity hold). The runtime's writable statics are exactly the ones
`RunUnitStateDriftTests.ProcessLifetimeStatics` lists: the two image counters (above; no test assumes adjacent values after this change, and the foreign-token
tests use values 2^29 bases away from the epoch), the collation latches and warm-up status (their tests share the `process-globals` collection), the
console-encoding latch, and two `[ThreadStatic]` fields. No other test reads a process-wide counter's next value.
