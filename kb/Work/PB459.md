# PB459 — one guard the standard states four times, written once

**Rows:** `GR-14.9.39.4-1`, `-3`, `-4`, `-29`, `-L2.1`, `-L2.2`, `-L2.3`. From the b2 adjudicators
`set-statement-p4` and `set-statement-p5`. **Every repro below was re-run on the HEAD `cobol.exe`
(base 89044aa0)**; all reproduce unchanged from the 5fe593a0 pin.

## THE MECHANISM — part 1: the integrality test that exists on exactly one arm

§14.9.39.4 states the same guard once per amount-taking format, each time with the same three consequents
(condition set to exist · the SET unsuccessful · the receiving operand unchanged), differing only in the
exception-condition NAME:

| rule | format | condition |
| --- | --- | --- |
| GR2 a) 1. a (row `-L2.1`) | Format 1, `SET index-name TO arithmetic-expression-1` | EC-BOUND-SUBSCRIPT |
| GR3 (row `-3`) | Format 2, `SET index-name UP/DOWN BY arithmetic-expression-2` | EC-BOUND-SUBSCRIPT |
| GR19 | Format 10, the data-pointer amount | EC-SIZE-ADDRESS |
| GR29 (row `-29`) | Format 14, the dynamic-capacity amount | EC-BOUND-SUBSCRIPT (nonnegative INTEGER) |

**GR19 is implemented, and implemented well.** `PtrEmitter.cs:82-101` deliberately does NOT collapse the amount
to a `long` before the runtime sees it — it splits on `x.Real` / `x.Scale == 0` and keeps the fraction alive, so
`CobolPtr.UpByScaled`'s `scaledBy % pow != 0` (`CobolPtr.cs:104`) and `UpByReal`'s `by != Math.Truncate(by)`
(`CobolPtr.cs:154`) can raise the named condition and return the operand unchanged. kb/Work PB151 was the
landing that stopped a `(long)(double)` truncation from bypassing it.

**The other three arms discard exactly that shape.** Each renders one truncating cast and stores the result:

```
SetEmitter.cs:28   long __set… = (long)(NumericRenderer.Align(num.Render(s.Value,  …), 0));   // EmitSetTo
SetEmitter.cs:86   long __set… = (long)(NumericRenderer.Align(num.Render(s.Amount, …), 0));   // EmitSetUpDown
SetEmitter.cs:96   long __cap… = (long)(NumericRenderer.Align(num.Render(s.Amount, …), 0));   // EmitSetCapacity
```

and the only screen downstream is `CobolDynTable.cs:134  long target = n < _min ? _min : n;`. **The asymmetry
IS the bug** — one dispatch, four arms, one finished (`feedback_two_arm_dispatch`, the project's most
reproducible defect shape).

## THE MECHANISM — part 2: an index-name is a bare `long` with no table

GR1 exists so the rest of the clause can say *that table*: GR2 a) 1. b, GR2 a) 3. b and GR4 a) all turn on
whether a value is "outside the limit specified in General rule 2 of 13.18.38, OCCURS clause", and GR2 a) 3. a
distinguishes an index-name "associated with the same table" from one that is not.

The association IS built — `DataBinder.cs:2781-2789` does `item.IndexNames.Add(idxName)` on the OCCURS-bearing
item and `SearchBinder` reads it — but **only in the table→index direction**. `DataBinder.IndexFields`
(`:136`) is `name → C# cell` and carries nothing else, and `SetBinder.cs:435-438 SetTargetOf` hands the emitter
`SetIndexTarget(ix.IndexField)`: a `long` with no owner. So no SET receiver can ask which table it indexes or
what that table's bound is, and every range obligation in Formats 1 and 2 has nowhere to live.

The consequence is total and mechanically checkable:

```
$ grep -rn 'EC-RANGE-INDEX' src/ --include=*.cs
src/Cobol.Net.Compiler/CodeGen/Verbs/SetEmitter.cs:23          (a comment conceding it)
src/Cobol.Net.Compiler/Validation/FlagConformancePass.cs:49,503,506,522,533,535   (a >>FLAG-02 e flagger)
src/Cobol.Net.Frontend/Preprocessor/FlagDirective.cs:67        (the directive description)
src/Cobol.Net.Runtime/Exceptions/ExceptionCatalog.cs:162       L3("EC-RANGE-INDEX", EcFatality.Fatal)
```

**Four hits, none of them a raise.** The `FlagConformancePass` site is the trap worth naming: it reads
`_turn.Enabled("EC-RANGE-INDEX", …)` and flags the SET, so the condition looks wired to anyone grepping for the
name, while it can never occur (`feedback_green_gates_arent_evidence` in its purest form).

`SetEmitter.cs:22-24` states the position honestly — "Range checking (EC-RANGE-INDEX) awaits the EC model —
COBOL-85 has no exception conditions, so the unchecked store IS the 85 semantics". That is right for `--std 85`
and wrong for the other three editions this compiler must ship.

⛔ **The premise is easy to get wrong and must not be:** the limit the four arms cite is the IMPLEMENTOR'S index
range, not the table's bounds. Every one of them ends "…even if that occurrence is not a valid occurrence within
this table", so an index pointing past its table is LEGAL and must not raise. Writing a table-bounds check here
would reject legal programs.

**Expected.** GR3 / GR2a1a / GR29: the receiving operand is unchanged and the named condition is set to exist —
EC-BOUND-SUBSCRIPT is Fatal in Table 13, so under an enabling `>>TURN` the run unit takes the condition (a USE
declarative may RESUME) instead of printing a moved value. GR29 in particular: GR30's minimum-capacity clamp
CANNOT stand in for it — the clamp is the rule for a legal new capacity below the OCCURS minimum, and GR29
rejects the operand *before* any new capacity is computed. GR4 a) + §13.18.38.4 GR2: the second `UP BY` cannot
be represented, so the fatal EC-RANGE-INDEX is raised and IDX stays at 9223372036854775801.

**What is deliberately NOT charged.** The §3.5 model in which an index IS its 1-based occurrence number makes
GR2 a) 3. a's "same table ⇒ content placed unchanged" and 3. c's "different table ⇒ the corresponding occurrence
number" the SAME machine operation, so the VALUE half of Formats 1 and 2 is correct and needs no association at
all — which is exactly why the missing reverse map went unnoticed for so long. It is the RANGE half that has
nowhere to live.

## THE CODE SITES AND THE SHAPE OF THE REPAIR

| site | arm |
| --- | --- |
| `CodeGen/Verbs/SetEmitter.cs:25-30` `EmitSetTo`, `:83-88` `EmitSetUpDown`, `:94-105` `EmitSetCapacity` | the three truncating casts |
| `CodeGen/Verbs/SetEmitter.cs:127-147` `StoreSetTarget`, `:152-172` `AugmentSetTarget` | the ONE store/augment pair PERFORM VARYING and SEARCH also ride |
| `Runtime/Values/Tables/CobolDynTable.cs:122-138` `SetCapacity` (+ `:140`,`:143` UpBy/DownBy) | clamps, never rejects |
| `Binding/DataBinder.cs:136` `IndexFields`, `:2781-2789` the one-directional registration | the missing index→table edge |
| `Binding/Procedure/Verbs/SetBinder.cs:435-438` `SetTargetOf` | mints `SetIndexTarget(cell)` with no owner |
| `Runtime/Exceptions/ExceptionState.cs:409` `SubscriptError` | the raiser that already exists and is never called from here |
| the model done right, for contrast: `CodeGen/Verbs/PtrEmitter.cs:75-102` + `Runtime/Control/CobolPtr.cs:96-112` | |

⛔ **Two structural repairs, not five inline `%` tests** (CLAUDE.md rule 5):

1. **ONE amount landing.** A `SetAmount` that returns (value, isIntegral, isNegative) and lets each format name
   its own exception condition, consumed by `EmitSetTo`, `EmitSetUpDown`, `EmitSetCapacity` and (already
   correct) the pointer arm — and by PB458's literal-alternative screen on the compile-time side. Written as
   two more hand-rolled tests, Format 16's arithmetic-expression-5 (whose sign test the code DOES carry, in
   `CobolDynString.SetSize`) becomes the fourth hand-written copy.
2. **Give the index-name symbol its table.** `SetIndexTarget(cell, table)` carrying the OCCURS bound and its
   ODO / dynamic-capacity variability, so GR2 a) 1. b, GR2 a) 3. a/b/c and GR4 a) all become ONE guarded store.
   The check is against the IMPLEMENTOR range (§13.18.38.4 GR2), which for a `long` cell means the arithmetic
   must detect 64-bit overflow — not a table-bounds test. And the chosen range must be DOCUMENTED (§A.1 128;
   PB460's row) or the check is unverifiable by a user.

Pair both with a drift test so "automatic" stays true: a test that fails if a new `SET`-family emitter path
renders a bare `(long)` narrowing of an amount.

## THE SIBLING SWEEP

* `StoreSetTarget` / `AugmentSetTarget` are shared with **PERFORM VARYING** (§14.9.28 GR13) and **SEARCH** —
  both inherit the missing integrality test and the missing range check. Fixing SET without them leaves the same
  hole one verb over.
* Every `--std` edition: the unchecked store IS COBOL-85's semantics, so the new raises must be gated to
  2002/2014/2023 and must not fire at `--std 85` (`feedback_edition_gate_sweep`).
* `FlagConformancePass.cs:503-535` should be re-read once the raise exists — a flagger for a condition that
  cannot occur is a false green, and it must keep flagging the right statements once the condition is real.
* `ExceptionCatalog.cs:162` (EC-RANGE-INDEX) is not the only catalog row with no raise site; sweep the catalog
  for siblings (EC-BOUND-SET is one — PB460; EC-RANGE-PTR is another — PB460/PB465).
* GR29 sits inside Annex A.4.4, which `docs/CONFORMANCE.md` §5 marks **Claimed** — see PB460.
