# PB621 — OPEN — the boundary is honest now; it is also further in than it needs to be

`crashes: true` is the harm flag because that is what the user's program DOES: a conforming program terminates the
run unit with a fatal EC-SIZE-OVERFLOW (or takes ON SIZE ERROR) where the value was representable in its receiver.
The termination is controlled and spec-permitted; it is still the program not completing.

Found 2026-09-05 by the `PB252` implementer (report §"New defects" (A)), whose landing turns the wrap into a
§14.7.5 r5 size error; this note is the QUALITY gap left behind it, and it is deliberately a separate mechanism
(PB252 removes the WRAP; this pushes the boundary OUTWARD).

## Repro (`tests/conformance/2002/pb252_native_carrier_boundary.cob`, case 2, on PB252's tree)

`FUNCTION RANGE` over ±1.7e30 with a `PIC SV9(8)` item in the same list, receiver `PIC S9(31)`: §15.76.4 r1's value is
1.7e30 − (−1.7e30) = 3.4e30, 31 digits, which FITS the receiver; the native arm aligns the list to scale 8, so the
intermediate is 3.4e38 and escapes the carrier. The program answers `RANGE-CONFORMS=SIZE-ERROR` where
`RANGE-CONFORMS=VALUE` was available.

## The rule, and why this is quality rather than conformance

§14.7.5 r5 permits the raise — "if native arithmetic is in effect and the implementor defines that the range of
values allowed for the intermediate data item is to be checked, when an arithmetic operation on the intermediate
data item would cause the new value to be outside of the allowed range" (`OK §14.7.5 5)`) — so the size error is a
conforming outcome, which is why PB252's golden pins the DISJUNCTION (the value, or the size error with the receiver
unchanged) and not either branch. A conforming compiler may do this; a commercial one should not when the value was
representable and the receiver told it so.

## The mechanism

`src/Cobol.Net.Compiler/CodeGen/Emit/IntrinsicRenderer.cs`: `AlignedArgs` / `AlignedArgsEx` align every argument to
the LIST's maximum scale, and the `SumScaled`, `RangeScaled`, `MeanScaled`, `MedianScaled`, `MidrangeScaled` arms
consume that. PB65 already solved the same problem for MAX/MIN: `MaxAt`/`MinAt` take the RECEIVER's scale when one is
known (`bool store = !num.Receiver.Receiverless && !num.Receiver.Real`) instead of the list maximum. `AlignedArgs`
has no such arm.

## Fix shape

Give `AlignedArgsEx` the receiver-scale arm PB65 gave `MaxAt`/`MinAt` — when a fixed-point receiver is known, align
to `max(receiver scale, the scale §15.x's returned-value rule needs)` rather than the list maximum, so the
intermediate carries no digits the result cannot keep; receiver-less and float contexts keep the list maximum. The
scale a returned-value rule NEEDS is per function (SUM/RANGE: the receiver's; MEAN/MEDIAN/MIDRANGE: the receiver's
plus one guard digit for the halving/division, per §14.6.9 truncation) and belongs on the catalog row, not in the
arm. Widen PB252's golden case 2 from the disjunction to the VALUE once the boundary moves; keep the disjunction
form for a case that overflows the receiver itself (§14.7.5 r3) as the control. Drift: every `CrossAlignedNativeArms`
member reads its alignment scale through the one receiver-aware helper.
