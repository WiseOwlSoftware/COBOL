# PB1532 — LANDED (w68w)

## The rules

> An instance object is destroyed either when it is determined that the object cannot take part in the continued execution of the run unit, or when the run unit terminates, whichever occurs first.

`cite.py --check 9.3.14.3 "An instance object is destroyed either when it is determined that the object cannot take part in the continued execution of the run unit"` → OK §9.3.14.3.

> — For file connectors in an object when the object is deleted.

`cite.py --check 9.1.4 "For file connectors in an object when the object is deleted"` → OK §9.1.4 (the implicit-CLOSE list).

## Repro (adjudicator + refuter `adj-a1-w1-s4`; probes committed at `adjudication/adj-a1-w1-s4/probes/gc1.cob`, `gc2.cob` on that branch)

`gc2.cob`: a loop creates an object that opens its own file OUTPUT and writes without CLOSE, drops the reference, forces
allocation; the next object's OPEN OUTPUT → `K=00000002 OPEN-OUTPUT=61` (re-confirmed by the adjudicator at the pin). `gc1.cob`:
the record is never flushed after ~4M allocations (READ = 10).

## Mechanism and code sites

The GC does determine unreachability and runs the finalizer — `src/Cobol.Net.Runtime/Control/CobolObject.cs` (~l.88,
`foreach (var k in fs) CobolFile.EnqueueInstanceClose(k)`) — but `CobolFile.EnqueueInstanceClose` reaches the registry through
`src/Cobol.Net.Runtime/Control/RunUnit.cs#Current` (`_current.Value ??= new RunUnit()`), an AsyncLocal that is EMPTY on the finalizer
thread, so the close is queued on a fresh orphan RunUnit. Only `CobolFile.CloseAll` at run-unit termination closes the file.

Fix: the object captures its OWNING run unit (or registry) at construction and the finalizer enqueues on that; never resolve
ambient run-unit state from a finalizer or thread-pool thread.

Every finalizer / thread-pool / timer caller of `RunUnit.Current` (PB1069 is the run-unit-scoping family). Row `DOC-A.1-113`

## Landed — w68w (fix-lane group W, branch `worktree-wf_e9a82a33-6b6-6`)

Re-probed on the w68w build before the fix: `unit:InstanceFileFinalizerTests.AnUnreachableObjectsFile_IsClosedInItsOwnRunUnit_BeforeTheNextOpen`
(an object tracks an OPEN OUTPUT instance connector, is dropped, `GC.Collect` + `WaitForPendingFinalizers`, then a
second connector opens the same file OUTPUT) printed `Expected "00" / Actual "61"` with the finalizer resolving
`RunUnit.Current` — the note's mechanism exactly. **Fix, at the one place:** `CobolObject.__TrackInstanceFile`
captures the creating run unit's `FileRegistry` (on the constructing thread) with the first tracked file, and
`~CobolObject` enqueues every close on THAT registry; the `CobolFile.EnqueueInstanceClose` facade — the ambient
resolution from the finalizer thread — is deleted. The same test is green on the fix (the creating run unit's next
OPEN drains the close). **Sibling sweep:** `rg "^\s*~[A-Z]\w*\(\)|Task\.Run|ThreadPool\.|new Timer\(|new
Thread\(|Parallel\.|ProcessExit|CancelKeyPress|PosixSignalRegistration" src` → the ONLY off-thread entry into the
runtime is `~CobolObject` (the CLI's `Parallel.ForEach` never touches a run unit), so no other caller resolves ambient
run-unit state from a finalizer, thread-pool or timer thread. DOC-A.1-113 (the determination already said "in the run
unit that created the object") is CONFORMS with the witness; batch `w68w/batch-w68w-PB1532.json`.
