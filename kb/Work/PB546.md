# PB546

## Mechanism — usage-clause-p3
usage-p3/F2 — ONE national leaf has TWO widths and the consumers split: DataItem.ElementaryByteWidth answers `2 * ElementaryImageWidth` (the documented D-N1 UTF-16 model, what FUNCTION BYTE-LENGTH / FUNCTION LENGTH / the declared group size report) while DataItem.IsCharacterImage/ImageWidth deliberately contributes the leaf's CHARACTER positions ("never byte-doubled for national"), which is what the group-image codec and every channel built on it lay out. Every leaf DECLARED after a national leaf therefore sits at half the offset the model published, and a group MOVE, a reference-modified group and a CALL BY REFERENCE window all read the wrong bytes with no diagnostic. The FILE-record channel refuses the same shape LOUD (COBOLNET0899), so one of the four byte channels is honest and three are silently wrong — and the drift test that exists to catch exactly this, ImageWidthIsStorageWidthTests, carves national out by name and calls it "the ONE sanctioned divergence", so it can never go red over it. This is PB188's landed shape (a wrong-width window "silently shifting every following member of the group image") repeated for the national leaf, and no kb/Work note owns it: PB327 owns the FILE channel only, PB231 the BASED/ALLOCATE refusal, both rejects-legal-source rather than wrong-answer.

### Expected, from the standard
13.18.60.4 GR8 (cite.py --check OK): "National characters shall be represented in the storage of the computer as characters of a uniform size equal to or a multiple of the size of characters in the computer's alphanumeric character set. Each implementor shall specify the size and representation of characters stored for usage NATIONAL." ONE uniform size, everywhere. COBOL.NET's specified size is 2 bytes per national position (D-N1; docs/CONFORMANCE.md DOC-A.1-33 names UTF-16BE as the storage form and DOC-A.1-209 relies on "the national determination is 2 bytes per position" to satisfy GR7's own <= test). So for `01 G. 05 N PIC N(2). 05 A PIC X(2).` the group is 6 bytes with N at bytes 1-4 (00 41 00 42) and A at bytes 5-6: BYTE-LENGTH-G=6, A-AT-5-6=[YZ], and a callee with `01 W PIC X(6)` reads 0,65,0,66,89,90 through FUNCTION ORD minus one.

### Observed
Measured with the pinned compiler at --std 2023. q73: BYTE-LENGTH-G=6, LENGTH-G=6, BYTE-LENGTH-N=4 — the model publishes the 2-byte size — but A-AT-3-4=[YZ] and A-AT-5-6=[  ]: the alphanumeric leaf declared at bytes 5-6 is actually at 3-4 and the declared tail is blank. q52 (CALL BY REFERENCE into `01 W PIC X(6)`) returns ORD 66 67 90 91 33 33 = A,B,Y,Z,space,space — the same halved layout across a program boundary. q25/q27 (group MOVE into PIC X(8)) return the same. q60 writes the same record shape to a SEQUENTIAL file and is refused: COBOLNET0899 "national data in a file record (data item 'N' of record 'R') is recognized but not yet implemented - the record codec is single-byte and the national character is two bytes (Phase 4a residue; ISO 8.1.2 / 13.18.60.4 GR8)". The code states the split in its own comments: DataItem.cs ElementaryByteWidth `Usage.National => 2 * ElementaryImageWidth` versus IsCharacterImage's "national and boolean leaves ... contribute their CHARACTER positions to a group image (ImageWidth = Length - never byte-doubled for national)", while IsImageCapable's doc comment asserts "ImageWidth ... IS ByteWidth for every item that reaches an image - the ONE-WIDTH invariant". tests/Cobol.Net.Tests.Unit/ImageWidthIsStorageWidthTests.cs#NationalLeaf_IsExactlyTwoBytesPerPosition asserts ImageWidth 4 / ByteWidth 8 and labels it sanctioned, which is why no gate is red today.
