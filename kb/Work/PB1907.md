# PB1907 — what WiseOwl COBOL does where the standard says "undefined"

## The owner's direction (2026-10-01, verbatim)

"What I would like is to determine what the best/appropriate/current behavior we provide judged against what other
implementations do in each case, document our behavior as what we do in these undefined cases, then produce a golden
that validates our now documented behavior doesn't drift over time."

## Why these six rows exist

Six inventory rows are verdicted CONFORMS and owe a witness, and golden-lane batch gl4 (DEVLOG 1834) found nothing a
golden could pin to the STANDARD, because the standard defines no result. Each rule is listed in Annex A.2, and §4.4
says a run unit that allows such a situation to happen "is a conforming run unit, although the resultant execution is
not defined by standard COBOL" (`cite.py --check 4.4 "A COBOL run unit that allows these situations to happen is a
conforming run unit"` → OK, §4.4 2)).

| Row | Rule | Annex A.2 item |
|---|---|---|
| GR-14.6.10-1 | operands not described by the same data description entry overlap: result undefined | 36 |
| GR-14.9.22.4-13, -18, -21 | INSPECT: an operand occupies the same storage as the INSPECT or tallying identifier | 21 d), e), f) |
| GR-14.9.48.4-18 | UNSTRING: overlapping sending, delimiter, count, pointer or tallying operands | 61 |
| GR-14.9.51.4-13 | WRITE: bytes beyond the end of record-name-1 are undefined | 64 |

## What the owner decided is the closing shape

The behavior is implementor-defined in effect, so it is a documented implementor choice (CLAUDE.md rule 1: ISO where
it controls, otherwise GnuCOBOL, otherwise IBM Enterprise COBOL or Micro Focus; that precedence settles latitude only).
Per case: (1) measure what WiseOwl COBOL does today, (2) survey GnuCOBOL (the tarball `tests/external/gnucobol-3.2.tar.xz`
carries the libcob source; no `cobc` is installed here), IBM Enterprise COBOL and Micro Focus, (3) pick the behavior
and write it into `docs/CONFORMANCE.md` as what we do in the undefined case, (4) land a golden pinning the documented
behavior so it cannot drift, citing the rule and the A.2 item, (5) record the verdict with `record_verdicts.py`. This
is NOT a section 8 owner-signed "no observable obligation" derivation; the owner chose to document and pin instead.

## INSPECT part landed (wave 1002 group A)

Rows GR-14.9.22.4-13, -18 and -21 are closed (`closes_rows`); docs/CONFORMANCE.md §3.1 carries D-INS1 to D-INS4 and
`tests/conformance/85/pb1907_inspect_{tally,format3_counter,replacing,converting}_overlap` pin them. GnuCOBOL 3.2 was
measured on every repro. Two changes of behavior, one mechanism: `InspectEmitter.EmitBody` re-reads identifier-1 (and
re-runs the shared cycle for a later TALLYING operand) after a counter store whenever `StorageOverlap.MayShareStorage`
cannot prove the counter disjoint from what the statement reads. REPLACING and CONVERTING already matched GnuCOBOL and
changed nothing. Survey correction: the survey's tally golden pinned the old behavior (`21A1A1`); the measured
GnuCOBOL and now-ours value is `31A1A1`. The note stays open for the other rows (GR-14.6.10-1, GR-14.9.48.4-18,
GR-14.9.51.4-13), owned by the other wave-1002 groups.

## Landing — WRITE and REWRITE past the record (wave 1002, group C)

Rows GR-14.9.51.4-13 and GR-14.9.35.4-15 closed (the REWRITE row was never in `inventory_rows`; it is the same
mechanism). The note stays open for the INSPECT and UNSTRING rows other groups carry. Determination D-WRT1
(docs/CONFORMANCE.md §3, "Implementor behavior in Annex A.2 undefined cases"): a byte past record-name-1 is the
record area's content at its position, a position no record description occupies is a space, and the NUMBER of
bytes stays ISO (§13.18.43.4 GR13 a), GR6) — GnuCOBOL's length clamp is not adopted (owner, 2026-10-01).
Code sites, for `orient.py`:
- `src/Cobol.Net.Compiler/Binding/Model/FileModel.cs#TransfersPastRecord` — the ONE predicate: not LINE SEQUENTIAL
  (GR21/GR22/GR17 c) define that transfer), record-name-1 in line and narrower than `AreaRecord`, and the length
  comes from DEPENDING ON or a fixed-length file. REUSE it for RELEASE.
- `src/Cobol.Net.Compiler/CodeGen/Verbs/SequentialIoEmitter.cs#SentRecordImage` — the one image helper, called by
  `EmitWrite`/`EmitRewrite` and `KeyedIoEmitter.EmitWrite`/`EmitRewrite`; the runtime's `FileConnector.Stored`
  is unchanged. Trap: a varying file without DEPENDING must NOT get the area image, `Stored` would take the image's
  length as the record length.
- Goldens `conformance:85/pb1907_write_past_record`, `pb1907_keyed_rewrite_past_record`,
  `conformance:2023/pb1907_past_record_whole_record` (the third was mutation-tested: dropping the line sequential or DEPENDING
  conditions turns L1, L2 and N1 red).
Open lead: RELEASE past the record (A.2 item 45, row GR-14.9.32.4-6, PARTIAL) shares the predicate but first needs
the implied RECORD format of a multi-01 SD decided (`SortBinder.BindRelease` releases at record-name-1's own size).

## Landed — overlapping MOVE and arithmetic operands (GR-14.6.10-1, wave 1002 group D)

Documented as D-OVL1 (the snapshot every overlapping MOVE and ADD performs) and D-OVL2 (the two corners aligned with
GnuCOBOL 3.2.0 on the owner's 2026-10-01 choice) in `docs/CONFORMANCE.md` §3, pinned by
`conformance:85/pb1907_overlap_move` (21 lines, identical to a built cobc's output). The corners are decided at bind
time by `MoveOverlap.Classify` over `StorageExtent` (the compile-time overlap fact) and carried on `MoveStore.Prefill`;
`MoveEmitter.EmitOverlapPrefill` renders them, so a MOVE that cannot be proven to overlap emits what it always did.
Held by `MoveOverlapDriftTests`. GnuCOBOL differences measured and NOT adopted (documented in D-OVL2): a numeric
DISPLAY sender into a shorter JUSTIFIED RIGHT item keeps its leftmost digits there (not an overlap effect, contradicts
§13.18.32.4), and a signed sender's sign is re-punched after the move (a negative zero).

## Landed — UNSTRING part (wave 1002, group B)

Row `GR-14.9.48.4-18` closed. `docs/CONFORMANCE.md` "Implementor behavior in Annex A.2 undefined cases" carries
D-UNS1 to D-UNS4. The change: `StringEmitter.EmitUnstring` re-reads the sender and identifier delimiters before each
receiving area after the first wherever a store can reach them (`StorageSharing.MayShare`, the one conservative
overlap predicate); DELIMITER IN receives the live delimiter content (`CobolStringOps.MatchedDelimiterIndex`); the
TALLYING item receives its content at the end plus the count, stored before the POINTER. Goldens
`conformance:2023/pb1907_unstring_overlap_{sender,delimiter,tallying,pointer,linkage}`, drift test
`UnstringLiveReadDriftTests`. All four cases measured byte-equal to GnuCOBOL 3.2 except one documented difference:
a `DELIMITED BY ALL` run is consumed before the INTO store here, after it in libcob (matters only for an ALL
delimiter the same statement overwrites; pinned as ours in the delimiter golden, leg B2).
