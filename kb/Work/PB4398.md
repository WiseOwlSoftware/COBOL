# PB4398 - LiveProcess's non-observation carries none of the evidence ProcessObserver's does

**Sites:** `tests/_shared/LiveProcess.cs#LiveProcess.ReadLine` (the timeout arm) and its one caller family,
`tests/WiseOwl.Cobol.Tests.Unit/RunUnitProcessBoundaryTests.cs#StartHolder` and the cases that read a holder's line.
The model to follow is `tests/_shared/ProcessObservation.cs#ProcessObserver.Observe`, which samples
`HostLoad.Sample()` at the start, and on a timeout reports `HostLoad.Describe(...)` and the child's own
`TotalProcessorTime` "so a reader can tell a starved process from a hung one" (PB3108's design).

**Witness.** Wave 20261808, group A (PB4204 chain, a tooling change, so the whole population ran), fix round 2 gate
`E:\COBOL\.claude\worktrees\wf_01545e8c-f44-36\TestResults\build-local\000002-20261101T204232Z` at `2fdefc6a6`:
RED on one Unit case of 39,225,
`RunUnitProcessBoundaryTests.ARefusedOpen_ReachesTheProgramsHandlers_WithAndWithoutAFileStatusAndADeclarative`:

    HarnessNonObservationException : ⛔ HARNESS NON-OBSERVATION — no stdout line from
    'dotnet "...\pb2485_holder_noother\pb2485_holder_noother.dll"' within 120000 ms (WISEOWL_COBOL_RUN_TIMEOUT_MS)
      at LiveProcess.ReadLine() (LiveProcess.cs:56) <- ExpectLine() <- StartHolder(...) (RunUnitProcessBoundaryTests.cs:214)

The same gate's Conformance population took 5,718 s (three gates held the pool's three slots), so the host was
loaded. But the holder's work directory is per-test (`ScratchDirectory.Create("pb2485w-")`), so no fixed path is
shared between concurrent gates, and the message cannot say whether the holder used any processor time at all, or
whether it was stuck in its `OPEN` (a lock it was waiting for) or never got scheduled. The agent re-gated the same
tip with no change (run `000003-20261101T223131Z`): the owner's rule (2026-10-10, kb/Work PB2590) is that a load- or
timing-sensitive red is a defect to root-cause, never a flake to re-gate past, and this message gives the next reader
nothing to root-cause it with.

**Mechanism.** PB3108 replaced the fixed 120 s run budget with `ObservationBudget` and made `ProcessObserver`'s
timeout carry host load and the child's processor time. `LiveProcess` (added by PB2485 for a process that STAYS
ALIVE) took `ObservationBudget.UnitMs` but not the evidence: its timeout arm throws a bare message. It is the one
child-process instrument that sat outside PB3108's sweep.

**Fix (the shape that makes the next instrument automatic).** One timeout reporter for both instruments: move the
"budget, work, own processor time, host load across the attempt" text that `ProcessObserver.Observe` builds into one
member both call, sample `HostLoad` when `LiveProcess.Start` launches the child, and have `ReadLine`'s timeout report
the child's `TotalProcessorTime` (and whether it has exited) through it. Pair it with a drift test that every
`HarnessNonObservationException` raised for a timeout goes through that reporter (no second literal message), so a
third instrument cannot repeat this. Then root-cause the witness itself with the evidence the new message gives: a
holder with near-zero processor time after 120 s is starved or blocked (find what it waits on), and one that spent
its budget is slow (find why one `OPEN` costs that much).
