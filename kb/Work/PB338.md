# PB338 — the governed READ decides after the position has moved

**Rows:** `GR-14.9.30.4-10`, `GR-14.9.30.4-11`, `GR-14.9.30.4-13`, `GR-14.9.30.4-18`. Two adjudicated mechanisms
plus the batch-1 refuter's GR13 finding, all one root.

## Part 1 — the position moves before governance decides (GR10 a/d, GR13 a, GR18)

**GR10 (keyed, status 51).** `out-b1/probe/keyedfpi/KEYEDFPI.cob` — two RELATIVE connectors F-A and F-B over one
file (`SHARING WITH ALL OTHER`, `LOCK MODE MANUAL`), records 1/2/3 = AAAAA/BBBBB/CCCCC; `OPEN I-O` both;
`READ F-A WITH LOCK`; `READ F-B`; `UNLOCK F-A RECORD`; `READ F-B`. Observed `A1=00 AAAAA` / `B1=51 RK=0000` /
`UNLA=00` / `B2=00 BBBBB RK=0002` — **the record the READ failed on is silently skipped.**

**GR18 (sequential, status 53/54).** `out-b1/probe/lock54/LOCK54.cob` — one RELATIVE connector, ACCESS DYNAMIC,
`LOCK MODE MANUAL WITH LOCK ON MULTIPLE RECORDS`, 20 records; sixteen `READ NEXT ... WITH LOCK`, then UNLOCK,
then `READ NEXT`. Observed `READ0016=54 RK=0015` / `UNLOCK=00` / `AFTER54=00 RK=0017`.

> §14.9.30.4 GR10 a): If the record operation conflict condition exists as a result of the READ statement: a) The
> file position indicator is unchanged

> GR10 d): The key of reference for indexed files is unchanged

Both `--check 14.9.30.4` → **OK**. So B's next sequential READ must select the SAME record: `B2=00 AAAAA
RK=0001`. For the lock-limit denial, §12.4.5.9.4 GR7 makes the statement unsuccessful and no rule exempts it
from GR18, so the indicator is set to indicate that no valid record position has been established and the next
sequential READ is '46' (§9.1.13.7 item 6 b) — never RRN 17.

**GR13 a) is the same requirement restated, and it was read as its unconditional half.** GR13 a) is not *the FPI
is set*; it is *the I-O status is updated AND, if the record operation conflict condition did not occur, the file
position indicator is set*. Under a conflict the FPI must not move.

**Mechanism.** `FileRegistry.ReadShared` (sequential) computes `SequentialConnector.NextReadOrdinal` BEFORE the
read and is correct for the 51 case; its own summary states the reason. `FileRegistry.ReadLockGovern` (keyed) is
called from `KeyedIoEmitter.EmitRead` only AFTER `var __kst = CobolFile.FileReadKeyedNext(...)`, by which point
`RelativeConnector.ReadSequential` has set `_fpi`/`_inclusive`/`_positioner`/`_lastSlot` and
`IndexedConnector.ReadSequential` has set `_fpiKey`/`_fpiArrival`/`_lastReadPrime`; `IndexedConnector.ReadRandom`
additionally assigns `_refKey = keyIndex` before any lookup, which is GR10 d). Its own doc-comment admits the
shape (*the keyed shape is post-read*), and the comment at `FileRegistry.cs:585` — *FPI kept (GR10a)* — is
exactly backwards for this arm: *kept* there means *kept as the read left it*, not *unchanged*.

The SEQUENTIAL arm shares the defect on its OTHER exit: `ReadShared`'s
`if (ok && ApplyReadLockDiscipline(...) is not null)` runs after `f.Read` has already called
`FileConnector.ReadSucceeded`, which advances the ordinal, sets `PrevOpWasSuccessfulRead` and CLEARS
`LastReadUnsuccessful` — so a 53/54 denial leaves a successful-looking position behind a failure status.

## Part 2 — GR11 a) is conditioned on the READ succeeding

`out-b1/probe/gr11a/GR11A.cob` — two SEQUENTIAL connectors over one file (`SHARING WITH ALL OTHER`, `LOCK MODE
MANUAL` = single record locking); three `READ F-A WITH LOCK` (A ends holding ordinal 3); an at-end
`READ F-A` (status 10); then three `READ F-C`. Observed `C3=51 BBBBB`; expected `C3=00 CCCCC`.

> §14.9.30.4 GR11 a): If single record locking is specified for the file connector associated with file-name-1,
> any prior record lock associated with that file connector is released by the execution of the READ statement

`--check 14.9.30.4 "any prior record lock associated with that file connector is released by the execution of
the READ statement"` → **OK** — no success qualifier, and the standard qualifies DELIBERATELY elsewhere (11 b)
*at the completion of the successful execution*, 11 c/d *a successfully accessed record*). §12.4.5.9.4 GR6 says
it outright: *Execution of any I-O statement except START releases any previously locked record in that file for
that file connector* (`--check 12.4.5.9.4` → **OK**). A's at-end READ is an executed I-O statement.

`FileRegistry.ApplyReadLockDiscipline` performs the release, but neither caller reaches it on a failure:
`ReadLockGovern` returns early on `statusJustRead.Length == 0 || statusJustRead[0] != '0'`, and `ReadShared`
guards with `if (ok && ...)`. **The sibling verbs prove the intended shape:** `WriteShared`, `RewriteShared` and
`DeleteShared` each call `ReleaseAllForConnector`/`ReleaseAllExcept` UNCONDITIONALLY, before the operation,
exactly as GR6 requires. READ is the odd arm.

## The fix shape

One shape for both organizations: identify the record the READ would make available BEFORE committing the
position (the keyed connectors already re-derive their position per READ, so a peek-then-commit split is
available), and make the position commit conditional on the GOVERNANCE outcome rather than on the physical read.
Lift the GR11 a) release out of `ApplyReadLockDiscipline` to the top of BOTH READ entries, before the conflict
check, mirroring the mutating verbs — so §12.4.5.9.4 GR6 lives in one place for all four verbs instead of two.

**No existing test sees any of this:** `unit:CobolFileLockTests.ReadShared_SequentialOrdinals_Conflict51_AndAdvancingOnLockSkips`
and `conformance:2002/file_sharing_seq` exercise only the sequential 51 path, which is the arm that is right; the
GR13 test-refs the adjudication cited all exercise items b)/c) or the sequential organization only.

**Code sites:** `FileRegistry.cs#ReadLockGovern`, `#ReadShared`, `#ApplyReadLockDiscipline` ·
`IndexedConnector.cs#ReadRandom` · `FileConnector.cs#ReadSucceeded` · `KeyedIoEmitter.cs#EmitRead`.
