# PB3191 — a declared constant-name as a bare condition gets a false "not defined"

Source: `w1085d-PB3153-report.md` "## New defects" (filed by the clerk, 2026-10-15; the finisher noted it as beyond its slice).

**Repro.** `E:\COBOL-coord\scratch\w1085d\fin\swk1.cob`: `01 K CONSTANT AS 0.` then `IF K ...`. The compiler refuses with COBOLNET1639 "'K' is not defined — no declaration in this source element gives the name". The program is non-conforming as a bare condition, but the message is false: K is declared.

**Site.** The bare-operand fall-through in `ConditionBinder.AnalyzeBareOperand` (`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs:1089` as of the finisher's tree; verify before editing). A `B"1"`-valued constant hits the same path.

**Open question for the implementer, with the spec first.** Whether §8.8.4.3.3 SR1 admits a boolean constant-name as a condition (a `B"1"` constant is a boolean literal; the 2023 standard permits boolean data names and conditions in some positions). Run `python scripts/spec/cite.py --check 8.8.4.3.3 "<text>"` on the quoted rule before relying on that clause number; it is the finisher's citation and has not been re-derived here. If the spec admits it, this is rejects_legal_source and its severity rises; if not, the fix is the diagnostic: the right message names a constant-name used where a condition is required, not an undefined name. Sweep the sibling fall-through arms of the same method for other declared names reported as undefined.

## Landed

Re-probed on the wave-1105 build (`swk1.cob`: `IF SWON` and `IF BK` both COBOLNET1639) and the spec question answered:
§13.10.4 GR1 makes a constant-name "as if literal-1 ... were written where constant-name-1 is written" and
§13.10.3 SR2 admits it wherever a format specifies a literal, so a `B"1"` constant is the boolean literal of
§8.8.2 and a legal §8.8.4.3 simple boolean condition (`rejects_legal_source`), while `AS 0` is `IF 0`, still no
condition (§8.8.4.2.1) but now reported COBOLNET2318 naming the constant. The break was wider than the bare
condition: `B-AND`/`B-NOT`/COMPUTE operands and EVALUATE routed through the same two Probe-only readers. Fixed in
`ConditionBinder` (`IsBooleanValueOperand`, `BindBoolOperandValue`, `RefuseNonCondition`) through
`ExpressionBinder.LiteralAliasOf`, the one literal-alias resolution; a non-boolean alias in a boolean expression is
COBOLNET1511 naming what it is. Goldens `2002/pb3191_boolean_constant_name_as_condition` and the three
`negative/pb3191-*`. DEVLOG: `pending-pb3191-constant-name-as-condition`.

**For the next implementer.** `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#BindBoolOperandValue` /
`#IsBooleanValueOperand` / `#RefuseNonCondition` — a constant-name or symbolic-character is a LITERAL, not a data
item: every condition or boolean-leaf reader that asks `ctx.Refs.Probe` / `ResolveSending` alone sees "not
defined" (COBOLNET1639); ask `host.Expr.LiteralAliasOf` first, as `ExpressionBinder.FieldOperand` does, and never call
`ConstantOf`/`SymbolicOf` from a binder (`LiteralAliasResolutionDriftTests` fails the build). Trap: the
`semgrep verify.py` raw-diagnostic-code-literal count is a ratchet, so a new refusal shares the existing
`COBOLNET1511` site instead of adding a literal; and `pb3153-method-constant-hides-object-condition-name` had
baked the false 1639 into its `.err`.
