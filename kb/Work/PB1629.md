# PB1629

Filed 2026-09-26 by the train-63 lander from the w62n (PB1604) implementer's lead. The harm is diagnostic quality
only: the refusal is correct (§8.5.1.9.1 3) — a dynamic-capacity table "may be defined in any place, other than the
file section").

**Repro** (w62n probes, `E:\Temp\claude\E--CobolSharp\ba65f072-4d30-4868-9bd3-4e5c60087107\scratchpad\w62n\`):
`t1.cob` (FD record `TYPE` of a typedef holding OCCURS DYNAMIC) reports `t1.cob(18,11)`, which is the working-storage
typedef line. `t2.cob` (SAME AS) does the same. The error should point at the FD / SD record entry whose TYPE or
SAME AS brought the table into the file section. It could also name that typedef line as a secondary location.

**Code site.** `DataBinder.Odo.cs:326-331`: `Edition.At(item)` uses the CLONED item's source position, which is
the typedef's. Pinned today by `OccursDynamicGuardTests.FileSectionDynamicTable_EveryRoute_Rejected1526`, which
checks the code and not the position.
