# PB48 — OPEN — ZERO loses its figurative identity in a STRING argument position

> ⚙ **FOUND WHILE CLOSING [[PB25]], AND IT IS A DIFFERENT MECHANISM.** PB25's figurative-argument defect was in
> the RENDERER (a loud visitor arm) and in the LENGTH binder; both are fixed. These two cases survive it because
> the operand never reaches those arms as a figurative at all — it arrives already converted to a number.

**MEASURED (2026-08-05, after PB25 landed):**

| source | result | required |
|---|---|---|
| `FUNCTION LOWER-CASE(ZERO)` | `COBOLNET1627: argument-1 is of class numeric` at BIND | the character `"0"` |
| `FUNCTION NUMVAL(ZERO)` | **`NotImplementedCobolFeature: intrinsic string argument 'BoundNumericLiteral'`** at RUN TIME | `0` |
| `FUNCTION LOWER-CASE(SPACE)` | ✅ `" "` (PB25) | — |

## THE MECHANISM

A function argument parses as an `arithmeticExpression`, and `ZeroTokenRewriter` rewrites the figurative `ZERO` to
`ZERO_ARITH` "in arithmetic context" (the token-rewriter pass, see `CobolExpressions.g4` `primaryExpression`). So
by bind time the operand is a `BoundNumericLiteral`, not a `BoundFigurative` — which is why PB25's
`Visit(BoundFigurative)` fix does not reach it, and why the §15.3 argument-class screen sees class NUMERIC.

**The rewrite is right for genuine arithmetic and wrong here.** §8.3.3.6.4 GR1: "when a figurative constant
represents a character value, the figurative constant represents an alphanumeric character value … the character
value representation of the figurative constant ZERO (ZEROS, ZEROES) … is the value of the character '0'". A
§15.57.3 argument position requires class alphabetic/alphanumeric/national — a CHARACTER context — so ZERO there
is the alphanumeric character `"0"`, length 1 by GR3b.

## ▶ WHAT TO CHECK FIRST

⚠ **Do NOT simply stop rewriting ZERO inside function arguments.** `FUNCTION MAX(ZERO 5)` and
`FUNCTION SQRT(ZERO)` are genuine ARITHMETIC argument positions where the numeric reading is correct — the class
required differs PER FUNCTION and per argument ordinal, which is exactly what `IntrinsicArgumentRules` already
encodes (§15.3 argument types). So the question is whether the figurative identity can be PRESERVED to bind time
and resolved there against the required class, rather than decided by a token pass that cannot know the function.
⚠ [[feedback_two_arm_dispatch]]: the same token rewrite governs the other figurative constants. Check whether
SPACE/QUOTE in an ARITHMETIC argument (`FUNCTION MAX(SPACE 5)`) is correspondingly mis-admitted — the converse
error — before changing the direction of the rewrite.
⚠ The wrong-stage half is independently worth fixing: even under the current classification, `NUMVAL(ZERO)`
reaching a RUN-TIME `NotImplementedCobolFeature` rather than a bind diagnostic is the [[PB47]] shape.
