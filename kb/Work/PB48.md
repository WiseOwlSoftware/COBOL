# PB48 — LANDED — a token-adjacency pass answered a question only the binder could answer

> ⚙ **FOUND WHILE CLOSING [[PB25]], AND IT WAS A DIFFERENT MECHANISM.** PB25's figurative-argument defect was in
> the string RENDERER and in the LENGTH binder. These cases survived it because the operand never reached those
> arms as a figurative at all — it arrived already converted to a number.

## WHAT THE SPEC REQUIRES

§8.3.3.6.4 GR4 — "The zero format represents the numeric value '0', one or more of the boolean character '0', or
one or more of the character '0' in the computer's runtime coded character set, **depending on context**." GR1
picks the character reading: a figurative constant representing a character value "represents an alphanumeric
character value … the character value representation of the figurative constant ZERO … is the value of the
character '0'". GR3b makes a bare one ONE character long. §8.4.3.2.3 SR8 admits a LITERAL as argument-1 and
§8.3.3.6.3 SR1 admits a figurative constant wherever a rule allows a literal, so a bare `ZERO` argument is legal
to every function; **which reading applies is decided by that function's own §15.3 argument type.** The converse
is SR1a: "If the literal is restricted to a numeric literal, the only figurative constant permitted is ZERO
(ZEROS, ZEROES) **without the ALL phrase**" — and §8.8.1.1 likewise names exactly one figurative among the
operands an arithmetic expression may be built from. All citations `cite.py --check`ed.

## THE MECHANISM, AND WHY THE FIX IS A TOKEN TYPE

`ZeroTokenRewriter` converts `ZERO` to the arithmetic `ZERO_ARITH` whenever it is adjacent to `(` or `)`, on the
reasoning that such a ZERO sits inside a parenthesized arithmetic expression. An argument list is delimited by
exactly those characters, so **every bare ZERO argument was decided as class NUMERIC before any function was
known.** §8.4.3.2.3 SR6 says that paren is categorically not a grouping paren: "the left parenthesis is ALWAYS
treated as the left parenthesis of that function's arguments".

The lexer already maintained `_fnParenStack` — the ONE place that knows which parens those are — so it now
publishes it as the token TYPE (`FNARG_LPAREN` / `FNARG_RPAREN`). **The rewriter is unchanged apart from the
COLON arms below**: its own rule about ARITHMETIC parens simply became true as written. Re-deriving the predicate
inside the rewriter was the alternative and was rejected — that is one rule written twice
([[feedback_one_rule_one_place]]).

⭐ **THE TWO ARMS DISAGREED, WHICH IS HOW THE ANSWER WAS KNOWN BEFORE ANY CODE CHANGED** ([[feedback_two_arm_dispatch]],
now 6×). The keyword-omitted form (SR2) re-lexes its arguments through `FunctionArgFragment`, where there are no
parens to be adjacent to — so `LOWER-CASE(ZERO)` already returned `"0"` while `FUNCTION LOWER-CASE(ZERO)` was
rejected as illegal. The golden asserts both forms, value for value.

## THE FOUR ARMS, AND THE THREE THAT WERE NOT IN THE ENTRY

Only the first was named when this note was written. The rest are what implementing it found.

1. **The token** — `CobolLexer.g4` types the argument-list parens; `functionCall` consumes them; `refModPart`
   accepts BOTH flavours, because SR6's precondition is "if a function's definition **permits arguments**", a
   CATALOG question no lexer can answer — so after a ZERO-argument name the very same token is a reference
   modifier (`FUNCTION CURRENT-DATE (1:8)`, the standard's own D.14.3.6 shape). The rewriter gains the ref-mod
   COLON as arithmetic context (§8.4.3.3.3 SR4), which is where those positions lost their only arithmetic
   neighbour.
   ⚠ The `&& PreviousTokenCouldBeDataName()` conjunct on the FNARG mark was **dropped**: of the ten
   `functionName` alternatives, nine are `_dataNameTokens` and BIT is not, so it made `FUNCTION BIT(…)` the one
   call whose parens were not an argument region — an exception with no rule behind it.
2. **The class screen** — `IntrinsicArgumentRules` modelled an operand's class as a SCALAR, so a figurative,
   having none, fell out of the screen entirely as "not statically decidable" and fail-open passed it to the
   emitter. It is now `CandidateClasses` — **the set of classes the operand can present** — and `Violation`
   INTERSECTS. ZERO passes a class-numeric rule and a class-alphanumeric one; SPACE passes only the second; and
   `ALL "5"` is deliberately not neutral, which is SR1a's "without the ALL phrase". `ClassOf` survives as the
   singleton view, so no fixed-class operand changes verdict ([[feedback_model_the_rule_shape_not_one_case]]).
3. **The MAX/MIN body choice** — `args.All(IsStringOperand)` counted a neutral ZERO as a NON-string vote and
   forced the numeric body on an alphanumeric list. §15.59.3 r2 ("All arguments shall be of the same class") is
   what makes the repair exact: the arguments that HAVE a class are the context GR4 defers to.
4. **The result type** — `UniformArgumentType` read `CategoryOf(args, 0)` literally, so a leading figurative
   collapsed the list to numeric while arm 3 had already chosen the STRING body. The two halves of one decision
   disagreeing surfaced as `FUNCTION MAX (no numeric render recipe)` at run time. It now reads the first argument
   that HAS a category — again r2's uniformity. ⭐ **Arms 3 and 4 are a two-arm dispatch whose own source comment
   says "SEPARATE concern, deliberately not merged"; that separation is correct and is exactly why fixing one
   without the other produced a new failure rather than a fix.**

Plus the sweep: **`BindByteLengthFold` was PB25's own defect one method away from where PB25 fixed it.** Its
default arm named "a numeric/**figurative** literal" invalid on the authority of §15.14.3, which says the
opposite — r1 admits "an alphanumeric or national literal", and GR1 makes a figurative in a character context
exactly that. `FUNCTION BYTE-LENGTH(SPACE)` was legal source aborting at run time **before PB48 too**
([[feedback_scan_all_similar]]).

## WHAT LANDED

- `CobolLexer.g4` (FNARG token types + the SR6 mark) · `CobolExpressions.g4` (`functionCall`) ·
  `CobolParserCore.g4` (`refModPart`) · `ZeroTokenRewriter` (COLON arms + the rule restated)
- `IntrinsicArgumentRules` (`CandidateClasses` + the intersection) · `IntrinsicResultType`
  (`FirstCategory`, and figurative ZERO as an integer operand) · `IntrinsicBinder`
  (`IsClassNeutralOperand`, the body choice, `BindByteLengthFold`, `FNARG_LPAREN` for PB8's SR6 test)
- Golden `pb48_figurative_zero_intrinsic_argument` (30 assertions, both reference forms) + negatives
  `pb48-figurative-space-numeric-argument` and `pb48-figurative-all-numeric-argument`
- `CobolLexerModeDriftTests` — 4 new token-level facts, **proven in the failing direction** (removing the retype
  reds 7 rows) so the guard is not a green assertion that never looked ([[feedback_green_gates_arent_evidence]])

**GATE:** Conformance 715/715 (wave-local) · Unit 3702/3702 · characterization 33/33.
