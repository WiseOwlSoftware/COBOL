**Rule it breaks:** complexity at a stated input size on a compile-time path (DESIGN-architecture-review section 5.4 and its section 4 item 5; dimensions.md 3); the same mechanism PhysicalModel already memoizes for exactly this reason (PhysicalModel.cs:10-19, 87-118: width and init recomputing each other turned nested-group emission exponential, DEVLOG 502, kb/Work PB1590)

**Scenario:** VarParts(G) builds a Dictionary, a HashSet and a List over G's physical children, and for every Nested / NestedTable / OdoTable member d it calls VarFixedWidth(d) AND VarComponentCount(d), each of which is a fresh VarParts(d) (GroupImageCodec.cs:622-626, 648-651). No memo exists, so T(k) = 1 + 2 T(k+1): one VarParts of the outer group of a chain of D nested variable-length groups (01 G0. 02 G1. ... each holding the next, the innermost holding a PIC X DYNAMIC LENGTH item, legal 2023 source up to level 49) performs 2^(D+1)-1 classifications. EmitVarImageMethods then repeats that through VarParts, CarriesNested, CarriesDynTable (each recursing per level), ContiguousLayout and RecordOdo, EmitCurrentImageMethod does it again, and RecordStructEmitter.EmitStructTypeDecls (RecordStructEmitter.cs:176-180) emits both methods for EVERY group of the chain. Count read from the pinned code: D = 10 gives 2,047 VarParts builds for the outer group alone, D = 20 about 2.1 million, D = 47 (the deepest the level numbers allow) about 2.8e14, i.e. the compile never finishes; a fixed-length group of the same depth stays linear because PhysicalModel's memo covers it.
