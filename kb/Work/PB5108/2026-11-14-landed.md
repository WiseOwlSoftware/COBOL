**Landing (2026-11-14, wave 20262039 group E): the placement screen for numeric and integer functions; the note is landed.**

Re-probed on a Debug build of the branch's base (8320c2ad32): `MOVE FUNCTION SQRT (4) TO N`, `DISPLAY FUNCTION SQRT (4)`,
`DISPLAY FUNCTION LENGTH (W)`, `MOVE FUNCTION LENGTH (W) TO N`, `PERFORM FUNCTION INTEGER (2.5) TIMES`, and the ADD, SUBTRACT,
MULTIPLY and DIVIDE operand forms (`ADD FUNCTION LENGTH (W) TO Y`, `SUBTRACT FUNCTION SQRT (4) FROM Y`, `MULTIPLY FUNCTION MAX
(N 3) BY Y`, `DIVIDE FUNCTION MAX (N 3) INTO Y`, `DIVIDE Y BY FUNCTION MAX (N 3) GIVING N`, `ADD 1 FUNCTION LENGTH (W) GIVING Y`)
all compiled at `--std 85` with exit 0 and no diagnostic. Three siblings the notes did not name did too: `GO TO ... DEPENDING ON
FUNCTION LENGTH (W)`, `PERFORM VARYING ... FROM FUNCTION LENGTH (W)` and `INITIALIZE ... REPLACING ... BY FUNCTION LENGTH (W)`.

The edge. §1985:IV.4.3.8.3.3 SR4 (Amendment 1; §1989:A.2.3 GR2 and GR3): "A function-identifier which references an integer or
numeric function may be used only in an arithmetic expression." ISO/IEC 1989:2002 Annex F.2 item 60 removed it ("Numeric and
integer functions may now be used anywhere a numeric sender is allowed"; `§2002:F.2`, checked with `scripts/spec/cite.py --check`),
so the edge is a construct row, `numeric-function-identifier-operand-2002` (COBOL0900, VCR row 7.76), like PB5129's CALL row.

Fix. ONE screen, `IntrinsicBinder.ScreenIdentifierPlacement`, asks the bound operand's category (numeric, which an integer function
also is) and reports the row below 2002. It is asked by every door that binds a function-identifier written AS an identifier: the one
`IntrinsicOperand` channel (MOVE, DISPLAY, PERFORM TIMES, GO TO DEPENDING, WRITE ADVANCING, INSPECT, INITIALIZE REPLACING), the arithmetic
verbs' operand wrapper (`ExpressionBinder.BindArithmeticStatementOperand`, which replaced `BindExpr` at the five sending-operand
sites of `ArithmeticBinder`, because the wrapper walk is shared with relation and EVALUATE operands, where a function IS an
arithmetic expression) and PERFORM VARYING's FROM and BY operand. COMPUTE, a relation, EVALUATE's selection operands and a subscript
or reference-modifier bound are arithmetic expressions and are untouched; an alphanumeric function stays legal (SR3). The report
SOURCE operand keeps its own row (`report-source-expression-2002`): `ReportWriterBinder.SourceIdentifierOperand` binds the function
without the screen so the one operand is not reported twice.

Goldens: `cases/15.2-Types-of-functions/pb5108_numeric_function_as_identifier` (accepted 2002 to 2023: MOVE, ADD, SUBTRACT, MULTIPLY,
DIVIDE, PERFORM TIMES and PERFORM VARYING with function operands), `pb5108_function_placement_85_legal` (the control, accepted at 85:
COMPUTE, a relation, an alphanumeric MOVE) and `pb5108-numeric-function-as-identifier-85` (refused at 85, COBOL0900).

Existing goldens the refusal exposed (accepted at 85 with a numeric function in an identifier position, so 85 non-source): twelve were
rewritten to the 85-legal form with the same output (`COMPUTE x = FUNCTION f` for `MOVE FUNCTION f TO x`; a work item of the function's
device picture for a DISPLAY operand: `pb527_picture_placement`, `pb394_sending_value_evaluated_once_85`, `l1c01_alnum_literal_characters`,
`l1c10_figurative_space_quote_zero_chars`, `pb1153_counter_register_character_image`, `l1c01_group_start_coincident`,
`l1c05_coded_character_values`, `pb1542_code_set_unrepresentable_85`, `pb690_file_character_set_85`,
`pb690_report_line_byte_image_85`, `pb5130_integer_date_year_10000_85`, `l1_integer_floor_85`); two narrowed to 2002 and later:
`pb1421_goto_depending_function_identifier` (its subject is the identifier position) and `pb4075_wide_argument_consumers` (a 39-digit
DISPLAYed MEAN, which no 85 item holds).

Left unchanged and reported: a numeric function as an INSPECT, STRING or CANCEL operand now draws this COBOL0900 at 85 beside the
refusal (COBOL0847, COBOL1626, COBOL1696) those statements already give at every edition.
