# PB5846 - a Linkage Section item that is not a USING operand is accepted as a subscript or a reference-modification operand (every edition)

**Ruling: UPHELD (b), harm under_rejects and wrong_answer.** The row `1985-GR-X.5.1-4` does not close on its inherited verdict. A Linkage Section item that is not in the USING phrase is accepted as a subscript or a reference-modification operand. It is the sibling of the landed kb/Work PB3287. The checker's confidence: high. Cause (b): the same at `--std 2023`. Severity MAJOR: a wrong-answer defect is at least MAJOR.

**The checker's evidence (rulings.json, copied).** `§1985:X.5.1 GR4` says Linkage items may be referenced within the Procedure Division of that program "if, and only if" they meet legs a to e (USING operand, subordinate to one, a redefinition or renaming of one, etc.). A data-name written as a subscript or as a reference-modifier position is a reference within the Procedure Division; L2 is in no leg. The compiler refuses L2-N as a statement operand (COBOL2746, control `lkctl.cob`) but takes it as a subscript (`L1-E (L2-N)` prints `SUB A`) and as a ref-mod position (`L1 (L2-N:1)` compiles and fails at run time with EC-BOUND-REF-MOD (0:1)), reading storage that has no argument behind it. The same at `--std 2023` (`§2023:13.7.3 SR4`). The reader's legs a to e are right for the top-level identifier; the reader did not probe the operand positions. The mechanism is the sibling of landed kb/Work PB3287 (a second resolution entry that drops ResolveImplCore's screens): `SubscriptBinder.ResolveSubscriptName` resolves through `refs.Names.ResolveUnqualified` and `ResolveQualified` and never reaches NameResolution's linkage screen.

**Sites:**
- `src/WiseOwl.Cobol.Compiler/Binding/SubscriptBinder.cs#ResolveSubscriptName` (called for a subscript or reference-modification data-name; it has no linkage screen)
- `src/WiseOwl.Cobol.Compiler/Binding/ReferenceResolver.cs#Identify` (where the screen lives, reached through `NameResolution.ScreenLinkageReference`)

**Where** (the checker's reading): the first member above has no linkage screen; the screen lives in the second.

**1985 rows.** `1985-GR-X.5.1-4`. `work.py check` refuses a 1985 rule id in `inventory_rows` (kb/Work PB5094), so it is named here. **2023 row** the checker names: `SR-13.7.3-4`.

**Repro** (`E:/COBOL-coord/scratch/my-20261115/contradictions-b10/src/lksub.cob`; the control is `lkctl.cob`).

`lksub.cob` (L2 is no USING operand; used as a subscript and as a reference-modification position; compiles):

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. LKMAIN.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 W-T.
          05 W-E PIC X OCCURS 3 TIMES.
       PROCEDURE DIVISION.
       P0.
           MOVE "ABC" TO W-T.
           CALL "LKSUB" USING W-T.
           DISPLAY "BACK".
           STOP RUN.
       IDENTIFICATION DIVISION.
       PROGRAM-ID. LKSUB.
       DATA DIVISION.
       LINKAGE SECTION.
       01 L1.
          05 L1-E PIC X OCCURS 3 TIMES.
       01 L2.
          05 L2-N PIC 9.
       PROCEDURE DIVISION USING L1.
       P1.
           DISPLAY "SUB " L1-E (L2-N).
           DISPLAY "REF " L1 (L2-N:1).
           EXIT PROGRAM.
       END PROGRAM LKSUB.
       END PROGRAM LKMAIN.
```

`lkctl.cob` is the same program with the two DISPLAY lines of `P1` replaced by the one line `DISPLAY "SUB " L2-N.` and `PROGRAM-ID. LKCTL.` for the main program (the control: L2-N as a statement operand).

| `lkctl.cob` (control) | exit 65, error COBOL2746: `L2-N` belongs to LINKAGE SECTION record `L2`, which the procedure division may not reference | (not run) |

**Expected:** refused, COBOL2746, as for `DISPLAY L2-N` (`§1985:X.5.1 GR4`). **Observed:** compiles; prints `SUB A`; the ref-mod form dies with EC-BOUND-REF-MOD at run time.
