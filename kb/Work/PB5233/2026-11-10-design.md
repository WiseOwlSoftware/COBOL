## 1. The command surface

### 1.1 Shared rules

- **Invocation.** `python scripts/build.py <verb> …`, with no wrapper. Process priority is set by `build.py` itself through `build_runs.set_priority`: `SetPriorityClass` on Windows, `os.nice` on Linux. Children inherit it, so the `-Priority` duty of `build-local.ps1:21-26` survives.
- **Detached runs.** `check` and `land` create a numbered run directory and start themselves detached through `detached.spawn_detached`. The caller follows the log to the verdict and exits with the run's code. Killing the caller leaves the run going (`gate.py:1011-1041` today).
  - Check runs live in `<worktree>/TestResults/build/<n>-<UTC>Z/`. Land runs live in `<branch worktree>/TestResults/land/<n>-<UTC>Z/`.
  - Each run directory holds `run.log`, `run.pid`, `run.spawn` and, at the end, `outcome.json`.
  - `outcome.json` holds `{line, exit_code, head, tree, wall_s, targets:[{name, kind, state, key, seconds, recorded}]}`. It has no schema number, because no landing reads it.
- **Locks.** All are OS locks freed when the holder dies.
  - `check`: `<worktree git dir>/cobol-build.lock`.
  - `land`: `<worktree git dir>/cobol-land.lock` for the whole run. It also takes the build lock around each write to the worktree (merge, stamp, push). Nesting order is land lock, then build lock, then slot.
  - A held lock gives BUSY (exit 3): nothing ran and nothing is red.
- **Liveness.** STARTING is decided by an exact identity: the spawn record holds `{pid, created}` (process creation time). It replaces the 60 s `START_WINDOW_S` guess (`gate.py:287-290`, `862-872`).

**Exit codes**, one table in `build_verdict.py` for every verb:

| Code | Word | Verbs |
|---|---|---|
| 0 | GREEN · UP TO DATE · MERGED · NOTHING TO LAND | all |
| 1 | RED · STALE (why) | check, why, land |
| 2 | NOT RUN [cause] | all |
| 3 | BUSY | check, land |
| 4 | PENDING | await (the rolling wave's `AWAIT_PENDING_EXIT = 4` stays) |
| 5 | CONFLICT | land |
| 6 | REFUSED [reason] | land |
| 7 | WAITING [on] | land |
| 8 | BOUNCED [class] | land |
| 9 | STALLED | land |

**NOT RUN causes** (`build_verdict.NOT_RUN_CAUSES`; the ENVIRONMENT/BRANCH split of `gate.py:182-235` is kept):

| Cause | Class | Note |
|---|---|---|
| settings, toolchain, tree, launch, run, store, fetch, github, merge-blocked, stamp, main-moving, edited, pruned, interpreter, host, sdk, disk | ENVIRONMENT | interpreter, host, sdk and disk stay because `linux-gate.sh` prints them |
| driver, merge-failed, population, arguments, verdict, unclassified | BRANCH | |

### 1.2 `check`

```
python scripts/build.py check [--priority normal|below-normal|idle]   (default below-normal)
  (internal: --run <dir>   the detached child;   --foreground   land's in-process use, no detach)
```

It brings every target up to date for the measured working tree. There is no target selection and no filter: ONE SHAPE in spirit.

1. **Start.** Take the build lock (BUSY). Create the run directory. Check the toolchain (`NOT RUN [toolchain]`, as at `gate.py:1652-1657`). Measure the tree (`build_tree.measured_tree`; `NOT RUN [tree]` if git cannot). Compute the leaf keys (`NOT RUN [tree]`). Look up each target. A malformed store record is `NOT RUN [store]` naming the file.
2. **Plan line.**
   `build: 34 targets; 31 up to date, 3 to run: unit, audit:DOC AUDITS, selftest:scripts/devlog.py`
3. **Up-to-date lines.** For each up-to-date target:
   `build: characterization UP TO DATE — pass at key 811295d200b6 (run 000003-20261111T050102Z of build-stage1, 2026-11-10T21:01:02Z, 37 cases)`
4. **Script and generated targets** run immediately, outside the slot, under the self-test budget:
   `build: audit:DOC AUDITS START (2 of 3; declared 20s)`, then `build: audit:DOC AUDITS PASS in 14.2s`, or `RED in 3.1s — <its verdict line>`, or `TIMEOUT after 60s (declared 20s)`.
   Each ran target says why it ran: `— ran because 2 input(s) changed since the pass of run 000002 (docs/x.md, docs/y.md)`, or `— no pass recorded for windows/Debug/<toolchain>`, or `— its dependency suite's output changed (a1b2… → c3d4…)`.
5. **Build and test targets.** If any test target or `needs: build` self-test is stale:
   1. Fetch the GnuCOBOL corpus (`external_corpus.ensure`, before the slot).
   2. Take the slot (`NOT RUN [settings]` if the slot settings turn malformed, `gate.py:1716-1718`).
   3. Run `dotnet build WiseOwl.Cobol.sln -v quiet`. A failure is `build RED (dotnet build exit N)`, and every dependent is `NOT RUN (dependency build RED)` inside the RED verdict.
   4. Run the stale test targets concurrently, the built self-tests beside them. The retry and ordering rules are in section 1.6.
   Example: `build: unit RAN — 40,493/40,493 ran (skipped 12), EXACT, 251.3s; pass recorded at key 5f90035e8db9`, or `build: unit RED — 2 failed (N.Unit.Foo, N.Unit.Bar); 40,491 passed cases recorded at key 5f90… for the retry`.
6. **Edit check.** At the end the tree is measured again. A target whose key moved while it ran records nothing and is `NOT RUN [edited]`. This is per target, finer than `gate.py:1387`'s whole-tree test.
7. **Verdict line** (the last line; at most 8 target names, the rest counted; the full list is in `outcome.json`):
   - `=== BUILD CHECK: GREEN — 34 targets: 3 ran (unit 40,493/40,493, audit:DOC AUDITS, selftest:scripts/devlog.py), 31 up to date · toolchain <summary> (run 000007-20261111T061500Z) ===` → 0
   - `=== BUILD CHECK: RED — 2 red: unit (2 cases failed), audit:CITATIONS (exit 1); 5 ran, 29 up to date of 34 (run …) ===` → 1
   - `=== BUILD CHECK: NOT RUN [<cause>] — <why>; nothing recorded (run …) ===` → 2
   - `=== BUILD CHECK: BUSY — another check or land holds this worktree (<holder label>): nothing ran, nothing is red ===` → 3

**Keep-going.** A red target never stops another, so audits no longer stop the hosts (`gate.py:1728-1746`, `1862-1868`, PB3061, PB4326 are deleted). Every finished target records its result. The total cost is the same as fail-fast plus a re-run: fail-fast cost an early verdict plus a later full test run, keep-going costs a full test run now plus near-zero later, because the passes are recorded. It also removes the need for `--rederive`. A red line is printed the moment its target ends.

### 1.3 `why`

```
python scripts/build.py why <target> [--tree <rev>]    (default: the measured working tree)
```

- **Which pass it compares against.** The newest pass of `<target>` with the same platform and configuration, chosen by this rule: (1) one recorded by this worktree, else (2) one whose head is an ancestor of HEAD, else (3) the newest anywhere. The line says which rule chose it.
- **Changed-input lines** (up to 50, then `… and N more`): `  M src/WiseOwl.Cobol.Compiler/X.cs`, `  A tests/…`, `  D …`. Changed settings print as `  toolchain: <old> → <new>`. For a script target, the lines come from `self_tests.explain`.
- **Verdicts:**
  - `=== BUILD WHY: unit UP TO DATE — key 5f90035e8db9 at tree 1a2b3c4d5e6f (windows, Debug, <toolchain>): the pass of run 000003… of build-stage1, 2026-11-10T21:01:02Z ===` → 0
  - `=== BUILD WHY: unit STALE — 3 input(s) changed since the pass of run 000002… at tree 9f8e…, recorded 2026-11-10T20:12:00Z (chosen: this worktree's newest): src/A.cs, src/B.cs, tests/WiseOwl.Cobol.Tests.Unit/C.cs ===` → 1
  - `=== BUILD WHY: conformance STALE — its dependency suite's output changed (digest a1b2c3 → d4e5f6) ===` or `… its dependency suite has no pass at its key: run check ===` → 1
  - `=== BUILD WHY: unit STALE — no pass of unit is recorded for windows/Debug/<toolchain>: it has never passed here ===` → 1
  - `=== BUILD WHY: NOT RUN [arguments] — no target named X (targets: unit, repo-drift, …) ===` → 2
  - `=== BUILD WHY: NOT RUN [pruned] — the pass of run R recorded tree T, which is no longer in the object store (git gc): the key differs, and which input changed cannot be named ===` → 2

### 1.4 `land`

```
python scripts/build.py land <branch> [--worktree DIR] [--lane registrar|golden|clerk] [--dry-run]
```

It runs detached in the branch worktree's `TestResults/land/<run>` and is followed to its verdict. Each step prints `land: <step>: …`. A step that stops the landing on the branch's account also appends `BLOCKED: land — …` to the fix-lane report (`record_blocked`, today `enqueue.py:506-519`).

1. **Resolve.** Refusals: `REFUSED [main]`, `REFUSED [no-worktree]`. Take the land lock (BUSY). Refuse a dirty worktree, ignoring the half-stamp paths as `enqueue.py:834-837` does: `REFUSED [dirty]`. **The DEVLOG entry, at the first step** (PB5207): the branch must carry `DEVLOG/pending-*.md` or an entry this branch already stamped; else `REFUSED [no-entry] — the branch has no DEVLOG/pending-<slug>.md (first line "## <Title>"): it is the one thing a person writes`.
2. **Resume.** If the branch has an open pull request whose head equals HEAD and it is already with the queue (auto-merge on, or in the queue), go straight to step 9: `land: resuming the watch of PR #N at <sha12>`. This makes a re-run after a killed land exact. It merges nothing new, and a moved head would leave the queue.
3. **Fetch main.** Failure is `NOT RUN [fetch]`. If HEAD equals main, or HEAD is already in main: `NOTHING TO LAND — …` → 0.
4. **Queue guard.** `ruleset.check` must say ACTIVE; else `WAITING [queue-inactive] — …` → 7 (the lane writes HALT). An unanswerable ruleset is `NOT RUN [github]`.
5. **Review.** The rule is unchanged: `prune_worktrees.unreviewed_since` over the report's `**Review:** CLEAN <reviewer> <head>`, skipped with `--lane`. Failure: `REFUSED [unreviewed] — …` → 6, plus BLOCKED.
6. **Merge main** with plain git (`git_merge.merge`) under the build lock.
   - A conflict: `CONFLICT in a, b — merge aborted, branch unchanged` → 5, plus BLOCKED.
   - Could not be completed, ENVIRONMENT cause: `NOT RUN [merge-blocked]`.
   - Could not be completed, BRANCH cause: `RED [merge-failed]` → 1, plus BLOCKED. This keeps the classification of `enqueue.py:786-801`.
7. **Check the merged tree with that tree's own code:** `python <wt>/scripts/build.py check --foreground --priority normal`. The output is copied into the land log.
   - RED: `RED — unit, audit:WORK REGISTER red at the merged tree 3c4d5e6f7a8b (check run …)` → 1, plus BLOCKED.
   - NOT RUN or BUSY: passed through.
8. **Prepare the pull request.**
   1. Predecessor wait, as at `enqueue.py:907-916` and `927-940`: `WAITING [predecessor] — PR #A, #B land a DEVLOG entry this branch carries` → 7.
   2. Stamp with `devlog.py stamp`. A git failure is `NOT RUN [stamp]`; a refusal is `REFUSED [no-entry]`.
   3. Title the pull request from the one new entry. A `devlog.RangeError` is `NOT RUN [tree]`; not exactly one entry is `REFUSED [no-entry]`.
   4. Check again. It is incremental: normally only the DEVLOG-reading audits run.
   5. Run the landing checks, now two: `devlog.py check` → `REFUSED [devlog-check]`, `landing_check.py` → `REFUSED [landing-check]`. `work.py check` and the two rename audits leave `CHECKS`: they are audit targets the merged-tree check already ran with the merged tree's own scripts, which is what `in_tree=True` gave them (`enqueue.py:242-253`).
   6. If main moved meanwhile, go back to step 6, at most `CATCH_UP = 3` times; else `NOT RUN [main-moving]`.
   7. Push, open or reuse the pull request, and turn on `gh pr merge --auto`. Any failure is `NOT RUN [github]`. Auto-merge is confirmed by reading `gh pr view --json autoMergeRequest`, not by matching "already" in GitHub's message (`enqueue.py:371-372`).
   8. Print `ENQUEUED pr=<n> sha=<sha> branch=<b> url=<u>`; `QUEUED_LINE` keeps its grammar. Write the landing-measure record. If the record cannot be written, say so in the final verdict's detail.
9. **Own the pull request.** Read `queue_facts` for this one pull request every 60 s and print each state change. The state machine is `land_lane.py:912-998` and `895-909`, moved:
   - In the queue: `land: PR #N in the merge queue`, and keep reading (PB3772).
   - **Merged:** `=== LAND: MERGED — pull request #N merged into main as <sha12> at <time>; queued <t>, <m> min in the queue (<branch>) ===` → 0. It also runs `landing_measure.complete(only=N)`.
   - **A pull-request check failed before the queue:** `BOUNCED [pr-check] — PR #N: job "<job name>" failed (run <id>)` → 8, plus BLOCKED.
   - **Main conflicts (DIRTY):** `BOUNCED [dirty] — …` → 8. The lane writes the conflict brief.
   - **Removed by a merge-group red:** classify (section 1.4.1). INFRA or RUNNER the first time: `land: PR #N bounced [RUNNER] — … ; re-queued once`, keep watching. Otherwise: `BOUNCED [GENUINE|MERGE|UNCLASSIFIED|INFRA-AGAIN|RUNNER-AGAIN] — PR #N: job "<job>" failed in merge-group run <id>: <why>` → 8, plus BLOCKED.
   - **Stalled out of the queue:** the ladder of `land_lane.py:745`, `979-998` (grace `QUEUE_GRACE_MIN = 10` after the checks' work ends). Read 1 re-runs the stuck run, read 2 closes, reopens and re-queues (refused while a run on the head is live, PB4052), read 3 alerts the operator: `=== LAND: STALLED — PR #N: <what>, after a re-run and a requeue; the operator is alerted ===` → 9. A job whose status GitHub does not report counts as a stalled read and climbs the same ladder, which ends in an operator alert.
   - **The PR head moved on GitHub:** `WAITING [superseded] — PR #N's head moved to <sha12>: a new push is a new landing` → 7.
   - **No pull request open and not merged:** `STALLED — no pull request is open for <branch> and its work is not on main (closed by hand?)` → 9, plus alert.

`--dry-run` writes nothing and does not detach. It names the merged tree with `git merge-tree --write-tree origin/main HEAD` and prints the targets that would run there. Its line is `=== LAND: DRY RUN — would merge origin/main (merged tree 3c4d…), run 2 targets (unit, audit:WORK REGISTER), stamp and queue (<b>) ===`.

#### 1.4.1 Bounce classification (the failing job and its class)

- **Failing jobs.** `queue_facts.fetch_bounce_results` gains `failed_jobs` (`gh run view <id> --json jobs`). Every BOUNCED line names the first failing job, with the count of the rest.
- **The comparison.** The run's red cases (trx, by name) are compared with the local evidence at the tree that step 7 checked: `build_check.local_evidence(tree)` returns, per test target, the listing and the passed set from the store (section 1.6, cases and listings). This replaces `enqueue.tested_locally` and `gate.measuring_runs` (`land_lane.py:842-892`).
- **The classes** (the logic of `land_lane.py:814-839`):

| Class | When |
|---|---|
| INFRA | the run timed out, or no test failed |
| RUNNER | every red case passed locally at that key |
| GENUINE | a red case is listed locally but was skipped (NotExecuted) |
| MERGE | a red case is absent from the local listing: main moved after the check, or the merged tree made it |
| UNCLASSIFIED | the results are unreadable, or the store has no evidence for that target at that key |

The test-free-lane class ("the inert or tooling lane → RUNNER", `land_lane.py:880-881`) goes away with the lanes. A red case belongs to a test target, and that target has evidence or it does not.

### 1.5 `await`

```
python scripts/build.py await <run> [--worktree DIR] [--wait-s N]   (default 540)
```

This is `gate.py --await` (`gate.py:960-1008`, `3593-3597`) for check and land runs alike. It prints the outcome's line and exits with its code. It prints `NOT RUN [verdict]` (2) when the process died without an outcome, `NOT RUN [run]` when there is no such run directory, and `=== BUILD AWAIT: PENDING — no outcome in <run> after N s; <who> ===` (4) when time runs out. A relative `<run>` is the worktree's own (`resolve_run`, `gate.py:912-918`).

**Method.** In a scratch clone (its own git common directory, so its own store):

**Required.**
- The test-target set that ran equals the old assemblies that ran, in all 12.
- Per-assembly counts are equal.
- The verdict word is equal, and (10) and (11) name the same red case and the same red audit.
- Audits and self-tests: the new set that ran differs from the old only in listed, explained deltas. The old code ran every audit in every gate; the new code runs those whose traced inputs changed, and each skipped audit is shown green when run once by hand. Self-tests that read changed compiler data are a superset, each named with the input that explains it.

The machine time is about 3 hours, run once. The evidence goes to `E:\COBOL-coord\scratch\build-stage4\diff\`.

## 6. Risks, and what this stage does not do

### Risks

- **PB5232's interface** (A3) may not support audit commands or `explain`. 4a's first commit then adds them to `self_tests.py`; agree on this in PB5232's review.
- **A traced audit key can miss a read made by a subprocess.** Mitigations: whole-tree keying when a traced git command reads the tree (the existing rule in `self_tests.py`), and CI's `audits` job, which keeps running every audit until stage 6.
- **Store growth** (passes, case blobs of about 4 MB per Unit listing, memos). Measure the size after 2 weeks before adding pruning.
- **Long-lived land processes.** A reboot ends the runner (DIED); the lane's retry resumes exactly (step 2). This needs its own arm.
- **GitHub calls.** About 1 call per minute per landing in the watch. Fine against 5,000 per hour.
- **Merged-tree checks** cost a slot and about 250–500 s on the roughly 27 % of landings that bring `src/` (4 of 15 measured).
- **Deleting the slot classes** removes PB4888's fix-gate lever. Watch the slot-wait share.
- **Conflicts** with PB5235 in `build-and-test.yml` and `buildgraph.py`. Agree a merge order.
- **The edit check** can produce `NOT RUN [edited]` for agents who edit during a check (MANDATORY says no edits during a gate).
