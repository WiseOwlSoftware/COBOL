# PB1651 — LANDED (with PB3637)

Filed 2026-09-27 by the train-66 lander from the wave-66 G implementer report.

**Observed.** `python scripts/spec/where.py <clause>` on a Windows console whose code page is cp1252 raises
`UnicodeEncodeError` at `scripts/spec/where.py:61` when it prints a `§` or other non-cp1252 character. It works only
when `PYTHONIOENCODING=utf-8` is set. MANDATORY-PRACTICES P6 names `where.py` as a first-call orientation tool, so
every agent on a cp1252 host hits this.

**Repro.** In a PowerShell or Git Bash console without `PYTHONIOENCODING`: `python scripts/spec/where.py 13.16.3`.

**Fix shape.** Reconfigure stdout to UTF-8 at start-up (`sys.stdout.reconfigure(encoding="utf-8")`), as the other
`scripts/spec/*.py` tools that print clause text do. Sweep the sibling scripts for the same missing call.

## Landed with PB3637 (wave 20261503 group A, branch `worktree-wf_94698d58-de0-1`)

One mechanism, fixed once: every live Python entry point calls `scripts/standard_streams.py#ensure_utf8` as the first statement of its `__main__` block (a hook: at module level, after its imports), every per-script `reconfigure` copy is deleted, and `ScriptStandardStreamsDriftTests` runs `standard_streams.py --check`, which RUNS every argparse entry point's `--help` and a usage error under a cp1252 stdout and stderr. Re-probed after the fix through a pipe with no UTF-8 environment: `python scripts/spec/where.py 13.16.3` exit 0 with no UnicodeEncodeError. kb/Work/PB3637.md `## Landed` has the determination (the call in the program, by the owner's direction of 2026-10-10 recorded above, not the environment) and the code sites.
