# PB4655 - a bounce on a cancelled merge-group run leaves its landing record open for good

**Sites:** `scripts/orchestrator/landing_measure.py` (`complete`)

`landing_measure.py complete` prints this on every run, and returns 2 (its `bad` count) however many other records it
completes:

```
⛔ landing-measure: PR #1101: 1 bounce cause(s) name more than the 0 bounce(s)
```

The record holds `bounces: 1, bounce_causes: ["infrastructure"]`, which is right. GitHub's timeline shows PR #1101 removed
from the queue at 05:52:15Z with reason `failed_checks`, added again at 06:08:10Z and merged at 06:23:28Z, all on
2026-11-04. Its first merge-group run, 41779240040, was cancelled (PB4571 is the hang behind it).

`complete` sets `bounces` to the count of the pull request's merge-group runs whose conclusion is `failure` or
`timed_out`. A cancelled run counts as neither, so the patch carries `bounces: 0`, and `record` refuses it because one
cause is more than zero bounces. The whole patch is lost with it, so the record never gains its merge time or CI wall.
PR #1101 stays in the open set, and each later `complete` repeats the refusal.

Two defects meet here. The count is not GitHub's own fact about a bounce: the timeline's `RemovedFromMergeQueueEvent`
says what the run conclusions do not. And `complete` overwrites a recorded `bounces` with a smaller observation, where
the `record` path beside it keeps the larger (`max(old.get("bounces") or 0, len(causes))`).

Other pull requests whose bouncing run was cancelled undercount the same way when no cause was recorded for them, with no
refusal to show it. That population has not been measured.
