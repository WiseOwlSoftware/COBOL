# PB3615 — INITIALIZE of a USAGE BIT table is quadratic in the occurrence count

**Sites:** `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs` (`ExpandImplicitFillers` and `PadGapPlace`, the pad loop near line 491; the class-lane window stores near line 468).

## Found

Source: `w20261024b-PB3597-report.md`. One mechanism: a bit table's element or gap is stored through a reference-modified
place over ONE backing string, and each store rebuilds that whole string, so n stores cost O(n^2) bits.

- **R1-1 (introduced by the PB3597 change).** The record-struct pad loop of `INITIALIZE ... WITH FILLER REPLACING BOOLEAN`
  stores each of the n - 1 gaps through a reference-modified place over the one pad string, so every iteration rebuilds the
  whole (n-1) * gap-bit string.
- **R1-2 (pre-existing, no kb/Work note covered it).** INITIALIZE of a bit table in a Tier-B class (an EXTERNAL record) is
  quadratic even without WITH FILLER, since each window store rebuilds the class string backing; the new class-lane gap loop
  inherits the cost.

## The fix

Build the pad (or the table window) as one string and store it once, or store the whole range through a bulk store that
does not rebuild per element; measure with a table of 100,000 occurrences before and after (a structural guard, not a
wall-clock limit: count the string rebuilds).
