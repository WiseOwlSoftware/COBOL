# PB201

Found 2026-08-31 while MEASURING the reachability of `NumericRenderer.FieldNumCore`'s group arm for
[[PB178]] (the cluster-A burn-down). PRE-EXISTING; nothing in that landing touched the subscript path.

**MEASURED, both shapes, at `--std 2023` strict AND `--permissive` (identical output — no dialect gate is
involved):**

- a WORKING-STORAGE group as a subscript, `01 WG. 05 WF1 PIC 9(2).` … `MOVE TE(WG) TO R` →
  `error CS1503: Argument 1: cannot convert from '_PRG_NRSUB2._T_0' to 'long'` — the group's record STRUCT
  is handed to `CobolTable.At` where an index is wanted.
- a BASED group as a subscript, `01 BODO BASED. 05 BF1 PIC 9(2). 05 BT OCCURS 1 TO 5 DEPENDING ON NN …` …
  `MOVE TE(BODO) TO R` → `error CS0103: The name 'BODO' does not exist in the current context` — the raw
  COBOL word is emitted verbatim, because a class-tier group has no C# field of that name at all.

**THE MECHANISM, and why it is not [[PB178]]'s.** The subscript index is the D10 TRANSITIONAL string carrier
(a rendered index expression on the `AccessPath` segment, per the PHASE-07 Step 11 plan / plan D10), so the
subscript path renders the reference DIRECTLY rather than routing it through `NumericRenderer.FieldNum`. That
is why the group arm of `FieldNumCore` — which decodes a group's image as an unsigned integer, and which
`--permissive` does reach for an ARITHMETIC operand — never sees a subscript. Two consequences, both bad:

1. `ExpressionBinder`'s §8.8.1.1 group-operand rejection (COBOLNET0844) does not fire either, so the
   construct is neither properly REJECTED nor properly COMPILED — it is accepted at bind and then breaks the
   backend. Under-rejects, then crashes.
2. Whatever the eventual verdict, the two shapes must not diverge: today one emits a struct and the other
   emits an undefined identifier.

**DERIVE BEFORE FIXING.** §8.4.2.3 governs what a subscript may be (the subscript forms and their integer
requirement) — read it and cite the exact rule before choosing between (a) a bind rejection, the likely
answer, since a group is not an integer numeric item, or (b) routing the subscript through the ONE numeric
read the way every other numeric context does. ⛔ Do NOT infer the answer from §8.8.1.1: that clause governs
ARITHMETIC EXPRESSIONS, and a subscript is not one — the real clause may permit or forbid on different
grounds (`feedback_a_real_clause_can_answer_a_different_question`).

**WHY IT MATTERS BEYOND THE CRASH.** This is the last unmeasured arm of `FieldNum`'s 9 callers. The PB178
landing established that a group operand reaching a numeric context is reachable under `--permissive`; the
subscript path is the one caller where it does not reach at all, and the reason is a transitional carrier
that D10 is scheduled to remove. Fixing it before D10 lands means fixing it twice; fixing it after means the
crash ships until PHASE 15. That trade-off is the owner's, not the implementer's.

## Landed — 2026-09-04

**RE-PROBED FIRST, and the note only half held.** On this worktree's own freshly built `cobol.exe` the STRICT lane
already REJECTED both shapes with COBOLNET0844 — `1884ba1e` (kb/Work PB170) had put a class screen on the fast
path — so the note's "identical output at strict AND `--permissive`" was stale. What still reproduced, exactly
as written, was the `--permissive` lane: `MOVE TE(WG) TO R` →
`error CS1503: cannot convert from '_PRG_PRGNRSUB2._T_0' to 'long'`, and the BASED group →
`error CS0103: The name 'BODO' does not exist in the current context`. The warning promises to decode "its digit
characters as an unsigned integer" and the emitted C# never did.

**THE ROOT CAUSE IS THE CARRIER, NOT THE CLASS — and the sweep found the far worse siblings.**
`ReferenceResolver.PositionRead` renders `CobolTable.Occ(<path>)` (or `CobolString.RefModPosition(<path>, scale)`)
at bind time and lets C# overload resolution supply the conversion. That is the deliberate device that lets ONE
text serve a `long` field and the `string` image a post-bind analysis may promote it to — but the overload
sets are only `(long) | (string)` unscaled and `(long) | (string) | (Int128)` scaled, while `DataItem.ElementType`
also yields `double`/`float`, an unscaled `Int128`/`ulong`/`UInt128`, `ManagedPointer`, `ProgramPointer`, an
object-reference type, and a group's per-program `record struct`. MEASURED on `e4850fc7`, in the **DEFAULT strict
lane, on source §8.8.1.1 and §8.4.2.3.4 GR1b make perfectly legal**:

- `MOVE E(W-FL) ...` with `01 W-FL USAGE FLOAT-LONG` → `CS1503 cannot convert from 'double' to 'long'`
- `MOVE E(W-BIG) ...` with `01 W-BIG PIC 9(20) USAGE COMP` → the same, from `System.Int128`
- `MOVE E(W-U) ...` with `01 W-U USAGE BINARY-DOUBLE UNSIGNED` → the same, from `ulong`
- `MOVE W-W(W-FL:2) ...` → the same at the reference-modification bound (§8.4.3.3.3 SR4)

So the filed defect (a group under `--permissive`) was the mildest member of its family: three legal-source
rejections in the default lane sat beside it, undetected because nothing in the corpus subscripted a float or a
wide item.

**THE SWEEP FOUND A SECOND EMITTER OF THE SAME BET, AND IT HAD NO ROUTE.** `RuntimeApi.TableOcc` renders the
OCCURS DEPENDING ON current-count read — `CobolTable.Occ(<the control item>)` — at CODEGEN time, from a
Place, so it cannot decline and re-route the way the subscript renderer can. §13.18.38.3 SR17 asks only that
"Data-name-1 shall describe an integer", so a 20-digit COMP item and an unsigned BINARY-DOUBLE are both legal
control items, and `MOVE <odo-group> TO X` over either failed the backend with four CS1503s on one program
(`System.Int128` and `ulong` → `long`), in the DEFAULT lane. That is what settles the design question:
the three INTEGER carriers genuinely were MISSING OVERLOADS and had to be added, because this site needs the
capability rather than an escape.

**The fix is therefore both halves, each at its one place.** `CobolTable.Occ` gains `(Int128)`, `(ulong)` and
`(UInt128)`, all narrowing through the new `CobolNum.Position` — **THE ONE narrowing, and it SATURATES**,
because §8.4.2.3.4 GR2 makes "greater than the highest permissible occurrence number" a condition that must be
DETECTED, and a plain `(long)` cast can WRAP an out-of-range position back inside `1..n` and lose it. (`Occ(string)`
and the shared `CobolNum.PositionOf` were both doing exactly that raw cast, and now go through `Position` too —
`FromAlphanumeric` returns up to 38 digits.) The FLOAT carriers are deliberately NOT added: a `double` can be
fractional and §8.4.2.3.4 GR1b's integrality test lives only in the scaled arity, so a float operand must keep
taking the D18 route where the rule is applied once, to the result. `PositionCarrierOverloadDriftTests` pins that
exclusion as a decision rather than an oversight.

**And the routing half, at the one place the rule belongs.** `PositionRead` now admits only a carrier the helper it
is about to emit declares a parameter for (`UnscaledPositionCarriers` / `ScaledPositionCarriers`) and returns null
otherwise, so `RenderSegment` takes the D18 materialization route it ALREADY documents as the answer for anything
it cannot render — "an optimization over that route, never the arbiter of what is legal in the position". On
that route `ExpressionBinder.OperandRef` applies the §8.8.1.1 screen (the same COBOLNET0844, both lanes) and
`NumericRenderer.FieldNum` — THE ONE numeric read — supplies the carrier-correct decode: the float
sending check, the wide tier, and for a group the §8.5.2.1 alphanumeric IMAGE through the ONE sending reader, so
an occurs-depending group sends its §13.18.38.4 GR8 CURRENT-count part. Widening the runtime overload set
instead was rejected: it fixes `double` and `Int128` and leaves the group behind permanently, because a group's
carrier is a per-program generated type that can never have a runtime overload.

**Both of the note's stated consequences are discharged.** (1) The construct is now properly REJECTED under strict
and properly COMPILED under `--permissive`, never accepted-then-broken. (2) The two shapes no longer diverge:
`E(WG)` and `E(BG)` over the same "02" image both select occurrence 2, asserted in one test.

**The emit floor is byte-identical for an ordinary subscript** — verified by diffing the generated C# for an
integer item, an alphanumeric item, a scaled item and a ref-mod bound across the change.

**Goldens.** `tests/conformance/2023/pb201_position_operand_carriers` (FLOAT-LONG, FLOAT-SHORT, `PIC 9(20) COMP`,
`BINARY-DOUBLE UNSIGNED`, and two ref-mod bounds; expected values computed from the occurrence numbers over
`T = "ABCD"`), `tests/conformance/2023/pb201_odo_count_carriers` (the SECOND emitter: an OCCURS DEPENDING
group image whose control item is a 20-digit COMP / an unsigned BINARY-DOUBLE, sending its §13.18.38.4
GR8a current-count part), negatives `pb201-subscript-group-item`, `pb201-refmod-group-bound` (85/2002/2014/2023) and
`pb201-subscript-based-group` (2002+; BASED is a 2002 addition),
`ArithmeticOperandClassTests.Permissive_GroupPositionOperands_DecodeTheirImageAndAgree`, and the drift guard
`PositionCarrierOverloadDriftTests` — which reflects over `CobolTable.Occ` / `CobolString.RefModPosition` and
fails if the carrier list and the real overloads part company in EITHER direction, or if the two arms stop
admitting the same set. Its failure branch was fired twice before being trusted.

**RULE 17 IS THE GUARD THE SECOND EMITTER'S CARRIER CLAIM RESTS ON, so it got its own negative.**
`RuntimeApi.TableOcc` cannot decline a carrier, so "every carrier that can reach it has an overload" is only true
while something bounds the set — and exactly one thing does: §13.18.38.3 SR17, "Data-name-1 shall describe an
integer", enforced at `DataBinder.Odo.OdoResolve` as `Category: Numeric, IsFloat: false, Scale: 0` (COBOLNET0852).
MEASURED against `PicInfo.ClrType`, that predicate leaves exactly `long` / `Int128` / `ulong` / `UInt128` — plus
the `string` a whole-group promotion may select — and `CobolTable.Occ` declares a parameter for all five; the
`double`/`float`/`decimal` arms are reachable only through `IsFloat`, which SR17 excludes. The screen had no
negative golden, so the accept side alone was holding the claim up: `pb201-odo-depending-not-integer`
(a `PIC 9V9` control item, reject-at 85/2002/2014/2023 — OCCURS DEPENDING is COBOL-85 and SR17 has no
introduction axis) is now the half that fires. Were SR17 to stop firing, a COMP-2 control item would reach
`TableOcc` and put back the very CS1503 this note is about.

**Inventory.** The four rows in `inventory_rows` were re-verdicted CONFORMS by the batch
`pb201-position-operand-carriers` (GAP 3013 → 3009): §8.4.2.3.4 GR1 (all three determination arms, each pinned
by its own golden), §8.4.2.3.4 GR2 (the range condition, and the saturating narrowing that stops a wide carrier
wrapping an out-of-range position back inside `1..n`), §8.4.3.3.3 SR4 (both ref-mod bounds, accept and reject
sides) and §13.18.38.3 SR17.

**⛔ RESIDUE, recorded not fixed (a different root cause, outside this mechanism).** `--permissive` still
offers the digit-decoding leniency to an operand that HAS NO character image: `COMPUTE R = PTR + 1` with
`01 PTR USAGE POINTER` fails the backend with `CS0030 Cannot convert type 'ManagedPointer' to 'System.Int128'`,
and it did so BEFORE this change (that path never touches `PositionRead`). A pointer subscript now reaches the
same one defect instead of a second, differently-shaped one. The honest posture is the one
`IndexNameInPositionError` already documents for the R16 identifier slots — there is no coercion to offer, so
it should be an Error in BOTH lanes, gated on `DataItem.IsImageCapable` in `ExpressionBinder.OperandRef`.
