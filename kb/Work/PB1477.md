# PB1477 — LANDED (wave 68 T)

## The rule (every citation re-run by the registrar through `cite.py --check`)

> The rules for comparing a conditional variable with a condition-name value are the same as those specified for relation conditions

`python scripts/spec/cite.py --check 8.8.4.5.3 "…"` → `OK  §8.8.4.5.3 2)  (General rules)`

## Refuter evidence — row `GR-8.8.4.5.3-2` (PARTIAL)

PARTIAL — The comparison is NOT the relation-condition comparison for a conditional variable that is a group containing an OCCURS DEPENDING ON table (legal: SR1 of 13.18.63.3 excludes only strongly-typed and variable-length groups, and 8.5.1.12 defines variable-length group as one with a dynamic-length item or dynamic-capacity table, not ODO). StringMembershipValue sizes a figurative (ALL literal, ZEROS, SPACES...) to parent.ImageWidth = the MAXIMUM extent, while the operand read is the CURRENT extent; the relation IF GV = ALL "X" sizes the figurative to the current operand and answers TRUE where the 88 answers FALSE. Every other probed shape (PIC A, AE, NE, P-scaling, DECIMAL-POINT COMMA, 31-digit, FLOAT-LONG, boolean pad, PCS ALSO range) agrees with the relation rules.

**Code site.** src/Cobol.Net.Compiler/CodeGen/Emit/ConditionRenderer.cs#RenderCondition88; src/Cobol.Net.Compiler/CodeGen/Emit/ConditionRenderer.cs#RenderMembershipTest; src/Cobol.Net.Compiler/CodeGen/Emit/ConditionRenderer.cs#StringMembershipValue; src/Cobol.Net.Compiler/Binding/ValueSubject.cs

## What the fixer owes

RenderCondition88 / RenderMembershipTest must size a figurative to the operand's CURRENT extent exactly as the relation renderer does — better, route the 88 value comparison through the relation comparison itself so the two can never diverge again. Golden: ODO group, IF GV = ALL "X" and the 88 agree at a partial count.

## Landing (wave 68 T)

**Re-probed.** On the pre-fix main build `88 GV-ALLX VALUE ALL "X"` over `01 GV. 05 GE PIC X OCCURS 1 TO 5
DEPENDING ON N` at N=2 holding "XX" printed F while `IF GV = ALL "X"` printed T; ALL "XX", ALL "X" THRU "Z",
HIGH-VALUE and `EVALUATE TRUE WHEN GV-ALLX` all printed F. On the fixed build every one prints T and the N=3
control ("XXY") stays F (`conformance:85/pb1477_cond88_odo_figurative`).

**Rule.** §8.8.4.5.3 GR2 (the 88 compares by the relation rules) + §13.18.38.4 GR8 a) (an occurs-depending group
item referenced as an operand uses only the part of the table the DEPENDING object's value specifies) + §8.3.3.6.4
GR2 (a figurative is repeated to the associated item's character-position count) — all `cite.py --check` OK.

**Fix.** The figurative VALUE is no longer folded to the declared width at compile time: it is a SEED
(`MembershipOperand.IsFigSeed`) sized at run time against the variable as read (`CobolString.CompareFig` /
`ThruMemberFig`), which is the relation condition's own sizing; the 88 THRU range and the EVALUATE WHEN range now
share ONE renderer, `ConditionRenderer.RenderStringRange`.

**For the next implementer.**
- `ConditionRenderer.cs#StringMembershipOperand` — the one reader of a string 88 VALUE operand (locale-edited,
  numeric-edited, figurative seed, literal). REUSE it; never compute a width here (the runtime sizes the seed).
- `ConditionRenderer.cs#RenderStringRange` — the ONE alphanumeric/national/boolean THRU-range rendering (EVALUATE
  WHEN range + 88 VALUE THRU); the §14.7.8 rule-2 EC carrier choice lives there.
- Trap: the VALUE-clause STORE paths (`ValueInitializer`, `GroupValueSlicer`) legitimately keep the declared-width
  fold — a store fills the declared item; only the COMPARISON reads the current extent.
