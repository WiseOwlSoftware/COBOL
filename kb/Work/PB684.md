# PB684 — OPEN — the sidecar that could not be rewritten

Found 2026-09-05 by the `PB328` implementer (report §"New defects") while sweeping every write-capable host call in
`src/Cobol.Net.Runtime/IO/`.

## The shape

`src/Cobol.Net.Runtime/IO/FixedFileAttributes.cs#Store` (≈291–294) is
`try { File.WriteAllText(SidecarPath(hostPath), …); } catch (IOException) { } catch (UnauthorizedAccessException) { }
catch (ArgumentException) { } catch (NotSupportedException) { }`. §9.1.6 fixes a file's attributes at creation
(`cite.py --check 9.1.6 "fixed file attributes"` → OK) and §14.9.27.4 GR18 makes OPEN OUTPUT a creation
(`--check 14.9.27.4 "If the OUTPUT phrase is specified, the successful execution of the OPEN statement creates the
file"` → OK 18)). **Repro:** create a file through COBOL.NET (OPEN OUTPUT records `<file>.cbattr`), make the SIDECAR
alone read-only while the data file stays writable, then OPEN OUTPUT the same path from a program whose FD declares a
different organization or record size: the new attributes are silently not recorded, the previous file's survive, and
the NEXT OPEN INPUT/I-O/EXTEND compares the connector against them under GR10 and answers '39' — a conforming OPEN
rejected on a catalog for a file that no longer exists.

## Why an adjudication and not a fix

The swallow is arguably deliberate: the catalog is COBOL.NET's own artifact and GR10's validated set is
implementor-defined (the sidecar is a determination, not a rule). But "silently keep the OLD attributes" and
"silently record none" are different outcomes and only the second is harmless. The question to settle first: when the
sidecar cannot be rewritten at a creation, does the implementation (a) delete or invalidate the stale sidecar and run
attribute-less (GR10 cannot fire; the '39' family is lost for that file until a later creation succeeds), (b) refuse
the creating OPEN with '30' (§9.1.13.6 item 1 — the environment could not complete the creation as the
implementation defines it), or (c) keep today's behaviour and document it? (b) is the reading closest to "the
attributes are fixed at creation"; (a) is what a user who made the sidecar read-only by accident would expect.
Survey what the sidecar-keeping compilers do before choosing (owner-decision protocol: follow the surveyed model
implementations; ask only on a significant consideration).

## Then the fix

Whichever arm: `Store` must not swallow silently — it reports or it invalidates. A unit test in
`FileAuthorityPresenceTests`' shape (the precondition established for real: sidecar read-only, data file writable),
one per organization, expected status derived from the chosen arm; DOC-A.1 row for the determination if (a) or (b)
adds an implementor-defined statement. Dispatchable after train 12 lands (PB328 owns `FileConnector.Open`'s new
write-capability line; the sidecar path sits beside it).
