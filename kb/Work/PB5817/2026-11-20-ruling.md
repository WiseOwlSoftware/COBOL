# PB5817 ruling, 2026-11-20

**Mythos session ruling (2026-11-20): NOT A DEFECT; the adjudicator's DEFECT below is overruled.** §1985:IV.4.3.8.2.3 SR3 is satisfied as written by an index-name of any entry in the hierarchy, and §1985:IV.4.3.8.2.4 GR2 makes the index-to-occurrence correspondence implementor-defined ("This correspondence is defined by the implementor", cite.py OK). So the meaning of an index in another dimension's position is the implementor's, CLAUDE.md rule 1's precedence applies, and GnuCOBOL 3.2 accepts it with the same result. Recorded as docs/conformance/3/D-85-INDEX-IN-ANOTHER-DIMENSION.md.

# PB5817 ruling
Verdict: DEFECT
Harm (DEFECT only): under_rejects
Rule: OK  §1985:IV.4.3.8.2.3 SR3  (4.3.8.2.3 Syntax Rules)  the text is in SR3
  quoted: "Index-name-1 must correspond to a data description entry in the hierarchy of the table being referenced which contains an INDEXED BY phrase specifying that index-name"
  read with (each checked OK):
  - §1985:IV.4.3.8.2.3 SR2  "the subscripts are written in the order of successively less inclusive dimensions of the table"
  - §1985:IV.4.3.8.2.4 GR1  "Each successive element within that dimension of the table is referenced by occurrence numbers of 2, 3"
  - §1985:IV.4.3.8.2.4 GR2  "The value of the index referenced by index-name-1 corresponds to the occurrence number of an element in the associated table. This correspondence is defined by the implementor."
  - §1985:VI.6.23.4 GR1  "Index-names are associated with a given table by being specified in the INDEXED BY phrase of the OCCURS clause for that table"
  - §1985:VI.6.23.4 GR3a  "if index-name-2 is related to the same table as index-name-1, no conversion takes place"
  - §1985:III.2 (Table)  "A set of logically consecutive items of data that are defined in the Data Division of a COBOL program by means of the OCCURS clause"
  - §1985:II.4.4.2  "correspond to an occurrence number for that specific dimension of the table with which the index is associated"; "An index-name can be used to reference only the table to which it is associated"
Evidence:
- E:/COBOL-coord/scratch/rulings-1985-open/s1/setsw.cob (the note's repro: R3 OCCURS 2 INDEXED BY RX, C3 OCCURS 3 INDEXED BY CX; `C3 (RX, CX)` and `C3 (CX, RX)`), `--std 85 --run`, run dir s1/runs/setsw-001, EXIT: 0, stdout `OK=b SW=d`. Expected: `C3 (CX, RX)` refused at compile time (CX in the R3 position, RX in the C3 position).
- Regression net only: GnuCOBOL 3.2 (`cobc -std=cobol85 -x -Wall`, WSL, binary s1/gc/setsw) compiles it with no diagnostic and prints `OK=b SW=d`. GnuCOBOL does not check the association at all here; its acceptance is an absent check, not an exercised latitude, and rule 1's precedence settles latitude only.
Mechanism: src/WiseOwl.Cobol.Compiler/Binding/SubscriptBinder.cs#ScreenIndexNameAssociation with #DeclaredInHierarchy (lines 823-845): it asks only whether the index's IndexDeclaration.Table is SOME entry on the referenced item's parent chain, never which entry the subscript POSITION selects. `IndexUse` (SubscriptBinder.cs line 49, `record struct IndexUse(IToken Token, IndexDeclaration Decl)`) does not even carry the position, so the dimension test cannot be written against it. The comment there records the hierarchy-only reading as PB459's choice from the 2023 text.
Fix shape: give IndexUse the subscript's ordinal (its dimension, outermost = 1, after SR4's subscript-count check), and make the screen ask "is decl.Table the OCCURS entry of the referenced item's hierarchy at that dimension" (walk the parent chain collecting OCCURS-bearing entries, reverse, index by ordinal). Report it as COBOL1961 citing §1985:IV.4.3.8.2.3 SR3 at --std 85, with a message that names the dimension ("'CX' is the index of C3; the first subscript of C3 selects an occurrence of R3"). The 2023 row SR-8.4.2.3.3-4 is a separate ruling on the 2023 text; until it is ruled, the positional arm is the 85 reading and is selected by edition through the one citation/edition seam (not a second screen). Goldens at --std 85: `C3 (CX, RX)` refused with COBOL1961; controls that compile: `C3 (RX, CX)`, `C3 (RX, 2)`, `C3 (1, CX)`, relative indexing `C3 (RX + 1, CX - 1)`, and a three-level table using each level's own index; plus the existing cross-table case (`E2 (IX1)`, IX1 of another table) still refused.
Reasoning: The two readings of SR3 are (1) "index-name-1 must be declared by SOME entry of the referenced table's hierarchy" and (2) "the entry index-name-1 corresponds to, by its subscript position, must be the one whose INDEXED BY names it". The rest of the 1985 text makes reading 1 leave the swapped reference with no meaning, which is what decides it:
- In 1985 every OCCURS clause defines a table (§1985:III.2), and an index-name is associated with the table whose OCCURS names it (§1985:VI.6.23.4 GR1); so CX's table is C3's OCCURS and RX's is R3's, not "the two-dimension hierarchy".
- An index's value is an occurrence number of ITS associated table only, by an implementor-defined correspondence (§1985:IV.4.3.8.2.4 GR2; §1985:II.4.4.2 "for that specific dimension"). The 1985 text deliberately leaves the representation to the implementor (a displacement on many mainframe compilers), and the only defined way to move a value between two tables' indexes is SET, which CONVERTS when the indexes are "related to" different tables (§1985:VI.6.23.4 GR3a); the compiler itself already binds RX and CX to different tables for that conversion (the note's confirmed GR1 row).
- The subscript in each position must supply an occurrence number of that position's dimension (SR2, GR1). CX in the R3 position would have to supply an R3 occurrence number, and no rule converts an index value in a subscript. Under reading 1 the reference is therefore legal syntax with no defined semantics, which the text never does on purpose; under reading 2 SR3's "correspond" does the work GR2 presupposes. Section II's "An index-name can be used to reference only the table to which it is associated" states the same thing in the concepts chapter; the ruling does not depend on Section II binding as a rule, since GR2, VI.6.23.4 GR1/GR3a and the glossary carry it.
This is not implementor latitude (the text grants none on which index may stand in which position), so CLAUDE.md rule 1's GnuCOBOL step does not apply. The harm is under_rejects: the compiler accepts the reference and prints `d` (it reads CX's occurrence number as an R3 occurrence number), a plausible answer, so wrong_answer is not set. Pointer only: the 2023 text's SR4 has the same words, so row SR-8.4.2.3.3-4 likely falls the same way, but that is a ruling on the 2023 text and PB459's 2023 choice is not overturned by this note.
