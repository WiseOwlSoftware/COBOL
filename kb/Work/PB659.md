# PB659 — OPEN — the rule's reach and the row's reach disagree

Found 2026-09-05 by the `PB305` implementer (report §"New defects" B), which deliberately did NOT widen the
`editions` column — an edition-reach decision outside its mechanism — and cited its 85 golden
(`tests/conformance/85/pb305_cross_argument_numeric_edited_85.cob`, `PB305CROSS85`) only in the four rows' notes
prose, not as a formal test-ref.

## The question

§15.59.3 r2 and its three siblings (`cite.py --check 15.59.3 …` OK per PB305's report; re-run before acting) carry
no edition qualification in the 2023 text. Intrinsic functions entered the standard with the 1989 Intrinsic
Function Module addendum to COBOL-85, and this compiler's `--std 85` supports them (the 85 golden proves the cross
rule is enforced there), so the rows' `editions: 2002,2014,2023` is a record of when the CURRENT wording appeared,
not of where the compiler applies the rule. Which one the `editions` column means is a campaign-wide convention —
`docs/VERSION_TEST_MATRIX_DESIGN.md` and `docs/VERSION_CHANGE_REFERENCE.md` decide it — and the four rows should
follow it rather than be widened by hand here.

## The work

Read the convention; if `editions` means "the editions at which this compiler claims the rule", widen the four rows
to `85,2002,2014,2023` with the 85 golden as a formal test-ref and check every other intrinsic-function rule row
for the same understatement (the `AR-15.*` population whose functions exist in the 1989 addendum — measure with a
script over the inventory, not by hand); if it means "the editions whose text carries the rule", leave the rows and
record the 85 enforcement in `docs/VERSION_TEST_MATRIX_DESIGN.md` as the module's 85 posture so the matrix has a
cell for it. Either way the answer is one sentence in the design doc and a batch, not four edits.
