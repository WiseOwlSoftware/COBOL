# PB40 — LANDED — a CLASS screen cannot enforce a TYPE rule

> ⚙ **flags:** under-rejects · silent
> **FOUND WHILE VERIFYING A CLAIM IN [[PB15]] RATHER THAN BY LOOKING FOR IT.** PB15's note said the new
> INTEGER-following result rules were "declared but not yet observable". Probing that claim instead of asserting
> it produced a case where integer-ness IS observable and nothing checks it.

**MEASURED (2026-08-04, at `9d3c45a2`):**

```cobol
01 W-F PIC 9V9 VALUE 6.5.
01 W-R PIC X.
    MOVE FUNCTION CHAR(FUNCTION ABS(W-F)) TO W-R      *> compiles clean; no diagnostic
```

§15.15.3 r1 is "Argument-1 shall be an integer." §15.2 item 5: "Integer functions … An integer function has an
operational sign and **no digits to the right of the decimal point**." `FUNCTION ABS(W-F)` over a scaled item is
a NUMERIC function, not an integer one (§15.7.1's table), so this violates §15.15.3 r1 and is accepted silently.
The control compiles and runs correctly: `FUNCTION CHAR(FUNCTION ABS(W-I))` with `W-I PIC 9(3) VALUE 65` prints
`@` (ordinal position 65, 1-based). All three citations `cite.py --check`ed.

## Root cause — the screen resolves through CLASS, and §15.3 type 6 is not a class

`IntrinsicArgumentRules` is a CLASS screen by design and says so: "§15's rules say 'shall be of CLASS numeric' …
so they resolve through Table 2's CLASS column." That is right for the `'n'` code and WRONG for the `'i'` one:
§15.3 **type 6 is INTEGER**, and both an integer function and a numeric function are class numeric (§15.2 items 5
and 6 — "these are of the class and category numeric"), so the `'i'` arm cannot distinguish them and admits both.
`ClassOf` maps a nested call through `ClassOfCategory(ic.ResultCategory)`, and `ResultCategory` folds
INTEGER into `PicCategory.Numeric`, so the information is gone before the screen sees it.

⚠ **CHAR is additionally not in `IntrinsicArgumentRules.Verified` at all**, so today no screen fires for it on any
axis. Fixing only the Verified row would leave the `'i'` arm still unable to tell the two apart — **the rule and
the classifier are two separate halves and both are needed**, which is PB19's lesson (an audited row over a lossy
classifier).

## Why [[PB15]] is the half that makes this fixable

PB15 landed `IntrinsicResultType.Resolve`, which returns the §15.2 **type** rather than the category precisely so
INTEGER survives. So the missing piece is a scale/integer-aware operand test in the screen —
`IntrinsicResultType` already has `IsIntegerOperand`, which answers exactly this question for literals, items
(PICTURE scale 0, usage not INDEX) and nested calls (resolved, not declared). This is a wiring job over an
existing correct primitive, not new machinery.

⛔ **AND THE POPULATION IS NOT JUST CHAR.** Every catalog row whose `ArgKinds` carries `'i'` is in scope
(FACTORIAL §15.36.3, DATE-OF-INTEGER §15.22.3, DAY-OF-INTEGER §15.24.3, INTEGER-OF-DATE, INTEGER-OF-DAY, the
Y2K windowing trio's argument-2/3, FORMATTED-DATE's argument-2, BOOLEAN-OF-INTEGER, …). ⚠ **Do not screen from
`ArgKinds` wholesale** — PB1 established that column is UNAUDITED and enforcing it as written rejected 12 legal
corpus programs. Each row enters `Verified` only with its clause read and `cite.py --check`ed.

## A second consumer, from the standard itself

**§8.4.3.2.3 SR12** — "An integer function other than the integer form of the ABS function shall not be specified
where an unsigned integer is required." That clause is independent evidence that the integer/numeric split is
load-bearing (it legislates about "the integer form of the ABS function" by name), and it names a SECOND
unimplemented screen: the unsigned-integer positions. Worth adjudicating in the same wave.

## ⚙ LANDED 2026-08-06

**The rule the fix rests on decides on the function's TYPE, not on its value** — which is what makes the
rejection safe. §8.4.3.2.3 SR11 (`--check`ed): "A numeric function shall not be specified where an integer
operand is required, **even though a particular reference of the numeric function might yield an integer
value**." So a nested call whose §15.x.1 table resolves to Numeric is inadmissible outright, with no question of
"but this one is integral". `IntrinsicArgumentRules.IntegerViolation` is consulted by the `'i'` code alongside
the class test.

**⚠ AND IT IS DELIBERATELY NARROW, BECAUSE THE OPPOSITE ERROR WAS ONE LINE AWAY.** §15.3 type 6 admits "an
arithmetic expression that will always result in an integer value" in as many words, so a screen written as
"reject unless PROVABLY an integer" would have refused `FUNCTION CHAR(W-I + 1)` — the PB1 failure mode reached
from the other direction. Only two shapes are provably outside type 6 and only those two are rejected: a NUMERIC
function (SR11) and a numeric data item with digits to the right of the decimal point. Everything else fails
open.

⛔ **THE SWEEP FOUND IT WAS NOT ONE FUNCTION.** This note named `FUNCTION CHAR`; measured, every `'i'` position
was affected — `FACTORIAL(FUNCTION ABS(6.5))` silently returned 720 and `INTEGER-OF-DAY(FUNCTION ABS(6.5))`
returned 0. The fix is in the shared code, so all of them close together.
⚠ This note also said "CHAR is additionally not in `IntrinsicArgumentRules.Verified` at all" — **stale**: CHAR and
CHAR-NATIONAL have been `'i'` rows since the Phase-B batch-2 wave. The screen did fire; it just could not see the
distinction.

⭐ **AND IT CAUGHT A GOLDEN ASSERTING ILLEGAL SOURCE.** `pb32_dec_carrier_intrinsic_argument` ran
`FUNCTION MOD(A + B, B)` over `PIC S9(9)V99` items, and its header cited §15.3 **type 10** ("an arithmetic
expression or a numeric data item") for the whole family — but MOD is **type 6**: §15.64.3 r1 is "Argument-1 and
argument-2 shall be integers". The golden asserted that illegal source COMPILES, and it was accepted only
because a scaled numeric item is class numeric. Corrected to `FUNCTION MOD(J + 10, 7)`, which keeps the
dec-carrier point (an arithmetic-expression argument through the AlignedArgs route under STANDARD-DECIMAL)
intact; §15.64.4 makes the value 6. **A golden is not evidence of legality — it is evidence of what we decided,
and this one had decided wrong** ([[feedback_green_test_can_hold_a_gap_open]]).

**Golden** `pb40_integer_argument_positions` (the ACCEPT side — four shapes type 6 admits, plus FACTORIAL and
MOD) · negatives `pb40-numeric-function-in-integer-position`, `pb40-scaled-item-in-integer-position`.

## ⛔ THE BATTERY WENT RED, AND THE RED WAS THE EXTERNAL ORACLE DISAGREEING — CORRECTLY ATTRIBUTED

`=== BATTERY: NOT GREEN (rc=1) ===`, on one row: the GnuCOBOL differential reported
**1 PER-CASE FLIP — `run_functions:221`, `AGREE_ACCEPT → WE_REJECT_THEY_ACCEPT`**, carrying this fix's own
`COBOLNET1627`. §0's mechanical rule classes an AGREE→divergence flip a REGRESSION, so it had to be attributed
before it could be dispositioned.

**ATTRIBUTED FROM THE CASE, NOT FROM THE LABEL.** The test (title "FUNCTION CHAR") declares its argument
`PIC S9(4)V9(4)` — four digits to the right of the decimal point — and passes it straight to `FUNCTION CHAR`.
§15.15.3 r1 is "Argument-1 shall be an integer" and §15.3 type 6 admits "an integer data item" or an
always-integral arithmetic expression; a scaled item is neither. **So the program is illegal COBOL and GnuCOBOL
is being lenient** — we now diverge in the STRICT direction, on source the standard rejects. That is a
conformance improvement wearing the mechanical label of a regression.
⚠ GPL: only the facts needed to attribute the flip were taken (the argument's PICTURE and the test title). No
source or expected output was copied.
