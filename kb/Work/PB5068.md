# PB5068 — a drained loop never holds

Filed 2026-11-09 by the operator session while it wound the loop down for a CLI update.

**Symptom.** The log `E:\COBOL-coord\logs\orchestrate-operator-20261109b.log` shows the same unit choice ten times from
19:03:42 onward: `unit 'wave' (campaign PB4812: no ready note (PB4885 waits on PB4997; PB4886 waits on PB4885)) on
opus`. Each one ended `exit 0, handoff done`, after about 127 to 174 s and 6 or 7 calls, and planned 0 groups
(`plan_wave.py --from-budget` planned 0 groups, 0.00 of 14.97 weekly points). The tenth handoff
(`handoff.last.json`, wave 20261970) set `next_unit: null` and said: "Ten consecutive wave units planned zero groups;
work.py next shows nothing unblocked that harms a user's program. Do not start another wave unit until a kb/Work note
becomes actionable." The supervisor started an eleventh at 19:30:35 anyway. Each empty unit costs an Opus session start
(the skill load and the planner run), and with nothing actionable the loop would spin like this indefinitely.

**Mechanism.** `scripts/orchestrator/next_unit.py` has no "nothing to do" outcome. `base_choice` turns a handoff with
no `next_unit` into a wave-type unit. Then `choose` passes every wave-type choice to `campaign_choice`, and that
function's `if not ready:` branch returns `{"unit": "wave", ...}` even when every lane waits on another note. Neither
path asks whether the fix-lane planner has anything to plan, and the handoff's own judgment ("do not start another wave")
is read only as a reason string (PB2522 made the alternation the supervisor's rule, not the model's).

**Sites:** `scripts/orchestrator/next_unit.py:215` (`base_choice`), `scripts/orchestrator/next_unit.py` (`campaign_choice`,
its `if not ready:` branch) and `scripts/orchestrator/next_unit.py` (`choose`).

**Fix shape.** Give the supervisor an IDLE choice that the disk decides, not the model. When no campaign lane is ready
and the fix-lane population (`work.fixable`, the predicate the planner uses, PB4951) is empty, and no branch waits for
review, a finisher or landing, choose `idle`. The supervisor then sleeps, runs only the review and landing lane ticks,
and starts a wave again only when `work.fixable` or a lane state changes (a note lands, a block lifts). A test drives
`choose` with drained lanes and an empty fixable set and asserts `idle`. A second test asserts that a fixable note
appearing ends the idle state.
