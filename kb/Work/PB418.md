# PB418 — one substituted premise, four rules broken, and a DEFAULT phrase that writes the wrong value

Adjudicated in lane-3 batch b2 (`initialize-statement` part 2, with two refuter corrections).
⚠ **The adjudicator's pointer probes no longer compile on HEAD** — see §3 — so the defect was re-cast onto
legal source and **re-measured on HEAD 89044aa0**. It reproduces.

## 1. The mechanism

`InitializeSender` (`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs:213-227`) opens

```csharp
if (spec.ToValue && (spec.ValueCategory is null || spec.ValueCategory == cat) && rawValue is { } raw)
    return InitializeValueOperand(raw);
```

and `ExpandInitialize` (`:158-164`) uses that method's non-null result as its **only** qualification signal —
for a pointer / object-reference receiver at `:160`, and for every other receiver at `:164`. So the VALUE
arm's gate is *"the item carries a Format-1 VALUE clause"* where the standard's gate is a three-way test.
Two of the three ways are unimplemented, and each produces its own wrong answer:

* **The categorical way.** The standard makes a data-pointer / message-tag / object-reference /
  program-pointer receiver a receiving operand under the VALUE phrase **unconditionally**, and it exists
  precisely because those categories can never carry a VALUE clause: `§13.18.63.3` forbids one on
  FUNCTION-POINTER, MESSAGE-TAG, OBJECT-REFERENCE and PROGRAM-POINTER outright, and for a plain USAGE POINTER
  the only writable value is the predefined NULL, which `§8.4.3.10.3` permits **only** as an INITIALIZE/SET
  sending operand, an argument, or in a relation condition — never in a VALUE clause. `rawValue` is therefore
  always null for these categories in a conforming program and the arm is **100% dead**.
* **The table-VALUE way.** The binder reads only `DataItem.RawValue` (the Format-1 VALUE text) and never
  `DataItem.TableValues` (the Format-2 map of literal lists to occurrence ranges); the two are mutually
  exclusive by construction (`Binding/Model/DataItem.cs` says so). A table-VALUE element reaches
  `InitializeSender` with `rawValue == null`, fails the VALUE arm, matches no REPLACING category, and — absent
  the DEFAULT phrase — falls off the end to `return null`, so **no store at all** is emitted for any
  occurrence. The same missing read is both the qualification rule and the per-occurrence sender rule, which
  is why one line of omission produces two rule failures.

**The refuter's sharpest observation, and the reason this note exists as one note:** because
`InitializeSender` is simultaneously the qualification test *and* the sender choice, adding
`THEN TO DEFAULT` does not merely fail to help — it converts the silent omission into a silent **wrong
value**. The DEFAULT arm qualifies the occurrence and then supplies the category default, so all three
occurrences are overwritten with SPACES where the table VALUE should have restored AA/BB/CC. **The DEFAULT arm
is the code that writes the wrong bytes**, and that is a strictly worse observable than writing nothing.

The structural cause is one thing said twice: the receiver TEST and the SENDER CHOICE are the same method.
That is why the pointer branch has to abuse a *sender* as a *predicate*, and why the DEFAULT arm cannot
express "already qualified through VALUE, keep that sender".

**Corroborating, out of scope for this clause but found on the way:** the compiler accepts
`05 P1 USAGE POINTER VALUE NULL.` — which `§8.4.3.10.3` forbids — and then fails the backend. So the one shape
that could have made `rawValue` non-null for a pointer does not work either; the VALUE arm is unreachable by
every route. That belongs to the VALUE-clause / NULL rows, not to this note's.

**General rule 7 (dynamic length) — the refuter's second correction, verified by reading on HEAD.**
`InitializeBinder.cs:167` is `if (item.IsDynamicLength) source = new BoundStringLiteral("");`, placed **after**
the sender choice at `:164`, so it overrides the VALUE sender and the REPLACING sender as well as the category
default. Only the category-default branch is (a) forced by the standard — the figurative-constant length rule
quoted above is why the pre-fix compiler left such an item at length 1 — (b) justified by the code's own
comment, and (c) pinned by `conformance:2014/initialize_dynamic_length`. The other two branches rest on an
**unadjudicated** reading that puts general rule 7 in direct conflict with the VALUE-restoring sender rule and
with `§8.6.4`, and the conflict's resolution is recorded nowhere — not in `kb/Work`, not in
`docs/rearchitecture/CODE-SPEC-AUDIT.md` CA1, not in the golden's header (which names only the
category-default branch). The measured consequence is on PB415's SR8 row: the statement whose whole purpose is
to restore the VALUE-clause state does not restore it, and a REPLACING sender the programmer wrote is
discarded **at bind time**, so a function-identifier sender is never even evaluated.

## 4. The code site and the shape of the repair

* `.../Verbs/InitializeBinder.cs:213-227` `InitializeSender` — the `rawValue is { } raw` gate; qualification
  and sender choice fused into one method.
* `.../Verbs/InitializeBinder.cs:158-163` `ExpandInitialize` — the pointer / object-reference branch that uses
  a sender's non-nullness as a predicate.
* `.../Verbs/InitializeBinder.cs:164` — the same abuse for every other receiver; `:167` — the dynamic-length
  substitution that lands after the choice.
* `.../Binding/Model/DataItem.cs` — `TableValues`, populated and never read here.
* `.../CodeGen/DataDivision/ValueInitializer.cs` — the declaration-time consumer that **does** read it, and
  therefore the proof the data is available.

**CLAUDE.md rule 5: split the two rules that are one method.** Give the walk a *qualification* function
(`bool IsReceivingOperand(item, spec)`) implementing general rule 5's step c as three explicit conditions, and
a separate *sender* function implementing general rule 6's ordered a → b → c. Then the categorical condition,
the table-VALUE condition and the eight category words PB415 will add are each **a case in one place**, the
pointer branch stops needing a predicate that is really a sender, and the DEFAULT arm can no longer overwrite
a value the VALUE arm already qualified. Reading `TableValues` per occurrence is then a sender-side lookup
keyed on the loop's bind-time index, which the expansion already has.

The general-rule-7 conflict is an **owner determination**, and it is the one thing here that is not a
mechanical fix: does the dynamic-length length-zeroing override an explicit VALUE or REPLACING sender, or only
the category default? Whichever way it goes, it needs goldens on the TO VALUE and REPLACING arms before that
row can close.

## 5. The sibling sweep the fixer must do

* **Both branches of `ExpandInitialize`.** The `rawValue`-as-predicate abuse appears at `:160` (pointer-ish)
  and at `:164` (everything else). Fixing one leaves the other — the register's most reproducible defect shape.
* **Every consumer of `DataItem.RawValue` in the binder** must be asked whether it should have been asking
  `TableValues` too; `ValueInitializer` is the model for what the pair means.
* **The pointer-level rule the new probes exposed.** Now that a USAGE POINTER child of a plain group is
  correctly rejected, every probe, golden and test that declares one is illegal source. Sweep
  `tests/` and the probe corpus for `05 … USAGE POINTER` / `OBJECT REFERENCE` / `PROGRAM-POINTER` under a
  non-STRONG group before trusting any of them.
* **The DEFAULT arm's ordering** must be re-verified against a Format-1 VALUE *and* a Format-2 VALUE after the
  split; the currently-green `conformance:2002/initialize_phrases` pins only the Format-1 half.
* Editions: the TO VALUE phrase, the DEFAULT phrase, Format-2 VALUE and these usages are COBOL-2002+;
  dynamic-length items are COBOL-2014+. MESSAGE-TAG is 2023 and inside the owner-declined MCS facility.
