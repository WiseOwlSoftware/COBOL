# PB418 — one substituted premise, four rules broken, and a DEFAULT phrase that writes the wrong value

## LANDED WHOLE 2026-09-20 — the GR7 owner determination is answered (D-DL1), and the note is terminal

⛔ **`status: landed`.** The one thing holding this note since 2026-09-13 was the OPEN OWNER DETERMINATION on
§14.9.20.4 general rule 7 — does the dynamic-length length-zeroing override an explicit VALUE or REPLACING
sender, or only the category default? It is answered as **DETERMINATION D-DL1** (`docs/CONFORMANCE.md` §3):
**GR7 is the GR6c arm’s rule, not a post-pass over all three sending-operand arms.**

**The reading chosen, and the reading rejected.** REJECTED: GR7 as printed, unconditionally — which is what
this compiler did, and which erases the sending operand GR6a and GR6b have just designated. CHOSEN: GR7 applies
only where the item qualified through GR5c3 (DEFAULT) or GR5c4 (neither phrase), i.e. only where GR6c supplies
the sender. Four grounds, each `cite.py --check`’d at the code site and in `docs/CONFORMANCE.md` §3:

1. §14.6.2.3.2 GR7 states **the same action at the other occasion with the carve-out spelled out** — "The length
   of each dynamic-length elementary item **that is specified without a VALUE clause** is set to zero". The
   standard’s own parallel sentence excludes the VALUE case; §14.9.20.4 GR7 is elliptical, not broader.
2. §8.6.4 makes a dynamic-length item’s initial-state LENGTH the VALUE clause’s length, and §14.9.20.4 GR6a3
   demands a sender that "produces the same result as the initial value of the data item as produced by the
   application of the VALUE clause". Under the unconditional reading **no sender can satisfy GR6a3** for this
   population — a general rule becomes unsatisfiable, not merely narrowed.
3. §14.9.20.3 SR8 designates literal-1 / identifier-2 as THE sending operand under REPLACING; the unconditional
   reading makes that designation inert for every dynamic-length receiver. (That is kb/Work PB415’s
   `SR-14.9.20.3-8`, closed by this same change.)
4. GR7 is NECESSARY only on the GR6c arm: §8.3.3.6.4 GR3b gives a bare figurative constant a length of one
   character, so GR6c’s "Figurative constant alphanumeric SPACES" would otherwise leave the item at length 1
   rather than §13.18.19.4 GR1’s minimum of zero. On the other two arms GR7 adds nothing another rule does not
   already say — it only subtracts.

**The fix is one predicate at the one site.** `ElementaryAction`’s
`if (item.IsDynamicLength) source = new BoundStringLiteral("")` became
`if (item.IsDynamicLength && q is InitializeQualification.ViaDefault) …` — possible only because PB418’s own
GR5c/GR6 split made the qualification a value rather than a side effect of the sender choice. `grep -rn

`MoveEmitter`’s dynamic-length store is what now carries the VALUE / REPLACING sender’s own length, which is the
same store `ValueInitializer` uses at declaration time — so the restored state and the initial state cannot
disagree, which is precisely what GR6a3 asks for.

**Witnessed at both poles.** `conformance:2014/initialize_dynamic_length` (the GR6c arm, `LEN=00`) is unchanged
and still green; `conformance:2014/pb418_initialize_dynamic_length_senders` pins the GR6a arm (`LEN=05 [hello]`),

## 1. The mechanism

`InitializeSender` (`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs:213-227`) opens

```csharp
if (spec.ToValue && (spec.ValueCategory is null || spec.ValueCategory == cat) && rawValue is { } raw)
    return InitializeValueOperand(raw);
```

and `ExpandInitialize` (`:158-164`) uses that method's non-null result as its **only** qualification signal —
for a pointer / object-reference receiver at `:160`, and for every other receiver at `:164`. So the VALUE
arm's gate is *"the item carries a Format-1 VALUE clause"* where the standard's gate is a three-way test.
Two of the three ways are unimplemented, and each produces its own wrong answer:

* **The categorical way.** The standard makes a data-pointer / message-tag / object-reference /
  program-pointer receiver a receiving operand under the VALUE phrase **unconditionally**, and it exists
  precisely because those categories can never carry a VALUE clause: `§13.18.63.3` forbids one on
  FUNCTION-POINTER, MESSAGE-TAG, OBJECT-REFERENCE and PROGRAM-POINTER outright, and for a plain USAGE POINTER
  the only writable value is the predefined NULL, which `§8.4.3.10.3` permits **only** as an INITIALIZE/SET
  sending operand, an argument, or in a relation condition — never in a VALUE clause. `rawValue` is therefore
  always null for these categories in a conforming program and the arm is **100% dead**.
* **The table-VALUE way.** The binder reads only `DataItem.RawValue` (the Format-1 VALUE text) and never
  `DataItem.TableValues` (the Format-2 map of literal lists to occurrence ranges); the two are mutually
  exclusive by construction (`Binding/Model/DataItem.cs` says so). A table-VALUE element reaches
  `InitializeSender` with `rawValue == null`, fails the VALUE arm, matches no REPLACING category, and — absent
  the DEFAULT phrase — falls off the end to `return null`, so **no store at all** is emitted for any
  occurrence. The same missing read is both the qualification rule and the per-occurrence sender rule, which
  is why one line of omission produces two rule failures.

**The refuter's sharpest observation, and the reason this note exists as one note:** because
`InitializeSender` is simultaneously the qualification test *and* the sender choice, adding
`THEN TO DEFAULT` does not merely fail to help — it converts the silent omission into a silent **wrong
value**. The DEFAULT arm qualifies the occurrence and then supplies the category default, so all three
occurrences are overwritten with SPACES where the table VALUE should have restored AA/BB/CC. **The DEFAULT arm
is the code that writes the wrong bytes**, and that is a strictly worse observable than writing nothing.

The structural cause is one thing said twice: the receiver TEST and the SENDER CHOICE are the same method.
That is why the pointer branch has to abuse a *sender* as a *predicate*, and why the DEFAULT arm cannot
express "already qualified through VALUE, keep that sender".
