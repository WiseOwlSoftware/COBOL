# PB317 — the NO REWIND phrase reaches the parser and stops there

**Rows:** `GR-14.9.27.4-11`, `GR-14.9.27.4-12`.

## The program

`<lane3 scratch>/out-b1/probe/norewind/NOREW01.cob` (`ORGANIZATION IS SEQUENTIAL`, `FILE STATUS IS FS`), at the
default `--std 2023`:

```cobol
OPEN OUTPUT F.  WRITE R.  CLOSE F.
OPEN INPUT  F WITH NO REWIND.   DISPLAY FS.   *> prints 00, must print 07
CLOSE F.
OPEN OUTPUT F WITH NO REWIND.   DISPLAY FS.   *> prints 00, must print 07
CLOSE F WITH NO REWIND.         DISPLAY FS.   *> prints 07 — the CLOSE arm is correct
```

## The rule

§14.9.27.4 GR11:

> The NO REWIND phrase will be ignored if it does not apply to the storage medium on which the file resides. If
> the NO REWIND phrase is ignored, the OPEN statement is successful and the I-O status associated with
> file-name-1 is set to '07'.

`--check 14.9.27.4 "The NO REWIND phrase will be ignored if it does not apply to the storage medium on which the
file resides"` → **OK**.

§14.9.27.4 GR11's *"does not apply to the storage medium"* is given its meaning by §9.1.13.2 item 6: '07' is
set when a CLOSE with the NO REWIND / REEL / UNIT / FOR REMOVAL phrase **or an OPEN statement with the NO
REWIND phrase** references a
physical file on a non-reel/unit medium. COBOL.NET's only medium is mass storage — non-reel/unit — which is
precisely why `FileRegistry.CloseReelUnit` and `CloseNoRewind` already return '07' and cite this same item.
§14.9.27.4 GR12 b), under which NO REWIND would instead SUPPRESS repositioning, is not reachable on this medium
and is not implemented either, so the compiler holds no position on the phrase under either rule.

The Annex A.3 escape does not apply: A.3 item 33 makes the OPEN NO REWIND phrase dependent on a reel **or mass
storage** device, and a mass storage device is present — exactly as for the identically-worded A.3 item 30 CLOSE
twin the compiler does implement.

## What the compiler does

`CobolIO.g4` `openFileSpec` is `dataReference (REVERSED | WITH? NO REWIND)?`; `BindOpen` reads only
`spec.dataReference()` and never inspects `spec.REVERSED()` or `spec.NO()`/`spec.REWIND()`; `BoundOpen` has no
REWIND field; `EmitOpen` emits a bare `RuntimeApi.FileOpen`; there is no `OpenNoRewind` anywhere in
`FileRegistry` or `FileConnector`. A grep of `src/Cobol.Net.*` for `"07"` returns exactly two sites, both CLOSE
(`FileRegistry.cs:239` `CloseReelUnit`, `:256` `CloseNoRewind`); `FileStatusCode` has no named constant for '07'.

This is the project's most reproducible defect shape: a dispatch with two arms where only one was fixed.
`kb/Work/PB141` corrected `CLOSE ... WITH NO REWIND` (which had also reported '00') and left the OPEN arm
untouched — and `CloseNoRewind`'s own doc comment derives the '07' from §9.1.13.2 item 6 while quoting only the
CLOSE half of that item's sentence.

**Code sites:** `SequentialIoBinder.cs#BindOpen` (lines 37-45) · `BoundTree.cs#BoundOpen` (no REWIND field,
unlike `BoundClose`/`BoundCloseKind.NoRewind`) · `SequentialIoEmitter.cs#EmitOpen` ·
`FileRegistry.cs#CloseNoRewind` (the fixed twin) · `src/Cobol.Net.Runtime/IO/FileStatus.cs`.

## Two documents inherited the omission and are fixed in the same change set

* `docs/CONFORMANCE.md` §2 row `33-34 | OPEN WITH NO REWIND / EXTEND | Partial | EXTEND claimed; WITH NO REWIND
  inert (no reel device)` contradicts A.3 item 33's own *reel or mass storage* wording.
* `docs/CONFORMANCE.md` line 111 asserts *"the only 07 setter is CLOSE REEL/UNIT"*, untrue since PB141 added
  `CloseNoRewind`.

## The fix shape

The tape/positioning phrases ride the bound OPEN as a per-file-spec value the way the CLOSE kind already rides
`BoundClose`'s per-file tuple — i.e. the per-group `BoundOpen.Files` restructuring **PB316** already requires.
`EmitOpen` then selects an `OpenNoRewind` entry and `FileRegistry` gains the OPEN twin of `CloseNoRewind`: one
medium model, one '07' derivation, both statements.

## Landed 2026-09-05

Re-probed first on a worktree built from `b61a308a`: `OPEN INPUT F WITH NO REWIND` → `00`, `OPEN OUTPUT F WITH
NO REWIND` → `00`, `CLOSE F WITH NO REWIND` → `07`. Reproduced exactly as written. After the fix all three read
`07`.

**The shape was the one this note predicted, and it grew by two rules.** `BoundOpen.Files`' three-element tuple
became the named record **`BoundOpenFile(File, Mode, NoRewind, Unsupported)`** — per FILE-NAME, because
§14.9.27.4 GR20 makes the separate OPEN statements a multi-file OPEN is equivalent to carry *"the same open mode
specification, the sharing-phrase, retry-phrase, and REWIND phrase"*: the mode and the two phrases are the
group's, the REWIND phrase is the file-name's own. `BindOpen` reads `spec.REWIND()`; **both** emitter arms carry
the flag — the plain `RuntimeApi.FileOpen` → `CobolFile.OpenNoRewind` and the sharing-aware `FileOpenShared`,
because SHARING/RETRY and NO REWIND are independent phrases of one general format and a statement may write both
(honouring it on one arm only would have been this defect's own shape, re-introduced one layer down). The mode
rendering the emitter kept inline became `RuntimeApi.FileOpenModeExpr`, so the sharing entry and the NO REWIND
entry cannot disagree about a mode.

**`FileRegistry.NoRewindPhraseEffect` is the ONE site of GR11 and GR12**, keyed on the same
`PhysicalFileCategory` the CLOSE arm's Table 14 is keyed on. It refuses any category but (a) Non-unit LOUDLY —
GR12 b)'s suppress-the-repositioning arm is unimplemented because no supported medium permits rewinding — and
overlays `'07'` only where the status' first digit is `'0'`, since §14.9.27.4 GR25 a) reserves an unsuccessful
open's own diagnosis. `unit:CloseTable14Tests.OpenNoRewind_IsTheCloseArmsTwinOnTheSameMedium` is the drift test
for that closure.

**Two syntax rules landed with it, and had to.** §14.9.27.3 SR5 (*"The NO REWIND phrase may be specified only
for sequential files"*) and SR6 (*"… only when the INPUT or OUTPUT phrase is specified"*) are `kb/Work PB318`'s
rows `SR-14.9.27.3-5` / `SR-14.9.27.3-6`, but they share this note's root cause — the phrase never left the parse
tree, so nothing could pair it with either the file's organization or its group's mode — and **SR5 is what makes
GR11 answerable**: without it a relative or indexed file reaches a runtime rule that category (d) has no answer
for. Both are screened in `StatementValidation` (`CheckOpenNoRewindOrganization` → COBOLNET1802,
`CheckOpenNoRewindOpenMode` → COBOLNET1803), SR5 on the same `FileModel.IsSequential` predicate its CLOSE twin
§14.9.6.3 SR1 tests, so the two arms of one rule the standard writes twice cannot drift. PB318's other two rows
(SR1, SR2) are untouched and it stays open.

**Determination recorded** (`docs/CONFORMANCE.md` §3): where §9.1.13.2 item 4 a)'s `'05'` would also apply — an
OPTIONAL INPUT file that is not present, opened `WITH NO REWIND` — GR11's `'07'` governs, because GR11 is an
explicit assignment in the statement's own general rules while item 4 a) is a description in the status-value
clause, and §14.9.27.4 assigns `'05'` only in GR17, whose EXTEND/I-O modes SR6 bars from carrying the phrase.

**Goldens:** `conformance:2023/pb317_open_no_rewind` (every value derived in the program's own header, including
the proof that the phrase is IGNORED rather than honoured — `OPEN OUTPUT … WITH NO REWIND` still empties the
file per GR18); `conformance:85/pb317_open_no_rewind_85` (edition invariance — the phrase is ungated, only its
sibling REVERSED was deleted in 2002, VCR 7.12); `conformance:negative/pb317-open-norewind-relative` (SR5) and
`conformance:negative/pb317-open-norewind-extend` (SR6), both `reject-at: 85 2002 2014 2023`.

**Docs corrected in the same change set:** `CONFORMANCE.md` §2 rows 33–34 (the disposition and its witnesses),
§3's *"the only '07' setter is CLOSE REEL/UNIT"* bullet — untrue since PB141 and doubly so now — plus the new
`'07'`-over-`'05'` determination; `COBOLNET_FILES_DESIGN.md` D11 (the OPEN half of the medium determination);
`VERSION_CHANGE_REFERENCE.md` row 7.12, which cited **§14.9.26 — the MULTIPLY statement** — for NO REWIND's
survival; `DIAGNOSTICS.md` for the two new codes.

**Rows:** `GR-14.9.27.4-11` DIVERGES → CONFORMS (closed); `SR-14.9.27.3-5` and `SR-14.9.27.3-6` NOT-IMPLEMENTED
→ CONFORMS (closed); `GR-14.9.27.4-12` PARTIAL → CONFORMS but deliberately still a GAP — see below.

### ⛔ One thing in this note did NOT hold, and it leaves an owner question open

The note said GR12 b) *"is not reachable on this medium"* and treated arm (a) as a live obligation, following
the inventory row, which recorded arm (a) as VERIFIED against `SequentialConnector.OpenCore`. **The whole rule
is vacuous, both arms.** GR11 and GR12 partition the media between them — GR11 governs a medium the phrase
*"does not apply to"* (§9.1.13.2 item 6: non-reel/unit), GR12 a medium that *"permits rewinding"* — so placing
every sequential connector in category (a), which §9.1.13.2 item 6 already FORCED, chooses GR11 and empties
GR12. What `OpenCore` realizes is §14.9.27.4 **GR14** (*"the file position indicator for that file connector is
set to 1"*), which is unconditional; a golden written for GR12 a) would be measuring GR14, which is exactly the
evidence `DRV-DOC-A.1-19` records deleting a witness for.

So `GR-14.9.27.4-12` wants a `docs/CONFORMANCE.md` §8 derivation row `DRV-GR-14.9.27.4-12`, arm
`unpopulatable-antecedent`, closed set = the two `PhysicalFileCategory` values any connector reports. **An agent
may not sign one** (`Derivation.refusals` → `bad-signature`), so the row is recorded CONFORMS-but-uncovered and
stays a GAP until the owner signs. The drafted row is in the PB317 implementer report.
