# PB3336 — the performance witnesses

Implement FROM `docs/rearchitecture/DESIGN-runtime-library.md` 2.2.1.11 (the table of bounds and the witnesses (a)-(d);
(d) landed with PB3335, `WholeStoreBanDriftTests`; witness (e), a transaction's cost, needs the transaction runtime and is
PB3337's). Follows PB3335 (the engine complete). No wall-clock assertion anywhere (the repository's rule): every witness
reads `PagedFile.Counters` (`IoCounters`, cumulative) across one statement.

## Mechanism

`tests/Cobol.Net.Tests.Unit/Store/KeyedStorePerformanceWitnessTests.cs`, one class per file shape {RELATIVE, INDEXED with 0
and with 2 alternate keys (one WITH DUPLICATES, one unique)}, each cell {ascending keys, a fixed random permutation} × {NO
OTHER, ALL OTHER}:

- (a) linearity: load N = 5 000 and 4N records (the sizes straddle the prime tree's root split; N = 20 000 was this note's
  first guess and both sizes are depth 3, so the depth growth was never exercised); every statement within its 2.2.1.11
  row, the ledger within R2's checkpoint, the mean per statement at 4N within the mean at N + the depth growth, the
  ledger's growth and the FREE batch;
- (b) OPEN reads the header after a CLOSE (≤ 3 + 7, whatever N) and after a process death (3 + the ledger tree's pages and
  its fresh pages, the dead run unit's completed statements adopted);
- (c) 1 000 cold random READs by the prime key read exactly d (+ 1 under the mutex); by the unique alternate key its path,
  the prime tree's, + 1 when the composite's prefix seek crosses a leaf;
- the READ NEXT walk (PB2129's and PB2755's scenarios) reads each page once, AT END answers '10', the alternate key WITH
  DUPLICATES answers '02' exactly when the next record shares the value;
- every exception path is a case beside its success: '22' (prime and unique alternate), '23' (READ, DELETE), '30' and the
  permanent error's replay (one case per verb: WRITE, READ, READ NEXT, START, REWRITE, DELETE, in both sharing modes,
  each touching no page), '51' with RETRY failing and succeeding — each writes nothing.

## Landed (wave 1118, group A6)

Re-probed on the merged PB3335 build: the witnesses did not exist, and the seam they need did not either — `PagedFile`
counts and drops its cache, but nothing reached a connector's store from a test. `KeyedConnector.PagedStore` and
`FileRegistry.PagedStoreOf` are that seam (internal, read-only). The cases run the real connectors with the pages in
`PageArrayMedium` (an in-memory page array per physical file, the latest version of each page and nothing else; the host
file keeps the handles and the locks), so the 87 cases cost about 4 minutes in parallel and count identically on every
host.

What the counts corrected in 2.2.1.11 (the design text now states each, with its measurement):
- **The ledger's share of a statement is not ≤ 2.** The ledger is keyed by page number and loaded whole; a statement of
  scattered keys releases pages anywhere in the file, so its path copy writes the ledger's root and one leaf per leaf its
  entries land on — measured ℓ ≈ 5 pages per WRITE in a random relative load at 20 000 records (ascending: 1), and the
  ledger at 1 028 entries on 9 pages under two alternate keys. R2's checkpoint (1 024 entries, plus the pages of the one
  statement that begins at it: `PagedFile.Begin` promotes only a ledger that already exceeds it), not the file's size, bounds
  it, so the load stays linear; the witness asserts the bound with ℓ read from the file and asserts the checkpoint. Whether
  the ledger should be organized so a statement's entries land on one leaf is a lead in the wave-1118 A6 report.
- **A split adds pages.** The WRITE rows now carry s, one page per level that splits; the witness proves the statements'
  excess over the no-split row, summed over a load, is at most the pages the trees gained.
- **OPEN after a death** reads the ledger tree's pages beside its fresh pages (it is loaded whole); the coherent entry's
  adoption by a writable store likewise reads the ledger tree, not "≤ 2".
- **A READ by an alternate key** reads one more page when the prefix seek of its (key value, release ordinal) composite
  lands past a leaf's last entry (13 to 17 of 1 000).
- **An unsuccessful statement** ('22', '23', '51' and each RETRY attempt, a replayed permanent error per ISO §9.1.13.1) writes
  nothing. A replayed permanent error reads nothing either, not even the coherent entry's page 2, and takes no store mutex:
  docs/CONFORMANCE.md DOC-A.1-105 says such a statement "does not touch the physical file", so
  `KeyedConnector.BeginStatement` is inert while the condition is in effect and `FileRegistry.NoLockQuestion` asks no lock
  question before the verb replays it (the condition outranks a '51'). A new row says so (review R1-2).

The prototype's wall-clock arithmetic stays in 2.2.1.11's closing sentence; this group adds nothing wall-clock.
`perf_baseline.py --against` the R0 record (PB2129's last line) needs a Release build and a whole-scope gate; it remains the
lander's, as the A5 report recorded.
