**Finding:** CA1062: five public model members of the compiler, which has nullable enabled, are reported for missing null guards; the right disposition is to configure the rule off, not to add guards

**Rule:** CA1062 (validate arguments of public methods), at AnalysisLevel latest-all as DESIGN-architecture-review §5.5 applies analyzers first. The pin builds with <Nullable>enable</Nullable> (Directory.Build.props), so every one of these parameters is already declared non-null and the compiler checks the callers. The one-mechanism-per-job rule (CLAUDE.md rule 4, no second mechanism) argues against a run-time guard as well.

**Scenario:** The analyzer reports CellTableSegment.Of (AccessPath.cs:143-144, parameter table), ActivationCrossing.StringCarried (ActivationCrossing.cs:18-21) and LeafCarried (:42-43), CsNames.CSharpNamespace (CsNames.cs:166-167, parameter ns) and CsNames.Allocate (:172-177, parameter scope). Each parameter is non-nullable. The types are public, but no assembly outside WiseOwl.Cobol.Compiler names them; the tests reach them through InternalsVisibleTo (WiseOwl.Cobol.Compiler.csproj:21-22). If an R4 wave takes the analyzer at its word and applies the code fix, it adds ArgumentNullException.ThrowIfNull to hot model helpers: StringCarried runs for every item that crosses an activation boundary, and Allocate runs for every emitted name. That is a second null mechanism beside the nullable annotations, it is checked at run time instead of compile time, and the same fix would spread to every public member of the Binding.Model folder.

**Target:** In the R4 analyzer pass for CA1062 (design DESIGN-architecture-review §8.7 item 4), record the disposition once: dotnet_diagnostic.CA1062.severity = none in a compiler analyzer config (the src/WiseOwl.Cobol.Runtime/.editorconfig shape: a header that states the reason), with nullable reference types as the stated reason. Add no ThrowIfNull guards. Whether these model types should be internal is a separate visibility question, not part of this rule.
