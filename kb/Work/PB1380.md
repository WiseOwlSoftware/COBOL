## Landed 2026-09-27 (wave 66, group L)

**Re-probed on the wave-66 worktree build first** (the refuter's `refute-rmzl/q4.cob`, under `>>TURN EC-BOUND-REF-MOD CHECKING ON`): BEFORE, `MOVE RN(2:3) TO T` gave `GGGHHH`, `RN(1:N)` / `RN(1:L)` / `R1(1:N)` raised nothing, and `MOVE "Z" TO RN(2:N)` left `G = "Z     III"`. The defect reproduced exactly as registered, and it was WIDER than registered: the no-THROUGH alias (`R1(1:N)`, forwarded to data-name-2's place) dropped its modifier too, and so did the §8.4.3.3.3 SR1 screen — `66 RB RENAMES GB` over a `PIC 9(4) COMP` item compiled `RB(1:2)` clean.

**Root cause.** `ReferenceResolver.ResolveImplCore` composed a level-66 entry in an arm of its own that RETURNED before the shared tail (the SR1 screen `RefModExclusion`, then `RefModView`). That arm was also the only place a RENAMES place could be built at all, so the by-item entries — `ResolveItem`, `ResolveItemRefMod` (the report CONTROL clause's data-division ref-mod), `ResolveByName` (which excluded `Renames: null` in so many words) — built none. The two-arm dispatch: the syntactic arm handled RENAMES but skipped the tail; the by-item arm had the tail but no RENAMES.

**Fix.** The RENAMES composition moved INTO `PlaceForItem`, the ONE item→place builder (`PlaceForRenames`, with `SpanLeafPlace` folding the two copies of the leaf-cell character-form test into one). `ResolveImplCore` now has no RENAMES arm: every named item builds its place the same way and meets the same ref-mod tail. identifier-1's DESCRIPTION for SR1 and the view is the PLACE's item (`inner.Item`) on all three ref-mod entries (the syntactic path, `ResolveItemRefMod`, `RefModOf`) — the THROUGH alias itself (an alphanumeric group, §13.18.45.4 GR2) or data-name-2 for the no-THROUGH form (GR1). `PlaceForItem`'s failure out-parameter became `PlaceGap(Deferred, Refused)` so a refused declaration BEHIND an alias (a spanned leaf, or data-name-2) is still named in COBOLNET2364 rather than the alias. `RenamesPlaceBuilderDriftTests` pins the shape: the resolver reads the RENAMES descriptor at one code line (the `PlaceForRenames` dispatch) and a `RenamesPlace` is constructed at one site.

**Citation correction.** The adjudication's "§8.4.3.3.2 SR1" for "an alphanumeric group item" is mis-numbered: `cite.py --check 8.4.3.3.2 "an alphanumeric group item"` → FAIL; the admission list is §8.4.3.3.3 SR1 (`--check` → `OK §8.4.3.3.3 1)`). `spec_refs` corrected.
