# PB192 — LANDED — the DELETE FILE fixed-file-attribute definition

> ⚙ **Authority:** the owner protocol of 2026-08-30 ("confirm to what the other model COBOL implementations do")
> plus a survey that was **unanimous among the implementations that have the statement**. Plan item **D-E**.

## What was blocking `GR-14.9.10.4-19`

Both the adjudicator and the independent refuter reached the same place and stopped there: `FileRegistry.
DeleteFile` validates no attributes, and `docs/CONFORMANCE.md` §3 described that as *"Documented non-support
until a physical-attribute store exists"*. **A deferral is not a definition**, and §14.9.10.4 GR19 asks for a
definition —

> "The implementor shall define which of the fixed-file attributes are validated during the execution of the
> DELETE FILE statement. The validation of fixed-file attributes may vary depending on the organization or
> storage medium of the file."
> (`cite.py --check 14.9.10.4 …` → OK, GR19)

— which Annex A.1 item 50 makes both **required** and **required to be documented** (`cite.py --check A.1
"DELETE FILE statement (validation of fixed file attributes). This item is required."` → OK, A.1 50). Under D13
an adjudicator may not convert a deferral into a determination, so the row stayed a GAP.

## The decision

**The validated set is EMPTY, and uniformly so.** Not one of the §9.1.6 attributes is checked — organization,
prime or alternate record keys, SUPPRESS WHEN, code set, logical or physical record sizes, record type, key
collating sequence, record delimiter. GR19's second sentence *permits* the set to vary by organization or
medium; ours does not, and saying so explicitly matters: "uniformly empty" is a stronger and simpler thing for a
program to rely on than "empty for the cases anyone tried".

**This satisfies GR19 rather than waiving it.** The obligation is to define the set. Nothing in the rule requires
it to be non-empty, so an empty definition discharges it exactly as a non-empty one would.

**The consequence, written down so it is never re-derived as a defect:** GR18 sets '39' when the connector's
attributes and the physical file's fixed attributes do not match. With nothing validated there is nothing to
mismatch, so **'39' is unreachable from DELETE FILE by definition, not by omission**.

## What landed

- `docs/CONFORMANCE.md` **§7 gains the A.1 item-50 determination row**; `audit_annex_a1.py` now counts item 50
  discharged — **164 → 163** remaining obligations, §7 rows 38 → 39. The §7 preamble's own figures were stale by
  three (it still said "33 of the 199 … 166 remain", measured 2026-08-29) and are refreshed from the script's
  output, with a note that the script and not the paragraph is the count's owner.
- `docs/CONFORMANCE.md` **§3's '39' bullet is SPLIT**. It had collapsed two different cases into one deferral,
  which is what hid a conforming determination inside a gap: DELETE FILE is conforming-by-definition; **OPEN is a
  real unimplemented gap** and stays one.
- Verdict `GR-14.9.10.4-19` NEEDS-OWNER-DECISION → **CONFORMS**, test-ref `2023/delete_file_attribute_set_empty`.
  GAP 3657 → 3656.
- Golden `tests/conformance/2023/delete_file_attribute_set_empty.cob`: a DELETE FILE issued through a connector
  contradicting the physical file in **two** of the attributes §9.1.6 names as fixed — the organization ("the
  primary attribute") and the logical record size, 20 vs 40 bytes — must still delete, with GR20 a)'s '00'. The
  deletion is then shown to be real (GR14's successful '05' on the re-delete; §9.1.13.4's '35' on OPEN INPUT).
  Every expected status was derived from the rules before the program was run. **The golden was proven to
  discriminate before it was trusted**: with '39' substituted for the expected '00' the corpus runner goes red on
  that case by name.
