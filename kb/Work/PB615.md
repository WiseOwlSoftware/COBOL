# PB615 — LANDED — a missing adapter arm is indistinguishable from an omitted argument

Found 2026-09-05 by the `PB238` implementer (report §14 d), whose drift test
`CallAbiNumericCarrierDriftTests.ACarrierOutsideTheSix_DegradesToTheOmittedCarrier` was first written as
`Assert.ThrowsAny` on the strength of the file's doc comment and came out RED — the code does not fail loud.
Re-derived on this tree for this note.

## The rule

`cite.py --check 14.9.4.4 "If an OMITTED phrase is specified or a trailing argument is omitted, the omitted-argument
condition for that parameter evaluates to true in the called program."` → OK §14.9.4.4 11); `cite.py --check 14.9.4.4 "If a
parameter for which the omitted-argument condition is true is referenced in a called program, except as an argument or in the
omitted-argument condition, the EC-PROGRAM-ARG-OMITTED exception condition is set to exist."` → OK §14.9.4.4 12): GR11 and
GR12 define the meaning of an argument the CALL statement OMITS. An argument that
was supplied on a carrier the callee's adapter cannot read is not omitted; it is a conformance failure between
the argument and the formal (§14.8.2), and the standard's answer to that is a diagnosable nonconformance or an
EC-PROGRAM-ARG-MISMATCH condition, never a value.

## The mechanism

`src/Cobol.Net.Runtime/Control/CallAbi.cs#CobolArgAdapt` — each adapter's type switch ends in `Omitted<T>(i)`;
`Omitted<T>`'s read calls `RunUnit.Current.Exceptions.ProgramArgOmittedError(...)` and then `return default!`.
With `EC-PROGRAM-ARG-OMITTED` checking off (the default), the callee reads 0 (or an empty string) for a
supplied argument — a wrong answer with no signal. PB238's six-carrier numeric vocabulary makes this reachable
only for a carrier outside the six (its drift test proves it with `decimal`), but every future carrier
addition that misses one adapter arm lands here silently — the exact reason PB230 gave `NumParseImage` a
required argument.

## Fix shape

Split the two cases: `Omitted<T>` stays for a genuinely omitted argument (GR12), and a carrier the adapter
cannot read raises the ARG-MISMATCH condition when checking is enabled and FAILS LOUD (a runtime invariant
naming the carrier and the formal) when it is not — a supplied-but-unreadable argument is a compiler defect,
never a program state. Fix the doc comment to say what the code does. The drift test flips from
"degrades to the omitted carrier" to "fails loud", which is its intended reading.

## Landed — 2026-09-22 (wave 46 group K)

Re-probed: `CallAbiNumericCarrierDriftTests.ACarrierOutsideTheSix_DegradesToTheOmittedCarrier` still read ZERO
(green on the defect). Every `CobolArgAdapt` fallback that was `Omitted<T>(i)` for a PRESENT argument is now
`Unreadable<T>`, which throws `CobolCallException("EC-PROGRAM-ARG-MISMATCH")` marked `RaisedAtAdoption`
(§14.9.4.4 GR3 d): "the program call is not successful"). `ProgramTable.CallProgram`'s boundary CONSUMES that mark
instead of setting `ControlTransferred`, so this CALL's ON EXCEPTION runs (GR3 h) and an outer boundary still
marks it post-transfer (GR3 i). `Omitted<T>` is reached only for a genuinely omitted argument. The drift test is
now `ACarrierOutsideTheSix_FailsTheActivationWithArgMismatch`; golden `2002/pb615_unreadable_argument_carrier`
(a data-pointer BY CONTENT into a PIC 9(3) formal — §14.8.2.3.3 rule 1 length violation). The class doc no
longer claims the omitted carrier "fails loud on first reference".
⚠ DETERMINATION: the failure is raised whether or not EC-PROGRAM-ARG-MISMATCH checking is enabled — GR3 d)
makes the call unsuccessful regardless and only the EC's existence is gated; there is no value to proceed with.
