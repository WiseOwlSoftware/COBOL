# PB3473 — the planner takes prose ids for the report's notes

**Sites:** `scripts/orchestrator/plan_wave.py`, `scripts/orchestrator/test_plan_wave.py`

## What happens
`scripts/orchestrator/plan_wave.py` `parse_report` builds `Report.ids` as `PB.findall(text) + [lead]`, where `text`
is the report's whole HEADER (`header_lines`: every line above the first `## ` heading). A report header carries prose
as well as fields, so any note id it mentions becomes a note the report answers. The classifier then files that note
under the report's branch: a DONE report whose branch is not landed puts every such id in `awaiting` ("awaiting landing
(excluded; an `enqueue` unit first)"), and the note is not planned.

## Witness (wave 1135, 2026-10-20)
`E:\COBOL-coord\scratch\reports\w1134z-PB3465-report.md` opens with "Wave 1134's plan held PB3337 (the top of
`work.py next`), PB3460 and PB1278 on `.claude/settings.local.json` ..." above its first `##`. `plan_wave.py
--from-budget --borrow-days 6` printed

    awaiting landing (excluded; an `enqueue` unit first): fix-pb3465-never-work-paths-20261020: PB3337

and planned only PB3466. PB3337's own SPLIT branch, `worktree-wf_5b092cc6-8b9-1` (report `w1133a-PB3337-report.md`,
4 WIP commits), got no finisher, although the previous handoff named it as the wave's work. The PB3465 report's
"For the next implementer" section says the opposite: plan PB3337 once PB3465 lands. The hold ends by itself when
PB3465 lands (its class becomes landed), so the cost here is one wave's delay of the top-ranked note; a report on a
branch that stays unlanded would hold a mentioned note indefinitely.

## Root cause and the shape of the fix
The report's claimed notes come from free text. The notes a report answers are its LEAD plus the notes its dispatch
named (the dispatch ledger group's `notes`, or a structured header field), never every id the author mentions. The
sibling PB3084 is the same mechanism in `prune_worktrees.newest_report` (a branch name read from prose): both readers
should read only structured header fields, through one header-field reader, with a drift test that a prose mention
changes nothing. Sweep every other `PB.findall` over report text in `scripts/orchestrator/`.

## Landed (wave 1136 A, the finisher of w1135z; answers review finding R1-1)

**This note is PB3152's `awaiting` arm** (review R1-1, register duplicate): both are `plan_wave.plan()`'s `newest` loop
keying every open id on the newest report whose HEADER mentions it. The two are one mechanism and were fixed once, in
PB3152's shape, and both notes are closed by this landing. The "Root cause and the shape of the fix" section above
proposed a header-field reader shared with `prune_worktrees.newest_report`; that was wrong, and it is withdrawn: a note
id has no header field to read (the template's Status line carries none, and an agent that forgot one would silently
drop a note), while the dispatch ledger already records, mechanically, the notes every group was dispatched with.

- `plan_wave.Report.ids` is deleted; `Report.notes` replaces it, and `plan_wave.answered_notes(report, ledger_groups)`
  is its one definition: the report's lead (the id in its file name) plus the notes of the ledger group the report
  `answers` (the PB3311 predicate: its slug, written at or after the group's `at`). A report no ledger group knows
  (an attended branch's) answers its lead alone. `load_reports(reports_dir, coord_dir)` fills it; the planner passes
  its coordination directory, the branch survey and the landing checks read status and branch only and pass none.
- All three readers of the mention now read `Report.notes`: `plan()`'s `newest`, `attempts` (so a mention is
  no attempt in `choose_model`) and `classify_inflight` (a branch's notes are its newest report's `notes`).
  `inflight_file_sets` and `held_by_dispatch` already read `answers` (PB3311).
- A note a DONE branch closes beyond its dispatch (branch review R1-1: `PB3383 (+ PB925)`) is held in `awaiting
  landing` by the branch's own register: `plan_wave.closed_by_branch` lists the `kb/Work/PB*.md` the branch changed
  since `origin/main` whose version on the branch is `landed` or `retired` (the register rule: a fix flips its note in
  the commit that lands it), and `add_closed_notes` completes the `notes` of every report on an unlanded
  branch with them. The ledger alone would have released such a note to a second dispatch of finished work.
- Witnesses (`scripts/orchestrator/test_plan_wave.py`, section 6b'''0): a FINDINGS report and a CLEAN report whose
  HEADERS mention open notes (a mention in a `## ` body was always ignored) answer their leads alone, the mentioned
  notes are planned in their own clusters and are not `awaiting landing`, the FINDINGS finisher is planned under its
  lead, and a mention is no attempt. With the old reading the six checks go red. The two fixtures that relied on a
  header mention for a multi-note group ("PB12 NOT started") now record the group in a ledger, as a real dispatch does.
- Swept: no other reader of note ids in report text exists in `scripts/` (`landing_check.subject_ids` and
  `plan_wave.unlanded_branch_notes` read commit subjects). The sibling PB3084 (`prune_worktrees.newest_report` reads a
  BRANCH name from prose) is a different reader and stays open.
- Branch review round 2 (R2-1, R2-2): `add_closed_notes` completes the `notes` of EVERY report on an unlanded branch, SPLIT and FINDINGS ones too (a SPLIT finisher cherry-picks the branch's closed work, so those notes belong to its group, not to fresh cluster groups), and `plan()` plans ONE finisher per report: the closed notes can exceed the cap, and a chunk past it was a second agent on the same branch re-answering the same review findings. Witnesses: test_plan_wave.py section 6b'''00 (R2), three checks red on the round-1 head; the fake git of 6b'''00 now returns nothing for any range or pathspec but `origin/main...<branch> -- kb/Work` (R2-3).
