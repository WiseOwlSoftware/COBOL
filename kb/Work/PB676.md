# PB676 — OPEN — one rule, eighteen transcriptions

Found 2026-09-05 by the `PB326` implementer (report §"New defects" 1), which added the fifteenth to eighteenth
copies (EC-FLOW-REPORT, EC-REPORT-ACTIVE, EC-REPORT-INACTIVE, EC-REPORT-FILE-MODE) in the ESTABLISHED shape on
purpose — two shapes side by side in one file would have been worse than one repeated shape — and filed the
extraction here rather than doing a partial one.

## The shape

§14.6.13.1.1 (`cite.py --check 14.6.13.1.1 "no exception condition is raised"` → OK) is ONE rule: a checked
exception condition is raised only when checking is enabled for it. `src/Cobol.Net.Runtime/Exceptions/ExceptionState.cs`
transcribes it once per condition:

```
grep -n "public void .*Error(string detail)" -A 8 src/Cobol.Net.Runtime/Exceptions/ExceptionState.cs
```

fourteen pre-existing bodies plus PB326's four, each literally the five-line `if (<X>Checking) { Set(...); throw ...; }`
with the nonfatal twins (`DataConversionError`, `BoundOverflowError`) differing only in `fatal:` and the throw. No
wrong answer today; the harm is that the next copy is written by hand and a wrong `fatal:` or a missing `Set` is
invisible among its neighbours, and there is no drift test pairing each `…Error` helper with its `…Checking` flag
and its `CheckingFlags` field. Same family as [[PB655]] (a list where a structure belongs) and [[PB640]]'s
raise-site census.

## Fix

Extract `private void FatalIfEnabled(bool enabled, string ec, string detail)` (and a `NonfatalIfEnabled` sibling)
and reduce every helper to a one-line expression body — change the dispatch, not the callers. Pair it with a drift
test asserting that every `…Error` helper's EC name matches its `…Checking` property's `CheckingFlags` field, so
the pairing stays true when the nineteenth condition arrives. The static shim forwarders follow the same
extraction.
