# PB676 — LANDED — one rule, twenty-six transcriptions, now one method

Found 2026-09-05 by the `PB326` implementer (report §"New defects" 1), which added the fifteenth to eighteenth
copies (EC-FLOW-REPORT, EC-REPORT-ACTIVE, EC-REPORT-INACTIVE, EC-REPORT-FILE-MODE) in the ESTABLISHED shape on
purpose — two shapes side by side in one file would have been worse than one repeated shape — and filed the
extraction here rather than doing a partial one.

## The shape

§14.6.13.1.1 (`cite.py --check 14.6.13.1.1 "no exception condition is raised"` → OK) is ONE rule: a checked
exception condition is raised only when checking is enabled for it. `src/Cobol.Net.Runtime/Exceptions/ExceptionState.cs`
transcribes it once per condition:

```
grep -n "public void .*Error(string detail)" -A 8 src/Cobol.Net.Runtime/Exceptions/ExceptionState.cs
```

fourteen pre-existing bodies plus PB326's four, each literally the five-line `if (<X>Checking) { Set(...); throw ...; }`
with the nonfatal twins (`DataConversionError`, `BoundOverflowError`) differing only in `fatal:` and the throw. No
wrong answer today; the harm is that the next copy is written by hand and a wrong `fatal:` or a missing `Set` is
invisible among its neighbours, and there is no drift test pairing each `…Error` helper with its `…Checking` flag
and its `CheckingFlags` field. Same family as [[PB655]] (a list where a structure belongs) and [[PB640]]'s
raise-site census.

## Fix

Extract `private void FatalIfEnabled(bool enabled, string ec, string detail)` (and a `NonfatalIfEnabled` sibling)
and reduce every helper to a one-line expression body — change the dispatch, not the callers. Pair it with a drift
test asserting that every `…Error` helper's EC name matches its `…Checking` property's `CheckingFlags` field, so
the pairing stays true when the nineteenth condition arrives. The static shim forwarders follow the same
extraction.

## Landed — 2026-09-05

`ExceptionEngine.FatalIfEnabled(bool enabled, string ec, string detail)` and `NonfatalIfEnabled(bool enabled,
string ec)` state §14.6.13.1.1's raise rule ONCE (`cite.py --check 14.6.13.1.1 "if checking for an exception that
occurs is not enabled, no exception condition is raised"` → OK, and the sentence is verbatim at ISO_COBOL.md
:21345). All **26** gated raise sites in `ExceptionState.cs` are now one expression each — 21 identical fatal
`void …Error(string detail)` bodies, 2 nonfatal, plus `ArgumentError` (the fatal raise then §15.3's `return 0`),
`PerformVaryingIndexError` (GR3's own non-positive test folded into the gate argument) and `DataIncompatibleError`
(§14.7.6's CORRESPONDING latch first, then the rule). 1439 → 1323 lines. The static shim forwarders needed no
change: they were ALREADY one-line `=> E.X(detail)` delegations, with no copy of the rule in them.

**The count in the title is the filing count, not the measured one.** The note said eighteen; the census on
today's tree is 22 fatal transcriptions plus 2 nonfatal plus 2 special-cased, because the filing grep
(`public void .*Error(string detail)`) could not see `ArgumentError` (returns `long`) or
`PerformVaryingIndexError` (two parameters).

**The pairing is now checked, and it was checkable because the pair is already DECLARED.** `EcEmitter`'s
`FatalAmbientGates` / `NonfatalAmbientGates` say which `…Checking` flag the emitted statement guard sets for each
exception-name — so the (name, flag) pair was written down TWICE, once there and once by hand in each helper body,
with nothing comparing them. Both tables are now `internal` and `ExceptionRaiseHelperDriftTests` (new, three
facts) reads them:

1. **The pairing, behaviourally.** For every public `…Error` helper: what it raises with all flags on must be a
   name the emitter has a FLAGGED row for; with every flag on EXCEPT that row's flag it must raise NOTHING; with
   that flag alone it must raise exactly that name; and the fatality it records must be `ExceptionCatalog`'s
   Table 13 category (§14.6.13.1.3 vs §14.6.13.1.4). Behavioural, not name-matching, so a helper that raises the
   right name through a neighbour's flag cannot pass.
2. Every flagged gate row has a helper that reads it (EC-OO-UNIVERSAL excepted, for the reason the gate table
   itself gives: §14.9.23.4 GR7c's activator half is read by the callee's generated `__CobolInvoke`). This is the
   ambient-gate SLICE of the wider census [[PB349]] owns; the test says so and says to delete it when PB349 lands.
3. Every flag the emitter NAMES exists on the engine and on the static shim — the emitter writes
   `ExceptionState.{flag} = true;` as TEXT, so a renamed flag is not a build error here but a generated-C#
   compile error in whichever user program enables that one condition.

**The watchdog was fired RED twice before being trusted.** Mis-pairing `ReportInactiveError` to
`ReportActiveChecking` (the exact copy-paste this note describes) →
*"ReportInactiveError raised EC-REPORT-INACTIVE with ReportInactiveChecking OFF and every other flag ON — it is
gated by a NEIGHBOUR's checking flag"*. Giving `DataConversionError` a fatal raise →
*"DataConversionError raises EC-DATA-CONVERSION, which Table 13 categorizes Nonfatal, but it THREW a
CobolFatalException"*. Both restored.

**Byte-identical behaviour, proven.** The generated C# for an EC-bearing program (`>>TURN EC-BOUND-REF-MOD
EC-BOUND-SUBSCRIPT CHECKING ON`, a ref-mod and a subscripted MOVE) is IDENTICAL before and after, and so are the
stdout, the stderr and the exit code of a program that actually raises (`abnormal run-unit termination:
EC-BOUND-SUBSCRIPT (fatal): subscript 9 is outside 1..4`). No call site changed.

**Two exception-NAME drifts found in the prose beside the helpers, and fixed** — the same defect this note is
about, one level up: `CheckingFlags.PerformVarying`'s doc named "EC-PERFORM-VARYING" where the Table 13 name is
EC-RANGE-PERFORM-VARYING (§14.9.28.4 GR3), and `CheckingFlags.FloatOverflow`'s named "EC-SIZE-OVERFLOW" where the
condition it gates is EC-DATA-OVERFLOW (§14.9.25.4 GR6 d)4.a — "the algebraic value of the sending operand is
farther from zero than is permitted by the usage specifications of the receiving data item", verified with
`cite.py --find`). While correcting the second, `FloatOverflowError`'s claim that an arithmetic ±Inf is "a valid
§14.6.8.3 GR1 value" was re-derived: rule 1 governs FLOAT-SHORT/-LONG/-EXTENDED receivers and implementor-defined
conditions; it is rule 2 that sends a STANDARD floating-point conversion to ISO/IEC 60559, and what actually
excludes an arithmetic ±Inf is that GR6 d)4.a is MOVE-specific. Corrected in place.

**The OTHER arm, deliberately not changed.** Four runtime sites gate a nonfatal `Set` on an enablement passed as
a PARAMETER rather than an ambient flag (`CobolTiming.ContinueAfter` ×2 — `checkLessThanZero`;
`CobolDynString.SetSize` ×2 — `checkStorage`), because the emitter folds those at compile time and the site's own
control flow depends on whether it raised. The specific defect this note names — a helper mis-reading a
NEIGHBOUR's flag — cannot occur where there is no flag to confuse, so those sites keep their inline form; they
belong to [[PB640]]'s raise-site census, not here.

**Rows:** none. The note's `inventory_rows` is empty and no traceability row moves — this is a structural fix
with byte-identical behaviour, so no rule's verdict changes.

**Docs:** `docs/COBOLNET_CONDITIONS_EXCEPTIONS_DESIGN.md` gains the "THE RAISE RULE IS WRITTEN ONCE" bullet with
the five-declaration recipe for adding a condition; `CheckingFlags`'s own "adding a condition" paragraph, which
stopped at the flag, now names all five and both drift tests. **Diagnostic codes:** none used
(COBOLNET1862–COBOLNET1863 remain free).
