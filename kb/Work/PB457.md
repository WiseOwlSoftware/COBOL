# PB457 — a named CAPACITY register that no reference form can reach

**Row:** `SR-14.9.39.3-29` (SET Format 14 — *data-name-2 shall reference a data item defined in the CAPACITY
phrase of a dynamic-capacity-table format OCCURS clause*). Found by the b2 adjudicator `set-statement-p2`,
**re-measured here on the HEAD `cobol.exe` (base 89044aa0)**, not inherited from the 5fe593a0 pin.

## THE MECHANISM

The CAPACITY register is deliberately kept off the ordinary name table — `DataBinder.Odo.cs:268` says so in as
many words ("Kept off ByName/Roots — reachable ONLY through CapacityRegisters (the resolver hook)"), and the
register itself is minted at `DataBinder.Odo.cs:271-278` with `CobolName = spec.CapacityName` and a
`_capacityRegisters[capName] = item` entry at `:291`. The single hook that reads that dictionary is
`ReferenceResolver.cs:846-855`:

```csharp
return r.HasNoSuffix && r.BaseName is { } name
    && data.CapacityRegisters.TryGetValue(name, out var capTable)
    && capTable.OccursSpec?.CapacityRegister is { } capReg
    && BuildTablePath(capTable) is { } capPath
    ? new CapacityRegisterPlace(capPath, capReg) : null;
```

Two conjuncts, each of which silently deletes a legal reference form:

* **`r.HasNoSuffix`** is a test on the *parse* shape, not on subscripting. `dataReferenceSuffix` carries
  QUALIFICATION as well as subscripts, so `SET WS-CAP OF WS-TABLE TO 7.` fails it.
* **`BuildTablePath(capTable)`** (`ReferenceResolver.cs:882`, the zero-index overload of `:890`) returns `null`
  the moment any ancestor of the table is itself a table — it demands one index expression per enclosing table
  level and is handed none. So a dynamic table nested under a fixed or dynamic table has a *named* register
  that the hook can never build a place for.

Because the register is off `ByName`/`Roots`, failing the hook is not a fallback to a slower path: it is the
end of resolution, and the general resolver then emits `COBOLNET1639: '…' is not defined — no declaration in
this source element gives the name '…'`, which is simply false. **The register needs a real `Place` with a
subscript-carrying access path, not a bare-name dictionary lookup.**

⛔ **The adjudicator's premise on the subscripted form is WRONG and must not survive into the fix.** The finding
argued that `SET C2 (2) TO 4.` is the form "8.4.2.3 requires, since there is one such table per outer
occurrence". §13.18.38.3 SR31 forbids exactly that: *data-name-3 shall not be subscripted*. So the compiler's
**rejection** of the subscripted form is right in outcome; only its diagnostic is wrong (see below). What is
left after SR31 is that a bare or qualified reference is the ONLY legal form, and both are refused.

## EXPECTED vs OBSERVED — re-run on HEAD

Compiler: `src/Cobol.Net.Cli/bin/Debug/net10.0/cobol.exe` (base 89044aa0). Probes copied from the b2 scratchpad
into `scratchpad/probe-g8-set-b/set2/`.

```
$ cobol.exe sr29_flat_ok.cob --std 2023 --run            # control: 05 E … OCCURS DYNAMIC CAPACITY IN C0, SET C0 TO 4
CAP=[  4]                                                 # correct

$ cobol.exe sr29_qualified.cob --std 2023 --run          # 01 WS-TABLE. 05 WS-E … CAPACITY IN WS-CAP;  SET WS-CAP OF WS-TABLE TO 7.
sr29_qualified.cob(10,12): error COBOLNET1639: 'WS-CAPOFWS-TABLE' is not defined … 'WS-CAP' …

$ cobol.exe sr29_nested_in_fixed_bare.cob --std 2023 --run   # 05 OUT-E OCCURS 3. 10 IN-E … CAPACITY IN C2;  SET C2 TO 4.
sr29_nested_in_fixed_bare.cob(11,12): error COBOLNET1639: 'C2' is not defined …

$ cobol.exe sr29_nested_in_dynamic.cob --std 2023 --run      # dynamic inside dynamic: OUTER C1 works, inner C2 does not
sr29_nested_in_dynamic.cob(12,12): error COBOLNET1639: 'C2(2)' is not defined …

$ cobol.exe sr29_nested_in_fixed_sub.cob --std 2023 --run    # the SR31-illegal subscripted form
sr29_nested_in_fixed_sub.cob(11,12): error COBOLNET1639: 'C2(2)' is not defined …
```

**Expected.** `SET WS-CAP OF WS-TABLE TO 7.` is legal — §13.18.38.3 SR30 puts data-name-3 at the same level as
the OCCURS entry, so `WS-TABLE` is a valid qualifier, and §8.4.2.2.3 SR2 permits qualifying a name that does not
need it — so it shall set the capacity to 7 and print `CAP=[  7]`, as `sr29_flat_ok.cob` does for the bare form.
`SET C2 TO 4.` on a nested table is legal too (SR30 makes `C2` unique in the source element, and SR31 forbids
the subscripted alternative), so it shall change a capacity, not be rejected. Only the subscripted form shall be
rejected — and with an SR31 diagnostic, not with a false "not defined".

Note the same unreachability is not SET-specific: `MOVE C2 (2) TO ED` in the same probes fails identically,
which is why the repair belongs in the resolver and not in `SetBinder`.

## THE CODE SITE AND THE SHAPE OF THE REPAIR

| site | what it does | what is wrong |
| --- | --- | --- |
| `src/Cobol.Net.Compiler/Binding/DataBinder.Odo.cs:264-291` | mints the register, keeps it off `ByName`/`Roots`, files it under a flat `name → table` dictionary | the register has no *place*, only a name; qualification and nesting are unrepresentable |
| `src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs:846-855` `CapacityRegisterFor` | the sole lookup | `HasNoSuffix` rejects qualification; `BuildTablePath(capTable)` (zero-index) rejects every nested table |
| `src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs:890-909` `BuildTablePath(table, outerIndexExprs)` | already builds the indexed whole-table path | it EXISTS and takes outer index expressions — the hook just never supplies them |
| `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/SetBinder.cs:377-391` `DynTryBindSetCapacity` | the Format-14 selector | correct as written; it inherits the hook's blind spot |

⛔ **The repair is structural, not a loosened conjunct** (CLAUDE.md rule 5). A scalar `name → DataItem`
dictionary stands where a *symbol with an access path* belongs. The register is a real data item (SR30 says so:
"treated as though implicitly defined at the same level as the entry containing the OCCURS clause"), so:

1. Give the register a real entry in the ordinary symbol machinery — level, parent, and the qualification chain
   its declared level implies — so `WS-CAP OF WS-TABLE` resolves through the ONE resolver, not a side table.
   That deletes the `HasNoSuffix` conjunct instead of narrowing it.
2. Resolve the register's place with the **enclosing** tables' subscripts, using the two-argument
   `BuildTablePath` that already exists. §13.18.38.3 SR31 forbids the programmer from writing those subscripts,
   so where they come from is an OPEN SEMANTIC QUESTION the fixer must settle from the spec before coding: SR30
   places the register inside the outer table, yet SR31 forbids subscripting it. Adjudicate that pairing (and,
   if it is genuinely undecidable, record it as a determination) rather than picking a convenient answer — do
   NOT close the row on the nested case by guessing.
3. Replace `COBOLNET1639` for a subscripted register with a targeted SR31 diagnostic. Today the compiler is
   accidentally right for the wrong reason, which is the state in which a later "fix" turns it wrong.

## THE SIBLING SWEEP

* Every other reference to a CAPACITY register goes through the same hook: `MOVE`, arithmetic operands,
  `FUNCTION LENGTH` / `BYTE-LENGTH` over a variable-length group (`DataBinder.Odo.cs:262-267` names those as the
  register's other readers), `SEARCH` bounds, `INITIALIZE` of a dynamic table. Fix the hook, then re-probe each.
* The duplicate-name screen `COBOLNET1523` (`DataBinder.Odo.cs:283-289`, §13.18.38.3 SR30 first sentence) is
  what makes a name-keyed lookup safe in the flat case; once the register joins the ordinary symbol table, check
  that screen still fires and does not become a double diagnostic against the general duplicate-definition path.
* The unnamed-register path (`if (spec.CapacityName is not { } capName) continue;`, `DataBinder.Odo.cs:280`)
  must keep working — an unnamed register has no `CobolName` and must stay unreachable by name.
* Nested dynamic tables reach `BuildTablePath(table, outerIndexExprs)` from `table(ALL)` enumeration too
  (kb/Work PB62 is cited at `:885`); confirm that arm and this one end up on ONE path.

## ROWS

* `SR-14.9.39.3-29` — the verdict rests on the SELECTOR being complete, not on a screen: Format 14's three
  shapes are letter-for-letter Format 1's and Format 2's, so "is this receiver a CAPACITY register" is the only
  thing that can pick the format, and `DynTryBindSetCapacity` asks exactly that. Measured working for the flat
