# PB4703 — stored sign read-back misses a FOR-form string; the upper bound has no witness

**Sites:** `src/WiseOwl.Cobol.Runtime/Values/Numeric/CobolEdit.cs` (`CobolEdit.DeEdit`, `CobolEdit.Render` and `CobolEdit.Materialize` (the `placedBy` marker, was the bool `placed`), `CobolEdit.LandingZones`, `CobolEdit.LandedStringAt`, `CobolEdit.BlankLandingRun`, `CobolEdit.LandingZone`, all new), `tests/WiseOwl.Cobol.Tests.Unit/CobolEditStoredSignTests.cs` (`CobolEditStoredSignTests`), the goldens `conformance-suite/cases/13.18.40.5-Editing-rules/pb4703_deedit_for_floating_embedded_landing` and `pb4703-deedit-for-floating-embedded-at-85`, `docs/CONFORMANCE.md` (the embedded-landing determination), `docs/DATA_MODEL_DESIGN.md` (the `placedBy` paragraph)

Reported by the branch review, not probed. Copied from the PB4621 report:

R1-1: the read-back arm covers only a floating `+`/`-` string: a sign landed on an IS-form character-1 embedded in a FLOATING
character-1 (FOR) string is still not read, because `signStart`/`signEnd` stay -1 when the mask has no `+`/`-` string. Pre-existing and
not regressed by the PB4621 diff, in the sibling arm of the same condition; the review calls it low because the mask mixes a FOR and
an IS phrase in one picture, which SR12b (13.18.40.3) admits only on the reading PictureAnalyzer takes, and is rare.

R1-2: the upper bound `i < signEnd` has no witness: the past-the-string rows (`--9T9`, `++9T9`, golden E/F) pass with or without it,
because a 9 always sets `digitSeen` and the older `digitSeen` test already answers them. The only masks where a character-1 past the
string is reached with no digit read, those with a decimal point ending the string, have no row.

## Landing

Re-probed on a Debug build (probe `PIC LLTLL9 EDITING L FOR NEGATIVE IS "-" EDITING T IS ":"`): -555 formats as `  -555`
and de-edited to +555 (R1-1 reproduced), likewise `FOR NEGATIVE IS "("` (`  (555`). R1-2 holds as filed: removing
`i < signEnd` left every earlier test green.

The probe found the same root three more ways, fixed in the same change:

* `Render` marked a landing with `placed[i] = true`, and `Materialize` then wrote the string of the symbol AT that position.
  A floating string landing on an embedded simple insertion symbol therefore wrote the wrong symbol's string: a wide
  currency string was cut to its first character (`PIC $$B$$9`, CURRENCY SIGN IS "USD", 555 gave `    $555` and
  de-edited to 5), and a FOR literal landing on a wider IS-form character-1 lost the sign (`T IS "::"` gave `  ::555`
  for -555, which de-edits to +555). `placedBy[i]` now names the symbol whose string stands at the position;
  `Materialize` writes the landed text at the end of the embedded symbol's slot (docs/CONFORMANCE.md determination).
* `DeEdit` read a floating FOR string's blank negative text (a FOR phrase naming only POSITIVE, SR12c) at every suppressed
  position, so `PIC LLL9 EDITING L FOR POSITIVE IS "+"` holding +5 (`  +5`) de-edited to -5. A blank is no evidence at a
  position; the item is negative when the positive text never landed.
* `DeEdit` set `digitSeen` only at a `9`/`Z`/`*`/`+`/`-` digit position, not at a floating FOR or currency digit position.

R1-2: the witnesses are `--.T9`, `++.T9` and `--.T99` with `EDITING T IS "-"` (a decimal point ends the string, no digit
precedes T); mutation-checked: dropping `i < signEnd` fails three of the six rows.

* `DeEdit` matched a floating FOR string's blank text greedily at each suppressed position (width of the text, not one
  space), so a blank positive text wider than one (`FOR NEGATIVE IS "(("`, positive defaulted) put the walk out of step
  and 555 in `LLTLL9` de-edited to 55. A nonblank text is still matched per position; a blank wide landing is read as the
  string's whole suppressed prefix (`BlankLandingRun`).

For the next implementer: `CobolEdit#Materialize` is the one place a landed text is written (`placedBy[i]` names the
symbol, `LandedText(by)` its string); `CobolEdit#DeEdit` reads it back through `LandingZones`/`LandedStringAt`/
`BlankLandingRun`, all over `FloatingZone`; REUSE `FloatingZone`, never a second extent. Trap: `cobol.exe --run` loads the
Runtime assembly built last, and `dotnet test` of the Unit project rebuilds it (a mutation probe left the CLI wrong until
`dotnet build src/WiseOwl.Cobol.Cli`).

Branch review round 1 (two blocking findings, both fixed):

* R1-1: `BlankLandingRun` compared a nonblank landed text at the first nonspace character of the run, so a literal that
  begins with a space (`FOR NEGATIVE IS " -"`) never matched and the run was consumed as the blank landing (`LLL9` holding
  -5 de-edited to +5). `LandsAt` now compares the text at its own first nonspace character; unit rows
  `DeEdit_FloatingExtendedSignWithLeadingSpaceLiteral_RoundTrips` and golden lines J1-J5.
* R1-2: the floating `+`/`-` string wrote a sign landing on a wider embedded character-1 across the whole slot
  (`--T--9`, `T IS "::"`, -555 gave `  --555`). `Render` now records `placedBy` at those two placements, `Materialize` writes
  the one sign at the end of the slot (`LandedText(by, logical[i])`), and `DeEdit` reads the sign at `phys + w - 1`; unit
  rows `DeEdit_SignLandedOnEmbeddedWideCharacter1_RendersOneSignAtTheEndOfTheSlot` and golden lines K1-K4.
