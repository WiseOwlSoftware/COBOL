# PB2606 — an attended DONE branch does not trigger the land unit

Found by w1038v (PB2602). PB2602 makes the loop's land unit the ONE landing queue while the loop runs: the attended
session writes a DONE report under `<coord>\scratch\reports` instead of dispatching a lander, and `units/land.md` now
takes every branch `python scripts/prune_worktrees.py --brief` lists WAITING TO LAND. But nothing makes the loop RUN a
land unit for such a branch.

## Defect

Code site: `scripts/orchestrator/next_unit.py` `choose()` rule 6 (`done = [b["branch"] for b in
h.get("branches_pending", []) …]`, :135 on ea20c28e3): the only trigger for `land` is the previous handoff's
`branches_pending`, which a unit fills from its own fleet. An attended branch appears there only if a later unit
happens to classify it (a `resume` unit) — until then the next unit is `wave`, which neither lands it nor (with PB2607)
reliably holds its notes back.

Not fixed in w1038v: `next_unit.py` is being changed by the in-flight w1038t-loop-control (PB2596, the operator's
steering of the next unit), so a second edit of `choose()` would collide.

## Fix shape

Rule 6 also fires on the lifecycle survey: `land` when `prune_worktrees.survey` (no fetch) has a WAITING TO LAND row,
reason naming those branches; a `test_orchestrate.ps1` / next_unit self-test case with a DONE report under a private
coordination directory and no handoff entry.
