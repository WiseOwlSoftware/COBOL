Filed 2026-09-22 by REGISTRAR #10 from the wave-45 group-G lead (PB959 implementer report: "the witness-loss --check
(like every audit_*.py) runs only in build-local/battery, not in build-and-test.yml"). **Re-derived on main
`f503888da`, not inherited.**

## Measured

- `grep -n -i "audit_\|witness" .github/workflows/build-and-test.yml` → **nothing**. The only `python3` steps in the
  workflow are `scripts/filter_population.py` population guards.
- `grep -n -i "build-local\|audit\|work.py" scripts/push-main.sh` → only its own `--audit` flag (stale landing
  branches, PB950). The landing script runs no content gate. It waits for CI.
- `scripts/build-local.sh:37-39` and `build-local.ps1:24-28` run `audit_code_citations`, `audit_doc_citations` and
  `audit_evidence_supersession` with `--check`. PB959 (train 46) adds `audit_witness_loss --check` to the same place.
- `python scripts/spec/work.py check` is not a CI step either.

So the one mandatory, unforgeable gate on `main` (`ci-gate`, `enforce_admins: true`, owner decision Q23) enforces none
of these invariants. They hold only while every lander runs `build-local` voluntarily.

## Why it is not simply "add the steps"

CI checks out with `submodules: false` (build-and-test.yml lines 70/215/282/331, kb/Work PB159), because `specs/` is a
PRIVATE repository. Counting spec-text references per script: `audit_derivations` references the spec 0 times,
`audit_annex_a1` and `audit_doc_citations` once each, `audit_code_citations` 11 times. Some audits therefore need the
standard's text and cannot run in CI as configured. Others, including the witness-loss comparison (inventory vs its
own git history) and `work.py check` (the register's shape), need only the repository.

## What the owner of this note must do

1. Classify each `audit_*.py` / `--check` script as SPEC-FREE or SPEC-BOUND by running it with `specs/` absent, not
   by reading it.
2. Add every spec-free check to `build-and-test.yml` as a step of a job that `ci-gate` requires. Check that each one
   FAILS once in CI by pushing a deliberately narrowed inventory to a scratch `ci/` branch
   (`feedback_prove_the_watchdog_fails`).
3. For the spec-bound checks, give the owner the bare choice (one question): a CI secret or deploy key to fetch the
   private submodule, or a documented residual risk. Asking is the only step here that needs the owner.
4. Update plan §9 (verification commands) and the `gate` skill so they name which invariants CI enforces.
