# PB2879 — parallel Linux gate legs

Owner, 2026-10-09 ~10:50 PDT: "According to Task Manager, the WSL gate is only takes roughly 10% of the CPU", then
"Let's make this change now: Do it in such a way we lose as little as possibly if we hit the limit".

## Measured

- WSL sees 32 CPUs and 62 GB (`nproc`, `free -g`): the VM is not constrained.
- `scripts/linux-gate.sh` runs `for leg in "${wanted[@]}"` one leg at a time (selftests, unit, characterization,
  conformance, guard, selftests-built); each test leg runs its own `dotnet test` (with its own build). Alone, the gate
  took 351 s on 2026-10-09 (selftests 11 s, unit 84 s incl. 18 s build, characterization 8 s, conformance 63 s, guard
  69 s, selftests-built 38 s, plus clone and restore).

## Plan (checkpointed: each step is a pushed commit on branch `linux-gate-parallel`)

1. After the clone, build the solution ONCE (`dotnet build Cobol.Net.sln`), then start every requested leg in the
   background against that build (`--no-build` for the dotnet test legs), each writing its own log, and `wait` for all.
2. Keep each leg's verdict line, its log path and the ONE `=== LINUX GATE: GREEN|RED|NOT RUN ===` line exactly as
   today, so landers, briefs and check_practices.py need no change; a leg that cannot run is still NOT RUN, never a pass.
3. `--nice` and `--legs` keep working; a `--serial` flag keeps the old behaviour for diagnosis.
4. Measure: the new gate's wall time alone and concurrently with the Windows lander gate, recorded here and in L10.
