# PB245

**Row still claimed:** `RV-15.4.1-4`

There is no back-link from a landed fix to the inventory rows that record it. A Phase-B §15 batch's forensic
notes therefore went on describing a tree that no longer existed, and fourteen rows held the GAP open on
mechanisms seven landings had already closed. The rows were sent to a GOLDEN ROUND on 2026-09-09 — every rule
re-derived from `specs/ISO_COBOL.md` before anything was run, a spec-derived golden written for it, and the
golden run on a build of the tree — and **thirteen of the fourteen closed CONFORMS on real witnesses**. The
mechanism that let them rot is unchanged and is what keeps this note open.

## What the golden round settled

⛔ 'LOOKS CLOSED' WAS NOT ACCEPTED AS A VERDICT. Each row's expected value came from the clause first; nine new
positive goldens and negatives were written and measured (`tests/conformance/2002|2014|2023/l1_*`,
`tests/conformance/negative/l1-*`), and every observed value matched the derivation.

- `AR-15.40.3-5` · `AR-15.40.3-6` — FORMATTED-DATETIME's argument-4 magnitude bound and its format screen
  (PB11): the run-time `CobolDate.OffsetOutOfRange` guard and the bind-time COBOLNET1633 screen driven by
  `DateTimeFormatGrammar`'s zone classifier.
- `AR-15.43.3-2` — HIGHEST-ALGEBRAIC's standard-binary usage bar (R10 + PB122): the mode is read, the
  §3.166/§3.167 families come from `UsageFamilies`, and the diagnostic states the rule it enforces.
- `AR-15.67.3-4` · `AR-15.68.3-7` · `AR-15.69.3-3` — the NUMVAL-family standard-decimal digit cap (PB33/PB34):
  one table (`ArithmeticModes.NumvalDigitCap`) reaching every producer and validator on both lanes. The
  standard-binary half of each rule is unreachable by PB198's documented §4.2.6 decline of the mode.
- `RV-15.83.4-2` — SMALLEST-ALGEBRAIC's returned value on a float carrier (PB122), now pinned to a window one
  unit wide in the twentieth significant digit rather than the three digits the prior witness carried.
- `AR-15.95.3-1` — TEST-NUMVAL-F's class screen (PB124 wave 5): class ALPHABETIC is expressible and excluded,
  and the admit side (numeric-edited, group, national) is fixtured so closing the hole cannot over-reject.
- `RV-15.96.4-1` · `RV-15.96.4-2` — TRIM LEADING and TRAILING with two or more argument-2 (PB117): the
  sequential fold, measured against the set-union answer on order-carrying pairs. No fixture had pinned the
  TRAILING shape with multiple argument-2 at all.
- `AR-15.100.3-3` · `AR-15.100.3-6` · `RV-15.100.4-1` — YEAR-TO-YYYY's argument-2 default, its sum window and
  maximum-year, pinned by evaluating the standard's own equivalent arithmetic expression at run time. The rows'
  recorded residue was the float carrier: PB119 fixed the overload split (measured correct under `--permissive`)
  and PB248 made a floating-point item at a §15.3 type-6 position a bind-time rejection, so conforming source
  cannot reach that lane at all.

⚠ `RV-15.4.1-4` DID NOT CLOSE, and it is the row this note still claims. Two of its three recorded costs are
dead (PB125 landed FACTORIAL's standard-decimal EAE arm; PB198 recorded the standard-binary decline). The third
survives: half A — §15.4.1 NOTE 1 item 4, 'The result is explicitly implementor-defined' — has no located code
and no test. The round narrowed what closing it needs and corrected the row's own list of instances: NOTE 1
scopes item 4 to *the result of an equivalent arithmetic expression*, and §15.75 (RANDOM), §15.80
(SECONDS-PAST-MIDNIGHT) and §15.38 (FORMATTED-CURRENT-DATE) carry no equivalent arithmetic expression, so three
of the four functions the row named are the wrong functions for this rule. E (§15.27.3 r1) and PI (§15.73.3 r1)
do make the NATIVE returned value an implementor-defined approximation of a stated expression, but NOTE 1 item 1
already covers native arithmetic, so they cannot discharge item 4 either. What is owed is an enumeration of the
functions that have an EAE **and** whose returned value the standard makes explicitly implementor-defined under
a STANDARD mode — the set item 4 and its normative twin (the lead-in's rule 2 c) actually govern — and that is
not an agent's to assume.

## Mechanism

`tests/version-matrix/traceability-inventory.json` is the ONLY record of these defects, and the landing loop (a
`kb/Work/` note flipped to `status: landed` + a DEVLOG entry + `scripts/spec/record_verdicts.py`) has NO step
that re-verdicts the rows a fix closes. The rows' notes carry located `file:line` evidence, which is exactly
what goes stale silently: every one of the fourteen was re-measured at HEAD against its OWN located claim and
the claim was false. The consequence is measurable and directional — the GAP denominator counted closed work as
open, and `work.py next` ranked the campaign on it. Thirteen rows is the size of the error in ONE clause family.

## Fix shape

A `closes-rows:` field in the `kb/Work` frontmatter (or a mechanical `code-location` → landing cross-check),
plus a CI check that a note flipping to `status: landed` either names the inventory rows it closes or asserts it
closes none — so the back-link exists as DATA rather than as a habit. That is the same 'selected, not listed'
discipline PB198 used for the standard-binary predicate.

⚠ SCOPE HONESTY: this note measured ONE clause family (the §15 rows in one reviewer's slice). The same batch
adjudicated §8.8.1 and §14.9.1–14.9.12; the population elsewhere is unmeasured and the sweep is part of the
work.

## 2026-09-19 — the surviving row closed; the mechanism did not (wave 40, §15 intrinsic residues)

`RV-15.4.1-4` is CONFORMS and has LEFT this note's `inventory_rows`, on the one thing the golden round said was
owed: **the enumeration**, done MECHANICALLY over §15 rather than from recall. NOTE 1's own lead-in scopes item
4 to *the result of an equivalent arithmetic expression*, so it reaches only functions that HAVE one, and the
clauses containing "The equivalent arithmetic expression is as follows" are exactly fourteen — §15.7 ABS,
§15.9 ANNUITY, §15.17 COMBINED-DATETIME, §15.23 DATE-TO-YYYYMMDD, §15.25 DAY-TO-YYYYDDD, §15.36 FACTORIAL,
§15.60 MEAN, §15.74 PRESENT-VALUE, §15.79 SECONDS-FROM-FORMATTED-TIME, §15.81 SIGN, §15.86 STANDARD-DEVIATION,
§15.88 SUM, §15.98 VARIANCE, §15.100 YEAR-TO-YYYY. **Not one of those fourteen function clauses contains
"implementor-defined", "implementor defines" or "defined by the implementor" anywhere in it**, so item 4's
antecedent is false for every equivalent arithmetic expression THE STANDARD defines — unpopulatable before it is
ever an implementation question, which makes §1(c)'s covering test unmeetable rather than unwritten. The row
closes as a §1.1 derivation on the `unpopulatable-antecedent` arm, `docs/CONFORMANCE.md` §8
`DRV-RV-15.4.1-4`, whose Names cell carries the enumeration itself so the argument can be re-checked rather
than believed. The `conformance:2023/exp_standard_decimal_eae` test-ref is cleared from the row: it is evidence
about rule 1's "shall equal" obligation, which is `RV-15.4.1-1`'s. With it, §15 stands at **zero GAP** (557
rows, 0 non-OK).

## 2026-09-20 — LANDED: the back-link is DATA, and both halves of it are gates

The owner's 2026-09-19 decision is implemented whole, and this note's own subject — the MECHANISM — is what
changed.

**The field.** `closes_rows:` on a `kb/Work/` note names the traceability-inventory rows that note's landing
CLOSED. It is the twin of `inventory_rows` and deliberately not the same field: `inventory_rows` is the CLAIM a
note makes while it is open, and it EMPTIES as its rows are re-verdicted, so at the moment a note landed the
link disappeared. A landing that closed no row writes `closes_rows: []` **and** a `closes_rows_reason:`
sentence, because the silence is what this note is about. ⚙ Spelled with an underscore, not the decision's
`closes-rows`: every multiword key in this frontmatter is snake_case (`inventory_rows`, `blocked_by`,
`spec_refs`), and `kb/Work.base` addresses a property as `note.<key>` — where a hyphen would at best need
quoting and at worst read as an operator. The decision's spelling is the concept's name, not the key's.

**The gate** is `ClosesRowsBackLinkDriftTests` (`tests/Cobol.Net.Tests.Unit`, beside
`DefectiveRowCoverageDriftTests`), and it is two invariants, one per arm of the decision: a landed `kind: defect`
note states what it closed (rows, or a reason that is a sentence rather than a token), and every row any note
names as closed is one the inventory still counts as OK — its computed `state`, not merely a resolving
verdict: a CONFORMS row whose covering test is missing is still GAP, and the GAP is the number this note
is about — the row a landing claimed but never re-verdicted is the
exact event this note measured. ⛔ Both arms were proved RED on the live register before either was believed:
stripping `kb/Work/PB205`'s field named that file and quoted the fix; adding the still-PARTIAL
`SR-13.18.60.3-4` to it produced *"closes_rows names 'SR-13.18.60.3-4', whose verdict is 'PARTIAL' — that row is
NOT closed"*. Both were restored and the four cases are green.

**The back-fill is DERIVED, not asserted.** `scripts/spec/backfill_closes_rows.py` walks the inventory's own
commit history — 257 commits — and treats a row that moved from a non-resolving verdict (or none) to a resolving
one as a row that landing closed. 2,006 such transitions exist; 425 of them cannot be attributed to a single
note and are left unattributed rather than divided, because guessing would put a row on a note that did not
close it. The result: **1,972 row attributions across 485 notes**, filtered to rows that still resolve today so
a regressed row is never claimed as closed. The script is idempotent (a second run reported 484 kept, 1 added —
the one this session had stripped for the red-proof), insert-only, and byte-faithful, which matters because
`PB261` and `PB283` carry a stray lone CR that makes git treat them as binary: a normalizing writer showed a
200-line diff for a one-line change.

**The reader was repaired first, because the gate would have inherited its bug.** [[PB875]] — both readers of
this register failing OPEN on a WRAPPED list — is landed in the same change set. There is now ONE reader per
language (`scripts/spec/work.py parse_frontmatter`, `tests/_shared/WorkRegister.cs`), held to one another by
`tests/version-matrix/work-frontmatter-parity-cases.json` and by the C# gate RUNNING `work.py parity --json`
rather than assuming it. Measured over all 939 notes, old reader vs new: exactly ONE difference, `PB205`, whose
wrapped claim was read as 4 rows where it names 12 — and which the C# gate had been reading as none at all.

**⚠ THE SCOPE-HONESTY PARAGRAPH IS NOW MEASURED, and it is not zero.**
`python scripts/spec/backfill_closes_rows.py --suspects` counts the complement — rows still carrying a
non-resolving verdict whose forensic `notes` name a work note that has ALREADY reached a terminal status —
across the whole inventory rather than one clause family: **75 rows**. That is a MEASUREMENT, not a verdict and
not a gate: a landed note named in a row's prose is not proof the row is stale, which is exactly why the
register's enforced back-link runs NOTE→ROW. It is the aimed population for the next golden round, and it is
recorded here so the next one is aimed rather than sampled. Turning it into a gate would make the burn-down red
on 75 rows nobody has re-derived, which is a different decision and an owner's.

**What this does NOT do.** It does not re-verdict a single row, and the GAP is unchanged at 2,366. The back-fill
records what the history already says; the 75 suspects are the work it points at.
