# PB205

Found by the cluster-A review fleet (finding C11, as corrected by its refuters) and PROBED at the landing,
2026-08-31. Registered rather than fixed in that landing because the fix cascades past the CONTROL clause — see
"Why this is its own note" below.

## The rule

§13.18.16.3 SR4, verbatim (`cite.py --check` OK): **"Data-name-1 may be reference-modified. If it is,
leftmost-position and length shall be integer literals."** So a ref-modded CONTROL operand is EXPRESSLY LEGAL
source, and §13.18.16.4 GR3 then saves and compares *that slice* as the prior control value.

## Measured

```cobol
01 CX PIC X(6).
RD R-1
    CONTROL IS CX(1:3)
```

→ compiles clean and emits, at `--std 2023`:

```csharp
__RPT_0.AddControl(false, () => CX, __v => { CX = __v; });
```

The ref-mod is **gone**. The control break is taken on all six characters, so a report whose minor control is a
3-character prefix breaks on changes in positions 4–6 as well: a **silent wrong answer on legal source**, with no
diagnostic at any edition.

**Mechanism.** `DataBinder.Reports` binds each CONTROL operand with `var (b, q) = KeyReference(dref);`.
`KeyReference` (DataBinder.cs, the FILE-CONTROL key-reference helper) walks `dref.dataReferenceSuffix()` and keeps
ONLY `s.qualification()` — `subscriptPart` and `refModPart` are dropped on the floor. `ReportControlModel` then
carries a bare (name, qualifiers) pair, `LookupQualified` returns the whole `DataItem`, and
`ReportWriterEmitter` resolves it with `refs.ResolveItem(item)`, which has no ref-mod parameter.

**SR4's own restriction is therefore unscreened too**: `CONTROL IS CX(N:3)` with a data-name leftmost-position is
illegal ("shall be integer literals") and is accepted just as silently, because the ref-mod never reaches the
binder at all.

## Why this is its own note (the measured cascade)

The fix is NOT one line. It needs, in order:

1. `ReportControlModel` to carry the ref-mod (two `int?`s — SR4 makes them compile-time literals, so they need no
   expression machinery).
2. The capture site to read `refModPart`'s integer literals, and an SR4 arm rejecting a non-literal one
   (COBOLNET1699's descriptor already lists §13.18.16.3 rules and would extend to SR3/SR4/SR5/SR7).
3. The emitter to wrap the resolved place in a `RefModPlace` — and here is the cascade: the ref-mod SUBSTRATE
   wrap (`GroupImagePlace` / `BitImagePlace` / `NumericImagePlace`, plus the §8.4.3.3.3 SR1 `RefModExclusion`
   screen) lives INSIDE `ReferenceResolver`'s parse-context-keyed ref-mod path. A data-division caller cannot
   reach it without factoring that wrap out into a `ResolveItemRefMod(item, start, length)` entry. Spelling the
   wrap a second time at the CONTROL site is the copy this repo's one-rule-one-place law forbids, so the
   refactor IS the fix.

The CALL-boundary half of the cascade was ALREADY REPAIRED in the cluster-A landing, because that landing
regressed it and the twin-arm check caught it: `CallEmitter.CallStringRead` / `CallStringWrite` now carry an
explicit `RefModPlace` arm each (§8.4.3.3.4 GR6 — the ref-mod result is an elementary item over the slice), so
`CALL "S" USING G(1:3)` round-trips instead of failing backend compilation with CS1061. That means step 3's
DOWNSTREAM consumer is ready; what remains is steps 1, 2 and the resolver factoring.

## Carried-forward debt in the same clause (recorded here, NOT as a new list)

The §13.18.16.3 screen implements SR3, SR5, SR7 and — since the cluster-A landing — the §13.18.60.3 SR10 INDEX
rule as COBOLNET1700. Still unscreened, all PRE-EXISTING and all belonging to the P14 Step-0b SR census:

- **SR2** — "Data-name-1 shall not be defined in the report section." Caught only as a SIDE EFFECT: report-section
  names are never entered into `ByName`, so such an operand fails resolution and draws
  COBOLNET-report-control-operand-unresolved (§8.4.2.1) instead of SR2's own rejection. Right verdict, wrong rule,
  and it would silently change meaning the day report-section names join `ByName`.
- **SR4's integer-literal restriction** — see above; blocked on the same threading.
- **SR6** — "Data-name-1 shall be unique in any given CONTROL clause." No screen anywhere; a duplicated operand
  builds two control levels over one item.
- **§13.18.16.4 GR6** — a fourth shape rule on the same operand, unscreened.

A witness for each belongs with the fix.

## Landed 2026-09-04

The fix is the one the cascade above predicted, and the re-probe on the landing tree found the mechanism BIGGER
than the note described: the dropped ref-mod is not one clause's defect but ONE MECHANISM WITH THREE ARMS, and
the note had seen only the first.

**The rule, re-derived.** A CONTROL-clause operand is a WRITTEN REFERENCE, and three clauses write one:
13.18.16.3 SR4 (the CONTROL clause), 13.18.57.3 SR10 (a TYPE CH/CF operand) and 13.18.54.3 SR8 (SUM ... RESET
ON). All three say the same two things in the same words - the operand may be qualified and reference-modified,
and if it is, "leftmost-position and length shall be integer literals" - and the latter two then ask the same
question of it: SR10's "shall be the same as one of the operands of the CONTROL clause of the corresponding
report description entry", SR8's "shall be an operand of the CONTROL clause of the current report description".
That identity has to be over the WRITTEN reference, because 13.18.16.3 SR6's second sentence lets two operands
"refer to the same physical data item or to overlapping data items" - the referenced item cannot be what
distinguishes them. Every clause OUTSIDE this family reads the other way: 8.4.3.3.3's NOTE says "where
data-name-n is used in a general format or syntax rule, then reference-modification is not permitted", which is
exactly why SR4/SR8/SR10 have to permit it expressly, and it bounds the sweep.

**Measured before, on this tree.** `CONTROL IS CX(1:3)` over `PIC X(6)` compiled clean and broke on all six
characters. Worse, with two slices of one item - `CONTROLS ARE CX(1:3) CX(4:3)`, the shape SR6 expressly permits
- `TYPE CF CX(4:3)` and `TYPE CF CX(1:3)` BOTH matched control level 0 by name: the minor footing never printed
at all, and every GENERATE broke. `CONTROL IS CX(WS-N:3)` (SR4's own restriction) was accepted silently, because
the ref-mod never reached the binder to be screened.

**The shape of the fix.** `ReferenceResolver.RefModView` is factored out of the parse-context-keyed path as THE
ONE ref-mod view builder (the 8.4.3.3.3 SR1 exclusion, the group / numeric image substrate wrap, the
`RefModPlace`), and `ResolveItemRefMod(item, start, length)` reaches it BY ITEM - which is what a data-division
clause needs and could not previously get. `ReferenceResolver.ReadOperandSuffixes` reads an operand's suffixes
lexically, owning the two-carrier knowledge (the DEFAULT-mode `refModPart` and the SUBSCRIPT-mode captured group)
so no clause re-derives it; SR4's integer-literal restriction makes the read purely lexical. In the binder,
`ReportControlRef` (name + qualifiers + ref-mod literals) is captured by ONE helper, `ControlOperandRef`, for all
three clauses, and `ControlLevelOf` is the ONE "same as one of the operands" comparison. The emitter resolves a
ref-modded operand through `ResolveItemRefMod`, so 13.18.16.4 GR3's prior control is the 8.4.3.3.4 GR5 unique
data item - the slice.

**The carried-forward debt in this clause is closed with it**: SR2 has its own arm (it was rejected under
8.4.2.1 as an unresolved name - a real clause answering a different question - and the report-section-exclusive
name set is now shared with the 13.15.3 SR16 scan rather than built twice); SR4's integer-literal restriction and
SR6's uniqueness are screened; a SUBSCRIPT is rejected on the spelling, since SR3 bars the OCCURS case and
8.4.2.3.3 SR2 the other. 13.18.16.4 GR6 (a zero-length group operand) is NOT closed: every 8.5.4 form a CONTROL
operand could take is already rejected at compile time by SR5 (an occurs-depending table subordinate) or SR7 (a
variable-length group), except a variable-length logical record whose runtime length is zero - a runtime state
with no exception condition named for it. That is a derivation, and a derivation is the owner's signature to
give (design doc 1.1 / kb/Work PB386), so the row stays GAP with the argument recorded here.

Diagnostics: no new code. The rejections ride COBOLNET1699 (whose descriptor now lists SR2 / SR3 + 8.4.2.3.3
SR2 / SR4 / SR5 / SR6 / SR7), COBOLNET1630 (a second ref-mod, 8.4.3.3.3 SR3), COBOLNET1647 (the SR1 exclusion,
through the one `RefModExclusion` reader) and the two existing report-control descriptors for SR10 and SR8.
