**Zero diagnostics.** Both keys are category NUMERIC, both are inside the record description, and both rules say

operand the standard forbids as a key.

## What the standard prints — and the second obligation the screen never reaches

Both twins re-derived with `cite.py --check`:

- `--check 12.4.5.12.3 "of category alphanumeric or category national within a record description entry"` →
  **OK §12.4.5.12.3 2)** — *"Data-name-1 and data-name-2 shall reference a data item of category alphanumeric or
  category national within a record description entry associated with the file-name specified in this file
  control entry."*
- `--check 12.4.5.6.3 "within a record description entry associated with the file-name to which the ALTERNATE
  RECORD KEY clause is subordinate"` → **OK §12.4.5.6.3 2)** — *"Data-name-1 and data-name-2 shall be defined as
  a data item of category alphanumeric or national within a record description entry associated with the
  file-name to which the ALTERNATE RECORD KEY clause is subordinate."*

Each sentence states **two** obligations joined by "within": a CATEGORY (alphanumeric or national) and a
LOCATION (inside a record description of this file). The register's own lesson applies —
`feedback_model_the_rule_shape_not_one_case`: a rule read as one predicate gets one screen, and the arm nobody
noticed is the one that ships. Neither arm has a site today (see below), and the category arm has none even in
PB699's in-flight fix.

The category test is not a bare `PicCategory.Alphanumeric` comparison: `--check 13.18.29.4 "an alphanumeric group
item"` → **OK §13.18.29.4 3)** — *"If a GROUP-USAGE clause is not specified or implied for a group item that is
not strongly typed and is not a variable-length group, that group item is an alphanumeric group item"* — so a
plain group key is legal and a `GROUP-USAGE NATIONAL` group is legal, while alphabetic, numeric, edited, boolean
and the PICTURE-less usages are not. `DataBinder.IsAlphanumericDataItem`
(`src/Cobol.Net.Compiler/Binding/DataBinder.cs:1486-1487`) already encodes exactly that shape for §12.4.5.2 SR7
and is the precedent to reuse, widened by the national arm these two rules add.

## ⛔ The report's premise, corrected: the within-a-record arm is NOT screened on main

The report says *"`FileControlKeyRules` now screens the WITHIN-A-RECORD half for data-name-1"*. That is true of
PB699's **in-flight** change set and false of main, and the difference matters for whoever picks this up.
`DataBinder.ResolveFiles`, `DataBinder.cs:1417-1420`:

```csharp
DataItem? InRecords(string keyName, IReadOnlyList<string> quals) =>
    file.Records.Select(r => FindQualified(r, keyName, quals)).FirstOrDefault(x => x is not null)
    ?? (quals.Count == 0 && ByName.TryGetValue(keyName, out var l) && l.Count > 0 ? l[0] : null);
if (file.RecordKeyName is { } rk) file.RecordKeyItem = InRecords(rk, file.RecordKeyQualifiers);
```

The `??` arm is a **whole-program** name lookup: a RECORD KEY naming a WORKING-STORAGE item resolves silently,
which is the location arm of the same SR2 going unenforced. So on main SR2 has **no** enforcement site at all,
and PB699's landing closes half of it. This note owns the remaining half — the category arm — and both rows stay
GAP until it lands, which is why `inventory_rows` claims them here rather than on PB699
(`feedback_verdict_evidence_invariant`: a half-implemented rule must not collect a verdict).

## Where it belongs

`KeyedIoBinder.KeyedValidateFile` (`src/Cobol.Net.Compiler/Binding/Procedure/Verbs/KeyedIoBinder.cs:407`) holds
today's key-clause screens — §12.4.5.12.3 SR1 / §12.4.5.6.3 SR1's OCCURS ban and all three §12.4.5.13.3 rules for
RELATIVE KEY, one of which (`:434`, `rk.Pic is not { Category: PicCategory.Numeric, Scale: 0, Signed: false }`)
**is** a category screen. So the compiler already knows how to write this rule; it wrote it for the relative key
and not for the prime or alternate keys. That asymmetry inside one method is the whole defect in miniature.

⚠ `KeyedValidateFile` runs only on the first keyed VERB (PB699's subject), so a screen written there still would
not fire for an indexed file that is only OPENed and CLOSEd. The row belongs in `FileControlKeyRules` — PB699's
entry-time table (train 16 row 6, in flight; `FileControlKeyRules.cs` not on main yet) — for the same reason
PB742's does.

## The fix shape

**One row per clause in `FileControlKeyRules`, expressed as the RULE's two arms, not as two independent checks.**
Both rules have identical structure over three operands each (data-name-1 and data-name-2 — data-name-2 is the
SOURCE phrase's operand and is Annex A.3 item 40, not claimed, so data-name-1 is the live half today), and the
same structure recurs at §12.4.5.13.3 for RELATIVE KEY with a different category. Model the *rule*: a key clause
carries an operand, a required category set, and a required location — three columns — so adding the SOURCE
operand later, or a fourth key clause, is a row rather than a method (CLAUDE.md rule 5).

Diagnostic: `DiagnosticCatalog.FileKeyClauseRule` is the existing code for this family and the message should
name what the operand IS, the way `DataBinder.CategoryFace` (`DataBinder.cs:1491-1495`) already does for SR7 —
"a category-numeric item" — rather than restating the rule.

⛔ **Over-rejection sweep before landing.** A category screen newly REJECTS every program whose indexed key is
numeric, which is a real and common legacy shape. Run the GnuCOBOL differential and the external corpus
(`tests/external/gnucobol/tests/`) and count the newly-refused programs *before* the commit
(`feedback_survey_compilers_on_latitude` for what the other compilers do with a `PIC 9` key). ⚠ There is no
latitude to find: SR2 is a syntax rule, not an implementor choice — so a large hit population is a
strictness-axis decision to bring to the owner, never a reason to weaken the rule.

**Rows claimed:** `SR-12.4.5.12.3-2` and `SR-12.4.5.6.3-2`, both GAP. Closing this defect (with PB699's location
arm) is what earns them CONFORMS — neither may be recorded on the location arm alone.

## Sweep

- **§12.4.5.13.3 SR2's category screen is the live sibling** and is written as a positive `Pic` pattern; the two
  rules here need the *set* form (alphanumeric-or-national, group-or-elementary), which is why reusing
  `IsAlphanumericDataItem` beats copying the relative-key line.
- **The keys' other rules.** SR1 (no OCCURS) is enforced; SR2's two arms are this note plus PB699; the remaining
  §12.4.5.12.3 / §12.4.5.6.3 syntax rules should be read as a set and their sites listed before either lands, so
  a third dead member is not discovered the same way a year from now
  (`feedback_a_dead_lookup_is_also_unverified`).
- **The emitter's fallback.** PB699's report and `DataBinder.cs:1242-1250` both record that an unlocatable prime
  key used to reach a RUN-TIME abort; a compile-time category screen must not re-introduce a runtime arm — the
  diagnostic is the whole repair.
