## Finding — copy-statement-p1 (wrong-answer)

The COPY statement header is a forgiving hand scan, not a parse: ResolveOneCopy reads the name, an optional IN/OF qualifier, recognises REPLACING only as the IMMEDIATELY next word, and skips every other character to the next period. So the legal SUPPRESS PRINTING-then-REPLACING order silently loses the whole REPLACING phrase, and every malformed header (concatenation, national/numeric literal, figurative constant, junk words, missing BY, empty REPLACING, PRINTING without SUPPRESS) compiles without a diagnostic.

**Rows:** FMT-7.2.3.2, SR-7.2.3.3-4, SR-7.2.3.3-5

**Repro:**

```
BK1.cpy: '       01 AA-X PIC X(5) VALUE "HELLO".'  Program WORKING-STORAGE: '       COPY BK1 SUPPRESS PRINTING REPLACING ==AA-X== BY ==BB-Y==.'  PROCEDURE: 'DISPLAY BB-Y.' -> COBOLNET1639 'BB-Y' is not defined (the REPLACING phrase was discarded). Also: 'COPY "BK" & "1".', 'COPY N"BK1".', 'COPY SPACE.', 'COPY BK1 GARBAGE MORE.', 'COPY BK1 REPLACING.' all compile silently.
```

**Expected from the spec:** §7.2.3.2 general format places [SUPPRESS PRINTING] before the optional REPLACING phrase, so the first program must compile and DISPLAY BB-Y must print HELLO (as it does without SUPPRESS). §7.2.3.3 SR4 ('A concatenation expression or figurative constant shall not be specified for literal-1, or literal-2') and SR5 ('Literal-1 and literal-2 shall be alphanumeric literals') require the other headers to be rejected; words outside the general format are syntax errors.

**Observed:** p01 -> COBOLNET1639 BB-Y undefined (with both names declared the program would silently run the unreplaced library text); p02 (no SUPPRESS) -> HELLO. p05/p06/s04/s01/s02/s03/s06 all accepted with no diagnostic. Root cause: ResolveOneCopy lines 385-409 check MatchWord(REPLACING) only at the position after the qualifier and then `while (text[afterCopy] != '.') afterCopy++`. The fix is a real COPY-statement parse (all phrases in format order, anything else diagnosed), not a SUPPRESS special case.

**Code site:** src/Cobol.Net.Frontend/Preprocessor/CopyProcessor.cs#ResolveOneCopy (lines 378-409); #ReadTextNameOrLiteral

## Finding — copy-statement-p1 (under-rejects)

The placement rules for the COPY keyword are not checked: FindCopyKeyword accepts any non-word character before COPY, so a COPY that is not preceded by a space is expanded, and a COPY written inside another COPY statement's pseudo-text is spliced and then expanded as a nested COPY. The circularity check's comment also cites the wrong rule: it says SR1 where the rule is GR12.

**Rows:** SR-7.2.3.3-1, SR-7.2.3.3-2

**Repro:**

```
'       01 Q PIC X.COPY BK1.' -> compiles, HELLO. 'COPY BK1 REPLACING ==AA-X== BY ==COPY BK2.==.' (BK2.cpy: '01 ZZ-Z PIC X(3) VALUE "ZZZ".') -> no SR1 diagnostic; BK2 is expanded into the text (only an incidental parse error follows). 'COPY BK1 REPLACING ==AA-X== BY ==BB-Y COPY BK1==.' -> CBL3621 'Circular COPY', which is the wrong reason.
```

**Expected from the spec:** §7.2.3.3 SR1: 'a COPY statement shall not appear within a COPY statement'. SR2: 'A COPY statement shall be preceded by a space except when it is the first statement in a compilation group'. Both programs are to be rejected with a diagnostic that names the rule. CopyProcessor.cs:423's '§7.2.3.3 SR 1: a COPY shall not directly or indirectly include itself' should cite §7.2.3.4 GR12 ('shall not cause the processing of a COPY statement that directly or indirectly copies itself').

**Observed:** FindCopyKeyword boundBefore = !IsLetterOrDigit && not '-'/'_' (line 607), so '.', '(' and a closing quote all count. ResolveOneCopy never scans its own operands for a COPY word. The placement half of SR1 does work: q05 mid-statement COPY, q04 COPY inside a literal not expanded, q06 comment line skipped.

**Code site:** src/Cobol.Net.Frontend/Preprocessor/CopyProcessor.cs#FindCopyKeyword (line 607); #ResolveOneCopy (line 423 comment)

## Finding — copy-statement-p2 (wrong-answer)

COPY phrase parse is positional: ResolveOneCopy recognizes REPLACING only immediately after the text-name / OF-IN qualifier and never parses SUPPRESS [PRINTING]; the scan-to-period that follows discards a REPLACING phrase written after SUPPRESS (the general-format order) and stops at a '.' inside its pseudo-text

**Rows:** GR-7.2.3.4-8, GR-7.2.3.4-6

**Repro:**

```
p2book.cpy: `01 AAA-VAR PIC X(3) VALUE "AAA".`; main: `COPY p2book SUPPRESS PRINTING REPLACING ==AAA-VAR== BY ==BBB-VAR==.` then `DISPLAY BBB-VAR.` (E:/Temp/claude/E--CobolSharp/a700c052-f9e4-4942-84ff-a13c7505d6ec/scratchpad/adj-d2/out/probe/copy-p2/p2.cob; p2b.cob bare SUPPRESS; p13.cob with a period inside pseudo-text)
```

**Expected from the spec:** BBB-VAR is declared and the program displays AAA (§7.2.3.4 GR8: each matched occurrence of pseudo-text-1 is replaced; §7.2.3.2 places [SUPPRESS PRINTING] before REPLACING). p13 compiles, the COPY statement ending at the separator period after the closing ==  (GR6).

**Observed:** p2/p2b: error COBOLNET1639 'BBB-VAR' is not defined — the REPLACING phrase was silently dropped (a program that also declares AAA-VAR elsewhere / relies on the old name runs with the unreplaced text: wrong answer). p13: error COBOL0001 unexpected '=' — the raw `while text[afterCopy] != '.'` scan ended the statement at the period inside pseudo-text-1 (legal source rejected). GR10's nested-COPY check is skipped on the same path.

**Code site:** src/Cobol.Net.Frontend/Preprocessor/CopyProcessor.cs#ResolveOneCopy (lines 385-409: qualifier, then `MatchWord(text, afterCopy, "REPLACING")`, then the scan-to-period)

## Row GR-7.2.3.4-10 — PARTIAL (adjudicator + refuter record)

GR10: 'If the REPLACING phrase is specified, the library text shall not contain a COPY statement.' ResolveOneCopy reports COBOLNET1640 (Error) when replacements.Count > 0 and FindCopyKeyword finds a COPY in the normalized library text — the same scanner the expander splices by, so a COPY inside a literal or *> comment is not counted. Landed as kb/Work R34. Test ReplacingOverNestedCopy_DrawsGr10 asserts the error; FlatReplacing_StaysClean is the negative control. Edge note: when the REPLACING phrase follows SUPPRESS it is discarded (GR8 finding), so GR10 is then not checked either — same mechanism, not a separate defect. || REFUTED: PARTIAL — GR10 applies whenever the REPLACING phrase is specified. In the legal format COPY t SUPPRESS REPLACING ..., ResolveOneCopy never parses SUPPRESS. The REPLACING operands are skipped by the scan to the period, so replacements.Count==0 and COBOLNET1640 is never raised for a library that contains a COPY. The flat-REPLACING branch is verified; the SUPPRESS branch is not, so the verdict is PARTIAL. The unit test pins only the flat form.

**Code location:** src/Cobol.Net.Frontend/Preprocessor/CopyProcessor.cs#ResolveOneCopy; src/Cobol.Net.Editions/Diagnostics/DiagnosticCatalog.cs#CopyReplacingNestedCopy
