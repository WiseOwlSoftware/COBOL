# PB3870 — the gate self-test took iterdir's first entry as the run directory

**Sites:** `scripts/run_gate_legs.py#self_test`, `scripts/run_gate_legs.py#run_dirs`

## The defect

Three arms of `run_gate_legs.py --self-test` (the leg-1-only record, the failed timings publish, and ONE SHAPE) read a
gate's `verdict.json` from `next((root / <case> / "runs").iterdir())`. The run root holds the run directory AND the
`runs.lock` file `Gate.new_run` takes to number runs. `iterdir` order is the filesystem's: NTFS lists `000001-…` before
`runs.lock`, so Windows always passed; ext4 orders by name hash, and on CI's runner `runs.lock` came first, so the arm read
`runs.lock/verdict.json` and the self-test crashed. The merge-group run of PR #689 (PB3868, which does not touch this
script) failed on it.

## Why the local gates did not see it (the CI invariant)

The Windows gate lists NTFS in name order. The Linux half of the gate runs in a WSL clone on ext4, where the hash order of
these names happened to put the run directory first: six runs of main's version under WSL on 2026-10-27 all passed. The
order depends on the names, including the random temp directory, so neither local leg could be relied on to see it. The
fix removes the order dependence instead of chasing it.

## The fix

The three arms read the run through `run_dirs(run_root)`, the one listing of a run root's runs (run directories only,
matched by `RUN_DIR`, oldest first), which `Gate.new_run`, `previous_run` and `enqueue.tested_locally` already use; the
self-test had re-derived it as a raw `iterdir`. Sweep: no other `next(... iterdir())` exists under `scripts/` or the
harness; the remaining `iterdir` reads in tests sort their names or test for emptiness, and the self-test's other two
run-root reads (`plan-torn`, the prune fixture) keep only directories or build a fixture with no lock.
