# PB835 — OPEN — the LOCALE arm honours the separator's IDENTITY and never its group SIZES

Source: the `PB256` implementer report, "New defects found outside this mechanism" item A (the LOCALE arm is
PB64/PB250's mechanism, not PB256's).

## Repro — re-run on this tree

`scratchpad/reg4/probe/p01_locale_grouping.cob` (PROGRAM-ID `R4P01`), `--std 2023 --run`, with
`SPECIAL-NAMES. LOCALE FR IS "fr_FR".`:

```
T-0 1=000000        FUNCTION TEST-NUMVAL-C("0 1",   LOCALE FR) -> 0   (valid)
T-12 34=000000      FUNCTION TEST-NUMVAL-C("12 34", LOCALE FR) -> 0   (valid)
N-1 23 4=001234     FUNCTION NUMVAL-C("1 23 4",     LOCALE FR) -> 1234
```

`"0 1"`, `"12 34"` and `"1 23 4"` are all certified valid and valued. For `fr_FR` the `mon_thousands_sep`
resolves to a plain space in this runtime, which is why the shapes are accepted at all; what is never consulted
is `mon_grouping`, the list of group SIZES, so a separator may stand between any two digits.

## The rule, quoted

```
$ python scripts/spec/cite.py --check 15.68.3 "Argument-1 may contain one or more grouping separators in accordance with locale fields mon_thousands_sep and mon_grouping"
  OK  §15.68.3 5)  (Argument rules)
      6. Argument-1 may contain one or more grouping separators in accordance with locale fields mon_thousands_sep and mon_grouping.
```

The rule names **`mon_grouping`** — the group-size list — beside the separator string, and "in accordance with"
is the whole of the obligation. The non-locale arm (r4 a) is correctly unconstrained: its own format is
`digit [ , digit ] ...` with no size term, so the latitude there is not evidence for latitude here.

## Expected vs observed

Expected: `TEST-NUMVAL-C("0 1", LOCALE FR)` returns the position of the first offending character (a nonzero
value) because a single digit cannot be a `mon_grouping` group in the `fr_FR` convention; observed 0 (valid).
A program that screens input with the validator therefore accepts malformed data and values it — a silent wrong
answer downstream of the validator, not in it.

## Code site

`src/Cobol.Net.Runtime/Intrinsics/CobolIntrinsics.NumvalLocale.cs`, `TryLocTemplate`'s `LocTok.Num` arm. Its own
comment states the narrowing as a choice — *"separators by IDENTITY and flanking only (never group sizes)"* —
with no adjudication recorded anywhere against r5 b) 6's explicit `mon_grouping`.

## The decision this needs

Either `mon_grouping` is enforced (the group-size walk, right to left, with the trailing-element repetition rule
of the POSIX field), or the narrowing is an adjudicated determination and is written down in
`docs/CONFORMANCE.md` A.4.9 beside the other LOCALE determinations. Filing it as a defect rather than an
adjudication because the standard's sentence is not ambiguous: it names the field.

## Sibling sweep the fixer owes

* `NUMVAL-C` and `TEST-NUMVAL-C` share the template walk — fix once, and check both directions (the validator's
  position result and the valuer's digit accumulation).
* The same file's LC_NUMERIC twin (`grouping` rather than `mon_grouping`) if NUMVAL/TEST-NUMVAL ever take a
  LOCALE phrase.
* `docs/COBOLNET_LOCALE_DESIGN.md` records the L12 determinations — a determination added here belongs there.
