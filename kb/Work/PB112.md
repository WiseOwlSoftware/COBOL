# PB112 — LANDED 2026-08-19 (DEVLOG 1337) — LOCALE-TIME's separator byte varied by host ICU version

> ⚙ **flags:** wrong answer + silent in the cross-host sense — on any ONE host the output is self-consistent, but
> the SAME program prints U+0020 on Windows and U+202F on a new-ICU Linux, and nothing diagnoses it; found
> 2026-08-19 as **CI's Linux-only red** on `2014/pb64t4_locale_functions` (four consecutive runs since T4 —
> `b13d4383`, `94957acf`, `bd04ba7d`, `d54ddad2`; the Windows corpus-nist shard green throughout) · **landed
> 2026-08-19** in the commit that carries this note.

**Measured, not reasoned:** the xUnit assert message showed two IDENTICAL-looking strings (`…09 PM]…` vs
`…09 PM]…`, caret at pos 175); the PB108 TRX artifact carried the bytes — expected `U+0020`, actual `U+202F`
(NARROW NO-BREAK SPACE), the ICU 72 / CLDR 42 change to en-US's standard time formats. Windows' bundled ICU
predates it; the GitHub Ubuntu runners' does not. WSL could not reproduce (its distro ICU is older — plain
space), so the failing-direction proof is CI itself plus the synthetic-pattern unit pin.

**Root cause:** DETERMINATION L10 reads `d_fmt`/`t_fmt` from the host culture's
`ShortDatePattern`/`LongTimePattern` verbatim — including whatever SPACING characters that host's ICU vintage puts
inside them. The project's own collation precedent (owner decision Q4: our own derived CLDR tables, "so the order
is identical on every host") names host-ICU variance as the disease; LC_TIME had it.

**Fix (the L10 addendum, documented in CONFORMANCE.md §4 item 5's T4 block):** `LocaleFacts.NormalizeSpacing` —
U+202F and U+2009 inside the date/time PATTERNS normalize to the plain space, applied in the `DateFormat` /
`TimeFormat` getters (the ONE place a CultureInfo is read; every consumer — LOCALE-DATE, LOCALE-TIME,
LOCALE-TIME-FROM-SECONDS — formats through them). Grounds: (1) host-stability — the separator inside a fixed
COBOL text field must not depend on where the program runs; (2) ISO 9945's own locale data (`t_fmt` `%r`) and
GnuCOBOL's strftime rendition both use the plain space ([[follow_gnucobol_on_split_latitude]]). Pinned by
`CobolLocaleTests.TimePatternSpacing_IsHostStable` (the normalizer on a synthetic U+202F pattern — host-independent;
`For("en-US").TimeFormat` free of U+202F/U+2009 on every host; the end-to-end `Time("130509","en-US") ==
"1:05:09 PM"` byte pin) and by the T4 golden itself, which is what CI's Linux corpus-nist shard runs.
