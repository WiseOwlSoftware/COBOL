# PB2605 — the DEVLOG-staged hook checks the main checkout's index for every commit

Found by the PB2599 sibling sweep (wave 1038 group U, 2026-10-08): every hook that asks "which tree does this command
act on?" was swept, and `scripts/hooks/devlog_staged.py` does not ask it at all.

## Defect

`scripts/hooks/devlog_staged.py:15` `REPO = pathlib.Path(__file__).resolve().parents[2]`, and `:33-37` run
`git diff --cached --name-only` with `cwd=str(REPO)`. The hook is registered as
`python "$CLAUDE_PROJECT_DIR/scripts/hooks/devlog_staged.py"` (`.claude/settings.json`, PreToolUse Bash), so REPO is
the session's project checkout (the main tree), whatever tree the `git commit` in the command runs in. A commit in a
worktree is therefore judged by the main tree's index: nothing is staged there, so the hook bails and is silent. The
rule it states ("every commit carries a DEVLOG.md entry") is checked only for commits made in the main checkout.

Repro: from `E:\COBOL` (nothing staged), stage a change without DEVLOG.md in any worktree `<wt>` and run
`echo '{"tool_input":{"command":"cd <wt> && git commit -m x"}}' | python scripts/hooks/devlog_staged.py` — no output
(no ask), although `<wt>`'s staged set lacks DEVLOG.md.

## Why it was not fixed with PB2599

The mechanical fix is one line of the shared parser (`shell_location.steps` + `git_dir`, exactly what
`status_guard.commit_dirs` does). But the hook's decision is `ask`, and implementer WIP checkpoint commits carry no
DEVLOG entry by design (the lander writes one entry per train, MANDATORY-PRACTICES L1), so following the commit would
put an `ask` in front of every implementer checkpoint: in an unattended `bypassPermissions` unit that is either a
silent pass or a stall. Which commits the DEVLOG rule covers (every commit, or only commits that land on main) is the
owner's decision; the hook should then check the commit's own tree and apply that scope.
