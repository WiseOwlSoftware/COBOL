# PB2605 — the DEVLOG-staged hook checks the main checkout's index for every commit

Found by the PB2599 sibling sweep (wave 1038 group U, 2026-10-08): every hook that asks "which tree does this command
act on?" was swept, and `scripts/hooks/devlog_staged.py` does not ask it at all.

## Defect

`scripts/hooks/devlog_staged.py:15` `REPO = pathlib.Path(__file__).resolve().parents[2]`, and `:33-37` run
`git diff --cached --name-only` with `cwd=str(REPO)`. The hook is registered as
`python "$CLAUDE_PROJECT_DIR/scripts/hooks/devlog_staged.py"` (`.claude/settings.json`, PreToolUse Bash), so REPO is
the session's project checkout (the main tree), whatever tree the `git commit` in the command runs in. A commit in a
worktree is therefore judged by the main tree's index: nothing is staged there, so the hook bails and is silent. The
rule it states ("every commit carries a DEVLOG.md entry") is checked only for commits made in the main checkout.

Repro: from `E:\COBOL` (nothing staged), stage a change without DEVLOG.md in any worktree `<wt>` and run
`echo '{"tool_input":{"command":"cd <wt> && git commit -m x"}}' | python scripts/hooks/devlog_staged.py` — no output
(no ask), although `<wt>`'s staged set lacks DEVLOG.md.

## Why it was not fixed with PB2599

The mechanical fix is one line of the shared parser (`shell_location.steps` + `git_dir`, exactly what
`status_guard.commit_dirs` does). But the hook's decision is `ask`, and implementer WIP checkpoint commits carry no
DEVLOG entry by design (the lander writes one entry per train, MANDATORY-PRACTICES L1), so following the commit would
put an `ask` in front of every implementer checkpoint: in an unattended `bypassPermissions` unit that is either a
silent pass or a stall. Which commits the DEVLOG rule covers (every commit, or only commits that land on main) is the
owner's decision; the hook should then check the commit's own tree and apply that scope.

## Owner decision (2026-10-08 ~07:45 PDT)

Asked through AskUserQuestion: "PB2605: does the DEVLOG-entry rule cover every commit, or only the commits that land
on main?" Answer, verbatim: **"Only commits landing on main"**.

## Landed (branch w1041q-devlog-scope, wave 1041 group Q)

**Re-probe (2026-10-08, base 7fb5cab75).** With a change staged in a worktree and nothing staged in `E:\COBOL`,
`echo '{"tool_input":{"command":"cd <wt> && git commit -m x"}}' | python E:/COBOL/scripts/hooks/devlog_staged.py`
printed nothing (exit 0): the defect reproduced.

**One mechanism, at the landing.** A commit cannot know whether it will land; a landing can, and every landing passes
`scripts/push-main.sh` (owner decision Q23, PB796). So `scripts/hooks/devlog_staged.py` moved (git mv) to
`scripts/orchestrator/landing_devlog.py` and became the landing check: it reads `DEVLOG.md` at the landing's base and
at its head (`git show <rev>:DEVLOG.md`, the range's own trees, never an index), and refuses unless the range adds at
least one `## Entry <id>` whose id is not already on main, each new heading carries the stamp
`## Entry NNN — YYYY-MM-DD HH:MM TZ — Title`, and the new entries sit at the TOP. A heading that reuses a number already
on main (a stale number after a rebase, L8) is not new. `push-main.sh` runs it right after its fast-forward check,
before the partition check and before a CI run is spent: exit 6 (new, in the header's exit list) on a refusal; an
unreadable range dies with exit 2, never a pass. The PreToolUse registration in `.claude/settings.json` is gone, so
no hook asks at an implementer's checkpoint (no ask, no stall in a bypassPermissions unit). There is no second copy
of the rule: the commit-time arm is deleted, not narrowed.

**Self-test** (`landing_devlog.py --self-test`, discovered by `scripts/self_tests.py`, so every gate and CI run it):
10 cases on real scratch repositories: a train of WIP checkpoints plus one top entry passes; no DEVLOG change, a
retitled existing heading, a reused number, an unstamped heading, an entry below an existing one, and a tree without
DEVLOG.md are refused; two new top entries pass; an unreadable revision is NOT RUN; and the PB2605 repro, per the
decision: a worktree commit with only code staged, in the `cd`, `git -C` and `Set-Location` shapes, is run through
EVERY PreToolUse hook `.claude/settings.json` registers for Bash and PowerShell and draws no DEVLOG ask from any of
them (and a registered hook script that does not exist is red). Proved to bite: a planted hook that follows the
commit's tree through `status_guard.commit_dirs` turned the case BAD (3 asks), and the stale `devlog_staged.py`
registration turned it BAD as "registered but missing".
