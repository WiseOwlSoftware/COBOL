# PB692 — LANDED — a file control entry rule with no home

Found 2026-09-05 by the `PB334` implementer (report §"New defects" 2): `grep -rn "12.4.5.5.2" --include=*.cs src/`
returns nothing but generated-parser noise, and the entry compiles.

## The rule

§12.4.5.5.2 SR2 (`cite.py --check 12.4.5.5.2 "The DYNAMIC and RANDOM phrases shall not be specified for a
sequential file"` → OK 2)). It is a rule about the FILE CONTROL ENTRY, so it cannot live on a verb: PB334 enforces
§14.9.30.3 SR6 on the sequential READ arm through the shared check precisely because `file.AccessMode == Random` is
reachable there today — a screen at the statement, not a substitute for SR2 at the entry.

## Fix

In the FILE-CONTROL binder (`DataBinder`'s file control entry handling, where ORGANIZATION and ACCESS MODE are both
captured onto `FileModel`): refuse RANDOM/DYNAMIC when the organization is sequential (the default organization is
sequential — cover the OMITTED clause too), at every edition (the 1985 text has the same rule; confirm in the version
reference), through an existing entry-rule descriptor if one fits or one new code. Sweep the sibling entry rules of
§12.4.5.5.2 while there (the RELATIVE KEY phrase's organization conditions, the same clause) and measure which have a
home; negatives at four editions. Note for whoever lands it: once SR2 is enforced, PB334's SR6 screen on the
sequential arm becomes unreachable — keep it (cheap, and it is the statement's own rule), but say so beside it.

## Landed

`DataBinder.BindFileControl`, immediately after the clause loop and beside the §12.4.5.9 SR2 screen that was
already there: `file.IsSequential && file.AccessMode is Random or Dynamic` (the predicate names the two
phrases SR2 names, not the negation of SEQUENTIAL) → **COBOLNET1858**,
positioned at the ACCESS MODE clause itself. Reproduced first on this worktree's own `cobol.exe`
(`ORGANIZATION IS SEQUENTIAL ACCESS MODE IS RANDOM` compiled AND ran, exit 0); the same source now exits 70 with
`COBOLNET1858` at all four editions.

Three things the note asked for, and what each turned out to be:

- **Both phrases, not one.** SR2 names DYNAMIC *and* RANDOM; `pb692-access-random-organization-sequential` and
  `pb692-access-dynamic-organization-sequential` are the same entry written each way.
- **The omitted ORGANIZATION clause.** §12.4.5.10.3 GR6 makes the bare `SELECT F ASSIGN … ACCESS MODE IS
  DYNAMIC.` a sequential file, and it is the shape a screen keyed on a written clause would miss;
  `FileModel.Organization` already defaults to `Sequential`, so `IsSequential` covers it with no extra arm.
  `pb692-access-dynamic-organization-omitted` pins it at four editions.
- **LINE SEQUENTIAL.** That it is "a sequential file" in SR2's sense is derived, not assumed: §12.4.5.10.3 GR2
  puts the phrase in the ORGANIZATION clause, that clause is written only in the Format-3 file control entry,
  and §12.4.5.2 SR11 says "Format 3 shall be specified only for a sequential file or a report file".
  `pb692-access-random-line-sequential` names **2023 alone** — the organization is a
  COBOL-2023 introduction, so at 85, 2002 and 2014 the source is rejected by PB688's
  organization gate (COBOLNET0900) and SR2 never gets to speak.

**The complement was measured.** A static scan of all 1483 SELECT entries under `tests/` (batch dir
`sweep_cells.py`) found every cell this screen rejects EMPTY — no corpus program declares the combination — and
every legal cell populated *except* LINE SEQUENTIAL with an explicit `ACCESS MODE IS SEQUENTIAL`, which had zero
witnesses. `conformance:2023/pb692_line_sequential_access_sequential` is that missing
positive — a 2023 program, because `ORGANIZATION IS LINE SEQUENTIAL` is itself a
COBOL-2023 introduction (kb/Work PB688).

**Sibling sweep of the file-control entry rules** (measured, `enforce only this rule` per the dispatch):
§12.4.5.9 SR2 has a home here and now shares `IsSequential` instead of a second open-coded enum pair;
§12.4.5.2 SR7 has one (`ResolveAssignUsing`, PB324); §12.4.5.13 SR2/SR3 have one. Still homeless and reported,
not fixed: §12.4.5.5.2 **SR1** (RANDOM banned on a SORT/MERGE USING/GIVING file — a statement-context rule, so
D13 puts it in the SORT/MERGE binder), §12.4.5.2 SR8/SR9/SR11/SR13 (format ↔ organization/SD consistency) and
SR12 (LINE SEQUENTIAL excludes RESERVE). The key entry rules are **PB699**, filed independently the same day and
the same shape — an entry rule that waits for a verb; §12.4.5.2 **SR10** belongs with them, its substance
enforced by `KeyedIoBinder.KeyedValidateFile` but cited there as §12.4.5.13, which carries no such requirement.

**Reachability note for PB334.** PB334 was still `open` on this base, so its §14.9.30.3 SR6 screen on the
*sequential* READ arm does not exist yet to annotate. The sentence it needs is written where it can be written —
in the comment at this screen: from here on, `IsSequential && AccessMode != Sequential` is unreachable, so any
statement-level test of `AccessMode == Random` on a sequential-organization file is defence-in-depth, never the
only guard. The SR6 screen in `KeyedIoBinder` stays fully reachable (RANDOM is legal for relative and indexed).
