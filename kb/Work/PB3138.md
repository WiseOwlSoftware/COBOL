# PB3138 — console windows still flash on the desktop; the launcher is not yet named

> flags: process-only

Source: the owner, 2026-10-13 ("It is opening terminal windows briefly again", then twice more); investigated by the
operator the same evening.

**Observed (a window recorder polling every 100 ms):** Windows Terminal windows that open for one to three seconds,
titled `C:\Program Files\Git\usr\bin\bash.exe` (one titled `npm`), at 23:43:52Z, 23:44:48Z, 23:45:12Z, 23:49:17Z,
23:49:27Z, 23:49:32Z, 00:11:05Z, 00:33:40Z, 00:33:45Z, 00:37:38Z and 00:37:42Z. Each coincides with an `OpenConsole.exe`
started by `svchost.exe`, which is Windows handing a NEW console to the default terminal: some process that had no
console started a console program, and Windows gave the child a console with a window. For 00:11:05Z the console's
client was a `bash.exe` three deep under a parent that had already exited (started 00:10:29Z).

**Ruled out by measurement:**
- The landing lane and the gates. From 00:40Z to 03:40Z the recorder saw no such window while the lane ran three
  landings with their Linux gates (`wsl.exe` under the lane's runner) and about twenty implementer gates ran every
  Windows self-test (`devlog.py`, `test_orchestrate_*.ps1` and the rest). The lane's runner has a windowless console
  since PB3117.
- The supervisor's units: no unit started between 23:40Z and 03:40Z (one wave unit ran 22:39Z–03:40Z).

**Measured facts that bear on it:**
- Claude Code's Bash tool starts Git's launcher, `C:\Program Files\Git\bin\bash.exe`, with NO console (an
  `AttachConsole` probe from outside fails with ERROR_INVALID_HANDLE). The launcher's child, `usr\bin\bash.exe`, has a
  windowless console, so a Bash-tool command's own tree normally opens nothing.
- Git Bash processes whose parent has exited, left behind by finished or stopped commands, can have a console whose host
  is gone (`AttachConsole` fails with ERROR_PIPE_NOT_CONNECTED, 233).
- Every recorded window fell inside one attended session's two gate runs of branch `readme-dispositions`
  (23:41:49Z–00:14:41Z and 00:28:03Z–00:53:51Z), and inside a stretch of heavy attended-session activity. Not every
  window lines up with a gate phase, so this is a correlation, not a cause.
- `scripts/telemetry/otlp_sink.py --ensure` still starts the sink with `DETACHED_PROCESS`; PB3117's sweep left it
  because the sink starts no child process, so it cannot be this.

**Hypothesis, not confirmed:** a Git Bash process with no usable console (started with no console, or whose console host
has gone) starts a program; Windows creates a new console for it with a window, and Windows Terminal, as the default
terminal, shows it until the program exits. The title is the first client's image path, here Git's `usr\bin\bash.exe`.

**Next step:** the recorder now also logs the command line of the console client and of each of its ancestors when a
`PseudoConsoleWindow` appears. The next window names the command and its launcher; the fix is then made at that launch
(a windowless console, never `DETACHED_PROCESS`; the owner's rule), with a test that fails if the launch gets a visible
console, as PB3117's self-test #13 does for the lane. The owner can also choose the Windows default-terminal setting;
that is their setting, never changed by a session.

**Related:** PB3117 (the lane's runner, fixed the same way).
