# PB4077 — a later CLEAN releases a same-file successor that does not contain the CLEAN head

**Sites:** `scripts/prune_worktrees.py` (`carrying_findings`, `review_answers`), `.claude/skills/workstream/references/rolling-wave.md` (the "Same-file successors" paragraph)

Searched first: PB3380, PB3381, PB3404 and PB3509 are related but none covers this.

## Mechanism
The docstring of `carrying_findings` says the successor "is WAITING TO LAND again once a later round of that review records CLEAN or that head is on main". The first arm does not require the successor's tip to contain the CLEAN head, nor that head to be on main. The rolling-wave paragraph "the predecessor ... lands it, the successor's pull request merging on top" assumes an order nothing enforces.

## Witness (2026-10-30)
Wave 20261758 group A (PB3953): the review findings file `E:\COBOL-coord\scratch\review-w20261758-a.jsonl` has round 1 FINDINGS at `5d4e0ac1d`. Its R1-1 is BLOCKING (medium): `FunctionValueField.Compare` orders a wide temporary against a non-wide exact one by the 34-digit image, which is a wrong answer. Round 2 is CLEAN at `0941c35dc` on `worktree-wf_b7b6d335-6b8-4`; `review_findings.py last-verdict` reads CLEAN, round 2.

Wave 20261759 group A (PB1369, branch `worktree-wf_f1a5f2c9-2d2-1`) merged `5d4e0ac1d` (merge `baad3c202`), not `0941c35dc`. Its review was CLEAN at `946dbcba6`, and the lane queued it as PR #787 (created 2026-10-30T01:00:14Z; its title names DEVLOG 2754 for PB3953 and PB1369 together). The PB3953 branch's own attempt 000322 (01:06Z) then stopped exit 16 DRIVER FILE QUEUED behind #787 (`kb/Work/PB3953.md` and `PublicAPI.Unshipped.txt`). So #787, first in the merge queue, brings R1-1 to main unanswered, and the fix reaches main only when the PB3953 branch lands after it. The merge group cannot see it: R1-1's golden legs 8-11 live only in `0941c35dc`.

## Harm
A finding the review held BLOCKING (a wrong answer) reaches main for the interval. The predecessor's later landing must also untangle a DEVLOG entry the successor already stamped.

## Fix direction (not decided)
Treat a later CLEAN as releasing the successor only when the successor's tip contains that CLEAN head or the head is on main. Otherwise the successor reads IN FLIGHT, waits_on the predecessor's branch, until it lands. Add a `test_prune_worktrees` case with this exact shape.
