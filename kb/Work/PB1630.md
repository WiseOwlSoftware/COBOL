# PB1630 — LANDED

Filed 2026-09-26 by the orchestrator from the wave-62 O (PB1617) implementer's report, lead 1 (the train-63 lander
did not carry cluster O, so its leads were not filed there).

## Repro
`E:\Temp\claude\E--CobolSharp\ba65f072-4d30-4868-9bd3-4e5c60087107\scratchpad\w62o\probe\callp.cob` line 4:
`CALL "PRQ2" AS NESTED USING BY CONTENT NULL` into `01 LP USAGE POINTER` compiles, then terminates with
`EC-PROGRAM-ARG-MISMATCH … cannot be read through a pointer or object-reference formal`.

## Rule
§14.8.2.3.3 (SET paragraph): an argument for a pointer or object-reference formal conforms when a SET of the formal
from it would be legal — and `SET pointer TO NULL` is legal. BY CONTENT delivers a copy (§14.2.3 GR9).

## Code sites
`CallEmitter.cs:659` renders a NULL argument as a string fill; `CallAbi.cs:735` `Slot<T>` has no NULL arm. PB1617
(landing with the next train, branch `worktree-agent-a9718838ca4e047a1`) moved figurative fills into
`CallEmitter.FigurativeArgumentImage` and routed pointer/object formals through the SET paragraph in
`ParameterConformance.ContentConformanceReason` — build on that.

## Landed (w62p implementer, 2026-09-26)

Re-probed on the w62p build (base `07a9aaa12` + PB1617): `callp.cob` line 4 terminated with
EC-PROGRAM-ARG-MISMATCH exactly as filed. The sweep found the same root — NULL read as a figurative FILL instead of
the identifier §8.4.3.1.2 Format 8 / Format 6 makes it — on four more arms of the one crossing: `CALL … AS NESTED
USING BY VALUE NULL` was refused as a non-numeric literal-2 (COBOLNET1762, §14.9.4.3 SR23 asked of an identifier-4
that SR22 admits); the keyword-less `USING NULL` into a BY VALUE formal (same screen); `INVOKE … USING NULL` into a
POINTER formal was refused as "not yet carried" (the INVOKE arm admitted only an object-reference formal and rendered a
bare `null`); and NULL into a PIC X or group formal COMPILED and ran as a one-character LOW-VALUE fill (§14.9.25.3 SR1
bars class pointer from the MOVE §14.8.2.3.3 rule 2d asks).

**Fix.** ONE storage-free carrier, `PredefinedNullArgument.Instance` (`CallAbi.cs`), for the CALL and function lanes
in the written mode; `CobolArgAdapt.Slot<T>` / `SlotValue<T>` answer it with a fresh cell holding their carrier's null
(`CobolArgAdapt.PredefinedNull<T>`, now also the pointer arm of `Omitted<T>`), every other adapter refuses it as
EC-PROGRAM-ARG-MISMATCH — so the §12.3.8.4 GR10 c) crossing (no formal known) is the same crossing.
`ParameterConformance.ContentConformanceReason` gives NULL the verdict of an identifier of class pointer (SET paragraph
for a slot formal, refusal otherwise) for CALL, function and INVOKE alike; `CallBinder.Sr23LiteralIsNumeric` no longer
asks SR23 of NULL; `BoundInvokeArg.NullObject` became `PredefinedNull`, rendered as the formal's
`PicInfo.DefaultInitializer`. Witnesses: conformance:2002/pb1630_null_argument_crossing,
conformance:negative/pb1630-call-content-null-alnum-formal, `PredefinedNullArgumentTests` (Unit).

**Not closed here:** PB1427's NULL operand model (NULL still rides the `figurativeConstant` arm) and its §8.4.3.10.3
SR1 a) context screen for the non-argument contexts (IF X = NULL, INSPECT, STRING, LENGTH(NULL), INITIALIZE
REPLACING BY NULL) — this landing fixes the ARGUMENT slots of that rule only.
