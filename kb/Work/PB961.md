## Reproduced

`scratchpad/reg10/snan.cob`:

```cobol
       01 G1.
          05 S  USAGE FLOAT-BINARY-32.
       01 G1X REDEFINES G1 USAGE BINARY-LONG UNSIGNED.
       01 G2.
          05 D  USAGE FLOAT-BINARY-64.
       01 G2X REDEFINES G2 USAGE BINARY-DOUBLE UNSIGNED.
           SET CONTENT OF S TO FLOAT-NOT-A-NUMBER-SIGNALING
           DISPLAY "S32=" G1X
           SET CONTENT OF D TO FLOAT-NOT-A-NUMBER-SIGNALING
           DISPLAY "D64=" G2X
           SET CONTENT OF S TO FLOAT-NOT-A-NUMBER
           DISPLAY "Q32=" G1X
```

Observed:

```
S32=2143289345          = 0x7FC00001  (quiet bit SET: a QUIET NaN with payload 1)
D64=09218868437227405313 = 0x7FF0000000000001  (correct signaling NaN)
Q32=2143289344          = 0x7FC00000  (correct quiet NaN)
```

Expected for S32: `0x7F800001` = 2139095041, the binary32 signaling encoding CONFORMANCE.md DOC-A.1-176 documents.
binary64 is right, and binary32 is wrong. The group-A implementer saw the same result without a REDEFINES (S-SNAN=N,
S-QNAN=Y through the class condition), so the defect is in the value lane, not the REDEFINES codec.

## Mechanism (from the emitted C#)

`snan.g.cs` line 47:
`CobolNum.FormatImageFloat(System.BitConverter.Int32BitsToSingle(unchecked((int)0x7F800001)), _P_1)`.
`FormatImageFloat` takes a **`double`** (`src/Cobol.Net.Runtime/Values/Numeric/CobolNum.Image.cs:114`) and narrows
it back with `(float)value`. On x64, the float→double conversion (`cvtss2sd`) QUIETS a signaling NaN, as ISO/IEC 60559
format conversions do. The 64-bit lane has no conversion, which is why D64 is right. DOC-A.1-176 says "the emitted
expression is a … reinterpretation, which performs no arithmetic and so cannot quiet the value". That is true of the
expression and false of the pipeline that stores it.

## What the fixer must do

1. Give the binary32 lane a `float` path end to end: a `FormatImageFloat(float, …)` twin or a bits-typed parameter.
   Note the file's own CS0121 warning about integer arguments before you add an overload. Then sweep EVERY site
   that carries a FLOAT-BINARY-32 value through `double`: image codec, typed-field store, MOVE float→float, CALL /
   RETURNING carriers and the `IeeeSpecials` emission. **Every float→double widening of a binary32 SNaN is this
   bug.**
2. Correct DOC-A.1-176's sentence in `docs/CONFORMANCE.md`, and pin the bits with a golden that reads them back
   through a REDEFINES (the shape above), at 2014 (where SET CONTENT is introduced) and at 2023.
   `IeeeSpecialsTests.TheEmittedExpression_EvaluatesToTheDocumentedBits` passes because it tests the expression,
   not the stored image. Extend it to the stored image.
3. Both inventory rows are recorded CONFORMS today on that expression-level evidence. This note claims them: the
   landing must re-record GR-14.9.39.4-35 with the new golden as a witness.

## Landed 2026-09-22 (wave 49, branch worktree-wf_ca96470f-e1c-3) — the binary32 value never meets a binary64

Re-probed first on the worktree's own build (0/0): `S32=2143289345` (0x7FC00001, QUIET) — and, beyond the note,
`IF S IS FLOAT-NOT-A-NUMBER-SIGNALING` was `N` for a plain TYPED FLOAT-BINARY-32 item too, with no image lane in
the path. **The note's mechanism was half of it.** The second half is the JIT: an inline
`BitConverter.Int32BitsToSingle(unchecked((int)0x7F800001))` is folded into a floating constant, which RyuJIT carries
as a `double`, so an optimized (Release — the backend's `OptimizationLevel.Release`) build stores `0x7FC00001`
before any image lane is reached (measured in a standalone console: Release quiets, Debug does not). Two roots, one
shape — a binary32 value passing through binary64 — so both are fixed here:

- **Materialization:** `IeeeSpecials.Text` deleted; `IeeeSpecials.Bits` is the one table and `RuntimeApi.FloatFromBits`
  spells it as `CobolFloat.FromBinary32Bits(0x7F800001u)` / `FromBinary64Bits(…UL)` — `NoInlining`, so no JIT constant.
- **Image lanes:** `CobolNum.FormatImageSingle(float, …)` / `ParseImageSingle` (no double); `StoreImage(…, float)`
  uses the latter. `RuntimeApi.NumFormatImageFloat` / `NumParseImageFloat` take the ITEM's width with no default, so
  every site states it: the group image codec (AsImage/FromImage, table elements, the Tier-B seed), VALUE seeding,
  MOVE / COMPUTE / ACCEPT / SET float receivers, the storage-image text channel and the windowed-float DISPLAY read.
  The ARITHMETIC read (`NumericRenderer`'s windowed-float arm) passes `binary32Carrier: false` — widening is the
  operation there.
- **Same-usage MOVE:** §14.9.25.4 GR6 c) — "transferred to the receiving data item without change" — is now a copy on
  the carrier (`NumericRenderer.FloatCarrierRead`), not `StoreSingleChecked((double)S)`; INVOKE BY CONTENT's float arm
  reads through the same helper.
