# PB840 — LANDED — the sum counter has a name and nothing can say it

Source: the `PB367b` implementer report, item (a) (observed while building
`ReportWriterConformanceTests.UseBeforeReporting_Gr9ab_...`, which is why GR9 b) had to be witnessed indirectly).

## Repro — re-run on this tree

`scratchpad/reg4/probe/p03c_named_sum_counter.cob` (PROGRAM-ID `R4P03C`), `--std 2023 --run`:

```cobol
       RD R1 CONTROL IS FINAL.
       01 CFG TYPE IS CONTROL FOOTING FINAL LINE PLUS 1.
          03 CF-SUM COLUMN 4 PIC 99 SUM WS-A.
       PROCEDURE DIVISION.
           ...
           MOVE CF-SUM TO WS-SEEN
```

```
(20,12): error COBOLNET1639: 'CF-SUM' is not defined - no declaration in this source element gives the name
         'CF-SUM' ... (ISO 8.4.2.1)
```

## The rules, quoted

```
$ python scripts/spec/cite.py --check 13.18.54.4 "the data-name is the name of the sum counter"
  OK  §13.18.54.4 5)  (General rules)
      5) If a data-name immediately follows the level number in the entry containing the SUM clause, the data-name is the name of the sum counter, not the name of the associated printable item, if any.
$ python scripts/spec/cite.py --check 13.18.54.4 "It is permissible for procedure division statements to alter the content of sum counters"
  OK  §13.18.54.4 12)  (General rules)
```

GR5 says the data-name names the COUNTER; GR12 says procedure division statements may alter its content — which
presupposes that they may reference it. A program that reads or adjusts its own report totals cannot be written.

## Code site

`src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs` (the COBOLNET1639 raise) and the report-section binder in
`src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs`, which builds the counter but never publishes its
data-name into the source element's name space. The counter exists at run time (`CobolReport`'s sum state); what
is missing is the SYMBOL.

## Sibling sweep the fixer owes

* The same question for every REPORT SECTION name a procedure division statement may legally reference:
  `LINE-COUNTER` and `PAGE-COUNTER` (both already resolvable — they are the template), a report group's
  data-name as the operand of GENERATE, and the RD's own report-name for INITIATE/TERMINATE/SUPPRESS.
* §13.18.54.3's rules on where a sum counter may be referenced (qualification by report-name) — the fix must
  carry the qualification, not just the bare name.
* `docs/COBOLNET_REPORTS_DESIGN.md` records the name-space model; extend it in the same change set.

## Landed - 2026-09-19, wave 39 (group REPORT-WRITER-SUM)

`status: landed`. The counter is now a `Model.ReportSumCounterPlace` - the CAPACITY / DEBUG register pattern, a
VIEW over engine state - built by `ReferenceResolver.SumCounterFor` from `DataBinder.SumCounters` and rendered
by `PlaceRenderer` to `CobolReport.SumValue` / `SetSumValue`. Being a PLACE is the point: GR12 permits
procedure division statements to ALTER the counter, and a read-only bound-expression interception (the
LINE-COUNTER shape) would have fixed one arm of a two-arm dispatch. The former `BoundReportSumRef` is DELETED
and the compose of a SUM entry's printable face reads the same place, which is also what GR4's "moved, according
to the general rules of the MOVE statement" asks for. `MOVE CF-SUM TO WS-SEEN` compiles; the golden
`tests/conformance/85/pb882_report_sum_counter_identity.cob` exercises both directions.

The sibling sweep: LINE-COUNTER / PAGE-COUNTER were already resolvable (they are the template this followed);
a report group's data-name as GENERATE's operand and the RD's report-name for INITIATE/TERMINATE/SUPPRESS
resolve through `ReportGroupResolution` and `RwFindReport`. The qualification S13.18.54.3 asks for is carried:
a sum counter's only available qualifier is the report-name of S8.4.2.2.2 Format 1, and the resolver takes it,
diagnosing an unmatched qualifier or a name two entries establish (COBOLNET2145 - legal to DECLARE per PB882,
illegal to REFERENCE per S8.4.2.2.1). `docs/COBOLNET_REPORT_WRITER_DESIGN.md` S2/S3/S5 carry the model. The
note claims no inventory rows.
