# PB336 — two guards in the wrong order, in three connectors

**Rows:** `GR-14.9.30.4-1`.

## The program

`<lane3 scratch>/out-b1/probe/optabs/OPTABS.cob` — `SELECT OPTIONAL F` (SEQUENTIAL) and `SELECT OPTIONAL R`
(RELATIVE, ACCESS SEQUENTIAL), neither physical file present; `OPEN INPUT`, then two READs each. Observed:
`OPEN-F=05` / `F-READ1=10` / `F-READ2=10` / `OPEN-R=05` / `R-READ1=10` / `R-READ2=10`. Contrast
`out-b1/probe/seqprev/EOF46.cob` on a PRESENT one-record file: `R1=00` / `R2=10` / `R3=46`.

## The rule

§9.1.13.4 item 1 c) scopes '10' to a sequential READ *attempted for the first time on a file described as
optional and the physical file is not present*. §14.9.30.4 GR21's FIRST SENTENCE then governs the second
attempt:

> if the previous READ or START statement for the file connector was unsuccessful, then the READ statement is
> unsuccessful and the I-O status is set to 46

`--check 14.9.30.4 "the READ statement is unsuccessful and the I-O status"` → **OK**; §9.1.13.7 item 6 b)
confirms it (*The preceding READ statement referencing that file connector was unsuccessful*). So `F-READ2` and
`R-READ2` shall both be '46'.

## What the compiler does

`SequentialConnector.Read` orders its guards `!IsOpen` → `Mode` → `OptionalAbsent` → `LastReadUnsuccessful`, and
the `OptionalAbsent` arm both SETS `LastReadUnsuccessful` and returns '10' — so the '46' guard it has just armed
is unreachable for that connector for the life of the open. `RelativeConnector.ReadSequential` and
`IndexedConnector.ReadSequential` have the identical ordering: the same pattern in three places, which is the
sweep.

**That the ordinary EOF path in the SAME chain does return '46' is what makes this a defect rather than a spec
reading** — the implementation already agrees with GR21's first sentence, and only this one arm escapes it.

## The fix shape

Swapping the two guards is the whole fix, and the ordering then matches GR21's own sentence order. Do it in all
three connectors, and add the drift test that runs the two-READ shape against all three organizations, since the
uniformity across connectors is what made a per-connector patch look sufficient.

**Code sites:** `SequentialConnector.cs#Read` · `RelativeConnector.cs#ReadSequential` ·
`IndexedConnector.cs#ReadSequential`.

## Landed — 2026-09-05

Re-probed first on a worktree build of today's tree, and the mechanism held exactly as written, on all three
organizations: `OPEN-F=05 / F-READ1=10 / F-READ2=10 / F-READ3=10`, `OPEN-R=05 / R-READ1=10 / R-READ2=10`,
`OPEN-X=05 / X-READ1=10 / X-READ2=10`. **The note under-counted the blast radius by two shapes.** GR21's
antecedent is "the previous READ *or START* statement", and §9.1.13.7 item 6 has both an a) and a b) arm, so the
same guard order also swallowed the '46' owed after an unsuccessful START and after an unsuccessful *random*
READ — both measured at '10' where item 6 a) / 6 b) require '46' (`REL-START=23 / REL-AFTER-START=10`,
`REL-RANDOM=23 / REL-SEQAFTERRANDOM=10`, and the indexed twins). Four wrong statuses, one ordering.

**The fix was the extraction, not the swap.** Swapping two lines in three files would have left three copies of
one rule — which is what made a per-connector patch look sufficient in the first place — so the whole READ
precondition chain moved to `FileConnector`, once:

- `ReadOpenModeGuard()` — §14.9.30.4 GR2 / §9.1.13.7 item 7 → '47'. Was written out five times.
- `SequentialReadGuard()` — GR2, then **GR21's '46'**, then §9.1.13.4 item 1 c)'s '10', in the standard's own
  order. The comment says *why* the order is the rule: the '10' arm is itself an unsuccessful READ, so it arms
  GR21 for its successor, and that is precisely what makes '10' "first time" only.
- `RandomReadAbsentOptionalGuard()` — §9.1.13.5 item 3 b) → '23', deliberately **not** first-time-scoped and
  never '46' (GR21 opens "For a sequential READ statement"), but still arming the poison for a following
  sequential READ on a dynamic-access connector (§9.1.13.7 item 6 b) is not restricted to sequential reads).

`SequentialConnector.Read`, `RelativeConnector.ReadSequential` and `IndexedConnector.ReadSequential` now delegate;
`RelativeConnector.ReadRandom` and `IndexedConnector.ReadRandom` take the two random-side guards (the indexed one
still establishes its key of reference, GR30/GR31, between them). START's own absent-optional rule
(§14.9.41 GR5 → `StartFail()`) is a different rule of a different statement and was deliberately left alone.

**Verified:** `05/10/46/46` on all three organizations; the present-file contrast still `00/00/10/46`;
`23` then `46` after a failed START and after a failed random READ.

**Goldens:** `tests/conformance/2023/pb336_optional_absent_read_46.cob` (PROGRAM-ID `PB336RD`) walks all three
organizations, the present-file contrast arm, both GR21 antecedents and the random-READ shape in one program;
`tests/conformance/85/pb336_optional_absent_read_46_85.cob` (PROGRAM-ID `PB33685`) is its 1985 twin — the rule
carries no edition marker and the runtime connectors carry no edition gating, so the oldest supported edition is
where a regression would surface first. **Drift test:**
`tests/Cobol.Net.Tests.Unit/ReadPreconditionOrderDriftTests.cs` pins the STRUCTURE the goldens cannot see — that
the poison is tested before the absent-OPTIONAL arm inside the shared guard, and that no connector re-inlines a
private copy — with a failure proof that drives the same predicates over a fabricated swapped source.

**Row `GR-14.9.30.4-1` stays PARTIAL and the GAP count does not move**, because that row's other half — status
'09' has no producer anywhere (§9.1.13.2 item 7 / GR16) — is untouched by this. The row was handed to [[PB329]],
whose Part 2 is now the only thing holding it open.
