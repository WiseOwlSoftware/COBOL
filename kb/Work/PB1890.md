# PB1890 — LANDED

## Landed — wave 1006 group B, 2026-10-03

Re-probed first on a fresh Debug build: `DISPLAY T(F)`, `DISPLAY T(IX + 0.0000000001)` and
`DISPLAY W(1 + 0.0000000001:2)` printed `2`, `2`, `AB` under `>>TURN EC-BOUND-SUBSCRIPT EC-BOUND-REF-MOD CHECKING ON`.

**Fix — the adjudication's design, the test before the store.** The D18 materializer
(`StatementBinder.MaterializeSubscriptSegment`) no longer registers a `BoundCompute` into the 9-fraction §15.4
temporary. It registers a new pre-operation leaf, `BoundPositionValue(Value, Temp, RefMod)`, which
`ArithmeticEmitter.EmitPositionValue` renders RECEIVER-LESS (a nested quotient keeps its guard digits, no resultant
scale truncates it) and hands, on its own carrier (`NumericRenderer.IntakeCarrier`, now the ONE carrier mapping the
§15.3 type-6 intake shares), to `CobolTable.OccValue` / `OccValueDec` / `OccValueReal` or the `CobolString.RefModValue*`
twins. Those ask the carrier's own exact predicate (`CobolNum.HasFraction(Int128, scale)`, `CobolDec.HasFraction`, and
`CobolNum.HasFraction(double)` — the binary64 predicate, now one function the intrinsic intake also calls), raise
EC-BOUND-SUBSCRIPT / EC-BOUND-REF-MOD through the existing raise sites, and return the truncated, SATURATED `long`
position, which the temp (now a 19-digit integer, `SegmentTempPic`) stores. The position read is unchanged.
Standard-decimal arithmetic is covered by the same route (the SDIDI carrier). With checking off a subscript truncates
(the lenient continue); a ref-mod violation terminates the run unit as every unchecked one does (R60).

Citations (`cite.py --check`): 8.4.2.3.4 "does not result in an integer, the EC-BOUND-SUBSCRIPT exception condition is
set to exist" → OK §8.4.2.3.4 1) b); 8.4.3.3.4 "results in a non-integer value" → OK §8.4.3.3.4 5); 5.5 "the
implementor shall define when the operand represents an integer" → OK §5.5 3) a); 5.5 "whose decimal fixed-point
representation contains only zeros to the right of the decimal point" → OK §5.5 3) b).

Goldens: `conformance:2023/pb1890_position_expression_exact` (float item, expression subscript, expression ref-mod,
three integral controls) and `conformance:2023/pb1890_position_expression_standard_decimal`. DOC-A.1-124's open
exception sentence is gone (docs/CONFORMANCE.md), and GR-5.5-3 / DOC-A.1-124 are CONFORMS.

Sibling sweep (the note's list): `CobolString.RefModPosition` and `CobolTable.Occ` (all overloads) read a declared item
at its own scale through its profile — exact, unchanged; the expression arms of both now go through the new intakes.
`CobolIndex.TryAmount` / `TryAmountReal` already test the exact value (PB1526's sweep). `ReferenceResolver.PositionRead`
reads the integer temp. No other site stored a position into a fixed-scale temporary (grep `SegmentTempPic`,
`__SUBEXPR-`: one producer).

Found 2026-09-30 by the w0930-numeric implementer while landing PB1526 (the intrinsic-argument half of the same rule). The rows
`GR-5.5-3` and `DOC-A.1-124` were claimed by PB1526 and stay PARTIAL on THIS half, so they move here.

## The rule

§5.5 3) a): under native arithmetic "the implementor shall define when the operand represents an integer"
(`cite.py --check 5.5 "the implementor shall define when the operand represents an integer"` → OK §5.5 3) a)). WiseOwl
COBOL's definition is `docs/CONFORMANCE.md` DOC-A.1-124: **the operand's EXACT value has no nonzero digit right of the point,
tested on the value the native intermediate holds for an arithmetic expression, at EVERY rule that asks** — a subscript
(§8.4.2.3.4 GR1b), a reference-modification position, a SET index / amount, an intrinsic integer argument (§15.3 type 6).

## Code site, and why it was not fixed in the PB1526 landing

`src/Cobol.Net.Compiler/Binding/Bound/StatementBinder.SubscriptSegments.cs:72` (`SegmentTempPic` =
`Procedure.SendingValueTemp.FunctionValuePic`, 21 integer + 9 fraction digits) and `:144` (the `BoundCompute` that stores the
segment's value into the temporary with `CobolRounding.Truncation`); the test itself is the right one
(`CobolTable.OccScaled` → `CobolNum.HasFraction`), it just runs on the truncated copy.

Too large for the intrinsic-argument change, for two reasons: (1) the temporary's description is the ONE §15.4 temporary the
sending-value materializer (§14.9.25.4 GR1) and the numeric class conditions (DOC-A.1-92's S9(21)V9(9) capacity facts) also
read, so widening its fraction changes documented determinations; (2) no fixed fraction width can be exact for an arbitrary
native expression or a binary64 (2 + 1.0E-20 needs 20 digits, a double near 2 has ~16) — DOC-A.1-124 says an expression is
tested on the value the intermediate holds, which means testing the expression's value BEFORE any store, and that is the
D10 transitional string carrier (`RefModPlace.Start` / `Length`) migration the file's own header forbids until PHASE 15 CUT
2.5 deletes this path. The fix belongs with that migration (an exact-value position read on a `BoundExpr` carrier); until
then DOC-A.1-124's subscript / ref-mod arms are exact only to 9 fraction digits.

## Adjudication 2026-09-30 (read-only ISO check, every citation run through `cite.py --check`): the standard-arithmetic arm DIVERGES

Section 5.5 3) a) leaves "when the operand represents an integer" to the implementor (Annex A.1 item 124, DOC-A.1-124), so in NATIVE arithmetic the 9-fraction truncating temporary is licensed.
But 5.5 3) b) requires, under STANDARD-DECIMAL or STANDARD-BINARY, that the operand "shall be equal to a standard intermediate data item ... whose decimal fixed-point representation
contains only zeros to the right of the decimal point"; 8.4.2.3.4 1) b) sets EC-BOUND-SUBSCRIPT "If the evaluation of arithmetic-expression-1 does not result in an integer"; 8.4.3.3.4 5) does the same
for EC-BOUND-REF-MOD. `StatementBinder.SubscriptSegments.cs` (~L126-144) stores every expression segment into the 9-fraction truncating temporary whatever the arithmetic mode, so under
`OPTIONS. ARITHMETIC IS STANDARD-DECIMAL` with EC-BOUND checking on, `T(IX + 0.0000000001)` and `W(1 + 0.0000000001:2)` select a position where the standard REQUIRES the exception. The adjudicator
read this from the code and did not run it: **probe it first** (pinned worktree, `>>TURN EC-BOUND-SUBSCRIPT EC-BOUND-REF-MOD CHECKING ON`).

**It is not deferrable to the Phase 15 carrier migration (CLAUDE.md rule 3).** Fix design: make the segment pre-operation an INTEGRAL STORE. Evaluate the segment's BoundExpr once on its own carrier
(the exact scaled Int128 or 256-bit value in native, the SDIDI or SBIDI in the standard modes, binary64 for a float item) and ask the ONE integrality predicate PB1526's intrinsic intake already uses
(`CobolNum.HasFraction` and its siblings); on a fraction raise EC-BOUND-SUBSCRIPT or EC-BOUND-REF-MOD for that position, otherwise store the integer into the temporary. The test runs before the store,
so neither reason this note gives for waiting applies. The same change closes the native exception in DOC-A.1-124 (drop that sentence; flip GR-5.5-3 and DOC-A.1-124 to their landed state).
