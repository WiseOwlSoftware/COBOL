# PB3652 — the branch survey reads a replayed SPLIT branch as a DECISION row: prune_worktrees.contained() decides "lands through another branch" by ancestry only

**Sites:** `scripts/prune_worktrees.py` (`contained`, ~line 940, and its survey rows), `scripts/orchestrator/plan_wave.py` (the planner side that already honours `replays`).

## What happens

A SPLIT branch whose commits a later branch cherry-picked is listed DECISION by `python scripts/prune_worktrees.py` until the later branch lands, though the planner (PB3170) no longer dispatches it: `contained()` tests ancestry only and never consults `replays`. Same root family as PB3170 but a different function and a different consumer: the survey and the landing lane read the states, not the planner. It changes the landing lane states, so it was not folded into PB3170.

## Fix direction

Have `contained()` (or the survey row builder) read the same `replays` result the planner uses, so a replayed SPLIT branch reads as carried by its carrier. One rule, one place: no second replay test in the survey. Witness: a scratch repository with a SPLIT branch and a later branch cherry-picking it; the survey must not list it DECISION.

## Source

Report `w20261030c2-PB3170-report.md` (PB3170, PR #509), "New defects" item 1. The report asked whether this is the same mechanism as R2-1 (PB3651): it is not, since R2-1 is the carrier tie-break inside `replays` and this is a consumer that never calls `replays`.

## Landed (2026-10-24, wave 20261031 group B)

Re-probed on a scratch repository: `split-p` (SPLIT) cherry-picked into `split-q` (SPLIT) read DECISION, and so did
`split-m` (SPLIT), an ANCESTOR of `done-c` (DONE, awaiting review), a carrier the planner's `branch_carrier` already
honours. The note named the replay arm; the ancestry arm of `contained()` had the same hole, because it skipped every
DECISION row that has a report that is not FINDINGS, and a SPLIT row is one. Fixed at one place in two arms:
`contained(rows, graph, reports, work_dir)` now admits an UNFINISHED (`plan_wave.FINISH_STATUSES`) DECISION row as a
candidate, and reads, after ancestry, the planner's own replay rule: `prune_worktrees.replay_view` builds `replays`' inputs
(the ranked carriers, the unlanded branches, the ABANDONED set) for BOTH readers, `plan_wave.branch_replays` calls it, and
the survey's `survey_replays` calls it with the rows' ranks and `kb/Work`'s abandon records, so there is no second replay
test in the survey. A replayed row reads IN FLIGHT with `carrier` set (so `owned()` excludes it), its `why` naming the
carrier and the rule. Not carried: a partly replayed branch, one replayed by an ABANDONED branch, a FINDINGS-stamped
row (its finisher answers the findings), a finished unreviewed row (the reviewer reads it). Tests: the survey self-test
fixtures `rp-pred`/`rp-succ`/`rp-part`/`rp-partc`/`rp-gone`/`rp-dead`/`an-pred`/`an-succ` (red with the old
`contained`, shown), and a drift scan that only `prune_worktrees.py` calls `replays` (`test_plan_wave.py`).
