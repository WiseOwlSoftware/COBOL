# PB3975 — DIVIDE ... REMAINDER stores the remainder after a quotient size error

**Sites:** `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/ArithmeticEmitter.cs` (`ArithmeticEmitter.EmitDivideRemainder`, the
`else` arm that runs when the statement has no size-error phrase or checking is off).

Filed 2026-10-28 by the enqueue unit's clerk from the PB3869 implementer's lead, carried unchanged. Not re-probed.

## Rule

ISO/IEC 1989:2023 14.9.12.4 General rule 6 c) (checked with `cite.py --check`): "If the size error condition is not
raised, a subsidiary quotient is developed ... The remainder is calculated as indicated in General rule 7 and is stored
in the data item referenced by identifier-4 unless storing the value would cause a size error condition, in which case
the content of identifier-4 is unchanged". The remainder step is conditioned on the quotient raising no size error.

## Repro (measured by the PB3869 implementer)

`DIVIDE 1000 BY 4 GIVING A REMAINDER R` with `A PIC 99` and `R PIC 9`, no `ON SIZE ERROR` phrase (or checking off):
the quotient 250 overflows `A`, and the program still stores the remainder, printing `50 0`.

## Scope and disposition

Under a size-error phrase the clause leaves identifier-4 unchanged and the emitter honors it. When the statement has no
phrase, or checking is off, the quotient's result is implementor-defined (14.7.5), and the report records that
DOC-A.1-70 should decide whether the remainder is stored then. Fix at the root with that decision recorded in
`docs/CONFORMANCE.md` (DOC-A.1-70), a golden per arm, and a sweep of the sibling lanes (`NativeSubsidiaryQuotient`,
`CarriedSubsidiaryQuotient`).

## Re-probed on an abandoned branch (`worktree-wf_5cf68b99-205-1`, abandoned in PB3989): plan it again from main

Wave 20261735 group A fixed this note on a branch that also followed GnuCOBOL's COMP-5 exemption, which the owner ruled
GnuCOBOL's error (PB3989), so the branch does not land. Its findings stand and are copied here (report
`E:/COBOL-coord/scratch/reports/w20261735a-PB3869-report.md`):

- **The filed case is not a defect as filed.** `DIVIDE 1000 BY 4 GIVING A REMAINDER R` (A `PIC 99`, R `PIC 9`) prints `50 0`
  on main and on GnuCOBOL 3.2. Rule 6 c) keeps r only when the size error is the SIZE ERROR phrase's (or checking is
  enabled), and there the emitter already gates the store. With checking off and no phrase, §14.7.5 sends the condition
  to §14.6.13.1.3 8), so CLAUDE.md rule 1 follows GnuCOBOL, which (libcob `cob_div_quotient` / `cob_div_remainder`)
  stores the remainder formed from the quotient truncated at identifier-3's scale with every integer digit.
- **The cases that DO differ.** No phrase: `DIVIDE 1003 BY 4 GIVING B REMAINDER R3` (B `PIC 99`, R3 `PIC 999`) gives 803 on
  main and 003 on GnuCOBOL: PB129's digit cap made the subsidiary quotient 50. The branch removed the cap (rule 6 c)'s
  digit count governs only a quotient that raised no size error, which fits identifier-3, so the cap acts only in item
  8's case): `SubsidiaryShape` / `SubsidiaryShapeOf`, `NativeSubsidiaryQuotient`, `FixedPointSubsidiary`,
  `RuntimeApi.DecSubsidiaryQuotient` (`NumCapDigits` deleted), `CobolDec.SubsidiaryQuotient` (its digits parameter
  deleted), `CobolNum.CapDigits` deleted (runtime major 20 to 21); the native lane's back-multiply takes the quotient's
  own digit bound (`NumericRenderer.QuotientDigitBound`, shared with `Combine`'s nested quotient).
- **The open question the re-plan must settle.** With only a NOT ON SIZE ERROR phrase (checking off) main keeps R3 (777)
  and GnuCOBOL stores 003; the branch stored it (`EcState.SizeErrNotPhraseOnly`). PB3989 says WiseOwl keeps EVERY
  receiver of a [NOT] SIZE ERROR statement that meets a size error, which reads as keep; the implementer derives whether
  identifier-4 is such a receiver (§14.9.12.4 rule 6 c), §14.6.13.1.3 8)) and records the answer in DOC-A.1-70, asking
  the owner only if the spec and PB3989 leave it open. With ON SIZE ERROR GnuCOBOL stores 003 too, against rule 6 c);
  there ISO decides and WiseOwl keeps 777.
- **Witness shapes.** Goldens `14.9.12-DIVIDE/pb3975_remainder_after_quotient_size_error` (2002, 2014, 2023) and
  `..._standard_decimal` (2014, 2023); `pb129_remainder_no_phrase` then expects R2=0001 (GnuCOBOL prints the same);
  `SizeErrorDispositionTests` rows `DIVIDE 4003 BY 2 GIVING A REMAINDER R` (both lanes).
