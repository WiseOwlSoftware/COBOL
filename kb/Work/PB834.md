# PB834 — OPEN — the class-pointer / class-object formal carrier is the STRING carrier, so a nested CALL passing one does not compile

Found 2026-09-13 by the `PB640` implementer (report § "New defects found outside my mechanism", item (a)), while
verifying §14.2.3 GR9's four conversion legs on the ACTIVATING side. GR9's SET leg — "if the formal parameter is
of class index, object, or pointer, a SET statement" — is verified for class INDEX (golden row `IDXLEG`) and is
NOT verifiable for class OBJECT or class POINTER, because the program that would exercise it does not compile at
all. Allocated by the train-31 lander, which transferred `GR-14.2.3-9` and `GR-14.2.3-10` here from `PB640` and
flipped that note to `landed`: PB640's own mechanism (the numeric crossing performed by the activating element,
checkable there, raising EC-SIZE-TRUNCATION under `>>TURN EC-SIZE CHECKING ON`) is closed and its goldens ship,
and the two rows stay PARTIAL for a reason OUTSIDE it — which is this note.

## The repro

`scratchpad/PB640/probe10.cob`: a nested `CALL "SUB" AS NESTED USING BY REFERENCE PTRV` where the argument is
`01 PTRV USAGE POINTER` and the callee's formal is `01 LPTR USAGE POINTER`; and the same shape with
`USAGE OBJECT REFERENCE cls`. Both `BY REFERENCE` and `BY CONTENT` fail, and they fail in the C# compiler rather
than in any COBOL screen:

- `error CS0029: Cannot implicitly convert type 'string' to 'CobolNet.Runtime.ManagedPointer'`
- `error CS1061: 'string' does not contain a definition for 'SHOW'`

Harm: **rejects legal source**, with a raw Roslyn error and no COBOL diagnostic — the two worst properties a
rejection can have together. `CallBinder` already screens §14.8.2.3.2's restricted-pointer sentence, so the
binder DELIBERATELY ACCEPTS this pairing; nothing downstream declines it either, it simply emits C# that will
not build.

## The mechanism

The CALLEE-side formal carrier for a class-pointer / class-object formal is emitted as the STRING carrier:
`__lnkp0` comes out a `ManagedPointer<string>`, so the generated `__lnkp0.Value` is a `string` where a
`ManagedPointer` (class pointer) or a class instance (class object) is required. The carrier choice is made where
the formal parameters are adopted, beside the `RuntimeApi.ArgAdaptNum` / `ArgAdaptText` calls, and the matching
`CobolArgAdapt` arms do not exist at all — this is the ARGUMENT direction of the
`StoreReturn(ManagedPointer)` / `StoreReturn(ProgramPointer)` overloads PB133 wave B already landed for
RETURNING, which is why the return path works and the argument path does not.

## The rule

§14.2.3 GR8 — the formal parameter "operates as if the formal parameter occupies the same storage area as the
argument" — and GR9's SET bullet, "if the formal parameter is of class index, object, or pointer, a SET
statement" (both `cite.py`-verified in the PB640 report). §14.8.2.3.2's restricted-pointer sentence is a separate
screen and is already enforced.

## Code sites

- `src/Cobol.Net.Compiler/CodeGen/ProgramEmitter.cs` — the formal-carrier adoption (beside
  `RuntimeApi.ArgAdaptNum` / `ArgAdaptText`).
- `src/Cobol.Net.Runtime/Control/CallAbi.cs` — the missing `CobolArgAdapt` arms for `ManagedPointer` /
  `ProgramPointer`, the argument-direction twin of PB133 wave B's `StoreReturn` overloads.

## The rows

`GR-14.2.3-9` and `GR-14.2.3-10` are both PARTIAL and say so in their own notes: every other leg of both rules is
verified (the no-conversion first branch, the numeric COMPUTE leg on both dispositions, the class-INDEX SET leg,
the ANY LENGTH leg, the elementary DYNAMIC LENGTH leg, the MOVE leg, and the INVOKE lane of GR10), and the class
OBJECT / class POINTER SET leg is the single unverified one. Closing this note is what flips both rows to
CONFORMS. ⚠ Note that GR-14.2.3-10's PARTIAL has a second, softer face: the class-object / class-pointer
value-copy carrier is loud-staged at bind with `COBOLNET0899`, so the BY VALUE spelling is a documented
recognized-not-implemented rather than an uncompilable emission — the BY REFERENCE / BY CONTENT nested spelling
above is the one with no diagnostic at all.

## A second lead recorded on the same report, NOT claimed here

(`CobolArgAdapt.Text` / `TextValue` build their digit-image `NumProfile` with `Signed = false` hard-coded and
never read the formal's sign; §14.2.3 GR11 resolves references to data-name-1 "in accordance with their
description in the linkage section", and that description is SIGNED). `01 SM PIC S9(4)V99 VALUE -12.34` passed
BY CONTENT to a REDEFINED (image-carried) formal displays `00123D` where the local control displays `00123M`.
That is a SILENT WRONG ANSWER in a different mechanism and wants its own note; it is written down here so the
lead is not lost.
