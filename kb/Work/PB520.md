# PB520

## Mechanism — data-description-entry-p2
F6 — §13.16.3 SR8's PICTURE-prohibition roster is enforced clause by clause in BindEntry as five separate `if (entryUsage is ... && pictureText is not null)` arms, and the INDEX usage has no arm. A written PICTURE on a USAGE INDEX item is therefore neither rejected nor honoured: BindEntry passes it to PictureAnalyzer.Analyze with Usage.Index and the resulting profile is indistinguishable from the picture-less index item, so the user's declaration is silently discarded. A hand-maintained roster of usages is the wrong shape here — the spec states the prohibition as a SET of usages, and the roster has already drifted once.

### Expected, from the standard
ISO/IEC 1989:2023 §13.16.3 SR8 (cite-checked): "The PICTURE clause shall not be specified for the subject of a RENAMES clause or for an item whose usage is binary-char, binary-short, binary-long, binary-double, float-short, float-long, float-extended, index, message-tag, object reference, pointer, function-pointer, or program-pointer." `01 IX PIC 9(4) USAGE INDEX.` shall be rejected at compile time, in the same band as the sibling usages (COBOLNET0870/0881/0812/1521).

```
$ python scripts/spec/cite.py --check 13.16.3 "The PICTURE clause shall not be specified for the subject of a RENAMES clause or for an item whose usage is binary-char, binary-short, binar..."
  OK  §13.16.3 8)  (Syntax rules)
```

### Observed
Both programs compile clean and print `EQ3` then `LEN=8` — the illegal PIC 9(4) has no effect whatsoever and draws no diagnostic. The roster's other members ARE screened and cite this very rule: BINARY-CHAR/-SHORT/-LONG/-DOUBLE at DataBinder.cs ~2447 (COBOLNET0870, 'ISO §13.16.3 SR8'), PROGRAM-POINTER/FUNCTION-POINTER at ~2459 (COBOLNET0881, 'ISO §13.16.3 SR8'), OBJECT REFERENCE at ~2428 (COBOLNET0812), POINTER at ~2482 (COBOLNET0881), the float family at ~2579 (COBOLNET1521). INDEX is the one usage that instead falls into the `pic = pictureText is not null ? PictureAnalyzer.Analyze(...)` head of the chain at ~2591. The message-tag member of the roster is currently unreachable for a different reason — `USAGE MESSAGE-TAG` does not parse at all (COBOL0001 'no viable alternative at input MESSAGE-TAG'), a §13.18.60 gap that will surface this same missing arm when the usage lands. The RENAMES-subject member is satisfied structurally: `renamesClause` is a whole alternative of `dataDescriptionBody` (CobolData.g4:231-235), so no PICTURE can be written on a level-66 entry.
