# PB3261 — MOVE receiving-subscript evaluated before sending reference modifier

**Mechanism.** `MOVE X(1:L) TO T(I)` is emitted as `CobolTable.At(TB.T, CobolTable.Occ(I, _P_3)) = CobolString.Store(CobolString.RefMod(X, ...), 4)`. C# evaluates the ref-returning left operand first, so the receiving subscript is range-tested before the sending reference modifier is evaluated. When both are out of range the wrong exception condition is raised and the wrong USE declarative is selected.

**Repro.** `E:\COBOL-coord\scratch\w1091\w1091e\probe\p8gr11.cob` at `--std 2002`, I=9 (T OCCURS 3), L=50 (X is X(8)). `MOVE X(1:L) TO T(I)` runs `SEL EC-BOUND-SUBSCRIPT`; the correct result is EC-BOUND-REF-MOD. The mirror `MOVE T(I) TO X(1:L)` is already correct. Generated C#: `p8gr11.g.cs:220` in that probe folder.

**Rule.** §14.9.25.4 1): "the reference modifier, subscript, or function-identifier is evaluated only once, immediately before data is moved to the first of the receiving operands" (`cite.py --check 14.9.25.4` OK, re-run for this note). Declarative selection is §14.9.49.4 GR11 as cited by the PB370 implementer report w1091e; the clerk did not re-derive that number. Open question for the implementer: run `cite.py --check` on the GR11 clause before it enters a code comment or golden.

**Code site.** `src/Cobol.Net.Compiler/CodeGen/` MoveEmitter's store path (the `<ref> = <value>` shape); the store builder is the one place to fix (evaluate the sending operand, then the receiving address). The implementer locates the exact member (`python scripts/spec/where.py 14.9.25.4`).

**Siblings to sweep (every `<ref> = <value>` store whose receiver is subscripted, reference-modified or ODO).** `ReceivingStore`, the arithmetic GIVING/COMPUTE receivers, SET, STRING/UNSTRING INTO.

**Fix shape.** One store primitive that evaluates the sending side first, shared by every receiver arm (rule 5: not a per-verb patch). Goldens: a two-order MOVE (both out of range, each order), in a program and with the GIVING/COMPUTE siblings. Fixing it lets PB370's GR-14.9.49.4-11 close.

## Landing (wave 1102 G, branch worktree-wf_0119da77-f35-13)

**Re-probe (reproduced on this build).** `p8gr11.cob` at `--std 2002`: `MOVE X(1:L) TO T(I)` ran `SEL
EC-BOUND-SUBSCRIPT`. The sibling probes (`sib.cob`, `sib3.cob`, `sib4.cob` in the w1102g scratch `probe` directory)
found three more arms on the same root, each selecting EC-BOUND-SUBSCRIPT where the sender's EC-BOUND-REF-MOD occurs
first: `MOVE X(1:L) TO N(I)` (numeric receiver), `STRING X(1:L) DELIMITED SIZE INTO T(I)` (the STRING emitter read
identifier-3 into its working image before any sender) and `ADD FUNCTION NUMVAL(X(1:L)) TO N(I)` (the in-place
combine read N(I) first, and the store identified it first). The note's mirror, `MOVE T(I) TO X(1:L)`, was right only
by accident: the splice converts the receiver's start and length before its value argument, and only the length test
sits after the value. `INITIALIZE T(I) REPLACING ... BY X(1:L)` selects EC-BOUND-SUBSCRIPT, which is right (below).

**Rule.** §14.9.25.4 GR1 (MOVE: identifier-1's reference modifier, subscript or function-identifier "is evaluated only
once, immediately before data is moved to the first of the receiving operands", and "Item identification for
identifier-2 is performed immediately before the data is moved to the respective data item"); §14.7.7 rule 4
(arithmetic: the initial evaluation first, then "Item identification for the receiving data items is done as each data
item is accessed"); §14.9.39.4 GR12 / GR14 / GR16 (pointer-family SET: the receiver is identified "immediately before
the value of that data item is changed"); §14.6.4 7) for STRING and INITIALIZE, which give no timing of their own
("the identifiers within a statement are evaluated in left to right order as the first operation of the execution of
that statement"); §14.9.49.4 GR11 makes the order observable. Every clause `cite.py --check` OK.
⚠ DETERMINATION (INITIALIZE): §14.6.4 7)'s left-to-right order identifies identifier-1, the receiver, before the
REPLACING phrase's sending identifier, so the receiver's condition is selected first. Rejected reading: GR4's implicit
MOVE carries §14.9.25.4 GR1's sender-first order into INITIALIZE (the implicit statements act on items the INITIALIZE
statement has already identified).

**Fix.** `PlaceIdentification.SenderFirst(sender, receiver, value, store)` is the one sender-first store: when both
`IdentifiesAtRunTime` answers are true it renders `{ var __sending = <value>; <store(__sending)> }`, else the store as
it was. `IdentifiesAtRunTime(Place)` asks Freeze itself whether it would hoist a fragment, plus an occurs-depending
length and an omitted-formal guard; `IdentifiesAtRunTime(BoundOperand)` is false only for literals, figuratives, NULL
and a refused operand. Every MoveEmitter store arm (elementary, slice, group image, group leaves, group to elementary,
variable-length group) renders through it, decided once per receiver in `EmitReceiver` (receiver first for INITIALIZE,
`ImplicitMovePhrase.ReceiverIdentifiedFirst`, and for an overlap prefill). SET's data-, function- and program-pointer
stores route through `SetEmitter.StorePointer` (one receiver; several were already evaluated once by `SendOnce`). The
arithmetic statements materialize the initial evaluation for one receiver that identifies at run time
(`ArithmeticEmitter.MaterializesInitialEvaluation`, beside the several-receiver case it always covered). STRING reads
each sending operand and delimiter that identifies at run time, in statement order, before identifier-3 and before
the POINTER value. Found on the way (I9): `SetEmitter.EmitSetProgramPointer` cited §14.9.39.4 GR18 (Format 10,
EC-DATA-PTR-NULL) for Format 9's rule, GR16; corrected.

**Golden.** `conformance:2002/pb3261_sender_first_order` (PB3261SF): thirteen statements failing on both sides, the
nonfatal-first EVALUATE shape and in-range value legs; expected values from the rules above. No negative: the
evaluation order is not edition-gated, and the 2002 exception facility it rides is already refused at 85
(`negative/pb1036-sort-merge-turn-at-85` and its siblings).

**Rows.** Batch `w1102g-pb3261`: GR-14.9.49.4-11 PARTIAL → CONFORMS, GAP 60 → 59.
