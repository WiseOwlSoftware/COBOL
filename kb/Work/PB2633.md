**Rule it breaks:** ISO §15.8.4 r1 (the ACOS returned value is in [0, pi]) and §14.7.4.3 r2 (no ROUNDED phrase = truncation); loud failure / no silent overflow (DESIGN-architecture-review §5, engineering-standards). Pow10.AsWide documents its range as 0..38 but its out-of-table fallback loop multiplies past 10^38 unchecked.

**Scenario:** 01 R2 PIC S9PP. 01 U2 PIC 9PP. 01 X PIC S9V9 VALUE 0.5. COMPUTE R2 = FUNCTION ACOS(X). COMPUTE U2 = FUNCTION ACOS(X). Run with the pin's built cobol.exe (src/Cobol.Net.Cli/bin/Debug/net10.0, --run): DISPLAY shows R2=J (overpunch -1, i.e. -100) and U2=1 (100); the correct landing of 1.047 truncated to hundreds is 0 (R1 PIC S9P and R0 PIC S9 land correctly: 0 and 1). Mechanism: the receiver scale is -2 (PictureAnalyzer.cs:378 scale = -trailingP); FromDoubleBounded computes limit = CodomainPi37 / Pow10.AsWide(37 - (-2)); AsWide(39) runs the fallback loop and wraps to -2.08e37, so limit = -1 and `q > limit ? limit` returns -1 for every q >= 0. No size error, no EC, under any ROUNDED mode: the clamp runs whenever the catalog row has a codomain (IntrinsicRenderer.cs:780), not only under ROUNDED. Computed for every negative scale: only Pi at -2 (limit -1) and -11 (limit +1) go wrong today, which is luck of the wrap, not design.

**Measured how:** R2 batch finding `runtime-values-1--code--f2#1` (pair runtime-values-1--code), read in the pinned tree at 8be23006851a; skeptics rule upheld, scenario upheld, site upheld.

**Spec:** §15.8.4 "The returned value is the approximation of the arccosine of argument-1 and is greater than or equal to zero and less than or equal to" (`cite.py --check` passed at collection); §14.7.4.3 "If the ROUNDED phrase is not specified, execution is as if ROUNDED MODE IS TRUNCATION had been specified" (`cite.py --check` passed at collection)

**Target:** FromDoubleBounded treats scale <= -1 explicitly (every codomain bound is < 10^38, so the limit at a non-positive-power scale is floor(bound / 10^(37-scale)) = 0 for scale <= -1, computed without a power past 10^38), and Pow10.AsWide fails loudly for an exponent outside 0..38 instead of wrapping (the same hardening PB648 plans for a negative exponent), with a unit row for scale -2 on each codomain constant and a golden COMPUTE into PIC S9PP / 9PP.

**Design reference:** PB648.

## Landed (wave 1042 group E, 2026-10-08)

Re-probed: `COMPUTE R2 = FUNCTION ACOS(X)` with `R2 PIC S9PP` stored J (-100) before the change and `{` (zero hundreds) after.
`FromDoubleBounded` now treats a negative scale explicitly (every codomain constant is a scale-37 value below 10^38, so the
limit at scale <= -1 is 0 and the divisor is never formed past 10^38). `Pow10.AsWide` and `Pow10.FiveAsWide` now THROW
`ArgumentOutOfRangeException` outside their tables (0..38 and 0..54) instead of wrapping the Int128 or answering 1 for a
negative exponent (the hardening PB648 asked for; PB648's own text names the same two methods, and this change makes its
fix true). Cites checked: 15.8.4 r1, 14.7.4.3 r2.

The hardening FOUND TWO MORE SILENT CALLERS, fixed here (I9): (1) `CobolDec.Div` with a 39-digit numerator (an Int128
significand reaches 1.7E+38): `38 - digits` is -1 there, `AsWide(-1)` multiplied by 1 while the quotient exponent still
counted the step, so the quotient came out ten times too large (found when `CobolNumDivideAlignmentTests` threw); the first
pre-scale step is clamped to zero. (2) A TRAILING-P seconds argument (`PIC 9(3)PP` holding 36000 is the unscaled 360 at
scale -2) reached `CobolDate.EmitFormatted`, `CombinedDatetime` and `CobolLocale.TimeFromSeconds`, which divided by
`AsWide(-2)` = 1, so FORMATTED-TIME rendered 00:06:00 for ten o'clock; `CobolDate.WholeSecondsAtScale` reads such an argument
as whole seconds AFTER the 7.3.17.4 screen (so the product cannot leave the carrier), and COMBINED-DATETIME's emitted result
scale is `max(0, scale) + 5`. Tests: goldens `conformance:85/pb2633_codomain_bound_trailing_p_receiver` (ACOS and ASIN into
S9PP, 9PP, S9P and S9P(11), truncated and ROUNDED, plus the S9 control) and
`conformance:2014/pb2633_trailing_p_seconds_argument` (FORMATTED-TIME, FORMATTED-DATETIME, COMBINED-DATETIME);
`unit:Pow10RangeTests` (both tables' edges, the clamp's limit for every codomain at every scale -31..31, the 39-digit
division), `unit:CobolLocaleTests.TimeFromSeconds_ATrailingPArgument_IsWholeSeconds`. Sibling sweep: all 46
`AsWide(` callers in `src/` were read; the ones that can see a scale difference or a user scale are guarded or fixed above, and
the full Unit (32,798) and Conformance (11,239) populations ran green on this tree before the date edits and again after.

## Landing

- `src/Cobol.Net.Runtime/Values/Numeric/Pow10.cs#AsWide` / `#FiveAsWide` THROW outside their tables: a new `AsWide(expr)` caller must bound `expr` where the scale is known. `CobolIntrinsics.cs#FromDoubleBounded` treats scale < 0 explicitly.
- `src/Cobol.Net.Runtime/Intrinsics/CobolDate.cs#WholeSecondsAtScale` is the ONE reader of a seconds argument's negative (trailing-P) scale; call it AFTER the 7.3.17.4 screen. `IntrinsicRenderer`'s COMBINED-DATETIME arm reads the result at `Math.Max(0, scale) + 5`.
- Trap: `CobolDec.Div` pre-scale (`k`) must be clamped at zero for a 39-digit numerator; `RuntimeApiGuardTests` counts a bare `CobolX.` even in a TRAILING comment on a code line.
