# PB5477 - a level-66 RENAMES of one numeric integer item used as a subscript (ELT (RN)) generates C# that does not compile (CS1061, CS0103): the subscript read names the alias as a member of its record

**Sites:**

- `src/WiseOwl.Cobol.Compiler/Binding/SubscriptBinder.cs` (`SubscriptBinder.ResolveSubscriptName`, `SubscriptBinder.PositionRead`); `src/WiseOwl.Cobol.Compiler/Binding/Model/DataItem.cs` (`DataItem.AttributeItem`, `DataItem.OwnsNoField`: the model-layer reads of the RENAMES descriptor, since `RenamesPlaceBuilderDriftTests` keeps the resolver from reading it)
- `tests/version-matrix/inventory-1985/1985-SR-IV.4.3.8.2.3-5.json` (the re-verdicted row); `conformance-suite/cases/IV.4.3.8.2@1985-Subscripting/1985-SR-IV_4_3_8_2_3-5-renames-alias.cob` (the witness)

**Mechanism.** A 66 RENAMES of one item takes "all of the data attributes of data-name-2" (§1985:VI.5.11.4 GR2), so `66 RN RENAMES GA` (GA PIC 9) is a numeric elementary integer item and a legal subscript (SR5). Everywhere else the alias resolves to the renamed item (`DISPLAY RN`, `ADD 1 TO RN` and `MOVE RN TO W` render `GR.GA`), but the subscript read `SubscriptBinder.ResolveSubscriptName` / `PositionRead` builds renders `CobolTable.Occ(GR.RN, _P_5)`: the alias as a member of its record and a numeric profile that was never declared. The backend refuses the generated C#, so legal source fails with no COBOL diagnostic. It fails the same way at --std 2023. kb/Work PB5335 (landed) fixed the same alias confusion for a group RENAMES in a CALL.

**Found by.** The 1985 code read, read 4 (`kb/Work/PB4996/2026-11-13-read-4.md`): the refuter of `E:/COBOL-coord/scratch/coderead-85/out-read4/rd-04-refute.json` OVERTURNED the read's CONFORMS of 1985-SR-IV.4.3.8.2.3-5 (the refusal half conforms).

**Inventory.** `work.py check` refuses a 1985 rule id in `inventory_rows` (kb/Work PB5094, open), so `inventory_rows` is empty and the rows this note claims are the rule ids below. Its rows are recorded naming this note (records-rd4).
