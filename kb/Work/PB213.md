# PB213

Found and CLOSED by the PB169–PB172 burn-down cluster (2026-08-31); registered because CLAUDE.md rule 8 wants
a defect to be a note before it is a DEVLOG paragraph, even when it is opened and closed in one change set.

MEASURED on 9a89fbd1, not deduced: with `01 IDX USAGE INDEX.`, `SET IDX TO 2` then `COMPUTE N = IDX + 1`
compiled clean under STRICT and printed `N=0003`, and `MOVE E(IDX) TO R` indexed occurrence 2.

MECHANISM. An index data item's `PicInfo` carries category NUMERIC for the storage model
(`PicInfo.IndexItem`), so `ExpressionBinder.NonNumericOperandKind`'s category-keyed arms could not see it and
its `_ => null` default meant "admissible". §8.5.2.1 Table 2 puts an index data item in class INDEX, and
§13.18.60.3 SR10 (`cite.py --check` → OK) closes its reference contexts to "a SEARCH or SET statement, a
relation condition, an intrinsic function argument" — no arithmetic-operand entry, no subscript entry.
`IntrinsicArgumentRules.ClassOfPlace` had keyed `Usage: Usage.Index` → `CobolClass.Index` correctly all along,
BEFORE the category table, and the receiving-side twin `ScreenResultant` rejected an index resultant by name.
Two arms of one rule; one written.

CLOSED BY: expressing §8.8.1.1 as `IsArithmeticOperandClass` over `IntrinsicArgumentRules.CandidateClasses`
(the ONE §8.5.2.1 Table-2 classifier) and deleting the private switch's verdict role. The index arm — and the
pointer and object-reference arms, which the same `_ => null` also admitted silently — fall out with no new
rule, which is the rule-5 test: the shape that makes the next case automatic. Pinned by
`negative/pb170-compute-index-data-item`, `negative/pb170-subscript-index-data-item` and
`ArithmeticOperandClassTests.Strict_RejectsAnIndexDataItemAsAPositionOrArithmeticOperand` at all four editions.

⚠ **AND THE FIRST FIX OVER-REACHED, which is recorded here because the correction is the interesting part.**
Deriving the answer from the class screen alone ("class index is not class numeric") also rejected
`SET IN1 TO IDN1` in EIGHT NIST programs -- IC106A, IC107A, IC207A, IC208A, NC131A, NC133A, NC135A, NC236A --
every one a SET statement that §13.18.60.3 SR10 names outright. SR10 ENUMERATES CONTEXTS ("a SEARCH or SET
statement, a relation condition, an intrinsic function argument, an inline method invocation argument, the
USING phrase of a procedure division header, or the USING phrase of a CALL or INVOKE statement"), so it is a
THIRD axis of the operand context, not a property of the operand
(feedback_model_the_rule_shape_not_one_case). `OperandContextRules.Rules()` now declares it as such. The
residual -- one enum member serving sites that r7 lists and SR10 does not -- is [[PB215]].
