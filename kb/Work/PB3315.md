# PB3315 — the rendered-views audit is slow in the gate's pre-slot path

## Found (finisher w1105f, PB3270, 2026-10-16/17)
Report: `E:\COBOL-coord\scratch\reports\w1105f-PB3270-report.md` line 59. With about 10 gates running on the machine,
the gate's pre-slot `audit RENDERED VIEWS` step took far longer than the rest of the pre-slot work (the self-tests ran
139 s in total). Both logs print the step line right after the self-tests verdict:
- `E:\COBOL-coord\scratch\w1105f-finisher-gate.log` line 198: `--- audit RENDERED VIEWS (1687.4s) ---`
- `E:\COBOL-coord\scratch\w1105f-finisher-gate2.log` line 198: `--- audit RENDERED VIEWS (1210.4s) ---`

In both runs nearly all of the time was `scripts/rendered_views.py --check` waiting on `scripts/spec/gen_ledger.py
--check`. The first run exceeded the harness's 30-minute default background limit and was killed before it took a gate
slot, so the finisher lost the whole gate; the second added about 20 minutes to a gate that then took slot 3 of 3 with
no wait. The cost is paid before the slot, so the slot cap does not bound it, and every gate pays it.

## Code sites (re-checked in the worktree at origin/main 8b6afe349)
- `scripts/spec/gen_ledger.py:147` `git()`: one `subprocess.run(["git", ...])` per call.
- `scripts/spec/gen_ledger.py:416-422` `notes_at`: reads the register at a commit through `git cat-file --batch` (the
  subprocess is at `:422`); `:447` is a further `git cat-file --batch-check`; `:414-418` is the `git log --stdin`
  walk of recorded commits. The report's `:416-469` range covers these.
- `scripts/rendered_views.py --check` (registry `VIEWS`, PB3026) runs `gen_ledger.py --check` as one of its six views.

Not yet measured: how many git subprocesses one `--check` spawns, and how the wall time divides between spawn cost,
the `git log` walk and the per-point `notes_at` reads under contention.

## Fix shape (for the implementer to confirm)
1. Measure first: count the git subprocesses of one `gen_ledger.py --check` and time them idle versus under load
   (about 10 concurrent gates), so the cost is attributed to spawn count, the history walk, or contention.
2. Then make the check cheap (fewer subprocesses, one long-lived `cat-file --batch`, reuse of the recorded series,
   memoising by the commit it already keys on) or move it out of the pre-slot path (for example into leg 1 inside the
   slot, or CI), keeping the PB3026 guarantee that every view renders.
3. Never a longer timeout. Add a structural guard (a subprocess-count bound, not a wall-clock one).

Related, not the same mechanism: PB3026 (the rendered-views registry), PB3068.
