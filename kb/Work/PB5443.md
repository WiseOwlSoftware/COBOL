# PB5443 - a GATE-PENDING group with a live gate is not a settled group

**Site.** `scripts/orchestrator/progress.py`, the per-group loop in `progress()`. A report whose status is not DONE is
counted `groups["other"]` (around line 237) and never adds its wave to `wave_running`. The DONE arm asks
`implementer_activity(r.worktree)` for a live gate lock; the GATE-PENDING arm does not. The gate's heartbeat lands in the
worktree's TestResults `gate.log`, not in the coordination scratch, so no act is seen either. The orphan list (around lines
272-273) takes the queued groups of a begun wave that are not in `wave_running`.

**Failure scenario.** Wave 9, group A has a GATE-PENDING report written 150 minutes ago, naming a worktree whose gate lock is
HELD (a live gate). Group B has no report and no act. `progress()` returns running 0, other 1, queued 1, orphans [w9b].
`progress.py --record` (`answer_orphans`) then writes a NOT STARTED report for B and releases its notes to `plan_wave`,
although the rolling wave still holds B in its queue and starts it when A's gate await (`awaitGate`, up to about 243
minutes) ends. Two implementers then work the same notes.

**How rare.** Every started group of the wave must be in that state (likely only at a gate cap of 1 or after several
turn-cap returns), and the gate must be more than 120 minutes past the last act. The reviewer's probe is
`E:/COBOL-coord/scratch/review-w20262008-a/orphan_probe.py`.

**Fix direction.** Count a report whose worktree holds a live gate (`implementer_activity`, as the DONE arm does) as
running for its wave, or derive `wave_running` from every group whose report is not settled (GATE-PENDING with a running
gate). Add the scenario as a `progress.py --self-test` case.
