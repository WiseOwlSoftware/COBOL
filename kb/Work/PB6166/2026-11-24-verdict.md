# PB6166 verdict — CONFORMS: a BEFORE write after an AFTER write presents on the same line (an overprint) in every edition

# PB6166 — verdict: CONFORMS (1985, 2002, 2014, 2023)

**Question.** At `--std 85`, after `WRITE ... AFTER ADVANCING n`, does a following `WRITE ... BEFORE ADVANCING m` present
its line on the line the AFTER write printed (an overprint) or on a new line?

**Answer.** On the same line. The standard's device model moves the representation of the printed page only by an
advance; presenting a line does not move it. The AFTER write advances and then presents, so the device stays on that
line. The BEFORE write presents first, so it presents on that same line, and only then advances. The runtime's bare
carriage return before the second record is that overprint. Every edition states it the same way; none leaves the
vertical position to the implementor. Only the device representation (CR) is implementor-chosen, and that choice is
already recorded (docs/CONFORMANCE.md "ADVANCING 0", kb/Work R54, PB1667).

## 1985, from its own text

Every citation below was checked with `python scripts/spec/cite.py --check` (verdict `OK` for each). The 1985 rendering
of PDF page 429 (folio VII-55) was read and matches the transcription of GR16 b–h. The Amendment 2 renumbering (Errata
C264/C265) is already applied, so the rule cited as GR16 is the one printed as (15).

- §1985:VII.4.7.4 GR16f: with AFTER, "the line is presented after the representation of the printed page is advanced".
  So after `WRITE P1R AFTER ADVANCING 2 LINES` the device has advanced 2 lines and presented ONE where it now stands.
- §1985:VII.4.7.4 GR16e: with BEFORE, "the line is presented before the representation of the printed page is advanced".
  Nothing between the two statements advances the page, so TWO is presented where the device stands, which is ONE's line.
- §1985:VII.4.7.4 GR16c: an amount of zero means "no repositioning of the representation of the printed page is
  performed". The rules therefore separate repositioning (the amount) from presentation. A zero-amount write lands on the
  line already there. That is only coherent if presenting a line does not itself move the device.
- §1985:VII.4.7.4 GR16: with no ADVANCING phrase the implementor acts as if AFTER ADVANCING 1 LINE was specified. This
  shows the same model. If presentation advanced the device, every plain WRITE would double-space.
- The page and line model. §1985:VII.3.7.4 GR9: LINAGE-COUNTER "represents the line number at which the device is
  positioned within the current page body". By §1985:VII.3.7.4 GR9c2 it changes only by the ADVANCING amount ("the
  LINAGE-COUNTER is incremented by integer-1"), whether BEFORE or AFTER, and never because a line was presented. After
  OPEN (counter 1) and AFTER 2 the counter is 3, and ONE was presented at line 3. The BEFORE write that follows presents
  at the position the counter names, line 3, and then increments. The LINAGE model says the same line.
- PAGE. §1985:VII.4.7.4 GR16h: without LINAGE, the record is presented on the physical page before or after
  repositioning. The repositioning technique is implementor-defined, but the record's own position is not: under BEFORE
  it is the current line. The repro's `BEFORE ADVANCING PAGE` is therefore the same overprint.
- The device. §1985:C.3 item 19 lists BEFORE/AFTER ADVANCING as dependent on a device capable of vertical positioning.
  That makes the physical rendering hardware-dependent (CR for "same line, column 1"). It does not make the position
  hardware-dependent.

**1985 answer:** the same line, an overprint.

## 2002, from its own text

§2002:14.8.47.3 GR21e and GR21f carry the 1985 wording of e and f; GR21c carries the zero-amount rule; §2002:13.16.32.3
GR7 carries the LINAGE-COUNTER device-position definition. GR21 adds that a physical file without vertical positioning
ignores the ADVANCING and END-OF-PAGE phrases (§2002:14.8.47.3 GR21, checked). That changes nothing for a print file.
**2002 answer:** the same line.

## 2014, from its own text

§2014:14.9.47.3 GR22e, GR22f and GR22c, and §2014:13.18.34.3 GR7, use the same wording (checked; 2014 is in cite.py label
mode). **2014 answer:** the same line.

## 2023, from its own text

§2023:14.9.51.4 GR25e and GR25c are unchanged. §2023:14.9.51.4 GR25f is new: it adds the case of BEFORE and AFTER in
ONE statement ("If the AFTER phrase is used and the BEFORE phrase is also used": present per e, then advance). That is
a single-statement form and does not change the two-statement sequence asked here. §2023:13.18.34.4 GR7 keeps the
LINAGE-COUNTER definition. **2023 answer:** the same line. This was already decided for 2023 in kb/Work PB1840 (landed
2026-10-18) and is documented in docs/CONFORMANCE.md "A line presented onto an open line is the same overprint".

The bytes are byte-identical to the refuter's run r4-001.

- `AFTER ADVANCING 2` is two line ends, then ONE, and the line stays open (`DeviceLine.Open`).
- `BEFORE ADVANCING PAGE` is a CR (same line, column 1, so TWO overprints ONE), then TWO, then the form feed (GR16h,
  no LINAGE).
- The plain WRITE (implicit AFTER 1) is one line end, then THREE: line 2 of the new page, as GR16 requires.
- The LINAGE file is outside the question but is consistent. L1 goes on line 2 (AFTER 1 from line 1). AFTER PAGE is
  4 line ends to line 1 of the next 5-line page (GR16g).

**Code site.** `src/WiseOwl.Cobol.Runtime/IO/SequentialConnector.cs`:

- `Present`: `if (_device == DeviceLine.Open) _writer!.Write('\r');` gives a presentation onto an open line the overprint.
- `WriteTravel` and `AdvanceLines`: a positive travel clears the device to `Fresh`; a zero amount returns it (`Returned`).
- `Advance`: PAGE writes `\f`.

The three-state `DeviceLine` is the one representation of the model above. Exception, by design: a line-sequential file
before 2023 (`LineDelimiterOnlyFrames`, kb/Work PB5984) presents each record as its own line, because that medium is
not a vertically-positioning device. That does not apply to the repro's print file and has no 1985 analogue (1985 has
no LINE SEQUENTIAL).

**GnuCOBOL** (a regression net only; not re-probed here, because `cobc` is not on this host). PB1840 recorded that
GnuCOBOL appends the BEFORE record to the open line's text (`ONETWO`). The standard states the position, so rule 1's
precedence does not reach GnuCOBOL. That difference is a known, documented deviation by GnuCOBOL, not by WiseOwl.

## Disposition

- CONFORMS in all four editions. No code change.
- Row `1985-GR-VII.4.7.4-16`: this observation gives no GAP for it. Flip PB6166 to `status: closed` (adjudicated, no
  defect), with `closes_rows: []` unless the row's other sub-rules are judged elsewhere: this verdict covers GR16 c, e,
  f and h only as they bear on the mixed BEFORE-after-AFTER sequence.
- The 1985 reading follows PB1840's 2023 reading. Add §1985:VII.4.7.4 GR16e/f to the docs/CONFORMANCE.md "open line"
  paragraph so the 1985 basis is stated in the same place.
