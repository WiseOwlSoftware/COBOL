# PB472 — OPEN — the inventory has one file writer and two row shapes

Surfaced 2026-09-04 by the `PB386` landing, which added `derivation` as a sixth `ADJUDICATED` field. ⚠ **The
mechanism below was re-derived and demonstrated on this tree for this note**; the anecdote it was dispatched with
— that PB386's lander had to run `build_inventory.py` after `record_verdicts.py` to restore one shape — is
consistent with the code but is *not* recorded in DEVLOG entry 1453 or in the implementer's report, which mention
`build_inventory.py` only as the round-trip proof that the new field survives a rebuild. The defect is the code,
and it stands on its own.

## The two writers

**`scripts/spec/build_inventory.py`** constructs each row as a fresh literal — the canonical skeleton, every field
on every row, in one fixed order:

```python
row = {
    "rule-id": …, "section": …, "kind": …, "ordinal": …, "subject": …,
    "verdict": "", "code-location": "", "test-ref": "", "derivation": "", "editions": "", "notes": "",
}
…
row["state"] = schema.state_for(row)
```

**`scripts/spec/record_verdicts.py`** never builds a row. It loads the JSON and mutates in place:

```python
for field in ADJUDICATED:          # ("verdict","code-location","test-ref","derivation","editions","notes")
    row[field] = rec.get(field, "")
row["state"] = schema.state_for(row)
```

A Python dict preserves insertion order, so assigning a key the loaded row does **not** already carry **appends**
it — after `state`, which the skeleton writes last. Demonstrated, on a row shaped as an inventory generated before
`derivation` existed:

```
skeleton  : [… 'test-ref', 'editions', 'notes', 'state']
after RV  : [… 'test-ref', 'editions', 'notes', 'state', 'derivation']
divergent : True
```

`inventory_schema.write_inventory` is a single, careful, atomic **file** writer — but it serializes whatever dict
it is handed, so the divergence passes straight through it. There is **one file writer and no row serializer**,
and that is the whole of the defect.

## What it costs

The moment a new `ADJUDICATED` field is introduced, the 4,311-row file splits into two shapes: rows a batch
touched carry the field in one position, rows it did not carry it in another (or, for a field added without a
rebuild, not at all). Consequences, in order of how much they cost a reader:

* **The diff of a routine landing becomes unreadable** — every touched row re-serializes with a moved key, so the
  batch's real content is buried in shape churn, and a reviewer cannot see which verdicts actually changed.
* **A rebuild is silently required after every field addition**, and nothing says so. The recovery
  (`build_inventory.py` after `record_verdicts.py`) is folklore, not a step in any brief or gate.
* **Two shapes in one file is the condition every reader has to tolerate** — the C# gates, `gen_ledger.py`,
  `audit_annex_a1.py`. They read by key so they survive it, which is exactly why nothing goes red and the
  divergence can sit there.

Measured on this tree **after** the PB386 landing: all 4,311 rows currently carry one identical key sequence
(`rule-id, section, kind, ordinal, subject, verdict, code-location, test-ref, derivation, editions, notes,
state`). So the file is *clean today* — which is the point. Nothing asserts that it stays clean, and the next
`ADJUDICATED` field re-opens it.

## Fix shape

1. **One row serializer in `scripts/spec/inventory_schema.py`**, next to `write_inventory` and derived from the
   schema rather than typed twice — the canonical key sequence in one place. `build_inventory.py` builds through
   it; `record_verdicts.py` normalizes through it; `write_inventory` normalizes every row on the way out, so a
   caller that forgets cannot produce a divergent file. This is the shape that makes the **next** field automatic
   (CLAUDE.md rule 5) rather than the smallest diff that fixes `derivation`.
2. **A drift test that would have caught it, and is proven able to fail.** A Python `--self-test` in
   `record_verdicts.py` (or `inventory_schema.py`) that runs the record loop over a row missing a new field and
   asserts the key sequence is unchanged, **and** a C# assertion in `SpecTraceabilityInventoryDriftTests` that
   every row in the live inventory carries the identical key sequence — fired once against a hand-divergent row
   before it is trusted (`green_gates_arent_evidence`).

⛔ **Not fixed by the process-review landing that opened this note** — it is a fix-lane item with its own
implementer. It touches `scripts/spec/` and the Unit test assembly, so it is one mechanism and fits one
implementer under the 220-turn cap.
