# PB106 — LANDED — the collation key cache (`Runtime/Collation/Cache/`)

> ⚙ **flags:** owner-directed 2026-08-18/19 ("hard implementation mode", section 7: `CollationKeyCache.cs`
> (`ConcurrentDictionary<string, CacheEntry>`, `public static CollationKey GetOrBuild(string s)`, LRU or size-based
> eviction configurable via `CacheConfig`), `CacheEntry.cs` (key, timestamp, hit count), `CacheConfig.cs` (max size,
> strategy, enable flag), `README.md` (strategy, performance benefits, integration with `CollationEngine`); section 8
> [1] "use CollationKeyCache.GetOrBuild before building keys") · a performance facility over [[PB101]]'s engine.

## What landed (2026-08-19)

- `CollationKeyCache` — one per `Collator` (`For(collator)`, held weakly; `Shared` = root; the static
  `GetOrBuild(string)`), `GetKey`/`TryGet`/`Compare`, `Count`/`Hits`/`Misses`/`Evictions`, `Entries`, `Clear`;
  `CacheEntry` — key, `CreatedAt`/`LastAccess` (Stopwatch ticks — the runtime reads no wall clock outside the run
  unit's clock seam; the first version's `DateTimeOffset.UtcNow` failed `ClockSeamDriftTests`), `HitCount`; `CacheConfig` — `Enabled`, `MaxEntries` (8,192), `Eviction` (LRU | SizeBased), `MaxTextLength`
  (512), `EvictionFraction` (0.25), `FromEnvironment()` (`COBOL_COLLATION_CACHE`, `COBOL_COLLATION_CACHE_EVICTION`),
  `Validated()`.
- **Eviction, measured twice**: v1 read `ConcurrentDictionary.Count` on every insert (every bucket lock — ~18 µs) and
  `ToArray()`-snapshotted the dictionary (every bucket lock again) per batch: a miss under churn cost **27× a bare
  build**. v2: an interlocked count, and the batch gathered by a lock-free enumeration, sorted by stamp (last access
  for LRU, creation for FIFO), oldest removed — amortized over a quarter of the capacity's inserts: a miss under
  churn now costs **≈1.4× the build** (`CacheBenchmarks`). (A CLOCK second-chance variant was tried in between: cheaper
  still, but only approximately LRU on a burst — the exact-LRU test caught it; the sort is affordable, so exact LRU it is.)
- **Wiring** (the rule the numbers justify — `Cache/README.md` §2): `CobolCollation.SupportsKeys` / `KeyOf`
  (the LOCALE arm keys through the collator's cache after the §8.8.4.2.11 trim; the table arms answer false);
  `CobolSort.KeyColumns` — every record's key columns DECODED ONCE (numeric values, `CollationKey`s under a LOCALE
  sequence, sliced windows otherwise) before the sort/merge compares — n decodes instead of 2·n·log n walks;
  `IndexedConnector.KeyCompare` compares LOCALE-keyed file keys through `KeyOf`; `CollationEngine.GetKey(text, tag)`,
  `Collator.GetKeyCached`. NOT wired into `Collator.Compare` / relation conditions: the streaming comparison of two
  short operands (27 ns) beats two lookups + a key compare (48 ns).
- **Verified**: `CollationKeyCacheTests` (10) — one key per text, counters, LRU keeps the recently used, FIFO
  evicts the oldest, disabled/over-long pass-through, environment config, 4,000 concurrent lookups under eviction
  always correct, per-collator caches apart, `LocaleCollation.KeyOf` ⇄ `Compare` (Danish), a SORT under the Swedish
  sequence orders exactly like a stable sort by `Compare` and keys through the cache. Full unit suite green.
- **Benchmarked** (`CacheBenchmarks`): hit 23.6 ns vs build 214 ns (9×, 0 B); case-different 120-char record pairs
  through keys 196 ns vs 3,245 ns streaming (16.6×); short pairs 48 vs 27 ns (streaming wins); prefix-shared long
  pairs 322 vs 246 ns (streaming wins, the prefix skip).
