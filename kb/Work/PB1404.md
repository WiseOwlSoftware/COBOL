## Finding — `cobol-words` (under-rejects; rows `GR-8.3.2.2-L2.2`)

**Mechanism.** The compilation-group externalized-name check (COBOLNET2213) enumerates only §8.3.2.2 list item 1 (outermost programs, functions, classes, interfaces) — list item 2 (data-names, file-names and record-names of EXTERNAL items) never enters the one namespace, so an EXTERNAL data item sharing its externalized name with a program, or an EXTERNAL file with an EXTERNAL data item, compiles and runs with no diagnostic (a two-arm population: one list modeled, the sibling list not)

**Repro.** out/probe/ext2/kc.cob: PROGRAM-ID. KCMAIN. with `01 KCSUB PIC X(5) EXTERNAL.` + `CALL 'KCSUB'`, and PROGRAM-ID. KCSUB. in the same group -> `cobol kc.cob --std 2023 --run` prints IN KCSUB, exit 0. kc2.cob: `FD KCF IS EXTERNAL.` in KC2A and `01 KCF PIC X(4) EXTERNAL.` in KC2B -> prints B XX, exit 0.

**Expected from the spec.** The same COBOLNET2213 refusal the check already gives a program/function pair: the name KCSUB (resp. KCF) is externalized as a program and as a data item (resp. a file and a data item) — not the same kind of entity or item within the run unit.

**Observed / reasoning.** BinderDriver.CheckDefinitionNameUniqueness builds its population from ExternalizedDefinitions(units, oo), which its own comment scopes to 'outermost program definitions, function definitions, object-class definitions and interface definitions'; EXTERNAL data/file/record names (DataItem EXTERNAL, FD IS EXTERNAL) are never added. Fix: feed list item 2 into the same dictionary (keyed on the AS literal when present, else the word, with the existing NameEq), with a drift test that every §8.3.2.2 externalized kind has a producer.

**Code site.** src/Cobol.Net.Compiler/Binding/BinderDriver.cs#CheckDefinitionNameUniqueness / ExternalizedDefinitions

## What the fixer owes

Feed BinderDriver.ExternalizedDefinitions from the §8.3.2.2 list as DATA (both items), so the one namespace check sees EXTERNAL data/file/record names; state the conflict rule in the diagnostic.

## Landed 2026-10-04 (wave-1012 implementer J)

The compilation-group externalized-name namespace now takes 8.3.2.2's list item 2 as well as item 1. `DataBinder.ExternalizedSubjects` is the one producer of a source element's EXTERNAL data items, records and files (its own 13.18.22.3 SR2 screen now reads it instead of a second hand-built loop) and `BinderDriver.ExternalizedDefinitions` feeds it, for every unit and every class half, into the one dictionary `CheckDefinitionNameUniqueness` keeps. Two EXTERNAL items of one kind under one name are the same instance (the clause: 'they refer to the same instance') and stay legal; different kinds - an EXTERNAL data item against a program, an EXTERNAL file against an EXTERNAL data item - draw COBOLNET2213. Goldens: `2002/pb1404_external_same_kind_is_one_instance`, `negative/pb1404-program-and-external-data-one-name`, `negative/pb1404-external-file-and-external-data-one-name`. No separate drift test was added: each producer arm is pinned by its own negative, and a new externalized kind joins the one `ExternalizedDefinitions` list.
