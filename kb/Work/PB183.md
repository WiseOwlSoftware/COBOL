## The architecture: one enumeration, not a fifth hand-copy at four sites

A pointer usage can be acquired by FOUR routes — a written USAGE clause, §13.18.60.4 GR1 group inheritance, a
TYPE clone, and a SAME AS copy. SR14's drafting twin §13.18.57.3 SR6 is implemented in this tree as TWO
hand-written parent walks (`ExpandType` at DataBinder.cs:1635 and `ExpandSameAs` at :1962, the second commented
"the ExpandType twin"), so writing SR14 the same way would have reproduced that duplication at twice the scale.
Instead the screen runs ONCE over `DataBinder.ConformanceForest()` — the written-entry forest, which walks
`Roots` + `LinkageRoots` + the `TypeDecls` TEMPLATES and PRUNES the TYPE-clone subtrees. All four routes fall to
that one predicate, and a fifth route added later is screened for free.

**The subject test is the spec's own notion of "elementary", not `DataItem.IsGroup`, and that difference was
measured rather than reasoned.** `IsGroup` is `Pic is null && Children.Count > 0`, and `ParseUsage` synthesizes a
pointer profile onto an entry before its subordinates are known — so `01 G USAGE POINTER. 05 A PIC X.` binds a
header that is neither `IsGroup` nor honestly elementary. The FIRST build of this screen was keyed on `IsGroup`,
rejected every other shape, and waved that one through arm A and then *blessed* it in arm B as "a level-1
elementary pointer". `Sr14Elementary` is `Children.Count == 0` (§8.5.1.3.2) and the negative fixture
`pb183-usage-pointer-group-usage` is the witness. (A related asymmetry stays visible rather than papered over:
`ResolveIndexItems` sheds a group header's synthesized profile for INDEX and OBJECT REFERENCE but not for
POINTER / PROGRAM-POINTER. Arm A makes the shape it describes nonconforming, so it is now unreachable on
conforming source.)

## The two decisions the note left open, both settled from the standard

**DOES LEVEL 77 SATISFY SR14? YES.** The letter says "at level 1", and the standard writes "level 1 or level 77"
elsewhere when it means both — a real argument the other way, which loses to two texts. §8.5.1.3.2: "Three types
of entries exist for which there is no true concept of level", the second being entries that specify
noncontiguous working-storage, local storage and linkage data items — so a 77 entry is not AT a level greater
than 1, it is outside the level system, and SR14's arm cannot exclude it by level arithmetic. And §13.11.1
declares the two spellings ALTERNATIVES for one thing: "Data elements that bear no hierarchical relationship to
any other data item may be described as records that are single elementary items. Alternatively, such data
elements ... may be described as separate data description entries having level-number 77." SR14's evident
subject is SUBORDINATION to a non-strong group, and a 77 entry is defined by having no such relationship. The
surveyed implementations agree (GnuCOBOL's testsuite uses `77 ptr USAGE POINTER.` throughout). Held by ONE named
predicate, `Sr14PermittedLevel`, so a re-reading is a one-line change; pinned by a unit theory.

**DIALECT POSTURE: hard error, no permissive escape.** SR14 is a plain syntax rule, so the conforming response
is a compile-time diagnostic — the same posture as its drafting twin §13.18.57.3 SR6 (COBOLNET1532). It is not
dialect-gated: `--permissive` is the migration mode for constructs an edition REMOVED, which this is not, and
follow-GnuCOBOL covers implementor-defined LATITUDE, which a syntax rule is not.

### The external differential — RUN, and the analysis's prediction was WRONG

Sixteen GnuCOBOL testsuite programs carry the shape (`listings`, `run_extensions` ×6, `run_file` ×2,
`run_fundamental`, `syn_definition`, `syn_misc` ×3) — FCD structures and MySQL-shaped handles, production idioms
rather than corner cases. The 2026-08-30 analysis predicted **ZERO** baseline-row flips, on the ground that none
of the affected rows was currently `AGREE_ACCEPT`.

**Measured instead of trusted: `gnucobol_differential.py` over all 1,323 cases produces EXACTLY ONE flip.**

```
FLIP  listings:2320   AGREE_ACCEPT -> WE_REJECT_THEY_ACCEPT   COBOLNET1724 on 'ws-mysql-cid'
```

The prediction was wrong because at least one affected row WAS `AGREE_ACCEPT`. This is precisely why the
analysis flagged its own row-attribution method as a caveat ("the exact row-to-case mapping should be
re-derived by the differential harness itself before the prediction is treated as a gate") — and why a
prediction is not a measurement.

**The flip is CORRECT and the rejection stands.** The case is `listings.at:2325`:

```cobol
       01  ws-mysql.
           02  ws-mysql-cid      usage pointer.
           02  ws-mysql-result   usage pointer.
           ...
```

`01 ws-mysql.` is an ordinary group — no `TYPEDEF STRONG` — and its level-02 members carry `usage pointer`.
That is exactly what SR14 forbids. GnuCOBOL accepts it as a dialect extension; ISO does not permit it. The row
now joins the 548 already in the `WE_REJECT_THEY_ACCEPT / DEFAULT_DIALECT` bucket, and the baseline was
rewritten with this attribution.

⚖ **THE ONE THING WORTH AN OWNER'S EYE.** The measured real-world cost of the strict posture is no longer
"one corpus fixture, zero differential rows" — it is one corpus fixture, one differential row, and sixteen
external programs, all of them the same widespread production idiom (a group of pointer handles). The posture
was chosen from the standard and remains derivable: SR14 is a SYNTAX RULE, so follow-GnuCOBOL-on-latitude does
not apply, and the drafting twin §13.18.57.3 SR6 is a hard `Edition.Error` with no permissive escape. But if the
owner wants migration cover for this idiom, the hook is ready-made: the level/strong test is ONE named predicate
(`Sr14PermittedLevel` / `Sr14UnderStrongTypeDeclaration`) and a `--permissive` leniency would be a one-line
change at a single site. Recorded, not asked — the rule decides unless the owner overrides it.

## Companion derivation, ANSWERED: §13.18.57.3 SR4 does NOT overturn the internal-typedef-REDEFINES carve-out

SR4 ("If type-name-1 is described with the STRONG phrase, the subject of the entry shall not be implicitly or
explicitly redefined in whole or in part") has as its SUBJECT the entry CARRYING the TYPE clause, and
§13.18.57.3 SR2 ("A data description entry in which a TYPE clause is specified shall not be followed immediately
by a subordinate data description entry or a level 88 entry") makes a subordinate REDEFINES under a TYPE entry
syntactically unwritable. The only REDEFINES that can reach a strong subtree from outside is
`01 X REDEFINES S.`, already rejected. A REDEFINES written INSIDE the typedef TEMPLATE has no TYPE-clause
subject at all, so SR4 never reaches it. PB179's cross-root narrowing was correct and unchanged. Recorded in
`CheckStrongTypeDeclarations`' doc-comment and pinned by `pb183_redefines_in_strong_typedef_ok`.

## What this landing does NOT close, named so the gaps are visible

- **SR21 (MESSAGE-TAG exclusivity) is not implementable today** and is deliberately NOT written as dead code:
  there is no `Usage.MessageTag` member (a 2023 addition, VCR row 32). `EveryUsageMemberCarriesAnSr14Verdict`
  fails the moment the member lands, which is how the obligation is held open. SR14's MESSAGE-TAG arm and SR4's
  are in the same position; FUNCTION-POINTER is covered by the written-clause arm but never reaches the class
  arm (staged loud at `ParseUsage`, the P13 prototype band).
- **The pre-2023 shape of these rules is not derivable from the 2023 text.** Annex E carries no note on
  §13.18.60.3, but Annex E's scope is 2014→2023 only, so its silence is a MISSING observation. The arms ship
  UNGATED pending the ISO 2002/2014 texts, which is the safe direction: it enforces the rule the compiler can
  cite. → [[PB296]].
- **PB179's Tier-D backstop is KEPT, not deleted.** Its comment now names the landed screen. It remains the loud
  guard for the recovery paths; deleting it would let a pointer leaf reach the byte-window machinery as a silent
  zero-width Tier-B alias.
- **§13.18.60.3's other syntax rules were not audited here** — only the declaration-placement family. The
  traceability inventory's 21 rows for this clause read GAP even for SR3/SR5/SR10/SR12/SR13/SR20, which the code
  demonstrably enforces; that mismatch is → [[PB295]].
