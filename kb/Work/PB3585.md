# PB3585 — the self-test budget cap assumes CPU-bound work

**Sites:** `scripts/self_tests.py` (BUDGET_CAP) and `.github/workflows/build-and-test.yml` (the `windows-self-tests` job, for the measurement only).

`scripts/self_tests.py` `BUDGET_CAP = os.cpu_count() or 4`: 4 places on CI's Windows runner, where 1,444 s of
self-tests ran in 440 s of wall (merge group run 40004159292). The self-tests are bound by git process creation and
file I/O (PB3582), so the cores are not the limit. But no cap beats the longest single self-test (prune_worktrees.py,
168 s on that run), so this waits for PB3582 to shorten the long ones.

## The measurement to make

On CI's `windows-self-tests` job (PB3581), the same commit at caps 4, 8 and 12 (a `--jobs` argument or an environment
override, used only for the measurement): wall, and the slowest self-tests' times at each cap (a loaded runner slows
each). Change the default only for a measured gain, and keep the cap machine-wide (the budget's purpose: N concurrent
gates on one host).

## Measured (wave 20261025, group A3)

The question is whether the cores are the limit. Three readings, two of CI and one of this host:

- **CI keeps all four places busy.** Merge-group runs 40058976771, 40057441922 and 40048830853 (jobs 120768189541,
  120763500498, 120736701319): 290, 369 and 236 s of wall for 1,031, 1,332 and 812 summed self-test seconds (3.4 to 3.6
  at once). From each job's log timestamps, four self-tests ran at every 20 s sample from the 20th second to the last
  long one. The places were never short of work. The runners differ by 1.6x for the same work.
- **The phase needs about 85 % of a 4-core runner's processor time.** This host ran the Windows phase inside a Job
  object pinned to 4 logical processors (scratch `jobmeasure.py`). The phase's processes used 988 CPU-seconds (499 user,
  489 kernel) and started 12,996 processes. A 4-core runner has 1,160 processor-seconds in 290 s. On a runner whose
  processors are as fast as this host's, a wider budget can win at most the remaining 15 %; on a slower one, less. The wall of that
  run (1,919 s, 13 % of the 4 processors) does not count: the host was 86 % busy with three other gates and starved
  the run. The 8- and 12-place runs were stopped for the same reason. No reading from that host could stand for a
  runner's wall time.
- **The order costs more than the cap.** Each self-test starts in discovery order. In run 40058976771,
  `prune_worktrees.py` (90 s) started at 196 s and ran alone for the last 50 s of the 286 s phase. Running the longest
  first needs each self-test's last duration. The PASS store records it, but CI starts from an empty store, so the
  fix needs a CI design and is reported as a lead.

**Decision:** the default stays one place per core. CI cannot settle the question from a branch (a dispatch run is the
whole matrix, and an implementer does not push), so every run now settles it. The GREEN verdict line says how busy the
host's processors were across the phase, and `--budget N` runs one phase at another width.

## Landing (wave 20261025, group A3)

- `scripts/self_tests.py`: `HostCpu` takes two readings of `GetSystemTimes` (Windows) or `/proc/stat` (Linux), the
  same reading `tests/_shared/HostLoad.cs` takes. The GREEN line adds `the host's P processors u% busy` to its budget
  clause. `--budget N` (a whole number, at least 1) replaces `--jobs`, which no caller passed and which only narrowed
  the thread pool. The pool is now one thread per place. New self-test arms cover the busy share's arithmetic, an
  unreadable or non-advancing reading, this host's reading, the line, and `--budget`'s refusals.
- `docs/rearchitecture/DESIGN-test-build-ci.md` §3.14.10 item 2 records the reading, the measurement and the decision.
- For the next implementer: `scripts/self_tests.py#HostCpu` is the host-busy reading (REUSE it, do not write another);
  `#main` `--budget` sets the width of one run (`Budget.for_repo(repo, cap)`). Trap: a wall time measured on a shared
  host is starved by the other gates (1,919 s here against CI's 290 s). Count the run's CPU-seconds and processes
  through a Job object instead (`JobObjectBasicAccountingInformation`), and take wall times only from CI's job logs,
  whose per-line timestamps give each self-test's start and end.
- **Reading CI after the landing:** the `windows-self-tests` job's verdict line. Under about 70 % busy, measure
  `--budget 8` and `--budget 12` on that runner before changing the default.
