# PB993 — OPEN

## Repro — measured
`scratchpad/w49e/p837o.cob` (the GIVING file's implicit OPEN fails fatally; a USE AFTER EXCEPTION declarative is
present). Observed on main: `DECL O-OUT 30` / `DECL O-OUT 42` / `AFTER-SORT 42` — the declarative runs for the OPEN,
then AGAIN for a WRITE against the unopened file, and the program continues past the SORT as if it completed.

## The rule
`OK  §14.9.40.4 15)` — "If a fatal exception condition exists for file-name-3 as a result of the implicit OPEN during
file initiation, the SORT is terminated." (cite.py prints the path 15); the paragraph is the GIVING-side tail of the
file-initiation rule.) MERGE carries the same sentences for its USING and GIVING files (§14.9.24.4 GR7 a), GR12 a)/b)).
The SORT GR12 b "fatal … file-name-1" (USING side) wording needs a determination of what "terminated" leaves in the
GIVING file — record it in docs/CONFORMANCE.md.

## Code site
`SortEmitter.EmitImplicitOpen` and the USING/GIVING loops: the implicit OPEN reports to the declarative and returns; no
termination path exits the SORT.

## What the fixer owes
One termination exit for the whole statement (SORT and MERGE, USING and GIVING), taken after the declarative returns;
goldens for each of the four arms. PB837's branch (implicit CLOSE status) touches the same emitter — land after it.
