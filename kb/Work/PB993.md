# PB993 — LANDED (wave 55, finisher C)

## Repro — measured
`scratchpad/w49e/p837o.cob` (the GIVING file's implicit OPEN fails fatally; a USE AFTER EXCEPTION declarative is
present). Observed on main: `DECL O-OUT 30` / `DECL O-OUT 42` / `AFTER-SORT 42` — the declarative runs for the OPEN,
then AGAIN for a WRITE against the unopened file, and the program continues past the SORT as if it completed.

## The rule
`OK  §14.9.40.4 15)` — "If a fatal exception condition exists for file-name-3 as a result of the implicit OPEN during
file initiation, the SORT is terminated." (cite.py prints the path 15); the paragraph is the GIVING-side tail of the
file-initiation rule.) MERGE carries the same sentences for its USING and GIVING files (§14.9.24.4 GR7 a), GR12 a)/b)).
The SORT GR12 b "fatal … file-name-1" (USING side) wording needs a determination of what "terminated" leaves in the
GIVING file — record it in docs/CONFORMANCE.md.

## Code site
`SortEmitter.EmitImplicitOpen` and the USING/GIVING loops: the implicit OPEN reports to the declarative and returns; no
termination path exits the SORT.

## What the fixer owes
One termination exit for the whole statement (SORT and MERGE, USING and GIVING), taken after the declarative returns;
goldens for each of the four arms. PB837's branch (implicit CLOSE status) touches the same emitter — land after it.

## Landed — wave 55 finisher C (2026-09-22)

Re-probed on the finisher's own build before the fix: `p837o.cob` printed `DECL O-OUT 30` / `DECL O-OUT 48` /
`DECL O-OUT 48` / `DECL O-OUT 42` / `AFTER-SORT 42` (PB837 had since given each as-if statement its own hook, so the
unopened file's two WRITEs now reached the declarative too). After: `DECL O-OUT 30` / `AFTER-SORT 30`.

**The fix is ONE table, `SortEmitter.RuleFor`** — (verb × as-if statement) → the disposition of a fatal and of a
nonfatal unsuccessful status, each split on whether an applicable USE procedure ran and completed normally. Every
as-if OPEN/READ/WRITE/CLOSE goes hook → `EmitDisposition`, which renders TERMINATE (`goto` the statement's end
label), BYPASS (MERGE GR12 a) — `goto` past the GIVING file's WRITE loop and CLOSE) or CONTINUE. The default cell
is §9.1.13.1's (`OK §9.1.13.1`): a fatal status transfers "to the end of the statement that produced the fatal
exception condition", the SORT/MERGE; the specific cells are SORT GR12 b)/GR15 (`OK §14.9.40.4 12)`, `OK
§14.9.40.4 15)`) and MERGE GR7 a), GR12 a), GR12 b) (`OK §14.9.24.4 7) a)`, `OK §14.9.24.4 12)`). The USE-completed
fact comes from the hooks themselves: `__IoCheck`/`__IoCheckEc` now answer -3 for "no procedure applied" apart from
-1 "ran, completed normally" (the EC-free `__IoCheck` answers a bool), and the transfer passes `__verbRule` so
`__IoCheckEc` does not end the run unit on a fatal status — §14.6.13.1.3 2) precedes 5)/7) (`OK §14.6.13.1.3 2)`).
Determinations (GR12 b)'s file-name-1 read as the USING file; "exception condition exists" = unsuccessful status; a
terminated statement performs no remaining implicit function, so a GIVING file whose WRITE terminated it stays
open) are in `docs/CONFORMANCE.md` §3. `SortTransferRuleDriftTests` pins every cell and the one hook call.
