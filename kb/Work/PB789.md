# PB789 — OPEN — one rule string, two different failures

Filed 2026-09-06 14:19 PDT by the registrar from the PB770 implementer's report (§"New defects found",
paragraph C). PB770 itself LANDED in train 19 and is on main; this is the residue it names and did not touch.
**Every claim below was re-derived on main at `07cbb2ad`** from the source, not inherited from the report — and
one of the report's two claims does not survive that re-derivation (see the premise correction).

## The mechanism, quoted from main

`src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs:73`. The helper takes `rule` ONCE and hands the SAME
string to two `Edition.Error` calls that report two unrelated failures:

```csharp
internal CodedCharacterSet? CodedCharacterSetOf(string alphabetName, string site, string rule)
{
    AlphabetDef? a = …; NationalAlphabetDef? n = …;
    if (a is null && n is null)
    {
        Edition.Error("COBOLNET0898", $"{site}: '{alphabetName}' is not an alphabet-name declared by a "
            + $"SPECIAL-NAMES ALPHABET clause ({rule}; §12.3.7)");        // :79-80 — the UNDECLARED-NAME arm
        return null;
    }
    var set = a is not null ? a.CodedSet : n!.CodedSet;
    if (set is null)
    {
        Edition.Error(DiagnosticCatalog.LocaleAlphabetNotACharacterSet, …                                     // :86-88 — the LOCALE arm
            + $"character set (§12.3.7.4 GR7, Table 6), so it cannot be referenced here ({rule})");
        return null;
    }
    return set;
}
```

The helper's own doc comment (`:68-72`) states the split correctly — *"a LOCALE alphabet defines a collating
sequence only … and an undeclared name is COBOLNET0898 naming the site"* — and then the parameter list collapses
it: one `rule`, both arms.

## The call sites, MEASURED — and the report's enumeration corrected

⚠ **The report says "Four call sites inherit it: the class condition's alphabet-name-1, SYMBOLIC CHARACTERS … IN,
CLASS … IN, CODE-SET."** Measured on main (`grep -rn CodedCharacterSetOf src/` — six hits, two of them prose in
doc comments), the four INVOCATIONS are:

| site | file:line | the `rule` string it passes |
|---|---|---|
| FD CODE-SET, alphabet-name-1 | `src/Cobol.Net.Compiler/Binding/DataBinder.cs:3512` | `ISO §13.18.13.3 SR1 — alphabet-name-1 shall reference an alphabet that defines an alphanumeric coded character set` |
| FD CODE-SET, alphabet-name-2 | `src/Cobol.Net.Compiler/Binding/DataBinder.cs:3514` | `ISO §13.18.13.3 SR2 — alphabet-name-2 shall reference an alphabet that defines a national coded character set` |
| `CLASS … IN alphabet-name-4` | `src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs:1303` | `ISO §12.3.7.3 SR17 d — alphabet-name-4 shall not reference an alphabet specified with the LOCALE phrase` |
| `SYMBOLIC CHARACTERS … IN alphabet-name-3` | `src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs:1342` | `ISO §12.3.7.3 SR16 g — alphabet-name-3 shall not reference an alphabet specified with the LOCALE phrase` |

So it is FOUR calls, but **CODE-SET is two of them and the class condition's alphabet-name-1 is none of them** —
that site appears only in `IsLocaleAlphabet`'s doc comment (`:57-63`, "kb/Work PB64 T5"), which is a different
helper. The count is right; the list is not, and the correction matters because the fix has to touch every arm
that passes a `rule`, not the one a reader would go looking for first.

Note the shape of the damage per arm: the two CODE-SET strings are *class* rules (SR1/SR2 — "shall reference an
alphabet that defines an alphanumeric / national coded character set"), which read almost plausibly under an
undeclared name; the two SPECIAL-NAMES strings are *LOCALE* rules (SR16 g / SR17 d), which do not. The report's
witness is the worst of the four.

## The witness, as the implementer measured it

Measured by the PB770 implementer on his own build while checking the `run_misc:5406` GnuCOBOL witness:

```
error COBOLNET0898: SYMBOLIC CHARACTERS … IN A-EBC: 'A-EBC' is not an alphabet-name declared by a SPECIAL-NAMES
  ALPHABET clause (ISO §12.3.7.3 SR16 g — alphabet-name-3 shall not reference an alphabet specified with the
  LOCALE phrase; §12.3.7)
```

`A-EBC` is not declared at all, so it is not "an alphabet specified with the LOCALE phrase" and SR16 g has
nothing to say about it. `feedback_a_real_clause_can_answer_a_different_question`, in the DIAGNOSTIC rather than
in a design comment: the clause is real, its quoted text is genuinely in the standard, and it answers a question
the user did not ask.

Every one of the four call-site strings is a TRUE statement of its own clause. None of them is the rule an
undeclared name breaks. That rule is **§8.4.2.1** — and this compiler already knows it:
`src/Cobol.Net.Compiler/Binding/ReferenceResolver.cs:250` emits COBOLNET1639 with the words
*"the statement's reference identifies no resource (ISO §8.4.2.1: \"a statement shall contain a reference that
uniquely identifies that resource\")"*, and `:183` names it as R30's rule. The undeclared arm should cite what
its sibling diagnostic cites.

## ⛔ Premise correction — the report's "cosmetic sibling" is not a defect

The report closes paragraph C with: *"Cosmetic sibling in the same message: the site string renders as `SYMBOLIC
CHARACTERS . IN A-EBC` — a stray period where the clause has no name to print."* **There is no stray period on
main.** Measured on the bytes:

```
$ sed -n '1342p' src/Cobol.Net.Compiler/Binding/DataBinder.Switches.cs | od -c
…   S   Y   M   B   O   L   I   C       C   H   A   R   A   C   T   E   R   S
342 200 246       I   N       {   i   n   W   o   r   d   .   G   e   t   T   e   x   t …
```

`342 200 246` is `E2 80 A6` = U+2026 HORIZONTAL ELLIPSIS — the same elision marker `CLASS {name} … IN {…}` uses
one site over, standing where the clause's symbolic-character / integer list would be. The `.` in the report is
a console best-fit fold of U+2026, not the program's output. `feedback_render_dont_reason`: a rendering is only
evidence about the renderer until you look at the bytes. Nothing to fix here; do not "repair" the ellipsis.

## Fix shape — the clause moves from the CALL SITE to the REFUSAL

`CodedCharacterSetOf` should not take a `rule` at all. The undeclared-name arm's rule is the SAME at all four
sites (§8.4.2.1 — a reference that uniquely identifies a resource), so it belongs INSIDE the helper, beside the
`COBOLNET0898` it accompanies; only the LOCALE arm's rule varies by caller, so only that one is a parameter.
Rename it accordingly (`localeRule`), and the fifth site cannot inherit the wrong clause because there is no
longer a parameter that could carry it — the shape that makes the NEXT case automatic (CLAUDE.md rule 5), not
the one that makes this case small.

⚠ Consider whether the undeclared-name arm should stop emitting COBOLNET0898 at all and route through the R30
chokepoint that owns §8.4.2.1 (COBOLNET1639) — one rule, one place. That is a bigger change than this note
requires and is called out here so the fixer decides it deliberately rather than by omission.
