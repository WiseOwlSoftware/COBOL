# PB5653 - implicit items built from a bare PicInfo have no PICTURE identity (PB5617's root at two more sites)

**What the report says.** "ImplicitRegisters.cs:84 (`sub` PicInfo) and FileControlBinder.FileSection.cs:351 build implicit items with no PICTURE
identity; passing such an item BY REFERENCE to a PIC-described formal may be refused COBOL0828 (same root as PB5617). Unprobed."

**Why this is a new note and not an append to PB5617.** PB5617 is `landed` and fixed only `CommunicationSectionBinder.AddSlot` (the implicit CD fields, 2002
`TEXT LENGTH` and the rest). An append file beside a landed note is in no work view, so the two sibling sites get a note of their own that `work.py next` ranks.

**Mechanism (read, 2026-11-15).** `ImplicitRegisters.ActivateDebugRegisters` builds `sub`, the DEBUG-SUB-n picture (`new PicInfo(PicCategory.Numeric,
Usage.Display, Length: 4, Digits: 4, Scale: 0, Signed: true) { SignKind = ... }`, the `// General rule 10: DEBUG-SUB-n is PICTURE S9999 SIGN IS LEADING
SEPARATE` line), and `Alnum(width)` builds the other DEBUG-* members the same way; `FileControlBinder.MaterializeImpliedRecord` builds the implied record area as
`new PicInfo(PicCategory.Alphanumeric, Usage.Display, Length: max.Value, ...)`. None sets a picture character-string, which is how PB5617's argument/formal
conformance test (same PICTURE, USAGE, SIGN) came to refuse an implicit CD field against `PIC 9(4)`. Whether an argument that is a DEBUG-SUB-n item (a
DEBUG-ITEM sub-item, readable inside a USE FOR DEBUGGING declarative) or the implied record can be passed BY REFERENCE to a PIC-described formal is
UNPROBED: the fixer probes first (a `CALL ... USING BY REFERENCE DEBUG-SUB-1` into a callee whose LINKAGE item is `PIC S9999 SIGN IS LEADING SEPARATE`;
a CALL passing the implied record item, which is unnamed, so the second site may be unreachable and need only a no-reachable-caller note).

**Rule.** The same rule PB5617 cites (verdicts in that note): `§2002:14.7.1.2.1`, "then the definition of the formal parameter and the definition of the
argument shall have" (see PB5617 for the full quotation and its `cite.py --check` verdict OK).

**Sites:**
- `src/WiseOwl.Cobol.Compiler/Binding/ImplicitRegisters.cs` (`ImplicitRegisters.ActivateDebugRegisters`)
- `src/WiseOwl.Cobol.Compiler/Binding/FileControlBinder.FileSection.cs` (`FileControlBinder.MaterializeImpliedRecord`)

**Sibling sweep for the fixer.** Every `new PicInfo(` / `PicInfo.` construction outside the picture-clause binder that stands for an item the programmer did
not write a PICTURE for (the implicit items of the DEBUG, communication, report (PAGE-COUNTER / LINE-COUNTER), exception and file sections), against PB5617's
fix (`CommunicationSectionBinder.AddSlot` builds the profile with `PictureAnalyzer.Analyze` from the PICTURE text of the equivalent description and keeps it in
`DataItem.PictureText`, the way a written entry is bound; PB5617's landing file records that the grep of `new PicInfo(` over `Binding/` found exactly these two
other sites). Use that path; do not add a second. The structural fix is one factory that states the equivalent PICTURE, with a drift test that every
implicit-item construction goes through it (CLAUDE.md rule 5).

**Retired (wave 20262150 group D, 2026-11-23): the refusal is unreachable at both sites, so no source program is rejected.** Probes on the
tree of this branch (`python scripts/orchestrator/run_probe.py --compile-only`, programs under the wave scratch `w20262150d/p/dbgsub.cob` and
`sibreg.cob`):

- *DEBUG-SUB-n (`ImplicitRegisters.ActivateDebugRegisters`).* A `CALL "SUBX" USING BY REFERENCE DEBUG-SUB-1` into a callee whose LINKAGE item is
  `PIC S9999 SIGN IS LEADING SEPARATE`, inside `USE FOR DEBUGGING ON W1`: at `--std 2002` the declarative is refused COBOL0902 (the debug module was
  deleted by 2002) and the argument COBOL1677 ("references the DEBUG-ITEM special register, which no DATA DIVISION entry describes", §2023:14.9.4.3 SR3);
  at `--std 85` the argument is refused COBOL1677 too (the compiler's own citation, not re-derived here). The registers exist only at 85, and 85 has no same-PICTURE rule for an argument (§2002:14.7.1.2.1 is the 2002 text, `cite.py --check` OK)
  for COBOL0828 to apply. No edition both has the register and asks the identity.
- *The implied record area (`FileControlBinder.MaterializeImpliedRecord`).* The entry is unnamed (`CobolName = null`, kept off the symbol table's
  data-names) and its FILLER is unnamed, so no reference, hence no CALL argument, can denote it.
- *Siblings (the special registers).* LINAGE-COUNTER as a BY REFERENCE argument is refused COBOL2026 (a receiving operand); TALLY, SORT-RETURN and
  RETURN-CODE are not defined at 2002 (COBOL1639, and none is in the 2002 text), so no other implicit item is passed to a formal at 2002 either.

The mechanism the note names is still true (these two sites build a bare `PicInfo`, with no `PicInfo.Clause`), but nothing a program can write observes
it, so there is no defect to fix and no golden to write; PB5617's fix (`CommunicationSectionBinder.AddSlot`) was needed because a CD field IS nameable.
A later feature that makes either item nameable owes the same `PictureAnalyzer.Analyze` path first.
