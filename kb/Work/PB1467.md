## Finding — `simple-relation-conditions-p1` (crashes; rows `GR-8.8.4.2.1-13`)

**Mechanism.** F1 — no relation surface asks the variable-length-group compatibility question: a relation whose operand is a variable-length group is bound and emitted as a whole-group IMAGE comparison, which does not exist for such a group, so a COMPATIBLE pair (legal, §8.8.4.2.17) aborts the run unit and an INCOMPATIBLE pair (§8.5.1.12.1 forbids it) is not refused at compile time and aborts the same way

**Repro.** 01 G1. 05 G1A PIC X(2) VALUE "AB". 05 G1D PIC X DYNAMIC LENGTH. 05 G1C PIC X(2) VALUE "ZZ".  01 G2 (same shape).  MOVE "HELLO" TO G1D G2D.  IF G1 = G2 DISPLAY "T1 Y" ELSE DISPLAY "T1 N" END-IF  -> run: Unhandled NotImplementedCobolFeatureException 'whole-group image of G1 with a dynamic-length / dynamic-capacity member … Tier-C'. Second program: 01 G1 (with a DYNAMIC LENGTH leaf), 01 X1 PIC X(5).  IF G1 = X1 …  -> compiles clean, same abort. (probe srel2/vlg.cob, vlg_bad.cob, --std 2023)

**Expected from the spec.** §8.8.4.2.17: the compatible pair compares left to right as §8.8.4.2.7, dynamic-length items at their current length — T1 Y; then (G2D 'HELLP') G1 < G2 Y; (G2D 'HELL') G1 > G2 Y and G1 = G2 N. §8.5.1.12.1: 'may not undergo a comparison … unless the other operand is a compatible group' — IF G1 = X1 must be refused at compile time.

**Observed / reasoning.** Both programs compile with no diagnostic and abort at the first relation. PB393 (landed) built VariableLengthCompatibility for MOVE/INITIALIZE/CORRESPONDING and PB204/PB818 for the call boundary; CheckRelationalOperands (the ONE relation checkpoint) and the relation emitter have no variable-length arm.

**Code site.** src/Cobol.Net.Compiler/Binding/Validation/StatementValidation.cs#CheckRelationalOperands (no VariableLengthCompatibility screen); src/Cobol.Net.Compiler/CodeGen/Emit/ConditionRenderer.cs (whole-group image operand)
