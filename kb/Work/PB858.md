Source: the `PB721` implementer report, item (a). PB721 left it whole rather than half-shipped — screening two
arms of three is the defect the SR4 split exists to prevent.

## The rule, quoted

```
$ python scripts/spec/cite.py --check 13.18.43.3 "Data-name-1 shall describe an elementary unsigned integer in the working-storage, local-storage, or linkage section"
  OK  §13.18.43.3 6)  (Syntax rules)
```

Three obligations: ELEMENTARY, UNSIGNED INTEGER, and the SECTION. The first two are answerable from the resolved
operand today; the third is not.

## Code site and the blocker

The resolved operand is `FileModel.VaryingDependingItem`, set in `DataBinder.ResolveFiles` — the same site
`RecordClauseRules.Screen` already runs from, so this is three ROWS of an existing table the day the fact
exists. The blocker: `EntrySection` is passed to `DataBinder.BindEntries` and thrown away, and `DataItem`
carries no section member.

## Shape of the fix (structural)

`DataItem` gains its SECTION (the fact the binder already has and discards). That one member also serves
§13.18.63.4's section-keyed VALUE rules, §13.18.22's EXTERNAL placement rules and every future "shall be
described in the X section" rule — which is why the answer is the member, not a bespoke lookup for this rule.
Pair it with a drift test asserting every `DataItem` built by `BindEntries` carries a section.

## Sibling sweep the fixer owes

* `OCCURS DEPENDING ON`'s own data-name-1 rules (§13.18.38.3) have the same section shape.
* Every rule in the inventory whose text contains "working-storage, local-storage, or linkage section" — that
  grep IS the scope of the new member's first pass.


## Landing (wave 1021 group B)

Re-probed on this wave's build first: the note's repro (`DEPENDING ON F-LEN`, F-LEN inside the FD's record) compiled
clean and ran (`RAN`). The blocker the note named was already gone: `DataItem.Section` exists since kb/Work PB1080
(the FILE STATUS screen reads it). `cite.py --check 13.18.43.3 "Data-name-1 shall describe an elementary unsigned
integer in the working-storage, local-storage, or linkage section"` -> OK §13.18.43.3 6).

**Fix.** Three rows of `RecordClauseRules.Rules`, one per obligation, under a new subject
`RecordRuleSubject.DependingOperand` (`RecordClauseSubject.Depending` carries the resolved item): elementary (a group
is refused), unsigned integer (`PicInfo.IsUnscaledInteger` and not signed, the predicate §13.18.38.3 SR17 reads),
and the section (`DataItem.Section` not working-storage, local-storage or linkage). `DataBinder.ResolveFiles` now
resolves `VaryingDependingItem` BEFORE `RecordClauseRules.Screen`. One code, **COBOLNET2922**
(`DiagnosticCatalog.RecordDependingOperand`), reported at the DEPENDING phrase. SD entries get it too (same screen).
`RecordClauseRuleDriftTests.Sr6StatesThreeObligations_AndTheTableHasARowForEach` re-derives the three arms.

**Goldens.** `negative/pb858-record-depending-in-record` (section arm) and
`negative/pb858-record-depending-not-unsigned-integer` (group, signed, decimal), both reject-at 85 2002 2014 2023.
The positive is the existing `85/l1c23_record_varying_bounds_depending` (working-storage operand).

**For the next implementer.** `RecordClauseRules.cs#Rules` — a new RECORD clause rule is a ROW; a rule about the
DEPENDING operand uses `RecordRuleSubject.DependingOperand` and reads `s.Depending`. `DataItem.Section` is the one
section fact for every "described in the X section" rule.
