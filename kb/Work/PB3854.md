# PB3854 — a render-only mode must write nothing a running wave reads

**Sites:** `.claude/skills/workstream/make_dispatch_specs.py` (`main`, the loop that writes `msg-w<wave>-<letter>.txt` into `cfg['scratch']`)

## The defect

`make_dispatch_specs.py --no-record` is documented as "render and check only, recording nothing in the dispatch ledger"
(PB3114). It records nothing in the LEDGER, but `main` still writes each rendered spec into the groups file's own
`scratch`. The w20261709a implementer ran it over the real groups files for a sibling sweep: it overwrote 133
`msg-w*.txt` under E:\COBOL-coord\scratch (live ones included: `op/w-pb3776`, `op/w-pb3852`, `-six`, `mythos`,
`w20261700/01/05`) with the branch's template. It re-rendered all 133 from the groups files with main's tooling and
checked its own spec came back; specs of old waves (w1049 to w1125) were rendered by older tooling, so theirs are
regenerated, not byte-identical. A sweep must today rewrite `scratch` in a copy of each groups file first.

## Acceptance

- A mode that writes nothing a running wave reads: either `--no-record` writes no file at all (render and check only,
  results and refusals on stdout), or a given `--out DIR` receives the specs; a groups file's own `scratch` is never
  the target of a render-only run.
- The help text states exactly what is written and where.
- A self-test seen RED first: it runs the render-only mode over a groups file whose `scratch` holds a sentinel spec and
  asserts the sentinel is byte-identical afterwards.
- Sweep: every other script that takes a groups file and a `scratch` (`plan_wave.py`, the rolling wave) is checked for
  the same write-on-a-read-only-path confusion.
- Standing owner rules: fix the root causes, never simply making the diagnostic pass; always be consistent with
  ourselves barring an explicit requirement differently.
