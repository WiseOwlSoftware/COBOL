# PB3654 — a note the reader cannot parse leaves the register silently

**Sites:** `scripts/spec/work.py` (`load`, `read_note`, `read_notes`, `register_problems`, `check`, `main`'s `--work`, `reading_view`, `directory_findings`), `tests/version-matrix/work-frontmatter-cases.json`, `scripts/orchestrator/plan_wave.py` (`load_notes`), `scripts/orchestrator/test_plan_wave.py`, `scripts/spec/gen_ledger.py` (a comment).

## What happens

`load()` reads every `kb/Work/*.md` through `parse_frontmatter`, and a file it answers `None` for ("not a note") is
skipped with no word (`if d is None: continue`). A file NAMED like a note (`PB<n>.md`, `A<n>.md`, `R<n>.md`) whose
frontmatter is damaged therefore leaves the register: `work.py next` never ranks it, the planner never sees its
`**Sites:**`, the inventory claim gate never sees its rows, and `work.py check` prints `✓ N work items, all
well-formed`. That is the fail-open shape PB875 removed for a wrapped list, one level up: a malformed NOTE is read as no
note at all.

Second hole beside it: `check()` ignores `--work` (the "test seam" `main` parses): `work.py --work <dir> check` checks
`kb/Work` and prints its count, so the seam cannot witness the first hole.

## Measured 2026-10-24

The clerk branch `notes-PB3651-queue-leads` (PR #513) committed PB3651, PB3652 and PB3653 with a stray backtick at the
start of EVERY line (the first line read `` `--- ``), inner backticks escaped as `` \` `` and an apostrophe as the
literal text `\x27`. The clerk ran `work.py check` and reported it clean; the enqueue unit's probe reproduced it:
a directory holding the damaged PB3653.md and a good PB3650.md, `work.py --work <dir> check`, printed `✓ 2922 work items,
all well-formed` and exit 0 (the repository's count, not the directory's two). PR #513 merged the damaged notes
(2026-10-24T21:52:27Z) before the repair reached it; the repair lands in the follow-up landing of the same branch,
with this note.

## Fix direction

`load` (or `check` alone, if `next` must stay tolerant) refuses a `kb/Work` file whose NAME is a note id and whose
frontmatter does not parse, naming the file and the first bad line; a file that is not named as a note (an index, a
README) stays skipped. `check` takes the `--work` directory like the other commands. A fixture row in
`work-frontmatter-cases.json` for "every line prefixed" and one for "no opening `---`", and a `--self-test` arm that
runs `check` over a fixture directory, pin both.

## Source

Found by the enqueue unit (2026-10-24 ~21:50Z) while verifying the second lead clerk's PR #513.

## Landed (wave 20261504 group A, PB3654 first)

The note's re-probe reproduced on this build: a directory holding a backtick-prefixed `PB3653.md` and a good `PB3650.md`,
`work.py --work <dir> check`, printed the repository's `✓ 3025 work items` and exit 0. Both holes are fixed at the one
reader: `work.read_note(name, text)` answers a file that is not named like a note (`NOTE_FILE`: `PB<n>.md`, `A<n>.md`,
`R<n>.md`) with a skip and a file named like one whose frontmatter does not parse with a refusal naming the first bad line
(the opening fence is not line 1, a byte-order mark hides it, or the block is never closed). `load` stops
(`SystemExit`) on any refusal, so `next`, the planner, the ledger and every other reader fail closed instead of ranking a
register missing a note; `check` reports each refusal without stopping (`register_problems`) and takes `--work`, running
the audits that compare the register with the rest of the tree (inventory, R3 program, Bases view) only for the
repository's own `kb/Work`. The planner had a copy of the silent skip, `plan_wave.load_notes`, and refuses the same way.
Fixture: four new cases in `work-frontmatter-cases.json` (every line prefixed, no opening fence, never closed, byte-order
mark), each with the new `file` and `refusal` fields, and `work.py --self-test` writes the fixture into a directory and
runs `register_problems`, `load` and `check` over it. `gen_ledger.py` reads historical trees and keeps counting an
unparseable file as no note (a comment now says why).
