# PB487

## Mechanism — data-description-entry-p1
`dataDescriptionClause` ends in `genericDataClause -> genericClause : IDENTIFIER (IDENTIFIER|literal)*`, a vendor-extension catch-all that swallows ANY word sequence at the end of a data description entry. It makes the Format-1 clause list open-ended, and it is why the ALIGNED clause -- which has no grammar rule of its own anywhere in src/Cobol.Net.Frontend/Grammar -- is accepted and silently inert. Every '...the only other clauses permitted are...' rule of 13.16.3 is unenforceable against a word the parser does not recognize.

### Expected, from the standard
13.16.2 Format 1 is a CLOSED list of clauses, with `[ ALIGNED ]` among them; 13.18.1.4 GR1 requires an ALIGNED item to be aligned on the first bit of the first available BYTE, with implicit filler bits per 8.5.1.6.3 -- so `05 B1 PIC 1(4) BIT. 05 B2 PIC 1(4) BIT ALIGNED.` occupies TWO bytes, not one. 13.16.3 SR13 names ALIGNED's neighbours in the CONSTANT RECORD exclusion, and SR17/SR18 permit only level-number, entry-name, PICTURE, USAGE and VALUE beside ANY LENGTH / DYNAMIC LENGTH -- so an ALIGNED co-clause on those entries shall be diagnosed, and an unrecognized word shall be a syntax error.

```
(the finding quotes no rule sentence verbatim, so there is nothing to --check; the implementer MUST quote §13.16.2 and re-run `cite.py --check` before writing a code comment)
```

### Observed
ALIGNED is reserved from 2002 (ReservedWords.Table.cs:20) but has no lexer token and no parser rule, so it arrives as IDENTIFIER and genericDataClause eats it. FUNCTION LENGTH of the bit group is 1 with and without ALIGNED -- the clause is accepted and does nothing, which is the silent-wrong-layout case the design's loud-guard rule exists to prevent. The same catch-all accepts `WIBBLE WOBBLE`, so the permitted-set rules SR12/SR13/SR17/SR18 can never be complete however carefully their condition lists are maintained. Closing the Format-1 list (and giving ALIGNED its own rule and 13.18.1.3 SR1 check) resolves one FMT row and lifts four SR rows out of PARTIAL at once.

## Mechanism — usage-clause-p3
usage-p3/F3 — the data-description-entry parse silently DISCARDS an arbitrary run of unrecognized words between the data-name and the clause list, so any clause word the grammar does not know is treated as if it had not been written. Reached here through the COBOL-2023 MESSAGE-TAG usage, whose bare (USAGE-less) spelling 13.18.60.2 makes legal for every usage: `01 M MESSAGE-TAG.` compiles clean and binds an ordinary alphanumeric item. Where the swallowed entry is a GROUP header the program runs with a silently wrong data description; where it is ELEMENTARY the missing PicInfo escapes the binder and the compiler itself fails — an unhandled System.NullReferenceException in MoveEmitter, or a raw Roslyn CS0103 the user cannot act on. The same swallow accepts `01 M FOOBAR.`, `01 M FOOBAR PIC X(3).` and `01 M FOOBAR BAZQUX PIC X(3).`, so the blast radius is every misspelled or unimplemented clause word in the DATA DIVISION, not one usage.

### Expected, from the standard
13.18.60.4 GR9 (cite.py --check OK): "The MESSAGE-TAG clause specifies that a data item is a message-tag data item and contains an implementor-defined value that identifies a message and a server or requestor. The class and category of a message-tag data item are message-tag." MESSAGE-TAG is a COBOL-2023 addition (Annex E.2 item 25 adds it to the reserved words; cite.py --check E.2 OK), 13.18.60.2 prints `[ USAGE IS ]` as optional for every usage in the figure, and A.1 item 212 makes the size and contents a required documentation item. Since the usage is not implemented, the CONFORMING outcome for `01 M MESSAGE-TAG.` at --std 2023 is a named refusal in the 0899 band ("recognized but not yet implemented"), exactly as `01 M USAGE FUNCTION-POINTER.` gets; at --std 85/2002/2014 it is COBOLNET0900. Under NO reading may the entry bind as an alphanumeric item, and under no reading may a MOVE into it crash the compiler. Separately, an unrecognized word in a data description entry shall be a syntax error, never discarded.

```
$ python scripts/spec/cite.py --check 13.18.60.4 "The MESSAGE-TAG clause specifies that a data item is a message-tag data item and contains an implementor-defined value that identifies a mes..."
  OK  §13.18.60.4 9)  (General rules)
```

### Observed
Measured at --std 2023. The prefixed spelling IS refused, if bluntly: `01 M USAGE MESSAGE-TAG.` -> COBOL0001 "no viable alternative at input 'MESSAGE-TAG'" (q13). The bare spelling is not refused at all (q14/q76). The word is genuinely reserved (q74: `01 MESSAGE-TAG PIC X(4).` -> COBOLNET0901), so the funnel that should have named it exists and never sees this position. The generalized probes q77/q78/q79 prove the swallow is a property of the entry parse and not of this word. Mechanism by inspection: CobolData.g4's `dataDescriptionEntry : levelNumber dataName? dataDescriptionBody DOT` and `dataDescriptionClause` contain no alternative that admits a bare cobolWord, and MESSAGE-TAG has no lexer token, so the extra words are consumed by error recovery whose report never reaches the diagnostic stream. The binder even documents the gap it is left with (DataBinder.UsageDeclaration.cs:61: "The MESSAGE-TAG phrase is a 2023 addition ... and has no Usage member yet, so SR14's message-tag arm and SR21 ... are forward obligations").
