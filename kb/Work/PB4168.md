# PB4168 — PB4118's SEND TO LINAGE-COUNTER / PAGE-COUNTER OF RPT ... RETURNING or RAISING END-SEND draws a bare parse ...

**Sites:** `src/WiseOwl.Cobol.Frontend/Grammar/CobolParserCore.g4` (`mcsSendStatement`, `dataReference` and its LINAGE-COUNTER / PAGE-COUNTER alternative), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/DeclinedFacilityBinder.cs` (the declined MCS SEND, which performs no I/O and is accepted inert, COBOL1578).

The lead's text (PB4118 report, 'New defects / leads' item 1): `SEND TO LINAGE-COUNTER FROM x RETURNING r END-SEND` (and RAISING, and `PAGE-COUNTER OF RPT ... RAISING`) draws a bare parse error (COBOL2269/COBOL0001 "unexpected END-SEND") at the END-SEND token while LINE-COUNTER and a no-tail LINAGE-COUNTER parse; "the parse of the dataReference LINAGE_COUNTER/PAGE_COUNTER alternative followed by SEND's tail looks off (CobolParserCore.g4 mcsSendStatement/dataReference). The program is illegal either way, so only the diagnosis is poor."

PB4118's own note records the same observation in passing ("`SEND TO LINAGE-COUNTER ...` already died in the parser when RETURNING or RAISING followed; with `LINE-COUNTER` or a bare statement it compiled") and fixed nothing here.

**Probes:** `E:/COBOL-coord/scratch/w20261773d/reg.cob`, `reg4.cob`, `reg5.cob`.

**Fix the lead proposes:** find why the LINAGE_COUNTER / PAGE_COUNTER `dataReference` alternative, followed by SEND's RETURNING or RAISING tail, loses END-SEND (the LINE-COUNTER alternative does not), so the statement draws the PB4118 shape diagnosis (COBOL2024 / COBOL1850) instead of a token-level parse error. Sweep the other statements that take a `dataReference` followed by a tail for the same alternative.

Not filed: the same report's item 2 (`SEND TO RETURN-CODE FROM x RETURNING r` reads RETURN-CODE as a bare server name): the report itself says RETURN-CODE is no ISO special register in `specs/ISO_COBOL.md`, so no rule applies.

**Source:** `E:/COBOL-coord/scratch/reports/w20261773d-PB4118-report.md`, 'New defects / leads' item 1.

## Retired (wave 20261780 C, 2026-10-30): the probe's own line ran past the program-text area

Re-probed on the tree: `reg.cob`, `reg4.cob` and `reg5.cob` do draw `COBOL2269: unexpected 'END-SEN'` / `unexpected 'EXCEPTIO'` /
`COBOL0001: unexpected 'END'` - and the token texts say why. Each SEND line is 74 to 83 characters long in a FIXED-form source,
and the program-text area ends at column 72 (columns 73-80 are the identification area, ignored), so `END-SEND.` became
`END-SEN` and `LAST EXCEPTION` became `LAST EXCEPTIO`. `LINE-COUNTER` is two characters shorter than `LINAGE-COUNTER`, which is
why that spelling "parsed". The same statements wrapped inside column 72 (`SEND TO LINAGE-COUNTER` / `FROM WS-MSG RETURNING
WS-REPLY END-SEND.`, and the RAISING and `PAGE-COUNTER OF RPT` forms) draw exactly the PB4118 shape diagnosis the note asked for:
COBOL1578 and `COBOL2024: SEND TO operand 'LINAGE-COUNTER': the clause's general format prints data-name-n ...`. The parser was
right; the `dataReference` LINAGE-COUNTER / PAGE-COUNTER alternatives lose nothing. (PB4118's landing paragraph repeats the same
observation in passing; it has the same cause.)

The one real gap the episode shows - a word CUT by the margin is reported as an ordinary unexpected token, with nothing saying
that the source line ran past column 72 (the PB1950 goldens met the same trap) - is a separate diagnostic-quality question,
reported as a lead from this wave rather than filed here.
