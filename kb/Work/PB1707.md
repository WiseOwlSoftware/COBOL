## Finding

**Repro.** `E:\Temp\claude\E--COBOL\73cac64c-391d-42c0-bcdf-c880e3e10305\scratchpad\w70u\p\rmp.cob`:
`DISPLAY CX(1:77777777777)` with EC-BOUND-REF-MOD not enabled compiles and the run ends with `Out of memory.`. Crash.

**Rule.** §8.4.3.3.4 5) c) (`cite.py --check` OK): the length reaching past the item is a violation whose EC-BOUND-REF-MOD
is not checked, so the behaviour is undefined — but the compiler's lenient path must not turn it into a process crash
that allocates the saturated length.

**Code site.** `src/Cobol.Net.Runtime/Values/Text/CobolString.cs:151-154` (`len = length`; `PadRight(len)`) on the
unchecked path. Independent of PB1706 (a bind-time check of CONTROL operands) and of PB1579 (which refuses literals beyond
the host limit only where the consumer is a CONTROL operand). Note: wave 70 group C (PB1117) changed `CobolString.cs`
(`RefModPosition`); re-read the lines on the current tree.


## Re-verified 2026-09-30 (exceptions-group research, main `4a1dda60e`) — REPRODUCES; the crash has TWO causes to decide

`p1707.cob` (`01 CX PIC X(5)`, `DISPLAY CX(1:77777777777)`, no `>>TURN`) prints `BEFORE` then `Out of memory.`, exit
127. Cause, current tree: `src/Cobol.Net.Runtime/Values/Text/CobolString.cs#RefMod` — on the unchecked path `len =
length` (the saturated `SpecifiedRefModLength`, ≈2^31) and `slice.PadRight(len)` allocates it. The WRITE twin
`SpliceInto` already clamps (`Math.Min(length, dst.Length - start)`), so read and write answer the same violation
differently. A moderate overrun shows the read rule: `DISPLAY CX(1:10)` prints `ABCDE` + 5 spaces today.

**Spec (cite-checked):** §8.4.3.3.4 5) c) "The sum of leftmost-position and length minus the value one shall be less
than or equal to the number of positions in the data item referenced by identifier-1." (OK §8.4.3.3.4 5) c)) —
violated ⇒ EC-BOUND-REF-MOD, fatal; with checking off §14.6.13.1.3 8) leaves continuation to the implementor, and its
last paragraph: "If checking is not enabled for a fatal exception condition and the exception condition is detected by
the compiler, the implementor is not required to produce executable code." (OK §14.6.13.1.3 8)).

**Survey (owner protocol 2026-08-30).** GnuCOBOL 3.2 detects a LITERAL out-of-range reference modification at compile
time and REFUSES it (`cobc/typeck.c`: `cb_error_x (x, _("length of '%s' out of bounds: %d"), …)` and `"offset of '%s'
out of bounds: %d"`, when the item size is fixed). For a run-time-computed length with checks off, GnuCOBOL, IBM
Enterprise COBOL (no SSRANGE) and Micro Focus all simply address the storage that follows the item — there is no
memory-safe behaviour to copy.

## Task brief (research 2026-09-30) — ⛔ NEEDS AN OWNER DECISION on part 2 before implementation

**Part 1 — compile-time detection (follows GnuCOBOL; no owner decision needed under the 2026-08-30 protocol):** a
reference modification whose leftmost-position and/or length are LITERALS (after constant folding) and violate
§8.4.3.3.4 5) b)/c) against an item of FIXED size is detected at bind. With EC-BOUND-REF-MOD checking NOT enabled at
that statement: refuse it (error — §14.6.13.1.3 8)'s last paragraph licenses producing no code, GnuCOBOL refuses);
with checking enabled: compile it (the run-time raise is what the program asked for) and warn. New diagnostic code from
`pwsh scripts/session-probe.ps1`'s next-free; DOC-A.1-69 ("which fatal exception conditions are detected at compile
time") gains EC-BOUND-REF-MOD beside EC-ORDER-NOT-SUPPORTED. ⚠ This rejects source that compiled before — rule 3 calls
that an owner decision unless the standard licenses it; §14.6.13.1.3 8) does, and GnuCOBOL does it: say so in the
DEVLOG and CONFORMANCE entry.

**Part 2 — the run-time lenient read (OWNER DECISION: no survey answer exists, see above).** Options:
- **(A) Clamp, like the write** — the unchecked read yields only the positions the item has from `leftmost` on (`CX(1:10)`
  → `ABCDE`, `CX(1:77777777777)` → `ABCDE`): ONE lenient rule for read and write. Changes the moderate-overrun output
  (5 trailing spaces disappear); must re-check the SORT RELEASE path CONFORMANCE D-SMA describes ("space-extends the
  record area as the lenient reference modification `(1:size)` would") — if it calls `CobolString.RefMod` it changes too.
- **(B) Keep today's pad-to-requested-length, but cap the requested length at a host limit** (e.g. the largest
  item the compiler accepts) — keeps `CX(1:10)` → `ABCDE     ` byte-identical and turns the crash into a very long
  line of spaces; the cap is arbitrary and the result still manufactures characters no storage holds. Not recommended.
- **(C) Terminate** — with checking off, an overrun whose padded length exceeds the item size ends the run unit
  (implementor-defined under §14.6.13.1.3 8), the "loud abort where the standard names no outcome" doctrine the
  EC super-batch owner decision of 2026-07-28 set). Changes `CX(1:10)` from continuing to terminating.
- ⚠ **An existing owner rule already points at (C).** The EC super-batch owner decision of 2026-07-28
  (`docs/rearchitecture/DESIGN-ec-oo-superbatch.md`, Risks: "checking-OFF is LENIENT wherever the standard names the
  outcome, and a LOUD ABORT wherever it names none") covers this site: §8.4.3.3.4 names no outcome for an out-of-range
  reference modification (it only sets EC-BOUND-REF-MOD). But today's pad-and-continue predates that rule and applies
  to EVERY overrun, so (C) changes moderate overruns too, and the general checking-off policy (A.1 items 103/218) is
  still kb/Work PB322 determination E. **The question for the owner is therefore narrow: confirm that the 2026-07-28
  rule governs the unchecked reference-modification read (→ (C), every overrun terminates), or carve it out for (A).**
  Research recommendation: **(C)**, because it is the owner's own standing rule and it removes the crash without
  inventing a result; (A) is the fallback if the owner prefers continuation. Part 1 is independent of this answer.
