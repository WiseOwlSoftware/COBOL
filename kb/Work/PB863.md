# PB863 — OPEN — three literal categories, one node

Source: the `PB165` implementer report, "New defects found outside this mechanism" item 3 ("worth a note if the
registrar agrees, but it is outside my mechanism"). Filed as ANALYSIS because the harm is latent: no measured
wrong answer, and the fix is a bound-tree change whose scope is the consumers.

## The mechanism

`BoundStringLiteral(string Value)` carries the characters and not the category. §8.3.3's literal categories —
alphanumeric, national, boolean — are distinguished at parse (the `N"..."` / `B"..."` prefixes) and then erased.

## Why it matters

```
$ python scripts/spec/cite.py --check 14.9.25.3 "Table 16"
  OK  §14.9.25.3 10)  (Syntax rules)
      10) For all other cases not described in Syntax rules 8 and 9, table 16, Validity of types of MOVE statements, specifies the validity of the move.
```

Table 16's rows for Alphanumeric, National and Boolean senders DIFFER — e.g. an Alphabetic receiver takes an
alphanumeric sender (`Yes`) and not a national or boolean one (`No`); a Numeric receiver takes alphanumeric and
national (`Yes`) and not boolean (`No`). A consumer that cannot tell the three apart must accept the union, so
every such screen under-rejects. `ContentAlphanumericLiteralMismatch` documents exactly this weakening today.

## Shape of the fix

Carry the category on the node (`BoundStringLiteral(string Value, LiteralCategory Category)`), set once at
parse. Every Table-16 consumer then narrows to the exact row, and the `ContentAlphanumericLiteralMismatch`
comment's weakening disappears rather than being re-derived.

## Code site

`src/Cobol.Net.Compiler/Binding/Bound/BoundTree.cs` (`BoundStringLiteral`), its constructors in the expression
binder, and every consumer that asks a category question of a literal sender (`grep BoundStringLiteral`).
