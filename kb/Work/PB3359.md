# PB3359 — an owner requirement on a campaign's groups has no path into the specs or the review

Found by the wave-1115 unit (campaign PB3353), 2026-10-17 22:30 PDT. Grepped `kb/Work` for `steer` + `reviewer` +
`body`/`spec`, `standing requirement`, `exception-path`, `outlets design`: no note covers it.

**The requirement.** The owner, 2026-10-17 ~22:25 (verbatim, recorded in
`E:\COBOL-coord\scratch\operator-steer-restart-20261017.md` section 00 item 8): "Note: out test cases for sort and file
I/o must cover both the success and abnormal exception cases. Therefore they also validate outlets design." The steer
says every campaign PB3353 group (and every SORT or file I/O finisher) covers the abnormal and exception paths as fully as
the success paths, that "a wave unit puts this sentence in every SORT or file I/O group's `body` when it renders the
specs", and that "a reviewer raises a finding when a branch lacks the exception-path tests".

**The gap, in two halves.**

1. *The implementer gets it only by hand.* `scripts/orchestrator/plan_wave.py` builds each group's `body` from its notes
   (`as_group_json`, called at `plan_wave.py:1370`) and has no input for a requirement that applies to every group of a
   campaign. The wave-1115 unit met the steer by appending the sentence to every group's `body` in
   `E:\COBOL-coord\scratch\groups.json` with a one-off script (`E:\COBOL-coord\scratch\add-owner-test-req-w1115.py`) and
   re-running `make_dispatch_specs.py` and `check_practices.py` (GREEN). The unit prompt says to re-run the planner rather
   than edit groups.json, so every later campaign wave depends on its unit reading the steer and repeating the edit; a
   unit that does not is never told it missed it.
2. *The reviewer never gets it.* `wf_rolling_wave.js` `reviewBranch` (line 145) points the `cobol-reviewer` at the
   branch, worktree, head, report and findings file, never at the dispatch spec `msg-w<wave>-<letter>.txt`, and
   `.claude/skills/review/SKILL.md` "The branch form" (line 64) reads no spec either. So the steer's "a reviewer raises a
   finding when a branch lacks the exception-path tests" is enforced by nothing; a branch missing them can be stamped
   CLEAN and landed by the lane.

**Failure scenario.** A later campaign PB3353 wave unit plans with `plan_wave.py --cluster PB3353`, does not apply the
steer by hand, and an implementer fixes an I-O status setter with success-path goldens only; the reviewer, which never
saw the requirement, stamps CLEAN; the landing lane lands it. The owner's requirement is silently unmet on main.

**The shape the fix should take (rule 5).** One structured place for a requirement on a campaign's groups (for example a
`requirements:` field on the campaign's lead note, or a standing-requirements file the steer names) that `plan_wave.py`
copies into every group's `body` and the args file, and that `wf_rolling_wave.js` passes to the branch reviewer (or the
review prompt names the group's dispatch spec, so the reviewer checks the branch against everything the implementer was
told). A drift test pins that a requirement in that place reaches both the rendered spec and the reviewer prompt.

## Landed (wave 1116 B)

A campaign's owner requirements live in ONE place, the `## Standing requirements` section of the lead note (a bullet each;
PB3353's carries the 2026-10-17 ~22:25 exception-path requirement). `plan_wave.campaign_requirements` reads it for
every group whose notes name the campaign in `cluster:` (`plan_wave.group_requirements`: by membership, in a fix-lane wave and
a `--cluster` wave alike, review R1-1); the planner writes each requirement into that group's spec `body`, its groups.json
entry and its args entry; `check_practices.py` (`specs_missing_requirements`) refuses a rendered spec that lacks one its own
group declares; `wf_rolling_wave.js` hands the branch reviewer the group's dispatch spec and the requirements
(`reviewerRequirements(g)`), and the review skill's branch
form says a branch lacking one is a finding (category `requirement`). The section is prose, not a frontmatter list,
because a requirement is a sentence with commas and the list grammar (`work._split_list`, with its C# parity twin) splits
on them. Pinned by `test_plan_wave.py` section 9a. The campaign lead PB3330 (the keyed-storage engine, on its design
branch when this landed) needs the same section when it reaches main: its groups are file I/O groups.
Design: DESIGN-orchestrator-loop.md section 9.1, "Standing requirements".
