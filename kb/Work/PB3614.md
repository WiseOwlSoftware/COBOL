# PB3614 — SequentialJournal sizes a journal in 32-bit int arithmetic

**Sites:** `src/Cobol.Net.Runtime/IO/Sharing/SequentialJournal.cs` (`Parse`, the torn-tail bound near line 338; `Read`, `checked((int)medium.Length(record))` near line 362).

## Found

Source: `w20261024a2-PB670-report.md`. Both are latent (no connector drives the journal yet), same file, one mechanism:
the journal's sizes are held as `int`.

- **R1-2 (Parse).** The torn-tail bound `if (payload < 0 || at + 1 + payload + ChecksumBytes > bytes.Length) break;` is
  computed in unchecked int arithmetic. An R record whose length word (`20 + ReadInt32LittleEndian(...)`) is near
  `int.MaxValue` makes `at + 1 + payload + 4` wrap negative, the `break` is skipped, and `bytes.Slice(at, 1 + payload)`
  throws `ArgumentOutOfRangeException` instead of ending the records as a torn tail.
- **R1-3 (Read).** `Read` loads the whole record file through `new byte[checked((int)medium.Length(record))]`: a journal
  over 2 GiB throws `OverflowException`, which neither `ReadOrNull` nor the Rollback contract handles.

## The fix

Do the bound in `long` (so a wrapped record reads as a torn tail), and decide what a journal too large to load means
(read it in a bounded way, or a defined refusal that Rollback handles) rather than an unhandled exception. A test for
each: a hand-built journal with a near-`int.MaxValue` length word, and the large-file arm through the medium double.

## Landed (wave 20261032 group H, 2026-10-24)

Re-probed on this branch's base (864cb8c32): the note's two sites no longer exist as written. PB3340's review rounds rebuilt the
reader as a stream (`SequentialJournal.ReadRecord` over a `BufferedStream`, `NextRecord` per record), so `Parse`'s `bytes.Length`
bound and `Read`'s whole-file `checked((int)medium.Length(record))` are gone, and a journal over 2 GiB is read as any other (R1-3
DISCHARGED: the reader never loads the file whole; witness `A_journal_over_two_gibibytes_reads_its_records_without_loading_it_whole`
over a sparse 3 GiB stream). The same mechanism survived in the streaming reader's `R` arm: `new byte[1 + 20 + length + ChecksumBytes]`
from the untrusted length word. Before the fix a word of `int.MaxValue`, `int.MaxValue - 10` and `int.MaxValue - 24` threw
`OverflowException` (the int sum wraps) and `int.MaxValue - 60` threw `OutOfMemoryException`, from `ReadRecord`, so out of
`Enter`/`Settle` (a dead transaction's next entry step) and past `Rollback`'s `IOException`-only catch. After it each is a torn
tail: the records end at the last whole one.

Fix: `NextRecord`'s `R` arm judges the length word in `long` arithmetic against `Array.MaxLength` and against what the record file
still holds (`reader.Length - reader.Position`) BEFORE allocating, so no allocation exceeds the file it reads and none wraps
(DESIGN-runtime-library.md 2.2.2.4 states it). Siblings swept: `RecordFraming.ReadFrame` and `ReadExtentTable` already bound every
length word by `medium.Holds(...)` before allocating (PB2754); `SortRunFile.Next` reads a run file this process wrote itself, not a
torn-tail format; `NoteImage`'s `20 + bytes.Length` cannot wrap (a `byte[]` is at most `Array.MaxLength`).

For the next implementer: `SequentialJournal#NextRecord` is the one decoder of an `R` record's length word (FrameDecoderDriftTests
names it); `SequentialJournalTests#JournalWithTornImage` and `SparseStream` build a torn or over-2 GiB record file without writing one.
