# PB2915 — `--help` crashes under the Windows console encoding

RETIRED: a duplicate of PB1546, which now owns this mechanism and this note's evidence; kept only so references resolve.

Found 2026-10-10 twice, independently: by the operator (`python scripts/spec/work.py --help` and
`python scripts/spec/gen_ledger.py -h` piped into `head`) and by the w1051z implementer
(`python scripts/filter_population.py --help`, its report's lead, code site `scripts/filter_population.py:312`).

**Repro:** in Git Bash or PowerShell on Windows, with `PYTHONIOENCODING` unset, `python scripts/spec/work.py --help | head`
→ `UnicodeEncodeError: 'charmap' codec can't encode character '⛔'` from `argparse.print_help`, exit 1. With
`PYTHONIOENCODING=utf-8` it prints. The cause is the console encoding (cp1252 when stdout is a pipe), not the help
text: the scripts' module docstrings, used as `description=__doc__`, carry ⛔ and ⭐.

**Sweep (2026-10-10, branch w1051v-pb2914):** 10 Python scripts under `scripts/` and `.claude/skills/` use argparse,
contain non-ASCII text and never call `sys.stdout.reconfigure`. Some other scripts already reconfigure (e.g.
`scripts/hooks/dispatch_guard.py` reconfigures stderr): the fix exists, it is applied by hand, file by file.

**Fix (rule 5, one place):** one shared way every script starts its stdio as UTF-8 (a helper every entry point calls,
or `PYTHONUTF8=1` set where the scripts are launched: the hooks' environment, `.claude/settings.json` env, the loop's
child environment, CI), chosen so a NEW script cannot regress; and a drift test that runs `--help` of every argparse
script under a cp1252 stdout and requires exit 0.

**Owner direction (2026-10-10 18:12 PDT):** "this would work if the compiler startup (plus likely test cases) set the
console output encoding to UTF-8". So the console output encoding is set to UTF-8 at STARTUP, in the program, and by
the test cases that launch it. The environment variable alone does not do it.
The compiler already does this: `src/Cobol.Net.Runtime/IO/StandardStreams.cs#EnsureUtf8` (kb/Work PB899) is called
first thing by the `cobol` CLI (`src/Cobol.Net.Cli/Program.cs#Main`) and by every RUN program
(`ProgramTable.RunMain`), and its remarks record why it is one shared helper rather than an `if` per entry point.
The scripts have no equivalent. A census on 2026-10-10 (main 316a9d731) found about 25 hand-copied
`sys.stdout.reconfigure(encoding="utf-8")` / `stream.reconfigure(...)` calls, each written differently (stdout only,
stderr only, with or without `errors="replace"`, at import time or inside `main`), plus `PYTHONIOENCODING`/`PYTHONUTF8`
set by three test harnesses (`tests/_shared/PythonInstrument.cs`, `scripts/self_tests.py`, `scripts/arch/test_wf_r2_review.mjs`).
The fix is the scripts' counterpart of `EnsureUtf8`: one shared Python helper that every entry point calls at startup
(stdout and stderr, once per process, safe on a host with no console). Every hand-copied `reconfigure` call is
replaced by it in the same change (CLAUDE.md rule 4: no second mechanism stays behind). The test harnesses that launch
scripts keep setting UTF-8 for the child, as the owner's "plus likely test cases" asks. The drift test above
requires every argparse entry point to call the helper.
