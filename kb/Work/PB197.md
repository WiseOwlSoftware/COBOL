# PB197 — LANDED — the declined arithmetic mode was accepted in silence by two unit kinds

## Measured before believed, and then swept

The finding named ONE arm (METHOD-ID). Probing it confirmed the hole and, because every bug is a pattern, the
sweep went over **all six grammar productions that carry an `optionsParagraph`**. At `--std 2014`, before the fix:

| Unit kind (grammar production) | COBOLNET0806 |
|---|---|
| PROGRAM-ID · FUNCTION-ID (`identificationParagraph`) | yes |
| CLASS-ID (`classDefinition`) | yes |
| FACTORY (`factoryParagraph`) | yes |
| OBJECT (`objectParagraph`) | yes |
| **INTERFACE-ID (`interfaceDefinition`)** | **NO — exit 0, no diagnostic** |
| **METHOD-ID (`methodDefinition`)** | **NO — exit 0, no diagnostic** |

At `--std 2023` the method arm drew only COBOLNET0903, the obsolescence *warning* — which reads like a handled
case and is not the non-support screen at all. At `--std 2002` it drew COBOLNET0900, the introduction gate, so
the one edition where the mode does not exist was the only one that said anything.

**The interface arm was a second, different bug.** The method arm was a screen in the wrong place; the interface
arm had no `OptionsBinder` call at all — `OoDriver.BindInterfaceData` never bound the skeleton's OPTIONS
paragraph, so its clauses had no effect on the prototypes either (§10.6.1 / §11.9.4 GR1). Fixing only the screen
would have left it hollow.

## Why it matters

§4.2.6 requires "An implementation shall provide a warning mechanism at compile time to indicate use of
syntactically-detectable processor-dependent language elements not supported by that implementation". Two of the
seven unit kinds had none, so a method could select an arithmetic mode COBOL.NET does not implement and be
compiled without a word — and §8.8.1.4.1 makes that mode "a method of evaluating an arithmetic expression, an
arithmetic statement, the SUM clause, and certain integer and numeric functions", i.e. it governs the unit's
whole arithmetic. Silent, and under-rejecting.

## The fix — one construction point, not a third copy

- The screen moved to **`OptionsBinder.ArithmeticOf`**, where the clause is READ. Every unit kind's OPTIONS
  paragraph reaches `OptionsBinder.BindParagraph`, so all six productions are covered by construction rather
  than by six remembered call sites. The `DataBinder.cs` twin is **deleted**.
- Screening the CLAUSE rather than the resulting MODEL keeps §11.9.4 GR1 inheritance quiet: a contained unit
  that merely inherits a container's mode wrote nothing and is not diagnosed twice. Measured after the fix:
  every one of the seven arms draws **exactly one** COBOLNET0806.
- `OoDriver.BindInterfaceData` now binds the interface skeleton's OPTIONS paragraph — the missing call.
- The diagnostic text was corrected while it moved: it said "is an obsolete feature … and is not supported",
  which names a fact that grants nothing. The ground is **processor-dependence** (A.3 item 2 + §4.2.6); see
  [[PB198]].

## The drift test, and what makes it one

`ArithmeticModeScreenDriftTests` reads the options-bearing productions **out of the `.g4` files** and requires a
fixture per production, so a NEW options-bearing unit kind fails the test until it is covered — the difference
between "the arms we knew about are screened" and "every arm is". Proven to fail: removing the
`interfaceDefinition` fixture produces
`grammar : … interfaceDefinition …` / `fixtures: …` and a red test naming exactly what is missing.

It also pins the per-edition diagnostics **with their absences** — 2002 → 0900 + 0806, 2014 → 0806 alone,
2023 → 0806 + 0903 — after a falsification attempt showed the negative corpus alone could not tell the two
edition legs apart (0806 fires at 2002 as well, so swapping the 2002 case's expected code still passed).
