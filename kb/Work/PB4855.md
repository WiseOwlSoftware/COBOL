# PB4855 - operands held only as a DataItem are never references to the debug reach walk (BoundTableSortKey.Key, BoundSort.Table, BoundAddressOf.Item, BoundAllocate.Based, BoundSetAddress), and INITIALIZE of a whole OCCURS DYNAMIC table has no written place

**What the report says.** Round-1 lead (stands): operands held only as a `DataItem` (no place) are never references: `BoundTableSortKey.Key`, `BoundSort.Table` (SORT format 2), `BoundAddressOf.Item`, `BoundAllocate.Based`, `BoundSetAddress`; `BoundReferences.Visit` (`Enters`).

New defect 1: INITIALIZE of a whole OCCURS DYNAMIC table has no written place (`InitializeBinder.BindInitializeTarget`, dynamic arm): its element stores stay references; needs a place for the table.

**Not probed.** The report names no program for either lead and the clerk reproduced neither.

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundSort.cs` (`BoundTableSortKey.Key`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundSort.cs` (`BoundSort.Table`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundTree.cs` (`BoundAddressOf.Item`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundTree.cs` (`BoundAllocate.Based`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundTree.cs` (`BoundSetAddress`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundReferences.cs` (`BoundReferences.Visit`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs` (`InitializeBinder.BindInitializeTarget`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundInitialize.cs` (`BoundInitialize.Written`).

Filed from review leads of waves 20261884 and 20261885 by the enqueue clerk; the lead's claim is the reviewer's, not adjudicated here.

**Partly landed (wave 20261887 A).** Re-probed: `ALLOCATE BP`, `SET ADDRESS OF BQ TO P` and `SET P TO ADDRESS OF AX` ran no section for
ALL REFERENCES OF BP, BQ and AX (2002 compile with `--permissive`, the one compile that has both the verb and the removed facility). The three
arms that name a data item with a place of its own now carry it: `BoundAllocate.Written`, `BoundPointerReceiver.BasedWritten` and
`BoundAddressOf.Written` (the place the operand wrote, built by `PtrBinder.BasedPlace` and `ReferenceResolver.ResolveForAddressOf`), and the
reach walk reads them like every other place (`DebugFacilityTests.PointerVerbOperands_AreReferences`).

**Still open: the WHOLE-TABLE family.** `BoundTableSort.Table`, `BoundTableSortKey.Key` (SORT Format 2), the table `SEARCH` names (PB4854's second
sentence) and the whole OCCURS DYNAMIC table of `INITIALIZE` are operands that name a table, or an item under one, WITHOUT its subscripts, and the
compiler has no place for that: `PlaceBuilder.PlaceForItem` answers `DeferredShape.DynamicWholeTable` or null for an unsubscripted OCCURS item,
and nothing renders the storage image of a whole table, which general rule 24 c (the content of the data item referenced) needs for
DEBUG-CONTENTS. The fix is a whole-table place with an image (a redesign of the place model beyond this slice), after which each of the four
statements names it as it names its other written operands; until then those four references run no section.

**Re-probed, wave 20261905 A (still open, deliberately).** `SORT T ASCENDING` (Format 2) with `USE FOR DEBUGGING ON ALL REFERENCES OF T`, compiled
`--std 2002 --permissive` (probe `E:/COBOL-coord/scratch/w20261905a/run/probe4855.cob`), runs the section for the three `T (n)` of the DISPLAY and NOT for
the SORT: the whole-table family above is unchanged. It is not a reach gap alone: `BoundReferences` could yield the `DataItem` the statement names
(as wave 20261905 did for the counter registers, `Reach.Registers`), but rule 24 c's DEBUG-CONTENTS, "the content of the data item referenced", is
the storage image of the WHOLE table, which no emitter renders for a typed element array, a shared REDEFINES area or a dynamic table without a new
place kind (`WholeTablePlace`) and its image arms in `PlaceRenderer`, the storage-form and usage passes, and the place drift tests. That redesign stays
the next slice of this note.

**Re-probed, wave 20261915 A (still open).** The same probe (`E:/COBOL-coord/scratch/w20261915a/p/probe4855.cob`, `--std 2002 --permissive`) prints `DB1 T` for each
MOVE and for the DISPLAY and nothing for `SORT T ASCENDING`: the whole-table family is unchanged. The wave's group was the messaging root; the `WholeTablePlace`
redesign above is a separate mechanism and stays the next slice of this note.

**Landed (wave 20261921 E): the whole-table family.** Re-probed first on 6e542f8204: `SEARCH T` at `--std 85` (probe
`E:/COBOL-coord/scratch/w20261921e/p/srch.cob`) ran the ALL REFERENCES OF T section only for the WHEN phrase's `T (TX)`, `SORT T ASCENDING`
with `USE FOR DEBUGGING ON T` (`srt.cob`, `--std 2002 --permissive`) ran nothing, and `INITIALIZE T` of an OCCURS DYNAMIC table with
`USE FOR DEBUGGING ON T` (`dyn.cob`, `--std 2023 --permissive`) ran nothing. The fix is no new place kind: a whole table IS the
`TableAllPlace` enumeration (ISO/IEC 1989:2023 §2023:15.3, "as if each table element associated with that subscript position were
specified"), built by ONE builder, `PlaceBuilder.WholeTable(item, outer)` (the enclosing occurrences the statement names as fixed
subscripts, every remaining level ALL over its current count), and each statement holds it as its written operand:
`BoundSearch.Table` (identifier-1; the enclosing occurrence is identifier-1's subscripts, now read for every nested table, else the WHEN
phrases' first reference, now captured for every nested table), `BoundTableSort.Written` and `BoundTableSortKey.Written` (a key data-name
the statement writes), and `BoundInitialize.Written` on the whole-dynamic-table arm. The reach walk and `BoundStores` (the table SORT arm is
now `ReadWrite` for both) read them like any other place. DEBUG-CONTENTS of such a reference is `CobolTable.AllImage` (the occurrences'
storage images in storage order, the walk `AllArgs` shares, empty at a count of zero), DEBUG-SUB-n the enclosing occurrence and spaces for
the levels it ranges over (`DebugTriggerEmitter.OccurrenceNumbers` stops at the place's own index vector), and DEBUG-CONTENTS is sized to
every occurrence of a target (`RecordLayout.AllOccurrencesImageWidth`, rule 15). Determinations: docs/CONFORMANCE.md D-DEBUG-WHOLE-TABLE.
Witnesses: `conformance:cases/_unassigned/pb4855-debug-whole-table-search` (85), `DebugFacilityTests.TableSortOperands_AreWholeTableReferences`,
`DebugFacilityTests.InitializeWholeDynamicTable_IsOneWholeTableReference`.
