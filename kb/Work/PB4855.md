# PB4855 - operands held only as a DataItem are never references to the debug reach walk (BoundTableSortKey.Key, BoundSort.Table, BoundAddressOf.Item, BoundAllocate.Based, BoundSetAddress), and INITIALIZE of a whole OCCURS DYNAMIC table has no written place

**What the report says.** Round-1 lead (stands): operands held only as a `DataItem` (no place) are never references: `BoundTableSortKey.Key`, `BoundSort.Table` (SORT format 2), `BoundAddressOf.Item`, `BoundAllocate.Based`, `BoundSetAddress`; `BoundReferences.Visit` (`Enters`).

New defect 1: INITIALIZE of a whole OCCURS DYNAMIC table has no written place (`InitializeBinder.BindInitializeTarget`, dynamic arm): its element stores stay references; needs a place for the table.

**Not probed.** The report names no program for either lead and the clerk reproduced neither.

**Sites:** `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundSort.cs` (`BoundTableSortKey.Key`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundSort.cs` (`BoundSort.Table`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundTree.cs` (`BoundAddressOf.Item`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundTree.cs` (`BoundAllocate.Based`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundTree.cs` (`BoundSetAddress`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundReferences.cs` (`BoundReferences.Visit`), `src/WiseOwl.Cobol.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs` (`InitializeBinder.BindInitializeTarget`), `src/WiseOwl.Cobol.Compiler/Binding/Bound/BoundInitialize.cs` (`BoundInitialize.Written`).

Filed from review leads of waves 20261884 and 20261885 by the enqueue clerk; the lead's claim is the reviewer's, not adjudicated here.

**Partly landed (wave 20261887 A).** Re-probed: `ALLOCATE BP`, `SET ADDRESS OF BQ TO P` and `SET P TO ADDRESS OF AX` ran no section for
ALL REFERENCES OF BP, BQ and AX (2002 compile with `--permissive`, the one compile that has both the verb and the removed facility). The three
arms that name a data item with a place of its own now carry it: `BoundAllocate.Written`, `BoundPointerReceiver.BasedWritten` and
`BoundAddressOf.Written` (the place the operand wrote, built by `PtrBinder.BasedPlace` and `ReferenceResolver.ResolveForAddressOf`), and the
reach walk reads them like every other place (`DebugFacilityTests.PointerVerbOperands_AreReferences`).

**Still open: the WHOLE-TABLE family.** `BoundTableSort.Table`, `BoundTableSortKey.Key` (SORT Format 2), the table `SEARCH` names (PB4854's second
sentence) and the whole OCCURS DYNAMIC table of `INITIALIZE` are operands that name a table, or an item under one, WITHOUT its subscripts, and the
compiler has no place for that: `PlaceBuilder.PlaceForItem` answers `DeferredShape.DynamicWholeTable` or null for an unsubscripted OCCURS item,
and nothing renders the storage image of a whole table, which general rule 24 c (the content of the data item referenced) needs for
DEBUG-CONTENTS. The fix is a whole-table place with an image (a redesign of the place model beyond this slice), after which each of the four
statements names it as it names its other written operands; until then those four references run no section.
