# A6 — PERFORMANCE BENCHMARK + GENERATED-CODE COST MODEL

- PERFORMANCE BENCHMARK + GENERATED-CODE COST MODEL — compile throughput (large programs/copybooks), Tier-B string-canonical storage cost, PC-dispatcher overhead, MOVE-heavy loops, file-I/O throughput, allocation profile
- "Commercial-quality" has ZERO perf evidence; a storage-model surprise is cheap to fix before P15/P16 lock the architecture and the legacy comparison dies
- An in-repo benchmark suite (CI-trended) + the cost model + any architecture-decision escalations
- **P14 Step 12** (new — the perf gate; a P15 precondition)
- PENDING

**2026-10-06 (R69):** kb/Work PB2117 is this gate's instrument — the in-repo benchmark suite, the whole-population
gate time and the recorded baseline the architecture review's waves compare against. The comparison is GnuCOBOL
under WSL and the self-relative baseline, never the legacy engine (an engine compiling a different
subset is not a baseline), so PB2110 (the delete) did not wait on A6. PB2117 lists A6 in its `cluster`.

**2026-10-07 (PB2117 landed: the instrument exists, and its first answers).** `scripts/arch/perf_baseline.py` records
the baseline at `docs/rearchitecture/evidence/perf-baseline/354c79ef3312.md` (product commit `354c79ef3312`, two
sessions, conditions and noise band in the record), and `--against` compares any later tree with it. What it
measured against GnuCOBOL 3.2 (`cobc -x -O2`) on the same WSL kernel and file system, each net of its own start-up
floor:

- **PERFORM dispatch is not the cost.** `PERFHOT` (5,000,000 passes) runs in 391 ms against GnuCOBOL's 566 ms
  (0.7x) and allocates 4.9 KiB per run: the paragraph dispatcher is cheaper than libcob's.
- **The storage model is the cost (the Tier-B question, answered).** `MOVEHOT` is 3.0x GnuCOBOL (947 against
  312 ms) and allocates 1.72 GiB per run, about 926 bytes per pass: every alphanumeric MOVE, every DISPLAY-numeric
  group member and every group MOVE builds a new string (`CobolString.Store`, `CobolString.SpliceInto`,
  `CobolNum.FormatImage`, and `AsImage` then `FromImage` in the generated loop). `SEQHOT` is 2.8x (621 against
  220 ms) and allocates about 1.3 KB per record written and read. Both scale linearly, so this is a constant factor,
  not a complexity defect: an architecture-decision escalation for the storage model, not a bug fix.
- **Indexed files are a complexity defect.** `IDXHOT` is 60x GnuCOBOL at 2,000 records, 138x at 4,000 and 330x at
  8,000; ours grows 3.3x and then 3.8x per doubling, GnuCOBOL 1.4x and 1.6x. `IndexedConnector` keeps the file as an
  unindexed record list: a random READ is a linear scan (`FindRandom`), every WRITE scans for a duplicate key, and
  `Ordered()` sorts the whole file on every sequential READ NEXT. Reported to the orchestrator as a new defect lead.
- **Compile throughput.** Warm, a full compile of the largest NIST program (IX113A, 5,816 lines) takes about 430 ms,
  of which the front end and bind are about 60 ms, so the backend dominates. A cold `cobol` process takes 2.3 s on
  a quiet host, most of it start-up rather than compilation.

Still open here: the generated-code COST MODEL (per construct, from the allocation figures) and the storage-model
escalation itself, which needs an owner decision on the record representation.
