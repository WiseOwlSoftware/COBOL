# PB3409 — `drop_remote` treats an already-deleted remote branch as a failure and never prunes its tracking ref

Found by the enqueue unit's `prune_worktrees.py --apply` run, 2026-10-18 22:15 PDT (log
`E:\COBOL-coord\scratch\prune-apply-20261018-2215.log`).

**Mechanism.** `scripts/prune_worktrees.py#drop_remote` (main 49e1c6b79, lines 880-892) decides from
`refs/remotes/origin/<branch>`, a remote-tracking ref that nothing prunes. GitHub already deleted the head branch at
merge (`delete_branch_on_merge`, `scripts/orchestrator/ruleset.py:15`), so the tracking ref is stale, and
`git push origin --delete <branch>` fails with `remote ref does not exist`. The tool then prints
`could not delete origin/<b>: error: unable to delete '<b>': remote ref does not exist error: failed to push some refs`.
In the 22:15 run that was 13 of the 14 removed branches (one real delete). The stale tracking ref stays behind: `git
branch -r` listed 178 refs while `git ls-remote --heads origin` listed 21.

**Harm.** Every apply prints a wall of `error:` lines, so a REAL push failure (authentication, a protected ref) is
buried in the noise (a loud failure turned into noise), and any reader of `refs/remotes/origin/*` sees about 157
branches that no longer exist.

**Fix shape.** Treat `remote ref does not exist` as already gone and delete the stale tracking ref
(`git update-ref -d refs/remotes/origin/<branch>`), or run `git fetch --prune origin` once before the deletes; either
way only a failure that is not "already gone" is reported as an error. Self-test arm with a bare remote whose branch is
deleted behind the tracking ref: no error line, the tracking ref gone; and an arm where the push really fails, which
still reports.
