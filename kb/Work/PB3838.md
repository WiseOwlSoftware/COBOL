# PB3838 — record every GnuCOBOL defect and ISO departure, reproducibly, for upstream

**Sites:** `scripts/spec/work.py#KINDS`, `scripts/spec/work.py#check`, `scripts/spec/work.py#actionable`,
`scripts/spec/work.py#HARM_FLAGS`, `scripts/spec/work.py#upstream_problems`, `scripts/spec/work.py#body_sections`,
`scripts/spec/work.py#fenced_blocks`, `scripts/spec/work.py#upstream_findings`,
`scripts/spec/work.py#self_test`, `scripts/spec/work.py#_upstream_fixture`, `kb/Work.base`, `scripts/differential_fuzz.py#open_fuzz_notes`,
`scripts/gnucobol_differential.py` (whole: the change adds a new member and its call sites in this file)

## The defect

Our two differentials judge every disagreement with GnuCOBOL, and each night's triage sorts out the GnuCOBOL side:
`GNUCOBOL-SIDE` 54 signatures (209 programs) on the fourth fuzz night and 50 (243) on the fifth
(`docs/rearchitecture/evidence/fleet-optimization/2026-10-24-differential-fuzz-fourth-night.md`,
`2026-10-26-differential-fuzz-fifth-night.md`); the 2026-10-21 overnight record has a section "The GnuCOBOL side: bug or
choice". Among them are clear defects (cobc segfaults on a program that CALLs itself, an internal compiler error on
BYTE-LENGTH, intrinsic functions it compiles and then does not implement at run time, a floating-insertion hole on
`-B-B-B9`), places where it is stricter than the standard under `-std=cobol2014`, and 2014 features it lacks.

None of that is recorded in a form anyone could file upstream. The findings are prose sentences in evidence documents,
grouped by family, with counts. No record carries the minimal program, the exact `cobc` command, the observed output,
or a checked ISO citation. The witness programs exist only in `conformance-suite/results/fuzz-2026102*/programs`
(git-ignored, on this machine only: 28,927, 20,184, 22,407 and 26,921 files in the four night-run directories still
present on 2026-10-26), so a disk failure
or a cleanup loses every repro. A later attempt to report one would redo the investigation from nothing.

## What a record must carry (the bar; a record missing any item is not done)

1. **A minimal test case**: the smallest program that shows the behaviour, written by us or reduced from our own fuzz
   output, in the note body, its reference format stated. Never text from GnuCOBOL's GPL testsuite or its expected
   output (licensing: the differential's corpus is GPL; cite only its group titles and keywords).
2. **The exact environment**: the cobc version (3.2.0, Ubuntu `gnucobol3 3.2-4build1` under WSL), the full command and
   flags (`-std=cobol2014 -x`, `-fsyntax-only`, `-free`), and how the program was run.
3. **The observed result**: cobc's diagnostic text, the program's output, the exit code, the crash or internal-error
   message.
4. **The expected result per ISO**: the clause and rule number, validated with `python scripts/spec/cite.py --check`,
   the edition (the one the `-std` flag claims: 2014 for `-std=cobol2014`), and a short quote of the rule. A behaviour
   only ISO/IEC 1989:2023 requires is a feature request, never a bug against 3.2.
5. **The class**: crash or internal compiler error · wrong output · rejects legal ISO source · accepts source the
   standard forbids, under a strict `-std` · compiles but is not implemented at run time · feature missing.
6. **Our compiler's result** on the same program: the second implementation, and the reasoning the record relies on.
7. **The fix site in GnuCOBOL** for the patch route: file and function in the 3.2 source
   (`tests/external/gnucobol-3.2.tar.xz`), read observationally, never copied.
8. **The upstream state**: the date the GnuCOBOL tracker was searched for a duplicate (and what was found), the upstream
   revision the repro was re-run on, the ticket or patch link once filed, and a draft issue title and body.

## Excluded (not GnuCOBOL defects)

Implementor latitude (the triage's `LATITUDE`), `NOT-COMPARABLE` and `UNINITIALIZED` rows, harness artifacts (`cobc -x`
refusing `PROCEDURE DIVISION USING`), and our own documented extensions (`-std=cobol2014` refusing COMP-1 and COMP-3).

## The plan (this campaign, tier order)

1. **The register (LANDED, tier 1: see "The record format" below).** An `upstream` note kind in `work.py` (`KINDS`), with its own fields (the eight items above as
   frontmatter where they are structured: `upstream_project`, `upstream_version`, `upstream_class`, `upstream_status`
   unreported · reported · fixed-upstream · declined · duplicate, `upstream_ref`), checked by `check`, excluded from
   `actionable` (it ranks nothing in our Fix next: its harm flags describe a GnuCOBOL user), a `kb/Work.base` view, and
   a drift test. One Opus implementer.
2. **Harvest before anything else** (the repros are on one machine): one mechanical agent collects every
   `GNUCOBOL-SIDE` signature of every night, plus the GnuCOBOL-testsuite differential's per-case results where ISO
   sides with us and the `kb/Work` adjudications and `docs/CONFORMANCE.md` entries that record GnuCOBOL contradicting a
   rule ISO controls; deduplicates them into families; copies each family's witness programs out of the git-ignored
   directories into the coordination scratch.
3. **Reduce, cite, classify**: one Opus adjudicator per family, about four wide, checkpointed per family: reduce to a
   minimal repro, run cobc under WSL, derive the ISO expectation from the spec and check the citation, record the
   GnuCOBOL source site. Every "GnuCOBOL is wrong" verdict goes to an independent refuter before it is filed, because
   it is meant for publication.
4. **File** each surviving finding as an `upstream` note (a clerk, from the structured report).
5. **Make the next case automatic**: the fuzz triage brief files its `GNUCOBOL-SIDE` findings directly as `upstream`
   notes to this bar, so no later night's findings fall back to prose.
6. **Later, owner-gated, the filing itself**: build GnuCOBOL's current development branch under WSL (the 3.2 release
   does not build with GCC 15) and re-run every repro on it; search the tracker for duplicates; the owner approves the
   exact text of every issue before it is posted. Patches: GnuCOBOL takes bug reports through its SourceForge ticket
   system and keeps its main repositories in Subversion; its source copyright is reported to be held by the FSF, which
   asks contributors to its packages for a copyright assignment. Both are to be verified before the first patch.

## Standing requirements

- Every record meets the eight-item bar above; a finding that cannot yet meet it stays in the harvest, never filed half.
- Nothing is posted or submitted outside WiseOwlSoftware without the owner's approval of the exact text or diff.
- No GnuCOBOL source, testsuite program or expected output is committed or quoted at length (GPL).

## The record format (tier 1, landed 2026-10-27)

`kind: upstream` (`work.py` `KINDS`), checked by `upstream_problems` on every `work.py check` and held by `upstream_findings`
in `work.py --self-test` (the drift test of the kind). Frontmatter: `upstream_project`, `upstream_version` (the exact release the
repro ran on), `upstream_class` (`crash` · `wrong-output` · `rejects-legal-source` · `accepts-forbidden-source` ·
`not-implemented-at-run-time` · `feature-missing`), `upstream_edition` (`1985` · `2002` · `2014` · `2023`, the edition the `-std`
claims), `upstream_status` (`unreported` · `reported` · `fixed-upstream` · `declined` · `duplicate`), `upstream_ref` (the ticket or
patch link; required once not `unreported`, refused while `unreported`), `spec_refs` (the checked clauses, non-empty). The record sits
outside every list of OUR work by one rule: it must be `process_only: true` and name no `cluster`, `tier`, `blocked_by`,
`inventory_rows` or `closes_rows` (relate it with `related:`), so `actionable`, `next`, the planner's lanes, the ledger's
compiler-work counts and the fuzz cadence's open-note rule (`open_fuzz_notes`), which read those fields and `process_only` but not
`kind`, never see it. Its harm flags (set freely) describe the GnuCOBOL user. Its `status` is terminal exactly when `upstream_status`
is `fixed-upstream`, `declined` or `duplicate`. An edition-2023 behaviour must be class `feature-missing` (a feature request, never a
bug against 3.2). Body: one non-empty `##` section per item of the bar, headed `Minimal test case`, `Environment`,
`Observed result`, `Expected result` (per ISO), `Our compiler` (our result), `Fix site` (in the other project's source),
`Upstream state` (the duplicate search, the revision re-run, the link) and `Draft issue`; no fenced block over 60 lines (a longer
one is how GPL testsuite text is committed). `kb/Work.base` has the `Upstream records` view and keeps the kind out of `Open but no
harm flag set` (`check_base_agrees`). The records are filed (tier 4): see "Filed (tier 4)" below.
