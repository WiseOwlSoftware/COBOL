## Mechanism
`src/WiseOwl.Cobol.Runtime/Values/Numeric/CobolDec.cs#FromDouble` (line ~52) converts the binary64 operand to its
shortest-decimal image; `FloatResultant.FromDec` then lands the standard-decimal result into binary64 under the
implied TRUNCATION of §14.7.4.3 10), which rounds toward zero one ulp below 0.1. The w61e implementer found that an
exact 34-digit conversion does not cure it either.

## To decide
An owner-visible determination under §8.8.1.5.1 (the implementor-defined conversion of a binary operand to
standard-decimal form): accept and document (DOC row) or choose a conversion/landing that round-trips. Survey
GnuCOBOL / IBM per CLAUDE.md rule 1 first.

## Re-filed as a defect (analyses sweep, 2026-10-23)

Adjudicated read-only by an Opus cobol-adjudicator on main e7cf38ce4; accepted by the Mythos session.

Under STANDARD-DECIMAL (and STANDARD 2002, which shares the engine) a lone floating-point operand is never lifted into the SDIDI: NumericRenderer lifts float operands to CobolDec only at an operator (DecBinary, Negate), so COMPUTE r = F1 lands the binary64 natively (exact expansion), while COMPUTE r = F1 + 0 converts through CobolDec.FromDouble's shortest round-trip decimal. §8.8.1.5.1 makes standard-decimal the method of evaluating 'an arithmetic expression, an arithmetic statement', a lone identifier included, and leaves only the conversion MECHANISM to the implementor: one mechanism, not two. Repro probes/pb1606/t.cob: lone .1000000000000000055 vs +0 .1000000000000000000; F4 0.1 vs F2 0.09999999999999999. The note's own question: the one-ulp-low float landing is rule-following under the implied TRUNCATION of §14.7.4.3 2) for every conversion that rounds to nearest (correctly rounded decimal128 0.1000000000000000055511151231257827 is also below binary64 0.1), so it is not a defect once the lone path converts too. Fix: lift every float operand of an SD-evaluated statement through ONE conversion; choose it and write the §8.8.1.5.1 determination into docs/CONFORMANCE.md. Recommended: the correctly rounded 60559 convertFormat (34 digits), which matches native's documented exact-expansion choice (CONFORMANCE 'Why the exact expansion and not the shortest-round-trip decimal') over the shortest round-trip. GnuCOBOL, IBM and MF have no standard-decimal mode to survey. Goldens: lone vs +0 vs *1 into V9(19) and FLOAT-LONG under SD.

Evidence: Re-run under ARITHMETIC IS STANDARD-DECIMAL, FLOAT-LONG F1 = 0.1: COMPUTE F4 = F1 gives 0.1 but COMPUTE F2 = F1 + 0 gives 0.09999999999999999; into PIC V9(19), COMPUTE D = F1 gives .1000000000000000055 (the exact expansion) but F1 + 0 and F1 * 1 give .1000000000000000000 (CobolDec.FromDouble's shortest round-trip). In decimal128, x + 0 and x * 1 equal x, so one statement mode has two float-to-SDIDI conversions.

## Landed 2026-10-23

**Re-probe (own build, `probes/pb1606/t.cob`).** Reproduced as filed: `COMPUTE F4 = F1` 0.1 but `COMPUTE F2 = F1 + 0`
0.09999999999999999; into `PIC V9(19)` the lone form `.1000000000000000055` and `F1 + 0` / `F1 * 1` `.1000000000000000000`.

**Root cause.** Two float-to-SDIDI conversions in one statement mode: a float item that was the whole expression
reached `ArithmeticEmitter.StoreArith` as a binary64 and landed natively (its exact expansion), while an operand beside
an operator went through `NumericRenderer.DecOperandExact` and `CobolDec.FromDouble`, the shortest round-trip decimal.

**Fix.** One conversion, `CobolDec.FromBinary64(d, mode)`: the binary64's exact value rounded once to 34 digits under
INTERMEDIATE ROUNDING (§8.8.1.5.2 r1, the mode exactly as every other operand that "cannot be expressed exactly in an
SDIDI"), read from the runtime's exact formatter (`E766`) with the digits past the 38th folded into one sticky bit and
rounded by the existing `Round34` funnel (ties, PROHIBITED and the range clamp stay in one place; no `BigInteger`).
`StoreArith` converts a lone float operand through `DecOperand`; `DecOperandExact` converts every other float item
through the same function. `CobolDec.FromDouble` is gone: an implementor-defined APPROXIMATION (a §15.4.1 function's
returned value, a non-integer power) keeps the shortest decimal as `CobolDec.FromApproximation`. The floating-point
numeric-edited sender (`CobolEdit.FormatFloatStore` / `TryFormatFloat`, which used the same shortest decimal) now reads
the exact value (`FromBinary64ToOdd`), so `ROUNDED MODE IS PROHIBITED` sees 0.1 as inexact there as it already did for
a fixed-point receiver. The determination, with its consequences, is in docs/CONFORMANCE.md section 3 and numeric
design D3.

**Decision recorded for the owner.** The 0.09999999999999999 the note was filed for is not removed, it is made
consistent: under implied TRUNCATION (§14.7.4.3 r2, r10) every correctly rounded float-to-decimal conversion of 0.1
lands one ulp low in a binary float receiver, so `COMPUTE F2 = F1` now stores it too. And a COMP-2 holding 0.1 no longer
equals the literal 0.1 under STANDARD-DECIMAL (`IF F = 0.1` false). Reversing either is one function (`FromBinary64` to
the shortest decimal) plus the same documentation.

**Witnesses.** `8.8.1.5.2-.../pb1606_float_item_conversion` and `_intermediate_even` / `_truncation` / `_prohibited`,
`14.6.8.4-.../pb1606_float_sender_exact_value`, the negative `pb1606-float-item-standard-decimal-below-2014`,
`CobolDecBinary64ConversionTests` (an independent BigInteger oracle over 680 doubles in three modes) and
`FloatItemSdidiLiftDriftTests`. Goldens whose expected value rested on the shortest decimal were re-derived from the
rule: `arith_standard` (W5), `pb253_prose_float_*` (the float-receiver channel compared two float receivers),
`pb3017_sdidi_divide_remainder_beyond_the_int128_carrier` (1.0E+30 as a double is 1000000000000000019884624838656).
