# PB570

## Mechanism
the WITH NO SIGN phrase is read from the ENTRY'S OWN usageClause only, so a group-level `USAGE PACKED-DECIMAL WITH NO SIGN` loses BOTH its SR31 screen and its GR11 storage effect - the inherited leaf keeps the SIGNED layout with no diagnostic

### The refutation this note is written from
Row `SR-13.18.40.3-31` was adjudicated CONFORMS and OVERTURNED to `PARTIAL` by the refuter. Its reasoning, verbatim:

> REFUTED -- the exact two-arm-dispatch shape the SR30 record was praised for avoiding, one row later. DataBinder.cs:2342 sets `noSign = usage.noSignPhrase() is not null` from the ENTRY'S OWN usageClause, and the SR31 test at :2647-2657 runs only inside that entry's bind, so the GROUP-INHERITED arm is never asked. 13.18.60.4 GR1 (If the USAGE clause is specified or implied at a group level, it applies only to each elementary item in the group) makes a group-level USAGE PACKED-DECIMAL WITH NO SIGN apply to every elementary item -- and that is the project's OWN reading, since the group-inherited USAGE NATIONAL leg cites 13.18.40.3 SR30 by number in its message. So `01 G USAGE PACKED-DECIMAL WITH NO SIGN. 05 W1 PIC S9(4).` is exactly what SR31 forbids and it compiles clean, at two nesting depths. The entry's own arm is solid (full USAGE spelling, bare usage word, lowercase -- all COBOLNET1566), so one arm of two: PARTIAL. A second, larger fact makes the omission unmistakable rather than debatable: the group's NO SIGN phrase is dropped WHOLESALE, not merely unchecked -- FUNCTION LENGTH(G) is 3 for the signed leaf AND 3 for an unsigned leaf under the same group header, while an own-entry PIC 9(4) PACKED-DECIMAL WITH NO SIGN is 2 bytes against 3 for plain packed. So 13.18.60.4 GR11's storage effect is silently lost for every inherited item too (a WRONG-STORAGE finding belonging to 13.18.60.4 GR11's row, outside this part -- reported here because it is the same root cause). Even under the narrowest reading of 'specified for the subject of the entry' the implementation is wrong: on that reading the group-level phrase is legal and must still take effect, and it does not.

### Inventory row `GR-13.18.60.4-11` (PARTIAL)
Every clause of the rule was measured with the pinned compiler. "a radix of 10 is used" and "each digit position shall occupy the minimum possible configuration" - binary-coded decimal, two digit positions per byte: probe p49 moves 123 into a `PIC S9(3) PACKED-DECIMAL` inside a group and reads the group image byte by byte with FUNCTION ORD - 0x12 0x3C for +123, 0x12 0x3D for -123, i.e. the digits packed two per byte with a trailing sign nibble. "Each implementor specifies the precise effect …, including the representation of any algebraic sign" - the determination is docs/CONFORMANCE.md §7 item 215 (BCD, two digits per byte, most significant first, trailing sign nibble C/D). "Sufficient computer storage shall be allocated … to contain the maximum range of values implied by the associated decimal picture character-string" - PicInfo.StorageWidth is `Digits/2 + 1`, which is exactly ceil((Digits+1)/2) sign nibble included; probe p7 confirms 3 bytes for S9(5) and for 9(4), 6 for S9(9)V99. THE 2023 WITH NO SIGN PHRASE (Annex E.3.2 item 5 - "The USAGE clause has been enhanced to allow the representation of a PACKED-DECIMAL data item in the storage of the computer to contain no sign value"): "reserves no storage for representing any sign value" - StorageWidth becomes `(Digits+1)/2`; probe p7 gives 2 bytes for `PIC 9(4) … WITH NO SIGN` against 3 for plain packed, probe p49 reads the image as 0x12 0x34 for 1234 with no sign nibble at all, and conformance:2023/usage_packed_no_sign pins the even-digit delta (9(6): 4 vs 3) with expectations derived from the rule. "The PICTURE character string of the data item shall not contain the symbol 'S'" - COBOLNET1566 (probe p8), citing §13.18.40.3 SR31. §13.18.60.4 GR11's own next sentence, "the data item is always considered to have a zero, or positive value" - probe p9: `MOVE -42` stores 00042 and `COMPUTE P1 = 10 - 20` stores 00010. The phrase's 2023 introduction gate fires below 2023 (COBOLNET0900 at 85/2002/2014, probe p46) and the phrase is rejected on a non-PACKED-DECIMAL usage (COBOLNET1565, probe p10). || REFUTED: PARTIAL — The WITH NO SIGN sentence - 'If the WITH NO SIGN phrase is specified the representation of the data item in the storage of the computer reserves no storage for representing any sign value' - is honoured on ONE of its two legal declaration shapes and SILENTLY DROPPED on the other. SS13.18.60.4 GR1 (cite-checked) says 'If the USAGE clause is specified or implied at a group level, it applies only to each elementary item in the group', and SS13.18.60.3 SR3 confirms the standard contemplates PACKED-DECIMAL arriving by group inheritance ('an elementary data item subordinate to a group item whose declaration contains a USAGE clause specifying ... PACKED-DECIMAL'). So `01 GRP USAGE PACKED-DECIMAL WITH NO SIGN.  05 EG PIC 9(4).` must give EG a sign-free representation, ceil(4/2) = 2 bytes. MEASURED in ONE program with the pinned compiler at --std 2023: group-level NO SIGN EG = 3 bytes, group-level plain EQ = 3, ELEMENTARY NO SIGN EL = 2, elementary plain EP = 3. The group form is byte-for-byte the SIGNED layout, with no diagnostic at all (exit 0) - the phrase is accepted and discarded. The USAGE PACKED-DECIMAL itself DOES propagate (3, not the 4 a DISPLAY item would give), so this is not a whole-clause miss: it is the phrase alone. MECHANISM, read at the adjudicator's own code-location's binder: DataBinder.cs:2647-2657 - `if (noSign) { if (entryUsage is not Usage.Packed) 1565; else if (pic is { Signed: true }) 1566; else if (pic is not null) pic = pic with { PackedNoSign = true }; }`. On a GROUP entry `pic` is null (no PICTURE clause), so every arm falls through and the flag is never recorded, and nothing carries it to the subordinate entries - the textbook two-arm dispatch with only the elementary arm implemented. Consequence for a user's program: a 2023 record laid out with a group-level PACKED-DECIMAL WITH NO SIGN is written one byte too wide per item and will not interchange. Everything else in GR11 does hold and was re-measured independently (radix-10 BCD two digits per byte, most-significant first: group images read 01 23 for 9(3) NO SIGN, 12 3D for S9(3) = -123, 01 23 45 for 9(5) NO SIGN, 01 23 4F for 9(4) plain, all matching CONFORMANCE.md item 215; widths 3/3/6/2/3/3/1/1/11/16 for S9(5), 9(4), S9(9)V99, 9(4)NS, 9(6)NS, 9(5)NS, 9(1)NS, S9(1), S9(18)V99, S9(31); MOVE -42 -> 0042 and COMPUTE 10-20 -> 000010; COBOLNET1566 on an S picture with SS13.18.40.3 SR31 cite-checked exact; COBOLNET1565 on BINARY; COBOLNET0900 below 2023). The cited test conformance:2023/usage_packed_no_sign is genuinely spec-derived but pins ONLY the elementary shape (9(6) 4 vs 3), which is precisely why the group shape went unseen.
