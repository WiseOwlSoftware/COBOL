## Measured (rows this note claims beyond the findings above)

### `GR-8.8.4.13-1` — PARTIAL (adjudicator + refuter record, verbatim)

Rule (cite.py --check 8.8.4.13 "evaluation of that hierarchical level terminates as soon as a truth value for it is determined" -> OK §8.8.4.13 1)): the connected conditions within a hierarchical level are evaluated left to right, and evaluation stops once the level's truth value is known. Code: ConditionBinder.BindFlatSequence binds every OR/AND/abbreviated-AND chain (full and EVALUATE partial-expression spines) in source order into BoundLogical("||"|"&&"), and ConditionRenderer.Visit(BoundLogical) emits the parenthesized C# short-circuit operators, so each parenthesized or implied level becomes one C# sub-expression that is evaluated left to right and short-circuits. Side-effecting operands in non-first positions (user-function activations) are attached per evaluation (UdfAttachPerEvaluation), so they are not hoisted ahead of the short-circuit. XOR is rendered with ^ and evaluates both operands, which is correct because an XOR level's truth value is never known from one operand. Probe with the pinned cobol.exe under >>TURN EC-ALL CHECKING ON (out/probe/cond-expr/p1.cob): a skipped OR/AND operand holding an out-of-range subscript T(0), a divide by zero 10/Z, a reference modification S(1:0), FUNCTION SQRT(-4) and FUNCTION MOD(10 0) raised nothing (A1 A2 B1 B2 G1 J1 J2). Negative controls n1/n2/n3 with the operand reached raised EC-BOUND-SUBSCRIPT, EC-SIZE-ZERO-DIVIDE and EC-BOUND-REF-MOD, so the probe is not vacuous. Tracing UDF activations: A AND B AND C -> ABC; G=0 OR (H=1 AND I=0) OR J=1 -> GHIJ; (K=0 AND L=1) OR M=1 -> KM (L skipped); WS-A = 5 OR TRC("O") abbreviated -> no activation; WS-A = 6 OR 5 OR TRC("Q") -> no activation; NOT (P=1 OR R=1) -> P; EVALUATE TRUE WHEN S=0 AND T=1 / WHEN U=1 OR V=1 -> SU; W=1 XOR Y=0 -> WY (both, left to right). All match the rule. Covering test: conformance:2002/udf_per_eval (C3/C4 prove an AND right operand is skipped when the left is false and an OR right operand is skipped when the left is true, which also shows the left operand is evaluated first). No existing golden covers nested levels or skipped exception-raising operands. That would be a coverage improvement, not a defect. The register note PB987 (landed) covers rule 2 object-property refetch, not this rule. || REFUTED: PARTIAL — Rule 1 (cite.py --check 8.8.4.13 "evaluation of that hierarchical level terminates as soon as a truth value for it is determined" -> OK) holds for the evaluation ORDER in every shape probed, but the mechanism that defers a non-first operand until the short-circuit reaches it (the per-evaluation lambda wrapping of a hoisted subscript / reference-modification operand) does not compile under >>TURN EC-ALL CHECKING ON when that operand's subscript or ref-mod position is a user-defined function activation: the lambda body carries the size-error RESUME dispatch 'goto __xfer', which C# forbids inside a lambda (CS0159). Legal source (IF WS-A = 0 OR EL(TRC("C", 1)) = 1) is therefore rejected by the backend, only in the non-first-operand position (the same subscript in the first operand compiles and runs). A rule whose implementing mechanism fails on a legal operand shape is PARTIAL, not CONFORMS.

## What the fixer owes

Never emit a statement-level transfer inside a lambda: have the deferred operand return a status the enclosing statement dispatches on (or emit the short-circuit as statements, not an expression). Golden under EC-ALL with the function in a non-first operand.
