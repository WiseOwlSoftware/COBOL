# PB3612 — OWNER DECISION (2026-10-23): a branch is gated locally ONCE at its head; the merge with main is gated by the merge queue's CI, never re-gated locally; the Linux gate runs the targeted leg

## The owner's words
2026-10-23, attended Mythos session, about 20:4x PDT:

"Taking one hour to finish a branch is stupidly ridiculously slow."

"Developers merge separate branches into a continually moving main all the time without problems. Maybe the rare merge conflict, which they address. Why don't we do that?"

Then, to the process laid out in the decision below: "yes".

## Measurement that led to it
PB3140's landing on 2026-10-23 (the `landing-measure` line in the enqueue log: "local gate 4615.0 s in 3 run(s)"): three local gate runs on both hosts, because main moved twice while the branch waited for a gate slot (cap 3, three landings at once). Each run was a Windows leg 1 plus all four Linux legs, and then CI's whole-population run on the merge result again. About one hour from CLEAN to queued per branch, measured on five branches that evening. The lane's landing rate is 1.47 changes per hour (`landing_measure.py`).

## The decision
It supersedes the landing half of the CI-invariant practice of 2026-10-04 and kb/Work PB3022 item 10. The invariant itself stands: nothing reaches CI untested locally.

1. The IMPLEMENTER gates its branch head once: `build-local.ps1` leg 1 on Windows plus the TARGETED Linux leg (the same leg-1 plan run under WSL, not the four whole legs). That is the one definition of "tested locally".
2. Branch review on the branch as now (two rounds at most; PB3381).
3. `enqueue.py land` merges origin/main in, stamps the DEVLOG, runs the landing checks, opens the PR and queues it. There is NO local gate of the merge result and NO re-gate when main moves again: the merge queue's CI (`ci-gate`, the whole population on the exact merge) is the gate for the merge. One exception, the case a developer would also re-test: when the merge of main touched a file the branch also touches (a true textual merge in a shared file), the targeted Windows leg runs once on the merged head before queuing.
4. A queue bounce goes to ONE finisher, as a developer fixes a red PR; a conflict is resolved by that finisher.
5. The gate slot cap stays a cap on concurrent gates, not on landings: with no landing gate, landings no longer wait for a slot.

## Landed (wave 20261029, group A3)

The decision is implemented as written, in four mechanisms (the implementation contract above, each site changed):

- **The implementer's one gate runs both hosts' targeted legs under its one slot.** `run_gate_legs.py` runs the Linux half
  (`Gate._linux_leg`, `Host.linux_leg`) after a green Windows half: `bash scripts/linux-gate.sh --legs targeted --plan
  <run>/plan.json --plan-legs <n>` clones HEAD under WSL, builds it once and runs the driver's own `--plan-leg` on the SAME
  plan's legs (`plan_leg`: `Gate._run_leg`, the population and identity checks; no audits, no slot). A Linux half RED is a
  RED gate naming the host; one that measured nothing ends the gate NOT RUN with the Linux gate's cause. The verdict file
  records `linux` and `head_tree`; a reused answer needs a GREEN Linux half of this head's tree. `linux-gate.sh` keeps its
  whole-leg form as the tool that reproduces a Linux CI red.
- **`enqueue.py land` gates nothing.** `tested_locally` reads the worktree's gate records: a tip none covers GREEN (with its
  Linux half, of the committed head's own tree) is refused, exit 13 UNTESTED, before anything is merged. The merge with main
  is the merge queue's to test. The exception: bringing main in changed a file the branch also changes (`merge_overlap`,
  setting aside driver-merged and inert files) runs the one gate once on the merged head; the lanes I10 does not review
  (`--lane`) gate their tip once when no record covers it. The Linux row, `SLOT_WRAP`, `gate_argv`, `GATED_MARK` and
  `gated_covers` are deleted. The `enqueue.py --self-test` arms are the "test_enqueue.py cases" the contract asked for
  (no such file exists): no gate at landing, an overlap runs one, an unrecorded head is refused.
- **`landing_measure.py` records `landing_gate_runs`** (0 or 1; null before this rule, said UNMEASURED), and `summary` has a
  row for it: the "after" figure is read on the first five landings under the rule (`summary --since`).
- **Docs in the same change set:** MANDATORY-PRACTICES I1, I8, L1, L2, L10, L12, the gate skill, the briefs, the dispatch
  spec template and its `LINUX_GATE` paragraph, the agent definition, DESIGN-test-build-ci.md sections 3.15, 3.17.2, 3.17.3,
  and 3.18, DESIGN-orchestrator-loop.md's exit table, CLAUDE.md's Testing paragraph, README, DOC_INDEX.

Deliberate difference from the contract's wording: the overlap exception runs the ONE gate (`build-local`: Windows leg 1 and
its Linux half), not a Windows-only leg, because the gate has one shape (PB3022).

## Landing

- `scripts/run_gate_legs.py#Gate._linux_leg` / `Host.linux_leg` / `plan_leg` — the Linux half of the targeted leg. REUSE
  `Gate._run_leg`, `_check_populations` and `_check_identity` (plan_leg calls them; a second runner would fork the
  handshake). Trap: the identity records land beside the plan file, so `plan_leg` copies the plan into its own results
  directory, or the Linux run overwrites the Windows run's records; the harness's observation log must be written on the
  Linux filesystem (linux-gate.sh runs `--results` in the gate's own directory and copies it out).
- `scripts/linux-gate.sh#targeted_leg` — `--legs targeted --plan <plan.json|none> [--plan-legs 1[,2]]`; `check_plan` holds
  the two options together. `LinuxGateDriftTests.TheDriversLinuxHalf_AndTheLinuxGatesTargetedMode_AgreeOnTheirArguments`
  pins the driver's command line to the script's options.
- `scripts/orchestrator/enqueue.py#tested_locally` — the landing's evidence (one reader of a gate's `verdict.json`:
  `head`, `tree`, `head_tree`, `linux`, `lane`); `merge_overlap` — the one exception; `land#gate_once` — the rare gate.
  Trap: any commit after the gate that is not main's, a clean merge or DEVLOG-only makes the tip UNTESTED, so every
  non-DEVLOG edit (a note, a doc) comes BEFORE the last gate; the report and the DEVLOG entry may follow it.
- `scripts/orchestrator/landing_measure.py#record_enqueued` (`landing_gates`) — 0 or 1 gates run by the landing itself.
