# PB3612 — OWNER DECISION (2026-10-23): a branch is gated locally ONCE at its head; the merge with main is gated by the merge queue's CI, never re-gated locally; the Linux gate runs the targeted leg

## The owner's words
2026-10-23, attended Mythos session, about 20:4x PDT:

"Taking one hour to finish a branch is stupidly ridiculously slow."

"Developers merge separate branches into a continually moving main all the time without problems. Maybe the rare merge conflict, which they address. Why don't we do that?"

Then, to the process laid out in the decision below: "yes".

## Measurement that led to it
PB3140's landing on 2026-10-23 (the `landing-measure` line in the enqueue log: "local gate 4615.0 s in 3 run(s)"): three local gate runs on both hosts, because main moved twice while the branch waited for a gate slot (cap 3, three landings at once). Each run was a Windows leg 1 plus all four Linux legs, and then CI's whole-population run on the merge result again. About one hour from CLEAN to queued per branch, measured on five branches that evening. The lane's landing rate is 1.47 changes per hour (`landing_measure.py`).

## The decision
It supersedes the landing half of the CI-invariant practice of 2026-10-04 and kb/Work PB3022 item 10. The invariant itself stands: nothing reaches CI untested locally.

1. The IMPLEMENTER gates its branch head once: `build-local.ps1` leg 1 on Windows plus the TARGETED Linux leg (the same leg-1 plan run under WSL, not the four whole legs). That is the one definition of "tested locally".
2. Branch review on the branch as now (two rounds at most; PB3381).
3. `enqueue.py land` merges origin/main in, stamps the DEVLOG, runs the landing checks, opens the PR and queues it. There is NO local gate of the merge result and NO re-gate when main moves again: the merge queue's CI (`ci-gate`, the whole population on the exact merge) is the gate for the merge. One exception, the case a developer would also re-test: when the merge of main touched a file the branch also touches (a true textual merge in a shared file), the targeted Windows leg runs once on the merged head before queuing.
4. A queue bounce goes to ONE finisher, as a developer fixes a red PR; a conflict is resolved by that finisher.
5. The gate slot cap stays a cap on concurrent gates, not on landings: with no landing gate, landings no longer wait for a slot.

## Implementation contract
One Opus implementer, fix lane, campaign PB1957.

- `scripts/orchestrator/enqueue.py` (`land`): drop the Windows and Linux gate steps except the file-overlap exception; keep the merge, the DEVLOG stamp, the landing checks and the queue. Keep the verdict-record reuse for the branch head's own gate as the "tested locally" evidence: refuse to land a branch whose head has no recorded GREEN leg-1 run (Windows) and no recorded targeted Linux run, with a named exit code.
- `scripts/linux-gate.sh`: a `--legs targeted` mode that runs the same plan leg 1 computes, used by build-local's Linux step and by the implementer's gate. The whole-legs mode stays for reproducing a CI red.
- `scripts/build-local.ps1`: the implementer's one gate runs both hosts' targeted legs under the one slot.
- The agent definitions, MANDATORY-PRACTICES rows L1/L2/L12/I8, the `gate` skill, `DESIGN-test-build-ci.md` §3.17 (the landing's doc) and CLAUDE.md's "Testing" paragraph (owner-owned text: the implementer edits it to the decision's words and the owner reads the diff), all in the same change set (rule 6).
- Drift tests: `test_enqueue.py` cases for "no gate at landing", "overlap, one targeted run" and "unrecorded head refused".
- Measurement: `landing_measure.py` before and after, on the first five landings under the new rule.

**Sites:** `scripts/orchestrator/enqueue.py`, `scripts/orchestrator/test_enqueue.py`, `scripts/linux-gate.sh`, `scripts/build-local.ps1`, `scripts/orchestrator/landing_measure.py`, `.claude/skills/workstream/templates/MANDATORY-PRACTICES.md`, `.claude/skills/gate/SKILL.md`, `.claude/agents/`, `docs/rearchitecture/DESIGN-test-build-ci.md`, `CLAUDE.md`.
