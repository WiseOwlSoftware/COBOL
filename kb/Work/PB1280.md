## Measured

### Finding redefines-clause — §13.18.44.3 SR2, SR3 (first half; the FORMAT-clause half is the declined A.4.8 facility, PB281) (under-rejects; rows SR-13.18.44.3-2, SR-13.18.44.3-3)

**Mechanism.** redefines-entry-placement-screens: ResolveRedefines resolves data-name-2 by name and never checks the ENTRY-level placement rules - SR2's level-number identity (a 77 and an 01 are both in Roots) and SR3's ban on REDEFINES in a level-1 FILE SECTION entry. The legacy compiler's CBL3112 level-mismatch screen was never ported; the SR8 comment in ResolveRedefines ASSUMES SR3 holds.

**Repro.** (a) `WORKING-STORAGE SECTION. 77 A PIC X(4) VALUE "ABCD". 01 B REDEFINES A PIC X(4).` DISPLAY B (sr2_77_01.cob, --std 85 and 2023). (b) `FILE SECTION. FD F. 01 R1 PIC X(10). 01 R2 REDEFINES R1 PIC X(10).` (sr3_fd01.cob, --std 85 and 2023).

**Expected, from the standard.** A compile-time diagnostic at every edition for each: SR2 'The level-numbers of data-name-2 and the subject of the entry shall be identical'; SR3 'This clause shall not be specified in level 1 entries in the file section'.

**Observed.** Both compile clean (rc 0) and run (ABCD / OK) at --std 85 and 2023.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.cs#ResolveRedefines

### Finding redefines-clause — §13.18.44.3 SR1 (under-rejects; rows SR-13.18.44.3-1)

**Mechanism.** redefines-clause-position: the dataDescriptionClauses list is free-order and no Cobol.Net site checks that REDEFINES immediately follows the entry-name (or the level-number); the only screen is the LEGACY CBL0808 warning.

**Repro.** `01 A PIC X(4) VALUE "ABCD". 01 B PIC X(4) REDEFINES A.` DISPLAY B (sr1_after_pic.cob, --std 85 and 2023); `01 B GLOBAL REDEFINES A. 05 B1 PIC X(4).` (sr1_after_usage_grp.cob).

**Expected, from the standard.** A compile-time diagnostic: SR1 'The REDEFINES clause shall immediately follow the entry-name clause; if the entry-name clause is not specified, the REDEFINES clause shall immediately follow the level-number.'

**Observed.** Compiles clean and prints ABCD at both editions.

**Code site.** src/Cobol.Net.Frontend/Grammar/Core/CobolData.g4#dataDescriptionClauses; src/Cobol.Net.Compiler/Binding/DataBinder.cs#BindEntry (clause loop - the ordinal of the redefinesClause among the entry's clauses is available there)

### Finding redefines-clause — §13.18.44.3 SR8; §13.18.44.4 GR1 (under-rejects; rows SR-13.18.44.3-8)

**Mechanism.** sr8-exception-and-unit: the SR8 size screen in ResolveRedefines exempts EVERY level-1 data-name-2 (the 'without the EXTERNAL clause' condition is ignored - the comment calls it unmodeled) and compares ByteWidth, so a bit-granular redefiner that needs more bits than data-name-2 inside the same byte is not measured.

**Repro.** (a) `01 A PIC X(4) EXTERNAL. 01 B REDEFINES A PIC X(8).` MOVE "12345678" TO B, DISPLAY A (sr8_external.cob). (b) `01 G. 05 A PIC 1(4) USAGE BIT. 05 B REDEFINES A PIC 1(8) USAGE BIT. 05 C PIC X.` (sr8_bits.cob).

**Expected, from the standard.** Both rejected: SR8 'The storage area required for the subject of the entry shall not be larger than the storage area required for the data item referenced by data-name-2, unless the data item referenced by data-name-2 has been specified with level number 1 and without the EXTERNAL clause'; GR1 measures the area in bits (8 > 4).

**Observed.** Both compile clean; (a) prints 1234 - an 8-character alias over a 4-character run-unit-shared EXTERNAL item.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.cs#ResolveRedefines (the COBOLNET1539 arm: `tgt.Level != 1 && item.ByteWidth * ... > tgt.ByteWidth * ...`)

### Finding redefines-clause — §13.18.44.3 SR13 (under-rejects; rows SR-13.18.44.3-13)

**Mechanism.** redefines-constant-record-target: no screen reads CONSTANT RECORD on data-name-2, so a constant record can be redefined and then MODIFIED through the redefining name.

**Repro.** `01 A CONSTANT RECORD. 05 X PIC X(4) VALUE "ABCD". 01 B REDEFINES A PIC X(4).` PROCEDURE: `MOVE "WXYZ" TO B. DISPLAY X.` (sr13_constant_record_move.cob).

**Expected, from the standard.** Compile-time rejection: SR13 'The data description entry for data-name-2 shall not contain the CONSTANT RECORD clause.'

**Observed.** Compiles clean and prints WXYZ - the constant record's content changed.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.cs#ResolveRedefines / #ClassifyRedefinesClasses (the per-written-entry screen block beside SR12/SR14/SR17)

### Finding redefines-clause — §13.18.44.3 SR15; §8.5.1.6.3; §13.18.1.4 GR1 (under-rejects; rows SR-13.18.44.3-15)

**Mechanism.** redefines-alignment-unscreened: SR15 has no implementation. SYNCHRONIZED performs no alignment (DOC-A.1-195) so character items are vacuously aligned, but USAGE BIT items are bit-aligned (§8.5.1.6.3) and ALIGNED / character items are byte-aligned, and a redefiner of a mid-byte bit item is accepted - and then silently placed at the byte boundary, not at data-name-2's first bit.

**Repro.** `01 G. 05 A PIC 1(3) USAGE BIT VALUE B"101". 05 B PIC 1(5) USAGE BIT VALUE B"11111". 05 C REDEFINES B PIC X.` PROCEDURE: `MOVE "A" TO C. DISPLAY "LEN=" FUNCTION LENGTH(G) " A=" A " B=" B.` (sr15_bit_char2.cob); also `05 C REDEFINES B PIC 1(5) USAGE BIT ALIGNED.` (sr15_bit_aligned.cob).

**Expected, from the standard.** Compile-time rejection: SR15 'The description of the subject of the entry shall be such that its required alignment is the same as the alignment of the data item referenced by data-name-2' - B begins at bit 3 (§8.5.1.6.3, next bit after a same-level bit item) while C requires a character boundary and the ALIGNED item the first bit of a byte (§13.18.1.4 GR1).

**Observed.** Both compile clean; the first prints `LEN=1 A=010 B=00001` - C's write landed on bits 0-7 (over A), contradicting GR1's association at B's first bit.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.cs#ResolveRedefines (no SR15 arm exists; the bit offset is computed in src/Cobol.Net.Compiler/Binding/Model/BitLayout.cs)

## Landed 2026-10-04 (wave-1011 implementer B2)

**Re-probed on the wave's predecessor build (the pre-change binary) and on this one** (`p/r_*.cob`, 12 programs): every shape in the note
compiled clean (rc 0) before: `77 A` + `01 B REDEFINES A`, `01 R2 REDEFINES R1` in an FD, REDEFINES after PICTURE / GLOBAL, `01 B REDEFINES A
PIC X(8)` over `01 A PIC X(4) EXTERNAL`, 8 bits over 4, a CONSTANT RECORD redefined and modified (`WXYZ`), a character item over a bit item
that begins mid-byte; and `05 A / 05 A REDEFINES A / 05 C REDEFINES A` was refused with COBOLNET1656 although it is legal.

**Mechanism.** `ResolveRedefines` found data-name-2 by NAME alone and asked it nothing: the clause-placement table even named it the home of
"level and position rules" (the clause-placement table), and its SR8 comment ASSUMED SR3 held. The entry-level rules now live together in the new
`DataBinder.RedefinesEntry.cs`: `ScreenRedefinesPosition` (SR1, asked in `BindEntry`, where the clause list is: "immediately follows the
entry-name" is "is the FIRST clause", the entry-name and level-number not being in the list) and `ScreenRedefinesEntry` over the RESOLVED pair
(SR2 identical level-numbers; SR3 no REDEFINES in a level-1 FILE SECTION entry; SR8 moved here from the inline block, corrected twice — the
level-1 exemption needs "without the EXTERNAL clause", and the areas are compared in BITS, §13.18.44.4 GR1, a bit item exactly through
`BitLayout.RunBits`; SR13 data-name-2 is no CONSTANT RECORD; SR15 alignment). New code COBOLNET2739 `redefines-entry-rule` (SR8 keeps
COBOLNET1539). Target selection also changed (SR7, SR10, §8.4.2.2.1 rule 2): data-name-2 is the nearest same-named preceding entry that is
NOT itself a redefinition, and at top level one of the subject's own section — so the legal name-reuse shape binds to the original and a
LOCAL-STORAGE 01 no longer redefines a WORKING-STORAGE 01 (the refuter's r2, now COBOLNET1654).

**SR15 determination** (the standard leaves "required alignment" to §8.5.1.6.3 and §13.18.1.4 GR1): a subject needs a byte boundary unless it is
a bit item placed by rule 1 (the next bit position); a byte-boundary subject over a data-name-2 that begins mid-byte has no storage association
GR1 can make (it "starts at the first bit of the data item referenced by data-name-2"); a bit-aligned subject fits any bit; a character subject
over a bit item that begins a byte is legal. `CONFORMANCE.md` carries no separate row for it (the rule is a plain syntax rule).

**Citations** (all `cite.py --check` OK): 13.18.44.3 SR1, SR2, SR3, SR8, SR10, SR13, SR15; 8.4.2.2.1 2); 13.18.44.4 GR1 (read through the existing
SR8 comment).

**Sibling sweep.** The other REDEFINES arms: the implicit FD area sharing and the SAME RECORD AREA link are `RedefinitionKind.ImplicitArea` /
`SameRecordArea`, not `Clause`, and never reach these screens; RENAMES is PB1283's. SR4/SR5/SR7/SR9/SR10/SR12/SR14/SR16/SR17 already had
screens (PB93, PB177, PB1698..). The method-data (OO) arm of target selection (`OoRootOwner`) keeps its own scope list and gets the same
original-definition choice because the choice sits after the scope is picked.

**Witnesses.** `conformance:negative/pb1280-redefines-*` (10 programs: level-77 target, level-1 file-section entry, after PICTURE, after GLOBAL,
EXTERNAL larger, bits larger, CONSTANT RECORD, character over mid-byte bits, ALIGNED over mid-byte bits, other section) and
`conformance:2002/pb1280_redefines_entry_rules_legal` (`A WX PQ`, computed from SR7 + NOTE 1, SR8 and §8.5.1.6.3). Rows SR-13.18.44.3-1, -2, -3,
-8, -13, -15 (DIVERGES) and SR-8.4.2.2.1-2 (PARTIAL) become CONFORMS.
