# PB429 — the receiving-operand designation, measured in the direction nobody probed

## The mechanism

SR4 designates identifier-2 as MOVE's receiving operand. The designation itself is `ExpressionBinder.ResolveTargets`
over `moveReceivingPhrase`'s `dataReferenceList`, and every receiver-side rule reads that list — the SR1 receiver
class screen, the SR5 per-target figurative gate and its image marking, `MoveReceiverCategory` for Table 16, the
SR7 boolean screen, the SR8 receiver-category test, `CheckStrongMove` and `MarkRefModStoreImage` all iterate
`targets`. The NEGATIVE direction is correct and easy to check: the receiving position admits only a data
reference, so a literal receiver is refused (`COBOL0308 A data-name is expected here, not a literal`) and a
function-identifier receiver is a parse error, which is §8.4.3.2.3 SR1 holding structurally.

The POSITIVE direction — that every legal identifier-2 is ACCEPTED — is the half that was asserted and never
probed, and it is false. `MOVE 7 TO PAGE-COUNTER OF RPT1` is refused with COBOLNET0899, whose own text says the
construct is legal and unimplemented. That is a staged-loud rejection of legal source: the program does not
compile, and the diagnostic is the compiler conceding the point.

           the procedure division, PAGE-COUNTER and LINE-COUNTER may be referenced in any context where an
           integer data item may appear…

    python scripts/spec/cite.py --find "LINE-COUNTER shall not be"
    §8.4.3.15.3 3)  (Syntax rules)
        3) LINE-COUNTER shall not be referenced as a receiving operand.
    1 occurrence(s)

    python scripts/spec/cite.py --find "procedurally altered"
    §13.18.37.4 6)  (General rules)
        6) If the WITH RESET phrase is present, the value of PAGE-COUNTER for the report is set to 1 (one)
           immediately after the page feed caused by the next page advance … this phrase ensures that
           PAGE-COUNTER will be one, effective from the start of the next page (unless procedurally altered).

The pair is decisive. SR1 puts PAGE-COUNTER and LINE-COUNTER anywhere in the procedure division that an integer
data item may appear — which includes a MOVE receiving operand — and SR3 then subtracts LINE-COUNTER, and ONLY
LINE-COUNTER, from the receiving side. PAGE-COUNTER as identifier-2 is therefore legal by the explicit
construction of the two rules, and §13.18.37.4 GR6's parenthetical "(unless procedurally altered)" confirms that
a program altering PAGE-COUNTER is the intended use, not an edge.

⚠ The b2 refuter cited the last of these as "§13.18.37"; the sentence is in §13.18.37.4 GR6 (the NEXT GROUP
clause's WITH RESET rule) and is cited that way above. It also paraphrased SR3 as "shall not be SPECIFIED as a
receiving operand"; the standard says "shall not be REFERENCED as a receiving operand" — quoted verbatim above.

## The code sites and the shape of the repair

- The refusal is raised on the counter-reference path reached from
  `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/MoveBinder.cs#Bind` via `ExpressionBinder.ResolveTargets` over
  `src/Cobol.Net.Frontend/Grammar/CobolParserCore.g4#dataReferenceList`; the SENDING direction of the same counter
  already works (`MOVE PAGE-COUNTER OF RPT1 TO W` binds), so the receiving arm is the gap.
- `src/Cobol.Net.Compiler/Binding/Bound/BoundTree.cs#BoundMove` — the target list every receiver-side rule reads.

**MAKE THE COUNTER A REAL INTEGER PLACE, NOT A MOVE SPECIAL CASE** (CLAUDE.md rule 5). §8.4.3.15.3 SR1 does not
name MOVE — it says "any context where an integer data item may appear". So the repair is to give PAGE-COUNTER a
receiving-capable `Place` in the report-writer model (the counter the RD already maintains), after which MOVE,
ADD, SUBTRACT, COMPUTE, INITIALIZE, SET and every other integer-receiver context work without further arms, and
LINE-COUNTER's SR3 prohibition becomes ONE screen on that place rather than a per-verb refusal. Adding a MOVE-only
arm would reproduce the same hole in every other verb the rule reaches — which is what the sweep below is for.

## The sibling sweep the fixer must do

- Every other verb with an integer receiving operand: ADD/SUBTRACT/MULTIPLY/DIVIDE … GIVING, COMPUTE, INITIALIZE,
  SET, ACCEPT, UNSTRING's counters, INSPECT TALLYING. Each must accept PAGE-COUNTER and refuse LINE-COUNTER, and
  each is untested today.
- The OTHER "several counter/SOURCE/SUM legs" `docs/CONFORMANCE.md:862` names in the same 0899 band. This note
  measures one of them; the others are the same shape and were not probed.
- ⚠ The LINE-COUNTER refusal is CORRECT but is emitted as COBOLNET0899, the "is not yet implemented" band. A
  rule-derived rejection wearing an unimplemented-feature code tells the user their legal program is unsupported
  when in fact their program is illegal. Give SR3 its own code (or an existing rejection code) in the same change
  set, and sweep the 0899 band for other rule-rejections misfiled into it — a correct rejection under a
  "not yet implemented" banner is indistinguishable, to a reader and to a selector, from this note's actual
  defect.
