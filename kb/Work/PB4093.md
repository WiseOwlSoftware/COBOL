# PB4093 — enabling EC-SIZE-OVERFLOW alone makes a truncating COMPUTE keep its old receiver value

**Sites:** `src/WiseOwl.Cobol.Compiler/CodeGen/Verbs/ArithmeticEmitter.cs#EmitArith`, `src/WiseOwl.Cobol.Compiler/CodeGen/EcEmitter.cs#EmitSizeHandling`

**Observed.** Under EC-SIZE-OVERFLOW checking alone, `COMPUTE WS-C = WS-A * WS-A`, with WS-A PIC 9(3) holding 100 and WS-C PIC
9(3) holding 7, leaves WS-C at `007` (repro `E:/COBOL-coord/scratch/mythos/w-n1/w20261762d/f1/ov.cob`, "AFTER COMPUTE2
007"). `EmitArith` routes the statement to `TryStore` because an EC-SIZE name is enabled. The result 10000 overflows
by truncation, not by EC-SIZE-OVERFLOW. `EmitSizeHandling` then drops the latched EC-SIZE-TRUNCATION, because it is
not enabled, and the receiver is never stored. That is the "unchanged" disposition of a statement with a SIZE ERROR
phrase, applied where there is none.

**Expected.** EC-SIZE-TRUNCATION is not enabled, so it is not raised (§14.6.13.1.1, `cite.py --check` OK). The statement has
no SIZE ERROR phrase, so the not-enabled disposition applies: §14.6.13.1.3 item 8, documented as DOC-A.1-70. Execution
continues, and the receiver gets the low-order digits of the result at its scale, so WS-C = 000.

**Fix.** The store path follows the condition that actually occurred and whether that name is enabled, never whether
any EC-SIZE name is enabled. A truncation that is not enabled stores the low-order digits per DOC-A.1-70. One that is
enabled raises EC-SIZE-TRUNCATION and leaves the receiver as §14.7.5 and §14.6.13.1.3 require. Same root as PB4092
(family-level versus per-name checking): fix them together or in sequence. Goldens: the case above, plus each EC-SIZE
name enabled alone against an overflow and against a truncation.
