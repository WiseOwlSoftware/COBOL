# PB746 — OPEN — an ungated phrase, and an edition nobody has derived

Found 2026-09-06 in the PB702 implementer's report (NEW DEFECT 3), which measured the acceptance and correctly
declined to date it. Registered here against main (`89555b09`) with the derivation attempted and **not closed** —
the same posture as [[PB733]], and for the same reason: the belief is older than any source that could support it.

⛔ **THE HARM FLAG IS CONDITIONAL.** `under_rejects` is set so `work.py next` can rank the item, and it is true
**only if** the USING phrase is post-1985. If the derivation closes the other way the flag comes off and the item
becomes a traceability correction. The derivation is the first work item, not an afterthought — see "Fix".

## Measured on main, statically — no build, no probe

The PB702 report's probe (`cobol tests/conformance/85/pb324_assign_using_85.cob --std 85` compiles silently, no
COBOLNET0900) was **not re-run** here; nothing was built. It did not need to be, because a stronger and standing
form of the same measurement is already in the tree:

| where | what main says |
|---|---|
| `src/Cobol.Net.Frontend/Grammar/Core/CobolIO.g4:43-46` | `assignClause : ASSIGN TO? assignTarget (USING dataReference)? \| ASSIGN USING dataReference ;` — **no semantic predicate on either arm** |
| `src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs` | `grep -n "AssignClause\|assignClause\|AssignUsing"` → **no hits**; the pass has no visitor for the clause |
| `tests/version-matrix/constructs.json` (209 rows) | **no row whose id/display/description matches `assign`** — so the version-matrix edition-gate sweep is structurally unable to see the phrase |
| `tests/conformance/85/manifest.json:10` | `"pb324_assign_using_85"` is **enabled**, and `tests/conformance/85/pb324_assign_using_85.out` exists — a POSITIVE golden that runs at `--std 85` and asserts output |

So acceptance at `--std 85` is not an incidental probe result: it is **pinned by an enabled golden in the standing
conformance suite**, and the golden says so in its own preamble
(`tests/conformance/85/pb324_assign_using_85.cob:3-5`):

> *"No edition gate exists for the phrase, so 85 shall not reject it and shall not silently fall back to the
> file-name (kb/Work PB324)."*

That sentence is the belief, written into the artefact that then confirms it
(`feedback_green_test_can_hold_a_gap_open`: a GREEN test pinning a posture reads as a DECISION).

## ⛔ What the derivation actually produced — read this before writing a gate

Four in-repo sources were checked mechanically. **None of them dates the phrase.**

1. **Annex E** (`specs/ISO_COBOL.md` lines 42847–44100, the whole of E.1/E.2/E.3.1/E.3.2/E.3.3). The string
   `assign` occurs **once**, at E.3.3 item 43 — *"numeric-edited data items to be **assigned** values specified as
   numeric literals"* — which is the VALUE clause, not this clause. `dynamic file` occurs **zero** times. Annex E
   is the 2014→2023 window, so this is a real result and not a null one: **the USING phrase is not a COBOL-2023
   introduction; it existed by 2014.**
2. **`docs/VERSION_CHANGE_REFERENCE.md`** carries **no ASSIGN row** (`grep -in "assign"` → three hits, all the
   English word "assigned"/"assignment" in unrelated rows 86/100/441). Its own scope limit forecloses the
   question: *"There is **no 85→2002 row set here at all** — when gating an 85↔2002 difference, derive it from the
   2002 standard, not from this file."*
3. **`docs/ISO2023_CONFORMANCE_PLAN.md`**, the post-85 feature catalog VCR redirects to (M2/M3/M4):
   `grep -in "assign"` → **no hits**.
4. **`tests/version-matrix/reserved-words.json`** — the one per-edition datum the repo owns, and the datum that
   decided PB300's PADDING row. It is **silent here by construction**:
   `{"word": "ASSIGN", "r85": true, …, "provenance": "continuous since 1985"}` and
   `{"word": "USING", "r85": true, …, "provenance": "continuous since 1985"}`. Both words are reserved at 85 for
   OTHER constructs (`ASSIGN TO`, `CALL … USING`), so a word-level register can never date a PHRASE built from
   two words it already reserves.

⇒ **NOT DERIVABLE IN-REPO.** The phrase is ≤2014 and undated below that. Anything sharper needs the ISO/IEC
1989:2002 or 1989:2014 text, which this repo does not hold.

## The inventory question — the part that generalizes

`GR-12.4.5.3-3` (`tests/version-matrix/traceability-inventory.json:14815`) is `verdict: CONFORMS`, `state: OK`,
`editions: "85,2002,2014,2023"`. Its notes end:

> *"Edition-invariant: 12.4.5.3 GR3 is unchanged across 85/2002/2014/2023, and the 85 arm rides
> conformance:85/pb324_assign_using_85."*

**Is that the refuted-record shape the report compares it to (`GR-14.9.41.4-17`)? No — not as the report frames
it, and the comparison should not propagate in that form.** `GR-14.9.41.4-17` on main
(`traceability-inventory.json`, `verdict: DIVERGES`, `state: GAP`, `editions: "85,2002,2014,2023"`) contains **no
text resembling** *"the record claims edition 85 for a branch COBOL-85 does not have and the compiler does not
gate"*. What it actually carries is the opposite of a refutation — an explicit per-branch qualification in its
`EDITIONS AS ADJUDICATED` tail:

> *"1985 / 2002 / 2014 / 2023 for items a)–e) generally; the LENGTH-clause branch of b) rides on the WITH LENGTH
> phrase (2014/2023 established, earlier band not datable from this transcription); the SUPPRESS WHEN sentence of
> e) is 2023-only (Annex E.3.3 item 42 …)."*

**But the SHAPE the report reached for is real, and both rows have it.** `editions` is a **scalar string** on a
row whose rule has **branches with different edition bands** — `feedback_model_the_rule_shape_not_one_case`. On
`GR-14.9.41.4-17` the scalar says 85 while the prose says two of the five branches are not; on `GR-12.4.5.3-3` the
scalar says 85 for a GR3 whose a) arm (TO device-name/literal) is certainly 1985 and whose b) arm (USING
data-name-1) is undated. In both rows the machine-readable field and the human-readable notes disagree, and only
the field is queryable.

**Is `GR-12.4.5.3-3`'s verdict unsound?** ⛔ **Not proven unsound — unverified on exactly one of its clauses, and
circular on another.** The CONFORMS verdict over GR3's four sentences rests on measured behaviour (the two PB673
goldens, `pb324_assign_using_dynamic`'s BLANK=31 leg) and is untouched by this note. The two clauses that are not:

- *"12.4.5.3 GR3 is unchanged across 85/2002/2014/2023"* — an inherited belief; §4 above shows no in-repo source
  states it. It may well be true; nothing here has derived it.
- *"the 85 arm rides conformance:85/pb324_assign_using_85"* — **circular**. That golden was written FROM the
  belief (its preamble asserts it verbatim), so it can only confirm that the compiler does what the belief
  predicts. It can never establish that COBOL-85 HAS the phrase, which is the proposition the `editions` field
  claims.

The same sentence has already been inherited once: `GR-14.9.27.4-26` (`verdict: CONFORMS`, `state: OK`,
`editions: "85,2002,2014,2023"`) says *"no edition gate exists for the USING phrase, which
conformance:85/pb324_assign_using_85 pins at the oldest supported edition."* **Two rows, one undated belief** —
which is exactly the propagation CLAUDE.md rule 1 names as the failure mode.

⛔ **NEVER HAND-EDIT THE INVENTORY.** The correction is a `scripts/spec/record_verdicts.py` BATCH — name it
**`pb746-assign-using-editions`** — re-recording `GR-12.4.5.3-3` and `GR-14.9.27.4-26` together once the
derivation closes, so the two rows cannot drift apart again.

## Fix

**Step 1 (blocking, and it is the whole difficulty).** Date the USING phrase against the ISO/IEC 1989:2002 text
(or 2014). Until that is in hand, nothing below can be written correctly, and the two inventory rows should not be
re-verdicted on a guess.

**Step 2a — if the phrase is ≥2002.** It is a post-85 construct with no gate, which is `feedback_edition_gate_sweep`
territory: a `constructs.json` row (`assign-using-2002`, `introducedIn: 2002`, `expectDiagnostic: COBOLNET0900`),
the gate itself — a `{is2002()}?` at the LEFT EDGE of the `ASSIGN USING` alternative and of the `(USING …)?` tail
(`feedback_left_edge_predicates`), or a `VisitAssignClause` in `VersionConformancePass`, whichever matches the
clause-gating mechanism the rest of `CobolIO.g4` uses — plus the mandatory edition-gate test sweep, and
`tests/conformance/85/pb324_assign_using_85` re-trued from a positive golden to a negative one (its whole reason
for existing is the claim that would then be false). Both inventory rows re-record through the batch above.

**Step 2b — if the phrase is 1985.** Nothing in the compiler changes. The two rows still change: the belief
becomes a derivation with a named source, and the golden's preamble gains the citation it currently lacks.

## Adjacent observation — NOT a defect, recorded so the next reader does not re-open it

`assignClause`'s first arm accepts `ASSIGN TO x USING y` (both phrases on one clause). That looked like an
over-acceptance and is not one:

- The printed Format 3 general format (`specs/ISO_COBOL.md:13167-13172`) shows the combination as one of the two
  alternatives — `TO { device-name-1 | literal-1 } … [ USING data-name-1 ]` stacked over a bare
  `USING data-name-1` — so the grammar matches the diagram exactly.
- `--check 12.4.5.2 "The allowable and required syntactical combinations of data-name-1 with device-name-1 and of
  data-name-1 with literal-1 are defined by the implementor"` → **OK §12.4.5.2 6)**. The standard hands the
  combination to the implementor, which is only meaningful if it can be written.

⚠ The FIGURE NOTE thirty lines below the diagram (`specs/ISO_COBOL.md:13201`) contradicts the diagram it
annotates: *"The outer braces are a plain required choice — either the `TO` line or the `USING data-name-1`
line."* That is a transcription-note defect of the falsely-restrictive kind CLAUDE.md rule 1 warns about — but
**the page was NOT rendered here** (`scripts/render-spec-page.py`), so this is filed as an observation and not
adjudicated. The identical note appears on the Format 4 (sort-merge) ASSIGN clause at `:13223`.
