# PB156

Row: GR-14.9.2.4-4 (DIVERGES per the refuter's reading; the adjudicator read D16's §8.8.1.3 latitude as covering it). pb99_floating_literal_operand_exact's own header states the D16 position and avoids the lossy case. Bare question: does D16's binary64 promotion stand for float LITERALS mixed with wide EXACT operands (documenting the GR4 tension as a determination), or must a float literal land exactly (decimal expansion) when every other operand is exact? FLOAT-DECIMAL usages are 1564-unreachable, so the literal is the only reachable case.

*(Found by Phase-B batch 8 — §8.8.1 + §14.9.1–14.9.12, 2026-08-29; one adjudicator + one independent refuter per subject. Full forensic evidence: the named rows' `notes` in `tests/version-matrix/traceability-inventory.json`; the raw finding lines in the session scratchpad `pb-batch8/findings.txt`.)*

## ANSWERED — owner decision D-B, 2026-08-30; implemented 2026-08-31 (the arithmetic wave)

**The decision: a floating-point literal is its EXACT §8.3.3.3.3 rule-5 value everywhere.** The bare question
above asked whether D16's binary64 promotion stands for a float literal mixed with wide exact operands, or
whether the literal must land exactly. The owner chose exact, which also converges with the stricter GR4
reading — the same behaviour either way, so no latitude is being spent.

### The derivation, re-checked against THIS tree before implementing

§14.9.2.4 GR4 (`cite.py --check` PASSED): *"When native arithmetic is in effect and none of the operands is
described with usage binary-char, binary-short, binary-long, binary-double, float-short, float-long, or
float-extended, enough places shall be carried so as not to lose any significant digits during execution."*

A literal is not "described with usage" anything. And §14.7.7 rule 2 (`cite.py --check` PASSED) settles the
reading the other way round: it lists *"a data item described with usage binary-char, … float-extended, or of a
standard floating-point usage"* and *"a floating-point literal"* as **separate bullets** — so where the drafters
mean to include a float literal alongside the usages, they say so, and GR4 does not.

⚠ **One design-note claim CORRECTED.** The plan called §14.9.44.4 GR4 a "verbatim SUBTRACT twin". It is one word
apart: SUBTRACT says *"so as not to lose significant digits during execution"* where ADD says *"so as not to
lose **any** significant digits"* (both `cite.py --check` PASSED against their own clauses). Nothing turns on
it, but the row's notes now quote each clause's own text rather than one text for both.

### The change

`NumericRenderer.LiteralNum` and `LiteralOperandNum` **collapsed to one method**, so the POSITION of a literal
can no longer select its value; `RenderOperandLike`'s `BoundNumLiteral` special case went with them (it existed
only because the two renderings differed, and now reduces to `Render(e, ReceiverContext.None)` by construction).
`CombineCore` is untouched: its `Real` lane still takes precedence whenever a float ITEM or a float RECEIVER is
present, which is exactly where GR4's own condition stops holding — D16 is narrowed, not overturned.
`ExpressionBinder.CheckLiteral`'s decimal128 range arm is now unconditional and the `FitsBinaryFloat` arm is
deleted (that half is [[PB195]], which closes with this note).

The invariant the goldens now hold: **the VALUE a literal contributes is its exact §8.3.3.3.3 rule-5 value, in
every position and every arithmetic mode, and no operand ever arrives rounded to binary64.** `ADD 1.0E+0`
computes what `ADD 1.0` computes, `2 ** 0.5E+0` what `2 ** 0.5` computes — because those are the same values.

⚠ **This sentence originally read "a literal's NOTATION never changes the arithmetic; only its VALUE does", and
as an invariant it is false** ([[PB274]], found by this wave's own review fleet). Under NATIVE arithmetic the
notation still selects the intermediate LANE: a float literal operand routes the statement onto the decimal128
lane (34 significant digits) where a fixed-point literal keeps `CombineNative`'s Int128 one (~38), so
`A * B + 0.0E+0` and `A * B + 0.0` differ for 18-digit A and B, and INTERMEDIATE ROUNDING (§11.9.11) reaches the
first and not the second. That is a published §8.8.1.3 determination (CONFORMANCE.md A.1 item 82), not part of
the invariant, and `pb156_float_literal_exact_native`'s LANE / LANEF legs pin it. Separately, the exact-integer
`**` arm is keyed on the exponent's VALUE now rather than its spelling, so `10 ** 30`, `10 ** 30.0` and
`10 ** 3.0E+1` really are one expression ([[PB272]] — they were not when this note was written).

### Residual, recorded honestly

§8.3.3.3.3 rule 2 admits a **36-digit significand** and the SDIDI carrier holds **34**, so the 35th and 36th
significand digits of such a literal round at `CobolDec.FromParsed` under the INTERMEDIATE ROUNDING mode. The
form is accepted (SR2 is satisfied); the two trailing digits are not preserved. Published in CONFORMANCE.md
§7 A.1 item 82.

### Sibling sweep — two CALL-lane defects found, NOT fixed here

The sweep asked where else a float literal is rendered. `CallEmitter` has its own literal rendering and does not
go through `LiteralNum`: [[PB263]] (BY CONTENT — a raw Roslyn CS1503 on every float literal) and [[PB264]]
(BY VALUE — a `(long)` cast that truncates a float literal and modularly WRAPS a wide fixed-point one). Both
pre-exist this wave; both are registered rather than folded into it, because §14.9.4 argument conformance is a
different subsystem. D-B's claim is therefore stated with that exception named, in the code comment and in the
numeric design.
