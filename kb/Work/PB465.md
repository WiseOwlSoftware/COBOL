# PB465 — the right rule, the wrong exception condition, on the arm no test drives

**Row:** `GR-14.9.39.4-19` (SET Format 10 — *if arithmetic-expression-3 does not evaluate to an integer,
EC-SIZE-ADDRESS is set to exist, the SET is unsuccessful, and identifier-9 is unchanged*). This row was
adjudicated CONFORMS and **overturned by the b2 refuter**; I re-measured the refutation on the HEAD
`cobol.exe` (base 89044aa0) and it holds.

## THE MECHANISM

`PtrEmitter.EmitSetPointerUpDown` (`PtrEmitter.cs:75-102`) splits the amount three ways and, for a NATIVE-FLOAT
amount, routes it to `CobolPtr.UpByReal` keeping the `double` alive (`:82-92`). That split is the good part —
kb/Work PB151 landed it precisely so a `(long)(double)` truncation could not bypass GR19's raise.

The arm it selects then over-fires:

```csharp
src/Cobol.Net.Runtime/Control/CobolPtr.cs:152-161
public static ManagedPointer UpByReal(ManagedPointer? p, double by)
{
    if (!double.IsFinite(by) || by != Math.Truncate(by) || by < long.MinValue || by > long.MaxValue)
    {
        ExceptionState.SizeAddressError(
            "SET pointer UP/DOWN BY a non-integer amount (ISO 14.9.39 Format 10 GR19)");
        return p ?? ManagedPointer.Null;
    }
    return UpBy(p, (long)by);
}
```

`by != Math.Truncate(by)` **is** GR19's test. The other three disjuncts are a MAGNITUDE / representability
guard folded into the same raise and the same message. An amount of 1.0E19 held in a `FLOAT-LONG` item **is an
integer value**, so GR19's antecedent is FALSE and EC-SIZE-ADDRESS must not be set — yet the run unit
terminates fatally under `>>TURN EC-SIZE-ADDRESS CHECKING ON`, and with checking OFF the statement silently
applies GR19's "unsuccessful … unchanged" outcome to a case GR19 does not govern.

**The rule the standard supplies for this case names a DIFFERENT condition.** GR20 governs the resulting
address, and it sets EC-RANGE-PTR, not EC-SIZE-ADDRESS. And under this implementation's own recorded choice —
`CobolPtr.cs:68-72`, "The implementor data-pointer range is UNBOUNDED … EC-RANGE-PTR is never raised at SET
time" — no condition should be set here at all and the pointer should simply move, an out-of-cell address
surfacing at the next dereference. **Under either reading the exception condition that fires is the wrong
one**, which makes this a wrong answer on legal COBOL rather than a missing branch. §14.6.13.1.1's
multiple-condition latitude does not cover it: only one condition is true here and the code sets the other.

## THE RULES, QUOTED, EACH `--check`ed ON THIS TREE

* `--check 14.9.39.4 "If this new address is outside the range of values allowed by the implementor for a
  data-pointer data item, the EC-RANGE-PTR exception condition is set to exist"` →
  **OK §14.9.39.4 20) (General rules)**. GR20 is the rule for an unrepresentable RESULT.
* `--find "EC-SIZE-ADDRESS exception condition is set to exist, the execution of the SET statement is
  unsuccessful"` → **§14.9.39.4 19) (General rules)**, whose antecedent is "If arithmetic-expression-3 does not
  evaluate to an integer" — an antecedent about the AMOUNT'S VALUE, not its magnitude.
* `--find "EC-BOUND-PTR exception condition is set to exist"` → **§13.18.5.4 4) (General rules)**: "If the
  subject of the entry is referenced while its address is not NULL and not a valid address of storage, the
  EC-BOUND-PTR exception condition is set to exist." — the condition the unbounded-range determination defers
  the failure to.
* `--check A.1 "USAGE POINTER clause (alignment, size, representation, and range of values). This item is
  required."` → **OK §A.1 216)** — the determination that decides which of the two readings is this
  implementation's, and which `docs/CONFORMANCE.md` does not carry (PB460's row).

## EXPECTED vs OBSERVED — re-run on HEAD

Probes written for this note into `scratchpad/probe-g8-set-b/p4/` (the refuter's were not in the b2 probe tree).

```
$ cobol.exe pb465realturn.cob --std 2023 --run
   01 BUF PIC X(4) VALUE "ABCD".   01 P USAGE POINTER.   01 A USAGE FLOAT-LONG VALUE 1.0E19.
   >>TURN EC-SIZE-ADDRESS CHECKING ON
   SET P TO ADDRESS OF BUF.   SET P UP BY A.   DISPLAY "MOVED".
abnormal run-unit termination: EC-SIZE-ADDRESS (fatal): SET pointer UP/DOWN BY a non-integer amount
    (ISO 14.9.39 Format 10 GR19)

$ cobol.exe pb465realoff.cob --std 2023 --run          # checking OFF, pointer position read through a BASED alias
   01 A USAGE FLOAT-LONG VALUE 1.0E19.   01 B USAGE FLOAT-LONG VALUE 2.0.
AFTER-2.0=[C]        SET P UP BY B  -> offset 2 in "ABCD": the integral-at-scale control is CORRECT
AFTER-1E19=[A]       SET P UP BY A  -> offset 0: the pointer did not move, silently
```

**Expected.** 1.0E19 is an integer, so GR19's condition is false: no EC-SIZE-ADDRESS, and the run unit does not
terminate. Under this implementation's unbounded-range determination the pointer simply moves and
`DISPLAY "MOVED"` prints; under a bounded-range determination the condition set to exist would be EC-RANGE-PTR
(GR20), and the pointer would be unchanged for THAT reason with THAT name in `FUNCTION EXCEPTION-STATUS`.
Either way, `EC-SIZE-ADDRESS … non-integer amount` is wrong, and the message actively misinforms.

## WHY NO TEST CAUGHT IT

The refuter's account is *nearly* right and I correct it here. There ARE two unit tests over this rule:

* `tests/Cobol.Net.Tests.Unit/CobolPtrTests.cs:42` `UpByScaled_IsTheExactGr19ValueRule` — calls only
  `CobolPtr.UpByScaled(p, 20|25, 1)`; it never touches `UpByReal`, the arm `PtrEmitter.cs:82-92` selects for
  every native-float amount. (This much the refuter reported correctly.)
* `tests/Cobol.Net.Tests.Unit/CobolPtrTests.cs:135` `UpByReal_IntegralityOnTheDouble` — this one DOES call
  `UpByReal`, with 1.5 (unchanged) and 2.0 (displaces by 2). ⚠ The refuter's claim that `UpByReal` is untouched
  by any test is therefore **overstated**.

The accurate statement is narrower and more useful: **neither test drives an INTEGRAL amount outside `long`
range**, so both pass while the magnitude disjuncts go unexercised. Both tests probe the axis the subject
varies (integral vs fractional) and neither flips the axis it holds fixed (small vs large) —
`feedback_probe_the_shape_the_subject_hides`.

## THE CODE SITE AND THE SHAPE OF THE REPAIR

| site | today |
| --- | --- |
| `Runtime/Control/CobolPtr.cs:152-161` `UpByReal` | one condition, one raise, two different rules |
| `Runtime/Control/CobolPtr.cs:96-112` `UpByScaled` | the scaled twin — its `scaledBy % pow != 0` is GR19 alone and is CORRECT |
| `Runtime/Control/CobolPtr.cs:73-92` `UpBy` | the mover; carries the unbounded-range determination in its doc-comment |
| `CodeGen/Verbs/PtrEmitter.cs:82-101` | the Real / scaled / plain split that selects the arm |
| `Runtime/Exceptions/ExceptionState.cs:380-390` `SizeAddressError` | the raiser |

⛔ **Do not simply delete the three magnitude disjuncts** (CLAUDE.md rule 5). That silently converts an
unrepresentable displacement into a `(long)` cast with undefined behaviour, which is a worse answer than the
wrong condition. The repair is to separate the two rules the one condition conflates:

1. **GR19 is the integrality test and nothing else** — `by != Math.Truncate(by)`, plus the NaN/infinity case,
   which is genuinely "does not evaluate to an integer". Keep the EC-SIZE-ADDRESS raise and the
   unchanged-operand return for exactly those.
2. **Magnitude belongs to GR20**, and its answer follows from the A.1 216 determination. Decide it, write it
   into `docs/CONFORMANCE.md` (PB460's row), and implement THAT: either the range is unbounded, in which case
   the displacement must be carried without a `long` cast losing it, or it is bounded, in which case
   EC-RANGE-PTR is raised with the operand unchanged. A guard that cannot say which rule it is enforcing is the
   defect.
3. Whichever lands, the message must stop saying "non-integer amount" for a magnitude case.

## THE SIBLING SWEEP

* `UpByScaled` (`:96-112`) has the SAME latent magnitude question — `scaledBy / pow` can be any `long`, and the
  subsequent `UpBy(p, …)` has no range test either. Ask which arm you fixed
  (`feedback_two_arm_dispatch`).
* `CobolPtr.AllocateReal`/`Allocate` (`:145`) applies an `(Int128)` conversion to a float amount from the same
  emitter split; check whether it folds magnitude into a rule about value.
* `EmitAllocate`'s Scale==0/Real split is named at `PtrEmitter.cs:84` as having been mispriced once already —
  re-check it against §14.9.3's own rules.
* Every unit test in `CobolPtrTests.cs` named for a rule: check that it drives the arm the EMITTER selects, not
  a sibling entry point. `UpByScaled_IsTheExactGr19ValueRule` is named for GR19 and never runs the float arm.
* EC-RANGE-PTR is a catalog row (`ExceptionCatalog.cs:166`) with no raise site — the same shape as
  EC-RANGE-INDEX (PB459) and EC-BOUND-SET (PB460).

## ROWS

* `GR-14.9.39.4-19` — was CONFORMS; **DIVERGES**. The rule's own content is implemented correctly on the scaled
  arm and for the small-magnitude float case (measured: `AFTER-2.0=[C]`), but the float arm the emitter selects
  raises GR19's condition for a case GR19 does not govern (measured: fatal EC-SIZE-ADDRESS on an integral
  1.0E19, and a silent no-move with checking off). The row cannot close until A.1 216's range determination
  exists, because that is what decides the correct answer for the magnitude half.
