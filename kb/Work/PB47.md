# PB47 — LANDED — an illegal EVALUATE pairing was diagnosed at the wrong STAGE

> ⚙ **FOUND WHILE CLOSING [[PB45]].** PB45's two defects both ended at the same line — `EvaluateBinder`'s
> `BoundConditionError("EVALUATE TRUE/FALSE paired with a value WHEN object")`. Both were LEGAL source reaching a
> rejection, and both are fixed. What was left at that line is the opposite case: **ILLEGAL source reaching it,
> and being reported at the wrong stage.**

## THE DEFECT

`BoundConditionError` is realized as a **run-time** `NotImplementedCobolFeatureException`, so

```cobol
EVALUATE TRUE
    WHEN W-Z          *> an identifier object against a TRUE subject
```

compiled CLEAN and threw when that WHEN was reached — and only if it was reached. **§14.9.13.3 SR10 + Table 15
make it a SYNTAX RULE violation**, i.e. a compile-time diagnostic. The message was wrong twice over: the feature
is not "not yet implemented", and the source is inadmissible.

## ✅ LANDED — AND TABLE 15 IS A TABLE

`EvaluateOperandCombinations` holds the 9×6 matrix in the standard's own row/column order, and
**`EvaluateOperandCombinationsDriftTests` re-parses Table 15 out of `specs/ISO_COBOL.md` and compares all 54
cells**, asserting the population so a broken scrape cannot pass vacuously. That is the difference between a
transcription and a derivation ([[feedback_a_dead_lookup_is_also_unverified]] — PB1's `ArgKinds` column was not
merely unread but UNVERIFIED, and enforcing it as written rejected 12 legal corpus programs). New diagnostic
**`COBOLNET1634`**; negative fixture `pb47-evaluate-table15-invalid-combination`.

## ⛔ THE SCREEN DECLINES RATHER THAN GUESSES — AND THAT IS NOT CAUTION, IT IS §14.9.13.3 SR6

Both classifiers return null when they cannot answer with certainty, and a null on either side means **no
diagnostic**. This narrows what already failed; it does not widen what is refused.

**The first version did guess, and the gate caught it within a minute.** Classifying a BOOLEAN operand as a
condition — which `ConditionBinder.BareOperandAsCondition`'s §8.8.4.3 arm reports — rejected the legal
`EVALUATE BW WHEN B"01"` over a `PIC 1(2)` item, because identifier × condition is a blank cell. The rule that
makes it legal is **SR6**, and it is the same subject-dependence PB45 kept running into:

> a) If the selection subject is TRUE or FALSE and the selection object is a boolean expression that results in
> one boolean character, the selection object is treated as a boolean condition and therefore **condition-2**.
> c) If the selection subject is other than TRUE or FALSE … it is treated as a boolean expression and therefore
> **boolean-expression-2**.

Those are two different Table 15 rows, chosen by the SUBJECT *and* by a "results in one boolean character" length
test that is not implemented. So a boolean operand on either side is declined outright, with SR6 cited at the
`return null`.

⚠ **RECORDED, so the gap is not mistaken for coverage** ([[feedback_green_test_can_hold_a_gap_open]]): the
**boolean-expression** and **partial-expression** rows of Table 15 are carried by the matrix but are **not
reachable** today — the grammar stages both (the DEVLOG-621 `comparisonExpression` note), so no operand
classifies into them. The table is right; the classifier's coverage is partial by construction, and the drift
test keeps the table honest for when the grammar catches up.

## ⚠ WHAT WAS DELIBERATELY NOT DONE

Enforcing every blank cell would add NEW rejections the compiler has never made — e.g. **literal × literal is a
blank cell**, so `EVALUATE "A" WHEN "B"` is invalid per SR10. That is enforced now (both sides classify as
Literal with certainty, per §14.9.13.4 GR1: "If an operand of the EVALUATE statement consists of a single
literal, that operand is treated as a literal, not as an expression"), and the comprehensive battery — NIST 353,
the full corpus and the GnuCOBOL differential — is what says no legal program relied on it.
