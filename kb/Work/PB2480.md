# PB2480 — no script seeds a second account's config dir

Owner, 2026-10-07 13:17 PDT: a second Claude Code session, logged into a second Max 20x account (`CLAUDE_CONFIG_DIR=C:\Users\brent\.claude-acct2`), runs every Opus/Sonnet dispatch, the orchestrator loop and the landings (the OPERATOR); the first account's session keeps Mythos work. The owner seeded the second config dir by hand. Owner 13:36 PDT: account 2's week resets Saturday 2026-10-10 10:00 PDT and must be spent to 100 % before then, so every hour the tooling stops dispatch wrongly is quota lost.

**Model:** Opus (tooling with self-tests). All six notes are one mechanism (the account is a parameter of the coordination tooling, never an assumption) and are dispatched as one group.

## Defect

The owner built `C:\Users\brent\.claude-acct2` by hand on 2026-10-07 13:20. Account 1's `C:\Users\brent\.claude.json`
carries `claudeInChromeDefaultEnabled: true` and `hasCompletedClaudeInChromeOnboarding: true`; account 2's
`.claude-acct2\.claude.json` carries only `cachedChromeExtensionInstalled`, and the operator session found no
`mcp__claude-in-chrome__*` tools (ToolSearch, 13:33). The meter therefore came from the owner's `/usage` paste.

## Shape

`scripts/account-profile.ps1 -ConfigDir <dir>`: copy `settings.json`, `config.json`, `plugins\`, `skills\`; junction
`projects\E--COBOL\memory` to the shared memory folder; set the non-secret feature flags (Chrome enabled) in the new
`.claude.json`; never copy credentials. Idempotent (re-run repairs). Document the Chrome pairing under a non-default
config dir (the native host `~/.claude/chrome/chrome-native-host.bat` runs `claude.exe --chrome-native-host` with no
config dir: verify which account's session it serves and record the finding or the fallback, `/usage` in the
terminal). `scripts/hooks/tooling_check.py` gains a line that checks the running config dir is seeded.


## Landed (branch acct2-tooling, wave 1033 group T)

Re-probed 2026-10-07 on this tree: `account.py --seed-check` under `CLAUDE_CONFIG_DIR=C:\Users\brent\.claude-acct2`
reports `claudeInChromeDefaultEnabled is None` and `hasCompletedClaudeInChromeOnboarding is None` (the memory junction
the owner made is correct), exit 1; the default account reports itself the source.

- What a named account's dir carries is DATA: `model_rules.json` `accounts.seed` (copy `settings.json`, `config.json`,
  `plugins`, `skills`; junction `projects/{repo_key}/memory` to the default account's; flags
  `claudeInChromeDefaultEnabled`, `hasCompletedClaudeInChromeOnboarding`; never `.credentials.json`).
  `account.py --seed-plan` turns it into paths, `--seed-check` lists what is missing.
- `scripts/account-profile.ps1 -ConfigDir <dir>` carries the plan out idempotently: a missing file or directory child
  is copied, the account's own files are kept (`-Force` overwrites top-level files), a wrong junction is re-pointed, a
  real directory where the junction belongs is refused, the flags are set with the rest of `.claude.json` byte-faithful
  in value (`ConvertFrom-Json -DateKind String`), written atomically; then it runs `--seed-check`.
- `tooling_check.py` gains the `Claude account seed` line (OK, or ASK-OWNER naming the command), at every session start.
- Chrome pairing, measured: the native host `~\.claude\chrome\chrome-native-host.bat` runs `claude.exe

  keyed by the Windows user, not the Claude account; so one pairing serves either account once the flags are set. The

  session's (`account.py --field email`). Fallback: `/usage` in that account's terminal.
