**based-clause** — §13.18.5.3 SR2 (no dynamic-length / variable-length-group subject) is screened nowhere; the BASED arm inherits whatever the ONE cell forcer (ForceStringCanonical) can carry, and PB1026 taught the cell to carry dynamic-length leaves

- **Repro:** --std 2023 (also 2014): `01 G BASED. 05 A PIC X(3). 05 D PIC X DYNAMIC LENGTH.` `ALLOCATE G. MOVE "ABC" TO A. MOVE "HELLO" TO D. DISPLAY "A=" A " D=" D.` -> compiles and prints A=ABC D=HELLO (probe sr2b.cob). The dynamic-capacity-table spelling (sr2c.cob) is refused only by COBOLNET1695 'recognized but not yet implemented'.
- **Expected (spec):** Both rejected at compile time with a named SR2 diagnostic: §13.18.5.3 SR2 'The subject of the entry shall not be a dynamic-length elementary item or a variable-length group.', and §8.5.1.12.1 makes any group with a dynamic-length elementary or dynamic-capacity-table subordinate a variable-length group.
- **Observed:** The BASED declaration validation (DataBinder.cs ~L4644) checks level, REDEFINES and EXTERNAL only; ByteWindowResidueOf / VariableLengthCellResidueOf are CARRIAGE gates (what the cell can hold), shared with EXTERNAL and ADDRESS OF where variable-length groups are legal, so they cannot stand in for SR2. The elementary spelling is caught by §13.16.3 SR18 (correct). Fix belongs in the BASED validation arm as a spec screen independent of carriage.
- **Code site:** src/Cobol.Net.Compiler/Binding/DataBinder.cs (BASED declaration validation ~L4644); src/Cobol.Net.Compiler/Binding/DataBinder.Linkage.cs#ForceStringCanonical / #VariableLengthCellResidueOf

## Landing (wave 68, group U)
Re-probed on the w68u build: `sr2b.cob` (BASED group with a DYNAMIC LENGTH leaf) compiled and printed
`A=ABC D=HELLO`; `sr12v.cob` (`CONSTANT AS LENGTH OF` a group with a DYNAMIC LENGTH leaf) printed `2`; the elementary
DYNAMIC LENGTH operand was refused only by the GR6 "not computable" arm. Probing the value side found a third
defect under GR6: `CONSTANT AS LENGTH OF` read `DataItem.ImageWidth` while `FUNCTION LENGTH` read the §15.50.4 fold,
so `X(2) + N(2)` gave 4 against the function's 6, and `PIC 1(8) USAGE BIT` gave its 1-byte occupancy against 8.

**Mechanism: one rule written in several places.** The pair "a dynamic-length elementary item or a variable-length
group" (§13.18.5.3 SR2, §13.10.3 SR12, §13.18.44.3 SR17, §12.4.5.8.3 SR3) had one spelling per consumer, and the
CONSTANT one walked dynamic-capacity TABLES only. BASED had no screen for it at all.
- `VariableLengthCompatibility.DynamicLengthOrVariableLengthGroup` is now THE screen of the pair (the group half is
  `IsVariableLength`, §8.5.1.12.1 verbatim). REDEFINES SR17 (`Sr17Shape` deleted), FILE STATUS SR3, CONSTANT SR12
  and the new BASED SR2 arm all go through it.
- BASED SR2: `DataBinder.CheckUsageDeclarations`, beside SR1, new code **COBOLNET2560**. It clears `IsBased` (the
  BASED placement arms' rule) so the cell classifier adds no "not yet implemented" COBOLNET1695 for the same entry.
  It reads the shape, never the carriage gates (`ByteWindowResidueOf` / `VariableLengthCellResidueOf`).
- CONSTANT SR12 now also ADMITS what the table walk wrongly refused: `LENGTH OF T (1)` where T is itself OCCURS
  DYNAMIC (T is not a variable-length group) is 5.
- GR6 value: `IntrinsicBinder.LengthPositions` moved to the data model as `ItemLength.Positions`; the CONSTANT
  entry and both FUNCTION LENGTH arms read it (INTRINSICS + DATA_MODEL design docs updated).

Goldens: `conformance:2014/pb1213_varlen_neighbours` (positive, legal neighbours + the GR6 values beside FUNCTION
LENGTH), `negative/pb1213-based-variable-length-group`, `negative/pb1213-constant-length-variable-group`.
Sibling not taken: §13.18.12.3 SR2 (CODE clause identifier-1, three shapes) is owned by PB1129 / PB1218.
