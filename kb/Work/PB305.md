# PB305 — the model states the right thing in one arm and contradicts it in the other

⚠ **This is a counter-example to a row currently recorded GREEN.** `AR-15.37.3-2` is a real register row
(`docs/rearchitecture/spec-rule-catalog.json:30986`, `tests/version-matrix/traceability-inventory.json:44749`)
and it records **verdict CONFORMS / state OK / LANDED 2026-08-17** (kb/Work PB58).

## The rules

* §15.37.3 r2: *"If argument-1 is of class alphabetic or alphanumeric, argument-2 shall be a data item or literal
  of either class alphabetic or alphanumeric"* — `cite.py --check 15.37.3` OK.
* §8.5.2.1 **Table 2** puts category *numeric-edited (if usage is display)* in class **alphanumeric** —
  `cite.py --check 8.5.2.1` OK on the table's own heading sentence. ⚠ `--check 8.5.2` FAILS for that row; the
  table is in §8.5.2.1.
* §8.4.3.3.4 r6 c) says the same in words: *"the categories numeric and numeric-edited are considered class and
  category national if the usage is national; otherwise they are considered class and category alphanumeric"* —
  `--check` OK.

So `01 ED PIC ZZ9.` is class **alphanumeric**, r1 admits it as argument-1 and r2 admits the alphanumeric literal
`"5"` beside it.

## Repro (held out of the corpus deliberately)

`out/string-p2/repro/find-string-numeric-edited-arg1.cob` in the golden lane's scratchpad — `PROGRAM-ID
L1FSNUMED`, `--std 2023`:

```cobol
       01 ED PIC ZZ9.
       01 P  PIC 9(4).
           MOVE 5 TO ED.
           MOVE FUNCTION FIND-STRING(ED "5") TO P.
           DISPLAY "NUMED=" P.
```

Expected `NUMED=0003` — `MOVE 5 TO` a `PIC ZZ9` item leaves the three character positions `"  5"`, so §15.37.4 r1
returns the first occurrence at character position 3. **It is not registered in any manifest**: it is legal source
the compiler rejects, so it must not enter the corpus until the fix lands.

## Root cause

`IntrinsicArgumentRules.cs:466` maps `PicCategory.NumericEdited => CobolClass.NumericEditedDeEditing`, a member
distinct from `CobolClass.Alphanumeric`. The FIND-STRING schema is
`Schema("§15.37.3 r1/r2/r3", ['s','s','i'], cross: CrossArgRule.MatchArgument1, crossClause: "§15.37.3 r2")`.
`CrossViolation` (~line 1225) intersects the candidate sets, and the **only** normalization before the
intersection at line 1243 is line 1242:

```csharp
cs = [.. cs.Select(c => c == CobolClass.Alphabetic ? CobolClass.Alphanumeric : c).Distinct()];
```

It folds `Alphabetic` and **not** `NumericEditedDeEditing`. So `[NumericEditedDeEditing] ∩ [Alphanumeric]` is
empty and `CheckArgumentClasses` reports `DiagnosticCatalog.IntrinsicArgumentClass` = `COBOLNET1627`.

**The per-position screen is NOT the culprit and is correct.** Line 959's `'s'` set already lists
`NumericEditedDeEditing` beside `Alphanumeric` with the comment *"Table 2 makes numeric-edited (display) class
ALPHANUMERIC, so a class rule admits it as such"*, and the enum member's own doc says *"Anywhere a rule says
'shall be of CLASS alphanumeric', this counts as alphanumeric"*. The cross rule is the one place that sentence was
not applied — `feedback_two_arm_dispatch`.

## The self-refutation, and be exact about WHICH message says it

`CrossViolation` walks the governed positions in order and reports the FIRST one that empties the intersection, so
`FIND-STRING(ED "5")` empties at position 1 and prints the plain name: *"argument-2 is of class alphanumeric,
which cannot agree with argument-1"*. Write the pairing the other way round — `FIND-STRING("ABC" ED)` — and
position 1 carries `NumericEditedDeEditing`, whose `Name()` (line 1258) is the string `"alphanumeric
(numeric-edited)"`: the message then reads *"argument-2 is of class alphanumeric (numeric-edited), which cannot
agree with argument-1; ISO §15.37.3 r2 requires it to be of the same class as argument-1"* — **it names the class
as alphanumeric in the same sentence in which it rejects it for not being alphanumeric.** Both orders are legal
under r2; the reversed one is the shorter proof and costs one line beside the repro.

## The fix, and the sweep

The normalization is a **hand-written one-case fold where a Table-2 class PROJECTION belongs**, so every schema
carrying a cross rule inherits it. Replace it with one projection function used by both the per-position screen
and the cross screen, so ONE reader answers "what class is this operand for a class rule". Siblings in the same
table using `MatchArgument1` — TRIM (§15.96.3 r2), SUBSTITUTE (§15.87.3 r2), NUMVAL-C (§15.68) — inherit the same
fold and must be re-measured with the fix. Pair it with a drift test asserting the two screens agree on every
`CobolClass` member, so the next class added cannot be admitted by one and refused by the other.
