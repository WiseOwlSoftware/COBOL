# PB305 — the model states the right thing in one arm and contradicts it in the other

⚠ **This is a counter-example to a row currently recorded GREEN.** `AR-15.37.3-2` is a real register row
(`docs/rearchitecture/spec-rule-catalog.json:30986`, `tests/version-matrix/traceability-inventory.json:44749`)
and it records **verdict CONFORMS / state OK / LANDED 2026-08-17** (kb/Work PB58).

## The rules

* §15.37.3 r2: *"If argument-1 is of class alphabetic or alphanumeric, argument-2 shall be a data item or literal
  of either class alphabetic or alphanumeric"* — `cite.py --check 15.37.3` OK.
* §8.5.2.1 **Table 2** puts category *numeric-edited (if usage is display)* in class **alphanumeric** —
  `cite.py --check 8.5.2.1` OK on the table's own heading sentence. ⚠ `--check 8.5.2` FAILS for that row; the
  table is in §8.5.2.1.
* §8.4.3.3.4 r6 c) says the same in words: *"the categories numeric and numeric-edited are considered class and
  category national if the usage is national; otherwise they are considered class and category alphanumeric"* —
  `--check` OK.

So `01 ED PIC ZZ9.` is class **alphanumeric**, r1 admits it as argument-1 and r2 admits the alphanumeric literal
`"5"` beside it.

## Repro (held out of the corpus deliberately)

`out/string-p2/repro/find-string-numeric-edited-arg1.cob` in the golden lane's scratchpad — `PROGRAM-ID
L1FSNUMED`, `--std 2023`:

```cobol
       01 ED PIC ZZ9.
       01 P  PIC 9(4).
           MOVE 5 TO ED.
           MOVE FUNCTION FIND-STRING(ED "5") TO P.
           DISPLAY "NUMED=" P.
```

Expected `NUMED=0003` — `MOVE 5 TO` a `PIC ZZ9` item leaves the three character positions `"  5"`, so §15.37.4 r1
returns the first occurrence at character position 3. **It is not registered in any manifest**: it is legal source
the compiler rejects, so it must not enter the corpus until the fix lands.

## Root cause

`IntrinsicArgumentRules.cs:466` maps `PicCategory.NumericEdited => CobolClass.NumericEditedDeEditing`, a member
distinct from `CobolClass.Alphanumeric`. The FIND-STRING schema is
`Schema("§15.37.3 r1/r2/r3", ['s','s','i'], cross: CrossArgRule.MatchArgument1, crossClause: "§15.37.3 r2")`.
`CrossViolation` (~line 1225) intersects the candidate sets, and the **only** normalization before the
intersection at line 1243 is line 1242:

```csharp
cs = [.. cs.Select(c => c == CobolClass.Alphabetic ? CobolClass.Alphanumeric : c).Distinct()];
```

It folds `Alphabetic` and **not** `NumericEditedDeEditing`. So `[NumericEditedDeEditing] ∩ [Alphanumeric]` is
empty and `CheckArgumentClasses` reports `DiagnosticCatalog.IntrinsicArgumentClass` = `COBOLNET1627`.

**The per-position screen is NOT the culprit and is correct.** Line 959's `'s'` set already lists
`NumericEditedDeEditing` beside `Alphanumeric` with the comment *"Table 2 makes numeric-edited (display) class
ALPHANUMERIC, so a class rule admits it as such"*, and the enum member's own doc says *"Anywhere a rule says
'shall be of CLASS alphanumeric', this counts as alphanumeric"*. The cross rule is the one place that sentence was
not applied — `feedback_two_arm_dispatch`.

## The self-refutation, and be exact about WHICH message says it

`CrossViolation` walks the governed positions in order and reports the FIRST one that empties the intersection, so
`FIND-STRING(ED "5")` empties at position 1 and prints the plain name: *"argument-2 is of class alphanumeric,
which cannot agree with argument-1"*. Write the pairing the other way round — `FIND-STRING("ABC" ED)` — and
position 1 carries `NumericEditedDeEditing`, whose `Name()` (line 1258) is the string `"alphanumeric
(numeric-edited)"`: the message then reads *"argument-2 is of class alphanumeric (numeric-edited), which cannot
agree with argument-1; ISO §15.37.3 r2 requires it to be of the same class as argument-1"* — **it names the class
as alphanumeric in the same sentence in which it rejects it for not being alphanumeric.** Both orders are legal
under r2; the reversed one is the shorter proof and costs one line beside the repro.

## The fix, and the sweep

The normalization is a **hand-written one-case fold where a Table-2 class PROJECTION belongs**, so every schema
carrying a cross rule inherits it. Replace it with one projection function used by both the per-position screen
and the cross screen, so ONE reader answers "what class is this operand for a class rule". Siblings in the same
table using `MatchArgument1` — TRIM (§15.96.3 r2), SUBSTITUTE (§15.87.3 r2), NUMVAL-C (§15.68) — inherit the same
fold and must be re-measured with the fix. Pair it with a drift test asserting the two screens agree on every
`CobolClass` member, so the next class added cannot be admitted by one and refused by the other.

⚠ **Not measured** — the tree was frozen when this was derived; it is a reading of the code path and must be
confirmed by a run before the fix is written.

## Landed 2026-09-05 — the fold was a PROJECTION, and the population was TWELVE functions

**Reproduced first, on this tree's own build**, and the note's reading of the code path held in every particular
including the self-refuting message:

```
error COBOLNET1627: FUNCTION FIND-STRING argument-2 is of class alphanumeric, which cannot agree with
argument-1; ISO 15.37.3 r2 requires it to be of the same class as argument-1.        (FIND-STRING(ED "5"))
error COBOLNET1627: FUNCTION FIND-STRING argument-2 is of class alphanumeric (numeric-edited), which cannot
agree with argument-1; ISO 15.37.3 r2 ...                                            (FIND-STRING("  5" ED))
```

**The population was wider than the note predicted.** The note named TRIM, SUBSTITUTE and NUMVAL-C as the
`MatchArgument1` siblings. Measured on the pre-fix build, EVERY schema carrying a cross rule inherited the fold —
twelve functions, and the four the note did not name are the `AllSameClass` arm: `FUNCTION MAX(<PIC ZZ9> "A")`,
MIN, ORD-MAX and ORD-MIN were refused just as widely, on §15.59.3 r2 / §15.63.3 r2 / §15.71.3 r3 / §15.72.3 r3.
An independent adversarial probe sweep had already recorded FIND-STRING, MAX and MIN as this exact defect on
2026-08-09 (`docs/rearchitecture/backlog-probe-sweep-2026-08-09.json`), inside prose no work list could see.

**⛔ ELEVEN OF THE TWELVE ROWS WERE RECORDED GREEN.** Only AR-15.96.3-2 was GAP, and for an unrelated reason
(TRIM's variadic tail is unscreened — that PARTIAL is untouched and still open). The other eleven all read
`CONFORMS / OK` while the compiler turned away legal source under the very rule they claimed. The evidence could
not see it: `2023/find_string_argument1_classes` DOES carry a numeric-edited FIND-STRING case, but it wrote
`FIND-STRING(EDH EDN)` — numeric-edited paired WITH numeric-edited — so the two candidate sets intersected
non-empty and the screen passed for the wrong reason (`feedback_probe_the_shape_the_subject_hides`). **The mixed
pairing is the shape that was never written.**

### The rules, each `--check`ed

* §15.37.3 r2 — "If argument-1 is of class alphabetic or alphanumeric, argument-2 shall be a data item or literal
  of either class alphabetic or alphanumeric. If argument-1 is of class national, argument-2 shall be of class
  national." — `cite.py --check 15.37.3` OK.
* §8.5.2.1 — "Use of the name of a data class or data category in the rules of COBOL refers to the category unless
  class is specifically indicated." — OK. This is the sentence that makes the class/category axis real.
* §8.4.3.3.4 6) c) — "the categories numeric and numeric-edited are considered class and category national if the
  usage is national; otherwise they are considered class and category alphanumeric." — OK.
* **The decisive new reading: EVERY cross clause in the catalogue is CLASS-worded.** §15.96.3 r2 and §15.87.3 r2
  say "class alphabetic or class alphanumeric"; §15.59.3 r2, §15.63.3 r2, §15.71.3 r3 and §15.72.3 r3 say "All
  arguments shall be of the same class with the exception that mixing of arguments of alphabetic and alphanumeric
  classes is allowed"; §15.48.3 r3, §15.79.3 r3 and §15.92.3 r2 say "the same type as argument-1", read as the
  class by each schema row's own comment. So the cross screen needs no per-rule axis flag — the projection applies
  unconditionally, which is what made the fix three lines rather than a table.
* **§15.68.3 is the proof that the two readings must stay apart**: r1 is CATEGORY-worded ("Argument-1 shall be of
  category alphanumeric or national") and r2 is CLASS-worded ("shall be of the same class as argument-1") — one
  function, one operand, two different questions.

### The fix

`IntrinsicArgumentRules.TableTwoClass` is the new ONE reader of "what class is this operand, for a rule that says
CLASS" — §8.5.2.1 Table 2's class column over the lattice's refined members, mapping `NumericEditedDeEditing` to
`Alphanumeric` and identity elsewhere. `CrossBlock` composes it with the cross rules' own alphabetic|alphanumeric
merge, **projecting first and merging second**, and `CrossViolation` now normalizes through `CrossBlock`. The
order is the whole bug: a merge applied to the UNPROJECTED member left numeric-edited alone in a block of its own.

The note asked for "one projection function used by both the per-position screen and the cross screen". **That
half of the prescription was corrected during implementation** and the correction is recorded here: forcing both
screens through one projection would make §15.68.3 inexpressible, because the per-position screen must be able to
SEE the category the class column folds away. What the two screens share is the projection, not the answer. So
`Admissible`'s CLASS-worded arms ('n', 'i', 'b', 's', 'c') are now derived from it by `ByClass(...)` — a refined
member is admitted BY ITS CLASS, never by being remembered in the list — while the one CATEGORY-worded arm ('t')
keeps a literal list on purpose, and the shape now says which is which. `ByClass` emits the rule's own wording
order with each class's refinements following it, so no diagnostic text changed. The derived sets are `static
readonly`, because a derived set must be computed once and the screen runs per argument of every intrinsic call.

Also corrected in the same change set: `ClassOfCategory`'s comment on the `NumericEdited` arm still carried the
de-editing justification the owner overturned on 2026-08-02 — the second copy that never got the correction.

### Sweep, goldens and drift

`grep -n "CrossArgRule\|Admissible\|NumericEditedDeEditing" IntrinsicArgumentRules.cs` located every site; the
one fold was the only place the projection was missing, and the per-position screen was correct exactly as the
note said. Goldens: `2023/pb305_cross_argument_numeric_edited` (all ten functions the rule admits) and
`85/pb305_cross_argument_numeric_edited_85` (the MAX family at the oldest edition — the class column is
edition-invariant), both written as EQUIVALENCES between the edited item and the byte-identical `PIC X` twin
built from it by MOVE, which is precisely what Table 2 asserts and carries no dependence on the runtime collating
sequence; three anchors are pinned to values derived from the standard without it (FIND-STRING 3 per §15.37.4 r1,
SECONDS-FROM-FORMATTED-TIME 45296 per §15.79.4 r1's own arithmetic, TEST-FORMATTED-DATETIME 0 per §15.92.4 r1).
Negatives `negative/pb305-cross-class-national-mixed` (the over-merge witness) and
`negative/pb305-numval-c-edited-category` (the category witness) hold the other side.
`IntrinsicArgumentClassDriftTests.EveryCrossArgumentRule_AcceptsTwoOperandsOfOneTable2Class` walks the whole
schema table against one witness per `CobolClass` member and fails if any cross screen SPLITS a Table-2 class;
`EveryClassWordedArgumentKind_IsClosedUnderItsTable2Class` holds the `ByClass` derivation. Both were run RED
against the pre-fix fold, naming all twelve functions, before the fix was restored.
