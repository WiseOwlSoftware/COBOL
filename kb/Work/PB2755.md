**Rule it breaks:** performance dimension (tools/claude-skills/skills/review/references/dimensions.md 3: complexity at a stated input size on a hot path; DESIGN-architecture-review section 5.4): a per-statement operation must not cost time proportional to the file; section 8.3 already prescribes an ordered key index (KeyIndex: find, insert, remove and ordered scan by key) for the indexed organization (PB2129) and none for the relative one

**Scenario:** Count read from the pinned code: SelectSequentialSlot (RelativeConnector.cs:262-280) enumerates _slots.Keys from the LOWEST RRN on every READ NEXT / READ PREVIOUS until it passes the file position indicator, so READ number k visits k keys and a READ NEXT walk of an N-record relative file visits N(N+1)/2 keys: 5.0e7 at N = 10,000, 5.0e9 at N = 100,000, 5.0e11 at N = 1,000,000 (hours for a file GnuCOBOL reads in well under a second). Every READ also constructs a SortedDictionary key enumerator, whose SortedSet enumerator allocates a Stack<Node> of 2*log2(N+1) entries, and a READ under record locking pays the walk twice (PeekSequentialRecordId:288 runs the same selection before ReadSequential:312). START with < or <= (Start:512-513) walks the whole map, START with > or >= walks up to the operand, START FIRST takes _slots.Keys.Min() (Enumerable.Min over the whole key collection, StartFirstLast:524), and RelativeStore.Remove rescans every key with Keys.Max() whenever the highest RRN is deleted (KeyedStoreTable.cs:143), so a DELETE of the records from the top down is O(N^2) too. No benchmark row covers the relative organization (perf baseline 354c79ef3312 has IDXHOT, SEQHOT, MOVEHOT, PERFHOT only), so the R3 wave should add a RELHOT row beside IDXHOT to show the curve linear.

**Measured how:** R2 batch finding `runtime-io-2--performance--f1#1` (pair runtime-io-2--performance), read in the pinned tree at 8be23006851a; skeptics rule upheld, scenario upheld, site upheld. Measurement: count read from the pinned code at stated sizes: a READ NEXT walk of N records visits N(N+1)/2 RRN keys (SelectSequentialSlot enumerates from the lowest key each READ) = 5.0e9 key visits plus 100,000 enumerator Stack allocations at N = 100,000; START < / <= and START FIRST visit all N keys per statement; no baseline row covers the relative organization

**Skeptics' corrections applied:** rule lens: severity "Critical" -> "Warning"

**Target:** RelativeStore owns an ordered RRN index with O(log N) successor and predecessor queries (first key >= k, first key > k, last key < k, last key <= k, lowest, highest) and keeps it current through its existing Put/Remove/Clear mutators; SelectSequentialSlot, Start and StartFirstLast each become one call to it and Remove re-derives Highest by a predecessor query. Prefer ONE ordered-index type shared with the indexed organization (the KeyIndex section 8.3 assigns to PB2129, made generic over the key so an RRN is just a long key) over a second hand-written index, so the next keyed organization gets the bound automatically; pin it with a scaling benchmark row (RELHOT) rather than a wall-clock test.
