# PB3387 — a watcher that fired mid-session was never re-armed

**What happened (2026-10-18, operator session c95c0b86).** The operator's watcher (`mailbox.py watch --inbox operator
--timeout 0`) fired at 14:40 PDT on a Mythos message. The operator was in the middle of a doc sweep the owner had asked
for, and it neither read the message nor re-armed the watcher. At 15:00 it wrote "always re-arm the inbox watcher"
into its own resume memory without arming it. A context compaction followed. Its probe, at 15:57, printed "⛔ mailbox
(operator): 6 open in to-operator (oldest 14:40); NO watcher armed for this session", the summary listed re-arming as
pending, and the session still ended its next turn with a report to the owner and nothing else. Nine messages waited
until 17:14: eight from the Mythos lane, three of them landing requests for the reviewed engine branches, and the
loop's ledger publish notice. The owner asked: "WHY ARE YOU FAILING TO READ MESSAGES FROM mYTHOS?" `send` warns a
sender when the recipient's inbox holds messages open over 30 minutes (PB2816), but that reaches the sender, not the
session that stopped listening.

**Why PB2814 did not catch it.** PB2814 put the watcher state on every surface a session reads (the probe at every
start, resume, clear and compaction, plus `list` and `done`). It worked: the 15:57 probe showed the ⛔ line. But a line
to read is not a hold. A session that is busy with something else can read past it, as this one did twice: the
14:40 firing and the 15:57 line. A watcher also exits each time it fires, so between starts nothing re-states it at all.

**The fix (this change).**
- `scripts/hooks/inbox_guard.py`, a Stop hook (`.claude/settings.json`), asks `mailbox.status` at every attended
  turn's end. When it reads false, the hook refuses the stop with the ⛔ line as its reason, so the session acts on the
  inbox and arms the watcher before the turn ends. A loop unit (`COBOL_LOOP_UNIT`), a host without the coordination
  directory and a session with a watcher armed pass silently. A turn already continued for a Stop hook
  (`stop_hook_active`) gets the line as a warning, so the hook never loops. A failure of the hook itself is a warning,
  never an exception. Its `--self-test` drives every arm, and `self_tests.py` discovers it.
- **The process table is a kernel snapshot.** `coord.process_table` asked PowerShell CIM for `Win32_Process`, which
  took 8 to 12 s on this host under load (`mailbox.py status` measured 12.5 s). That is too slow for a check at every
  turn's end. It now reads one Toolhelp32 snapshot and each process's command line through
  `NtQueryInformationProcess` (`ProcessCommandLineInformation`): 0.12 s for 395 processes, and `status` takes 0.7 s. The
  sibling `coord.process_name` asked `tasklist` (6.5 s) and now reads the same snapshot. `coord.py --self-test` pins
  both against this process and a dead pid.
- `DESIGN-orchestrator-loop.md` (the mailbox section), `mailbox.py`'s watcher comment and the session-start skill name
  the hook.

**The branch review's finding, answered (R1-1, high).** `watch` returned at once while the inbox held ANY open
message, so a watcher could not stay armed beside a message the session had seen and could not close yet (one waiting
on the owner, a landing still running). With the hook, that loops: the turn ends, the hook refuses, the session arms
a watcher, the watcher exits on the old message within one poll, its exit re-invokes the session, and so on, one turn
per cycle with no owner input. The fix makes the watcher and the hold agree. `watch` fires only on messages no earlier
watch returned, which it records and prunes to the open messages (one record per session since R2-1, below). With a
watcher armed, the hook refuses nothing: a seen message open past `STALE_MINUTES` is named in a warning at every turn's
end. Both self-tests pin it: `mailbox.py` (a seen open message does not end the next watcher, a new one does and
only it is returned, a closed one drops out of the record) and `inbox_guard.py` (an armed watcher beside an old open
message gives a warning, never a refusal).

**The second round's finding, answered (R2-1, medium).** The R1-1 fix kept ONE delivered record per inbox, but a
watcher wakes only the session that armed it, so when two sessions watch one inbox (a restarted operator while the old
window is open; an ad-hoc account-1 session beside Mythos), the first watcher to poll recorded a new message delivered
and the other session's watcher never fired: a lost wake-up, the harm this note exists to prevent. The reviewer
reproduced it with two threads. The record is now per watching session, `mailbox/delivered-<lane>-<session pid>.json`
(the session's Claude Code process, `session_root`), and each watch deletes the records of sessions whose process has
ended. The `mailbox.py` self-test pins two sessions on one inbox: both are woken by the same waiting messages and by
each new one, and a dead session's record is deleted while a live one's is kept.

**Not covered.** The hook acts at a turn's END. A session in one very long turn still hears nothing until that turn
ends. The watcher's exit is a task notification delivered between tool calls, so a session that reads its
notifications still sees it fire.
