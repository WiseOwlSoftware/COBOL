### Observed
InheritUsageClauses is a STORAGE rewrite, not a conformance pass: it prefers the leaf's own usage over the group's with no equality test (SR2 has no site at all -- `grep '13.18.60.3 SR2' src/` is empty), and it declines every leaf outside one narrow shape without diagnosing it, which drops the group's written clause on the floor. MEASURED, all edition-invariant at --std 85/2002/2014/2023 unless noted. SR2: `01 G USAGE COMP. 05 A PIC 9(4). 05 B PIC 9(4) USAGE DISPLAY.` compiles; B is a 4-byte DISPLAY item and the group is 6 bytes where the conforming spelling gives 4 (u_sr2_measure vs u_sr2_measure_ok; e85_sr2_85/2002/2014/2023 print B=[0034]). COMP over COMP-3 gives the leaf the 3-byte packed form (u_sr2_comp_vs_comp3); a nested contradiction takes the NEAREST enclosing clause (u_sr2_nest2, LEN=3); an intermediate group that contradicts its parent compiles clean (u_sr2_nested_group). SR3 limb 2: `01 G USAGE COMP. 05 A PIC X(3).` compiles and A stays a 3-byte alphanumeric DISPLAY item -- the COMP is silently discarded (u_sr3_group_inherit, u_sr3_group_x_measure, e85_sr3g_85/2002/2014/2023). SR20 + SR13: `01 G USAGE DISPLAY. 05 A PIC N(2).` and `01 G USAGE COMP. 05 A PIC N(4).` compile at 2002+ and A is 8 bytes, byte-for-byte identical to the same leaf under a usage-less group (u_sr20_group_m prints A=8 B=8 G=8; u_sr20_group_comp; e85_sr20g_2002/2014/2023) -- SR13a's national implication is applied from the picture alone, outside its own precondition, and the group's clause has no effect and draws no diagnostic. THE SHAPE OF THE FIX is structural, not four patches: the GR1 walk should carry the clause DOWN and then let ONE per-leaf screen ask the same USAGE x PICTURE question the direct-clause path already asks in PictureAnalyzer, so a fifth rule about an inherited usage is automatic. The precedent is in the same file -- ResolveIndexItems already runs exactly such a leaf sweep for BIT (SR5) and NATIONAL (SR12), and those two rules are the only ones of the family that hold on inherited source (measured: u_sr5_group is COBOLNET0881 'USAGE BIT inherited from its group ...'). CROSS-REFERENCE: the SR-13.18.60.3-3 row cites F3 for its OTHER half (a numeric-edited picture with a DIRECTLY written binary usage); SR3's SECOND limb -- an inherited usage -- is this finding, and the SR-13.18.60.3-13 and SR-13.18.60.3-20 rows cite this finding as F4b. SWEEP: every 13.18.60.3 rule whose subject is 'an elementary data item ... a USAGE clause associated with', plus §13.18.60.4 GR1 itself (part 3 of this subject).

## Mechanism — usage-clause-p2
usage-group-inheritance-float-arm-crashes - a group item that carries a FLOATING-POINT usage keeps the ELEMENTARY float profile the entry binder synthesized for it, and the emitter then emits the group as a scalar `float`/`double` field. DataBinder.BindEntry builds `PicInfo.FloatItem(entryUsage, ...)` for every float usage before subordinates are known - correct, because a picture-less entry cannot yet be told from a group header. DataBinder.ResolveIndexItems is the pass that undoes that once the forest is complete, and it sheds a synthesized profile from a group header for exactly four shapes: `ReferenceEquals(item.Pic, PicInfo.IndexItem)`, `PicCategory.ObjectReference`, the NATIONAL/BIT `Pending` marks, and `{ Category: Numeric, Usage: BinaryChar or BinaryShort or BinaryLong or BinaryDouble }`. There is NO float arm, so `item.Pic` survives on the group, RecordStructEmitter emits a `float` field named for the group, and every reference to a subordinate becomes `<float>.<member>` - a raw Roslyn CS1061. The shape is the two-arm dispatch pattern: the same file's sibling list (InheritUsageClauses' `Usage.Binary or Usage.Packed or Usage.Comp5`) is the OTHER hand-list of the same fact, and the two disagree about which usages a group may carry. The structural fix is one derivation - the effective usage of an elementary item, given its own clause and its nearest enclosing one - consumed by the group-header shed, the leaf application AND the §13.16.3 SR8 screen, with a drift test that fails when a new `Usage` member is absent from it.

### Expected, from the standard
ISO/IEC 1989:2023 §13.18.60.4 GR1: "If the USAGE clause is specified or implied at a group level, it applies only to each elementary item in the group." So A's usage IS float-short, and §13.16.3 SR8 then applies to A: "The PICTURE clause shall not be specified for the subject of a RENAMES clause or for an item whose usage is binary-char, binary-short, binary-long, binary-double, float-short, float-long, float-extended, index, message-tag, object reference, pointer, function-pointer, or program-pointer." The source is therefore ILLEGAL and the required outcome is the named §13.16.3 SR8 diagnostic against the LEAF - the compiler already owns that message as COBOLNET1521 for the elementary case ("PICTURE may not be specified with a floating-point usage ... a floating-point item is picture-less") and need only reach it through the INHERITED usage. What is never conforming is a backend crash: §4.2.2 requires violations of the standard to be reported by the compile-time warning mechanism, and a raw CS1061 from the generated C# names neither the rule nor the offending entry. (If the owner instead reads the shape as legal - a group whose leaves are all float - the required outcome is a group of three PICTURE-less float leaves; either way the group itself is a group, never a scalar float.)

Observed by probe, then located by reading. ## Mechanism — usage-clause-p2
usage-group-inheritance-hand-listed-set - `DataBinder.InheritUsageClauses` applies a group-level USAGE to its elementary leaves only for a hand-written three-member set (`effective is Usage.Binary or Usage.Packed or Usage.Comp5`) over leaves that are already `{ Category: Numeric, IsFloat: false, Usage: Usage.Display }`. Every other usage a group may legally carry falls through silently: the leaf keeps the usage-display default it was given at entry bind, and NO diagnostic is issued. So a group-level BINARY-CHAR / BINARY-SHORT / BINARY-LONG / BINARY-DOUBLE or INDEX over a PICTURE-bearing leaf produces a DIFFERENT REPRESENTATION AND WIDTH from the one GR1 mandates, and also swallows the §13.16.3 SR8 violation that the inherited usage creates. This is the same root as the float crash (finding usage-group-inheritance-float-arm-crashes): the set of usages a group may carry is written down twice - once as InheritUsageClauses' inherited set and once as ResolveIndexItems' group-header shed list - and neither is derived from the `Usage` enum, so a member added to the enum joins neither. The fix is structural, not two more `or` arms: ONE derivation of an elementary item's effective usage (own clause, else nearest enclosing) feeding the shed, the leaf application and an SR8 screen keyed on the derived usage, plus a drift test that enumerates `Usage` and fails on any member the derivation does not classify.

### Expected, from the standard
ISO/IEC 1989:2023 §13.18.60.4 GR1: "If the USAGE clause is specified or implied at a group level, it applies only to each elementary item in the group." A, B and C therefore have usage binary-long, binary-char and index respectively - and §13.16.3 SR8 forbids a PICTURE clause "for an item whose usage is binary-char, binary-short, binary-long, binary-double, float-short, float-long, float-extended, index, message-tag, object reference, pointer, function-pointer, or program-pointer". So each of the three entries is ILLEGAL source and the required outcome is a named SR8 diagnostic naming the LEAF and the usage it inherited. Silently binding the leaf as usage-display is doubly wrong: it accepts source the standard rejects (§4.2.2 requires a violation to be reported), and where the group later crosses a byte boundary - a record area, a REDEFINES window, a CALL BY REFERENCE image - it lays out a width the standard never sanctioned for that item. The same conclusion holds if the owner decides such source should be diagnosed as a §13.18.60.3 SR2/SR3 problem instead: the one outcome the spec does not permit is silence.

### Observed
Observed by probe, then located. `InheritUsageClauses`' whole body is `Usage? effective = item.OwnUsage ?? inherited; if (item.OwnUsage is null && effective is Usage.Binary or Usage.Packed or Usage.Comp5 && item.Pic is { Category: PicCategory.Numeric, IsFloat: false, Usage: Usage.Display } pic) item.Pic = pic with { Usage = effective.Value, ... };` - the three-member set is literal, and its doc comment says so ("Scope: the binary/packed integer usages (NC107A's `01 U9 USAGE COMPUTATIONAL` with PICTURE-only children)"), i.e. the set was sized to a NIST surface rather than to the rule. `ResolveIndexItems` does shed the group header's synthesized BinaryChar..BinaryDouble and IndexItem profiles, so the group itself is correctly a group - which is exactly why the failure is silent rather than loud: the header is fixed and the leaves are forgotten. Note the picture-LESS cases work (probe p38: `01 G USAGE INDEX.` over two picture-less leaves gives 8-byte index items and a working `SET`/relation), so the defect is precisely the PICTURE-bearing leaf, which is the shape SR8 makes illegal and which the compiler therefore never diagnoses.
