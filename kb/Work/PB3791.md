# PB3791 — two readers of one range diff in `landing_check.check`

**Sites:** `scripts/orchestrator/landing_check.py#check` (arm 0), `scripts/orchestrator/inflight.py#range_names`, `scripts/orchestrator/inflight.py#changed_files`, `scripts/orchestrator/test_plan_wave.py` (the `range_names` checks)

## Measured

Arm 0 (a landing that carries a NEVER_WORK path) runs
`git("diff", "--name-only", "--no-renames", f"{base}...{rev}")` at landing_check.py:225, the same question
`plan_wave.changed_files` (documented as THE changed-file reader of the landing check) asks nine lines above for the
`mine` arm. `check()` therefore holds two readers of one range diff, which can drift apart (a pathspec batching or
rename rule fixed in one, PB3582) and spawns one extra git process per landing.

## Acceptance

- Arm 0 reads the set `changed_files` returned; `check()` asks the range once.
- `landing_check.py self_test` keeps arm 0's plant and its clean twin and pins that one reader (a test fails if a second
  `git diff --name-only` of the range returns).

## Landed (wave 20261752 group B)

**Re-probe.** Reproduced on the base: `check()` called `inflight.changed_files` for `mine` and its own
`diff --name-only --no-renames base...rev` for arm 0 (two reads of one range). **Root.** The two questions differ only in the
filter: `changed_files` drops the NEVER_WORK paths arm 0 needs to see. `inflight.range_names` is now the one question (every
path, unfiltered) and `changed_files` is `work_names(range_names(...))`; `check()` reads `range_names` once and derives both
`mine` and arm 0's leaked paths from it. **Pin.** `landing_check.py --self-test` counts the `diff --name-only` of the landing's
range through a counting git callable for a landing carrying a NEVER_WORK path and one that does not (mutation-checked: a
re-added second read fails both arms); `test_plan_wave.py` pins `range_names` against `changed_files`.
