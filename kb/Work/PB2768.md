# PB2768 — the table-witness drift test

**Owner decision, 2026-10-08 (kb/Work PB468 Q5):** one table-driven test (for example one xUnit method with an
`InlineData` row per rule-id) may serve as the witness that closes many inventory rows, provided a drift test fails the
build whenever a table row and its inventory row fall out of step in either direction.

## What closes it

1. A drift test (PB468 names it `InventoryTableCoverageDriftTests`) that, for every test method the inventory's
   `test-ref` cites as a table witness: (a) every inventory row closed on it has a table row naming that rule-id, and
   (b) every table row names a real inventory row that cites the method. Either mismatch fails with the rule-id.
2. The `test-ref` syntax for a table witness (method plus rule-id) documented where `test-ref` is specified, and
   `record_verdicts.py` accepting it only for methods the drift test covers.
3. Self-test arms for both directions. Until this lands, no table witness closes a row (PB468: question 5 "is refused
   without the two-way drift test").

## Owner direction 2026-10-08: generalize to any BATCHED witness

Owner, 2026-10-08 ~14:30 PDT: "generalizing this, it seems we could improve testing efficiency by batching related
features into a test case that tries all such features, as long as a failure can identify exactly which one(s) of the
features failed and how." So the witness this note guards is not only an xUnit table but any fixture that checks many
related rules at once:

- **Positive (run) fixtures:** one program, many checks; each check prints a labelled line (rule-id, expected, actual),
  as the NIST CCVS programs do, so a golden diff names the failing check and how it failed.
- **Negative (reject) fixtures:** one source, several INDEPENDENT violations, each expecting its own diagnostic code at
  its own line. Semantic and binding violations only; a syntax violation whose recovery can cascade or suppress the next
  diagnostic stays one per fixture.
- **Masking is NOT RUN, never PASS.** A compile error or run-time abort in one check stops the checks after it; the
  harness reports those as not run (a missing observation is not a pass), names the culprit from the diagnostic's line or
  the last check started, and re-runs the fixture's checks in isolation, a cost paid only when the fixture is red.
- **The drift test above covers every batched fixture:** each check carries the rule-id it witnesses, and every
  inventory row closed on a batched fixture has its check.

Measured on the gate (worktree wf_2ca5e648-fef-1, 2026-10-08 13:48): the Conformance leg ran 5,760 tests in 55 s wall,
1,115 CPU-seconds, median 54 ms per test (the compiled-program cache), so batching saves little gate time. The win is
AUTHORING: PB2767's rejection witnesses (up to a few hundred rows) and the remaining burn-down written as one fixture per
family of related rules cut files, agent turns and review several-fold.
