# PB460 — a determination made in a code comment is not a determination, and a Claimed module with a missing element

**Rows:** `GR-14.9.39.4-17`, `GR-14.9.39.4-20`, `GR-14.9.39.4-30`. From the b2 adjudicator `set-statement-p4`.
**Re-measured on the HEAD tree and the HEAD `cobol.exe` (base 89044aa0)**; both halves reproduce unchanged.
⛔ This note does NOT edit `docs/CONFORMANCE.md` — it names the rows the fixer must add.

## THE MECHANISM — part 1: required A.1 rows the user documentation does not carry

`docs/CONFORMANCE.md` §7 is this project's Annex A.1 implementor-defined register. Measured on HEAD:

```
$ grep -c '^| 128 |' docs/CONFORMANCE.md          -> 0
$ grep -c '^| 216 |' docs/CONFORMANCE.md          -> 0
$ grep -cE '^\| 17[456] \|' docs/CONFORMANCE.md   -> 0
$ grep -c 'EC-RANGE-PTR' docs/CONFORMANCE.md      -> 0
```

Five rows §14.9.39 turns on are absent, and every one of them carries the standard's strongest obligation:

| A.1 | subject | which §14.9.39.4 rule needs it |
| --- | --- | --- |
| 128 | OCCURS clause (range of values allowed in the index) | GR2 a) 1. b, GR2 a) 3. b, GR4 a) — "the limit specified in General rule 2 of 13.18.38" |
| 174 | SET statement (effect of SET on function whose address is being stored in a function-pointer) | GR15 (Format 8) |
| 175 | SET statement (effect of SET on program whose address is being stored in a program-pointer) | GR17 (Format 9) |
| 176 | the NaN payload value | GR34/GR35 (Format 15) |
| 216 | USAGE POINTER clause (alignment, size, representation, and range of values) | GR20's EC-RANGE-PTR arm |

**The pattern, not the five rows, is the finding.** §4.2.16 conformance is claimed against the USER
DOCUMENTATION, so an undocumented required item is a conformance gap even where the behaviour is beyond
reproach — and the 216 case shows why that matters. A real, considered determination EXISTS for it, and it is a
good answer for a managed cell model:

```
src/Cobol.Net.Runtime/Control/CobolPtr.cs:68-72
    The implementor data-pointer range is UNBOUNDED (the recorded implementor choice):
    EC-RANGE-PTR is never raised at SET time — an out-of-cell address surfaces at the next
    dereference as EC-BOUND-PTR.
```

It lives in a C# doc-comment, so it has no reader outside that file. A user reading the conformance document
cannot learn why a condition the standard names is never raised. `ExceptionCatalog.cs:166` carries the
EC-RANGE-PTR row with no raise site — the observable face of a determination nothing states.

The behaviours themselves are NOT charged here: GR17's is right (`SetEmitter.EmitSetProgramPointer` performs a
handle copy and nothing else, which is a legitimate implementor answer), and GR20's movement half is right with
a defensible range choice. What is charged is that three verdicts in this clause cannot reach CONFORMS for a
reason no further probing could remove.

## THE MECHANISM — part 2: A.4.4 marked **Claimed** with one of its own elements missing

Annex A.4.4 (*Dynamic capacity tables*) item 1 names four exception conditions. Three have live raise sites:
EC-BOUND-OVERFLOW (`CobolDynTable.RefReceiving`), EC-BOUND-TABLE-LIMIT and EC-FLOW-SEARCH (`GrowTo` /
`SetCapacity`). **EC-BOUND-SET has none.** Measured on HEAD:

```
$ grep -rn 'EC-BOUND-SET' src/ --include=*.cs
src/Cobol.Net.Runtime/Exceptions/ExceptionCatalog.cs:67   (a comment)
src/Cobol.Net.Runtime/Exceptions/ExceptionCatalog.cs:81   L3("EC-BOUND-SET", EcFatality.Nonfatal)
src/Cobol.Net.Runtime/Values/Tables/CobolDynTable.cs:94   (a comment conceding it)
$ grep -c 'EC-BOUND-SET' docs/CONFORMANCE.md              -> 0
docs/CONFORMANCE.md:855   | A.4.4 | Dynamic capacity tables | **Claimed** | … EC-BOUND-OVERFLOW raise live |
```

The code's own defence is the defect's shape, not its refutation: `CobolDynTable.cs:94` argues the condition
"stays a nonfatal staged follow-on — being nonfatal, it produces identical observable results with checking OFF
(the default)". Nonfatal conditions are precisely the ones a program deliberately TURNs ON and takes in a USE
declarative, so "identical with checking off" describes exactly the population that cannot observe it and says
nothing about the population the feature exists for.

`docs/CONFORMANCE.md` §5's own preamble defines **Partial** as the state in which "the supported / not-supported
split is itemized (the §4.2.7 second-sentence requirement)". Recording A.4.4 as **Claimed** makes the one
document that would have warned a user say there is no hole.

The green-test trap is visible too: `conformance:2014/dyn_capacity_set` drives TO / UP BY / DOWN BY / the
minimum clamp and passes, and its `TO 10` expected maximum is never exceeded — the suite's green is evidence
about the arms it drives and silent about this one (`feedback_green_gates_arent_evidence`).

## EXPECTED vs OBSERVED — re-run on HEAD

I re-wrote both probes from the finding's listings into `scratchpad/probe-g8-set-b/p4/` (that slug's sources
were not in the b2 probe tree), and I **changed the GR30 probe's amount from a literal to an identifier** —
the finding used `SET CAP TO 9.` against `TO 6`, which is exactly the §14.9.39.3 SR30 violation PB458 charges,
so the original probe was illegal source and could not carry a GR30 verdict. With an identifier amount the
program is legal and GR30 is the only rule in play.

```
$ cobol.exe p4gr30expr.cob --std 2014 --run
   05 E PIC 9(3) OCCURS DYNAMIC CAPACITY IN CAP FROM 2 TO 6.   01 A PIC 9(4) VALUE 9.
   >>TURN EC-BOUND-SET CHECKING ON  /  SET CAP TO 4.  SET CAP TO A.
TO4=[   4]
TOA=[   9]
STATUS=[                               ]

$ cobol.exe p4gr20range.cob --std 2002 --run
   01 BUF PIC X(4).  01 P USAGE POINTER.
   >>TURN EC-RANGE-PTR CHECKING ON  /  SET P TO ADDRESS OF BUF.  SET P UP BY 1000000.
AFTER-RANGE STATUS=[                               ]
```

**Expected.** For GR30: the capacity change to 9 is CORRECT — EC-BOUND-SET is Nonfatal (Table 13, and
`ExceptionCatalog.cs:81` agrees), and GR30's "capacity unchanged" belongs to the EC-BOUND-TABLE-LIMIT arm only —
but the new capacity exceeds the expected maximum 6, so the condition shall be set to exist:
`FUNCTION EXCEPTION-STATUS` returns `EC-BOUND-SET` padded, not 31 blanks, and a `USE AFTER EXCEPTION CONDITION
EC-BOUND-SET` declarative runs. Only STATUS is wrong.

For GR20: `AFTER-RANGE` with no condition is CONSISTENT with the unbounded-range determination — the finding is
not that the behaviour is wrong but that nothing outside `CobolPtr.cs` states the range that makes it right.

## THE CODE SITES AND THE SHAPE OF THE REPAIR

| site | what to do |
| --- | --- |
| `docs/CONFORMANCE.md` §7 (the A.1 register) | add rows 128, 174, 175, 176, 216. For 216: state alignment, size, representation and RANGE OF VALUES, that the range is UNBOUNDED, and therefore that GR20's "outside the range of values allowed by the implementor" antecedent is unsatisfiable and EC-RANGE-PTR is never raised at SET time — an out-of-cell address surfacing at the next dereference (§13.18.5.4 GR4 sets EC-BOUND-PTR there). For 175: the SET has NO effect on the addressed program — neither loaded nor initialised nor placed in its initial state. For 128: the index's permitted range, which is also what PB459's range check must test against. |
| `docs/CONFORMANCE.md` §5 row A.4.4 (`:855`) | either land the EC-BOUND-SET raise (preferred — it is one comparison) or downgrade to **Partial** with the split itemized, per §4.2.7's second sentence |
| `src/Cobol.Net.Runtime/Values/Tables/CobolDynTable.cs:122-138` `SetCapacity` | the missing raise. `_expected` is ALREADY carried on the table and already consulted for the implicit-growth twin (EC-BOUND-OVERFLOW, `:74-77`); the datum, the checking flag and the nonfatal-raise helper all exist — this is a missing call, not a missing mechanism |
| `src/Cobol.Net.Runtime/Control/CobolPtr.cs:68-72` | the determination moves (or is mirrored) into the register; leave the doc-comment as a pointer |

⛔ **The durable repair is not five hand-written rows** (CLAUDE.md rule 5). Annex A.1 marks each item "shall be
documented" or "does not have to be documented", and the compiler already knows which clauses it implements. A
CI check that reads A.1's must-document items out of `specs/ISO_COBOL.md` and fails when §7 lacks a row for one
whose subject clause is implemented is the shape that makes the NEXT missing row automatic — instead of waiting
for the next adjudication to find it, which is how these five surfaced.
