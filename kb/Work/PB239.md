# PB239

## Landed (2026-09-22, wave 52)

The address-identifier is now what §8.4.3.1.2 says it is — identifier FORMAT 9 — and not a phrase of SET.
ONE `addressIdentifier` rule (`programAddressIdentifier | dataAddressIdentifier`) is an alternative of every CALL
operand slot identifier-2/identifier-4 occupies (bare, BY REFERENCE, BY CONTENT, Format-2 BY VALUE); the SET
Format-7 sender spells its ADDRESS phrase through the same `dataAddressIdentifier` rule, so the data pass's
storage forcing walks those NODES (every surface is forced by construction) and each arm binds through the ONE
operand binder its SET twin uses (`PtrBinder.BindDataAddress`, the extracted `SetBinder.BindProgramAddressOperand`).
The argument crosses as a detached pointer cell in every mode (`BoundCallArg.DataAddress` / `ProgramAddress` →
`CallEmitter.ArgCarrierText`) — SR4's sending operand, Annex D.6.5.6.4's "never updated even when passed by
reference"; a Format-2 pairing meets §14.8.2.3.2's class-pointer paragraph (`CallBinder.AddressConformanceReason`);
an unlocatable program arm is §8.4.3.13.4 GR4's NULL, raised as EC-PROGRAM-NOT-FOUND while the argument array is
built when the CALL's checking enables it (§14.9.4.4 GR3a — `ProgramRegistry.EntryOfArgument`). ⚠ DETERMINATION:
§14.9.4.3 SR10's Format-1 BY REFERENCE class-pointer ban does not reach an address-identifier (SR3–SR5 + Annex
D.6.5.6.4). Gates: `address-identifier-2002` (the operand) and — the FMT row's re-measured residue — `call-as-phrase-2002`
(an 85 compile accepted `CALL "X" AS NESTED` silently). Evidence: conformance:2002/pb239_call_address_identifier
(both arms of SR4, incl. the BY CONTENT data item the note said only a legacy bake covered — N=005),
conformance:2014/pb239_call_program_address_not_found, negatives pb239-call-address-identifier-at-85,
pb239-call-address-formal-category, pb239-call-as-phrase-at-85.

**Rows:** `SR-14.9.4.3-3`, `SR-14.9.4.3-4`, `FMT-14.9.4.2`

`ADDRESS OF` is a SET-only production, so the address-identifier argument §14.9.4.3 SR3/SR4 name by that word is a parse error — and the only test of BY CONTENT's sending semantics is a legacy bake.

Rows: SR-14.9.4.3-3 (sentence 1's section rule and sentence 2's object-data ban, both over 'identifier-2 or an address-identifier'), SR-14.9.4.3-4 (a BY CONTENT identifier-2 — or an address-identifier — is a SENDING operand). ONE missing grammar alternative, two rules whose second admitted operand kind can never be written.

MECHANISM. `callArgument : callByReference | callByValue | callByContent`, and each of those three bottoms out at `dataReference`, `literal` or `arithmeticExpression`. There is no address-identifier alternative anywhere in the CALL argument grammar; ADDRESS OF is parsed only inside setAddressStatement. So `CALL 'S' USING BY CONTENT ADDRESS OF R` — which SR3 and SR4 both name in so many words — is a parse error, and the classification arm those rules define has never been exercised on the shape it exists for.

WHAT IS ALREADY RIGHT ON BOTH ROWS. SR3 sentence 2 (BY REFERENCE, specified OR implied — i.e. the RESOLVED mode after GR5/GR9 — shall not carry factory/instance object data) is enforced through DataBinder.OoIsObjectData, which had exactly two consumers, both INVOKE, until PB132 gave it its CALL consumer; conformance:negative/pb132-call-byref-object-data pins it. SR3 sentence 1's section rule holds BY CONSTRUCTION for everything resolvable (report groups never enter the storage forest; screen entries are names only, and a screen-name operand now draws the CITED COBOLNET1677 at bind instead of a staged runtime loud). SR4's sending-only semantics ARE realized for a BY CONTENT identifier-2: CallEmitter.ArgText returns RefCarrier(p) — an OverField accessor over the caller's storage — only for `a.Mode == CobolPassMode.Reference`, and every other mode falls to `ManagedPointer<...>.Cell(...)`, a detached snapshot whose doc-comment says 'BY CONTENT/BY VALUE snapshot the value into a cell AT CALL INITIATION', so the callee's stores reach the cell and never the caller.

THE SECOND, EVIDENCE HALF (the process_only flag). The only test of that semantics is tests/Cobol.Net.Tests.Conformance/CallDifferentialTests.cs's CallByContent_CalleeMutationNotVisibleToCaller, which literally begins `=> AssertSameAsLegacy(` — a legacy differential, non-qualifying as closing evidence under ground rule 3 — and no tests/conformance golden mutates a BY CONTENT formal at all. So even the arm that IS implemented is pinned only against the frozen oracle.

ONE NOTE ON SCOPE, from SR-14.9.4.3-4's own REFUTED half: the compiler's choice between SR4 and SR5 for a Format-2 bare argument used to be decided by the wrong rule (GR5's Format-1 transitivity applied to Format 2). PB131 landed GR9's formal-mode derivation, so that half is discharged; what survives on this row is the address-identifier gap and the evidence gap above.

WHAT WOULD CLOSE IT: an address-identifier alternative on callArgument (with the ADDRESS OF production factored out of setAddressStatement so there is one spelling, not two), the SR3/SR4 classification for it, plus a spec-derived golden in the conformance:2023/pb53_by_content_move_rules shape — callee ADDs to the formal, caller DISPLAYs the unchanged argument, expectation derived from §14.2.3 GR9 — and one passing ADDRESS OF a based record BY CONTENT.

SPEC REFS as carried by the rows: §14.9.4.3 SR3, SR4 (cite.py OK); §14.6.7 ('An operand is a sending operand if its contents prior to the execution of a statement may be used by the execution of the statement'); §14.2.3 GR9; §14.9.4.4 GR5/GR9 for the resolved mode.
