# PB5323 - the roster drift test does not prove that Rebind has an arm for every kind rostered AccessPath

**Sites:** `tests/WiseOwl.Cobol.Tests.Unit/OdoDependenceRosterDriftTests.cs#EveryRoleMatchesItsKind` and
`src/WiseOwl.Cobol.Compiler/Binding/Model/OdoDependence.cs#Rebind`. Both files arrive on main with pull request #1513
(branch `worktree-wf_c902d12a-c75-2`, head 26af9e6388); the line numbers below are that head's.

## What the reviewer said

Round 2 closed CLEAN with one low lead, R2-1 (not blocking):

> The roster drift test proves every Place kind has a row and that the row fits the kind (decorator or not), but not that
> Rebind has an arm for the row: Role.AccessPath is accepted for any non-decorator, while Rebind takes only MemberPlace,
> DynTablePlace and RedefViewPlace under that role and throws for any other (OdoDependence.cs Rebind fallthrough). The
> failure is loud (an InvalidOperationException in the binder), not a wrong answer.

## Checked against the branch (2026-11-11, `git show worktree-wf_c902d12a-c75-2:<file>`)

- `OdoDependence.cs` lines 71 to 73 roster three kinds as `Role.AccessPath`: `MemberPlace`, `DynTablePlace`,
  `RedefViewPlace`. `Rebind` (line 98) has one arm for each of the three (lines 102 to 104), each a hand-written
  `with { Path = RebindPath(...) }` (`RedefViewPlace` rewrites `Backing` and `Cell`), and a fallthrough at line 110 that
  throws `InvalidOperationException("OdoDependence: <kind> is rostered as <role> but no arm of Rebind takes it")`.
- `EveryRoleMatchesItsKind` decides a row with
  `OdoDependence.Role.AccessPath or OdoDependence.Role.NoObject => !decorator`. Any kind that does not derive from
  `PlaceDecorator` fits `AccessPath`.

So the lead holds. A fourth leaf kind that carries an `AccessPath` and is rostered `Role.AccessPath` passes
`EveryPlaceKindHasARole` and `EveryRoleMatchesItsKind`, and the compiler stops at the first format 3 INSPECT over it, or
at a reference modifier over it whose position has pre-operations. The failure is loud and names the kind, so no program
gets a wrong answer; the cost is a compiler abort the drift test was written to prevent.

## The fix

CLAUDE.md rule 5 asks for the shape that makes the next case automatic. The reviewer named two shapes:

1. The kinds rostered `AccessPath` share one interface that exposes their paths (a rewrite over the set of paths), so
   `Rebind` has ONE arm for the role and a new kind needs no arm. `EveryRoleMatchesItsKind` then requires that a kind is
   rostered `AccessPath` exactly when it implements the interface.
2. Keep the three arms and make the test require that the kinds rostered `AccessPath` are exactly the set `Rebind` takes.
   This is a second hand-kept list beside the roster.

Shape 1 is the one to build: it removes the arms instead of listing them twice. The implementer checks whether
`RedefViewPlace`'s two paths (`Backing`, and `Cell` when present) fit one interface member before starting, and records
the outcome in the design document that describes `OdoDependence`.
