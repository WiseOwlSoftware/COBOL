# PB3188 — the wave planner never sees the files a finisher's branch changed

> ⚙ **flags:** process-only

Filed by the clerk, 2026-10-15, from the wave-1085 unit's lead (id allocated by that unit). Harm: wasted finisher work and a landing conflict that needs a third finisher; no wrong answer.

**Observed** (wave 1085 plan, 2026-10-15). Group C (finisher for PB3165, branch `worktree-wf_5579bfb3-423-17`) and group D (finisher for PB3153, branch `worktree-wf_15ec6338-3a0-19`) were planned with no `after:` between them. Their lead notes' computed file sets differ (C: `Binding/ReferenceResolver.cs`, D: `Binding/DataBinder.cs`), but their BRANCH diffs overlap: `git diff --name-only origin/main...<branch> -- src` lists `Binding/DataBinder.cs`, `Binding/DataBinder.Oo.cs` and `Binding/ReferenceResolver.cs` on both. D's branch (commit 47cf8d500) also fixes PB3165's own defect (`ReferenceResolver.cs#CapacityRegisterFor`) in a second design, which its review finding R1-1 records. Run in parallel, the two finishers would each keep a design, and the second landing would conflict and need a third finisher.

**Mechanism.** `scripts/orchestrator/plan_wave.py` builds the finisher groups at line ~795 (`groups.append(Group("finisher", chunk, c["file"], list(c.get("files", [])), ...`) from the cluster's NOTE file set only; the collision and successor logic (lines ~840-879, `g.after = prev.letter`) never sees the files the branch the finisher must merge actually changed. Line numbers as of the 2026-10-15 unit; verify before editing.

**Hand repair this time.** The wave-1085 unit set D `after: 'C'` in `groups.json` and `wf-args-w1085.json` (planner originals kept as `*.planner`), prefixed D's `pred` with the one-design instruction, and re-rendered the specs (`make_dispatch_specs.py`, practices GREEN). Script: `E:/COBOL-coord/scratch/w1085-sequence-cd.py`.

**Second witness, same mechanism** (the planner sees a branch only through its LEAD note), wave 1085 group B. The planner planned a FINISH-FIRST finisher for PB3127 whose spec said its ABSENT predecessor worktree (28e-2) meant "its landed part is already on main". It was not on main: the whole fix is on `worktree-wf_c0ed6078-78e-8` (lead PB3101, WAITING TO LAND, reviewed CLEAN), which flips PB3127 to landed. The "awaiting landing (excluded)" list held 78e-8 under PB3101 only, so PB3127 (`worktree-wf_d6f41ebf-faa-2`) was dispatched again and came back DISCHARGED (about 20 turns, no commits; report `w1085b-PB3127-report.md`). Site: `plan_wave.py` `finisher_pred` (line ~655, ABSENT means landed) and the awaiting-landing exclusion (keyed on the lead).

**Fix direction** (not designed here). A finisher group's file set is its note files UNION the `src/` files of `origin/main...<branch it merges>`, so the existing one-group-per-file rule makes the later finisher a successor automatically. Add a planner self-test with two finisher branches on one file. Also consider: a branch whose commits name another open note (the reviewer's R1-1 shape) puts that note's group in the same chain, and the awaiting-landing exclusion keys on every note a waiting branch closes, not on its lead alone.
