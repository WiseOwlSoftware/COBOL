# PB328 — the same read-only file answers 37 for sequential and 00 for indexed

**Rows:** `GR-14.9.27.4-16`, `GR-9.1.13.6-6`. Found by the batch-1 refuter; the adjudication had verified the
rule's second half and tested the first on ONE organization.

## The rule

> §14.9.27.4 GR16: If the I-O phrase is specified, the file shall support the input and output statements that
> are permitted for the organization of that file when opened in the I-O mode. If the file does not support
> those statements, the I-O status value for file-name-1 is set to '37' and the execution of the OPEN statement
> is unsuccessful.

`--check 14.9.27.4 "If the I-O phrase is specified, the file shall support the input and output statements that
are permitted for the organization of that file when opened in the I-O mode"` → **OK**, and §9.1.13.6 6) a) 2.
gives '37' the same meaning from the status side.

## What the compiler did

> ⚠ This section was written before landing train 10. **Two of its claims did not hold on the tree the fix was
> built on** and are corrected here rather than deleted, because the mechanism they describe was right and only
> its coordinates had moved. (1) The line numbers are stale: PB323 rewrote `FileConnector.Open`. (2) "The ONLY
> producer of '37' on OPEN" was already false — PB323 had added `HostFile.Probe`'s `FilePresence.Unauthorized`
> short-circuit, a *second* producer, for §14.9.27.4 GR3. That producer answers a different question
> (observability), which is exactly why it never covered this one: a read-only file probes **Present**.

The only producer of '37' for a WRITE-INCAPABLE file on OPEN was `catch (UnauthorizedAccessException)` wrapped
around `OpenCore` in `FileConnector.Open`. That catch fires for SEQUENTIAL because `SequentialConnector.OpenCore`
opens a WRITE-capable stream in the I-O arm. It **never fires for RELATIVE or INDEXED**, whose I-O arms only call
`Attach()` — a READ of the store — so writability was never probed at OPEN.

On the SAME read-only file the compiler answers '37' for sequential and '00' for indexed and relative. The
success is then believed downstream: `READ NEXT` is '00', a REWRITE of that record is '00', and the loss
surfaces only as '30' at CLOSE on a file that is byte-for-byte unchanged.

This is a **detection-site** defect, not a platform limit: `OPEN OUTPUT` on the same read-only keyed files
correctly answers '37', because that arm eagerly calls `RecordFraming.WriteStore`.

## Sweep (CLAUDE.md rule 4)

The identical omission makes `OPEN EXTEND` on a read-only indexed or relative file answer '00' where §9.1.13.6
6) a) 1. requires '37'. That belongs to §14.9.27.4's EXTEND/OUTPUT rule, outside this row, and is fixed here.

**Code sites:** `FileConnector.cs#Open` · `SequentialConnector.cs#OpenCore` · `RelativeConnector.cs#OpenCore` ·
`IndexedConnector.cs#OpenCore`.

## The fix shape

The writability probe belongs to the OPEN CONTRACT, not to whichever arm happens to touch a stream: one
`RequireWritable(mode)` step every `OpenCore` runs for the I-O, OUTPUT and EXTEND modes, so an organization
added later inherits it. A drift test that opens a read-only file in all three modes across all three
organizations and asserts '37' nine times keeps it true.

## Landed

Landed as designed, with the probe hoisted one level HIGHER than the note proposed. The note's
`RequireWritable(mode)` would still have been a step *every `OpenCore` runs*, i.e. three call sites to keep in
agreement; the question is asked instead in `FileConnector.Open` itself, once, between GR10's '39' and
`OpenCore` — so there is nothing for a fourth organization to inherit incorrectly, and `HostFileProbeDriftTests`
pins the call count at one and bans the helper outside `FileConnector`.

- **`HostFile.PermitsWrite`** (`IO/FileSupport.cs`) is the one place the runtime asks the host whether a present
  file may be written: a real write open (`FileMode.Open` + `FileAccess.Write` + `FileShare.ReadWrite`, nothing
  written), because a read-only attribute, a Unix mode bit and a deny-write ACE are three mechanisms with one
  consequence and only the host can rank them. Only `UnauthorizedAccessException` is an answer; every other
  `IOException` propagates to the single §9.1.13.6 item 1 '30' mapping, exactly as `HostFile.Probe`'s do.
- **`FileConnector.Open`** calls it for I-O, EXTEND and OUTPUT on a `Present` file. INPUT is excluded and the
  exclusion is load-bearing, not an optimization — see below.
- **Reproduced first**, on this worktree's own build at `17c11fd4`, with three files the compiler created and a
  host read-only attribute: `OPEN I-O` answered SEQ '37', REL '00', IDX '00'; the keyed successes were believed
  (`READ` '00', `REWRITE` '00') and CLOSE reported '30' on a file whose MD5 had not changed. `OPEN EXTEND` had
  the same split; `OPEN OUTPUT` was already 37/37/37. **After: nine cells, 37 everywhere.**
- **Over-fire measured, not assumed.** The same read-only files still `OPEN INPUT` '00' and read their record on
  all three organizations; a writable file still opens I-O '00' and rewrites on all three; GR25 holds through
  the probe (content MD5 *and* last-write time identical after the refused open).
- **The INPUT exclusion's premise was measured too.** The code comment justifies excluding INPUT by claiming
  §9.1.13.6 item 6 a) 3. is already answered by the organizations' eager reads. That claim was unmeasured, so it
  was measured: with `icacls /deny :(R)` on the data files themselves (the directory still listable, so
  `HostFile.Probe` answers **Present** and GR3 is not the producer), `OPEN INPUT` answers '37' on sequential,
  relative and indexed. `OpenInput_PresentAndObservableButNotReadable_Is37` now pins it. That measurement is
  what let `GR-9.1.13.6-6` — all four sub-cases of the '37' status — be adjudicated CONFORMS alongside GR16.
- **Both halves of GR16 are covered, not just the defective one.** GR16 requires the file to support the input
  **and** output statements the I-O mode permits, and Table 20 lists READ under the I-O column beside REWRITE —
  so a file this process may WRITE but not READ is '37' on OPEN I-O too. Measured with `icacls /deny :(RD)`
  (read *data* only, so a raw write open still succeeds and `PermitsWrite` accepts the file): '37' on all three
  organizations, produced by the eager read rather than by the new probe.
  `OpenIo_PresentAndWritableButNotReadable_Is37` asserts the write-probe premise first, so the two halves can
  never be confused for each other. (A blanket `(R)` deny would have collapsed the complement — it takes rights
  a write open also needs — which is the trap this test's helper documents.)
- **The guard was proved to fail.** With the check disabled, 7 of the class's assertions go red — the four keyed
  I-O/EXTEND cells, the two keyed OPTIONAL cells and the GR25 inertness assertion — while the three sequential
  cells and the three OUTPUT cells stay green. That is the defect's two-arm fingerprint, reproduced by the test.
- The drift guard was renamed `FileExistenceProbeDriftTests` → **`HostFileProbeDriftTests`**: it now guards two
  questions (presence and write capability), and a class named for only one of them would have rotted.
- No conformance golden: the corpus runner compiles a `.cob` and compares its output, with nowhere to express
  "and first make this file read-only". The witnesses are unit tests that establish the precondition for real
  and verify it with a raw stream open rather than with the subject under test.

Docs updated in the same change set: `docs/CONFORMANCE.md` (a new '37' write-capability bullet beside the
existing authority one) and `docs/rearchitecture/DESIGN-runtime-library.md` (the OPEN contract now documents two
host questions, not one). No diagnostic codes were needed — this is a run-time I-O status, not a compile-time
diagnostic.
