# PB328 — the same read-only file answers 37 for sequential and 00 for indexed

**Rows:** `GR-14.9.27.4-16`. Found by the batch-1 refuter; the adjudication had verified the rule's second half
and tested the first on ONE organization.

## The rule

> §14.9.27.4 GR16: If the I-O phrase is specified, the file shall support the input and output statements that
> are permitted for the organization of that file when opened in the I-O mode. If the file does not support
> those statements, the I-O status value for file-name-1 is set to '37' and the execution of the OPEN statement
> is unsuccessful.

`--check 14.9.27.4 "If the I-O phrase is specified, the file shall support the input and output statements that
are permitted for the organization of that file when opened in the I-O mode"` → **OK**, and §9.1.13.6 6) a) 2.
gives '37' the same meaning from the status side.

## What the compiler does

The compiler's ONLY producer of '37' on OPEN is `catch (UnauthorizedAccessException)` wrapped around `OpenCore`
at `FileConnector.cs:181-183`. That catch fires for SEQUENTIAL because `SequentialConnector.OpenCore` opens a
WRITE-capable stream in the I-O arm (`SequentialConnector.cs:263`). It **never fires for RELATIVE or INDEXED**,
whose I-O arms only call `Attach()` — a READ of the store (`RelativeConnector.cs:127`, `IndexedConnector.cs:158`)
— so writability is never probed at OPEN.

On the SAME read-only file the compiler answers '37' for sequential and '00' for indexed and relative. The
success is then believed downstream: `READ NEXT` is '00', a REWRITE of that record is '00', and the loss
surfaces only as '30' at CLOSE on a file that is byte-for-byte unchanged.

This is a **detection-site** defect, not a platform limit: `OPEN OUTPUT` on the same read-only keyed files
correctly answers '37', because that arm eagerly calls `RecordFraming.WriteStore`.

## Sweep (CLAUDE.md rule 4)

The identical omission makes `OPEN EXTEND` on a read-only indexed or relative file answer '00' where §9.1.13.6
6) a) 1. requires '37'. That belongs to §14.9.27.4's EXTEND/OUTPUT rule, outside this row, and is fixed here.

**Code sites:** `FileConnector.cs#Open` (lines 181-183) · `SequentialConnector.cs#OpenCore` (line 263) ·
`RelativeConnector.cs#OpenCore` (line 127) · `IndexedConnector.cs#OpenCore` (line 158).

## The fix shape

The writability probe belongs to the OPEN CONTRACT, not to whichever arm happens to touch a stream: one
`RequireWritable(mode)` step every `OpenCore` runs for the I-O, OUTPUT and EXTEND modes, so an organization
added later inherits it. A drift test that opens a read-only file in all three modes across all three
organizations and asserts '37' nine times keeps it true.
