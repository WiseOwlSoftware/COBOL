# PB364 — one key column carrying two rule scopes

**Rows:** `SR-14.9.49.3-8`, `SR-14.9.49.3-14`. Reported by use-statement p1 and by the batch-1 refuter as two
mechanisms, one method apart, with the same cause.

## Part 1 — SR14, and the green test that certifies the over-rejection

`<lane3 scratch>/out-b1/probe/f1rules/SR14BARE.cob` — two declarative sections, each `USE AFTER EC EC-SIZE.` with
**no FILE phrase**. Compile at `--std 2023`:
`error COBOLNET0716: declarative section 'D2': the exception-name/file pair 'EC-SIZE' is already specified in
another USE statement of this procedure division (ISO 14.9.49.3 SR14)`. The genuinely-prohibited form still works
(`SR14DUP.cob`, two sections each `USE AFTER EC EC-I-O-AT-END FILE F1.`, correctly draws COBOLNET0716), so only
the bare arm is wrong.

> SR14: The same pair of exception-name-2 and file-name-2 shall not be specified in more than one USE statement
> within the same procedure division

`--check 14.9.49.3` → **OK**. The rule is scoped to PAIRS, and §14.9.49.2's Format 3 figure puts exception-name-2
only in the `exception-name-2 { FILE file-name-2 } ...` alternative; **a bare name is exception-name-1.**
§14.9.49.4 GR3 confirms the split (*file-name-2 is specified and exception-name-2 ...* in GR3 c/d against
*file-name-2 is not specified and exception-name-1 ...* in GR3 e/f/g) and supplies the SEMANTICS for duplicates
instead of forbidding them:

> The first declarative that satisfies the selection criteria is executed and no other declaratives are executed.

`--check 14.9.49.4` → **OK**. The standard also shows it knows how to forbid the unpaired case when it wants to —
SR7 and SR8 do exactly that for Format 1, SR9 for Format 2 — and wrote no such sentence for exception-name-1.

`DeclBindUseF3` calls the same local `AddPair` for BOTH alternatives — `if (fileNames.Length == 0) { AddPair(
info.Name, null); continue; }` — and `AddPair` keys `ctx.EcState.DeclEcPairs` on
`ec + "|" + (file?.CobolName ?? "")`, so the bare entry occupies the key `EC-SIZE|` and a second bare entry
collides. **One scalar key column carrying two distinct rule scopes.**

⛔ **THE TEST HOLDS IT OPEN.** `tests/Cobol.Net.Tests.Conformance/ExceptionConditionConformanceTests.cs#UseF3_DuplicatePairAcrossSections_Diagnosed`
(line 925) asserts COBOLNET0716 for a program with two BARE `USE AFTER EXCEPTION CONDITION EC-USER-D.`
declaratives and no FILE anywhere, under a comment citing SR14 — so a passing, spec-derived-LOOKING conformance
test currently certifies the over-rejection, which is why the row has no valid covering test. It must be
**RE-DERIVED from SR14's text** — given a FILE-scoped pair — never rebaselined; and the missing POSITIVE test (two
bare same-named declaratives compile, and the FIRST is selected) is GR3's own contract.

## Part 2 — SR8, enforced per OPERAND inside one statement

> SR8 forbids the file-name appearing in more than one USE AFTER EXCEPTION **statement**.

`_declScopedFiles.Add(fname)` sits **inside the per-operand loop of a single USE statement**
(`ProcedureTableBuilder.cs:461-479`), so a Format-1 USE that names the same file twice in ONE statement is
rejected: `RU8SAME` — `USE AFTER STANDARD ERROR PROCEDURE ON F1 F1.` — draws COBOLNET0897 *file 'F1' already has
a USE procedure in this source element*, and `RU8SAME3` shows it also ABORTS the rest of the operand list. **One
statement is not more than one statement.** The Format-1 figure writes `{ file-name-1 } ...` with an ellipsis and
nothing restricts the repetition; no general rule is made ambiguous by it — GR6 a) associates the one procedure
with the file whether the name is written once or twice. A hard error on source the standard permits, at all four
editions (measured: `R85SR8S`, `R02SR8S`, `R14SR8S` and the 2023 default all reproduce it).

**The scope half of SR8 is correct and was re-derived.** The adjudication rested *no leak across divisions* on a
probe (`nest.cob`) that names the outer file F1 and the inner file G1 — a shared `_declScopedFiles` could never
have collided there, so the probe was incapable of detecting the defect it was cited for. The probes that can —
`RU8NEST` (an outer program and its CONTAINED program each with an FD named F1 and a `USE ... ON F1.`) and
`RU8TWOP` (two NON-nested top-level programs) — both compile clean, so the scope really is per procedure
division. That half survives.

## The fix shape

Both screens register at the wrong granularity. Restrict the SR14 key to entries that actually carry a file
(leave the bare arm unregistered), and hoist BOTH registrations OUT of their per-operand loops to the STATEMENT
level, which is the unit both rules name. Then re-derive the pinning test from the rule text. The same
per-operand shape is one method away in `DeclBindUseF3` — `RU14SAME` (`USE AFTER EC EC-I-O-AT-END FILE F1 FILE
F1.`) draws COBOLNET0716 whose own text says *another USE statement* — so the two arms are fixed together or the
sweep is half done.

**Code sites:** `ProcedureTableBuilder.cs#DeclBindUseF3` (lines ~514-543), lines 461-479 ·
`EcBindState.cs#DeclEcPairs` · `ExceptionConditionConformanceTests.cs#UseF3_DuplicatePairAcrossSections_Diagnosed`.

## Landed — 2026-09-05

Both screens now run through ONE `UseOperandRegister<TKey>` in `ProcedureTableBuilder`, because
§14.9.49.3 SR7, SR8, SR9 and SR14 are four instances of a single sentence — *"the same X shall not be … in more
than one USE statement within the same procedure division"* (SR7 spells the same boundary as *"only once in the
declaratives portion of a given procedure division"*). The register stages the operands of the statement being
bound apart from the division's accumulated keys and folds them in at `DeclEndUseStatement`, called from the ONE
place a USE statement is bound (`DeclCollectSection`). Three verdicts, not two: `First` binds, `Repeated` (the
same operand again inside THIS statement) binds nothing and says nothing, `Duplicate` (an earlier statement of
this division) is the diagnostic. `EcBindState.DeclEcPairs` is deleted — the SR14 set lived in a second home for
no reason and is now beside its three siblings.

The `Repeated` arm must bind the operand ONCE rather than twice, and that is not tidiness: the F1 declarative
dispatch the emitter generates is `switch (__f) { case <fileKey>: … }` (`DispatchEmitter` / `EcEmitter`
`EmitUseTiers`), so a duplicated `FileModel` in `BoundDeclarative.Files` would emit two identical case labels and
Roslyn would reject the generated C#. Loosening SR8 without the dedupe would have traded a wrong rejection for a
compiler crash.

**SR14's key is the PAIR.** A bare exception-name is exception-name-**1** and never enters the register — the
Format-3 figure (rendered from PDF p774: `exception-name-1 | exception-name-2 { FILE file-name-2 } … …`) puts
exception-name-2 only in the FILE alternative, and §14.9.49.4 GR3 c)/d) against e)/f)/g) split on the same axis.
GR3 gives the repeat its OUTCOME rather than forbidding it, and the corpus positive
`tests/conformance/2002/l1_use_sr14_bare_name_repeated` proves that outcome as OUTPUT: two bare
`USE AFTER EXCEPTION CONDITION EC-I-O-AT-END.` declaratives, only the first runs.

**The green test that held the row open was RE-DERIVED, not rebaselined.**
`ExceptionConditionConformanceTests.UseF3_DuplicatePairAcrossSections_Diagnosed` now writes the FILE-scoped pair
SR14 actually names; the shape it used to assert (two bare `EC-USER-D` declaratives) is a separate ACCEPTING
theory at 2002/2014/2023. Both arms of both rules are now pinned at every edition the rule has:
`UseF1_SameFileInTwoStatements_Diagnosed` / `UseF1_SameFileTwiceInOneStatement_IsAccepted` at 85·2002·2014·2023,
`UseF3_SamePairTwiceInOneStatement_IsAccepted` / `UseF3_RepeatedBareExceptionName_IsAccepted` at 2002·2014·2023.

Goldens: `tests/conformance/85/l1_use_sr8_file_named_twice` (+ `.out`),
`tests/conformance/2002/l1_use_sr14_pair_twice_one_statement` (+ `.out`),
`tests/conformance/2002/l1_use_sr14_bare_name_repeated` (+ `.out`),
`tests/conformance/negative/l1-use-sr8-file-in-two-statements` (reject-at 85 2002 2014 2023),
`tests/conformance/negative/l1-use-sr14-pair-in-two-statements` (reject-at 2002 2014 2023).
Rows `SR-14.9.49.3-8` (PARTIAL → CONFORMS) and `SR-14.9.49.3-14` (DIVERGES → CONFORMS); GAP 2802 → 2800.
No new diagnostic code was needed — the change only removes rejections. Design: the EC/conditions deep-dive
D11 now carries the one-mechanism-four-rules paragraph.

**What did NOT hold on today's tree.** The note says RU8SAME3 "ABORTS the rest of the operand list". It does not:
`EditionContext.Error` only records a diagnostic, and the Format-1 loop had no `continue` on the duplicate arm, so
F2 was still bound — what was observable was only that the whole compilation failed. The dispatch message for this
work also carried §14.9.47.3 for the USE syntax rules; §14.9.47 is UNLOCK. The note's own §14.9.49.3 is right, and
every citation here was re-run through `cite.py --check`.

**One sibling found and NOT fixed here** (a different subsystem, reported for its own note): §12.4.5.7.3 SR8 —
*"Neither data-name-1 nor record-key-name-1 shall be specified in more than one COLLATING SEQUENCE clause"* — is
enforced per NAME across all clauses by `DataBinder.cs`'s `seenInClause`, so ONE key-level clause naming the same
key twice (`COLLATING SEQUENCE OF IX-KEY IX-KEY IS ALPHA-X`, legal under the Format-2 figure's ellipsis) draws
COBOLNET1582 *"named in more than one COLLATING SEQUENCE clause"*. Probe `COLLSAME.cob` reproduces at `--std 2023`.
