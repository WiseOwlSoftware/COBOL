# PB3518 — the exhaustion witness may pin a non-conforming answer

Low, non-blocking lead from the branch review of PB3498 (`E:/COBOL-coord/scratch/reports/w1142a-PB3498-report.md`, `## Review findings` R1-1). The branch is not yet on main (PR #382); the sites below are as they stand on that branch, so re-read them after it lands.

**The lead.** `tests/WiseOwl.Cobol.Tests.Unit/HandleColumnLockHostDriftTests.cs` about line 336: the new exhaustion witness asserts `Outcome.Unavailable` for a fresh SHARING WITH ALL OTHER I-O request while its own setup holds a READ ONLY INPUT column (kept), which Table 19 refuses that request against. The test therefore may pin a non-conforming answer as correct, and its comment ("never Refused, since 61 is another connector's") is false for that setup: `HandleColumnLockHost.Establish` returns `Unavailable` when `Publish` exhausts (about line 82) before it ever tests the refused columns.

**Open question (stated, not adjudicated).** When publication is exhausted and the request also conflicts with a held column, does a user program see status 61 (refused) or the status `Unavailable` maps to? The ISO rule is Table 19 (section 14.9.27.4); an adjudicator decides which outcome the spec requires.

**Fix shape, once decided.** Either order `Establish` so the refused-column test runs before `Publish` (and correct the witness), or change the witness setup so no held column conflicts with the request, and correct the comment.

**Sites:**
- `tests/WiseOwl.Cobol.Tests.Unit/HandleColumnLockHostDriftTests.cs`
- `src/WiseOwl.Cobol.Runtime/` `HandleColumnLockHost.Establish` and `Publish`

## Landing

For the next implementer: `src/WiseOwl.Cobol.Runtime/IO/Sharing/HandleColumnLockHost.cs#Unpublishable` owns the exhausted-publication answer;
reuse `AnotherHoldsARefusedColumn` and `OwnBytes` for any further refused-column test, never a fresh loop over `OthersHold`. Trap: the
witness must take its kept holders BEFORE the outsider locks a column range (a holder of another column meets the outsider as a holder),
and a `Take` with nothing held in a refusing column is the only setup where `Unavailable` is the right answer.
The sidecar host's `Publish` returning null (host takes no lock, or 12 lost races) still answers `Unavailable` without testing: a lead.

Review round 1 (R1-1): `Publish` returns a `RegionLockResult`; `Unpublishable` takes it and tests the refused columns only for `Held` (every try collided), never for `Unavailable` (a handle that carries no lock). Witness: `AHandleThatCarriesNoLockIsUnavailableWhileAnExhaustedPublicationBesideAHolderIsRefused`.

Landed in wave 20261028, group C.

Re-probe on a fresh build: the lead was real, and the defect was in `HandleColumnLockHost.Establish`, not only in the witness. With a
READ ONLY INPUT holder kept and every try of a SHARING WITH ALL OTHER I-O publication colliding, the request answered `Unavailable`, so
the OPEN went on beside a connector Table 19 refuses it against, and the witness pinned that. The open question is answered from the
rule: a refusal is a conflict with an existing connector (ISO 14.9.27.4 Table 19; 9.1.13.9 1) '61'), and failing to publish is a host
limit that is not a conflict, so the two are independent. `Unpublishable` tests the refused columns (the asker's own bytes left out)
before it answers: `Refused` when another holder is seen, `Unavailable` otherwise. The Linux host already answers `Refused` for a held
byte of its own column, and the sidecar host already tests when it may not write its lock directory (PB2917). The column publication, the
owed-writes publication and a superseding request go through the one helper; `OwnBytes` and `AnotherHoldsARefusedColumn` replace three
copies of the refused-column loop. Witnesses: `HandleColumnLockHostDriftTests.APublicationThatEveryTryCollidesInIsRefusedByAHeldColumnTable19Refuses`
(new; red before the fix with Expected Refused, Actual Unavailable) and the corrected
`APublicationThatEveryTryCollidesInIsUnavailableAndLeavesWhatWasHeldStanding` (no held column refuses its request).
