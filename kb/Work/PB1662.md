# PB1662 — LANDED

## Landed (wave 1004, group D) — THE NOTE'S PREMISE WAS OVERTURNED, AND THE FIX IS THE OTHER ARM

Re-probed: `IF I1 = FUNCTION LENGTH(XA)` compiled (the fold reaches `RelationComparability` as a literal-shaped
operand), and so did every defined relation; but `IF I1 = FUNCTION INTEGER(3.7)`, `IF I1 = FUNCTION SQRT(9)` — the same
function-identifier, unfolded — were COBOLNET2533. So the screen answered one rule two ways by what the optimizer could
compute, as the note says. **The note chose to refuse the folded one; the spec admits both.** §8.4.3.2.1: "A
function-identifier references the unique data item that results from the evaluation of a function" (`cite.py --check
8.4.3.2.1` OK), and §15.2 items 4 and 5 give that item class and category numeric — so it is §8.8.4.2.13 row 2's "numeric
data item" (`cite.py --check 8.8.4.2.13 "an index-name and a numeric data item or numeric literal"` OK). The note's premise
("A function-identifier is neither a data item nor a literal") contradicts §8.4.3.2.1, and so did PB1468's first-wave
determination D-RELCLASS ("a function opposite an index-name is refused"), which also admitted an INTEGER function in the
sibling §8.8.4.2.5 row as the integer numeric temporary §15.4 makes it: one table, the same word "data item", two readings.
Rule 1 settles it; D-RELCLASS is corrected in the same change.

`RelationComparability.IndexNameAgainstNumeric` admits a numeric/integer function-identifier (and a COUNTER REGISTER, "a
temporary unsigned integer data item", §8.4.3.14.4 GR1 — a sibling found in the same arm) as row 2's data item; an
arithmetic expression stays refused. The fold keeps its origin (`BoundNumericLiteral.FunctionValue`, set in
`BindIntrinsicCore`, shared with PB1398), so a later screen that must treat a folded function as the function-identifier it
was written as (PB1470's "at least one operand that is not a literal" is the next candidate) has the fact to ask.
Witnesses: `conformance:85/pb1662_index_name_against_function` (folded, INTEGER, SQRT, MAX; equal and unequal),
`RelationComparabilityTests` (its function rows are now row-2 partners, plus a folded `FUNCTION LENGTH(XA)` kind).
Sweep of "is this a literal" consumers of the fold: the screens that read `BoundNumericLiteral` for a syntax rule are
`RelationComparability` (this), PB1470 (open, not a literal-vs-function rule today) and the IntrinsicBinder LENGTH arms
(PB1398); no other consumer rejects a literal by form.

Filed 2026-09-27 by the train-67 lander from the wave-67 N implementer report (`w67n-PB1468-report.md`, new
defect 2). Under-reject, low harm: the program runs and compares the folded value.

**Rule.** §8.8.4.2.13: "Relation tests may be made only between" 1) two index-names, 2) an index-name and a
numeric data item or numeric literal, 3) an index data item and an index-name or another index data item
(`cite.py --check 8.8.4.2.13` OK). A function-identifier is neither a data item nor a literal; PB1468's
COBOLNET2533 refuses an unfolded function or expression opposite an index-name.

**Code site.** The intrinsic constant fold that yields a `BoundNumericLiteral` (IntrinsicBinder), then
`src/Cobol.Net.Compiler/Binding/RelationComparability.cs#IndexNameAgainstNumeric`, which sees the literal.

**What the fixer owes.** The comparability screen reads the operand's WRITTEN form (the fold keeps a marker of its
origin, or the screen runs before the fold — the same "screen what was written" rule PB1468 applied to the EVALUATE
intermediate). Negative golden `IF I1 = FUNCTION LENGTH(XA)` -> COBOLNET2533; sweep every other fold consumer that
asks "is this a literal" for a syntax rule.
