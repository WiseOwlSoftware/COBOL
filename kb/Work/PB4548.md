# PB4548 — concatenation-figurative-zero-refused: -std=cobol2014: "A" & ZERO is refused: "only literals with the same category can be concatenated"

Filed 2026-11-03 by `scripts/fuzz_triage.py file` from the triage of the differential-fuzz run `fuzz-batch-3000-20261103`, after an independent refuter. Upstream status `unreported`: the tracker has not been searched (owner-gated, PB3838). The run directory is git-ignored and local: the minimal program below is the repro.

## Summary

Under `-std=cobol2014`, cobc 3.2 refuses a concatenation expression whose operand is the figurative constant ZERO (`"A" & ZERO & "B"`) with "only literals with the same category can be concatenated". The same expression with QUOTE, SPACE or HIGH-VALUE compiles and runs correctly (`[A"B]`, `[A B]`, and `[A` X'FF' `B]`). ISO allows a figurative constant as either operand and gives the result the class of the other operand. Class: rejects legal source. Fuzz programs: fz00040, fz00041, fz00744, fz00745, fz01450, fz01449, fz02155 (night fuzz-batch-3000-20261103, slice D2).

## Minimal test case

Free reference format.

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. CAT1.
PROCEDURE DIVISION.
DISPLAY "[" "A" & ZERO & "B" "]"
STOP RUN.
```

## Environment

`cobc (GnuCOBOL) 3.2.0`, WSL2 Ubuntu x86_64. Compiled with `cobc -x -free -std=cobol2014 -o p cat1.cob` (`-fsyntax-only` gives the same diagnostics); no executable is produced, so nothing is run.

## Observed result

Compile, exit code 1:

```text
cat1.cob:4: error: only literals with the same category can be concatenated
    2 | PROGRAM-ID. CAT1.
    3 | PROCEDURE DIVISION.
    4 > DISPLAY "[" "A" & ZERO & "B" "]"
    5 | STOP RUN.
    6 | <EOF>
rc=1
```

## Expected result (per ISO)

The program is legal and displays `[A0B]`: ZERO in the concatenation is one character (rule 3 a) of 8.3.3.6.4), it represents the alphanumeric character '0' because the other operand is alphanumeric, and the expression is an alphanumeric literal. The rules are quoted from ISO/IEC 1989:2023; the concatenation expression is in the 2014 edition (cobc accepts it under -std=cobol2014 for other operands).

- §2023:8.8.3.2 (checked): "except that a figurative constant may be specified as one or both operands"
- §2023:8.8.3.3 (checked): "when one of the operands is a figurative constant, the class of the literal or concatenation expression that constitutes the other operand"
- §2023:8.3.3.6.4 (checked): "When a figurative constant is specified in a concatenation expression, the length of the string is one character"
- §2023:8.3.3.6.4 (checked): "The zero format represents the numeric value '0', one or more of the boolean character '0', or one or more of the character '0' in the computer's runtime coded character set, depending on context"

## Our compiler

WiseOwl COBOL (fresh judge, `cobol cat1.cob --std 2014 --source-format free -o cat1.dll`) compiles it with no diagnostic; `dotnet cat1.dll` exits 0 with `[A0B]`.

## Fix site

cobc/tree.c `cb_concat_literals` (line 2793 of the 3.2 source; the test is at line 2802): it refuses any pair whose tree categories differ (`x1->category != x2->category`). The figurative constant ZERO reaches it with the numeric category, while QUOTE, SPACE and HIGH-VALUE have the alphanumeric category, so only ZERO is refused. A figurative operand should take the other operand's class before the comparison.

## Draft issue

**Title:** Concatenation expression refuses the figurative constant ZERO: "A" & ZERO, ZERO & ZERO

As posted (owner-reviewed, 2026-11-04):

cobc refuses a concatenation expression with the figurative constant ZERO as an operand, such as `"A" & ZERO` or `ZERO & ZERO`, while `"A" & SPACE` and `"A" & QUOTE` work. The same check, in a smaller case, refuses any figurative constant beside a national literal.

### To reproduce

`cat1.cob` (attached, free format):

~~~~
IDENTIFICATION DIVISION.
PROGRAM-ID. CAT1.
PROCEDURE DIVISION.
DISPLAY "[" "A" & ZERO & "B" "]"
STOP RUN.
~~~~

    cobc -x -free -std=cobol2014 cat1.cob

### What happens

3.2.0 and 3.3-dev r5751 both stop, exit 1, with

~~~~
cat1.cob:4: error: only literals with the same category can be concatenated
~~~~

and the source excerpt. `cat2.cob` gets the same error for `VALUE "A" & ZERO & "B"`, `ZERO & "B"`, `SPACE & ZERO` and `VALUE N"A" & SPACE & N"B"`, and "only alphanumeric, utf-8, national or boolean literals may be concatenated" for `ZERO & ZERO`. The national line also draws cobc's -Wunfinished warning for national literals.

### What should happen

The program displays `[A0B]`. ISO/IEC 1989:2023 8.8.3.2 syntax rule 1 requires both operands to be of the same class "except that a figurative constant may be specified as one or both operands". By 8.8.3.3 general rule 1 a) and b) the result has the class of the other operand, or is alphanumeric when both are figurative constants, and by 8.3.3.6.4 general rule 3 a) the figurative constant is one character. The same in 2002 and in the 2014 FCD.

### Why it happens

`cb_concat_literals` in `cobc/tree.c` first refuses any pair whose categories differ (`x1->category != x2->category`). `cb_zero` is built with `CB_CATEGORY_NUMERIC` and the other figurative constants with `CB_CATEGORY_ALPHANUMERIC`, so ZERO never matches an alphanumeric literal and no figurative constant matches a national one; `ZERO & ZERO` passes that test and then fails the next one. `get_data_from_const` already maps ZERO to `'0'`, but `cb_concat_literals` refuses ZERO before that code is reached. `concat_literals` also takes the result's category from the left operand.

### Proposed fix

The attached `n10-concat-figurative-zero.patch` (against 3.3-dev r5751) makes `cb_concat_literals` give a figurative constant the other operand's category, or alphanumeric when both are, before the checks (NULL is still refused), and `concat_literals` builds the literal with that category. With a national operand, `get_data_and_size_from_lit` makes the figurative constant one national character, 00 20 for SPACE as the scanner stores `N" "`, and FF FF for HIGH-VALUE as MOVE HIGH-VALUE does; a MOVE SPACE to a PIC N item stores 20 20 today, so you may prefer another representation. `B"1" & B"0"` is still refused, because cobc builds B literals as numeric literals.

With the patch `cat1` prints `[A0B]` and `cat2` prints

~~~~
[A0B] [0B] [00] [ 0]
NATIONAL OK
~~~~

It adds the testsuite case "Concatenation with figurative constants" to `run_misc.at`, with ChangeLog entries in `cobc/` and `tests/`. `make check`: 1373 expected, 9 skipped, 0 failed (1372 unpatched); the new test fails without the patch.
