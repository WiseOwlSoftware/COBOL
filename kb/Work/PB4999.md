# PB4999 - a cut that still parses gets no margin-R note

**Found.** Wave 20261926 group C retired PB4981, a reported wrong answer, after finding the cause in the test source: a
fixed-form line of 74 characters carried `** 0.7` with the `7` in column 73, so the compiler read `** 0.` and computed a
different value. Columns 73-80 are the program-identification area, which the compiler ignores (fixed reference format),
so the cut is correct; but nothing told the programmer. The margin-R note (`CobolErrorListener.NoteMarginRCut`, PB2555,
PB4372) is given only when the parse FAILS on a line after a cut, so a cut that leaves a program that still parses, as
here, is silent and changes the program's meaning.

**Owed.** A warning when program text is cut at margin R in the middle of a token: column 72 is non-blank and column 73
continues the same token (no separator between them). A tag-shaped identification-area entry (sequence text after a
space at column 72, PB4372's recurrence test) stays silent. The shape must reuse `MarginRCut`'s one decision of what a
cut word is, not a second scan.

**Repro.** A fixed-form program whose `COMPUTE X = Y ** 0.7` line places the `7` in column 73; compile and run: the
result is `Y ** 0`, with no diagnostic.

**Sites:** `src/WiseOwl.Cobol.Frontend/Common/MarginRCut.cs` (`MarginRCut`, `MarginRCut.LastCutPosition`),
`src/WiseOwl.Cobol.Frontend/Preprocessor/ReferenceFormatMap.cs` (`ReferenceFormatMap.CutOf`),
`src/WiseOwl.Cobol.Frontend/Parsing/CobolErrorListener.cs` (`CobolErrorListener.NoteMarginRCut`),
`src/WiseOwl.Cobol.Editions/Diagnostics/DiagnosticCatalog.cs` (`DiagnosticCatalog.ProgramTextPastMarginR`).

**Same lead again (2026-11-08, w20261926c-PB4980-report.md).** The worker proposed a lint for non-blank text in columns 73-80 of a fixed-format line, the check that would have prevented the PB4981 false finding; this note's margin-R warning is that check for compiled source (a test-source lint, if wanted, is a separate script over `tests/` and `conformance-suite/`).

## 2026-11-08 - LANDED (wave 20261936, group E)

Re-probe on the Debug build (`E:/COBOL-coord/scratch/w20261936e/p1.cob`, `COMPUTE X = Y ** 0.7` with the `.` at position 72 and the
`7` at 73): the program compiled with no diagnostic and printed the value of `Y ** 0`.

**Fix (the other arm of one question).** `CobolErrorListener` asks "was this line's program text cut where it may have been program
text?" only beside a syntax error. `MarginRCutScreen.Warnings` (new, `Frontend.Parsing`) asks it of every default-channel token of the
lexed stream through the same `IMarginRCutLocator`, using the decision the listener's in-word arm already used
(`LocatedMarginRCut.EndsAtMarginR`: the token's last character at position 72, the cut text beginning at position 73, no space
between). New warning COBOL6688 (`DiagnosticCatalog.TokenCutAtMarginR`), reported after the parse and placed among its reports
(`DiagnosticBag.AddBeforeEffects`); a line that already drew COBOL5788 is not named twice. The sentence about what was cut moved into
`MarginRCut.Account` / `MarginRCut.Remedy`, shared by both warnings. A tag or sequence number set off by a space, a recurring tag, an
inline comment's rest, a comment line, an omitted branch and free form stay silent. Witnesses: `unit:MarginRCutTokenTests` (10 cases),
`conformance:cases/A.1-Implementor-defined-language-element-list/pb4999-token-cut-at-margin-r`.
