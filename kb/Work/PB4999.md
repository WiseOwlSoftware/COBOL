# PB4999 - a cut that still parses gets no margin-R note

**Found.** Wave 20261926 group C retired PB4981, a reported wrong answer, after finding the cause in the test source: a
fixed-form line of 74 characters carried `** 0.7` with the `7` in column 73, so the compiler read `** 0.` and computed a
different value. Columns 73-80 are the program-identification area, which the compiler ignores (fixed reference format),
so the cut is correct; but nothing told the programmer. The margin-R note (`CobolErrorListener.NoteMarginRCut`, PB2555,
PB4372) is given only when the parse FAILS on a line after a cut, so a cut that leaves a program that still parses, as
here, is silent and changes the program's meaning.

**Owed.** A warning when program text is cut at margin R in the middle of a token: column 72 is non-blank and column 73
continues the same token (no separator between them). A tag-shaped identification-area entry (sequence text after a
space at column 72, PB4372's recurrence test) stays silent. The shape must reuse `MarginRCut`'s one decision of what a
cut word is, not a second scan.

**Repro.** A fixed-form program whose `COMPUTE X = Y ** 0.7` line places the `7` in column 73; compile and run: the
result is `Y ** 0`, with no diagnostic.

**Sites:** `src/WiseOwl.Cobol.Frontend/Common/MarginRCut.cs` (`MarginRCut`, `MarginRCut.LastCutPosition`),
`src/WiseOwl.Cobol.Frontend/Preprocessor/ReferenceFormatMap.cs` (`ReferenceFormatMap.CutOf`),
`src/WiseOwl.Cobol.Frontend/Parsing/CobolErrorListener.cs` (`CobolErrorListener.NoteMarginRCut`),
`src/WiseOwl.Cobol.Editions/Diagnostics/DiagnosticCatalog.cs` (`DiagnosticCatalog.ProgramTextPastMarginR`).
