**Rule it breaks:** ISO 8.4.2.2.1 (uniqueness shall be established through qualification for each user-defined name explicitly referenced) with 13.18.54.4 GR5 (the data-name of a SUM entry is the name of the sum counter); the resolver own ResolveUnqualified refuses the same collision between two ordinary items (kb/Work R33), so the two arms of one rule disagree

**Scenario:** Verified on the pin build (cobol.dll at 8be230068): WORKING-STORAGE 01 WS-G. 02 TOT-N PIC 99 VALUE 7, REPORT SECTION 02 TOT-N COLUMN 1 PIC 99 SUM WS-T, PROCEDURE MOVE 3 TO WS-T, GENERATE DET-1, DISPLAY TOT-N compiles with no diagnostic and prints 03 (the sum counter). Two data-names share the spelling and none is qualified, so the reference shall be refused (COBOLNET1639, as for two WORKING-STORAGE TOT-N); instead ResolveImplCore asks SumCounterFor BEFORE ordinary lookup and SumCounterFamilyFor consults ordinary items only when the written qualifiers reach no counter (line 2025), so with no qualifiers the counter always wins. A MOVE to TOT-N alters the report total where the programmer may have meant the WORKING-STORAGE item: a silent wrong answer on source the standard requires to be rejected

## Landed

Re-probed on the Debug build (`p1`: WORKING-STORAGE `02 TOT-N` under `01 WS-G`, a REPORT SECTION `TOT-N ... SUM WS-T`,
`DISPLAY TOT-N`): the unqualified reference compiled clean and bound the sum counter, as the note says.

**Fix (the root, not the arm).** `ReferenceResolver.SumCounterFamilyFor` asked only the counters and consulted ordinary
items when the written qualifiers reached no counter. A SUM entry's data-name is a data-name (§13.18.54.4 GR5), so it is
ONE candidate beside the ordinary data items of its spelling, and §8.4.2.2.3 SR1 counts them together. The method now adds
the ordinary candidates the SAME qualifiers reach (`DataBinder.QualifiedCandidates`, the set the ordinary lookup reads) in
the SAME source element (`DeclaringDepth == ReportDepth` of the counter) to the counter matches and reports COBOLNET2145 when
the sum exceeds one. Qualified forms still tell them apart (`TOT-N OF WS-G`, `TOT-N OF R-1`). The other arm of the same
dispatch, the table(ALL) intrinsic argument (`IntrinsicBinder.TryBindAllArgument`), asks the SAME `SumCounterFamilyFor`, so it
inherits the verdict (`ReferenceIdentificationDriftTests.TheTableAllArgument_AsksTheSameCounterResolver`).

**Goldens.** `conformance:85/pb3232_sum_counter_qualified_beside_data_item` (derived from §13.18.54.4 GR2/GR3/GR7 c) 1 and
§8.4.2.2.3 SR2: `TOT-N OF WS-G` reads 07, `TOT-N OF R-1` reads the counter 11, the MOVE 5 alters only the data item) and
`negative:pb3232-sum-counter-beside-data-item` (all four editions, COBOLNET2145). No existing corpus program (50 report
programs, the NIST RW set) collided.

**Not closed here (sibling probes, no evidence of a defect):** a sum counter spelled like a condition-name or index-name at
equal depth keeps the other class by `SymbolTable.NearerDataNameHides`'s documented rule; not probed further.
