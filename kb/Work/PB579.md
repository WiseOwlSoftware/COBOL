### Inventory row `GR-13.18.60.4-16` (NOT-IMPLEMENTED)
USAGE FLOAT-BINARY-128 is NOT PROVIDED. The rule pins the format to ISO/IEC 60559:2020 binary128 and .NET has no IEEE binary128 type, so ParseUsage rejects the usage LOUD with COBOLNET1564 naming Annex A.3 item 17 (probe p15 at --std 2023; the grammar's usageKeyword and the 2014 introduction gate both carry the member so the reject is never a parse error at the wrong stage, and a double-backed approximation - which would be non-conforming against a PINNED format - is never emitted). The ground is spec-sanctioned: A.3 item 17 makes FLOAT-BINARY-32/-64/-128 processor-dependent and §4.2.6 says "Language elements that pertain to specific processor-dependent elements for which support is not claimed need not be implemented", with the absence to be specified in the implementor's documentation - which docs/CONFORMANCE.md §2 row 17 does ("Partial - binary32→float, binary64→double claimed; binary128 not"). ⛔ THE DOCUMENTED-NON-SUPPORT VERDICT IS THE OWNER'S, NEVER AN AGENT'S (D13), so this row is recorded NOT-IMPLEMENTED: an owner decision converting it needs no new evidence - the witness the schema requires (a test proving we diagnose rather than silently miscompile) already exists and is named in test-ref.

### Inventory row `GR-13.18.60.4-17` (NOT-IMPLEMENTED)
USAGE FLOAT-DECIMAL-16 is NOT PROVIDED. The rule pins the format to ISO/IEC 60559:2020 decimal64; .NET's System.Decimal is a different format entirely, so ParseUsage rejects LOUD with COBOLNET1564 naming Annex A.3 item 19 (probe p16 at --std 2023). The grammar DOES parse the usage and its bracketed encoding/endianness tail (kb/Work PB174), deliberately, so that legal 2014+ source such as `USAGE FLOAT-DECIMAL-16 BINARY-ENCODING` is refused by the honest diagnostic - the non-support of the usage - rather than by a raw parse error at the wrong stage; conformance:negative/pb174-float-decimal-encoding-nonsupport pins exactly that stage choice. Licence: A.3 item 19 (processor-dependent) plus §4.2.6, documented at docs/CONFORMANCE.md §2 row 19 ("Not claimed"). ⛔ DOCUMENTED-NON-SUPPORT is the owner's verdict (D13); NOT-IMPLEMENTED is what an agent may record. The witness the conversion would need already exists.

### Inventory row `GR-13.18.60.4-18` (NOT-IMPLEMENTED)
USAGE FLOAT-DECIMAL-34 is NOT PROVIDED - the decimal128 twin of GR17. ParseUsage rejects LOUD with COBOLNET1564 naming Annex A.3 item 19 (probe p17 at --std 2023, and probe p21 shows the same reject for `FLOAT-DECIMAL-34 HIGH-ORDER-RIGHT DECIMAL-ENCODING`, i.e. the tail parses and the usage is what is refused). Licence: A.3 item 19 plus §4.2.6, documented at docs/CONFORMANCE.md §2 row 19. ⛔ DOCUMENTED-NON-SUPPORT is the owner's verdict (D13); recorded NOT-IMPLEMENTED here, with the witness already on disk.

### Inventory row `GR-13.18.60.4-19` (PARTIAL)
a) b) and c) CONFORM for the standard BINARY floating-point usages, measured on the BYTES rather than on a self-inverse round trip. Probe p29 (--std 2023) puts 1.0 in three FLOAT-BINARY-32 items and reads each group's image with FUNCTION ORD: HIGH-ORDER-LEFT gives 64 129 1 1 (0x3F 0x80 0x00 0x00 - big-endian, a), HIGH-ORDER-RIGHT gives 1 1 129 64 (little-endian, b), and no phrase gives big-endian. Probe p30 adds an `OPTIONS. FLOAT-BINARY IS HIGH-ORDER-RIGHT.` paragraph: the phrase-less item becomes little-endian and an item writing HIGH-ORDER-LEFT stays big-endian - c), and the precedence is §11.9.8.3 SR2/SR3's own wording ("in which an endianness-phrase is not specified"), not a preference. The no-OPTIONS default is HIGH-ORDER-LEFT, the documented choice at docs/CONFORMANCE.md §7 item 48 (§11.9.8.3 SR1 leaves it to the implementor). The phrase is refused where the general format does not print it (COBOLNET1716 on FLOAT-LONG - probe p19) and a repeat is refused (COBOLNET1718); the whole phrase is COBOL-2014-gated (COBOLNET0900 at 85/2002 - probe p47). Derivation is centralized: UsageFamilies.IsStandardBinaryFloat / IsStandardDecimalFloat write §3.166/§3.167 down once, PicInfo.FloatItem applies GR19a/b once. PARTIAL FOR TWO REASONS, both of them the reach of the rule rather than its logic: d) - the implied phrase for the standard DECIMAL floating-point usages via §11.9.9 - can never execute, because FLOAT-DECIMAL-16/-34 are not provided (rows GR17/GR18, Annex A.3 item 19), and a) and b) are likewise unreachable for FLOAT-BINARY-128 (row GR16, A.3 item 17), so of the five usages §3.166/§3.167 name only two ever reach GR19's effect. kb/Work PB174 landed the per-item phrase and is closed.

### Inventory row `GR-13.18.60.4-20` (NOT-IMPLEMENTED)
Nothing in this rule can execute. a) and b) give BINARY-ENCODING and DECIMAL-ENCODING their meaning "in a data item described with any standard decimal floating-point usage", and c) defers the unstated case to §11.9.9 - all three are conditioned on the standard DECIMAL floating-point usages, which are NOT PROVIDED (FLOAT-DECIMAL-16/-34, rows GR17/GR18, rejected COBOLNET1564 under Annex A.3 item 19). What EXISTS is the syntax and the applicability screen, deliberately and no further: CobolData.g4's `floatFormatPhrase*` parses the bracketed choice-indicator group in either order (§5.2.6.4), DataBinder.BindEntry rejects an encoding-phrase on anything but FLOAT-DECIMAL-16/-34 with COBOLNET1717 citing GR20a (probe p20: `USAGE FLOAT-BINARY-32 BINARY-ENCODING`) and rejects a repeat with COBOLNET1718 - and the surviving value is then NOT carried onto PicInfo, which the binder's own comment records as a measured choice ("a field nothing reads is a lookup nothing has ever contradicted"). So there is no encoding to implement until the usages land. Annex A.3 item 20 makes the encoding-phrase itself processor-dependent and §4.2.6 licenses the absence; docs/CONFORMANCE.md §2 row 20-21 records it as N/A because item 19 is not claimed. ⛔ Converting this row to DOCUMENTED-NON-SUPPORT is an owner decision (D13), not an agent's - and it should be taken together with GR17/GR18, since it is derivative of them.

- `GR-13.18.63.4-24` — adjudicated DIVERGES, which would have REPLACED the same owner verdict in the other
  direction. Excluded by the same rule (now enforced structurally in `merge_batch.py`, which reads the
  inventory and refuses any record whose row already carries an owner verdict).

THE MEASUREMENT. The printed Format 5 figure brackets the connective — `[ IS / ARE ] { INVALID / VALID }` —
and §13.18.63.3 SR39 is the very rule that makes it optional. So `{VALUE|VALUES} literal-5 [THRU literal-6]
VALID.` with no IS/ARE is legal Format-5 source. The compiler ACCEPTS it silently at 2002, 2014 and 2023
(rc=0, no diagnostic); every other spelling declines COBOLNET1708. Cause: `| VALID` is an UNGUARDED
`cobolWord` alternative (CobolWords.g4:106), so the greedy VALUE operand loop consumes VALID as a
constant-name operand and the Format-5 tail `({is2002()}? validateValidPhrase)?` never matches. The
unresolved operand then reaches the backend as a bare C# identifier with no COBOLNET1547 — a raw Roslyn
error, not a decline.

THE QUESTION (one, bare): **does a DOCUMENTED-NON-SUPPORT row stand while the decline that justifies it has a
measured hole, or does the hole reopen the rows until the decline is airtight?**

Either answer is cheap to act on and the work is already filed: the leak itself is registered as a defect note
in this batch (the unguarded `| VALID` alternative, and the unresolvable-operand-reaches-the-backend twin), so
repairing the decline needs no new investigation. What an agent may not do is move the four rows.
