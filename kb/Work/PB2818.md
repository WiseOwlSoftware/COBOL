# PB2818 — a dynamic-capacity table of USAGE BIT elements emits uncompilable C#

Found by the w1045f implementer (PB2691, report lead 1) and filed by the train 1045 lander, 2026-10-08 18:20 PDT.

## Repro

`E:\COBOL-coord\scratch\w1045f\p\b3.cob`, `--std 2014`:

```cobol
       01 G1.
          05 A PIC 1 USAGE BIT VALUE B"1".
          05 T PIC 1 USAGE BIT OCCURS DYNAMIC CAPACITY IN C1.
          05 D PIC X DYNAMIC LENGTH LIMIT 5.
       PROCEDURE DIVISION.
           MOVE B"1" TO T(1)
           DISPLAY C1
```

The compile ends in CS0029 (cannot convert `string` to `CobolDynTable<string>`) on the generated field for `T`.
The source is legal: §8.5.1.9.1 rule 3 lets a dynamic-capacity table "be defined in any place, other than the file
section, in which a fixed-capacity table may be defined", and a table of USAGE BIT elements may be defined there. The
expected `C1` after the MOVE is derived from §8.5.1.9.3 (implicit changes in capacity) when the fix's golden is written.

## Site

The dynamic-table field emission for a bit leaf: the field initialiser `DataEmitter` / `GroupImageCodec` produce for an
OCCURS DYNAMIC leaf whose element is USAGE BIT (the bit element's carrier is a string image, and the table wrapper
is not applied).

## Fix shape

Give a bit element's dynamic table the same `CobolDynTable<T>` wrapping every other leaf's dynamic table gets, from
the one place the leaf's carrier type is chosen. Then revisit PB2691's `Unplaced` determination (a dynamic table packed
into a non-byte-granular bit run has no relative byte position, so the group is compatible with no group): it becomes
reachable once this compiles, and needs a golden.

## Test

A 2014 positive golden holding the repro (with the `C1` value derived from §8.5.1.9.3) and a negative below 2014.

## Landed 2026-10-10 (w1056f)

**Re-probed first, on this worktree's build (base 4e4e38b54).** `E:\COBOL-coord\scratch\w1045f\p\b3.cob` at `--std 2014`
still ended `error CS0029: Cannot implicitly convert type 'string' to 'CobolDynTable<string>'` at `T = CobolBits.Slice(...)`.
The generated C# showed the ROOT: `CobolBits.Pack(A + T, 2)` and `T = CobolBits.Slice(__bits0, 1, 1)` - the table was a MEMBER
of the group's 2-bit run, though `CobolDynTable<string> T` is a separate out-of-line object. The note's site,
`CobolDynTable.cs`, is not touched: the runtime table was already generic and the defect was the compiler's layout. A
table alone in its group compiled, because a one-member run has no neighbour to be packed with.

**Root cause.** `BitLayout.RunMember` / `SharesByteWith` took a dynamic-capacity table of bit items as one more same-level
bit item, so the one run law (`BitLayout.RunsOf`, read by `PhysicalModel`, `GroupImageCodec` and the 8.5.1.12 atom builder)
packed it with its neighbours. A table is out-of-line storage ("table data items are not required to be contiguous in
physical memory. The size, location, and time of physical allocation ... are implementor-defined", 8.5.1.9.1).

**Determination (docs/CONFORMANCE.md DOC-A.1-61).** A dynamic-capacity table of bit items shares no byte, in either
direction: it starts at "the first bit position of the first available byte" (8.5.1.6.3, "all other bit data items"),
each occurrence is ceil(n / 8) characters (BYTE-LENGTH, 15.14.4 rule 4) holding its n positions PACKED, and the item
after it starts on the next byte boundary. That gives the table the relative byte position 8.5.1.12.2 pairs tables by.

**Fix (one place per arm).** `BitLayout.RunMember` and `SharesByteWith` exclude a dynamic table; `BitLayout.RunBits`
counts it as one element rounded up to a byte (8.5.1.12.3, "considered to be the length of a single element").
`GroupImageCodec.CurrentMemberImage` / `TableElementFromImage` gained the bit lane (`CobolBits.Pack` / `Unpack`), the
inverse of each other. `VariableLengthCompatibility`'s PB2691 `Unplaced` determination (a table in a non-byte-granular
run is compatible with no group) is DELETED, not revisited: it described a layout that no longer exists, and a bit GROUP
holding a table is already refused by COBOL1653 (13.18.29.3 SR1). SIBLING ARM (two-arm dispatch): `Place.For` gave a
dynamic table's BYTE origin 0 (`ReferenceResolver`: "IS its element, at offset zero of the element cell") but its BIT
origin the table's reservation in the parent scope, so a bit table beside other members of an EXTERNAL / BASED group
read and wrote past its one-byte element cell and lost every store (`T3 (2)` read back 0); fixed the same way,
`item.IsDynamicTable ? 0 : item.ClassBitOffset`.

**Goldens.** `tests/conformance/2014/pb2818_dyn_bit_table` (struct group, same-shape and different-width neighbours, a
10-bit two-byte element, an EXTERNAL group) and negative `pb2818-dyn-bit-table-below-2014` (COBOL0900 at 85/2002). The
PB2691 negative `pb2691-bit-run-dynamic-table-incompatible` still refuses its MOVE, now by 8.5.1.12.2 on `D`'s relative
byte position (its comment and `.err` say so).

**For the next implementer.** FUNCTION LENGTH / BYTE-LENGTH of a group holding USAGE BIT items and a runtime-length
subordinate is still the named stage COBOL1756 (`IntrinsicBinder.VariableLengthGroupSum`, the `group.HasBitDescendant`
test): the fixed extent is a layout, not a sum. It is the same family but a different mechanism.
