# PB485 — LANDED — the check existed in the legacy engine and was never ported

Found 2026-09-04 attributing battery #44's two GnuCOBOL differential flips (`scratchpad/battery-44/flips/ATTRIBUTION.md`);
every citation and measurement below was made on the battery-44 worktree at `1d949007` and re-derived for this note.

## Harm

COBOL.NET silently accepts data description entries whose level-number ISO does not define, in the strict
`--std 2023` lane with no `--permissive` and no diagnostic. The entry is not rejected and not ignored: it is bound
as an ordinary data item and, because the level number exceeds every preceding level, **nested under whatever
entry precedes it**. `78 K VALUE 5.` becomes a memberless group `K` subordinate to the previous `01`/`77`, and a
numeric use of it reaches the deferred Tier-C whole-group-image island and throws
`NotImplementedCobolFeatureException` at run time. The user gets a runtime abort where the standard requires a
compile-time indication of an explicit syntax-rule violation.

## Repro (`scratchpad/battery-44/flips/probe/`, all `--std 2023`, no `--permissive`)

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. P78REFMOD.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  V         PIC X(20).
       78  K         VALUE 5.
       PROCEDURE DIVISION.
           MOVE "AB" TO V (K:2)
           DISPLAY V
           STOP RUN.
```

`cobol p78refmod.cob --std 2023 --run` → compiles (exit 0), then `NotImplementedCobolFeatureException: … numeric
use of group item 'K' with a dynamic-length / dynamic-capacity member`. Expected: a §13.18.33.3 SR5 diagnostic at
the entry. `plevel50.cob` (`50 BAD PIC X(3).`) and `phuge.cob` (`999999999999 BAD PIC X(3).`) both compile AND run
clean, exit 0 — the whole level-number range is unchecked, not level 78 alone. The ISO spelling of the intent,
`pconst.cob` (`01 K CONSTANT AS 5.`, §13.10), is correct today and prints `    AB`.

## The rule

```
python scripts/spec/cite.py --check 13.18.33.3 "shall have level-numbers 66, 77, 88, or 1 through 49"
OK  §13.18.33.3 5)  (Syntax rules)
python scripts/spec/cite.py --check 13.18.33.1 "Level numbers 1 through 49 indicate the position of a data item"
OK  §13.18.33.1   (General)
python scripts/spec/cite.py --check 4.2.2 "shall provide a warning mechanism that optionally may be invoked by the user at compile time to indicate violations of the general formats and the explicit syntax rules"
OK  §4.2.2   (Acceptance of standard language elements)
```

`cite.py --find "level-number 78"` → no clause. Level 78 is a MicroFocus/GnuCOBOL extension, not ISO; the owner's
`follow_gnucobol_on_split_latitude` covers implementor-defined latitude and expressly not non-ISO extensions, and
`dialect_two_axes` requires every leniency to be dialect-gated — accepting it silently in the strict lane is neither.
§13.18.33.3 carries the whole family and each arm needs its own section context: SR2 (subordinate to FD/SD: 66, 88,
1–49), SR4 (subordinate to RD: 1–49), SR5 (WORKING-STORAGE / LOCAL-STORAGE / LINKAGE: 66, 77, 88, 1–49), SR6 (screen
entries: 1–49), SR3 (1–9 may be written 01–09).

## Code site

`src/Cobol.Net.Compiler/Binding/DataBinder.cs:633` — `int.TryParse(entry.levelNumber().GetText(), out int lvl);` —
the ONE place the level number enters the typed-native model, with no range test and a silent `lvl = 0` on parse
failure. The grammar is deliberately permissive (`levelNumber : INTEGERLIT ;`, `Grammar/Core/CobolData.g4:216`), so
the screen belongs at the bind site, section-aware, not in the grammar. ⛔ **Two-arm dispatch:** `levelNumber` is
reached through two parser rules — `dataDescriptionEntry` (`CobolData.g4:213`), bound here, and
`linkageProcedureParameter` (`CobolData.g4:196-198`, the COBOL-2002 procedure-parameter form under `linkageEntry`),
which does not pass through `DataBinder.cs:633` at all. Write the screen once and route both arms to it.

**The check existed and was never ported.** `CBL0815` — "Invalid level number '{0}' for '{1}': level numbers must be
1-49, 66, 77, or 88" — is declared in `src/Cobol.Net.Frontend/Diagnostics/DiagnosticDescriptors.cs:390` and has zero
users outside the LEGACY engine (`src/CobolSharp.Compiler/Semantics/SemanticBuilder.cs:1239`). Its comment ("no
valid program has an out-of-range level, so it never fires on the corpus") is a dead-lookup artefact: it never fires
because nothing calls it. Whether the fix reuses `CBL0815` or takes a COBOLNET code is the implementer's call; a dead
descriptor left behind is not.

## How battery #44 measured it

The GnuCOBOL differential at `1d949007` reports two per-case flips against the committed baseline, both attributed
exclusively to `5082cffc` (PB201): before it, the phantom group's name was emitted as a field of the preceding item
(`CobolTable.Occ(NUMVAR.CONST4)`, seven CS1061s), an uncompilable-C# crash that counted as REJECT; after it, the
group takes the D18 route and compiles. `syn_move:453` (baseline `WE_REJECT_THEY_ACCEPT`, measured `AGREE_ACCEPT`)
and `syn_misc:5093` (baseline `AGREE_REJECT`, measured `WE_ACCEPT_THEY_REJECT`; GnuCOBOL's own reason there is a
compile-time out-of-bounds reference-modification flag that §8.4.3.3.4 GR5c makes a RUN-time EC-BOUND-REF-MOD and
§4.2.2 ¶4 does not require — on that axis we conform and they are stricter than the standard). **Both baseline rows
are already the ISO-correct verdicts and were left unchanged on purpose** — rebaselining would pin a known
non-conformance into the regression net. Enforcing SR5 restores both rows for the right reason.

Blast radius (`flips/sweep.py`, `sweep2.py`): 82 of the 1,323 compiled corpus cases carry a level-78 entry (68
`WE_REJECT_THEY_ACCEPT`, 9 `AGREE_REJECT`, 5 ACCEPT — the two flips plus three that were leaking before train 1:
`syn_misc:5499`, `syn_occurs:103` (its title is "OCCURS with level 78"; even GnuCOBOL rejects it), `run_file:9847`),
plus 9 in secondary members the differential never compiles. **After the fix those three move toward REJECT and are
rebaselined as spec-licensed movement in the landing.** Zero of COBOL.NET's own test programs use an out-of-range
level, so the screen breaks no golden.

## Goldens the fix ships with

`negative/` for each SR arm — WORKING-STORAGE 78 (SR5), an FD-subordinate 77 (SR2), an RD-subordinate 66 (SR4), a
SCREEN-section 77 (SR6), the huge/unparseable level — plus a positive golden proving `01 K CONSTANT AS 5.` still works
and the `01`–`09` spellings pass (SR3). SR5's set is identical in 85/2002/2014/2023, so the screen is unconditional
across all four editions — assert it per edition, do not assume it.

## Batch-b3 extension (lane 3, §13.16.3) — 2026-09-04

The lane-3 adjudication of the DATA DESCRIPTION ENTRY reached this same hole from the other end and measured its §13.16.3 face, so the two rows below are added to this note rather than re-filed:

- `SR-13.16.3-1` — "A level-number is required as the first element in each data description entry." The level-number is parsed as a bare `levelNumber : INTEGERLIT` (CobolData.g4:216) and carried as an `int` on `DataDescriptionCst.Level` (line 23) with no domain screen anywhere.
- `SR-13.16.3-2` — the level-number domain itself (1–49, 66, 77, 88). Nothing in the typed-native front end tests membership, which is exactly the `78 K VALUE 5.` acceptance this note already records; the §13.16.3 rows are the general-entry statement of the same obligation.

The fix is ONE domain screen at the entry bind, not a level-78 special case — a hand-maintained list where a domain belongs is what let 82 corpus cases through (CLAUDE.md rule 5).

## Landed — 2026-09-04

`LevelNumberPass` (`src/Cobol.Net.Compiler/Validation/LevelNumberPass.cs`), a sibling to
`ExpressionFormationPass` on that pass's own stated precedent, is now the ONE place a level-number is screened. It
runs FIRST in `BinderDriver.Bind`, before any binding: the rules are pure syntax, and a level-number outside its
permitted set makes the storage tree it heads meaningless, so screening first replaces a cascade of downstream
noise — and a run-time abort — with one diagnostic at the entry.

**TWO axes, not one — and the second is what the registrar's §13.16.3 rows were about.**

- **The SECTION axis, `COBOLNET1746` `level-number-out-of-range`** — §13.18.33.3 SR2/SR4/SR5/SR6. Four
  *different* sets: 77 is legal in working-storage (SR5) and illegal in a record area (SR2); the report (SR4) and
  screen (SR6) arms admit no special level at all. A flat "1-49, 66, 77, 88" test — which is exactly what the
  legacy `CBL0815` message states — accepts `77 F-BAD PIC X(3).` under an FD. That case is now a golden.
- **The FORMAT axis, `COBOLNET1747` `level-number-entry-format`** — §13.18.33.4 GR2a/b/c ("may be used only as
  described by …"), §13.16.2's format shapes, and §13.16.3 SR1/SR2. Independent of the section axis: `78` in
  working-storage is a section violation; `05 R RENAMES A THRU B.` has a perfectly in-range level and is a format
  violation. **That one reached the EMITTER** and produced uncompilable C# (`_T_0 does not contain a definition
  for 'R'`, CS1061) — the same backend-crash shape the level-78 hole took before PB201 unmasked it. The format is
  read from the entry BODY and never from the level-number, or GR2b and GR2c would be vacuous; the level-number
  selects which check runs and the body answers it.

**The note was wrong about the blast radius, and the correction is the design.** It recorded TWO parser arms
reaching `levelNumber`; today's grammar has **FOUR** — `dataDescriptionEntry` (CobolData.g4:213),
`linkageProcedureParameter` (:197), `reportGroupEntry` (CobolReportWriter.g4:74) and `screenDescriptionEntry`
(CobolScreen.g4:31) — reaching three different binders and, for the procedure-parameter arm, none at all. Writing
the test at each site would have been four copies of one rule with a fifth guaranteed to be forgotten, so the rule
is written once and `LevelNumberArmDriftTests` derives BOTH load-bearing lists from the `.g4` files: the entry
rules that spell a level-number, and the sections that host a data description entry. A new arm fails the test
until `Classify` names it.

⛔ The drift test's first form scanned the whole pass FILE and was a **false green**: deleting the screen arm from
`Classify` left `ScreenDescriptionEntryContext` standing in the neighbouring `EntryName` switch and the test stayed
green over the hole it exists to catch. The break was injected, observed green, the test rewritten to scan only the
`Classify` region, then re-broken and observed RED before being trusted.

**`CBL0815` was NOT reused and is NOT dead.** The note called it a dead descriptor; it has a live caller in the
legacy engine (`SemanticBuilder.cs:1239`) and three legacy unit tests (`PicValidityTests`), so retiring it would
break the oracle that survives to the P15 cut-over. It is also *wrong*: its one flat set contradicts SR2, SR4 and
SR6. Importing that message into the typed-native front end would have shipped the section-blind bug the
`pb485-level-77-file-section` golden now witnesses.

**Goldens** — thirteen negatives (`tests/conformance/negative/pb485-*`), each asserted at every edition it
declares, 51 edition-cells in all. Section axis: WS 78, linkage 50, FD-subordinate 77 (SR2), RD-subordinate 66
(SR4), screen 77 (SR6), a twelve-digit unparseable level, and a missing level-number (SR1, a `COBOL0001` parse
error — the one arm enforced structurally). Format axis: a 66 with no RENAMES, a RENAMES body at 05, a RENAMES
body at 77 (GR2a), an 88 with a PICTURE, an explicit `77 FILLER`, and an omitted 77 entry-name. Three positives:
`85/pb485_level_number_legal_forms` (01–09, a bare 1, 49, 66, 77, 88), `2023/pb485_constant_entry_spelling` (the
§13.10 `01 K CONSTANT AS 5.` that is the conforming spelling of a level 78) and
`2023/pb485_entry_format_legal_forms` (every legal special-level shape). Full conformance corpus 1345/1345.

**Inventory.** SR-13.18.33.3-1..5, SR-13.16.3-1, SR-13.16.3-2 and GR-13.18.33.4-2 recorded CONFORMS — GAP
3005 → 2997. SR-13.18.33.3-6 was ALREADY OK as `DOCUMENTED-NON-SUPPORT` (Annex A.4.2 screen handling is not
claimed, kb/Work PB260) and was deliberately left alone: the screen arm is enforced, but that row's resolution is
an owner adjudication about the module, not about the level-number set.

**Found while building the goldens, NOT this mechanism:** §13.16.3 SR9's implied PICTURE (`01 W VALUE "AB".`)
is unimplemented and emits uncompilable C# (CS0103) on legal source. It is registered as
`tests/conformance/2023/pb485_value_only_format1.cob` in the manifest's **pending** list, because it is also the
only available witness for a design property of the format screen — see the landing report's new-defect paragraph.
