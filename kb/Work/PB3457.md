# PB3457 — a witness comment that derives 9 from the entry count

Low, non-blocking lead from the branch review of PB3410 (report `E:\COBOL-coord\scratch\reports\w1132c-PB3410-report.md`,
`## Review findings` R1-1; findings file `E:\COBOL-coord\scratch\review-w1132-c.jsonl`). PB3410 landed in PR #322.
Finding, verbatim:

> tests/Cobol.Net.Tests.Unit/Store/KeyedStorePerformanceWitnessTests.cs:69 The LedgerPagesAtCheckpoint doc comment
> states that 1 024 entries plus one statement's pages fill at most 8 leaves and a root, as if 9 followed from the entry
> count, but it does not: 9 is only the maximum measured for this workload.

**Fix shape (for the implementer).** Reword the comment to say the bound is the measured maximum for this workload (and
what it depends on), or derive it from the entry size and page capacity if it can be derived. The assertion PB3410 added
is not in question.

**Sites:**
- `tests/Cobol.Net.Tests.Unit/Store/KeyedStorePerformanceWitnessTests.cs:69`

## Landed

Re-probed by reading the code on the branch: the doc comment on `LedgerPagesAtCheckpoint` (PB3410 had already dropped the
"8 leaves" count) still said the entries "fill at most this many leaves and the root above them", which reads as a bound
derived from the entry count. It cannot be derived: a ledger leaf holds 4 064 / (6 + 4 + 9) = 213 entries when full, so
1 028 entries need at least 5 leaves, and the ledger is keyed by page number, so a scattered load leaves leaves half full to
full (a node merges only below a quarter page). The measured cell is the root over 8 leaves, about 60 percent full. The
comment now says the 9 is the measured maximum of this workload, what it depends on, and that it is re-measured, never
re-derived, when one of those changes. The sibling arms say the same now: the `Load` doc comment and the design 2.2.1.11
paragraph (`DESIGN-runtime-library.md`). No assertion changed.
