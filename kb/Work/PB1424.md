### `GR-8.4.3.2.4-3` — PARTIAL (adjudicator + refuter record, verbatim)

GR3 (cite.py --check 8.4.3.2.4 'the function to be activated is identified by function-prototype-name-1 in accordance with the rules specified in 12.3.8' -> OK §8.4.3.2.4 3)). UdfBindCall resolves the REPOSITORY-declared name through host.UserFunctions (the group signature table, which includes prototypes) and takes arity, formals and RETURNING from that signature. A REPOSITORY name that is also an intrinsic name dispatches to the user function. The activation names the externalized name (fn.Externalized). This was read, not probed: the udf_* goldens exercise it indirectly, and none of them is specifically about identification, so no test is named. || REFUTED: PARTIAL — Identification per 12.3.8 works for the program-unit case (AS literal alias and user function shadowing a same-named intrinsic both probe correct), but (1) a function-prototype-name in a CLASS/METHOD source element is never identified: UserFunctions is not wired for class units and the 1505 text itself says function references from class units remain a separate follow-up; (2) 12.3.8 GR11 a) identifies by EXTERNALIZED name, while the signature table is keyed by the FUNCTION-ID word, so a REPOSITORY entry naming a previous definition by its AS externalized name is refused.

## What the fixer owes

Key the group signature table by externalized name (the PB303 mapping) and wire UserFunctions for class/method units; goldens for both.
