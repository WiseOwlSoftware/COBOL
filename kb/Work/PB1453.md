# PB1453 — LANDED

## The rule (every citation re-run by the registrar through `cite.py --check`)

> the EC-PROGRAM-NOT-FOUND exception condition is set to exist and the value of the address-identifier is the predefined address NULL

`python scripts/spec/cite.py --check 8.4.3.13.4 "…"` → `OK  §8.4.3.13.4 4)  (General rules)`

## Refuter evidence — row `GR-8.4.3.13.4-4` (PARTIAL)

PARTIAL — The NULL-value half conforms on every surface. The 'EC-PROGRAM-NOT-FOUND is set to exist' half is broken on two surfaces. (1) Relation operand: with >>TURN EC-PROGRAM-NOT-FOUND CHECKING ON, the IF emits EntryOfOperand("NOSUCHP", false), so the condition is never set. EXCEPTION-STATUS stays blank, no declarative runs and execution continues. The adjudicator's note says this surface raises the fatal condition; the probe shows it does not. PtrEmitter.ProgramAddressText reads ecState.Info for the carrying statement, and inside a condition that yields no enabled entry. (2) SET surface: the condition is set, but it is processed as nonfatal. EC-PROGRAM-NOT-FOUND is Fatal in Table 13, so §14.6.13.1.3 items 5 and 7 require abnormal run-unit termination once checking is enabled, whether the USE declarative completes normally or no declarative applies. Instead SET continues with the next statement. Only the CALL-argument surface (pb239) behaves correctly (declarative, then abnormal termination).

**Code site.** src/Cobol.Net.Runtime/Control/ProgramTable.cs#EntryOf; src/Cobol.Net.Runtime/Control/ProgramRegistry.cs#EntryOfArgument; src/Cobol.Net.Runtime/Control/ProgramRegistry.cs#EntryOfOperand; src/Cobol.Net.Compiler/CodeGen/Verbs/PtrEmitter.cs#EmitSetEntry

Goldens: checked relation (declarative runs, then abnormal termination), checked SET (same); keep ec1/ok2 as the unchecked NULL witnesses.

## Re-verified 2026-09-30 (exceptions-group research, main `4a1dda60e`) — relation half REPRODUCES; root cause located

`p1453.cob` (`>>TURN EC-PROGRAM-NOT-FOUND CHECKING ON`; a `USE AFTER EXCEPTION CONDITION EC-PROGRAM-NOT-FOUND`
declarative; `IF ADDRESS OF PROGRAM "NOSUCHP" = NULL DISPLAY "REL-EQ" END-IF`) prints `REL-EQ / EC= (blank) / AFTER`,
exit 0. The runtime raise (`ProgramRegistry.EntryOfOperand(name, checkNotFound: true)` → `Set` + `CobolFatalException`)
is correct; what is missing is the ENABLED SET: `EcBinder.QueryFor` has a `BoundSetEntry` arm and the CALL
`ProgramNames` arm, and nothing for an IF (or any other statement) whose OPERAND is a program-address-identifier — so
`PtrEmitter.ProgramAddressText` renders `checkNotFound: false` and no guard exists to dispatch a raise. The same hole
covers an INVOKE argument (`BoundInvoke` queries `OoInvokeNames`/`ExternalNames` only). This is the sixth instance of
the shape kb/Work **PB1762** models (PB452, PB409, PB326, PB349/PB1036, PB233 before it).

## Landed 2026-09-30 (exceptions-batch, DEVLOG 1818)

**Fix.** `EcBinder.OperandRaisableNames` (+ the `OperandRaises` table, first row `BoundAddressOperand { Program: not null }` ->
EC-PROGRAM-NOT-FOUND) derives a statement's enabled names from the operands in its OWN `OwnValueParts()` (conditions walked to their
leaves); `QueryFor` calls it after the node-kind switch. Nested statements are deliberately NOT walked (each is its own EC region,
PB441 - a deviation from the brief, which said to recurse). `EcEmitter.FatalAmbientGates` gained `("EC-PROGRAM-NOT-FOUND", null)` so the
statement gets the try/catch for `ProgramRegistry.EntryOfOperand`'s fatal throw. Relation (IF / EVALUATE WHEN / PERFORM UNTIL) and INVOKE-argument
surfaces both raise now (main build: `MISS NULL / EC1=` blank). Golden `2002/pb1453_program_address_operand_not_found`;
`FatalRaiseSelectionTests` x5 (abnormal arms, checking-off witness); `OperandRaiseNamesDriftTests` (every declared name has a gate row).
**Not done (PB1762/PB1037):** folding the four `ContainsIntrinsic` ambient gates into the same walker. Side effect: a CALL/SET statement with
EC-PROGRAM-NOT-FOUND enabled now also carries a dead `catch (CobolFatalException ... EC-PROGRAM-NOT-FOUND)` (harmless text).
