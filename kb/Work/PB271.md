# PB271 — the float receiver that could not notice an overflow

Found by the arithmetic-wave review fleet over the D-B/D-C/PB194/PB195 working tree, 2026-08-31, and fixed in the change set that landed the wave. Every number below was re-derived independently by the implementer (a 34-digit emulation of `CobolDec.cs` validated against the shipped `pb167` goldens, and 80–120-digit `Decimal` truth) BEFORE the confirming run, and then confirmed by it.

## The rule

`cite.py --check 14.9.25.4 "If the algebraic value of the sending operand is farther from zero than is permitted
by the usage specifications of the receiving data item, the EC-DATA-OVERFLOW exception condition is set to exist,
and the content of the receiving data item is undefined"` → **OK** (§14.9.25.4 GR **6 d) 4. a.** — not "GR4 step
4a", which five sites in this repo had inherited and which is the elementary-move definition; all five are
corrected in this change set).

## The mechanism

`MoveEmitter`'s float arm rendered `NumericRenderer.Real(...)` first, which for a decimal sender is
`(...).ToDouble()`. An SDIDI reaches ±9.999…E+6144, twenty decades past binary64 — so the magnitude was already
±Infinity by the time either check ran, and neither could fire. Pre-existing under `ARITHMETIC IS
STANDARD-DECIMAL`; owner decision D-B made a float literal past binary64 legal in the DEFAULT mode, which put a
decimal128 sending value in front of a binary64 receiver in ordinary programs for the first time.

## Measured, before and after

```
>>TURN EC-DATA-OVERFLOW CHECKING ON        BEFORE                 AFTER
MOVE 1.0E+400 TO <FLOAT-BINARY-64>         stores +Infinity       EC-DATA-OVERFLOW (fatal)
MOVE 1.0E+400 TO <FLOAT-BINARY-32>         stores +Infinity       EC-DATA-OVERFLOW (fatal)
MOVE 1.0E+400 TO <FLOAT-LONG>              stores +Infinity       EC-DATA-OVERFLOW (fatal)
MOVE 1.0E-400 TO <FLOAT-BINARY-64>         stores 0               stores 0  (not this EC)

checking OFF (the default)                 stores ±Infinity       stores ±Infinity  (unchanged)
```

## The fix, and its scope

`CobolFloat.StoreChecked(CobolDec, single)` tests the ALGEBRAIC value — it must hold the `CobolDec`, because
after `ToDouble` the magnitude is gone. A `CobolDec` has no infinity, so `IsInfinity` on the CORRECTLY-ROUNDED
conversion is exactly "farther from zero than the usage permits"; a `> MaxValue` comparison would be wrong,
since a value between the maximum and the next representable magnitude rounds back to the maximum.

GR6 d)4.a binds a receiver *"described with a standard floating-point usage"* — FLOAT-BINARY-32/-64 here. For
COMP-1/COMP-2/FLOAT-SHORT/-LONG/-EXTENDED §14.6.8.3 rule 1 says instead *"the implementor specifies any exception
conditions that might be set to exist during data conversion"* (cite.py-verified), and COBOL.NET's determination
is the SAME condition — one rule for every float receiver. The single-precision arm has raised it for COMP-1
since D21, so this makes the family consistent rather than adding a second regime.

## Severity, honestly

§14.6.13.1.1 makes checking off by default, and GR6 d)4.a itself makes the receiver's content undefined in this
case — so a default build was never non-conforming, and ±Infinity remains what it stores. The breach was
confined to a program that enables the check, where a FATAL condition the standard mandates was silently skipped
and no `USE AFTER EXCEPTION CONDITION EC-DATA-OVERFLOW` declarative could fire. Both halves are now pinned:
`ec_data_overflow` (checking ON) and the new `pb271_float_receiver_overflow` (checking OFF — the store behaviour
a default build actually sees).
