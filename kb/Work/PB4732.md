# PB4732 - cobc 3.2 converts a double to decimal lossily

Filed 2026-11-04 as an upstream candidate from the determination of PB4622 (wave 20261870 a). Nothing is posted: upstream status `unreported`, the tracker has not been searched, and the report standard (memory: report-standard, use-sf-ticket-cache) applies before anything is filed. Evidence outside git on one machine: `E:/COBOL-coord/scratch/op-w20261870/a/p/` (`p2.gnu.txt`, `p4.gnu.txt`, `p5.gnu.txt`) and `E:/COBOL-coord/scratch/op-w20261870/clerk/u1.cob`.

## Minimal test case

Free reference format, `u1.cob`:

```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. U1.
DATA DIVISION.
WORKING-STORAGE SECTION.
01 DN   USAGE FLOAT-LONG VALUE -2.5E+40.
01 X5   PIC 9(5).
PROCEDURE DIVISION.
    MOVE DN TO X5
    DISPLAY X5
    STOP RUN.
```

## Environment

- `cobc (GnuCOBOL) 3.2.0`, WSL2 Ubuntu on Windows 11.
- `cobc -x -free -std=cobol2014 -o u1g u1.cob && ./u1g`

## Observed result

```
49088
```

The same lossy intake shows in the other probes: `FLOAT-LONG 0.1` enters a decimal expression as `+0.0999999999999999916` (p5 S04), `A1 + A2` over 0.1 and 0.2 stores `+0.2999999999999999750` (p2 G01), and `FUNCTION REM (0.7 0.1)` stores `+0.0000000000000000138` where the items' binary64 values leave `+0.0999999999999999222`.

## Expected result (per ISO)

The binary64 `-2.5E+40` is exactly -25000000000000000155002161260194579873792 (Python `Decimal(-2.5E+40)`). ISO/IEC 1989:2023 §2023:14.6.8.2 4), checked with `scripts/spec/cite.py --check`: "If the receiving operand is a fixed-point numeric item, the data is aligned by decimal point and is transferred to the receiving digits with zero fill or truncation on either end as required." Keeping the five low-order integer digits of that value gives 73792. §2023:8.8.1.5.1 leaves the mechanism of conversion of a float item into a standard-decimal intermediate to the implementor, so a derived value in an expression is latitude, but a MOVE into a fixed-point item takes the item's value and has none.

Edition as recorded: 2014. FLOAT-LONG exists from 2002, and `-std=cobol2014` is the edition the probe claimed.

## Class

Wrong output (a lossy conversion of a binary64 value to decimal on a MOVE).

## Our compiler (WiseOwl)

`MOVE DN TO X5` stores 73792 (p2 A04), the binary64's exact digits. Related: PB4622 (a function over a float item must land the same value), PB4731 (whether float-item arithmetic follows the exact sum).

## Draft issue

**Title:** MOVE of a FLOAT-LONG item to a PIC 9(5) item stores 49088 for the binary64 value -2.5E+40, whose exact digits end 73792

GnuCOBOL 3.2.0, `cobc -x -free -std=cobol2014`. A `FLOAT-LONG` item holding -2.5E+40 (the binary64 value is exactly -25000000000000000155002161260194579873792) is moved to a `PIC 9(5)` item:

```cobol
01 DN   USAGE FLOAT-LONG VALUE -2.5E+40.
01 X5   PIC 9(5).
    MOVE DN TO X5
    DISPLAY X5
```

The program displays `49088`. Truncating the item's exact value to the receiving digits (ISO/IEC 1989:2023 14.6.8.2 4)) gives `73792`. The conversion from a double to a decimal is lossy; the same loss shows when FLOAT-LONG 0.1 enters a decimal expression as 0.0999999999999999916.
