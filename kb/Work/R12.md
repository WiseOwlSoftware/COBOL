# R12 — a BinaryCapacity item crossing the CALL boundary as its picture-digit image silently truncates a beyond-picture value

Found while landing R10's COMP-5 half (2026-08-08). A `Digits > 18` numeric leaf — and, since R10, an unsigned
8-byte COMP-5 leaf (`ulong` carrier) — crosses the CALL boundary as a STRING carrier built from
`OperandText.FieldImage` → `CobolNum.FormatDisplay`, which renders the **picture-digit image**: the value modulo
10^Digits. A BinaryCapacity item legitimately holds values beyond its picture digits (it owns its full container
range, ISO §13.18.60.4 GR12 — the R10 owner decision), so a `CALL … USING` BY REFERENCE argument of, say,
`PIC 9(18) COMP-5` holding 2^64−1 arrives in the callee as the low 18 digits, and the copy-back at activation
end writes the truncated value over the caller's item. §14.2.3 GR8 says BY REFERENCE "operates as if the
[formal] occupies the same storage area as the argument" — the image round trip must therefore be lossless for
every value the item can hold.

**Shape of the fix (design question, not a patch):** the string ABI for a BinaryCapacity leaf must carry the
CONTAINER value, not the picture image — either the full-container digit string (max 39 digits) with the formal
side parsing it back through the U-lane, or a native binary crossing (the container bytes). Sweep the whole
`CallPlaceIsString` family: the caller carrier, `ArgAdaptNum`'s profile-driven leg, the callee copy-in/copy-out,
and RETURNING delivery. The V59ImagePredicateDriftTests read/write lockstep applies.

Not blocked; reachable only by a program that both stores a beyond-picture value into a COMP-5 item and passes
that item BY REFERENCE/CONTENT — no corpus program does today, which is why this is MINOR despite being a
silent wrong answer.
