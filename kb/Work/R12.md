# R12 — a BinaryCapacity item crossing the CALL boundary as its picture-digit image silently truncates a beyond-picture value

Found while landing R10's COMP-5 half (2026-08-08). A `Digits > 18` numeric leaf — and, since R10, an unsigned
8-byte COMP-5 leaf (`ulong` carrier) — crosses the CALL boundary as a STRING carrier built from
`OperandText.FieldImage` → `CobolNum.FormatDisplay`, which renders the **picture-digit image**: the value modulo
10^Digits. A BinaryCapacity item legitimately holds values beyond its picture digits (it owns its full container
range, ISO §13.18.60.4 GR12 — the R10 owner decision), so a `CALL … USING` BY REFERENCE argument of, say,
`PIC 9(18) COMP-5` holding 2^64−1 arrives in the callee as the low 18 digits, and the copy-back at activation
end writes the truncated value over the caller's item. §14.2.3 GR8 says BY REFERENCE "operates as if the
[formal] occupies the same storage area as the argument" — the image round trip must therefore be lossless for
every value the item can hold.

**Shape of the fix (design question, not a patch):** the string ABI for a BinaryCapacity leaf must carry the
CONTAINER value, not the picture image — either the full-container digit string (max 39 digits) with the formal
side parsing it back through the U-lane, or a native binary crossing (the container bytes). Sweep the whole
`CallPlaceIsString` family: the caller carrier, `ArgAdaptNum`'s profile-driven leg, the callee copy-in/copy-out,
and RETURNING delivery. The V59ImagePredicateDriftTests read/write lockstep applies.

Not blocked; reachable only by a program that both stores a beyond-picture value into a COMP-5 item and passes
that item BY REFERENCE/CONTENT — no corpus program does today, which is why this is MINOR despite being a
silent wrong answer.

## LANDED 2026-08-08 — and the measured defect was WORSE than this note claimed

**The note's premise needed correction before anything else** (probe at `e37cb1d8`): the string-ABI crossing
for wide/unsigned native leaves was not "silently truncating" for BY REFERENCE — it was UNCOMPILABLE. The
caller's `ManagedPointer<string>.OverField` write lambda assigned the cell's string to the native field
(CS0029), and the CALLEE side hardcoded a `ManagedPointer<long>` cell while its own binder emitted
carrier-typed reads against it (CS1503 for ulong/UInt128 formals). The two ABI sides had never agreed for
the wide tiers; only the BY CONTENT READ half (picture-digit `FormatDisplay`, lossy) matched the note's
silent-truncation description.

**The fix is design (B) — NATIVE carrier crossing end-to-end, no image, no codecs (the typed-native
doctrine):**
- `CallPlaceIsString` drops the `Digits > 18` and ulong-tier legs — every native fixed-point leaf crosses in
  a cell of its OWN carrier (`CallNumCarrier` = `ElementType`), read AND written by the same aliasing
  lambdas that always worked for `long`.
- `CobolArgAdapt.Num`/`NumValue` are GENERIC over the carrier (`INumberBase<T>`), with a
  `ReadNumericCell`/`WriteNumericCell` pair spanning the four carriers for cross-carrier and string-cell
  views (the D5 boundary unchanged; conversions ride the Int128 lane with the R10 bits contract at the
  UInt128 ends, so same-carrier crossings are lossless by construction). `StoreReturn` gains the typed
  overloads (the UInt128 one renders its own text before the bits reinterpretation).
- The callee's formal cell type IS the formal's `ElementType`, seeded by `PicInfo.DefaultInitializer` (cell
  and seed cannot drift); `ArgAdaptNum`/`ArgAdaptNumValue` emit the type argument.
- A 19+-digit numeric LITERAL argument was a LOUD stage — now a typed `Int128`/`UInt128` cell.

Probes after: the 8-byte container max survives the BY REFERENCE round trip
(`W18-AFTER=18446744073709551615`); the callee's `ADD 1` through a UInt128 cell reaches the caller
(`W19-AFTER=…6`). Golden `call_by_reference_wide_comp5` (2023). The callee's own DISPLAY of a
beyond-picture formal still shows the picture-digit image — that is [[R13]]'s latitude question, not a
crossing loss.
