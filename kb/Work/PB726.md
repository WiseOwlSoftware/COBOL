# PB726 — OPEN — the roster exists, it is verbatim, and nothing reads it

The [[PB688]] implementer found three separate missing 2023 edition gates in about ten minutes by reading the
Foreword's main-changes list and asking `constructs.json` whether each bullet had a row. Train 14's lander called
this the most valuable of the nine findings it collected. **The gap is now measured rather than asserted.**

## Three hazards measured, each of which makes the naive implementation silently green

⛔ `feedback_green_gates_arent_evidence` — a roster checker that never actually reads the roster passes forever.

1. **The Foreword is not addressable by `cite.py`.** `python scripts/spec/cite.py --check Foreword "The main
   changes are as follows"` → `FAIL: there is no clause §Foreword in the transcription`, and
   `--find "An optional Commit and rollback processing facility …"` → `NO CLAUSE contains …`. `cite.py` indexes
   numbered clause regions only. [[PB688]]'s landed note already records this. **Consequence:** the drift test
   must key on the transcription's own line region (the `The main changes are as follows:` line through the
   paragraph at 1133), and `audit_code_citations.py` can never validate a Foreword quote — so every roster claim
   the test makes has to be pinned by the test's own fixture, not by the citation auditor. Where a numbered
   citation exists it should be preferred: Annex E.2 item 5 and Annex E.3.3 items 16/38 cover the directive group
   and **do** `--check` OK (see [[PB725]]).
2. **The transcription splits the first group across two page breaks and the split DROPS the list markup.**
   Lines 1087–1095 are markdown list items (`  - — …`); lines 1103–1112, after the `---` markers at 1097 and
   1100, are bare `— …` lines at column 1 with no list prefix and no group heading of their own. A parser that
   walks markdown list nodes sees **9** bullets in the general-enhancements group instead of **19**, silently
   under-counts by ten, and reports a clean roster while missing Line Sequential, COMMIT/ROLLBACK, PICTURE
   EDITING and seven more. The test must parse the em-dash lines in the region, not the markdown list structure —
   and it must assert the total (34) so a re-transcription that changes the shape fails loudly instead of
   shrinking.
3. **The roster is a FLOOR, never a ceiling, and the standard says so.** The Foreword itself closes with *"For
   more details and additional changes, see E.2 … and E.3"*. Six of the 26 `introducedIn: 2023` rows in
   `constructs.json` today have no Foreword bullet at all — `goback-status-2023`, `continue-after-2023`,
   `write-before-and-after-advancing-2023`, `options-initialize-2023`, `inline-method-invocation-2023`,
   `sync-on-group-2023`. So the assertion is **one-directional**: every bullet shall map to something; a row
   without a bullet is normal and shall not fail.

## The bullet that proves a literal match is not enough — verified against the canonical page

Bullet #2 reads *"The PERFORM statement has been enhanced to specify a time period for pausing the program"*, and
there is no such PERFORM format: a grep for `pausing` in the whole transcription returns only line 1091, and no
PERFORM clause carries a SECONDS phrase. The construct is `CONTINUE AFTER arithmetic-expression SECONDS`
(§14.9.9 — `cite.py --check 14.9.9 "CONTINUE"` → OK; `constructs.json` row `continue-after-2023`, citation *"ISO
§14.9.9.2 / §14.9.9.4 GR1; Annex E.3.3 item 14"*).

**This is NOT a transcription defect.** Rendered off the canonical PDF rather than trusted
(`python scripts/render-spec-page.py 26` → PDF page 26 / printed folio xxvi, read as an image): the printed
Foreword says *"The PERFORM statement has been enhanced to specify a time period for pausing the program"*,
verbatim. The standard's own Foreword is loose about which statement carries the feature. Therefore the roster
map **must be an adjudicated table with a cited justification per entry**, checked in and reviewed — a keyword or
fuzzy match would either mis-bind this bullet to a PERFORM row or report a false gap forever.

## The fix shape

A drift test beside the other version-matrix drift tests (`ConstructRegistryDrift`, `VersionMatrix`), reading the
roster region of `specs/ISO_COBOL.md` and asserting, for each of its 34 bullets, exactly one of:

- a `tests/version-matrix/constructs.json` row id, or
- an `IntrinsicCatalog` entry name, or
- a **named exemption carrying a one-line cited justification** (e.g. EC-I-O-WARNING: an exception condition, not
  a construct — it is gated by the EC table, cite the clause).

The map lives beside the test as data; the test asserts (a) the bullet COUNT, so a re-transcription cannot shrink
the roster silently, (b) that every bullet is mapped, and (c) that every mapped id still exists. It must NOT
assert the converse (hazard 3). ⛔ `feedback_prove_the_watchdog_fails` — before it is trusted, delete one row
from the map and one row from `constructs.json` and watch it go red in both directions; a roster test that has
never failed is hazard 2 wearing a green tick.

⛔ This is a mechanically-derived check over the spec, in the same family as the rule catalog → traceability
inventory → burn-down and `constructs.json` itself. It is NOT a new work register (CLAUDE.md rule 8): it produces
failures, and each failure becomes a `kb/Work/` note the ordinary way.

## Why it matters

Every one of [[PB688]] (landed, LINE SEQUENTIAL had no gate), [[PB725]] (PUSH/POP/DISPLAY have no gate) and the
coverage residue in [[PB724]] was found by a human reading this list once. The list will not be read again unless
something reads it. `feedback_green_test_can_hold_a_gap_open`: a version matrix that never contradicts the
standard's own change list reads as a version matrix that is finished, and the mission bar (owner decision D13 —
four per-edition compilers validated by the VERSION TEST MATRIX) is exactly the claim this check is evidence for.
⛔ A note on the clause number, because rule 1 is about INHERITED citations and this one WAS inherited, five
times: the mission bar was spelled *"100% conforming to ISO/IEC 1989:2023 per §4.2.16"*, and
`cite.py --check 4.2.16 "An implementation shall satisfy the user documentation requirements"` → **OK §4.2.16
(User documentation)** — a genuine conformance criterion, but the DOCUMENTATION one, not the definition. The
clause that defines it is §4.2.1: `--check 4.2.1 "To conform to this Working Draft International Standard, an
implementation of standard COBOL shall provide the required normative elements specified in Clause 6, Reference
format through Clause 16, Standard classes"` → **OK §4.2.1 (General)**, and its full sentence ends *"…and
optionally meet the normative elements identified in A.4, Optional language element list, and meet the criteria of
4.2.2 through 4.2.17"* — which is D13's shape exactly, §4.2.16 included as one criterion among sixteen.
**Repaired 2026-09-06** in `CLAUDE.md`, `PROMPT.md` and `docs/COBOLNET_REARCHITECTURE_PLAN.md` (three sites, D13's
own row among them). The dozen other §4.2.16 references in `docs/` mean the user-documentation obligation and are
CORRECT — `docs/CONFORMANCE.md` **is** the §4.2.16 record; they were read and left alone.
