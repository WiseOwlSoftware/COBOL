# PB295

Found while landing [[PB183]] (2026-09-01).

**THE OBSERVATION.** All 21 rows of §13.18.60.3 in `tests/version-matrix/traceability-inventory.json` read
`state: GAP` with an empty `code-location` — *including* rules the compiler visibly enforces, each with its own
diagnostic and message quoting the rule:

| rule | enforced at |
| --- | --- |
| SR3 | `PictureAnalyzer.cs` (`+ "item — PICTURE {picture} is alphabetic/alphanumeric (ISO §13.18.60.3 SR3)"`) |
| SR5 | `PictureAnalyzer.cs`; `DataBinder.cs` (the USAGE BIT / boolean-picture arms) |
| SR10 | `ExpressionBinder.cs`, `AcceptDisplayBinder.cs`, `DataBinder.Reports.cs` — the index-data-item reference list |
| SR12 | `PictureAnalyzer.cs`, `DataBinder.cs` — the national-picture restriction |
| SR13 | `BitLayout.cs`, `PicInfo.cs` — the implied-USAGE rules |
| SR20 | `PictureAnalyzer.cs` — "only the NATIONAL phrase … PICTURE contains 'N'" |

`grep -rn '13\.18\.60\.3' --include=*.cs src/` returns ~30 hits across those files. This is not a small residue:
one clause's worth of landed conformance work is recorded as not done.

**WHY IT MATTERS BEYOND ONE CLAUSE.** The inventory is the PHASE-14 completion measure ("Done = the Step-0
traceability inventory at zero GAP"). A GAP row that means "nobody has adjudicated this yet" and a GAP row that
means "this is unimplemented" are indistinguishable in the file, and the burn-down counts them the same way. The
practical consequence is the [[a_dead_lookup_is_also_unverified]] shape at scale: PB183's analysis could not use
the inventory as evidence for ANY enforcement claim and had to re-derive every one by grepping `src/` — which is
exactly the hand-derivation the register exists to prevent. Some quantity of the 3,633 remaining GAP rows is
work already in the tree.

**WHAT THIS NOTE IS NOT.** It is not a proposal to bulk-flip rows. Each verdict needs its own `code-location` and
`test-ref`, and `SpecTraceabilityInventoryDriftTests` checks those resolve — that gate is the reason a sloppy
sweep would be caught, and also the reason a sweep is real work rather than a script.

**REPRO / MEASUREMENT.**

```
python -c "import json; rows=json.load(open('tests/version-matrix/traceability-inventory.json'))['rows']; \
  print([ (r['rule-id'], r['state']) for r in rows if r['section']=='13.18.60.3' ])"
grep -rn '13\.18\.60\.3' --include=*.cs src/ | wc -l
```

**PROPOSED SHAPE OF THE FIX (a measurement first, not a flip).** The mechanical part is derivable: every
`ISO §<clause> SR<n>` citation already in `src/` names a rule whose row could be *proposed* for adjudication,
with the citing file/symbol as the candidate `code-location`. A script that emits that candidate list — clause,
rule, citing sites, and whether any corpus fixture's `.err` names the diagnostic emitted there — turns "3,633
GAP rows, provenance unknown" into "N rows with code pointing at them, awaiting a verdict" and M with nothing.
That is the same derived-from-the-spec shape the rule catalog and the inventory already have, and it is a
generated view rather than a hand list. Rows would still be adjudicated one batch at a time through
`record_verdicts.py`.
