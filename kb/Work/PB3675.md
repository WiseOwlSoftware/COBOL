# PB3675 — PublishHolder's null hides which failure happened

**Sites:** `src/Cobol.Net.Runtime/IO/IHostMedium.cs` (`IHostMedium.PublishHolder`, `HostMedium.PublishHolder`),
`src/Cobol.Net.Runtime/IO/Sharing/SequentialJournal.cs` (`SequentialJournal.Begin`), `tests/Cobol.Net.Tests.Unit/FaultHostMedium.cs`
(`FaultHostMedium.PublishHolder`, `FaultHostMedium.PublicationAnswer`), `docs/rearchitecture/DESIGN-runtime-library.md` (2.2.2.5 R1);
`RegionLockResult` is the value carried.

Filed 2026-10-24 by the enqueue unit's clerk from two leads on the same mechanism. Not re-probed; both are code
readings by the people named.

## What happens

`HostMedium.PublishHolder` (`IHostMedium.cs:92`) now discards the `RegionLockResult` that tells two failures apart: an
unsupported host (the sidecar cannot hold a holder at all) and a lost-race burst (`Held`: every try lost its race to
another process). It returns `null` for both. `SequentialJournal.Begin` (`SequentialJournal.cs:184`) throws "the host
cannot hold a transaction's holder" for `null`, which is false for the lost race. The `IHostMedium.PublishHolder`
summary does not say that `null` covers both causes.

## Leads folded here

- Wave 20261032 group H implementer (PB3614, branch `worktree-wf_6ffe8083-b46-17`, PR #534 merged), `results[7]`, "R1-2
  (not fixed, needs a contract change)": the fix is to carry the `RegionLockResult` through `IHostMedium.PublishHolder`.
- Group G reviewer (PB3632, branch `worktree-wf_6ffe8083-b46-29`, PR #536 merged), R1-2 LEAD (low), report
  `E:\COBOL-coord\scratch\reports\w20261032g-PB3632-report.md`: the same site, same words.

## Fix shape

Return the `RegionLockResult` (or a small result type that names unsupported-host and lost-race) from `PublishHolder`,
have `Begin` choose its message and exception disposition from it, and update the interface summary. Sweep the other
callers of `PublishHolder` for the same collapse of two causes into `null`.

## Landing

Re-probed on a fresh build: `SequentialJournal.Begin` over the production medium with every publication try lost
(`SidecarLockFiles.RaceInjector`) threw "the host cannot hold a transaction's holder" (the new journal-level witness was red, 1 of 3).
`IHostMedium.PublishHolder` now returns the publication's `RegionLockResult` with the holder in an `out` parameter (the vocabulary
`SidecarLockFiles.Publish` has had since PB3632), and `Begin` refuses with a message for the cause that happened: `Held` says every
try lost its race to another run unit's removal of the lock directory, `Unavailable` keeps "the host cannot hold" (DOC-A.1-75). The
disposition stays one `IOException`, the statement's '30' with the file unaffected (§9.1.13.6 item 1; §14.9.27.4 GR25), because
Publish already paces and retries twelve times and no other I-O status names a transient failure to begin a transaction. Sibling
sweep: the other `Publish` callers (`SidecarColumnLockHost`, `SidecarRegionLocks`) took the result at PB3632;
`HandleColumnLockHost` and `PhysicalFileTable` already carry `RegionLockResult`. For the next implementer:
`FaultHostMedium.PublicationAnswer` answers a publication `Held` or `Unavailable` without publishing, and
`SequentialJournalHolderPublicationTests` runs the real race through `RaceInjector`.
