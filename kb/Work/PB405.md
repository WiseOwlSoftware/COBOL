# PB405 — a `break` written for the dispatcher's switch, bound by C# to the nearest loop

## 1. The mechanism

`StatementEmitter.Visit(BoundExitParagraph)` (`src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:112`) emits
`__pc = CurrentPc + 1; break;` and `Visit(BoundExitSection)` (`:121-129`) emits
`__pc = SectionEndPc + 1; if (__exitPc == SectionEndPc) return __pc; break;`. Both `break`s are written to
leave the dispatcher's `switch (__pc)` in `DispatchEmitter.EmitDispatchMethod`. **C# binds `break` to the
innermost enclosing breakable statement**, and an inline PERFORM lowers to a real C# loop
(`ControlFlowEmitter.EmitPerformLoop`, `src/Cobol.Net.Compiler/CodeGen/Verbs/ControlFlowEmitter.cs:234-246`). So an EXIT PARAGRAPH or EXIT SECTION written
inside an inline PERFORM breaks THAT LOOP, not the dispatch.

For EXIT PARAGRAPH the effect is a **silent degradation to EXIT PERFORM**: the loop is left, the rest of the
current paragraph then executes, and the paragraph's fall-through epilogue overwrites `__pc` with
`CurrentPc + 1` — the same value the statement set, so the transfer coincidentally survives while the skip
does not.

For EXIT SECTION it is **worse**: the fall-through epilogue overwrites the `__pc = SectionEndPc + 1` the
statement set, so the section-exit target is discarded and every remaining paragraph of the section runs too.

This is the two-arm dispatch shape at its most literal — a statement-level arm that was reasoned about and an
inside-a-loop arm that never was. The statement-level behaviour is genuinely correct, which is why nothing
caught this: the only EXIT PARAGRAPH test is `ControlFlowDifferentialTests.ExitParagraph`, a `DifferentialGolden`
pinned to the legacy oracle (barred from closing a row), and the two `SectionDifferentialTests` cases that ARE
spec-derived both place EXIT SECTION at statement level.

## 2. The rules, quoted, each `--check`ed on this tree

    python scripts/spec/cite.py --check 14.9.14.4 "an implicit CONTINUE statement immediately following the last explicit statement of the current paragraph"
      -> OK  §14.9.14.4 6)  (General rules)
    python scripts/spec/cite.py --check 14.9.14.4 "an unnamed empty paragraph immediately following the last paragraph of the current section"
      -> OK  §14.9.14.4 7)  (General rules)

Both rules end "preceding any return mechanisms for that paragraph / section", and the NOTE between them says
those return mechanisms are the ones associated with PERFORM, SORT and USE. **An inline PERFORM is not one of
them** — it is not a return mechanism at all, it is a loop inside the paragraph — so neither rule gives an
inline PERFORM any standing to intercept the transfer. That is the whole derivation.

## 3. Expected vs observed — RE-MEASURED ON HEAD (89044aa0), both rules

    $ cobol.exe gr6-inline.cob --std 2023 --run
      IT 1 / IT 2 / TAIL-MAIN / NEXT                                                              [exit 0]

`gr6-inline.cob` is `MAIN-P.` containing `PERFORM VARYING I FROM 1 BY 1 UNTIL I > 3 / DISPLAY "IT " I /
IF I = 2 EXIT PARAGRAPH END-IF / END-PERFORM / DISPLAY "TAIL-MAIN".` followed by `NEXT-P. DISPLAY "NEXT".`
Expected per GR6: control passes to the implicit CONTINUE after the LAST EXPLICIT STATEMENT of MAIN-P, so
`TAIL-MAIN` is skipped — `IT 1 / IT 2 / NEXT`. Observed: `TAIL-MAIN` runs. The generated `case 0` is verbatim

    while (!(I > 3L)) { WriteLine("IT " + ...); if (I == 2L) { __pc = 1; break; } __pcont0: ; I = I + 1; }
    __pexit0: ;
    System.Console.WriteLine("TAIL-MAIN");
    __pc = 1;
    break;

— the `break` leaves the `while`, not the `switch`.

    $ cobol.exe gr7-inline.cob --std 2023 --run
      IT 1 / IT 2 / TAIL-S1A / S1B / S2A                                                          [exit 0]

`gr7-inline.cob` puts the same inline PERFORM in `S1-A` of section `S1`, with `DISPLAY "TAIL-S1A".` after
END-PERFORM, then `S1-B. DISPLAY "S1B".` and `S2 SECTION. S2-A. DISPLAY "S2A".` Expected per GR7: control
passes to the unnamed empty paragraph after S1's LAST paragraph, so both `TAIL-S1A` and the whole of `S1-B` are
skipped — `IT 1 / IT 2 / S2A`. Observed: both run. The generated `case 0` shows the overwrite exactly:

    if (I == 2L) { __pc = 2; if (__exitPc == 1) return __pc; break; }   // §14.9.14.4 GR7 ...
    ...
    __pexit0: ;
    System.Console.WriteLine("TAIL-S1A");
    __pc = 1;                      // <- the fall-through epilogue discards the __pc = 2 above
    break;

## 4. The code site and the shape of the repair

- `src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:112` — `Visit(BoundExitParagraph)`.
- `src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:121-129` — `Visit(BoundExitSection)`, the `break` at `:127`.
- `src/Cobol.Net.Compiler/CodeGen/DispatchEmitter.cs#EmitDispatchMethod` — the `switch (__pc)` the `break` was
  written for.
- `src/Cobol.Net.Compiler/CodeGen/Verbs/ControlFlowEmitter.cs:234-246` — `EmitPerformLoop`, the C# loop that
  intercepts the `break`, and the `__pexit{id}` / `__pcont{id}` labels it already plants.

**⛔ THE REPAIR IS STRUCTURAL, NOT A THIRD SPECIAL CASE.** The bug is that *leaving the dispatcher* is spelled
as a raw C# `break` at four separate emit sites while *leaving a PERFORM* is correctly spelled as a `goto` to a
planted label. `Visit(BoundExitPerform)` already knows this — its own comment says a bare `break`/`continue`
exits only the innermost C# loop and is wrong for a multi-level VARYING (CA31/CA32), which is why the inline
arm emits `goto __pexit{id}` / `goto __pcont{id}`. **The same reasoning was never applied to the statements
that need to leave the dispatcher.**

The shape that makes the next loop-shaped container automatic: give the dispatcher **one planted exit label per
paragraph body** (`__dispatch{pc}:` immediately after the paragraph's statements, before the epilogue) and emit
`__pc = <target>; goto __dispatch{pc};` from every statement that transfers control out of the current
paragraph — EXIT PARAGRAPH, EXIT SECTION, NEXT SENTENCE's last-sentence arm (PB414), GO TO, and
`BoundExitPerform`'s `_ =>` fallback (PB403). A `goto` cannot be captured by an intervening loop, so the next
container the emitter learns to lower is correct by construction instead of by review — and the epilogue's
unconditional `__pc = CurrentPc + 1` must move *after* that label so it can no longer overwrite a target that
was deliberately set.

Pair it with a drift test that compiles each transfer statement **inside** an inline PERFORM and asserts the
emitted C# contains no bare `break;` between the loop's opening brace and its close.

## 5. The sibling sweep the fixer must do

- **Every `w.Line("break;")` in `StatementEmitter` and `DispatchEmitter`** aimed at the dispatcher switch. The
  known set today is `Visit(BoundGoTo)` (`:110`), `Visit(BoundExitParagraph)` (`:112`),
  `Visit(BoundExitSection)` (`:127`), `Visit(BoundExitPerform)`'s `_ =>` arm (`:143`),
  `Visit(BoundNextSentence)`'s null-label arm (`:207`) and the RESUME pc-jump inside
  `Visit(BoundContinueAfter)`. **GO TO inside an inline PERFORM is ALREADY BROKEN THE SAME WAY, measured on
  HEAD**, and it is the commonest of the three: `MAIN-P.` holding `PERFORM VARYING I ... IF I = 2 GO TO TARGET-P
  END-IF END-PERFORM DISPLAY "TAIL-MAIN".` with `MID-P.` and `TARGET-P.` after it prints
  `IT 1 / IT 2 / TAIL-MAIN / MID / TARGET` where the transfer requires `IT 1 / IT 2 / TARGET`; the emitted
  `case 0` is `... if (I == 2L) { __pc = 2; break; } ... __pexit0: ; WriteLine("TAIL-MAIN"); __pc = 1; break;`
  — the same captured `break` and the same epilogue overwrite. **That row belongs to the GO TO lane, not to this
  note**, and is reported to the registrar so it gets an owner; it is recorded here because it is the strongest
  argument that the repair must be structural.
- **Every other C# container the emitter lowers to a breakable statement**, not just inline PERFORM:
  `switch` for EVALUATE, SEARCH's loop, the F3 PERFORM's try/finally region. A transfer statement inside an
  EVALUATE WHEN arm inside a paragraph is the same conjunction.
- **The `if (__exitPc == SectionEndPc) return __pc;` guard** is correct today only because it executes before
  the `break`; under the repair it becomes an ordinary part of the paragraph exit and should be re-derived, not
  moved verbatim.
- **PB403 and PB414 are the same emitter defect** reached by two other routes; land the three together or the
  drift test will pass on one arm while the others regress.

## A FIFTH site, measured by the b2 registrar's cross-file writer — 2026-09-04

`RESUME AT` from a SEARCH declarative reached from inside an inline PERFORM is **lost** the same way: it prints
`AFTER-PERFORM` where the un-nested control transfers correctly to `R-PARA`. That is the `GR-14.9.37.4-1` row,
whose verdict batch b2 records under `PB388` — the row stays there, but the MECHANISM is this note's, and the
emitter sites it reaches are `StatementEmitter.cs` (`BoundGoTo`), `ControlFlowEmitter.cs` (the SEARCH EC
dispatch), `BoundExitSection` and `BoundNextSentence`'s fallback.

⭐ **So the family is five sites, not two, and it is ONE repair.** `PB405` (EXIT PARAGRAPH / EXIT SECTION) ·
`PB413` (GO TO out of an inline PERFORM) · `PB414` (NEXT SENTENCE's last-sentence arm) · `PB403`'s
`BoundExitPerform` fallback · and this SEARCH `RESUME AT`. Every one of them spells "leave the dispatcher" as a
raw C# `break`, which binds to the innermost lowered loop rather than to the paragraph dispatcher, while "leave
a PERFORM" is correctly spelled as a `goto` to a planted label. **A landing that fixes one verb and leaves the
others on `break` is the same defect a third time.** The repair is a per-paragraph dispatcher-exit label with
the fall-through epilogue moved after it, plus a drift test asserting that no bare `break;` survives inside a
lowered loop.
