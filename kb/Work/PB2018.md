# PB2018 — LANDED: `IF N < (K + 2)` compiles when K is an index-name

Found while adjudicating battery #88's flip `run_misc:1060` (DEVLOG 1883): that case's rejection (an index-name compared with a
parenthesised arithmetic expression) is correct, but probing it exposed the sibling the binder does not reject. Reproduced on
tree `6e4b5deb0` at `--std 2023`:

```
01 T.  02 E PIC X OCCURS 5 INDEXED BY K.
01 N PIC 9(4) VALUE 3.
...  SET K TO 2   IF N < (K + 2) DISPLAY "UNDER-REJECT".
```

It compiles with no diagnostic and runs. `COMPUTE N = K + 2` is correctly rejected (COBOLNET1637).

Spec: §8.8.1.1 allows as arithmetic-expression operands only identifiers of numeric data items, numeric literals and ZERO, and an
index-name is not an identifier (§8.3.2.2.11); §13.18.38.3 SR7 allows an index-name only "as an operand in a relation
condition", not inside an expression. §8.8.4.2.13 item 2 (the occurrence-number rule) covers only a DIRECT relation operand, so
the nested `K` is an arithmetic operand and needs COBOLNET1637 (a warning under `--permissive`).

Mechanism (the adjudicator's reading, to be re-verified at implementation): kb/Work R29 binds the whole relation operand under
`OperandContext.ArithmeticIndexWindow`, which turns off `IndexNameScreen` (`ExpressionBinder.IndexNameExpr`,
`src/Cobol.Net.Compiler/Binding/ExpressionBinder.cs` about lines 477-498) for every index-name anywhere in the expression, not
just a top-level relation operand. R29's landing note says "bare and compound relation operands" stay green: if "compound" meant
exactly this shape, this note RE-OPENS that decision, and the implementer must read R29 first and say so. Related: PB1468
(D-RELCLASS) adjudicated the comparison of an index-name with an expression and the rejection side stays as it is.

## Landed — 2026-10-05 (wave 1020 D)

RE-PROBED first: `IF N < (K + 2)` compiled clean and printed UNDER-REJECT. DETERMINATION (the note asked it be said): R29's landing
read "bare and compound relation operands" as legal, and its golden `85/index_name_r7_windows` carried `IF IX + 1 = 4` as RELEXPR-OK.
That reading was WIDER than the standard. 13.18.38.3 SR7 admits an index-name "as an operand in a relation condition" and 8.8.4.2.13
says "Relation tests may be made only between" an index-name and "a numeric data item or numeric literal": the relation's OWN
operand. In `N < (K + 2)` and `K + 1 = 4` the operand is an arithmetic expression and K is an operand of THAT expression, where 8.8.1.1
admits only numeric data items, numeric literals and ZERO. R29 is therefore RE-OPENED on that one reading and corrected. ROOT: a
relation or EVALUATE operand that is not a bare name was bound under `ArithmeticIndexWindow`, which turns the index-name screen off
for every name anywhere in the expression; the two fallthrough arms (`ConditionBinder.ComparisonOperandOf`,
`EvaluateBinder`'s twin) now bind through `BindExpr` (Arithmetic), so the name takes the SET-window-free rules of `COMPUTE`:
COBOLNET1637 (a warning under `--permissive`, the occurrence number computes) and an index DATA item there is COBOLNET0844. A bare
operand never reaches the spine (`FieldOperand`), so `IF IX = 3`, `IF IX = IY`, `SET` and `SEARCH` are untouched. The
`ArithmeticIndexWindow` enum summary, `BindIndexWindowExpr`'s doc and DESIGN-binder-bound-tree.md section 3.6 are corrected; the
IndexNameContext message says "an operand OF a relation condition, never inside an arithmetic expression". The golden loses its
`RELEXPR-OK` line. Goldens: negatives `pb2018-index-name-in-relation-expression`, `-compound-relation-operand`,
`-index-data-item-in-relation-expression`, `-in-evaluate-expression`. Docs: CONFORMANCE.md D-RELINDEXEXPR.
