# PB549

## Mechanism — usage-clause-p3
usage-p3/F5 — the ONLY ISO-2023 syntax that puts a program's address into a program-pointer is the program-address-identifier of 8.4.3.13.2, `ADDRESS OF PROGRAM { identifier-1 | literal-1 | program-prototype-name-1 }`, and it is not in the grammar at any edition — it is a bare parse error. What COBOL.NET implements instead is `SET pp TO ENTRY {literal|identifier}`, a Micro Focus / IBM vendor spelling whose words appear NOWHERE in the 2023 standard (a grep of specs/ISO_COBOL.md for "TO ENTRY" returns nothing), while the grammar comment on that rule describes it as "ISO 14.9.39 Format 9 with the 8.4.3.13 program-address-identifier as the sender" — Format 9 is `SET {identifier-7}... TO identifier-8`, both operands category program-pointer (SR21), and 8.4.3.13's format is ADDRESS OF PROGRAM. So the standard spelling is rejected and the extension is the only route; a conforming COBOL-2002+ program that loads a program-pointer the standard's way does not compile.

### Expected, from the standard
8.4.3.13.2 general format: `ADDRESS OF PROGRAM { identifier-1 | literal-1 | program-prototype-name-1 }`, with ADDRESS and PROGRAM underlined (required words) and exactly one operand selected. 8.4.3.13.4 GR1 makes it "a unique data item of class pointer and category program-pointer that contains the address of a program", GR2 (cite.py --check 8.4.3.13.4 OK) "For a COBOL program, the address is that of the outermost program identified by the externalized program-name in its PROGRAM-ID paragraph", and GR4 (cite.py --check 8.4.3.13.4 OK) "If the runtime system cannot locate the program, the EC-PROGRAM-NOT-FOUND exception condition is set to exist and the value of the address-identifier is the predefined address NULL". 13.18.60.4 GR24 (cite.py --check OK) is what that identifier fills: "A data description entry that specifies the USAGE PROGRAM-POINTER clause specifies a program-pointer data item ... that may contain the address of a program ... For a COBOL program, the address is for an outermost program." EXPECTED: q48 compiles and prints SUBF-RAN.

### Observed
Measured at --std 2023: `SET PP TO ADDRESS OF PROGRAM "UP3SUBF"` gives `error COBOL0001: no viable alternative at input 'PROGRAM'` and `error COBOL0201: unexpected 'PROGRAM'. PROGRAM is a reserved word.` (q48; q46 is the same shape and fails identically). Grammar by inspection: CobolParserCore.g4:1213-1218 defines `setEntryStatement : SET dataReference+ TO ENTRY (nonNumericLiteral | dataReference)` and there is no ADDRESS OF PROGRAM alternative anywhere in Grammar/. The SEMANTICS behind the vendor spelling are right, which is what makes this a syntax gap rather than a semantic one: q47 loads an outermost sibling program, finds the pointer NOT NULL, CALLs through it and gets "HERE" back; q44 shows a CONTAINED program's name yielding NULL, matching 8.4.3.13.4 GR2's 'outermost' and GR4's NULL. So the whole facility is present and only its standard surface is missing. ⚠ Adjacent documentation gap on the same rule: A.1 item 217 ("USAGE PROGRAM-POINTER clause (alignment, size, and representation of data; and allowable languages), General rule 24") is a REQUIRED item and docs/CONFORMANCE.md carries no DOC-A.1-217 row — the ledger's 200-block runs 202, 204, 205, 206, 207, 208, 209, 211, 215 and stops. The same is true of items 210 (FUNCTION-POINTER, GR26), 212 (MESSAGE-TAG, GR9), 213 (NATIONAL, GR8 — forward-referenced as "row 213" by DOC-A.1-209), 214 (OBJECT REFERENCE, GR22a) and 216 (POINTER, GR23).
