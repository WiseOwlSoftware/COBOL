# PB394 — one rule ("evaluate the sender once"), two verbs, no hoist

## THE MECHANISM

Both halves are the same missing structure: **the sending value is never materialized**, so the emitter re-runs
the source EXPRESSION at every place it needs the value.

* **MOVE.** `MoveEmitter.Emit` is `for (int i = 0; i < m.Targets.Count; i++) { … }` and **every arm inside the
  loop re-renders `m.Source`** — `MoveKind.Convert` calls `ConvertSource(m.Source, …)`, and `RefModSlice`,
  `Group` and `GroupToElementary` each call `OperandText.AsString(m.Source, …)`. `MoveBinder.Bind` builds
  `BoundMove(source, resolved)` with one source node, N targets and no hoist. So with two receivers the
  subscript, reference modifier or function-identifier of the SENDER is evaluated a second time **after the
  first store has landed**. The RECEIVER side is already correct — item identification happens immediately
  before each store — which is exactly what makes this a **one-sided hoist**: the receiver arm was written to
  the rule and the sender arm was not.
* **EVALUATE.** `EvaluateBinder.BindWhenItem` calls `BindValueOperand(subjOp)` at `:210` — inside the **per-PAIR**
  method, i.e. once per subject/object pair, not once per statement — and `EvaluateEmitter` renders each pair's
  composed match into a chained `if/else if`, so the subject expression is emitted **once per RELATIONAL USE**,
  which is TWICE for a THRU arm (`left >= lo && left <= hi`, `:215-231`).

**The compiler already knows this is wrong.** `BindWhenItem` calls `UdfStagePerEvaluationResidue` at `:211`
quoting GR3 verbatim ("evaluated once per statement … this lowering re-binds subjects per WHEN"). But that stage
is narrowed to `UdfBinder.Pending` — **USER-defined function subjects only** — so every intrinsic-function
subject and every other value-varying subject passes silently. That is the two-arm shape again: the arm that
DIAGNOSES the residue was written; the arm that would make the residue unnecessary was not
(`feedback_two_arm_dispatch`).

## THE CODE SITES, AND THE SHAPE OF THE REPAIR

* `src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs#Emit` — the per-target `for` loop; every arm re-renders
  `m.Source`. `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/MoveBinder.cs#Bind` — `BoundMove(source,
  resolved)` with no hoist.
* `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EvaluateBinder.cs:210` (`BindValueOperand(subjOp)` inside
  `BindWhenItem`), `:211-213` (the narrowed stage that documents the defect), `:215-231` (the range arm that
  renders `left` twice); `src/Cobol.Net.Compiler/CodeGen/Verbs/EvaluateEmitter.cs#Emit`;
  `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/UdfBinder.cs#UdfStagePerEvaluationResidue`.

**Repair (CLAUDE.md rule 5 — a materialized value, not a widened stage):**

1. **MOVE**: hoist the sending VALUE into one C# local before the target loop and store that local into every
   receiver. It must capture the **value, not the place** — the group and ref-mod arms pass the raw source text
   to different renderers, so the one hoist has to cover all four `MoveKind`s. Hoisting unconditionally (not
   only when `Targets.Count > 1`) keeps the shape uniform and is what the rule's own `temp` equivalence
   describes.
2. **EVALUATE**: bind the subject ONCE, above the WHEN loop, into a temp every arm and every half of every range
   reads. That is also **the only shape in which GR3's "assigned a value, a range of values, or a truth value"
   is representable at all**. Binding per pair is precisely what forces the residue stage to exist — so the fix
   DELETES `UdfStagePerEvaluationResidue`'s reason to be, rather than widening it. ⚠ **Widening the stage would
   turn a wrong answer into a rejection of legal source**; do not do that as an interim step.
3. Add a drift test that a value-varying sender/subject is evaluated exactly once per statement — the
   `FUNCTION RANDOM` count technique above (measure the NEXT value) is a stable, seedable way to assert it
   without depending on any particular random value.

## HALF LANDED — 2026-09-13 (the once-only half; the run-time-extent LENGTH half remains, below)

**The mechanism the note asked for exists**: `src/Cobol.Net.Compiler/Binding/Procedure/SendingValueTemp.cs`,
THE ONE materialization of a sending value, built on the existing compiler-temp + statement-PRE-op machinery
(`DataBinder.CreateCompilerTemp` + `DataBinder.PendingPreOps`, drained at the `BindStatement` chokepoint) rather
than a second hoist per verb. The intermediate's description is the OPERAND'S OWN, so the store into it is an
identity move and §14.9.25.4 GR1's equivalence is exact rather than approximate.

* **MOVE.** `MoveBinder.BindMoveOf` — the ONE application of the MOVE statement's rules, so every implicit move
  inherits it — materializes the sender when `Targets.Count > 1`. At ONE receiver the source is rendered once
  already and the equivalence's first two steps collapse (temp's description IS identifier-1's), so the
  intermediate is unobservable and is not created; MOVE is the most executed verb in a COBOL program.
* **EVALUATE.** `EvaluateBinder.Bind` builds ONE `SubjectSlot` per selection subject before any WHEN binds and
  hands the same node to every pair; `BindSubjectValue` materializes the value when more than one pair reads it
  (a THRU object counts as two uses, GR4 a) 5.). The slot also carries the subject's bare-operand analysis, so
  `ClassifyPair` no longer re-resolves the symbol per pair. The value-subject `UdfStagePerEvaluationResidue`
  call is DELETED — a subject activation now hoists to statement scope, which is what GR3 asks for. The stage
  survives NARROWED to the CONDITION-subject arm only, because the bound tree still has no
  condition→boolean-operand bridge in which a TRUTH value could live; it was never widened.
