# PB5863 landing, 2026-11-16: what was built, and how it differs from the shape this note decided

**Built.** A code read is evidence at its pin. `scripts/spec/code_reads.py import` resolves every `code-location` entry of
a read in the tree of its `--pin` (one `git cat-file --batch` per pin) and refuses the slice, naming the rule, the entry
and the pin, when an entry does not resolve there. The rule is the gate's: `scripts/spec/code_location.py` is the Python
twin of `SpecTraceabilityInventoryDriftTests.SymbolResolves`/`UnresolvedCodeLocations`, held to it by two RepoDrift tests:
`TheCodeLocationResolver_AgreesWithTheFixtureAndWithPython` (33 planted cases in
`tests/doc-facts/code-location-parity-cases.json`, both engines and the recorded answer) and
`EveryCSharpFilesSymbols_AgreeWithThePythonResolver` (Roslyn's declared names and code words against the Python engine's for
all 901 tracked C# files under `src/`). The gate test `EveryCodeReadLocation_ResolvesInTheTree` is deleted. A read whose
code has moved since its pin is owed a re-read: `code_reads.moved_since` feeds `plan`'s one re-read group, each row with
its reason (`fixed`, its note landed since, kb/Work PB5854; `moved`, the entries that no longer resolve), in the text and
in `--json`; `--check` prints the count as information and is never red for it. `verify-pins --edition YEAR` resolves every
stored record at its own pin (a hand verb, not part of `--check`: a shallow checkout lacks old pins); run on 2026-11-16 it
printed `verify-pins 1985: 1335 record(s) at 6 pin(s); 0 whose code-location does not resolve at its own pin`. In the same
file the audit's reads at a pin now go through one process per pin (`pins_open`): `--check` went from 40 s to 7 s.
Self-test: `scripts/selftests/spec/code_reads/test_code_reads.py`, cases 14 to 17. Design: `DESIGN-spec-conformance-review.md`
section 10.6.1.

**How it differs from the shape decided above.** The note decided (1) a rule in the implementer's template that a read a
change un-resolves is withdrawn, (2) a one-command withdrawal of every unresolved read, and (3) an importer that refuses an
impossible pin. The owner's question on 2026-11-16 ("why are we waiting for a known red to appear, then handle the
error?") showed the red itself was the fault: code moving is expected, and a read is not wrong because it did. So the red
is gone and nothing needs withdrawing; no template rule is needed, because a fix that renames a member no longer meets
anything. `withdraw` keeps its one use, a read defective as a read. (3) is answered at the root: a read whose locations
do not resolve at its pin is refused, which is what a wrong pin produces; the ancestry of the pin is not checked. The
withdrawn read of `1985-GR-X.5.3.4-10` and the three PB5847 withdrew stay withdrawn; their rows are owed a read.
