# PB2523 — the audits fail fast, before the build

## Measured (operator, wave 1034, 2026-10-07)

16 implementer gates at cap 3 (`verdict.json` in `E:\COBOL\.claude\worktrees\wf_3fe29228-bf0-*\TestResults\build-local\*`):
4 of the 8 first-run reds were AUDIT-only reds reported after a full ~6-min population run with every test green — three
`DRIFT RULES INDEX RED`, one `DOC CITATIONS RED` — plus one `DRIFT RULES INDEX RED; STOPPED AFTER LEG 1`. This branch's
own first gate (wave 1033 group V, run `20261007T234147Z-4492bc`) was the same shape: `CITATIONS RED; DRIFT RULES INDEX
RED` after the whole population.

## Cause

`scripts/run_gate_legs.py#AUDITS` ran first, but by design "a red one makes the gate RED but the gate still builds and
tests: every red of the run in one verdict". For an implementer that design spends a build and a whole population (or
leg 1) to report a red that was known in seconds, and the re-gate pays it again.

## Landed (wave 1033 group V, 2026-10-07, branch `gate-batch`)

- `Host.prepare` is split into `Host.audits` and `Host.fetch_corpus`. `Gate._gate` runs the audits first and, in
  IMPLEMENTER mode, a red one ends the gate at once: `=== BUILD-LOCAL GATE: RED — DRIFT RULES INDEX RED — fail-fast: the
  audits run before the build and NO LEG RAN; fix the audit and re-gate · … ===`, exit 1, with `verdict.json` written
  (`timings.audits_s`). No build, no listing, no leg. The LANDER keeps going (its one run shows every red of the train).
- Self-test: "a red audit (a stale drift-rules index) STOPS the implementer gate before the build: RED, the audit named,
  no leg ran" (seen RED with the fail-fast removed: the legs ran) and "a red audit in -Mode lander is RED and the legs
  still run"; both asserted by `GateLegDriftTests` arm (3).
- Docs: DESIGN-test-build-ci section 3.14.3 step 3, the gate skill.
