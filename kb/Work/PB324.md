# PB324 — the record lands in a file named after the file-name

**Rows:** `GR-14.9.27.4-26`.

## The program

`<lane3 scratch>/out-b1/probe/assign-using/p.cob` — `SELECT FU ASSIGN USING WS-NAME` with
`01 WS-NAME PIC X(11) VALUE "target1.dat"`; OPEN OUTPUT, WRITE, CLOSE; then list the directory.

## The rule

§14.9.27.4 GR26 routes to §12.4.5.3 GR3/GR4. GR3 b):

> When the USING phrase of the ASSIGN clause is specified, the file connector referenced by file-name-1 is
> associated with a physical file identified by the content of the data item referenced by data-name-1 in the
> runtime element that executes the OPEN, SORT, or MERGE statement.

and GR3's lead sentence fixes the TIMING:

> The association occurs at the time of execution of an OPEN, SORT, or MERGE statement that referenced
> file-name-1.

`--check 12.4.5.3 "The association occurs at the time of execution of an OPEN, SORT, or MERGE statement"` →
**OK**. The record must therefore land in `target1.dat`, re-resolved at every OPEN.

## What the compiler does

The program compiles with no diagnostic, OPEN OUTPUT reports '00', and the record lands in **`fu.txt`** —
`CobolFile.ResolveHostPath` applied to the FILE-NAME, which is `FileModel.AssignTarget`'s constructor default
when no `assignTarget` node is present. `target1.dat` is never created. `DataBinder.BindFileControl` (line 792)
reads only `assignClause().assignTarget()`; the USING `dataReference` child is read nowhere in `src`.

The TIMING half is broken independently: `FileRegistry.Register` (line 104) calls `ResolveHostPath` at unit
activation and stores the result in the get-only `FileConnector.HostPath`, so a MOVE into data-name-1 between
two OPENs cannot change the association — the standard's concepts annex states the intended behaviour outright
(*the MOVE statements only have an effect on the dynamic assignment when a subsequent OPEN statement for the
file connector is executed*).

**Code sites:** `DataBinder.cs#BindFileControl` (line 792) · `CobolIO.g4#assignClause` (lines 36-39) ·
`FileRegistry.cs#Register` (line 104) · `CobolFile.cs#ResolveHostPath` (lines 233-237).

## The fix shape

Carry the USING data item on `FileModel`, and make the connector's host path SETTABLE at OPEN through a
per-OPEN re-resolution entry point — which §12.4.5.3 GR3 requires for every ASSIGN form, not just USING — then
state GR4's allowable-content and consistency rules in `docs/CONFORMANCE.md`. `kb/Work/A2` already lists ASSIGN
USING as a proved silently-unenforced SYNTAX rule; this is the general-rule semantic half.

## Landed — 2026-09-05

**Both halves of §12.4.5.3 GR3 now hold, through ONE entry point.** `FileConnector.Associate()` is the only writer
of a connector's `HostPath`, and `FileRegistry` calls it from `Open`, `OpenShared` (which the emitted SORT/MERGE
implicit opens also reach — §14.9.40.4 GR12a/GR15a, §14.9.24.4 GR7a) and `DeleteFile`'s unassociated
screen. It is a no-op for the GR3 a) TO-form, whose association is static, so the two arms of GR3 share one
mechanism rather than getting a register-time one and an open-time one. `DataBinder.BindFileControl` now reads BOTH
phrases of the clause on both general-format arms, and the bare `ASSIGN USING data-name-1` form registers with an
EMPTY assign target — there is no device-name-1/literal-1 to be associated with — instead of silently
defaulting to the file-name. `SequentialIoEmitter.EmitAssignSources` installs one
`CobolFile.SetAssignUsing(key, () => data-name-1)` per USING file, UNGUARDED on every activation beside the LINAGE
evaluator and for the same PB168 reason, on BOTH registration arms (`DispatchEmitter.__Activate` for a program, the
class constructor in `OoEmitter.EmitFileMembers` for an object — Annex D.19.9.2's own worked example is an
instance file). Design decision **D15** in `docs/COBOLNET_FILES_DESIGN.md` records the shape.
**⛔ SUPERSEDED 2026-09-05 by [[PB673]]:** the install is gone. §12.4.5.3 GR3 b) names the data item "in the
runtime element that executes the OPEN, SORT, or MERGE statement", and one connector can be described by several
of them (§13.18.22.4 GR4 a), so the executing element's own operand is rendered AT the statement and passed as an
argument (`SequentialIoEmitter.ExecutingElementArgs` → `FileConnector.Associate(spec, dynamic)`). Everything else
PB324 landed — the timing, the '31' content rules, DOC-A.1-73/DOC-A.1-10 — stands unchanged.

**§12.4.5.2 SR7 is enforced** at bind time from `DataBinder.ResolveAssignUsing`, once the forest is indexed:
`COBOLNET1810` for the category half (an alphanumeric group item qualifies per §13.18.29.4 GR3; alphabetic,
numeric, edited, national, boolean and the PICTURE-less usages do not, and a name that resolves to nothing takes the
same code) and `COBOLNET1811` for the subordinate-to-its-own-FD half — the dangerous one, since such an operand
is overwritten by every READ of the file it names.

**GR4's implementor obligations are stated**, in `docs/CONFORMANCE.md` §7 as `DOC-A.1-73` (the content with
leading and trailing spaces removed IS the assign target, mapped by the literal-1 rule; the association is made at
OPEN/SORT/MERGE and nowhere else; empty-after-trim or control-character content is unusable and takes
§9.1.13.6 item 2's **'31'**, the status the standard reserves for exactly this) and `DOC-A.1-10` (there are NO
consistency rules between the content and device-name-1/literal-1 — GR4's own "if any" makes the empty set a
complete answer, and where both phrases are written the USING content wins outright).

**Sibling swept (rule 4).** `FileRegistry.ConnectorShare` cached a host path taken at `RegisterSharing` time and six
physical-file-table lookups read that copy. It was only ever correct because the path could not change; a mutable
association turns it into a stale sharing key. The field is gone and every lookup reads `c.HostPath` /
`HostPathOf(name)`. Two more: `CobolFile.ResolveHostPath("")` used to answer the literal file `.txt`, and
`FileConnector.Open` caught only `UnauthorizedAccessException`/`IOException` — now that the host path is a
runtime value, `ArgumentException` and `NotSupportedException` map to §9.1.13.6 item 1's '30' instead of
escaping. `OoEmitter`'s EXTERNAL `SelectFingerprint` carries the USING data-name, because §12.4.5.3 GR1 b names
all THREE operands ("A consistent specification for data-name-1, device-name-1, and literal-1 in the ASSIGN
clause").

**Evidence.** `conformance:2023/pb324_assign_using_dynamic` (the '31' blank-content arm, two physical files through
one connector, an OPTIONAL witness proving `dynf.txt` is never created, the read-back of each file, the mixed
`ASSIGN TO … USING …` precedence leg with its own OPTIONAL witness, and DELETE FILE on the live
association); `conformance:85/pb324_assign_using_85` (the same behaviour at the oldest supported edition — no
edition gate exists for the phrase); `conformance:negative/pb324-assign-using-not-alphanumeric` and
`conformance:negative/pb324-assign-using-in-own-record` (SR7's two halves, rejected at 85/2002/2014/2023).
Rows `GR-14.9.27.4-26` (DIVERGES → CONFORMS), `DOC-A.1-73` and `DOC-A.1-10` are recorded; GAP 2830 → 2827.

**NOT done here, and deliberately.** No edition gate is applied to the USING phrase. The clause is a 2002-era
addition on the evidence of §9.1.21's placement, but `docs/VERSION_CHANGE_REFERENCE.md` has no 85→62 row set
at all and neither `docs/ISO2023_CONFORMANCE_PLAN.md` nor the version matrix's `introducedIn` tags catalogue it, so
gating it here would invent a delta rather than derive one — and a wrong gate REJECTS LEGAL SOURCE. The
compiler therefore accepts it at every edition (the grammar's standing superset posture), pinned at 85 by the
golden above. The gate is a separate item once the 1989:2002 text can be consulted.
