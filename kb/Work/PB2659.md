# PB2659 — LANDED — a recursion depth of about 250 killed the process

Found 2026-10-08 ~04:20 PDT by the cobol-adjudicator drafting PB1636 determinations, probing the battery-green pin
`ea20c28e3` (lead **L1** of `E:\COBOL-coord\scratch\w1040-drv\drafts.md`). Filed by the wave 1040 group U implementer,
who re-ran the probes on `853f38cab`.

## Repro (re-run on 853f38cab, Debug build)

`E:\COBOL-coord\scratch\w1040u\probes\d200.cob` and `d300.cob`: a `RECURSIVE` program with a 30-character name that
CALLs itself until `DEPTH = LIM`, then displays `FUNCTION LENGTH(FUNCTION MODULE-NAME(STACK))`.

- depth 200: `S=[MNSTKDEEPRECURSEPROBEAAAAAAAAA;MNSTKDEEP] L=000006201`, `EC=[` 31 spaces `]`, exit 0.
- depth 300: `Stack overflow.` followed by a CLR stack trace (`__Dispatch` / `__Activate` repeated 253 times); the
  process dies. No EC is set, no declarative runs, the §14.6.11 implicit CLOSE never happens.
- `mn2.cob` (depth 2200, the DOC-A.1-132 witness shape): the same `Stack overflow.`

## Rule

- §14.9.4.4 GR3c (`cite.py --check 14.9.4.4` → OK 3)): *"If the program is located but the resources necessary to
  execute the program are not available, the EC-PROGRAM-RESOURCES exception condition is set to exist, the program call
  is not successful, and execution continues as specified in General rule 3h. The runtime resources that are checked
  in order to determine the availability of the called program for execution are defined by the implementor."*
- §8.4.3.2.4 GR6c (OK 6)): the same sentence for a user-defined function activation.
- §14.9.23.4 GR7b (OK 7)): *"If the method is not found or the resources necessary to execute the method are not
  available, the EC-OO-METHOD exception condition is set to exist"*.
- §8.6.6 (OK): *"A recursive program may call itself directly or indirectly."*
- Annex A.1 items 14, 89, 102 (OK 14), 89), 102)): the resources checked are implementor-defined and documented.
- §14.6.11 2) (OK): the implicit CLOSE of every open file, *"even when an error occurs"*; a process kill skips it.

So the standard has a defined outcome for "an activation the implementation cannot support": the activation is not
successful and the EC is set. The documented determinations (docs/CONFORMANCE.md DOC-A.1-14, -89, -102) chose an EMPTY
checked set and said *"Available memory and activation depth are not checked: running out of either is a host
failure, the run unit ends abnormally"* — but the run unit does not end abnormally in any §14.6.12 sense: the CLR kills
the process. GnuCOBOL 3.2 (measured in WSL, `E:\COBOL-coord\scratch\w1040u\gc\deep.cob`) reaches 74,687 activations of
the same shape on its default 8 MB stack and then dies of SIGSEGV with no message, so neither precedence leg defines a
better outcome than the standard's own GR3c.

## Code sites

- `src/Cobol.Net.Runtime/Control/ProgramTable.cs#RunMain` — runs the main program on the calling (host main) thread.
- `src/Cobol.Net.Runtime/Control/ProgramTable.cs#CallProgram` — the CALL and function activation boundary; checks
  locate (GR3b), recursion (GR3f) and arguments (GR3d), never resources (GR3c).
- `src/Cobol.Net.Compiler/CodeGen/Verbs/OoEmitter.cs` method prologue — the INVOKE activation boundary (GR7).
- No `Thread` with a `maxStackSize` and no stack check exist anywhere in `src/Cobol.Net.Runtime`.

## Harm

A legal RECURSIVE program (a tree walk, a recursive descent parser, a factorial) dies at a depth of about 250 with a
.NET stack trace, losing whatever the §14.6.11 CLOSE would have flushed. It also blocks the spec-derived golden for
DOC-A.1-132 (MODULE-NAME(STACK) at depth 2200 has length 68201, with no EC-BOUND-FUNC-RET-VALUE).

## Landing (wave 1040 group U, branch `w1040u-recursion-depth`)

The stack is now the one runtime resource GR3c / GR6c / GR7b check (docs/CONFORMANCE.md DOC-A.1-14, -89, -102;
DESIGN-runtime-library §2.1 "The run unit's thread and the activation resource check"):

- The main program runs on a 384 MiB run-unit thread (`ActivationStack.RunOnRunUnitThread`, from
  `ProgramTable.RunMain`), sized from measurement so a minimal self-CALLing program under full checking reaches
  GnuCOBOL 3.2's default-stack depth (74,687): 104,585 on Windows, 92,137 on Linux; 256,126 unchecked.
- `ProgramTable.CallProgram` asks `ActivationStack.IsAvailable` right after locating (before GR3d–f) and raises
  EC-PROGRAM-RESOURCES through the CALL carrier (CALL and function activation); the emitted head of every method body
  calls `ActivationStack.RequireForMethod` (EC-OO-METHOD) before the GR7 d) external check.
- A second defect the fix exposed: the GR3i boundary mark was a catch-and-rethrow, and each rethrow nests a new
  exception dispatch on top of the stack, so an unhandled EC-PROGRAM-RESOURCES crossing 150,000 boundaries overflowed
  the stack again. It is now an exception filter (`ProgramTable.MarkBoundaryCrossing`).

Probes after the fix (`E:\COBOL-coord\scratch\w1040u\probes`): d300/mn2 run (L=68201 at 2200); rnoexc ends
`abnormal run-unit termination: CALL 'RNOEXC': … (ISO §14.9.4.4 GR3c — EC-PROGRAM-RESOURCES)`, exit 1, its file
closed with the record written; rfunc and rmeth end in EC-PROGRAM-RESOURCES and EC-OO-METHOD; rdecl runs its
declarative; rstop's STOP RUN at depth 100,000 exits 7.

For the next implementer:
- `src/Cobol.Net.Runtime/Control/ActivationStack.cs#IsAvailable` — THE resource check; every new activation path
  asks it (never `RuntimeHelpers` directly). `RunOnRunUnitThread` is the only place a run-unit thread is made.
- `src/Cobol.Net.Runtime/Control/ProgramTable.cs#CallProgram` — the GR3c raise sits right after `ResolveVisible`;
  ⛔ trap: never `catch … { throw; }` on the activation path — use a filter (`MarkBoundaryCrossing`), or an
  exhausted recursion overflows while unwinding.
- `src/Cobol.Net.Compiler/CodeGen/Verbs/OoEmitter.cs#EmitMethod` — the GR7 b) line via
  `RuntimeApi.MethodActivationResources`; a PROPERTY accessor is not checked (it executes no statement).
- `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/EcBinder.cs` — EC-PROGRAM-RESOURCES is queried for
  `BoundCallProgram` only (not in `ProgramNames`, which CANCEL shares).

## Train 1040 review

The step-5b review found one cosmetic defect in this change, fixed in its commit: moving the method-name and
class-name literals above the new GR7 b) line dropped a space from the emitted frame push
(`var __ms =CobolModule.Stack`). The emitted text is restored. The review checked the exception filter that replaced
the catch-and-rethrow (`ProgramTable.MarkBoundaryCrossing`): a filter runs before the inner `finally` blocks, but the
only readers of `ControlTransferred` are the CALL-site catch filters, which run after it in the same innermost-first
order, so the GR3d/GR3i outcomes are unchanged. No ThreadStatic state outside `ActivationStack` crosses into the
run-unit thread.
