        <li><strong>One owner-visible change from train 7</strong> (PB623): <span class="mono">MOVE &lt;COMP-2 8.2&gt; TO PIC 9V9</span> now stores 8.1, because the float-to-fixed transfer is the binary64's exact value at every magnitude (§14.6.8.2 r1, no latitude) and rule 4 truncates; <span class="mono">ROUNDED</span> still gives 8.2. The question if the owner wants it reversed: should a FLOAT-LONG sending item convert by its shortest round-trip decimal instead, accepting that a MOVE and a COMPUTE of the same item then disagree?</li>
        <li><strong>One more from train 9</strong> (PB670, PB322's family): now that Table 19 arbitrates every OPEN, two clause-less connectors opening one file in conflicting modes answer '61' at COBOL-85 too, where the file-sharing statuses do not exist — permit the open as 1985's silence allows, refuse it with the operating system's '30' as before, or keep the deterministic '61'? The runtime has no edition, so any answer but the last needs a new seam.</li>
        <li><strong>One from train 12's sweep</strong> (PB690): every sequential reader and writer is built on Latin-1, so a character above U+00FF is written as a question mark with no status — and the fix needs a decision no implementer should make alone: for a sequential file with no CODE-SET clause, what is its coded character set? UTF-8 (lossless, variable bytes per character), Latin-1 refusing an unrepresentable character with a record-content status (one byte per character, never corrupts silently), or UTF-16 (the program's own repertoire, no interchange)? The surveyed model implementation is byte-transparent.</li>
        <li><strong>One from train 13's sweep</strong> (PB701): the indexed store now keeps one release order per key of reference, but the physical file carries one sequence of record images, so a mutually cyclic pair of per-key duplicate orders — a REWRITE moving a record into another's duplicate set under one key while both stay duplicates under another — cannot survive a CLOSE. Should the on-disk format carry the per-key ordinals (a format change with a migration for every existing indexed file), or does the acyclic-only guarantee stand as a documented determination?</li>
        <li><strong>One from the registrar's transcription check</strong> (PB738): a content-stream scan of all 1,261 pages found exactly five places where the published standard itself drops a character ("The valu62'" for "The value '62'"); the transcription reproduces the printed defect faithfully, so <code>cite.py</code> and the rule catalog work on the garbled text. Keep it faithful, or add an editorial-note convention for recovered readings?</li>
        <li><strong>One from the runtime's sharing posture</strong> (PB740): two clause-less connectors on one ASSIGN that the standard's own arbiter permits to coexist (OPEN INPUT, then OPEN EXTEND) are refused by the operating-system handle with status 30 and the appended record is never written, while a connector declared SHARING WITH NO OTHER admits an external writer. The in-run-unit half is being fixed; the question left: should a clause-less connector keep its exclusive operating-system posture against processes outside the run unit, or take the arbiter's answer only?</li>
        <li><strong>Still open, and not yet a bare question:</strong> the introducing edition of <span class="mono">USAGE POINTER TO type-name</span> — and now, from train 10, the introducing edition of the ASSIGN clause's <span class="mono">USING data-name</span> phrase (PB674), which the compiler accepts at every edition because nothing in the tree can derive an 85↔2002 boundary. Both are one question already on file as R28: is the ISO/IEC 1989:2002 text available to the project? The per-edition mission cannot be finished without it.</li>
