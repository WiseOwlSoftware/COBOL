### F1 · exception-statement

REJECTS LEGAL COBOL (parse error, new) -- `WRITE record-name-1 FROM FUNCTION EXCEPTION-STATEMENT` (and REWRITE ... FROM, RELEASE ... FROM) fails to parse. REPRO: IDENTIFICATION DIVISION. PROGRAM-ID. ECWFROM. ENVIRONMENT DIVISION. INPUT-OUTPUT SECTION. FILE-CONTROL. SELECT F ASSIGN TO "f.txt" ORGANIZATION IS LINE SEQUENTIAL. DATA DIVISION. FILE SECTION. FIX SHAPE (rule 4/5, sweep the pattern): audit every `(dataReference | literal)` operand rule in the grammar against 8.4.3.1.2 Format 1, add the functionCall alternative to each SENDING position (keyword-led, so it can never shadow dataReference), and pair it with a drift test that fails when a new sending-operand rule omits it -- do not patch writeFrom alone.

REJECTS LEGAL COBOL (NEW — the refute pass's finding, and the reason RV-15.33.3-1 was downgraded) — NO COBOL WORD MAY CONTAIN AN UNDERSCORE, though the standard has permitted it since COBOL-2002. §8.3.2.1 (validated: cite.py --check 8.3.2.1 "Each character of a COBOL word that is not a special character word shall be selected from the set of basic letters, basic digits, extended letters, and the basic special characters hyphen and underscore. The hyphen or underscore shall not appear as the first or last character in such words." -> OK) and, for this subject specifically, §14.6.13.1.1 (validated: cite.py --check 14.6.13.1.1 "The level-3 exception-names for user-defined exceptions shall start with the characters 'EC-USER-' and end with a suffix containing only characters selected from the set of basic letters, basic digits, and the hyphen and underscore basic special characters." -> OK). REPRO (--std 2023, prebuilt cobol.exe): `RAISE EXCEPTION EC-USER-A_B.` GOT `error COBOL0001: no viable alternative at input '_'` + COBOL0307 + COBOL0001. It is NOT specific to exception-names: `01 WS_A PIC X(5) VALUE "HELLO".` GOT `error COBOL0001: no viable alternative at input 'WS_'`. ROOT CAUSE READ FROM THE GRAMMAR: src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4 `fragment NAME_BODY` = `[0-9]+ '-' [a-z0-9] [a-z0-9-]* | [0-9]+ [a-z] [a-z0-9-]* | [a-z] [a-z0-9-]* [a-z0-9] | [a-z]` — the underscore appears in no alternative, so an underscore-bearing word cannot lex. ### F12 · exp

REJECTS LEGAL COBOL — a SIGNED floating-point numeric literal cannot be written as an intrinsic-function argument. `FUNCTION EXP(-1.5E3)` is rejected with COBOLNET1504 "FUNCTION EXP takes 1 argument(s); 2 given (ISO §15.3)". SPEC: §8.3.3.3.3 r2 "The literal to the left of the 'E' represents the significand. It may be signed and shall include a decimal point." (the sign is part of the literal); §8.3.3.3.1 "Numeric literals are of the class and category numeric."; §8.4.3.2.3 SR8 "Argument-1 shall be an identifier, a literal, a boolean expression, or an arithmetic expression."; §15.3 type 10; §15.34.3 r1 class numeric. All four --check verified. ROOT CAUSE (src/Cobol.Net.Frontend/Grammar/Core/CobolLexer.g4): `FLOATLIT : ( [0-9]+ '.' [0-9]* | '.' [0-9]+ ) 'E' [-+]? [0-9]+` has no leading sign, so it cannot start at '-'; inside a FUNCTION-argument region `SignedLiteralCanStart()` is true after '(' and `FN_SIGNED_DECIMALLIT : {SignedLiteralCanStart()}? [+-] DEC_BODY -> type(SIGNED_DECIMALLIT)` wins maximal munch with "-1.5", orphaning "E3" as an IDENTIFIER via NAME_BODY; `functionArgList` is plain juxtaposition, so the parser reports two arguments. There is NO `FN_SIGNED_FLOATLIT` twin and no `SUB_FLOATLIT` at all. BOTH reference forms fail: the keyword-omitted re-parse (IntrinsicBinder#ReparseArgs → FunctionArgFragment with PrimeFunctionArgs) hits the same rule, and `SignedLiteralCanStart()` returns true unconditionally at `InputStream.Index == 0`. Unsigned `FUNCTION EXP(1.5E3)` works, which is why no sampling caught it; tests/conformance/2002/float_literal.cob only writes `MOVE -1.5E3 TO WS-A`, outside any argument region. SIBLING SWEEP (every bug is a pattern): this is NOT EXP-specific — it hits EVERY intrinsic argument position that admits a numeric literal (ABS, SQRT, LOG, MOD, MAX/MIN, ANNUITY, REM, …) and every argument position of a user-defined function reached through the same grammar. It is also the SAME rule as the lexer's own SIGNED_DECIMALLIT ordering note ("-15.6 orphans .6") applied to only two of the three literal shapes. FIX: add the signed floating-point twin alongside FN_SIGNED_DECIMALLIT/FN_SIGNED_INTEGERLIT — ordered FIRST so maximal munch keeps the exponent (a `FN_SIGNED_FLOATLIT : {SignedLiteralCanStart()}? [+-] ( [0-9]+ '.' [0-9]* | '.' [0-9]+ ) 'E' [-+]? [0-9]+ -> type(FLOATLIT)`), plus the SUBSCRIPT-mode SUB_FLOATLIT the mode is missing, and a drift test pinning the three literal shapes against one another so the next literal form cannot be added to only two of them.

### F13 · exp

SILENTLY WRONG VALUE, NO SIZE ERROR (the PB5 residue, still live at 2002+) — CobolIntrinsics#FromDouble's saturation clamp is REACHABLE from a declarable receiver, contradicting its own doc remark. REPRO: `IDENTIFICATION DIVISION. PROGRAM-ID. EXPCLAMP. DATA DIVISION. WORKING-STORAGE SECTION. 01 R PIC 9(31). PROCEDURE DIVISION. COMPUTE R = FUNCTION EXP(70) ON SIZE ERROR DISPLAY "SIZE" NOT ON SIZE ERROR DISPLAY "OK". DISPLAY R. STOP RUN.` at --std 2002/2014/2023. SPEC-DERIVED EXPECTED: §15.34.3 r1 puts no upper bound on the argument, §15.34.4 r1's EAE is `(FUNCTION E ** (argument-1))`, and §15.4.1 under native arithmetic permits "an implementor-defined approximation of the value of that expression" — e**70 ≈ 2.5154386709191670 × 10^30 fits a 31-digit receiver, so §14.7.4 raises nothing and R must hold that approximation. CURRENT: RenderFloat emits `CobolIntrinsics.FromDouble(CobolIntrinsics.Exp((double)70), 9)`; `ws = max(Receiver.Scale, 9) = 9`, `scaled = 2.5e39 >= 1.7e38`, so FromDouble returns Int128.MaxValue and R becomes 0170141183460469231731687303715 — wrong by a factor of ~14.8, with `OK` printed and no diagnostic. The clamp bites at |value| ≈ 1.7 × 10^29, i.e. from FUNCTION EXP(68) upward. WHY THE COMMENT IS WRONG: FromDouble's remark claims the Int128 ceiling at scale 9 is "past the 10^18 any PICTURE can describe", but EditionInfo.MaxDigits is `Year < 2002 ? 18 : 31`, EditionContext#CheckDigitCapacity admits 19–31 digits at 2002+, and PicInfo stores a >18-digit item as Int128 — so 30- and 31-digit receivers are ordinary at exactly the editions EXP exists in.
