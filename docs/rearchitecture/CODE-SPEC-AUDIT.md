## ACCEPT / DISPLAY / SET (3 findings, 28 rules checked)

### CA1. [MAJOR/high] INITIALIZE of a dynamic-length elementary item (bare / default form)
- **Spec:** §14.9.20.4 GR7 — "When a dynamic-length elementary item is initialized, its length is set to zero."
- **Code:** `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs:214 (InitializeItemCategory) → :148/:206 (InitializeSender → BoundFigurative 'S') → emit via src/Cobol.Net.Compiler/CodeGen/Verbs/MoveEmitter.cs:285-286 (DynStore) → src/Cobol.Net.Runtime/Values/Text/CobolDynString.cs:25-29 (Store)` — InitializeItemCategory has no special case for IsDynamicLength; a DYNAMIC LENGTH item (category alphanumeric/national) is classified as ordinary Alphanumeric/National, so the default sender is figurative SPACE and the InitializeStore is emitted as an ordinary implicit MOVE. MoveEmitter routes it through ConvertSource's IsDynamicLength branch = CobolDynString.Store(new string(' ',1), limit), and a figurative sender has length 1 (never repeated for a dynamic-length receiver), so the item is left with LENGTH 1 (a single space) instead of length 0.
- **Fails:** 01 D PIC X DYNAMIC LENGTH.  … SET SIZE OF D TO 5 (D now length 5) … INITIALIZE D … DISPLAY FUNCTION LENGTH(D). Code prints 1 (D = a single space); spec-correct output is 0 (D is empty). The same 1-vs-0 divergence occurs for a fresh D and for a group containing D under INITIALIZE grp.

### CA2. [MAJOR/medium] INITIALIZE (default, no REPLACING/VALUE) of a data-pointer, program-pointer, or object-reference receiving-operand (as identifier-1 or as a group member of identifier-1)
- **Spec:** §14.9.20.4 GR4 + GR6c (and GR5a1's EXCEPT clause) — GR4: "If the category of a receiving-operand is data-pointer, function-pointer, message-tag, object-reference, or program-pointer, the implicit statement is: SET receiving-operand TO sending-operand"; GR6c fill table: Data-pointer → "Predefined address NULL", Program-pointer → "Predefined address NULL", Object-reference → "Predefined object reference NULL". GR5a1 excludes non-MOVE-receivers "except data items of category ... pointer, object-reference, or program-pointer" (i.e. these are NOT excluded).
- **Code:** `src/Cobol.Net.Compiler/Binding/Procedure/Verbs/InitializeBinder.cs:224 (InitializeItemCategory `_ => null`) and :147 (ExpandInitialize: `if (InitializeItemCategory(item) is not { } cat) return;`)` — InitializeItemCategory returns null for PicCategory.Pointer/ProgramPointer/ObjectReference (they fall to the `_ => null` arm), and ExpandInitialize treats a null category as 'excluded, left unchanged'. - **Fails:** 01 G. 05 OBJ USAGE OBJECT REFERENCE. 05 X PIC X(4). … SET OBJ TO some-object … INITIALIZE G … IF OBJ = NULL DISPLAY "NULL" ELSE DISPLAY "SET". Spec: OBJ is reset to NULL, prints "NULL"; code: OBJ unchanged, prints "SET" (and X is spaced either way). Likewise `INITIALIZE some-pointer` emits nothing at all where the spec requires SET some-pointer TO NULL.

## ARITHMETIC (3 findings, 23 rules checked)

### CA4. [MAJOR/high] Composite-of-operands 31-digit check for ADD … GIVING and SUBTRACT … GIVING (Format 2) — the GIVING receiver is wrongly counted into the composite
- **Spec:** §14.9.2.3 SR1b (ADD) and §14.9.44.3 SR1b (SUBTRACT); §14.7.7 rule 2 — §14.9.2.3 SR1b: 'In format 2, by using all of the operands in the statement excluding the data items that follow the word GIVING.' §14.9.44.3 SR1b is identical for SUBTRACT. The composite is 'the superimposition of specified operands … aligned on their decimal points' — a pure GIVING resultant is not an operand.
- **Code:** `src/Cobol.Net.Compiler/Binding/Validation/StatementValidation.cs:129-131 (receiver-shape loop), fed by ArithmeticBinder.cs:36 (ADD GIVING) and :57 (SUBTRACT GIVING)` — CheckComposite unconditionally Shape()s every numeric receiver (lines 129-131) into maxInt/maxFrac, and BindAdd/BindSubtract pass the GIVING receivers as the `receivers` argument, so the GIVING receiver's digit positions are added to the composite and counted against the 31-digit cap.
- **Fails:** 01 A PIC 9(25). 01 B PIC 9(25). 01 C PIC 9(6)V9(10).  `ADD A B GIVING C.`  Composite of operands excluding C = 25 int + 0 frac = 25 ≤ 31 → spec-legal. Code computes maxInt=max(25,25,6)=25, maxFrac=max(0,0,10)=10 → composite 35 > 31 → emits COBOLNET0805 and REJECTS a conformant program. (Same for `SUBTRACT A FROM B GIVING C` shapes.)

### CA5. [MAJOR/high] Nested/intermediate division in a COMPUTE inherits the RECEIVER's ROUNDED MODE — so ROUNDED MODE IS PROHIBITED is applied to an intermediate quotient, raising a spurious size error
- **Spec:** §14.7.4.3 GR7 (PROHIBITED) + §14.7.7 NOTE 1; native intermediate precision §8.8.1.3; §14.7.5 (size error cases enumerate no intermediate-inexactness case for native) — §14.7.4.3 GR7: 'If the PROHIBITED phrase is specified, and the arithmetic value cannot be represented exactly in THE RESULTANT IDENTIFIER, the EC-SIZE-TRUNCATION exception condition is set to exist …'. §14.7.7 NOTE 1: 'The ROUNDED phrase applies only to this transfer of data' (the final store). PROHIBITED is defined against the resultant identifier, never against an intermediate; for native arithmetic intermediate precision is implementor-defined (§8.8.1.3) and inexactness of an intermediate is not a size error (§14.7.5 lists no such case).
- **Code:** `src/Cobol.Net.Compiler/CodeGen/Emit/NumericRenderer.cs:271-284 (Divide: guard-digit condition + `mode = ds == _rcv.Scale ? _rcv.Rounding : Truncation`); throw at src/Cobol.Net.Runtime/Values/Numeric/CobolNum.cs:190-191 (DivideOrThrow PROHIBITED)` — Divide() only adds guard digits when an operand scale exceeds the receiver scale; for the common case where every operand scale ≤ receiver scale (e.g. integer operands), a division that is actually NESTED inside a larger expression is treated as outermost: ds = receiver scale and mode = _rcv.Rounding. When that mode is PROHIBITED and the statement is checked (ON SIZE ERROR phrase or >>TURN EC-SIZE CHECKING ON → InSizeError), it emits CobolNum.DivideOrThrow(…, Prohibited), which throws CobolSizeError on the inexact intermediate quotient.
- **Fails:** 01 X PIC 99V99.  `COMPUTE X ROUNDED MODE IS PROHIBITED = 10 / 3 * 3 ON SIZE ERROR DISPLAY "ERR".`  Intermediate 10/3 is inexact at scale 2 → code throws → size error path taken, X left unchanged and 'ERR' displayed. Spec-correct: PROHIBITED governs only the value stored into X; the deliverable value (9.99, or 10.00) IS exactly representable in X, so no size error occurs and X is stored. With >>TURN EC-SIZE CHECKING ON (no phrase) the spurious CobolSizeError latches EC-SIZE-TRUNCATION and fatally terminates a statement that should succeed.

### CA6. [MINOR/medium] Composite-of-operands: USAGE BINARY-CHAR/-SHORT/-LONG/-DOUBLE operands are not excluded from the composite
- **Spec:** §14.7.7 rule 2b — §14.7.7 rule 2b: 'When any of the operands is … a data item described with usage binary-char, binary-short, binary-long, binary-double, float-short, float-long, or float-extended … the composite of all OTHER operands shall not contain more than 31 digits.' ### CA7. [MAJOR/high] Class condition on a ZERO-LENGTH operand — ALPHABETIC / ALPHABETIC-LOWER / ALPHABETIC-UPPER / user-defined class-name
- **Spec:** §8.8.4.4.4 GR1 (and GR2) — "1) If the data item referenced by identifier-1 is a zero-length item, the truth value of the class condition without the word NOT is false. 2) If the word NOT is specified, the truth value is reversed."
- **Code:** `src/Cobol.Net.Runtime/Values/Text/CobolClass.cs:28 (IsAlphabetic; identical defect at :37 IsAlphabeticUpper, :46 IsAlphabeticLower, :83 IsInClass), dispatched from src/Cobol.Net.Compiler/CodeGen/Emit/ConditionRenderer.cs:281-283 and :70-72` — IsAlphabetic/IsAlphabeticUpper/IsAlphabeticLower/IsInClass only null-check, then iterate the characters and `return true` when none violate the repertoire; for an empty (zero-length) string the loop body never runs, so they return TRUE. This contradicts GR1 (must be false). Note IsNumeric (:19) and IsNumericZoned (:59) correctly guard `string.IsNullOrEmpty(s) => false`, so only the alphabetic/user-class tests are wrong. RenderClass (ConditionRenderer.cs:267) emits the call with no zero-length guard, and the runtime call is not compile-time folded, so the wrong value reaches the program. IsInClass's own doc-comment even asserts the divergent "empty value is true vacuously".
- **Fails:** `IF DYN IS ALPHABETIC` where DYN is a zero-length operand (a dynamic-length item currently holding "", an OCCURS-DEPENDING group with a depending count of 0, or `X(1:0)` under REF-MOD-ZERO-LENGTH). ### CA8. [MINOR/high] Simple sign condition, Format 2 — a bare (unparenthesized) standard-floating-point data-name `data-name-1 IS [NOT] {POSITIVE|NEGATIVE|ZERO}`
- **Spec:** §8.8.4.7.4 GR2 (Format 2), with §8.8.4.7.3 SR1/SR2 distinguishing Format 1 vs Format 2 — "a) If the POSITIVE phrase is specified, the result is true if the sign of the content of the data item identified by data-name-1 is positive as specified for its basic floating-point interchange format, and false otherwise, regardless of whether the content of that item would evaluate to true in a NUMERIC class test or a ZERO sign test." (b) mirrors this for NEGATIVE. The NOTE: "a data item described with a standard floating-point usage may return a true value in either a POSITIVE or NEGATIVE sign test and also in a ZERO sign test." Format 1 SR1 explicitly excludes a standard-float data item, so a bare float name is Format 2.
- **Code:** `src/Cobol.Net.Compiler/CodeGen/Emit/ConditionRenderer.cs:257-259 (RenderSign); binder builds one shape with no Format-1/2 split at src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs:427` — RenderSign renders EVERY sign condition — including a bare standard-float data-name, which is a Format 2 condition — with the Format 1 algebraic test `v.Expr > 0` / `< 0` / `== 0` on the IEEE double. It never tests the IEEE sign bit, so it applies Format-1 (algebraic) semantics to a Format-2 operand. The binder (ConditionBinder.cs:427) creates one BoundSignCondition(kind,not) with no parenthesization/format flag, so `(FL) IS POSITIVE` (Format 1) and `FL IS POSITIVE` (Format 2) render identically.
- **Fails:** `01 FL USAGE FLOAT-LONG.  MOVE 0 TO FL.  IF FL IS POSITIVE ...` — FL holds +0.0 whose IEEE sign is positive, so spec Format 2 GR2(a) makes POSITIVE true (branch taken); code emits `(double)FL > 0` = `0.0 > 0` = false (branch NOT taken). Likewise `-0.0 IS NEGATIVE`: spec true, code `-0.0 < 0` = false; and a positive-signed NaN `IS POSITIVE`: spec true, code `NaN > 0` = false.

## File I/O (4 findings, 31 rules checked)

### CA15. [MINOR/high] READ of a LINE SEQUENTIAL file whose physical line exceeds the record area (max record size) — I-O status '06' and next-unread-char positioning
- **Spec:** §9.1.13.2 item 5 ('06'); §14.9.30 GR15 (READ, line sequential) — §9.1.13.2 item 5: 'I-O status = 06. - **Spec:** §14.9.14.4 GR5b (with §14.9.28.4 GR13a/GR13e augment semantics) — §14.9.14.4 GR5b: "The execution of an EXIT PERFORM statement with the CYCLE phrase causes control to be passed to an implicit CONTINUE statement immediately preceding the END-PERFORM phrase ..." — reaching the end-of-PERFORM loop control means the VARYING induction variable must still be augmented and the UNTIL condition re-tested (§14.9.28.4 GR13).
- **Code:** `src/Cobol.Net.Compiler/CodeGen/StatementEmitter.cs:137 (BoundExitPerform, F3Region.None arm emits `continue;` for Cycle) together with the induction-variable augment placed at the END of the loop body in ControlFlowEmitter.cs:277, 285, 306 (EmitVarying)` — For a VARYING loop the emitter writes the induction-variable augment (`I = I+1`) as a plain statement at the END of the `while` body (TEST BEFORE) — and for TEST AFTER the exit test `if(cond) break;` plus the augment sit after `body()`. EXIT PERFORM CYCLE emits a bare C# `continue;`, which jumps to the `while` condition re-evaluation and SKIPS the trailing augment (and, for TEST AFTER, also the exit test). The induction variable never advances, so the loop cannot terminate. Confirmed in generated pcyc.g.cs: `continue;` inside `while (!(I > 3L))` precedes `I = I+1;`.

Actual (verified from generated C#): the `continue` skips `I = I+1`, so I stays 2 forever — an INFINITE LOOP (program never terminates).

### CA36. [MAJOR/high] SEARCH / SEARCH ALL — unsuccessful-path exception dispatch when the AT END phrase is absent (EC-RANGE-SEARCH-INDEX / EC-RANGE-SEARCH-NO-MATCH)

### CA37. [MINOR/medium] SET dynamic-capacity-table (Format 14) executed during a SEARCH of the same table — EC-FLOW-SEARCH
- **Spec:** §14.9.39 GR31; §14.6.13.1.1 NOTE 3; §14.6.13.1.3 (fatal handling / #8 latitude) — GR31: "This statement shall not be executed during the execution of a SEARCH statement referring to the same table. If this rule is violated, the EC-FLOW-SEARCH exception condition is set to exist and the SET statement is not executed." NOTE 3: "An exception condition is set to exist only if checking for that condition is enabled ... If the exception condition occurs and it is not enabled, the results of the operation are undefined."
- **Code:** `src/Cobol.Net.Runtime/Values/Tables/CobolDynTable.cs:112-114 (SetCapacity)` — SetCapacity throws `new CobolFatalException("EC-FLOW-SEARCH", ...)` UNCONDITIONALLY whenever _searching>0 — regardless of whether EC-FLOW-SEARCH checking is enabled, and with no ambient guard (EC-FLOW-SEARCH is in neither FatalAmbientGates nor NonfatalAmbientGates in EcEmitter). So the throw is never caught for USE/Format-3 dispatch and terminates the run unit even in the default (checking-off) configuration. Every other auto-raised fatal EC in the runtime (e.g. ExceptionState.RefModError / FloatNotFiniteError) gates on its checking flag and returns leniently when off.
- **Fails:** Default settings (no TURN directives). A `SEARCH T ... WHEN cond  SET T CAPACITY UP BY 1 END-SEARCH` where the WHEN matches and T is OCCURS DYNAMIC: the SET runs inside the EnterSearch/ExitSearch bracket, so _searching>0 and the program terminates fatally. GR31 with checking off (NOTE 3: EC not set) defines the outcome as "the SET statement is not executed" (skip and continue). NOTE: §14.6.13.1.3 #8 grants the implementor latitude to terminate when checking is off, which weakens the checking-off case; the cleaner divergence is the checking-ON case, where the unguarded throw bypasses the required USE-declarative / Format-3 handler dispatch.

### CA38. [MINOR/low] Dynamic-capacity table growth beyond the implementor maximum — EC-BOUND-TABLE-LIMIT (fatal), via explicit SET or implicit growth
