### Canonical recipe — route a new FATAL EC through dispatch

To route a NEW FATAL EC (e.g. EC-FOO-BAR) through the ambient scaffold: (1) ExceptionCatalog.cs — register the name with Level 3, its Level2Parent, Fatal category, and introducedIn edition (if not already present). (2) ExceptionState.cs / ExceptionEngine — add `public bool FooBarChecking { get; set; }` and `public void FooBarError(string detail){ if (FooBarChecking) { Set(\"EC-FOO-BAR\", fatal:true); throw new CobolFatalException(\"EC-FOO-BAR\", detail); } }`; add the matching forwarding property + method to the static ExceptionState shim (~line 455/492). (3) Runtime raise site — at the actual operation (in CobolString/CobolNum/CobolDynTable/etc.) call `ExceptionState.FooBarError(detail)` BEFORE (or instead of) the lenient default; when checking is off the helper returns and the pre-existing lenient clamp/default stands, so a pre-EC build is byte-identical. (4) EcBinder.cs — decide gating: for a condition that can fire from ANY statement in a checking-on region add an ambient gate line in the QueryFor tail (~line 375): `if (ctx.EcState.Turn.Enabled(\"EC-FOO-BAR\", null, line)) enabled.Add((\"EC-FOO-BAR\", null));` (optionally guarded by a Contains-filter); for a condition tied to a specific node kind add a precise `case BoundXxx: Query([\"EC-FOO-BAR\"]); break;` in the QueryFor switch instead. (5) EcEmitter.cs — add `(\"EC-FOO-BAR\", \"FooBarChecking\")` to FatalAmbientGates (line 109). That is the whole emitter change: EmitArgOrPlain then automatically sets FooBarChecking=true, wraps the statement in try, emits `catch (CobolFatalException __af) when (__af.EcName == \"EC-FOO-BAR\")` that Set()s the last-exception status (if WITH LOCATION), calls `int __r = EcDispatchExpr(...)`, does `if(__r>=0){__pc=__r;break;}` for RESUME AT, and `if(__r!=-2) throw;` to terminate an unresumed fatal (reaching ProgramTable.RunMain→AbnormalTermination), with a finally that resets the flag. No DispatchEmitter/ProgramEmitter change is needed — __EcDispatch/__EcPerform already exist whenever the unit has F3 declaratives / an F3 PERFORM.

### Canonical recipe — route a new NONFATAL EC

To route a NEW NONFATAL EC (records the last-exception status only, never terminates, §14.6.13.1.4): (1) ExceptionCatalog.cs — register Level 3 with the NONfatal category. (2) ExceptionEngine — add `public bool FooChecking { get; set; }` and `public void FooError(string detail){ if (FooChecking) Set(\"EC-FOO\", fatal:false); }` (NO throw); add the shim forwarders. (3) Runtime raise site — call `ExceptionState.FooError(detail)`; the substitution/default result is applied by the caller REGARDLESS of checking (the condition is purely observational). (4) EcBinder.cs QueryFor tail — add the ambient gate `if (ctx.EcState.Turn.Enabled(\"EC-FOO\", null, line)) enabled.Add((\"EC-FOO\", null));` (or a precise case). (5) EcEmitter.cs — add `(\"EC-FOO\", \"FooChecking\")` to NonfatalAmbientGates (line 74). EmitChecked then wraps the statement with `ExceptionState.FooChecking = true;` … `finally { ExceptionState.FooChecking = false; }` and NO catch — nonfatal never throws, so no dispatch/__pc handling is emitted around it (a matching USE declarative / F3 WHEN can still SELECT it later via the last-exception status, but the statement itself simply continues). For a nonfatal EC latched at a KNOWN site with a statement phrase (STRING/UNSTRING-style), use the EmitOverflow helper pattern instead of an ambient gate: Set(name,false) then, only if no ON-phrase, EcDispatchExpr + `if(__r>=0){__pc=__r;break;}`.

### Verb-specific wrinkles the recipe must handle

- INVOKE / EC-OO: the fatal object-crossing ECs (EC-OO-UNIVERSAL, EC-OO-NULL, EC-OO-METHOD) are thrown DIRECTLY as `new CobolFatalException("EC-OO-...", ...)` at the __CobolInvoke sites in OoEmitter.cs (lines 259–370) and at ObjRequireNonNull — they do NOT go through FatalAmbientGates or a Checking flag; the CobolObject root raises EC-OO-METHOD via base.__CobolInvoke. A raised exception OBJECT (RAISE identifier-1 / RAISING identifier) is a SEPARATE channel: EmitRaiseObject uses ObjDispatchExpr→__EcObjDispatch (Format-4 declaratives, UnitHasF4), is NEVER fatal by itself, and propagates via the _propagatedObject slot (not _propagated).
- CALL / CANCEL: EC-PROGRAM-* and EC-EXTERNAL-* are thrown as CobolCallException (a DISTINCT type from CobolFatalException) from ProgramTable.CallProgram/Cancel and caught SEPARATELY at RunMain — a new CALL-family EC uses CobolCallException, not FatalAmbientGates. The call site's ON EXCEPTION/ON OVERFLOW converts it (siteHandlesPropagation / GR3h). EC-EXTERNAL uses the two-mask handshake (ExternalCheckMask set by the emitted CALL site, moved to ActivatorExternalMask across the activation boundary, saved/restored/re-zeroed). GOBACK/EXIT…RAISING stages via _propagated, consumed by the CALL-site pickup or ApplyPropagationDefault (fatal→terminate an EC-off activator).
- F3-PERFORM cross-activation isolation: CallProgram snapshots PerformDepth and TrimPerformTo on return so a callee's raise is not intercepted by the caller's active WHEN frame; an F3 METHOD raises the frame-stack floor on entry (RaisePerformFloor, §9.10.1-C2) so its own unmatched raises don't hit the activator's WHEN. RunTopFrame walks innermost→floor and marks visited frames Handling (GR21) to avoid re-catch.
- SET Format-14 (SET capacity, OCCURS DYNAMIC): EmitSetCapacity emits CobolDynTable.SetCapacity/CapacityUpBy/DownBy; the GR31 EC-FLOW-SEARCH (a SEARCH of the same table is active) is raised INSIDE the runtime table, not via an ambient gate. Implicit dyn-table growth past expected capacity is the nonfatal EC-BOUND-OVERFLOW ambient gate. SET SIZE (Format-16, dyn-length) uses a per-statement BoundSetSize.CheckStorage bool (bound-time TurnState) to gate the nonfatal EC-STORAGE-NOT-AVAIL — a precise-flag alternative to the ambient gate.
- SEARCH (CA36, §14.9.37.4 GR1b2): a SEARCH with EC-RANGE checking ON but NO AT END phrase does NOT use FatalAmbientGates (these range ECs are nonfatal, Set fatal:false). ControlFlowEmitter tracks the raised EC-RANGE-SEARCH-INDEX/-NO-MATCH in a __searchEc local and, at the shared AT-END funnel, dispatches through Ec.EcDispatchExpr (>=0→__pc jump/break for RESUME AT; -1/-2/-3 fall through to search-end). This requires ControlFlow.Ec wired by UnitEmitters (line 89). When an AT END phrase IS present, it takes precedence and no dispatch is emitted.
- EC-I-O: routed not by an ambient flag but by a per-statement compile-time __mask (IoMaskFor) into __IoCheckEc, which bridges I-O status→EC (ExceptionCatalog.IoEcOfStatus), runs the F1 file/mode + F3 GR3c–g + GR4b outward-GLOBAL tiers, and throws CobolFatalException only for a fatal I-O status class. A statement with no enabled EC-I-O emits the plain __IoCheck (byte-identical).
- Nested / contained programs: the GR4b outward-GLOBAL continuation is __outer.__RunGlobalUse (ProgramEmitter.EmitRunGlobalUse) — currently exercised only on the I-O (__IoCheck / __IoCheckEc) path; __EcDispatch does NOT yet walk outward for GLOBAL F3 declaratives (recorded as a deep-dive limitation).

_Machinery notes:_ The dispatch-result protocol is shared by __RunUse/__EcDispatch/__EcPerform/__IoCheckEc/RunTopFrame and is the contract every fix must preserve: -1 = declarative completed / no action; -2 = RESUME AT NEXT STATEMENT (fall through past the raising statement, suppresses fatal termination); -3 = no qualifying handler; >=0 = RESUME AT procedure-name's pc (the caller does `__pc = __r; break;`, i.e. GO TO). The zero-scaffolding invariant is load-bearing: every artifact is gated (Turn.AnyEnabled, UnitHasF3/F3Perform/F4, HasIoChecked) so an EC-free unit emits byte-identical source — a new gate/flag must keep that true (checking-off ⇒ the runtime helper returns leniently, the binder emits no wrapper, the emitter emits no guard). The serial surface is small and hot: ExceptionState.cs (engine + shim), ExceptionCatalog.cs, EcBinder.cs, and EcEmitter.cs are touched by essentially every EC-gate fix, so EC-infra fixes cannot be parallelized across worktrees without collision — they must land serially. Two DISTINCT fatal exception TYPES reach RunMain (CobolFatalException for EC-conditions and raw runtime raise-points; CobolCallException for CALL/CANCEL/FUNCTION-NOT-FOUND) — a new fatal EC picks the family by its raise mechanism, and only the CobolFatalException family participates in the FatalAmbientGates statement-guard RESUME path.
