- **D-FRA — the record area of a file whose record is a dynamic-length item, a variable-length group or a pointer,
  and the record image such a record sends and receives** (2026-09-22; kb/Work PB981, row `GR-13.18.33.4-3`).
  §2023:13.18.33.4 GR3 makes every level-1 entry of an FD or SD *"implicit redefinitions of the same area"*, and no rule
  forbids those records from being a dynamic-length item, a variable-length group (§2023:8.5.1.12.1) or a level-1
  pointer (§2023:13.18.60.3 SR14); §2023:12.4.6.4.4 GR2 extends the same sharing to the files of a record-area SAME clause.
  The standard does not say where such an item lives — *"Dynamic-length elementary items may be physically located
  in memory within the record they are subordinate to, or they may be located elsewhere in the computer's memory"*
  (§2023:8.5.1.10.3), its internal structure is implementor-defined (§2023:8.5.1.10.2), and a pointer or message tag is a managed slot (A.1 items 210/212/216) — but it does say how the item BEHAVES: *"a variable-length data item behaves in all
  respects as though it were in fact contiguous with its neighbors whenever a procedural operation is applied to a
  group containing it"* (§2023:8.5.1.11.2). GnuCOBOL, IBM Enterprise COBOL and Micro Focus do not admit a dynamic-length
  item in the file section at all (IBM 6.4: WORKING-STORAGE, LOCAL-STORAGE and LINKAGE only), so there is no
  implementation to follow. **WiseOwl COBOL's determination:** (i) such a record is an OUT-OF-LINE record — it does not
  overlay the file's character record area, which the file's other records share as before; (ii) a READ or RETURN
  makes the CURRENT RECORD, at its own length, available in every out-of-line record of the area (and of the
  SAME-clause peers): a dynamic-length record takes it as its new content (§2023:8.5.1.10.4), a variable-length group is
  decomposed left to right — each dynamic-length item takes as many characters as the record holds beyond the
  fixed material still to come, up to its maximum size, and the fixed members take their own positions (a
  dynamic-capacity table is never a member here: it "may be defined in any place, other than the file section",
  §2023:8.5.1.9.1 3)) — and a pointer or message-tag record takes the 8-position token the file carried (A.1 items 212/216; kb/Work PB4838), while an
  object-reference record is not reached (it has no character image, so its value is unchanged); (iii) a WRITE, REWRITE or RELEASE of an out-of-line record sends its contiguous image at its current
  extent — the variable-length group's members concatenated exactly as DISPLAY shows them (A.1 item 57), a
  dynamic-length record's content, a pointer or message-tag record's 8-position token (an object-reference record sends the zero-length image); (iv) the implicit RECORD clause
  (§2023:13.18.43.4 GR5, *"defined by the implementor"*; A.1 item 147 in §7, for an FD and an SD entry alike) is **Format 2** when a record is variable-length — minimum with
  every dynamic item at zero length, maximum with each at its maximum size (GR8) — and Format 1 otherwise, as
  before; **an EXPLICIT Format 1 clause keeps the file FIXED** whatever its records hold (§2023:13.18.43.4 GR6, "Format 1 is
  used to specify fixed-length records"; §2023:9.1.6 makes the record type and size fixed file attributes every program
  using the file shares — kb/Work PB1562; the form such a record takes is (vi)), integer-1 being the file's record
  size and the area's width, which §2023:13.18.43.3 SR3 keeps every description within; and SR3 / SR4 now SCREEN such a record — GR8 b)'s maximum for a dynamic-length item is its
  maximum size (§2023:8.5.1.10.1: the smallest of its LIMIT, the largest integer its prefixed usage stores and the
  implementor maximum, A.1 item 62) and its minimum is zero (§2023:8.5.4 item 4), so `RECORD CONTAINS 20` over an
  unbounded dynamic member is COBOL2010 (it used to be skipped, on the ground that GR8 had nothing to sum);
  (v) **a variable-length group record is sent WITH ITS EXTENT TABLE** (kb/Work PB1053) — each
  variable-length component's fixed-run offset and current length — because with two or more such components the
  contiguous image alone cannot be inverted (a record `"AA" "KEY" "CCCC"` and a record `"AAKEY" "CCC" "C"` are the
  same characters, and the fixed member between them would be read from the wrong ones). The table is implementor
  information "on the physical storage medium" beside the record — the §2023:9.1.7.2 licence the record-length header
  already uses — and, like that header, it is never "reflected in the record area or the record size" (§2023:12.4.5.11.4
  GR1): the record is still exactly the contiguous image of (iii). Every organization that FRAMES its records
  carries it (a RECORD VARYING record-sequential frame, every relative and indexed frame — `RecordFraming`), the
  sort store carries it from RELEASE (and the USING transfer) to RETURN (and the GIVING transfer), and a READ /
  RETURN hands it back beside the current record. The split in (ii) then uses the record's own table whenever the
  receiving group's components CORRESPOND to it — "Two dynamic-length elementary items correspond if they start
  at the same relative byte positions within their groups" (§2023:8.5.1.12.2) — and the table describes the very
  characters received; each component takes exactly the characters it was written with, so every layout
  round-trips, however many variable-length members flank a fixed one or sit side by side. A record that carries
  no table — written through a character record or at a RECORD VARYING DEPENDING length other than its composed
  one, held in a LINE SEQUENTIAL file (a line is plain text with no frame: (x)), or received by a non-corresponding group — is split by the take step of (ii): exact for ONE
  variable-length member wherever it sits, the earlier member taking the excess with several. An in-place
  sequential REWRITE (§2023:14.9.35.4 GR16 fixes the frame's size) replaces the frame's table with the new record's when
  it has as many components, and otherwise VOIDS it (every offset -1, which corresponds to no layout) rather than
  leave a table describing the replaced record. (vi) **a file of FIXED-length records carries a variable-length record
  in its FIXED FORM** (kb/Work PB1562; `CobolContiguousLayout.ToFixedForm`) — a file whose RECORD clause is an explicit
  Format 1 (§2023:13.18.43.4 GR6) is plain blocks of integer-1 bytes with no frame, and §2023:9.1.6 makes its record type and
  size attributes the SAME for a second program that describes the file as `RECORD CONTAINS 20` over `PIC X(20)`,
  which must read the same bytes. So (v)'s table has nowhere to live, and no control information that depends on one
  program's record description can be added to the physical record (§2023:13.18.43.4 GR2 licenses control information
  "required by the operating environment", and the environment's requirement is a function of the file's type and
  size, not of a description the other program does not have). Each such record therefore occupies the ONE shape
  every record of the file shares: every dynamic-length member at the position it has when it holds its MAXIMUM size
  (its §2023:8.5.1.10.1 maximum size — the LIMIT — which is the maximum §2023:13.18.43.4 GR8 b) sums for the record, as PB1276 reads it, so
  that `A` limit 9, `KY` X(3), `C` limit 8 are bytes 1-9, 10-12 and 13-20),
  space padded, the remainder of the integer-1 bytes spaces; a READ takes each member back at that width and drops
  its trailing spaces, so a member that does not end in a space round-trips exactly. **The one loss is stated:** in
  a fixed-size field a trailing space is padding, never data (the same convention as a line sequential record,
  §2023:14.9.51.4 GR21), so `"AB "` is written as `"AB"`'s bytes and reads back with length 2. The form is the same in
  every organization — sequential, relative and indexed (witnessed for each: `conformance:cases/13.18.43-RECORD/pb1562_variable_group_under_fixed_record_clause`, `…/pb1880_variable_group_under_fixed_record_clause_relative` and `…/pb1880_variable_group_under_fixed_record_clause_indexed`, which also pin the invalid-key, delete and start arms) — and an indexed RECORD KEY a dynamic member precedes is
  one plain window at its fixed-form offset, the key a second program names (§2023:9.1.7.4: a key's number of components, length and relative positions "are fixed file attributes"); a REWRITE's record-name-1 size is the
  maximum layout (§2023:13.18.43.4 GR13 — the number of bytes in the record — compared by §2023:14.9.35.4 GR16), and a dynamic-length ELEMENTARY record is its content padded to integer-1 and read back
  without the padding. A file whose RECORD clause is Format 2 or 3, or is absent (the implied Format 2 of (iv)),
  keeps (v): its frames are variable-length records. **Rejected readings:** framing the Format 1 file as
  variable-length records with the extent table (the first PB1562 landing: a second program describing the file as
  `PIC X(20)` got OPEN '39' on a relative file and read the framing bytes as data on a sequential one); keeping the
  contiguous image and padding it (the table cannot be carried, and the split is lost — the original defect); a
  trailing-space-exact encoding (information-theoretically impossible in integer-1 bytes: 20 bytes cannot hold
  every length pair of two dynamic members and their content). **Rejected readings of the whole:** refusing the source (the
  previous staged-loud posture; no rule forbids it); treating the file's character bytes as the dynamic item's
  storage (the item's content would be bounded by the area and padded by it, contradicting §2023:8.5.1.10.4's "the new
  value becomes the content of the item"); a length-prefixed record image FOR AN ITEM THAT NAMES NO STRUCTURE (the
  length field is the representation a DYNAMIC LENGTH STRUCTURE clause names, §2023:8.5.1.10.2, and an item whose clause
  names none has not asked for it — a NAMED structure is given exactly that form in the record, D-DL3 — and for the
  unstructured item it would put the lengths INSIDE the record
  a character record of the same area, a RECORD VARYING DEPENDING item and a key position all read, where (v) keeps
  them in the frame); refusing at bind a record the take step cannot invert (legal source, and the physical form
  is the implementor's to choose); the take step alone for every record (the previous posture — PB1053 measured
  `A=[AAKEY] KY=[CCC] C=[C]` for the record written as `AA` / `KEY` / `CCCC`). **EXTERNAL** (kb/Work PB1026): §2023:13.18.22.4 GR4 b)
  makes "the data contained in all record description entries" of an EXTERNAL file external, so an out-of-line
  record of such a file is run-unit storage of its own, shared by every describer — keyed by the FILE's
  externalized name (GR5) and the record's ordinal among the file's out-of-line records in declaration order,
  since GR5 externalizes no record name; a pointer-class record is carried the same way (§2023:13.18.22.3 SR4 restricts
  the clause "specified for a data item", and here it is specified for the file). (A SORT/MERGE or indexed key that
  follows a variable-length member is D-KWV below.) **(vii) A WRITE, REWRITE or RELEASE under a SAME RECORD AREA
  clause makes the released record available in the other records of the area** (kb/Work PB1195; §2023:14.9.51.4 GR4,
  §2023:14.9.35.4 GR6, §2023:14.9.32.4 GR3 — *"The logical record is also available as a record of other file-names
  referenced in the same SAME RECORD AREA clause ..., as well as the file associated with record-name-1"*), through
  the same two halves a READ uses: the shared CHARACTER area takes the record's image when the released record is
  itself out of line, and each OTHER out-of-line record of the area (`FileModel.OutOfLineRecordsOfArea`) takes the
  record at its released length (GR13) with its extent table — only after a SUCCESSFUL statement, and decided at
  compile time so a program with no out-of-line record in the area renders as before. The READ side is completed
  alike: a file whose every record is out of line has no character window of its own, and its READ now reaches the
  character window of a clause peer (`SequentialIoEmitter.EmitRecordAreaStore`). **(viii) A record holding an OCCURS DEPENDING table of VARIABLE-LENGTH elements** (kb/Work PB2497) — each occurrence holds a dynamic-length item, so §2023:8.5.1.12.1 makes it a variable-length group — is a record type like any other: a WRITE, REWRITE or RELEASE sends the first K occurrences' current images, K being data-name-1's value at the start of the statement (the sending operand's count, §2023:13.18.38.4 GR8 a for a data-name-1 outside the record, GR8 b for one inside it; when the file description has the VARYING phrase of the RECORD clause, GR9 has the program set it to the occurrences written), with the extent table of (v), which then describes exactly the components of those occurrences. The record's LENGTH cannot say how many occurrences it holds (the elements have no fixed width, and data-name-1 is data, not layout), so a READ or RETURN takes the count from, in order: **the record's own extent table** when it travelled and describes the record — the number of components it describes, each occurrence bringing the same number (`OdoTail.CountFrom`); **the maximum** for the fixed form of (vi), where every occurrence sits at its fixed-form position (the writer pads the occurrences it holds and the file's fixed length fills the rest with spaces, which is their fixed form); and otherwise **data-name-1**: the record is decomposed at the table's maximum — the receiving record area's maximum length, §2023:13.18.38.4 GR8 b) — which places a data-name-1 the record holds itself (§2023:13.18.38.3 SR20 puts it before the table: *"The data item defined by data-name-1 shall not occupy a byte position within the range of the first byte position defined by the data description entry containing the OCCURS clause and the last byte position defined by the record description entry containing that OCCURS clause"*), and then again at data-name-1's value, clamped to the table's bounds; a data-name-1 outside the record keeps its value from the start of the statement (GR8 a). The first decomposition places data-name-1 exactly when no variable-length member precedes it; when one does, the maximum's fixed run leaves that member too little of the record, so when data-name-1 does not read back the count it was decomposed at, the record is decomposed at the SMALLEST count, from the table's minimum, at which data-name-1 reads that count back (the take step's own preference for the earlier member), and at the first count again when none does. The decomposition is (ii)'s take step, exact for a record with one variable-length member at that count and otherwise giving the earlier member the excess, as (ii) states. The same layout locates an indexed or sort key (at the extent table's count, else at the maximum). **Rejected readings:** refusing the record (the previous loud; no rule forbids it, and every other variable-length record already round-trips); taking the count from the record's length (it has none to give); the maximum alone for a record that carries no table (it splits a one-occurrence record into the wrong positions, where data-name-1 recovers it exactly). **(ix) A record whose OCCURS DEPENDING table of fixed-image elements is counted in BITS** (kb/Work PB3030) — a USAGE BIT item lies beneath it, and §2023:8.5.1.6.3 places a bit item *"at the next bit position in storage"*, so its occurrences share bytes — sends the member that holds the table to the ceiling, in characters, of its bits at the sending count (§2023:15.50.4 rule 9's rounding), and its record layout states the table as the last component in CHARACTERS from the character that holds the table's first bit, one character per unit (`OdoTail.RecordUnit` / `RecordMaxUnits`): the record's length then says the table's character extent, which is all a record of characters can say, since an occurrence that shares a byte has no character boundary of its own. A READ / RETURN takes the record's characters whole, as (ii) takes any trailing component; the bits of the last character past the count are whatever the writer's image held there, as they are past the count of any sending group. A receiving group that uses only part of such a table (§2023:13.18.38.4 GR8 a) keeps its later occurrences at the BIT (`OdoTail.KeepUnused`), its declared struct and its storage cell alike. **Rejected readings:** one element per unit in characters (a bit occurrence is not a character, and the per-occurrence character width rounded up overstates the table); refusing the shape (the previous named stage COBOL1756; no rule forbids it). One producer — `OdoModel.FixedImageTail`, read by `GroupImageCodec` and by a cell-backed group's `VarGroupWindow`. **(x) A LINE SEQUENTIAL file carries no extent table, and what the standard asks of its READ is the contiguous image and nothing finer** (kb/Work PB1563; a record with two or more dynamic-length members, which `"AA" "KEY" "CCCC"` under `LIMIT 9` / `X(3)` / `LIMIT 8` reads back as `"AAKEYC" "CCC" ""`). *The derivation.* **(1) A line is plain text.** §2023:12.4.5.10.3 GR2: *"Each record in a line sequential file is terminated by an implementor-defined line delimiter"*, and §2023:9.1.7.2: *"In line sequential files the length of each record is determined by the number of characters between the preceding line delimiter and the following line delimiter or the end of file if no line delimiter is present"* - every character between two delimiters IS the record, so (v)'s table has nowhere to live, and an encoding written INTO the line (a separator or a length field) would hand a second program that reads the file as `PIC X(n)` characters the writer never wrote, exactly the reading (vi) rejects for a fixed-length file; and the only characters such an encoding could use are the ones below U+0020, which are outside the line sequential character set (A.1 item 115) - a WRITE of a record that holds one is '71' (§2023:14.9.51.4 GR23), so the encoding would also be indistinguishable from data. GR2's *"The range of allowable characters in a line sequential file is implementor-defined"* licenses the SET of characters, never information added beside the record (that licence is §2023:9.1.7.2's, for RECORD sequential files only). **(2) What the READ must deliver.** §2023:14.9.30.4 GR13 c): *"the record is made available in the record area"*, with GR15 padding it on the right with spaces to the record descriptions' minimum size (every dynamic member at zero length, §2023:13.18.43.4 GR8 a)) or truncating it at their maximum ('06'); and §2023:8.5.1.11.2: a variable-length item *"behaves in all respects as though it were in fact contiguous with its neighbors whenever a procedural operation is applied to a group containing it"*. So after the READ the group's contiguous image - what DISPLAY, MOVE, a comparison and `FUNCTION LENGTH` (§2023:15.50.4 rule 7) see - is EXACTLY the line, padded or truncated by GR15. That holds for every line by construction: the take step only ever PARTITIONS the image. **(3) Where one dynamic member ends and the next begins inside that image is stated by no rule**: §2023:8.5.1.12.2's correspondence (*"start at the same relative byte positions within their groups"*) relates two groups' storage, not a medium, and no READ rule speaks of members. It is the implementor's. GnuCOBOL, IBM Enterprise COBOL and Micro Focus do not admit a dynamic-length item in the file section (above), so there is nothing to follow (CLAUDE.md rule 1) and the choice is (ii)'s take step - the one split every medium without a table uses, so a record is decomposed the same way whether it arrives from a line, a block file written by another program or a sort store. It is exact for a record with ONE dynamic member wherever it sits, and for any record whose earlier members were written at their maximum; otherwise the earlier member takes the excess and the member lengths differ from the ones written, with the record itself unchanged. The write side is the same convention as (vi)'s: §2023:14.9.51.4 GR21 does not transfer *"any spaces to the right of the rightmost non-space character"*, so trailing spaces of the last member are padding, not data, and a WRITE, a REWRITE (GR17 sends no table either) and the sort's USING and GIVING transfers to or from a line sequential file all agree. **(4) No diagnostic is required**: no rule of §2023:12.4.5.10.3, §2023:14.9.30.4 or §2023:8.5.1.11 makes the repartitioning an error or asks for a warning, a layout with one dynamic member loses nothing, and the compiler cannot tell which layout the program's lines will hold, so none is issued. A program that needs member-exact round trips uses a file that frames its records (record sequential, relative or indexed: (v)). **Rejected readings:** an in-line encoding (above); a sidecar file holding the table (a second file the standard does not know, lost when the line file is copied or edited); refusing the source (no rule forbids the record; CLAUDE.md rule 3); a different split for lines only (a second rule for the same ambiguity). **The REWRITE sibling** (found with it): §2023:14.9.35.4 GR17 a) refuses a REWRITE only after a READ that transferred PART of the line, and the connector decided "part" against the record area's character window (`RecordWidth`, the fixed run of a variable-length group) where GR15 truncates at the descriptions' MAXIMUM size (`FileConnector.MaxRecordSize`), so a whole 9-character line of a 3-character fixed run made every REWRITE of that record '44'; `SequentialConnector.NextFrame` now asks the one bound the READ's truncation asks. **The READ '09' sibling** (found by the branch review): §2023:14.9.30.4 GR16's *"the record area contains one or more characters not in the implementor-defined character set for a line sequential file"* asks about the DELIVERED record area, which for a variable-length group is the whole contiguous line and not its fixed run, so `SequentialConnector` asks the character set of the delivered line at its own width (a control character in a dynamic member past the fixed run is '09' exactly as the WRITE's GR23 and the REWRITE's GR17 d) answer '71' for it). Witnessed by `conformance:cases/12.4.5.10-ORGANIZATION/pb1563_line_sequential_dynamic_members` (the success paths and the statuses '00', '06', '10', '44', '46', '47', '48', '71', with a USE procedure and FILE STATUS, and with FILE STATUS alone), by `conformance:cases/12.4.5.10-ORGANIZATION/pb1563_line_sequential_dynamic_members_exceptions` (READ '09' past and inside the fixed run and in the remainder of an over-length line; REWRITE '43', '49', '71' and the unchanged line; '51' on a READ, a READ with RETRY and a REWRITE against a record another connector locked, and the REWRITE that succeeds once the lock moved; a SORT whose USING file is absent, '35', and whose GIVING file cannot be created, '30') and, for the exceptions that have neither a FILE STATUS nor a USE procedure and so end the run unit (§2023:9.1.13.1 - '46', '43', '71', and the SORT's '35'), by `LineSequentialDynamicMembersAbnormalTests`; and by the refusal `conformance:cases/12.4.5.10-ORGANIZATION/pb1563-line-sequential-dynamic-members-below-2023`.
