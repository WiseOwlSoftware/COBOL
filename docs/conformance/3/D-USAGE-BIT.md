- **D-USAGE-BIT — USAGE BIT — alignment and representation of data (§2023:13.18.60.4 GR5 · §2023:8.5.1.6.3).** Annex A.1 has NO item for USAGE BIT — it runs 208 (COMPUTATIONAL, GR6) straight to 209 (DISPLAY, GR7), and §2023:8.5.1.6.3 is cross-referenced only by item 195 (SYNCHRONIZED) — so this determination is recorded here under §2023:4.2.6 rather than in the A.1 register, where it sat under item 209’s number until 2026-09-03. A `USAGE BIT` item **occupies bits**, as GR5 requires. Bits per character position is **8** — §2023:8.1.2 leaves it implementor-specified, and 8 is what makes it agree with DISPLAY's one byte per character position. Alignment follows §2023:8.5.1.6.3 exactly: a bit item immediately following an elementary bit item **of the same level** takes the next bit position (they share a byte); any other bit item starts at the first bit of the next available byte; implicit filler advances to the next item's natural boundary and fills a trailing partial byte to an integral number of characters, and §2023:15.50.4 r5 counts that filler. A bit group that follows a same-level bit item begins in the middle of a byte, and the byte boundaries inside it (every "first bit position of the first available byte", and an ALIGNED subject, §2023:13.18.1.4 GR1) are boundaries of the **record**, not of the group (kb/Work PB3158). A bit group whose first item begins on a byte boundary (it is ALIGNED, say) begins on that boundary too — §2023:8.5.1.6.3 "the alignment of the start of a group item and the alignment of the first item within that group, when the first item is a bit data item, are at the same bit position in storage" — so the filler before it belongs to the enclosing group, and a REDEFINES subject of that shape requires a byte boundary (§2023:13.18.44.3 SR15; kb/Work PB3167). **A TABLE whose element is a bit group holding such a member** (an ALIGNED member, §2023:13.18.1.4 GR1, or any member §2023:8.5.1.6.3 puts at "the first bit position of the first available byte") lays out differently at each bit position it could begin at, and §2023:13.18.1.4 GR2 ("An ALIGNED clause specified for a multiple-occurrence data item applies to each occurrence of that item") puts the ALIGNED member of EVERY occurrence on a byte of the record. **WiseOwl COBOL's DETERMINATION** (kb/Work PB3167; the owner may overturn it): the occurrences of such a table are a whole number of bytes apart — the element's width rounded up to a byte — so every occurrence begins at the same bit position within a byte as the first and is laid out exactly as the first, and implicit filler bits between occurrences (none after the last, §2023:8.5.1.6.3 generates filler only "for the next item") make up the difference. This keeps the one length §2023:13.18.38.4 7) gives "the subject of the entry", and it is the per-occurrence filler §2023:13.18.55.4 8) b) states for a synchronized table ("generated for each occurrence of those data items") and IBM Enterprise COBOL's slack bytes between the occurrences of a synchronized table; GnuCOBOL 3.2 rejects GROUP-USAGE BIT ("reserved word, but isn't supported"), so it offers no reading. Rejected: laying each occurrence at the next bit position after the last, which makes the first occurrence's members sit at other offsets and its length differ from the later ones'. So `05 BA PIC 1(2) USAGE BIT. 05 SUB GROUP-USAGE BIT OCCURS 3. 10 SA PIC 1 USAGE BIT. 10 TA PIC 1(5) USAGE BIT ALIGNED.` puts SUB(k) at bit 2 + 16(k−1) and TA(k) at bit 8 + 16(k−1), and the group is 45 positions; a table whose element holds no such member is packed bit by bit, unchanged. In a record image a bit run is **packed high-order bit first** — §2023:8.5.1.6.3 numbers positions from "the first bit position" — followed by its implicit filler bits. **The implicit filler is STORAGE of its group** (kb/Work PB3564): §2023:8.5.1.6.3 describes the bits that advance alignment to the next item's boundary and the bits that complete the last byte of a record group — and, through §2023:13.18.1.4 GR2, the bits between the occurrences of an ALIGNED table — "implicitly ... as a filler elementary bit data item", so a group MOVE (§2023:14.9.25.4 GR4: an alphanumeric move, no conversion), a READ, a MOVE of m boolean positions to a bit group (§2023:13.18.29.4 GR1b: its filler positions are part of m) and a group VALUE (§2023:13.18.63.4 GR5: the group area is initialized without regard to the items in it) write those positions, and the next DISPLAY, comparison, MOVE or WRITE of the group reads them back: `MOVE "AB" TO G1` over `05 G1-B PIC 1 USAGE BIT. 05 G1-X PIC X.` displays `AB`. Their initial state is zero (§2023:13.18.63), an elementary store to a neighbouring member never changes them, and INITIALIZE without the FILLER phrase leaves them alone and INITIALIZE ... WITH FILLER makes them receivers (§2023:14.9.20.4 5) a) 2.: implicit FILLER items). The record-struct lane holds each in a hidden string field of the group's struct (`BitLayout.FillersOf` is the one list, `PhysicalModel` declares the fields, `GroupImageCodec` packs and unpacks them); a REDEFINES class, an EXTERNAL or BASED record and a LINKAGE area hold the bits in the shared bytes themselves, so both lanes read a group alike. **The three shapes registered as kb/Work PB3598, as determined.** (1) *A run that holds an OCCURS DEPENDING table.* Its tail is measured at the table's maximum count, and a stored field holds the positions past the maximum extent, which no occurrence owns. That filler is data of the group at every count: it is moved with the characters it lies in, by an ordinary group's receiving store (a group with no dynamic-length item or dynamic-capacity table is a fixed-length group, §2023:8.5.1.12.1, so its move is an alphanumeric move of whole characters, §2023:14.9.25.4 GR4) and by a variable-length group's, which moves it as one of "each character position that is not occupied by a corresponding table" (§2023:14.9.25.4 GR9 a: an OCCURS DEPENDING table is no corresponding table, §2023:8.5.1.12.2 "Two tables correspond if at least one of them is a dynamic-capacity table", so every character position moves; `OdoTail.KeepUnused`). The bits that end the current extent's last character at a count BELOW the maximum are not filler: §2023:8.5.1.6.3 generates the filler after "the last data item in a record", which is the table at its maximum, so those bits are the first unused occurrence's, whose content "is undefined" (§2023:13.18.38.4 7)) and which §2023:13.18.38.4 8) a) leaves out of the operation. The two receiving stores differ there only where the standard leaves the content undefined, which is implementor latitude (§2023:13.18.38.4 7), 8) a)), and both conform: an ordinary group's alphanumeric move writes whole characters (the sender's bits), a variable-length group's store keeps the receiver's bits of the unused occurrences, the choice made since kb/Work PB3030 (`_unassigned/pb3030_bit_odo_run_continuation`; the bits spelled for T(4) and T(2) in `pb3598_odo_bit_run_tail_variable_group` are that choice, not the standard's, and only the filler bits are bound by §2023:14.9.25.4 GR9 a)). INITIALIZE ... WITH FILLER therefore resets the stored positions beyond the maximum extent and no in-range bit (a depending item inside the group makes the group a receiver at its maximum length, §2023:13.18.38.4 8) b); outside it the unused occurrences are not used). Witnesses `conformance:cases/14.9.25-MOVE/pb3598_odo_bit_run_tail_travels_with_the_group` (ordinary groups) and `pb3598_odo_bit_run_tail_variable_group` (variable-length and cell-backed groups). (2) *The padding of an element of a dynamic-capacity bit table* (`05 T PIC 1(3) USAGE BIT OCCURS DYNAMIC`) is **not an implicit filler item and is not stored; it reads zero in every image** (DETERMINATION, the owner may overturn it). Each element is out-of-line storage of its own ("table data items are not required to be contiguous in physical memory. The size, location, and time of physical allocation of a dynamic-capacity table are implementor-defined", §2023:8.5.1.9.1 3)), so §2023:8.5.1.6.3's filler "to advance alignment to a required natural boundary for the next item within that group" has no next item to advance to; the five bits that round a 3-bit element up to its character are the rounding of its length (§2023:15.14.4 4), which an elementary item at level 77 or 01 has too and which §2023:8.5.1.6.3's NOTE says generates no filler); and a group MOVE carries the table's elements, never those bits ("Correspondingly numbered elements are moved according to the rules of the MOVE statement", §2023:14.6.9.2), so no statement but INITIALIZE ... WITH FILLER could name them, and it names only the implicit filler items. Witness `unit:DynamicBitElementPadTests`. (3) *A strongly-typed group carried as a leaf vector* carries its filler after its members (see below). The filler of a strongly-typed group that crosses an activation boundary as its leaf vector travels with the vector (after its members), and the tail of a run in a record-struct group that holds the canonical of a Tier-B REDEFINES class is stored beside the class's backing (the canonical's own bits are the backing's, the tail follows them in the group's layout; kb/Work PB3597). INITIALIZE ... WITH FILLER resets the filler everywhere it is stored — in a REDEFINES class, an EXTERNAL or BASED record and a LINKAGE area through one bit item per gap of the shared bytes, in the record-struct lane through its hidden field — with ZEROES or a REPLACING BOOLEAN sender; the bits between the occurrences of an ALIGNED table are n - 1 items in both lanes, and the sender reaches each gap on its own (kb/Work PB3597). ⚠ The item's VALUE CARRIER is a `'0'`/`'1'` string, which is not observable to a COBOL program and is not a conformance claim; what is claimed is the SIZE, ALIGNMENT and IMAGE above. A boolean item with **no** USAGE clause is a different case: §2023:13.18.60.3 SR13(b) implies DISPLAY and GR7 makes it one alphanumeric character per boolean position. **A FILE's record area follows the same image** (§2023:9.1.2: the record area is storage; kb/Work PB680): a `USAGE BIT` record, elementary or a bit leaf in an alphanumeric group, is sent and received as its PACKED bytes — `ceil(bits / 8)` characters, the trailing filler bits as the record group holds them (zero until a move writes them; §2023:13.18.43.4 GR4 makes the value of the filler bits that complete the last byte of a logical record undefined, so a file written by another program may leave anything there, which a READ stores and a WRITE sends back) — by every I-O verb (sequential, line sequential, relative and indexed WRITE / REWRITE / READ, `WRITE FROM` / `READ INTO`, SORT / MERGE `USING` / `GIVING` and `RELEASE` / `RETURN`), never as its `'0'`/`'1'` carrier. Witnesses: `conformance:cases/13.18.60-USAGE/pb680_bit_record_area_file_io` (sequential, relative, indexed and SORT/MERGE, read back through a second connector whose record is `PIC X`), `pb680_bit_record_area_line_sequential` (LINE SEQUENTIAL, 2023), `pb680_bit_record_area_file_exceptions` (the I-O statuses 04, 10, 35, 41, 42, 46, 47, 48 and the USE declarative on such a file) and the negative `pb680-bit-record-area-below-2002`.
