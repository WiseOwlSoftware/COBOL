---
heading: "### 3.3 The communication facility at COBOL-85 and 2002 (kb/Work PB4677)"
---
WiseOwl COBOL implements the facility ISO/IEC 1989:2002 Annex A prints as optional and obsolete and COBOL-85 prints as its communication module (owner decision 12 of PB4614,
2026-11-04), with a message control system of its own. `docs/rearchitecture/DESIGN-communication-facility.md` is the design and the user's reference for `mcs.json`. At 2002 each construct
draws the obsolete-element warning COBOL0903; from 2014 it is removed, COBOL0902. These are its determinations:

| Item | Determination |
|---|---|
| The message control system (E.5.1) | The runtime is the MCS: the directory `WISEOWL_COBOL_MCS`, else the current directory, holds the user's definitions in `mcs.json` and the MCS's state in the paged store `mcs.store`, so run units on one machine communicate through it. Every statement is one statement of the store engine, under its cross-run-unit mutex. With no `mcs.json`, every symbolic name is unknown. Two device-bearing names (destinations that deliver to no queue, terminals) that are identical or differ only in case would be one device file on a case-folding host, so the definition file is refused (status 91) on every host |
| A program scheduled by the MCS (A.1.2.3 GR6, GR28) | A process acting for the MCS sets `WISEOWL_COBOL_MCS_SCHEDULED`, the queue's levels separated by `/` or the terminal's name. WiseOwl COBOL itself starts no program. Unset, the names are spaces. The message that caused the scheduling is the head message of that queue structure or terminal at the time the program runs, so the first RECEIVE referencing the INITIAL input-output CD returns it (§1985:XIV.2.2.4 GR25), and the terminal named in data-name-3 is fixed from the first statement (GR30): a program that changes it makes every statement referencing the CD unsuccessful with status 21, "Symbolic source is unknown. No action taken." (`ScheduledProgramTests`, `MessageControlTests.ScheduledTerminal_ChangedBeforeTheFirstStatement_IsUnknown`) |
| RECEIVE: when data is not available (2002 B.1 item 116) | The designated structure holds no complete message. Without NO DATA the run unit waits, polling the store |
| The choice among unnamed levels (E.5.5.3, E.5.5.4) | Alphabetical by symbolic name, each level first in, first out |
| Status key 9x (2002 B.1 item 28; Table A.1) | `91` the definition file cannot be used. `92` the host refuses the store or a device's file, or cannot carry the store's lock (the host's locks answer `Unavailable`: a file system with no byte-range or open-file-description locks, or one where the lock-file host cannot publish a lock): the MCS never runs unlocked, and never relies on a share-none open, which .NET on Unix leaves to an advisory `flock` that such a file system declines silently. The statement takes no action: the CD's area changes only in its status key, nothing the run unit sees of the store or a device has changed, and a retry finds what the first attempt found, so a program that retries on 92 delivers once. `93` the store refused the statement and the MCS cannot tell whether it landed (the reopen that decides is refused too): the CD's area changes only in its status key, but the statement may have taken effect, so a program that retries on 93 can deliver twice. A RECEIVE passes control as if data had been made available on each. (DESIGN-communication-facility.md §6 "Status 92 takes no action") |
| Error key A-Z (2002 B.1 item 27; Table A.2) | None is defined. '0' is written for a destination with no error |
| Error keys of a statement refused before its destinations (§1985:XIV.2.2.4 GR22; kb/Work PB5281) | A wrong KEY on ENABLE or DISABLE OUTPUT (status 40), and a SEND of text longer than its item (50) or of no text (60), take no action, and still write every occurrence 1 to DESTINATION COUNT, as GR22 requires: 1 for a destination the MCS does not know, otherwise what Table 2 says of the destination as it is (5, already enabled or disabled, for ENABLE and DISABLE; 2, disabled, for SEND), else 0. The statement's own condition is the status key's. A destination count out of range (status 30) names no occurrence, so none is written |
| Communication devices (A.2.6.3 GR1, GR2, GR12, GR14-GR18) | Oriented to variable-length messages: a destination with no `deliverTo` and a terminal append each complete message as a line of the file `<name>.out`, written at the device's committed end (the store records it), so what a dead or refused statement left past that end is overwritten by the next message and cut by the first statement of the next run unit. Vertical positioning is not applicable, so the MCS ignores ADVANCING and REPLACING LINE. The line end after each message is the device's message delimiter, not a character of the message: each message begins "on the next available character position of the communication device" (§1985:XIV.3.6.4 GR2), the first one after the delimiter |
| A destination named more than once in the DESTINATION TABLE of one SEND (§1985:XIV.3.6.4 GR6) | Each occurrence is a destination of the statement: the message is delivered once per occurrence, each copy the whole message with its own segment and message control, and each occurrence's error key is set on its own (kb/Work PB5306, PB5288). A PURGE names the same occurrences, so each occurrence purges its own partial message |
| ACCEPT MESSAGE COUNT and a message partly received (§1985:XIV.3.1.4 GR1; §1985:VI.6.24.4 GR3; kb/Work PB5285, PB5339) | A message a run unit has begun to receive is still in the queue until its last portion is returned, so every run unit's count includes it, the run unit that holds the remainder and another one alike: the store records the partly received message (`PartialReceives`) with its owner run unit, and a run unit that ends takes the remainder with it (14.5.10 rule 2, §1985:VI.6.24.4 GR3), so a message partly received by a run unit that is gone is dropped and never counted |
| The source of a received message (§1985:XIV.2.2.4 GR10; kb/Work PB5280) | The symbolic source names a source or a terminal of the MCS's definitions; any other name, such as the name of the destination a message was sent to when that destination defines no source, is not known to the MCS and the source is spaces |
| A statement that fails and the terminal of an input-output CD (§1985:XIV.2.2.4 GR31; kb/Work PB5283) | The first statement referencing the CD fixes SYMBOLIC TERMINAL whatever its status: a later statement after a change is unsuccessful (SEND, status 20; RECEIVE, PURGE and ENABLE or DISABLE I-O TERMINAL, 21) |
| The size of SEND's identifier-1 (§1985:XIV.3.6.4 GR3; §1985:IV.4.3.4; kb/Work PB5378) | At --std 85 the size of an elementary data item and of a group item is the number of characters in standard data format, so the text length is counted, and the text transferred, in those characters for both: an elementary binary or packed item is its digits (9(4) COMP is 4; a signed one carries its sign fused onto its last digit, the S being no counted character, §1985:VI.5.9.4 GR8d, so S9(4) COMP is 4 as well), and a group is its storage image with each such item replaced by its digits (a group of `XX` and `9(4) BINARY` is 6, FUNCTION LENGTH's 4 being its storage). From 2002 a group is its storage image; the 2002 text is not in the specs this repository carries, so that edition's elementary arm is unchanged |
| Special control characters in a message (2002 B.2 item 52) | Carried as data |
| A portion left at the end of the run unit (2002 B.2 item 53; 14.5.10 rule 2) | It lives in the run unit and is gone with it, as is the remainder of a message begun |
| A negative ADVANCING identifier (2002 B.2 item 54) | Ignored with the rest of the phrase |
| The KEY phrase at COBOL-85 (§1985:XIV.3.2.4 GR7, §1985:XIV.3.3.4 GR6; kb/Work PB5287) | The password of an endpoint defined with `key`; a wrong value is status 40 and takes no action, as CCVS-85 CM102M expects. The standard leaves the rules for a match to the implementor, so the value and the password are compared as alphanumeric operands, the shorter extended with spaces (§2023:8.8.4.2.7): trailing spaces count in neither, and a password of spaces matches a key of spaces. An endpoint with no `key` admits any value. A statement with no KEY phrase has nothing to match and is honored against a passworded endpoint too, while a written KEY is always matched, so a KEY of spaces against a password that is not spaces is status 40: omitting the phrase and writing a blank key differ. The 1985 text leaves this to the implementor. It made the phrase optional ("The KEY phrase of the DISABLE statement has been placed in the obsolete element category and has been made an optional phrase", §1985:p.XVII-84) without saying what an omitted phrase does; the password is the implementor's ("KEY phrase of DISABLE statement. Password is built into the system", §1985:p.XVII-93, and the same for ENABLE); and "the rules for determining when the value in the KEY phrase matches the system password are not specified, thereby resulting in a situation defined by the implementor" (§1985:p.XVII-84). Read word for word, GR7 would refuse every statement without the phrase even where no password exists, making mandatory the phrase 1985 had just made optional. GnuCOBOL 3.2 does not implement the module and IBM Enterprise COBOL provides none, so the precedence of CLAUDE.md rule 1 yields nothing (kb/Work PB4996, held-row adjudication of `1985-GR-XIV.3.2.4-7` and `1985-GR-XIV.3.3.4-6`). CCVS-85 is no ground either way: every ENABLE and DISABLE in CM101M to CM105M, CM201M, CM202M, CM303M, CM401M and DB205A writes KEY |
| A SEND with no FROM (§1985:XIV.3.6.4 GR9, GR10, GR11; kb/Work PB4996) | The indicator is carried as an empty portion with that indicator: it closes the current segment, and with EMI or EGI the current message. So after an EMI a lone EGI is an empty message that ends the group: a RECEIVE returns it with END KEY 3, MESSAGE COUNT counts it, and a device receives an empty line. ESI then EMI gives the segment and an empty segment that ends the message (END KEY 2). The text says that "If identifier-1 is not specified, only the indicator is transmitted to the MCS" (GR9), that "The MCS will recognize these indications and establish whatever is necessary to maintain" segment, message and group control (GR10), and that "An EGI need not be preceded by an ESI or EMI" (GR11), which makes a preceding EMI optional, not equivalent. How the MCS keeps group control is the implementor's. The lone EGI cannot be attached to the message the EMI ended: that message was released whole and may already have been transmitted or received ("the MCS will not transmit any portion of a message to a communication device until the entire message has been released to the MCS", GR6). GnuCOBOL 3.2 does not implement the module and IBM Enterprise COBOL provides none (kb/Work PB4996, held-row adjudication of `1985-GR-XIV.3.6.4-10`) |
| FILLER in a CD entry (§1985:XIV.2.2.3 SR6, SR15; §1985:XIV.2.2.4 GR2; kb/Work PB4996) | FILLER may replace a member of the series of data-names, the entry's second option; a clause of the first option names a data-name, and FILLER there is refused, COBOL6169 (omit the clause instead). "Within this series any data-name may be replaced by the reserved word FILLER" (SR6, SR15) could refer to the enumeration of the clauses' data-names or to the series option, and the text decides for the series: GR2 is where the standard calls an option of this entry a series ("The second option may be used to replace the above clauses by a series of data-names which, taken in order, correspond to the data-names defined by these clauses"), FILLER is needed only there because a positional member cannot be left out while a clause can, and the Format 2 entry, which has clauses and no series option, prints its uniqueness rule (SR10) without the FILLER sentence. GnuCOBOL 3.2 admits FILLER in neither option, so the precedence of CLAUDE.md rule 1 yields no contrary practice (held-row adjudication of `1985-SR-XIV.2.2.3-6` and `-15`) |
| ENABLE and DISABLE I-O TERMINAL and a message the MCS holds (§1985:XIV.3.3.4 GR1, GR4; §1985:XIV.3.2.4 GR5; §1985:XIV.3.5.4 GR5; kb/Work PB4996) | ENABLE and DISABLE I-O TERMINAL open and close the terminal's link to the MCS. A message the MCS already holds for the terminal (seeded, or entered while the path was active) is received whether or not the path is active; a SEND while the path is inactive is status 10 and is held until ENABLE. GR4 activates "the logical path between the source (as defined by the content of the data item referenced by data-name-3 (SYMBOLIC TERMINAL)) and the program", and GR1 places that path outside the MCS-to-program link: "The logical path for the transfer of data between the COBOL programs and the MCS is not affected by the ENABLE statement". Whether a message the MCS holds has crossed the source's link is the implementor's, because "The conditions under which data is not made available are defined by the implementor" (§1985:XIV.3.5.4 GR5). GnuCOBOL 3.2 implements no MCS and IBM Enterprise COBOL provides no communication module, so WiseOwl's design stands (DESIGN-communication-facility.md §6 "Logical paths"; held-row adjudication of `1985-GR-XIV.3.3.4-4`) |
| ENABLE and DISABLE INPUT and the logical paths (§1985:XIV.3.2.4 GR3, GR4; §1985:XIV.3.3.4 GR2, GR3; kb/Work PB5286) | The statements act on the path between each source and each queue, not on one flag per endpoint: DISABLE INPUT of a queue closes it and every queue below it against every defined source, ENABLE INPUT TERMINAL opens a source against every queue, and either reopens what the other closed. 15 is the answer when every path and endpoint state the statement names was already as asked (DESIGN-communication-facility.md §6 "Logical paths") |
