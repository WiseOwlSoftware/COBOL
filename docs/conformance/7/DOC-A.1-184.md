The ALPHANUMERIC class is not empty (owner decision kb/Work PB793, following the surveyed model implementations where the standard leaves a point open and the vendors split); what each name MEANS is item **183**. The NATIONAL class IS empty and item **185** is therefore vacuous: the native national character set is the UTF-16 repertoire (determination D-N1) and the standard's own `UCS-4` / `UTF-8` / `UTF-16` keywords already name the ISO/IEC 10646 forms, so no national code-name would name a set that is not already reachable. The OTHER words that may stand alone in an alphabet definition are the general format's own keywords - `NATIVE`, `STANDARD-1`, `STANDARD-2` in the ALPHANUMERIC branch; `NATIVE`, `UCS-4`, `UTF-8`, `UTF-16` in the NATIONAL one; `LOCALE` in either - and the 12.3.7.4 GR10 figurative constants of a one-operand literal phrase. A word the source element declares as a constant-name is literal-1 of a literal phrase (13.10.3 SR2, kb/Work PB1942) and is never read as a code-name: ⚠ DETERMINATION — where one spelling could be both, the program's own declaration of the word wins over the implementor's system-name, the same answer the LOCALE clause's external-locale-name-1 gets (item 181). Any OTHER bare word is a source error, **COBOL1907** `alphabet-code-name`, whose message names the supported set from the table itself. &#x26D4; That refusal closes an under-rejection that was also a WRONG ANSWER: an unrecognized code-name used to be reinterpreted as a LITERAL PHRASE SPELLING OUT ITS OWN LETTERS, so `ALPHABET A-ASC IS ASCII` built an alphabet whose first four positions were A, S, C, I and every downstream reference (PROGRAM COLLATING SEQUENCE, SORT, SYMBOLIC CHARACTERS ... IN, CLASS ... IN, CODE-SET) read that (kb/Work PB770 leg e). The supported set is ONE table (`ImplementorCodeNames`), read by the binder, by the coded-character-set reference sites and by the diagnostic alike, so the names, their meanings and the message can never disagree.
