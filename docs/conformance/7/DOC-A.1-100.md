EC-CONTINUE-IMP, EC-EXTERNAL-IMP and EC-MCS-IMP are COBOL-2023 names; below 2023 they are refused with COBOL0878. EC-SCREEN-IMP and EC-VALIDATE-IMP belong to the screen and VALIDATE modules, which this implementation does not provide (Annex A.4.2, A.4.14). They are refused wherever they are written, with COBOL1707 and COBOL1710. The other 20 can be used in `>>TURN`, `RAISE EXCEPTION` and wherever an exception-name is allowed. Table 13 leaves their fatality to the implementor (Imp), and this implementation treats every one as fatal. An unhandled one ends the run unit abnormally, and so does a `RAISE EXCEPTION` of one with checking not enabled. **Meaning: the implementation itself sets only EC-PROGRAM-IMP and EC-MCS-IMP.** EC-PROGRAM-IMP is set only when a contained program is activated while the program that contains it has no instance (an internal consistency failure of the program table, reported as 'internal: contained program ... activated while its container is not instantiated'). EC-MCS-IMP is set by SEND and RECEIVE for any failure of the message control system itself (an unusable socket directory, a socket error that is not a partner's end; D-MCS-CHECK), when checking for it is enabled. The implementation never sets any of the others, so a program sees them only when it raises them itself. EC-I-O-IMP is Table 13's 'I-O status 9x' condition, but the only 9x status WiseOwl COBOL defines, '90', carries EC-I-O-LINAGE instead (item 110). EC-RAISING-IMP is never set at run time either. The names and fatality are `ExceptionCatalog` (EcFatality.Imp); the one raise site is `ProgramTable.ParentInstance`, through the default exception-name of `CobolCallException`. A conforming program does not reach that site: it guards an internal inconsistency, because the §2023:8.4.6.3 scope rules admit a caller of a contained program only from inside its container's own subtree, and that caller's activation keeps the container instantiated. Every other level-2 `-IMP` name is raised only by the program's own `RAISE EXCEPTION`.
