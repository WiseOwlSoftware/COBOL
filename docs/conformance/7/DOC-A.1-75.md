A connector with no sharing mode specified locks as the implementor-default mode (item 77). The lock lasts until the connector is closed, **except for a relative or indexed file in an active APPLY COMMIT clause (§2023:14.9.6.4 GR9, §2023:14.9.7.4 GR4, §2023:9.1.16; kb/Work PB3480, PB3484): its CLOSE keeps the file lock, the handle that is it and every record lock the connector holds until the next COMMIT or ROLLBACK, or the run unit's end (§2023:9.1.18.5).** The connector's own re-OPEN carries them on, and a connector a registration displaces or an object's deletion drops (§2023:12.4.6.3.4 GR5: a canceled element's clause stays active until a COMMIT or ROLLBACK deactivates it) goes on being the COMMIT's and the ROLLBACK's until then. **Record locks and keyed records cross run units too (kb/Work PB2660).** A RELATIVE or INDEXED connector also holds each record lock it takes as an exclusive byte-range lock (shared and then tested for an `OPEN INPUT` connector on Linux) on one byte of its physical file far beyond any record, derived from the record's identity, so another WiseOwl COBOL run unit's access to that record answers **51** (§2023:9.1.13.8 1)) and a `RETRY` waits for it; and the store is kept coherent across run units by a byte-range statement mutex on the file, held through the connector's own handle (exclusive through a writable one, shared through a reader's; a statement that holds it shared writes nothing, even beside a writable connector of its own run unit, kb/Work PB3335). A RELATIVE or INDEXED connector under every sharing mode but `SHARING WITH NO OTHER` (kb/Work PB3333, PB3334; `docs/rearchitecture/DESIGN-runtime-library.md` §2.2.1.7) runs each record statement, and its OPEN's adoption of the file, under the mutex: the statement reads ONE page (the store's work meta page) to learn whether another run unit changed the file since this one last saw it, and when it did adopts that page's trees and drops its page cache; it then reads the pages it touches and writes the pages it changes, and the work meta page, before the mutex is given back, so every statement is one step to every other run unit; a `SHARING WITH NO OTHER` connector, which no other run unit can open beside, writes its pages at every statement with no mutex. An indexed record's n + 1 entries (its frame and one entry per alternate key) change in that ONE statement, so no run unit ever reads half of another's change and no update is lost to another's CLOSE. These locks are an agreement among WiseOwl COBOL run units: another program sees them only if it takes the same byte-range locks (or, on macOS, the same lock files, below). A SEQUENTIAL connector publishes its record locks the same way, naming a record by its ordinal (kb/Work PB2692). The reverse direction also holds: when the host refuses a WiseOwl COBOL OPEN because another process, in any language, holds the file under an incompatible lock or share mode, the OPEN fails with I-O status **61** (§2023:9.1.13.9 1)); a DELETE FILE refused the same way gets **62**. **On Windows** the lock is the host share mode of the connector's own handle, which is mandatory and per-access, so every process on the machine is bound by rules 1–3, and the connector also publishes its Table 19 column (kb/Work PB3482): it holds exclusively one byte, chosen at random, of that column's 2^32-byte range at 2^62 + 2^61 + 2^60 + 2^32 × the column's number (the same 0 to 4 number the Linux byte offset carries) through a read handle of its own, and, before the OPEN succeeds, tests the ranges of the five columns its request row refuses (its own column's range with its own byte left out), so every WiseOwl COBOL run unit is arbitrated by Table 19 across processes as on Linux; a `SHARING WITH NO OTHER` connector publishes nothing, because its handle is exclusive and refuses the read handle and every other open itself. A share mode refuses by ACCESS, so one case it cannot say is carried by the column: an INPUT opener that still owes its transaction's writes (APPLY COMMIT, kb/Work PB3337) holds a handle open for writing, which the `FileShare.Read` of a `SHARING WITH READ ONLY` request refuses, although Table 19 prints *Normal open* for that request beside an INPUT opener. An INPUT opener that owes writes publishes that with its column (one more exclusive byte, of a sixth 2^32-byte range at 2^62 + 2^61 + 2^60 + 5 × 2^32; kb/Work PB3499), and a request refused by the host with its column held, while another WiseOwl COBOL run unit's connector owes writes, is therefore OPENed again with `FileShare.ReadWrite` (`FileLockPosture.WhenOwedWritesAreAdmitted`); every request Table 19 refuses is still refused, by the columns. **Determination:** a program outside the protocol that holds the file open for writing still refuses a READ ONLY request '61', whether or not a WiseOwl COBOL INPUT opener that owes no writes is open beside it; only when an INPUT opener that owes writes is, the share mode cannot tell its writer from the outside one and the READ ONLY connector's handle admits both for the rest of its OPEN. The one thing a share mode cannot refuse is the truncation by an `OPEN OUTPUT` (Table 19 prints *Unsuccessful open* in every OUTPUT cell), so an `OPEN OUTPUT` on an existing file first requests exclusive access of the host and is refused with **61** if any handle holds it, before anything is truncated (on Linux the region lock refuses the OUTPUT like every other cell). **On Linux (x86-64 and arm64, kernel 3.15 or later, a filesystem that holds byte-range locks)** the connector also holds an advisory open-file-description byte-range lock (`fcntl` `F_OFD_SETLK`) on the physical file — its Table 19 column, published as a shared lock on one byte far beyond any record — and, before the OPEN succeeds, tests the five columns its request row refuses for another holder (`F_OFD_GETLK`), so every WiseOwl COBOL run unit is arbitrated by §2023:9.1.15 Table 19 across processes as it is inside one; the lock is removed by the CLOSE (or an unsuccessful OPEN) and dies with a run unit that terminates. Only a regular file is locked: a device node such as `/dev/null` carries no region lock (it is not a file whose bytes another run unit can damage, and the lock would otherwise arbitrate every run unit on the machine that assigns it). The share mode (`flock`) is still taken on the connector's own handle, so rule 1 also excludes an outside process that takes `flock`. **A program in another language, or one that opens the file without taking either lock, is neither stopped nor detected** except by the share mode's strength on that host (on Linux and macOS a shared `flock`, which refuses a writer only under NO OTHER); a program in another language is bound by rules 2 and 3 only if it takes the same region locks (the byte layout is `RunUnitFileLock`'s). **On macOS** (and every Unix that is not Linux on x86-64 or arm64, kb/Work PB2484) the same table is carried by a LOCK FILE PER HOLDER instead of a byte-range lock: the connector creates `.wolk-<16 hex digits>/<column>-<guid>` in a directory beside the physical file (the digits are the SHA-256 of the file's name under the host's case rule, `HostFile.PhysicalFileKey`; the column is the same 0 to 4 number the Linux byte offset carries) and holds it open, so that .NET takes an EXCLUSIVE `flock` on it; before the OPEN succeeds it tests the lock files of the five columns its request row refuses by asking for a SHARED lock on each, which only a live holder's file refuses (so two run units testing one leftover at the same instant never read each other as a holder, kb/Work PB2917), and the kernel drops the `flock` with the descriptor, so a run unit that is killed holds nothing. Two OPENs at the same instant cannot both pass (each publishes before it tests, and a holder never counts its own file); the CLOSE (or an unsuccessful OPEN) deletes the connector's lock file before it closes the descriptor and the directory with its last file, and a leftover of a killed run unit is deleted by the next OPEN. The lock is measured, not assumed: right after creating its file the connector asks for exclusive access to it, and a host that does not refuse that (a network file system without `flock`, `DOTNET_SYSTEM_IO_DISABLEFILELOCKING`) or a directory the process may not write beside the file leaves the connector with the share mode alone, exactly as an unavailable region lock does on Linux. The classic `fcntl` locks macOS offers cannot stand in (closing any descriptor of the file drops them, `fcntl` is variadic, which Apple's arm64 calling convention passes differently from a fixed P/Invoke signature, and its open-file-description commands are private). Differences from Linux: two spellings of one file reach one lock directory under the host's case rule (on macOS `Cust.dat` and `cust.dat` are one file), a symbolic or hard link remains a second spelling, a device such as `/dev/null` is unlocked only because no lock directory can be created beside it, and a FIFO in a writable directory is arbitrated like any other file (Linux excludes it by file type). **The record-lock and store-mutex halves of the cross-run-unit protocol above are carried the same way on macOS (kb/Work PB2936).** Each held byte of the region map (the store mutex, the lock-presence byte, one hashed byte per record) is a lock file in the SAME lock directory named `r<the byte as 16 hex digits>-<S or X>-<guid>` (shared or exclusive), published before it is tested exactly as a column is: an exclusive hold is refused by any other live holder of the byte, a shared one by an exclusive holder, so a second run unit's READ WITH LOCK of a record the first holds answers **51** (§2023:9.1.13.8 1)) and two run units no longer overwrite each other's keyed store, as they did before PB2936, silently. A WAITING hold (the store mutex) retries after a jittered pause until the holder gives the byte back. **Determination — a holder the process cannot observe.** A lock file this process may not open (another user's under a restrictive umask, or an entry that is not a file) is neither free nor swept (kb/Work PB2917): a request that its column refuses is refused **61** (§2023:9.1.13.9 1)), a non-waiting record hold answers **51**, and a WAITING hold, which cannot wait for a release it cannot see, proceeds without the cross-run-unit mutex for that statement (the run unit then has the guarantees it can keep alone). The price is that a killed run unit's leftover that nobody may read or delete refuses requests until its owner or an administrator removes the `.wolk-*` directory: a refusal is loud, where a silent grant loses a lock. **Several users.** The lock directory is created with the permissions of the physical file's directory and its files with the directory's read and write bits, not the first holder's umask, so a second user of a shared directory can publish into it and read the first user's files; a user who may not write the lock directory cannot publish its own column, but a live or unobservable conflicting holder still refuses it, and with none its OPEN has the share mode alone, exactly as an unavailable region lock does on Linux. A user who may enter the lock directory but not LIST it cannot look at all: every holder is unobservable to it, so its OPEN is refused ('61') wherever its request row refuses a column, and a record lock it requests without waiting is held by another ('51').
