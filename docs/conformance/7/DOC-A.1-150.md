**LINE-SEQUENTIAL** names the line sequential file's method of item 151 (b), each record ended by the line delimiter, and makes the file a LINE SEQUENTIAL file in every respect the statements and the run time see (its records variable-length, READ PREVIOUS and OPEN REVERSED not available, the 1985 AT END rule still in force), also at COBOL-85, where no ORGANIZATION phrase for it exists. **The record rules are the edition's own** (kb/Work PB5903; before 2023, where no line sequential file exists, the delimiter is only the method of determining the length of a variable length record, and “Any method used will not be reflected in the record area or the record size used within the program” (§1985:VII.2.8.4 GR1), so a record is written at its size, trailing spaces included, and a READ of a line shorter than the minimum or longer than the maximum record size is §1985:VII.4.4.4 GR13's record length conflict, '04', the long line truncated with no remainder. **Before 2023 the delimiter is the record boundary and nothing else** (`SequentialConnector.LineDelimiterOnlyFrames`): the vertical positioning of an ADVANCING phrase or a LINAGE page has no image on that medium (kb/Work PB5984). §1985:VII.4.7.4 GR12 establishes the successor relationship “by the order of execution of WRITE statements” and GR16 gives the ADVANCING phrase “control of the vertical positioning of each line on a representation of a printed page”, a phrase §1985:C.3 (its item 19) makes “dependent upon a device capable of vertical positioning”; a delimited file is no such device, and a line end, form feed or carriage return written for the positioning would read back as a record of its own or inside one. So every WRITE, ADVANCING or not, writes its record and one delimiter, and LINAGE-COUNTER and the end-of-page conditions still follow the logical page. GnuCOBOL 3.2, whose LINE SEQUENTIAL organization is an extension at `-std=cobol85`, writes the blank lines and reads them back as records; that choice contradicts GR12 and is not taken. The REWRITE of such a file is the sequential REWRITE (kb/Work PB5915): '44' with the file unchanged unless the record has as many character positions as the whole line the READ took (§1985:VII.4.5.4 GR10, §1985:VII.1.3.5), never 2023's GR17 c) pad-and-succeed; a record of those character positions whose characters take another number of bytes on the medium (A.1 item 115) cannot replace the line in place and is '44' too. A record area holding a character outside the line character set is refused at WRITE and REWRITE alike with the status the edition gives §2023:14.9.51.4 GR23's '71' (kb/Work PB5882), an implementor-defined unsuccessful status before 2023. The two syntax rules whose subject is the WRITTEN LINE SEQUENTIAL phrase of the ORGANIZATION clause (§2023:12.4.5.2 SR12 on RESERVE, §2023:13.4.5.3 SR4 on BLOCK CONTAINS and RECORD CONTAINS) do not reach such a file. BINARY-SEQUENTIAL on a file whose ORGANIZATION clause writes LINE SEQUENTIAL names a method the file cannot have and is refused. **Every other word is refused (COBOL7598)**: a word the implementor associates with no method is no implementor-name, so accepting it would accept source the general format does not print; GnuCOBOL's fourth arm, a warning “not recognized; will be ignored”, is a leniency and is not taken. Neither name is a reserved word: each is recognized from the clause operand's text (`RecordDelimiterNames`, the one table), so a program may still declare a data-name or a paragraph spelled BINARY-SEQUENTIAL or LINE-SEQUENTIAL (§1985:IV.4.2.2.1, §2023:8.3.2.1 SR4).
