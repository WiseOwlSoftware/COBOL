GR7 i asks for three things per name, and Table 6 gives code-name-1 a Y in both the coded-character-set and the collating-sequence column, so each name answers all three.<br>**`ASCII` - the ISO/IEC 646 International Reference Version.** *Coded character set:* the 128 characters of ISO/IEC 646 IRV. *Ordinal number of characters:* 128; ordinal n is the character at ordinal position n of that set. *Correspondence with the native alphanumeric character set:* the IDENTITY on U+0000-U+007F - ordinal n corresponds to native character U+(n-1) - because the first 128 positions of the native alphanumeric character set ARE ISO/IEC 646 IRV (item 188 / determination D-N1). *Collating position of each character:* its native collating position, i.e. the sequence IS the native order, which is what 12.3.7.4 GR7 c already says of the STANDARD-1 keyword (\"The collating sequence referenced by both the STANDARD-1 and STANDARD-2 phrases shall be as defined by the order in which characters appear in ISO/IEC 646\"). `ASCII` is therefore a supported SPELLING of a set the standard also names; it is provided because other implementations spell it that way and a program that does is not otherwise portable. No runtime carrier is emitted for it.<br>**`EBCDIC` - IBM CCSID 37 (code page 037, \"EBCDIC US/Canada\").** *Coded character set:* the 256 characters of CCSID 37. *Ordinal number of characters:* 256; ordinal n is the character CCSID 37 assigns to code unit n-1. *Correspondence with the native alphanumeric character set:* the CCSID 37 code page itself - the whole table, derived at compile time from .NET's `Encoding.GetEncoding(37)` and never transcribed (`ImplementorCodeNames.SingleByteCodePage`). It is a bijection of the 256 code units onto exactly the 256 native characters U+0000-U+00FF. *Collating position of each character:* a character the page spells takes the position equal to its CCSID 37 code unit (so X'81' `a` &lt; X'C1' `A` &lt; X'F0' `0`, the reverse of the native order on both pairs). **Every OTHER native character** - the 65,280 UTF-16 code units above U+00FF that CCSID 37 does not spell - **takes a position greater than every specified one, in unchanged native relative order**: this implementation adopts 12.3.7.4 GR7 k3's own rule (\"Any characters of the native collating sequence that are not specified in the literal phrase shall assume a position in the collating sequence that is greater than that of the highest character specified in this literal phrase. The relative order within the set of these unspecified characters is unchanged from the native collating sequence\") as its GR7 i specification, so every native character has a position and none shares one. Those characters are NOT members of the coded character set: they have no ordinal and no medium representation, so no SYMBOLIC CHARACTERS or CLASS ordinal reaches them and a CODE-SET record containing one cannot be written (13.18.13.4 GR6 b). **HIGH-VALUE / LOW-VALUE under this sequence** (12.3.7.4 GR8/GR9): LOW-VALUE is the native character CCSID 37 puts at code unit X'00'; HIGH-VALUE is U+FFFF, the last character of the unspecified tail the GR7 k3 rule above places after the page's 256 (owner decision kb/Work R52 — the whole native repertoire, not the Latin-1 block, kb/Work PB1093). On a `CODE-SET IS EBCDIC` medium HIGH-VALUE is written as X'FF', the coded character set's highest code unit (owner decision kb/Work R51 item 4; `CodeSetConversion.HighUnit`), and X'FF' reads back as HIGH-VALUE. **Which EBCDIC**, surveyed rather than assumed: CCSID 37 is the canonical registered complete single-byte EBCDIC page and the z/OS default, i.e. the one the compiler whose users write `ALPHABET ... IS EBCDIC` means; GnuCOBOL's own default translation table corresponds to no registered CCSID and its named alternates are CCSID 500 variants, so following its LATITUDE (which names are accepted) does not mean adopting its table - none of its tables or sources are used here.
