cells: ["DOC-A.1-71", "**FILE-CONTROL entry, ASSIGN clause — TO phrase meaning and rules**, §2023:12.4.5 SR5 and SR6, required + documented", "§2023:12.4.5.1 prints the TO phrase as a LIST — `ASSIGN [TO] {device-name-1 | literal-1} …`, the ellipsis on the inner brace pair in every format — and §2023:12.4.5.2 SR5 makes \"the meaning and rules for the allowable specification of device-name-1 and the value of literal-1\" the implementor's. **The determination (CLAUDE.md rule 1: ISO leaves it open → GnuCOBOL, whose documented form is a device word followed by one file name): the TO phrase is EITHER one operand, which names the physical file, OR a DEVICE CLASS — `DISK` or `PRINTER` — followed by one operand, which names the physical file.** Both device classes denote a file of the host file system, so the class word selects nothing further: `ASSIGN TO DISK \"a.dat\"` and `ASSIGN TO \"a.dat\"` name the same file. Every other list — two file names, three or more operands, a literal before another operand, or a leading word that is not a provided class (a console device such as `KEYBOARD` is not: a file connector here is always a host file) — is refused BY NAME, **COBOL2256**, citing SR5 and this row. **What an operand names:** literal-1's value, or device-name-1's spelling, is mapped to a host path by `CobolFile.ResolveHostPath` — a target already carrying a `.`, `/` or `\\` is used verbatim; any other is lowercased and given a `.txt` extension in the current directory — the same mapping item 73 applies to data-name-1's content. The host path is then made ABSOLUTE against the current directory at the association, and that absolute spelling is the physical file's identity to the run unit: Table 19's arbitration and the keyed record stores compare it case-insensitively on Windows and macOS and case-sensitively elsewhere (`HostFile.PhysicalFileComparer`, kb/Work PB2748), so `data.dat` and `./data.dat` are one physical file and, on Linux, `Cust.dat` and `cust.dat` are two; a symbolic or hard link remains a second spelling. **A word that is BOTH a declared constant-name and a device-name-1 (kb/Work PB2500):** §2023:12.4.5.1 admits `{device-name-1 | literal-1}` at one position, §2023:13.10.3 SR2 admits a constant-name wherever a format specifies a literal, §2023:8.3.2.1 4) lets one word be a system-name and a user-defined word, and §2023:12.4.5.2 SR5 leaves the meaning of both to the implementor, so the standard does not say which reading wins. ⚠ DETERMINATION (ISO leaves it open → GnuCOBOL, which substitutes the declared constant): **the program's own declaration of the word wins** — the same answer the LOCALE clause's external-locale-name-1 (item 181) and the ALPHABET clause's code-name (item 184) already give. A word that names a constant entry is literal-1 \"as if … written\" (§2023:13.10.4 GR1) and meets §2023:12.4.5.2 SR4 as a written literal does (an alphanumeric literal, not zero-length; a numeric, national, boolean or zero-length constant is **COBOL2645**, naming the constant), a constant whose own entry was refused reports at the entry only, and a word that names no constant is device-name-1, its own spelling. In a two-operand list the leading word is read as the device class when it spells one even if the program declares a constant of that spelling (the only allowable two-operand list is class + name, and the constant reading would be a list of two names); the second operand is read as any single operand is. The word reaches `AssignTargetRule.WordText` through `LiteralEnvironment.ReadConstant`, the one constant lookup the SPECIAL-NAMES and AS-phrase positions already use. **SR6 (the syntactical combinations with data-name-1):** all three are allowed — the TO phrase alone, `ASSIGN USING data-name-1` alone, and both together, in which case §2023:12.4.5.3 GR3 b) lets the content win (item 10). The list is read in ONE place, `AssignTargetRule.Resolve`; the grammar (`CobolIO.g4#assignClause`, `assignTarget+`) takes the whole general format and used to answer a second operand with the parse error COBOL0308 (kb/Work PB829). **The determination holds at COBOL-85.** The 1985 entries print the same list (§1985:VII.2.3.2, §1985:VIII.2.3.2, §1985:XIII.2.3.2), leave the allowable content of implementor-name-1 and literal-1 to the implementor (§1985:VII.2.3.3 SR3, §1985:VIII.2.3.3 SR3, §1985:XIII.2.3.3 SR3; §1985:I.1.5.2.1: \"certain language elements whose syntax or function is specified to be, in part, implementor defined\"), and accept that such limits \"may prevent the successful translation of some programs that meet the requirements of Standard COBOL\" (§1985:I.1.7). **The 1985 sort-merge entry is the exception (kb/Work PB5587).** §1985:XI.2.3.2 prints `SELECT file-name-1 ASSIGN TO {implementor-name-1 | literal-1} …` and §1985:XI.2.3.3 carries no restriction of literal-1: its SR2 says only that \"only the ASSIGN clause is permitted to follow file-name-1\", where the sequential, relative, indexed and report entries each add \"Literal-1 must be a nonnumeric literal and must not be a figurative constant\" (§1985:VII.2.3.3 SR3, copied in VIII, IX and XIII). With no such rule \"A figurative constant may be used whenever 'literal' appears in a format\" (§1985:IV.4.2.2.2.3 GRL2.3), and the list the format prints is the sort-merge entry's own, so at COBOL-85 an SD's SELECT admits a figurative constant or a numeric literal as literal-1 (the generic `literal` of the format, where the other entries' SR3 says \"nonnumeric\") and a list of operands, and none is refused: the three refusals (the figurative-constant and numeric-literal arms of SR4, COBOL2645, and the list, COBOL2256) are recorded as `FileModel.EntryShapeFindings` by `AssignTargetRule.Resolve` and reported by `FileControlKeyRules.Screen`, which knows the file is an SD and the edition. A sort file is never opened by name, so the operands name nothing.
