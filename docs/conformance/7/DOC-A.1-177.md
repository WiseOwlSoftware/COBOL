cells: ["DOC-A.1-177", "**SIGN clause — representation when the picture character-string contains the symbol 'S' and no optional SIGN clause applies**, §2023:13.18.52.4 GR4 + §2023:8.5.1.5, required + documented", "**The operational sign is FUSED onto the TRAILING digit position, and WHICH characters it uses is the compile option `--sign-encoding`, default `ibm`** — owner decision kb/Work PB803, 2026-09-09: *\"Keep both behind an option with the default being IBM and Micro Focus compatibility.\"* GR4 grants both halves at once (“Neither the representation nor the position of that operational sign is specified by the symbol 'S'. The implementor shall specify the position and representation of the operational sign”) and §2023:8.5.1.5 repeats the obligation (“if it is not used, operational signs will be represented as defined by the implementor”), so this determination answers both. **POSITION — TRAILING**: an item with no SIGN clause is byte-identical to one that writes `SIGN IS TRAILING`, and different from one that writes `SIGN IS LEADING`. **REPRESENTATION — two conventions, one table pair each, chosen at COMPILE time:** `ibm` (**the default**) fuses positive 0–9 to `{ABCDEFGHI` and negative 0–9 to `}JKLMNOPQR`, so `PIC S9(3)` +123 is `12C`, −123 is `12L` and `SIGN IS LEADING` −123 is `J23`; `ascii` leaves a POSITIVE digit alone and makes a negative digit *digit + 0x40* (`pqrstuvwxy`), so `PIC S9(4)` −1234 is `123t` and `SIGN IS LEADING` −1234 is `q234`. Surveyed rather than invented: `ibm` is what IBM Enterprise COBOL, Micro Focus and GnuCOBOL's `-fsign=ebcdic` write, `ascii` is GnuCOBOL's `-fsign=ascii` (its default on a PC host) — read from that compiler's published test expectations, never its sources. The value is spelled **`ibm`, not “ebcdic”**, because nothing about those characters is EBCDIC-encoded on an ASCII host: they are what an EBCDIC-descended CONVENTION produces after translation, and the misnomer would make the option unreadable. **The fused sign occupies an EXISTING digit position and adds none** (§2023:13.18.52.4 GR5 a, which is normative and not part of the latitude), so `PIC S9(3)` is 3 character positions under either convention. **⚠ THE INTERCHANGE CONSEQUENCE, stated rather than left implicit:** the convention is a property of the **COMPILED PROGRAM** — baked into every emitted `NumProfile` and into every emitted signed class condition, never read from the process environment — so two programs of one run unit compiled under different options each read storage by their OWN convention, exactly as two vendors' programs do. Nothing records the convention of a DATA FILE: it is whatever wrote the file, and a mismatch is undetectable (a record holding `123t` read through a program compiled `ibm` yields +1230, silently). A signed DISPLAY item that must cross a convention boundary should be declared `SIGN IS SEPARATE`, whose characters §2023:13.18.52.4 GR6 b) pins to `+`/`-` with no implementor latitude at all. ONE table pair per convention lives in `ZonedSign` (`src/WiseOwl.Cobol.Runtime/Values/Numeric/ZonedSign.cs`), consulted by the encoder (`CobolNum.FormatDisplaySigned`), the decoder (`CobolNum.ParseDisplay`) and the class condition alike; the option reaches them through `PicInfo.ProfileInitializer(SignEncoding)`, the one place a `NumProfile` is written.", "`conformance:cases/13.18.52-SIGN/pb803_sign_default_representation`; `conformance:wiseowl/cases/13.18.52-SIGN/pb803_sign_encoding_ascii`; `conformance:cases/13.18.52-SIGN/pb803_sign_default_representation_85`"]
