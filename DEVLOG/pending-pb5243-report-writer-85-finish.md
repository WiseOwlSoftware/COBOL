## PB5243, PB5245, PB5246, PB5248, PB5249: the five open Report Writer findings of the 1985 code read, fixed at their roots

**Scope.** One root (the report writer's emitter, binder and runtime), five notes, from the 1985 code read of slices 51, 52 and 56. Every probe was re-run on this build first and all five reproduced.

**PB5248, PB5245, PB5246 (three runtime edition arms).** Each is a 2023 rule that PB1130, PB957 and PB1652 landed at every edition, where the 1985 text says something else. Each is now a `DialectBehavior` member over the edition the compilation bakes into `CobolReport` (`CobolReport.Edition`, the PB5128 mechanism), with its VCR row and both editions quoted: `SumSizeErrorBlanksPrintableItem` (row 7.57: at 85 the counter is MOVEd to the item, §1985:XIII.3.19.4 GR4, no spaces and no raise), `TerminateDiscardsSavedNextGroup` (7.58: at 85 the saved integer meets the first control footing's fit test, §1985:XIII.3.10.8 GR3, XIII.4.7.4 GR1) and `GroupIndicateConsumedByIssuedGenerate` (7.59: at 85 only a GENERATE that presented consumes the indication, §1985:XIII.3.13.4 GR1, XIII.4.6.4 GR3; `PresentBody` now returns whether the group presented). All three start in 2002, whose text (13.16.52.3 GR4, 13.16.35.3 GR4 a), 13.16.26.3 GR1) words the rule as 2023 does.

**PB5249 (GENERATE report-name and SUM ... UPON).** The runtime took `null` for "no detail" and used it both for "print no detail" and for "which detail is this GENERATE for", so a UPON term never fired. `BoundGenerate` now carries `SummaryDetail` (the report's one named detail, known at bind), the runtime has `GenerateSummary`, and `GenerateCore` takes `printDetail` separately from the detail name, so one subtotalling path serves both forms. This is every edition: §1985:XIII.3.20.4 GR11 says so for a one-detail report and §2023:14.9.16.4 GR2 says "the same processing as for a GENERATE data-name statement ... except that no detail is printed". A report with several details names none (docs/CONFORMANCE.md pins that reading).

**PB5243 (Table 1).** `ReportEntryClauseTable` holds the five rows of §1985:XIII.3.9.3 SR11 Table 1 once, and `ScreenReportEntryClauseTable` asks an elementary format 3 entry at 85 whether its clauses are the cells of one row. VALUE with BLANK WHEN ZERO and SUM with JUSTIFIED are refused; SOURCE with JUSTIFIED, BLANK WHEN ZERO or GROUP INDICATE and no COLUMN, which the 2023 screens refused, is accepted. SOURCE, SUM and VALUE as alternatives of one brace (§1985:XIII.3.9.2, §2023:13.15.2, §1985:XIII.3.22.4 GR1) is refused at every edition; the operand-list order that used to pick SUM over SOURCE over VALUE in silence is gone. The SR10, SR13, SR15 and GROUP INDICATE-column screens became 2002-and-later arms because Table 1 holds all of them at 85. No diagnostic code was allocated: COBOL2247 carries them.

**Goldens.** `pb5248_sum_size_error_presentation`, `pb5245_terminate_saved_next_group` (each `.85.out` and `.out`), `pb5246_group_indicate_suppressed_generate` (2002-2023) and `..._85` (85), `pb5249_generate_report_name_sum_upon`, `pb5243_table1_permitted_rows` (85), `pb5243-source-with-value` (refused at every edition), `pb5243-value-with-blank-when-zero` and `pb5243-sum-with-justified` (refused at 85). A fourth refusal, USAGE on a column-less SUM entry, was dropped: §1985:XIII.3.9.3 SR8 a) already refuses it, and the Table check now leaves that case to SR8 a) so it is reported once. Expected values are derived in each program's comment from the rule text; the 85 SUM size-error test states only digit versus space, because the standard leaves the digit undefined.

**Open lead, not fixed.** §1985:XIII.3.20.4 GR11 b) also runs the sole detail's USE BEFORE REPORTING procedure for GENERATE report-name; the engine runs none. It is a separate edition difference (2023 produces no group, so no USE) and is listed in the report.
