## Entry 3619 — 2026-11-14 12:59 PST — 2023 messaging RECEIVE stores the message characters into an elementary numeric receiver (PB5527)

PB5527 suspected that the 2023 messaging RECEIVE, like the 1985 communication RECEIVE of PB5489, would drop non-digit characters when its receiver (identifier-1 of GIVING) is an elementary numeric display item. The re-probe confirmed it: with a BALANCE server run unit replying `AB34`, `RECEIVE WS-TAG GIVING K-NUM WS-LEN` over `K-NUM PIC 9(4) VALUE 1234` printed `GOT [0034] LEN=0004`. Root: `UsageCollectionPass.Visit(BoundReceiveMessage)` collected the receiver only as a whole-group operand, so an elementary numeric item kept a native carrier whose `StoreImage` parse keeps only digits. Fix: the visit also records `Channel(n.Into)` (the character channel STRING's identifier-3 uses), so the item stores its character image, which §2023:14.9.31.4 GR1b ("The content of identifier-1 is the content of the message") requires; the probe then printed `[AB34]`. Golden: `conformance-suite/wiseowl/cases/14.9.31-RECEIVE/pb5527-receive-into-numeric-message-characters` (requestor plus server file, as PB4745's). No negative was added: the facility's refusal below 2023 is already pinned. No inventory row closes. Sibling sweep: SEND's FROM only reads; the 1985 RECEIVE is PB5489's; no other messaging arm stores into a place.
