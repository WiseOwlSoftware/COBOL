## The implicit filler bits after a USAGE BIT item have storage: MOVE "AB" TO a group of a bit item and a character displays AB (PB3564)

Fuzz run fuzz-20261022-163846 found `MOVE "AB" TO G1` over `05 G1-B PIC 1 USAGE BIT. 05 G1-X PIC X.` displaying `NUL,B`, and an ALIGNED bit table inside an alphanumeric group displaying NUL NUL after a move (fz03422). ISO §8.5.1.6.3 generates implicit filler bits after a bit item "as needed to advance alignment to a required natural boundary for the next item within that group" and at the end of a record group "as needed to increase the number of bits to fill an integral number of characters", and says those positions "are implicitly described as a filler elementary bit data item"; a group move is "treated exactly as if it were an alphanumeric to alphanumeric elementary move" (§14.9.25.4 GR4), so the bytes of the group, filler bits included, must round-trip.

**Re-probe (own build).** The note reproduced, and the loss was wider than the one run tail: the bits between the occurrences of an ALIGNED table (the fz03422 shape), the bits between the runs of a GROUP-USAGE BIT group (`MOVE B"1111111111" TO BG` over `BA PIC 1(2). BB PIC 1(2) ALIGNED` read `1100000011`) and the same positions under a group VALUE were all zero-filled and dropped. A REDEFINES, EXTERNAL, BASED or LINKAGE group never lost them (their string backing is the bytes), so the same group read differently with and without an alias.

**Root.** The record-struct lane had no storage for implicit filler: every composer wrote literal zeros for it (`BitAreaOf`, `CobolBits.Pack`'s trailing pad, `CobolBits.Strided`'s pad) and every distributor dropped it (`FromBits`, the run unpack, `EmitRunMemberFromBits`).

**Fix.** `BitLayout.FillersOf(owner)` is the one list of the fillers a group's struct stores (a `RunTail` after each run, a `TablePad` between the occurrences of a strided table); `PhysicalModel` declares each as a hidden string field (`Physical.FillerBits`, emitter-fixed name `__bf<k>`, zero positions initially); `GroupImageCodec` composes them into the packed run image, the bit face (`AsBits`) and a strided table's carrier, and distributes them on `FromImage`, `FromBits` and the table distributor (new `CobolBits.Strided(..., pads)` / `StridePads`); `GroupValueSlicer.SliceBitInit` initializes them from a group VALUE area (§13.18.63.4 GR5). A bit group's byte face is now its bit face packed (`AsImage` = `Pack(AsBits())`, `FromImage` = `FromBits(Unpack())`), one composition behind both faces, which also removes the run-image / bit-face disagreement for a group that begins mid-byte (PB3158). The leaf vector of a strongly-typed group skips the fields (its cell-backed twin has none). Which arm: the record-struct lane's; the cell lane (Tier-B backing) already stored them, and `BitRunImageDriftTests.AliasedGroup_HoldsTheFillerAGroupMoveWrote` now holds the two lanes equal on eight shapes. Docs: `docs/CONFORMANCE.md` (USAGE BIT determination) and `docs/COBOLNET_DATA_MODEL_DESIGN.md` (D20 storage text) state the stored filler and its limits.

**Not stored, registered as leads (read zero as before):** a run holding an OCCURS DEPENDING table, the padding of an element of a dynamic-capacity bit table, the filler of a leaf-vector-carried strong group, and INITIALIZE ... WITH FILLER does not reset the implicit filler (the cell lane never did).

**Goldens.** `14.9.25-MOVE/pb3564_group_move_keeps_bit_filler`, `13.18.1-ALIGNED/pb3564_aligned_filler_keeps_group_bits`, `13.18.60-USAGE/pb3564_bit_record_filler_file_io` (sequential and relative READ / WRITE / REWRITE with READ INTO / WRITE FROM, AT END 10, INVALID KEY 23, OPEN status 35) and the 2002 negative `pb3564-group-move-keeps-bit-filler-below-2002` (COBOLNET0900). Unit: `Strided_TakesItsPaddingFromTheStoredFiller_AndStridePadsReadsItBack`. 148 bit-related conformance programs pass unchanged (run.py over the regenerated wiseowl manifest); the whole Unit assembly passes but the two external-corpus tests, which need the GPL corpus absent from a fresh worktree.

**Rows.** None claimed or closed (§8.5.1.6.3 has no catalog rows; GR-14.9.25.4-4 already CONFORMS). **Self-review.** Architecture: one list, three readers, no second cursor; full code: the image lane's tail is guarded to the run's own characters for a group that begins mid-byte; performance: `FillersOf` is asked per run / table, a large pad initializes as a repeat; duplication: the pack / unpack of a run is one helper each. Nothing found beyond the guard.
