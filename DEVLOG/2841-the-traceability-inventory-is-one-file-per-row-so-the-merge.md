## Entry 2841 — 2026-10-30 22:00 PDT — The traceability inventory is one file per row, so the merge queue lands row-closing fixes in parallel (PB4148)

**The mechanism.** `tests/version-matrix/traceability-inventory.json` was one 7.6 MB list of 4,214 rows, and a fix that closes a row edits it. The merge queue merges with plain git and runs none of the repository's merge drivers, so `enqueue.py` held every later pull request that touched a driver-merged file (exit 16): the inventory was the second-largest cause of those holds, 10 in the landing lane's logs, after the suite's refusal registry (PB4147).

**The re-probe.** On this build `merge_drivers.DRIVERS` still named the file under `cobol-keyed-inventory`, `.gitattributes` repeated it, and `covered_by_driver("tests/version-matrix/traceability-inventory.json")` was true, which is the test `enqueue.driver_file_holders` asks. After the change the registry lists four drivers (`cobol-keyed-constructs`, `cobol-work-note`, `cobol-abi-pin`, `cobol-keyed-publicapi`) and the function is false for the old path and for every row file.

**The fix shape (CLAUDE.md rules 4 and 5).** A row is a file: `tests/version-matrix/inventory/<rule-id>.json`, an object written `json.dumps(indent=1)` with an LF, so two branches that close different rows edit different files and git's plain merge keeps both; two branches that change the SAME row conflict, which is a real conflict. The file is named by the row's id because a reader then finds a row without a scan and a rule's rename is a file's rename. `scripts/spec/inventory_store.py` is the one reader and writer in Python and `tests/_shared/TraceabilityInventory.cs` the one in C#; both replace what were three Python loaders (`inventory_schema.load_inventory`, `ledger_plan.load_inventory`, direct `json.loads` in five scripts) and six C# drift tests that each parsed the whole file. `load_inventory` refuses a directory with a stray, misnamed, unreadable or case-colliding file, naming each one, so a row is never silently skipped. `write_inventory` rewrites only the files whose text changed (a rebuild of an unchanged catalog changes 0 of 4,214) and deletes the file of a rule the spec dropped; each file is written through a temp file and an atomic replace. The order `load_inventory` returns is the spec's (section by numeric part, ordinal, id), not the catalog's page order: no consumer depended on position, every one keys a row by `rule-id`.

**History.** Four tools walk the inventory's history, and a walk crosses this commit. `inventory_store.inventory_at(rev)` reads a revision's directory in two git processes (`ls-tree`, then `cat-file --batch`), or the single legacy file of an older commit; `audit_witness_loss`, `backfill_closes_rows`, `inventory_ratchet` and `gen_ledger`'s trend read it, and `HISTORY_PATHSPECS` is the pair of paths a `git log` asks about. `gen_ledger.measure_commits` keeps PB3315's property that the number of git processes does not grow with the number of commits: it reads each commit's directory tree and the distinct row blobs in the same two processes as before, summarising each blob to its id, state and verdict as it arrives. `audit_witness_loss --check --base ce89f1485` and `inventory_ratchet.py --base ce89f1485` run GREEN across the layout change (the base holds the legacy file).
