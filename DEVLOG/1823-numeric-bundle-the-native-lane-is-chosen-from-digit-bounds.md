Eight related defects, one commit. They shared three mechanisms, and the stated scope of each (one unchecked multiply, one alignment scale, one lane test) was too small. **(1) Can this operation leave the `Int128` carrier?** `NumX` gains `Digits`, an upper bound on the decimal digits of an exact operand's unscaled value (a field read states `PicInfo.UnscaledDigitBound` — a COMP-5 item owns its container range; a literal its own digit count; the exact sum, difference, negation and product derive theirs). `NumericRenderer.Multiply` decides at compile time: N+M ≤ 38 is a bare multiply, N+M > 38 forms the exact 256-bit product on the SDIDI reduced to 34 digits by ROUND-TO-ODD (`CobolDec.MulToOdd`: an inexact product keeps an odd last digit, so the receiver's one rounding sees the tail in every ROUNDED mode and PROHIBITED — a first draft truncated, and the self-review found ROUNDED AWAY-FROM-ZERO storing …002 for 1 + 2e-30 + 1e-60), and an unknown bound takes `MulChecked` in every statement, so a native product no longer wraps (PB1143: `PIC 9V9(30)` × `PIC 9V9(30)` is legal — §14.7.7 r2 a) caps the composite — and stored `…7300173` for 1.5 × 2.25). `CobolNum.Divide`'s radix alignment never wraps either (SDIDI `DivToOdd` path; found by the sibling sweep). The same bound routes SUM / RANGE / MEAN / MEDIAN / MIDRANGE to their SDIDI bodies when the aligned arguments cannot fit (PB621; MOD / REM deliberately stay loud — their value is a difference of nearly equal magnitudes, MOD(9E30, 0.12345678) needs 39 digits of the dividend, which the 34-digit SDIDI cannot carry, so an SDIDI body would answer an approximation silently). The note's own fix shape for PB621 — align to the receiver's scale — is unsound for arithmetic (RANGE(0.6, −0.5) into a scale-0 receiver is 1.1, but arguments cut to scale 0 first give 0), so the arguments keep their digits and the carrier changes; `pb252`'s case 2 moved from a disjunction to the value. **(2) Does a float operand own this lane?** A floating-math function's returned value and a non-integer native power are engine-produced approximations, not operands "described with usage float-…" (§14.9.2.4 GR4, §14.9.44.4 GR4); `NumX.Approximate` marks them and `CombineCore` lifts them to the SDIDI beside non-float operands, so `13.2 + FUNCTION SQRT(16)` is 17.2 (it stored 17.1) and `0.1 + FUNCTION SQRT(0.04) = 0.3` is TRUE; a COMP-2 item or a float receiver keeps binary64 (PB1641). **(3) Whose sign is a dropped tail?** `CobolDec.AddSigned` folded the shifted operand's discarded tail into an unsigned sticky bit; the tail has the low operand's sign, so `1 − 1.0E-50` held 1.000…0 under TRUNCATION where §11.9.11.2 3) e) owes 34 nines — now `near − sign(near)` with sticky, and an exact Int128 computation for a 38-digit cancellation (PB1510; every expected value is Python `decimal`).
