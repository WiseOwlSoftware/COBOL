## Entry 2872 — 2026-10-31 13:03 PDT — PB4180 — a handoff that names `enqueue` is a request, so the loop stops chaining enqueue units to wait for merges

`units.jsonl` held 28 chains of consecutive `enqueue` units since 2026-10-01 (76 units, 49.7 hours of the one supervisor with the unit that ran while this was written). The latest, 2026-10-30 16:22 to 17:21, handed off `enqueue` three times to wait for #811 and #851 to merge while campaigns PB4147 and PB2911 had a ready note and no turn. The mechanism is rule 2 of `next_unit.py`: a handoff's `next_unit` returned before every other rule, and the enqueue unit's own handoff rule let it name itself whenever a branch was still in the merge queue. Since PB3103 and PB3608 the landing lane lands every WAITING TO LAND branch and the review lane reviews every WAITING FOR REVIEW one, beside whatever unit runs, so a unit spent waiting produced nothing. Re-probe: the old `test_next_unit.py` asserted exactly this (a handoff naming `enqueue` with an empty coordination directory chose `enqueue`), and `--enqueue-chains` over the live `units.jsonl` reports the note's 28 chains.

The fix takes both arms the note allows, because one is the mechanism and the other is the instruction that kept producing it. `base_choice` now treats `enqueue` as the one unit whose work the lanes own: rule 2 runs it only while `enqueue_work` (rule 6's single reader of the agent work) finds some, and otherwise falls through to the meter, resume and wave rules with a reason that says the named enqueue was declined. Every other named unit (`resume`, `meter`, a wave-type unit) is still an order. `units/enqueue.md` step 8 forbids naming `enqueue` for a merge, a landing or a review; `units/wave.md` and `units/resume.md` no longer tell the next unit to be `enqueue` for branches the lanes own. The design doc (section 3.2 rule 2, the unit table, the test list) says the same.

The drift measure the note asks for is `next_unit.py --enqueue-chains`: every run of two or more consecutive `enqueue` units, with its unit count, duration and reasons. A `meter` unit between two is invisible (it is read-only and no part of the work chain); any other unit ends the run.

`test_next_unit.py` replays the 2026-10-30 handoff over a survey of WAITING TO LAND, ENQUEUED and NOT QUEUED rows and expects the wave; a hold, a review lane that is not ticking, and a DONE branch with no lane survey still run the unit; a declined enqueue yields to the meter and resume rules; and the chain measure is checked on a planted history. `test_orchestrate_campaign.ps1` moved its three enqueue arms to the new contract, adding the campaign case (a declined enqueue hands the turn to the campaign lane).
