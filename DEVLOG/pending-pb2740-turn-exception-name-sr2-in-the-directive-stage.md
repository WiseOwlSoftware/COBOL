## An unknown exception-name in an omitted `>>TURN` is refused: §7.3.25.3 SR2 moves from the binder to the directive stage

`>>IF 1 = 0 / >>TURN EC-NOSUCH CHECKING ON / >>END-IF` compiled clean while the same directive outside the `>>IF` was COBOLNET0711, and `>>TURN EC-EXTERNAL-FORMAT-CONFLICT` at `--std 2002` was clean in the omitted branch and COBOLNET0878 in a compiled one (kb/Work PB2740, an R2 finding against PB2003's omitted-branch check). Both reproduced on the worktree build. The cause was where the rule lived: SR2 and the per-name edition window were checked only in `TurnState.Build`, which folds compiled events, so the omitted-branch check-only entry (`TurnDirectiveProcessor.CheckOperand`, ISO §7.2.1) could not see them. The comment in `Process` claiming `dialectLevel` fed the exception-name edition window was wrong: `ParseTurn` used it only for the §8.3.2.1 word-length rule.

**Fix shape.** One home for the rule, below both channels because the front end cannot reference the binder: `src/Cobol.Net.Editions/ExceptionNameRule.cs` (`TryGet`: unknown name, COBOLNET0711; `Window`: name introduced later, COBOLNET0878). `ParseTurn` asks it for every exception-name, so `Process` and `CheckOperand` report alike; a refused name never enters the `TurnEvent` (the other names of the directive still do, and a directive whose names were all refused is not also reported malformed, COBOLNET0718); the event carries the catalog's canonical spelling. `EcNameResolution.TryResolve` (USE, RAISE, RAISING, the PERFORM WHEN list) asks the same rule, so there is no second copy of the two messages. `TurnState.Build` stops reporting 0711/0878 and asks only the policy half through the new `EcNameResolution.AdviseResolved` (declined-module postures, the §15.33 width advisory); a name the stage did not resolve throws, since that is a broken hand-off and not a user error. Below COBOL-2002 the window is not asked (the directive is already COBOLNET0900). `EcNameResolutionDriftTests` pins the new caller sets (the compiler's callers of the rule, and the front end's and editions' callers of the rule and of `ExceptionCatalog.TryGet`).

**Witnesses.** Negatives `pb2740-omitted-branch-turn-unknown-name` (2002/2014/2023) and `pb2740-omitted-branch-turn-name-below-2023` (2002/2014); positives `2002/pb2740_omitted_branch_turn_valid_names` (level-1, level-3, EC-USER- and EC-I-O-with-file names in an omitted branch are accepted and enable nothing) and `2023/pb2740_omitted_branch_turn_2023_name`; unit `TurnDirectiveExceptionNameTests` (compiled and omitted give the same diagnostics for each case). `TurnStateTests.UnknownName_DiagnosedAndIgnored` became `UnresolvedName_IsABrokenHandOff`. No inventory row is claimed or closed, but row SR-7.3.25.3-2 (already CONFORMS) is re-sited to where SR2 now lives: a `record_verdicts.py` batch moves its code-location to `ExceptionNameRule.cs#TryGet` and `TurnDirectiveProcessor.cs#ParseTurn` and its test-ref to the `TurnDirectiveExceptionNameTests` theories and the two negatives, and retires the three old witnesses with their reason (`audit_witness_loss.py --check` GREEN, GAP 101 → 101).

**Finisher (the landing's Linux gate).** The first landing attempt stopped `GATE RED (Linux)`: the Linux unit leg's `SpecTraceabilityInventoryDriftTests.EveryTestRef_ResolvesToARealTest` reported SR-7.3.25.3-2's test-ref `unit:TurnStateTests.UnknownName_DiagnosedAndIgnored` gone, because the rename above had not re-sited the row. The Windows gate was green because that case is about 4 s, over the 2 s limit for a cheap tree-wide sweep, so `gate_plan.py` planned it into leg 2 and only the landing's whole Linux unit leg ran it. This is the case kb/Work PB3131 records: a change that renames a test or a symbol an inventory row names does not pull the inventory drift class into leg 1. The re-site above is the fix.

**Sweep.** Of the other stage-owned directive operands (FLAG-02, FLAG-14, COBOL-WORDS, and the closed-word rows), compiled and omitted lines give the same operand-syntax codes; the only differences measured are the COBOLNET0903 obsolescence warning and the COBOL-WORDS placement error COBOLNET2652, which are not operand syntax.
