## At --std 85 a *> in a debugging section or debugging line is comment text, and a failed COPY draws no second error (PB5588)

**PB5588.** At `--std 85` without WITH DEBUGGING MODE, `*>` inside a USE FOR DEBUGGING section or on a debugging line was refused COBOL0900 as the 2002 floating comment indicator, although the standard compiles that text "as if they were comment lines" (§1985:XV.2.1.3 GR2, §1985:VI.4.3.4 GR5) and a comment line holds any characters (§1985:III, Comment Line). Re-probed first on this build: `dfloat.cob` (section) and `ddline.cob` (line) both gave COBOL0900 and exit 65; the control with the same characters in a `*` comment line compiled.

**Cause.** PB5470 made `*>` an ordinary COBOL-85 text-word and moved the 85 refusal to `SurvivingFloatingComments.Report`, run in `Frontend.Preprocess` on the finished text, before `DebuggingLineRewriter` decides in `LexAndParseOnce` what is comment. The lexer skips a floating comment, so no token says it was there; the decision cannot be read off the token stream afterwards.

**Fix.** The gate is two steps. `SurvivingFloatingComments.Note` finds each surviving `*>` where the old call stood and records it with its line of the lexed text. `DebuggingLineRewriter.Rewrite` reports the text lines it makes comment (a hidden debugging line; a hidden debugging section from its header to the line before the next header; the portion's own header and END DECLARATIVES when only debugging sections stand in it), the one place that decides it. `Frontend.Parse` then calls `ReferenceFormatDiagnostics.ReportSurvivingFloatingComments`, which issues COBOL0900 and COBOL2495 for the `*>` not on such a line, moved back to where the gate's reports stood (`DiagnosticBag.MoveTail`) so the order of diagnostics did not change. The same text with WITH DEBUGGING MODE is program text and is still refused.

**The lead (a failed COPY draws a second COBOL0900).** The compiler's own note for a COPY that brought in no text was a plain `*> COPY X — library text not found` line, which the gate read as source. It is now `*>` plus U+FDD2 (`CopyProcessor.NotePrefix`, a noncharacter like the debugging-line and comment-entry carriers) and `TextWordScanner` reads the line as a single space, so no text reader takes it for the program's. `dcopymiss2.cob` now draws CBL3620 alone. Same root as the main finding: the gate read text that is not the program's.

**Goldens.** `pb5588_floating_text_in_debugging_comment_85` (accepted at 85, a `*>` in a debugging section and on a debugging line, prints MAIN) and `pb5588-floating-on-source-debugging-line-85` (refused at 85 with the mode, COBOL0900). Units: `DebuggingLineRewriterTests.NoMode_TheCommentLinesAreTheDebuggingLinesAndTheDebuggingSections`, `ReferenceFormatLogicalConversionTests.SurvivingFloatingComment_OnACommentLine_IsNoIntroduction`, `TextManipulationStatementTests.CopyNotFound_LeavesANoteThatIsNoProgramText`.

**Rows.** `1985-GR-XV.2.1.3-2` PARTIAL to CONFORMS (GAP 39 to 38); `1985-GR-VI.4.3.4-5` gains the witnesses; `1985-GR-XII.2.4-6` re-sited to `SurvivingFloatingComments.Note`.

**Branch review round 1.** R1-1 (blocking, fixed): the gate reports after the lex and parse, so the lexer stage's `priorErrors` no longer knew of its error and the PB3845 word-character screen was skipped when the surviving `*>` was the only frontend error. `LexAndParseOnce` now asks `ReferenceFormatDiagnostics.HasProgramTextFloatingComment(commentLines)` once the debugging rewrite has said which lines are comment (a noted `*>` exists only where the edition has no such indicator, an always-error gate); `WordCharacterScreenTests.ASurvivingFloatingComment_DoesNotHideTheScreen` fails without the line and passes with it. Leads fixed: R1-2 (the doc comment of `OneCopyResult` back on its record), R1-3 (`Note` takes the text line from `MappedText.LineIndexAt`), R1-4 (row `1985-GR-XV.2.1.3-2` keeps its seven GR2 sites beside the three gate sites).
