## Entry 3775 — 2026-11-16 09:48 PST — ACCEPT into a binary or packed item takes the item's own size, not one whole record

kb/Work PB5856. `AcceptSource.DeviceNumeric` windowed the transfer to the receiver's size only for a zoned byte form and read one whole 80-character record for every other, so `12345678` into `PIC 9(4) COMP` or `COMP-3` stored 5678 (`PIC 9(4)` stored 1234) and `12.50CR` into `PIC 9(3)V99 COMP` stored zero. The standard stores only the leftmost characters, sized by the item's size in standard data format characters (§1985:VI.6.5.4 GR4b with §1985:IV.4.3.4; §2023:14.9.1.4 GR4b), whatever the usage; GR1 leaves the conversion of those characters to the implementor, never which characters. kb/Work PB3513 had taken the whole-record read from GnuCOBOL; the ISO text controls.

The fix is one line at the root: the window is the size the emitter already computes for every arm (`ReceivingStore.CharacterPositions`), for every byte form. Re-probe on the witness input: D4, C4, K4 `1234`, S4 `+2345`, SC4 `-0123` (`-123456` into `PIC S9(4) COMP`), CV `012.50`, DV `012.50`; before, C4 and K4 `5678` and CV `000.00`. COMP-5, BINARY-LONG, BINARY-SHORT, an implied decimal point, P positions, a numeric-edited receiver and ACCEPT FROM SYSIN take their own size too; a floating-point receiver keeps one whole record. A fixed-point receiver is never larger than one record (38 digits and a sign), so GR4a's further records are unreachable for it.

DOC-A.1-1's whole-record sentence and its `12.50CR`, `890.00` and BINARY-CAPACITY wrap examples are corrected (no ACCEPT wraps now: the window holds no more digits than the PICTURE). Witnesses `VI.6.5@1985-ACCEPT-STATEMENT/g85_pb5856` (fixed form) and `14.9.1-ACCEPT/pb5856-accept-binary-packed-window` (2023); `AcceptDifferentialTests` expectations that pinned the whole-record read follow. Closes `1985-GR-VI.6.5.4-4`; `GR-14.9.1.4-4` gains the witness and the code site.
