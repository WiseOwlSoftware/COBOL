## PB4709: ABS, MAX and MIN over an always-integer arithmetic expression are Integer functions

**The defect.** Table 21 / 15.7.1 makes ABS an Integer function for an Integer argument, and 15.3 item 6 says an Integer argument is "an arithmetic expression that will always result in an integer value or an integer data item". `IntrinsicResultType.IsIntegerArgument` read that for a bare integer item, a literal, a nested integer function and (since PB4635) a parenthesized sole item or literal, and nothing else. `ABS(I2 + 1)`, `ABS(- I2)` and `MAX(I2 + 1 1)` therefore stayed on the Numeric row: `FACTORIAL(ABS(I2 + 1))` was COBOL1627 and `PERFORM FUNCTION MAX(I2 + 1 1) TIMES` COBOL1646, both legal source.

**Re-probe.** On this branch's build before the change: both programs refused with those codes (a.cob in the wave scratch). After: FACTORIAL(ABS(3 + 1)) = 24, FACTORIAL(ABS(-3)) = 6, and the PERFORM body ran 4 times.

**The fix, at the root.** The result-type rows and the type-6 refusal screen are two readers of one clause, and only the screen had a term-by-term reading of "always" (`IntrinsicArgumentRules.ProvablyIntegral`, sound not complete). `IsIntegerArgument` now asks it for every computed operand, so the parenthesized-sole-operand special case (`EnclosedOperand`) is subsumed rather than extended, and the next expression shape `ProvablyIntegral` learns is automatically Integer-typed. A quotient over an item (`I2 / 2`), a scaled item (`S2 + 1`) and a numeric function keep the Numeric row.

**Sibling arm.** `ProvablyIntegral` answered false for an integer-type function term, so `ABS(FUNCTION INTEGER(S) + 1)` stayed Numeric, and the refusal screen's constant witness failed open on `I2 + 0.5 + FUNCTION INTEGER(S)` (3 + 0.5 + 2 is never an integer). It now answers true for a `BoundIntrinsicCall` of result type Integer (15.2 type 5); the beneath-walk never entered calls, so the two still agree.

**Goldens.** `cases/15.3-Arguments/pb4709_integer_expression_argument` (accept 2002 onward, ABS being a 2002 function: 24, 6, 4 iterations, 120, 6, 2, 6, each computed from the spec), refusals `pb4709-abs-non-integral-expression` (ABS(S2 + 1) is Numeric, COBOL1627) and `pb4709-integer-function-term-non-integral-sum` (COBOL1627). Rows: AR-15.3-6 already CONFORMS; no row closed.

**Self-review.** Architecture: one reading of "always integral", no second copy. Full code: the doc comments of `EnclosedOperand` and `ProvablyIntegral` now name the real readers. Performance: the added call is on the bind path only. Duplication: none added. docs/INTRINSICS_DESIGN.md states the meaning of "integer argument" for the result rows.

**Review round 1 (R1-1 blocking, R1-2 to R1-6 leads).** R1-1: the first version typed `ABS(I2 + 1.0)` Integer by VALUE (`ProvablyIntegral` folds the literal) while the function still returned its argument at the argument's own scale, so `MOVE FUNCTION ABS(I2 + 1.0) TO A10` stored `4.0` (main refused it, COBOL0819) and a multi-receiver MOVE stored `4`: one reference, two values, against 15.2 item 5 ("no digits to the right of the decimal point"). The reviewer's whole family reproduced on this build (`ABS(1.5 + 0.5)`, `MAX(I2 + 1.0 1)`, `ABS(I2 * 2.0)`, `SUM(I2 + 1.0 1)`, `ABS((1.0))`, nested `ABS(ABS(I2 + 1.0) * 2)`), and so did `ABS(4 / 2)` (`2.00000000`) and `MIN(I2 ** 2.0 3.0)` (`3.0`). The root is that the Integer row was selected by the value of the argument while the value's scale followed its form. The fix keeps the spec's typing (an expression that always results in an integer is an Integer argument) and gives the row the scale-0 value its type states: `IntrinsicResultType.IntegerRowArguments`, called once in `IntrinsicBinder` where the result type is resolved, rewrites each argument of a call that RESOLVED to Integer through `IntrinsicArgumentRules.IntegralForm` (every integral-valued subtree becomes the integer literal of its exact value; the +, -, *, unary - and ** spine is walked). A row declared Integer (FACTORIAL, MOD) is left alone: its type-6 positions are already read as integers by the renderer's intake. The alternative of narrowing the typing to integer-FORM expressions was rejected: it would keep refusing `FACTORIAL(ABS(I2 + 1.0))`, legal by 15.3 item 6.

R1-2: a bare `1.0` and the parenthesized `(1.0)` are one arithmetic expression, so `IsIntegerArgument` now reads a source-written numeric literal by value as well (a folded function's literal keeps its function's type, 8.4.3.2.3 SR11); `FACTORIAL(ABS(1.0))` compiles as `FACTORIAL(ABS((1.0)))` does. R1-3: `ProvablyIntegral` answers true for a counter register (8.4.3.14.4 GR1), as `IsIntegerOperand` does, so `ABS(LINAGE-COUNTER OF F + 1)` is Integer and `LINAGE-COUNTER OF F + 0.5` is now refused by the type-6 screen as never integral (it failed open). R1-4 (pre-existing): `NonIntegralItemsBeneath` now walks the arguments of a call, so `S2 - FUNCTION ABS(S2)` over an unsigned PIC 9V9 (always 0) is no longer refused; `S2 - FUNCTION INTEGER(S2)` is still refused (it is FRACTION-PART). R1-5: the Table 21 quotation lives in 15.6 (cite.py --find), not 15.7.1; the doc comments now cite "the per-function tables of 15.7.1 and its siblings, summarized by 15.6 Table 21". R1-6: the golden comment names the real refusal file.

Goldens added: `cases/15.3-Arguments/pb4709_integer_row_scale_zero` (accept 2002 onward; thirteen MOVE results into PIC X(3) receivers where a stored fraction shows, plus the counter, bare literal and opaque-call COMPUTEs, every value computed from the spec) and the refusal `pb4709-counter-register-non-integral-sum` (COBOL1627).
