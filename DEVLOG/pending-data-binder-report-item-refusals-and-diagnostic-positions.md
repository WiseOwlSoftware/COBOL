## The data binder's report-item refusals, a level-01 multiple LINE clause, and every refusal names its position

Wave 20261780 group D, four notes on one root (the data binder's report-section edges): PB3766, PB3768, PB4109, PB2034. No diagnostic code was allocated or used (COBOL5599 to COBOL5601 are returned).

**PB3766, the order of inheritance.** A contained program's own FILE STATUS and OCCURS DEPENDING ON that name a container's GLOBAL report item (ISO 13.18.27.4 GR1, refused by 13.8.6.2.3) were told "not defined" (COBOL1639, COBOL0851), because `BinderDriver.BindUnitData` inherited the containers' GLOBAL reports after `data.Bind`, and the resolvers that ask `ReportEntryReferenceRefused` run inside it. The driver now offers the list (`DataBinder.ContainerGlobalReports`, nearest container first) and `DataBinder.InheritContainerReports` inherits it at the end of `BindDeclarations`, after the unit's own names are declared (a local name still hides, 8.4.6.2) and before `BindResolve`. A second source of the list (a container-chain walk inside `ReportEntriesNamed`, the note's other option) was not built: two producers of one list is the drift this repo keeps paying for.

**PB3768, a missed arm and its sibling.** `ResolveAssignUsing` told a report item named in ASSIGN ... USING "no such data item is described" (COBOL1810). The sweep of the clauses that name a data item found the same false verdict on RECORD KEY and ALTERNATE RECORD KEY (SR2's COBOL0863 "references nothing described"). Both now ask the one refusal; the key resolver records the name in `refusedKeys` so `FileControlKeyRules` stays silent about an operand already refused. `ReportItemReferenceTests.EveryUndefinedNameArm_AsksTheOneRefusal` named files by substring, which stays green when a new arm in the same file forgets the question; it now names the three data-division arms by member.

**PB4109, a level-01 multiple LINE clause.** `BindReportEntry` replays a repeating entry once per operand, and at level 01 every replay opened another `ReportGroupModel` of the same name, so `GENERATE DET-A` drew a false COBOL1920 ("described in more than one report description entry (R-1, R-1)") for every spelling of the clause. The note's first question was whether the clause is legal at level 01. It is: 13.18.35.3 SR10 states no level restriction, and 13.18.35.4 GR9's "functionally equivalent to a LINE clause with a single operand, together with a simple OCCURS clause" is an equivalence of function, not of syntax (SR25 would demand a STEP phrase of every absolute multiple LINE clause, and none exists), so 13.18.38.3 SR1 a)'s bar on OCCURS at level 01 does not reach a clause that contains no OCCURS. The group is opened only on the entry's first repetition (`opensGroup`); the replays multiply its lines. Golden `13.18.35-LINE/pb4109-level-01-multiple-line` (2002; lines 3 and 5, then relative 7 and 10, derived from GR4c, GR5a, GR5b3, GR7, GR9, GR23) and the refusal `pb4109-level-01-multiple-line-at-85`. `rejects_legal_source` is set on the note.

**PB2034, positions.** The note said an `EditionDiagnostic` carries no location and proposed to give it one. The type is not the mechanism: every diagnostic is positioned by the sink's cursor, which a walker sets (`edition.At(context)`, kb/Work PB82), and a diagnostic prints bare when its producer runs outside every walker. A corpus sweep (all 3089 refusals of `diagnostics.json`, each at its first refused edition) found 54 bare lines on this tree: the note's families (RD rules, external-file consistency, the RETURNING item, ANY LENGTH in a property method, COBOL0806) and the same fault beside them (the CONTROL, TYPE CH/CF, RESET, SUM-addend and UPON rules of the same post-build report resolver, COBOL1643, COBOL1507, COBOL1525, the file-level COLLATING rules). Each producer now positions the sink where it knows the clause or entry (`ReportModel.At`, `ReportClauseName.At`, `FileModel.ClauseOrEntryAt` replacing three inline copies of the expression, the printable item's and the SUM addend's contexts, `BinderDriver.NameCtx` lifted to class level). The same sweep afterwards finds none. A second position channel on `EditionDiagnostic` would have been exactly the parallel mechanism the cursor replaced. The net that keeps it true is `EditionHarness.AssertEveryDiagnosticPositioned`, asked of every error and warning of every refusal at every edition (8981 rows) by `WiseOwlRefusal_RefusesTheSourceWithItsDiagnostic`: the next producer that forgets its position fails at the first negative that exercises it.
