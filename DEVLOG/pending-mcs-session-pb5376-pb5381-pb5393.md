## Message control session: repeated destinations, the per-activation terminal lock, and status 80 for INPUT

Three defects of `MessageControlSession` (kb/Work PB5376, PB5381, PB5393), each re-probed first on the pre-change compiler and fixed at its root; each now has a conformance case.

**PB5376, DISABLE/ENABLE OUTPUT with a destination named twice.** `SetOutput` changed each destination while it walked the DESTINATION TABLE, so the second occurrence of a destination saw the change the first had made: D3, D3 on a connected D3 answered `15 05`, and D3, D9, D3 answered `80 015`. It now judges every occurrence by the state at the start of the statement (§1985:XIV.3.2.4 GR1, §1985:XIV.3.3.4 GR1) and changes the destinations afterwards. After the fix D3, D3 answers `00 00` and D3, D9, D3 answers `20 010`. Cases `1985-GR-XIV_3_2_4-1-repeated-destination` and `1985-GR-XIV_3_3_4-1-repeated-destination`.

**PB5381, the SYMBOLIC TERMINAL lock.** `Dialogue.LockedTerminalChanged` kept the lock of an input-output CD in a run-unit dictionary keyed by CD name, so it survived CANCEL and each CALL of an INITIAL program. The lock is now state of the program instance: the generated program holds one `CdActivation` per CD and passes it as the CD argument of every statement (`CommunicationEmitter.EmitMembers`, `ActivationOf`; `MessageControl.*` take it in place of the CD name), so a new instance starts with none (§1985:X.5.3.4 GR2). A statement the store refuses (9x) lifts the lock it set (`Dialogue.UndoLocks`). The comparison is of content and exact: `t2` after a `T2` lock is a changed item (§1985:XIV.2.2.4 GR31); it was folded to case before. The public surface changed (`PublicAPI.Unshipped.txt`), and the two unit test classes that call the session directly pass a `CdActivation`. Case `1985-GR-XIV_2_2_4-31-activation` (CANCEL arm, INITIAL-program arm, exact-content arm: `SUBC T3 00` after CANCEL where `20` was answered).

**PB5393, status 80 for ENABLE/DISABLE INPUT.** `SetPath` answered 20 as soon as `FindQueue` failed and never asked the 15 condition of the levels it knew. `MessageDefinitions.FindQueuePrefix` (sharing a `Resolve` walk with `FindQueue`) now gives the deepest known level, and `MessageStoreState.QueuePathsAre` asks, without changing anything, whether that structure is wholly in the requested state: then 80 (§1985:B.2.2), else 20; neither takes action. The design doc's sentence "Status 80 appears only for destinations" is corrected. Case `1985-GR-XIV_3_2_4-3-known-prefix-unknown-level` (80, 80, 80 and the 20 and 15 that stay).

No inventory row moves: the three notes claim 1985 rule ids that kb/Work PB5094 keeps out of `inventory_rows` and `closes_rows`. No refused-below-1985 program was added: each rule is a runtime status of a statement the edition matrix already gates, and the diagnostics directory holds none for the facility's general rules.
