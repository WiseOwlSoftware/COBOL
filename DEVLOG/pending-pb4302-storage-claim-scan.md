## PB4302: the storage-claim operands of a compilation are found by one walk of its parse tree, sliced per source element

**Re-probe (the note, on this tree).** `cobol check-batch` over five repetitions of the G6 `NESTED_100` and `NESTED_200` chains (Debug build, loaded box, so the ratio is the evidence, not the milliseconds): 3,480 ms and 12,731 ms before the change, x3.7 per doubling. The cost was real and had two parts. `DataBinder.PtrDescendants` was a recursive `yield` iterator, so a node cost its depth in `MoveNext` calls and every interior node an iterator object; and the three pointer scans built on it (`ScanByReferenceOperands`, `PtrScanAddressOfSenders`, `PtrScanAddressOfTargets`, the last through the first) were asked by every container about every program it contains (`PtrBindBasedAndAddressables`, `CallBindLinkage`), so a chain of N nested programs walked N(N+1)/2 program subtrees. Fixing the iterator alone leaves the second part quadratic (the note's own prototype, 114 / 154 / 665 ms at depth 100 / 200 / 400).

**Fix shape.** `StorageClaimScan` (new, `BindSession.ClaimScans`, one per compilation, handed to each unit's `DataBinder`) walks the compilation's tree once with an explicit stack and records, in document order, the ADDRESS OF heads (§8.4.3.11) and the operands an activation may pass BY REFERENCE (§14.9.4.4 GR5 and GR9, §14.9.23.4 GR6, §14.6.5), together with the half-open span of each list under every `procedureDivision` and every `nestedProgram`. A question about a region is a slice. The region's root is the top of its parent chain, so the first question in any order starts the one walk. The container's `IsUserFunction` predicate (§8.4.6.6) is not baked into the walk: function-call arguments are recorded with their function name and the asking element's predicate is applied at read time, which answers the note's caution about a bottom-up merge changing which items are forced into cells. `ParseTreeWalk` (new) is the one explicit-stack pre-order walk the binder asks for by node. Two further, behaviour-neutral cuts: a unit that declares no GLOBAL name does not ask about contained programs at all (both claim loops discard a contained head that is not among its GLOBAL roots, `ResolveStorageClaimHead` and then `CallGlobalRoots.Contains`, and the lookup is a pure read, so the question had no possible answer, ISO §13.18.27.4 GR2), and a procedure division with no USING phrase no longer collects the contained programs' ADDRESS OF names to read none of them.

**Siblings swept (CLAUDE.md rule 4).** Every recursive `yield` iterator over a parse tree or the data-item tree that the note names or the binder's data pass reaches is now an explicit-stack walk: `DataBinder.Descendants` (constant scan, once per data division), `SetAlterBinder.AlterStatementsIn`, the two report-subscript walkers in `DataBinder.Reports.cs`, `DataBinder.PreOrder` (deleted, eleven callers now ask `DataItem.SelfAndDescendantsOf`) and `DataItem.DescendantsOf`. `PtrDescendants`, `ScanByReferenceOperands` and `PtrScanAddressOfSenders` are deleted; their callers changed in the same commit.

**Result.** NESTED_200 12,731 ms before; 4,212 to 5,433 ms after, NESTED_100 2,881 to 3,607 ms, NESTED_10 1,160 to 1,739 ms (the fixed process cost): x1.5 per doubling, so what is left is the parse and the work that is linear in nodes. `StorageClaimScanTests` pins the answers (ISO order, the transitive BY phrase rule, subscripts and expressions never passed, the user-function predicate belonging to the asker) and the walk count (`TreesWalked == 1` however many regions ask and in whatever order), and a sweep that the scan has exactly two construction sites, `BindSession` and the `DataBinder` default, with `BinderDriver` handing the session's to every unit. Conformance witness `13.18.27-GLOBAL/pb4302-address-of-global-from-grandcontained` (GR-13.18.27.4-2): OUTER's GLOBAL record is addressed from INNER, two programs down through a MIDDLE that declares nothing, and INNER's store through the pointer is what OUTER prints. It holds the slice over a grandchild and the no-GLOBAL early-out together. No inventory row is closed (process-only); no negative was added because the change implements no rule and the edition gate of the constructs the witness uses is pinned elsewhere.

**Self-review.** Architecture: one mechanism per job (the scan owns the walk and the record, the binder owns the resolution), no C# text in a bound node, a region other than a procedure division or a contained program is refused loudly instead of answered with a wrong slice. Full code: the scan's classifier is the old one arm for arm (INVOKE USING, user-function arguments, CALL RETURNING, CALL USING with its transitive phrase), `OperandIdentifier` keeps "the outermost data reference when its text is the whole operand". Performance: the scan allocates one record per operand, none per node; the one walk covers the data and environment divisions too, because a function call in a constant expression of a contained program's data division was in the old subtree walk and must stay in the slice. Duplication: three tree walkers collapsed into `ParseTreeWalk`, the data-item walkers into `DataItem`. `EcBinder.ExceptionPerform`.s own `Descendants<T>` found on the way, now `ParseTreeWalk.Descendants(...).OfType<T>()`.
