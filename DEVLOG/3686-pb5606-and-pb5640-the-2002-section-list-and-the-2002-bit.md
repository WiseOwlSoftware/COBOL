## Entry 3686 — 2026-11-15 08:29 PST — PB5606 and PB5640: the 2002 section list and the 2002 bit reference-modification length

Two `--std 2002` under-rejections, both in the ADDRESS OF / CALL / INVOKE operand screens.

**PB5606.** `ADDRESS OF identifier-1` (§2002:8.4.2.11.2 SR1) and `SAME AS data-name-1` (§2002:13.16.47.2 SR7) name four data sections; COBOL 2002 has a fifth, the communication section. The binder never told a CD record item from a working-storage one, so `SET P TO ADDRESS OF A1` (A1 in a CD record) printed SET and `05 C1 SAME AS C2` (C2 in a CD record) compiled. Re-probed on this build before the fix: both reproduced. Fix: `AddressOfOperandScreen.Admit` refuses an operand whose root `DataItem.Section` is `EntrySection.Communication` (COBOL2785), and `DataBinder.ExpandSameAsEntry` refuses such a target (COBOL1556). Goldens: `pb5606-address-of-section-list` and `pb5606-same-as-section-list` (accepted at 2002), `pb5606-address-of-communication-item` and `pb5606-same-as-communication-item` (refused at 2002). Sibling sweep: the CALL/INVOKE argument screen (`SectionDataItem`) accepts CD items, as §2002:14.8.22.2 SR9 requires; the other section enumerations read were 2023 text with no communication section.

**PB5640.** `ScreenBitAlignment` asked only the reference modification's leftmost position be a literal, which is the 2023 CALL/INVOKE/function rule. The 2002 and 2014 texts of the same rules (§2002:14.8.22.2 SR12, §2002:14.8.4.2 SR6/SR8, §2002:8.4.2.2.2 SR12; §2014:14.9.22.2 SR12, §2014:14.9.4.2 SR6/SR8, §2014:8.4.2.2.2 SR14) ask for the whole reference modification, leftmost position and length. Re-probed: `INVOKE O "TAKEB" USING B8(1:L)` compiled at 2002. Sweeping the sibling arms found a second, larger gap: §2023:8.4.3.11.3 SR4 a) (ADDRESS OF) and §2023:14.9.35.3 SR7 / §2023:14.9.51.3 SR9 (the FILE phrase) keep the whole reference modification at 2023 itself, and the screen ignored the length there too, so `ADDRESS OF BX(1:N)` was accepted at every edition. Fix shape (rule 5, the next case automatic): `BitAlignmentRule.For(statement, year)` is the ONE table of the edition's clause, the alignment clause and the reach of the reference-modification requirement; `ScreenBitAlignment` takes a `BitAlignmentStatement` instead of a clause string, and `BitStartOf(place, wholeRefMod)` checks the length. The messages now cite the edition's own clause. Goldens: `pb5640-invoke-bit-refmod-literal-length` (accepted 2002), `pb5640-invoke-bit-refmod-data-length`, `pb5640-call-bit-refmod-data-length` (refused 2002 and 2014), `pb5640-invoke-bit-refmod-data-length-2023` and `pb5640-call-bit-refmod-data-length-2023` (accepted at 2023, the narrowed rule), `pb5640-address-of-bit-refmod-data-length` (refused at 2002, 2014 and 2023).

Rows closed (`record_verdicts --edition 2002`, GAP 2511 to 2508): 2002-SR-8.4.2.11.2-1, 2002-SR-13.16.47.2-7, 2002-SR-14.8.22.2-12.

Review round 1: the FILE phrase (WRITE/REWRITE FILE FROM) keeps the whole reference modification at every edition (§2023:14.9.51.3 SR9 a, §2023:14.9.35.3 SR7 a), a new refusal with no golden.
