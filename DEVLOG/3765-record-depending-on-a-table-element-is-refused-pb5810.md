## Entry 3765 — 2026-11-16 07:49 PST — RECORD DEPENDING ON a table element is refused (PB5810)

`RECORD IS VARYING ... DEPENDING ON TL`, with TL an unsubscripted item under an OCCURS clause, compiled clean at every edition and the length register was then ignored: a WRITE of a 13-byte record into a 4-to-12 file gave status 00 where an elementary TL gives 44, and a sort file's RETURN left the length item at 00. The subscripted spelling was already refused (COBOL2024); the unsubscripted one is a table element reference with no subscript, which `§2023:8.4.2.3.3 SR5` (`§1985:IV.4.3.8.2.3 SR4` below 2002) forbids outside seven contexts, none of them this clause.

The re-probe on the branch build reproduced all three programs of the note (indexed, relative, sort-merge) at `--std 85` and `--std 2023`. The fix is one screen at the one site where the operand resolves, `FileControlBinder.Resolve.cs#ScreenRecordDependingOccurs`, so the indexed, relative and sort-merge descriptions (the same RECORD clause by `§1985:IX.3.2.4 GR5`, `VIII.3.2.4 GR5`, `XI.3.2.4 GR2`) are all covered. It reports COBOL2270 and clears the resolved item, so SR6's rows stay silent. No new diagnostic code was needed. Sibling sweep: FILE STATUS, RELATIVE KEY, LINAGE, the key clauses and the padding character already screen OCCURS (`ScreenFileStatusItem`, `FileControlKeyRules`, `ResolveLinage`, `FileControlBinder.Padding.cs`); APPLY COMMIT and VALUE OF go through `ResolveClauseOperand` with their own rules and are not this clause.

Goldens: three refusals (`pb5810-record-depending-table-element-indexed`, `-relative`, `-sort`, refused at all four editions) and the accepted `pb5810_record_depending_elementary_relative` (status 44 at length 9, 00 at length 5). Rows re-verdicted PARTIAL to CONFORMS: `FMT-13.18.43.2`, `FMT-13.4.6.2`, `SR-13.4.5.3-5`, `SR-13.4.5.3-7` (GAP 38 to 34). The three 1985 code-read rows are left to a registrar.
