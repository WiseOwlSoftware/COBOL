## PB5639, PB5575: an indexed READ PREVIOUS after OPEN at 2002/2014 compares against the lowest position, and ARITHMETIC IS STANDARD runs the 32-digit model

**PB5639.** At `--std 2002` and `2014` an indexed `READ PREVIOUS` right after `OPEN` answered the first record (`P1=K002|00`). kb/Work PB344 had derived that from Annex E.2 item 22's justification alone, before the 2002 and 2014 text was held. That text sets the file position indicator at OPEN to "the characters that have the lowest ordinal position in the collating sequence" (§2002:14.8.26.3 GR12) and has a PREVIOUS select "the first existing record ... whose ... key value is less than or equal to the file position indicator" (§2002:14.8.29.3 GR18c2; 2014 the same), so the answer is at end, `10`, unless a key is that lowest value, and the text's own NOTE says "normally get an at end condition for indexed". Fix: `IndexedConnector.SelectSequentialRecord` seeks the last key at most `IndexedConnector.LowestKey` (the key sequence's LOW-VALUE character over the key length) below 2023; 2023 stays the unconditional at end. The three `pb344_read_previous_indexed` goldens are corrected and gain P5 (a LOW-VALUES key, the one case where the editions part). Rows: 2002-GR-14.8.29.3-18 CONFORMS; 2002-GR-14.8.26.3-12 is a KEPT rule whose verdict lives on its 2023 row. Registered, not fixed: the RELATIVE twin (the same 2002 rule makes a relative PREVIOUS after OPEN select record number at most 1, where the compiler answers the first existing record at every edition).

**PB5575, run-time arm.** The 2014 text keeps standard arithmetic as the 32-digit model too (§2014:8.8.1.3.1.1, .2, .4, .5), so `ARITHMETIC IS STANDARD` is that model at 2002 and 2014, and the 34-digit SDIDI is STANDARD-DECIMAL's alone. The note had estimated a precision/range parameter through the whole engine; truncation composes, so none was needed. `CobolDec.ToSidi` cuts a result to 32 digits and checks the 10^-999 to 10^1000 - 10^968 range (EC-SIZE-OVERFLOW / EC-SIZE-UNDERFLOW), `CobolDec.ToSidiRounded` rounds to 31 digits. The emitter (`NumericRenderer.StandardIntermediate`) runs the operations at TRUNCATION, wraps `DecBinary` and the power in `ToSidi`, and rounds to 31 digits where §2002:8.8.1.3.1.3 says: a relation and a sign condition, and the final transfer into a receiver without ROUNDED. The compile-time 2002 mode calls the same `ToSidi`. Re-probe at `--std 2002`: `COMPUTE A = B * 100 + 9 - B * 100` printed `00009` and prints `00000`; `IF B * 100 + 9 - B * 100 IS ZERO` was false and is true; `COMPUTE X = 10 ** N / Z` (N = 1000) reached EC-SIZE-ZERO-DIVIDE and reaches EC-SIZE-OVERFLOW first; `SEARCH ... WHEN 2 / 3 * 3 = ...` found nothing and finds element 1. Goldens: `8.8.1.3@2002-STANDARD-ARITHMETIC/pb5575-rt-std-arith-32-digit-truncation` (values by hand, the ANNUITY value by a Python decimal model) and `pb5575-rt-std-arith-before-2002` (COBOL0804 at 85); unit tests `StandardIntermediateDataItemTests`. Twelve 2002 rows CONFORMS (GAP 2517 to 2504 with PB5639's). Still open in PB5575: the rounding of a function argument with no equivalent expression, the 32-digit limit of a function's returned value (E, EXP, EXP10, ANNUITY, FACTORIAL, STANDARD-DEVIATION and the date functions run on the 34-digit engine), and a `ROUNDED MODE IS TRUNCATION` receiver read as no ROUNDED phrase.
