## kb/Work PB4719: the message control system's symbolic name is a file-name component on every host

The device of a destination or a terminal is the file `<name>.out` of the MCS directory, and `MessageStoreState.NameOf` screened a name only for `/` and `\`. On Windows a name holding a colon was still defined with status 00: `C:EVIL` is a drive-relative path, `A:B` opens an NTFS alternate stream, and `NUL`, `CON` or `COM1` (with or without an extension) are devices, not files. Re-probed first: the 34 new refusal cases of `UnusableDefinitionFile_IsStatus91_OnEveryStatement` all failed against the old screen (the definition was accepted), then passed with the fix.

The fix is at the one screen, as the owner directed (via Mythos, 2026-11-04): `NameOf` refuses every character in the union of `Path.GetInvalidFileNameChars` and the Windows set (control characters and `" * / : < > ? \ |`), so the result no longer depends on the host OS (on Linux the host call omits all but `/` and NUL), and refuses a name whose stem before the first dot, trailing spaces trimmed, is a Windows device name (`CON PRN AUX NUL CONIN$ CONOUT$`, `COM` and `LPT` with 0 to 9 and the superscripts). The names that merely resemble one (`CONSOLE`, `COM10`, `LPT`, `A.B`) are still names, and a second theory pins them. The sweep found no sibling: `mcs-state.json` is read by lookup in the definitions' dictionaries and builds no path, and the only `Path.Combine` of a name is `device + ".out"`. The design section 6 states the new rule.

Self-review: the stem rule follows Microsoft's "Naming Files, Paths, and Namespaces"; the ISO text defines no host file naming (the MCS is the implementor's, E.5.1), so no clause is cited. The screen's three members were added beside `NameOf` as its parts rather than as a second mechanism.
