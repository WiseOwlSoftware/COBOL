## PB4326 + PB4330: self-tests only for a change that touches tooling, audits beside the build and the legs, and the audits run once in CI (pipeline redesign steps 3 and 7)

Steps 3 and 7 of the pipeline redesign PB4323 (owner 2026-10-31, PIPELINE-REVIEW.md section 10), one branch because both change `.github/workflows/build-and-test.yml` and the same lane decision. Neither is a defect: both remove work that measured nothing. A script self-test reads only tooling, yet every gate ran all of them (147 s median, reused or not) and then waited 145 s for the one that reads the built assemblies; CI's `audits` job, the same 5.7 minutes, ran on the pull request, again in the merge group and a third time on the push of the merge-queue commit.

**Step 3 (PB4326).** `scripts/inert_lane.py`, the one classification, gains the TOOLING flag: a full-lane change touches tooling when a changed path is under `scripts/`, `.github/`, `tools/`, `.claude/`, is `.gitattributes` or `toolchain.env`, or ends `.py`, `.ps1` or `.sh`. An empty or unlistable change touches tooling (nothing proves it does not); an inert one never does. `classify` prints `tooling=true|false`, `Lane` carries it, and the arms of `inert_lane.py --self-test` pin the paths. `.gitattributes` and `toolchain.env` are two paths the review's definition does not list; they are in because the Windows self-tests job checks the checkout bytes `.gitattributes` decides and runs on the Python version `toolchain.env` pins. The gate (`run_gate_legs.py`): the `SELF-TESTS` audit is the one name in `TOOLING_ONLY`, `Host.audit_commands(tooling)` drops it otherwise, and the post-build self-tests (`filter_population.py`'s, which lists the built assemblies) start only when `out.tooling`. The audits are no longer a serial valley ahead of the slot: they are `_beside` work, started once the lane is known. The inert lane joins them at once (they are its whole gate). A full lane runs them beside the corpus fetch, the slot wait, the build, the listings and the legs; a red one is seen before the slot and again before the legs start (`NO LEG RAN`, fail-fast as before, PB2523), and one found while the legs run STOPS the leg hosts: `Host.run_leg` registers each host in `Host.legs_live` (the registry the audits already use), leading its own process group, `Host.stop_legs` kills the trees and any host that starts afterwards, and the gate ends RED naming the audit with the partial results not measured. `verdict.json` gains `assembly_wall_s`, `effective_concurrency` (the legs' summed wall seconds over the span the legs took) and `tooling`; additive, no schema bump. CI: `changes` gets a `tooling` output from the same `classify`, and `windows-self-tests` runs only when `run_matrix` and `tooling` are both true; the Linux `audits` job keeps every Linux self-test. A tooling-only diff still runs all the test legs, as today: the review's tooling lane without legs is step 5's lane.

**Step 7 (PB4330).** `audits` is `if: github.event_name == 'merge_group' || needs.changes.outputs.run_matrix == 'true'`: every merge group (not behind `run_matrix`, so a notes-only landing is still audited), and any other event only when its matrix runs, a dispatch run or a push no merge group verified. A pull request's run is `changes` + `ci-gate`; a verified push's adds only the two cache jobs. `toolchain-cache` on push was PB4324's; `package-cache` stays beside it because without it main would stop saving the NuGet packages and the GnuCOBOL tarball every matrix job restores. The DEVLOG step of `audits` runs on `merge_group` alone, with the group's `base_sha`; the `pull_request` arm of the shell case is gone with the pull request's run. The `changes` job's pull-request arm no longer computes a base, since nothing on a pull request reads it.

**What the re-probe showed.** Both notes described the base correctly (the `AUDITS` tuple carried `SELF-TESTS`, `BESIDE` held `post_build_self_tests`, `audits` had no `if`). Nothing to discharge. Not measurable here: the saved minutes show in the next merge-queue run, and the effect of audits-beside on the gate's wall in the next gate records (`timings.audits_s`, `legs_s`, the new `effective_concurrency`).

**Drift tests and self-test arms.** `run_gate_legs.py --self-test`: 78 arms PASS, five of them new (a red audit known before the slot, one that turns red while the gate queues for it, a red audit that stops running legs, the tooling and non-tooling gate, the audit list by lane, the record's `assembly_wall_s` and `effective_concurrency`); the fake host's `audits` is no longer an event of the main thread's order, and the arms that read that order read `["fetch", "slot", "build", ...]`. `InertLaneDriftTests` gains `TheScriptSelfTests_RunOnlyWhenTheChangeTouchesTooling_InCiAndInTheGate` and its audits-job test now holds the `if` and the absence of `pull_request`; `SelfTestDiscoveryDriftTests` pins `TOOLING_ONLY`; `GateLegDriftTests` declares the new arm names.
