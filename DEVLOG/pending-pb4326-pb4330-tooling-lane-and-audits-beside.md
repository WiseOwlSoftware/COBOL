## PB4326 + PB4330: self-tests only for a change that touches tooling, audits beside the build and the legs, and the audits run once in CI (pipeline redesign steps 3 and 7)

Steps 3 and 7 of the pipeline redesign PB4323 (owner 2026-10-31, PIPELINE-REVIEW.md section 10), one branch because both change `.github/workflows/build-and-test.yml` and the same lane decision. Neither is a defect: both remove work that measured nothing. A script self-test reads the scripts and a short list of data, yet every gate ran all of them (147 s median, reused or not) and then waited 145 s for the one that reads the built assemblies; CI's `audits` job, the same 5.7 minutes, ran on the pull request, again in the merge group and a third time on the push of the merge-queue commit.

**Step 3 (PB4326).** `scripts/inert_lane.py`, the one classification, gains the TOOLING flag: a full-lane change touches tooling when a changed path is under `scripts/`, `.github/`, `tools/`, `.claude/`, is `.gitattributes` or `toolchain.env`, or ends `.py`, `.ps1` or `.sh`. An empty or unlistable change touches tooling (nothing proves it does not); an inert one never does. `classify` prints `tooling=true|false`, `Lane` carries it, and the arms of `inert_lane.py --self-test` pin the paths. `.gitattributes` and `toolchain.env` are two paths the review's definition does not list; they are in because the Windows self-tests job checks the checkout bytes `.gitattributes` decides and runs on the Python version `toolchain.env` pins. The gate (`run_gate_legs.py`): the `SELF-TESTS` audit is the one name in `TOOLING_ONLY`, `Host.audit_commands(tooling)` drops it otherwise, and the post-build self-tests (`filter_population.py`'s, which lists the built assemblies) start only when `out.tooling`. The audits are no longer a serial valley ahead of the slot: they are `_beside` work, started once the lane is known. The inert lane joins them at once (they are its whole gate). A full lane runs them beside the corpus fetch, the slot wait, the build, the listings and the legs; a red one is seen before the slot and again before the legs start (`NO LEG RAN`, fail-fast as before, PB2523), and one found while the legs run STOPS the leg hosts: `Host.run_leg` registers each host in `Host.legs_live` (the registry the audits already use), leading its own process group, `Host.stop_legs` kills the trees and any host that starts afterwards, and the gate ends RED naming the audit with the partial results not measured. `verdict.json` gains `assembly_wall_s`, `effective_concurrency` (the legs' summed wall seconds over the span the legs took) and `tooling`; additive, no schema bump. CI: `changes` gets a `tooling` output from the same `classify`, and `windows-self-tests` runs only when `run_matrix` and `tooling` are both true; the Linux `audits` job keeps every Linux self-test. A tooling-only diff still runs all the test legs, as today: the review's tooling lane without legs is step 5's lane.

**Step 7 (PB4330).** `audits` is `if: github.event_name == 'merge_group' || needs.changes.outputs.run_matrix == 'true'`: every merge group (not behind `run_matrix`, so a notes-only landing is still audited), and any other event only when its matrix runs, a dispatch run or a push no merge group verified. A pull request's run is `changes` + `ci-gate`; a verified push's adds only the two cache jobs. `toolchain-cache` on push was PB4324's; `package-cache` stays beside it because without it main would stop saving the NuGet packages and the GnuCOBOL tarball every matrix job restores. The DEVLOG step of `audits` runs on `merge_group` alone, with the group's `base_sha`; the `pull_request` arm of the shell case is gone with the pull request's run. The `changes` job's pull-request arm no longer computes a base, since nothing on a pull request reads it.

**Review round 1, finding R1-1 (BLOCKING): the path-prefix proxy was refuted by the self-tests' own recorded inputs.** The first cut said a script self-test "reads only tooling". The PASS store (PB2914) says otherwise: `drift_rules.py`'s self-test reads `tests/_shared/TestRepo.cs` (it asserts `helpers['VersionMatrix'] == 'tests/version-matrix'` on the real file), `grammar_source.py`'s the `.g4` grammar, the orchestrator's self-tests `.agent-fleet.json`, the audits' `docs/CONFORMANCE.md` and `tests/version-matrix/`. A branch editing only `TestRepo.cs` classified as `tooling=false`, so the gate skipped `SELF-TESTS` and went GREEN, and the merge group's `audits` job then turned red (reproduced in a scratch copy). The fix is structural, not a longer prefix list: `inert_lane.py` gains `TOOLING_READS` (23 entries measured from the 145 stored records, each naming its readers), and `self_tests.py` PROVES the list complete on every run it records: `Classification.unclassified_reads` is applied to the self-test's traced reads, and a self-test that passes but read a tracked path that is neither tooling, a `TOOLING_READS` entry nor an INERT corpus is RED, naming the path, until it gets an entry. So the next case is automatic: the day a self-test reads a new path, the run that shows it fails and says which line to add. A full run on this Windows tree (137 self-tests, no reuse) was GREEN under the proof; the first Linux run (WSL clone of the head, 118 self-tests) was RED on exactly one, census.py reading LICENSE, which the proof named and which got its entry. The residue is named, not hidden, in `inert_lane.py` and DESIGN 3.18: a whole-tree reader (a self-test whose trace shows a git command over the whole repository; `test_plan_wave.py`, `test_dispatch_guard.py` and `impacted_tests.py` walk every markdown file or path, so no path list bounds them), the `DEVLOG/` and `kb/` corpora (every landing grows them, and `devlog.py check` and `work.py check` govern them in every lane), and a directory listing (names, not an edit of a listed file). Arms: `inert_lane.py --self-test` (two new on the proof, the tooling arm pins `TestRepo.cs`, the grammar, `.agent-fleet.json`, the inventory and `docs/CONFORMANCE.md`), `self_tests.py --self-test` (two new: an unclassified read is RED and records no PASS; a whole-tree reader is not judged), and `InertLaneDriftTests.TheToolingFlag_IsProvedAgainstWhatEverySelfTestRead_AndSeesTheDataItReads`.

**Review round 2, finding R2-1 (BLOCKING): the whole-tree exemption skipped every read of a self-test, not only its population.** `Runner._record` skipped the proof for any self-test whose trace showed a git command over the whole repository. Measured on the PASS store: of the 14 whole-tree readers, three read the tree as a population (`test_dispatch_guard.py` opened 12,726 files, `test_plan_wave.py` 14,492, `impacted_tests.py` 5,447) and the other four with non-tooling reads read a few specific paths: `work.py` `docs/DESIGN.md` (its site rule; a branch renumbering `## 0.5` there turns `work.py --self-test` red after a green gate), `merge_drivers.py` `Directory.Build.props`, `RuntimeAbi.cs` and `RuntimeAbi.pin`, and the steer and stop tests `docs/REARCHITECTURE_PLAN.md`. The fix is the structure, not a longer exemption: a self-test is exempt only when it DECLARES `# SELF-TEST-POPULATION: tree - <why>` in its first lines (the three population readers do), the declaration is held to the trace (declared and no whole-tree git read: RED, so a stale declaration never exempts a self-test unproved), and every other self-test, whole-tree git command or not, is judged on all its reads, so the five specific paths became `TOOLING_READS` entries (and edits to them now run the self-tests). Arms: `self_tests.py --self-test` replaces the "walker is not judged" arm with an undeclared walker RED, a declared one GREEN and recorded, a declaration the trace does not bear out RED, and the marker's parse; `inert_lane.py --self-test` pins the new entries. Docs: inert_lane.py docstring (a), self_tests.py docstring (POPULATION), DESIGN-test-build-ci 3.18, the comments in run_gate_legs.py and build-and-test.yml, PB4326.
