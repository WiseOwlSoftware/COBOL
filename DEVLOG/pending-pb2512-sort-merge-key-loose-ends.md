## PB2512: the MERGE key diagnostic quotes its own clause, the PB1173 key goldens break one rule each, and edition 85 refuses an occurs-depending key by determination

Three loose ends of the PB1924 SORT/MERGE key adjudication, taken together because they share `SortKeyAdmission` and its goldens (campaign PB3353).

**Re-probe on this build.** All three reproduced. `SortKeyAdmission.Violation` printed SORT 14.9.40.3 6) d) in the MERGE diagnostic, and the clause it cites (14.9.24.3 4) d)) has a comma before "or an item subordinate" that the SORT copy lacks (`cite.py --check` passes both, since it ignores punctuation). The PB1173 SORT/MERGE negatives declared USING and GIVING records of X(5) over SD records of 1 to 4 bytes, so each also broke the record-size rules (SORT SR5, SR11; MERGE SR3, SR12); the build checks the key first and stops, so the fixtures were refused for the key rule only by that ordering. The 85 build refused an occurs-depending group key while no golden asserted it.

**Fixes.**
1. `SortKeyAdmission.Violation` picks the d) quote per statement (a `switch` on the rule set, one arm each for SORT Format 2, MERGE and SORT Format 1). New golden `pb1173-merge-key-odo-group` pins the MERGE form including the comma; `pb1173-sort-file-key-variable-group` pins the comma-less SORT form.
2. Eight fixtures resize their USING and GIVING records to the SD record (X(2), X(3), X(4), X(1); X(8) for the two pointer fixtures, `DataItem.PointerByteWidth`, 13.18.60.4 GR23). Each was recompiled with the key swapped for an admissible one (clean), and a control with a wrong size was refused by SR5, so the key rule is the only fault. A sweep of every other SORT/MERGE negative in `diagnostics.json` found no other SD/FD mismatch. The SD/FD sizes of `pb1173-sort-file-key-dynamic-length` changed shape (a K1 byte and `LIMIT 3` on SK) so the variable-length range and the sizes agree. New negatives: the MERGE twins of the SR4 d) shapes (`pb1173-merge-key-odo-group`, `-merge-key-dynamic-length`, `-merge-key-variable-group`) and `pb1173-sort-file-key-variable-group`.
3. Edition 85: the repository holds no 1985 text, so this is a determination, not a derivation (`docs/CONFORMANCE.md` D-SKE): the arm stays ungated, `85` is added to `refuse-at` of both occurs-depending-group goldens, on the strength of the Micro Focus and Veryant references ("must not be variable length items"). If a holder of the 1985 standard shows no such rule, the arm becomes an edition gate.

4. Review round 1 (R1-1): the same mistake sat in `SortBinder.SortAddFileKeys` itself. Its key-not-in-record refusal and its two OCCURS-position refusals quoted SORT's "§14.9.40.3 SR6a" and "SR6b/SR6f" for a MERGE statement. `SortKeyAdmission.Clause(rules)` is now the one statement-to-clause map, read by `Violation` and by those three refusals, and they cite "SR6 a)" / "SR4 a)" and "b) and f)" in each statement's own rule. New goldens `pb1173-merge-key-not-in-record` (pins `SR4 a)`) and `pb1173-merge-key-boolean` (the SR4 c) boolean arm for MERGE, which had no witness); `pb1173-sort-file-key-not-in-record` now pins `SR6 a)`. R1-2: D-SKE records the GnuCOBOL 3.2 survey (accepts the key at every dialect, so no guidance) before resting on Micro Focus; Veryant is no longer cited.

**Owner test requirement.** The change is a compile-time refusal; the goldens cover each illegal key form the rules name for SORT Format 1 and MERGE with its diagnostic: OCCURS, class pointer, dynamic-length item, variable-length group and occurs-depending group for both; key outside the SD and class boolean for both since round 1 (SORT's goldens predate the branch). No runtime I/O path is reached.
