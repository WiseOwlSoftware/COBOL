## PB107: the collation engine's residue lands: quaternary relations, caseLevel, numericOrdering, a table build 12x cheaper, an allocation-free NFD; hiraganaQ left as one owner question

PB107 was the performance-review residue of the collation engine (PB104-PB106): three CLDR settings reported unsupported (`caseLevel`, `numericOrdering`, `hiraganaQ`), the `<<<<` relation applied as an identity, a ~6 ms per-locale table build, and an NFD that allocated 394 B on accented text. Each was re-probed on the build first; one root, `Runtime/Collation/`.

**The quaternary relation.** `ja` reported "116 quaternary (<<<<) relation(s) applied as identities" and `ぁー` vs `ァー` compared -1 where the host ICU compares 0. `CollationElement` gained `Quaternary` (0 on every root element); `CldrTailoringBuilder` got a fourth `Line` and a `BuildElement` slot, `<<<<` inserts a new slot after the anchor's instead of copying the position; `Collator` has a level 4 whenever the collation is Shifted or the table `HasQuaternary` (`WeightAt` level 4: the slot, or `MaxPrimary` + slot under Shifted). Hiragana now precedes Katakana at `-u-ks-level4` (JIS X 4061, the rule file's own comment) and stays equal through level 3, as ICU has it. The sibling found while there: `p|x` became the contraction p+x with p's elements read at the rule's moment, so ja's `ァ|ー` carried a stale ァ (ja.xml places ァ later, by `&ぁ<<<<ァ`); p's final elements are now read when the table is planned. That one was the -1 against ICU's 0.

**caseLevel.** `CollationOptions.CaseLevel`: a level of case alone between level 2 and 3, at any strength, with ICU's participation rule (a primary at primary strength, a secondary above), and the tertiary weight without the case prefix. `Collator.ActiveLevels` is now the one list `Compare` and `GetKey` walk (the ladder of `if (c != 0 || Strength == ...)` is gone), and `CollationKey` stores its levels by number. .NET's `IgnoreNonSpace` is primary strength plus the case level in ICU, which made an oracle: 1,444 pairs agree (a width-variant corpus pair excluded, .NET adds its own rules for those).

**numericOrdering.** A maximal run of General_Category Nd digits is one mapping, a number: a lead element where the digits stand, the count of significant digits, then the digits. The digit set is the table's own Unicode data, not the host's, so the generator writes the 77 runs of ten (format 3, checked to be blocks of values 0..9) and `CollationTable.TryGetDecimalDigit` reads them; the runtime reads format 3 only and the format 1/2 branches are deleted. The identical-prefix skip is off under it (a run straddles any boundary), and `PrefixShapeOf` sees the run as one mapping. 20,000 random pairs over digits of several scripts, letters, a mark and punctuation agree with .NET 10's `CompareOptions.NumericOrdering`. The one deliberate difference: ICU splits a run past 254 digits into numbers, so a 255-digit number sorts before a 254-digit one there; UTS #35 says numeric value, so here it is one number.

**The table build.** Measured stage by stage before choosing (115 builds of es/da/vi/cs/tr at 7.5 ms): the Builder constructor's scan of the 41,724-element base pool into hash sets and sorts 2.7 ms; the pool re-weighted through a delegate per element 1.8 ms; `Line.Number` visiting and allocating a Slot for each of ~25,000 roots ~1.5 ms; two `pool.ToArray()` 0.5 ms; copies and closure 0.7 ms. Fixed at those causes, not by either option the note listed (an overlay cannot share a pool whose weights renumber; tertiary headroom changes the numeric `.tailor` scale): the root lists are the BASE table's and computed once; `Line.Number` is sparse; `ElementRemap` re-weights through direct lookup arrays; `Rebuild` fills one array with spare room. Spanish 7.9 ms / 10.5 MB to 0.66 ms / 2.1 MB; a collation with no rules is the root table at 2 KB. All 143 locale tables (every pack file plus eight `-u-` variants) fingerprint identical before and after, over code points 0..2FFFF, every contraction, the groups, maps and counts.

**The NFD.** Pooled working arrays, `string.Create`, and a span form into the caller's `stackalloc` (a pooled char array past 128): 520 to 42 B per accented text, a mixed-script comparison 130 B to 0.

**hiraganaQ** stays reported, and is now the note's one question: CLDR marks `kh` deprecated, ICU 53+ ignores it, and doing it needs the Script property (Hiragana is not a block), which the pinned data lacks. Implement it (pin `Scripts.txt`, format 4) or decline it as a deprecated key is the owner's call, not a deferral by default.

Tests: `CldrCollationSettingsTests` (quaternary, case level, numeric ordering, the table's digits against the pinned UnicodeData), `NormalizerTests`, `CldrBuildCostTests` (allocation bounds, not clocks), the ICU cross-check gains the ja prefix/iteration pairs and a case-level test; the two tests that named `kn` as the unsupported example now use `kh`. The public API file records the new `CollationElement`/`CollationOptions`/`CollationKey` shapes. Self-review of the diff (architecture: one list of levels for compare and key, one table builder; full code: the rules cited are UTS #35 Part 5 and ICU's `compareUpToQuaternary`, sibling arms of `WeightAt` agree; performance: hot path adds one `foreach` over a 3-5 int array and a bool test in the iterator; duplication: the root lists exist once) found and fixed the stale-prefix defect above and nothing else open.
