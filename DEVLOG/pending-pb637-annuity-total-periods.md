## PB637: ANNUITY's argument-2 is a total integer; the standard-decimal body takes it as the SDIDI integer

FUNCTION ANNUITY under ARITHMETIC IS STANDARD-DECIMAL took argument-2 through the PARTIAL-function narrowing (`IntArg`, a `long` body). §15.9.3 r3 says only "Argument-2 shall be a positive integer", a sign and integer-ness rule, so a count past 9 223 372 036 854 775 807 is a legal argument and §15.3 r14 has no incorrect value to raise on. The probe on this tree reproduced the note: `ANNUITY(0, N)` with `N PIC 9(25) VALUE 10^20` stored 0 with checking off and terminated the run unit with EC-ARGUMENT-FUNCTION under `>>TURN EC-ARGUMENT-FUNCTION CHECKING ON`.

**Classification.** TOTAL, but not the way the adjudication read it. §15.4.1 r1 makes the standard-decimal returned value equal the value of the equivalent expression of §15.9.4. At rate 0 that is `1 / argument-2`, representable for every n (10^20 gives 1E-20). At a positive rate the expression's own `(1 + rate) ** n` leaves the decimal128 range once n·ln(1+rate) passes about 14 000, which is the expression's size condition (EC-SIZE-OVERFLOW, §8.8.1.5.2 r2, raised in `CobolDec.Pow`). The body already raised it at n = 10^6, inside `long`; the narrowing turned n = 10^20 into a different, width-dependent condition. The adjudication's expected 0.05 for `ANNUITY(0.05, 10^20)` is the mathematical limit and is overturned: the written expression has no value there. A small rate keeps a finite value (rate 1E-30, n 10^20 gives 1.00000000005E-20), which the narrow intake could not reach.

**Fix, and the branch review's correction of it.** The first fix widened the body to `AnnuityDec(CobolRounding, CobolDec, Int128)`. The branch review (R1-1, blocking) measured that an SDIDI integer reaches past `Int128` too: `RawArg` already holds the count unbounded on the SDIDI (`IntegerArgUnboundedDec`), and the `Int128` parameter made the renderer land it on `IntegerArgWideDec` and lift it back, so `ANNUITY(0, 10 ** 40)` still ended the run unit with EC-SIZE-OVERFLOW where `1 / (10 ** 40)` in the same program evaluates. The root is that ANY native integer carrier between the position intake and the body re-narrows the SDIDI value. The body is now `AnnuityDec(CobolRounding, CobolDec, CobolDec)` and the `Annuity` arm of `IntrinsicRenderer.RenderDec` passes `DecArg(ic, 1)`: the count rides the SDIDI end to end. Re-probed on this build: `ANNUITY(0, 10 ** 40)` and `ANNUITY(0, N20 * N20)` give 1E-40 and equal `1 / (N20 * N20)`. The other ANNUITY lane, the binary64 body, never narrowed. FACTORIAL's and COMBINED-DATETIME's `long` SDIDI bodies stay bounded.

**The guard was blind to it, twice.** `IntrinsicCarrierAgreementDriftTests.SingleCarrierIntrinsicBodies` paired a runtime body to its renderer arm by name, so no `…Dec` body (AnnuityDec, FactorialDec) was ever examined; it now maps `{Arm}Dec` onto the arm's entry. And its `Int128` pairing is the very claim the review overturned for an SDIDI-carried count, so `IntegerArgumentsThatRideTheSdidi_TakeNoNativeIntake` holds the closed set `SdidiIntegerArms` (ANNUITY) to the SDIDI form: the arm renders no `IntArg`/`IntArgWide`, the body has no `long`/`Int128` parameter, and a detector self-test carries the `long`, `Int128` and SDIDI arm texts. The `AsIntWide` doc comment and `DESIGN-runtime-library.md` say the same (review R1-3).

**Public surface.** `AnnuityDec`'s parameter type changed in `PublicAPI.Shipped.txt`, an incompatible change to the activation boundary: runtime major 17, `RuntimeAbiPinDriftTests` re-pinned to the hash the new signature prints.

**Goldens and tests.** `conformance:cases/15.9.3-Argument-rules/pb637_annuity_total_periods` (checking ON, armed by a non-positive count; 19-, 25- and 31-digit n; a 10^50 count past `Int128`; §15.4.1 NOTE 2's relation; the tiny-rate value; the size condition on both sides of the 64-bit window) and `pb637_annuity_total_periods_unchecked` (the silent-0 leg, with the 10^50 count). Both are accepted from 2014: the ARITHMETIC clause is a 2014 introduction (`tests/version-matrix/constructs.json` row `arithmetic-standard-decimal-2014`; review R1-2 caught the earlier 2023 rationale); no `reject-at` negative since no syntax is introduced. `CobolIntrinsicsDecTests.AnnuityDec_*` takes the count as a `CobolDec` (10^20, 10^38, 10^40). No inventory row was non-OK; `closes_rows` is empty with its reason on the note.

Gate: see the report; no diagnostic codes were used.
