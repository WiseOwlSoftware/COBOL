## PB637: ANNUITY's argument-2 is a total integer; the standard-decimal body takes it as Int128

FUNCTION ANNUITY under ARITHMETIC IS STANDARD-DECIMAL took argument-2 through the PARTIAL-function narrowing (`IntArg`, a `long` body). §15.9.3 r3 says only "Argument-2 shall be a positive integer", a sign and integer-ness rule, so a count past 9 223 372 036 854 775 807 is a legal argument and §15.3 r14 has no incorrect value to raise on. The probe on this tree reproduced the note: `ANNUITY(0, N)` with `N PIC 9(25) VALUE 10^20` stored 0 with checking off and terminated the run unit with EC-ARGUMENT-FUNCTION under `>>TURN EC-ARGUMENT-FUNCTION CHECKING ON`.

**Classification.** TOTAL, but not the way the adjudication read it. §15.4.1 r1 makes the standard-decimal returned value equal the value of the equivalent expression of §15.9.4. At rate 0 that is `1 / argument-2`, representable for every n (10^20 gives 1E-20). At a positive rate the expression's own `(1 + rate) ** n` leaves the decimal128 range once n·ln(1+rate) passes about 14 000, which is the expression's size condition (EC-SIZE-OVERFLOW, §8.8.1.5.2 r2, raised in `CobolDec.Pow`). The body already raised it at n = 10^6, inside `long`; the narrowing turned n = 10^20 into a different, width-dependent condition. The adjudication's expected 0.05 for `ANNUITY(0.05, 10^20)` is the mathematical limit and is overturned: the written expression has no value there. A small rate keeps a finite value (rate 1E-30, n 10^20 gives 1.00000000005E-20), which the narrow intake could not reach.

**Fix.** `CobolIntrinsics.AnnuityDec(CobolRounding, CobolDec, Int128)`; the count lifts as an SDIDI operand (`CobolDec.FromParsed`, §8.8.1.5.2 r1 rounds a count wider than 34 digits) and the `Annuity` arm of `IntrinsicRenderer.RenderDec` takes `IntArgWide`. The other ANNUITY lane, the binary64 body, never narrowed. FACTORIAL's and COMBINED-DATETIME's `long` SDIDI bodies stay bounded.

**The guard was blind to it.** `IntrinsicCarrierAgreementDriftTests.SingleCarrierIntrinsicBodies` paired a runtime body to its renderer arm by name, so no `…Dec` body (AnnuityDec, FactorialDec) was ever examined and the narrow SDIDI arm passed for the whole life of PB254/PB636. It now maps `{Arm}Dec` onto the arm's entry, pairs Annuity as wide, asserts the arm was examined, and its self-test carries ANNUITY's old and new arm text.

**Public surface.** `AnnuityDec`'s parameter type changed in `PublicAPI.Shipped.txt`, an incompatible change to the activation boundary: runtime major 17, `RuntimeAbiPinDriftTests` re-pinned (the first gate's only red).

**Goldens and tests.** `conformance:cases/15.9.3-Argument-rules/pb637_annuity_total_periods` (checking ON, armed by a non-positive count; 19-, 25- and 31-digit n; §15.4.1 NOTE 2's relation; the tiny-rate value; the size condition on both sides of the 64-bit window) and `pb637_annuity_total_periods_unchecked` (the silent-0 leg), both accepted from 2023 because the ARITHMETIC clause is; no `reject-at` negative since no syntax is introduced. Both ran in leg 1 and passed, with the six `CobolIntrinsicsDecTests.AnnuityDec_*` cases. No inventory row was non-OK; `closes_rows` is empty with its reason on the note.
