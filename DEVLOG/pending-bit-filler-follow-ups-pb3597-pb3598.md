## The implicit bit filler follow-ups of PB3564: a table pad is n - 1 items, a Tier-B canonical's run tail is stored, an ODO run's tail and a leaf-carried group's filler travel (PB3597, PB3598)

PB3564 gave the implicit filler after a USAGE BIT run a stored field and left five shapes as review leads (PB3597: two, PB3598: three). This change closes four and narrows the fifth. No inventory row is claimed or closed (both notes claim none).

**PB3597 lead 1 - REPLACING BOOLEAN over a table pad.** The repro (`INITIALIZE G WITH FILLER REPLACING BOOLEAN DATA BY B"1"` over `T PIC 1(3) USAGE BIT ALIGNED OCCURS 2` + `X PIC X`) aborted at run time by name. A pad is n - 1 elementary filler items (8.5.1.6.3), so both lanes now receive them in ONE loop over the gaps (`InitializeBinder.ExpandImplicitFillers`): the record-struct lane stores the pad as one string of every gap, so a gap is its reference-modified place (`PadGapPlace`, start `(v - 1) * gapBits + 1`); the class lane's gap is the first gap's item under the table's own occurrence displacement (`BitLayout.WindowFillersOf` now returns `WindowFiller`s: the first gap and the gap count). The class lane (PB3564 review R2-1) had been unrolled to one statement per gap: an EXTERNAL `T ... ALIGNED OCCURS 2000` generated 2095 lines (389 KB) of C#, now 100.

**PB3597 lead 2 - the run tail beside a Tier-B canonical.** `MOVE "AB" TO G` over `M1 PIC 1(2). M2 PIC 1(3). M2R REDEFINES M2 PIC 1(2). X PIC X.` read back `@` (0x40) for `A`: the tail was stored nowhere (the note said unreset; the move already lost it). Root: whether a position is a field or a window of a class's backing was decided per position (`FillerPosition.InClass`, true when any run member was in a class) when it is the OWNER's fact. The flag is dissolved into `BitLayout.InTierBClass(owner)`; `PhysicalModel` also declares the tail field after a class canonical that leads a run (`FillerFieldsOf`).

**PB3598 shape 3 - the leaf vector.** A strongly-typed group with a POINTER leaf crosses as a vector of its members; the filler was no member, so `MOVE V1 TO V2` left V2's filler (V1 `0xC0`, V2 `0x80`). The fillers now ride the vector after the members: `RecordStructEmitter.EmitLeafMethods` (one string per `FillersOf` entry) and `PlaceRenderer.CellLeaves` / `CellLeavesStore` (one per `WindowFillersOf` entry), enumerating the same positions in the same order.

**PB3598 shape 1 - a run holding an OCCURS DEPENDING table (the stored part).** The run now has a stored tail at its maximum count (`FillerPositions` no longer skips it; `HasFixedTail` is deleted): `MOVE "~~" TO G` at a count of 3 over a 1 TO 4 table of 3-bit items read `125` in the second character where the rule requires `127` (the two positions past the maximum extent were stored nowhere). The other half of the note's claim is a conflict, not a missing store: at a smaller count the filler that ends the current extent's last character lies in the first unused occurrence's storage, so the same bits are filler (data of the group, moved as characters) and an occurrence GR8 a) leaves unused, and the compiler's two receiving stores answer differently (an ordinary ODO group's splices characters: the sender's filler wins; `OdoTail.KeepUnused` splices at the first unused occurrence's bit: the occurrence wins, as `_unassigned/pb3030_bit_odo_run_continuation` and `_variable_group` pin). Splicing the second at the character was tried, turned both goldens and was reverted: it overturns a recorded determination and needs an owner decision (in the note).

**Not done (PB3598 stays open).** The padding of an element of a dynamic-capacity bit table: the element carrier is the boolean string every operation reads, so the pad needs a parallel column that follows every capacity change of `CobolDynTable`; it can become non-zero only through a READ of a variable-length record. And INITIALIZE ... WITH FILLER over an ODO run resets only the stored positions past the maximum, not the in-range filler. Both are in the note.

**Tests.** Goldens `14.9.20-INITIALIZE/pb3597_initialize_with_filler_replacing_boolean_in_a_table_pad` (three occurrences, so two gaps and a sender smeared over the stored pad fails; an explicit PIC 1(3) / FILLER PIC 1(5) record is the control), `pb3597_bit_run_tail_beside_a_redefines_canonical` (the canonical continuing, leading and followed by a bit item), `14.9.25-MOVE/pb3598_odo_bit_run_tail_travels_with_the_group`, three negatives below 2002 (COBOLNET0900), `BitRunImageDriftTests` BFL11-BFL13 (record-struct twin = aliased twin = the round trip), `LeafVectorFillerTests` (a unit test: the filler of a pointer-bearing group is portable only through DISPLAY, whose pointer positions are implementor-defined), and the existing nets re-run (the pb3030 / pb3156 / pb3167 / pb3158 / pb3564 goldens and the ODO unit tests). Re-probed before and after on each shape.

**Self-review.** Architecture: the storage law is one fact per owner (`InTierBClass`) instead of one flag per position; both lanes of a pad share one loop shape; the vector's two producers read one enumeration. Duplication: the two lanes of a pad share one loop shape; the two receiving stores of an ODO group still answer the filler differently (the open question in PB3598). Looked for and found: the class lane's unrolled gaps (fixed), the removed `InClass` flag's two readers (both updated), a determination in two pinned goldens that a character splice would have overturned (reverted, registered). Residual leads are in PB3598.
