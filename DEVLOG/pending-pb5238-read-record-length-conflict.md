## PB5238 retired: a READ inside the file's record sizes is not a record length conflict, whatever the reader's descriptions

The note held that a relative READ (and, by the held-rows addendum, the indexed and record sequential READ) of a record shorter than the smallest or longer than the largest RECORD DESCRIPTION must answer 04 (§1985:VIII.4.5.4 GR16, §1985:IX.4.5.4 GR18, §1985:VII.4.4.4 GR13, §2023:14.9.30.4 GR14). The re-probe reproduced it (`p16u.cob` at `--std 85`: `R1 00`, `R2 00`, `R3 00`).

I built the fix as the note directs: the descriptions' smallest and largest size reach the connector (`RegisterRecordDescriptionSizes`), one shared test replaces the clause-bound comparison, the keyed arm is edition-gated (the 2002 and 2014 texts state the rule for every organization, 2023 for record sequential only; VCR row 7.61). The probes then printed the 04s the note expects (`R1 04`, `R2 04`, `R3 00`) and the gate answered RED with 24 existing conformance tests failing, each a variable-length file whose records lie inside its RECORD clause and outside the description's size reading back 04 (`l1c23_record_varying_bounds_depending`, `pb721_zero_length_record`, `pb3350_read_previous_varying_span`, `open_fixed_attribute_conflict`, ...): the literal reading makes every short record of `RECORD VARYING 1 TO 80` over one `PIC X(80)` a conflict.

The text states the same condition twice, and the two statements disagree under that reading: GR14 measures against "the record description entries", but §2023:9.1.13.2 item 3 and §1985:VIII.1.3.4 item 1 b define 04 as a record outside "the fixed file attributes", §2023:9.1.6 makes "the minimum and maximum logical record size" such an attribute, and §2023:14.9.30.4 NOTE 2 says the condition occurs only when OPEN does not check the minimum or maximum as a fixed file attribute "or when a specific physical record within a physical file violates the fixed file attributes for that physical file". Reading "the record description entries" as the file's minimum and maximum record size (the RECORD clause's integers, which GR9/GR10 default from the descriptions) reconciles them, keeps what the 24 tests and the sequential connector already did, and leaves 04 to a record that violates the attributes, which a WRITE ('44') and an OPEN ('39') keep out of a keyed file. The note's own "reading to settle" paragraph named this tension.

So the fix was reverted (the branch history keeps it: commits 2ba5fe794e and b9fd5fb768), the note is retired with the reading recorded in `docs/CONFORMANCE.md` beside the '04' entry, and `conformance-suite/cases/14.9.30-READ/pb5238_read_inside_record_clause_is_no_length_conflict` pins it at every edition (relative and indexed, by key and in sequence, records of 7, 12 and 25 bytes inside a 6 to 30 clause under 10- and 15-byte descriptions: all 00; it turns red under the other reading). The note's citation for the descriptions lying inside the clause, §1985:VII.3.8.3 SR2 (Format 2), is correct (cite.py --check prints OK on its text); an earlier draft of this entry called it wrong, which the branch review corrected. No inventory rows closed (the inventory has no 1985 rows, PB5094).
