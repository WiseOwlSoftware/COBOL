## The operands of a declined facility's statement are read: VALIDATE and the MCS SEND and RECEIVE no longer swallow undefined names (PB3568)

Fuzz program fz02791 (`VALIDATE WS-ALPHA SETTING WS-STATUS`) compiled clean: SETTING is no word of the statement, so it is a third operand, and nothing named it. The cause was one level above the program: `StatementBinder.BindUnsupportedFacility` is the statement half of "accept inert", it returns a `BoundNop`, and nothing else ever read the parse subtree of VALIDATE (§14.9.50), of the MCS RECEIVE (§14.9.31) or of the MCS SEND (§14.9.38). Declining a facility licenses its behaviour to be absent (§4.2.6 ¶3, §4.2.7); the identifiers the statement names are still identifiers. The re-probe on a fresh build showed the note's three shapes (an undefined name, `VALIDATE WS-A (1:2)`, a POINTER operand) and the siblings the note had not measured: an undefined FROM or GIVING operand of a SEND or RECEIVE, an undefined name inside the statements of an `ON EXCEPTION` phrase, and an unknown `RAISING EXCEPTION` name.

A new collaborator, `DeclinedFacilityBinder` (under `Binding/Procedure/Verbs`), reads those subtrees and builds no node. VALIDATE: every identifier-1 resolves through the sending-side resolver (an undefined name is the ordinary COBOLNET1639) and is screened against the syntax rules of §14.9.50.3: SR1 (reference-modified, or not described in a section the rule lists: COBOLNET4777), SR2 (class index, object or pointer: COBOLNET4778) and SR4 and SR5 (a 66-level entry, ANY LENGTH: COBOLNET4779). SR3 reads a `VALIDATE-STATUS` clause that COBOLNET1708 already refuses, and SR6 is COBOLNET1607's. The reference modifier is read off the written reference, because a numeric item's reference modification is a shape the resolver defers and would otherwise slip past. MCS at 2023: the FROM, GIVING and RETURNING references resolve, the `CONTINUE AFTER` expression binds, the exception phrases' statements bind, and SEND's exception-name goes through the one exception-name funnel (COBOLNET0711 for an unknown name; an EC-MCS name keeps its accept-inert warning). The SEND `TO` operand is deliberately NOT resolved: Format 1 names a message-server-name, "the name of a message server run unit" (§14.9.38.3 SR2), which is no data item, and the grammar cannot tell it from Format 2's message-tag. The message-tag class checks have no item to refuse while USAGE MESSAGE-TAG is itself refused (COBOLNET1943). A deferred reference shape, a legal operand whose storage place this compiler has not built, is taken back off the unbuilt-operand ledger: the statement is inert, so the funnel's "reaching this statement aborts the run unit" would be false.

The shape that makes the next declined statement automatic: `StatementBinder` routes every `BindUnsupportedFacility` call through a `BindDeclined…` method that reads the operands first, and the new `DeclinedFacilityOperandDriftTests` fails a recognize-and-name call outside one, and a declined statement rule whose `dataReference` count differs from the adjudicated roster (VALIDATE 1, RECEIVE 3, SEND 3 of which 2 resolve, with the reason for the third). The deep-dive reading is `docs/CONFORMANCE.md` §4 items 1 and 3, which now say so.

Goldens: eight refusals in `conformance-suite/cases/14.9.50-VALIDATE/pb3568-validate-*` (undefined, reference-modified, report-section item, pointer, index, object reference, 66-level, ANY LENGTH), each refused at 2002, 2014 and 2023; the control `wiseowl/cases/14.9.50-VALIDATE/pb3568-validate-legal-operands-inert` (a group, a qualified item, a subscripted element: only the COBOLNET1580 warning, and the run is inert); four 2023 refusals under `wiseowl/cases/14.9.31-RECEIVE` and `14.9.38-SEND`. Writing the control caught the compiler working: the first draft's DISPLAY line ran past column 72 and the now-resolved qualifier read `SECOND-RE`. The four VALIDATE syntax-rule inventory rows (SR-14.9.50.3-1, -2, -4, -5) gain the new witnesses and keep their DOCUMENTED-NON-SUPPORT verdict: the facility is still declined, so the landing closes no row.
