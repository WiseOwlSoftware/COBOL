## PB3109: the lock-file host's lock directory is renamed away before it is deleted, so a waiting region-lock hold no longer answers Unavailable on Windows

PB3109 (runtime/io-sharing, MAJOR, wrong answer and silent) bounced PR 19 out of the merge queue: `RegionLocksDriftTests.TwoWaitingHoldsBothGetTheByteInTurn(kind: LockFiles)` read `Expected [Ok, Ok] Actual [Unavailable, Ok]`.

**Re-probe.** On this build's pre-fix `Cobol.Net.Runtime.dll`, the PB2690 harness shape (two endpoints, a barrier, waiting exclusive holds, one CPU burner per core, first-chance exceptions attributed to the first runtime frame): NTFS 11 of 3,000 rounds answered `Unavailable`, with exactly 11 `UnauthorizedAccessException 0x80070005 at HostFile.OpenLockHolder`; ReFS 2 of 8,000. One correction to the note's account: on this Windows (build 26300) `RemoveDirectory` on NTFS has POSIX delete semantics, so a directory deleted while another handle is open vanishes at once; the delete-pending state the harness's shape (a) builds with the legacy `FileDispositionInfo` is not what the runtime meets. What it meets is the window inside its own `RemoveDirectory` against a racing `CreateNew`, which needs no other handle.

**Fix.** `SidecarLockFiles.LockFileHolder.Dispose` deleted the empty lock directory in place. `SidecarLockFiles.RetireDirectory` is now the one place a lock directory is removed, and it treats the directory as `Retire` (PB2917) treats a lock file: where share modes are mandatory an empty directory is renamed to `.wolk-gone-<guid>` and only that name is deleted, so no name a publisher or tester enters is ever deleted in place and "access denied" on the lock directory stays a decisive answer. A directory with entries, or one the host will not move while a holder's file is open (measured: `0x80070005`), stays standing; a publisher that resolved the old name meets `DirectoryNotFoundException`, which `Publish` already retries. Elsewhere it is deleted, an unlink being atomic. Leaving the directory standing on Windows was rejected: it would litter a `.wolk-*` directory beside every file ever opened there. The residue of a kill between the rename and the delete is one empty `.wolk-gone-` directory. After the fix, the same harness: NTFS 0 of 3,000, ReFS 0 of 8,000, no `UnauthorizedAccessException` at `OpenLockHolder`, nothing left behind.

**Witnesses.** The race cannot be made to happen on demand, and a witness that holds a share-delete handle across the CLOSE passes before and after (measured), so the witness reads the order the host reports: `DirectoryNameWatch` watches the parent directory and `RegionLocksDriftTests.TheLastHoldersCloseRenamesTheLockDirectoryAwayRatherThanDeletingItInPlace` and `SidecarColumnLockHostDriftTests.TheLastHoldersCloseRenamesTheLockDirectoryAwayAndTheNextOpenIsGranted` assert that the lock directory's name went by a rename to `.wolk-gone-` and never by a deletion under its own. Both are red on the old `Directory.Delete` and green after, in classes already carrying `[Trait("Host", "ReFS")]` (leg 1, tier 0h). The note's shape (a), a frozen legacy deleter at the lock directory's own name, is not witnessed: no consumer can tell a delete-pending directory from a permission-denied one (PB2917), so no fix that keeps "access denied" decisive can make it pass; the fix removes the runtime's own source of the state.

**Docs.** `SidecarLockFiles` class remarks and `docs/rearchitecture/DESIGN-runtime-library.md` (the lock-file primitive paragraph) state the rule for the directory beside the one for files. No inventory row is claimed or closed (`closes_rows_reason` says why).
